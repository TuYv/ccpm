# Android 基准测试对比

## 核心原则

将物理 Android 配置对比视为可复现的实验：
在解读排名或选择默认配置之前，先验证工作负载和设备条件是否可比。

## 流程

1. 说明决策、配置、工作负载、指标定义和重复次数。保留准确的构建标识、配置、原始结果和跟踪记录；然后验证每个预期案例和迭代是否都已运行。区分缺失、失败和排除的运行；不要只比较最快的幸存结果。
2. 控制并记录相关设备条件，包括设备型号和状态、温控与电源模式、显示亮度、后台负载，以及网络或输入条件。将设备专用命令和 CPU 掩码保存在项目运行手册中。
3. 平衡或反转运行顺序，并重复比较。报告结果的离散范围以及运行顺序是否保持；不要在看到结果后丢弃较慢的迭代。
4. 当排名反转或变异性较大时，先进行调查再做决策。使用跟踪记录检查测量区间以及可能的原因，例如 CPU 放置、争用或温度状态。固定性能设置并不能证明 CPU 放置情况。如果使用 affinity，请发现设备拓扑，在测量跟踪区间内验证放置情况，将结果标记为受控对比，并在之后恢复设备设置。
5. 根据未四舍五入的观测值计算汇总结果，然后仅在展示时进行四舍五入。明确说明聚合方式：逐次运行百分位数的平均值并不是合并观测值的百分位数。选择能够回答既定决策问题的聚合方式；不要普遍规定使用某一种统计量。
6. 将受控实验的证据与普通用户性能区分开来。如果多个条件同时发生变化，应将该比较报告为控制程度更高，但不要将其全部差异归因于某一个控制因素。使用 CPU 帧耗时证据为视觉质量/性能决策提供参考，但不要声称它测量了 GPU shader 时间。
7. 最后给出原始证据的位置、已完成案例的计数、变异性、跟踪发现、控制和恢复状态，以及有界决策或剩余不确定性。

## 边界

- 单次稳定的基准测试运行可以支持范围狭窄的观察，但不足以支持稳健的配置排名。
- 不要将设备特定的 CPU 掩码、亮度值、迭代次数或汇总统计量转化为永久默认值。
- 当跟踪记录或重复覆盖无法解决排名反转时，保持默认配置不变，或明确说明该限制后做出临时决策。
