# 综合研究智能体最佳实践

此技能旨在解决多步骤研究任务中的常见问题：未处理的工具错误、缺少验证、推理过程不透明以及过早得出结论。它提供了结构化的来源验证、错误恢复和思考透明度协议，可显著提高研究质量与可靠性。

## 何时启用

- 任务涉及使用 search、read_url 或 fetch 操作开展网络研究
- 任务需要从多个来源收集信息
- 任务对完整性或验证有明确要求
- 任务包含需要验证的文件操作（save、write、read）
- 任何需要进行 3 次以上工具交互的研究或信息收集工作流

## 核心概念

- 验证检查点：在阶段转换时执行明确的验证步骤，以确认工具输出、来源相关性和信息完整性，然后再继续
- 错误恢复协议：必须确认并处理工具故障，采用后备策略，而不是在不作说明的情况下继续
- 来源可追溯性：清晰跟踪哪些来源已被实际获取，哪些来源仅引用自既有知识，以防止产生幻觉
- 实质性思考块：详细记录每一步的洞见、关联、缺口和决策依据
- 跨来源验证：通过多个来源验证关键主张，并明确指出共识、矛盾和信息缺口

## 应避免的模式

- **静默忽略工具故障**：工具调用返回错误（404、超时、无效 URL），但智能体未予确认便继续执行，可能因此遗漏关键信息。始终记录故障，并尝试恢复或说明存在的信息缺口。
- **含糊的完成声明**：智能体在未说明学到了什么、哪些来源支持相关主张或仍存在哪些缺口的情况下，便宣称“我已有足够的信息”或“研究是全面的”。应改为提供具体的覆盖情况总结。
- **未经验证的来源选择**：智能体直接读取搜索结果中的 URL，而未先评估其相关性、可信度或时效性。这会将工具调用浪费在低质量来源上。在深入阅读之前，始终对来源进行排序并确定优先级。
- **泛泛的思考块**：思考内容仅包含对下一步操作的描述（“现在我将搜索 X”），而未分析已获得的知识、这些知识与目标之间的联系，或仍有哪些问题有待解决。思考应当具有实质性和反思性。
- **验证方法错误**：使用 list_directory 验证文件创建情况可能会因缓存而产生假阴性结果。始终使用 read_file 验证实际文件内容。
- **引用未获取的来源**：在最终报告中引用从未成功获取或读取的来源（URL、论文标题）。明确跟踪来源，并禁止引用未获取的内容。
- **冗余工具调用**：执行相互重叠的搜索，或在未跟踪已获取内容的情况下读取来源。维护一个“已发现资源”跟踪器，以避免重复。

## 推荐实践

- **实施阅读前的来源评估**：在读取 URL 之前，根据相关性、可信度、时效性和权威性对搜索结果进行排序。在思考块中记录选择依据。
- **使用结构化思考块**：每个思考块必须包括：(a) 从来源/操作中了解到的内容，(b) 这些内容与研究目标的关联，(c) 发现的任何矛盾/空白，(d) 所做的策略决策。避免使用泛泛的后续行动陈述。
- **强制确认错误**：当任何工具失败时，下一个思考块必须明确说明该问题：注明失败类型，提出恢复策略（重试、使用替代来源或记录空白），并解释所选择的方法。
- **创建完成前验证清单**：在宣布研究完成之前，验证：所有必需章节均有具体证据、所有来源均已成功检索、关键论点已交叉验证，并且所有空白均已记录。
- **实施跨来源验证**：从多个来源收集信息后，明确比较研究结果。注明各来源在哪些方面一致、在哪些方面相互矛盾，以及哪些内容仍未经验证。以此评估总体可信度。
- **维护来源跟踪表**：在思考中创建一个简单表格，说明哪些 URL 已获取、哪些获取失败，以及哪些 URL 被用于支持特定论点。切勿引用未检索到的来源。
- **使用 Read_File 进行验证**：确认文件写入时，使用 read_file 验证实际内容，而不是使用 list_directory，因为后者可能存在缓存问题并导致误报。
- **添加明确的验证阶段**：读取来源后，先撰写一段简短的综合说明，确认其有用性，指出其与研究目标的相关性，并确定仍然存在的空白，然后再进入下一阶段。

## 指南

1. 每次工具调用后，明确检查响应中是否存在错误，并在下一个思考块中确认失败情况及恢复策略
2. 在读取 URL 之前，根据相关性/可信度对来源进行排序并记录选择依据——绝不在未评估的情况下读取结果
3. 思考块必须至少包含 3-5 句，并包括：了解到的内容、与目标的关联、空白/矛盾以及后续步骤
4. 创建完成前检查清单，验证：所有要求均已覆盖、来源均已检索、论点均已验证、空白均已记录
5. 维护来源跟踪记录——仅引用已成功获取的 URL；禁止引用未检索到的来源
6. 撰写最终报告时，加入“局限与空白”章节，记录已尝试但失败的事项或仍未经验证的内容
7. 保存操作后，使用 read_file（而非 list_directory）验证文件内容
8. 尽可能通过至少 2 个来源对关键论点进行交叉验证；明确指出共识或矛盾
9. 跟踪已收集的信息以避免重复搜索——为多阶段研究实施“已找到资源”跟踪器
10. 将含糊的“全面”陈述替换为具体总结：“涵盖了关于 Y 主题的 X 个来源；缺少 Z 方面的内容”

## 示例

- ***之前（反模式）**：'我搜索了上下文工程并找到了一些结果。现在我要阅读一些 URL，然后撰写报告。我已经掌握了足够的信息，可以继续。'

**之后（正确模式）**：'搜索返回了 15 条关于上下文工程的结果。正在评估相关性：Liu 等人（2024）关于“中间信息丢失”现象的研究似乎最具权威性；Anthropic 文档可能包含最新的上下文窗口规格；Patel（2023）介绍了 RAG 最佳实践。将这些结果列为优先级最高的 3 项。首先阅读排名第一的结果。如果主要来源失效（URL 错误），则会通过备用搜索查找正确的文档 URL，并在最终报告中注明这一信息缺口。'
- ***之前（反模式）**：工具在访问 Anthropic 上下文窗口 URL 时返回 404 错误。智能体没有说明该问题便继续执行。之后引用“Claude 拥有 200K 上下文窗口”时未提供来源。最终报告引用了一篇从未获取过的 Google Research 论文。

**之后（正确模式）**：工具在访问 Anthropic URL 时返回 404。思考：'主要来源失效。后备方案：搜索其他 Anthropic 文档 URL，或查找存档版本。如果无法获取，则仅注明来自二手来源的上下文窗口数据，并添加有关验证状态的免责声明。' 随后：'已交叉验证 Claude 上下文窗口：Anthropic 博客（已成功读取）和两个开发者文档来源均确认其为 200K。对此结论有信心。' 来源跟踪表显示：Anthropic URL（失败，已使用备用来源）、博客（成功）、开发者文档（成功）。

## 分数预期

涉及多个工具（6 个以上）和多步推理链的复杂研究任务通常能获得 **65-75 分**。这并非提示词本身的限制，而是由以下因素造成：

- 工具输出固有的可变性会影响推理路径
- 多种有效方法会产生不同的中间分数
- 长周期智能体执行具有随机性

**应重点关注相对改进和消除反模式**，而不是绝对分数。对于复杂任务，通过优化获得 5-10% 的提升已相当显著。
