# 评估 React Native 迁移

产出一份只读的迁移决策。诊断产品和交付系统；不要执行迁移。

## 确定产品范围

从一个能向代理提供尽可能多生产客户端代码库的工作区开展评估。当前检出的代码不能证明其中包含整个产品。

在评估就绪程度之前：

1. 检查当前仓库以及代理可用的每个工作区根目录。
2. 根据产品文档、CI、发布配置、工作区清单、子模块以及对同级仓库的引用，推断支持的客户端平台。
3. 找到每个生产客户端代码库，包括独立的原生 iOS 和 Android 仓库、应用变体，以及任何与人员配置或拟议代码共享相关的 Web 客户端。
4. 记录一份平台清单，其中包含客户端、仓库或路径、产品归属证据和访问状态。

如果同时支持 iOS 和 Android，请先检查两个原生代码库，再推荐路径。如果某个代码库仍不可用，请将其证据标记为 `unknown`，说明评估仅覆盖可访问的平台，并相应降低置信度。不要仅仅因为当前仓库中缺少某个平台的项目，就推断该平台不受支持。

**范围门槛：**已列出所有受支持的生产客户端，并且每个代码库均可访问、明确不可用或经确认不存在。

## 首次响应门槛

当尚未通过范围门槛时，首次响应必须严格为：

```markdown
**Question:** Where can I access the production codebase for each client platform this product supports, including iOS and Android if both exist?

**Why it matters:** A migration path based on only one platform can miss native dependencies, product behavior, and delivery constraints that change the decision.
```

通过范围门槛后，如果仓库证据不可用，应深入追问，而不是泛泛调查。

如果可衡量的迁移驱动因素未知，首次响应必须严格为：

```markdown
**Question:** What measurable delivery or business problem should a React Native migration solve?

**Why it matters:** This determines whether migration is relevant and which outcomes the assessment must test.
```

如果驱动因素已知，则仅使用相同的两行格式询问下一个影响最大且尚不明确的问题。在问题和理由之后立即结束本轮响应。不要添加开场白、调查问卷、建议或实施指导。

## 规则

- 将每个生产应用都视为事实依据，包括未记录的行为。
- 在提问之前，检查可用的代码、CI、测试、发布配置、产品文档和运行时证据。
- 当 iOS 和 Android 在实现、行为、依赖项、交付或路线图方面存在差异时，明确比较两者。
- 仅基于每个受支持平台的证据提出产品级结论，否则应限定其平台覆盖范围。
- 将重要结论标记为 `observed`、`measured`、`reported`、`assumed` 或 `unknown`。
- 根据证据提出建议，而不是依据汇总的就绪度评分。
- 默认收集证据，而不是默认采用棕地、绿地或迁移本身。
- 负责决策阶段。在 Path A 被接受之前，不要应用实施技能，也不要选择 Expo 或 bare React Native。
- 仅计算 React Native 相对于当前原生系统的边际价值。
- 通过已接受且经过验证的工作来衡量代理，而不是根据 token、生成的代码或 pull request 数量。
- 不要对工期、成本、代码共享、代理生产力或 ROI 作出普遍性断言。

## 选择证据模式

当源代码或交付产物可用时，采用基于代码仓库的评估：

1. 完成平台清单，并确定评估可以检查哪些代码仓库。
2. 对于每个可访问的移动端代码库，定位应用变体、CI、测试、发布配置、架构记录和产品文档。
3. 在每个原生代码库中搜索 SDK、权限、应用扩展、存储、身份验证、推送、深度链接、分析、实验和平台特定行为。
4. 引用代码仓库名称、文件路径和行号，以便在代码库相互独立时仍可追溯证据来源。
5. 仅就缺失的代码库位置，或代码仓库无法确定的产品、组织和运营事实向利益相关者提问。

当代码仓库不可用或仍缺少重要证据时，采用访谈评估：

1. 从可衡量的交付或业务问题开始，除非用户已经提供了该问题。
2. 每轮只提出一个会影响决策的问题。
3. 用一句话说明答案会影响哪条路径、哪项风险或哪项假设。
4. 对模糊或矛盾的回答，使用范围更窄的后续问题进行质疑，而不是将其作为证据接受。
5. 记录答案，更新证据状态，并选择下一个影响最大的未知项。
6. 当继续获得答案已无法改变建议、置信度或检查点时，停止追问。

在通过证据门槛之前，每次回复必须仅包含：

```markdown
**Question:** [one question]

**Why it matters:** [one sentence]
```

在这些轮次中，不要包含问卷、路径建议、检查点或实施指导。如果用户暂停访谈，请返回当前证据状态和影响最大的单个未知项，不要假装评估已经完成。

**访谈轮次门槛：** 已请求一个答案，已明确其对决策的影响，并且没有出现第二个问题。

## 1. 收集决策证据

说明决策、截止日期、当前替代方案和可衡量的驱动因素。对框架的偏好不是驱动因素。

检查以下维度：

| 维度 | 最低证据要求 |
| --- | --- |
| 产品 | 支持的平台、应用变体、共享与平台特定的路线图、关键流程、无障碍、分析和边界情况 |
| 原生能力面 | SDK、模块、权限、后台工作、应用扩展、支付、硬件 API、自定义渲染以及可行的 React Native 实现路径 |
| 连续性 | 身份验证与会话、安全存储与持久化存储、推送令牌、深度链接、订阅、已安装用户的更新、法律、安全和离线约束 |
| 验证 | 可复现构建、测试账户、手动与自动化 QA、设备控制、原生参考证据、性能基线和独立审查 |
| 发布 | 当前发布节奏与恢复能力、内部分发、功能开关、实验、应用商店分阶段发布，以及期望的二进制发布通道与可选的 OTA 通道 |
| 责任归属 | 决策权限，以及产物、功能对等、原生边界、共享基础能力、验证和发布的负责人 |
| 智能体治理 | 获批的模型与源代码边界、受保护的密钥与测试数据、最小权限访问、证据留存、审计跟踪，以及由人工进行的架构和发布审批 |
| 交付基线 | 重复实现与审查、等待与交接、功能对等差距、双平台验证、发布指标、缺陷、返工和维护成本 |

对于依赖 OTA 的方案，必须明确负责人，并制定运行时兼容性、发布、可观测性、回滚或重新发布以及审计策略。仅仅具备 OTA 能力并不能算作迁移收益。

组建一个精简的迁移核心团队，将现有的产品与原生技术知识同 React Native 迁移专业能力结合起来。只询问那些缺失且可能改变决策的事实；其余内容均以假设形式明确列出。

**关卡：**每个维度都有证据或明确标记为未知，并且所有会阻碍路径选择的未知项都已明确指出。

## 2. 选择路径

选择一种结果，并说明其他方案为何不合适。

| 结果 | 适合推荐的情况 |
| --- | --- |
| **路径 A：棕地迁移** | 发布连续性或已安装用户的使用连续性最为重要、与原生代码深度耦合、各流程可以独立迁移，或者整款应用一次性切换的风险不可接受。应计入宿主边界和双重架构的成本。 |
| **路径 B：绿地迁移** | 行为可以恢复，原生依赖有可信的替代方案，连续性可以得到验证，验证能力强，并且在完成替换之前可以控制遗留范围。 |
| **路径 C：绿地优先检查点，并以棕地迁移作为后备方案** | 绿地迁移能提供更简单的目标架构，但仍存在重大不确定性，并且在扩大迁移规模之前，可以证明已完成的 React Native 工作能够在原生宿主中运行。 |
| **推迟** | 商业理由看似合理，但缺少证据、验证能力、责任归属、预算或发布准备。明确最小化的准备工作和重新启动决策的条件。 |
| **不迁移** | 原生系统已经能够实现预期成果，移动端重复交付的问题并不严重，路线图在不同平台间并不对称，平台专属工作占主导地位，或者经风险调整后的回报缺乏可信度。 |

将路径 C 视为 Callstack 在 2025 年之后逐渐形成的运营模式，而不是行业基准。智能体访问能力使行为移植更具可行性；只有针对本产品进行量化检查，才能确定实际速度和质量。

路径 A 获得认可后，将实施规划移交给 [react-native-brownfield-migration](../react-native-brownfield-migration/SKILL.md)。不要重复其中关于 Expo、XCFramework、AAR 或宿主集成的指导。

**关卡：**有决定性证据支持某一种结果，拒绝其他方案时给出了理由，并且置信度与证据质量相符。

## 3. 定义具有代表性的检查点

对于路径 C，以及任何一个不确定因素可能导致推荐路径失效的情况，都应使用检查点。采用由组织提供的固定日历周期和工作量预算。选择两到三个垂直流程：

1. 一个涵盖 UI、数据、分析和导航的常见流程。
2. 一个经过身份验证且有状态的流程，涵盖持久化、错误和会话行为。
3. 最有可能证伪该方案的边界，例如原生 SDK、后台任务、硬件 API、离线行为、应用扩展、无障碍要求或低端 Android 设备限制。

将每个流程与原生源代码参考、运行时证据、负责人和对等场景关联起来。不要只选择简单的页面。

根据现有产品定义可衡量的验收标准：

- 行为、状态、验证、错误、分析、无障碍和视觉输出与原生参考实现一致。
- 身份验证、存储、深度链接、推送和选定的原生边界可在要求的设备和操作系统版本上正常工作。
- 启动、交互、内存和崩溃行为达到约定的基线或容差。
- CI、内部分发、可观测性和预期的发布通道足够可靠，可以继续推进。
- 每个流程都有设备级证据，并经过上下文无污染的独立审查。
- 路径 C 能够打包，并能在每个要求的原生宿主中打开至少一个具有代表性的 React Native 流程。

对至少一个流程执行两轮工作：

1. **忠实实现轮：** 保留行为、分析、无障碍、状态和边缘情况。记录为保持一致性而保留的原生形态架构。
2. **惯用实现轮：** 引入 React 组件组合、清晰的状态边界、类型化导航、可复用原语、合适的测试和经过测量的性能。重复执行一致性和设备检查。

在扩大规模之前，为 `MIGRATION.md`、`SCREENS.tsv`、`STATE_AND_STORAGE.tsv`、`DEPENDENCIES.tsv`、`EVENTS.tsv` 和 `PARITY_CHECKS.md` 指定负责人。在评估期间，应识别缺失的产物，而不是创建完整清单，除非用户明确要求。

最终必须作出一个决定：继续绿地开发、继续路径 C、将已完成的工作转入路径 A、推迟或停止。不要仅仅因为检查点的结果不理想就延长检查点。

**门槛：** 流程、预算、标准、证据、负责人和终局决策均已明确。

## 4. 测试经济性

将一项具有代表性的变更从可实施状态映射到在两个平台上经过验证的可用状态。记录两个时间周期：

1. **变更交付周期：** 从提交到产物可供生产用户群使用；分别记录二进制交付和 OTA 交付。
2. **跨平台功能交付周期：** 从可实施状态到在 iOS 和 Android 上经过验证的可用状态。

计算潜在回报，包括减少重复实现和业务逻辑审查、降低一致性协调成本、提升工程师流动性，以及经过测量的发布或恢复改进。模型中仍须包含 iOS 和 Android 设备验证。除非单独获得资金并完成评估，否则不要将 Web 融合作为基准情形的一部分。

计算全部投入：检查点、双轨维护、原生模块、培训、惯用实现的第二轮工作、测试和设备自动化、可观测性、发布基础设施、平台所有权、切换，以及原生界面退役。

不要虚构回报周期的输入数据。当所提供的数据存在不确定性时，使用范围值。当验证和边界工作耗尽预期节省、原生界面持续增加、双轨维护没有明确的退役期限、智能体只增加返工却未带来经过验证的吞吐量提升、一致性有所改善但交付没有改善，或释放出的产能没有规划用途时，应修订、推迟或停止。

**门槛：** 可以比较边际收益与全部投入，且不把双平台验证视为已消除的工作。

## 输出契约

仅在通过证据门槛后，或用户结束访谈时，才使用此契约。

按以下顺序返回一份简明报告：

1. **建议：** 结果、置信度、决定性理由和决策边界。
2. **证据：** 平台清单、覆盖范围限制，以及重要发现，包括来源状态和平台差异。
3. **假设与阻碍因素：** 按对决策的影响程度排序的未知项。
4. **检查点：** 预算、流程、标准、负责人、证据和终止性决策。
5. **基线与 ROI：** 已测量的输入、缺失的输入、计入的回报、全部投入和排除项。
6. **下一项决策：** 由谁、依据哪些证据、在何时决定什么。

结论应保持诊断性质。如果涉及执行，仅说明编排、任务契约、提示词、重试规则和私有智能体需要根据具体项目确定。绝不披露或虚构私有实现材料。
