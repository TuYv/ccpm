# 供应链风险审计器

为项目的直接依赖（npm、PyPI、Go）生成一份供应链风险报告，并对其 lockfile 解析到的全部内容执行安全通告扫描。测量由两个确定性脚本完成；你的工作，则是它们拒绝自动化的那部分判断。

## 为什么测量由脚本完成，而不是你

报告中的每一个数字都是对他人项目的断言，而在本技能围绕脚本重构之前，人工收集的数字曾被测错：GitHub 的贡献者计数显示有五人以上在维护 `lodash`，而 npm 的 ACL 显示只有一人；`gh` 显示某个每周下载量高达 1.64 亿的包下载量为零。不要通过 `gh`、网络搜索或记忆来估算维护者数量、下载量、陈旧程度或 CVE 历史——运行采集器，并引用它测得的结果。

在阅读脚本输出之前，有两条由脚本强制执行的规则值得了解：

- **不可用的数据绝不是风险证据。** 每项评估标准都会归结为 assessed-clean（评估为无风险）、assessed-flagged（评估为标记）或 unassessable-with-a-reason（附原因的无法评估）三种结论之一。
- **缺失的测量绝不等于无风险的结论。** 一次什么都没测到的运行会以非零状态退出，而不是打印一份“未发现任何问题”的报告。

## 工作流程

1. 确认目标目录中存在清单文件：`package.json`、`pyproject.toml`、`requirements*.txt` 或 `go.mod`。如果都不存在，如实说明并停止——不要对该采集器不解析的生态系统进行手工审计。会被读取以获取精确版本并执行传递依赖扫描的 lockfile 包括：`package-lock.json`/`npm-shrinkwrap.json`、`uv.lock`，以及 go 1.17+ 的 `go.mod`。`yarn.lock`、`pnpm-lock.yaml` 和 `poetry.lock` 不会被读取——报告会在它们存在时说明这一点，版本信息则回退到固定版本或最新发布版本。
2. 检查 `gh auth status`。未认证的 GitHub 每小时仅允许 60 次请求，而认证后为 5,000 次，且采集器对每个依赖都会发起多次请求；若缺少认证，预期仓库类标准将返回无法评估。请如实说明这一点，而不是悄悄地把它修复。
3. 先采集，再渲染。除非另有要求，将输出放在被审计仓库之外的某处：

   ```sh
   uv run {baseDir}/scripts/collect.py <project-dir> --json <out-dir>/findings.json
   uv run {baseDir}/scripts/render.py <out-dir>/findings.json --out <out-dir>/report.md
   ```

   约 50 个依赖预计耗时几分钟——每个依赖若干次 HTTP 请求，Go 模块较多时更多，未认证 `gh` 时更慢。如果 `collect.py` 以非零状态退出，表示它拒绝出具报告——请逐字转述其消息，而不是重试或设法绕过。
4. 阅读 `report.md` 和 `findings.json`。报告是交付物；当你需要引用某个结论时，JSON 中携带着每个结论背后的数据。
5. 补充采集器无法提供的内容，并与它实际测得的内容明确区分：

   - 面向该读者的一段简短叙述：应优先处理什么，以及为什么。
   - 针对安全通告类发现的升级路径——确认修复是相隔一个补丁版本还是一个大版本。
   - 针对已停止维护或已归档依赖的替代候选。在点名某个候选之前，先验证它确实存在于注册表中，并将这些内容标注为判断，而非测量结果。
   - 对于被标记的安装脚本：`npm ci --ignore-scripts` 对该项目的构建是否可行。

## 补充内容的写作风格

补充的文字要按安全报告的行文方式来写，并将同样的语体一视同仁地应用于报告附录和最终回复——回复会被逐字粘贴进工单和报告。陈述发现、发现背后的数据，以及应采取的行动。

- 非人称、陈述式：不使用第一或第二人称（“我运行了采集器”、“你应该升级”），不使用缩约形式，不使用感叹号。
- 主动语态，以事项本身作为动作主体：“升级到 1.19.0 可清除全部 25 条通告”，而不是“建议升级 axios”。
- 客观：不使用强调词或主观表述（“非常”、“显著”、“幸运的是”），也不猜测项目为何做出其选择。
- 时态：审计做过的事用过去时，依赖的当前状态用现在时，行动与否的后果用将来时。
- 建设性：建议要指明行动及其代价，而不是指出责任人。

如果会话中存在可用的 `report-writing:writing-style` 技能，请遵循它——它是这一语体的完整版本。

渲染出的报告只包含事实。下方的解读规则是对你的指示，而非给读者的内容——不要把它们作为免责说明或框架复制到交付物中。

## 解读报告

- **无法评估不等于风险。** PyPI 不发布维护者 ACL，Go 没有注册表；这些行说明的是哪些信息无法知晓，而不是哪里出了问题。
- **覆盖范围表为每项断言划定边界。** “无通告”的意思是“在已评估的范围内没有”——在重复一个无风险的结论之前，先核对已评估的数量。
- **逐字引用数字。** 不要重新推导、四舍五入或润色报告中的数字；每一个数字都可以从产物中复现。
- **未出现在发现中不构成背书。** 没有发现的依赖只是对照这些标准进行了测量。

## 应拒绝的合理化借口

- “`gh` 能比采集器更快地给出维护者数量。”这样测量是错的——仓库贡献者和注册表发布权限属于不同的群体。
- “没有发现，所以依赖是安全的。”请阅读覆盖范围表；在 PyPI 和 Go 上，一半的标准在结构上就无法评估。
- “无法评估的行只会让读者困惑；我把它们删掉。”这些行是报告中每一项断言的边界。删掉它们会把部分覆盖变成一份健康证明，而这正是本技能重构所要防止的失败。
- “版本大概足够接近了。”针对最新发布版本检查的范围，与由 lockfile 解析出的版本，是两种不同的断言；报告会标明它做出的是哪一种。保留该标签。

## 何时不该使用

- 许可证合规审计。
- 扫描目标项目自身源码中的漏洞或机密——本技能从不读取依赖的源码，只读取注册表、安全通告和仓库元数据。
- 判断该项目能否安装或构建。本审计的设计是仅凭依赖列表——清单和 lockfile——即可运作，并且从不安装、构建或执行任何内容。安装失败与导入时报错不在范围内；如果用户似乎期待这些，应当明确说明。
- npm、PyPI 和 Go 之外的生态系统；应说明该生态系统不受支持，而不是为其即兴拼凑一份审计。
