# 问 Matt

你不可能记住每一项技能，所以要主动询问。

**流程（flow）**是贯穿各项技能的一条路径。大多数路径沿着一条**主流程**运行，另有两条**入口匝道**汇入其中。其余技能要么独立使用，要么作为贯穿底层的词汇层。

## 主流程：想法 → 交付

这是大多数工作的必经路线。你有了一个想法，并希望将它构建出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你**正在工作目录中开展工作**，就从这里开始：它是有状态的，会将了解到的信息保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？那就改用 `/grill-me`，详见“独立使用”部分。两者都运行同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，因此只要有仓库可供存放这些记录，它就是两者中更好的选择。）
2. **分支：你能否在对话中解决所有问题？** 如果某个问题需要通过可运行的内容来解答（状态、业务逻辑，或必须亲眼看到的 UI），那就绕道制作原型，并在两个方向上都使用 **`/handoff`** 进行衔接（原型位于它自己的目录中，而这正是 `/handoff` 的用途；参见“阶段边界”）：
   - 先用 **`/handoff`** 将信息交接出去，然后针对该文件开启一个全新的会话，
   - 使用 **`/prototype`**，通过一次性代码解答问题，
   - 再用 **`/handoff`** 将你了解到的信息交接回来，并在原始想法的讨论线程中引用它。
3. **分支：这是一个需要多个会话完成的构建任务吗？**
   - **是** → 使用 **`/to-spec`**（将讨论线程转化为规格说明），然后使用 **`/to-tickets`** 将其拆分成曳光弹式任务单，每个任务单都要声明自己的**阻塞边**。在本地跟踪器中，每个任务单对应 `.scratch/<feature>/issues/` 下的一个文件，由人工按照阻塞项优先的顺序处理；在真正的跟踪器中，这些边会变成原生阻塞链接，因此只要某个任务单的所有阻塞项都已完成，就可以着手处理它：为每个任务单分别启动 **`/implement`，并在每个任务单之间执行 `/clear` 清除上下文**。每个任务单都是自包含的，因此最后一个任务单的上下文可以直接丢弃。
   - **否** → 就在这里、同一个上下文窗口中使用 **`/implement`**。

   无论哪种情况，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个议题（每次完成一个红灯—绿灯切片），然后在提交之前运行 **`/code-review`** 收尾，对差异进行双轴审查（标准 + 规格说明）。如果你只想以测试优先的方式构建某个具体行为，而不需要完整的规格说明，可以单独使用 **`/tdd`**；如果你想以某个固定点为基准审查分支或 PR，则可以单独使用 **`/code-review`**。

### 上下文卫生

让步骤 1–3 保持在**一个不间断的上下文窗口**中（在 `/to-tickets` 完成之前不要压缩或清除），这样访谈、规格说明和任务单都能建立在同一套思考之上。之后，每次 `/implement` 都从全新的上下文开始，以任务单为依据开展工作。

这里的上限是 **[智能区间](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：在这个窗口内（对于最先进的模型，约为 150k 个 token），模型仍能保持敏锐的推理能力。如果会话在执行 `/to-tickets` 之前就接近这一上限，不要在能力退化的状态下勉强继续；应在最近的阶段边界执行 `/compact`，然后继续进行（参见“阶段边界”）。

## 汇入主流程的入口

一种会产生工作、随后汇入主流程的起始情境。

- **Bug 和请求不断积压** → **`/triage`**。它让议题依次经过各个分诊角色，产出可直接交给智能体处理的议题，之后再由 **`/implement`** 接手。

  分诊仅适用于**并非由你创建的**议题：Bug 报告、传入的功能请求，以及任何未经整理便到来的内容。由 `/to-tickets` 产出的工单已经可以直接交给智能体处理，因此**不要对它们进行分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。适用于那些棘手的问题：初看之后仍无法解决的 Bug、间歇性出现的不稳定故障，以及在两个已知正常状态之间悄然引入的回归问题。在建立**紧密反馈循环**（一条能针对*这个* Bug 稳定报错的命令）之前，它拒绝进行理论推断，随后通过添加回归测试来修复问题。当真正的发现是缺少一个能有效锁定该 Bug 的良好接缝时，它会在事后分析中将工作移交给 **`/improve-codebase-architecture`**。

- **一项庞大而模糊的工作：绿地项目或大型功能开发，规模大到无法在一次会话中完成** → **`/wayfinder`**，这是此处对认知要求最高的流程。当从当前位置通往目的地的路径尚不可见时，它会在议题跟踪器上绘制一幅由**决策工单**构成的**共享地图**，逐一解决这些工单，产出的是**决策，而非交付物**，直到迷雾散去、路径清晰。**`/grill-with-docs`** 用于打磨你能在一次会话中把握的想法，而 wayfinder 则用于处理一次会话无法把握的想法；它更慢、信息密度也更高，因此只应在确实需要时使用，绝不要用于范围明确的功能。

  地图清晰后，**它会移交工作，而不是进行构建**：在 **`/to-spec`** 处汇入主流程，由它将地图中相互关联的决策整合成可执行的构建计划，然后照常依次使用 `/to-tickets` 和 `/implement`。直接将地图送入 `/implement` 会跳过这一整合步骤，并丢失相互关联的细节，因此只有在这项工作最终被证明规模确实很小时，才应直接进入 `/implement`。

## 代码库健康度

不是功能开发，只是维护工作。

- 只要有空闲时间，就运行 **`/improve-codebase-architecture`**，让代码库始终适合智能体在其中开展工作。它会找出**深化机会**；选择其中一个，就会*生成一个想法*，你可以在 `/grill-with-docs` 处将其带入主流程。它负责勘察并发现候选项；**`/codebase-design`**（见下文）则是用于设计所选候选项的工作台。

## 底层词汇

两个由模型调用、运行在其他技能*底层*的参考资料，各自都是其词汇的唯一事实来源。当问题出在**词语**而非流程上时，可以直接使用它们；也可以让上述技能自行引入它们。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑一个含糊的术语、厘清一个含义过载的词（例如用“account”承担三种职责），或将难以逆转的决策记录为 ADR。这是 `/grill-with-docs` 为使 `CONTEXT.md` 保持为一份清晰的术语表而推动实施的主动方法。
- **`/codebase-design`** 是用于设计模块*形态*的深模块词汇体系（module、interface、depth、seam、adapter、leverage、locality）：在一个清晰的接缝处，通过一个小型接口封装大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套词汇。

## 阶段边界

**阶段**是会话中的一段工作：盘问、实现、QA。在两个阶段的**边界**处，你有五种选择，而如何在它们之间做出选择，是整张图中最模糊的决定：

- **继续**：留在原地。没有成本，也不会丢失任何内容。
- **`/clear`**：清空窗口，适用于这里的内容对接下来的工作都不重要时。
- **`/handoff`** 会写入一个可移植的 Markdown 文件。适用范围很窄：仅用于**新的执行环境**、**新的目录**、**同事**，或在**阶段中途**分叉出一个支线任务。它带来的价值是可移植性。
- **子代理**：将一个范围严格限定的任务发送到它自己的窗口，并取回报告。
- **`/compact`** 会压缩当前上下文，并用它为一个新会话提供初始信息。这是树底部的**默认选择**，而不是最先采用的手段。

请阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)，了解这棵有序决策树：五个问题、每个分支背后的推理，以及为什么获取一手资料的成本使得**继续**成为第一个需要排除的选项。应在边界处做出决定；阶段中途，要么继续，要么将剩余工作拆分给子代理。

## 独立使用

完全独立于主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 相同的不留情面式访谈，但它是**无状态的**：不会在本地保存任何内容，也不会创建 `CONTEXT.md`。当你**不是在工作目录中开展工作**时使用它（打磨计划、设计、文章，或任何底下没有仓库的工作）。如果你处于工作目录中，则应改用 `/grill-with-docs`：它会进行相同的访谈并留下书面记录，因此毫无疑问是更好的选择。
- **`/grilling`** 是访谈原语本身：多轮访谈、问题前沿；事实由代理负责，而决策由你负责。`/grill-me` 和 `/grill-with-docs` 是两种有名称的入口方式，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都会在内部运行它。只有当你想要纯粹的访谈、不需要任何外层封装时，才直接使用它。
- **`/resolving-merge-conflicts`** 会逐个冲突块处理正在进行的合并或变基冲突，根据追溯至冲突双方一手资料的**意图**来解决冲突，而不是直接选择某些代码行，然后完成该操作。它绝不会运行 `--abort`。它是独立的，不属于任何流程：当你已经处于冲突处理中时使用它。
- **`/prototype`** 是一个小型的一次性程序，用来回答一个设计问题：这个状态模型是否合理，或者这个 UI 应该是什么样子。一次性是对代码编写方式的约束，而不是销毁它的承诺：得到的答案会融入实际代码，而原型本身会作为**一手资料**保留在从 main 分出的 `prototype/<name>` 分支上，并由实现 issue 指向它。它是主流程第 2 步中的绕行路径，但只要某个设计问题很难在纸面上确定，就可以使用它。
- **`/research`**：将阅读资料的跑腿工作委托给一个**后台代理**：它依据**一手资料**调查某个问题，然后在仓库中留下一个带引用的 Markdown 文件。它阅读时，你可以继续工作。它生成的文件应在 `/grill-with-docs` 阶段带入主流程，因为研究为思考提供材料，而不是取代思考。
- 当阻碍你的内容既不在你的脑海中，也不在代码库中，而是在**别人的**脑海中时，就该使用 **`/to-questionnaire`**；它会编写一份问卷供对方填写。它是 `/grill-me` 的反向形式：它不会就主题采访你，而是就**发送事宜**采访你（要发给谁、你需要对方返回什么），并让问题直指信息缺口。返回的内容可作为 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 用于只有**人类**才能完成的步骤：配置基础设施、设置凭据或 CI 密钥、在不熟悉的第三方控制面板中点击操作、执行一次性的迁移或切换。它会生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并将其写入 `.env` 和 GitHub secrets，从而使这套流程不再需要你每次都重新向代理解释。它由模型调用，因此代理一旦遇到只有你才能跨过的障碍，就会使用它。如果代理自己就能完成，那它就应该自己做；它只适用于确实需要人类参与的场景。
- **`/wait-what`** 用于纠正未能传达清楚的消息。在对话中途、任何其他 skill 内部使用它，代理便会使用 `CONTEXT.md` 中的词汇，以通俗英语重新表达刚才所说的内容，并补上你所缺少的上下文。它在事后起效；`/grill-with-docs` 则是事前的解决办法，因为及早就共享语言达成一致，才能从一开始就避免术语突然出现。
- **`/teach`**：跨多个会话学习一个概念，并将当前目录用作有状态的工作区。
- **`/writing-for-agents`** 是为编写供代理使用的文档而提供的参考资料：skills、AGENTS.md，以及被指向的文档。
