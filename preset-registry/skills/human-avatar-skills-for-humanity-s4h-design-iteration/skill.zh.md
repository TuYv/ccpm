# 设计：迭代

没有任何设计能在首次接触现实世界后仍完好无损。最优秀的设计师深知这一点，并会为此做好规划：他们迅速做出某个方案，将其置于现实中检验，了解其中的问题，然后做出更好的方案。迭代周期并非一种失败模式，而是设计得以改进的机制。问题不在于是否要迭代，而在于如何组织每一轮迭代，使其以最少的投入获得最多的认知。

几十年来，迪特·拉姆斯在密切观察的基础上不断设计和重新设计博朗的产品——并不是因为第一个版本有误，而是因为契合度需要通过探索来发现，而非事先规划。唐·诺曼在*《日常生活中的设计》*中的核心洞见是：设计师对用户的判断是错误的——这种错误具有系统性和可预测性，而且无法仅靠推理发现。唯一的解决办法就是观察：把设计成果摆在人们面前，不做任何解释，只观察会发生什么。

本技能对迭代周期进行了结构化。它区分了每个阶段需要哪种类型的测试（发散型还是收敛型），明确了适合当前问题的原型保真度，并定义了相应的决策标准，用于判断何时应缩小范围、何时应转变方向，以及何时已经积累了足够的认知，可以正式投入实施。

## 你的流程

**第 1 步：陈述当前假设**
每个原型都是对某个假设的检验。明确地陈述它：“我们相信[具体设计选择]将为[执行这项任务的用户]带来[这一结果]。”如果假设含糊不清，测试就无法提供有用的信息。具体并不意味着过早承诺——具体性正是使学习成为可能的前提。

**框架检查：** 继续之前，确认当前设计阶段和正在检验的假设。用一句话说明你识别出的内容——正在迭代的设计及其需要回答的关键问题——然后使用 `AskUserQuestion`：
- **问题：** “我的理解是：[你对假设和阶段的一句话概括]。对吗？”
- **标题：** “框架”
- **选项：**
  - **是——继续**——框架正确
  - **调整**——其中一个要素有偏差；用户会在你继续之前予以纠正
  - **重新界定**——实际情况与你的理解不同；继续之前先纳入修正内容

**第 2 步：确定迭代类型**
两种截然不同的测试类型需要不同的设置：

- **发散型测试：** “哪个方向最有前景？”当存在多个相互竞争的设计方向，而你需要缩小范围时使用。设置多个选项。每次只改变一个因素。衡量偏好、理解程度或参与度。
- **收敛型测试：** “这个方案有效吗？”当方向已经确定，而你正在优化契合度时使用。结合真实使用场景测试具体设计。衡量实际任务的完成情况。

确定需要哪种类型。将两者混在一起会导致无法得出清晰的认知。

**第 3 步：确定原型**
使原型保真度与所要回答的问题相匹配：

- **草图/纸面原型：** 用于在尚未投入任何视觉外观设计之前，测试某种交互模型是否合理
- **线框图/低保真原型：** 用于测试结构、导航和信息层级
- **中保真原型：** 用于测试理解程度、流程以及操作顺序是否有效
- **高保真原型：** 用于测试用户对完整体验的反应——美感、语气和情绪反应
- **实时/功能性原型：** 用于测试真实条件下的真实行为

最常见的错误是构建超出当前阶段所需的原型。对于一个用草图就能回答的问题，制作高保真原型不仅浪费时间，还会让人对方案产生依恋，从而使测试结果出现偏差。

明确说明：要制作什么、采用何种保真度，以及应该和不应该包含哪些内容。

**步骤 4：设计测试**
无法回答假设的测试就不是真正的测试。请定义：

- **问题：** 你具体想了解什么？
- **方法：** 观察、任务完成、访谈、A/B、日记研究——每种方法适合回答不同的问题。观察能揭示人们实际做了什么；访谈能揭示他们相信什么；任务完成测试能揭示设计在哪些地方失效。
- **参与者：** 哪些用户、多少人、处于何种情境。群体越小、越具体，信号就越清晰。
- **什么才算结果：** 预先定义正向结果是什么样的，以及出现什么情况意味着需要转向。

**步骤 5：解读信号**
测试结束后，将观察与解读分开。人们实际上做了什么、说了什么，或者没能完成什么？他们在哪里犹豫、提出问题或偏离预期路径？这些时刻就是数据。解读应源于数据——而不是反过来。

对发现进行分类：
- **证实假设：** 证明方向正确的证据
- **否定假设：** 表明需要转向或移除的证据
- **意外信号：** 未被纳入假设但实际出现的情况；先记录下来，不要立即将其纳入方案

**步骤 6：确定下一轮迭代**
根据发现做出决定：
- **继续并优化：** 假设得到证实；下一轮迭代继续细化同一方向
- **转向：** 假设被否定；在制作下一个原型之前改变方向
- **收窄：** 已测试多个方向；淘汰其中一个或多个；下一轮将深入探索保留下来的方向
- **定案：** 已积累足够的认知；适合进入收敛阶段

说明所做的决定及其理由。

## 人工确认

继续之前，请使用 `AskUserQuestion` 工具。用 1–2 句话说明你对当前情况的理解——设计目前处于哪个阶段，以及关键的不确定性是什么——然后询问：

- **问题：** “我的理解是：[你用 1–2 句话给出的解读]。你希望如何继续？”
- **标题：** “范围”
- **选项：**
  - **完整周期计划**——规划完整的迭代周期，包括原型规格和测试设计
  - **仅原型规格**——重点确定要制作什么以及采用何种保真度
  - **仅测试设计**——重点确定如何测试已有设计
  - **重新界定**——当前理解有误；进行纠正，后续分析将依据纠正后的框架展开

根据用户的选择继续。如果用户选择重新界定，请在进行任何分析之前纳入其纠正内容。

## 备注

迭代中最常见的失败模式是“只学习，不决策”——每项测试都会产生一些发现，为略作修改后的下一项测试提供参考，但由于没有人愿意确定一个方向，整个循环始终无法收敛。应在测试前定义决策标准，而不是在测试后。第二常见的失败是在错误的保真度下测试错误的内容——通常是构建过度——这会使原型的修改成本高昂，并导致团队偏向渐进式优化，而不是真正的学习。

此技能通常与 `/s4h-design-user-needs`（定义原型应依据什么进行测试）和 `/s4h-design-simplicity`（在下一轮迭代前移除不需要的内容）自然搭配使用。如需生成可供测试的替代方向，`/s4h-creativity-alternatives` 可以高效地产生选项。

- **问题：**“迭代周期已规划。下一步做什么？”
- **标题：**“下一步”
- **选项：**
  - `/s4h-design-simplicity` — 在构建之前，从当前设计中移除不必要的内容

  - **完成** — 收尾并综合整理目前为止的成果
