name: gha
description: Analyze GitHub Actions failures and identify root causes
argument-hint: <url>
---
调查这个 GitHub Actions URL：$ARGUMENTS

使用 gh CLI 分析这次工作流运行。你的调查应包括：

1. **获取基本信息并确定实际失败原因**：
   - 哪个工作流/作业失败了、何时失败、失败于哪个提交？
   - 关键：仔细阅读完整日志，找出究竟是什么具体导致了退出码 1
   - 区分警告/非致命错误与实际失败
   - 寻找类似 "failing:"、"fatal:" 的模式，或决定何时以退出码 1 退出的脚本逻辑
   - 如果同时看到 "non-fatal" 和 "fatal" 错误，请重点关注实际导致失败的原因

2. **检查不稳定性**：检查完全相同的那个失败作业在过去 10-20 次运行中的情况：
   - 重要：如果一个工作流包含多个作业，你必须检查具体失败的那个作业的历史记录，而不只是工作流的历史
   - 使用 `gh run list --workflow=<workflow-name>` 获取运行 ID，然后使用 `gh run view <run-id> --json jobs` 检查该特定作业的状态
   - 对该特定作业而言，这是一次性失败还是反复出现的模式？
   - 该作业最近的成功率是多少？
   - 该作业上次通过是在什么时候？

3. **确定破坏性提交**（如果该特定作业存在失败模式）：
   - 找到该特定作业第一次失败的运行，以及它最后一次通过的运行
   - 找出引入失败的提交
   - 通过以下方式验证：该作业在该提交之后的所有运行中都失败吗？在该提交之前的所有运行中都通过吗？
   - 如果验证通过，就以高置信度报告该破坏性提交

4. **根本原因**：根据日志、历史记录以及任何破坏性提交，可能的原因是什么？
   - 重点关注实际导致失败的原因（而不只是你看到的任何错误）
   - 结合日志和失败逻辑验证你的假设

5. **检查是否已有修复 PR**：搜索可能已经解决此问题的处于打开状态的 PR：
   - 使用 `gh pr list --state open --search "<keywords>"`，配合相关的错误消息或文件名
   - 检查是否有打开的 PR 修改了失败的文件/工作流
   - 如果已存在修复 PR，请在报告中注明，并跳过建议部分

撰写一份最终报告，包含：
- 失败摘要（具体是什么触发了退出码 1）
- 不稳定性评估（一次性失败还是反复出现，成功率）
- 破坏性提交（如已确定并经过验证）
- 根本原因分析（基于实际触发失败的因素）
- 已有的修复 PR（如已找到——附上 PR 编号和链接）
- 建议（如果修复 PR 已存在则跳过）
