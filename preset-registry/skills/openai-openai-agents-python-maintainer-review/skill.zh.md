# 维护者评审

## 目标

做出维护者决策，而不是泛泛的代码审查总结。应区分以下问题：

1. 所声称的行为是否真实存在？
2. 独立于报告者提出的 API 或修复方案，实际存在什么用户预期结果或约束？
3. 现有受支持的功能是否已经能够通过合理的组合或配置实现该结果？
4. 如果仍然存在缺口，所提方案是否属于最佳设计，并且是否位于正确的实现层？
5. 普通用户是否确实可能遇到该缺口？遇到时会发生什么？
6. 该问题是否重要到需要现在采取行动？
7. 如果这个 PR 尚不存在，维护者是否会选择创建并实现同样的工作？
8. 对于 PR，该解决方案是否值得合并并长期维护？
9. 重叠或过时的操作是否可能破坏共享状态，或清理由仍在继续的工作所拥有的资源？
10. 如果存在相互竞争的 PR，维护者应该选择推进哪一条唯一的实现路径？
11. 哪些存在歧义的范围或语义选择属于应由维护者决定的产品/API 决策？贡献者应按照什么具体方向实现？
12. 应使用什么简洁的维护者消息，清晰且礼貌地传达关闭决定或修改请求？

应将议题中请求的字段、回调、标志、类或实现策略视为提议的机制，而不是已经接受的需求。不要一开始就询问如何实现它。首先证明现有支持尚不能满足某个具体的用户预期结果，并证明所提机制优于现有替代方案。

首先说明当前评审状态。在仍有影响决策的证据有待确认时，使用 `Preliminary assessment`；仅当评审可以得出结论时，才使用 `Maintainer decision`。应将差异、议题叙述或贡献者投入视为证据，而不是将其当作影响程度的替代指标。

## 工作流程

### 1. 确定准确目标

- 接受 GitHub issue 或 PR URL 作为主要输入。在开始评审前，确定其所有者、仓库、条目类型和编号。
- 对于 issue，阅读完整报告、评论、复现步骤、环境信息、链接材料和维护者回复。
- 对于 PR，检查当前远程 base 和 head、完整补丁、相关情况下的提交历史、测试、关联 issue 和评审讨论。不要使用当前本地检出内容代替正在评审的远程变更。
- 用一句可证伪的话陈述该主张。区分报告的症状与报告者提出的原因或修复方案。
- 当兼容性或回归声明很重要时，确定已发布行为的边界。
- 当提议的变更会删除、重新排序或重新解释既有的可观察行为或明确的现有测试预期时，在给出任何正面评估之前，检查引入该行为的提交、blame 和原始测试。刻意纳入已发布版本的测试覆盖属于兼容性风险证据，即使它本身并不构成永久性的公共契约。
- 验证链接证据是否与 PR 的确切运行时变体、提供程序或工具类型、触发条件及用户预期结果相匹配。通用的 issue 标题、概念上的相似性或诸如 `Related to` 的措辞，并不能将需求证据转移到相邻扩展上。如果所报告的场景已经修复，则应将其他变体视为新的需求，并要求它们提供各自的证据。

遵循仓库关于远程访问和变更操作的说明。评审并不授权发表评论、添加标签、更改分支、推送或执行其他远程写入操作。

### 2. 确定尚未满足的需求，并质疑提议的解决方案

在深入评估提议的实现之前，以及在对任何 issue 或 PR 作出正面评价之前，完成此轮分析。

首先指定一个 `Need status`：

- **已证实**：确切范围具有具体且受支持的场景、真实路径复现、已发布的兼容性要求、反复出现的需求，或具有实质性后果的广泛不变量。
- **合理但未经证实**：该路径可能存在，但尚未确定提供方行为是否符合现实、对用户的影响范围、发生频率、后果或需求。
- **已覆盖**：某个合理且受支持的工作流已经能够实现该结果。
- **不受支持**：该结果不属于 SDK 契约的范围，或应由提供方、适配器或调用方所属的层负责。

只有`已证实`的需求才能获得`可按原样合并`或`经过针对性修改后可合并`的评价。对于`合理但未经证实`，优先选择`需要证据`或`不值得完成`；对于`已覆盖`或`不受支持`，优先选择关闭，或采用相应的更简单替代方案。

将以下四项决策彼此分开，并在比较实现之前记录它们：

1. **观察有效性**：报告的输出、状态或代码路径差异是否真实存在。
2. **下游后果**：它具体改变了哪些用户、运维、兼容性或持久状态方面的结果。
3. **需求状态**：上述四种证据分类之一。
4. **Issue 处置方式**：确定优先级、接受、缩小范围、请求证据或关闭。

真实的观察结果仍然可能没有已证实的需求，并对应`关闭`操作。当仅确认了观察结果时，不要简单地将 issue 描述为“有效”。如果缺少下游后果，请勿在提议的语义契约之间作出选择、选择相互竞争的 PR，或起草实现变更。

在指定为`已证实`之前，要求满足以下证据路径之一：

1. **已观察到的影响**：受支持的场景、真实路径复现或可信的用户报告，表明存在对用户可见、运维、兼容性或持久状态方面的实质性后果。
2. **实质性预防**：受支持或常见的故障路径可能触达该条件；被违反的不变量所防范的损害本质上具有实质性；并且完整的代码路径追踪或符合现实的探测证实了该后果。此路径不要求存在已知事故。

对于两条路径，都要追踪`现实的触发条件 -> 受支持的执行路径 -> 可观察或持久的影响`。局部的中间状态不一致、可构造的分支、冗余操作、防御性改进或理论上更简洁的不变量，如果没有实质性的下游影响，就不能证明需求已得到证实。差异很小、补丁在技术上正确或测试成本低，都不会降低这一门槛。实质性的预防结果包括安全或隐私暴露、凭据泄露、持久化数据或状态损坏、重复的外部副作用、无法恢复的兼容性破坏、死锁或无限期挂起，以及现实中可重复发生的资源耗尽。

对于仅涉及表示形式的变更，应指出补丁前后某个具体的使用方计算、决策或持久化解释有何不同，然后说明当前结果为何错误。如果补丁仅改变列表形态、占位符是否存在、元数据、顺序或术语，却没有恢复信息或改变有实际意义的使用方结果，那么其必要性不能评为 `Demonstrated`。

契约存在歧义本身并不能证明该契约应该变更。当多个当前形态已经发布或被有意纳入测试覆盖时，在有明确结果证明需要选择不同的语义契约之前，应优先不修改代码。不要仅仅因为某种形态更对称或更容易解释就选择它。

当报告仅能证明逻辑层面的改进无害或影响尚属推测时，应优先选择 `Not worth completing` 或 `Close`，而不是要求进一步完善实现。只有当某个缺失的具体复现步骤或后果追踪确实可能改变实际影响判断时，才使用 `Needs evidence`。

1. 重新表述期望达成的用户结果，不要提及所请求的 API、类、文件、选项或实现。将实际约束与报告者偏好的实现机制区分开来。
2. 追踪在当前版本和当前目标中实现该结果最接近的受支持方式。检查负责该功能的代码路径、公共 API、测试及相关文档，不要因为不熟悉某项能力就假定它不存在。考虑配置、组合、克隆、回调、扩展点、提供商适配器，以及在调用方拥有的层级完成相关工作。
3. 判断报告所展示的是能力缺口、易用性或可发现性问题、不受支持的用例，还是根本没有得到证实的问题。更便捷的写法并不自动意味着能力缺失。
4. 将提议的解决方案与现有最优方案以及至少一个设计更优的候选方案进行比较：不修改代码、提供更清晰的文档或验证、采用范围更窄的修复、复用现有抽象，或在更合理的共享边界上实施约束。
5. 对于每种可行方案，比较其是否满足具体场景、会创建哪些新的公共或内部契约、跨路径一致性、兼容性以及永久维护成本。

不要把证明新代码能够运行的测试视为功能确有必要的证据。`FakeModel` 响应、手动构造的提供商条目、模拟对象或新的回归测试，可以证明代码路径可达以及实现正确；但它们本身不能证明真实的提供商行为、用户覆盖范围、发生频率、实际后果、需求或实质性的预防效果。

API 对称性、命名一致性以及与相邻工具、提供商或输出类型保持一致，都属于设计论据，而非需求证据。当对齐能够消除现有复杂性或落实一个已得到广泛证明的不变量时，它可能足以支撑相关工作；但新增分支、测试、文档或公共行为，仍需要独立的实际理由。

将显式公开的 `Literal`、枚举、可辨识联合或等效的静态类型限制视为其他值不在受支持契约范围内的证据。不要仅仅为了拒绝公共类型已经排除的值，而添加重复的客户端运行时验证。只有在有证据表明 SDK 本身会接收无类型数据、在产生副作用之前快速失败可保护已记录的契约或重要不变量，或者无效值会对受支持路径造成实质性影响时，才应要求添加此类验证。宿主语言能够绕过类型提示、传入恶意构造的运行时对象，或在构造后修改属性，这些情况本身并不足以成为添加永久性验证分支和测试的理由。

当上游服务器或提供商已经会拒绝不受支持的请求时，应将该边界视为事实依据，并避免在客户端重复相同的接受规则。只有在等待服务器拒绝会造成已证实的重大隐患或实质性效率问题时，才添加快速失败的客户端验证，例如可避免的计费工作、重复的网络延迟或资源消耗、不可逆的副作用或状态变更，或者错误出现得太晚或过于晦涩，导致难以合理修正。相比复制可能随时间推移而发生偏差的提供商允许列表或约束，应优先依赖服务器不断演进的验证机制。

#### 人为构造的边界情况和极端值准入标准

如果某个议题或 PR 的必要性仅通过构造常规受支持的数据生产方无法生成的值，或在受支持的使用方式中没有现实来源的值来证明，则不要接受。这包括 `NaN` 或无穷大等非有限数、极其巨大的数值、不可能出现的枚举或可辨识联合成员、手动破坏的类型化对象，以及绕过其所属公共边界或传输边界而直接调用辅助函数。单元测试能够触发这样的分支，只能证明该情况可以被构造出来，并不能证明这是一个值得通过维护代码来应对的问题。

默认将这些报告判定为 `Close` 或 `Not worth completing`，即使补丁很小且技术上正确；除非证据至少能够证明以下一点：

1. 受支持的提供商、解析器、公共 API 工作流或可信的用户报告会在现实条件下产生完全相同的值。
2. 已发布的公共契约有意接受该值类别，并且常规调用方代码无需先违反该契约即可生成该值。
3. 完整的安全追踪表明，攻击者可控的输入能够跨越实际的信任边界，并造成现实中可利用的资源耗尽或其他具体的安全边界违规。

如果没有证明该值的现实来源以及导致后果的完整受支持路径，那么“这可能会永远休眠”“这可能会溢出”或“这可能会禁用限制”等说法均不足以成立。不要仅凭安全标签就将其视为例外：应明确指出信任边界、谁能够控制输入、输入如何到达 SDK，以及具体受到保护的结果。如果追踪链路完整，来自真正不受信任的传输边界的畸形值可能足以证明修复的合理性；而假想的恶意提供商、经过猴子补丁修改的对象或手动构造的有效载荷，本身并不足以证明这一点。

当此门槛未通过时，不要花费评审精力来改进实现、测试或错误措辞。建议关闭该议题及其 PR（如果存在），并且仅在现实证据确实可能出现时，明确说明哪些具体的现实证据能够成为重新考虑的依据。

如果需求并非 `Demonstrated`，只需将补丁检查到足以理解其契约、风险和维护成本的程度。不要因为实现缺陷、缺少测试或文档不足而建议请求更改，因为只有在需求门槛通过后，这些问题才会成为阻止合并的因素。如果报告没有提供具体场景、现有功能看起来已经足够，或者所请求的机制仅解决假设性的便利问题，应优先选择 `Needs evidence`、`Close`、`Supersede with a simpler alternative` 或 `Not worth completing`，而不是代替报告者设计其所请求的功能。

### 3. 按适当范围查找相互竞争的开放 PR

在深入评估指定 PR 之前执行此操作。PR URL 选定的是起点，不一定代表完整的比较范围。

- 通过显式的关闭关键字、已链接的议题、议题时间线或开发链接、PR 正文与评论，以及复现的症状来确定主要议题。如果关联是推断得出而非显式指定，请说明依据。
- 当某个议题被显式链接时，通过议题时间线、开发链接、交叉引用、关闭关键字和普通引用，列出所有处理该议题的开放 PR。包括草稿 PR，但要将其标记为草稿。
- 当没有链接任何议题时，使用标题、复现过程、被违反的不变量和运行时路径中最有力的两到三个信号，执行有界的重复项搜索。当额外查询不太可能找到可信的竞争实现时停止。
- 从当前比较集合中排除已关闭或已合并的 PR，但在相关时将其用作历史信息。
- 不要仅仅因为 PR 提及同一子系统就将它们归为一组。它们必须共享同一议题、症状、被违反的不变量，或具有实质性重叠的修复方案。
- 在内部记录搜索方法和候选集合。如果无法通过仓库访问来确定完整性，应明确说明这一点，而不是声称已经找到了所有开放 PR。不要在最终报告中列出不相关的搜索结果。
- 当存在多个候选方案时，应从需求覆盖范围、运行时正确性、范围、实现层、测试、兼容性、复杂度、就绪程度、维护者尚需完成的工作，以及有用部分能否组合等方面进行比较。应优先选择可维护性最佳的解决方案，而不是默认选择最先提交的方案或差异最小的方案。

### 4. 使用案头评审证据流程

始终从案头评审开始。在判断一项小改动是微不足道还是意义重大之前，先检查具体的运行时路径。检查调用方、相邻辅助函数、验证层、回退路径和现有测试。仅在历史记录或文档会影响决策时才进行搜索。检查测试代码属于案头评审的一部分；执行测试、导入、示例、复现、基准测试或服务调用则属于运行时探查。

此技能不规划或执行运行时探测。调用此技能、请求审查或提供 issue 或 pull request URL，并不构成对测试、导入、示例、复现、基准测试、服务调用或其他运行时探测技能的授权。如果案头审查后仍存在会影响决策的运行时证据缺口，请将评估保持为初步结论，并建议另行开展运行时调查。说明尚未解决的问题、该问题为何可能改变决策、所需的证据，以及适当的基线、发布版本或已知良好的对照。请勿提供确切命令、请求批准、调用其他技能或通过此技能执行代码。

对于仓库特定的运行时不变量，请从 `.agents/references/README.md` 开始，并且只打开与受影响边界相匹配的参考资料。在审查 issue 和 PR 期间，应将 `.agents/references/` 视为只读：使用其中的内容识别预期不变量、相邻接口面和回归风险，然后根据远程变更、当前代码、测试、文档、发布边界和有针对性的运行时证据来验证当前声明。请勿将编辑参考资料作为审查的附带操作，不要根据这些资料推断当前 issue 或 PR 的状态，也不要将旧 issue 或 PR 的结果视为当前证据。如果审查发现了应当记录的可复用不变量，请建议单独进行仓库维护更新，除非用户明确要求在同一任务中更新参考资料。

请按以下证据顺序进行：

1. 追踪最接近的现有受支持能力，并确定它们是否已经能够实现用户的根本目标。
2. 检查现有测试并完整追踪代码路径，包括在触发时必须进行的交错与所有权检查，但不执行代码。
3. 在不执行代码的情况下，将实现和现有证据与已发布版本、基础分支或已知良好的对照进行比较。
4. 如果仍存在会影响决策的运行时不确定性，请停止审查，并按照下述证据要求建议另行开展运行时调查。

#### 案头审查

根据静态证据得出结果：

##### 强制性的未满足需求与设计检查

在给出正面评估之前，请完成第 2 步中的检查，并能够基于具体证据说明以下所有事项：

1. 当前受支持行为无法实现的用户目标。
2. 最接近的现有 API 或组合路径，以及它无法满足需求的确切原因。
3. 为什么提议的行为应当位于所选抽象层，而不是调用方、适配器、验证、文档或现有扩展点。
4. 为什么提议的永久契约优于不进行代码变更，以及最有力的更窄范围替代方案。
5. 哪种真实场景、兼容性要求或重复出现的需求足以证明新增维护面的合理性。
6. 如果没有贡献者已经提供补丁，维护者是否仍会选择推进同一项工作。

如果缺少任何答案，并且该答案可能改变是否应当存在相应代码的判断，请勿认定该 issue 可采取行动或该 PR 值得合并。仅请求区分真正的能力缺口与使用方式、可发现性或解决方案设计问题所需的证据。这是产品与架构方面的证据缺口，本身并不构成运行时探测的触发条件。

##### 强制交错与所有权检查

当补丁新增、移除或重新安排清理、重试、重新连接、取消、监听器、共享 future 或任务、连接或流、状态标志，或者跨 `await`、回调、事件或延迟完成点的可变状态时，在对 PR 作出任何正面评估之前执行此项检查。

1. 列出每个共享资源或状态值，并枚举所有可以修改它的路径，包括不同的公共方法以及包装器或委托路径。应涵盖监听器、future、任务、连接、流、锁、缓存、状态标志、持久化和遥测。
2. 跟踪至少两个重叠操作 `A` 和 `B`，覆盖每个暂停点或重入点。应从最强的不同修改方中选择 `B`，而不能只选择 `A` 的第二次调用。检查以下情况：`A pending -> B starts -> A fails -> B succeeds`、`A pending -> B starts -> B fails -> A succeeds`、在设置与完成之间发生关闭或取消，以及旧的完成结果在较新的工作之后到达。
3. 对于基于快照的清理或回滚，始终跟踪 `A snapshots -> A destructively mutates -> B commits newer state -> A rollback resumes`。要求 `A` 之前的状态与 `B` 已提交的修改按正确顺序保留下来，并且持久化状态、缓存、索引、标志及相关所有权状态保持一致。
4. 对于每次清理或回滚，确定它被允许处置的确切尝试和资源代次。要求在实际修改边界处具备所有权令牌、代次、身份检查、比较并交换、事务、已证明的串行化机制或等效的不变量。不要从预期用法推断排他性；只有在显式契约或快速失败验证强制执行该限制时，才将重叠视为不受支持。
5. 对比基线与当前版本的幸存者不变量。用缺失处理程序、已关闭的共享资源、已还原的状态或失败的幸存任务来替代重复工作，属于回归，而不是成功的清理。如果补丁针对另一条失败、取消或重试路径新调用了过时清理，不要仅因该清理原本就已存在而忽略它。
6. 检查测试是否使用延迟 future、回调或事件来控制操作交错。要求断言失败操作和幸存操作的可观察行为以及最终资源的一致性，而不能只检查监听器数量或单个异常结果。

不要仅仅因为顺序执行的重新连接、重试、失败和关闭测试通过，就将并发敏感的补丁标记为 `Merge-worthy as-is`。如果证据没有记录完整的修改面、具体的所有权机制、最强不同修改方的交错，以及幸存者与一致性结果，则触发的所有权检查尚未完成。如果代码跟踪证明存在不安全的交错，应根据静态证据得出结论，并要求进行针对性修复和添加回归测试。如果所有权仍不明确，则将结果保持为初步结论，并说明解决该问题所需的确切运行时证据。

- 如果通过完整的可达代码路径跟踪，可以确定相关主张或 PR 明确不成立，则无需进行运行时探测即可结束评审。示例包括不可能或不受支持的路径、与现有处理重复、已证明无实际作用、直接的兼容性破坏，或明显错误的抽象。不要仅仅为了避免探测，就将存在歧义的结果判定为负面。
- 如果初步结果为正面、不存在尚未解决的运行时问题，并且任何已触发的交错与所有权检查均已完成，那么案头评审可能足以支持维护者作出最终决定。不要仅为了重述那些不可能合理改变决定的证据而建议进行额外的运行时调查。
- 如果存在任何尚未解决、且可能合理改变主张有效性、严重程度、是否值得合并、所需改动或首选竞争 PR 的运行时问题，请报告 `Preliminary assessment`。说明尚未解决的问题、它为何可能改变决定、所需证据以及适当的对照，然后建议单独开展运行时调查，但不要规划或执行该调查。
- 纯粹与风格、文档、CI 状态或仓库就绪情况相关的问题，不足以成为建议开展运行时调查的理由，除非它掩盖了某个运行时问题。

当与决策相关的运行时问题仍未解决时，不要给出明确肯定的维护者决定。如果无法获得所需的运行时证据或相关情况仍未经测试，则应将结果保持为初步结论，并说明确切的置信度限制。

对于涉及验证、快速失败行为、清理、重试、中断或并发的变更，除主要行为外，还要追踪生命周期顺序：

- 识别在新检查或失败点之前获取的监听器、任务、连接、文件、锁、状态变更及其他资源。
- 验证当构造、进入上下文管理器、验证、连接或执行在正常清理运行之前引发异常时，清理是否仍能完成。
- 当失败可能遗留可观察状态或资源时，要求提供负向路径测试。

不要过度调查。当额外证据不太可能改变有效性、严重程度或维护者建议时，停止调查。

### 5. 校准有效性和影响

使用 `references/evaluation-framework.md` 评估主张的有效性、实际影响范围、后果、广度、频率、可恢复性、兼容性和严重程度。将已观察到的事实与推断分开，并说明哪些缺失证据可能改变决策。

在将需求归类为能力缺口、易用性或可发现性缺口、不受支持的用例，或尚未证实存在缺口之前，先报告 `Need status`。如果现有的受支持工作流已经能够产生所请求的结果，就不要因缺少所请求的机制而认定存在实际影响。不要仅凭可达性、API 不对称性或补丁在技术上成功，就推断其具有实际重要性。

对于 PR，应让 `Severity` 仅描述底层问题或用户需求。不要将其与拟议补丁带来的风险混为一谈。将补丁引发的重大回归、兼容性、生命周期或维护风险单独报告为 `Patch risk`。

不要仅仅因为某个报告可能由 AI 发现或编写，就推断其价值较低。不要揣测作者身份或动机。通过客观信号识别为贡献而刻意构造的报告：缺少可复现行为、输入不切实际、调用路径不可能、重复已有处理、测试没有覆盖所声称的问题，或修复在运行时没有任何实际效果。

### 6. 应用维护者投入测试

使用该框架中的议题处置方式和 PR 检查项，判断结果是否值得投入永久性的代码、测试、文档和维护者精力。将代码质量与仓库就绪程度分开分类。

使用以下一种代码建议：

- **可按原样合并**：需求真实、实现可靠、范围适当、测试充分。
- **经过针对性修改后可合并**：需求真实且方向可行，但需要进行范围明确的修正。
- **应以更简单的替代方案取代**：需求真实，但更小或更连贯的修复方案更可取。
- **不值得继续完成**：影响可忽略或缺乏证据支持、行为无实际效果、抽象层次错误，或完成成本过高。

除非 `Need status` 为 `Demonstrated`，否则 `Merge-worthy as-is` 和 `Merge-worthy after focused changes` 均为无效结论。一组范围有限的实现修复无法将 `Plausible but unproven` 的需求提升为值得合并的建议。

对于 `Merge-worthy as-is` 和 `Merge-worthy after focused changes`，如果有助于传达集成状态，请使用以下一种仓库就绪状态：

- **就绪**：当前 head 可供审查，且所需检查均已通过。
- **CI 或审查待完成**：代码建议已经稳定，但所需的外部关卡尚未完成。
- **需要变基或解决冲突**：该 head 无法干净合并，或已实质性过时。
- **受阻**：某个具体的外部条件或仓库条件阻碍了可靠的合并决策。

对于 `Supersede with a simpler alternative` 和 `Not worth completing`，请省略仓库就绪状态；CI、审查、可合并性或分支新鲜度不会改变这些处置结论。应改为说明任何会实质性影响证据可信度的验证限制。包含就绪状态时，只能使用上述四种状态之一，不要自行创造诸如 `ready mechanically` 之类的变体，也不要使用变基状态来表示语义层面的过时。

不要仅仅因为 CI 尚未完成，就下调原本合理的代码建议。如果仍需解决语义冲突或进行实质性代码变更，不要声称 PR 已就绪。

当多个开放的 PR 处理同一问题时，应给出一个组合层面的建议：选择最强的 PR、要求对某个候选 PR 进行针对性修改、将具体思路整合到一个 PR 中、以更简单的方法取代所有候选方案，或关闭重复项。说明为什么推荐路径优于其他各个方案，但不要把报告变成逐行审查。

始终将提议的补丁与当前最强且已有依据支持的方法以及至少一种替代方案进行比较：不修改代码、进行验证或完善文档、采用范围更窄的修复、复用现有 helper，或在不同层级统一实施该不变量。如果审查仅证明补丁有效，却未说明当前产品为何无法满足底层需求，以及为何该设计更可取，那么审查就是不完整的。

当仍存在多个合理的语义范围、兼容性边界或公共 API 契约时，不要让贡献者在应由维护者决定的选项中作出选择。应根据证据、兼容性契约以及产品/API 设计原则确定首选范围，然后要求进行该项具体修改。如果证据不足以作出选择，请将审查标记为初步审查，或请求维护者提供意见；不要将开放式的实现分支作为应由贡献者作出的决定。

### 7. 报告发现和维护者操作

请按以下优先级选择评估所用语言：

1. 遵循当前对话中明确提出的语言要求。
2. 遵循来自 `~/.codex/AGENTS.md`、仓库的 `AGENTS.md` 或其他适用指令文件中的相关语言指令。
3. 如果最近几轮对话始终使用同一种语言，则使用该语言。
4. 否则，默认使用英语。

不要根据 GitHub URL、贡献者、代码或浏览器区域设置推断评估语言。无论评估语言是什么，维护者评论草稿都必须使用英语。报告应以决策为导向且保持精炼。默认使用不超过五条证据要点；只有当决策确实依赖更多证据时才增加。

使用 `references/evaluation-framework.md` 中匹配的精简报告变体。当仍在等待与决策相关的证据时，使用其中的初步评估变体，并在结尾说明证据限制，以及可选择另行开展运行时调查的建议，而不要给出最终建议。对于简单情况，应合并章节，而不是为了充实篇幅而扩展回答。优先列出意外或负面的运行时发现；当存在候选方案竞争时，明确指出首选的 PR 或方案。

对于 PR，将 `Need status` 放在代码建议之前。当需求状态不是 `Demonstrated` 时，首先说明该结果，省略仓库就绪情况，并避免将补丁修复作为维护者的主要行动。

当现有功能或更优替代方案对决策有实质影响时，在证据和建议中明确说明。指出确切的受支持路径、它覆盖和不覆盖的内容，以及它更可取的原因。不要将 `Not worth completing` 或 `Supersede with a simpler alternative` 的结论埋没在对实现质量的赞扬之下。

当建议关闭、请求更多证据、请求代码更改或取代某个 PR 时，附上框架中定义的、可直接复制粘贴的英文维护者评论。如果多个 PR 需要采取不同操作，请为每个受影响的 PR 分别标注一份草稿。主行动段落中仅包含会阻止合并的请求；可选的文档或润色事项应明确标为不阻止合并，或直接省略。

在返回任何维护者评论草稿之前，使用 `AGENTS.md` 中适用于整个仓库的规则以及 `references/evaluation-framework.md` 中的详细指南，执行一次 GitHub 粘贴就绪检查。在草稿中，同一仓库中的 issue 或 PR 使用 `#123`，跨仓库引用使用 `owner/repo#123`。从可直接复制的草稿中移除带 Markdown 链接的 issue 或 PR 标签、Codex 导航链接、本地文件链接、仅供 Codex 使用的引用标记或脚注，以及应用指令。保留指向 API 文档、设计说明及其他不使用 GitHub 原生 issue 或 pull-request 语法的目标的普通描述性链接。

还要执行一次行动差异检查。每个祈使句都必须对应当前远程 head 与期望状态之间的具体差异。移除要求“保持”、保留、记录、测试或更改当前 head 已经满足的行为，或并非合并阻断项的请求。`Merge-worthy as-is` 结果不得包含请求更改的措辞。除非针对该目标要采取的行动是处理重复项或取代关系，否则不要在面向贡献者的草稿中加入方案组合比较。

对于请求更改的评论，应将由维护者决定的语义选择表述为明确指令，而不是选项菜单。可以在理由中简要提及被否决的替代方案，但请求的行动必须明确所选择的行为、范围或兼容性边界。当 X 与 Y 的选择会改变 SDK 契约或用户可见语义时，应使用“请执行 X，因为……”而不是“执行 X 或 Y 均可”。

除非明确要求，否则不要逐行审查。不要将测试通过等同于值得合并，也不要将逻辑正确的补丁等同于具有实际价值。
