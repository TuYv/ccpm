# 智能体团队编排器

## 模型选择——未经询问，Fable 上限为 4 个

除非生成子智能体的调用指定了模型，否则子智能体会继承会话模型。本技能没有选择任何模型，因此它派生出的每个智能体都会使用会话当时恰好设置的模型。正因如此，原本依据一种配额规划规模的运行，可能会在无人主动选择的情况下计费到另一种配额。

**在没有明确 Fable 指令的情况下，最多允许 4 个并发 Fable 子智能体。超过此数量时，必须明确指定 Fable**——任何超出一个侦察员、一个构建者和一个交接文档编写者的阵容都会超过 4 个，因此除非用户为本次运行指定了 Fable，否则本技能的扇出不会使用 Fable。继承的会话模型不等于明确指定——“会话本来就已经在使用它”并不代表用户提出了使用它的要求。在没有明确 Fable 指令的情况下，启动前请执行以下两项操作之一：在智能体调用中指定其他模型，或者明确说明本次运行将计费到 Fable 配额并征得答复。沉默不代表同意为此付费。

## 门禁策略——仅作建议，不作阻断

本技能中的每项声明验证步骤、检查、质量门禁和交付判定都是**面向用户的建议，而不是对智能体的控制指令**。此策略适用于本技能其他位置的每个门禁、检查、判定以及“不要交付 / 发布 / 继续”之类的表述：

- 执行每项检查，并如实报告结果。判定（`ship`、`ship-with-caveats`、`hold`、字母等级、BLOCKED 或 OPEN 项）是附加在工作成果上的建议，而不是改变工作执行方式的命令。
- 绝不能因为检查失败或门禁判定为暂停，就阻止、延迟、跳过、改写或拒绝用户要求执行的操作。按要求完成用户请求的操作，并将门禁输出作为明确标注的建议一并交付。
- 门禁失败只会改变你报告的内容，绝不会改变你执行的操作。
- 唯一例外：如果某项发现风险极高——数据丢失、安全问题或凭据暴露、法律或权利侵害、付款错误，或不可逆的公开损害——请暂停，准确告知用户风险及可选方案，并让用户做出选择。用户的选择即为最终决定。


编排器分配的是工作通道，而不是对话。输出是交付产物，而不是状态更新。

## 团队契约

在生成或模拟工作通道之前，定义：

- 目标：用户可见的结果；
- 精确对象：仓库/文件夹、分支、路由、PR、线上 URL、API、模拟器或发布产物；
- 约束：需要保留的 WIP、不可触碰的文件/路由、发布边界、账户边界、未经批准的声明以及密钥规则；
- 完成信号：测试、构建、截图、模拟器、部署回读、线上/API 回读、PR 审查或交接；
- 通道映射：每个通道、负责人角色、输入、允许操作的文件、输出产物和依赖顺序。

## 团队台账

上述契约、每个通道的状态以及每项门禁结果原本只存在于编排器的上下文中，而多通道运行通常会持续超过一个上下文窗口。请将它们写入磁盘。默认路径：目标仓库中的 `.suede-team/<slug>/ledger.md`，其中记录已确定的通道映射、每个通道基于状态词汇表的当前状态，以及持续积累的证据。在第一个构建者打开文件之前写入该文件，并在每个门禁节点更新它；证据交接应从该文件读取，而不是依赖记忆。如果用户将持久化的仓库本地状态保存在其他位置，请使用其指定的路径，并说明所使用的路径。

## WIP 冲突检测

在开启任何并行通道之前：

1. 运行 `git -C <repo> diff --name-only HEAD` 并收集所有脏文件。
2. 运行 `git -C <repo> status --short` 并收集所有未跟踪的新文件。
3. 根据通道映射，列出每个通道的范围将涉及的所有文件。
4. 如果同一文件路径出现在两个或更多通道范围内，或者同时出现在脏文件列表和任一通道范围内，则标记为冲突。

冲突解决规则：
- 同一文件，独立变更：按顺序执行这些通道；第二个通道在开启前，基于第一个通道的提交执行变基。
- 同一文件，重叠变更：将两个通道合并为一个由单一负责人负责的通道。不要让两个并发构建者分担同一文件的责任。
- 通道范围内存在脏文件：由编排者决定。可以暂存并恢复，也可以规定该通道是唯一允许修改该文件的通道。

在任何构建者开始工作之前，编排者将解决后的通道映射写入团队账本（`.suede-team/<slug>/ledger.md`，参见“团队账本”）。构建者不得打开未包含在其所分配通道映射中的文件。

## 默认角色配置

从侦察员 + 构建者 + 交接文档撰写者开始。仅在需要设置关卡时添加角色：设计变更添加设计审查员，代码风险添加代码评分员 + 代码审查员，公开发布添加发布验证员。

- **侦察员：** 查找仓库、文档、当前状态、脏文件、线上路由以及
  可能的影响范围。
- **规划员：** 将需求转化为带有验收标准和依赖关系的可验证任务。
- **构建者：** 在现有系统内进行范围明确的代码或内容变更。
- **设计审查员：** 检查渲染后的视觉质量、响应式行为、
  可访问性、文案和状态覆盖情况。
- **代码评分员：** 从正确性、安全性、数据/状态、Suede 真实性、用户体验/发布行为、
  测试和部署就绪度等方面给出 A-F 级发布风险评分。
- **代码审查员：** 进行全上下文审查，并将发现的问题转化为修复简报。
- **可见性评分员：** 从可发现性、首屏清晰度、行动号召吸引力、佐证、AI
  可读性和设计信号等方面，对公开页面、GitHub Pages 站点、文档和
  发布界面进行评分。
- **发布验证员：** 检查构建、部署、线上/API 行为、App Store/iOS
  真实性、密钥和已发布声明。
- **交接文档撰写者：** 生成签署后的交付记录。如果交接文档遗漏任何必填字段（参见“交接质量检查清单”），则工作尚未完成；必须暂缓交付。

对于高风险工作，应将构建者和审查员分开。

## RFC 模式

对于重大架构决策、新功能设计或影响范围广泛的变更，应在启动构建者之前运行 RFC（意见征求）。

RFC 会在确定如何实施之前，强制各方先就做什么以及为什么做达成一致。

RFC 状态词汇：`draft | accepted | superseded | withdrawn`。

在撰写 RFC 之前，请阅读
[`references/incident-and-rfc-templates.md`](references/incident-and-rfc-templates.md)
并填写其中列出的每个章节——问题陈述、建议的解决方案、考虑过的替代方案、
风险、成功标准、决策记录。

以下情况必须提交 RFC：共享接口变更、schema 迁移、auth 流程重写、payment 路径变更、公共 API 契约变更，或任何已经讨论两次但仍未达成结论的方案。在 RFC 状态变为 `accepted` 之前，不得开启任何构建通道。

可跳过的情况：方案显而易见、影响范围有限且边界清晰的变更。

## 功能标志策略

并非每项变更都应该通过硬部署发布。功能标志支持渐进式发布、A/B 测试，以及无需重新部署的即时回滚。

**何时使用功能标志：**
- 生产流量路径中面向用户的新功能
- 对 auth、payment 或数据迁移路径的变更
- 任何无法通过 revert 即时回滚的变更（例如 schema 迁移）
- A/B 测试

一旦某个通道使用了功能标志，请在开始逐步扩大流量之前，阅读
[`references/scenario-templates.md`](references/scenario-templates.md)
中“功能标志策略”章节里的生命周期、不应使用功能标志的情形列表以及维护规范。
每个标志在创建时都必须设定移除日期；过期未清理的标志将被视为
P3 代码审查问题。

## 回滚决策树

部署后出现问题时，团队需要一个预先约定的决策框架，以避免陷入决策僵局。

```
Is there active data loss or corruption? → ROLLBACK IMMEDIATELY. Don't investigate first.
Is there a security exposure (PII, auth bypass, payment data)? → ROLLBACK IMMEDIATELY. Notify security.
Is a primary user path broken (login, checkout, core workflow)? → ROLLBACK unless fix is <15 minutes away.
Is performance degraded but functional? → Hold and investigate. Set a 30-minute timer.
Is it a cosmetic issue? → Hot-fix forward. No rollback.
```

回滚后：
1. 立即撰写摘要：回滚了什么、影响了什么、通知了谁。
2. 在 PR 中留下回滚说明，并创建后续 issue。
3. 在重新发布之前，进行一次轻量级事后复盘（见下文）。

## 事后复盘

对于任何生产事故、发布失败或重大回滚，都应进行事后复盘。坚持无责原则：关注系统，而非个人。

严重级别：P0（全面中断）/ P1（主要路径中断）/ P2（服务降级）/ P3（外观问题）。

P0 和 P1 事故必须进行事后复盘。P2 可选，但建议进行。P3 可跳过。
需要进行事后复盘时，请使用
[`references/incident-and-rfc-templates.md`](references/incident-and-rfc-templates.md)
中的模板编写，并填写每个部分：时间线、影响、根本原因、促成因素、做得好的方面，以及包含负责人和截止日期的行动项。

## 阶段循环

阶段循环是以最小规模运行的持续团队循环。当完整的 10 道关卡人员配置显得过度，但仍需要侦察、规划、构建、验证和发布阶段时，请使用阶段循环。

对于高风险变更，请在发布前参考回滚决策树。对于渐进式发布，请使用功能标志策略。对于共享接口变更，必须先进入 RFC 模式，之后才能开启规划阶段。

## 公共贡献计划

当目标是在自有或外部公共
repository 中开展重复性工作时，请在开启通道之前完整阅读
[`references/public-contribution-program.md`](references/public-contribution-program.md)。
使用其中的确定性 ledger 为任务评分，将每个 repo/issue 组合租约分配给一名工作者，并防止重复工作。
初始 authority 应设为 `local_only`，并禁用发布。
对于外部目标，应停留在已审核的贡献包阶段，除非用户另行批准创建草稿 PR。

对外产物门禁适用于分支名称、提交消息和 PR 文案。使用项目惯用语言，并省略自愿添加的工具来源品牌标识或尾注。绝不伪造作者身份或否认使用工具；上游披露要求优先于中性包装，并将该通道移交所有者审核。

## 模型分级

分配仍能正确完成该角色工作的能力最低的模型。整个团队中各模型的成本和延迟会累积；不要默认让每个通道都使用能力最强的模型。

- **机械性任务**（独立函数、单个文件、规范完整且无需判断）：使用能够胜任的最廉价模型。
- **集成和判断任务**（多文件协调、根据现有代码库进行模式匹配、非简单调试）：使用标准模型。
- **架构、设计和审核角色**（编写 RFC、代码评分、安全敏感型审核、发布验证）：使用可用的能力最强的模型。

当某个通道的任务复杂度不明确时，默认提高一个等级而不是降低；廉价模型返回 `NEEDS_CONTEXT` 或错误答案所产生的重新调度成本，比一开始就选用正确等级的模型更高。

## 构建者调度协议

被调度的构建者会在其输出进入审核之前报告以下四种状态之一。通道进入团队名单中的下一阶段之前，应分别进行相应处理：

- **已完成**：进入团队名单中的下一阶段。
- **已完成，但存在疑虑**：构建者已完成任务，但标记了疑虑。阅读该疑虑。如果涉及正确性或范围，请在审核前解决；如果只是单纯的观察事项，请在交接中注明并继续。
- **需要上下文**：构建者缺少通道映射本应提供的信息。提供该信息并重新调度同一个构建者；不要默默替它猜测。
- **已阻塞**：构建者无法继续。重新调度前先诊断原因：上下文缺口需要补充更多上下文，推理能力不足需要使用能力更强的模型，任务过大需要拆分成更小的通道，计划错误则升级给人工处理（参见升级协议）。绝不要在不做任何调整的情况下重新调度同一个构建者，并寄希望于得到不同结果。

如果构建者在任务过程中提出澄清问题，应先回答再让其继续；不要为了赶截止时间而让它在问题尚未解决时自行猜测。

## 持续团队循环

使用能够完成工作的最小循环，但当任务范围广、风险高、与发布相关，或用户要求使用最大规模的智能体团队时，应有意识地升级。

选择循环：

- **顺序式：**适用于范围明确的常规工作，也是默认选择。
- **持续 PR：**适用于严格 CI、PR 审核、分支规范或公开发布管控至关重要的情况。
- **RFC/DAG：**适用于在实施前需要进行任务拆解、设计决策或依赖排序的工作。应先运行 **RFC 模式**，记录问题陈述、建议解决方案、替代方案、风险和决策记录，然后再启动构建者。
- **探索式并行：**适用于多个独立方案、审计或表层检查可以在不修改相同文件的情况下并行开展的情况。
- **恢复：**适用于检查失败、缺陷反复出现、发布受阻、声明偏离事实或循环空转之后。

对于 max-agent 工作，仅在必要时按以下职责序列逐级推进：

```text
Scout -> Planner -> Builder lane(s) -> Design reviewer -> Visibility grader
-> Code grader -> Code reviewer -> Release verifier -> Handoff writer
```

在该职责序列外设置以下门禁：

1. **循环选择：**说明为何选择顺序循环、持续 PR、RFC/DAG、
   探索式并行或恢复循环。
2. **团队契约：**明确目标、交付对象、约束、工作通道图、依赖
   顺序、完成信号和发布门禁。
3. **规划质量门禁：**确保任务原子化、验收标准可观察、
   指定文件/界面、覆盖必备要求，并明确发布/账户边界。
4. **在制工作所有权门禁：**每个构建者明确负责特定文件或界面；任何
   冲突都必须按顺序处理。
5. **执行波次：**仅当输出不会发生冲突时，才并行执行工作通道。
6. **质量/评估门禁：**执行相关的源内容、文案、设计、代码、
   可见性、构建、截图、API 或线上检查。检查失败后，最多允许进行
   三次真正不同的修复——每次尝试都必须改变诊断结论或策略。如果
   相同的根本原因反复出现，应提前停止，并将这一重复原因上报给用户。
7. **对抗性审查：**询问结果会如何在生产环境、发布、
   已发布声明、滥用、无障碍、移动端或交接环节中失败。
8. **共识审查：**将多个审查视角合并为阻塞项、已接受的
   注意事项、立即修复项和后续事项。
9. **发布锁：**在作出任何公开完成声明之前，构建/部署/线上/API/App Store/iOS/已发布声明的准确性
   由发布验证者负责。
10. **证据交接：**记录变更文件、命令、截图或 URL、
    验证结果、注意事项、阻塞项、状态和下一步行动。

循环停滞协议：(1) 冻结除失败通道之外的所有通道，(2) 分配一个仅诊断通道（不进行修复，只查明根本原因），(3) 编写仅包含一项验收标准的差距计划，(4) 仅处理该差距，(5) 重新运行最初失败的检查。在该检查通过之前，不得扩大处理范围。

## 通道间通信

当构建者通道完成其输出，且审查者通道依赖该输出时，必须显式发出信号，而不能默认其已完成。

完成工作的通道应写入一则 Lane Ready 通知：

```
Lane: [name]
Status: output ready for review
Artifact: [file path, URL, or PR link]
Reviewer: [lane name that receives this output]
Unresolved: [any known issue the reviewer should know before starting]
```

在收到其通道图中每个上游依赖项发出的 Lane Ready 通知之前，审查者通道不得启动。

编排器负责转发 Lane Ready 通知。在顺序线程中，编排器应代表每个已完成工作的通道发布 Lane Ready 通知，然后再调用下一个通道。

如果通道的输出尚未依据团队契约中的验收标准进行验证，则该通道不得自行声明已就绪。

## 规划质量门禁

规划只有满足以下条件才算就绪：

- 每项任务只涉及一个关注点；
- 依赖项已按顺序排列；
- 验收标准是可观察的，而非主观的；
- 已指定所需的文件或界面；
- 已覆盖必备要求；
- 测试、截图、构建或 API 检查与高风险行为相对应；
- 发布和账户边界已明确。

如果仍存在重大不确定性，请先进行一次简短的探索性验证，并在验证结果返回之前将实施排除在范围之外。

## 评审收敛

对于重要的合并，至少从两个相互独立的视角进行评审：

- 一个视角关注实现是否按预期工作；
- 另一个视角关注它可能如何在生产、评审、发布或公开使用中失败。

将评审结果合并为：

- 一致认定的阻塞项；
- 合理但存在分歧的风险；
- 已接受的注意事项；
- 需要立即执行的修复；
- 不应构成阻塞的后续事项。

重复修复和评审周期，直到不存在阻塞项，或工作进入暂停状态。

## 状态词汇

有效状态依次为：`scoped` → `planned` → `executing` → `changed locally` → `verified locally` → `reviewed` → `committed` → `pushed` → `deployed` → `verified live` → `released`

中断状态：`blocked`（需要外部操作）| `held`（需要完成指定的修复后才能继续）

不要跳过任何状态。`changed locally` 不等于 `verified locally`。`deployed` 不等于 `verified live`。在团队契约规定的完成信号通过之前，不要标记为 `released`。

## 升级协议

停止循环，明确报告相关状况，并等待人工批准后再继续。

| 状况 | 阈值 | 操作 |
|---|---|---|
| 重复修复周期 | 同一项失败检查的修复与重新运行周期 > 3 次 | 停止。编写诊断摘要。询问：验收标准是否正确，还是修复策略有误？ |
| 严重程度未知的安全发现 | 任何涉及身份验证、会话、PII、支付数据或访问控制，且无法确信可归类为低风险的发现 | 停止。不要尝试修复。明确报告具体发现和不确定的影响范围。由人工决定下一步。 |
| 发生数据暴露的生产事件 | 任何迹象表明生产日志、错误报告或用户报告中暴露了 PII、支付数据或身份验证令牌 | 停止所有工作流。触发回滚决策树。立即通知人工。在回滚之前不要进一步调查。 |
| 成本激增 | 在没有获得已验证输出的情况下调用工具 > 20 次，或单次循环中预计的 API/基础设施成本 > $50 | 停止。总结进展和剩余范围。请求人工授权继续。 |
| 约束冲突 | 团队契约中的两项约束互相排斥 | 停止规划。通过具体示例说明冲突。在人工解决之前不要继续。 |

任何代理都不得通过重新界定任务范围或在未经人工确认的情况下宣称状况已经解决，来绕过升级阈值。

## 危险信号——停止

- “这些执行通道可能不会修改相同的文件”——“可能”并不是执行通道映射。请先运行 WIP 冲突检测。
- “实现方案显而易见，跳过 RFC”——如果经过两次讨论仍未得出结论，那它就并非显而易见。
- “标记为完成吧，代码已经写好了”——`changed locally` 并不等同于 `verified locally`；状态词汇不允许使用捷径。
- “别写那个注意事项，这样交接看起来更干净”——缺少字段的交接状态是 `held`，而不是完成。
- “再修一轮就能解决”——如果同一项检查已连续失败超过 3 轮，请停止并执行循环停滞协议。
- “构建者可以评审自己的执行通道”——对于高风险工作，构建者和评审者必须相互独立。

## 交接质量检查清单

只有当以下每个字段都已填写且内容真实时，交接才算完整。交接撰写者需确认每一项，以表示认可。

必填字段：
- [ ] 目标：确切的仓库、分支、路由或 URL（不能写“主应用”）
- [ ] 变更：每个被修改、创建或删除的文件路径（不能写“多个文件”）
- [ ] 命令：按顺序列出运行过的每条 bash 命令，并附上实际输出或退出代码
- [ ] 验证：可观察的证据（截图 URL、测试输出、curl 响应、构建日志），不能只写“可以正常工作”
- [ ] 状态：必须是状态词汇中的一种；除非已满足团队契约中的完成信号，否则不能写“完成”
- [ ] 下一步：最重要且尚未解决的单一步骤（不能写“见上文”）
- [ ] 注意事项：所有已知的限制、假设或延期事项；不得为了让交接看起来更干净而省略任何内容

如果缺少任何字段，交接撰写者必须先补充完整，才能将状态标记为 `released` 或 `verified live`。缺少字段的交接状态为 `held`。

## 路由

- 工作是对单个仓库的一项变更，并且可由一个打包的 DAG 端到端执行 →
  **suede-graph-flo-xr**。优先级规则：涉及单个仓库、单项变更，并可在一次
  脚本化运行中完成从研究到发布的工作交由该技能；需要手动处理、持续进行、
  跨仓库或属于公共贡献计划的编排工作则保留在此处。此处计划中的单个执行通道
  如果需要完整的研究与反驳流程，可以仅将该执行通道交给 **suede-graph-flo-xr**。
- 需要议题租约、隔离工作树、评审以及权限门控数据包的周期性自有/公共仓库贡献计划 → 阅读
  `references/public-contribution-program.md`，并继续将此技能用作控制器
- 代码执行通道需要评审或发布评级 → **suede-code**（组合模式）、**suede-code-review**（仅提供发现结果）或 **suede-code-grader**（仅提供评级）
- 仓库的合并门禁薄弱或缺失 → **suede-ci-gate**
- 工作需要分支所有权、陈旧镜像工作树设置、收尾选项或清理规范 → **suede-git-hygiene**（Suede Labs 私有配套技能，不包含在此包中）
- 某个执行通道会发布 AI 行为 → 在该执行通道的质量门禁关闭前使用 **suede-ai-eval**
- 公开发布执行通道需要页面判定 → **suede-visibility-grader**，然后使用 **suede-launch-packaging**
