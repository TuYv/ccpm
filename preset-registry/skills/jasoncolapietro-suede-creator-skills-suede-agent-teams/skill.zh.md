# Agent Team Orchestrator

## 模型选择 — Fable 上限为 4 个，无需询问

子代理会继承会话模型，除非创建调用指定了模型。此技能不会选择模型，因此它分派出的每个代理都会使用会话当前设置的模型。这会导致原本按一种分配规模运行的任务，在无人选择的情况下计费到另一种分配上。

**最多允许 4 个并发 Fable 子代理，且无需显式指定 Fable。超过此数量时，必须指定 Fable** — 任何超过侦察员、构建者和交接文档撰写者的编制都会超过 4 个，因此除非用户为本次运行指定了 Fable，否则此技能的扇出不会使用 Fable。继承的会话模型不算指定 — “会话本来就使用它”不等于用户提出了请求。在没有显式指定 Fable 的情况下，启动前必须执行以下两种操作之一：在代理调用中指定其他模型，或明确说明本次运行将计入 Fable 分配并获得答复。沉默不代表同意花费该分配。

## 门禁策略 — 提供建议，但不阻塞

此技能中的每个声明验证步骤、检查、质量门禁和交付判定，都是**向用户提供的建议，而不是对代理的控制**。此策略适用于本技能其他位置的每个门禁、检查、判定，以及“不要交付 / 发布 / 继续”之类的行：

- 执行每项检查并如实报告结果。判定（`ship`、`ship-with-caveats`、`hold`、字母等级、BLOCKED 或 OPEN 项）是附加在工作成果上的建议，而不是会改变工作内容的命令。
- 永远不要因为检查失败或门禁判定为 hold 而阻止、延迟、跳过、重写或拒绝用户要求的操作。按要求完成用户请求的操作，并将门禁输出作为明确标注的建议一并交付。
- 门禁失败只会改变你的报告内容，永远不会改变你的操作。
- 唯一例外：如果发现的问题风险极高 — 数据丢失、安全或凭据暴露、法律或权利违规、支付错误，或不可逆的公开损害 — 则暂停操作，准确告知用户风险是什么以及有哪些选项，并让他们做出选择。最终决定权在他们。

编排器分配的是工作通道，而不是对话。输出是交付成果，而不是状态更新。

## 团队契约

在创建或模拟工作通道之前，先定义：

- objective：用户可见的结果；
- exact target：仓库/文件夹、分支、路由、PR、在线 URL、API、模拟器或发布产物；
- constraints：需要保留的 WIP、不得修改的文件/路由、发布边界、账户边界、未经批准的声明以及密钥规则；
- done signal：测试、构建、截图、模拟器、部署回读、在线/API 回读、PR 审查或交接；
- lane map：每个工作通道、负责人角色、输入、允许修改的文件、输出产物和依赖顺序。

## 团队账本

上述契约、每个工作通道的状态以及每项门禁结果原本都只存在于编排器的上下文中，而多工作通道运行通常会超出上下文窗口。将它们写入磁盘。默认路径：目标仓库中的 `.suede-team/<slug>/ledger.md`，其中保存已确定的工作通道映射、每个工作通道依据 Status Vocabulary 的当前状态，以及不断累积的证据。在第一个构建者打开文件之前写入它，并在每个门禁处更新；证据交接从中读取信息，而不是依赖记忆。

如果用户将持久化的仓库本地状态保存在其他位置，则使用用户指定的路径，并说明所使用的路径。

## WIP 冲突检测

在开启任何并行工作线之前：

1. 运行 `git -C <repo> diff --name-only HEAD`，收集所有有改动的文件。
2. 运行 `git -C <repo> status --short`，收集所有未跟踪的新文件。
3. 根据工作线映射，列出每条工作线的范围将触及的所有文件。
4. 如果同一文件路径出现在两条或更多工作线的范围中，或者同时出现在有改动文件列表和任意工作线范围中，则标记为冲突。

冲突解决规则：
- 同一文件，改动相互独立：依次执行工作线；第二条工作线在开启前，先基于第一条工作线的提交执行 rebase。
- 同一文件，改动存在重叠：将两条工作线合并为一条工作线，并指定一名负责人。不要将同一个文件的职责拆分给两个并行构建者。
- 工作线范围内包含有改动的文件：由协调者决定。可以暂存并恢复改动，也可以将该工作线指定为唯一允许触及该文件的工作线。

在任何构建者开始工作之前，协调者将解决后的工作线映射写入团队台账（`.suede-team/<slug>/ledger.md`，参见团队台账）。任何构建者都不得打开不在其分配的工作线映射中的文件。

## 默认人员配置

从 Scout + Builder + Handoff Writer 开始。只有在需要某个门禁时才添加角色：设计变更添加 Design Reviewer，代码风险添加 Code Grader + Code Reviewer，公开发布添加 Release Verifier。

- **Scout：** 查找仓库、文档、当前状态、有改动的文件、实际路由以及
  可能的影响范围。
- **Planner：** 将需求转化为包含可验证任务、验收标准和依赖关系的计划。
- **Builder：** 在现有系统内进行范围狭窄的代码或内容变更。
- **Design reviewer：** 检查渲染后的视觉质量、响应式行为、
  无障碍、文案和状态覆盖情况。
- **Code grader：** 从正确性、安全性、数据/状态、Suede 事实准确性、UX/发布行为、
  测试和部署准备度等方面评定 A-F 级别的发布风险。
- **Code reviewer：** 进行完整上下文审查，并将发现的问题转化为修复简报。
- **Visibility grader：** 从可查找性、首屏清晰度、CTA 吸引力、证明材料、
  AI 可读性和设计信号等方面，对公共页面、GitHub Pages 站点、文档和
  发布页面进行评级。
- **Release verifier：** 检查构建、部署、线上/API 行为、App Store/iOS
  事实准确性、密钥和已发布声明。
- **Handoff writer：** 生成签署后的交付记录。如果交接遗漏任何必填字段（参见交付质量检查清单），则工作尚未完成；交付将被搁置。

对于高风险工作，应将构建者与审查者分开。

## RFC 模式

对于重大的架构决策、新功能设计或影响范围广泛的变更，在生成构建者之前先运行 RFC（征求意见）。

RFC 会在确定 HOW 之前，强制团队就 WHAT 和 WHY 达成一致。

RFC 状态词汇：`draft | accepted | superseded | withdrawn`。

在编写 RFC 之前，请阅读
[`references/incident-and-rfc-templates.md`](references/incident-and-rfc-templates.md)
并填写其中列出的每个部分——问题陈述、提议的解决方案、考虑过的替代方案、风险、
成功标准和决策记录。

以下情况必须要求 RFC：共享接口变更、架构迁移、身份验证流程重写、支付路径变更、公共 API 契约变更，或任何已经讨论过两次但仍未达成决议的方案。在 RFC 状态为 `accepted` 之前，不得开启任何构建通道。

跳过条件：变更清晰且范围明确，方案显而易见，影响范围狭窄。

## Feature Flag 策略

并非所有变更都应作为硬部署发布。Feature Flag 支持渐进式发布、A/B 测试，以及无需重新部署即可即时回滚。

**使用 Feature Flag 的情况：**
- 生产流量路径中的面向用户的新功能
- 对身份验证、支付或数据迁移路径的变更
- 任何无法通过 revert 即时回滚的变更（例如架构迁移）
- A/B 测试

一旦某个通道启用了 Feature Flag，在开始逐步放量之前，请阅读 [`references/scenario-templates.md`](references/scenario-templates.md) 的 Feature Flag 策略部分中的生命周期、无需使用 Feature Flag 的情况列表以及规范规则。每个 Feature Flag 在创建时都必须设置移除日期；过期的 Feature Flag 属于 P3 代码审查问题。

## 回滚决策树

部署后出现问题时，团队需要一套预先达成共识的决策框架，以避免陷入犹豫不决。

```
是否存在正在发生的数据丢失或损坏？→ 立即回滚。不要先调查。
是否存在安全暴露（PII、身份验证绕过、支付数据）？→ 立即回滚。通知安全团队。
主要用户路径是否中断（登录、结账、核心工作流）？→ 回滚，除非修复能在 <15 分钟内完成。
性能是否下降但功能仍可用？→ 暂停并调查。设置 30 分钟计时器。
是否只是界面问题？→ 直接热修复。不要回滚。
```

回滚后：
1. 立即撰写摘要：回滚了什么、受到什么影响、通知了谁。
2. 在 PR 中留下回滚备注，并创建后续跟进问题。
3. 在重新发布之前，执行一次轻量级事后复盘（见下文）。

## 事后复盘

对于任何生产事故、发布失败或重大回滚，都要执行事后复盘。坚持无责原则：关注系统，而不是个人。

严重级别：P0（完全中断）/ P1（主要路径中断）/ P2（性能下降）/ P3（界面问题）。

P0 和 P1 事故必须进行事后复盘。P2 可选，但建议进行。P3 跳过。
需要进行事后复盘时，请根据
[`references/incident-and-rfc-templates.md`](references/incident-and-rfc-templates.md)
撰写，并填写每个部分：时间线、影响、根本原因、促成因素、进展顺利的方面，以及包含负责人和截止日期的行动项。

## 阶段循环

阶段循环是以最小规模运行的持续团队循环。当完整的 10 个关卡名册过于繁重，但仍需要侦察、规划、构建、验证和发布阶段时，请使用它。

对于高风险变更，请在发布前参考回滚决策树。对于渐进式发布，请使用 Feature Flag 策略。对于共享接口变更，在开放规划阶段之前，必须启用 RFC 模式。

## 公共贡献计划

当目标是在自有或外部公共代码仓库中开展重复性工作时，请在开启通道之前完整阅读
[`references/public-contribution-program.md`](references/public-contribution-program.md)。
使用其中的确定性台账为任务评分，将每个代码仓库/问题对租约给一名工作者，并防止重复工作。以
`local_only` 权限级别开始，并禁用发布功能。除非用户另行批准草稿 PR，否则请将外部目标保持为经过审核的贡献数据包。

对外产物门禁适用于分支名称、提交消息和 PR 文案。使用符合项目惯例的语言，并省略自愿添加的工具来源品牌标识或尾注。绝不伪造作者身份或否认工具使用；上游披露要求优先于中性包装，并将该通道转交所有者审查。

## 模型分层

分配仍能正确完成该角色的能力最低的模型。成本和延迟会在整个成员列表中累积；不要默认将每个通道都分配给能力最强的模型。

- **机械性任务**（独立函数、单个文件、没有判断需求的完整规格）：使用成本最低且有能力的模型。
- **集成与判断任务**（多文件协调、针对现有代码库进行模式匹配、非简单调试）：使用标准模型。
- **架构、设计和审查角色**（RFC 编写、代码评估、安全敏感审查、发布验证）：使用可用的能力最强模型。

当通道任务的复杂度不明确时，默认上调一个层级而非下调；廉价模型返回 `NEEDS_CONTEXT` 或错误答案所造成的重新分派成本，高于一开始就使用合适层级模型的成本。

## 构建者分派协议

被分派的构建者在其输出进入审查前会报告四种状态之一。在通道进入成员列表的下一阶段前，处理每一种状态：

- **完成**：继续进入成员列表中的下一阶段。
- **完成但有顾虑**：构建者已完成，但标记了一个疑问。阅读该顾虑。若涉及正确性或范围，请在审查前解决；若只是单纯观察，请在交接中记录并继续。
- **需要上下文**：构建者缺少通道映射本应提供的信息。提供该信息并重新分派同一构建者；不要代替它悄然猜测。
- **受阻**：构建者无法继续。在重新分派前诊断原因：上下文缺口应补充更多上下文，推理缺口应换用能力更强的模型，任务过大应拆分为更小的通道，错误计划应升级给人工处理（参见升级协议）。绝不要在不做任何改变的情况下重新分派同一构建者，并期待不同结果。

在任务中途提出澄清问题的构建者，会在继续前得到答复；不要让它为了赶截止日期而猜测未解决的问题。

## 持续团队循环

使用能够完成工作的最小循环，但当任务范围广、风险高、受发布约束，或用户要求使用最大规模的代理团队时，应有意识地升级。

选择循环：

- **顺序执行：**正常范围明确的工作默认使用。
- **持续 PR：**当严格 CI、PR 审查、分支规范或公开发布控制很重要时使用。
- **RFC/DAG：**当工作在实施前需要拆分、设计决策或依赖排序时使用。先运行 **RFC 模式**，在生成构建者前记录问题陈述、拟议解决方案、替代方案、风险和决策记录。
- **探索性并行：**当多个相互独立的方法、审计或表面检查可以在不触及相同文件的情况下运行时使用。
- **恢复：**在检查失败、重复缺陷、发布受阻、声明偏离或循环反复时使用。

对于 max-agent 工作，仅在需要时通过以下名册进行升级：

```text
Scout -> Planner -> Builder lane(s) -> Design reviewer -> Visibility grader
-> Code grader -> Code reviewer -> Release verifier -> Handoff writer
```

使用以下关卡包裹该名册：

1. **循环选择：**说明为何该循环是顺序式、持续 PR、RFC/DAG、
   探索性并行或恢复式。
2. **团队契约：**目标、产出、约束、泳道映射、依赖
   顺序、完成信号和发布关卡。
3. **规划质量关卡：**原子任务、可观察的验收标准、
   已命名的文件/界面、必备要求、发布/账户边界。
4. **WIP 所有权关卡：**每个构建者拥有明确的文件或界面；任何
   冲突均应按顺序处理。
5. **执行波次：**仅当输出不会冲突时才并行执行泳道。
6. **质量/评估关卡：**运行相关的源码、文案、设计、代码、
   可见性、构建、截图、API 或线上检查。失败的检查最多可获得
   三次真正不同的修复机会——每次尝试都必须改变诊断或策略。当
   相同根本原因重复出现时，应提前停止，并将重复原因升级给用户。
7. **对抗性评审：**询问结果会如何在生产环境、发布、
   已发布声明、滥用、无障碍访问、移动端或交接中失败。
8. **共识评审：**将多个评审视角合并为阻塞项、已接受的注意事项、
   立即修复项和后续跟进项。
9. **发布锁定：**在任何公开完成声明之前，构建/部署/线上/API/App Store/iOS/已发布声明的准确性
   均由发布验证者负责。
10. **证据交接：**记录变更文件、命令、截图或 URL、
    验证、注意事项、阻塞项、状态和下一步操作。

循环停滞协议：(1) 冻结除失败泳道之外的所有泳道，(2) 分配一个仅诊断泳道（不修复，仅分析根本原因），(3) 编写包含单一验收标准的缺口计划，(4) 仅执行该缺口，(5) 重新运行原始失败检查。在该检查通过之前，不得扩大范围。

## 泳道间通信

当一个构建者泳道完成其输出，且某个评审者泳道依赖该输出时，信号必须明确，而非默认推定。

完成的泳道会写入一则泳道就绪通知：

```
Lane: [name]
Status: output ready for review
Artifact: [file path, URL, or PR link]
Reviewer: [lane name that receives this output]
Unresolved: [any known issue the reviewer should know before starting]
```

评审者泳道在收到其泳道映射中每个上游依赖发出的泳道就绪通知之前，不得启动。

编排者负责路由泳道就绪通知。在顺序线程中，编排者代表每个完成的泳道发布泳道就绪通知，然后再调用下一个泳道。

如果泳道的输出尚未依据团队契约中的验收标准完成验证，则不得自行声明就绪。

## 规划质量关卡

在满足以下条件之前，计划尚未就绪：

- 每项任务只关注一个事项；
- 依赖关系已排序；
- 验收标准可观察，而非主观；
- 所需文件或界面已命名；
- 必备要求已覆盖；
- 测试、截图、构建或 API 检查映射到高风险行为；
- 发布和账户边界明确。

如果仍存在重大不确定性，先进行一次简短的探索，并在探索报告返回前将实施排除在范围之外。

## 审查收敛

对于重要合并，至少运行两种独立的审查视角：

- 一种审查实现是否按预期工作；
- 一种审查它可能如何在生产环境、审查、发布或公开使用中失败。

将发现合并为：

- 共识阻塞项；
- 合理但存在分歧的风险；
- 已接受的注意事项；
- 现在要执行的修复；
- 不应阻塞的后续事项。

重复修复和审查循环，直到不再存在阻塞项或工作被搁置。

## 状态词汇

按顺序排列的有效状态：`scoped` → `planned` → `executing` → `changed locally` → `verified locally` → `reviewed` → `committed` → `pushed` → `deployed` → `verified live` → `released`

中断状态：`blocked`（需要外部操作）| `held`（继续之前需要指定修复）

不得跳过。`changed locally` 不等于 `verified locally`。`deployed` 不等于 `verified live`。在 Team Contract 的完成信号通过之前，不得标记为 `released`。

## 场景模板

针对常见的高风险部署，存在六种预构建配置：(a) Auth Rewrite、
(b) Payment Integration、(c) Public Launch Review、(d) Data Migration、(e) Performance
Audit、(f) Recovery / Incident Response。当目标与其中某项匹配时，先完整阅读
[`references/scenario-templates.md`](references/scenario-templates.md)，
再开启通道，并且只调整已命名的目标——每个模板都包含自己的
成员名单、通道映射、RFC 和标志要求、评分器容差以及完成信号。

## 升级协议

停止循环，公开该条件，并在继续之前等待人工签核。

| 条件 | 阈值 | 操作 |
|---|---|---|
| 重复修复循环 | 同一失败检查经过 > 3 次修复-重跑循环 | 停止。撰写诊断摘要。询问：验收标准是否正确，还是修复策略有误？ |
| 严重程度未知的安全发现 | 任何涉及 auth、session、PII、payment data 或 access control，且无法确信地归类为低风险的发现 | 停止。不要尝试修复。公开确切发现和不确定的影响范围。由人工决定下一步。 |
| 发生数据暴露的生产事故 | 生产日志、错误报告或用户报告中任何表明 PII、payment data 或 auth token 暴露的迹象 | 停止所有通道。触发回滚决策树。立即通知人工。在回滚前不要进一步调查。 |
| 成本激增 | 在没有已验证输出的情况下 > 20 次工具调用，或单次循环预计 API/基础设施成本 > $50 | 停止。总结进展和剩余范围。请求人工授权继续。 |
| 相互矛盾的约束 | Team Contract 中两项约束彼此排斥 | 停止规划。用具体示例公开冲突。在人工解决之前不得继续。 |

任何代理都不得通过重新界定任务范围，或在未经人工确认的情况下宣布条件已解决，来覆盖升级阈值。

## 红旗 — 停止

- “这些执行线大概不会改到相同文件”——“大概”不是执行线地图。先运行 WIP 冲突检测。
- “方案很明显，跳过 RFC”——如果已经讨论过两次仍未解决，那就不明显。
- “标记为完成，代码已经写好了”——`changed locally` 不等于 `verified locally`；状态词汇表没有捷径。
- “不要写那个注意事项，让交接看起来更干净”——缺少字段的交接状态是 `held`，不是完成。
- “再来一个修复周期就能解决”——同一项失败检查超过 3 个周期后，停止并运行循环停滞协议。
- “构建者可以审查自己的执行线”——对于高风险工作，构建者和审查者必须保持分离。

## 交接质量检查清单

只有在下方每个字段都已填写且真实无误时，交接才算完成。交接编写者通过确认每一项来签署确认。

必填字段：
- [ ] 目标：准确的仓库、分支、路由或 URL（不是“主应用”）
- [ ] 变更：每个被修改、创建或删除的文件路径（不是“多个文件”）
- [ ] 命令：按顺序列出运行过的每条 bash 命令，以及实际输出或退出代码
- [ ] 验证：可观察的证据（截图 URL、测试输出、curl 响应、构建日志），不是“它能用”
- [ ] 状态：词汇表中的一种状态；除非满足 Team Contract 中的完成信号，否则不能写“完成”
- [ ] 下一步：唯一最重要的未解决步骤（不是“见上文”）
- [ ] 注意事项：所有已知限制、假设或延期事项；不得为了让交接看起来更干净而省略

如果任何字段缺失，交接编写者必须在将状态标记为 `released` 或 `verified live` 前补全。缺少字段的交接状态为 `held`。

## 路由

- 工作是单个仓库的变更，并且一个打包的 DAG 可以端到端运行它 →
  **suede-ship**。优先规则：单个仓库、单项变更、在单次脚本运行中完成从调研到发布的工作，应交由此处；手动、持续进行、跨仓库的编排，或公开贡献计划则保留在这里。这里的计划中，若某条单独执行线需要完整的调研与证伪处理，可以仅将该执行线交给 **suede-ship**。
- 一个持续性的、自主拥有的/公开仓库贡献计划需要议题租约、隔离工作树、审查和经权限门控的数据包 → 阅读
  `references/public-contribution-program.md`，并将此技能保留为控制器
- 代码执行线需要审查或发布等级 → **suede-code**（组合）、**suede-code-review**（仅发现项）或 **suede-code-grader**（仅评分）
- 仓库的合并门禁较弱或缺失 → **suede-ci-gate**
- 工作需要分支所有权、过期镜像工作树设置、完成选项或清理规范 → **suede-git-hygiene**（私有的 Suede Labs 配套工具，不在此包中）
- 某条执行线发布 AI 行为 → 在该执行线的质量门禁关闭前使用 **suede-ai-eval**
- 公开发布执行线需要页面判定 → **suede-visibility-grader**，然后 **suede-launch-packaging**
