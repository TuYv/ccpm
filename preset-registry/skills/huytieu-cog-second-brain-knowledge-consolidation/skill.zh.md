# COG 知识整合技能

## 目的
通过模式识别和系统化综合，将来自脑 dump、每日简报和回顾记录的零散洞见转化为连贯的框架和“单一事实来源”知识文档。

## 何时调用
- 用户希望整合其洞见
- 用户说“整合知识”“构建框架”“综合洞见”
- 到了定期维护知识库的时间（每周、每月、每季度）
- 用户希望从积累的脑 dump 中提取模式
- 在可能受益于框架参考的重大决策之前

## Agent 模式感知

**检查 `00-inbox/MY-PROFILE.md` frontmatter 中的 `agent_mode`：**
- 如果 `agent_mode: team` — 将扫描和模式提取工作委派给并行子代理（例如，为每个领域分配一个代理：个人脑 dump、职业脑 dump、项目专属内容、每日简报）。每个代理识别主题和模式，然后由一个综合代理将发现结果整合为框架。
- 如果 `agent_mode: solo`（默认）— 直接处理所有扫描、模式识别和框架构建工作。不进行委派。

## 预检

**获取当前时间戳（生成任何文件之前必须执行）：**

1. 使用 Bash 运行 `date '+%Y-%m-%d %H:%M'`，获取实际的当前日期和时间
2. 存储该值，并将其用于 `created:` frontmatter 字段
3. 绝 NEVER 猜测或伪造时间——始终使用 `date` 命令返回的值

## 流程

### 1. 数据收集

**扫描 vault，查找尚未处理或仅部分处理的内容：**

- 上次整合以来的所有脑 dump：
  - `02-personal/braindumps/`
  - `03-professional/braindumps/`
  - `04-projects/*/braindumps/`
  - `00-inbox/braindump-*.md`（混合领域）

- 每日简报和回顾记录：
  - `01-daily/briefs/`
  - `01-daily/checkins/`

- 以下位置中的任何会议记录或项目文档：
  - `04-projects/*/planning/`
  - `04-projects/*/resources/`

**确定范围：**
- 询问用户：“我应该分析哪个时间段？（上周、上个月、上个季度、全部时间，还是自定义范围？）”
- 识别尚未处理的内容（检查是否存在 `status: "captured"` 或缺少整合元数据）

**收集统计信息：**
- 要分析的文档总数
- 按领域和类型划分的明细
- 覆盖的日期范围

### 2. 模式识别

对所有内容应用系统化的模式检测：

#### 频率分析
**哪些内容反复出现？**
- 识别在多份文档中提及的主题
- 跟踪主题频率和聚类情况
- 识别持续存在的问题或担忧
- 发现反复出现的行动项或决策

#### 时间聚类
**哪些洞见是在同一时期出现的？**
- 按时间段对相关洞见进行分组
- 识别思考如何随时间演变
- 识别思考发生转变的转折点
- 绘制触发变化的催化因素

#### 领域关联
**哪些模式跨越了多个领域？**
- 影响职业思考的个人洞见
- 应用于项目的职业经验
- 促成个人成长的项目经历
- 横跨所有领域的战略主题

#### 矛盾分析
**思考在哪里发生冲突？**
- 识别相互矛盾的想法或方法
- 区分演变与不一致
- 理解解决过程或持续存在的张力
- 跟踪观点随时间的变化

#### 跨领域模式
**贯穿所有维度的元模式：**
- 决策方式
- 问题解决策略
- 学习模式
- 情绪/能量模式
- 关系模式
- 创作过程

### 3. 框架开发

将模式综合为可执行的框架：

#### 识别核心原则
**从零散的洞见到基本真理：**
- 模式揭示了哪些更深层的原则？
- 涌现出了哪些规则或启发式方法？
- 正在形成哪些心智模型？
- 哪些策略已被证明有效？

#### 根据证据进行检验
**使用源材料验证框架：**
- 源材料中的洞见是否支持这些原则？
- 是否存在反例或例外？
- 我们对这个框架的信心有多大？
- 边界条件是什么？

#### 定义边界
**框架何时适用/不适用？**
- 这个框架适用于哪些情境？
- 它有哪些局限？
- 什么时候不应使用它？
- 它依赖哪些假设？

#### 创建应用
**如何使用这个框架：**
- 具体使用场景
- 决策应用
- 问题解决模板
- 实际实施步骤

### 4. 知识整合

更新和创建知识库文档：

#### 更新现有框架

对于每个需要更新的框架，使用 `references/templates.md` 中的 consolidated-knowledge 模板。

保存至：`05-knowledge/consolidated/[framework-name]-framework.md`

#### 创建新框架

对于新识别出的框架，使用 `references/templates.md` 中的 new-framework 模板。

保存至：`05-knowledge/consolidated/[framework-name]-framework.md`

#### 更新模式文档

使用 `references/templates.md` 中的 pattern 模板记录该模式。

保存至：`05-knowledge/patterns/pattern-[name].md`

#### 创建时间线条目

使用 `references/templates.md` 中的 thinking-evolution 模板构建时间线条目。

保存至：`05-knowledge/timeline/[topic]-evolution-YYYY-MM.md`

### 5. 生成整合报告

使用 `references/templates.md` 中的 report 模板创建主整合文档。

保存至：`05-knowledge/consolidated/consolidation-YYYY-MM-DD.md`

### 6. 清理与归档

**标记已处理的 braindumps：**
更新已处理 braindumps 中的 frontmatter：
```yaml
status: "consolidated"
consolidated_in: "[[consolidation-YYYY-MM-DD]]"
consolidated_date: "YYYY-MM-DD"
```

**归档过时内容：**
将已被取代的框架或洞见移动至：
`00-inbox/archive/[filename]-archived-YYYY-MM-DD.md`

添加说明归档原因以及取代它的内容。

**保持知识库整洁：**
- 删除冗余内容，同时保留重要上下文
- 更新交叉引用
- 修复失效链接
- 确保标签一致

### 7. 确认完成

整合完成后：
- 向用户显示：“知识整合完成！已处理 [X] 份文档”
- 突出显示：“已更新 [X] 个框架，已创建 [X] 个新框架”
- 显示：“整合报告已保存至 [file path]”
- 建议审阅已创建或更新的关键框架
- 主动提出可详细解释任何特定框架

## 循环工程

整合是一个**循环直至无新发现的提取过程，并包含完整性审查器**，而不是一次性扫描。共享术语请参阅 `.claude/skills/loop-engineering/SKILL.md`。

**循环：**扫描一批范围内的文档 → 提取主题、模式和候选框架原则 → 运行完整性审查器（“是否还有未阅读的范围内文档？是否存在跨 N+ 份文档反复出现、但尚未被任何框架捕捉的主题？”）→ 如果审查器发现新内容，则再执行一轮提取 → 当连续 2 轮都没有发现新内容（干涸）时停止。在 `agent_mode: team` 中，首次扫描会按领域分发，每个领域一个工作者（个人 / 职业 / 各项目 / 简报）；每个工作者仅返回其结论，随后由综合阶段进行合并。

**验证器（在可行之处使用确定性验证）：**
- **可追溯性：**每条框架原则至少链接一份源文档。没有 `[[source]]` 的原则会被丢弃，而不会发布。这是机械性检查，也是 COG 在整合中“验证优先”的规则。
- **覆盖率：**每份范围内文档最终都标记为 `status: "consolidated"`，并带有 `consolidated_in` 反向链接。
- **去重：**创建框架之前，检查 `05-knowledge/consolidated/`，以便更新现有框架而非创建重复项。
- 完整性审查器（“我们是否遗漏了某个主题？”）是唯一基于判断的检查；保持其明确且与证据相链接。

**终止条件（分层）：**
- **干涸：**连续 K=2 轮未发现新主题或文档。
- **覆盖完成：**所有范围内文档均标记为已整合。
- **硬性上限：**设置最大提取轮数，避免嘈杂的语料库无限循环。

**模式：**循环直至无新发现（主干）+ 计划-执行-验证（每一轮）+ 编排器-工作者（团队模式的领域扫描）+ 完整性审查器。

**循环内上下文：**增量写入整合报告，并针对运行中的集合而非对话内容，对新主题进行去重。将内容外部化至报告文件，才能防止大型语料库撑爆上下文窗口。

## 整合指南

### 质量优先于数量
- 不要强行形成尚未成熟的洞见
- 让模式从证据中自然浮现
- 对不完整的思考保持耐心
- 高质量框架需要时间和证据
- 将框架标记为“新兴”“可用”或“稳定”

### 保留细微差别
- 不要过度简化复杂洞见
- 保留重要的上下文和条件
- 说明框架何时存在局限性
- 保留尚未解决的矛盾
- 明确承认不确定性

### 保持可追溯性
- 始终链接回源文档
- 展示框架的证据链
- 记录思考的演变过程
- 支持未来验证或修订
- 让框架主张易于审计

### 持续演进的文档
- 框架应随着新洞见不断演进
- 定期更新优于追求完美的初稿
- 使用清晰的状态指示（初现/运作中/稳定）
- 鼓励迭代与完善
- 通过 Git 保留版本历史

## 分析技术参考

### 模式检测方法
1. **频率分析：** 统计提及次数，聚类主题
2. **时间聚类：** 按时间分组，追踪演进
3. **领域关联：** 跨领域建立联系
4. **矛盾分析：** 识别冲突，追踪解决过程
5. **能量模式检测：** 分析情绪与实践模式

### 框架综合流程
1. **识别核心原则：** 提取基本真理
2. **根据证据进行检验：** 使用来源进行验证
3. **定义边界：** 确立适用范围
4. **创建应用：** 开发使用场景
5. **记录演进：** 追踪随时间的发展

### 时间线构建方法
1. **标记转折点：** 思考发生转变的时刻
2. **识别催化因素：** 触发变化的因素
3. **记录演进：** 理解如何发展
4. **提取经验：** 演进带来的启示

## 成功指标
- 完整性：处理所有相关洞见
- 连贯性：框架在逻辑上保持一致
- 可追溯性：与源材料之间具有清晰的关联
- 可执行性：框架可应用于决策
- 演进性：记录思维的发展过程
- 用户价值：框架确实在实践中得到使用

## 常见使用场景
- **每周整合：** 将一周的洞见处理为模式
- **每月框架开发：** 构建战略框架
- **每季度战略综合：** 进行全局性整合
- **每年知识库清理：** 维护质量与相关性
- **决策前框架咨询：** 将框架应用于重大决策
- **项目复盘：** 为框架提取经验

## 理念

知识整合技能体现了 COG 的自我演进智能：
- 将零散的想法转化为战略框架
- 尊重思维随时间的演进
- 构建“单一事实来源”的持续演进文档
- 保持可追溯性与基于证据的推理
- 创建可执行的知识，以实现更好的决策
- 在寻求模式的同时尊重细微差异
- 重视迭代与持续完善
