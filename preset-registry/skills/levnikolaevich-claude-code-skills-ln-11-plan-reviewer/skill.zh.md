# 计划审阅者

**目标：** 对实施计划进行只读、以证据为先的第二轮审查。验证计划；不要执行它。高质量的结果应当能够支持决策、以实际仓库为依据、明确说明不确定性，在保证安全的前提下采用问题所需的最低复杂度，并以最少的文字和执行步骤表达。

**执行约定：** 有序复选框是完成定义。内部将每一项跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具故障都不是证明。在每个部分后核对各项。返回前，解决所有 `PENDING`，且仅统计 `PROVEN` 和 `CLEARED`；对每个缺口应用此技能的结论和批准规则。保留用户意图、范围和现有授权。继续已获授权的工作；仅针对有重要影响的未决选择或所需的外部批准提出询问。根据实质风险调整审查深度，但不得暗中跳过检查。保留依赖关系和安全顺序；否则，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备选方案 |
|---|---|---|---|
| 仓库说明和当前状态 | 原生文件读取加 Git | 始终读取当前主机适用的仓库说明；当分支或变更上下文重要时，使用 `git status`、`diff` 和历史记录 | 等效的主机文件和 Shell 工具 |
| 路径、文本、配置、文档及聚焦的代码读取 | 原生文件列表、搜索、大纲和范围读取 | 问题属于文本或结构层面，且不需要符号标识 | 在扩展前缩小路径和模式范围 |
| 符号、引用、调用方、实现、循环依赖和影响范围 | 语言服务器或主机原生代码智能 | 计划会修改现有代码关系、公共 API、模块边界或架构 | 有针对性的搜索，加上对定义和使用方的直接检查 |
| 计划编辑风险 | 代码智能加调用方和使用方搜索 | 计划指定了编辑区域、路由、事件、响应契约或现有变更表面 | 手动检查已命名符号和相邻集成点 |
| 构建、测试、迁移和脚本可行性 | 通过 Shell 执行仓库定义的命令 | 计划依赖于某个命令、基线、生成的产物或现有测试表面可用 | 检查脚本和 CI 配置；将执行标记为未经验证 |
| 更正和外部声明研究 | 通过文档搜索或 Web 查阅官方供应商文档、规范或标准 | 外部行为或更正依赖于变更平台语义 | 可靠的第一方工程资料；否则将声明或更正标记为 `UNVERIFIED` |
| 独立质疑 | 在独立上下文中使用原生子代理 | 计划受益于执行、全新上下文或对抗性视角 | 将选定视角作为一次有边界的自审批次运行，并报告独立性降低 |

仅在能够回答当前证据问题时使用首选工具。工具失败不属于领域问题：应报告置信度降低；只有在缺少证据导致无法安全决策时才阻塞。对于散文或配置问题，不要使用语义工具；不要通过网络研究重新发现稳定的本地事实。

## 证据规则

| 证据 | 权威性 |
|---|---|
| 仓库文件、清单、架构、生成的契约和可执行行为 | 当前项目状态的事实来源 |
| 官方厂商文档、规范、RFC 和安全标准 | 外部契约和当前支持行为的事实来源 |
| 与项目实际版本范围匹配的发行说明和迁移指南 | 兼容性和升级声明的事实来源 |
| 可靠的一手工程材料 | 当官方来源未涉及某项设计权衡时，作为支持性证据 |
| 社区讨论或训练知识 | 仅作为线索；绝不足以支撑阻塞性事实声明 |

当来源相互矛盾时，对于已安装和已实现的内容，优先以仓库为准；对于外部系统所承诺的内容，以官方文档为准。仓库证据可以证明计划存在缺陷；外部实践来源可以为修正机制提供依据，但不能凭空创造本地要求。应明确陈述分歧，不要默默选择方便的答案。

## 检查清单

### 1. 建立评审约定

- [ ] 确定确切的计划、用户请求、关联需求和仓库范围。如果不存在具体计划，则以 `BLOCKED` 结束，而不是自行编造一个计划进行评审。
- [ ] 在解读代码、文档或预期工作流程之前，阅读所有适用的仓库指令文件。只识别与变更相关的项目政策、标准和 ADR；区分当前认可的权威内容与草稿、已取代内容、过时内容或仅具描述性的材料，不要将所有文档都视为具有约束力。
- [ ] 在可能影响评审时检查 Git 状态：当前分支、未提交的变更、比较基线和相关的近期历史。
- [ ] 区分字面请求和提议的解决方案与其潜在意图；说明参与者、受保护的结果、可观测的完成定义、非目标、约束和假设，并标记缺乏依据的意图推断。
- [ ] 根据已有证据的项目或产品成熟度、决策周期、当前规模、团队与运维能力以及业务利害关系，校准可接受的复杂度。只有在具体的时间范围、使用者、负载或约束提供支持时，才将未来增长视为需求。
- [ ] 区分计划中的缺陷与既存的相邻问题。只有在计划引入或加剧某个既存问题、依赖于关于该问题的错误假设、必须解决该问题才能满足目标，或造成直接交付风险时，才将其作为计划问题；否则将其记录为范围外观察，不要扩大计划范围。
- [ ] 区分可从仓库中发现的事实与需要用户意图决定的选项；先进行探索；当合理的不同解释会产生实质不同的计划时，提出一个能够解决该决策的简洁问题，而不是进行问卷式提问。
- [ ] 对评审深度进行分类。将身份验证、授权、资金、破坏性操作、数据迁移、公共 API、并发、分布式工作流和不可逆发布视为高风险。
- [ ] 保持运行只读。不要修改源计划、实现、任务跟踪器、分支或外部系统；修正后的计划只能出现在评审回复中。仅允许主机许可的、可重建的诊断缓存或构建产物，并在创建后予以披露。

### 2. 以仓库为依据制定计划

- [ ] 构建一份受影响模块、入口点、配置、架构、迁移、测试、文档和部署面的精简地图。
- [ ] 根据仓库约定和常见职责，发现共享的架构与治理产物：系统设计基线、当前状态地图、目标设计、已接受的决策、工程政策、图表和迁移计划。将它们视为可选证据，绝不要视为必需的工作流依赖项。
- [ ] 在应用约束之前，检查产物状态、权威性、所有者、来源、截至日期、是否已被取代以及评审触发条件。维护一份变更范围内的政策与决策台账，记录适用的来源以及用于证明合规、明确获批的偏差或未解决缺口的计划证据。缺少产物本身不会阻塞评审；实质性未解决的驱动因素才会。
- [ ] 验证计划中提及的每个现有路径、符号、组件、命令、环境键、接口和依赖项。将确实新增的产物标记为新增。
- [ ] 阅读足够的实现上下文，以理解所有权和不变量，而不只是计划明确列出的文件。
- [ ] 仅在 Git 历史或 blame 能够揭示仍然相关的约束或约定时检查它们；不要将历史代码视为当前设计正确的证明。
- [ ] 检查现有的测试和 CI 范围，确保所提议的验证命令、fixture、环境和验收证据切实可行。
- [ ] 为实质性声明维护证据台账：声明、来源、置信度以及它支持或反驳的计划决策。
- [ ] 当已知的并行工作可能与受影响的契约、架构、文件或结果发生冲突时进行检查；没有重叠信号时，不要盘点每个分支或计划。
- [ ] 当新增文件不可能改变计划决策、发现结果或置信度级别时，停止扩大扫描范围。

### 3. 研究更正内容和未知的外部声明

- [ ] 仅在仓库证据确认存在实质性候选缺口后研究更正内容；优先使用仓库中已有的机制，不要浏览资料来臆造发现。
- [ ] 提取计划中属于外部或不稳定的信息：版本、API 签名、弃用项、标准、安全要求、库的能力、性能特征和平台限制。
- [ ] 在搜索通用文档之前，先从项目清单、锁定文件、配置和生成的元数据中确认已安装的版本和启用的功能。
- [ ] 在提出依赖外部 API、库、安全控制、协议、平台、标准或版本的更正建议之前，查阅与已安装或提议版本相匹配的官方文档，验证受支持的解决方案、约束、弃用项和安全指南。
- [ ] 对于尚未解决的设计权衡，将主要工程证据与本地要求和运行约束进行比较；记录证据未能选出唯一解决方案的情况。
- [ ] 打开并检查计划所依赖的任何特定文档、提案、议题或 URL，不要仅凭引用或释义予以信任。
- [ ] 将解决方案研究添加到实质性声明台账中：来源/日期、受支持的机制、考虑过的更正、决策、置信度和对计划的影响；不要创建单独的研究登记表。
- [ ] 应用研究到行动的门槛：如果来源没有揭示具体缺陷、风险、缺失的决策或有更充分依据的替代方案，则将其保留为信息，不要夸大评审范围。
- [ ] 如果无法获得权威研究，将受影响的声明标记为 `UNVERIFIED`；当实现安全性或重要设计选择依赖该声明时，使用 `BLOCKED`。评审批准绝不授权执行；应为实施者识别不稳定的外部事实及其重新验证触发条件；只要其版本和假设仍然有效，就重复使用已有证据。

### 4. 从每个适用视角进行审查

- [ ] **意图与可追溯性：**每项拟议变更和复杂性来源都映射至预期结果、验收标准、安全需求或有证据支持的约束；合并服务于相同结果的工作，并移除推测性的或仅具仪式性的步骤。
- [ ] **仓库适配性：**计划尊重实际项目结构、约定、受支持的技术栈、现有能力、成熟度、当前规模、团队和运维能力，以及当前工作，且不覆盖无关变更。对于台账中每项适用的当前项目策略或 ADR，将受影响的计划范围追溯至合规性，或追溯至经明确批准且理由充分的偏离；仅当变更涉及这些方面时，才纳入项目定义的日志记录、错误分类与边界映射、配置、可观测性、安全性、持久化、测试和发布规则。
- [ ] **架构、所有权与可追溯性：**分层、模块、编排、副作用、依赖方向和资源所有权保持明确、一致且恰如其分。计划尊重已确认的约束、已接受的决策、目标边界和当前迁移阶段；暴露陈旧或矛盾的工件，而不是默默选择方便的方案。
- [ ] **根本原因与完整性：**在范围内的入口点、生产者、消费者、注册、状态转换以及实质性失败/恢复路径中追溯归属的修正。拒绝掩盖症状、调用方特例、旁路，以及意外的排序、时序或数据依赖。战术性遏制措施需要明确意图或即时安全需求、负责人、移除条件和持久化后续跟进；止于因果业务范围。
- [ ] **接口与数据：**凡是发生变更的公共 API、事件、模式、配置、持久化、序列化、兼容性和迁移路径都应被命名。对于发生变更的语义值和封闭集合——例如状态、角色、权限、事件名称、错误代码、配置键、功能标识符、限制、超时和路由键——为范围内所有生产者和消费者规划一个通过仓库标准机制共享的权威所有者（例如类型联合、枚举、常量集、值对象、模式、类型化配置或生成的契约）。不要要求提取无重复、无无效状态或漂移风险的无害一次性本地字面量。
- [ ] **场景完整性：**对于每个关键流程，追溯行为者触发 -> 入口点 -> 运行时发现或装配 -> 使用上下文 -> 可观察结果；当首次有意义的使用、失败、恢复和重复会改变预期体验时，应将其纳入。
- [ ] **正确性与失败模式：**在适用时覆盖边界、无效状态、部分失败、重试、幂等性、并发、取消、超时、回滚和清理。
- [ ] **安全与隐私：**按风险比例覆盖信任边界、身份验证、授权、验证、密钥、敏感数据、日志记录、破坏性操作和滥用路径。
- [ ] **依赖与排序：**使用能够安全达成验收目标的最少依赖有序步骤；并行步骤不存在同一批次依赖或共享可变输出，且迁移、生产者、消费者、部署和兼容性转换保持正确顺序。
- [ ] **容量与降级：**根据有证据支持的需求，限制用户或数据可控的工作量和状态负载；说明速率假设和失败行为，但不为假设性的流量引入扩缩容机制。
- [ ] **测试与验收：**对于每项实质性变更风险和受影响的测试，计划应说明测试依据、现有证据、独立判定标准、测试层级和门禁理由，以及一项测试组合操作：`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有理由的 `NO_TEST`。选择能证明每项实质性风险的最小可靠边界；当用户旅程需要时使用 E2E；要求具有独特缺陷信号的最少测试，以完成证据而非数量或原始覆盖率作为依据，并为临时证明设置审查或退役触发条件，而不重新设计无关的测试健康状况。
- [ ] **交付与运维：**仅当变更需要时，纳入文档、配置发布、可观测性、部署、回滚和运维人员操作。
- [ ] **简单性与替代方案：**评估 `NO_CHANGE`、`DELETE_OR_CONFIGURE`、`REUSE_LOCAL`、`USE_PLATFORM_OR_STDLIB`、`REUSE_INSTALLED`、`ADOPT_DEPENDENCY`，然后是 `MINIMAL_CUSTOM`；说明所选层级以及被拒绝的适用更简单选项。新代码、依赖、层、服务、配置、可扩展性或运维机制需要具备具体的能力或生命周期成本理由。整合必须保留所有权、验证、正确性、安全性、兼容性、可测试性和可逆性。
- [ ] **减法完整性：**对于发生变更的逻辑、约束、配置、模式、路由、状态或操作，识别过时代码、分支、标志、键、默认值、兼容垫片、数据路径、文档、测试、权限、指标和发布脚手架。仅当证据证明其已被取代且在范围内时，才计划移除；否则记录保留证据，或记录临时路径的负责人和移除条件。

### 5. 在需要时质疑材料不确定性

- [ ] 仅当未解决的重要问题确实需要独立质疑且用户允许时，才进行独立质疑；否则清除条件性质疑项。选择能够改变结论的最小化、彼此有区别的执行模拟、新鲜上下文或对抗性视角集合，不设配额。将质疑限制在一轮有界范围内；直接解决由此产生的证据缺口。
- [ ] 向每位审查者提供相同的冻结材料包，包括计划、真实目标、相关仓库路径、约束、假设和证据问题；不得提供先前的对话历史、主要审查结论或同级审查者的输出。如果宿主无法提供新鲜且隔离的上下文，则使用彼此独立的自我审查轮次，并披露独立性降低的情况。
- [ ] 将选定的视角一次性并行启动，或以一次盲式批次启动，等待全部完成，并将每条建议视为需要仓库或权威证据支持的候选发现。直接解决冲突并验证候选项；绝不启动验证者或另一轮审查。
- [ ] 将事前验尸中的担忧分类为有证据支持的风险、无依据的担忧或未陈述的假设；驳回无依据的担忧，并为每个接受的风险或假设给出失效影响以及具体的验证或缓解步骤。
- [ ] 将审查者不可用、工具故障、速率限制或提问视为覆盖范围限制，而不是计划存在缺陷的证据。仅当具体原因发生变化时，才重试或替换一名因技术原因失败的已选审查者，并使用相同的证据问题；这将完成原始轮次，不得扩大范围。

### 6. 综合形成决策完备的结果

- [ ] 对仓库检查、研究和独立审查中的发现进行去重；保留最有力的证据，并保留有意义的分歧。
- [ ] 将发现分类为 `BLOCKER`、`MAJOR` 或 `MINOR`：阻塞项会阻止安全交接，主要问题预示着大量返工或回归，次要问题可提高清晰度但不会改变可行性。
- [ ] 对每个候选项应用重要性和可接受替代方案门槛。必须存在被违反的要求或契约，或在已有证据规模下具体的用户、业务、安全、运营、交付或生命周期影响。驳回无依据或既存且无关的问题、吹毛求疵、个人偏好、理论纯粹性、通用实践、假设规模，以及当前权衡合理时仅仅不同的实现方式。对于每个接受的发现，解释为何该妥协不可接受，并要求最小但完整的结果，同时允许等价方案。
- [ ] 对依赖外部信息的修正引用经过验证的来源；对仓库自有缺陷引用本地证据。仅将无支持的主张标记为 `UNVERIFIED`；不要因为缺少可选的实践来源，就掩盖已经独立证明的缺陷。
- [ ] 确认关键接口、所有权、数据流、失败行为、兼容性、验证和发布均已通过明确约束做出决策或限定范围；将等价的实现细节留给实现者。
- [ ] 对每个重要假设记录置信度、假设为假时会破坏什么，以及在开始依赖该假设的工作之前由谁或哪个步骤进行验证。
- [ ] 将发现映射到结论：当所需的用户选择、访问权限或权威事实不可用时，使用 `BLOCKED`；对于任何可修正的 `BLOCKER` 或 `MAJOR`，使用 `REVISE`；仅当计划安全且可执行，不存在未覆盖的要求或有重大影响的决策，但仍存在有界的非阻塞 `MINOR` 修订项或已明确接受的剩余风险时，使用 `READY WITH CONCERNS`；仅当不存在需要修正的发现或阻塞性证据缺口时，使用 `READY`。
- [ ] 对于 `REVISE`，当精确的本地修订可以使计划保持一致时，提供这些修订；仅当变更涉及计划的结构或依赖关系时，才提供完整替代方案。保留原有意图、已接受的修正以及必需的实现和验证结果。
- [ ] 对于 `READY WITH CONCERNS`，仅提供精确的本地计划修订和已接受的非阻塞风险；不要复述计划中未改变的部分。
- [ ] 对于 `BLOCKED`，只提出能够实质性解锁不同计划所需的最少问题，并说明已经验证的内容。

## 输出约定

使用用户的语言按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较少时，每个字段可使用一行；省略空表格，不要复制链接的工件：

1. **结果：** Skill 专属结论及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill 专属字段；区分事实、推断和未经验证的声明。链接工件；在有帮助时使用表格。
4. **验证：** 检查及结果、不可用的证据、适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响以及确切的下一步操作；剩余风险和需要作出的决策。

**Skill 专属证据：** 计划决策、必需的更正、验收和排序缺口；任务/计划需求 → 证据 → 状态。包括适用的政策/ADR 合规情况和已批准的偏差、根因分析的完整性、保留或移除的机制、测试和文档操作、独立质疑覆盖情况，以及仅针对依赖外部因素的更正提供权威参考。每个发现都需要包含优先级、位置、违反的约定、实质影响以及最小充分更正；允许采用等效的有效方案。只在响应中保留已更正的计划或会改变决策的修订内容。
