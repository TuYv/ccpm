# 计划审查员

**目标：** 对实施计划进行只读、证据优先的二次审查。验证计划；不要执行它。高质量结果应当决策完备、基于实际仓库、明确说明不确定性、复杂度不超过问题所需，并以在保持安全的前提下最少的文字和执行步骤表达。

**执行约定：** 将下方有序复选框工作流视为本技能的完成定义。审查前，创建一份内部覆盖台账，按打印顺序使用标题的 ID 范围为每个复选框建立一行 `PENDING`。仅在具备具体证据引用时将某行改为 `PROVEN`，在具备其条件触发因素不存在的证据时改为 `CLEARED`，或改为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败均不能构成证明。
在每个编号章节结束时，核对其台账行并解决所有 `PENDING`。作出结论前，对台账、证据和草稿恰好执行一次收尾检查：质疑没有支持依据的 `PROVEN` 或 `CLEARED` 状态，呈现每项已接受的发现，并对齐矩阵、限制条件和结论。修正报告或降低结论等级；不要重新扫描仓库、重启审查或启动另一轮子代理。
返回前，仅将 `PROVEN` 和 `CLEARED` 行视为完成，从台账中推导计数，对每个 `UNPROVEN` 应用本技能的结论规则，不允许存在 `PENDING`，并在开头添加 **清单：X/Y 完成**<br>**未完成：无 | ID — 原因；结果影响；确切的下一步操作**；列出每一行 `UNPROVEN`。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 仓库说明和当前状态 | 原生文件读取加 Git | 始终读取当前主机适用的仓库说明；当分支或变更上下文相关时，使用 `git status`、`diff` 和历史记录 | 等效的主机文件和 shell 工具 |
| 路径、文本、配置、文档和聚焦代码读取 | 原生文件列表、搜索、大纲和范围读取 | 问题属于文本或结构性问题，且不需要符号标识 | 在扩展内容前缩小路径和模式范围 |
| 符号、引用、调用方、实现、循环和影响范围 | 语言服务器或主机原生代码智能 | 计划变更现有代码关系、公共 API、模块边界或架构 | 有针对性的搜索加上对定义和使用方的直接检查 |
| 计划编辑风险 | 代码智能加调用方和使用方搜索 | 计划指定编辑区域、路由、事件、响应契约或现有变更面 | 手动检查指定符号和相邻集成点 |
| 构建、测试、迁移和脚本可行性 | 通过 shell 运行仓库定义的命令 | 计划依赖于某个命令、基线、生成产物或现有测试面可用 | 检查脚本和 CI 配置；标记执行未经验证 |
| 修正和外部声明研究 | 通过文档搜索或 Web 获取官方供应商文档、规范或标准 | 外部行为会影响计划，或重要候选项需要其所需实践参考 | 可靠的第一方工程材料；否则将该声明或修正标记为 `UNVERIFIED` |
| 独立质疑 | 在独立上下文中使用原生子代理 | 计划可受益于执行、全新上下文或对抗性视角 | 将选定视角作为一批有界自审恰好运行一次，并报告独立性降低 |

仅当首选工具能够回答当前的证据问题时才使用它。工具失败并不代表领域层面的结论：应报告置信度降低，并且仅在证据缺失导致无法安全决策时才予以阻断。不要使用语义工具处理散文或配置问题，也不要通过 Web 调研重新发现稳定的本地事实。

## 证据规则

| 证据 | 权威性 |
|---|---|
| 仓库文件、清单、架构、生成的契约以及可执行行为 | 当前项目状态的事实来源 |
| 官方供应商文档、规范、RFC 和安全标准 | 外部契约及当前受支持行为的事实来源 |
| 与项目实际版本范围匹配的发布说明和迁移指南 | 兼容性和升级声明的事实来源 |
| 可信的一手工程资料 | 当官方来源未涉及某项设计权衡时作为支持性证据 |
| 社区讨论或训练知识 | 仅作为线索；绝不足以支持会导致阻断的事实性结论 |

当来源存在分歧时，对于已安装和已实现的内容，以仓库为准；对于外部系统所承诺的内容，以官方文档为准。仓库证据可以证明计划缺陷；外部实践来源可以论证修正机制，但不能凭空创造本地要求。应明确说明分歧，而不是默默选择方便的答案。

## 检查清单

### 1. 建立审查契约（`CONTRACT-1` 至 `CONTRACT-9`）

- [ ] 明确具体计划、用户请求、关联需求和仓库范围。如果不存在具体计划，应以 `BLOCKED` 停止，而不是虚构一个计划进行审查。
- [ ] 在解读代码、文档或预期工作流之前，阅读所有适用的仓库说明文件。仅识别与变更相关的项目政策、标准和 ADR；区分当前已接受的权威材料与草案、已被取代、过时或仅具描述性的材料，不要将每份文档都视为具有约束力。
- [ ] 当 Git 状态可能影响审查时，应检查该状态：当前分支、未提交的更改、比较基准以及相关的近期历史记录。
- [ ] 将字面请求和拟议解决方案与底层意图区分开来；说明行为主体、受保护的结果、可观察的完成定义、非目标、约束和假设，并标记缺乏支持的意图推断。
- [ ] 根据有证据支持的项目或产品成熟度、决策周期、当前规模、团队与运维能力以及业务风险，校准可接受的复杂度。只有在具体的时间范围、使用方、负载或约束能够支持时，才将未来增长视为一项需求。
- [ ] 将计划中的缺陷与预先存在的相邻问题区分开来。仅当计划引入或加剧现有问题、依赖关于该问题的错误假设、必须解决该问题才能实现目标，或造成即时交付风险时，才将其视为计划中的发现；否则，应将其记录为范围外观察项，且不要扩展计划。
- [ ] 区分可从仓库中发现的事实与需要用户意图才能确定的选择；先进行探索，并且当不同的合理解读会产生实质不同的计划时，提出一个能够解决该决策的简洁问题，而不是进行问卷式询问。
- [ ] 对审查深度进行分类。将身份验证、授权、资金、破坏性操作、数据迁移、公共 API、并发、分布式工作流以及不可逆发布视为高风险。
- [ ] 整个过程保持只读。不要修改源计划、实现、任务跟踪器、分支或外部系统；修正后的计划只能出现在审查回复中。仅允许创建宿主环境准许的、可重新生成的诊断缓存或构建产物，并在创建后予以披露。

### 2. 以代码仓库为依据制定计划（`REPO-1` 至 `REPO-11`）

- [ ] 建立一份范围明确的映射，涵盖受影响的模块、入口点、配置、模式、迁移、测试、文档和部署面。
- [ ] 根据代码仓库惯例和常见职责查找共享的架构与治理制品：系统设计基线、当前状态图、目标设计、已接受的决策、工程策略、图表和迁移计划。将它们视为可选证据，绝不能作为必需的工作流依赖项。
- [ ] 在应用约束之前，检查制品的状态、权威性、所有者、来源、截至日期、取代关系和审查触发条件。维护一份以本次变更为范围的策略与决策台账，记录适用来源，以及用于证明合规、明确获批的偏离或未解决缺口的计划证据。缺少制品本身并不会阻止审查；存在实质性的未解决驱动因素才会。
- [ ] 验证计划中提到的每个现有路径、符号、组件、命令、环境键、接口和依赖项。将确实属于新增的制品标记为新增。
- [ ] 阅读足够的实现上下文，以理解所有权和不变量，而不只是阅读计划明确提到的文件。
- [ ] 当结论取决于符号标识、调用方、实现、模块耦合、API 使用方或影响范围时，使用语义图查询。
- [ ] 仅当 Git 历史记录或 blame 信息能够揭示仍然适用的约束或惯例时才进行检查；不要将历史代码视为当前设计正确的证明。
- [ ] 检查现有测试和 CI 覆盖面，确保拟议的验证命令、夹具、环境和验收证据切实可行。
- [ ] 为实质性主张维护证据台账：主张、来源、置信度，以及其支持或反驳的计划决策。
- [ ] 检查活跃分支、计划、迁移或同级工作中是否存在结构性重叠：共享契约、文件、模式，或相同触发条件但结果冲突；仅有关键字相似只能作为线索。
- [ ] 当更多文件无法再改变任何计划决策、发现或置信度时，停止扩大扫描范围。

### 3. 调研修正方案和未知的外部主张（`RESEARCH-1` 至 `RESEARCH-9`）

- [ ] 只有在代码仓库证据确认存在实质性候选缺口之后，才调研修正方案；优先采用代码仓库中已有的机制，不要通过浏览外部资料来凭空制造发现。
- [ ] 提取计划中涉及外部因素或不稳定因素的主张：版本、API 签名、弃用情况、标准、安全要求、库能力、性能特征和平台限制。
- [ ] 在搜索通用文档之前，先从项目清单、锁文件、配置和生成的元数据中确定已安装版本和已启用功能。
- [ ] 在推荐依赖外部 API、库、安全控制、协议、平台、标准或版本的修正方案之前，查阅与已安装或拟议版本匹配的官方文档，验证受支持的解决方案、约束、弃用情况和安全指南。
- [ ] 对于每个可能成为发现的实质性候选项，打开并阅读支持修正机制的最新官方文档或规范；只有在官方来源无法解决权衡问题时，才使用信誉良好的第一手工程资料。不要使用外部指南重新定义由需求、代码和测试确立的、归代码仓库所有的业务逻辑。
- [ ] 打开并检查计划所依赖的任何特定文档、提案、议题或 URL，而不是轻信引文或转述。
- [ ] 将解决方案调研记录为精炼的证据：主题、来源和日期、已验证的主张、候选修正方案、选定方法、已拒绝的替代方案、置信度、对计划的影响，以及该选择为何是最小且完整的适配方案。
- [ ] 应用从调研到行动的准入规则：如果某个来源未揭示具体缺陷、风险、缺失的决策或有更充分依据的替代方案，则仅将其保留为参考信息，不要夸大审查内容。
- [ ] 如果无法获得权威调研资料，将受影响的主张标记为 `UNVERIFIED`；当实现安全性或影响重大的设计选择依赖于该主张时，使用 `BLOCKED`。审查批准绝不代表授权执行；要求后续实施者在编辑前立即重新验证不稳定的外部事实。

### 4. 从每个适用视角进行审查（`LENS-1` 至 `LENS-15`）

- [ ] **意图与可追溯性：** 每项拟议变更及复杂性来源都应映射到预期成果、验收标准、安全需求或有证据支持的约束；合并服务于同一成果的工作，并移除推测性或仅具形式意义的步骤。
- [ ] **仓库适配性：** 计划应尊重实际项目结构、约定、受支持的技术栈、现有能力、成熟度、当前规模、团队与运维能力以及当前正在进行的工作，不覆盖无关变更。对于台账中每项适用的当前项目策略或 ADR，将受影响的计划范围追溯至合规要求，或追溯至经明确批准且理由充分的偏离；仅当变更涉及项目定义的日志记录、错误分类与边界映射、配置、可观测性、安全性、持久化、测试和发布规则时，才将其纳入计划。
- [ ] **架构、所有权与可追溯性：** 层级、模块、编排、副作用、依赖方向和资源所有权应保持明确、一致且适度。计划应遵守已确认的约束、已接受的决策、目标边界以及当前迁移阶段；应揭示过时或相互矛盾的制品，而不是默默选择最方便的那个。
- [ ] **根因与解决方案完整性：** 证明拟议机制能够在其归属边界解决因果需求，并覆盖范围内的每个入口点、生产者、消费者、运行时注册、状态转换以及实质性的失败或恢复路径。拒绝症状修补、调用方特定的特殊情况、重复的旁路通道，以及偶然形成的顺序、时序或数据依赖。仅当明确要求战术性遏制措施，或即时安全需要此类措施时，才予以接受，并且必须明确其负责人、移除条件和持久化后续方案；完整性的边界止于因果业务范围，而非整个仓库。
- [ ] **接口与数据：** 凡公共 API、事件、模式、配置、持久化、序列化、兼容性和迁移路径发生变化之处，都应明确指出。对于发生变化的语义值和封闭集合——例如状态、角色、权限、事件名称、错误代码、配置键、功能标识符、限制、超时和路由键——应规划一个权威所有者，并通过仓库标准机制（例如类型化联合、枚举、常量集、值对象、模式、类型化配置或生成的契约）供范围内的所有生产者和消费者共享。不要要求提取无重复、无无效状态风险或漂移风险的无害一次性局部字面量。
- [ ] **场景完整性：** 对每个关键流程，追踪参与者触发操作 -> 入口点 -> 运行时发现或装配 -> 使用上下文 -> 可观测结果；当首次有意义的使用、失败、恢复和重复操作可能改变预期体验时，将其纳入考虑。
- [ ] **正确性与失败模式：** 在适用情况下，涵盖边界、无效状态、部分失败、重试、幂等性、并发、取消、超时、回滚和清理。
- [ ] **安全与隐私：** 根据风险程度，涵盖信任边界、身份认证、授权、验证、密钥、敏感数据、日志记录、破坏性操作和滥用途径。
- [ ] **依赖关系与顺序：** 使用能够安全达到验收要求的最少依赖有序步骤；并行步骤之间不得存在同一波次内的依赖关系或共享的可变输出，同时确保迁移、生产者、消费者、部署和兼容性转换保持正确顺序。
- [ ] **容量与降级：** 根据有证据支持的需求，限制由用户或数据控制的工作量和状态负载；明确速率假设和失败行为，且不得为假设性流量引入扩展机制。
- [ ] **测试与验收：** 对于每项实质性变更风险和每个受影响的测试，计划都应说明测试依据、现有证明、独立判定依据、测试层级与门禁理由，并指定一项测试组合操作：`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或理由充分的 `NO_TEST`。对于实质性的用户可观测风险，优先采用确定性的 E2E 测试，并说明采用范围更窄证据的理由；要求使用数量最少但具有独特缺陷信号的测试，以完成证明而非测试数量或原始覆盖率作为依据，并为临时证明设置审查或退役触发条件，而不重新设计无关的测试健康状况。
- [ ] **交付与运维：** 仅在变更需要时，纳入文档、配置发布、可观测性、部署、回滚和运维人员操作。
- [ ] **KISS——简洁性与替代方案：** 优先选择此解决方案阶梯中第一个足以满足需求的层级：`NO_CHANGE`、`DELETE_OR_CONFIGURE`、`REUSE_LOCAL`、`USE_PLATFORM_OR_STDLIB`、`REUSE_INSTALLED`、`ADOPT_DEPENDENCY`，最后是 `MINIMAL_CUSTOM`。要求提供证据说明为何选择该层级，以及每个适用的更简单层级为何不足；拒绝在缺乏实质性语义需求的情况下直接跳到新依赖项、自定义代码、层级、服务、抽象、配置、可扩展性、基础设施或运维机制的计划。在所有权和验证仍然清晰的情况下合并相邻工作，同时保持正确性、安全性、兼容性、可测试性和可逆性；KISS 并非追求代码高尔夫，也不意味着省略保障措施。
- [ ] **减法完整性：** 对于发生变化的逻辑、约束、配置、模式、路由、状态或操作，识别已过时的代码、分支、标志、键、默认值、兼容垫片、数据路径、文档、测试、权限、指标和发布脚手架。仅当证据证明其已被取代且属于范围内时，才计划移除；否则，应记录保留证据，或记录临时路径的负责人和移除条件。`One in, two out` 是一种简化提示，绝非配额。
- [ ] 仅当证据表明某视角的触发条件在计划和仓库中均不存在时，才将其标记为 `CLEARED`；绝不能默默跳过高风险视角。

### 5. 执行一轮独立质询（`CHALLENGE-1` 至 `CHALLENGE-5`）

- [ ] 针对计划仅执行一轮独立审查。对于小型低风险工作，选择一名盲审者；对于普通中等风险工作，选择两名不同的审查者；对于高风险、架构性、跨服务、不熟悉或存在实质性歧义的工作，则选择全部三种审查视角：执行模拟、全新实现和对抗性故障分析。不得因修正、分歧或低置信度而启动第二轮分析。
- [ ] 向每位审查者提供同一份冻结材料包——计划、真实目标、相关仓库路径、约束、假设以及证据问题——且不包含先前的对话历史、主要审查的结论或其他审查者的输出。如果宿主无法提供全新的隔离上下文，则使用不同的自审轮次，并披露独立性有所降低。
- [ ] 以并行方式或单次盲审批次一次性启动所选审查视角，等待全部完成，并将每条建议视为需要仓库证据或权威证据支持的候选发现。直接解决冲突并验证候选发现；绝不启动验证者或另一轮审查。
- [ ] 将事前剖析中的疑虑分类为有证据支持的风险、无依据的担忧或未明确说明的假设；排除无依据的担忧，并为每项被接受的风险或假设说明其失效影响以及具体的验证或缓解步骤。
- [ ] 将审查者不可用、工具故障、速率限制或提问视为覆盖范围限制，而非计划存在缺陷的证据。仅当具体原因发生变化时，才重试或替换一名因技术原因失败的已选审查者，并使用相同的证据问题；这将完成原始轮次，且不得扩大其范围。

### 6. 综合形成决策完备的结果（`CLOSE-1` 至 `CLOSE-11`）

- [ ] 对仓库检查、研究和独立审查中发现的问题进行去重；保留最有力的证据，并保留有意义的分歧。
- [ ] 将发现分类为 `BLOCKER`、`MAJOR` 或 `MINOR`：阻断项会妨碍安全交接，重大项预示着大量返工或回归，次要项则在不改变可行性的情况下提升清晰度。
- [ ] 对每个候选发现应用重要性与可接受替代方案门槛。必须存在被违反的要求或契约，或者在有证据支持的规模下，对用户、业务、安全、运维、交付或生命周期产生具体影响。拒绝缺乏依据的问题、预先存在且无关的问题、吹毛求疵、个人偏好、理论上的纯粹性、泛泛的实践、假设性的规模，以及当前权衡合理时仅仅不同的实现方式。对于每个被接受的发现，说明为何该妥协不可接受，并要求最小但完整的结果，同时允许采用等效解决方案。
- [ ] 在每个发现所要求的解决方案中，以直接相关的 Markdown 实践链接形式提供经验证的研究来源。该来源必须支持所提出的机制，而不能仅仅支持缺陷类别；拒绝搜索结果链接、泛泛的文章和装饰性引用，并在没有可信来源可用时将修正标记为 `UNVERIFIED`。
- [ ] 确认每个会产生后果的实现选择均已确定：接口、所有权、数据流、失败行为、兼容性、验证，以及适用情况下的发布。
- [ ] 对每项实质性假设，记录其置信度、假设错误时会破坏什么，以及在依赖该假设的工作开始前由谁或哪个步骤对其进行验证。
- [ ] 将发现映射到裁决：当所需的用户选择、访问权限或权威事实不可获得时，使用 `BLOCKED`；对于任何可修正的 `BLOCKER` 或 `MAJOR`，使用 `REVISE`；仅当计划安全且可执行，不存在未覆盖的要求或会产生后果的决策，但仍有范围明确且非阻断性的 `MINOR` 修订或明确接受的残余风险时，使用 `READY WITH CONCERNS`；仅当不存在需要修正的发现或阻断性证据缺口时，使用 `READY`。
- [ ] 对于 `REVISE`，提供一份完整的替代计划，采用数量最少、按依赖关系排序且能够产生成果的步骤，保留用户意图和已接受的修正；省略对上下文的重复陈述、元工作，以及不会增加实现或验证价值的阶段。
- [ ] 对于 `READY WITH CONCERNS`，仅提供准确的局部计划修订和已接受的非阻断性风险；不要重述计划中未更改的部分。
- [ ] 对于 `BLOCKED`，仅提出能够实质性解锁不同计划的最少问题，并说明已经验证的内容。
- [ ] 遵循宿主要求的任何包装格式，但应在证据和裁决允许的范围内尽量保持响应简短：事实只陈述一次，省略空泛评论和未更改的计划部分，并保留下述输出内容及裁决语义。
