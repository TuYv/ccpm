# 变体

此技能接收一项描述好的 UI，并构建三个有意不同的版本。它们会放在真实页面中的一个选择器之后，方便你来回切换并做出选择。

这里的其他所有技能都负责评判。此技能负责生成候选方案，并将决定权交还给你。审查现有 UI 应使用 `interface-review` 和 `better-interface`，而本技能不会选出胜者。

## 不同的答案，而不是不同的色调

三个只在强调色上有所差异的变体无法带来任何启发。你在它们之间来回切换，却看不到真正的选择，这次运行也就浪费了。

因此，每个变体都应沿着本技能集合所负责的一个维度，对同一份需求给出不同的答案：

| 维度 | 负责技能 | 变化内容 |
| --- | --- | --- |
| 结构 | `better-layout` | 分组、顺序、列数、折叠哪些内容 |
| 密度 | `better-layout` | 间距尺度、点击区域、可容纳多少内容 |
| 强调 | `better-colors` | 填充色用在哪里、哪些内容弱化 |
| 字体 | `better-typography` | 字号层级、字重对比、行宽 |
| 文案风格 | `better-writing` | 标签、语气、文案量 |

选择**一个主要维度**，并让每个变体在该维度上采取不同的定位。次要选择应由主要维度自然推导，而不是独立变化。高密度变体可能需要更小的字号层级，这是协调一致，而不是引入第二个维度。

同时改变所有维度，会产生三个无法归因的结果。你只能知道自己喜欢哪一个，却不知道是什么让它奏效，所以下一个 UI 部件仍然要从零开始。

## 每个变体都必须达到的底线

一个外观胜出却触发升级条件的变体，不是候选方案。它只是一个表面漂亮的缺陷。

在变体进入选择器之前，它必须通过 `better-interface` 的升级触发条件。每个控件都有无障碍名称，键盘能够访问指针可以操作的所有内容，焦点清晰可见，在 320px 宽度下没有任何内容被裁切，并且没有任何含义仅依赖颜色传达。

这条底线对所有变体完全相同。它不是一个变化维度，也绝不能为了其他维度而妥协。如果某个方向只有突破这条底线才能成立，请明确说明并放弃该方向。

## 1. 将范围限定为一个部件

每次运行只处理一个 UI 部件。“仪表盘”不是一个部件；指标卡片才是。如果需求涉及多个部件，请指出其他部件所依附的核心部件，说明原因，并建议将其余部件留待后续运行。

用一句话重述需求：这个部件是什么、在哪里渲染，以及它必须完成什么任务。

## 2. 了解基础环境

变体必须看起来像是明天就能发布，因此需要了解它们所依托的环境：

- 样式系统、组件库以及所有动效库。
- 设计令牌：颜色、间距、圆角、字号尺度、缓动。
- 产品的信息密度和文案风格。高密度的专业工具会限制最大胆的变体能走多远。
- 部件的渲染位置：位于什么背景上、与哪些相邻元素并列、会在哪些宽度下显示。

如果没有可供查看的项目，请使用中性灰色、一种强调色和系统字体栈，并说明你采用了这些设置。

## 3. 在编写代码前确定维度

默认生成三个变体。只有在用户要求时，或方案空间确实很广时，才增加到五个。超过五个后，没有人会逐一比较，只会不断滚动浏览。

先把方案集写下来，每个方案对应一个名称和一个轴线位置。名称应体现其方向，例如 `Quiet`、`Editorial`、`Dense`，绝不要使用 `Option A`。

当任意两个变体都不处于同一位置，并且你能用一个短语描述每个变体在轴线上的位置时，这一步就完成了。

## 4. 将其构建到真实页面中

变体单独看时往往效果不错，这正是为什么不应该孤立地评判它。将变体放到实际承载该组件的页面上，与真实的页面框架、真实的相邻元素和逼真的数据一起呈现。

使用 URL 查询参数（`?variant=quiet`）进行选择，这样每个变体都对应一个可发送给他人的链接。通过一个浮动控件设置该参数；具体规范见 [picker.md](picker.md)。

每次只渲染一个变体，并以完整尺寸呈现。缩略图会扭曲间距和比例，而间距通常正是你需要权衡选择的要素。

如果没有合适的页面可以承载它，就构建一个独立的 HTML 文件，并保留同样的选择器。

为每个变体提供真实内容：符合产品语境的文案、可信的名称，以及页面实际承载的条目数量。Lorem ipsum 和三行数据会让任何结构看起来都不错。

## 5. 展示权衡，然后停止

先亲自逐一查看每个变体。确保每个变体都能正常渲染，每项交互都有响应，控制台没有错误。

然后将决定权交出去：

| 变体 | 轴线位置 | 适用情形 | 代价 |
| --- | --- | --- | --- |
| Quiet | 最低视觉权重 | 页面每天都会使用 | 最不令人印象深刻 |
| Editorial | 最大字号、最多留白 | 这一时刻值得突出强调 | 占用垂直空间 |

说明选择器运行在哪里、哪个按键可以切换它，以及你评判时使用的宽度。答案在 375px 和 1440px 下可能会有所不同。

绝不要在表格中标出偏好的方案。如果被直接询问，应根据该组件出现的频率和产品的个性作答，而不是根据你在构建哪个方案时最享受。

## 6. 推进一个方案，删除其余方案

选定后：按照项目自身的规范，在该方案所属的位置将其完整实现，然后删除其他方案和测试框架。

如果对方要求再做一轮，则保留测试框架并再次执行第 3 步，围绕你倾向的方向选择新的位置。

在正式推进之前，测试框架绝不从生产代码导入内容，生产代码也绝不从测试框架导入内容。

## 完成之前

| 错误 | 修正方式 |
| --- | --- |
| 变体之间仅强调色或文案不同 | 将其中一个移到主轴线上的不同位置，或者将其删除 |
| 所有轴线同时变化 | 只改变一个轴线，让其余变化随之自然产生 |
| 在空白路由上进行评判 | 将它们放到实际承载该组件的页面上 |
| Lorem ipsum、三行数据、"Jane Doe" | 使用真实文案，以及页面实际承载的条目数量 |
| 最大胆的变体跳过了键盘操作或焦点状态 | 满足最低标准，否则放弃该方向 |
| 在表格中标出偏好的方案 | 说明每个变体的代价，让用户选择 |
| 使用项目的令牌重新设计选择器 | 让它明显独立于设计系统之外 |
| 正式推进后仍保留测试框架 | 除非对方要求保留，否则将其删除 |
