# 变体

此技能会针对一块描述过的 UI 构建三个有意做出差异的版本。它们会显示在真实页面中的选择器后面，因此你可以在它们之间切换并进行选择。

这里的其他技能负责评判。此技能负责生成候选方案，并将决定权交还给你。评审现有 UI 应使用 `interface-review` 和 `better-interface`，它们不会选择最终胜者。

## 不同的答案，而不是不同的色调

三个仅在强调色上有所不同的变体毫无意义。在它们之间切换时，你看不到真正的选择，这次运行也就浪费了。

因此，每个变体都应当在本集合负责的某个维度上，针对同一份需求给出不同的答案：

| 维度 | 负责技能 | 变化内容 |
| --- | --- | --- |
| 结构 | `better-layout` | 分组、顺序、列数、哪些内容折叠 |
| 密度 | `better-layout` | 间距尺度、点击区域、可容纳的信息量 |
| 强调 | `better-colors` | 填充色出现的位置、哪些内容退居次要 |
| 字体 | `better-typography` | 字号阶梯、字重对比、行宽 |
| 语气 | `better-writing` | 标签、语调、文案长度 |

**选择一个主要维度**，让每个变体在这个维度上处于不同的位置。次要选择应由主要维度推导出来，而不是自行变化。一个高密度的变体可能需要更小的字号阶梯，而这属于整体一致性，不是第二个维度。

同时改变所有维度会产生三个无法归因的结果。你只能知道自己喜欢哪一个，却不知道它为什么有效，于是下一个组件又得从零开始。

## 每个变体都必须达到的底线

一个外观取胜、却无法通过升级触发条件的变体，不是候选方案，而是一个表面漂亮的 bug。

在变体进入选择器之前，它必须通过 `better-interface` 的升级触发条件。每个控件都有可访问名称，键盘能够到达指针可以到达的所有内容，焦点清晰可见，在 320px 宽度下不会发生裁切，任何含义都不能只依赖颜色表达。

所有变体的这条底线都必须相同。它不是一个维度，也绝不能拿它与其他维度交换。如果某个方向只有通过破坏这条底线才能实现，就明确说明并放弃该方向。

## 1. 确定一个组件的范围

每次运行只处理一个 UI 组件。“仪表盘”不是一个组件；指标卡才是。如果需求涵盖多个组件，就指出其中作为其他组件依托的那个组件，说明原因，并将其余组件作为后续运行。

用一句话重述需求：这个东西是什么、在哪里渲染、必须完成什么任务。

## 2. 了解基础环境

变体必须看起来像是明天就能发布，因此要先阅读它们所依托的基础环境：

- 样式系统、组件库以及任何动效库。
- 设计令牌：颜色、间距、圆角、字号阶梯、缓动。
- 产品的密度和语气。高密度的专业工具会限制最大胆变体可以走多远。
- 该组件的渲染位置：所处的背景、相邻的组件，以及需要适配的宽度。

如果没有项目可供阅读，就使用中性灰色、一个强调色和系统字体栈，并说明你就是这样做的。

## 3. 在编写代码之前确定维度

默认生成三个变体。只有在被要求时，或空间确实足够宽裕时，才增加到五个。超过五个之后，人们不会进行比较，而只会滚动浏览。

先写下这组变体，每个变体各有一个名称和一个轴位置。名称应说明方向是什么，例如 `Quiet`、`Editorial`、`Dense`，不要使用 `Option A`。

当没有两个变体共用同一位置，并且你能用一句话说出每个变体所在的轴时，这一步就完成了。

## 4. 将其构建到真实页面中

一个变体单独看起来不错，这正是不能在孤立环境中评判它的原因。将这些变体放到实际承载该组件的页面中，同时使用真实的页面框架、真实的相邻内容和符合实际的数据。

使用 URL 查询参数进行选择（`?variant=quiet`），这样每个变体都是一个可以发给别人的链接。通过一个浮动控件设置该参数；规范见 [picker.md](picker.md)。

一次渲染一个变体，并使用完整尺寸。缩略图会扭曲间距和缩放比例，而间距通常正是你需要在不同方案之间做选择的部分。

如果没有页面可以承载它，就构建一个自包含的 HTML 文件，并保留同样的选择器。

为每个变体提供真实内容：符合产品形态的文案、合理的名称，以及页面实际会承载的项目数量。Lorem ipsum 和三行内容会让每种结构看起来都不错。

## 5. 展示权衡并停止

先亲自浏览每个变体。每个变体都能渲染，每个交互都有响应，控制台保持干净。

然后将决定权交给对方：

| 变体 | 轴位置 | 适用情况 | 代价 |
| --- | --- | --- | --- |
| Quiet | 最低的视觉权重 | 页面会被每天使用 | 最不容易留下印象 |
| Editorial | 最大字号，最多留白 | 这个时刻值得强调 | 占用大量垂直空间 |

说明选择器运行在哪里、按哪个键可以切换，以及你是在什么宽度下进行评判的。375px 和 1440px 下的答案可能不同。

不要在表格中标记最喜欢的方案。如果对方直接询问，就根据该组件被看到的频率和产品的个性来回答，而不是根据你最喜欢构建哪一个来回答。

## 6. 选定一个并删除其余部分

确定选择后，在它所属的位置按照项目自身的约定正确构建该变体，然后删除其他变体和测试框架。

如果对方要求再进行一轮，则保留测试框架并重新执行第 3 步，围绕你倾向的方向选择新的位置。

在正式采用之前，测试框架绝不能导入生产代码，生产代码也绝不能导入测试框架。

## 完成之前

| 错误 | 修复方法 |
| --- | --- |
| 变体之间只有强调色或文案不同 | 将其中一个移动到主轴上的不同位置，或者删掉它 |
| 每个轴都同时发生变化 | 只改变一个轴，让其余部分由它决定 |
| 在空白路由上进行评判 | 将它们放到实际承载该组件的页面中 |
| Lorem ipsum、三行内容、“Jane Doe” | 使用真实文案和页面实际会承载的项目数量 |
| 最大胆的变体跳过键盘操作或焦点处理 | 清理基础问题，或者放弃这个方向 |
| 在表格中标记最喜欢的方案 | 说明每个变体的代价，让用户自行选择 |
| 使用项目的设计令牌重新设计选择器 | 让它在视觉上明确处于设计系统之外 |
| 正式采用后仍留下测试框架 | 删除它，除非对方要求保留 |
