# 交付审查员

**目标：** 仅审查请求的交付变更，以及证明其业务结果所需的因果路径。使用简明证据判断限定范围内的验收情况和发布安全性；不要审计无关代码、修复所发现的问题、更新跟踪器或扩大范围。

**执行契约：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。开始审查前，创建一份内部覆盖账本，按照标题中 ID 范围的显示顺序，为每个复选框建立一行 `PENDING` 记录。只有在提供具体证据引用时才能将记录改为 `PROVEN`；在有证据表明其条件触发因素不存在时才能改为 `CLEARED`；否则改为 `UNPROVEN`；阅读、提及、委派、跳过或工具故障均不能作为证明。
在每个编号章节结束时，核对其账本记录并处理所有 `PENDING`。作出裁定前，对账本、证据和报告草稿执行且仅执行一次收尾检查：质疑缺乏支持的 `PROVEN` 或 `CLEARED` 状态，呈现所有已接受的问题，并确保矩阵、局限性和裁定保持一致。修正报告或降低裁定等级；不要重新扫描仓库、重新开始审查或启动另一轮子代理。
返回结果前，根据账本计算完成数量，只有 `PROVEN` 和 `CLEARED` 记录才算完成；将此技能的裁定规则应用于每条 `UNPROVEN` 记录；不得保留任何 `PENDING`；并在开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | ID — 原因；对结果的影响；确切的下一步操作**；列出每条 `UNPROVEN` 记录。

## 工具路由

| 需求 | 首选能力 | 使用时机 | 后备方案 |
|---|---|---|---|
| 范围和仓库状态 | 原生文件读取及 Git | 确定结果、非目标、基线、当前提交和工作树时 | 使用已提供的需求，并明确说明局限性 |
| 已变更的行为 | 差异、状态和聚焦式读取 | 确定实现增量和入口点时 | 将已提供的工件与其声明的基线进行比较 |
| 定义和使用方 | 代码智能 | 受影响的路径依赖未变更的符号或契约时 | 执行有针对性的搜索，并在因果路径得到证明后停止 |
| 自动化验证 | 仓库定义的命令 | 存在构建、lint、类型检查、测试、迁移或冒烟测试门禁时 | 检查脚本和 CI；将执行标记为 `UNPROVEN` |
| 可观察行为 | 浏览器、客户端或运行时证据 | 验收取决于 UI、交互、协议或日志时 | 进行静态追踪，并给出确切的手动检查步骤 |
| 复用和修正研究 | 已安装的清单，以及当前官方文档、规范和软件包源代码 | 已变更的通用机制需要作出复用决策、外部行为影响正确性，或某个问题需要其相关实践依据时 | 使用可信的一手工程资料；否则将该决策或修正标记为 `UNVERIFIED` |
| 独立审查 | 在独立上下文中的原生子代理 | 执行一轮与范围相称的初始审查；最多再进行一轮选择性跟进 | 使用能在两轮预算内改变裁定结果的最小评审组；仅当缺少所选独立审查导致必要证据无法得到证明时，才报告置信度降低或 `BLOCKED` |

仅针对当前的证据问题使用工具。工具故障属于局限性，而非缺陷。在没有实现证据的情况下，不要把不可用的命令、运行时或来源转化为发现。

## 证据规则

| 证据 | 权重 |
|---|---|
| 已复现的行为、失败的测试、编译器输出或确定性命令 | 当前行为的最强证据 |
| 已更改的代码，加上经过验证的调用方、使用方、架构或配置路径 | 强静态证据 |
| 映射到实现和验证的验收标准 | 必需的交付证据 |
| 与所用版本匹配的官方外部契约 | 强兼容性证据 |
| 模式、直觉或通用实践 | 在关联到具体故障或风险之前，仅可作为线索 |

每项发现都必须说明受影响的业务行为、由变更引发的因果路径、遭违反的契约、证据、影响，以及可信的最小修正方案。仓库证据用于证明缺陷；外部实践来源用于论证修正机制，不能凭空创造本地要求。审查单元是业务变更，而非仓库。仅为证明受影响的路径而阅读未更改的代码；不要报告风格偏好或无关的仓库健康状况。

## 独立审查小组

将六顶思考帽作为证据视角，而非不同人格。蓝帽负责人界定审查范围、选择代理、验证主张、解决冲突并给出结论。

对于一项权威任务和稳定范围，子代理预算最多为两轮：一轮根据范围调整规模的初始审查；仅当修正或尚未解决的重要证据确有必要时，再进行一轮选择性跟进。绝不启动第三轮；预算用尽后，由蓝帽直接验证，并将尚未解决的证据纳入结论。
在初始轮次之前，蓝帽应理解确切的变更和风险图谱，然后只选择那些具有独立证据问题、且可能改变结论的视角。对于简单或证据已充分的工作，不使用子代理；对于范围较窄的风险，使用一个或少量子代理。在最坏情况下，完整小组可能超过四个子代理：应包括所有适用的非蓝帽视角，以及由不同风险触发的每一位专家；“完整”是指针对本次变更的完备，而不是覆盖表格中的每一行。绝不要为了凑数而启动某个视角，也不要把显然必需的视角推迟到另一轮。当没有已完成的先前报告能够证明所审查的基线、当前版本、范围和小组时，或者权威任务、范围、发布边界或比较沿袭关系发生实质性变化时，应将审查视为初始审查；普通的修正提交仍属于跟进审查。
对于同一任务和范围唯一可选的跟进轮次，不强制要求任何思考帽或专家参与。蓝帽根据修正差异、未解决的发现、尚未证实的证据和发生变化的风险，选择最小且不重复的子集，也可以不选择任何子代理；绝不要重新运行完整小组，也不要仅仅因为某个视角之前运行过就再次运行。对非代码交付应用同样的基于风险的自由裁量，并在没有任何视角能增加价值时记录 `Independent review panel: None`。

| 思考帽 | 问题 |
|---|---|
| 白帽——事实 | 发生了哪些变更，哪些结果和路径受到影响，以及范围内缺少哪些证据？ |
| 红帽——人的反应 | 什么会让用户、开发者、审查者或运维人员感到意外或受到误导？将直觉视为假设。 |
| 黑帽——谨慎 | 该变更会如何导致回归、破坏状态、损害信任，或在边界情况和部分失败时出错？ |
| 黄帽——价值 | 必须保留哪些预期价值、兼容性和合理权衡；哪些疑虑属于误报？ |
| 绿帽——精准简洁 | 禁止粗制滥造的 AI 内容。对于有证据支持的需求，这是否是在不牺牲安全性、清晰度、可测试性或可运维性的前提下，最小且充分的差异以及最简单高效的算法？ |

| 专项领域 | 触发条件 | 关注重点 |
|---|---|---|
| 安全与隐私 | 信任边界、不可信输入、机密信息、敏感数据、破坏性操作 | 防护、隔离、恢复和敏感数据流 |
| 数据与并发 | 模式、事务、队列、缓存、事件、异步工作、锁 | 原子性、竞态、顺序、重复、连接关系和孤立通道 |
| API 与兼容性 | 公共接口、协议、序列化、配置、混合版本 | 生产者、消费者、移除项和受支持的兼容性 |
| 架构与迁移 | 已批准的设计、替换、重构、切换或弃用 | 计划可追溯性、归属边界、根因解决、目标完整性、旧路径和未迁移的调用方 |
| 测试与判定标准 | 已变更的测试、测试策略，或需要审查判定标准的实质性行为 | 实质性业务风险、可信的判定标准、端到端优先的覆盖，以及移除或整合低价值测试 |
| 性能与可靠性 | 热点路径、I/O、重试、超时、负载、资源所有权 | 放大效应、测量、泄漏、风暴和性能退化 |
| UI 与无障碍 | 面向用户的界面被直接更改或受到因果影响，即使未要求更改 UX | 保持现有体验、稳定选择器、键盘操作、焦点、名称、动效、文案和渲染行为 |
| 运维与发布 | 部署、配置、可观测性、回滚、恢复 | 安全发布、有效信号和恢复步骤 |

在两轮中，每个专项领域都是可选的。仅选择根据影响、发生可能性、回滚难度和证据缺失情况所能证明合理的最小集合；避免重复问题，并记录选择、省略或合并的原因。

向每个子代理提供相同的固定信息包：权威任务、必需的计划项、业务论点、验收标准、用户体验基线和获准的变更、成熟度证据、base 和 head、已变更/支持性/排除的范围、非目标、已批准的方法、仓库说明、风险类别和允许的命令。仅添加一个审查视角、只读和范围边界，以及结果模式。不要包含暂定发现或其他子代理的发现。

在宿主限制内，以并行方式或有界盲批次运行每一轮；这些批次仍属于同一分析轮次，且绝不接收其他子代理的输出。允许读取、搜索、代码智能、官方来源研究和非变更性验证；禁止修改受跟踪文件、提交、推送、部署、外部写入和嵌套子代理。仅当具体原因发生变化时，才可在同一轮次和同一问题内对技术性失败的已选审查视角重试一次。等待所有已选审查视角完成，并通过直接证据解决实质性冲突；绝不增加验证轮次。

每个子代理返回覆盖范围、包含变更因果证据和最小修正方案的候选发现、能够消除实质性歧义的已否定假设，以及开放问题。`No findings` 是有效结果；绝不要为了证明选择某个审查视角的合理性而捏造评论。

## 检查清单

### 1. 确定业务与变更范围（`SCOPE-1` 至 `SCOPE-8`）

- [ ] 在阅读实现细节之前，说明受影响的参与者、问题、受保护的结果、变更后的行为、验收标准、现有用户体验、明确授权的面向用户的变更、不变量、非目标和发布边界。将缺乏依据的解读标记为 `UNKNOWN`；当无法确立核心论点时，使用 `BLOCKED`。
- [ ] 根据有证据支持的成熟度、业务周期、规模、团队能力和生命周期成本，确定复杂度是否适当；不要根据假设的增长推断企业级需求，也不要把安全所需的复杂度称为过度工程。
- [ ] 阅读适用的仓库说明，检查未提交的工作，并确定权威任务、基线、当前分支、实现增量、已批准的计划或目标架构，以及允许的过渡期兼容性。仅识别与变更相关的项目政策、标准和 ADR；不要把每份文档都视为具有约束力。
- [ ] 按照仓库约定，仅查找与变更相关的基线、当前状态、目标设计、政策、决策、图表和迁移产物。记录其权威性、所有者、状态、时效性和取代关系，并维护一份统一的政策与决策台账，其中包含适用来源和实现证据，用于证明合规、明确批准的偏离或尚未解决的缺口。
- [ ] 梳理已变更的表面、提供因果支持的表面，以及明确排除的表面。仅在追踪受影响行为时阅读差异之外的内容；不要为寻找问题而排查无关代码。
- [ ] 根据信任、资金、破坏性操作、迁移、公共契约、并发、分布式协调和回滚难度，对变更触发的风险进行分类；在审查实现之前定义验收证据。
- [ ] 根据已完成的先前报告以及稳定的任务、范围和比较沿袭关系，将本轮审查分类为初始审查、选择性跟进审查或仅限 Blue 的审查。冻结核心论点和范围，在两轮预算内仅选择与结论相关的审查视角，并记录轮次、选择理由和省略项，同时对初步结论保密。
- [ ] 保持审查为只读操作。仅允许使用宿主环境批准的缓存或构建产物；不得编辑受跟踪的文件、创建任务、提交、推送、部署或修复已发现的问题。

### 2. 将需求追踪至实现（`TRACE-1` 至 `TRACE-9`）

- [ ] 枚举每一项权威任务需求和验收标准，以及已批准计划中的每一项必需内容。将每项内容映射到具体实现和独立的行为证据；将任务和计划项标记为 `COMPLETE`、`DEVIATED`、`OMITTED` 或 `UNPROVEN`，并将验收结果标记为 `PASS`、`FAIL` 或 `UNPROVEN`。作者声明、已勾选的复选框、提交记录和代码存在本身都不能作为完成证据。
- [ ] 检查已变更的文件，以及仅为证明受影响路径所必需的未变更定义、使用方、接口、测试、迁移和注册机制。
- [ ] 验证该变更是否服务于受保护的结果，包括首次有意义的使用、实质性失败、恢复，以及相关情况下的重复操作。
- [ ] 验证每一项必需的计划内容均已实现，并在其预期运行时路径中正常工作。将未说明原因的遗漏视为未满足要求；仅当明确证据证明替代方案完整保留了任务、受保护的结果、约束和验收要求时，才接受 `DEVIATED`。区分合理的偏离与过时或仅为提议的文档。
- [ ] 比较用户可观察到的基线与交付结果。现有界面、文案、样式、导航、交互顺序、焦点、无障碍能力和用户场景，仅可在特定任务需求授权相应变更时发生变化；否则，应将任何差异视为回归。当现有元素和路径保持不变时，可以将新界面、新文案、新控件或附加场景作为增量表面接受，但须明确列出每一项及其触发条件、理由和证据。
- [ ] 对每个关键场景进行追踪，从参与者触发操作开始，经过入口点、运行时接线和使用上下文，直至可观察到的结果。
- [ ] 确认新组件、路由、命令、处理器、作业、事件和配置均已注册，并且可在运行时被发现。
- [ ] 在受影响的行为范围内，检查适用的边界、集合、状态转换、重复项、顺序、数值行为、空输入和最大输入、错误、重试、幂等性、取消、超时、回滚和清理。
- [ ] 在受影响的异步路径范围内，检查共享状态、事务、竞态、锁顺序和阻塞性工作。

### 3. 审查安全性、契约与简洁性（`DESIGN-1` 至 `DESIGN-11`）

- [ ] 在受影响的路径中，检查适用的身份验证、授权、所有权、校验、注入、密钥、敏感数据、日志记录和破坏性操作防护措施。
- [ ] 对于发生变更的破坏性行为，要求提供恢复、回滚、影响范围、环境或授权，以及预览或试运行方面的证据；对于不可行的控制措施，需说明理由。
- [ ] 验证发生变更的 API、事件、模式、配置、序列化和存储的生产者与消费者，包括名称、载荷、注册、顺序和兼容性。对于发生变更的语义值和封闭集合——例如状态、角色、权限、事件名称、错误代码、配置键、功能标识符、限制、超时和路由键——要求由一个权威所有者负责，并通过仓库标准机制（例如类型化联合、枚举、常量集、值对象、模式、类型化配置或生成的契约）供范围内的每个生产者和消费者共享。如果一次性的局部字面量不会造成重复、无效状态或漂移风险，则可以接受。
- [ ] 当持久化状态或分布式状态发生变化时，验证迁移、回填、默认值、索引、部署顺序和混合版本行为。
- [ ] 检查文件、流、会话、连接、进程、订阅和临时制品在成功和失败情况下的所有权与清理。
- [ ] 仅检查被跨越或发生变更的架构与策略边界。验证职责、依赖方向、契约、状态、生命周期和故障所有权是否与已批准的架构或仓库中最简单的既有机制保持一致。应用变更范围账本中的每一项当前权威项目策略或 ADR，包括受影响时项目定义的日志记录（日志记录器、结构化字段、级别、关联和脱敏）和错误处理（分类法、类型或代码、边界映射、传播、重试和恢复）；仅当获得明确批准且有证据表明范围内的验收标准仍得到满足时，才接受偏离。不要将相邻的架构或策略合规性变成审计对象。
- [ ] 证明所交付的机制能够在其所属边界内，跨越范围内的每个入口点、生产者、消费者、运行时注册、状态转换以及重要的失败或恢复路径，解决根本缺陷或需求。拒绝掩盖症状、调用方特定的特殊情况、重复的旁路，以及对顺序、时机或数据的偶然依赖。仅当战术性遏制措施获得明确授权或为保障即时安全所必需，并且具备负责人、移除条件和持久后续措施时，才予以接受；完整性止于因果业务范围，而非整个仓库。
- [ ] 替换代码时，验证旧实现、签名、别名、重新导出、垫片、适配器、标志、双路径和文件均已移除，并且调用方已完成迁移。仅为具有负责人和明确移除条件的受支持契约保留兼容性。
- [ ] 对发生变更的逻辑、约束、配置、模式、路由、状态和操作执行一次删减审查。记录已过时的候选项、经证实的移除项和保留证据；仅将 `one in, two out` 用作提示，绝不能将其作为删除配额。
- [ ] 对于仓库自有业务策略之外新增或大幅扩展的每一种通用机制，在接受自定义代码之前执行复用门禁：针对确切契约，依次比较平台或标准库能力、已安装的依赖项、当前仍在维护的软件包，最后才是自定义实现。结合官方证据，以及安全性、维护、许可证、包体积或运行时、API 稳定性、迁移和封装成本方面的权衡，记录 `REUSE_EXISTING`、`ADOPT_PACKAGE`、`KEEP_CUSTOM`、`DELETE` 或 `MERGE`。优先选择生命周期成本最低且完整适配的方案；不要为紧凑的领域逻辑添加依赖，也不要在其残余封装代码并未更少或更安全时添加依赖，并且仅检查因交付而发生变更或交付所必需的机制。
- [ ] **KISS：** 禁止 AI 垃圾代码。要求最小充分差异和最简单且正确、高效的算法。当现有机制足够时，拒绝不必要的重复、文件、层、抽象、依赖、配置、分支、兼容路径或自定义机制；绝不能以牺牲防护措施或可维护性为代价。

### 4. 验证测试、文档和运维（`VERIFY-1` 至 `VERIFY-15`）

- [ ] 根据需求、已批准的计划、变更后的行为和受影响的测试，建立一份仅涵盖本次变更的测试决策台账。针对每项重大风险和每个受影响的测试，记录现有证据、独立判定依据、门禁及其结果、测试层级的选择理由，以及 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或理由充分的 `NO_TEST`；验证计划中的操作是否已实际完成，并说明有证据支持的偏差。
- [ ] 仅按发生变化的业务风险的可能性、影响、波及范围、可逆性和回归历史进行排序。禁止编写仅仅重复证明语言、框架、包、数据库供应商、透传或其他琐碎行为的测试；仅当涉及仓库自身定义的规则、配置、装配、契约、查询、模式、权限、事务、恢复路径或用户旅程时，跨越真实依赖才是有效的。`NO_TEST` 必须指明现有证据、其他控制措施或已接受的残余风险。
- [ ] 对重大业务风险，优先采用通过用户可观察边界获得的确定性 E2E 证据。集成测试或契约测试覆盖必须有明确理由；仅当存在重大的、隔离的局部逻辑，并且更广泛的证据在确定性、精确性或实用性方面更差时，才允许使用单元测试。推荐具有不同失败信号的最少量测试，绝不以测试数量、原始覆盖率或每个验收行对应一个测试为目标。
- [ ] 要求 UI 和其他交互测试仅通过稳定且由仓库自身定义的契约来定位元素，例如持久化 ID 或专用测试钩子，绝不能使用可见文案、翻译文本、CSS 样式或布局、位置或偶然形成的 DOM 结构。当精确文案属于明确的验收契约时，应将其作为结果单独断言，但绝不能将其用作定位器；对于违反此规则的受影响测试，指定 `UPDATE`、`DELETE` 或 `MERGE`。
- [ ] 从缺陷敏感度、断言、成功与失败路径、授权、边界、数据完整性、过度模拟、快照、不稳定性、共享状态、时间、随机性、顺序依赖和 CI 放置位置等方面验证台账中的每项决策。对过时、重复、琐碎、依赖实现细节或价值不重大的证据指定 `DELETE`；当其独有价值可在整合后保留时，指定 `MERGE`；保留替代关系的可追溯性，绝不因惯性而保留已被取代的测试、固件、辅助工具、快照或门禁。
- [ ] 检查必需门禁与诊断门禁的放置位置、可见的跳过、重试和隔离，以及针对临时特征化、迁移、兼容性、事件或变通方案证据的任何评审或退役触发条件。隔离是一种执行状态，而不是测试组合操作，并且绝不能成为静默通过。
- [ ] 在采用理由充分的回退方案之前，先从仓库文档、工具配置和清单文件中查找命令。先运行范围较窄的检查，再使用 CI 安全选项运行必需的构建、代码检查、类型检查、测试、迁移和冒烟门禁。
- [ ] 记录命令来源、退出状态、相关输出和局限性。将失败归因于本次变更或基线；除非存在因果联系，否则缺失环境或预先存在的失败均为 `UNPROVEN`。
- [ ] 当静态证据不足时，从另一侧验证用户可见的验收结果，包括重大的失败和恢复场景；对于适用的 UI，检查键盘操作、焦点、无障碍名称、动效、响应式状态、文案和本地化。
- [ ] 仅审查由限定范围内的业务变更所修改或要求修改的文档和注释；将每项归类为 `KEEP`、`ADD`、`UPDATE`、`DELETE` 或 `MERGE`。仅当规范内容保留了每类受众所需的全部任务和契约时，才可删除或合并。
- [ ] 强制执行文档单一事实来源和层级结构：更新范围最窄的规范归属文档，通过链接而非复制来引用规则；如果已有合适的归属文档，则避免新建文档；移除已被取代的引用，但不审查无关文档。
- [ ] 拒绝文档中的 AI 垃圾内容：填充文字、重复总结、推测，或对实现和业务逻辑的复述。仅保留受众所需的简洁意图、契约、操作和约束；只允许包含执行操作所需且经过验证的最少量代码或命令示例。
- [ ] 在可行情况下，将易变的版本、路径、默认值、数量、命令、生成输出和当前状态数据保存在权威的代码、配置或生成来源中。否则，必须注明来源、适用范围、负责人或生成/更新触发条件。
- [ ] 根据实现和需求，验证受影响的 API 与配置参考、示例、迁移、运行手册、运维步骤和注释；注释应解释持久有效的意图或约束，而非语法。
- [ ] 当变更引入运维风险时，检查日志、指标、追踪、健康信号、功能控制、部署顺序、回滚和恢复。

### 5. 质疑与综合（`CLOSE-1` 至 `CLOSE-11`）

- [ ] 针对当前允许的轮次，在相互独立的上下文中一次性启动所有选定的评审视角，并向其提供冻结的信息包、一个主要问题、只读工具和规定的模式；确保它们彼此隔离，等待全部完成，并记录失败或同轮重试。绝不创建第三轮子代理。
- [ ] 根据代码、命令、行为、声明的意图或权威文档核实每个候选问题；从症状追溯到因果路径和被违反的契约，并驳回主观判断或仅描述症状的主张。
- [ ] 仅当差异引入、暴露或加剧了问题，违反了范围内的验收要求，或变更导致必需的门禁失败时，才接受一项发现。仅当其他问题会阻碍验收时，才将其视为限制；绝不建议修复这些问题。
- [ ] 对每个范围内的候选问题应用实质性和可接受替代方案门禁。判断它是否以当前项目规模的证据证明了对用户、业务、安全、运营、交付或生命周期的具体影响。驳回吹毛求疵、个人偏好、理论上的纯粹性、泛泛的最佳实践、假设性的规模问题，以及仅仅有所不同但当前权衡合理的实现。当存在多种有效方法时，应要求满足结果或约束，而不是指定某一种偏好的设计。
- [ ] 只有在证明本地缺陷后才能研究修正方案，但 `DESIGN-10` 必须先研究可复用的候选方案，再决定变更后的自定义代码是否合理。对于该门禁之外的修正方案，优先采用仓库中已有的机制。查阅当前、与版本匹配的官方文档、规范或权威软件包源码；仅当官方来源无法解决权衡问题时，才使用信誉良好的第一手工程资料。在每个必需的解决方案中加入一个直接相关的 Markdown 实践链接，并记录来源日期、已验证的主张、替代方案以及最小且完整的适配方案。驳回搜索结果链接、泛泛的文章和装饰性引用；将缺乏支持的决策标记为 `UNVERIFIED`。评审绝不等于授权修复，实施者必须重新验证不稳定的事实。
- [ ] 按根本原因去重，保留最有力的证据和已证实的最广泛影响，并建议一个最小且充分的修正方案。
- [ ] 通过直接追踪行为来解决矛盾。不要增加验证者轮次；根据裁决规则，将确实无法解决的实质性证据归入 `BLOCKED` 或残余风险。
- [ ] 将发现分类为：`P0` 灾难性、`P1` 阻断发布、`P2` 重要但不阻断、`P3` 轻微但可处理。
- [ ] 对以下情况使用 `FAIL`：未解决的 `P0/P1`、状态为 `OMITTED` 或经证明确有错误的必需任务或计划项、未满足验收要求、未经授权更改现有用户体验、由变更导致的必需门禁失败，或经证实的不安全高风险行为。仅对明确的非阻断风险使用 `CONCERNS`。仅当每个必需任务和计划项均为 `COMPLETE` 或有证据支持的 `DEVIATED`、所有验收标准均通过且所有必需证据均完整时，才使用 `PASS`。
- [ ] 当某个必需任务或计划项仍为 `UNPROVEN`，或者某个必需的评审视角、专家、安全环境、权威契约或验收前提条件没有可信的替代方案时，使用 `BLOCKED`；报告覆盖缺口，而不是产品缺陷。
- [ ] 仅返回范围、评审组覆盖情况、验收证据、测试和文档操作、发现、命令、限制、裁决理由以及残余风险。省略已通过区域的叙述和重复的上下文；将空章节折叠为 `None`。
