# 并行调试

通过并行代理调查、采用竞争性假设分析（Analysis of Competing Hypotheses，ACH）方法来调试复杂问题的框架。

## 何时使用此技能

- 缺陷存在多个貌似合理的根本原因
- 初步调试尝试未能定位问题
- 问题涉及多个模块或组件
- 需要基于证据的系统性根因分析
- 希望在调试中避免确认偏误

## 假设生成框架

围绕以下 6 类故障模式生成假设：

### 1. 逻辑错误

- 条件逻辑不正确（运算符用错、遗漏分支）
- 循环或数组访问中的差一（off-by-one）错误
- 缺少对边界情况的处理
- 算法实现不正确

### 2. 数据问题

- 无效或意外的输入数据
- 类型不匹配或类型强制转换错误
- 在应有值的位置出现 Null/undefined/None
- 编码或序列化问题
- 数据截断或溢出

### 3. 状态问题

- 并发操作之间的竞态条件
- 过期缓存返回过时数据
- 初始化或默认值不正确
- 共享状态被意外修改
- 状态机转换错误

### 4. 集成故障

- 违反 API 契约（请求/响应不匹配）
- 组件之间版本不兼容
- 环境之间配置不匹配
- 环境变量缺失或不正确
- 网络超时或连接失败

### 5. 资源问题

- 内存泄漏导致性能逐渐劣化
- 连接池耗尽
- 文件描述符或句柄泄漏
- 磁盘空间或配额超限
- 低效处理导致 CPU 饱和

### 6. 环境

- 缺少运行时依赖
- 库或框架版本错误
- 平台特有的行为差异
- 权限或访问控制问题
- 与时区或区域设置相关的行为

## 证据收集标准

### 什么构成证据

| 证据类型     | 强度     | 示例                                                         |
| ----------------- | -------- | --------------------------------------------------------------- |
| **直接证据**        | 强   | `file.ts:42` 处的代码显示 `if (x > 0)` 应为 `if (x >= 0)` |
| **相关性证据** | 中   | 提交 `abc123` 之后错误率上升                      |
| **证言证据**   | 弱   | “在我机器上是好的”                                        |
| **缺失性证据**       | 视情况而定 | 代码路径中未发现空值检查                            |

### 引用格式

标注证据时，始终使用 file:line 格式的引用：

```
**Evidence**: The validation function at `src/validators/user.ts:87`
does not check for empty strings, only null/undefined. This allows
empty email addresses to pass validation.
```

### 置信度级别

| 级别               | 判定标准                                                                            |
| ------------------- | ----------------------------------------------------------------------------------- |
| **高（>80%）**     | 多项直接证据、因果链清晰、无矛盾证据      |
| **中（50-80%）** | 部分直接证据、因果链合理、存在少量模糊之处                     |
| **低（<50%）**      | 以相关性证据为主、因果链不完整、存在部分矛盾证据 |

## 结果仲裁协议

在所有调查者完成汇报之后：

### 步骤 1：对结果分类

- **已确认**：置信度高、证据充分、因果链清晰
- **可能成立**：置信度中等、有一定证据、因果链合理
- **已证伪**：证据与假设相矛盾
- **无法定论**：证据不足以确认或证伪

### 步骤 2：比较已确认的假设

若多个假设均得到确认，按以下因素排序：

1. 置信度
2. 支持证据的数量
3. 因果链的强度
4. 是否不存在矛盾证据

### 步骤 3：确定根本原因

- 若某个假设明显胜出：将其判定为根本原因
- 若多个假设可能性相当：可能是复合性问题（存在多个促成原因）
- 若没有假设得到确认：根据已收集的证据生成新的假设

### 步骤 4：验证修复

在宣布该缺陷已修复之前：

- [ ] 修复针对已识别的根本原因
- [ ] 修复未引入新问题
- [ ] 原始复现用例不再失败
- [ ] 相关边界情况已覆盖
- [ ] 已添加或更新相关测试
