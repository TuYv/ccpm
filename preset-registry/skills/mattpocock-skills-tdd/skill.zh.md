# 测试驱动开发

TDD 是红灯 → 绿灯循环。本技能是让这一循环产出值得保留的测试所需的参考指南：什么是好的测试、测试应放在哪里、应避免的反模式，以及循环的规则。每一节都适用于每一轮循环：应在循环开始前和进行过程中查阅，而不是事后查阅。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），以确保测试名称和接口词汇与项目的领域语言一致，并遵循与你所改动区域相关的 ADR。

## 什么是好的测试

测试应通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变，但测试不应随之改变。好的测试读起来就像一份规格说明：“用户可以使用有效购物车结账”准确说明了具备什么能力，而且它不关心内部结构，因此能够经受重构。

示例请参阅 [tests.md](tests.md)，模拟指南请参阅 [mocking.md](mocking.md)。

## 接缝：测试应放在哪里

**接缝**是进行测试的公共边界：你可以在不深入内部的情况下观察行为的接口。测试应位于接缝处，绝不能针对内部实现。

**只在预先约定的接缝处测试。** 在编写任何测试之前，先写明要测试的接缝，并与用户确认。未经确认的接缝不得编写测试。你无法测试所有内容，因此，预先约定接缝可以确保测试工作集中在关键路径和复杂逻辑上，而不是每个边缘情况上。

请询问：“公共接口是什么，我们应该测试哪些接缝？”

当该接口的形态本身尚未确定时（模块应该有多深、接缝应位于何处、接口应公开什么），请使用“codebase-design”调用 Skill 工具，以获取相关术语。它是模块、接口、深度、接缝、适配器、杠杆效应和局部性等术语的共享来源，应将其作为参考资料查阅，而不是作为一个会话来运行。

## 反模式

- **与实现耦合**：模拟内部协作者、测试私有方法，或通过旁路进行验证（例如查询数据库，而不是使用接口）。其明显特征是：行为没有改变，但重构时测试却失败了。
- **同义反复**：断言以与代码相同的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、以同样方式手工推导出的快照、断言某个常量等于其自身），因此它必然通过，永远不可能与代码产生分歧。预期值必须来自独立的事实来源：已知正确的字面值、推演完成的示例或规格说明。
- **水平切片**：先编写所有测试，再完成所有实现。批量测试验证的是_想象中的_行为：你测试的是事物的_形态_，而不是面向用户的行为；测试会对真实变化变得不敏感；而且你会在理解实现之前就确定测试结构。应改为使用**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是一枚**曳光弹**，根据上一轮循环带来的认知作出响应。

## 循环规则

- **先红灯，后绿灯。** 先编写失败的测试，然后只编写足以让它通过的代码。不要预判未来的测试，也不要添加推测性的功能。
- **每次只完成一个切片。** 每轮循环只处理一个接缝、一个测试和一个最小实现。
- **重构不属于这一循环。** 它属于审查阶段（参阅 `code-review` 技能），而不是红灯 → 绿灯的实现循环。
