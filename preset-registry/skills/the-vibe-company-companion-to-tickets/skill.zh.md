# 转换为工单

把一个计划、规格说明或对话拆解为一组**工单（tickets）**：曳光弹式的垂直切片，每张工单都声明**阻塞**它的那些工单。

问题追踪器和分流标签的词汇表应当已经提供给你。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。如果用户传入一个引用（规格说明路径、issue 编号或 URL）作为参数，请获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索过代码库，请先探索，以了解代码的当前状态。工单的标题和描述应使用项目领域词汇表中的术语，并遵守你所涉及区域内的 ADR。

寻找机会对代码进行预重构（prefactor），让实现更容易。“先让变更变容易，再做那个容易的变更。”

### 3. 起草垂直切片

把工作拆解为**曳光弹**式工单。

<vertical-slice-rules>

- 每个切片都切出一条狭窄但完整（COMPLETE）的、贯穿所有层（schema、API、UI、测试）的路径：是垂直切片，而非（NOT）只覆盖单一层的水平切片
- 一个完成的切片可以独立演示或验证
- 每个切片的规模应能装进一个全新的上下文窗口
- 任何预重构都应最先完成

</vertical-slice-rules>

为每张工单给出它的**阻塞边**：即必须先完成才能启动它的其他工单。没有阻塞者的工单可以立即开始。

**大范围重构是垂直切片的例外。**一次**大范围重构**是指单个机械性变更（重命名一个列、修改一个共享符号的类型），其**影响范围（blast radius）**波及整个代码库，以至于一次编辑就会同时破坏成千上万个调用点，没有任何垂直切片能以绿色（通过）状态落地。不要强行把它塞进曳光弹；而是按**扩张—收缩（expand–contract）**的顺序来编排。先扩张：把新形式加在旧形式旁边，保证不破坏任何东西。然后按影响范围分批（按包、按目录）迁移调用点，每一批是独立的一张工单，被“扩张”那张工单阻塞；由于旧形式仍然存在，CI 可以一批接一批地保持绿色。最后收缩：一旦没有任何调用方残留，就在一张被所有迁移批次阻塞的工单中删除旧形式。当连单个批次都无法独自保持绿色时，保留这个顺序，但让它们共享一个集成分支，这些工单共同阻塞一张最终的集 experience 成与验证工单；只有在那里才承诺绿色。

### 4. 与用户确认

把提议的拆分方案以编号列表的形式呈现。对每张工单，展示：

- **标题**：简短的描述性名称
- **阻塞于**：哪些其他工单（如果有的话）必须先完成
- **交付内容**：这张工单所打通的端到端行为

请询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确：每张工单是否只依赖真正构成门槛的工单？
- 是否有工单应当合并或进一步拆分？

反复迭代，直到用户认可这个拆分方案。

### 5. 将工单发布到已配置的追踪器

发布已获认可的工单。**如何**发布取决于 `/setup-matt-pocock-skills` 所配置的追踪器；无论哪种方式，工单本身都是相同的，只是阻塞边的形式有所变化：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写一个文件，按依赖顺序（阻塞者在前）从 `01` 开始编号。每个文件的“阻塞于”部分列出它所依赖的工单编号/标题。使用下面的单工单文件模板：一张工单一个文件，绝不合并为单个文件。
- **真实的 issue 追踪器（GitHub、Linear、……）** → 按依赖顺序（阻塞者在前）为每张工单发布一个 issue，使每张工单的阻塞边都能引用真实的标识符。平台若有原生的阻塞 / 子 issue 关系，就使用它；否则，把每张工单的“阻塞于”设置为对应的阻塞 issue。除非另有指示，应用 `ready-for-agent` 分流标签；这些工单天然适合由 agent 认领。

在**前沿（frontier）**上工作：即所有阻塞者都已完成的那类工单。对于纯线性链条，就是自上而下。

不要（NOT）关闭或修改任何父 issue。

无论采用哪种形式，都要避免具体的文件路径或代码片段：它们很快就会过时。例外：如果某个原型产出了一个比文字描述更精确地表达某项决策的片段（状态机、reducer、schema、类型形状），就把它内联进来，并简要注明它来自某个原型。裁剪到富含决策的部分，不是可运行的演示，只是关键内容。
