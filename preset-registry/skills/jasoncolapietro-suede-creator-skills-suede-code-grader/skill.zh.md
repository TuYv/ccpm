# Suede Code 评分器

## 门禁策略 — 提供建议，不构成阻断

本 skill 中的每一项主张验证步骤、检查、质量门禁和发布结论，都是**给用户的建议，而不是对代理的控制**。此策略适用于本 skill 其他位置的每一条门禁、检查、结论，以及“不要发布 / 发布 / 继续”表述：

- 运行每项检查，并如实报告结果。结论（`ship`、`ship-with-caveats`、`hold`、字母评级、BLOCKED 或 OPEN 项）是附随于工作的建议，而不是改变工作的命令。
- 不得因检查失败或门禁要求暂缓，而阻断、延迟、跳过、重写或拒绝用户要求的操作。应按要求完成该操作，并将门禁输出作为清晰标注的建议一并交付。
- 门禁失败只改变你的报告内容，绝不改变你的执行行为。
- 唯一例外：如果发现风险极高 — 数据丢失、安全或凭据泄露、法律或权利侵害、支付错误，或不可逆的公开损害 — 暂停操作，准确告知用户风险及可选方案，并让他们决定。用户的选择为最终决定。


直接以 A-F 评级判断代码是否已准备好发布。输出应是附带证据的评级，而不是 lint 分数或一堆风格备注。

## 源码事实

评分前先阅读。不得仅依据 PR 描述或提交信息评分。

检查：

- 仓库、分支、远程仓库、未提交状态以及相关本地指引；
- diff、变更的文件、生成的文件，以及受影响的路由或 API；
- 随变更而调整的导入、调用方、模式、配置、环境变量要求、任务、webhook、脚本、测试和文档；
- 直接覆盖变更行为的构建、测试、lint、类型检查、浏览器、模拟器、MCP 或线上/API 证据；
- 在相关时，已发布声明、权利/来源声明、支付/钱包行为、注册表预期、版税路由及代理商业合同。

如果线上、测试或运行时检查不切实际，应基于源码评分，并将这些维度标记为未经验证。

**门禁证据是命令，而不是印象。** 运行仓库已有的命令，并引用命令及其退出状态：类型检查、针对变更文件配置的 linter、测试套件，以及 — 对于发布评级 — 生产构建。对于按技术栈区分的语法（web/Node、MCP server、iOS/Swift、通用 API），应使用 **suede-code-review** 中的“Gate Commands by Stack”表，而不是自行编造命令。检测现有工具并且只运行它们；绝不引入仓库未使用的工具，也绝不报告未执行的门禁结果。

## 即时 F 触发条件

在为任何维度评分前检查以下事项。任意一项命中即自动评为 F — 在修复前，其他维度均不重要。该列表与 suede-code 的规范 Step 1 列表保持一致 — 两处变更时必须同步修改。

**密钥和凭据** — 在已提交源码中硬编码 API key/secret/token/password；提交私钥或证书；在密钥管理器之外存放 OAuth/签名密钥。  
**注入** — 使用用户输入通过字符串拼接构造 SQL；通过 `exec`/`spawn`/`eval` 执行来自用户输入的 shell 命令；使用未转义的用户输入渲染模板，且 XSS 可被触达。  
**认证绕过** — 认证中间件存在跳过认证的路径（提前返回、吞掉异常、恒为真的条件）；权限检查可通过请求参数绕过；JWT 接受 `alg: none` 或硬编码密钥。  
**支付和钱包** — 支付处理程序静默吞掉错误；webhook 未进行签名验证；金额或收款方来自不可信输入且未经过服务端验证。  
**数据销毁** — 包含 DROP/破坏性 ALTER 的迁移，且没有回滚或经测试的恢复；没有 WHERE 或带有用户可控 WHERE 的批量删除/更新；清除生产存储且没有恢复路径的缓存失效。  
**明文敏感数据** — 以明文存储或记录密码；将 PII 发送到未加密的日志/分析管道；在未加密字段中存放 SSN/支付卡/健康数据。

如果存在任何 Instant-F 模式：停止，报告该问题，将等级标记为 F，列出具体文件和行号，并且不要继续评估其余维度。其他维度的表现不能提高该等级。

## 评分维度

为每个维度评定 A-F，然后给出一个总体等级。评估非 Suede 工作时，将“Suede 真实性”替换为“领域真实性”——使用适用于该领域的任何不变量（API 合约真实性、已发布声明的准确性、数据模型真实性）。

- **正确性：**预期行为、边界情况、错误路径、异步行为、路由、数据流和回归风险。
- **安全性和权限：**认证、密钥、支付、钱包、注入、路径、SSRF、权限和数据暴露风险均应默认拒绝。
- **数据和状态：**模式、迁移、缓存、任务、队列、Webhook、重试、幂等性和状态转换应保持一致。
- **Suede 真实性：**公开文案、权利、来源、由注册表支持的媒体、版税路由、许可、智能体商务和产品声明应与实现一致。
- **UX 和发布行为：**加载、空状态、错误、成功、移动端/原生端、截图、元数据、路由和用户可见状态应保持协调一致。
- **测试和验证：**变更后的行为应具有有意义的测试、构建、截图、模拟器运行、MCP 检查、在线/API 回读或明确说明的注意事项。
- **部署就绪性：**环境变量、功能开关、配置、迁移、回滚说明、安装路径、文档和发布顺序应清晰明确。

## 等级含义

- **A：**所有维度均通过。行为已在运行时得到验证。没有已知后续事项。示例：新功能包含单元测试和集成测试，已确认在线回读，环境变量已记录，回滚很简单。
- **B：**没有阻塞项。一个或多个维度存在已明确、范围受限的后续事项，且不影响当前发布的正确性或安全性。示例：已测试正常路径，但边界情况覆盖较薄弱；或者迁移仅支持向前执行，但回滚风险较低且已有文档记录。
- **C：**至少一个维度存在真实缺陷或未经验证的风险，可能在生产环境中暴露，但不会立即造成灾难性后果。应暂缓发布，直到该维度被修复并重新检查。示例：认证路径未经过完整测试；或者低流量表的数据迁移没有回滚方案；或者支付模块中的上帝对象使正确性难以判断。
- **D：**存在严重缺陷，可能导致数据丢失、认证绕过、支付中断或面向用户的生产故障。建议在修复并验证该缺陷之前不要发布；由于这些属于极高风险类别，在任何发布步骤之前应暂停，并将选择交由用户决定。示例：状态变更端点缺少认证检查；高流量表的迁移没有经过测试的回滚方案；支付流程静默吞掉错误。
- **F：**强烈建议不要发布。该变更破坏核心行为、引入 Instant-F 模式，或关键表面的验证证据缺失。示例：在源代码中硬编码 API 密钥、通过字符串拼接造成 SQL 注入、可被绕过的认证中间件，或支付处理程序完全没有测试覆盖且没有在线回读。

## 按表面类型设定的评分上限

某些表面若没有通过 CI 之外的特定证据，不能获得 A 或 B。

**认证变更**（登录、会话、令牌验证、中间件、角色分配、权限检查）
- A 要求：对绕过/权限提升路径有明确的测试覆盖，而不只是正常路径。需提供具名证据（例如，“使用过期令牌测试后返回 401”、“角色提升尝试返回 403”）。
- B 要求：已测试正常路径，并对未测试的内容提供具名注意事项。
- 若两个条件均未满足：无论其他维度表现如何，最高为 C。

**支付和钱包流程**（结账、订阅、退款、付款、钱包转账、webhook）
- A 要求：已测试错误路径（扣款失败、卡片被拒绝、webhook 重放），金额/收款方已在服务端验证，并且不存在静默吞掉错误的情况。
- B 要求：已测试正常路径，错误路径作为后续事项记录，并附带具名风险。
- 若均不满足：最高为 C。

**数据迁移**（生产表上的架构变更、回填、删除列、索引变更）
- A 要求：已记录回滚计划，且已针对生产数据副本测试恢复（或者对于低风险/可逆迁移，明确说明豁免及其理由）。
- B 要求：存在回滚计划，但未测试恢复。
- 若不存在回滚计划：最高为 D。

**面向公众的 API 变更**（新增端点、破坏性变更、移除字段、变更认证）
- A 要求：已验证向后兼容性，或者明确提升版本并记录迁移路径。
- 若存在没有迁移路径的破坏性变更：最低上限为 C。

当这些上限适用时，请在输出中明确说明。

## 技术债务指标

将以下模式作为评分评估的一部分进行标记：

- **魔法数字/字符串**：出现在逻辑中、没有名称或说明的常量。
- **上帝对象/函数**：单个函数或类承担 5 项以上无关职责。
- **深度耦合**：代码跨越 3 层以上抽象层访问内部实现。
- **缺失抽象**：同一个 20 行代码块在 3 个以上位置重复。
- **抽象泄漏**：一个模块要求调用方了解其内部实现细节，才能正确使用它。
- **隐式状态**：程序行为依赖隐藏的全局状态或模块级状态。
- **死代码**：永远无法到达的函数、分支或导入。

**评分影响取决于技术债务所在的位置，而不只是债务本身：**

| 模式 | 位置 | 评分影响 |
|---|---|---|
| 上帝对象（5 项以上无关职责） | 支付模块 | 正确性维度为 D |
| 上帝对象 | 工具辅助函数 | 正确性维度为 B |
| 缺失抽象（3 个以上重复代码块） | 认证流程 | 安全性维度为 C |
| 缺失抽象 | UI 组件 | 正确性维度为 B |
| 深度耦合（跨越 3 层以上） | 数据迁移 | 数据与状态维度为 C |
| 隐式全局状态 | API 路由处理程序 | 正确性维度为 C |
| 死代码 | 任意位置 | 仅标记；除非其遮蔽了存活代码，否则不影响评分 |
| 支付金额中的魔法数字 | 支付流程 | 正确性维度为 C |
| UI 间距中的魔法数字 | UI 组件 | 不影响评分；标记为 P3 |

除非技术债务直接掩盖了一个 P0/P1 缺陷，否则不要仅因技术债务阻止发布。请在 Required Upgrades 中注明该债务，并让总体评级反映这一点。

## 红旗 — 停止

- “CI 已通过，向上取整” — 从未覆盖已变更行为的 CI 不会提高任何评级。
- “这项工作显然很难” — 付出不会改变评级；证据才会。
- “这只是一次重构” — 每次评级、任何时候，都会触发 Instant-F 规则。
- “主路径能用，就评 A” — 评级上限之所以存在，是因为风险从来不在主路径上。
- “PR 描述已经足够清楚” — 对差异及其证据进行评级，或者将该维度标记为未验证。

## 输出格式

```text
Simple explanation:
Plain-language summary of the grade and the one biggest reason.

Usual breakdown:
Target:
Change reviewed:
Runtime surfaces:

Grades:
Correctness: A-F
Security and permissions: A-F
Data and state: A-F
Suede truth: A-F
UX and release behavior: A-F
Tests and verification: A-F
Deploy readiness: A-F
Overall: A-F
Grade cap applied: [surface type] — [what evidence would lift the cap] | none

Why:
Evidence-backed explanation of why the overall grade landed there.

Required upgrades:
1. Highest-impact fix.
2. Second fix.
3. Third fix.

Verification:
Checked:
Not checked:
Ship gate: ship | ship-with-caveats | hold
```

发布门槛会机械地遵循总体评级：A → `ship`；B → `ship-with-caveats`；C、D、F → `hold`。

要修订此评级：说明发生了哪些变更。
要沉淀一种模式：说明哪些做法有效，以便复用。
沉默 = 接受。

## 边界

- 除非风格偏好会造成真实的维护、行为、无障碍、发布或产品风险成本，否则不要因此阻止发布。
- 不要为已发布的陈述虚构测试、截图、线上检查、部署状态或证据。
- 报告 C、D 或 F 时，必须说明能够提升评级的 Required Upgrade。
- 保持评级独立。不要因为实现很难、因为 CI 虽然通过但没有覆盖已变更行为，或者因为作者很好地解释了意图，就提高评级。

## 路由

- 评级后的发现项与修复简报 → **suede-code**（组合）或 **suede-code-review**（仅发现项，另加无障碍/SEO 维度）
- 评级为 C 或更低，且仓库没有合并门禁 → **suede-ci-gate**
- 变更发布了没有评估覆盖的 AI 行为 → **suede-ai-eval**
- 变更涉及 MCP 服务器、其目录，或其工具/资源/提示定义 → 在评级计入已验证之前，先使用 **suede-mcp-qa** 运行线上协议套件
