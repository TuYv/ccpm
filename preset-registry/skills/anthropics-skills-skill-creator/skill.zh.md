# 技能创建者

一个用于创建新技能并持续迭代改进它们的技能。

从高层来看，创建技能的过程大致如下：

- 决定你希望技能做什么以及大致如何实现  
- 编写技能草稿  
- 创建一些测试提示并运行 `claude-with-access-to-the-skill`  
- 帮助用户从定性和定量两方面评估结果  
  - 在运行在后台进行时，先起草一些定量评估（如果没有的话；如果已有，则可以照用，或者在你认为需要修改时进行调整）。然后向用户说明（如果这些评估已经存在，就解释已存在的那些）  
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果，并让他们查看定量指标  
- 根据用户对结果评估的反馈（以及定量基准测试中显现出的任何明显缺陷）重写技能  
- 重复直到你满意为止  
- 扩展测试集并在更大规模下再次尝试

你在使用这个技能时的任务，是判断用户当前处于流程中的哪个环节，然后介入并帮助他们推进这些阶段。比如，他们可能会说“我想做一个 X 的技能”。你可以帮助细化他们的意思，编写草稿、编写测试用例、弄清楚他们想如何评估、运行所有提示词，并反复迭代。

另一方面，他们可能已经有了技能草稿。在这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应该始终保持灵活；如果用户说“我不需要跑一堆评估，只想随便聊聊”，你也可以这样做。

在技能完成后（同样顺序也可以灵活调整），你还可以运行技能描述优化器——我们有一个单独的脚本用于此——用来优化技能触发。

懂了吗？懂。

## 与用户沟通

该技能可能会被不同程度熟悉编程术语的用户使用。如果你没听说过（而且你怎么会听说，毕竟这是最近才开始的），现在有一种趋势：Claude 的能力正在促使水管工打开终端，父母和祖父母去谷歌“如何安装 npm”。另一方面，绝大多数用户可能都相当懂计算机。

所以请留意上下文线索，以判断如何措辞你的沟通！在默认情况下，给你一点参考：

- “evaluation” 和 “benchmark” 属于边界词，但可以使用
- 对于 “JSON” 和 “assertion”，在你不先确认用户懂它们之前，不要直接使用

如果你不确定，简要解释这些术语是可以的；如果你不确定用户是否能理解，也可以用简短定义进行澄清。

## 创建技能

### Capture Intent

先理解用户的意图。当前对话中可能已经包含用户想要提炼的工作流（例如他们说“把这个变成一个技能”）。如果是这样，请先从对话历史中提取答案——已使用的工具、步骤顺序、用户做过的修正、观察到的输入/输出格式。用户可能需要补齐缺口，并在继续下一步前确认。

1. 这个技能应该让 Claude 做什么？
2. 在什么情况下触发这个技能？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 我们是否要设置测试用例来验证技能有效？对于输出可客观验证的技能（文件转换、数据提取、代码生成、固定流程步骤）而言，测试用例很有价值。对于输出主观的技能（写作风格、艺术创作）通常不需要。请按技能类型给出合适默认建议，但让用户决定。

### Interview and Research

主动提问边界情况、输入/输出格式、示例文件、成功标准和依赖项。在这部分理清之前，请先不要写测试提示。

检查可用的 MCP；如果有助于调研（搜索文档、寻找相似技能、查找最佳实践），优先使用子代理并行调研；否则就在当前上下文内完成。带着上下文来，可以减少用户负担。

### Write the SKILL.md

基于用户访谈，填充以下组件：

- **name**：技能标识符
- **description**：何时触发、做什么。这是主要触发机制——要同时包含技能功能和具体使用场景。不建议把“何时使用”信息放在正文里。注意：目前 Claude 有“触发不足”（undertrigger）倾向，即明明有用却没用上技能。为应对这一点，请把技能描述写得更“积极主动”一些。例如，不要写“如何构建一个简洁快速的仪表盘来展示内部 Anthropic 数据。”，可以改为“如何构建一个简洁快速的仪表盘来展示内部 Anthropic 数据。每当用户提到仪表盘、数据可视化、内部指标，或想展示任何公司数据时，请务必使用这个技能，即使他们没有明确说‘仪表盘’。”
- **compatibility**：所需工具、依赖项（可选，通常不需要）
- **the rest of the skill :)**

### 技能编写指南

#### Anatomy of a Skill

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### 分步披露

技能使用三级加载系统：
1. **Metadata**（name + description）——始终在上下文中（约 100 字）
2. **SKILL.md body**——在技能触发时加载（理想状态下 <500 行）
3. **Bundled resources**——按需加载（无限制，脚本可在未全部加载的情况下执行）

这些字数是近似值，如有需要可适当延长。

**关键模式：**
- 将 `SKILL.md` 保持在 500 行以内；如果接近该限制，添加额外的分层，并清晰给出模型在后续应去往何处继续
- 在 `SKILL.md` 中明确引用文件，并给出何时读取它们的指引
- 对于较大的参考文件（>300 行），包含目录

**领域组织**：当一个技能支持多个领域/框架时，按变体组织：

```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

Claude 只读取相关的参考文件。

#### 不出其意原则

无需赘述，但技能中不得包含恶意软件、利用代码或任何可能危害系统安全的内容。技能内容的意图不应与用户理解不一致。不要配合创建误导性技能或用于未授权访问、数据外泄或其他恶意行为的技能。像“扮演某个 XYZ”这类内容是可以的。

#### 编写模式

优先在指令中使用祈使语气。

**定义输出格式**——可以这样写：

```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——包含示例很有帮助。你可以这样排版（但如果示例中出现“Input”和“Output”，可以稍微偏离这种写法）：

```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### Writing Style

尽量用解释来说明某事为何重要，而不是一味使用强硬的 MUST。运用理论化视角（theory of mind），并尽量让技能保持通用，而不是过于局限于具体示例。先写一版草稿，再用新的视角审视并优化。

在继续处理你给的这段英文文档之前，我先确认一下：你希望我在这个项目里加载哪一组受管能力？

当前匹配到的项是：`skill-creator`（位于 `skill-creator` 插件组）。  
请确认是：

- 仅加载 `skill-creator` 插件组（推荐）
- 或者只使用当前已加载能力（不加载新组）  
- 或者先让我只列出可用组供你决定

空反馈意味着用户觉得没问题。将你的改进重点放在用户有明确抱怨的测试用例上。

完成后请结束查看器服务进程：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是迭代循环的核心。你已经跑过测试用例，用户已经审阅了结果，现在你需要根据反馈改进技能。

### 如何思考改进

1. **从反馈中抽象总结。** 这里发生的更大层面变化是，我们正在尝试打造可以被使用成千上万次（也许更多，没人知道）的技能，用于很多不同提示词。现在你和用户只是不断地在少量示例上反复迭代，因为这样更快。用户对这些示例非常熟悉，也能很快判断新输出是否合格。但如果你和用户共同迭代出的技能只适用于这些示例，那就没用。与其做一些繁琐、过拟合的改动，或施加压迫式的刚性“必须”，当遇到顽固问题时，你可以尝试扩展视角，使用不同的类比，或推荐不同的工作模式。尝试成本相对低，也许会得到更好的结果。

2. **保持提示词精简。** 删除那些没有起到作用的内容。一定要阅读对话记录，不只看最终输出——如果看起来技能在让模型浪费大量时间做低效事情，你可以尝试去掉让它这样做的技能部分，再观察结果如何。

3. **解释原因。** 尽量认真说明你要求模型做每件事背后的**原因**。当今的大模型很聪明，具备良好的思维推理能力；只要给它一个合适的框架，它能超越死记指令，真正把事情做好。即使用户反馈简短或语气激动，也要努力理解任务本身、用户为何这样写、以及他们到底写了什么，然后把这种理解转化为指令。如果你发现自己总在全大写里写 ALWAYS 或 NEVER，或采用过于僵硬的结构，这是个警报——如果可能，重构指令并解释其逻辑，让模型明白你为何提出这个要求。这种方式更人性、更有力量，也更有效。

4. **寻找跨测试用例的重复工作。** 阅读测试运行记录，留意子代理是否都独立写了类似的辅助脚本，或都采用了同样的多步方法去完成某件事。如果 3 个测试用例里都让子代理写了 `create_docx.py` 或 `build_chart.py`，这是技能应当打包该脚本的强信号。把它写一次放到 `scripts/`，并告诉技能去使用它。这样以后每次调用都不用再重复造轮子。

这个任务很重要（我们在这里尝试创造每年数十亿美元的经济价值！）而你的思考时间不是瓶颈；请花时间认真斟酌。我建议先写一个修订草案，再重新审视并继续改进。一定要尽力站在用户视角，理解他们真正想要和需要什么。

### 迭代循环

改进技能后：

1. 将你的改进应用到技能中
2. 将所有测试用例在新的 `iteration-<N+1>/` 目录下重新运行，包括基线运行。如果你在创建新技能，基线始终是 `without_skill`（无技能）——这在各次迭代中保持不变。如果你在改进现有技能，则自行判断用什么作为基线更合理：用户最初提供的原始版本，还是上一次迭代版本。
3. 用 `--previous-workspace` 指向上一轮迭代，启动评审
4. 等待用户审核并告知完成
5. 读取新反馈，再次改进并重复

持续进行，直到：
- 用户表示满意
- 反馈全部为空（看起来都很好）
- 你不再能做出有意义的改进

## 进阶：盲测比较

当你想更严谨地比较两个版本技能时（例如用户问“新版本到底更好吗？”），可以使用盲测比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 获取细节。基本思路是：给独立代理两个输出，但不告诉它们哪个是哪个，让它判断质量；然后分析为什么获胜者赢了。

这不是必需的，需要子代理配合，而且多数用户不需要。通常人类评审循环就足够了。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用技能的主要机制。创建或改进技能后，建议优化该描述，以提高触发准确率。

### 第 1 步：生成触发评估查询

创建 20 条评估查询——包含应触发和不应触发两类。以 JSON 保存：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须真实可用，且是 Claude Code 或 Claude.ai 用户可能实际输入的内容。不要写抽象请求，而要写具体详细、足够有上下文的请求。例如文件路径、用户工作或处境相关个人背景、列名和值、公司名、URL，带一点点前情提要。有些可以是小写、带缩写或拼写错误或口语表达。使用不同长度的句子，并侧重边界场景，而不是写得过于清晰的用例。

不好：`"Format this data"`, `"Extract text from PDF"`, `"Create a chart"`

好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**查询（8-10 条），考虑覆盖范围。你需要同一意图的不同表述——有正式的、有口语的。要包含用户没有明确提到技能或文件类型但明显需要它的情况。加入一些少见的使用场景，以及这个技能与其他技能竞争但应该获胜的情况。

对于**不应触发**查询（8-10 条），最有价值的是近似样例——和技能有关键词或概念重叠但实际上需要其他方式的情况。考虑相邻领域、歧义表述、一个朴素关键词匹配会误触发但实际上不应触发的情况，以及查询虽然涉及技能同样处理的内容，但在另一个上下文里更适合使用其他工具。

关键是要避免：不要把不应触发查询设计成明显无关。比如把“Write a fibonacci function”当作 PDF 技能的反例太容易——它并不能检验什么。负向用例应该真正“刁钻”。

### 第 2 步：让用户审核

用以下 HTML 模板向用户展示评估集：

1. 阅读 `assets/eval_review.html` 模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估条目的 JSON 数组（不要加引号——这是 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换是否应触发、增删条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——若有多个文件（例如 `eval_set (1).json`），请检查下载目录中的最新版本

这一步很关键——糟糕的评估查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期查看进度。”

将 `eval` 集保存到工作区后，在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用来自系统提示中的模型 ID（当前会话所使用的模型），以确保触发测试与用户实际体验一致。

在运行期间，定期 `tail` 输出内容，向用户更新当前迭代以及分数情况。

这会自动处理完整的优化循环。它将 `eval` 集拆分为 60% 训练集和 40% 留出测试集，评估当前描述（每个查询运行 3 次以获得可靠的触发率），然后调用 Claude 基于失败项提出改进建议。每次都会在训练集和测试集上重新评估新的描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，显示各轮的结果，并返回包含 `best_description` 的 JSON——该字段按测试集得分而非训练集得分选择，以避免过拟合。

### 技能触发机制

理解触发机制有助于设计更好的评估查询。技能会在 Claude 的 `available_skills` 列表中出现，包含其名称和描述，Claude 会根据该描述决定是否调用技能。关键在于，Claude 只会在无法轻松独立完成任务时才会调用技能——像“读取这个 PDF”这类简单单步查询，即使与描述完全匹配，也可能不会触发技能，因为 Claude 可以直接用基本工具处理。复杂、 多步或专业化查询在描述匹配时才会更稳定地触发技能。

这意味着你的评估查询应足够实质化，以至于 Claude 实际上会从调用技能中受益。像“read file X”这样的简单查询是很差的测试样本——无论描述质量如何，它们都不会触发技能。

### 第 4 步：应用结果

从 JSON 输出中提取 `best_description`，并更新该技能的 `SKILL.md` frontmatter。向用户展示前后差异，并报告得分。

### 打包与提交（仅当 `present_files` 工具可用时）

检查你是否可以使用 `present_files` 工具。如果没有，请跳过此步骤。如果可以，打包技能并将 `.skill` 文件提交给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，引导用户前往生成的 `.skill` 文件路径，以便其安装。

## Claude.ai 专用说明

在 Claude.ai 中，核心流程相同（草稿 → 测试 → 评审 → 改进 → 重复），但因 Claude.ai 不支持子代理，某些细节会变化。需要调整的地方如下：

**运行测试用例**：没有子代理意味着不能并行执行。对于每个测试用例，先读取该技能的 `SKILL.md`，然后按其说明独立完成测试提示。逐个执行。这个流程不如独立子代理严谨（你编写了技能，也在亲自运行它，因此上下文完整），但它是一次有效的自检——人工评审环节会弥补这点。跳过基线运行——只需按请求使用技能完成任务。

**评审结果**：如果你无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或你在远程服务器上），则完全跳过浏览器评审。改为直接在对话中展示结果。每个测试用例都显示提示和输出。如果输出是用户需要查看的文件（例如 `.docx` 或 `.xlsx`），请将其保存到文件系统，并告诉用户所在路径以便下载和检查。直接请求反馈：  
“How does this look? Anything you'd change?”

**基准测试**：跳过量化基准测试——它依赖于子代理之间的基线比较，在没有子代理的环境下并无实际意义。重点关注用户的定性反馈。

**迭代循环**：与此前相同——改进技能、重测用例、请求反馈——只是中间不包含浏览器评审。如果你有文件系统，仍可按轮次将结果组织到迭代目录中。

**描述优化**：本节需要 `claude` CLI 工具（特别是 `claude -p`），该工具仅在 Claude Code 可用。若在 Claude.ai 上，请跳过。

**盲测对比**：需要子代理。请跳过。

**更新已有技能**：用户可能要求更新已有技能，而非创建新技能。此时：
- **保留原始名称。** 记录技能目录名和 `name` frontmatter 字段——保持不变。例如，如果已安装的技能是 `research-helper`，请输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **编辑前先复制到可写位置。** 已安装技能路径可能是只读的。请先复制到 `/tmp/skill-name/`，在那里编辑并从副本打包。

## Cowork 专用说明

如果你在 Cowork，主要注意事项如下：

- 你拥有子代理，因此主流程（并行生成测试用例、运行基线、评分等）都可以正常运行。（不过，如果超时问题严重，也可以改为串行运行测试提示。）
- 你没有浏览器或显示器，所以在生成评估查看器时，使用 `--static <output_path>` 写出独立 HTML 文件，而不是启动服务。然后提供一个用户可点击的链接，方便他们在浏览器中打开 HTML。
- 出于某些原因，Cowork 环境似乎不太会在运行测试后自动生成评估查看器，所以再强调一遍：无论你在 Cowork 还是 Claude Code，测试完成后都应始终生成评估查看器，供人工查看示例，再开始自己修正技能时尝试调整。请使用 `generate_review.py`（不要自己手写定制 HTML）。提前说明一次：**务必在自己评估输入之前生成评估查看器**。你要让它们尽快展示给人工审核者！
- 反馈机制不同：由于没有运行中的服务，查看器的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。你随后可以从中读取内容（可能需要先申请访问权限）。
- 打包可用——`package_skill.py` 只需 Python 和文件系统。
- **描述优化（`run_loop.py` / `run_eval.py`）** 在 Cowork 应可正常运行，因为它通过 `claude -p` 调用子进程，而非依赖浏览器；但请等到你已完成技能优化且用户确认效果良好后再运行。
- **更新已有技能**：用户可能要求更新已有技能而非创建新技能。请遵循上文 Claude.ai 小节中的更新指导。
