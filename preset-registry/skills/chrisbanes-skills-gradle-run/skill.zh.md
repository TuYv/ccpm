# Gradle 运行

## 核心原则

将完整的 Gradle 输出视为临时产物，绝不能将其作为对话上下文。代理发起的每条 Gradle 命令都必须通过紧凑输出包装器运行；绝不要流式传输、使用 `tee`、粘贴或重新打开完整的构建日志。

## 流程

1. 对请求进行分类。仅用于验证另一项实现变更的针对性 Gradle 命令属于附带验证。构建、检查、警告清理或失败调查循环属于以 Gradle 为中心的工作流。
2. 确定此已安装 skill 的目录，并确认 `python3` 和 `<skill-dir>/scripts/gradle_run.py` 可用。如果其中任一项不可用，请在直接运行 Gradle 之前停止，并报告未满足的先决条件。
3. 在执行第一条命令之前创建一个包装器工作流：

   ```sh
   python3 <skill-dir>/scripts/gradle_run.py create
   ```

   将 `create`、每次 `run` 和 `finish` 都作为独立的 shell 命令运行；不要将生命周期操作与发现、状态或清理命令串联执行。保留返回的不透明工作流标识符。仅使用此包装器运行 Gradle。除非命令已选择控制台行为，或用户明确授权使用 `--scan`，否则它会添加 `--console=plain` 和 `--no-scan`。进行警告发现时，在 Gradle 命令中包含 `--warning-mode all`；其他情况下，仅在用户要求时才包含该参数。将 `workflow is busy` 结果视为所有权违规：等待当前运行完成或纠正所有者，而不是启动另一条命令或并发结束工作流。
4. 对于附带验证，留在当前代理中，并使用非空的验证问题运行范围最小的所属任务：

   ```sh
   python3 <skill-dir>/scripts/gradle_run.py run \
     --workflow <id> --scope targeted \
     --question "Does :module:test pass after this change?" -- \
     ./gradlew :module:test
   ```

   根据验证问题中的验收声明选择任务。如果问题询问固件测试是否通过，请运行 `test`；不要仅仅因为编辑的是 Kotlin 就改用编译任务。

   只读取有界 JSON 摘要，并根据其中失败的任务、指纹和摘录继续操作。除非用户明确请求该产物，否则不要检查其日志。在最终报告中，重复验证问题，并根据该有界摘要作答。分别说明托管的 `gradle_run.py run` 包装器是执行器，以及嵌套的 Gradle 任务；不要只展示嵌套的 Gradle 命令，也不要将其描述为直接调用 Gradle。
   摘要和账本会隐去常见的凭据模式；保留的完整日志特意保持原始状态，可能包含机密信息，因此绝不要粘贴或重新打开它来替代摘要。
5. 对于以 Gradle 为中心的工作流，创建一个全新的、可移植的 Solver 诊断所有者。仅当运行时公开其模型和推理时，才报告这些信息。授予其对仓库的只读访问权限，并让其负责包装器运行和诊断；它不得编辑源代码、测试、配置或生成的项目文件，也不得委派 Gradle 所有权。父代理负责对仓库的所有编辑。如果无法创建全新的持久所有者，请停止，而不要让父代理运行工作流循环。
6. 让该所有者复用之前可操作的摘要，按指纹对警告和失败进行分组，并返回准确的文件或行证据以及范围最小的下一条命令。相较于后续通用的 Gradle 失败块，优先采用源代码或编译器失败指纹。仅当现有的针对性证据无法回答记录的问题时，才运行初始的宽泛命令。该所有者在整个工作流期间保持可用，并使用同一包装器和适用范围最小的任务验证父代理所做的每项变更。
7. 仅对聚合项目检查记录 `broad`。为每次宽泛运行提供一个不同的问题，且该问题无法通过范围更小的任务回答。包装器会标记重复的命令和主要失败指纹；如果主要的源代码或编译器失败重复出现，请停止运行循环。在提出修复方案或另一条 Gradle 命令之前，检查报告的源代码行及其附近的声明、导入或接收者上下文；然后根据该证据修订诊断。在最终诊断中，将这项针对性检查列为下一步操作；在该检查实际发生之前，不要声称要修复源代码。如果包装器被中断，请使用其记录的信号和保留的日志；它会停止隔离的 Gradle 进程组或 Windows 进程树，从部分日志中提取有界诊断信息，并在返回前持久化账本。仅保留仍由有界近期运行账本表示的日志。
8. 在请求的宽泛验证通过后结束，或者报告尚未解决的警告指纹以及验证无法继续的原因。总结紧凑账本，包括每个验证问题及其有界答案，然后结束该工作流：

```sh
   python3 <skill-dir>/scripts/gradle_run.py finish --workflow <id>
   ```

   在最终报告中，说明工作流在该摘要之后已完成，并且清理操作仅删除了其包装器所拥有的日志。

   Finish 会保留少量标记和锁元数据，因此，对同一个已完成标识符重复执行操作具有幂等性，而未知标识符会以失败关闭。如果 finish 无法验证受管理的标识符，或者工作流仍处于活动状态，则保留所有文件并报告失败。此 Skill 不限制无关的审查、探索、实现或其他子代理。

## RED/GREEN 代理场景

1. 直接：“运行 `check` 并修复每一条警告。”RED 重复运行完整构建，并将其日志保留在上下文中。GREEN 创建一个诊断负责人，记录宽泛问题，对精简诊断进行分组，逐项针对性地验证每个修复，并且仅在最终验证时运行所请求的宽泛检查。
2. 新问题：在针对性任务通过后，最终的宽泛检查发现了下游故障。GREEN 记录新问题，定位到负责该问题的任务，并且仅在该任务通过后才再次运行一次宽泛检查。
3. 重复：在声称已修复后，未发生变化的源代码故障指纹仍然存在。GREEN 停止重新构建，检查所引用的源代码行及其周围的声明或导入上下文，然后在指出修复方案或另一条 Gradle 命令之前报告修订后的诊断。它不会将新的问题字符串视为允许盲目重复执行的依据。
4. 失败关闭：包装器、Python 运行时或持久化诊断负责人不可用。GREEN 不直接运行任何 Gradle 后备方案，而是报告缺失的先决条件。外观有效但未知的 finish 标识符同样会失败；不会将其视为先前已完成的工作流。
5. 反例：“更改此 Kotlin 辅助函数后，运行 `:module:test`。”GREEN 使用包装器，但仍由当前代理执行这项附带的针对性验证，将每个生命周期操作作为独立命令运行，并报告受管理的包装器、验证问题和有界答案；它不会用编译替代指定的测试任务。
6. 边界：当 Gradle 工作流正在运行时，用户启动了一个无关的审查子代理。GREEN 允许这样做；此 Skill 仅负责 Gradle 输出处理和诊断委派。
7. 中断：Gradle 发出诊断并进入一个抵抗信号的工作进程后，Ctrl-C 连续触发两次。GREEN 容忍第二次信号，停止隔离的进程组，提取部分诊断，保留日志，并在返回前将 SIGINT 记录到精简账本中。RED 会重新进入清理流程、使任一进程继续运行，或者丢失诊断或中断记录。
8. 独占所有权：第二个运行或 finish 请求使用了活动工作流。GREEN 在启动或删除任何内容之前以失败关闭。RED 会覆盖序列日志、丢失账本更新或删除活动工作流。
9. 敏感输出：Gradle 属性和警告中包含凭据。GREEN 对有界摘要、问题、命令和账本进行脱敏，同时将原始完整日志作为本地敏感制品保留。RED 会在模型可见的元数据中发送或持久化凭据。
10. 保留与可移植性：旧运行留下了有界账本，而 Windows 包装器仍有后代进程。GREEN 仅清理被逐出的运行所对应的日志，并在中断时使用平台的进程树边界。RED 会泄漏无限增长的日志，或仅终止 Windows 启动器。
