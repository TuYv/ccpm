# Gradle 运行

## 核心原则

将完整的 Gradle 输出视为临时产物，绝不能将其作为对话上下文。每个由代理发起的 Gradle 命令都必须通过紧凑输出包装器运行；绝不能流式传输、使用 `tee`、粘贴或重新打开完整的构建日志。

## 流程

1. 对请求进行分类。仅用于验证另一项实现变更的聚焦 Gradle 命令属于附带验证。构建、检查、警告清理或失败调查循环属于以 Gradle 为中心的工作流。
2. 确定此已安装 Skill 的目录，并确认 `python3` 和 `<skill-dir>/scripts/gradle_run.py` 均可用。如果任一项不可用，请在直接运行 Gradle 之前停止，并报告未满足的前置条件。
3. 在执行第一个命令前创建一个包装器工作流：

   ```sh
   python3 <skill-dir>/scripts/gradle_run.py create
   ```

   保留返回的不透明工作流标识符。仅使用此包装器运行 Gradle。除非命令已经指定控制台行为，或用户明确授权使用 `--scan`，否则它会添加 `--console=plain` 和 `--no-scan`。在发现警告时，在 Gradle 命令中包含 `--warning-mode all`；其他情况下，只有用户要求时才包含该选项。将 `workflow is busy` 结果视为所有权违规：等待活动运行结束或纠正所有者，而不是启动另一个命令或并发结束工作流。
4. 对于附带验证，留在当前代理中，并使用非空的验证问题运行最小的归属任务：

   ```sh
   python3 <skill-dir>/scripts/gradle_run.py run \
     --workflow <id> --scope targeted \
     --question "Does :module:test pass after this change?" -- \
     ./gradlew :module:test
   ```

   根据验证问题中的验收声明选择任务。如果问题询问固件测试是否通过，则运行 `test`；不要仅仅因为编辑的是 Kotlin 就改用编译任务。

   只读取有界 JSON 摘要，并根据其中失败的任务、指纹和摘录继续操作。除非用户明确请求该产物，否则不要检查其日志。在最终报告中，重复验证问题，并根据该有界摘要作答，同时明确说明包装器运行了该任务；不要将其描述为直接调用 Gradle。摘要和账本会遮盖常见凭据模式；保留的完整日志特意保持原始状态，可能包含机密信息，因此绝不能粘贴或重新打开它来代替摘要。
5. 对于以 Gradle 为中心的工作流，创建一个全新的、可移植的 Solver 诊断所有者。仅当运行时公开其模型和推理时，才报告这些信息。授予它对仓库的只读访问权限，以及包装器运行和诊断的所有权；它不得编辑源代码、测试、配置或生成的项目文件，也不得委派 Gradle 所有权。父级负责仓库中的所有编辑。如果无法创建全新的持久所有者，则停止操作，而不是让父级运行工作流循环。
6. 让该所有者复用之前可执行的摘要，按指纹对警告和失败进行分组，并返回准确的文件或行证据以及范围最窄的下一个命令。相比后续的通用 Gradle 失败块，应优先采用源代码或编译器失败指纹。仅当现有的针对性证据无法回答已记录的问题时，才运行初始的宽泛命令。该所有者在整个工作流期间都保持可用，并使用同一个包装器和适用范围最窄的任务验证父级所做的每项变更。
7. 仅将聚合项目检查记录为 `broad`。为每次宽泛运行提供一个更窄任务无法回答的独立问题。包装器会标记重复命令和主要失败指纹；如果主要的源代码或编译器失败重复出现，则停止运行循环。在提出修复方案或另一个 Gradle 命令之前，检查报告的源代码行及其附近的声明、导入或接收者上下文；然后根据该证据修正诊断。在最终诊断中，将该聚焦检查列为下一步操作；在实际检查发生前，不要说要修复源代码。如果包装器被中断，请使用其记录的信号和保留的日志；它会停止隔离的 Gradle 进程组或 Windows 进程树，从部分日志中提取有界诊断信息，并在返回前确保持久保存账本。仅保留仍由有界的近期运行账本表示的日志。
8. 在请求的宽泛验证通过后结束；或者报告尚未解决的警告指纹，以及验证无法继续的原因。总结紧凑账本，包括每个验证问题及其有界答案，然后结束该工作流：

```sh
   python3 <skill-dir>/scripts/gradle_run.py finish --workflow <id>
   ```

   在最终报告中，说明工作流在该摘要之后已完成，并且清理操作仅删除了其包装器拥有的日志。

   完成操作会保留少量标记和锁元数据，因此对同一个已完成标识符重复执行操作是幂等的，而未知标识符会以失败关闭方式处理。如果完成操作无法验证受管理的标识符，或者工作流仍处于活动状态，则保留所有文件并报告失败。此 Skill 不限制无关的审查、探索、实现或其他子代理。

## RED/GREEN 代理场景

1. 直接场景：“运行 `check` 并修复所有警告。”RED 在上下文中保留日志，反复运行完整构建。GREEN 创建一个诊断所有者，记录宽泛问题，对精简诊断进行分组，针对每项修复执行小范围验证，并且仅将请求的宽泛检查作为最终验证来运行。
2. 新问题场景：在针对性任务通过后，最终的宽泛检查发现了一个下游故障。GREEN 记录新问题，定位到负责该问题的任务，并且仅在该任务通过后才重新运行一次宽泛检查。
3. 重复场景：在声称已修复后，一个未变化的源代码故障指纹仍然存在。GREEN 停止重新构建，检查所引用的源代码行及其周围的声明或导入上下文，然后在给出修复方案或另一个 Gradle 命令之前，报告修订后的诊断。它不会将新的问题字符串视为允许盲目重复执行的依据。
4. 失败关闭场景：包装器、Python 运行时或持久化诊断所有者不可用。GREEN 不会直接使用 Gradle 作为后备方案，而是报告缺少的前置条件。一个看似有效但实际未知的完成标识符也会失败；它不会被视为先前已完成的工作流。
5. 反例：“更改这个 Kotlin 辅助程序后，运行 `:module:test`。”GREEN 使用包装器，但会将这个附带的针对性验证保留给当前代理执行，并报告验证问题及其有界答案；它不会用编译替代明确指定的测试任务。
6. 边界场景：当 Gradle 工作流运行时，用户启动了一个无关的审查子代理。GREEN 允许这样做；此 Skill 仅负责 Gradle 输出处理和诊断委派。
7. 中断场景：Gradle 发出诊断信息并进入一个抵抗信号的工作进程后，用户按了两次 Ctrl-C。GREEN 能够容忍第二个信号，停止隔离的进程组，提取部分诊断信息，保留日志，并在返回前将 SIGINT 记录到精简账本中。RED 会重新进入清理流程、留下任一进程继续运行，或者丢失诊断信息或中断记录。
8. 独占所有权场景：第二个运行或完成请求使用了一个活动工作流。GREEN 在启动或删除任何内容之前以失败关闭方式处理。RED 会覆盖序列日志、丢失账本更新，或删除活动工作流。
9. 敏感输出场景：Gradle 属性和警告中包含凭据。GREEN 会对有界摘要、问题、命令和账本中的敏感信息进行脱敏，同时将原始完整日志作为本地敏感制品保留。RED 会在模型可见的元数据中发送或持久化该凭据。
10. 保留与可移植性场景：某次旧运行保留了有界账本，而 Windows 包装器仍有后代进程。GREEN 仅清理由淘汰运行产生的日志，并在中断时使用平台进程树边界。RED 会导致日志无限累积，或仅终止 Windows 启动器。
