# 文档清理器

文档会以两种不同的方式出现问题，而它们需要不同的处理方式。

**它会腐化。** 某些内容发生了变化——端口、路径、流程、决策——但文档仍在描述旧有情况。这个领域将其称为*文档腐化*或*版本漂移*：文档资料逐一失去同步，直到人们不再信任整套文档。

**它会膨胀。** 同一个主题积累了三个文件，每个文件都只对了一部分，却没有一个是权威来源。

这两种问题都源于同一个根本原因：**一项事实被记录在了比其定义位置更多的地方。** 以下所有内容都围绕如何解决这一问题展开。

## 核心原则（适用于两种模式）

**删除前先进行批判性评估。绝不要盲目删除。** 在提议移除任何章节之前，先分析它的独特价值。目标是在不丢失信息的前提下精简内容。

这一原则适用于此技能中所有具有删除性质的操作，而不仅仅是整合：归档文档、去除派生值以及删除交叉引用都属于删除，执行之前都必须进行同样的分析。“它看起来很多余”不算分析。

## 你当前处于哪种模式？

| 用户的说法 / 当前情况 | 模式 |
|---|---|
| “我修改了 X” / 存在差异 / 某个流程已更新 | **1 — 变更后治理** |
| “哪些文档现在有误”“检查过时的命令/路径” | **1 — 变更后治理** |
| “清理文档”“关于这个主题的文件太多了”“合并这些文件” | **2 — 整合** |
| 一个主题分散在多个文件中，且没有明确的归属文件 | **2 — 整合** |

两种模式共用下文的漂移测试。当两种模式都适用时，先执行模式 1：整合那些事实本身*也已过时*的文档，只会生成一份言之凿凿却内容错误的文档。

**关于 `CLAUDE.md` / `AGENTS.md` 的说明：** 两种模式都像适用于其他文档一样适用于它们——发生变更后对其进行治理，在它们相互重复时进行整合。唯一应由其他工具处理的任务是*重构单个过大的文件*——将低频细节下沉到参考资料中，同时保持顶层内容精简。这正是 daymade-claude-code 的 `claude-md-progressive-disclosurer` 技能所擅长的；当问题在于篇幅和分层，而非真实性或重复时，应优先使用它。如果该技能不可用，模式 2 仍然可以处理此文件——只是需要手动进行价值分析。

## 漂移测试（两种模式的核心）

在将任何值写入文档之前——以及在判断现有值是否值得保留时——请**按顺序询问以下三个问题，并在第一个命中项处停止**：

**1. 这个值能否根据此处或权威来源中已经记录的详细信息计算得出？**
→ 它是一个**派生值**。不要写入它。有人询问时再进行计算。
示例：数量（“6 个章节”“覆盖 N 个组”）、总数、对下方表格各行进行汇总的状态，以及当下方日志已经注明日期时再写“最后更新于”。

移除派生值时，应修正整个句子，而不是留下空缺：“下面四项检查”应改为“下面的检查”。只删除数字却留下不完整的语法，是另一种缺陷，而不是修复。

*例外——生成的导航。* 按此测试，复述各级标题的目录属于派生值，手工维护的目录确实应该删除。但如果它是在构建时由文档工具链生成的，或者平台要求使用该标记来渲染导航，则不要动它：这些内容是按需计算的，而这正是问题 1 所询问的情况。删除目录之前，先检查是否存在生成器。

**2. 无法计算，但同一事实已在其他地方权威定义？**
→ 它是一个**副本**。链接到该定义。不要复述该值。

**3. 两者都不是——它记录的是某个特定时刻的真实情况？**
→ 现在可以把它写下来。价格历史记录行、决策日志条目、“截至 2026-03，供应商要求 X”——这些都属于合理情况，删除它们会破坏审计轨迹。

问题 3 需要谨慎处理，因为*每一个*过时值都曾在某个时刻为真——正因如此，它后来才会过时。但请注意问题 3 决定什么，以及不决定什么。

**它只决定一件事：这段内容不存在漂移问题。** 它不是派生值，也不是副本，因此所有漂移补救措施都不适用于它——不要重新计算它，不要用链接取代它，也不要把它“更新”为当前值。这段内容是否值得保留，是一个*内容价值*问题，应在模式 2 的价值分析中与文档所有者共同作出判断，而不是在这里判断。

**本节此前有三个草稿版本试图在这里直接决定保留还是删除，但每个版本都未能通过评审。** 有必要说明原因，以免有人重新构建这种逻辑：每个版本都要求代理知道一些它无法得知的信息——内容是否可以重新生成、重新生成的成本是多少、由谁来生成，或者某人认为存在的另一个副本是否真的存在。基于无法验证的判断授权删除，正是本技能旨在消除的自我证明式模式，而且这将成为该文件中唯一一次没有证据支持的删除。

因此，该测试只负责分类：

> **这段内容描述的是事物当前的状态吗？** 如果是，那么其中带日期的旧值只是披着日期外衣的问题 1 或问题 2 情形，日期并不能挽救它。
>
> **还是说，它记录的是某个时刻的真实情况**——一条变更日志、一条决策日志记录、一行价格历史记录、一条事件时间线、一项带日期的测量结果、一份事后分析？如果是，那么它属于问题 3。不要改动该值。

**把此测试应用于段落，而不是文件**——这里的*段落*是指会被作为一个整体阅读的单元：**条目、表格行、带日期的备注**、某个标题下的章节。操作指南中可能包含一个真正的历史记录块，而变更日志顶部也可能带有当前状态摘要；文件级判断会把这两者都判错。但也不要在*低于*段落的层级上运行此测试——事后分析中的时间线及其根本原因章节共同构成一份记录，如果将它们拆开，以“可从日志中重现”为由删除时间线，就会破坏由这些部分共同组成的整体。

**对于这些段落，问题 3 的优先级高于问题 1 和问题 2，尽管它排在后面。** 变更日志中的一行“2026-01-04：将上传限制提高到 50 MB”*确实*会命中问题 2——上传限制在配置中有权威定义——如果到此为止，就会用链接取代它，从而破坏这条记录。问题 1 会通过另一条路径造成相同的破坏：“2026-01-04：新增 eu-west-3，使区域总数达到 12 个”包含一个计数，而计数正是问题 1 自己给出的示例——但重新计算得到的是*今天的*区域数量，这会改写当天所记录的事实。命中首项即停止的规则是为了提高效率，而不是为了把历史记录导向链接或重新计算。

当你无法判断某段内容是在记录历史还是描述当前状态时，**请询问——不要通过删除来解决。** 原因在于两种错误的后果并不对称：如果你误把记录当作当前状态的重复表述并将其删除，就会毁掉仅存的一份副本；而如果你误把重复表述当作记录并予以保留，代价不过是多占几行。如果你在无人值守模式下运行，无法询问，就不要改动该段内容，并在报告中说明。

**链接只能解决情形 2。** 将链接指向派生值属于范畴错误：并不存在一个可供指向的唯一权威单元格，因此链接会变成一种自身也会过时的脚手架，*同时*还会造成两个位置彼此一致的错误印象。

**为什么这一顺序很重要：** 对于 API 文档中的漂移问题，成熟的解决方案是“从源生成，不要手动复制”（OpenAPI/Swagger 的存在正是为了解决这个问题）。问题 1 是将同样的思路应用于正文——确保数字正确的最可靠方法，就是不要把它写两遍。

### 位置不能成为例外

无论位于何处，事实就是事实。出于上述检验的目的，以下所有内容都属于正文，而且陈旧值恰恰会在这些地方逃过审查而存留下来：

frontmatter · YAML/JSON 元数据 · 括号内的补充说明 · 索引表中的描述列 · 复选框状态 · 正文内容之前的引入性说明 · 跨文档脚注 · 表格中新增的列 · 正文中遗留的提交消息式注释

### 什么算作事实

任何会随时间变化且在某处有权威定义的内容：数字、状态、所有权、关系、分类、规则、决策来源、日期、计数。业务规则也算——“所有报价都经由财务负责人处理”只在一个地方定义，并由其他地方引用，绝不能在每份下游文档中重复表述。

## 模式 1——变更后治理

按顺序执行以下步骤。顺序本身就是关键：在确定什么是权威内容之前就修复派生文档，只会使工作成倍增加。

**1. 根据变更界定范围，而不是根据仓库界定范围。**
列举这次变更所修改的*事实*——这个端口、这条路径、这个过程名称、这个默认值。这份列表决定了工作的边界。**列表是有边界的；但对列表中每一项的搜索没有边界**——某项事实不易察觉的副本，恰恰存在于此次变更从未触及的文件中，因此在步骤 5 中，需要在整个仓库范围内搜索每项事实。禁止的是另一件事：打开文件去查找*无关的*问题。无边界的全面排查会让一项文档任务变成无法审查的重构。

**2. 确定每项受影响事实的权威来源（SSOT）。**
哪个文件*定义*了这个端口／路径／过程，而不只是提到了它？首先更新该文件。所有下游内容要么指向它，要么由它派生。

判断“定义”的实用标准是：**要让现实发生变化，必须在哪里进行更改**——部署实际读取的文件、代码加载的 schema、人员逐步遵循的 runbook。一个文件在解释其他内容时复述该值，只是在提及它。当两个文件看起来都具有声明性质时，按以下优先顺序选择：机器会使用的文件优先于仅供人阅读的文件；最接近其所描述对象的文件；已被其他文档引用的文件。然后在报告中说明你选择了哪个文件，以及依据了上述哪项理由——一旦步骤 2 让其他所有内容都指向它，随意的选择就会成为永久决定，因此这应该是一项明确说明的决策，而不是由你最先打开哪个文件这一偶然因素决定。

**3. 以实现为准——将其视为证据，而不是修改实现的邀请。**
当代码、脚本、配置文件或实际运行结果与文档冲突时，实现是证据，文档是主张。记录实际情况；
绝不要编写描述你希望代码如何运行的文档。

**如果实现本身有误，请停下来并报告——不要在此 Skill 下修复代码。**
仅通过阅读两者之间的分歧，你无法判断是“文档已过时”还是“代码存在缺陷”；
这种判断需要了解变更背后的意图，而这应由用户决定。文档更新过程若悄然变成代码修改，
就会成为第 1 步所禁止的同一种范围失控问题，而且后果更严重。

**4. 在编辑每份受影响的文档之前，先决定如何处置它。**

| 文档情况…… | 操作 |
|---|---|
| 仍可用于指导操作；只有部分具体事实发生了偏移 | **更新** |
| 建立在一个已不再成立的前提之上 | **归档 / 停用** |

不要修补前提已不成立的文档——这样得到的内容会在内部自洽，却在整体上错误，
比明显过时的文件更难发现。
在原处留下“本节已被取代”的说明并不是第三种选择。维护者的整理说明不应出现在读者的阅读路径中；
读者缺少使其有意义的上下文，只会因此感到困惑。将它移出阅读路径。

**“归档”意味着：移出读者的阅读路径，但仍保留在历史记录中。** 具体来说：查找项目已有的
约定（`_archive/`、`archive/`、`deprecated/` 或项目采用的其他目录）并遵循它；
如果没有此类约定，则在与该文件同一级的位置创建 `_archive/`。无论哪种情况，都应使用 `git mv`
移动文件，以便历史记录随之保留，然后重新指向或移除所有入站引用。**不要**直接删除文件，
也不要只在 frontmatter 中添加 `status: deprecated`，却仍将文件留在读者能够找到的位置——
一份仍位于读者阅读路径中的已停用文档，仍然会被阅读。

归档任何并非由你创建的内容之前都应先询问，原因与阶段 4 的第 3 步需要达成一致相同。
**如果正在无人值守模式下运行且无法询问：不要改动该文档，并报告它需要停用。**
不要转而修补它——当前提已不成立时，更新文档中的事实只会让它更具误导性，而非减少误导。

**5. 在修改任何事实之前，先找出该事实的每一处副本。**
这一步最容易被跳过，而典型的失败恰恰发生在这里：最显眼的一处被更新了，
另外三处不显眼的副本却没有更新。确切命令见下文的*验证*部分。

风险最高的情况是**对序列中的项目重新编号或插入新项目**，因为你修改的并非单个事实，
而是一整组相互引用的事实：正文中写着“参见第 7 步”、同级文件中的交叉引用，以及——最棘手的是——
将数量写进句子里的正文（“下面的四项检查”）。最后一种情况不包含你正在搜索的任何编号，
因此按步骤编号搜索永远无法发现它。

**对此不存在机械化的全面排查方法，也不应假装存在。** 两种看似合理的范围界定方法都经过了衡量，
结果均告失败：

- *在整个仓库范围内搜索数量词* → 在一个真实的文档仓库中需要扫描 224,330 行 / 约 550 MB
  （若限定到单个项目目录则为 17.7 MB）。没人会运行这样的搜索，而一条必然会被绕过的指令
  比没有指令更糟糕。
- *仅在提到该主题的文件中搜索数量词* → 范围有限，但**恰恰在关键方向上是错误的**。
  将数量写死在句子里的正文，往往正是通过别名、翻译、代词或裸链接来指代该主题的正文——
  “下面的四项检查”、 「预检有四个检查」——而从不使用它的标题。实测结果：一个确实包含
  过期数量的文件，在搜索该主题名称或文件名时匹配数为*零*。该过滤条件与目标负相关。

因此，请改为执行以下操作，并报告它未覆盖的范围：

1. **完整阅读你重新编号的文件。** 大多数过期的自引用都存在于该文件中。
2. **先构建文件列表，再在其中搜索数量词。** 模式 1 中此前的步骤并未生成这个列表——不要使用
   *更新引用*中的入站引用搜索，那属于模式 2，回答的是另一个问题（“什么内容指向了这个
   **文件**”，而不是“什么内容讨论了这个**主题**”）。请在此处生成列表：

   ```bash
   ROOT=$(git rev-parse --show-toplevel 2>/dev/null) || { echo "not in a git repo — pass the docs root explicitly" >&2; exit 1; }
   rg -l -F "<the subject's name>" "$ROOT" --no-ignore --hidden -g '!.git'
   ```

   这会找出直接写明该主题名称的文件；第 3 步会覆盖那些未直接写明名称的文件。
   由于文件数量很少，请直接列出文件名，而不要将列表通过管道传给 `xargs`（空列表会导致
   GNU `xargs` 在完全没有路径参数的情况下运行搜索，从而转而搜索当前目录——这会产生看似
   有效的输出，但搜索范围是错误的）：

   ```bash
   rg -n -i -H \
     -e '\b(one|two|three|four|five|six|seven|eight|nine|ten|both) [a-z]+\b' \
     -e '[一二三四五六七八九十两](个|条|步|项|点)' -e '[0-9]+(个|条|步|项|点)' \
     -e '\b[0-9]+ [a-z]+\b' \
     path/to/one.md path/to/two.md
   ```
   有两个细节都经过了实测：使用 `-H`，是因为当只向 `rg` 提供一个文件时，它会省略文件名，
   而这里需要的完整答案恰恰是“哪个文件”。此外，该模式刻意匹配*任意*后续单词，而不是使用
   名词列表——列表不一定包含你的项目所使用的名词（“four **gates**”“three **lanes**”），
   而且漏检不会有任何提示。只搜索少量文件时，多出一些噪声的成本很低；漏掉目标行则不然。
3. **自行列出该主题的别名并搜索这些别名**，然后在搜索到的文件中查找数量词。这一步没有任何
   工具能够替你完成。

然后说明你检查了什么：*“已阅读重新编号的文件；已在按名称引用它的 N 个文件中搜索数量词；
未通过机械方式覆盖使用其他名称指代它的正文。”* 这句话比一个悄无声息地代表上述两种失败
之一的绿色勾选标记更有价值。

**6. 清理过程中遇到的派生值——但仅限于你已经在编辑的文件。**
删除已打开文件中的过期数量属于日常清理，而不是范围蔓延。为了寻找更多问题而打开无关文件
才是范围蔓延。正是这条边界让变更保持在可审查范围内。

**7. 按照*报告内容*下的结构报告你所做的工作**。

## 模式 2 — 整合

整合冗余文档，同时保留所有有价值的内容。上述*核心原则*适用于此模式下的每一次删除。

### 阶段 1：发现

1. **识别涵盖该主题的所有文档文件**，并在搜索前说明搜索边界
   （一个目录、一个套件或一个项目）——与模式 1 第 1 步采用相同的
   有界范围规则。如果只给两个代理“文档”而不指定边界，它们会整合不同的文件集。
   通常的方法是在该边界内执行主题关键词扫描——注意使用 `-F`，因为像 `C++`、`.NET`
   或 `v1.0.0` 这样的主题词是字面量，如果将其作为模式，它们几乎会匹配所有内容：
   `rg -l -i -F -e '<topic term>' -e '<synonym>' <boundary> --no-ignore --hidden -g '!.git'`
   此列表界定了整个整合工作的范围，因此垃圾列表必然导致垃圾分析。
2. **统计所有文件的总行数**——对第 1 步得到的列表运行 `wc -l`
3. **绘制内容重叠关系图**：对于每个文件中的每个标题，记录还有哪些其他文件涵盖
   相同内容。产出物是一张“标题 → 同样涵盖该内容的文件”的表；出现在多个文件中的
   章节是整合候选项。此步骤**仅**判断内容是否重叠——不决定保留还是删除。某个独有章节
   在阶段 2 中仍可能因与重复无关的原因而被删除（不言自明、已被取代、属于副产物），
   因此应将其理解为*“这里没有任何依据允许将独有章节作为冗余内容删除”*，而不是
   *“独有就意味着会被保留”*。

### 阶段 2：价值分析

针对每份文档，逐章节建立表格：

| 章节 | 行数 | 处理方式 | 原因 |
|---------|-------|-------|--------|
| API 参考 | 25 | 保留 | 独有的端点文档 |
| 设置步骤 | 40 | 精简 | 冗长但不可或缺 |
| 环境变量表 | 30 | 删除 | 与权威文件 `README.md` 中的表格重复 |

请注意，删除示例中*并非*以下内容：带日期的测试运行记录、会议记录或事件时间线。
这些内容看起来是任何文档中最容易删除的部分，但它们恰恰是本技能不允许你悄无声息地
删除的一类内容——请参阅下方三段之后的规则。上述示例之所以属于“删除”，是因为某个
明确指定的文件包含相同内容，而这是唯一一种可以通过指向某项内容来证明合理性的删除。

- **保留**——独有、必要、经常被引用
- **精简**——有价值但冗长
- **删除**——重复、一次性、不言自明、已过时
- **归档**——整份文档的*前提*已经失效（已取消系统的设计说明、已退役服务的事后分析）。
  它既不是需要修正的过时现状，也不是应当删除的重复内容。如果没有此类别，“已被取代”
  和“它是一份记录”会将同一份文档推向相反的方向，而最终结果将取决于你最后读到哪一条。

  现行文档中前提已经失效的**章节**，是在更细一级上出现的相同问题，而“归档”不接受这种
  情况——它仅适用于整份文档。应将其视为因前提失效而需要删除的内容，并在阶段 3 的计划中
  明确列出，而不是自行决定：“因迁移已取消而失效的 Kafka 迁移章节”恰恰属于所有者可能会
  回答“其实我们仍会参考它”的那类决策。

**“归档”裁定会将该文档移出此次整合范围。** 它不会继续进入
  阶段 3 或阶段 4——没有内容需要合并，也没有内容需要精简。请按照
  模式 1 的归档流程处理——即 **模式 1 — 变更后治理** 下以
  `"Archive" means: out of the reader's path, still in history` 开头的段落——在报告中说明
  你已这样处理，然后继续
  整合其余内容。也不要将它纳入阶段 3 的行数计划：它将原封不动地离开，
  因此把它的行数计作“缩减”会声称取得了你实际上并未实现的节省。

在处理过程中，对每一行执行漂移测试，并允许它在**两个**
方向上推翻分类：

- 仅仅重述可从其他地方计算出的值的章节，无论写得多好，都是**删除**
  （问题 1）。
- **记录某一时刻真实情况**的章节——变更日志、决策日志、
  事件时间线、带日期的测量结果、事后复盘——属于问题 3，而问题 3 只说明
  漂移补救措施不适用于它。对它作出保留还是删除的裁定，是你在此处、在这张表上
  像处理其他任何行一样作出的价值判断。**你唯一不能做的，是把它作为“一次性记录”
  删除却不明确说明**：漂移测试警告此类内容属于审计轨迹，因此必须将其作为一项
  明确命名的拟议删除内容提交给所有者，并附上你的理由，绝不能悄悄放入“删除”行。

详细标准：`references/value_analysis_template.md`。

### 阶段 3：整合计划

提出包含实际数字的目标结构，并提交以获得同意——这就是阶段 4 要求你在删除任何内容前
获得批准的计划：

```
Before: 726 lines (3 files, high redundancy)
After:  ~100 lines (1 file + a pointer from the project's main doc)
Reduction: 86%
Value preserved: pending — established by the preservation check after execution
```

行数和缩减比例是你现在就可以进行的测量。**“价值已保留”则不是**：在计划阶段，
这等于由执行删除的一方断言其删除无害，而这种自我认证的模式正是此技能旨在消除的。

该项应在阶段 4 的步骤 7 完成后填写，而且它**不是百分比**——究竟以什么为基数计算百分比
将不得不凭空捏造。它应是基于明确说明的分母进行计数：*“步骤 1 清单中的全部 34 项
均得以保留”*，或者 *“34 项中的 31 项”*，并指出其余三项及每一项的去向。

**分母仅包括“保留”和“精简”项。** 步骤 1 清单也特意涵盖了“删除”章节，而这些项
本来就*应该*从整合后的文件中消失——如果在此处将它们计入，就会使“全部保留”从设计上
成为不可能，而一个无人能够达成的目标会令人不再为之努力。它们应在单独的一行中交代：
*“另有来自‘删除’章节的 6 项，逐一注明其副本保留在何处，或说明其为何将被移除”*。
两个数字，两个问题，二者都不能隐藏在另一个之中。写出分母，而不只是结论——
*“我检查的每一项都得以保留”*，无论检查的是一项还是三十四项都同样成立，因此它反映的是
你的尽职程度，而不是文档的命运。未能全部保留就是需要报告的发现，绝不能把数字向上取整，
也绝不能为了让报告显得更好看而撤销你自己所做的精简。

### 阶段 4：执行

**即使 git 可以撤销，删除他人的文档对读者而言也是不可逆的。
在执行第 3 步之前，先展示阶段 3 的计划并取得同意。** 阶段 3 使用“提议”
一词是有原因的；核心原则决定的是你分析时应有多谨慎，而不是你是否
获得了授权。如果你正在无人值守的情况下运行且无法询问，请执行第 1–2 步，然后停止，并报告
你原本会删除哪些内容。

1. **首先提取保留证据——在你为整合后的文档写下任何一行内容之前。**
   顺序决定了这项检查是否有意义：如果声明列表是在重写后编写的，它就只是你碰巧
   保留下来的内容清单，因此总能匹配。若在重写前编写，它就是重写必须满足的规范。

   要如实说明是什么在强制执行这一点：最终产物中没有任何东西能区分一个列表是
   在重写前编写的，还是事后推导出来的，因此这是一项约定，而不是一道关卡。赋予它
   唯一可行的约束力——**在开始第 2 步之前输出该列表**，将其写入报告或
   临时文件。重写前就以书面形式存在的列表可以用来核对；
   事后才出现的列表无法与对结果的转录区分开来。

   **计量单位是每个承重项对应一个条目，而不是每个章节或每个类别对应一个条目。**
   划分得多细需要判断，两个谨慎的执行者可能会得出不同的数量
   ——这是可以接受的。不可接受的是，粗略划分时某些从句会缺失，因此无论你如何计数，
   以下两类都必须拥有各自独立的条目：

   - **后果从句。** “重试前回滚”是一条指令；“在迁移只应用了一部分时重试会损坏
     `events` 表，而且没有任何机制会自动修复它”则是任何人愿意遵守该指令的原因。
     粗略列表会保留指令却丢掉后果，而后果恰恰是让这条指令在快速浏览时仍能被重视的那一半。
   - **症状 → 原因映射。** “部署步骤返回 401 意味着令牌已过期，
     而不是账户有误”无法从“令牌每 90 天过期一次”重新推导出来。
     这是故障排查内容，而且只有一行，因此最先消失。

   **这两类是底线，而不是重要内容的边界。** 特别指出它们，是因为它们是
   粗略列表最容易遗漏的从句——而不是因为除此以外的从句就是安全的。还有三类容易漏网、
   值得手动检查的内容：**顺序约束**
   （“先应用迁移，再重启工作进程”——没有说明后果，因此第一条规则覆盖不到它）、
   **范围限定符**（“这仅适用于 `staging` 集群”），以及**埋在正文中的阈值**
   （“最多退避重试 5 次”）。每一项都只有一个从句那么长，每一项都会改变读者的操作，
   而且没有一项会主动凸显自己。

   检查**每一个**章节——包括标记为“删除”的章节——并从源内容中记录：
   - 保留 → 其中每个项目各记录一行有辨识度的原文（每个陷阱、每项约束、
     每个代码片段——一个包含三个陷阱的章节应记录三行，而不是一行）
   - 压缩 → 每项承重声明：每项约束、数字、条件、警告
   - **作为重复内容删除 → 其中的项目，以及每个项目的保留副本位于何处。**
     这是最容易被跳过的步骤，也是最能捕获严重故障的步骤：
     阶段 1 **按标题**映射重叠内容，因此某个章节可能仅因标题重复而被标记为重复，
     但其中却包含一条其他文件都没有的陷阱。跳过清点后，这条陷阱对后续每项检查而言都不可见
     ——它从未出现在列表中，因此第 7 步会报告“每个项目都保留了下来”，而且从检查结果看确实如此。
   - 因任何其他原因删除 → 其中的项目，以及每个项目被删除的原因。能明确说出内容的删除
     是一项决定；无法明确说出的删除，则是一个你尚未察觉的意外。
   - 以上所有类别 → 每个 URL，逐字记录

**此清单能做什么、不能做什么。** 它能发现*遗漏*问题——你本打算迁移某些内容，
   但没有迁移。它无法发现*判断*问题：如果你在阶段 2 认定某些内容并不重要，
   它就永远不会进入清单，而步骤 7 仍会顺利通过。
   **这一缺口确实存在，此流程中的任何步骤都无法弥补它。** 阶段 3 的计划
   会交给人工审核，但其中包含的是目标结构和行数，而不是此清单，因此
   它同样无法发现判断有误的条目；它检查的是结果的形式，而不是
   结果中包含了什么。不要将步骤 7 通过报告为没有丢失任何有价值内容的证据——
   应如实报告：这是在检查你*识别出*的所有内容是否均已迁移。
   如果你还希望判断本身也得到审核，唯一的办法就是将条目清单
   交给并非清单编写者的人查看。

   继续之前先做一项合理性检查：条目数量与源材料是否相称？一份
   三页的运行手册只产生四个条目，说明你只是粗略浏览了一遍——而这样一份单薄的清单，
   恰恰就是之后能够通过检查的清单。
2. 创建合并后的文档，并迁移该清单中的每一个条目
3. 删除冗余的源文件
4. 更新所有对它们的引用（`CLAUDE.md` / 项目的主文档、README、导入）
5. **在主文档或 README 中留下指向新位置的链接**——如果原先没有，就创建一个。
   合并操作会把内容移到一个尚无人知道如何访问的位置；如果没有此步骤，
   只有执行合并的人才能找到这些内容。
6. 验证不存在失效链接（参见下文的*更新引用*——仅搜索裸文件名
   是不够的）
7. **在宣布完成之前，使用步骤 1 中的清单执行下方的保留检查**。
   这是此阶段的关卡，而不是可有可无的附录。

   如果你跳过了步骤 1，而源文件已由 git 跟踪，它们仍然可以恢复——
   但要注意使用哪个 ref：**在删除操作提交之前**，内容位于
   `git show HEAD:<path>`；**一旦提交删除操作**，该路径在 HEAD 中便不复存在，
   你需要使用 `git show HEAD~1:<path>`（或删除操作之前的提交）。该路径
   相对于仓库根目录，因此从子目录中使用 `git show HEAD:./<path>`。两种错误形式
   都会明确失败并显示 `fatal: path ... does not exist`，所以你会知道。
   绝对不能从合并后的文件中获取预期字符串——那是在用文件自身作为衡量基准。

## 验证

一项文档检查要值得信赖，必须具备两个特性：必须进行**字面**匹配（事实中
可能包含正则表达式引擎会视为通配符的字符——如果作为模式搜索，`v1.0.0`
也会匹配 `v1X0X0`，而 `[2026-08-13]` 会因字符范围无效而中止），并且
必须进行**连续**匹配（跨越两行的事实仍是一个事实，而不是两个）。

`ripgrep` 可以同时满足这两点：`-F` 进行字面匹配，`-U` 允许匹配跨越多行。

**始终传入明确的路径。** 这并非风格偏好：如果未提供路径参数且
stdin 为非交互式——智能体的 shell 正是如此——`rg` 会搜索 *stdin*，
而不是你的文件。具体出现以下两种症状中的哪一种取决于该 stdin，并且两种情况
都已经过测量：

- **stdin 已关闭或管道已耗尽** → 退出码为 1，无输出。这与“字符串未出现在任何位置”的结果逐字节完全相同，因此该错误看起来会像是干净地通过了检查。在一个有四个文件包含该字符串的目录中，未指定路径的形式什么也没有报告。
- **stdin 被继承且始终无法到达 EOF** → 命令会一直**挂起**，直到被某种机制终止。如果搜索莫名其妙地挂起，请先检查是否遗漏了路径参数，再断定是文件系统速度慢。

出于 *What makes this check honest* 中详述的原因，**每次遍历目录的搜索**都必须带上两个标志：`rg` 默认会跳过被 VCS 忽略的文件以及隐藏文件，而 `.github/` 是隐藏目录，里面有大量已记录的命令。未带这些标志的搜索只会查看文档的一个严格子集（实测：只搜索了 4 个文件，而不是 6 个）。显式指定文件的搜索不需要这些标志——无论忽略规则或隐藏规则如何，`rg` 都会读取你传给它的路径——因此，本文件后面的逐项检查省略了这些标志。

只设置一次搜索根目录，并让设置失败时明确报错，而不是悄悄缩小范围：

```bash
ROOT=$(git rev-parse --show-toplevel 2>/dev/null) || { echo "not in a git repo — set ROOT to the docs root by hand" >&2; exit 1; }
```

不要在这里写 `|| echo .`。悄无声息地回退到 `.` 会将搜索范围限定为你碰巧所在的目录，同时仍以状态码 0 退出——于是，“整个仓库范围”会悄悄变成“这个子树”，而位于上一级目录中的事实会被报告为不存在（实测如此）。如果你不在仓库中，请手动将 `ROOT` 设置为文档根目录；关键在于这是你有意选择的。

```bash
# Every copy of a fact, before you change it. Path and both flags are load-bearing.
rg -U -F "the exact fact string" "$ROOT" --no-ignore --hidden -g '!.git'

# Per-file counts — the artifact you paste into your report.
rg -U -F --count-matches "the exact fact string" "$ROOT" --no-ignore --hidden -g '!.git'

# Multi-line facts: the newline has to be a real newline. In bash/zsh that means $'...';
# "\n" inside double quotes is a literal backslash-n and matches nothing (measured).
rg -U -F $'first line of the fact\nsecond line of it' "$ROOT" --no-ignore --hidden -g '!.git'
```

启用 `--no-ignore` 后，`-g '!.git'` 就不是可选项：如果没有它，搜索会报告 `.git/COMMIT_EDITMSG` 和 `.git/logs/HEAD` 中的命中项——也就是那些用于*描述*你的更改的提交消息——并把它们视为仍然存在的副本。这些内容永远无法被“清理”，因此，把它们计入的检查会使你养成忽略计数不一致的习惯，从而让检查无法发现真正的残留项。`--no-ignore` 还会重新纳入 `node_modules/` 和其他供应商代码树；当它们出现时，请用相同方式将其排除。

**请在搜索之前写下预期计数，而不是在搜索之后。** 在看到输出后才决定的计数不可能失败。请说明哪些文件应该仍包含该值、哪些文件不应该包含，然后运行：

```bash
rg -U -F --count-matches "the old value" "$ROOT" --no-ignore --hidden -g '!.git'
rg -U -F --count-matches "the new value" "$ROOT" --no-ignore --hidden -g '!.git'
```

将每项结果与你的列表进行双向的**集合相等性**比较：出现但不应该出现的文件是残留项，而列表中存在但结果中*没有*出现的文件同样意味着失败——`--count-matches` 会从输出中完全省略零匹配的文件，因此，本应接收新值却悄然没有接收到的文档，看起来与一次干净的运行完全相同。

这个检查之所以可信，是因为：

- **旧值并不总是要归零。** 更新日志条目、决策日志，或一句“截至 <date>，这是 X”记录的是历史，因此可以合理地保留旧值（漂移测试问题 3）。为了让计数归零而删除这些内容，会破坏审计轨迹，只为让检查通过。请预先列出这些历史文件；该列表*之外*的任何命中都是残留。
- **`--no-ignore --hidden` 是有意为之，而且它们并不是同一个标志。** 默认情况下，`rg` 会同时跳过被 VCS 忽略的文件和隐藏文件。`--no-ignore` 只会恢复第一组；如果没有 `--hidden`，搜索仍然不会打开 `.github/`，而贡献指南、问题模板以及包含大量文档化命令的工作流都位于其中（实测：添加 `--hidden` 后，一次示例搜索的结果从 4 个文件增加到 6 个）。无法看到这些目录的收敛门禁，会在仍有陈旧副本存留时显示为通过。应将它们纳入搜索并判断额外命中，而不是假定它们无关紧要。

**在相信零结果之前先校准——无论你使用了哪种工具。** 搜索没有返回任何内容有两种原因：事实已不存在，或命令有误。两者看起来完全相同。在报告“没有剩余副本”之前，使用相同形式的命令搜索一个你*确定*存在的字符串。如果这也没有返回任何内容，说明坏掉的是检测工具，而不是文档。这正是针对上文未指定路径的 `rg` 故障的直接补救方法，而且只需一行。

### 不使用 ripgrep

`git grep -nF "fact" -- .` 可在任何 git 仓库中运行，并且是跨平台的统一实现（不像 `grep`，其递归和符号链接行为在 BSD、GNU 和替代实现之间有所不同）。它存在以下限制，这些限制都经过实测，并且都会给出一个看似笃定的错误答案，而不是报错：

> **它只搜索已跟踪的文件。** 你刚刚在模式 2 中编写的整合文档是新的且未被跟踪——因此，通过 `git grep` 运行的保留性检查会报告其内容缺失，于是你会“恢复”那些从未丢失的内容。请先对它执行 `git add`，或直接读取该文件。

> **对多行字符串使用 `-F` 时，会悄无声息地退化为分别匹配各行。** 即使某个文件只保留了两行事实中的第一行，也仍然会报告命中——因此，一次有损迁移会被认证为“内容仍然存在”，而这恰恰是保留性检查本应捕获的错误。`grep` 和 `git grep` 都是如此。

如果这两种工具都不可用，只要能运行 Python，就可以在任何地方执行连续内容检查：

```bash
python3 -c 'import sys, pathlib
# .rstrip("\n") matters: your editor adds a trailing newline to needle.txt, and a fact
# sitting at a file'"'"'s end has none — without the strip, that copy is silently missed.
needle = pathlib.Path(sys.argv[1]).read_text(encoding="utf-8").rstrip("\n")
for f in sys.argv[2:]:
    n = pathlib.Path(f).read_text(encoding="utf-8").count(needle)
    if n: print(f, n)' needle.txt doc1.md doc2.md
```

### 更新对已移动或删除文件的引用

搜索不带路径的文件名可以找到一部分入站链接，却会漏掉其余链接，然后报告“已验证”。文件被引用的形式不止一种：

```bash
BASE=old-doc            # filename without extension
rg -n -F -e "$BASE.md" -e "[[$BASE" -e "($BASE" -e "/$BASE" "$ROOT" --no-ignore --hidden -g '!.git'
```

这涵盖了 Markdown 链接、Wiki 风格的 `[[old-doc]]`、裸路径和导入。它无法替你完成的
事情包括：

- **文件所在目录的深度发生变化时，相对路径会失效。** 从某一层引用时使用的 `../guide.md`，
  从另一层引用时则是 `../../guide.md`。通过 grep 搜索文件名可以找到对应行；路径是否仍能
  正确解析，则需要逐个链接另行判断。
- **“验证没有失效链接”包含两个方向，而阶段 4 只要求你负责其中一个。**
  *入站*——“是否仍有内容指向我删除的内容？”——这是整合操作可能破坏的部分，而上面的搜索
  可以给出答案。完成这项检查；这是该步骤真正要求履行的义务。

  *出站*——“这些文件中的每个链接是否仍能正确解析？”——这是一项通用的文档质量保证工作，
  不应在这里自行拼凑实现。请使用真正的链接检查器：

  ```bash
  lychee --offline --root-dir "$PWD" docs/   # local paths only, no network
  lychee docs/                               # also checks external URLs (slow, fails for unrelated reasons)
  ```

  如果文档使用根目录相对链接（`/docs/x.md`——mkdocs、Docusaurus、GitHub Pages 下的
  常见风格），那么 `--root-dir` 并非可选项：不使用它时，lychee 会把每个此类链接都报告为
  错误，这正是下文所说应当避免的误报。除非添加 `--include-fragments`，否则不会检查锚点
  （`x.md#section`）。

  **`0 Total` 并不代表检查通过——请先校准，再相信结果。** 实测（lychee 0.24.2）：
  不存在的路径会明确失败并以退出码 1 退出，但一个存在却不包含任何 Markdown 的目录会输出
  `🔍 0 Total … ✅ 0 OK 🚫 0 Errors`，并且**以退出码 0 退出**——与一次无问题的检查
  完全相同。指向高一层或深一层的目录，都可能得到一个实际什么也没检查却显示为绿色的对勾。
  请查看 `Total` 计数：如果为 0，要么确认这些文件确实不包含链接，要么说明你检查的位置
  有误。（如果文件中的链接全都位于行内代码或围栏代码块中，结果为 0 是合理的——lychee
  会正确地跳过这两类内容。）

  `lychee`（`brew install lychee` / `cargo install lychee`）能够正确解析 Markdown，
  而 shell 管道做不到这一点：尖括号链接 `[x](<my file.md>)`、带标题的链接
  `[x](y.md "Title")`、嵌套圆括号、引用式链接 `[x][ref]`，以及围栏代码块内的链接，
  都会令正则表达式加 `test -e` 的方案在两个方向上出错——既会悄无声息地漏掉真正的链接
  失效，也会错误标记有效链接。如果没有可用的链接检查器，请说明未执行出站检查，而不要用
  自行拼凑的方案代替。

### 保留情况检查（模式 2）

这项检查的旧形式是一份用于逐项勾选的清单——“已保留关键流程”“已保留易踩坑事项”。
删除这些内容的人自己勾选这些复选框，因此检查永远不可能失败。应当用证据替代自我评估：
列出每一项具体内容，并指出它现在位于何处。下文中的分类是一份用于全面排查内容*类型*的
清单，而不是证据计数时所采用的单位。

使用你在第 4 阶段第 1 步中构建的列表——每个承载关键内容的条目对应一项，并且是在
重写之前编写的。（错过了那一步？第 4 阶段第 7 步说明了如何从 git 恢复源文件以及
应使用哪个 ref。）绝对不要从整合后的文件中提取预期字符串：那只能证明该文件与自身一致。

**方法取决于处置方式，使用错误的方法会产生错误的删除报告。**
标记为“保留”的章节应该逐字保留下来；标记为“精简”的章节本来就*应该*被重写，因此逐字搜索其旧句子
却没有找到任何结果，恰恰说明精简正在发挥作用，而不是内容丢失。

| 处置方式 | 如何证明内容得以保留 |
|---|---|
| **保留**，原样沿用 | 对每个已保存条目：`rg -U -F "<saved distinctive line>" <consolidated file>` → 应有匹配结果 |
| **保留**，与另一章节合并——**仅限于重写前已记录该合并的情况**（记录在第 3 阶段计划或第 1 步清单中） | 逐字搜索会匹配不到——将两个以不同措辞表述同一约束的章节合并，会产生第三种表述，而这正是模式 2 的目的。请使用下方的“精简”方法。**不要为了让搜索变绿而把原句粘贴回去**：这会恢复你原本要消除的重复内容。 |

**适用以上两行中的哪一行，必须在重写前决定，绝不能在检查时决定。** 如果你无法指出计划或清单中
说明该章节将被合并的那一行，那么就适用上面第一行，未匹配就是未匹配。这并非单纯的记录工作：如果允许刚刚搜索失败的智能体
自行选择按哪一行接受评判，就会把严格的逐字检查门槛变成宽松门槛，而且这种转变*只发生在检查刚刚发现问题的情况下*。它所放过的
失败并不是合并——而是某个普通的“保留”章节在重写过程中被悄悄改写，其后果条款被删除，再被重新贴上“已合并”标签，
从而让更宽松的方法在这个被削弱的句子上返回匹配结果。
| **精简** | 对每个已保存的主张（每项约束、数字、条件、警告）：引用整合后文件中承载该主张的行。无法指出对应位置的主张就是被删除了，无论正文长度看起来如何。 |
| **删除** | 对每个已保存条目：说明保留下来的副本位于何处；或者——如果没有副本——说明删除它的原因。“它看起来很多余”不算理由；必须明确指出其中包含的内容。 |

以下类别是**帮助回忆的提示，而不是检查单位**——它们的作用是让你注意到自己遗漏的某一类内容，
而每一类最终仍然必须按照上表提供逐条证据。勾选六个类别并不等于提供了六项证据。

| 类别（同样适用于“保留”和“精简”） | 需要提供的证据 |
|---|---|
| 基本流程（设置、配置） | 按照上方对应的处置方式行执行 |
| 关键约束和陷阱 | 同上，每个陷阱对应一项——这些正是精简时最常被遗漏的承载关键内容的主张 |
| 故障排除指南 | 同上 |
| 技术债务／路线图条目 | 同上 |
| 外部链接和参考资料 | 从**保留或精简**章节中保存的每个 URL，都必须逐字出现在新文件中（检查字符串是否存在，而不是发起 HTTP 请求）。URL 在精简后要么完整保留，要么就是被删除了——不存在“更短的 URL”。从“删除”章节保存的 URL 则按照“删除”行处理：说明链接保留在何处，或者说明它将被删除及其原因。**不要为了让这一行变绿而把链接粘贴回整合后的文件中**——这会恢复你已经决定删除的内容 |
| 调试技巧和代码片段 | 同上；即使位于精简后的章节中，代码也必须逐字保留 |

**命中只能证明该字符串存在于文件中；不能证明它位于正确的位置。** 一条仅适用于预发布环境的警告如果落在“生产环境”标题下，或者一项约束被移到了限定其适用范围的条件之外，仍能通过此项检查，但此时表达的内容已经是错误的。当某一项的含义取决于它所处的位置时，应阅读其上下文，而不是看到匹配项就停止——同理，一次造成信息损失的多行移动也可能被认定为“仍然存在”。

任何无法得到命中结果的内容都没有被保留——它已被删除。这可能是正确的决定，但应在报告中将其列为删除项，而不是将其包含在勾选通过的项目中。

**零删除是完全合理的结果。** 如果价值分析表明每个章节都有保留的必要，就报告“没有需要整合的内容”并停止。第 3 阶段中的缩减百分比只是一项度量，绝不是目标——如果代理为了有一个可报告的数字而删除内容，那就完全颠倒了这项工作的初衷。

## 报告内容

明确说明以下每一项。对其中任何一项保持沉默，都会被理解为“无话可说”，而这种情况很少属实：

1. **发现的不一致之处**——哪些内容彼此不一致
2. **采用的权威来源**——对于每项事实，你将哪个文件视为其定义来源；当多个文件看起来都具有声明性质时，你基于什么理由作出选择
3. **更改的文件及原因**——每个文件一行
4. **删除的派生值和冗余引用**——每一项原本位于何处，以及为什么它属于派生内容，而不是值得保留的事实
5. **搜索证据**——你运行的命令及其结果数量，以便上述每项说法都可核查，而不只是断言。这与*输出产物*中列出的产物相同；两处列表指的是同一份报告，而不是两份。
6. **修正后的流程**——如果流程发生了更改，应提供完整的端到端流程
7. **仍未解决的问题**——未处理的例外、已知过时但不在范围内的区域，以及你无法消除的风险

在模式 2 中，此报告还应包含价值分析表以及更改前后的指标。

第 4 点最容易被遗漏，而它的影响会不断累积：明确指出已删除的派生值，可以让读者理解为什么不应再次添加它。

## 反模式

| 模式 | 问题 | 替代做法 |
|---|---|---|
| 盲目删除 | 丢失信息 | 先逐节进行价值分析 |
| 保留所有内容 | 未实现任何缩减 | 严格应用价值标准 |
| 多个事实来源 | 必然导致未来出现分歧 | 只保留一个权威位置，其他位置链接到它 |
| 孤立引用 | 链接失效 | 移动内容后更新所有引用 |
| 持久化派生值 | 会悄无声息地过时；没有任何机制发出警示 | 漂移测试问题 1——不要写入它 |
| 链接派生值 | 支撑结构本身也会过时，还会造成两者保持一致的错误信心 | 同上——该值不应存在 |
| 修补前提已失效的文档 | 内部一致，但整体错误 | 将其归档（处置流程第 4 步） |
| 只更新最显眼的出现位置 | 隐蔽的副本继续存在，并在之后与其产生矛盾 | 编辑前先搜索（第 5 步） |
| 记录预期行为 | 文档与实际情况从第一天起就出现分歧 | 以实现为准（第 3 步） |
| 无边界的“既然都到这里了”式清理 | 差异无法审查；真正的更改被淹没其中 | 有边界的清理（第 6 步） |

## 输出产物

一次成功的处理会产出：

1. **修正后的文档** — 每项事实都有唯一的权威位置
2. **价值分析**（模式 2）— 逐节说明理由
3. **前后指标对比**（模式 2）— 减少的行数、保留的价值
4. **搜索证据** — 执行的命令及其计数，使相关声明可供核查
5. **更新后的引用** — 主文档或 README 中存在指向新位置的链接，并且所有指向已移动内容的链接均可正常解析

文档保持一致后，顺理成章的后续操作包括：

```
Docs are now consistent — [N] files updated, [M] derived values removed.

Options:
A) Convert the recurring parts into a project rule — if the same drift keeps
   recurring, the fix is a rule in the project's main doc, not another cleanup pass
B) Render or publish the result — if these docs have a build/publish step
C) Nothing further — the docs are the deliverable
```
