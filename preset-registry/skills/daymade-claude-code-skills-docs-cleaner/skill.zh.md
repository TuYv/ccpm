# Docs Cleaner

文档常以两种反复出现的方式出错，而它们需要不同的处理。

**它会腐烂。** 某些东西变了——端口、路径、流程、决定——而文档
仍然在描述旧世界。这个问题有个说法，叫 *documentation rot* 或 *version
drift*：内容一项一项地逐渐失配，直到人们不再信任这套文档。

**它会膨胀。** 同一个主题积累成三个文件，每个都部分正确，却都不是
权威来源。

它们都追溯到同一个根因：**一个事实被写在了多个地方，而不是在一个地方定义。** 下面的一切都源于修正这一点。

## 核心原则（约束两种模式）

**删除前必须进行批判性评估。绝不能盲删。** 在建议删除之前，先分析每个部分的独特价值。目标是在不丢失信息的前提下减少冗余。

这约束本技能里所有“像删除”的动作，不只是合并：归档文档、删除派生值、移除交叉引用，都是删除，且都必须先做同样的分析。“看起来重复”并不是这种分析。

## 你处于哪种模式？

| 用户说了什么 / 情况如何 | 模式 |
|---|---|
| “I changed X” / 存在 diff / 某个流程被更新了 | **1 — 变更后治理** |
| “哪些文档现在错了”，“检查过时的命令/路径” | **1 — 变更后治理** |
| “整理这些文档”，“这里文件太多了”，“把这些合并” | **2 — 整合** |
| 一个主题分散在多个文件中，而且没有明确归属 | **2 — 整合** |

两种模式共用下面的 Drift Test。两者都适用时，先运行模式 1：把已经事实失真的文档先合并，只会得到一份更加自信地出错的文档。

**关于 `CLAUDE.md` / `AGENTS.md` 的说明：** 两种模式都把它们当作普通文档来处理——变更后对它们进行治理，重复时对它们进行整合。唯一该交给别处处理的工作，是*重构一个单独过大的文件*——把低频细节下放到引用中，同时保持顶层简洁。`daymade-claude-code` 的 `claude-md-progressive-disclosurer` skill 就是为此而建；当问题是体量和分层，而不是事实或重复时，应优先使用它。如果它不可用，模式 2 仍然可以处理这个文件——只是你要手工完成价值分析。

## Drift Test（两种模式的核心）

在把任何值写入文档之前——以及在决定某个现有值是否值得保留时——按顺序问这三个问题，并在第一个命中处停止：

**1. 这能否从这里已经记录的细节，或从权威来源中计算出来？**
→ 这是一个**派生值**。不要写它。等别人需要时再计算。
示例：一个计数（“6 个部分”，“涵盖 N 个分组”）、一个总数、一个由下方表格各行汇总出来的状态、在下面的日志已经说明的情况下写“last updated on”。

当你删除它时，要修正句子本身，而不是留下一个空洞：“下面四项检查”应改成“下面的检查”。删掉数字却留下悬空语法，是另一种缺陷，不是修复。

*例外 — 生成的导航。* 一个重述各级标题的目录，在这个测试下属于一个派生值，手工维护的目录确实应当删除。但如果它是在构建时由文档工具链生成的，或者平台需要这个标记来渲染导航，就不要动它：这些内容是按需计算出来的，这正是问题 1 要求处理的情况。删除前先检查是否有生成器。

**2. 不能计算，但同一事实是否在别处被权威地定义了？**
→ 这是一份**复制**。链接到那个定义，不要重述这个值。

**3. 既不是前两者，而是记录某个时刻真实存在的状态？**
→ 现在你可以把它写下来。价格历史行、决策日志条目、“截至 2026-03，供应商要求 X”——这些才是正当情形，删除它们会破坏审计轨迹。

问题 3 需要谨慎对待，因为*每一个*过时的值在某个时刻都是真的——正因为如此，它才会变得过时。但要注意问题 3 决定了什么，又不决定什么。

**它只决定一件事：这段内容不是漂移问题。** 它既不是派生值，也不是复制，因此所有漂移修复手段都不适用于它——不要重算它，不要把它链接到别处，也不要把它“更新”为当前值。至于这段内容本身是否值得保留，那是一个*内容价值*问题，应当由模式 2 的价值分析和文档所有者一起决定，而不是在这里决定。

**这个部分之前的三个草稿都试图在这里决定保留还是删除，并且都没有通过审查。** 这样说明原因是有必要的，这样没人会再把它重建出来：每个版本都要求代理知道它并不具备的信息——内容是否可以重新生成、代价是多少、由谁生成，或者别人以为存在的另一份副本是否真的存在。基于不可验证的信念授权删除，是这个 skill 存在要消除的那种自证式形态，而那也会是文件里唯一一次没有证据的删除。

所以，这个测试只做分类：

> **这段内容是在描述现在的情况吗？** 那么其中一个带日期的旧值就是问题 1 或 2 的情形，只是披着日期的外衣，而日期并不能让它免责。
>
> **还是它在记录某个时刻真实发生过的事** —— 一条变更日志、一条决策日志、一条价格历史记录、一条事件时间线、一条带日期的测量值、一份事后复盘？那它就是问题 3。保留这个值。

**要把这个判断应用到 passage，而不是 file** — 这里的 *passage* 指的是会被当作一个整体来阅读的单元：**条目、表格行、带日期的注释**、某个标题下的 section。一本操作指南里可以包含一个真正的历史块，而一份 changelog 顶部也可能带有当前状态摘要；按文件整体下结论会把这两者都判错。但也不要把它再往下拆到 passage 之下——一份 postmortem 的时间线和根因部分是同一份记录，把它们拆开，只为了能把时间线当作“可从日志重建”而删除，会毁掉它们所属的那个整体。

**对于这些 passage，问题 3 的优先级高于问题 1 和 2，尽管它问得更晚。** 一条 changelog 记录“2026-01-04: 将上传限制提高到 50 MB”*确实*会命中问题 2——上传限制在 config 中有权威定义——但如果就此停下，你会把它改成一个链接，并破坏这条记录。问题 1 也会通过另一条路径造成同样的损害：“2026-01-04: 新增 eu-west-3，使我们的 region 总数达到 12”包含一个计数，而计数正是问题 1 的示例之一——但重算它会给出*今天*的 region 数量，从而改写那一天所记录的内容。先命中就停止的规则是为了效率，不是为了把历史导向链接或重算。

当你无法判断一段文字是在记录历史还是陈述当前状态时，**请询问——不要通过删除来解决。** 这种不对称性正是原因：删除一条你误认为是当前状态重述的记录，会毁掉唯一的副本；而保留一条你误认为是记录的重述，代价只是多出几行文字。若你在无人值守状态下运行且无法询问，请保持该段落不变并在报告中说明。

**链接只能解决情况 2。** 让链接指向派生值属于类别错误：不存在一个唯一的权威单元格可供指向，因此该链接本身会成为会过时的脚手架，*同时*还会造成两处内容已保持一致的错误印象。

**为什么这个顺序很重要：** 应对 API 文档漂移的成熟答案是“从源头生成，不要手工复制”（OpenAPI/Swagger 的存在正是为此）。问题 1 是将同样的直觉应用于散文——确保一个数字正确的最可靠方式，就是不要把它写下两次。

### 位置不构成豁免

无论事实出现在哪里，它都是事实。就上述测试而言，以下所有内容都属于正文，而且陈旧的值恰恰会在这些地方躲过审计：

frontmatter · YAML/JSON metadata · 括号中的补充说明 · 索引表中的描述列 · 复选框状态 · 正式内容之前的引言框架 · 跨文档脚注 · 表格中新增的一列 · 留在散文中、形似提交信息的注释

### 什么算作事实

任何会随时间变化、并且在某处具有权威定义的内容：数字、状态、归属、关系、分类、规则、决策来源、日期、计数。业务规则也算——“所有报价均经由财务负责人处理”应只定义一次，并被引用，绝不能在每份下游文档中重复陈述。

## 模式 1 —— 变更后治理

请按顺序执行。顺序本身就是重点：在确定什么是权威内容之前修复派生文档，只会成倍增加工作量。

**1. 根据变更界定范围，而不是根据仓库。**
枚举此次变更所改变的*事实*——这个端口、这个路径、这个过程名称、这个默认值。这份列表决定了工作边界。**列表是有界的；但对其中每一项的搜索不是**——某项事实不显眼的副本恰恰存在于此次变更从未触及的文件中，因此应在第 5 步中对每项事实进行全仓库搜索。被禁止的是另一件事：打开文件去寻找*无关的*问题。无边界的扫描会让文档任务变成无法审查的重构。

**2. 为每项受影响的事实确定权威来源（SSOT）。**
哪个文件*定义*了这个端口 / 路径 / 过程，而非只是提到了它？先更新该文件。所有下游内容要么指向它，要么由它派生。

判断“定义”的实用标准是：**现实要发生变化，必须在哪个位置进行修改**——部署实际读取的文件、代码加载的模式、人工逐步遵循的运行手册。某个文件在解释其他内容时复述该值，只是在提及它。当两个文件看起来都具有声明性时，依次优先选择：机器消费的文件，而不是仅供人类阅读的文件；最接近其所描述对象的文件；已被其他文档引用的文件。然后在报告中说明你选择了哪个文件，以及基于上述哪些理由——一旦第 2 步将其他所有内容指向它，任意选择就会成为永久决定，因此它应当是明确作出的决策，而不是取决于你先打开了哪个文件的偶然结果。

**3. 根据既定意图和授权解决实现分歧。**
将代码、脚本、配置和观测到的运行结果视为当前行为的证据，而不是对预期行为的自动授权。当需求、权威来源或测试明确了预期行为，并且用户已经授权进行范围内的实现修复时，应先修复并验证实现，然后再更新文档以保持一致。将修复限制在任务已经授权的事实和文件范围内。

当预期行为含糊不清，或实现变更尚未获得授权时，应报告该分歧，并在编辑代码前获取缺失的决定或授权。不要让文档描述期望中的行为，也不要暗中把文档整理工作变成实现项目。

**4. 在编辑每份受影响的文档前，先决定其处置方式。**

| 文档属于以下情况…… | 应采取的措施 |
|---|---|
| 仍然具有可操作性；只有具体事实发生了偏移 | **更新** |
| 建立在已不再成立的前提之上 | **归档 / 退役** |

不要修补前提已经消失的文档——这样会得到一份内部自洽、整体错误的文档，比一份明显过时的文件更难被发现问题。在文档中留下“本节已被取代”的说明并不是第三种选择。维护者记录不应出现在读者路径中；读者缺少使其有意义的上下文，只会因此感到困惑。应将其移出读者路径。

“归档”意味着：移出读者路径，但仍保留在历史中。具体来说：查找项目已经采用的约定（`_archive/`、`archive/`、`deprecated/` 或项目使用的其他目录），并遵循该约定；如果不存在，则在与文件同级的位置创建 `_archive/`。无论采用哪种方式，都应使用 `git mv` 移动文件，以保留历史记录，然后重新指向或移除所有入站引用。**不要**直接删除文件，也不要仅通过添加 `status: deprecated` frontmatter、却将文件留在读者仍能找到的位置来敷衍——一份已退役但仍处于读者路径中的文档，仍然会被阅读。

出于与第 4 阶段第 3 步需要达成一致相同的原因，在归档任何并非由你创建的内容前都应先询问。**在无人值守且无法询问时：保持文档不变，并报告其需要退役。**不要改为修补它——前提已经失效的文档，在更新其事实后只会变得更具误导性，而不是更少。

**5. 在更改每个事实之前，找到该事实的所有副本。**
这一步最容易被跳过，也是经典失败的根源：更新了显眼的出现位置，却遗漏了另外三个不显眼的位置。准确的命令见下文的*验证*部分。

风险最高的情况是**对序列中的项目重新编号或插入项目**，因为你改变的不是一个事实，而是一整组相互引用的事实：正文中写着“请参阅第 7 步”的内容、同级文件中的交叉引用，以及——最棘手的是——将数量写入句子中的表述（“下面的四项检查”）。最后一种表述完全不包含你正在搜索的数字，因此按步骤编号搜索永远无法找到它。

**对此没有机械化的扫查方式，你不应假装存在。** 两种显而易见的范围界定都已验证过，且都不可行：

- *在整个仓库中搜索计数词* → 在一个真实文档仓库中为 224,330 行 / 约 550 MB
  （限定为单个项目目录时为 17.7 MB）。没有人会运行这个，而且一条保证自身会被绕过的指令，比没有指令更糟。
- *只在提及该主题的文件中搜索计数词* → 范围有限，但**在关键方向上是错误的**。将计数嵌入句子中的文案，恰恰会通过别名、译名、代词或裸链接来指代主题——“下面四项检查”、 「预检有四个检查」——而从不使用其标题。实测：一个包含真实过期计数的文件，在针对主题名称或文件名的搜索中匹配结果为*零*。该筛选条件与目标呈负相关。

因此请改为这样做，并说明它未覆盖什么：

1. **完整阅读你重新编号的文件。** 大多数过期的自引用都在其中。
2. **先构建文件列表，再在其中搜索计数词。** Mode 1 中此前没有任何步骤生成过这个列表——不要去使用 *更新引用* 中的入站引用搜索，它属于 Mode 2，回答的是不同的问题（“什么指向了这个**文件**”，而不是“什么讨论了这个**主题**”）。请在此处生成：

   ```bash
   ROOT=$(git rev-parse --show-toplevel 2>/dev/null) || { echo "not in a git repo — pass the docs root explicitly" >&2; exit 1; }
   rg -l -F "<the subject's name>" "$ROOT" --no-ignore --hidden -g '!.git'
   ```

   这会得到直接写出主题名称的文件；步骤 3 会覆盖那些没有直接写出名称的文件。
   这是一个很小的集合，因此请直接列出文件名，
   而不是把列表通过管道传给 `xargs`（空列表会使 GNU `xargs` 在完全不带路径的情况下运行搜索，进而搜索当前目录——这是一个看起来像有输出、实则范围错误的结果）：

   ```bash
   rg -n -i -H \
     -e '\b(one|two|three|four|five|six|seven|eight|nine|ten|both) [a-z]+\b' \
     -e '[一二三四五六七八九十两](个|条|步|项|点)' -e '[0-9]+(个|条|步|项|点)' \
     -e '\b[0-9]+ [a-z]+\b' \
     path/to/one.md path/to/two.md
   ```
   两个细节，都经过实测：使用 `-H` 是因为当 `rg` 恰好只接收一个文件时会省略文件名，而“是哪一个文件”正是这里要回答的全部内容。该模式刻意匹配*任意*后续单词，而不是列出一组名词——列表不会包含项目所用的名词（“four **gates**”、“three **lanes**”），而遗漏将悄无声息。在少量文件中，额外噪声的成本很低；漏掉那一行则不是。
3. **自行列出主题的别名并搜索它们**，然后在由此找到的所有文件中搜索计数词。这一步没有任何工具能替你完成。

然后说明你检查了什么：*"阅读了重新编号的文件；在按名称引用它的 N 个文件中搜索了计数词；通过其他名称指代它的文案未被机械化覆盖。"* 这句话比一个悄然意味着上述两种失败之一的绿色勾选更有价值。

**6. 清理你在处理过程中遇到的派生值——但仅限于你本来就在编辑的文件。**
移除已打开文件中的过时计数是维护，不是范围蔓延。为了寻找更多此类内容而打开无关文件则是范围蔓延。这个边界确保变更可供审查。

**7. 按照 *What to report* 下的结构报告你所做的工作。**

## 模式 2 —— 整合

在保留所有有价值内容的前提下，整合冗余文档。上述 *核心原则* 约束本模式中的每一项删除。

### 阶段 1：发现

1. **识别涵盖该主题的所有文档文件**，并且在搜索前说明你所搜索的边界（一个目录、一套组件、一个项目）——采用与模式 1 第 1 步相同的有界范围规则。面对“文档”这一说法却没有边界，两个代理会整合出不同的文件集。通常的做法是在该边界内按主题关键词扫描——请注意 `-F`，因为像 `C++`、`.NET` 或 `v1.0.0` 这样的主题术语是字面量，作为模式时几乎会匹配所有内容：
   `rg -l -i -F -e '<topic term>' -e '<synonym>' <boundary> --no-ignore --hidden -g '!.git'`
   此列表界定了整个整合范围，因此垃圾列表会导致垃圾分析。
2. **统计文件总行数**——对第 1 步的列表执行 `wc -l`
3. **映射内容重叠**：对于每个文件中的每个标题，记录还有哪些文件涵盖了相同内容。产物是一张“标题 → 同样涵盖该内容的文件”表；出现在多个文件中的章节就是整合候选项。此步骤仅用于判定**重叠**——不决定保留还是删除。唯一的章节仍可能因与重复无关的原因在阶段 2 被删除（不言自明、已被取代、某项工作的副产物），因此请将其理解为：*“这里没有任何内容允许你以冗余为由删除唯一章节”*，而不是：*“唯一就意味着它会被保留”*。

### 阶段 2：价值分析

对于每份文档，按章节构建一张表：

| 章节 | 行数 | 价值 | 原因 |
|---------|-------|-------|--------|
| API 参考 | 25 | 保留 | 唯一的端点文档 |
| 设置步骤 | 40 | 精简 | 冗长但必不可少 |
| 环境变量表 | 30 | 删除 | 与 `README.md` 中的表格重复，而后者是权威来源 |

请注意，Delete 示例**不是**什么：一次有日期的测试运行记录、一条会议笔记、一份事故时间线。在任何文档中，这些看起来都是最容易删除的内容，而它们恰恰是本技能不允许你悄然删除的那一类——请参阅下方三段后的规则。上述示例之所以是 Delete，是因为一个具名文件持有相同内容；这是唯一一种你可以通过指向其他内容来证明合理性的 Delete。

- **保留** —— 唯一、必要、经常被引用
- **精简** —— 有价值但冗长
- **删除** —— 重复、一次性、不言自明、过时
- **归档** —— 整份文档的*前提*已失效（例如已取消系统的设计说明、已退役服务的事后分析）。它不是需要修正的过时当前状态，也不是应当删除的重复内容。没有这个类别，“已被取代”和“它是一份记录”会将同一份文档拉向相反方向，而最终结果取决于你最后读到的是哪一个。

实时文档中一个前提已经失效的**章节**，是同一问题下沉一个层级的表现，而
Archive 不接受这种情况——它定义于整篇文档。将其视为一次 Delete，其原因是前提
已失效，并在 Phase 3 计划中指名说明，而不是自行决定：“为一项已取消的迁移而写的
Kafka 迁移章节”正是所有者可能回答“实际上我们仍在引用它”的那类判断。

**Archive 判定会将该文档从本次整合中移除。**它不会进入
Phase 3 或 Phase 4——没有任何内容需要合并，也没有任何内容需要精简。应按
Mode 1 的归档流程处理——即 **Mode 1 — Post-change governance** 下以
`"Archive" means: out of the reader's path, still in history` 开头的段落——在报告中说明
你已这样做，然后继续
整合其余内容。也不要将它列入 Phase 3 的行数计划：它是原封不动地离开，因此将其行数
计为“缩减”会宣称一项你实际上没有实现的节省。

在处理每一行时都运行 Drift Test，并让它在**两个**
方向上覆盖类别：

- 一个章节如果只是在重述可从其他地方计算得出的值，就是 **Delete**，无论它写得多么好（问题 1）。
- 一个章节如果**记录了某个时刻的事实**——变更日志、决策日志、事故时间线、带日期的测量结果、事后复盘——则属于问题 3，而问题 3 只说明漂移补救措施不适用于它。它的保留或删除判定，是你在这里、在这张表中作出的价值判断，与其他任何行一样。**唯一不能做的，是将它作为“一次性记录”删除却不明确说明**：它正是 Drift Test 警告可能属于审计轨迹的类别，因此必须作为具名的拟议删除项提交给所有者，并附上理由，绝不能悄然作为一行 Delete 处理。

详细标准：`references/value_analysis_template.md`。

### Phase 3：整合计划

提出包含真实数字的目标结构，并提交以供批准——这是 Phase 4 要求你在删除任何内容之前获得签字确认的计划：

```
Before: 726 lines (3 files, high redundancy)
After:  ~100 lines (1 file + a pointer from the project's main doc)
Reduction: 86%
Value preserved: pending — established by the preservation check after execution
```

行数和缩减比例是你现在可以取得的测量值。**“Value preserved”不是**：在计划阶段，它意味着删除方断言自己的删除无害，这正是此技能旨在消除的自我认证模式。

它应在 Phase 4 第 7 步之后填写，而且它**不是百分比**——百分比的基数将不得不凭空捏造。它是相对于已说明分母的计数：*“step-1 inventory 中的全部 34 项都得以保留”*，或 *“34 项中的 31 项”*，并指明其余三项及各自去向。

**分母仅包括 Keep 和 Condense 项。**step-1 inventory 特意也涵盖了 Delete 章节，而这些项目*本来就应当*不出现在整合后的文件中——在这里计算它们，会使“全部保留”在设计上就无法达成，而一个无人能够实现的目标，人们终将不再追求。它们应在单独一行中说明：*“以及 Delete 章节中的 6 项，每一项都注明其副本存续的位置或其被移除的原因”*。两个数字，两个问题，彼此都不隐藏在对方之中。写出分母，而不只是判定——*“我检查的每一项都得以保留”*，检查一项时和检查三十四项时同样成立，因此它报告的是你的勤勉，而不是文档的命运。任何未能全部保留的情况都是需要报告的发现，绝不能把数字向上取整，也绝不能为了让报告看起来更好而撤销你自己的精简。

### 第 4 阶段：执行

**删除别人的文档，从读者的角度看是不可逆的，即使 git 能撤销。先展示第 3 阶段的计划并获得同意，然后再执行第 3 步。** 第 3 阶段之所以写着 "propose" 是有原因的；Core Principle 约束的是你分析得有多仔细，而不是你是否被授权。若你是在无人看管的情况下运行，且无法询问，就做第 1–2 步，停下，并报告你会删掉什么。

1. **先提取保留证据——在你写下合并文档的任何一行之前。** 顺序决定了这项检查是否有意义：在重写之后才写的声明清单，只是你碰巧保留下来的内容清单，所以它总会匹配。先写下来，它才是重写必须满足的规范。

   要诚实面对真正的约束：成品里没有任何东西能区分一份在重写前写下的清单和一份在重写后整理出来的清单，所以这只是一个约定，不是一个门禁。给它唯一可用的约束力——**在开始第 2 步之前把清单输出到报告或临时文件里。** 在重写之前就存在于文字中的清单，才能拿来和结果核对；重写之后才出现的清单，无法与结果的转录区分开来。

   **单位是每个负载性项目一条，而不是每个 section 一条，也不是每个 category 一条。** 切分得多细是判断问题，两个认真工作的 agent 可能会得出不同数量——这可以接受。不可接受的是粗切时会丢掉哪些条款，所以无论如何，下面两类都必须各自单独成条：

   - **后果条款。** "Roll back before retrying" 是一条指令；"retrying on a half-applied migration corrupts the `events` table and there is nothing that repairs it automatically" 才是让人遵守它的原因。粗糙的清单会保留指令、丢掉后果，而后果正是让它在扫读时还能站住脚的那一半。
   - **症状 → 原因映射。** "A 401 from the deploy step means the token lapsed, not that the account is wrong" 不能从 "the token expires every 90 days" 重新推出来。这是排障内容，而且只有一行，所以最先消失。

   **这两类只是下限，不是重要内容的边界。** 它们之所以被点名，是因为粗略清单最常丢掉的就是这些条款——不是因为其他条款就安全。下面三类也值得人工检查：**顺序约束**（"apply the migration before restarting the workers"——没有写后果，所以第一条规则覆盖不到它），**作用范围限定**（"this applies to the `staging` cluster only"），以及**藏在叙述里的阈值**（"backs off up to 5 attempts"）。每一类都只有一条子句长，每一类都会改变读者的行为，而且都不会自己显眼地跳出来。

   逐个处理**每个** section——包括标记为 Delete 的那些——并从源文中写下：
   - Keep → 其中每一项的一行独特原文（每个 gotcha、每个约束、每个片段——一个包含三个 gotcha 的 section 需要三行，而不是一行）
   - Condense → 每一条负载性声明：每个约束、数字、条件、警告
   - **Delete-as-duplicate → 其中的项目，以及每个项目的存活副本在哪里。** 这是最容易被跳过、也最能抓住最糟失败的步骤：Phase 1 按 **heading** 映射重叠，所以某个 section 可能仅凭标题就被标记为重复，但它里面还保留着其他文件都没有的一个 gotcha。跳过这份清单，这个 gotcha 就会对后续所有检查都不可见——它从来没上过清单，所以第 7 步会报告“每个项目都存活了”，而且这话是认真的。
   - 由于其他原因删除 → 其中的项目，以及每个项目为什么要删。你能说清楚的删除是一个决定；你说不清楚的删除，是你还没察觉到的意外。
   - 以上全部 → 每个 URL，逐字照录

**此列表能做什么、不能做什么。** 它能捕捉*记忆遗漏*——你本打算带过某项内容，却没有带过去。它无法捕捉*判断失误*：如果你在阶段 2 判断某项内容不重要，它就不会进入列表，而第 7 步也会顺利通过，不会发现它。**这个缺口确实存在，且本流程中的任何内容都无法弥补它。** 阶段 3 的计划会交给人工审核，但其中包含的是目标结构和行数——而不是此列表——因此同样无法捕捉判断错误；它检查的是结果的形态，而不是结果包含了什么。不要把第 7 步通过报告成没有丢失任何有价值内容的证据——应当报告为：它检查的是你**识别出来的所有内容**是否都已带过来。
   如果你还希望审核判断本身，唯一能做到这一点的方式，就是把项目列表交给没有编写它的人查看。

   继续之前先做一个合理性检查：项目数量看起来符合源材料的规模吗？一份三页的运行手册最后只有四个项目，说明你只是略读了它——而一份过于单薄的列表，恰恰是之后最容易通过检查的列表。
2. 创建合并后的文档，将列表中的每个项目都带过去
3. 删除冗余的源文件
4. 更新所有对这些文件的引用（`CLAUDE.md` / 项目的主文档、README、导入项）
5. **在新位置留下指针**，放在主文档或 README 中——如果不存在，就创建一个。合并会将内容移动到一个目前没有任何路径指向的位置；没有这一步，除了执行合并的人之外，其他人都无法找到这些内容。
6. 验证没有损坏的链接（参见下方的*更新引用*——仅搜索裸文件名是不够的）
7. **在宣布完成之前，运行下方的保留检查**，使用第 1 步中的列表。它是本阶段的门槛，而不是可选附录。

   如果跳过了第 1 步，且源文件已由 git 跟踪，它们仍然可以恢复——但要注意使用哪个 ref：**在删除提交之前**，内容位于 `git show HEAD:<path>`；**一旦删除已提交**，该路径就不再存在于 HEAD 中，此时需要使用 `git show HEAD~1:<path>`（或删除操作之前的那个提交）。路径是相对于仓库根目录的，因此从子目录执行时应使用 `git show HEAD:./<path>`。两种错误形式都会以 `fatal: path ... does not exist` 明确失败，因此你会知道出错了。绝对不能从合并后的文件中提取预期字符串——那样测量的只是文件自身与自身的一致性。

## 验证

让文档检查实现**字面匹配**（事实中包含的字符可能会被正则表达式引擎视为通配符——作为模式搜索时，`v1.0.0` 也会匹配 `v1X0X0`，而 `[2026-08-13]` 会因字符范围无效而中止）以及**连续匹配**（跨越两行的事实仍然是一个事实，而不是两个）。

`ripgrep` 同时提供这两项能力：`-F` 进行字面匹配，`-U` 允许匹配跨越多行。

在交付字面命令示例之前，应在其声明的 shell 和环境中，针对隔离的 fixture，按原样运行确切的安全代码片段。将其接受的 flags、flag 优先级、结果和退出状态与实现或 CLI 契约进行比较。不要针对活动目标执行具有破坏性、向外部发送、修改生产环境或包含凭据的示例；应根据代码或帮助输出验证其 flags 和优先级，并说明哪些端到端行为未经过实际执行。

**始终传递显式路径。** 这不是风格偏好：在没有路径参数且 stdin 为非交互式的情况下（agent 的 shell 正是如此），`rg` 会搜索 *stdin*，而不是你的文件。你会遇到以下两种症状中的哪一种，取决于 stdin 的状态，并且两种情况都已测量：

- **stdin 已关闭或管道已耗尽** → 退出码为 1，没有输出。这与“该字符串在任何地方都未出现”字节完全一致，因此这个错误看起来像一次正常通过。在一个有四个文件包含该字符串的目录中，无路径形式没有报告任何内容。
- **stdin 被继承且永远不会到达 EOF** → 命令会**挂起**，直到有东西将其终止。如果搜索莫名其妙地挂起，在认定文件系统很慢之前，先检查是否缺少路径参数。

每一次遍历目录的搜索都必须带上两个标志，原因见 *是什么让这项检查可信*：`rg` 默认会跳过被 VCS 忽略的文件 *以及* 隐藏文件，而 `.github/` 是隐藏的，其中包含大量已记录的命令。不带这两个标志的搜索只会查看文档的一个严格子集（测量结果：4 个文件而非 6 个）。显式指定文件的搜索不需要它们，因为 `rg` 会读取你交给它的路径，不受忽略或隐藏规则影响，这也是本文件后面的逐项检查省略它们的原因。

只设置一次搜索根目录，并让失败明确报错，而不是悄然缩小范围：

```bash
ROOT=$(git rev-parse --show-toplevel 2>/dev/null) || { echo "not in a git repo — set ROOT to the docs root by hand" >&2; exit 1; }
```

不要在这里写 `|| echo .`。静默回退到 `.` 会将搜索范围限定为你当前所在的任意目录，同时仍以退出码 0 结束，因此“全仓库”会悄然变成“这个子树”，而位于上一级的事实会被报告为不存在（已测量）。如果你不在仓库中，请手动将 `ROOT` 设置为文档根目录；关键是这是你主动选择的范围。

```bash
# Every copy of a fact, before you change it. Path and both flags are load-bearing.
rg -U -F "the exact fact string" "$ROOT" --no-ignore --hidden -g '!.git'

# Per-file counts — the artifact you paste into your report.
rg -U -F --count-matches "the exact fact string" "$ROOT" --no-ignore --hidden -g '!.git'

# Multi-line facts: the newline has to be a real newline. In bash/zsh that means $'...';
# "\n" inside double quotes is a literal backslash-n and matches nothing (measured).
rg -U -F $'first line of the fact\nsecond line of it' "$ROOT" --no-ignore --hidden -g '!.git'
```

一旦启用 `--no-ignore`，`-g '!.git'` 就不是可选项：没有它时，搜索会报告 `.git/COMMIT_EDITMSG` 和 `.git/logs/HEAD` 中的匹配——那些*描述*你变更的提交消息——仍是存活副本。这些副本永远无法被“清理”，因此一个统计它们的检查会训练你忽略计数不匹配，从而让它对真正的问题失去作用。`--no-ignore` 还会恢复 `node_modules/` 及其他供应商树；它们出现时也要以同样方式排除。

**在搜索之前写下预期计数，而不是之后。** 你在看过输出后才决定的计数不可能失败。说明哪些文件应当仍包含该值、哪些不应包含，然后运行：

```bash
rg -U -F --count-matches "the old value" "$ROOT" --no-ignore --hidden -g '!.git'
rg -U -F --count-matches "the new value" "$ROOT" --no-ignore --hidden -g '!.git'
```

将每项结果与你的列表进行**集合相等性**的双向比较：出现了但不应出现的文件是遗留项，而列表中存在但*没有*出现的文件同样是失败——`--count-matches` 会完全省略零匹配文件，因此本应接收新值却悄然未更新的文档，看起来与一次干净的运行完全相同。

使这项检查保持诚实的原因：

- **旧值并不总是应当归零。** 变更日志条目、决策日志，或“截至 <date>，这曾是 X”这样的句子会记录历史，并且合理地保留旧值（Drift Test 问题 3）。为了让计数归零而删除这些内容，是为了满足检查而破坏审计轨迹。请预先列出历史文件；该列表*之外*的任何内容都是遗留项。
- **`--no-ignore --hidden` 是有意添加的，而且它们不是同一个标志。** 默认情况下，`rg` 会跳过被 VCS 忽略的文件*以及*隐藏文件。`--no-ignore` 只恢复第一组；若没有 `--hidden`，搜索仍然不会打开 `.github/`，而贡献指南、议题模板和包含已文档化命令的工作流正位于其中（实测：添加 `--hidden` 后，样本搜索从 4 个文件增至 6 个）。将它们包括在内并评估额外命中，而不是假定它们无关紧要。

**在相信零结果之前先校准，无论你使用了什么工具。** 搜索没有返回结果有两种原因：事实已不存在，或命令有误。两者看起来完全一样。在报告“没有剩余副本”之前，针对一个你*确定*存在的字符串运行相同形式的命令。如果该命令同样没有返回结果，出问题的是工具而不是文档。这是对上文无路径 `rg` 失败的直接补救措施，而且只需一行。

### 没有 ripgrep 时

`git grep -nF "fact" -- .` 可在任何 git 仓库中工作，并且是跨平台的单一实现（不同于 `grep`，其递归和符号链接行为在 BSD、GNU 及替代实现之间各不相同）。它有以下限制，均经过测量，而且都会产生一个自信但错误的答案，而不是报错：

> **它只搜索被跟踪的文件。** 你刚刚在 Mode 2 中编写的整合文档是新的且未跟踪——因此，通过 `git grep` 运行的保留检查会报告其内容缺失，而你会“恢复”原本从未丢失的内容。先执行 `git add`，或直接读取该文件。

> **对多行字符串使用 `-F` 会悄然退化为逐行匹配。** 仅保留两行事实中第一行的文件仍会报告命中——因此，一次有损移动会被认证为“内容仍然存在”，而这正是保留检查要捕获的那一种错误。`grep` 和 `git grep` 都如此。

当这两种工具都不可用时，只要能运行 Python，就可以执行连续性检查：

```bash
python3 -c 'import sys, pathlib
# .rstrip("\n") matters: your editor adds a trailing newline to needle.txt, and a fact
# sitting at a file'"'"'s end has none — without the strip, that copy is silently missed.
needle = pathlib.Path(sys.argv[1]).read_text(encoding="utf-8").rstrip("\n")
for f in sys.argv[2:]:
    n = pathlib.Path(f).read_text(encoding="utf-8").count(needle)
    if n: print(f, n)' needle.txt doc1.md doc2.md
```

### 更新对已移动或删除文件的引用

搜索裸文件名只能找到部分入站链接，并遗漏其余链接，随后却报告“已验证”。文件可能以不止一种形式被引用：

```bash
BASE=old-doc            # filename without extension
rg -n -F -e "$BASE.md" -e "[[$BASE" -e "($BASE" -e "/$BASE" "$ROOT" --no-ignore --hidden -g '!.git'
```

这会覆盖 Markdown 链接、wiki 风格的 `[[old-doc]]`、裸路径和导入语句。但以下事项不会由它替你完成：

- **文件改变目录层级后，相对路径会失效。** `../guide.md` 在一级目录下的写法，在另一个位置可能需要改为 `../../guide.md`。grep 文件名可以找到对应行，但链接是否仍能解析是另一个问题，需要逐个链接检查。
- **“验证没有损坏的链接”有两个方向，而 Phase 4 只要求其中一个。**
  *入站* ——“是否仍有内容指向我删除的文件？”——这是合并操作可能破坏的内容，上面的搜索可以回答。执行这一项；这是该步骤的实际职责。

  *出站* ——“这些文件中的每个链接是否仍能解析？”——这是通用的文档 QA 工作，不应在这里手写实现。请使用真正的链接检查器：

  ```bash
  lychee --offline --root-dir "$PWD" docs/   # local paths only, no network
  lychee docs/                               # also checks external URLs (slow, fails for unrelated reasons)
  ```

  如果文档使用根相对链接（`/docs/x.md` —— mkdocs、Docusaurus、GitHub Pages 下的常见样式），则 `--root-dir` 不是可选项：否则 lychee 会将所有此类链接报告为错误，这正是下文所说的应避免的误报。除非添加 `--include-fragments`，否则不会检查锚点（`x.md#section`）。

  **`0 Total` 不代表检查通过 —— 在相信结果之前，先校准检查范围。** 实测（lychee 0.24.2）：不存在的路径会明确失败并以状态码 1 退出，但一个存在且不包含 Markdown 文件的目录会输出 `🔍 0 Total … ✅ 0 OK 🚫 0 Errors`，并以状态码 0 退出——这与干净运行完全相同。把它指向高一层或低一层的目录，就会得到一个看似通过、实际什么也没检查的绿色结果。请读取 `Total` 数量：如果为 0，要么确认文件确实不包含链接，要么说明你搜索了错误的位置。（如果文件中的所有链接都在行内代码或围栏代码块中，`Total` 合法地为 0——lychee 会正确跳过这两种内容。）

  `lychee`（`brew install lychee` / `cargo install lychee`）能够正确解析 Markdown，而 shell 管道无法做到这一点：尖括号链接 `[x](<my file.md>)`、带标题的链接 `[x](y.md "Title")`、嵌套括号、引用式链接 `[x][ref]` 以及围栏代码块中的链接，都会让“正则表达式加 `test -e`”的方法失效，无论检查入站还是出站链接都是如此——它会悄悄漏掉真实的损坏链接，并错误地标记有效链接。如果没有可用的链接检查器，请说明未运行出站检查，不要用手写的检查器替代。

### 保留检查（模式 2）

这种检查的旧形式是一份待勾选事项列表：“保留了必要流程”“保留了易错点”。删除它们的人自己勾选这些框，因此检查永远不会失败。用证据取代自我评估：列出每个具体项目，并说明它现在位于何处。后面的类别是用来全面扫查的*类别提示*，而不是证据计数的单位。

使用你在第 4 阶段第 1 步建立的列表——每个承载关键信息的项目对应一条，并且是在重写之前记录的。（错过了那一步？第 4 阶段第 7 步说明了如何从 git 中恢复源内容，以及应使用哪个 ref。）绝对不能做的是从合并后的文件中提取预期字符串：那只能证明文件与自身一致。

**具体方法取决于处置方式，使用错误的方式会产生错误的删除报告。** 标记为 Keep 的章节应逐字保留；标记为 Condense 的章节*本来就应该*被重写，因此对其旧句子进行逐字搜索确实找不到结果——这说明压缩生效了，而不是内容丢失。

| 处置方式 | 如何证明其得到保留 |
|---|---|
| **Keep**，原样迁移 | 对每个已保存的项目执行：`rg -U -F "<saved distinctive line>" <consolidated file>` → 得到匹配结果 |
| **Keep**，与其他章节合并——**仅当合并是在重写之前记录的**（记录于第 3 阶段计划或第 1 步清单中） | 逐字搜索会找不到结果——用不同措辞表达相同约束的两个章节合并后会产生第三种表述，而这正是模式 2 的目的。使用下面 Condense 的方法。**不要为了让搜索变为绿色而把原句粘贴回来**：那会重新引入你正在消除的重复内容。 |
| **Condense** | 对每条已保存的声明（每项约束、数字、条件、警告），引用合并后文件中承载该声明的那一行。无法指出出处的声明就是被丢弃了，无论篇幅多长都一样。 |
| **Delete** | 对每个已保存的项目，说明幸存副本位于何处；如果没有幸存副本，则说明它为什么要被删除。“看起来是重复内容”不是理由；必须说明其中包含了什么。 |

上面两行中的哪一行适用，必须在重写之前决定，绝不能在检查时决定。如果你无法指出计划或清单中的某一行，证明该章节当时要被合并，那么就适用上面第一行，搜索不到就是未通过。这不是文书工作：让刚刚搜索失败的 agent 自己选择评分方式，会把严格的逐字门槛变成软门槛，而且只会在它刚刚捕获到问题的情况下这样做。它放过的不是合并，而是一个普通的 Keep 章节在重写期间被悄悄改写，其后果条款被删除，然后被重新标记为“已合并”，以便较宽松的方法能够在弱化后的句子上返回匹配结果。

下面的类别是**召回提示，而不是计数单位**——它们用于提醒你注意遗漏的类别，而每个类别仍然必须按照上表解析为逐项证据。勾选六个类别不等于提供了六份证据。

| 类别（同样适用于 Keep 和 Condense） | 应提供的证据 |
|---|---|
| 必要流程（设置、配置） | 按上面对应的处置方式行处理 |
| 关键约束和易错点 | 同上，每个易错点提供一份——这些是压缩时最容易丢失的承载关键信息的声明 |
| 故障排查指南 | 同上 |
| 技术债务 / 路线图项目 | 同上 |
| 外部链接和参考资料 | 从 **Keep 或 Condense** 章节中保存的每个 URL 都必须在新文件中逐字出现（检查字符串是否存在，而不是发起 HTTP 请求）。URL 要么在压缩过程中完整保留，要么就是被删除了——不存在“更短的 URL”。从 Delete 章节中保存的 URL 则遵循 Delete 行：说明链接在哪里保留，或者说明它将被删除以及原因。**不要为了让这一项变绿而将链接粘贴回合并后的文件**——那会重新引入你决定删除的内容 |
| 调试提示和代码片段 | 同上；即使位于压缩章节中，代码也必须逐字保留 |

**一次命中证明该字符串在文件中；并不能证明它位于正确的位置。** 一条仅适用于暂存环境的警告落在“生产环境”标题下，或一项约束被移出其限定范围的条件语句之外，都能通过这项检查，但表达的内容已经错误。当某项内容的含义取决于其所在位置时，应阅读其周围的行，而不是在匹配处停止——这也正是一次有损的多行移动仍可能被认证为“依然存在”的原因。

任何无法产生命中的内容都没有被保留——它已被删除。这可能是正确的决定，但应在报告中将其作为删除事项记录，而不是放在一个勾选标记里。

**零删除结果是合理的结果。** 如果价值分析表明每个章节都值得保留，就报告“无需整合”并停止。第 3 阶段的精简百分比是一项度量，绝不是目标——为了有数字可报告而删除内容的代理，已经完全颠倒了重点。

## 应报告的内容

明确陈述以下每一项。对其中任何一项保持沉默都会被理解为“无话可说”，而这很少符合事实：

1. **发现的不一致之处** —— 哪些内容彼此不一致
2. **所用的权威来源** —— 你将哪个文件视为各项事实的定义来源；当多个文件看起来都具有声明性时，你基于什么理由选定它
3. **修改的文件及原因** —— 每个文件一行
4. **移除的派生值和冗余引用** —— 每一项原本在哪里，以及为什么它符合派生值的条件，而不是值得保留的事实
5. **搜索证据** —— 你运行的命令及其计数，以便上面的每项声明都可验证而非仅被断言。这与 *输出工件* 下列出的工件相同；两个列表指的是一份报告，不是两份。
6. **修正后的流程** —— 如果流程发生了变化，则提供端到端的完整流程
7. **仍未解决的问题** —— 未处理的例外情况、范围外已知过时的区域、你无法消除的风险

在模式 2 中，该报告还包括价值分析表以及修改前后的指标。

第 4 点是最容易被遗漏的一点，也是会不断累积影响的一点：点明被移除的派生值，能让读者理解为什么它不应再次出现。

## 反模式

| 模式 | 问题 | 应改为 |
|---|---|---|
| 盲目删除 | 丢失信息 | 先逐章节进行价值分析 |
| 保留所有内容 | 未实现精简 | 严格应用价值标准 |
| 多个事实来源 | 必然导致未来分歧 | 一个权威位置，其他位置链接到它 |
| 孤立引用 | 链接失效 | 移动内容后更新每一处引用 |
| 保留派生值 | 会悄然过时；没有任何机制提示 | 漂移测试问题 1 —— 不要写入它 |
| 链接派生值 | 同样会过时的脚手架，还会造成两者已对齐的虚假信心 | 同上 —— 该值本就不应存在 |
| 修补前提已失效的文档 | 内部一致，但整体错误 | 归档它（处置，第 4 步） |
| 只更新显而易见的出现位置 | 隐蔽副本会存留下来，并在之后与其矛盾 | 编辑前先搜索（第 5 步） |
| 记录尚未实现的愿望 | 文档与现实从第一天起就发生分歧 | 遵循第 3 步：只修复已确定、已获授权的行为；否则报告该分歧 |
| 无边界的“既然都在这里了”式清理 | 差异无法审查；真正的修改会淹没其中 | 有边界的清理（第 6 步） |

## 输出产物

一次成功的执行将产出：

1. **已修正的文档** —— 每项事实只有一个权威位置
2. **价值分析**（模式 2）—— 按章节说明理由
3. **前后指标对比**（模式 2）—— 减少的行数、保留的价值
4. **搜索证据** —— 所执行的命令及其计数，使相关结论可供核查
5. **已更新的引用** —— 主文档或 README 中存在指向新位置的链接，且每个指向已移动内容的链接均可解析
