# 怀疑驱动开发

## 概述

自信的答案并不等于正确的答案。长时间的会话会不断积累上下文，在无人察觉的情况下，悄然将假设变成“事实”。怀疑驱动开发是一种实践：在任何非平凡的输出定稿之前，引入一名拥有全新上下文的审查者，并让其倾向于**证伪**，而非认可。

这不是 `/review`。`/review` 是对已完成产物的裁决。而这是一种贯穿过程的工作方式：在纠正方向的成本仍然较低时，对非平凡的决策进行交叉质询。

## 何时使用

如果至少满足以下一项，决策就是**非平凡的**：

- 引入或修改了分支逻辑
- 跨越了模块或服务边界
- 断言了类型系统或编译器无法验证的属性（线程安全性、幂等性、顺序、不变量）
- 其正确性依赖于未来读者无法看到的上下文
- 其影响范围不可逆（生产部署、数据迁移、公共 API 变更）

在以下情况下应用此技能：

- 即将在不确定的情况下做出架构决策
- 即将提交非平凡的代码
- 即将声称某个并非显而易见的事实（“这是安全的”“这能够扩展”“这符合规范”）
- 正在处理自己并未完全理解的代码

**以下情况请勿使用：**

- 机械性操作（重命名、格式化、移动文件）
- 遵循清晰、无歧义的用户指令
- 阅读或总结现有代码
- 正确性显而易见的单行改动
- 纯工具操作（运行测试、列出文件）
- 用户已明确要求优先保证速度而非验证

如果你怀疑每一次敲击键盘的操作，就永远无法交付任何成果。此技能仅适用于上文定义的非平凡决策。

## 加载约束

此技能是为**主会话编排器**设计的，其中步骤 3（DOUBT，详见下文）可以启动一名拥有全新上下文的审查者。

- **请勿将此技能添加到角色的 `skills:` frontmatter 中。** 遵循步骤 3 的角色会启动另一个角色——这是 `../../references/orchestration-patterns.md` 明确禁止的编排反模式（“角色不会调用其他角色”）。
- **如果你发现自己正在子代理上下文中应用此技能**（Claude Code 会阻止嵌套启动子代理）：首选做法是向用户说明怀疑驱动流程无法嵌套运行，并让主会话处理。只有在万不得已的情况下，才可使用降级的自我质询后备方案——将 ARTIFACT + CONTRACT 重写为一条全新的自我提示，在心理上与先前的推理严格隔离，然后执行步骤 1–5。这**并非全新上下文审查**（你仍携带着自己的上下文），因此应将结果标记为降级，并且只要能够联系到用户，就应优先升级处理。

## 流程

应用此技能时，复制以下检查清单：

```
Doubt cycle:
- [ ] Step 1: CLAIM — wrote the claim + why-it-matters
- [ ] Step 2: EXTRACT — isolated artifact + contract, stripped reasoning
- [ ] Step 3: DOUBT — invoked fresh-context reviewer with adversarial prompt
- [ ] Step 4: RECONCILE — classified every finding against the artifact text
- [ ] Step 5: STOP — met stop condition (trivial findings, 3 cycles, or user override)
```

### 步骤 1：CLAIM —— 明确当前成立的主张

用两三行说明该决策：

```
CLAIM: "The new caching layer is thread-safe under the
        read-heavy workload described in the spec."
WHY THIS MATTERS: a race here corrupts user data and is
                  hard to detect in QA.
```

如果你无法如此简洁地写出该主张，那么你拥有的只是感觉，而不是决策。在审视它之前，先将其明确出来。

### 步骤 2：EXTRACT —— 最小可审查单元

不了解前置上下文的审查者需要的是**制品**和**契约**，而不是推导过程。

- 代码：差异或函数——而不是整个文件
- 决策：用 3–5 句话说明提案，以及它必须满足的约束
- 断言：主张以及据称支持该主张的证据（与步骤 1 中的 CLAIM 块保持区分，后者是协调者正在审视的假设）

去掉你的推理过程。如果你把结论交出去，得到的只会是对这些结论的验证。该单元必须足够小，让审查者读一遍就能将其完整记在脑中——如果这是一个包含 500 行代码的 PR，请先进行拆分。

### 步骤 3：DOUBT —— 调用无前置上下文的审查者

审查者的提示词**必须具有对抗性**。措辞方式决定答案。

```
Adversarial review. Find what is wrong with this artifact.
Assume the author is overconfident. Look for:
- Unstated assumptions
- Edge cases not handled
- Hidden coupling or shared state
- Ways the contract could be violated
- Existing conventions this might break
- Failure modes under unexpected input

Do NOT validate. Do NOT summarize. Find issues, or state
explicitly that you cannot find any after thorough examination.

ARTIFACT: <paste artifact>
CONTRACT: <paste contract>
```

**只传递 ARTIFACT + CONTRACT。不要传递 CLAIM。** 把你的结论交给审查者，会使其产生倾向于认同的偏见。审查者必须独立判断该制品是否满足契约。

在 Claude Code 中，`agents/` 里的基于角色的审查者在设计上就以隔离上下文启动，可用于此处——有关角色列表以及各领域的匹配关系，请参阅 `agents/`。

**上述对抗性提示词优先于角色的默认响应形式。** `code-reviewer` 等角色被设计为给出兼顾优点和缺点的平衡结论；而怀疑驱动方式需要只输出问题。调用时应逐字粘贴该对抗性提示词，使其覆盖角色的默认行为。如果无法干净地覆盖某个角色的响应形式，则改用带有该对抗性提示词的通用子代理。

#### 跨模型升级

单一模型的审查者与原作者存在共同盲点——更冷静且架构不同的模型能发现这些盲点。对于非简单决策，怀疑驱动方式本就需要主动选择使用，因此在这一范围内提供跨模型选项是该技能价值的一部分，而非可有可无的额外阻碍。

**交互式会话：始终提供。绝不静默跳过。**

**步骤 1：询问用户**

完成上述步骤 3 中的单模型审查后、进入 RECONCILE 之前，暂停并询问：

> *“单模型审查已完成。是否需要跨模型复核意见？可选项：Gemini CLI、Codex CLI、手动外部审查（由你将内容粘贴到其他地方），或跳过。”*

在每次交互式质疑循环中，都必须询问此问题——即使相关制品看起来风险很低。是否值得付出相应成本，由用户而非代理决定。代理的职责是明确提供这一选择。

**第 2 步：如果用户选择 CLI——先验证，再调用**

1. 检查工具是否位于 PATH 中（`which gemini`、`which codex`）。
2. 在传入完整提示词之前，先测试工具能否正常工作（`gemini --version` 或等效命令）——过期或损坏的二进制文件可能会通过 `which` 检查，但在处理实际输入时失败。
3. 与用户确认确切的调用方式，包括所需的标志、身份验证和环境变量（例如 API 密钥）。不同实现各不相同；切勿自行假设。
4. **仅**传入 ARTIFACT + CONTRACT + 对抗性提示词。不传入会话上下文，也不传入 CLAIM。
5. 注意 shell 转义。如果制品中包含引号、`$(...)` 或反引号，优先使用 stdin（`echo … | gemini`）或 heredoc，而不是内联的 `-p "…"`。如有疑问，请在运行前让用户确认调用方式。
6. 将输出带入第 4 步（RECONCILE）。

**绝不要将制品插入 shell 引号包裹的参数中。**代码、Markdown 和审查提示词通常包含反引号、`$(...)` 和引号字符，这些内容可能截断提示词或执行其中嵌入的 shell。请将完整提示词写入文件，并通过 stdin 将其传入。

示例形式（请根据已安装的工具验证标志——不同实现和版本的语法各不相同）：

```bash
# Write the adversarial prompt + ARTIFACT + CONTRACT to a temp file first.
# Then pipe via stdin so shell metacharacters in the artifact stay inert.

# Codex (read-only sandbox keeps the CLI from writing to your workspace):
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini ('--approval-mode plan' is read-only; '-p ""' triggers non-interactive
# mode and the prompt is read from stdin):
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

只读沙箱是保障安全的关键细节：质疑制品本身可能包含指令（有意或无意的提示词注入），否则跨模型 CLI 可能会针对你的工作区执行这些指令。

**第 3 步：如果 CLI 不可用或失败**

明确指出失败。提供以下选项：手动运行、尝试其他工具或跳过。不要静默回退到单模型——用户应当知道跨模型审查并未发生。

**第 4 步：如果用户跳过**

在输出中确认已跳过（*“仅基于单模型的发现继续处理”*），然后继续执行 RECONCILE。可以跳过，但不能静默跳过。

**非交互式上下文**（CI、`/loop`、autonomous-loop、计划任务运行）：

- **跳过**跨模型审查，并且必须在输出中**明确说明**：*“已跳过跨模型审查：当前为非交互式上下文。”*
- **绝不要在未获得用户明确授权的情况下调用外部 CLI**——这是保障安全的关键属性。

跨模型审查会增加成本、延迟和工具脆弱性。代理在每个循环中明确提供这一选择；由用户决定当前制品是否值得进行跨模型审查。

### 第 4 步：协调（RECONCILE）— 将发现反馈回去

审查者的输出是数据，而不是裁决。**你仍然是协调者。** 在分类之前，对照每一项发现重新阅读产物文本——不加判断地照单全收审查者的意见，与忽略它们属于同一种失败模式。

对于每一项发现，按照以下**优先顺序**分类（第一个匹配的类别优先）：

1. **误读契约**——审查者之所以指出某个问题，是因为你提供的契约不清晰或不完整。先修正契约，在下一个周期中重新分类。
2. **有效且可操作**——确实存在问题，需要修改产物。修改它，然后重新进入循环。
3. **有效的权衡**——问题确实存在，但修复成本高于接受它的成本。明确记录这项权衡，以便用户了解。
4. **噪声**——审查者指出的内容在其不了解的上下文中其实是正确的。记录下来，继续处理其他内容，并思考：如果将该上下文添加到契约中，是否能避免这次误报？

新的审查者可能因为缺少上下文而出错。不要仅仅因为它是“新的”就听从它。

### 第 5 步：停止（STOP）— 有界循环，而非递归

在以下情况下停止：

- 下一次迭代只返回琐碎的或已经考虑过的发现，**或者**
- 已完成 3 个周期（升级给用户，不要独自进行第四个周期），**或者**
- 用户明确表示“发布吧”

如果经过 3 个周期后，审查者仍然发现实质性问题，则产物可能尚未准备就绪。将这一情况告知用户——三个周期仍未解决，本身就是有关产物的重要信息，而不是继续循环的理由。

如果因为产物规模较大，3 个周期“显然不够”：那说明产物太大了——返回第 2 步并进行拆分。不要提高上限。

## 常见的自我辩解

| 自我辩解 | 事实 |
|---|---|
| “我很有信心，可以跳过质疑步骤” | 对于新颖的问题，信心与正确性的相关性很低。恰恰是在确信无疑时，盲点最容易隐藏。 |
| “启动一个审查者成本很高” | 调试生产环境中的错误提交成本更高。检查是有界的，错误则不是。 |
| “审查者只会吹毛求疵” | 只有在范围不明确时才会如此。将提示词约束为“会导致该内容无法满足契约的问题”。 |
| “我会在最后用 `/review` 进行质疑” | `/review` 是最终关卡。由质疑驱动的检查能在早期发现错误方向，此时纠正路线的成本较低。等到创建 PR 时就太晚了。 |
| “如果我质疑每一步，就永远无法发布” | 此 Skill 适用于非琐碎的决策，而不是每一次按键操作。重新阅读“When NOT to Use”。 |
| “两个意见总比一个好” | 当第二个意见掌握的上下文更少并产生噪声时，并非如此。应当协调判断，而不是盲目听从。 |
| “审查者不同意，所以是我错了” | 审查者不了解你的上下文——分歧是信息，而不是裁决。重新阅读产物、进行分类，然后再做决定。 |
| “跨模型总是更好” | 跨模型能够发现单一模型与自身共享的盲点，但也会增加成本和工具脆弱性。在每个交互式质疑周期中都提供这一选项——由用户决定该产物是否值得这样做。智能体的职责是呈现选择，而不是设置门槛。 |
| “用户已经同意过一次，所以我可以继续调用 CLI” | 每次调用都需要单独授权。每次调用之间，产物、提示词和标志都会发生变化——每次运行前，都要向用户重新确认具体命令。 |

## 危险信号

- 为一行重命名或格式调整启动一个全新上下文的审查者
- 不重新阅读制品文本，就将审查者的输出视为权威结论
- 循环超过 3 轮却不升级给用户处理
- 用“这样好吗？”来提示审查者，而不是要求“找出问题”
- 在高风险决策中因时间压力而跳过质疑
- 对未发生变化的制品重新启动全新上下文审查（你只会得到相同的发现；这只是在拖延）
- **质疑表演（可检查的信号）**：在 2 轮或更多轮次中，审查者都提出了实质性发现，但没有任何发现被归类为可执行项。你是在验证，而不是质疑。停止并升级处理。
- 只在提交之后才进行质疑——那是 `/review`，而不是质疑驱动开发
- 未向用户确认外部 CLI 工具存在、已配置且支持完全相同的语法，就硬编码对该工具的调用
- **在交互式质疑周期中悄悄跳过跨模型审查。** 即使不推荐使用，也必须明确展示这一选项。可以跳过，但不能悄悄跳过。
- 外部 CLI 报错或缺失时悄悄回退——应明确告知失败，并让用户重新指示方向
- 从审查者的输入中移除契约
- 将 CLAIM 传给审查者（这会使其偏向赞同）

## 与其他技能的交互

- **`code-review-and-quality` / `/review`**：二者互为补充。`/review` 是事后的 PR 结论；质疑驱动是在决策过程中逐项进行的。两者都要使用。
- **`source-driven-development`**：SDD 根据官方文档核实*有关框架的事实*。质疑驱动核实*你对制品的推理*。SDD 检查 API 是否存在；质疑驱动检查你是否在契约约束下正确使用了它。
- **`test-driven-development`**：TDD 的 RED 步骤是质疑的具体化——失败的测试就是一次证伪尝试。当 TDD 适用时，该失败测试本身*就是*对行为声明的质疑步骤。
- **`debugging-and-error-recovery`**：当审查者发现真实的故障模式时，转入调试技能来定位并修复问题。
- **仓库编排规则**（`../../references/orchestration-patterns.md`）：此技能从主会话进行编排。由一个角色调用另一个角色属于反模式 B——请参阅上面的加载约束。

## 验证

应用质疑驱动开发后：

- [ ] 每个非简单决策（依据上述定义）在成立之前，都已被明确命名为 CLAIM
- [ ] 每个非简单制品至少进行了一次全新上下文审查（根据“与其他技能的交互”部分，由 TDD 的 RED 步骤产生的失败测试可满足行为声明的这一要求）
- [ ] 审查者收到的是 ARTIFACT + CONTRACT——而不是 CLAIM，也不是你的推理
- [ ] 给审查者的提示是对抗性的（“找出问题”），而不是验证性的（“这样好吗”）
- [ ] 依据制品文本对发现进行了分类（而非不加判断地认可），并采用以下优先顺序：误读契约 / 可执行项 / 权衡项 / 噪声
- [ ] 已满足某个停止条件（仅剩简单发现、达到 3 轮或用户要求停止）
- [ ] 在交互模式下，无论制品风险高低，都已向用户**明确提供**跨模型审查选项，并在输出中确认了用户的回应
- [ ] 在非交互模式下，已跳过跨模型审查，并明确告知这一跳过行为
- [ ] 调用任何外部 CLI 之前，都已检查 PATH、测试二进制文件可正常运行、向用户确认语法，并获得明确的运行授权
