# 上下文退化模式

在上下文故障产生连锁反应之前对其进行诊断和修复。上下文退化并非二元状态，而是一个连续过程，会通过五种不同且可预测的模式表现出来：中间信息丢失、污染、干扰、混淆和冲突。每种模式都有特定的检测信号和缓解策略。应将退化视为一个具有可测量阈值的工程问题，而非不可预测的故障模式。

## 何时启用

在以下情况下启用此技能：
- 智能体在长对话中的表现意外下降
- 调试智能体产生错误或不相关输出的情况
- 设计必须可靠处理大型上下文的系统
- 评估生产系统的上下文工程方案
- 调查智能体输出中的“中间信息丢失”现象
- 分析智能体行为中与上下文相关的故障

不要为其他技能负责的相邻工作启用此技能：
- 在没有实际故障的情况下解释基础上下文机制：`context-fundamentals`。
- 在已知故障模式后应用令牌效率优化策略：`context-optimization`。
- 设计压缩或交接摘要策略：`context-compression`。
- 将大型输出、日志或暂存状态持久化到提示词之外：`filesystem-context`。

## 核心概念

围绕注意力 U 形曲线安排上下文位置：开头和结尾位置能获得可靠的注意力，而在长上下文实验中，中间位置的回忆准确率会显著降低（claim-context-degradation-lost-middle-ruler）。这并非模型缺陷，而是注意力机制所导致的结果——第一个令牌（通常为 BOS）会充当“注意力汇点”，吸收不成比例的注意力预算，随着上下文增长，中间令牌获得的注意力会越来越少。

将上下文污染视为一个断路器问题。一旦幻觉、工具错误或错误检索到的事实进入上下文，就会通过反复自我引用不断加剧。被污染的目标部分会导致后续的每一项决策都强化错误假设。检测需要追踪声明的来源；恢复则需要截断至污染点之前，或仅使用经过验证的上下文重新开始。

在加载上下文之前进行严格过滤——即使只有一份不相关文档，也会显著降低相关任务的表现。模型无法“跳过”不相关的上下文；它们必须关注所提供的全部内容，从而使相关内容与不相关内容之间产生注意力竞争。将可能需要但并非立即相关的信息置于工具调用之后，而不是预先加载。

隔离任务上下文以防止混淆。当上下文包含多种任务类型或在不同目标之间切换时，模型会纳入来自错误任务的约束、调用适用于其他上下文的工具，或混合多个来源的要求。通过独立上下文窗口进行明确的任务分段，可以消除交叉污染。

通过优先级规则而非信息堆积来解决上下文冲突。当上下文中出现多个各自正确但相互矛盾的来源时（版本冲突、视角冲突、多来源检索），模型无法判断应采用哪一个。明确标记矛盾、确定来源优先级，并在过时版本进入上下文之前将其过滤掉。

## 详细主题

### 中间信息丢失：检测与放置策略

将关键信息放在上下文的开头和结尾，绝不要放在中间。U 形注意力曲线意味着，位于中间的信息在回忆准确率上会降低 10-40%。对于超过 4K token 的上下文，这种影响会变得显著。

使用能够在注意力优势位置呈现关键发现的摘要结构。添加明确的章节标题和结构标记——这些元素会形成注意力锚点，帮助模型浏览长上下文。当必须完整纳入某份文档时，在其前面添加关键要点摘要，并在其后附上关键结论。

监测中间信息丢失的症状：上下文中存在正确信息，但模型将其忽略；响应与所提供的数据相矛盾；或者模型“忘记”了长提示词中较早给出的指令。

### 上下文污染：预防与恢复

在所有外部输入进入上下文之前对其进行验证。工具输出、检索到的文档和模型生成的摘要是三种主要的污染途径。它们都会引入未经验证的断言，而后续推理会将这些断言视为事实依据。

通过以下信号检测污染：在此前能够成功完成的任务上，输出质量下降；工具错配（使用了错误的工具或参数）；以及尽管已明确纠正，幻觉仍然持续存在。当这些信号同时出现时，应怀疑是上下文污染，而不是模型能力问题。

恢复时应移除被污染的内容，而不是在其上叠加更正。截断至污染发生之前的位置，使用仅保留已验证信息的干净上下文重新开始，或者明确标记受污染的部分并要求从头重新评估。在受污染的上下文上层层叠加更正很少奏效——原始错误仍会保有注意力权重。

### 上下文干扰：重在筛选，而非堆积

应筛选进入上下文的内容，而不是依赖模型忽略无关内容。研究表明，即使只有一份干扰文档，也会导致可测量的性能下降——其影响呈阶跃函数，而非线性曲线。多个干扰项会使问题进一步加剧。

在加载检索到的文档之前应用相关性过滤。使用命名空间和结构化组织方式，使章节边界清晰明确。相比预加载，应优先采用基于工具调用的访问方式：将参考资料置于检索工具之后，使其仅在与当前推理步骤直接相关时才进入上下文。

### 上下文混淆：任务隔离

将不同任务划分到独立的上下文窗口中。上下文混淆不同于上下文干扰——它指的是模型将错误上下文中的约束应用于当前任务，而不仅仅是注意力被稀释。其迹象包括：响应针对查询中的错误方面、调用了适用于其他任务的工具，以及输出混合了多个来源的要求。

在不同任务上下文之间实现清晰的过渡。使用状态管理，按任务隔离目标、约束和工具定义。当无法避免在单个会话中切换任务时，使用明确的“上下文重置”标记，以指明哪些约束适用于当前片段。

### 上下文冲突：冲突解决协议

在冲突发生之前建立信息源优先级规则。上下文冲突不同于投毒——多条信息各自都是正确的，但彼此矛盾（版本冲突、视角差异、多源检索得到不同事实）。

实施版本过滤，在过时信息进入上下文之前将其排除。当矛盾不可避免时，使用结构化冲突注释明确标记：说明冲突的内容、每项主张来自哪个信息源，以及哪个信息源具有优先权。如果没有明确的优先级规则，模型将以不可预测的方式解决矛盾。

### 实证基准与阈值

使用这些基准来设定设计约束，而不要将其视为普遍真理。RULER 风格的证据表明，宣称支持长上下文并不能保证模型在该长度下具备令人满意的任务表现（claim-context-degradation-lost-middle-ruler）。在“大海捞针”测试中取得近乎满分的成绩，并不能预测真实场景中的长上下文表现。

**特定模型的性能退化阈值**

性能开始退化的临界点会因模型系列和任务类型而有显著差异。一般而言，对于复杂检索任务，预计性能会在达到所宣称上下文窗口的 60-70% 时开始退化（RULER 基准发现，在宣称支持 32K 以上上下文的模型中，只有 50% 能在该长度下维持令人满意的表现）。主要规律包括：

- **具备扩展思考能力的模型**通过逐步验证减少幻觉，但会产生更高的延迟和 token 成本
- **针对智能体/编码优化的模型**通常能更好地管理包含大量工具输出的上下文中的注意力
- **拥有超大上下文窗口（1M+）的模型**能够处理更多原始上下文，但仍然遵循 U 形性能退化曲线——更大的窗口并不能消除问题，只会推迟问题出现

始终使用你的具体工作负载对性能退化阈值进行基准测试，而不要依赖已发布的基准。每次模型更新后，特定于模型的阈值都可能过时（参见 Gotcha 2）。

### 反直觉的研究发现

在设计上下文策略时，应考虑以下有研究支持的意外发现：

**打乱顺序的上下文可能优于连贯的上下文。**研究发现，对于某些检索任务，不连贯（打乱顺序）的干扰信息集合可能优于按逻辑排序的集合（claim-context-degradation-distractor-shuffled）。连贯的上下文可能会产生干扰检索的错误关联；不连贯的上下文则可能迫使模型进行精确匹配。不要假定组织得更好的上下文总能产生更好的结果——应对两种排列方式都进行测试。

**单个干扰项会产生不成比例的巨大影响。**与添加第一个干扰文档后继续添加更多干扰项相比，仅加入一个无关文档造成的性能损失就异常显著。应将干扰项防范视为一个二元问题：要么保持上下文干净，要么接受显著的性能下降。

**目标信息与问题的相似度较低会加速性能退化。**与表层相似度较高的任务相比，需要跨越不相似内容进行推理的任务，其性能会随着上下文长度增加而更快退化。设计检索机制时，应最大限度提高查询与检索内容之间的语义重合度。

### 更大的上下文何时会造成负面影响

不要想当然地认为更大的上下文窗口会提升性能。性能在达到特定于模型的阈值之前会保持稳定，之后则会迅速下降——这条曲线并非平缓下滑，而是呈非线性断崖式下降。对于许多模型而言，即使其窗口支持远大于此的容量，在 8K-16K token 时也会开始出现明显的性能下降。

还要考虑成本：处理 400K token 上下文所需的时间和算力成本相比 200K 呈指数级增长，而非线性增长。对于许多应用而言，这使得大上下文处理在经济上并不现实。

要认识到认知瓶颈：即使拥有无限上下文，要求单个模型在数十项相互独立的任务中保持质量，也会导致性能下降，而增加上下文并不能解决这一问题。应将任务拆分给多个子代理，而不是扩展上下文。

## 实用指南

### 四类缓解框架

根据当前出现的性能下降模式，采用以下四种策略：

**写出** — 使用暂存区、文件系统或外部存储，将上下文保存在窗口之外。当上下文使用量超过窗口容量的 70% 时使用此策略。这样既能保持活跃上下文精简，又能通过工具调用保留信息访问能力。

**选择** — 通过检索、过滤和优先级排序，仅将相关上下文调入窗口。当出现注意力分散或混淆症状时使用此策略。在加载之前进行相关性评分；低于阈值的内容应予以排除，而不是将所有可用内容全部纳入。

**压缩** — 通过总结、抽象和观测屏蔽，在保留信息的同时减少 token 数量。当上下文持续增长但所有内容都相关时使用此策略。用紧凑的结构化摘要替换冗长的工具输出；将重复出现的模式抽象为单一引用。

**隔离** — 将上下文拆分到多个子代理或会话中，防止任何单个上下文增长到超过其性能下降阈值。当出现混淆或冲突症状，或者任务彼此独立时使用此策略。这是最激进的策略，但对于复杂的多任务系统而言，往往也是最有效的策略。

### 提升韧性的架构模式

实现即时上下文加载：仅在当前推理步骤需要信息时才进行检索，而不是提前加载。使用观测屏蔽，在处理完冗长的工具输出后将其替换为紧凑的引用。部署子代理架构，使每个代理仅保留与任务相关的上下文。在上下文超过特定于模型的性能下降起始阈值之前触发压缩——而不是等到症状出现之后。

## 示例

**示例 1：检测性能下降**
```yaml
# Context grows during long conversation
turn_1: 1000 tokens
turn_5: 8000 tokens
turn_10: 25000 tokens
turn_20: 60000 tokens (degradation begins)
turn_30: 90000 tokens (significant degradation)
```

**示例 2：缓解中间信息丢失问题**
```markdown
# Organize context with critical info at edges

[CURRENT TASK]                      # At start
- Goal: Generate quarterly report
- Deadline: End of week

[DETAILED CONTEXT]                  # Middle (less attention)
- 50 pages of data
- Multiple analysis sections
- Supporting evidence

[KEY FINDINGS]                     # At end
- Revenue up 15%
- Costs down 8%
- Growth in Region A
```

**示例 3：上下文污染熔断器**
```text
symptom: agent keeps citing an incorrect retrieved claim after correction
diagnosis: poisoned context, not a missing-instruction problem
action:
  1. identify first turn where the bad claim entered
  2. truncate or restart from before that point
  3. reload only verified sources
  4. record the rejected claim and source provenance
```

**示例 4：上下文冲突标注**
```yaml
conflict:
  topic: billing API version
  source_a: docs/v1.md says endpoint is /charges
  source_b: docs/v2.md says endpoint is /payments
  precedence: docs/v2.md
  reason: current production version
```

## 指南

1. 在开发过程中监控上下文长度与性能之间的相关性
2. 将关键信息放在上下文的开头或结尾
3. 在性能严重下降之前实施压缩触发机制
4. 在将检索到的文档添加至上下文之前，验证其准确性
5. 使用版本控制，防止过时信息引发冲突
6. 对任务进行分段，防止不同目标之间发生上下文混淆
7. 应以优雅降级为设计目标，而不是假定条件始终完美
8. 使用逐渐增大的上下文进行测试，以找出性能下降阈值

## 易踩的坑

1. **正常波动看起来像性能下降**：模型输出质量在不同运行之间会自然波动。不要因单次质量下降就诊断为性能下降——应通过多次运行建立基线，并寻找与上下文增长相关且持续出现的下降趋势。某次运行中出现 5-10% 的质量下降属于噪声；若同样的下降在超过 40K token 后持续出现，则是有效信号。

2. **特定于模型的阈值会过时**：基准测试表中的性能下降起始值反映的是特定模型版本。提供商更新、微调变化和基础设施调整都可能使阈值向任一方向偏移 20-50%。应每季度以及在任何重大模型更新后重新进行基准测试，而不是将已发布的阈值视为永久不变。

3. **大海捞针测试得分会造成虚假的信心**：模型在大海捞针测试中获得 99% 的得分，并不意味着它在生产环境中能够良好处理 128K token。大海捞针测试衡量的是从静态上下文中检索单一事实的能力——真实工作负载要求模型进行多事实推理、遵循指令，并综合整个上下文窗口中的信息。应使用能够反映实际工作负载模式的任务特定基准测试。

4. **相互矛盾的检索文档会悄无声息地污染上下文**：当 RAG 流水线检索到两份在某项事实方面存在分歧的文档时，模型可能会在不提示冲突的情况下默默选择其中一份。这看起来像是正确的响应，但实际上选择是随机的。应在文档进入上下文之前，在检索层实现矛盾检测。

5. **提示词质量问题会伪装成性能下降**：糟糕的提示词结构（指令有歧义、缺少约束、任务描述不清晰）会产生与上下文性能下降完全相同的症状——输出不一致、忽略指令、错误使用工具。在诊断性能下降之前，请先验证同一提示词在较短的上下文长度下能否正确工作。如果它在 2K token 时就失败，那么问题出在提示词，而不是上下文。

6. **性能退化呈非线性，并存在断崖式临界点**：性能并非逐渐下降——它会保持稳定，直至达到模型特定的阈值，随后急剧下降。为“优雅降级”而设计的系统往往会错过这种模式，因为监控检查通常假设性能会线性下降。应在远早于断崖式临界点的位置设置压缩触发条件（已知退化起始点的 70%），而不是等到退化开始时才触发。

7. **过度组织上下文可能适得其反**：直觉上，结构良好且连贯的上下文应该比杂乱无章的内容表现更好。研究表明，对于检索任务，打乱顺序的干草堆有时反而优于连贯的干草堆，因为连贯的上下文会产生错误关联。应测试大量使用结构化格式对于特定任务是否确实有帮助——不要想当然地认为它有帮助。

## 集成

此技能负责诊断和缓解正在发生的上下文故障。故障识别后，具体实施策略由相邻技能负责：

- `context-fundamentals`：在故障发生前，从概念层面解释注意力和上下文窗口。
- `context-optimization`：诊断后采用掩码、缓存、分区及其他提升 token 效率的策略。
- `context-compression`：当累积的上下文必须压缩时，生成结构化摘要并进行交接。
- `filesystem-context`：卸载原始输出、日志和临时状态，以便检查受污染或体量庞大的上下文，而无需将其保留在提示词中。
- `multi-agent-patterns`：将任务隔离到不同的上下文中，以防止混淆和冲突。
- `evaluation`：退化测试和生产环境监控。
