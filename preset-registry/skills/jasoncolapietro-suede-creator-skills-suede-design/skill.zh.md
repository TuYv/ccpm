# Suede 设计

使用此 skill，让 Suede 界面显得经过深思熟虑、高级、清晰易读且充满生命力，同时避免陷入千篇一律的 AI 产出。它涵盖产品 UI、品牌界面、落地页、仪表盘、组件系统、响应式优化以及视觉 QA。

**核心原则：**去掉 logo 后，界面仍必须一眼可辨地属于这个产品，并且在声称结果可用之前先渲染结果。

## 工作立场

- 基于当前源代码和渲染后的屏幕开展工作。当仓库、在线 URL、截图或本地预览可供检查时，不要凭记忆进行设计。
- 对于 Suede 品牌，只能使用 `JasonColapietro/suede-creator-skills` 中的 `docs/assets/suede-ai-logo-transparent.png`（SHA-256 `83a7ee0317e4debe2e7b076c20ba067feb76a587f9e829dc6310ae4be4b44dfa`）。绝不要重新绘制、描摹、近似、排版、重新着色、变形或生成替代版 Suede S。`suede-skill-icon.png` 是 Passport 图标，不是 Suede 品牌标志。如果批准的文件不可用或其校验和不一致，请停止并请求该文件；宁可省略标志，也不要擅自臆造。
- 让 Suede 的公开文案始终围绕创作者所有权、可编程 IP、权利、来源、由注册表支持的媒体、版税路由以及代理商商务展开。不要把 Suede 简化成一个泛泛的 AI 音乐应用。
- 优先使用现有的应用框架、设计令牌、组件、图标库和路由模式。只有在能够消除实际复杂性或符合既有本地模式时，才添加新的抽象。
- 对于视觉工作，渲染结果。截图胜过代码检查。最低要求：1280px 宽度的桌面端、390px 宽度的移动端。对于 App Store 提交：1290×2796px（6.7 英寸）、1488×2266px（iPad Pro 13 英寸）。
- 要捕获渲染结果：`npx playwright screenshot <url> --viewport-size=1280,900 desktop.png`（将 viewport 替换为上面的移动端/App Store 尺寸；一次性设置：`npx playwright install chromium`），或者使用环境中可用的内置预览/截图工具。

在进行任何设计工作之前，先阅读界面上下文：
- 本地 `PRODUCT.md`：用户、品牌、语调、反向参考、战略原则
- 本地 `DESIGN.md`：颜色令牌、字体比例、组件清单、间距
- `AGENTS.md`、`AI_HANDOFF.md` 或 `README.md`：代理指导和界面上下文

如果主要界面缺少 PRODUCT.md 或 DESIGN.md，请记录这一点，并基于现有上下文继续工作。任务完成后，提出创建这些文件。

然后在工作更新中声明以下预检信息：

```text
SUEDE_DESIGN_PREFLIGHT: target=<repo-or-folder> surface=<route-or-url> register=<brand|product> context=<pass|partial|none> design_system=<loaded|not_found> git=<pass|skipped:reason> render=<pass|pending|skipped:reason>
```

此外，当工作涉及文案、设计系统、视觉 QA、Suedify、可见性或公开发布质量时，也应用由 suede-workflow-skills 负责的共享 no-missed 质量门禁（其 no-missed-quality-gates 参考）。  
（要求从此 pack 安装 suede-workflow-skills。如果未安装，请根据此 skill 的 Implementation Workflow、Ship Gate 和 Visual QA Report 部分中的标准，运行 Copy Gate、Visual QA Gate、SEO/AEO/AI EO Gate、Design System Gate 和 Launch Gate 检查清单。）

## 任务路由

选择与请求匹配的最小路径。

- **明确的小修复：**检查当前 UI，进行范围狭窄的修改，验证渲染结果，
  并报告更改内容。
- **模糊或全新的设计：**收集上下文，提出 2-3 种带权衡的方案，
  推荐其中一种，并在实施前获得批准。
- **大型重新设计：**先编写一份精简的形态简报：受众、页面任务、
  语域、场景、色彩策略、排版、布局、标志性时刻、约束条件和 QA 计划。
- **视觉系统工作：**在提出更改之前，扫描当前 CSS、tokens、组件、间距、
  阴影、断点、图标使用情况和重复出现的 UI 模式。
- **从源文件到实现的 QA：**如果存在 mock、截图、Figma frame 或图像目标，
  且同时存在已渲染的实现，则在交付前对两者进行视觉比较，并在项目根目录保存 `visual-qa-report.md`。
- **长时间的润色循环：**通过可见的检查清单进行迭代。如果同一问题反复出现，
  冻结循环，将范围缩小到出现问题的单元，并使用明确的验收标准重新运行。

## 交付纪律

在进行重要或大型的 Suede 设计工作之前，编写一份精简的交付契约：

- objective：用户可见的结果；
- surface：repo、route、live URL、branch 和 owner；
- done signal：截图、构建、测试、部署回读或评审产物；
- constraints：需要保留的 WIP、不应触碰的 routes、尚未获批准的文案声明，以及发布/上线边界；
- lanes：哪些工作可以并行执行，哪些必须等待，以及每条 lane 需要写入什么内容。

不要因为代码发生了变化就认为工作已完成。只有在完成信号已检查，或已明确说明剩余差距时，才能称其为完成。

当多个 lane 必须同时推进时，例如文案、布局、资源、实现和 QA，使用
`suede-agent-teams` 处理大型设计工作。在设计工作改变共享组件、路由、身份验证、支付、分析、发布配置或已发布声明的真实性时，在上线关卡前使用
`suede-code-review`。对于可以直接检查、修补、渲染和验证的小型视觉或文案修复，则跳过两者。

## Suede UI 契约

在创建新界面、进行重大重新设计、构建可复用组件系列或开展设计系统工作之前，在实施前锁定设计契约：

- 受众、界面任务、主要操作和上线阶段；
- 间距比例、网格行为、断点和稳定尺寸；
- 色彩角色、语义状态、对比度要求，以及深色/浅色模式行为；
- 排版角色、层级限制、正文行宽和截断策略；
- 按钮、空状态、加载、错误和成功状态所使用的文案词汇；
- 资源来源、logo 使用、裁剪规则、截图状态和动效规则；
- 针对桌面端、移动端、无障碍和渲染证据的验收检查。

根据文案质量、视觉效果、色彩、排版、间距和体验状态检查结果。如果工作纯粹属于后端，或只是针对单个元素的狭窄修复，则只记录相关的契约项目，不要强行编写完整规格。

## 上下文检查清单

1. 确定界面范围：仓库/文件夹、路由、线上 URL、部署目标、分支、
   未提交的文件，以及相关本地文档。
2. 在存在时阅读仓库本地的 `AGENTS.md`、`CLAUDE.md`、`AI_HANDOFF.md`、`README.md`、
   `PRODUCT.md`、`DESIGN.md` 或任务文档。
3. 确定定位：
   - **品牌：**营销、发布、活动、公共页面、作品集、编辑内容。
   - **产品：**应用外壳、仪表板、工具、表单、设置、管理后台、工作流。
4. 描述具体使用场景：谁在使用、在哪里使用、处于什么光线下、承受着什么压力，以及他们接下来需要完成什么操作。
5. 在对质量做出判断之前，先检查当前渲染的 UI 在桌面端和移动端断点下的表现。

## 设计法则

数值规则——间距、字号比例、颜色、对比度、密度、动效和状态——位于 `references/design-laws.md` 中。在编写或评审实际样式时请阅读它。进行请求分流或确定工作范围时不需要阅读它。

## 设计系统使用体验

对于任何主要的 Suede 界面、可复用的应用外壳、发布系统或重要的组件系列，以最小但有用的保真度产出以下工件：

- **Token 映射：**颜色角色、字号比例、间距、圆角、阴影、动效、z 层级和语义化状态名称，存储在 `DESIGN.md` 或 `design-tokens.json` 中。
- **状态矩阵：**为每个涉及数据的组件定义默认、悬停、聚焦、激活、禁用、加载、空状态、成功、警告、错误和权限被拒绝状态。
- **文案词汇表：**统一整个产品的操作标签、Toast 文案、错误消息和空状态提示。
- **截图契约：**使用带有种子演示数据的命名状态，使营销、App Store、QA 和文档能够复现相同的视觉效果。
- **无障碍检查：**对比度、焦点顺序、触控目标、键盘操作路径，以及对减少动态效果的兼容性。
- **迁移说明：**说明仍然存在的旧样式、禁止触碰的内容，以及新工作如何采用该系统而不重写无关页面。

当某个设计令牌、组件、间距模式、颜色、字体处理方式或状态模式至少重复出现三次，或控制着高可见度界面时，提取一个设计系统问题。将偏差根因归类为令牌缺失、忽略令牌、组件缺口、内容压力、平台惯例或遗留债务。

对于范围广泛的设计系统审计，按以下方式评分：

```text
Color consistency: /10
Typography hierarchy: /10
Spacing rhythm: /10
Component consistency: /10
Responsive behavior: /10
Dark/light behavior: /10
Motion restraint: /10
Accessibility: /10
Information density: /10
Polish: /10
Total: /100
```

低于 70/100 表示系统正在失效：在该界面上为新功能设计样式之前，先修复得分最低的两个维度。审计报告中，任何得分为 4/10 或更低的维度都属于 P1 问题。

## 范围限制与例外

以下各项是不可妥协的要求，本列表具有最高权威性。
请引用本节，而不要在其他位置重复陈述某项限制。完整的限制清单（包括每种被禁止的模式、各项限制适用的范围、BEFORE/AFTER 替代方案，以及严格限定的允许例外）位于
`references/scoped-bans.md` 中。当某项设计选择看起来需要例外，或在评审某个例外是否确实合理时，请阅读该文件。

- **装饰性光球、散景色块、通用渐变网格背景。** 在主视觉后方放置三个 30% 不透明度的径向渐变，等同于没有艺术指导。应替换为一个明确的选择：噪点纹理、几何系统、真实产品截图、插画场景，或本身就是背景的排版组合。渐变网格、颗粒感和分层透明度在服务于某种具名美学时仍然合理；用纯 CSS 近似效果来代替艺术指导则不合理。
- **渐变文字。** `-webkit-background-clip: text` 彩虹或金属质感标题。应替换为一个全字重的高对比度标题，并搭配一个使用纯色的强调词。
- **装饰性玻璃面板。** 漂浮在渐变背景上的 `backdrop-filter: blur()` 卡片。应替换为使用正确层级 token 的不透明表面，并加上 1px 边框以明确边界。
- **将图标卡片网格作为页面结构。** 一个由图标、标题和一句说明组成的 3x2 网格，只是产品类别的堆砌，不是布局。应替换为映射用户实际操作的行或区块。
- **一阶类别配色。** “音乐工具，所以用深紫色。”“可观测性，所以用深蓝色。”仅凭产品类别就能猜到的调色板，是 Color 法则旨在拒绝的训练数据反射；深色背景上的低饱和青绿色，则是同一种失败的二阶版本。
- **虚假指标、虚假推荐语、虚假合作伙伴声明。没有例外路径。** 应替换为：(a) 带来源注释的真实统计数据，(b) 携带 `[NEEDS REAL DATA]` 标记的占位符，或 (c) 不依赖数字的结构性元素。

前五项允许基于来源保真度、平台惯例、可访问性、已确认的品牌系统或直接用户请求而作出范围明确的例外。说明该例外为何合理。最后一项没有任何例外。

## 文案规则

- 像产品运营者一样写作，而不是像宣传册。
- 每个标签都应命名一个动作，而不是一个类别。使用“注册作品”而非“注册”。使用“验证权利”而非“权利验证”。执行者始终是用户；对象始终应明确具体。
- 删除填充内容、模糊承诺和重复标题的表述。
- 在按钮、提示消息、空状态和确认消息中使用同一个动作名称。
- 错误信息必须说明发生了什么以及如何修复。
- 空状态应指向下一个具体操作，而不是笼统的“开始使用”。

## 美学方向

对于任何新界面或重大重新设计，在编写代码之前先确定清晰的美学方向。明确说出它。

色调范围。选择一种，并精确执行：
- **精致极简**：克制、留白、仅以字重作为强调、没有装饰
- **编辑风格**：强烈的排版层级、不对称、文字即结构、标题优先的布局
- **粗野主义**：原始网格、暴露的结构、高对比度、有意的反精致
- **复古技术风**：等宽字体、终端配色、扫描线纹理、系统 UI 参照
- **有机风格**：圆润形态、暖中性色、可触感纹理、柔和阴影
- **极繁主义**：以密度带来愉悦、分层元素、多个活跃字体、受控的混乱
- **精致奢华**：充裕留白、衬线字体层级、低饱和调色板、痴迷细节的工艺
- **产品实用主义**：信息密度、数据优先、紧凑控件、没有装饰性外壳

大胆的极繁主义和精致的极简主义都行得通。真正失败的是两者都不是：没有明确方向的设计会显得千篇一律。选定一种基调，并贯彻到底。

**令人难忘的因素**：每个主要界面都应该有一个值得被记住的设计动作。对于 Suede，这可能是权利台账、波形证明面板，或权属链时间线。对于其他公司，则应该是一个与主题原生相关的装置：只有对他们的产品来说才有意义的东西。在实现之前先把它命名出来。

**AI 垃圾检查**：在确定一种美学之前，先进行两项直觉测试：
1. 仅凭产品类别，就能猜出主题和配色吗（“可观测性 → 深蓝色”、“医疗 → 白色 + 青绿色”）？这就是第一层训练数据直觉。拒绝它。
2. 仅凭产品类别加上反向参考，就能猜出美学所属的家族吗？这就是第二层陷阱：避开了第一种直觉，却没有避开第二种。继续深入。

**主题句**：要足够具体地描述一个物理场景，让它迫使你得出设计答案。“一名录音室工程师凌晨 2 点在第二块显示器上审查一场权利争议”，会迫使你做出不同于“一个用户正在查看数据”的选择。如果这句话没有迫使你得出答案，就说明它还不够具体。继续添加细节，直到它能做到为止。深色与浅色都绝不是默认选项。不要因为工具使用深色看起来很酷就选深色，也不要为了稳妥而选浅色。

**背景与氛围**：当渐变网格、噪点纹理、几何图案、层叠透明效果、戏剧化阴影、颗粒叠加和装饰性边框服务于整体美学时，它们都可以作为合理的工具。什么时候这些东西是工具，什么时候它们成了艺术指导的替代品，将在“范围限定的禁用项与例外”中界定。

## 实现工作流

1. **扫描：**检查当前文件、样式、渲染后的 UI 以及路由行为。
2. **塑形：**必要时，编写一份简洁计划，明确颜色、字体、布局、动效、资源、文案和验证方面的决策。
3. **构建：**在本地架构内进行有针对性的编辑。不要进行无关的重构。
4. **渲染：**运行本地服务器或使用现有预览。在可行时，截取桌面端和移动端截图：`npx playwright screenshot <url>
   --viewport-size=1280,900 desktop.png` 和 `npx playwright screenshot <url>
   --viewport-size=390,844 mobile.png`；如果环境中有内置的预览/截图工具，也可以使用它。
5. **审查：**检查字体、间距、颜色、资源还原度、文案、无障碍、响应式行为、加载态、空状态、错误态、悬停态、聚焦态和激活态。
6. **验证：**运行相关的 lint、类型检查、测试、构建或针对性命令。文件发生变化时运行 `git diff --check`。在声称具备公开行为之前，验证实际 URL 或 API。
7. **交接：**对于有意义的工作，记录目标、变更文件、命令、验证结果、注意事项和下一步。

## 红旗——停止

如果出现以下任何想法，请停下来，运行你正准备跳过的检查：

- “代码看起来没问题，所以渲染出来也会没问题。”把它渲染出来。截图胜过代码检查。
- “这个改动太小，不值得做视觉质量检查。”一行 CSS 的改动就可能破坏移动端导航。检查桌面端和移动端。
- “这是音乐工具，所以用深紫色。”这是第一层的类别直觉。“范围限定的禁用项与例外”中会明确排除这种做法。
- “暂时使用占位指标没关系。”虚假数字会被直接交付。“范围限定的禁用项与例外”规定了三种允许的替代方案，不存在例外路径。
- “我记得参考设计是什么样。”在同一轮检查中对比源文件与实现，永远不要凭记忆比较。
- “我稍后再把令牌记下来。”未记录的令牌就是偏差的起点。现在就记下差距。

```text
Status: ship | ship-with-caveats | hold
```

当核心路径损坏、声明不实、截图与实现不匹配、无障碍问题阻塞主要操作，或无法验证线上路由时，使用 `hold`。仅当注意事项明确、非关键且对于当前发布阶段可接受时，才使用 `ship-with-caveats`。

`hold` 会停止工作。不要绕过它，不要将其降级为
`ship-with-caveats`，也不要继续打补丁。输出以下内容并等待：

```text
HALT: <the single blocker, named with file, route, or missing evidence>
Options:
1. <option>
2. <option>
3. <option, if a third is real>
Awaiting: which option to take
```

给出 2-4 个真实选项，而不是罗列所有选项。冻结的润色循环同样适用：当同一失败第三次重复出现时，以此格式暂停，而不是开启第四次尝试。

## 视觉 QA 报告

将源视觉目标与实现进行比较时，保存 `visual-qa-report.md`，其中包含：

- 源视觉真值的路径或 URL
- 实现的路径、URL 或截图
- 视口和状态
- 主题、身份验证状态、内容/数据状态以及交互状态
- 全视图比较证据
- 重点区域比较证据，或说明为何不需要
- 按 P0/P1/P2/P3 严重程度排序的发现
- 上一轮之后完成的补丁
- `final result: passed` 或 `final result: blocked`

在同一次视觉检查中比较源文件和实现，不要凭记忆比较。使用
`npx playwright screenshot <url>
--viewport-size=1280,900 impl.png`（使视口与源目标匹配）渲染实现，或者在可用时使用你所在环境内置的预览/截图工具。检查排版、间距/布局、颜色/令牌、图像和素材保真度、标志/图标、文案/内容、加载/空/错误/悬停/聚焦/激活状态、响应式表现、无障碍以及相关的动效。

当所需比较中的源文件或渲染产物缺失，或仍存在可采取行动的 P0/P1/P2 级布局、排版、颜色、素材、文案、无障碍、响应式、交互状态或源文件保真度问题时，使用 `final result: blocked`。仅当不存在可采取行动的 P0/P1/P2 级发现时，才使用 `passed`。

## 输出风格

先给出发现，再说明理由。指出文件和行号。对于构建任务，说明发生了什么变化并展示渲染证据。永远不要在面向用户的输出中提及内部流程步骤（preflight、task router）。

不要验证现有设计，也不要复述已经存在的内容。报告得分最低的维度和具体失败元素，或者说明不存在可采取行动的发现。用户亲自完成的内容不会让评分变得宽松；“它已经看起来不错”不是一个发现。
