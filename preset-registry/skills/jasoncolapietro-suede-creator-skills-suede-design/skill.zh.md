# Suede 设计

使用此 skill，使 Suede 界面呈现出经过深思熟虑、高级、清晰易读且充满活力的感觉，同时避免流于千篇一律的 AI 产出。它涵盖产品 UI、品牌界面、落地页、仪表盘、组件系统、响应式优化和视觉 QA。

**核心原则：**即使去掉 logo，界面仍必须让人一眼认出这是该产品，并且在声称其可用之前先渲染结果。

## 工作立场

- 基于当前源码和渲染后的屏幕开展工作。当仓库、在线 URL、截图或本地预览可供检查时，不要凭记忆进行设计。
- 对于 Suede 品牌，只能使用 `JasonColapietro/suede-creator-skills` 中的 `docs/assets/suede-ai-logo-transparent.png`（SHA-256 `83a7ee0317e4debe2e7b076c20ba067feb76a587f9e829dc6310ae4be4b44dfa`）。绝不重新绘制、描摹、近似、排版、重新着色、变形或生成替代版 Suede S。`suede-skill-icon.png` 是 Passport 图标，不是 Suede 品牌标志。如果批准的文件不可用或其校验和不一致，请停止并请求提供该文件；宁可省略标志，也不要自行臆造。
- Suede 的公开文案应围绕创作者所有权、可编程 IP、权利、溯源、由注册表支持的媒体、版税分配和代理商商务展开。不要将 Suede 简化为一个泛化的 AI 音乐应用。
- 优先使用现有的应用框架、设计令牌、组件、图标库和路由模式。只有在能够消除实际复杂性或符合既有本地模式时，才新增抽象层。
- 对于视觉工作，渲染结果。截图胜过代码检查。最低要求：桌面端宽度 1280px，移动端宽度 390px。对于 App Store 提交：1290×2796px（6.7 英寸）、1488×2266px（iPad Pro 13 英寸）。
- 要捕获渲染结果：`npx playwright screenshot <url> --viewport-size=1280,900 desktop.png`（将 viewport 替换为上面的移动端/App Store 尺寸；一次性设置：`npx playwright install chromium`），或者使用环境中可用的内置预览/截图工具。

在进行任何设计工作之前，先阅读界面上下文：
- 本地 `PRODUCT.md`：用户、品牌、语调、反向参考、战略原则
- 本地 `DESIGN.md`：颜色令牌、字体比例、组件清单、间距
- `AGENTS.md`、`AI_HANDOFF.md` 或 `README.md`：代理指导和界面上下文

如果主要界面缺少 PRODUCT.md 或 DESIGN.md，请记录这一点，并基于可用上下文继续工作。完成任务后，主动提出创建这些文件。

然后在工作更新中声明以下预检信息：

```text
SUEDE_DESIGN_PREFLIGHT: target=<repo-or-folder> surface=<route-or-url> register=<brand|product> context=<pass|partial|none> design_system=<loaded|not_found> git=<pass|skipped:reason> render=<pass|pending|skipped:reason>
```

此外，当工作涉及文案、设计系统、视觉 QA、Suedify、可见性或公开发布质量时，也要应用由 suede-workflow-skills 负责的共享无遗漏质量门禁
（需要从此 pack 安装 suede-workflow-skills。如果未安装，请根据此 skill 的 Implementation Workflow、Ship Gate 和 Visual QA Report 部分中的标准，运行 Copy Gate、Visual QA Gate、SEO/AEO/AI EO Gate、Design System Gate 和 Launch Gate 检查清单。）

## 任务路由

选择适合请求的最小路径。

- **明确的小修复：**检查当前 UI，进行范围最小的修改，验证渲染结果，
  并报告改动内容。
- **有歧义或全新的设计：**收集上下文，提出 2-3 种方案及其权衡，
  推荐其中一种，并在实施前获得批准。
- **大型重新设计：**先编写一份精简的形态简报：受众、页面任务、风格基调、
  场景、色彩策略、排版、布局、标志性时刻、约束条件和 QA 计划。
- **视觉系统工作：**在提出修改方案前，扫描当前 CSS、tokens、组件、间距、
  阴影、断点、图标使用情况和重复的 UI 模式。
- **从源稿到实现的 QA：**如果存在 mock、截图、Figma frame 或图像目标，
  并且还有已渲染的实现，则在交付前对两者进行视觉比较，并将 `visual-qa-report.md` 保存到项目根目录。
- **长时间的润色循环：**通过可见的检查清单进行迭代。如果同一问题反复出现，
  则暂停循环，将范围缩小到出现问题的单元，并使用明确的验收标准重新运行。

## 交付规范

在进行重要或大型的 Suede 设计工作之前，编写一份精简的交付契约：

- objective：用户可见的结果；
- surface：repo、route、live URL、branch 和 owner；
- done signal：截图、构建、测试、部署回读或评审产物；
- constraints：需要保留的 WIP、不可触碰的路由、尚未获批准的文案声明，以及发布/上线边界；
- lanes：哪些工作可以并行运行，哪些必须等待，以及每条 lane 产出什么。

不要因为代码发生了变化就认为工作已完成。只有在检查过 done signal，或明确说明剩余差距后，才能称工作完成。

当多个 lane 必须同时推进（例如文案、布局、素材、实现和 QA）时，使用 `suede-agent-teams` 进行大型设计工作。在 ship gate 之前，如果设计工作改动了共享组件、路由、auth、payments、analytics、release config 或已发布声明的真实性，请使用 `suede-code-review`。对于可以直接检查、修补、渲染并验证的小型视觉或文案修复，则跳过这两者。

## Suede UI 契约

在创建新 surface、进行重大重新设计、构建可复用组件系列或开展设计系统工作之前，先锁定设计契约，再开始实现：

- 受众、surface 的任务、主要操作和上线阶段；
- 间距尺度、网格行为、断点和稳定尺寸；
- 色彩角色、语义状态、对比度要求以及深色/浅色模式行为；
- 排版角色、层级限制、正文行宽和截断策略；
- 按钮、空状态、加载、错误和成功状态所使用的文案词汇；
- 素材来源、logo 使用方式、裁剪规则、截图状态和动效规则；
- 针对桌面端、移动端、可访问性和渲染证据的验收检查。

从文案质量、视觉效果、色彩、排版、间距和体验状态等方面评审结果。如果工作纯粹属于后端，或只是针对单个元素的狭窄修复，则仅记录相关的契约项，而不要强行编写完整规范。

## 上下文检查清单

1. 确定界面所在位置：仓库/文件夹、路由、线上 URL、部署目标、分支、
   未提交的文件，以及相关的本地文档。
2. 在存在时，阅读仓库本地的 `AGENTS.md`、`CLAUDE.md`、`AI_HANDOFF.md`、`README.md`、
   `PRODUCT.md`、`DESIGN.md` 或任务文档。
3. 确定使用的定位：
   - **品牌：** 营销、发布、活动、公共页面、作品集、编辑内容。
   - **产品：** 应用外壳、仪表盘、工具、表单、设置、管理后台、工作流。
4. 描述实际使用场景：谁在使用、在哪里使用、处于什么光线下、面临什么压力，以及他们接下来需要完成什么操作。
5. 在对质量作出判断前，先在桌面端和移动端断点检查当前实际渲染的 UI。

## 设计法则

数值规则——间距、字号比例、颜色、对比度、密度、动效、状态——位于 `references/design-laws.md` 中。在编写或审查实际样式时都应阅读该文件。仅进行请求分流或确定工作范围时，无需阅读。

## 组件来源

当构建工作需要本地系统所缺少的部分——基础原语、动画场景组件或 AI 聊天界面——请从 `references/ui-component-sources.md` 中经过审核的注册表获取，并在导入生效前执行该文件中的采用检查清单（优先本地、重新进行设计令牌化、动效法则、许可证级别、渲染验证）。导入组件时阅读该文件；审查或重新设计现有 UI 则无需阅读。

## 设计系统的易用性

对于任何重要的 Suede 界面、可复用的应用外壳、发布系统或重要组件族，以最低但足够有用的保真度产出以下工件：

- **令牌映射：** 颜色角色、字号比例、间距、圆角、阴影、动效、z 层级和语义状态名称，存储在 `DESIGN.md` 或 `design-tokens.json` 中。
- **状态矩阵：** 为每个涉及数据的组件定义默认、悬停、聚焦、激活、禁用、加载、空、成功、警告、错误和权限被拒绝状态。
- **文案词汇表：** 在整个产品中保持一致的操作标签、Toast 文案、错误消息和空状态提示。
- **截图契约：** 使用带种子数据的命名状态，使营销、App Store、QA 和文档能够复现相同的视觉效果。
- **无障碍检查：** 对比度、焦点顺序、触控目标、键盘操作路径和减少动效的合规性。
- **迁移说明：** 说明仍然存在的旧样式、不可修改的内容，以及新工作如何采用该系统而不重写无关页面。

当某个令牌、组件、间距模式、颜色、字体处理方式或状态模式重复至少三次，或控制着高可见性界面时，提取一个设计系统问题。将偏差的根本原因归类为令牌缺失、忽略令牌、组件缺口、内容压力、平台惯例或遗留负债。

对于广泛的设计系统审计，按以下标准评分：

```text
Color consistency: /10
Typography hierarchy: /10
Spacing rhythm: /10
Component consistency: /10
Responsive behavior: /10
Dark/light behavior: /10
Motion restraint: /10
Accessibility: /10
Information density: /10
Polish: /10
Total: /100
```

低于 70/100 表示系统存在故障：在该界面上设计新功能之前，先修复得分最低的两个维度。审计报告中，任何得分为 4/10 或更低的维度都属于 P1 问题。

## 有范围的禁用项与例外

以下禁用项是不可妥协的要求，此列表具有最终权威性。请引用本节，而不要在其他地方重复说明某项禁用规定。完整的图集（包括每种禁用模式、每项禁用所适用的范围、BEFORE/AFTER 替代方案，以及严格限定的允许例外）位于
`references/scoped-bans.md`。当某个设计选择看起来需要例外，或审查某项例外是否确实合理时，请阅读该文件。

- **装饰性光球、散景斑块、通用渐变网格背景。** 在英雄区后方放置三个 30% 不透明度的径向渐变，说明缺乏艺术指导。应替换为具体选择：噪声纹理、几何系统、真实的产品截图、插画场景，或本身就作为背景的排版组合。渐变网格、颗粒感和分层透明度在服务于某种明确命名的美学时仍然合理；用纯 CSS 近似来代替艺术指导则不行。
- **渐变文字。** 使用 `-webkit-background-clip: text` 制作彩虹色或金属质感标题。应替换为一个使用完整字重的高对比度标题，并将强调词设为纯色。
- **装饰性玻璃面板。** 在渐变背景上悬浮使用 `backdrop-filter: blur()` 的卡片。应替换为符合正确层级令牌的不透明表面，并加上 1px 边框进行定义。
- **以图标卡片网格作为页面结构。** 由图标、标题和一句简介组成的 3x2 网格，是产品类别堆砌，不是布局。应替换为与用户实际操作相对应的行或区段。
- **一阶类别配色。** “音乐工具，所以用深紫色。”“可观测性，所以用深蓝色。”仅凭产品类别就能猜出的配色，正是 Color 法则旨在拒绝的训练数据惯性，而深色背景上的低饱和青绿色则是同一种失败的二阶版本。
- **虚假指标、虚假推荐语、虚假合作伙伴声明。无例外路径。** 应替换为 (a) 真实数据及来源说明，(b) 带有 `[NEEDS REAL DATA]` 标记的占位内容，或 (c) 不依赖数字的结构性元素。

前五项允许出于来源保真度、平台惯例、可访问性、已确认的品牌系统或用户直接请求而设置有范围的例外。请说明该例外为何成立。最后一项不允许任何例外。

## 文案规则

- 像产品运营人员一样写作，而不是像宣传册一样写作。
- 每个标签都应命名一项操作，而不是一个类别。“登记作品”，而不是“登记”；“验证权利”，而不是“权利验证”。执行者始终是用户；对象始终应当具体明确。
- 删除填充内容、模糊承诺和重复标题。
- 在按钮、提示消息、空状态和确认信息中使用相同的操作名称。
- 错误信息必须说明发生了什么以及如何修复。
- 空状态应指向下一项具体操作，而不是泛泛地写“开始使用”。

## 美学方向

对于任何新界面或重大重新设计，在编写代码之前，先确定清晰的美学方向。明确写出该方向。

色调谱系。选择一种，并精准执行：
- **精致极简**：克制、留白，仅以重量感作为唯一强调，不加装饰
- **编辑风**：强烈的字体层级、不对称、将文本作为结构、以标题为先的布局
- **粗野主义**：原始网格、暴露的结构、高对比度、刻意拒绝打磨
- **复古技术风**：等宽字体、终端配色、扫描线纹理、系统 UI 参考
- **有机风**：圆润形态、温暖中性色、触感纹理、柔和阴影
- **极繁主义**：以密度为乐趣、层叠元素、多种活跃字体、受控的混乱
- **奢华精致**：充裕空间、衬线字体层级、低饱和配色、对细节近乎执着的工艺
- **产品实用主义**：信息密度优先、数据优先、紧凑控件、不添加装饰性外壳

大胆的极繁主义和精致的极简主义都行。失败模式是两者都不是：没有明确方向的设计会显得千篇一律。选择一种基调，并彻底贯彻。

**令人难忘的因素**：每个主要界面都应该有一个值得被记住的设计动作。对 Suede 来说，这可以是权利台账、波形证据面板，或权属链时间线。对其他公司来说，它应该是一种与主题原生的装置：只有对 THEIR 产品才有意义的东西。在实现之前先给它命名。

**AI 垃圾检查**：在确定审美方向之前，运行两项直觉测试：
1. 仅凭产品类别，别人能否猜出主题和配色（“可观测性 → 深蓝色”，“医疗 → 白色 + 青绿色”）？这就是第一阶训练数据直觉。拒绝它。
2. 仅凭类别加上反向参考，别人能否猜出审美所属的家族？这是第二阶陷阱：避开了第一反射，却没有避开第二反射。继续深入。

**主题句**：具体地描述一个物理场景，具体到足以迫使设计给出答案。“一名录音室工程师凌晨 2 点在第二显示器上审查一场权利争议”与“一个用户正在查看数据”会迫使你做出完全不同的选择。如果这句话没有迫使答案出现，那就还不够具体。继续添加细节，直到它能做到。深色与浅色都绝不是默认选项。不要因为工具使用深色看起来很酷就选深色，也不要为了保险而选浅色。

**背景与氛围**：渐变网格、噪点纹理、几何图案、分层透明效果、戏剧性阴影、颗粒叠加和装饰性边框，只要服务于整体审美，都是合理的工具。将这些元素作为工具，与将它们作为艺术指导的替代品之间的界限，详见 Scoped Bans And Exceptions。

## 实现工作流

1. **扫描：**检查当前文件、样式、渲染后的 UI 以及路由行为。
2. **构思：**必要时，围绕颜色、字体、布局、动效、素材、文案和验证决策，编写一份简明计划。
3. **构建：**在本地架构内进行范围收窄的编辑。避免进行无关的重构。
4. **渲染：**运行本地服务器或使用现有预览。在条件允许时，截取桌面端和移动端截图：`npx playwright screenshot <url>
   --viewport-size=1280,900 desktop.png` 和 `npx playwright screenshot <url>
   --viewport-size=390,844 mobile.png`；如果环境提供内置预览/截图工具，也可以使用。
5. **审查：**检查字体、间距、颜色、素材还原度、文案、无障碍、响应式行为、加载、空状态、错误、悬停、焦点和激活状态。
6. **验证：**运行相关的 lint、类型检查、测试、构建或专注于目标的命令。文件发生更改时运行 `git diff --check`。在声称具有公开行为之前，验证实时 URL 或 API。
7. **交接：**对于有意义的工作，记录目标、已更改的文件、命令、验证结果、注意事项和下一步。

## 红旗 — 停止

如果出现以下任何想法，请停下来，执行你正准备跳过的检查：

- “代码看起来没问题，所以渲染出来也会没问题。” 把它渲染出来。截图胜过代码检查。
- “这个改动太小，不值得做视觉 QA。” 一行 CSS 改动就可能破坏移动端导航。检查桌面端和移动端。
- “是音乐工具，所以用深紫色。” 这是第一层级的类别惯性反应。Scoped Bans And Exceptions 中会明确排除这种做法。
- “暂时使用占位指标没关系。” 虚假数字会被发布出去。Scoped Bans And Exceptions 中列出了三种允许的替代方案，并且不存在例外路径。
- “我记得参考效果是什么样。” 在同一轮检查中比较源文件和实现，绝不要凭记忆。
- “我稍后再把 token 记录下来。” 未记录的 token 正是偏差开始的方式。现在就记下差距。

## 发布门禁

对于发布页面、应用外壳、面向公众的营销界面、App Store 资源或
高可见度的仪表板工作，最后以简短的发布门禁结束：

```text
Surface:
Done signal:
Evidence:
Blockers:
Accepted caveats:
Next action:
Status: ship | ship-with-caveats | hold
```

当核心路径损坏、声明不实、截图与实现不匹配、无障碍问题阻碍主要操作，或无法验证线上路由时，使用 `hold`。仅当注意事项明确、非关键且对于当前发布阶段可以接受时，才使用 `ship-with-caveats`。

`hold` 会暂停工作。不要绕过它，不要将其降级为
`ship-with-caveats`，也不要继续打补丁。输出以下内容并等待：

```text
HALT: <the single blocker, named with file, route, or missing evidence>
Options:
1. <option>
2. <option>
3. <option, if a third is real>
Awaiting: which option to take
```

给出 2-4 个真实选项，而不是所有可能选项。冻结的润色循环同样适用：当同一失败第三次重复出现时，应使用此格式停止，而不是开始第四次尝试。

## 视觉 QA 报告

将源视觉目标与实现进行比较时，使用以下内容保存
`visual-qa-report.md`：

- 源视觉真实依据的路径或 URL
- 实现的路径、URL 或截图
- 视口和状态
- 主题、auth state、内容/数据状态和交互状态
- 全视图比较证据
- 重点区域比较证据，或说明为何不需要
- 按 P0/P1/P2/P3 严重程度排序的发现
- 上一轮检查后进行的补丁修改
- `final result: passed` 或 `final result: blocked`

在同一轮视觉检查中比较源文件和实现，不要凭记忆进行比较。
使用 `npx playwright screenshot <url>
--viewport-size=1280,900 impl.png`（使视口与源目标匹配）渲染实现，或者在可用时使用
你所在环境内置的预览/截图工具。检查排版、间距/布局、颜色/token、图像和资源的保真度、
logo/图标、文案/内容、加载/空状态/错误/悬停/聚焦/激活状态、
响应式表现、无障碍，以及在适用时的动效。

当所需比较中的源文件或渲染产物缺失，或仍存在可采取行动的 P0/P1/P2 级布局、排版、颜色、
资源、文案、无障碍、响应式、交互状态或源文件保真度问题时，使用 `final result: blocked`。仅当不存在仍需处理的 P0/P1/P2 级问题时，才使用 `passed`。

## 输出风格

先给出问题，再说明理由。注明文件名和行号。对于构建任务，说明发生了哪些变化，并展示渲染结果证据。不要在面向用户的输出中提及内部流程步骤（preflight、task router）。

不要为现有设计做验证，也不要复述已经存在的内容。报告得分最低的维度和具体失败元素，或者说明不存在可执行的问题。用户亲自制作的内容不会因此获得更高评价，"它看起来已经不错了"不算问题。
