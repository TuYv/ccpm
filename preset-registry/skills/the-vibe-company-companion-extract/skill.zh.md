识别可复用的模式、组件和设计令牌，然后将它们提取并整合到设计系统中，以实现系统化复用。

## 发现

分析目标区域，识别提取机会：

1. **找到设计系统**：定位你的设计系统、组件库或共享 UI 目录（用 grep 搜索 "design system"、"ui"、"components" 等）。了解其结构：
   - 组件组织和命名约定
   - 设计令牌结构（如有）
   - 文档编写模式
   - 导入/导出约定

   **关键**：如果不存在设计系统，请先询问再创建。先了解首选的位置和结构。

2. **识别模式**：寻找以下内容：
   - **重复的组件**：被多次使用的相似 UI 模式（按钮、卡片、输入框等）
   - **硬编码的值**：本应作为令牌的颜色、间距、排版、阴影
   - **不一致的变体**：同一概念的多种实现（3 种不同的按钮样式）
   - **可复用的模式**：值得系统化的布局模式、组合模式、交互模式

3. **评估价值**：并非所有内容都应被提取。考虑：
   - 它是否被使用了 3 次或更多，或者很可能被复用？
   - 将其系统化是否能提升一致性？
   - 它是通用模式，还是特定于上下文的模式？
   - 维护成本与收益如何权衡？

## 规划提取

制定系统化的提取计划：

- **要提取的组件**：哪些 UI 元素将变成可复用组件？
- **要创建的令牌**：哪些硬编码的值将变成设计令牌？
- **要支持的变体**：每个组件需要哪些变体？
- **命名约定**：与现有模式相匹配的组件名、令牌名、prop 名
- **迁移路径**：如何重构现有用法，使其使用新的共享版本

**重要**：设计系统是逐步增长的。提取当前明确可复用的内容，而不是提取所有将来某天可能可复用的内容。

## 提取与增强

构建改进的、可复用的版本：

- **组件**：创建设计良好的组件，具备：
  - 清晰的 props API 和合理的默认值
  - 适用于不同用例的恰当变体
  - 内置无障碍支持（ARIA、键盘导航、焦点管理）
  - 文档和使用示例

- **设计令牌**：创建的令牌应具备：
  - 清晰的命名（primitive 与 semantic）
  - 恰当的层级和组织
  - 对每个令牌使用时机的说明

- **模式**：为模式编写文档，包含：
  - 何时使用该模式
  - 代码示例
  - 变体和组合

**绝不**：
- 提取一次性的、特定于上下文的实现而不做泛化
- 创建过于通用以至于无用的组件
- 提取时不考虑现有设计系统的约定
- 省略恰当的 TypeScript 类型或 prop 文档
- 为每一个值都创建令牌（令牌应具有语义含义）

## 迁移

用新的共享版本替换现有用法：

- **查找所有实例**：搜索你已提取的模式
- **系统化替换**：更新每一处用法以使用共享版本
- **充分测试**：确保视觉和功能上的一致
- **删除死代码**：移除旧的实现

## 编写文档

更新设计系统文档：

- 将新组件添加到组件库
- 记录令牌的用法和取值
- 添加示例和指南
- 更新任何 Storybook 或组件目录

记住：一个好的设计系统是一个活的系统。在模式出现时就提取它们，用心地丰富它们，并始终如一地维护它们。
