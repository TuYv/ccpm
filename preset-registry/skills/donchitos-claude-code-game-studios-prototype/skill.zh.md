## 目的

这是一个**概念原型**——一个快速、用完即弃的构建版本，用于回答一个问题：
*“这个核心创意实际交互起来真的有趣吗？”*

**默认用途**——在运行 `/brainstorm` 和 `/setup-engine` 后立即运行此技能，然后再编写
GDD 或架构文档。它的结论将决定这个概念是否值得投入资源来编写完整的
设计文档。

**已经进入制作中期？** 你也可以在任何阶段运行此技能，以测试特定机制、
设计变更或技术问题。传入 `--spike` 可激活尖峰模式：一次
约 4 小时的轻量构建，无需以 GDD 为前提，也不会影响阶段门禁。

**已经完成 GDD 和架构设计？** 如果要在投入制作阶段之前验证完整的游戏循环，
请改为运行 `/vertical-slice`。

## 阶段 1：定义问题

确定审查模式（仅确定一次，并存储下来供本次运行中的所有门禁派生任务使用）：
1. 如果传入了 `--review [full|lean|solo]` → 使用该值
2. 否则，读取 `production/review-mode.txt` → 使用其中的值
3. 否则 → 默认使用 `lean`

**检查是否为尖峰模式：** 如果传入了 `--spike`，请跳到本技能底部的
**尖峰模式**部分。

否则，在继续之前使用 `AskUserQuestion` 确认意图：

- **提示**：“你希望如何使用本次原型会话？”
- **选项**：
  - `Prototype this concept` — 构建一个用完即弃的版本，在编写 GDD 之前验证核心创意是否有趣（1–3 天）
  - `Skip — concept already proven` — 我已有充分证据证明这个创意可行；记录下来并直接进入设计阶段
  - `Mid-production spike` — 我已经处于制作阶段，希望快速测试某个特定机制或技术问题（约 4 小时，不影响阶段门禁）

**如果选择 "Skip — concept already proven"：**
询问（使用纯文本，而不是控件）：“你有什么证据证明这个概念可行？”
记录单行回答，然后停止。注明：“已跳过概念原型——证据：
[回答]。”建议下一步：`/map-systems` 或 `/design-system [mechanic]`。

**如果选择 "Mid-production spike"**：跳到下方的**尖峰模式**部分。

**如果选择 "Prototype this concept"**：继续执行下方的阶段 1。

---

**关于原型策略的说明：** 关于成功独立游戏开发的研究结论高度一致——构建
2–3 个概念变体并让最佳方案胜出，远比持续迭代单个概念直至其可行
更有可能取得成功。这是你的第一个原型，但不一定是唯一一个。如果此原型得出
PIVOT 结论，请考虑是要完善此概念，还是围绕同一游戏创意
换一个不同的切入点重新开始，并为其制作原型。

**将游戏开发活动作为原型载体：** 如果你本来就计划制作概念原型，
可以考虑将其安排在游戏开发活动期间（Ludum Dare、GMTK Game Jam、Global Game Jam）。这类活动
会提供强制性的时间限制（48–72 小时）、让构建初期版本即时分发给数千名
玩家进行评分和评价，并通过设定截止时间从机制上防止范围蔓延。
许多已经发行的游戏（Celeste、VVVVVV）最初都是游戏开发活动原型。这并非必需——但
如果时机合适，值得考虑。

从参数中读取概念描述。在构建任何内容之前，先定义这个原型必须回答的**可证伪假设**：

> *“如果玩家[做了 X]，他们会感到[Y]——如果出现[可衡量的信号 Z]，我们就能确认这一点。”*

好的示例：“如果玩家使用抓钩摆荡，移动会让人感觉流畅——如果玩家在上手后 2 分钟内能连续摆荡 3 次以上且不停顿，我们就能确认这一点。”

不好的示例：“这玩起来有趣吗？” ← 不可测试，也不可证伪。

**如果概念过于模糊，无法形成假设，就在这里停止。** 请用户缩小问题范围后再继续。没有明确问题的原型只会浪费时间。

还要问：**“这个概念中风险最高的假设是什么？”** 这是原型首先应该测试的内容——不是最容易的部分，而是风险最高的部分。

## 阶段 3：选择原型路径

选择原型路径。如果传入了 `--path [html|engine|paper]`，就使用指定的路径。否则，先参考以下速查表，然后阅读下方各路径的完整说明：

| 类型 | 推荐路径 | 关键原因 |
|-------|-----------------|------------|
| 平台跳跃 / 动作 / 格斗 | **引擎** | 操作手感本身就是假设；浏览器延迟会产生错误结果 |
| 竞速 / 体育 | **引擎** | 原因相同——时机与物理反馈就是重点 |
| 俯视角射击 / 双摇杆射击 | **引擎** | 瞄准手感对时机十分敏感 |
| 谜题（逻辑） | **HTML** 或 **纸面** | 时机不是重点；逻辑和清晰度才是 |
| 卡牌游戏 | 优先使用**纸面** | 在编写代码之前，手动迭代速度最快 |
| 叙事 / 视觉小说 | **纸面**（Twine / Ink / Yarn Spinner） | 故事就是机制——无需承担代码开销即可进行测试 |
| 策略 / 4X / 城市建造 | **纸面**（电子表格模拟） | 在构建之前验证经济与成长规则 |
| Roguelike（重系统） | **纸面** → **引擎** | 在构建之前验证规则集是否有趣 |
| 放置 / 点击 / 增量 | **HTML** | 回合制逻辑，不要求对操作手感敏感 |
| 音乐节奏游戏 | 优先使用**纸面**（在音频中设计关卡） | 在引擎存在之前先设计关卡 |
| RPG / 开放世界 | **纸面** → **引擎** | 系统复杂度高：先验证规则，再验证手感 |
| 恐怖 / 氛围类 | **引擎** | 氛围需要真实渲染 |

**经验法则：**“这感觉对吗？”→ 引擎。“这些规则有趣吗？”→ 纸面。“这个逻辑正确吗？”→ HTML 或纸面。

### 路径：HTML（可在浏览器中游玩）

**最适合：**谜题游戏、卡牌游戏、回合制策略、文字游戏、放置游戏、俯视角逻辑游戏。适用于任何不要求精确时机的游戏。

**可靠性：**一次成功率约为 85–90%。智能体会编写一个独立、完备的 HTML 文件，用户可直接在浏览器中打开——无需安装。

**局限性——浏览器延迟会让游戏手感产生误导。** 浏览器会引入
50–133ms 的渲染时间波动。因此，对于动作游戏、平台游戏、格斗游戏，或任何旨在测试输入时机、
跳跃弧线或碰撞手感的游戏，HTML 原型从根本上并不可靠。如果要验证的假设是手感，
请改用引擎路径。

**此路径的替代工具：** PICO-8（限制极强，非常适合复古
街机概念，只需一条命令即可导出到 Web）、Phaser.js（功能更强的浏览器游戏
框架，仍然无需安装）或 Twine（叙事/选择型游戏）。
对于各自适用的类型，这些工具比原生 HTML 更快——如果合适，请建议使用它们。

**输出：** 单个 `prototype.html`（或对应的 PICO-8/Phaser 文件），用户可在任意浏览器中打开。

**分发——HTML 路径的最大优势：** 与引擎原型不同，此
构建版本可以在几分钟内触达全球的真实玩家。请积极利用这一点：
- **itch.io**——上传文件、分享链接，即可在数小时内获得游玩次数和文字反馈。
  免费。这里的独立游戏社区会试玩粗糙的构建版本，并不会期待成品级的打磨。
  这是零成本的真实外部验证。
- **Loom + 文件共享**——通过 Google Drive/Dropbox 分享，并请他人在游玩时使用 Loom 录制
  屏幕和音频。无需同步安排时间，你就能获得记录真实第一印象、
  反应和困惑的视频。
- **r/playmygame 或 r/WebGames**（Reddit）——活跃的社区，专门
  测试早期构建版本并主动提供坦诚反馈。
- **游戏开发 Discord 服务器**（GMTK、Brackeys、GameDev.tv）——成员经常互相测试
  原型；请他人测试一个 HTML 文件是门槛最低的请求。

---

### 路径：引擎（引擎项目）

**最适合：** 动作游戏、平台游戏、重度物理游戏，以及任何将
即时操作手感本身作为待验证假设的游戏。当 HTML 延迟会使结果产生误导时，请使用此路径。

**可靠性：** 一次成功率约为 50–60%。预计需要进行 2–4 轮迭代——这很
正常，并不代表失败。

**局限性——要求已安装并运行引擎。** 此路径是一个
多轮协作循环：
1. 代理编写代码
2. 用户在引擎中运行代码
3. 用户报告错误或观察结果
4. 代理修复并迭代

**沉没成本规则：** 如果用户已经迭代超过 2 小时，却仍未
达到可玩状态，请停止。范围过大，或问题本身有误。
重新定义假设并大幅简化，或切换到纸面路径。

**输出：** 位于 `prototypes/[name]-concept/` 中的最小可运行引擎项目。

**更轻量的替代方案——Love2D (Lua)：** 如果为了制作一个一次性构建版本而启动项目引擎（Godot、Unity、Unreal）
显得过于繁重，可以考虑 Love2D——这是一个极简 2D
框架，几分钟即可安装，无需搭建项目脚手架，并且采用
原生渲染，不存在浏览器延迟。许多独立开发者使用它快速制作 2D 动作游戏和
平台游戏原型（Balatro 使用 Love2D 制作原型；Nuclear Throne 的早期构建版本
也使用了它）。其开销介于 HTML 和完整引擎之间：比
打开浏览器更繁重，但比搭建完整的引擎项目更轻量。最适合在项目引擎以 3D 为主，
或配置项目引擎需要花费大量时间时，用于验证 2D
动作游戏/平台游戏的手感。

---

### 路径：纸面原型（规则文档 + 游玩记录）

**最适合：** 策略游戏、卡牌游戏、桌游式机制、经济系统、成长循环，以及任何逻辑可以手动模拟的游戏。
当你需要验证的是规则而非手感时，适用于任何类型。

**可靠性：** 100%。无需代码、无需引擎、无需安装。

**局限性——无法验证每时每刻的操作手感。** 纸面原型可以证明规则在内部逻辑上自洽，且决策具有趣味性。
但它无法告诉你跳跃的手感是否恰当，也无法判断爆炸效果是否令人满足。

**纸面原型试玩观察流程（由 5 人以上参与执行）：**
1. 只讲解一次规则。把规则摘要表交给他们，然后退到一旁。
2. 不要进一步解释。不要提供帮助。不要澄清。困惑本身就是数据。
3. 静静观察。记录他们每一次放慢速度、重新阅读或提出问题的时刻。
4. 试玩结束后，只问一个问题：“哪里让你感到困惑？”——不要问“你喜欢吗？”
5. 每轮迭代都使用新的测试者。同一个人无法再次提供新的第一印象数据。
6. 如果 3 名以上的测试者在同一个地方感到困惑，说明这条规则存在问题——重新设计后再进行测试。

**输出：** 一份可打印的规则文档 + 一份完整的游玩记录，展示一次模拟试玩过程。

**此路径适用的叙事工具：** 对于侧重对话和剧情驱动的游戏，请跳过通用规则文档——改用专门的叙事脚本工具：
- **Twine** —— 零代码超文本互动小说工具；非常适合试验分支结构和测试选择的影响
- **Ink** (Inkle) —— 在 *80 Days*、*Heaven's Vault* 和 *Overboard* 中使用的纯文本脚本语言；可直接导出至 Unity 和 Godot
- **Yarn Spinner** —— 在 *A Short Hike*、*DREDGE* 和 *Night in the Woods* 中使用的对话脚本工具；可原生集成 Unity 和 Godot

这三种工具都能让你在几分钟内编写和试玩分支对话。叙事原型的关键指标是：
**触发第一个情感节点所需的时间**——需要经过多少轮对话，玩家才会产生某种感受？如果超过 3–4 轮对话，说明开场节奏太慢。

---

评估哪条路径最符合该假设，然后使用 `AskUserQuestion`，并预先说明你的建议：

- **提示词**：“你想使用哪种原型路径？（根据你的概念，我建议选择 [path]——[用一句话说明原因]。）”
- **选项**：
  - `HTML — browser prototype` —— 适用于益智、卡牌、回合制、策略和放置类游戏。双击即可打开，无需安装。可靠性为 85–90%。**不适合动作游戏**——浏览器延迟会对手感造成误导。
  - `Engine — native prototype` —— 适用于动作、平台跳跃、物理类游戏，或任何将手感本身作为待验证假设的游戏。单次成功率为 50–60%；通常需要进行 2–4 轮迭代。需要安装引擎。
  - `Paper — rules document + play log` —— 适用于策略、经济、逻辑和桌游式机制。可靠性为 100%。无法验证手感。

## 阶段 4：规划原型

用 3–5 个要点定义最小可行原型：

- 可证伪的假设是什么？
- 风险最高的假设是什么——这个原型如何优先对其进行测试？
- 要回答这个问题，绝对最低限度需要哪些内容？
- 明确排除哪些内容？（菜单、存档系统、错误处理、打磨、架构——全部排除）

**范围限制：** 概念原型只测试一种机制——而不是整个游戏。
如果范围涵盖多种机制，请缩减范围。如有疑问，就进一步缩减。

在构建之前，先向用户展示此计划。获得确认后再继续。

确认后，将会话检查点写入 `production/session-state/active.md`
（如果 `production/session-state/` 不存在，则创建该目录）。包括：概念名称、
假设、所选路径、范围要点，以及当前阶段（“阶段 5——
实现”）。这样一来，如果会话在构建过程中结束，下一个会话就能继续进行，而无需从头开始——
这对于需要多天完成的引擎路径工作尤其重要。

## 阶段 5：实现

询问：“我可以在 `prototypes/[concept-name]-concept/`
创建原型目录并开始实现吗？”

如果可以，则创建该目录。每个文件都必须以下列内容开头：

```
// PROTOTYPE - NOT FOR PRODUCTION
// Question: [Core question being tested]
// Date: [Current date]
```

这里特意放宽了标准：

- 可以随意硬编码值
- 使用占位资源（彩色矩形、调试图形）
- 完全跳过错误处理
- 使用能实现目标的最简单方法
- 复制代码，而不是从生产代码中导入
- 不要架构，不要模式，不要抽象

**不要添加润色内容。** 不要添加菜单、游戏结束画面、音乐或教程文本，
除非教程本身就是要测试的机制。任何超出
假设范围的添加都是浪费。

**试玩测试提示：** 如果你能找到任何没见过这款游戏的人——
朋友、家人或网上的陌生人——观察他们在没有讲解的情况下游玩，
会比自己测试获得好得多的信号。安静地观察，不要引导他们。
困惑就是数据。结束后只问一个问题：“哪里让你感到困惑？”而不是“你
喜欢它吗？”

**没有外部测试者可用？** 采用轮换方式：如果你构建了系统 A，那么对于
系统 B 来说，你就是一名没有先入之见的测试者。这种方式非常适合两人团队。独立开发者？
先离开 2-3 天，然后再以全新的状态试玩——虽然你无法获得完美的第一印象
信号，但可以发现最严重的阻碍。另一个选择是：把自己的
原型当作速通游戏来玩（强迫自己在 5 分钟内完成，期间不停下来
修复问题）——你感受到的阻力，也正是陌生玩家会遇到的阻力。

**想获得更细粒度的 UX 数据？** 让测试者在游玩时**大声说出思考过程**——
实时描述他们的想法：“我正在按空格键……什么也没发生……这是
跳跃键吗？”这样可以在困惑发生的那一刻将其暴露出来，而不是
等到试玩后的复盘。最适合测试 UI/UX 和上手引导的清晰度。无声
观察仍然更适合测试原始手感；大声思考会稍微改变人们的
游玩方式，但能提供丰富得多的数据，帮助你了解他们为何困惑。

**HTML 原型？** itch.io、Reddit（r/playmygame）和 Discord（GMTK、Brackeys）
可以让你今天就零成本接触到陌生玩家——请参阅上方
HTML 路径部分中的分发选项。

**想在编写代码之前测试 AI、NPC 或复杂系统的行为？** 使用
**绿野仙踪**技术：一个人正常游玩，另一个人则在幕后实时
控制 NPC、敌人或系统行为——做出人类会做的决定，而不是由算法决定。
玩家会以为这些行为是自动生成的。这样一来，你无需编写任何
寻路或决策树代码，就能验证 AI 设计的*体验是否正确*。通过观察人类
控制者自然而然做出的反应，你可以准确了解 AI 需要做什么。

### 引擎路径：多轮循环

编写初始代码后：

> “原型文件已编写完成。现在请在你的引擎中运行项目。
> 如果出现错误，请将错误粘贴到这里，我会修复。如果项目能够运行，
> 请描述你看到的内容，以及你是否觉得它正在回答那个问题。”

持续迭代，直到原型可玩。每轮循环：
1. 用户运行 → 报告错误或观察结果
2. 智能体修复错误或调整机制
3. 重复上述步骤，直到原型可玩或触发沉没成本规则

### HTML 路径：单文件输出

将单个 `prototype.html` 写入 `prototypes/[concept-name]-concept/`。将
所有样式、逻辑和资源内联到文件中。该文件必须能够通过双击直接打开，
无需服务器。

### 纸面路径：文档 + 日志

编写 `prototypes/[concept-name]-concept/rules.md`（游戏规则）和
`prototypes/[concept-name]-concept/play-log.md`（模拟游戏过程，逐步演示
一个完整的游玩循环，并叙述掷骰结果、决策和结果）。

## 阶段 6：试玩复盘

原型已经构建完成。现在将它交给用户，并记录他们的实际体验。
不要跳过这一步直接生成报告——报告的质量完全取决于你在这里收集到的
观察结果。

**对于 HTML 路径：** 完全按照以下内容说：
> “原型已经准备就绪。请在浏览器中打开 `prototypes/[name]-concept/prototype.html`
> 并进行试玩。你可以花任意长的时间。不要匆忙完成——请尝试像一名新玩家那样
> 对待它。完成后回到这里。”

**对于引擎路径：** 多轮迭代循环已经记录了错误和行为。现在询问总体评价：
> “既然它已经能够运行——请像玩家而不是开发者那样多玩几次。
> 等你对它形成整体感受后再回来。”

**对于纸面路径：** 完全按照以下内容说：
> “阅读 `prototypes/[name]-concept/rules.md`，并像第一次游玩一样
> 按照 `play-log.md` 中的流程进行。如果附近有人，请尝试和他们一起
> 按规则游玩。至少看完一个完整的游玩循环后再回来。”

用户返回后，**一次只问一个**以下问题——等待用户回答后，再询问下一个：

1. **假设检验：**
   > “假设是：[重述阶段 1 中的假设]。它是否经受住了检验——
   > CONFIRMED、PARTIALLY CONFIRMED 还是 REFUTED？告诉我你观察到了什么。”

2. **最佳时刻：**
   > “如果有的话，在哪个时刻你觉得它开始奏效了？请具体说明。”

3. **最糟糕的时刻：**
   > “最令人沮丧、困惑或感觉出问题的时刻是什么？请具体说明——
   > 不要只说‘感觉很慢’，而应说‘跳跃操作大约需要半秒才有响应，
   > 感觉像是在和操作方式较劲’。”

4. **意外情况：**
   > “是否发生了任何你没有预料到的事情——无论好坏？”

5. **结论：**
   > “PROCEED、PIVOT 还是 KILL——并用一句话说明原因。”

收集完所有回答后，再开始生成报告。如果任何回答含糊不清
（“感觉还行”“相当不错”），请追问：“能否说得更具体一些？
究竟是哪些方面让你觉得还行？”精确的观察结果能让报告变得有用。
含糊的观察结果则会让报告毫无价值。

## 阶段 9：总结与后续步骤

输出总结：假设、结果和最终建议。
链接到 `prototypes/[concept-name]-concept/REPORT.md`。

**如果为 PROCEED：**
你的概念原型已经验证了核心创意。现在应根据刚刚获得的经验，对其进行妥善设计。

建议路径（按顺序）：
1. `/design-review design/gdd/game-concept.md` —— 根据原型揭示的结果验证概念文档
2. `/gate-check` —— 确认是否已准备好进入系统设计阶段
3. `/art-bible` —— 定义视觉识别（可选，但值得在编写 GDD 之前完成）
4. `/map-systems` —— 将概念拆分为所有游戏系统
5. `/design-system [mechanic]` —— 为每个 MVP 系统编写 GDD；在调节参数和公式章节中使用原型所得经验
6. `/review-all-gdds` —— 检查跨系统一致性

**注意：**如果你使用了 HTML 路径，但对手感仍不确定，请考虑在编写 GDD 之前，快速运行一个以手感为目标的引擎路径原型。

**如果为 PIVOT：**

在转入下一个原型之前，记录需要延续到后续版本的说明。逐个询问以下两个问题（使用纯文本）：

1. “这个原型中具体有哪些有效之处，是我们应在下一个版本中保留的？”
2. “最重要的一项改动是什么？”

询问：“我可以将其写入 `prototypes/[concept-name]-concept/PIVOT-NOTE.md` 吗？”

如果可以，则写入该文件，内容包括：原始假设、要保留的内容、要更改的内容，以及下一个原型的修订后假设。下次运行 `/prototype` 时，检查 `prototypes/` 中是否有任何 `PIVOT-NOTE.md` 文件——如果找到，则读取这些文件，并使用修订后的假设作为起点，而不是从头形成假设。

- 运行 `/prototype [revised-concept]` 以测试调整后的方向
- 或者，如果概念需要更根本性的重新思考，运行 `/brainstorm [hint]`

**如果是 KILL：**

在继续之前，运行以下检查，以确认该结论是合理判断，而不是一时受挫：

- [ ] 经过 2 次以上试玩后，测试者仍不清楚核心机制？
- [ ] 所有场次中都没有观察到“有趣时刻”（微笑、大笑或主动重试）？
- [ ] 对同一概念进行了 3 次以上 PIVOT 迭代，但没有明显改进？
- [ ] 该概念只有在进行大量解释或由开发者引导玩家时才能成立？
- [ ] 构建它让人觉得是在完成义务，而不是令人兴奋？

如果有 2 项以上适用 → KILL 结论合理。如果只有 0–1 项适用 → 在终止之前，考虑再进行一次有针对性的 PIVOT。

**将终止记录到 `prototypes/GRAVEYARD.md` 中**（如果该文件不存在，则创建）。
询问：“可以将这个概念追加到 `prototypes/GRAVEYARD.md` 吗？”如果可以，添加一条记录：

```
## [Concept Name] — YYYY-MM-DD
- **Kill reason:** [specific blocker — not "it was boring" but "players never understood the core action"]
- **What worked:** [2-3 things worth carrying forward to future concepts]
- **What failed:** [the specific mechanic, design decision, or scope issue]
- **Next time:** [one explicit action to try differently on a similar concept]
```

该文件的存在是为了避免在下一个概念中再次犯同样的错误。

- 运行 `/brainstorm open` 或 `/brainstorm [new-hint]` 以探索不同的概念
- 原型报告即为交付成果——无需采取进一步行动

## Spike 模式

**触发方式：** 使用 `--spike` 标志，或在阶段 1 中选择“制作中期 Spike”入口。

**目的：** 在制作过程中测试某个具体的技术或设计问题，而无需承担完整概念原型工作流的开销。不要求具备 GDD 前置条件。不会影响阶段门禁。硬性时间上限：约 4 小时。

**适用场景：**
- 你正处于制作阶段，并希望测试是否应添加新机制
- 在正式构建某项技术方案之前，你不确定该方案是否可行
- 正在考虑一项设计变更，并希望快速进行变更前后的对比
- GDD 中的某个系统实现难度超出预期，而你希望先对困难部分制作原型
- 在编写游戏玩法代码之前，你需要确认目标硬件能否维持所需帧率（**性能 Spike**——见下文）

**Spike 模式工作流（替代阶段 1–9）：**

1. **定义 Spike 问题**（使用纯文本，而不是微件）：“这个 Spike 要回答哪个具体问题？请用一句话回答：‘我们能否使用 [approach Y] 来 [do X]？’”

2. **选择路径**——使用与阶段 3 相同的 AskUserQuestion 微件（HTML / Engine / Paper）。

3. **确定范围**——最多 2–3 个要点。仅限一个机制、一个技术问题，除此之外不要包含任何内容。

4. **构建**——采用与概念原型相同的宽松标准。硬性时间上限：4 小时。如果无法在 4 小时内完成可演示成果，说明问题范围过大。请将其拆分。

5. **观察并决策**——无需进行正式的试玩复盘。询问：“这个 Spike 回答了问题吗？回答 YES 或 NO，并用一句话说明原因。”

6. **编写 Spike 说明**（不是完整报告）并保存到 `prototypes/[concept-name]-spike-[date]/SPIKE-NOTE.md`：
   - 测试的问题
   - 结果（YES，可以实现 / NO，无法实现 / PARTIAL——需要进一步调查）
   - 下一步操作（加入当前冲刺 / 进一步调查 / 放弃该想法）

7. **更新 `production/session-state/active.md`**，清除探索状态并返回当前冲刺状态。

**无需 CD 门禁。无需阶段门禁。无需 PROCEED/PIVOT/KILL。** 探索结果为决策提供信息，但不直接做出决策。开发者根据探索所揭示的结果，决定是否将该机制/方法加入冲刺待办事项。

**性能探索（特殊情况）：** 如果游戏涉及高负载渲染——
大型开放世界、数百个同时运行的物理实体、大量粒子系统、
复杂着色器——请在编写玩法代码之前进行性能探索，以确认
目标硬件能够维持所需的帧率。它与其他探索有两点不同：
- 要回答的问题是“引擎能否在[最低配置硬件]上以 60fps 渲染[场景 X]？”
  而不是“这个机制体验好吗？”
- 输出是基准测试数值，而不是体验结论
- 不需要任何玩法逻辑——只需让预期的最大场景负载（地形、绘制
  调用、物理对象、粒子）同时运行
- 构建时间仍需控制在约 4 小时的上限内；此次探索的工作是搭建渲染
  负载，而不是制作游戏
- 如果在此范围内答案为 NO，那么这就是一个会影响所有后续工作的架构或范围约束
  ——最好现在就将其暴露出来，而不是等到 Sprint 8

### 重要约束

- 原型代码绝不能从生产源文件中导入任何内容
- 生产代码绝不能从原型目录中导入任何内容
- 如果建议为 PROCEED，则生产实现必须从头编写——绝不能将原型代码重构为生产代码
- 总投入严格限制为 1 天（概念原型只测试一个机制）
- 只测试一个机制——如果范围扩大，请停止并简化问题
- 不做润色。不要菜单，不要游戏结束流程，不要音乐，不要 UI，除非它本身就是要测试的机制
- 如果进行了 2 小时的引擎迭代后仍陷入困境，请重新定义问题或更换路径
- **3 次 PIVOT 迭代 → 强制做出 KILL 决策。** 如果同一个概念已经是第三次
  得出 PIVOT 结论，那么这个概念很可能行不通。
  问问自己：“这是正确的想法，还是我陷入了沉没成本陷阱？”从头对一个新概念
  制作原型，几乎总会优于对一个举步维艰的概念进行第四次迭代。
- 构建 2-3 个不同的概念变体并从中选出最佳方案，是一种比将同一个概念
  反复迭代到极致更健康的策略。原型之间的自然选择
  胜过单纯依靠意志力。
- **联网/多人游戏：** 本地原型无法验证联网机制的实际体验。
  延迟会从根本上改变战斗、移动和预测的体验——一个在本地 0ms 延迟下运行的原型，
  与在 80ms 网络延迟下的体验会截然不同。使用本地原型验证该机制是否
  *有趣*。不要将其作为该机制在真实网络
  条件下*体验良好*的证据。网络体验需要真实对等端或模拟延迟（例如限速
  工具、网络状况模拟器）。
