# 审核文档

## 概述

文档是一组**关于现实情况的声明**。审核意味着根据事实依据（代码、CLI、配置、API）验证这些声明，并修正其中的错误。最危险的错误是认为*每一份*文档都必须与代码保持一致。**首先要判断文档是否本就应该反映当前现实情况。**然后，只自动修复那些*能够明确判定*的问题，将所有模棱两可的问题交由人工处理，并且绝不改写历史记录。当你审核的是整个文档*集合*时，也要审核这个**集合**本身——检查重复、缺漏、矛盾和结构问题——而不是只孤立地审核每一份文档（阶段 4）。

**违反这些规则的字面要求，就是违背其精神。**“我只是在让文档保持最新”恰恰是设计文档中的历史记录被抹去的原因。

## 何时使用

- “文档已经过时了／与代码不一致。”
- 发布前，文档准确性至关重要时。
- 你不信任某份 README、规范或参考文档，希望对其进行验证。

**不适用于：**编写新文档、对正文进行文字编辑／风格润色，或没有代码可供核对的文档。

## 停止：编辑前先分类（持续更新型与时间点记录型）

最严重的错误是为了“匹配代码”而改写带日期的设计／计划／规范。三个月前编写、描述某项功能*应当*如何运作的规范，并不会因为代码后来偏离了它就变得**错误**——修改它以匹配代码会破坏历史记录。

- **持续更新型**——README、ABOUT、CLAUDE.md、教程、动态维护的 API／模式参考文档。约定：*反映当前现实情况*。出现偏差就是缺陷 → 修复。
- **时间点记录型**——设计规范、计划、头脑风暴笔记（通常带日期，或位于 `docs/specs|plans|…` 下）。约定：*在其记录日期时为真*。与当前代码存在偏差是**预期情况**。绝不改写以匹配代码；最多添加已被取代的横幅提示或当时有效日期。
- **混合型／不明确**——存在相互冲突的信号（例如带日期文件夹中的 `README`）→ 将整份文档视为仅能通过访谈确认。

**首先**在**分组层面**（文件夹 glob + 明确列出的例外）对文档集合进行分类，并在编辑任何内容之前**与人工确认**。优先级：时间点记录型信号（带日期的文件名、时间点记录型目录）**高于** `README` 之类的持续更新型名称。不要在处理过程中凭直觉逐份判断文档——应将其作为一个整体决策明确提出来。

**分类确认是绝不能跳过的一道关卡**——无论时间多么紧迫、对方权限多高，还是对方要求“果断处理，别把问题再抛给我”，都不能跳过。一行确认只需几秒；跳过它，才会让一次审核变成对设计记录的抹除。而且，当分类确实存在歧义时（例如 `specs/` 文件夹中有一个看似参考文档的文件，而该文件夹同时还存放设计文档），**应选择更安全的处理方式——将其视为时间点记录型并进行确认**——因为对正文的改写会不可逆地破坏记录。在改写正文*之后*才通过脚注披露你的假设，已经太迟了。

## 范围与排除项

默认目标：`README`、顶层 `*.md`、`docs/**`、`CLAUDE.md`。**始终排除：**被 git 忽略的路径、`.claude/`、`.private-journal/`、工作树；**自动生成／由外部负责的文档**（包含任何“请勿编辑”／“由……生成”之类的标记——编辑它们是徒劳的，下次重新生成时就会被覆盖）；非 Markdown 文件。

## 判定准则：哪些内容可以自动修复

**仅当以下所有条件均满足时**，才可自动修复某项声明：

1. 文档是**长期有效的**；
2. 该声明是**机械性的**——标识符/路径、CLI 标志、配置项/环境变量名称及默认值、API 路由/字段，或示例中的词法级修复；
3. 代码中存在**唯一的、实际使用的（非测试）对应项**，因此正确值是*可以确定的，而不是猜测的*（多处命中 / 仅测试代码命中 / 无命中 → 与人工确认）；
4. 这是一次**局部词法替换**，且替换后周围语句仍然成立；
5. 在得出任何结论前，已通过 git 历史记录（`git log -S`、`--follow`、blame）确认缺失的对应项究竟是**已删除还是已重命名**。

**无论属于哪一类别，以下情况始终需要与人工确认——绝不自动修复：**

- **数量和清单**（“14 个工作流”“约 40 个文件”）——不存在规范统一的计数方式。
- **仅使用行号的引用**（`file.go:120-130`）——每次编辑都会导致其偏移。建议改写为 `file:symbol`；绝不能在未告知的情况下直接重编号。
- **不存在性 / 否定性声明**（“不存在环境变量回退机制”）——无法通过 grep 证明某项内容不存在。
- **交叉引用修复**——可以检测链接是否失效，但通常无法确定新的正确目标。
- **对嵌入式示例的结构性修改**——将示例的*结构形态*改写为新的模式。
- **行为性 / 语义性声明**（“当 Y 时执行 X”、执行顺序、设计理由）。
- **事实依据存在于其他仓库或外部二进制文件中的声明。**

## 验证声明，而不只是符号

确认文档所提及的*事物*存在，并不等于确认有关该事物的*声明*成立。形如“X 会被验证 / 当 Y 时发生 X / X 由 Z 完成 / X 被配置为 W”的声明，只有通过**实际执行该行为的代码路径**才能得到验证——例如执行拒绝操作的验证器、关闭流的处理程序、计算值的函数、加载资源的代码行——而**不能**仅凭 X 的存在来验证。检查动词，而不只是名词。

- “加载器会拒绝声明了 `runner` 的 emit 节点”→ 在验证器中找到执行拒绝操作的代码，否则该声明就是错误的。
- “当运行进入终止状态时，流会关闭”→ 找到针对*每一种*终止状态执行关闭操作的代码，否则就要指出遗漏了哪一种状态。
- “差异在 `internal/document` 中计算”→ 找到该位置的调用代码，而不只是函数定义。
- “Tailwind 从 CDN 加载”→ 检查实际的 `<script src>`，而不只是确认使用了 Tailwind。

这是最常见的错误 `matches`：名词核对无误，验证者便放过了动词。应说明具体机制，并让引用指向实际*执行*声明所述行为的代码。

## 流程

**0 — 确定范围、熟悉情况、分类（主线程）。** 首先构建一份**事实依据地图**：明确 CLI 定义、路由、配置和核心类型所在的位置（阅读 `CLAUDE.md` 中的包结构图和目录布局）。提出文档组级别的分类方案；**与人工确认**。

**1 — 验证。** 对于**长期有效的**文档，为每篇文档分派一个子代理（限制并发数量；为每篇文档设置声明处理预算）。每个子代理提取原子声明，依据判定准则进行分类，并对照事实依据进行验证——验证的是**实际执行每项声明的代码路径，而不只是确认所提及的符号存在**（参见“验证声明，而不只是符号”）——然后返回发现结果，且**每个判定都必须附带 `file:line` 或命令输出引用，包括 `matches`**。不进行编辑。对于**特定时间点的**文档：在主线程中处理（或使用一个批量处理代理）——不进行声明与代码的对照检查，只做元信息检测（已被取代但未标记、缺少日期、仍被作为当前有效内容链接、引用失效）。

**2 — 分流与应用（主线程）。** 将确定无疑的自动修复应用到工作树。针对其余所有问题开展一次**有界且按优先级排序的**访谈（优先处理常青文档中高置信度的过时内容；将长尾问题留待报告处理）。应用获批的时点型元修复。

**3 — 以对抗方式验证你自己的编辑（主线程）。** 在宣布完成之前，**重新检查你刚刚应用的编辑**——审计自身的修复恰恰最容易藏有看似自信实则错误的断言：过度断言、将过时的代码*注释*重述为事实、删除时遗漏了仍然有效的概念，或无法通过验证的示例。派出**两个或更多相互竞争的子代理**，竞相在已应用的差异中找出尽可能多的正当错误；每项断言都必须根据实际*执行*该行为的代码路径重新验证（而不只是确认符号存在），并附上 `file:line` 或命令输出引用。明确告诉它们彼此正在竞争，并且**为凑数而填充或夸大发现将被取消资格**——这种设定正是保证此轮检查诚实可靠的关键。修复每一项得到确认的问题。只有在此之后，才在已验证的常青文档上**标记最后审阅信息**，并将所有内容保持为**未提交**状态，以供人工审阅。

**4 — 文档集审阅（整个集合，而不是逐篇文档）。** 阶段 1–3 针对单篇文档执行，因此它们**无法发现文档集层面的缺陷**。当你审计一个文档*集合*（而不是单个文件）时，应对整个集合执行一次检查——使用独立且相互竞争的代理，并向它们提供规范归属方方案：

- **重复**——同一事实在 2 篇或更多文档中被实质性地重复陈述，因而会发生偏移（实践中也确实已经发生）。为每项事实指定唯一的**规范归属方**（HTTP 路由 → API 文档、CLI 标志 → CLI 文档、字段模式 → 模式文档、运行时/触发语义 → 运行时文档、事件类型 → 日志文档，……），并以交叉引用替换副本。为删减工作**每篇文档分配一个代理**——每个代理只负责*一个文件*，从而避免编辑冲突。
- **覆盖范围 / 缺口**——枚举代码库的各个表面（包、CLI 命令、路由、事件类型、配置），并检查每一项是否都在*某处*有文档记录。单篇文档审计无法发现缺失的文档——只有列出*理应*存在的内容，才能发现它。按照同样的标准编写缺失的文档，或记录这些缺口。
- **跨文档矛盾**——同一事实在两篇文档中有两种不同的表述（其中一个是错误的）。在规范归属方处统一协调。
- **结构 / 规范性**——是否有一个**索引**（由一篇文档列出整个集合，并为每项附上一行简介）？维护它。命名是否一致？时点型文档是否被错误地放入常青文档文件夹？排序方式是否已成为历史遗留（连续编号暗示范围是冻结且完整的）？

单篇文档各自整洁，并不意味着整个文档集健康。此阶段专门捕获阶段 1–3 无法发现的那类问题。

## 最后审阅标记

仅在**常青文档**上，以幂等方式在 EOF 处维护一个区块（如果末尾已有 `---` 分隔线，则复用它；根据哨兵标记执行查找和替换，绝不要堆叠重复区块）：

```
---
<!-- doc-audit:last-reviewed -->
_Last reviewed: 2026-06-07 · commit `abc1234` · verified against code (2 claims deferred to review)._
```

日期 + SHA **仅用于溯源**（审查时的 HEAD），不是范围界定键。只标记你实际核验过的文档。**不要标记时点文档**——它们是冻结的记录，重新标记只会造成无谓改动。

## 危险信号——立即停止

- 在**尚未先行分类**的情况下，打算对整套规范/计划文档“全部更新到最新状态”。→ 先分类并确认。
- 正准备对 `file:line` 引用**重新编号**。→ 通过访谈将其转换为 `file:symbol`。
- 正准备按照新模式**重写示例的结构**。→ 进行访谈，不要自动修复。
- 在“果断一点 / 不要确认”的压力下，正准备自行对文档分类并**重写其正文**。→ 分类确认是唯一绝不能跳过的关卡。明确提出确认；一句话的确认只需几秒钟。
- 因为 grep 未命中，就断定某项功能已“移除”或删除其文档。→ 先检查 git 历史记录。
- “差不多，我直接把数量修正一下就行。”→ 数量问题交给人来处理。
- 编辑标有“generated”或“do not edit”的文件。→ 跳过该文件。
- 在**没有引用依据**的情况下将某项陈述标记为“匹配”。→ 要么提供引用，要么不要声称匹配。
- 正准备**在没有对自己的编辑进行第二轮对抗性检查的情况下结束工作**。→ 先执行竞争性核验流程（Phase 3）；修复其中发现的问题。
- 仅仅因为**符号存在**，而未检查代码是否确实*执行了*相关陈述所声称的行为，就将该陈述标记为“匹配”。→ 核验动词，而不是名词。
- 审查了每篇文档，却从未从**文档集合**层面检查（重复、缺失、矛盾、索引）。→ 逐篇文档的检查无法发现集合层面的问题；执行语料库审查（Phase 4）。

## 自我辩解

| 借口 | 事实 |
|--------|---------|
| “规范说的是 X，但代码说的是 Y，所以规范错了。” | 只有当规范是**持续更新型**文档时才成立。时点设计文档可以与当前代码不同——先分类。 |
| “这显然是参考文档，我直接修复就行。” | 凭直觉逐篇判断文档，正是设计文档的历史记录遭到改写的原因。与人确认分类。 |
| “他们说要果断，不要把决定推回去——所以我会自行分类和重写。” | 分类确认是唯一绝不能跳过的关卡；它决定了你是在修复文档，还是在抹除设计记录。一句话的确认只需几秒钟。 |
| “其中没有任何内容看起来像带日期的设计叙事，所以它是持续更新型文档。” | 缺少明显的设计语言并不能证明它是持续更新型文档，尤其是在 `specs/` 这类内容混杂的文件夹中。存在歧义 + 破坏性编辑 → 将其视为时点文档并进行确认。 |
| “我在最后披露了自己的假设。” | 在重写正文后再加脚注已经太晚了——记录已被更改。应在编辑*之前*确认，而不是之后。 |
| “行号变了，我会更新它。” | 每次编辑都会导致行号漂移；重新定位后，它还会再次失效。将其转换为 `file:symbol`。 |
| “我会将示例更新为新模式。” | 对示例进行结构性重写会改变其含义 → 进行访谈，不要自动修复。 |
| “grep 什么也没找到，这项功能已经不存在了。” | grep 未命中并不能证明功能已被移除。检查 git 历史记录；它可能只是被重命名了。 |
| “37 和约 40 很接近，我直接写成实际数量就行。” | 数量没有统一的规范口径——交给人来处理。 |
| “符号/路由/字段存在，所以这项陈述核验通过。” | 存在 ≠ 陈述成立。核验实际*执行*该行为的代码路径（验证器/处理程序/调用点），而不只是确认该名词存在。 |
| “每篇文档都核验无误，所以这些文档没有问题。” | 单篇文档准确 ≠ 整个文档集合健康。重复、文档缺失和跨文档矛盾只有在语料库层面（Phase 4）才会显现。 |

## 常见错误

- 在分类之前就开始编辑。
- 为每份时点文档分别启动一个子代理——应进行批处理；它们尚未经过声明验证。
- 首次运行时积压无限量的访谈任务——确定优先级，将剩余部分推迟到报告中处理。
- 自动提交审查结果——应保持未提交状态，供人工审核。
- 未对自己的编辑进行对抗性验证就宣布完成——你修复的内容是那些自信但错误的声明最容易藏身的地方（阶段 3）。
- 将逐文档验证视为全部工作——重复、缺漏、跨文档矛盾以及缺失索引都是文档集层面的缺陷，逐文档检查无法发现这些问题（阶段 4）。
- 只验证名词，不验证动词——只确认某个符号存在，而不确认代码是否确实执行了文档所声称的行为。
