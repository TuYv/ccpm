# 领域驱动开发（DDD）工作流

## 开发模式配置（关键）

[注意] 此工作流根据 `.moai/config/sections/quality.yaml` 中的配置进行选择：

```yaml
constitution:
  development_mode: ddd    # or tdd
```

**何时使用此工作流**：
- `development_mode: ddd` → 使用 DDD（此工作流）
- `development_mode: tdd` → 改用 TDD（moai-workflow-tdd）

**主要区别**：
- **DDD**：针对测试覆盖率极低的现有代码库，优先编写特征测试
- **TDD**（默认）：所有工作均采用测试优先开发，包括具有 pre-RED 分析的棕地项目

## 快速参考

领域驱动开发为重构现有代码库提供了一种系统化方法，适用于必须优先保证行为不变的场景。TDD 用于创建新功能，而 DDD 则在不改变行为的情况下改进结构。

核心循环 - 分析-保留-改进：

- 分析：识别领域边界、度量耦合度、进行 AST 结构分析
- 保留：编写特征测试、创建行为快照、验证测试安全网
- 改进：以增量方式调整结构，同时持续验证行为

何时使用 DDD：

- 重构已有测试的遗留代码
- 在不改变功能的情况下改进代码结构
- 减少生产系统中的技术债务
- 处理 API 迁移和弃用
- 代码现代化项目
- 绿地项目（使用调整后的循环——见下文）

何时不应使用 DDD：

- 需要改变行为时（首先修改 SPEC）
- 代码已存在，但目标是改变行为而非保持行为不变的重构时（DDD 会保留行为；如需新增行为，请先修改 SPEC，或使用 TDD）

绿地项目适配：

对于没有现有代码的新项目，DDD 会对其循环进行如下调整：

- 分析：进行需求分析，而非代码分析
- 保留：通过规范测试定义预期行为（测试优先）
- 改进：实现代码以满足已定义的测试

这使 DDD 成为 TDD 的超集——它既包含 TDD 的测试优先方法，也支持重构场景。

## 核心理念

### DDD 与 TDD 对比

TDD 方法（用于新功能）：

- 循环：红-绿-重构
- 目标：通过测试创建新功能
- 起点：不存在代码
- 测试类型：定义预期行为的规范测试
- 结果：具有测试覆盖的新可用代码

DDD 方法（用于重构）：

- 循环：分析-保留-改进
- 目标：在不改变行为的情况下改进结构
- 起点：具有既定行为的现有代码
- 测试类型：捕获当前行为的特征测试
- 结果：结构得到改进且行为完全相同的代码

### 行为保留原则

DDD 的黄金法则是：重构前后的可观察行为必须完全一致。这意味着：

- 所有现有测试必须不经修改即可通过
- API 契约保持不变
- 副作用保持不变
- 性能特征保持在可接受的范围内

## 实施指南

### 阶段 1：分析

分析阶段侧重于理解当前代码库的结构并识别重构机会。

#### 领域边界识别

通过检查以下内容识别代码库中的逻辑边界：

- 模块依赖关系和导入模式
- 组件之间的数据流
- 共享状态和耦合点
- 公共 API 接口

使用 AST-grep 分析结构模式。对于 Python，搜索导入模式以了解模块依赖关系。对于类层次结构，分析继承关系和方法分布。

#### 耦合与内聚指标

评估代码质量指标：

- 传入耦合度（Ca）：依赖此模块的类的数量
- 传出耦合度（Ce）：此模块所依赖的类的数量
- 不稳定性（I）：Ce / (Ca + Ce)——值越高表示越不稳定
- 抽象度（A）：抽象类数量 / 类总数
- 与主序列的距离：|A + I - 1|

低内聚和高耦合表明这些部分适合进行重构。

#### 结构分析模式

使用 AST-grep 识别存在问题的模式：

- 方法或职责过多的上帝类
- 方法过度使用其他类数据的特性依恋
- 表明缺少抽象的过长参数列表
- 跨模块的重复代码模式

创建分析报告，记录：

- 当前架构概览
- 已识别的问题区域及其严重程度评级
- 建议的重构目标及风险评估
- 展示耦合关系的依赖图

### 阶段 2：保护

保护阶段在进行任何更改之前建立安全保障。

#### 特征测试

特征测试用于捕获现有行为，而不对其正确性作出任何假设。目标是记录代码实际执行的行为，而不是它应该执行的行为。

创建特征测试的步骤：

- 步骤 1：通过执行识别关键代码路径
- 步骤 2：创建覆盖这些路径的测试
- 步骤 3：先让测试失败，以发现实际输出
- 步骤 4：更新测试，使其预期结果与实际输出一致
- 步骤 5：记录发现的任何意外行为

特征测试命名约定：test*characterize*[component]\_[scenario]

#### 行为快照

对于复杂输出，使用快照测试捕获当前行为：

- API 响应快照
- 序列化输出快照
- 状态转换快照
- 错误消息快照

在重构期间，快照文件充当行为契约。

#### 测试安全网验证

在进入改进阶段之前，验证：

- 所有现有测试均通过（100% 通过）
- 新增的特征测试覆盖重构目标
- 受影响区域的代码覆盖率达到阈值
- 安全网中不存在不稳定测试

如果条件允许，运行变异测试以验证测试的有效性。

### 阶段 3：改进

改进阶段进行结构性更改，同时持续验证行为是否得到保留。

#### 增量转换策略

切勿一次进行大规模更改。请遵循以下模式：

- 进行尽可能小的结构性更改
- 运行完整测试套件
- 如果测试失败，立即还原
- 如果测试通过，提交更改
- 重复上述步骤，直到实现重构目标

#### 安全重构模式

提取方法：当一个代码块可以被命名并隔离时使用。使用 AST-grep 搜索重复代码块或过长的方法，以识别候选项。

提取类：当一个类承担多项职责时使用。将相关方法和字段移至新类，同时通过委托维持原有 API。

移动方法：当一个方法使用其他类的数据多于自身类的数据时使用。移动该方法，同时保留所有调用点。

内联重构：当间接层增加复杂性却没有带来收益时使用。以直接实现替代委托。

重命名重构：当名称无法反映当前理解时使用。使用 AST-grep rewrite 以原子方式更新所有引用。

#### AST-Grep 辅助转换

使用 AST-grep 进行安全且具备语义感知能力的转换：

对于方法提取，创建一条规则来识别代码模式，并将其重写为提取后的形式。

对于 API 迁移，创建一条规则来匹配旧 API 调用，并将其重写为新 API 格式。

对于弃用处理，创建规则来识别已弃用模式，并建议现代替代方案。

#### 持续验证循环

每次转换后：

- 运行单元测试（快速反馈）
- 运行集成测试（行为验证）
- 运行特征测试（快照比较）
- 确认没有引入新的警告或错误
- 在适用时检查性能基准

## DDD 工作流执行

### 标准 DDD 会话

通过 moai:2-run 以 DDD 模式执行 DDD 时：

步骤 1 - 初始评估：

- 阅读 SPEC 文档以了解重构范围
- 识别受影响的文件和组件
- 评估当前测试覆盖率

步骤 2 - 执行分析阶段：

- 对目标代码运行 AST-grep 分析
- 生成耦合度和内聚度指标
- 创建领域边界图
- 记录重构机会

步骤 3 - 执行保留阶段：

- 验证所有现有测试均通过
- 为未覆盖的路径创建特征测试
- 生成行为快照
- 确认安全网充分可靠

步骤 4 - 执行改进阶段：

- 以增量方式执行转换
- 每次更改后运行测试
- 立即提交成功的更改
- 记录发现的所有问题

步骤 5 - 验证与完成：

- 运行完整测试套件
- 比较重构前后的指标
- 验证所有行为快照均匹配
- 生成重构报告

### DDD 循环模式

对于需要多次迭代的复杂重构：

- 根据范围设置最大循环迭代次数
- 每次循环专注于一个重构目标
- 退出条件：所有目标均已处理或达到迭代次数上限
- 通过更新 TODO 列表跟踪进度

## 质量指标

### DDD 成功标准

行为保留（必需）：

- 所有原有测试均通过
- 所有特征测试均通过
- API 契约无变化
- 性能保持在限定范围内

结构改进（目标）：

- 降低耦合度指标
- 提高内聚性得分
- 降低代码复杂度
- 更好地分离关注点

### DDD 专项 TRUST 验证

应用侧重于 DDD 的 TRUST 5 框架：

- 可测试性：特征测试覆盖率充足
- 可读性：命名和结构改进已验证
- 可理解性：领域边界更加清晰
- 安全性：未引入新的漏洞
- 透明性：所有变更均有文档记录且可追溯

## 集成点

### 与 AST-Grep Skill 集成

DDD 高度依赖 AST-grep 来完成：

- 结构化代码分析
- 模式识别
- 安全的代码转换
- 多文件重构

规则位于 `.moai/config/astgrep-rules/`；使用 `moai ast-grep` 进行扫描，并使用 `moai ast-edit` 应用重写。

### 与测试工作流集成

DDD 对测试工作流形成补充：

- 使用测试模式中的特征测试
- 与变异测试集成，以验证安全网
- 利用快照测试基础设施

### 与质量框架集成

DDD 的输出会用于质量评估：

- 变更前后的指标对比
- 使用 TRUST 5 验证变更
- 技术债务跟踪

## 故障排除

### 常见问题

转换后测试失败：

- 立即恢复到最后一个已知正常状态
- 分析哪些测试失败以及失败原因
- 检查转换是否意外改变了行为
- 考虑采用更小的转换步骤

特征测试不稳定：

- 识别非确定性的来源
- 模拟外部依赖
- 修复依赖时间或执行顺序的行为
- 考虑调整快照容差设置

性能下降：

- 在变更前后进行性能分析
- 识别受变更影响的热点路径
- 考虑使用缓存或进行优化
- 记录可接受的权衡

### 恢复流程

当 DDD 会话遇到问题时：

- 使用 git stash 保存当前状态
- 重置到最后一次成功的提交
- 审查导致失败的转换
- 规划替代方案
- 从保留的状态继续

## 常见的自我合理化说辞

| 自我合理化说辞 | 事实 |
|---|---|
| “这段遗留代码显然已经坏了，我直接重写就行” | 看似有问题的代码可能编码了调用方所依赖的生产环境行为。先进行 ANALYZE，再通过测试进行重写。 |
| “特征测试只是无意义的繁琐工作” | 它们是让你能够无所顾虑地进行重构的安全网。没有它们，重构就等同于重写。 |
| “我对这个模块已经足够了解，可以跳过 ANALYZE” | 理解不等于验证。ANALYZE 会迫使你明确说出假设，并正视调用方。 |
| “这个函数没有测试，是因为它没有值得测试的行为” | 如果它有调用方，它就有契约。这个契约正是需要进行特征刻画的对象。 |
| “只要足够谨慎，我就能保留原有行为” | 谨慎并不是一种保障机制。测试是捕获回归问题的唯一机制。 |
| “这次重构规模太小，没必要使用 DDD” | 小型重构之所以会导致无声的回归，恰恰是因为人们跳过了安全网。 |

**切斯特顿栅栏原则**：不要移除或替换你无法解释其用途的代码。ANALYZE 阶段专门用于揭示看似错误的代码背后的设计缘由。

## 危险信号

- 重构提交既没有新增测试，也没有修改任何现有测试
- 缺少 ANALYZE 产物，或其被简化为单行摘要
- 特征测试只断言返回值，忽略副作用和状态变化
- IMPROVE 阶段引入了未经测试覆盖的新公共 API
- 声称行为保持不变，却没有重构前后的测试证据
- 在 IMPROVE 期间删除旧测试，而不是对其进行更新
