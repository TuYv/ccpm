# 内部沟通

内部沟通往往以可预见的方式失败：不该最先获知消息的人先听说了，信息解释了决策却没有说明后果，而且草稿在进入 2,000 个收件箱之前无人测试。本技能将公告视为一种具有影响范围、发布顺序和通过/不通过质量标准的交付物，而不是一项写作练习。

三个关键杠杆是：**谁以什么顺序获知消息**、**信息必须包含什么内容**，以及**通过哪个渠道传递**。只要正确处理这些问题，语气的重要性远低于人们通常的想象。

## 何时使用本技能

- 宣布**组织重组、裁员或领导层变动**，因为顺序一旦出错便无法挽回
- 推行需要员工采取行动的**政策变更**（返岗办公、费用、安全、绩效流程）
- 沟通有截止日期且要求用户采取行动的**产品或系统迁移**
- 重新设计目前读起来像状态信息堆砌的定期**全员大会或高管周报**
- 发送前对**草稿进行压力测试**：阅读难度、术语密度、缺失要素
- 为持续数周的变革计划确定**渠道和节奏**，而不是只发送一次性邮件

## 本技能需要的输入

- **变更本身**：哪些内容将发生变化、生效日期、是否可逆
- **受众列表**，包括影响程度（高 / 中 / 低）以及各群体的大致人数
- **草稿文本**（如有；纯 markdown 或文本均可）
- **约束条件**：禁发期、法务审核、监管披露、市场敏感性
- **可用渠道**，以及你的组织成员实际会查看哪些渠道
- 发送后**谁可以回答问题**，以及在哪里回答

## 先澄清

生成内容之前，请确认以下输入。如果任何一项未知或含糊，请提问——不要自行假设：

- [ ] **影响范围——哪些人受到实质影响，哪些人只是需要知情**——这决定了你需要采用级联传达（管理者优先）还是单次广播，而级联传达需要 3-5 天
- [ ] **决策是否可逆**——可逆的变更可以作为提案发布，并设置反馈期；不可逆的变更绝不能这样做，因为邀请他人提供你不会采纳的意见，是失去信任最快的方式
- [ ] **生效日期和要求用户采取的行动**——这会设定计划中的每个 T-offset，并决定信息属于告知性质还是指示性质
- [ ] **是否存在任何法律或市场敏感事项**——禁发约束优先于理想的发布顺序，并会迫使你采用同步发布，而不是级联传达

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草”，则继续执行，并在交付物顶部列出你的假设。

## 工作流

### 工作流 1——发送前审核草稿

对每一则覆盖超过约 50 人的公告执行此流程。整个过程只需 30 秒，却能发现最容易引发大量后续问题的失败模式。

1. 将草稿保存为 JSON，包含 `title`、`body`、`audience` 和 `channel`。
2. 运行审核器。它会评估五个必要要素（发生了什么变化、为什么变化、谁会受到影响、需要做什么、在哪里提问）、阅读难度等级、术语密度和模糊措辞。
3. 修复每一个标记为 `FAIL` 的要素。除非受众包括非母语使用者或一线员工，否则将阅读难度等级的 `WARN` 视为建议；如果包括，则应将其视为 `FAIL`。
4. 重新运行，直到分数超过 75。

```bash
python3 business-operations/internal-comms/scripts/announcement_auditor.py \
  --input business-operations/internal-comms/assets/sample_announcement.json \
  --min-score 75 --format text
```

### 工作流 2 — 安排变更沟通顺序

1. 描述变更，并列出受影响的受众及其人数。
2. 运行顺序规划器。它会计算影响范围，按照
   *影响优先、影响力次之*的规则对受众排序，并分配相对于全员发布日的 T 日偏移量。
3. 检查管理者赋能步骤——如果计划表明你需要执行此步骤，而你却跳过了，
   管理者就会从自己的下属那里得知变更，而这是组织重组沟通中最
   常见的一类失败。
4. 导出计划，并为每个步骤指定一名负责人。

```bash
python3 business-operations/internal-comms/scripts/comms_sequencer.py \
  --input business-operations/internal-comms/assets/sample_change.json \
  --format text
```

### 工作流 3 — 选择渠道

1. 从六个维度描述消息特征：紧迫性、复杂性、受众规模、
   敏感性、是否需要双向讨论，以及是否需要可长期留存的记录。
2. 运行评分器，对渠道进行排名，并查看哪些渠道被明确排除。
3. 使用排名最高的渠道作为主要渠道，并使用排名最高的*可长期留存*渠道
   作为正式记录系统。绝不能把聊天消息作为正式记录。

```bash
python3 business-operations/internal-comms/scripts/channel_fit_scorer.py \
  --input business-operations/internal-comms/assets/sample_message_profile.json \
  --top 4 --format json
```

## 决策框架

### 影响范围 → 顺序模式 [已验证]

影响范围是指其*工作或雇佣关系发生变化*的人数，而不是
收到电子邮件的人数。

| 范围 | 模式 | 全员发布前的提前时间 | 管理者赋能 |
|--------|---------|----------------------------|--------------------|
| 1-10 | 先进行直接的一对一沟通，再低调发布团队通知 | 当天 | 不需要 |
| 11-50 | 管理者简报 → 团队会议 → 书面跟进 | 1-2 天 | 必须，60 分钟会议 |
| 51-250 | 高管简报 → 管理者简报 + FAQ → 全员大会 → 书面通知 | 3-5 天 | 必须，附沟通话术 + FAQ |
| 250+ | 增加针对非正式意见领袖的预先简报，以及为期 2 周的强化沟通节奏 | 5-10 天 | 必须，外加管理者问答渠道 |

例外情况：法律禁令或市场敏感性会将这一流程压缩为同步发布。
发生这种情况时，应在消息中明确说明——“由于信息披露规则，我们无法先向管理者通报”——
而不是让人们自行推断这是疏忽所致。

### 五个必备要素 [已验证]

每项重要公告都应按以下顺序回答这些问题。缺少其中任何一项的消息
都会引发一类可预见的后续问题。

| 要素 | 缺少时会导致 | 最低标准 |
|---------|--------------------|-------------|
| **发生了什么变化** | “等等，这是现在发生，还是以后发生？” | 在第一段用一句话说明，并包含生效日期 |
| **为什么** | 谣言和最坏情况猜测 | 说明实际原因，包括迫使其发生的限制条件 |
| **谁会受到影响** | 每位读者都会认为自己受影响 | 明确指出相关群体，并明确说明“如果你不属于这些群体，则不会受到任何影响” |
| **要做什么** | 什么都不会发生 | 给出带截止日期的行动要求，或者明确写出“无需采取行动” |
| **去哪里提问** | 问题被提交给错误的人 | 指定具体联系人或渠道，并说明何时会得到回复 |

### 消息类型 → 结构 [建议]

| 类型 | 开头内容 | 长度 | 反馈窗口 |
|------|-----------|--------|-----------------|
| 不可逆决策（重组、裁员、关停） | 决策本身 | 300-500 字 | 无——不要征求意见 |
| 可逆政策 | 要解决的问题 | 400-700 字 | 5-10 个工作日 |
| 迁移 / 截止日期 | 行动和日期 | 200-350 字 | 仅接受问题 |
| 庆祝 / 里程碑 | 成果以及完成者 | 150-250 字 | 无 |
| 坏消息（事故、未达目标） | 用直白的语言说明发生了什么 | 250-400 字 | 事后复盘链接 |

### 持续数周的变更沟通节奏 [建议]

只宣布一次，人们会忘记；每周都宣布，人们会充耳不闻。有效的模式是：
**T-0 发布公告，T+3 天更新 FAQ，T+1 周由经理跟进，T+2 周发布进展说明，
T+4 周完成收尾。** 共五次触达，篇幅逐次缩短。包括强化沟通渠道在内的完整表格，请参阅
`references/change-comms-cadence.md`。

## 反模式

### 突袭式广播
**错误：** 在没有事先向经理说明情况的情况下，向全体员工发送重组或政策公告。
**发生原因：** 领导层担心消息泄露，而同时发送会让人觉得“公平”且一视同仁。
**替代做法：** 提前 24-48 小时向经理说明情况，提供沟通话术和 FAQ，并明确告诉他们
哪些内容可以转述，哪些不可以。无法回答团队第一个问题的经理会失去威信，而重建这种威信
需要数月时间。如果泄露风险确实很高，应将时间窗口压缩至 2 小时，而不是完全取消。

### 将决策埋在论证之下
**错误：** 先用三段说明市场背景，然后才陈述将要发生的变化。
**发生原因：** 作者希望读者得出与自己相同的结论，因此会重现自己的推理过程。
**替代做法：** 第一句就说明决策，然后再解释理由。持不同意见的读者会更仔细地阅读理由，
而不是相反。先讲背景的结构看起来像是在构建论据，这会传递出一种防御姿态。

### 虚假征询
**错误：** 宣布一个已经敲定的决定，同时附上“我们非常希望听取您的反馈”。
**发生原因：** 这能缓和消息的传达方式，并且比直接下达指令显得更具协作性。
**替代做法：** 如果决定已经敲定，就明确说明：“此事已经决定。以下是我们考虑过的因素。”
如果意见确实可以改变结果，请说明具体还有哪些事项尚未确定，以及征求意见的截止时间。
先征求反馈再置之不理，对信任造成的损害明显大于完全不进行征询。

### 用术语作为缓冲
**错误：** “我们正在重新调整运营模式，以便更好地利用各小组之间的协同效应。”
**发生原因：** 对写作者而言，抽象表达会让令人不适的消息显得不那么直接。
**替代做法：** 写出一个人会直接说出口的句子。审查工具会标记占比超过总词数 2% 的术语；
对于高影响力消息，任何超过该比例的情况都意味着草稿在掩盖某些事情，而读者会假定它
掩盖的是最糟糕的情况。

### 问题没有明确的负责人
**错误：** 以“如有任何问题，请联系我们”结尾。
**原因：** 没人愿意主动腾出自己的日程来处理这些问题。
**正确做法：** 指定一个人或具体频道，并明确响应承诺（“#change-rto，
将在一个工作日内答复”）。未被引导至明确渠道的问题会变成走廊里的闲聊，
而走廊里的闲聊最终会成为人们记住的消息版本。
