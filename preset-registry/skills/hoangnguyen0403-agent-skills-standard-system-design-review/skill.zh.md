# 系统设计评审

## **优先级：P1（高）**

依据证据而非意图评分。没有数字或工件支撑的声明得分为零。

## 九个维度（每项 0-10 分）

| 维度 | 得分为 10 时 | 得分为 0 时 |
| --- | --- | --- |
| 需求 | 已写明功能需求、NFR 和范围外事项，并指定负责人 | 只有功能描述 |
| 容量证据 | 已计算峰值 QPS、存储和带宽，且数据更新至最近一次流量变化 | 缺少数据，或数据早于最近一次流量变化 |
| 冗余 | 无单点故障；已演练故障转移并测得 RTO | 单实例，或关键路径上的故障转移未经测试 |
| 数据扩展 | 已梳理访问模式、明确单一所有者，并说明增长路径 | 一个共享存储，没有增长计划，表无界增长 |
| 缓存 | 热点读路径已缓存，并定义 TTL 和失效机制 | 已证实的热点路径没有缓存，或缓存无法失效 |
| 异步卸载 | 慢速和突发性工作已进入队列，并设有处理速率和 DLQ | 所有工作都在请求路径上同步执行 |
| 可观测性 | 已对流量、错误、延迟和饱和度进行监控，并设置由负责人维护的告警 | 只有日志，或告警没有运行手册 |
| 发布 | 使用金丝雀发布或功能开关，具有指标回滚触发条件和可逆迁移 | 一次性发布，不可逆迁移 |
| 成本合理性 | 成本规模与流量和风险相匹配，并且有人能够说明依据 | 为无人测量过的假想规模购买了拓扑 |

报告每个维度的得分及所使用的证据，总分 90 分。根据系统的实际风险为各维度加权：一个 100 RPS 的内部工具不会因为缺少多地域部署而被判定为失败。

## 评审方法

1. 先确定事实基线：当前流量、数据量、事故历史，以及负责人报告的首要痛点。
2. 根据工件和指标评估九个维度；将无法验证的声明标记为 `UNVERIFIED`。
3. 端到端追踪最繁忙和最关键的路径；最差的一跳才是真正的瓶颈。
4. 按以下格式列出发现：严重性 - 维度 - 证据 - 后果 - 最小修复措施。
5. 将发现转化为路线图：立即止血、下一步结构性改进、之后可选事项。
6. 检查可运维性：凌晨 3 点由谁负责运行，哪个团队负责哪个部分，以及该团队是否确实具备运维能力。

## 需要检查的常见错误

- 在需求或数据形成之前就绘制了架构。
- 声称具备冗余，但共用一个配置平面、凭据或控制平面。
- 在从未优化过的查询之上直接添加缓存。
- 在索引、副本和缓存尚未耗尽其能力之前就采用分片。
- 队列没有处理速率预算、没有 DLQ，并且依据深度而非年龄设置告警。
- 根据 CPU 而不是用户可见的症状或错误预算消耗设置告警。
- 将迁移与代码作为一个不可逆步骤一起发布。

## 反模式

- **没有证据就不能评分**：引用指标、工件或演练记录；否则标记为 `UNVERIFIED`。
- **默认不建议重写**：优先采用能够消除已证实瓶颈的最小修复措施。
- **不要使用统一的严重性**：根据用户影响和可逆性排序，而不是按照维度顺序排序。
- **没有后续行动就不能提出发现**：每个缺口都要对应一个可交由负责人执行的修复措施。
