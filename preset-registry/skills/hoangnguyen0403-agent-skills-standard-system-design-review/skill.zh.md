# 系统设计评审

## **优先级：P1（高）**

基于证据而不是意图评分。没有数字或制品支撑的声明得分为零。

## 九个维度（每项 0-10 分）

| 维度 | 得 10 分的条件 | 得 0 分的条件 |
| --- | --- | --- |
| 需求 | 已由负责人写明功能需求、NFR 和范围外内容 | 只有功能描述 |
| 容量证据 | 已计算峰值 QPS、存储和带宽，并且数据是当前的 | 缺少数字，或数据早于上一次流量变化 |
| 冗余 | 无 SPOF；已通过演练验证故障转移，并测得 RTO | 单实例，或关键路径上的故障转移未经测试 |
| 数据扩展 | 已梳理访问模式、明确单一归属，并说明增长路径 | 一个共享存储，没有增长计划，表无界增长 |
| 缓存 | 热点读路径已配置缓存，并定义 TTL 和失效机制 | 已证实的热点路径没有缓存，或缓存无法失效 |
| 异步卸载 | 慢速和突发性工作已进入队列，并设定排空速率和 DLQ | 所有工作都同步执行于请求路径上 |
| 可观测性 | 已对流量、错误、延迟和饱和度进行监控，并配置有负责人负责的告警 | 只有日志，或告警没有运行手册 |
| 发布 | 使用金丝雀发布或特性开关，并配置带有指标回滚触发条件的可逆迁移 | 一次性发布，不可逆迁移 |
| 成本合理性 | 支出规模与流量和风险相匹配，并且有人能够说明这一点 | 为无人测量过的臆想规模购买了相应的拓扑 |

报告每项得分及所使用的证据，总分为 90 分。根据系统的实际风险对各维度加权：一个 100 RPS 的内部工具不会因为缺少多地域部署而判定为失败。

## 评审方法

1. 首先建立事实基线：当前流量、数据量、事故历史，以及负责人报告的首要痛点。
2. 根据制品和指标对八个维度进行评分；任何无法验证的声明都标记为 `UNVERIFIED`。
3. 端到端追踪最繁忙和最关键的路径；最差的一跳才是真正的瓶颈。
4. 将发现列为：`严重性 - 维度 - 证据 - 后果 - 最小修复`。
5. 将发现转化为路线图：立即止血、下一步进行结构性修复、之后再考虑可选项。
6. 检查可运维性：凌晨 3 点谁来运行它，每个部分由哪个团队负责，以及该团队是否真的能够运维它。

## 需要检查的常见错误

- 在需求或数据尚不存在之前就绘制架构。
- 声称具备冗余，但实际共享同一个配置平面、凭据或控制平面。
- 在从未优化过的查询之上直接添加缓存。
- 在索引、副本和缓存尚未充分利用之前就采用分片。
- 队列没有排空速率预算、没有 DLQ，并且按深度而不是按年龄配置告警。
- 针对 CPU 而不是面向用户的症状或错误预算消耗配置告警。
- 将迁移和代码作为一个不可逆的步骤一起发布。

## 反模式

- **没有证据就不得分**：引用指标、制品或演练；否则标记为 `UNVERIFIED`。
- **默认不建议重写**：优先选择能够消除已证实瓶颈的最小修复。
- **不要统一设定严重性**：根据用户影响和可逆性排序，而不是按照维度顺序排序。
- **没有下一步行动就不要提出发现**：每个缺口都要配有可供负责人执行的修复方案。
