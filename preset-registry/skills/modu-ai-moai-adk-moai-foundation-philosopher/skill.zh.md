# MoAI 基础哲学家

一种强调深入分析而非快速计算的战略思考框架。它整合了三种经过验证的方法论，用于系统化解决问题。

核心理念：行动前深入思考。质疑假设。考虑替代方案。明确权衡取舍。检查认知偏差。

## 快速参考（30 秒）

什么是哲学家框架？

一种用于复杂决策的结构化方法，结合了：
- 第一性原理分析：将问题拆解为基本事实
- 斯坦福设计思维：通过发散与收敛生成解决方案
- 麻省理工学院系统工程：系统化风险评估与验证

五阶段思考流程：
1. 假设审查：揭示并质疑我们认为理所当然的事项
2. 第一性原理分解：拆解问题，找到根本原因
3. 替代方案生成：创建多个解决方案选项
4. 权衡分析：系统地比较各个选项
5. 认知偏差检查：验证思考质量

何时启用：
- 影响 5 个以上文件的架构决策
- 技术选型（库、框架、数据库）
- 性能与可维护性之间的权衡
- 重构范围决策
- 对破坏性变更的考量
- 任何具有重大长期影响的决策

## 实施指南（5 分钟）

### 阶段 1：假设审查

目的：在隐藏假设成为盲点之前将其揭示出来。

五个关键问题：
- 我们在没有证据的情况下假定了哪些事情为真？
- 如果这个假设最终被证明是错误的，会怎么样？
- 这是硬性约束，还是仅仅是一种偏好？
- 有什么证据支持这个假设？
- 还应由谁来验证这个假设？

假设类别：
- 技术假设：技术能力、性能特征、兼容性
- 业务假设：用户行为、市场状况、预算可用性
- 团队假设：技能水平、人员可用性、领域知识
- 时间线假设：交付预期、依赖项进度安排

假设文档格式：
- 假设陈述：清晰描述所做的假设
- 置信度：根据证据评定为高、中或低
- 证据依据：支持此假设的内容
- 错误风险：假设被证明为错误时的后果
- 验证方法：如何在正式投入前进行验证

原因：未经审视的假设是导致项目失败和返工的首要原因。
影响：尽早揭示假设可避免 40%–60% 的项目中途方向调整。

### 阶段 2：第一性原理分解

目的：拨开复杂性，找到根本原因和基本需求。

五个为什么技巧：
- 表层问题：用户或系统观察到的现象
- 第一个为什么：分析直接原因
- 第二个为什么：调查深层原因
- 第三个为什么：识别系统性驱动因素
- 第四个为什么：组织或流程因素
- 第五个为什么（根本原因）：需要解决的根本问题

约束分析：
- 硬约束：不可协商（安全、合规、物理条件、预算）
- 软约束：可协商的偏好（时间安排、功能范围、工具）
- 自我施加的约束：伪装成需求的假设
- 自由度：可以采用创造性解决方案的领域

分解问题：
- 这项请求背后的实际目标是什么？
- 我们真正试图解决的是什么问题？
- 如果没有任何约束，解决方案会是什么样子？
- 最小可行解决方案是什么？
- 在仍能实现目标的前提下，我们可以去掉什么？

原因：大多数问题都是在错误的抽象层级上解决的。
影响：第一性原理思维可将解决方案的复杂度降低 30-50%。

### 阶段 3：生成备选方案

目的：避免过早收敛于次优解决方案。

生成规则：
- 至少需要三个不同的备选方案
- 至少包含一个非常规选项
- 始终将“什么都不做”作为基准方案
- 考虑短期与长期影响
- 同时探索渐进式和变革式方法

备选方案类别：
- 保守型：低风险、渐进式改进、采用熟悉的技术
- 平衡型：中等风险、显著改进、包含一定创新
- 激进型：较高风险、变革性改变、采用前沿方法
- 颠覆型：挑战基本假设，采用完全不同的方法

创造力技巧：
- 逆向思考：什么会让这个问题变得更糟？然后反其道而行之。
- 类比：其他领域如何解决类似问题？
- 移除约束：如果预算、时间或技术不受限制，会怎样？
- 简化：最简单的可行解决方案是什么？

原因：第一个解决方案很少是最佳解决方案。
影响：考虑 3 个以上的备选方案可将决策质量提高 25%。

### 阶段 4：权衡分析

目的：使隐含的权衡变得明确且可比较。

标准评估准则：
- 性能：速度、吞吐量、延迟、资源使用量
- 可维护性：代码清晰度、文档、团队熟悉度
- 实施成本：开发时间、复杂度、学习曲线
- 风险水平：技术风险、失败概率、回滚难度
- 可扩展性：增长容量、灵活性、未来适应能力
- 安全性：漏洞面、合规性、数据保护

加权评分方法：
- 根据项目优先级为各项准则分配权重（合计 100%）
- 按 1-10 分为每个选项的各项准则评分
- 计算加权综合得分
- 记录每项评分的理由
- 确定分数对权重变化的敏感度

权衡记录：
- 我们获得什么：所选方法的主要收益
- 我们牺牲什么：明确接受的成本和局限性
- 为何可以接受：接受这些权衡的理由
- 缓解计划：如何应对不利因素

原因：隐含的权衡会导致后悔和反复质疑。
影响：明确的权衡可将利益相关者的一致性提高 50%。

### 阶段 5：认知偏差检查

目的：通过检查常见的思维错误，确保建议的质量。

需要监控的主要偏见：
- 锚定偏见：过度依赖最先接触到的信息
- 确认偏见：寻找支持既有信念的证据
- 沉没成本谬误：因过去的投入而继续坚持
- 可得性启发式：过度重视近期或令人印象深刻的事件
- 过度自信偏见：对自己的判断过分确信

偏见检测问题：
- 我是否因为最先想到这个解决方案而对它有所偏爱？
- 我是否主动寻找过反对自己偏好的证据？
- 如果不考虑任何先前投入、从头开始，我还会推荐这个方案吗？
- 我是否受到近期经验的影响，而这些经验可能并不适用？
- 什么情况会让我改变对这项建议的看法？

缓解策略：
- 事前验尸：想象该决策已经失败；哪里出了问题？
- 唱反调：反驳你自己的建议
- 外部视角：基准概率对成功率有何启示？
- 主动寻求异议：咨询可能会质疑你的人
- 反转测试：如果有人提出相反的方案，你会怎么说？

原因：即使是专家，在时间压力下也会受到认知偏见的影响。
影响：偏见检查可避免 20-30% 的错误技术决策。

## 高级实施（10 分钟以上）

### 与 MoAI 工作流集成

SPEC 阶段集成：
- 在 /moai:1-plan 期间应用假设审计
- 在 spec.md 的问题分析部分记录假设
- 在 plan.md 中包含已考虑的替代方法
- 在 acceptance.md 中定义验证标准

DDD 阶段集成：
- 使用第一性原理识别核心测试场景
- 为遗留代码生成特征测试替代方案
- 为新功能生成规格测试替代方案
- 将权衡分析应用于测试覆盖率决策

质量阶段集成：
- 在代码审查流程中加入认知偏见检查
- 验证假设在实施后是否仍然有效
- 在最终文档中记录已接受的权衡

### 时间分配指南

复杂决策的建议投入分配：
- 假设审计：占分析时间的 15%
- 第一性原理分解：占分析时间的 25%
- 替代方案生成：占分析时间的 20%
- 权衡分析：占分析时间的 25%
- 认知偏见检查：占分析时间的 15%

分析与实施的总时间分配：
- 简单决策（1-2 个文件）：10% 用于分析，90% 用于实施
- 中等决策（3-10 个文件）：25% 用于分析，75% 用于实施
- 复杂决策（10 个以上文件）：40% 用于分析，60% 用于实施
- 架构决策：50% 用于分析，50% 用于实施

### 决策文档模板

战略决策记录：

决策标题：清晰说明所做的决策

背景：为何需要此决策

已审查的假设：
- 假设 1，包括置信度和验证状态
- 假设 2，包括置信度和验证状态

根因分析：
- 已识别的表层问题
- 通过五问法确定的根本原因

已考虑的替代方案：
- 方案 A，包括优点、缺点和评分
- 方案 B，包括优点、缺点和评分
- 方案 C，包括优点、缺点和评分

已接受的权衡：
- 所选方法带来的收益
- 我们牺牲了什么，以及为什么可以接受

偏见检查已完成：
- 确认已采取的偏见缓解措施

最终决策：选定的方案及其主要理由

成功标准：我们将如何衡量决策是否正确

审查触发条件：会促使我们重新考虑的情况

## 常见的自我辩解

| 自我辩解 | 事实 |
|---|---|
| “对这个决策进行第一性原理分析未免小题大做” | 看似简单的决策往往隐藏着未经验证的假设。第一性原理可以在它们演变成错误之前将其揭示出来。 |
| “我已经知道这些权衡了，没必要列出来” | 未列出的权衡对审查者而言是不可见的。明确的权衡表有助于做出明智的决策。 |
| “设计思维是用于 UX 的，不适用于后端架构” | 设计思维关注的是用户需求。每个 API 都有用户。同理心能够促成更好的接口。 |
| “系统思维对单模块变更没有任何价值” | 单个模块存在于系统之中。遗漏反馈循环和耦合点会导致生产环境事故。 |
| “我会选择显而易见的解决方案，然后继续推进” | 显而易见的解决方案往往只是最先想到的方案，而不是最佳方案。发散—收敛过程能够探索替代方案。 |

## 危险信号

- 做出架构决策时未列出考虑过的替代方案
- 设计文档中缺少权衡表
- 根本原因分析停留在表面症状（只问一次“为什么”，而不是五次）
- 在为偏好的方法辩护时未承认认知偏见
- 系统图中缺少反馈循环或外部依赖项
