# 界面评审

此技能运行跨学科评审。它将界面路由至各个 `better-*` 技能，收集它们的证据，并整合为一份按优先级排序的结论。

编排是它唯一负责的内容。无障碍规则属于 `better-accessibility`，结构属于 `better-layout`，文案属于 `better-writing`，字体排印属于 `better-typography`，色彩属于 `better-colors`，视觉打磨和动效属于 `better-ui`。绝不要在此处重复或覆盖它们的规则。

针对未提交工作、分支和拉取请求的变更范围评审属于 `interface-review`；它会解析范围并对发现项分类，然后再将评审交回。

## 证据，而非品味

严格把控升级触发条件，不要干涉经过审慎选择的项目决策。这两者方向一致。无论风格指南如何规定，触发条件都代表失败；而你仅仅不同意的密度、圆角或表达语气，并不是发现项。

因此，报告的门槛是证据，而非品味。给出 `Approve` 的门槛是：你确实检查了你声称检查过的内容。一份源于真实检查的简短报告，胜过一份为了显得详尽而填充内容的长报告。

## 核心原则

### 1. 先解析范围

根据请求和当前工作区推断屏幕、流程、功能或仓库范围。在输出中说明已解析的范围。

覆盖 **将领域技能作为事实来源** 下列出的每个领域技能中的全部内容，包括存在时的空状态、加载状态、错误状态和窄宽度状态。最多报告 15 个发现项。

当范围过大而无法进行可信检查时，将其缩小为一个完整流程：请求所聚焦的流程；若无法确定，则为每位用户都必须经过的入口路径。说明边界及其排除的内容。绝不要暗示未检查的界面已被评审。

### 2. 将变更发送至 `interface-review`

提及分支、拉取请求、提交范围或未提交变更的请求，属于变更评审，而非屏幕评审。请明确说明这一点，并要求用户运行 `interface-review`；该技能由用户调用，无法从此处启动。

绝不要在此处解析变更范围。读取差异、对发现项分类，以及将变更文件扩展至受影响界面，均属于 `interface-review`。猜测这些内容会导致报告拥有任何人都无法核验的范围。

当 `interface-review` 将评审交回时，它会提供变更范围、每个发现项的状态，以及变更范围的报告格式。严重程度、排序、数量上限和结论仍保留在此处，并且三者均只涵盖 `Introduced` 和 `Regression`。

### 3. 先侦察，再判断

识别框架、样式系统、组件库、设计令牌、支持的视口，以及任何预览或测试命令。以项目自身的惯用方式编写每项修复建议，从而不会有任何发现项变成采用不同技术栈的请求。这决定修复建议的形式，而非代码是否足够好。

然后阅读项目为其自身界面编写的内容：`CONTRIBUTING.md`、`CODING_STANDARDS.md`、`AGENTS.md`、`CLAUDE.md`、设计系统文档、Storybook 文档、界面 ADR。说明你找到了哪些，或者说明一个也没有。

阅读它们是为了确定一个问题应归属何处，而不是为了获得忽略它的许可。已有文档记录的约定并不能证明该约定是好的，“它在风格指南里”也不会让一个问题失效。它们改变的是你**在哪里**报告。当指南或共享令牌是原因时，针对该来源报告一次，并将各组件列为其位置。

### 4. 将领域技能作为事实来源

在审查之前，确认以下每个归属技能都可用。加载并应用每个可用的归属技能，并在汇总前完成每个领域的审查。

按以下顺序审查，以免基础性缺陷被润色问题掩盖：

1. `better-accessibility`
2. `better-layout`
3. `better-writing`
4. `better-typography`
5. `better-colors`
6. `better-ui`

对于此处加载的领域技能，采用其原则、参考资料和验证检查。其严重性分级和格式适用于独立使用；本文件中的汇总格式、共享严重性和问题数量上限将取代它们。

如果某个归属技能不可用，将该领域标记为 `Not reviewed`，注明其名称，并继续处理其余领域。不要凭记忆重建其规则，不要用相邻技能替代，也不要声称已实现整体覆盖。

当两个技能看似涵盖同一个问题时，将其归属给底层规则的所有者，并在**原因**单元格中注明次要影响。只报告一次。

### 5. 要求提供证据

每个问题都应引用 `path/to/file:line`，并展示当前实现。不要仅根据视觉外观报告代码层面的问题；当运行时行为决定结果时，也不要仅根据源代码报告视觉问题。

### 6. 按用户影响排序

使用统一的严重性等级：

- `HIGH`：阻塞任务、误导用户、隐藏内容或控件、造成数据丢失风险，或导致反复出现的系统性故障。
- `MEDIUM`：显著损害理解、效率、适应性或一致性。
- `LOW`：对任务影响有限的孤立润色问题。

在同一严重性内，按问题影响的范围以及一次修复带来的收益排序。令牌或共享组件修复的优先级高于同一症状出现在单个叶子节点中的情况。

**升级触发条件。** 一旦归属技能确认以下任一项，它就应直接判为 `HIGH`，绝不能因为表面问题看起来轻微而下调：

- 没有可访问名称的交互控件。
- 可通过键盘聚焦但没有可见焦点指示器的控件。
- 可通过指针访问但无法通过键盘访问的控件或路径。
- 忽略 `prefers-reduced-motion` 的动画或自动播放内容。
- 在 320px 宽度或 200% 缩放下被裁剪、重叠或无法访问的内容或控件。
- 其渲染后的对比度组合未达到所需比例的正文或控件文本。
- 仅通过颜色传达的状态或含义。
- 没有确认、撤销或明确区分处理的破坏性操作。
- 没有办法查看完整值的截断内容。
- 只能越过滚动边缘访问，或隐藏在没有可见提示的折叠内容之后的内容或控件。
- 未说明恢复方式的错误。
- 用于与其含义不符场景的语义颜色，例如将危险色调用于非破坏性操作。
- 仅通过动画传达的状态变化；当动画未运行时，没有颜色、图标或标签保留下来。

触发项优先于其他所有发现。当触发项数量超过上限允许的数量时，先列出它们，并说明上限排除了多少项。上限可以缩短报告；但绝不能成为未报告阻断项的原因。

这些规定的是严重程度，而不是新规则。归属技能决定症状是否存在；此列表决定它的代价。在变更评审中，针对触发项的已确认 `Regression` 即使同一症状作为既有问题时应为 `MEDIUM`，也属于 `HIGH`。

### 7. 优先选择成本更低的修复方案

严重程度说明一个发现有多严重；这里说明应提出哪种修复方案。当有多种方案可行时，选择以下最先适用的一种：

1. **删除。** 本可由间距承担作用的分隔符、高频交互上的动画、原生元素已使其冗余的 ARIA 属性、没有任何内容导入的色阶。
2. **使用平台能力。** 使用原生元素、原生控件或浏览器自身的焦点环，而不是自定义重建。
3. **复用项目已有内容。** 在引入任何新值之前，使用现有的令牌、间距步长或动效曲线。
4. **修正值。** 修正错误的缓动、圆角、间距或对比度组合，使用归属技能给出的精确值。
5. **添加。** 添加平台无法提供的新令牌、包装器、媒体查询或 ARIA 属性。

如果第 1 步可行，却在第 5 步提出修复方案，这本身就是一个发现。应报告删除方案。

### 8. 合并系统性发现

一个根本原因对应一个发现。在同一行中列出所有已确认的位置，而不是每个出现位置各占一行。绝不要为了达到上限而填充；简短的评审或没有发现都是有效结果。

### 9. 验证可以验证的内容

运行项目提供的安全且相关的检查。当运行时行为或视觉判断很重要时，检查渲染后的界面，并报告确切的命令或交互及其结果。无法运行的检查属于**未验证**，绝不是一个发现。

### 10. 默认在不修改的情况下评审

将评审请求视为只读。除非用户同时要求你实施这些发现，否则不要编辑源代码。当用户提出实施要求时，将合并后的报告作为变更范围，并在之后重新运行相关验证。

## 完成之前

| 错误 | 修复方式 |
| --- | --- |
| 六份彼此独立的领域报告 | 一张按优先级排序的发现表 |
| 仅根据源代码推断视觉声明 | 检查渲染状态，或将其标记为未验证 |
| 覆盖范围存在未说明的缺口 | 展示实际检查过哪些领域和状态 |
| 将缺少归属技能视为已覆盖 | 将该领域标记为 `Not reviewed`，并注明该技能 |
| 报告被修改文件中的每个遗留问题 | 在独立章节中列出三个既有发现 |
| 既有问题阻碍变更评审 | 将既有发现排除在上限和结论之外 |
| 变更从未涉及某领域，却将其标记为 `Clear` | 标记为 `Not reviewed: no evidence in the change scope` |

## 评审输出格式

格式位于 [review-format.md](review-format.md)：范围与覆盖情况、发现表、验证和结论。只有在其中报告发现后，评审才算完成。
