# 界面审查

此技能执行跨领域审查。它会将界面交由各个 `better-*` 技能审查，收集它们的证据，并汇总为一个经过排序的结论。

它仅负责编排。无障碍规则属于 `better-accessibility`，结构属于 `better-layout`，文案属于 `better-writing`，字体排印属于 `better-typography`，颜色属于 `better-colors`，视觉打磨和动效属于 `better-ui`。绝不要在此处重复或覆盖它们的规则。

针对未提交工作、分支和拉取请求的变更范围审查属于 `interface-review`；该技能会先确定范围并对发现的问题进行分类，然后再将审查交回。

## 证据，而非品味

严格关注升级触发条件，不要干预项目有意为之的选择。这两点方向一致。无论风格指南怎么说，触发条件一旦出现就意味着失败；而你仅仅不认同的密度、圆角或表达语气并不构成问题。

因此，报告问题的标准是证据，而非品味。给出 `Approve` 的标准是，你确实检查了自己声称检查过的内容。基于真实检查的简短报告，胜过为了显得全面而填充出来的冗长报告。

## 核心原则

### 1. 首先确定范围

根据请求和当前工作区，推断要审查的屏幕、流程、功能或仓库范围。在输出中说明确定后的范围。

针对 **将领域技能作为事实依据** 下列出的每个领域技能，完整覆盖该范围；如果存在空状态、加载状态、错误状态和窄宽度状态，也要涵盖。最多报告 15 个问题。

当范围过大、无法进行可信的检查时，将其缩小至一个完整流程：优先选择请求所聚焦的流程；若无法确定，则选择每位用户都必须经过的入口路径。说明范围边界及其排除的内容。绝不要暗示已审查实际上未经检查的界面。

### 2. 将变更交给 `interface-review`

如果请求指定了分支、拉取请求、提交范围或未提交的变更，那么它属于变更审查，而不是屏幕审查。明确说明这一点，并请用户运行 `interface-review`；该技能只能由用户调用，无法从此处启动。

绝不要在此处确定变更范围。读取差异、对问题进行分类，以及从已变更文件扩展到受影响的界面，都属于 `interface-review` 的职责。若凭空猜测，报告的范围将无法被任何人核验。

当 `interface-review` 将审查交回时，它会提供变更范围、每个问题的状态，以及变更范围报告格式。严重程度、排序、数量上限和结论仍由此处负责，并且这三项仅涵盖 `Introduced` 和 `Regression`。

### 3. 先侦察，再判断

识别框架、样式系统、组件库、设计令牌、支持的视口，以及所有预览或测试命令。使用项目自身的惯用方式编写每项修复建议，避免让任何问题最终变成要求采用不同技术栈的请求。这决定的是修复方案的形式，而不是代码是否足够优秀。

然后阅读项目为自身界面制定的文档：`CONTRIBUTING.md`、`CODING_STANDARDS.md`、`AGENTS.md`、`CLAUDE.md`、设计系统文档、Storybook 文档、界面 ADR。列出你找到的文档；如果一份也没有，也要明确说明。

阅读这些内容是为了确定问题发现应归属何处，而不是为了获得丢弃它的许可。已有文档记录的约定并不能证明该约定是合理的，而“它已写入风格指南”也不能让问题发现失效。它们改变的是你报告问题的**位置**。当某项指南或共享令牌是问题根源时，只针对该来源报告一次，并将相关组件列为其位置。

### 4. 将领域技能作为事实依据

在开始审查之前，确认以下每个负责领域的技能均可用。加载并应用每个可用的负责技能，并在汇总之前完成各领域的审查。

按以下顺序审查，以免基础性问题被表面优化所掩盖：

1. `better-accessibility`
2. `better-layout`
3. `better-writing`
4. `better-typography`
5. `better-colors`
6. `better-ui`

对于此处加载的领域技能，应采用其原则、参考资料和验证检查。其严重性等级和格式适用于独立使用；本文件中的汇总格式、统一严重性等级和问题发现数量上限将取代它们。

如果某个负责领域的技能不可用，请将该领域标记为 `Not reviewed`，注明其名称，然后继续审查其余领域。不要凭记忆重建其规则，不要用相邻领域的技能替代，也不要声称已实现全面覆盖。

当两个技能看似都涵盖同一个问题时，应将其归属给底层规则的负责技能，并在 **Why** 单元格中注明次要影响。只报告一次。

### 5. 要求提供证据

每项问题发现都要引用 `path/to/file:line`，并展示当前实现。当运行时行为决定结果时，不要仅凭视觉外观报告代码层面的问题，也不要仅凭源代码报告视觉问题。

### 6. 按用户影响排序

使用统一的严重性等级：

- `HIGH`：阻碍任务、误导用户、隐藏内容或控件、造成数据丢失风险，或引发反复出现的系统性问题。
- `MEDIUM`：对理解、效率、适应性或一致性造成显著损害。
- `LOW`：影响任务有限的局部细节问题。

在同一严重性等级内，根据问题影响的位置数量以及一次修复能带来的收益大小进行排序。令牌或共享组件层面的修复优先于某个末端位置中的相同症状。

**升级触发条件。** 一旦负责技能确认存在以下任一问题，应立即将其定为 `HIGH`，绝不能因为问题出现的界面区域较小而降低等级：

- 交互式控件没有无障碍名称。
- 可通过键盘访问的控件没有可见的焦点指示器。
- 某个控件或路径可通过指针访问，但无法通过键盘访问。
- 动效或自动播放内容忽略 `prefers-reduced-motion`。
- 在 320px 宽度或 200% 缩放时，内容或控件被裁切、重叠或无法访问。
- 正文或控件文本的实际渲染对比度未达到规定比率。
- 仅通过颜色传达状态或含义。
- 破坏性操作没有确认、撤销机制或明显不同的视觉处理。
- 内容被截断，且无法查看完整值。
- 内容或控件只能越过滚动边界才能访问，或隐藏在没有可见提示的展开区域后面。
- 错误信息未说明任何恢复方法。
- 语义颜色的使用违背其含义，例如将危险色调用于非破坏性操作。
- 仅通过动效传达状态变化，且当动画未运行时，没有留下任何颜色、图标或标签来表示该变化。

触发项的优先级高于其他所有发现。当触发项数量超过上限时，先列出它们，并说明有多少项因上限而未列出。上限可以缩短报告，但绝不能成为漏报阻断项的原因。

这些触发项用于确定严重程度，而非制定新规则。归属 Skill 负责判断症状是否存在；此列表负责确定其代价。在变更审查中，确认属于 `Regression` 且命中触发项的问题应定为 `HIGH`，即使同一症状作为既有问题时只会定为 `MEDIUM`。

### 7. 优先选择成本更低的修复方案

严重程度说明发现有多糟；本节说明应提出哪种修复方案。当有多个方案可行时，选择以下顺序中最先适用的方案：

1. **删除。** 可以用空格代替的分隔符、高频交互中的动画、原生元素已使其多余的 ARIA 属性、没有任何内容导入的色阶。
2. **使用平台能力。** 使用原生元素、原生控件、浏览器自带的焦点环，而不是自定义重建。
3. **复用项目现有内容。** 在引入任何新值之前，优先使用现有的设计令牌、间距级别或运动曲线。
4. **修正值。** 使用归属 Skill 给出的确切值，修正错误的缓动、圆角、间距或对比度组合。
5. **添加。** 添加新令牌、包装器、媒体查询，或平台无法提供的 ARIA 属性。

如果第 1 步已有可用方案，却在第 5 步编写修复方案，那么该修复方案本身就是一项发现。应改为报告删除方案。

### 8. 合并系统性发现

一个根本原因对应一项发现。将每个已确认的位置列在同一行中，而不是每次出现都单独占一行。绝不要为了达到上限而凑数；简短的审查或没有发现任何问题，都是有效结果。

### 9. 验证可验证的内容

运行项目提供的安全且相关的检查。当运行时行为或视觉判断很重要时，检查渲染后的界面，并报告确切的命令或交互及其结果。无法运行的检查应标记为 **未验证**，绝不能将其作为一项发现。

### 10. 默认以不修改内容的方式进行审查

将审查请求视为只读操作。除非用户还要求你实施这些发现，否则不要编辑源代码。如果用户确实提出实施要求，应将合并后的报告作为变更范围，并在完成后重新运行相关验证。

## 完成之前

| 错误 | 修复方式 |
| --- | --- |
| 六份彼此割裂的领域报告 | 一张按优先级排序的发现表 |
| 仅根据源代码推断视觉结论 | 检查渲染后的状态，或将其标记为未验证 |
| 未说明覆盖范围中的空缺 | 展示实际检查了哪些领域和状态 |
| 将缺少归属 Skill 的领域视为已覆盖 | 将该领域标记为 `Not reviewed`，并注明所需的 Skill |
| 报告被改动文件中的每个遗留问题 | 仅报告三项既有发现，并将它们放在单独的章节中 |
| 既有问题阻断变更审查 | 既有发现不计入上限，也不影响最终结论 |
| 变更从未涉及某领域，却将该领域标记为 `Clear` | 将其标记为 `Not reviewed: no evidence in the change scope` |

## 审查输出格式

输出格式定义在 [review-format.md](review-format.md) 中：范围与覆盖情况、发现表、验证结果以及最终结论。只有按该格式报告发现后，审查才算完成。
