# 界面审查

此技能执行跨学科审查。它会将界面分发给每个 `better-*` 技能，收集它们的证据，并汇总出一个按优先级排序的结论。

它只负责编排。可访问性规则属于 `better-accessibility`，结构属于 `better-layout`，文案属于 `better-writing`，字体属于 `better-typography`，颜色属于 `better-colors`，视觉润色和动效属于 `better-ui`。不要在此处重复或覆盖它们的规则。

未提交工作、分支和拉取请求的变更范围审查属于 `interface-review`，由它确定范围并对发现的问题进行分类，然后将审查结果交回。

## 证据，而非品味

要严格依据升级触发条件进行审查，并对经过深思熟虑的项目选择保持克制。这两者的作用方向相同。无论样式指南如何规定，触发条件所代表的都是失败；而仅仅是你不同意的密度、圆角或语气，并不构成问题。

因此，报告问题的标准是证据，而非品味。`Approve` 的标准是你确实检查了自己声称检查过的内容。一份来自真实检查的简短报告，胜过一份为了显得全面而堆砌内容的长报告。

## 核心原则

### 1. 先确定范围

根据请求和当前工作区，推断屏幕、流程、功能或仓库范围。在输出中说明已确定的范围。

覆盖 **Use domain skills as the sources of truth** 下列出的每个领域技能所涉及的全部内容，包括存在时的空状态、加载状态、错误状态和窄屏宽状态。最多报告 15 个问题。

当范围过大、无法可信地完成检查时，将其缩小为一个完整流程：优先选择请求所围绕的流程；如果无法确定，则选择每位用户都必须经过的入口路径。说明范围边界以及排除的内容。绝不要暗示未检查的界面也已经经过审查。

### 2. 将变更交给 `interface-review`

如果请求中提到了分支、拉取请求、提交范围或未提交的变更，那么这是变更审查，而不是屏幕审查。说明这一点，并要求用户运行 `interface-review`；该技能由用户调用，无法从这里启动。

绝不要在此处确定变更范围。读取差异、对问题进行分类，以及从变更文件扩展到受影响界面，都属于 `interface-review`。如果擅自推测，报告就会基于一个无人能够核验的范围。

当 `interface-review` 交回审查结果时，它会提供变更范围、每个问题的状态以及变更范围审查报告格式。严重性、排序、数量上限和结论仍由此处负责，并且这三者只涵盖 `Introduced` 和 `Regression`。

### 3. 先侦察，再判断

识别框架、样式系统、组件库、设计令牌、支持的视口，以及任何预览或测试命令。所有修复都要遵循项目自身的惯用方式，这样提出的问题就不会变成要求采用不同技术栈的请求。这决定修复的形式，但不决定代码是否已经足够好。

然后阅读项目关于自身界面所编写的文档：`CONTRIBUTING.md`、`CODING_STANDARDS.md`、`AGENTS.md`、`CLAUDE.md`、设计系统文档、Storybook 文档以及界面 ADR。说明你找到了哪些文档，或者说明没有找到任何文档。

阅读这些内容，是为了找到某个发现应归属的位置，而不是寻求放弃该发现的许可。有文档记录的约定并不能证明该约定是好的，“风格指南里就是这么写的”也不能让某个发现失效。它们改变的是你报告的位置。当某条指南或共享令牌是问题根因时，只针对该来源报告一次，并将相关组件列为其位置。

### 4. 使用领域技能作为事实依据

在开始审查前，确认以下每个负责方技能都可用。加载并应用所有可用的负责方技能，并在汇总前完成每个领域的审查。

按以下顺序进行审查，以免基础性问题被表面上的精致掩盖：

1. `better-accessibility`
2. `better-layout`
3. `better-writing`
4. `better-typography`
5. `better-colors`
6. `better-ui`

从此处加载的领域技能中，采用其原则、参考资料和验证检查项。其严重性分级和格式用于独立使用；本文件中的汇总格式、统一严重性和发现数量上限取代它们。

如果某个负责方技能不可用，将该领域标记为 `Not reviewed`，注明该技能并继续其余审查。不要凭记忆重新创建其规则，不要用相邻领域的技能替代，也不要声称已完成整体覆盖。

当两个技能看起来涵盖同一个问题时，将其归给底层规则的负责方，并在 **Why** 单元格中注明次要影响。只报告一次。

### 5. 要求提供证据

每个发现都要引用 `path/to/file:line`，并展示当前实现。当运行时行为决定结果时，不要仅凭视觉表现报告代码层面的发现，也不要仅凭源代码报告视觉层面的发现。

### 6. 按用户影响排序

使用统一的严重性分级：

- `HIGH`：阻碍任务、误导用户、隐藏内容或控件、造成数据丢失风险，或导致重复出现的系统性失败。
- `MEDIUM`：实质性损害理解、效率、适应性或一致性。
- `LOW`：对任务影响有限的局部润色问题。

在同一严重性内，按发现影响到的位置数量以及一次修复所带来的收益排序。令牌或共享组件层面的修复，优先于单个叶节点中的相同症状。

**升级触发条件。** 一旦负责方技能确认存在以下任一情况，就应立即定为 `HIGH`，绝不能因为影响面较小而平均降低：

- 没有可访问名称的交互控件。
- 键盘可访问但没有可见焦点指示器的控件。
- 可通过指针访问但无法通过键盘访问的控件或路径。
- 忽略 `prefers-reduced-motion` 的动效或自动播放内容。
- 在 320px 宽度或 200% 缩放下被裁剪、重叠或无法访问的内容或控件。
- 正文或控件文本的实际渲染对比度不符合要求的比例。
- 仅通过颜色传达状态或含义。
- 没有确认、撤销或明确区别处理的破坏性操作。
- 被截断且无法获取完整值的内容。
- 只有滚动到边缘之后，或打开没有可见提示的披露控件之后，才能访问的内容或控件。
- 没有说明任何恢复方式的错误。
- 语义颜色的使用违背其含义，例如在非破坏性操作上使用危险色相。
- 仅通过动效传达的状态变化；当动画未运行时，没有留下颜色、图标或标签等其他提示。

触发器的优先级高于所有其他发现。当触发器数量超过上限时，先列出它们，并说明有多少个触发器因上限而被排除。上限可以缩短报告，但绝不能成为遗漏阻断项的理由。

这些内容决定严重性，而不是新增规则。由所属 skill 判断症状是否存在；由此列表决定该症状的代价。在变更审查中，针对触发器确认的 `Regression` 即使同样的症状作为预-existing 问题时仅为 `MEDIUM`，也应为 `HIGH`。

### 7. 优先选择成本更低的修复方式

严重性说明发现有多严重；本节说明应提出哪种修复方式。当有多个修复方案都可行时，选择最早满足条件的方案：

1. **删除。** 例如，空格可以承担作用的分隔线、高频交互上的动画、原生元素已使其多余的 ARIA 属性、没有任何引用的渐变。
2. **使用平台能力。** 使用原生元素、原生控件、浏览器自带的焦点环，而不是自定义重建。
3. **复用项目已有内容。** 在新增任何值之前，优先使用已有的 token、间距步长或动效曲线。
4. **修正值。** 使用所属 skill 给出的确切值，修正错误的缓动、圆角、间距或对比度组合。
5. **新增。** 新的 token、包装器、媒体查询，或平台无法提供的 ARIA 属性。

在第 1 步可行时，却采用第 5 步编写的修复本身就是一个发现。应报告删除操作。

### 8. 合并系统性发现

一个根因对应一个发现。在同一行列出所有已确认的位置，而不是每次出现都单独占一行。绝不要为了达到上限而凑数；简短的审查或没有发现都是有效结果。

### 9. 验证可以验证的内容

运行项目提供的安全且相关的检查。当运行时行为或视觉判断很重要时，检查渲染后的界面，并报告确切的命令或交互及其结果。无法运行的检查应标记为 **未验证**，绝不能作为发现。

### 10. 默认以不修改内容的方式进行审查

将审查请求视为只读操作。除非用户同时要求你实施这些发现，否则不要编辑源代码。当用户要求实施时，应将合并后的报告作为变更范围，并在之后重新运行相关验证。

## 完成前

| 错误 | 修复 |
| --- | --- |
| 六份互不关联的领域报告 | 一张按优先级排序的发现表 |
| 仅根据源代码推断视觉结论 | 检查渲染后的状态，或标记为未验证 |
| 覆盖范围存在无声缺口 | 展示实际检查过的领域和状态 |
| 将缺少所属 skill 视为已覆盖 | 将领域标记为 `Not reviewed` 并注明该 skill |
| 报告所修改文件中的每个遗留问题 | 三个预-existing 发现，放在独立章节中 |
| 预-existing 问题阻碍变更审查 | 将预-existing 发现排除在上限和结论之外 |
| 变更从未涉及某领域，却将其标记为 `Clear` | 标记为 `Not reviewed: no evidence in the change scope` |

## 审查输出格式

格式位于 [review-format.md](review-format.md)：范围和覆盖情况、发现表、验证结果以及结论。只有按照该格式报告发现后，审查才算完成。
