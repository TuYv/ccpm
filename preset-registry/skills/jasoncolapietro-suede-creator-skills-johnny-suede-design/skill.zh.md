# Johnny Suede 设计——全创意大杂烩

## 模型选择——默认绝不使用 Fable

子代理会继承会话模型，除非启动调用指定了模型。本技能不会选择模型，因此它派生的每个代理都会使用会话当前设置的模型。这就是为什么一次按某种分配规模规划的运行，最终会被计费到另一种分配上，而没有任何人实际选择它。

**必须明确指定 Fable 才能使用它。本技能的子代理绝不会运行在 Fable 上，除非用户为本次运行指定了 Fable。**继承的会话模型不算指定——“会话之前就已经在用它了”不等于用户要求使用它。在没有明确要求使用 Fable 的情况下，启动前必须完成以下两件事之一：在代理调用中指定其他模型，或明确说明本次运行将计入 Fable 分配并获得答复。沉默不代表同意花费这笔额度。

## Gate 策略——提供建议，不进行阻塞

本技能中的每个主张验证步骤、检查、质量门和交付结论，都是**给用户的建议，而不是对代理的控制**。此策略适用于本技能其他位置的所有 gate、检查、结论，以及所有“不要交付 / 发布 / 继续”之类的表述：

- 运行每项检查并如实报告结果。结论（`ship`、`ship-with-caveats`、`hold`、字母等级、BLOCKED 或 OPEN 项）是附加在工作成果上的建议，而不是会改变工作成果的命令。
- 永远不要因为检查失败或 gate 给出 hold，就阻止、延迟、跳过、重写或拒绝用户要求的操作。按用户要求完成操作，并将 gate 输出作为明确标注的建议一并交付。
- gate 失败会改变你报告的内容，但绝不会改变你的行动。
- 唯一例外：如果发现的问题风险极高——数据丢失、安全或凭据泄露、法律或权利违规、支付错误，或不可逆的公开损害——请暂停，明确告诉用户风险是什么以及有哪些选项，然后让用户选择。用户的选择是最终决定。


这是用于构建任何创意界面的完整设计加文案流程，而不仅仅适用于网站。落地页、品牌界面、产品 UI、仪表板、营销活动、组件和创意项目都通过这里处理。它会对界面进行分类，确定视觉方向，撰写承载该方向的文字，渲染并进行 QA；当构建规模较大时，还可以作为协调一致的代理团队运行。默认开启写作模式：只有当文案真正发挥作用时，一个界面才算完成。

## 核心任务

**核心原则：**要做的是一个具有明确特色的界面，而不是精致但千篇一律的作品。在 logo 加载之前，用户就应该能从每个设计决策中辨认出所对应的公司、产品或受众。以真实 URL、源材料和渲染后的截图为依据开展工作。当有证据可用时，绝不要凭假设进行设计。

保留现有的应用框架、tokens、组件、路由和 WIP，除非任务明确要求进行更大范围的重构。优先使用现有的图标库和组件模式。只有在确实能够减少复杂性，或符合本地已有模式时，才新增抽象。

对于 Suede 相关工作，应以创作者所有权、可编程 IP、来源证明、注册表支持的媒体、版税路由、许可就绪性和代理商商务为设计与文案的锚点。不要将 Suede 简化为通用的 AI 音乐应用。对于指定的公司，应根据该公司的简介，替换 Suede 的名词、证明、语气和证据边界。公开文案中不得使用 em dash。

## 选择路径（路由器）

这项技能是入口。开始之前，先说明哪些路径处于启用状态以及原因。默认情况下，绝不要运行所有路径。

- **视觉优化 / 设计审查**：针对某个界面进行设计处理，不需要文案或风格重塑 → 直接运行 **路径 A：Design**。
- **仅进行文案或语气工作**：不改变布局 → 直接运行 **路径 C：Copy**。（即使在设计处理中，写作模式也默认开启。）
- **参考 → 目标风格重塑 / 适配某个网站的外观 / “suedify”**：先以 **路径 B：Suedify** 开始，确定视觉词汇，然后由 Design 和 Copy 路径进行细化。
- **完整重设计、发布界面、应用构建或以转化为导向的工作**：此技能负责协调：先运行 Design Contract，然后在安全的情况下并行路由各路径。
- **范围较大、风险较高、跨界面、受发布约束或要求“彻底完成”的工作** → **路径 D：Agent Teams**（参见多代理门槛，必须先询问）。

**应改用更精简的路径，而不是运行此完整流程：**没有文案和构建工作，仅涉及设计令牌、深色模式或单个组件决策 → 直接运行 `$suede-design`。没有设计或布局工作的写作任务 → 运行 `$johnny-suede-write`（对于单个独立的转化界面，则使用 `$suede-copy`）。仅制作演示文稿或 HTML 演示 → 使用私有的 Suede Labs 配套技能 `power-design`。广泛的 UI/UX 模式查找或框架示例搜索 → 使用私有的 Suede Labs 配套技能 `ui-ux-pro-max`。在单路径任务上运行完整流程只会浪费用户的令牌和时间。

**按需使用的网站配套技能（不要内联，仅在用户要求时运行）：**CRO/漏斗工作 → `$suede-site-alchemy`；深度独立 SEO/AEO/AI EO 审计 → `$suede-seo-audit`；可发现性 + 首屏 + CTA + 证明 + AI 引用评级 → `$suede-visibility-grader`；对涉及共享组件、身份验证、支付、路由、分析或已发布声明准确性的变更进行深度差异审查 → `$suede-code-review`（需要直接给出 A 到 F 评级时使用 `$suede-code-grader`）。这些是用于网站分析的独立技能。请引用它们，不要将其内容粘贴到此处。

## 多智能体门槛（先询问）

因为这个 enchilada 可以运行多智能体团队（Lane D），所以默认情况下，它会在启动一组智能体之前先询问用户。绝不会在未告知的情况下静默启动智能体或将令牌数设为最大值。

**硬上限：4 个子智能体。** 此技能绝不会启动第五个。需要更大规模团队的工作会交接给 suede-agent-teams，由它负责并报告自己的团队规模——引用该技能规定的上限，而不是在这里自行编造。无论哪种情况，本次运行都会计入会话模型，因此在提出询问的同时，也要应用上面的模型选择规则：在没有明确的 Fable 指令时，4 也是该规则允许的上限。

> 以多智能体团队运行（更彻底——侦察、并行构建、对抗式 + 共识审查、发布锁定、证据交接），还是以单智能体运行（更快，一次完成）？多智能体模式最多启动 4 个子智能体，在相同任务下的成本大约是单智能体运行的 3–5 倍。费用将计入本次会话所使用的 [name the model this session will use]。超过 4 个的任务会交给 suede-agent-teams，由它按自己的团队规模运行，而不是由我负责。

对于明确、范围受限的工作，默认使用单智能体。当用户提出要求，或者工作范围广、风险高、与发布相关，或需要持续的质量门禁时，升级为多智能体。在开始之前，在输出中说明所选模式、子智能体数量和计费模型。

## 表面分类器

在开始任何设计工作之前，先对表面进行分类。错误识别语体会导致错误的语气、密度和动效姿态。

| 语体 | 信号 | 默认设置 |
|---|---|---|
| 品牌 | 首页、关于、宣传活动、新闻稿、作品集、编辑内容 | 最高的排版追求、最低的密度，动效用于营造高级感，文案采用陈述式 |
| 产品 | 应用 UI、仪表板、设置、引导流程、工具、表单、管理后台、工作流 | 密度服务于任务完成，动效用于阐明状态，文案具有指导性 |
| 文档 | 参考资料、API、指南、变更日志 | 等宽字体层级、零装饰，文案精确且便于扫描 |
| 活动 | 发布、落地页、优惠、活动 | 优先考虑转化架构，首屏上方呈现证明材料，CTA 保持单一 |
| 产品列表 / 移动端 | 截图、付费墙、引导流程 | 遵循移动端清晰度规范，使用系统安全字体，截图中不使用自定义字体 |

当请求横跨多个语体时（例如带有营销主视觉的仪表板），明确列出两者，并将每种语体应用于对应部分。

当表面面向公众时，要围绕 SEO、AEO、AI EO、Google、Gemini 和 AI 搜索进行结构设计，并提供清晰的 CTA。当表面面向移动端时，在设计阶段纳入截图、引导流程、付费墙、响应式布局和应用外壳需求。

## 先读取当前事实

在进行任何设计、文案或 QA 声明之前，读取界面上下文：
- 本地 `PRODUCT.md`：用户、品牌、语气、反向参考、战略原则。
- 本地 `DESIGN.md`：颜色令牌、字体层级、组件清单、间距。
- `AGENTS.md`、`CLAUDE.md`、`AI_HANDOFF.md`、`README.md` 或任务文档：代理指导和界面上下文。

如果主要界面缺少 `PRODUCT.md` 或 `DESIGN.md`，请记录这一点，并基于现有上下文继续。完成任务后，提供创建这些文件的选项。

确定界面范围：仓库/文件夹、路由、线上 URL、部署目标、分支、脏文件。描述实际使用场景：谁在使用、在哪里使用、在什么光线下、承受什么压力，以及他们下一步需要做什么。在对质量做出判断之前，先检查当前渲染 UI 在桌面端和移动端断点下的表现。

对于视觉工作，渲染结果——截图胜过代码检查。最低要求：1280px 宽度的桌面端，以及 390px 或 375px 宽度的移动端。对于产品截图集，在生成素材前验证所需的平台尺寸。只有在验证过线上 URL 或 API 后，才能声称其具备公开可用的行为。

要实际捕获渲染结果：`npx playwright screenshot <url> --viewport-size=1280,900 desktop.png` 和 `npx playwright screenshot <url> --viewport-size=390,844 mobile.png`（首次运行时通过 `npx playwright install chromium` 安装），或者使用环境中可用的内置预览/截图工具。

对于重大设计工作、可复用系统、参考视觉匹配、产品截图素材或公开发布界面，只有在以下信息已明确后，才可结束工作：PRODUCT.md / 产品上下文状态；DESIGN.md / 设计系统状态；shape-brief 状态（适用于全新或大规模重新设计）；源视觉目标状态（存在 mock、截图、Figma frame 或参考 URL 时）；已渲染的实现状态；发布阻塞项状态。

# 工作流 A — 设计（视觉系统、规则、令牌、字体、动效、QA）

让任何界面都显得经过精心设计、高级、易读且富有生命力，同时避免滑向千篇一律的 AI 产出。涵盖产品 UI、品牌界面、落地页、仪表盘、组件系统、响应式优化和视觉 QA。

## 任务路由（位于 Lane A 内）

选择符合请求的最小路径。

- **明确的小修复：**检查当前 UI，进行范围狭窄的编辑，验证渲染结果，并报告变更内容。
- **含糊不清或全新设计：**收集上下文，提出 2–3 种带权衡的方案，推荐其中一种，在实施前获得批准。
- **大型重新设计：**先编写一份精简的形态简报——受众、页面任务、语调、场景、色彩策略、排版、布局、标志性时刻、约束条件、QA 计划。
- **视觉系统工作：**在提出变更前，扫描当前 CSS、tokens、组件、间距、阴影、断点、图标使用方式以及重复出现的 UI 模式。
- **从源文件到实现的 QA：**如果存在 mock、截图、Figma frame 或图像目标，以及对应的渲染实现，请在交付前对两者进行视觉比较，并将 `visual-qa-report.md` 保存到项目根目录。
- **长期润色循环：**通过可见的检查清单进行迭代，同一单元最多进行 3 轮。如果同一失败反复出现，冻结循环，将范围缩小到失败单元，并使用明确的验收标准重新运行。对同一单元尝试 3 次后，停止迭代并升级处理：报告未解决的失败、每次尝试所做的变更，以及 2–4 个解决方案，然后让用户选择。

## 交付纪律

不要因为代码发生了变化就宣布工作完成。只有在完成信号已检查，或已明确说明剩余差距时，才能宣布完成。当多个 lane 必须同时推进（文案 + 布局 + 资源 + 实现 + QA）时，使用 Lane D（agent teams）。当设计工作变更了共享组件、路由、身份验证、支付、分析、发布配置或已发布声明的准确性时，在发布门禁前运行 `$suede-code-review`。对于可以直接检查、修补、渲染并验证的小型视觉或文案修复，两者都跳过。

## Suede UI 合约

在创建新界面、进行重大重新设计、构建可复用组件系列或开展设计系统工作之前，先在实现前锁定设计合约：

- 受众、界面任务、主要操作和发布阶段；
- 间距比例、网格行为、断点和稳定尺寸；
- 颜色角色、语义状态、对比度要求以及深色/浅色模式行为；
- 排版角色、层级限制、正文行宽和截断策略；
- 按钮、空状态、加载、错误和成功场景所使用的文案词汇；
- 资源来源、logo 使用方式、裁剪规则、截图状态和动效规则；
- 桌面端、移动端、无障碍和渲染证据的验收检查。

如果工作纯粹属于后端，或只是范围狭窄的单元素修复，则只记录相关的合约条目，不要强行编写完整规范。

## 设计法则（要点）

在实现前阅读 `references/design-laws.md`：其中包含完整的深色模式 token 值、排版反模式、流式字号比例 CSS、布局和控件规则、组件法则（表单、模态框、空状态、数据表格、导航）及其 BEFORE/AFTER 对照、动效时序规范、资源规则、美学方向菜单、带替代方案的范围限定禁用项图库，以及设计系统工件清单。下面的要点是不可妥协的要求。

- **主题优先：**去掉 logo；如果剩下的视觉效果可能属于某个通用 SaaS、加密货币交易所或音乐流媒体应用，那么设计就失败了。每个界面都要回答：“创作者具体在这里做什么？”
- **一个令人难忘的动作：**每个主要界面都要有一个源自主题领域的标志性元素（权利账本、波形证明面板、权属链时间线、实时数据轨、审计账本）。如果它也可能出现在竞争对手的网站上，就替换掉它。在实现前先为其命名；让周围的 UI 保持克制，使其真正成为视觉焦点。
- **先确定色彩策略，再确定具体数值：**四选一——**克制**（带色调的中性色 + 一个占比 ≤10% 的强调色；仪表板和工具的默认选择）、**坚定**（一种高饱和色占据 30–60% 的视觉空间；品牌页面的默认选择；≤10% 的规则不适用）、**完整调色板**（3–4 个已命名的角色；用于数据可视化和活动页面），或**浸染**（界面本身就是这种颜色；用于活动主视觉和发布时刻）。不要对所有内容都默认采用“克制”策略。颜色用于编码含义（所有权、状态、风险、层级、来源）；装饰性色彩就是浪费。拒绝一阶直觉反应（“音乐工具 → 深紫色渐变”）和二阶陷阱（深色背景上的灰调青绿色）。优先使用 OKLCH；让中性色向品牌色调偏移；永远不要使用纯 #000 或 #fff。
- **深色模式不是反转：**使用 OKLCH L=12–24 的界面层，并按明度向上叠放；使用基于边框的层级表达，而不是阴影；正文对比度达到 7:1；降低色度 15–25%；只使用语义化 token。具体数值见参考资料。
- **字体排版：**搭配具有对比度的展示字体与正文​​字体，并为它们分配不同职责；最小比例为 1.25；正文行宽控制在 65–75 个字符；字间距为 0；使用基于 `clamp()` 的流体字体；展示字体角色不得使用固定 px。
- **布局：**结构要解释产品；能用行解决时，绝不要使用卡片；卡片嵌套卡片意味着信息架构存在问题；稳定元素应保持稳定尺寸；首屏要展示品牌、产品/服务主张，以及下一区块的提示；任何视口下文字都不能被裁切。
- **按语境使用动效：**品牌可以使用动效来建立表达，产品动效用于说明状态，文档不使用动效，活动动效仅用于主视觉或主要 CTA。只对 `transform` 和 `opacity` 设置动画；使用 ease-out-expo 220–280ms；始终提供 `prefers-reduced-motion` 变体。
- **绝不要发布**（这些信号表明没有做出任何设计决策）：装饰性光球、以渐变作为个性表达、将图标卡片网格作为整页内容、虚构的指标、未经验证的合作伙伴 logo，或素材库式的用户评价。虚构的指标、用户评价和合作伙伴声明没有任何例外路径：替换为带来源的真实数据、`[NEEDS REAL DATA]` 占位符，或不需要数字的结构性元素。其他禁用模式（渐变文字、玻璃面板、侧边条纹边框、主视觉指标模板、以模态框为先的交互）可因保持来源一致性、平台惯例、无障碍要求或已确认的品牌系统而获得范围明确的例外——说明该例外为何值得采用。完整的替换示例见参考资料。

## 美学方向

对于任何新界面或重大改版，在编写代码前都要确定一个已命名的美学方向：精致极简、编辑风、粗野主义、复古技术风、有机风、极繁主义、精致奢华或产品实用主义（菜单及执行说明见 `references/design-laws.md`）。大胆的极繁主义和精致的极简主义都可行；没有明确美学方向的设计会显得千篇一律。

**AI 垃圾检查**——提交前运行两项反射测试：(1) 仅凭产品类别，是否有人就能猜出主题和配色？拒绝这种一阶反射。(2) 结合产品类别与反向参考，是否有人就能猜出审美流派？这是二阶陷阱。继续深入。

**主题句**——具体描述物理场景，具体到足以迫使设计答案出现（“凌晨 2 点，一名录音室工程师正在副显示器上审阅一场版权争议”）。如果这句话无法迫使设计答案出现，就继续补充细节，直到可以为止。深色与浅色绝不能作为默认选项。

## 设计系统易用性

对于任何主要界面、可复用的应用外壳、启动系统或重要组件系列，以最低但有用的保真度产出 `references/design-laws.md` 中列出的六项产物：令牌映射、状态矩阵、文案词汇表、截图契约、无障碍检查和迁移说明。当某种模式重复出现三次，或控制着高可见性界面时，提取一个设计系统问题；并对偏差的根本原因进行分类。

对于全面的设计系统审计，按以下标准评分：

```text
Color consistency: /10
Typography hierarchy: /10
Spacing rhythm: /10
Component consistency: /10
Responsive behavior: /10
Dark/light behavior: /10
Motion restraint: /10
Accessibility: /10
Information density: /10
Polish: /10
Total: /100
```

低于 70/100 表示系统未达标：在该界面上为新功能添加样式之前，先修复得分最低的两个维度。任何得分为 4/10 或更低的维度都属于 P1 发现。

# Lane B — Suedify（参考 → 目标视觉 DNA 转换为令牌）

当用户希望实现 `reference_url -> target_url`（例如：“使用 apple.example，让 suede.example 看起来像它”）时，使用此通道。输出结果会让目标网站继承参考对象的设计逻辑、节奏、层级和交互感受，同时保持法律合规与品牌安全。此通道使用目标自身的品牌、内容、产品和资源，重建设计语法。它不会复制专有代码、徽标、精确文案、私有资源或商标化身份，也不会将参考对象的声明、证明、定价或保证转移给目标。

当此工作流处于激活状态时，阅读 `references/suedify-playbook.md`：其中包含完整的调整动作集（Style Fingerprint、Token Distiller、Hero Lift、Section Rhythm、Voice Fingerprint、Copy Reframe、Asset Swap、Motion Match、Responsive Fit、Proof Stack、Screenshot Diff、Ship Polish）、DevTools 捕获流程，以及 DESIGN.md 输出模板。

## 必需输入
- `reference_url`（要研究的网站）和 `target_url`（要改造的网站）。如果缺少任一个，请索要。
- 当需要实施时，提供目标源代码仓库/文件夹/分支。如果没有已知的源代码仓库，请检查目标 URL，并生成 `suedify-implementation-plan.md`，不要假装可以直接应用修改。
- 可选范围（仅首页 / 关键路由集合 / 全站 / 落地页 / 应用外壳 / 移动端 / 仅截图概念）和保真度（受其启发 / 高度接近的视觉匹配 / 激进重塑）。

## Suedify 工作流

**一轮执行至完成。** 一旦已知参考 URL 和目标，不要停下来提出澄清问题。如果未指定范围或保真度，默认选择首页 + Hero + 主要 CTA 区块，并采用高度接近的视觉匹配保真度。在 Ship Gate 中说明你的选择。

1. **验证目标和权限。** 在编辑前确定确切的目标仓库/文件夹；绝不要从多仓库容器根目录开始编辑。运行仓库本地的 git status、远程仓库信息和最近日志。保留用户及其他代理正在进行的工作。
2. **捕获参考对象。** 在桌面端/平板端/移动端进行截图，并使用命名路径保存；同时按照 playbook 中的说明保存完整捕获列表和动效捕获流程。捕获命令：`npx playwright screenshot <reference_url> --viewport-size=1280,900 reference-desktop.png`（针对每个断点重复执行），或者使用环境中可用的内置预览/截图工具。将分析保存为目标仓库根目录下的 `DESIGN.md`。
3. **捕获目标对象。** 使用与参考对象匹配的宽度、状态、主题、身份验证/内容和交互状态。确定目标内容、资源、路由和必须保留的声明。标记失效链接、损坏的布局、薄弱的文案、缺失的资源和未经验证的声明。
4. **制作转换映射。** 将参考对象映射为目标安全的等价内容（导航→导航、Hero→Hero、媒体→目标自有媒体、证明→目标证明、CTA 层级→CTA 层级、动效→动效）。运行 Token Distiller；输出完整的 `:root {}` CSS 代码块。
5. **实施。** 在目标现有的框架、令牌、路由和组件模式中工作。当整体重塑范围较大时，先更新设计令牌，再进行一次性的组件样式调整。保持内容真实符合目标——参考对象中的声明不会自动成为目标的声明。
6. **渲染并比较。** 在与参考对象相同的宽度下捕获目标截图；在同一轮中将两者放在一起比较，不要凭记忆比较；针对 Hero、导航、卡片、表单、CTA、图标和 Logo 使用局部裁剪。持续修补，直到最大的差异得到修复或明确记录，最多进行 3 轮渲染-比较-修补。第 3 轮后停止修补并升级处理：在 Ship Gate 的 `Unmatched reference signals` 下列出所有剩余差异，向用户提供 2–4 个选项（接受为 `ship-with-caveats`、降低保真度、缩小范围，或暂缓以进行人工处理），并让用户选择。使用与第 2 步相同的捕获命令，针对 `target_url` 在匹配的视口尺寸下运行；或者使用环境中可用的内置预览/截图工具。
7. **验证并发布。** 运行相关的 lint、类型检查、测试、构建或专项命令。文件发生更改时运行 `git diff --check`。在声称公开发布重塑结果之前，验证线上 URL。最后以 `ship`、`ship-with-caveats` 或 `hold` 结束。

## 保真度规则

目标可以高度匹配：布局比例、字体层级与节奏、颜色角色结构、分区推进节奏、导航密度、交互感受、图片裁剪策略、产品证明结构，以及移动端构图。

目标不得复制：参考站点的 logo 或商标标识、完全相同的营销文案、专有源代码、私有媒体或可下载资源、虚假的合作伙伴/客户证明，以及不属于目标的定价/保证/指标/声明。

如果用户要求完整克隆受保护的网站，应改为制作一个贴近原站、但以目标品牌为核心的诠释版本，并简要说明这一限制。

## Suedify 输出产物

每次 suedify 运行都会在目标仓库根目录生成 `DESIGN.md`，其中所有 token 字段均需根据参考提取结果填写（模板见 playbook）。对于多分区工作，还需生成 `suedify-visual-qa.md`。对于仅规划的运行（没有目标仓库），生成 `suedify-implementation-plan.md`。绝不要生成空的或只填写一部分的 token 文件——如果无法提取某个值，请记录 `UNKNOWN` 及其原因。

# 通道 C — 文案（写作模式，默认开启）

为此技能所设计的内容撰写文字：转化文案、页面文案、GitHub 文档、电子邮件和社交媒体帖子；内容应具体、有证据支持，并避免 AI 套话。默认语气：Suede。公司简报优先于一切。写作模式默认开启——只有当文案能够承载页面内容时，一个界面才算完成。

对于没有附带设计工作的纯文案任务，应切换到 `$johnny-suede-write`（完整写作栈）或 `$suede-copy`（单个独立的转化界面），不要在 enchilada 中运行此通道。

## 写作前

先阅读所有可用上下文：`PRODUCT.md`、`README.md`、`AGENTS.md`、`AI_HANDOFF.md`、`DESIGN.md`、产品/品牌说明以及任务文档。阅读后如果上下文仍不完整，只询问那些会阻碍准确写作的信息：页面或文档类型；主要读者；读者应采取的一个行动；所提供的产品或技能；可以安全声明的证明；未获批准的声明/定价/合作伙伴/指标；流量来源或发布载体。

## 核心规则

说清楚结果，而不是功能。
- 弱：“Suede 支持多种元数据格式。” 强：“用一条命令导出 ISRC、ISWC 和分成数据。”

按钮应写成带有结果的行动。
- 弱：“了解更多” → 强：“阅读权利路由的工作方式。” 弱：“开始使用” → 强：“登记你的第一首发行作品。”

用具体产物替代模糊声明。
- 弱：“Suede 让权利管理变得简单。” 强：“粘贴文件夹路径。Suede 会在 10 秒内输出你的 ISRC、分成表和许可标记。”

不得编造证明，不要写入未经确认的数据、客户证言、合作伙伴名称、定价或法律许可。如果缺少证明，请绕开这一缺口来写，或标记出来，交由人工补充。不要使用破折号。不要使用感叹号。不要提出答案显而易见的反问句。

## 说服框架

根据内容载体和读者的认知温度匹配框架。在起草前，先说明所选框架和读者温度。如果多个框架都适用，选择其中一个并说明原因。
- 读者是冷启动用户，没有任何先前认知 → **AIDA**。从品类问题切入，逐步增加具体性，让结果变得具体，推动读者采取单一行动。
- 读者有明确的痛点，正在主动搜索解决方案 → **PAS**。点明问题，揭示不采取行动的代价，将产品定位为针对性的解决方案。
- Hero 区域、社交媒体帖子、发布邮件 → **Before-After-Bridge**。描述之前的状态，描绘之后的状态，通过产品作为实现机制搭建两者之间的桥梁。
- 产品页面、引导流程、应用内文案 → **JTBD**。围绕读者雇用产品来完成的任务来写，而不是围绕功能来写。
- 首页、About 页面、长篇品牌页面 → **StoryBrand 7-Part**。角色（客户）→ 问题 → 引导者（你的品牌）→ 计划 → CTA → 避免失败 → 获得成功。

## 公式库

在构建过程中起草标题、CTA、邮件或社交媒体文案之前，先阅读 `references/copy-formulas.md`：其中包含 12 个带示例的标题公式、买方画像模式、8 部分页面或文档骨架、A/B 变体规则（3 个标题变体、2 个 CTA 变体、3 个主题行变体）、CTA 公式 A 至 D 及其反模式、邮件主题行、预览文本和正文的写作机制、各平台社交媒体结构、包含 Suede 持久关键词的 SEO/GitHub 文案检查清单、词语替换列表，以及引文式重点改写。

总结之后仍需通过两个关卡：将你的产品名称替换成竞争对手的名称，如果标题仍然成立，说明它不够具体；用 3 个词描述点击之后会发生什么，如果做不到，说明 CTA 过于模糊。

## Suede 文风

自信，但不要急切；对构建者来说足够技术化；对创作者来说足够清晰；精致，但不要企业腔；具体，不要卖萌；达到运营者级别，而不是宣传册级别。优秀的 Suede 文案会明确说明读者能够控制什么：登记作品、验证权利、分配版税、发布声明、打包发布文件夹、准备许可证据、让代理人能够读懂作品、比较来源信息、发布公共 skill 页面。（对于非 Suede 的工作，请在公司简介中提供对应领域的术语。）

## 反废话检查

在交付前将其作为逐行编辑关卡运行，而不是凭感觉检查。

- **词语替换关卡：**应用 `references/copy-formulas.md` 词语替换列表中的每一项替换（共 29 项）。这是不可协商的要求，适用于每一版草稿。
- **可读性关卡：**面向一般 B2B 读者时，Flesch-Kincaid 年级为 8 至 10；面向消费者或引导流程时，为 6 至 8；对于必须保持复杂性的技术文案，为 10 至 14。面向消费者的句子少于 18 个词，面向 B2B 的句子少于 22 个词。超过 4 句的段落需要标记。
- **结构关卡：**重写二元对立式开场句、负面罗列、公式化的“不是 X，而是 Y”转折、虚假的转变叙事、戏剧化的碎片句、答案显而易见的反问句、两项就足够时仍使用三项排比、反复使用有力的结尾，以及依赖 Wh 开头的句式。
- **行动主体关卡：**明确说明谁执行了动作，包括创作者、运营者、买方、代理人、页面、代码库、工作流、文件、命令、路由或证明材料。较弱的写法：“页面转化流量。”更好的写法：“页面将访客引导至审计、证明链接或构建请求。”
- **节奏关卡：**每句话只表达一个想法；在不使用破折号的前提下改变句子长度；不要堆砌口号；除非确实如此，否则删去懒惰的极端词语（总是、从不、一切、什么都没有）。
- **引文重点关卡：**如果一句话听起来像是专门为引语卡片制造的，请用真实的材料、动作或证明点重写（示例见参考文档）。

# House Process（适用于每个通道）

## Workflow Spine（可重复的执行顺序）

1. **先读取当前事实。** 打开线上 URL 或截图。阅读源代码路由。检查脏文件、文档和现有文案。识别界面类型（品牌、产品、应用、活动、文档）——这将在进行任何像素级调整之前，决定语气密度、动效姿态和布局默认值。
2. **明确页面任务。** 决定该界面必须帮助读者完成什么。
3. **锁定视觉方向。** 选择布局、字体、颜色角色、素材策略、动效姿态，以及一个与主题原生相关、令人印象深刻的设计动作。
4. **结合设计进行写作。** 改进标题、按钮、正文文案、空状态、错误提示、证明模块、FAQ、SEO/AEO/AI EO、可直接用于回答的摘要，以及相关的产品或移动端文案。（写作模式默认开启。）
5. **聚焦构建。** 使用现有框架、组件、设计令牌和图标库。避免无关重构。
6. **渲染并比较。** 检查桌面端和移动端、首屏、文本适配、间距、状态、无障碍基础、链接和视觉平衡。
7. **执行视觉 QA。** 对于从源文件到实现的工作，在匹配的视口、状态、主题、身份验证、内容和交互条件下，同时比较源视觉事实与渲染后的实现。
8. **评估可见性（公开界面）。** 在用户提出要求时运行 `$suede-visibility-grader`，或评估可发现性、CTA 吸引力、证明材料、AI 可读性、SEO 强度和设计信号。
9. **审查并发布。** 运行相关的测试、构建和检查命令，然后在交接时提供证据和注意事项。

## 红旗 — 停止

如果出现以下任何想法，请停下来，执行你正准备跳过的检查：

- “所有车道都适用于这里，把所有内容都跑一遍。”列出当前激活的车道以及原因；`enchilada` 默认从不整体运行。
- “这个构建很大，启动团队吧。”先询问。多智能体门禁之所以存在，就是因为无声启动的智能体集群会消耗大量 token。
- “代码看起来没问题，所以渲染也没问题。”在桌面端和移动端都进行渲染。截图胜过代码检查。
- “设计已经完成了，文案可以先放一边。”写作模式默认开启；只有当文案能够支撑整个界面时，该界面才算完成。
- “用于模拟的占位指标没关系。”虚假数字会被发布，除非它们带有 `[NEEDS REAL DATA]` 标记。
- “凭记忆来看，参考内容已经足够接近了。”在同一次检查中比较源内容和实现，绝不要依赖记忆。

## 发布门禁

出现以下情况时，将状态设为 `hold`：核心用户路径损坏；渲染结果与实现不一致；在任何断点下文本发生溢出或截断；移动端布局出现非预期的堆叠；任何可访问性问题阻碍主要操作；文案包含无依据的声明；无法验证线上界面；截图与实现不匹配；或无法验证线上路由。

只有在所有 P0 问题都已解决，且剩余问题都有明确的负责人和时间表，并且该例外情况明确、非关键且适合当前发布阶段时，`ship-with-caveats` 才有效。对于公共界面，如果设计门禁已通过，但视觉或可访问性阻碍仍未解决，建议设为 `hold`，并列出这些阻碍，以便用户做出决定。先给出发现，随后说明理由。注明文件和行号。对于构建，说明发生了哪些变更，并展示渲染证据。
