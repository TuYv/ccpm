# Johnny Suede Design — 全创意领域的 Enchilada

## 模型选择——默认绝不使用 Fable

子代理会继承会话模型，除非调用时指定了其他模型。本技能不会选择模型，因此它派生出的每个代理都会使用会话当时所设置的模型。这就导致原本按某一分配额度规划的运行，在无人选择的情况下被计费到另一分配额度上。

**必须明确指定 Fable 才能使用它。本技能的子代理绝不会运行在 Fable 上，除非用户为本次运行指定了 Fable。** 继承的会话模型不等于明确指定——“会话本来就在使用它”不代表用户要求使用它。在没有明确的 Fable 指令时，启动代理前必须二选一：在代理调用中指定其他模型，或者明确说明本次运行将计入 Fable 分配额度并获得答复。沉默不代表同意花费这笔额度。

## 闸门策略——提供建议，不进行阻塞

本技能中的每一步声明验证、检查、质量闸门和交付判定，都是**给用户的建议，而不是对代理的控制指令**。本策略适用于本技能其他位置的每一道闸门、每项检查、每个判定，以及所有“不要交付 / 发布 / 继续”之类的表述：

- 运行每项检查并如实报告结果。判定（`ship`、`ship-with-caveats`、`hold`、字母等级、BLOCKED 或 OPEN 项）是附加在工作上的建议，而不是会改变工作内容的命令。
- 绝不要因为某项检查失败或某道闸门判定为 hold，就阻止、延迟、跳过、重写或拒绝用户要求的操作。按用户要求完成操作，并将闸门输出作为清晰标注的建议一并交付。
- 闸门失败会改变你的报告内容，但绝不会改变你的行动。
- 唯一例外：如果发现的问题风险极高——例如数据丢失、安全或凭据暴露、法律或权利违规、支付错误，或不可逆的公开损害——请暂停，准确告知用户风险所在及可选方案，并让用户做出选择。用户的选择为最终决定。


这是用于构建任何创意界面的完整设计加文案流程，而不只是网站。落地页、品牌界面、产品 UI、仪表板、营销活动、组件和创意项目都通过这里处理。它会对界面进行分类，确定视觉方向，撰写承载其核心信息的文字，渲染并执行 QA；当构建规模较大时，还可以作为协同代理团队运行全流程。默认开启写作模式：只有当文案真正发挥作用时，一个界面才算完成。

## 核心工作

**核心原则：**目标是打造一个具体鲜明、而非精致却千篇一律的界面。在 Logo 加载之前，用户就应该能从每一项设计决策中辨认出指定的公司、产品或受众。以在线 URL、源文件和渲染截图为依据开展工作。当有证据可用时，绝不要凭假设进行设计。

保留现有的应用框架、tokens、组件、路由和 WIP，除非任务明确要求进行更大范围的重构。优先使用现有的图标库和组件模式。只有在确实能够消除复杂性，或符合本地已确立的模式时，才新增抽象。

对于 Suede 相关工作，应以创作者所有权、可编程 IP、溯源、注册表支持的媒体、版税路由、授权就绪状态和代理商商务为设计与文案的锚点。不要将 Suede 简化为通用的 AI 音乐应用。对于给定的公司，应根据该公司的 brief，替换 Suede 的名词、证明材料、语气和证据边界。公共文案中不得使用 em dash。

## 选择工作路径（路由器）

此技能是入口。开始前，先说明哪些路径处于启用状态以及原因。默认情况下，绝不要运行所有路径。

- **仅对界面进行视觉优化或设计调整**，不需要修改文案或重新设计风格 → 直接运行 **路径 A：设计**。
- **仅进行文案或语气工作**，不改变布局 → 直接运行 **路径 C：文案**。（即使在设计调整中，写作模式默认开启。）
- **参考对象 → 目标对象的风格重塑 / 调整网站外观 / “suedify”** → 先从 **路径 B：Suedify** 开始，以确定视觉词汇，然后由设计和文案路径进行优化。
- **完整重新设计、发布界面、应用构建或以转化为导向的工作** → 此技能负责协调：先运行设计契约，然后在安全的情况下并行分配各路径。
- **规模较大、风险较高、跨界面、面向发布，或要求“彻底完成”的工作** → 使用 **路径 D：代理团队**（参见多代理门槛，**先询问**）。
- **范围未知** → 先运行侦察步骤，阅读界面，然后在开始操作前说明所采用的语域和路径。

**应改用更低层级的技能，而不是运行此技术栈：** 没有文案和构建工作，仅涉及设计令牌、深色模式或单个组件决策 → 直接运行 `$suede-design`。没有设计或布局工作的写作任务 → 运行 `$johnny-suede-write`（单独的转化界面则使用 `$suede-copy`）。仅制作演示文稿或 HTML 演示 → 使用私有的 Suede Labs 配套技能 `power-design`。广泛的 UI/UX 模式查询或框架示例搜索 → 使用私有的 Suede Labs 配套技能 `ui-ux-pro-max`。对单路径任务运行完整技术栈会浪费用户的令牌和时间。

**按需使用的网站配套技能（不要内联，仅在用户要求时运行）：** CRO/漏斗工作 → `$suede-site-alchemy`；深入的独立 SEO/AEO/AI EO 审计 → `$suede-seo-audit`；可发现性 + 首屏 + CTA + 证明材料 + AI 引用评级 → `$suede-visibility-grader`；对涉及共享组件、身份验证、支付、路由、分析或已发布声明准确性的变更进行深入差异审查 → `$suede-code-review`（需要直接给出 A 至 F 评级时使用 `$suede-code-grader`）。这些是用于网站分析的独立技能。请引用它们，但不要将其内容粘贴到此处。

## 多智能体门槛（先询问）

由于这个 enchilada 可以运行多智能体团队（Lane D），因此默认情况下，它会在启动一组智能体之前先询问用户。绝不要默默启动智能体或将令牌数调至上限。

**硬上限：4 个子智能体。** 此技能绝不会启动第五个。需要更大规模智能体团队的工作会交给 suede-agent-teams，由它负责管理并报告自己的团队规模——引用该技能规定的上限，而不是在此处自行编造。无论哪种情况，本次运行都会计入会话模型，因此在提出询问的同时，也要遵循上文的模型选择规则：在没有明确 Fable 指令的情况下，4 也是该规则允许的上限。

> 运行多智能体团队（更彻底——侦察、并行构建、对抗式 + 共识审查、发布锁定、证据交接），还是单智能体（更快，一次完成）？多智能体模式最多启动 4 个子智能体，在相同任务下的成本约为单智能体运行的 3–5 倍。费用将计入本次会话所使用的 [在此处填写模型名称]。超过 4 个的需求将交给 suede-agent-teams，并由它按自己的团队规模执行，而不是由我负责。

对于明确且范围受限的工作，默认使用单智能体。当用户提出要求，或工作范围广、风险高、与发布相关，或者需要持续的质量门禁时，升级为多智能体。在开始前，先在输出中说明所做的选择、子智能体数量和计费模型。

## 界面分类器

在开始任何设计工作之前，先对界面进行分类。错误判断其类型会导致错误的语气、错误的信息密度和错误的动效策略。

| 类型 | 特征 | 默认设置 |
|---|---|---|
| 品牌 | 首页、关于、活动、新闻稿、作品集、编辑内容 | 最高的排版追求，最低的信息密度；动效应体现高级感；文案采用陈述式 |
| 产品 | 应用界面、仪表板、设置、引导、工具、表单、管理后台、工作流 | 信息密度服务于任务完成；动效用于阐明状态；文案具有指导性 |
| 文档 | 参考文档、API、指南、更新日志 | 使用等宽字体层级，零装饰；文案精准且便于扫描阅读 |
| 活动 | 发布、落地页、优惠、活动 | 首要考虑转化架构；首屏上方展示证明材料；CTA 保持单一 |
| 产品列表 / 移动端 | 截图、付费墙、引导 | 遵循移动端清晰度规范，使用系统安全字体；截图中不使用自定义字体 |

当请求涉及多种类型时（例如带有营销主视觉的仪表板），要同时标明两种类型，并将每种类型应用于对应部分。

当界面面向公众时，应通过清晰的 CTA 按钮，为 SEO、AEO、AI EO、Google、Gemini 和 AI 搜索进行结构化设计。当界面面向移动端时，在设计阶段纳入截图、引导、付费墙、响应式布局和应用外壳需求。

| 必需信息 | 来源 |

## 公司简报（非 Suede 工作）

以自然语言或以下字段提供：公司 / 产品或服务 / 受众 / 类别 / 语调 / 要使用的术语 / 要避免的术语 / 证明材料 / 允许的声明 / 禁止的声明 / 主要 CTA / 参考 URL / 资产或品牌规范。

当简报处于生效状态时，用简报中的内容替换所有 Suede 定位、领域语言和证据边界。保留完整工作流。在输出中将 "Cue Suede" 重命名为 "Cue [Company]"。

## 先读取当前事实

在进行任何设计、文案或 QA 声明之前，先读取界面上下文：
- 本地 `PRODUCT.md`：用户、品牌、语气、反向参考、战略原则。
- 本地 `DESIGN.md`：颜色 token、字号层级、组件清单、间距。
- `AGENTS.md`、`CLAUDE.md`、`AI_HANDOFF.md`、`README.md` 或任务文档：代理指导和界面上下文。

如果主要界面缺少 `PRODUCT.md` 或 `DESIGN.md`，请记录这一点，并基于现有上下文继续。完成任务后，主动提出创建这些文件。

识别界面：仓库/文件夹、路由、线上 URL、部署目标、分支、脏文件。描述具体使用场景：谁在使用、在哪里使用、在什么光线下、承受什么压力，以及他们下一步需要做什么。在对质量做出判断之前，先在桌面端和移动端断点检查当前渲染的 UI。

对于视觉工作，渲染结果——截图胜过代码检查。最低要求：宽度为 1280px 的桌面端，以及宽度为 390px 或 375px 的移动端。对于产品截图集，在生成资产之前，验证所需的平台尺寸。声称公开行为之前，验证线上 URL 或 API。

要实际捕获渲染结果，请使用：`npx playwright screenshot <url> --viewport-size=1280,900 desktop.png` 和 `npx playwright screenshot <url> --viewport-size=390,844 mobile.png`（首次运行时使用 `npx playwright install chromium` 安装），或者使用环境中可用的内置预览/截图工具。

对于重大的设计工作、可复用系统、参考视觉匹配、产品截图资产或公开发布界面，只有在以下事项明确后，才可以结束工作：PRODUCT.md / 产品上下文状态；DESIGN.md / 设计系统状态；全新设计或大型重新设计的形状简报状态；存在 mock、截图、Figma 画面或参考 URL 时的源视觉目标状态；已渲染的实现状态；发布阻塞项状态。

# 工作流 A — 设计（视觉系统、规律、token、字体、动效、QA）

让任何界面都显得经过刻意设计、高级、易读且富有生命力，同时避免陷入千篇一律的 AI 产出。涵盖产品 UI、品牌界面、落地页、仪表板、组件系统、响应式优化和视觉 QA。

## 任务路由（在 Lane A 内）

选择与请求相匹配的最小路径。

- **明确的小修复：**检查当前 UI，进行范围窄化的编辑，验证渲染结果，并报告所做的更改。
- **模糊或全新的设计：**收集上下文，提出 2–3 种带有权衡说明的方案，推荐其中一种，在实施前获得批准。
- **大型重新设计：**先编写一份精简的形态简报 — 受众、页面任务、风格基调、场景、色彩策略、排版、布局、标志性时刻、约束条件、QA 计划。
- **视觉系统工作：**在提出更改之前，扫描当前 CSS、令牌、组件、间距、阴影、断点、图标使用方式以及重复出现的 UI 模式。
- **源文件到实现的 QA：**如果有 mock、截图、Figma frame 或图像目标，以及一个已渲染的实现，则在交付前对两者进行视觉比较，并在项目根目录保存 `visual-qa-report.md`。
- **长期润色循环：**通过可见的检查清单进行迭代，同一单元最多执行 3 轮。如果同一问题反复出现，则冻结循环，将范围缩小到失败的单元，并使用明确的验收标准重新运行。对一个单元进行 3 次尝试后，停止迭代并升级处理：报告尚未解决的失败、每次尝试所做的更改，以及 2–4 个解决方案选项，然后让用户选择。

## 交付纪律

不要因为代码发生了变化就宣布工作完成。只有在完成信号已经过检查，或已明确说明剩余差距时，才能宣布完成。当多个路径必须同时推进时（文案 + 布局 + 资源 + 实现 + QA），使用 Lane D（代理团队）。当设计工作会更改共享组件、路由、身份验证、支付、分析、发布配置或已发布声明的准确性时，在发布闸门前运行 `$suede-code-review`。对于可以直接检查、修补、渲染和验证的小型视觉或文案修复，两者都跳过。

## Suede UI 合约

在创建新界面、进行重大重新设计、构建可复用组件系列或执行设计系统改造之前，先在实施前锁定设计合约：

- 受众、界面职责、主要操作和发布阶段；
- 间距尺度、网格行为、断点和稳定尺寸；
- 颜色角色、语义状态、对比度要求以及深色/浅色模式下的行为；
- 排版角色、层级限制、正文行宽和截断策略；
- 按钮、空状态、加载、错误和成功状态所使用的文案词汇；
- 资源来源、logo 使用方式、裁剪规则、截图状态和动效规则；
- 桌面端、移动端、无障碍和渲染证据的验收检查。

如果工作纯粹属于后端，或只是范围窄化的单元素修复，则只记录相关的合约条目，而不是强制编写完整规范。

## 设计法则（要点）

实施前阅读 `references/design-laws.md`：其中包含完整的深色模式令牌值、排版反模式、流式字体比例 CSS、布局和控件规则、组件法则（表单、模态框、空状态、数据表格、导航）及其 BEFORE/AFTER 对照、动效时间规范、资源规则、美学方向菜单、带替代方案的范围限定禁用项画廊，以及设计系统产物清单。下面的要点是不可妥协的要求。

- **主题优先：**去掉 logo；如果剩下的视觉效果可能属于一个通用 SaaS、加密货币交易所或音乐流媒体应用，就说明设计失败了。每个界面都要回答：“创作者具体在这里做什么？”
- **一个令人难忘的动作：**每个主要界面都要有一个源自主题本身的标志性元素（权利账本、波形证明面板、权属链时间线、实时数据栏、审计账本）。如果它可以出现在竞争对手的网站上，就替换掉它。在实现之前先为它命名；保持周围 UI 克制，让它承担起核心作用。
- **先确定色彩策略，再确定具体数值：**从以下策略中确定一种——**克制**（带色调的中性色 + 一个占比 ≤10% 的强调色；仪表板和工具的默认选择）、**坚定**（一种高饱和度颜色占据 30–60% 的视觉空间；品牌页面的默认选择；≤10% 的规则不适用）、**完整配色**（3–4 个已命名的角色色；用于数据可视化和活动页面），或**浸染**（界面本身就是这种颜色；用于活动主视觉和发布时刻）。不要对所有内容都默认使用克制策略。颜色用于编码含义（所有权、状态、风险、层级、来源）；装饰性颜色就是浪费。拒绝一阶条件反射（“音乐工具 → 深紫色渐变”）和二阶陷阱（深色背景上的低饱和青绿色）。优先使用 OKLCH；让中性色朝品牌色相偏移；绝不使用纯 `#000` 或 `#fff`。
- **深色模式不是反转：**使用 OKLCH L=12–24 的界面层，并逐层向明亮方向堆叠；通过边框表达层级，而不是使用阴影；正文对比度达到 7:1；色度降低 15–25%；只能使用语义化 tokens。参考中的数值。
- **排版：**使用具有对比度的展示字体/正文字体组合，并让两者承担不同职责；比例至少为 1.25；正文每行控制在 65–75 个字符；字间距为 0；使用基于 `clamp()` 的流式排版；展示类角色不得使用固定 px。
- **布局：**结构要解释产品；能用行解决时，绝不要使用卡片；卡片里嵌套卡片意味着信息架构出了问题；稳定元素要保持稳定尺寸；首屏要展示品牌、产品/服务 offer，以及下一个区块的提示；任何视口下文本都不得被裁切。
- **根据场景确定动效：**品牌可以使用动效，产品动效要阐明状态，文档不使用动效，活动动效只用于主视觉或主要 CTA。只为 `transform` 和 `opacity` 添加动画；使用 ease-out-expo 220–280ms；始终提供 `prefers-reduced-motion` 变体。
- **绝不要发布**（这些都表明没有做出设计决策）：装饰性 orb、把渐变当作个性、将图标卡片网格作为整个页面、虚假指标、未经核实的合作伙伴 logo，或库存式用户评价。虚假指标、用户评价和合作伙伴声明没有任何例外路径：用带来源的真实统计数据、`[NEEDS REAL DATA]` 占位符，或不需要数字的结构性元素替代。其他禁用模式（渐变文字、玻璃面板、侧边条纹边框、主视觉指标模板、模态框优先的交互）允许在来源保真度、平台惯例、无障碍或已确认的品牌系统等情况下进行范围明确的例外——说明该例外为何有充分依据。参考中提供了包含替代方案的完整图集。

**组件来源：**当构建需要本地系统缺少的基础原语、动画展示组件或 AI 聊天界面时，从 `references/ui-component-sources.md` 中经过审核的注册表获取，并在导入落地前运行其采用检查清单（优先本地化、重新设计 tokens、动效规范、许可证层级、渲染证明）。

## 审美方向

对于任何新界面或重大重新设计，在编写代码之前确定一个明确命名的审美方向：精致极简、编辑风、粗野主义、复古技术风、有机风、极繁主义、奢华精致风或产品实用主义（菜单及执行说明见 `references/design-laws.md`）。大胆的极繁主义和精致的极简主义都可行；没有明确方向的设计会显得千篇一律。

**AI 媒样检查**——在确定方案之前进行两项直觉测试：(1) 仅凭产品类别，是否就能猜出主题和配色？拒绝这种一阶直觉。(2) 结合产品类别和反向参考，是否就能猜出审美类型？这是二阶陷阱。要进一步突破。

**主题句**——具体描述物理场景，细致到足以迫使设计给出答案（“一名工作室工程师凌晨 2 点在副显示器上审查一项版权争议”）。如果这句话无法迫使设计给出答案，就继续补充细节，直到可以为止。深色或浅色绝不能作为默认选项。

## 设计系统的易用性

对于任何主要界面、可复用的应用外壳、启动系统或重要组件系列，以 `references/design-laws.md` 中列出的最小有效保真度产出六项成果：令牌映射、状态矩阵、文案词汇表、截图契约、无障碍检查和迁移说明。当某种模式重复出现三次，或控制着高可见性界面时，提取一个设计系统问题；同时对偏差的根本原因进行分类。

对于范围较广的设计系统审计，按以下标准评分：

```text
Color consistency: /10
Typography hierarchy: /10
Spacing rhythm: /10
Component consistency: /10
Responsive behavior: /10
Dark/light behavior: /10
Motion restraint: /10
Accessibility: /10
Information density: /10
Polish: /10
Total: /100
```

低于 70/100 表示系统未达标：在该界面上为新功能进行样式设计之前，先修复得分最低的两个维度。任何得分为 4/10 或更低的维度都属于 P1 问题。

## 视觉 QA 报告（Lane A）

将源视觉目标与实现进行比较时，保存 `visual-qa-report.md`，其中包含：
- 源视觉真值的路径或 URL
- 实现的路径、URL 或截图
- 视口和状态
- 主题、身份验证状态、内容/数据状态以及交互状态
- 全视图对比证据
- 重点区域对比证据，或说明为何不需要进行重点区域对比
- 按 P0/P1/P2/P3 严重程度排序的问题
- 上一次检查后所做的修复
- `final result: passed` 或 `final result: blocked`

在同一次视觉检查中比较源文件和实现，而不是凭记忆比较。使用 `npx playwright screenshot <url> --viewport-size=1280,900 impl.png`（将视口与源目标匹配）渲染实现；如果环境中提供了内置预览/截图工具，也可以使用该工具。检查排版、间距/布局、颜色/令牌、图像和资源的还原度、徽标/图标、文案/内容、加载/空/错误/悬停/聚焦/激活状态、响应式表现、无障碍，以及相关情况下的动效。如果缺少必需比较所需的源文件或渲染产物，或者仍存在可执行的 P0/P1/P2 问题，则使用 `final result: blocked`。只有在不存在任何可执行的 P0/P1/P2 问题时，才使用 `passed`。

# Lane B — Suedify（参考 → 目标视觉 DNA 翻译为 tokens）

当用户希望实现 `reference_url -> target_url` 时使用此通道（例如：“使用 apple.example，让 suede.example 看起来像它”）。输出结果会让目标网站继承参考网站的设计逻辑、节奏、层级结构和交互感受，同时保持法律合规和品牌安全。此通道使用目标网站自身的品牌、内容、产品和资源，重新创建其设计语法。它不会复制专有代码、徽标、精确文案、私有资源或商标化身份，也不会将参考网站的声明、证明、定价或保证转移给目标网站。

此通道启用时阅读 `references/suedify-playbook.md`：其中包含完整的操作集合（Style Fingerprint、Token Distiller、Hero Lift、Section Rhythm、Voice Fingerprint、Copy Reframe、Asset Swap、Motion Match、Responsive Fit、Proof Stack、Screenshot Diff、Ship Polish）、DevTools 捕获流程以及 DESIGN.md 输出模板。

## Required Inputs
- `reference_url`（要研究的网站）和 `target_url`（要进行转换的网站）。如果缺少任一项，请要求提供。
- 如果需要实施，还需要目标源代码仓库/文件夹/分支。如果没有已知的源代码仓库，则检查目标 URL，并生成 `suedify-implementation-plan.md`，而不是假装可以应用修改。
- 可选的深度（仅主页 / 关键路由集合 / 完整网站 / 落地页 / 应用外壳 / 移动端 / 仅截图概念）和保真度（受其启发 / 视觉上接近匹配 / 激进重塑）。

## Suedify Workflow

**一次性执行至完成。** 一旦已知参考 URL 和目标 URL，不要停下来询问澄清问题。如果未指定深度或保真度，默认为主页 + Hero + 主要 CTA 区块，并采用 close-visual-match 保真度。在 Ship Gate 中说明你的选择。

1. **Verify target and permissions.** 在编辑前确定准确的目标仓库/文件夹；永远不要从多仓库容器根目录开始编辑。运行仓库本地的 git status、remote 和 recent log。保留用户及其他代理正在进行的 WIP。
2. **Capture the reference.** 在桌面端/平板端/移动端进行截图并使用命名路径，同时按照 playbook 中的要求保存完整的捕获列表和动效捕获流程。将分析结果作为 `DESIGN.md` 保存到目标仓库根目录。捕获命令：`npx playwright screenshot <reference_url> --viewport-size=1280,900 reference-desktop.png`（针对每个断点重复执行），或者使用环境中可用的内置预览/截图工具。
3. **Capture the target.** 使用与参考网站匹配的宽度、状态、主题、登录状态/内容和交互状态。确定目标网站必须保留的内容、资源、路由和声明。标记死链接、布局损坏、文案薄弱、缺失资源和未经验证的声明。
4. **Make the translation map.** 将参考网站映射为对目标安全的等价物（导航→导航、Hero→Hero、媒体→目标自有媒体、证明→目标证明、CTA 梯度→CTA 梯度、动效→动效）。运行 Token Distiller；输出完整的 `:root {}` CSS 区块。
5. **Implement.** 在目标网站现有的框架、tokens、路由和组件模式中进行工作。当整体重塑范围较大时，先更新设计 tokens，再处理一次性的组件样式。确保内容符合目标网站实际情况——参考网站的声明不会自动成为目标网站的声明。
6. **Render and compare.** 在与参考网站相同的宽度下捕获目标网站截图；在同一轮处理中将两者放在一起比较，而不是凭记忆比较；针对 Hero、导航、卡片、表单、CTA、图标和徽标使用聚焦裁剪图。持续修补，直到最大的不匹配项得到修复或被明确列出，最多进行 3 轮渲染-比较-修补。在第 3 轮时停止修补并升级处理：在 Ship Gate 的 `Unmatched reference signals` 下列出所有剩余不匹配项，向用户提供 2–4 个选项（接受为 `ship-with-caveats`、降低保真度、缩小范围，或为人工处理暂缓为 `hold`），并让用户选择。使用与第 2 步相同的捕获命令，针对匹配的视口尺寸运行 `target_url`，或者使用环境中可用的内置预览/截图工具。
7. **Verify and ship.** 运行相关的 lint、typecheck、test、build 或聚焦命令。文件发生更改时运行 `git diff --check`。在声称已完成公开重塑之前，验证线上 URL。最后以 `ship`、`ship-with-caveats` 或 `hold` 结束。

## 保真度规则

目标可以高度匹配：布局比例、字体层级与节奏、色彩角色结构、区块推进节奏、导航密度、交互感受、图片裁切策略、产品证明结构以及移动端构图。

目标不得复制：参考网站的 logo 或商标标识、完全相同的营销文案、专有源代码、私有媒体或可下载资源、虚假的合作伙伴/客户证明，以及不属于目标的定价/保证/指标/声明。

如果用户要求完整克隆受保护的网站，应改为制作贴近原网站、但以目标品牌为核心的诠释版本，并简要说明这一限制。

## Suedify 输出产物

每次 suedify 运行都会在目标仓库根目录生成 `DESIGN.md`，其中所有 token 字段均须根据参考提取结果填写（模板见操作手册）。对于包含多个区块的工作，还要生成 `suedify-visual-qa.md`。对于仅规划的运行（没有目标仓库），生成 `suedify-implementation-plan.md`。绝不要生成空的或部分填写的 token 文件——如果无法提取某个值，记录 `UNKNOWN` 及其原因。

## Suedify 发布门禁

```text
Reference URL:
Target URL:
Target source:
Fidelity level:
Depth:
Screenshots:
Changed:
Verification:
Unmatched reference signals:
Legal/brand caveats:
Status: ship | ship-with-caveats | hold
```

当目标无法编辑、无法验证线上路由、主要布局出现问题、文案声明不实、不安全地复制了参考资源、未经批准便使用占位资源或 CSS/图形替代真实图片、导航/表单/CTA 无法正常工作、移动端构图出现问题，或目标不再呈现自身品牌特征时，使用 `hold`。

# Lane C — 文案（写作模式，默认开启）

为此技能所设计的内容撰写文字：转化文案、页面文案、GitHub 文档、电子邮件和社交媒体帖子；内容应具体、有证据支撑，并避免 AI 套话。默认语气：Suede。公司 brief 的优先级高于一切。写作模式默认开启——文案能够承载整个界面之前，该界面就还没有完成。

对于没有附带设计工作的纯文案任务，请切换到 `$johnny-suede-write`（完整写作流程）或 `$suede-copy`（单个独立的转化界面），不要在 enchilada 中运行此 lane。

## 写作前

先阅读所有可用上下文：`PRODUCT.md`、`README.md`、`AGENTS.md`、`AI_HANDOFF.md`、`DESIGN.md`、产品/品牌说明以及任务文档。如果阅读后上下文仍然缺失，只询问那些会阻碍准确写作的信息：页面或文档类型；主要读者；读者应采取的一个行动；所提供的产品或技能；可以安全声明的证明；未获批准的声明/定价/合作伙伴/指标；流量来源或发布渠道。

## 核心规则

描述结果，而不是功能。
- 不佳：“Suede 支持多种元数据格式。” 更好：“使用一条命令导出 ISRC、ISWC 和分成数据。”

将按钮写成带有结果的行动。
- 不佳：“了解更多” → 更好：“阅读权益路由的工作方式。” 不佳：“开始使用” → 更好：“注册你的第一条发行内容。”

用具体产物替代模糊声明。
- 不佳：“Suede 让权益管理变得简单。” 更好：“粘贴文件夹路径。Suede 会在 10 秒内输出你的 ISRC、分成表和授权标记。”

不得虚构证明，不要撰写未经确认的数据、客户评价、合作伙伴名称、定价或法律许可。如果没有可用的证明材料，就绕开这一缺口，或标记出来，交由人工补充。不得使用破折号。不得使用感叹号。不得提出答案显而易见的反问句。

## 说服框架

根据内容载体和读者的认知温度匹配框架。在起草前说明所选框架和读者温度。如果多个框架都适用，选择一个并说明原因。
- 读者是冷启动用户，没有此前认知 → **AIDA**。从品类问题切入，逐步增加具体性，让结果变得具体，推动读者采取单一行动。
- 读者已经明确感受到痛点，正在主动搜索解决方案 → **PAS**。点明问题，呈现不采取行动的代价，将产品定位为具体的解决方案。
- Hero 区块、社交媒体帖子、发布邮件 → **Before-After-Bridge**。描述此前的状态，描绘之后的状态，以产品作为实现转变的机制。
- 产品页、引导流程、应用内文案 → **JTBD**。围绕读者雇用产品来完成的任务来写，而不是围绕功能来写。
- 首页、About 页面、长篇品牌页 → **StoryBrand 7-Part**。角色（客户）→ 问题 → 指导者（你的品牌）→ 计划 → CTA → 避免失败 → 实现成功。

## 公式库

在 build 中起草标题、CTA、邮件或社交媒体文案之前，先阅读 `references/copy-formulas.md`：其中包含 12 个带示例的标题公式、买家角色模式、8 部分页页文档结构、A/B 变体规则（3 个标题变体、2 个 CTA 变体、3 个主题行变体）、CTA 公式 A 至 D 及其反模式、邮件主题行、预览文本和正文的写作机制、各平台的社交媒体结构、包含 Suede 持久关键词的 SEO/GitHub 文案检查清单、词语替换列表，以及引述改写示例。

摘要之后仍需通过两道关卡：将你的产品名称替换成竞争对手的名称，如果标题仍然成立，说明它不够具体；用 3 个词描述点击之后会发生什么，如果做不到，说明 CTA 过于模糊。

## Suede 语气

自信，但不急促；对构建者而言足够技术化；对创作者而言足够清晰；精致，但不官僚；具体，不卖萌；达到运营者级别，而不是宣传册级别。优秀的 Suede 文案会明确说明读者能够控制的事项：登记作品、验证权利、分配版税、发布声明、打包发布文件夹、准备许可证据、让代理人能够读懂作品、比较来源、发布公共 skill 页面。（对于非 Suede 的工作，在公司简介中提供对应领域的词汇。）

## 反废话检查

在交付前将其作为逐行编辑关卡执行，而不是凭感觉检查。

- **词语替换关卡：**应用 `references/copy-formulas.md` 词语替换列表中的每一项替换（共 29 项）。这是不可协商的要求，适用于每一份草稿。
- **可读性关卡：**面向 B2B 通用读者时，Flesch-Kincaid Grade 保持在 8 至 10；面向消费者和 onboarding 内容时，保持在 6 至 8；对于必须保持复杂性的技术文案，保持在 10 至 14。面向消费者的句子少于 18 个词，面向 B2B 的句子少于 22 个词。标记超过 4 句话的段落。
- **结构关卡：**改写二元对立式开场句、否定式罗列、公式化的“不是 X，而是 Y”转折、虚假的转变叙事、戏剧化的片段、自问自答的反问句，以及两个项目已经足够时仍使用三个项目的排比、重复的有力结尾和依赖 Wh 开头的句式。
- **行动主体关卡：**明确说明谁执行了动作，可能是创作者、运营者、买家、代理人、页面、仓库、工作流、文件、命令、路由或证明材料。较弱的写法：“页面将流量转化。”更好的写法：“页面将访客引导至审计、证明链接或构建请求。”
- **节奏关卡：**每句话表达一个想法；避免使用破折号，长短句交替；不要堆叠口号；除非确实如此，否则删掉懒惰的极端词语，例如“总是”“从不”“一切”“没有任何东西”。
- **引述关卡：**如果某句话听起来像是专门为引述卡片制造的，就用真实的成品、动作或证明点改写它（示例见参考文档）。

# 内部流程（适用于所有方向）

## 工作流主线（可重复的顺序）

1. **先读取当前事实。** 打开线上 URL 或截图。阅读源代码路由。检查有改动但尚未提交的文件、文档和现有文案。识别界面类型（品牌、产品、应用、活动、文档）——这会在进行任何像素级调整前，决定语气密度、动效姿态和布局默认值。
2. **明确页面任务。** 决定该界面必须帮助读者完成什么。
3. **确定视觉方向。** 选择布局、字体、颜色角色、素材策略、动效姿态，以及一个令人印象深刻且属于该主题的独特设计动作。
4. **结合设计撰写文案。** 改进标题、按钮、正文、空状态、错误信息、证明模块、FAQ、SEO/AEO/AI EO、适合直接回答的摘要，以及适用时的产品或移动端文案。（默认开启写作模式。）
5. **聚焦构建。** 使用现有框架、组件、设计令牌和图标库。避免无关的重构。
6. **渲染并比较。** 检查桌面端和移动端、首屏、文本适配、间距、各类状态、无障碍基础要求、链接和视觉平衡。
7. **执行视觉 QA。** 对于从源代码到实现的工作，在相同的视口、状态、主题、身份验证、内容和交互条件下，将源视觉事实与渲染后的实现放在一起比较。
8. **评估可见性（公共界面）。** 在被要求时运行 `$suede-visibility-grader`，或对可发现性、CTA 吸引力、证明材料、AI 可读性、SEO 强度和设计信号进行评分。
9. **评审并发布。** 运行相关的测试/构建/检查命令，然后带着证据和注意事项交接。

## 红旗信号 — 停止

如果出现以下任何想法，请停下来，执行你正准备跳过的检查：

- “这里所有 lane 都适用，把所有东西都跑一遍。”列出当前启用的 lane 及其原因；整套流程默认从不全部运行。
- “这次构建规模很大，组建团队吧。”先询问。之所以设置多智能体门禁，是因为无声运行的智能体群会消耗大量 token。
- “代码看起来没问题，所以渲染也没问题。”在桌面端和移动端都进行渲染。截图胜过代码检查。
- “设计已经完成了，文案可以先放一边。”默认开启写作模式；在文案能够支撑整个界面之前，这个界面就还没有完成。
- “给 mock 用一个占位指标没关系。”虚假数字会被直接发布，除非它们带有 `[NEEDS REAL DATA]` 标记。
- “凭记忆看起来已经足够接近参考了。”在同一轮中对比源文件和实现，绝不要依赖记忆。

## 发布门禁

出现以下任一情况时，使用 `hold`：核心用户路径中断；渲染结果与实现不一致；在任何断点下文本溢出或被截断；移动端布局出现非预期的堆叠；任何无障碍问题阻碍主要操作；文案做出了无依据的声明；无法验证线上界面；截图与实现不匹配；或无法验证线上路由。

仅当所有 P0 问题都已解决，且剩余问题都有明确的负责人和时间线，同时该例外情况明确、非关键且适合当前发布阶段时，`ship-with-caveats` 才有效。对于公共界面，当设计门禁通过但视觉或无障碍阻塞问题仍未解决时，建议使用 `hold`，并列出这些阻塞问题，以便用户做出决定。先给出发现，再说明理由。注明文件和行号。对于构建任务，说明发生了哪些变化，并展示渲染证据。
