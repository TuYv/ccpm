# COG 循环工程

> **简而言之：** 有些 COG 技能并非一次性提示词，而是循环：行动、观察、验证、决定是否继续。这项技能提供这些技能所使用的共享术语。铁律是：**信任确定性检查，绝不相信智能体自身声称“看起来已经完成”的自我报告。** 每个循环都必须声明其验证器、停止条件，以及它遵循的模式。

这是一份参考资料和设计辅助文档，而不是内容生成工作流。使用循环的技能（daily-brief、knowledge-consolidation、url-dump、weekly-checkin，以及 auto-research 和 scout 等研究/分诊技能）会链接到这里，而不是重复陈述这些规则。当你构建或修复迭代式技能时，请直接调用它。

## 为什么需要循环

链条执行固定步骤：先 A，然后 B，再 C。循环则是动态的：智能体采取行动、读取真实反馈（抓取到的页面、日期戳、文件数量），对反馈进行推理，然后重复执行，直到达成目标或触发停止条件。大多数“持续进行直到足够好”的知识工作都是循环，而明确指出循环，比寄希望于单个提示词一次就做到位更有利于 COG。

## COG 循环

```
   ┌──────────────────────────────────────────────┐
   │  1. Gather    pull context (vault + sources)   │
   │  2. Act       one step: search / fetch / scan  │
   │  3. Observe   read the real result             │
   │  4. Verify    run the deterministic check      │
   │  5. Update    write progress to a vault file   │
   │  6. Decide    continue?  → loop                │
   │               stop?      → finish + report     │
   └──────────────────────────────────────────────┘
```

第 4 步是承重核心。没有验证器的循环，只不过是一条不断重复的链条。

## 终止条件（使用多层机制，绝不能只有一个）

稳健的循环需要多个退出机制，以确保它总能停止：

| 退出机制 | 含义 | 示例 |
|------|-----------|---------|
| **确定性验证器** | 通过机械式的通过/失败判定来确认目标 | “发布日期在 7 天以内” |
| **硬性迭代上限** | 无论发生什么，都限制最大执行轮数 | “每个主题搜索 5 次后停止” |
| **预算护栏** | 限制最长时间、工具调用次数或 token 数量 | “总抓取次数达到 20 次后停止” |
| **无进展检测** | 最近几轮没有产生任何变化 | “连续 2 次搜索都未发现新内容” |
| **人工升级处理** | 将陷入停滞的循环交还给用户 | “询问两次后仍不明确：询问用户” |

每个循环都要选择一个验证器，以及至少一个安全退出机制（迭代上限或预算护栏）。无进展检测可以阻止那些仅靠迭代上限难以及时发现的隐性无限循环。

## 验证优先（将 COG 的规则应用于循环）

COG 坚持验证优先：不得产生幻觉，必须提供来源。在循环内部，这意味着：

- **优先采用机械式检查。** 日期比较、来源数量、“必填字段非空”检查、“文件已标记为已整合”检查都无法被操纵，也无法被幻觉伪造。
- **仅将基于判断的检查用于真正无法量化的问题**（这个主题确实是新的吗？这份摘要忠实于原文吗？）。当你必须使用判断时，请说明置信度并链接证据。
- **绝不接受智能体自身声称“我认为这已经完成了”。** 这是循环产出自信垃圾最常见的原因。

## 循环内上下文管理

长循环会让窗口充斥旧的工具输出，并开始发生偏移（“上下文腐化”）。可通过以下方式应对：

- **将状态外置到知识库。** 在执行过程中，将进度写入输出文件。知识库文件才是记忆；对话只是草稿区。
- **压缩并修剪。** 用一两行总结已完成的轮次。提取出所需内容后，丢弃原始页面文本。
- **隔离子智能体。** 在 `agent_mode: team` 中，只向每个工作智能体提供它所需的片段，并且只取回其结论，以便每个子任务都在干净的窗口中运行。绝不要将一个工作智能体的原始输出粘贴到下一个工作智能体的提示词中。

## 已命名的模式

| 模式 | 形式 | COG 的使用场景 |
|---------|-------|-------------------|
| **行动-观察（ReAct）** | 推理 → 行动 → 观察 → 重复 | 每个 COG 循环的基础 |
| **反思-重试（Reflexion）** | 失败时，写下经验教训，换一种方式重试 | url-dump / scout 获取重试、daily-brief 重新搜索 |
| **规划-执行-验证** | 规划步骤、执行步骤、逐一验证 | knowledge-consolidation 的各轮处理 |
| **评估器-优化器** | 生成内容、根据标准评分、重复直至通过 | daily-brief 条目验证、url-dump 质量门控 |
| **编排器-工作智能体** | 拆分为多个子任务，在全新窗口中运行并综合结果 | 团队模式扫描、auto-research 线程、team-brief |
| **循环直至无新内容** | 持续执行，直到连续 K 轮都没有发现新内容 | knowledge-consolidation 主题提取 |
| **人在回路中** | 当循环陷入停滞，或决定应由用户作出时，升级处理或询问用户 | weekly-checkin 反思、引导流程 |

## 失败模式与修复方法

| 失败模式 | 修复方法 |
|---------|-----|
| 上下文溢出 / 偏移 | 压缩、修剪、外置到知识库、隔离子智能体 |
| 无声的无限循环 | 无进展检测加上硬性上限 |
| 虚构成功 | 信任确定性验证器，绝不依赖自我报告 |
| 错误累积 | 尽早验证并在每一轮都验证，而不是只在最后验证 |
| 成本失控 | 设置预算防护，并在“足够好”时停止，而不是追求“完美” |
| 目标偏移 | 始终将目标和停止条件写在循环状态的顶部 |

## 技能如何使用此内容

技能的 `## Loop Engineering` 章节应简短而具体。它需要说明：

1. **循环**，用一两行说明（哪些内容会重复）。
2. **验证器**（机械式的通过/失败判定）。
3. **终止条件**（验证器加上安全退出条件）。
4. 上表中的**模式**。

它不会重述此技能的内容，而是指向这里。
