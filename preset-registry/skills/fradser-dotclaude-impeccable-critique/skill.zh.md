## 步骤

### 步骤 1：准备

调用 /impeccable，其中包含设计原则、反模式和**上下文收集协议**。在继续之前遵循该协议。如果尚不存在设计上下文，你必须先运行 /impeccable teach。此外，还需了解：该界面试图实现什么目标。

### 步骤 2：收集评估结果

启动两项相互独立的评估。为避免偏见，**两项评估都不得看到另一项的输出**。

你应该将每项评估分别委派给不同的子代理，以确保独立性。使用你所在环境的代理生成机制（例如 Claude Code 的 `Agent` 工具或 Codex 的子代理生成功能）。子代理应以结构化文本形式返回其发现。暂时不要向用户输出这些发现。

如果当前环境不支持子代理，则依次完成每项评估，并在继续之前将发现写入内部笔记。

**标签页隔离**：当浏览器自动化可用时，每项评估都必须创建各自的新标签页。绝不要复用现有标签页，即使其中已经打开了正确的 URL。这样可以防止两项评估的页面状态相互干扰。

#### 评估 A：LLM 设计审查

阅读相关源文件（HTML、CSS、JS/TS）；如果浏览器自动化可用，还需对实际页面进行视觉检查。**为此创建一个新标签页**；不要复用现有标签页。导航后，通过设置文档标题为该标签页添加标识：
```javascript
document.title = '[LLM] ' + document.title;
```
像设计总监一样思考。评估以下方面：

**AI 粗制滥造检测（关键）**：它是否看起来和其他所有 AI 生成的界面一样？对照 impeccable skill 中的全部**“不要”**准则进行审查。检查是否存在 AI 常用配色、渐变文字、深色辉光、玻璃拟态、首屏指标布局、千篇一律的卡片网格、通用字体以及所有其他明显特征。**检验标准**：如果有人说“这是 AI 做的”，你是否会立刻相信？

**整体设计审查**：视觉层级（视线流动、主要操作是否清晰）、信息架构（结构、分组、认知负荷）、情感共鸣（是否符合品牌和受众）、可发现性（交互元素是否显而易见）、构图（平衡、留白、节奏）、排版（层级、可读性、字体选择）、色彩（用途是否明确、一致性、无障碍性）、状态与边界情况（空状态、加载、错误、成功）、微文案（清晰度、语气、实用性）。

**认知负荷**（参阅 [cognitive-load](reference/cognitive-load.md)）：
- 执行包含 8 项的认知负荷检查清单。报告未通过项的数量：0-1 = 低（良好），2-3 = 中等，4+ = 严重。
- 统计每个决策点的可见选项数量。如果 >4，则标记出来。
- 检查渐进式披露：复杂内容是否仅在需要时才呈现？

**情感旅程**：
- 该界面会唤起什么情绪？这是有意为之的吗？
- **峰终定律**：最强烈的时刻是否是积极的？体验是否有良好的结尾？
- **情感低谷**：检查高风险时刻（付款、删除、提交）是否会引发焦虑骤增。是否提供了设计干预措施（进度指示器、安抚性文案、撤销选项）？

**尼尔森启发式原则**（参阅 [heuristics-scoring](reference/heuristics-scoring.md)）：
为 10 项启发式原则分别打 0-4 分。这些评分将呈现在报告中。

返回结构化的发现，涵盖：AI 粗制滥造判定、启发式原则评分、认知负荷评估、做得好的方面（2-3 项）、优先问题（3-5 项，包含问题内容、原因和修复方式）、次要观察，以及发人深省的问题。

#### 评估 B：自动检测

运行随附的确定性检测器，该检测器会标记 25 种特定模式（AI 粗制滥造的迹象和常规设计质量问题）。

**CLI 扫描**：
```bash
npx impeccable --json [--fast] [target]
```

- 将 HTML/JSX/TSX/Vue/Svelte 文件或目录作为 `[target]` 传入（任何包含标记的内容）。不要传入仅包含 CSS 的文件。
- 对于 URL，跳过 CLI 扫描（它需要 Puppeteer）。改用浏览器可视化。
- 对于大型目录（包含 200 个以上可扫描文件），使用 `--fast`（仅使用正则表达式，跳过 jsdom）
- 对于包含 500 个以上文件的情况，缩小范围或询问用户
- 退出代码 0 = 无问题，2 = 存在发现项

**浏览器可视化**（当浏览器自动化工具可用，且目标是可查看的页面时）：

叠加层是为用户提供的**视觉辅助工具**。它会直接在用户的浏览器中突出显示问题。不要滚动页面来截取叠加层的屏幕截图。应改为读取控制台输出，以编程方式获取结果。

1. **启动实时检测服务器**：
   ```bash
   npx impeccable live &
   ```
   记下输出到 stdout 的端口（自动分配）。使用 `--port=PORT` 可指定固定端口。
2. **新建标签页**并导航至目标页面（本地文件使用开发服务器 URL，其他情况使用直接 URL）。不要复用现有标签页。
3. 通过 `javascript_tool` **标记标签页**，以便用户区分：
   ```javascript
   document.title = '[Human] ' + document.title;
   ```
4. **滚动到顶部**，确保注入前页面已滚动至最顶部
5. 通过 `javascript_tool` **注入**（将 PORT 替换为步骤 1 中的端口）：
   ```javascript
   const s = document.createElement('script'); s.src = 'http://localhost:PORT/detect.js'; document.head.appendChild(s);
   ```
6. 等待 2-3 秒，让检测器渲染叠加层
7. 使用 `read_console_messages` 并设置模式 `impeccable`，**从控制台读取结果**。检测器会记录所有带有 `[impeccable]` 前缀的发现项。不要滚动页面来截取叠加层的屏幕截图。
8. **清理**：完成后停止实时服务器：
   ```bash
   npx impeccable live stop
   ```

对于包含多个视图的目标，在 3-5 个具有代表性的页面上执行注入。如果注入失败，则仅使用 CLI 结果继续操作。

返回：CLI 发现项（JSON）、浏览器控制台发现项（如适用），以及注明的所有误报。

### 步骤 3：生成综合评审报告

将两项评估综合成一份报告。不要只是简单拼接。将各项发现融会贯通，指出 LLM 评审与检测器结论一致之处、检测器发现了哪些 LLM 遗漏的问题，以及检测器的哪些发现属于误报。

以设计总监的方式组织反馈：

#### 设计健康度评分
> *参阅 [heuristics-scoring](reference/heuristics-scoring.md)*

以表格形式呈现尼尔森十大可用性启发式原则的评分：

| # | 启发式原则 | 评分 | 关键问题 |
|---|-----------|-------|-----------|
| 1 | 系统状态的可见性 | ? | [具体发现；如果表现良好，则填写“n/a”] |
| 2 | 系统与现实世界的匹配 | ? | |
| 3 | 用户控制与自由 | ? | |
| 4 | 一致性与标准 | ? | |
| 5 | 错误预防 | ? | |
| 6 | 识别优于回忆 | ? | |
| 7 | 灵活性与效率 | ? | |
| 8 | 美观且简约的设计 | ? | |
| 9 | 错误恢复 | ? | |
| 10 | 帮助与文档 | ? | |
| **总分** | | **??/40** | **[评级区间]** |

评分要诚实。4 分意味着真正出色。大多数真实界面的得分在 20-32 分之间。

#### 反模式结论

**从这里开始。** 这看起来像是 AI 生成的吗？

**LLM 评估**：你自己对 AI 粗制滥造痕迹的评估。涵盖整体审美感受、布局雷同、构图泛化，以及塑造个性的机会缺失。

**确定性扫描**：总结自动检测器发现的内容，并给出数量和文件位置。注明检测器额外发现但你遗漏的任何问题，并标记所有误报。

**视觉叠加层**（如果使用了浏览器）：告知用户，叠加层现在已显示在其浏览器的 **[Human]** 标签页中，并会突出显示检测到的问题。总结控制台输出所报告的内容。

#### 整体印象
简要给出直观感受：哪些方面有效、哪些方面无效，以及最值得把握的一个改进机会。

#### 做得好的方面
重点指出 2-3 个做得好的地方。具体说明它们为什么有效。

#### 优先问题
按重要性排序，列出 3-5 个影响最大的设计问题。

对于每个问题，使用 **P0-P3 严重级别**进行标记（严重级别定义请参阅 [heuristics-scoring](reference/heuristics-scoring.md)）：
- **[P?] 问题**：清楚地说明问题名称
- **重要性**：这会如何损害用户体验或削弱目标
- **修复方式**：应该如何处理（请具体说明）
- **建议命令**：可以使用哪个命令来解决此问题（从以下命令中选择：/animate、/quieter、/shape、/optimize、/adapt、/clarify、/layout、/distill、/delight、/audit、/harden、/polish、/bolder、/typeset、/critique、/colorize、/overdrive）

#### 用户画像风险信号
> *参阅 [personas](reference/personas.md)*

自动选择与此界面类型最相关的 2-3 个用户画像（使用参考文档中的选择表）。如果 `CLAUDE.md` 包含由 `impeccable teach` 生成的 `## Design Context` 部分，还应根据受众/品牌信息生成 1-2 个项目特定的用户画像。

对于每个选定的用户画像，逐步检查其主要用户操作，并列出发现的具体风险信号：

**Alex（高级用户）**：未检测到键盘快捷键。表单需要点击 8 次才能完成主要操作。强制使用模态框进行引导。放弃风险很高。

**Jordan（初次使用者）**：侧边栏采用仅图标导航。错误消息中使用技术术语（“404 Not Found”）。没有可见的帮助入口。将在第 2 步放弃。

请具体说明。指出哪些确切的元素和交互未能满足每个用户画像的需求。不要编写泛泛的用户画像描述；要写清楚他们在哪些地方受阻。

#### 次要观察
关于值得处理的较小问题的简要说明。

#### 值得思考的问题
可能有助于找到更好解决方案的启发性问题：
- “如果主要操作更醒目一些，会怎样？”
- “这真的需要让人感觉如此复杂吗？”
- “一个更自信的版本会是什么样子？”

**请记住**：
- 直截了当。含糊的反馈会浪费所有人的时间。
- 具体明确。说“提交按钮”，而不是“某些元素”。
- 既要指出问题所在，也要说明它为何会影响用户。
- 给出具体建议，而不只是说“可以考虑探索……”
- 严格确定优先级。如果所有事情都很重要，那就没有什么是真正重要的。
- 不要弱化批评。开发者需要坦诚的反馈，才能交付出色的设计。

### 第 4 步：询问用户

**展示发现的问题后**，根据实际发现提出有针对性的问题。停止并调用 AskUserQuestion 工具进行澄清。这些回答将决定行动计划。

可以按照以下思路提问（根据具体发现进行调整；不要提出泛泛的问题）：

1. **优先方向**：根据发现的问题，询问用户当前最重视哪个类别。例如：“我发现了视觉层级、颜色使用和信息过载方面的问题。我们应该先处理哪个方面？”提供最主要的 2–3 个问题类别作为选项。

2. **设计意图**：如果评审发现调性不匹配，询问这是否是有意为之。例如：“这个界面给人的感觉偏冷峻且商务化。这是预期的调性，还是应该更温暖、更大胆或更活泼？”根据能够解决已发现问题的方向，提供 2–3 个调性选项。

3. **范围**：询问用户希望处理多少问题。例如：“我发现了 N 个问题。你希望全部处理，还是只关注最重要的 3 个？”提供“仅处理最重要的 3 个”“处理所有问题”“仅处理关键问题”等范围选项。

4. **约束条件**（可选；仅在相关时询问）：如果发现的问题涉及多个方面，询问是否有任何不可改动的内容。例如：“是否有任何部分需要保持原样？”这样可以避免计划涉及用户认为已经完成的内容。

**提问规则**：
- 每个问题都必须引用报告中的具体发现。绝不要询问“你的受众是谁？”之类的泛泛问题。
- 最多提出 2–4 个问题。尊重用户的时间。
- 提供具体选项，而不是开放式问题。
- 如果发现的问题很明确（例如只有 1–2 个清晰的问题），则跳过提问，直接进入第 5 步。

### 第 5 步：建议的操作

**收到用户的回答后**，根据用户在第 4 步中确定的优先级和范围，给出按优先级排序的操作摘要。

#### 操作摘要

根据用户的回答，按优先级顺序列出建议的命令：

1. **`/command-name`**：简要说明需要修复的内容（包含评审发现中的具体背景）
2. **`/command-name`**：简要说明（包含具体背景）
...

**建议规则**：
- 只能推荐以下命令：/animate、/quieter、/shape、/optimize、/adapt、/clarify、/layout、/distill、/delight、/audit、/harden、/polish、/bolder、/typeset、/critique、/colorize、/overdrive
- 首先按照用户明确提出的优先级排序，其次按照影响程度排序
- 每项描述都应包含足够的背景信息，使该命令知道需要关注什么
- 将每个优先级问题映射到适当的命令
- 跳过不能解决任何问题的命令
- 如果用户选择了有限范围，则只包含该范围内的项目
- 如果用户将某些区域标记为不可改动，则排除会影响这些区域的命令
- 如果建议了任何修复操作，最后一步应为 `/polish`

展示摘要后，告诉用户：

> 你可以让我逐项运行这些操作、一次性全部运行，或者按照你喜欢的任意顺序运行。
>
> 修复后重新运行 `/critique`，查看你的评分提升情况。
