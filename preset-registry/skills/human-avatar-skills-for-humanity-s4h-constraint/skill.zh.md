# 约束

将约束推理应用于任何由限制塑造（或阻碍）可能性的情境。诊断需要开展哪种约束工作，并应用正确的工具。

## 哪种工具适用

| 你需要…… | 工具 |
|---|---|
| 检验一个声称存在的约束是否真实 | hardness-testing |
| 将约束转化为创意驱动力 | rule-inversion |
| 找到满足实际要求的最小范围 | scope-reduction |
| 绕过固定约束，寻找实现同一目标的路径 | workaround-mapping |

## 路由决策

**框定检查：**继续之前，确认具体约束及其正在阻碍的目标。用一句话说明你识别出的内容——约束本身及其正在阻止的事情——然后使用 `AskUserQuestion`：
- **问题：**“我的理解是：[用一句话框定约束及其正在阻碍的目标]。对吗？”
- **标题：**“框定”
- **选项：**
  - **是 — 继续** — 框定正确
  - **调整** — 有一处不准确；用户会先纠正，然后你再继续
  - **重新框定** — 实际情况与当前理解不同；继续之前先纳入用户的纠正

- **约束感觉可能只是一种假设、习惯或政治因素** → hardness-testing
- **约束确实存在，但你希望它发挥生成作用而不是形成阻碍** → rule-inversion
- **范围已经超出实际所需** → scope-reduction
- **约束确实固定，你需要绕过它** → workaround-mapping
- **不明确** → 首先使用 hardness-testing；大多数“约束”都会在审视下消解

## 确认方向

诊断出适用的工具后，使用 `AskUserQuestion` 工具确认方向。动态构建问题，并在其中包含你的诊断：

- **问题：**“我的判断是：**[诊断出的工具]** — [用一句话说明它为何适用]。你希望如何继续？”
- **标题：**“方向”
- **选项：**
  - **是，运行该工具** — 使用已提供的上下文立即执行诊断出的技能
  - **显示所有选项** — 列出此类别中的所有技能，并为每项提供一行说明
  - **快速版本** — 如果此情境存在较轻量的替代方案，则运行该方案
  - **重新诊断** — 重新审视情境描述，得出不同的判断

根据用户的选择继续。

## 硬度测试

*检验一个声称存在的约束是否真实。*

询问：是谁说这是固定不变的？这个决定是什么时候、在什么条件下做出的？最近有人测试过它吗？对约束进行分类：物理定律（真正的硬约束）、技术限制（很硬，但可能发生变化）、组织规则（软约束——有人可以改变它）、习惯或假设（根本不算约束）。对于软约束：需要什么才能推动它发生变化？目标是将真正的限制与那些仅仅因为容易接受而被当作约束的事物区分开来。

**输出：**约束分类（硬约束/软约束/假设）、支持该分类的证据；对于软约束，还需说明需要什么才能推动其发生变化。

## 规则反转

*将制约转化为创意驱动力。*

把制约明确表述为一项设计要求：“我们必须[制约]。”然后问：什么样的解决方案不仅能容忍这一限制，反而会真正*因它而变得更好*？制约会排除一些选项——它又让哪些剩余选项成为独有的可能？历史上一些最有趣的设计决策正是由限制促成的；限制不只是约束，也能让人聚焦。

**输出：** 将制约重新表述为一项要求，列出 3-5 个只有在这一制约下才可能出现的方向，并选出其中最值得进一步发展的方向。

---

## 范围缩减

*找出满足实际要求的最小方案。*

将想要的与需要的区分开来。对于当前范围中的每个要素：它实际完成的任务是什么？这个任务能否以更简单的方式完成，或者完全不做？提出这个问题：如果必须用一半的时间/预算/范围交付，我们会首先砍掉什么？答案往往会揭示哪些部分从来都不是真正必需的。最小可行版本通常比完整版本更清晰。

**输出：** 实际的核心要求。所有可以移除的内容。真正满足需求的最简单版本。

---

## 变通路径梳理

*在不消除固定制约的情况下寻找绕行路径。*

接受这一制约是固定不变的。然后梳理在此制约下存在的解决方案空间：如果这一限制是永久性的，还能做些什么？是否存在不必突破这一制约也能到达同一目标的替代路径？是否存在完全不会触及这一限制，却能获得 80% 价值的部分解决方案？绕过制约通常比尝试消除制约更快，也更持久。

**输出：** 在固定制约下可用路径的梳理结果，包括每条路径的投入和价值估算。给出最可行的变通方案及其理由。
