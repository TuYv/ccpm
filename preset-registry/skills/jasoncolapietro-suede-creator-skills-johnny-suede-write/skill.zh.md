# Johnny Suede Write

## 模型选择 —— 默认绝不使用 Fable

子代理会继承会话模型，除非启动调用明确指定了模型。这项技能没有选择模型，因此它派出的每个代理都会使用会话当前设置的模型。这样一来，原本按某个分配规模估算的运行，可能在无人选择的情况下被计入另一个分配。

**必须明确指定 Fable 才能使用它。除非用户为本次运行指定了 Fable，否则本技能的子代理绝不会运行在 Fable 上。继承的会话模型不算指定——“会话已经在使用该模型”并不等于用户提出了请求。在没有明确指定 Fable 的情况下，启动代理前必须二选一：在代理调用中指定其他模型，或者明确说明本次运行将计入 Fable 配额并征得同意。不得在未获得同意的情况下默默消耗该配额。**

## 门禁政策 —— 提供建议，不构成阻塞

本技能中的每个声明验证步骤、检查、质量门禁和发布判定，都是**给用户的建议，而不是对代理的控制**。本政策适用于本技能其他位置出现的所有门禁、检查、判定，以及“不要发布/不要公开/不要继续”之类的表述：

- 执行每项检查，并如实报告结果。判定（`ship`、`ship-with-caveats`、`hold`、字母评级、BLOCKED 或 OPEN 项）是附加在工作结果上的建议，而不是会改变代理行为的命令。
- 不得因为检查失败或门禁判定为 hold 而阻止、延迟、跳过、重写或拒绝用户要求的操作。按用户要求完成操作，并将门禁输出一并交付，明确标注为建议。
- 门禁失败改变的是报告内容，而不是要执行的操作。
- 唯一例外：如果发现极高风险的问题——数据丢失、安全或凭据泄露、法律或权利违规、支付错误，或不可逆的公开损害——请暂停，准确告知用户风险是什么以及有哪些选项，并让用户作出选择。用户的选择为最终决定。


写作总方案。所有写作请求都通过一项技能处理：长篇、短篇、GitHub 和文档、社交媒体、电子邮件、产品列表文案、品牌语调统一，以及面向公众的解释性演讲稿。默认采用 Suede 的品牌语调。用户提供的公司简报优先级最高。

**核心原则：**文案必须凭借具体名词、买家可见的结果、真实证据和一个主要行动来证明自己值得占据页面空间。不装饰，不虚构。

## 选择路径（路由器）

阅读请求，然后选择路径。大多数工作只属于一条路径；有些工作需要串联多条路径。

| 你想要…… | 路径 |
|---|---|
| 从零开始撰写或重写任何文案载体 | **写作模式**（如下）——选择具体模式 |
| 生成标题、CTA 或电子邮件主题 | **标题公式 / CTA 公式 / 变体协议** |
| 调整现有文案，使其听起来像 Suede，而不是泛泛的 AI 文案 | **品牌语调统一**路径 |
| 给公众用户一段用于向他人解释 Suede 的话 | **面向公众的解释性演讲稿**路径 |
| 审核/评估现有文案，并返回问题和评分 | **文案审计**输出格式 |
| 在撰写文案的同时进行元数据/结构/文案质量 SEO 检查 | **SEO 与 GitHub 文案** + **SEO 审计模式** |
| 撰写或收紧供代理阅读的文档（SKILL.md、CLAUDE.md、AGENTS.md） | **代理文档**路径 |

**改为下沉，而不是运行这套栈：**对于没有 SEO 审核或语气重新调整需求的单个独立转化界面（一个电子邮件、一个 Hero、或一组按钮），直接运行 suede-copy。当文案包含在设计或布局构建中时，运行 johnny-suede-design；其 Copy lane 会应用这些规则。对于在高风险公共界面上经过调研、分多个阶段完成的内容，升级到 suede-ship-copy。

跨 lane 任务（例如“重写主页、将其重新调整为我们的品牌语气，并提供社交媒体变体”）应在共享上下文中按顺序运行：编写界面文案，在其上运行 Brand-Voice Alignment，然后生成变体。说明你运行了哪条链路。

如果请求是完整的独立 SEO/AEO 审核并附带评分报告、将落地页转化为转化引擎、A-F 页面评级、代码评级/审查，或基于参考 URL 的重新设计，这些任务属于本写作范畴之外的专用 skills（suede-seo-audit、suede-site-alchemy、suede-visibility-grader、suede-code-grader、suede-code-review、suede-agent-teams、suede-design，或 johnny-suede-design 及其用于重新设计的 Suedify lane）。请将任务路由到相应 skill，并传递完整上下文；不要在此处重新实现这些功能。本 skill 负责写作。

## 多 Agent 默认规则

如果任务规模或风险足够大，需要作为协同 agent 团队运行（例如涵盖多个界面的完整发布包，或一个与多个 skill 中的审核和审查串联的写作任务），**请在启动任何任务前先询问用户**：“作为多 agent 团队运行（更全面），还是使用单个 agent？”明确说明，多 agent 模式可能比大多数情况多消耗一些 tokens。对于单个写作界面，直接写即可，无需询问。

## 写作模式

写作前确定模式。请在输出标题中说明所选模式。

**长篇**（博客文章、案例研究、白皮书、README、文档页面、产品列表描述）
- 以结果开篇，而不是以主题开篇。
- 结构：钩子 → 问题 → 机制 → 证据 → 行动。
- 最低要求：H1、2-3 个小标题、一个 FAQ 区块、meta description、可直接用于回答的摘要。
- 目标分数：62/70。

**短篇**（标语、Hero 标题、CTA、产品描述、社交媒体文案、引导页）
- 一个具体名词 + 一个买方可见的结果 + 一个动词。不要填充词。
- 提供 3 个不同长度的变体。字符数对于移动端、社交媒体和广告很重要，请注明字符数。
- 目标分数：65/70（密度和具体性权重更高）。

**GitHub / Docs**（README、SKILL.md、API 文档、变更日志、贡献指南）
- 第一句说明它做什么，而不是它是什么。
- 结构：单行描述 → 安装 → 快速开始 → 参考。
- 技术文档中不要使用营销语言。证据应是代码示例和可运行的命令。
- 目标分数：60/70（真实性和具体性权重更高）。

**面向 Agent 的文档**（SKILL.md、CLAUDE.md、AGENTS.md、指针所指向的参考文件）
- 读者是模型，因此目标是可预测的流程，而不是更好的句子：每次运行都通过文档采用相同路径。
- 先编写指针（`description`、`AGENTS.md` 行），再编写正文。决定 agent 何时访问这些材料的是指针的措辞，而不是指针的目标。
- 每一步都以 agent 可以检查的标准结束。每句话都必须能够改变模型的默认行为，否则就删掉。
- 目标分数：60/70。完整杠杆组：运行下面的 **Agent-Facing Docs** lane。

**社交媒体**（Twitter/X、LinkedIn、Instagram、Discord、发布帖）
- 以最具体的主张或结果开头，而不是先交代背景。
- 使用所提供的语气，并通过共享的 Slop Stop 检查，去除空洞的公告式表达。
- 交付内容：主帖 + 短版 + CTA + 3 个开场钩子变体。
- 平台结构和字数限制：阅读 `references/email-and-social-formats.md`。

**邮件 / 私信**（冷启动触达、发布邮件、培育邮件、公开说明简报）
- 主题行就是标题。最后再写主题行。
- 从读者的问题开始，而不是从发件人的消息开始。
- 每封邮件只提出一个请求。只使用一个 CTA。
- 交付内容：主题（3 个变体）+ 预览文本 + 正文 + CTA + P.S. 行。完整机制：阅读 `references/email-and-social-formats.md`。

## 写作前

在提问前，先阅读所有可用的上下文文件：`PRODUCT.md`、`README.md`、`AGENTS.md`、`AI_HANDOFF.md`、`DESIGN.md`、产品营销或品牌说明、任务专属文档。

如果阅读后仍缺少上下文，只询问会阻碍准确文案所需的信息：
- 页面或文档类型
- 主要读者
- 读者应采取的一个行动
- 所提供的产品或技能
- 可以安全声称的证明
- 尚未获批准的主张、定价、合作伙伴或指标
- 流量来源或发布渠道

## 核心规则

说清楚结果，而不是功能。
- 弱："Suede 支持多种元数据格式。"
- 强："用一条命令导出 ISRC、ISWC 和拆分数据。"

将按钮写成带有结果的行动。
- 弱："了解更多" → 强："阅读权利路由的工作方式"
- 弱："开始使用" → 强："注册你的第一版发行内容"

用具体产物替代模糊主张。
- 弱："Suede 让权利管理变得简单。"
- 强："粘贴文件夹路径。Suede 会在 10 秒内输出你的 ISRC、拆分表和许可标记。"

不要编造证明。不要写入未经确认的统计数据、用户推荐、合作伙伴名称、定价或法律许可。如果没有证明材料，就围绕这一缺口进行写作，或标记出来让人工补充。

除非公司简介另有规定，否则使用 Suede 的标点默认设置。Slop Stop 负责上下文相关的编辑规则；保留受保护的源文本片段和语气。

## 说服框架

根据渠道和读者的认知温度匹配框架。在起草前说明所选框架和读者温度。如果有多个框架都适用，选择一个并说明原因。

- 读者是冷受众，之前没有了解过：**AIDA**（认知 → 兴趣 → 渴望 → 行动）。从类别问题切入，逐步增加具体性，将结果描述得具体，推动读者采取单一行动。
- 读者有明确的痛点，正在主动搜索：**PAS**（问题 → 激化 → 解决方案）。点明问题，揭示不采取行动的代价，将产品定位为具体的解决方案。
- Hero 区块、社交媒体帖子、发布邮件：**Before-After-Bridge**。描述使用产品前的状态，描绘使用产品后的状态，再以产品作为实现转变的机制。
- 产品页面、引导流程、应用内文案：**JTBD**（待完成的任务）。围绕读者想要完成的事情来写，写他们雇用产品去完成的任务，而不是功能。
- 首页、关于页面、长篇品牌页面：**StoryBrand 7-Part**。角色（客户）→ 问题 → 向导（你的品牌）→ 计划 → CTA → 避免失败 → 获得成功。

## 标题公式

对于任何 hero 或电子邮件主题，至少生成 3 个标题候选，每个候选使用不同的公式。阅读 `references/headline-and-cta-formulas.md`，了解包含结构和示例的 12 种公式库（好奇心缺口、数字引导的具体性、如何实现结果、因为、具体性锚点、前后对比、真实问题、反转异议、如果那么、带证明钩子的主张、准确命名问题、权威加具体性）。

门槛：将你的产品名称替换成竞争对手的名称。如果标题仍然成立，说明它不够具体。重新改写后再评分。

## Persona 模式

在写作前说明 persona。它会改变词汇、证明类型和 CTA 表述。如果一个页面面向多个 persona，为决策者撰写 hero，并在次级部分加入实践者证明。

- **决策者**（高管、创始人、买家、投资者）：以结果和不采取行动的成本为主线，使用收入、风险、时间等维度；证明应是结果和明确点名的成果，而不是功能（“将发布准备时间从 3 天缩短到 40 分钟”）；CTA 应低风险且清晰（“查看工作流”）；跳过实现细节和 CLI 命令。
- **实践者**（开发者、设计师、运营人员、创作者）：重点说明工作原理，而不是它为何重要；证明应是命令、文件路径、架构示例、错误输出；CTA 直接明确（“运行 linter”“Fork 此 skill”）；跳过 ROI 语言和模糊的转变式主张。
- **怀疑者**（比较型买家、曾经失望过的人）：直接点出异议（“每个工具都声称能解决这个问题。以下是我们的不同之处。”）；证明应可由第三方验证（“打开脚本，阅读输出。”）；CTA 零压力（“阅读代码”“亲自运行”）；跳过炒作和最高级表述。
- **创作者 / 终端用户**（非技术人员）：用直白的语言说明他们会获得什么变化；证明应是人能理解的前后对比；CTA 应尽可能降低门槛（“用一个发布文件夹试试”）；跳过技术词汇和命令语法。

对于 GitHub/文档文案，默认使用实践者；对于销售/落地页，默认使用决策者；对于竞争或对比文案，默认使用怀疑者。

## 页面和文档结构

对于页面、README 或文档界面，构建以下主干。对于较小的部分，只使用适用的组件。

1. **Hero：** 用一句话说明结果。
2. **副标题：** 用一到两句话补充受众、工作流和证明。
3. **主要 CTA：** 读者现在可以采取的行动。
4. **证明：** 文件、脚本、文档、截图、URL、线上路由、示例或命令。
5. **工作原理：** 分为三或四个步骤，每步都包含一个动词和一个结果。
6. **安全性：** 说明该工作流不声称或不会做什么。
7. **FAQ：** 直接回答异议和搜索意图。
8. **最终 CTA：** 以更低的门槛重复该行动。

## 变体规范

对于任何标题、CTA、主题行或 hero 文案，默认生成 3 个变体，除非用户另有指定。为每个变体添加标签，说明其针对的维度，并推荐一个。让用户进行选择，而不是替他们猜测。

变体维度：具体性（一个抽象版本、一个中等具体版本、一个带具体数字或明确证明的高度具体版本）；语调（创始人口吻、产品口吻、面向怀疑者）；长度（完整的长句、压缩后的中等长度、简短有力的一击）。

每个渠道：标题提供 3 个角度（结果导向、问题导向、机制导向）；CTA 至少提供 2 个变体；邮件主题提供 3 个（好奇心或利益；社会证明或数字；直接提问或挑战）。

## CTA 公式

每个 CTA 都要回答：“我点击后会立刻发生什么？”四种公式及示例位于 `references/headline-and-cta-formulas.md`：动词 + 直接结果；动词 + 对象 + 利益；低承诺式表述（怀疑者/探索）；考虑后果式表述（决策者）。

需要删掉的反模式：“开始使用”（开始什么？）；“了解更多”（了解什么的更多信息？）；“注册”（具体注册什么？）；“免费试用”，但没有说明试用的具体内容；任何带感叹号的 CTA。

门槛：用 3 个词描述点击后会发生什么。如果做不到，说明 CTA 太模糊。

## 电子邮件和社交媒体格式

在起草任何电子邮件、DM、LinkedIn、X/Twitter 或 Instagram 文案之前，先阅读 `references/email-and-social-formats.md`：其中包含主题行公式、预览文本规则、5 部分邮件正文结构、降低退订率的发送顺序，以及各平台帖子的结构和格式限制。

即使经过总结，以下要求也不可妥协：最后再写主题；每封邮件只有一个请求和一个 CTA；预览文本要补充信息，而不是重复主题；社交帖子的前两行就是帖子正文；以最具体的主张开头，绝不要先交代背景。

## Suede 语调

使用以下语域：自信，但不急切；对构建者来说足够技术化；对创作者来说足够清晰；精致，但不企业腔；具体，不卖萌；达到运营者级别，而不是宣传册级别。

优秀的 Suede 文案会明确读者能够控制的事情：登记作品、验证权利、路由版税、发布权利声明、打包发布文件夹、准备许可证据、让代理能够读懂作品、比较来源信息、发布公共 skill 页面。

对于 Suede 的工作，将公开语言锚定在创作者所有权、可编程 IP、来源信息、注册表支持的媒体、版税路由、许可准备度和代理商业之上。不要把 Suede 简化成通用的 AI 音乐应用。（对于非 Suede 的工作，在公司简介中提供该领域对应的术语。）

## 品牌语调对齐路径

使用此路径，将*现有*文案调整为符合品牌语调，同时保留其原有特点，避免将其扁平化为通用的 AI 产品语言。这是编辑，而不是从零开始写作。

**语调规则：**
- 从读者能够执行的操作开始。
- 点明具体产物：技能、文档、脚本、报告、安装命令、权利护照、来源说明、分成核对、QA 检查清单。
- 优先使用创作者所有权、可编程 IP、权利、来源信息、注册表支持的媒体、版税路由、许可准备度和代理商业等表达。
- 避免使用模糊的“AI 音乐应用”框架。

## 面向代理的文档通道

当文档由代理而非人阅读时运行此通道：`SKILL.md`、`CLAUDE.md`、`AGENTS.md`，或指针所到达的参考资料。
人类文案争取注意力；代理文档消耗注意力，而且每一行始终加载的内容都会在每一轮消耗 token，无论它是否真正触发。

六个杠杆，按收益排序如下。完整方法以及每项的测试和好/坏示例，请阅读 `references/writing-for-agents.md`。

1. **强化指针。**上下文指针要指明代理上下文之外的材料，并编码访问该材料的条件。将指针的首要词放在前面，让每个分支恰好对应一个触发条件，并删去正文已经包含的身份信息。必须访问的材料如果藏在模糊的指针后面，这是方差缺陷，而不是风格问题：先强化措辞，再考虑是否内联材料。
2. **命名预算。**始终加载的材料会消耗*上下文负载*；必须由人记住的材料会消耗*认知负载*。在添加内容之前，先说明它消耗的是哪一种负载。
3. **放置在层级中。**放入文件内的步骤、文件内的参考资料，或通过指针披露的指针后参考资料。分支测试决定放置方式：每个分支都需要的内容内联，只有部分分支会访问的内容通过指针披露。超过约 100 行的参考资料移到 `references/`；`SKILL.md` 保持在 500 行以内。
4. **让步骤以可检查的标准结束。**“每个导出函数都有一行说明，注明由谁调用”胜过“直到你理解该模块”。模糊的界限会让代理提前结束；要求严格的标准会推动代理完成必要的调查。
5. **将重复表述压缩为首要词。**用一个模型已经掌握的紧凑概念（*tight*、*red*、*tracer bullet*）承载含义，将其作为 token 重复使用，但绝不再用句子复述，以较少的 token 锚定整个区域的行为。
6. **删去不胜过默认行为的内容。**一个含义只放在一个地方。将 `package.json`、配置和 `--help` 留给环境处理。删除模型本来就会遵循的完整句子。

将每条禁令改写为积极目标：“写单行注释”，而不是“不要写长注释”。通过禁令进行引导，会提高读者对被禁止行为的注意力，而不是抑制它。

交付修订后的文档，然后给出杠杆计数（指针得到强化、分支得到整合、标准得到明确、重复表述得到合并、无操作句得到删减）和评分。

## Anti-Slop Pass

在完成的草稿上运行 Suede Slop Stop（使用 suede-deslop）。加载其规范方法和完整的清理列表；不要再次运行第二套词语替换流程。保留提供的行文风格、刻意设计的语气和受保护的源文本片段。仅要求提供问题发现时，保持草稿不变。事实核验始终留在证据检查中，绝不要隐藏在风格编辑里。

然后运行下方的可读性检查和本写作者的 70 分评分。Slop Stop 的
/50 诊断不能替代此评分体系中的转化性、具体性或可发现性维度。

### 可读性门槛
面向 B2B 大众读者：Flesch-Kincaid 8-10 级；面向消费者/新手引导：6-8 级；面向技术/开发者的文案：10-14 级，在精确性需要更高复杂度时适用。消费者文案的平均句长低于 18 个词，B2B 文案低于 22 个词。标记超过 4 句的段落。

## 证据边界

此技能用于组织和准备文案。它不会清除权利、确认所有权、批准付款、写入注册表或保证结果。任何地方都不得出现竞品名称。

允许使用：创始人提供的事实、可验证的产品行为、已记录的集成、公开链接、可复现的命令。

移除：不在有效合同中的付款金额、未经基准测试的注册表写入时间、没有注明日期来源的排名、没有有效集成的合作伙伴 Logo、尚未发布的功能可用性，以及任何暗示法律许可、付款批准、分发、私有服务访问或结果保证的表述。

当某项声明处于边界状态时，将其改写为可测试的行为（“当你执行 Y 时，X 会发生”），而不是最高级表述（“最快 / 唯一 / 第一”）。只要出现权利、资金、注册表或发布相关表述，就添加证据边界。

## 工作流程

1. **选择路径。** 使用路由器。大多数任务只涉及一条路径。
2. **勘察内容表面。** 确定读者、页面类型、渠道、主要操作、证明材料、实时/来源 URL，以及相关的产品或移动端上下文和证据边界。
3. **确定语域和角色。** 明确谁在发声（创始人、产品、文档、公共说明、技术运营人员），以及读者与公司的关系（正在了解、正在评估、已经在使用）。在输出标头中说明所选语域和角色模式。
4. **设置写作模式。** 长篇、短篇、GitHub/Docs、社交媒体或电子邮件。写作前说明所选模式。
5. **先写结果。** 先说明读者可以做什么，而不是罗列功能。应用适合该内容表面的说服框架（AIDA、PAS、Before-After-Bridge、JTBD 或 StoryBrand 7-Part）。说明使用了哪个框架。
6. **构建证据链。** 使用真实文件、链接、截图、命令、文档、安装包、实时 URL 或产品产物。不得编造证明材料。
7. **执行可发现性检查。** 添加 SEO/AEO/AI EO 标题、元描述、H1、副标题、FAQ、可直接用于回答的摘要、内部链接、结构化数据说明，以及适用时的应用商店文案。仅当格式无法容纳时才跳过；说明跳过的内容及原因。
8. **运行 Suede Slop Stop。** 使用共享方法，然后执行该路径的可读性检查。清理时保留事实和语气。
9. **验证每条陈述。** 在每份公开输出中逐条应用证据边界。
10. **生成变体。** 对于任何标题、CTA 或主题行，按照变体协议为每项提供 3 个变体。为每个变体添加标签，并推荐其中一个。
11. **交付前评分。** 参见评分部分。如果低于阈值，先修改再交付。然后以正确的形式打包输出，并交付可直接使用的文案。

## 红旗 — 停止

如果出现以下任何想法，请停止并运行原本准备跳过的检查：

- “这份草稿看起来很干净，跳过 Slop Stop。”运行上下文检查；保留原本已经有效的措辞。
- “模式很明显，不需要说明。”说明模式、角色和框架，才能让结构保持诚实。
- “只是一个按钮标签，跳过评分。”微文案触达的读者可能比博客文章更多。
- “这个声明已经足够接近事实了。”差不多就是编造的证据。删除它，或明确标记它。
- “用户赶时间，不提供多个版本。”标题、CTA 和主题行的多个版本就是交付内容。
- “这是用户写的文案，弱化这个发现。”报告缺陷和实际测得的分数。不要以赞美开头，不要用重述文案优点来代替发现，也不要因为作者就在场而把低于门槛的分数向上取整。

## 发布门槛

在以下情况下，建议不要发布文案，并说明原因，把最终决定留给用户：

- 主要行动不明确
- 页面承诺了产品并未实现的功能
- 证据是虚构的或未经验证
- 文案隐藏了法律、付款、隐私或发布方面的限制条件
- 分数低于 58/70，或对于公开发布、首页、产品列表、GitHub、投资者相关内容或公开说明文案，分数低于 62/70
- 文案未通过竞品替换测试：将竞品名称替换进来后，文案仍然成立
