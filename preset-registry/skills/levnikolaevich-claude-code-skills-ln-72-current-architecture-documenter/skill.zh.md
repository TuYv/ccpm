# 当前架构文档编制者

**目标：** 对已检出仓库中实现的架构生成一份可信快照。记录实际存在的内容及其行为；不要对其评分、规定目标架构、修复代码，或将预期中的图表当作事实。

**执行约定：** 有序复选框是完成定义。将每一项在内部跟踪为 `PENDING`、带有具体证据的 `PROVEN`、带有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能构成证明。每完成一个章节后核对各项。返回之前，解决所有 `PENDING`，并且只统计 `PROVEN` 和 `CLEARED`；对每个缺口应用本技能的结论和批准规则。
保留用户意图、范围和现有授权。继续已获授权的工作；仅针对具有重要影响的未解决选择或所需的外部批准提问。根据实质性风险调整深度，但不得悄然跳过检查。保持依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 快照身份和工作树状态 | Git 状态、分支、远程仓库和 HEAD | 将提供的快照记录为 `UNVERIFIED` |
| 结构和配置 | 原生列表、搜索、清单和直接文件读取 | 缩小范围的手动检查 |
| 符号、依赖项和消费者 | 语言智能或已解析的依赖工具 | 搜索定义、注册、导入和调用方 |
| 运行时和部署拓扑 | 入口点、IaC、容器、CI、配置和运行时证据 | 将部署关系标记为 `UNKNOWN` |
| 文档修改 | 对已批准的架构文档进行最小化补丁 | 若没有已授权的可写路径，则返回 `BLOCKED` |

优先采用本地证据而非远程仓库状态。路径、图表或命名约定在可执行连线或权威契约确认之前仅是线索。

## 工件规则

- 复用清晰的当前状态架构文档；否则使用 `docs/architecture/current-state.md`。
- 将文档锚定到远程仓库、分支、HEAD、工作树状态和观察日期。
- 使用文件路径、符号、命令或配置键引用重要声明。
- 将声明标记为 `OBSERVED`、`DOCUMENTED`、`INFERRED` 或 `UNKNOWN`。
- 将实际结构与预期目标设计及审计发现分开。
- 先在粗粒度层面映射声明的系统范围，然后仅深入到能够解释其关键行为的程度；不要将有边界的请求扩展为全仓库清单。
- 优先使用面向职责的描述，而非详尽的文件清单。
- 记录证据截止点，以便读者区分未检查范围与真实不存在。
- 仅在影响架构理解时保留易变的计数或清单。

## 检查清单

### 1. 确立文档约定

- [ ] 明确仓库范围、目标读者、已批准的目标位置、所需深度和语言。
- [ ] 阅读仓库说明，并记录快照身份及脏工作树的限制。
- [ ] 搜索现有的当前状态、基线、目标设计、决策、图表和部署工件。
- [ ] 复用明确无歧义的当前状态文档，或选择默认路径，避免重复项目知识。
- [ ] 除已批准的架构文档外，本次运行保持只读。

### 2. 梳理系统广度

- [ ] 根据清单文件和 CI 识别语言、框架、包根目录、生成产物范围，以及规范的构建或运行命令。
- [ ] 识别用户、外部系统、入口点、应用程序、服务、进程、工作进程、定时任务和部署单元。
- [ ] 梳理主要领域或模块、职责、所有权和依赖方向。
- [ ] 梳理数据存储、缓存、队列、文件、外部 API、模式以及事实来源系统。
- [ ] 记录公共接口、运行时发现、注册机制、配置组合方式和环境边界。
- [ ] 记录构建、部署、扩缩容和故障边界，不要根据目录名称推断独立性。

### 3. 追踪关键行为

- [ ] 根据业务重要性和架构影响范围选择具有代表性的关键流程。
- [ ] 追踪每个流程，从参与者或触发器开始，经过入口点、运行时协调、领域行为、持久化或集成，到可观测结果。
- [ ] 在有证据的情况下，记录同步和异步跳转、事务归属、一致性、重试、超时、幂等性和错误传播。
- [ ] 描述从仓库证据中可见的部署、启动、关闭、健康检查、可观测性和恢复路径。
- [ ] 仅深入研究其复杂性或不确定性会影响架构理解的子系统；不要将普通实现细节纳入架构文档。

### 4. 编写当前状态产物

- [ ] 编写快照标识、系统上下文、组件清单、职责、依赖和数据流、运行时拓扑、关键流程、部署、所有权以及证据索引。
- [ ] 在文档中内嵌最少但有用的图表，或通过路径链接现有图表产物。
- [ ] 区分已观察到的实现与文档记录的意图，并明确列出偏差或矛盾，不要评定其严重程度。
- [ ] 除非有权威证据确立远程专属、仅运行时可见、组织层面或生产环境事实，否则将其标记为 `UNKNOWN`；区分已声明的部署配置与观察到的实际拓扑。
- [ ] 保留有来源且由人工维护的上下文及其证据状态；记录矛盾，并标记不受支持的历史声明，不要将其继承为已观察到的事实。

### 5. 验证并报告

- [ ] 根据已检查的快照证据验证每条引用，并删除不受支持的声明；只有在来源发生变化或此前的检查未能确立该声明时，才重新打开来源。
- [ ] 确认该梳理说明了关键行为如何被发现、执行、持久化和部署。
- [ ] 确认抽象层级没有混用，并确保正文和图表中的名称保持一致。
- [ ] 当快照有证据支持且有实际用途时，使用 `DOCUMENTED`；当重要拓扑仍然未知时，使用 `INCONCLUSIVE`；当无法安全确立仓库身份、范围或目标位置时，使用 `BLOCKED`。

## 自检

- [ ] **返回前进行协调。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或经授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

1. **Result：** 未执行 Skill 相关审查或变更，暂无可支持的结果。

2. **Scope：** 未提供待审查的 `SKILL.md` 片段、代码仓库、文件路径或具体任务；因此未确定审查范围、排除项、基线或实质性假设。

3. **Evidence：** 无可检查的 Artifact、快照标识、远程仓库、分支、HEAD、工作树状态或日期。未映射上下文、模块、运行时/部署、数据接口、归属关系及关键流程。未发现可确认的变更章节、图表或待运行时、组织及外部确认的声明。

4. **Verification：** 未执行检查、测试或清理操作；没有可用证据，也未产生外部状态变更。

5. **Completion：** `Checklist: 0/1 complete`  
   `Incomplete: UNPROVEN`：缺少待处理的文档或仓库上下文，无法形成 Skill-specific verdict；影响是无法确认任何结果、范围或风险；下一步是提供待翻译的英文 `SKILL.md` 片段，或提供需要审查/修改的仓库与具体目标。残余风险：全部审查结论仍未建立；所需决策：明确本次任务是翻译文档还是执行代码/Skill 审查。
