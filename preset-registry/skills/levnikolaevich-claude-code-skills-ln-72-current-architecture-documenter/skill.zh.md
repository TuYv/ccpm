# 当前架构文档编写器

**目标：** 对已检出仓库中实现的架构生成一份可信快照。记录现有内容及其行为方式；不要对其评分、规定目标架构、修复代码，或将预期设计图当作事实。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，并且仅在其操作和所需证据均已完成时将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的判定和批准规则应用于每个未完成项，并在开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项。

## 工具选择

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 快照标识和工作树状态 | Git 状态、分支、远程仓库和 HEAD | 将所提供的快照记录为 `UNVERIFIED` |
| 结构和配置 | 原生列表、搜索、清单文件和直接读取文件 | 有针对性的人工检查 |
| 符号、依赖项和使用方 | 语言智能或已解析的依赖项工具 | 搜索定义、注册、导入和调用方 |
| 运行时和部署拓扑 | 入口点、IaC、容器、CI、配置和运行时证据 | 将部署关系标记为 `UNKNOWN` |
| 文档修改 | 对已批准的架构文档应用最小补丁 | 如果没有获得可写路径的授权，则返回 `BLOCKED` |

优先采用本地证据，而非远程仓库状态。在可执行连接关系或权威约定确认之前，路径、图表或命名约定都只能作为线索。

## 产物规则

- 复用清晰的当前状态架构文档；否则使用 `docs/architecture/current-state.md`。
- 将文档锚定到远程仓库、分支、HEAD、工作树状态和观察日期。
- 使用文件路径、符号、命令或配置键引用支撑重要结论的证据。
- 使用 `OBSERVED`、`DOCUMENTED`、`INFERRED` 或 `UNKNOWN` 标记结论。
- 将实际结构与预期目标设计及审计发现区分开来。
- 首先绘制整个系统的全貌，然后仅深入分析解释关键行为所需的两到三个领域。
- 保留矛盾和不确定性，而不是根据偏好加以消解。
- 优先采用以职责为导向的描述，而非详尽的文件清单。
- 记录证据截止范围，以便读者区分未检查的范围与确实不存在的内容。
- 仅在易变的计数或清单会影响架构理解时才予以保留。

## 检查清单

### 1. 确立文档约定

- [ ] 明确仓库范围、目标读者、已批准的目标位置、所需深度和语言。
- [ ] 阅读仓库说明，并记录快照标识以及工作树存在未提交修改所带来的限制。
- [ ] 搜索现有的当前状态、基线、目标设计、决策、图表和部署产物。
- [ ] 复用含义明确的当前状态文档，或选择默认路径，避免重复记录项目知识。
- [ ] 除已批准的架构文档外，在整个执行过程中保持只读。

### 2. 梳理系统广度

- [ ] 从清单文件和 CI 中识别语言、框架、包根目录、生成内容以及规范的构建或运行命令。
- [ ] 识别用户、外部系统、入口点、应用程序、服务、进程、工作器、计划任务和部署单元。
- [ ] 梳理主要领域或模块、职责、归属关系和依赖方向。
- [ ] 梳理数据存储、缓存、队列、文件、外部 API、模式和记录系统。
- [ ] 记录公共接口、运行时发现、注册、配置组合和环境边界。
- [ ] 记录构建、部署、扩缩容和故障边界，不要根据目录名称推断独立性。

### 3. 追踪关键行为

- [ ] 根据业务重要性和架构覆盖范围选择具有代表性的关键流程。
- [ ] 追踪每个流程：从参与者或触发器开始，经过入口点、运行时协调、领域行为、持久化或集成，直至可观察的结果。
- [ ] 在有证据支持的情况下，记录同步和异步跳转、事务归属、一致性、重试、超时、幂等性和错误传播。
- [ ] 描述可从仓库证据中观察到的部署、启动、关闭、健康检查、可观测性和恢复路径。
- [ ] 仅深入分析最困难的两三个子系统；不要在架构文档中包含常规实现细节。

### 4. 编写当前状态产物

- [ ] 编写快照标识、系统上下文、组件清单、职责、依赖关系和数据流、运行时拓扑、关键流程、部署、归属关系和证据索引。
- [ ] 内联包含最少但有用的图表，或通过路径链接现有图表产物。
- [ ] 区分观察到的实现与文档记载的意图，并明确列出偏差或矛盾，但不评定严重程度。
- [ ] 当本地证据无法证实时，将仅存在于远程、仅存在于运行时、组织层面或生产环境中的事实标记为 `UNKNOWN`。
- [ ] 保留现有的人工维护上下文，除非仓库证据能够证伪；若确实证伪，则记录该矛盾。

### 5. 验证并报告

- [ ] 打开每个引用的文件或符号，并删除缺乏支持的断言。
- [ ] 确认该架构图谱解释了关键行为如何被发现、执行、持久化和部署。
- [ ] 确认没有混用抽象层级，并且正文和图表中的名称保持一致。
- [ ] 确认未引入目标建议、审计结论、产品代码、测试或外部状态。
- [ ] 当快照有证据支持且有用时，使用 `DOCUMENTED`；当重要拓扑仍然未知时，使用 `INCONCLUSIVE`；当无法安全确定仓库标识、范围或目标位置时，使用 `BLOCKED`。

## 输出约定

```markdown
# Current Architecture Documentation

**Verdict:** DOCUMENTED | INCONCLUSIVE | BLOCKED
**Artifact:** path
**Snapshot:** remote, branch, HEAD, worktree state, observed date

## Architecture mapped
- Context, modules, runtime and deployment units
- Data, interfaces, ownership, and critical flows

## Evidence limitations
| Claim or area | Status | Evidence inspected | Exact next action |
|---|---|---|---|

## Changes made
- Created or updated sections and diagrams

## Residual unknowns
Facts that require runtime, organizational, or external confirmation.
```
