## 首先澄清

在优化注册流程之前，请确认以下信息。如果其中任何一项未知或含糊，请询问——不要自行假设：

- [ ] **流程类型**——免费试用、免费增值、付费或候补名单（决定可接受的摩擦程度和最小字段集）
- [ ] **B2B 还是 B2C**——B2B 可以接受更多字段；B2C 需要尽可能减少摩擦（决定 SSO 的优先级和字段数量）
- [ ] **当前字段 + 完成率 + 流失情况**——基准数据及需要消除的摩擦点（每移除一个字段约可提升 10%）
- [ ] **首次使用产品前真正需要的数据**——区分必填字段与可推迟收集或通过数据补全获取的字段（“首次使用前”测试）

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草”，则继续执行，并在审计报告顶部列出你的假设。

| 问题 | 重要性 |
|----------|---------------|

## 身份验证策略

### 按摩擦程度排序的身份验证方式

| 方式 | 摩擦程度 | 最适合 | 对转化率的影响 |
|--------|---------------|----------|------------------|
| Google SSO（一键登录） | 非常低 | B2B SaaS、生产力工具 | 与邮箱 + 密码相比提升 15-30% |
| Apple 登录 | 非常低 | 以 iOS/Mac 用户为主的受众 | 在 Apple 设备上提升 10-20% |
| Microsoft SSO | 低 | 企业级 B2B | 对企业用户提升 10-15% |
| GitHub SSO | 低 | 开发者工具 | 对开发者受众提升 15-25% |
| 魔法链接（电子邮件） | 低 | 注重安全的用户、B2B | 与密码相比提升 5-10% |
| 邮箱 + 密码 | 中等 | 通用备用方案 | 基准 |
| 手机号 + OTP | 中等 | 移动优先、B2C | 因市场而异 |
| 邮箱 + 密码 + 验证 | 高 | 必须进行验证时 | 与无需验证相比下降 10-20% |

### SSO 策略决策

| 目标用户 | 主要 SSO | 次要 SSO | 是否保留邮箱+密码？ |
|--------------|-------------|---------------|---------------------|
| B2B SaaS（通用） | Google Workspace | Microsoft | 是 |
| 开发者工具 | GitHub | Google | 是 |
| 企业 | Microsoft/Okta | Google | 是（供个人评估使用） |
| B2C 消费者 | Google | Apple | 是 |
| 移动端优先 | Apple / Google | 手机 OTP | 可选 |
| 注重隐私 | 魔法链接 | 邮箱+密码 | 是 |

### SSO 放置位置

```
┌──────────────────────────────────┐
│  Create your account             │
│                                  │
│  [Continue with Google]          │  ← SSO options first
│  [Continue with Microsoft]       │
│                                  │
│  ──── or ────                   │  ← Visual separator
│                                  │
│  Email: [_______________]       │  ← Email+password as alternative
│  Password: [_______________]    │
│                                  │
│  [Create Account]               │
└──────────────────────────────────┘
```

**规则：**
- SSO 按钮放在邮箱表单上方（而非下方）
- 使用品牌化按钮样式（Google 官方按钮等）
- 在 SSO 与邮箱选项之间添加“或”分隔线
- SSO 将字段数减少至零（姓名和邮箱由提供商提供）

## 字段精简方法

### “首次使用前”测试

对于每个字段，都要问：**没有这些数据，产品是否真的无法运行？**

| 字段 | 是否通过测试？ | 操作 |
|-------|-------------|--------|
| 邮箱 | 是（账户身份标识） | 保留 |
| 密码 | 是（账户安全） | 保留（或使用 SSO/魔法链接） |
| 名 | 通常否 | 推迟到引导流程或个人资料中收集 |
| 姓 | 否 | 推迟收集或完全删除 |
| 公司名称 | 通常否 | 从邮箱域名补充 |
| 电话号码 | 很少 | 除非需要短信验证，否则推迟收集 |
| 职位 | 否 | 推迟到引导流程中收集或通过数据补充 |
| 团队规模 | 否 | 推迟到引导流程中收集 |
| 您是如何了解到我们的？ | 从不 | 注册后调查或归因分析 |
| 行业 | 否 | 从公司数据中补充 |

### 数据补充来源

| 字段 | 数据补充方法 | 时机 |
|-------|-------------------|--------|
| 公司名称 | 查询邮箱域名（Clearbit、Apollo） | 注册后立即进行 |
| 公司规模 | 公司数据 API | 注册后立即进行 |
| 行业 | 公司数据 API | 注册后立即进行 |
| 职位 | LinkedIn API 或 CSM 人工调研 | 首次销售联系之前 |
| 位置 | IP 地理定位 | 注册时 |

### 最小可行字段集

| 注册类型 | 最少字段 | 附加字段（如需要） |
|------------|----------------|----------------------|
| 免费增值 | 仅邮箱（或 SSO） | -- |
| 免费试用（产品驱动） | 邮箱 + 密码（或 SSO） | -- |
| 免费试用（销售辅助） | 邮箱 + 密码 + 公司 | + 角色（用于分流） |
| 付费注册 | 邮箱 + 密码 + 支付信息 | -- |
| 候补名单 | 邮箱 | + 一个资格筛选问题 |
| 企业试用 | 邮箱 + 公司 + 角色 | + 团队规模（用于资源配置） |

## 多步骤流程架构

### 何时使用多步骤流程

| 条件 | 单步骤 | 多步骤 |
|-----------|------------|------------|
| 字段总数 | 1-4 | 5+ |
| 是否需要筛选用户/分流 | 否 | 是 |
| 产品是否需要配置 | 否 | 是 |
| 是否为需要设置团队的 B2B 产品 | 否 | 是 |

### 步骤设计

**第 1 步：创建账户（阻力最低）**
- 电子邮箱 + 密码（或 SSO）
- 此步骤不要包含任何其他内容
- 如果此步骤负担过重，60% 以上的用户会在这里放弃

**第 2 步：个性化设置（如有需要）**
- 选择角色/目标/使用场景
- 这将用于个性化其产品体验
- 提供跳过按钮（“稍后设置”）

**第 3 步：配置（如有需要）**
- 邀请团队、连接集成、导入数据
- 每个子步骤均可选择“暂时跳过”
- 展示完成每项操作的价值（“邀请你的团队进行协作”）

### 进度设计

- 显示步骤数：“第 1 步，共 3 步”
- 显示进度条
- 为每个步骤添加描述性标签：“创建账户”“你的角色”“你的团队”
- 允许返回上一步（保留已输入的数据）
- 通过步骤返回操作或浏览器返回按钮返回时，绝不要重置表单

## 信用卡要求分析

### 决策框架

| 因素 | 要求提供信用卡 | 不要求提供信用卡 |
|--------|-----------|------------------|
| 试用转付费目标 | 试用转付费率 > 60% | 在流量更高的情况下，试用转付费率 > 30% |
| 产品复杂度 | 简单，可立即体现价值 | 复杂，需要探索 |
| ACV | > $100/月 | < $100/月 |
| 销售模式 | 产品驱动 | 销售辅助 |
| 竞品做法 | 竞品要求提供信用卡 | 竞品提供免信用卡试用 |
| 目标受众 | 企业客户（购买意愿明确） | SMB/专业消费者（处于观望阶段） |

### 影响分析

| 方案 | 注册量 | 试用用户质量 | 试用转付费率 | 净收入 |
|----------|-------------|---------------|---------------|-------------|
| 无需信用卡 | 更高（+40-80%） | 更低（抱着试试看心态的用户更多） | 更低（2-15%） | 净收入通常更高 |
| 需要信用卡 | 更低 | 更高（意愿明确） | 更高（40-70%） | 取决于用户量 |
| 信用卡“$0 扣款” | 中等 | 中等 | 中等（20-40%） | 中等 |

### 建议框架

**默认不要求提供信用卡**，除非：
1. 你的产品能够立即提供显而易见的价值（没有学习门槛）
2. 要求提供信用卡时，试用转付费率 > 50%
3. 你拥有能够应对较低用户量的高接触度销售团队
4. 免费试用的支持成本难以承受

**如果要求提供信用卡：** 请醒目展示：
- “在 [date] 之前不会向你收费”
- “可在 [date] 之前随时取消”
- “我们会在试用结束前 3 天向你发送电子邮件”

## 提交后的体验

### 注册后立即执行

| 元素 | 实现方式 |
|---------|---------------|
| 自动登录 | 立即让用户登录（绝不要强制用户另行登录） |
| 欢迎界面 | 展示明确的下一步操作，而不是空白的仪表板 |
| 确认邮件 | 立即发送，其中包括：后续流程、主要功能、支持联系方式 |
| 电子邮箱验证 | 尽可能延后。如果必须验证，则以内嵌方式发送验证信息，并允许用户在验证前继续使用产品 |

### 邮箱验证策略

| 方式 | 对激活率的影响 | 适用场景 |
|----------|---------------------|-------------|
| 不验证 | 激活率最高 | 低风险产品、免费增值产品 |
| 验证后解锁特定功能 | 良好——用户会先完成激活 | 提供免费套餐的 B2B SaaS |
| 在 24 小时内验证 | 中等——可营造紧迫感 | 需要发送邮件的产品 |
| 使用前必须验证 | 激活率最低 | 受监管行业、金融产品 |

**默认建议：** 允许用户立即使用产品。在 24-48 小时内完成验证。仅限制必须验证邮箱才能使用的功能（例如发送邮件、邀请团队成员）。

## 移动端注册优化

### 移动端专属规则

| 规则 | 实现方式 |
|------|---------------|
| SSO 优先 | 在移动端使用 Google/Apple 登录只需轻点一次 |
| 单列布局 | 移动端切勿并排放置字段 |
| 大尺寸输入框 | 所有触控目标的高度至少为 44px |
| 合适的键盘 | `type="email"`、`type="tel"`、`type="password"` |
| 支持自动填充 | 使用标准字段名称，以支持浏览器自动填充 |
| 固定 CTA | 将“创建账户”按钮固定在视口底部 |
| 不使用 CAPTCHA | 使用隐形 reCAPTCHA 或替代方案 |
| 密码可见性 | 提供显示/隐藏密码的切换功能 |

### 移动端与桌面端注册的差异

| 方面 | 桌面端 | 移动端 |
|--------|---------|--------|
| 主要认证方式 | SSO 或邮箱+密码 | 首选 SSO（一键登录） |
| 每个页面的字段数 | 最多 5 个 | 最多 3 个 |
| 密码规则 | 预先显示要求 | 交互时显示 |
| CAPTCHA | 可接受标准 reCAPTCHA | 使用隐形方式或不使用 |
| 社会认同 | 侧边栏或相邻区域 | 表单下方或上方 |

## 按产品类型划分的注册流程模式

### B2B SaaS 试用

```
[Google SSO] or [Email + Password]
→ Auto-login to product
→ Welcome screen: "What brings you here?" (3 options)
→ Guided first action based on selection
→ Team invite prompt (optional, day 2-3)
```

### B2C 消费者应用

```
[Apple Sign In] or [Google Sign In] or [Email]
→ Immediately into product
→ Personalization (follows, preferences) inline
→ Profile completion deferred
```

### 企业级/销售辅助型

```
[Work Email + Password + Company Name]
→ Auto-login to sandbox
→ Role + team size (for provisioning)
→ CSM outreach triggered for qualified accounts
→ Guided setup with dedicated support
```

### 候补名单/抢先体验

```
[Email only]
→ Confirmation page: position in waitlist
→ Referral mechanism: "Jump ahead by sharing"
→ Weekly update email on progress
→ Access granted email with one-click activation
```

## 渐进式信息收集

通过多次会话收集信息，而不是使用一份冗长的表单。

### 渐进式信息收集计划

| 会话 | 收集内容 | 收集方式 |
|---------|----------------|-----|
| 注册（第 1 次会话） | 邮箱 + 认证 | 注册表单 |
| 首次使用（第 1-2 次会话） | 角色、主要目标 | 产品内提示或设置向导 |
| 第 3-5 天 | 团队规模、使用场景 | 产品中的情境式问题 |
| 第 7-14 天 | 行业、公司规模 | 问卷或数据补充 |
| 首次付款前 | 账单信息 | 升级流程 |

### 实施规则

- 每个用户画像信息收集触点最多询问 1-2 个问题
- 始终说明询问原因（“以便我们为你提供个性化体验”）
- 始终提供“跳过”选项
- 绝不询问可以自动补充的信息
- 存储不完整的用户画像，并随时间逐步完善

## 错误和边界情况处理

### 密码要求

| 方法 | 用户体验 | 安全性 |
|----------|----------------|----------|
| 预先显示要求 | 最佳——用户知道应该输入什么 | 良好 |
| 获得焦点时显示要求 | 良好 | 良好 |
| 仅在提交后显示错误 | 差——令人沮丧 | 相同 |
| 实时复选标记 | 最佳——渐进式验证 | 良好 |

**建议：** 以清单形式显示密码要求，并在用户输入时实时勾选已满足的要求。

### 常见错误场景

| 错误 | 糟糕的用户体验 | 良好的用户体验 |
|-------|--------|---------|
| 电子邮箱已注册 | “错误：账户已存在” | “此电子邮箱已有账户。[登录]或[重置密码]” |
| 密码强度不足 | “密码强度太低” | 使用复选标记显示已满足和未满足的要求 |
| SSO 失败 | 通用错误页面 | “使用 Google 登录时出现问题。[重试]或[改用电子邮箱]” |
| 网络错误 | 表单被清空，且没有提示信息 | “连接出现问题。你的数据已保存。[重试]” |
| 速率限制 | 被阻止但没有任何解释 | “尝试次数过多。请在 [N] 分钟后重试” |

## A/B 测试框架

### 高影响力测试

| 测试 | 假设 | 指标 |
|------|-----------|--------|
| 添加 Google SSO | SSO 可将完成率提高 15-30% | 注册完成率 |
| 移除非必要字段 | 字段越少，完成率越高 | 完成率 + 激活率 |
| 单步骤与多步骤对比 | 对于包含 5 个以上字段的表单，多步骤形式让人感觉更容易完成 | 完成率 |
| 要求提供 CC 与不要求提供 CC 对比 | 不要求提供 CC 所增加的用户量足以抵消转化率下降 | 净收入 |
| 推迟电子邮箱验证 | 允许立即访问产品可提高激活率 | 激活率 |

### 衡量规则

- 同时跟踪注册完成率和后续激活率
- 如果某项测试提高了注册量，却降低了激活率，就不能算成功
- 按流量来源跟踪（付费流量与自然流量的反应可能不同）
- 分别跟踪移动端和桌面端

## 指标和基准

### 关键指标

| 指标 | 公式 | 基准 |
|--------|---------|-----------|
| 注册页面访问到完成的转化率 | 完成次数 / 页面浏览量 | 30-50%（B2B），40-60%（B2C） |
| SSO 采用率 | SSO 注册数 / 总注册数 | 提供 SSO 时为 30-60% |
| 字段级流失率 | 每个字段的放弃量 | 找出流失率最高的字段 |
| 完成用时 | 从首次交互到提交的秒数中位数 | 简单流程 < 45s，多步骤流程 < 2min |
| 移动端完成率 | 移动端完成次数 / 移动端页面浏览量 | 与桌面端的差距应在 15% 以内 |
| 电子邮箱验证率 | 已验证用户数 / 总注册数 | 48 小时内 > 70% |

## 故障排除

| 问题 | 可能原因 | 解决方案 |
|---------|-------------|------------|
| 注册完成率低于 30%（B2B）或 40%（B2C） | 字段过多、没有 SSO 选项，或表单与 CTA 位于不同页面 | 精简为仅填写电子邮件或使用 SSO；将表单与价值主张放在同一页面；每移除一个字段可将转化率提高约 10% |
| 提供 SSO 后采用率仍低于 30% | SSO 按钮位于电子邮件表单下方，或 SSO 提供商与目标受众不匹配 | 将 SSO 按钮移至电子邮件表单上方，并使用“or”分隔线；根据受众匹配 SSO（B2B 使用 Google，iOS 用户使用 Apple） |
| 移动端完成率比桌面端低 15% 以上 | 表单未针对触控操作进行优化（输入框过小、键盘类型错误、没有自动填充） | 确保触控目标最小为 44px，使用 type="email"/type="tel"，启用浏览器自动填充，将 CTA 固定在视口底部 |
| 密码字段流失率高 | 复杂的密码要求仅在提交后显示，或没有密码可见性切换按钮 | 以实时检查清单的形式显示要求，添加显示/隐藏切换按钮，考虑使用魔法链接或 SSO 彻底取消密码 |
| 电子邮件验证导致激活率下降 | 要求用户在使用任何产品功能前完成验证，阻碍了关键的首次会话体验 | 将验证推迟 24-48 小时；允许用户立即使用产品；仅对电子邮件发送功能设置验证门槛 |
| “Email already registered”错误频繁出现 | 用户忘记自己已有账户；错误消息未帮助他们恢复访问 | 将错误改为“This email has an account. [Log in] or [Reset password]”，并提供直接链接 |
| 多步骤流程的放弃率高 | 步骤没有渐进安排、没有进度指示器，或每个步骤的字段过多 | 显示步骤数和进度条；将第 1 步限制为仅创建账户；在非必要步骤中添加“Skip for now” |

## 成功标准

- 在优化后的 60 天内，注册页面从访问到完成注册的转化率达到 30-50%（B2B）或 40-60%（B2C）
- 正确提供 SSO 时，通过 SSO 完成的注册占总注册量的 30-60%
- 简单流程的完成时间中位数保持在 45 秒以内，多步骤流程保持在 2 分钟以内
- 移动端完成率与桌面端完成率的差距在 15% 以内
- 注册后 48 小时内的电子邮件验证率超过 70%
- 字段级流失分析显示，没有任何单一字段导致超过 10% 的增量放弃率
- 注册后的激活率（完成第一个关键操作）与注册率同步提升（而非以牺牲实际效果换取虚荣指标）

## 范围与限制

**范围内：** 身份验证策略（SSO、魔法链接、电子邮件+密码）、字段精简方法、多步骤流程架构、信用卡要求分析、提交后体验设计、移动端注册优化、渐进式用户画像完善计划、错误与边缘情况处理，以及注册流程的 A/B 测试框架。

**范围外：** 注册后的引导和激活（使用 onboarding-cro）、非注册类表单，例如潜在客户信息收集或联系表单（使用 form-cro）、注册表单之前的落地页转化（使用 page-cro）、应用内升级和付费墙流程（使用 paywall-upgrade-cro）。脚本仅处理本地数据 -- 不与身份验证提供商（Auth0、Clerk 等）或分析平台集成。

**限制：** 转化率基准来自 SaaS/应用行业的汇总数据，并会因垂直领域、价格点和受众而异。SSO 采用率在很大程度上取决于受众构成（开发者受众采用 GitHub SSO 的比例可达 40% 以上，而 SMB 受众可能更偏好电子邮件）。信用卡要求分析基于行业平均水平建模 -- 实际影响需要在具体场景中通过 A/B 测试来验证。渐进式用户画像完善建议以标准 SaaS 生命周期阶段为前提。

## 集成点

- **onboarding-cro** -- 注册流程在账户创建时结束；onboarding-cro 从首次登录开始接手，直至激活
- **form-cro** -- 字段级优化原则（验证、键盘类型、错误处理）适用于注册表单
- **page-cro** -- 落地页质量会直接影响注册表单的触达率；应先优化页面，再优化表单
- **paywall-upgrade-cro** -- 试用注册配置（要求信用卡、试用期长度）会影响后续升级流程的设计
- **pricing-strategy** -- 定价模式（免费增值或试用）决定注册流程类型和字段要求
- **referral-program** -- 推荐用户的注册流程应预填推荐人上下文并显示激励信息

## 相关技能

- **onboarding-cro** -- 用于优化注册后的激活。signup-flow-cro 在用户拥有账户时结束；onboarding-cro 从此处开始。
- **form-cro** -- 用于非注册类表单（潜在客户信息收集、联系、演示申请）。其优化框架与注册流程不同。
- **page-cro** -- 当瓶颈是通往注册流程的落地页，而非注册表单本身时使用。
- **paywall-upgrade-cro** -- 当真正的挑战是将免费用户转化为付费用户，而非促使其注册时使用。
