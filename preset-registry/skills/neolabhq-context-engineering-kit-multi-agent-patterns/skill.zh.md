# Claude Code 的多智能体架构模式

多智能体架构将工作分配给多个智能体调用，每个调用都有各自聚焦的上下文。如果设计得当，这种分配方式可以实现超越单智能体局限的能力。如果设计不当，则会引入协调开销，抵消其优势。关键洞见在于，子智能体的主要作用是隔离上下文，而不是将角色分工拟人化。

## 核心概念

多智能体系统通过分布式处理来应对单智能体的上下文限制。目前有三种主流模式：用于集中控制的监督者/编排器模式、用于灵活交接的点对点/集群模式，以及用于分层抽象的层级模式。关键设计原则是上下文隔离——子智能体的主要作用是划分上下文，而不是模拟组织角色。

有效的多智能体系统需要明确的协调协议、能够避免谄媚倾向的共识机制，并谨慎关注瓶颈、分歧和错误传播等故障模式。

## 为什么采用多智能体架构

### 上下文瓶颈

单智能体在推理能力、上下文管理和工具协调方面存在固有上限。随着任务变得更加复杂，上下文窗口会逐渐被累积的历史记录、检索到的文档和工具输出填满。性能会按照可预测的模式下降：中间信息丢失效应、注意力稀缺以及上下文污染。

多智能体架构通过将工作划分到多个上下文窗口来应对这些限制。每个智能体都在聚焦于其子任务的干净上下文中运行。结果在协调层进行汇总，无需任何单一上下文承担全部负担。

### 并行化论据

许多任务包含可并行处理的子任务，而单个智能体必须按顺序执行这些子任务。一项研究任务可能需要搜索多个相互独立的信息源、分析不同文档，或比较相互竞争的方案。单个智能体会依次处理这些任务，并在每一步中不断累积上下文。

多智能体架构将每个子任务分配给一个拥有全新上下文的专用智能体。所有智能体同时工作，然后将结果返回给协调器。现实中的总耗时接近耗时最长的子任务，而不是所有子任务耗时的总和。

### 专业化论据

不同任务适合不同的智能体配置：不同的系统提示词、不同的工具集、不同的上下文结构。通用智能体必须在上下文中携带所有可能的配置。专业化智能体只携带自身所需的内容。

多智能体架构能够实现专业化，同时避免组合爆炸。协调器将任务路由到专业化智能体；每个智能体都使用针对其领域优化的精简上下文运行。

## 架构模式

### 模式 1：监督者/编排器

监督者模式由一个中央智能体负责控制，将任务委派给专业智能体并综合结果。监督者维护全局状态和执行轨迹，将用户目标分解为子任务，并将其路由给适当的工作智能体。

```
User Request -> Supervisor -> [Specialist A, Specialist B, Specialist C] -> Aggregation -> Final Output
```

**适用场景：** 可明确拆解的复杂任务、需要跨领域协调的任务，以及人工监督至关重要的任务。

**优点：** 可严格控制工作流，更容易实施人工介入，并确保遵循预先定义的计划。

**缺点：** 监督者的上下文会成为瓶颈，监督者的失败会级联至所有工作者，还存在监督者错误转述子代理响应的“传话游戏”问题。

**Claude Code 实现：** 创建一个主命令，通过使用 Task 工具调用专门的子代理来进行编排。监督者命令包含协调逻辑，并调用子代理执行专业工作。

```markdown
<!-- Example supervisor command structure -->
1. Analyze the user request and decompose into subtasks
2. For each subtask, dispatch to appropriate specialist:
   - Use Task tool to spawn subagent with focused context
   - Pass only relevant context to each subagent
3. Collect and synthesize results from all subagents
4. Return unified response to user
```

**传话游戏问题：** 当监督者错误转述子代理的响应并导致信息保真度下降时，监督者架构的表现可能会更差。解决方法是：当综合处理会丢失重要细节时，允许子代理直接传递响应。在 Claude Code 中，这意味着让子代理直接写入共享文件或逐字返回其输出，而不是由监督者重写所有内容。

### 模式 2：点对点/群体

点对点模式移除了中央控制，允许代理根据预定义协议直接通信。任何代理都可以通过显式的移交机制将控制权转移给其他任何代理。

**适用场景：** 需要灵活探索的任务、僵化规划会适得其反的任务，以及具有无法预先拆解的新涌现需求的任务。

**优点：** 不存在单点故障，能够有效扩展以支持广度优先探索，并可促成新涌现的问题解决行为。

**缺点：** 协调复杂度会随着代理数量增加而上升，在缺少中央状态维护者时存在偏离目标的风险，并且需要健壮的收敛约束。

**Claude Code 实现：** 创建能够根据发现的需求调用其他命令的命令。使用共享文件（如任务列表或状态文件）作为协调机制。

```markdown
<!-- Example peer handoff structure -->
1. Analyze current state from shared context file
2. Determine if this agent can complete the task
3. If specialized help needed:
   - Write current findings to shared state
   - Invoke appropriate peer command/skill
4. Continue until task complete or hand off
```

### 模式 3：分层式

分层结构将代理组织成不同的抽象层级：战略层、规划层和执行层。战略层代理定义目标和约束；规划层代理将目标分解为可执行的计划；执行层代理执行原子任务。

```
Strategy Layer (Goal Definition) -> Planning Layer (Task Decomposition) -> Execution Layer (Atomic Tasks)
```

**适用场景：** 具有清晰层级结构的大型项目、包含管理层级的企业工作流，以及同时需要高层规划和细致执行的任务。

**优势：** 与组织结构相对应、关注点分离清晰，并且能够在不同层级使用不同的上下文结构。

**劣势：** 层级之间存在协调开销，战略与执行可能不一致，错误传播过程复杂。

**Claude Code 实现：** 使用不同抽象层级的命令来构建插件。高层命令专注于战略并调用中层规划命令，而中层规划命令又会调用原子级执行命令。

## 将上下文隔离作为设计原则

多智能体架构的主要目的是实现上下文隔离。每个子智能体都在一个专注于其子任务的干净上下文窗口中运行，不会携带从其他子任务累积而来的上下文。

### 隔离机制

**指令传递：** 对于简单且定义明确的子任务，协调器会创建聚焦的指令。子智能体只接收完成其特定任务所需的指令。在 Claude Code 中，这意味着通过 Task 工具向子智能体传递最少且有针对性的提示词。

**文件系统记忆：** 对于需要共享状态的复杂任务，智能体会读取持久化存储并向其中写入数据。文件系统充当协调机制，避免因传递共享状态而导致上下文膨胀。这是 Claude Code 最自然的模式——智能体通过 markdown 文件、JSON 状态文件或结构化文档进行通信。

**完整上下文委派：** 对于子智能体需要全面理解的复杂任务，协调器会共享其全部上下文。子智能体拥有自己的工具和指令，但会接收完整上下文以进行决策。应谨慎使用，因为这会违背上下文隔离的初衷。

### 隔离的权衡

完整上下文委派可提供最大的能力，但会违背使用子智能体的初衷。指令传递可维持隔离，但会限制子智能体的灵活性。文件系统记忆无需传递上下文即可实现状态共享，但会带来一致性方面的挑战。

正确的选择取决于任务复杂度、协调需求以及工作的性质。

## 共识与协调

### 投票问题

简单多数投票将薄弱推理产生的幻觉与可靠推理同等对待。如果不加干预，由于智能体天然倾向于达成一致，多智能体讨论可能会退化为基于错误前提的共识。

### 加权贡献

根据置信度或专业能力对智能体的贡献进行加权。置信度更高或具备相关领域专业能力的智能体在最终决策中拥有更高权重。

### 辩论协议

辩论协议要求智能体通过多轮交互相互批评彼此的输出。对于复杂推理，对抗性批评通常比协作式共识具有更高的准确性。

**Claude Code 实现：** 创建一个审查阶段，让一个代理对另一个代理的输出进行批评。将其设计为多个独立命令：一个用于初始工作，一个用于批评，还可以选择提供一个根据批评进行修订的命令。

### 基于触发器的干预

监控多代理交互中的特定行为标志：
- **停滞触发器：** 当讨论没有取得任何进展时激活
- **迎合触发器：** 检测代理是否在没有独立推理的情况下模仿彼此的答案
- **偏离触发器：** 检测代理是否正在偏离最初目标

## 失败模式与缓解措施

### 失败：监督者瓶颈

监督者会累积来自所有工作代理的上下文，从而容易出现上下文饱和和性能下降。

**缓解措施：** 实施输出约束，使工作代理仅返回提炼后的摘要。使用基于文件的检查点机制持久化状态，避免在上下文中携带完整历史记录。

### 失败：协调开销

代理之间的通信会消耗 token 并引入延迟。复杂的协调机制可能会抵消并行化带来的收益。

**缓解措施：** 通过明确的交接协议最大限度地减少通信。使用结构化文件格式进行代理间通信。尽可能批量处理结果。

### 失败：偏离目标

在缺乏集中协调的情况下，追求不同目标的代理可能会偏离预期目标。

**缓解措施：** 为每个代理定义明确的目标边界。实施收敛检查，验证工作是否正在朝共同目标推进。限制代理执行的迭代次数。

### 失败：错误传播

一个代理输出中的错误会传播到使用该输出的下游代理。

**缓解措施：** 在将代理输出传递给使用方之前进行验证。实施重试逻辑。设计组件发生故障时的优雅降级机制。

## 在 Claude Code 中应用模式

### 将命令用作监督者

创建一个主命令，用于：
1. 分析任务并制定计划
2. 通过 Task 工具分派子代理执行专业化工作
3. 收集结果（通过返回值或共享文件）
4. 综合生成最终输出

### 将子代理用作专家

为专业领域定义子代理：
- 每个子代理专注于一个专业领域
- 子代理接收与其专业领域相关的聚焦上下文
- 子代理返回协调者可以聚合的结构化输出

### 将文件用作共享内存

使用文件系统进行代理间协调：
- 状态文件用于跟踪各代理的进度
- 输出文件用于收集并行工作的结果
- 任务列表用于协调剩余工作

### 示例：代码审查多代理系统

```
Supervisor Command: review-code
├── Subagent: security-review (security specialist)
├── Subagent: performance-review (performance specialist)
├── Subagent: style-review (style/conventions specialist)
└── Aggregation: combine findings, deduplicate, prioritize
```

每个子代理仅接收待审查的代码及其专业领域的关注重点。监督者将所有发现聚合为一份统一的审查结果。

## 指南

1. 将上下文隔离设计为多智能体系统的首要优势
2. 根据协调需求而非组织隐喻选择架构模式
3. 在 Claude Code 多智能体模式中，默认使用基于文件的通信
4. 实现显式交接协议，并清晰传递状态
5. 使用批判/辩论模式达成共识，而非简单认同
6. 监控监督者瓶颈，并通过文件实现检查点机制
7. 在智能体之间传递输出前进行验证
8. 设置迭代次数限制，防止无限循环
9. 显式测试失败场景
10. 从简单方案开始——仅当单智能体方法失败时，才增加多智能体复杂性

## 记忆与状态管理

对于跨多个会话或需要持久状态的任务，使用基于文件的记忆：

### 工作记忆

即上下文窗口本身。它可以提供即时访问，但会在会话结束时消失。只保留当前活跃的信息；对已完成的工作进行总结。

### 会话记忆

在会话期间创建、用于跟踪进度的文件：
- 任务列表（已完成的内容、剩余内容）
- 中间结果
- 决策日志

### 长期记忆

可跨会话保留的持久文件：
- 用于项目级上下文的 CLAUDE.md
- 指定目录中的记忆文件
- 采用 markdown 或 JSON 格式的结构化知识库

### 多智能体记忆模式

- **交接文件：** 智能体 A 写入状态，智能体 B 读取并继续
- **结果聚合：** 多个智能体分别写入不同文件，监督者读取所有文件
- **进度跟踪：** 由所有智能体共同更新共享任务列表
- **知识积累：** 智能体将发现追加到共享知识文件中

选择能够满足需求的最简单记忆机制。基于文件的记忆透明、易于调试，且不需要基础设施。

# 记忆系统设计

记忆提供了持久化层，使智能体能够跨会话保持连续性，并基于积累的知识进行推理。简单智能体完全依赖上下文来实现记忆，在会话结束时会丢失所有状态。复杂智能体会实现分层记忆架构，在即时上下文需求与长期知识保留之间取得平衡。从向量存储到知识图谱，再到时态知识图谱的演进，代表了为改善检索和推理而对结构化记忆进行的逐步加大投入。

## 核心概念

记忆存在于从即时上下文到永久存储的连续谱系中。在一个极端，上下文窗口中的工作记忆可以提供零延迟访问，但会在会话结束时消失。在另一个极端，永久存储可以无限期保留，但需要经过检索才能进入上下文。

简单的向量存储缺乏关系结构和时间结构。知识图谱可保留关系以支持推理。时态知识图谱则添加有效期，以支持时间感知查询。具体实现选择取决于查询复杂度、基础设施约束和准确性要求。

## 详细主题

### 记忆架构基础

**上下文—记忆谱系**
记忆呈现为一个从即时上下文到永久存储的连续谱系。在一个极端，上下文窗口中的工作记忆可实现零延迟访问，但会在会话结束时消失。在另一个极端，永久存储可以无限期保留，但必须经过检索才能进入上下文。有效的架构会沿着这一谱系使用多个层级。

这一谱系包括工作记忆（上下文窗口、零延迟、易失）、短期记忆（会话内持久化、可搜索、易失）、长期记忆（跨会话持久化、结构化、半永久）和永久记忆（归档、可查询、永久）。每个层级都有不同的延迟、容量和持久性特征。

**为什么简单的向量存储存在不足**
向量 RAG 通过将查询和文档嵌入共享的嵌入空间来提供语义检索。相似度搜索会检索语义最相近的文档。这种方式非常适合文档检索，但缺少智能体记忆所需的结构。

向量存储会丢失关系信息。如果智能体得知“客户 X 在日期 Z 购买了产品 Y”，那么在直接询问时，向量存储可以检索到这一事实。但它无法回答“购买了产品 Y 的客户还购买了哪些产品？”，因为关系结构没有被保留。

向量存储在处理时态有效性方面也存在困难。事实会随时间变化，但除了使用显式元数据和筛选之外，向量存储没有机制来区分“当前事实”和“过时事实”。

**转向基于图的记忆**
知识图谱会保留实体之间的关系。图并非使用孤立的文档分块，而是对实体 A 通过关系 R 与实体 B 相关联这一信息进行编码。这样便可以执行遍历关系的查询，而不只是进行相似度搜索。

时态知识图谱会为事实添加有效期。每个事实都有一个“生效时间”时间戳，还可以有一个“失效时间”时间戳。这样便可以执行时间旅行查询，重建特定时间点的知识。

**基准性能对比**
深度记忆检索（DMR）基准提供了不同记忆架构的具体性能数据：

| 记忆系统 | DMR 准确率 | 检索延迟 | 备注 |
|---------------|--------------|-------------------|-------|
| Zep（时态知识图谱） | 94.8% | 2.58s | 准确率最高，检索速度快 |
| MemGPT | 93.4% | 不固定 | 综合性能良好 |
| GraphRAG | ~75-85% | 不固定 | 相比基线 RAG 提升 20-35% |
| 向量 RAG | ~60-70% | 快 | 丢失关系结构 |
| 递归摘要 | 35.3% | 低 | 信息严重丢失 |

与完整上下文基线相比，Zep 将检索延迟降低了 90%（对于 GPT-5.2，延迟从 28.9s 降至 2.58s）。这种效率源于只检索相关子图，而不是检索全部上下文历史记录。

在复杂推理任务中，GraphRAG 的准确率相比基线 RAG 提升约 20-35%，并通过基于社区的摘要将幻觉减少多达 30%。

### 记忆层架构

**第 1 层：工作记忆**
工作记忆就是上下文窗口本身。它允许即时访问当前正在处理的信息，但容量有限，并且会在会话结束时消失。

工作记忆的使用模式包括：用于让智能体跟踪中间结果的草稿计算、为当前任务保留对话内容的会话历史、跟踪当前目标进度的当前任务状态，以及保存当前正在使用的信息的已检索活跃文档。

优化工作记忆的方法包括：只保留活跃信息、在已完成的工作淡出注意范围之前对其进行总结，以及将关键信息放在更容易获得注意的位置。

**第 2 层：短期记忆**
短期记忆在当前会话期间持续存在，但不会跨会话保留。它提供搜索和检索功能，且没有永久存储所带来的延迟。

常见实现包括：持续存在到会话结束的会话级数据库、指定会话目录中的文件系统存储，以及以会话 ID 为键的内存缓存。

短期记忆的使用场景包括：在不塞满上下文的情况下跨轮次跟踪对话状态、存储稍后可能需要的工具调用中间结果、维护任务检查清单和进度跟踪，以及在会话期间缓存检索到的信息。

**第 3 层：长期记忆**
长期记忆可以无限期地跨会话保留。它使智能体能够从过去的交互中学习，并随时间推移积累知识。

长期记忆的实现方式涵盖从简单的键值存储到复杂的图数据库。具体选择取决于需要建模的关系复杂度、所需的查询模式，以及可接受的基础设施复杂度。

长期记忆的使用场景包括：跨会话学习用户偏好、构建随时间不断增长的领域知识库、维护包含关系历史的实体注册表，以及存储可供复用的成功模式。

**第 4 层：实体记忆**
实体记忆专门跟踪与实体（人物、地点、概念、对象）有关的信息，以保持一致性。由此形成一个基础知识图谱，使实体能够在多次交互中被识别。

实体记忆通过跟踪一次对话中提到的“John Doe”与另一次对话中的是同一个人，来维护实体身份。它通过存储随时间推移发现的实体事实来维护实体属性。它通过跟踪发现的实体间关系来维护实体关系。

**第 5 层：时态知识图谱**
时态知识图谱通过显式的有效期扩展了实体记忆。事实并非仅有真或假，而是在特定时间范围内为真。

这使得系统可以通过检索在该日期范围内有效的事实，回答“用户在日期 X 的地址是什么？”之类的查询。当过时信息与新数据相矛盾时，它可以防止上下文冲突。它还能对实体如何随时间变化进行时态推理。

### 记忆实现模式

**模式 1：文件系统即记忆**
文件系统本身可以充当记忆层。这种模式简单，无需额外的基础设施，并且能够采用即时加载机制，而正是这种机制让基于文件系统的上下文高效运作。

实现时使用文件系统层级结构进行组织。采用能够表达含义的命名约定。以结构化格式（JSON、YAML）存储事实。在文件名或元数据中使用时间戳进行时间追踪。

优点：简单、透明、可移植。
缺点：不支持语义搜索、不支持关系追踪、需要手动组织。

**模式 2：带元数据的向量 RAG**
通过丰富元数据增强的向量存储可提供带过滤功能的语义搜索。

实现时对事实或文档进行嵌入，并将其与元数据一起存储，元数据包括实体标签、时间有效性、来源归属和置信度分数。查询时将元数据过滤器与语义搜索结合使用。

**模式 3：知识图谱**
知识图谱对实体和关系进行显式建模。实现时定义实体类型和关系类型，使用图数据库或属性图进行存储，并为常见查询模式维护索引。

**模式 4：时态知识图谱**
时态知识图谱为事实添加有效期，从而支持时间旅行查询，并防止过时信息造成上下文冲突。

### 记忆检索模式

**语义检索**
使用嵌入相似度搜索，检索与当前查询在语义上相似的记忆。

**基于实体的检索**
通过遍历图关系，检索与特定实体相关的所有记忆。

**时态检索**
使用有效期过滤器，检索在特定时间点或时间范围内有效的记忆。

### 记忆整合

记忆会随时间不断累积，因此需要进行整合，以防止其无限增长并移除过时信息。

**整合触发条件**
在记忆大量累积后、检索返回过多过时结果时、按计划定期执行，或收到显式整合请求时触发整合。

**整合过程**
识别过时事实、合并相关事实、更新有效期、归档或删除废弃事实，并重建索引。
