# 项目开发方法论

本技能涵盖识别适合由 LLM 处理的任务、设计有效的项目架构，以及使用智能体辅助开发进行快速迭代的原则。无论是构建批处理流水线、多智能体研究系统，还是交互式智能体应用，本方法论都适用。

本技能的工作单元是整个项目或多阶段流水线。单个工具的设计（描述、模式、错误消息）属于 `tool-design`。每项技能的激活路由属于对应技能及语料库索引。本技能负责项目层面的问题：究竟是否应该使用 LLM 来构建、流水线应采用何种形态、成本是多少，以及应如何迭代。

## 何时激活

当工作单元是整个项目或流水线时，激活本技能：

- 判断 LLM 从根本上是否适合某项任务（在编写任何代码之前评估任务与模型的适配性）。
- 规划多阶段批处理或智能体流水线（获取 / 准备 / 处理 / 解析 / 渲染）。
- 估算重度使用 LLM 的项目所需的 token、资金成本和时间。
- 在项目层面选择单智能体或多智能体。
- 组织智能体辅助迭代（由智能体协助构建项目本身）。
- 在流水线契约层面设计结构化输出（跨阶段交接格式）。

对于由其他技能负责的相邻工作，请勿激活本技能：

- 单个工具的描述、模式、命名、响应格式、错误消息：`tool-design`。
- 单条执行轨迹的 token 效率策略（掩码、分区、缓存）：`context-optimization`。
- 决定是否在智能体拓扑层面将工作拆分给多个子智能体：`multi-agent-patterns`。
- 设计自主控制循环（锁定指标、新颖性门控、人工审批边界）：`harness-engineering`。

## 核心概念

### 任务与模型适配性识别

在编写任何代码之前，先评估任务与模型的适配性，因为围绕一个根本不适配的任务构建自动化系统会浪费数天时间。针对每个拟议任务，使用以下两个表格进行评估，以决定继续还是停止。

**当任务具有以下特征时继续：**

| 特征 | 理由 |
|----------------|-----------|
| 跨来源综合 | 与基于规则的替代方案相比，LLM 更擅长整合多个输入中的信息 |
| 基于评分准则的主观判断 | 带有标准的评分、评估和分类天然适合语言推理 |
| 自然语言输出 | 当目标是生成供人阅读的文本时，LLM 能够直接完成 |
| 容错性 | 单次失败不会破坏整个系统，因此 LLM 的非确定性可以接受 |
| 批处理 | 各项目之间不需要保持对话状态，从而保持上下文简洁 |
| 训练数据中包含领域知识 | 模型已经具备相关上下文，从而减少提示工程开销 |

**当任务具有以下特征时停止：**

| 特征 | 理由 |
|----------------|-----------|
| 精确计算 | 语言模型在数学、计数和精确算法方面并不可靠 |
| 实时性要求 | LLM 的延迟过高，无法实现亚秒级响应 |
| 完美准确性要求 | 幻觉风险使 100% 的准确性无法实现 |
| 依赖专有数据 | 模型缺少必要的上下文，且无法仅通过提示获取这些上下文 |
| 顺序依赖 | 每一步都高度依赖前一步的结果，导致错误不断累积 |
| 确定性输出要求 | 相同输入必须产生完全相同的输出，而 LLM 无法保证这一点 |

### 手动原型步骤

在投入自动化之前，始终通过手动测试验证任务与模型的适配性。将一个有代表性的输入复制到模型界面中，评估输出质量，并根据结果回答以下问题：

- 模型是否具备完成此任务所需的知识？
- 模型能否以所需格式生成输出？
- 大规模运行时可以预期达到怎样的质量水平？
- 是否存在需要解决的明显故障模式？

之所以要这样做，是因为失败的手动原型预示着自动化系统也会失败，而成功的手动原型则能同时提供质量基线和提示词设计模板。这项测试只需几分钟，却能避免浪费数小时的开发时间。

### 流水线架构

将大语言模型项目构建为分阶段流水线，因为将确定性阶段与非确定性阶段分离，有助于快速迭代和控制成本。每个阶段都应设计为：

- **离散**：各阶段之间具有清晰的边界，以便对每个阶段进行独立调试
- **幂等**：重新运行会产生相同的结果，从而避免重复工作
- **可缓存**：将中间结果持久化到磁盘，避免代价高昂的重复计算
- **独立**：每个阶段都可以单独运行，从而能够有选择地重新执行

**使用以下规范的流水线结构：**

```
acquire -> prepare -> process -> parse -> render
```

1. **采集**：从数据源（API、文件、数据库）获取原始数据
2. **准备**：将数据转换为提示词格式
3. **处理**：执行大语言模型调用（成本高昂的非确定性步骤）
4. **解析**：从大语言模型输出中提取结构化数据
5. **渲染**：生成最终输出（报告、文件、可视化内容）

阶段 1、2、4 和 5 是确定性的。阶段 3 是非确定性的，并且成本高昂。保持这种分离，因为这样既可以仅在必要时重新运行成本高昂的大语言模型阶段，又能快速迭代解析和渲染过程。

### 将文件系统用作状态机

使用文件系统而非数据库或内存数据结构来跟踪流水线状态，因为文件是否存在能够自然地提供幂等性，并便于以人类可读的方式进行调试。

```
data/{id}/
  raw.json         # acquire stage complete
  prompt.md        # prepare stage complete
  response.md      # process stage complete
  parsed.json      # parse stage complete
```

通过检查输出文件是否存在，判断某个条目是否需要处理。通过删除某个阶段的输出文件及其下游文件来重新运行该阶段。直接读取中间文件进行调试。此模式之所以有效，是因为每个目录彼此独立，从而能够轻松实现并行化和简单的缓存。

### 结构化输出设计

为提示词设计结构化且可解析的输出，因为提示词设计会直接决定解析的可靠性。每个结构化提示词都应包含以下要素：

1. **章节标记**：解析器能够匹配的明确标题或前缀
2. **格式示例**：准确展示输出应采用的格式
3. **说明解析用途**：明确说明“我将以编程方式解析此内容”，使模型优先遵循格式要求
4. **受限值**：枚举选项、评分范围和固定格式

构建能够从容处理 LLM 输出变化的解析器，因为 LLM 并不会完美遵循指令。使用足够灵活的正则表达式模式来适应轻微的格式变化，在缺少某些部分时提供合理的默认值，并记录解析失败以供审查，而不是让程序崩溃。

### 智能体辅助开发

使用具备智能体能力的模型，通过快速迭代来加速开发：描述项目目标和约束，让智能体生成初始实现，针对具体失败进行测试和迭代，然后根据结果优化提示词和架构。

采用以下实践，因为它们能让智能体的输出保持专注和高质量：
- 预先提供清晰、具体的要求，以减少修改轮次
- 将大型项目拆分为独立组件，以便分别验证每个组件
- 在进入下一阶段之前测试每个组件，以尽早发现失败
- 一次只让智能体专注于一项任务，以防止上下文退化

### 成本和规模估算

在开始之前估算 LLM 处理成本，因为在规模化处理时，词元成本会迅速累积，而过晚发现预算超支将迫使你进行代价高昂的返工。使用以下公式：

```
Total cost = (items x tokens_per_item x price_per_token) + API overhead
```

对于批处理，估算每个项目的输入词元数（提示词 + 上下文），估算每个项目的输出词元数（典型响应长度），乘以项目数量，并额外增加 20-30% 的缓冲，以应对重试和失败。

在开发期间跟踪实际成本。如果成本显著超出估算，可通过截断来缩短上下文长度，对较简单的项目使用较小的模型，缓存并复用部分结果，或增加并行处理以缩短实际耗时。

## 详细主题

### 选择单智能体还是多智能体架构

对于各项目相互独立的批处理，默认使用单智能体流水线，因为它们更易于管理、运行成本更低，也更容易调试。仅当满足以下任一条件时，才升级为多智能体架构：

- 需要并行探索不同方面
- 任务超出单个上下文窗口的容量
- 专用子智能体经基准测试证明能够提升质量

选择多智能体是为了实现上下文隔离，而不是对角色进行拟人化。子智能体会获得全新的上下文窗口来处理专注的子任务，从而避免长时间运行的任务出现上下文退化。

有关详细的架构指导，请参阅 `multi-agent-patterns` 技能。

### 架构精简

从最小化架构开始，仅当生产环境中的证据证明有必要时才增加复杂性，因为过度设计的脚手架往往会限制而不是增强模型性能。

Vercel 的 d0 案例研究报告称，将许多专用工具精简为两个基础能力后，成功率得到了提升：命令执行和 SQL（claim-project-development-vercel-d0-reduction）。文件系统智能体模式使用标准 Unix 实用工具，而不是自定义探索工具。

**在以下情况下进行精简：**
- 数据层有完善的文档且结构始终一致
- 模型具备足够的推理能力
- 专用工具带来的限制多于助益
- 维护脚手架所花的时间多于改进成果所花的时间

**在以下情况下增加复杂度：**
- 底层数据混乱、不一致或文档不完善
- 领域需要模型所欠缺的专业知识
- 安全约束要求限制智能体的能力
- 操作确实复杂，并且能从结构化工作流中受益

有关详细的工具架构指导，请参阅 `tool-design` 技能。

### 迭代与重构

从一开始就为多次架构迭代做好规划，因为大规模生产级智能体系统始终需要重构。Manus 自发布以来已对其智能体框架进行了五次重构。“苦涩的教训”表明，针对当前模型局限而添加的结构，会随着模型改进而成为制约。

遵循以下实践，为变化做好准备：
- 保持架构简单且不预设立场，从而降低重构成本
- 跨模型代际进行测试，以验证框架没有限制性能
- 设计能够受益于模型改进的系统，而不是将当前局限固化其中

## 实用指南

### 项目规划模板

按顺序遵循此模板，因为每个步骤都会在下一步投入精力之前验证相关假设。

1. **任务分析**
   - 明确定义输入和期望输出
   - 分类：综合、生成、分类或分析
   - 根据业务影响设定可接受的错误率
   - 估算每次成功完成任务所产生的价值，以证明成本的合理性

2. **手动验证**
   - 使用目标模型测试一个有代表性的示例
   - 根据要求评估输出质量和格式
   - 识别需要增强解析器稳健性或修改提示词的失败模式
   - 估算每个项目的 token 数量，用于成本预测

3. **架构选择**
   - 根据上述标准选择单一流水线或多智能体架构
   - 确定所需的工具和数据源
   - 使用文件系统状态设计存储和缓存策略
   - 为处理阶段规划并行化方案

4. **成本估算**
   - 按 items x tokens x price 计算，并预留 20-30% 的缓冲
   - 估算每个流水线阶段的开发时间
   - 确定基础设施需求（API keys、存储、计算资源）
   - 预测生产运行中的持续运营成本

5. **开发计划**
   - 分阶段实施，每个阶段测试通过后再继续
   - 为每个阶段定义包含预期输出的测试策略
   - 设定与质量指标挂钩的迭代里程碑
   - 规划具备回滚能力的部署方案

## 示例

**示例 1：批量分析流水线（Karpathy 的 HN 时间胶囊）**

任务：以事后视角分析 10 年前的 930 个 HN 讨论并进行评级。

架构：
- 5 阶段流水线：fetch -> prompt -> analyze -> parse -> render
- 文件系统状态：data/{date}/{item_id}/，其中包含各阶段的输出文件
- 结构化输出：6 个部分，并有明确的格式要求
- 并行执行：使用 15 个工作进程进行 LLM 调用

结果：总成本为 $58，执行时间约 1 小时，输出为静态 HTML。

**示例 2：架构精简（Vercel d0）**

任务：用于内部分析的文本转 SQL 代理。

之前：使用许多专用工具，实测成功率较低，平均执行时间较长。

之后：使用两个工具（bash + SQL），实测成功率更高，平均执行时间更短（claim-project-development-vercel-d0-reduction）。

关键洞察：语义层本身已经是很好的文档。Claude 只需要获得直接读取文件的权限。

详细分析请参阅[案例研究](./references/case-studies.md)。

## 指南

1. 在构建自动化之前，通过手动原型验证任务与模型的适配性
2. 将流水线构建为离散、幂等且可缓存的阶段
3. 使用文件系统进行状态管理和调试
4. 设计提示词以生成结构化、可解析的输出，并提供明确的格式示例
5. 从最小化架构开始；仅在证明有必要时增加复杂性
6. 尽早估算成本，并在整个开发过程中持续跟踪
7. 构建健壮的解析器，以处理 LLM 输出的各种变化
8. 预期并规划多轮架构迭代
9. 测试脚手架究竟有助于还是限制了模型性能
10. 使用代理辅助开发，快速迭代实现方案

## 注意事项

1. **跳过手动验证**：在验证模型能够完成任务之前就构建自动化，如果方案本身存在根本性缺陷，将浪费大量时间。始终先通过模型界面运行一个有代表性的示例。
2. **单体流水线**：将所有阶段合并到一个脚本中，会增加调试和迭代的难度。应拆分各个阶段并持久化中间输出，以便每个阶段都能独立重新运行。
3. **对模型约束过度**：添加模型原本能够自行处理的防护措施、预过滤和验证逻辑，会降低性能。在保留脚手架之前，应先测试它究竟有帮助还是有负面影响。
4. **直到生产阶段才关注成本**：在规模化运行时，令牌成本会迅速累积。从一开始就进行估算和跟踪，避免预算意外迫使架构返工。
5. **要求完美解析**：期望 LLM 完美遵循格式指令，会导致系统十分脆弱。应构建健壮的解析器来处理各种变化，并记录失败情况以供审查。
6. **过早优化**：在基础流水线正确运行之前添加缓存、并行化和优化，会把精力浪费在迭代过程中可能被丢弃的代码上。
7. **模型版本锁定**：构建仅适用于某个特定模型版本的流水线，会导致系统十分脆弱。应跨多个模型代际进行测试，并抽象 LLM 调用层，以便无需重写流水线逻辑即可替换模型。
8. **缺少评估便部署**：在没有衡量输出质量的情况下发布代理流水线，会导致回归问题无法被发现。应在开发期间定义质量指标，并在每次更改模型或提示词之前和之后运行评估检查。
9. **溯源漂移**：将原始输入、中间输出和最终方案分散存放在临时建立的文件夹中，会导致审计变得不可能。应将每次流水线运行的源证据、转换结果、验证报告和决策保存在同一个目录中。

## 集成

此技能负责项目形态和流水线决策。相邻领域的决策由其他技能负责：

- `tool-design`：单个工具的接口层（描述、schema、响应格式、错误消息、MCP 命名空间、单个工具整合）。如果问题是“这个特定工具应该是什么样子”，而不是“流水线应该是什么样子”，则转交至该技能。
- `multi-agent-patterns`：Agent 拓扑决策（监督者与群体模式之比较、分层模式、交接协议、Agent 之间的上下文隔离）。此技能在项目层面决定使用单 Agent 还是多 Agent；拓扑结构的具体细节归 multi-agent-patterns 所有。
- `harness-engineering`：围绕项目的自主控制循环（锁定指标、新颖性门控、运行状态机、人工审批边界）。如果问题是“如何让它在无人值守的情况下连续运行数天”，则转交至该技能。
- `context-fundamentals`：上下文约束的概念框架，这些约束会影响每个阶段的提示词设计。
- `evaluation`：流水线运行的结果衡量和质量门控。
- `context-compression`：用于长时间运行的流水线阶段产生需要总结的轨迹时。
