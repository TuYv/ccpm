# 记忆系统设计

记忆提供了持久化层，使智能体能够跨会话保持连续性，并基于积累的知识进行推理。简单的智能体完全依赖上下文来实现记忆，会在会话结束时丢失所有状态。复杂的智能体则采用分层记忆架构，在即时上下文需求与长期知识保留之间取得平衡。从向量存储到知识图谱，再到时序知识图谱的演进，体现了为改善检索和推理而不断增加对结构化记忆的投入。

## 何时启用

在以下情况下启用此技能：
- 构建必须跨会话持久保存知识的智能体
- 在记忆框架（Mem0、Zep/Graphiti、Letta、LangMem、Cognee）之间进行选择
- 需要在多轮对话中保持实体一致性
- 实现基于积累知识的推理
- 设计可在生产环境中扩展的记忆架构
- 根据基准测试（LoCoMo、LongMemEval、DMR）评估记忆系统
- 使用自动实体/关系抽取和自我改进记忆（Cognee）构建动态记忆

对于由其他技能负责的相邻工作，请勿启用此技能：
- 基于文件的暂存区、运行日志和工具输出卸载：`filesystem-context`。
- 对话压缩或供人阅读的交接摘要：`context-compression`。
- 单条轨迹内的掩码、前缀缓存、令牌预算或检索范围限定：`context-optimization`。
- 基于 RDF 状态的形式化信念/愿望/意图模型：`bdi-mental-states`。

## 核心概念

可将记忆视为一个从易失性上下文窗口到持久化存储的连续谱。默认选择能够满足检索需求的最简单层级，因为基准测试证据表明，对于某些记忆工作负载，工具复杂度不如可靠检索重要（claim-memory-locomo-filesystem-baseline）。只有当检索质量下降，或智能体需要多跳推理、关系遍历或时间旅行查询时，才添加结构（图、时序有效性）。

## 详细主题

### 生产级框架概览

根据智能体所需的主要检索模式选择框架。使用此表缩小候选范围，然后通过下方的基准测试数据进行验证。

| 框架 | 架构 | 最适合 | 权衡 |
|-----------|-------------|----------|-----------|
| **Mem0** | 向量存储 + 图记忆，可插拔后端 | 多租户系统、广泛的集成需求 | 对多智能体场景的专门优化较少 |
| **Zep/Graphiti** | 时序知识图谱，双时态模型 | 需要关系建模 + 时序推理的企业 | 高级功能仅限云端 |
| **Letta** | 具有分层存储（上下文内/核心/归档）的自编辑记忆 | 完整的智能体自省、有状态服务 | 对简单用例而言过于复杂 |
| **Cognee** | 通过包含可自定义 Tasks 的可自定义 ECL 管道构建多层语义图 | 可适应并学习的演进式智能体记忆；多跳推理 | 摄取阶段的处理更繁重 |
| **LangMem** | 面向 LangGraph 工作流的记忆工具 | 已经使用 LangGraph 的团队 | 与 LangGraph 紧密耦合 |
| **File-system** | 使用命名约定的纯文件 | 简单智能体、原型设计 | 无语义搜索、无关系 |

当智能体需要双时间建模（同时跟踪事件发生时间和摄取时间）时，请选择 Zep/Graphiti，因为其三层知识图谱（情节、语义实体、社区子图）擅长处理时态查询。当优先事项是借助托管基础设施快速投入生产时，请选择 Mem0。当智能体需要通过其智能体开发环境进行深度自省时，请选择 Letta。当智能体必须构建稠密的多层语义图谱时，请选择 Cognee——它将文本块和实体类型作为节点分层组织，并使用详细的关系边进行连接，而且每个核心部分（摄取、实体提取、后处理、检索）都可以自定义。

### 记忆层（决策点）

选择能够满足持久化要求的最浅层记忆。每加深一层都会增加基础设施成本和运维复杂性，因此只有在较浅层无法满足检索或持久性需求时才应升级。

| 层级 | 持久性 | 实现方式 | 使用时机 |
|-------|------------|----------------|-------------|
| **工作记忆** | 仅限上下文窗口 | 系统提示词中的暂存区 | 始终使用——通过注意力占优的位置进行优化 |
| **短期记忆** | 会话范围 | 文件系统、内存缓存 | 中间工具结果、对话状态 |
| **长期记忆** | 跨会话 | 键值存储 → 图数据库 | 用户偏好、领域知识、实体注册表 |
| **实体记忆** | 跨会话 | 实体注册表 + 属性 | 维持身份一致性（“John Doe”在不同对话中代表同一个人） |
| **时态知识图谱** | 跨会话 + 历史记录 | 带有效期区间的图 | 随时间变化的事实、时间旅行查询、防止上下文冲突 |

### 检索策略

使检索策略与查询形态相匹配。语义搜索能很好地处理直接的事实查询，但在多跳推理中性能会下降；基于实体的遍历能处理“关于 X 的一切”这类查询，但需要图结构；时态过滤能处理不断变化的事实，但需要有效性元数据。当准确性至关重要且基础设施预算允许时，可将多种策略组合成混合检索。

| 策略 | 适用场景 | 局限性 |
|----------|----------|------------|
| **语义式**（嵌入相似度） | 直接的事实查询 | 在多跳推理中效果下降 |
| **基于实体**（图遍历） | “告诉我关于 X 的一切” | 需要图结构 |
| **时序式**（有效性过滤） | 事实随时间变化 | 需要有效性元数据 |
| **混合式**（语义 + 关键词 + 图） | 整体准确率最佳 | 所需基础设施最多 |

混合方法仅检索相关的子图或记忆，从而减少活跃上下文。Cognee 通过图、向量和关系型存储中的多种搜索模式实现混合检索，使智能体能够选择适合查询类型的检索策略，而不是采用一刀切的方法。

### 记忆整合

定期运行整合以防止无限增长，因为不受控制的记忆累积会随着时间推移降低检索质量。**使其失效，但不要丢弃**——保留历史对于需要重建过去状态的时序查询至关重要。当记忆数量达到阈值、检索质量下降或到达预定时间间隔时，触发整合。有关可运行的整合代码，请参阅[实现参考](./references/implementation.md)。

## 实践指南

### 选择记忆架构

**从最简单的可行层开始，仅在检索质量下降时增加复杂性。**大多数智能体从第一天起并不需要时序知识图谱。请遵循以下升级路径：

1. **原型设计**：使用文件系统记忆。将事实存储为带时间戳的结构化 JSON。这样可以在投入基础设施之前验证智能体行为。
2. **规模化**：当智能体需要语义搜索和多租户隔离时，迁移到 Mem0 或带有元数据的向量存储，因为基于文件的查找无法处理相似度查询。
3. **复杂推理**：当智能体需要关系遍历、时序有效性或跨会话综合时，添加 Zep/Graphiti。Graphiti 使用带有通用关系的结构化连接，使图保持简单且易于推理；Cognee 则构建具有详细关系边的更密集多层语义图——应根据智能体需要时序双模型（Graphiti）还是更丰富的互联知识结构（Cognee）进行选择。
4. **完全控制**：当智能体必须通过深度内省自行管理其记忆时，使用 Letta 或 Cognee，因为这些框架将记忆操作公开为智能体的一等动作。

### 与上下文集成

即时加载记忆，而不是预加载所有内容，因为大型上下文载荷成本高昂，并且会降低注意力质量。将检索到的记忆放置在注意力较集中的位置（上下文的开头或结尾），以最大限度地增强其对生成结果的影响。

### 错误恢复

妥善处理检索失败，因为记忆系统本身就存在噪声。按顺序应用以下恢复策略：

- **检索结果为空**：回退到范围更广的搜索（移除实体过滤器、扩大时间范围）。如果结果仍为空，则提示用户进行澄清。
- **结果过时**：检查 `valid_until` 时间戳。如果大多数结果均已过期，请在重试前触发整合。
- **事实冲突**：优先采用 `valid_from` 最新的事实。如果置信度较低，则向用户说明存在冲突。
- **存储失败**：将写入操作排队等待重试。绝不要因记忆写入而阻塞智能体的响应。

## 示例

**示例 1：Mem0 集成**
```python
from mem0 import Memory

m = Memory()
m.add("User prefers dark mode and Python 3.12", user_id="alice")
m.add("User switched to light mode", user_id="alice")

# Retrieves current preference (light mode), not outdated one
results = m.search("What theme does the user prefer?", user_id="alice")
```

**示例 2：时态查询**
```python
# Track entity with validity periods
graph.create_temporal_relationship(
    source_id=user_node,
    rel_type="LIVES_AT",
    target_id=address_node,
    valid_from=datetime(2024, 1, 15),
    valid_until=datetime(2024, 9, 1),  # moved out
)

# Query: Where did user live on March 1, 2024?
results = graph.query_at_time(
    {"type": "LIVES_AT", "source_label": "User"},
    query_time=datetime(2024, 3, 1)
)
```

**示例 3：Cognee 记忆摄取与搜索**
```python
import cognee
from cognee.modules.search.types import SearchType

# Ingest and build knowledge graph
await cognee.add("./docs/")
await cognee.add("any data")
await cognee.cognify()

# Enrich memory
await cognee.memify()

# Agent retrieves relationship-aware context
results = await cognee.search(
    query_text="Any query for your memory",
    query_type=SearchType.GRAPH_COMPLETION,
)
```

## 指南

1. 从文件系统记忆开始；只有当检索质量有需求时才增加复杂性
2. 对任何可能随时间变化的事实跟踪其时态有效性
3. 使用混合检索（语义 + 关键词 + 图）以获得最佳准确率
4. 定期整合记忆——将其设为失效，但不要丢弃
5. 针对检索失败进行设计：当记忆查询没有返回任何内容时，始终提供备用方案
6. 考虑持久记忆对隐私的影响（保留策略、删除权）
7. 在进行更改前后，使用 LoCoMo 或 LongMemEval 对记忆系统进行基准测试
8. 在生产环境中监控记忆增长和检索延迟

## 常见陷阱

1. **将所有内容都塞入上下文**：把所有可用记忆加载到提示词中成本高昂，还会降低注意力质量。应改用带相关性过滤的即时检索。
2. **忽略时态有效性**：事实会过时。如果不跟踪有效性，过时的信息就会污染上下文，导致智能体基于错误的假设采取行动。
3. **过早进行过度工程化**：在某些基准测试中，简单的文件系统后端记忆可能优于更专业的工具（claim-memory-locomo-filesystem-baseline）。只有当简单方法被明确证明无效时，才增加复杂性。
4. **没有整合策略**：记忆无限增长会随时间推移降低检索质量。设置记忆数量阈值或计划时间间隔以触发整合。
5. **嵌入模型不匹配**：使用一个嵌入模型写入记忆，再使用另一个模型读取，会导致检索效果很差，因为不同向量空间无法互换。为每个记忆存储固定使用单一嵌入模型；如果模型发生变化，则对所有条目重新进行嵌入。
6. **图模式过于僵化**：结构化程度过高的图模式（僵化的节点类型、固定的关系标签）会在领域演进时失效。应优先采用通用关系类型和灵活的属性包，这样新增实体类型时就无需迁移模式。
7. **陈旧记忆污染**：与当前状态相矛盾的旧记忆会在不知不觉中破坏智能体的行为。实施过期策略或置信度衰减机制，使智能体降低陈旧事实的优先级，并在检测到矛盾时明确呈现。
8. **记忆与上下文不匹配**：检索到的记忆在主题上相关，但在上下文中并不正确（例如，当智能体讨论的是 Python 编程语言时，却检索到关于“Python”这种蛇的记忆）。可通过在记忆条目中加入会话或领域元数据，并在检索期间据此进行过滤来缓解这一问题。

## 集成

此技能负责持久化语义记忆。相邻技能负责暂存、压缩和上下文策略：

- `filesystem-context`：在需要进行语义检索之前，使用基于文件的暂存区、日志和简单运行状态。
- `context-compression`：以文字摘要和交接信息保留会话状态。
- `context-optimization`：在有效上下文预算内进行即时记忆加载和检索范围限定。
- `context-degradation`：将过时或相互冲突的记忆视为上下文污染或冲突。
- `bdi-mental-states`：当信念、愿望、意图和溯源链至关重要时，进行形式化的心理状态建模。
- `multi-agent-patterns`：跨智能体共享记忆。
- `evaluation`：记忆质量、检索正确性和基准选择。
