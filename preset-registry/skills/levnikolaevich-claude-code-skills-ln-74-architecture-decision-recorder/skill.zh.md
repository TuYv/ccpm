# 架构决策记录

**目标：** 在紧凑且持久的记录中保留一个具有架构重要性的选择的背景、影响因素、备选方案、决策和后果。只更改已批准的决策文档；不要设计整个系统、默默批准决策、删除历史、审计代码或实施该选择。

**执行契约：** 有序复选框是完成定义。内部将每一项跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个章节后都要重新核对各项。返回前，解决所有 `PENDING`，并只统计 `PROVEN` 和 `CLEARED`；将技能的判定和批准规则应用于每个缺口。保留用户意图、范围和现有授权。继续执行已授权的工作；仅针对有重大影响且尚未解决的选择或所需的外部批准进行询问。根据实质风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；对于其他义务，选择适合的验证方法。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 现有决策约定 | 搜索仓库并直接读取文档 | 使用默认路径和紧凑格式 |
| 决策驱动因素 | 需求、架构制品、实现证据和利益相关者陈述 | 将不受支持的驱动因素标记为 `UNKNOWN` |
| 备选方案和外部声明 | 仓库证据加当前官方来源 | 将时效性声明标记为 `UNVERIFIED` |
| 顺序和取代关系 | 现有文件名、索引和决策链接 | 返回 `BLOCKED`，而不是复用编号 |
| 文档变更 | 对一个已批准的决策记录进行最小补丁修改，并添加必要的取代链接 | 如果授权或路径不明确，则返回 `BLOCKED` |

一条记录只包含一个决策。如果请求包含具有不同驱动因素或生命周期的独立决策，只有在获得明确批准后才能拆分。

## 制品规则

- 如果仓库中已有 ADR 约定，则复用该约定。
- 否则使用 `docs/architecture/decisions/NNNN-<slug>.md`，并采用下一个未使用的单调递增编号。
- 绝不重新编号、删除或重写历史记录中的决策和理由。根据以下规则，允许对状态和取代链接进行范围受限的更新；区分不断演进的提议草稿和已接受的历史记录。
- 新记录默认设为 `Proposed`。
- 只有在获得有权决策者的明确确认后，才能使用 `Accepted`。
- 提议中的替代记录链接到当前决策，但不改变其生效状态。只有在替代记录获得明确接受后，才将旧记录标记为 `Superseded`，并建立双向链接；保留历史内容。
- 保持记录足够简短，以便作为单个决策进行审阅。
- 保留未来维护者安全地重新考虑该决策所需的理由。
- 明确标注回顾性记录；不要暗示文档是在实施前获得的批准。
- 将接受前所需的证据与采用后的监控要求分开。
- 优先使用稳定的仓库引用，而不是对话、分支本地或临时链接。

## 检查清单

### 1. 确立决策契约

- [ ] 明确具体决策、范围、负责人或决策者、受影响的系统，以及该选择为何具有架构层面的重要性。
- [ ] 阅读仓库说明、Git 状态和现有的决策记录规范。
- [ ] 在分配新的记录编号之前，搜索重复、冲突、已弃用或已被取代的决策。
- [ ] 确认请求针对的是一个决策，而不是宽泛的设计或实施计划。
- [ ] 明确已批准的状态；在未明确接受的情况下，默认为 `Proposed`。

### 2. 收集上下文和影响因素

- [ ] 以价值中立的语言陈述当前上下文和问题。
- [ ] 根据现有证据提取业务驱动因素、质量属性、约束、假设和决策期限。
- [ ] 识别受影响的边界、契约、数据、安全性、运维、成本、所有权和迁移影响。
- [ ] 区分当前事实、预测和偏好。
- [ ] 记录可能改变选择的矛盾或缺失证据。

### 3. 评估备选方案

- [ ] 包含现状和最简单的可信选项，除非能够证明它们不可行。
- [ ] 包含实质不同的备选方案，而不是表面上的变体。
- [ ] 使用相同的驱动因素比较各个选项：正确性、质量目标、复杂度、可逆性、成本、运维、团队适配性和演进能力。
- [ ] 说明每个被拒绝的备选方案为何在当前上下文中处于劣势，但不要声称其在所有情况下都较差。
- [ ] 记录敏感性或复审触发条件，说明这些条件出现时为何可以在之后优先考虑被拒绝的选项。

### 4. 记录决策

- [ ] 编写标题、状态、日期、决策者或负责人、上下文、驱动因素、考虑过的选项、决策、后果、验证方式和复审触发条件。
- [ ] 使用主动且可测试的语言陈述决策，并明确哪些事项仍被有意留待决定。
- [ ] 记录正面、负面和中性的后果，以及已接受的风险。
- [ ] 通过稳定的仓库引用链接受影响的需求、设计、图表、接口、迁移文档或问题单。
- [ ] 对拟议或已接受的取代关系应用制品规则；验证链接并保留先前的决策依据。

### 5. 验证并报告

- [ ] 确认记录只包含一个决策，并且无需查阅对话历史即可理解。
- [ ] 确认重要主张都有证据，或标记为假设/未知并附带验证行动；对于回顾性记录，绝不臆造历史依据或被拒绝的备选方案。
- [ ] 确认没有在缺少明确授权的情况下分配 `Accepted`。
- [ ] 当记录和状态有效时使用 `RECORDED`；当重要上下文或所需的接受授权仍未解决时使用 `INCOMPLETE`；一份完整且明确标记为 `Proposed` 的记录不要求获得接受才能使用 `RECORDED`；对于范围不明确、编号不安全、所有权冲突或没有可写入的目标位置的情况，使用 `BLOCKED`。

## 自检

- [ ] **返回前进行协调。** 检查逐项证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。修正报告或经授权的制品。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露仍存在的缺口。

1. **Result:** 未提供具体 Skill 任务或文档片段，暂无法形成技能专属结论或支持的结果。
2. **Scope:** 未审阅或修改任何文件；无排除范围、基线或可用假设。
3. **Evidence:** 未发现 Artifact path、决策身份/状态/负责人、选定选项、备选方案、后果、证据或验收要求。
4. **Verification:** 未执行检查；没有可用证据，也没有需要清理或处理的外部状态。
5. **Completion:** `Checklist: 0/1 complete`; `Incomplete: UNPROVEN`：缺少待处理的 Skill 任务或文档片段，无法评估结果；影响是无法开始审阅或修改；下一步是提供具体任务、相关文件路径或英文 `SKILL.md` 片段。剩余风险：目标和验收标准未定义；所需决策：明确需要完成的操作。
