# 架构决策记录器

**目标：**在一份紧凑且持久的记录中，保留一个具有架构重要性的选择所涉及的上下文、驱动因素、备选方案、决策和后果。仅修改已批准的决策文档；不要设计整个系统、默默批准决策、删除历史记录、审计代码或实现该选择。

**执行契约：**将下面按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框跟踪为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用表明其条件触发器不存在的证据将其解决为 `CLEARED`，或解决为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。  
返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，将此技能的裁决、决策和批准规则应用于每个 `UNPROVEN`，并在开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | section/item — 原因；对结果的影响；确切的下一步操作**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 现有决策约定 | 仓库搜索和直接读取文档 | 使用默认路径和紧凑格式 |
| 决策驱动因素 | 需求、架构工件、实现证据和利益相关者陈述 | 将不受支持的驱动因素标记为 `UNKNOWN` |
| 备选方案和外部声明 | 仓库证据加上当前官方来源 | 将时效性声明标记为 `UNVERIFIED` |
| 序列和取代关系 | 现有文件名、索引和决策链接 | 返回 `BLOCKED`，而不是重复使用编号 |
| 文档变更 | 对一份已批准的决策记录进行最小补丁修改，并添加必要的取代关系链接 | 如果权限或路径不明确，则返回 `BLOCKED` |

一份记录只包含一个决策。如果请求包含具有不同驱动因素或生命周期的独立决策，只有在获得明确批准后才能拆分。

## 工件规则

- 如果仓库中存在既定的 ADR 约定，则沿用该约定。
- 否则使用 `docs/architecture/decisions/NNNN-<slug>.md`，并采用下一个未使用的单调递增编号。
- 绝不重新编号、覆盖或删除历史记录。
- 新记录默认设为 `Proposed`。
- 只有在获得授权决策者的明确确认后，才能使用 `Accepted`。
- 将被替代的记录标记为 `Superseded`，并双向链接；保留其原始内容。
- 共享需求和架构工件仅通过路径或标题链接。
- 记录正面、负面和中性的后果，不使用倡导性语言。
- 保持记录足够简短，以便作为单个决策进行审阅。
- 保留未来维护者安全地重新考虑该决策所需的理由。
- 明确标记回顾性记录；不要暗示在实现之后创建的文档代表事先批准。
- 将接受前所需的证据与采用后所需的监控分开。
- 优先使用稳定的仓库引用，而不是对话、分支本地或临时链接。

## 检查清单

### 1. 确立决策契约

- [ ] 明确具体决策、范围、负责人或决策者、受影响的系统，以及该选择为何在架构上具有重要意义。
- [ ] 阅读仓库说明、Git 状态和现有的决策约定。
- [ ] 在分配新记录之前，搜索重复、冲突、已弃用或取代现有决策的决策。
- [ ] 确认请求针对的是一个决策，而不是宽泛的设计或实现计划。
- [ ] 确定已批准状态；在未明确接受时，默认为 `Proposed`。

### 2. 收集上下文和驱动因素

- [ ] 使用价值中立的语言陈述当前上下文和问题。
- [ ] 根据现有证据提取业务驱动因素、质量属性、约束、假设和决策时限。
- [ ] 确定受影响的边界、契约、数据、安全性、运维、成本、所有权和迁移影响。
- [ ] 将当前事实与预测和偏好分开。
- [ ] 记录可能改变选择的矛盾或缺失证据。

### 3. 评估替代方案

- [ ] 纳入现状和最简单的可信选项，除非能够证明它们不可行。
- [ ] 纳入实质不同的替代方案，而不是表面上的变体。
- [ ] 根据相同的驱动因素比较各选项：正确性、质量目标、复杂度、可逆性、成本、运维、团队适配性和演进能力。
- [ ] 说明每个被拒绝的替代方案为何在当前上下文中处于劣势，但不要声称其在所有情况下都不如其他方案。
- [ ] 记录敏感性或评审触发条件，说明未来什么情况下被拒绝的选项可能更合适。

### 4. 记录决策

- [ ] 写明标题、状态、日期、决策者或负责人、上下文、驱动因素、考虑过的选项、决策、后果、验证方式和评审触发条件。
- [ ] 使用主动且可测试的语言陈述决策，并明确哪些事项仍被有意留待决定。
- [ ] 记录正面、负面和中性的后果，以及已接受的风险。
- [ ] 通过稳定的仓库引用链接受影响的需求、设计、图表、接口、迁移文档或问题。
- [ ] 对于取代关系，在不删除此前决策依据的情况下更新状态和交叉链接。

### 5. 验证并报告

- [ ] 确认记录只包含一个决策，并且无需对话历史即可理解。
- [ ] 确认每个具有后果的主张都有证据、明确命名的假设或明确的负责人。
- [ ] 确认未在缺乏明确授权的情况下指定 `Accepted`。
- [ ] 确认除获批准的决策文档外，没有更改架构、代码、测试、任务跟踪器或外部系统。
- [ ] 当记录和状态有效时使用 `RECORDED`；当重要上下文或授权仍未确定时使用 `INCOMPLETE`；当范围含糊、编号不安全、所有权冲突或没有可写入的目标位置时使用 `BLOCKED`。

## 输出契约

```markdown
# Architecture Decision Record

**Verdict:** RECORDED | INCOMPLETE | BLOCKED
**Artifact:** path
**Decision status:** Proposed | Accepted | Deprecated | Superseded

## Decision captured
- Context, selected option, and decisive drivers

## Alternatives and consequences
- Rejected options, accepted costs, and review triggers

## Links changed
- New record and any supersession links

## Open authority or evidence
Only items that prevent acceptance or could reverse the decision.
```
