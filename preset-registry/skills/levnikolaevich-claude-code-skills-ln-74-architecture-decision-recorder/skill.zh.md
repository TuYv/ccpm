# 架构决策记录器

**目标：** 以紧凑、持久的记录保存一项具有重大架构意义的选择所涉及的背景、影响因素、备选方案、决策及后果。只能修改已获批准的决策文档；不要设计整个系统、在未明确说明的情况下批准决策、删除历史记录、审计代码或实现该选择。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序处理每一项，并且仅当其操作和所需证据均已完成时，才能将其标记为完成。标记为 `N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的判定和批准规则应用于每个未完成项目，并在开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的后续操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 现有决策惯例 | 仓库搜索和直接读取文档 | 使用默认路径和紧凑格式 |
| 决策驱动因素 | 需求、架构产物、实现证据和利益相关者陈述 | 将缺乏依据的驱动因素标记为 `UNKNOWN` |
| 备选方案和外部声明 | 仓库证据以及当前的官方来源 | 将时效性较强的声明标记为 `UNVERIFIED` |
| 编号顺序和取代关系 | 现有文件名、索引和决策链接 | 返回 `BLOCKED`，而不是重复使用编号 |
| 文档修改 | 仅对一份已获批准的决策记录及必要的取代关系链接进行最小化修改 | 如果权限或路径不明确，则返回 `BLOCKED` |

一份记录只记录一个决策。如果请求中包含具有不同驱动因素或生命周期的独立决策，只有在获得明确批准后才能将其拆分。

## 产物规则

- 如果仓库中已有既定的 ADR 惯例，请沿用该惯例。
- 否则，使用 `docs/architecture/decisions/NNNN-<slug>.md`，其中编号采用下一个尚未使用的单调递增编号。
- 绝不要重新编号、覆盖或删除历史记录。
- 新记录的默认状态为 `Proposed`。
- 只有在获得授权决策者的明确确认后，才能使用 `Accepted`。
- 将被取代的记录标记为 `Superseded`，并建立双向链接；保留其原始内容。
- 对共享需求和架构产物仅通过路径或标题建立链接。
- 以不带倾向性的语言记录正面、负面和中性后果。
- 记录应足够简短，以便作为单个决策进行审查。
- 保留未来维护者安全地重新审视该决策所需的理由。
- 明确标注追溯性记录；不得暗示在实现之后创建的文档曾构成事先批准。
- 将接受前所需的证据与采用后所需的监控分开。
- 优先使用稳定的仓库引用，而不是对话、分支局部链接或临时链接。

## 检查清单

### 1. 确立决策约定

- [ ] 明确具体决策、范围、负责人或决策者、受影响的系统，以及该选择为何具有重大的架构意义。
- [ ] 阅读仓库说明、Git 状态和现有决策惯例。
- [ ] 在分配新记录前，搜索重复、冲突、已弃用或构成取代关系的决策。
- [ ] 确认该请求是一项决策，而不是宽泛的设计或实现计划。
- [ ] 明确已获批准的状态；当接受情况未得到明确说明时，默认为 `Proposed`。

### 2. 收集背景与影响因素

- [ ] 使用价值中立的语言陈述当前背景和问题。
- [ ] 从现有证据中提取业务驱动因素、质量属性、约束、假设和决策期限。
- [ ] 识别受影响的边界、契约、数据、安全、运维、成本、所有权和迁移影响。
- [ ] 将当前事实与预测和偏好区分开来。
- [ ] 记录可能改变选择的矛盾或缺失证据。

### 3. 评估备选方案

- [ ] 包含维持现状和最简单的可信方案，除非它们已被证明不可行。
- [ ] 包含存在实质性差异的备选方案，而非表面上的变体。
- [ ] 根据相同的驱动因素比较各方案：正确性、质量目标、复杂性、可逆性、成本、运维、团队适配度和演进能力。
- [ ] 说明每个被否决的备选方案为何在此背景下落选，但不要声称其普遍劣于其他方案。
- [ ] 记录未来可能使被否决方案更为可取的敏感因素或评审触发条件。

### 4. 记录决策

- [ ] 写明标题、状态、日期、决策者或负责人、背景、驱动因素、已考虑的方案、决策、后果、验证方式和评审触发条件。
- [ ] 使用主动、可测试的语言陈述决策，并明确哪些事项被有意保留为未决。
- [ ] 记录正面、负面和中性后果，以及已接受的风险。
- [ ] 通过稳定的仓库引用链接受影响的需求、设计、图表、接口、迁移文档或议题。
- [ ] 对于取代已有决策的情况，更新状态和交叉链接，但不要抹除先前的决策依据。

### 5. 验证并报告

- [ ] 确认记录只包含一个决策，并且无需对话历史即可理解。
- [ ] 确认每项会产生后果的主张都有证据、具名假设或明确负责人。
- [ ] 确认未在缺少明确授权的情况下将状态设为 `Accepted`。
- [ ] 确认除获批的决策文档外，架构、代码、测试、任务跟踪器或外部系统均未发生变更。
- [ ] 当记录和状态有效时使用 `RECORDED`；当重要背景或授权仍未确定时使用 `INCOMPLETE`；当范围不明确、编号不安全、所有权冲突或没有可写入目标时使用 `BLOCKED`。

## 输出契约

```markdown
# Architecture Decision Record

**Verdict:** RECORDED | INCOMPLETE | BLOCKED
**Artifact:** path
**Decision status:** Proposed | Accepted | Deprecated | Superseded

## Decision captured
- Context, selected option, and decisive drivers

## Alternatives and consequences
- Rejected options, accepted costs, and review triggers

## Links changed
- New record and any supersession links

## Open authority or evidence
Only items that prevent acceptance or could reverse the decision.
```
