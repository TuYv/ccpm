# 依赖升级器

**目标：** 以小批次、可归因的方式升级依赖项。保留清单、锁定文件、运行时支持和产品行为；除非有兼容性、安全性或维护方面的证据，否则不要将更新版本视为有价值。

**执行契约：** 有序复选框是完成定义。内部将每一项标记为 `PENDING`、附有具体证据的 `PROVEN`、附有该条件不存在的证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每个部分完成后都要重新核对。在返回前，解决所有 `PENDING` 项，并只统计 `PROVEN` 和 `CLEARED` 项；根据技能的判定和批准规则处理每个缺口。

保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决的重大选择或所需的外部批准询问用户。根据实际风险调整深度，但不要在不说明的情况下跳过检查。保留依赖项和安全检查的顺序；在此之外，为每项义务选择适当的验证方式。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 包管理器检测 | 清单、锁定文件、工作区文件、运行时文件和仓库说明 | 始终在选择命令或更新范围之前 | 构建和 CI 配置 |
| 过期和存在漏洞的软件包 | 原生包管理器的过期检查和审计命令 | 包管理器和注册表可用时 | 官方注册表、供应商公告和锁定文件检查 |
| 破坏性变更和支持情况 | 官方发行说明、迁移指南、变更日志、公告和运行时支持表 | 每次有影响的次版本、主版本、替换或安全更新 | 主要来源代码库的版本发布信息；否则标记为 `UNVERIFIED` |
| 使用情况和影响范围 | 语言服务器或宿主原生代码智能工具 | 更新后的 API、类型、插件、构建工具或运行时可能影响消费者时 | 针对导入、符号、配置和脚本的定向搜索 |
| 安全的版本变更 | 原生包管理器命令 | 更新清单和生成的锁定状态时 | 不要手动编辑锁定文件或模拟包解析 |
| 验证 | 仓库定义的安装、还原、构建、代码检查、类型检查、测试、迁移和冒烟测试命令 | 变更之前以及每个批次之后 | 检查 CI 和脚本，并明确标记为未验证 |
| 差异和回滚 | Git 状态、差异以及隔离提交或工作树 | 保护用户变更并仅回滚失败的批次时 | 如果无法安全隔离批次，则停止 |

绝不要发布软件包、轮换凭据、部署，或削弱审计和验证门禁。不要在没有使用环境常规安全措施的情况下，运行来自不受信任软件包源的软件包生命周期脚本。

## 证据规则

- 清单声明约束，锁定文件记录已解析的版本；当活动环境不同时，安装元数据可以证明活动环境。注册表中的“latest”不能覆盖运行时或兼容性约束。
- 漏洞发现必须包含受影响的版本、公告、可达性或暴露环境，以及可信的修复方案。
- 破坏性变更声明必须包含与确切版本转换相匹配的发行或迁移证据。
- 仅当锁定文件变更由选定的原生包管理器生成，且符合仓库预期版本时，才保留这些生成的锁定文件变更。
- 升级成功需要仓库验证，而不仅仅是安装或还原成功。

## 检查清单

### 1. 发现范围并保护工作区

- [ ] 在所请求的更新范围内检测包管理器、清单文件、锁文件、注册表、运行时/工具版本固定、生成状态和依赖关联的工作区；仅在存在已证实的兼容性依赖时扩展范围。
- [ ] 将每个交付物分类为应用程序、库、插件、CLI、容器或构建工具，以便正确解读版本范围、锁文件、对等依赖约束和支持的运行时承诺。
- [ ] 阅读仓库说明，确定支持的包管理器版本、更新命令、锁文件策略和 CI 预期。
- [ ] 检查 Git 状态并隔离工作，确保不会覆盖现有用户更改，也不会将其误认为是升级输出。
- [ ] 建立本次运行所属的资源台账，记录每个已创建的绝对路径、工作树、进程 ID、缓存、报告和临时产物；绝不将预先存在的资源登记为清理目标。
- [ ] 明确所请求的范围：仅安全更新、常规补丁或次要版本维护、指定包、主版本更新、运行时迁移，还是完整刷新。
- [ ] 在编辑前获取安装或恢复、构建、代码检查、类型检查、测试、冒烟测试和安全审计基线。
- [ ] 记录预先存在的失败、公告、弃用提示、对等依赖冲突和不受支持的运行时组合。

### 2. 研究并规划批次

- [ ] 使用原生过期检查和审计命令，在不更改文件的前提下清点直接依赖和相关传递依赖的更新。
- [ ] 将移除项、安全修复、常规更新、主版本变更、构建工具变更以及运行时或生态系统迁移分开处理。
- [ ] 查阅官方发行说明和迁移指南，了解 API 变更、配置变更、默认值、对等依赖约束、运行时支持和已移除行为。
- [ ] 解析环境标记、额外依赖、可选/开发组、对等依赖、目标框架和特定平台包；如果项目承诺支持更广泛的矩阵，仅能在当前机器上解析的依赖图并不充分。
- [ ] 查阅官方安全公告，了解受影响的版本范围、利用条件、修复版本、缓解方案，以及该依赖是否可在本项目中被触达。
- [ ] 针对每个重要依赖，搜索实际导入、符号、插件、脚本、配置、生成代码和运行时加载。
- [ ] 将未使用、重复、已弃用、已被替代或在平台上冗余的依赖作为单独的移除候选项；要求提供运行时和动态加载证据，且当移除超出所请求的升级范围时，需获得用户明确批准。
- [ ] 按实际兼容性图谱安排批次顺序；包管理器/运行时、工具链、基础库、框架、集成和叶子依赖只是发现指南，而非固定顺序。将相互依赖的转换合并处理。
- [ ] 将常规批次控制在足以归因失败的小范围内；仅当兼容性矩阵要求时，才将框架系列、分析器、生成的客户端或紧密受限的对等依赖一起分批。
- [ ] 当存在互斥的版本策略、运行时支持、许可证、注册表策略，或迁移范围会改变产品意图时，暂停并请求用户指示。

### 3. 安全地应用每个批次

- [ ] 使用原生包管理器，按照仓库预期的版本和标志更新清单文件与锁定文件。
- [ ] 除非包管理器无法安全地保留锁定图，否则在请求范围较窄时避免广泛重新解析；如无法避免产生大量变更，请说明原因。
- [ ] 在安全风险需要时，检查安装脚本、注册表来源、校验和、软件包来源，以及意外新增的传递依赖包。
- [ ] 根据已记录的破坏性变更，更新所需的导入、API、类型、配置、构建脚本、插件、生成的客户端和应用程序代码。
- [ ] 仅当已接受的行为、前置条件、配置或命令发生变化时，更新用户或运维文档。
- [ ] 立即检查差异，确认不存在无关格式化、被删除的约束、注册表漂移、换行符变更、生成的构件以及意外降级。
- [ ] 检查解析后的依赖图，确认没有新出现的重复主版本、不满足或被静默忽略的对等依赖、发生变化的可选功能，以及会改变运行时行为的传递依赖替换。
- [ ] 没有证据时，不得抑制警告、禁用审计、跳过必要检查、强制固定不兼容的对等依赖，或添加兼容性变通方案。

### 4. 验证并保留或回滚

- [ ] 从足够干净的状态运行安装或还原，以证明锁定文件可复现。
- [ ] 每个批次之后，运行相关的构建、代码检查、类型检查、单元测试、集成测试、冒烟测试、打包、迁移和应用启动检查。
- [ ] 将受影响的运行时、目标框架、操作系统、架构和功能组合分类为必需或可选；只有在每个必需单元都有本地或可信 CI 证据时才保留批次；当必需覆盖范围没有可信替代方案时，返回 `BLOCKED`。
- [ ] 验证变更后的 API、插件、序列化器、构建输出和通用测试可能未覆盖的运行时路径。
- [ ] 当更新后的依赖可能显著影响指标时，对比包大小、启动、构件或性能指标。
- [ ] 重新运行安全审计，并区分已修复、仍存在、新引入、不可达和无修复方案的安全公告。
- [ ] 仅当验证通过且预期行为仍受支持时，才保留该批次。
- [ ] 对于失败的批次，区分基线或环境故障与升级缺陷；修复有界的迁移错误并重新检查，或在不触碰用户工作成果的情况下完整回滚整个批次。记录阻塞原因，并仅继续处理相互独立且安全的批次。
- [ ] 在应用下一个批次之前，将保留的依赖状态确立为基线。
- [ ] 将每个计划中的批次分类为：已应用并完成验证时为 `KEPT`；已应用但验证失败后完整回滚时为 `REVERTED`；因所需决策、兼容性策略或独立前置条件尚未解决而有意未应用时为 `SKIPPED`。

### 5. 完成并报告

- [ ] 确认所有必需的仓库验证都覆盖合并后的保留状态。复用仍然有效的结果；运行缺失的检查，并重新运行因后续批次或未解决故障而失效的检查。
- [ ] 确认清单文件、锁定文件、运行时固定版本、CI、容器、文档和生成的元数据在最终版本上保持一致。
- [ ] 仅移除由本次运行负责的记录项：确认绝对路径仍位于批准的临时根目录内，停止准确记录的进程 ID，保留已存在的脏工作区或预先存在的工作树，并有意保留需要报告的证据构件。
- [ ] 列出有意跳过的软件包，并给出确切的约束、风险、安全公告或迁移原因。
- [ ] 将批次记录与最终版本、迁移编辑、安全公告、锁定文件变更以及剩余风险进行核对。
- [ ] 仅当请求的更新范围已满足并完成验证时使用 `UPDATED`；当保留了安全子集但请求的工作或可选覆盖范围仍未完成时使用 `PARTIAL`；当没有保留任何批次且基线已恢复时使用 `NO_CHANGE`；当无法安全推进或无法完成必需验证时使用 `BLOCKED`。

## 自检

- [ ] **返回前进行核对。** 检查项目级证据、需求覆盖情况、矛盾、范围、结论和适用的清理措施。更正报告或已获授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。简短结果每个字段可使用一行；省略空表格，且不要复制已链接的工件：

1. **结果：** 特定于 Skill 的结论和有依据的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 下述特定于 Skill 的字段；区分事实、推断和未经验证的声明。链接工件；在适用时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理措施/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项目的原因、对结果的影响和确切的下一步操作；剩余风险和所需决策。

**特定于 Skill 的证据：** 管理器、工作区、运行时、请求的更新策略，以及既有失败/警告。按批次列出：包、版本、迁移、`KEPT / REVERTED / SKIPPED` 和验证。包括已修复/剩余/新增的警告、对等依赖/运行时/注册表约束、锁文件变更、跳过包的原因、组合状态检查、运行所拥有的清单/锁文件/差异，以及回滚/清理证据。
