# 依赖升级

**目标：** 以小批次、可归因的方式升级依赖项。保留清单文件、锁定文件、运行时支持和产品行为；没有兼容性、安全性或维护方面的证据时，不要仅因版本更新就认为其具有价值。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框都标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，或在证明其条件触发器不存在时解决为 `CLEARED`，否则标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。  
返回前，解决所有 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为完成，针对每个 `UNPROVEN` 项应用此技能的结论、决策和批准规则，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 包管理器检测 | 清单文件、锁定文件、工作区文件、运行时文件和仓库说明 | 在选择命令或更新范围之前始终执行 | 构建和 CI 配置 |
| 过时和存在漏洞的软件包 | 原生包管理器的过时检查和审计命令 | 包管理器和注册表可用时 | 官方注册表、供应商公告和锁定文件检查 |
| 破坏性变更和支持情况 | 官方发行说明、迁移指南、变更日志、公告和运行时支持表 | 每次有影响的次要版本、主要版本、替代方案或安全更新 | 主要来源的仓库发行信息；否则标记为 `UNVERIFIED` |
| 使用情况和影响范围 | 语言服务器或宿主原生代码智能工具 | 更新后的 API、类型、插件、构建工具或运行时可能影响使用者时 | 针对性的导入、符号、配置和脚本搜索 |
| 安全的版本变更 | 原生包管理器命令 | 更新清单文件和生成的锁定状态时 | 不要手动编辑锁定文件或模拟包解析 |
| 验证 | 仓库定义的安装、还原、构建、代码检查、类型检查、测试、迁移和冒烟测试命令 | 变更前以及每个批次之后 | 检查 CI 和脚本，并明确标记为未验证 |
| 差异和回滚 | Git 状态、差异，以及隔离提交或工作树 | 保护用户变更，并仅回滚失败的批次时 | 如果无法安全隔离批次，则停止 |

绝不要发布软件包、轮换凭据、部署，或弱化审计和验证门禁。不要在没有使用环境通常安全防护措施的情况下，运行来自不受信任软件包源的生命周期脚本。

## 证据规则

- 清单文件和锁定文件定义了已安装的内容；注册表中的 “latest” 不会覆盖项目的运行时或兼容性约束。
- 漏洞发现需要包含受影响的版本、公告、可达性或暴露背景，以及可信的修复方案。
- 破坏性变更声明需要有与确切版本迁移相匹配的发行或迁移证据。
- 仅当锁定文件变更由选定的原生包管理器根据预期的仓库版本生成时，才保留这些生成的锁定文件变更。
- 升级成功需要仓库验证，而不仅仅是安装或还原成功。

## 检查清单

### 1. 发现范围并保护工作区

- [ ] 检测所有包管理器、工作区、清单文件、锁定文件、集中式版本文件、注册表、运行时固定版本、工具清单以及生成的依赖文件。
- [ ] 将每项交付物分类为应用程序、库、插件、CLI、容器或构建工具，以便正确解读版本范围、锁定文件、对等依赖约束和受支持运行时承诺。
- [ ] 阅读仓库说明，并确定受支持的包管理器版本、更新命令、锁定文件策略以及 CI 预期。
- [ ] 检查 Git 状态并隔离此次工作，确保现有用户更改不会被覆盖或误认为是升级输出。
- [ ] 建立由本次运行负责的资源清单，记录每个已创建的绝对路径、工作树、进程 ID、缓存、报告和临时产物；绝不要将预先存在的资源登记为清理目标。
- [ ] 明确请求的范围：仅安全修复、常规补丁或次版本维护、指定包、主版本升级、运行时迁移，或完整刷新。
- [ ] 在编辑前记录安装或还原、构建、代码检查、类型检查、测试、冒烟测试和安全审计的基线。
- [ ] 记录预先存在的失败、通告、弃用项、对等依赖冲突以及不受支持的运行时组合。

### 2. 研究并规划批次

- [ ] 使用原生的过期检查和审计命令，在不更改文件的情况下盘点直接依赖和相关传递依赖的更新。
- [ ] 将移除项、安全修复、常规更新、主版本变更、构建工具变更以及运行时或生态系统迁移分开处理。
- [ ] 查阅官方发布说明和迁移指南，了解 API 变更、配置变更、默认值、对等依赖约束、运行时支持以及已移除的行为。
- [ ] 检查环境标记、额外依赖、可选/开发组、对等依赖、目标框架以及平台特定的包；当项目承诺支持更广泛的矩阵时，仅在当前机器上能够解析的依赖图并不足够。
- [ ] 检查官方通告，了解受影响的范围、利用条件、修复版本、变通方案，以及该依赖是否在本项目中可达。
- [ ] 针对每个具有重要影响的依赖，搜索实际的导入、符号、插件、脚本、配置、生成代码和运行时加载情况。
- [ ] 将未使用、重复、已停止维护、已被替代或在平台上冗余的依赖分别识别为待移除项；移除时必须有运行时和动态加载方面的证据，并且当移除超出请求的升级范围时，必须获得用户明确批准。
- [ ] 按前置条件安排批次：包管理器或运行时、构建工具、基础库、框架、集成，最后是叶节点包。
- [ ] 将常规批次控制在足够小的范围内，以便定位失败原因；只有当兼容性矩阵要求时，才将框架系列、分析器、生成的客户端或具有严格约束的对等依赖一起分批处理。
- [ ] 当互斥的版本策略、运行时支持、许可、注册表策略或迁移范围会改变产品意图时，暂停并请用户作出决定。

### 3. 安全地应用每个批次

- [ ] 使用原生包管理器，按照仓库预期的版本和标志更新清单文件与锁定文件。
- [ ] 除非包管理器无法安全保留锁定图，否则在请求范围较窄时避免广泛重新解析；如无法避免变更，应说明不可避免的变动。
- [ ] 在安全风险值得关注时，检查安装脚本、注册表来源、校验和、包来源，以及意外新增的传递依赖包。
- [ ] 根据文档记录的破坏性变更，更新所需的导入、API、类型、配置、构建脚本、插件、生成的客户端和应用程序代码。
- [ ] 仅当既有行为、前置条件、配置或命令发生变化时，才更新用户或运维人员文档。
- [ ] 立即检查差异，关注无关的格式变更、被删除的约束、注册表漂移、换行符变动、生成的构件以及意外降级。
- [ ] 检查解析后的依赖图，关注新出现的重复主版本、不满足或被静默忽略的 peer、发生变化的可选功能，以及会改变运行时行为的传递依赖替换。
- [ ] 不得抑制警告、禁用审计、跳过必需检查、强制固定不兼容的 peer，或在没有证据的情况下添加兼容性变通方案。

### 4. 验证并保留或还原

- [ ] 从足够干净的状态执行安装或还原，以证明锁定文件具有可复现性。
- [ ] 在每个批次之后，运行相关的构建、lint、类型、单元、集成、冒烟、打包、迁移和应用启动检查。
- [ ] 将受影响的运行时、目标框架、操作系统、架构和功能组合分类为必需或可选；只有为每个必需单元格都具备本地或可信 CI 证据时，才保留批次；当必需覆盖没有可信回退方案时，返回 `BLOCKED`。
- [ ] 执行变更涉及的 API、插件、序列化器、构建输出和运行时路径，因为通用测试可能无法覆盖这些内容。
- [ ] 当更新的依赖可能对包体积、启动、构件或性能产生实质影响时，比较相应指标。
- [ ] 重新运行安全审计，并区分已修复、仍存在、新引入、不可达和没有修复方案的安全公告。
- [ ] 仅当验证通过且预期行为仍受支持时，才保留该批次。
- [ ] 还原整个验证失败的批次，不得触碰用户工作；记录造成阻塞的包或迁移，并仅继续处理彼此独立且安全的批次。
- [ ] 在应用下一个批次之前，将保留的依赖状态确立为基线。
- [ ] 将每个计划中的批次分类：已应用并通过验证时标记为 `KEPT`；已应用但验证失败后完全回滚时标记为 `REVERTED`；因必需决策、兼容性策略或独立前置条件尚未解决而有意未应用时标记为 `SKIPPED`。

### 5. 完成并报告

- [ ] 在合并后的保留状态上运行完整的必需仓库验证。
- [ ] 确认清单文件、锁定文件、运行时固定版本、CI、容器、文档和生成的元数据对最终版本保持一致。
- [ ] 仅移除本次运行所拥有的账本条目：验证绝对路径仍位于获批准的临时根目录内，停止准确记录的进程 ID，保留有未提交变更或预先存在的工作树，并有意保留已报告的证据构件。
- [ ] 列出有意跳过的包，并给出确切的约束、风险、安全公告或迁移原因。
- [ ] 报告直接依赖和重要传递依赖的变更、移除项、代码迁移、安全公告、验证结果、锁定文件变动以及残余维护风险。
- [ ] 当每个请求保留的批次都通过必需验证时，使用 `UPDATED`；当至少保留一个独立批次，而另一个批次被还原、跳过或仍存在可选覆盖范围时，使用 `PARTIAL`；当没有保留任何批次且基线已恢复时，使用 `NO_CHANGE`；当没有安全批次可以继续，或无法进行必需验证时，使用 `BLOCKED`。

## 输出契约

```markdown
# Dependency Upgrade

**Verdict:** UPDATED | PARTIAL | NO_CHANGE | BLOCKED

## Scope and baseline
- Package managers, workspaces, and runtime constraints
- Requested update policy
- Pre-existing verification and advisories

## Batches
| Batch | Packages | Version changes | Decision | Verification |
|---|---|---|---|---|
| ... | ... | ... | KEPT / REVERTED / SKIPPED | ... |

## Security and compatibility
- Fixed, remaining, and introduced advisories
- Breaking changes and code migrations
- Runtime, peer, and registry constraints

## Final verification and residual risks
Commands, results, skipped packages, limitations, and follow-up decisions.

## Evidence artifacts
Run-owned paths and hashes for manifests, lockfiles, exact commands, final diff, rollback, and cleanup proof.
```
