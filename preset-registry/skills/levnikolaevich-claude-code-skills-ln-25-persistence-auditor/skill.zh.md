# 持久化审计员

**目标：** 对持久化及数据密集型运行时路径执行只读审计。将静态候选项与实际查询、事务、资源或一致性机制关联起来，在没有证据的情况下，不得声称存在性能影响。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。依次完成每一项，并且仅当相应操作及所需证据均已完成时，才将其标记为已完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，对每个未完成项应用此技能的判定、决策和批准规则，并在回复开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的后续操作**；列出每个未完成项。

## 工具路由

| 需求 | 首选工具 | 适用场景 | 后备方案 |
|---|---|---|---|
| 数据层映射 | 对清单、模型、映射、存储库、迁移、查询、缓存、队列和连接池配置使用原生文件搜索 | 确定存储、框架、所有权和范围 | 从已知请求、作业或命令入口点开始追踪 |
| 调用路径和资源所有权 | 语言服务器或宿主原生代码智能工具 | 跟踪服务调用、事务边界、异步流程、会话作用域和清理过程 | 有针对性的搜索，并直接检查定义和调用方 |
| 查询行为 | 现有查询日志、追踪、ORM 诊断和应用程序指标 | 确定频率、重复情况、耗时、行数和缓存行为 | 静态分析循环内查询和数据获取形态，并明确说明局限性 |
| 查询计划 | 在获准的非生产目标上使用数据库原生解释工具 | 存在安全的只读查询以及具有代表性的模式和数据 | 静态检查索引、谓词、连接、统计信息假设和生成的 SQL |
| 运行时性能 | 现有分析器、基准测试或存储库诊断命令 | 需要测量分配、阻塞、循环放大或 I/O 成本 | 完成静态成本路径分析，并标记为未测量 |
| 正确性验证 | 存储库定义的测试、集成环境和迁移检查 | 安全复现事务、重试、一致性或生命周期行为 | 静态故障路径追踪和所需验证计划 |
| 外部语义 | 与已安装版本匹配的数据库、驱动程序、框架和运行时官方文档 | 隔离、连接池、取消、缓存、触发器或异步语义会影响某项发现 | 基于主要来源的 Web 调研；否则标记为 `UNVERIFIED` |

切勿连接生产环境或运行会产生更改的诊断。`EXPLAIN ANALYZE` 会执行语句：仅可对获准的一次性或非生产目标中已确认的只读查询使用它。审计期间不得创建索引、执行迁移、运行 vacuum、重写数据或更改连接池设置。

## 证据规则

- 查询次数、耗时、行数、计划、锁或性能分析证据，比静态性能疑点更有说服力。
- 当完整路径可见时，静态证据可以证明正确性和生命周期缺陷，但性能影响必须标记为未测量。
- 在将 ORM 约定、有界的管理路径、仅启动时执行的工作以及有意保持较小的数据集判定为问题之前，必须先考虑其上下文。
- 事务建议必须与实际使用的数据库、隔离级别、驱动程序、框架和重试模型相匹配。
- 建议必须保留数据完整性和失败语义，而不能只考虑降低延迟。

## 检查清单

### 1. 确立数据与运行时上下文

- [ ] 检测范围内的数据库、ORM、驱动程序、缓存、队列、模式、迁移、连接池、依赖注入作用域和运行时入口点。
- [ ] 根据仓库中的证据，确定已安装的版本、数据库能力、部署拓扑、一致性要求和预期工作负载。
- [ ] 识别关键数据路径、高流量路径、流式处理路径、计划任务，以及跨外部调用持有事务或资源的操作。
- [ ] 在运行诊断或解读当前工作之前，阅读仓库说明并检查 Git 状态。
- [ ] 确定可用的查询日志、指标、跟踪、性能分析数据、代表性数据、测试环境和安全的诊断权限。
- [ ] 确保审计为只读，并记录执行的每项查询、命令、目标以及创建的构件。

### 2. 审计查询与缓存效率

- [ ] 跟踪具有代表性的路径，从入口点经过业务逻辑，直至生成查询和物化结果。
- [ ] 查找 N+1 行为、重复的相同数据获取、循环内查询模式、按顺序执行的独立读取，以及多余的存在性查询或计数查询。
- [ ] 检查过度获取、宽泛的实体加载、无界读取、过早物化、缺少分页，以及由用户控制的结果规模放大。
- [ ] 检查是否缺少批量操作、是否逐行写入、是否存在可避免的往返请求和零散提交，以及是否有采用基于集合的处理方式的机会。
- [ ] 仅在结合模式和工作负载上下文的情况下，检查谓词、连接、排序和分组操作、索引匹配情况、查询计划假设以及统计信息。
- [ ] 检查缓存归属、键设计、作用域、失效机制、缓存击穿控制、负缓存、陈旧容忍度，以及与数据库保证之间的重复。
- [ ] 在建议修复方案之前，区分延迟是由查询结构、连接等待、锁、网络、序列化、应用程序处理还是下游服务所导致。
- [ ] 测量预期影响，或对其进行明确标注；不要将候选索引或缓存方案描述为已经证实的优化。

### 3. 审计事务与一致性

- [ ] 识别每个事务由谁开始、提交、回滚、重试和释放，并确认其所有权是否与业务操作相匹配。
- [ ] 检查相关写入之间的原子性、过早提交、缺少回滚、异常被吞掉、嵌套事务行为以及部分成功状态。
- [ ] 查找长时间持有的事务、事务内的网络或文件调用、持锁期间的用户交互，以及跨越不必要计算过程的事务。
- [ ] 检查隔离级别假设、更新丢失、写偏差、重复处理、乐观锁或悲观锁，以及重试安全性。
- [ ] 在适用情况下，验证幂等键、唯一约束、去重、发件箱或收件箱行为，以及至少一次投递路径。
- [ ] 检查触发器、通知、事件和订阅者的命名、提交时可见性、载荷兼容性、顺序、重复投递和孤立消费者；如果会破坏业务原子性，不要仅仅为了暴露进度而添加中间提交。
- [ ] 检查迁移和回填的事务行为、锁持有时长、混合版本兼容性、可恢复性以及故障恢复。
- [ ] 当行为与版本相关时，对照已安装数据库、驱动程序和框架的官方语义验证建议。

### 4. 审查运行时与资源生命周期

- [ ] 检查异步路径中的阻塞式数据库、文件系统或网络 I/O，以及可能导致工作线程或事件循环饥饿的同步等待。
- [ ] 检查数据密集型循环中重复发生的分配、复制、序列化、字符串构建、转换和集合扩容。
- [ ] 跟踪会话、连接、游标、读取器、流、锁、订阅和临时文件在成功、错误、超时、取消及流式处理完成等情况下的生命周期。
- [ ] 考虑消费者放弃和部分枚举：生成器、异步迭代器、流式响应和客户端断开连接时，即使永远无法正常完成，也必须释放资源。
- [ ] 检查依赖注入作用域与资源生命周期是否匹配，尤其是单例对作用域状态的访问，以及后台或流式任务持有请求资源的情况。
- [ ] 对于后台、流式或其他生命周期较长的任务，验证资源所有权是否有界，并确保在需要时才获取资源，而不是保留生命周期较短的会话或连接；传入工厂或池是一种有效设计，但并非通用要求。
- [ ] 检查池大小、超时、获取、验证、回收、泄漏迹象，以及跨副本、进程、工作线程和故障转移容量的连接总预算，而不仅仅是单个进程的设置。
- [ ] 检查取消传播、命令超时、重试风暴、熔断行为，以及重试尝试之间和任务被放弃后的清理。
- [ ] 检查 ORM 过期、延迟加载、分离实体和隐式自动刷新，确保不会在预期的会话或事务生命周期之外执行查询或写入。
- [ ] 在可获得运行时测量数据时，先区分热点路径与低频或有界代码，再评定性能严重性。

### 5. 验证发现并报告

- [ ] 对高严重性正确性缺陷，使用安全测试或完整故障跟踪进行复现；对性能缺陷，则尽可能提供查询、执行计划、锁或性能分析证据。
- [ ] 在确认发现之前，过滤掉由框架管理的生命周期、有界维护任务、固件、为保留历史而存在的迁移，以及有文档说明的一致性权衡。
- [ ] 对源于同一个根查询、事务边界、作用域不匹配或池配置的症状进行去重。
- [ ] 对每个候选问题应用实质性和可接受替代方案门槛。要求在有证据支持的工作负载和部署规模下，存在具体的完整性、安全性、可用性、延迟、可扩展性、资源或重复性维护影响。拒绝吹毛求疵、查询风格偏好、理论上的纯粹性、泛化的最佳实践、假设性负载，以及不同但合理的一致性或性能权衡；当多种设计都可行时，应要求提供数据或运行时结果，而不是指定某一种偏好的机制。
- [ ] 在每项发现所要求的解决方案中加入直接相关的 Markdown 实践链接：优先使用最新的数据库、驱动程序、框架或运行时官方文档或规范；只有当官方来源无法解决相关权衡时，才使用可信的一手工程资料。打开并验证来源；来源必须支持所建议的机制，而不能仅与缺陷类别相关。拒绝搜索结果链接、泛化的最佳实践文章和装饰性引用。
- [ ] 根据数据损坏、安全性、中断风险、可扩展性、延迟、资源耗尽和复发性，将发现分类为 `P0`-`P3`。
- [ ] 包含调用路径、查询或资源、证据、故障或成本机制、影响、置信度、当前权衡不可接受的原因，以及允许采用等效解决方案的最小安全补救措施。
- [ ] 当关键数据路径、数据库语义或所需的非生产环境在缺乏可信回退方案的情况下无法验证时，使用 `BLOCKED`；对于有证据支持但尚未解决的损坏、原子性、中断、资源耗尽风险、必要门禁失败或其他 `P0/P1` 问题，使用 `FAIL`；仅对有证据支持的非阻塞风险或实质性的未测量不确定性使用 `CONCERNS`；只有当关键路径可信且不存在实质性发现时，才使用 `PASS`。
- [ ] 返回结论，并分别说明实测范围和静态分析范围、补救顺序、限制以及残余的持久化风险。

|---|---|---|---|
