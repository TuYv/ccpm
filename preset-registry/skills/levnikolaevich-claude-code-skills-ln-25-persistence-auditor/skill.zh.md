# 持久化审计员

**目标：** 对持久化和数据密集型运行时路径执行只读审计。将静态候选项与真实的查询、事务、资源或一致性机制关联起来，并避免在没有证据的情况下声称存在性能影响。

**执行契约：** 有序复选框即为完成定义。内部将每一项跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个部分后重新核对各项。在返回前解决所有 `PENDING` 项，并仅统计 `PROVEN` 和 `CLEARED`；对每个缺口应用该技能的判定和批准规则。
保持用户意图、范围和现有授权不变。继续执行已获授权的工作；只有在存在有重大影响且尚未解决的选择，或需要外部批准时才询问。根据实际风险调整深度，不得静默跳过检查。保持依赖关系和安全顺序；除此之外，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 数据层映射 | 对清单、模型、映射、存储库、迁移、查询、缓存、队列和连接池配置进行原生文件搜索 | 建立存储、框架、所有权和范围时 | 从已知的请求、任务或命令入口点开始跟踪 |
| 调用路径和资源所有权 | 语言服务器或宿主原生代码智能工具 | 跟踪服务调用、事务边界、异步流程、会话作用域和清理逻辑时 | 定向搜索，并直接检查定义和调用方 |
| 查询行为 | 现有查询日志、跟踪记录、ORM 诊断信息和应用指标 | 确定频率、重复情况、耗时、行数和缓存行为时 | 静态分析循环中的查询和获取形态，并明确说明其局限 |
| 查询计划 | 在获准的非生产目标上使用数据库原生 explain 工具 | 存在安全的只读查询以及具有代表性的架构和数据时 | 静态检查索引、谓词、连接、统计信息假设和生成的 SQL |
| 运行时性能 | 现有性能分析器、基准测试或存储库诊断命令 | 需要测量分配、阻塞、循环放大或 I/O 成本时 | 完成静态成本路径分析，并标记为未测量 |
| 正确性验证 | 存储库定义的测试、集成环境和迁移检查 | 安全地复现事务、重试、一致性或生命周期行为时 | 静态失败追踪和必要的验证计划 |
| 外部语义 | 与已安装版本匹配的官方数据库、驱动程序、框架和运行时文档 | 隔离、连接池、取消、缓存、触发器或异步语义会影响某项发现时 | 基于主要来源进行 Web 研究；否则标记为 `UNVERIFIED` |

绝不要连接生产环境或运行会产生变更的诊断。`EXPLAIN ANALYZE` 会执行该语句：仅对已确认的只读查询，并且只在获准的一次性或非生产目标上使用。审计期间不得创建索引、执行迁移、执行 vacuum、重写数据或更改连接池设置。

## 证据规则

- 查询次数、持续时间、行数、执行计划、锁或性能分析证据比静态性能怀疑更有说服力。
- 静态证据可以在完整路径可见时证明正确性和生命周期缺陷，但性能影响必须标记为未经测量。
- ORM 约定、有界的管理路径、仅在启动时执行的工作，以及有意控制规模的数据集，在成为问题发现之前都需要结合上下文判断。
- 事务建议必须与实际使用的数据库、隔离级别、驱动程序、框架和重试模型相匹配。
- 建议必须保持数据完整性和失败语义，而不能只降低延迟。

## 检查清单

### 1. 明确数据和运行时上下文

- [ ] 检测范围内的数据库、ORM、驱动程序、缓存、队列、架构、迁移、连接池、依赖注入作用域和运行时入口点。
- [ ] 根据仓库证据确定已安装的版本、数据库能力、部署拓扑、一致性要求和预期工作负载。
- [ ] 识别关键数据路径、高流量路径、流式处理路径、计划任务，以及在外部调用期间持有事务或资源的操作。
- [ ] 在运行诊断或解读当前工作之前，阅读仓库说明并检查 Git 状态。
- [ ] 确定可用的查询日志、指标、追踪、性能分析、代表性数据、测试环境和安全的诊断权限。
- [ ] 保持审计为只读；记录执行过的查询形态、命令、目标和创建的工件，并对敏感参数、凭据和行数据进行脱敏。

### 2. 审计查询和缓存效率

- [ ] 从入口点追踪代表性路径，直到生成查询和实体化过程，包括在决定哪些数据可以被读取或修改时所涉及的租户/所有者谓词和行级控制。
- [ ] 查找 N+1 行为、重复获取、循环内查询放大、不必要的独立读取串行执行，以及冗余的存在性/计数查询；提出批处理或并行化方案时，保留快照、排序、连接预算和事务约束。
- [ ] 检查过度获取、宽范围实体加载、无界读取、过早实体化、缺失分页，以及由用户控制的结果放大。
- [ ] 检查缺失的批量操作、逐行写入、可避免的往返、碎片化提交，以及采用基于集合的处理的机会。
- [ ] 仅结合架构和工作负载上下文，检查谓词、连接、排序和分组操作、索引匹配、查询计划假设及统计信息。
- [ ] 检查缓存的归属、键设计、作用域、失效、缓存击穿控制、负缓存、陈旧容忍度，以及与数据库保证的重复。
- [ ] 在提出修复建议之前，区分由查询形态、连接等待、锁、网络、序列化、应用程序工作或下游服务造成的延迟。
- [ ] 测量或明确标记预期影响；不要将候选索引或缓存描述为已证明的优化。

### 3. 审计事务和一致性

- [ ] 确定每个事务由谁开始、提交、回滚、重试和释放，并检查其所有权是否与业务操作匹配。
- [ ] 检查相关写入之间的原子性、提前提交、缺失回滚、被吞掉的异常、嵌套事务行为以及部分成功状态。
- [ ] 查找持有时间过长的事务、事务内部的网络或文件调用、锁期间的用户交互，以及跨越不必要计算的事务。
- [ ] 检查隔离级别假设、丢失更新、写偏斜、重复处理、乐观锁或悲观锁，以及重试安全性。
- [ ] 在适用的情况下，验证幂等键、唯一约束、去重机制、outbox 或 inbox 行为，以及至少一次投递路径。
- [ ] 检查触发器、通知、事件和订阅者的命名、提交时可见性、负载兼容性、顺序、重复投递以及孤立消费者；如果中间提交会破坏业务原子性，不要仅为暴露进度而添加中间提交。
- [ ] 检查迁移和回填的事务行为、锁持有时长、混合版本兼容性、可恢复执行能力以及故障恢复。
- [ ] 当行为取决于版本时，根据已安装数据库、驱动程序和框架的官方语义验证建议。

### 4. 审计运行时和资源生命周期

- [ ] 检查异步路径中的阻塞式数据库、文件系统或网络 I/O，以及可能导致工作线程或事件循环饥饿的同步等待。
- [ ] 检查数据密集型循环中的重复分配、复制、序列化、字符串构建、转换和集合增长。
- [ ] 跟踪会话、连接、游标、读取器、流、锁、订阅和临时文件在成功、错误、超时、取消和流式处理完成等情况下的生命周期。
- [ ] 纳入消费者放弃和部分枚举：生成器、异步迭代器、流式响应以及客户端断开连接时，即使未正常完成，也必须释放资源。
- [ ] 检查依赖注入作用域与资源生命周期是否匹配，尤其要关注单例访问有作用域的状态，以及后台或流式工作持有请求资源的情况。
- [ ] 对于后台、流式或其他生命周期较长的工作，验证资源所有权是否有界，并确保在需要时获取资源，而不是保留生命周期更短的会话或连接；传入工厂或连接池是一种有效设计，但不是普遍要求。
- [ ] 检查池大小、超时、获取、验证、回收、泄漏证据，以及跨副本、进程、工作线程和故障转移容量的总连接预算，而不只是单个进程的设置。
- [ ] 检查取消传播、命令超时、重试风暴、熔断器行为，以及每次重试之间和废弃工作之后的清理。
- [ ] 检查 ORM 的过期、延迟加载、脱离状态的实体和隐式自动刷新，确保不会在预期的会话或事务生命周期之外执行查询或写入。
- [ ] 在可用时使用运行时测量，在确定性能严重性之前区分热点路径与低频或有界代码。

### 5. 验证发现并报告

- [ ] 对高严重性正确性缺陷，通过安全测试或完整的失败追踪进行复现；对于性能缺陷，在可能的情况下提供查询、执行计划、锁或性能分析证据。
- [ ] 在确认发现之前，过滤由框架管理的生命周期、范围受限的维护任务、测试夹具、为保留历史而保留的迁移，以及已记录的 一致性权衡。
- [ ] 对共享同一根查询、事务边界、作用域不匹配或连接池配置的症状进行去重。
- [ ] 应用实质性门槛：要求在已有证据所覆盖的规模下，存在具体的完整性、安全性、可用性、延迟、可扩展性、资源或重复维护影响。拒绝仅基于偏好、理论纯粹性、通用实践、假设规模和合理替代方案提出的问题；要求证明结果或约束，而不是偏好的实现方式。
- [ ] 外部修正应基于与版本匹配的官方契约；对于尚未解决的权衡，使用主要工程来源。引用受支持的机制；对于本地缺陷，本地证据即可。
- [ ] 根据数据损坏、安全性、停机风险、可扩展性、延迟、资源耗尽和复发情况，将发现分类为 `P0`-`P3`。
- [ ] 当关键数据路径、数据库语义或所需的非生产环境无法验证，且没有可信的替代验证方案时，使用 `BLOCKED`；对于已有证据但尚未解决的数据损坏、原子性、停机、资源耗尽风险、要求失败的门禁或其他 `P0/P1` 问题，使用 `FAIL`；仅对于已有证据的非阻塞风险或重要但未度量的不确定性使用 `CONCERNS`；只有在关键路径可信且不存在实质性发现时，才使用 `PASS`。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。修正报告或经授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或尚未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较少时，每个字段可以使用一行；省略空表格，不要复制链接的工件：

1. **结果：** Skill 特定的结论和有依据的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill 特定字段；区分事实、推断和未经验证的声明。链接工件；适当时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；剩余风险和所需决策。

**Skill 特定证据：** 存储、版本、工作负载、部署，以及已度量路径与仅通过静态检查的路径；查询/缓存效率、事务、一致性和资源生命周期。发现需要包含优先级、调用路径/查询/资源、证据和置信度、故障或成本机制、工作负载影响、不可接受的权衡，以及最小安全修正和验证。标注未度量的影响和已接受的一致性权衡。
