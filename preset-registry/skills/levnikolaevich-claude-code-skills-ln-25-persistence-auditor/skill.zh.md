# 持久化审计员

**目标：** 对持久化和数据密集型运行时路径执行只读审计。将静态候选项关联到真实的查询、事务、资源或一致性机制，并避免在没有证据的情况下声称存在性能影响。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成标准。将每个复选框标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用触发条件不存在的证据将其解决为 `CLEARED`，否则标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。
返回前，解决所有 `PENDING`，只将 `PROVEN` 和 `CLEARED` 项计为已完成，对每个 `UNPROVEN` 项应用此技能的判定、决策和批准规则，并在开头添加 **检查清单：X/Y 项已完成**<br>**未完成：无 | section/item — 原因；对结果的影响；确切的下一步操作**；列出每一项 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 数据层映射 | 对清单文件、模型、映射、仓储、迁移、查询、缓存、队列和连接池配置执行原生文件搜索 | 建立存储、框架、所有权和范围时 | 从已知的请求、作业或命令入口点进行追踪 |
| 调用路径和资源所有权 | 语言服务器或主机原生代码智能工具 | 跟踪服务调用、事务边界、异步流程、会话范围和清理逻辑时 | 定向搜索，并直接检查定义及调用方 |
| 查询行为 | 现有查询日志、追踪信息、ORM 诊断信息和应用指标 | 确定频率、重复情况、耗时、行数和缓存行为时 | 对查询循环和提取形态进行静态分析，并明确其局限性 |
| 查询计划 | 在获准的非生产目标上使用数据库原生 explain 工具 | 存在安全的只读查询以及具有代表性的架构/数据时 | 静态检查索引、谓词、连接、统计信息假设和生成的 SQL |
| 运行时性能 | 现有分析器、基准测试或仓库诊断命令 | 需要测量分配、阻塞、循环放大或 I/O 成本时 | 完成静态成本路径，并标记为未测量 |
| 正确性验证 | 仓库定义的测试、集成环境和迁移检查 | 安全地复现事务、重试、一致性或生命周期行为时 | 静态失败追踪和所需的验证计划 |
| 外部语义 | 与已安装版本匹配的官方数据库、驱动程序、框架和运行时文档 | 隔离、连接池、取消、缓存、触发器或异步语义会影响发现结果时 | 基于主要来源进行网络研究；否则标记为 `UNVERIFIED` |

绝不要连接到生产环境，或运行会产生变更的诊断。`EXPLAIN ANALYZE` 会执行该语句：仅可对获准的临时环境或非生产目标上的已确认只读查询使用它。审计期间不得创建索引、执行迁移、执行 vacuum、重写数据或更改连接池设置。

## 证据规则

- 查询数量、持续时间、行数、执行计划、锁或性能分析证据，比静态性能怀疑更有说服力。
- 当完整路径可见时，静态证据可以证明正确性和生命周期缺陷，但性能影响必须标记为未经测量。
- ORM 约定、有界的管理路径、仅在启动时执行的工作，以及有意保持较小的数据集，在形成问题发现之前都需要结合上下文判断。
- 事务方面的建议必须与实际使用的数据库、隔离级别、驱动程序、框架和重试模型相匹配。
- 建议必须保留数据完整性和失败语义，而不只是降低延迟。

## 检查清单

### 1. 建立数据和运行时上下文

- [ ] 检测范围内的数据库、ORM、驱动程序、缓存、队列、架构、迁移、连接池、依赖注入作用域和运行时入口点。
- [ ] 根据仓库证据确定已安装的版本、数据库能力、部署拓扑、一致性要求和预期工作负载。
- [ ] 识别关键数据路径、高吞吐路径、流式处理路径、计划任务，以及在外部调用期间持有事务或资源的操作。
- [ ] 在运行诊断或解读当前工作之前，阅读仓库说明并检查 Git 状态。
- [ ] 确认可用的查询日志、指标、追踪、性能分析数据、代表性数据、测试环境和安全的诊断权限。
- [ ] 保持审计为只读，并记录每一条已执行的查询、命令、目标和创建的制品。

### 2. 审计查询和缓存效率

- [ ] 从入口点经过业务逻辑，追踪代表性路径直到生成的查询和实体物化。
- [ ] 查找 N+1 行为、重复的相同读取、循环中的查询模式、顺序执行的独立读取，以及冗余的存在性或计数查询。
- [ ] 检查过度获取、宽泛的实体加载、无界读取、过早物化、缺少分页，以及由用户控制的结果放大。
- [ ] 检查缺少批量操作、逐行写入、可避免的往返、碎片化提交，以及采用基于集合的处理方式的机会。
- [ ] 仅在结合架构和工作负载上下文的情况下，检查谓词、连接、排序和分组操作、索引匹配、查询计划假设及统计信息。
- [ ] 检查缓存的所有权、键设计、作用域、失效、缓存击穿控制、负缓存、陈旧容忍度，以及与数据库保证的重复。
- [ ] 在提出修复建议之前，区分延迟是由查询形状、连接等待、锁、网络、序列化、应用程序工作还是下游服务造成的。
- [ ] 测量预期影响，或明确标记预期影响；不要将候选索引或缓存呈现为已被证明的优化。

### 3. 审计事务和一致性

- [ ] 确定每个事务由谁开始、提交、回滚、重试和释放，以及所有权是否与业务操作相匹配。
- [ ] 检查相关写入之间的原子性、提前提交、缺少回滚、吞掉异常、嵌套事务行为和部分成功状态。
- [ ] 查找长时间持有的事务、事务内的网络或文件调用、锁定期间的用户交互，以及跨越不必要计算的事务。
- [ ] 检查隔离性假设、丢失更新、写偏斜、重复处理、乐观锁或悲观锁，以及重试安全性。
- [ ] 在适用的情况下，验证幂等键、唯一约束、去重、outbox 或 inbox 行为，以及至少一次投递路径。
- [ ] 检查触发器、通知、事件和订阅者的命名、提交时可见性、负载兼容性、顺序、重复投递和孤立消费者；如果这会破坏业务原子性，不要仅为了暴露进度而添加中间提交。
- [ ] 检查迁移和回填的事务行为、锁持续时间、混合版本兼容性、可恢复执行能力和失败恢复。
- [ ] 当行为取决于版本时，根据已安装数据库、驱动程序和框架的官方语义验证建议。

### 4. 审计运行时与资源生命周期

- [ ] 检查异步路径中的阻塞式数据库、文件系统或网络 I/O，以及可能导致工作线程或事件循环饥饿的同步等待。
- [ ] 检查数据密集型循环中的重复分配、复制、序列化、字符串构建、转换和集合增长。
- [ ] 跟踪会话、连接、游标、读取器、流、锁、订阅和临时文件在成功、错误、超时、取消以及流式处理完成时的生命周期。
- [ ] 纳入消费者放弃和部分枚举的情况：生成器、异步迭代器、流式响应和客户端断开连接即使未正常完成，也必须释放资源。
- [ ] 检查依赖注入作用域是否与资源生命周期匹配，尤其要关注单例访问有作用域的状态，以及后台或流式工作持有请求资源的情况。
- [ ] 对于后台、流式或其他生命周期更长的工作，验证资源所有权是否有界，并确认资源是在需要时获取，而不是保留生命周期更短的会话或连接；传入工厂或池是一种有效设计，但并非普遍要求。
- [ ] 检查池大小、超时、获取、验证、回收、泄漏证据，以及跨副本、进程、工作线程和故障转移容量的总连接预算，而不仅是单个进程的设置。
- [ ] 检查取消传播、命令超时、重试风暴、熔断行为，以及重试尝试之间和放弃的工作之后的清理。
- [ ] 检查 ORM 过期、延迟加载、脱离上下文的实体和隐式 autoflush，确保不会在预期的会话或事务生命周期之外执行查询或写入。
- [ ] 在可用时使用运行时度量，在判定性能严重程度之前区分热点路径与低频或有界代码。

### 5. 验证发现并报告

- [ ] 尽可能使用安全测试或完整的故障跟踪来复现高严重性正确性缺陷，并使用查询、执行计划、锁或性能分析证据来复现性能缺陷。
- [ ] 在确认发现之前，排除由框架管理的生命周期、有界维护任务、测试固件、为保留历史而保留的迁移，以及有文档说明的一致性权衡。
- [ ] 对共享同一根查询、事务边界、作用域不匹配或池配置的问题症状去重。
- [ ] 对每个候选项应用实质性和可接受替代方案门槛。必须在有证据支持的工作负载和部署规模下，产生具体的完整性、安全性、可用性、延迟、可扩展性、资源或重复维护影响。拒绝吹毛求疵、查询风格偏好、理论上的纯粹性、泛化的最佳实践、假设性负载，以及另一种合理但不同的一致性或性能权衡；当存在多种可行设计时，要求提供数据或运行时结果，而不是要求采用某一种偏好的机制。
- [ ] 在每个发现的必需修复方案中放置一个直接相关的 Markdown 实践链接：优先使用当前的官方数据库、驱动程序、框架或运行时文档，或使用规范；仅当官方来源无法解决该权衡时，才使用信誉良好的第一方工程材料。打开并验证来源；它必须支持所提议的机制，而不仅仅是缺陷类别。拒绝搜索结果链接、泛化的最佳实践文章和装饰性引用。
- [ ] 根据数据损坏、安全性、中断风险、可扩展性、延迟、资源耗尽和复发情况，将发现分类为 `P0`-`P3`。
- [ ] 包含调用路径、查询或资源、证据、故障或成本机制、影响、置信度、当前折衷方案为何不可接受，以及允许等效方案时的最小安全修复。
- [ ] 当关键数据路径、数据库语义或所需的非生产环境无法在没有可信替代方案的情况下完成验证时，使用 `BLOCKED`；对于已有证据表明但尚未解决的数据损坏、原子性、中断、资源耗尽风险、必需但失败的门禁，或其他 `P0/P1`，使用 `FAIL`；仅对于有证据支持的非阻塞风险或实质性但尚未度量的不确定性使用 `CONCERNS`，并且只有在关键路径可信且不存在实质性发现时才使用 `PASS`。
- [ ] 返回判定结果，并分开列出已度量范围和静态范围、修复顺序、限制条件以及残余的持续性风险。

## 输出契约

```markdown
# Persistence Audit

**Verdict:** PASS | CONCERNS | FAIL | BLOCKED

## Data context and evidence
- Stores, frameworks, versions, and deployment topology
- Critical and measured paths
- Diagnostics, commands, and environments used

## Health summary
| Area | Status | Evidence basis |
|---|---|---|
| Query and cache efficiency | PASS / CONCERNS / FAIL | measured / static |
| Transactions and consistency | PASS / CONCERNS / FAIL | ... |
| Runtime performance | PASS / CONCERNS / FAIL | measured / static |
| Resource lifecycle | PASS / CONCERNS / FAIL | ... |

## Findings
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete persistence defect | Call path, query, transaction, or resource; evidence and confidence; material failure or cost mechanism at evidenced scale; why the current tradeoff is not acceptable | Smallest safe correction and verification plus a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent valid consistency or performance mechanisms |

Use `None` when no candidate survives the evidence, materiality, workload-context, and acceptable-alternative gates.

## Measurement gaps and residual risks
Unmeasured candidates, unavailable environments, and accepted consistency tradeoffs.
```
