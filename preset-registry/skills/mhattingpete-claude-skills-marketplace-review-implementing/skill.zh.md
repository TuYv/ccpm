# 实施审查反馈

根据代码审查反馈，系统化地处理并实施更改。

## 适用场景

- 提供了审查者的评论或反馈
- 粘贴了 PR 审查说明
- 提到要实施审查建议
- 表示“处理这些评论”或“实施反馈”
- 分享审查者要求的更改列表

## 系统化工作流程

### 1. 解析审查者说明

识别各个反馈项：
- 拆分编号列表（1.、2. 等）
- 处理项目符号列表或未编号的反馈
- 提取不同的更改请求
- 开始前澄清有歧义的事项

### 2. 创建待办事项列表

使用 TodoWrite 工具创建可执行的任务：
- 每个反馈项对应一个或多个待办事项
- 将复杂反馈拆分成更小的任务
- 使任务具体且可衡量
- 开始前将第一个任务标记为 `in_progress`

示例：
```
- Add type hints to extract function
- Fix duplicate tag detection logic
- Update docstring in chain.py
- Add unit test for edge case
```

### 3. 系统化实施更改

针对每个待办事项：

**定位相关代码：**
- 使用 Grep 搜索函数/类
- 使用 Glob 按模式查找文件
- 阅读当前实现

**进行更改：**
- 使用 Edit 工具进行修改
- 遵循项目约定（CLAUDE.md）
- 除非要更改行为，否则保留现有功能

**验证更改：**
- 检查语法正确性
- 在适用时运行相关测试
- 确保更改符合审查者的意图

**更新状态：**
- 完成后立即将待办事项标记为 `completed`
- 转到下一个待办事项（同一时间只能有一个 `in_progress`）

### 4. 处理不同类型的反馈

**代码更改：**
- 使用 Edit 工具修改现有代码
- 遵循类型提示约定（PEP 604/585）
- 保持风格一致

**新功能：**
- 如有需要，使用 Write 工具创建新文件
- 添加相应的测试
- 更新文档

**文档：**
- 按照项目风格更新文档字符串
- 根据需要修改 Markdown 文件
- 保持说明简洁

**测试：**
- 将测试编写为函数，而不是类
- 使用描述性名称
- 遵循 pytest 约定

**重构：**
- 保留现有功能
- 改进代码结构
- 运行测试以验证没有回归

### 5. 验证

实施更改后：
- 运行受影响的测试
- 检查代码检查错误：`uv run ruff check`
- 验证更改不会破坏现有功能

### 6. 沟通

让用户及时了解进展：
- 实时更新待办事项列表
- 对有歧义的反馈请求澄清
- 报告阻碍因素或挑战
- 完成时总结更改

## 边界情况

**反馈相互冲突：**
- 向用户寻求指导
- 清楚地说明冲突

**需要进行破坏性更改：**
- 实施前通知用户
- 讨论影响和替代方案

**更改后测试失败：**
- 修复测试后再将待办事项标记为完成
- 确保所有相关测试均通过

**引用的代码不存在：**
- 向用户请求澄清
- 继续操作前确认理解无误

## 重要准则

- **始终使用 TodoWrite** 跟踪进度
- **每完成一项后立即将待办事项标记为已完成**
- **任何时候只能有一个待办事项处于 in_progress 状态**
- **不要批量标记完成**——实时更新状态
- **对于不明确的反馈，请提出问题**
- **如果更改会影响经过测试的代码，请运行测试**
- **所有代码更改都应遵循 CLAUDE.md 约定**
- **如果之后创建提交，请使用约定式提交**
