# 智能体系统的评估方法

智能体会动态决策、不同运行之间具有非确定性，并且通常不存在唯一正确答案，因此应采用不同于传统软件的方式评估智能体系统。构建能够考虑这些特征的评估框架，提供可执行的反馈、捕获回归问题，并验证上下文工程选择是否达到预期效果。

## 何时启用

在以下情况启用此技能：
- 系统性测试智能体性能
- 验证上下文工程选择
- 衡量随时间推移取得的改进
- 在部署前捕获回归问题
- 为智能体流水线构建质量门禁
- 比较不同的智能体配置
- 持续评估生产系统

对于由其他技能负责的相邻工作，请勿启用此技能：
- 设计 LLM 评判器本身、成对比较、评判器校准或偏差缓解：`advanced-evaluation`。
- 设计自主控制面、新颖性门禁、回滚或 PR 审批边界：`harness-engineering`。
- 在衡量某个特定上下文故障模式之前对其进行调试：`context-degradation`。

## 核心概念

评估应侧重结果而非执行路径，因为智能体可能会找到通往目标的其他有效路线。判断智能体是否通过合理的过程实现了正确的结果，而不是判断它是否遵循了特定的步骤序列。

使用多维度评分标准，而不是单一分数，因为一个数字会掩盖特定维度中的关键故障。将事实准确性、完整性、引用准确性、来源质量和工具效率作为独立维度进行记录，然后根据具体用例为它们分配权重。

仅在确定性检查和评分标准稳定后，才使用由模型评判的评估。当工作重点是评判器提示词、成对比较、校准或偏差缓解时，请切换到高级评估。

只要产物具有机器可检查的结构，就应在 LLM 评判之前运行确定性验证。模式有效性、重复键、评分标准计算、清单同步、检索状态和必需的证据路径都应快速失败，避免评估器消耗 token 或返回主观分数。

**性能驱动因素**

在设计评估预算时，应用浏览智能体研究成果：token 使用量、工具调用次数和模型选择可能主导测得的性能方差（claim-evaluation-browsecomp-variance）。

| 因素 | 可解释方差 | 影响 |
|--------|-------------------|-------------|
| Token 使用量 | 主要驱动因素 | 增加探索可以提升性能，直到成本或上下文质量崩溃 |
| 工具调用次数 | 次要驱动因素 | 只有在调用能够检索到有用证据时，增加工具使用才有帮助 |
| 模型选择 | 次要但具有乘数效应 | 更好的模型通常能更高效地使用 token 和工具 |

在设计评估时，根据这些影响采取行动：
- **设置现实的 token 预算**：使用符合生产实际的 token 限制来评估智能体，而不是提供无限资源。
- **比较模型升级与 token 增加的效果**：与预算更大但能力较弱的模型相比，更好的模型可能可以更高效地使用 token。
- **验证多智能体架构**：额外的智能体会增加 token 和工具调用；应将其与单智能体基线进行比较。

## 详细主题

### 评估挑战

**处理非确定性和多条有效路径**

设计能够容忍路径差异的评估，因为智能体可能采用完全不同但都有效的路径来实现目标。一个智能体可能搜索三个来源，而另一个可能搜索十个；两者都可能得出正确答案。避免检查特定步骤。相反，应定义结果标准（正确性、完整性、质量）并据此评分，将执行路径视为参考信息而非评估依据。

**测试依赖上下文的故障**

在不同复杂度级别和交互长度下进行评估，因为智能体故障通常会以微妙的方式依赖上下文。智能体可能在简单查询上表现成功，却在复杂查询上失败；可能搭配一组工具时表现良好，换成另一组工具时却失败；也可能随着长期交互中上下文不断累积而性能下降。应纳入简单、中等、复杂和非常复杂的测试用例，以揭示这些模式。

**分别评估复合质量维度**

将智能体质量拆分为不同维度（事实准确性、完整性、连贯性、工具效率、过程质量），并分别独立评分，因为智能体可能在准确性上得分很高，但在效率上得分较低，反之亦然。然后，根据用例的优先级计算经过调整的加权汇总分数。与通过取平均值而掩盖信号相比，这种方法能够揭示哪些维度需要改进。

### 评估量表设计

**构建多维度评估量表**

定义涵盖关键维度的评估量表，并为从优秀到失败的各个等级提供描述。纳入以下核心维度，并根据不同用例调整权重：

- 事实准确性：陈述与事实依据一致（知识类任务应赋予较高权重）
- 完整性：输出涵盖请求的各个方面（研究类任务应赋予较高权重）
- 引用准确性：引用与所声称的来源一致（对信任敏感的场景应赋予较高权重）
- 来源质量：使用适当的一手来源（需要权威输出的场景应赋予较高权重）
- 工具效率：在合理次数内使用正确的工具（成本敏感型系统应赋予较高权重）

**将评估量表转换为数值分数**

将各维度的评估结果映射为数值分数（0.0 到 1.0），应用各维度的权重，并计算加权总分。根据用例要求设置及格阈值，通常一般用途为 0.7，高风险应用为 0.9。除汇总分数外，还应存储各维度的单独分数，因为这些明细能够推动有针对性的改进。

### 评估方法

**使用 LLM 作为评审以实现规模化**

构建基于 LLM 的评估提示，其中包括：清晰的任务描述、接受测试的智能体输出、可用时提供的事实依据、包含明确等级描述的评估尺度，以及要求给出结构化判断及理由。LLM 评审能够在大型测试集上提供一致且可扩展的评估。应使用与被评估智能体不同的模型系列，以避免自我拔高偏差。

**辅以人工评估**

将边缘案例、异常查询以及随机抽取的生产流量样本交由人工评审，因为人工能够发现自动评估所遗漏的虚构答案、系统故障和细微偏差。跟踪人工评审中出现的模式，以识别系统性问题，并将发现反馈到自动评估标准中。

**对有状态智能体应用最终状态评估**

对于会改变持久化状态（文件、数据库、配置）的智能体，应评估最终状态是否符合预期，而不是评估智能体如何达到该状态。定义预期的最终状态断言，并在每次测试运行后通过程序进行验证。

### 测试集设计

**选择有代表性的样本**

在早期开发阶段，从小规模样本（20-30 个用例）开始，因为此时改动会产生显著影响，并且存在大量容易实现的改进。随着系统逐渐成熟，将规模扩大到 50 个以上的用例，以获得可靠的评估信号。从真实使用模式中抽样，加入已知的边缘用例，并确保覆盖不同的复杂度级别。

**按复杂度分层**

按照复杂度级别组织测试集，防止简单示例抬高评分：
- 简单：单次工具调用、事实查询
- 中等：多次工具调用、比较逻辑
- 复杂：大量工具调用、存在显著歧义
- 非常复杂：长时间交互、深度推理、综合分析

在报告总体评分的同时，报告各分层的评分，以揭示智能体实际存在困难的环节。

### 上下文工程评估

**系统化验证上下文策略**

在同一测试集上使用不同的上下文策略运行智能体，并比较质量评分、令牌使用量和效率指标。这样可以将上下文工程的影响与其他变量隔离开来，并避免根据个别经验做出决策。

**运行退化测试**

通过在不同上下文大小下运行智能体，测试上下文退化如何影响性能。识别上下文开始引发问题时的性能断崖，并确定安全运行限制。将这些限制反馈到上下文管理策略中。

### 持续评估

**构建自动化评估流水线**

将评估集成到开发工作流中，使其在智能体发生变更时自动运行。持续跟踪结果、比较版本，并阻止关键指标出现回退的版本部署。

**监控生产环境质量**

对生产环境中的交互进行抽样并持续评估。当质量下降到警告阈值（通过率 0.85）和严重阈值（通过率 0.70）以下时发出警报。维护展示不同时间窗口趋势分析的仪表板，以检测逐渐发生的质量退化。

## 实用指南

### 构建评估框架

按照以下顺序构建评估框架，因为跳过前面的步骤会导致测量结果无法反映真实质量：

1. 在编写任何评估代码之前，定义与用例相关的质量维度，因为后期选择的维度往往反映的是易于测量的内容，而非真正重要的内容。
2. 创建具有清晰、描述性等级定义的评分标准，使评估者（人类或 LLM）能够给出一致的评分。
3. 基于真实使用模式和边缘用例构建测试集，按复杂度分层，并至少包含 50 个用例，以获得可靠的评估信号。
4. 实现自动化评估流水线，使其在每次重大变更时运行。
5. 在进行变更之前建立基线指标，以便相对于已知基准衡量改进。
6. 对所有重大变更运行评估，并与基线进行比较。
7. 持续跟踪指标以进行趋势分析，因为逐渐发生的质量退化比突然下降更难察觉。
8. 定期使用人工审查补充自动化评估。
9. 将确定性验证失败与质量判断分开，确保无效产物无法凭借有利的 LLM 评分蒙混过关。

### 避免评估陷阱

防范以下会损害评估可靠性的常见问题：

- **对特定路径过拟合**：评估结果而非具体步骤，因为智能体可能找到新颖且有效的路径。
- **忽略边缘情况**：纳入多样化的测试场景，覆盖完整的复杂度范围。
- **痴迷于单一指标**：使用多维度评分标准，因为单一分数会掩盖特定维度的问题。
- **忽视上下文影响**：使用符合实际情况的上下文长度和历史记录进行测试，而不是在无上下文干扰的条件下测试。
- **跳过人工评估**：自动化评估会遗漏一些人类能够可靠发现的细微问题。

## 示例

**示例 1：简单评估**
```python
def evaluate_agent_response(response, expected):
    rubric = load_rubric()
    scores = {}
    for dimension, config in rubric.items():
        scores[dimension] = assess_dimension(response, expected, dimension)
    overall = weighted_average(scores, config["weights"])
    return {"passed": overall >= 0.7, "scores": scores}
```

def evaluate_pr_candidate(candidate):

## 指南

1. 使用多维度评分标准，而非单一指标
2. 评估结果，而非具体执行路径
3. 覆盖从简单到复杂的各个复杂度级别
4. 使用符合实际情况的上下文长度和历史记录进行测试
5. 持续开展评估，而非只在发布前进行
6. 使用人工审核补充 LLM 评估
7. 持续跟踪指标以检测趋势
8. 根据使用场景设置明确的通过/失败阈值

## 常见陷阱

1. **评估过度拟合特定代码路径**：测试能够通过，但代理在输入稍有变化时就会失败。应根据结果和语义编写评估标准，而不是依据表面模式，并定期轮换测试输入。
2. **LLM 评判者的自我增强偏差**：模型对自身输出的评分高于独立评判者。应使用与被评估模型不同的模型家族作为评估评判者。
3. **测试集污染**：评估示例泄漏到训练数据或提示词模板中，导致分数虚高。应对评估集进行版本管理，并将其与提示词或微调使用的任何数据分开。
4. **指标投机**：针对指标而非实际质量进行优化，会产生得分很高但令用户失望的代理。应定期使用人工判断对自动化指标进行交叉验证。
5. **单维度评分**：单一的汇总数值会掩盖特定维度上的严重失败。始终在总体分数之外报告各维度分数；如果任何单一维度低于其最低阈值，则应判定评估失败。
6. **评估集过小**：少于 50 个示例会产生不可靠的信号，并导致不同运行之间存在较大方差。将评估集扩展至至少 50 个用例，并报告置信区间。
7. **未按难度分层**：简单示例会抬高总体分数，掩盖在困难用例上的失败。应按复杂度层级报告分数，并对总体分数进行加权，以防止简单用例占据主导地位。
8. **将评估视为一次性工作**：评估必须持续进行，而不能只作为发布门禁。随着模型更新、工具变化和使用模式演进，代理质量会发生漂移。应在每次变更时运行评估，并按照固定的生产环境周期定期运行评估。

## 集成

此技能负责结果衡量和质量门禁。相邻技能负责专门的评估器设计和控制循环治理：

- `advanced-evaluation`：LLM 评判提示词设计、成对比较、校准和偏差缓解。
- `harness-engineering`：锁定的评估器、可编辑界面、回滚和人工审批边界。
- `context-degradation`：检测和衡量退化模式。
- `context-optimization`：衡量优化对 token、成本、延迟和质量的影响。
- `multi-agent-patterns`：评估协调质量和并行化权衡。
- `tool-design`：评估工具选择和恢复效果。
- `memory-systems`：评估记忆检索和保留质量。
