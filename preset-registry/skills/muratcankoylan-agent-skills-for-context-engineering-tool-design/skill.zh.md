# 面向智能体的工具设计

将每个工具设计为确定性系统与非确定性智能体之间的契约。与面向人类的 API 不同，面向智能体的工具必须仅通过描述就能让契约毫无歧义：智能体根据描述推断意图，并生成必须符合预期格式的调用。任何歧义都可能成为潜在的失败模式，而无论进行多少提示词工程都无法弥补。

此技能的工作单元是单个工具或工具目录。项目形态、流水线架构、任务与模型的适配，以及项目层面的成本决策属于 `project-development`。是否引入子智能体的决策属于 `multi-agent-patterns`。此技能负责连接确定性代码与智能体的接口层。

## 何时激活

当工作单元是工具时，激活此技能：

- 编写新的工具描述、模式或响应格式。
- 调试智能体选错工具或生成格式错误调用的情况。
- 整合存在重叠的工具目录（典型情况是“我们有 17 个工具，但智能体有一半时间会选错”）。
- 设计可操作的错误消息，使智能体能够自行纠正。
- 在整个目录中以一致的方式命名工具和参数（MCP 命名空间、动词-名词命名法）。
- 在添加第三方工具之前，根据整合原则对其进行评估。

不要针对由其他技能负责的相邻工作激活此技能：

- 决定项目是否应该使用 LLM，或流水线应包含哪些阶段：`project-development`。
- 决定是在多个子智能体之间拆分工作，还是让单个智能体使用更多工具：`multi-agent-patterns`。
- 在轨迹层面减少工具输出的 token 权重（观测遮蔽、大规模格式选项选择）：`context-optimization`。

## 核心概念

围绕整合原则设计工具：如果人类工程师无法明确判断在某种情况下应该使用哪个工具，就不能指望智能体做得更好。精简工具集，直到每个工具都只有一个毫无歧义的用途，因为智能体通过比较描述来选择工具，而任何重叠都会引发选择错误。

将每个工具描述都视为塑造智能体行为的提示词工程。描述并非为人类编写的文档——它会被注入智能体的上下文，并直接引导其推理。编写能够回答工具做什么、何时使用以及返回什么的描述，因为这三个问题正是智能体在选择工具时评估的内容。

## 详细主题

### 工具-智能体接口

**工具即契约**
将每个工具设计为一份自包含的契约。人类调用 API 时，会阅读文档、理解约定并提出适当的请求。智能体则必须从单个描述块中推断出完整契约。通过加入格式示例、预期模式和明确约束，使契约毫无歧义。不要遗漏调用者需要了解的任何信息，因为智能体在发起调用前无法提出澄清问题。

**将工具描述视为提示词**
编写工具描述时，要意识到它们会直接加载到智能体上下文中，并共同引导其行为。像“搜索数据库”这样含糊的描述，再配上晦涩的参数名称，会迫使智能体进行猜测——而猜测会导致错误调用。相反，应包含使用场景、参数格式示例以及合理的默认值。描述中的每个词都会帮助或妨碍工具选择的准确性。

**命名空间与组织**
随着工具集合不断扩大，应使用共同前缀为工具划分命名空间，因为层次化分组有助于智能体进行选择。当智能体需要执行数据库操作时，它会路由到 `db_*` 命名空间；当它需要进行 Web 交互时，则会路由到 `web_*`。如果没有命名空间，智能体就必须评估扁平列表中的每一个工具，而随着工具数量增加，选择准确性会随之下降。

### 整合原则

**单一综合工具**
应构建单一的综合工具，而不是多个功能重叠的狭窄工具。与其分别实现 `list_users`、`list_events` 和 `create_event`，不如实现 `schedule_event`，通过一次调用查找可用时间并完成安排。综合工具在内部处理完整工作流，从而免除智能体按正确顺序串联调用的负担。

**整合为何有效**
采用整合是因为智能体的上下文容量和注意力有限。工具集合中的每个工具都会在工具选择期间争夺注意力，每条描述都会消耗上下文预算中的 token，而功能重叠则会造成歧义。整合可以消除冗余描述、避免选择歧义，并缩小有效工具集。Vercel 的 d0 案例研究就是一个具体示例：它将专用工具精简为规模更小的基础工具集，并取得了更好的实测结果（claim-tool-design-vercel-d0-reduction）。

**何时不应整合**
当工具具有根本不同的行为、服务于不同场景，或必须能够独立调用时，应保持分离。过度整合会产生另一个问题：单个工具若包含过多参数和模式，智能体就难以正确设置其参数。

### 架构精简

将整合原则推向逻辑上的极致：移除大多数专用工具，转而采用基础的通用能力。生产环境中的证据表明，这种方法的表现可能优于复杂的多工具架构。

**文件系统智能体模式**
通过单一的命令执行工具提供直接的文件系统访问能力，而不是为数据探索、模式查找和查询验证构建自定义工具。智能体使用标准 Unix 实用程序（grep、cat、find、ls）来探索和操作系统。这种方法之所以有效，是因为文件系统是一种经过验证且模型深入理解的抽象；标准工具具有可预测的行为；智能体可以灵活串联基础能力，而不受预定义工作流的限制；此外，文件中的优质文档可以取代摘要工具。

**何时精简优于复杂设计**
在以下情况下选择精简：数据层文档完善且结构一致；模型具备足够的推理能力；专用工具限制了模型而非赋能模型；或者维护脚手架所花费的时间多于改进结果所花费的时间。在以下情况下应避免精简：底层数据杂乱或文档不完善；相关领域需要模型不具备的专业知识；必须通过安全约束限制智能体的操作；或者操作确实能从结构化工作流中受益。

**面向未来的模型构建**
设计能够从模型改进中受益的最小化架构，而不是固化当前局限的复杂架构。应审视每个工具究竟是在赋予新能力，还是在限制模型本可自行完成的推理 -- 随着模型不断改进，作为“护栏”构建的工具往往会变成负担。

有关生产环境中的实证，请参阅[架构精简案例研究](./references/architectural_reduction.md)。

### 工具描述工程

**描述结构**
组织每个工具的描述，使其回答以下四个问题：

1. 该工具的作用是什么？准确说明该工具完成的任务 -- 避免使用“有助于”或“可用于”等含糊表述。
2. 应在何时使用？明确直接触发条件（“用户询问定价”）和间接信号（“需要当前市场费率”）。
3. 它接受哪些输入？说明每个参数的类型、约束、默认值和格式示例。
4. 它返回什么？记录输出格式、结构、成功响应示例和错误条件。

**默认参数选择**
设置能够反映常见使用场景的默认值。默认值无需智能体指定不必要的参数，从而减轻其负担，并防止因遗漏参数而导致错误。所选默认值应能够产生有用的结果，而无需智能体理解每一个选项。

### 响应格式优化

提供不同的响应格式选项（简洁与详细），因为工具响应的大小会显著影响上下文的使用量。简洁格式仅返回必要字段，适合用于确认。详细格式返回完整对象，适合需要完整上下文来支持决策的情况。在工具描述中说明每种格式的适用场景，使智能体学会正确选择。

### 错误消息设计

面向两类受众设计错误消息：调试问题的开发者，以及从故障中恢复的智能体。对于智能体，每条错误消息都必须具备可操作性 -- 必须说明出了什么问题，以及如何纠正。对于可重试的错误，应包含重试指引；对于输入错误，应提供正确的格式示例；对于不完整的请求，应明确指出缺失的字段。仅显示“失败”的错误消息无法提供任何恢复信息。

### 工具定义模式

为所有工具建立一致的模式。工具名称采用动词-名词模式（`get_customer`、`create_order`），所有工具使用一致的参数名称（始终使用 `customer_id`，绝不能有时使用 `id`、有时使用 `identifier`），并采用一致的返回字段名称。一致性能够降低智能体的认知负担，并提升其跨工具泛化能力。

### 工具集合设计

将工具集合限制为用途互不重叠的最小集合，因为描述重叠会导致模型混淆，而且工具更多并不总能带来更好的结果。当确实需要更多工具时，使用命名空间创建逻辑分组。实现选择机制：按领域对工具进行分组、提供基于示例的选择提示，以及使用可路由到专用子工具的伞式工具。

### MCP 工具命名要求

使用 MCP（模型上下文协议）时，始终使用完全限定的工具名称，以避免出现“找不到工具”错误。

格式：`ServerName:tool_name`

```python
# Correct: Fully qualified names
"Use the BigQuery:bigquery_schema tool to retrieve table schemas."
"Use the GitHub:create_issue tool to create issues."

# Incorrect: Unqualified names
"Use the bigquery_schema tool..."  # May fail with multiple servers
```

如果没有服务器前缀，当存在多个 MCP 服务器时，智能体可能无法找到工具。建立命名约定，确保所有工具引用中都包含服务器上下文。

### 使用智能体优化工具

将观察到的工具故障反馈给智能体，让其诊断问题并改进描述。在目标工具目录中复现之前，应将报告的效率提升视为特定于工作负载的结果。

**工具测试智能体模式**：

```python
def optimize_tool_description(tool_spec, failure_examples):
    """
    Use an agent to analyze tool failures and improve descriptions.

    Process:
    1. Agent attempts to use tool across diverse tasks
    2. Collect failure modes and friction points
    3. Agent analyzes failures and proposes improvements
    4. Test improved descriptions against same tasks
    """
    prompt = f"""
    Analyze this tool specification and the observed failures.

    Tool: {tool_spec}

    Failures observed:
    {failure_examples}

    Identify:
    1. Why agents are failing with this tool
    2. What information is missing from the description
    3. What ambiguities cause incorrect usage

    Propose an improved tool description that addresses these issues.
    """

    return get_agent_response(prompt)
```

这会形成一个反馈循环：使用工具的智能体生成故障数据，随后由智能体利用这些数据改进工具描述，从而减少未来的故障。

### 测试工具设计

根据五项标准评估工具设计：无歧义性、完整性、可恢复性、效率和一致性。通过向智能体提供具有代表性的请求，并根据预期行为评估由此产生的工具调用来进行测试。

## 实用指南

### 工具选择框架

设计工具集合时：
1. 识别智能体必须完成的不同工作流
2. 将相关操作组合到综合性工具中
3. 确保每个工具都有明确且无歧义的用途
4. 记录错误情况和恢复路径
5. 使用真实的智能体交互进行测试

### 工具审核清单

在将任何工具添加到智能体之前，请使用此清单进行检查：

1. **名称**：采用动词-名词形式；如果目录包含多个领域，则使用命名空间。
2. **描述**：说明工具的功能、何时使用以及返回什么。
3. **模式**：每个参数都包含类型、约束、默认值和示例值。
4. **返回结构**：成功和错误负载均有文档说明，并且可供机器读取。
5. **恢复**：每个错误都会告知智能体在重试之前需要更改什么。
6. **重叠**：没有其他工具具有相同的触发场景。
7. **整合决策**：除非需要独立调用，否则合并相邻的窄功能工具。
8. **令牌影响**：较大的响应支持简洁模式或文件引用模式。

## 示例

**示例 1：设计良好的工具**
```python
def get_customer(customer_id: str, format: str = "concise"):
    """
    Retrieve customer information by ID.

    Use when:
    - User asks about specific customer details
    - Need customer context for decision-making
    - Verifying customer identity

    Args:
        customer_id: Format "CUST-######" (e.g., "CUST-000001")
        format: "concise" for key fields, "detailed" for complete record

    Returns:
        Customer object with requested fields

    Errors:
        NOT_FOUND: Customer ID not found
        INVALID_FORMAT: ID must match CUST-###### pattern
    """
```

**示例 2：糟糕的工具设计**

此示例展示了几种工具设计中的反模式：

```python
def search(query):
    """Search the database."""
    pass
```

**此设计存在的问题：**

1. **名称含糊**："search" 含义不明确——搜索什么，目的是什么？
2. **缺少参数信息**：哪个数据库？查询应采用什么格式？
3. **没有返回值说明**：此函数返回什么？列表？字符串？如何处理错误？
4. **没有使用场景**：智能体应在何时使用此工具，而不是其他工具？
5. **没有错误处理**：如果数据库不可用，会发生什么？

**失败模式：**
- 智能体可能会在本应使用更具体工具时调用此工具
- 智能体无法确定正确的查询格式
- 智能体无法解读结果
- 智能体无法从失败中恢复

## 指南

1. 编写能够说明工具是什么、何时使用以及返回什么的描述
2. 通过整合来减少歧义
3. 提供响应格式选项以提高 token 效率
4. 设计有助于智能体恢复的错误消息
5. 建立并遵循一致的命名约定
6. 限制工具数量，并使用命名空间进行组织
7. 通过真实的智能体交互测试工具设计
8. 根据观察到的失败模式进行迭代
9. 审视每个工具究竟是在赋能模型还是限制模型
10. 优先选择基础的通用工具，而非专用封装
11. 相比工具的复杂程度，更应重视文档质量
12. 构建能够从模型改进中获益的最小化架构

## 注意事项

1. **描述含糊**：诸如“在数据库中搜索客户信息”之类的描述留下了太多未解答的问题。应明确说明具体的数据库、查询格式和返回结构。
2. **晦涩的参数名称**：名为 `x`、`val` 或 `param1` 的参数会迫使智能体猜测其含义。应使用无需阅读更多文档即可表达用途的描述性名称。
3. **缺少错误恢复指导**：工具失败时若只返回诸如“发生错误”之类的通用消息，就无法提供恢复所需的信息。每个错误响应都必须告知智能体哪里出了问题以及接下来应尝试什么。
4. **工具间命名不一致**：在一个工具中使用 `id`，在另一个工具中使用 `identifier`，又在第三个工具中使用 `customer_id`，会造成混淆。应在整个工具集合中统一参数名称。
5. **MCP 命名空间冲突**：当多个 MCP 工具提供方注册名称相似的工具时（例如，两个服务器都公开 `search`），智能体将无法区分。始终使用完全限定的 `ServerName:tool_name` 格式，并在添加新的提供方时检查是否存在冲突。
6. **工具描述失效**：随着底层 API 的演进，描述会变得不准确——参数会增加、返回格式会变化、错误代码会调整。应像对待代码一样对待描述：对其进行版本控制，在 API 变更时进行审查，并根据当前行为进行测试。
7. **过度整合**：让单个工具处理过多工作流，会导致参数列表过于庞大，使智能体难以选择正确的参数组合。如果一个工具需要超过 8-10 个参数，或服务于本质上不同的使用场景，应将其拆分。
8. **参数膨胀**：过多的可选参数会加重智能体的决策负担。智能体需要评估的每个参数都会增加认知负荷。应提供合理的默认值，将相关选项组合为格式预设，并将很少使用的参数移入 `options` 对象。
9. **缺少错误上下文**：如果错误消息只说“失败”或“输入无效”，却不说明哪个输入有问题、为何失败或有效输入应是什么样子，智能体将无法自行纠正。每个错误响应中都应包含无效值、预期格式和一个具体示例。

## 集成

本技能负责工具接口层。相邻的决策由其他技能负责：

- `project-development`：项目形态、流水线阶段的选择、任务与模型的适配性、项目级成本估算。如果问题是“什么才是正确的流水线架构”，而不是“什么才是正确的工具 API”，请转至该技能。
- `multi-agent-patterns`：判断配备更多工具的单个智能体是否优于两个工具目录较小的智能体。如果问题是“是否应将其拆分为多个子智能体”，请转至该技能。
- `context-optimization`：轨迹级 Token 效率、观察结果掩码，以及在多次工具调用中选择响应格式选项。如果问题是“如何减少累积工具输出所占的 Token 量”，请转至该技能。
- `context-fundamentals`：关于工具定义如何消耗注意力预算的概念性问题。如果问题是“为什么增加工具会降低路由准确率”，请从该技能入手。
- `evaluation`：判断工具集是否从整体上改善了智能体的执行结果。
