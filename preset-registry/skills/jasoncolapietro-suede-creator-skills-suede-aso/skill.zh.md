# Suede ASO 审核

使用 Suede ASO 评分系统分析 App Store 和 Google Play 商品页。获取实时商品页数据，为元数据、视觉内容和评分打分，然后制定按优先级排序的行动计划。

## 审核前

**首先检查产品营销背景信息：**
如果 `.agents/product-marketing.md` 存在（或者在旧版设置中存在 `.claude/product-marketing.md` 或旧文件名 `product-marketing-context.md`），请在提问前阅读它。使用其中的背景信息，并且只询问尚未涵盖或与此任务具体相关的信息。

## 阶段 1 — 识别商店并获取信息

### 从 URL 检测商店类型

```
Apple:  apps.apple.com/{country}/app/{name}/id{digits}
Google: play.google.com/store/apps/details?id={package}
```

如果用户提供的是应用名称而不是 URL，请在网络上搜索：
`site:apps.apple.com "{app name}"` 或 `site:play.google.com "{app name}"`

### 获取商品页

使用 WebFetch 获取商品页。提取每一项可用字段：

**Apple App Store 字段：**

- 应用名称（标题）— 30 个字符限制
- 副标题 — 30 个字符限制
- 描述（长描述）— 不会被搜索索引，但会影响转化
- 推广文本 — 170 个字符，无需发布新版本即可更新
- 分类（主要 + 次要）
- 截图（数量、顺序、文案文字）
- 预览视频（是否存在、时长）
- 评分（平均分 + 数量）
- 最近评价（可见的评价）
- 价格 / 应用内购买项目
- 开发者名称
- 最后更新日期
- 版本历史说明
- 年龄分级
- 大小
- 所列语言 / 本地化版本
- 应用内活动（如有可见）

**Google Play 字段：**

- 应用名称（标题）— 30 个字符限制
- 简短描述 — 80 个字符限制
- 完整描述 — 4,000 个字符限制，**会**被搜索索引
- 分类 + 标签
- 特色图片（是否存在）
- 截图（数量、顺序）
- 预览视频（是否存在）
- 评分（平均分 + 数量）
- 最近评价（可见的评价）
- 价格 / 应用内购买项目
- 开发者名称
- 最后更新日期
- 更新内容文本
- 下载量范围
- 内容分级
- 数据安全部分
- 所列语言

如果 WebFetch 返回的数据不完整（商店采用客户端渲染），请注明缺失项，并基于现有信息开展工作。如果缺失字段至关重要，请要求用户粘贴这些字段。

### 视觉素材评估

WebFetch 无法提取截图图片或文案文字。**请对商品页进行截图**以获取视觉数据：

1. 导航至商品页 URL，并截取完整页面截图
2. 根据截图评估：图标质量、截图数量、文案文字、信息传达质量、预览视频是否存在、特色图片（Google Play）
3. 如果浏览器工具不可用，请要求用户分享商品页截图

**推广文本（Apple）：** 此 170 个字符的字段显示在描述上方，但在抓取的 HTML 中通常无法与描述区分。如果无法确认其是否存在，请注明这一点，并建议用户在 App Store Connect 中检查。

## 阶段 1.5 — 评估品牌成熟度

在评分前，将应用归类为以下三个层级之一。这决定了你如何解读对“教科书式 ASO”的偏离——知名品牌的有意品牌选择，与未知应用错失机会，并不相同。

### 层级定义

| 层级             | 信号                                                                                                                               | 示例                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **主导型**       | 家喻户晓，评分数超过 100 万，在类别中排名前 10，品牌认知度接近全民皆知。用户按品牌名称搜索，而不是使用通用关键词。 | Instagram、Uber、Spotify、WhatsApp、Netflix |
| **成熟型**       | 在所属类别中广为人知，评分数超过 10 万，自然安装量强，品牌具有一定知名度但并非全民皆知。                    | Strava、Notion、Duolingo、Cash App、Calm    |
| **挑战者型**     | 正在建立知名度，评分数少于 10 万，需要通过关键词和 ASO 策略获得发现。大多数应用都属于此类。                            | 你的应用、大多数独立开发者或初创公司的应用           |

分类在此处进行，即在任何评分之前。每个层级获得的各维度调整项位于
`references/scoring-criteria.md` 中的“品牌成熟度调整”部分，Phase 2 会在评分前加载这些内容——不要在此处重复陈述或重新推导这些调整项。

**核心原则：** 在扣分之前，先问自己：“这是一个错误，还是一个掌握了我不知道的数据的团队所做出的有意选择？”如果应用拥有超过 100 万条评分和专门的 ASO 团队，除非其选择明显错误，否则应假设这些选择是基于数据做出的。

## Phase 2 — 为每个维度评分

使用 `references/scoring-criteria.md` 中的标准，为每个维度打 0-10 分。
应用 Phase 1.5 中确定的品牌成熟度层级调整项。

平台规格和基准数据的参考文件：

- `references/apple-specs.md` — Apple 官方字符限制、截图/视频规格、CPP/PPO 规则、触发拒审的因素
- `references/google-play-specs.md` — Google Play 官方限制、截图规格、Android Vitals 阈值、相关政策
- `references/benchmarks.md` — 转化数据、评分影响、视频提升效果、截图表现、CPP/活动基准

### 维度与权重

| #   | 维度             | 权重 | 涵盖内容                                                               |
| --- | ---------------- | ---- | ---------------------------------------------------------------------- |
| 1   | 标题与副标题     | 20%  | 字符使用、关键词存在性、清晰度、品牌与关键词之间的平衡                 |
| 2   | 描述             | 15%  | 前 3 行、关键词密度（Google）、CTA、结构、宣传文本                     |
| 3   | 视觉素材         | 25%  | 截图数量/质量/信息传达、视频、图标、功能图                             |
| 4   | 评分与评论       | 20%  | 平均评分、数量、新近程度、开发者回复                                   |
| 5   | 元数据与新鲜度   | 10%  | 类别选择、更新新近程度、本地化数量、数据安全                           |
| 6   | 转化信号         | 10%  | 定价定位、IAP 透明度、社会证明、下载量范围                             |

**最终得分** = 实际已评估维度的加权总和。

### 不可评估的维度（计算任何得分前请先阅读）

`references/scoring-criteria.md` 将得分 0 定义为“无法评估（数据不可用）”。缺失数据在这里是常态，而不是例外 ——
WebFetch 无法提取截图或字幕文本，且宣传性文本无法与抓取到的 HTML 中的其他内容区分开来。对于未获取的数据评分为 0 并不代表列表质量差；将其计入评分会凭空制造不及格的等级（一个权重为 25% 且未观察到的 Visual Assets 维度，会悄无声息地将一个 A 级列表降为 D 级）。

内部规则：

1. 无法观察到的维度应从加权分母中**排除**，而不是评分为 0。重新调整其余权重，并说明所使用的分母（“在占总权重 75% 的 4 个维度上为 74/100”）。
2. 将每个被排除的维度列为**未评估**，说明原因以及用户需要提供哪些内容来完成评估（列表页面的截图、App Store Connect 访问权限）。
3. 如果未评估的总权重**超过 25%**，则完全**不提供字母等级**。改为报告部分得分和受阻的维度；不要给出证据无法支持的等级。

### 得分解释

| 得分   | 等级 | 含义                                             |
| ------ | ---- | ------------------------------------------------ |
| 85-100 | A    | 优化良好；重点放在 A/B 测试和迭代上              |
| 70-84  | B    | 基础良好；存在明确的改进机会                     |
| 50-69  | C    | 存在明显缺口；优先修复将带来较高影响             |
| 30-49  | D    | 多个维度都需要进行重大优化                       |
| 0-29   | F    | 列表需要彻底重做                               |

## 阶段 3 — 竞争对手对比（可选）

如果用户提供竞争对手 URL 或要求进行对比：

1. 获取同一类别中的 2-3 个头部竞争对手
2. 对每个竞争对手执行相同的评分
3. 创建对比表，突出显示用户的应用在哪些方面较弱或较强
4. 识别关键词差距 — 竞争对手排名所依赖、但用户的应用未进行目标覆盖的术语

如果未指定竞争对手，建议用户提供 2-3 个竞争对手，或主动提出搜索其类别中的头部应用。

## 阶段 4 — 生成报告

使用 `references/report-template.md` 中的模板来组织输出。

报告必须包括：

1. **评分卡** — 包含全部 6 个维度、各维度得分、实际使用的加权分母，以及等级的表格（当未评估维度的权重超过 25% 时，根据不可评估维度规则不提供等级）
2. **Top 3 快速见效项** — 用时少于 1 小时且影响最大的改动
3. **详细发现** — 按维度拆分，并列出具体问题和修复方案
4. **关键词建议** — 基于标题/描述分析以及竞争对手差距
5. **视觉素材建议** — 具体的截图/视频改进建议
6. **优先行动计划** — 按影响与工作量排序的改动列表

### 报告规则

- 每项建议都必须**具体且可执行**（“将副标题从 X 改为 Y”，而不是“改进副标题”）
- 为所有文本建议标注字符数
- 在相关情况下标记平台差异（Apple 与 Google）
- 说明在没有付费工具的情况下**无法**评估的内容（搜索量、精确排名）
- 提出关键词修改建议时，解释每个关键词为何重要

## 平台特定规则

字符限制、截图和视频规格、CPP 与实验规则、政策禁令、Android Vitals 阈值、编辑精选，以及拒绝触发条件，均在阶段 2 中列出的三个参考文件内进行了版本管理。在根据规格对任何维度评分之前，请先阅读所审计商店对应的文件——这些文件是唯一事实来源，此处不重复列出会随时间变化的平台事实。

唯一一项会影响每次审计评分的对比仍直接保留如下：

### Apple 索引的内容与 Google 索引的内容

| 字段                 | Apple 已索引？   | Google 已索引？        |
| --------------------- | ---------------- | ---------------------- |
| 标题                 | 是              | 是（最强信号） |
| 副标题 / 简短描述 | 是              | 是                    |
| 关键词字段         | 是（隐藏）     | 不存在         |
| 长描述      | 否               | 是（高度重视）          |
| 截图文案   | 是（自 2025 年起） | 否                     |
| 应用内活动         | 是              | 不适用（改用 LiveOps）  |
| 开发者名称        | 否               | 部分                    |
| IAP 名称             | 是              | 是                    |

## 常见问题检查清单

如发现以下问题，请予以标记。标有 _(取决于层级)_ 的项目应根据应用的品牌成熟度层级进行评估——对于 Dominant 应用，它们可能是有意为之的选择。

每个标记项都附带一项**作者行动**，让读者明确应如何处理：

| 行动 | 含义 |
|---|---|
| **阻止上架** | 存在被拒绝、下架或排名受抑制的风险。请在下次提交前修复。 |
| **必需** | 会导致可量化的安装量或转化损失。请在下一个发布周期修复。 |
| **可选** | 存在提升空间，而非缺陷。若产能允许则发布。 |

**始终标记（所有层级）：**

- [ ] 评分低于 4.0 — **必需**
- [ ] 上次更新距今超过 3 个月 — **必需**
- [ ] Google Play 描述没有关键词策略（密度低于 1%）— **必需**
- [ ] Google Play 缺少特色图片 — **阻止上架**（没有它就无法获得精选展示位）
- [ ] Apple 关键词字段可能存在重复词（根据标题+副标题推断）— **必需**
- [ ] 分类不匹配 — 应用在其他分类中面临的竞争会更少 — **必需**
- [ ] 截图少于 5 张 — **必需**

**仅为 Challenger/Established 标记** _(对 Dominant 应用而言并非错误)：_

- [ ] 标题仅将字符浪费在品牌名称上（没有关键词）— **必需** _(Dominant：品牌本身就是关键词)_
- [ ] 副标题/简短描述重复标题关键词 — **必需**
- [ ] 描述前 3 行内容泛泛而谈 — **必需** _(Dominant：可能是品牌语调的选择)_
- [ ] 没有预览视频 — **可选** _(Dominant：如果产品难以演示，这可能是合理选择)_
- [ ] 截图只是没有信息传达/说明文案的 UI 堆砌 — **必需** _(Dominant：生活方式/品牌图片的转化效果可能更好)_
- [ ] 仅有 1-2 种本地化语言 — **可选** _(应根据实际市场评分，而不是绝对数量)_
- [ ] 没有应用内活动或推广内容 — **可选** _(Dominant 工具类应用可能不需要发现流量帮助)_

**适用于所有层级的标记，但需注意上下文：**

- [ ] 未对负面评价进行开发者回复 — **必需** _(注意评价量级 — 回复 1000 万+条评价与回复 1000 条是不同的挑战)_
- [ ] 通用的“新功能”文本 — **可选** _(当版本包含重大变更时，Apple 2.3.12 规定其**会阻止上架**_)_

禁止使用的标题元数据（表情符号、全大写、“最佳”/“#1”/“免费”、Google
Play 上的行动号召）始终**会阻止上架** — 参见 `references/google-play-specs.md`。

## 任务特定问题

1. App Store 或 Google Play 的 URL 是什么？
2. 这是你的应用还是竞品应用？
3. 该应用所在的竞争类别是什么？
4. 你是否有可供对比的竞品 URL？
5. 你关注的是搜索可见性、转化率，还是两者兼顾？
6. 你是否可以访问 App Store Connect 或 Google Play Console 数据？

## 边界

- 在没有当前来源或控制台回读信息的情况下，不要宣称关键词排名、转化提升、评价状态或商店审核通过。
- 未经明确授权，不要编辑或提交商店元数据、截图、构建版本、价格或发布版本。
- 不要虚构竞品表现、客户情绪或平台基准；应标注估算及其来源日期。
- 不要复用受版权保护的竞品资产，也不要在截图建议中生成替代版的 Suede S。

## 路由

- 需要付费应用安装创意 -> 使用 `suede-ad-creative`。
- 需要安装归因或应用内事件 -> 使用 `suede-analytics`。
- 需要用于商店列表文案的客户语言 -> 使用 `suede-customer-research`。
- 需要 iOS 或 Android 产品构建 -> 使用 `site-to-ios-app` 或 `android-app-factory`；从零开始构建原生 iOS 应用是私有 Suede Labs 配套工具，不在此工具包中：ios-app-factory。
- 需要为通过 iOS 工厂流水线发布的应用撰写 App Store 元数据 -> 私有 Suede Labs 配套工具，不在此工具包中：ios-aso-launch。优先级：`suede-aso` 根据 URL 审核并评分在线列表；`ios-aso-launch` 为正在发布的版本撰写元数据字段。任一时刻，两个工具中只有一个拥有某个字段的管理权。
- 从这些技能中，将商店列表审核、元数据策略和截图排序路由回 `suede-aso`。
