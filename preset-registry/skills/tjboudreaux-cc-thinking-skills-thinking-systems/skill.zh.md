# 系统映射与杠杆点

把问题当作结构与交互来对待，而非孤立部件。梳理边界、存量/流量、回路/延迟与反复出现的模式；在完成副作用检查后，于可行的最高杠杆点进行干预。

## 何时使用

- 症状横跨多个服务/组件；针对单一技术栈的修复失效或反复反弹。
- 一处的改动破坏另一处；行为是涌现出来的。
- 局部修复之后问题仍然复发（结构性问题，不只是症状）。
- 参数/缓冲区的微调无法见效，需要对干预手段排序。

## 何时不使用

- 单一组件内的线性 bug，且有清晰的堆栈/diff——直接追踪并修复。
- 吞吐量受限于一个显而易见的阶段——使用 theory-of-constraints。
- 决策是单个拟议行动的后果链——使用 second-order。
- 方法选择（计划 vs 探测 vs 稳定化）——先用 cynefin。

## 步骤

1. **划定系统边界。** 命名目的、参与者、边界以及输入/输出流。排除决策视界之外的噪声；纳入任何可能引发该症状的路径。
2. **绘制存量与流量。** 列出不断累积的存量（队列深度、技术债、缓存大小、WIP）以及填充/消耗它们的速率。注意即使流量骤变也变化缓慢的量。
3. **找出反馈与延迟。** 对每个候选回路：区分增强型（放大）与平衡型（抵抗）；标注同向（+）与反向（-）的链接；命名延迟（TTL、部署延迟、指标延迟、爬坡时间）。反向链接为偶数 → 增强型；奇数 → 平衡型。长延迟 + 强修正 → 过冲风险。
4. **问题复发时匹配反复出现的结构。** 仅在存在复发或政策阻力时才检查；不要强行套用某个模式：
   - 饮鸩止渴——快速修复，延迟出现更糟的副作用
   - 转移负担——权宜之计挤压了根本性修复
   - 增长上限——增长撞上平衡性约束
   - 公地悲剧——局部最优耗尽共享存量
   - 恶性升级——相互反应的螺旋
   - 富者愈富——优势通过资源分配复利式放大
   - 增长与投资不足——产能滞后于需求直至危机爆发
   若认真尝试一遍后无一匹配，保留从零绘制的地图。
