# 诊断 Bug

一套用于处理疑难 Bug 的方法。仅在有明确理由时才跳过阶段。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），以清晰理解相关模块，并查看所涉及区域中的 ADR。

## 脱敏

此技能会要求你展示命令、输出和捕获的产物。**首先对所有机密信息进行脱敏**：在相应位置写入 `<REDACTED>`。基于环境变量构建循环，使凭据保留在环境中，而不会出现在你展示的内容里。捕获的产物中包含身份验证标头：仅引用包含有效信号的行。

如果脱敏后的输出不足以诊断 Bug，请说明情况并向用户询问。

## 阶段 1：构建反馈循环

**这就是此技能的核心。** 其他一切都只是机械操作。如果你针对该 Bug 有一个**紧密的**通过/失败信号（一个会因*这个* Bug 而变红的信号），你就能找到原因；二分查找、假设检验和插桩都只是利用这个信号。如果没有这样的信号，无论盯着代码看多久都无济于事。

应在这里投入格外多的精力。**积极主动。发挥创意。绝不放弃。**

### 构建反馈循环的方法，大致按以下顺序排列

1. 在任何能够触及该 Bug 的接缝处编写**失败测试**：单元测试、集成测试或端到端测试。
2. 针对正在运行的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用固定输入调用 **CLI**，将 stdout 与已知正确的快照进行 diff。
4. 编写**无头浏览器脚本**（Playwright / Puppeteer）来操作 UI，并对 DOM、控制台和网络行为进行断言。
5. **重放捕获的跟踪记录。** 将真实的网络请求、payload 或事件日志保存到磁盘；在隔离环境中通过相关代码路径重放。
6. **一次性测试工具。** 启动系统的最小子集（一个服务、模拟的依赖项），通过单次函数调用来执行出现 Bug 的代码路径。
7. **属性测试 / 模糊测试循环。** 如果 Bug 是“输出有时错误”，则运行 1000 个随机输入并寻找失败模式。
8. **二分查找测试工具。** 如果 Bug 出现在两个已知状态（commit、dataset、version）之间，则自动执行“在状态 X 启动、检查、重复”，以便通过 `git bisect run` 运行。
9. **差异比较循环。** 让同一个输入分别通过旧版本和新版本（或两种配置）运行，并对输出进行 diff。
10. **HITL bash 脚本。** 最后的手段。如果必须由人来点击，则使用 `scripts/hitl-loop.template.sh` 引导*他们*操作，从而使循环仍然保持结构化。捕获的输出会反馈给你。

构建正确的反馈循环，Bug 就已经解决了 90%。

### 收紧循环

将循环视为一个产品。一旦有了*一个*循环，就要**收紧**它：

- 能否让它更快？（缓存初始化过程、跳过无关的初始化、缩小测试范围。）
- 能否让信号更明确？（针对具体症状进行断言，而不是只检查“没有崩溃”。）
- 能否让它更具确定性？（固定时间、设定 RNG seed、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环只比没有循环好一点；一个耗时 2 秒且结果确定的循环才足够紧密，是调试工作的超级武器。

### 非确定性 Bug

目标不是获得一次干净的复现，而是实现**更高的复现率**。将触发过程循环 100 次、并行执行、增加压力、缩小时间窗口、注入 sleep。复现率为 50% 的偶发 Bug 可以调试；复现率为 1% 的则无法调试，因此应持续提高复现率，直至可以进行调试。

### 当你确实无法构建循环时

停下来并明确说明这一点。列出你尝试过的方法。向用户请求：(a) 访问能够复现问题的环境，(b) 一份经过脱敏的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像），或 (c) 获得添加临时生产环境检测代码的许可。在没有循环的情况下，**不要**继续提出假设。

### 完成标准：一个能变红的紧密循环

当循环足够**紧密**且**能够变红**时，阶段 1 即告完成：你可以给出**一条命令**（脚本路径、测试调用或 curl），并且你已经**至少运行过一次**（展示调用及其输出，需脱敏），且该命令满足：

- [ ] **能够变红**：它会触发实际的缺陷代码路径，并断言**用户所描述的确切症状**，因此遇到此缺陷时会变红，修复后会变绿。不能只是“运行时不报错”；它必须能够_捕获这个特定缺陷_。
- [ ] **确定性**：每次运行都得出相同结论（对于偶发性缺陷：按照上述要求固定条件，并达到较高的复现率）。
- [ ] **快速**：耗时数秒，而不是数分钟。
- [ ] **可由智能体运行**：你可以让它无人值守地运行；只有通过 `scripts/hitl-loop.template.sh` 才允许人工参与循环。

如果你发现自己在这条命令存在之前就开始阅读代码以构建理论，**请停下来：直接跳到假设，正是此技能要防止的失败方式。** 没有能够变红的命令，就不能进入阶段 2。

## 阶段 2：复现 + 最小化

运行循环。观察缺陷出现时循环变红。

确认：

- [ ] 循环产生的是**用户**所描述的故障模式，而不是恰好发生在附近的其他故障。错误的缺陷 = 错误的修复。
- [ ] 该故障可以在多次运行中稳定复现（或者对于非确定性缺陷，其复现率高到足以据此进行调试）。
- [ ] 你已经捕获了确切症状（错误消息、错误输出、耗时过长），以便后续阶段验证修复确实解决了该问题。

### 最小化

一旦循环变红，就将复现案例缩减为**仍然会变红的最小场景**。每次只删减输入、调用方、配置、数据和步骤中的**一项**，每次删减后都重新运行循环，并且只保留对触发故障不可或缺的部分。

这样做的原因是：最小复现案例会缩小阶段 3 中的假设空间（剩余需要怀疑的可变因素更少），并在阶段 5 中成为简洁的回归测试。

当**剩余的每个元素都不可或缺**时，即告完成：移除其中任何一个元素，都会使循环变绿。

在完成复现**和**最小化之前，不要继续。

## 阶段 3：提出假设

在测试任何假设之前，先生成 **3–5 个按优先级排序的假设**。只生成单个假设会使你锚定在第一个看似合理的想法上。

每个假设都必须是**可证伪的**：说明它会产生什么预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 将使缺陷消失 / <改变 Z> 将使缺陷恶化。”

如果你无法说明预测，那么这个假设只是一种感觉：丢弃它或使它更精确。

**在测试之前向用户展示排序后的列表。** 用户往往具备能够立即改变排序的领域知识（“我们刚刚部署了一项与第 3 条相关的变更”），或者知道哪些假设已经被排除。这是一个成本低廉但能大幅节省时间的检查点。不要因此停滞；如果用户暂时不在线，就按照你的排序继续进行。

## 阶段 4：插桩

每个探针都必须对应阶段 3 中的一项具体预测。**一次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分不同假设的边界处添加**有针对性的日志**。
3. 绝不要“记录所有内容再用 grep 搜索”。

**为每条调试日志添加标签**，使用唯一前缀，例如 `[DEBUG-a4f2]`。最后清理时，只需执行一次 grep。未添加标签的日志会保留；添加了标签的日志必须删除。

**性能分支。** 对于性能回归，日志通常不是正确的手段。应改为：先建立基准测量（计时工具、`performance.now()`、性能分析器、查询计划），然后进行二分排查。先测量，再修复。

## 阶段 5：修复 + 回归测试

在修复之前编写回归测试，但前提是存在**正确的测试接缝**。

正确的测试接缝，是指测试能够按照调用点实际发生的方式覆盖**真实的缺陷模式**。如果唯一可用的接缝过于浅层（缺陷需要多个调用方才能触发，却只测试单个调用方；单元测试无法复现触发缺陷的调用链），那么在该处编写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是排查结果。** 将其记录下来。代码库的架构正在阻碍对此缺陷进行可靠的回归约束。将此问题标记出来，留待下一阶段处理。

如果存在正确的接缝：

1. 将最小化复现用例转换为该接缝处的失败测试。
2. 确认它确实失败。
3. 应用修复。
4. 确认它通过。
5. 针对原始（未最小化的）场景，重新运行阶段 1 的反馈循环。

## 阶段 6：清理

在宣布完成之前必须满足：

- [ ] 原始复现用例不再复现问题（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录缺少测试接缝的情况）
- [ ] 已移除所有 `[DEBUG-...]` 插桩（使用 grep 搜索该前缀）
- [ ] 已删除一次性原型（或将其移至明确标记的调试位置）
- [ ] 已在提交 / PR 消息中说明最终被证实为正确的假设，以便下一位调试者了解情况
