# 诊断缺陷

一门应对难解缺陷的纪律。仅在明确且合理的情况下才跳过阶段。

在探索代码库时，阅读 `CONTEXT.md`（如果存在）以形成相关模块的清晰心智模型，并检查你所涉及区域中的 ADR。

## 脱敏

该技能要求你展示命令、输出和捕获的工件。**先对所有敏感信息进行脱敏**——用 `<REDACTED>` 代替。按环境变量搭建循环，使凭据保留在环境中，而不是展示出来。捕获的工件包含鉴权头：仅引用携带信号的行。

如果脱敏后的输出不足以诊断缺陷，请说明并询问用户。

## 阶段 1 — 构建反馈闭环

**这就是核心技能。** 其他都只是机械操作。如果你对该缺陷有一个紧密的通过/失败信号——能在该缺陷上转红，你就能找到根因；二分法、假设验证和插桩都只是围绕它运作。若没有这种信号，再怎么盯着代码也没有用。

在此投入不成比例的精力。**要积极。要有创造性。不要放弃。**

### 构建方式（按大致顺序尝试）

1. 在任何能触达该缺陷的接口上进行**失败测试**——单元、集成、端到端。
2. 对运行中的开发服务器发起 **Curl / HTTP 脚本** 请求。
3. 使用固定输入运行 **CLI 调用**，将 stdout 与已知正确快照比对。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，在 DOM/控制台/网络上断言。
5. **重放捕获的追踪。** 将真实网络请求/载荷/事件日志保存到磁盘；在隔离的代码路径中重放。
6. **一次性测试框架。** 启动最小子系统（单服务、模拟依赖），用单次函数调用触发该缺陷代码路径。
7. **属性 / 模糊测试循环。** 若缺陷为“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分法测试框架。** 若缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化执行“在状态 X 启动、检查、重复”，以便对其执行 `git bisect run`。
9. **差分测试循环。** 对旧版本与新版本（或两种配置）输入相同内容并比较输出差异。
10. **HITL bash 脚本。** 作为最后手段。如果必须有人类点击，就通过 `scripts/hitl-loop.template.sh` 驱动**他们**，使循环依然结构化。捕获的输出会反馈给你。

构建出合适的反馈循环后，问题可先解决约 90%。

### 紧缩循环

把循环当作产品来对待。一旦有了**一个**循环，就要**紧缩**它：

- 能否让它更快？（缓存初始化、跳过无关初始化、缩小测试范围。）
- 能否让信号更清晰？（断言具体症状，而不是“未崩溃”。）
- 能否让它更确定性？（固定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

30 秒左右的波动性循环几乎不比无循环好；2 秒的确定性循环才是“紧”的——一种调试超能力。

### 非确定性缺陷

目标不是一次性干净重现，而是**提高重现率**。将触发行为循环 100 次并行化，增加压力，缩小时间窗口，插入 sleep。50% 的波动缺陷是可以调试的，1% 则不可——持续提高到可调试为止。

### 当你确实无法构建循环时

停止并明确说出来。列出已尝试的内容。向用户索要：(a) 能复现问题的环境访问权限；(b) 一份脱敏后的捕获工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制）；或 (c) 临时生产级插桩权限。**不得在没有循环的情况下继续推测。**

### 完成标准——可转红的紧密循环

阶段 1 在下列条件满足时完成：你已拥有一个**紧密**且**可转红**的循环，能给出你**至少运行过一次**的**一条命令**（展示该调用和脱敏后的输出）：一个脚本路径、测试调用或 curl。该命令必须满足：

- [ ] **可转红**——它驱动真实的缺陷代码路径，并断言**用户的精确症状**，因此在该缺陷上可转红、修复后变绿。不能只“运行不报错”——必须能捕获该具体缺陷。
- [ ] **确定性**——每次运行判定一致（对于非确定性缺陷，按前述要求设置高重现率）。
- [ ] **快速**——耗时以秒计，而非分钟。
- [ ] **可由代理执行**——可无人值守运行；除非有人类参与，否则只通过 `scripts/hitl-loop.template.sh`。

如果在该命令出现前你发现自己在先读代码构建理论，**请立即停下——直接跳到假设正是此技能要避免的失败模式。** 没有可转红命令，就没有阶段 2。

## 阶段 2 — 重现 + 缩减

运行闭环。观察它转红——缺陷出现。

确认：

- [ ] 循环复现了用户描述的故障模式——不是附近出现的其他故障。错检会导致错修。
- [ ] 该故障可在多次运行中复现（或对非确定性缺陷，在足够高的频率下可复现以便调试）。
- [ ] 你已捕获到精确症状（错误信息、错误输出、慢响应时间），以便后续阶段验证修复是否真正解决。

### 缩减

一旦转红，缩小到**仍能转红的最小场景**。逐项删减输入、调用方、配置、数据和步骤——每删减一项就重跑循环——仅保留对失败有支撑作用的元素。

之所以要这样做：最小复现会在第 3 阶段缩小假设空间（可疑点更少），并在第 5 阶段成为干净的回归测试。

当**每个剩余元素都具有支撑作用**时完成——删除任意一项都会让循环变绿。

在未完成复现并缩减前，不要继续下一步。

## 阶段 3 — 假设

在测试前先生成**3–5 条排名假设**。单一假设生成会停留在第一个看似合理的想法。

每条假设都必须是**可证伪**的：写出它的可检验预测。

> 格式：“如果 <X> 是原因，那么改变 <Y> 会让缺陷消失 / 改变 <Z> 会让问题加重。”

若无法表达预测，则该假设仅是直觉——应放弃或细化。

**在测试前先向用户展示排名列表。** 他们通常具有上下文知识，能快速重排（“我们刚在 #3 上部署了变更”）或知道哪些假设已排除。廉价但高价值的检查点。若用户暂时离开，无需阻塞；按你的排序继续。

## 阶段 4 — 插桩

每个探针都必须对应第 3 阶段的某个具体预测。**一次只改一个变量。**

工具优先级：

1. 如果环境支持，优先使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在可区分假设的边界处进行**定向日志**。
3. 不要“日志全开再 grep”。

**为每条调试日志加唯一前缀标签**，例如 `[DEBUG-a4f2]`。这样结束时清理只需一次 grep。未打标签的日志会保留；带标签日志会被删除。

**性能分支。** 对性能回归，日志通常误导。应先建立基线测量（计时脚本、`performance.now()`、性能分析器、查询计划），再进行二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

先写回归测试——但前提是存在**正确的接合点**。

正确的接合点要求测试在真实调用点上覆盖**真实缺陷模式**。如果唯一可用的接合点过于浅层（例如单个调用者的测试，但缺陷需要多个调用者；或单元测试无法复现触发链），该测试会带来错误信心。

**若不存在正确接合点，这本身就是结论。** 记录下来。代码架构正在阻止将该缺陷固化。将其标记为下一阶段要处理的问题。

若存在正确接合点：

1. 将最小复现转为该接合点上的失败测试。
2. 观察其失败。
3. 应用修复。
4. 观察其通过。
5. 使用原始（未缩减）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 收尾 + 事后复盘

在宣布完成前必须满足：

- [ ] 原始复现场景不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已记录缺乏接合点）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移入明确标记的调试位置）
- [ ] 正确的假设已写入提交 / PR 说明——让下一位调试者可快速接续
