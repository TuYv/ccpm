# TRIZ

解决技术设计矛盾，而不采取中点折中。指出冲突所在，分离对立状态，并改造系统，使两项收益同时成立。

## 何时使用

- 架构、API 或系统参数朝相反方向拉扯（稳定 vs 演进、新鲜 vs 缓存、严格 vs 顺畅）。
- 你正准备接受一项权衡，理由是“不可能两者兼得”。
- 每个候选方案都存在同样的结构性弱点——冲突出在需求上，而不是选项列表中。

## 何时不要使用

- 在给定约束下某个选项就是更好 → 直接选它；不要人为制造矛盾。
- 一次低成本的测量就能显示哪一方才真正关键 → 去测量，而不是凭空发明分离方案。
- 某个标准模式已经能解决（cache-aside、CQRS、功能开关、版本化）→ 直接套用该模式。
- 非技术性的人际/组织冲突 → 超出范围；分离所针对的是系统参数。
- 普通的优先级排序或资源分配，且不存在同一参数的对立状态。

## 步骤

1. **以模板形式指出矛盾。** 写下：“我们需要 [PARAMETER] 为 [STATE_1] 以实现 [BENEFIT_1]，但为 [STATE_2] 以实现 [BENEFIT_2]。” 如果写不成这个形式，就此停止——改用其他方法。
2. **陈述最终理想解（IFR）。** 描述两项收益同时成立、只需最少新增机制、且没有永久性中点牺牲的情形。
3. **先尝试分离，再考虑发明。** 依次测试：**时间**（不同时刻）、**空间**（不同组件/层次）、**条件**（上下文、负载、风险）、**尺度**（接口 vs 实现、聚合 vs 元素）。保留第一个能在不引入隐藏折中的前提下同时实现两项收益的分离方案。
4. **若分离失败，应用发明式变换。** 优先选择资源消耗低的手段：分割、预先作用、反转（push/pull）、中介物、复制/副本、动态化（功能开关/配置）、另一维度（元数据/版本化/事件）。只扫描与所指明的参数冲突相对应的原理。
5. **优先复用既有资源。** 在新增服务或存储之前，先检查已有的数据、流量、请求头、调度器和副作用，看它们能否承载该分离。
6. **锁定具体解决方案并停止。** 明确设计变更、每种状态的所在位置，以及两项收益如何得到保留。当一套无折中的设计被陈述出来时停止；当诚实的分析表明只剩下受约束的权衡时也停止——此时应明确记录残余权衡，而不是强行上演 TRIZ 表演。

## 输出

给出一份 TRIZ 解决方案：

- `contradiction`：参数 / state_1+benefit_1 / state_2+benefit_2
- `ideal_final_result`：两项收益同时成立，无永久性折中
- `separation_tried`：时间 | 空间 | 条件 | 尺度 → 各自的结果
- `inventive_move`：若分离 alone 不足时所用到的原理或模式（若无则写无）
- `resources_reused`：被借用复用的既有能力
- `resolution`：具体的设计决策，以及每种状态在何处成立
- `residual_tradeoff`：无，或诚实保留的剩余折中

## 校验

- **模板门槛：** 如果矛盾无法写成所要求的形式，不要应用 TRIZ。
- **无折中检查：** 在权衡曲线上取纯中点、且没有任何分离或发明式变换的，属于失败的应用。
- **分离优先：** 未尝试时间/空间/条件/尺度分离就直接应用原理，视为不完整。
- **过度应用防线：** 如果测量或标准模式就能定下设计，跳过 TRIZ。
- **停止：** 一个指名的矛盾 → 分离/发明式变换一轮 → 具体解决方案；不要把原理循环用作装饰。
