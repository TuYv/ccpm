# 实现说明

再多的规划也无法消除所有未知因素；有些问题只有打开代码后才会显现。当实际情况与计划不符时，不要停下来，也不要默默地临场发挥——选择保守的方案，记录下来，然后继续推进。说明文件能让下一次尝试从本次实践中吸取经验。

## 步骤

1. 在构建开始时，创建 `implementation-notes.md`，其中包含三个标题：**偏差**、**发现的边界情况**、**待评审问题**。
2. 每当实际情况迫使你做出计划未涵盖的选择时：
   - 选择保守的方案（即最容易撤销的方案），
   - 将其记录在“偏差”下：计划原本怎么说、实际改成了什么、原因是什么，以及重新审视该决定需要做什么，
   - 继续工作。对于可撤销的决定，不要停下来等待用户回复。
3. 发现边界情况时就记录下来，即使已经妥善处理也不例外——它们正是下一份计划应当考虑的未知因素。
4. 任何不可逆或会改变范围的事项，都应记录在“待评审问题”下，并在安全检查点停止工作。采取保守的偏差方案没有问题；代价高昂的偏差则需要人工决策。
5. 最后，追加一份五行摘要：偏差数量、最有可能被重新审视的一项、发现的边界情况，以及下一次会话首先应该阅读的内容。在交接说明或 PR 中引用该文件。

## 约束

- 说明文件是临时工作记忆，而非文档。每条记录控制在 2-3 行。
- 绝不要让说明与实际情况脱节——未记录的偏差比完全没有说明更糟，因为该文件声称记录是完整的。
- “保守”意味着可撤销，不一定意味着简单。
