# Suede 客户研究

使用这套 Suede 客户研究手册，让定位、产品和文案建立在可追溯的客户证据之上，而不是假设之上。

## 开始之前

检查是否存在 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，或旧版 `product-marketing-context.md`），如果存在就阅读它——ICP、细分定义以及已有研究会决定你应该去哪里查找，以及什么样的样本才具有代表性。只询问其中尚未回答的问题。

---

## 两种研究模式

### 模式 1：分析现有资料
你已经拥有原始研究材料（访谈记录、问卷、评论、工单）。你的任务是提取有效信息。

### 模式 2：主动寻找研究
你需要从在线来源（Reddit、G2、论坛、社区、评论网站）收集情报。你的任务是了解应该去哪里查找，以及需要提取什么信息。

大多数项目会结合这两种模式。在继续之前，先确定适用哪种模式。

---

## 模式 1：分析现有研究资料

### 资料类型

**客户访谈 / 销售通话记录**
- 提取：痛点、触发因素、期望结果、使用的语言、异议、考虑过的替代方案
- 关注：他们决定寻找解决方案的那个时刻、之前尝试过什么，以及对他们而言成功是什么样的

**问卷结果**
- 在得出结论之前，先按客户层级、使用场景或合作时长对回答进行细分
- 标记：开放式回答与选择题回答分别说明了什么（两者经常相互矛盾）
- 识别：包含最有用信息的那 20% 回答

**客户支持对话**
- 挖掘：反复出现的投诉、令人困惑的地方、功能请求，以及“我希望它能……”这类表述
- 在分析之前先对工单进行分类——不要把所有工单都视为同等有效的信号
- 将 bug、困惑、缺失功能和预期不符区分开来

**赢单/输单访谈和流失客户记录**
- 赢单：是什么促成了最终决定？什么因素差点让他们选择竞争对手？
- 输单和流失：原因是价格、功能、匹配度、时机，还是其他因素？
- 按原因进行细分——不要对不同的流失原因取平均

**NPS 回答**
- 对于改进工作，被动者和贬损者比推荐者能提供更强的信号
- 将评分与文字反馈结合起来——一个附带具体投诉的 9 分，比一个没有任何评论的 10 分更有价值

### 提取框架

针对每份资料，提取：

1. **待完成的任务** — 客户想要达成什么结果？
   - 功能性任务：任务本身
   - 情感性任务：他们希望获得什么感受
   - 社交性任务：他们希望别人如何看待自己

2. **痛点** — 他们当前的处境中有哪些令人沮丧、失灵或不够理想的地方？
   - 优先关注未经提示主动提及、且带有情绪化语言的痛点

3. **触发事件** — 发生了什么变化，让他们开始寻找解决方案？
   - 常见触发因素：团队扩大、新员工入职、未达成目标、令人尴尬的事件、竞争对手做了某件事

4. **期望结果** — 用他们自己的话来说，成功是什么样的？
   - 记录准确引语，而不是转述

5. **语言和词汇**——客户实际使用的确切词语和短语
   - 这是文案的宝贵素材。“我们被电子表格淹没了” > “手动流程效率低下”

6. **考虑过的替代方案**——他们还看过或尝试过什么？
   - 包括什么都不做、雇人，或内部开发

### 综合分析步骤

从单个素材中提取信息后：

1. **按主题聚类**——将不同素材中相似的痛点、结果和触发因素归组
2. **频率 + 强度评分**——某个主题出现得有多频繁，以及客户感受有多强烈？
3. **按客户画像细分**——模式是否会因公司规模、角色、使用场景或使用时长而不同？
4. **识别“金句”**——为每个主题找出 5-10 条最具代表性的逐字引用
5. **标记矛盾**——客户口头上说一件事，但实际做了另一件事的情况

### 研究质量保障

在展示每条洞察之前，都要标注其置信度：

| 置信度 | 标准 |
|------------|----------|
| **高** | 主题出现在 3 个以上独立来源中；客户主动提及；在不同细分群体中保持一致 |
| **中** | 主题出现在 2 个来源中，或仅在受到引导时出现，或仅限于一个细分群体 |
| **低** | 单一来源；可能是异常情况；需要进一步验证 |

**时效窗口**：更加重视过去 12 个月内的来源。市场会发生变化——3 年前的访谈记录可能反映的是不同的产品和买家。

**样本偏差检查**：
- 在线评论者往往偏向重度用户和观点强烈的人群
- 支持工单偏向问题，而不是价值
- Reddit 上的用户相比主流买家更偏技术型，也更容易持怀疑态度
- 在得出关于“所有客户”的结论时，要将这些因素纳入考量

**最低可行样本**：在为某个细分群体建立画像，或得出该细分群体的消息传递结论之前，每个细分群体至少需要 5 个独立数据点——访谈、评论、工单或社区帖子均可。少于 5 个时，应将这些材料作为原始信号呈现，而不是研究发现。

## 模式 2：数字聚集地研究

在线社区是客户不加过滤地表达想法的地方。目标是找到关于问题领域的真实、未经调节的语言。

### 去哪里找

根据你的 ICP 类型选择来源——然后阅读 `references/source-guides.md`，了解详细的操作指南、搜索运算符以及各平台的提取技巧。

| ICP 类型 | 主要来源 |
|----------|----------------|
| B2B SaaS / 技术买家 | Reddit（特定角色的子版块）、G2/Capterra、Hacker News、LinkedIn、Indie Hackers、SparkToro |
| SMB / 创始人 | Reddit（r/entrepreneur、r/smallbusiness）、Indie Hackers、Product Hunt、Facebook Groups、SparkToro |
| 开发者 / DevOps | r/devops、r/programming、Hacker News、Stack Overflow、Discord 服务器 |
| B2C / 消费者 | 应用商店评论（1-3 星）、Reddit 兴趣/生活方式子版块、YouTube 评论、TikTok/Instagram 评论 |
| 企业客户 | LinkedIn、行业分析师报告、G2 Enterprise 筛选结果、招聘信息、SparkToro |

**快速决策指南：**
- 已经有产品类别？→ 从 G2/Capterra 评论开始（包括你自己的产品和竞争对手）
- 需要了解受众在哪里活动？→ 使用 SparkToro（可以发现播客、YouTube 频道、subreddit、网站、社交账号）
- 需要真实用语？→ 查看 Reddit 和 YouTube 评论
- 需要了解触发事件？→ 查看 LinkedIn 帖子、招聘信息、Hacker News 的“Ask HN”讨论串
- 需要竞争情报？→ 查看 G2 上竞争对手的 4 星评论、Product Hunt 讨论，以及 SparkToro 的竞争对手受众分析

### 从每个来源中提取的内容

对于找到的每一条内容：

| 字段 | 要记录的内容 |
|-------|----------------|
| 来源 | 平台、帖子 URL、日期 |
| 原文引用 | 准确的原话——不要改述 |
| 上下文 | 是什么促使对方发表这条评论？ |
| 情感倾向 | 正面 / 负面 / 中性 / 沮丧 |
| 主题标签 | 痛点 / 触发因素 / 结果 / 替代方案 / 用词 |
| 客户画像信号 | 帖子中体现的角色、公司规模、行业线索 |

### 综合分析前先保存采集结果

在从采集结果中提取主题之前，先保存你收集到的内容——否则下面的溯源门禁将无法执行，重新运行时也会重复整个采集过程。沿用 `suede-competitor-profiling` 使用的原始证据约定：每次运行在 `customer-research/raw/<YYYY-MM-DD>/` 下创建一个按日期命名的文件夹，其中每个来源对应一个文件（`reddit.md`、`g2-<competitor>.md`、`app-store.md`），另加一个列名为上述采集表字段的 `captures.csv`。每次运行都要新建日期文件夹，绝不要覆盖之前日期的文件夹——这样才能对比市场发生了哪些变化。模式 1 的材料（访谈记录、工单、赢单/丢单记录、NPS 原话）通常已经存在于某处：不要复制它们，而是在 `captures.csv` 中通过文件路径或系统标识符，以及日期和细分市场记录每条材料，这样每条引用都能解析到一个有名称的记录。

### 研究综合模板

从多个来源收集信息后，综合为：

```
## 主要主题（按频率 × 强度排序）

### 主题 1：[名称]
**总结**：[1-2 句话]
**频率**：出现在 X 个来源中的 Y 个
**强度**：高 / 中 / 低（根据使用的情绪化语言判断）
**代表性引用**：
- "[准确的原文引用]" — [来源，日期]
- "[准确的原文引用]" — [来源，日期]
**影响**：这对 messaging / 产品 / 定位意味着什么

### 主题 2：...
```

## 画像生成

### 尚无评论时

早期产品（或新类别）缺少第一方评论数据。不要虚构画像——应按以下顺序通过代理来源向外扩展：

1. **你自己的差异化优势**——产品与众不同之处决定了谁最能感受到这种差异；将其作为假设写下来
2. **直接竞争对手的评论**——他们的客户会用自己的语言描述问题空间（注意哪些方面受到称赞，以及哪些方面有所缺失）
3. **市场中的可比产品**——针对同一任务的相邻解决方案的 Amazon/app-store 评论
4. **面向同一受众的相邻品牌**——该买家还会购买什么；这些品牌的评论会揭示买家更广泛的语言和价值观

以这种方式构建的画像属于临时画像：为每个画像标注其代理来源，并在真实评论出现后用第一方证据替换代理证据。上述最小可行样本同样适用于代理证据。

### 画像结构

**在本次运行中编写第一个画像之前，请先阅读 [references/persona-templates.md](references/persona-templates.md)**——其中包含完整的填写结构（画像、首要任务、触发因素、痛点、期望结果、异议、替代方案、词汇、触达方式）。凭记忆编写画像会导致字段逐渐偏移，也会使画像之间失去可比性。

### 用户画像反模式

- **不要给它们起可爱的名字**（“Marketing Mary”），除非你的团队觉得这有帮助——这通常会分散注意力
- **不要跨细分市场取平均**——一个代表所有人的用户画像，实际上谁也代表不了
- **不要编造细节**——如果你没有某方面的数据，就留空，不要自行填补
- **每季度重新审视**——随着你的市场和产品演变，用户画像会逐渐失效

## 溯源检查关卡

在完成交付物后、发出之前执行此检查。以下边界条件
禁止编造引文、主题、样本量和频次统计；这使得检查可验证，
而不只是一个愿景。

- **每一条逐字引文都对应一条具名采集记录。** 模式 2：针对上述采集表中的每条记录，提供平台、讨论串 URL 和日期。模式 1：提供资产标识符或文件，以及日期和细分群体。无法归因到采集记录的引文将被**删除**——绝不将其转述为主题，也绝不纳入频次统计。
- **在同一轮检查中重新统计数字。** “在 Y 个来源中的 X 个出现过”以及每个高/中/低置信度标签，都应当立即根据采集记录重新计算，而不是沿用草稿中的内容。不再与计数相符的置信度标签应被降级，而不是为其辩护。
- **说明样本。** 在交付物本身中列出来源构成、细分群体、日期范围和采集总量，以便读者判断结论所依据的基础。

## 交付物格式

默认交付物：一份**研究综合报告**（主题、引文、模式、
影响）以及一份按主题组织的 **VOC 引文库**。除非
用户要求其他内容，否则请产出这些。

当目标需要时，提供以下替代或补充内容：一份**用户画像
文档**（1-3 个用户画像）、一份**待完成任务地图**（按细分群体划分的功能性、
情感性、社会性任务）、一份**竞争情报摘要**（客户
如何评价竞争对手与你），或一份**研究缺口分析**（你仍然
不知道什么，以及如何找到答案）。

## 继续之前要问的问题

如果上下文不明确：

1. **目标是什么？** 改善信息传达？构建用户画像？发现产品缺口？了解流失情况？
2. **你已经有什么？**（访谈记录、调研问卷、工单、G2 评价、什么都没有）
3. **目标细分群体是谁？**（所有客户、特定层级、已流失用户、未购买的潜在客户）
4. **你的产品是什么？**（如果产品营销上下文文件中未说明）

不要一次问完四个问题——先从第 1 和第 2 个开始，然后根据需要继续追问。

## 边界

- 不得编造引文、主题、样本量、情感倾向、用户画像特征或频次统计。
- 未经明确授权和同意，不得联系参与者、录制会话、抓取受限社区内容，或暴露身份识别数据。
- 不得将便利样本表述为具有代表性；应说明来源、细分群体、日期、样本量和收集限制。
- 不得仅凭综合分析决定产品优先级或客户事实；应区分证据、推断和开放问题。

## 路由

- 需要基于客户语言撰写最终文案 -> 使用 `suede-copy`。
- 仅需要竞争对手证据 -> 使用 `suede-competitor-profiling`。
- 需要 ICP 或定位综合分析 -> 使用 `suede-product-marketing`。
- 需要流失、外呼、付费推广或内容应用 -> 使用 `suede-churn-prevention`、`suede-cold-email`、`suede-ads` 或 `suede-content-strategy`。
- 从这些技能出发，将访谈设计、评价挖掘和证据综合分析重新路由回 `suede-customer-research`。
