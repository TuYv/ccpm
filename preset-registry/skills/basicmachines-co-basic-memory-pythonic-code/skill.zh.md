# Pythonic 代码

编写能让人类和 AI 读者一眼看懂领域行为的 Python 代码。以 WWGD 为考量视角：
选择最简单、正确、符合 Python 习惯且易于验证的设计。

首选的设计方法是**构造式领域建模**：定义程序能够构造的有效值和结果，然后让这些值和结果的类型将约束传递给使用它们的代码。

## 编码前先了解全貌

1. 阅读仓库中的 `AGENTS.md` 或 `CLAUDE.md` 指令。
2. 如果存在 `docs/ENGINEERING_STYLE.md`，请阅读它。
3. 当变更涉及领域语言、所有权、身份、事实来源规则或生命周期行为时，阅读 `docs/DOMAIN_MODEL.md`。
4. 编辑每个目标文件前，完整阅读该文件。
5. 确认受支持的 Python 版本、已配置的工具、周边代码模式，以及必须保持稳定的行为。

本地项目规则优先于通用风格建议。

## 按以下顺序做出决策

1. 保持正确性、领域不变量和公开行为。
2. 遵循仓库约定和兼容性约束。
3. 让数据流、控制流、错误和副作用清晰直观。
4. 选择当前能够降低认知负担的最小抽象。
5. 仅在 Python 惯用写法能澄清意图，而非只是缩短代码时使用它。
6. 通过类型、测试和仓库工具验证结果。

## 对有效空间进行建模

构造式领域建模描述程序支持什么，而不是从一个宽泛的表示开始，再不断增加无效组合列表。

- 使用必需字段的积类型表示一种有效状态，通常采用冻结的数据类。
- 使用 Python 3.12 `type` 别名定义的封闭联合来表示有意义的不同情况。
- 在 API、CLI、MCP、配置和持久化边界上，使用 Pydantic 模型和可辨识联合，以便对不可信值进行运行时验证或序列化。
- 对宽泛的边界数据结构只解析或分类一次，然后在内部传递范围更窄的领域值。不要让每个使用方都通过检查和类型转换重新确认该不变量。
- 使用显式的 `match` 分支处理封闭联合。当 `typing.assert_never` 能证明处理是穷尽的时，请使用它；同时避免使用会掩盖新增变体的兜底分支。
- 优先使用全函数，而不是偏函数。当某种情况在预期之内时，要么缩窄输入使其不可能发生，要么扩展返回联合，使调用方必须处理它。
- 当调用方能够以不同方式响应时，为可恢复的领域结果返回显式变体。仅将异常用于不变量被破坏、取消操作，以及不可预测的文件系统、网络、队列或数据库故障。
- 选择能够排除实际错误的最简单模型。不要添加仅用于包装的 ID、为每个操作都添加 Result 类型，或使用成本高于其清晰度收益的最高精度联合。

在缩窄 ORM 模型或兼容性架构之前，先追踪其写入方和序列化形式。存储层可以保持宽泛，而由解析器为核心工作流构造更安全的领域值。

## 优先使用函数，而非层次结构

- 从一个普通的、具有完整类型标注的函数开始。
- 当相关状态或操作结果需要一个名称时，将函数与 dataclass 配合使用。
- 当绑定行为比创建另一个对象更清晰时，使用回调、闭包或 `functools.partial`。
- 仅当行为确实会根据第一个参数的运行时类型而变化，并且开放注册是有意设计的扩展点时，才使用 `functools.singledispatch`。
- 对于真正可替换的行为，使用范围窄的 `Protocol`。不要使用仅包含属性的协议来描述内部结果数据；除非调用方确实需要结构化互操作性，否则应返回具体的冻结 dataclass。
- 当对象标识、内聚的可变状态、生命周期或资源所有权有此需要时，使用具体类。
- 仅当当前设计需要在运行时强制子类化或共享骨架行为时，才使用抽象基类。

不要用巧妙的函数式机制取代一种类层次结构。优先选择概念、隐藏规则和调用跳转最少的形式。

## 保持局部推理

- 当从上到下阅读最为清晰时，将一个直观的工作流放在一起。
- 仅当辅助函数的名称能够概括某项领域操作、隔离某个副作用或约束、消除有意义的重复，或者构成一个内聚且可测试的计算时，才提取辅助函数。
- 不要仅仅为了缩短函数而提取辅助函数。
- 如果一个类主要由私有方法构成，应将其视为一个信号：这些行为可能更适合放在显式的模块级函数中，对具有类型标注的值进行操作。
- 如果存在由 `_prepare_*`、`_resolve_*`、`_apply_*` 和 `_build_*` 调用组成的长链，应借此重新审视数据流，或为一个有实际意义的阶段对象命名。
- 避免使用只有一个实际实现的管理器、工厂、基类、适配器、策略和注册表抽象。
- 除非产品当前确实需要相应的扩展机制，否则应避免动态注册、元编程和由装饰器驱动的控制流。

如果提取辅助函数会让读者需要进行更多跳转，却不能增进理解，就应将逻辑保留在局部。

## 编写显式的 Python

- 根据值所承载的领域概念为其命名。
- 使用完整的类型标注和范围窄的类型。不要用 `Any`、宽泛的类型转换、试探性的 `getattr` 或无结构的字典来掩盖不确定性。
- 对内部领域值使用冻结 dataclass，在验证和序列化边界使用 Pydantic。Pydantic 模型并不天然就是内部状态表示的最佳选择。
- 优先使用直接迭代、上下文管理器、标准库构件，以及含义一目了然的简单推导式。
- 区分缺失与假值；仅当空值具有相同的预期含义时，才使用真值测试。
- 让异步工作、资源所有权、取消操作和清理过程清晰可见。
- 当不变量不成立或外部操作失败时，使用具体错误快速失败。不要使用异常来处理普通的领域分支，也不要添加静默回退和宽泛的异常处理。
- 注释应说明决策和约束，而不是操作机制。
- 优化经过测量确认的热点路径；不要为了假想的性能而牺牲可读性。

## 匹配请求的模式

### 编写

首先确立有效状态、结果和边界解析器。实现直接路径，使封闭变体得到穷尽处理，然后仅添加由实际变化、状态或边界所必需的抽象。

### 重构

保留可观察行为，将差异控制在聚焦范围内，并在行为存在风险时添加或更新回归测试。查找与可选字段耦合的状态字符串、重复验证、“不应该发生”的分支，以及通过异常携带的预期结果。仅当更小的构造式模型能够消除真实存在的不受支持状态时，才替换它们。不要机械地重写已经清晰的代码，不要将 I/O 失败转换为 Result 类型，也不要在追踪持久化数据的写入方之前重塑其结构。

### 审查

报告具体的可读性、抽象、类型、生命周期和领域模型风险。说明最小且切实可行的改进。询问所提出的类型究竟消除了哪种无效状态或未处理的义务；看似更强但没有具体收益的类型并不是改进。除非用户要求修复，否则不要编辑。

## 验证结果

运行能够证明更改有效的最小范围命令，然后根据风险扩大验证范围：

1. 针对已更改行为的聚焦测试。
2. 项目配置的格式化程序、代码检查器和类型检查器。当领域是封闭联合类型时，使用类型检查器证明使用方已进行穷尽处理。
3. 当边界受到影响时，运行仓库健康检查、打包、集成或完整门禁检查。

最终回复应首先说明结果和验证情况。仅当设计选择不明显或会对未来工作产生实质影响时，才予以说明。
