# Suede 销售赋能

Suede 销售赋能将经过验证的定位、证明材料和交易背景转化为销售代表可直接使用的演示文稿、单页资料、异议应对指南、演示和作战手册。每项资产都会将有来源支持的声明与建模得出的价值区分开来，并且在其受众和版本获批之前始终保持为草稿。

## 开始之前

**首先检查产品营销背景：**
如果 `.agents/product-marketing.md` 存在（或者 `.claude/product-marketing.md`，或在旧版设置中使用的旧文件名 `product-marketing-context.md`），请在提问前先阅读。使用其中的背景信息，只询问尚未涵盖或与当前任务具体相关的信息。

收集以下背景信息（如未提供则进行询问）：

1. **价值主张与差异化因素**
   - 你销售什么产品，面向哪些客户？
   - 你与下一个最佳替代方案相比有何不同？
   - 你能证明哪些成果？

2. **销售模式**
   - 你如何销售？（自助服务、内部销售、现场销售、混合模式）
   - 平均交易金额和销售周期长度
   - 参与购买决策的关键角色

3. **销售资料需求**
   - 你需要哪些具体资产？
   - 它们对应销售漏斗的哪个阶段？
   - 谁会使用它们？（AE、SDR、内部支持者、潜在客户）

4. **当前状况**
   - 目前有哪些材料？
   - 哪些方面运作良好，哪些方面不理想？
   - 销售代表最常要求什么？

## 核心原则

### 销售团队信任什么，就使用什么
让销售代表参与创建过程。使用他们的语言，而不是营销团队的语言。如果销售代表在发送演示文稿前还要重写一遍，那说明你写错了演示文稿。先用顶尖销售代表测试草稿。

### 针对具体情境，而非泛泛而谈
根据角色、交易阶段和使用场景进行定制。面向 CTO 的演示文稿应该与面向销售副总裁的演示文稿有所不同。用于会后跟进的单页资料，与用于贸易展会的单页资料服务于不同目的。

### 易于浏览胜过面面俱到
销售代表需要在 3 秒内获取信息，而不是 30 秒。使用加粗标题、简短要点和清晰的视觉层级。如果销售代表在通话过程中找不到答案，这份文档就失败了。

### 回归业务成果
每项声明都要与收入、效率或风险降低相关。没有“所以呢”，功能本身毫无意义。将“AI 驱动的分析”替换为“将报告时间缩短 80%”。

## 销售演示文稿 / 路演演示文稿

### 10-12 页框架

1. **当前世界的问题** — 买方当前正在承受的痛点
2. **问题的代价** — 不采取行动会付出什么代价（时间、金钱、风险）
3. **正在发生的转变** — 带来紧迫感的市场或技术变化
4. **你的方法** — 你如何以不同方式解决问题
5. **产品演示** — 3-4 个关键工作流，而不是功能导览
6. **证明要点** — 指标、客户 logo、分析师认可
7. **案例研究** — 讲好一个客户故事
8. **实施 / 时间线** — 他们如何从当前状态走向上线
9. **ROI / 价值** — 预期回报和回本周期
10. **定价概览** — 透明定价；如适用则采用分级定价
11. **下一步 / CTA** — 明确的行动和时间线

### 演示文稿原则

- **讲故事，而不是功能导览。** 每份演示文稿都要讲述一个故事：这个世界存在一个问题，有一种更好的方式，这是相关证明，这是实现目标的路径。
- **每页只讲一个观点。** 如果需要表达两个观点，就使用两页。
- **为演示而设计，而不是为阅读而设计。** 幻灯片应支持对话，而不是取代对话。文字要少，视觉效果要强。

### 按买家类型定制

| 买家 | 强调 | 弱化 |
|-------|-----------|--------------|
| 技术买家 | 架构、安全性、集成、API | ROI 计算、业务指标 |
| 经济买家 | ROI、回本周期、总成本、风险 | 技术细节、实施细节 |
| 内部拥护者 | 内部销售要点、快速见效、同行证明 | 深入的技术或财务细节 |

**完整的逐页指导**：参见 [references/deck-frameworks.md](references/deck-frameworks.md)

## 单页资料 / 会后留存资料

### 适用场景

- **会后总结** — 强化讨论内容，保持推进势头
- **帮助内部拥护者进行内部推介** — 为你的拥护者提供代表你进行销售所需的材料
- **展会宣传资料** — 快速介绍产品或服务，推动后续跟进

### 结构

1. **问题陈述** — 用一句话说明痛点
2. **你的解决方案** — 说明你做什么以及如何实现
3. **3 个差异化优势** — 说明你相比替代方案的优势
4. **证明点** — 一个有力的指标或客户引述
5. **CTA** — 明确的下一步行动及联系信息

### 设计原则

- 确保确实只有一页。最多只能有正反两面。
- 确保 30 秒内可快速浏览。使用醒目的标题、简短的项目符号和留白。
- 包含你的 logo、网站，以及具体的联系人（不要使用 info@）。
- 与你的品牌保持一致，但要简洁干净——这是销售工具，不是品牌宣传材料。

**按使用场景划分的模板**：参见 [references/one-pager-templates.md](references/one-pager-templates.md)

## 异议处理文档

### 异议类别

| 类别 | 示例 |
|----------|----------|
| 价格 | "太贵了"、"本季度没有预算"、"竞争对手更便宜" |
| 时机 | "现在不是合适的时机"、"也许下个季度吧"、"我们太忙，没时间实施" |
| 竞争 | "我们已经在使用 X 了"、"你们有什么不同？" |
| 决策权 | "我需要和老板确认一下"、"由委员会决定" |
| 现状 | "我们现有的方案运行得很好"、"没有坏就不要修" |
| 技术 | "能与 X 集成吗？"、"我们担心安全问题"、"能扩展吗？" |

### 回复框架

针对每个异议，记录：

1. **异议表述** — 销售人员实际听到的原话
2. **他们这样说的原因** — 话语背后的真实顾虑
3. **回复方式** — 如何回应并引导话题
4. **证明点** — 能够回应该顾虑的具体证据
5. **后续问题** — 推动对话继续进行

### 两种格式

- **实时通话速查表** — 包含异议、一句话回复和证明点。适合放在一个屏幕上。
- **详细文档** — 用于准备和培训，包含完整背景、沟通话术和角色扮演场景。

**完整的异议库**：参见 [references/objection-library.md](references/objection-library.md)

## ROI 计算器与价值主张

### 计算器设计

**输入**（潜在客户提供的当前状态指标）：
- 手动流程耗费的时间
- 当前工具成本
- 错误率或低效指标
- 团队规模

**计算**（你的价值计算公式）：
- 每周/月/年节省的时间
- 成本降低（工具、人员配置、错误）
- 收入影响（更快成交、更高转化率）

**输出**（潜在客户看到的内容）：
- 年度 ROI 百分比
- 回本周期（月）
- 3 年总价值

### 按角色划分的价值主张

| 角色 | 关注点 | 主打内容 |
|---------|-------------|-----------|
| CTO / VP Eng | 架构、规模、安全性、团队效率 | 技术优势、集成深度 |
| VP Sales | 销售管道、配额达成、销售代表生产力 | 收入影响、每位销售代表节省的时间 |
| CFO | 总成本、回本周期、风险 | ROI、成本降低、财务可预测性 |
| 终端用户 | 易用性、日常工作流程、学习曲线 | 节省的时间、消除的挫败感 |

### 实施选项

- **电子表格** — 构建速度最快，易于针对每笔交易进行定制。适合内部销售。
- **Web 工具** — 更加精致，能够获取潜在客户，扩展性更好。如果交易量较大，值得构建。
- **基于幻灯片** — 将 ROI 故事嵌入演示文稿中。适合面向高管的演示。

## 演示脚本与话术

### 脚本结构

1. **开场**（2 分钟）— 设定背景、介绍议程、确认本次通话的目标
2. **需求回顾**（3 分钟）— 总结你了解到的信息，确认优先事项
3. **解决方案演示**（15-20 分钟）— 演示 3-4 个与其痛点对应的关键工作流程
4. **互动环节** — 在演示过程中提问，而不只是最后提问
5. **结束**（5 分钟）— 总结价值，提出带有时间线的后续步骤

### 话术类型

| 类型 | 时长 | 重点 |
|------|----------|-------|
| 需求沟通 | 30 分钟 | 进行资格评估、了解痛点、梳理购买流程 |
| 首次演示 | 30-45 分钟 | 展示与其痛点相关的 3-4 个工作流程 |
| 技术深度演示 | 45-60 分钟 | 架构、安全性、集成、API |
| 高管概览 | 20-30 分钟 | 业务成果、ROI、战略一致性 |

### 核心原则

- **先了解需求，再进行演示。** 如果不了解对方的痛点，你就是在猜测哪些功能重要。
- **根据其使用场景进行定制。** 使用对方的术语、对方的数据（如果可能），以及对方的工作流程。
- **留出提问时间。** 如果潜在客户在演示过程中没有发言，这样的演示就无法促成成交。

**完整脚本模板**：参见 [references/demo-scripts.md](references/demo-scripts.md)

## 客户案例概要（销售格式）

### 销售案例与营销案例的区别

营销案例讲述一个故事。销售案例为销售代表提供可快速获取的佐证材料。内容应简短、聚焦成果，并添加标签以便检索。

### 结构

1. **客户概况** — 行业、公司规模、买方角色
2. **挑战** — 他们正在努力解决的问题（2-3 句话）
3. **解决方案** — 他们实施的内容（1-2 句话）
4. **成果** — 3 个具体指标（前后对比）
5. **引用语** — 一句客户原话
6. **标签** — 行业、使用场景、公司规模、角色

### 组织方式

组织案例研究，以便销售代表能够立即找到合适的案例：
- **按行业** — “给我展示一个医疗保健行业的案例”
- **按使用场景** — “给我展示一个使用我们的产品解决 X 的客户案例”
- **按公司规模** — “给我展示一个企业级案例”

## 提案模板

### 结构

1. **执行摘要** — 他们面临的挑战、你的解决方案、预期成果（最多 1 页）
2. **拟议解决方案** — 你将交付什么，以及如何对应他们的需求
3. **实施计划** — 时间表、里程碑、职责分工
4. **投入** — 定价、付款条款、包含的内容
5. **后续步骤** — 如何推进、决策时间表

### 定制指南

- 使用他们在需求沟通中采用的语言
- 提及他们明确说过的具体痛点
- 只包含相关的案例研究（相同行业或相同用例）
- 写出你沟通过的利益相关者姓名

### 常见错误

- **过长** — 如果超过 10 页，就没人会读。目标是 5-7 页。
- **过于泛泛** — 模板化的提案会让人觉得投入不足。至少要定制执行摘要。
- **把价格藏起来** — 不要让他们费力寻找。透明且自信地展示价格。

## 销售作战手册

### 作战手册应包含的内容

- **买方画像** — 你要向谁销售、他们的目标和痛点
- **资格认定标准** — BANT、MEDDIC 或你的框架
- **需求沟通问题** — 按主题组织，而不是写成脚本
- **异议处理** — 前 10 个异议及其回应
- **竞争定位** — 你如何赢过每个竞争对手
- **演示流程** — 针对每类角色的推荐顺序
- **邮件模板** — 跟进、提案、询问进展、结束跟进

### 何时构建

- **新产品发布** — 销售人员需要一个统一的事实来源
- **新市场细分** — 不同买方需要不同的方法
- **新员工上手** — 作战手册能显著缩短上手时间

### 保持持续更新

作战手册在不更新时就会失效。每季度进行审查，听取顶尖销售人员的意见，并移除任何过时内容。指定负责人 — 如果没有人负责，它就会逐渐腐朽。

## 买方角色卡片

### 卡片结构

| 字段 | 描述 |
|-------|-------------|
| 职能 / 职称 | 常见职称和汇报关系 |
| 目标 | 对他们而言，成功是什么样的 |
| 痛点 | 每天让他们感到沮丧的事情 |
| 主要异议 | 你会从该角色那里听到的 3-5 个异议 |
| 评估标准 | 他们如何评判解决方案 |
| 购买流程 | 他们在决策中的角色，以及会影响谁 |
| 信息切入点 | 最能引起共鸣的一句话 |

### 角色类型

- **经济买方** — 签字付款的人。关注 ROI 和风险。
- **技术买方** — 评估产品的人。关注功能和集成。
- **最终用户** — 每天使用产品的人。关注易用性和工作流适配度。
- **拥护者** — 在内部支持产品的人。需要足够的论据来替你进行推广。
- **阻碍者** — 反对购买的人。了解他们的顾虑，以便消除阻力。

## 特定任务问题

如果缺少上下文，请询问：

1. 你需要哪些销售资料？（演示文稿、单页资料、异议处理文档等）
2. 谁会使用这些资料？（AE、SDR、内部支持者、潜在客户）
3. 这些资料面向哪个销售阶段？（拓客、需求挖掘、演示、谈判、成交）
4. 目标用户画像是什么？（职位、资历、部门）
5. 你最常听到的 3 个主要异议是什么？

## 边界

- 未经最终受众、声明内容和版本的批准，不得发布、发送、演示或上传销售资料。
- 不得捏造客户引言、徽标、基准数据、节省金额、集成或产品能力；为每个证明点注明来源，并标注建模的 ROI。
- 不得决定定价、合同条款、折扣、保证或法律承诺。将这些决策交由负责的所有者处理。

## 路由

- 使用 `suede-product-marketing` 获取已批准的定位和证明背景。
- 使用 `suede-competitors` 获取比较信息和竞争战卡证据。
- 使用 `suede-pricing` 处理定价和套餐决策。
- 使用 `suede-revops` 处理销售管道阶段、路由和交易台运营。
