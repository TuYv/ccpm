# Suede 销售赋能

Suede 销售赋能将经过验证的定位、证明材料和交易背景转化为销售代表可直接使用的演示文稿、单页材料、异议处理指南、演示和行动手册。每项材料都会区分有来源依据的主张与模型估算价值，并且在受众和版本获得批准之前始终保持草稿状态。

## 开始之前

**首先检查产品营销背景信息：**
如果 `.agents/product-marketing.md` 存在（或 `.claude/product-marketing.md`，或者在较旧的设置中使用的旧文件名 `product-marketing-context.md`），请在提问前阅读它。使用其中的背景信息，只询问尚未涵盖或本任务特有的信息。

收集以下背景信息（如未提供，请询问）：

1. **价值主张与差异化优势**
   - 你销售什么，目标客户是谁？
   - 与次优替代方案相比，你有何不同？
   - 你能证明哪些成效？

2. **销售模式**
   - 你如何销售？（自助销售、内部销售、现场销售、混合模式）
   - 平均交易规模和销售周期长度
   - 参与购买决策的关键角色

3. **销售材料需求**
   - 你具体需要哪些材料？
   - 它们用于销售漏斗的哪个阶段？
   - 谁会使用它们？（AE、SDR、内部支持者、潜在客户）

4. **当前状态**
   - 目前有哪些材料？
   - 哪些有效，哪些无效？
   - 销售代表最常要求提供什么？

## 核心原则

### 销售团队只使用他们信任的材料
让销售代表参与材料创作。使用他们的语言，而不是营销团队的语言。如果销售代表在发送你的演示文稿之前需要重写它，那么你写的就是错误的演示文稿。首先让业绩最佳的销售人员测试草稿。

### 针对具体情境，而非泛泛而谈
根据角色、交易阶段和使用场景进行定制。面向 CTO 的演示文稿应与面向销售副总裁的演示文稿有所不同。用于会后跟进的单页材料与用于贸易展会的单页材料用途不同。

### 易于浏览胜过面面俱到
销售代表需要在 3 秒内而不是 30 秒内找到信息。使用粗体标题、简短要点和清晰的视觉层级。如果销售代表无法在通话过程中找到答案，这份文档就失败了。

### 回归业务成果
每项主张都应与收入、效率或风险降低相关联。功能如果没有回答“那又怎样”，就毫无意义。将“AI 驱动的分析”替换为“将报告时间缩短 80%”。

## 销售演示文稿 / 推介演示文稿

### 10-12 页幻灯片框架

1. **当前现状中的问题** — 买家如今正在承受的痛点
2. **问题的成本** — 不采取行动的代价（时间、金钱、风险）
3. **正在发生的转变** — 营造紧迫感的市场或技术变化
4. **你的方法** — 你如何以不同的方式解决问题
5. **产品演示** — 3-4 个关键工作流，而不是功能导览
6. **证明材料** — 指标、客户徽标、分析机构认可
7. **客户案例** — 讲好一个客户故事
8. **实施 / 时间表** — 客户如何从当前状态推进至正式上线
9. **ROI / 价值** — 预期回报和投资回收期
10. **定价概览** — 保持透明，如适用则采用分层定价
11. **后续步骤 / CTA** — 包含时间表的明确行动

### 演示文稿原则

- **讲述故事，而不是罗列功能。** 每份演示文稿都应讲述一个故事：当前世界存在一个问题，有一种更好的解决方式，这里有相关证明，而这就是实现它的方法。
- **每页只表达一个观点。** 如果需要表达两个观点，就使用两页。
- **为演示而设计，而不是为阅读而设计。** 幻灯片用于辅助对话，而不是取代对话。使用最少的文字和具有冲击力的视觉元素。

### 按买家类型定制

| 买家 | 重点强调 | 弱化 |
|-------|-----------|--------------|
| 技术买家 | 架构、安全性、集成、API | ROI 计算、业务指标 |
| 经济型买家 | ROI、回收期、总成本、风险 | 技术细节、实施细节 |
| 内部支持者 | 内部推销要点、速赢机会、同业证明 | 深入的技术或财务细节 |

**有关逐页幻灯片的完整指南**：请参阅 [references/deck-frameworks.md](references/deck-frameworks.md)

## 单页资料 / 会后留存资料

### 何时使用

- **会后回顾** — 强化讨论过的内容，保持推进势头
- **帮助内部支持者进行内部推销** — 为内部支持者提供替你推销所需的材料
- **展会宣传单** — 快速介绍并推动后续跟进

### 结构

1. **问题陈述** — 用一句话概括痛点
2. **你的解决方案** — 你提供什么，以及如何实现
3. **3 个差异化优势** — 为什么选择你而不是其他方案
4. **证明材料** — 一项有力的指标或客户引言
5. **行动号召** — 明确的下一步行动及联系信息

### 设计原则

- 严格控制在一页。仅正面，最多正反两面。
- 可在 30 秒内快速浏览。使用粗体标题、简短的项目符号和留白。
- 包含你的徽标、网站和具体联系人（不要使用 info@）。
- 与你的品牌保持一致，但要简洁清晰——这是销售工具，而不是品牌宣传材料。

**有关按使用场景分类的模板**：请参阅 [references/one-pager-templates.md](references/one-pager-templates.md)

## 异议处理文档

### 异议类别

| 类别 | 示例 |
|----------|----------|
| 价格 | “太贵了”、“本季度没有预算”、“竞争对手更便宜” |
| 时机 | “现在时机不对”、“也许下个季度再说”、“太忙了，没时间实施” |
| 竞争 | “我们已经在使用 X”、“你们有什么不同？” |
| 决策权 | “我需要和老板确认一下”、“由委员会决定” |
| 现状 | “我们现在用的就挺好”、“没坏就别修” |
| 技术 | “它能与 X 集成吗？”、“有安全方面的顾虑”、“它能扩展吗？” |

### 响应框架

针对每项异议，记录：

1. **异议表述** — 销售代表听到的原话
2. **提出异议的原因** — 话语背后的真实顾虑
3. **响应方式** — 如何表示理解并引导话题
4. **证明材料** — 能够消除顾虑的具体证据
5. **跟进问题** — 推动对话继续向前

### 两种格式

- 用于实时通话的**快速参考表**——异议、单句回应、证明材料。可在一个屏幕内完整显示。
- 用于准备和培训的**详细文档**——完整背景、话术和角色扮演场景。

**有关完整的异议库**：请参阅 [references/objection-library.md](references/objection-library.md)

## ROI 计算器和价值主张

### 计算器设计

**输入项**（由潜在客户提供的当前状态指标）：
- 花费在手动流程上的时间
- 当前工具成本
- 错误率或效率低下指标
- 团队规模

**计算项**（你的价值计算公式）：
- 每周/每月/每年节省的时间
- 成本降低（工具、人员、错误）
- 收入影响（更快成交、更高转化率）

**输出**（潜在客户看到的内容）：
- 年度 ROI 百分比
- 以月为单位的投资回收期
- 3 年总价值

### 按角色划分的价值主张

| 角色 | 关注点 | 主打内容 |
|---------|-------------|-----------|
| CTO / 工程副总裁 | 架构、规模、安全性、团队效率 | 技术优势、集成深度 |
| 销售副总裁 | 销售管道、配额达成率、销售代表生产力 | 收入影响、每位销售代表节省的时间 |
| CFO | 总成本、投资回收期、风险 | ROI、成本降低、财务可预测性 |
| 最终用户 | 易用性、日常工作流程、学习曲线 | 节省时间、消除挫败感 |

### 实现方案

默认采用**基于幻灯片的方式**——将 ROI 故事融入销售代表本来就会
演示的幻灯片中。当潜在客户提供自己的输入数据并希望自行
修改时，改用**电子表格**；只有当交易量足以证明其合理性时，才构建**Web 工具**。

## 演示脚本与话术

### 脚本结构

1. **开场**（2 分钟）——设定背景、说明议程、确认本次通话的目标
2. **需求探索回顾**（3 分钟）——总结已了解的信息、确认优先事项
3. **解决方案演示**（15-20 分钟）——展示与其痛点对应的 3-4 个关键工作流程
4. **互动环节**——在演示过程中提问，而不是只在最后提问
5. **结束**（5 分钟）——总结价值、提出包含时间表的后续步骤

### 话术类型

| 类型 | 时长 | 重点 |
|------|----------|-------|
| 需求探索电话 | 30 分钟 | 筛选潜在客户、了解痛点、梳理采购流程 |
| 首次演示 | 30-45 分钟 | 展示与其痛点相关的 3-4 个工作流程 |
| 技术深度讲解 | 45-60 分钟 | 架构、安全性、集成、API |
| 高管概览 | 20-30 分钟 | 业务成果、ROI、战略一致性 |

### 关键原则

- **先进行需求探索，再做演示。** 如果不了解他们的痛点，你就只能猜测哪些功能对他们重要。
- **针对他们的使用场景进行定制。** 使用他们的术语、他们的数据（如果可能）和他们的工作流程。
- **为提问留出时间。** 潜在客户全程不开口的演示，无法促成交易。

**完整脚本模板**：请参阅 [references/demo-scripts.md](references/demo-scripts.md)

## 案例研究简报（销售版）

### 销售案例研究有何不同

营销案例研究用于讲述故事。销售案例研究则为销售代表提供可快速获取的佐证。内容应简短、聚焦成果，并添加标签以便检索。

### 结构

1. **客户概况**——行业、公司规模、采购者角色
2. **挑战**——他们面临的问题（2-3 句话）
3. **解决方案**——他们实施了什么（1-2 句话）
4. **成果**——3 项具体指标（实施前/实施后）
5. **引用语**——客户的一句话
6. **标签**——行业、使用场景、公司规模、角色

### 组织方式

合理组织案例研究，让销售代表能够立即找到合适的案例：
- **按行业**——“给我看一个医疗保健行业的案例研究”
- **按使用场景**——“给我看一个使用我们的产品解决 X 问题的客户”
- **按公司规模**——“给我看一个大型企业的示例”

## 提案模板

### 结构

1. **执行摘要** — 他们面临的挑战、你的解决方案、预期成果（最多 1 页）
2. **建议的解决方案** — 你将交付的内容，并与他们的需求一一对应
3. **实施计划** — 时间线、里程碑、职责分工
4. **投入费用** — 定价、付款条款、包含的内容
5. **后续步骤** — 如何推进、决策时间线

### 定制指南

- 沿用他们在需求沟通中的语言
- 提及他们谈到的具体痛点
- 仅包含相关的案例研究（相同行业或用例）
- 写明与你沟通过的利益相关者姓名

### 常见错误

- **篇幅过长** — 如果超过 10 页，就不会有人读。目标应为 5-7 页。
- **过于宽泛** — 模板化的提案会给人敷衍的印象。至少要定制执行摘要。
- **隐藏价格** — 不要让他们费力寻找价格。应保持透明和自信。

## 销售作战手册

### 作战手册应包含的内容

- **买家画像** — 你的销售对象是谁，他们的目标和痛点是什么
- **资格评估标准** — BANT、MEDDIC 或你自己的框架
- **需求探索问题** — 按主题组织，而不是照本宣科的脚本
- **异议处理** — 最常见的 10 个异议及应对方式
- **竞争定位** — 面对每个竞争对手时，你如何胜出
- **演示流程** — 针对每类角色建议采用的演示顺序
- **电子邮件模板** — 跟进、提案、确认进展、终止跟进

### 何时构建

- **新产品发布** — 销售代表需要统一、权威的信息来源
- **进入新的细分市场** — 不同的买家需要不同的方法
- **新员工上手** — 作战手册可以显著缩短上手时间

### 持续维护与更新

每季度审查一次，征求优秀销售代表的意见，删除所有过时内容，并指定一名负责人。

## 买家角色卡片

### 卡片结构

| 字段 | 描述 |
|-------|-------------|
| 职位 / 头衔 | 常见职位名称和汇报关系 |
| 目标 | 对他们而言，成功是什么样的 |
| 痛点 | 每天令他们感到困扰的事情 |
| 主要异议 | 你会从该角色那里听到的 3-5 个异议 |
| 评估标准 | 他们如何评判解决方案 |
| 采购流程 | 他们在决策中的角色以及他们会影响谁 |
| 信息传达角度 | 最能引起他们共鸣的一句话 |

### 角色类型

- **经济决策者** — 签字付款的人。关注投资回报率和风险。
- **技术决策者** — 评估产品的人。关注功能和集成。
- **最终用户** — 每天使用产品的人。关注易用性和工作流程的契合度。
- **内部支持者** — 在组织内部倡导采购。需要有说服力的材料来帮你推销。
- **阻碍者** — 反对采购的人。了解他们的顾虑，以消除阻力。

## 输出格式

针对每种资料类型交付合适的格式：

| 资料 | 交付成果 |
|-------|-------------|
| 销售演示文稿 | 逐页大纲，包括标题、正文文案和演讲者备注 |
| 单页材料 | 完整文案及版式指导（视觉层级、各部分） |
| 异议处理文档 | 表格格式：异议、回应、佐证、后续跟进 |
| 演示脚本 | 按场景编排，包括时间安排、讲解话术和互动节点 |
| 投资回报率计算器 | 输入字段、公式、输出展示及示例数据 |
| 作战手册 | 包含目录和各章节的结构化文档 |
| 角色卡片 | 每个角色采用单页卡片格式 |
| 提案 | 按章节编写的文案及定制说明 |

交付材料中的每个论据和每个 ROI 数字都必须带有行内标签：`[source: named customer / study / internal report + date]` 或 `[modeled — assumptions: the inputs used]`。任何未加标签的数字都会阻碍交付——在材料发出前为其添加标签，或将其删除。销售演示文稿交付物采用以下单元，并针对上述 11 张幻灯片逐一重复：

```markdown
### Slide N — [slide name]
**Headline:** [the single idea, written as a sentence]
**Body copy:** [on-slide text, minimal]
**Speaker notes:** [what the rep says out loud, not a re-read of the slide]
**Visual:** [chart / screenshot / logo wall / none]
**Proof:** [source: …] or [modeled — assumptions: …] for every number above
```

## 边界

- 未经最终受众、声明和版本审批，不得发布、发送、展示或上传销售材料。
- 不得捏造客户引述、徽标、基准、节省金额、集成或产品功能；应为每项论据注明来源，并标明建模得出的 ROI。
- 不得决定定价、合同条款、折扣、保证或法律承诺。应将这些决策转交给相应的责任人。

## 路由

- 使用 `suede-product-marketing` 获取经批准的定位和论据背景。
- 使用 `suede-competitors` 获取对比和竞争作战卡证据。
- 使用 `suede-pricing` 处理定价和套餐决策。
- 使用 `suede-revops` 处理销售管道阶段、路由和交易支持运营。
