# 使用子代理实现

将编排与实现所有权分离：控制器负责调度，每个独立工作项由一个实现子代理负责直至完成。

## 流程

1. 阅读仓库说明，并检查当前分支和工作树。保留无关更改。当无法从当前状态安全地产生任务范围内的提交时，在委派前停止。
2. 解析并阅读已安装的 `implement` 技能。将其视为必需依赖。如果不可用，在进行任何更改前停止并报告缺失的依赖；绝不要凭记忆复现其流程。
3. 构建按依赖关系排序的队列。将未拆分的请求及其检查清单保留在同一个工作项中；只有在所提供的各项无法通过相互独立且保持行为不变的提交进行验证时，才将它们分组。
4. 一次处理一个工作项。在每个工作项开始前记录 `HEAD` 和工作树的既有状态；接受前一个工作项后再开始下一个。
5. 选择可移植的 **Solver** 角色，并将其映射到运行时具备实现能力的子代理类型。当环境提供这些信息时，记录可移植角色和实际运行时选择。生成一个所有者。控制器不得实现该工作项的任何部分。如果实现槽位暂时不可用，则等待容量。如果无法启动子代理，则停止并报告阻塞因素，不得退回由控制器实现。
6. 向该所有者提供一个决策完备的数据包，其中包含：
   - 确切的工单或计划任务及其验收标准；
   - 相关规范和仓库说明；
   - 在当前分支上对该工作项的排他所有权；
   - 必须保留的工作树既有状态；
   - 调用已安装的 `implement` 技能的指令；以及
   - 返回提交、已安装的 `implement` 技能当前完成契约所要求的证据，以及任何未解决阻塞因素的指令。
7. 等待该所有者完成后再开始另一个工作项。不得将其实现拆分给多个代理。如果结果不完整、工作树不干净、未提交，或未通过必需的检查，则将证据返回给同一所有者。如果其无法在所提供的契约内解决实质性阻塞因素，则停止。
8. 在推进之前独立验收该工作项；所有者的报告不构成验收证据。验证：
   - 验证 `HEAD` 至少前进了一个任务范围内的提交；
   - 检查从记录的 `HEAD` 到当前 `HEAD` 的完整提交范围和差异，确认符合该工作项的验收标准和范围；
   - 重新运行用户和仓库针对该工作项要求的验证；
   - 确认返回的证据满足已安装的 `implement` 技能当前的完成契约；以及
   - 验证相对于记录的既有状态，任务所有的差异为空。
9. 每次修复后重复第 8 步。接受最后一个工作项后，运行用户或仓库要求的任何最终验证。如果后续操作更改了文件，则将其返回给所有者进行验证和提交。

## 所有权边界

- 除非用户明确授予其他所有者且仓库说明允许，否则将远程变更保留给控制器处理。
- 对于审查修复和后续检查，重新使用负责该项的子代理；不要为同一事项再次承担上下文传递成本。
- 仅当负责方确实需要独立发现时，才使用只读辅助代理。它们不得编辑、提交，也不得替代实现负责人。
- 绝不要将其他事项的编辑或用户预先存在的更改吸收到当前负责方的提交中。

## 完成门槛

仅当每个排队事项都拥有针对任务范围的、经过审查和验证的提交，最终工作区与记录的预先存在状态一致，并且不存在负责人报告的阻塞因素时，才可完成。报告事项到提交的映射以及最终验证结果。否则应以阻塞状态结束，并指出第一个未完成的门槛。
