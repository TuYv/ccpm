# 使用子代理实现

将编排与实现所有权分离：控制器负责调度，每个独立工作项由一个实现子代理负责直至完成。将无法验证的变更放在同一个工作项中，在继续推进前接受其任务范围内的提交；如果验收失败，将验收证据返回给同一所有者，而不是由控制器修复或重新分配。

## 检查前置条件

评审模式不依赖外部 skill。实现模式要求使用 [Matt Pocock's skill set](https://github.com/mattpocock/skills) 中的 `implement` skill，该 skill 未随本仓库一同提供。使用 `npx skills add mattpocock/skills` 安装，并根据当前上游契约选择 `implement`、`tdd` 和 `code-review`。绝不要隐式安装。

## 选择模式

- 仅当用户要求在不运行所提供编排的情况下对其进行评估时，使用 `review`。
- 当用户要求执行所提供的 ticket 或计划任务时，使用 `implement`。

## 评审流程

1. 仅检查用户允许访问的仓库和所提供的编排状态。不要启动子代理、编辑文件、创建提交或联系远程服务。
2. 评估队列原子性、依赖顺序、实现所有权、任务范围内的验收、修复所有权以及控制器的变更边界。将已经验收的工作项视为已完成，不要再次分配。
3. 报告下一步编排行动，或说明无需采取行动，并提供证据及任何尚未解决的验收缺口。在实现流程开始前停止。

## 实现流程

1. 阅读仓库说明，检查当前分支和工作树。保留无关变更。当无法从当前状态安全地产生任务范围内的提交时，在委派前停止。
2. 解析并阅读已安装的 `implement` skill。将其视为必需依赖。如果不可用，在进行任何变更前停止。报告它来自 `mattpocock/skills`，提供 `npx skills add mattpocock/skills`，并说明用户必须选择 `implement`、`tdd` 和 `code-review`。绝不要隐式安装这些 skill，也不要凭记忆复现该流程。
3. 构建按依赖排序的队列。将未拆分的请求及其检查清单保留在同一个工作项中；仅当所提供的工作项无法通过彼此独立且保持行为的提交进行验证时，才将其分组。
4. 一次处理一个工作项。在每个工作项开始前记录 `HEAD` 和工作树的预存状态；开始下一个工作项前，先验收前一个工作项。
5. 选择可移植的 **Solver** 角色，并将其映射到运行时具备实现能力的子代理类型。当环境提供相关信息时，记录可移植角色和实际运行时选择。启动一个所有者。控制器不得实现该工作项的任何部分。如果实现槽位暂时不可用，等待容量。如果无法启动子代理，停止并报告阻塞原因，不要退回到由控制器实现。
6. 向该所有者提供一个决策完备的数据包，其中包含：
   - 确切的 ticket 或计划任务及其验收标准；
   - 相关规范和仓库说明；
   - 在当前分支上对该工作项的独占所有权；
   - 必须保留的工作树预存状态；
   - 调用已安装 `implement` skill 的指令；以及
   - 返回提交、已安装 `implement` skill 当前完成契约所要求的证据，以及任何尚未解决的阻塞原因的指令。
7. 等待该所有者完成后再开始另一个工作项。不要将其实现拆分给多个代理。如果结果不完整、工作树不干净、未提交或未通过必需检查，将证据返回给同一所有者。对于其无法在所提供契约内解决的实质性阻塞，停止。
8. 在推进前独立验收该工作项；所有者的报告不构成验收证据。验证：
   - 验证 `HEAD` 至少前进了一个任务范围内的提交；
   - 检查从记录的 `HEAD` 到当前 `HEAD` 的完整提交范围和差异，确认符合该工作项的验收标准和范围；
   - 检查所返回的命令、完整结果、测试版本，以及相关输入和环境标识；
   - 仅当完整证据显示成功、相关环境未发生变化，并且用户或仓库未要求重新独立运行时，才复用所请求的检查。同时还必须满足以下任一条件：测试版本等于当前 `HEAD`，或当前 `HEAD` 是测试版本的后代，且经独立检查的差异未改变该检查的相关输入；
   - 当证据缺失、失败、关联到无法解释的旧版本、受相关输入变更影响，或存在明确的新鲜度或独立运行要求时，重新运行每项受影响的检查；
   - 确认所返回的证据满足已安装 `implement` skill 当前的完成契约；以及
   - 验证相对于记录的预存状态，任务所有者负责的差异为空。
9. 每次修复后，重复独立的提交和差异检查，然后根据第 8 步重新评估证据。仅复用相关输入和环境在所检查的后代差异中保持不变的检查；重新运行受影响的检查。无法解释的旧版本证据视为过期证据。在最后一个工作项验收通过后，运行用户或仓库要求的任何最终验证。如果后续操作修改了文件，将其返回给所有者进行验证和提交。

## 所有权边界

- 除非用户明确授予不同的所有者且仓库指令允许，否则将远程变更保留在控制器中。
- 对于审查修复和后续检查，复用负责该项的子代理；不要为同一项重复承担上下文传递成本。
- 仅当所有者确实需要独立发现时，才使用只读辅助代理。它们不会编辑、提交或替代实现所有者。
- 永远不要将其他项的编辑或预先存在的用户变更吸收到当前所有者的提交中。

## 完成门槛

在 `review` 中，只有在报告了非变更评估、其证据以及任何验收缺口后才能完成，且不得开始实现。在
`implement` 中，只有当每个排队项目都具备任务范围内、经过审查并验证的提交，最终工作树与记录的预先存在状态一致，并且没有所有者报告的阻塞项时，才能完成。报告项目到提交的映射以及最终验证结果。否则以阻塞状态完成，并指出第一个未完成的门槛。
