# 使用子代理实施

将编排职责与实施所有权分离：控制器负责任务调度，每个独立工作项由一个实施子代理全程负责直至完成。

## 流程

1. 阅读仓库说明，并检查当前分支和工作树。保留无关更改。如果根据当前状态无法安全地产生限定于任务范围的提交，则在委派前停止。
2. 查找并阅读已安装的 `implement` skill。将其视为必需依赖项。如果它不可用，则在进行任何更改前停止并报告缺失的依赖项；切勿凭记忆复现其流程。
3. 根据提供的工单或计划任务构建工作队列：
   - 保留明确的边界和依赖顺序；
   - 将未拆分的实施请求视为一个工作项；
   - 将清单步骤保留在其所属的工作项内；并且
   - 仅当所提供的项目无法安全地产生彼此独立且保持行为不变的提交时，才将其分组。
4. 在当前分支上按顺序处理队列。处理每个工作项前，记录 `HEAD`，并要求前一个工作项已提交，且相对于所记录的预先存在的工作树状态，仅包含归属于该任务的干净差异。
5. 为下一个工作项选择可移植的 **Solver** 角色，并将其映射到运行时中具备实施能力的子代理类型。如果环境会公开相关信息，则记录可移植角色和实际的运行时选择。启动一个负责人。控制器不得实施该工作项的任何部分。如果实施槽位暂时不可用，则等待可用容量。如果无法启动子代理，则停止并报告阻塞问题，而不是退回由控制器实施。
6. 向负责人提供一份决策完备的信息包，其中包含：
   - 确切的工单或计划任务及其验收标准；
   - 相关规范和仓库说明；
   - 当前分支上该工作项的独占所有权；
   - 必须保留的预先存在的工作树状态；
   - 调用已安装的 `implement` skill 的指令；以及
   - 返回提交、已安装的 `implement` skill 当前完成契约所要求的证据，以及任何未解决阻塞问题的指令。
7. 等待该负责人完成后，再启动另一个负责人。不要将其实施工作拆分给其他代理。当其结果不完整、工作树不干净、未提交或未通过必需检查时，将相关证据发回给同一负责人，并让其修复自己的工作项。如果负责人无法在所提供的契约范围内解决实质性阻塞问题，则停止。
8. 在继续推进前，独立验收该工作项。将负责人的报告视为声明，而不是验收证据：
   - 验证 `HEAD` 已通过至少一个限定于任务范围的提交向前推进；
   - 检查从所记录的 `HEAD` 到当前 `HEAD` 的完整提交范围和差异，确认其符合工作项的验收标准和范围；
   - 重新运行用户和仓库针对该工作项要求的验证；
   - 确认返回的证据满足已安装的 `implement` skill 当前的完成契约；并且
   - 验证相对于所记录的预先存在状态，归属于该任务的差异为空。
9. 将每项未通过的验收检查发回给同一负责人，然后重复第 8 步。仅在验收通过后，才开始下一个工作项。最后一个工作项完成后，运行用户或仓库要求但各工作项级验收尚未覆盖的所有最终验证。如果后续操作更改了文件，则将这些更改交回其所属的子代理进行验证和提交。

## 所有权边界

- 除非用户明确指定了其他所有者且仓库说明允许，否则远程变更操作应由控制器负责。
- 对审查修复和后续检查复用原所有者子代理；不要为同一事项再次付出上下文传递成本。
- 仅当所有者确实需要独立调查时，才使用只读辅助代理。它们不编辑、不提交，也不取代实现所有者。
- 绝不要将其他事项的编辑或用户预先存在的更改纳入当前所有者的提交。

## 完成门禁

仅当队列中的每个事项都具有任务范围明确、经过审查和验证的提交，最终工作树与记录的预先存在状态一致，且所有者报告的阻塞均已消除时，方可完成。报告事项与提交的映射关系以及最终验证结果。否则，以阻塞状态结束，并指出第一个未满足的门禁。

## RED/GREEN 代理场景

对于每个场景，通过省略相关规则来建立 RED，然后恢复该技能并要求得到 GREEN 结果。

1. 提供的两个工单涉及不同模块，且第二个依赖第一个。RED 在控制器中实现，或同时启动两个代理。GREEN 使用 `implement` 将第一个工单交给一个 Solver 所有者，独立验收其提交，然后在更新后的分支上将第二个工单交给一个新的所有者。
2. 新颖案例：第一个所有者报告成功，但控制器检查发现已提交的差异中缺少一项必需的断言。RED 信任该报告或开始下一个工作项。GREEN 将未通过验收的证据返回给同一个所有者，然后重新检查修复并再次运行验证。
3. 缺少依赖项的案例：未安装 `implement`。RED 复制其记忆中的行为，或让控制器自行实现。GREEN 在发生变更前停止，并报告所需的依赖项。
4. 过度应用反例：一个工单包含四个共享同一接缝的 TDD 检查清单步骤。GREEN 将整个工单分配给一个所有者，而不是创建四个代理。
5. 耦合反例：两个计划任务必须更改同一个原子化 schema，且无法各自独立通过验证。GREEN 将它们归为一个工作项并交给一个所有者，同时记录为何拆分提交会带来风险。
