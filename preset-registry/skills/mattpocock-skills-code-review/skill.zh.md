对 `HEAD` 与用户提供的固定点之间的差异进行双轴审查：

- **标准**：代码是否符合此仓库中记录的编码标准？
- **规格说明**：代码是否忠实实现了最初的议题 / 规格说明？

两个审查轴会作为**并行子代理**运行，以免相互污染上下文，然后此技能会汇总它们的发现。

议题跟踪器应该已经提供给你。如果缺少 `docs/agents/issue-tracker.md`，请让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所指定的任何内容都是固定点（提交 SHA、分支名称、标签、`main`、`HEAD~5` 等）。如果用户没有指定，请向其询问。

只记录一次差异命令：`git diff <fixed-point>...HEAD`（使用三点语法，以便与合并基点进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`），且差异非空。错误的引用或空差异应在此处导致失败，而不是在两个并行子代理内部失败。

### 2. 确定规格说明来源

按以下顺序查找最初的规格说明：

1. 提交消息中的议题引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能匹配的规格说明文件。
4. 如果什么都找不到，请询问用户规格说明在哪里。如果用户表示不存在规格说明，**规格说明**子代理将跳过审查并报告“没有可用的规格说明”。

### 3. 确定标准来源

仓库中记录代码应如何编写的任何内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库记录的内容外，标准轴始终包含以下**坏味道基线**：一组固定的 Fowler 代码坏味道（《_重构_》第 3 章），即使仓库中没有记录任何标准也同样适用。它受以下两条规则约束：

- **以仓库为准。** 仓库中记录的标准始终优先；如果仓库标准认可某种会被基线标记的做法，则不报告该坏味道。
- **始终需要判断。** 每种坏味道都是带标签的启发式判断（“可能存在依恋情结”），而不是硬性违规。与此处的其他标准一样，跳过工具已经强制执行的任何内容。

每种坏味道均按*它是什么* → *如何修复*的形式描述；请将其与差异进行比对：

- **神秘命名**：函数、变量或类型的名称未能揭示其作用或所保存的内容。→ 对其重命名；如果无法找到一个如实表达含义的名称，则说明设计本身含糊不清。
- **重复代码**：相同的逻辑结构出现在变更中的多个差异块或文件内。→ 提取共用结构，并在两处调用它。
- **依恋情结**：某个方法访问另一个对象的数据多于访问自身的数据。→ 将该方法移到它所依恋的数据上。
- **数据泥团**：相同的几个字段或参数总是一起传递（意味着一个类型正等待诞生）。→ 将它们捆绑为一个类型，并传递该类型。
- **基本类型偏执**：使用基本类型或字符串来表示一个本应拥有自身类型的领域概念。→ 为该概念创建一个专用的小型类型。
- **重复的条件逻辑**：针对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 使用多态替代，或者让两处共用同一个映射。
- **霰弹式修改**：一个逻辑变更迫使差异中的许多文件出现零散修改。→ 将共同变化的内容集中到一个模块中。
- **发散式变化**：一个文件或模块因多个互不相关的原因而被修改。→ 将其拆分，使每个模块只因一个原因而变化。
- **夸夸其谈的通用性**：为规格说明中不存在的需求添加了抽象、参数或钩子。→ 删除它；将其重新内联，直到出现真实需求。
- **消息链**：调用方不应依赖的冗长 `a.b().c().d()` 导航链。→ 通过第一个对象上的单个方法隐藏这段遍历过程。
- **中间人**：一个类或函数主要只是将调用委派给其他对象。→ 移除它，直接调用真正的目标。
- **被拒绝的遗赠**：子类或实现类忽略或覆盖了所继承内容中的大部分。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

**标准子代理提示词**应包含：

- 完整的 diff 命令和提交列表。
- 你在第 3 步中找到的标准来源文件列表，**以及第 3 步中的代码异味基线**，二者均需完整粘贴（子代理无法通过其他方式访问这些内容）。
- 任务说明：“按相关文件/hunk 报告：(a) diff 中每一处违反已记录标准的地方：引用对应标准（文件 + 规则）；以及 (b) 你发现的任何基线代码异味：指出其名称并引用对应 hunk。区分明确违规与判断性问题：违反已记录标准可以认定为明确违规，但基线代码异味始终属于判断性问题，并且代码库中已记录的标准优先于基线。跳过所有由工具强制执行的内容。不超过 400 词。”

**规范子代理提示词**应包含：

- diff 命令和提交列表。
- 规范的路径或获取到的规范内容。
- 任务说明：“报告：(a) 规范要求但缺失或仅部分实现的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现、但实现方式可能有误的需求。每项发现都要引用对应的规范原文。不超过 400 词。”

如果缺少规范，则跳过规范子代理，并在最终报告中注明这一点。

### 5. 汇总

将两份报告分别放在 `## Standards` 和 `## Spec` 标题下，保持原文不变或仅做轻微整理。**不要**合并发现或重新排序，因为这两个维度是刻意分开的（参见 _为什么分成两个维度_）。

最后以一行摘要结尾：给出每个维度的发现总数，以及每个维度中最严重的问题（如有）。不要跨维度选出一个最严重的问题：这种重新排序正是采用分离方式所要避免的。

## 为什么分成两个维度

一项变更可能通过一个维度，却未通过另一个维度：

- 代码遵循了所有标准，但实现了错误的功能 → **标准通过，规范失败。**
- 代码完全实现了 issue 所要求的内容，但破坏了项目约定 → **规范通过，标准失败。**

分开报告可避免一个维度掩盖另一个维度的问题。
