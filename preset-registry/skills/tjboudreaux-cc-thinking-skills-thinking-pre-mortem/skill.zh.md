# 事前剖析

**核心规则：** 预见性回顾胜过“哪里可能出问题？”。假设计划已经失败（过去时态），生成具体的失败路径，将其反推为预防性要求，并把每条最重要的路径绑定到一项可验证的计划变更上。

## 何时使用

- 在项目启动、重大技术投入、高风险冲刺工作、上线或发布之前。
- 在计划看起来已经成熟但尚未执行之时，尤其是乐观情绪或过度自信很可能出现的情况下。
- 当决策的撤销成本很高，而风险仍停留在隐性层面、尚未被机制强制约束时。

## 何时不要使用

- 工作规模小、影响局部、且撤销成本低廉——跳过这些繁文缛节。
- 正处于事件处理中、时间紧迫——立即行动（OODA / 科学方法）；事前剖析是执行前的工具。
- 你能产出的只是无法绑定到本计划的泛泛风险（“范围蔓延”“需求不明确”）。
- 风险已由在线运行的门禁（CI、金丝雀、回滚、告警）强制约束，不存在残余的未列明路径。
- 一份成熟的风险登记册已经覆盖了同样的具体失败路径，并明确了负责人与检查手段。

## 流程

1. **以过去时态设定失败框架：** “现在是[截止日期之后]。计划失败了：[回滚 / 数据丢失 / 无人采用 / SLA 违约]。”必须解释一个已经发生的失败；仅仅预测一个失败是不够的。
2. **先不加过滤地生成失败原因：** 逐一扫描技术、流程、假设、依赖/外部因素、人员等维度。强制进行第二轮：“这个计划最需要成立但实际上没有成立的前提是什么？”先收集广度（力求产出许多不同的原因）；扫描过程中不要排序。
3. **排定优先级：** 按主题分组；按可能性 × 影响打分；保留前 3–5 条具体风险（舍弃无法绑定的泛泛条目）。
4. **失败优先的反向分析（吸收式反向路径）：** 对每条最高优先级风险，(a) 以过去时态复述失败结果，(b) 列出让该失败得以发生而必须成立的**必要条件/促成条件**，(c) 将每个条件**反转**为一条可验证的预防性要求（避免/要求规则 + 检查项），(d) 绑定**负责人、验证检查点和发布/阶段性门禁**。
5. **缓解并更新计划：** 对每条最高优先级风险，附上缓解步骤，必要时加上 spike/应急方案，并将反向分析得出的预防性要求作为明确的门禁写入计划。没有计划变更的事前剖析是不完整的。
6. **何时停止：** 当每条最高优先级风险都有了绑定的缓解措施或预防门禁，或者进一步的原因只是泛泛的重述——此时就发布更新后的计划，不要再继续头脑风暴。

## 输出

1. **失败情景**——带有日期和失败结果的过去时态灾难框架。
2. **失败原因**——未过滤的列表，以及随后按可能性 × 影响排出优先级的前 3–5 条。
3. **反向路径**——每条最高优先级风险：必要条件 → 反转后的预防性要求。
4. **缓解措施**——每条最高优先级风险的负责人、验证检查点、发布/阶段性门禁。
5. **计划变更**——新增到计划中的具体任务、spike、应急方案和门禁。

## 验证

- **证伪/停止：** 如果无法以过去时态连同必要条件一起陈述出任何针对本计划的失败路径，就停下来——你产出的是表演，而不是风险。如果某项“缓解措施”没有验证检查点，它就不算完成。
- **过度使用防护：** 不要对可逆的琐事、事件处理中的救火、或已经对同样路径建立了强制机制的系统做事前剖析。不要把抽象风险留作“稍后缓解”；要么把它们反转为门禁，要么当作不可执行而舍弃。
