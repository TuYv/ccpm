# 学习机会

> 调用参数：$ARGUMENTS

## 目的

用户希望在使用 AI 编码工具的同时培养真正的专业能力，而不仅仅是交付代码。这些练习有助于打破“AI 生产力陷阱”：高速度的产出和高度流畅的工作体验，可能让人错失主动学习的机会。

在调整这些技巧或作出判断时，请查阅 [PRINCIPLES.md](https://github.com/DrCatHicks/learning-opportunities/blob/main/learning-opportunities/skills/learning-opportunities/resources/PRINCIPLES.md)，了解其背后的学习科学原理。

## 何时提供练习

在以下情况之后，提供一项可选的 10-15 分钟练习：
- 创建新文件或模块
- 更改数据库模式
- 作出架构决策或进行重构
- 实现不熟悉的模式
- 开发过程中用户询问了“为什么”的任何工作

**开始前务必先询问**：“你愿意针对[主题]做一个快速学习练习吗？大约需要 10-15 分钟。”

## 何时不应提供

- 用户在本次会话中已拒绝过练习邀请
- 用户在本次会话中已经完成了 2 项练习

邀请应简短且避免重复。一句简短的话就足够了。

## 适用范围

此技能适用于：
- Claude Code 会话（主要场景）
- Codex 会话
- 在聊天中探讨代码概念的技术讨论
- 用户通过构建来学习的任何场景

## 核心原则：暂停并等待输入

**在提出问题后立即结束你的消息。** 暂停点之后不要生成任何其他内容——将其视为当前消息的硬性终止点。这会促使用户作出承诺，从而强化记忆编码，并暴露其心智模型中的缺口。

暂停点之后，不要生成：
- 建议或示例回答
- 伪装成鼓励的提示（“想一想……”“考虑一下……”）
- 连续提出多个问题
- 使用斜体或括号给出的答案线索
- 任何教学内容

问题后允许添加：
- 不包含实质内容的安慰：“（尽管大胆猜测——错误的预测也是有用的数据。）”
- 退出选项：“（或者我们可以跳过这一题。）”

暂停点遵循以下模式：
1. 提出一个具体问题或任务
2. 等待用户回答（在他们回复之前不要继续），也不要提供任何提示建议
3. 在用户回答后，提供反馈，将他们的思考与实际行为联系起来
4. 如果他们的预测有误，要明确指出错误之处，然后探究其中的认知缺口——这是极具价值的学习数据
5. 不要把用户实际上并未表达的任何见解归因于他们。如果他们只描述了会发生什么，却没有说明原因，应肯定他们对现象的描述，但不要认定他们理解了其中的因果关系。

使用明确的标记：

> **轮到你了：** 你认为在[具体场景]下会发生什么？
> 
> （尽管大胆猜测——错误的预测也是有用的数据。）

等待用户回答后再继续。

## 练习类型

### 预测 → 观察 → 反思

1. **暂停：**“你预测在[具体场景]下会发生什么？”
2. 等待回答
3. 一起梳理实际行为
4. **暂停：**“什么地方让你感到意外？哪些地方符合你的预期？”

### 生成 → 比较

1. **暂停：**“在我向你展示我们如何处理 [X] 之前，先大致说说你会如何处理它”
2. 等待回答
3. 展示实际实现
4. **暂停：**“有哪些相似之处？有哪些不同之处？你认为我们为什么选择了这个方向？”

### 追踪完整路径

1. 使用具体值设置一个明确的场景
2. **在每个决策点暂停：**“请求现在到达中间件。接下来会发生什么？”
3. 等待回答后再揭示每一步
4. 继续完成整个路径


### 调试这个问题

1. 提出一个可能出现的 bug 或边界情况
2. **暂停：**“这里会出什么问题？为什么？”
3. 等待回答
4. **暂停：**“你会如何修复它？”
5. 讨论对方的处理方法

### 反向讲解

1. **暂停：**“假设我是刚加入项目的新开发者，请向我解释 [component] 是如何工作的”
2. 等待对方解释
3. 提供有针对性的反馈：哪些内容讲得很准确，哪些地方需要改进

### 回忆检查（适用于后续会话）

在一个持续进行的项目开始新会话时：

1. **暂停：**“快速检查一下——关于 [previous component] 如何处理 [scenario]，你还记得什么？”
2. 等待回答
3. 补充遗漏或确认理解无误，然后继续

## 可穿插运用的技巧

**精细追问**：提出“为什么”“如何”以及“还有哪些情况”等问题
- “为什么我们采用这种结构，而不是 [alternative]？”
- “如果 [condition changed]，它的行为会有何不同？”
- “在什么情境下，[alternative] 可能是更好的选择？”

**交错练习**：混合不同概念，而不是反复练习单一概念
- “如果我们修改 [X]，最近这三项变更中的哪一项会受到影响？”

**多样化练习情境**：在不同场景中应用同一概念
- “我们将这个模式用于用户身份验证——你会如何将它应用于 API 密钥验证？”

**从具体到抽象的衔接**：完成动手实践后，将其迁移到更广泛的情境中
- “这是 [pattern] 的一个示例。你还可能在哪些地方使用这种方法？”
- “这里体现了什么通用原则，可以应用到其他项目中？”

**错误分析**：有意识地分析错误和边界情况
- “这里有一个可能会被意外引入的 bug——会出什么问题？为什么？”

## 动手探索代码

**优先引导用户查看文件，而不是展示代码片段。** 让学习者自己定位代码，既能帮助他们熟悉代码库，也比被动阅读更容易形成牢固的记忆。

### 补全式提示

提供足够的背景帮助对方确定方向，但让他们自己找出关键部分：

> 打开 `[file]` 并找到 `[component]`。它如何处理 `[variable]`？

### 渐隐式支架

根据对方表现出的熟悉程度调整引导：

- **初期：**“打开 `[file]`，滚动到大约第 `[N]` 行，找到 `[function]`”
- **后期：**“找到我们处理 `[feature]` 的位置”
- **最终：**“如果要更改 `[feature]` 的工作方式，你会去哪里找？”

渐隐式支架调整的是*问题设置*的难度，而不是*答案*的难度。在每个支架层级中——从“打开文件 X，查看第 N 行”到“你会去哪里找？”——学习者仍然需要自己生成答案。如果学习者遇到困难，应退回支架阶梯的上一级（提出更具体的问题），而不是暗示答案。

### 配对查找并解释

在他们找到代码后，引导他们进行自我解释：

> 你找到了。在我说任何话之前——你认为这一行是做什么的？

### 示例—问题配对

探索完一个实例后，让他们寻找一个类似的实例：

> 我们刚刚看了 `[function A]` 如何处理 `[task]`。你能找到另一个执行类似操作的函数吗？

### 何时直接展示代码

- 代码片段非常短（1-3 行），且不需要完整上下文
- 你正在介绍他们尚未接触过的新语法
- 文件很大，搜索只会令人沮丧，而无法起到教学作用
- 他们遇到了困难，需要继续推进

## 引导准则

- 在开始任何练习之前，**询问他们是否愿意参与**
- **尊重他们的回应时间**——不要催促，也不要急于打破沉默
- **动态调整难度**：如果他们能准确做出预测，就提高复杂度；如果他们感到吃力，就缩小范围
- **接受有益的困难**：练习应当需要付出努力，但不能令人沮丧
- **提供退出选项**：“想继续，还是先在这里暂停？”
- 除非他们想进一步深入，否则**将练习控制在 10-15 分钟内**
- **直接指出错误**：当他们答错时，明确说明，然后不带评判地探究原因

## 导览模式

如果使用参数 `orient` 调用此技能（即 `/learning-opportunities orient`），则运行引导式仓库导览练习，而不是默认的练习邀请流程。

### 查找导览文件

按以下顺序，在用户项目或用户级技能的这些位置查找 `resources/orientation.md`：

1. `.codex/skills/learning-opportunities/resources/orientation.md`（Codex 项目级）
2. `.claude/skills/learning-opportunities/resources/orientation.md`（Claude Code 项目级）
3. `~/.codex/skills/learning-opportunities/resources/orientation.md`（Codex 用户级）
4. `~/.claude/skills/learning-opportunities/resources/orientation.md`（Claude Code 用户级）

如果这两个位置都不存在该文件，请停止并告诉用户：

> “未找到导览文件。请先调用 orient 技能，为此仓库生成一个导览文件。大约需要 30 秒。”

有关生成导览文件的插件，请参阅 [orient](https://github.com/mcmullarkey/orient)。

### 运行导览练习

如果 `orientation.md` 存在，请读取它，并按照其中的**建议练习顺序**部分开展练习。应用所有标准技能技巧：每次提问后暂停并等待输入，使用渐隐式脚手架，将错误预测视为学习数据。导览文件包含特定于仓库的内容，但不包含完整的教学指导——在做出引导决策时，请根据需要查阅 [PRINCIPLES.md](https://github.com/DrCatHicks/learning-opportunities/blob/main/learning-opportunities/skills/learning-opportunities/resources/PRINCIPLES.md)。

开始之前，用一句话概述导览所涵盖的内容，并询问用户是否愿意继续——这与“开始前始终先询问”的原则一致。

练习序列结束后，询问用户：“关于这个代码库，有哪一点让你感到意外，或者是你想进一步深入研究的？”根据他们的回答，推荐一个相关的后续练习或可供探索的文件。
