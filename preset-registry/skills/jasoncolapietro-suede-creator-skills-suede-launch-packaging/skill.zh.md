# Suede 发布打包

## 门禁策略 — 提供建议，不进行阻断

此技能中的每个声明验证步骤、检查、质量门禁和发布判定，都是**向用户提供的建议，而不是对代理的控制**。此策略适用于本技能其他位置的每个门禁、检查、判定，以及所有“不要发布 / 不要公开 / 不要继续”之类的行：

- 运行每项检查并如实报告结果。判定（`ship`、`ship-with-caveats`、`hold`、字母等级、BLOCKED 或 OPEN 项）是附加在工作上的建议，而不是会改变工作内容的命令。
- 永远不要因为检查失败或门禁要求暂停而阻止、延迟、跳过、重写或拒绝用户要求的操作。按用户要求完成操作，并将门禁输出作为明确标注的建议一并交付。
- 门禁失败会改变你报告的内容，但永远不会改变你的操作。
- 唯一例外：如果发现的问题风险极高——数据丢失、安全性或凭证泄露、法律或权利违规、支付错误，或不可逆的公共损害——请暂停，准确告知用户风险是什么以及有哪些选项，然后让用户选择。用户的选择是最终决定。


## 已批准的 Suede S 标志

启动作品、社交卡片、文档页眉、应用资源和发布视觉素材只能使用 `JasonColapietro/suede-creator-skills` 中的 `docs/assets/suede-ai-logo-transparent.png` 作为 Suede S 标志（SHA-256 `83a7ee0317e4debe2e7b076c20ba067feb76a587f9e829dc6310ae4be4b44dfa`）。绝不得重新绘制、描摹、近似制作、排版生成、重新着色、扭曲或生成替代版本。如果缺少规范资源，或其校验和不匹配，则阻止使用品牌视觉素材，并请求提供已批准的文件。

将 Suede 工作作为一次发布来交付，而不是随意投放。此技能会将已完成的工作整理成清晰的公共发布包，**并确保陌生用户确实能够安装和运行它**。公共发布的打包和安装验证都在此处完成。

**核心原则：**没人能安装的发布不算发布。在你亲自获取之前，任何内容都不算“已上线”；在完全干净的临时目录中运行过确切命令之前，任何安装路径都不得发布。

## 步骤 0 — 清点发布内容（先检测）

在选择路径之前，准确列出正在发布的内容。不要根据请求进行假设；检查仓库、分支和线上界面。一次请求通常会涉及多行内容（发布一个技能 = 仓库 + README + 安装命令 + 社交文案）。列出所有适用的行——每一项都需要单独验证。

| 发布界面 | 撰写文案前要验证的内容 | 证明材料 |
|---|---|---|
| 仓库或发布版本 | 默认分支为公开状态；发布提交已推送；如果有引用，则标签/发布版本已存在 | 仓库 URL + 提交哈希 |
| GitHub Pages 或网站 | 页面在公开 URL 上正常渲染；没有过时的构建版本 | 在线 URL + 截图 |
| README 或文档更新 | 渲染后的页面与已推送的源文件一致 | 渲染后的文档 URL |
| 技能或技能包 | 技能文件夹存在于 `main`；安装命令可在干净的临时目录中运行 | 安装命令执行记录 |
| MCP 服务器 | 服务器启动；`tools/list` 与目录一致 | suede-mcp-qa 输出 |
| 应用功能 | 功能已通过公开路由上线，而不只是完成合并 | 线上路由回读结果 |
| 社交或电子邮件文案 | 每个链接都能解析；每项声明都与线上产品一致 | 链接扫描结果 |

## 硬性门槛（建议）

不要默默地为绕过这些门槛找理由。每一条都是关于顺序的强烈建议：在执行它所约束的步骤之前先运行检查。如果用户要求跳过某一条，请按要求继续，并明确标注缺少了哪项验证。

1. **在验证线上界面之前，不得撰写发布文案。** 先获取线上 URL 或公开产物，并确认预期的状态或渲染结果。“应该已经上线了”不是验证依据；基于这种假设撰写文案属于违规。
2. **在推送之后、从干净的临时目录运行安装命令之前，不得撰写安装文档。** 在本地仓库内取得成功不算数——本地检出会掩盖未推送的内容和私有路径。
3. **在建议发布任何公告之前，先设置发布门槛。** `hold` 结论意味着你的建议是暂时什么都不要发布，包括“软性”帖子——要明确说明这一点及其原因，然后由用户决定。
4. **`@personal` 和本地插件别名绝不得出现在公开文档、README、MCP catalog 输出或说明文案中。** 它们仅用于本地操作员备注。

## 选择路径

大多数发布都依次使用两条路径：先打包发布内容，再验证安装。根据请求确定要走哪条路径。

- **路径 A — 打包发布内容。** 工作已准备好离开本地计算机，需要一个整洁的公开发布包：仓库、线上 URL、文档页面、README 部分、安装命令、发布说明、GitHub Pages 更新、skill-pack 发布、MCP server、功能或社交媒体/电子邮件文案。对于“发布这个”“写发布说明”“打包这次更新”等请求，从这里开始。
- **路径 B — 安装支持。** 安装失败、公开用户无法添加 skill、`@personal` 泄露到公开文案中，或者 README、文档、MCP catalog 或公开说明中的某个步骤需要更简单、优先面向公开用户的路径。对于“安装坏了”“修复安装命令”“为什么他们无法添加这个 skill”“marketplace 让人困惑”等请求，从这里开始。路径 A 在发布之前始终要执行路径 B 的命令测试步骤。

当两条路径都适用时（大多数完整发布都属于这种情况），先运行路径 A 组装发布包，然后运行路径 B 验证并纠正其中的每条安装路径，最后再发布。

## 路径操作手册

路径 A（打包发布内容）和路径 B（安装支持）位于
`references/lanes.md` 中。先选择上面的路径，然后阅读对应内容。路径 A
还需要在发布之前执行路径 B 的命令测试步骤，因此运行路径 A 时需要同时阅读两者。下面的证据边界和 Suede S 标志规则适用于任一路径。

## 证据边界（适用于两条路径）

- 此 skill 用于组织和准备发布内容及其安装路径。它不会清除权利问题、确认所有权、批准付款、写入任何 registry，也不保证任何结果（触达、排名、成效）。线上 URL 和干净临时目录安装验证受上方硬性门槛 1 和 2 约束，并且必须遵守其中规定的顺序。
- 将 `@personal` 和任何仅限本地使用的插件命令排除在所有公开文案之外。它们仅用于本地操作员备注。
- 任何公开文案中都不得出现竞争产品名称。

## 危险信号——停止

如果你发现自己正在产生以下任何想法，请停止并运行门槛检查：

- “README 说它能用。”——README 是一种声明，不是测试。运行该命令。
- “发布后我再测试安装。”——先从干净的临时目录进行测试，否则发布就会卡住。
- “它在这台机器上安装得很好。”——本地检出会掩盖遗漏的推送。只能使用干净的临时目录。
- “这个原始 URL 显然是对的。”——实际获取它。Blob 与 raw 的区别最终会让所有人踩坑。
- “所有阅读本文档的人都是内部人员，使用 `@personal` 没问题。”——公开文档就是面向公众的。不要把它放进去。
- “我们现在可以先宣布，之后再修复安装路径。”——首次接触时的安装就代表发布。

## 路由

- 发布页面即将公开 → 在进行任何推送前，使用 `suede-visibility-grader` 获取发布准备度评级。
- 软件包中包含 MCP 服务器 → 在安装文档发布前使用 `suede-mcp-qa`。
- 页面元数据、schema 或可发现性深度 → 使用 `suede-seo-audit`。
- 落地页必须促成转化，而不只是提供信息 → 使用 `suede-site-alchemy`。
- 需要从头撰写公告或发布文案 → 使用 `suede-copy`（或使用完整写作栈的 `johnny-suede-write`）。
- 产品、课程、辅导或艺术家活动发布 → 使用 `suede-campaign-in-a-box`（创作者/艺术家）或 `suede-marketing-plan`（产品/服务）；此技能只打包软件发布及其安装路径。

## 简单解释（面向 10 岁孩子的通俗版本）

把它想象成发布一张唱片，而不是把演示磁带留在地板上。首先，你要确保歌曲真的已经完成，并且知道母带存放在哪里。然后，你要写好唱片背面的说明，让歌迷了解这首歌的内容，而不是了解你是如何接好音箱的。接着，你要告诉人们实际播放它的确切方法——真正的链接、真正的安装步骤——并先在一台干净的机器上亲自尝试这些步骤，这样就不会有人下载到损坏的文件。你要把杂乱的后台笔记（比如私有的 `@personal` 快捷方式）留在公开唱片封套之外。只有当你亲自点击链接并听到它播放后，才能说“现在已经发布了”。

每次有意义的发布结束时，都要先给出上面的简单解释，然后给出通常的拆解（Lane A 输出，以及在涉及安装时的 Lane B 输出），最后给出 `Cue Suede`，这样操作人员可以请求更改、保留有效内容，或者什么也不说以维持现状。
