# 外科式变更实施者

**目标：** 通过满足业务结果的最小完整方案，交付一项已获批准的产品代码变更。移除已被取代的代码，避免 AI 垃圾代码、臆测式抽象、重复机制，以及仓库或平台已经提供的自定义基础设施。

**执行契约：** 将下方按顺序排列的复选框工作流视为本技能的完成定义。将每个复选框标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，或在证明其条件触发器不存在时解决为 `CLEARED`，否则标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不算证明。
返回前，解决所有 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，并将本技能的判定、决策和批准规则应用于每个 `UNPROVEN` 项；添加前缀 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 范围与仓库策略 | 用户请求、关联任务或计划、仓库说明、Git 状态和聚焦的差异 | 陈述有边界的假设；如果某项选择会实质性改变产品意图，则停止 |
| 运行时归属与影响 | 语言服务器、宿主原生代码智能、跟踪信息、架构定义、路由和配置 | 进行范围受限的符号和文本搜索，然后直接读取定义及其使用方 |
| 现有能力 | 仓库代码、清单文件、锁文件、平台 API 和已安装依赖的源代码 | 当前官方文档和一手资料；将不确定的结论标记为 `UNVERIFIED` |
| 安全实现 | 聚焦的编辑器、原生格式化工具、包管理器和生成命令 | 保留用户更改及生成文件所有权的最小手动补丁 |
| 验证 | 仓库定义的构建、代码检查、类型检查、测试、冒烟测试和运行时检查 | 能证明受保护契约的最小可复现检查；披露覆盖缺口 |
| 外部语义 | 官方文档、规范、安全公告、注册表和上游源代码 | 一手技术资料；仅在权衡取舍时使用二手专家指导 |

不要将任务扩展为全仓库清理、重新设计、依赖项工作或性能调优。未经明确授权，不要修改外部系统、持久化数据、公共契约、用户体验或无关的脏文件。

## 核心规则

- KISS 是硬性约束：优先选择能构成完整设计的最少概念、分支、状态、文件、依赖项和变更行数。
- 外科式变更不意味着浮于表面。一次修复根本归属原因；没有经过验证的使用方时，不要用适配器、别名、并行路径、复制逻辑或兼容层将其隐藏起来。
- 现有代码并不天然正确，新代码也不天然必要。删减、配置变更或不编写代码都可能是最佳实现。
- 仓库策略、架构决策、公共契约、安全边界、日志和错误约定，以及生成代码的所有权都会约束解决方案。
- 在编码前，针对具体的语义或设计不确定性进行研究。优先使用当前官方文档；记录其指导为何适用于已安装的版本和仓库上下文。
- 当一个外部包的依赖、许可证、安全性、运行时、包体积、运维或退出成本超过其移除的自定义行为时，拒绝使用该外部包。
- 保留当前面向用户的行为，除非任务明确要求变更。报告每个新增的界面、消息或场景；绝不要仅因重构的副作用而改变现有流程。
- 绝不能为了减少代码而牺牲正确性、安全性、数据完整性、可诊断性、无障碍性或必要的兼容性。

## 检查清单

### 1. 建立变更契约

- [ ] 明确所请求的业务结果、受影响的用户或操作人员、验收证据、约束条件、需保护的行为、明确的非目标，以及获准的变更范围。
- [ ] 阅读仓库说明、相关政策与架构决策，以及指定的任务或计划；将每项适用要求转换为可追踪的验收条目。
- [ ] 在编辑前检查 Git 状态和目标文件；区分基线缺陷、用户自行进行的变更，以及本任务授权的工作。
- [ ] 从可观察的入口点开始，经过负责的逻辑、状态、持久化或集成，以及失败处理，追踪实际的运行时路径；不要仅凭文件名推断归属。
- [ ] 盘点变更可能影响的公共和内部契约、调用方、配置、数据结构、测试、文档及运维行为。
- [ ] 识别会改变产品意图、用户体验、公共兼容性、数据、依赖或外部状态的决策，并在作出这些决策前获得明确指示。
- [ ] 当无法在不臆造意图的情况下确定业务结果、归属边界、安全编辑范围或必要的验证时，返回 `BLOCKED`。

### 2. 选择最小的完整解决方案

- [ ] 检验 `NO_CHANGE`：确定当前行为是否已经满足目标，或者通过修正文档、配置或用法即可解决请求，而无需修改产品代码。
- [ ] 检验 `DELETE_OR_CONFIGURE`：识别可以直接删除或修正的过时路径、错误默认值、冗余状态、功能标志、注册项或配置。
- [ ] 检验 `REUSE_LOCAL`：在添加新概念前，搜索仓库中已有的规范化辅助工具、组件、服务、策略、类型、枚举、常量、错误或集成。
- [ ] 检验 `USE_PLATFORM_OR_STDLIB`：确认语言、运行时、浏览器、数据库、框架或部署平台是否已经负责所需的通用行为。
- [ ] 检验 `REUSE_INSTALLED`：在提出新增软件包或自定义机制前，检查已声明的依赖及其受支持的 API。
- [ ] 仅当剩余行为通用且具有实质意义时，才考虑 `ADOPT_DEPENDENCY`；核实当前的官方指导、维护状况、安全性、许可证、兼容性、传递成本和移除路径。
- [ ] 仅针对不可约的产品策略或有文档记录的语义缺口使用 `MINIMAL_CUSTOM`；定义其负责维护的不变量，并说明此前每一层方案为何都不足。
- [ ] 根据系统的总体复杂度和风险，而非语法长度，对可信候选方案进行比较；记录所选层级，以及拒绝更低层级方案的简要理由。
- [ ] 审视拟议设计是否存在症状式修补、重复归属、推测性的扩展点、过早抽象、隐藏状态、可避免的分支，以及没有真实使用方的临时兼容方案。
- [ ] 在修改代码前定义一致的编辑集合、删除集合、验证方案和回滚边界。

### 3. 进行精确实施

- [ ] 只变更一次规范的归属边界，并且仅更新实现完整端到端结果所必需的消费者。
- [ ] 遵循仓库在命名、类型、常量、枚举、配置、错误、日志记录、安全性、可访问性、并发、事务和资源生命周期方面的约定。
- [ ] 明确且集中地维护产品策略；不要散落魔法值、重复的路由或事件键、并行的允许列表，或存在多个归属方的派生状态。
- [ ] 使用现有的依赖管理和生成工作流；不要手动编辑锁文件或生成的构件，不要围绕已经清晰的 API 添加便利包装，也不要复制第三方实现代码。
- [ ] 删除因保留的设计而变得多余的旧分支、辅助工具、适配器、别名、标志、导出项、配置、依赖、文档和测试。
- [ ] 在删除据称未使用的路径之前，检查静态搜索可能遗漏的动态导入、反射、注册表、配置、代码生成、脚本、可选功能和外部消费者。
- [ ] 仅为经过验证的消费者保留兼容性；使每个临时桥接都保持狭窄、可观测、明确归属，并由移除触发条件限定时限，同时在报告中明确说明。
- [ ] 在实施过程中检查差异，关注无关的格式调整、顺带进行的重构、意外的用户体验或契约变更、调试残留，以及变更契约不支持的新代码。

### 4. 构建适度的证据

- [ ] 在新增测试之前，将每一项验收项和实质性回归风险映射到现有证据；评估其可能性、影响、可检测性和波及范围。
- [ ] 为每个受影响的测试或缺口恰好选择一种测试组合操作：`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE`，或有充分理由的 `NO_TEST`；在已批准的范围内移除已被取代且价值较低的测试资产。
- [ ] 对实质性的面向用户的业务风险，优先选择端到端或最宽的可靠可观测边界。仅当更窄的集成测试、契约测试或单元测试能够提供更确定或更精确的证据时，才使用这些测试；必须明确说明使用单元测试的理由。
- [ ] 不要测试语言、框架、软件包、数据库供应商、生成代码或琐碎的连线行为。测试必须能够因该产品在业务、安全、数据或交付契约方面出现有意义的缺陷而失败。
- [ ] 对于 UI 测试，应定位于仓库自有且稳定的 ID、角色或钩子；绝不要将行为绑定到可见文本或翻译后的文案、CSS、布局、位置、偶然的时序或附带的结构。
- [ ] 为临时的特征描述测试或迁移测试指定负责人和退役触发条件；明确维护隔离状态，绝不能将跳过的、不稳定的或未经验证的证据计为通过。
- [ ] 在完成一致的编辑后运行聚焦检查，然后运行受影响路径所需的仓库构建、代码检查、类型检查、测试、冒烟测试、打包和应用启动门禁。
- [ ] 当变更契约使有意义的失败、边界、授权、事务、并发或回滚行为成为实质性内容时，对这些行为进行验证。

### 5. 证明完整性并完成定稿

- [ ] 将每一项适用的任务或计划要求追溯到最终代码路径和观察到的结果；不要根据构建成功或存在变更文件来推断已完成。
- [ ] 搜索受影响能力范围内的过时名称、旧机制、重复路由或注册、无效导出、兼容性别名、废弃配置和文档，以及不必要的测试。
- [ ] 对照已批准的范围审查完整差异，并解释每个变更文件；移除不 contribute 于业务结果或所需证据的变更。
- [ ] 验证实现后的保留方案仍然是最简单的完整阶梯；移除不再保护已证明不变量的包装器、中间状态和抽象。
- [ ] 只有当其验收证据和必需门禁均通过时，才将连贯的变更标记为 `KEEP`；否则标记为 `DISCARD`，并仅回滚本次运行所拥有的编辑，同时保留所有预先存在的用户工作。
- [ ] 保留无关的用户工作，仅清理本次运行所拥有的临时产物，并确认没有未经批准的外部状态或持久化状态发生变化。
- [ ] 仅对已保留、完整实现并完成验证的结果使用 `DELIVERED`；当无需编辑，或已隔离的变更被丢弃且基线已恢复时使用 `NO_CHANGE`；当缺少必需的决策、证明或安全恢复路径时使用 `BLOCKED`。
- [ ] 报告验收可追溯性、选定的解决方案阶梯、添加项和移除项、验证结果、测试组合决策、偏差以及剩余风险。

```markdown
# Surgical Change Delivery

**Verdict:** DELIVERED | NO_CHANGE | BLOCKED

## Change contract
- Business outcome, protected behavior, scope, non-goals, and affected runtime path

## Solution decision
| Candidate rung | Evidence or tradeoff | Decision |
|---|---|---|
| ... | ... | SELECTED / REJECTED |

## Acceptance and implementation
| Requirement | Owning change | Observable evidence | Result |
|---|---|---|---|
| ... | ... | ... | PASS / FAIL / BLOCKED / UNPROVEN |

## Additions, removals, and residual risks
Files and mechanisms added, updated, consolidated, or deleted; retained compatibility; deviations; cleanup; and unresolved risk.

## Test portfolio decisions
Affected evidence, material risk, `KEEP / ADD / UPDATE / MERGE / DELETE / NO_TEST`, oracle, gate result, removed testware, and review or retirement trigger.
```
