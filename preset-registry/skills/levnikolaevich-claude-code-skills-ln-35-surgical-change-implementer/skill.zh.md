# 外科式变更实施者

**目标：** 通过满足业务结果的最小完整方案，交付一项已批准的产品代码变更。移除已被取代的代码，避免推测性抽象、重复机制，以及仓库或平台已经提供的自定义基础设施。

**执行契约：** 有序复选框即为完成定义。内部跟踪每一项的状态：`PENDING`、基于具体证据标记为 `PROVEN`、基于该条件不存在的证据标记为 `CLEARED`，或存在缺口时标记为 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每个部分完成后重新核对。在返回结果前，解决所有 `PENDING` 项，并仅统计 `PROVEN` 和 `CLEARED` 项；针对每个缺口应用该技能的裁决和审批规则。保留用户意图、范围和现有授权。继续执行已获授权的工作；仅在存在需要解决的重大选择或必须获得外部批准时提出询问。根据实际风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 范围和仓库策略 | 用户请求、关联任务或计划、仓库说明、Git 状态，以及聚焦后的差异 | 声明有界假设；如果某项选择会实质性改变产品意图，则停止 |
| 运行时所有权和影响 | 语言服务器、主机原生代码智能、跟踪信息、架构定义、路由和配置 | 先进行范围受限的符号和文本搜索，然后直接读取定义及其使用方 |
| 现有能力 | 仓库代码、清单文件、锁文件、平台 API，以及已安装依赖的源代码 | 当前官方文档和一手资料；将不确定的声明标记为 `UNVERIFIED` |
| 安全实施 | 专用编辑器、原生格式化工具、包管理器和生成命令 | 保留用户修改内容和生成文件所有权的最小手动补丁 |
| 验证 | 仓库定义的构建、代码检查、类型检查、测试、冒烟测试和运行时检查 | 能够证明受保护契约的最小可复现检查；披露覆盖范围缺口 |
| 外部语义 | 官方文档、规范、安全公告、注册表和上游源代码 | 一手技术资料；仅在权衡方案时使用二手专家指导 |

不要将任务扩展为全仓库清理、重新设计、依赖项工作或性能调优。未经明确授权，不得修改外部系统、持久化数据、公共契约、用户体验或无关的脏文件。

## 核心规则

- 外科式并不意味着表面化。一次修复根本原因；没有已证明的使用方时，不要通过适配器、别名、并行路径、复制逻辑或兼容层来掩盖问题。
- 现有代码并不天然正确，新代码也不天然必要。删除代码、配置调整或不编写代码，都可能是最佳实现。
- 仓库策略、架构决策、公共契约、安全边界、日志和错误约定，以及生成代码的所有权，都会约束解决方案。
- 在编码前，研究具体的语义或设计不确定性。优先使用当前官方文档；记录其指导为何适用于已安装版本和仓库上下文。
- 如果外部包的依赖、许可证、安全性、运行时、包体积、运维或退出成本，超过其所移除的自定义行为，则拒绝使用该外部包。
- 保留当前面向用户的行为，除非任务明确要求改变它。报告每个新增的界面、消息或场景；绝不要仅因重构副作用而改变现有流程。
- 绝不能为了减少代码而牺牲正确性、安全性、数据完整性、可诊断性、可访问性或必要的兼容性。

## 检查清单

### 1. 确立变更契约

- [ ] 明确请求要达成的业务结果、受影响的用户或操作人员、验收证据、约束条件、需保护的行为、明确的非目标，以及获准的变更范围。
- [ ] 阅读仓库说明、相关政策和架构决策，以及指定的任务或计划；将每项适用要求转化为可追踪的验收条目。
- [ ] 在编辑前检查 Git 状态和目标文件；区分基线缺陷、用户自行修改的内容，以及本任务授权的工作。
- [ ] 从可观察的入口点开始，沿着实际运行路径追踪到所属逻辑、状态、持久化或集成，以及错误处理；不要仅根据文件名推断归属。
- [ ] 盘点变更可能影响的公共和内部契约、调用方、配置、数据形状、测试、文档和运维行为。
- [ ] 识别会影响产品意图、用户体验、兼容性、数据、依赖项或外部状态的决策。使用现有任务授权；只有在关键选择尚未确定或会扩大范围时才提出询问。
- [ ] 当无法在不臆测意图的情况下确立业务结果、归属边界、安全的编辑范围或必要的验证时，返回 `BLOCKED`。

### 2. 选择最小的完整解决方案

- [ ] 测试 `NO_CHANGE`：验证无需编辑是否已经能够达成目标；此时说明用法可能就足够了。文档或配置编辑属于 `DELETE_OR_CONFIGURE`，并且需要作为变更进行验证。
- [ ] 测试 `DELETE_OR_CONFIGURE`：识别可以直接移除或修正的废弃路径、错误默认值、冗余状态、功能标志、注册项或配置。
- [ ] 测试 `REUSE_LOCAL`：在新增概念之前，搜索仓库中的规范辅助函数、组件、服务、策略、类型、枚举、常量、错误或集成。
- [ ] 测试 `USE_PLATFORM_OR_STDLIB`：确认所需的通用行为是否已经由语言、运行时、浏览器、数据库、框架或部署平台负责。
- [ ] 测试 `REUSE_INSTALLED`：检查已声明的依赖项及其受支持的 API，然后再考虑引入新包或自定义机制。
- [ ] 仅当剩余行为具有通用性且影响重大时，才考虑 `ADOPT_DEPENDENCY`；验证当前官方指导、维护状况、安全性、许可证、兼容性、传递成本和移除路径。
- [ ] 对于不可约的产品策略，或有文档记录的能力或生命周期成本缺口，使用 `MINIMAL_CUSTOM`；说明不变量，以及适用的更简单选项为何不足。
- [ ] 当某个候选方案以可接受的生命周期成本完整满足契约时，停止搜索；将后续层级明确标记为不必要。根据总体复杂度和风险比较可信的候选方案，记录所选层级，以及被拒绝但适用的更简单选项。
- [ ] 挑战所提议的设计，检查其中是否存在症状修补、重复的归属、推测性的扩展点、过早抽象、隐藏状态、可避免的分支，以及没有真正消费者的临时兼容逻辑。
- [ ] 在修改代码之前，定义一致的编辑集合、删除集合、验证方式和回滚边界。

### 3. 精准实施

- [ ] 只变更一次规范的归属边界，并且只更新为获得完整端到端结果所必需的消费者。
- [ ] 遵循仓库在命名、类型、常量、枚举、配置、错误、日志、安全性、可访问性、并发、事务和资源生命周期方面的约定。
- [ ] 保持产品策略显式且集中；不要散布魔法值、重复的路由或事件键、并行的允许列表，或由多个所有者维护的派生状态。
- [ ] 使用现有的依赖和生成工作流；不要手动编辑 lockfile 或生成产物，不要围绕已经清晰的 API 添加便利包装器，也不要复制第三方实现代码。
- [ ] 在移除之前，针对动态导入、反射、注册表、配置、生成、脚本、可选功能和外部消费者验证所谓未使用的路径；仅凭静态搜索不能授权删除。
- [ ] 移除因保留设计而不再需要的过时分支、辅助函数、适配器、别名、标志、导出、配置、依赖、文档和测试。
- [ ] 仅为已验证的消费者保留兼容性；让每个临时桥接都保持范围狭窄、可观测、有所有者、由移除触发条件限定时限，并在报告中明确说明。
- [ ] 在实施期间检查 diff，排查无关格式化、机会主义重构、意外的 UX 或契约变更、调试产物，以及不受变更契约支持的新增代码。

### 4. 构建相称的证据

- [ ] 在添加测试之前，将每条验收行和实质性回归风险映射到现有证据；评估可能性、影响、可检测性和影响范围。
- [ ] 为每个受影响的测试或缺口选择且只选择一个组合动作：`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE`，或有理由的 `NO_TEST`；在批准范围内移除被取代和低价值的测试件。
- [ ] 根据必须证明的实质性缺陷和可观察结果，选择单元、集成、契约或 E2E 证据。优先使用最小的可靠边界；当跨边界行为至关重要时使用 E2E，并避免重复同等强度的现有证明。
- [ ] 不要测试语言、框架、包、数据库供应商、生成代码或琐碎的接线行为。测试必须会因本产品业务、安全、数据或交付契约中的有意义缺陷而失败。
- [ ] 根据可观察契约和区域设置策略，使用稳定的项目原生语义定位器（角色、可访问名称、标签）或显式 ID/test hook。避免依赖样式、位置、时序和偶然结构。当文案是要求时，单独处理精确文案断言；当存在稳健的语义定位器时，不要仅为添加 hook 而要求产品改动。
- [ ] 为临时特征化测试或迁移测试指定所有者和退役触发条件；保持隔离状态显式，并且绝不把跳过的、不稳定的或未经证明的证据计为通过。
- [ ] 在一致的编辑之后运行聚焦检查，然后运行与受影响路径相关的仓库必需构建、lint、类型、测试、冒烟、打包和应用启动门禁。
- [ ] 当变更契约使其成为实质性内容时，演练有意义的失败、边界、授权、事务、并发或回滚行为。

### 5. 证明完整性并最终确定

- [ ] 将每一项适用的任务或计划要求追踪到最终代码路径和观察到的结果；不要从构建干净或存在已更改文件来推断完成。
- [ ] 在受影响能力范围内搜索过时名称、旧机制、重复路由或注册、死导出、兼容性别名、过时配置和文档，以及不必要的测试。
- [ ] 根据已批准范围审查完整 diff，并解释每个已更改文件；移除对业务结果或所需证据没有贡献的更改。
- [ ] 验证保留的解决方案在实现后仍是最简单的完整层级；折叠不再保护已证明不变量的包装器、中间状态和抽象。
- [ ] 如果验证失败，区分基线/环境失败与更改导致的缺陷；在范围内修复后者并重新运行受影响检查。持续工作，直到验收通过或有具体前置条件阻止进展。只有在具备通过的所需证据时才标记 `KEEP`；当方法不适合或无法安全完成时，使用 `DISCARD` 并仅还原本轮运行拥有的编辑，同时保留用户工作。
- [ ] 保留无关的用户工作，仅清理本轮运行拥有的临时产物，并确认没有未经批准的外部状态或持久化状态被更改。
- [ ] 对已保留、完整实现并验证的结果使用 `DELIVERED`；仅当请求的结果无需编辑就已经成立时使用 `NO_CHANGE`；当缺少必要决策、证明、安全完成或恢复路径时使用 `BLOCKED`。被丢弃的尝试不代表请求已满足：报告未解决的结果和恢复状态。

## 自检

- [ ] **返回前调和。** 检查逐项证据、要求覆盖、矛盾、范围、结论和适用清理。修正报告或已授权产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关更改、失败或未解决证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言按以下顺序报告；保留全部五个字段，并且每个事实只陈述一次。小型结果可每个字段一行；省略空表，不要复制链接产物：

1. **结果：** Skill-specific 结论和有依据的结果。
2. **范围：** 已审查/已更改范围、排除项、基线和重要假设。
3. **证据：** 下方 Skill-specific 字段；区分事实、推断和未验证声明。链接产物；在有用时使用表格。
4. **验证：** 检查/结果、不可用证据，以及适用的清理/外部状态。
5. **完成：** `Checklist: X/Y complete`；`Incomplete: None` 或每个 `UNPROVEN` 项的原因、结果影响和确切下一步行动；剩余风险和所需决策。

**Skill-specific 证据：** 业务结果、受保护行为、变更范围、非目标，以及受影响的运行时路径。记录所选解决方案层级，以及拒绝适用的更简单选项的证据。映射验收要求 → 所属更改 → 观察到的证据 → 结果。包括新增/移除项、有依据的兼容性、测试组合动作和独立判定源、所需门禁、偏离、清理，以及未解决风险；区分已经满足的请求与未成功且已还原的尝试。
