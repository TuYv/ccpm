# 外科手术式变更实施者

**目标：** 通过满足业务成果的最小完整解决方案，交付一项已获批准的产品代码变更。移除已被取代的代码，并避免 AI 垃圾、推测性抽象、重复机制，以及自定义实现仓库或平台已经提供的基础设施。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。依次完成每一项，且仅当相应操作及所需证据均已完备时，才能将其标记为完成。标记为 `N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回结果前，对每个未完成项目应用此技能的裁决和批准规则，并在开头添加 **清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出所有未完成项目。

## 工具选择

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 范围和仓库策略 | 用户请求、关联的任务或计划、仓库说明、Git 状态以及聚焦的差异 | 说明有明确边界的假设；如果某项选择会实质性改变产品意图，则停止 |
| 运行时归属和影响 | 语言服务器、宿主原生代码智能、跟踪信息、架构、路由和配置 | 对符号和文本进行窄范围搜索，然后直接阅读其定义和使用方 |
| 现有能力 | 仓库代码、清单、锁文件、平台 API 以及已安装依赖项的源代码 | 当前的官方文档和一手资料；将不确定的说法标记为 `UNVERIFIED` |
| 安全实施 | 聚焦的编辑器、原生格式化工具、包管理器以及生成命令 | 应用最小的手动补丁，保留用户变更以及生成文件的归属关系 |
| 验证 | 仓库定义的构建、代码检查、类型检查、测试、冒烟测试和运行时检查 | 能证明受保护契约的最小可复现检查；披露覆盖范围缺口 |
| 外部语义 | 官方文档、规范、安全公告、注册表以及上游源代码 | 一手技术资料；仅在权衡取舍时使用二手专家指导 |

不要将任务扩展为仓库级清理、重新设计、依赖项工作或性能调优。未经明确授权，不要修改外部系统、持久化数据、公共契约、用户体验或无关的未提交文件。

## 核心规则

- KISS 是一项硬性约束：优先采用概念、分支、状态、文件、依赖项和变更行数最少，同时又能构成完整设计的方案。
- 外科手术式并不意味着流于表面。一次性修复根本原因；如果没有经过证实的使用方，不要用适配器、别名、并行路径、复制的逻辑或兼容层来掩盖问题。
- 现有代码不一定正确，新代码也不一定必要。删除、配置调整或不编写代码都可能是最佳实现方案。
- 仓库策略、架构决策、公共契约、安全边界、日志和错误处理约定，以及生成代码的归属关系，都会约束解决方案。
- 编码前，应研究具体的语义或设计不确定性。优先使用当前的官方文档；记录其指导为何适用于已安装的版本和仓库上下文。
- 如果某个外部包的依赖、许可证、安全性、运行时、包体积、运维或退出成本，超过它所替代的自定义行为带来的成本，则拒绝使用该包。
- 除非任务明确要求变更，否则保留当前用户可见的行为。报告每个新增的界面、消息或场景；绝不要仅仅因为重构的副作用而改变现有流程。
- 绝不要为了减少代码而牺牲正确性、安全性、数据完整性、可诊断性、无障碍性或必需的兼容性。

## 检查清单

### 1. 建立变更契约

- [ ] 明确所请求的业务成果、受影响的用户或运维人员、验收证据、约束条件、受保护的行为、明确的非目标，以及获准的修改范围。
- [ ] 阅读仓库说明、相关策略和架构决策，以及指定的任务或计划；将每项适用要求转换为可追踪的验收条目。
- [ ] 编辑前检查 Git 状态和目标文件；区分基线缺陷、用户已有的变更与本任务授权的工作。
- [ ] 从可观察的入口点开始，沿实际运行时路径追踪至负责相关行为的逻辑、状态、持久化或集成及故障处理；不要仅根据文件名推断归属。
- [ ] 盘点此变更可能影响的公共与内部契约、调用方、配置、数据结构、测试、文档和运维行为。
- [ ] 识别会改变产品意图、用户体验、公共兼容性、数据、依赖项或外部状态的决策，并在执行前获得明确指示。
- [ ] 如果无法在不臆测意图的情况下确定业务成果、归属边界、安全编辑范围或必要的验证，则返回 `BLOCKED`。

### 2. 选择最小且完整的解决方案

- [ ] 验证 `NO_CHANGE`：确定当前行为是否已满足预期成果，或者是否可通过修正文档、配置或使用方式，在不编辑产品代码的情况下解决请求。
- [ ] 验证 `DELETE_OR_CONFIGURE`：识别是否存在可直接移除或纠正的过时路径、错误默认值、冗余状态、功能开关、注册项或配置。
- [ ] 验证 `REUSE_LOCAL`：在添加新概念之前，搜索仓库中规范的辅助函数、组件、服务、策略、类型、枚举、常量、错误或集成。
- [ ] 验证 `USE_PLATFORM_OR_STDLIB`：确认所需的通用行为是否已由语言、运行时、浏览器、数据库、框架或部署平台提供。
- [ ] 验证 `REUSE_INSTALLED`：在提出使用新软件包或自定义机制之前，检查已声明的依赖项及其支持的 API。
- [ ] 仅当剩余行为具有通用性且实质重要时，才考虑 `ADOPT_DEPENDENCY`；验证当前官方指导、维护情况、安全性、许可证、兼容性、传递成本和移除路径。
- [ ] 仅将 `MINIMAL_CUSTOM` 用于无法进一步简化的产品策略或有文档记录的语义缺口；定义它所负责维护的不变量，并说明之前的每一级方案为何均不充分。
- [ ] 根据系统整体复杂度和风险，而非语法长度，对可信候选方案进行比较；记录所选择的层级，以及拒绝较低层级方案的简要理由。
- [ ] 审视拟议设计是否存在仅修补症状、重复归属、推测性扩展点、过早抽象、隐藏状态、可避免的分支，以及缺乏真实使用方的临时兼容机制。
- [ ] 在修改代码之前，定义一致的编辑集合、删除集合、验证方案和回滚边界。

### 3. 精准实施

- [ ] 仅修改一次规范的归属边界，并且只更新实现完整端到端结果所必需的使用方。
- [ ] 遵循仓库在命名、类型、常量、枚举、配置、错误、日志、安全性、可访问性、并发、事务和资源生命周期方面的约定。
- [ ] 保持产品策略明确且集中；不要散布魔法值、重复的路由键或事件键、并行的允许列表，或存在多个归属方的派生状态。
- [ ] 使用现有的依赖项和生成工作流；不要手动编辑锁文件或生成的产物，不要为已经清晰的 API 添加便利包装器，也不要复制第三方实现代码。
- [ ] 移除保留设计不再需要的过时分支、辅助函数、适配器、别名、标志、导出、配置、依赖项、文档和测试。
- [ ] 在删除据称未使用的路径之前，检查静态搜索可能遗漏的动态导入、反射、注册表、配置、代码生成、脚本、可选功能和外部使用方。
- [ ] 仅为已经验证的使用方保留兼容性；确保每个临时桥接方案范围有限、可观测、有明确归属方、由移除触发条件限定时限，并在报告中明确说明。
- [ ] 在实施过程中检查差异，排查无关的格式调整、投机性重构、意外的用户体验或契约变更、调试产物，以及变更契约未支持的净新增代码。

### 4. 构建适度的证据

- [ ] 在添加测试之前，将每个验收项和重大回归风险映射到现有证据；评估其发生可能性、影响、可检测性和波及范围。
- [ ] 为每个受影响的测试或缺口准确选择一项测试组合操作：`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE`，或有合理依据的 `NO_TEST`；在已批准的范围内移除已被取代和低价值的测试资产。
- [ ] 对重大的、面向用户的业务风险，优先采用端到端测试或最宽泛且可靠的可观测边界。仅当更窄范围的集成测试、契约测试或单元测试能够提供更具确定性或更精确的证据时才使用它们；必须明确说明使用单元测试的理由。
- [ ] 不要测试语言、框架、包、数据库供应商、生成代码或简单接线行为。测试必须能在本产品的业务、安全、数据或交付契约出现实质性缺陷时失败。
- [ ] 对于 UI 测试，应定位由仓库所有并保持稳定的 ID、角色或钩子；绝不能将行为绑定到可见或已翻译的文案、CSS、布局、位置、偶发的时序或附带结构。
- [ ] 为临时的特征刻画测试或迁移测试指定归属方和退出触发条件；明确标示隔离状态，并且绝不将已跳过、不稳定或未经证实的证据计为通过。
- [ ] 在完成一致连贯的编辑后运行针对性检查，然后运行与受影响路径相关且仓库要求的构建、代码检查、类型检查、测试、冒烟测试、打包和应用启动门禁。
- [ ] 当变更契约表明失败、边界、授权、事务、并发或回滚行为具有实质影响时，对这些行为进行验证。

### 5. 证明完整性并完成交付

- [ ] 将每项适用的任务或计划要求追溯至最终代码路径和观察到的结果；不要根据构建成功或存在已更改的文件来推断工作已完成。
- [ ] 在受影响的能力范围内，搜索过时的名称、旧机制、重复的路由或注册、无用的导出、兼容性别名、过时的配置和文档，以及不必要的测试。
- [ ] 根据已批准的范围审查完整差异，并说明每个已更改文件的原因；移除对业务结果或必要证据没有贡献的更改。
- [ ] 验证实施后保留的解决方案仍然是最简单且完整的层级；精简不再保护已证实不变量的包装层、中间状态和抽象。
- [ ] 仅当一致性更改的验收证据和必要门禁均通过时，才将其标记为 `KEEP`；否则将其标记为 `DISCARD`，并仅还原本次运行产生的编辑，同时保留用户先前已有的所有工作。
- [ ] 保留不相关的用户工作，仅清理本次运行产生的临时产物，并确认未更改任何未经批准的外部状态或持久化状态。
- [ ] 仅对已保留、完整实施且经过验证的结果使用 `DELIVERED`；当无需编辑，或隔离的更改已被丢弃且基线已恢复时，使用 `NO_CHANGE`；当缺少必要的决策、证据或安全恢复路径时，使用 `BLOCKED`。
- [ ] 报告验收可追溯性、所选解决方案层级、新增项和移除项、验证结果、测试组合决策、偏差以及残余风险。

## 输出约定

```markdown
# Surgical Change Delivery

**Verdict:** DELIVERED | NO_CHANGE | BLOCKED

## Change contract
- Business outcome, protected behavior, scope, non-goals, and affected runtime path

## Solution decision
| Candidate rung | Evidence or tradeoff | Decision |
|---|---|---|
| ... | ... | SELECTED / REJECTED |

## Acceptance and implementation
| Requirement | Owning change | Observable evidence | Result |
|---|---|---|---|
| ... | ... | ... | PASS / FAIL / BLOCKED / UNPROVEN |

## Additions, removals, and residual risks
Files and mechanisms added, updated, consolidated, or deleted; retained compatibility; deviations; cleanup; and unresolved risk.

## Test portfolio decisions
Affected evidence, material risk, `KEEP / ADD / UPDATE / MERGE / DELETE / NO_TEST`, oracle, gate result, removed testware, and review or retirement trigger.
```
