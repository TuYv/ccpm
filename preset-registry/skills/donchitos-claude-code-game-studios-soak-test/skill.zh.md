# 耐久测试

耐久测试（也称为持久性测试）是一次带有特定观察目标的长时间游玩。与冒烟检查（覆盖广泛的关键路径，约 10 分钟）或单一功能试玩（约 30 分钟）不同，耐久测试会持续 **30 分钟到数小时**，以发现：

- **内存泄漏** — 仅在场景切换后才会出现的堆内存逐渐增长
- **性能漂移** — 随时间推移不断恶化的帧时间性能下降
- **状态累积缺陷** — 仅在某个机制重复 N 次后才会出现的问题（物品栏已满、分数溢出、AI 状态损坏）
- **趣味疲劳** — 初次体验时感觉良好，但长时间游玩后会变得重复乏味的机制
- **内容耗尽** — 玩家不再有新内容可体验的时间点

**此技能会生成观察规程和分析工具框架——实际游玩由人工完成。**

**输出：** `production/qa/soak-test-[date]-[duration].md`

**运行时机：**
- 打磨阶段——在 `/gate-check release` 之前
- 修复内存或稳定性问题之后（回归耐久测试）
- 尚未对长时间游玩进行正式跟踪时

---

## 1. 解析参数

**时长**（默认值：`1h`）：
- `30m` — 短时耐久测试；适合测试单个机制或场景
- `1h` — 标准耐久测试；覆盖大多数常见的泄漏类别
- `2h` — 扩展耐久测试；建议用于打磨阶段的首次完整耐久测试
- `4h` — 深度耐久测试；适用于设计为长时间单局游玩的游戏（RPG、模拟游戏）

**重点**（默认值：`all`）：
- `memory` — 重点关注堆大小、对象数量和泄漏模式
- `stability` — 重点关注崩溃、冻结和卡死检测
- `balance` — 重点关注趣味疲劳、内容耗尽和难度感知
- `all` — 以上所有内容

## 3. 定义观察检查点

根据时长生成定时检查点：

**30 分钟耐久测试**：T+0、T+10、T+20、T+30
**1 小时耐久测试**：T+0、T+15、T+30、T+45、T+60
**2 小时耐久测试**：T+0、T+20、T+40、T+60、T+80、T+100、T+120
**4 小时耐久测试**：T+0、T+30、T+60、T+90、T+120、T+180、T+240

在每个检查点，观察者都要记录第 4 阶段中定义的观察项目。

## 4. 生成耐久测试规程

### 内存／稳定性观察项目（如果重点为 memory 或 all）

特定于引擎的监控指导：

**Godot 4：**
- 打开调试器 → 监视器选项卡；在各检查点跟踪 `Memory → Static Memory` 和 `Object Count → Objects`
- 记录：静态内存（KB）、对象数量、孤立节点数量
- 告警阈值：前 15 分钟后，内存相较 T+0 增长超过 20%（加载时出现一定增长属于正常现象；持续增长则表示存在泄漏）
- 注意：在 Godot 4.6 中，`Performance.get_monitor(Performance.MEMORY_STATIC)` 返回的单位为字节

**Unity：**
- 打开 Memory Profiler（Window → Analysis → Memory Profiler）
- 记录：每个检查点的总预留内存（MB）、GC 已分配内存（MB）、对象数量
- 告警阈值：GC 已分配内存在 3 个或更多检查点间持续单调增长

**Unreal Engine：**
- 在每个检查点使用 `stat memory` 控制台命令
- 记录：已使用物理内存（MB）、可用物理内存
- 告警阈值：整个浸泡测试期间，已使用物理内存增长超过 50MB

### 稳定性观察项（当 focus = stability 或 all 时）

在每个检查点，记录：
- [ ] 自上一个检查点以来未发生崩溃、挂起或卡死
- [ ] 帧率仍在目标预算范围内（[target FPS] fps）
- [ ] 音频仍正常播放（无不同步或静音）
- [ ] 所有 HUD 元素仍正常渲染
- [ ] 输入响应符合预期（无输入丢失或延迟突增）

### 平衡性／疲劳度观察项（当 focus = balance 或 all 时）

在每个检查点收集主观观察结果：
- [ ] 核心机制是否仍让人感到有成就感（Y/N）
- [ ] 感知到的难度等级：[过于简单 / 合适 / 过于困难]
- [ ] 自上一个检查点以来，是否出现任何“我以前见过这个”的时刻？（新颖内容耗尽）
- [ ] 自上一个检查点以来，是否有任何感到受挫的时刻？记录原因。
- [ ] 自上一个检查点以来，是否有任何投入度达到峰值的时刻？记录原因。

## 协作协议

- **此技能生成协议——由人类执行**——切勿尝试自动运行浸泡测试。观察工作需要由人类观察员完成。
- **持续时间应与游戏的会话设计相匹配**——一款时长 5 分钟的游戏不需要进行 4 小时的浸泡测试；城市建造类游戏则可能需要。请酌情判断，如不明确则询问。
- **首次浸泡测试的关注范围应为 `all`**——缩小关注范围（仅内存）适用于特定修复后的回归浸泡测试，而非首次测试
- **写入前先询问**——创建协议文件前务必确认
