# 系统设计方案构建器

**目标：** 创建一份与风险相称、以证据为依据的目标系统设计，将需求转化为明确的边界、契约、数据流、故障行为、运维和权衡。仅修改获批准的设计文档；不得实施、审计或批准交付。

**执行契约：** 有序的复选框即为完成定义。将每一项在内部跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具故障均不构成证明。每个章节后重新核对各项。返回前，解决所有 `PENDING`，并且仅统计 `PROVEN` 和 `CLEARED`；对每个缺口应用该技能的结论和批准规则。
保留用户意图、范围和现有授权。继续已获授权的工作；仅针对具有实质影响的未解决选择或所需的外部批准提问。根据实质风险调整深度，但不得悄然跳过检查。保留依赖关系和安全顺序；其他情况下，为每项义务选择适当的验证方法。
将等效的用户或仓库证据视为有效输入；其他技能、具名工件或完整生命周期均不是前提条件。在可用时保留源需求和决策标识符。将复用证据绑定到相关源版本、未提交的变更、配置和环境；变更后仅使受影响的声明失效。
继续执行时，在恢复前重新核对任务、现有授权、当前状态和未解决的证据。对于长期工作，返回一条紧凑的继续记录，或更新已获授权的任务工件；只读技能不持久化该记录。区分工件就绪、已验证行为和执行外部操作的权限。
在任何必需批准之前准备已获授权的工作。如果某项指令阻碍进展，识别其确切来源并说明未解决的边界；不要基于一般性的谨慎凭空设立批准关卡。

## 工具路由

| 需求 | 首选能力 | 备选方案 |
|---|---|---|
| 需求与约束 | 已批准的需求、基线、决策和直接利益相关者输入 | 标记实质性缺口，并提出最小化的决策问题 |
| 当前实现与约定 | 仓库搜索、清单文件、入口点和架构工件 | 仅当用户或仓库确认其为绿地项目时才如此处理；否则将当前状态标记为 `UNKNOWN`，并在该缺口可能改变边界、兼容性或迁移时返回 `REVISE` 或 `BLOCKED` |
| 外部能力与限制 | 当前官方文档和规范 | 将声明标记为 `UNVERIFIED`；避免作出依赖供应商的承诺 |
| 估算 | 基于有来源工作负载假设的可复现算术计算 | 使用范围和敏感性分析；绝不将估算表述为测量结果 |
| 文档变更 | 对获批准的目标设计工件进行最小化补丁 | 若范围或路径不安全，则返回 `BLOCKED` |

将模式作为候选解决方案，而非目标。只有当某项需求、故障模式、所有权边界或经过衡量的时间跨度足以承担其生命周期成本时，才引入基础设施。

## 制品规则

- 复用清晰的目标设计文档；否则使用 `docs/architecture/target-design.md`。
- 按路径阅读可用的基线、当前状态、决策、接口、图示和迁移制品；这些制品均非必需。
- 分别标注事实、假设、估算、拟议决策和未解决的选择。
- 对具有重要影响的决策比较可信的替代方案，包括最简单可行的选项；当约束条件只允许一个选项时，记录原因，而不是臆造另一个方案。
- 优先选择可逆的方案，以及与系统相匹配的最简单拓扑。对于新应用，考虑模块化单体，再决定是否拆分为独立服务；不要将这种形态强加给库、插件或已有拓扑。
- 不要悄然更改已接受的决策；记录冲突以及所需的治理行动。

## 检查清单

### 1. 明确设计范围

- [ ] 在编辑前明确业务结果、参与者、用户旅程、范围、非目标、时间跨度、读者、语言，以及已批准的规范目标位置。
- [ ] 阅读仓库说明，并检查相关架构制品和当前实现。
- [ ] 提取功能需求和可衡量的质量驱动因素，并保留其来源和状态。
- [ ] 识别架构关键的未知事项，只提出那些答案会改变目标形态的问题。
- [ ] 当无法负责任地假设必要的业务边界或安全约束时，返回 `BLOCKED`。

### 2. 在选择组件前进行估算

- [ ] 在适用的情况下，估算平均和峰值请求或事件速率、并发量、负载和带宽、存储增长、保留量以及恢复数据量。
- [ ] 展示公式、范围、增长时间跨度和假设；识别可能导致方案选择发生逆转的变量。
- [ ] 识别可能首先出现的瓶颈，并为延后引入的扩展机制设定明确阈值。
- [ ] 将可用性、延迟、持久性、一致性、安全性、成本和可运维性要求，与实现偏好区分开来。
- [ ] 拒绝推测性的规模设计，并列出明确延后的复杂机制。

### 3. 定义领域、数据和契约

- [ ] 映射业务能力、领域或模块、所有权、不变量以及允许的依赖方向。
- [ ] 定义权威数据源、架构深度的数据模型、生命周期、保留策略、一致性和事务边界。
- [ ] 定义公共 API、事件、命令、架构、错误、幂等性、顺序、版本控制和兼容性预期。
- [ ] 定义信任边界、身份、授权、敏感数据、密钥、滥用控制以及与风险相称的审计需求。
- [ ] 除非框架和供应商细节确实构成约束，否则将其置于核心模型之外。

### 4. 构建 HLD 和关键 LLD

- [ ] 描述系统上下文、可部署单元、存储、队列、外部系统、职责以及带有明确标注的数据流。
- [ ] 针对关键旅程追踪成功、过载、依赖故障、部分故障、重试、超时、降级、恢复和取消流程。
- [ ] 仅对那些正确性、规模、安全性或可逆性风险足以值得实现级细节的组件进行深入设计。
- [ ] 定义可观测性、SLI 测量点、健康检查、部署策略、回滚、备份和运维人员操作。
- [ ] 定义拟议拓扑的所有权、团队影响、成本驱动因素和运维负担。

### 5. 决策与验证

- [ ] 根据需求、估算、故障行为、复杂性、成本、迁移和未来触发条件，对可信的备选方案进行比较。
- [ ] 陈述选定和拒绝的方案，包括后果、敏感点以及会重新开启该决策的假设。
- [ ] 识别值得拥有各自精简决策记录的重大决策，而无需启动另一个工作流。
- [ ] 为每个实质性驱动因素定义恰当的架构验收证据：契约检查、负载/故障实验、安全验证、恢复证明或可观测性信号。指定前提条件和通过标准；不要在设计期间执行它们。
- [ ] 概述从当前状态到目标状态的影响和兼容性需求，但不要扩展为完整的实施计划。

### 6. 编写与报告

- [ ] 编写上下文、驱动因素、估算、领域、契约、HLD、关键 LLD、故障与运维模型、安全性、备选方案、决策、验证、开放问题和演进触发条件。
- [ ] 保留已批准范围之外的现有内容，并且仅通过文档路径或标题链接共享工件。
- [ ] 重新阅读提案，检查无依据的事实、隐藏决策、混合抽象和缺乏正当理由的机制。
- [ ] 仅当设计的决策完整度足以进入实施规划时使用 `READY`；对于实质性但可解决的缺口使用 `REVISE`；当所需的意图、证据、权限或目标位置不可用时使用 `BLOCKED`。

- [ ] 证明每个实质性设计边界均可实施：将源需求关联到契约、数据、故障行为、未决选择和验收证据；区分已就绪的提案与已接受的决策。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖、矛盾、范围、结论和适用的清理工作。修正报告或已授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出契约

按用户的语言以如下顺序报告；保留全部五个字段，并且每项事实只陈述一次。较小的结果可以每个字段占一行；省略空表格，并且不要复制已链接的工件：

1. **结果：** 特定于 Skill 的结论和有证据支持的结果。
2. **范围：** 已审阅/变更的范围、排除项、基线和实质性假设。
3. **证据：** 以下特定于 Skill 的字段；区分事实、推断和未经验证的声明。链接工件；在有用时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的下一步操作；剩余风险和所需决策。

**特定于 Skill 的证据：** 工件路径；需求、估算、边界、契约、HLD/关键 LLD、已选定的决策、备选方案、证据和重新开启触发条件。总结验证/迁移需求、兼容性、发布、回滚、可观测性，以及仅影响实施规划的未决选择。
