# 流程映射器

将“这件事耗时太久，而且没人知道原因”转化为一份经过测量的流程图和按优先级排序的待办事项。大多数流程改进工作失败在两点上：它们绘制的是人们所描述的流程，而不是实际运行的流程；它们还将等待时间的节省错误地按劳动力成本节省来估值。本技能旨在同时避免这两个问题。

## 何时使用本技能

- **流程速度缓慢**，且没人能说清是哪个步骤导致的
- **工作在团队之间来回流转**，怀疑交接环节存在问题，但尚未进行测量
- **返工率很高**——提交内容被退回、工单被重新打开、订单被更正
- **在自动化任何环节之前**——检查该步骤是否根本就不应该存在
- **帮助新团队上手**其继承但无人记录的流程
- **改进计划需要一份待办事项列表**，并按回报而非投诉数量排序

## 本技能所需的输入

- 流程边界：触发事件、终止状态以及在流程中流转的单位
- 步骤列表，包括负责人（角色，而非具体人员）、每个步骤的处理时间和等待时间
- 尽可能使用系统时间戳而非自行报告的等待时间
- 每个步骤的返工率，以及每个循环返回到的步骤
- 每个步骤的记录系统，用于识别重复录入点
- 月度业务量和包含间接成本的小时成本，用于评估改进的价值

## 首先澄清

生成内容之前，请确认以下输入。如果有任何一项未知或含糊，请提问——不要假设：

- [ ] **我们要绘制哪个流程变体，它占总业务量的多少？**——绘制每一种例外情况会产生一张无法阅读的流程图；绘制仅占 20% 的路径则会优化错误的流程
- [ ] **等待时间来自哪里——时间戳还是记忆？**——自行报告的排队时间会被低估 40-70%，从而将约束错误地定位到其他步骤
- [ ] **目标是缩短交付周期、降低劳动力成本，还是提高质量？**——这些目标具有不同的约束条件，而且解决方案往往相反
- [ ] **业务方是否量化了速度提升的价值？**——如果没有业务方提供的数值，就无法对周期时间收益进行成本估算，必须单独论证

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草即可”，则继续，并在交付物顶部列出你的假设。

## 工作流

### 工作流 1——捕获并测量流程

1. 首先界定范围：在深入任何细节之前，先用一页内容就触发事件、终止状态、流转单位和流程变体达成一致。使用 `assets/process-map-template.md` 中的 SIPOC 框架。
2. 在组织研讨会之前，先观察实际工作过程。观察能够发现用于变通的电子表格和催办邮件；研讨会则无法发现这些。
3. 从系统时间戳中提取等待时间。使用中位数和第 85 百分位数，绝不要使用平均值——流程时间的分布具有很长的右尾。
4. 将每个步骤分类为增值、业务增值或非增值。根据审批的拒绝率对其进行检验：如果低于 5%，它就只是一个带着职位头衔的队列。
5. 运行分析器，并将建模得出的交付周期与实测的端到端交付周期进行核对。如果差距超过 20%，则意味着存在遗漏的步骤，或者更常见的是遗漏了等待时间。

```bash
python3 business-operations/process-mapper/scripts/process_analyzer.py \
  --input business-operations/process-mapper/assets/sample_process.json \
  --format text
```

### 工作流 2 — 诊断交接与返工循环

1. 对同一个流程文件运行交接分析器——无需单独输入。
2. 首先查看交接密度。如果每个步骤的负责人变更次数高于 0.5，整合所有权比优化任何单个步骤都更有效。
3. 检查总等待时间中有多少发生在交接环节。如果高于 60%，问题就出在团队之间，无论如何改进团队内部都无法解决。
4. 将每次系统切换都视为重新录入和数据丢失点，并将每个跨团队返工循环都视为一项检查；这项检查应放到触发返工的位置之前。
5. 关注来回移交：如果某个负责人先后参与了三个或更多彼此分离的环节，就应让其端到端负责相应流程段。

```bash
python3 business-operations/process-mapper/scripts/handoff_analyzer.py \
  --input business-operations/process-mapper/assets/sample_process.json \
  --format text
```

### 工作流 3 — 构建改进待办列表

1. 根据分析结果生成改进机会，并按以下改进层级依次应用：消除、整合、并行化、标准化、自动化。
2. 将每项节省拆分为 `touch_minutes_saved_per_unit`（人工时间，计入成本）和 `lead_minutes_saved_per_unit`（经过时间，不计入成本）。这种拆分方式是一项必要准则，可确保商业论证经得起检验。
3. 仅当企业已对其进行量化时，才提供 `annual_cycle_time_value`——该数字应由企业确定，而不是由分析师确定。
4. 运行评分器并查看分层结果。任何工作量超过 20 天的事项都是需要独立发起人的项目，而不是待办事项。
5. 在一种情况下应覆盖按回收期排序的顺序：如果一次通过率低于 85%，无论返工修复的回收期如何，都应优先安排。对于有一半单位需要返工的流程，流动性改进无法持续奏效。

```bash
python3 business-operations/process-mapper/scripts/improvement_scorer.py \
  --input business-operations/process-mapper/assets/sample_opportunities.json \
  --format json
```

## 决策框架

### 诊断阈值 [已验证]

| 信号 | 阈值 | 含义 |
|--------|-----------|---------------|
| 步骤占前置时间的比例 | 高于 20% | 这是制约因素 |
| 单个步骤的等待/操作时间比 | 高于 3x | 这是排队，而不是工作 |
| 等待/操作时间比 | 高于 10x | 批量排队式调度；应修正策略，而不是增加产能 |
| 每个步骤的返工率 | 高于 10% | 在进行任何提速工作之前先修复 |
| 端到端一次通过率 | 低于 85% | 返工是主要成本 |
| 交接密度 | 高于 0.5/step | 所有权碎片化 |
| 发生在交接环节的等待时间 | 高于 60% | 优化团队之间的协作，而不是团队内部 |
| 非增值操作时间 | 高于 25% | 自动化之前先消除 |
| 审批驳回率 | 低于 5% | 这种审批只是走过场 |

### 流程周期效率区间 [已验证]

对于事务型流程，PCE = 增值时间 / 前置时间：

| PCE | 区间 | 状况 |
|-----|------|-----------|
| 低于 5% | 较差 | 未改进的多团队流程。大多数流程最初都处于这一水平。 |
| 5-15% | 低于平均水平 | 已有一定流动性；队列仍然决定着前置时间。 |
| 15-25% | 平均 | 对于涉及三个或更多团队的流程而言较为合理。 |
| 25-50% | 良好 | 流动性强。剩余的改进空间在于批量大小和自动化。 |
| 高于 50% | 世界一流 | 在单一负责人流程之外很少见。请检查数据。 |

制造业基准并不适用。一个 PCE 为 20% 的跨职能审批流程表现良好，而不是很差。

### 改进层级 [已验证]

应用于同一个步骤时，越靠前的动词优于越靠后的动词：

| 排名 | 动词 | 问题 | 典型收益 |
|------|------|----------|-------------|
| 1 | 消除 | 这一步真的有必要发生吗？ | 该步骤的 100% |
| 2 | 合并 | 能否由同一个负责人完成这一步和下一步？ | 消除一次交接及其队列 |
| 3 | 并行 | 这一步必须等待上一步完成吗？ | 最多可节省较短分支的耗时 |
| 4 | 标准化 | 能否消除差异？ | 20-40%，并减少返工 |
| 5 | 自动化 | 能否由系统执行？ | 接触时间的 60-90% |

**最后才进行自动化。** 将本应消除的步骤自动化，会让浪费永久存在且消除成本高昂，因为今后的每次变更都需要经历一个开发周期。并行化是审批密集型流程中最未被充分利用的手段——信用、法务和安全审查通常并不存在真正的依赖关系，它们之所以按顺序执行，只是因为有人把流程画成了一条线。

### 节省价值的评估 [已验证]

| 节省项 | 计量单位 | 可核算成本？ |
|--------|----------|-----------|
| 消除的接触时间 | 工时 | 是——工时 x 综合费率 |
| 消除的等待时间 | 前置时间 | 只有在业务方提供数值时才可以 |

消除队列并不会释放任何人的工时。它可能通过加快收入实现或提高赢单率，产生远超人力节省的价值——但这个价值应由业务负责人提供，而不是来自分析师的电子表格。

## 反模式

### 将等待时间按人力成本核算
**错误：** 将前置时间减少总量乘以综合小时费率——“我们将每笔订单的耗时缩短了 25 小时，费率为每小时 72 美元，因此每笔订单可节省 1,800 美元。”
**产生原因：** 这种做法可以利用手头已有的数据得出一个惊人的数字，而且其算术形式与合理的接触时间计算完全相同。
**正确做法：** 只有接触时间才按人力成本核算。将前置时间的减少以其自身单位单独报告，并询问业务负责人这对他们而言价值多少。财务部门会在第一次审核时发现夸大的数字，而由此造成的可信度损失会连带影响同一份文档中真正的节省成果。

### 对描述中的流程进行建模
**错误：** 根据研讨会、现有 SOP 或对管理人员的访谈构建流程图，然后将其作为事实进行分析。
**产生原因：** 这种做法快速、轻松，而且房间里的每个人都相信自己的描述是准确的。没有人在撒谎——他们描述的是设计中的流程，因为重复发生的变通做法已经变得难以察觉。
**正确做法：** 观察工作实际发生的过程，并从系统时间戳中提取等待时间。然后将流程图逐项讲给实际执行这些工作的人听，以此进行验证；询问“我哪里弄错了？”，而不是“这样看起来对吗？”如果模型计算出的前置时间比实测值低 20% 以上，就说明你遗漏了步骤或等待时间——通常是那些没人想到要提及的催办邮件和批处理延迟。

### 优化非约束环节
**错误：** 实施一项改进计划，让六个步骤变得更快，结果却发现端到端前置时间没有变化。
**原因：** 改进工作投向了团队愿意改进的地方，而不是约束所在之处；每一项局部收益都真实且可衡量——只是无法惠及客户。
**正确做法：** 找到约束，在投入任何资源之前先充分利用约束并让其他环节服从约束，之后才增加产能。改进非约束步骤可以证明不会对流程层面产生任何改变。每次修复后都要重新测量，因为约束一旦得到缓解，就会发生转移。

### 在消除之前就自动化
**错误：** 委托开发软件来加速一个本就不该存在的步骤——典型例子是为一个仅驳回 2% 提交内容的审批环节构建自动化审批工作流。
**原因：** 自动化有预算科目、供应商和可见的交付成果。消除一个步骤则需要说服该步骤的负责人，让其接受自己的控制措施并无必要；这是一个没有预算代码的政治问题。
**正确做法：** 在编写任何代码之前，先执行改进层级中的前四个动词。自动化会将当前流程固化到软件中，并使此后的每次变更都成为开发项目——因此，自动化浪费的成本并不在于构建本身，而在于此后十年间为绕过它而持续付出的代价。
