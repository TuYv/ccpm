此 Skill 会利用当前的对话上下文和对代码库的理解生成一份规格说明（你可能将此文档称为 PRD）。不要访谈用户——只需综合你已经掌握的信息。

Issue Tracker 和分诊标签词汇应该已经提供给你——如果尚未提供，请运行 `/mattpocock:setup-matt-pocock-skills`。

## 关键要求：不要访谈——综合你已经掌握的信息

不要访谈用户；规格说明应综合上下文中已有的对话内容和对代码库的理解。在现有的最高层接缝处进行测试，优先使用一个接缝而不是多个接缝——在编写之前，先与用户确认这些接缝。

## 流程

1. 如果你尚未探索仓库，请探索仓库以了解代码库的当前状态。在整个规格说明中使用项目的领域术语表词汇，并遵循与你所修改区域相关的所有 ADR。

2. 勾勒出你计划用来测试该功能的接缝。应优先使用现有接缝，而不是创建新接缝。尽可能使用最高层的接缝。如果需要新接缝，请在尽可能高的层级提出。代码库中的接缝越少越好——理想数量是一个。

与用户确认这些接缝是否符合他们的预期。

3. 使用以下模板编写规格说明，然后将其发布到项目 Issue Tracker。应用 `ready-for-agent` 分诊标签——无需进行额外分诊。

<spec-template>

## 问题陈述

从用户的角度描述用户所面临的问题。

## 解决方案

从用户的角度描述该问题的解决方案。

## 用户故事

一份很长的、带编号的用户故事列表。每个用户故事都应采用以下格式：

1. 作为一名 <actor>，我想要 <feature>，以便 <benefit>

<user-story-example>
1. 作为一名手机银行客户，我想查看我的账户余额，以便能够在消费方面做出更明智的决定
</user-story-example>

这份用户故事列表应极其详尽，并覆盖该功能的所有方面。

## 场景

从上述用户故事中派生出的可执行场景，使用 Gherkin（Given/When/Then）编写。每个场景固定一种行为；这些场景共同构成用于验证实现的可执行规格说明。有关场景编写指南和 `.feature` 存储约定，请参阅 `/mattpocock:bdd`。

## 实现决策

列出已作出的实现决策。其中可以包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 开发者提供的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

例外情况：如果原型生成的代码片段能够比文字更精确地表达某项决策（状态机、reducer、schema、类型结构），请将其内联到相关决策中，并简要注明它来自原型。将其精简至包含关键决策的部分——不要提供可运行的演示，只保留重要内容。

## 测试决策

列出已做出的测试决策。包括：

- 描述什么是好的测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似类型的测试）

## 范围之外

描述不在此规范范围内的事项。

## 补充说明

有关该功能的任何其他说明。

</spec-template>
