# 代码成熟度评估器

## 目的

使用 Trail of Bits 的 9 大类别框架系统化评估代码库的成熟度。提供基于证据的评级和可操作的建议。

**框架**：Building Secure Contracts - Code Maturity Evaluation v0.1.0

---

## 工作原理

### 阶段 1：探索
探索代码库以了解：
- 项目结构与平台
- 合约/模块文件
- 测试覆盖率
- 文档可用性

### 阶段 2：分析
针对全部 9 个类别中的每一个，我将：
- **搜索代码**以查找相关模式
- **阅读关键文件**以评估实现
- 结合文件引用**呈现发现**
- 就代码中无法看到的流程**提出澄清性问题**
- 依据标准**确定评级**

### 阶段 3：报告
生成：
- 执行摘要
- 成熟度记分卡（全部 9 个类别的评级）
- 附带证据的详细分析
- 按优先级排序的改进路线图

---

## 评级体系

- **缺失（0）**：不存在/未实现
- **薄弱（1）**：需要进行多项重大改进
- **适中（2）**：尚可，仍可改进
- **满意（3）**：高于平均水平，仅需少量改进
- **优异（4）**：卓越，仅可能有微小改进

**评级逻辑**：
- 任一标准为“薄弱” → **薄弱**
- 无“薄弱” + 部分“适中”级标准未满足 → **适中**
- 全部“适中”级标准已满足 + 部分“满意”级标准已满足 → **满意**
- 全部“满意”级标准 + 卓越实践 → **优异**

## 9 大类别

我会评估 9 个综合类别，涵盖代码成熟度的各个方面。有关详细标准、分析方法和评级阈值，请参见 [ASSESSMENT_CRITERIA.md](resources/ASSESSMENT_CRITERIA.md)。

### 快速参考：

**1. 算术运算**
- 溢出保护机制
- 精度处理与舍入
- 公式规范
- 边界情况测试

**2. 审计**
- 事件定义与覆盖
- 监控基础设施
- 应急响应规划

**3. 身份验证/访问控制**
- 权限管理
- 角色分离
- 访问控制测试
- 密钥泄露场景

**4. 复杂度管理**
- 函数作用域与清晰度
- 圈复杂度
- 继承层次
- 代码重复

**5. 去中心化**
- 中心化风险
- 升级控制机制
- 用户退出路径
- 时间锁/多签模式

**6. 文档**
- 规范与架构
- 行内代码文档
- 用户故事
- 领域术语表

**7. 交易排序风险**
- MEV 漏洞
- 抢跑防护
- 滑点控制
- 预言机安全

**8. 底层操作**
- 汇编的使用
- 不安全的代码段
- 低级调用
- 合理性说明与测试

**9. 测试与验证**
- 测试覆盖率
- 模糊测试与形式化验证
- CI/CD 集成
- 测试质量

有关完整的评估标准——包括我将分析的内容、我将向你提出的问题，以及详细的评级阈值（薄弱/适中/满意/优异）——请参见 [ASSESSMENT_CRITERIA.md](resources/ASSESSMENT_CRITERIA.md)。

## 示例输出

评估完成后，你将收到一份全面的成熟度报告，其中包括：

- **执行摘要**：总分、前 3 项优势、前 3 项差距、优先建议
- **成熟度记分卡**：包含全部 9 个类别的表格，附评级分数和备注
- **详细分析**：逐类别的细分说明，附证据（file:line 引用）
- **改进路线图**：按优先级排序的建议（危急/高/中）及工作量估算

完整的评估报告示例请参见 [EXAMPLE_REPORT.md](resources/EXAMPLE_REPORT.md)。

## 评估流程

被调用后，我将：

1. **探索代码库**
   - 查找合约/模块文件
   - 识别测试文件
   - 定位文档

2. **分析每个类别**
   - 搜索相关代码模式
   - 阅读关键实现
   - 对照标准进行评估
   - 收集证据

3. **交互式评估**
   - 结合文件引用呈现我的发现
   - 询问代码中无法看到的流程
   - 讨论处于边界的情况
   - 共同确定评级

4. **生成报告**
   - 执行摘要
   - 成熟度记分卡表格
   - 附证据的详细类别分析
   - 按优先级排序的改进路线图

## 合理化借口（请勿跳过）

| 合理化借口 | 为什么它是错的 | 必须采取的行动 |
|-----------------|----------------|-----------------|
| “发现了一些问题，评估已完成” | 评估要求对全部 9 个类别进行评价 | 完成全部 9 个类别的评估，且每个类别都附有证据 |
| “我看到了事件，审计类别看起来不错” | 仅有事件并不等于审计成熟度 | 检查日志记录的全面性、测试以及应急响应流程 |
| “代码看起来很简单，复杂度很低” | 表面上的简单会掩盖组合复杂度 | 分析圈复杂度、依赖深度、状态机转换 |
| “这不是 DeFi 协议，MEV 类别不适用” | MEV 的范围超出了 DeFi（治理、NFT、游戏） | 在宣布“不适用”之前，先通过交易排序分析进行验证 |
| “没有发现汇编，底层类别不适用” | 底层风险包括外部调用、delegatecall、内联汇编 | 在跳过该类别之前，先搜索所有底层模式 |
| “这花费的时间太长了” | 透彻的评估需要为每个类别投入时间 | 完成全部 9 个类别的评估，并就链下流程提出澄清问题 |
| “我可以不凭证据就给出评级” | 没有 file:line 引用的评级 = 没有依据的断言 | 为每个类别的评估收集具体的代码证据 |
| “用户会知道该改进什么” | 模糊的指导 = 无法行动 | 提供按优先级排序的路线图，包含具体的改进项和工作量估算 |

## 报告格式

有关详细的报告结构与模板，请参见 [REPORT_FORMAT.md](resources/REPORT_FORMAT.md)。

### 结构：

1. **执行摘要**
   - 项目名称与平台
   - 总体成熟度（平均评级）
   - 前 3 项优势
   - 前 3 项关键差距
   - 优先建议

2. **成熟度记分卡**
   - 包含全部 9 个类别的表格
   - 评级与分数
   - 关键发现的备注

3. **详细分析**
   - 逐类别的细分
   - 附 file:line 引用的证据
   - 差距与改进行动

4. **改进路线图**
   - 危急（立即）
   - 高（1-2 个月）
   - 中（2-4 个月）
   - 工作量估算与影响
