# 仓库发布者

**目标：** 仅发布用户已授权的更改，然后从远程源验证结果。

**执行约定：** 有序复选框是完成定义。内部将每项跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委托或工具失败都不能作为证明。每个部分后协调各项。返回前，解决所有 `PENDING`，且仅计入 `PROVEN` 和 `CLEARED`；对每个缺口应用此技能的结论和审批规则。
保留用户意图、范围和现有授权。继续已授权的工作；仅针对会产生重大影响的未决选择或必需的外部批准进行询问。根据实质风险调整深度，不得悄然跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选能力 | 备选方案 |
|---|---|---|
| 范围、暂存、历史记录和同步 | 原生 Git CLI | 如果无法获得等效 Git 证据则停止 |
| 仓库验证 | 项目原生命令和已安装的验证器 | 有文档记录的手动检查 |
| 远程分支和 CI 状态 | 已认证的托管 CLI 或连接器 | Git 远程证据加直接工作流 URL |
| 干净源验证 | 当分发面发生变化时，使用临时克隆和隔离的主机配置 | 远程原始文件，并对所需安装证据标记为 `BLOCKED` |
| 静态站点验证 | 部署工作流加直接 HTTP 请求 | 托管 API 部署状态 |
| 当前市场行为 | 官方主机文档 | 标记假设并避免破坏性重试 |

优先使用紧凑的 Git 输出，然后再打开将要暂存文件的完整差异。不要以隐藏失败退出代码的方式管道命令。

对远程事实使用托管 API，对仓库事实使用 Git。本地分发或部署状态无法证明远程使用者更新有效。

## 检查清单

### 确定范围和证据

- [ ] 确认用户明确请求提交和推送，并识别目标分支。
- [ ] 在变更前阅读仓库说明、发布规则和当前分支策略。
- [ ] 检查 `git status -sb`、已暂存和未暂存的差异、未跟踪文件、远程仓库以及最近的提交风格。
- [ ] 识别无关的用户更改；未经明确的整个工作区授权，不得暂存这些更改。
- [ ] 像检查编辑后的文本一样仔细检查删除的文件和生成的文件。
- [ ] 检查行为、安装命令、目录、布局或公共站点是否需要相应的文档更新。
- [ ] 除非请求或仓库策略明确包含，否则不得在常规发布期间更改版本、标签或发布元数据。
- [ ] 对于市场编辑，确认每个稳定标识符均保持不变，除非已批准有意迁移。
- [ ] 当存在多个主机目录且仓库策略要求保持一致时，确认它们按要求顺序包含相同的分发单元。
- [ ] 当元数据在多个清单或目录中重复时，确认描述和源路径与规范源一致。

### 验证路由

- [ ] 在通用检查之前，发现并运行仓库原生的验证命令。
- [ ] 对于已更改的技能，运行仓库要求或主机原生的技能验证器，或执行其文档化的手动回退方案。
- [ ] 对于已更改的插件或包，运行仓库要求的验证器，或执行其文档化的手动回退方案。
- [ ] 对于存在且已更改，或仓库策略要求的每个分发面，运行所有主机原生严格验证器。
- [ ] 仅运行仓库和受影响面要求的目录一致性、清单解析、过时引用、本地链接和空白检查。
- [ ] 仅运行相关产品测试；不要在缺少仓库策略的情况下杜撰重量级发布门禁。
- [ ] 在确认必需检查失败时，于提交前停止，除非用户明确接受该失败。
- [ ] 使用确切缺失的依赖项或环境记录跳过的检查。

### 同步与提交

- [ ] 提交前获取目标远程仓库，并将本地 HEAD 与远程分支进行比较。
- [ ] 如果落后或发生分叉，检查双方并在授权的分支工作流内进行协调，同时保留用户更改；对于未解决的语义冲突或必需的历史重写，停止操作。绝不隐式强制推送。
- [ ] 当工作树包含混合更改时，暂存明确指定的路径；仅当用户批准所有更改时，才暂存整个工作树。
- [ ] 暂存后检查缓存的差异和差异统计。
- [ ] 从暂存集合中排除密钥、本地缓存、临时产物和非预期凭据，同时不删除用户拥有的文件；如果预期更改包含密钥，阻止该发布并报告经脱敏的证据。
- [ ] 遵循仓库的提交消息约定，并总结整个暂存更改。
- [ ] 保留已配置的提交签名和署名策略；不要虚构贡献者身份或禁用必需签名。
- [ ] 创建提交并记录其完整 SHA。
- [ ] 推送到授权分支，不更改分支保护规则，也不使用强制推送。

### 远程验证

- [ ] 通过 Git 或托管 API 在授权远程仓库上验证已发布的提交；仅当身份或同步状态不确定时才使用第二个来源。
- [ ] 以有界等待并通过直接运行 URL 跟踪推送提交所需的 CI。如果执行无法继续等待，将待处理状态报告为 `PARTIAL`；不要将待处理等同于成功。
- [ ] 如果静态站点发生更改，等待部署完成，并使用缓存规避请求验证线上内容。
- [ ] 如果安装或市场内容发生更改，将授权的、消费者可访问的远程仓库克隆到干净的临时目录中，并验证受影响的分发表面。
- [ ] 当安装或更新行为发生变化时，在隔离的主机配置中，从其文档化的分发源测试至少一个受影响的包或插件。
- [ ] 当存在稳定的分发标识符或版本时，验证已安装产物能以预期标识符和版本解析。
- [ ] 使临时主机配置与用户活动设置保持隔离，并在之后安全地移除它。
- [ ] 重新检查本地工作树和 HEAD 是否与已发布提交一致。如果远程仓库并发推进，验证其仍包含已发布提交并报告两个 SHA；不要覆盖较新的工作以恢复一致性。

### 安全门槛

- [ ] 绝不在输出中暴露认证令牌或凭据值。
- [ ] 除非明确要求，否则绝不创建发布、标签、包发布、讨论或拉取请求。
- [ ] 绝不删除远程分支或将默认分支作为副作用进行更改。
- [ ] 遇到分支保护、认证或必需检查时，返回 `BLOCKED`，而不是绕过它们。

## 判定

- `PUBLISHED` — 提交、推送、必需 CI 和适用的远程验证均已成功。
- `PARTIAL` — 推送已成功，但非破坏性的远程检查待完成或已失败。
- `BLOCKED` — 由于授权、同步、验证或远程访问失败，发布未能完成。

## 自检

- [ ] **返回前进行核对。** 检查项目级证据、需求覆盖情况、矛盾之处、范围、判定和适用的清理工作。更正报告或已授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出约定

以用户的语言按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。较小的结果可每个字段使用一行；省略空表格，不要复制已链接的产物：

1. **结果：** 技能特定的判定和有证据支持的结果。
2. **范围：** 审查/变更范围、排除项、基线和重要假设。
3. **证据：** 以下的技能特定字段；区分事实、推断和未经验证的主张。链接产物；必要时使用表格。
4. **验证：** 检查/结果、不可用证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或每个 `UNPROVEN` 项目的原因、结果影响和精确的下一步操作；残余风险和所需决策。

**技能特定证据：** 已发布/排除的路径、分支、完整提交 SHA、远程 URL、验证结果、CI/部署 URL，以及适用的干净源安装/更新证明。对于 `PARTIAL`，说明已推送的提交是否可以安全保留，以及完成验证的可观察事件。仅当远程提交和每个适用的必需工作流均已观察到时，才使用 `PUBLISHED`。
