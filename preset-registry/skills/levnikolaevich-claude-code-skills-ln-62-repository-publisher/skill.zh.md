# 仓库发布者

**目标：** 仅发布用户已授权的更改，然后从远程源验证结果。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序处理每一项，并且仅当该项的操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的判定、决策和审批规则应用于每个未完成项，并在回复开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 范围、暂存、历史记录和同步 | 原生 Git CLI | 如果无法获得等效的 Git 证据，则停止 |
| 仓库验证 | 项目原生命令和已安装的验证器 | 有文档说明的手动检查 |
| 远程分支和 CI 状态 | 已认证的托管平台 CLI 或连接器 | Git 远程证据以及直接工作流 URL |
| 干净源验证 | 当分发界面发生更改时，使用临时克隆和隔离的主机配置 | 远程原始文件，并将所需的安装证据标记为 `BLOCKED` |
| 静态站点验证 | 部署工作流以及直接 HTTP 请求 | 托管 API 的部署状态 |
| 当前市场行为 | 官方托管平台文档 | 标明假设并避免破坏性重试 |

优先使用精简的 Git 输出，然后再打开将被暂存文件的完整差异。切勿以会隐藏失败退出代码的方式通过管道传递命令。

使用托管 API 获取远程事实，使用 Git 获取仓库事实。本地分发或部署状态无法证明远程使用者的更新可以正常工作。

## 检查清单

- [ ] 确认用户明确要求提交并推送，并确定目标分支。
- [ ] 在进行更改之前，阅读仓库说明、发布规则和当前分支策略。
- [ ] 检查 `git status -sb`、已暂存和未暂存的差异、未跟踪文件、远程仓库以及近期提交风格。
- [ ] 识别用户无关的更改；除非明确授权整个工作树，否则不要暂存这些更改。
- [ ] 像检查已编辑文本一样仔细检查删除内容和生成的文件。
- [ ] 检查行为、安装命令、目录、布局或公共站点是否需要相应的文档更新。
- [ ] 不要仅仅因为缺少变更日志就创建一个；应遵循仓库中记录的发布策略。
- [ ] 在常规发布期间，不要更改版本、标签或发布元数据，除非请求或仓库策略明确包含这些更改。
- [ ] 对于市场编辑，确认每个稳定标识符均未更改，除非已批准有意的迁移。
- [ ] 当存在多个托管平台目录且仓库策略要求保持一致时，确认它们以要求的顺序包含相同的分发单元。
- [ ] 当元数据在多个清单或目录中重复时，确认描述和源路径与规范源一致。

## 验证路由

- [ ] 在运行通用检查之前，先发现并运行仓库原生的验证命令。
- [ ] 对于已更改的技能，运行仓库要求或宿主原生的技能验证器，或者执行其文档中说明的手动回退流程。
- [ ] 对于已更改的插件或软件包，运行仓库要求的验证器，或者执行其文档中说明的手动回退流程。
- [ ] 对于分发载体已存在且已更改，或仓库策略要求的情况，运行所有宿主原生的严格验证器。
- [ ] 仅运行仓库要求且受影响载体所需的目录一致性、清单解析、过时引用、本地链接和空白字符检查。
- [ ] 仅运行相关的产品测试；如果仓库策略中没有要求，不要自行设置重量级发布门禁。
- [ ] 如果确认某项必需检查失败，则在提交前停止，除非用户明确接受该失败。
- [ ] 记录跳过的检查，并注明缺失的确切依赖项或环境。

## 同步与提交

- [ ] 在提交之前，拉取目标远程仓库的信息，并将本地 HEAD 与远程分支进行比较。
- [ ] 如果历史记录发生分叉，请停止并报告双方的提交；不要隐式强制推送或重写历史记录。
- [ ] 当工作树中混有其他更改时，暂存明确的路径；仅当用户批准所有更改时，才暂存整个工作树。
- [ ] 暂存后检查缓存区差异和差异统计。
- [ ] 从暂存集中移除密钥、本地缓存、临时产物和无意包含的凭据。
- [ ] 遵循仓库的提交消息惯例，并概述整个暂存更改。
- [ ] 除非仓库策略要求或用户提出请求，否则不要添加自动生成的共同作者或签名。
- [ ] 创建提交并获取其完整 SHA。
- [ ] 推送到已获授权的分支，不得更改分支保护设置或使用强制推送。

## 远程验证

- [ ] 在可用时，同时使用 Git 和托管平台 API，确认远程分支解析到已推送的提交。
- [ ] 监视该提交所需的 CI 运行直至完成；报告运行页面的直接 URL 和失败情况。
- [ ] 如果静态网站发生更改，请等待部署完成，并使用绕过缓存的请求验证线上内容。
- [ ] 如果安装或市场内容发生更改，请将获授权且消费者可访问的远程仓库克隆到干净的临时目录中，并验证受影响的分发载体。
- [ ] 当安装或更新行为发生更改时，在隔离的宿主配置中，至少从其文档指定的分发源测试一个受影响的软件包或插件。
- [ ] 如果存在稳定的分发标识符或版本，请验证已安装的产物能否解析为预期的标识符和版本。
- [ ] 将临时宿主配置与用户的当前设置隔离，并在之后安全移除。
- [ ] 重新检查本地工作树，并确认本地 HEAD 与远程分支一致。

## 安全门禁

- [ ] 绝不在输出中暴露身份验证令牌或凭据值。
- [ ] 除非明确要求，否则绝不创建发布、标签、软件包发布、讨论或拉取请求。
- [ ] 绝不删除远程分支，也不将更改默认分支作为附带操作。
- [ ] 绝不将推送成功视为 CI、市场刷新或部署成功的证明。
- [ ] 遇到分支保护、身份验证或必需检查时，返回 `BLOCKED`，而不是绕过它们。

## 判定

- `PUBLISHED` — 提交、推送、必需的 CI 以及适用的远程验证均已成功完成。
- `PARTIAL` — 推送已成功，但非破坏性的远程检查仍在等待中或已失败。
- `BLOCKED` — 由于授权、同步、验证或远程访问失败，发布未能完成。

## 输出约定

返回：

1. 已发布的范围和排除的更改。
2. 分支、提交 SHA 和远程 URL。
3. 验证命令及其结果。
4. CI 和部署 URL。
5. 适用时，提供从干净源进行安装或更新的证据。
6. 判定。
7. 剩余风险以及任何需要手动跟进的事项。

如果发布状态为 `PARTIAL`，请说明已推送的提交是否可以安全保留，以及出现什么可观察事件后即可完成剩余检查。

在远程提交和每个适用的必需工作流均可观察到之前，不要将结果称为 `PUBLISHED`。
