# 仓库发布器

**目标：** 仅发布用户已授权的更改，然后从远程源验证结果。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框跟踪为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用表明其条件触发器不存在的证据将其解决为 `CLEARED`，或解决为 `UNPROVEN`；读取、提及、委派、跳过或工具失败都不能作为证明。
返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为完成，将此技能的裁决、决策和审批规则应用于每个 `UNPROVEN` 项，并在开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 范围、暂存、历史记录和同步 | 原生 Git CLI | 如果无法获得等效的 Git 证据则停止 |
| 仓库验证 | 项目原生命令和已安装的验证器 | 有文档记录的手动检查 |
| 远程分支和 CI 状态 | 已认证的托管平台 CLI 或连接器 | Git 远程证据加直接工作流 URL |
| 干净源代码验证 | 当分发面发生变化时，使用临时克隆和隔离的主机配置 | 远程原始文件，并对所需的安装证据标记为 `BLOCKED` |
| 静态站点验证 | 部署工作流加直接 HTTP 请求 | 托管平台 API 部署状态 |
| 当前市场行为 | 官方主机文档 | 标记假设并避免破坏性重试 |

优先使用紧凑的 Git 输出，然后打开将要暂存的文件的完整差异。不要以隐藏失败退出代码的方式通过管道连接命令。

使用托管平台 API 获取远程事实，使用 Git 获取仓库事实。本地分发或部署状态无法证明远程使用者更新正常工作。

## 检查清单

- [ ] 确认用户明确请求了提交和推送，并确定目标分支。
- [ ] 在执行变更前，阅读仓库说明、发布规则和当前分支策略。
- [ ] 检查 `git status -sb`、已暂存和未暂存的差异、未跟踪文件、远程仓库以及近期的提交风格。
- [ ] 识别无关的用户更改；未经明确的整个工作区授权，不要暂存这些更改。
- [ ] 像仔细检查已编辑文本一样检查删除内容和生成的文件。
- [ ] 检查行为、安装命令、目录、布局或公共站点是否需要相应的文档更新。
- [ ] 不要仅仅因为缺少变更日志就创建一个；遵循仓库记录的发布策略。
- [ ] 在普通发布期间不要更改版本、标签或发布元数据，除非请求或仓库策略明确包含这些内容。
- [ ] 对于市场编辑，确认每个稳定标识符都未发生更改，除非已批准有意进行迁移。
- [ ] 当存在多个主机目录且仓库策略要求保持一致时，确认它们包含顺序要求一致的相同分发单元。
- [ ] 当元数据在多个清单或目录中重复时，确认描述和源路径与规范源一致。

## 验证路由

- [ ] 在执行通用检查之前，先发现并运行仓库原生的验证命令。
- [ ] 对于已更改的技能，运行仓库要求的验证器或宿主原生的技能验证器，或者执行其文档中说明的手动回退方案。
- [ ] 对于已更改的插件或包，运行仓库要求的验证器，或者执行其文档中说明的手动回退方案。
- [ ] 运行所有分发面存在且已更改，或根据仓库策略要求运行的宿主原生严格验证器。
- [ ] 仅运行仓库要求且与受影响分发面相关的目录一致性、清单解析、过时引用、本地链接和空白检查。
- [ ] 仅运行相关的产品测试；如果仓库策略没有规定重量级发布门禁，不要自行设定。
- [ ] 在确认某项必需检查失败后，于提交前停止，除非用户明确接受该失败。
- [ ] 记录跳过的检查，并注明确切缺失的依赖或环境。

## 同步与提交

- [ ] 在提交前获取目标远程仓库，并将本地 HEAD 与远程分支进行比较。
- [ ] 如果历史发生分歧，停止并报告双方的提交；不要强制推送，也不要隐式重写历史。
- [ ] 当工作区包含混合变更时，暂存明确的路径；只有在用户批准所有变更时，才暂存整个工作区。
- [ ] 暂存后检查缓存区中的差异和差异统计。
- [ ] 从暂存集合中移除机密信息、本地缓存、临时产物和非预期的凭据。
- [ ] 遵循仓库的提交消息约定，并概括整个暂存变更。
- [ ] 除非仓库策略或用户要求，否则不要添加自动化共同作者或签名。
- [ ] 创建提交并记录其完整 SHA。
- [ ] 推送到已授权的分支，不得更改分支保护设置或使用强制推送。

## 远程验证

- [ ] 使用 Git 以及（如果可用）托管平台 API，确认远程分支解析到已推送的提交。
- [ ] 持续观察该提交所需的 CI 运行，直到其完成；报告直接的运行 URL 和失败信息。
- [ ] 如果静态网站发生更改，等待部署完成，并使用缓存清除请求验证线上内容。
- [ ] 如果安装内容或市场内容发生更改，将一个已授权、消费者可访问的远程仓库克隆到干净的临时目录中，并验证受影响的分发面。
- [ ] 当安装或更新行为发生变化时，使用其文档规定的分发源，在隔离的宿主配置中至少测试一个受影响的包或插件。
- [ ] 当存在稳定的分发标识符或版本时，验证已安装的产物能在预期的标识符和版本下解析。
- [ ] 将临时宿主配置与用户当前使用的设置隔离，并在之后安全地移除。
- [ ] 重新检查本地工作区，并确认本地 HEAD 与远程分支一致。

## 安全门禁

- [ ] 绝不在输出中暴露身份验证令牌或凭据值。
- [ ] 除非明确提出请求，否则绝不创建发布、标签、包发布、讨论或拉取请求。
- [ ] 绝不删除远程分支，也不应作为副作用修改默认分支。
- [ ] 绝不将推送成功视为 CI、市场刷新或部署成功的证明。
- [ ] 返回 `BLOCKED`，而不是绕过分支保护、身份验证或必需的检查。

## 结论

- `PUBLISHED` — 提交、推送、必需的 CI 以及适用的远程验证均已成功。
- `PARTIAL` — 推送已成功，但一项非破坏性的远程检查仍在等待中或已失败。
- `BLOCKED` — 由于授权、同步、验证或远程访问失败，发布未完成。

## 输出契约

返回：

1. 已发布的范围和排除的更改。
2. 分支、提交 SHA 和远程 URL。
3. 验证命令及其结果。
4. CI 和部署 URL。
5. 适用时，干净源代码安装或更新的证据。
6. 结论。
7. 剩余风险和任何需要手动跟进的事项。

如果发布状态为 `PARTIAL`，请说明已推送的提交是否可以安全地保留，并说明哪个可观察事件会完成剩余检查。

在远程提交和所有适用的必需工作流均可观测到之前，不要将结果称为 `PUBLISHED`。
