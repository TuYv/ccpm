Runs both reviews in parallel sub-agents and reports them side by side. Use when the user wants to review a branch, a PR, work-in-progress changes, or asks to "review since X".

对 `HEAD` 与用户提供的固定点之间的差异进行双维度审查：

- **规范** — 代码是否符合此仓库中记录的编码规范？
- **规约** — 代码是否忠实地实现了原始 issue / PRD / 规约？如果规约包含 Gherkin 场景（来自 `/mattpocock:bdd`），则这些场景是权威的验收标准。

两个维度会作为**并行子代理**运行，以免相互污染上下文，之后此技能会汇总它们的发现。

issue 跟踪器应该已经提供给你——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/mattpocock:setup-matt-pocock-skills`。

## 流程

### 1. 固定比较点

无论用户指定了什么，都将其作为固定点——可以是 commit SHA、分支名称、标签、`main`、`HEAD~5` 等。如果用户没有指定，请询问。

一次性确定差异比较命令：`git diff <fixed-point>...HEAD`（使用三点语法，因此会相对于合并基准进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`），并且差异非空。无效的引用或空差异应该在这里导致失败——而不是在两个并行子代理内部失败。

### 2. 确定规约来源

按以下顺序查找原始规约：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——按照 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能匹配的 PRD/规约文件。
4. 如果什么都没找到，使用 AskUserQuestion 工具询问规约位于何处（选项：仓库中 / 从 issue 或 PR 链接 / 外部文档 / 不存在规约）。如果没有规约，**规约**子代理将跳过并报告“没有可用的规约”。

### 3. 确定规范来源

仓库中任何说明代码应如何编写的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库记录的内容外，规范维度始终包含下面的**代码异味基线**——这是一组固定的 Fowler 代码异味（_重构_，第 3 章），即使仓库没有记录任何规范也适用。它受以下两条规则约束：

- **仓库规范优先。** 仓库中记录的规范始终具有最高优先级；如果仓库认可某种会被基线标记的做法，则不报告该异味。
- **始终需要判断。** 每种异味都是带标签的启发式判断（“可能存在依恋情结”），绝非硬性违规——并且与此处的任何规范一样，凡是工具已经强制执行的内容都应跳过。

每种异味都按照*它是什么* → *如何修复*的形式描述；请结合差异进行匹配：

- **神秘命名** — 函数、变量或类型的名称无法揭示其用途或所保存的内容。→ 对其重命名；如果无法找到一个如实表达含义的名称，则说明设计本身含糊不清。
- **重复代码** — 相同的逻辑结构出现在本次变更的多个差异块或文件中。→ 提取共享结构，并从两处调用它。
- **依恋情结** — 某个方法访问另一个对象的数据比访问自身数据还多。→ 将该方法移动到它所依恋的数据上。
- **数据泥团** — 相同的几个字段或参数总是一起传递（表明某个类型亟待诞生）。→ 将它们组合为一个类型，并传递该类型。
- **基本类型偏执** — 使用基本类型或字符串表示一个本应拥有自身类型的领域概念。→ 为该概念创建一个小型专用类型。
- **重复条件分支** — 针对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 使用多态替代，或者让两处共享同一个映射。
- **霰弹式修改** — 一个逻辑变更迫使你在差异中的许多文件内进行分散修改。→ 将需要一起变更的内容集中到一个模块中。
- **发散式变化** — 一个文件或模块因为多个不相关的原因而被修改。→ 将其拆分，使每个模块只因一个原因而变化。
- **夸夸其谈的通用性** — 为规约中并不存在的需求添加抽象、参数或钩子。→ 删除它；将其重新内联，直到真正的需求出现。
- **消息链** — 调用方不应依赖的长串 `a.b().c().d()` 导航。→ 将这段遍历隐藏在第一个对象的某个方法之后。
- **中间人** — 类或函数主要只是将调用委托给后续对象。→ 移除它，直接调用真正的目标。
- **被拒绝的遗赠** — 子类或实现者忽略或覆盖了所继承内容中的大部分。→ 放弃继承，改用组合。

### 4. 并行启动两个子智能体

发送一条包含两个 `Agent` 工具调用的消息。

**标准子智能体提示词** — 包括：

- 完整的 diff 命令和提交列表。
- 你在第 3 步中找到的标准来源文件列表，**以及第 3 步中的异味基线全文** — 子智能体无法通过其他方式访问这些内容。
- 任务说明：“报告 — 在相关情况下按文件/hunk 列出 — (a) diff 中每一处违反已记录标准的位置：引用该标准（文件 + 规则）；以及 (b) 你发现的任何基线异味：指出其名称并引用对应 hunk。区分明确违规与判断性问题 — 违反已记录标准可以是明确违规，但基线异味始终属于判断性问题，且仓库中已记录的标准优先于基线。跳过工具已强制执行的所有内容。控制在 400 字以内。”

**规范子智能体提示词** — 包括：

- diff 命令和提交列表。
- 规范的路径或已获取的内容。
- 任务说明：“报告：(a) 规范中缺失或仅部分实现的 Gherkin 场景（Given/When/Then）；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现、但实现方式似乎有误的需求。如果规范包含 Gherkin 场景，它们就是权威验收标准。每项发现都要引用对应的规范行。控制在 400 字以内。”

如果缺少规范，请跳过规范子智能体，并在最终报告中注明这一点。

### 5. 汇总

将两份报告分别置于 `## Standards` 和 `## Spec` 标题下，逐字保留或仅做轻微整理。**不要**合并或重新排序发现 — 这两个维度是有意保持独立的（参见 _为何使用两个维度_）。

最后以一行摘要结尾：给出每个维度的发现总数，以及每个维度中最严重的问题（如有）。不要在两个维度之间选出唯一的最严重问题 — 这种重新排序正是保持二者独立所要避免的。

### 5.4 预先读取记忆（标准维度）

在评分前，加载项目的已知陷阱：`Glob docs/memory/*.md`，然后读取 frontmatter 中 `category` 为 `pitfall` 或 `convention`，且 `summary` 与本次审查主题相关（diff 涉及的文件、模式或技术栈）的所有文件。这些是经过评估器验证、且该仓库已经为之付出过代价的失败模式。

在第 5.5 步的标准评分中，将已读取的记忆文件视为危险信号：如果 diff 呈现出某个已知陷阱，则在标准报告中将其记录为 FAIL，并引用记忆文件（`docs/memory/pitfall_<slug>.md`）作为证据。如果 `docs/memory/` 不存在，则跳过此步骤。

### 5.5 二元结论 + PASS 前先反驳

展示两份报告后，分别为每个维度给出二元结论：

- **标准维度**：二元 PASS（标准报告中没有未解决的标准违规或异味）/ REWORK（存在任何标准违规或已列出的异味）。
- **规范维度**：二元 PASS（规范中的所有 Gherkin 场景均已得到可证明的实现）/ REWORK（存在任何缺失、部分实现或错误实现的场景）。

**PASS 前先反驳（红队协议）：** 在为任一维度判定 PASS 前，尝试反驳你自己的 PASS：

1. 说明尽管工作看起来没有问题，但在该维度上仍可能 FAIL 的最有力理由。
2. 引用能够证实该失败的具体证据（diff hunk 或缺失的场景）。
3. 只有当该失败情形本身被具体的相反证据驳倒时，PASS 才成立。

未尝试反驳的 PASS 无效——应降级为 REWORK，并列出尚未反驳的风险。

**最终结论：** 如果任一维度为 REWORK，则结论为 REWORK；仅当两个维度均为 PASS（反驳后）时，结论才为 PASS。

## 关键要求：先反驳，再判定 PASS

未尝试反驳的 PASS 无效。在将任一维度判定为 PASS 之前，先陈述该工作仍可能失败的最有力理由，引用能够证实该理由的证据（diff 片段或缺失的场景），并且仅当有具体的相反证据将其驳倒时，才维持 PASS。绝不要合并这两个维度或重新确定其优先级——将二者分开正是为了防止一个维度掩盖另一个维度。

## 为什么要设置两个维度

一项变更可能在一个维度上通过，而在另一个维度上失败：

- 代码遵循所有标准，但实现了错误的功能 → **标准通过，规格失败。**
- 代码完全实现了 issue 的要求，但破坏了项目约定 → **规格通过，标准失败。**

分别报告这两个维度，可以防止一个维度掩盖另一个维度。
