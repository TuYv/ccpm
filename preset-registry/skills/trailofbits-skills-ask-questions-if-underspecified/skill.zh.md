# 规格不明确时先提问

## 何时使用

当请求存在多种合理的解读，或关键细节（目标、范围、约束、环境或安全性）不明确时，使用此技能。

## 何时不使用

当请求已经明确，或一次快速、低风险的探查性阅读就能补齐缺失的细节时，不要使用此技能。

## 目标

提出避免错误工作所需的最少澄清问题；在必答问题得到回答之前（或用户明确批准按所声明的假设继续之前），不要开始实现。

## 工作流程

### 1) 判断请求是否规格不明确

如果在探索了如何执行该工作之后，以下各项中仍有部分或全部不明确，则将该请求视为规格不明确：
- 定义目标（哪些应改变，哪些应保持不变）
- 定义“完成”的标准（验收标准、示例、边界情况）
- 定义范围（哪些文件/组件/用户在范围内/范围外）
- 定义约束（兼容性、性能、风格、依赖、时间）
- 明确环境（语言/运行时版本、操作系统、构建/测试运行器）
- 澄清安全性/可逆性（数据迁移、发布/回滚、风险）

如果存在多种合理的解读，就假定其规格不明确。

### 2) 优先提出必答问题（保持精简）

第一轮先提出 1-5 个问题。优先选择能排除整条工作分支的问题。

让问题易于回答：
- 为便于快速扫读而优化（简短、带编号的问题；避免大段文字）
- 尽可能提供选择题式的选项
- 在合适时建议合理的默认选项（将其清楚标注为默认/推荐选项；在列表中将推荐选项加粗，或者如果你以代码块形式呈现选项，则在代码块正上方放置一行加粗的 "Recommended"，并在代码块内部同样标注默认选项）
- 提供快速回复方式（例如，回复 `defaults` 即接受所有推荐/默认选项）
- 在有帮助时提供低门槛的“不确定”选项（例如 "Not sure - use default"）
- 如果能降低回答负担，将“必须知道”与“最好知道”的问题分开
- 合理组织选项，让用户能用紧凑的形式回复决策（例如 `1b 2a 3c`）；随后用通俗语言复述所选选项以作确认

### 3) 行动前先暂停

在收到必答问题的答案之前：
- 不要运行命令、编辑文件，或制定依赖于未知信息的详细计划
- 仅在探查步骤不会使你锁定某个方向的前提下，才执行明确标注的低风险探查步骤（例如查看仓库结构、阅读相关配置文件）

如果用户明确要求你在没有答案的情况下继续：
- 以简短的编号列表形式陈述你的假设
- 请求确认；只有当他们确认或更正这些假设后才继续

### 4) 确认理解，然后继续

获得答案后，用 1-3 句话复述需求（包括关键约束以及成功是什么样子），然后开始工作。

## 问题模板

- “在开始之前，我需要了解：(1) ……，(2) ……，(3) ……。如果你对 (2) 不在意，我将假设 ……。”
- “应该是以下哪一种？A) …… B) …… C) ……（任选其一）”
- “你认为怎样才算‘完成’？例如：……”
- “有没有我必须遵守的约束（版本、性能、风格、依赖）？如果没有，我将以现有项目的默认设置为准。”
- 使用带编号的问题、带字母的选项，并给出明确的回复格式

```text
1) Scope?
a) Minimal change (default)
b) Refactor while touching the area
c) Not sure - use default
2) Compatibility target?
a) Current project defaults (default)
b) Also support older versions: <specify>
c) Not sure - use default

Reply with: defaults (or 1a 2a)
```

## 反模式

- 不要提出通过快速、低风险的探查性阅读就能自行回答的问题（例如配置、现有模式、文档）。
- 如果一道紧凑的选择题或是否题能更快消除歧义，就不要提开放式问题。
