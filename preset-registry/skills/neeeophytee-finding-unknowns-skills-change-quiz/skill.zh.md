# 变更测验

经过长时间的会话后，代理所做的工作往往比用户意识到的更多，而差异对比只能展示表面变化。变更的实际行为取决于它与现有代码路径的交互方式。用户只应合并那些自己能够通过相关测验的变更。

## 步骤

1. 首先编写报告，分为四个简短部分：
   - **背景** — 本次会话旨在解决什么问题。
   - **变更内容** — 按意图（功能、修复、重构）而非文件进行分组。
   - **交互方式** — 变更涉及的现有代码路径，以及现在有哪些行为发生了变化，即使差异对比中并未显示相关文件。
   - **直观理解** — 用户应掌握的 2-3 个心智模型更新（例如“重试现在是幂等的，因为 X”）。
2. 对于较长的会话，将报告和底部的测验整理为一个独立完整的 HTML 页面供用户选择——这样比大段 Markdown 更易于阅读。
3. 然后进行测验：提出 5-8 个问题，重点考查不知情的维护者容易踩坑的内容。
   - 混合使用回忆题（“现在部署期间，正在执行的作业会怎样？”）和预测题（“如果有人使用过期令牌调用 X，他们会看到什么？”）。
   - 问题应侧重偏离常规的行为、边界情况和交互影响，而不是关于名称的琐碎细节。
4. 如实评分，每次只进行一轮。对于每个答错的问题，解释正确答案并标明其性质：答错要么表示用户的心智模型存在缺口，要么表明变更过于巧妙——明确指出属于哪一种。
5. 通过 = 可以合并。未通过 = 指明需要重新阅读的具体报告部分，然后提供一套新的变体测验。不要降低标准；此机制的核心目的就是防止未经阅读的变更被发布。

## 约束条件

- 测验涵盖变更及其影响范围，而非通用知识。
- 如果用户在两轮后仍无法通过，建议简化或拆分变更，而不是继续测验。
- 绝不能出于礼貌而判定用户回答正确。错误的通过判定会使此技能失去意义。
