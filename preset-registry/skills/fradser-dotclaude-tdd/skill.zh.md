# BDD 驱动的 TDD（自动化）

BDD 循环包含三个阶段：**发现**（对话 → 示例）、**形式化**（Gherkin 场景）、**自动化**（由 BDD 驱动的红-绿-重构）。本技能是 **BDD 驱动的自动化**参考——即在 `/mattpocock:bdd` 定义了做什么之后，说明如何实现测试。

在 `/mattpocock:implement` 或 `/mattpocock:bdd` 期间调用本技能时，应将其作为测试编写的权威参考。`/mattpocock:bdd` 技能负责场景设计和铁律；本技能负责确保测试代码质量符合 BDD 规范。

## 关键：BDD 场景优先

如果你是直接进入本技能（而不是通过 `/mattpocock:bdd` 或 `/mattpocock:implement`），请停下来询问用户：**“你是否已经为此行为定义了 Gherkin 场景？”**

- 如果**没有** → 先调用 `/mattpocock:bdd`，通过发现 → 形式化来定义场景，然后回到这里进行自动化。
- 如果**有** → 确认场景位于 `.feature` 文件或等效载体中，然后继续执行下面的红-绿循环。

## 什么是好的测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变，但测试不应该随之改变。好的测试读起来就像规范——“用户可以使用有效的购物车结账”准确说明了系统具备什么能力——并且能够经受重构，因为它不关心内部结构。

有关示例，请参阅 [tests.md](tests.md)；有关模拟指南，请参阅 [mocking.md](mocking.md)。

## 接缝——测试应该写在哪里

**接缝**是进行测试的公共边界：你可以在不深入内部的情况下观察行为的接口。测试应位于接缝处，绝不能针对内部实现。

**只在预先约定的接缝处进行测试。** 在编写任何测试之前，先写下待测试的接缝，并与用户确认。不得在未经确认的接缝处编写测试。不可能测试所有内容——预先就接缝达成一致，才能让测试工作聚焦于关键路径和复杂逻辑，而不是每个边缘情况。

询问：“公共接口是什么，我们应该测试哪些接缝？”

当该接口本身的形态尚不明确时——模块应该有多深、接缝应该位于何处、接口应该暴露什么——请使用 `/mattpocock:codebase-design` 技能来获取相关术语。它是模块、接口、深度、接缝、适配器、杠杆效应和局部性等术语的共享来源，应作为参考资料查阅，而不是作为一个会话来运行。

## 反模式

- **与实现耦合**——模拟内部协作者、测试私有方法，或者通过旁路进行验证（例如查询数据库，而不是使用接口）。其明显特征是：行为没有改变，但测试会在重构时失败。
- **同义反复**——断言以与代码相同的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、以相同方式手工推导出的快照、断言某个常量等于其自身），因此它从构造上就必然通过，永远不可能与代码产生分歧。预期值必须来自独立的事实来源——已知正确的字面值、完整推导的示例或规范。
- **水平切片**——先编写所有测试，然后再编写所有实现。批量测试验证的是_想象中_的行为：你测试的是事物的_形态_，而不是面向用户的行为；测试会对实际变更变得不敏感；而且你会在理解实现之前就确定测试结构。应改用**垂直切片**——一个测试 → 一个实现 → 重复，每个测试都是一枚**曳光弹**，根据上一个循环所带来的认知作出响应。

## 循环规则

- **先红后绿。** 先编写失败的测试，然后只编写足以让测试通过的代码。不要预判未来的测试，也不要添加推测性的功能。
- **一次一个切片。** 每个循环只处理一个接缝、一个测试和一个最小实现。
- **重构不属于此循环。** 它属于审查阶段（参见 `/mattpocock:code-review`），而不是红 → 绿的实现循环。

## 关键：BDD 驱动——而非独立的 TDD

此技能是 BDD 生命周期的**自动化**阶段。它始终在 `/mattpocock:bdd` 或 `/mattpocock:implement` 下以 **BDD 驱动的 TDD** 方式运行。如果被直接调用，请参阅本文件顶部的关键检查——在编写测试代码之前，确认场景已存在。

1. **发现**（哪些行为重要）——由 `/mattpocock:bdd` 通过 Gherkin 场景负责
2. **形式化**（将场景作为规范）——由 `/mattpocock:bdd` 通过 `.feature` 文件负责
3. **自动化**（此技能）——使场景通过的红绿循环

## 何时调用

在以下情况下显式调用此技能：
- 用户在 BDD 实现期间询问“我应该如何测试这个？”
- 用户询问有关模拟、接缝或测试结构的问题
- 用户编写了一个看起来与实现耦合的测试
- 用户询问系统边界处的模拟策略
- 用户不确定某个测试是良好的还是同义反复的

直接调用时，首先检查 Gherkin 场景是否存在（参见顶部的关键检查）。如果不存在，请先转到 `/mattpocock:bdd`，然后再继续自动化阶段。

`/mattpocock:bdd` 和 `/mattpocock:implement` 技能会在自动化阶段自动加载此技能——在这些流程中，你无需单独调用它。
