# 安全边际

核心规则：当残余不确定性加上违约成本可能招致毁灭性或代价高昂的失败时，承诺一个留有余量的数字。边际用于覆盖估算误差；它不是供人偷懒的免费冗余。

## 何时使用

- 负载不确定情形下的容量、超时、池大小、队列深度、存储或 SLA 数字
- 低估代价高昂的工期或预算承诺
- 扩容或恢复缓慢时的架构余量
- 任何出错会带来不对称下行风险的公开或生产承诺

## 何时不使用

- 违约能被立即发现并以近乎零的成本修复（快速自动扩缩容、可实时调节的限制）——静态的臃肿缓冲只会浪费资源
- `cost(buffer) > P(breach) × cost(breach)`——应合理定量或实际测量，而非一味拉满
- 不确定性可以通过测量或查表消除——先拿到真实数字
- 停止准则／搜索预算类问题——应使用有限理性，而非注水
- 参数完全已知且利害关系低、以边界优化为目标的场景

## 步骤

1. **不加余量的点估计。** 以明确的单位（RPS、周、GB、ms）陈述基础需求，并给出置信度（高／中／低）。
2. **不确定性与违约成本。** 列出不确定性来源（突发尖峰、增长、未知因素、依赖项波动）。说明若估计偏低会导致什么失败：宕机、错过发布、数据丢失、声誉受损——以及该失败是可恢复的还是毁灭性的。
3. **确定缓冲大小。** 将边际（乘以或加上）施加于残余不确定性和利害关系，而非虚荣心。典型区间（应依据证据调整）：
   - 广为人知、后果轻微：~1.2–1.5×
   - 熟悉但有未知因素／可逆：~1.5–2×
   - 全新领域、外部依赖、SLA、不可逆：~2–3×
   当缓冲成本超过预期违约成本时，应设上限或削减。
4. **毁灭约束。** 若违约可能造成不可逆伤害，应据此定规模，使最坏合理偏差仍保持在失败阈值之上；若该缓冲负担不起，就修改设计（削减负载、降级、分阶段），而不是假装精确。
5. **最强反例。** 同时挑战缓冲不足（“我们以后再扩”）与缓冲过度（闲置成本、复杂度）。存在历史数据时，优先采用“先测量再削减”。
6. **承诺并监控。** 公布带缓冲的承诺、失败阈值，以及能证明边际过大或过小的指标。数字确定且可监控后即停止。

## 输出

```text
Base estimate: … (units, confidence)
Uncertainty drivers: …
Breach cost / failure threshold: …
Margin applied: …× (or absolute buffer …)
Buffered commitment: …
Ruin check: pass | redesign needed
Cost of margin vs expected breach cost: …
Monitor: metric … ; thin if … ; excessive if …
```

## 验证

- **反例检验：** 若缓冲后的数字等于乐观点估计，说明没有施加边际——或者若在零违约成本陈述下仍加了边际，那就是照猫画虎式的注水。
- **停止条件：** 一旦承诺、阈值和监控都已就位，在没有新的不确定性证据时停止叠加倍数。
- **过度使用防护：** 当调整免费且即时，或真实数字可低成本测量时，不要注水。不要把搜索停止问题与容量缓冲混为一谈。
