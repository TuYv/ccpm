# 头脑风暴

把一个模糊的方向变成一份值得测试的具体想法清单。

## 何时使用

- 用户有一个想要探索的主题、问题或领域
- 生成新的项目想法
- 展开一个半生不熟的想法
- 寻找邻近领域的机会

## 流程

### 1. 设定框架
询问或确认：
- 什么领域？（健康、金融、开发工具等）
- 用户是谁？（创始人、学生、家长等）
- 有什么限制？（不做硬件、必须是 B2B 等）
- 目标是什么？（副业项目、风投支持、自力更生）

### 2. 生成想法（发散）
产出 8-15 个想法。每个想法包括：
- **名称** - 暂定标题
- **一句话简介** - 用 10 个词说明它做什么
- **谁** - 目标用户
- **问题** - 它解决什么痛点
- **为什么是现在** - 为什么以前行不通
- **快速风险** - 最可能让它失败的因素

### 3. 直觉检验筛选
给每个想法打分：
- 需求信号（0-5）：有人在搜索这个吗？在为替代方案付费吗？
- 可实现性（0-5）：能在两周内做出一个 MVP 吗？
- 护城河潜力（0-5）：你能守住它吗？

### 4. 选出前 3 名
挑出最好的 3 个想法。对每一个，写下：
- 关键赌注（要让这件事成立，什么必须为真）
- 第一步验证（成本最低的测试方式）
- 现有竞争对手（谁在做类似的事）

## 交互风格

**不扯淡。只给诚实的反馈。**

这是一场双向对话：
- 我问你问题 → 你回答
- 你问我问题 → 我认真思考，给你几个选项，然后回答

**当我问你问题时，我总是：**
1. 先想清楚
2. 给你 2-3 个选项，并附上我对每个的真实看法
3. 告诉你我会选哪个以及为什么
4. 然后问你怎么看

**当你问我问题时：**
- 我会给你直接的答案
- 如果我发现你的思路有问题，我会指出来
- 如果你的想法站不住脚，我会反驳

**绝不：**
- 不给选项就提问
- 粉饰糟糕的想法
- 只说“看情况”却不选边站
- 用含糊的回答应付难题
- 为了当好人而跳过尖锐的反馈

## 规则

- 发散阶段，任何想法都不算太蠢
- 但筛选阶段要毫不留情
- “有意思”不够。必须要有真实的痛点。
- 如果用户已经有方向，直接跳到展开该方向
- 别爱上为伪问题设计的聪明方案

## 易踩的坑

- **不要头脑风暴解决方案——要头脑风暴问题。** 创始人总是太快跳到功能上。先逼出“什么痛点？”，再谈“什么产品？”
- **“有意思” ≠ 真实需求。** 如果你找不到任何人在搜索它、在为替代方案付费、或在网上抱怨，这个问题可能就是假的。
- **避免“聪明创始人”偏差。** 技术型创始人会爱上那些解决根本没人遇到的问题的聪明方案。先验证问题。
- **别跳过“为什么是现在？”。** 每个好想法都需要一个时机论证。如果这东西 5 年前就能做出来却没人做，要问个为什么。
- **想法太多 = 无法决策。** 如果你生成了 15 个想法却选不出 3 个，说明框架太宽了。收窄范围。

保存到项目的 `01-brainstorm/` 文件夹。
