# 系统化调试

## 铁律

**不先查明根因，不得修复。**

只修补症状只会导致“打地鼠”式调试。任何未触及根因的修复，都会让下一个问题更难定位。先找出根因，再修复它。

---

## 阶段 1：根因调查

在形成任何假设之前先收集上下文。

1. **收集症状：** 阅读错误信息、堆栈跟踪和复现步骤。如果用户未提供足够上下文，请一次只提一个问题，不要一次提五个问题。  

2. **阅读代码：** 从症状出发，追踪代码路径回溯到可能的原因。查找所有引用，阅读失败点周边的逻辑。  

3. **检查近期变更：**
   ```bash
   git log --oneline -20 -- <affected-files>
   ```
   之前是否正常？发生了什么变化？回归通常意味着根因在 diff 里。  

4. **复现：** 你能稳定触发该问题吗？如果不能，在继续之前先收集更多证据。  

5. **检查记忆：** 查看此前在同一领域的调试记录。同一文件中的反复出现问题属于架构上的坏味道。  

输出：**“根因假设：...”**……一个具体、可测试的关于出错原因的结论。  

---

## 阶段 2：模式分析

检查该问题是否符合已知模式：

**竞争条件**……间歇性出现，依赖时序。查看对共享状态的并发访问。  

**Nil/null 传播**……NoMethodError、TypeError。缺少对可选值的保护。  

**状态损坏**……数据不一致、部分更新。检查事务、回调、钩子。  

**集成失败**……超时、异常响应。外部 API 调用、服务边界。  

**配置漂移**……本地可用，预发/生产失败。环境变量、特性开关、数据库状态。  

**缓存陈旧**……显示旧数据，清缓存后恢复。Redis、CDN、浏览器缓存。  

还要检查：
- 项目中的已知问题，查找相关问题
- git log 中同一区域以往的修复。相同文件中的反复问题不是偶然，而是架构上的坏味道。  

**外部检索：** 如果问题不符合任何已知模式，请在线搜索该错误类型。**先脱敏：** 去掉主机名、IP、文件路径、SQL 和客户数据。搜索错误类别，而不是原始报错文本。  

---

## 阶段 3：假设验证

在编写**任何**修复之前，先验证你的假设。

1. **确认假设：** 在可疑根因处加入临时日志、断言或调试输出。运行复现步骤。证据是否一致？  

2. **若假设错误：** 搜索该错误（先脱敏敏感信息）。回到阶段 1。收集更多证据。不要猜测。  

3. **三次规则：** 若 3 个假设都失败，**停止**。告诉用户：

   “已测试 3 个假设，没有一个命中。这可能是架构问题，而非简单 bug。”

   可选项：
   - 用新假设继续调查（请描述该假设）
   - 升级给人工评审（需要熟悉系统的人参与）
   - 增加日志并等待（给该区域打点，等待下次抓到）  

**预警信号**……如果你看到这些，就放慢节奏：
- “先临时修复”……没有“先临时”。要么修对，要么升级。
- 在追踪数据流之前就提出修复方案……你在猜测。
- 每次修复都在别处触发新问题……问题在错层，而非错代码。  

---

## 阶段 4：实施

根因确认后：

1. **修复根因，而非症状。** 以最小改动消除实际问题。  

2. **最小差异：** 触及最少文件，改动最少行数。克制住重构相邻代码的冲动。  

3. **编写回归测试**，要求：
   - **不含修复时失败**（证明测试有意义）
   - **含修复时通过**（证明修复有效）

4. **运行完整测试套件。** 不允许出现回归。  

5. **若修复触及超过 5 个文件：** 在继续之前先向用户提示影响范围。对一个 bug 修复来说这是很大的改动。  

---

## 阶段 5：验证与报告

**新一轮验证：** 复现最初的 bug 场景并确认已修复。此步骤不可选。  

运行测试套件。  

输出结构化调试报告：

**调试报告**
- **症状：** 用户观察到的现象
- **根因：** 实际出错的地方
- **修复：** 修改了什么（附文件路径）
- **证据：** 测试输出、复现并确认修复成功的结果
- **回归测试：** 新增测试的位置
- **相关：** 同区近期 bug、架构备注
- **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED

将报告保存到 `memory/`，使用今天的日期，便于未来会话引用。  

---

## 重要规则

- **修复尝试失败 3 次以上：停止并质疑架构。** 架构错误，而不是假设失败。
- **不要应用无法验证的修复。** 如果无法复现并确认，不要交付。
- **不要说“这个应该能修好”。** 要验证并证明。运行测试。
- **若修复触及超过 5 个文件：** 在继续前向用户提示。
- **完成状态：**
  - DONE……根因已找到、修复已应用、回归测试已编写、所有测试通过
  - DONE_WITH_CONCERNS……已修复但无法完全验证（如：间歇性问题、需要在预发环境验证）
  - BLOCKED……经过调查仍未明确根因，已升级处理
