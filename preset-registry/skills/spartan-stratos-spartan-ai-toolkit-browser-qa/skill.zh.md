# 浏览器 QA 技能

使用真实浏览器测试 Web 应用。找出用户会发现的 bug。

## 何时使用

- 构建完前端功能之后
- 为 UI 改动创建 PR 之前
- 当用户报告“界面看起来有问题”时
- 部署后的冒烟测试

## 此技能做什么

1. 启动带真实 Chromium 的 Playwright
2. 访问应用中每个可发现的页面
3. 检查控制台错误、网络失败、损坏的资源
4. 测试交互元素（表单、按钮、链接）
5. 验证移动端响应式表现
6. 生成结构化的 QA 报告

## QA 检查类别

### 1. 页面健康
每个页面都会进行以下检查：
- HTTP 状态码为 2xx
- 无 JavaScript 控制台错误
- 无失败的网络请求（4xx/5xx）
- 无缺失的图片或资源
- 页面加载时间在 3 秒以内

### 2. 布局与响应式
- 桌面端（1280px）：无横向滚动，无元素重叠
- 移动端（375px）：无横向滚动，文字可读，按钮可点按
- 无内容被意外裁剪或隐藏

### 3. 交互元素
- 按钮：点击 → 有反应（没有失效按钮）
- 链接：点击 → 导航到有效页面（无 404）
- 表单：空提交 → 显示验证提示。提交有效数据 → 显示成功反馈。
- 下拉菜单/模态框：打开 → 内容可见。关闭 → 内容隐藏。

### 4. 导航流程
- 导航中的每个链接都指向有效位置
- 后退按钮按预期工作
- 面包屑（如果存在）信息准确
- 认证重定向正常工作（受保护页面 → 登录 → 重定向回来）

### 5. 数据展示
- 列表显示数据（存在数据时不显示空状态）
- 分页正常工作（如果存在）
- 搜索/筛选会更新结果
- 数据获取期间显示加载状态
- API 失败时显示错误状态

## 注意事项

- **`networkidle` 在带有 websocket 或轮询的应用上会永远等待。** 如果应用有实时连接，请改用 `domcontentloaded` 或特定的元素选择器。
- **`page.click()` 对不可见元素会静默通过。** 交互前务必先验证元素可见。先使用 `await expect(locator).toBeVisible()`。
- **不启用触摸模拟的移动视口测试会漏掉真实 bug。** 在浏览器上下文中设置 `hasTouch: true`，而不只是设置视口大小。
- **控制台警告不是控制台错误。** 不要把 React hydration 警告或弃用提示当作 bug 报告。只有 `console.error` 和失败的网络请求才算 bug。
- **CI 上的截图与本地看起来不同。** macOS 与 Linux 之间在字体渲染、抗锯齿和 DPI 上存在差异。请使用视觉比较阈值，而不是像素级完美匹配。

## 规则

- **只用真实浏览器。** Playwright + Chromium。不做仅 HTTP 的测试。
- **默认无头模式。** 除非被要求，否则不要打开可见窗口。
- **测试两种视口。** 桌面端（1280px）和移动端（375px）。
- **控制台错误 = bug。** 必须报告。
- **一次性模式。** 启动浏览器、测试、关闭。不常驻守护进程。
- **失败时截图。** 出现问题时截图。
- **未经询问不要修复。** 先报告，再提供修复方案。
