# 基准比较器

**目标：** 在受控、可复现的条件下比较备选方案。正确性优先于速度，并且测量数据必须与估算、设置成本和解释分开。

**执行契约：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，并且仅在其操作和所需证据均已完成时才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的裁定、决策和批准规则应用于每个未完成项目，并在开头添加 **清单：X/Y 已完成**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 规范工作负载和判定标准 | 仓库固件、测试、预期差异、模式或独立指定的结果 | 在任一候选方案运行之前定义成功标准 | 创建能够代表该决策的最小确定性固件 |
| 隔离 | 干净的 Git 工作树、临时目录、受控环境、固定种子和可重置缓存 | 防止某个候选方案或某次运行污染其他候选方案或运行 | 采用顺序执行的洁净室设置，并验证清理结果 |
| 执行 | 对每个候选方案使用相同的 shell 运行器和封装器 | 以一致的方式捕获命令、退出状态、标准输出、标准错误、耗时和产物 | 手动执行，并明确说明可复现性限制 |
| 激活证明 | 日志、跟踪信息、命令记录、进程元数据或候选方案特有的产物 | 验证预期的备选方案确实已运行且未回退 | 无法证明激活时，将该次运行视为无效 |
| 正确性评分 | 测试、输出解析器、差异比较、模式验证或独立判定标准 | 在比较成本之前评估每个场景 | 根据书面预期进行人工盲评 |
| 性能和成本 | 单调计时器、资源指标、令牌或用量遥测、工具调用日志和失败次数 | 能够通过相同方法观察所有候选方案的指标时 | 标记派生值或估算值，并将其排除在测量聚合数据之外 |
| 外部语义 | 官方文档和规范 | 候选方案配置或声明的行为需要最新验证时 | 通过 Web 调研查阅第一手来源；否则将该声明标记为 `UNVERIFIED` |

不要在观察到偏好的候选方案后调整场景，不要混合来自不同工作负载的测量结果，也不要将内部估算作为外部测量的事实来呈现。基准测试可以创建临时工作树和产物，但不得更改源基线或未经批准的外部状态。

## 证据规则

- 在运行候选方案之前，明确场景、判定标准、指标、排除项和决策规则。
- 保持所有非测试变量不变，或记录并分析混杂因素。
- 正确性失败不能通过更快的速度、更少的令牌用量或更低的成本来弥补，除非决策明确允许降低正确性。
- 使用重复运行，并报告原始值、中心趋势、离散程度、失败和异常值；绝不要重点展示最佳运行结果。
- 将设置或索引成本、稳态成本、维护负担和运行时成本分开报告。
- 在不同字段中分别报告测量证据、派生证据、估算证据和定性证据。

## 检查清单

### 1. 定义决策和实验

- [ ] 说明基准测试必须支持的决策、候选方案、目标用户、代表性工作负载和明确的非目标。
- [ ] 既要包含较简单或内置候选方案可能合理胜出的普通案例，也要包含能够检验各候选方案所声称优势的案例；不要为其中一方构造功能演示。
- [ ] 定义场景输入、预期结果、正确性标准、失败条件，以及独立于候选方案自我报告的判定标准。
- [ ] 定义主要和次要指标、单位、测量点、验收阈值、允许的权衡，以及平局或无法得出结论时的规则。
- [ ] 确定必须保持固定的变量：仓库修订版本、模型、提示词、权限、运行时、硬件、数据、缓存策略和网络条件。
- [ ] 预先声明根据试运行得出的重复次数，并将其与最小有意义效应和观测到的噪声关联起来；或者声明一种有界的顺序停止规则，其中包含固定的误差容限和最大运行次数。
- [ ] 在查看第一个候选方案的结果之前，冻结场景文本、固定测试数据、预期结果、运行器、解析器和决策规则，并计算其哈希值。
- [ ] 在创建工作树、临时数据或运行器之前，阅读仓库说明并检查 Git 状态。
- [ ] 建立一份本次运行专属的资源清单，记录创建的每个绝对路径、工作树、进程 ID、缓存、账户、数据集、报告和临时工件；绝不要将预先存在的资源或凭据登记为清理目标。
- [ ] 要求场景无副作用或具有幂等性，并使用一次性账户或数据集；在执行前定义外部写入授权、成本和速率预算、清理方式以及回滚证据。
- [ ] 如果候选方案解决的并非同一任务、无法独立评定正确性、无法隔离外部影响，或者决策规则是在查看结果后才选定的，则返回 `BLOCKED`。

### 2. 构建对称的测试框架

- [ ] 对每个候选方案使用相同的运行器、超时设置、日志记录、环境构建方式和工件收集方式。
- [ ] 从同一提交创建干净的工作树或等效的隔离副本，并验证初始状态完全相同。
- [ ] 盘点可能导致候选方案行为在本应隔离的实验组之间泄漏的全局及用户级说明、钩子、插件、设置、凭据、缓存和环境变量；逐一禁用、统一或记录。
- [ ] 对可能影响结果的随机种子、时钟、区域设置、并发性、网络访问、依赖项版本、缓存状态、预热和场景顺序进行控制。
- [ ] 记录候选方案的确切配置、功能标志、提示词、命令行、权限和版本。
- [ ] 定义对称的调优策略和预算——默认配置、同等调优后的配置，或两者都测试——以免在看到另一候选方案的结果后再针对性优化其中一个候选方案。
- [ ] 添加激活检查，以证明每个候选方案均已实际使用，并识别静默回退、部分激活或混合执行的情况。
- [ ] 在开始基准测试之前，使用已知通过和失败的固定测试数据验证输出解析器、差异比较规则、测试判定标准和指标收集器。
- [ ] 将一次性设置、索引、编译或下载成本与稳态执行成本及摊销成本分开。
- [ ] 根据资源清单定义清理和故障恢复流程，确保崩溃或超时的运行不会污染后续运行。

### 3. 执行并收集证据

- [ ] 以均衡或随机的顺序运行候选方案，避免系统性的热缓存优势或时间先后优势。
- [ ] 为每次运行收集开始和结束状态、命令、退出状态、耗时、资源指标、日志、输出、差异、测试结果以及候选方案特有的产物。
- [ ] 在评分前验证激活状态；将未经证实或使用回退方案的运行标记为无效，而不是将其归于预期的候选方案。
- [ ] 在查看性能和成本指标之前，根据预先定义的判定标准评估正确性。
- [ ] 将任务完整性与正确性及效率分开评估：验证每一项必需结果和禁止出现的副作用，而不是将较小的差异、较低的 token 数量或仅部分成功视为任务完成。
- [ ] 对人工或定性评分者隐藏候选方案身份，并随机化展示顺序；记录分歧，而不是以偏向某个候选方案的方式解决分歧。
- [ ] 将超时、崩溃、输出格式错误、部分完成、工具错误和环境故障记录为不同的故障类别。
- [ ] 按照预先定义的次数重复有效运行，并保留每次运行的原始结果，不得删除不利的数据。
- [ ] 当环境漂移、速率限制、外部服务中断、后台负载或运行器缺陷导致后续运行不可比较时，暂停运行。
- [ ] 修复测试框架缺陷后，重新运行两个候选方案；绝不能只为一方修复证据。
- [ ] 将设置、激活、解析器和环境故障与任务执行错误分开处理，然后说明设置可靠性是否属于实际产品决策的一部分。

### 4. 分析有效性和结果

- [ ] 仅排除符合预先定义的无效判定规则的运行，并记录原因、证据以及排除该运行是否会改变结论。
- [ ] 在汇总之前，报告每个场景的正确性、故障、延迟、资源使用情况、token 或使用量、工具调用次数以及其他成本。
- [ ] 根据样本和分布情况使用中位数、百分位数、置信区间或其他合适的统计量；展示离散程度和样本量。
- [ ] 将单位或工作负载不同的指标分开处理，除非在执行前已定义权重，否则避免使用单一综合得分。
- [ ] 检查差异是否超出测量噪声，以及是否存在某个场景主导汇总结果的情况。
- [ ] 将设置成本、稳态成本、维护复杂性、可移植性、故障行为和运维负担与运行时指标分开分析。
- [ ] 明确标注合成测试数据、估算的 token、基于字符的代理指标、建模成本和人工判断，以免它们被误认为实际观测到的遥测数据。
- [ ] 当定性输出质量对决策有实质影响，且自动化正确性评估不足时，请求独立的盲审。

### 5. 决策、保留与清理

- [ ] 仅当候选方案满足正确性要求和预先定义的决策规则，且有足够的有效证据时，才使用 `WIN`。
- [ ] 当差异在运维层面可以忽略，或在既定优先级下各项权衡相互抵消时，使用 `TIE`。
- [ ] 当样本量、激活状态、判定标准、环境控制或相互冲突的场景导致无法做出可靠选择时，使用 `INCONCLUSIVE`。
- [ ] 保留可复现的命令、配置、场景定义、预期、原始结果、标准化结果以及独立验证所需的分析。
- [ ] 仅删除由本次运行创建的台账条目：验证绝对路径仍位于获准的临时根目录内，停止已准确记录进程 ID 的进程，保留存在未提交更改或预先存在的工作树，绝不删除凭据，并验证源状态和外部基线状态。
- [ ] 报告无效运行、排除项、混杂因素、结论对假设的敏感性，以及可证伪该结论的方式。
- [ ] 报告比较后仍然存在的决策风险，包括不受支持的工作负载、未测量的成本、不稳定的环境，以及可能逆转结论的假设。
- [ ] 返回场景级证据、汇总权衡、结论、决策指导、局限性和清理确认。
