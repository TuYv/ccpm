# 基准比较器

**目标：** 在受控且可复现的条件下比较不同方案。正确性优先于速度，测量数据必须与估算值、设置成本和解释分开。

**执行契约：** 有序复选框是完成标准。内部跟踪每一项的状态：`PENDING`、有具体证据支持的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一节后重新核对各项。在返回前解决所有 `PENDING`，并且只统计 `PROVEN` 和 `CLEARED`；对每个缺口应用该 skill 的裁决和批准规则。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且会产生实质影响的选择或所需的外部批准进行询问。根据实际风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 权威工作负载和判定依据 | Repository fixtures、tests、expected diffs、schemas 或 independently specified outcomes | 在运行任一候选方案前定义成功标准 | 创建能够代表该决策的最小确定性 fixture |
| 隔离 | Clean Git worktrees、temporary directories、controlled environment、fixed seeds 和 resettable caches | 防止某个候选方案或某次运行污染其他候选方案或运行 | 按顺序执行 clean-room setup，并验证清理结果 |
| 执行 | 对每个候选方案使用相同的 shell runner 和 wrapper | 以一致方式捕获命令、退出状态、stdout、stderr、计时和产物 | 手动执行，并明确说明可复现性限制 |
| 激活证明 | Logs、traces、command records、process metadata 或 candidate-specific artifacts | 验证实际运行的是预期方案，且未发生回退 | 无法证明激活时，将该次运行视为无效 |
| 正确性评分 | Tests、output parser、diff、schema validation 或 independent oracle | 在比较成本之前处理每个场景 | 根据书面预期进行人工盲评 |
| 性能和成本 | Monotonic timer、resource metrics、token 或 usage telemetry、tool-call logs 和 failure counts | 对所有候选方案使用相同方法观察指标 | 标记派生值或估算值，并将其排除在测量汇总之外 |
| 外部语义 | Official documentation 和 specifications | 候选方案的配置或声称的行为需要当前验证时 | 通过 primary-source web research；否则将该声明标记为 `UNVERIFIED` |

不得在观察到偏好的候选方案后调整场景，不得混合来自不同工作负载的测量结果，也不得将内部估算呈现为外部测量事实。基准测试可以创建临时 worktrees 和 artifacts，但不得更改源基线或未经批准的外部状态。

## 证据规则

- 保持所有未经测试的变量恒定，或记录并分析混杂因素。
- 除非决策明确允许正确性降低，否则更好的速度、token 使用量或成本不能弥补正确性失败。
- 使用重复运行，并报告原始值、中心趋势、离散程度、失败和异常值；绝不将最佳一次运行作为标题结果。
- 将设置或索引成本、稳态成本、维护负担和运行时成本分开。
- 在不同字段中分别报告测量得出的、推导得出的、估算的和定性的证据。

## 清单

### 1. 定义决策和实验

- [ ] 说明基准测试必须支持的决策、候选项、目标用户、代表性工作负载和明确的非目标。
- [ ] 既要包含较简单或内置候选项可能合理胜出的常规情形，也要包含能够检验每个候选项所宣称优势的情形；不得为某一方构建功能演示。
- [ ] 定义场景输入、预期结果、正确性标准、失败条件，以及独立于候选项自我报告的判定器。
- [ ] 定义主要和次要指标、单位、测量点、验收阈值、允许的权衡，以及平局或结论不确定规则。
- [ ] 定义处理变量，然后保持其他相关变量固定：修订版本、模型、提示词、权限、运行时、硬件、数据、缓存和网络。正在比较的变量不能同时被声明为固定。
- [ ] 使用现有的变异性证据、有界的试运行，或具有固定误差容限和最大运行次数的有界序贯规则，预先声明重复次数。如果预算无法确定有意义的效应，返回 `INCONCLUSIVE`。
- [ ] 在检查第一个候选项结果之前，冻结并哈希场景文本、固定装置、预期结果、运行器、解析器和决策规则。
- [ ] 在创建工作树、临时数据或运行器之前，阅读仓库说明并检查 Git 状态。
- [ ] 启动由运行所有的资源台账，记录每个创建的绝对路径、工作树、进程 ID、缓存、账户、数据集、报告和临时产物；绝不将预先存在的资源或凭据登记为清理目标。
- [ ] 要求场景无副作用或具有幂等性，并使用可丢弃的账户或数据集；在执行前定义外部写入授权、成本和速率预算、清理及回滚证据。
- [ ] 如果候选项未解决相同任务、无法独立评估正确性、无法隔离外部影响，或在结果出来后才选择决策规则，则返回 `BLOCKED`。

### 2. 构建对称测试框架

- [ ] 对每个候选项使用相同的运行器、超时设置、日志记录、环境构建和产物收集方式。
- [ ] 从同一提交创建干净的工作树或等效的隔离副本，并验证起始状态完全一致。
- [ ] 清点可能使候选项行为在看似隔离的分支之间泄漏的全局和用户级说明、钩子、插件、设置、凭据、缓存及环境变量；禁用、均衡或记录其中每一项。
- [ ] 控制可能影响结果的随机种子、时钟、区域设置、并发性、网络访问、依赖版本、缓存状态、预热和场景顺序。
- [ ] 记录确切的候选项配置、功能标志、提示词、命令行、权限和版本。
- [ ] 定义对称的调优策略和预算——默认配置、同等调优的配置，或两者兼有——以避免在看到另一候选项结果后才优化其中一方。
- [ ] 添加激活检查，以证明每个候选项均被使用，并识别静默回退、部分激活或混合执行。
- [ ] 在基准测试前，使用已知通过和失败的固定装置验证输出解析器、差异规则、测试判定器和指标收集器。
- [ ] 将一次性设置、索引、编译或下载成本与稳态执行成本和摊销成本分开。
- [ ] 基于资源台账定义清理和失败恢复措施，确保崩溃或超时的运行不会污染后续运行。

### 3. 执行并收集证据

- [ ] 以平衡或随机化的顺序运行候选方案，避免系统性的热缓存或时间优势。
- [ ] 对每次运行记录初始状态和结束状态、命令、退出状态、耗时、资源指标、日志、输出、差异、测试结果以及候选方案特有的工件。
- [ ] 在评分前验证激活状态；对于未经证实或使用回退方案的运行，标记为无效，不要将其归属于预期的候选方案。
- [ ] 先根据预定义的判定标准评估正确性，再检查性能和成本指标。
- [ ] 将任务完成度与正确性、效率分开评估：验证每个必需结果和禁止的副作用，而不是将更小的差异、更少的 token 数量或成功完成的子集视为任务完成。
- [ ] 让人工或定性评分者对候选方案身份保持盲态，并随机化呈现顺序；记录分歧，不要将分歧朝向偏好的候选方案解决。
- [ ] 将超时、崩溃、输出格式错误、部分完成、工具错误和环境故障记录为不同的失败类别。
- [ ] 遵循预先声明的重复或顺序停止规则；统计并保留所有尝试，包括失败和无效的运行。不要为了获得预期数量的成功结果而持续重试。
- [ ] 当环境漂移、速率限制、外部服务中断、后台负载或运行器缺陷导致后续运行无法进行可比时，暂停运行。
- [ ] 修复测试工具后，使受影响的比较失效，并在修正后的测试工具下针对这些场景重新运行两个候选方案；保留未受影响的证据，并标记之前的无效结果。
- [ ] 将设置、激活、解析器和环境故障与任务错误分别处理，然后说明设置可靠性是否属于实际产品决策的一部分。

### 4. 分析有效性和结果

- [ ] 仅排除符合预定义失效规则的运行，并记录排除原因、证据以及排除是否改变结论。
- [ ] 在汇总之前，按场景报告正确性、失败情况、延迟、资源使用、token 或用量、工具调用以及其他成本。
- [ ] 使用适合样本和分布的中位数、百分位数、置信区间或其他统计量；显示离散程度和样本量。
- [ ] 将不同单位或不同工作负载的指标分开处理，除非其权重是在执行前定义的，否则不要使用单一综合评分。
- [ ] 检查差异是否超过测量噪声，以及某个场景是否主导了汇总结果。
- [ ] 将设置成本、稳态成本、维护复杂度、可移植性、失败行为和运维负担与运行时指标分开分析。
- [ ] 标记合成夹具、估算 token 数量、基于字符的代理指标、建模成本和人工判断，确保它们不会被误认为是观测到的遥测数据。
- [ ] 当定性输出质量会实质性影响决策且自动化正确性不足时，请求独立的盲审。

### 5. 决策、保留并清理彩在线

- [ ] 仅当候选项满足正确性要求和预定义决策规则，并且拥有充分的有效证据时，才使用 `WIN`。
- [ ] 仅当证据支持预定义的可忽略差异范围或体现出平衡的权衡时，才使用 `TIE`；在证据不足的情况下未能检测到差异属于 `INCONCLUSIVE`。
- [ ] 当样本量、激活状态、判定标准、环境控制或相互冲突的场景导致无法可靠选择时，使用 `INCONCLUSIVE`。
- [ ] 保留可复现的命令、配置、场景定义、预期结果、原始结果、规范化结果，以及独立验证所需的分析。
- [ ] 仅删除由本次运行负责的账本条目：验证绝对路径仍位于批准的临时根目录内，停止准确记录的进程 ID，保留存在未提交更改或预先存在的工作树，绝不删除凭据，并验证源代码和外部基线状态。
- [ ] 报告无效运行、排除项、混杂因素、对假设的敏感性，以及结论可能被证伪的方式。
- [ ] 报告比较完成后仍存在的决策风险，包括未支持的工作负载、未测量的成本、不稳定的环境，以及可能逆转结论的假设。
- [ ] 验证决策指导是否遵循场景级证据和冻结的规则，并已将清理工作与局限性纳入考量。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、要求覆盖情况、矛盾、范围、结论和适用的清理工作。修正报告或已授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出契约

按以下顺序使用用户的语言进行报告；保留全部五个字段，并且每项事实只陈述一次。结果较少时，每个字段可使用一行；省略空表格，不要复制链接的产物：

1. **结果：** 技能特定的结论及有证据支持的结果。
2. **范围：** 已审查/已更改的范围、排除项、基线和重要假设。
3. **证据：** 以下技能特定字段；区分事实、推断和未经验证的声明。链接产物；适合时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项目的原因、对结果的影响和确切的下一步操作；说明剩余风险和所需决策。

**技能特定证据：** 冻结的决策、候选项、场景、独立判定标准、固定变量、配置、指标、重复次数、排除项和决策规则。证明激活状态和测试框架的有效性；报告无效运行、混杂因素、排除项和清理工作。在汇总之前，比较各场景的完整性、正确性、失败情况、主要指标、离散程度/样本量和其他成本。保留设置/维护方面的权衡、敏感性、证伪条件、原始结果、配置、场景产物，以及可用时的哈希值。
