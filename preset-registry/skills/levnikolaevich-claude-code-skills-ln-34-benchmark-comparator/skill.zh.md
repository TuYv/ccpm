# 基准比较器

**目标：** 在受控且可复现的条件下比较不同方案。正确性优先于速度，并且测量数据必须与估算值、设置成本和解读分开。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，或在证明其条件触发器不存在时解决为 `CLEARED`，否则标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败均不构成证明。  
返回前，解决所有 `PENDING` 项，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，根据此技能的判定、决策和批准规则处理每个 `UNPROVEN` 项，并在开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | 小节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 标准工作负载和判定基准 | 仓库固件、测试、预期差异、架构或独立指定的结果 | 在任一候选方案运行之前定义成功标准 | 创建能够代表该决策的最小确定性固件 |
| 隔离 | 干净的 Git 工作树、临时目录、受控环境、固定种子以及可重置的缓存 | 防止某个候选方案或某次运行污染其他候选方案或运行 | 按顺序设置干净环境，并验证清理结果 |
| 执行 | 对每个候选方案使用相同的 shell runner 和包装器 | 以一致方式捕获命令、退出状态、stdout、stderr、计时和构件 | 手动执行，并明确说明可复现性限制 |
| 激活证明 | 日志、跟踪记录、命令记录、进程元数据或候选方案专属构件 | 验证实际运行的是预期方案，且没有回退到其他方案 | 无法证明激活时，将该次运行视为无效 |
| 正确性评分 | 测试、输出解析器、差异、架构验证或独立判定基准 | 在比较成本之前针对每个场景执行 | 根据书面预期进行人工盲评 |
| 性能和成本 | 单调计时器、资源指标、令牌或使用量遥测、工具调用日志以及失败次数 | 对所有候选方案使用相同方法即可观测指标时 | 标记派生值或估算值，并将其排除在测量汇总之外 |
| 外部语义 | 官方文档和规范 | 候选方案配置或其声称的行为需要当前验证时 | 通过主要来源进行网络调研；否则将该声明标记为 `UNVERIFIED` |

不要在观察到偏好的候选方案后调整场景，不要混合来自不同工作负载的测量结果，也不要将内部估算作为外部测量事实呈现。基准测试可以创建临时工作树和构件，但不得更改源基线或未经批准的外部状态。

## 证据规则

- 在运行候选方案之前，明确场景、判定基准、指标、排除项和决策规则。
- 固定所有未测试变量，或记录并分析混杂因素。
- 除非决策明确允许正确性下降，否则正确性失败不能通过更好的速度、令牌使用量或成本来弥补。
- 使用重复运行，并报告原始值、中心值、离散程度、失败情况和离群值；绝不要将最佳运行结果作为主要结论。
- 将设置或索引成本、稳态成本、维护负担和运行时成本分开。
- 将测量证据、派生证据、估算证据和定性证据放在不同字段中。

## 检查清单

### 1. 定义决策与实验

- [ ] 说明基准测试必须支持的决策、候选方案、目标用户、代表性工作负载，以及明确的非目标。
- [ ] 除了涵盖能够体现各候选方案所宣称优势的场景，还应包括简单方案或内置方案也有合理胜算的普通场景；不要为其中一方构造功能演示。
- [ ] 定义场景输入、预期结果、正确性标准、失败条件，以及独立于候选方案自我报告的判定依据。
- [ ] 定义主要指标和次要指标、单位、测量点、接受阈值、允许的权衡，以及平局或无法得出结论时的规则。
- [ ] 确定必须保持不变的变量：仓库修订版本、模型、提示词、权限、运行时、硬件、数据、缓存策略和网络条件。
- [ ] 预先声明基于试运行得出的重复次数，并将其与最小有意义效果和观测噪声关联起来；或者采用有固定误差容忍度和最大运行次数的有界序贯停止规则。
- [ ] 在查看第一个候选方案的结果之前，冻结并计算场景文本、fixture、预期结果、运行器、解析器和决策规则的哈希值。
- [ ] 在创建 worktree、临时数据或运行器之前，阅读仓库说明并检查 Git 状态。
- [ ] 从运行开始维护由本次运行拥有的资源清单，记录每个新创建的绝对路径、worktree、进程 ID、缓存、账户、数据集、报告和临时工件；绝不要将预先存在的资源或凭据登记为清理目标。
- [ ] 要求场景无副作用或具备幂等性，并使用一次性账户或数据集；在执行前定义外部写入授权、成本和速率预算、清理措施以及回滚证据。
- [ ] 如果候选方案解决的不是同一任务、无法独立评估正确性、无法隔离外部影响，或者决策规则是在查看结果后才确定的，则返回 `BLOCKED`。

### 2. 构建对称的测试工具

- [ ] 对每个候选方案使用相同的运行器、超时时间、日志记录、环境构建方式和工件收集方式。
- [ ] 从同一提交创建干净的 worktree 或等效的隔离副本，并验证起始状态完全一致。
- [ ] 盘点可能使候选方案行为泄漏到原本应隔离的各组之间的全局级和用户级说明、钩子、插件、设置、凭据、缓存以及环境变量；对每一项进行禁用、均衡处理或记录。
- [ ] 控制可能影响结果的种子、时钟、区域设置、并发、网络访问、依赖版本、缓存状态、预热过程和场景顺序。
- [ ] 记录确切的候选方案配置、功能开关、提示词、命令行、权限和版本。
- [ ] 定义对称的调优策略和预算——默认配置、同等调优的配置，或两者兼用——以避免在看到另一候选方案的结果后单独优化其中一个候选方案。
- [ ] 添加激活检查，以证明每个候选方案确实被使用，并识别静默回退、部分激活或混合执行。
- [ ] 在基准测试前，使用已知的通过和失败 fixture 验证输出解析器、差异规则、测试判定依据和指标收集器。
- [ ] 将一次性设置、索引、编译或下载成本与稳态执行成本及摊销成本分开。
- [ ] 根据资源清单定义清理和故障恢复流程，确保崩溃或超时的运行不会污染后续运行。

### 3. 执行并捕获证据

- [ ] 以均衡或随机化的顺序运行候选项，避免系统性的热缓存或时间优势。
- [ ] 对每次运行捕获开始和结束状态、命令、退出状态、计时、资源指标、日志、输出、差异、测试结果以及候选项特有的工件。
- [ ] 在评分前验证激活状态；将未经证明的运行或回退运行标记为无效，而不是将其归于预期候选项。
- [ ] 在检查性能和成本指标之前，先根据预定义的判定基准评估正确性。
- [ ] 将任务完整性与正确性和效率分开评估：验证每一项必需结果以及禁止的副作用，而不是将更小的差异、更少的 token 数量或成功的子集视为完成任务。
- [ ] 对盲审人工或定性评估者隐藏候选项身份，并随机化呈现顺序；记录分歧，而不是将其导向某个偏好的候选项。
- [ ] 将超时、崩溃、格式错误的输出、部分完成、工具错误和环境故障记录为不同的失败类别。
- [ ] 按照预定义次数重复有效运行，并保留每次运行的原始结果，不得删除不利的数据。
- [ ] 当环境漂移、速率限制、外部服务中断、后台负载或运行器缺陷导致后续运行无法比较时暂停运行。
- [ ] 修复测试线束缺陷后，重新运行两个候选项；绝不能只为其中一方修复证据。
- [ ] 将设置、激活、解析器和环境故障与任务错误分别处理，然后说明设置可靠性是否属于实际产品决策的一部分。

### 4. 分析有效性和结果

- [ ] 仅排除符合预定义无效化规则的运行，并记录原因、证据以及排除是否会改变结论。
- [ ] 在汇总之前，报告每个场景的正确性、失败情况、延迟、资源使用、token 或用量、工具调用以及其他成本。
- [ ] 使用适合样本和分布的中位数、百分位数、置信区间或其他统计量；展示离散程度和样本量。
- [ ] 将不同单位或不同工作负载的指标分开，并避免使用单一综合评分，除非其权重已在执行前定义。
- [ ] 检查差异是否超过测量噪声，以及某个场景是否支配汇总结果。
- [ ] 将设置成本、稳态成本、维护复杂度、可移植性、失败行为和运营负担与运行时指标分开分析。
- [ ] 标明合成测试夹具、估算的 token 数量、基于字符的代理指标、建模成本和人工判断，使其不会被误认为是观测到的遥测数据。
- [ ] 当定性输出质量会实质性影响决策且自动化正确性不足时，请求独立的盲审。

### 5. 决策、保留和清理

- [ ] 仅当候选项满足正确性要求，并依据预定义决策规则获得了充分的有效证据时，才使用 `WIN`。
- [ ] 当差异在运营层面可以忽略，或在既定优先级下各项权衡达到平衡时，使用 `TIE`。
- [ ] 当样本量、激活状态、判定基准、环境控制或相互冲突的场景使可靠选择无法实现时，使用 `INCONCLUSIVE`。
- [ ] 保留可复现的命令、配置、场景定义、预期结果、原始结果、规范化结果以及独立验证所需的分析。
- [ ] 仅移除由本次运行拥有的台账条目：验证绝对路径仍位于批准的临时根目录内，停止准确记录的进程 ID，保留有未提交更改或预先存在的工作树，绝不删除凭据，并验证源状态和外部基线状态。
- [ ] 报告无效运行、排除项、混杂因素、对假设的敏感性，以及结论可能被证伪的方式。
- [ ] 报告比较完成后仍然存在的剩余决策风险，包括不受支持的工作负载、未测量的成本、不稳定的环境以及可能逆转裁决的假设。
- [ ] 返回场景级证据、汇总权衡、裁决、决策指导、局限性以及清理确认。
