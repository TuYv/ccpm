# 实施启动

使用此技能作为从已商定的实施范围过渡到隔离执行的明确节点。保持用户的原始检出和现有分支不变，并最终生成一个干净、可供用户推送的本地分支。

## 不可妥协的边界

- 将显式调用此技能视为对以下操作的授权：获取远程内容、创建一个专用工作树、变基或重放任务所拥有的更改、创建最终本地分支、暂存任务所拥有的文件，以及创建一个本地提交。它绝不授权推送、创建拉取请求或执行任何 GitHub 变更操作。
- 不要在仅调查阶段或获得必要的用户批准之前开始。请先完成规划以及任何必要的实施范围约定。
- 当需要远程 PR 证据时，使用只读 GitHub 访问。
- 保留不相关的更改以及用户拥有的更改。不要为了给此工作流腾出空间而移除现有工作树或重写现有分支。

## 1. 确立任务边界

记录原始需求、成功标准、预期目标（除非用户另有说明，否则为 `origin/main`）、任务所拥有的路径、兼容性边界、明确不支持的情况，以及所需的仓库技能。对于多步骤任务，创建并维护仓库要求的 ExecPlan。即使仓库策略要求创建 ExecPlan、审查包、账本、跟踪记录或临时报告，默认情况下它们也仅用于操作；除非原始需求或仓库策略明确规定该确切路径是必须提交的交付物，否则不要将其添加到交付路径清单中。

如果当前目录是本次对话中先前为同一任务创建的工作树，则恢复使用该工作树。否则，仅在用户当前的检出中继续操作到足以创建新工作树为止。

## 2. 从当前 main 创建分离的工作树

1. 在不做任何修改的情况下，验证源检出的原始状态。
2. 获取 `origin main`。如果获取失败，请停止操作，而不要声称过期的引用是最新的。
3. 记录获取到的 `origin/main` 提交。
4. 在已配置的 Codex 工作树根目录下选择一个面向任务的唯一路径。同时检查文件系统和 `git worktree list`；绝不要复用或删除发生冲突的路径。
5. 运行 `git worktree add --detach <worktree> origin/main`，并在该工作树中执行后续所有实施工作。
6. 确认新工作树以分离状态指向所记录的提交，并且初始状态干净。

此时不要创建最终分支。分离的工作树可确保最终由 `$pr-draft-summary` 建议的分支具有权威性，并防止临时命名意外成为输出结果。

## 3. 在不创建任务提交的情况下实施

在实施、针对性测试、格式化和审查修复期间，保持任务差异未提交。显式跟踪新文件，因为普通的差异统计会忽略未跟踪文件。将一份规范的交付路径清单与操作性产物分开维护，并要求清单中的每个路径都有具体的交付理由。使用适用的仓库技能和参考资料，包括在进行面向用户或运行时的更改之前使用 `$implementation-strategy`。

当任务可以在不暂时破坏受支持契约的情况下进行拆分时，每次实现一个范围较窄的端到端行为切片，并在添加下一个切片之前运行其针对性测试。不要将横切迁移或原子兼容性变更强行拆分为无法独立保持有效的人为切片。

不要创建检查点提交。如果外部中断需要额外保护，请保持专用工作树不变，或使用名称清晰的临时 stash；继续工作前恢复这些变更，并且不要将该 stash 视为交付物。

### 接手现有拉取请求

当用户要求完成其他作者的拉取请求时：

1. 通过只读访问刷新 PR 元数据、头部、讨论以及完整的三点差异。
2. 确认该 PR 仍然适合作为接手来源。不要将已经合并的 PR 视为仍在进行的接手对象。
3. 将原始 PR 的完整任务差异应用到基于当前 `origin/main` 的工作树中；不要从贡献者分支派生最终分支，也不要保留其中间提交拓扑。
4. 记录原始 PR 编号、PR 作者登录名、经过验证的提交身份、现有的有效 `Co-authored-by` 尾注、关联的 issue，以及替代实现必须保留的原始意图。
5. 如果无法从 PR 的提交中获得有效的作者身份，请在提交前停止并询问用户。绝不要虚构电子邮件地址。

## 4. 在最新的主分支上重放完整任务

在实现、针对性测试和格式化均稳定后，再次获取 `origin main`。如果它已有更新：

1. 确认每一项本地变更都归属于该任务。
2. 将已跟踪和未跟踪的任务变更保存到一个具有唯一名称的临时 stash 中。
3. 将分离的 HEAD 变基到 `origin/main` 上。由于不存在任务提交，此操作会将空的本地提交范围更新到新的基线。
4. 重新应用 stash，并确认仅在干净应用后才将其移除。
5. 只有当需求和周边源代码能明确得出正确结果时，才解决冲突。否则，请保留 stash 和冲突证据，然后停止并请求用户指示。
6. 重新运行格式化以及受新基线影响的每一项针对性检查。

将此次观察到的 `origin/main` 提交记录为最终基线候选。不要仅仅因为某个旧基线的变更看起来无关，就将其称为“最新”。

## 5. 完成最终审查和验证

针对最终基线候选上的完整任务所属差异，运行仓库中适用的完成门禁。在冻结第一个审查指纹之前，检查实际的最终提交钩子配置，并针对每个可能重写交付路径的钩子步骤，运行与之完全等效且安全、不产生提交的操作。重复执行重写步骤，直到内容具有幂等性，并在规范化后验证生成文件的哈希或来源。使用 `review_state.py --complete-diff-output <complete.diff>` 生成最终审查证据，使普通的任务所属未跟踪文件无需暂存即可包含在被审查的差异中。对于运行时代码、测试、示例、构建或测试行为，或者会影响行为的文档，请按照规定顺序运行 `$implementation-final-review` 和要求的 `$code-change-verification` 流程。遵守它们的指纹和失效规则。

仅当这些技能自身的仓库规则判定任务不符合条件时（例如仅涉及仓库元数据的变更），才跳过它们。不要仅仅因为差异很小就降低符合条件的门禁要求。

当审查无法收敛、验证失败、缺少必需证据，或最终内容未获得干净审查认可时，不要创建分支或提交。

## 6. 生成完整的 PR 交接材料

仅在审查和验证均已针对最终内容完成后，才调用 `$pr-draft-summary`。向其提供一个自包含的信息包，其中应包含原始需求、实现范围契约、重要决策和意图、包括未跟踪文件在内的完整变更路径清单、最终差异和统计信息、兼容性说明、议题引用以及接管来源信息。

工作树有意处于分离状态。告知 `$pr-draft-summary` 将当前分支值 `HEAD` 视为“尚无分支”，并要求其建议一个具体且未被使用的分支名称；绝不接受 `HEAD` 作为建议。描述必须说明完整的最终变更及其动机，而不能只说明最后一次审查修复。

对于接管，描述应以类似 `This pull request supersedes #<number> and ...` 的文字开头。仅当最终实现确实解决了相应议题时，才保留任何单独的议题关闭行。

如果生成后差异、范围、基线、行为声明、议题关系或来源信息发生变化，则重新生成整个 PR 交接材料。

## 7. 再次检查 main 并创建单个提交

在创建分支前，立即再次获取 `origin main`。如果它与最终基线候选不同，则返回第 4 节并在新基线上重新应用变更。然后执行 `$implementation-final-review` 的第 20 步：仅当经过验证的基线推进闭环证明任务差异和组件工作区完全相同，并且已完成一项完整、无重叠的上游依赖项/工具审计时，才保留干净审查认可。即使该闭环适用，也要在新基线上重新运行每个强制性最终验证门禁，并重新生成 PR 交接材料。如果任何闭环条件缺失或含糊不清，则重新执行受影响的检查、全新的独立审查、验证和 PR 交接材料生成。稳定后：

1. 检查建议的分支是否已存在于本地、远程或其他工作树中。在创建会发生冲突的分支之前，要求 `$pr-draft-summary` 提供下一个可用的数字后缀，并重新生成交接材料。
2. 在任务工作树中创建名称与建议完全一致的分支。
3. 仅暂存任务所有且将交付的路径清单，包括预期的新文件。提交前，将暂存的变更路径集合与规范交付清单逐字节比较；任何缺失或意外路径都必须立即中止操作。尤其不要仅仅因为实现期间需要某个被忽略的 ExecPlan 或审查产物，就将其暂存。
4. 使用 PR 草稿标题作为提交主题。
5. 对于接管，将经验证的原 PR 作者添加为 `Co-authored-by: Name <email>`，保留从导入的提交中获得的彼此不同且有效的共同作者尾注，并对身份去重。
6. 只创建一个提交。让仓库钩子正常运行。

创建分支和提交相同内容属于仓库记录维护，不会使已完成的纯内容审查失效。如果钩子或手动修复更改了任务内容，请停止操作，在 `$implementation-final-review` 下对更改进行分类，并重新运行所有已失效的关卡和 `$pr-draft-summary`，然后再替换或修订提交。

## 8. 验证并交接

运行 `python .agents/skills/implementation-kickoff/scripts/validate_handoff.py --repo <worktree> --base <final-base> --expected-branch <branch> --shipped-path-manifest <manifest>`。对于接管，还需为每个必须署名的身份传入 `--required-trailer-email <verified-email>`。交付路径清单必须是一个有限的常规文件，其类型和内容均从同一个已打开的描述符中读取。该文件每行包含一个准确的仓库相对交付路径，且不包含操作性产物。

如果最终审查提供了已审查内容的指纹，请独立确认已提交的差异具有该指纹。验证器检查 Git 拓扑和仓库整洁状态；它不能替代语义审查或指纹验证。

保留工作树。报告工作树路径、最终观测到的基础提交、分支、提交 SHA 和主题、验证结果、审查状态、PR 标题和描述，以及是否包含接管来源信息。将工作树路径和验证器输出视为本地诊断信息：绝不要将它们包含在 PR 标题、PR 描述或其他可直接复制使用的外部文本中。明确说明未推送任何内容，也未创建拉取请求。

## 失败处理

- 获取失败：停止操作，不创建或更新最终分支。
- 工作树或分支冲突：保留现有目标，并选择一个新的未使用路径或重新生成的分支建议。
- 重放冲突：保留可恢复的任务更改；如果正确的解决方式存在歧义，请请求指示。
- 审查或验证失败：保留分离状态的任务工作树以便继续处理；不要将提交打包为就绪状态。
- 提交钩子引发变更：使受影响的证据失效，修复缺失的钩子等效预检或生成文件规范化，然后重复运行所需关卡。
- 最终状态不整洁或包含多个提交：在不丢弃用户所有的工作且完成纠正之前，不要将其作为已完成状态进行交接。
