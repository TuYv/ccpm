# 可维护性/结构审计器（L3 工作器）

**类型：** L3 工作器

专门用于审计测试文件组织、孤立测试、分散的重复测试以及布局偏移，以确保测试套件不断增长时仍具备可维护性。

## 目的与范围

- 审计**测试可维护性/结构**（类别 8：中优先级）
- 检测布局模式（扁平式 / 镜像式 / 共置式 / 混合式）
- 标记超过增长阈值的扁平目录，并提供按领域分组的建议
- 验证测试与源代码映射的一致性、孤立测试以及分散的重复测试
- 输出 `MOVE`、`MERGE` 或 `DELETE_ORPHAN`
- 计算合规性评分（X/10）

## 输入

**必须阅读：** 加载 `references/audit_worker_core_contract.md`。

接收包含以下内容的 `contextStore`：`tech_stack`、`testFilesMetadata`（所有类型——包括自动化测试和手动测试）、`codebase_root`、`output_dir`、`domain_mode`、`all_domains`。

**注意：** 与其他接收按类型筛选后元数据的工作器不同，此工作器接收所有测试文件，因为目录结构分析需要完整了解自动化测试和手动测试的存放位置。

## 工作流程

检测策略：使用双层检测（候选项扫描，然后进行上下文验证）；仅当验证方法存在歧义时，才加载 `references/two_layer_detection.md`。

1) **解析上下文：** 从 `contextStore` 中提取测试文件列表、`output_dir`、`codebase_root` 和领域信息
2) **映射源代码结构：** 对源代码目录（`src/`、`app/`、`lib/`）执行 Glob，以构建源代码领域/模块树
3) **映射测试结构：** 按父目录对测试文件进行分组，统计每个目录中的文件数量，并对位置进行分类
4) **扫描检查（第 1 层）：** 使用 Glob/Grep 模式执行 6 项审计检查（参见“审计规则”）
5) **上下文分析（第 2 层——强制）：** 对每个候选发现应用第 2 层过滤器（参见各项检查）
6) **收集发现：** 记录违规项及其严重程度、位置、工作量、操作和建议
7) **计算评分：** 按严重程度统计违规项，并计算合规性评分（X/10）
8) **编写报告：** 根据 `references/templates/audit_worker_report_template.md` 在内存中构建完整的 Markdown 报告，并通过单次 Write 调用写入 `{output_dir}/ln-637--global.md`
9) **返回摘要：** 向协调器返回最简摘要（参见“输出格式”）

## 审计规则

### 1. 布局模式检测

**检查内容：** 检测项目采用的测试组织模式，并检查是否存在非预期的模式混用

**检测方法：**
- 对每个测试文件的位置进行分类：
  - **共置式：** 测试文件与源文件位于同一目录中（例如 `src/users/users.test.ts`）
  - **镜像式：** 测试文件位于平行的目录层级中（例如 `tests/users/users.test.ts` 映射 `src/users/`）
  - **集中扁平式：** 所有测试都位于单个目录中（例如 `tests/` 或 `__tests__/`）
  - **手动：** 位于 `tests/manual/` 中的文件（仅供参考，不予标记）
- 计算各种模式的分布百分比
- 如果超过 70% 的文件遵循同一种模式，则该模式为主导模式
- 如果没有任何模式达到 70%，则为混合模式

**第 2 层：**
- 如果不同的测试类型采用不同模式，则混合布局是可以接受的（例如，单元测试与源码放在一起，而集成测试位于 `tests/automated/integration/` 中）。检查偏差是否与测试类型相关
- 测试文件少于 5 个的项目 -> 跳过（规模太小，无法确立模式）

**严重程度：** 如果混合布局没有明确的基于类型的规则（同一类型的测试中超过 30% 偏离主导模式），则为 **MEDIUM**

**建议：** 统一测试放置方式——为每种测试类型选择一种模式，并记录在测试指南中
**操作：** `MOVE`

**工作量：** L

### 2. 测试与源码的映射

**内容：** 检测孤立的测试文件（源码文件已删除，但测试仍然存在）以及路径不匹配

**检测方法：**
- 对于每个测试文件，提取其隐含的源码模块：
  - `users.test.ts` -> `users.ts` 或 `users/index.ts`
  - `test_payments.py` -> `payments.py`
- 检查隐含的源码文件是否存在于预期位置
- 如果未找到源码文件 -> 孤立测试候选项

**第 2 层：**
- 跳过集成/e2e 测试（测试多个模块，不存在 1:1 的源码映射）
- 跳过采用集中式扁平布局的测试（不应存在基于路径的映射）
- 跳过从多个源码模块导入内容的测试文件（本质上属于集成测试）
- 跳过工具/辅助测试文件（`test_utils.ts`、`test_helpers.py`）

**严重程度：** 孤立测试（死代码）为 **MEDIUM**，路径不匹配为 **LOW**

**建议：** 删除孤立测试，或更新测试以匹配当前的源码结构
**操作：** 当对应的源码行为已不存在时使用 `DELETE_ORPHAN`；否则使用 `MOVE`

**工作量：** S

### 3. 扁平目录增长

**内容：** 检测文件数量过多、适合通过子目录分组的测试目录

**检测方法：**
- 统计每个目录中的测试文件数量（不包括 `node_modules`、`dist`、`build`）
- 阈值：
  - 一个扁平目录中有 15-20 个文件 -> LOW（接近上限）
  - 一个扁平目录中有 \>20 个文件 -> MEDIUM（建议重构）
- 对于 MEDIUM 级别的发现，通过分析文件名前缀来建议基于领域的分组：
  - 按共同前缀分组（例如，`test_auth_*.py` -> `auth/` 子目录）
  - 如果可以获取源码领域结构，则与其交叉参照

**第 2 层：**
- 如果目录已包含子目录，则跳过（已进行部分组织）
- 如果文件使用清晰的命名前缀，无需子目录即可提供充分的组织，则跳过
- 跳过 `tests/manual/`（手动测试结构有单独的约定）

**严重程度：** **MEDIUM**（>20 个文件），**LOW**（15-20 个文件）

**建议：** 按领域/功能将测试分组到子目录中。根据文件名分析建议具体的分组方式：
```
# Before (flat):
tests/test_auth_login.py, tests/test_auth_tokens.py, tests/test_users_crud.py, ...

# After (grouped):
tests/auth/test_login.py, tests/auth/test_tokens.py, tests/users/test_crud.py, ...
```

**工作量：** M
**操作：** `MOVE`

### 4. 领域分组对齐

**内容：** 检查测试目录分组是否与源码领域结构相对应

**检测方法：**
- 将源码领域目录（来自 `all_domains` 或扫描得到的 `src/`）与测试目录名称进行比较
- 对于每个源码领域，检查是否存在相应的测试分组：
  - 镜像布局：存在 `tests/{domain}/` 目录
  - 共置布局：测试文件存在于 `src/{domain}/` 中
- 标记没有任何对应测试分组的源码领域

**第 2 层：**
- 如果项目没有明确的领域结构（`domain_mode="global"` 或源代码领域少于 2 个），则跳过
- 跳过 references/common/utils 领域（这些是横切关注点，可能不需要专用测试组）
- 如果项目采用集中式扁平布局（不预期进行分组），则跳过

**严重程度：** 对于源文件超过 5 个但没有测试组的领域为 **MEDIUM**，否则为 **LOW**

**建议：** 为领域创建测试目录/组，以保持结构一致

**工作量：** M
**操作：** `MOVE`

### 5. 共置一致性

**内容：** 检测项目采用的共置模式并标记不一致之处

**检测：**
- 统计放在源文件旁的测试文件与放在专用测试目录中的测试文件数量
- 计算比率：共置数量 /（共置数量 + 集中放置数量）
- 如果比率为 0.0-0.2 -> 集中式模式
- 如果比率为 0.8-1.0 -> 共置模式
- 如果比率为 0.2-0.8 -> 混合模式（可能存在不一致）
- 对于混合模式：识别偏离主导模式的模块

**第 2 层：**
- 如果不同测试类型采用不同的放置方式，则混合模式可以接受：
  - 单元测试共置 + 集成/e2e 测试集中放置 -> 有效的混合模式
  - 检查测试文件命名/位置与类型之间的关联
- 测试文件少于 5 个的项目 -> 跳过

**严重程度：** 如果超过 20% 的同类型测试偏离主导放置模式，则为 **MEDIUM**

**建议：** 统一测试放置方式——移动偏离模式的测试，使其遵循项目的主导模式

**工作量：** M-L
**操作：** `MOVE`

### 6. 分散的重复测试

**内容：** 检测分散在多个文件中的重复或近似重复测试，这些测试使用一个规范测试会更易于维护

**检测：**
- 按导入的源模块和测试描述关键字对测试进行分组
- 查找文件之间重复的准备代码块、重复的断言和重复的场景名称
- 比较源代码导入存在重叠且准备/断言文本相似的测试文件

**第 2 层：**
- 跳过有意设计的矩阵测试，其中每个文件覆盖不同的环境、适配器、提供商或浏览器
- 当断言覆盖不同的产品行为时，跳过重复的名称
- 跳过已由 `ln-632` 报告为 E2E 浪费的重复问题；此工作程序仅负责结构性碎片化

**严重程度：** 当重复结构增加维护成本时为 **MEDIUM**，对于小范围的局部重复为 **LOW**

**建议：** 在保留产品信号的前提下，将重复测试合并到一个规范位置或共享辅助工具中

**工作量：** S-M
**操作：** `MERGE`

## 评分算法

**强制阅读：** 加载 `references/audit_scoring.md`。

**严重程度映射：**
- 孤立测试、过度扁平的目录（>20）、布局不一致、共置不一致、分散的重复测试 -> MEDIUM
- 接近扁平目录上限（15-20）、缺少领域测试组（小型领域）、路径不匹配 -> LOW

## 输出格式

**强制阅读：** 加载 `references/templates/audit_worker_report_template.md`。

按照 `references/audit_summary_contract.md` 编写 JSON 摘要。在托管模式下，调用方会同时传入 `runId` 和 `summaryArtifactPath`；在独立模式下，工作程序按照共享契约生成自己的运行范围制品路径。

将报告写入 `{output_dir}/ln-637--global.md`，其中 `category: "Test Maintainability"`，并执行以下检查：layout_pattern、test_source_mapping、flat_dir_growth、domain_grouping、colocation_consistency、fragmented_duplicates。

按照 `references/audit_summary_contract.md` 返回摘要。

当 `summaryArtifactPath` 缺失时，将独立运行时摘要写入 `.hex-skills/runtime-artifacts/runs/{run_id}/evaluation-worker/{worker}--{identifier}.json`，并可选择在结构化输出中回显相同的摘要。
```
Report written: .hex-skills/runtime-artifacts/runs/{run_id}/audit-report/ln-637--global.md
Score: X.X/10 | Issues: N (C:N H:N M:N L:N)
```

## 关键规则

应用已加载的 `references/audit_worker_core_contract.md`。

- **不要自动修复：** 仅报告问题，并提出重构建议
- **工作量应切合实际：** S = <1h，M = 1-4h，L = >4h
- **规模过小时跳过：** 如果测试文件总数少于 5 个，则返回 10/10 分且不包含任何发现
- **不检查命名：** 测试命名一致性（`.test.` 与 `.spec.`）不在范围内——不要重复检查
- **涵盖两种类型：** 同时分析自动化测试和手动测试文件的位置，以获得完整的布局全貌
- **提供具体建议：** 对于扁平目录增长问题，始终根据文件名前缀分析提出具体的子目录分组建议
- **独特视角：** 仅审计可维护性和结构。不要评估产品行为、E2E 用户旅程价值、作品集价值、缺失覆盖、可信度、断言强度或手动证据质量。
- **必须指定操作：** 每项发现都使用 `MOVE`、`MERGE` 或 `DELETE_ORPHAN` 中的一项
