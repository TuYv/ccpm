## 首先澄清

在设计付费墙之前，请确认以下输入。如果有任何一项未知或含糊不清，请务必询问——不要自行假设：

- [ ] **升级模式**——免费增值转付费、试用转付费或套餐升级（决定付费墙类型和触发架构）
- [ ] **免费与付费的边界**——哪些内容受到限制（定义付费墙需要传达的价值差距）
- [ ] **Aha 时刻**——确保只有在用户体验到价值后才触发提示（价值优先原则）
- [ ] **平台**——Web、iOS 或 Android（IAP 规则和佣金会对 Web 与应用内流程形成不同约束）

停止规则：仅询问对输出影响最大的 2-3 个问题。如果用户说“直接起草即可”，则继续执行，并在交付内容顶部列出你的假设。

## 初步评估

### 必需的背景信息

| 问题 | 重要性 |
|----------|---------------|
| 升级模式是什么？（免费增值转付费、试用转付费、套餐升级） | 决定付费墙类型 |
| 哪些内容免费，哪些内容付费？ | 定义需要传达的价值差距 |

| 用户的 Aha 时刻是什么？ | 决定付费墙应在何时出现 |
| 采用什么定价模式？（按席位、按用量、固定价格） | 影响付费墙信息传达 |
| 移动应用、Web 应用，还是两者都有？ | 涉及特定平台的要求 |

## 价值优先原则

付费墙设计中最重要的一条规则：**用户必须先体验到真正的价值，然后才能看到升级提示。**

### 价值优先检查清单

- [ ] 用户已完成激活事件（已到达 Aha 时刻）
- [ ] 用户已使用产品至少 2-3 次
- [ ] 用户已创建或存储一旦离开就会失去的数据
- [ ] 升级让人感觉是自然而然的下一步，而不是一个陷阱

### 何时展示与何时不应展示

| 展示时机 | 不应展示的时机 |
|------|------------|
| 达到顿悟时刻后 | 新手引导期间 |
| 用户确实触及限制时 | 首次登录时 |
| 用户点击付费功能时 | 用户正在执行任务时 |
| 完成里程碑后 | 遭遇令人沮丧的体验后立即展示 |
| 会话开始时（温和提醒） | 每次操作后 |

## 付费墙触发架构

### 触发器类型

| 触发器 | 触发时机 | 最适合 |
|---------|--------------|----------|
| 功能门控 | 用户点击锁定的功能 | 按功能区分的套餐层级 |
| 使用量限制 | 用户达到配额 | 基于使用量的定价 |
| 试用到期 | 试用期即将结束 | 限时试用模式 |
| 基于时间 | 活跃使用 N 天后 | 免费增值用户培育 |
| 基于里程碑 | 用户达成 X 后 | 在成功时刻追加销售 |
| 基于团队 | 团队规模超过免费席位限制时 | 按席位收费模式 |

### 触发器优先级映射

| 用户状态 | 主要触发器 | 时机 |
|-----------|----------------|--------|
| 已激活，尚未触及限制 | 功能门控（当用户尝试使用付费功能时） | 点击时 |
| 接近限制 | 温和警告（达到限制的 80%） | 主动提醒 |
| 已触及限制 | 使用量限制付费墙 | 执行超出限制的操作时 |
| 14 天试用期的第 7 天 | 试用即将结束提醒 | 会话开始时 |
| 14 天试用期的第 13 天 | 紧急试用到期提醒 | 会话开始时 + 电子邮件 |
| 试用期第 14 天 | 试用已到期 | 登录时 |
| 免费使用且已活跃 30 天以上 | 基于价值的升级提示 | 会话开始时，每周一次 |

```
│                                     │
```

| 触发器 | 标题模式 | CTA 模式 |

## 功能门控模式

### 软门控（预览 + 锁定）

用户可以看到该功能的作用，但无法完整使用。

```
┌──────────────────────────────┐
│  [Feature Preview]           │  Blurred screenshot or partial result
│                              │
│  [Lock Icon] Pro Feature     │
│                              │
│  [Feature name] lets you:    │
│  - Capability 1              │
│  - Capability 2              │
│                              │
│  [Upgrade to Pro - $X/mo]   │
│  [Maybe Later]              │
└──────────────────────────────┘
```

### 硬门控（阻止 + 说明）

用户完全无法访问该功能。清晰展示其价值。

```
┌──────────────────────────────┐
│  [Lock Icon]                 │
│                              │
│  This feature is available   │
│  on the Pro plan             │
│                              │
│  What you get:               │
│  - Benefit 1                 │
│  - Benefit 2                 │
│  - Benefit 3                 │
│                              │
│  [Upgrade to Pro]            │
│  [Compare Plans]             │
└──────────────────────────────┘
```

### 功能门控设计规则

- 始终说明该功能为何有价值（而不只是说明它已被锁定）
- 尽可能展示该功能会生成的内容（输出预览）
- 为想要了解更多详情的用户提供“比较套餐”链接
- 不要限制用户在试用期间已经使用过的功能

## 使用限额用户体验

### 接近限额（80% 警告）

```
┌──────────────────────────────────┐
│  [Progress Bar: 80%]            │
│  You've used 80 of 100 credits  │
│                                  │
│  [Get More Credits]  [Dismiss]  │
└──────────────────────────────────┘
```

### 达到限额（100%）

```
┌──────────────────────────────────────┐
│  [Progress Bar: 100%]               │
│  You've reached your monthly limit  │
│                                      │
│  Free: 100 credits | Pro: Unlimited │
│                                      │
│  [Upgrade to Pro]                   │
│  [Delete items to free space]       │  Alternative action
└──────────────────────────────────────┘
```

### 使用限额规则

- 在达到限额之前显示使用情况（在 UI 中显示进度指示器）
- 尽可能提供替代操作（删除、归档、导出）
- 达到限额时，绝不能删除用户数据
- 提供宽限期（不要在任务进行到一半时中断）

## 试用到期流程

### 试用倒计时序列

| 日期 | 渠道 | 消息 | 语气 |
|-----|---------|---------|------|
| 第 7 天（共 14 天） | 应用内横幅 | “你的试用期还剩 7 天” | 信息提示 |
| 第 10 天 | 电子邮件 | “还剩 4 天——以下是你已经取得的成果” | 价值总结 |
| 第 12 天 | 应用内模态框 | “还剩 2 天——不要失去对 [feature] 的访问权限” | 轻度紧迫感 |
| 第 13 天 | 电子邮件 | “明天是最后一天” | 紧迫感 + 优惠 |
| 第 14 天 | 应用内全屏页面 | “你的试用期已结束” | 明确的选项 |
| 第 15 天 | 电子邮件 | “我们已妥善保管你的数据——随时可以重新激活” | 安心保证 |


## 时机与频率规则

### 频率上限

| 规则 | 实现方式 |
|------|---------------|
| 每个会话最多显示 1 次付费墙 | 不要在一次访问中打断用户两次 |
| 用户关闭后冷却 3～7 天 | 如果用户点击“暂不”，至少等待 3 天 |
| 切勿在执行任务期间显示 | 如果用户正在创建、编辑或处于工作流中途，请勿打断 |
| 每月最多显示 3 次 | 如果用户在一个月内关闭 3 次，则在下个月之前停止显示 |
| 跟踪厌烦信号 | 如果用户反复在 1 秒内关闭付费墙，则延长冷却时间 |

### 逐步升级模式

| 尝试次数 | 方式 | 干扰程度 |
|---------|----------|-------------|
| 1 | 低调的横幅或侧边栏小组件 | 低 |
| 2 | 包含价值主张的模态框 | 中 |
| 3 | 包含特别优惠（折扣/延长试用期）的模态框 | 中高 |
| 4+ | 降低频率，改用电子邮件培育 | 低（更换渠道） |

## 升级流程优化

### 从点击付费墙到完成付款

| 步骤 | 优化方式 |
|------|-------------|
| 1. 点击升级 CTA | 打开升级流程（如非必要，请勿重定向到外部页面） |
| 2. 选择方案 | 预先选中推荐方案，并显示方案对比 |
| 3. 付款 | 预填已知信息（电子邮件、姓名），支持所有付款方式 |
| 4. 确认 | 立即开放付费功能访问权限，并发送确认电子邮件 |
| 5. 升级后 | 引导用户了解新解锁的功能，并营造庆祝时刻 |

### 减少阻力

- 让升级流程保持在当前情境中（使用模态框或滑出式面板，而非重定向至完整页面）
- 预填所有已知信息
- 支持已保存的付款方式，并为再次升级的用户提供一键升级
- 在付款步骤之前清楚显示价格（避免意外收费）

## 避免暗黑模式

### 绝不使用的模式

| 暗黑模式 | 失败原因 | 合乎道德的替代方案 |
|-------------|-------------|---------------------|
| 隐藏关闭按钮 | 破坏信任，并引发客服工单 | 在右上角清楚显示 X |
| 羞辱性文案（“不，我不想发展自己的业务”） | 带有操纵性，会降低用户对品牌的尊重 | “以后再说”或“暂不” |
| 倒计时器（制造虚假紧迫感） | 用户会发现倒计时重置，从而彻底损害可信度 | 仅用于确实即将到期的优惠 |
| 令人困惑的方案选择 | 用户感觉受骗，退款率更高 | 使用清晰的方案名称并进行如实对比 |
| 阻止关键操作 | 用户感觉被困住，并导致流失 | 允许用户继续使用现有功能 |
| 增加降级难度 | 存在监管风险（尤其是在欧盟/加拿大） | 提供一键降级选项 |

## 特定平台注意事项

### iOS App Store

- Apple 要求数字商品/服务使用应用内购买（IAP）
- Apple 收取 30% 的佣金（小型企业计划为 15%）
- 必须遵守 App Store 审核指南 3.1
- 不得在应用内链接到外部支付页面
- 必须清晰说明订阅条款和续订方式

### Google Play

- IAP 要求与 iOS 类似
- 数字商品必须使用 Google Play 结算
- 年收入的前 $1M 收取 15% 的佣金，之后收取 30%
- 必须提供清晰的订阅管理方式

### Web 应用

- 可完全控制支付流程和呈现方式
- 可提供任意支付方式
- 无平台佣金
- 可自由进行 A/B 测试，不受应用审核延迟影响

## 指标与基准

### 关键指标

| 指标 | 公式 | 基准 |
|--------|---------|-----------|
| 付费墙展示率 | 看到付费墙的用户数 / 活跃用户数 | 需跟踪，无通用基准 |
| 付费墙点击率 | 升级点击次数 / 付费墙展示次数 | 5-15% |
| 升级完成率 | 已完成升级次数 / 升级点击次数 | 30-60% |
| 免费转付费转化率 | 付费用户数 / 免费用户总数 | 免费增值模式为 2-5%，试用模式为 15-30% |
| 每用户收入（ARPU） | 总收入 / 活跃用户数 | 因用户细分而异 |
| 升级后流失率（30 天） | 30 天内流失的用户数 / 新增付费用户数 | < 10% |

### 警示信号

| 信号 | 诊断 | 行动 |
|--------|-----------|--------|
| 点击率 < 3% | 付费墙文案或展示时机不当 | 测试不同的触发条件和信息表达 |
| 完成率 < 20% | 升级流程阻力过大 | 简化支付流程 |
| 升级后流失率 > 15% | 所提供的价值与预期不符 | 检查功能访问权限和用户引导 |
| 免费转付费转化率 < 1% | 付费墙在用户获得价值之前出现 | 将触发时机延迟到用户激活之后 |

## A/B 测试框架

### 高影响力测试

| 测试 | 假设 | 指标 |
|------|-----------|--------|
| 触发时机（较早与较晚） | 较晚触发 = 更高的转化率 | 免费转付费转化率 |
| 软门槛与硬门槛 | 软门槛（预览）的转化效果更好 | 功能门槛点击率 |
| 文案变体 | 以价值为重点与以紧迫感为重点 | 付费墙点击率 |
| 价格呈现 | 默认按月与默认按年 | ARPU |

### 测试衡量

- 每个测试至少运行 2 周，或每个变体至少获得 100 次转化
- 同时跟踪升级率和升级后 30 天留存率
- 如果一个测试提高了升级量，却增加了流失率，则其净效果为负

## 工具参考

### 1. paywall_trigger_auditor.py

审计付费墙触发器配置中的时机、频率和覆盖范围问题。读取包含触发规则和用户事件数据的 JSON 文件，然后标记配置错误的触发器、缺失的冷却期以及暗黑模式风险。

```bash
python scripts/paywall_trigger_auditor.py triggers.json --format text
python scripts/paywall_trigger_auditor.py triggers.json --format json
```

| 标志 | 类型 | 说明 |
|------|------|-------------|
| `triggers.json` | 位置参数 | 包含触发规则和事件数据的 JSON 文件路径 |
| `--format` | 可选 | 输出格式：`text`（默认）或 `json` |

### 2. upgrade_funnel_analyzer.py

逐步分析从付费墙展示到支付完成的升级漏斗转化情况。识别流失率最高的步骤，计算各阶段之间的转化率，并与行业目标进行基准比较。

```bash
python scripts/upgrade_funnel_analyzer.py funnel.json --format text
python scripts/upgrade_funnel_analyzer.py funnel.json --format json
```

| 标志 | 类型 | 说明 |
|------|------|-------------|
| `funnel.json` | 位置参数 | 包含漏斗步骤数据的 JSON 文件路径 |
| `--format` | 可选 | 输出格式：`text`（默认）或 `json` |

### 3. paywall_copy_scorer.py

根据经过验证的转化模式为付费墙页面文案评分。评估标题结构、利益点清晰度、CTA 吸引力、社会认同元素以及暗黑模式风险。输出 0-100 分的评分和逐项反馈。

```bash
python scripts/paywall_copy_scorer.py copy.json --format text
```

## 故障排查

| 问题 | 可能原因 | 解决方案 |
|---------|-------------|------------|
| 付费墙 CTR 低于 3% | 触发器在用户到达顿悟时刻之前触发，或文案侧重功能而非利益点 | 将触发时机延迟至激活事件之后；将标题改写为以结果为导向的信息（根据 Strava 案例研究，CTR 最多可提升 23%） |
| 升级完成率低于 20% | 支付流程中的摩擦过多（重定向、缺少支付方式、意外收费） | 让流程保持在当前上下文中（模态框/侧滑面板），预填已知信息，并在支付步骤前显示价格 |
| 升级后流失率高于 15% | 价值预期不匹配——付费体验与付费墙承诺不符 | 审计升级后的功能访问权限，添加新解锁功能的引导式导览，并使文案与实际能力保持一致 |
| 免费用户到付费用户的转化率低于 1% | 付费墙在交付价值之前出现，或免费层级过于慷慨 | 梳理激活事件，并确保付费墙仅在顿悟时刻之后触发；审查免费功能与付费功能的边界 |
| 用户反复在 1 秒内关闭付费墙 | 付费墙打断了工作流，或出现得过于频繁 | 用户关闭后将冷却期延长至 7 天以上，每月最多展示 3 次，并改用侵扰性更低的形式（横幅而非模态框） |
| 移动端付费墙的表现比桌面端低 30% 以上 | iOS/Android IAP 流程存在摩擦、关闭按钮触控区域过小，或移动端使用了全屏遮罩层 | 确保触控区域为 44x44px，在移动端使用底部弹层形式，并遵守 App Store 指南 |
| 试用到期邮件的打开率较低 | 主题行过于通用、发送时机不当或邮件送达率存在问题 | 使用使用情况数据进行个性化（“你创建了 12 个项目”），在用户活跃时段发送，并检查垃圾邮件评分 |

## 成功标准

- 对于免费增值模式，免费到付费的转化率在优化后 90 天内达到 2-5%；对于试用模式，则达到 15-30%
- 所有触发类型的付费墙点击率稳定在 5-15%
- 升级完成率（从点击付费墙到完成付款）超过 30%
- 升级后 30 天留存率超过 90%（流失率低于 10%）
- 付费墙引发反感的信号（不到 1 秒即关闭）降至展示次数的 5% 以下
- 付费墙审计中不存在任何暗黑模式（无羞辱性文案、无隐藏关闭按钮、无虚假紧迫感）
- 实施年度方案选项默认选中后，年度方案在新增升级中的采用率达到 40% 以上（基准：提升 20-40%）

## 范围与限制

**范围内：** 产品内升级流程，包括功能门槛、使用量限制页面、试用到期流程、升级触发时机、挽留优惠策略、付费墙页面设计，以及用于优化免费增值到付费和试用到付费转化的 A/B 测试框架。

**范围外：** 面向公众的定价页面（使用 page-cro）、定价模式本身（使用 pricing-strategy）、用户注册后达到顿悟时刻之前的引导流程（使用 onboarding-cro）、初始注册流程（使用 signup-flow-cro），以及升级后的流失干预（使用 churn-prevention）。此技能不涵盖应用商店优化（ASO）或付费获客策略。脚本仅处理本地数据，不与支付处理平台、分析平台或 A/B 测试工具集成。

**限制：** 转化率基准基于 SaaS/应用行业的汇总数据，可能因垂直领域、价格水平和受众而存在显著差异。移动端付费墙的表现高度依赖各平台特定的应用内购买要求（Apple 收取 30% 佣金、Google Play 结算）。脚本分析的是静态快照；实时付费墙优化需要与此处未提供的分析和实验平台集成。

## 集成点

- **pricing-strategy** -- 将定价层级结构和价值指标输入付费墙文案与方案对比设计
- **onboarding-cro** -- 协调激活事件的定义；只有在新用户引导确认用户已达到顿悟时刻后，才应触发付费墙
- **churn-prevention** -- 将升级后的流失数据反馈至付费墙的预期管理；挽留优惠应与流失预防策略保持一致
- **page-cro** -- 面向公众的定价页面设计应与应用内升级流程保持一致；确保信息表达一致
- **signup-flow-cro** -- 注册流程完成后触发试用；试用时长和付费墙展示时机取决于注册情境
- **popup-cro** -- 共享频次上限逻辑和抑制规则；付费墙模态框遵循与营销弹窗相同的用户体验原则

## 相关技能

- **page-cro** -- 用于优化面向公众的定价页面。Paywall-upgrade-cro 负责处理产品内的升级时机。
- **onboarding-cro** -- 在用户尚未完成激活时使用。不要在用户达到顿悟时刻之前展示付费墙。
- **pricing-strategy** -- 在定价模式本身需要重新设计时使用（层级结构、价值指标、价格点）。
- **churn-prevention** -- 在用户升级后又流失时使用。如果用户从未升级，则问题属于此处。
- **signup-flow-cro** -- 用于初始注册流程。Paywall-upgrade-cro 负责处理注册后的变现。
