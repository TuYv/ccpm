# Suede 目录分发

Suede 将目录分发视为一个可验证的发现层，而不是提交数量竞赛。通过选择合适的目录、围绕真实的发布节点安排顺序、调整真实可信的定位，并检查每个列表和反向链接是否确实生效，来构建用户的反向链接与买家发现基础。

**铁律——审批针对每个目标：**

```
No external submission, account creation, paid placement, or review request
happens without explicit approval for that exact destination, copy, assets,
timing, and maximum cost. Approval for research or for another destination
never transfers. Any delta is re-approved before it ships.
```

## 开始之前

**首先检查产品营销背景：**
如果 `.agents/product-marketing.md` 存在（或 `.claude/product-marketing.md`，或者在较旧设置中使用的旧版 `product-marketing-context.md` 文件名），请在提问前阅读。使用其中的背景信息，只询问尚未涵盖或与此任务具体相关的信息。

## 核心理念

目录提交可以增加发现入口、引荐路径和反向链接，但其价值会因产品、目录、列表质量以及当前平台规则而异。将每项收益都视为需要通过列表状态、引荐分析、搜索数据和符合条件的结果进行验证的假设。目录计划应与目标页面及其他分发方式相互补充；它不能保证权威性、引用、流量、排名或潜在客户。

完整的目录清单位于 `references/directory-list.md`。定位变体库位于 `references/positioning-variations.md`。提交跟踪模板位于 `references/submission-tracker-template.csv`。

## 三条操作规则

### 规则 1：先打好基础，再提交
在建议提交之前，验证目录当前的官方要求，并记录来源 URL 和检查日期。链接页面应可由公众访问，内容真实可信，对目录受众有用，并且可衡量。仅准备当前表单要求的素材，使用真实的产品截图和已批准的品牌文件。当产品、司法管辖区或已验证的目录规则要求时，再添加定价、法律页面、视频、结构化数据或其他格式；不要臆造适用于所有情况的前置条件。

### 规则 2：先准备目标页面，再提交目录
为每类受众选择最相关且已验证的目标页面：主页、用例页面、集成页面、对比页面、模板或文档页面。它必须准确兑现列表中的承诺，并包含可衡量的下一步操作。不要强行规定固定的页面数量，也不要仅仅因为不存在无关的内容类型，就阻止一个合适的列表提交。

### 规则 3：根据目录类型调整定位
根据目录中已验证的字段、受众和规则调整描述。可以复用已批准的事实，但如果这样能提升相关性，就应改变侧重点；没有当前证据时，不要声称重复描述会触发搜索或 AI 惩罚。模板请参见 `references/positioning-variations.md`。

| 平台 | 重点突出 | 原因 |
|---|---|---|
| 初创企业目录 | **成果** | 受众是其他创始人。他们关心产品能做什么。 |
| SaaS 目录 | **替代方案定位** | 人们会搜索“[竞品] alternative”——要在那里满足他们的需求。 |
| AI 目录 | **AI 优先架构** | TAAFT/Futurepedia 的受众明确希望寻找 AI 工具。 |
| Agent/MCP 目录 | **Agent/MCP 角度** | 仅在确实具备可用兼容能力时使用。 |
| 无代码目录 | **易用性 + 强大功能** | 受众更看重构建速度，而不是深度。 |
| 开发者目录 | **技术深度** | 开发者受众认可技术实质。 |
| B2B 评测网站 | **ROI + 使用场景** | 买家希望看到成果和案例研究。 |

## 工作流程

### 步骤 1：准备情况评估（阶段 0）

根据当前要求评估所选目录：

1. 产品是否可公开访问（没有密码墙）？
2. 是否有定价页面（即使是“测试期间免费”）？
3. 隐私政策和条款是否已上线？
4. 是否具备所需的已批准 logo、截图和视频素材？
5. 目标页面是否与拟定的列表文案和 CTA 相匹配？
6. 是否已配置推荐和转化衡量？
7. 当前目录政策是否允许该产品、声明集合和分类？
8. 对于评测网站，是否有真实且符合资格的用户，并且提出请求的方式符合政策？
9. 谁拥有创建账号、接受条款和提交内容的权限？

缺少当前平台要求、真实可信的目标页面或提交权限，都会构成该目录的硬性阻碍。遇到阻碍时：停止在该目录上的工作，用一行说明阻碍（“<directory>: 缺少 <requirement>”），列出解决选项（获取该要求、替换为真实可信的目标页面、获得明确的提交权限，或将该目录从此层级中移除），并等待用户选择后再向该目录提交。其他差距属于优先级输入，而不是普遍适用的发布阻碍。

### 步骤 2：选择层级

完整目录见 `references/directory-list.md`。摘要：

| 层级 | 适用时机 | 需要核实的示例候选 |
|---|---|---|
| **旗舰发布** | 在相关发布活动前后 | Product Hunt、BetaList、HN Show HN、Fazier、DevHunt |
| **初创企业/SaaS** | 发布期间及持续进行 | AlternativeTo、SaaSHub、G2、Capterra、F6S |
| **AI 目录** | 如果产品具备有依据支撑的 AI 能力 | TAAFT、Futurepedia、Toolify、Future Tools |
| **Agent/MCP 注册表** | 如果存在可用的兼容集成 | Glama、APITracker、LF MCP Registry |
| **无代码目录** | 如果产品确实服务于该受众 | NoCodeFinder、No Code MBA |
| **集成市场** | 集成发布时 | 集成所有者的官方市场 |
| **个人资料和垂直领域目录** | 受众和分类匹配时 | 相关公司资料页或特定行业目录 |

**筛选规则：** 仅在产品根据平台当前的资格和分类规则确实匹配时提交。

### 步骤 3：准备素材变体

对于每个层级，只有在检查目标平台当前表单后，才能根据
`references/positioning-variations.md` 准备不同的变体：
- **Tagline** 按已验证的字段限制控制长度
- **Short description** 按已验证的字段限制控制长度
- **Long description** 按已验证的字段限制控制长度
- **Category tags** 仅限于已验证的分类体系和产品匹配范围
- **Logo** 资源
- **Screenshots** + 演示视频 URL
- **Founder story**（2–3 句话）

确保事实一致且已获批准。根据每个已验证表单调整长度和侧重点，不得虚构功能、客户、成果或平台支持。

### Step 4: 批量提交

设置跟踪表格（`references/submission-tracker-template.csv`）。
以有证据支持的批次开展工作，每批 **3–5 个目录**。达到上限后，先提交、核验并报告该批次的结果，再开始下一批。
每次提交都受 Iron Law 约束：必须先展示确切的公开文案、资源、账户、目标平台、时间安排和最高成本。

每次提交：
1. 核验当前表单、规则、价格和账户身份。
2. 准备确切的字段值和资源，形成可供审核的草稿。
3. 针对该目标平台获得明确批准（Iron Law）。
4. 仅填写和上传已批准的值。
5. 如价格发生变化、出现追加销售，或渲染后的预览存在实质性差异，须暂停并重新批准该变更。
6. 提交一次，然后记录确认信息。
7. 记录：日期、URL、状态、审核员备注。
8. 上线后，获取规范 listing URL，在渲染后的 HTML 中定位指向目标平台的锚点，并在跟踪表中记录其 `rel` 值、重定向行为、解析后的目标地址以及检查日期。响应标头中不存在 `rel` 并不能证明链接属性不存在——应检查渲染后的页面，并记录所使用的方法。

**报告规则：**只有当跟踪表中的 Live
URL、Rendered Link Attributes 和 Destination Verified 单元格都已填写检查日期时，listing 才能报告为 **live**。其他任何情况都应报告为 **submitted, unverified**。

## Flagship Launch Listing

对于任何有时效性的发布渠道，在制定计划前都要研究该平台。使用其当前的官方帮助文档、提交表单和社区规则；记录相关 URL 和检查日期。不得将凭记忆得出的算法行为、理想发布时间、资源尺寸、hunter 影响或互动阈值作为事实呈现。

### Preparation milestones

- 确认资格、账户状态、审核规则、排期选项、所需资源以及禁止的推广行为。
- 按当前表单的确切限制，起草真实准确的定位文案、已获批准的创始人故事、真实的产品视觉素材，以及可正常使用的目标平台 CTA。
- 预览 listing，并测试产品、注册、分析和支持流程。
- 根据用户拥有或获授权使用的渠道制定沟通计划。
- 指定一名人员负责回应真实的问题和反馈。

### Launch and follow-through

- 只有在用户授权 listing、时间安排和公开文案后，才能发布。
- 遵守当前的征集和外联政策。不得操纵投票、伪造互动，也不得在没有合法关系和授权的情况下向他人发送消息。
- 提供有帮助的回复，记录引荐和符合条件的成果，并总结经验。
- 仅在当前社区规则允许的地方分享复盘。

## 评测平台操作手册

评测目录可以帮助买家评估产品，但资格、激励、审核、徽章、报告和付费套餐规则会发生变化。在推荐活动之前：

1. 阅读所选平台当前的官方评测与激励政策。
2. 记录来源 URL、核查日期、资格规则、截止日期以及最高可验证成本。
3. 找到具有产品第一手使用经验的真实用户；绝不捏造、设置门槛、预先评分或编写评测脚本。
4. 在联系之前，针对收件人列表、措辞、渠道、频率以及任何激励措施获取明确授权。
5. 跟踪请求、已完成的评测、审核状态、推荐结果和投诉。根据实际符合资格的人群规模和用户目标设定指标。

除非已从当前权威来源核实，否则不要声称徽章门槛、报告截止标准、所有权关系、激励许可、套餐价格或预期回复率。较小的客户群是规划约束，而非自动证明某个列表没有价值。

## 落地页策略（反向链接指向的页面）

将每个列表匹配到最有用且真实可用的页面。首页在满足受众需求和承诺时可以适用；当证据支持时，专门页面可能更好。

| 页面类型 | 构建条件 |
|---|---|
| 替代方案页面 (`/alternatives/[competitor]`) | 当前客户或搜索证据显示存在对比意图 |
| 使用场景 / ICP 页面 (`/for/[audience]`, `/use-cases/[use-case]`) | 需求和产品证据证明值得建立专门页面 |
| 模板或资产图库 (`/templates/[slug]`) | 模板具有独立价值，且激活情况可衡量 |
| 自行撰写的类别汇总 | 团队能够研究该类别并披露其方法论 |
| 集成页面 | 集成已上线，且页面说明了设置、功能和限制 |

在任何对比或汇总页面上：核实重要的竞争对手声明，清楚说明每个选项适用的场景，为对比内容标注日期，并在事实变化时进行更正。根据质量产能和已测得的需求确定产出量，而不是借用流量或营收故事；不要承诺排名或 AI 引用。

大规模页面生产属于 `suede-programmatic-seo`；对比页面策略属于 `suede-competitors`。

## GEO（生成式引擎优化）

目录和落地页可能会出现在搜索引擎和问答引擎中。应将可见性视为可观察的结果，而不是权威评分或标记所保证的效果。

页面内引用策略（标题、schema、标注来源日期的事实、对比表格）由 `suede-seo-audit` 负责。有两条规则仍由本技能负责：获得真实的第三方讨论，而不是植入或伪造引用；并确保经授权的公司资料和实时集成注册表条目与已验证的实体事实保持一致。

### 衡量

使用已获授权、当前可调用的工具或手动检查来抽样相关查询。记录引擎、账户上下文、提示词、区域设置、日期、结果，以及结果是否可复现。在推荐任何追踪产品及其成本之前，先进行核实。

## 社区与持续分发

大多数目录提交是阶段性的；社区参与则是持续进行的。
在汇总漏斗结论之前，应将二者作为独立来源分别衡量。

交叉发布和社区链接仍属于反向链接：仅在社区当前规则允许的地方发布，在平台支持时使用规范 URL，并使用与目录列表相同的 Step 4.8 检查来验证渲染后的链接。

渠道选择、频率和帖子格式属于
`suede-community-marketing`、`suede-social` 和 `suede-content-strategy`。

## 不要做什么

1. **未经尽职调查和明确批准，不要购买批量提交套餐。** 核实确切的目标站点、编辑标准、数据处理、权利、最高成本和退款条款。
2. **不要提交到低质量或具有欺骗性的目录。** 评估受众匹配度、审核机制、真实流量证据、现有列表、出站链接行为和声誉，而不是依赖单一的权威评分。
3. **不要将目录视为整个 GTM。** 将其与内容、社区、评论、合作伙伴关系及其他已衡量的渠道进行比较。
4. **没有证据时，不要频繁调整列表。** 根据产品变更、平台通知和观察到的列表问题设定审查频率。
5. **不要过度关注发布当天的峰值。** 飞轮是模板 + 替代方案 + 评论 + 持续内容，而不是 PH 的某一天。

## 特定任务问题

1. **你要发布什么？**（类别会改变层级组合——AI、传统 SaaS、无代码工具或开发者工具。）
2. **发布日是什么时候？**（根据已验证的平台要求倒推安排。）
3. **你是否已构建目标页面？**（替代方案、使用场景、模板——如果没有，先构建。）
4. **正在考虑哪个旗舰平台，其当前规则要求什么？**
5. **有多少符合条件的用户可以收到符合政策的评论请求？**
6. **你是否拥有已上线并经过测试的 MCP 或代理能力？**（如果有，请验证兼容的注册表。）
7. **现有集成？**（如果有，请验证每个所有者的市场资格。）
8. **可以联系哪些自有受众，且用户是否已授权外联？**
9. **当前 DR 和引荐域名数量是多少？**（用于衡量累积效应的基线。）

## 输出格式

当用户要求提供目录计划时，返回：

1. **就绪情况评估** — 缺少哪些 Phase 0 项目，哪些会阻止提交
2. **层级选择** — 适用哪些层级、跳过哪些层级及原因
3. **提交顺序** — 映射至当前要求、由证据支持的批次
4. **目标页面列表** — 如缺失，应优先构建什么
5. **定位变体** — 各层级的实际文案（来自 `references/positioning-variations.md`）
6. **旗舰列表时间线** — 从当前规则映射至日历日期
7. **符合政策的评论计划** — 符合条件的受众、授权、文案、频率
8. **每周衡量计划** — 基线和经用户批准的目标
9. **跟踪器** — 链接至或包含来自 `references/submission-tracker-template.csv` 的 CSV

确保计划具有可执行性。每一项都应当是用户今天就能完成的事情。

## 边界

- 未经当前检查，不得声称某个目录具有 dofollow 属性、已被索引、具有高权威性或能够带来潜在客户。
- 未经明确授权，不得提交目录信息、创建账户、发布文案、购买展示位或请求评价。
- 不得捏造流量、排名、评价或引用结果；应标注估算值并记录证据日期。
- 在缺少必要产品背景信息时，不得决定定位或对外产品声明。

## 路由

- 对于更广泛的发布流程，使用 `suede-launch-packaging`。
- 对于目标页面，使用 `suede-programmatic-seo`；对于搜索或引用检查，使用 `suede-seo-audit`。
- 对于比较页面策略，使用 `suede-competitors`；对于编辑支持，使用 `suede-content-strategy`。
- 对于交互式目标资产，使用 `suede-free-tools`；对于社区和社交分发，使用 `suede-community-marketing`、`suede-social` 或 `suede-content-strategy`。
- 当旗舰发布也值得争取媒体报道时，使用 `suede-public-relations`。
- 从上述技能转回 `suede-directory-submissions`，以处理目录选择、目录信息定位和反向链接验证。
