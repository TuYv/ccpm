name: request-refactor-plan
description: Create a detailed refactor plan with tiny commits via user interview, then file it as a GitHub issue. Use when user wants to plan a refactor, create a refactoring RFC, or break a refactor into safe incremental steps.
---
请完成以下步骤。跳过你认为不必要的步骤。

1. 请用户详细描述他们想要解决的问题，并尽可能提供潜在的解决思路。

2. 探索代码仓库，以验证他们的说法并了解代码库的当前状态。

3. 询问他们是否考虑过其他方案，并向他们介绍其他可选方案。

4. 就实现方案采访用户。务必极其细致、全面。

5. 明确实现的确切范围。确定你计划更改的内容以及不计划更改的内容。

6. 检查代码库，确认该部分代码是否有测试覆盖。如果测试覆盖不足，请询问用户的测试计划。

7. 将实现拆分为一系列微小提交。请牢记 Martin Fowler 的建议：“让每一个重构步骤都尽可能小，这样你就始终可以看到程序处于正常工作状态。”

8. 使用以下议题描述模板创建一个 GitHub 议题，其中包含重构计划：

<refactor-plan-template>

## 问题陈述

从开发者的角度描述其面临的问题。

## 解决方案

从开发者的角度描述问题的解决方案。

## 提交

一份详尽的实现计划。使用通俗的英语编写该计划，并将实现拆分为尽可能小的提交。每个提交都应使代码库保持可工作状态。

## 决策文档

列出已做出的实现决策。其中可以包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 开发者提供的技术说明
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段。它们可能很快就会过时。

## 测试决策

列出已做出的测试决策。包括：

- 对良好测试的描述（只测试外部行为，不测试实现细节）
- 将要测试的模块
- 测试的现有范例（即代码库中类似类型的测试）

## 范围之外

描述此次重构范围之外的事项。

## 补充说明（可选）

有关此次重构的任何补充说明。

</refactor-plan-template>
