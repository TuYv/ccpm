# AI-Loop 技能

## 概述

`ai-loop` 技能为智能体工作流构建了一个有边界的开发循环。它将流程划分为明确的规划（Spec）、实现（Build）和验证（Review）阶段，帮助智能体构建并修正限定范围的代码变更，同时让需求、风险关卡和停止条件保持明确。

## 何时使用此技能

- 当你需要从头构建某个功能或对其进行大幅修改，并希望智能体在一个边界清晰的工作流内处理整个生命周期（规格说明、实现和验证）时使用。
- 当处理具有明确定义的范围和约束的独立组件、模块或功能时使用。
- 当用户要求进行一轮完整的开发，但工作仍具有明确的成功标准、合理的验证路径，且不存在未解决的安全或产品决策时使用。

## 工作原理

此技能执行一个由 Spec、Build 和 Review 三个阶段组成的受控开发循环。被调用时，智能体会依次经历这些阶段，直到限定范围的需求通过验证、达到停止条件，或需要人工批准为止。

在开始之前，请先定义：

- build-review 迭代的最大次数。
- 能够作为证据的验证命令或人工检查。
- 需要明确批准的操作，例如破坏性命令、生产环境变更、外部服务写入，或大范围的架构调整。

### 阶段 1：Spec（规划）

1. 通过访谈了解用户想要构建的功能或应用。每次只提出一个有针对性的问题，直到你完全理解目标、必备需求、约束条件，以及“完成”的标准。
2. **此时尚不要开始构建。**
3. 当你掌握了足够的信息后，编写一份清晰详细的规格说明，并保存到 `specs/<feature-name>.md`。
4. 规格说明必须包含：
   - 目标
   - 具体需求
   - 需处理的边界情况
   - 一个具体的“完成”定义，他人可据此对照检查构建结果
   - 迭代预算、验证命令和批准关卡。

### 阶段 2：Build（实现）

1. 阅读你刚在 `specs/<feature-name>.md` 中创建的规格说明。
2. 严格按照其描述进行构建。
3. **不要添加功能**，不要重构无关代码，也不要虚构规格说明中不存在的需求。
4. 严格专注于实现规格说明。列出你已覆盖的规格需求，以便评审步骤进行核对。

### 阶段 3：Review（验证）

1. 将你的实现与 `specs/<feature-name>.md` 进行对比。
2. 逐条核对每项需求，验证其是否得到满足。列出每一处差距、缺陷或缺失部分，并指明每一项所违反的具体规格条目。
3. 如果有任何未通过的项目且迭代预算尚未耗尽，写出所需的具体修复方案，并**循环回到阶段 2（Build）**来解决它们。
4. 当下一步修复会更改规格说明、超出迭代预算、需要高风险操作，或依赖规格说明中未记录的产品决策时，应停止并请求人工输入。
5. 只有当规格说明中的每项需求都完全满足，且声明的验证证据已通过时，才让构建通过并结束技能执行。

## 示例

### 示例 1：创建基础统计工具

**用户：**
> 我想添加一个用于计算数字数组基础统计量（平均值、中位数、众数）的工具。

**智能体（阶段 1 - Spec）：**
> 我可以帮忙。首先，这个统计计算器应该用哪种编程语言实现？另外，空数组或无效输入应如何处理？

**用户：**
> JavaScript。如果数组为空，返回 null。如果存在非数字，则忽略它们。

**智能体（阶段 1 - Spec）：**
> 谢谢。我已创建规格说明文件 `specs/stats-calculator.md`，其中包含我们讨论的需求。现在，我将开始实现它。

**智能体（阶段 2 - Build）：**
> *（创建 `stats_calculator.js`，并严格按照规格说明实现 `mean`、`median` 和 `mode`）*
> 我已经完成了计算器的实现。现在我将验证该实现。

**智能体（阶段 3 - Review）：**
> 正在对照 `specs/stats-calculator.md` 检查实现：
> - 需求：平均值计算 -> PASS
> - 需求：中位数计算 -> PASS
> - 需求：众数计算 -> PASS
> - 需求：空数组返回 null -> PASS
> - 需求：忽略非数字 -> FAIL（我注意到 `mode` 没有过滤掉非数字）。
>
> 我现在将循环回到阶段 2 来修复 `mode` 函数。

**智能体（阶段 2 - Build 循环返回）：**
> *（修复 `mode` 以过滤掉非数字）*
> 我已经更新了实现。让我们重新验证。

**智能体（阶段 3 - Review）：**
> - 需求：mode 过滤非数字 -> PASS
>
> 所有需求均已通过！统计计算器已完成并通过验证。

## 最佳实践

- ✅ 务必一次只提出一个澄清问题，以免在规划阶段让用户应接不暇。
- ✅ 务必在编写任何代码之前，将边界情况明确记录在 `specs/<feature-name>.md` 中。
- ✅ 务必在构建阶段严格遵守已获批准的规格说明。
- ✅ 务必为循环设置较小的迭代预算上限，并在预算耗尽时准确报告剩余工作。
- ✅ 务必在执行破坏性、生产环境、涉及凭据或对外可见的操作之前暂停，等待明确批准。
- ❌ 不要实现额外的功能或执行规格说明之外的无关重构。
- ❌ 不要跳过评审阶段，也不要在未验证每一项需求的情况下就让其通过。
- ❌ 在没有新证据或改变方法的情况下，不要反复重试同一个失败的修复。

## 局限性

- 此技能要求在 Spec 阶段提供关于该功能的充分上下文。
- 它最适合具有明确边界的独立功能或任务，而非开放式的架构重构。
- 评审阶段依赖智能体对照生成的规格说明进行自我评估；对于关键系统，仍建议进行人工评审。
- 它不能替代人工对安全敏感、破坏性、生产环境、合规或对外可见变更的批准。
- 如果需求相互冲突、测试无法运行，或验证依赖不可用的凭据或系统，它应当停止而非继续。

## 安全注意事项

- 在运行或测试 Build 阶段生成的代码时要保持谨慎。始终在安全的沙箱环境中运行测试。
- 避免在未验证安全性的情况下执行用户直接提供的任意 shell 命令。
- 确保没有将硬编码的机密信息、密钥或凭据添加到代码或规格说明中。
- 将生产部署、数据迁移、支付流程、凭据变更和外部写操作视为需要批准把关的工作。

## 常见陷阱

- **问题：** 智能体试图一次性构建一个庞大的系统，导致规格说明过于复杂、实现不完整。
  **解决方案：** 将 `ai-loop` 的范围限制在小型、模块化的功能上。把更大的系统拆分为多个独立的循环。
- **问题：** 规格说明含糊不清，导致构建阶段依赖假设。
  **解决方案：** 在规划阶段多花些时间提出有针对性的问题，把需求确定下来。
