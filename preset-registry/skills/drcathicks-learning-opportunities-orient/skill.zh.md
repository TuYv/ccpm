# 创建入门指南

## 目的

在 `learning-opportunities` 技能的 `resources/` 目录中生成仓库专属的 `orientation.md` 文件。使用 `orient` 参数调用该技能时，它会使用此文件为代码库的新成员开展结构化学习练习。

---

## 第 1 步：确定 orientation.md 的写入位置

无论 `learning-opportunities` 技能安装在何处，始终写入**项目级别**的位置。

在 Codex 中运行时，写入：

```
.codex/skills/learning-opportunities/resources/orientation.md
```

在 Claude Code 中运行时，写入：

```
.claude/skills/learning-opportunities/resources/orientation.md
```

这两个路径均相对于当前工作目录。

如果目标目录不存在，请创建该目录。如果目录已存在，则不要改动该目录及其中的任何文件——只写入 `orientation.md`。

这样可以使入门指南文件与其所描述的仓库位于同一处——它们可以提交到版本控制系统、与团队成员共享，并且绝不会在不同项目之间发生冲突。

---

## 参数检查

调用时传入的参数为：`$ARGUMENTS`

如果参数是 `showboat`，请跳转到下方的 **Showboat 路径**部分。

否则，继续执行第 2–5 步（默认路径）。

---

## 第 2 步：检测仓库的主要语言

检查项目根目录中是否存在以下清单文件或配置文件，并记录所有存在的文件。一个仓库可能使用多种语言。

| 语言       | 标志文件                                                   |
|:-----------|:----------------------------------------------------------|
| Python     | `pyproject.toml`、`setup.py`、`setup.cfg`、`Pipfile`、`requirements.txt` |
| JavaScript | `package.json`（无 `tsconfig.json`）                      |
| TypeScript | `package.json` + `tsconfig.json`                          |
| R          | `DESCRIPTION`、`NAMESPACE`、任意 `*.Rproj`                |
| Ruby       | `Gemfile`、任意 `*.gemspec`                               |
| Go         | `go.mod`                                                  |
| Rust       | `Cargo.toml`                                              |
| C/C++      | `CMakeLists.txt`、`configure.ac`、根目录下的 `Makefile`   |
| Java/Kotlin| `pom.xml`、`build.gradle`、`build.gradle.kts`             |
| C#         | 任意 `*.csproj` 或 `*.sln`                                |

记录检测到的所有语言。对于检测到的每种语言，完整阅读其主要清单文件——其中包含声明的用途、依赖项、入口点以及对入门至关重要的脚本/命令。

---

## 第 3 步：探索仓库

按照以下顺序进行探索，该顺序源自对专家级程序理解策略的研究。专家会进行**有策略且有选择性的**阅读，而不是穷尽式阅读。目标是建立关于结构的心智模型，而不是逐行理解。

### 3a. README 和顶层文档
阅读项目根目录中的 `README.md`、`README.rst` 或 `README`。同时检查是否存在 `docs/` 目录——如果存在，请阅读其索引或目录。这有助于了解项目声明的用途和目标受众。

*来源：Spinellis，《Code Reading: The Open Source Perspective》（2003）——在阅读任何应用程序代码之前，先从构建系统和 README 入手。*

### 3b. 目录树
运行 `find . -maxdepth 3 -not -path '*/.git/*' -not -path '*/node_modules/*' -not -path '*/__pycache__/*' -not -path '*/.venv/*'` 以获取顶层结构。将目录树视为架构层面的目录——命名约定（`src/`、`lib/`、`tests/`、`cmd/`、`pkg/`）在阅读任何代码之前就能揭示其用途。

*来源：Spinellis（2003）——“将目录树视为目录”。*

### 3c. 入口点
根据检测到的语言，识别并阅读主要入口点：

- **Python**：`__main__.py`、`cli.py`、`main.py`，或者 `pyproject.toml` 的 `[tool.poetry.scripts]` / `[project.scripts]` 部分
- **JavaScript/TypeScript**：`package.json` 中的 `main` 字段、`index.js`、`src/index.ts`
- **Go**：`cmd/*/main.go` 中的文件或根目录下的 `main.go`
- **Rust**：`src/main.rs` 或 `src/lib.rs`
- **R**：`R/` 目录、`DESCRIPTION` 文件的 `Imports`
- **Ruby**：`bin/` 中的文件、`lib/<gem-name>.rb`
- **C/C++**：`main.c`、`main.cpp`，或 `CMakeLists.txt` 中的主要目标

*来源：Hermans，《The Programmer's Brain》（2021，Manning）——沿着入口点和调用图逐层深入。*

### 3d. 测试文件
阅读 2–3 个测试文件，优先阅读集成测试或端到端测试，而不是单元测试。测试是可执行的规范——阅读测试名称和断言，是理解模块预期用途的最快方法之一。

*来源：Storey 等人，《How Software Developers Use Tools, Cognitive Strategies, and Representations to Navigate Code》（IEEE TSE，2006）——将测试套件用作规范。*

### 3e. 核心模块
根据目前了解到的信息，识别 5–8 个最重要的源文件。阅读其顶层结构（类/函数名称、导入、文档字符串），不必完整阅读每一处实现。

### 3f. 最近的 git 历史记录（如果 git 可用）
运行 `git log --oneline -20` 查看最近的活动。运行 `git log --format="%f" | sort | uniq -c | sort -rn | head -10` 以识别编辑次数最多的文件。变更频繁的文件通常是系统的核心。

*来源：Spolsky 的实践者文章——“找到最大、编辑次数最多的文件；阅读 git 历史记录，以理解代码为何会成为现在这样。”*

## 第 4 步：综合分析并编写 orientation.md

将文件写入第 1 步中确定的路径。严格使用以下结构：

```markdown
# Repo Orientation: [repo name]

> Generated by orient. Re-run to update.

## One-line purpose
[Single sentence: what this repo does and why it exists. Written for someone with no prior context.]

## Primary language(s)
[List languages detected, with the dominant one first.]

## Pipeline / workflow stages
[Ordered list of the main stages data or requests flow through. One line each. If the repo has no pipeline, describe the main modules and their relationships instead.]

## Key files
[6–10 entries in this format:]
- `path/to/file.py` — [what it does] | [why a new developer should read it]

## Core concepts
[3–5 domain or architectural concepts essential to working in this codebase. For each:]
**[Concept name]**: [Plain-English definition. Where in the code it lives.]

## Common gotchas
[2–3 things that commonly trip up new developers. Be specific — reference actual file paths or function names.]

## Suggested exercise sequence
[EXACTLY 2 exercises. These are orientation exercises — their job is to build a high-level mental model of the repo, not to drill implementation details.

Orientation exercises follow this pattern: direct the learner to read one specific, short artifact first, then ask them to synthesize or explain what they just read. Never ask them to predict something they couldn't know without reading — the goal is comprehension and synthesis, not prior knowledge.

Good orientation exercises:
- "Open README.md and read the Features section. Then close it and explain to a non-developer what this tool produces and why someone would use it."
- "Open `models.py`. Find the dataclass that represents everything the pipeline produces for one audio file. What fields does it have, and what does that tell you about the pipeline's stages?"
- "Open `config/default.yaml` and skim it. What are the two or three settings you'd most likely need to change for a new project, and why?"

Bad orientation exercises (save these for later sessions):
- "Without opening any files, predict the pipeline stages" — learner has no basis for this
- Predicting specific function outputs, column names, or algorithmic behavior
- Tracing through individual method implementations
- Debugging specific logic (e.g. merge suffix behavior, metadata propagation)

For each exercise, specify: the exact file to open, what to read, and what synthesis question to answer after reading.]

## Sources consulted
[List the files and paths you actually read while generating this file.]
```

每个部分都应简洁。这是一个教学脚手架，而非文档。清晰度优先于完整性。

## Showboat 路径

当参数为 `showboat` 时，此路径将替代步骤 2–5。它会在步骤 1 中确定的同一位置生成 `orientation.md`，但会使用 `showboat` CLI 工具（通过 `uvx`）构建详细、线性的代码导览。

### Showboat 第 1 步：检查 uv

运行 `command -v uv` 以验证是否已安装 `uv`。

如果未找到 `uv`，请告知用户：

> showboat 模式需要 `uv`，但在你的 PATH 中未找到它。
> 请从以下地址安装：https://docs.astral.sh/uv/getting-started/installation/

然后停止——不要继续执行后续步骤。

### Showboat 第 2 步：阅读仓库并规划文档

阅读仓库以了解其结构、用途和关键代码路径。然后规划一份线性的导览文档，其中包含：

- 标题和目录
- 按阅读顺序以叙事方式解释代码库的解说章节
- 包含解说中所引用实际代码片段的代码清单附录
- 建议的练习顺序（与步骤 4 的练习要求采用相同标准——恰好包含 2 个入门练习）

在开始编写任何内容之前，**预先规划好**所有章节标题、代码片段和连续的清单编号。每个清单都应获得一个连续编号（Listing 1、Listing 2 等）和一段简短描述。

### Showboat 第 3 步：了解 showboat 工具

运行 `uvx showboat --help` 以了解可用命令及其语法。

### Showboat 第 4 步：使用 showboat 命令构建 orientation.md

使用 showboat CLI 构建文件。输出路径与步骤 1 中的 `orientation.md` 相同。按以下顺序执行命令：

#### 4a. 初始化文档

```
uvx showboat init <path-to-orientation.md> "<Title>"
```

然后通过 `uvx showboat note` 添加目录。

#### 4b. 编写所有解说章节

使用 `uvx showboat note` 添加每个解说章节。注释内容应遵循以下规则：

- 注释中**不得使用围栏代码块**——应改用行内反引号代码（`` `like_this` ``）
- 使用行内链接引用代码清单：`*([Listing N: description](#listing-N))*`
- 采用叙事方式编写——解释代码为何以这种方式组织，而不只是说明它做了什么

#### 4c. 编写代码清单附录

对于 Showboat 第 2 步中规划的每个清单：

1. 添加锚点注释：使用 `uvx showboat note` 添加类似 `### Listing N: description` 的标题和 HTML 锚点 `<a id="listing-N"></a>`
2. 通过 `uvx showboat exec` 添加代码，以捕获实际文件内容（例如，使用 `cat` 或 `sed` 提取相关行）

#### 4d. 追加建议的练习顺序

通过 `uvx showboat note` 添加最后一个章节，其中恰好包含 2 个导览练习。这些练习遵循与默认路径的步骤 4 相同的标准：

- 首先引导学习者阅读一个具体且简短的材料
- 然后要求他们综合归纳或解释刚刚阅读的内容
- 绝不要求他们预测不阅读就无法知道的内容
- 明确指定：要打开的确切文件、要阅读的内容，以及要回答的综合归纳问题

#### 4e. 验证文档

运行：

```
uvx showboat verify <path-to-orientation.md>
```

在继续之前，修复报告的所有问题。

### Showboat 步骤 5：向用户确认

告知用户：

- 文件写入的位置
- 该文件是使用 showboat 模式（线性代码演练）生成的
- 使用方式：`/learning-opportunities orient`
- 他们可以随时重新运行 `/orient showboat` 来重新生成该文件
