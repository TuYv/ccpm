# 原型

原型是**用于回答某个问题、用完即弃的代码**。问题决定其形态。

## 选择分支

确定要回答的是哪个问题——依据用户的提示、周边代码，或者在用户在线时使用 AskUserQuestion 工具询问用户：

- **“这个逻辑／状态模型感觉正确吗？”** → [LOGIC.md](LOGIC.md)。构建一个微型交互式终端应用，推动状态机经历那些难以在纸面上推演的情况。
- **“这个应该是什么样子？”** → [UI.md](UI.md)。在单个路由上生成若干种截然不同的 UI 变体，并可通过 URL 查询参数和底部悬浮栏进行切换。

这两个分支会生成截然不同的产物——选错分支会让整个原型白费。如果问题确实含糊不清且无法联系到用户，则默认选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 关键：问题决定形态

在构建之前先确定要回答的问题——“这个逻辑／状态模型感觉正确吗？”应采用 LOGIC.md，“这个应该是什么样子？”应采用 UI.md；选错分支会让整个原型白费。从第一天起就将其视为用完即弃的代码：不写测试、不做润色、不做持久化——保留答案，删除代码。

## 同时适用于两者的规则

1. **从第一天起就用完即弃，并明确标注这一点。** 将原型代码放在靠近其实际使用位置的地方（紧邻它所要验证的模块或页面），以便清楚理解上下文——但命名时要让普通读者一眼看出它是原型，而不是生产代码。对于用完即弃的 UI 路由，应遵循项目现有的路由约定；不要自行创建新的顶层结构。
2. **一条命令即可运行。** 使用项目现有任务运行器支持的方式——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认不做持久化。** 状态保存在内存中。持久化是原型要*验证*的内容，而不是原型应依赖的内容。如果问题明确涉及数据库，则使用临时数据库或本地文件，并采用清晰的“PROTOTYPE — 清除我”名称。
4. **跳过润色。** 不写测试；除确保原型*可运行*所必需的错误处理外，不做其他错误处理；不做抽象。重点是快速获得认知。
5. **展示状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染所有相关状态，让用户能够看到发生了什么变化。
6. **完成后将其留档。** 将所有经过验证的决策整合到真实代码中，然后把原型本身作为**一手资料**留档：将其提交到一个用完即弃的分支中，不进入 main，并在实现 issue 中留下指向该分支的上下文链接。答案也要留档——包括结论及其解决的问题——记录在 issue 或某次 commit 中。main 分支只保留经过验证的决策。
