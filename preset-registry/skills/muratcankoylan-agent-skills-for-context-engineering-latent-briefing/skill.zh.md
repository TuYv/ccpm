# 潜在简报与 KV 缓存内存共享

分层多智能体系统经常为相同的上下文支付两次成本。编排器会积累一条很长的推理轨迹，但每个工作智能体通常只会收到范围有限的文本交接内容，例如子任务提示词加上原始文档片段。传递完整轨迹可以解决信息覆盖问题，但会推高每次调用工作智能体时的 token 成本。摘要会引入延迟和信息损失。检索有助于访问文档，但无法保留编排器不断演化的推理状态。

潜在简报通过在**表征层面**而非文本层面共享内存来解决这一问题。其核心思想是在工作智能体模型的 KV 缓存中压缩编排器轨迹，保留与**当前工作智能体任务**最相关的位置。该方法以**注意力匹配（AM）** KV 缓存压缩为基础，并通过任务引导查询、跨注意力头共享的 token 掩码以及稳健的阈值处理，使其适用于推理阶段的多智能体交接。

## 何时启用

在以下情况下启用此技能：

- 设计编排器-工作智能体或监督者-专家系统，其中工作智能体需要访问编排器的先前状态，而无须以文本形式重放完整轨迹
- 评估使用 LLM 摘要或 RAG 进行跨智能体状态传递的替代方案
- 将 **KV 缓存压缩**作为一等推理原语来实现或研究，而不仅仅是对相同提示词进行前缀缓存
- 调试递归式、分层式或大量使用工具的智能体图中的 token 激增问题
- 解读同时报告工作智能体 token 节省量、总 token 节省量、压缩开销和准确率的基准测试

对于由其他技能负责的相邻工作，请勿启用此技能：
- 无法访问内部 KV 张量、仅使用 API 的技术栈：使用 `context-compression`、`memory-systems` 或 `multi-agent-patterns`。
- 常规持久化内存、实体跟踪或图检索：`memory-systems`。
- 不涉及表征层状态共享的通用多智能体拓扑：`multi-agent-patterns`。
- 不转换 KV 状态的前缀缓存、掩码或预算策略：`context-optimization`。

## 核心概念

**token 激增模式。** 在递归式或 REPL 风格的系统中，编排器会反复调用工作智能体来检查证据、验证假设或回答子问题。编排器的轨迹会随着阶段性结论、无效探索、工具输出和先前工作智能体的响应而不断增长。如果每次调用工作智能体时都完整传递该轨迹，成本会迅速叠加。

**表征层共享。** 系统并非将轨迹摘要为自然语言，而是直接操作工作智能体模型的 **KV 缓存**。它会保留工作智能体针对当前任务会关注的位置，并丢弃其余位置。这比普通的前缀缓存更具针对性：前缀缓存会复用相同的前缀，而潜在简报还会在复用的轨迹内部执行**以任务为条件的选择性保留**。

**以注意力匹配作为压缩引擎。** AM 旨在寻找一个更小的缓存，使其注意力输出能够近似完整缓存的注意力输出。潜在简报通过改变评分信号和批处理策略，使 AM 适用于多智能体推理：

1. 使用从当前工作器提示词派生的**任务引导查询向量**。
2. 将分数聚合为一个**共享全局掩码**，而不是为每个注意力头分别选择独立的子集。
3. 使用诸如 `median + tau * MAD` 的稳健阈值，而不是为每个注意力头采用固定的 top-k。

**参考结果概况。**公开说明报告称，在长文档问答工作负载中，工作器 token 数量大幅减少、总 token 数量显著节省，并且压缩开销仅为个位数秒（claim-latent-briefing-public-results）。应将这些数字视为针对特定工作负载的证据，而非普遍保证。

## 详细主题

### 为什么纯文本缓解措施效果有限

| 方法 | 主要缺点 |
|----------|------------------|
| LLM 摘要 | 延迟高、抽象过程有损，而且无法保证摘要保留了下一个子任务所需的信息 |
| 检索 / RAG | 依赖分块和嵌入；可能遗漏跨块或跨步骤的依赖关系 |
| 传递完整轨迹 | 成本随每次工作器调用而增长，并且无关上下文可能降低工作器质量 |

当瓶颈并非文档检索本身，而是**如何高效且精确地将编排器状态传递给工作器**时，Latent Briefing 非常有用。

### 递归式编排器-工作器架构

**Recursive Language Models** 等框架将长上下文视为一种环境，并在其上进行递归：编排器分解工作并将任务委派给工作器。Latent Briefing 填补了这样一个空白：编排器已经构建了应当为工作器提供指导的任务特定状态，但将该状态重新序列化为文本的成本过高或噪声过多。

在理想设置下，工作器会为编排器轨迹维护持久化的 KV 状态。新的轨迹 token 会扩展该状态，随后在为当前子任务生成内容之前执行压缩。

### 三项推理时修改

1. **任务引导查询向量。**使用当前工作器任务提示词中的查询，而不是从上下文中提取的通用样本。通过工作器模型对轨迹和当前任务执行前向传播，然后根据任务对各个轨迹位置的关注强度为其评分。

2. **共享 token 选择。**跨层和注意力头聚合分数，为每个位置生成一个分数。使用一个共享掩码可实现批处理操作，并避免数百个互不兼容的逐注意力头求解过程。

3. **MAD 阈值处理。**保留高于诸如 `median + tau * MAD` 这类稳健异常值阈值的位置。`tau` 越高，压缩越激进。最优设置取决于任务类型、轨迹质量和文档长度。

### 基础设施前提条件

只有当系统对**工作器推理运行时拥有足够深入的控制权**，能够检查或转换 KV 状态时，Latent Briefing 才切实可行。对于无法访问内部 KV 张量、仅使用 API 的技术栈而言，它并不是一种理想的默认方案。它还假设编排器轨迹能够在工作器的模型空间中表示。如果编排器和工作器在 tokenizer、架构或注意力布局方面存在实质性差异，则直接共享表示可能不可行。

### 决策框架

选择与瓶颈相匹配的机制：

| 需求 | 优先选择 | 原因 |
|------|--------|-----|
| 逻辑变化极少的稳定重复前缀 | 前缀缓存 | 成本最低的优化；无信息损失 |
| 人类可读且可审计的跨步骤状态 | 结构化笔记或摘要 | 易于检查和存储 |
| 在大型外部语料库中进行稀疏查找 | 检索 / RAG | 高效查找文档 |
| 工作器需要编排器状态中与任务相关的部分，并且能够访问运行时 | 潜在简报 | 无需重放全部文本即可传递相关的潜在状态 |

潜在简报并不能普遍取代摘要或检索。它是一种专门的优化，适用于已经运行可控编排器—工作器技术栈的系统。

### 阈值区间

已报告的长文档问答结果表明：

- **较长的文档：**较轻度的压缩可以在节省 token 的同时，保留更广泛的证据覆盖范围。
- **较难的问题：**当编排器轨迹包含推测性或低价值分支时，更激进的压缩可能会有所帮助。
- **较短、较简单的上下文：**适度压缩可以去除冗余，同时不丢失所需证据。

这些是调优假设，而不是可移植的定律。请在目标工作负载上重新测量。

## 实践指导

- **首先定义共享内存边界。** 明确决定哪些内容进入轨迹缓存：先前的工作器回复、工具输出、思维链，还是仅选定的产物。压缩质量取决于最初允许哪些内容进入缓存。
- **基于验证数据而非个别经验进行调优。** 同时跟踪任务准确率、工作器 token 数、总 token 数、保留率和压缩开销。
- **测量端到端延迟。** 只有当压缩与生成的总耗时优于在相同质量目标下最佳的文本层替代方案时，压缩才有收益。
- **使用强基线。** 应与前缀缓存、结构化笔记、检索和选择性文本交接进行比较，而不只是与“发送所有内容”比较。
- **预期编排器存在方差。** 如果分解策略在每次运行中都会变化，应在足够多的试验上取平均值，以区分压缩效果与编排器噪声。

## 示例

**场景：编排器轨迹随着工作器调用而增长**

```text
Call 1: trajectory T1 -> worker answers subquestion A
Call 2: trajectory T2 = T1 + new reasoning + reply A
        compact KV(T2) using the task prompt for B
        worker answers subquestion B
```

B 的任务提示决定 `T2` 的哪些部分会保留到压缩后的工作器状态中。

**反例：仅支持 API 的工作器**

如果工作器运行在不公开 KV 张量的托管文本生成 API 后面，则无法直接实现潜在简报。请改用来自 `context-compression` 的结构化文本交接，或从 `memory-systems` 中检索状态。

## 指南

1. 当主要浪费来自向工作器重放编排器状态，而不是检索源文档时，优先使用潜在简报。
2. 当可审计性、可移植性或闭源模型 API 比 token 效率更重要时，优先使用纯文本交接。
3. 将压缩与**评估**协同设计。轻微的质量下降就可能抵消大量的 token 节省。
4. 将压缩激进程度公开为一个受控参数，而不是隐藏常量。

## 注意事项

1. **基础设施访问权限是第一道门槛。** 如果运行时无法检查并重写工作器的 KV 状态，那么 Latent Briefing 就只是一个研究构想，而不是一种可部署的技术。
2. **共享模型空间很重要。** KV 压缩是在特定模型的注意力空间中定义的。不要假设潜在状态交接能够在不相关的模型家族之间顺畅工作。
3. **阈值取决于工作负载。** 一个全局 `tau` 很少能同时适用于长上下文与短上下文以及简单任务与困难任务。当压缩变得过于激进时，可能会出现准确率断崖式下降。
4. **基准测试范围有限。** 公开结果主要聚焦于长文档问答。代码生成、数学和多文档综合任务的表现可能不同。
5. **编排器的差异可能掩盖实际信号。** 随机编排器可能会大幅改变执行轨迹，以至于淹没压缩带来的微小收益或损失。
6. **较弱的基线会夸大表面上的优势。** 在宣称系统级优势之前，应先与强大的文本层替代方案进行比较。

## 集成

- context-optimization - 前缀缓存和观测掩码仍然是默认的首选手段；Latent Briefing 是一种更为专门的优化，适用于兼容的编排器-工作器技术栈。
- multi-agent-patterns - 当多智能体的 token 成本由监督器轨迹重放驱动，而不仅仅来自协调开销时适用。
- context-compression - 当人类可读的状态、可移植性或审计日志很重要时，文本层摘要仍然是更优选择。
- memory-systems - 有助于判断何时应将跨步骤状态保存在外部记忆中，以及何时应保存在工作器的潜在状态中。
- tool-design - 工作器调用形式和任务提示决定了哪些 token 会在压缩期间获得较高分数。
