# 客户流失预防

生产级 SaaS 客户流失降低框架，涵盖取消流程架构、动态挽留优惠映射、退出调查设计、催款序列工程、支付恢复优化、客户赢回活动和流失影响建模。同时处理主动流失（客户决定离开）和被动流失（客户因支付失败而离开）。

## 首先澄清

在设计客户流失预防系统之前，请确认以下信息。如果有任何信息未知或不明确，请询问——不要擅自假设：

- [ ] **主动流失与被动流失的占比**——哪一种占主导（决定应构建取消流程/挽留优惠，还是催款/支付恢复机制）
- [ ] **现有取消流程与即时取消/通过客服取消的情况**——决定是从零构建还是进入优化模式
- [ ] **当前 MRR + ARPU + 计费周期**——用于估算金额影响和挽留优惠预算
- [ ] **支付处理商**——Stripe / Braintree / Paddle / Recurly（决定银行卡更新器和催款重试的实现方式）

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草”，则继续执行，并在交付物顶部列出你的假设。

## 初步评估

### 所需背景信息

| 问题 | 重要性 |
|----------|---------------|
| 当前每月客户流失率是多少？（主动流失与被动流失的占比） | 决定应采用哪种手段 |
| 是否已有取消流程，还是即时取消/通过客服取消？ | 决定采用构建模式还是优化模式 |
| 使用什么支付处理商？（Stripe、Braintree、Paddle） | 影响催款机制的实现 |
| 平均合同价值和计费周期是多少？ | 决定挽留优惠预算的规模 |
| 当前 MRR 是多少？ | 计算降低客户流失所带来的金额影响 |
| SaaS 模式是什么？（自助式还是销售辅助式） | 决定干预类型 |
| 目前是否收集退出原因？ | 决定是否有可用于挽留优惠映射的数据 |

## 客户流失分类

### 主动流失（客户决定离开）

| 类型 | 信号 | 可干预？ |
|------|--------|-------------|
| 价值缺口 | 获得的价值不足以匹配价格 | 是——挽留优惠、功能使用指导 |
| 产品与市场不匹配 | ICP 不正确，产品不适合其用例 | 部分可干预——降级或转型 |
| 转向竞争对手 | 找到了更好的替代方案 | 是——提供针对竞争对手的反向优惠 |
| 预算削减 | 无法再负担费用 | 是——折扣或暂停 |
| 项目完成 | 季节性或基于项目的需求 | 是——提供暂停选项 |
| 体验不佳 | 客服差、缺陷多或感到受挫 | 是——人工干预 |
| 从未激活 | 已注册但从未使用 | 部分可干预——在取消前重新激活 |

### 非自愿流失（支付失败）

| 原因 | 占支付失败的百分比 | 可挽回？ |
|-------|---------------------|-------------|
| 卡片已过期 | 40-50% | 是 -- 卡片更新服务 |
| 余额不足 | 20-30% | 是 -- 智能重试时机 |
| 银行拒付（欺诈标记） | 10-15% | 有时可以 -- 客户必须联系银行 |
| 账户已关闭 | 5-10% | 否 -- 客户必须提供新卡 |
| 网络错误 | 5-10% | 是 -- 自动重试 |

## 取消流程架构

### 五阶段取消流程

```
[Cancel Button] → [Exit Survey] → [Dynamic Save Offer] → [Confirmation] → [Post-Cancel]
```

### 阶段 1：触发取消

- 取消选项应易于找到（设置 > 账户 > 取消）。不要将其隐藏。
- 点击“取消”会启动取消流程 -- 不会立即取消账户
- 同时适用于桌面端和移动端

### 阶段 2：退出问卷（必填，1 个问题）

**问题：**“您取消订阅的主要原因是什么？”

以单选按钮形式展示（不要使用下拉菜单）。最多 8 个选项：

| 原因 | 内部代码 |
|--------|--------------|
| 相对于我获得的价值而言，价格太高 | PRICE |
| 使用频率不够高 | LOW_USAGE |
| 缺少我需要的功能 | MISSING_FEATURE |
| 改用其他产品 | COMPETITOR |
| 我的项目或需求已经结束 | PROJECT_END |
| 使用起来太复杂 | COMPLEXITY |
| 只是进行测试，原本就没打算继续使用 | TESTING |
| 其他（附可选文本字段） | OTHER |

**规则：**
- 必须先完成问卷，才能显示挽留优惠（回答将决定显示哪种优惠）
- 只询问一个问题。不要使用多页面问卷。
- 为“其他”选项提供可选的自由文本字段，也可将该字段作为任意选项的补充说明
- 每月跟踪回答分布，以识别系统性问题

### 阶段 3：动态挽留优惠

**将每个退出原因映射到唯一一个挽留优惠：**

| 退出原因 | 挽留优惠 | 优惠文案 |
|------------|-----------|------------|
| PRICE | 未来 2-3 个月享受 30-50% 折扣 | “我们希望为您提供未来 [N] 个月 [X]% 的折扣” |
| LOW_USAGE | 暂停账户 1-3 个月 | “暂停您的账户，并在需要时再回来” |
| MISSING_FEATURE | 路线图预览 + 变通方案 | “[Feature] 将在 [Q] 推出。以下是目前实现该功能的方法” |
| COMPETITOR | 竞品对比 + 折扣 | “以下是我们与 [competitor] 的对比。另外再享 [X]% 折扣” |
| PROJECT_END | 暂停选项 | “暂停而不是取消 -- 您的数据将得到安全保留” |
| COMPLEXITY | 免费上手指导会议 | “让我们为您完成设置 -- 与我们的团队进行 30 分钟免费会议” |
| TESTING | 不提供优惠 -- 让他们离开 | “感谢您试用我们的产品。随时欢迎您回来。” |
| OTHER | 通用挽留优惠 | “在您离开之前 -- 我们希望有机会弥补。[Contact support]” |

**优惠展示规则：**
- 每个页面只展示一个明确的优惠（不要提供多个选项）
- 将价值量化：使用“未来 3 个月节省 $120”，而不是“获得折扣”
- CTA：“接受优惠”与“继续取消”（两者均须清晰标注）
- 不使用倒计时，不营造虚假的紧迫感
- 不使用让用户产生内疚感的文案

### 阶段 4：确认

如果他们拒绝挽留优惠，或者没有可提供的优惠：

```
┌────────────────────────────────────────┐
│  We're sorry to see you go             │
│                                        │
│  What happens when you cancel:         │
│  - Your data is saved for 90 days     │
│  - Access continues until [date]      │
│  - You can reactivate anytime         │
│                                        │
│  [Yes, Cancel My Account]             │
│  [Wait, I Changed My Mind]            │
│                                        │
│  No pre-checked boxes.                │
│  No confusing language.               │
└────────────────────────────────────────┘
```

### 阶段 5：取消后

| 时间 | 渠道 | 消息 |
|--------|---------|---------|
| 立即 | 电子邮件 | 取消确认 + 数据保留政策 + 重新激活链接 |
| 第 7 天 | 电子邮件 | “我们想念你” + 单个重新激活 CTA + 他们错过的内容 |
| 第 30 天 | 电子邮件 | 产品更新 + 相关改进 + 重新激活优惠 |
| 第 60 天 | 电子邮件 | 提供力度最大的最终挽回优惠（如适用） |

## 退出调查设计

### 数据分析框架

每月跟踪退出调查回复并计算：

| 指标 | 公式 | 行动阈值 |
|--------|---------|-----------------|
| 原因分布 | 每种原因占取消总数的百分比 | 任何原因 > 30% = 系统性问题 |
| 按原因划分的挽留率 | 每种原因的挽留成功数 / 取消尝试数 | 任何原因的挽留率 < 5% = 优惠不合适 |
| 原因趋势 | 环比变化 | 呈上升趋势 = 问题正在恶化 |
| 功能缺口频率 | 已明确具体功能的“缺少功能”计数 | 排名前 3 的缺失功能 = 产品路线图输入 |

### 从退出调查中获取竞争情报

当用户选择“转用其他产品”时：

- 追加询问：“你要转用哪个产品？”（可选，自由文本或下拉列表）
- 跟踪从你这里赢走流失用户最多的 3 个竞争对手
- 将这些数据提供给 competitive-teardown skill，以进行季度分析

## 动态挽留优惠系统

### 优惠经济性

| 优惠类型 | 企业成本 | 挽留率基准 | 何时有利可图 |
|-----------|-----------------|---------------------|----------------|
| 7 折优惠（3 个月） | 3 个月收入的 30% | 15-25% | 如果挽留后的 LTV > 优惠成本 |
| 5 折优惠（2 个月） | 2 个月收入的 50% | 20-30% | 如果留存客户继续使用 6 个月以上 |
| 暂停（1-3 个月） | $0（暂停期间无收入） | 25-40% | 如果暂停后有 50% 以上的用户重新激活 |
| 免费入门指导 | CS 团队时间（约 $50-100） | 10-20% | 如果 ARPU > $100/月 |
| 降级到较低套餐 | 收入减少 | 30-50% | 如果有收入好过没有收入 |
| 解锁功能 | $0（已构建） | 5-15% | 始终有利可图 |

### 挽留优惠决策树

```
User selects exit reason →
├── PRICE →
│   ├── Customer ARPU > median? → Offer 30% discount
│   └── Customer ARPU < median? → Offer downgrade to cheaper plan
├── LOW_USAGE →
│   ├── Last login > 30 days? → Offer pause
│   └── Last login < 30 days? → Offer usage tips + discount
├── MISSING_FEATURE →
│   ├── Feature on roadmap? → Share roadmap + workaround
│   └── Feature not planned? → Offer discount or acknowledge gap
├── COMPETITOR →
│   ├── Known competitor? → Show comparison + retention offer
│   └── Unknown competitor? → General retention offer
├── PROJECT_END →
│   └── Always → Offer pause
├── COMPLEXITY →
│   ├── Enterprise/high-value? → Offer dedicated onboarding session
│   └── SMB/low-value? → Offer guided tutorial link
└── TESTING →
    └── Always → No offer, let go gracefully
```

## 催款序列设计

支付失败导致了总流失量的 20-40%。其中大部分可以通过适当的催款措施挽回。

### 智能重试计划

支付失败后不要立即重试。银行卡通常会在 3-7 天内恢复正常。

| 重试 | 时间 | 选择此时间的原因 |
|-------|--------|-----------------|
| 首次扣款 | 第 0 天 | 正常计费周期 |
| 第 1 次重试 | 第 3 天 | 大多数银行卡问题会在 72 小时内解决 |
| 第 2 次重试 | 第 7 天 | 与发薪周期保持一致 |
| 第 3 次重试 | 第 12 天 | 第二个发薪周期 |
| 第 4 次重试 | 第 18 天 | 采取服务措施前的最后一次尝试 |
| 服务措施 | 第 21 天 | 降级或取消 |

### 银行卡更新服务

启用银行卡自动更新功能，防止因银行卡过期造成客户流失：

| 支付处理商 | 服务 | 如何启用 |
|-----------|---------|---------------|
| Stripe | 银行卡自动更新 | 在大多数套餐中默认启用 |
| Braintree | Account Updater | 必须在商家设置中启用 |
| Paddle | 内置 | 自动 |
| Recurly | Account Updater | 需要配置 |

### 催款邮件序列

| 日期 | 主题行 | 正文重点 | CTA |
|-----|-------------|-----------|-----|
| 第 0 天 | “您的 [Product] 付款未能成功处理” | 陈述事实，不归咎于客户。银行卡可能已过期或余额不足。 | [更新付款方式] |
| 第 3 天 | “需要操作：更新您的 [Product] 付款信息” | 提醒他们将失去哪些内容的访问权限。 | [更新付款方式] |
| 第 7 天 | “您的 [Product] 账户存在风险” | 列出他们已经创建的功能配置或数据。营造轻微的紧迫感。 | [更新付款方式] |
| 第 14 天 | “最终通知：您的 [Product] 访问权限将在 7 天后终止” | 给出明确的截止日期。如果是银行方面的问题，主动提供帮助。 | [更新付款方式] + [联系支持] |
| 第 21 天 | “您的 [Product] 账户已暂停” | 说明账户状态的变化。数据仍然安全。可以轻松重新激活。 | [重新激活账户] |

**邮件规则：**
- 每封邮件都直接链接到付款信息更新页面（而不是控制面板）
- 不要让客户感到内疚或羞愧。银行卡支付失败是常有的事。
- 主题行应具体明确（包含产品名称）
- 包含欠款金额和银行卡号后 4 位
- 为需要帮助的客户提供支持渠道

## 客户挽回活动框架

### 客户挽回时机

| 时间窗口 | 成功率 | 方法 |
|--------|-------------|---------|
| 取消后第 7 天 | 5-10% | 温和提醒，不施加压力 |
| 取消后第 30 天 | 3-7% | 产品更新 + 优惠 |
| 取消后第 60 天 | 2-5% | 最有力度的优惠 + 重新开始 |
| 取消后第 90 天及以后 | 1-3% | 仅在产品发生重大变化时联系 |

### 客户挽回邮件序列

**第 7 天邮件：**
- 主题：“您的 [Product] 账户正在等待您回来”
- 正文：他们留下的内容（数据、项目、团队）。仅提供一个 CTA：重新激活。
- 不提供折扣。只需提醒产品价值。

**第 30 天邮件：**
- 主题：“来看看 [Product] 有哪些新变化”
- 正文：列出他们离开后推出的 2-3 项具体改进。仅提供一个 CTA：重新激活。
- 小额激励：“回归即可免费使用 1 个月”

**第 60 天邮件：**
- 主题：“我们期待您的回归——[优惠]”
- 正文：提供最有力度的优惠（前 3 个月五折或延长免费使用期）。给出明确的截止日期。
- 最后一次重要的主动挽回尝试。

## 客户流失健康度评分

### 客户流失的领先指标

| 信号 | 权重 | 检测方式 |
|--------|--------|-----------|
| 登录频率逐周下降 | 高 | 使用情况分析 |
| 功能使用率下降 | 高 | 功能事件跟踪 |
| 支持工单升级 | 高 | 服务台数据 |
| NPS 评分 < 7 | 高 | 调查数据 |
| 发票争议或付款问题 | 中 | 计费系统 |
| 关键支持者已离职 | 高 | 联系人监控 |
| 距合同续约 < 90 天 | 中 | CRM 数据 |
| 检测到正在评估竞争对手 | 高 | 销售情报 |

### 风险评分计算

```
Risk Score = Sum of (Signal Weight x Signal Present)

0-20: Low risk (monitor)
21-40: Moderate risk (proactive outreach)
41-60: High risk (intervention required)
61+: Critical risk (executive escalation)
```

## 指标与基准

### 关键指标

| 指标 | 公式 | 良好 | 优秀 |
|--------|---------|------|-----------|
| 挽留率 | 成功挽留的客户数 / 取消尝试次数 | 10-15% | 20%+ |
| 主动流失率 | 主动取消数 / 客户总数（每月） | < 3% | < 1.5% |
| 被动流失率 | 付款失败导致的取消数 / 客户总数（每月） | < 1.5% | < 0.5% |
| 付款挽回率 | 已挽回的失败付款数 / 失败付款总数 | 25-35% | 40%+ |
| 客户赢回率 | 重新激活数 / 取消数（90 天窗口期） | 5-10% | 10%+ |
| 退出调查完成率 | 已完成的调查数 / 取消尝试次数 | > 70% | > 90% |
| 挽留优惠接受率 | 已接受的优惠数 / 展示的优惠数 | 15-25% | 30%+ |

### 危险信号

| 信号 | 诊断 | 行动 |
|--------|-----------|--------|
| 挽留率 < 5% | 优惠与取消原因不匹配 | 重新构建优惠与原因的映射关系 |
| 退出调查完成率 < 60% | 调查过长或为可选项 | 将其设为必填，并仅保留 1 个问题 |
| 挽回率 < 20% | 重试逻辑或电子邮件存在问题 | 审核催款流程 |
| 单一原因 > 40% | 存在系统性的产品或定价问题 | 上报至产品团队或管理层 |
| 每月流失率 > 5% | 业务可能正在萎缩 | 仅靠防止客户流失无法解决；审查 ICP 和产品 |

## 客户流失影响计算器

### 快速估算

```
Monthly MRR at risk = Total MRR x Monthly churn rate
Annual MRR saved by 1% churn reduction = Total MRR x 0.01 x 12
Annual MRR saved by 20% save rate = (Monthly MRR at risk x 0.20) x 12

Example:
  MRR: $500,000
  Monthly churn: 4% = $20,000/month lost
  Reduce to 3% = $5,000/month saved = $60,000/year
  Add 20% save rate on remaining = $3,000/month saved = $36,000/year
  Total annual impact: $96,000
```

| 客户赢回活动 | 3 封电子邮件序列 | 第 7、30、60 天发送的电子邮件，包含主题行和优惠 |
| 客户流失记分卡 | 指标表 | 当前指标与基准的对比及差距分析 |
| 影响模型 | 收入计算 | 不同改善程度下减少客户流失所带来的金额影响 |

## 相关技能

- **customer-success-manager** -- 用于健康度评分、QBR 和扩展收入。不用于取消流程或催款设计。
- **pricing-strategy** -- 当客户流失的根本原因是定价或套餐不匹配时使用。不用于挽留优惠设计。
- **onboarding-cro** -- 当客户流失可追溯到激活不佳时使用。如果用户从未体验到价值，应先改进新用户引导。
- **referral-program** -- 用于获客。客户流失预防负责漏斗的另一端。

## 故障排除

| 问题 | 可能原因 | 解决方案 |
|---------|-------------|----------|
| 所有原因对应的挽留率均低于 5% | 挽留优惠与退出原因不匹配 | 使用调查数据重新构建退出原因与优惠之间的映射；运行 exit_survey_analyzer.py 以识别不匹配项 |
| 退出调查完成率低于 60% | 调查为选填项或过长 | 在显示挽留优惠之前，将单问题调查设为必填；移除多页面流程 |
| 支付挽回率低于 20% | 重试逻辑配置错误或催款邮件未发送 | 使用 dunning_sequence_analyzer.py 审核催款序列；验证邮件送达率和重试计划 |
| 单一退出原因占回复总数的 40% 以上 | 系统性的产品或定价问题 | 上报给产品团队或管理层；仅靠取消流程无法解决此问题 |
| 月度流失率高于 5% | 可能存在 ICP、产品市场契合度或定价问题 | 单靠客户流失预防无法解决此问题；应结合 pricing-strategy 和产品反馈闭环 |
| 赢回邮件的重新激活数为零 | 邮件未送达收件箱或优惠吸引力不足 | 检查送达能力（SPF、DKIM、DMARC）；测试更有吸引力的优惠；验证重新激活链接是否有效 |
| 非自愿流失上升，而自愿流失保持稳定 | 未启用银行卡信息更新服务或重试时机不佳 | 在支付处理平台上启用银行卡信息自动更新；在 dunning_sequence_analyzer.py 中检查重试计划 |

## 成功标准

- 月度主动流失率低于 2.5%（低于 1.5% 为优秀）
- 月度被动流失率低于 1.0%（低于 0.5% 为优秀）
- 取消流程挽留率达到 15-25%（高于 20% 为优秀）
- 支付失败后的款项追回率达到 30% 以上
- 退出调查完成率高于 80%
- 取消后 90 天内的赢回再激活率达到 5-10%
- 挽留优惠接受率高于 20%，且被挽留的客户在挽留后继续留存 6 个月以上

## 范围与限制

- **范围内：** 取消流程设计、退出调查架构、挽留优惠映射、催款序列、款项追回、赢回营销活动、流失影响建模
- **范围外：** 产品市场契合度分析、定价重构、ICP 重新定义、客户获取
- **数据依赖：** 脚本分析来自 JSON 输入的时间点快照；不提供实时 CRM 集成
- **非预测性 ML：** 所有评分均为确定性算法计算，不使用机器学习模型
- **法律说明：** 取消流程必须遵守 FTC 指南（美国）和消费者保护法（欧盟），不得使取消操作变得不合理地困难
- **收入估算：** 影响计算是基于输入假设得出的预测，并非保证

## 集成点

- **customer-success-manager** -- 将健康度评分输入流失风险评估；使用流失数据校准健康度评分阈值
- **pricing-strategy** -- 当退出调查数据显示 PRICE 是主要原因（>30%）时，升级至 pricing-strategy 以进行结构性定价审查
- **onboarding-cro** -- 当退出调查数据显示 LOW_USAGE 或 COMPLEXITY 是首要原因时，根本原因通常是激活不佳；应先修复入门引导
- **revenue-operations** -- 销售管道和预测模型应考虑流失率降低对净收入留存率（NRR）的影响
- **referral-program** -- 通过挽留优惠留存的客户，在持续使用 90 天后可作为推荐计划的招募对象
