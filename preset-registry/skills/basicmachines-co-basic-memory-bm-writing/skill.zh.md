# 编写有用的项目记忆

每当 Codex Basic Memory 技能编写或大幅修订笔记时，都应采用这一共享标准。此文件特意允许用户自定义：你可以在这里调整行文风格、侧重点和偏好的结构，使其符合你希望记录工作的方式。

特定任务的技能仍负责必需的元数据、模式、证据收集和工作流。此技能只塑造笔记的表达方式，绝不凌驾于事实约束之上。

## 行文风格

- 面向日后回来查阅并试图理解所发生之事的人或智能体来写。
- 表达要清晰、直接、亲切，并在技术上保持诚实。
- 与其泛泛称赞，不如给出具体观察。
- 当证据支持时，应表明观点。只要解释原因，将某项变更称为优雅、混乱、有风险、乏味或令人满意都无妨。
- 个性表达应服务于记忆，而非用于炫技。

## 讲述故事

- 为笔记建立一条叙事主线：问题 -> 方法 -> 当前状态及影响。
- 解释该方法为何有效、系统或工作流发生了怎样的变化，以及这种差异为何重要。
- 明确指出相关的权衡、棘手之处、有用的简化、移除的内容，以及有意搁置的工作。
- 优先使用确切的行为、组件名称、路径和命令，而不是“取得了进展”或“更新了实现”之类的表述。
- 使用有实质内容的文字说明上下文和推理。不要把笔记简化成满屏的项目符号，或逐提交罗列的变更日志。
- 如果存在可长期沿用的经验，应明确写出——例如发现的约束、明确划定的边界，或未来工作应避免的捷径。正是这些内容将状态报告转化为项目记忆。
- 深度应与主题相匹配。一条简短的记忆事实就应保持简短。

## 锚定工作

- 当笔记记录仓库工作时，应说明工作所在的位置：项目或仓库、git 分支以及 PR 或 issue；当某个具体提交很重要时，还应包括 commit sha。
- 将笔记模式定义的锚点放在 frontmatter 中；其余锚点记录为观察，例如 `- [branch] feat/bm-writing` 或 `- [pr] #1123`。
- 当 GitHub 上的 PR、issue 和 commit 锚点的规范 URL 已经验证时，将其呈现为 Markdown 链接。本地或尚未推送的 SHA 应保留为代码，不要为其构造可能并不存在的链接。
- 只锚定相关内容。没有仓库上下文的记忆事实完全不需要 git 锚点。

## 保留语义层

- 在 `## Observations` 下以 `- [category] fact` 的形式提炼可长期保留的事实。
- 将决策记录为 `[decision]` 观察项，而不是单独放在 Decisions 部分中的普通项目符号。
- 在 `## Relations` 下使用 `- relation_type [[Target Note]]` 表示图关系边。绝不要将关系表示为 `[relates_to]` 之类的观察项。
- 仅在关系有助于阐明上下文时添加关系；不要只是为了让笔记看起来彼此关联而凭空创建目标。

## 证据边界

- 不要虚构意图、影响、验证结果、决策或戏剧性情节。
- 明确说明不确定性和缺失的证据。
- 除非测试或部署确实已执行，或用户提供了结果，否则绝不要声称测试或部署已通过。
