# 事件存储设计

面向事件溯源应用程序的事件存储设计综合指南。

## 何时使用此技能

- 设计事件溯源（event sourcing）基础设施
- 在多种事件存储技术之间进行选型
- 实现自定义事件存储
- 优化事件的存储与检索
- 搭建事件存储的模式（schema）
- 规划事件存储的扩展

## 核心概念

### 1. 事件存储架构

```
┌─────────────────────────────────────────────────────┐
│                    Event Store                       │
├─────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │   Stream 1   │  │   Stream 2   │  │   Stream 3   │ │
│  │ (Aggregate)  │  │ (Aggregate)  │  │ (Aggregate)  │ │
│  ├─────────────┤  ├─────────────┤  ├─────────────┤ │
│  │ Event 1     │  │ Event 1     │  │ Event 1     │ │
│  │ Event 2     │  │ Event 2     │  │ Event 2     │ │
│  │ Event 3     │  │ ...         │  │ Event 3     │ │
│  │ ...         │  │             │  │ Event 4     │ │
│  └─────────────┘  └─────────────┘  └─────────────┘ │
├─────────────────────────────────────────────────────┤
│  Global Position: 1 → 2 → 3 → 4 → 5 → 6 → ...     │
└─────────────────────────────────────────────────────┘
```

### 2. 事件存储需求

| 需求              | 说明                                |
| ----------------- | ---------------------------------- |
| **只追加（Append-only）** | 事件是不可变的，只允许追加 |
| **有序**          | 流内有序且全局有序     |
| **带版本号**      | 乐观并发控制     |
| **订阅**          | 实时事件通知      |
| **幂等**          | 安全地处理重复写入     |

## 技术对比

| 技术             | 最适用场景                  | 局限性                      |
| ---------------- | ------------------------- | -------------------------------- |
| **EventStoreDB** | 纯事件溯源       | 用途单一                   |
| **PostgreSQL**   | 已有 Postgres 技术栈   | 需要手动实现            |
| **Kafka**        | 高吞吐量流式处理 | 不适合按流查询 |
| **DynamoDB**     | 无服务器、AWS 原生    | 查询能力受限                |
| **Marten**       | .NET 生态系统           | 仅限 .NET                 |

## 最佳实践

### 推荐做法

- **使用包含聚合类型的流 ID** - 例如 `Order-{uuid}`
- **包含关联 ID/因果 ID（correlation/causation ID）** - 用于链路追踪
- **从第一天起就为事件添加版本号** - 提前规划模式的演进
- **实现幂等性** - 使用事件 ID 进行去重
- **合理建立索引** - 适配你的查询模式

### 避免做法

- **不要更新或删除事件** - 它们是不可变的事实
- **不要存储大体积负载** - 保持事件小巧
- **不要省略乐观并发** - 它可以防止数据损坏
- **不要忽视背压** - 妥善处理慢速消费者
