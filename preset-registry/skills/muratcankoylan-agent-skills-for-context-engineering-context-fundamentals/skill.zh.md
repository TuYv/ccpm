# 上下文工程基础

上下文是语言模型在推理时可用的完整状态：系统指令、工具定义、检索到的文档、消息历史记录以及工具输出。上下文工程是一门对最小化的高信号词元集合进行筛选与组织，从而最大限度提高获得预期结果概率的学科。

此技能是该集合中所有其他技能赖以构建的概念基础。它阐释了什么是上下文、注意力机制如何运作、为什么上下文质量比数量更重要，以及理解其他所有上下文工程决策所需的思维模型。它不负责操作性工作：调试注意力失效属于 `context-degradation`，词元效率策略属于 `context-optimization`，对话摘要属于 `context-compression`，基于文件的卸载属于 `filesystem-context`，而项目形态决策属于 `project-development`。

## 何时启用

当工作涉及概念层面时，启用此技能：

- 解释什么是上下文，以及注意力机制如何制约智能体行为。
- 帮助需要先掌握思维模型、再深入学习操作性技能的新贡献者入门。
- 在选择具体策略之前，从第一性原理出发推理与上下文相关的设计决策（此约束意味着什么、为何存在这种权衡）。
- 编写或审阅需要以底层机制为操作指南奠定基础的文档。

不要为操作性工作启用此技能。具体操作由专门技能负责：

- 诊断中间信息丢失、上下文污染或注意力失效：`context-degradation`。
- 通过掩码、分区、前缀缓存、预算来降低词元成本：`context-optimization`。
- 将长会话压缩为交接摘要：`context-compression`。
- 卸载大型工具输出或维护持久暂存区：`filesystem-context`。
- 决定 LLM 项目或流水线的形态：`project-development`。

## 核心概念

将上下文视为有限的注意力预算，而非存储箱。添加的每个词元都会争夺模型的注意力，并消耗一旦进入推理过程便无法补充的预算。工程问题是在三项约束下最大限度提高每个词元的效用：硬性词元限制、较为宽松的有效容量上限，以及会对位于上下文中部的信息造成不利影响的 U 形注意力曲线（claim-context-degradation-lost-middle-ruler）。

组装上下文时应用以下四项原则：

1. **信息量优先于面面俱到** — 仅包含与当前决策相关的内容；设计能够按需检索额外信息的系统。
2. **感知位置的放置方式** — 将关键约束置于上下文的开头和结尾，因为长上下文评估表明，相较于位于边缘的信息，位于中间位置的信息较难被可靠地恢复（claim-context-degradation-lost-middle-ruler）。
3. **渐进式披露** — 启动时加载技能名称和摘要；仅当某项技能针对特定任务启用时，才加载其完整内容。
4. **迭代式筛选与组织** — 上下文工程不是一次性的提示词编写工作，而是一项每次向模型传递内容时都要持续实施的工作准则。

## 详细主题

### 上下文的构成

**系统提示词**
使用 XML 标签或 Markdown 标题将系统提示词组织成不同的部分（背景、指令、工具指南、输出格式）。系统提示词会在整个对话过程中持续存在，因此应将最关键的约束放在开头和结尾，因为这些位置最容易获得注意。

调整指令的抽象层级，以平衡两种失败模式。抽象层级过低会将脆弱的逻辑硬编码进去，在条件变化时失效。抽象层级过高则只能提供模糊的指导，无法为期望行为给出具体信号。应采用启发式驱动的指令：既足够具体，能够指导行为，又足够灵活，可以泛化——例如，使用编号步骤，同时在每一步中保留判断空间。

从最精简的指令开始，然后根据观察到的失败模式有针对性地添加指令，而不是预先塞入各种边缘情况。精心挑选多样且典型的少样本示例来展示预期行为，而不是罗列所有可能的场景。

**工具定义**
编写工具描述时，应回答三个问题：工具的作用是什么、何时使用，以及它会返回什么。应包含使用场景、参数默认值和错误情况——如果人类工程师都无法区分不同工具，智能体同样无法区分。

尽量精简工具集。合并功能重叠的工具，因为臃肿的工具集会产生模糊的决策点，并且在 JSON 序列化后占用大量上下文（与等效的纯文本描述相比，工具 schema 通常会膨胀 2-3 倍）。

**检索到的文档**
维护轻量级标识符（文件路径、已存储的查询、Web 链接），并通过即时检索将数据动态加载到上下文中。这与人类认知方式相似——维护索引，而不是副本。强标识符（例如 `customer_pricing_rates.json`）使智能体即使没有搜索工具也能找到相关文件；弱标识符（例如 `data/file1.json`）则会导致不必要的加载。

对大型文档进行分块时，应在自然的语义边界（章节标题、段落分隔处）进行拆分，而不是按照任意字符数限制进行切分，以免在概念中间将其割裂。

**消息历史**
消息历史充当智能体的暂存记忆，用于跟踪进度、维护任务状态，并在多个轮次之间保留推理过程。对于长期运行的任务，它可能逐渐占据上下文使用量的主要部分——应持续监控，并在其挤占当前有效指令之前进行压缩。

循环精简历史记录：当某个工具已在对话的较早阶段被调用后，其原始结果通常无需继续逐字保留。使用紧凑的摘要或引用替换过时的工具输出，以减少低信号的信息冗余。

**工具输出**
在智能体的运行轨迹中，工具输出通常会占据上下文的主要部分（claim-context-optimization-tool-output-dominance）。应用观察遮蔽：智能体处理完结果后，用紧凑的引用替换冗长输出。仅保留最近仍有相关性的文件内容；压缩或移除较早的内容。

### 上下文窗口与注意力机制

**注意力预算**
对于 n 个词元，注意力机制会计算 n 的平方数量级的成对关系。随着上下文增长，模型维持这些关系的能力会下降——这并非断崖式骤降，而是呈现性能梯度。主要使用较短序列训练的模型，用于处理跨越整个上下文依赖关系的专用参数较少，因此其有效上限远低于标称窗口大小。

设计时应考虑这一梯度：在针对目标工作负载进行测量之前，应假定有效容量显著低于宣称的窗口大小。标称上下文窗口很大，并不意味着不再需要针对特定任务进行性能退化测试（claim-context-degradation-lost-middle-ruler）。

**位置编码的限制**
位置编码插值可将序列处理能力扩展至训练长度之外，但会降低位置精度。与较短输入下的性能相比，在扩展上下文中，信息检索和长距离推理的准确率预计会有所下降。

**渐进式披露的实践**
在三个层级实现渐进式披露：

1. **Skill 选择**——启动时仅加载名称和描述；按需激活完整的 Skill 内容。
2. **文档加载**——先加载摘要；仅在任务需要时获取详细章节。
3. **工具结果保留**——完整保留近期结果；压缩或移除较早的结果。

保持清晰的边界：如果某个 Skill 或文档被激活，就应完整加载，而不是只加载一部分——部分加载会造成令人困惑的信息缺口，降低推理质量。

### 上下文质量与数量

不要认同上下文窗口越大就能解决记忆问题这一假设。处理成本会随着上下文长度不成比例地增长——不仅仅是成本线性增加，超过有效容量阈值后，模型性能也会下降。即使使用前缀缓存，长输入的成本仍然很高。

应用信号密度测试：对于每一部分上下文，都要判断移除它是否会改变模型的输出。如果不会，就将其移除。冗余内容不只是浪费词元——它还会主动稀释模型对高信号内容的注意力。

## 实用指南

本节提供概念层面的应用建议，并明确指出相关的操作型 Skill。

### 如何推理上下文决策

需要做出与上下文相关的设计决策时，应将概念问题与操作问题分开。概念问题是“这意味着什么，以及它为什么重要”；操作问题是“我们要应用什么具体技术”。使用本 Skill 回答前者；将后者交由负责该问题的专用 Skill 处理。

例如，决定是否要总结一段较长的 Agent 会话包含两个部分：(1) 为什么需要进行总结（注意力预算有限，U 形曲线会导致中间部分内容的处理效果下降，信号密度比信息量更重要——由本 Skill 解释）；以及 (2) 什么压缩策略能够保留正确的状态，并应在利用率达到什么阈值时触发压缩（`context-compression`）。

### 新贡献者的阅读顺序

初次接触上下文工程的贡献者应按以下顺序阅读：

1. 本技能，以理解注意力预算这一思维框架和 U 形曲线。
2. `context-degradation`，了解上下文失效在实践中的表现以及如何诊断。
3. 根据与其项目最相关的运维问题，从 `context-optimization`、`context-compression`、`filesystem-context`、`memory-systems` 中选择两到三个阅读。

跳过第 1 步，会导致操作者只会应用技术，却不理解其中的原因；跳过运维技能，则会造就不知道哪种技术适用于哪种失效模式的理论家。

## 示例

**示例 1：组织系统提示词**

此示例说明了这样一个概念：关键约束应放在注意力占优的位置（开头和结尾），而明确的章节边界有助于模型解析提示词：

```markdown
<BACKGROUND_INFORMATION>
You are a Python expert helping a development team.
Current project: Data processing pipeline in Python 3.9+
</BACKGROUND_INFORMATION>

<INSTRUCTIONS>
- Write clean, idiomatic Python code
- Include type hints for function signatures
- Add docstrings for public functions
- Follow PEP 8 style guidelines
</INSTRUCTIONS>

<OUTPUT_DESCRIPTION>
Provide code blocks with syntax highlighting.
Explain non-obvious decisions in comments.
</OUTPUT_DESCRIPTION>
```

**示例 2：将注意力预算作为一种心智模型**

大上下文模型不会对上下文中的所有内容给予同等程度的注意。有效容量取决于具体工作负载，而 U 形曲线会使放置在中间的信息受到影响。在决定要加载上游知识库中的多少内容时，应采用这样的心智模型：不要问“能否放得下”，而要问“模型是否仍会关注真正重要的部分”。

与之对应的运维问题（应使用哪种技术来减少负载）属于 `context-optimization` 的范畴。

## 指南

1. 将上下文视为一种收益递减的有限资源
2. 将关键信息放在注意力占优的位置（开头和结尾）
3. 使用渐进式披露，将内容推迟到需要时再加载
4. 使用清晰的章节边界来组织系统提示词
5. 在开发过程中监控上下文使用情况
6. 在利用率达到 70-80% 时触发压缩
7. 针对上下文退化进行设计，而不是寄希望于避免退化
8. 相比规模更大但信号密度更低的上下文，优先选择规模更小但信号密度更高的上下文

## 注意事项

1. **标称窗口并不等于有效容量**：即使模型宣称拥有很大的上下文窗口，在复杂的检索或推理任务中，也可能远未达到该上限就已出现性能退化。在你自己的退化测试证明可以提高预算之前，应将预算控制在标称窗口以下。

2. **基于字符数的 token 估算会悄然产生偏差**：对于英文散文，约 4 个字符/token 的经验法则并不适用于代码（2-3 个字符/token）、URL 和文件路径（每个斜杠、点和冒号都是独立的 token），也不适用于非英文文本（通常为 1-2 个字符/token）。对于任何预算关键型计算，都应使用提供商实际采用的 tokenizer（例如，OpenAI 模型使用 tiktoken，Anthropic 使用 token counting API）。

3. **工具 schema 在 JSON 序列化后会膨胀 2-3 倍**：在源代码中看起来很紧凑的工具定义，序列化后会显著膨胀——方括号、引号、冒号和逗号都会消耗 token。十个具有中等复杂度 schema 的工具，可能在发送任何消息之前就消耗 5,000-8,000 个 token。应审计序列化后工具的 token 数量，而不是源代码行数。

4. **消息历史会在智能体循环中悄然膨胀**：每次工具调用都会将请求和完整响应添加到历史记录中。经过 20-30 次迭代后，历史记录可能会占用上下文窗口的 70-80%，而智能体在推理质量崩溃之前不会表现出任何明显症状。为历史记录设置严格的 token 上限，并主动触发压缩。

5. **位于中间位置的关键指令会被忽略**：U 形注意力曲线意味着，上下文中间部分的回忆准确率比开头和结尾低 10-40%。切勿将安全约束、输出格式要求或行为护栏放在冗长系统提示词的中间——应将它们固定在顶部或底部。

6. **加载过于积极的渐进式披露会适得其反**：一发现相关迹象就加载所有“可能相关”的技能或文档，会再次造成上下文填塞问题。应设置严格的激活阈值——仅当任务明确符合某项技能的触发条件时才加载该技能，而不能仅仅因为主题与其相近就加载。

7. **混合不同层级的指令会导致行为不一致**：在同一个提示词中，将高度具体的规则（“始终使用恰好 3 个项目符号”）与模糊的指令（“提供有用的帮助”）结合起来，会产生相互冲突的信号。按层级对指令进行分组，并保持每个部分内部一致——要么由启发式规则驱动，要么采用规定式规则，不要将两者交错混合。

## 集成

此技能是概念基础。它不负责执行具体操作；它提供其他操作型技能所依赖的思维模型。

操作工作的路由图：

- `context-degradation`：诊断注意力失效、中间信息丢失、上下文污染和干扰问题。
- `context-optimization`：提高 token 效率的策略（掩码、分区、缓存、预算）。
- `context-compression`：在保留决策、文件和风险信息的同时压缩长会话。
- `filesystem-context`：将大型输出转移到文件系统，并将文件用作持久化暂存区。
- `memory-systems`：具有实体跟踪能力的跨会话记忆架构。
- `multi-agent-patterns`：判断何时应将工作拆分给多个智能体，以实现上下文隔离。
- `tool-design`：编写能够正确路由的工具描述和 schema。
- `project-development`：判断任务是否适合使用 LLM，并设计多阶段流水线。

首先阅读此技能以建立思维模型；在实际执行工作时，再阅读适合该任务的操作型技能。
