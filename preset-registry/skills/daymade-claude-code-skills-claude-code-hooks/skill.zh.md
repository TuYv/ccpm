# Claude Code 钩子

Claude Code 会在工具调用边界触发**钩子**。钩子是一条 shell 命令，它通过 stdin 接收 JSON 事件；对于阻塞型钩子，它会通过自身的**退出代码**决定工具调用是否继续。这是唯一能够从*结构上*阻止某种行为的机制——CLAUDE.md 中的文字规则只是一项建议，生成补全的驱动力可能会绕过它；而钩子是一堵墙。

## 何时适合使用钩子（以及何时不适合）

当**一条规则即使已经明确写下，却仍然不断遭到违反**时，请编写钩子。判断信号是：你添加了文字规则，它读起来很清楚，但相同的行为还是再次发生——因为在采取行动的那一刻，注意力 100% 集中在“把事情做完”上，提醒因此失去了作用。这种反复发生的情况，就是应该把规则从文字（建议性）转移到钩子（强制执行）的信号。治理经验法则：*Tier-0 不可逆操作 + 只有文字规则而没有钩子 → 它就应该成为钩子。*
（这里的 **Tier-0** = 无法在会话内部撤销其损害的操作：
销毁未提交的工作、将密钥推送到远程、删除文件、向外发布内容。判断标准是可逆性，而不是严重程度。）

在以下情况下，**不要**使用钩子：规则实际上从未被反复违反（不要为假想中的错误预先构建防护——这会产生没有已证实收益的成本），或者这条“规则”属于没有机械特征可供识别的判断问题（钩子只能匹配 token/模式；它无法判断设计是否优秀）。

## 钩子类型及退出代码的含义

| 类型 | 触发时机 | 退出 0 | 退出 2 | 其他 |
|---|---|---|---|---|
| **PreToolUse** | 工具运行之前 | 允许 | **阻止**调用（stderr → 作为指导显示给模型） | 任何其他退出状态 =“非阻塞错误”→ **调用继续进行** |
| **PostToolUse** | 工具运行之后 | 保持安静，**除非它在 stdout 上输出一个 `hookSpecificOutput` JSON——上下文注入就是通过这种方式实现的，并且发生在退出 0 时** | 向模型提供反馈（无法撤销工具运行） | — |
| **SessionStart** | 会话开始时 | 继续 | — | **始终退出 0**——绝不阻止会话 |
| **Stop**（以及 `SubagentStop`） | 模型即将结束响应时 | 允许停止 | **阻止停止**——迫使模型继续执行（stderr → 作为原因反馈给模型） | 循环安全：钩子会检查 `stop_hook_active`（这是必要条件，但**并不**充分——见规则 7）。执行框架的连续阻塞上限（默认为 8）**并不是**通用的最后保障——只要继续执行期间调用了工具，其计数器就会重置，因此对于补救过程涉及工具调用的钩子（也就是其中绝大多数，#27），永远不会触及该上限。请自行设置边界。同一事件的所有 Stop 钩子都会**并行**运行——一轮阻塞可以携带多个钩子的反馈 |

- **PreToolUse** 是主力——它是唯一能够*阻止*操作的钩子。
  `matcher` 用于选择工具（`Bash`、`Agent`、`WebFetch`……）。退出 2 会阻止调用，并且钩子的 **stderr** 会成为模型看到的消息——因此，请在其中说明*原因*和*正确的替代方案*，不要只写“已阻止”。
- **PostToolUse** 无法撤销操作，但它可以**注入权威上下文**，使后续的幻觉无法成立（例如，在提交之后重新读取真实的 git HEAD 并将其呈现出来——面对注入的事实，模型无法再“认为自己已经提交”）。
- **SessionStart** 用于对**防护机制本身进行健康检查**——健康时保持安静，发生故障时发出警告，并始终退出 0。
- **`set -euo pipefail` 与 `set -uo pipefail`——根据契约进行选择，并且要知道，有两种方式可以维持始终退出 0 的契约。** 可能执行阻塞的钩子
  （PreToolUse）需要 `-e`：脚本因意外故障而中止是可以接受的，因为调用方会将非 0/2 的退出状态视为“继续”。契约要求**始终退出 0** 的钩子（PostToolUse 注入器、SessionStart 检查）有两种可靠形式：(a) **移除 `-e`**，并使用 `||` 保护每一条有风险的命令——如果启用了 `-e`，某个合理地未找到任何内容的 `grep` 就会让钩子中途终止，而 CLI 只会显示一条空泛的 `Failed with non-blocking status code`
  （陷阱 #8，Pattern E 的形式）；或者 (b) **保留 `-e` 并添加 `trap 'exit 0' ERR`**，从而让所有故障仍被转换为退出 0，同时由 `-e` 继续保护处理流程
  （`git-commit-headcheck` 的生产环境形式，Pattern D）。两种方式都正确；
  你不能做的是只使用 `-e`，却既不设置 trap，也不使用 `||` 保护。经验法则：**对于做决定的钩子使用 `-e`；对于做报告的钩子，移除 `-e` 或设置 trap**
  （陷阱 #8）。
- **Stop 是一个特例，也是最常被误用的类型**：
  它是*唯一*能够对模型**自身刚刚生成的内容**（也就是模型自己的回复文本）作出反应的钩子类型。其他所有钩子类型——包括听起来似乎适合监管“说了什么”的
  `UserPromptSubmit`——都只能看到**用户的**输入；从结构上讲，它无法看到模型自己的*当前轮次*输出（这一说法仍然成立——这依然是将此类规则交给 Stop 的正确理由）。不过，这一保证并不能进一步证明 `.prompt` 字段始终源于一次
  键盘输入：后台任务通知自身的报告文本同样可能填充该字段，并且 stdin JSON 中没有任何内容会标记二者之间的区别——#30。类似“模型不得为尚未验证的事物编造简称”这样的规则应放在 Stop 上；如果改为放在
  `UserPromptSubmit` 上，它将会：(a) 一次都无法捕获其原本要处理的情况，因为相关文本根本不会流经该事件；并且 (b)
  每当用户自己输入的无关内容碰巧包含触发模式时，就会错误地阻止用户输入。
  这是类别错误，而不是调优问题——无论怎样改进错误事件上的正则表达式，都无法解决它。完整契约
  （`last_assistant_message` 与 `transcript_path`、防循环检查）位于
  [references/hook_patterns.md](references/hook_patterns.md) 的 Pattern E 中。
- **Stop 有两个具有相同循环保护的阻塞通道——根据意图选择，并让第一次（也是唯一一次）阻塞携带全部信息。** `decision:
  "block"` + `reason`，或普通的退出 2 + stderr，会显示为钩子*错误*——适用于硬性门禁（“绝不能允许这种情况继续存在”）。`hookSpecificOutput.additionalContext`
  会显示为中性的“Stop 钩子反馈”，且不会产生错误通知——适用于模型应当权衡的指导和提醒，而不是门禁。两者都会计入上表所述的相同连续阻塞上限，因此选择体现的是语气，而不是安全性。这对消息设计意味着：被阻止后的重试轮次
  （`stop_hook_active: true`）会被放行，**无论其中还剩下什么违规内容**——因此，一个 Stop 防护钩子恰好只有**一次**知情干预的机会。（只有当补救方式是“重写回复”时，上限才会强化这一点；如果补救涉及工具调用，计数器会被重置，永远不会触及该上限——#27。
  无论哪种情况，“只有一次机会”的结论都成立，因为它依赖的是锁存机制，而不是上限。）请在这
  一次阻塞中报告*所有*发现（只输出第一项的防护钩子会永久丢失其余发现——
  陷阱 #17），并将消息写成一份脱困手册，明确指出确切且可接受的修复方式，而不是仅仅给出判决——模型要么在一轮内收敛，要么会在猜测中耗尽上限。v2.1.145+ 的输入 `background_tasks` / `session_crons` 让
  阻塞型钩子可以区分“会话已完成”和“会话只是暂停以等待后台工作”——阻止暂停会强制产生毫无意义的继续执行，并浪费同一个上限。

完整的可运行骨架：[references/hook_patterns.md](references/hook_patterns.md)。

## 骨架（PreToolUse Bash 防护钩子）

```bash
#!/usr/bin/env bash
set -euo pipefail
INPUT=$(cat)                                   # the JSON event on stdin
TOOL=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_name',''))" 2>/dev/null||echo "")
[ "$TOOL" != "Bash" ] && exit 0                # only guard the tool you mean to
CMD=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" 2>/dev/null||echo "")
[ -z "$CMD" ] && exit 0
printf '%s' "$CMD" | grep -qw 'TRIGGER' || exit 0   # fast path: not relevant → allow
# ... precise detection here ...
if <command actually does the banned thing>; then
  echo "BLOCKED: ... WHY ... USE INSTEAD: ..." >&2   # stderr = the guidance shown
  exit 2
fi
exit 0
```

## 区分有效防护钩子与会毒化会话的防护钩子的规则

这些不是风格偏好——每一条都是我们实际发布并追溯定位过的具体故障。

### 1. 始终使用 **shlex 在词元层面进行匹配**，绝不要用 awk 拆分原始字符串

**误拦截正常命令的防护钩子比发生漏报的防护钩子更糟**——
人们会习惯性绕过一个不得不绕过的防护钩子，之后它便什么也保护不了
（核心原则：*误杀健康输入比漏报更糟*）。误拦截反复发生的原因
是在原始命令字符串上进行匹配。

- **错误做法**：使用 `awk '{gsub(/&&|\|\||;|\|/,"\n")}'` 将其拆分为多个片段——awk
  不理解 shell 引号，因此 `grep -E "a|TRIGGER|b"` 会在带引号的正则表达式
  *内部*的 `|` 处被拆分，`TRIGGER` 会变成一个虚假的命令，而防护钩子
  会拦截一次普通的 grep。（于 2026-07-21 发布；该防护钩子的第一次实际使用
  就误拦截了我自己的 grep。）
- **正确做法**：使用 **`shlex.shlex` 类**对整条命令进行词元化，而不是使用
  `shlex.split()` 函数——`split()` 仅在 `| ; & < >` 两侧有空格时才将它们视为分隔符，
  因此 `ls|TRIGGER x` 会被词元化为 `['ls|TRIGGER', 'x']`，
  你的命令位置检查根本看不到 `TRIGGER`（已实测；使用
  `punctuation_chars=True` 的类会生成 `['ls', '|', 'TRIGGER', 'x']`）。请原样使用
  [references/hook_patterns.md](references/hook_patterns.md#the-shlex-command-position-walker)
  中的遍历器，而不要随手写一个单行命令。带引号的
  `"a|TRIGGER|b"` 会保持为**一个词元**，因此正则表达式参数绝不会被误认为
  命令。然后检查目标是否位于**命令位置**
  （token[0]，或者紧跟在 `;`/`&&`/`||`/`|` 分隔符之后，并跳过 `VAR=val`
  环境变量赋值前缀）。命令位置遍历器见
  [references/hook_patterns.md](references/hook_patterns.md)。
- 推论：`echo "…TRIGGER…"``、`grep TRIGGER`、`# TRIGGER`、`man TRIGGER` 必须
  全部放行。你的测试集必须包含这些“提及但不执行”的情况。
- **推论——在 `git` 写入片段到达遍历器之前将其豁免。** 提交消息是任意数据，
  而整段消息文本会作为伪命令文本进入命令位置遍历流程——当
  `git commit -F - <<EOF` 的正文引用 `foo|TRIGGER` 时，`TRIGGER` 会落在命令位置，
  防护钩子便会拦截修复自身问题的提交（陷阱 #7 正是如此，并且已经发布）。
  任何检查命令字符串的 Bash 防护钩子都必须跳过以 `git` +
  `commit`/`rebase`/`tag`/`am`/`cherry-pick` 开头的片段——而且要在拆分任何行之前，
  在整条命令层面完成此操作（Pattern A 展示了相应顺序；生产版本使用的是
  `lib-git-commit-detect` 的邻接检查）。
- **推论——遍历器采用两阶段设计是有原因的。** `whitespace_split=True`
  会将换行符视为普通空白，因此多行代码块
  （`cd /x\ngit add\nTRIGGER -y`）会被折叠成一个以 `cd` 开头的片段，
  触发词永远不会处于命令位置——在真实记录上重放时，触发率为 0
  （陷阱 #11）。应先以 **shell 感知**的方式拆分为多行（遵守引号状态
  和反斜杠续行，因此带引号的多行字符串不会被拆散），然后对每一行执行
  shlex 遍历——Pattern A 和遍历器章节都提供了该拆分器
  （`split_shell_lines`，已在 qlmanage-guard 的生产环境中得到验证）。
  即使它也无法解析 heredoc 正文（那并非引号语法）；何时接受这一残余风险，
  由 #11 中的取舍决定。
- **但 shlex 并非万能解法，而且检测的*对象*不同，也会改变 fail-open
  是否安全。** `shlex.split()` 本身在遇到不配对的引号时会抛出 `ValueError`——
  带有 `#` 或未闭合引号的多行 `git commit -m "…` 消息是典型触发场景。
  随后的 `except ValueError: cmd.split()` 回退会选择*放行*；当你检测的是
  **被禁用的修饰符**时，这是正确的（是否携带 `--no-verify`？——漏掉它所产生的
  偏差方向是安全的，符合规则 1），但当你检测的是命令本身**是否就是目标命令**
  时，这很危险（这是不是 `git commit`？——此处出现 ValueError 意味着防护钩子
  永远无法识别该提交，并且静默地不触发；一个真实的跨域提交就曾因此在没有
  确认对话框的情况下发布）。对于*这是不是该命令*的判断，应优先使用范围较窄的
  **正则表达式**（将 `git` 和 `commit` 作为独立单词，并允许其间存在任意标志词元），
  因为它不会受到多行引号破坏的影响；而 shlex 遍历器应留给
  *命令位置／修饰符*检查，在这些检查中，fail-open 才是安全方向。
  （边界是：当谓词为“这究竟是不是某个特定的常见命令”时使用正则表达式——
  如 `git commit`、`git push`——因为正是这些命令自身的消息／参数会破坏
  词元化；当谓词为“某个*被禁用的*命令或修饰符是否位于命令位置”时使用遍历器——
  在这种情况下，被禁用的对象很少出现，而发生 ValueError 时 fail-open
  所产生的偏差方向是安全的，符合规则 1。）

### 2. 在注册之前，使用 **`bash -n` + 真实 JSON 事件进行端到端测试**

**损坏或逻辑错误的 PreToolUse hook 会污染*整个*会话** —
此后每次 Bash 调用都会被截断 / 重复 / 误报失败 / 看起来像是以幻觉方式执行，
而你会责怪“环境”，实际上问题出在你刚刚安装的 hook。（2026-07-05：一次编辑破坏了
一个 `[^;&|]` 正则表达式，`;&` 变成了 bash case 穿透标记，污染了半个会话，
直到 `bash -n` 发现问题。）
“部署时测试通过”还不够——文件可能在*之后的*编辑中损坏。

注册任何 hook 之前，都必须通过以下关卡：
```bash
bash -n hook.sh                                # syntax
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<trigger case>"}}'    | ./hook.sh; echo "exit=$?"  # want 2
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<healthy lookalike>"}}'| ./hook.sh; echo "exit=$?"  # want 0
```
将测试工具一并提供：[scripts/test_hook.sh](scripts/test_hook.sh) 会运行一整套
触发/放行用例表。**自我阻断陷阱：**一旦 hook 已在会话中启用，你就不能通过把
触发字符串放进你*自己的* Bash 命令来测试它——已启用的 hook 会阻断你的测试命令。
请将用例放入**脚本文件**并运行 `bash test_hook.sh`；外层命令不包含触发字符串，
因此不会自我阻断。

**一旦 hook 引发过一次真实事故（误阻断或静默漏检），
独自重新审阅代码是不够的**——某个 Stop-hook 防护逻辑在同一天重写时，
作者修复第一个 bug 的过程中又两次将其破坏（Python 注释中的一个引号，
重新审阅时无法察觉，只有运行实际失败的 JSON 用例才暴露出来）。此时应升级为
多视角智能体团队审查，每个发现都必须通过针对实际脚本*执行*真实负载来复现，
而不是阅读代码后表示认同——这就是通用的反向审查方法论
（`skill-creator` 的 `skill-development-methodology` 参考资料，第 6 阶段），只是将其
应用于 hook 而不是 skill。在一次这样的审查中，3 个视角（匹配
逻辑 / shell 嵌入安全性 / 事件契约稳健性）发现了 13 个已确认且独立复现的 bug，
以及 1 个其引用证据实际是虚构文档引文的发现——之所以能够识别出来，
完全是因为验证者被要求使用 curl 获取原始来源并 grep 精确字符串，
而不能相信引用。

### 3. 使用 SSOT + 符号链接，避免重新安装悄无声息地解除防护

实际脚本位于受版本控制的目录中，并通过**符号链接**放入 Claude 读取的 hooks 目录：
```
~/scripts/claude-hooks/<name>.sh      # SSOT (this setup: a private git repo)
~/.claude/hooks/<name>.sh             # symlink → SSOT

# install / recover:
ln -s ~/scripts/claude-hooks/<name>.sh ~/.claude/hooks/<name>.sh
```
重新安装 `~/.claude` 会清空 hooks 目录；符号链接目标仍然保留，
只需执行一次 `ln -s` 即可恢复。悬空的符号链接会在**没有任何
信号**的情况下禁用 Tier-0 防护——这正是需要 SessionStart 健康检查的原因（规则 4；
可运行框架：参见 [references/hook_patterns.md](references/hook_patterns.md) 中的模式 C）。

### 4. 注册是按配置文件进行的——收敛所有配置文件，并通过人工关卡放行

- 如果*当前配置文件的* `settings.json` 没有调用 `~/.claude/hooks/` 中的某个钩子，那么该钩子**什么也保护不了**。在所有配置文件都完成收敛之前，多配置文件用户一直处于零防护状态。请先在**主**配置文件的设置中注册（在此设置中为 `~/.claude/settings.json`；[references/hook_patterns.md](references/hook_patterns.md) 的 Registration 一节提供了确切的 jsonc 结构）——PreToolUse → 匹配器 `Bash` → 你的钩子——然后再收敛其余配置文件（此设置使用 `sync-profile-settings.py --all`，由 `claude-switch-models-setup` skill 负责）。SessionStart 健康检查会在每个配置文件中 grep Tier-0 防护，以发现配置漂移。CLI 的文件监视器会自动检测设置修改（依据官方钩子文档），因此注册后无需重启即可生效——可以通过观察防护在安全探测上触发来确认，也可以在下次会话的健康检查行中确认。
- **如果防护需要一个放行阀，请将其设置为*人工*关卡，而不是环境变量。** 静态的 `GUARD_OK=1` 逃生开关算不上关卡——模型可以自行设置该环境变量。请替换为：原生 macOS 对话框（`osascript`——模型无法点击）和/或在 `/dev/tty` 上手动输入 `YES`（模型无法在用户的终端中输入）；拒绝/取消/超时 = 强制不放行；将每次提示/绕过记录到审计文件中。相关模式见 [references/hook_patterns.md](references/hook_patterns.md)。

### 5. 确定失败**方向**，并测试*该方向*——而不只是正常路径

规则 1 对*检测调优*错误进行了优先级排序：假设防护已经运行，那么错误拦截一个正常命令，比漏掉一个罕见的恶意命令更糟，因为需要人们绕过的防护最终会被下意识地绕过。**本规则讨论的是另一个维度——防护机制根本没有运行**——所以这里并不是在颠倒“哪一种更糟”的结论；这两种排序并不冲突。一次调优遗漏只会让你漏掉一个案例；而这里的问题会让你在每一个具有该形式的输入上都静默失去防护。

失败场景是：防护**无法获取它所依据的判断对象**——解析抛出异常、路径无法解析、缺少依赖项或子进程超时——而那个用于防止钩子崩溃的 `2>/dev/null || true`，却悄无声息地将*“我无法检查”*转化成了*“没有需要报告的内容”*。钩子以 0 退出。**这一输出与真正的检查通过完全相同**，正因如此，这种问题可以持续数周而不被发现。

因此，在钩子*获取*某项内容的每个位置（解析命令、读取暂存文件、查询服务），都要明确决定：**如果返回结果为空，这意味着允许还是阻止？**——并将答案写在对应分支旁边。对于*修饰条件*检查，失败时放行通常是正确的（它是否带有 `--no-verify`？漏掉这一点只会损失一个案例）。对于*这究竟是不是目标对象*的检查，失败时阻止通常才是正确的（这是跨域提交吗？空结果意味着防护根本没有触发）。

**然后测试失败方向，而不是正常路径**：刻意向它提供无法解析的路径或无法解析的命令，并断言它仍然执行你所决定的行为。如果测试套件中的每一行都是因为*钩子静默地放行了一切*而通过，那么它与真正通过的测试套件毫无区别。

**请仔细阅读这些结果——对于不同的守卫类别，相同输入对应的正确答案恰好相反。** 以 `cd ~/no-such-dir && TRIGGER` 为例：

| 守卫类别 | 判断依据 | 正确退出结果 | 原因 |
|---|---|---|---|
| **令牌匹配器**（这是否是一种被禁用的命令形式？） | 仅命令文本 | **2，阻止** | `TRIGGER` 就出现在文本中；无法解析的 `cd` 并不会使其不再是触发器，而且如果守卫在这里不作响应，那么面对 `cd ~/real-dir && TRIGGER` 时它同样也会不作响应 |
| **状态推导器**（仓库的暂存集是否跨越多个领域？） | 从磁盘读取的状态 | **0，允许** | `cd` 失败，`&&` 短路，提交根本不会发生——没有任何需要守卫的操作 |
| **终止状态读取器**（补救操作是否已经发生？） | 回执/计数器文件（规则 7） | **0，允许**——*当状态文件本身就是终止条件时* | 无法读取回执意味着钩子无法知道自己是否已触发过；此处采用失败时关闭的策略会永远阻止操作，既不可能进行补救，也没有任何用户可见的原因——这*就是*循环，而且这是唯一一种比漏掉某个情况更糟的失败。**反向子情形——复制这一行之前请先阅读：**当状态只是叠加在独立判定条件之上的**预算**时（完成相应工作后，阻止仍会解除），无法读取时允许操作会**悄无声息地禁用整个钩子**——只要有一个不可写目录，它就会对所有输入永远保持沉默，这是最糟糕的失败形态。在这种情况下，应回退到*预算存在之前的行为*（继续评估判定条件），而不是保持沉默。**用一个问题区分二者：如果状态消失，补救是否仍然可能？** 否 → 回执情形，允许。是 → 预算情形，继续检查 |

因此，请在编写这一行*之前*确定你的钩子属于哪一类；测试工具的
`unresolvable path` 模板行预期结果为 **2**，因为该模板针对的是
令牌匹配器类别。把这一点弄反，会对一个正确的守卫信心十足地判定 FAIL。
对于状态推导型守卫，你要寻找的失败是：**命令实际上会运行，但守卫没有发现它**
——不配对的引号会导致令牌化抛出异常，回退逻辑会允许操作，于是真正的跨领域提交
在没有任何对话框提示的情况下被提交（规则 1 中关于
ValueError 的说明）。对于每一条允许操作的测试行，都要问：*这条命令实际上会执行该操作吗？*
如果不会，那么允许就是正确的。

对一个真实的状态推导型守卫运行这项精确探测时，第一次得到两个允许结果：
其中一个是正确的（即上述短路情形），另一个则是真正的失败时开放。
**探测会发现问题；但你仍然必须对发现的结果进行分类**
——这正是上面的类别表要放在测试行之前的原因。

真实案例（2026-07-22）：一个作用域守卫通过 `git -C "$REPO_DIR"`
读取暂存文件，而 `REPO_DIR` 是从**命令文本**中解析出来的——因此，
`cd ~/repo && git commit` 会向它传入字面值 `~/repo`，导致 `git -C`
失败，返回的暂存集为空，于是守卫得出“没有跨领域文件，允许”的结论。
所有跨仓库提交都在没有守卫的情况下完成，而且一切看起来始终正常。
问题结构 + 共享库转折：陷阱 #10。

该解析器还有第二种失败方向，而且更棘手。一旦你添加回退机制，使它不再以开放方式失败，该回退就会因为一种原因而正确、又因为另一种原因而错误——而两者打印出的内容完全相同。`git push`（没有显式目标）合理地回退到事件的 `cwd`；`git -C "$R" push` 则*指定了*一个钩子无法解析的目标，于是回退到同一个 `cwd`，然后信心十足地为另一个仓库呈现 ✅。这两种情况呈现出的内容逐字节完全相同（经测量，MD5 相等），因此无论是钩子还是读者，都无法区分诚实的判定与错误绑定的判定。**回退值必须携带选择它的原因**，并且只有“没有显式目标”才有资格获得判定。完整剖析、混淆代理视角，以及为什么包含字面路径的固件永远无法发现它：陷阱 #28。

### 6. 根据世界能够回答的事实进行判断——绝不要根据你自己的呈现结果，也不要根据命名习惯

规则 1 和规则 5 讨论的是*如何*匹配以及失败时*偏向哪一边*。本条规则讨论的是**用于匹配的对象来自哪里**，它有两种都会悄无声息发生的失败形态：

- **绝不要根据为人类格式化的字符串进行分支判断。** 如果钩子构建了一份报告——经过排序、拼接、截断为前 N 项，并在末尾附加 `(+M more)`——然后针对这份报告对自己的决策执行模式匹配，那么该分支也会继承呈现过程中的信息损失。超出截断点的项目对它而言根本不存在，因此该分支能在每个小型固件上正常工作，却恰恰会在它原本要处理的大型会话中停止触发。应通过独立通道发出供机器使用的事实（一行未经截断的 `KINDS:a,b,c`），并匹配*它*。呈现结果是输出，而不是数据源（陷阱 #12）。
- **应优先采用可核查的事实，而不是命名约定。** 根据路径形态（`/skills?/[^/]+/references/`）进行分类，只编码了一种目录布局；采用其他任何布局的仓库都会被分类为 `None`——悄无声息，而且永远如此。修复方法*不是*扩大模式范围，因为这会用悄无声息的漏判换来整个机器范围内的误报（规则 1 明确禁止这种取舍）；正确做法是提出一个文件系统能够回答的问题——*这个 `references/` 目录旁边是否存在 `SKILL.md`？* 事实能够经受布局变化；约定则不能。（当候选项**本身就是** `SKILL.md` 时，并不存在可供检查的同级对象——此时应按基本名称分类；#13 解释了为什么这是规范定义的事实，而不是本规则所警告的命名习惯。）
  **可核查的事实仍可能是错误的事实——应锚定问题并按类型过滤。** `test -f SKILL.md` 在下载文件夹中也会为真；曾有一个防护逻辑向上遍历祖先目录来寻找这个文件，结果吞掉了整个主目录，随后告诉一个真实会话去加载一个以该目录命名的技能——而这个名称根本不可能存在（规则 9 中的事故）。应锚定到某个*特定*目录的同级位置，或锚定到已知安装路径；未锚定的祖先遍历，不过是披着事实外衣的约定。

这两类问题都有一个征兆：某个分支在生产环境中一次也没有触发过，而测试却始终为绿色。打印格式化之前的原始分类结果，你就会看出自己遇到的是哪一种。

### 7. 如果钩子**要求补救**，请证明循环会终止

一个在 X 完成之前始终**阻塞**（退出码 2）的钩子——尤其是 Stop 钩子，因为它们会在之后每次停止时重新触发——并不是检查，而是一个**反馈循环**。（如果钩子只是*注入*一项要求并以退出码 0 退出，则根本不存在循环：没有任何东西会重新求值。这就是下文的机制 0，而且它作为正确默认选择的适用场景，远比人们通常认为的更多。）

```
condition T is true → hook demands remediation R → model performs R → T checked again
```

**如果完成 R 可能使 T 再次为真，那么该循环就不会收敛。** 没有错误，也没有崩溃；它只会一轮又一轮地消耗资源，直到有人介入——而这通常正是最终结果，因为每一轮都是一个*完整的*补救周期（分派、等待、采纳、编辑），而不是一次廉价的重试。**也正是由于这一特性，运行框架的连续阻塞 8 次上限无法救你：每当一次延续过程执行了工具时，它的计数器都会重置，因此，由工具调用组成的补救周期会让计数器永远停留在 1**（实测——#27）。即使这个上限确实被触发，它也只是防止会话失控的最后保障，而不是一种设计：该轮会在违规状态仍然存在时结束，而且运行框架会将该轮报告为 `reason:"completed"`——与真正完成时无法区分。“它最终会停下来”并不是任何你所期望意义上的终止，而在这里，它甚至根本不会最终停下来。`stop_hook_active` 在这里也*救不了*你——该字段只覆盖**一层重入**（“我刚刚阻塞的停止正在重试”）。它完全没有涵盖*跨轮次*的情况：模型确实离开并执行了 R（真正的工作、大量工具调用），然后自然停止；这是一次全新的 Stop，该字段为 `false`，而钩子会基于相同理由再次触发。

**该测试借鉴自程序验证中的终止性证明**——即[循环变式／秩函数](https://en.wikipedia.org/wiki/Loop_variant)：写下一个映射到良基序（通常就是 ℕ）的量 **V**，并证明 **V 在每个 `trigger → remediate → re-check` 周期中都严格递减**。没有 V，就没有终止性证明——不要注册该钩子。

**V 是设计阶段的义务，而不是代码**——你永远不会在钩子中计算它。实际交付的是*谓词*（即下文的机制）；V 则是用来论证该谓词会收敛的依据。把它放在下一位读者一定会看到的位置——脚本头部：

```bash
# TERMINATION: V = 1 - exists(<receipt path>)
# decreased by: R writes the receipt; nothing R does afterwards can remove it.
```

“证明它会递减”可归结为三个具体问题，而答案应写入该注释：

1. **R 会改变什么？** 指明确切的文件／字段／时间戳。
2. **该对象是否为 T 的操作数？** 如果是，而且 R 会使其重新朝着“触发”方向移动 →
   那么 V 不存在。
3. **执行 R 后，能使 T 再次为真的最小输入是什么？** 如果答案是“我刚刚触发时所用的同一个输入” →
   那么 V 不存在。重新设计谓词；不要重新调整阈值。

**一个真实的反例。** 某个 Stop 钩子要求，在合并产物（规则文件、技能、其他钩子）可以推送之前，必须进行独立审查：

- **T**（使钩子**触发**的条件）=“存在尚未被任何审查覆盖的编辑”，通过时间戳比较
  `last_edit > last_review` 实现（`last_edit` = 工件集合中最新的 mtime，
  `last_review` = 审查记录的 mtime——两个单一数值，这恰恰使这个比较看起来很安全）
- **R** = 派遣一个独立审查者

但一次值得执行的审查**会有输出**：其发现的问题会由**同一个智能体立即采纳，
而且是在它下一次尝试停止之前** → 这会产生新的编辑 → `last_edit` 晚于 `last_review` → **T 再次为真**。（如果稍后由人工在流程之外采纳这些发现，就不会形成循环——这个循环要求补救和重新检查发生在同一个智能体轮次内，而这恰恰是 Stop 钩子所保证的。）这里不存在 V——补救不会减少某个量，而是会*重置*
一个量。唯一的逃逸路径是“审查，然后什么都不改”，但这恰恰意味着派遣审查者毫无意义。实际观察到：连续三轮，每轮都是完整的审查并采纳周期，直到用户说停止才退出。

有两点使这个问题很难被察觉。**孤立来看，这个比较完全合乎情理**——“审查必须比最后一次编辑更新”正是你会写下的条件。而这句话描述的是**通过**条件——T 是它的否定。如果你把这句话原样记在脑中，却忽略了这个否定，那么在后续分析中，你推理的就会一直是错误的操作数；请始终把 T 定向为**触发**
条件。（将*代码*写成提前退出的守卫子句——`… && exit 0`——是正常的 shell 风格，这里讨论的并不是这个；这里的准则关乎你采用哪个方向进行推理。还要注意相等的情况：同一秒内的 mtime 会落在通过的一侧，也就是故障开放，这与下文这条规则对状态读取的要求一致。）运行上面的检查清单，结论就会机械地显现出来：R 改变了 `last_edit`（Q1）；`last_edit` 是 T 的一个操作数（Q2）；能够让 T 再次触发的最小输入就是补救自身的输出（Q3）→ 不存在 V。

**第二种失败形式：谓词根本看不到补救（可观测性缺口）。**上面的反例是一个会被补救*改变*的时序谓词。同一类问题还有一种更隐蔽的失败：补救确实发生了，但在当前环境中，谓词用于读取它的通道并不存在。真实案例（2026-07-26，在一次全体循环审计中发现）：一个 Stop
钩子通过扫描 tool_results 中的
`agentId: <hex>` 并读取 `subagents/agent-<hex>.jsonl`，来检测“是否发生过独立审查”——这在主配置中是正确的。团队模式会话使用的是完全不同的模式（生成回执为
`agent_id: <name>@session-<uuid>`，交付记录是 `teammate_id`
队友消息，文件为 `agent-a<name>-<hex>.jsonl`）——永远都是零匹配，因此
`last_review` 永远保持为 `None`，而每个复合编辑∧推送轮次都会重新触发这一要求：这是一个误报循环，在每个停止序列内最多阻塞一次，但跨轮次则没有上限；而且该会话中的“2/2 次触发”都发生在已被充分审查的工作上。同一家族，不同的药方：时序循环需要更好的*谓词*；可观测性循环需要更好的*通道*。在检查清单中添加第四个问题——**Q4：在这个钩子将运行的每一种环境中，谓词是否真的能够看到 R 发生？**对于读取转录记录的钩子，这意味着要解析每种配置/模式下的真实会话，而不是只针对一种模式做固件测试。（上述案例的修复方案：
多模式检测 + 将队友交付排除在轮次边界之外，以免它们截断检测窗口——陷阱 #20。）

**先按轴选择，再按顺序选择——这不是同一事物的五种强度。**
0 决定*是否要阻断*；1 决定*将其挂在哪个事件上*；2–4
是*谓词的形态*（选择 1 后，仍然需要从 2–4 中选择一个）。0→4
的顺序表示“循环被移除得有多彻底”，并且它与**你能实施多强的约束成反比**
——因此，应选择第一个仍能提供你实际所需约束的机制，而不是简单地选择第一个。

0. **不要阻断——注入。** 如果要求只是建议性的（你希望模型
   *考虑* R，而不是让它不完成 R 就无法结束），打印该要求并以 0 退出。
   不会进行重新求值，因此不存在需要证明会终止的循环。对于任何低于 Tier-0
   的事项，这都是合适的默认选择，而代价也很明确：提醒可能被忽略，
   因此请在标题中说明它是故障开放的——规则 4 的要点仍然成立：
   如果主体可以直接绕过一个门禁，那它就不是门禁。如果你需要的是*门禁*，请使用 2，
   并承担生成凭据的成本。注入通道：模式 D。
   ⚠️ **此选项在 Stop 上不存在**——而规则 7 的主要讨论对象*就是*
   Stop，所以在尝试使用它之前请先读清楚。在 Stop 上，`exit 0` 意味着“允许
   当前轮次结束”，因此之后不会再有推理步骤来接收这段文本；并且
   `hookSpecificOutput.additionalContext` 与 `exit 2` 一样计入同一个 8 次阻断上限
   （参见钩子类型一节），也就是说，它同样属于阻断。Stop 恰好只有两种模式：
   门禁，或静默。因此，在 Stop 上选择机制 0 意味着**更改事件**
   ——将注入挂到生成该制品的工具调用上（PostToolUse，模式 D）——或者承认你终究
   想要的是门禁，然后转到机制 2。
   ⚠️ **“无循环”仅在 R 不是你自己的匹配器目标时成立。** 一个作用于
   `Bash`、并告诉模型运行 `git ls-remote` 的注入器，会在这条命令本身上再次触发，
   并再次注入。形态相同，但更温和——模型可以忽略它，因此不存在强制迭代，
   但它会在每次重复时广播，而非什么都不做。请检查你所建议的 R 是否不是
   此钩子会匹配的操作。

1. **将检查移到操作边界。** 如果你想门控的是一个
   *操作*——推送、发布、删除——请使用 PreToolUse 来保护**该操作**，
   而不是使用 Stop 来保护**当前轮次**。**Stop 钩子的补救循环，往往是挂在错误事件上的操作门禁**，
   这正是钩子类型一节中“Stop 是异类，也是最常被误用的那个”这一说法的具体情形。
   **请准确理解这样做能带来什么。** PreToolUse 只会在模型
   *主动重试受门控操作*时再次触发，而模型始终可以选择放弃并正常结束当前轮次。
   因此，它能保证**当前轮次终止**——最坏情况从“当前轮次无法结束”降为
   “此操作不会发生”。但它**不会**让一个不收敛的谓词变得收敛：以上面的反例为例，
   将其原样移到 PreToolUse，循环仍会完整保留（推送 →
   被阻断 → 审查 → 采纳发现的问题 → 进行新的编辑 → 重试 → `last_edit` 再次领先
   → 被阻断）。该情形的问题出在它的**谓词**上，而不是事件上，因此
   你仍然需要从 2–4 中选择一种形态。另请注意，PreToolUse **没有**测试框架的兜底机制
   ——钩子类型表中的 8 次阻断上限仅适用于 Stop——所以将一个会自我重置的谓词移到这里，
   安全网反而会*更少*，而不是更多。
   ⚠️ 在以下两种形态中，此机制并非正确答案：**R 必须使用你所门控的那个工具来完成**
   （在 `Edit` 上设置门禁，并要求你先修复文件头——这会造成死锁，任何操作都永远无法满足它），
   以及**在一次会话中重复发生的操作**（在需要推送五个仓库的会话中设置 `git push`
   门禁 = 五次完整要求；这就是下文事故复盘中的密度问题，
   而机制 1 并不能让你免受这个问题影响）。

2. **将“已修复”定义为存在性事实，而非时间性事实——并以需要修复的对象作为键。** 让 R 生成一个制品，然后测试它*是否存在*；键是这一机制能够奏效的关键：

   ```bash
   KEY=$(git rev-parse HEAD 2>/dev/null || printf 'nogit')   # or a hash of the
   RECEIPT="${TMPDIR:-/tmp}/my-guard.${KEY}.ok"              # reviewed content
   [ -f "$RECEIPT" ] && exit 0            # V = 1 - exists, for THIS key
   ```

   `V = 1 - exists` 是**按键计算的**：对于每个键，它只会恰好减少一次，并且对于*该键*永远无法再次升高。新的工作会生成一个*新*键——这是新的需求，而不是重新触发。两种简单粗暴的键策略都会失败：使用单一全局路径，会使钩子在每台机器上只触发一次，之后便永远失效、毫无信号；使用基于时间的键，则正是本规则旨在禁止的时间谓词。**时间谓词几乎总是错误的形式**，因为你所要求的修复通常正是会改变被比较操作数的因素。
   ⚠️ 如果**模型**能够创建回执，那么这只是规则 4 中已经淘汰的 `GUARD_OK=1` 逃生通道换了顶帽子。应让不受模型驱动的某个机制写入它（评审子代理自己的输出文件、git note），或者承认该钩子只是建议性的，并在其文件头中明确说明。

3. **限制重复次数。** 每个会话、每个目标最多提醒 N 次——`session_id` 是唯一稳定的键（每个事件中都有该字段；参见“模式参考”中的 JSON 契约）：

   ```bash
   SID=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('session_id','nosid'))" 2>/dev/null || echo nosid)
   CNT="${TMPDIR:-/tmp}/my-guard.${SID}.count"
   N=$(cat "$CNT" 2>/dev/null || echo 0); N=$((N+1)); printf '%s' "$N" > "$CNT"
   [ "$N" -gt 3 ] && exit 0                # V = 3 - N, reaches 0 and stays
   ```

   这种做法很粗糙，而且刻意不管 R 是否真的发生——但它是*有限的*，而这正是之前缺失的性质。**不要**用 `$$` 或 `$PPID` 替代：每次运行钩子都会启动一个新进程，因此这些值每次调用都会变化，计数器永远无法累积。输出计数（“第 2 次提醒，共 3 次”）——参见下方的实战故事，了解为什么这种措辞值得保留。

4. **滞回／冷却窗口**（控制理论对[告警抖动](https://utcc.utoronto.ca/~cks/space/blog/sysadmin/HysteresisMeaningAndAlerts)的解法）：触发后，在一个时间窗口内禁止重新求值——使用一个时间戳文件，再加上 `[ $(( $(date +%s) - <stamp mtime> )) -lt 900 ] && exit 0`（在 BSD/macOS 上，mtime 使用 `stat -f %m`；在 GNU 上使用 `stat -c %Y`——此处其他代码片段也是如此）。它适用于*在阈值附近振荡*的条件；但对于修复会将条件**重置**的情况，则是**错误**的选择——这类情况需要机制 2 或 3。
   ⚠️ **滞回不提供 V——它是限速器，而非终止性证明。** 只有当条件自行消退时，循环才会结束；此时终止循环的是外部世界，而不是你的钩子。因此，其 `# TERMINATION:` 行必须指出那个外部事实（“时间戳到期时，X 已由 &lt;谁&gt; 解决”）。如果你无法诚实地写出这一行，那么你需要的是机制 2 或 3。（有一种值得注意的家族相似性：机制 0 是两者的极限情况——要么是将上限设为 0 的机制 3，要么是将窗口设为 ∞ 的机制 4。它们的差异在于执行方式，而非终止性。）

**状态本身的失败方向（规则 5）：开放式失败。** 如果回执
或计数器无法读取或写入——`TMPDIR` 不可写、沙箱限制、磁盘已满——
**允许停止**。这是该技能中唯一一个必须采用开放式失败而非酌情判断的地方：
一个无法读取自身状态却仍然阻止终止的终止机制，*本身*就是循环，
而且现在没有任何人类可见的原因。

**要求文本中的文字说明不能替代收敛谓词。** 如果某个
钩子的消息写着“如果你判断没有必要这样做，只需再次完成即可”，那么每一轮仍然
会耗费一个完整的修复周期，因为一个被告知必须执行 X 的模型通常就会执行 X。
逃生出口必须位于**谓词**中，而不是建议中。

**测试要求，以及这里最容易遗漏的部分：** 自测试
需要包含一个**“修复后”**用例——不能只测试“应该触发时会触发”，还要测试
**“R 完成后便不再触发。”** 如果没有这个用例，非终止在
*结构上是不可见的*：每个固件都只是一个孤立的时间点判断，
而非终止是**序列**的属性。一个只检查单个时间点的测试套件，
无论包含多少用例，对收敛性的覆盖率都是零——这就是为什么一个钩子可以
在自测试全部通过的情况下发布，却在首次真实运行时陷入循环。
能够观察到这一点的行对（回执不存在 → 触发，
回执存在 → 静默，而其设置/清理过程无法用普通 `run` 行表达）
已在 `scripts/test_hook.sh` 的 "AFTER-REMEDIATION ROWS" 下提供模板；症状 →
原因 → 修复见陷阱 #16。

**已证明终止 ≠ 它*让人感觉*已经终止（2026-07-25 实战记录）。** 一个使用
正确存在性事实 V 的 Stop 钩子在一个会话中触发了三次——每次触发都是由
一个*不同的*已完成任务带来的合理*新*推动，机制完全按设计工作——但用户的
体验仍然是“为什么这个东西像是卡在循环里了？”（这与机制 2 中的
“R 所做的任何事情都无法将其推回上方”并不矛盾：**V 是按键区分的**——
三个不同的键，三次彼此独立的单向递减。这也是当你无法判断自己面对的是哪种
情况时的诊断方法：如果每次触发都带有一个*新*键，则机制是正确的，问题在于
触发密度；如果重复触发共享*同一个*键——或者谓词根本没有键，因为它比较的是
时间戳——那么你遇到的就是上面的反例，需要替换该谓词。）三个彼此独立的修复周期
接连发生，从外部看与循环无法区分。变体证明解决的是机制问题；它并不能说明
**一个会话可能要求多少次不同的修复**。如果你的领域会产生这样的密度
（这里的复合产物每天会发布数次），请考虑将机制 2（存在性事实）与
机制 3（会话范围的上限）搭配使用，或者有意接受这种观感，并在钩子的输出中
明确说明——“提醒 2，最多 N 次”看起来是在取得进展，而没有任何说明的重复
看起来就像循环。**（2026-07-26 后续：这个钩子中那些看起来像是密度问题的
触发，后来发现 100% 都是误报——它的审查通道在团队模式下无法感知 schema；
请参阅上面的可观测性表单。在接受这种密度是“合理的”之前，请先确认这些触发
确实都有证据支持。）**

### 8. 等待也需要同样的证明——通知仅供参考，轮询必须有预算

规则 7 涵盖了由*钩子*创建的循环。同样的模式也会在没有钩子参与时反复出现：**智能体轮询异步结果**——例如子智能体的报告、后台任务的完成通知、CI 状态。真实会话（2026-07-25）：子智能体的完成通知通过一个可能延迟或丢弃消息的邮箱传递；三个不同的智能体都已完成工作，但通知却一直未送达，而等待中的智能体在约 40 分钟内白白执行了十几轮 `sleep 240` + 催促，直到人类询问它究竟在做什么。没有任何错误发生；这个循环只是没有变元。

规则 7 的机制同样适用——前两项可以直接对应；迟滞在这里没有对应项（等待不会振荡），它的位置由一个等待特有的陷阱取代：

1. **轮询产物，而不是通知。** 如果你真正需要的是某个结果（文件、git ref、API 状态、数据库中的一行），就等待*它*，而不是等待“它是否说自己已经完成”。通知是提示；产物才是事实。无论消息是否送达，只要事实落地，存在性检查就会立即终止。
2. **每次等待都必须有预算，并在编写循环时确定。** 最大轮数 × 间隔（例如 3 × 4 分钟），以及在第一次休眠*之前*就已存在的降级路径：自己完成、询问用户，或者将其标记为待处理并继续其他工作。“无限期等待看看”不是降级路径——它就是这个循环本身。
3. **传递协议仅供参考，并非机制。** “完成后通过 SendMessage 报告——沉默视为未完成”值得写下来，但它约束的是智能体是否*发送*，而不是邮箱是否*送达*。在一次会话中，三个提示词里都包含该协议的智能体全部陷入了沉默。设计等待时，应假设通知可能永远不会到达——因为它确实可能不会到达。

还有两个相邻的陷阱，都在同一次会话中付出了代价：**对一个实际上正在工作途中的“卡住”智能体执行 TaskStopping**——邮箱延迟不代表智能体空闲；一名审查者正在进行 20 分钟的真实语料库测试，却在即将提交结果的几分钟前因被判定为“卡住”而遭终止。另一个是**对等待本身进行 `--dry-run` 式探测**：在断定另一端保持沉默之前，先确认你自己的观察通道能够正常工作（在那次会话中，System Events 窗口计数对一个明明显示在屏幕上的对话框自信地返回了 0——权限故障伪装成了证据）。

### 9. 固定测试数据无法告诉你误报率——注册之前，先重放真实命令语料库

规则 1 对*哪种*错误更糟进行了排序（误拦截比漏拦截更糟，因为一个必须由人们绕过的防护会让人形成条件反射，直接绕过它）。规则 2 要求你在注册之前进行测试。二者都没有告诉你**误拦截面究竟有多大**——而测试表也无法告诉你，因为*你是依据生成检测器的同一个心智模型来编写其输入的*。其中的测试用例包含你想到的形式；按照其构造方式，你没想到的形式必然不存在。这不是一个可以通过增加行数来弥补的覆盖缺口。

**实测于 2026-08-06。** 一个 PreToolUse/Bash 防护钩子通过了一张包含 26 个用例、并对其运行了 5 个变异的测试表，随后被注册启用。之后，使用从最近 60 份会话记录中收集的 **11,903 条去重真实命令**进行重放：其中 143 条生成了候选项，线上钩子阻止了 46 条；对全部 46 条进行人工核查后发现，**有 10 条阻止错误——占其阻止总数的 21.7%**（两个边界情况被计为正确；若作相反判断，则约为 30%）。在 39 分钟内，它已经阻止了 3 个真实会话，其中一个会话被告知去加载一个根本不可能存在的技能——也就是下文的第三个缺陷，它以指向不存在目标的补救指导形式暴露出来。该钩子在同一小时内被移除。三个根本缺陷全部位于**解析**层：将续行符读取为分隔符；在分段扫描中把 heredoc 正文和数据参数计作执行内容；以及路径分类器没有类型过滤器。

这个故事并不能支持两种结论。它**并不**意味着“变异测试不起作用”：后来对同一套测试的审计发现，**钩子逻辑中有 5 处即使删除，全部 26 行测试仍然为绿色通过**；而且，有一行被作者标注为“已从装饰性测试修复”的测试实际上仍然只是装饰——*“我运行了变异测试”并不等于“变异测试是正确的”*，正是重放同时暴露了这两点。它也**并不**意味着“你不可能事先知道”：这些缺陷中有三个，是对本文件已经提供的代码进行手工重新实现所导致的（`split_shell_lines`、命令位置遍历，以及 `is_git_write` 对 `-C` 及其参数的处理）。规则 1 中*原样使用遍历器*才是那个成本更低却被跳过的修复方案；重放是最后的保障，而不是第一道防线。

**该方法包含四个步骤，而第 2 步正是经常被跳过的那一步：**

1. **收集。** 会话记录位于
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`，此外还包括在
   `~/.claude/history-sources.json` 中注册的所有归档。命令是 `.message.content[]` 中
   `type == "tool_use"` 且 `name == "Bash"` 的条目，位于字段 `.input.command` 中——**不是**钩子
   事件中的 `.tool_input.command`，后者具有不同的数据结构。进行去重，并选取足够多的
   会话记录，确保其中涵盖你自己近期使用过的工作形式（那次运行使用了 60 份）。
2. **使用随附的检测器进行预过滤，并将其原样切出**——绝不要使用手写的
   等价实现，否则你测量的只是自己两种猜测之间的一致程度。预过滤仅用于降低成本
   （11,903 → 143）；真正作出判断的是第 3 步。如果检测器不是一个可独立提取的代码块
   ——例如它是 shell，或被拆分到一个通过 source 引入的库中——就把它改造成这种形式；
   无法独立运行的检测器，同样也无法进行单元测试。
3. **将每个候选项连同其真实会话记录和 `session_id` 一起提供给真实钩子。**
   读取会话状态的防护钩子在伪造上下文中会给出不同答案。事件契约：
   `references/hook_patterns.md`。有两件事会带来麻烦——应在临时的
   `TMPDIR` 下运行，否则规则 7 的回执和每会话计数器会写入真实会话，*并且*
   在测量进行到一半时让防护钩子停止响应；另外，如果钩子包含人工确认关卡，应通过
   模式 B 的强制拒绝路径来驱动它，而不是回答 143 个对话框。
4. **人工核查每一条阻止记录——阻止列表就是误报测量结果。** 放行
   列表回答的是规则 5 的问题（它保持安静，是因为那里什么都没有，还是因为它看不见？）；
   而返回*零条*阻止记录的重放，应当让人怀疑测试工具本身，而不是把它当作一份无问题证明
   ——陷阱 #11 针对漏触发方向规定的也是使用同一种检测手段。

**如何处理这个数字。** 如果某个误拦截给出的补救指导错误或无法执行 → 完全不要注册：这种模式正是规则 1 旨在防止的反射式绕过产生流程。否则，将拦截列表视为修复列表，修复后重新回放。误报通常会集中在**你编写守卫时正在做的事情**上——那次运行中有一半的误报落在钩子开发文件上，因为作者那周正在构建钩子。还要专门扫描拦截列表中的**运维操作**（编辑钩子目录下的文件、对钩子运行 `bash -n`、守卫自身的 SSOT）：如果一个守卫会拦截移除自身的操作，就无法在会话内部将其关闭（#25——那个守卫甚至拦截了注销它自身的命令）。

说明一下工作量，以免这看起来像一个研究项目：一次采集加一轮循环，实际耗时只需几分钟。

## 构建顺序（按顺序执行）

1. **确认它确实会重复发生**，而不是假设性问题——否则不要构建。
   如果钩子将**要求执行补救措施**，而不只是进行拦截，请在编写任何逻辑之前，先将其终止变元 **V** 作为 `# TERMINATION:` 行写入脚本头部
   （规则 7）——并且首先检查你要设门禁的对象是否是一个*操作*；如果是，那么针对该操作设置 PreToolUse 守卫可以直接消除循环，而不是设法约束循环。如果无法指出一个在每次
   `trigger → remediate → re-check` 循环中严格递减的量，那么该设计不会终止——应该修复设计，而不是正则表达式。
2. 在 SSOT 目录中编写脚本；执行 `chmod +x`。
3. 使用 shlex 进行词法单元级匹配来实现**检测**（规则 1），匹配依据应是现实世界能够回答的事实，而不是你自己的渲染结果或命名约定（规则 6）。
4. 运行 **`bash -n` + `test_hook.sh`**，同时包含触发用例和外观相似的健康用例（规则 2）——在测试通过之前不要注册。应包括含有未展开路径的形式（`cd ~/elsewhere && …`，规则 5）；如果钩子设有人为门禁，应包含强制拒绝行（模式 B，“让门禁可测试”）；如果它要求执行补救措施，则应包含**补救后的成对测试行**——没有回执时触发，有回执时保持安静（模板位于 `scripts/test_hook.sh`；规则 7——时间点式夹具在结构上无法发现不终止问题）。
5. **回放真实命令语料库，并手动检查每一次拦截**（规则 9）——这会测量误拦截面，而步骤 4 中的夹具表在结构上无法做到这一点。逐字提取已发布的检测器用于预筛选；在临时 `TMPDIR` 下，将每个候选命令连同其真实执行记录和 `session_id` **传给**真实钩子。
6. **创建符号链接**到 `~/.claude/hooks/`（规则 3）。
7. 在主 `settings.json` 中**注册**，并使各配置文件收敛一致（规则 4）。
8. 对于 Tier-0/不可逆操作，添加**人工确认放行门禁**（规则 4）。
9. **持久化**：将 SSOT 提交到其私有仓库。可以选择添加一行 CLAUDE.md（正文说明*为什么*以及替代方案；钩子负责强制执行）。

## 已知陷阱（调试误触发的钩子之前请先阅读）

完整的“症状 → 原因 → 修复”目录：[references/hook_pitfalls.md](references/hook_pitfalls.md)。
主要问题包括：`stdin` 被 `python3 - <<PY` heredoc 消耗（钩子会悄无声息地放行所有内容）、awk 分割导致的误拦截（规则 1）、损坏的钩子污染会话（规则 2）、Python *注释*中的引号或反引号悄无声息地破坏 `python3 -c "…"` 块且不产生语法错误（陷阱 #9——应改用模式 E 中的带引号 heredoc 形式）、静态环境变量逃生通道（规则 4）、多个配置文件注册不完整、提交消息作为伪命令文本传入遍历器，并误拦截用于修复问题的提交，除非豁免 `git` 写入片段（#7）、从命令文本中解析出的路径保留其字面量 `~`，导致守卫在完全没有症状的情况下**开放式失败**（#10——这个问题不能等到被发现，因为沉默是它唯一的迹象）、某个分支读取钩子自身截断后的显示字符串（#12），或依赖该仓库并未遵循的命名约定（#13）——当测试套件只断言退出码时，两者都不可见（#14）——仅仅*包含*重定向的命令文本被算作写入（#15），以及钩子**要求的补救措施会将其重新武装**，从而陷入循环，但自测仍然通过，因为时间点式夹具在结构上无法发现不终止问题（#16，规则 7）。

**测试框架是隐藏变量——使用 `scripts/test_hook.sh`，不要自己手搓。**
下面每一种手搓出来的失败模式，产生的输出都与干净通过时*完全相同*，
因此看起来都是成功的（2026-07-22，在修复某个 Stop 钩子的白名单时一口气遇到了三个）：

1. **错误的事件结构。** Stop 钩子读取 `last_assistant_message` /
   `transcript_path`，而不是 `tool_name`/`tool_input`。传入一个具有 PreToolUse
   结构的事件，它找不到任何文本 → 以 0 退出 → “没有误拦截！”
2. **JSON 引号。** 单引号内的 `'{\"a\":1}'` 会原样输出反斜杠加引号；
   `json.loads` 抛出异常，钩子的 `2>/dev/null || exit 0` 将其吞掉，
   所有用例都“通过”。
3. **规则合理豁免的测试用例。** 基线字符串使用了一个规则*有意豁免*的字符串
   （防护规则会标记形如 `<name> Group` 的自造昵称，但会豁免普通短语
   `in the group` / `group chat`——而基线行碰巧使用了其中一个）。
   原本用于证明防护规则依然会生效的唯一一行并未触发，整个测试套件却显示为绿色。

**而且，如果钩子的产物是其消息，退出码就无法对它进行测试。**
阻断型钩子的契约主要是其退出码，因此 `run` 行足以覆盖它。但如果一个钩子的存在
就是为了*说出*某些内容——例如解释正确替代方案的 PreToolUse 消息、Stop 提醒——
那么它还有退出码永远看不到的第二个输出通道：破坏措辞、颠倒某个条件段落、
让 heredoc 吞掉一个章节，退出码仍会保持为 2，而所有行都会通过。添加来自
`scripts/test_hook.sh` 的 `says <label> <event> <pattern> <yes|no>` 行，
在两个夹具上断言**正反两种情况**（对于它所针对的输入应存在，对于它所跳过的相似输入
应不存在）——如果钩子完全不输出任何内容，单独一个 `want=no` 也会轻易通过，
因此只有当它与证明钩子确实会发声的 `want=yes` 行并列时才有意义。匹配**固定字符串**，
不要使用正则表达式：值得断言的短语经常包含方括号，而作为 BRE，`[skill]` 是一个
字符类，会匹配任何包含 s、k、i 或 l 的文本。然后**通过变异证明这些行确实会失败**：
复制钩子，注入每一行声称要捕获的那个确切 bug，并确认该行变红。在你亲眼看到测试套件
因正确的原因失败之前，全绿的套件不携带任何信息——曾经有两个真实 bug 在一个全绿的
24 用例套件中存活下来，因为每一行都只检查退出码（陷阱 #14）。

共同模式是：**所有用例结果一致是一种坏味道，而不是绿灯。** `test_hook.sh`
会从结构上捕获上面的模式 1 和 2——它要求每个 `run` 行都显式断言
`expected-exit`（而不是“它有没有打印内容”），并强制触发用例行与外观相似的正常用例行
同时存在，因此返回 0 的触发用例行会响亮地失败，而不是混在其中。它
**无法**捕获 #3：某一行的内容是否意外落入豁免范围，是你所编写内容的属性，
任何测试框架都不可能知道规则的意图。只有通过这种习惯才能捕获它——*首先*断言一个
已知有效的触发用例；当它没有触发时，先怀疑测试行，而不是钩子。
