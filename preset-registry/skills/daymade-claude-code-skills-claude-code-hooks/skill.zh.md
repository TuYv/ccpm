# Claude Code 钩子

Claude Code 会在工具调用边界触发 **钩子**。钩子是一个从 stdin 接收 JSON 事件的 shell 命令；对于阻塞型钩子，它通过自己的**退出码**决定工具调用是否继续。这是唯一能够*从结构上*阻止某种行为的机制——CLAUDE.md 中的文字规则只是建议，可能被完成驱动覆盖；而钩子是一堵墙。

## 何时适合使用钩子（以及何时不适合）

当**某条规则即使已经写明，却仍然不断被违反**时，就编写钩子。其典型表现是：你添加了文字规则，规则表述清晰，但相同行为仍然再次发生——因为在采取行动的那一刻，注意力 100% 集中在“把事情做完”上，提醒被忽略了。这种重复发生就是信号：应当将规则从文字（建议）转移到钩子（强制执行）。治理方面的经验法则：*Tier-0 不可逆操作 + 只有文字规则、没有钩子 → 它应该是一个钩子。*
（这里的 **Tier-0** = 在会话内部无法撤销其损害的操作：销毁未提交的工作、将机密推送到远程仓库、删除文件、向外发布某些内容。判断标准是可逆性，而不是严重程度。）

在以下情况下，**不要**急于使用钩子：规则实际上从未重复发生（不要为假设性的错误预先构建防护——没有经过验证的收益，却要付出成本），或者所谓的“规则”是没有机械特征的判断事项（钩子只能匹配令牌/模式；它无法判断一个设计是否优秀）。

如果症状是“它一直在审查 / 等待 / 重试”，不要假设答案是再添加一个钩子。首先完成规则 7 中的 **循环契约**，并阅读[陷阱 #36](references/hook_pitfalls.md#36-a-self-applied-review-rule-can-loop-without-any-hook)。循环可能完全是由代理反复应用文字规则造成的。

## 钩子类型及退出码的含义

| 类型 | 触发时机 | Exit 0 | Exit 2 | 其他 |
|---|---|---|---|---|
| **PreToolUse** | 工具运行前 | 允许 | **阻止**调用（stderr → 作为指导信息显示给模型） | 任何其他退出码 = “非阻塞错误” → **调用继续执行**——但前提是 stdout 不包含有效 JSON。Claude Code 会在**每个**退出码下读取 JSON 输出，而有效 JSON 会完全覆盖退出码。此处的骨架不会向 stdout 输出任何内容，因此其 fail-open 推理成立；如果添加 `permissionDecision` payload，退出码就不再是决定因素 |
| **PostToolUse** | 工具运行后 | 保持安静，**除非它在 stdout 上输出 `hookSpecificOutput` JSON——这就是注入上下文的方式，并且发生在退出码为 0 时** | 向模型提供反馈（无法取消已运行的工具） | — |
| **SessionStart** | 会话开始时 | 继续 | **无法阻止**——stderr 会向用户显示钩子错误通知，Claude 看不到该通知，会话仍然启动 | **无论如何都使用退出码 0**：不是因为非零退出码会阻止启动（它做不到），而是因为任何非零退出码都会在每次会话开始时，将 `<hook> hook error` 放入用户的 transcript 中。它会根据*会话的启动方式*接受一个 `matcher`——`startup`、`resume`、`clear`、`compact`、`fork` |
| **Stop**（+ `SubagentStop`） | 模型即将结束响应时 | 允许其停止 | **阻止停止**——强制模型继续执行（stderr → 作为原因反馈给模型） | 循环安全：钩子会检查 `stop_hook_active`（这是必要条件，**但不是充分条件——参见规则 7**）。harness 的连续阻塞上限（默认为 8）**不是**通用的兜底机制——其计数器会在任何执行了工具的继续操作中重置，因此对于补救措施涉及工具调用的钩子（绝大多数钩子都是如此），它永远不会触发（#27）。请自行设置上限。某个事件的所有 Stop 钩子都会**并行**运行——一次阻塞轮次可能携带多个钩子的反馈 |

- **PreToolUse** 是阻止 *tool call* 的主力工具——此表中的四种类型是本文件讲解的类型，并非所有可阻止事件的完整集合；而 **官方** hooks 参考（docs.claude.com / code.claude.com，而不是此 bundle 中的 `references/` 文件——后者只涵盖上述四种类型）现在列出了更多可阻止事件，包括 `UserPromptSubmit`、`PreCompact`、`TeammateIdle` 以及任务和配置事件。如果你需要门控的不是 tool call，请先去那里查找，而不是强行将其归入 PreToolUse。
  `matcher` 选择工具（`Bash`、`Agent`、`WebFetch`，……）——**而它的匹配方式取决于你使用的字符**：只包含字母、数字、`_`、`-`、空格、`,` 和 `|` 的 matcher 会按**完整字符串**进行比较（或按 `|`/`,` 分隔的完整字符串列表进行比较）；任何包含其他字符的 matcher 都会被视为**非锚定的 JavaScript 正则表达式**。两个方向都会悄悄造成问题——`Edit.*` 也会匹配 `NotebookEdit`（应将其锚定为 `^Edit$`），而 `mcp__memory` 则什么也匹配不到，因为它全部由完整匹配字符组成，且没有工具的名称恰好是它（你需要的是 `mcp__memory__.*`）。匹配区分大小写。退出码为 2 会阻止操作，且 hook 的 **stderr** 会成为模型看到的消息——因此应当在其中写明*原因*和*正确替代方案*，而不只是写“blocked”。
- **PostToolUse** 无法撤销操作，但可以**注入权威上下文**，让后续的幻觉无法成立（例如在提交后重新读取真实的 git HEAD 并将其展示出来——面对注入的事实，模型无法再“相信自己已经提交”）。
- **SessionStart** 用于**检查防护机制本身的健康状态**——健康时保持静默，出现故障时发出警告，并始终退出 0。请注意*原因*：这并不是因为非零退出会阻止会话（它做不到），而是因为这样会在每次会话开始时打印 hook-error 通知，直到有人修复它——一个在启动时频繁误报的检查，最终会让人学会直接滚动略过。
- **`set -euo pipefail` 与 `set -uo pipefail`——应根据契约进行选择，并了解如何保持始终退出 0 的契约有两种方式。** 可能阻止操作的 hook（PreToolUse）需要 `-e`：意外故障导致脚本中止是可以承受的，因为调用方会将非 0/2 的退出码视为“继续”。契约要求**始终退出 0** 的 hook（PostToolUse 注入器、SessionStart 检查）有两种合理形式：(a) **去掉 `-e`**，并对每个有风险的命令使用 `||` 守护——启用 `-e` 后，一个合理地找不到任何内容的 `grep` 就会让 hook 中途终止，而 CLI 会显示一个没有具体信息的 `Failed with non-blocking status code`（陷阱 #8，Pattern E 的形式）；或者 (b) **保留 `-e` 并添加 `trap 'exit 0' ERR`**，这样任何故障都会被转换为退出 0，同时 `-e` 仍会保护管道逻辑（`git-commit-headcheck` 的生产形式，Pattern D）。两者都正确；不能做的是只使用 `-e`，却既没有 trap，也没有 `||` 守护。经验法则：**对于负责决策的 hook 使用 `-e`；对于负责报告的 hook，去掉 `-e` 或为其添加 trap**（陷阱 #8）。
- **Stop 是个特例，也是最常被误用的类型**：它是唯一能够针对模型**自己刚刚生成的内容**（模型自身的回复文本）做出反应的 hook 类型。其他所有 hook 类型——包括听起来似乎适合监管“说了什么”的 `UserPromptSubmit`——看到的都只有**用户**输入；从结构上来说，它无法看到模型在**当前轮次**的自身输出（这一点是成立的——这仍然是将此类规则交给 Stop 的正确原因）。不过，这一保证并不意味着可以证明 `.prompt` 字段始终源自一次键盘输入：后台任务通知自身的报告文本也可能填入其中，而 stdin JSON 中没有任何字段标记二者的差异——#30。像“模型不得为尚未验证的事物自行编造简写名称”这样的规则应放在 Stop 上；如果反而放到 `UserPromptSubmit`，它将 (a) 一次也抓不到它原本要捕获的内容，因为该文本根本不会经过此事件；并且 (b) 每当用户自己的无关输入恰好包含触发模式时，错误地阻止用户输入。这是类别错误，而不是调参问题——在错误事件上进行多少正则表达式优化都无法修复它。完整契约（`last_assistant_message` 与 `transcript_path`、反循环检查）见 Pattern E，位于 [references/hook_patterns.md](references/hook_patterns.md)。
- **Stop 有两个阻止通道，且具有相同的循环保护——应根据意图进行选择，并让第一次（也是唯一一次）阻止携带全部信息。** `decision: "block"` + `reason`，或直接退出 2 + stderr，会显示为 hook *error*——适用于硬性门禁（“这绝不能成立”）。`hookSpecificOutput.additionalContext` 会以中性的“Stop hook feedback”显示，且不会产生错误通知——适用于模型应当权衡的指导和提醒，而不是门禁。两者都会计入上表中的连续阻止上限，因此选择的是语气，而不是安全性。这对消息设计意味着：被阻止的重试轮次（`stop_hook_active: true`）会在**保留所有剩余违规的情况下**放行——因此 Stop guard 恰好只有**一次有效干预机会**。（只有当你的修复方式是“重写回复”时，上限才会进一步强化这一点；如果修复过程涉及 tool calls，计数器会重置，上限永远不会触发——#27。无论如何，这个一次机会的结论仍然成立，因为它依赖的是锁存状态，而不是上限。）应在这一次阻止中报告**所有**发现的问题（只打印第一个问题的 guard 会永久丢失其余问题——陷阱 #17），并将消息写成一份逃生手册，明确指出可接受的精确修复方式，而不是给出判决——模型要么在一轮内收敛，要么就在不断猜测中耗尽上限。v2.1.145+ 的输入 `background_tasks` / `session_crons` 让阻止型 hook 能够区分“会话已结束”和“会话只是暂停、正在等待后台工作”——阻止暂停状态会迫使模型进行无意义的继续操作，并浪费同一个上限。

完整可运行的骨架：[references/hook_patterns.md](references/hook_patterns.md)。

## 骨架（PreToolUse Bash guard）

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS= read -rd '' INPUT || true                 # builtin; NOT $(cat) — see below
# 0-fork fast path: a builtin `case` on the raw JSON, BEFORE paying for python3.
# Your guard runs on EVERY matching tool call, so the irrelevant path is the one
# that has to be cheap. Keep this filter BROADER than what you actually block and
# never flag-level — it answers "is this even about X", nothing finer (#22).
case "$INPUT" in *TRIGGER*) ;; *) exit 0 ;; esac
TOOL=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_name',''))" 2>/dev/null||echo "")
[ "$TOOL" != "Bash" ] && exit 0                # only guard the tool you mean to
CMD=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" 2>/dev/null||echo "")
[ -z "$CMD" ] && exit 0
printf '%s' "$CMD" | grep -qw 'TRIGGER' || exit 0   # precise relevance check
# ... precise detection here ...
if <command actually does the banned thing>; then
  echo "BLOCKED: ... WHY ... USE INSTEAD: ..." >&2   # stderr = the guidance shown
  exit 2
fi
exit 0
```

**前两行并非风格问题。**`INPUT=$(cat)` 加上每个
`printf … | python3 -c …`，会在每次此 hook 匹配时产生进程派生，**包括那些它无话可说的调用**。由约 13 个 Bash-matcher hook 组成的集群，在并行会话和每秒多次的工具调用节奏下，使其持续产生每秒 40–200 次纯 guard 开销，并让 Gatekeeper 在全天 CPU 排名中位居首位，而系统中根本没有任何失控进程——集群本身没有问题；问题在于*无关路径*的单次调用开销（#22，其中包含逐个 guard 的转换方案及其测得的下限）。

在你把 `case` 行复制到其他任何地方之前，有三个注意事项——第一条决定了它究竟是快速路径还是绕过：

- **粗略过滤器必须是你所阻止内容的超集，而原始子字符串测试并不是。**`TRIG''GER -x` 会运行 `TRIGGER`——bash 会在执行前拼接掉引号——但原始事件文本中不包含 `TRIGGER` 子字符串，因此一个裸的 `case "$INPUT" in *TRIGGER*)` 会退出 0，guard 根本看不到它。**实测**：将这条完全相同的行放入已发布的 Pattern A 后，`TRIG''GER -x` 会从退出 2 变为退出 0，形成完整绕过——而 `scripts/test_hook.sh` 仍然报告 21 pass / 0 fail，因为没有任何行带有拼接后的 trigger。Pattern A 已经包含修复及其原因（“去拼接——从副本中移除引号和反斜杠——然后再次检查；误判为否定结果会造成完整绕过”）；放在该去拼接步骤*之前*的粗略过滤器会使其无法到达。按优先级排序，有两种安全形式：
  **过滤无法被拼接操作影响的内容**——JSON key 或 tool name（`case "$INPUT" in *'"tool_name":"Bash"'*)`），因为引号拼接存在于
  *command* 文本中，无法重写事件自身的结构；或者**在过滤器内部去拼接**，然后再进行测试（从输入的副本中移除 `"`, `'` 和 `\`，再进行匹配）。优先选择第一种：它不需要复杂的转义操作；而一个必须把自身引号写对的过滤器，也可能在无提示的情况下被写错。上述骨架按原样使用时是安全的，
  只是因为它自身的检测同样是简单的单词匹配；一旦过滤器下方的 guard 比过滤器更聪明，决定权就在过滤器手里。

- **这个骨架在无关输入上是故障开放的**（`grep -qw … || exit 0`），因此，在它前面加一个粗粒度过滤器改变的是成本，而不是语义。**故障关闭的防护则不同**：一个简单的子字符串过滤器会悄悄地把它的契约从阻止未知输入变成允许未知输入（实测——`'not json'` 直接通过了这个修复的第一轮筛选），而单独使用 `*tool_name*` 标记又会从另一侧重新打开同一个漏洞。在为一个本应阻止格式错误输入的防护套用快速路径之前，先阅读 #22 的门控要求。
- **脚本之上还有一个更便宜的层。** hook 处理器可以在其注册信息中携带一个 `if` 字段——例如 `"Bash(git *)"` 这样的权限规则语法——当它不匹配时，hook 命令**根本不会运行**：因为没有进程，所以也就没有 fork。它的设计就是尽力而为（文档称，当 Bash 命令无法解析时，它会故障**开放**，仍然运行你的 hook），因此要把它视为成本优化，**绝不能把它当作门控机制**——脚本内的检查仍然负责最终决策。这里有三个容易踩坑的地方：它恰好只接受一条规则（不支持 `&&`/`||`），它只会在工具事件上求值，而在非工具事件上设置了 `if` 的 hook **根本不会运行**。

## 区分有效防护与污染会话的规则

这不是风格偏好——每一条都是我们实际发布过、并追溯到根因的具体故障。

### 1. 使用 shlex 在**令牌层级进行匹配**，绝不要对原始字符串用 awk 拆分

一个**错误拦截正常命令的防护，比漏掉目标的防护更糟**——必须绕过的防护会被人下意识地绕过，最终它什么也保护不了（核心原则：*误杀健康输入比漏报更糟*）。错误拦截反复出现的原因，就是在原始命令字符串上进行匹配。


- **错误做法**：使用 `awk '{gsub(/&&|\|\||;|\|/,"\n")}'` 拆分片段——awk 不理解 shell 引号，因此 `grep -E "a|TRIGGER|b"` 会在引号内的正则表达式中的 `|` 处分割，`TRIGGER` 变成一个虚假的命令，防护就会拦截一条普通的 grep。（已于 2026-07-21 发布；这项防护第一次真正使用时，误拦截的就是我自己的 grep。）
- **正确做法**：使用 **`shlex.shlex` 类**对整个命令进行标记化，而不是使用 `shlex.split()` 函数——`split()` 只有在 `| ; & < >` 两侧存在空格时才会将它们视为分隔符，因此 `ls|TRIGGER x` 会被标记化为 `['ls|TRIGGER', 'x']`，你的命令位置检查根本看不到 `TRIGGER`（实测；启用 `punctuation_chars=True` 的类会得到 `['ls', '|', 'TRIGGER', 'x']`）。不要随手写一行代码，而应原样复制已经发布的 walker——但**要复制通过 `scripts/test_hook.sh` 的那个**，也就是 **Pattern A** 的版本。[walker 部分](references/hook_patterns.md#the-shlex-command-position-walker)是一个*紧凑*版本，并明确说明了这一点：它省略了每个 wrapper 的带值标志表，因此无法发现位于**带值标志 wrapper**之后的目标——实测，对于 `timeout 5 TRIGGER`、`sudo -u root TRIGGER` 和 `nice -n 10 TRIGGER`，它会返回“不在命令位置”，而 Pattern A 的版本可以捕获这三种情况。（裸写的 `sudo TRIGGER` 在两者中都没有问题——问题在于 wrapper 自身接收参数的标志，而紧凑表不知道要跳过这个参数。）已发布的测试框架中只包含其中一种形式，因此你实际看到的运行结果是：相对于 Pattern A 版本的 21/0，紧凑版本在 `wrapper-timeout` 上是 **20 pass / 1 fail**；另外两种形式由于没有对应的测试行，会无声地失败。带引号的 `"a|TRIGGER|b"` 会保持为**一个令牌**，因此正则表达式参数不会被误认为是命令。然后检查目标是否位于**命令位置**（`token[0]`，或者紧跟在 `;`/`&&`/`||`/`|` 分隔符之后，同时跳过 `VAR=val` 环境变量赋值前缀）。命令位置 walker 见 [references/hook_patterns.md](references/hook_patterns.md)。
- 推论：`echo "…TRIGGER…"`, `grep TRIGGER`、`# TRIGGER`、`man TRIGGER` 都必须通过。你的测试集**必须**包含这些“提及但未执行”的情况。
- **推论——在它们进入 walker 之前，先豁免 `git` 写入片段。** 提交消息是任意数据，整段消息文本会以伪命令文本的形式进入你的命令位置遍历——`git commit -F - <<EOF` 的正文如果包含引用 `foo|TRIGGER`，就会把 `TRIGGER` 放到命令位置，导致防护拦截它自己的修复提交（陷阱 #7 正是这一问题，且已经发布）。任何检查命令字符串的 Bash 防护，都必须跳过命令头部为 `git` 加上 `commit`/`rebase`/`tag`/`am`/`cherry-pick` 的片段——并且要在整个命令层级执行，先于任何按行拆分（Pattern A 展示了这个顺序；生产版本是 `lib-git-commit-detect` 的邻接检查）。
- **推论——walker 分成两个阶段是有原因的。** `whitespace_split=True` 会把换行视为普通空白，因此多行代码块（`cd /x\ngit add\nTRIGGER -y`）会被合并成一个以 `cd` 为头部的片段，触发器永远不会处于命令位置——在真实记录中重放触发器的命中率为 0（陷阱 #11）。首先以 shell 感知的方式按行拆分（遵守引号状态和反斜杠续行，因此带引号的多行字符串不会被拆碎），然后对每一行执行 shlex walker——Pattern A 和 walker 部分都提供了这个拆分器（`split_shell_lines`，已在 qlmanage-guard 中通过生产验证）。即使这样也无法解析 heredoc 正文（它不是引号语法）；何时接受这一残余风险，要看 #11 的判断。
- **但 shlex 也不是万能药，而且你检测的*对象*会决定故障开放是否安全。** `shlex.split()` 本身会在引号不平衡时抛出 `ValueError`——多行的 `git commit -m "…` 消息中包含 `#` 或未闭合引号，就是典型触发场景。随后使用 `except ValueError: cmd.split()` 回退并*放行*，在检测**被禁止的修饰符**时是正确的（是否携带 `--no-verify`？——漏掉它反而是安全的，符合规则 1 的方向），但在检测命令是否**确实是目标命令**时就很危险（这是 `git commit` 吗？——这里的 `ValueError` 意味着防护永远无法识别这个提交命令，于是静默地不触发；实际就曾有跨域提交因此在没有确认对话框的情况下发布）。对于“这是不是该命令”的判断，应优先使用一种不受多行引号破坏影响的窄范围**正则表达式**（`git` 和 `commit` 作为独立单词，中间可以有任意标志令牌）；将 shlex walker 留给*命令位置 / 修饰符*检查，在这些检查中，故障开放才是安全方向。（边界是：当谓词是“这是否完全是某个特定的常见命令”——`git commit`、`git push`——而该命令自身的消息/参数会破坏标记化时使用正则；当谓词是“命令位置中是否存在一个*被禁止的*命令或修饰符”时使用 walker——此时被禁止的对象很少见，而 `ValueError` 导致的故障开放反而是安全的，符合规则 1 的方向。）

### 2. 在**注册之前，端到端地使用 `bash -n` + 真实 JSON 事件进行测试**

**损坏或逻辑错误的 PreToolUse hook 会污染整个会话** —
后续每一次 Bash 调用都会被截断 / 重复 / 错误判定为失败 / 看起来像是幻觉式执行，而你会把责任归咎于“环境”，实际上问题出在你刚刚安装的 hook 上。（2026-07-05：一次编辑中 `[^;&|]` 正则表达式被破坏，`;&` 变成了 bash 的 case-fallthrough 标记，导致半个会话受到污染，直到 `bash -n` 找到了问题。）“部署时测试通过”还不够 — 文件可能在**之后的编辑**中被破坏。

在注册任何 hook 之前执行以下检查：
```bash
bash -n hook.sh                                # syntax
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<trigger case>"}}'    | ./hook.sh; echo "exit=$?"  # want 2
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<healthy lookalike>"}}'| ./hook.sh; echo "exit=$?"  # want 0
```
将测试 harness 一并纳入：[scripts/test_hook.sh](scripts/test_hook.sh) 会运行完整的触发/放行用例表。**自阻塞陷阱：**一旦 hook 在会话中生效，就不能通过在你自己的 Bash 命令中放入触发字符串来测试它 — 生效中的 hook 会阻止你的测试命令。将用例放入**脚本文件**，然后运行 `bash test_hook.sh`；外层命令本身不包含触发字符串，因此不会被自身阻塞。

**一旦某个 hook 导致过一次真实事故（误阻止或静默漏判），仅靠独自重新阅读代码是不够的** — 某个 Stop-hook guard 的当天重写过程中，作者在修复第一个 bug 时又两次重新引入了 bug（Python 注释中的一个引号，在重新阅读时不可见，只有运行实际失败的 JSON 用例才暴露出来）。此时应升级为多视角的 agent-team review，其中每个发现都必须通过对运行中的脚本执行真实 payload 来复现，而不能仅仅通过阅读代码并达成一致 — 这就是通用的 Counter Review 方法论（skill-creator 的 `skill-development-methodology` 参考文档，第 6 阶段）在 hook 上的应用，而不是在 skill 上的应用。在其中一次审查中，3 个视角（匹配逻辑 / shell 嵌入安全性 / 事件契约健壮性）发现了 13 个经过确认且独立复现的 bug，以及 1 个其所引用证据最终被证明是虚构文档引文的发现 — 只有因为验证者被要求 curl 原始源码并 grep 完全匹配的字符串，而不是相信引用，该问题才得以发现。

### 3. 使用 SSOT + symlink，避免重新安装时静默解除防护

将真实脚本放在版本控制目录中，并将其**符号链接**到 Claude 读取的 hooks 目录：
```
~/scripts/claude-hooks/<name>.sh      # SSOT (this setup: a private git repo)
~/.claude/hooks/<name>.sh             # symlink → SSOT

# install / recover:
ln -s ~/scripts/claude-hooks/<name>.sh ~/.claude/hooks/<name>.sh
```
重新安装 `~/.claude` 会清除 hooks 目录；符号链接的目标仍然存在，恢复操作只需执行一次 `ln -s`。断开的符号链接会在**没有任何信号**的情况下禁用 Tier-0 guard — 这正是为什么需要 SessionStart health check（规则 4；可运行的 skeleton：`references/hook_patterns.md` 中的 Pattern C）。

### 4. 注册是按配置文件划分的 — 收敛所有配置文件，通过 HUMAN gate 发布

- **注册面有两个，而健康检查可能只监控了其中一个。** 除了下面的配置文件设置外，仓库自身的 `.claude/settings.json`（以及 `settings.local.json`）也会为该仓库中的会话注册 hooks。它们位于 `~/.claude/hooks/` 之外，因此遍历该目录的护栏检查完全覆盖不到它们——语法、路径、`--selftest`，什么都检查不到。两个静默失败就这样被发布到了其中一个文件中，并在一个原本就是为了防止此类问题而构建的 SessionStart 健康检查下存活了两个月（#38、#39）。使用**绝对**路径注册项目 hooks — 相对路径会根据会话 cwd 解析，而一旦有人从子目录启动 `claude`，它第一次就会失效 — 并扩展健康检查，使其从事件的 cwd 开始向上遍历项目配置文件。
- 如果活动配置文件的 `settings.json` 没有调用某个 hook，那么 `~/.claude/hooks/` 中的 hook **什么也保护不了**。多配置文件用户一直在零防护的情况下运行，直到所有配置文件都完成收敛。在**主**配置文件的设置中注册（本配置中是 `~/.claude/settings.json`；[references/hook_patterns.md](references/hook_patterns.md) 的 Registration 部分给出了确切的 jsonc 结构）— PreToolUse → matcher `Bash` → 你的 hook — 然后收敛其余配置文件（本配置使用由 `claude-switch-models-setup` skill 负责的 `sync-profile-settings.py --all`）。SessionStart 健康检查会 grep 每个配置文件中的 Tier-0 防护，以捕获漂移。CLI 的文件监视器会获取设置编辑（官方 hooks 文档），因此无需重启即可使注册生效 — 通过观察护栏在安全探针上触发，或在下一次会话的健康检查行中确认。
- **如果护栏需要释放阀门，就使用 *human* gate，而不是环境变量。** 静态的 `GUARD_OK=1` 逃生通道不算 gate — 模型可以自行设置该环境变量。使用原生 macOS 对话框（`osascript` — 模型无法点击）；拒绝/取消/超时 = 硬 NO；将每次提示/绕过都记录到审计文件中。模式见 [references/hook_patterns.md](references/hook_patterns.md)。
  - ⚠️ **`/dev/tty` 不是第二个通道 — 文档说明 hooks 无法打开它。**
    该文件过去规定在对话框之外，还要在 `/dev/tty` 上输入 `YES`。
    官方参考文档明确指出：hooks “在其自身的会话中运行，**没有控制终端**”，并且“hook 进程及其任何子进程**无法打开 `/dev/tty`**”（`terminalSequence` 是文档中用于向其写入内容的替代方案）。因此，以此方式构建的“​​双通道” gate 实际上是一个通道加上死代码；而在没有 GUI 会话的机器上，任何人都无法批准该 gate。虽然这与本地观察结果一致，但请仔细阅读边界：在某个配置的共享审计日志中 — 共 1,801 条记录，有多个护栏向其中写入，其中三个实现了 tty 通道 — **360 行带有通道标签（236 次对话框确认、124 次拒绝或超时），但没有任何一行以任何形式提到 tty 通道。** 这意味着 tty 分支从未被*进入*；在 macOS 上，这正是你本来就会预测到的结果，因为对话框会先得到回答并使其短路。因此，日志表明这里没有任何东西曾依赖 tty；是文档，而不是这次测量，确立了 tty 完全无法工作这一点。保留对话框；如果你需要非 macOS gate，就需要一种本文件尚未有经过验证答案的通道。
  - ⚠️ **一个存活时间超过 hook 超时的 human gate 会失败开放。** Hook `command` 的超时默认为 600 秒（`UserPromptSubmit` 为 30 秒），而超时的 hook **不会阻止工具调用** — 因此未回答的对话框不会变成“否”，而会变成允许。将等待时间限制在远低于超时的范围内，并让无回答在 harness 替你处理之前由你自己解析为阻止。
  - 文档还提供了一个 UI 内通道 — PreToolUse `hookSpecificOutput` 中的 `permissionDecision: "ask"`，它会通过 Claude Code 自身的界面发起提示。值得了解，但**在 `bypassPermissions` / 自动接受模式下尚未在这里验证**，而这正是 Tier-0 gate 必须能够经受的模式；之所以规定使用对话框，是因为它不依赖权限模式。
  - **在 Tier-0 以下、允许使用模型可操作的逃生通道时，应让它成为正确的用法，而不是绕过标志。** 上述规则对 Tier-0 是绝对的，在这里不会改变 — 这里讨论的是那些达不到该标准、但仍需要为检测器无法区分的合法情况提供退出方式的正确性护栏。问题在于，你要让这种退出方式*成为什么*。`SKIP=1` / `--force` 环境变量逃生方式，恰好会训练规则 1 所警告的那种条件反射，而且在截止时间压力下，它与绕过没有区别。优先选择一种**本来就希望他们执行的操作**作为逃生方式，这样采取它会改进命令，而不是解除护栏：只要命令提到 `pipefail` / `PIPESTATUS` / `pipestatus`，`pipe-fallback-guard` 就会退出 0，因为编写了其中任何一个的作者已经证明自己理解管道退出码 — 护栏没有什么需要再教他们的了。应用这项测试：*如果有人使用我的逃生通道，最终得到的命令会更好吗，还是只是被解除阻塞？* 如果诚实的答案是“只是被解除阻塞”，那你拥有的就是一个换了好听名字的绕过标志。Tier-0 情况的同源原则是，覆盖机制只为测试 gate 而存在：**逃生通道只能让 gate 更严格** — 参见 [references/hook_patterns.md](references/hook_patterns.md) 中关于 `GIT_GUARD_TEST` 的讨论。

### 5. 判定失败的**方向**，并测试*这一点*——而不只是测试成功路径

规则 1 对*检测调优*错误进行了排序：在守卫已运行的前提下，错误拦截一个正常命令比漏掉一个罕见的恶意命令更糟，因为必须绕过的守卫会被人条件反射式地绕过。**本规则讨论的是另一个维度——守卫的机制根本没有运行**——所以这里并不是把“哪个更糟”的结论反过来；这两个排序从未交汇。一次调优遗漏只会让你损失一个案例；而这会让守卫在所有符合该形态的输入上悄无声息地失效。

问题在于：守卫**无法获取它要据以判断的对象**——解析失败、路径无法解析、依赖缺失、子进程超时——而恰恰是阻止钩子崩溃的 `2>/dev/null || true`，又悄悄地把“*我无法检查*”转换成了“*没有需要报告的内容*”。钩子以 0 退出。**这个输出与真正通过时完全相同**，所以这种问题可能持续数周而不被发现。

因此，在钩子每一个*获取*某个对象的地方（解析命令、读取暂存文件、查询服务），都要明确决定：**如果这里返回空值，是意味着允许还是阻止？**——并把答案写在分支旁边。对于*修饰符*检查，失败放行通常是正确的（是否携带 `--no-verify`？漏掉它只会损失一个案例）。而对于*这是否就是目标对象*的检查，失败关闭通常是正确的（这是否是一个跨域提交？空答案意味着守卫根本没有触发）。

**然后测试这个方向，而不是成功路径**：故意传入一个无法解析的路径或无法解析的命令，并断言它仍然按照你的决定执行。一个每一行都通过、但原因只是钩子悄悄放行了所有内容的测试套件，与一个确实通过的测试套件无法区分。

**仔细阅读这些结果——相同的输入，对于不同的守卫类别，正确答案可能恰好相反。** 以 `cd ~/no-such-dir && TRIGGER` 为例：

| 守卫类别 | 判断依据 | 正确退出状态 | 原因 |
|---|---|---|---|
| **令牌匹配器**（这是否是一种被禁止的命令形式？） | 仅命令文本 | **2，阻止** | `TRIGGER` 明明就在文本中；无法解析的 `cd` 并不会让它不再是一个触发器，而如果守卫在这里静默，它在 `cd ~/real-dir && TRIGGER` 上也会静默 |
| **状态推导器**（仓库的暂存集合是否跨越多个域？） | 从磁盘读取的状态 | **0，允许** | `cd` 失败，`&&` 短路，不会发生提交——没有需要守护的东西 |
| **终止状态读取器**（补救操作是否已经发生？） | 回执文件 / 计数器文件（规则 7） | **0，允许**——*当状态文件本身就是终止条件时* | 无法读取回执意味着钩子无法知道自己是否已经触发；此时失败关闭会在没有补救方式、也没有对人可见原因的情况下永久阻止——这*就是*循环，而且这是唯一比漏掉一个案例更糟的失败。**反转的子情况——复制此行之前先读这里：**当状态只是一个叠加在独立谓词之上的**预算**时（通过执行操作仍然可以解除阻止），读取失败时允许会**悄悄禁用整个钩子**——一个无法写入的目录就会让它对所有输入永久保持静默，这是最糟糕的失败形态。在这种情况下，应退回到*预算存在之前的行为*（继续评估谓词），而不是保持静默。**用一个问题区分这两者：如果状态消失，补救是否仍然可能？**不可能 → 回执情况，允许。可能 → 预算情况，继续检查。给出已经处理好的答案，这样就不必重新推导：规则 7 的机制 2（回执）**和**机制 3（每会话计数器）都属于**回执情况 → 允许**——机制 3 有意不判断 R 是否发生，因此它的计数器就是唯一的退出方式，静默会让本轮操作陷入困境。预算情况则是：计数器叠加在一个用户仍可自行满足的谓词之上 |

所以，应在写入该行 *之前* 决定你的 hook 属于哪一类，而 harness 的
`unresolvable path` 模板行要求 **2**，因为该模板针对的是 token-matcher 类。
弄反这一点，会让一个正确的 guard 得到一个看似确定的 FAIL。对于 state-deriving guard，
你要寻找的失败是：**命令实际上会运行，但 guard 没有发现它** —— 不平衡的引号会导致
tokenizing 抛出异常，fallback 允许通过，而真正的跨域 commit 就会在没有对话框的情况下提交
（rule 1 的 ValueError 说明）。对每一行允许通过的记录都问一句：*这个命令实际上会完成该操作吗？*
如果不会，那么 allow 就是正确的。

对一个真实的 state-deriving guard 运行这一完全相同的探针时，第一次执行返回了两个 allow：
一个是正确的（上面的短路情况），另一个则是真正的 fail-open。**探针负责发现问题；你仍然必须对它发现的内容进行分类** —
这正是为什么上面的 class table 要放在这些行之前。

真实案例（2026-07-22）：一个 scope guard 通过 `git -C "$REPO_DIR"`
读取 staged 文件，其中 `REPO_DIR` 是从 **命令文本** 中解析出来的 — 所以
`cd ~/repo && git commit` 传给它的是字面量 `~/repo`，`git -C` 执行失败，staged 返回为空，
于是 guard 得出“没有跨域文件，允许通过”的结论。每次跨仓库 commit 都未受 guard 保护，而表面上始终没有任何异常。
解剖 + 共享库转折点：pitfall #10。

该解析器还有第二种失败方向，而且更加棘手。一旦你加入 fallback，使它不再 fail open，
fallback 会因为一个原因而正确、因为另一个原因而错误 — 但两者打印出的却是同一行。
`git push`（没有显式目标）合理地 fallback 到事件的 `cwd`；`git -C "$R" push`
*指定* 了一个 hook 无法解析的目标，fallback 到同一个 `cwd`，然后针对另一个仓库渲染出一个看似确定的 ✅。
这两种情况的渲染结果逐字节相同（已测量，MD5 相等），因此 hook 和读者都无法区分诚实的判定与绑定错误的判定。
**fallback 值必须携带选择它的原因**，只有“没有显式目标”才可以生成判定。完整的解剖、
confused-deputy 视角，以及为什么包含字面量路径的 fixtures 永远无法捕获它：
pitfall #28。

### 6. 根据世界能够回答的事实进行判断 — 绝不要依据你自己的渲染结果，也绝不要依据命名习惯

Rules 1 和 5 讨论的是 *如何* 匹配以及 *以哪种方式* 失败。这一条讨论的是
**你所匹配的事物来自哪里**，而且它有两种都会悄无声息的失败形态：

- **绝不要基于为人类格式化的字符串进行分支判断。** 如果 hook 构建了一份报告 — 排序、拼接、截断到前 N 项并带上 `(+M more)` 尾部 —
  然后再针对这份报告对自己的决策进行模式匹配，那么该分支就会继承渲染过程丢失的信息。超过截断数量的项目对它而言根本不存在，
  因此该分支会在每个小型 fixture 上正常工作，却恰好在它所针对的大型会话中停止触发。通过独立的通道输出机器事实（单独一行未截断的 `KINDS:a,b,c`），然后匹配该事实。
  渲染结果是输出，不是数据源（pitfall #12）。
- **优先使用可检查的事实，而不是命名约定。** 根据路径形状
  (`/skills?/[^/]+/references/`) 进行分类，编码的是一种目录布局；任何采用其他布局的 repo 都会被静默地、永远地分类为 `None`。
  修复方法*不是*扩大模式范围，因为那只是把静默漏检换成全机器范围的误报（rule 1 明确禁止这种权衡）；而是提出一个文件系统能够回答的问题 —
  *这个 `references/` 目录旁边是否存在 `SKILL.md`？* 事实能够适应布局变化；约定则不能。（当候选对象**本身就是** `SKILL.md` 时，
  没有兄弟项可供询问 — #13 解释了为什么这是规范定义的事实，而不是本规则所警告的命名习惯。）
  **可检查的事实仍然可能是错误的事实 — 要锚定问题并按类型过滤。** `test -f SKILL.md` 在下载文件夹中也可能为真，
  而一个沿祖先目录查找该文件的 guard 吞掉了整个 home 目录，随后告诉真实会话加载一个以该目录命名的 skill — 这样的名称不可能存在（rule 9 的 incident）。
  应锚定到特定目录的兄弟项，或锚定到已知的安装路径；未锚定的祖先遍历，只是披着事实外衣的约定。

两者的共同特征是：某个分支在生产环境中一次都没有触发过，但其测试却是绿色的。打印未经格式化的原始分类结果，你就能看出自己属于哪一种。

### 7. 如果 hook **要求补救**，请证明循环会终止

一个会**阻塞**（exit 2）直到 X 完成的 hook——尤其是 Stop hook，因为它们会在之后每次停止时重新触发——不是检查，而是一个**反馈循环**。 （仅仅*注入*一项要求并以 0 退出的 hook 根本没有循环：没有任何东西会重新评估。这就是下面的机制 0，而且它通常比人们实际采用的做法更适合作为默认选项。）

```text
LOOP KEY: immutable logical target / lineage + one failure axis
FIRE T: the condition that starts another cycle
REMEDIATION R: the exact action one cycle performs
VARIANT V: the well-founded quantity that strictly decreases for this key
BUDGET: maximum cycles, fixed before cycle 1
SUCCESS EXIT: the observable that proves the axis is clear
CAPPED EXIT: what is left blocked / unshipped / pending when the budget ends
```

如果没有完整的契约，就不能使用阻塞式 Stop hook，也不能使用重复的审查或轮询循环。必须在 cycle 1 之前冻结 key。补救快照、提交或审查者名称都必须留在同一 lineage 中，不能创建新的预算。新的、无关的发现属于**新 key**：单独记录；它不会重置此循环的预算。一个无法指出新的证伪实验或更小 V 的 cycle 不会增加任何证据，应当停止。

对于**由 agent 驱动的独立审查循环**，默认预算是一次初始审查，加上在实质性修复之后进行一次范围严格限定的重新审查。第三位审查者不是自动安排的。如果重新审查仍在同一轴上复现 BLOCKER 或 MAJOR，则保持 hook 未注册 / artifact 未发布，报告被阻塞的状态，并要求一个新的、由用户授权的任务；该任务必须在 cycle 1 之前声明其 Loop Contract 中的预算。由 agent 声明的预算不能为自身授权。在该授权任务内部，必须明确说明立即停止会造成的具体安全或业务失败；可选的润色不符合条件。

已填写的审查循环示例：

```text
LOOP KEY: <initial frozen commit>'s review lineage + termination-contract fidelity
FIRE T: fresh review reports a same-axis BLOCKER / MAJOR
REMEDIATION R: reproduce that finding, apply one bounded fix, run its narrow check
VARIANT V: 2 - completed review cycles
BUDGET: 2 cycles total (initial review + one re-review)
SUCCESS EXIT: no same-axis BLOCKER / MAJOR
CAPPED EXIT: artifact stays unregistered / unshipped; report remaining findings
```

初始冻结提交的每个修复后代都仍属于这个 key。当前快照会发生变化，以便审查者检查修复；但 lineage 及其剩余预算不会变化。

没有任何机制会强制执行这个无 hook 预算——它只有在 agent 遵循 Skill 时才有效。正因为有这个限制，封顶退出状态必须清晰可见，并且绝不能被报告为“已完成”。

**如果完成 R 能再次使 T 为真，则该循环不会收敛。** 不会报错，也不会崩溃；它会一轮又一轮地运行，直到人类中断——而这通常确实会发生，因为每一轮都是一个*完整的*修复周期（dispatch、wait、adopt、edit），而不是廉价的重试。**而同样的特性也意味着，harness 的连续 8 个 block 上限救不了你：它的计数器会在每次执行了工具的 continuation 上重置，因此由工具调用组成的修复周期会让计数永远停留在 1**（已测量——#27）。即使它最终触达该上限，那也是针对失控会话的后备机制，而不是设计方案：该轮结束时，违规仍然存在，而 harness 会将该轮报告为 `reason:"completed"`——这与真正完成无法区分。“它最终会停止”在任何你真正需要的意义上都不算终止，而在这里它甚至不会最终停止。`stop_hook_active` 在这里也**救不了你**——该字段只涵盖**一层重新进入**（“我刚刚阻止的 stop 正在重试”）。它对**跨轮次**的情况毫无说明：模型确实执行了 R（实际工作、许多工具调用），然后自然停止；这时这是一个全新的 Stop，该字段为 `false`，hook 会基于同样的理由再次触发。

**这个测试借鉴自程序验证中的终止性证明**——一个[循环变式 / 排名函数](https://en.wikipedia.org/wiki/Loop_variant)：写下一个映射到良基序（通常就是 ℕ）的量 **V**，并证明 **V 在每个 `trigger → remediate → re-check` 周期中都严格递减**。没有 V，就没有终止性证明——不要注册该 hook。

**V 是设计阶段的义务，不是代码**——你永远不会在 hook 中计算它。实际交付的是*谓词*（下面的机制）；V 则是证明该谓词会收敛的论证。把它放在下一位读者最容易踩坑的地方——脚本头部：

```bash
# TERMINATION: V = 1 - exists(<receipt path>)
# decreased by: R writes the receipt; nothing R does afterwards can remove it.
```

“证明它会递减”包含三个具体问题，答案应写入该注释中：

1. **R 会改变什么？** 写明确切的文件 / 字段 / 时间戳。
2. **该对象是否是 T 的操作数？** 如果是，并且 R 将它移回“触发”方向 → 就不存在 V。
3. **R 之后，使 T 再次为真的最小输入是什么？** 如果答案是“我刚刚触发时使用的同一个输入” → 就不存在 V。重新设计谓词；不要重新调整阈值。

**一个真实的反例。** 某个 Stop hook 要求在复合制品（规则文件、skills、其他 hooks）可以被推送之前，必须进行独立审查：

- **T**（使 hook **触发**的条件）=“存在尚未被审查覆盖的编辑”，其实现方式是时间戳比较 `last_edit > last_review`（`last_edit` = 制品集合中最新的 mtime，`last_review` = 审查记录的 mtime——两个单独的数字，而这正是该比较让人感觉安全的原因）
- **R** = dispatch 一个独立审查者

但是，值得运行的审查**是有输出的**：其发现会被**同一个代理立即采纳，并且发生在它下一次尝试停止之前** → 这会产生新的编辑 → `last_edit` 超过 `last_review` → **T 再次为 true**。（如果稍后由人类在代理回合之外采纳这些发现，就不会形成循环——该循环需要在同一个代理回合内完成修复和重新检查，而这正是 Stop hook 所保证的。）这里不存在 V——修复不会减少某个量，而是*重置*某个量。唯一的退出方式是“审查，然后什么都不改”，而这恰恰说明调度审查器是徒劳的。观察结果是：连续三个回合，每个回合都完成了审查并采纳其结果的完整循环，最终都只有在用户说停止后才退出。

有两点让这一点很难看出来。**单独看，这个比较看起来完全合理**——“审查必须比上一次编辑更新”正是你会写出的条件。而这句话是**通过**条件——T 是它的否定。把它原样记在脑中，却忽略那个否定，接下来的整个分析中你推理的就是错误的操作数；要始终把 T 作为**触发**条件来理解。（将*代码*写成提前退出的守卫子句——`… && exit 0`——是正常的 shell 风格，这不是这里讨论的重点；这里的纪律要求是明确你进行推理时所采用的方向。还要注意相等的情况：同一秒的 mtime 会落在通过一侧，也就是 fail-open，这与下面这条规则对状态读取的要求一致。）运行上面的检查清单，结论会机械地显现出来：R 会改变 `last_edit`（Q1）；`last_edit` 是 T 的一个操作数（Q2）；使 T 再次触发所需的最小输入就是修复自身的输出（Q3）→ 不存在 V。

**第二种失败形式：谓词完全看不到修复（可观测性缺口）。** 上面的反例是一个会被修复*推动*的时序谓词。同一类问题中还有一种更隐蔽的失败：修复确实发生了，但谓词读取修复所依赖的通道在当前环境中根本不存在。真实案例（2026-07-26，在一次全舰队循环审计中发现）：一个 Stop hook 通过扫描 tool_results 中的
`agentId: <hex>` 并读取 `subagents/agent-<hex>.jsonl`，来检测“发生过一次独立审查”——这在主配置中是正确的。Team-mode 会话完全使用不同的 schema（生成回执为 `agent_id: <name>@session-<uuid>`，传递内容作为带有 `teammate_id` 的 teammate 消息，文件为 `agent-a<name>-<hex>.jsonl`）——永远匹配不到，因而 `last_review` 永远保持为 `None`，每个 compounding-edit∧push 回合都会重新触发该要求：这是一个误报循环，在每个停止序列中最多触发一次，但跨回合则无界增长；而该会话中的“2/2 fires”实际上都发生在已经完成审查的工作上。这属于同一类问题，但需要不同的药方：时序循环需要更好的*谓词*；可观测性循环需要更好的*通道*。在检查清单中增加第四个问题——**Q4：在这个 hook 将运行的每一种环境中，该谓词是否确实能够 SEE R 发生？** 对于读取 transcript 的 hook，这意味着要从每个配置文件/模式中解析真实会话，而不是只针对一种 schema 做 fixture 测试。（上述案例的修复方案：采用多 schema 检测，并排除 teammate deliveries 对回合边界的影响，以免它们截断检测窗口——陷阱 #20。）

**先按轴选择，再按顺序选择——这不是同一事物的五种强度。**
0 决定*是否要阻断*；1 决定*要挂在哪个事件上*；2–4 是
*谓词的形态*（选择了 1 之后，仍然需要从 2–4 中选择一个）。0→4
的顺序表示“循环被移除得有多彻底”，而且它与“你能够施加多少约束”
**成反比**——因此应选择第一个仍能提供你实际所需约束力的选项，而不是
简单地选择第一个选项。

0. **不要阻断——注入。** 如果需求只是建议性的（你希望模型
   *考虑* R，而不是没有它就无法完成），就打印它并以 0 退出。
   不会有任何重新评估，因此也没有需要证明会终止的循环。对于低于 Tier-0
   的任何需求，这是正确的默认选择，其代价也必须坦诚说明：提醒可能会被
   忽略，因此应在标头中说明它是 fail-open 的——规则 4 的要点仍然成立，
   主体可以直接走过去的门，就不是门。如果你需要的是一道*门禁*，就使用 2
   并为回执付出代价。注入通道：Pattern D。
   ⚠️ **此选项在 Stop 上不存在**——而规则 7 的主要讨论对象*就是*
   Stop，因此在使用它之前请先读完这里。在 Stop 上，`exit 0` 的含义是“让
   这次轮次结束”，因此文本没有后续的推理步骤可以传达给模型；而
   `hookSpecificOutput.additionalContext` 与 `exit 2` 计入同一个 8-block
   上限（见 hook-types 部分），也就是说它同样属于阻断。Stop 恰好只有两种
   模式：门禁，或静默。因此，在 Stop 上选择机制 0，就意味着**改变事件**——
   将注入挂到生成该产物的工具调用上（PostToolUse，Pattern D）——或者承认
   你最终还是想要一道门禁，并改用机制 2。
   ⚠️ **“没有循环”只有在 R 不是你自己的匹配器目标时才成立。** 一个挂在
   `Bash` 上、告诉模型运行 `git ls-remote` 的注入器，会在该命令本身再次触发，
   并再次注入。同样的形态，只是更柔和——模型可以忽略它，因此不存在强制迭代，
   但它会在重复时广播，而不是完全没有重复。请检查你建议的 R 不是此 hook
   所匹配的操作。

1. **将检查移到操作边界。** 如果你想要门禁的是一个*操作*——一次推送、
   发布或删除——就用 PreToolUse 保护**该操作**，而不是用 Stop 保护**这次
   轮次**。**Stop-hook 的补救循环经常其实是挂错事件的操作门禁**，这正是
   hook-types 部分所说的“Stop 是那个与众不同的选项，也是最常被误用的选项”
   的具体情形。
   **要准确理解这样做能带来什么。** 只有当模型*主动重试受门禁保护的操作*
   时，PreToolUse 才会再次触发；模型始终可以拒绝该操作，并正常结束这次轮次。
   因此它保证的是**轮次会终止**——最坏情况从“轮次无法结束”降低为“该操作
   不会发生”。但它**不会**让一个不收敛的谓词收敛：以上面的反例为例，将其
   原样移到 PreToolUse，循环仍会完整保留（push → blocked → review →
   findings adopted → new edits → retry → `last_edit` is ahead again →
   blocked）。这个案例的问题出在它的**谓词**，而不是它的事件上，因此你仍然
   需要从 2–4 中选择一种形态。还要注意，PreToolUse **没有** harness
   backstop——hook-types 表中的 8-block 上限仅适用于 Stop——因此，将一个
   会自我重置的谓词移到这里后，安全网反而更少，而不是更多。
   ⚠️ 有两种形态不适合使用这一机制：**R 必须通过你所门禁的那个工具来完成**
   （例如，在 `Edit` 上设置一个守卫，要求你先修复文件头——这会造成死锁，
   没有任何操作能够满足它），以及**一个操作会在同一会话中重复发生**
   （一个会话推送五个仓库，而你设置了 `git push` 门禁 = 五次完整的需求；
   这正是下面战争故事中的密度问题，而机制 1 并不会让你免于它）。

2. **让“已完成修复”成为一个存在性事实，而不是时间事实——并以需要修复的对象作为其键。** 让 R 落地一个制品，并测试*它是否存在*；关键在于：

   ```bash
   KEY=$(git rev-parse HEAD 2>/dev/null || printf 'nogit')   # or a hash of the
   RECEIPT="${TMPDIR:-/tmp}/my-guard.${KEY}.ok"              # reviewed content
   [ -f "$RECEIPT" ] && exit 0            # V = 1 - exists, for THIS key
   ```

   `V = 1 - exists` 是**按键计算的**：每个键恰好减少一次，并且对于*该键*永远无法再次增加。新的工作会生成一个*新*键——那是新的需求，而不是重新启用。两种朴素的键设计都不行：单一的全局路径会让钩子在每台机器上触发一次，然后永久沉寂且没有任何信号；基于时间的键则正是本规则要禁止的时间谓词。**时间谓词几乎总是错误的形态**，因为你所要求的修复通常正是会改变你拿来比较的操作数的东西。
   这个内容 SHA 键对于一次性回执门控是正确的。它**不会**重新定义代理审查谱系：由该谱系的修复所创建的提交，仍然使用其原始键和原始预算。
   ⚠️ 如果**模型**能够创建回执，那么这就是规则 4 中已废弃的 `GUARD_OK=1` 逃生舱，只是换了个新面貌。应让模型无法驱动的某个东西来写入它（审查子代理自己的输出文件、git note），或者接受该钩子只是建议性的，并在其标头中明确说明。

3. **为重复次数设置上限。** 每个会话、每个目标最多提醒 N 次——`session_id` 是实现这一点的唯一稳定键（它存在于每个事件中；参见模式参考中的 JSON 契约）：

   ```bash
   SID=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('session_id','nosid'))" 2>/dev/null || echo nosid)
   CNT="${TMPDIR:-/tmp}/my-guard.${SID}.count"
   N=$(cat "$CNT" 2>/dev/null || echo 0); N=$((N+1)); printf '%s' "$N" > "$CNT"
   if [ "$N" -gt 3 ]; then
     CAPPED_REASON='Loop budget exhausted; the blocked condition remains unresolved. Do not report completed.'
     python3 - "$CAPPED_REASON" <<'PY'
   import json, sys
   print(json.dumps({"continue": False, "stopReason": sys.argv[1]}))
   PY
     exit 0                              # explicit capped stop, not silent success
   fi
   ```

   这种做法很粗糙，而且有意不判断 R 是否确实发生——但它是*有限的*，而这正是原本缺失的属性。**不要**用 `$$` 或 `$PPID` 替代：每次钩子运行都会创建一个新进程，因此它们会在每次调用时变化，计数器永远无法累积。打印计数（“第 2 次提醒，共 3 次”）——下文的战争故事会说明为什么这句话值得保留。封顶输出使用文档规定的通用 [`continue:false` / `stopReason` JSON 字段](https://code.claude.com/docs/en/hooks#json-output)，这样用户看到的是一个达到上限的停止，而不是一个无法区分的成功 Stop。这会停止会话；但**不会**保护发布操作。如果封顶退出信息表明某个制品仍未发布，则应在操作边界通过 PreToolUse 单独强制执行。

4. **滞回 / 冷却窗口**（控制理论针对
   [告警抖动](https://utcc.utoronto.ca/~cks/space/blog/sysadmin/HysteresisMeaningAndAlerts)的答案）：
   触发后，在一段窗口期内抑制重新评估——一个印记文件，加上
   `[ $(( $(date +%s) - <stamp mtime> )) -lt 900 ] && exit 0`（在 BSD/macOS 上，mtime
   是 `stat -L -f %m`；在 GNU 上是 `stat -L -c %Y`——本文其他代码片段也是如此；**`-L` 不可省略**，
   因为规则 3 会在你要执行 stat 的每个路径处放置符号链接，如果没有它，你读取的就是链接自身的
   mtime，而不是印记的 mtime；这样 SSOT 被编辑时印记永远不会更新——#41）。适用于围绕某个阈值
   *振荡*的条件；对于修复操作会**重置**的条件则是**错误**的——这类情况需要使用 2 或 3。
   ⚠️ **滞回不提供 V——它是速率限制器，而不是终止性证明。** 循环只有在条件自行缓解时才会结束，
   而使其结束的是外部世界，而不是你的 hook。因此它的 `# TERMINATION:` 行必须写明这个外部事实
   （“在印记过期时，X 已由 <谁> 解决”）。如果你无法诚实地写出这一行，那么你需要的是 2 或 3。
   （一个值得注意的家族相似性：机制 0 是两者的极限情况——机制 3 将上限设为 0，或机制 4 将窗口
   设为 ∞。它们的区别在于执行方式，而不在于终止方式。）

**状态本身的失败方向：应用规则 5 的问题，不要根据字面匹配。** 如果状态无法读取或写入——
`TMPDIR` 不可写、沙箱、磁盘已满——由规则 5 的 guard-class 表决定，而它的判断依据是询问：
**“如果这个状态消失，修复操作是否仍然可能？”** 对于机制 2 和 3，答案是**不可能**——回执是
R 已发生的唯一记录，而机制 3 则有意不去判断 R 是否发生，因此它的计数器是唯一的退出路径——
所以应当**允许停止**。一个无法读取自身状态却仍然阻止执行的终止机制，*就是*这个循环，只不过现在
连人类可见的原因都没有了。

⚠️ **不要仅仅因为两者都提到“计数器”，就把机制 3 归入规则 5 的“反转子情况”。** 那个子情况
针对的是这样一种计数器：它只是在用户仍可独立满足的谓词之上，*预算提醒次数*——在那种情况下，
计数器不可读时停止提醒，只会让一个原本还有其他清除方式的 hook 静默，因此你仍要继续评估该谓词。
机制 3 没有这样的备用谓词。**实测结果，而且这正是这种配对产生的失败：**将机制 3 的代码片段粘贴到
Pattern E 的骨架中（按照 `-e`-vs-trap 项的说明，其中附带 `set -uo pipefail`），将
`TMPDIR` 指向一个不可写目录，连续五次运行都会返回退出码 2——`N` 无法持久化到大于 1 的值，
上限永远不会达到，而一旦修复操作涉及工具调用，#27 已经排除了将 harness 上限作为后备机制的可能。
这里的失败方向完全由代码片段未携带的一行 `set` 决定，因此**应当把 guard 放在实际失败的步骤——
写入操作——上，而绝不能放在读取操作上**：

```bash
printf '%s' "$N" > "$CNT" 2>/dev/null || exit 0   # can't persist ⇒ can't terminate
```

读取操作已经受到保护（`cat … 2>/dev/null || echo 0`），并且**必须保持这种方式**：计数器文件缺失是首次运行时的正常情况，因此在读取操作上使用 `|| exit 0` 会让钩子在完全健康的环境中永久静默。实测结果如下，每个变体连续运行五次：在可写的 `TMPDIR` 上，对写入操作进行保护会得到 `2,2,2,0,0`，在不可写的 `TMPDIR` 上则得到 `0,0,0,0,0`——两种情况下都正确；而对读取操作进行保护则在**两种**情况下都得到 `0,0,0,0,0`，也就是说，这个保护条件根本不会触发。

**需求文本中的说明性文字不能替代一个会收敛的谓词。** 一个消息写着“如果你认为这没有必要，就再次完成”的钩子，每一轮仍然会耗费一个完整的修复周期，因为被告知必须执行 X 的模型通常就会执行 X。逃生通道必须位于**谓词**中，而不是建议中。

**测试要求，以及这里最容易跳过的事情：**自测需要一个**“修复之后”**的用例——不仅要测试“应该触发时会触发”，还要测试**“R 完成后会停止触发”**。如果没有这一项，非终止在**结构上是不可见的**：每个 fixture 都只是一个孤立的时间点判断，而非终止是**序列**的属性。只检查单个时间点的测试套件，无论有多少用例，对收敛性都没有任何覆盖——这就是为什么一个钩子可以带着通过的自测发布，却在第一次真实遇到问题时仍然循环。能够发现这一点的行对（回执不存在 → 触发，回执存在 → 静默，以及普通的 `run` 行无法表达的设置/清理操作）已经模板化放在 `scripts/test_hook.sh` 的“修复后用例”部分；症状 → 原因 → 修复对应陷阱 #16。

**证明了终止 ≠ 实际感觉上已经终止（2026-07-25 的惨痛经历）。** 一个具有正确存在性事实 V 的 Stop 钩子在一次会话中触发了三次——每次触发都是来自不同已完成任务的、合法的**新**推动，机制完全按照设计正常工作——但用户的体验仍然是“为什么这东西卡在循环里？”（这与机制 2 的“R 所做的任何事情都不能让它再次升高”并不矛盾：**V 是按键划分的**——三个不同的键，分别对应三个独立的单向递减。这也是当你无法判断自己处于哪种情况时的诊断依据：如果每次触发都带有一个**新**的键，那么机制是正确的，问题在于密度；如果重复触发共享**同一个**键——或者谓词根本没有键，因为它比较的是时间戳——那么你遇到的就是上面那个反例，谓词需要被替换。）从外部看，连续进行三个相互独立的修复周期，与陷入循环无法区分。变体证明解决了机制问题；但它没有说明**一次会话可能要求多少次不同的修复**。如果你的领域会产生如此高的密度（这里叠加产生的工件每天会发布数次），可以考虑将机制 2（存在性事实）与机制 3（会话范围的上限）结合使用，或者有意接受这种观感，并在钩子的输出中明确说明——“最多 N 次中的第 2 次提醒”读起来像是在取得进展，而没有任何说明的重复看起来就像循环。**（2026-07-26 后续：同一个钩子那些看起来像密度问题的触发，最终被证实 100% 都是误报——它的审查通道在团队模式下无法识别 schema；参见上面的可观测性表单。在接受“合法的密度”这一解释之前，先确认这些触发确实有证据支持。）**

**终止与价值是两个独立的关卡。** V 证明循环会结束；Loop
Contract 的预算和封顶退出机制决定是否值得继续付费执行下一轮。暴露出这一
区别的无 hook review-loop 失败案例，包括范围漂移为何会悄无声息地制造出无穷
无尽的“新”工作，属于陷阱 #36。

### 8. 等待也需要同样的证明——通知只是提示，轮询必须携带预算

规则 7 讨论的是由 *hook* 创建的循环。同样的形态也会在没有 hook 参与时
反复出现：**agent 轮询异步结果**——子 agent 的报告、后台任务的完成通知、
CI 状态。真实会话（2026-07-25）：子 agent 的完成通知通过一个可能延迟或丢失
消息的邮箱送达；三个不同的 agent 都已完成工作，但通知一直未送达，等待中的
agent 在约 40 分钟内反复执行了十几轮 `sleep 240` + 催促，直到人类询问它
到底在做什么。没有任何报错；这个循环只是没有变式。

规则 7 的机制可以对应过来——前两项可以直接对应；滞回没有对应物（等待不会
振荡），它的位置由等待特有的一个陷阱占据：

1. **轮询产物，而不是通知。** 如果你真正需要的是某个结果（文件、git ref、
   API 状态、DB 中的行），就等待*它*，而不是等待“它是否说自己完成了”。
   通知是提示；产物才是事实。存在性检查会在事实落地的那一刻终止，无论是否
   有任何消息送达。
2. **每次等待都必须携带预算，并在编写循环时确定。** 最大轮数 × 间隔
   （例如 3 × 4 分钟），以及一个在第一次 sleep 之前就已存在的降级路径：
   自己完成、询问用户，或将其标记为待处理并转去做其他工作。“无限等待，看看
   再说”不是降级路径——它就是这个循环。
3. **投递协议只是提示，不是机制。** “完成后通过 SendMessage 报告——
   沉默表示未完成”值得写下来，但它约束的是 agent *是否发送*，而不是邮箱
   *是否投递*。在一次会话中，提示词里带有该协议的三个 agent 最终都没有
   消息。设计等待机制时，应假设通知可能永远不会到达——因为它确实可能不会。

两个相邻的陷阱，在同一次会话中都付出了代价：**对一个实际上正在工作的
“卡住” agent 执行 TaskStopping**——邮箱延迟不等于闲置；一名 reviewer
正在进行 20 分钟的真实语料测试，却在即将交付前几分钟被当作“卡住”而终止。
以及 **对等待本身进行 `--dry-run` 风格的探测**：在断定另一方没有响应之前，
先确认你自己的观察通道正常（在那次会话中，System Events 的窗口计数对一个
实际显示在屏幕上的对话框返回了一个确定无疑的 0——权限失败伪装成了证据）。

### 9. Fixture 无法告诉你误报率——注册前先重放真实命令语料库

规则 1 对**哪种**错误更糟进行了排序（误拦截比漏拦截更糟，因为人们必须绕过
的防护会被本能地绕过）。规则 2 要求你在注册前进行测试。但它们都无法告诉你
**误拦截面实际有多大**——测试表无法做到这一点，因为*你是根据产生检测器的
同一套心智模型编写其输入的*。它的测试用例包含的是你想到的形态；你没想到的
形态，按定义就不存在。这不是通过增加行数就能弥补的覆盖率缺口。

**实测于 2026-08-06。** 一个 PreToolUse/Bash 守卫通过了一张包含 26 个案例的表格，并对其运行了 5 次变异测试，随后完成注册。之后，使用从最近 60 份会话记录中提取的 **11,903 条去重真实命令**进行重放：其中 143 条产生候选项，实际 hook 拦截了 46 条，而逐一人工检查这 46 条后发现 **10 条是错误拦截——占其拦截总数的 21.7%**（其中两次边界调用被计为正确；如果按另一种方式判断，错误率约为 30%）。在 39 分钟内，它已经拦截了 3 个真实会话，其中一个被告知要加载一个根本不存在的 skill——这是下面第三个缺陷，以指向虚无的修复指导形式暴露出来的。它在同一个小时内被移除。三个根本缺陷都位于**解析**层：续行标记被当作分隔符读取，分段扫描将 heredoc 正文和数据参数计为执行内容，以及路径分类器没有类型过滤。

这个故事并不支持两个结论。它**并不是**“变异测试不起作用”：之后对同一套测试的审计发现，**hook 的逻辑中有 5 个部分可以删除，而 26 行测试仍然全部通过**；作者标注为“已从装饰性修复”的其中一行实际上仍然是装饰性的——*“我运行了变异测试”不等于“变异测试是正确的”*，而重放同时暴露了这两点。它也**并不是**“你本来不可能知道”：其中三个缺陷是对本文件已经提供的代码进行手工重写造成的（`split_shell_lines`、命令位置遍历，以及 `is_git_write` 对 `-C` 及其参数的处理）。规则 1 中的*逐字使用遍历器*才是成本更低的修复，却被跳过了；重放是后备防线，而不是第一道防线。

**方法——四个步骤，其中第 2 步最容易被跳过：**

1. **收集。** 会话记录位于
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`，此外还包括在
   `~/.claude/history-sources.json` 中注册的任何归档。命令是 `.message.content[]` 中满足
   `type == "tool_use"` 且 `name == "Bash"` 的条目，位于字段 `.input.command` 中——**不是** hook
   事件的 `.tool_input.command`，后者是另一种结构。去重，并收集足够多的会话记录，使你自己最近的工作形态包含在其中（那次运行使用了 60 份）。
2. **使用随附的检测器进行预筛选，并逐字切出**——绝不要手写一个等价实现，否则你测量的只是你自己的两个猜测之间的一致性。预筛选的存在只是为了降低成本（11,903 → 143）；第 3 步才负责作出判断。如果检测器不是一个可以独立提取运行的代码块——无论是 shell 代码，还是拆分在某个被引入的库中——就把它变成一个；无法独立运行的检测器同样无法进行单元测试。
3. **将每个候选项交给真实 hook，并提供它自己的真实会话记录和 `session_id`。**
   读取会话状态的守卫在伪造上下文中会给出不同答案。事件契约见：`references/hook_patterns.md`。有两件事会造成问题——请在临时
   `TMPDIR` 下运行，否则规则 7 的回执和每会话计数器会写入真实会话，并在你自己的测量过程中途让守卫静默；此外，如果 hook 有人工
   gate，请通过模式 B 的强制拒绝路径驱动它，而不是回答 143 个对话框。
4. **人工检查每一次拦截——拦截列表就是误报率的测量结果。** 允许列表回答的是规则 5 的另一个问题（它是因为那里什么都没有而安静下来，还是因为它无法看见？）；而一次重放若返回**零次**拦截，应当怀疑测试工具，而不是将其视为通过——陷阱 #11 在触发不足的方向上规定了同样的测量方式。

**如何处理这个数字。** 修复指导错误或不可能执行的误拦截 → 根本不要注册：这种形态正是制造反射式绕过规则 1 所要阻止的过程。否则，把拦截列表当作修复列表并重新回放。预计误报会集中在**你编写守卫时正在做的事情**上——那次运行中有一半落在了 hook 开发文件上，因为作者那周正在构建 hooks。并且要专门扫描拦截列表中的**运维操作**（对 hooks 目录下文件的编辑、对某个 hook 执行 `bash -n`、守卫自身的 SSOT）：一个会拦截自身移除操作的守卫，无法从会话内部关闭。最近记录的案例是 #25：守卫拦截了一个**只读的** `git config core.hooksPath` 查询——这是距离自我锁死只差一步的同一个盲点。一旦守卫已经把你锁在外面，逃生路径见 **#3** 的列表（使用 Edit/Write 工具编辑 `settings.json`，它永远不会触发 `Bash` matcher；或者使用不同的 `CLAUDE_CONFIG_DIR` 启动会话）。

规模控制方面，为避免这看起来像一个研究项目：一次收集加一次循环，实际耗时几分钟。

## 构建顺序（按顺序）

1. **确认这是真实存在的重复发生问题**，而不是假设出来的——否则不要构建。
   如果 hook 将会**要求修复**而不只是拦截，请在编写任何逻辑之前，先写出完整的 Loop Contract（key / axis / T / R / V / budget / two exits），并将 V 作为脚本头部中的 `# TERMINATION:` 行写入（规则 7）。首先检查你要设防的对象是否是一个*操作*，如果是，那么针对该操作设置 PreToolUse 守卫可以消除循环，而不是驯服循环。
   无法命名一个会在每次 `trigger → remediate → re-check` 循环中严格递减的量？该设计不会终止——修复设计，而不是正则表达式。
2. 在 SSOT 目录中编写脚本；`chmod +x`。
3. 使用 shlex 进行 token 级匹配来实现**检测**（规则 1），匹配依据应是世界可以回答的事实，而不是你自己的渲染结果或命名约定（规则 6）。
   - **先检查 ShellCheck 是否已经能判定这个问题——然后记录答案，因为下一个作者还会问同样的问题。** 它是 shell 反模式的事实标准，所以审阅者首先会问：“为什么不直接用 shellcheck？”在 **0.11.0** 上于 2026-08-15 测量，针对
     `find . -name x | head -5 || echo "no"`——这是一个被证明永远不会触发的 fallback，因为 `||` 会绑定到管道的**最后一个**阶段，而 `head` 在空输入时退出码为 0：**默认配置不报告任何内容，退出码为 0**。`--enable=all` 会发现 **SC2312**（`check-extra-masked-returns`），但它也会在 `cmd | jq . || echo bad` 上触发，而后者的最后一个阶段确实可能失败，fallback 也确实有意义。
     有三个理由使它不适合作为*门禁*——而且每个理由都具有普遍性：
     它**默认关闭**（因此目前并未保护任何人），它无法区分失效的 fallback 和有效的 fallback（无差别触发会导致规则 1 的误拦截螺旋），并且它自己建议的修复方式是“使用 `|| true` 来忽略”，这与预期目的相反。它还检查的是**文件**，而不是工具调用事件。
     这个问题通常应得出的结论是：标准 linter 是正确的**检查**工具，但通常不应将阻塞门禁**委托**给它，因为 linter 针对的是建议性覆盖面，而门禁需要精确性。你的 hook 所贡献的正是这种精确性。已发布的示例：`pipe-fallback-guard`，它的精确性来自一个小型列表，其中列出了确实会吞掉上游退出码的最后阶段命令（`head`/`tail`/`wc`/`cat`/`sort`/……），并且有意排除了 `grep`/`jq`/`awk`/`sed`，因为这些命令确实可能失败。
4. 使用触发案例和看似健康的对照案例执行 **`bash -n` + `test_hook.sh`**（规则 2）——在测试通过之前不要注册。包括携带未展开路径的形态（`cd ~/elsewhere && …`，规则 5）；如果 hook 有人工门禁，则加入一个强制拒绝行（Pattern B，“Make the gate testable”）；如果它要求修复，则加入**修复后的行对**——没有 receipt 时触发，有 receipt 时静默（模板位于 `scripts/test_hook.sh`；规则 7——时间点 fixture 在结构上无法发现不终止）。
   - **为 hook 提供 `--selftest` 模式，并使其具备双向测试能力。** 然后让 SessionStart 守卫健康检查（见上文“Hook types”——其全部职责就是检查守卫本身的那个检查）对每个已安装且提供该模式的 hook 调用 `<hook> --selftest`。这是唯一能够捕获以下故障的自动检查，而 `bash -n` 以及下面的第 4-7 步在结构上都无法发现该故障：hook 已经**退化为永久空操作**。这种故障按构造就是不可见的——一个永不触发的守卫，其输出与一个没有任何报告内容的会话完全相同，因此它可能持续数周。两个 fixture 是*最低要求*，而不是目标：一个必须拦截的样本和一个必须放行的样本，这样才能同时捕获“停止触发”和“开始误拦截”——只使用其中任意一种都无法覆盖另一种。
     **按杀死的 mutants 数量来确定规模，而不是按 fixture 数量来确定规模**，并像校准测试套件一样校准它：故意破坏检测器，并确认 `--selftest` 以非零状态退出。一个从未被验证会失败的 selftest，与 `exit 0` 没有区别。
     在已发布的 `compounding-edit-review` 上测量：其**第一个版本的两个 fixture 只杀死了 14 个 mutants 中的 4 个**——其注释声明重要的每个行为都没有覆盖，包括一个会短路 anti-loop 检查、但 selftest 仍然打印 OK 的 mutation。现在它运行 58 个案例。
     真正的约束不是 fixture 数量，而是**会话启动时的实际耗时**，因为这项开销会在每个会话中支付：这 58 个案例耗时**约 5.3 秒**，而两探针 liveness 检查耗时**约 140 毫秒**。当杀死 mutants 让你超过这个预算时，应该**拆分**而不是缩减——在 `--selftest` 中使用一个廉价且固定规模的 liveness probe，在构建时通过 `test_hook.sh` 运行完整回归测试集。
     缩减到 mutant-kill 临界线以下，只是换回一个在守卫已失效时仍然通过的 selftest。
     **为拆分方案提供一个触发机制，否则完整部分永远不会运行。** “在构建时”不是一种机制——一条写着*修改此文件后运行完整测试集*的注释，与整个文件旨在弥合的“文字说明与强制执行之间的差距”完全相同，并且会以同样的方式失败。对 `shared-repo-head-drift` 测量出的闭环形态是：21 个案例 / 冷启动 17.8 秒，将 SessionStart 的健康检查压缩为 9 个断言的 probe / 2.2 秒：在 hook 中同时保留 `--selftest` 和 `--selftest-full` 两部分，让健康检查进行选择——如果文件自上次完整通过后发生过变化，则运行完整测试集，否则运行 probe。这样，开销会落在**编辑后的第一个会话**中，而这正是值得支付完整测试集开销的时候。
     ```bash
     sig=$(stat -L -f '%m %z' "$h" 2>/dev/null || true)   # -L or you stat the symlink — #41
     stamp="$STAMPS/$(printf '%s' "$h" | shasum | cut -c1-16).full"
     [ -n "$sig" ] && [ "$(cat "$stamp" 2>/dev/null || true)" = "$sig" ] || mode="--selftest-full"
     bash "$h" "$mode" >/dev/null 2>&1 </dev/null || return 1   # </dev/null: an
     # unknown flag drops into the main path and reads stdin — on SessionStart that
     # hangs every new session
     [ "$mode" = "--selftest-full" ] && printf '%s' "$sig" > "$stamp" 2>/dev/null
     ```
     失败方向应当是**转向完整测试集**：签名不可读、不匹配，或 stamp 目录不可写时，都运行完整测试集。这里不存在修复循环（规则 7 不适用）——它只是在选择运行哪个层级，因此宁可变慢，也不要盲目运行。只在完整运行**通过**时写入 stamp，这样失败后下一个会话仍会运行完整测试集。
     选择 probe 的案例不能是“前 N 个”：它需要一个必须触发的案例和一个必须静默的案例，否则两个退化方向无法同时覆盖。注意某个必须静默的案例可能实际上是空洞的——一个仅提供 advisory 的 hook 总是退出 0，因此 `run` 风格的退出码行无法证明其中不存在误报，断言必须采用 `says` 风格（#40、#14）。
5. **回放真实命令语料，并手动检查每次拦截**（规则 9）——这一步测量误拦截面，而第 4 步的 fixture 表在结构上无法测量该指标。逐字提取已发布的 detector 进行预过滤；将每个候选项连同其真实 transcript 和 `session_id`，在临时的 `TMPDIR` 下交给真实 hook。
6. **Symlink** 到 `~/.claude/hooks/`（规则 3）。
7. 在主 `settings.json` 中**注册**，并使各 profile 收敛（规则 4）。
8. 对于 Tier-0/不可逆操作，添加**人工确认释放门禁**（规则 4）。
9. **持久化**：将 SSOT 提交到其私有 repo。可选地添加一行 CLAUDE.md（正文说明*原因*及替代方案；hook 负责强制执行）。

## 已知陷阱（调试失效 hook 前请阅读）

完整目录（症状 → 原因 → 修复）：[references/hook_pitfalls.md](references/hook_pitfalls.md)。
重点包括：`stdin` 被 `python3 - <<PY` heredoc 消耗（hook 静默地允许一切操作）、awk 拆分导致的误阻止（规则 1）、损坏的 hook 污染会话（规则 2）、Python *注释*中的引号或反引号静默破坏 `python3 -c "…"` 代码块且不产生语法错误（陷阱 #9——应改用模式 E 中带引号的 heredoc 形式）、静态环境变量逃生通道（规则 4）、多配置文件注册不完整、提交消息作为伪命令文本到达 walker，导致除非豁免 `git` 写入片段，否则会误阻止你自己的修复提交（#7），以及从命令文本解析出的路径保留了字面量 `~`，使守卫在没有任何症状的情况下**默认放行**（#10——这是唯一一种你无法等到它显现的情况，因为沉默就是它唯一的信号），某个分支读取 hook 自己被截断的显示字符串（#12），或者依赖本仓库并不遵循的命名约定（#13）——当测试套件只断言退出码时，这两种问题都不可见（#14）——仅仅**包含**重定向的命令文本被算作写入（#15），以及 hook 所**要求的修复操作会重新激活它自身**，导致循环；由于即时状态 fixture 从结构上无法发现不终止，即使自测结果为绿色也可能如此（#16，规则 7）。

**测试 harness 才是隐藏变量——使用 `scripts/test_hook.sh`，不要手写。**下面每一种手写测试失败模式都会产生与正常通过完全相同的输出，因此看起来像是成功（2026-07-22，在修复 Stop hook 的白名单时，一次就遇到了三个）：

1. **事件形状错误。**Stop hook 读取的是 `last_assistant_message` / `transcript_path`，而不是 `tool_name`/`tool_input`。传入一个 PreToolUse 形状的事件后，它找不到文本 → 退出 0 → “没有误阻止！”
2. **JSON 引号错误。**单引号中的 `'{\"a\":1}'` 会输出字面量反斜杠-引号；`json.loads` 抛出异常，而 hook 中的 `2>/dev/null || exit 0` 会将其吞掉，于是每个用例都“通过”。
3. **测试用例正好属于规则合法豁免的情况。**基线字符串使用了规则**特意豁免**的字符串（守卫会标记形如 `<name> Group` 的自造昵称，但豁免普通短语 `in the group` / `group chat`——而基线行碰巧使用了其中一个）。原本用于证明守卫仍会生效的那一行没有触发守卫，于是整个测试套件显示为绿色。

**如果 hook 的产物是它输出的消息，那么退出码无法测试这一点。**阻止型 hook 的契约主要是退出码，因此 `run` 行可以覆盖它。但如果 hook 存在的目的就是“说些什么”——例如 PreToolUse 对正确替代方案的解释、Stop 提醒——那么它还有第二个输出通道，而退出码看不到这个通道：破坏措辞、反转条件段落、让 heredoc 吞掉一整个部分，退出码仍会保持为 2，同时每一行测试都通过。添加来自 `scripts/test_hook.sh` 的 `says <label> <event> <pattern> <yes|no>` 行，断言**两个 fixture 中的两种极性**（对于它所针对的输入，内容存在；对于它跳过的相似输入，内容不存在）——单独的 `want=no` 在 hook 完全不输出任何内容时也会因空验而通过，因此它只有与一个证明 hook 确实会输出内容的 `want=yes` 行并列时才有意义。匹配**固定字符串**而不是正则表达式：值得断言的短语通常包含方括号，而在 BRE 中 `[skill]` 是一个字符类，会匹配包含 s、k、i 或 l 的任意文本。然后**通过变异来证明这些行确实能够失败**：复制 hook，注入每一行声称能够捕获的确切 bug，并确认该行变红。在你观察到测试因正确原因失败之前，一个绿色的测试套件不携带任何信息——曾经有两个真实 bug 在一个完全绿色的 24 用例测试套件中存活下来，因为每一行都只检查退出码（陷阱 #14）。

常见的形态是：**所有情况都通过是一种危险信号，而不是放行信号。** `test_hook.sh`
会从结构上捕获上面的第 1 和第 2 种形态——它会为每一行 `run` 断言一个明确的
`expected-exit`（而不是问“它是否打印了某些内容”），并强制要求触发器行与看起来正常的
相似行同时存在，因此返回 0 的触发器行会明确失败，而不会悄悄混在其中。它
**无法**捕获第 3 种形态：某一行的内容是否意外落入豁免条件，这是你所编写内容本身的
属性，没有任何测试框架能够知道你的规则意图。对此只能依靠一种习惯来捕获——先断言一个
已知应当触发的触发器；如果它没有触发，先怀疑测试行，而不是 hook。
