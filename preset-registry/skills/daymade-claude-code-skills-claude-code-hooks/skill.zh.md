# Claude Code Hooks

Claude Code 会在工具调用边界触发 **hooks**。hook 是一个从 stdin 接收 JSON 事件的 shell 命令；对于阻塞型 hook，它通过自己的**退出代码**决定工具调用是否继续。这是唯一能够*从结构上*阻止某种行为的机制——CLAUDE.md 中的文字规则只是建议，可能被完成驱动覆盖；而 hook 是一道墙。

## 何时应该使用 hook（以及何时不该使用）

当**某条规则即使已经写明，仍然不断被违反**时，就应该编写 hook。判断信号是：你添加了文字规则，内容清晰易懂，但该行为仍再次发生——因为在采取行动的那一刻，注意力 100% 集中在“把事情做完”上，提醒就失效了。这种重复发生，就是应该将规则从文字（建议性）迁移到 hook（强制执行）的信号。治理方面的经验法则：*Tier-0 不可逆操作 + 只有文字规则、没有 hook → 它应该成为 hook。*
（这里的 **Tier-0** = 一种无法在会话内部撤销其损害的操作：销毁未提交的工作、将机密推送到远程端、删除文件、向外部发布内容。判断标准是可逆性，而不是严重程度。）

在以下情况下，**不要**急于使用 hook：该规则实际上从未重复出现过（不要为假设性的错误预先构建防护——付出了成本，却没有已证实的收益），或者这条“规则”属于没有机械特征的判断（hook 只能匹配令牌/模式；它无法判断一个设计是否优秀）。

如果症状是“它一直在审查 / 等待 / 重试”，不要假设答案是再添加一个 hook。首先完成规则 7 中的**循环契约**，并阅读[pitfall #36](references/hook_pitfalls.md#36-a-self-applied-review-rule-can-loop-without-any-hook)。循环可能完全是由 agent 反复应用一条文字规则造成的。

## Hook 类型及退出代码的含义

| 类型 | 触发时机 | Exit 0 | Exit 2 | Other |
|---|---|---|---|---|
| **PreToolUse** | 工具运行前 | 允许 | **阻止**调用（stderr → 作为指导信息显示给模型） | 任何其他退出代码 = “non-blocking error” → **调用继续执行**——但仅当 stdout 不包含有效 JSON 时成立。Claude Code 会在**每个**退出代码下读取 JSON 输出，而有效 JSON 会完全覆盖退出代码的作用。此处的骨架不会向 stdout 打印任何内容，因此其 fail-open 推理成立；如果添加 `permissionDecision` payload，退出代码就不再是决定因素 |
| **PostToolUse** | 工具运行后 | 保持静默，**除非它在 stdout 上打印 `hookSpecificOutput` JSON——这就是注入上下文的方式，而且发生在 exit 0 时** | 向模型提供反馈（无法撤销已运行的工具） | — |
| **SessionStart** | 会话开始时 | 继续 | **无法阻止**——stderr 会向用户显示 hook-error 通知，Claude 看不到该通知，会话仍然启动 | **仍然使用 exit 0**：不是因为非零退出代码会阻止启动（它做不到），而是因为任何非零退出代码都会在每次会话开始时，导致用户的记录中出现 `<hook> hook error`。它接收一个用于匹配*会话启动方式*的 `matcher`——`startup`、`resume`、`clear`、`compact`、`fork` |
| **Stop**（+ `SubagentStop`） | 模型即将结束响应时 | 允许其停止 | **阻止停止**——迫使模型继续执行（stderr → 作为原因反馈回去） | 循环安全：hook 会检查 `stop_hook_active`（这是必要条件，**但不是充分条件——见规则 7**）。harness 的连续阻塞上限（默认为 8）**不是**通用的后备保护——其计数器会在任何执行了工具的继续操作中重置，因此对于修复措施涉及工具调用的 hook（绝大多数 hook 都是如此），该上限永远不会触发（#27）。请自行设置上限。同一事件的所有 Stop hook 都会**并行**运行——一轮阻塞可以携带多个 hook 的反馈 |

- **PreToolUse** 是阻止 *tool call* 的主力 — 这张表中的四种类型是本文件讲解的类型，并不是所有可阻止事件的完整集合；而且，**official** hooks reference（docs.claude.com / code.claude.com，而不是此 bundle 中的 `references/` 文件 — 后者只涵盖上述四种类型）现在列出了更多可阻止事件，包括 `UserPromptSubmit`、`PreCompact`、`TeammateIdle`，以及任务和配置事件。如果你需要 gate 的不是 tool call，请先查看那里，而不是强行将其归到 PreToolUse 上。
  `matcher` 选择工具（`Bash`、`Agent`、`WebFetch`，……）— **而它的匹配方式取决于你使用的字符**：只包含字母、数字、`_`、`-`、空格、`,` 和 `|` 的 matcher 会作为**精确字符串**进行比较（或者作为由 `|`/`,` 分隔的精确字符串列表）；任何其他情况都会被视为**未锚定的 JavaScript 正则表达式**。两个方向都会悄无声息地造成问题 — `Edit.*` 也会匹配 `NotebookEdit`（应将其锚定为 `^Edit$`），而 `mcp__memory` 则什么也匹配不到，因为它只包含精确匹配字符，且没有工具的名称恰好是这个字符串（你需要的是 `mcp__memory__.*`）。匹配区分大小写。退出码 2 会阻止操作，而 hook 的 **stderr** 会成为模型看到的消息 — 所以应在其中说明*原因*和*正确的替代方案*，不要只写 `"blocked"`。
- **PostToolUse** 无法撤销操作，但可以**注入权威上下文**，让后续的幻觉无法成立（例如，在 commit 后重新读取真实的 git HEAD 并将其展示出来 — 面对注入的事实，模型无法再“相信自己已经完成了 commit”）。
- **SessionStart** 用于对**防护机制本身进行健康检查** — 健康时保持静默，出现故障时发出警告，并始终退出码为 0。注意其**原因**：并不是因为非零退出会阻止 session（它做不到），而是因为这样会在每次 session 启动时打印 hook-error notice，直到有人修复它为止 — 一个在启动时总是虚惊的检查，最终会让人学会直接滚动略过它。
- **`set -euo pipefail` 与 `set -uo pipefail` — 应根据 contract 进行选择，并且要知道有两种方式可以维持始终退出码为 0 的 contract。** 可能阻止操作的 hook（PreToolUse）需要 `-e`：意外失败导致脚本中止是可以接受的，因为调用方会将非 0/2 的退出码视为“继续”。contract 为 **ALWAYS exit 0** 的 hook（PostToolUse injectors、SessionStart checks）有两种合理形式：(a) **去掉 `-e`**，并对每条有风险的命令使用 `||`-guard — 启用 `-e` 时，一条正常地查找不到内容的 `grep` 就会让 hook 中途终止，而 CLI 会显示一条没有具体内容的 `Failed with non-blocking status code`（陷阱 #8，Pattern E 的形式）；或者 (b) **保留 `-e`，并添加 `trap 'exit 0' ERR`**，这样任何失败都会转化为退出码 0，同时 `-e` 仍会守护底层流程（`git-commit-headcheck` 的生产形式，Pattern D）。两者都正确；不能做的是只使用 `-e`，却既没有 trap，也没有 `||`-guards。经验法则：**对于做出决策的 hook 使用 `-e`；对于进行报告的 hook，去掉 `-e` 或为其添加 trap**（陷阱 #8）。
- **Stop 是特例，也是最常被误用的类型**：它是**唯一**能够对模型**刚刚自行生成的内容**（模型自己的回复文本）作出反应的 hook 类型。其他所有 hook 类型 — 包括听起来似乎适合监管“说了什么”的 `UserPromptSubmit` — 都只能看到**用户**的输入；从结构上来说，它无法看到模型在**当前轮次**自行生成的输出（这一点成立 — 这仍然是将此类规则交给 Stop 的正确理由）。不过，这一保证并不延伸到证明 `.prompt` 字段始终源自键盘输入：后台任务通知自身的报告文本也可能填充该字段，而 stdin JSON 中没有任何内容标记这两者的区别 — #30。类似“模型不得为未经验证的事物凭空编造简写名称”的规则应放在 Stop 上；如果改放到
  `UserPromptSubmit`，那么它将 (a) 一次也捕获不到它原本要防止的内容，因为该文本根本不会流经该事件；同时 (b) 每当用户自己的无关输入碰巧包含触发模式时，错误地阻止用户输入。这是类别错误，而不是调参问题 — 在错误的事件上进行多少正则表达式优化都无法修复它。完整 contract（`last_assistant_message` 与 `transcript_path`、以及反循环检查）见 [references/hook_patterns.md](references/hook_patterns.md) 中的 Pattern E。
- **Stop 有两个阻止通道，且具有相同的循环保护 — 应根据意图进行选择，并让第一次（也是唯一一次）阻止包含全部信息。** `decision: "block"` + `reason`，或普通的退出码 2 + stderr，会显示为 hook *error* — 适用于硬性 gate（“这绝对不能成立”）。`hookSpecificOutput.additionalContext` 会以中性的 “Stop hook feedback” 显示，且不会产生错误通知 — 适用于模型应当权衡的指导和提醒，而不是硬性 gate。两者都会计入上表中的连续阻止上限，因此选择的是语气，而不是安全性。这对消息设计意味着：被阻止的重试轮次（`stop_hook_active: true`）会**连同所有仍然存在的违规一起**放行 — 因此 Stop guard 恰好只有**一次有效阻止机会**。（只有当你的补救方式是“重写回复”时，上限才会进一步强化这一点；如果补救方式涉及 tool calls，计数器会重置，上限永远不会触发 — #27。无论如何，一次有效阻止的结论都成立，因为它依赖的是 latch，而不是上限。）应在这一次阻止中报告**所有**发现的问题（只打印第一个问题的 guard 会永久丢失其余问题 — 陷阱 #17），并将消息写成一份说明如何脱离困境的手册，明确指出可接受的修复方式，而不是给出判决 — 模型要么在一轮内收敛，要么就在不断猜测中耗尽上限。v2.1.145+ 的输入 `background_tasks` / `session_crons` 允许阻止型 hook 区分“session 已完成”和“session 只是暂停、正在等待后台工作” — 阻止暂停会迫使模型进行无意义的后续操作，并浪费同一个上限。

完整可运行的骨架：[references/hook_patterns.md](references/hook_patterns.md)。

## 骨架（PreToolUse Bash guard）

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS= read -rd '' INPUT || true                 # builtin; NOT $(cat) — see below
# 0-fork fast path: a builtin `case` on the raw JSON, BEFORE paying for python3.
# Your guard runs on EVERY matching tool call, so the irrelevant path is the one
# that has to be cheap. Keep this filter BROADER than what you actually block and
# never flag-level — it answers "is this even about X", nothing finer (#22).
case "$INPUT" in *TRIGGER*) ;; *) exit 0 ;; esac
TOOL=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_name',''))" 2>/dev/null||echo "")
[ "$TOOL" != "Bash" ] && exit 0                # only guard the tool you mean to
CMD=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" 2>/dev/null||echo "")
[ -z "$CMD" ] && exit 0
printf '%s' "$CMD" | grep -qw 'TRIGGER' || exit 0   # precise relevance check
# ... precise detection here ...
if <command actually does the banned thing>; then
  echo "BLOCKED: ... WHY ... USE INSTEAD: ..." >&2   # stderr = the guidance shown
  exit 2
fi
exit 0
```

**前两行并非风格问题。**`INPUT=$(cat)` 加上每个
`printf … | python3 -c …`，会在这个 hook 匹配的每次调用中创建进程，**包括那些它无话可说的调用**。大约 13 个 Bash-matcher hook × 并行会话 × 亚秒级工具调用频率，导致持续产生每秒 40–200 个纯粹用于 guard 开销的进程，并让 Gatekeeper 在没有任何失控进程的情况下登上全天 CPU 排名榜首——整个 fleet 没有问题；有问题的是*无关路径*每次调用的开销（#22，其中包含按 guard 转换的步骤以及实测下限）。

在你把 `case` 这一行复制到其他地方之前，有三个注意事项——第一条决定了它究竟是快速路径还是绕过路径：

- **粗粒度过滤器必须是你所拦截内容的超集，而原始子字符串测试并不是。**`TRIG''GER -x` 会运行 `TRIGGER`——bash 会在执行前拼接掉引号——但原始事件文本中不包含 `TRIGGER` 子字符串，因此单独的 `case "$INPUT" in *TRIGGER*)` 会退出 0，guard 根本看不到它。**实测**：将这一行原样放入已发布的 Pattern A 后，`TRIG''GER -x` 会从退出 2 变为退出 0，形成完整绕过——而 `scripts/test_hook.sh` 仍然报告 21 pass / 0 fail，因为没有任何测试行带有经过拼接的 trigger。Pattern A 已经包含了修复及其原因（“反拼接——去除引号和反斜杠——然后再次检查；误报阴性会造成完整绕过”）；放在该反拼接步骤**之前**的粗粒度过滤器会使其无法触达。按优先顺序，有两种安全形式：
  **过滤拼接无法影响的内容**——JSON key 或 tool name（`case "$INPUT" in *'"tool_name":"Bash"'*)`），因为引号拼接存在于
  *command* 文本中，无法改写事件自身的结构；或者**在过滤器内部进行反拼接**，再进行测试（从输入副本中去除 `" `、`'` 和 `\`，然后匹配）。优先选择第一种：它不需要进行复杂的转义操作，而一个必须正确处理自身引号的过滤器，也可能在不知不觉中出错。上面的骨架按原样使用时是安全的，
  只是因为它自身的检测同样是简单的单词匹配；一旦过滤器下面的 guard 比过滤器更智能，真正做决定的就是过滤器。

- **这个骨架对无关输入是放行失败（fail-open）的**（`grep -qw … || exit 0`），所以在它前面加一个粗粒度过滤器改变的是成本，而不是语义。**放行失败的守卫则不同**：一个简单的子字符串过滤器会悄悄地把它的契约从阻止未知输入变成允许未知输入（实测——`'not json'` 直接穿过了这个修复的第一道过滤），而单独使用 `*tool_name*` 标记又会从另一侧重新打开同一个漏洞。在为一个本应对格式错误的输入执行阻止的守卫设计快速路径之前，先阅读 #22 的门控要求。
- **脚本之上还有一层成本更低的机制。** hook 处理程序可以在注册时携带一个 `if` 字段——例如 `"Bash(git *)"` 这样的权限规则语法——当不匹配时，hook 命令**根本不会运行**：因为没有进程，所以连一次 fork 都没有。它在设计上是尽力而为的（文档说，当 Bash 命令无法解析时，它会放行失败，仍然运行你的 hook），因此应将其视为成本优化，**绝不能将其作为门控**——脚本内的检查仍然负责做最终决定。这里有三个容易踩坑的地方：它严格只支持一条规则（不支持 `&&`/`||`），只会在工具事件上求值，而且在非工具事件上设置了 `if` 的 hook **完全不会运行**。

## 将可用的守卫与污染会话的守卫区分开的规则

这不是风格偏好——每一条都对应于我们实际发布过、并追溯到根因的具体故障。

### 1. 使用 shlex 在**令牌级别进行匹配**，绝不要对原始字符串使用 awk 拆分

一个**错误阻止正常命令的守卫，比漏报的守卫更糟**——必须绕过的守卫会被人下意识地绕过，最终它什么也保护不了（核心原则：*误杀健康输入比漏报更糟*）。错误阻止反复出现的根因，是对原始命令字符串进行匹配。


- **错误做法**：使用 `awk '{gsub(/&&|\|\||;|\|/,"\n")}'` 拆分命令段——awk 不理解 shell 引号，因此 `grep -E "a|TRIGGER|b"` 会在带引号的正则表达式内部的 `|` 处被拆开，`TRIGGER` 变成一个虚假的命令，守卫于是阻止了一条普通的 grep 命令。（于 2026-07-21 发布；这个守卫第一次真正使用时，就错误阻止了我自己的 grep。）
- **正确做法**：使用整个命令的 **`shlex.shlex` 类**进行令牌化，而不是 `shlex.split()` 函数——只有当 `| ; & < >` 由空格分隔时，`split()` 才会将它们视为分隔符，因此 `ls|TRIGGER x` 会被令牌化为 `['ls|TRIGGER', 'x']`，你的命令位置检查根本看不到 `TRIGGER`（实测；启用 `punctuation_chars=True` 的类会得到 `['ls', '|', 'TRIGGER', 'x']`）。不要随手写一行代码，而应原样复制一个已经发布的 walker——但**要复制通过 `scripts/test_hook.sh` 的那个**，也就是 **Pattern A**。 [walker 部分](references/hook_patterns.md#the-shlex-command-position-walker) 是一种*紧凑*形式，并且明确说明了这一点：它省略了每个 wrapper 的带值标志表，因此无法检测出位于**带值标志 wrapper**之后的目标——实测中，对于 `timeout 5 TRIGGER`、`sudo -u root TRIGGER` 和 `nice -n 10 TRIGGER`，它都会返回“不在命令位置”，而 Pattern A 的版本可以捕获这三种情况。（`sudo TRIGGER` 这种不带参数的形式在两者中都没问题——紧凑表不知道要跳过的是 wrapper 自身需要参数的标志。）已发布的测试工具中只有其中一种形式，因此你实际看到的运行结果是：针对 Pattern A 版本为 21/0，而针对紧凑版本，在 `wrapper-timeout` 上是 **20 通过 / 1 失败**；另外两种形式由于没有对应的测试行，会静默失败。带引号的 `"a|TRIGGER|b"` 会保持为**一个令牌**，因此正则参数绝不会被误认为是命令。然后检查目标是否处于**命令位置**（`token[0]`，或紧跟在 `;`/`&&`/`||`/`|` 分隔符之后，同时跳过 `VAR=val` 环境变量赋值前缀）。命令位置 walker 见 [references/hook_patterns.md](references/hook_patterns.md)。
- 推论：`echo "…TRIGGER…"`, `grep TRIGGER`、`# TRIGGER`、`man TRIGGER` 都必须通过。你的测试集**必须**包含这些“提及但未执行”的情况。
- **推论——在它们到达 walker 之前，先豁免 `git` 写入命令段。** 提交消息是任意数据，整段消息文本会以伪命令文本的形式进入你的命令位置遍历——`git commit -F - <<EOF` 的正文如果包含引用 `foo|TRIGGER` 的内容，就会把 `TRIGGER` 放到命令位置，守卫会阻止它自己的修复提交（陷阱 #7 正是这种情况，而且已经发布）。任何检查命令字符串的 Bash 守卫，都必须跳过命令头为 `git` 加上 `commit`/`rebase`/`tag`/`am`/`cherry-pick` 的命令段——并且要在整个命令级别、任何按行拆分之前完成这一步（Pattern A 展示了这一顺序；生产版本使用 `lib-git-commit-detect` 的相邻性检查）。
- **推论——walker 之所以分两阶段是有原因的。** `whitespace_split=True` 会将换行视为普通空白，因此多行代码块（`cd /x\ngit add\nTRIGGER -y`）会被压缩成一个以 `cd` 为头的命令段，触发器永远不会处于命令位置——在真实记录中重放时，触发率为 0（陷阱 #11）。应先以 shell 感知的方式按行拆分（遵循引号状态和反斜杠续行，因此带引号的多行字符串不会被分割），再对每一行执行 shlex walker——Pattern A 和 walker 部分都提供了该拆分器（`split_shell_lines`，已在 qlmanage-guard 中经过生产验证）。即使它也无法解析的，是 heredoc 正文（这不是引号语法）；何时接受这一残余风险，由 #11 决定。
- **但 shlex 不是银弹，检测的*内容*会决定放行失败是否安全。** `shlex.split()` 本身会在引号不配对时抛出 `ValueError`——多行 `git commit -m "…` 消息中带有 `#` 或未闭合引号，就是典型触发条件。此时 `except ValueError: cmd.split()` 的回退会*放行*，当你检测的是**被禁止的修饰符**时这是正确的（是否携带 `--no-verify`？——漏掉它反而是安全的，符合规则 1 的方向），但当你检测的是命令**是否就是你的目标命令**时则很危险（这是 `git commit` 吗？——此处的 ValueError 会导致守卫无法识别该提交命令，并静默地不触发；确实有一次跨域提交因此在没有确认对话框的情况下发布了）。对于“这是否是该命令”的判断，应优先使用一种窄范围的**正则表达式**（`git` 和 `commit` 作为独立单词，中间允许出现任意标志令牌），它不会受到多行引号破坏令牌化的影响；而 shlex walker 应保留用于*命令位置 / 修饰符*检查，在这些检查中，放行失败的方向是安全的。 （边界是：当谓词是“这是否完全是某个特定的常见命令”——`git commit`、`git push`——而该命令自身的消息/参数会破坏令牌化时，使用正则；当谓词是“命令位置上是否存在一个*被禁止的*命令或修饰符”时，使用 walker——此时被禁止的内容很少见，ValueError 导致的放行失败反而是安全的，符合规则 1 的方向。）

### 2. 在注册前端到端地使用 **bash -n + 真实 JSON 事件进行测试**

**一个损坏或逻辑错误的 PreToolUse hook 会污染整个会话** —
后续每次 Bash 调用都会被截断／重复／错误地判定失败／看起来像是产生了幻觉式执行，而你会把问题归咎于“环境”，实际上罪魁祸首是你刚刚安装的 hook。（2026-07-05：一次编辑中 `[^;&|]` 正则表达式损坏，`;&` 变成了 bash 的 case-fallthrough token，导致半个会话被污染，直到 `bash -n` 才发现问题。）“部署时测试通过”还不够 — 文件可能在后续编辑中损坏。

在注册任何 hook 之前执行以下检查：
```bash
bash -n hook.sh                                # syntax
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<trigger case>"}}'    | ./hook.sh; echo "exit=$?"  # want 2
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<healthy lookalike>"}}'| ./hook.sh; echo "exit=$?"  # want 0
```
将测试工具一起打包：[scripts/test_hook.sh](scripts/test_hook.sh) 会运行一整套触发／放行用例。**自我阻断陷阱：**一旦 hook 在会话中生效，就不能通过在你自己的 Bash 命令中放入触发字符串来测试它 — 已生效的 hook 会阻断你的测试命令。将用例放入**脚本文件**中，然后运行 `bash test_hook.sh`；外层命令不包含触发字符串，因此不会被自身阻断。

**一旦某个 hook 导致过一次真实事故（误阻断或静默漏检），仅靠独自重新阅读代码是不够的** — 某个 Stop-hook guard 在同一天内被作者重写后，修复首个 bug 时又被重新引入了两次；其中一个问题是 Python 注释中的引号，在重新阅读时不可见，只有运行实际失败的 JSON 用例才暴露出来。此时应升级为多视角 agent-team 审查，其中每个发现都必须通过对 live script 执行真实 payload 来复现，而不能仅通过阅读代码并达成一致 — 这就是通用的 Counter Review 方法（skill-creator 的 `skill-development-methodology` 参考文档，Phase 6），只是将其应用于 hook 而非 skill。在一次这样的审查中，3 个视角（匹配逻辑／shell 嵌入安全性／事件契约健壮性）发现了 13 个经过确认且可独立复现的 bug，以及 1 个其所引用证据最终被证明是虚构文档引文的发现 — 之所以能识别出来，仅仅是因为验证者被要求 curl 原始来源并 grep 精确字符串，而不是盲目信任引用。

### 3. 使用 SSOT + symlink，避免重新安装时静默解除 guard

将真实脚本放在版本控制目录中，并**symlink**到 Claude 读取的 hooks 目录：
```
~/scripts/claude-hooks/<name>.sh      # SSOT (this setup: a private git repo)
~/.claude/hooks/<name>.sh             # symlink → SSOT

# install / recover:
ln -s ~/scripts/claude-hooks/<name>.sh ~/.claude/hooks/<name>.sh
```
重新安装 `~/.claude` 会清除 hooks 目录；symlink 的目标仍然保留，恢复时只需执行一次 `ln -s`。一个悬空 symlink 会在**完全没有任何信号**的情况下禁用 Tier-0 guard — 这正是为什么需要 SessionStart health check（规则 4；可运行的 skeleton： [references/hook_patterns.md](references/hook_patterns.md) 中的 Pattern C）。

### 4. 注册是按配置文件分别进行的——让所有配置文件收敛，通过**人工**闸门发布

- **有两个注册入口，而健康检查可能只监视其中一个。** 除了下面的配置文件设置之外，仓库自己的 `.claude/settings.json`（以及 `settings.local.json`）也会为该仓库中的会话注册 hooks。它们位于 `~/.claude/hooks/` 之外，因此遍历该目录的防护检查完全覆盖不到它们——语法、路径、`--selftest`，什么都检查不到。两个静默失败曾经被发布在这样的文件中，并在一个本来就是为了防止此类问题而构建的 SessionStart 健康检查下存活了两个月（#38、#39）。项目 hooks 应使用**绝对**路径注册——相对路径会相对于会话 cwd 解析，第一次有人从子目录启动 `claude` 时就会失效——并扩展健康检查，使其从事件的 cwd 开始向上查找项目设置。
- 如果*活动配置文件的* `settings.json` 没有调用 `~/.claude/hooks/` 中的某个 hook，那么这个 hook **什么也保护不了**。多配置文件用户曾经在所有配置文件收敛之前一直处于零防护状态。在**主**配置文件的设置中注册（本配置中是 `~/.claude/settings.json`；[references/hook_patterns.md](references/hook_patterns.md) 的 Registration 部分包含确切的 jsonc 结构）——PreToolUse → matcher `Bash` → 你的 hook——然后让其余配置文件收敛（本配置使用 `sync-profile-settings.py --all`，由 `claude-switch-models-setup` skill 负责）。SessionStart 健康检查会 grep 每个配置文件中的 Tier-0 防护，以捕获漂移。CLI 的文件监视器会发现设置编辑（官方 hooks 文档），因此无需重启即可使注册生效——可以通过观察防护在安全探测上触发，或在下一次会话的健康检查行中确认。
- **如果防护需要释放阀门，就使用*人工*闸门，而不是环境变量。** 静态的 `GUARD_OK=1` 逃生口不算闸门——模型可以自行设置该环境变量。使用原生 macOS 对话框（`osascript`——模型无法点击）；拒绝/取消/超时 = 硬性 NO；将每次提示/绕过都记录到审计文件中。模式见 [references/hook_patterns.md](references/hook_patterns.md)。
  - ⚠️ **`/dev/tty` 不是第二条通道——文档说明 hooks 无法打开它。**
    这个文件过去曾规定除了对话框之外，还要在 `/dev/tty` 上输入 `YES`。
    官方参考文档明确指出：hooks “在自己的会话中运行，**没有控制终端**”，并且“hook 进程及其任何子进程**无法打开 `/dev/tty`**”（`terminalSequence` 是文档中用于向其写入的替代方案）。因此，用这种方式构建的“​​双通道”闸门实际上是一条通道加上无效代码，而且在没有 GUI 会话的机器上，任何人都无法批准该闸门。
    这与本地观察结果一致，不过请仔细理解边界：在某个配置的共享审计日志中——共有 1,801 条记录，多个防护都向其中写入，其中三个实现了 tty 通道——**360 行带有通道标签（236 次对话框确认、124 次拒绝或超时），但没有任何一行以任何形式提到 tty 通道。** 这意味着 tty 分支从未被*进入*；在 macOS 上，这正是你本来会预测到的结果，因为对话框会先得到回答并将其短路。因此，日志表明这里没有任何行为依赖 tty；是文档，而不是这次测量，确立了 tty 完全无法工作这一点。
    保留对话框；如果需要非 macOS 闸门，就需要一种本文件尚未验证答案的通道。
  - ⚠️ **一个存活时间超过 hook 超时的人工闸门会失败开放。** Hook `command` 的超时默认为 600s（`UserPromptSubmit` 为 30s），而超时的 hook **不会阻止工具调用**——因此，未响应的对话框不会变成“否”，而会变成允许。将等待时间限制在远低于超时的范围内，并让无回答在 harness 替你处理之前先由你自己解析为阻止。
  - 文档还提供了一条 UI 内通道——PreToolUse `hookSpecificOutput` `permissionDecision: "ask"`，它会通过 Claude Code 自己的界面发出提示。了解这一点很有价值，但**这里尚未在 `bypassPermissions` / 自动接受模式下验证**，而这恰恰是 Tier-0 闸门必须能够经受的模式；之所以规定使用对话框，是因为它不依赖权限模式。
  - **在 Tier-0 以下、允许模型自行处理的逃生口存在的地方，应让它成为正确的用法，而不是绕过标志。** 上述规则对 Tier-0 是绝对的，在这里不会放宽——这里讨论的是那些达不到 Tier-0 的正确性防护，它们仍然需要为检测器无法区分的合法情况提供退出方式。问题在于，你要让这个退出方式*是什么*。`SKIP=1` / `--force` 环境变量逃生会准确训练规则 1 所警告的那种条件反射，而且在截止期限压力下，它与绕过没有区别。应优先选择一种**本来就希望他们执行的操作**作为逃生方式，这样采取它会改进命令，而不是解除防护：`pipe-fallback-guard` 一旦命令提到 `pipefail` / `PIPESTATUS` / `pipestatus` 就退出并返回 0，因为写出这些内容的作者已经证明自己理解管道退出码——防护已经没有什么可教他们的了。应采用的测试是：*如果有人使用我的逃生口，最终生成的命令会更好吗，还是仅仅被解除阻止？* 如果诚实的答案是“仅仅被解除阻止”，那么你拥有的就是一个换了好听名字的绕过标志。Tier-0 情况的同源原则是，覆盖仅用于测试闸门时：**逃生口只能让闸门更加严格**——参见 [references/hook_patterns.md](references/hook_patterns.md) 中关于 `GIT_GUARD_TEST` 的讨论。

### 5. 判断失败的**方向**，并测试*这一点*——不要只测试成功路径

规则 1 对*检测调优*错误进行了排序：在守卫已经运行的前提下，错误拦截一个正常命令，比漏掉一个罕见的错误命令更糟，因为必须绕过的守卫会被人条件反射式地绕过。**本规则讨论的是另一个维度——守卫的机制根本没有运行**——因此这里并没有反转“哪种更糟”的判断；这两个排序从未交汇。调优失误只会让你漏掉一个案例；而这会让守卫在所有符合该形态的输入上悄无声息地失效。

失败情形是：守卫**无法获取它据以判断的对象**——解析抛出异常、路径无法解析、依赖缺失、子进程超时——而恰恰是阻止钩子崩溃的 `2>/dev/null || true`，悄悄地把*“我无法检查”*转换成了*“没有需要报告的内容。”* 钩子以 0 退出。**这个输出与真正的通过完全相同**，所以这种问题可以持续数周而不被发现。

因此，在钩子每一个*获取*某项内容的地方（解析命令、读取暂存文件、查询服务），都要明确决定：**如果这里返回空值，是意味着允许还是阻止？**——并把答案写在分支旁边。对于*修饰符*检查，失败开放通常是正确的（是否带有 `--no-verify`？漏掉它只会让你错过一个案例）。对于*这到底是不是目标对象*的检查，失败关闭通常是正确的（这是一次跨域提交吗？空答案意味着守卫根本没有触发）。

**然后测试这个方向，而不是成功路径**：故意传入一个无法解析的路径或无法解析的命令，并断言它仍然按照你的决定执行。一个其中每一行都通过、*只是因为钩子悄悄地放行了一切*的测试套件，与一个真正通过的测试套件无法区分。

**仔细阅读这些结果——相同的输入，对于不同的守卫类别，正确答案可能完全相反。** 以 `cd ~/no-such-dir && TRIGGER` 为例：

| 守卫类别 | 判断依据 | 正确退出码 | 原因 |
|---|---|---|---|
| **令牌匹配器**（这是否是某种被禁止的命令形式？） | 仅命令文本 | **2，阻止** | `TRIGGER` 就在文本中；无法解析的 `cd` 并不会让它不再是一个触发器，而如果守卫在这里保持沉默，那么在 `cd ~/real-dir && TRIGGER` 上它也会保持沉默 |
| **状态推导器**（仓库的暂存集合是否跨越多个域？） | 从磁盘读取的状态 | **0，允许** | `cd` 失败，`&&` 短路，不会发生提交——没有任何需要守护的对象 |
| **终止状态读取器**（修复操作是否已经完成？） | 回执 / 计数器文件（规则 7） | **0，允许**——*当状态文件本身就是终止条件时* | 无法读取回执意味着钩子无法得知自己是否已经触发；在这里失败关闭会导致永久阻塞，同时又没有可执行的修复措施，也没有人类可见的原因——这*就是*循环，而且这是唯一比漏掉一个案例更糟的失败。**反向子情况——复制这一行之前请先读这里：**当状态只是在一个独立谓词之上的**预算**时（通过执行操作仍然可以解除阻止），读取失败时允许会**悄悄禁用整个钩子**——一个不可写的目录就会让它对所有输入永久保持静默，这是最糟糕的失败形态。此时，应回退到*预算存在之前*的行为（继续评估谓词），而不是保持沉默。**用一个问题区分这两种情况：如果状态消失了，修复是否仍然可能？** 否 → 回执情形，允许。是 → 预算情形，继续检查。下面给出经过验证的答案，这样就不必每个人都重新推导：规则 7 的机制 2（回执）**和**机制 3（每会话计数器）都属于**回执情形 → 允许**——机制 3 有意不判断 R 是否发生，因此其计数器是唯一的出口；让它保持静默会使本轮流程陷入困境。预算情形则是：计数器叠加在一个用户仍可自行满足的谓词之上 |

所以，应当在写入该行**之前**决定你的 hook 属于哪个类别，而 harness 的
`unresolvable path` 模板行期望的是 **2**，因为该模板针对的是 token-matcher 类别。弄反这一点，会让一个正确的 guard 得到自信的 FAIL。对于 state-deriving guard，你要查找的失败是：**命令实际上会运行，而 guard 没有识别出来**——不平衡的引号会导致分词抛出异常，fallback 允许通过，于是真正的跨域提交会在没有弹窗的情况下完成（规则 1 的 ValueError 说明）。对于每一行允许通过的记录，都要问：*这个命令实际上会完成该操作吗？* 如果不会，那么允许通过就是正确的。

针对一个真实的 state-deriving guard 运行这条完全相同的探针时，第一次就返回了两个 allow：一个是正确的（上面的短路情况），另一个是真正的 fail-open。**探针会找出问题；但你仍然必须对它找到的内容进行分类**——这就是为什么上面的类别表要放在各行之前。

真实案例（2026-07-22）：一个 scope guard 通过 `git -C "$REPO_DIR"` 读取暂存文件，其中 `REPO_DIR` 是从**命令文本**中解析出来的——因此 `cd ~/repo && git commit` 传给它的是字面量 `~/repo`，`git -C` 执行失败，暂存文件结果为空，于是 guard 得出“没有跨域文件，允许通过”的结论。每个跨仓库提交都未受 guard 保护，而从来没有任何迹象表明出了问题。其构造 + 共享库方面的变体：陷阱 #10。

那个解析器还有第二种失败方向，而且更加棘手。一旦你加入 fallback，使其不再 fail-open，fallback 会因为某个原因而对、因为另一个原因而错——但两者打印出的行完全相同。`git push`（没有显式目标）合理地回退到事件的 `cwd`；`git -C "$R" push` 则**指定**了一个 hook 无法解析的目标，回退到同一个 `cwd`，随后却针对另一个仓库渲染出一个自信的 ✅。这两种情况逐字节完全相同（经过测量，MD5 相等），因此 hook 和读者都无法分辨诚实的判定与绑定错误的判定。**fallback 值必须携带选择它的原因**，只有“没有显式目标”才能得出判定。完整构造、confused-deputy 视角，以及为什么带有字面量路径的 fixture 永远无法捕获这一问题：陷阱 #28。

### 6. 根据世界能够回答的事实进行判定——绝不要根据自己的渲染结果，也不要根据命名习惯

规则 1 和 5 讨论的是*如何*匹配，以及失败时*采用哪种方式*。这一条讨论的是**你所匹配的内容来自哪里**，而且它有两种都会悄无声息的失败形态：

- **绝不要根据你为人类格式化的字符串进行分支。** 如果 hook 构建了一份报告——排序、拼接、截断为前 N 项并附上 `(+M more)` 尾部——然后再根据这份报告对自己的决定进行模式匹配，那么这个分支就会继承渲染过程造成的信息损失。截断线之后的项目对它而言根本不存在，因此该分支在所有较小的 fixture 上都能工作，却恰好会在它原本要处理的较大 session 上停止触发。应当通过单独的通道输出机器事实（一行未截断的 `KINDS:a,b,c`），并匹配该事实。渲染结果是输出，不是数据源（陷阱 #12）。
- **优先使用可检查的事实，而不是命名约定。** 根据路径形状（`/skills?/[^/]+/references/`）进行分类，会将某一种目录布局写死；任何采用其他布局的仓库都会被静默地、永久地分类为 `None`。修复方法**不是**扩大模式范围，因为那只是用全机器范围的误报替代静默漏报（规则 1 明确禁止这种权衡）；正确做法是询问文件系统能够回答的问题——*这个 `references/` 目录旁边是否存在一个 `SKILL.md`？* 事实能够经受布局变化；约定则不能。（当候选对象**本身**是一个 `SKILL.md` 时，就没有可供询问的同级对象——#13 解释了为什么这是规范定义的事实，而不是本规则所警告的命名习惯。）
  **可检查的事实仍然可能是错误的事实——要固定问题的锚点，并按类型过滤。** 下载目录中也可能满足 `test -f SKILL.md`，而某个沿祖先目录查找该文件的 guard 扩大吞掉了整个 home 目录，随后告诉真实 session 去加载一个以该目录命名的 skill——这样的名称不可能存在（规则 9 的事故）。应当将问题锚定在**特定**目录的同级对象上，或锚定在已知的安装路径上；没有锚点的祖先目录遍历，只是披着事实外衣的约定。

两者的共同征兆是：某个分支在生产环境中从未真正触发过一次，但其测试却全都通过。打印原始的格式化前分类结果，你就能看出自己遇到的是哪一种。

### 7. 如果钩子**要求修复**，就证明循环会终止

一个会持续**阻塞**（exit 2），直到 X 完成为止的钩子——尤其是 Stop 钩子，因为它们会在之后每次停止时再次触发——不是检查，而是一个**反馈循环**。
（仅仅*注入*要求并以 0 退出的钩子根本没有循环：没有任何东西会重新评估。这就是下面的机制 0，而且它通常才是正确的默认选择。）

```
condition T is true → hook demands remediation R → model performs R → T checked again
```

**在第一次循环开始前写好循环契约（既适用于由钩子强制执行的循环，也适用于由代理驱动的审查 / 等待 / 重试循环）：**

```text
LOOP KEY: immutable logical target / lineage + one failure axis
FIRE T: the condition that starts another cycle
REMEDIATION R: the exact action one cycle performs
VARIANT V: the well-founded quantity that strictly decreases for this key
BUDGET: maximum cycles, fixed before cycle 1
SUCCESS EXIT: the observable that proves the axis is clear
CAPPED EXIT: what is left blocked / unshipped / pending when the budget ends
```

没有完整的契约，就不能使用阻塞式 Stop 钩子，也不能使用重复的审查或轮询循环。在第一次循环开始前冻结该键。修复快照、提交或审查者名称都必须留在同一条谱系中，不能据此产生新的预算。新的、无关的发现属于**新键**：单独记录；它不会重置本循环的预算。如果某次循环无法指出新的证伪实验或更小的 V，就不会增加任何证据，应当停止。

对于**由代理驱动的独立审查循环**，默认预算是一次初始审查，加上实质性修复后进行一次范围严格限定的重新审查。第三位审查者不会自动加入。如果重新审查仍在同一轴上复现 BLOCKER 或 MAJOR，则保持钩子未注册 / 构件不发布，报告阻塞状态，并要求创建一个新的、经用户授权的任务；该任务必须在第一次循环开始前声明其循环契约和预算。代理自行声明的预算不能授权代理自己。在获得授权的任务中，明确说明现在停止会造成的具体安全或业务失败；可选的润色不符合要求。

填写完成的审查循环示例：

```text
LOOP KEY: <initial frozen commit>'s review lineage + termination-contract fidelity
FIRE T: fresh review reports a same-axis BLOCKER / MAJOR
REMEDIATION R: reproduce that finding, apply one bounded fix, run its narrow check
VARIANT V: 2 - completed review cycles
BUDGET: 2 cycles total (initial review + one re-review)
SUCCESS EXIT: no same-axis BLOCKER / MAJOR
CAPPED EXIT: artifact stays unregistered / unshipped; report remaining findings
```

初始冻结提交的每个修复后派生版本都仍属于该键。当前快照会发生变化，以便审查者检查修复；但其谱系及剩余预算不会变化。

没有任何机械机制会强制执行这个无钩子预算——它只有在代理遵循 Skill 的情况下才有效。正因为存在这一限制，封顶退出状态必须清晰可见，而且绝不能报告为“已完成”。

**如果完成 R 能再次使 T 为真，则循环不会收敛。** 不会报错，不会崩溃；它会一轮又一轮地运行，直到人为中断——这通常确实会发生，因为每一轮都是一个*完整的*修复周期（dispatch、wait、adopt、edit），而不是廉价的重试。**而正是这一特性，使得 harness 的连续 8 个 block 上限也无法拯救你：它的计数器会在每次执行了工具的 continuation 时重置，因此由工具调用组成的修复周期会永远将其固定在 1**（已测量 — #27）。即使它确实最终触发，该上限也只是针对失控会话的兜底机制，而不是设计：这一轮结束时，违规状态仍然存在，而 harness 会将该轮报告为 `reason:"completed"` ——这与真正完成无法区分。“它最终会停止”在任何你所需要的意义上都不算终止，而在这里它甚至不会最终停止。`stop_hook_active` 在这里也**救不了你**——该字段恰好只覆盖**一层重新进入**（“我刚刚阻止的 Stop 正在被重试”）。它对*跨轮次*的情况毫无说明：模型确实执行了 R（真实工作、许多工具调用），然后自然停止；这时这是一个全新的 Stop，该字段为 `false`，hook 会基于同样的理由再次触发。

**这个测试借鉴自程序验证中的终止性证明**——一个[循环变体 / 秩函数](https://en.wikipedia.org/wiki/Loop_variant)：写下一个映射到良基序（通常就是 ℕ）的量 **V**，并证明 **V 在每个 `trigger → remediate → re-check` 周期中都严格递减**。没有 V，就没有终止性证明——不要注册该 hook。

**V 是设计时的义务，不是代码**——你永远不会在 hook 中计算它。实际交付的是*谓词*（下面的机制）；V 则是证明该谓词会收敛的论证。把它写在下一个读者会因此踩坑的位置——脚本头部：

```bash
# TERMINATION: V = 1 - exists(<receipt path>)
# decreased by: R writes the receipt; nothing R does afterwards can remove it.
```

“证明它会递减”归结为三个具体问题，答案应写入该注释中：

1. **R 会改变什么？** 指明确切的文件 / 字段 / 时间戳。
2. **该对象是否是 T 的操作数？** 如果是，并且 R 将其移回“触发”方向 → 就不存在 V。
3. **R 之后，使 T 再次为真所需的最小输入是什么？** 如果答案是“我刚刚触发所用的同一个输入” → 就不存在 V。重新设计谓词；不要重新调整阈值。

**一个真实的反例。** 某个 Stop hook 要求在复合构件（规则文件、skills、其他 hooks）可以被推送之前，先进行一次独立审查：

- **T**（使 hook **触发**的条件）=“存在尚未被任何审查覆盖的编辑”，其实现方式是时间戳比较 `last_edit > last_review`（`last_edit` = 构件集合中最新的 mtime，`last_review` = 审查记录的 mtime —— 两个单独的数值，而这正是该比较让人感觉安全的原因）
- **R** = dispatch 一个独立的审查者

但一项值得运行的审查**是有输出的**：其发现会被**同一个 agent 立即采纳，在它下一次尝试停止之前** → 这会产生新的编辑 → `last_edit` 越过 `last_review` → **T 再次为 true**。（如果是人类稍后在外部采纳了这些发现，就不会形成循环——这个循环需要在同一个 agent 回合内完成修复和重新检查，而这正是 Stop hook 所保证的。）不存在 V——修复不会减少某个量，而是*重置*它。唯一的退出方式是“审查，然后什么都不改”，而这恰恰说明派发审查器是没有意义的。观察结果是：连续三个回合，每个回合都是完整的审查并采纳循环，最终都只有在用户说停止后才退出。

有两点让这一点很难看出来。**孤立地看，这个比较看起来完全合理**——“审查必须比上一次编辑更新”正是你会写出的内容。而且这句话是**通过**条件——T 是它的否定。把它原封不动地记在脑中，不带上那个否定，接下来整个分析中你实际上都在推理错误的操作数；要始终把 T 作为**触发**条件来理解。（把*代码*写成提前退出的守卫子句——`… && exit 0`——是正常的 shell 风格，这不是这里讨论的重点；这里的纪律在于你以哪种方向进行推理。还要注意相等情况：同一秒的 mtime 会落在通过的一侧，也就是 fail-open，这与下面这条规则对状态读取的要求一致。）运行上面的检查清单，结论会机械地显现出来：R 会更改 `last_edit`（Q1）；`last_edit` 是 T 的一个操作数（Q2）；使 T 再次触发所需的最小输入就是修复自身的输出（Q3）→ 不存在 V。

**第二种失败形式：谓词完全看不到修复（可观测性缺口）。** 上面的反例是一个会被修复*移动*的时间谓词。同一类问题中还有一种更隐蔽的失败：修复确实发生了，但谓词用来读取它的通道在当前环境中根本不存在。真实案例（2026-07-26，在一次全舰队循环审计中发现）：某个 Stop hook 通过扫描 tool_results 中的
`agentId: <hex>` 并读取 `subagents/agent-<hex>.jsonl` 来检测“发生过一次独立审查”——这在主配置中是正确的。Team-mode 会话使用完全不同的 schema（生成回执 `agent_id: <name>@session-<uuid>`，交付内容以 `teammate_id` teammate 消息的形式出现，文件为 `agent-a<name>-<hex>.jsonl`）——永远匹配不到任何内容，因此 `last_review` 永远保持为 `None`，每一个 compounding-edit∧push 回合都会再次触发该要求：这是一个误报循环，每个停止序列最多触发一次，但跨回合则无界增长；而该会话中的“2/2 fires”其实都发生在已经完成审查的工作上。同属一类问题，但需要不同的处理方式：时间循环需要更好的*谓词*；可观测性循环需要更好的*通道*。在检查清单中加入第四个问题——**Q4：在这个 hook 将运行的每一种环境中，谓词是否确实能够看见 R 的发生？** 对于读取 transcript 的 hook，这意味着要从每个配置文件/模式中解析真实会话，而不是只对一种 schema 做 fixture 测试。（上面案例的修复方案：多 schema 检测，并排除 teammate deliveries 对回合边界的影响，以免它们截断检测窗口——陷阱 #20。）

**先按轴选择，再按顺序选择——这不是同一件事的五种强度。**
0 决定*是否完全阻塞*；1 决定*挂在哪个事件上*；2–4 是
*谓词的形态*（选择了 1 之后，仍然需要从 2–4 中选择一个）。0→4
的顺序表示“循环被移除得有多彻底”，而且它与“你能施加多少约束”
**成反比**——所以应选择第一个仍能提供你实际需要的约束的选项，而不只是
机械地选择第一个。

1. **将检查移到动作边界。** 如果你想门禁的是一个*动作*——push、publish、
   delete——就用 PreToolUse 保护**动作**，而不是用 Stop 保护**这一轮**。
   **Stop-hook 修复循环通常就是挂错事件的动作门禁**，这正是 hook-types 部分中
   “Stop 是那个与众不同的选项，也是最常被误用的选项”的具体案例。
   **要准确理解这能带来什么。** 只有当模型*自愿重试受门禁的动作*时，PreToolUse
   才会再次触发，而且模型始终可以拒绝并正常结束这一轮。因此它保证的是
   **这一轮会终止**——最坏情况从“这一轮无法结束”降为“这个动作不会发生”。它
   **不会**让一个不收敛的谓词收敛：取上面的反例，将它原样移到 PreToolUse 中，
   循环会完整保留（push →
   blocked → review → findings adopted → new edits → retry → `last_edit` 又领先了
   → blocked）。该案例的问题出在它的**谓词**，而不是它的事件，因此你仍然要从 2–4
   中选择一种形态。还要注意，PreToolUse **没有** harness 兜底——hook-types 表格中的
   8-block 上限仅适用于 Stop——因此，将一个会自行重置的谓词移到这里，得到的安全网
   反而更少，而不是更多。
   ⚠️ 有两种形态下，这个机制是错误的答案：**R 必须使用你所门禁的同一个工具来完成**
   （例如，在 `Edit` 上设置一个要求你先修复文件 header 的保护——这会造成死锁，永远
   没有任何东西能够满足它），以及**一个动作会在同一会话中重复发生**（一个要求
   `git push` 的门禁，处于会 push 五个仓库的会话中 = 五次完整要求；这就是下面
   war story 中的密度问题，而机制 1 并不会让你免受它的影响）。

2. **将“已完成修复”定义为存在性事实，而不是时间事实——并以需要修复的对象作为其键。** 让 R 写入一个工件，并测试*它是否存在*；关键在于：

   ```bash
   KEY=$(git rev-parse HEAD 2>/dev/null || printf 'nogit')   # or a hash of the
   RECEIPT="${TMPDIR:-/tmp}/my-guard.${KEY}.ok"              # reviewed content
   [ -f "$RECEIPT" ] && exit 0            # V = 1 - exists, for THIS key
   ```

   `V = 1 - exists` **按键计算**：每个键只会恰好减少一次，并且*对于该键*永远无法再被推高。新的工作会生成一个*新*键——那是新的需求，而不是重新武装。两种朴素的键设计都不行：一个全局路径会让钩子在每台机器上触发一次，然后永远死寂地停在那里，没有任何信号；而基于时间的键正是本规则要禁止的时间谓词。**时间谓词几乎总是错误的形态**，因为你要求的修复通常正是推动被比较操作数发生变化的因素。
   这个内容 SHA 键对于一次性回执门控是正确的。它并**不会**重新定义代理审查谱系：由该谱系的修复所创建的提交仍然使用其原始键和原始预算。
   ⚠️ 如果**模型**可以创建回执，那么这就是规则 4 中已废弃的 `GUARD_OK=1` 逃生舱，只是换了个新面貌。应让模型无法驱动的对象来写入它（例如审查子代理自己的输出文件、git note），或者接受该钩子只是建议性的，并在其标头中明确说明这一点。

3. **对阻塞性修复循环设置上限——绝不要对反复出现的建议性交付设置上限。** 仅当钩子正在强制执行一个有界循环，且达到上限后的退出明确表示操作仍被阻塞、尚未交付或处于待处理状态时，才在每个会话、每个目标上最多提出 N 次要求。`session_id` 是该终止预算的稳定键（每个事件中都有它；参见模式参考中的 JSON 契约）：

   ```bash
   SID=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('session_id','nosid'))" 2>/dev/null || echo nosid)
   CNT="${TMPDIR:-/tmp}/my-guard.${SID}.count"
   N=$(cat "$CNT" 2>/dev/null || echo 0); N=$((N+1)); printf '%s' "$N" > "$CNT"
   if [ "$N" -gt 3 ]; then
     CAPPED_REASON='Loop budget exhausted; the blocked condition remains unresolved. Do not report completed.'
     python3 - "$CAPPED_REASON" <<'PY'
   import json, sys
   print(json.dumps({"continue": False, "stopReason": sys.argv[1]}))
   PY
     exit 0                              # explicit capped stop, not silent success
   fi
   ```

   这种方法很粗糙，而且故意不判断 R 是否实际发生——但它是*有限的*，而这正是原本缺失的性质。不要用 `$$` 或 `$PPID` 替代：每次钩子运行都是一个全新的进程，因此它们会在每次调用时发生变化，计数器永远不会累积。打印计数（“提醒 2/3”）——下面的战争故事会说明为什么这样的措辞值得保留。达到上限时的输出使用了文档规定的通用 [`continue:false` / `stopReason` JSON 字段](https://code.claude.com/docs/en/hooks#json-output)，因此用户看到的是达到上限的停止，而不是一个无法区分的成功 Stop。这会停止会话；但**不会**保护发布操作。如果达到上限时的退出消息表明某个工件仍未交付，请在操作边界通过 PreToolUse 单独强制执行。

不要将此计数器复制到一个产品目标是持续可用的注入器中。如果其提醒过于密集，应根据观测到的使用情况重新调整节奏或迟滞；如果封顶状态会变成“条件仍然存在，但钩子永远静默”，那么该计数器就没有合法的终止状态，机制 3 便是错误的设计。

4. **迟滞 / 冷却窗口**（控制理论对
   [告警抖动](https://utcc.utoronto.ca/~cks/space/blog/sysadmin/HysteresisMeaningAndAlerts)的回答）：
   触发后，在一段窗口期内抑制重新评估——一个标记文件加上
   `[ $(( $(date +%s) - <stamp mtime> )) -lt 900 ] && exit 0`（在 BSD/macOS 上，mtime 是
   `stat -L -f %m`，在 GNU 上是 `stat -L -c %Y`——本段中的其他代码片段也是如此；**`-L` 至关重要**，因为规则 3 会在你将要执行 stat 的每个路径上放置符号链接，而不加它时读取的是链接自身的 mtime，SSOT 被编辑时标记不会更新——#41）。适用于围绕某个阈值*振荡*的条件；对于修复操作会**重置**的条件则是**错误的**——这类条件需要使用 2 或 3。
   ⚠️ **迟滞不提供 V——它是速率限制器，而不是终止证明。** 循环只有在条件自行缓解时才会结束，而此时使其结束的是外部世界，而不是你的钩子。因此，其 `# TERMINATION:` 行必须点明这个外部事实（“到标记过期时，X 已由 <whom> 解决”）。如果你无法诚实地写出这一行，那么你真正需要的是 2 或 3。冷却机制控制建议多久可以发声一次；它不会把反复出现的建议转变为机制 3 所管理的有界修复循环。

**状态本身的失败方向：应用规则 5 的问题，不要根据字面匹配。** 如果状态无法读取或写入——不可写的 `TMPDIR`、沙箱、磁盘已满——由规则 5 的防护分类表作出决定，而它通过提出 **“如果这个状态消失，修复操作是否仍然可能？”** 来作出判断。对于机制 2 和 3，答案是**否**——回执是 R 已发生的唯一记录，而机制 3 则有意不去判断 R 是否发生，因此它的计数器是唯一的退出途径——所以**允许停止**。一个无法读取自身状态却仍然阻塞的终止机制，*就是*这个循环，只不过现在没有人类可见的原因。

⚠️ **不要仅仅因为两者都说“计数器”，就将机制 3 路由到规则 5 的“反转子情况”。** 该子情况适用于这样一种计数器：它只是在用户仍可独立满足的谓词之上，*为提醒次数设置预算*——在那种情况下，对不可读取的计数器保持静默，只会让一个原本有其他清除方式的钩子不再发声，因此你仍应继续评估该谓词。机制 3 没有这样的后备谓词。**已经测量过了，而这正是该组合会产生的失败：**将机制 3 的代码片段粘贴到 Pattern E 的骨架中（根据 `-e` 与 trap 的项目符号，该骨架会带有
   `set -uo pipefail`），将 `TMPDIR` 指向一个不可写目录，连续五次运行都会返回退出码 2——`N` 永远无法持久化到 1 以上，永远无法达到上限；而一旦修复操作涉及工具调用，#27 已经排除了将 harness 上限作为后备措施的可能性。这里的失败方向完全由代码片段本身没有携带的一行 `set` 决定，因此**应将防护放在实际失败的步骤——写入——上，绝不要放在读取上**：

```bash
printf '%s' "$N" > "$CNT" 2>/dev/null || exit 0   # can't persist ⇒ can't terminate
```

读取操作已经受到保护（`cat … 2>/dev/null || echo 0`），并且**必须保持这种方式**：计数器文件缺失是正常的首次运行，因此在读取操作上使用 `|| exit 0` 会让钩子在完全健康的环境中永久静默。实测结果是，每个变体连续运行五次：在可写的 `TMPDIR` 上，为写入操作添加保护会得到 `2,2,2,0,0`，在不可写的 `TMPDIR` 上会得到 `0,0,0,0,0`——两种情况下都正确；而为读取操作添加保护在**两种情况下**都会得到 `0,0,0,0,0`，也就是说，这个保护实际上永远不会触发。

**需求文本中的说明不能替代一个会收敛的谓词。** 一个消息写着“如果你认为这没有必要，就再次结束”的钩子，每一轮仍然会产生一次完整的修复周期，因为被告知必须执行 X 的模型通常就会执行 X。逃生口必须位于**谓词**中，而不是建议中。

**测试要求，以及这里最容易跳过的事项：**自测试需要一个**“修复之后”**的用例——不只是测试“应该触发时会触发”，还要测试**“R 完成后会停止触发”**。没有这一项，非终止在**结构上不可见**：每个 fixture 都只是某个孤立时间点的判断，而非终止是**序列**的属性。只检查单个时间点的测试套件，无论有多少用例，都完全覆盖不到收敛性——这就是钩子可以带着绿色的自测试发布，却在第一次真实遇到问题时仍然循环的原因。能够发现这一点的用例对（receipt 缺失 → 触发，receipt 存在 → 静默，以及普通 `run` 行无法表达的设置/清理操作）已经在 `scripts/test_hook.sh` 的“AFTER-REMEDIATION ROWS”下提供了模板；症状 → 原因 → 修复对应陷阱 #16。

**证明了终止 ≠ 让人感觉已经终止（2026-07-25 事故复盘）。** 一个具有正确存在事实 V 的 Stop 钩子在一次会话中触发了三次——每次触发都是来自不同已完成任务的一个合法**新**推送，机制完全按照设计工作——但用户的体验仍然是“为什么这东西卡在循环里？”（这与机制 2 的“R 所做的任何事情都无法让它重新上升”并不矛盾：**V 是按键区分的**——三个不同的键对应三个独立的单向递减。这也是在无法判断自己属于哪种情况时的诊断方法：如果每次触发都带有一个**新**键，机制是正确的，问题在于密度；如果重复触发共享**同一个**键——或者谓词根本没有键，因为它比较的是时间戳——那么你遇到的就是上面的反例，需要替换该谓词。）连续发生的三个独立修复周期从外部看起来与循环没有区别。变体证明解决了机制问题；但它没有说明**一次会话可以要求多少个不同的阻塞性修复**。如果一个**阻塞式 Stop 钩子**产生了这种密度（这里复合产物每天会发布好几次），可以考虑将机制 2（存在事实）与机制 3（会话范围的终止预算）配对使用，或者有意接受这种观感，并在钩子的输出中明确说明——“最多 N 次中的第 2 次阻塞性要求”读起来像是在推进，而不加说明的重复则像是在循环。对于反复注入建议的钩子，只能通过频率控制/迟滞来解决密度问题；生命周期上限会在会话中途无声地使产品退出。
**（2026-07-26 后续：这个钩子看起来像是密度问题的触发，后来发现 100% 都是误报——它的审查通道在团队模式下无法识别 schema；请参见上面的可观测性表单。在接受“合法”这一判断之前，先确认这些触发确实都有证据依据。）**

**终止与是否值得是两个独立的闸门。** V 证明循环会结束；Loop
Contract 的预算和封顶退出机制决定是否值得再付出代价执行一轮。暴露了这一
区别的无 hook review-loop 失败案例，包括为什么范围漂移会悄无声息地铸造出
无穷无尽的“新”工作，详见陷阱 #36。

### 8. 等待也需要同样的证明——通知只是建议，轮询必须携带预算

规则 7 涵盖的是由 *hook* 创建的循环。同样的形态也会在没有 hook 参与时
再次出现：**代理轮询异步结果**——子代理的报告、后台任务的完成通知、CI
状态。真实会话（2026-07-25）：子代理完成通知通过一个可能延迟或丢失通知的
邮箱送达；三个独立的代理都已完成工作，但通知一直未送达，等待中的代理在
约 40 分钟内执行了十几轮 `sleep 240` + 催促循环，直到人类询问它到底在做
什么。没有任何错误；这个循环只是没有变体。

规则 7 的机制可以对应迁移过来——前两项可以直接迁移；滞回没有对应物（等待
不会发生振荡），它的位置由等待特有的一个陷阱占据：

1. **轮询产物，而不是通知。** 如果你真正需要的是某个结果（一个文件、一个
   git ref、一个 API 状态、数据库中的一行），就等待那个结果，而不是等待
   “它是否说自己完成了”。通知只是提示；产物才是事实。存在性检查会在事实
   落地的瞬间终止，无论是否有任何消息到达。
2. **每次等待都必须携带预算，并在编写循环时选定。** 最大轮数 × 间隔
   （例如 3 × 4 分钟），以及一个在第一次 sleep 之前就已存在的降级路径：
   自己完成、询问用户，或将其标记为待处理并转去做其他工作。“无限等待，
   看看会怎样”不是降级路径——它就是循环本身。
3. **投递协议只是建议，不是机制。** “完成后通过 `SendMessage` 报告——
   沉默视为未完成”值得写下来，但它约束的是代理是否*发送*，而不是邮箱是否
   *投递*。在一次会话中，提示词里都有该协议的三个代理全都沉默了。设计
   等待时要假设通知可能永远不会到达——因为它确实可能不会到达。

两个相邻的陷阱，同样在那次会话中付出了代价：**TaskStopping 一个其实正在
进行工作的“卡住”代理**——邮箱延迟不等于闲置；一个审查者正在进行 20 分钟
的真实语料测试，却在即将交付前几分钟被以“卡住”为由终止。以及**对等待本身
进行 `--dry-run` 式探测**：在断定对方沉默之前，先确认你自己的观察通道正常
（在那次会话中，System Events 的窗口计数对一个正在屏幕上的对话框自信地
返回了 0——权限失败伪装成了证据）。

### 9. Fixture 无法告诉你误报率——在注册之前重放一套真实命令语料

规则 1 对哪种错误更糟进行了排序（误拦截胜过漏拦截，因为人们必须绕过的
防护会被条件反射式地绕过）。规则 2 要求你在注册之前进行测试。但这两条规则
都无法告诉你**实际的误拦截面有多大**——测试表做不到，因为*测试输入是你
根据产生检测器的同一套心智模型编写的*。其中的案例只包含你想到的那些形态；
你没想到的形态，按构造而言就是缺失的。这不是通过增加行数就能弥补的覆盖率
缺口。

**测得于 2026-08-06。** 一个 PreToolUse/Bash 防护器通过了一张包含 26 个用例、并对其执行了 5 次变异的表格测试，随后完成注册。之后，使用从最近 60 份会话转录中收集的 **11,903 条去重真实命令**进行回放：其中 143 条产生了候选项，实际运行的钩子拦截了 46 条，而逐一人工检查这 46 条后发现 **10 条错误——占其拦截总数的 21.7%**（其中两条边界调用被计为正确；如果采用另一种判断方式，则约为 30%）。在 39 分钟内，它已经拦截了 3 个真实会话，其中一个会话被告知要加载一个不可能存在的 skill——这是下面第三个缺陷，其表现为指向虚无的修复指导。它在同一小时内被移除。三个根本缺陷全部位于**解析**层：续行标记被当作分隔符读取；分段扫描将 heredoc 主体和数据参数计为执行内容；以及路径分类器没有类型过滤。

这个故事并不支持两个结论。它**并不是**“变异测试不起作用”：之后对同一套测试的审计发现，钩子逻辑中有 **5 段代码可以删除，而 26 行测试仍然全部通过**；作者标注为“已从装饰性修复”的其中一行实际上仍然是装饰性的——*“我运行了变异测试”并不等于“变异测试是正确的”*，而回放同时暴露了这两点。它也**不是**“你不可能事先知道”：其中三个缺陷是对本文件已经提供的代码进行手写重实现造成的（`split_shell_lines`、命令位置遍历，以及 `is_git_write` 对 `-C` 及其参数的处理）。规则 1 中的*逐字使用遍历器*才是成本更低的修复，但它被跳过了；回放是兜底措施，而不是第一道防线。

**方法——四个步骤，其中第 2 步最容易被跳过：**

1. **收集。** 会话转录位于
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`，此外还包括注册在
   `~/.claude/history-sources.json` 中的任何归档。命令是 `.message.content[]` 条目，其中
   `type == "tool_use"` 且 `name == "Bash"`，位于字段 `.input.command` 中——**不是**钩子事件的 `.tool_input.command`，后者是另一种结构。去重，并收集足够多的转录，使你自己近期的工作形态也包含其中（那次运行使用了 60 份）。
2. **使用随附的检测器进行预过滤，并逐字切出**——绝不要手写等价实现，否则你测量的只是你自己的两个猜测之间的一致性。预过滤仅用于降低成本（11,903 → 143）；真正做出判断的是第 3 步。如果检测器不是可提取的代码块——无论是 shell 代码，还是拆分在一个被 sourced 的库中——就把它变成可提取的代码块；无法独立运行的检测器，也无法进行单元测试。
3. **将每个候选项交给真实钩子，并提供其自身的真实转录和 `session_id`。**
   读取会话状态的防护器在伪造上下文下会给出不同答案。事件契约见：`references/hook_patterns.md`。有两点会造成问题——请在临时
   `TMPDIR` 下运行，否则规则 7 的收据和每会话计数器会写入真实会话，并在你自己的测量过程中途让防护器停止工作；如果钩子包含人工闸门，请通过模式 B 的强制拒绝路径驱动它，而不是回答 143 个对话框。
4. **人工检查每一次拦截——拦截列表就是误报测量结果。** 允许列表回答的是规则 5 的另一个问题（它停止输出，是因为那里没有任何内容，还是因为它无法看到？）；而一次回放若返回 **0** 次拦截，应当让人怀疑测试工具，而不是将其视为无问题——陷阱 #11 针对触发不足的方向规定了同样的测量手段。

**如何处理这个数字。** 如果某个误拦截的修复指引是错误的或不可行的 → 根本不要注册：这种形态正是规则 1 要防止的反射式绕过规则的制造过程。否则，就把拦截列表当作修复列表，然后重新回放。预计误报会集中在**你编写防护规则时正在做的事情**上——那次运行中有一半误报落在了 hook 开发文件上，因为作者那周正在编写 hook。而且要专门扫描拦截列表中的**运维操作**（对 hooks 目录下的文件进行编辑、对 hook 执行 `bash -n`、防护规则自身的 SSOT）：一个会拦截自身移除操作的防护规则，无法在会话内部关闭。最近记录的案例是 #25，当时防护规则拦截了一个**只读的** `git config core.hooksPath` 查询——这正是距离自我锁死还差一步的同一个盲点。一旦防护规则**已经**把你锁在外面，逃生路径就在 **#3** 的列表中（使用 Edit/Write 工具编辑 `settings.json`，它永远不会触发 `Bash` matcher；或者使用不同的 `CLAUDE_CONFIG_DIR` 启动会话）。

这种聚集现象只是一种倾向。对于检测器是**文本模式**的防护规则，其中有一类情况却是必然的：**记录反模式会复现它自身的触发条件。** 解释该防护规则的提交消息、文档示例、你写入自身知识库的说明——每一项都会原样携带被禁止的形态，作为数据进入语料库。2026-08-30 在一次包含 852 条命令的回放中测得：与该防护规则标题所描述的形态匹配的 4 条命令中，**3 条是正常的**——一条关于该防护规则的提交消息、一条嵌入了该模式的文档写入，以及一条刻意在正确形式旁边运行错误形式以展示差异的校准命令。如果检测器不加区分地看待该模式，那么在它自身的标志性形态上就会有**75% 的判断错误**，而且每一次拦截都会发生在作者正在写下防护规则说明、写到句子中途的时候。两个豁免条件可以消除这一类问题，而且两者都不是特殊情况：**数据接收端 heredoc 的正文**（`references/hook_patterns.md`，位于命令位置遍历器的 heredoc 限制范围内——即用于区分接收端的剥离器），这涵盖了提交消息和文档写入；以及**同一条命令中存在正确形式**，这涵盖了校准命令——一个把修复方式写在 bug 旁边的作者是在展示它，而不是在提交它。第二种情况与 pipe-fallback 防护规则所使用的 `pipefail` 逃生舱口形态相同：命令携带了证据，表明其作者已经了解这一点，因此不要再与其争论。它的机制是再增加一个字面测试，在检测器之前运行并使其短路——对于 `pipe-fallback-guard`，就是子字符串集合 `pipefail`/`PIPESTATUS`/`pipestatus`（规则 4）；对于具有规范修复方式的检测器，则是该修复方式的独特片段。务必保持狭窄且字面化：针对正确形式建立一个*模式*会重新开启整个猜测问题，而作者必须有意输入的固定字符串很难被意外触发，并且其失败方向是漏报。

规模控制：避免读起来像一个研究项目：一次收集加一次循环，墙上耗时几分钟。

## 构建顺序（按顺序）

1. **确认它是真实的循环复现**，而不是假设性的——否则不要构建。
   如果这个钩子会**要求修复**而不只是阻止，那么在编写任何逻辑之前，先写出完整的 Loop Contract（key / axis / T / R / V / budget / two exits），并将 V 作为 `# TERMINATION:` 行放入脚本头部（规则 7）。首先检查你要设门控的对象是否是一个*操作*；如果是，则在该操作上设置 PreToolUse guard，可以消除循环，而不是设法驯服它。
   如果无法命名一个在每次 `trigger → remediate →
   re-check` 循环中严格递减的量，那么该设计就是不会终止的——修复设计，而不是正则表达式。
   在添加任何重复计数器之前，先命名其有上限的产品状态。有效的循环预算最终必须进入 blocked、unshipped、pending 或其他明确的终止状态。“会话仍在继续，但 advisory 永久静默”不是终止状态；应让重复的 advisory 交付不受生命周期上限限制，并在多个完全到期的窗口之后证明长期活性。
2. 在 SSOT 目录中编写脚本；执行 `chmod +x`。
3. 使用 shlex 进行令牌级匹配来执行**检测**（规则 1），匹配依据应是世界能够回答的事实，而不是你自己的渲染结果或命名约定（规则 6）。
   - **首先检查 ShellCheck 是否已经能够判定这一点——然后记录答案，因为下一个作者还会问同样的问题。** 它是 shell 反模式的事实标准，所以“为什么不直接使用 shellcheck”是审阅者首先会问的问题。于 2026-08-15 在 **0.11.0** 上针对
     `find . -name x | head -5 || echo "no"` 进行测量——这是一个从理论上就永远不会触发的 fallback，因为 `||` 绑定到 pipeline 的**最后**一个阶段，而 `head` 在输入为空时退出码为 0：**默认配置不报告任何内容，退出码为 0**。`--enable=all` 会发现
     **SC2312**（`check-extra-masked-returns`），但对于 `cmd | jq . || echo bad` 也会触发；在那里最后一个阶段确实可能失败，fallback 也确实有意义。
     有三个原因使它不适合作为*门控*——而且每个原因都具有普遍性：
     它**默认关闭**（因此目前并没有保护任何人），无法区分失效的 fallback 和有效的 fallback（无差别触发会导致规则 1 所说的错误阻止螺旋），并且它自己建议的修复方法是“使用 `|| true` 来忽略”，这与目标背道而驰。它还检查的是**文件**，而不是工具调用事件。
     这个问题的一般答案是：标准 linter 适合用来**检查**，但通常不适合委托给它来执行阻塞性门控，因为 linter 针对的是 advisory 广度，而门控需要精确性。你的钩子所贡献的正是这种精确性。已交付的示例：`pipe-fallback-guard`，其精确性来自一个小型列表，其中列出了确实会吞掉上游代码的最后阶段命令（`head`/`tail`/`wc`/`cat`/`sort`/……），并且会有意排除 `grep`/`jq`/`awk`/`sed`，因为这些命令确实会失败。
4. 使用 `bash -n` + `test_hook.sh`，并加入触发案例和看起来正常的相似案例（规则 2）——全部通过之前不要注册。要包含携带未展开路径的形式（`cd ~/elsewhere && …`，规则 5）；如果钩子包含人工门控，则加入一个强制拒绝行（模式 B，“让门控可测试”）；如果它要求修复，则加入**修复后的行对**——没有回执时触发，有回执时静默（模板位于 `scripts/test_hook.sh`；规则 7——时间点 fixture 从结构上无法发现不终止）。
   - **为钩子提供 `--selftest` 模式，并使其具备双向测试能力。** 然后让 SessionStart guard-rail health check（见上面的“Hook types”——其全部职责就是检查各个 guard）对每个已安装且提供该模式的钩子调用 `<hook> --selftest`。这是唯一能捕获以下故障的自动检查，而 `bash -n` 以及下面第 4-7 步从结构上都无法捕获该故障：钩子已经**退化为永久 no-op**。这种故障在构造上不可见——一个永不触发的 guard，产生的输出与会话中没有任何内容可报告时完全相同，这正是它可能持续数周的原因。两个 fixture 只是**最低要求**，而不是目标：必须有一个必须阻止的样本和一个必须放行的样本，这样才能同时捕获“停止触发”和“开始错误阻止”两种情况——只具备其中一种样本无法做到这一点。
     **应根据杀死的 mutants 数量来确定规模，而不是根据 fixture 数量。** 并像校准测试套件一样校准它：故意破坏检测器，并确认 `--selftest` 以非零状态退出。一个从未被验证过会失败的 selftest，与 `exit 0` 没有区别。
     在已交付的 `compounding-edit-review` 上进行测量时发现：它**第一版的两个 fixture 只杀死了 14 个 mutants 中的 4 个**——其注释声明的所有承重行为都没有覆盖，包括一个会短路 anti-loop 检查、但 selftest 仍打印 OK 的 mutation。现在它运行 58 个案例。
     真正的约束不是 fixture 数量，而是会话开始时的**墙上耗时**，因为这项检查每次会话都要付出成本：这 58 个案例耗时约 **5.3 秒**，而两个 probe 的活性检查约 **140 毫秒**。当杀死 mutants 让你超过该预算时，应当**拆分**，而不是缩减——让 `--selftest` 执行廉价的固定规模活性 probe，在构建时由 `test_hook.sh` 执行完整回归测试组。
     缩减到 mutant-kill 线以下，只是换回了一个在 guard 已经失效时仍然通过的 selftest。
     **为拆分方案提供触发机制，否则完整部分永远不会运行。** “在构建时”不是一种机制——一条写着*修改后运行完整测试组*的注释，与本文件试图弥合的整篇“文字说明与强制执行之间的鸿沟”是同一种问题，并且会以同样的方式失败。已在 `shared-repo-head-drift` 上测量的方案是：21 个案例 / 冷启动 17.8 秒，将 SessionStart 的 health check 降为包含 9 个断言的 probe、耗时 2.2 秒：在钩子中以 `--selftest` 和 `--selftest-full` 的形式保留两部分，并让 health check 进行选择——如果文件自上次完整通过以来发生过变化，就运行完整测试组，否则运行 probe。这样，成本会落在**编辑后的第一个会话**上，而这正是值得支付完整测试组成本的时机。
     ```bash
     sig=$(stat -L -f '%m %z' "$h" 2>/dev/null || true)   # -L or you stat the symlink — #41
     stamp="$STAMPS/$(printf '%s' "$h" | shasum | cut -c1-16).full"
     [ -n "$sig" ] && [ "$(cat "$stamp" 2>/dev/null || true)" = "$sig" ] || mode="--selftest-full"
     bash "$h" "$mode" >/dev/null 2>&1 </dev/null || return 1   # </dev/null: an
     # unknown flag drops into the main path and reads stdin — on SessionStart that
     # hangs every new session
     [ "$mode" = "--selftest-full" ] && printf '%s' "$sig" > "$stamp" 2>/dev/null
     ```
     失败方向是**转向完整测试组**：签名无法读取、不匹配，或 stamp 目录不可写，都会运行完整测试组。这里不存在修复循环（规则 7 不适用）——它只是在选择要运行的层级，因此宁可变慢，也不要盲目通过。只有完整测试组**通过**时才写入 stamp，这样失败会让下一个会话仍然运行完整测试组。
     选择 probe 的案例不能是“前 N 个”：它需要一个必须触发和一个必须静默的案例，否则两个退化方向无法同时覆盖。注意某个必须静默的案例可能其实是空洞的——advisory-only 钩子总是退出 0，因此 `run` 风格的退出码行无法证明其中不存在误报，断言必须采用 `says` 风格（#40、#14）。
5. **重放真实命令语料，并手动检查每一次阻止**（规则 9）——这一步测量的是误阻止面，而第 4 步中的 fixture 表在结构上无法测量这一点。将已交付的检测器原样截取出来作为预过滤器；把每个候选项连同其自身真实的 transcript 和 `session_id`，在临时的 `TMPDIR` 下交给真实钩子。
6. **创建符号链接**到 `~/.claude/hooks/`（规则 3）。
7. 在主 `settings.json` 中**注册**，并使各 profile 收敛（规则 4）。
8. 对于 Tier-0/不可逆操作，添加**人工确认释放门控**（规则 4）。
9. **持久化**：将 SSOT 提交到其私有仓库。可以选择添加一行 CLAUDE.md（正文说明*原因*以及替代方案；钩子负责强制执行）。

## 已知陷阱（调试失效的 hook 前请先阅读）

完整目录（症状 → 原因 → 修复）：[references/hook_pitfalls.md](references/hook_pitfalls.md)。
重点包括：`stdin` 被 `python3 - <<PY` heredoc 消耗（hook 静默地允许一切操作）、awk 拆分导致的误拦截（规则 1）、损坏的 hook 污染会话（规则 2）、Python *注释*中的引号或反引号会在没有语法错误的情况下静默损坏 `python3 -c "…"` 代码块（陷阱 #9——应改用模式 E 中带引号的 heredoc 形式）、静态环境变量逃生通道（规则 4）、多配置文件注册不完整、提交消息以伪命令文本的形式到达 walker，并错误拦截你自己的修复提交，除非豁免 `git` 写入片段（#7），以及从命令文本中解析出的路径保留了字面量 `~`，导致防护以**放行**方式失效而完全没有症状（#10——这是唯一一个你无法等到发现的陷阱，因为它唯一的迹象就是沉默）；某个分支读取 hook 自己被截断的显示字符串（#12），或依赖本仓库并不遵循的命名约定（#13）——而当测试套件只断言退出码时，这两者都不可见（#14）——仅仅**包含**重定向的命令文本被计作写入（#15），以及 hook 所**要求的修复操作会重新启用它自身**，在自测试为绿色的情况下循环，因为时间点固定的 fixture 从结构上就无法发现不终止问题（#16，规则 7）。

**harness 才是隐藏变量——请使用 `scripts/test_hook.sh`，不要自己手写。** 下面每一种手写测试的失败模式都会产生与干净通过**相同**的输出，因此看起来像是成功（2026-07-22，在修复 Stop hook 的白名单时，一次就遇到了三个）：

1. **事件形状错误。** Stop hook 读取的是 `last_assistant_message` / `transcript_path`，而不是 `tool_name`/`tool_input`。如果输入一个 PreToolUse 形状的事件，它找不到任何文本 → 退出码为 0 → “没有误拦截！”
2. **JSON 引号错误。** 单引号中的 `'{\"a\":1}'` 会输出一个包含字面量反斜杠-引号的字符串；`json.loads` 抛出异常，而 hook 中的 `2>/dev/null || exit 0` 将其吞掉，于是每个用例都“通过”。
3. **测试用例恰好属于规则明确豁免的情况。** 基线字符串使用了一个规则*有意豁免*的字符串（该防护会标记形如 `<name> Group` 的自造昵称，但豁免普通短语 `in the group` / `group chat`——而基线行恰好使用了其中一个）。原本用于证明防护仍会生效的那一行没有真正触发防护，于是整个测试套件显示为绿色。

**如果 hook 的产物是它输出的消息，那么退出码就无法测试它。** 阻止型 hook 的契约主要是退出码，因此 `run` 行可以覆盖它。但如果 hook 存在的目的就是*说些什么*——例如说明正确替代方案的 PreToolUse 解释，或 Stop 提醒——那么它还有一个退出码无法观察到的第二输出通道：破坏措辞、反转条件段落、让 heredoc 吞掉某个部分，而退出码仍会完全保持为 2，于是每一行都能通过。添加来自 `scripts/test_hook.sh` 的 `says <label> <event> <pattern> <yes|no>` 行，断言**两个 fixture 中的两种极性**（对于它所针对的输入存在，对于它跳过的相似输入不存在）——单独一个 `want=no` 在 hook 完全不输出任何内容时也会因空洞而通过，因此它只有与一个 `want=yes` 行并列时才有意义，后者用于证明 hook 确实会输出内容。匹配**固定字符串**，不要使用正则表达式：值得断言的短语通常包含方括号，而在 BRE 中，`[skill]` 是一个字符类，会匹配任何包含 s、k、i 或 l 的文本。然后**通过变异来证明这些行确实能够失败**：复制 hook，注入每一行声称要捕获的确切 bug，并确认该行变红。在你看到测试因正确的原因失败之前，一个绿色的测试套件不携带任何信息——曾经有两个真实 bug 在一个完全绿色的 24 用例测试套件中存活下来，因为每一行都只检查退出码（陷阱 #14）。

常见的形态是：**所有情况都通过是一种危险信号，而不是放行信号。** `test_hook.sh`
会在结构上捕获上述第 1 和第 2 种形态——它会为每一行 `run` 明确断言
`expected-exit`（而不是断言“是否打印了某些内容”），并强制让触发行与看起来正常的相似行
同时存在，因此一个返回 0 的触发行会明确失败，而不会混在其中。它
**无法**捕获第 3 种形态：一行的内容是否意外落入某个豁免范围，这是你所写内容本身的
属性，没有任何测试框架知道你规则的意图。这个问题只能通过习惯来捕获——先断言一个已知
应当触发的触发行；如果它没有触发，先怀疑测试行，而不是 hook。
