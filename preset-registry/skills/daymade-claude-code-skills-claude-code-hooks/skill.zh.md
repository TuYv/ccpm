# Claude Code 钩子

Claude Code 会在工具调用边界触发**钩子**。钩子是一个 shell 命令，它通过 stdin 接收 JSON 事件；对于阻断型钩子，它会通过**退出码**决定是否继续执行工具调用。这是唯一能够从*结构上*阻止某种行为的机制——CLAUDE.md 中的文字规则只是一项建议，完成任务的驱动力可能会越过它；而钩子是一堵墙。

## 何时应该使用钩子（以及何时不应该）

当**一条已经写明的规则仍不断被违反**时，应编写钩子。判断信号是：你添加了文字规则，它读起来清晰明了，但该行为仍然再次发生——因为在采取行动的那一刻，注意力 100% 集中在“把事情完成”上，提醒便失去了作用。这种反复发生就是一个信号，表明应将规则从文字（建议性）转移到钩子（强制执行）。治理经验法则：*Tier-0 不可逆操作 + 只有文字规则，没有钩子 → 应该使用钩子。*
（此处的 **Tier-0** = 其损害无法在会话内部撤销的操作：破坏未提交的工作、将机密推送到远程、删除文件、向外发布内容。判断标准是可逆性，而不是严重程度。）

以下情况**不要**诉诸钩子：规则实际上从未被反复违反（不要针对假想错误预先构建防护——有成本却没有经证实的收益），或者所谓的“规则”属于没有机械化特征的判断问题（钩子只能匹配 token/模式；它无法判断设计是否优秀）。

如果症状是“它不断审查 / 等待 / 重试”，不要想当然地认为答案是另一个钩子。首先完成规则 7 中的 **Loop Contract**，并阅读[陷阱 #36](references/hook_pitfalls.md#36-a-self-applied-review-rule-can-loop-without-any-hook)。
该循环可能完全是由智能体反复应用一条文字规则造成的。

## 钩子类型及退出码的含义

| 类型 | 触发时机 | 退出码 0 | 退出码 2 | 其他 |
|---|---|---|---|---|
| **PreToolUse** | 工具运行之前 | 允许 | **阻止**调用（stderr → 作为指导信息显示给模型） | 任何其他退出码 =“非阻断错误”→ **调用继续执行**——但仅限于 stdout 不包含有效 JSON 时。Claude Code 会在**每个**退出码下读取 JSON 输出，有效 JSON 会完全覆盖退出码的作用。此处的骨架不会向 stdout 输出任何内容，因此其故障开放逻辑成立；一旦添加 `permissionDecision` 载荷，退出码便不再是决策依据 |
| **PostToolUse** | 工具运行之后 | 保持安静，**除非它向 stdout 输出 `hookSpecificOutput` JSON——这正是注入上下文的方式，并且发生在退出码为 0 时** | 向模型提供反馈（无法撤销工具运行） | — |
| **SessionStart** | 会话开始时 | 继续 | **无法阻止**——stderr 会向用户显示钩子错误通知，Claude 永远不会看到它，会话仍会开始 | **无论如何都应以 0 退出**：并不是因为非零退出码会阻止会话（它无法阻止），而是因为任何非零退出码都会在每次会话启动时向用户的会话记录中写入一条 `<hook> hook error`。它接受一个 `matcher`，用于匹配会话的*启动方式*——`startup`、`resume`、`clear`、`compact`、`fork` |
| **Stop**（+ `SubagentStop`） | 模型即将结束响应时 | 允许停止 | **阻止停止**——强制模型继续（stderr → 作为原因反馈给模型） | 循环安全：钩子会检查 `stop_hook_active`（这是必要条件，**但并不充分**——参见规则 7）。执行框架的连续阻断上限（默认值为 8）**不是**通用的安全保障——只要后续执行过程中调用了工具，它的计数器便会重置，因此对于补救过程涉及工具调用的钩子而言，它永远不会达到上限，而大多数钩子都属于这种情况（#27）。请自行设置边界。同一事件的所有 Stop 钩子会**并行**运行——一轮阻断可以同时携带多个钩子的反馈 |

- **PreToolUse** 是阻止*工具调用*的主力——本表中的四种类型是本文档所讲解的类型，并非所有可阻止事件的完整集合；**官方** hooks 参考文档（docs.claude.com / code.claude.com，而非本套资料中的 `references/` 文件——后者仅涵盖上述四种类型）目前列出了更多可阻止事件，包括 `UserPromptSubmit`、`PreCompact`、`TeammateIdle`，以及任务和配置事件。如果你需要设卡的对象不是工具调用，请先查阅该参考文档，不要强行把它套到 PreToolUse 上。
  `matcher` 用于选择工具（`Bash`、`Agent`、`WebFetch`……）——**而它的匹配方式取决于你使用的字符**：仅包含字母、数字、`_`、`-`、空格、`,` 和 `|` 的 matcher 会按**精确字符串**进行比较（或者按以 `|`/`,` 分隔的精确字符串列表进行比较）；包含任何其他字符时，则会被视为**未锚定的 JavaScript 正则表达式**。这两个方向都会悄无声息地踩坑——`Edit.*` 也会匹配 `NotebookEdit`（请用 `^Edit$` 将其锚定），而 `mcp__memory` **什么也匹配不到**，因为它完全由精确匹配字符组成，并且没有任何工具的名称恰好是它（你需要的是 `mcp__memory__.*`）。匹配区分大小写。以退出码 2 退出会阻止调用，且 hook 的 **stderr** 会成为模型看到的消息——因此应在其中说明*原因*和*正确的替代方案*，而不只是写一句 "blocked"。
- **PostToolUse** 无法撤销操作，但它可以**注入权威上下文**，使后续的幻觉无法成立（例如，在提交后重新读取真实的 git HEAD 并将其呈现出来——面对注入的事实，模型无法继续“相信自己已经提交了”）。
- **SessionStart** 用于对**防护机制本身进行健康检查**——正常时保持静默，出现故障时发出警告，并始终以退出码 0 退出。请注意其中的*原因*：并不是因为非零退出码会阻止会话（它做不到），而是因为在有人修复问题之前，它会在每次会话开始时都打印 hook 错误通知——如果一项检查总是在启动时发出虚假警报，人们最终就会习惯直接滚动略过它。
- **`set -euo pipefail` 与 `set -uo pipefail`——应根据契约选择，并且要知道有两种方式可以维持始终以退出码 0 退出的契约。** 可能进行阻止的 hook（PreToolUse）需要 `-e`：意外故障导致脚本中止是可以接受的，因为调用方会将非 0/2 退出码视为“继续执行”。契约要求**始终以退出码 0 退出**的 hook（PostToolUse 注入器、SessionStart 检查）有两种合理写法：(a) **去掉 `-e`**，并使用 `||` 防护每一条有风险的命令——启用 `-e` 时，只要有一条 `grep` 合理地未找到任何内容，hook 就会中途终止，而 CLI 会显示一条没有具体信息的 `Failed with non-blocking status code`（陷阱 #8，Pattern E 的写法）；或者 (b) **保留 `-e` 并添加 `trap 'exit 0' ERR`**，这样任何故障仍会被转换为退出码 0，同时 `-e` 继续保护管道流程（`git-commit-headcheck` 的生产环境写法，Pattern D）。两者都正确；不能使用的是单独启用 `-e`，既没有 trap，也没有 `||` 防护。经验法则是：**对于做决策的 hooks，使用 `-e`；对于做报告的 hooks，去掉 `-e` 或为其设置 trap**（陷阱 #8）。
- **Stop 是其中的异类，也是最常被误用的类型**：它是*唯一*能够响应模型**自身刚刚生成的内容**（即模型自己的回复文本）的 hook 类型。其他所有 hook 类型——包括听起来似乎适合用来管控“输出内容”的 `UserPromptSubmit`——都只能看到**用户的**输入；从结构上讲，它无法看到模型自己在*当前轮次*的输出（这一判断仍然成立——这仍是应将此类规则放到 Stop 上的正确理由）。不过，这项保证并不意味着能够证明 `.prompt` 字段始终来自键盘输入：后台任务通知自身的报告文本也可以填充该字段，而 stdin JSON 中没有任何信息能够标明二者的区别——#30。像“模型不得为尚未验证的事物杜撰简称”这样的规则应放在 Stop 上；如果改为放在 `UserPromptSubmit` 上，它将会：(a) 一次也无法捕获它原本要捕获的内容，因为该文本根本不会流经这个事件；并且 (b) 只要用户自己输入的无关内容碰巧包含触发模式，就会错误地阻止该输入。这是类别错误，而不是调优问题——无论怎样优化错误事件上的正则表达式，都无法修复它。完整契约（`last_assistant_message` 与 `transcript_path`、防循环检查）见 [references/hook_patterns.md](references/hook_patterns.md) 中的 Pattern E。
- **Stop 有两个带有相同循环保护机制的阻止通道——应按意图选择，并让第一次（也是唯一一次）阻止承载全部信息。** `decision:
  "block"` + `reason`，或者直接以退出码 2 退出并写入 stderr，会显示为 hook *错误*——适用于硬性关卡（“绝不能让这种内容保留下来”）。`hookSpecificOutput.additionalContext` 会显示为中性的 "Stop hook feedback"，且没有错误通知——适用于模型应当权衡的指导和提醒，而非关卡。两者都计入上表所述的同一个连续阻止次数上限，因此选择差异在于语气，而不在于安全性。这对消息设计意味着：被阻止后的重试轮次（`stop_hook_active: true`）会被放行，**无论其中还剩下什么违规内容**——因此，Stop 防护只有**一次**提供有效信息的机会。（只有当你的补救方式是“重写回复”时，该上限才会进一步强化这一点；如果补救涉及工具调用，计数器会重置，上限永远不会触发——#27。无论如何，“只有一次机会”的结论仍然成立，因为它依赖的是锁存机制，而非次数上限。）应在这一次阻止中报告*所有*发现的问题（只打印第一个问题的防护会永久丢失其余问题——陷阱 #17），并将消息写成一份明确指出具体可接受修复方式的脱困指南，而非裁决——模型要么在一轮内收敛，要么就会在猜测中耗尽上限。v2.1.145+ 的输入 `background_tasks` / `session_crons` 使阻止型 hook 能够区分“会话已经完成”和“会话只是暂停以等待后台工作”——阻止暂停状态会迫使系统进行毫无意义的续写，并浪费同一个次数上限。

完整的可运行骨架：[references/hook_patterns.md](references/hook_patterns.md)。

## 骨架（PreToolUse Bash 防护钩子）

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS= read -rd '' INPUT || true                 # builtin; NOT $(cat) — see below
# 0-fork fast path: a builtin `case` on the raw JSON, BEFORE paying for python3.
# Your guard runs on EVERY matching tool call, so the irrelevant path is the one
# that has to be cheap. Keep this filter BROADER than what you actually block and
# never flag-level — it answers "is this even about X", nothing finer (#22).
case "$INPUT" in *TRIGGER*) ;; *) exit 0 ;; esac
TOOL=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_name',''))" 2>/dev/null||echo "")
[ "$TOOL" != "Bash" ] && exit 0                # only guard the tool you mean to
CMD=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" 2>/dev/null||echo "")
[ -z "$CMD" ] && exit 0
printf '%s' "$CMD" | grep -qw 'TRIGGER' || exit 0   # precise relevance check
# ... precise detection here ...
if <command actually does the banned thing>; then
  echo "BLOCKED: ... WHY ... USE INSTEAD: ..." >&2   # stderr = the guidance shown
  exit 2
fi
exit 0
```

**为什么开头两行并非风格选择。** `INPUT=$(cat)` 加上每个
`printf … | python3 -c …`，会在**该钩子匹配的每一次调用中产生进程派生开销，包括
那些它根本无话可说的调用**。约 13 个匹配 Bash 的钩子组成的集合 × 并行
会话 × 亚秒级工具调用频率，带来了持续每秒 40–200 次纯粹由
防护钩子开销产生的进程派生，使 Gatekeeper 在全天 CPU 排名中高居榜首，却根本
不存在任何失控进程——这组钩子本身没有问题；问题在于*无关路径*的单次调用成本
（#22，其中包含逐个防护钩子的转换方法及其实测下限）。

将 `case` 行复制到其他任何地方之前，请注意三点——第一点决定了它究竟是
快速路径还是绕过漏洞：

- **粗粒度过滤器必须涵盖你所阻止内容的超集，而原始子字符串测试
  并不满足这一点。** `TRIG''GER -x` 会运行 `TRIGGER`——bash 会在执行前
  拼接并去掉引号——但原始事件文本中不含 `TRIGGER` 子字符串，因此单纯的
  `case "$INPUT" in *TRIGGER*)` 会以 0 退出，防护钩子永远看不到它。**实测结果**：
  将这一行原样加入随附的模式 A，`TRIG''GER -x` 就会从
  以 2 退出变为以 0 退出，形成完全绕过——与此同时，`scripts/test_hook.sh` 仍报告
  21 个通过 / 0 个失败，因为没有任何测试行包含拼接后的触发词。模式 A 已经
  包含了修复及其原因（“去拼接——移除引号和反斜杠——然后再次检查；一次
  假阴性就意味着完全绕过”）；把粗粒度过滤器放在这一步去拼接操作*之前*，
  会使后者永远无法执行。按推荐顺序，有两种安全形式：
  **针对拼接操作无法影响的内容进行过滤**——JSON 键或工具名称
  （`case "$INPUT" in *'"tool_name":"Bash"'*)`），因为引号拼接发生在
  *命令*文本中，无法改写事件自身的结构；或者**在过滤器内部先去拼接**
  再进行测试（从输入副本中移除 `"`, `'` 和 `\`，然后匹配）。
  优先选择第一种：它不需要复杂的转义处理；如果过滤器自身的引号使用必须
  准确无误，它也就可能在出错时悄无声息。上面的骨架按原样使用时是安全的，
  仅仅是因为它自身的检测同样只是普通的单词匹配；一旦过滤器下方的防护逻辑
  比过滤器更智能，最终结果便由过滤器决定。

- **这个骨架在输入不相关时采用失败时放行策略**（`grep -qw … || exit 0`），因此，在它前面添加一个
  粗粒度过滤器只会改变成本，而不会改变语义。**失败时阻断的守卫则不同**：
  一个简单的子字符串过滤器会悄无声息地把它的契约从“阻断未知输入”变为“放行未知输入”
  （实测——`'not json'` 直接通过了该修复方案的初版），而仅使用一个 `*tool_name*`
  标记，又会从另一个方向重新打开同一个漏洞。在为一个理应阻断畸形输入的守卫设计快速路径
  *之前*，请先阅读 #22 的门控要求。
- **脚本之上还有一个成本更低的层。** 钩子处理程序可在其注册信息中携带一个
  `if` 字段——使用权限规则语法，例如 `"Bash(git *)"`——当它不匹配时，
  钩子命令**完全不会运行**：零次 fork，因为根本没有进程。按照设计，它仅提供尽力而为的保证
  （文档指出，当 Bash 命令无法解析时，它会失败时*放行*，仍然运行你的钩子），
  因此应把它视为一种成本优化，**绝不能把它当作门控**——最终决定仍由脚本内的检查作出。
  有三个容易踩坑之处：它只能容纳一条规则（不支持 `&&`/`||`），它只在工具事件上求值，
  而在非工具事件上设置了 `if` 的钩子**永远不会运行**。

## 区分正常工作守卫与污染会话守卫的规则

这些并非风格偏好——每一条都对应一个我们曾发布并追溯定位的具体故障。

### 1. 始终使用 shlex 在**词元级别进行匹配**，绝不要用 awk 拆分原始字符串

守卫**错误阻断健康命令比漏报更糟**——必须绕过的守卫会让人形成条件反射般的绕过习惯，
最终它将无法保护任何东西（核心原则：*误杀健康输入比漏报更糟*）。误阻断反复出现的原因，
就是直接在原始命令字符串上执行匹配。


- **错误做法**：使用 `awk '{gsub(/&&|\|\||;|\|/,"\n")}'` 将命令拆分为若干段——awk
  不理解 shell 引号，因此 `grep -E "a|TRIGGER|b"` 会在带引号正则表达式*内部*的
  `|` 处被拆分，`TRIGGER` 会变成一个并不存在的命令，守卫因此阻断一个普通的 grep。
  （发布于 2026-07-21；该守卫第一次真正投入使用，就错误阻断了我自己的 grep。）
- **正确做法**：使用 **`shlex.shlex` 类**对整个命令进行词元化，而不是使用
  `shlex.split()` 函数——`split()` 仅在 `| ; & < >` 两侧有空格时才会将其视为分隔符，
  因此 `ls|TRIGGER x` 会被词元化为 `['ls|TRIGGER', 'x']`，你的命令位置检查根本看不到
  `TRIGGER`（实测；使用 `punctuation_chars=True` 的类会得到
  `['ls', '|', 'TRIGGER', 'x']`）。应逐字复制一个已发布的遍历器，而不是随手写个单行版本——
  但**要复制能通过 `scripts/test_hook.sh` 的那个版本**，也就是 **A 模式中的版本**。
  [遍历器一节](references/hook_patterns.md#the-shlex-command-position-walker)提供的是一个
  *精简*版本，并且明确说明了这一点：它省略了各个包装器的带值标志表，因此会漏掉位于
  **带值标志包装器**之后的目标——实测，它会将 `timeout 5 TRIGGER`、
  `sudo -u root TRIGGER` 和 `nice -n 10 TRIGGER` 判定为“不在命令位置”，而 A 模式的版本
  能捕获这三种情况。（裸命令 `sudo TRIGGER` 在两个版本中都能正常处理——问题在于包装器
  *自身*的标志需要接受一个参数，而精简表不知道应跳过这个参数。）发布的测试工具中只包含
  其中一种形式，因此你实际看到的运行结果是：精简版本在 21 项测试中**通过 20 项，
  `wrapper-timeout` 失败 1 项**，而 A 模式为 21/0；另外两个问题会静默失败，因为没有测试行
  覆盖它们。带引号的 `"a|TRIGGER|b"` 会保持为**一个词元**，因此正则表达式参数绝不会被
  误认为命令。然后，检查目标是否处于**命令位置**（token[0]，或紧跟在
  `;`/`&&`/`||`/`|` 分隔符之后，同时跳过 `VAR=val` 环境变量赋值前缀）。命令位置遍历器见
  [references/hook_patterns.md](references/hook_patterns.md)。
- 推论：`echo "…TRIGGER…"`、`grep TRIGGER`、`# TRIGGER`、`man TRIGGER` 必须全部放行。
  你的测试集必须包含这些“提及但不执行”的情况。
- **推论——在 `git` 写操作段到达遍历器之前将其排除。** 提交消息可以是任意数据，而整段
  消息文本都会作为伪命令文本进入你的命令位置遍历过程——`git commit -F - <<EOF` 中，
  如果正文引用了 `foo|TRIGGER`，`TRIGGER` 就会落入命令位置，导致守卫阻断它自己的修复提交
  （陷阱 #7 正是这种已发布的故障）。任何检查命令字符串的 Bash 守卫，都必须跳过头部为
  `git` + `commit`/`rebase`/`tag`/`am`/`cherry-pick` 的命令段——并且必须在整个命令层面、
  任何按行拆分之前完成这一步（A 模式展示了处理顺序；生产版本使用
  `lib-git-commit-detect` 的邻接检查）。
- **推论——遍历器采用两阶段处理是有原因的。** `whitespace_split=True` 会把换行符当作普通
  空白字符，因此，多行代码块（`cd /x\ngit add\nTRIGGER -y`）会被折叠为一个以 `cd`
  开头的命令段，触发命令永远不会处于命令位置——在真实记录上回放时，触发率为 0
  （陷阱 #11）。应先以 **shell 感知方式**拆分为多行（正确处理引号状态和反斜杠续行，
  因此带引号的多行字符串不会被拆碎），然后再用 shlex 遍历每一行——A 模式和遍历器一节
  都提供了这个拆分器（`split_shell_lines`，已在 qlmanage-guard 的生产环境中验证）。
  即便如此，它仍无法解析 heredoc 正文（那并不是引号语法）；何时接受这一残余风险，
  应按 #11 的结论处理。
- **但 shlex 并非万能药，而且你要检测的*内容*决定了失败时放行是否安全。**
  `shlex.split()` 本身会在引号不匹配时抛出 `ValueError`——包含 `#` 或未闭合引号的多行
  `git commit -m "…` 消息就是典型触发条件。随后，`except ValueError: cmd.split()`
  回退路径会执行*放行*；当你检测的是**禁用修饰符**时，这是正确做法（它是否携带
  `--no-verify`？——漏掉它是偏向安全的错误，符合规则 1 的方向），但当你检测的是
  **该命令本身是否就是你的目标**时，这会很危险（这是 `git commit` 吗？——如果此处出现
  ValueError，守卫就永远无法识别该提交，并悄无声息地不触发；我们曾因此发布过一次没有
  确认对话框的真实跨域提交）。对于“这是否为该命令”的判断，应优先使用范围狭窄的
  **正则表达式**（将 `git` 和 `commit` 作为独立单词，二者之间允许任意标志词元），
  它不会受到多行引号破损的影响；而 shlex 遍历器应保留给*命令位置／修饰符*检查，
  因为在这些检查中，失败时放行才是安全方向。（边界是：当谓词为“这究竟是不是某个特定的
  常见命令”时使用正则表达式——例如 `git commit`、`git push`——这些命令自身的消息或参数
  正是导致词元化失败的内容；当谓词为“是否有*禁用的*命令或修饰符处于命令位置”时使用
  遍历器——在这种情况下，禁用项很少见，ValueError 导致的失败时放行是偏向安全的错误，
  符合规则 1 的方向。）

### 2. 在注册之前，先使用 **bash -n + 真实 JSON 事件进行端到端测试**

**损坏或逻辑错误的 PreToolUse hook 会污染整个会话** —
之后的每次 Bash 调用都会被截断、重复、错误地判定为失败，或者看起来像是产生了幻觉般被执行，
而你会把问题归咎于“环境”，实际上罪魁祸首正是你刚安装的 hook。
（2026-07-05：一次编辑破坏了 `[^;&|]` 正则表达式，`;&` 变成了
bash 的 case 穿透标记，污染了半个会话，直到 `bash -n` 才发现问题。）
“我的测试在部署时通过了”并不足够——文件可能在后续编辑中损坏。

在注册任何 hook 之前进行把关：
```bash
bash -n hook.sh                                # syntax
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<trigger case>"}}'    | ./hook.sh; echo "exit=$?"  # want 2
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<healthy lookalike>"}}'| ./hook.sh; echo "exit=$?"  # want 0
```
把测试框架一并提供：[scripts/test_hook.sh](scripts/test_hook.sh) 会运行一整套
触发/放行用例表。**自我阻断陷阱：** 一旦 hook 已在会话中生效，你就无法通过在自己的 Bash
命令中放入触发字符串来测试它——当前生效的 hook 会阻止你的测试命令。应将用例放入一个
**脚本文件**中，然后运行 `bash test_hook.sh`；外层命令不包含触发字符串，
因此不会自我阻断。

**一旦 hook 导致过一次真实事故（误阻断或静默漏检），
仅靠独自重新阅读代码是不够的**——在一次 Stop-hook 防护逻辑的当日重写中，
作者在修复第一个 bug 时又两次重新引入了问题（Python 注释中的一个引号，
重新阅读时无法察觉，只有运行实际失败的 JSON 用例才暴露出来）。此时应升级为多视角的
智能体团队审查，其中每一项发现都必须通过针对实际脚本*执行*真实 payload 来复现，
而不能只是阅读代码并表示赞同——这就是通用的 Counter Review 方法论
（skill-creator 的 `skill-development-methodology` 参考资料，第 6 阶段），只不过
应用对象从 skill 换成了 hook。在一次这样的审查中，3 个视角（匹配
逻辑 / shell 嵌入安全性 / 事件契约稳健性）发现了 13 个经确认且独立复现的 bug，
以及 1 项其引用证据最终被证明是幻觉文档引文的发现——之所以能识别出来，
仅仅是因为验证者被要求 curl 原始来源并 grep 精确字符串，而不是相信该引用。

### 3. 使用 SSOT + 符号链接，防止重新安装时悄无声息地解除防护

实际脚本放在受版本控制的目录中，并通过**符号链接**放入 Claude 读取的 hooks 目录：
```
~/scripts/claude-hooks/<name>.sh      # SSOT (this setup: a private git repo)
~/.claude/hooks/<name>.sh             # symlink → SSOT

# install / recover:
ln -s ~/scripts/claude-hooks/<name>.sh ~/.claude/hooks/<name>.sh
```
重新安装 `~/.claude` 会清空 hooks 目录；符号链接目标仍然存在，
只需执行一次 `ln -s` 即可恢复。悬空的符号链接会在**没有任何
信号**的情况下禁用 Tier-0 防护——这正是需要 SessionStart 健康检查的原因（规则 4；可运行的
框架：参见 [references/hook_patterns.md](references/hook_patterns.md) 中的 Pattern C）。

### 4. 注册按配置文件分别进行——收敛所有配置文件，通过人工闸门放行

- 如果*当前配置文件的* `settings.json` 没有调用 `~/.claude/hooks/` 中的钩子，
  那么该钩子**不会保护任何东西**。在所有配置文件完成收敛之前，多配置文件用户一直处于
  零防护状态。请在**主**配置文件的设置中注册
  （在此配置中为 `~/.claude/settings.json`；
  [references/hook_patterns.md](references/hook_patterns.md) 的“注册”一节提供了准确的 jsonc
  结构）——PreToolUse → 匹配器 `Bash` → 你的钩子——然后收敛其余配置文件（此配置
  使用 `sync-profile-settings.py --all`，由 `claude-switch-models-setup`
  skill 负责）。SessionStart 健康检查会在每个配置文件中 grep Tier-0 防护，
  以捕获配置漂移。CLI 的文件监视器会自动加载设置更改（官方
  钩子文档），因此注册无需重启即可生效——可通过观察防护在安全探测上触发，
  或查看下次会话的健康检查行来确认。
- **如果防护需要一个泄压阀，请将其设为*人工*闸门，而不是环境变量。**
  静态的 `GUARD_OK=1` 逃生口根本不算闸门——模型可以自行设置该环境变量。
  使用原生 macOS 对话框（`osascript`——模型无法点击）；
  拒绝/取消/超时 = 强制 NO；将每次提示/绕过都记录到审计文件中。
  模式见 [references/hook_patterns.md](references/hook_patterns.md)。
  - ⚠️ **`/dev/tty` 不是第二通道——文档说明钩子无法打开它。**
    本文件过去曾规定，除了对话框之外，还要在 `/dev/tty` 上键入 `YES`。
    官方参考文档明确指出：钩子“在自己的会话中运行，**没有
    控制终端**”，并且“钩子进程及其任何子进程**无法
    打开 `/dev/tty`**”（`terminalSequence` 是文档指定的写入替代方案）。
    因此，以这种方式构建的“双通道”闸门实际上只是一个通道加一段死代码，
    而且在没有 GUI 会话的机器上，任何人都永远无法批准该闸门。
    这与本地观察结果一致，但要仔细理解其边界：在某个
    配置的共享审计日志中——共 1,801 条记录，由多个防护写入，其中三个
    实现了 tty 通道——**有 360 行带有通道标签（236 次对话框
    确认，124 次拒绝或超时），却没有任何一行以任何方式提到
    tty 通道。**这意味着 tty 分支从未被*进入*；在 macOS 上，
    这本来就是可以预料的，因为对话框会先返回结果并使其短路。
    因此，日志表明此处从未有任何内容依赖 tty；证明 tty 完全无法工作的，
    是文档，而不是这次测量。
    保留对话框；如果你需要非 macOS 闸门，
    则需要一种本文件尚未提供经验证答案的通道。
  - ⚠️ **存活时间超过钩子超时的人工闸门会以开放状态失败。**钩子 `command`
    的默认超时时间为 600s（`UserPromptSubmit` 上为 30s），而超时的钩子
    **不会阻止工具调用**——因此，无人应答的对话框不会变成“否”，
    而会变成允许。将等待时间限制在远低于超时时间的范围内，并在执行框架
    替你作出决定之前，自行将无应答解析为阻止。
  - 文档还提供了一种 UI 内通道——PreToolUse `hookSpecificOutput`
    `permissionDecision: "ask"`，它会通过 Claude Code 自身的界面发出提示。
    这值得了解，但在 `bypassPermissions` /
    自动接受模式下，**此处尚未验证**；而这恰恰是 Tier-0 闸门必须能够抵御的模式。
    之所以规定使用对话框，是因为它不依赖权限模式。
  - **在 Tier-0 以下，允许模型可自行使用的逃生方式时，应将其设计为
    正确用法，而不是绕过标志。**上述规则对于 Tier-0 是绝对的，
    在这里也不会放宽——这里讨论的是达不到 Tier-0 级别的正确性防护；
    对于检测器无法区分的合法情况，它们仍然需要一种退出方式。
    问题在于你要让这种退出方式*成为什么*。`SKIP=1` /
    `--force` 环境变量逃生方式，恰恰会培养规则 1 所警告的条件反射，
    而在截止期限压力下，它与绕过没有区别。应优先选择这样的逃生方式：
    **它本身就是你原本希望他们采取的做法**，使得采用该方式会改进命令，
    而不是解除防护：当命令提到
    `pipefail` / `PIPESTATUS` / `pipestatus` 时，`pipe-fallback-guard` 会立即以 0 退出，
    因为写下其中任何一项的作者已经证明自己理解管道退出码——该防护
    已经没有什么可教他们的了。应采用的检验标准是：*如果有人使用我的逃生口，
    最终得到的命令会变得更好，还是仅仅解除了阻塞？*如果诚实的答案是
    “仅仅解除了阻塞”，那你拥有的只是一个名字更好听的绕过标志。对于 Tier-0
    情况还有一个同类原则，此时覆盖机制的存在仅用于测试闸门：
    **逃生口只能让闸门变得更严格**——参见
    [references/hook_patterns.md](references/hook_patterns.md) 中关于 `GIT_GUARD_TEST`
    的讨论。

### 5. 确定故障的**方向**，并测试*这个方向*——而不只是正常路径

规则 1 对*检测调优*错误进行了排序：在防护机制已经运行的前提下，错误拦截一条正常命令，比漏掉一个罕见的异常命令更糟，因为一个必须由人们绕过的防护机制，最终会被人下意识地绕过。**本规则讨论的是另一个维度——防护机制本身根本没有运行**——因此这里并没有颠倒“哪个更糟”的判断；这两种排序互不相交。一次调优漏检只会让你损失一个案例；而这种故障会让你失去整个防护机制，并且对所有具有这种形式的输入都悄无声息地失效。

故障情形是：防护机制**无法获取它赖以判断的对象**——解析引发异常、路径无法解析、依赖缺失、子进程超时——而原本用于防止钩子崩溃的  
`2>/dev/null || true`，却悄悄地将*“我无法检查”*转换成了*“没有需要报告的内容”*。钩子以 0 退出。**这个输出与真正通过检查时完全相同**，因此这种问题能够持续数周而不被发现。

所以，在钩子*获取*某些内容的每个位置（解析命令、读取暂存文件、查询服务），都要明确决定：**如果返回结果为空，这意味着允许还是阻止？**——并把答案写在相应分支旁边。对于*修饰项*检查，故障时放行通常是正确的（它是否带有 `--no-verify`？漏掉它只会损失一个案例）。对于*这到底是不是目标对象*的检查，故障时阻止通常是正确的（这是一次跨域提交吗？结果为空意味着防护机制根本没有触发）。

**然后测试故障方向，而不是正常路径**：故意向它传入无法解析的路径或无法解析的命令，并断言它仍会执行你所决定的行为。如果测试套件中的每一行都因为*钩子悄无声息地放行了一切*而通过，那么它与真正通过的测试套件无法区分。

**仔细阅读这些结果——对于不同类别的防护机制，相同输入对应的正确答案正好相反。**以 `cd ~/no-such-dir && TRIGGER` 为例：

| 防护机制类别 | 判断依据 | 正确的退出码 | 原因 |
|---|---|---|---|
| **令牌匹配器**（这是被禁止的命令形式吗？） | 仅命令文本 | **2，阻止** | `TRIGGER` 就在那里，直接出现在文本中；无法解析的 `cd` 不会让它变成非触发命令，而且如果防护机制在这里保持沉默，那么面对 `cd ~/real-dir && TRIGGER` 时它也会保持沉默 |
| **状态推导器**（仓库的暂存集合是否跨越多个域？） | 从磁盘读取的状态 | **0，允许** | `cd` 失败，`&&` 短路，提交根本不会发生——没有任何需要防护的操作 |
| **终止状态读取器**（补救操作是否已经执行？） | 回执／计数器文件（规则 7） | **0，允许**——*当状态文件本身就是终止条件时* | 无法读取回执意味着钩子无法知道自己已经触发过；在这里故障时阻止，会导致永久阻塞，既无法进行补救，也没有任何人类可见的原因——这*就是*循环，也是唯一一种比漏掉一个案例更糟的故障。**相反的子场景——复制这一行之前请先阅读：**当状态只是在独立谓词之上叠加的**预算**时（完成相应工作仍然可以解除阻止），读取失败时放行会**悄无声息地禁用整个钩子**——一个不可写目录就能让它对所有输入永远保持沉默，这是最糟糕的故障形态。在这种情况下，应退回到*预算存在之前的行为*（继续评估谓词），而不是保持沉默。**用一个问题区分二者：如果状态消失，补救是否仍然可行？**否 → 回执场景，允许。是 → 预算场景，继续检查。这里给出完整答案，免得每个人都要重新推导：规则 7 的机制 2（回执）**以及**机制 3（每会话计数器）都属于**回执场景 → 允许**——机制 3 有意不判断 R 是否发生，因此它的计数器是唯一出口，禁用计数器会使该轮次陷入困境。预算场景则是将计数器叠加在一个用户仍可独立满足的谓词之上 |

因此，在编写测试行**之前**，先确定你的钩子属于哪一类；测试框架的
`unresolvable path` 模板行预期结果为 **2**，因为该模板针对的是
令牌匹配器类。把这一点弄反，会对一个正确的防护措施给出十分肯定的 FAIL。
对于状态推导型防护措施，你要找的失败是：**该命令实际上确实会执行，而防护措施却没有发现它**
——不配对的引号会导致令牌化抛出异常，回退逻辑会选择允许，于是一次真正的跨域提交
在没有任何对话框的情况下就被送出去了（规则 1 中关于 ValueError 的说明）。
对每个结果为允许的测试行都要问一句：*这条命令实际上会完成那件事吗？*
如果不会，那么允许就是正确的。

对一个真实的状态推导型防护措施运行这个精确的探针时，第一次执行返回了两个允许结果：
其中一个是正确的（即上面的短路情况），另一个则是真正的
失败开放。**探针会发现问题；但你仍然必须对它发现的结果进行分类**
——这就是为什么上面的类别表要放在这些测试行之前。

真实案例（2026-07-22）：一个作用域防护措施通过 `git -C "$REPO_DIR"`
读取暂存文件，而 `REPO_DIR` 是从**命令文本**中解析出来的——因此，`cd ~/repo && git commit`
会向它传入字面量 `~/repo`，`git -C` 执行失败，获取到的暂存文件列表为空，而防护措施
由此得出“没有跨域文件，允许”的结论。所有跨仓库提交都绕过了防护，
而且从表面上看始终没有任何异常。完整剖析及共享库带来的额外转折：陷阱 #10。

这个解析器还有另一个方向的失败，而且更为棘手。一旦你
添加回退逻辑来阻止它失败开放，这个回退逻辑就会因为一种原因而正确，
又因为另一种原因而错误——而两种情况输出的却是同一行。`git push`（没有
显式目标）合理地回退到事件的 `cwd`；`git -C "$R" push`
则*指定了*一个钩子无法解析的目标，于是回退到同一个 `cwd`，然后
针对另一个仓库给出一个十分肯定的 ✅。这两种情况的渲染结果
逐字节完全相同（实测 MD5 相同），因此无论钩子还是读者都无法
分辨哪个判断是真实的、哪个绑定错了对象。**回退值必须携带选择它的原因**，
并且只有“没有显式目标”才有资格得出判断。完整剖析、混淆代理视角，
以及为什么使用字面路径的固件永远无法发现这个问题：陷阱 #28。

### 6. 根据现实世界可以回答的事实进行判断——绝不要根据你自己的渲染结果，也不要根据命名习惯

规则 1 和规则 5 讨论的是*如何*匹配以及失败时*偏向哪一边*。本规则讨论的是
**你所匹配的内容来自哪里**，它有两种都会悄无声息发生的失败形式：

- **绝不要根据你为人类格式化的字符串进行分支判断。** 如果钩子构建了一份
  报告——经过排序、拼接、截断为前 N 项，并在末尾添加 `(+M more)`——然后
  又通过模式匹配这份报告来作出自己的决定，那么该分支就会继承
  渲染过程造成的信息损失。超过截断点的项目对它而言根本不存在，因此这个
  分支在每个小型固件上都能正常工作，却恰恰会在它原本要处理的大型
  会话中停止触发。应在独立通道中输出机器可读的事实（单独一行、未经截断的
  `KINDS:a,b,c`），并匹配*该内容*。渲染结果是输出，而不是
  数据源（陷阱 #12）。
- **优先选择可验证的事实，而不是命名约定。** 根据路径形态进行分类
  (`/skills?/[^/]+/references/`) 固化了一种目录布局；采用其他任何布局的仓库
  都会被分类为 `None`——悄无声息，而且永远如此。修复方法*不是*放宽
  模式，因为这只会把静默漏判换成整个机器范围内的误报（规则 1
  明确禁止这种取舍）；正确做法是提出一个文件系统能够回答的问题——
  *这个 `references/` 目录旁边是否存在 `SKILL.md`？* 事实能够经受
  布局变化，约定则不能。（当候选项本身**就是** `SKILL.md` 时，
  并不存在可供查询的同级项——应根据 basename 进行分类；#13 解释了为什么
  这是由规范定义的事实，而不是本规则所警告的命名习惯。）
  **可验证的事实仍然可能是错误的事实——要锚定问题并按类型过滤。**
  `test -f SKILL.md` 在下载文件夹中也可能为真；曾有一个防护措施沿着
  祖先目录查找这一文件，结果把整个主目录都囊括了进去，随后要求一个真实
  会话加载以该目录命名的技能——而这个名称根本不可能存在（规则 9 中的事件）。
  应锚定到某个*特定*目录的同级位置或已知安装路径；未锚定的
  祖先遍历，不过是披着事实外衣的约定。

两者的判断依据都是：某个分支在生产环境中一次都未触发过，而其测试却一直为绿色。打印格式化之前的原始分类结果，你就会看到自己遇到的是哪一种情况。

### 7. 如果钩子**要求补救**，请证明循环能够终止

一个在完成 X 之前始终**阻止执行**（退出码为 2）的钩子——尤其是 Stop 钩子，因为它们会在之后每次停止时再次触发——并不是检查，而是一个**反馈循环**。
（如果钩子只是*注入*一项要求并以 0 退出，则根本不存在循环：没有任何内容会被重新评估。那就是下面的机制 0，而且它作为正确默认方案的适用场景，远比人们通常认为的更多。）

```
condition T is true → hook demands remediation R → model performs R → T checked again
```

**在第一个周期之前编写循环契约——这同样适用于由钩子强制执行的循环，以及由智能体驱动的审查／等待／重试循环：**

```text
LOOP KEY: immutable logical target / lineage + one failure axis
FIRE T: the condition that starts another cycle
REMEDIATION R: the exact action one cycle performs
VARIANT V: the well-founded quantity that strictly decreases for this key
BUDGET: maximum cycles, fixed before cycle 1
SUCCESS EXIT: the observable that proves the axis is clear
CAPPED EXIT: what is left blocked / unshipped / pending when the budget ends
```

如果契约尚未完成，就不能使用会阻止执行的 Stop 钩子，也不能反复运行审查者循环或轮询循环。在第一个周期之前冻结键。补救快照、提交或审查者名称都属于同一谱系，不能借此产生新的预算。一个全新的、不相关的发现对应一个**新键**：请单独记录；它不会重置此循环的预算。如果某个周期无法指出新的证伪实验或更小的 V，它就没有增加任何证据，必须停止。

对于**由智能体驱动的独立审查循环**，默认预算为一次初始审查，加上在完成实质性修复后进行的一次范围严格限定的重新审查。不会自动引入第三位审查者。如果重新审查仍在同一维度上复现 BLOCKER 或 MAJOR，则让钩子保持未注册／产物保持未交付状态，报告阻塞状态，并要求创建一个新的、经用户授权的任务，且该任务的循环契约必须在第一个周期之前声明其预算。由智能体自行声明的预算不能自我授权。在该已授权任务中，需要明确说明现在停止会导致的具体安全故障或业务故障；可有可无的润色不符合条件。

填写完毕的审查循环示例：

```text
LOOP KEY: <initial frozen commit>'s review lineage + termination-contract fidelity
FIRE T: fresh review reports a same-axis BLOCKER / MAJOR
REMEDIATION R: reproduce that finding, apply one bounded fix, run its narrow check
VARIANT V: 2 - completed review cycles
BUDGET: 2 cycles total (initial review + one re-review)
SUCCESS EXIT: no same-axis BLOCKER / MAJOR
CAPPED EXIT: artifact stays unregistered / unshipped; report remaining findings
```

初始冻结提交的每个修复后代都仍属于此键。当前快照会发生变化，以便审查者检查修复；谱系及其剩余预算不会改变。

没有任何机制会强制执行这个无钩子预算——它只有在智能体遵循该 Skill 时才有效。正因存在这一限制，达到上限时的退出状态必须清晰可见，而且绝不能被报告为“已完成”。

**如果完成 R 会让 T 再次变为真，循环就不会收敛。** 不会报错，也不会崩溃；它会一轮又一轮地运行，直到有人手动中断——而这通常正是最终的结果，因为每一轮都是一次*完整的*补救周期（派发、等待、采纳、编辑），而不是廉价的重试。**同样是这一特性，导致执行框架设置的连续阻塞 8 次上限也救不了你：每次执行过工具后继续运行，计数器都会重置，因此，由工具调用构成的补救周期会让计数器永远停留在 1**（实测结果——#27）。即使真的触及该上限，它也只是防止会话失控的最后保障，而不是一种设计方案：这一轮结束时，违规状态仍然存在，而执行框架会将该轮报告为 `reason:"completed"`——与真正完成完全无法区分。“它最终会停下来”不属于任何你想要的终止保证，而且在这里，它甚至根本不会最终停下来。`stop_hook_active` 在这里也*救不了*你——该字段只涵盖**一层重入**（“我刚刚阻止的停止操作正在重试”）。它完全没有涉及*跨轮次*场景：模型确实离开去执行 R（真正的工作，包含大量工具调用），然后自然停止；这是一个全新的 Stop，该字段为 `false`，钩子会基于相同的理由再次触发。

**这一测试借鉴自程序验证中的终止性证明**——即[循环变体 / 排名函数](https://en.wikipedia.org/wiki/Loop_variant)：写下一个映射到良基序（通常就是 ℕ）的量 **V**，并证明 **V 在每个 `trigger → remediate → re-check` 周期中都会严格递减**。没有 V，就没有终止性证明——不要注册该钩子。

**V 是设计时义务，而不是代码**——你永远不需要在钩子中计算它。实际交付的是*谓词*（下文介绍的机制）；V 则是证明该谓词会收敛的论证。把它放在下一位读者一定会看到的位置——脚本头部：

```bash
# TERMINATION: V = 1 - exists(<receipt path>)
# decreased by: R writes the receipt; nothing R does afterwards can remove it.
```

“证明它会递减”具体包含三个问题，而答案应写进该注释：

1. **R 改变了什么？** 指明具体的文件 / 字段 / 时间戳。
2. **该项是否为 T 的操作数？** 如果是，而且 R 会让它重新趋向于“触发” →
   那么 V 不存在。
3. **执行 R 后，能让 T 再次变为真的最小输入是什么？** 如果答案是
   “就是我刚刚据以触发的同一个输入” → 那么 V 不存在。请重新设计谓词；
   不要调整阈值。

**一个真实的反例。** 某个 Stop 钩子要求，在复合制品（规则文件、技能、其他钩子）可以被推送之前，必须进行独立审查：

- **T**（使钩子**触发**的条件）=“存在尚未被任何审查覆盖的编辑”，通过时间戳比较
  `last_edit > last_review` 实现（`last_edit` = 整个制品集合中的最新 mtime，
  `last_review` = 审查记录的 mtime——只是两个单独的数字，这恰恰让这种比较看起来很安全）
- **R** = 派发一名独立审查者

但一个值得运行的审查**必然会有输出**：其发现会**由同一个代理立即采纳，且发生在它下一次尝试停止之前** → 这会产生新的编辑 → `last_edit` 移到 `last_review` 之后 → **T 再次为真**。（如果之后由人工在带外采纳这些发现，就不会形成循环——该循环要求补救和重新检查发生在同一个代理的轮次内，而这正是 Stop hook 所保证的。）这里不存在 V——补救措施并不会减少某个量，而是会*重置*一个量。唯一的脱身方式是“审查，然后什么也不改”，而这恰恰意味着派出审查者毫无意义。实际观察结果：连续三轮，每一轮都是完整的审查并采纳周期，最终只有在用户说停止后才退出。

有两点使这个问题难以察觉。**单独来看，这个比较完全合理**——“审查必须比最后一次编辑更新”正是你会写出的条件。而这句话是**通过**条件——T 是它的否定。如果你不带这个否定，原样把它记在脑中，那么在接下来的分析中，你推理的将是错误的操作数；应始终让 T 保持为**触发**条件的方向。（把*代码*写成提前退出的守卫子句——`… && exit 0`——是正常的 shell 风格，这里讨论的并不是这个问题；这里的纪律是你以哪个方向进行推理。还要注意相等的情况：同一秒的 mtime 会落在通过的一侧，即采用失败开放策略，这与下文中该规则对状态读取的要求一致。）运行上面的检查清单，结论就会自然而然地得出：R 改变了 `last_edit`（Q1）；`last_edit` 是 T 的一个操作数（Q2）；能让 T 再次触发的最小输入正是补救措施自身的输出（Q3）→ 不存在 V。

**第二种失败形式：谓词完全看不到补救措施（可观测性缺口）。**上面的反例是一个会被补救措施*改变*的时序谓词。同一类问题还有一种更隐蔽的失败：补救措施确实发生了，但在此环境中，谓词读取它所依赖的通道并不存在。真实案例（2026-07-26，在一次全量循环审计中发现）：某个 Stop hook 通过扫描 tool_results 中的 `agentId: <hex>` 并读取 `subagents/agent-<hex>.jsonl`，来检测“是否进行过独立审查”——这在主 profile 上是正确的。Team-mode 会话使用的是完全不同的 schema（spawn 回执为 `agent_id: <name>@session-<uuid>`，交付内容是带有 `teammate_id` 的 teammate 消息，文件则为 `agent-a<name>-<hex>.jsonl`）——永远都是零匹配，因此 `last_review` 始终保持为 `None`，每个 compounding-edit∧push 轮次都会再次触发该要求：这是一个误报循环，在每个停止序列中被限制为一次阻止，但跨轮次没有上限；而该会话中的“2/2 次触发”全部发生在已充分审查的工作上。同属一类问题，但解决方法不同：时序循环需要更好的*谓词*；可观测性循环需要更好的*通道*。在检查清单中加入第四个问题——**Q4：在该 hook 将要运行的每一种环境中，谓词真的能够看到 R 发生吗？**对于读取 transcript 的 hook，这意味着要解析来自每个 profile/mode 的真实会话，而不是只用一种 schema 的 fixture 进行测试。（上述案例的修复方法：多 schema 检测 + 从轮次边界中排除 teammate 交付内容，防止它们截断检测窗口——陷阱 #20。）

**先按维度选择，再按顺序选择——这并不是同一种机制的五种强度。**
0 决定*是否要阻塞*；1 决定*将阻塞挂在哪个事件上*；2–4
是*谓词的形态*（选择 1 后，你仍然需要从 2–4 中选择一种）。0→4
的顺序表示“循环被消除得有多彻底”，它与**你能施加的强制程度成反比**
——因此，应选择第一个仍能提供你实际所需强制力的选项，而不是简单地选择第一个选项。

0. **不要阻塞——改为注入。** 如果要求只是建议性的（你希望模型
   *考虑* R，而不是让它不完成 R 就无法结束），就输出提示并以 0 退出。
   不会发生重新求值，因此也就没有需要证明会终止的循环。对于任何低于 Tier-0 的事项，
   这都是正确的默认选择，而其代价也很明确：提醒可能会被忽略，因此应在标题中说明它是
   fail-open 的——规则 4 的要点仍然成立：主体可以径直绕过的门控就不是真正的门控。
   如果你需要的是一个*门控*，请使用 2，并承担获取凭据的成本。注入通道：模式 D。
   ⚠️ **此选项在 Stop 上并不存在**——而规则 7 的主要讨论对象*正是*
   Stop，因此在试图使用它之前，请先读完这里。在 Stop 上，`exit 0` 意味着“允许
   回合结束”，因此之后不会再有推理步骤接收这段文本；而且
   `hookSpecificOutput.additionalContext` 与 `exit 2` 受同一个阻塞 8 次上限约束
   （参见 hook-types 一节），也就是说，它同样属于阻塞。Stop 恰好只有两种模式：
   门控，或者静默。因此，在 Stop 上选择机制 0 实际上意味着**更改事件**
   ——将注入挂到生成该产物的工具调用上（PostToolUse，模式 D）——或者承认你
   终究想要的是门控，然后转到机制 2。
   ⚠️ **只有当 R 不是你自己的匹配器目标时，“没有循环”才成立。** 一个针对
   `Bash` 的注入器若提示模型运行 `git ls-remote`，就会在该命令执行时再次触发，
   并再次注入。形态相同，只是更温和——模型可以忽略它，因此不存在强制迭代，
   但它仍会在每次重复时广播，而非毫无动作。请检查你建议执行的 R 是否正是此 hook
   会匹配的动作。

1. **将检查移到动作边界。** 如果你想门控的是一个*动作*——推送、发布、删除——
   就使用 PreToolUse 保护**该动作**，而不是使用 Stop 保护**整个回合**。
   **Stop-hook 补救循环通常只是挂错了事件的动作门控**，这正是 hook-types 一节中
   “Stop 是异类，也是最常被误用的那个”这一说法的具体情形。
   **要准确理解这样做能带来什么。** 只有当模型*主动重试被门控的动作*时，
   PreToolUse 才会再次触发，而模型始终可以选择放弃并正常结束其回合。因此，它保证
   **回合会终止**——最坏情况从“回合无法结束”降为“这个动作不会发生”。但它
   **不会**让一个不收敛的谓词变得收敛：以前面的反例为例，在不做任何修改的情况下
   将其移到 PreToolUse，循环仍会完整保留（push → 被阻塞 → 审查 → 采纳发现 →
   进行新编辑 → 重试 → `last_edit` 再次更新 → 被阻塞）。该情形的问题出在其
   **谓词**，而不是事件，因此你仍需要从 2–4 中选择一种形态。另请注意，PreToolUse
   **没有**执行框架兜底——hook-types 表中的阻塞 8 次上限仅适用于 Stop——因此，
   移到这里的自重置谓词拥有的安全保障不是更多，而是*更少*。
   ⚠️ 有两种情形不应使用此机制：**R 必须使用你门控的那个工具来完成**
   （例如，对 `Edit` 设置保护，要求你先修复文件头——这会造成死锁，要求永远无法满足），
   以及**同一会话中会重复发生的动作**（例如，一个会推送五个仓库的会话中的
   `git push` 门控 = 五次完整要求；这就是下方实战案例中的密度问题，而机制 1
   并不能让你免受这一问题影响）。

2. **将“已经修复”定义为存在性事实，而非时间性事实——并根据需要修复的对象为其设置键。** 让 R 生成一个工件，并检查它*是否存在*；键是这一机制能够奏效的关键：

   ```bash
   KEY=$(git rev-parse HEAD 2>/dev/null || printf 'nogit')   # or a hash of the
   RECEIPT="${TMPDIR:-/tmp}/my-guard.${KEY}.ok"              # reviewed content
   [ -f "$RECEIPT" ] && exit 0            # V = 1 - exists, for THIS key
   ```

   `V = 1 - exists` 是**按键计算的**：对于每个键，它只会减少一次，并且*对于该键*永远无法再次增加。新工作会生成一个*新*键——这是新的需求，而不是重新启用。两种简单的键设置方式都会失败：使用单个全局路径会使钩子在每台机器上只触发一次，之后便永久失效且不再提供任何信号；而基于时间的键正是本规则意在禁止的时间谓词。**时间谓词几乎总是错误的形式**，因为你所要求的修复通常正是会改变比较操作数的因素。
   对于一次性的回执门控，这种基于内容 SHA 的键是正确的。但它**不会**重新定义智能体审查谱系：由该谱系的修复所创建的提交仍归属于其原始键和原始预算。
   ⚠️ 如果**模型**能够创建回执，那么这只是规则 4 中已废弃的 `GUARD_OK=1` 逃生通道换了个外壳。应让回执由模型无法驱动的机制写入（审查子智能体自己的输出文件、git note），否则就应承认该钩子仅提供建议，并在其头部明确说明。

3. **设置重复次数上限。** 每个会话中，每个目标最多提醒 N 次——`session_id` 是唯一稳定的键（每个事件中都包含它；参见模式参考中的 JSON 约定）：

   ```bash
   SID=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('session_id','nosid'))" 2>/dev/null || echo nosid)
   CNT="${TMPDIR:-/tmp}/my-guard.${SID}.count"
   N=$(cat "$CNT" 2>/dev/null || echo 0); N=$((N+1)); printf '%s' "$N" > "$CNT"
   if [ "$N" -gt 3 ]; then
     CAPPED_REASON='Loop budget exhausted; the blocked condition remains unresolved. Do not report completed.'
     python3 - "$CAPPED_REASON" <<'PY'
   import json, sys
   print(json.dumps({"continue": False, "stopReason": sys.argv[1]}))
   PY
     exit 0                              # explicit capped stop, not silent success
   fi
   ```

   这种做法很粗糙，而且刻意不判断 R 是否真的发生——但它是*有限的*，而这正是之前缺失的属性。不要用 `$$` 或 `$PPID` 替代：每次运行钩子都会启动一个新进程，因此这些值在每次调用时都会变化，计数器永远无法累积。输出计数（“第 2 次提醒，共 3 次”）——请参阅下方的实战故事，了解为什么这种措辞值得保留。达到上限时的输出使用了文档规定的通用 [`continue:false` / `stopReason` JSON 字段](https://code.claude.com/docs/en/hooks#json-output)，这样用户看到的是因达到上限而停止，而不是一次无法与成功区分的 Stop。这会停止会话；但它**不会**保护发布操作。如果达到上限时的退出信息表明某个工件仍未发布，请在操作边界处使用 PreToolUse 单独实施限制。

4. **滞后机制 / 冷却窗口**（控制理论针对
   [告警抖动](https://utcc.utoronto.ca/~cks/space/blog/sysadmin/HysteresisMeaningAndAlerts)给出的答案）：
   触发后，在一段时间窗口内禁止重新求值——使用一个时间戳文件，再加上
   `[ $(( $(date +%s) - <stamp mtime> )) -lt 900 ] && exit 0`（在 BSD/macOS 上，mtime
   通过 `stat -f %m` 获取；在 GNU 上则通过 `stat -c %Y` 获取——本文其他代码片段
   也是如此）。这适用于*围绕阈值振荡*的条件；但**不适用于**
   会被补救措施**重置**的条件——后者需要机制 2 或 3。
   ⚠️ **滞后机制不提供 V——它是速率限制器，不是终止性
   证明。**只有当条件自行消退时，循环才会结束，而此时终止循环的是外部世界，
   不是你的钩子。因此，其 `# TERMINATION:` 行必须指出这一外部事实（“在时间戳
   到期之前，X 已由 <whom> 解决”）。如果你无法诚实地写出这一行，那么你需要的
   是机制 2 或 3。（有一种值得注意的家族相似性：机制 0 是这两者的极限情况——
   即上限设为 0 的机制 3，或窗口设为 ∞ 的机制 4。它们的区别在于执行方式，
   而不在于终止性。）

**对于状态本身的失败方向：应用规则 5 的问题，不要按字面措辞匹配。**
如果无法读取或写入状态——例如 `TMPDIR` 不可写、存在沙箱限制、磁盘已满——
则由规则 5 的防护类别表作出决定，而其判断依据是询问：**“如果该状态消失，
补救措施是否仍然可行？”**对于机制 2 和 3，答案是**否**——回执是 R 已发生的
唯一记录，而机制 3 又特意不关心 R 是否发生，因此其计数器是唯一的退出途径——
所以应当**允许停止**。如果一个终止机制无法读取自身状态却仍然进行阻塞，
那么它*本身就是*那个循环，而且现在还没有任何人类可见的原因。

⚠️ **不要仅仅因为机制 3 和规则 5 的“反向子情况”都提到“计数器”，就把机制 3
归入该子情况。**该子情况适用于这样一种计数器：它只是在用户仍可独立满足的
谓词之外，对*反复催促*设置预算——在这种情况下，如果计数器不可读就停止发声，
会让一个原本还有其他清除方式的钩子静默，因此你应当继续对谓词求值。
机制 3 没有这样的后备谓词。**实测结果表明，这种组合会产生如下故障：**
将机制 3 的代码片段粘贴到模式 E 的框架中（根据关于 `-e` 与 trap 的项目，
该框架自带 `set -uo pipefail`），将 `TMPDIR` 指向一个不可写目录，它会在连续
五次运行中都返回退出码 2——`N` 永远无法持久化到超过 1，上限永远不会达到；
而且，一旦补救措施涉及工具调用，#27 已经排除了将运行框架上限作为兜底方案。
这里的失败方向完全由一条该代码片段自身并未包含的 `set` 行决定，因此
**应当把防护放在真正失败的步骤——写入——上，而绝不能放在读取上**：

```bash
printf '%s' "$N" > "$CNT" 2>/dev/null || exit 0   # can't persist ⇒ can't terminate
```

读取操作已经受到防护（`cat … 2>/dev/null || echo 0`），而且**必须保持这种
方式**：计数器文件不存在是首次运行时的正常情况，因此在读取操作上使用
`|| exit 0`，会让钩子在完全健康的环境中永远静默。实测每种变体连续运行五次：
防护写入操作时，在可写的 `TMPDIR` 上得到 `2,2,2,0,0`，在不可写的目录上得到
`0,0,0,0,0`——两种情况都正确；防护读取操作时，**两种情况**得到的都是
`0,0,0,0,0`，也就是说，这是一种根本不会触发任何操作的防护。

**需求文本中的说明性文字不能替代一个会收敛的谓词。** 即使某个钩子的消息写着“如果你认为这没有必要，就直接再次完成”，每一轮仍然会耗费一个完整的补救周期，因为一个被告知必须执行 X 的模型通常就会执行 X。逃生通道必须位于**谓词**中，而不是建议中。

**测试要求，以及这里最容易遗漏的内容：**自检需要包含一个**“补救之后”**的案例——不只是“应该触发时会触发”，还要验证**“R 完成后就会停止触发。”** 如果没有这个案例，非终止在*结构上是不可见的*：每个测试夹具都只是针对某个孤立时间点的判断，而非终止则是**序列**的属性。只检查单点的测试套件，无论拥有多少案例，对收敛性的覆盖率都是零——这正是为什么一个钩子可以在自检全绿的情况下发布，却在首次实际运行时就陷入循环。真正能够观察到这一点的行对（回执不存在 → 触发，回执存在 → 静默，并且包含普通 `run` 行无法表达的设置/清理过程）已经在 `scripts/test_hook.sh` 的“AFTER-REMEDIATION ROWS”下提供了模板；症状 → 原因 → 修复见陷阱 #16。

**证明会终止 ≠ *感觉上*已经终止（2026-07-25 实战教训）。** 一个具有正确存在性事实 V 的 Stop 钩子在一次会话中触发了三次——每次触发都是由一个*不同*的已完成任务发起的合法*新*推动，该机制完全按设计运行——但用户的体验仍然是“为什么这个东西像是卡在循环里了？”（这与机制 2 中“R 所做的任何事情都无法将其重新推高”并不矛盾：**V 按键分别计算**——三个不同的键，三次独立的单向下降。当你无法判断自己处于哪种情况时，这也是诊断方法：如果每次触发都携带一个*新*键，那么机制是正确的，问题在于密度；如果重复触发使用的是*同一个*键——或者谓词因为比较时间戳而根本没有键——那么你遇到的就是上面的反例，需要替换谓词。）从外部看，三个连续发生的独立补救周期与循环没有区别。变元证明解决的是机制问题；它并没有说明**一次会话可能要求多少项不同的补救**。如果你的领域会产生这样的密度（这里的复合制品每天会交付数次），可以考虑将机制 2（存在性事实）与机制 3（会话级上限）配合使用；或者有意识地接受这种观感，并在钩子的输出中明确说明——“最多 N 次提醒中的第 2 次”让人感觉是在取得进展，而没有任何修饰的重复则让人感觉像是循环。**（2026-07-26 后续：同一个钩子中那些看起来属于此类密度问题的触发，最终发现 100% 都是误报——其审查通道在团队模式下无法感知模式；参见上面的可观测性表单。在接受这种密度是“合理的”之前，请先验证这些触发是否真的有证据支持。）**

**终止性和值得与否是两道独立的门槛。** V 证明循环会结束；Loop Contract 的预算和设有上限的退出机制则决定是否值得为另一个周期付出成本。揭示这一区别的无钩子审查循环故障，包括范围漂移为何会悄无声息地产生无穷无尽的“新”工作，见陷阱 #36。

### 8. 等待也需要同样的证明——通知仅供参考，轮询必须有预算

规则 7 讨论的是由*钩子*产生的循环。即使不涉及钩子，同样的模式也会再次出现：**智能体轮询异步结果**——子智能体的报告、后台任务的完成通知、CI 状态。真实会话（2026-07-25）：子智能体的完成通知通过一个可能延迟或丢失消息的邮箱传送；三个不同的智能体都已完成工作，但通知一直滞留未送达，等待中的智能体在约 40 分钟里白白执行了十几轮 `sleep 240` + 催促，直到人类询问它到底在做什么。没有发生任何错误；这个循环只是没有变元。

规则 7 的机制同样适用——前两项可直接套用；迟滞在这里没有对应物（等待不会振荡），其位置由一个等待特有的陷阱取代：

1. **轮询产物，而不是通知。** 如果你真正需要的是某个结果（文件、git ref、API 状态、数据库中的一行），就等待*它*，而不是等待“它是否说自己完成了”。通知是提示；产物才是事实。一旦事实落地，存在性检查就会立即终止，无论是否有任何消息到达。
2. **每次等待都必须有预算，并在编写循环时确定。** 最大轮数 × 间隔（例如 3 × 4 分钟），以及在第一次休眠*之前*就已存在的降级路径：自己完成、询问用户，或者将其标记为待处理并转去做其他工作。“无限期等待看看”不是降级路径——它就是这个循环。
3. **交付协议仅供参考，并非机制。** “完成后通过 SendMessage 报告——沉默视为未完成”值得写下来，但它约束的是智能体是否*发送*，而不是邮箱是否*送达*。在一次会话中，三个提示词里都包含该协议的智能体全部陷入沉默。设计等待逻辑时，要假设通知可能永远不会到达——因为它确实可能不会到达。

还有两个相邻的陷阱，它们都在同一次会话中付出了代价：**对一个其实正在工作中的“卡住”智能体执行 TaskStopping**——邮箱延迟不等于空闲；一名正在进行 20 分钟真实语料库测试的审查智能体，在即将交付结果的前几分钟被当作“卡住”终止了。以及**对等待本身进行 `--dry-run` 风格的探测**：在断定另一端保持沉默之前，先确认你自己的观测通道能够正常工作（在那次会话中，System Events 的窗口计数对一个屏幕上实际存在的对话框自信地返回了 0——权限故障伪装成了证据）。

### 9. 固定测试数据无法告诉你误报率——注册前先重放真实命令语料库

规则 1 对*哪种*错误更糟进行了排序（误拦截优于漏拦截，因为一个迫使人们绕过的防护机制，最终会被下意识地绕过）。规则 2 要求你在注册前进行测试。两者都没有告诉你**误拦截面究竟有多大**——测试表也无法告诉你，因为*你是基于生成检测器的同一套心智模型编写其输入的*。其中的测试用例只包含你想到的模式；按照构造方式，你没有想到的模式必然缺失。这不是一个靠增加行数就能弥补的覆盖率缺口。

**实测于 2026-08-06。** 一个 PreToolUse/Bash 防护钩子通过了包含 26 个用例、对其运行了 5 种变异的表格测试，并完成注册。之后，又用从近期 60 份会话记录中收集的 **11,903 条去重后的真实命令**进行重放：其中 143 条产生了候选项，线上钩子阻止了 46 条，而人工检查全部 46 条后发现，**其中 10 条阻止错误——占其阻止总数的 21.7%**（两个边界案例按正确计算；若作相反判断，则约为 30%）。在 39 分钟内，它已经阻止了 3 个真实会话，其中一个会话被告知加载一个根本不可能存在的技能——即下文的第三个缺陷，它以指向不存在目标的补救指导形式暴露出来。该钩子在同一小时内就被移除了。三个根本缺陷全都位于**解析**层：将续行标记读取为分隔符；在扫描命令段时，把 heredoc 正文和数据参数也算作执行内容；以及路径分类器没有类型过滤器。

这个故事并不能支持两种结论。它**并不**意味着“变异测试不起作用”：后来对同一套测试的审计发现，**钩子逻辑中有 5 处即使删除，全部 26 行测试仍然保持通过**；而且有一行被作者标注为“已从装饰性测试修复”，实际上仍然只是装饰性的——*“我运行了变异测试”不等于“变异测试是正确的”*，正是重放同时暴露了这两个问题。它也**并不**意味着“你不可能事先知道”：其中三个缺陷都是手工重新实现了本文件已经提供的代码（`split_shell_lines`、命令位置遍历，以及 `is_git_write` 对 `-C` 及其参数的处理）。规则 1 中的*原样使用遍历器*才是成本更低却被跳过的修复方式；重放是最后的保障，而不是第一道防线。

**方法——四个步骤，而步骤 2 正是最常被跳过的那个：**

1. **收集。** 会话记录位于
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`，此外还包括在
   `~/.claude/history-sources.json` 中注册的所有归档。命令是 `.message.content[]` 中
   `type == "tool_use"` 且 `name == "Bash"` 的条目，位于字段 `.input.command` 中——**不是**钩子
   事件中的 `.tool_input.command`，后者具有不同的数据结构。进行去重，并抽取足够多的
   会话记录，以覆盖你自己近期使用的工作形式（那次运行使用了 60 份）。
2. **使用随附的检测器进行预过滤，并逐字原样抽取其代码**——绝不要使用手写的
   等价实现，否则你测量的只是自己两个猜测之间的一致程度。预过滤仅用于降低成本
   （11,903 → 143）；真正作出判断的是步骤 3。如果检测器不是一个可以独立抽取的
   代码块——例如它是 shell 代码，或分散在被 source 的库中——那就把它改造成这样的代码块；
   一个无法独立运行的检测器，同样也无法进行单元测试。
3. **将每个候选项连同其自身真实的会话记录和 `session_id` 一起传给真实钩子。**
   读取会话状态的防护钩子在伪造的上下文中会给出不同答案。事件约定见：
   `references/hook_patterns.md`。有两件事会让你踩坑——应在临时的
   `TMPDIR` 下运行，否则规则 7 的回执和每会话计数器会写入真实会话，*并且*
   在你自己的测量进行到一半时使防护钩子静默；如果钩子设有人类确认关卡，应通过
   Pattern B 的强制拒绝路径来驱动它，而不是回答 143 个对话框。
4. **人工检查每一次阻止——阻止列表就是误报测量结果。** 允许列表回答的是规则 5 的
   问题（它变得安静，是因为那里确实什么都没有，还是因为它看不见？）；如果重放返回
   *零次*阻止，应当怀疑测试工具本身，而不是将其视为一份无问题证明——陷阱 #11
   规定，在触发不足的方向上也应使用同样的检测手段。

**如何处理这个数字。** 如果某个误拦截给出的修复指导错误或无法执行 → 根本不要注册：这种形态正是反身绕过规则 1 要防止产生的制造流程。否则，将拦截列表视为修复列表，修复后重新回放。误报很可能集中出现在**你编写守卫时正在处理的内容**上——那次运行中有一半误报落在钩子开发文件上，因为作者那周正在构建钩子。还要专门扫描拦截列表中的**运维操作**（对钩子目录下文件的编辑、对钩子运行 `bash -n`、守卫自身的 SSOT）：如果一个守卫会阻止自身被移除，就无法从会话内部将其关闭。最接近的已记录案例是 #25，其中守卫拦截了一个**只读的** `git config core.hooksPath` 查询——这正是距离自锁仅一步之遥的同一盲点。一旦守卫已经把你锁在外面，逃生路径见 **#3** 的列表（使用 Edit/Write 工具编辑 `settings.json`，它绝不会触发 `Bash` 匹配器；或者使用不同的 `CLAUDE_CONFIG_DIR` 启动会话）。

关于工作量，避免让这件事读起来像个研究项目：收集一次，再循环一次，实际耗时几分钟。

## 构建顺序（依次执行）

1. **确认它确实会重复发生**，而非假设——否则不要构建。
   如果钩子将**要求执行修复**，而不只是拦截，请在编写任何逻辑之前写出完整的循环契约（键 / 轴 / T / R / V / 预算 / 两个出口），并将 V 作为 `# TERMINATION:` 行放入脚本头部（规则 7）。首先检查你要设门禁的对象是否是一个*操作*；如果是，那么针对该操作的 PreToolUse 守卫会直接消除循环，而不是驯服它。
   无法说出一个在每次 `trigger → remediate → re-check` 循环中严格递减的量？那这个设计不会终止——修复设计，而不是正则表达式。
2. 在 SSOT 目录中编写脚本；执行 `chmod +x`。
3. 使用 shlex 进行词元级匹配来完成**检测**（规则 1），并以现实世界能够回答的事实作为依据，而不是以你自己的呈现方式或命名约定为依据（规则 6）。
   - **首先检查 ShellCheck 是否已经能判定它——然后记录答案，因为下一位作者还会问同一个问题。** ShellCheck 是 shell 反模式检查事实上的标准，因此评审者首先会问：“为什么不直接使用 shellcheck？”于 2026-08-15 使用 **0.11.0** 对 `find . -name x | head -5 || echo "no"` 进行实测——这是一个已证明永远不会触发的后备分支，因为 `||` 绑定到管道的**最后一个**阶段，而 `head` 在输入为空时以 0 退出：**默认配置不报告任何内容，退出码为 0**。`--enable=all` 会启用 **SC2312**（`check-extra-masked-returns`），但它也会对 `cmd | jq . || echo bad` 触发，而在该命令中，最后一个阶段确实可能失败，因此后备分支是有意义的。它不适合作为*门禁*有三个原因——每个原因都具有普适性：
     它**默认关闭**（因此目前没有保护任何人），无法区分无效后备分支和有效后备分支（无差别触发 = 规则 1 所述的误拦截螺旋），而且它自己建议的修复方式是“使用 `|| true` 忽略”，这与本意恰好相反。它检查的也是**文件**，而不是工具调用事件。
     这个答案的一般形式是：标准代码检查器值得**检查一下**，但通常不适合将阻断式门禁**委托给它**，因为代码检查器针对的是咨询性检查的广度，而门禁需要精确度。你的钩子所提供的价值正是这种精确度。已发布的示例：`pipe-fallback-guard`，其精确度来自一小组确实会吞掉上游退出码的末级命令（`head`/`tail`/`wc`/`cat`/`sort`/……），并且刻意排除 `grep`/`jq`/`awk`/`sed`，因为这些命令确实可能失败。
4. 使用包含触发案例和外观相似的正常案例的 **`bash -n` + `test_hook.sh`**（规则 2）——在测试通过前不要注册。应包含带有未展开路径的形态（`cd ~/elsewhere && …`，规则 5）；如果钩子有人为门禁，则包含一个强制拒绝行（模式 B，“让门禁可测试”）；如果钩子要求修复，则包含**修复后的成对测试行**——没有回执时触发，有回执时保持安静（模板位于 `scripts/test_hook.sh`；规则 7——时间点式夹具从结构上无法发现不终止问题）。
   - **为钩子提供 `--selftest` 模式，并使其具备双向测试能力。** 然后让 SessionStart 守卫健康检查（见上文“钩子类型”——其唯一职责就是检查守卫本身）对每个提供自测的已安装钩子调用 `<hook> --selftest`。这是唯一能够自动发现 `bash -n` 和下方步骤 4–7 从结构上都无法发现的故障的检查：钩子已经**退化为永久空操作**。这种故障按其构造方式就是不可见的——一个永不触发的守卫所产生的输出，与无事可报告的会话完全相同，因此它可能持续存在数周。两个夹具是*下限*，而不是目标：一个必须拦截的样本**以及**一个必须放行的样本，这样才能同时发现“停止触发”和“开始误拦截”——只有任一类型都不够。
     **应根据杀死的变异体数量来确定规模，而不是根据夹具数量**，并采用与校准测试套件相同的方式进行校准：故意破坏检测器，并确认 `--selftest` 以非零状态退出。从未见过失败的自测与 `exit 0` 无法区分。
     对已发布的 `compounding-edit-review` 进行实测：其**第一版的两个夹具只杀死了 14 个变异体中的 4 个**——其自身注释中声明为关键的每项行为都完全没有覆盖，其中包括一个使防循环检查短路、但自测仍打印 OK 的变异。现在它会运行 58 个案例。
     真正的约束不是夹具数量，而是**会话启动时的实际耗时**，因为每个会话都要承担这项成本：这 58 个案例的实测耗时为 **~5.3 s**，而双探针存活检查仅需 **~140 ms**。如果为了杀死变异体而使测试超出该预算，应选择**拆分**而不是缩减——在 `--selftest` 中运行廉价、固定规模的存活探针，在构建时通过 `test_hook.sh` 运行完整的回归测试。缩减到变异体杀死线以下，只会换回一个在守卫已经失效时仍能通过的自测。
5. **回放真实命令语料库，并手工检查每次拦截**（规则 9）——这衡量的是误拦截面，而步骤 4 中的夹具表从结构上无法衡量这一点。逐字提取已发布的检测器用于预筛选；在临时 `TMPDIR` 下，将每个候选项连同其自身真实的记录和 `session_id` 一起传给真实钩子。
6. **创建符号链接**到 `~/.claude/hooks/`（规则 3）。
7. 在主 `settings.json` 中**注册**，并收敛各配置文件（规则 4）。
8. 对于 Tier-0/不可逆操作，添加**人工确认放行门禁**（规则 4）。
9. **持久化**：将 SSOT 提交到其私有仓库。可选择添加一行 CLAUDE.md（正文说明*为什么*以及替代方案；钩子负责强制执行）。

## 已知陷阱（在调试误触发的 hook 前请先阅读）

完整目录（症状 → 原因 → 修复方法）：[references/hook_pitfalls.md](references/hook_pitfalls.md)。
主要问题包括：`stdin` 被 `python3 - <<PY` heredoc 消耗（hook 会悄无声息地放行
一切）、awk 分割导致的误拦截（规则 1）、损坏的 hook 污染会话
（规则 2）、Python *注释*中的引号或反引号悄无声息地破坏
`python3 -c "…"` 代码块且不产生语法错误（陷阱 #9——应改用模式 E 中的带引号 heredoc
形式）、静态环境变量逃生通道（规则 4）、多配置文件注册不完整、
提交消息以伪命令文本的形式进入遍历器，导致你自己的修复提交被误拦截，除非豁免 `git` 写入片段
（#7），以及从命令文本中解析出的路径保留了字面量 `~`，导致
防护机制在完全没有任何症状的情况下**开放式失败**（#10——这个问题不能等到
察觉后再处理，因为沉默就是它唯一的迹象）、某个分支读取 hook 自身
被截断的显示字符串（#12），或依据此仓库并未遵循的命名约定进行判断
（#13）——当测试套件只断言退出码时，这两者都不可见（#14）——
仅仅*包含*重定向的命令文本被算作写入（#15），以及
hook **要求的补救措施会重新启用它自身**，从而陷入循环，但自测仍显示为绿色，
因为时间点固定装置在结构上无法发现非终止行为（#16，
规则 7）。

**测试工具是隐藏变量——请使用 `scripts/test_hook.sh`，不要自己临时编写
一个。** 下面每种手工编写测试工具的失败模式，都会产生与正常
通过时*完全相同*的输出，因此看起来像是成功（2026-07-22，在修复一个 Stop
hook 的白名单时，一次遇到了三个）：

1. **错误的事件结构。** Stop hook 读取 `last_assistant_message` /
   `transcript_path`，而不是 `tool_name`/`tool_input`。如果提供 PreToolUse 结构的事件，
   它找不到任何文本 → 以 0 退出 → “没有误拦截！”
2. **JSON 引号。** 单引号内的 `'{\"a\":1}'` 会输出字面量
   反斜杠加引号；`json.loads` 抛出异常，hook 的 `2>/dev/null || exit 0` 将其吞掉，
   所有测试用例都“通过”。
3. **规则合理豁免的测试用例。** 基线字符串使用了
   规则*刻意豁免*的字符串（防护规则会标记形如 `<name> Group` 的新造昵称，
   但会豁免普通短语 `in the group` / `group chat`
   ——而基线行碰巧使用了其中一个）。原本用来证明
   防护规则仍会生效的那一行并未触发防护，而整个测试套件看起来仍是绿色。

**而且，如果 hook 的产物是它输出的消息，退出码就无法对其进行测试。**
阻塞型 hook 的契约主要是退出码，因此可以用 `run` 行覆盖。但如果
hook 的存在目的就是为了*说明*某些内容——例如 PreToolUse 对正确替代方案的说明、
Stop 提醒——它就有第二个输出通道，而退出码完全无法观测该通道：
破坏措辞、反转条件段落、让 heredoc 吞掉某一节，退出码仍会保持为 2，
同时所有测试行都会通过。请添加来自 `scripts/test_hook.sh` 的
`says <label> <event> <pattern> <yes|no>` 行，**使用两个固定装置断言正反两种情况**
（对于目标输入应存在，对于会被跳过的相似输入应不存在）——单独的 `want=no`
会在 hook 完全不输出任何内容时空泛地通过，因此只有与证明 hook 确实会输出内容的
`want=yes` 行配合时才有意义。请匹配**固定字符串**，而不是正则表达式：
值得断言的短语通常包含方括号，而在 BRE 中，`[skill]` 是一个字符类，
会匹配任何包含 s、k、i 或 l 的文本。然后**通过变异来证明这些测试行确实能够失败**：
复制 hook，注入每一行声称能够捕获的确切缺陷，并确认该行变红。在你亲眼看到
测试套件因正确原因失败之前，一个绿色测试套件所携带的信息量为零——曾有两个真实缺陷
在一个完全绿色的 24 用例测试套件中存活下来，因为每一行都只检查退出码
（陷阱 #14）。

常见模式是：**所有用例结果一致是一种坏味道，而不是可以放行的绿灯。** `test_hook.sh`
会从结构上捕获上述第 1 和第 2 种情况——它要求每个 `run` 行都显式断言 `expected-exit`
（而不是“它是否打印了某些内容”），并强制将触发行与外观相似的健康行放在一起，
因此，返回 0 的触发行会明显失败，而不会混在其他结果中。它
**无法**捕获第 3 种情况：某一行的内容是否意外落入豁免范围，取决于你写了什么，
而任何测试工具都无法知道你的规则意图。只有依靠这样的习惯才能捕获这种情况——先断言一个已知有效的触发用例，
如果它没有触发，应先怀疑该行，而不是怀疑钩子。
