# Claude Code Hooks

Claude Code 会在工具调用边界触发 **hooks**。hook 是一个 shell 命令，它通过 stdin 接收 JSON 事件；对于阻塞型 hook，它会通过自己的**退出码**决定是否允许工具调用继续执行。这是唯一能够从*结构上*阻止某种行为的机制——CLAUDE.md 中的文字规则只是一项建议，完成任务的驱动力可能会越过它；而 hook 是一道墙。

## 什么时候应该使用 hook（以及什么时候不应该）

当**某条规则即使已经明确写下，却仍然被反复违反**时，就应编写 hook。判断信号是：你添加了文字规则，表述也很清楚，但这种行为之后仍再次发生——因为在采取行动的那一刻，注意力 100% 集中在“把事情做完”上，提醒便失去了作用。这种重复发生就是将规则从文字（建议性）转为 hook（强制执行）的信号。治理经验法则：*Tier-0 不可逆操作 + 只有文字规则、没有 hook → 应该使用 hook。*
（这里的 **Tier-0** = 其损害无法在当前会话内撤销的操作：
销毁未提交的工作、将密钥推送到远程仓库、删除文件、向外发布内容。判断标准是可逆性，而不是严重程度。）

在以下情况下，**不要**贸然使用 hook：规则实际上从未被再次违反过（不要为假想中的错误预先构建防护措施——这只会产生成本，却没有经过验证的收益），或者这条“规则”属于没有机械化特征可供识别的判断问题（hook 只能匹配 token/模式；它无法判断某项设计是否优秀）。

## Hook 类型以及退出码的含义

| 类型 | 触发时机 | 退出码 0 | 退出码 2 | 其他 |
|---|---|---|---|---|
| **PreToolUse** | 工具运行之前 | 允许 | **阻止**调用（stderr → 作为指导信息展示给模型） | 任何其他退出码 =“非阻塞错误”→ **调用继续执行**——但仅限于 stdout 不包含有效 JSON 时。Claude Code 会在**每个**退出码下读取 JSON 输出，有效的 JSON 会完全覆盖退出码的作用。这里的骨架不会向 stdout 打印任何内容，因此其失败时放行的逻辑成立；一旦添加 `permissionDecision` 载荷，退出码便不再决定结果 |
| **PostToolUse** | 工具运行之后 | 保持静默，**除非它在 stdout 上打印 `hookSpecificOutput` JSON——上下文注入正是以这种方式实现的，并且发生在退出码为 0 时** | 向模型提供反馈（无法撤销工具运行） | — |
| **SessionStart** | 会话开始时 | 继续 | **无法阻止**——stderr 会向用户显示 hook 错误通知，Claude 永远看不到它，会话仍会照常开始 | **无论如何都应以 0 退出**：并不是因为非零退出码能够阻止会话（它不能），而是因为任何非零值都会在每次会话开始时，将一条 `<hook> hook error` 放进用户的会话记录中。接受一个用于说明*会话如何启动*的 `matcher`——`startup`、`resume`、`clear`、`compact`、`fork` |
| **Stop**（+ `SubagentStop`） | 模型即将完成响应时 | 允许其停止 | **阻止停止**——强制模型继续执行（stderr → 作为原因反馈给模型） | 循环安全：hook 会检查 `stop_hook_active`（这是必要条件，但**并不**充分——参见规则 7）。运行框架的连续阻塞上限（默认为 8）**并不是**通用的兜底机制——只要某次继续执行期间运行了工具，它的计数器就会重置，因此对于需要调用工具来补救的 hook（大多数 hook 都属于这种情况，#27），永远不会触及该上限。请自行设置边界。某个事件的所有 Stop hook 都会**并行**运行——一轮阻塞可以携带多个 hook 的反馈 |

- **PreToolUse** 是阻止*工具调用*的主力——此表中的四种类型是本文件所讲解的类型，并不是所有可阻止事件的完整集合；**官方** hooks 参考文档（docs.claude.com / code.claude.com，而不是此资料包中的
  `references/` 文件——那些文件只涵盖上述四种类型）目前列出了更多可阻止事件，包括 `UserPromptSubmit`、`PreCompact`、
  `TeammateIdle`，以及任务和配置事件。如果需要设卡的对象不是工具调用，请先查阅这些文档，不要强行把它归到 PreToolUse。
  `matcher` 用于选择工具（`Bash`、`Agent`、`WebFetch` 等）——**而具体如何匹配取决于你使用的字符**：如果 matcher 只包含字母、数字、`_`、`-`、空格、`,` 和 `|`，则会按**精确字符串**进行比较（或视为由 `|`/`,` 分隔的精确字符串列表）；包含其他任何字符时，则会被视为**未锚定的 JavaScript 正则表达式**。这两种规则都可能悄无声息地带来问题——`Edit.*` 也会匹配 `NotebookEdit`（应使用 `^Edit$` 将其锚定），而 `mcp__memory` 则**什么也匹配不到**，因为它完全由精确匹配字符组成，而没有任何工具恰好名为该字符串（你需要的是 `mcp__memory__.*`）。匹配区分大小写。退出码 2 会执行阻止操作，而 hook 的 **stderr** 会成为模型看到的消息——因此应在那里说明*原因*和*正确的替代方案*，而不只是写“已阻止”。
- **PostToolUse** 无法撤销操作，但它可以**注入权威上下文**，使后续的幻觉无法成立（例如，在提交后重新读取真实的 git HEAD 并呈现出来——面对注入的事实，模型无法继续“相信自己已经提交”）。
- **SessionStart** 用于对**防护机制本身进行健康检查**——正常时保持静默，损坏时发出警告，并始终以 0 退出。请注意其中的*原因*：并不是因为非零退出码会阻止会话（它做不到），而是因为在有人修复问题之前，它会在每次会话启动时都打印 hook 错误通知——如果一项检查每次启动都谎报军情，人们很快就会习惯直接忽略它。
- **`set -euo pipefail` 与 `set -uo pipefail`——应根据约定进行选择，并且要知道有两种方式可以维持始终以 0 退出的约定。** 可能执行阻止操作的 hook（PreToolUse）需要 `-e`：脚本因意外故障而中止是可以接受的，因为调用方会将非 0/2 的退出码视为“继续”。对于约定为**始终以 0 退出**的 hook（PostToolUse 注入器、SessionStart 检查），有两种合理形式：(a) **移除 `-e`**，并使用 `||` 防护每一条有风险的命令——启用 `-e` 时，只要某个 `grep` 合理地未找到任何内容，就会让 hook 中途终止，而 CLI 只会显示一条没有上下文的 `Failed with non-blocking status code`（陷阱 #8，模式 E 的形式）；或者 (b) **保留 `-e` 并添加 `trap 'exit 0' ERR`**，使任何故障仍会被转换为退出码 0，同时让 `-e` 继续保护管道流程（`git-commit-headcheck` 的生产环境形式，模式 D）。两者都正确；不能采用的是单独使用 `-e`，既不设置 trap，也不添加 `||` 防护。经验法则：**对于作出决定的 hook，使用 `-e`；对于报告情况的 hook，移除 `-e` 或用 trap 处理它**（陷阱 #8）。
- **Stop 是一个异类，也是最常被误用的类型**：它是*唯一*能对模型**自身刚刚生成的内容**（即模型自己的回复文本）作出反应的 hook 类型。其他所有 hook 类型——包括听起来似乎适合审查“说了什么”的 `UserPromptSubmit`——都只能看到**用户的**输入；从结构上说，它无法看到模型自己在*当前轮次*中的输出（这一说法仍然成立——这依旧是应将此类规则交给 Stop 的正确理由）。然而，这项保证并不能证明 `.prompt` 字段始终来源于键盘输入：后台任务通知自身的报告文本也可能填入该字段，而 stdin JSON 中没有任何内容可以标明二者的差异——#30。像“模型不得为尚未验证的事物编造简称”这样的规则应放在 Stop 上；如果改为放在 `UserPromptSubmit` 上，它将会：(a) 一次也无法捕获其原本要处理的内容，因为该文本根本不会流经此事件；并且 (b) 只要用户自己输入的无关内容碰巧包含触发模式，就会错误地阻止用户输入。这是类别错误，而不是调优问题——在错误的事件上，无论如何细化正则表达式都无法修复它。完整约定（`last_assistant_message` 与 `transcript_path`、防循环检查）见 [references/hook_patterns.md](references/hook_patterns.md) 中的模式 E。
- **Stop 有两个阻止通道，并且具有相同的循环保护机制——应根据意图进行选择，并让第一次（也是唯一一次）阻止承载全部信息。** `decision:
  "block"` + `reason`，或直接以退出码 2 退出并写入 stderr，会显示为 hook *错误*——适用于硬性关卡（“绝不能让此内容保留下来”）。`hookSpecificOutput.additionalContext`
  会显示为中性的“Stop hook 反馈”，不会产生错误通知——适用于模型应当权衡的指导和提醒，而不是硬性关卡。两者都会计入上表所述的同一连续阻止次数上限，因此二者的区别在于语气，而不是安全性。这对消息设计意味着：被阻止后的重试轮次（`stop_hook_active: true`）会被放行，**无论其中还剩下多少违规内容**——因此 Stop 防护只有**一次**提供有效信息的机会。（只有当补救方式是“重写回复”时，该上限才会强化这一点；如果补救涉及工具调用，计数器会重置，该上限永远不会生效——#27。无论哪种情况，“只有一次机会”的结论都成立，因为它依赖的是锁存机制，而不是上限。）应在这一次阻止中报告*所有*发现（只输出第一项问题的防护机制将永久丢失其余问题——陷阱 #17），并将消息写成一份脱困手册，明确指出可接受的具体修复方式，而不是只给出判决——模型要么在一轮内收敛，要么就会因猜测而耗尽上限。v2.1.145+ 输入中的 `background_tasks` / `session_crons` 允许阻止型 hook 区分“会话已结束”与“会话只是暂停以等待后台工作”——阻止暂停状态会迫使系统进行毫无意义的后续处理，并浪费同一个上限。

完整的可运行骨架：[references/hook_patterns.md](references/hook_patterns.md)。

## 骨架（PreToolUse Bash 防护钩子）

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS= read -rd '' INPUT || true                 # builtin; NOT $(cat) — see below
# 0-fork fast path: a builtin `case` on the raw JSON, BEFORE paying for python3.
# Your guard runs on EVERY matching tool call, so the irrelevant path is the one
# that has to be cheap. Keep this filter BROADER than what you actually block and
# never flag-level — it answers "is this even about X", nothing finer (#22).
case "$INPUT" in *TRIGGER*) ;; *) exit 0 ;; esac
TOOL=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_name',''))" 2>/dev/null||echo "")
[ "$TOOL" != "Bash" ] && exit 0                # only guard the tool you mean to
CMD=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('tool_input',{}).get('command',''))" 2>/dev/null||echo "")
[ -z "$CMD" ] && exit 0
printf '%s' "$CMD" | grep -qw 'TRIGGER' || exit 0   # precise relevance check
# ... precise detection here ...
if <command actually does the banned thing>; then
  echo "BLOCKED: ... WHY ... USE INSTEAD: ..." >&2   # stderr = the guidance shown
  exit 2
fi
exit 0
```

**为什么前两行并非风格选择。** `INPUT=$(cat)` 加上每个
`printf … | python3 -c …`，会在此钩子匹配的**每一次调用中产生进程派生开销，包括
那些它根本无需处理的调用**。约 13 个匹配 Bash 的钩子组成的集合 × 并行
会话 × 亚秒级工具调用频率，使纯防护钩子开销持续达到每秒 40–200 次进程派生，
并让 Gatekeeper 在全天 CPU 排名中高居榜首，却完全不存在任何失控进程——钩子集合本身没有问题；
问题在于*无关路径*的单次调用成本
（#22，其中包含逐个防护钩子的转换方法及其测得的最低开销）。

在把 `case` 行复制到其他任何地方之前，请注意三个事项——第一个事项决定了它究竟是
快速路径还是绕过漏洞：

- **粗粒度过滤器必须覆盖你所阻止内容的超集，而原始子字符串测试
  并不满足这一点。** `TRIG''GER -x` 会运行 `TRIGGER`——bash 会在
  执行前拼接并移除引号——但原始事件文本不包含 `TRIGGER` 子字符串，因此仅使用
  `case "$INPUT" in *TRIGGER*)` 会以 0 退出，防护钩子永远无法检查它。**实测结果**：
  将这一行原样放入随附的 Pattern A 后，`TRIG''GER -x` 会从
  退出码 2 变为退出码 0，形成完全绕过——与此同时，`scripts/test_hook.sh` 仍会报告
  21 pass / 0 fail，因为没有任何测试行包含拼接后的触发词。Pattern A 已经
  包含修复方案及其原因（“去拼接——移除引号和反斜杠——然后再次检查；一次
  假阴性就意味着完全绕过”）；放在该去拼接操作*之前*的粗粒度过滤器会使后者无法执行。
  有两种安全形式，按推荐顺序排列：**针对拼接操作无法影响的内容进行过滤**——JSON 键或工具名称
  （`case "$INPUT" in *'"tool_name":"Bash"'*)`），因为引号拼接发生在
  *命令*文本中，无法改写事件本身的结构；或者**在过滤器内部
  先去拼接再进行测试**（从输入副本中移除 `"`、`'` 和 `\`，然后匹配）。
  优先选择第一种：它不需要复杂的转义操作，而如果一个过滤器连自身的引号都必须确保正确，
  就可能在出错时毫无察觉。上面的骨架按原样使用是安全的，
  但这仅仅是因为它自身的检测同样只是简单的单词匹配；一旦过滤器下方的防护逻辑
  比过滤器更智能，最终起决定作用的就是过滤器。

- **这个骨架对无关输入采用故障开放策略**（`grep -qw … || exit 0`），因此在它前面加一个粗粒度过滤器只会改变成本，而不会改变语义。**故障关闭型守卫则不同**：一个简单的子字符串过滤器会悄无声息地将其契约从阻止未知输入变成允许未知输入（实测——`'not json'` 直接通过了该修复的第一版），而仅靠一个 `*tool_name*` 标记又会从另一侧重新打开同一个漏洞。在为一个本应阻止格式错误输入的守卫设计快速路径之前，先阅读 #22 的门控要求。
- **脚本之上还有一个成本更低的层。** Hook 处理程序可在注册信息中携带一个 `if` 字段——使用 `"Bash(git *)"` 这样的权限规则语法——当规则不匹配时，Hook 命令**根本不会运行**：零次 fork，因为没有任何进程。按照设计，它是尽力而为的（文档说明，当 Bash 命令无法解析时，它会故障*开放*，仍然运行你的 Hook），因此应将其视为成本优化，**绝不能将其作为门控**——最终仍由脚本内检查作出决定。三个容易踩坑之处：它只能包含一条规则（不支持 `&&`/`||`），它只会在工具事件上求值，而且在非工具事件上设置了 `if` 的 Hook **永远不会运行**。

## 区分正常工作守卫与污染会话守卫的规则

这些不是风格偏好——每一条都对应一个我们已经发布并追溯定位的具体故障。

### 1. 始终使用 shlex 在**词元层级进行匹配**，绝不要用 awk 拆分原始字符串

守卫**误拦健康命令比漏掉命令更糟**——一个迫使人们绕过的守卫，会让人形成下意识绕过它的习惯，最终它将毫无保护作用（核心原则：*误杀健康输入比漏报更糟*）。误拦反复出现的根本原因，就是直接在原始命令字符串上进行匹配。


- **错误做法**：使用 `awk '{gsub(/&&|\|\||;|\|/,"\n")}'` 拆分命令段——awk 不理解 shell 引号，因此 `grep -E "a|TRIGGER|b"` 会在带引号正则表达式*内部*的 `|` 处被拆分，`TRIGGER` 变成一个虚假的命令，守卫因而阻止一次普通的 grep。（发布于 2026-07-21；该守卫第一次真正投入使用，就误拦了我自己的 grep。）
- **正确做法**：使用 **`shlex.shlex` 类**对整个命令进行词元化，而不是使用 `shlex.split()` 函数——`split()` 只有在 `| ; & < >` 两侧由空格分隔时才会将它们视为分隔符，因此 `ls|TRIGGER x` 会被词元化为 `['ls|TRIGGER', 'x']`，你的命令位置检查根本看不到 `TRIGGER`（实测；使用 `punctuation_chars=True` 的类会得到 `['ls', '|', 'TRIGGER', 'x']`）。应逐字复制一个已经发布的遍历器，而不是随手写一个单行版本——但**要复制能够通过 `scripts/test_hook.sh` 的那个版本**，也就是 **Pattern A 的版本**。[遍历器章节](references/hook_patterns.md#the-shlex-command-position-walker)使用的是一个*紧凑*版本，而且其中明确说明了这一点：它省略了各包装器的带值标志表，因此会漏掉借助**带值标志包装器**传入的目标——实测，对于 `timeout 5 TRIGGER`、`sudo -u root TRIGGER` 和 `nice -n 10 TRIGGER`，它都会返回“不在命令位置”，而 Pattern A 的版本能够捕获这三者。（裸 `sudo TRIGGER` 在两个版本中都没有问题——紧凑表不知道该跳过的是包装器*自身*需要参数的标志。）发布的测试工具中只包含了其中一种形式，因此你实际看到的运行结果是：紧凑版本在 `wrapper-timeout` 上为 **20 pass / 1 fail**，而 Pattern A 为 21/0；另外两种失败没有显现，因为没有测试行覆盖它们。带引号的 `"a|TRIGGER|b"` 会保持为**一个词元**，所以正则表达式参数绝不会被误认为命令。然后检查目标是否位于**命令位置**（token[0]，或紧跟在 `;`/`&&`/`||`/`|` 分隔符之后，同时跳过 `VAR=val` 环境变量赋值前缀）。命令位置遍历器见 [references/hook_patterns.md](references/hook_patterns.md)。
- 推论：`echo "…TRIGGER…"`、`grep TRIGGER`、`# TRIGGER`、`man TRIGGER` 都必须放行。你的测试集必须包含这些“提及但不执行”的情况。
- **推论——在 `git` 写操作命令段到达遍历器之前将其豁免。** 提交消息是任意数据，而整段消息文本会以伪命令文本的形式进入命令位置遍历——对于 `git commit -F - <<EOF`，如果正文引用了 `foo|TRIGGER`，`TRIGGER` 就会落在命令位置，守卫因此阻止自己的修复提交（陷阱 #7 正是如此，而且已经发布）。任何检查命令字符串的 Bash 守卫都必须跳过头部为 `git` + `commit`/`rebase`/`tag`/`am`/`cherry-pick` 的命令段——并且必须在整个命令层级、任何按行拆分之前完成（Pattern A 展示了该顺序；生产版本是 `lib-git-commit-detect` 的相邻性检查）。
- **推论——遍历器采用两阶段处理是有原因的。** `whitespace_split=True` 会把换行符当作普通空白，因此多行代码块（`cd /x\ngit add\nTRIGGER -y`）会被折叠成一个以 `cd` 开头的命令段，触发器永远不会出现在命令位置——在真实记录上重放时，触发率为 0（陷阱 #11）。应先以 **shell 感知**方式拆分为行（遵循引号状态和反斜杠续行，因此带引号的多行字符串不会被拆散），然后对每一行进行 shlex 遍历——Pattern A 和遍历器章节都提供了该拆分器（`split_shell_lines`，已在 qlmanage-guard 的生产环境中验证）。即使它也无法解析 heredoc 正文（那不是引号语法）；何时接受这一残余风险，由 #11 决定。
- **但 shlex 并非万能，而且你检测的*内容*会影响故障开放是否安全。** `shlex.split()` 本身在遇到未配对引号时会抛出 `ValueError`——带有 `#` 或未闭合引号的多行 `git commit -m "…` 消息就是典型触发条件。随后的 `except ValueError: cmd.split()` 回退会选择*放行*；当你检测的是**禁用修饰符**时，这种行为是正确的（它是否携带 `--no-verify`？——漏掉它符合安全方向，即规则 1 的方向），但当你检测的是**该命令本身是否就是目标命令**时，这种行为很危险（这是 `git commit` 吗？——此处出现 ValueError，意味着守卫永远识别不出该提交，于是悄无声息地不触发；一个真实的跨域提交正是以这种方式在没有确认对话框的情况下被发布）。对于*这是不是目标命令*这一判断，应优先使用范围明确的**正则表达式**（将 `git` 和 `commit` 作为独立单词，两者之间允许存在任意标志词元），它不会受到多行引号破坏的影响；shlex 遍历器应保留用于*命令位置／修饰符*检查，因为在这些检查中，故障开放才是安全方向。（边界是：当谓词为“这究竟是不是某个特定的常见命令”时使用正则表达式——例如 `git commit`、`git push`——因为正是它自身的消息／参数会破坏词元化；当谓词为“某个*禁用的*命令或修饰符是否位于命令位置”时使用遍历器——此时禁用项很少见，而 ValueError 导致的故障开放符合安全方向，即规则 1 的方向。）

### 2. 在注册前，先用 **bash -n + 真实 JSON 事件进行端到端测试**

**损坏或逻辑错误的 PreToolUse hook 会污染整个会话**——
之后的每一次 Bash 调用都会被截断 / 重复 / 误判为失败 / 看起来像是幻觉执行，
而你会把问题归咎于“环境”，实际上罪魁祸首是你刚安装的 hook。
（2026-07-05：一次编辑破坏了 `[^;&|]` 正则表达式，`;&` 变成了
bash case 贯穿执行标记，污染了半个会话，直到 `bash -n` 才发现问题。）
“部署时测试通过”还不够——文件可能会在之后的编辑中损坏。

在注册任何 hook 之前执行以下门禁检查：
```bash
bash -n hook.sh                                # syntax
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<trigger case>"}}'    | ./hook.sh; echo "exit=$?"  # want 2
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"<healthy lookalike>"}}'| ./hook.sh; echo "exit=$?"  # want 0
```
将测试工具一并提供：[scripts/test_hook.sh](scripts/test_hook.sh) 会运行包含触发和放行用例的完整表格。
**自我拦截陷阱：**一旦 hook 在会话中生效，你就不能通过在自己的 Bash
命令中放入触发字符串来测试它——已生效的 hook 会拦截你的测试命令。请将用例放入
**脚本文件**，然后运行 `bash test_hook.sh`；外层命令不包含触发字符串，
因此不会被自我拦截。

**一旦 hook 已经造成过一次真实事故（误拦截或静默漏检），
独自重新阅读代码是不够的**——某个 Stop-hook 防护逻辑在同一天重写时，
作者为修复第一个 bug 又两次将其破坏（Python 注释中的一个引号，重新阅读时无法察觉，
只有运行实际失败的 JSON 用例才暴露出来）。此时应升级为多视角智能体团队审查，
其中每一项发现都必须通过对实际运行的脚本*执行*真实 payload 来复现，
而不能只是阅读代码后表示认同——这就是通用的反向审查方法论
（skill-creator 的 `skill-development-methodology` 参考资料，第 6 阶段）在 hook
而非 skill 上的应用。在一次这样的审查中，3 个视角（匹配逻辑 / shell 嵌入安全性 /
事件契约稳健性）发现了 13 个经过确认且独立复现的 bug，以及 1 项其所引用证据
实际上是幻觉文档引文的发现——之所以能识破，只是因为验证者被要求使用 curl 获取原始来源，
并用 grep 搜索精确字符串，而不是相信引文。

### 3. 使用 SSOT + 符号链接，避免重新安装时悄无声息地解除防护

真实脚本位于受版本控制的目录中，并通过**符号链接**放入 Claude 读取的 hooks 目录：
```
~/scripts/claude-hooks/<name>.sh      # SSOT (this setup: a private git repo)
~/.claude/hooks/<name>.sh             # symlink → SSOT

# install / recover:
ln -s ~/scripts/claude-hooks/<name>.sh ~/.claude/hooks/<name>.sh
```
重新安装 `~/.claude` 会清空 hooks 目录；符号链接的目标仍然存在，
只需执行一次 `ln -s` 即可恢复。悬空的符号链接会在**完全没有信号**的情况下
禁用 Tier-0 防护——这正是需要 SessionStart 健康检查的原因（规则 4；可运行的
骨架：参见 [references/hook_patterns.md](references/hook_patterns.md) 中的模式 C）。

### 4. 注册按配置文件分别进行——收敛所有配置文件，并通过人工关卡放行

- 如果*当前配置文件的* `settings.json` 没有调用 `~/.claude/hooks/` 中的钩子，那么该钩子**什么也保护不了**。在所有配置文件完成收敛之前，多配置文件用户一直处于零防护状态。请在**主**配置文件的设置中注册（本设置中为 `~/.claude/settings.json`；[references/hook_patterns.md](references/hook_patterns.md) 的 Registration 一节给出了确切的 jsonc 结构）——PreToolUse → 匹配器 `Bash` → 你的钩子——然后收敛其余配置文件（本设置使用 `sync-profile-settings.py --all`，由 `claude-switch-models-setup` skill 负责）。SessionStart 健康检查会在每个配置文件中 grep Tier-0 防护，以发现配置漂移。设置修改会被 CLI 的文件监视器捕获（官方钩子文档），因此注册无需重启即可生效——可以通过观察防护在安全探测上触发来确认，也可以在下一次会话的健康检查行中确认。
- **如果防护需要一个释放阀，请将其设置为*人工*关卡，而不是环境变量。**
  静态的 `GUARD_OK=1` 逃生口根本算不上关卡——模型可以自行设置该环境变量。请使用原生 macOS 对话框（`osascript`——模型无法点击）；拒绝/取消/超时 = 强制否决；将每次提示/绕过都记录到审计文件中。模式见 [references/hook_patterns.md](references/hook_patterns.md)。
  - ⚠️ **`/dev/tty` 并不是第二通道——文档明确说明钩子无法打开它。**
    本文件过去曾规定，除对话框外，还要在 `/dev/tty` 上输入 `YES`。官方参考文档对此有明确说明：钩子“在自己的会话中运行，**没有控制终端**”，而且“钩子进程及其任何子进程都**无法打开 `/dev/tty`**”（`terminalSequence` 是文档中用于替代向其写入操作的方案）。因此，以这种方式构建的“双通道”关卡实际上只是一个通道加上一段永远无法运行的代码；而在没有 GUI 会话的机器上，任何人都永远无法批准该关卡。这也与本地观察结果一致，不过请仔细理解其适用边界：在某个设置的共享审计日志中——共 1,801 条记录，由多个防护写入，其中三个实现了 tty 通道——**有 360 行带有通道标签（236 次对话框确认，124 次拒绝或超时），但没有任何一行以任何方式提及 tty 通道。** 这意味着 tty 分支从未被*进入*；无论如何，这正是你在 macOS 上可以预期的结果，因为对话框会先得到响应并通过短路逻辑跳过它。因此，该日志表明这里没有任何内容曾依赖 tty；真正证明 tty 完全无法工作的，是文档，而不是这次测量。保留对话框；如果你需要一个非 macOS 关卡，就需要一种本文件尚未给出经验证答案的通道。
  - ⚠️ **存续时间超过钩子超时限制的人工关卡会以开放方式失败。** 钩子 `command` 的超时时间默认为 600s（`UserPromptSubmit` 上为 30s），而超时的钩子**不会阻止工具调用**——因此，无人响应的对话框不会变成“否决”，反而会变成允许。请将等待时间限制在远低于超时时间的范围内，并在运行框架替你作出决定之前，自行让无响应解析为阻止。
  - 文档还提供了一个 UI 内通道——PreToolUse `hookSpecificOutput` `permissionDecision: "ask"`，它会通过 Claude Code 自身的界面发出提示。这个通道值得了解，但这里**尚未验证它在 `bypassPermissions` / 自动接受模式下的行为**，而这恰恰是 Tier-0 关卡必须能够抵御的模式；之所以规定使用对话框，是因为它不依赖权限模式。
  - **在 Tier-0 以下、允许模型可自行处理的逃生方式时，应让它成为正确用法，而不是绕过标志。** 上述规则对于 Tier-0 是绝对的，在这里也不会放宽——这里讨论的是未达到 Tier-0 标准的正确性防护；对于检测器无法区分的合法情况，它们仍然需要提供一种出路。问题在于，你要把这条出路设计成*什么*。`SKIP=1` / `--force` 这样的环境变量逃生方式，培养的正是规则 1 所警告的条件反射；在截止期限压力下，它与绕过没有区别。应优先选择一种**本来就希望他们采取的做法**作为逃生方式，这样使用它会改进命令，而不是解除防护：只要命令中提到 `pipefail` / `PIPESTATUS` / `pipestatus`，`pipe-fallback-guard` 就会退出 0，因为写下其中任意一项的作者已经证明自己理解管道退出码——防护已经没有什么可教他们的了。应采用以下检验标准：*如果有人使用了我的逃生口，最终得到的命令是变得更好，还是仅仅解除了阻止？* 如果诚实的答案是“仅仅解除了阻止”，那你拥有的只是一个名字更好听的绕过标志。对于 Tier-0 情况，还有一个对应原则，此时覆盖机制仅用于测试关卡：**逃生口只能让关卡变得更严格**——参见 [references/hook_patterns.md](references/hook_patterns.md) 中关于 `GIT_GUARD_TEST` 的讨论。

### 5. 确定失败的**方向**，并专门测试*该方向*——而不只是测试顺利路径

规则 1 对*检测调优*错误进行了排序：假设防护机制已经运行，那么误拦截一个
正常命令要好过漏掉一个罕见的有害命令，因为一个需要人们绕过的防护机制
最终会被下意识地绕过。**本规则讨论的是另一个维度——防护机制
根本没有运行**——因此，这里并没有颠倒“哪种情况更糟”的判断；
这两种排序并不相交。调优疏漏只会让你漏掉一个案例；而这种失败会让你在
所有具有该形态的输入上悄无声息地失去整个防护机制。

失败情形是：防护机制**无法获得它据以判断的对象**——解析抛出异常、路径无法
解析、依赖缺失、子进程超时——而那个用于防止钩子崩溃的
`2>/dev/null || true`，却悄无声息地将*“我无法检查”*
转换为*“没有需要报告的内容”*。钩子以 0 退出。**该输出与真正通过
完全相同**，这正是此类问题能够持续数周而不被发现的原因。

因此，在钩子*获取*某些内容的每一个位置（解析命令、读取
暂存文件、查询服务），都要明确决定：**如果返回空值，这意味着
允许还是阻止？**——并把答案写在相应分支旁。对于*修饰条件*检查，
失败时放行通常是正确的（它是否带有 `--no-verify`？漏掉它只会让你
漏掉一个案例）。对于*这到底是不是目标对象*的检查，失败时阻止
通常才是正确的（这是跨域提交吗？空答案意味着防护机制根本没有触发）。

**然后测试这个方向，而不是顺利路径**：有意向它提供一个无法解析的路径或
无法解析的命令，并断言它仍然会执行你所决定的行为。如果测试套件中的
每一行都只是*因为钩子悄无声息地放行了一切*而通过，那么它与一个真正
通过的测试套件无法区分。

**请仔细解读这些结果——对于不同类别的防护机制，相同输入的正确答案
恰好相反。**以 `cd ~/no-such-dir && TRIGGER` 为例：

| 防护机制类别 | 判断依据 | 正确退出码 | 原因 |
|---|---|---|---|
| **词元匹配器**（这是被禁止的命令形式吗？） | 仅命令文本 | **2，阻止** | `TRIGGER` 就明明白白地出现在文本中；无法解析的 `cd` 并不会让它不再是触发项，而且如果防护机制在这里沉默，那么在 `cd ~/real-dir && TRIGGER` 上它也会沉默 |
| **状态推导器**（仓库的暂存集合是否跨越多个域？） | 从磁盘读取的状态 | **0，允许** | `cd` 失败，`&&` 短路，提交根本不会发生——没有任何需要防护的操作 |
| **终止状态读取器**（补救措施是否已经执行？） | 回执/计数器文件（规则 7） | **0，允许**——*当状态文件本身就是终止条件时* | 无法读取回执意味着钩子无法知道自己是否已经触发；此处失败时阻止会造成永久阻塞，既无法进行补救，也没有任何人类可见的原因——这*就是*循环，而且它是唯一一种比漏掉案例更糟的失败。**反转的子情形——复制此行前请先阅读：**当状态只是叠加在独立谓词之上的**预算**时（完成相应工作仍然可以解除阻止），无法读取时允许会**悄无声息地禁用整个钩子**——只需一个不可写目录，就会让它对所有输入永远保持沉默，而这是最糟糕的失败形态。在这种情况下，应退回到*引入预算之前的行为*（继续求值该谓词），而不是保持沉默。**用一个问题区分两者：如果状态消失了，补救是否仍然可行？**否 → 回执情形，允许。是 → 预算情形，继续检查。这里给出推导完毕的答案，免得所有人都要重新推导：规则 7 的机制 2（回执）**以及**机制 3（每会话计数器）都属于**回执情形 → 允许**——机制 3 被刻意设计为无法感知 R 是否已经发生，因此它的计数器是唯一出口，禁用该计数器会让当前轮次陷入困境。预算情形则是将计数器叠加在一个用户仍可独立满足的谓词之上 |

因此，在编写测试行*之前*，先确定你的钩子属于哪一类；而测试框架的
`unresolvable path` 模板行预期结果为 **2**，因为该模板针对的是
令牌匹配器类。把这一点弄反，会让正确的防护逻辑被信心十足地判定为 FAIL。对于状态推导型防护逻辑，你要寻找的失败是：**命令确实会
运行，而防护逻辑却没有发现它**——未闭合的引号会导致令牌化抛出异常，
回退逻辑随后放行，于是一次真正的跨域提交在没有任何对话框提示的情况下完成（规则 1 中的
ValueError 说明）。对于每一条被放行的测试行，都要问：*这条命令实际上会完成那件事吗？*
如果不会，那么放行就是正确的。

对一个真实的状态推导型防护逻辑运行这一精确探针时，第一轮出现了两次放行：
一次是正确的（即上面的短路情况），另一次则是真正的
失败开放。**探针负责发现问题；你仍然必须对它发现的结果进行分类**——
这就是为什么上面的类别表要放在测试行之前。

真实案例（2026-07-22）：一个作用域防护逻辑通过 `git -C "$REPO_DIR"`
读取暂存文件，其中 `REPO_DIR` 是从**命令文本**中解析出来的——因此，`cd ~/repo && git commit`
传给它的是字面值 `~/repo`，`git -C` 执行失败，暂存文件列表返回为空，而防护逻辑
得出结论：“没有跨域文件，放行。”所有跨仓库提交都在没有防护的情况下完成，
而且一切看起来始终正常。问题剖析及共享库带来的变体：陷阱 #10。

该解析器还有第二种失败方向，而且更为棘手。一旦你
添加回退逻辑来阻止它失败开放，该回退逻辑就会因为一种原因而正确，
又因为另一种原因而错误——但两者打印出的内容完全相同。`git push`（没有
显式目标）合理地回退到事件的 `cwd`；`git -C "$R" push`
*指定了*一个钩子无法解析的目标，却回退到同一个 `cwd`，然后
针对另一个仓库信心十足地显示 ✅。这两种情况的渲染结果
逐字节完全相同（经测量，MD5 相同），因此无论钩子还是读者都无法
区分诚实的判定与绑定错误的判定。**回退值必须携带选择它的原因**，
而且只有“没有显式目标”才有资格得出判定。完整的问题剖析、混淆代理视角，
以及为什么使用字面路径的固件永远发现不了它：陷阱 #28。

### 6. 根据现实世界能够回答的事实来判断——绝不要根据你自己的渲染结果，也不要根据命名习惯

规则 1 和规则 5 讨论的是*如何*匹配以及失败时*偏向哪一边*。本规则讨论的是
**你所匹配的内容来自哪里**，而它有两种都会悄无声息发生的失败形态：

- **绝不要根据为人类格式化的字符串进行分支判断。** 如果钩子构建了一份
  报告——经过排序、拼接、截断为前 N 项，并带有 `(+M more)` 尾部——然后
  再将自己的决策与该报告进行模式匹配，那么这个分支就会继承
  渲染过程造成的信息损失。超过截断点的项目对它而言根本不存在，因此该
  分支在每个小型固件上都能正常工作，却恰恰会在它原本要处理的大型
  会话中停止触发。应在独立通道上发出机器可读的事实（单独一行、未经截断的
  `KINDS:a,b,c`），并匹配*该内容*。渲染结果是输出，不是
  数据源（陷阱 #12）。
- **优先选择可验证的事实，而不是命名约定。** 根据路径形态
  （`/skills?/[^/]+/references/`）进行分类，只编码了一种目录布局；采用任何
  其他布局的仓库都会被分类为 `None`——永远无声无息。修复方法*不是*扩大
  模式范围，因为那只会把无声漏报换成整台机器范围内的误报（规则 1
  明确禁止这种取舍）；正确做法是提出一个文件系统能够回答的问题——
  *这个 `references/` 目录旁边是否有 `SKILL.md`？* 事实能够经受
  布局变化，约定则不能。（当候选对象**本身就是** `SKILL.md` 时，
  并不存在可供检查的同级对象——应按 basename 分类；#13 解释了为什么这
  是规范定义的事实，而不是本规则所警告的命名习惯。）
  **可验证的事实仍可能是错误的事实——要锚定问题并按
  类型过滤。** `test -f SKILL.md` 在下载文件夹中也可能为真，而某个防护逻辑曾通过
  向上遍历祖先目录查找这一文件，结果吞掉了整个主目录，随后要求一个真实
  会话加载一个以该主目录命名的 skill——这是一个不可能存在的名称（规则 9 中的事故）。
  应锚定到某个*特定*目录的同级位置，或锚定到已知安装路径；不带锚点的
  祖先目录遍历，不过是披着事实外衣的约定。

两者共同的迹象是：某个分支在生产环境中一次都没有触发过，而它的
测试却全部通过。打印格式化之前的原始分类结果，你就会看到
自己遇到的是哪一种情况。

### 7. 如果钩子**要求补救**，请证明循环会终止

一个在完成 X 之前始终**阻塞**（exit 2）的钩子——尤其是 Stop 钩子，因为
它们会在之后每次停止时重新触发——不是检查，而是一个**反馈循环**。
（如果钩子只是*注入*一项要求并以 0 退出，则根本不存在循环：没有任何内容
会被重新评估。这就是下面的机制 0，而且它成为正确默认选择的频率
比人们以为的更高。）

```
condition T is true → hook demands remediation R → model performs R → T checked again
```

**如果完成 R 可能使 T 再次为真，那么循环就不会收敛。** 没有
错误，也没有崩溃；它会一轮又一轮地消耗资源，直到有人介入——
通常确实会如此，因为每一轮都是一个*完整的*补救周期
（分派、等待、采纳、编辑），而不是一次廉价的重试。**同样也正是因为
这一特性，运行框架设置的连续阻塞 8 次上限救不了你：
只要每次继续执行时调用过工具，它的计数器就会重置，因此由工具调用
构成的补救周期会让计数器永远停留在 1**（实测——#27）。即使
确实达到了该上限，它也只是防止会话失控的最后防线，而不是一种设计：
该轮会在违规状态依然存在的情况下结束，而运行框架会将该轮报告为
`reason:"completed"`——与真正完成无法区分。
“它最终会停止”并不构成任何你所需要的终止性，而且在这里它甚至
根本不会最终停止。`stop_hook_active` 在这里*救不了*你——该字段只涵盖
**一层重入**（“我刚刚阻塞的停止正在重试”）。
它完全没有涉及*跨轮次*的情况：模型确实离开并执行了 R
（实际工作，包含许多工具调用），然后自然停止；这是一次全新的 Stop，
该字段为 `false`，而钩子会基于相同的理由再次触发。

**这项测试借鉴了程序验证中的终止性证明**——即[循环变式 /
秩函数](https://en.wikipedia.org/wiki/Loop_variant)：写下一个映射到
良基序（通常就是 ℕ）的量 **V**，并证明 **V 在每个
`trigger → remediate → re-check` 周期中都严格递减**。
没有 V，就没有终止性证明——不要注册该钩子。

**V 是设计阶段的义务，不是代码**——你绝不会在钩子中计算它。
实际交付的是*谓词*（即下面这些机制）；V 是证明该谓词会收敛的论证。
把它放在下一位读者必然会看到的地方——脚本头部：

```bash
# TERMINATION: V = 1 - exists(<receipt path>)
# decreased by: R writes the receipt; nothing R does afterwards can remove it.
```

“证明它会递减”具体对应三个问题，而答案应写入该
注释：

1. **R 会改变什么？** 指明确切的文件 / 字段 / 时间戳。
2. **该事物是 T 的操作数吗？** 如果是，而且 R 会使它重新趋向“触发” →
   那么就不存在 V。
3. **执行 R 之后，能让 T 再次为真的最小输入是什么？** 如果答案是
   “我刚刚触发过的同一个输入” → 那么就不存在 V。重新设计谓词；
   不要重新调整阈值。

**一个真实的反例。** 某个 Stop hook 要求，在累积性制品（规则文件、skills、其他
hooks）可以被推送之前，必须进行一次独立审查：

- **T**（使 hook **触发**的条件）=“存在尚未被任何审查覆盖的编辑”，实现方式是比较时间戳
  `last_edit > last_review`（`last_edit` = 整个制品集合中的最新 mtime，
  `last_review` = 审查记录的 mtime——两个单一数值，这恰恰使得这种比较看起来很安全）
- **R** = 派遣一名独立审查者

但一次值得运行的审查**会有输出**：它的发现会由**同一个 agent 立即采纳，
并且发生在该 agent 下一次尝试停止之前** → 这会产生新的编辑 →
`last_edit` 超过 `last_review` → **T 再次为真**。（如果之后由人工在带外采纳，
就不会出现循环——该循环要求补救和重新检查发生在同一个 agent 的轮次内，
而这正是 Stop hook 所保证的。）这里不存在 V——补救并不会减少某个量，
而是会*重置*一个量。唯一的逃逸方式是“审查，然后什么也不改”，而这恰恰是派遣审查者
毫无意义的情况。实际观察结果：连续三轮，每一轮都是完整的审查并采纳周期，直到用户说
停止才退出。

有两点使这个问题很难被发现。**这个比较孤立来看完全合理**——“审查必须比上次编辑更新”
正是你会写出的条件。而这句话是**通过**条件——T 是它的否定。如果你不带这个否定，
就把它原样记在脑中，那么在后续分析中，你推理的就会是错误的操作数；请始终将 T 定向为
**触发**条件。（将*代码*写成提前退出的守卫子句——`… && exit 0`——是正常的 shell 风格，
这里讨论的并不是这一点；这种规范关注的是你以哪种方向进行推理。还要注意相等情况：
同一秒的 mtime 会落在通过一侧，也就是故障开放，这与下文这条规则对状态读取的要求一致。）
运行上面的检查清单，结论就会自然得出：R 会改变 `last_edit`（Q1）；
`last_edit` 是 T 的一个操作数（Q2）；能够重新触发 T 的最小输入就是补救本身的输出
（Q3）→ 不存在 V。

**第二种失败形式：谓词根本无法看到补救操作
（可观测性缺口）。** 上面的反例使用的是一个会被补救操作*推动*的时序谓词。
同一家族中还有一种更隐蔽的失败：补救已经发生，但谓词用来读取它的通道在当前环境中
并不存在。真实案例（2026-07-26，在一次全量实例循环审计中发现）：某个 Stop
hook 通过扫描 tool_results 中的 `agentId: <hex>` 并读取
`subagents/agent-<hex>.jsonl`，来检测“是否已进行独立审查”——这在主 profile
中是正确的。Team-mode 会话使用完全不同的 schema（生成回执为
`agent_id: <name>@session-<uuid>`，交付内容是以 `teammate_id`
标识的 teammate 消息，文件为 `agent-a<name>-<hex>.jsonl`）——永远是零匹配，
因此 `last_review` 始终保持为 `None`，每个“累积性编辑∧推送”的轮次都会重新触发
该要求：这是一个误报循环，在每个停止序列内最多阻塞一次，但跨轮次没有上限；而该会话中
“2/2 次触发”全都发生在已经完成全面审查的工作上。同一家族，不同的处理方法：
时序循环需要更好的*谓词*；可观测性循环需要更好的*通道*。在检查清单中添加第四个问题——
**Q4：在这个 hook 将运行的每一种环境中，谓词真的能看到 R 发生吗？**
对于读取 transcript 的 hooks，这意味着要解析来自每种 profile/mode 的真实会话，
而不是只用一种 schema 的 fixture 进行测试。（上述案例的修复方法：
多 schema 检测 + 从轮次边界中排除 teammate 交付内容，使其无法截断检测窗口——陷阱 #20。）

**先按维度选择，再按顺序选择——这并不是同一事物的五种强度。**
0 决定*是否要阻塞*；1 决定*要把它挂在哪个事件上*；2–4
是*谓词的形态*（选择 1 后，仍需从 2–4 中选择一个）。0→4
的顺序表示“循环被消除得有多彻底”，它与**你能实施的强制程度成反比**
——因此，应选择仍能满足你实际强制需求的第一个方案，而不是简单地选择第一个方案。

0. **不要阻塞——改为注入。** 如果要求只是建议性的（你希望模型
   *考虑* R，而不是让它在不满足 R 时无法结束），就将其打印出来并以 0 退出。
   不会发生重新求值，因此也不存在需要证明会终止的循环。对于低于 Tier-0 的任何情况，
   这都是正确的默认选择，而其代价也很明确：提醒可以被忽略，所以应在标头中说明它是故障开放的
   ——规则 4 的要点仍然成立，主体可以绕过的门禁就不是真正的门禁。如果你需要的是一个
   *门禁*，请使用 2，并为回执付出代价。注入通道：Pattern D。
   ⚠️ **此选项在 Stop 上不存在**——而规则 7 的主要讨论对象*就是*
   Stop，所以在尝试使用它之前请先阅读这里。在 Stop 上，`exit 0` 意味着“允许本轮
   结束”，因此不会有后续推理步骤来接收这段文本；而且
   `hookSpecificOutput.additionalContext` 与 `exit 2` 一样计入同一个 8 次阻塞上限
   （参见 hook-types 一节），也就是说，它同样属于阻塞。Stop 恰好只有两种模式：
   门禁，或者静默。因此，在 Stop 上选择机制 0 实际上意味着**更改事件**
   ——将注入挂到生成该制品的工具调用上（PostToolUse，Pattern D）——或者承认你终究
   想要的是一个门禁，然后转到机制 2。
   ⚠️ **仅当 R 不是你自己的匹配器目标时，“无循环”才成立。** 一个挂在
   `Bash` 上、告诉模型运行 `git ls-remote` 的注入器，会在该命令执行时再次触发，
   并再次注入。形态相同，但更温和——模型可以忽略它，因此不存在强制迭代，
   但它会在每次重复时广播，而不是什么都不做。请检查你建议的 R 是否正是此钩子
   会匹配的操作。

1. **将检查移到操作边界。** 如果你想设门禁的是一个
   *操作*——推送、发布、删除——请使用 PreToolUse 守卫**该操作**，
   而不是使用 Stop 守卫**本轮对话**。**Stop 钩子的补救循环通常是挂错事件的操作门禁**，
   这正是 hook-types 一节中“Stop 是异类，也是最常被误用的那个”这一说法的具体情形。
   **请准确理解这样做能带来什么。** 只有当模型
   *主动重试受门禁限制的操作*时，PreToolUse 才会再次触发，而模型始终可以选择放弃，
   并正常结束本轮。因此，它能保证**本轮会终止**——最坏情况从“本轮无法结束”
   降为“此操作不会发生”。但它**不能**让一个不收敛的谓词变得收敛：以上面的反例为例，
   将其原封不动地移到 PreToolUse，循环仍会完整保留（push →
   被阻塞 → 审查 → 采纳发现的问题 → 进行新编辑 → 重试 → `last_edit` 再次领先
   → 被阻塞）。这种情况的问题出在它的**谓词**上，而不是事件上，因此你仍需从 2–4
   中选择一种形态。还要注意，PreToolUse **没有**测试框架的兜底机制
   ——hook-types 表中的 8 次阻塞上限仅适用于 Stop——因此，将一个会自行重置的谓词
   移到这里，安全网会*更少*，而不是更多。
   ⚠️ 有两种情形不应使用此机制：**R 必须通过你设置了门禁的那个工具完成**
   （在 `Edit` 上设置守卫，却要求你先修复文件标头——这会造成死锁，永远无法满足要求），
   以及**在同一会话内重复发生的操作**（在一个要推送五个仓库的会话中设置
   `git push` 门禁 = 五次完整要求；这就是下方实战故事中的密度问题，
   而机制 1 并不能让你免受此问题影响）。

2. **将“已经修复”设为一个存在性事实，而非时间性事实——并以需要修复的对象作为键。** 让 R 生成一个制品，然后测试它*是否存在*；键正是这种方式能够奏效的关键：

   ```bash
   KEY=$(git rev-parse HEAD 2>/dev/null || printf 'nogit')   # or a hash of the
   RECEIPT="${TMPDIR:-/tmp}/my-guard.${KEY}.ok"              # reviewed content
   [ -f "$RECEIPT" ] && exit 0            # V = 1 - exists, for THIS key
   ```

   `V = 1 - exists` 是**按键计算的**：每个键只会恰好减少一次，并且对于*该键*永远无法被重新推高。新工作会产生一个*新*键——这是一个新需求，而不是重新触发。两种朴素的键控方式都会失败：使用单个全局路径会导致钩子在每台机器上只触发一次，之后便永久失效、毫无信号；而基于时间的键正是本规则要禁止的时间性谓词。**时间性谓词几乎总是错误的形式**，因为你所要求的修复通常正是会改变被比较操作数的因素。
   ⚠️ 如果**模型**能够创建回执，那么这不过是规则 4 中已弃用的 `GUARD_OK=1` 逃生通道换了件外衣。应由模型无法驱动的对象来写入回执（审查者子代理自己的输出文件、git note），否则就应承认该钩子仅提供建议，并在其头部明确说明。

3. **设置重复次数上限。** 每个会话中针对每个目标最多提醒 N 次——`session_id` 是唯一稳定的键（它存在于每个事件中；参见模式参考中的 JSON 约定）：

   ```bash
   SID=$(printf '%s' "$INPUT" | python3 -c "import sys,json;print(json.load(sys.stdin).get('session_id','nosid'))" 2>/dev/null || echo nosid)
   CNT="${TMPDIR:-/tmp}/my-guard.${SID}.count"
   N=$(cat "$CNT" 2>/dev/null || echo 0); N=$((N+1)); printf '%s' "$N" > "$CNT"
   [ "$N" -gt 3 ] && exit 0                # V = 3 - N, reaches 0 and stays
   ```

   这种方式很粗糙，并且刻意不去判断 R 是否真的发生了——但它是*有限的*，而这正是之前缺失的属性。**不要**用 `$$` 或 `$PPID` 替代：每次运行钩子都会启动一个新进程，因此这些值每次调用都会变化，计数器永远无法累积。输出计数（“第 2 次提醒，共 3 次”）——请参阅下文的事故教训，了解为什么这种措辞不可或缺。

4. **滞后机制／冷却窗口**（控制理论对[告警抖动](https://utcc.utoronto.ca/~cks/space/blog/sysadmin/HysteresisMeaningAndAlerts)的解决方案）：
   触发后，在一段窗口期内禁止重新求值——使用一个时间戳文件，再加上
   `[ $(( $(date +%s) - <stamp mtime> )) -lt 900 ] && exit 0`（在 BSD/macOS 上，mtime 使用
   `stat -f %m`；在 GNU 上使用 `stat -c %Y`——此处其他代码片段也是如此）。这适用于那些*围绕阈值振荡*的条件；但**不适用**于会被修复操作**重置**的条件——后者需要使用机制 2 或 3。
   ⚠️ **滞后机制不提供任何 V——它是速率限制器，而非终止性证明。** 只有当条件自行消退时，循环才会结束；此时结束循环的是外部世界，而不是你的钩子。因此，它的 `# TERMINATION:` 行必须指出该外部事实（“当时间戳过期时，X 已由<何人>解决”）。如果你无法如实写出这一行，那么你需要的是机制 2 或 3。（还有一种值得注意的家族相似性：机制 0 是二者的极限情形——要么是将上限设为 0 的机制 3，要么是将窗口设为 ∞ 的机制 4。它们的区别在于执行方式，而不在于终止性。）

**状态本身发生故障时的处理方向：应用规则 5 的问题，而不是根据词语进行匹配。** 如果状态无法读取或写入——`TMPDIR` 不可写、沙箱限制、
磁盘已满——则由规则 5 的防护类别表来决定，而它的判断方式是询问：**“如果这个
状态消失了，修复是否仍然可能？”** 对于机制 2 和 3，答案是**否**——收据是 R 已经发生的唯一记录，而机制 3
刻意不判断 R 是否发生，因此它的计数器是唯一的退出途径——所以**允许停止**。一个无法读取自身
状态却仍然进行阻塞的终止机制*本身就是*循环，而且现在连人类可见的原因都没有。

⚠️ **不要仅仅因为机制 3 和规则 5 的“反转子情况”都提到了
“计数器”，就把机制 3 归入该子情况。** 该子情况适用于这样的计数器：它只是在用户仍能独立满足的
谓词之上，对*重复催促*进行次数限制——在这种情况下，计数器不可读时保持安静，会让一个原本还有其他解除方式的
钩子静默，因此你应继续求值该谓词。机制 3 没有这样的备用谓词。**实测表明，这正是这种组合会产生的
故障：** 将机制 3 的代码片段粘贴到模式 E 的框架中（根据 `-e`-与-trap 要点，该框架带有
`set -uo pipefail`），将
`TMPDIR` 指向一个不可写目录，它会在连续五次运行中都返回退出码 2——`N` 永远无法持久化到 1 以上，
上限永远不会达到，而且一旦修复涉及工具调用，#27 已经排除了把执行框架上限作为兜底方案的可能。这里的故障
方向完全由代码片段本身并未包含的一行 `set` 决定，因此
**应将防护放在实际失败的步骤上——即写入——绝不要放在
读取上**：

```bash
printf '%s' "$N" > "$CNT" 2>/dev/null || exit 0   # can't persist ⇒ can't terminate
```

读取操作已经受到防护（`cat … 2>/dev/null || echo 0`），而且**必须保持这种
方式**：计数器文件不存在是首次运行时的正常情况，因此在读取操作上使用 `|| exit 0`
会让钩子在完全健康的环境中永远保持静默。每种变体连续运行五次的实测结果如下：防护写入操作时，在可写的
`TMPDIR` 上得到 `2,2,2,0,0`，在不可写的目录上得到 `0,0,0,0,0`——两种情况都正确；防护读取操作时，
**两种情况都**得到 `0,0,0,0,0`，也就是说，这种防护会导致钩子根本一次都不触发。

**要求文本中的文字说明不能替代一个会收敛的谓词。** 如果一个
钩子的消息写着“如果你判断这没有必要，只需再次结束”，它仍然会在每一轮产生一个完整修复周期的成本，
因为一个被告知必须执行 X 的模型通常会执行 X。逃生通道必须位于**谓词**中，而不是
建议中。

**测试要求，以及这里最容易遗漏的事项：** 自检
需要一个**“修复后”**用例——不仅要测试“应触发时会触发”，还要测试
**“R 完成后会停止触发”。** 如果没有该用例，不终止问题在*结构上不可见*：每个测试夹具都只是一个孤立的
时间点判断，而不终止是**序列**的属性。只检查单个时间点的测试套件，无论包含多少用例，
其收敛性覆盖率都是零——正因如此，钩子可能带着全绿的自检发布，却在第一次真实遭遇时就陷入循环。
能够发现该问题的行对（收据不存在 → 触发，收据存在 → 静默；其中的设置/清理无法用普通 `run` 行表达）
已在 `scripts/test_hook.sh` 的“修复后行”下提供模板；症状 →
原因 → 修复见陷阱 #16。

**已证明终止 ≠ 它*感觉上*已经终止（2026-07-25 实战案例）。** 一个 Stop
钩子采用了正确的存在性事实变式 V，却在一次会话中触发了三次——每次
触发都是由一个*不同的*已完成任务发起的合法*新*推动，
机制完全按设计工作——但用户的体验仍然是“为什么这东西
像是卡在循环里了？”（这与机制 2 中的“R 所做的任何事都无法
将它推回去”并不矛盾：**V 是按键区分的**——三个不同的键，三次彼此独立的单向
递减。当你无法判断自己处于哪种情况时，这也可以作为诊断方法：
如果每次触发都携带一个*新*键，说明机制是正确的，问题在于密度；
如果重复触发共享*同一个*键——或者谓词根本没有键，因为它比较的是
时间戳——那么你就处于上面的反例中，需要替换该谓词。）三个独立的补救周期接连发生，
从外部看与循环没有区别。变式证明解决的是
机制问题；它并未说明**一次会话可能需要多少次不同的补救**。
如果你的领域会产生这种密度（这里的复合产物每天会交付
数次），可以考虑将机制 2（存在性事实）与
机制 3（会话级上限）结合使用，或者有意接受这种观感，并在
钩子的输出中明确说明——“最多 N 次提醒中的第 2 次”让人感到正在取得进展，而不加说明的
重复看起来就像循环。**（2026-07-26 后续：同一个钩子中那些看起来
属于密度问题的触发，后来发现 100% 都是误报——它的审查
通道在团队模式下无法感知 schema；参见上面的可观测性形式。在将
密度认定为“合理”之前，请先验证这些触发是否确实有证据支撑。）**

### 8. 等待也需要同样的证明——通知仅供参考，轮询必须带有预算

规则 7 涵盖的是由*钩子*造成的循环。即使没有涉及钩子，
同样的模式也会再次出现：**智能体轮询异步结果**——子智能体的
报告、后台任务的完成通知、CI 状态。真实会话
（2026-07-25）：子智能体完成通知通过一个可能
延迟或丢弃通知的邮箱传递；三个独立的智能体都已完成工作，但
通知一直未送达，而等待中的智能体在约 40 分钟内空耗了十几个
`sleep 240` + 催促周期，直到人类询问它究竟在
做什么。没有发生任何错误；这个循环只是没有变式。

规则 7 的机制可以映射到这里——前两个可以直接应用；滞后机制没有
对应项（等待不会振荡），它的位置由一个特定于
等待的陷阱取代：

1. **轮询产物，而不是通知。** 如果你真正需要的是一个
   结果（文件、git ref、API 状态、DB 中的一行），就等待*它*，而不是
   等待“它有没有说自己完成了”。通知是一条提示；产物才是
   事实。一旦该事实落地，存在性检查就会立即终止，无论
   是否有任何消息送达。
2. **每次等待都必须带有预算，并在编写循环时确定。** 最大轮数
   × 间隔（例如 3 × 4 分钟），以及在
   第一次休眠*之前*就已存在的降级路径：自己完成、询问用户，或者将其标记为待处理并继续
   其他工作。“无限期等待看看”不是降级路径——它就是
   循环。
3. **交付协议仅供参考，不是机制。** “完成后通过
   SendMessage 报告——保持沉默视为未完成”值得写明，但
   它约束的是智能体是否*发送*，而不是邮箱是否*投递*。
   在一次会话中，提示词里都包含该协议的三个智能体全都陷入了沉默。
   设计等待流程时，应假设通知可能永远不会到达——因为
   它确实可能不会到达。

两个相邻的陷阱，都在同一次会话中付出了代价：**将一个实际上正在工作的“卡住”代理停止**——邮箱延迟并不等于空闲；一名审阅者正在进行 20 分钟的真实语料库测试，却在即将交付结果的几分钟前因被认定“卡住”而遭终止。以及**对等待本身进行 `--dry-run` 式探测**：在断定对方保持沉默之前，先确认你自己的观察通道能够正常工作（在那次会话中，System Events 的窗口计数对屏幕上实际存在的对话框信心十足地返回了 0——权限故障伪装成了证据）。

### 9. 固定测试用例无法告诉你误报率——注册之前，先重放真实命令语料库

规则 1 对*哪种*错误更严重进行了排序（误拦截优于漏拦截，因为一个需要人们绕过的守卫，会让人形成下意识绕过它的习惯）。规则 2 要求你在注册前进行测试。二者都无法告诉你**误拦截面实际上有多大**——测试表也无法做到，因为*它的输入是你依据产生检测器的同一套心智模型编写的*。其中的用例只包含你想到的形式；而你未曾想到的形式，从构造上就不可能出现。这不是靠增加测试行就能弥补的覆盖率缺口。

**实测于 2026-08-06。** 一个 PreToolUse/Bash 守卫通过了包含 26 个用例、并对其运行 5 个变异的测试表，随后完成注册。之后使用从最近 60 份会话记录中收集的 **11,903 条去重真实命令**进行重放：其中 143 条产生了候选项，实际钩子拦截了 46 条，而手动检查全部 46 条后发现**其中 10 条是错误拦截——占其全部拦截的 21.7%**（两个边界案例按正确计算；如果反过来判定，则约为 30%）。在 39 分钟内，它拦截了 3 个真实会话，其中一个会话被告知去加载一个根本不存在的技能——也就是下文的第三个缺陷，以指向不存在目标的补救指导形式浮现出来。它在同一个小时内被移除。三个根本缺陷全都位于**解析**层：续行标记被当作分隔符读取；分段扫描将 heredoc 正文和数据参数计为执行内容；路径分类器没有类型过滤器。

这个故事*不能*支持两个结论。它**并不**意味着“变异测试不起作用”：后来对同一套测试进行审计时发现，**钩子逻辑中有 5 部分即使被删除，全部 26 行测试仍然保持通过**；而且有一行被作者标注为“已从装饰性测试修复”的测试仍然只是装饰——*“我运行了变异测试”并不等于“变异测试是正确的”*，正是重放暴露了这两个问题。它也**并不**意味着“你不可能事先知道”：这些缺陷中有三个，都是对本文件已经提供的代码进行手写重实现而产生的（`split_shell_lines`、命令位置遍历，以及 `is_git_write` 对 `-C` 及其参数的处理）。规则 1 中的*原样使用遍历器*才是被跳过的、更低成本的修复方式；重放是最后的保障，而不是第一道防线。

**方法——共四步，而第 2 步正是最常被跳过的一步：**

1. **收集。** 会话记录位于
   `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`，此外还包括在
   `~/.claude/history-sources.json` 中注册的所有归档。命令位于满足
   `type == "tool_use"` 且 `name == "Bash"` 的 `.message.content[]` 条目中，字段为
   `.input.command`——**不是**钩子事件中的 `.tool_input.command`，后者具有不同的结构。进行去重，并选取足够多的会话记录，以确保其中包含你自己近期工作的命令形式（那次运行使用了 60 份）。
2. **使用随附的检测器进行预过滤，并逐字原样截取其代码**——绝不要使用手写的等效实现，否则你测量的只是自己两种猜测之间的一致程度。预过滤仅用于降低成本（11,903 → 143）；真正作出判断的是第 3 步。如果检测器不是一个可单独提取的代码块——例如它是 shell，或被拆分在一个通过 source 引入的库中——就把它改造成这样的代码块；无法独立运行的检测器，同样也无法进行单元测试。
3. **将每个候选项连同其自身的真实会话记录和 `session_id` 一起传给真实钩子。**
   读取会话状态的守卫在伪造上下文中会给出不同答案。事件契约：
   `references/hook_patterns.md`。有两件事会让你踩坑——请在临时的
   `TMPDIR` 下运行，否则规则 7 的回执和每会话计数器会写入真实会话，*并且*
   在测量进行到一半时让守卫停止发声；如果钩子设有人为确认关卡，请通过模式 B 的强制拒绝路径驱动它，而不是手动回答 143 个对话框。
4. **手动检查每一次拦截——拦截列表就是误报测量结果。** 允许列表回答的是规则 5 的问题（它保持安静，是因为那里什么都没有，还是因为它看不见？）；如果重放返回*零次*拦截，那么应当怀疑测试工具，而不是把它当作一份清白证明——陷阱 #11 针对触发不足的方向规定了使用同一种检测手段。

**如何处理这个数字。** 如果某个误拦截块给出的补救指导是错误的或无法执行的 → 完全不要注册：这种形态正是反身绕过规则 1 要防止其产生的制造流程。否则，把拦截列表当作修复列表处理，然后重新回放。可以预期，误报会集中在**你编写守卫时正在做的事情**上——那次运行中有一半落在钩子开发文件上，因为其作者那一周正在构建钩子。还要专门扫描拦截列表中的**运维操作**（编辑 hooks 目录下的内容、对钩子运行 `bash -n`、守卫自身的 SSOT）：如果一个守卫会阻止自身被移除，就无法从会话内部将其关闭。最接近的已记录案例是 #25，其中守卫拦截了一个**只读的** `git config core.hooksPath` 查询——这正是距离自我锁死仅一步之遥的同一个盲点。一旦守卫已经将你锁死，逃生路径见 **#3** 的列表（使用 Edit/Write 工具编辑 `settings.json`，它永远不会触发 `Bash` 匹配器；或者使用不同的 `CLAUDE_CONFIG_DIR` 启动会话）。

关于工作量规模，避免让这件事看起来像一个研究项目：一次采集加一轮循环，实际耗时以分钟计。

## 构建顺序（按先后次序）

1. **确认它确实会重复发生**，而不是假设性的——否则就不要构建。
   如果钩子将**要求执行补救措施**，而不只是进行拦截，请在编写任何逻辑之前，将其终止变体 **V** 作为一行 `# TERMINATION:` 写入脚本头部（规则 7）——并且首先检查你要设门禁的对象是否是一个*操作*；如果是，那么在该操作上设置 PreToolUse 守卫可以直接消除循环，而不是设法约束它。如果无法指出一个在每次 `trigger → remediate → re-check` 循环中都会严格递减的量，那么该设计不会终止——应修复设计，而不是正则表达式。
2. 在 SSOT 目录中编写脚本；执行 `chmod +x`。
3. 使用 shlex 进行词元级匹配来完成**检测**（规则 1），以外部世界能够回答的事实为依据，而不是以你自己的呈现方式或某种命名约定为依据（规则 6）。
   - **首先检查 ShellCheck 是否已经能作出判断——然后记录答案，因为下一位作者也会问同一个问题。** 它是事实上的 shell 反模式标准工具，因此“为什么不直接使用 shellcheck”是评审者首先会问的问题。于 2026-08-15 使用 **0.11.0** 针对 `find . -name x | head -5 || echo "no"` 进行实测——这是一个经证明永远不可能触发的回退，因为 `||` 绑定到管道的**最后一个**阶段，而 `head` 在输入为空时以 0 退出：**默认配置不报告任何内容，退出码为 0**。`--enable=all` 会检出 **SC2312**（`check-extra-masked-returns`），但它也会对 `cmd | jq . || echo bad` 触发，而在这个例子中，最后一个阶段确实可能失败，回退也确实有意义。有三个原因使它没有资格成为*门禁*——而且每个原因都具有普适性：它**默认关闭**（所以现在没有保护任何人），它无法区分无效回退和有效回退（无差别触发 = 规则 1 所述的误拦截螺旋），而且它自己建议的补救方法是“使用 `|| true` 忽略”，这与意图正好相反。它检查的也是**文件**，而不是工具调用事件。这个答案的一般形式是：标准 linter 是正确的**检查对象**，但通常不适合**受托充当阻断门禁**，因为 linter 为广泛提供建议而优化，而门禁需要精确性。你的钩子所贡献的正是这种精确性。已发布的示例是 `pipe-fallback-guard`，其精确性来自一份很小的末级命令列表，这些命令确实会吞掉上游退出码（`head`/`tail`/`wc`/`cat`/`sort`/…）；同时，它有意排除 `grep`/`jq`/`awk`/`sed`，因为这些命令确实可能失败。
4. 使用 **`bash -n` + `test_hook.sh`** 测试触发用例和外观相似的健康用例（规则 2）——在全部通过之前不要注册。应包含带有未展开路径的形态（`cd ~/elsewhere && …`，规则 5）；如果钩子包含人工门禁，则应包含一行强制拒绝用例（模式 B，“让门禁可测试”）；如果钩子要求执行补救措施，还应包含**补救后的成对用例行**——没有回执时触发，有回执时保持安静（模板见 `scripts/test_hook.sh`；规则 7——时间点式固件在结构上无法发现不终止问题）。
   - **为钩子提供 `--selftest` 模式，并让该模式支持双向测试。** 然后让 SessionStart 守卫健康检查（见上文“钩子类型”——其全部职责就是检查守卫自身的那个检查）对每个提供了该模式的已安装钩子调用 `<hook> --selftest`。这是唯一能自动捕获以下故障的检查，而 `bash -n` 以及下文第 4-7 步在结构上都无法捕获该故障：钩子已经**退化成永久无操作状态**。从构造上说，这种故障不可见——一个永不触发的守卫产生的输出，与一个没有任何内容需要报告的会话完全相同，因此它可能持续存在数周。两个固件只是*下限*，而不是目标：一个必须拦截的样本**以及**一个必须放行的样本，这样才能同时捕获“停止触发”和“开始误拦截”——只有其中任何一种都不够。**应根据杀死的变异体数量确定规模，而不是根据固件数量确定规模**；校准方式也应与校准测试套件时相同：故意破坏检测器，并确认 `--selftest` 以非零状态退出。一个从未被观察到失败的自检，与 `exit 0` 无法区分。对已发布的 `compounding-edit-review` 进行实测：其**第一版的两个固件只杀死了 14 个变异体中的 4 个**——它自身注释中声明为关键保障的所有行为都没有覆盖，包括一个会让防循环检查短路、但自检仍打印 OK 的变异。现在它会运行 58 个用例。真正的约束不是固件数量，而是**会话启动时的实际耗时**，因为每次会话都要付出这一成本：这 58 个用例耗时**约 5.3 秒**，而双探针活性检查仅需**约 140 毫秒**。当杀死变异体所需的测试使你超出这一预算时，应选择**拆分**而不是缩减——在 `--selftest` 中使用成本较低、规模固定的活性探针，并在构建时通过 `test_hook.sh` 运行完整的回归测试集。如果缩减到变异体杀死线以下，换来的只不过是一个即使守卫已经失效也仍会通过的自检。
5. **回放真实命令语料库，并手动检查每一次拦截**（规则 9）——这会度量误拦截范围，而第 4 步中的固件表在结构上无法做到这一点。逐字提取已发布的检测器来进行预筛选；在临时 `TMPDIR` 下，将每个候选项连同其真实记录和 `session_id` 一并提供**给**真实钩子。
6. **创建符号链接**到 `~/.claude/hooks/`（规则 3）。
7. 在主 `settings.json` 中**注册**，并使各配置档收敛一致（规则 4）。
8. 对于 Tier-0/不可逆操作，添加**人工确认放行门禁**（规则 4）。
9. **持久化**：将 SSOT 提交到其私有仓库。可选择添加一行 CLAUDE.md 内容（正文说明*为什么*以及替代方案；钩子负责强制执行）。

## 已知陷阱（在调试误触发的钩子之前阅读）

包含症状 → 原因 → 修复方式的完整目录：[references/hook_pitfalls.md](references/hook_pitfalls.md)。
重点包括：`stdin` 被 `python3 - <<PY` heredoc 消耗（钩子悄无声息地允许
一切）、awk 拆分导致的误拦截（规则 1）、损坏的钩子污染会话
（规则 2）、Python *注释*中的引号或反引号悄无声息地破坏
`python3 -c "…"` 块且不产生语法错误（陷阱 #9——应改用模式 E 中的带引号 heredoc
形式）、静态环境变量逃生口（规则 4）、多配置文件注册不完整、
提交消息作为伪命令文本传入遍历器，并误拦截你自己的修复提交，除非豁免 `git` 写入片段
（#7），以及从命令文本解析出的路径保留其字面量 `~`，导致
防护在没有任何症状的情况下**开放失败**（#10——这是你不能等到
察觉后再处理的问题，因为沉默是它唯一的迹象）、某个分支读取钩子自身
截断后的显示字符串（#12），或依赖此仓库并未遵循的命名约定
（#13）——当测试套件只断言退出码时，这两者都不可见（#14）——
仅仅*包含*重定向的命令文本被计为写入（#15），以及
其**要求的补救措施会将自身重新激活**的钩子，形成循环，但自测仍显示绿色，
因为时间点固定装置在结构上无法发现不终止问题（#16，
规则 7）。

**测试工具是隐藏变量——使用 `scripts/test_hook.sh`，不要自行编写
测试工具。** 下面每种自行编写测试工具导致的失败模式，产生的输出都与干净
通过时*完全相同*，因此看起来像是成功（2026-07-22，在修复某个 Stop
钩子的白名单时，一次遇到了三个）：

1. **错误的事件形状。** Stop 钩子读取 `last_assistant_message` /
   `transcript_path`，而不是 `tool_name`/`tool_input`。向其提供 PreToolUse 形状的事件，
   它找不到任何文本 → 以 0 退出 → “没有误拦截！”
2. **JSON 引号。** 单引号内的 `'{\"a\":1}'` 会输出字面量
   反斜杠加引号；`json.loads` 抛出异常，钩子的 `2>/dev/null || exit 0` 将其吞掉，
   所有测试用例都“通过”。
3. **规则确实会豁免的测试用例。** 基线字符串使用了
   规则*有意豁免*的字符串（防护会标记形式为
   `<name> Group` 的新造昵称，但会豁免普通短语 `in the group` / `group chat`
   ——而基线行恰好使用了其中之一）。原本用于证明
   防护仍会生效的唯一一行并未触发防护，而整个测试套件仍显示绿色。

**而且，如果钩子的产物是其消息，退出码就无法对其进行测试。** 阻断型
钩子的契约主要是其退出码，因此 `run` 行可以覆盖它。但如果钩子的存在就是为了
*表达*某些内容——例如 PreToolUse 对正确替代方案的说明、Stop 提醒——那么它还有
退出码永远无法看到的第二个输出通道：
破坏措辞、颠倒条件段落、让 heredoc 吞掉某个部分，退出码仍会保持为 2，
同时每一行测试都会通过。添加来自 `scripts/test_hook.sh` 的
`says <label> <event> <pattern> <yes|no>` 行，
在两个固定装置中断言**两种极性**（对其目标输入存在，对其跳过的相似输入
不存在）——单独的 `want=no` 会在钩子完全不输出任何内容时空洞地通过，
因此只有与证明钩子确实会发声的 `want=yes` 行并列时才有意义。
匹配**固定字符串**，不要使用正则表达式：值得断言的短语通常包含方括号，
而在 BRE 中，`[skill]` 是一个字符类，会匹配任何包含 s、k、i 或 l 的文本。然后
**通过变异证明这些行确实会失败**：复制钩子，注入每一行声称能够捕获的
确切 bug，并确认该行变红。在你亲眼看到测试套件因正确原因失败之前，
绿色测试套件携带的信息量为零——曾有两个真实 bug 在一个完全绿色的
24 用例测试套件中幸存下来，因为每一行都只检查退出码（陷阱 #14）。

共同的模式是：**所有用例结果一致是一种坏味道，而不是放行信号。** `test_hook.sh`
会从结构上捕获上面的第 1 和第 2 种情况——它要求每个 `run` 行都有明确的 `expected-exit`
（而不是“它是否打印了某些内容”），并强制要求在外观正常的相似行旁边加入触发行，
这样，返回 0 的触发行就会显眼地失败，而不是混在其他行中。它
**无法**捕获第 3 种情况：某行的内容是否意外落入豁免范围，取决于你所编写的内容，
而任何测试工具都不知道你的规则意图。只有通过养成这样的习惯才能捕获这种情况——
*首先*断言一个已知有效的触发项；当它没有触发时，先怀疑测试行，而不是钩子。
