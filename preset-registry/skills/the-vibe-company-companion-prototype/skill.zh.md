# 原型

原型是**用来回答某个问题的一次性代码**。问题决定形态。

## 选择分支

判断要回答的是哪个问题：可以依据用户的提示词、周边的代码，或者在用户在场时直接询问：

- **“这个逻辑/状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。构建一个可共享的单一 HTML 文件（自由操作按钮加上带标签页的引导式演示），把状态机推入那些在纸面上难以推演的场景，并且让非开发者也能上手操作。
- **“它应该长什么样？”** → [UI.md](UI.md)。在单一路由上生成多个截然不同的 UI 变体，可通过 URL 查询参数和一个悬浮底栏进行切换。

这两个分支产出的成果截然不同，选错分支就会浪费整个原型。如果问题确实含糊且联系不上用户，就默认选择与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型开头写明这一假设。

## 两条分支通用的规则

1. **从第一天起就是可丢弃的，并且要明确标注。** 把原型代码放在其实际会被使用的地方附近（紧挨着它所为之做原型的模块或页面），让上下文一目了然，但命名要让随手翻看的读者能看出这是原型而非生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **启动毫无门槛。** UI 原型通过项目任务运行器中的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是用户双击即可打开的单个 HTML 文件。无论哪种方式，启动它都不需要任何思考。
3. **默认不做持久化。** 状态只存在于内存中。持久化是这个原型要去_检验_的东西，而不是它应当依赖的东西。如果问题明确涉及数据库，就使用一个临时数据库，或一个文件名中清楚写着 "PROTOTYPE, wipe me" 的本地文件。
4. **不做打磨。** 不写测试，不做超出让原型_可运行_所必需的错误处理，不做抽象。重点在于快速学到东西。
5. **呈现状态。** 在每次操作之后（逻辑）或每次变体切换时（UI），打印或渲染完整的相关状态，让用户看到发生了什么变化。
6. **完成后归档。** 把所有已验证的决策并入正式代码，然后把原型本身作为**一手资料**保存下来：提交到一个独立于 main 的一次性分支上，并在实现 issue 中留下指向该分支的上下文指引。同时把答案（结论以及它所解决的问题）也记录到 issue 或某个提交中。main 分支只保留已验证的决策。
