# Suede Code

## 闸门策略 — 提供建议，不构成阻断

本技能中的每个主张验证步骤、检查、质量闸门和交付结论，都是对用户的**建议，而不是对代理的控制**。此策略适用于本技能其他位置的每个闸门、检查、结论，以及“不要交付 / 发布 / 继续”行：

- 运行每项检查，并如实报告结果。结论（`ship`、`ship-with-caveats`、`hold`、字母等级、BLOCKED 或 OPEN 项）是附加在工作上的建议，不是会改变工作的命令。
- 不得因为检查失败或闸门给出 hold，而阻止、延迟、跳过、重写或拒绝用户要求的操作。应按要求完成该操作，并将闸门输出作为明确标注的建议一并交付。
- 失败的闸门只会改变你的报告内容，绝不会改变你的执行操作。
- 唯一例外：如果发现极高风险——数据丢失、安全或凭据泄露、法律或权利违规、付款错误，或不可逆的公开损害——请暂停，准确告知用户风险是什么以及有哪些选项，并让他们选择。用户的选择为最终决定。


代码一次审查：默认同时进行深入、基于证据的审查，**以及**直截了当的 A-F 交付等级评定。发现告诉你哪里有问题；等级告诉你是否可以交付。每项发现都要有文件、证据和修复路径。没有证据，就没有发现。没有信号，就不要堆砌数量。

**仅在被要求时运行。** 本技能绝不会因 diff、保存或提交而自动触发。请显式调用它（审查这个、给这个评分、对这个做安全检查、这个能否安全交付）。不得将其作为其他工作的副作用运行。

## 模型路由

默认：Sonnet。对于身份验证、付款和公共 API 表面审查，建议使用 Opus。

## 工作立场

- 审查当前源代码、当前 diff、本地文档和相关运行时行为。
- 将代码生成与审查分开。如果代码由你编写，请切换到审查模式，并寻找你的实现可能遗漏的问题。
- 保留用户和其他代理正在进行的工作。不要暂存、还原或重写不相关的文件。
- 优先提供高信号发现，而非堆砌数量。当格式化工具或本地约定已能处理时，不要留下风格吹毛求疵。
- 每项阻断性发现都需要证据、影响和具体的修复路径。

## 审查约定

审查前，请识别：

- **target：**仓库、分支、PR、提交范围、diff、路由、API 或发布构建；
- **intent：**变更声称要实现的目标；
- **risk lanes：**前端、后端、数据、身份验证、付款、契约、iOS、发布、公开文案、分析、密钥、部署、文档。

## 上下文图

在评判 diff 前构建轻量级图：

1. 已变更文件和生成文件。
2. 该变更涉及的导入、调用方、路由、API 处理程序、作业、钩子、模型、模式和配置/环境依赖项。
3. 应随行为一同更新的测试、夹具、迁移、发布脚本、文档和截图。
4. 运行时表面：本地路由、线上 URL、API 端点、模拟器流程、仪表板、App Store 元数据或部署目标。
5. 领域契约：创作者所有权、权利/来源、注册表支持的媒体、版税路由、代理商务、钱包/付款流程，以及已发布声明的准确性。

标记超出差异范围的风险：当相关文件、默认值、文档、环境变量或部署要求不再一致时。

## 运行检查门禁并遵守项目规则

在进行人工分析之前，运行仓库已有的检查门禁并纳入结果——类型检查、对变更文件运行已配置的 linter、测试套件、依赖发生变更时运行依赖审计，以及对差异执行真实的密钥扫描。检测有哪些检查；仅运行存在的检查；绝不伪造未运行的结果；当某个门禁无法运行时，在 Verification 中说明。然后阅读仓库自身的约定——`CLAUDE.md`、`AGENTS.md`、linter/formatter 配置、最近祖先目录的规则——并将其视为约束：不要标记规则允许的内容，要标记规则禁止的内容，也不要再次提出用户已经接受的模式。

## 审查模式

- **快速差异审查：** 小型变更、影响范围有限、聚焦问题发现。
- **深度 PR 审查：** 多文件行为、公开接口、数据/认证/支付、发布或跨仓库风险。
- **计划审查：** 实现尚未开始；检查范围、顺序、验收标准、测试映射和缺失的决策。
- **修复验证：** 修复后的审查；重新扫描变更文件，并确认原始问题已消失。
- **发布审查：** 验证构建、密钥、环境变量、公开文案、截图、元数据、部署以及线上/API 回读。

### 深度级别

添加 `--depth` 修饰符：

- **`--quick`**（约 2 分钟）：模式扫描——明显的缺陷、硬编码密钥、缺失的空值检查、注入模式、损坏的错误处理。不进行跨文件分析。
- **`--standard`**（默认，约 10 分钟）：针对变更路径逐文件检查正确性、语言陷阱（如下）、状态处理、变更行为的测试覆盖，以及变更文件内的调用图。
- **`--deep`**（约 25 分钟）：通过完整导入图和调用链追踪进行跨文件分析——只有在跨模块跟踪数据时才会出现的语义错误。用于认证、支付、迁移和公开 API 变更。

在每份输出顶部注明深度级别。

## 第 1 步——即时 F 触发条件（在任何评分之前检查）

任意单项匹配均自动判为 **F**。停止审查，报告文件和行号，并且不要为其余维度评分——其他维度无法提高该评级。此列表是规范副本；suede-code-grader 包含完全相同的列表——修改时必须同时修改两者。

**密钥和凭据**——在已提交源代码中硬编码 API 密钥/密文/token/密码；提交了私钥或证书；在密钥管理器之外保存 OAuth/签名密钥。  
**注入**——使用用户输入通过字符串拼接构造 SQL；通过 exec/spawn/eval 从用户输入构造 shell 命令；在可触发 XSS 的情况下，使用未经转义的用户输入渲染模板。  
**认证绕过**——认证中间件存在跳过认证的路径（提前返回、吞掉异常、恒为真的条件）；权限检查可通过请求参数绕过；JWT 接受 `alg: none` 或硬编码密钥。  
**支付和钱包**——支付处理程序静默吞掉错误；webhook 未验证签名；金额或收款方来自不可信输入且未进行服务端验证。  
**数据销毁**——迁移包含 DROP/破坏性 ALTER，且没有回滚、没有经过测试的恢复方案；批量删除/更新没有 WHERE 或 WHERE 由用户控制；缓存失效会清空生产存储且没有恢复路径。  
**明文敏感数据**——以明文存储或记录密码；将 PII 发送到未加密的日志/分析管道；在未加密字段中存储 SSN/支付卡/健康数据。

## 第 2 步 — 语言陷阱

**TypeScript** — 应使用 `unknown` + 守卫却使用了 `any`；没有证明性守卫的非空断言 `!`；非穷尽的可辨识联合类型（缺少 `assertNever`）；前面没有守卫的不安全 `as` 类型断言；没有配合 `keyof typeof` 使用的 `Object.keys()`；本应 `await` 却写成 `return someAsyncFn()`。

**React** — 缺失或不完整的 `useEffect` 依赖项；陈旧闭包（例如，`useEffect(fn, [])` 中的 `setInterval` 读取 state）；在具有身份标识的项目上 `.map()` 时缺少 `key` 或使用 `index` 作为 `key`；性能热点路径中未经 `useMemo`/`useCallback` 包装的内联对象/函数 props；跨越 2 层以上的 prop drilling（P3）；未通过 setter 修改 state（对 state 执行 `arr.push`）。

**Next.js** — 服务端/客户端边界违规（`'use client'` 导入仅限服务端的模块，或服务端文件使用浏览器全局变量）；异步服务端组件周围缺少 `Suspense`；面向用户的数据路由缺少 `error.tsx`/`loading.tsx`（P2）；可在客户端 bundle 中访问到未使用 `NEXT_PUBLIC_` 前缀的机密；未缓存的 `generateMetadata`/`getServerSideProps` 外部请求；在 App Router 中导入 `next/router`。

**数据库（Drizzle/Prisma）** — 循环中的 N+1 查询；筛选/排序/连接列缺少索引；没有使用事务的多表写入；逻辑上唯一的字段缺少唯一性约束；可增长表上没有 `LIMIT` 的无边界查询。

**性能** — 新增超过 20 KB minzipped 的导入（标记其体积，并优先选择可 tree-shaken 的方案）；没有 `async`/`defer` 的渲染阻塞 `<script>`；未懒加载的非关键路由（`next/dynamic`）；对非 SVG 资源使用原始 `<img>` 而不是 `next/image`。

**Swift / iOS** — 没有证明性守卫的强制 `!`/`try!`/`as!`（会在运行时抛出错误的 `try!` 为 P1）；强引用捕获 `self` 的 escaping closure（需要 `[weak self]`）；在主线程外修改 UI/`@Published`/`@State`；跨越挂起点的 actor 重入；服务端可能省略的非可选 `Codable` 字段；对非稳定 `id` 使用 `ForEach`；未取消的 URLSession task/observer。

**整个仓库（`--deep`）** — 超出已变更文件的导入图范围，扫描仓库中每一个已变更符号的调用方，检查共享假设（在其他位置镜像的 config/defaults/env），对触及的行执行 `git log -L`/`blame` 以排查重新引入的回归，并确认变更符合其兄弟模式。说明你追踪了什么。

## 第 3 步 — OWASP Top 10（在 auth/api/middleware/routes 或 crypto/session/payment 导入时自动运行）

在发现中引用对应类别。A01 访问控制失效（每次数据访问均进行 authz，不得发生水平越权）· A02 加密机制失效（传输中/静态加密，不使用 MD5/SHA-1/DES，机密存放在 env 中）· A03 注入（参数化、转义输出）· A04 不安全设计（假设攻击者未认证，内建速率限制）· A05 安全配置错误（已变更的默认值、安全错误信息、关闭调试）· A06 易受攻击和过时的组件（当前依赖项、无 CVE）· A07 身份识别和认证失败（MFA、防暴力破解、会话失效）· A08 软件和数据完整性失效（受保护的 CI/CD、已验证的校验和、经过验证的反序列化）· A09 安全日志和监控失败（认证/访问/验证失败已记录日志且防篡改）· A10 服务端请求伪造（SSRF）（URL allowlist，不请求内部地址）。

## 第 4 步 — 评分（A-F，默认执行）

为每个通道评分 A-F，然后给出一个总体评分。对于非 Suede 工作，将“Suede 真实性”替换为“领域真实性”。

- **正确性** — 行为、边界情况、错误路径、异步、路由、数据流、回归风险。
- **安全性和权限** — 认证、密钥、支付、钱包、注入、路径、SSRF、权限、数据暴露均应采用失败关闭原则。
- **数据和状态** — Schema、迁移、缓存、作业、队列、Webhook、重试、幂等性、状态转换保持一致。
- **Suede 真实性** — 公开文案、权利、来源、注册表支持的媒体、版税路由、许可、智能体商业、产品声明与实现相符。
- **UX 和发布行为** — 加载、空状态、错误、成功、移动端/原生端、截图、元数据、路由状态能够协调一致。
- **测试和验证** — 已变更的行为具有有意义的测试、构建、截图、模拟器运行、实时/API 回读或明确说明的注意事项。
- **部署就绪性** — 环境变量、标志、配置、迁移、回滚说明、安装路径、文档、发布顺序清晰明确。

**评分含义：** **A** 所有通道通过，已在运行时验证，无后续事项。**B** 无阻塞项，存在已说明且范围明确的后续事项。**C** 存在可能在生产环境暴露的实际缺陷或未经验证的风险 — 建议修复前暂缓。**D** 存在很可能导致数据丢失、认证绕过、支付故障或用户可见失败的严重缺陷 — 建议不要发布，并且由于这些属于极高风险类别，应暂停并将是否发布的决定交由用户。**F** 核心行为损坏、触发 Instant-F，或缺少关键表面的证据。

**推荐门禁机械地遵循评分：** A → `ship`；B → `ship-with-caveats`；C、D、F → `hold`。无论评分为何，部署安全性发现（第 5 步）也会将推荐门禁调整为 `hold`。门禁是供用户执行的建议，并非对智能体的锁定。

**按表面划分的评分上限**（适用时明确说明）：
- **认证**（登录、会话、令牌、中间件、角色）— A 需要测试绕过/权限提升路径，而不仅是正常路径；B 需要正常路径 + 已说明的注意事项；否则上限为 **C**。
- **支付/钱包**（结账、订阅、退款、付款、转账、Webhook）— A 需要测试错误路径（扣款失败、拒付、重放）+ 服务端金额/收款人验证 + 不得静默吞错；B 需要正常路径 + 已记录的错误路径风险；否则上限为 **C**。
- **数据迁移** — A 需要已记录的回滚方案 + 针对类生产数据测试过恢复流程（或有合理豁免）；B 需要回滚方案，恢复流程未经测试；没有回滚方案则上限为 **D**。
- **公共 API 变更** — A 需要已验证的向后兼容性或版本化迁移路径；破坏性变更但没有路径时，上限为 **C**。

**技术债务** — 对评分的影响取决于所在位置，而不只是模式。认证/支付/迁移路径中的债务严格一个等级（支付模块中的上帝对象是 D，而不是 C）。核心/高流量路径中的债务按标准处理。工具/脚本中的债务会标记为 Required Upgrade，但除非其蔓延至关键路径，否则不会降低总体评分。不要仅因技术债务而阻止发布，除非它直接掩盖了 P0/P1 缺陷。对于具名的可维护性目录，加载随 suede-code-review 捆绑的十二种代码异味 Design Smell Baseline 参考资料 — 同样适用约束规则：仓库覆盖、严重性由判断决定、跳过工具已强制执行的内容。

## 第 5 步 — 部署安全门禁（每次都在最后运行）

对每个 pass/conditional/block 进行分级：**破坏性变更**（若契约发生变更但没有迁移方案则 block）、**回滚安全性**（若 `git revert` 无法撤销则 block —— 迁移、收费、已发送邮件、删除）、**影响范围**（标明约 0% / 约部分 / 约 100%）、**环境就绪情况**（若必需的环境变量尚未存在于生产环境则 block）、**依赖变更**（若存在 CVE 或未固定版本的生产依赖则 block）、**数据变更**（若存在无已测试恢复方案的不可逆写入则 block）、**安全性变化**（若新增攻击面但没有缓解措施则 block）、**自动化覆盖**（在连接生产环境的仓库中，若 `.github/workflows/` 或等效 CI 未覆盖变更的表面，或 `main` 未强制执行必需检查，则 block）。

## 第 6 步 — 提交脏污评分（每次都在最后运行）

扫描原始 diff 中每一行新增（`+`）内容，检查绝不能进入 git 历史的内容，涵盖七个维度：**密钥和凭据**（`sk_`、`pk_`、`ghp_`、`xoxb-`、`AKIA`、`-----BEGIN`、`password=`、`secret=`、`token=`、紧邻类似密钥名称的长十六进制/base64 字符串） · **调试残留**（`console.log`、`debugger`、`binding.pry`、`byebug`、`var_dump(`、`TODO: remove`、`FIXME: before merge`、被注释掉的真实逻辑） · **冲突标记**（新增行中出现 `<<<<<<<`、`=======`、`>>>>>>>`、`|||||||` 表示该文件从未被完全解决） · **意外暂存的文件**（`node_modules/`、`.next/`、`dist/`、`build/`、`__pycache__/`、`.DS_Store`、`*.log`、多余的锁文件） · **WIP 痕迹**（面向生产的字符串中出现 `[WIP]`、`DO NOT MERGE`、`TEMP:`、`lorem ipsum`/`asdf`） · **过大的或二进制 blob**（大于 500 KB 的文件、字体、编译后的二进制文件、指定资源目录之外的媒体文件） · **暴露的内部引用**（内部 IP 或主机名、非配置文件中的预发布 URL、源代码中的个人邮箱地址）。

将每个维度评为 `clean | suspicious | dirty`，并输出总体评级：**CLEAN** = 没有命中；**SUSPICIOUS** = 低置信度命中，可能是 fixture 或文档示例 —— 指出它并让审阅者确认；**DIRTY** = 高置信度命中，必须在合并前移除，并作为 P0 发现报告。总体评级为 `DIRTY` 时，应将建议门禁调整为 `hold`，与 Deploy Safety block 完全一致。

## 发现格式

以发现内容开头，并按严重程度排序。重复模式只分组一次。

```text
[P0] path/to/file.ts:142
问题：JWT 密钥回退为空字符串；当 SECRET 未设置时，任何令牌都有效。
修复：process.env.JWT_SECRET ?? (() => { throw new Error('JWT_SECRET required') })()
验证：设置 JWT_SECRET="" 后执行 curl /api/me —— 预期为 401，目前为 200。
OWASP：A02 加密失败
置信度：高
```

P2/P3 每项各占一行。**严重程度：** P0 数据丢失/安全/支付/发布损坏/不安全的公共行为 · P1 可能的生产回归、认证缺陷、主要路径损坏、已发布的错误陈述、缺少部署要求 · P2 有意义的边界情况失败、不完整状态、变更行为缺少测试覆盖 · P3 低风险改进、清晰度、清理工作。若无法关联到文件/路由/命令/状态/行为，请标记为开放问题。

## 修复模式（仅在 `--fix` 或明确请求时）

自动应用本地 P2/P3 修复（单文件，不改变契约），每项修复单独提交，并带上问题 ID。对于 P0/P1，在应用前以已确认的修复简报形式呈现；未经明确确认，绝不自动修改认证、支付或数据迁移代码。修复后，针对已修改文件重新运行相关模式；最多 3 个周期，之后作为设计问题升级处理。

## Suede 专项检查

跨应用、API、原生壳和服务器的认证/会话行为 · 创作者权利/来源/注册表/许可/版税/代理商业声明与已实现行为一致 · 支付/钱包/x402/结账/信用额度流程以失败关闭方式处理 · 公开页面不虚构指标、定价、合作伙伴、推荐内容或发布日期承诺 · 在作出生产环境声明前，Vercel/账户/部署假设与本地指南一致 · App Store/iOS 截图、元数据、隐私回答和构建行为与应用一致 · 迁移、环境变量、标志、cron/作业、队列、webhook、密钥已文档化且可部署 · 多端契约不会在 Web、后端、移动端、站点和文档之间发生漂移。

## 意图、范围与精度

确认差异实现了其声称的内容——将每项验收标准映射到代码或测试；没有依据支撑的声明属于 P1 真实性缺口——并标记范围蔓延（无关重构、捆绑依赖升级、掩盖变更的全量格式化）；建议拆分过大的 PR。输出前自查：每条发现都有文件:行号 + 修复方案，不与任何 gate 的职责重复，低置信度的风格意见合并为一行“细节建议”，以及任何不会影响发版决策的内容都应删除。

**置信度标签基于可观察证据，而非感觉：** `high` = 已复现、已跨调用链追踪，或关联到具名的失败输入或命令；`medium` = 从代码中阅读得出，未执行；`low` = 模式看起来有问题，但没有输入、调用路径或运行时状态可以证明。每项 P0/P1 发现都要标明标签；低置信度的安全怀疑仍可报告，但必须附上其标签；低置信度的*风格*观察应归入细节建议行。

## 红旗 — 停止

一旦发现自己在想以下任何一种情况，就重新运行你正准备跳过的 gate：

- “CI 是绿色的，所以没问题” — 从未实际覆盖已变更行为的 CI 不能作为证据。
- “这个差异很小” — 小差异同样可能触及认证和支付；每次都要运行 Instant-F 触发器。
- “这是我写的，我知道它能工作” — 切换到审查模式，寻找你的实现可能遗漏的问题。
- “作者很好地解释了意图” — 意图不是测试、回读或截图。
- “这很费工夫，向上取整给 B” — 付出的努力不会改变评分；证据才会。
- “跳过部署 gate，这只是文案改动” — 每次都必须在最后运行第 5 步。

## 输出结构

以一段 **简单说明（通俗易懂，面向 10 岁孩子）** 开头——用一段 10 岁孩子能理解的简单英语说明：是否通过，以及最主要的单一原因。然后：

```text
发现                 （按严重程度排列，包含证据 + 修复方案）
代码评分             （7 个维度 A-F + 总评、如有评分上限、原因、所需升级）
部署安全性           （8 个维度 + 结论）
提交脏状态           （7 个维度 + CLEAN | SUSPICIOUS | DIRTY）
待解决问题
验证                 （已检查 / 未检查）
SHIP GATE: hold | ship-with-caveats | ship — [一句话说明阻塞因素或注意事项]
```

如无发现，请明确说明，并指出任何残余风险或未运行的检查。不要虚构测试、截图、线上检查或部署状态。若修改评级，请说明发生了什么变化；若沉淀模式，请说明哪些做法有效；沉默 = 已接受。

## --threat-verify 模式

检查威胁模型中声明的缓解措施（ADR 威胁表、PLAN.md 风险部分，或自由格式的“Threat: X / Mitigation: Y”配对）是否确实已实现，并将每项分类为 CLOSED / OPEN / UNREGISTERED，写入 THREAT-REVIEW.md 表格。它不寻找新的漏洞——那是 OWASP 通道的职责。完整流程和输出格式位于 `references/threat-verify.md`：当调用方传入 `--threat-verify`，或要求你验证威胁缓解措施或检查威胁模型合规性时阅读它；普通审查时不要阅读。

## 边界

- 保留用户和其他代理的 WIP。不要暂存、还原或重写无关文件。
- 不要虚构你未运行的测试、截图、线上检查、部署状态或门禁结果。
- 未经用户明确确认，绝不要自动应用对认证、支付或数据迁移代码的修复；P0/P1 修复应先作为简报提出。
- 不要因格式化工具、类型检查器或已记录的项目规则已经约束的风格偏好而阻塞，也不要因为工作量或从未执行变更行为的 CI 而提高评级。
