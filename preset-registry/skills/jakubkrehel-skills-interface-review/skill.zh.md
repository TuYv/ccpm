# 变更审查

此技能审查的是变更，而不是界面。它会确定范围，将变更的文件扩展到它们影响的界面，并读取 diff 的两侧，对每个发现进行分类。

范围由它负责。领域规则属于 `better-*` 技能。严重性、合并、覆盖率、上限和结论属于 `better-interface`，此技能会将审查交给它。

正确性、测试、安全性和性能属于项目的一般代码审查。指出一次相关问题，然后继续。

## 变更，而不是代码库

作者想知道的是“我是否把它弄得更糟了？”。报告变更造成的问题，对于它仅仅触及的内容则基本保持沉默。指出三个预先存在的问题算是一种礼貌；指出三十个则是另一种审查，而且没人要求这样做。

先阅读变更，再形成判断。明确说明的意图决定哪些内容算是不完整，而粗略浏览 diff 会导致你报告的问题其实已经在下一个代码块中修复。

## 核心原则

### 1. 先确定变更范围

整个调用内容就是目标，因此 `/interface-review pr 482` 会审查拉取请求 482。[范围确定](scope-resolution.md)列出了已接受的目标，以及每种目标的确定方式。

未提供目标时，按以下顺序确定，并在首次匹配后停止：

1. `HEAD` 超前于 `git merge-base origin/<default-branch> HEAD`：审查该范围**加上**所有未提交的变更，并分别说明提交数量和未提交文件数量。
2. 工作树存在未提交变更：审查这些未提交的变更。
3. 两者皆否：没有可供审查的变更。按照**没有变更时，应先询问而不是自行臆造**停止。

顺序很重要。先检查工作树，否则一个无关的格式修改就会掩盖一个包含十二个提交的分支，而报告仍声称覆盖完整。

排除锁文件、快照、生成的输出、供应商代码和二进制文件，并说明排除了什么。排除后范围为空时，也会到达相同的结果，只是路径不同。

### 2. 没有变更时，应先询问而不是自行臆造

工作树干净，且没有任何提交超前于合并基线，意味着用户要求审查一个并不存在的变更。绝不要自行退回到 `HEAD~1..HEAD`。最后一个提交只是碰巧落在那里的内容，通常是一次合并，也通常是其他人的工作；对它的报告与对用户实际意图的报告无法区分。

说明你找到的仓库事实，然后提供可选路径并等待。[没有可供审查的内容](scope-resolution.md#nothing-to-review)列出了需要收集的事实：

- **最后一个提交**，即 `HEAD~1..HEAD`，以短 SHA 和主题行命名，让用户在选择之前看到他们将得到的内容。
- **由用户指定的目标**：`pr <n>`、分支、引用或范围，按照**先确定变更范围**中的规则确定。
- **整个仓库的界面审计**，这不是变更审查。将其作为仓库范围的审查交给 `better-interface`，不要包含此技能的范围块、状态或预先存在的问题部分。没有变更时，每个发现都是预先存在的，分类也就没有意义。

在询问之前，先检查当前分支是否有开放的拉取请求，并优先提供该拉取请求。其提交已经合并的分支意味着无需更改，但它的拉取请求仍然正是用户所指的内容。

如果排除之后范围为空，请说明排除了哪些文件，并以同样的方式询问。绝不要将对空内容的审查报告为 `Approve`。

### 3. 差异不是界面范围

变更的文件只是证据，而不是审查对象。它的**影响范围**是它所渲染到的界面，审查这些界面。

默认将影响范围扩展一跳：直接导入它的模块和直接调用它的代码。只有对于设计令牌、主题值和共享原语，才扩展第二跳，因为其中一行代码就可能影响整个产品。

最多审查五个消费者，顺序依据[范围解析](scope-resolution.md#expanding-to-consumers)中的规则排列，然后说明有多少个消费者没有展开。没有上限的全面扫描无法支撑其声称的覆盖范围，而不声明截止范围会让人误以为已经完整覆盖。

### 4. 阅读被删除的行

回归问题在变更后的状态中是不可见的。根据[已删除信号](removed-signals.md)阅读每个代码块中 `-` 一侧的内容。

信号只是线索，不是问题结论。只有当变更中没有任何内容替代某项被删除的内容时，该删除才构成回归，并且这一判断由领域技能负责。将每个未匹配的删除交给其所有者，只报告该技能确认的问题，并将其标记为 `Regression`。这会告诉作者，他们破坏了原本正常工作的内容，而不是犯了一个新的错误。

### 5. 对每个问题进行分类

为每个问题指定一种状态：

- `Introduced`：该变更引入了此问题。
- `Regression`：该变更削弱了之前正确的行为。
- `Pre-existing`：该问题存在于被触及的代码中，但并非由该变更造成。

根据差异触及的内容，而不是问题所在的文件来确定状态：变更从未触及的行，即使距离代码块只有三行，也属于 `Pre-existing`。必要时，针对基础引用进行确认：

```bash
git blame -L <line>,<line> "$BASE" -- path/to/file
```

将每个问题连同其状态一并提交给 `better-interface`，由它应用上限和裁决规则。

### 6. 要求变更符合其声明的意图

阅读拉取请求的标题和正文、关联的问题以及提交消息，然后审查该界面是否实现了它们所声称的内容。

这一步能够发现**不完整**的变更。界面范围审查无法发现这类问题，因为它检查的是已经存在的状态，而这里的重点恰恰是缺失的状态：

- 新增的变体、尺寸或主题只应用于部分状态，而不是全部状态：悬停、聚焦、激活、禁用、加载、选中。
- 新增了面向用户的字符串，却没有在项目维护的翻译目录中添加对应条目。
- 新增了组件，却没有空状态、加载状态、错误状态、禁用状态或窄宽度状态。
- 将控件添加到了一个界面，却没有添加到已经包含其同类控件的其他同级界面。

不要报告范围蔓延。变更是否做得太多是流程问题，而不是界面问题。

### 7. 将审查交给 `better-interface`

将范围区块、受影响的界面以及每个问题的状态交给 `better-interface`。它会将问题路由给领域技能，应用严重性级别，进行合并，执行上限并给出裁决。

如果 `better-interface` 不可用，报告解析后的范围和文件清单，将其标记为缺失的 skill 并停止。不要自行设定严重性等级、上限或结论。

### 8. 永远不要修改工作树

变更审查是只读的，包括检出操作。获取 pull request 引用；永远不要检出它们。`git fetch` 只会写入 `.git`，因此是允许的。`gh pr checkout`、`git checkout`、`git switch` 和 `git stash` 会重写作者正在打开的文件。它们会因本地编辑而失败，或丢弃这些编辑，因此永远不允许使用。

渲染验证是可选的。除非项目提供了低成本预览，或用户要求进行渲染审查，否则将视觉和运行时声明标记为 **Not verified**。如果满足条件，请使用隔离的工作树（`git worktree add /tmp/review-<n> refs/remotes/pr/<n>`），完成后将其移除。

## 完成之前

| 错误 | 修复 |
| --- | --- |
| 审查了分支中的一处额外编辑，而不是审查整个分支 | 在工作树之前检查 `merge-base`，并报告两个计数 |
| 因为没有变更而审查了最后一次提交 | 陈述事实，并提供最后一次提交、命名目标或仓库审计选项 |
| 审查了没有其使用方的代码块 | 向外扩展一层；对于 tokens 和 primitives 扩展两层，并说明跳过了什么 |
| 只阅读了差异的 `+` 一侧 | 在 `-` 一侧搜索被移除的可访问性、焦点、动效和文本信号 |
| 将等效替换报告为回归 | 将移除归给其负责人；只报告它所确认的内容 |
| 将一次移除报告为新的错误 | 将其状态标为 `Regression`，以便作者了解它之前是可用的 |
| 将代码块附近的一行标记为 `Introduced` | 根据差异实际触及的内容确定状态，并使用针对基础引用的 `git blame` 加以确认 |
| 为了审查而检出了 pull request | 获取该引用并在原位置审查 |
| 引用了在所审查引用上不存在的行号 | 针对范围块中指定的 head 引用进行引用 |
| 在此处重述严重性等级或发现上限 | 遵循 `better-interface` 的规定 |
| 在报告中加入正确性、测试或安全性发现 | 只命名一次该关注点，指向项目的代码审查，并将其删除 |

## 审查输出格式

以范围块开头：

| 字段 | 值 |
| --- | --- |
| 目标 | `branch`、`working`、`staged`、`pr 482` 或按原样输入的范围 |
| 基础引用 | `origin/main`，位于 `a1b2c3d` |
| 头引用 | `refs/remotes/pr/482`，位于 `e4f5g6h` |
| 提交 | 7 个已提交，2 个文件未提交 |
| 范围内文件 | 排除后为 12 个 |
| 已排除 | `pnpm-lock.yaml`、`src/__snapshots__/`：锁文件和快照 |
| 已扩展的界面 | `CheckoutPage`、`SettingsPanel`；另外 3 个 `Button` 使用方未展开 |

随后原样呈现覆盖范围表。变更范围内没有证据的领域标记为 `Not reviewed: no evidence in the change scope`，这是覆盖范围声明，而不是缺口。

然后列出发现，并为 **Classify every finding** 添加 `Status` 列：

| 严重性 | 领域 | 状态 | 位置 | 之前 | 之后 | 原因 |
| --- | --- | --- | --- | --- | --- | --- |
| HIGH | Accessibility | Regression | `src/Dialog.tsx:42` | 本次变更移除了 `aria-label="Close"` | 在仅包含图标的控件上恢复 `aria-label="Close"` | 关闭控件在本次变更之前具有可访问名称，而现在不再具有 |

如果没有 `Introduced` 或 `Regression` 发现，则省略该表，并写明“此变更中没有需要采取行动的界面发现。”

然后列出 `Pre-existing` 发现，最多三项，按严重程度从高到低排列，并明确说明这些问题不属于本次变更的责任范围。如果没有此类发现，则省略该部分。

| 严重程度 | 领域 | 位置 | 问题 |
| --- | --- | --- | --- |
| MEDIUM | 排版 | `src/Toolbar.tsx:7` | 数字徽章使用比例数字；早于本次变更已存在 |

数量上限和最终结论仅涵盖 `Introduced` 和 `Regression`。`Pre-existing` 发现不计入数量上限，因此触及遗留文件不会变成对整个文件的审查。它们也不影响最终结论，因此仅有既存问题的变更应判定为 `Approve`。

当仍有任何 `HIGH` 问题时，以 `Block` 结尾；否则以 `Approve` 结尾，同时将表格中剩余的发现作为待处理事项。当 `better-interface` 可用时，严重程度分级和数量上限由其提供。
