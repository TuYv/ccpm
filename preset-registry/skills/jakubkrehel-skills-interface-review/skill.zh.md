# 变更审查

此技能审查的是变更，而不是某个界面。它会确定范围，将变更的文件扩展到其所影响的界面，阅读 diff 的前后两侧，并对每一项发现进行分类。

范围就是它所负责的全部内容。领域规则属于 `better-*` 技能。严重程度、合并归类、覆盖范围、数量上限和结论属于 `better-interface`，此技能会将审查移交给它。

正确性、测试、安全性和性能属于项目的常规代码审查范畴。指出一次相关问题，然后继续。

## 审查变更，而非代码库

作者问的是“我的变更是否让情况变得更糟？”。应报告由变更导致的问题，对于它仅仅触及的问题则尽量保持沉默。指出三项预先存在的问题是一种善意；指出三十项则成了另一种审查，而且没人要求这样做。

先阅读变更，再对其形成看法。所声明的意图决定了哪些内容属于未完成，而草草浏览 diff 会让你对后续代码块已经修复的代码提出问题。

## 核心原则

### 1. 首先确定变更范围

整个调用就是目标，因此 `/interface-review pr 482` 会审查拉取请求 482。[范围解析](scope-resolution.md)说明了可接受的目标以及各类目标的解析方式。

如果未提供目标，则按以下顺序解析，并在首次匹配时停止：

1. `HEAD` 领先于 `git merge-base origin/<default-branch> HEAD`：该范围**加上**所有未提交的变更，并分别说明提交数量和未提交文件数量。
2. 工作树是脏的：未提交的变更。
3. 两者都不是：没有可供审查的变更。停止并询问，具体遵循**没有变更时，应询问而不是凭空指定**。

顺序很重要。如果先检查工作树，一处无关的格式调整就会遮蔽一个包含十二次提交的分支，而报告仍会声称已完整覆盖。

排除锁文件、快照、生成的输出、供应商代码和二进制文件，并说明排除了哪些内容。排除后范围为空，也会通过另一条路径得到相同的结果。

### 2. 没有变更时，应询问而不是凭空指定

如果工作树干净，并且没有任何内容领先于合并基准，则意味着用户要求审查的变更并不存在。绝不要自行回退到 `HEAD~1..HEAD`。最后一次提交只是恰好最新落地的内容，通常是一次合并，也常常是其他人的工作；对它生成的报告与针对用户原本意图生成的报告无法区分。

说明你发现的仓库事实，然后提供以下选项并等待回复。[没有可审查的内容](scope-resolution.md#nothing-to-review)列出了需要收集的事实：

- **最后一次提交**，即 `HEAD~1..HEAD`，通过短 SHA 和主题标明，以便用户在选择之前了解将会审查什么。
- **由用户指定的目标**：`pr <n>`、分支、ref 或范围，按照**首先确定变更范围**进行解析。
- **整个仓库的界面审计**，这不是变更审查。将其作为仓库范围的审查交给 `better-interface`，不包含此技能的范围块、状态或预先存在问题部分。没有变更时，每一项发现都是预先存在的，这种分类没有任何意义。

在询问之前，先检查当前分支是否存在打开的拉取请求，并优先提供该请求。如果某个分支的提交已经合入，那么比较结果不会显示任何变更，但它的拉取请求仍然恰好是用户所指的内容。

如果经过排除后范围变为空，请说明排除了哪些文件，并以同样的方式询问。绝不要将没有审查任何内容的结果报告为 `Approve`。

### 3. 差异不是界面

发生变更的文件只是证据，而不是审查对象。它的**影响范围**是其渲染到的所有界面的集合；应审查这些界面。

默认将影响范围向外扩展一跳：直接导入方和调用方。只有对于设计令牌、主题值和共享基础组件，才扩展第二跳，因为其中一行代码就能影响整个产品。

最多审查五个使用方，并按照[范围解析中的规则](scope-resolution.md#expanding-to-consumers)排序，然后说明有多少个使用方未进行扩展。没有边界的全面检查无法支撑其声称的覆盖范围，而不加说明的截断会让人误以为已经完整覆盖。

### 4. 阅读被删除的行

回归在变更后的状态中是不可见的。根据[删除信号](removed-signals.md)检查每个代码块中 `-` 一侧的内容。

信号只是线索，不是发现项。只有当变更中没有任何内容替代被删除的部分时，删除才构成回归，而这一判断应由对应领域的技能负责。将每个未被替代的删除项交给其负责人，只报告该技能确认的问题，并将其状态标记为 `Regression`。这会告诉作者，他们破坏了原本正常工作的内容，而不是犯了一个新错误。

### 5. 对每个发现项进行分类

为每个发现项指定一种状态：

- `Introduced`：由此次变更引入。
- `Regression`：此次变更削弱了此前正确的内容。
- `Pre-existing`：存在于被触及的代码中，但并非由此次变更导致。

应根据差异触及的内容而不是发现项所在的文件来确定状态：即使某一行距离变更块只有三行，只要此次变更从未触及它，它就是 `Pre-existing`。必要时对照基础引用进行确认：

```bash
git blame -L <line>,<line> "$BASE" -- path/to/file
```

将每个发现项连同其状态一并向上提交，并让 `better-interface` 应用其数量上限和结论规则。

### 6. 根据变更声明的意图对其进行审查

阅读拉取请求的标题和正文、关联的问题以及提交消息，然后审查界面是否实现了其中的声明。

这正是发现**不完整**变更的方式。界面审查无法发现此类问题，因为它检查的是已经存在的状态，而这里的重点是缺失的状态：

- 新的变体、尺寸或主题仅应用于部分状态，而非全部状态：悬停、聚焦、激活、禁用、加载中、已选择。
- 新增了面向用户的字符串，但项目维护的翻译目录中没有对应条目。
- 新组件缺少空状态、加载状态、错误状态、禁用状态或窄宽度状态。
- 某个控件添加到了一个界面，却没有添加到已经包含同类控件的其他同级界面。

不要报告范围蔓延。变更是否做得过多是流程问题，而不是界面问题。

### 7. 将审查交给 `better-interface`

将范围块、受影响的界面以及每个发现项的状态交给 `better-interface`。它会将问题路由到对应的领域技能、确定严重程度、进行整合、执行数量上限并给出结论。

如果 `better-interface` 不可用，请报告已解析的范围和文件清单，将其明确列为缺失的 Skill，然后停止。不要虚构严重程度等级、数量上限或结论。

### 8. 绝不修改工作树

变更审查是只读的，检出内容也不例外。可以获取拉取请求的 ref，但绝不能将其检出。`git fetch` 只写入 `.git`，因此允许使用。`gh pr checkout`、`git checkout`、`git switch` 和 `git stash` 会重写作者当前打开的文件。遇到本地编辑时，它们可能执行失败或丢弃这些编辑，因此绝不允许使用。

渲染验证是可选的。除非项目提供了成本较低的预览方式，或者用户要求进行渲染审查，否则应将视觉和运行时相关的结论标记为**未验证**。如果满足这些条件，请使用隔离的工作树（`git worktree add /tmp/review-<n> refs/remotes/pr/<n>`），并在完成后将其移除。

## 完成之前

| 错误 | 修复方式 |
| --- | --- |
| 审查了一处零散编辑，而不是整个分支 | 先于工作树检查 `merge-base`，并报告两者的数量 |
| 因为没有变更而审查了最后一次提交 | 说明事实，并建议审查最后一次提交、指定目标或进行仓库审计 |
| 审查了代码块变更，却没有审查其使用方 | 向外扩展一层；对于令牌和基础组件，扩展两层；并列出跳过的内容 |
| 只阅读了 diff 的 `+` 侧 | 在 `-` 侧搜索被移除的可访问性、焦点、动效和文本信号 |
| 将等效替代报告为回归 | 沿着移除项追踪到其所有者；只报告能够确认的问题 |
| 将移除项报告为新问题 | 将其状态标记为 `Regression`，让作者知道它之前可以正常工作 |
| 将代码块变更附近的某一行标记为 `Introduced` | 根据 diff 实际涉及的内容确定状态，并使用针对基础 ref 的 `git blame` 进行确认 |
| 为了审查而检出了拉取请求 | 获取相应 ref，并直接在原处审查 |
| 引用了所审查 ref 上不存在的行号 | 根据范围块中指定的 head ref 进行引用 |
| 在此处重述严重程度等级或问题数量上限 | 遵循 `better-interface` |
| 报告中包含正确性、测试或安全性问题 | 只提及一次该问题，指向项目的代码审查流程，然后不再展开 |

## 审查输出格式

以范围块开头：

| 字段 | 值 |
| --- | --- |
| 目标 | `branch`、`working`、`staged`、`pr 482` 或输入的范围 |
| 基础 ref | `origin/main`，位于 `a1b2c3d` |
| Head ref | `refs/remotes/pr/482`，位于 `e4f5g6h` |
| 提交 | 7 个已提交，2 个文件有未提交变更 |
| 范围内的文件 | 排除后共 12 个 |
| 已排除 | `pnpm-lock.yaml`、`src/__snapshots__/`：锁文件和快照 |
| 已扩展的界面 | `CheckoutPage`、`SettingsPanel`；另有 3 个 `Button` 使用方未扩展 |

随后原样给出覆盖范围表。对于变更范围内没有证据的领域，标记为 `Not reviewed: no evidence in the change scope`；这是一项覆盖范围说明，而不是缺陷。

接着列出发现的问题，并按照**对每个发现进行分类**的要求包含 `Status` 列：

| 严重程度 | 领域 | 状态 | 位置 | 之前 | 之后 | 原因 |
| --- | --- | --- | --- | --- | --- | --- |
| 高 | 可访问性 | 回归 | `src/Dialog.tsx:42` | 此次变更移除了 `aria-label="Close"` | 在仅包含图标的控件上恢复 `aria-label="Close"` | 此次变更之前，关闭控件具有可访问名称，但现在已不再具有 |

如果没有 `Introduced` 或 `Regression` 发现项，则省略表格，并注明“此变更中没有可采取行动的界面问题。”

然后列出 `Pre-existing` 发现项，最多三项，按严重程度从高到低排列，并明确说明这些问题不属于本次变更的责任范围。没有此类问题时，省略该部分。

| 严重程度 | 领域 | 位置 | 问题 |
| --- | --- | --- | --- |
| MEDIUM | 排版 | `src/Toolbar.tsx:7` | 数字徽标使用比例数字；此问题早于本次变更 |

数量上限和结论仅涵盖 `Introduced` 和 `Regression`。`Pre-existing` 发现项不计入数量上限，因此，改动遗留文件不能演变成对整个文件的审查。它们也不影响结论，因此，如果一项变更仅存在预先存在的发现项，结论应为 `Approve`。

如果仍存在任何 `HIGH` 级别的问题，则以 `Block` 结尾；否则以 `Approve` 结尾，并将其余发现项保留在表格中，作为待完成的工作。当 `better-interface` 可用时，严重程度分级和数量上限以其规定为准。
