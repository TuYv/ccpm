# 变更审查

此技能审查的是一项变更，而非一个界面。它会确定范围，将变更的文件扩展到其影响的界面，阅读 diff 的两侧，并对每项发现进行分类。

范围仅限于它负责的内容。领域规则属于 `better-*` 技能。严重程度、合并、覆盖范围、上限和结论属于 `better-interface`，此技能会将审查移交给它。

正确性、测试、安全性和性能属于项目的通用代码审查。将关注点指出一次，然后继续。

## 变更，而非代码库

作者想问的是“我是否把它变得更糟了？”。报告变更造成的问题，并且对于它仅仅触及的内容基本保持沉默。三项既有发现是礼节；三十项则是另一种审查，且是没人要求的那一种。

在形成观点之前先阅读变更。所声明的意图决定了哪些内容算是不完整，而粗略浏览的 diff 会产生关于下一个 hunk 已经修复的代码的发现。

## 核心原则

### 1. 先确定变更范围

整个调用就是目标，因此 `/interface-review pr 482` 会审查拉取请求 482。[范围确定](scope-resolution.md)列出了可接受的目标及其各自的确定方式。

未提供目标时，按以下顺序确定，并在首次匹配时停止：

1. `HEAD` 比 `git merge-base origin/<default-branch> HEAD` 靠前：该范围 **以及** 任何未提交的变更，其中提交数量和未提交文件数量应分别说明。
2. 工作树存在未提交变更：未提交的变更。
3. 两者皆非：没有可审查的变更。停止并按 **没有变更时，询问而非虚构一个** 的要求提问。

顺序很重要。先检查工作树，否则一处零散的格式调整会掩盖一个包含十二个提交的分支，而报告仍声称实现了完整覆盖。

排除锁文件、快照、生成的输出、供应商代码和二进制文件，并说明排除了哪些内容。排除后范围为空时，会通过不同的路径到达同一结果。

### 2. 没有变更时，询问而非虚构一个

干净的工作树且没有任何内容领先于合并基线，意味着用户要求审查一项不存在的变更。绝不要自行回退到 `HEAD~1..HEAD`。最后一个提交是恰好落地的任何内容，通常是一次合并，通常是其他人的工作，而对它的报告与针对用户意图的报告无法区分。

说明你发现的仓库事实，然后提供可选路径并等待。[无内容可审查](scope-resolution.md#nothing-to-review)列出了需要收集的事实：

- **最后一个提交**，`HEAD~1..HEAD`，以短 SHA 和主题命名，使用户能在选择前看到将获得的内容。
- **由他们指定的目标**：`pr <n>`、分支、ref 或范围，按 **先确定变更范围** 的方式确定。
- **整个仓库的界面审计**，这不是变更审查。将其作为仓库范围审查交给 `better-interface`，不使用此技能的范围区块、状态或既有内容部分。没有变更时，每项发现都是既有的，分类没有任何意义。

在询问之前，先检查当前分支上是否有未关闭的拉取请求，并优先提供它。提交已合并的分支会解析为没有变更，而其拉取请求仍然完全符合用户的意图。

如果在排除后范围变空，请说明排除了哪些文件，并以相同方式询问。绝不要将对空内容的审查报告为 `Approve`。

### 3. diff 不是界面

已变更的文件是证据，而不是审查对象。它的**影响范围**是它所渲染的界面集合；审查这些界面。

默认将影响范围扩展一跳：直接导入方和调用方。仅对设计令牌、主题值和共享原语扩展第二跳，因为那里的一行变更会影响整个产品。

最多审查五个消费者，按[范围解析中的规则](scope-resolution.md#expanding-to-consumers)排序，然后说明有多少未扩展。没有边界的扫描无法支撑其声称的覆盖范围，而未说明的截断会让人以为已经完整覆盖。

### 4. 阅读被删除的行

回归在变更后的状态中不可见。根据[删除信号](removed-signals.md)，阅读每个区块的 `-` 一侧。

信号是线索，不是发现。只有当变更中没有任何内容替代某项删除时，该删除才是回归，并且领域技能拥有这一判断权。将每项未匹配的删除路由给其负责人，只报告该技能确认的内容，并将其状态标记为 `Regression`。这会告诉作者，他们破坏了原本可用的内容，而非犯了新的错误。

### 5. 对每项发现进行分类

为每项发现赋予一种状态：

- `Introduced`：该变更造成了它。
- `Regression`：该变更削弱了先前正确的内容。
- `Pre-existing`：存在于被触及的代码中，但并非由该变更造成。

根据 diff 触及的内容而不是它所在的文件来确定状态：即使距某个区块仅三行，变更从未触及的行也是 `Pre-existing`。在重要时针对基准引用进行确认：

```bash
git blame -L <line>,<line> "$BASE" -- path/to/file
```

将每项发现连同其状态一并上报，并让 `better-interface` 应用其上限和结论规则。

### 6. 让变更符合其声明的意图

阅读拉取请求标题和正文、关联议题以及提交消息，然后审查该界面是否实现了它们所声称的内容。

这能发现**不完整的**变更。界面审查无法发现它，因为它检查的是已存在的状态，而这里的重点是缺失的状态：

- 新变体、尺寸或主题应用于某些状态但未应用于全部状态：悬停、聚焦、激活、禁用、加载、选中。
- 新的面向用户字符串在项目维护的翻译目录中没有对应条目。
- 新组件没有空状态、加载状态、错误状态、禁用状态或窄宽度状态。
- 控件被添加到一个界面，却没有添加到已经包含其同类控件的兄弟界面。

不要报告范围蔓延。变更是否做得过多是流程问题，而不是界面问题。

### 7. 将审查交给 `better-interface`

将范围块、受影响的界面以及每项发现的状态交给 `better-interface`。它会路由到领域技能，应用严重性级别，进行整合，执行上限，并给出结论。

如果 `better-interface` 不可用，请报告已解析的范围和文件清单，将其命名为缺失的 skill，然后停止。不要编造严重性等级、数量上限或结论。

### 8. 绝不修改工作树

变更审查是只读操作，包括检出操作。获取拉取请求引用；绝不要检出它们。`git fetch` 仅写入 `.git`，因此允许使用。`gh pr checkout`、`git checkout`、`git switch` 和 `git stash` 会重写作者当前打开的文件。它们会因本地编辑而失败，或者丢弃这些编辑，因此绝不允许使用。

渲染验证为可选项。除非项目提供低成本预览，或用户要求进行渲染审查，否则将视觉和运行时声明标记为 **未验证**。如果需要，请使用隔离的工作树（`git worktree add /tmp/review-<n> refs/remotes/pr/<n>`），并在完成后将其移除。

## 完成之前

| 错误 | 修正方法 |
| --- | --- |
| 审查了一个零散编辑，而不是分支 | 在工作树之前检查 `merge-base`，并报告两个计数 |
| 因为没有变更而审查了最后一次提交 | 陈述事实，并提供最后一次提交、指定目标或仓库审计 |
| 审查了代码块，却未审查其使用方 | 扩展一跳，对于 token 和基础组件扩展两跳，并说明跳过了什么 |
| 只阅读了 diff 的 `+` 一侧 | 在 `-` 一侧搜索被移除的无障碍、焦点、动效和文本信号 |
| 将等效替换报告为回归 | 将移除操作交由其所有者处理；仅报告它所确认的问题 |
| 将移除操作报告为新的错误 | 将其状态标记为 `Regression`，让作者知道它以前是可用的 |
| 将代码块附近的行标记为 `Introduced` | 根据 diff 实际触及的内容确定状态，并使用针对基础引用的 `git blame` 加以确认 |
| 为了审查而检出了拉取请求 | 获取该引用并原地审查 |
| 引用了在被审查引用中不存在的行号 | 根据范围块中指定的头部引用进行引用 |
| 在此重述了严重性等级或问题数量上限 | 交由 `better-interface` 处理 |
| 报告中包含正确性、测试或安全性发现 | 一次说明该问题，指向项目的代码审查，然后删除它 |

## 审查输出格式

以范围块开头：

| 字段 | 值 |
| --- | --- |
| 目标 | `branch`、`working`、`staged`、`pr 482`，或输入的范围 |
| 基础引用 | `origin/main` 位于 `a1b2c3d` |
| 头部引用 | `refs/remotes/pr/482` 位于 `e4f5g6h` |
| 提交 | 7 个已提交，2 个文件未提交 |
| 范围内文件 | 排除后为 12 个 |
| 已排除 | `pnpm-lock.yaml`、`src/__snapshots__/`：锁文件和快照 |
| 已扩展的界面 | `CheckoutPage`、`SettingsPanel`；另外 3 个 `Button` 使用方未扩展 |

覆盖表紧随其后，保持不变。变更范围内没有证据的领域应标记为 `Not reviewed: no evidence in the change scope`，这是一项覆盖声明，而非缺口。

然后列出发现，并根据 **对每项发现进行分类** 为其添加 `Status` 列：

| 严重性 | 领域 | 状态 | 位置 | 之前 | 之后 | 原因 |
| --- | --- | --- | --- | --- | --- | --- |
| HIGH | 无障碍 | Regression | `src/Dialog.tsx:42` | 此变更中移除了 `aria-label="Close"` | 在仅含图标的控件上恢复 `aria-label="Close"` | 关闭控件在此变更前具有可访问名称，现在不再具有 |

如果没有 `Introduced` 或 `Regression` 发现项，则省略该表格，并说明“此更改中没有可操作的界面问题。”

然后列出 `Pre-existing` 发现项，最多三项，按严重性从高到低排列，并明确说明这并非此次更改的责任。若没有此类发现项，则省略该部分。

| 严重性 | 领域 | 位置 | 问题 |
| --- | --- | --- | --- |
| MEDIUM | 排版 | `src/Toolbar.tsx:7` | 数字徽标使用比例数字；早于此次更改就已存在 |

上限和结论仅涵盖 `Introduced` 和 `Regression`。`Pre-existing` 发现项不计入上限，因此修改旧文件不能变成一次全文件审查。它们也不影响结论，因此如果某项更改的唯一发现项都是既有问题，则应为 `Approve`。

当仍存在任何 `HIGH` 问题时，以 `Block` 结束；否则以 `Approve` 结束，并将表格中剩余的发现项保留为待完成的工作。当 `better-interface` 可用时，严重性等级和上限均以其规定为准。
