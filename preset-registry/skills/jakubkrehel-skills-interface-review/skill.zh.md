# 评审变更，而不只是评审它留下的代码

diff 并不是一个表面。变更删除的行与新增的行同样重要，而它触及的文件也很少涵盖其影响的全部范围。

本技能只负责变更范围：解析目标、将变更文件扩展到受影响的界面、读取 diff 的两侧，以及对每条发现进行分类。领域规则属于 `better-*` 技能。模式、严重性、合并、覆盖范围、上限、输出格式和结论属于 `better-interface`，本技能会将评审交给它。不要在此处重复或覆盖它们的规则。

正确性、测试、安全性和性能属于项目的一般代码评审。每个问题只需指出一次，然后继续。

## 核心原则

### 1. 先解析变更范围

`better-interface` 负责模式解析；模式之后的所有内容都是目标，因此 `/interface-review quick pr 482` 表示对拉取请求 482 进行一次 `quick` 评审。[范围解析](scope-resolution.md)列出了接受的目标以及每个目标对应的命令。

未提供目标时，按以下顺序解析，并在首次匹配后停止：

1. `HEAD` 超前于 `git merge-base origin/<default-branch> HEAD`：评审该范围**加上**所有未提交的变更，并分别说明提交数量和未提交文件数量。
2. 工作树存在未提交变更：评审这些未提交的变更。
3. 两者都不满足：没有可评审的变更。根据原则 2 停止并询问用户。

顺序很重要：先检查工作树会让一次无关的格式化编辑掩盖一个包含十二个提交的分支，而报告仍声称覆盖完整范围。

排除锁文件、快照、生成的输出、引入的第三方代码和二进制文件，并说明排除了什么。如果排除后范围为空，这只是通过另一条路径到达原则 2：列出被排除的文件并询问用户。

### 2. 没有变更时应询问，而不是自行编造

如果工作树干净，且没有任何内容超前于 merge base，说明用户要求评审一个并不存在的变更。绝不要自行退回到 `HEAD~1..HEAD`。最后一次提交只是恰好落地的内容——通常可能是一次合并，也可能是其他人的工作——而针对它生成的报告无法与针对用户实际意图生成的报告区分开来。

说明你发现的仓库事实，然后提供可选路径并等待用户选择。[没有可评审内容](scope-resolution.md#nothing-to-review)列出了相关命令：

- **最后一次提交**，即 `HEAD~1..HEAD`，同时列出短 SHA 和主题，以便用户在选择前了解将要得到的内容。
- **用户指定的目标**：`pr <n>`、分支、引用或范围，按照原则 1 解析。
- **整个仓库的界面审计**，这不是变更评审。将其作为仓库范围评审交给 `better-interface`，并去掉本技能的范围区块、状态和预先存在问题区块：没有变更时，每个发现都是预先存在的问题，这种分类不携带任何信息。

在提问之前，先检查当前分支上是否存在未合并的 pull request；如果存在，优先提供它。一个其提交已经落入基分支的分支会被解析为无变更，但它对应的 pull request 仍然正是用户想要的内容。

排除后为空的范围，只是以另一种方式到达了相同情况。说明排除了哪些文件，并以相同方式提问，而不是将对空内容的审查报告为 `Approve`。

### 3. Diff 不是界面范围

变更文件只是证据，而不是审查对象。它所渲染到的界面集合才是其**影响范围**；请审查这些界面。

默认将影响范围扩展一跳：直接导入者和调用者。只有对于设计令牌、主题值和共享原语，才扩展第二跳，因为其中一行代码就可能影响整个产品。

最多审查五个消费者，按 [范围解析](scope-resolution.md#expanding-to-consumers) 中的规则排序，并说明有多少个消费者未展开。无界限的扫描会产生你无法支撑的覆盖率声明；不说明截止范围则会让报告看起来完整，实际却并不完整。

### 4. 阅读被删除的行

回归在变更后的状态中不可见。根据[已删除信号](removed-signals.md)，阅读每个代码块中 `-` 一侧的内容。

信号只是线索，不是发现。只有当变更中没有任何内容替代某项被删除的内容时，该删除才构成回归，而这一判断由领域 skill 负责。将每个未匹配的删除交给其所属方，并且只报告该 skill 确认的内容。然后将其状态标记为 `Regression`，这会告诉作者他们破坏了原本正常工作的内容，而不是犯了一个新的错误。

### 5. 为每个发现分类

为每个发现指定一个状态：

- `Introduced`：该变更创建了它。
- `Regression`：该变更削弱了此前正确的内容。
- `Pre-existing`：它存在于被触及的代码中，但并非由该变更导致。

根据 diff 触及的内容，而不是根据发现所在的文件来确定状态：变更从未触及的行，即使距离某个代码块只有三行，也应标记为 `Pre-existing`。必要时对照基准引用进行确认：

```bash
git blame -L <line>,<line> "$BASE" -- path/to/file
```

将每个发现连同其状态一并上报，并让 `better-interface` 应用其上限和裁决规则。

### 6. 让变更符合其声明的意图

阅读 pull request 的标题和正文、关联的 issue 以及提交消息，然后审查该界面是否实现了它们所声称的内容。

这会发现**不完整的**变更，而界面审查无法发现这类问题，因为界面审查检查的是存在时的状态，而这里的问题恰恰在于这些状态缺失：

- 新增的变体、尺寸或主题只应用于部分状态，而不是全部状态：hover、focus、active、disabled、loading、selected。
- 新增了面向用户的字符串，但项目维护的翻译目录中没有对应条目。
- 新增了组件，但没有空、加载、错误、禁用或窄宽度状态。
- 将控件添加到一个界面，却没有添加到已经包含其同类控件的其他同级界面。

不要报告范围蔓延。变更是否做得太多是流程问题，而不是界面问题。

### 7. 将审查交给 `better-interface`

掌握范围、受影响的界面，以及差异的正反两侧后，将审查连同范围块和每项发现的状态交给 `better-interface`。它会将问题路由到相应的领域技能，应用严重性级别，进行汇总，执行上限，并给出结论，其中包括其 **Change-Scoped Reviews** 部分下的变更范围规则。

如果 `better-interface` 不可用，请报告已解析的范围和文件清单，指出缺失的技能，并停止。不要自行编造严重性级别、上限或结论。

### 8. 绝不修改工作树

变更审查是只读的，包括检出操作。获取 pull request 引用；绝不要检出它们。`git fetch` 只会写入 `.git`，因此是允许的。`gh pr checkout`、`git checkout`、`git switch` 和 `git stash` 会重写作者当前打开的文件，可能因本地编辑而失败或丢弃这些编辑，因此在任何模式下都绝不允许使用。

渲染验证需要显式选择：除非项目提供低成本预览，或用户要求进行渲染审查，否则将视觉和运行时声明标记为 **Not verified**。如果满足条件，请使用隔离的工作树（`git worktree add /tmp/review-<n> refs/remotes/pr/<n>`），并在完成后将其移除。这样可以保持作者的工作树不变，而检出操作无法做到这一点，因此检出不是这里的替代方案。

## 常见错误

| 错误 | 修复方式 |
| --- | --- |
| 审查了分支中的一次无关编辑，而不是整个分支 | 先于工作树检查 `merge-base`，并报告两者的计数 |
| 因为没有变更就审查了最后一次提交 | 陈述仓库事实，并提供最后一次提交、命名目标或仓库审计选项 |
| 审查了代码块，却没有审查其使用者 | 扩展一跳；对于 tokens 和 primitives 扩展两跳，并说明跳过了什么 |
| 只阅读差异中 `+` 的一侧 | 搜索 `-` 一侧，查找被移除的无障碍、焦点、动效和文本信号 |
| 将等价替换报告为回归 | 将移除操作路由给负责的技能，只报告该技能确认的问题 |
| 将移除操作报告为新错误 | 将其状态标记为 `Regression`，让作者知道它以前是可用的 |
| 将代码块附近的一行标记为 `Introduced` | 根据差异实际触及的内容确定状态，并使用针对基础引用的 `git blame` 进行确认 |
| 为了审查 pull request 而将其检出 | 获取该引用，并在原地审查 |
| 引用了已审查引用中不存在的行号 | 根据范围块中指定的 head 引用进行引用 |
| 在此处复述模式、严重性、上限、输出格式或结论 | 交由 `better-interface` 处理 |
| 在报告中提出正确性、测试或安全性问题 | 只指出一次该关注点，指向项目的代码审查，并删除该问题 |

## 审查输出格式

`better-interface` 负责格式，包括其 **Change-Scoped Reviews** 部分下的四项变更范围补充内容。按原样遵循，不要在此处添加任何内容。

此技能提供范围块：

| 字段 | 值 |
| --- | --- |
| 目标 | `branch`、`working`、`staged`、`pr 482` 或输入的范围 |
| 基础引用 | `origin/main` 位于 `a1b2c3d` |
| 头部引用 | `refs/remotes/pr/482` 位于 `e4f5g6h` |
| 提交 | 7 个已提交，2 个文件未提交 |
| 范围内文件 | 排除后共 12 个 |
| 已排除 | `pnpm-lock.yaml`、`src/__snapshots__/`：锁文件和快照 |
| 已扩展的界面 | `CheckoutPage`、`SettingsPanel`；另外 3 个 `Button` 使用者未扩展 |

此外，按照原则 5，为每项发现附上状态。

在 `better-interface` 的 **Verification** 下，列出确切的 `git` 和 `gh` 命令及其结果，包括对 `.git` 的每一次写入（fetch、deepen、`set-head`、worktree），这样原则 8 中的只读声明才可审计。
