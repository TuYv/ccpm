# 产能规划器

将人员数量转换为可实际承诺的工时。大多数产能计划都以同样的方式失败：
它们计算人数而不是实际交付工时，忽略上手周期，并调整供给以适应路线图，而不是反过来。
此技能独立计算有效产能，将其与经过风险调整的需求进行匹配，
并公布取舍线。

## 何时使用此技能

- **季度规划** — 决定团队未来 90 天内可以承诺完成哪些工作
- **检验路线图** — 利益相关者有一份工作清单，并想知道它是否能被纳入计划
- **提出招聘申请** — 以工时和金额量化结构性缺口
- **招聘、外包还是推迟** — 选择如何弥补产能缺口
- **季度中期重新规划** — 消耗速率出现偏差，需要重新协商承诺
- **入职影响** — 模拟三名新员工本季度实际能够交付的工作量

## 此技能需要的输入

- 团队名册：姓名、职能、资历、FTE、任职月数
- 已知缺勤：已预订的 PTO 天数、每人的值班轮换周数
- 管理开销估算：会议负担和非交付开销占比
- 该周期内的工作日数和每日工时
- 候选承诺项，以及各自的职能、工时估算、置信区间和优先级
- 对于场景分析：各季度的需求曲线、薪资/承包商费率、开始日期

## 首先澄清

生成前，请确认以下输入。如果有任何一项未知或含糊，请提问——不要假设：

- [ ] **这是供给问题还是需求问题？** — 确定招聘申请的规模与检验路线图需要使用不同的脚本，并会生成不同的产物
- [ ] **哪些人计入交付产能？** — 将经理、技术负责人或尚未填补的职位按完整 FTE 计入，会使结果产生 10-40% 的变化
- [ ] **这些估算是否已经过风险调整？** — 重复应用置信度膨胀会将需求高估 40% 以上；完全不应用则会以相同幅度低估需求
- [ ] **缓冲是根据历史情况还是主观意图设定的？** — 预留给计划外工作的余量是影响取舍线的最大单一杠杆

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草”，则继续执行，并在产物顶部列出你的假设。

## 工作流

### 工作流 1 — 建模有效产能

确定团队实际能够交付的工作量，并在任何人查看
路线图之前完成计算。始终先运行此工作流。

1. 创建团队名册：每人一个条目，包含实际 FTE 和任职月数。对于尚未入职的人员，使用负数 `tenure_months`。
2. 获取**已预订的** PTO，而不是平均 PTO。Q3 和 Q4 并不是平均水平的季度。
3. 根据日历审计而非记忆设置 `meeting_load_pct`——两者之间的差距通常为 5-10 个百分点。
4. 运行模型，并根据 `references/capacity-benchmarks.md` 中的合理区间检查有效工时比率：低于 45% 表明结构已失效，高于 80% 则是不切实际。
5. 记录各职能的有效工时——这些是工作流 2 的输入。

```bash
python3 business-operations/capacity-planner/scripts/capacity_model.py \
  --input business-operations/capacity-planner/assets/sample_team.json \
  --format text
```

### 工作流 2 — 确定截断线

按优先级顺序将经过风险调整的需求与容量进行匹配，并报告无法容纳的内容。

1. 列出每个候选承诺，包括专业领域、原始估算、置信区间和优先级。将任何已经对外承诺的事项标记为 `"committed": true`。
2. 根据过去三个季度实际发生的非计划工时设置缓冲比例。默认为 20%；如果团队负责面向客户的事故响应，则使用 30%。
3. 运行缺口分析并查看截断线，而不是总数。
4. 在**本周**升级处理截断线以上的所有 `committed: true` 事项——一个你已经知道无法兑现的承诺需要沟通，而不是作为风险记录。
5. 将截断线以下的事项列表与计划一同发布。该列表就是交付物。

```bash
python3 business-operations/capacity-planner/scripts/commitment_gap.py \
  --input business-operations/capacity-planner/assets/sample_commitments.json \
  --buffer-pct 20 --format text
```

### 工作流 3 — 比较招聘、外包和延期

仅适用于截断线以下的工作。绝不要使用情景分析来论证一个容量无法容纳的计划。

1. 按季度构建规划周期内的需求曲线——至少覆盖四个季度；如果缺口看起来是结构性的，则覆盖八个季度。
2. 为每个现实可行的选项定义一个情景，其中包括将延期作为零成本基准情景。
3. 运行比较并查看四个维度，而不只是成本：缓解所需时间、每交付工时成本、可逆性和知识留存。
4. 根据 `references/planning-methods.md` 中的决策规则对结果进行合理性检查。四个季度的规划周期会系统性地偏向外包，因为招聘与外包的成本交叉点出现在第 9-14 个月。
5. 在建议中附上其前置时间。“招聘两名工程师”缓解的是下下个季度，而不是本季度。

```bash
python3 business-operations/capacity-planner/scripts/scenario_compare.py \
  --input business-operations/capacity-planner/assets/sample_scenarios.json \
  --format json
```

## 决策框架

### 从总工时转换为有效工时 [已验证]

一名已完全进入状态的 IC 在一个 63 天季度内的规划数据：

| 层级 | 工时 | 累计总计 |
|-------|-------|---------------|
| 总工时（63 天 x 8 小时） | 504 | 504 |
| 已安排的 PTO（5 天） | -40 | 464 |
| 值班（2 周 @ 损耗 40%） | -32 | 432 |
| 会议 + 管理开销（20%） | -86 | 346 |
| 非计划工作缓冲（20%） | -69 | **277 个可承诺工时** |

**每名已完全进入状态的 IC 每季度使用 270-300 个可承诺工时。** 一名技术负责人可交付 120-160 个工时；一名工程经理可交付 0 个工时。一名在季度第一天入职的中级员工可交付 90-110 个工时。

### 哪种手段可以弥补缺口

| 缺口大小 | 是否持续超过 4 个季度？ | 手段 | 缓解所需时间 |
|----------|----------------------------|-------|----------------|
| 任意 | — | **削减范围** [已验证] | 立即 |
| 低于 10% | 否 | **减少管理开销** [已验证] | 2-4 周 |
| 10-30% | 否 | **延期**，并指定后续时间段 | 立即 |
| 10-40% | 否，工作可拆分 | **外包** [推荐] | 1-3 周 |
| 任意 | 是 | **招聘** [已验证可解决结构性缺口] | 5-8 个月 |
| 较大 | 是，且在 2 个季度内需要 | **招聘 + 外包过渡** [推荐] | 1-3 周，在 Q+2 时交接 |

请按以下顺序考虑这些措施。降低管理开销是投资回报率最高的杠杆，却几乎总是被忽略，因为它不属于任何人的职责——对于一个十人团队，恢复 8% 的有效工时，价值接近一个 FTE，而且无需任何成本。

桥接模式的失败情形是交接始终没有发生，承包人员最终以承包费率长期留任。应将交接日期和知识转移产物直接写入合同。

### 按置信度放大估算 [建议]

| 置信度 | 定义 | 乘数 |
|-----------|------------|-----------|
| 高 | 团队交付过几乎完全相同的项目；设计已完成 | 1.15x |
| 中 | 已理解整体形态；未知因素已知 | 1.40x |
| 低 | 新领域、新依赖项，或设计尚未开始 | 1.90x |

两个季度后，根据你自己的 `actual / original estimate` 历史数据重新校准。对于“中”等置信度，大多数团队的实际值落在 1.3 到 1.6 之间。切勿在“低”置信度下作出对外承诺——要么先降低风险，使其达到中等置信度，要么按放大后的数值承诺日期。

### 利用率区间 [已验证]

| 计划利用率 | 表现 |
|--------------------|-----------|
| 低于 60% | 承诺不足；空余空间会被低价值工作填满 |
| 70-80% | **目标。** 可在不延误承诺事项的情况下消化突发事件 |
| 80-90% | 任何意外都会导致某项承诺受影响 |
| 高于 90% | 排队效应占据主导；周期时间呈非线性上升 |

这是排队论，而非积极性问题。按 95% 的利用率进行规划，即使每项估算都准确无误，也必然导致延期交付。

## 反模式

### 将人员数量等同于产能
**错误：** 用 FTE 数量乘以工作时数，并将结果称为产能——8 名工程师 x 504 小时 = 4,032 个可用小时。
**原因：** 这是唯一容易获得的数字，也是财务和管理层已经在追踪的数字。有效工时则需要进行尚未有人建立的度量。
**正确做法：** 每次都执行从总工时到有效工时的逐层扣减计算。真实数字是总工时的 50-70%，而两者之间的差距正是所有过度承诺产生的地方。如果没有实测的管理开销数据，就使用 60%，并从本季度开始测量。

### 通过招聘解决本季度的问题
**错误：** 通过开放招聘职位来应对产能缺口，然后在规划时假定新员工能在当前周期内作出贡献。
**原因：** 招聘是审批路径最清晰的杠杆——申请增加人员编制是大家熟悉的对话，而“我们要砍掉三个路线图事项”则不然。
**正确做法：** 招聘最早也只能缓解下下个季度的问题：填补职位需要 8-14 周，之后还需要 3-6 个月才能达到正常产出水平。通过缩减范围或使用承包人员来弥补当前缺口；应根据连续三个季度负载高于 85% 的趋势启动招聘，而不是因为某一个季度表现不佳就招聘。让新员工加入一个已经超负荷的团队，还会使其达到正常产出水平的速度再慢 20%，因为没有人有时间帮助任何人完成入职适应。

### 完美契合的计划
**错误：** 提交一份需求与供给仅相差几个百分点、且取舍线以下没有任何事项的产能计划。
**原因：** 在规划期间，估算会被悄悄下调，直到路线图与团队产能相匹配；或者需求清单会在会议前被截短，使被删除的内容根本不会出现。
**正确做法：** 将完美契合视为流程失败的证据，并找出究竟是哪个数字被改动了。每一份诚实的计划都有一条清晰可见的取舍线，而线下事项清单是整个过程产出的最有用工件——它让利益相关者能够权衡优先级，而不是到了第 10 周才发现他们的事项从一开始就不可能完成。

### 将缓冲区当作乐观程度调节器
**错误：** 为了让计划看起来可行，随意设置计划外工作预留比例——当路线图无法纳入计划时，就将其从 20% 降至 10%。
**原因：** 缓冲区看起来像闲置容量，而闲置容量看起来像是可以通过协商削减的东西。会议室里没有人为它据理力争。
**正确做法：** 根据过去三个季度实际发生的计划外工作时数来设置缓冲区；它是一项测量值，而不是安全垫。如果上个季度连续两周的计划外工作超出了缓冲区，正确的做法是提高它。削减缓冲区并不会创造容量——只会将缺口推迟到第 10 周，而届时弥补缺口的成本会更高。

## 文件

| 文件 | 用途 |
|------|---------|
| `scripts/capacity_model.py` | 将人员名册、间接开销和上手周期转换为每人及各专业领域的有效工时 |
| `scripts/commitment_gap.py` | 根据置信度放大估算值，按优先级顺序填充分配容量，并报告取舍分界线 |
| `scripts/scenario_compare.py` | 预测一定周期内招聘、外包和延期场景，并计算每个已交付工时的成本 |
| `references/capacity-benchmarks.md` | 按角色划分的有效工时比例、上手曲线、值班和会议负荷、利用率区间，以及招聘与外包的经济性对比 |
| `references/planning-methods.md` | 规划顺序、需求预测、弥合缺口的手段、治理节奏，以及应对利益相关者质疑的方法 |
| `assets/capacity-plan-template.md` | 季度容量计划，包含取舍分界线、缺口应对选项、风险和每周跟踪 |
| `assets/sample_team.json` | 包含七人的人员名册，涵盖处于上手阶段的新员工、兼职人员和多个专业领域 |
| `assets/sample_commitments.json` | 九项承诺，与示例人员名册经 `capacity_model.py` 计算得出的容量相对应 |
| `assets/sample_scenarios.json` | 四个季度的需求曲线，包含招聘、外包和延期场景 |
