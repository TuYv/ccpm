# 诊断

一套应对棘手问题的纪律。只有在有明确理由时才跳过阶段。

在探索代码库时，使用项目领域术语表来建立相关模块的清晰心智模型，并检查你正在修改区域内的 ADR。

## 第一阶段 — 构建反馈循环

**这就是这个技能。** 其他都是机械性的。如果你有一个快速、确定性的、可由 agent 执行的通过/失败信号用于定位 bug，你就能找到原因——二分、假设验证和插桩都只是对该信号进行消耗。如果没有这个信号，再怎么盯着代码看也无济于事。

在这里投入不成比例地更多精力。**要有进取心。要有创意。拒绝放弃。**

### 构建方法——大致按此顺序尝试

1. 在能触及 bug 的任何缝隙上使用**失败测试**——单元、集成、e2e。
2. 针对运行中的开发服务器执行 **Curl / HTTP 脚本**。
3. 使用固定输入的 **CLI 调用**，将 stdout 与已知正确快照进行差异比对。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并对 DOM/console/network 断言。
5. **回放捕获到的追踪。** 将真实的网络请求 / payload / 事件日志保存到磁盘；在隔离的代码路径中重放它。
6. **一次性试验平台。** 启动系统最小子集（一个服务、mock 依赖），用单次函数调用覆盖触发 bug 的代码路径。
7. **属性 / 模糊测试循环。** 如果 bug 是“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分试验平台。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”，以便你能执行 `git bisect run`。
9. **差异循环。** 用同一输入跑旧版本与新版本（或两套配置）并对比输出差异。
10. **HITL bash 脚本。** 最后手段。如果必须有人点击，用 `scripts/hitl-loop.template.sh` 驱动 _他们_，以使循环仍然有结构。捕获的输出会反馈给你。

建立正确的反馈循环，bug 就修好了 90%。

### 迭代优化循环本身

把这个循环当作一个产品来对待。一旦你有了一个循环，问自己：

- 我能让它更快吗？（缓存初始化、跳过无关初始化、缩小测试范围。）
- 我能让信号更准确吗？（断言具体症状，而不是“没有崩溃”。）
- 我能让它更确定吗？（锁定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

一个 30 秒的 flaky 循环几乎不比没有循环好。一个 2 秒的确定性循环是调试超能力。

### 非确定性 bug

目标不是得到干净的复现，而是**提高复现率**。将触发动作循环 100 次、并行化、加压、缩小时序窗口、注入 sleep。50% 的 flaky bug 是可调试的；1% 则不是——继续提高到可调试为止。

### 当你确实无法构建循环时

停下来明确说明。列出你尝试过的内容。向用户请求：(a) 任何能复现问题的环境访问权限，(b) 一份捕获到的工件（HAR 文件、日志转储、core dump、带时间戳的屏幕录制），或 (c) 临时添加生产环境插桩的许可。没有循环，不要继续猜测。

在你确信有一个可用的循环之前，不要进入第二阶段。

## 第二阶段 — 复现

运行该循环。看着 bug 出现。

确认：

- [ ] 循环产生的是用户描述的故障模式，而不是“邻近但不同”的故障。错误的 bug 会带来错误的修复。
- [ ] 该故障在多次运行中可复现（或者对于非确定性 bug，至少在足够高的复现率下可复现，以便进行调试）。
- [ ] 你已捕获到精确症状（错误信息、错误输出、慢速响应），以便后续阶段验证修复是否真正解决了它。

没有复现到 bug 前不要继续。

## 第三阶段 — 假设

在测试前先生成 **3–5 个按优先级排列的假设**。单一假设生成依赖第一个看似合理的想法。

每个假设都必须是**可证伪**的：陈述其可验证的预测。

> 格式：“如果 `<X>` 是根因，那么改变 `<Y>` 将使 bug 消失 / 改变 `<Z>` 会让它变得更糟。”

如果你无法陈述预测，那这个假设只是直觉——要么放弃，要么进一步细化。

**在测试前先把排序后的列表展示给用户。** 他们常常有能即时重排的领域知识（“我们刚部署了 #3 的变更”），或已排除掉的假设。这个检查点很廉价，能省很多时间。不要被这个步骤阻塞——如果用户离线，继续按你的排序执行。

## 第四阶段 — 插桩

每个探针都必须对应第三阶段某个具体预测。**一次只改一个变量。**

工具偏好：

1. 如果环境支持，优先使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在区分各假设的边界处使用**有针对性的日志**。
3. 永远不要“记录所有内容再 grep”。

**为每条调试日志加上唯一前缀**，例如 `[DEBUG-a4f2]`。到最后清理时就只需一次 grep。未打标签的日志保留；带标签的日志会被清除。

**性能分支。** 对于性能回归，日志通常不可靠。应先建立基线测量（计时脚手架、`performance.now()`、分析器、查询计划），然后再二分。先测量，后修复。

## 第五阶段 — 修复 + 回归测试

在修复前先写回归测试，但前提是**存在正确的切入点**。

正确的切入点应是：测试在调用点处覆盖**真实 bug 模式**。如果唯一可用的切入点过于浅层（只有单一调用方测试，而 bug 需要多个调用方；无法复现触发链路的单元测试），那里的回归测试只会带来虚假信心。

**如果不存在正确切入点，本身就是一个发现。** 记录下来。代码库架构正在阻止你把这个 bug 锁定。把这点标记到下一阶段。

如果存在正确切入点：

1. 将最小化复现转化为该切入点上的失败测试。
2. 观察其失败。
3. 应用修复。
4. 观察其通过。
5. 以原始（未最小化）场景重新运行第一阶段反馈循环。

## 第六阶段 — 清理 + 复盘

在宣布完成前必需：

- [ ] 原始复现不再复现（重跑第一阶段循环）
- [ ] 回归测试通过（或记录了缺少切入点）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到清晰标记的调试位置）
- [ ] 正确的假设已写入提交 / PR 描述——让下一个调试者受益

**然后再问：是什么能避免这次 bug？** 如果答案涉及架构变更（缺少良好的测试切入点、调用链缠结、隐藏耦合），在修复完成后再移交给 `/improve-codebase-architecture` 技能并附上具体细节——要在修复后再给建议，因为你现在掌握的信息比开始时更多。
