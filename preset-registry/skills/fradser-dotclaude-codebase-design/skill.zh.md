# 代码库设计

设计**深模块**：在简洁的接口背后提供大量行为，将其置于清晰的接缝处，并且能够通过该接口进行测试。凡是设计或重构代码，都应使用这套语言和这些原则。目标是为调用者提供杠杆效应，为维护者提供局部性，并为所有人提供可测试性。

## 术语表

必须严格使用这些术语——不要替换为“组件”“服务”“API”或“边界”。统一的语言正是关键所在。

**模块**——任何具有接口和实现的事物。刻意不限定规模：它可以是函数、类、包，也可以是跨层切片。_避免使用_：单元、组件、服务。

**接口**——调用者为了正确使用模块而必须了解的一切：不仅包括类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。_避免使用_：API、签名（过于狭窄——它们仅指类型层面的表面）。

**实现**——模块内部的内容，即其代码主体。它与**适配器**不同：某个事物可以是实现很大的小型适配器（Postgres 仓库），也可以是实现很小的大型适配器（内存假实现）。讨论重点是接缝时使用“适配器”；否则使用“实现”。

**深度**——接口所提供的杠杆效应：调用者（或测试）每学习一个单位的接口，就能运用多少行为。当大量行为位于小型接口背后时，模块是**深的**；当接口几乎与实现一样复杂时，模块是**浅的**。

**接缝** _(Michael Feathers)_——一个无需在该处进行编辑就能改变行为的位置；模块接口所在的*位置*。接缝应置于何处本身就是一项设计决策，与接缝背后放置什么相互独立。_避免使用_：边界（它与 DDD 的限界上下文含义重叠）。

**适配器**——在接缝处满足某个接口的具体事物。它描述的是*角色*（填补什么位置），而不是实质（内部是什么）。

**杠杆效应**——调用者从深度中获得的收益：每学习一个单位的接口，就能获得更多能力。一份实现可以在 N 个调用点和 M 个测试中反复产生回报。

**局部性**——维护者从深度中获得的收益：变更、缺陷、知识和验证集中在一个位置，而不是分散到各个调用者中。一次修复，处处生效。

## 关键要求：严格使用这些词汇

使用**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆效应**、**局部性**——绝不要使用“组件”“服务”“API”或“边界”。统一的语言正是此技能的关键所在；替换术语会破坏其他所有技能所依赖的共享模型。

## 深模块与浅模块

**深模块** = 小型接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块** = 大型接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时，请思考：

- 能否减少方法的数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂性？

## 原则

- **深度是接口的属性，而非实现的属性。** 深模块在内部可以由小型、可模拟、可替换的部件组成——只不过它们不属于接口的一部分。模块既可以有**内部接缝**（对其实现私有，由其自身测试使用），也可以在接口处有**外部接缝**。
- **删除测试。** 设想删除这个模块。如果复杂性随之消失，那么它只是一个透传层。如果复杂性重新出现在 N 个调用方中，那么它就发挥了应有的作用。
- **接口就是测试面。** 调用方和测试会跨越同一个接缝。如果你想越过接口进行测试，那么这个模块的形态很可能不正确。
- **一个适配器意味着假想的接缝，两个适配器意味着真实的接缝。** 除非确实有某些东西会跨接缝发生变化，否则不要引入接缝。

## 面向可测试性的设计

良好的接口能让测试自然而然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **较小的表面积。** 方法越少 = 所需测试越少。参数越少 = 测试设置越简单。

## 关系

- 一个**模块**只有一个**接口**（即它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，以其**接口**为参照进行衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**处，并满足**接口**。
- **深度**为调用方带来**杠杆效应**，为维护者带来**局部性**。

## 不采用的表述方式

- **将深度视为实现代码行数与接口代码行数之比**（Ousterhout）：这会鼓励用冗余代码填充实现。我们改用“深度即杠杆效应”的定义。
- **将“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：这种理解过于狭窄——这里的接口包括调用方必须了解的每一项事实。
- **“边界”**：该术语与 DDD 的限界上下文含义重叠。应使用**接缝**或**接口**。
