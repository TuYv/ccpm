# 供应商管理

涵盖从筛选到退出的整个供应商生命周期。该领域主要存在两种失败：
按支出而非影响范围对供应商进行分级，以及因错过通知截止日期而丧失
续约时的所有谈判筹码。本技能旨在防止这两种情况发生。

## 何时使用本技能

- **筛选供应商**，并需要一份经得起审查的评分卡
- **续约临近**，需要在通知截止日期之前确定该日期
- **审查供应商组合**，评估集中度、风险等级覆盖情况和整合机会
- **准备业务审查**，包括 SLA 履约情况和应付抵扣额
- **供应商表现不佳**，需要基于趋势而非个别事例构建论据
- **规划退出**，并需要确保执行顺序正确

## 本技能需要的输入

- 对于筛选：加权标准、必备要求，以及每家供应商基于证据的 0-10 分评分
- 对于供应商组合：每家供应商的年度支出、类别、续约日期、通知天数和自动续约标记
- 每家供应商的风险输入：数据分类、业务关键性、替代方案可用性、子处理方使用情况
- 每份合同的内部负责人
- 对于 SLA 报告：已承诺的指标及其目标值、实际值、方向、抵扣层级和往期历史记录
- 年度合同价值和合同约定的抵扣上限

## 首先澄清

生成内容之前，请确认以下输入。如果任何一项未知或含糊，请务必询问——不要自行假设：

- [ ] **已知的是通知截止日期，还是只有续约日期？**——真正限制行动的是通知截止日期；一旦错过，就会在整个续约周期内失去所有谈判筹码
- [ ] **评分权重是否在对任何供应商评分之前设定？**——在看过候选供应商后才选择的权重，产生的是论证，而不是决策
- [ ] **该供应商实际持有或接触哪些内容？**——数据敏感性和关键性决定风险等级；支出并不能
- [ ] **哪些必备条件确实属于通过/不通过项？**——该列表中的每一项都会淘汰候选供应商，因此偏好项应归入加权标准

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草即可”，则继续执行，并在交付物顶部列出你的假设。

## 工作流

### 工作流 1——筛选供应商

1. 在查看任何候选供应商**之前**，就加权标准和必备条件列表达成一致。记录由谁在何时达成一致。
2. 为每项标准定义评分锚点——明确 10 分和 5 分分别是什么样。这可以防止评分卡沦为事后论证工具。
3. 根据证据（演示、客户访谈、已审阅的文档）而非印象为每个候选供应商评分。在评分卡中注明证据。
4. 运行评分工具，并在查看排名之前先阅读稳定性检查结果。差距低于 5% 视为平手——此时应改为根据商务条款、退出成本或客户访谈来做决定。
5. 如果某项权重变化 50% 就会导致结果逆转，请在继续之前将该标准提交给决策负责人重新审议。

```bash
python3 business-operations/vendor-management/scripts/vendor_scorecard.py \
  --input business-operations/vendor-management/assets/sample_vendor_candidates.json \
  --format text
```

### 工作流 2 — 审查供应商组合

1. 建立供应商清单，包含续约日期、通知天数和自动续约标记。通知截止日期由此推导得出，而它才是关键日期。
2. 显式设置 `as_of`，确保分析结果可复现，并可供日后审查。
3. 运行分析器并优先处理紧急续约事项——任何标记为 LOCKED 的项目都已经错过了本期的谈判窗口。
4. 以两种形式检查集中度：单一供应商份额超过 25-30% 即构成依赖，而品类 HHI 则能反映你拥有的是议价能力还是多元化优势。
5. 将每份无人负责的合同都视为未来会自动续约的合同。在处理报告中的其他事项之前，先为其指定负责人。

```bash
python3 business-operations/vendor-management/scripts/portfolio_analyzer.py \
  --input business-operations/vendor-management/assets/sample_portfolio.json \
  --format text
```

### 工作流 3 — 开展 SLA 审查

1. 收集承诺的指标，包括目标值、实际值、方向和抵扣分级。纳入之前各期的数据——趋势才是论据。
2. 运行报告，并对照合同上限检查已获得的抵扣额。抵扣额超过上限，意味着补救机制过于薄弱，无法促使行为发生改变。
3. 申领抵扣。未申领抵扣是常态，而且大多数合同都要求你主动提出申请。
4. 将严重违约事项升级至合同负责人，而不是客户经理——客户经理无法更改导致违约的条款。
5. 将审查结果纳入续约诉求：设置真正具有约束力的抵扣分级，并约定重复违约后的终止权。

```bash
python3 business-operations/vendor-management/scripts/sla_report.py \
  --input business-operations/vendor-management/assets/sample_sla.json \
  --format json
```

## 决策框架

### 风险分级 [已验证]

对数据敏感度和业务关键性进行评分，然后应用修正项。

| 数据分类 | 分值 | | 业务关键性 | 分值 |
|--------------------|--------|---|---------------------|--------|
| PHI / 健康数据 | 4 | | 关键（收入会在数小时内中断） | 4 |
| PII | 3 | | 高（核心职能会在一天内停止） | 3 |
| 财务数据 | 3 | | 中（生产力损失） | 2 |
| 机密数据 | 2 | | 低（造成不便） | 1 |
| 内部数据 | 1 | | | |
| 公开数据 | 0 | | | |

修正项：没有现成替代方案 +2 · 可通过网络访问你的系统 +2 ·
次级处理方 +1 · 非充分性认定司法管辖区 +1 · 供应商员工少于 20 人 +1。

| 总分 | 级别 | 核心义务 |
|-------|------|------------------|
| 8+ | **第 1 级：关键** | 年度安全审查、季度业务审查、经过**测试**的退出计划、带抵扣机制的 SLA |
| 6-7 | **第 2 级：高** | 入驻时完成完整问卷、每半年审查、形成书面退出计划 |
| 4-5 | **第 3 级：中** | 简版问卷、年度审查、经过验证的数据导出 |
| 低于 4 | **第 4 级：低** | 确认其涉及哪些数据；无需采取进一步措施 |

**根据影响范围而非支出金额确定级别。** 一个掌握你全部客户
名单、价值 $8K 的工具，其优先级高于一个未持有任何敏感信息、价值 $400K 的托管合同。

### 续约议价能力的来源 [已验证]

| 来源 | 价值 | 所需条件 |
|--------|-------|----------|
| 一个真正的替代方案 | 10-30% | 3-6 周的真实评估，以及一位愿意推动切换的内部支持者 |
| 供应商财年时点 | 10-25% | 了解其财年结束时间，并据此安排你的签约时间 |
| 多年期承诺 | 10-20% | 价格保护、SLA 未达标时的退出权以及涨价上限——三者缺一不可 |
| 用量 / 整合 | 15-30% | 真实增长，而非期望中的席位数量 |
| 客户推荐或案例研究 | 5-15% | 付出的是营销时间，而非金钱 |
| 年度预付 | 5-10% | 承担现金流占用，并且必须先核查供应商的持续经营能力 |

不构成议价筹码的做法：抱怨价格、在没有替代方案的情况下威胁离开、没有具体诉求就升级沟通，或强调忠诚度——长期合作会降低
供应商的风险，因此合作时间较长的客户往往反而面临更高的定价。

### 续约时间表 [已验证]

| 距续约日的天数 | 行动 |
|--------------------|--------|
| 180 | 对比使用量与权益；确认负责人；决定续约 / 重新谈判 / 退出 |
| 150 | 如果要认真重新谈判，则启动替代方案评估 |
| 120 | 与供应商进行首次沟通——在其制定报价之前表明预期 |
| 90 | **大多数年度合同的通知截止日期。如有任何疑虑，就发出通知。** |
| 60 | 谈判实质条款：价格、涨价上限、席位下调、SLA 补偿、退出权 |
| 30 | 完成签约；此时仍未解决的任何事项最终都会朝有利于供应商的方向解决 |

发出通知并不意味着离开——它会将自动续约转变为一次谈判。

### 比价格更有价值的条款 [推荐]

| 条款 | 目标 |
|------|--------|
| 年度涨价上限 | CPI，或最高 3-5% |
| 席位下调权 | 续约时可无罚金下调 |
| 因 SLA 未达标而终止 | 明确定义违约阈值，且不收取罚金 |
| 数据导出格式 | 开放、有文档说明且经过测试 |
| 子处理者变更通知 | 提前 30 天通知，并享有异议权 |
| 收购时的合同转让 | 必须征得同意，或赋予退出权 |

席位下调是最有价值但最少被提出的条款：几乎每份 SaaS
合同都允许你在合同期内增加席位，却禁止减少席位。

## 反模式

### 按支出金额分级
**错误：** 按合同金额决定尽职调查力度——对大型基础设施合同进行严格审查，却只刷信用卡、不做任何询问就购买价值 8,000 美元的工具。
**原因：** 采购部门负责该流程，而采购门槛以金额衡量。审批工作流依据支出金额触发，因为财务系统只能看到这一指标。
**正确做法：** 根据数据敏感性和业务关键性分级，并结合可替代性和子处理者因素进行调整。存有客户名单的小工具，其潜在影响范围远大于不持有任何敏感信息的大额合同，而它恰恰最有可能在未经安全审查的情况下直接刷卡购买。

### 在通知截止日期过去后才发现
**错误：** 只跟踪续约日期，直到距续约日 60 天时才发现，提前 90 天通知的窗口已在一个月前关闭，合同也已自动续约一年。
**原因：** 合同和日历显示的是续约日期。通知截止日期是一个无人计算的衍生日期，而自动续约条款的写法又刻意让人容易忽略。
**正确做法：** 跟踪每份合同的这两个日期，并将通知截止日期视为真正的截止日期。对于任何打算重新谈判的合同，都应将截止日期发出通知作为常规操作——这会重新开启合同谈判，又不会迫使你必须离开。无人负责的合同最容易出现这种问题，因此应为每个供应商指定一名内部负责人。

### 为既定决策背书的评分卡
**错误：** 先选定供应商，再构建一套加权评分卡，通过调整权重和评分让该供应商成为赢家。
**原因：** 这很少是出于恶意。有人在演示期间形成了看法，之后又在这种既有看法的影响下设定权重——每一项权重单独看似乎都合乎情理，但合在一起却并非如此。
**正确做法：** 在对任何候选供应商评分之前，设定并记录各项权重，并明确说明 10 分和 5 分分别对应什么标准。然后进行敏感性检查：如果某一项权重变动 50% 就会导致赢家改变，那么结果只是权重设置的产物，而不是对供应商进行评估所得出的结论；决策负责人需要在签字之前了解这一点。

### 将 SLA 视为一种控制措施
**错误：** 接受 99.9% 的正常运行时间承诺和 2% 的服务抵扣，并认为风险已经得到控制。
**原因：** SLA 确实存在，其中也有量化指标，并且满足了检查清单上的要求。但没有人计算过，与停机造成的损失相比，这些抵扣究竟价值多少。
**正确做法：** 为补救措施定价。对于每季度 $20K 的费用，2% 的抵扣只有 $400，而一次停机造成的损失可能远高于此——这只是供应商早已计入成本的零头，并非控制措施。应协商分级抵扣（5/10/25%）、高于当期费用 20% 的抵扣上限，以及在多次违约后终止合同的权利。失去客户会改变供应商的行为；抵扣不会。此外，应根据错误预算而不是百分比衡量可用性——若实际可用性比 99.9% 低半个百分点，停机时间将接近允许值的六倍。
