# 公开构建——最佳实践

## 理念

公开构建不是营销，而是让人们看到你工作的过程。最好的帖子就像是在向一位同样资深的工程师朋友讲述你的思考过程。不要夸夸其谈，不要说“我很激动地宣布”。只需要说：这是我构建的东西，这是它为什么重要，这是我学到的东西。

## 分享什么（以及不分享什么）

**分享：**
- 技术决策及其背后的理由（“选择 SQLite 而不是 Postgres，因为……”）
- 架构洞察（“这是 9 层路由流水线的工作方式”）
- 失败以及你从中学到的东西（“花了 3 个小时调试一个竞态条件。根本原因是：……”）
- 前后指标对比（“压缩死亡螺旋：使用 Mnemos 后从 26 → 0”）
- 带有背景说明的开源发布，而不只是链接
- 让你感到意外的反直觉发现

**绝不要分享：**
- 营收数据、用户数量、估值
- 客户名称或可识别的客户细节
- 内部 URL、API 密钥、凭据
- 任何受 NDA 约束的内容
- 你可能无法兑现的路线图承诺
- 伪装成内容的“我们正在招聘”

## 针对不同渠道的最佳实践

### LinkedIn

**受众：** 构建产品的工程师、CTO 和创始人。他们在会议间隙刷动态，寻找能让自己思考的内容。

**格式：**
- 1-3 个段落，800-2000 个字符是最佳范围
- 先说洞察，而不是背景
- 适当多换行——大段文字会扼杀互动
- 每篇帖子只传达一个明确的要点
- 第一段不要放外部链接（LinkedIn 会降低站外点击的权重）

**语气：** 自信，并且能教会别人一些东西。你是一位向同行解释自己方法的资深工程师。不要使用未经解释的术语。如果你使用了其他人可能不了解的技术，请简要说明。

**发布时间：** 目标时区周二至周四上午 8-10 点。避免周末和周一早上（大家都在处理积压的事务）。

**有效的内容：**
- 带有具体代码示例的技术深度解析
- 通过架构图讲述“我是如何构建 X 的”
- 从失败中总结的经验（这类内容的表现优于成功故事，比例为 3:1）
- 对行业趋势的鲜明观点（但前提是你有数据支持）

**表现不佳的内容：**
- “我很激动地宣布”式的新闻稿
- 没有技术洞察的纯产品更新
- 没有实质内容的励志内容
- 没有强有力开场、长度却超过 2500 个字符的帖子

### X (Twitter)

**受众：** 真正交付产品的开发者。他们刷得很快，评判得更快。你只有一句话的机会来赢得他们的注意。

**格式：**
- 最多 280 个字符
- 除非某个洞察确实需要 3+ 条帖子，否则不要发线程
- 以反直觉或令人意外的元素开头
- 每篇帖子只表达一个想法。如果你有两个想法，就发两篇帖子。
- 截图需要添加描述其中内容的替代文本

**语气：** 简洁犀利、观点鲜明、零废话。想象一下你正在给一位做产品的朋友发短信。如果听起来像营销文案，就删掉它。

**发布时间：** 目标时区周二至周五上午 9-11 点或下午 2-4 点。周末也可能适合开发者受众（他们会构建副业项目）。

**有效的内容：**
- 一句话技术洞察（“优秀 API 和卓越 API 之间的差别在于错误消息。”）
- 带有指标的前后对比
- “刚刚发布了 X。这是最让我意外的一点。”
- 提出真正的技术问题（为了互动而提问会适得其反）

**容易失败的做法：**
- 堆砌 Hashtag
- 本可以合并成一篇的多个帖子
- 没有个人经历支撑的泛泛“热点观点”
- 不加上下文地发布链接

## 内容日历节奏

**每日（如果你有想说的内容）：**
- 发布一条 X 帖子，讲述你今天正在做什么或学到了什么

**每周：**
- 发布一篇 LinkedIn 帖子：更深入的技术见解或项目里程碑

**每个事件（由插件触发）：**
- PR 合并 → 24 小时内发布 LinkedIn，当天发布 X
- 功能上线 → 两个渠道都发布，先发 LinkedIn，90 分钟后发 X
- Review 通过 → 仅发布 X（架构见解简短有力）
- 重大版本发布 → LinkedIn 深度解析 + X 公告

## 应避免的反模式

1. **“我们”陷阱** —— 独立构建者使用“我们”会显得不自信。除非你确实是团队，否则使用“我”。
2. **诱导互动** —— 每篇帖子结尾都写“同意吗？”或“有什么想法？”会显得很 desperate。让洞察本身独立成立。
3. **不构建却发帖** —— 如果你已经两周没有交付任何东西，就不要发帖。你的内容应该是工作成果的副产品，而不是工作的替代品。
4. **LinkedIn 兄弟腔** —— “我深感谦卑，也非常荣幸地与大家分享……”立即删掉。你不是在领奖。
5. **过度润色** —— 一篇读起来像经过 5 轮编辑的帖子，会显得很企业化。直接发布草稿。
6. **忽略回复** —— 如果有人愿意花时间互动，请在 24 小时内回复。评论区的对话往往比原帖表现更好。

## 衡量哪些做法有效

跟踪以下信号（Buffer、LinkedIn analytics、X analytics）：
- **曝光量** —— 有多少人看到了它
- **互动率** —— (点赞数 + 评论数 + 转发数) / 曝光量
- **个人资料访问量** —— 这篇帖子是否促使人们进一步了解你？
- **入站互动** —— 提及具体帖子的私信、连接请求或邮件

一篇表现良好的 LinkedIn 帖子：互动率为 3-5%。表现出色的帖子：8%+。在 X 上，对于技术内容来说，超过 2% 就算扎实。

## 插件集成

公开构建插件会自动遵循这些做法：

```yaml
# What gets shared vs skipped:
on_pr_merged:
  - Share if: >3 files changed, meaningful commit message
  - Skip if: typo fix, dependency bump, config change only

on_feature_shipped:
  - Share: always, with screenshot
  - LinkedIn: deep dive on architecture decisions
  - X: punchy one-liner on impact

on_review_passed:
  - Share if: 3/3 unanimous approval
  - X only: architecture insights are punchy
  - Skip if: 1/3 or 0/3 (revisions aren't share-worthy)
```

## 默认匿名

所有帖子在发布前都会通过 `anonymize.yaml` 进行脱敏。公司名称会变成通用描述。收入会变成“达到规模”。读者了解的是你的工程能力，而不是雇主的财务状况。
