# review-cockpit

## 用途

一份持续更新的**审核文档**，同时作为会话的控制界面。无需再把会议记录放在这里、工单放在那里、两份草稿散落在聊天中；所有内容都汇集到**一个文件**中，你可以在 Obsidian 侧边面板（或 Claude 侧边面板）打开它并推进工作：一目了然地查看进度、就地审核每一项、直接在文档中批准或要求修改，并在代理工作时观察文档更新。它复刻了一个“协作”驾驶舱（进度 / 工作文件夹 / 上下文）。

## 何时使用

- 任何存在**至少 2 项需要审核或批准的内容**的会话（“处理 X，然后规划/起草 Y、Z”类任务默认适用）。
- 会议处理 + 小组规划、多工单批量处理、包含多份草稿的简报、规格 + 计划 + 草稿。
- 不适用于单个简单交付物（一个文件、没有批准闭环）——这种情况下使用普通文件即可。

可与 `closed-loop`（验证）、`harvest`（经验沉淀）和 V 模型检查点搭配使用。此技能规定的是**如何呈现和推进交付物**，而不是验证流程。

## 唯一规则

**每个会话只使用一份文档。**文档以驾驶舱开头，之后每个审核项对应一张审核卡片。会话产出的每项工件都要从**工作文件夹**表格中链接出去（运行过程中分散到子文件中没有问题；驾驶舱是唯一入口）。绝不要只告诉用户“请查看文件 A、B、C”——应把驾驶舱交给他们。

## 结构

复制 `04-projects/harness/templates/session-review.md`。将工作副本保存到相关项目文件夹中，并命名为 `YYYY-MM-DD-<slug>-review.md`（或 `-plan.md`）。

**驾驶舱（顶部）：**
1. **状态行**——一行内容：有多少项等待审核 + 最后更新时间戳。
2. **🧭 进度**——一个检查清单，每项一行，每行都带有状态符号；一个文本进度条 +“X/N 项已完成 · A 项等待审核 · B 项待处理”。**将每一项设置为可点击并跳转到其审核卡片的锚点**——使用 GitHub slug 规则（小写、空格→`-`、移除标点/表情符号）编写 `[N. Title](#n-title)`。项目标题中不要使用 `+ # ← → ( )`，以确保 slug 中只有单个连字符，并且链接能在 Obsidian 和 Claude 侧边面板中正确跳转。
3. **📁 工作文件夹**——列出本次会话产出的每项工件及其 `~/vault/...` 路径或链接的表格（会议记录、本文件、证据目录、外部议题/PR、已发布的消息）。
4. **🔌 上下文**——工作所依据的来源（录音、Slack 讨论串、议题）、使用的工具/连接器、相关工单。

**审核项（下方）：**每项对应一张卡片：
- **状态**——符号 + 文字（参见状态词汇表）。
- **操作**——已完成或拟议进行的工作。
- **交付物**——链接/路径，或者直接放在卡片下方的内联草稿，以便就地审核（待发送消息、文档正文）。
- **检查清单**——以复选框形式列出该项的验收标准。
- **🗒 你的决定**——由你编辑的批准栏位（`approve` / 你要求的修改）。
- **决策日志**——仅追加记录，说明发生了什么以及你做出了什么决定。

**页脚：**“如何通过本文档推进工作”（批准/修改机制 + 状态词汇表），使文档无需额外说明即可理解和使用。

**状态词汇：** ⏳ 待处理 · 🔄 进行中 · 📝 待审核 · ✏️ 已请求更改 · ✅ 已完成 · ⛔ 已阻塞

## 更新协议（保持实时更新）

- **每完成一个有意义的步骤后**，更新：进度清单和进度条、受影响事项的状态、工作文件夹（添加新产物）以及该事项的决策日志。同时更新 `updated:` 前置元数据和状态行。
- 优先使用有针对性的 `Edit`，而不是完整重写，以免覆盖你的行内编辑或批准。**编辑前，请重新读取文件**——你可能已经在 **🗒 由你决定** 中输入了批准或更改请求，或勾选了复选框。
- 当你批准某个事项时，执行该事项，将其移至 ✅，并在决策日志中记录结果（附外部链接——议题/PR/消息 URL）。
- 当你请求更改时，将该事项设为 ✏️ 已请求更改，应用更改，就地重新起草，然后将其恢复为 📝 待审核。

## 交互约定

文档是共享操作界面；你可以通过以下两种方式进行操作，两者都有效：
- **在文档/侧边面板中：** 编辑 **🗒 由你决定** 或勾选复选框。重新读取并执行。
- **在聊天中：** “第 3 项没问题”“批准第 2 项和第 4 项”“调整需求沟通的语气”。将其映射到事项编号并执行。

区分**草稿**事项（代理提出方案并等待批准——例如由你负责发送的 Slack 消息）与**自动**事项（代理可以直接执行——例如提交你明确要求创建的 GitHub 议题）。草稿事项在获批前保持 📝；自动事项则直接变为 ✅，并附上产物链接。如果不确定某个事项属于草稿还是自动事项，请将其保持为 📝。

## 后置条件

文档本身为只读，但其中跟踪的事项通常会更改外部状态——请遵守每个事项自身的后置条件（重新获取议题、确认 Slack 消息已成功发出等），并在决策日志中记录经过验证的链接。绝不能仅凭一次变更调用就将事项标记为 ✅。

## 可选：渲染视图

Markdown 文档是主要载体（你通过编辑它进行批准）。如果想获得信息更丰富、可一览全局的视图，可以额外将驾驶舱（进度 + 工作文件夹 + 上下文 + 事项状态）渲染为 HTML **产物**——但 Markdown 仍是唯一事实来源和可编辑界面。
