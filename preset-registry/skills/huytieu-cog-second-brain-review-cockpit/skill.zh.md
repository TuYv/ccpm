# review-cockpit

## 用途

一份持续更新的**评审文档**，同时充当会话的控制面板。与其把会议记录散落在这里、工单放在那里，再把两份草稿留在聊天中，不如将所有内容汇总到**一个文件**中；你可以在 Obsidian 侧边栏（或 Claude 侧边栏）打开并驱动它：一眼查看进度，在原地评审每个项目，直接在文档中批准或请求修改，并观察文档随着代理工作而更新。它对应于“协作”驾驶舱（进度 / 工作文件夹 / 上下文）。

## 适用时机

- 任何需要你**评审或批准至少 2 项内容**的会话（“先处理 X，再规划/起草 Y、Z”这类流程的默认选择）。
- 会议处理 + pod 规划、多工单执行、包含多份草稿的简报、规格说明 + 计划 + 草稿。
- 不适用于单个简单的交付物（一个文件、不需要审批循环）——这种情况下使用普通文件即可。

与 `closed-loop`（验证）、`harvest`（经验总结）和 V 模型检查点配合使用。此 skill 管理的是**交付物如何呈现和推进**，而不是验证流程。

## 唯一规则

**每个会话使用一份文档。** 文档以一个驾驶舱开头，随后为每个项目设置一张评审卡片。会话生成的每个工件都要从 **工作文件夹** 表格中链接出去（运行过程中可以拆分到子文件中；驾驶舱是唯一入口）。绝不要只对用户说“请查看文件 A、B、C”——要把驾驶舱交给用户。

## 结构

复制 `references/session-review-template.md`。将工作副本保存到相关项目文件夹中，命名为 `YYYY-MM-DD-<slug>-review.md`（或 `-plan.md`）。

**驾驶舱（顶部）：**
1. **状态行** — 一行显示：等待评审的项目数量 + 最近更新时间戳。
2. **🧭 进度** — 一个清单，每行一个项目，并带有状态符号；包含文本进度条以及“已完成 X/N · 等待评审 A · 待处理 B”。**将每个项目设置为指向其评审卡片的可点击锚点**——使用 `[N. Title](#n-title)`，并遵循 GitHub slug 规则（小写、空格→`-`、去除标点/表情符号）。项目标题中不要使用 `+ # ← → ( )`，以便 slug 保持干净的单连字符形式，并确保链接在 Obsidian + Claude 侧边栏中都能正常跳转。
3. **📁 工作文件夹** — 列出本次会话生成的每个工件，并附上其 `~/vault/...` 路径或链接（会议记录、本文档、证据目录、外部 issue/PR、已发布的消息）。
4. **🔌 上下文** — 工作所依据的来源（录音、Slack 线程、issue）、使用的工具/连接器、相关工单。

**评审项目（下方）：** 每个项目一张卡片：
- **状态** — 符号 + 文字（见词汇表）。
- **操作** — 已完成的工作或拟议的操作。
- **交付物** — 链接/路径，或直接将内联草稿放在卡片下方，以便你在原地评审（待发送的消息、文档正文）。
- **清单** — 该项目的验收标准，以复选框形式列出。
- **🗒 你的决定** — 供你编辑的批准栏（`approve` / 你要求的修改）。
- **决策日志** — 仅追加的记录，记录发生了什么 / 你作出的决定。

**页脚：**“如何驱动此文档”（批准/修改机制 + 状态词汇），确保文档无需额外说明即可使用。

**状态词汇：** ⏳ 待处理 · 🔄 进行中 · 📝 需要评审 · ✏️ 已请求修改 · ✅ 已完成 · ⛔ 已阻塞

## 更新协议（保持实时更新）

- **每完成一个有意义的步骤后**，刷新：进度清单 + 进度条、受影响项目的状态、工作文件夹（添加新生成的产物）以及项目的决策日志。递增 `updated:` frontmatter + 状态行。
- 优先使用定向的 `Edit`，而不是完整重写，以免覆盖你在行内编辑或审批中的内容。**编辑前，重新读取文件**——你可能已经在 **🗒 你的决定** 中输入了审批意见或修改请求，或勾选了复选框。
- 当你批准某个项目时，执行该项目，将其移至 ✅，并在决策日志中记录结果（附外部链接——issue/PR/消息 URL）。
- 当你要求修改时，将项目设为 ✏️ 要求修改，应用修改，在原位置重新起草，然后将其恢复为 📝 待审核。

## 交互约定

该文档是共享操作界面；你可以通过两种方式驱动流程，二者均有效：
- **在文档 / 侧边栏中：** 编辑 **🗒 你的决定** 或勾选复选框。重新读取并执行。
- **在聊天中：**“3 可以了”、“批准 2 和 4”、“调整一下需求沟通的语气”。将这些指令映射到项目编号并执行。

区分 **草稿** 项目（由代理提出并等待批准——例如由你负责发送的 Slack 消息）和 **自动** 项目（代理可以直接执行——例如你明确要求创建的 GitHub issue）。草稿项目保持 📝，直到获得批准；自动项目直接移至 ✅，并附上产物链接。不确定某个项目属于草稿还是自动时，将其保持为 📝。

## 后置条件

文档本身是只读的，但它所跟踪的项目通常会改变外部状态——遵守每个项目自身的后置条件（获取 issue 的最新状态、确认 Slack 消息已发送等），并在决策日志中记录已验证的链接。绝不要仅凭一次变更调用就将项目标记为 ✅。

## 可选：渲染视图

Markdown 文档是主要依据（你通过编辑它来进行审批）。如果你希望获得更丰富的一览视图，也可以额外将操作台的 HTML **产物**（包括进度、工作文件夹、上下文和项目状态）渲染出来——但 Markdown 仍是事实来源和可编辑界面。
