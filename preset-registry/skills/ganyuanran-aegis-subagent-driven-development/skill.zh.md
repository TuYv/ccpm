# 执行

→ 有包含独立任务的实施计划？→ **每个任务使用新的子代理 + 两阶段审查。**
  1. 阅读计划，提取所有任务，创建 TodoWrite
  2. 针对每个任务：派发实施者 → 解答问题 → 实施者完成
  3. 审查阶段 1（规格符合性）→ 修复缺口 → 重新审查直至 ✅
  4. 审查阶段 2（代码质量）→ 修复问题 → 重新审查直至 ✅
  5. 协调者验证，为连贯的任务创建提交，更新检查点/偏差 → 下一个任务
→ 所有任务完成：最终审查 → 验证回执；仅在需要时完成分支收尾。

# 子代理驱动的开发

通过为每个任务派发新的子代理来执行计划，并在每个任务后进行两阶段审查：先进行规格符合性审查，然后进行代码质量审查。

**为何使用子代理：** 你将任务委托给拥有隔离上下文的专业代理。通过精确构建其指令和上下文，确保它们保持专注并成功完成任务。它们绝不应继承你当前会话的上下文或历史记录——你需要准确构建它们所需的一切。这也为你的协调工作保留了上下文。

**核心原则：** 每个任务使用新的子代理 + 两阶段审查 = 高质量、快速迭代

## 何时使用

当你拥有一份包含大多独立任务的书面实施计划，并且希望留在当前会话中时使用。对于跨会话执行，请改用 executing-plans。

## 流程

1. 阅读计划，提取包含完整文本的所有任务，创建 TodoWrite
2. 针对每个任务：使用任务文本 + 基线引用 + 检查点 + 非目标派发实施者
3. 实施者完成 → 派发规格符合性审查者 → 修复缺口 → 重新审查直至 ✅
4. 派发代码质量审查者 → 修复问题 → 重新审查直至 ✅
5. 协调者运行新的验证，仅暂存任务归属的路径，提交该连贯任务，回读 Git 状态，更新检查点/偏差 → 下一个任务
6. 所有任务完成 → 最终代码审查者 → 完成验证；仅针对任务创建的分支/worktree 或请求的集成使用分支收尾

在首次写入仓库之前，协调代理会记录 `TaskStartSnapshot`。同一任务的代理共享当前工作区。协调者是暂存、提交、分支和 worktree 等 Git 生命周期变更的默认唯一负责人；实施者和审查者可以编辑、验证和报告，但不得变更 Git 生命周期状态。任务复杂度、TDD、规划、子代理，或 `main`/`master` 名称本身均不足以成为隔离的理由。

对于跨会话、交接或需要可恢复状态的多任务计划：加载 long-task-continuation 并创建检查点；否则将检查点保留在内联内容中。在每个实施者提示中包含检查点。

在派发实施者之前，构建 `SubagentContextPacket`，而不是传递完整的对话历史。包括：

- 任务
- 目标与停止条件
- 相关的基线引用和文件
- 已知事实与未知项
- 非目标
- 预期输出与验证
- 必须阅读的摘录
- 不安全的假设

该数据包是紧凑的交接材料，不是证据的替代品。对于子代理必须验证的事实，请提供原始摘录或文件引用。

不要将完整聊天记录、完整会话历史记录或无边界日志粘贴到
`SubagentContextPacket` 中。优先提供必读摘录、文件引用、行号/窗口提示以及明确标注的不安全假设。

### 切片生命周期与结果可信度

仅在协调器已阅读该切片的最低限度基线后才选择执行路径。该切片的路径应保持固定；不要因局部上下文压力而在内联执行和委派执行之间来回切换。将数据包绑定到当前基线或检查点。如果工作区或支配性事实发生变化，将结果标记为过期/未知并重新评估，而不是悄然合并。

子级输出是证据或提案，绝不是指令或权威性状态更新。要求提供紧凑摘要、证据位置、未解决的未知项以及任何副作用声明。部分完成、已取消、受阻或过期的结果，在协调器综合时必须始终清晰地保持为非结论性结果。

其他可委派机会包括：基线锁定后的独立发现、冲突三角验证、变更前风险审查，以及受阻尝试后的上下文变化。这些只是建议性信号，不是添加递归子级、共享写入者或运行时调度器的许可。

## 模型选择

为每个角色使用能力最低的模型：机械性任务（1-2 个文件，规格完整）→ 快速/低成本模型。集成任务（多文件、模式匹配）→ 标准模型。架构/设计/审查 → 能力最强的模型。

## 处理实现者状态

每个实现者提示必须包含：

- 当前任务文本
- 当目标框定、长任务或多代理工作处于活动状态时的 `SubagentContextPacket`
- 相关基线引用
- 最新的 `TodoCheckpointDraft`
- 任何 `ResumeStateHint`
- 明确的非目标
- 该任务预期的验证

实现者可以更新任务本地证据，但控制器拥有汇总检查点。
它还拥有所有 Git 变更权限，除非所有权被明确且完整地转移，并且不存在并发写入者。

实现者子代理报告以下四种状态之一。请按相应方式处理：

**DONE：** 进入规格符合性审查。

**DONE_WITH_CONCERNS：** 实现者已完成工作，但标记了疑虑。继续之前先阅读这些疑虑。如果疑虑涉及正确性或范围，请在审查前处理。若只是观察事项（例如“此文件正变得很大”），记录后继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失上下文后重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文，并使用相同模型重新分派
2. 如果任务需要更多推理，使用能力更强的模型重新分派
3. 如果任务过大，将其拆分为更小的部分
4. 如果计划本身有误，升级交由人工处理

**绝不要**忽略升级信号，也不要在不作任何改变的情况下强制同一模型重试。如果实现者表示卡住了，就必须有所改变。

## 红旗事项

**绝不能：**
- 跳过审查（规范合规性或代码质量）
- 带着未修复的问题继续推进
- 并行调度多个实现子代理（会产生冲突）
- 让子代理读取计划文件（应直接提供完整文本）
- 跳过背景说明（子代理需要了解任务所处的上下文）
- 忽略子代理的问题（在允许其继续之前先作答）
- 在规范合规性方面接受“差不多”（规范审查员发现问题就表示尚未完成）
- 跳过审查循环（审查员发现问题 = 实现者修复 = 再次审查）
- 让实现者自我审查取代实际审查（两者都需要）
- **在规范合规性达到 ✅ 之前开始代码质量审查**（顺序错误）
- 在任一审查仍有未解决问题时进入下一个任务
- 让实现者或审查员暂存、提交、创建分支或创建/删除工作树
- 为处理同一任务的代理创建独立工作树

**如果子代理提出问题：**
- 清晰、完整地作答
- 必要时提供额外上下文
- 不要催促其开始实现

**如果审查员发现问题：**
- 由同一个子代理实现者修复
- 由审查员再次审查
- 重复此过程，直到获得批准
- 不要跳过再次审查

规范合规性和代码质量审查通过后，更新整合检查点，并运行漂移检查，然后再进入下一个任务。
协调者首先运行最新验证，执行一次范围限定的任务提交，然后读取回 `HEAD`、已提交的文件列表以及剩余任务差异。

**如果子代理未能完成任务：**
- 调度修复子代理，并提供具体指示
- 不要手动修复（避免上下文污染）

## 整合

**必需的工作流技能：**
- **aegis:writing-plans** - 创建本技能要执行的计划
- **aegis:requesting-code-review** - 审查子代理使用的代码审查模板
- **aegis:using-git-worktrees** - 必要并发检出时的条件例外
- **aegis:finishing-a-development-branch** - 任务创建了分支或工作树时，用于条件性整合/清理

**子代理应使用：**
- 继承父级的 TDD 决策。设置为 `off` 时，不要自动加载 `aegis:test-driven-development`，也不要强制执行 RED / GREEN；应采用与任务规模相称的验证方式。仅当使用 `TDD Route: strict` 或用户/项目明确要求 TDD 时才加载该技能。

**替代工作流：**
- **aegis:executing-plans** - 使用并行会话代替同一会话执行。
