# 执行

→ 已有包含独立任务的实施计划？→ **每个任务使用全新的子代理 + 两阶段审查。**
  1. 阅读计划，提取所有任务，创建 TodoWrite
  2. 针对每个任务：派遣实施者 → 回答问题 → 实施者完成任务
  3. 第一阶段审查（规范符合性）→ 修复遗漏 → 重新审查直至 ✅
  4. 第二阶段审查（代码质量）→ 修复问题 → 重新审查直至 ✅
  5. 协调者验证并提交完整一致的任务，更新检查点/偏差 → 下一个任务
→ 所有任务完成：最终审查 → 验证回执；仅在需要时完成分支收尾。

# 子代理驱动的开发

通过为每个任务派遣全新的子代理来执行计划，并在每个任务完成后进行两阶段审查：先进行规范符合性审查，再进行代码质量审查。

**为什么使用子代理：** 你将任务委派给具有隔离上下文的专业代理。通过精确编写其指令和上下文，可以确保它们保持专注并成功完成任务。它们绝不应继承你当前会话的上下文或历史记录——你需要准确构建它们所需的一切。这也能保留你自己的上下文，以便开展协调工作。

**核心原则：** 每个任务使用全新的子代理 + 两阶段审查（先规范，后质量）= 高质量、快速迭代

## 何时使用

当你已有书面实施计划，其中包含大多相互独立的任务，并希望留在当前会话中执行时使用。对于跨会话执行，请改用 executing-plans。

## 流程

1. 阅读计划，提取所有任务的完整文本，创建 TodoWrite
2. 针对每个任务：使用任务文本 + 基线引用 + 检查点 + 非目标来派遣实施者
3. 实施者完成 → 派遣规范符合性审查者 → 修复遗漏 → 重新审查直至 ✅
4. 派遣代码质量审查者 → 修复问题 → 重新审查直至 ✅
5. 协调者运行全新验证，仅暂存该任务所属的路径，提交完整一致的任务，回读 Git 状态，更新检查点/偏差 → 下一个任务
6. 所有任务完成 → 最终代码审查者 → 完成验证；仅对任务创建的分支/工作树或应要求进行的集成执行分支收尾

在首次写入仓库之前，协调代理记录
`TaskStartSnapshot`。同一任务的代理共享当前工作区。默认情况下，协调者是唯一负责暂存、提交、分支和工作树等 Git 状态变更的角色；实施者和审查者负责编辑/验证/报告，但不改变 Git 生命周期状态。任务复杂度、TDD、规划、子代理或使用
`main`/`master` 名称本身，都不能成为进行隔离的理由。

对于会跨会话、需要移交或需要可恢复状态的多任务计划，在开始之前加载 long-task-continuation 并创建检查点；否则以内联方式保留检查点。在每个实施者提示中包含该检查点。

在派遣实施者之前，构建 `SubagentContextPacket`，而不是
传递完整的对话历史记录。包括：

- 任务
- 目标和停止条件
- 相关基线引用和文件
- 已知事实和未知事项
- 非目标
- 预期输出和验证
- 必读摘录
- 不安全的假设

该信息包是一份紧凑的交接材料，而非证据的替代品。对于子代理必须验证的事实，应提供原始摘录或文件引用。

不要将完整的聊天记录、完整的会话历史或无限量的日志粘贴到
`SubagentContextPacket` 中。应优先提供必读摘录、文件引用、行号/窗口
提示，以及明确标注的不安全假设。

## 模型选择

根据角色使用能力最低但足以胜任的模型：机械性任务（1-2 个文件、完整规范）→ 快速/低成本模型。集成任务（多文件、模式匹配）→ 标准模型。架构/设计/审查任务 → 能力最强的模型。

## 处理实现者状态

每个实现者提示词都必须包含：

- 当前任务文本
- 当目标框定、长任务或多代理工作处于活动状态时，包含 `SubagentContextPacket`
- 相关基线引用
- 最新的 `TodoCheckpointDraft`
- 任何 `ResumeStateHint`
- 明确的非目标
- 该任务预期的验证方式

实现者可以更新任务局部证据，但控制器拥有整合后检查点的所有权。
它还负责所有 Git 变更操作，除非在不存在并发写入者的情况下，明确且完整地
转移了所有权。

实现者子代理会报告以下四种状态之一。应根据不同状态妥善处理：

**DONE：** 继续进行规范合规性审查。

**DONE_WITH_CONCERNS：** 实现者已完成工作，但提出了疑虑。继续之前先阅读这些疑虑。如果疑虑涉及正确性或范围，应在审查前解决。如果只是观察意见（例如“这个文件变得很大”），则记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要尚未提供的信息。提供缺失的上下文，然后重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文，并使用同一模型重新分派
2. 如果任务需要更强的推理能力，使用能力更强的模型重新分派
3. 如果任务过大，将其拆分为更小的部分
4. 如果计划本身有误，上报给人工处理

**绝不要**忽略上报的问题，或在不做任何改变的情况下强制同一模型重试。如果实现者表示遇到阻碍，就必须做出改变。

- `./implementer-prompt.md` - 分派实现者子代理
- `./spec-reviewer-prompt.md` - 分派规范合规性审查子代理

## 危险信号

**绝不要：**
- 跳过审查（规范合规性审查或代码质量审查）
- 在问题尚未修复时继续推进
- 并行分派多个实现子代理（会产生冲突）
- 让子代理读取计划文件（应改为提供完整文本）
- 跳过背景说明上下文（子代理需要理解任务在整体工作中的位置）
- 忽略子代理的问题（应在让其继续之前回答）
- 在规范合规性方面接受“差不多就行”（规范审查者发现问题 = 尚未完成）
- 跳过审查循环（审查者发现问题 = 实现者修复 = 再次审查）
- 让实现者的自我审查替代实际审查（两者都需要）
- **在规范合规性审查通过 ✅ 之前开始代码质量审查**（顺序错误）
- 在任一审查仍有未解决问题时转到下一个任务
- 让实现者/审查者执行暂存、提交、创建分支或创建/删除工作树
- 为处理同一任务的代理创建各自独立的工作树

**如果子代理提出问题：**
- 清晰、完整地回答
- 必要时提供更多上下文
- 不要催促其进入实现阶段

**如果审查者发现问题：**
- 由实现者（同一个子代理）修复
- 审查者再次审查
- 重复此过程直至批准
- 不要跳过再次审查

规范符合性和代码质量审查通过后，更新整合检查点并运行偏差检查，然后再继续下一个任务。
协调者首先运行全新验证，执行一次范围明确的任务提交，
然后回读 `HEAD`、已提交文件列表以及剩余任务差量。

**如果子代理未能完成任务：**
- 派遣修复子代理，并提供具体指示
- 不要尝试手动修复（避免上下文污染）

## 集成

**必需的工作流技能：**
- **aegis:writing-plans** - 创建本技能所执行的计划
- **aegis:requesting-code-review** - 面向审查子代理的代码审查模板
- **aegis:using-git-worktrees** - 必须进行并发检出时使用的条件性例外
- **aegis:finishing-a-development-branch** - 对任务创建的分支或工作树进行条件性集成/清理

**子代理应使用：**
- 继承父级的 TDD 决策。当设为 `off` 时，不要自动加载 `aegis:test-driven-development`，也不要强制执行 RED / GREEN；应采用与任务相称的验证方式。仅在 `TDD Route: strict` 或用户/项目明确要求 TDD 时加载该技能。

**替代工作流：**
- **aegis:executing-plans** - 用于并行会话，而非同一会话内执行
