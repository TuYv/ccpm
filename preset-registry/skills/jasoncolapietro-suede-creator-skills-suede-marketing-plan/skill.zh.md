# Suede 营销运营计划

Suede 制定一份全面的营销运营计划，涵盖获客、激活、留存、推荐和营收。基于客户已验证的预算、团队、阶段、证据、约束条件以及公开的 Suede 执行路径构建这份 12 个月计划，然后交叉引用 `suede-marketing-ideas` 库和嵌入式的 17 部分当前状态评估标准。

交付物是一份可直接粘贴到 Notion 的 Markdown 文档——应当是兼职 CMO 向创始人呈现的那类战略产物。它必须针对客户量身定制（而非通用模板）、足够详尽（覆盖所有战术层面，而不只是规定的内容），并且在运营上诚实可信（反映其团队以当前技术栈和人员规模实际能够执行的事项）。

## 如何调用此技能

`/suede-marketing-plan {client-name-or-domain}` — 参数为客户名称
或域名；若没有参数，则提示用户提供。

如果 `.agents/product-marketing.md` 存在，先读取它，并且只询问其中未涵盖的内容；路径回退请参见 `suede-product-marketing`。

调用时，该技能会读取 `.agents/suede-marketing-plans/{client-slug}/progress.md`，并根据 `references/methodology.md` 步骤 1.1.2 中记录的状态机恢复执行（fresh → INIT → REVIEW → FINALIZE → finalized）。已完成的计划绝不会被静默覆盖——应询问用户是修订为 v{N+1}、重新开始，还是重新打开某个部分。

## 三个阶段

完整工作流位于 `references/methodology.md`。简要总结：

### 阶段 1 — INIT（调研 + 信息收集）

阅读所有与客户相关的可用材料。从所有已接入的工具（Ahrefs、GA4 MCP、Stripe MCP 等）中提取数据。进行结构化信息收集，涵盖：客户概览、ICP、当前漏斗状态、融资状态、团队构成、营销预算、当前活跃渠道、已完成事项、进行中事项、受阻事项、工具技术栈。保存至 `research.md`。

将嵌入式的 17 部分当前状态评估标准（`references/current-state-rubric.md`）作为第 3 节的评分依据——根据可用材料为每个部分打 0–5 分。

### 阶段 2 — REVIEW（以交互方式逐一审阅 13 个部分）

在聊天中展示每个部分的草案。对于每个部分，你可以：
- 按原样批准（“good”、“next”）
- 调整（“将 X 改为 Y”）
- 添加观察结论（“也提及 Z”）
- 扩展（“对此进行更深入的说明”）

通过 `references/methodology.md` 中可恢复的写入意图事务持久化每个已确认部分：记录部分编号和内容哈希，提升 `sections/NN.md`，协调其复选框/产物/当前部分/时间戳元数据，验证，然后清除该意图。如果中断，请运行 `/suede-marketing-plan client-name` 以协调该意图后再继续。

### 阶段 3 — FINALIZE（编译 + 验证 + 发布）

将全部 13 个部分编译至 `final_plan.md`。执行验证检查：确认 `suede-marketing-ideas` 创意编号、公开 Suede 路径和已命名集成项准确无误；检查是否存在不应发布的机器特定路径；确保品牌语调与战略框架中记录的内容一致。

如果用户希望与团队共享，可选择提供发布到共享 GitHub 仓库的选项（例如 `{client-org}/{client-context}/marketing/plan.md`）。

## 13 个章节的计划结构

完整模板位于 `references/plan-template.md`。结构如下：

1. **执行摘要** — 3 项重大押注、90 天优先事项、12 个月成果。行文应便于直接纳入投资人或董事会更新。
2. **战略框架** — 品类主张、提炼后的 ICP、商业模式逻辑、品牌语调的不可妥协项。
3. **当前状态** — 团队、预算、已完成事项、进行中事项、受阻事项。根据嵌入式的 17 个章节当前状态评估标准进行评分（`references/current-state-rubric.md`）。
4. **获客** — 陌生人如何建立认知。当前使用、计划使用和跳过的渠道，90 天和 12 个月的动作，技能与工具。
5. **激活** — 新用户如何获得能够促成转化的体验。引导流程、首次会话、App Store / 注册、付费墙、生命周期设置。
6. **留存** — 已转化用户如何留下来并加深参与。生命周期流程、流失预防、召回、将支持作为营销。
7. **推荐** — 留存用户如何带来更多用户。大使 / 联盟 / Guides / 口碑传播机制。
8. **收入** — 定价、产品包装、增购、捆绑销售、从硬件到软件、B2B ACV。
9. **90 天路线图** — 第 1–2 周（解除阻塞）、第 3–4 周（打基础）、第 5–8 周（提升速度）、第 9–12 周（复利增长）。标注 AARRR 阶段并分配负责人。
10. **12 个月展望** — 按季度设置决策检查点，并与已验证的资源、证据、负责人和审批条件关联。
11. **营销运营技术栈** — 将可用的营销技能和已授权的集成映射到每个 AARRR 阶段、负责人、评审关卡和备用方案。
12. **战术创意库** — `suede-marketing-ideas` 所有战术库中的创意，均与 AARRR 交叉引用，并标注基于证据的状态：当前 / 已批准测试 / 有条件 / 延后 / 跳过。
13. **衡量、RACI、待决事项、附录** — 北极星指标、各阶段的先导指标、RACI 表、阻塞性决策、指向更深层文档的链接。在编写本章节前阅读 `references/measurement-framework.md` — 其中包含本章节所汇编的北极星指标选择模式、各 AARRR 阶段的先导指标、评审节奏、KPI 目标设定、终止标准和护栏指标。

## AARRR 框架

AARRR 取代了较早的“渠道和战术”方法，因为它强制要求每条建议都标注漏斗阶段，从而让计划能够按优先顺序执行。

完整介绍见 `references/aarrr-framework.md`。快速规则：

- **获客** = 陌生人 → 建立认知（漏斗顶部）
- **激活** = 已建立认知 → 首次获得价值体验（注册、引导流程、首次会话）
- **留存** = 重复使用的用户（生命周期、流失预防、加深参与）
- **推荐** = 留存用户 → 带来更多用户（计划、病毒式传播机制）
- **收入** = 变现（定价、增购、捆绑销售、ACV 扩展）

品牌和内容是**贯穿各阶段的要素**，而不是独立的 AARRR 阶段 — 它们服务于每个阶段。

## 当前状态评分标准

计划中的“当前状态”部分依据内置的 17 部分评分标准对客户进行评分。完整评分标准见 `references/current-state-rubric.md`——它是事实来源，并非任何外部 skill 的衍生版本。

如果用户已经有一份单独评分的审计报告，请将其作为带日期的证据保留，并且仅复用那些来源、范围、群体/时间窗口和定义仍与当前状态一致的评分。否则，应使用当前材料并依据评分标准的证据门槛进行评分；对于缺乏支持的行，标记为 `Unknown`。

## 交叉引用——本计划集成的 skills

1. **`suede-marketing-ideas`** — 负责策略库及其编号。计划的第 12 节将每项策略与 AARRR 和客户状态进行交叉引用；该 skill 的参考资料负责策略数量及证据立场。详见 `references/idea-cross-reference.md`。
2. **`suede-product-marketing`** — 建立基础的 `.agents/product-marketing.md` 上下文文件（定位、ICP、语调）。请先阅读此文件；第 2 节（战略框架）将在此基础上展开。
3. **特定 AARRR 阶段的 skills** — `suede-onboarding`、`suede-signup`、`suede-emails`、`suede-referrals`、`suede-pricing` 等。“营销运营栈”（第 11 节）将这些 skills 映射到各个 AARRR 阶段。

本计划**明确主张哪些 skills 服务于哪些阶段**。完整映射见 `references/ops-stack-mapping.md`。

## 营销运营栈

这是 fCMO 风格计划区别于通用营销计划的关键所在。计划不仅说明*要做什么*，还说明*由哪些 skills 和工具来执行*。

公开的 Suede skill 包和经过验证的集成，可以让小团队更稳定地重复执行获批的工作流。计划必须明确展示这一运营栈，按照 AARRR 阶段逐一说明，但不得声称工具可以替代人员配置或保证产出效率；实际产能仍取决于客户的数据、负责人、审核流程和运营约束。

完整映射见 `references/ops-stack-mapping.md`。

## 有条件的能力解锁

每份计划都必须说明预算到位后会发生什么变化，但融资阶段本身绝不能决定支出或招聘。请将 `references/funding-stage-unlocks.md` 作为问题清单。每项解锁都应基于经过验证的现金、资金可支撑时间、董事会批准的烧钱额度、经过衡量的获客能力、当前负责人和品类约束推导得出。

## 通过可追溯的假设设定预算

使用客户带日期的财务和漏斗输入来构建情景，然后由财务负责人批准最高支出、复核日期和停止条件。完整限制见 `references/budget-planning.md`：

1. **基于产能** — 从已批准的现金/资金可支撑时间上限和经过衡量的渠道产能出发；对结果范围进行建模。
2. **基于目标的情景** — 从目标反向推导，使用有来源的 ARPC、留存率、毛利率、综合 CAC 和交付产能。将结果视为敏感性模型，而不是预测或融资建议。

不要附加通用的实验占比或基于阶段的增长倍数。负责人应选择一个有上限的测试金额，确保即使公司损失这笔金额，也不会突破资金可支撑时间。

## 增长模式——SaaS 增长的真实形态

使用 `references/growth-patterns.md`，将线性、阶梯函数和分层曲线假设与带日期的客户证据进行比较。ARR 和融资阶段是背景信息，而不是普适阶段。计划必须明确不确定性、产能、复盘日期和停止条件，而不是承诺某条曲线。

## 团队与代理模式

使用 `references/team-and-agency-model.md`，在选择员工、承包商、代理机构、自动化或暂缓执行之前，先梳理结果、当前负责人、产能、访问权限、风险和持续时间。不要根据阶段或公司规模推断首位招聘对象、职位名称、供应商类型或外包比例。

## 每份计划都必须定制的内容

通用计划就是失败的计划。每份计划都必须明确针对以下内容进行定制：

1. **当前营销预算**——每月确切金额（$/mo），按项目拆分（付费投放、工具、人力、长期顾问费用）。此外还要提供混合 CAC（必须包含薪资、内容成本、工具、长期顾问费用，而不只是付费广告支出）以及当前占 ARR 的比例分配。
2. **单位经济模型**——ARPC、年度留存率、LTV。这些数据会影响第 8 节和第 10 节中的预算计算。
3. **团队构成和覆盖范围**——每一位参与营销的人员、其负责的结果、产能、技能、访问权限和审批边界。
4. **客户目前正在做什么**——按渠道列出，并标明状态（有效 / 无效 / TBD）。
5. **他们已经完成且应当被认可的工作**——过去的发布、PR 时刻、内容和合作关系。不要写一份忽略客户引以为豪的工作的计划。
6. **已观察到的增长模式**——线性、阶梯函数或分层行为的证据，以及不确定性和当前约束。
7. **有条件的能力里程碑**——能够促成招聘、启用渠道或选择供应商的确切证据、资源、审批和停止条件。
8. **与具体行动相匹配的营销技能**——AARRR 各部分中的每项行动都要注明执行该行动所需的技能。
9. **执行方式和访问权限状态**——每项行动都要注明负责人、当前产能、人工执行或工具辅助的方式、复核关卡和备用方案。工具是可选项，绝不能作为无需招聘的证据。

如果无法在 INIT 中确认其中任何一项，就将其列入第 13 节的“待决事项”中——绝不要含糊带过。**CAC 未知是影响最大的待决事项**——每一项收入预测都依赖于它。

## 常见客户类型差异

计划结构保持一致，但业务模式标签不会决定渠道、支出、节奏或人员配置。使用 `references/client-types.md` 来询问：

- 哪些带日期的漏斗证据能够确定当前约束？
- 哪些受众、意图或行为证据能够使某项渠道测试具有合理性？
- 哪些群体经济指标和交付约束会限定曝光规模？
- 谁负责工作、审批、复盘日期和停止决策？
- 哪些法律、平台、声明、同意或权利关卡适用？

将每种原型模式视为需要验证的候选方案，而不是可以直接照搬的默认方案。

## 质量标准

优秀计划与通用计划的区别在于：

**良好计划的信号：**
- 每项行动都注明其服务的 AARRR 阶段
- 每项建议都基于真实客户数据（其实际预算、实际团队、实际现有渠道）
- 90 天路线图明确负责人，而不仅仅是行动项
- 条件性能力明确解锁所需的已验证资源、证据、负责人、审批、审查日期和停止条件
- 运营技术栈部分针对每项行动列出具体技能 + MCP
- 创意库展示我们*不*做什么及其原因（包含附带理由的跳过创意）
- 高管摘要可独立阅读——可直接用于投资者更新
- 未决决策明确列出，而非一笔带过

**应避免的失败模式：**
- 罗列策略但没有排序
- 推荐团队以当前规模无法执行的事项
- 在当前证据和可问责的决策确认之前，假定付费预算、渠道准备度或审批已经存在
- 对令人不适的指标（例如流失率）一笔带过，而不是将其明确为未决决策
- 使用泛泛的表述（“建设社群”“改善 SEO”）而没有具体行动
- 忽略品牌声音——计划的每个部分都必须遵守客户的声音规则
- 用客户实际不需要的技能/创意填充计划
- 未承认团队已经完成的工作

## 输出格式

最终交付物是单个 Markdown 文件：`.agents/suede-marketing-plans/{client-slug}/final_plan.md`。

标题（`## 1. Executive summary` 等）使用 H2，以便干净地粘贴到 Notion。任何结构化比较均使用表格（RACI、创意库、运营技术栈）。为创意库提供状态图例。对其他章节的内部引用使用 `§N`（例如，“参见 §5 了解 Activation 详情”）。

篇幅预期：一份综合计划约为 8,000–12,000 字。若客户处于早期阶段、可覆盖范围有限，则可以更短；若客户有多年历史需要予以确认，则可以更长。

## 每份计划的文件布局

```text
.agents/suede-marketing-plans/
└── {client-slug}/
    ├── materials/         # 客户提供的文件（演示文稿、审计输出、品牌声音文档等）
    ├── research.md        # 在 INIT 期间编写的研究记录
    ├── progress.md        # 状态机——阶段、current_section、已批准的产物、plan_version
    ├── sections/
    │   ├── 01.md          # 每个已批准章节均保存为规范产物
    │   └── ...            # 使用零填充，以便按顺序排序
    └── final_plan.md      # 汇编后的交付物（FINALIZE 输出）
```

`progress.md` 的完整架构和恢复决策树位于 `references/methodology.md` 的步骤 1.1.1 和 1.1.2 中。

## 任务专属问题（在 INIT 期间使用）

完整的访谈问卷位于 `references/methodology.md`。最重要的问题：

1. **财务背景** — 哪些现金、资金续航底线、已批准支出、承诺、融资条件和决策日期会约束该计划？融资轮次标签仅供参考。
2. **团队** — 所有参与营销的人员有哪些？每个人负责什么？存在哪些缺口？
3. **预算** — 当前每月营销支出是多少，按付费获客、工具、外包服务和人员成本细分？任何增加支出由哪些确切证据、产能、审批、最大风险敞口、审查日期和停止条件约束？
4. **当前渠道** — 哪些带日期的来源、队列、指标定义和归因窗口支持“有效”“无效”或“未知”的判断？哪些未经尝试的渠道假设具备受众证据和已批准的测试？
5. **已完成事项** — 本计划应确认哪些过往营销活动 / 发布 / 内容 / 公关时刻？
6. **进行中事项** — 哪些内容已起草但尚未发布？每项内容的阻碍是什么？
7. **工具技术栈** — 哪些已经接通？Customer.io / Mailchimp / Resend？Shopify / Stripe / App Store Connect？GA4 / Mixpanel / Amplitude？GitHub / Notion / Figma？
8. **Beta 还是 GA？** — 如果产品处于 beta 阶段，GA 时间线是什么？是否有节流限制？存在哪些门槛？
9. **本季度最重要的修复事项** — 创始人的判断。
10. **本季度最重要的忽略事项** — 哪些看起来重要但实际上并不重要。

## 计划应当多么详尽？

默认应当写得全面。创始人会与团队和投资者分享计划；在这里追求简短是因小失大。一份结构合理的 10,000 字计划，比一份遗漏运营技术栈或创意库的 3,000 字计划更有用。

不过，不要为了凑字数而填充内容。每个部分都应当**信息密度高，而不是臃肿**。如果某个部分没有内容可写，就明确写出来——“已延期——当前规划周期内没有获批的测试或负责人”既诚实又有用。

## 关于语气的说明

这份计划面向的是敏锐、忙碌且对营销话术持怀疑态度的创始人。要像一位经过深思熟虑的同事那样写，而不是像演示文稿撰写人那样写。不要为了使用术语而使用术语。直接陈述主张，明确列出权衡，说明假设。不确定时，要指出待解决的问题，而不是随意猜测。

执行摘要应当足够简短，能在 60 秒内读完。其余内容则应值得读者深入阅读。

## 边界

- 不要虚构市场证据、客户研究、预算、团队产能、转化数据、资金或实施状态。
- 未经明确授权，不要发布计划、分配支出、联系供应商、创建营销活动或更改运营系统。
- 不要将预测、比较对象、情景或有条件的能力表述为保证。
- 在所需负责人尚未批准的情况下，不要自行决定法律、财务、招聘、品牌风险或高管层面的权衡。

## 路由

- 使用 `suede-product-marketing` 处理定位，使用 `suede-customer-research` 处理客户之声证据。
- 使用 `suede-marketing-ideas` 获取更广泛的选项集，使用 `suede-marketing-loops` 处理已获批准的周期性运营。
- 当一项战略押注存在争议时——例如有两个都站得住脚的方向、一项不可逆的承诺，或一项用户数月内都无法重新审视的押注——使用 `suede-marketing-council`。
- 使用 `suede-marketing-psychology` 说明某个 Activation 或 Revenue 动作背后的行为机制，并将其表述为可测试的假设。
- 使用 `suede-onboarding`、`suede-emails`、`suede-referrals` 或 `suede-pricing` 执行生命周期运营。
- 使用 `suede-seo-audit`、`suede-programmatic-seo`、`suede-ads` 或 `suede-ad-creative` 执行获客。
- 使用 `suede-launch-packaging` 处理发布时刻。
