# 布局

在文字被读到之前，位置、间距和对齐就已经传达了层级关系。这项技能构建并压力测试这种结构：调整大小、转换方向，以及为 RTL 镜像翻转。

将每项修复都写入项目的样式系统。下面的数值是针对尚未建立密度系统的界面的起始值；如果项目已有密度系统，应按其定义使用，而不是用看似熟悉的替代值。只要仍能通过压力测试，就保留有意设计的平台界面元素、紧凑的专业工具和项目令牌。

点击区域和焦点行为属于 `better-accessibility`。圆角、阴影和动画属于 `better-ui`。行长和文本间距属于 `better-typography`。

## 用空间分组，而不是用线

优先用空间分组，其次使用背景形状，最后才使用分隔线，并且只在仅靠空间无法传达结构时使用。组与组之间的间距至少必须是组内间距的 2×（组内 `8px`，组间 `16px`+），否则分组会显得杂乱。对齐边缘和重要性排序见 [grouping-and-alignment.md](grouping-and-alignment.md)。

## 让控件与内容保持区分

为每个交互元素提供背景形状、边框或一致的放置区域。控件如果采用与旁边静态文本相同的样式，就无法被识别为控件。

## 对齐到共享边缘

确定对齐边缘并始终坚持使用；每一条偏离的边缘都会显得杂乱。每个从属层级使用一个项目间距步长，其中 `16px` 是一个实用的默认值。

对于依赖方向的布局，使用逻辑属性：`padding-inline-start`、`margin-inline-end`。只有在确实表示物理几何关系时，才使用物理上的 left 和 right。

## 按重要性排序

最重要的内容应位于靠近顶部和起始边缘的位置。阅读顺序从上到下、从起始端到末尾端流动。思考时使用起始端和末尾端，而不是左和右。

## 暗示隐藏内容

渐进式披露需要一个可见的提示。使用项目已确立的提示方式，或者让下一个项目从滚动边缘露出 `16–32px`，也可以显示一个披露控件。隐藏内容时完全没有提示，效果就和不存在一样。

## 在目标之间留出呼吸空间

如果尚未建立密度系统，请从相邻的带边框或填充控件之间留出 `12px` 开始；对于无边框的纯文本或纯图标控件，周围留出 `24px`。紧凑布局可以使用更小的间距，只要 `better-accessibility` 的点击区域不重叠，并且控件仍能保持区分。布局边距和断点方案见 [spacing-and-adaptivity.md](spacing-and-adaptivity.md)。

## 让按钮与边缘保持内缩

在内容布局中，将全宽按钮放在布局边距内，并使用清晰可见的圆角；在移动端，可以从接近 `16px` 的内联间距开始。边到边的操作在遵循既有平台界面元素、考虑安全区域并且能与系统 UI 保持区分时才适用。

## 内容延伸，控件浮动

背景和媒体延伸至视口边缘。控件和文本保持在布局边距及安全区域（`env(safe-area-inset-*)`）内。固定界面元素应浮在内容层之上，而不是遮挡内容。

## 在结构崩溃前保持它

断点应由内容决定，而不是设备预设决定。只要展开布局确实能够容纳，就尽可能长时间地保持展开，并尽晚折叠。组件级适配优先使用容器查询，并先测试最小和最大尺寸。

## 为增长和裁切做好规划

翻译后的字符串会变长，而较短的字符串按比例增长得更多，因此单词按钮标签是屏幕上风险最高的元素。不要为文本容器设置固定宽度或高度，并让行自动换行。使用伪本地化和一种具有代表性的语言环境进行测试，而不是预留某个百分比的空间。

不要把关键操作放在调整大小或滚动时容易被裁切的位置。将其保留在正常文档流中，或放在适合产品的稳定界面区域中。

## 完成之前

| 错误 | 修复 |
| --- | --- |
| 本地化布局中使用 `margin-left` / `padding-right` | 使用 `margin-inline-start` / `padding-inline-end` |
| 内容布局按钮贴近视口边缘 | 在项目边距内缩进；保留有意设置的平台界面区域 |
| 因为 768/1024 是默认值，就在这些位置设置断点 | 在内容实际无法继续容纳的位置设置断点 |
| 按照一种语言的长度为文本容器设置固定宽度 | 使用 `max-width` 并允许换行；测试伪本地化 |
| 窗格底部容易被裁切的位置放置主要操作 | 使用粘性定位，或使用带安全区域内边距的稳定界面区域 |

## 报告

**严重程度。** `HIGH` 会阻挡受支持视口中的内容或操作。`MEDIUM` 会损害层级结构、阅读顺序或适应性。`LOW` 是孤立的对齐或间距问题。

**验证。** 不使用浏览器时：检查是否使用逻辑属性替代物理属性，容器查询和媒体查询是否针对受支持的视口列表，以及 DOM 顺序是否符合预期的阅读顺序。使用浏览器时：检查每个受支持的宽度、200% 缩放和 RTL 镜像。将所有无法执行的检查报告为 `Not verified`。

**格式。** 按每项违反的原则对发现的问题分组，按严重程度排序；每个根本原因占一行，并列出其出现的所有位置：

| 严重程度 | 位置 | 修改前 | 修改后 | 原因 |
| --- | --- | --- | --- | --- |

`Location` 的格式为 `path/to/file:line`。`Why` 应说明违反的原则以及对用户的影响。

只要仍有任何 `HIGH` 问题，就以 `Block` 结尾；否则以 `Approve` 结尾，并将其余问题保留在表格中作为待处理事项。不要批准未检查的覆盖范围。如果没有需要报告的内容，请说明 "No actionable layout findings"，并报告验证结果。
