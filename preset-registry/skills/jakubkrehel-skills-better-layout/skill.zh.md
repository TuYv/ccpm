# 布局

位置、间距和对齐方式在人们阅读任何文字之前就已经建立了层级。此技能用于构建这种结构并对其进行压力测试：调整尺寸、翻译内容，以及为 RTL 镜像布局。

所有修复都应使用项目的样式系统。以下数值适用于尚未建立密度系统的界面，可作为起点；如果项目已有密度系统，请原样使用，而不要替换成看起来熟悉的方案。对于经过压力测试后仍然适用的平台界面元素、紧凑型专业工具和项目令牌，应保留其既有设计。

点击区域和焦点行为属于 `better-accessibility`。圆角、阴影和动画属于 `better-ui`。行长和文本间距属于 `better-typography`。

## 使用间距而非线条进行分组

优先使用间距分组，其次使用背景形状，最后才使用分隔线，并且仅在单靠间距无法体现结构时使用。组间间距必须至少是组内间距的 2 倍（组内 `8px`，组间 `16px` 或更大），否则分组会显得杂乱。有关对齐边缘和重要性排序的内容，请参阅 [grouping-and-alignment.md](grouping-and-alignment.md)。

## 让控件与内容保持明显区别

为每个交互元素提供背景形状、边框或一致的放置区域。如果控件的样式与旁边的静态文本相同，它看起来就不像控件。

## 对齐到共同边缘

选定对齐边缘并始终遵循；任何偏离的边缘都会显得杂乱。每增加一级从属关系，就使用一个项目间距步长，`16px` 是一个实用的默认值。

对于与方向相关的布局，请使用逻辑属性：`padding-inline-start`、`margin-inline-end`。仅在处理真正的物理几何关系时使用物理意义上的左侧和右侧。

## 按重要性排序

最重要的内容应靠近顶部和起始边缘。阅读顺序从上到下、从起始侧到结束侧。应从起始侧和结束侧的角度思考，而不是左侧和右侧。

## 提示隐藏内容

渐进式披露需要可见的提示。使用项目已有的提示方式，或让下一项越过滚动区域边缘露出 `16–32px`，或显示披露控件。没有任何提示的隐藏内容等同于不存在。

## 在目标之间留出空间

如果没有现成的密度系统，相邻的带边框或填充控件之间可从 `12px` 开始，无边框的纯文本和纯图标控件周围可从 `24px` 开始。紧凑型布局可以使用更小的间距，前提是 `better-accessibility` 点击区域不重叠，并且控件仍能彼此区分。有关布局边距和断点方案，请参阅 [spacing-and-adaptivity.md](spacing-and-adaptivity.md)。

## 让按钮与边缘保持内缩

在内容布局中，应将全宽按钮放置在布局边距以内，并保留清晰可见的圆角；在移动端，行内方向的起始边距可从 `16px` 左右开始。如果贴边操作遵循既有的平台界面元素规范、考虑了安全区域，并且能够与系统 UI 清晰区分，也可以采用边到边布局。

## 内容延伸至边缘，控件悬浮其上

背景和媒体延伸至视口边缘。控件和文本应位于布局边距和安全区域（`env(safe-area-inset-*)`）以内。吸附式界面元素应悬浮在内容层上方，而不是遮挡内容。

## 保持结构，直到无法容纳

断点应由内容决定，而不是设备预设。只要展开布局确实能够容纳内容，就应继续保持，并尽可能晚地折叠。组件级适配优先使用容器查询，并首先测试最小和最大尺寸。

## 为内容增长和裁剪做好规划

翻译后的字符串会变长，而且短字符串的增长比例更大，因此只有一个单词的按钮标签是屏幕上风险最高的元素。不要为文本容器设置固定宽度或高度，并允许行换行。使用伪本地化和一种具有代表性的语言区域进行测试，而不是按百分比预留空间。

绝不要把关键操作放在会因调整大小或滚动而被裁剪的位置。应将其保留在正常文档流中，或放在适合该产品的稳定界面框架中。

## 完成之前

| 错误 | 修复方式 |
| --- | --- |
| 在可本地化布局中使用 `margin-left` / `padding-right` | 使用 `margin-inline-start` / `padding-inline-end` |
| 内容布局中的按钮紧贴视口边缘 | 在项目边距内缩进；保留有意设计的平台界面框架 |
| 因为 768/1024 是默认值而在这些位置设置断点 | 在内容确实无法继续容纳的位置设置断点 |
| 根据单一语言设置固定宽度的文本容器 | 使用 `max-width` 并允许换行；测试伪本地化 |
| 主要操作位于窗格底部容易被裁剪的位置 | 使用粘性定位，或使用带安全区域内边距的稳定界面框架 |

## 报告

**严重性。** `HIGH` 表示在支持的视口中阻挡内容或操作。`MEDIUM` 表示损害层次结构、阅读顺序或适应能力。`LOW` 表示孤立的对齐或间距优化问题。

**验证。** 无浏览器时：检查是否使用逻辑属性代替物理属性，根据支持的视口列表检查容器查询和媒体查询，并根据预期阅读顺序检查 DOM 顺序。有浏览器时：检查每个支持的宽度、200% 缩放和 RTL 镜像。将每项无法执行的检查报告为 `Not verified`。

**格式。** 按发现项所违反的原则分组，并按严重性排序；每个根本原因占一行，列出其出现的所有位置：

| 严重性 | 位置 | 修改前 | 修改后 | 原因 |
| --- | --- | --- | --- | --- |

`Location` 的格式为 `path/to/file:line`。`Why` 应说明所违反的原则以及对用户的影响。

如果仍有任何 `HIGH`，以 `Block` 结尾；否则以 `Approve` 结尾，并将其余问题保留在表格中作为待办工作。绝不要对未检查的覆盖范围给出 `Approve`。如果没有需要报告的内容，请注明“No actionable layout findings”，并报告验证情况。
