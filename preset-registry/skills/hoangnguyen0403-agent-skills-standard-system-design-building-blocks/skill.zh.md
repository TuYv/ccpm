# 系统构建模块

## **优先级：P1（高）**

仅为消除一个明确命名的约束而添加组件。每个组件都会增加故障模式和成本。

## 选择表

| 观察到的约束 | 组件 | 可接受的成本 |
| --- | --- | --- |
| 单个实例耗尽 CPU 或连接数 | 在负载均衡器后进行水平扩展 | 必须保持无状态；会话迁移到存储中 |
| 读 QPS 超过存储上限；数据允许一定陈旧性 | 读穿缓存 | 允许最长达 TTL 的陈旧读取；增加失效复杂度 |
| 写入突发量超过存储可持续处理的吞吐量 | 队列加异步工作进程 | 最终完成；需要幂等消费者 |
| 缓慢的非关键工作阻塞请求路径 | 后台任务或事件 | 需要额外考虑交付保证 |
| 静态或媒体字节占据大部分出口流量 | CDN | 缓存清除存在延迟；未命中时仍需要源站 |
| 各服务重复实现横切关注点：身份认证、配额、路由 | API 网关 | 集中的瓶颈点；必须具备高可用性 |
| 单个租户或键可能耗尽容量 | 速率限制器或准入控制 | 拒绝请求需要明确的客户端契约 |
| 缓存或分片节点在扩缩容期间改变数量 | 一致性哈希 | 需要重新平衡逻辑；热点键倾斜仍然存在 |

## 缓存规则

- 对于读密集型路径，默认采用 **cache-aside**；只有在写后读必须精确一致时才使用 write-through。
- 根据可容忍的陈旧性设置 TTL，而不是图方便。每个缓存键都需要明确规定 TTL 和失效触发条件。
- 保护未命中路径：当热点键过期时，single-flight 或请求合并可以防止缓存击穿。
- 永远不要缓存无法失效的数据。永远不要在共享键下缓存用户级数据。

## 队列规则

- 明确选择交付语义：至少一次交付加幂等消费者是安全的默认选择。
- 按必须保持有序的实体进行分区；顺序是分区级别的，绝不是全局的。
- 按突发量规划队列大小，并定义排空速率。无界队列会将吞吐量问题转化为延迟和内存问题。
- 当队列深度超过排空预算时，在生产者处施加背压；主动丢弃优于无声增长。

## 会话状态

- 默认使用无状态令牌（签名 JWT 或由边缘验证的不透明 ID）；应用层不保存任何用户级状态。
- 当会话必须立即可撤销，或承载的信息超过令牌容量时，迁移到共享会话存储（Redis）。
- 粘性会话是最后手段：它难以平稳应对一次部署，并且会阻碍缩容。永远不要将会话状态存储在应用内存中。

## 边缘与流量规则

- L4 对连接进行均衡，L7 根据内容进行路由；当路由需要依据路径、标头或金丝雀发布时，使用 L7。
- 健康检查必须测试依赖感知的就绪端点，而不是静态的 200。
- 在边缘按身份和成本类别进行速率限制；返回客户端能够遵循的重试提示。

## 反模式

- **没有约束就不要添加组件**：无法解决任何已声明问题的组件应当移除。
- **不要把缓存当作正确性修复手段**：缓存可以掩盖慢查询；先修复查询，再添加缓存。
- **没有消费者预算就不要使用队列**：上线前定义排空速率和 DLQ。
- **不要在应用内存中共享可变会话**：这会阻碍水平扩展。
