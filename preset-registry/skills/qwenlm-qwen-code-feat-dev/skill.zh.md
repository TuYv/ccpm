# 功能开发工作流

在 qwen-code 中实现需要设计、行为验证或跨多个文件协调变更的功能时，使用此工作流。每个阶段都会产出一个具体的工件。不要合并阶段；每个阶段的输出都会供下一阶段使用。

## 工件路径

使用以下路径存放规划工件：

- `docs/design/<feature>.md`
- `.qwen/e2e-tests/<feature>.md`

## 阶段 1：调查

了解请求的行为以及当前 qwen-code 的实现。

如果可用，请使用代码探索代理。要求它检查相关的 qwen-code 区域，包括：

- 现有功能定义：工具、参数、模式、命令、UI 或配置。
- 运行时连接：生成、生命周期、状态、权限、钩子和清理。
- 边界情况和错误处理。
- 集成点和限制。

同时检查用于定义或约束预期行为的文档、问题、测试和附近实现。如果没有可用的探索代理，则在本地完成同样的调查。

输出：当前行为、期望行为、约束条件以及带行号的关键文件路径所构成的心智模型。

## 阶段 2：设计文档

编写设计文档，涵盖：

- 问题陈述和当前状态，包括行为差距。
- 按层或组件划分的拟议变更。
- 关键设计决策及其理由。
- 受影响的文件。
- 范围边界。
- 待解决的问题。

使用段落、表格和项目符号。除非对关键数据结构必不可少，否则避免使用代码片段。可以使用 JSON 配置示例。

输出：写入磁盘的设计文档。

## 阶段 3：测试计划

使用 `e2e-testing` skill 选择测试模式。然后编写 E2E 测试计划，涵盖：

- 按能力划分的测试组：参数接受、核心行为、错误处理、清理和回归。
- 实现前后所需执行的确切命令及预期行为。
- 为相互独立的测试组指定唯一的 tmux 会话名称和临时目录。
- 哪些测试组可以由单独的 `test-engineer` 代理并行运行。

输出：写入磁盘的测试计划。

## 阶段 4：试运行

使用全局安装的 `qwen` CLI，而不是本地构建，对照当前基线验证测试计划。

当运行时支持时，为相互独立的测试组生成 `test-engineer` 代理。功能尚未实现，因此测试应当失败或显示出行为差距。如果试运行发现命令损坏、过滤条件错误或误报，则迭代测试计划。

输出：已确认可运行且具有准确实现前基线的测试计划。

## 阶段 5：实现

编辑前先阅读相关源文件。实现设计文档中描述的变更，并遵循项目约定：

- ESM 和严格的 TypeScript。
- Prettier 格式化。
- 与源文件相邻的测试。
- 除设计内容之外，不进行推测性的抽象。

实现后：

```bash
npm run build
npm run typecheck
npm run bundle
```

同时从相关软件包目录运行已变更文件对应的聚焦单元测试。

输出：能够构建并通过聚焦测试的本地实现。

## 阶段 6：验证

使用 `node dist/cli.js` 针对本地构建运行完整的 E2E 测试计划。  
在有用且可用时，派生独立的 `test-engineer` 代理。

如果测试失败，则进行诊断、修复、重新构建、重新打包并重新测试，直到所有组都通过。

输出：追加到测试计划中的 E2E 结果。

## 阶段 7：自我审计和代码审查

首先，按照 AGENTS.md 的 General
workflow 中自我审计步骤的要求，对完整 diff 进行自我审计（开放式检查以及假定有误的验证，直到连续两次检查均无问题）。如果审计修改了源代码，则返回
阶段 5-6，然后再继续自我审计。随后运行 `/review`，并提供列出所有已更改文件的审查任务。对每条评论进行分类后再采取行动：

- **有效**：确实存在的 bug 或有意义的改进。修复它。
- **误报**：审查者遗漏了上下文。跳过它。
- **过度思考**：技术上合理，但不值得增加复杂性。跳过它。

修复后，重新运行单元测试和快速 E2E 冒烟检查。

输出：处理完有效审查发现的干净实现。

## 阶段 8：收尾

除非用户要求，否则跳过。创建分支，使用 Conventional Commits 提交，推送，并使用项目 PR 模板创建草稿 PR。在适用时，将 E2E 结果作为单独的 PR 评论发布。

## 迭代规则

- 如果阶段 6 失败，则返回阶段 5，然后重新运行阶段 6。
- 如果阶段 7 发现有效问题，则修复这些问题，运行快速的阶段 6 完整性检查，然后重新运行自我审计。
- 阶段 5-7 之间的循环不得超过 3 次，除非先询问用户。
- 如果测试计划不准确，则更新它并记录原因。
