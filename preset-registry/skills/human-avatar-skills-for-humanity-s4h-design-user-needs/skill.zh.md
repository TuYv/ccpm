# 设计：用户需求

最常见的设计失败，是把错误的东西做得很好。人们不会清楚地表达需求——他们表达的是解决方案。“我想要一匹更快的马”“我需要一个更大的收件箱”“给我更多选项。”这些请求被表述为针对某个问题的解决方案，但用户并未真正说清楚这个问题。若设计师只按字面理解这些请求，就会做出更快的马、更大的收件箱、更多的选项——却完全错过背后的真正需求。

克莱顿·克里斯坦森的“待办任务”框架明确提出了这种视角转变：人们不是购买产品，而是雇用产品来完成一项任务。理解这项任务——而不是产品请求——才是设计师真正要面对的课题。唐·诺曼进一步区分了陈述需求（人们说了什么）、观察需求（人们做了什么）和潜在需求（人们尚未意识到自己需要什么，但如果展示给他们看，他们会立刻认出来）。这三种需求都很重要。其中只有一种会被直接告诉你。

本技能会分析所有这三个层次，通过结构化探询，将真正的需求与表述出来的替代诉求区分开来，并揭示真正重要的设计目标。

## 你的流程

**第 1 步：陈述请求**
准确记录对方提出的请求，使用其原本的措辞。保留原有表述——精确的语言能够揭示对方是如何界定问题的。

**界定检查：** 继续之前，确认请求及其产生的情境。用一句话说明你识别出的内容——明确提出的请求及其来源情境——然后使用 `AskUserQuestion`：
- **问题：** “我的理解是：[你用一句话对请求及其情境所作的界定]。对吗？”
- **标题：** “界定”
- **选项：**
  - **是——继续**——界定正确
  - **调整**——其中有一项不准确；用户会先进行修正，然后你再继续
  - **重新界定**——实际情况与你的理解不同；先纳入修正内容，然后再继续

**第 2 步：分解任务**
应用“待办任务”分解法。针对所陈述的请求，识别：

- **功能性任务：** 他们试图完成什么？需要达成什么结果？
- **情感性任务：** 他们希望在执行过程中有怎样的感受？完成后又希望有怎样的感受？
- **社会性任务：** 在这种情境下，他们希望他人如何看待自己？

这三类任务都是真实的设计要求。忽视情感性任务和社会性任务，会做出功能上可用、却无人愿意使用的东西。

**第 3 步：追溯情境**
梳理这项任务产生时的情境。它何时发生？由什么触发？对方之前尝试过什么？目前采用了什么变通方法，而这种方法揭示了他们认为什么程度已经足够好？变通方法是潜在需求的信号——它表明人们愿意容忍什么，进而暗示如果有更好的选择，他们会选择什么。

**第 4 步：区分陈述的愿望与真实需求**
对于请求中明确提出的每个要素，都要问：这是解决方案（一种具体形式），还是需求（一种结果）？解决方案通常可以改写为需求。“我想要一个仪表板”→“我需要无需搜索，就能同时看到多个事项的状态。”“我想关闭通知”→“我需要控制自己何时关注他人的请求。”

将所有以解决方案为框架的要素，重新表述为以需求为框架的要素。

**步骤 5：揭示潜在需求**
潜在需求之所以未被明确表达，是因为人们尚未将其设想为可能实现的事物。它们可以通过以下方式浮现：
- 询问人们对当前最佳选项有哪些不满（而不是询问任何特定解决方案）
- 询问他们希望不必做什么
- 观察人们会在哪些地方自行采用变通方法和捷径
- 询问“怎样才能让它好上十倍？”——人们很少会要求显而易见的东西；他们会想象那些尚未被构建出来的事物

列出候选潜在需求。标注每项需求的置信度。

## 人工确认

在继续之前，请使用 `AskUserQuestion` 工具。用 1–2 句话说明你对当前情况的理解——设计背景是什么，以及此处最重要的是哪类任务——然后询问：

- **问题：**“我的理解是：[用 1–2 句话说明你的理解]。你希望如何继续？”
- **标题：**“范围”
- **选项：**
  - **完整分析**——完成所有步骤，并在整个过程中展示推理
  - **仅关键发现**——只输出最终结论，跳过逐步细节
  - **聚焦任务**——深入拆解功能、情感和社会任务，跳过潜在需求
  - **重新界定**——当前理解有误；请予以纠正，后续分析将遵循修正后的框架

根据用户的选择继续。如果用户重新界定了问题，请先纳入修正内容，再进行任何分析。

## 输出格式

**明确提出的请求：**
> [原始措辞]

**待完成的任务：**

| 任务类型 | 描述 |
|---|---|
| 功能 | [他们试图完成什么] |
| 情感 | [他们希望有何感受] |
| 社会 | [他们希望他人如何看待自己] |

**当前的变通方法及其揭示的信息：**
[描述该变通方法。它对可接受的容忍范围和未满足的需求有何启示。]

**明确表达的想要之物 → 真实需求：**

| 表述为（解决方案） | 重新表述为（需求） |
|---|---|
| [解决方案框架] | [需求框架] |

**潜在需求：**
- [需求]——*置信度：高/中/推测*

**设计目标：**
> [精准表述的核心需求。用一到两句话说明。这是设计应着力解决的目标。]

## 说明

此处最常见的错误是将情感任务与一般情绪混为一谈——“他们想感到开心。”情感任务应当更加具体：他们希望感到一切尽在掌控、自己有能力、不尴尬、受到信任、高效。这些都是可以通过设计实现的。模糊的情感目标则不行。

此技能很适合与 `/s4h-design-constraints` 搭配使用——明确真实需求后，下一个问题便是哪些约束条件界定了解决方案空间。它也应先于 `/s4h-design-iteration` 使用；后者会在已有设计方向后，为测试循环提供结构。如需进行更广泛的受众分析——目标受众是谁，不同群体之间有何差异——请参阅 `/s4h-communication-audience-modeling`。

## 后续步骤

交付此输出后，使用 `AskUserQuestion` 提供下一步选项：

- **问题：**“需求已梳理。接下来做什么？”
- **标题：**“下一步”
- **选项：**
  - `/s4h-design-constraints`——梳理用于界定哪些解决方案真正可行的约束条件
  - `/s4h-design-iteration`——构建围绕这些需求进行原型设计和测试的循环
  - `/s4h-creativity-brainstorm`——既然真实需求已经明确，开始生成解决方案方向
  - **完成**——结束并综合整理目前为止的成果
