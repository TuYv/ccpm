# 文档审计员

**目标：** 将文档作为只读证据系统进行审计：新贡献者、运维人员、用户或编码智能体能否找到正确的信息源、信任其中的声明，并在没有隐藏上下文的情况下采取行动？既要审查独立文档，也要审查承载公共或运维知识的代码注释。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序处理每一项，只有当相应操作和所需证据均已完成时，才能将其标记为完成。`N/A`、跳过、不可用或已委派的项目仍视为未完成。
返回结果前，对每个未完成项目应用此技能的裁定、决策和批准规则，并在结果开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出所有未完成项目。

## 工具选择

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 文档清单和层级结构 | 使用窄范围模式的原生文件列表 | 确定文档覆盖面、生成内容区域和导航结构时 | 仓库目录树和已知入口文档 |
| 链接、重复术语、声明和矛盾 | 先使用原生文本搜索，再进行针对性阅读 | 查找引用、过时名称、重复指南、路径、命令和配置键时 | 手动进行跨文档比较 |
| 代码和配置事实 | 原生代码搜索、清单、模式定义和直接文件读取 | 文档声称某个路径、选项、端点、行为或默认值存在时 | 当文本不足以验证时，执行安全的检查命令 |
| 时效性和所有权 | Git 日志、追溯和差异比较 | 确定声明何时发生变化、文档是否与活跃代码保持同步，或谁负责某项约定时 | 当前代码和明确的所有权文件 |
| 命令和示例 | 以非修改或试运行模式使用 Shell | 验证帮助文本、命令是否存在、配置解析、生成的输出或示例语法时 | 检查命令注册和测试；将运行时证明标记为不可用 |
| 外部事实 | 官方文档、规范和发行说明 | 当前外部 API、版本、标准或平台行为会影响正确性时 | 通过 Web 调研查找第一手来源；否则标记为 `UNVERIFIED` |

不得运行会发布、迁移、部署、写入生产状态或重写文档的命令。仅在获得允许并予以披露时，才可生成缓存。

## 证据规则

| 声明类型 | 所需证据 |
|---|---|
| 仓库路径、符号、命令、配置、端点或默认值 | 当前仓库内容或安全命令的输出 |
| 外部 API、版本、标准或兼容性声明 | 与相关版本匹配的官方来源 |
| 数量或覆盖范围声明 | 可复现的查询，并注明范围和排除项 |
| 历史依据 | 仍与实现一致的当前决策记录或历史记录 |
| 建议 | 已证实的读者理解障碍、矛盾、维护成本或运维风险 |

仅当确实有受众需要缺失的知识时，缺少文档才构成一项问题。过时的陈述比缺少可选的说明更严重，因为它会引导读者采取错误的行动。

## 检查清单

### 1. 确定范围和受众

- [ ] 识别范围内的文档入口、公共文档、维护者文档、运维手册、生成的参考文档、示例和代码注释界面。
- [ ] 识别目标受众及其具体任务：理解、安装、配置、运行、故障排除、扩展或验证系统。
- [ ] 阅读适用的仓库说明，并确定文档所有权、生成命令、语言策略和单一事实来源约定。
- [ ] 在评估缺陷之前，将人工编写的文档与生成的、第三方引入的、归档的、临时的和示例内容区分开来。
- [ ] 将每个目标分类为入口/索引、参考、操作指南、解释、决策记录、生成的输出或示例；优先检查规范性文档和陈述密集的文档，然后再检查仅用于导航的文件。
- [ ] 确定哪些代码、配置、模式、测试和外部契约可以验证文档中的陈述。
- [ ] 确保审计过程为只读，并将任何无法使用的来源、命令或环境记录为限制条件。

### 2. 检查结构和可发现性

- [ ] 验证根入口文档是否说明了目的、支持的用途、先决条件、安装路径以及适合其受众的导航方式。
- [ ] 检查层次结构、标题、目录、本地导航、交叉链接、锚点，以及相关材料的放置位置是否可预测。
- [ ] 查找失效的、重定向的、区分大小写的或仓库相对路径形式的链接，并验证所链接的文件和标题是否存在。
- [ ] 识别孤立文档、重复入口、循环导航、过深的跳转链，以及只能通过仓库搜索才能找到的重要内容。
- [ ] 检查每个概念是否只有一个规范性的归属文档，以及次要文档是否通过链接引用规则、阈值或流程，而不是创建分支版本。
- [ ] 验证生成的文档是否注明其生成器，并且不会诱导用户手动编辑随后会被覆盖的内容。
- [ ] 检查是否可以拆分或压缩大型文档，同时不隐藏安全执行操作所需的顺序或上下文。

### 3. 检查相关性、覆盖范围和一致性

- [ ] 将每份文档的标题、范围说明和目标受众与其实际内容进行比较。
- [ ] 根据文档类型评判内容：索引应提供导航而不重复细节，参考文档应优化精确查找，操作指南应采用安全的步骤顺序，解释性文档应建立正确的思维模型，而决策记录应保留背景、决策、备选方案和后果。
- [ ] 标记填充内容、重复的摘要、推测性叙述、通用的生成式文本，以及无助于目标受众做出决定或采取行动的形式化章节。
- [ ] 优先记录持久的意图、契约、约束和操作方式，而不是复制实现或业务逻辑；仅保留安全执行操作所需的最少且经过验证的代码或命令示例。
- [ ] 识别偏离主题的内容、范围蔓延、未说明的先决条件、隐藏的假设，以及不再支持当前任务的章节。
- [ ] 在适用时，检查对公共行为、配置、部署、迁移、故障恢复、安全敏感操作和扩展点的覆盖情况。
- [ ] 追踪各文档中的需求和架构陈述；报告矛盾和归属不明确的问题，而不是默默选择其中一种说法。
- [ ] 查找已过时的将来时计划、已完成的 TODO、已移除的功能、旧版兼容性指南、旧目录布局，以及过时的截图或示例。
- [ ] 检查术语、实体名称、标识符、大小写和生命周期状态是否与代码及各文档保持一致。
- [ ] 验证警告、先决条件、破坏性操作、回滚步骤和失败结果是否出现在读者需要它们的位置。
- [ ] 在始终加载的代理指令文件中，标记更适合由工具强制执行的确定性格式规则，以及放置在仓库根目录而不是限定在受影响路径附近的路径特定规则。

### 4. 验证事实和示例

- [ ] 提取有关路径、文件、符号、版本、数量、命令、标志、环境变量、配置键、端口、端点、模式和默认值的重要声明。
- [ ] 在验证前构建规范化的声明台账，并按主题对重复声明进行分组，以便一次仓库检查即可发现过时的副本和跨文档矛盾。
- [ ] 根据当前仓库证据或安全命令验证每项声明；记录检查的确切来源和范围。
- [ ] 在查阅外部文档或声称当前支持情况之前，先从清单文件和锁定文件中确定已安装的版本。
- [ ] 对外部 API、弃用情况、安全标准、平台限制和兼容性声明使用官方来源。
- [ ] 仅在安全的本地或一次性环境中执行示例；否则应检查解析、测试和预期输出，并将其标记为已静态验证。
- [ ] 检查示例是否存在缺少导入、将占位符作为真实值展示、路径无效、密钥不安全、语法过时，以及输出不再与实际行为相符等问题。
- [ ] 在判定声明为错误之前，先排除示例、模板、未来计划、条件式指令和外部系统引用；仅当某项条件声明的前提条件在本项目中处于启用状态时，才对其进行验证。
- [ ] 使用可复现的查询和有据可查的排除条件验证数值计数；避免保留在缺少自动化机制时会发生偏移的汇总计数。
- [ ] 在可行的情况下，建议将易变的版本、路径、默认值、清单、生成的输出和状态快照移至权威代码、配置或生成来源；否则，应明确为防止内容悄然过时所需的来源、范围、负责人或生成/更新触发条件。
- [ ] 应用从研究到行动的门槛：只有当外部指南证明仓库内存在具体缺陷或风险时，才能将其转化为发现项。

### 5. 审查注释并生成报告

- [ ] 检查注释和文档字符串是否包含有用的设计依据、不变量、契约、副作用、失败行为和不明显的约束。
- [ ] 对照当前签名、参数、返回值、抛出的错误、副作用、可空性和生命周期义务，检查公共接口或不明显接口的文档字符串。
- [ ] 标记仅复述语法、保留历史记录、包含无效代码、承诺代码并未提供的行为，或重复本可通过名称和类型更好表达的信息的注释。
- [ ] 检查公共接口是否具备语言或生态系统所要求的文档，以及示例是否符合实际契约。
- [ ] 在报告之前，先排除有意针对受众进行的简化、框架惯例、生成的文本和已接受的遗留约束。
- [ ] 将范围内的每个文档或注释表面分类为 `KEEP`、`ADD`、`UPDATE`、`DELETE` 或 `MERGE`；仅当规范内容涵盖所有必需的受众任务和契约时，才建议删除或合并。
- [ ] 对每个候选项应用重要性和可接受替代方案门槛。要求证明其会导致读者出错、任务受阻、不安全操作、内容矛盾，或按仓库现有规模产生反复的维护成本。排除吹毛求疵、行文偏好、理论上的纯粹性、通用最佳实践，以及合理的受众或维护权衡；当多种结构均可行时，应要求达成读者结果，而非采用某一种偏好的格式。
- [ ] 在每个发现项要求的解决方案中加入直接相关的 Markdown 实践链接：优先使用当前官方文档或规范；仅当官方来源无法解决相关权衡时，才使用信誉良好的第一手工程资料。打开并验证来源；来源必须支持所建议的机制，而不能仅与缺陷类别相关。排除搜索结果链接、泛泛的最佳实践文章和装饰性引用。
- [ ] 根据错误操作、无法运行、维护偏移或轻微阻碍所造成的危害，将发现项分类为 `P0`-`P3`。
- [ ] 为每个发现项提供文档位置、验证证据、受影响的受众、影响、当前折中方案不可接受的原因，以及最小且充分的修正方案或规范负责人，同时允许采用等效解决方案。
- [ ] 当安全关键声明、必需的受众操作流程或权威来源在没有可信替代方案的情况下无法验证时，使用 `BLOCKED`；当证据证明指南不安全、必需的操作流程无法执行，或存在尚未解决的 `P0/P1` 时，使用 `FAIL`；仅将 `CONCERNS` 用于实质性但不会造成阻塞的信任缺口；只有在必需的声明和操作流程均已验证且不存在实质性发现项时，才使用 `PASS`。
- [ ] 返回结论，并包含已审计范围、已验证和未验证的声明、按优先级排序的发现项、盲区和剩余信任风险。

## 输出契约

```markdown
# Documentation Audit

**Verdict:** PASS | CONCERNS | FAIL | BLOCKED

## Scope and audiences
- Documents and comment surfaces audited
- Audiences and tasks considered
- Exclusions and generated content

## Trust summary
| Area | Status | Evidence |
|---|---|---|
| Structure | PASS / CONCERNS / FAIL | ... |
| Coverage | PASS / CONCERNS / FAIL | ... |
| Factual accuracy | PASS / CONCERNS / FAIL | ... |
| Durability and SSOT | PASS / CONCERNS / FAIL | ... |
| Comments and examples | PASS / CONCERNS / FAIL | ... |

## Document actions
| Surface | Action | Evidence |
|---|---|---|
| ... | KEEP / ADD / UPDATE / DELETE / MERGE | ... |

## Findings
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete documentation or comment defect | Location, repository, command, or official evidence; affected audience and material impact; why the current tradeoff is not acceptable | Smallest sufficient correction, canonical owner, and a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent structures that preserve the required reader outcome |

Use `None` when no candidate survives the evidence, materiality, audience-need, and acceptable-alternative gates.

## Unverified claims and residual risks
Claims that could not be checked, why, and the evidence still required.
```
