# 文档审计员

**目标：** 将文档作为只读证据系统进行审计：新贡献者、运维人员、用户或编码代理能否找到正确来源、信任其中的声明，并在没有隐藏上下文的情况下采取行动？同时审查独立文档和承载公共或运维知识的代码注释。

**执行契约：** 有序复选框是完成定义。内部将每项跟踪为 `PENDING`、有具体证据的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每个部分完成后重新核对各项。返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将技能的判定和批准规则应用于每个缺口。
保留用户意图、范围和现有授权。继续执行已授权的工作；仅针对仍未解决且会产生重大影响的选择或所需的外部批准进行询问。根据实质风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 文档清单和层级结构 | 使用窄匹配模式的原生文件列表 | 建立文档界面、生成区域和导航结构时 | 仓库树和已知入口文档 |
| 链接、重复术语、声明和矛盾 | 原生文本搜索，然后进行定向阅读 | 查找引用、过时名称、重复指导、路径、命令和配置键时 | 跨文档手动比较 |
| 代码和配置事实 | 原生代码搜索、清单、模式和直接文件读取 | 文档声称某个路径、选项、端点、行为或默认值存在时 | 当文本不足以完成验证时，执行安全的检查命令 |
| 新鲜度和归属 | Git log、blame 和 diff | 确定声明何时变更、文档是否跟踪活跃代码，或谁负责某项约定时 | 当前代码和明确的归属文件 |
| 命令和示例 | 以非变更或 dry-run 模式运行 Shell | 验证帮助文本、命令是否存在、配置解析、生成输出或示例语法时 | 检查命令注册和测试；将运行时证明标记为不可用 |
| 外部事实 | 官方文档、规范和发行说明 | 当前外部 API、版本、标准或平台行为会影响正确性时 | 基于主要来源进行 Web 研究；否则标记为 `UNVERIFIED` |

不得运行会发布、迁移、部署、写入生产状态或重写文档的命令。仅当获得许可并进行披露时，才可生成缓存。

## 证据规则

| 声明类型 | 所需证据 |
|---|---|
| 仓库路径、符号、命令、配置、端点或默认值 | 当前仓库或安全的命令输出 |
| 外部 API、版本、标准或兼容性声明 | 与相关版本匹配的官方来源 |
| 数量或覆盖率声明 | 包含范围和排除项的可复现查询 |
| 历史原因 | 仍与实现相符的当前决策记录或历史 |
| 建议 | 已证明的读者失败、矛盾、维护成本或运维风险 |

只有当真实受众确实需要缺失的知识时，缺少文档才算问题。应根据过时或缺失的指导会导致读者何种失败或损害来判断。

## 检查清单

### 1. 确定范围和受众

- [ ] 识别范围内的文档入口、公开文档、维护者文档、运维手册、生成的参考文档、示例，以及代码注释界面。
- [ ] 识别目标受众及其具体任务：理解、安装、配置、运行、故障排查、扩展或验证系统。
- [ ] 阅读适用的仓库说明，并确认文档所有权、生成命令、语言策略和权威来源约定。
- [ ] 在评估缺陷前，将编写的文档与生成内容、供应商内容、归档内容、临时内容和示例内容区分开。
- [ ] 将每个目标分类为入口/索引、参考文档、操作指南、说明文档、决策记录、生成内容或示例；在仅用于导航的文件之前，优先处理权威文档和声明密集型文档。
- [ ] 明确哪些代码、配置、架构、测试和外部契约可以验证文档声明。
- [ ] 保持审查只读，并记录任何不可用的源、命令或环境，作为限制条件。

### 2. 检查结构和可发现性

- [ ] 验证根入口文档是否说明了适合其受众的用途、支持范围、前置条件、安装路径和导航方式。
- [ ] 检查层级、标题、目录、文档内导航、交叉链接、锚点和相关内容的可预测位置。
- [ ] 验证本地路径和锚点，包括大小写敏感性；检查外部重定向是否指向错误或不可用的目标；有意设计且正常工作的重定向不算问题。
- [ ] 识别孤立文档、重复入口、循环导航、过深的导航链，以及只能通过仓库搜索找到的重要内容。
- [ ] 检查每个概念是否有唯一的权威归属，次要文档应通过链接引用规则、阈值或流程，而不是复制分叉。
- [ ] 验证生成的文档是否注明生成器，并且没有引导用户手动编辑会被覆盖的内容。
- [ ] 检查大型文档是否可以拆分或压缩，同时不隐藏安全执行所需的顺序或上下文。

### 3. 检查相关性、覆盖范围和一致性

- [ ] 将每篇文档的标题、范围声明和目标受众与其实际内容进行比较。
- [ ] 根据文档类型评估内容：索引应负责路由而不重复细节，参考文档应便于精确查找，操作指南应按安全顺序编排，说明文档应帮助建立正确的心智模型，决策记录应保留背景、决策、备选方案和后果。
- [ ] 标记无实际帮助的填充内容、重复摘要、推测性叙述、通用生成文本和仪式性章节。
- [ ] 优先保留持久的意图、契约、约束和运维信息，而不是复制实现细节或业务逻辑；仅保留安全执行所需的、经过验证的最少代码或命令示例。
- [ ] 识别跑题内容、范围蔓延、未解释的前置条件、隐藏假设，以及不再支持当前任务的章节。
- [ ] 在适用的情况下，检查对公开行为、配置、部署、迁移、故障恢复、安全敏感操作和扩展点的覆盖情况。
- [ ] 跨文档追踪需求和架构声明；报告矛盾和归属不明之处，不要擅自选择其中一种解释。
- [ ] 查找过时的将来时计划、已完成的 TODO、已移除的功能、旧版兼容性指导、过时的目录布局，以及陈旧的截图或示例。
- [ ] 检查术语、实体名称、标识符、大小写和生命周期状态是否与代码及其他文档保持一致。
- [ ] 验证警告、前置条件、破坏性操作、回滚步骤和失败结果是否出现在读者需要它们的位置。
- [ ] 在始终加载的代理指令中，识别工具已经强制执行的冗余格式说明，以及可以移至受支持的作用域文件中的路径特定细节。保留发现机制、非显而易见的要求和主机兼容性。

### 4. 验证事实和示例

- [ ] 提取有关路径、文件、符号、版本、数量、命令、标志、环境变量、配置键、端口、端点、架构和默认值的实质性声明。
- [ ] 在验证前构建规范化的声明台账，并按主题对重复声明分组，以便一次仓库检查即可发现陈旧副本和跨文档矛盾。
- [ ] 根据当前仓库证据或安全命令验证每项声明；记录检查的确切来源和范围。
- [ ] 在查阅外部文档或声称当前支持情况之前，先从清单和锁文件中解析已安装版本。
- [ ] 对外部 API、弃用、安全标准、平台限制和兼容性声明使用官方来源。
- [ ] 仅在安全的本地或一次性环境中执行示例；否则检查解析、测试和预期输出，并标记为静态验证。
- [ ] 检查示例是否缺少导入、将占位符当作真实值呈现、路径无效、存在不安全的密钥、语法已过时，以及输出是否不再匹配行为。
- [ ] 在其声明的上下文中解读示例、模板、未来计划和外部引用。即使当前处于禁用状态，也要针对受支持的前提条件验证条件性指南；不要将假设性示例判定为已部署行为。
- [ ] 使用可复现的查询和已记录的排除项验证数字统计；避免保留会在没有自动化的情况下漂移的汇总统计。
- [ ] 在可行的情况下，建议将易变的版本、路径、默认值、清单、生成输出和状态快照迁移到权威代码、配置或生成来源；否则，明确来源、范围以及防止静默陈旧所需的负责人或生成/更新触发条件。
- [ ] 应用从研究到行动的门槛：外部指南仅在证明仓库内存在具体缺陷或风险时，才能成为一项发现。

### 5. 审查注释并生成报告

- [ ] 检查注释和文档字符串是否包含有用的原理、约束条件、契约、副作用、失败行为和不明显的限制。
- [ ] 将公共或不明显接口的文档字符串与当前签名、参数、返回值、抛出的错误、副作用、可空性和生命周期义务进行核对。
- [ ] 标记语法复述、过时历史、死代码、虚假承诺，以及更适合通过名称或类型表达的信息；保留仍能解释约束或防止已知回归的历史原理。
- [ ] 检查公共接口是否具有语言或生态系统要求的文档，以及示例是否符合实际契约。
- [ ] 在报告前过滤有意的受众简化、框架约定、生成的文案和已接受的遗留约束。
- [ ] 将每个范围内的文档或注释表面分类为 `KEEP`、`ADD`、`UPDATE`、`DELETE` 或 `MERGE`；仅当规范性覆盖保留每项所需的受众任务和契约时，才建议删除或整合。
- [ ] 应用实质性门槛：要求存在具体的读者错误、受阻任务、不安全操作、矛盾，或具有证据规模的重复维护成本。排除品味、理论纯粹性、通用实践、假设性规模和合理替代方案；要求说明结果或约束，而非偏好的实现。
- [ ] 基于版本匹配的官方契约提出外部修正，并使用主要工程来源处理未解决的权衡。引用受支持的机制；本地缺陷可由本地证据证明。
- [ ] 根据错误操作造成的损害、无法运行、维护漂移或轻微摩擦，将发现分类为 `P0`-`P3`。
- [ ] 当安全关键声明、所需受众旅程或权威来源无法在具有可信回退方案的情况下验证时，使用 `BLOCKED`；当证据证明存在不安全指南、所需旅程无法运行，或存在未解决的 `P0/P1` 时，使用 `FAIL`；仅将实质性但不阻塞的信任缺口标记为 `CONCERNS`，并且仅当所需声明和旅程均已验证且不存在实质性发现时标记为 `PASS`。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或已授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时，每个字段可以占一行；省略空表格，不要复制链接工件：

1. **结果：** Skill-specific 结论及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill-specific 字段；区分事实、推断和未经验证的声明。链接工件；适用时使用表格。对每个纳入范围的表面记录 `KEEP / ADD / UPDATE / DELETE / MERGE`；允许使用等价结构。
4. **验证：** 检查/结果、不可用的证据、适用的清理工作和外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每项 `UNPROVEN` 的原因、对结果的影响以及确切的后续操作；说明剩余风险和所需决策。

**Skill-specific 证据：** 文档受众和用户旅程；结构、覆盖范围、准确性、持久性/SSOT 以及注释可信度。对每个纳入范围的表面记录 `KEEP / ADD / UPDATE / DELETE / MERGE`。发现项需要包含优先级、文档位置、验证证据、受影响的受众、实质性影响、不可接受的权衡，以及最小修正或规范所有者；允许使用等价结构。区分未经验证的声明和已证实的缺陷。
