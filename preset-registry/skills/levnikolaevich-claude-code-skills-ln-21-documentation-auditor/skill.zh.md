# 文档审计员

**目标：** 将文档作为只读证据系统进行审计：新的贡献者、运维人员、用户或编码代理能否找到正确的来源、信任其中的声明，并在无需隐藏上下文的情况下采取行动？同时审查独立文档和承载公开知识或运维知识的代码注释。

**执行契约：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框都标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用表明其条件触发因素不存在的证据将其解决为 `CLEARED`，或将其标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。
返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，将此技能的裁决、决策和批准规则应用于每个 `UNPROVEN`，并在开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | 部分/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 文档清单和层级结构 | 使用窄范围模式的原生文件列表 | 建立文档范围、生成区域和导航结构时 | 仓库树和已知入口文档 |
| 链接、重复术语、声明和矛盾 | 原生文本搜索，然后进行重点阅读 | 查找引用、过时名称、重复指导、路径、命令和配置键时 | 手动进行跨文档比较 |
| 代码和配置事实 | 原生代码搜索、清单、架构和直接文件读取 | 文档声称某个路径、选项、端点、行为或默认值存在时 | 当文本不足以确认时，执行安全的检查命令 |
| 新鲜度和所有权 | Git 日志、blame 和 diff | 确定某项声明何时发生变化、文档是否跟踪活跃代码，或谁负责某项约定时 | 当前代码和明确的所有权文件 |
| 命令和示例 | 以非变更或试运行模式运行 Shell | 验证帮助文本、命令存在性、配置解析、生成的输出或示例语法时 | 检查命令注册和测试；将运行时证明标记为不可用 |
| 外部事实 | 官方文档、规范和发行说明 | 当前外部 API、版本、标准或平台行为会影响正确性时 | 通过一手来源进行网络研究；否则标记为 `UNVERIFIED` |

不要运行会发布、迁移、部署、写入生产状态或重写文档的命令。仅在获准且已披露的情况下，才可使用生成的缓存。

## 证据规则

| 声明类型 | 所需证据 |
|---|---|
| 仓库路径、符号、命令、配置、端点或默认值 | 当前仓库或安全命令的输出 |
| 外部 API、版本、标准或兼容性声明 | 与相关版本匹配的官方来源 |
| 数量或覆盖率声明 | 具有明确范围和排除项的可复现查询 |
| 历史原因 | 仍与实现相匹配的当前决策记录或历史记录 |
| 建议 | 已证实的读者失败、矛盾、维护成本或运维风险 |

只有当确实存在需要这些缺失知识的受众时，缺少文档才算作一个问题。过时的声明比缺少可选说明更严重，因为它会引导读者采取错误的行动。

## 检查清单

### 1. 确定范围和受众

- [ ] 确定范围内的文档入口、公开文档、维护者文档、运维操作手册、生成的参考文档、示例以及代码注释等载体。
- [ ] 确定目标受众及其具体任务：理解、安装、配置、运行、故障排查、扩展或验证系统。
- [ ] 阅读适用的仓库说明，并识别文档归属、生成命令、语言政策以及事实来源约定。
- [ ] 在评估缺陷之前，将手工编写的文档与生成内容、第三方引入内容、归档内容、临时内容和示例内容区分开。
- [ ] 将每个目标分类为入口/索引、参考文档、操作指南、说明文档、决策记录、生成输出或示例；优先检查规范性文档和声明密集型文档，而不是仅用于导航的文件。
- [ ] 明确哪些代码、配置、架构、测试和外部契约可以验证文档中的声明。
- [ ] 保持审计只读，并将任何不可用的源、命令或环境记录为限制条件。

### 2. 检查结构和可发现性

- [ ] 验证根入口文档是否说明了适合其受众的用途、支持范围、前置条件、安装路径和导航方式。
- [ ] 检查层级、标题、目录、局部导航、交叉链接、锚点以及相关材料是否位于可预期的位置。
- [ ] 查找失效、重定向、区分大小写或相对于仓库的链接，并验证链接指向的文件和标题是否存在。
- [ ] 识别孤立文档、重复入口、循环导航、过深的导航链，以及只能通过仓库搜索找到的重要内容。
- [ ] 检查每个概念是否有唯一的规范归属文档，以及次级文档是否通过链接引用规则、阈值或流程，而不是各自分叉出一份。
- [ ] 验证生成的文档是否标明其生成器，并且没有诱导用户手动编辑那些会被覆盖的内容。
- [ ] 检查大型文档是否可以拆分或压缩，同时不隐藏安全行动所需的顺序或上下文。

### 3. 检查相关性、覆盖范围和一致性

- [ ] 将每份文档的标题、范围声明和目标受众与其实际内容进行比较。
- [ ] 根据文档类型评估内容：索引应负责路由而不重复细节，参考文档应优化精确查找，操作指南应以安全的顺序组织，说明文档应建立正确的心智模型，决策记录应保留背景、决策、备选方案和后果。
- [ ] 标记无助于目标受众进行决策或采取行动的填充内容、重复摘要、推测性叙述、通用生成文本和形式主义章节。
- [ ] 相比复制实现细节或业务逻辑，优先保留持久的意图、契约、约束和运维信息；仅保留安全行动所需的、经过验证的最少代码或命令示例。
- [ ] 识别无关内容、范围蔓延、未解释的前置条件、隐藏假设，以及不再支持当前任务的章节。
- [ ] 在适用的情况下，检查对外行为、配置、部署、迁移、故障恢复、安全敏感操作和扩展点的覆盖情况。
- [ ] 跨文档追踪需求和架构声明；报告矛盾和归属不明确的问题，而不是默默自行作出选择。
- [ ] 查找过时的将来时计划、已完成的 TODO、已移除的功能、旧版兼容性指南、旧目录布局，以及过时的截图或示例。
- [ ] 检查术语、实体名称、标识符、大小写和生命周期状态是否与代码及其他文档保持一致。
- [ ] 验证警告、前置条件、破坏性操作、回滚步骤和失败结果是否出现在读者需要它们的位置。
- [ ] 在始终加载的代理指令文件中，标记那些更适合通过工具强制执行的确定性格式规则，以及放置在仓库根目录、而不是靠近受影响路径的路径特定规则。

### 4. 验证事实和示例

- [ ] 提取有关路径、文件、符号、版本、数量、命令、标志、环境变量、配置键、端口、端点、架构和默认值的重要声明。
- [ ] 在验证前建立规范化的声明台账，并按主题对重复声明进行分组，以便一次仓库检查即可发现过时副本和跨文档矛盾。
- [ ] 根据当前仓库证据或安全命令验证每条声明；记录检查的确切来源和范围。
- [ ] 在查阅外部文档或声称当前支持情况之前，先从清单文件和锁定文件中确定已安装的版本。
- [ ] 对于外部 API、弃用事项、安全标准、平台限制和兼容性声明，使用官方来源。
- [ ] 仅在安全的本地环境或一次性环境中执行示例；否则检查解析过程、测试和预期输出，并将其标记为静态验证。
- [ ] 检查示例是否缺少导入、是否将占位符呈现为真实值、是否包含无效路径或不安全的密钥、是否使用过时语法，以及输出是否仍与实际行为匹配。
- [ ] 在认定声明为错误之前，先筛除示例、模板、未来计划、有条件的指令和外部系统引用；仅当条件声明的前置条件在本项目中处于激活状态时，才验证该声明。
- [ ] 使用可复现的查询和有文档记录的排除项验证数值数量；避免保留会在没有自动化的情况下逐渐漂移的汇总数量。
- [ ] 在可行的情况下，建议将易变的版本、路径、默认值、清单、生成输出和状态快照移至权威代码、配置或生成源；否则，确定为防止其悄然过时所需的来源、范围以及负责人或生成/更新触发条件。
- [ ] 应用研究到行动的门槛：只有当外部指导能够证明仓库中存在具体缺陷或风险时，才将其转化为发现项。

### 5. 审查注释并生成报告

- [ ] 检查注释和文档字符串中是否包含有用的设计理由、不变量、契约、副作用、失败行为和不明显的约束。
- [ ] 将公共接口或不明显接口的文档字符串与当前签名、参数、返回值、抛出错误、副作用、可空性和生命周期义务进行比对。
- [ ] 标记叙述语法、保留历史、包含死代码、承诺代码并未提供的行为，或重复了更适合通过名称和类型表达的信息的注释。
- [ ] 检查公共接口是否包含语言或生态系统要求的文档，以及示例是否符合实际契约。
- [ ] 在报告之前，筛除有意面向受众进行的简化、框架惯例、生成的文本和已接受的遗留约束。
- [ ] 将每个范围内的文档或注释表面分类为 `KEEP`、`ADD`、`UPDATE`、`DELETE` 或 `MERGE`；仅当规范覆盖能够保留每项所需的受众任务和契约时，才建议删除或合并。
- [ ] 对每个候选项应用重要性和可接受替代方案门槛。要求在仓库已有证据的规模上，证明存在读者错误、任务受阻、不安全操作、矛盾或反复出现的维护成本。拒绝吹毛求疵、文风偏好、理论纯粹性、泛化的最佳实践，以及合理的受众或维护权衡；当有多种结构都可行时，应要求以读者结果为依据，而不是坚持某一种首选格式。
- [ ] 在每个发现项的必需解决方案中放置一个直接相关的 Markdown 实践链接：优先使用当前的官方文档或规范；仅当官方来源无法解决该权衡时，才使用信誉良好的第一方工程材料。打开并验证来源；该来源必须支持所提出的机制，而不仅仅是缺陷类别。拒绝搜索结果链接、泛化的最佳实践文章和装饰性引用。
- [ ] 根据错误操作造成的危害、无法运行、维护漂移或轻微摩擦，将发现项分类为 `P0`-`P3`。
- [ ] 使用文档位置、验证证据、受影响的受众、影响、当前折衷方案为何不可接受，以及最小充分修正或规范所有者来支持每个发现项，同时允许等效解决方案。
- [ ] 当无法在没有可信替代方案的情况下验证安全关键声明、必需的受众操作路径或权威来源时，使用 `BLOCKED`；当证据证明指导不安全、必需的操作路径无法运行，或存在未解决的 `P0/P1` 时，使用 `FAIL`；仅对于重要但不阻塞的问题使用 `CONCERNS`；只有在必需的声明和操作路径均已验证且不存在重要发现项时，才使用 `PASS`。
- [ ] 返回包含已审计范围、已验证和未验证的声明、按优先级排序的发现项、盲点以及剩余信任风险的结论。

## 输出契约

```markdown
# Documentation Audit

**Verdict:** PASS | CONCERNS | FAIL | BLOCKED

## Scope and audiences
- Documents and comment surfaces audited
- Audiences and tasks considered
- Exclusions and generated content

## Trust summary
| Area | Status | Evidence |
|---|---|---|
| Structure | PASS / CONCERNS / FAIL | ... |
| Coverage | PASS / CONCERNS / FAIL | ... |
| Factual accuracy | PASS / CONCERNS / FAIL | ... |
| Durability and SSOT | PASS / CONCERNS / FAIL | ... |
| Comments and examples | PASS / CONCERNS / FAIL | ... |

## Document actions
| Surface | Action | Evidence |
|---|---|---|
| ... | KEEP / ADD / UPDATE / DELETE / MERGE | ... |

## Findings
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete documentation or comment defect | Location, repository, command, or official evidence; affected audience and material impact; why the current tradeoff is not acceptable | Smallest sufficient correction, canonical owner, and a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent structures that preserve the required reader outcome |

Use `None` when no candidate survives the evidence, materiality, audience-need, and acceptable-alternative gates.

## Unverified claims and residual risks
Claims that could not be checked, why, and the evidence still required.
```
