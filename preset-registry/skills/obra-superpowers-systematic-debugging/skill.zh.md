# 系统化调试

## 概述

**核心原则：** 在尝试修复之前务必先找到根因。只修复症状就是失败。

**违反该流程的字面要求就等于违背调试精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你还没有完成第一阶段，就不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境中的漏洞
- 非预期行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下场景使用：**
- 时间紧张（紧急情况下容易诱发猜测）
- “只要一个快速修复”看起来很明显
- 你已经尝试了多个修复
- 之前的修复没有生效
- 你并未完全理解这个问题

**不要跳过：**
- 问题看似简单（简单的问题也有根因）
- 你很着急（匆忙保证会导致返工）
- 经理要求立刻修好（系统化比盲目乱改更快）

## 四个阶段

在进入下一阶段之前你必须完成当前阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 你能稳定触发吗？
   - 具体步骤是什么？
   - 每次都会发生吗？
   - 若无法复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 有什么变更可能导致此问题？
   - Git diff、近期提交
   - 新依赖、配置更改
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing，API → service → database）：**

   **在提出修复建议前，先添加诊断埋点：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：** 哪一层失败（secrets → workflow ✓, workflow → build ✗）

5. **追踪数据流**

   **当错误深埋在调用栈时：**

   See `root-cause-tracing.md` in this directory for the complete backward tracing technique.

   **简化版本：**
   - 坏值从何处产生？
   - 谁用坏值调用了它？
   - 一直向上追踪直到找到来源
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**先找出模式再修复：**

1. **寻找可参考的示例**
   - 在同一代码库中找出类似但正常工作的代码
   - 什么类似的内容是可工作的？

2. **对照参考实现**
   - 如果正在实现该模式，请完整阅读参考实现
   - 不要草草浏览——逐行阅读
   - 在应用前完整理解该模式

3. **识别差异**
   - 正常与故障之间有什么不同？
   - 列出每一处差异，即使很小
   - 不要假设“那不可能有影响”

4. **理解依赖**
   - 这需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 明确表述：“我认为 X 是根因，因为 Y”
   - 把它写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小可能的改动来测试该假设
   - 一次只改一个变量
   - 不要一次修复多个问题

3. **验证后再继续**
   - 有效吗？是 → 进入第四阶段
   - 无效？形成新的假设
   - 不要在其上叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装自己懂
   - 请求帮助
   - 进一步调研

### 阶段 4：实施

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 最简单可复现版本
   - 如果可以，使用自动化测试
   - 没有框架时使用一次性测试脚本
   - 修复前必须先有
   - 使用 `superpowers:test-driven-development` skill 编写合格的失败测试

2. **实施单点修复**
   - 处理已识别出的根因
   - 一次只做一个改动
   - 不做“顺手改点别的”式优化
   - 不捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 是否有其他测试被破坏？
   - 问题是否真正解决？
   - 在宣告成功前使用 `superpowers:verification-before-completion` skill

4. **如果修复不生效**
   - 停止
   - 统计：你已经尝试了多少次修复？
   - 如果 < 3：回到第一阶段，结合新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 不要在没有架构讨论的情况下尝试修复 #4

5. **如果 3 次以上修复失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在不同位置暴露新的共享状态/耦合/问题
   - 修复需要“做大规模重构”才能落地
   - 每次修复都会在其他地方引入新症状

   **停止并质疑基本前提：**
   - 这种模式在本质上合理吗？
   - 我们是否在“因惯性而坚持”？
   - 我们应重构架构还是继续修症状？

   **在尝试更多修复前先与人类搭档讨论**

   这不是假设失败——这是架构错误。

## 红旗信号：停止并遵循流程

如果你发现自己在想：
- “先快速修复，之后再调研”
- “先试着改 X 看看是否有效”
- “加上多个改动，再跑测试”
- “跳过测试，我手工验证”
- “大概是 X，我去修它”
- “我不完全理解，但这个应该行”
- “模式是 X，但我会以不同方式改写”
- “主要问题是：[列出未经过调查的修复]”
- 在追踪数据流前就提出解决方案
- **“再试一次修复”（已尝试 2 次以上）**
- **每次修复都在不同位置暴露新问题**

**以上全部都意味着：停止。回到第一阶段。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 人类搭档发来的信号表明你做错了

**留意这些引导：**
- “那不是发生的吗？” - 你在未经验证就先做了假设
- “它会显示吗...？” - 你本应先收集证据
- “别再猜了” - 你在未理解就提出修复
- “Ultra-think this” - 要质疑基本原理，而不是只看症状
- “我们卡住了吗？”（带怒气）- 你的方法未奏效

**看到这些时：** 停止。回到第一阶段。

## 常见借口

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单问题也有根因。对简单 bug 来说，流程也很快。 |
| “紧急，没有时间走流程” | 系统化调试比反复猜测试错更快。 |
| “先试这个，再调研” | 第一次修复就定下了模式。从一开始就做对。 |
| “我会在确认修复后再写测试” | 未测试的修复不稳定。先测试才能证明它。 |
| “一次做多个修复更省时” | 无法隔离起作用的改动，会引入新 bug。 |
| “参考太长，我改写一下模式” | 部分理解必定出错。必须完整阅读。 |
| “我看到问题了，让我修复” | 看见症状 ≠ 理解根因。 |
| “再试一次修复”（2 次以上失败后） | 3 次以上失败意味着架构问题。先质疑模式，不要再修。 |
