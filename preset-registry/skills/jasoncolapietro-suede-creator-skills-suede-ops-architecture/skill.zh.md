# Suede 运营架构

```text
排序原则：先数据，再工作流，最后智能。
```

读取碎片化数据的代理不会报告自己只掌握了三分之一的信息。它会基于这三分之一的信息，给出流畅、自信的回答。碎片化输入会大规模地产生经过润色的错误，而经过润色的错误能够通过那些明显混乱本无法通过的审查。架构的作用，就是阻止模型被要求回答一个其输入无法回答的问题。

这项技能最终产出的是一份书面架构，而不是一个构建完成的系统。下面的每一步都会在 Output Contract 中生成一行内容，每个关卡都会说明代理在失败时要做什么。

## 开始之前

收集以下信息。基于现有信息开展工作，并在 Output Contract 中说明缺失的内容，而不是因此停滞不前。

1. **实体** — 该运营所围绕的名词（客户、项目、订单、工作、曲目、发行、患者）。
2. **工作单元** — 人们反复执行的事项，每项一行，使用实际执行者所用的措辞。
3. **工具列表** — 所有存放运营数据的系统，包括电子表格、共享驱动器，以及任何被用作数据库的收件箱。
4. **周期长度** — 一个工作单元从开始到完成所需的中位天数。
5. **每个工作单元的影响范围** — 错误输出会造成什么代价，以及是否可以撤销。

在对不熟悉的工作运行第 3 步之前，阅读 `references/triage-examples.md`，了解经过实际演练的分类示例。

## 第 1 步 — 先定义架构，再设计界面

在设计界面、自动化或代理之前，先命名实体、实体字段及其关系。

为每个实体记录：它所携带的字段、它所属的实体，以及它会经历的生命周期状态。

**关卡。** “开始之前”中的每个工作单元都必须读取或写入至少一个已命名的实体。一个工作单元如果不接触任何实体，说明架构定义不完整。

**暂停格式。** 停止。用一行指出未映射的工作单元。提供以下选项：添加缺失的实体、将该工作单元归入现有实体，或以书面形式将其标记为超出范围。等待选择。

## 第 2 步 — 每个实体仅保留一条写入路径

每个实体只能有一个创建记录的位置，以及一条更新记录的路径。其他一切都只能读取。

对于每个实体，列出每一条写入**路径**：所有能够创建或更新该实体的工具、脚本、表单和集成。通过同一个应用程序录入数据的人共享该应用程序的路径，不分别计数；两个应用程序写入同一条记录，就算两条路径。

**关卡。** 每个实体的写入路径数量必须确定为一条。向同一条记录提供两条路径，会在更新的软件上重建该系统原本要消除的信息孤岛。

**暂停格式。** 停止。逐行写出实体名称及其每条竞争性路径。提供以下选项：指定一个规范写入方，让其他方改为读取；将所有写入方置于一个负责写入的服务之后；或拆分为两个具有独立生命周期的实体。等待选择。

## 第 3 步 — 对每个工作单元进行分类

将每个工作单元分配给自动化、代理或人工。依次应用书面规则测试，并在首次匹配时停止。

| 测试 | 判定 | 构建为 |
|---|---|---|
| 完整规则可以被写下来，包含每个分支，不存在“视情况而定”“通常”或“酌情处理”之类的表述——并且输入已经是结构化的 | **自动化** | 确定性代码。不使用模型。 |
| 规则可以被写下来，但输入以散文、音频或图像的形式到达 | **带一个提取步骤的自动化** | 模型将输入解析为该模式；由已写明的规则做出决定。 |
| 规则无法被完整写下来，但在获得相同上下文的情况下，两名胜任的人员会给出相同答案 | **智能体** | 模型基于步骤 1 中的模式进行解读、起草或回答。 |
| 规则无法被完整写下来，并且两名胜任的人员会给出不同答案 | **由人工决定** | 系统汇总完整上下文并呈现出来；由人员做出选择。 |

在确定性工作中加入模型，只会换来不确定性和单次调用成本，却没有任何收益。通过第一项测试的工作应继续使用代码。

不要估算共识程度，而要解决共识问题：把过去三个真实案例交给两名实际负责这项工作的人。答案一致，就将该工作单元归入智能体；答案不一致，就将其归入人工。

**影响范围覆盖规则。** 在使用上表后应用此规则，并且此规则优先于上表结果。任何错误输出会转移资金、触达团队外部的人员、改变访问权限或删除数据的工作单元，无论上方的判定结果如何，都变为**智能体提出建议，人工批准**。判断标准是可逆性，而不是难度。

发送到团队已经拥有的频道中的通知不会触达频道外部，并保留其在表中的判定：向内部频道发帖的路由自动化仍然只是普通自动化。

**暂停格式。** 当一个工作单元无法分类时——其规则从未被写下来，或者解决共识问题所需的两个人无法联系到——停止。用一行写出该工作单元。提供以下选项：立即编写规则并重新分类；与实际负责这项工作的人一起进行三案例比较；在其中一个选项落实前按“由人工决定”交付；或将其标记为不在范围内。等待选择。

## 步骤 4——吸收、保留或淘汰每个工具

列表中的每个工具都必须得到一个判定和一条证明路径。工具出现在配置中并不能证明它正在使用：请引用最近一次写入的时间戳、席位数量、发票中的一行或最近的导出记录。

| 判定 | 标准 | 结果 |
|---|---|---|
| **吸收** | 该工具执行的功能已由新系统的模式负责，并且它不是任何受监管或财务数据的记录系统 | 重建该功能，取消该工具 |
| **保留** | 它是受监管、财务或依法留存数据的记录系统，或者它承载的集成接口如果重建，成本将超过构建预算 | 集成该工具并从中读取数据 |
| **淘汰** | 在完整的使用周期内没有任何写入——持续使用的工具为九十天，处于年度或季节性周期中的工具（例如税务、审计、保险或续期软件）为整整一年——或者其功能已完全由某个保留或吸收的工具覆盖 | 取消该工具，不进行任何重建 |

没有证据路径的工具应归类为未知，而不是直接淘汰。将其报告为未知，并说明哪些证据可以作出最终判断。

## 步骤 5 — 以书面形式选择迁移路径

在架构阶段就作出决定，构建过程中绝不临时 improvisation。按顺序应用，并在首次匹配后停止。

| 条件 | 路径 |
|---|---|
| 在日常工作中每天都会读取历史记录 | **完整迁移** — 清理、映射、回填，运行一个周期的并行系统，确定有日期的切换时间，设置只读窗口，然后退役旧系统 |
| 参考记录的存续时间长于工作周期；已关闭的交易很少重新打开 | **混合迁移** — 迁移客户、联系人、供应商、目录；将交易历史以只读形式保留在原处 |
| 周期较短，已关闭的记录很少重新打开 | **切换日期** — 不进行回填；新工作在新系统中打开，进行中的工作在旧系统中完成，旧系统在一个周期内自行清空 |

单独的保留要求并不会强制进行完整迁移。应阅读该要求的具体措辞：大多数要求只需在规定期限内保留只读存档即可满足，而混合迁移和切换日期路径都能保留这些记录。为日常使用而迁移，为保留要求而存档。

切换日期是成本最低、选择最少的路径。当周期较短时，完整迁移需要付出代价去移动那些会在回填完成前就关闭的记录。

每条路径都适用两条规则。切换日期必须至少提前两周通知整个团队，并在日期到来前完成培训。旧工具必须在计划中按日期列明取消时间，因为持续保留的备用工具会在一个月内变成相互竞争的系统。

## 步骤 6 — 编排为可执行的阶段

安排构建顺序，确保没有任何内容建立在不断变化的基础之上：先是架构，然后是工作流，最后是代理。

每个阶段都必须有一个由命令验证的完成标准。若某个阶段的标准只是判断（“架构看起来稳定”），就不存在真正的关卡——应将其替换为一个命令、一次回读或一次文件检查，并由其输出作出决定。

| 阶段 | 完成情况由以下内容验证 |
|---|---|
| 架构 | 迁移可在空数据库上干净地应用，并且步骤 1 中的每个实体都能完成往返验证 |
| 工作流 | 步骤 3 中每个确定性工作单元都能在真实测试数据上运行，包括失败分支 |
| 代理 | 每个代理工作单元都针对固定评估集进行评分，在运行评估集之前预先写明通过阈值，并且在真实工作依赖它之前完成评分 |
| 迁移 | 所选路径的切换日期已确定、人员已安排并已完成沟通 |

当前阶段的命令通过后，才能进入下一阶段。报告命令及其输出，不要声称阶段已经完成。

**暂停格式。** 当某个阶段的命令失败或尚未运行时，停止。用一行写明阶段名称和失败的命令。提供以下选项：修复该阶段并重新运行命令；缩小阶段范围，使命令能够在更小的范围内通过；或记录一份明确的书面例外，写明由谁接受了该风险。等待选择。

## 输出契约

```text
ENTITIES
- entity / fields / relationships / lifecycle states

WRITE PATHS
- entity / canonical writer / readers / collisions resolved

WORK TRIAGE
- work unit / verdict (automation | extraction | agent | human) / blast-radius override applied

TOOL VERDICTS
- tool / absorb | keep | kill | unknown / proof path

MIGRATION
- path chosen / cycle length / lookup frequency / cutover date / tools cancelled on

PHASE PLAN
- phase / completion command / gate status

OPEN
- unresolved halts, missing inputs, and unclassified tools
```

## 边界

- 负责产出架构；不要构建它、迁移数据或取消正在生效的订阅。
- 除非粘贴能够证明该阶段完成的命令输出，否则不要将阶段标记为完成。
- 不要根据配置条目、记忆或较早的审计结果对工具进行分类。请引用当前的证明路径，或报告为未知。
- 不要让代理负责错误输出会造成不可逆后果的工作；此类工作应由代理提出方案，再由人工批准。
- 不要臆造周期长度、查询频率或成本数字。请询问具体数字，或在输出契约中将其记录为缺失。
- 当实时系统可以读取时，不要把之前的交接记录、蓝图或清单当作当前事实。

## 路由

- 需要先直接收集“开始前”输入，梳理当前操作并核算其摩擦成本，再进行架构设计
  -> 使用 `suede-customer-research` 负责访谈和综合方法，但其对象是外部客户群体，因此借用其技术，不要采用其中的角色画像或工作任务框架。
- 需要在一个受证据门控的计划下跨多个文件构建变更 -> 使用
  `suede-graph-flo-xr`。
- 需要拥有明确文件所有权和回滚机制的并行构建者 -> 使用
  `suede-agent-teams`。
- 需要潜在客户生命周期、评分、阶段和 CRM 路由规则 -> 使用
  `suede-revops`。
- 需要能够证明第 6 步代理层级的评估集 -> 使用 `suede-ai-eval`。
- 需要已交付系统的度量层 -> 使用 `suede-analytics`。
- 需要仅针对已构建差异进行发现性审查 -> 使用 `suede-code-review`。
- 需要围绕构建过程设置 CI、必需检查或合并门禁 -> 使用
  `suede-ci-gate`。
- 来自 `suede-agent-teams`：在各工作通道开放前，将路由架构、写入路径和工作分诊决策路由回此处。
