## 阶段 0：解析参数

提取模式参数（`new`、`update` 或 `status`），并确定审查模式（仅确定一次，存储后供本次运行中的所有关卡生成使用）：
1. 如果传入了 `--review [full|lean|solo]` → 使用该值
2. 否则读取 `production/review-mode.txt` → 使用其中的值
3. 否则 → 默认为 `lean`

完整的检查模式请参阅 `.claude/docs/director-gates.md`。

**审查模式检查**（在关卡运行前）：
- 如果 `production/review-mode.txt` 存在，则读取该文件并使用其中的模式。
- 如果该文件不存在，且这是一个 `new` 冲刺：使用 `AskUserQuestion`：
  - 提示："尚未设置审查模式。你希望本次冲刺采用哪种审查深度？"
  - 选项：
    - `[A] full — 生成所有总监和负责人关卡`
    - `[B] lean — 跳过非阶段关卡的总监审查（推荐用于大多数冲刺）`
    - `[C] solo — 跳过所有关卡生成`
  - 选择后：将所选模式写入 `production/review-mode.txt`。说明："审查模式已设置为 [mode]，并保存至 production/review-mode.txt。"
- 如果该文件不存在，且这不是一个 `new` 冲刺（例如，正在更新现有冲刺）：静默默认为 `lean`。

## 阶段 1：收集上下文

1. 从 `production/milestones/` **读取当前里程碑**。

2. 从 `production/sprints/` **读取上一个冲刺**（如有），以
   了解开发速率和结转工作。

3. **扫描 `design/gdd/` 中的设计文档**，查找标记为已准备好
   实施的功能。

4. **检查 `production/risk-register/` 中的风险登记册**。

## 阶段 2：生成输出

对于 `new`：

**生成冲刺计划**，遵循以下格式并将其呈现给用户。此时不要询问是否写入——必须先运行制作人可行性关卡（阶段 4），该关卡可能会要求在写入文件前进行修订。

```markdown
# Sprint [N] — [Start Date] to [End Date]

## Sprint Goal
[One sentence describing what this sprint achieves toward the milestone]

## Capacity
- Total days: [X]
- Buffer (20%): [Y days reserved for unplanned work]
- Available: [Z days]

## Tasks

### Must Have (Critical Path)
| ID | Task | Agent/Owner | Est. Days | Dependencies | Acceptance Criteria |
|----|------|-------------|-----------|-------------|-------------------|

### Should Have
| ID | Task | Agent/Owner | Est. Days | Dependencies | Acceptance Criteria |
|----|------|-------------|-----------|-------------|-------------------|

### Nice to Have
| ID | Task | Agent/Owner | Est. Days | Dependencies | Acceptance Criteria |
|----|------|-------------|-----------|-------------|-------------------|

## Carryover from Previous Sprint
| Task | Reason | New Estimate |
|------|--------|-------------|

## Risks
| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|

## Dependencies on External Factors
- [List any external dependencies]

## Definition of Done for this Sprint
- [ ] All Must Have tasks completed
- [ ] All tasks pass acceptance criteria
- [ ] QA plan exists (`production/qa/qa-plan-sprint-[N].md`)
- [ ] All Logic/Integration stories have passing unit/integration tests
- [ ] Smoke check passed (`/smoke-check sprint`)
- [ ] QA sign-off report: APPROVED or APPROVED WITH CONDITIONS (`/team-qa sprint`)
- [ ] No S1 or S2 bugs in delivered features
- [ ] Design documents updated for any deviations
- [ ] Code reviewed and merged
```

对于 `update`：

**更新现有的冲刺计划**：

1. 从 `production/sprints/` 读取最新的冲刺计划。
2. 展示当前故事列表及其在 `production/sprint-status.yaml` 中的当前状态。
3. 询问用户要进行哪些更改：添加、移除、调整优先级或重新估算故事。使用 `AskUserQuestion` 收集更改。
4. 应用更改，并重新展示完整的修订后计划以供审查。
5. 对修订后的计划重新运行制作人可行性关卡（阶段 4）。
6. 同时写入更新后的 Markdown 计划和 YAML（采用与 `new` 模式相同的审批方式）。

注意：`update` 模式不会重置故事状态。已标记为 `in-progress` 或 `done` 的故事会保留其状态。只有处于 `backlog` 和 `ready-for-dev` 状态的故事可以自由移除或调整优先级。

对于 `status`：

**生成状态报告**：

```markdown
# Sprint [N] Status -- [Date]

## Progress: [X/Y tasks complete] ([Z%])

### Completed
| Task | Completed By | Notes |
|------|-------------|-------|

### In Progress
| Task | Owner | % Done | Blockers |
|------|-------|--------|----------|

### Not Started
| Task | Owner | At Risk? | Notes |
|------|-------|----------|-------|

### Blocked
| Task | Blocker | Owner of Blocker | ETA |
|------|---------|-----------------|-----|

## Burndown Assessment
[On track / Behind / Ahead]
[If behind: What is being cut or deferred]

## Emerging Risks
- [Any new risks identified this sprint]
```

## 阶段 3：准备冲刺状态文件

生成新的冲刺计划后，还需准备 `production/sprint-status.yaml` 的内容。
这是机器可读的故事状态事实来源——供
`/sprint-status`、`/story-done` 和 `/help` 读取，无需解析 Markdown。

**暂时不要写入 YAML**——将其保留在上下文中。制作人可行性关卡（阶段 4）可能会修改故事列表。阶段 4 完成后，这两个文件将在一次写入审批中一并写入。

格式：

```yaml
# Auto-generated by /sprint-plan. Updated by /story-done and /dev-story.
# DO NOT edit manually — use /story-done to update story status.
#
# Status value mapping (yaml ↔ story file Status field):
#   backlog        ↔  Not Started
#   ready-for-dev  ↔  Ready
#   in-progress    ↔  In Progress
#   review         ↔  In Review
#   done           ↔  Complete
#   blocked        ↔  Blocked

sprint: [N]
goal: "[sprint goal]"
start: "[YYYY-MM-DD]"
end: "[YYYY-MM-DD]"
generated: "[YYYY-MM-DD]"
updated: "[YYYY-MM-DD]"

stories:
  - id: "[epic-story, e.g. 1-1]"
    name: "[story name]"
    file: "[production/stories/path.md]"
    priority: must-have        # must-have | should-have | nice-to-have
    status: ready-for-dev      # backlog | ready-for-dev | in-progress | review | done | blocked
    owner: ""
    estimate_days: 0
    blocker: ""
    completed: ""
```

根据冲刺计划的任务表初始化每个故事：
- 必须完成的任务 → `priority: must-have`、`status: ready-for-dev`
- 应该完成的任务 → `priority: should-have`、`status: backlog`
- 最好完成的任务 → `priority: nice-to-have`、`status: backlog`

对于 `update`：读取现有的 `sprint-status.yaml`，保留未发生变化的故事状态，添加新故事，并移除已取消的故事。

## 阶段 4：制作人可行性关卡

**评审模式检查** — 在生成 PR-SPRINT 之前执行：
- `solo` → 跳过。注明：“PR-SPRINT 已跳过 — 单人模式。”继续进入阶段 5（QA 计划关卡）。
- `lean` → 跳过（不是 PHASE-GATE）。注明：“PR-SPRINT 已跳过 — 精简模式。”继续进入阶段 5（QA 计划关卡）。
- `full` → 正常生成。

在最终确定冲刺计划之前，通过 Task 生成 `producer`，并使用关卡 **PR-SPRINT**（`.claude/docs/director-gates.md`）。

传入：拟议的故事列表（标题、估算、依赖项）、团队总工时/天数容量、上一冲刺遗留的所有内容、里程碑约束和截止日期。

展示制作人的评估结果。

如果为 UNREALISTIC：修改故事选择（将故事推迟至 Should Have 或 Nice to Have），并在请求写入批准之前重新展示更新后的计划。

如果为 CONCERNS，使用 `AskUserQuestion`：
- 提示：“制作人指出了此冲刺计划存在的问题。你希望如何继续？”
- 选项：
  - `[A] 按计划继续 — 我接受风险`
  - `[B] 调整范围 — 推迟部分 Should Have 故事`
  - `[C] 延长冲刺时间线`

如果选择 [A]：继续请求写入批准。
如果选择 [B]：修改故事列表，重新展示更新后的计划，然后继续请求写入批准。
如果选择 [C]：调整冲刺日期和容量，重新展示更新后的计划，然后继续请求写入批准。

处理完制作人的裁定后，询问：“我可以将冲刺计划写入 `production/sprints/sprint-[N].md`，并将状态写入 `production/sprint-status.yaml` 吗？”如果同意，则写入这两个文件（根据需要创建目录）。裁定：**COMPLETE** — 冲刺计划和状态文件已创建。如果不同意：裁定：**BLOCKED** — 用户拒绝写入。

写入后，添加：

> **范围检查：** 如果此冲刺包含超出原始史诗范围而新增的故事，请在实施开始前运行 `/scope-check [epic]` 以检测范围蔓延。

## 阶段 5：QA 计划关卡

在结束冲刺计划之前，检查此冲刺是否存在 QA 计划。

使用 `Glob` 查找 `production/qa/qa-plan-sprint-[N].md`，或查找 `production/qa/` 中引用此冲刺编号的任何文件。

**如果找到 QA 计划**：在冲刺计划输出中注明 — “QA 计划：`[path]`” — 然后继续。

**如果不存在 QA 计划**：不要在不作说明的情况下继续。明确指出这一点：

> “此冲刺没有 QA 计划。没有 QA 计划的冲刺计划意味着测试要求尚未定义 — 开发人员将无法从 QA 角度了解怎样才算‘完成’，并且没有 QA 计划，此冲刺就无法通过 Production → Polish 关卡。
>
> 在开始任何实施工作之前，立即运行 `/qa-plan sprint`。它只需要一个会话，并会生成每个故事所需的测试用例要求。”

使用 `AskUserQuestion`：
- 提示：“未找到此冲刺的 QA 计划。你希望如何继续？”
- 选项：
  - `[A] 立即运行 /qa-plan sprint — 我会在开始实施之前完成此操作（推荐）`
  - `[B] 暂时跳过 — 我明白在 Production → Polish 关卡，QA 签核将被阻止`

如果是 [A]：以“冲刺计划已编写完成。接下来运行 `/qa-plan sprint`，然后开始实施。”结尾。
如果是 [B]：在冲刺计划文档中添加以下警告块：

```markdown
> ⚠️ **No QA Plan**: This sprint was started without a QA plan. Run `/qa-plan sprint`
> before the last story is implemented. The Production → Polish gate requires a QA
> sign-off report, which requires a QA plan.
```

## 阶段 6：后续步骤

冲刺计划编写完成且 QA 计划状态得到解决后：

- `/qa-plan sprint` — **必须在开始实施之前运行** — 为每个故事定义测试用例，使开发人员依据 QA 规范进行实施，而不是从零开始
- `/story-readiness [story-file]` — 在开始故事之前，验证其是否已准备就绪
- `/dev-story [story-file]` — 开始实施第一个故事
- `/sprint-status` — 在冲刺进行期间检查进度
- `/scope-check [epic]` — 在开始实施之前确认没有范围蔓延

**审查模式配置：**所有总监关卡（制作人可行性评估、QA 审查、代码审查）均遵循项目审查模式。对于 `new` 冲刺，如果文件不存在，则在阶段 0 中设置审查模式；也可以在每次运行时通过参数 `--review full|lean|solo` 覆盖该模式。文件 `production/review-mode.txt` 包含以下值之一：
- `lean` — 跳过自动化总监关卡（文件不存在时的默认值——对独立开发者而言速度最快）
- `full` — 将所有总监关卡作为生成的子代理运行
- `solo` — 无条件跳过所有关卡（单人开发，无审查）

`/sprint-plan`、`/story-readiness`、`/story-done` 及其他技能会在启动时读取此文件。
