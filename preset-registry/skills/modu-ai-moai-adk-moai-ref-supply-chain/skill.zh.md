# 软件供应链防御性安全参考

用于加固软件供应链的防御性实践参考——该供应链涵盖从源代码、构建过程到消费者安装的制品。每一节均从防御、加固、检测或验证的角度展开：描述弱点、如何检测以及如何预防，而绝不说明如何利用弱点。AI/LLM 特有的供应链问题（模型和训练数据来源）位于
`moai-ref-llm-security`；Web 应用程序漏洞位于
`moai-ref-owasp-checklist`。

## 适用场景

在构建、发布或使用软件组件时应用本参考。其威胁模型假定供应链不可信：你拉取的任何依赖项、运行的任何构建步骤，以及交付的任何制品，都可能已被替换、篡改或冒充。以下防御措施旨在确立来源（它来自哪里？）、完整性（它是否已被更改？）和规范性（这是我原本打算使用的组件吗？）。

## 供应链信任边界

防御的核心洞见是：供应链中的每一次交接都是一个边界，组件可能在此处被替换或篡改。应在每一次交接时确立来源并验证完整性。

| 边界 | 替换/篡改风险 | 主要防御措施 |
|----------|----------------------------|-----------------|
| 源解析（名称 → 软件包） | 依赖混淆、仿冒拼写 | 命名空间限定、安装时验证、名称允许列表 |
| 依赖项下载 | 软件包注册表遭入侵、中间人攻击 | 通过哈希锁定锁文件、签名验证 |
| 传递闭包 | 存在漏洞或恶意的深层依赖项 | 传递依赖审计、深度限制、SBOM 差异比较 |
| 构建 | 构建遭篡改、步骤被注入 | SLSA 来源证明、隔离式/临时构建器 |
| 制品发布 | 制品被替换 | Sigstore 签名、来源证明声明 |
| 消费者安装 | 接受未经验证的制品 | 在安装/准入时验证签名和来源证明 |

## SBOM——生成与验证

软件物料清单（SBOM）是制品中所含组件的清单。它是所有下游防御措施的基础：对于尚未列入清单的内容，你无法进行审计、扫描或验证。

### 格式选择

这两种开放 SBOM 格式可互操作；应根据生态系统适配程度和消费者需求进行选择。

| 格式 | 管理机构 | 优势 |
|--------|---------|----------|
| SPDX | Linux Foundation（ISO/IEC 5962 标准） | 以许可证为中心；受到监管和法律领域的广泛认可 |
| CycloneDX | OWASP | 以安全为中心；原生支持漏洞和依赖关系建模 |

### 最低元素基线

一份实用的 SBOM 至少应包含 NTIA 规定的最低元素：供应商、组件名称、版本、唯一标识符、依赖关系、SBOM 数据的作者以及时间戳。缺少依赖关系的 SBOM 只是清单，而不是图——它无法回答“是什么引入了这个存在漏洞的组件？”。

### 生成与验证实践

标准的 SBOM 生成工具（syft 是事实上的跨生态系统标准，可输出 SPDX 和 CycloneDX）会检查制品或源代码树，并生成组件清单。应将 SBOM 的生成作为构建过程的**一部分**，而不是在构建后进行——之后生成的 SBOM 无法发现仅在构建时使用的依赖项。验证 SBOM 时，应从制品中重新生成 SBOM 并进行差异比较：已交付 SBOM 与重新生成的 SBOM 之间存在偏差，表明制品遭到篡改或原始 SBOM 不完整。

- **在构建时生成**，以确保 SBOM 准确反映最终解析得到的完整依赖闭包。
- **将 SBOM 作为已签名的证明附加**（参见下文的 Sigstore），使使用者不仅能读取清单，还能信任其内容。
- **比较不同版本之间的 SBOM 差异**，以便在新引入的依赖项或版本升级的依赖项发布之前将其识别出来。

## 依赖混淆防御

依赖混淆（于 2021 年公开披露）是指解析器拉取了一个公共包，该包与预期的私有/内部包同名并将其遮蔽，原因是解析器优先选择了公共注册表。防御方法是让解析器针对内部名称优先使用可信来源，或仅使用可信来源。本节完全着眼于防御：介绍如何防止这种替换，而非如何实施替换。

| 控制措施 | 防御原理 |
|---------|---------------------|
| 命名空间/作用域预留 | 在公共注册表中预留组织的包命名空间，使内部名称无法被外部主体占用 |
| 按名称固定来源 | 将解析器配置为仅从内部注册表获取内部名称；绝不允许内部名称在内部注册表中未找到时转而使用公共注册表 |
| 安装时哈希验证 | 在锁定文件中将每个依赖项固定到内容哈希，从而拒绝内容不同的同名替换包 |
| 注册表路由控制 | 使用注册表代理，将内部命名空间的请求路由到内部来源，并拒绝这些名称回退到公共注册表 |

锁定文件哈希固定是这里的跨领域控制措施：不同生态系统中的包管理器都会为每个已解析的依赖项记录内容哈希——`pip` 将哈希写入 requirements 锁定文件，`npm` 在其锁定文件中记录完整性哈希，`cargo` 在其锁定文件中记录校验和——并在安装时验证该哈希。因此，无论包由哪个注册表提供，字节内容不同的同名替换包都无法通过检查。

## 恶意包分诊手册

当某个依赖项存在可疑情况——被信息源、安全公告或审查人员标记——应在其进入系统之前进行分诊（或者通过分诊决定是否将其移除）。本手册仅涉及检测和响应，绝不分析如何制作恶意包。

### 分诊信号（检测）

| 信号 | 表明的情况 |
|--------|-------------------|
| 名称与热门包高度相似 | 可能存在拼写抢注（参见“拼写抢注防御”） |
| 最近发生维护者变更或出现新发布者 | 账户可能已被接管，或已移交给恶意行为者 |
| 存在安装/安装后脚本 | 代码会在安装时运行——这是一种常见的滥用手段；应检查其具体行为 |
| 脚本中存在非预期的网络或文件系统访问 | 数据外泄或持久化行为 |
| 版本发布节奏异常/主版本号突然大幅跃升 | 废弃包可能已被劫持 |
| 代码仓库与已发布制品不匹配 | 已发布制品并非由其声称的源代码构建而成 |

### 响应流程

1. **隔离**：固定到最后一个已知安全版本，并在解析器/代理中阻止可疑版本，确保任何构建都不会拉取该版本。
2. **验证来源**：检查制品是否具有签名和来源证明（参见下文的 Sigstore / SLSA）；无法验证的制品应继续隔离。
3. **盘点影响范围**：使用 SBOM 查找已经拉取可疑版本的所有构建（这正是 SBOM 依赖关系图的用途）。
4. **向上游报告**：通知包注册表的安全/公告渠道；如果是内部包，则通知内部安全负责人。大多数注册表都提供恶意软件/滥用行为报告渠道。
5. **记录**：记录分诊结论及相关证据，以便未来再次发生时能够更快地作出判定。

## SLSA 来源级别

SLSA（软件制品供应链级别，Supply-chain Levels for Software Artifacts）定义了构建完整性级别。
来源是描述制品如何构建的签名元数据；级别表示该来源的可信程度。
当前的 Build 轨道定义了四个级别
（L0–L3）；构建越难被篡改，级别就越高。（较早的 SLSA
版本将这些级别编号为 L1–L4——理念相同，都是四个递进级别。）

| 级别 | 提供的保证 | 如何验证 |
|-------|--------------------|---------------|
| Build L0 | 无任何保证 | 不适用——视为未经验证 |
| Build L1 | 存在来源：构建过程有文档记录，并会生成来源 | 检查制品是否附带来源，以及来源是否描述了构建过程 |
| Build L2 | 由托管构建平台提供的签名来源——可通过签名发现篡改 | 验证来源签名的信任链是否指向预期的构建平台身份 |
| Build L3 | 加固构建：来源不可伪造，构建在隔离的临时环境中运行，机密材料与构建过程相隔离 | 验证签名，并确认构建器身份属于经过加固的隔离平台 |

防御性实践：**为你使用的内容设定最低级别要求。** 如果制品的来源低于
环境要求的级别，发布流水线应拒绝部署该制品——生产环境通常至少要求
签名来源（L2+），而高保障环境则要求使用加固构建器（L3）。

## Sigstore / cosign 签名与验证

Sigstore 是跨生态系统签名和验证软件制品的事实标准。
标准的 Sigstore 签名工具 cosign 可对制品进行签名并
验证签名；它与一个签发短期身份绑定证书的证书颁发机构以及一个记录每个签名的透明度日志配合使用。本
节将 Sigstore 定位为使用者采用的验证机制，绝不能将其作为
伪造签名的方式。

### 无密钥签名模型

无密钥签名消除了长期私钥——签名流水线中最常被窃取的机密。
取而代之的是：

1. 签名者通过身份提供商（OIDC）进行身份验证。
2. CA 签发一个与该身份绑定的**短期证书**。
3. 使用临时密钥对制品进行签名。
4. 签名和证书会记录在**公共透明度日志**中。

结果是：验证者可以确认*哪个身份签署了此制品*，而无需任何
一方持有可能被窃取的长期密钥。

### 在使用者边界进行验证

其防御价值体现在**验证**端。使用者（或准入关卡）
会验证制品的签名，并在接受该制品之前，根据预期的
身份策略检查签名者身份。标准验证调用
形式为 `cosign verify --certificate-identity <expected> --certificate-oidc-issuer
<expected> <artifact-ref>`。验证采用失败关闭原则：未签名或签名身份错误的
制品将被拒绝。

- **在安装/准入时进行验证**，而不只是在发布时——真正重要的边界
  是制品被接受的位置。
- **固定预期的签名者身份**，以便拒绝签名有效但身份错误的
  制品。
- **以相同方式验证 SBOM 和来源证明**——它们也是经过签名的
  制品。

## 包注册表加固

注册表是一个高价值目标：一旦攻陷注册表，攻击者就能从源头替换制品。应同时加固用于发布的注册表以及所运营的任何内部镜像。

| 控制措施 | 防御原理 |
|---------|---------------------|
| 为所有发布/管理员账户启用双因素认证 | 账户接管是注册表遭入侵最常见的途径；双因素认证可阻止凭据填充攻击 |
| 注册表端签名/强制证明 | 要求制品携带可验证的签名和来源信息，才能发布或使用 |
| 镜像/代理固定 | 通过哈希将内部镜像固定到特定的上游版本，避免上游变更在无提示的情况下传递进来 |
| 限定范围的发布令牌 | 为每个软件包签发遵循最小权限原则的发布令牌；切勿使用可发布任意软件包的宽泛权限令牌 |
| 已发布版本不可变 | 禁止覆盖并重新发布现有版本，防止已发布的制品事后被替换 |
| 发布审计日志 | 记录每次发布的身份信息和制品哈希，以便检测篡改和响应事件 |

## 拼写仿冒防御

拼写仿冒会注册一个名称与热门软件包极为相似的软件包（例如字母顺序颠倒、增删字符或使用形似拼写），期待开发者输错名称。其防御手段是名称验证和允许列表；本节不会说明如何注册仿冒软件包。

| 控制措施 | 防御原理 |
|---------|---------------------|
| 依赖项名称允许列表 | 仅解析经过审核的允许列表中的确切软件包名称；近似名称不会出现在列表中 |
| 自动拼写错误/相似度检测 | 在 CI 中运行名称相似度检查，标记名称与热门软件包仅相差一次编辑操作的新依赖项 |
| 命名空间注册 | 以防御为目的，注册组织自身名称中容易被误拼的变体，使其无法被他人抢注仿冒 |
| 固定确切名称和哈希 | 将确切名称固定与哈希固定结合使用，这样即使发生名称冲突，错误字节也无法通过哈希检查 |

名称允许列表与哈希固定是最强的组合：允许列表拒绝非预期的*名称*，而哈希检查拒绝预期名称下非预期的*字节*。

## 传递依赖项审计

项目的大部分依赖面都由传递依赖项构成——即由直接依赖项引入的依赖项。即使漏洞或恶意软件包位于三层依赖之外，它仍然存在于你的制品中。应审计完整的依赖闭包，而不仅仅是直接依赖项。

### 审计维度

| 维度 | 防御控制措施 |
|-----------|-------------------|
| 漏洞 | 根据漏洞公告扫描完整的传递依赖闭包；达到严重性阈值时使构建失败 |
| 许可证 | 根据允许的许可证策略扫描传递依赖项的许可证；标记深层依赖项中不合规的许可证 |
| 深度/数量 | 限制依赖项深度和总数；异常深或异常宽的依赖闭包是需要审查的信号 |
| 锁文件完整性 | 在锁文件中通过哈希固定整个依赖闭包，确保经过审计的依赖闭包就是实际安装的依赖闭包 |

### 生态系统中立的审计

每种语言生态系统都提供了一个基于漏洞公告数据库的审计工具，用于遍历传递依赖闭包并报告已知存在漏洞的依赖项——例如，`pip-audit`（Python）、`npm audit`（Node.js）、`cargo audit`（Rust）、`govulncheck`（Go）和 `bundler-audit`（Ruby）都会查询各自生态系统的漏洞公告数据库。在 CI 中运行对应生态系统的审计工具，当发现的问题超过选定的严重级别时使构建失败，并在每次锁文件发生变更时重新运行，以便在合并前发现新引入的传递依赖漏洞。对于跨生态系统项目，可以使用读取 SBOM 的软件成分分析（SCA）工具，一次性对所有生态系统执行统一审计。

## 防御性严重级别

| 级别 | 标签 | 措施 | 示例 |
|-------|-------|--------|---------|
| P0 | 严重 | 阻止发布 | 在生产部署时接受未签名的制品；未对内部命名空间包使用锁文件哈希固定 |
| P1 | 高 | 合并前修复 | CI 中未执行传递依赖漏洞审计；构建时未生成 SBOM |
| P2 | 中 | 在当前迭代内修复 | 未对新增依赖项执行自动化仿冒包检测；发布到注册表时未启用 2FA |
| P3 | 低 | 在待办事项中跟踪 | 已有 SBOM，但未将其作为签名证明附加；尚未强制执行许可证审计 |

## 常见的自我辩解

| 自我辩解 | 事实 |
|---|---|
| “我们只使用知名软件包，因此不需要 SBOM” | 如果没有清单，就无法对新披露的漏洞进行分类处置。SBOM 能告诉你有问题的组件是否存在于你的制品中。 |
| “通过版本固定锁文件就足够了” | 只固定版本而不固定哈希，仍会接受版本字符串相同但内容被替换的文件。按内容哈希固定，这样相同版本的内容替换就会失败。 |
| “依赖混淆只会影响使用私有包的公司” | 任何项目，只要其解析器在解析内部名称时可能回退到公共注册表，就会面临风险。应将内部名称限定到可信来源。 |
| “签名验证会拖慢我们的流水线” | 验证是接受被篡改制品与拒绝它之间的边界。代价高昂的是让未经验证的制品进入生产环境，而不是执行验证步骤。 |
| “传递依赖是上游维护者的问题” | 存在漏洞的传递依赖会以你的名义包含在你的制品中交付。应审计完整的依赖闭包；问题所在的依赖层级深度并不会改变它存在于谁的制品中。 |
| “对于内部构建来说，SLSA 有些小题大做” | 你要求的 SLSA 级别，就是你针对构建篡改所获得的保障级别。内部构建同样可能遭到篡改；对于任何要部署的内容，至少应要求提供签名的来源证明。 |

**默认验证来源**：你使用的每个制品在其签名和来源经过检查之前都是未经验证的，你解析的每个名称在与预期名称和哈希匹配之前也是未经验证的。信任通过验证建立，而非源于熟悉程度。

<!-- moai:evolvable-start id="red-flags" -->
## 危险信号

- 制品未经签名和来源验证便部署到生产环境
- 当内部源中不存在相应包时，内部命名空间的包名可能会回退到公共注册表
- 锁文件仅固定版本而未固定内容哈希，因此替换为相同版本的内容也能通过验证
- 构建时未生成 SBOM，因此无法得知已部署制品的组件清单
- 从未根据漏洞或许可证公告审计传递依赖闭包
- 添加新依赖时，未检查其名称与热门包名的相似性
- 注册表发布/管理员账户未启用双因素身份验证
- 已发布的制品版本事后仍可重新发布（覆盖）

<!-- moai:evolvable-start id="verification" -->
## 验证

- [ ] 构建时生成 SBOM（SPDX 或 CycloneDX），且其中包含依赖关系等最低必要元素
- [ ] 内部命名空间的包名只能从受信任的内部源解析；已禁用这些名称向公共源的回退
- [ ] 锁文件通过内容哈希固定每个依赖，并在安装时验证该哈希
- [ ] 在 CI 中审计传递依赖闭包的漏洞和许可证合规性，超过选定的严重性等级时构建失败
- [ ] 新依赖在采用前通过名称相似性 / 拼写抢注检查
- [ ] 在安装或准入时，根据签名和预期的签名者身份（Sigstore）验证所使用的制品
- [ ] 要求已部署制品达到最低 SLSA 来源等级，流水线拒绝低于该等级的制品
- [ ] 注册表发布/管理员账户使用双因素身份验证以及具有作用域限制、遵循最小权限原则的发布令牌
