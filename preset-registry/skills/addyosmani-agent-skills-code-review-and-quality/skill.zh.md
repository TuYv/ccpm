# 代码审查与质量

## 概述

通过质量门禁开展多维度代码审查。每项变更在合并前都必须经过审查——无一例外。审查涵盖五个维度：正确性、可读性、架构、安全性和性能。

**批准标准：**如果一项变更明确改善了代码的整体健康度，即使它并不完美，也应予以批准。完美的代码并不存在——目标是持续改进。不要因为一项变更与你自己的写法不完全一致就阻止它。如果它改善了代码库并遵循项目约定，就应批准。

## 何时使用

- 合并任何 PR 或变更之前
- 完成功能实现之后
- 当其他代理或模型生成了需要你评估的代码时
- 重构现有代码时
- 修复任何缺陷之后（同时审查修复代码和回归测试）

## 五维审查

每次审查都要从以下维度评估代码：

### 1. 正确性

代码是否实现了它所声称的功能？

- 是否符合规范或任务要求？
- 是否处理了边界情况（null、空值、边界值）？
- 是否处理了错误路径（而不只是正常路径）？
- 是否通过了所有测试？这些测试是否确实验证了正确的内容？
- 是否存在差一错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

其他工程师（或代理）能否在无需作者解释的情况下理解这段代码？

- 命名是否具有描述性并符合项目约定？（不要使用缺乏上下文的 `temp`、`data`、`result`）
- 控制流是否直观（避免嵌套三元表达式和深层回调）？
- 代码组织是否合乎逻辑（相关代码集中放置，模块边界清晰）？
- 是否存在应当简化的“炫技式”技巧？
- **能否用更少的代码行实现？**（可以用 100 行完成却写了 1000 行，就是失败）
- **抽象带来的价值是否足以抵偿其复杂性？**（在出现第三个用例之前不要进行泛化）
- 注释是否有助于澄清不明显的意图？（但不要为显而易见的代码添加注释。）
- 是否存在死代码残留：无操作变量（`_unused`）、向后兼容垫片或 `// removed` 注释？
- **是否把新的条件分支生硬地塞进了不相关的流程？**这是设计异味，而不是小问题——应将逻辑放入独立的辅助函数、状态或策略中，而不是让现有路径纠缠不清。
- **是否反复出现针对同一种结构的条件判断？**这表明缺少相应的模型或分派器。一个“临时”分支通常会成为永久的技术债。

### 3. 架构

这项变更是否符合系统的设计？

- 它是遵循现有模式，还是引入了新模式？如果是新模式，是否有充分理由？
- 是否保持了清晰的模块边界？
- 是否存在应该共享的重复代码？
- 依赖关系的流向是否正确（不存在循环依赖）？
- 抽象层级是否恰当（既不过度设计，也不过度耦合）？
- **这次重构是降低了复杂性，还是仅仅转移了复杂性？**统计读者理解这项变更时必须掌握的概念数量。如果一个“更整洁”的版本并未减少这个数量，那它就没有变得更整洁——相比将相同的逻辑重新集中起来，应优先选择能让整个分支、模式或层级消失的重构方式。与其打磨一个抽象，不如删除它。
- **特定功能的逻辑是否泄漏到了共享模块或通用模块中？**将逻辑保留在其所属层中，复用现有的规范辅助函数，而不是创建近似重复的实现，并且不要将架构偏移合理化。
- **类型边界是否明确？**应质疑无必要的 `any`/`unknown`/可选类型/类型转换，以及用来掩盖不明确不变量的静默回退——明确边界通常也能简化周围的控制流。

### 4. 安全性

有关详细的安全指导，请参阅 `security-and-hardening`。此变更是否引入了漏洞？

- 是否对用户输入进行了验证和清理？
- 是否确保密钥不会出现在代码、日志和版本控制中？
- 是否在需要的地方检查了身份认证和授权？
- SQL 查询是否参数化（没有使用字符串拼接）？
- 输出是否经过编码以防止 XSS？
- 依赖项是否来自可信来源且不存在已知漏洞？
- 是否将来自外部来源（API、日志、用户内容、配置文件）的数据视为不可信数据？
- 外部数据流在用于逻辑处理或渲染之前，是否已在系统边界处经过验证？

### 5. 性能

有关详细的性能分析和优化指导，请参阅 `performance-optimization`。此变更是否引入了性能问题？

- 是否存在 N+1 查询模式？
- 是否存在无界循环或不受约束的数据获取？
- 是否存在本应异步执行的同步操作？
- UI 组件中是否存在不必要的重新渲染？
- 列表端点是否缺少分页？
- 是否在热点路径中创建了大型对象？

## 结构性改进措施

当你指出结构性问题时，应提出具体的改动方案，而不只是指出问题。仅仅说“这里很复杂”的审查意见会让作者无所适从。应优先采用有明确名称的重构方式：

- **将一连串条件判断替换为**类型化模型或显式分发器。
- **合并重复分支**，形成一条更清晰的流程。
- **将编排逻辑与业务逻辑分离**，使两者都能独立阅读。
- **将特定于功能的逻辑移出共享模块**，放入拥有该概念的包中。
- **复用规范的辅助函数**，而不是使用自定义的近似重复实现。
- **明确类型边界**，从而消除下游的分支判断。
- **删除透传包装器**，因为它只增加了间接层级，却没有让 API 更清晰。
- **提取辅助函数，或拆分大型文件**，形成职责明确的模块。

与其选择把相同复杂性分散到各处的方案，不如优先选择能够减少活动部件的改进措施。

## 变更规模

小而聚焦的变更更容易审查、合并速度更快，也更适合安全部署。建议将变更控制在以下规模：

```
~100 lines changed   → 良好。可以一次审查完成。
~300 lines changed   → 如果是单个逻辑变更，则可以接受。
~1000 lines changed  → 规模过大。应当拆分。
```

**不仅要关注差异大小，还要关注文件大小。** 即使差异很小，也仍可能使文件超出合理规模——单个文件达到约 1000 行*总行数*（不同于上文约 1000 行*变更行数*的阈值）通常是一个需要检查的信号，而不是硬性上限。当一项变更使一个已经很大的文件明显增大时，应先考虑是否需要提取辅助函数、子组件或模块，而不是继续堆叠内容。先拆分，再添加。

**“一项变更”的定义：** 一个独立且完整的修改，只处理一件事情，包含相关测试，并保证系统在提交后仍可正常运行。它是某项功能的一部分，而不是整项功能。

**变更过大时的拆分策略：**

| 策略 | 方法 | 适用场景 |
|----------|-----|------|
| **堆叠** | 先提交一个小变更，再基于它开始下一个变更 | 存在顺序依赖 |
| **按文件组** | 将需要不同审查者的文件组拆分为不同变更 | 横跨多个关注点 |
| **水平拆分** | 先创建共享代码或存根，再添加使用方 | 分层架构 |
| **垂直拆分** | 将功能拆分为更小的全栈切片 | 功能开发 |

**适合进行大规模变更的情况：** 完整删除文件，以及自动化重构——在这类变更中，评审者只需验证变更意图，而不必逐行检查。

**将重构与功能开发分开。** 同时重构现有代码并添加新行为的变更实际上是两个变更——请分别提交。小规模清理（如变量重命名）可由评审者酌情决定是否包含在内。

## 变更说明

每个变更都需要一份能够在版本控制历史中独立存在的说明。

**第一行：** 简短、使用祈使语气且能够独立表意。使用“删除 FizzBuzz RPC”，而不是“正在删除 FizzBuzz RPC”。其信息必须足够充分，让搜索历史记录的人无需阅读差异内容即可理解该变更。

**正文：** 说明正在变更什么以及为什么变更。包含代码本身无法体现的背景、决策和推理。在相关情况下，链接到缺陷编号、基准测试结果或设计文档。如果所采用的方法存在不足，应明确说明。

**反模式：** “修复缺陷”“修复构建”“添加补丁”“将代码从 A 移动到 B”“第一阶段”“添加便利函数”。

## 评审流程

### 第 1 步：了解背景

查看代码之前，先了解变更意图：

```
- What is this change trying to accomplish?
- What spec or task does it implement?
- What is the expected behavior change?
```

### 第 2 步：先评审测试

测试能够揭示变更意图和覆盖范围：

```
- Do tests exist for the change?
- Do they test behavior (not implementation details)?
- Are edge cases covered?
- Do tests have descriptive names?
- Would the tests catch a regression if the code changed?
```

### 第 3 步：评审实现

从以下五个维度逐步检查代码：

```
For each file changed:
1. Correctness: Does this code do what the test says it should?
2. Readability: Can I understand this without help?
3. Architecture: Does this fit the system?
4. Security: Any vulnerabilities?
5. Performance: Any bottlenecks?
```

### 第 4 步：对发现的问题进行分类

为每条评论标注严重程度，以便作者了解哪些是必须修改的，哪些是可选的：

| 前缀 | 含义 | 作者应采取的行动 |
|--------|---------|---------------|
| *（无前缀）* | 必须修改 | 合并前必须处理 |
| **严重：** | 阻止合并 | 安全漏洞、数据丢失、功能损坏 |
| **细节：** | 次要、可选 | 作者可以忽略——格式、风格偏好 |
| **可选：** / **请考虑：** | 建议 | 值得考虑，但并非必须 |
| **供参考** | 仅供参考 | 无需采取行动——为将来提供背景信息 |

这样可以防止作者将所有反馈都视为强制要求，并在可选建议上浪费时间。

**优先指出重要问题。** 按影响力排列发现的问题：首先是正确性和安全性，其次是结构性退化和遗漏的简化机会，然后才是其他问题。不要让真正的问题淹没在无关紧要的细节中——少量有充分把握的评论胜过一长串意见。如果你发现了一个结构性问题和十个细节问题，那么这个结构性问题*就是*此次评审的核心。

### 第 5 步：验证验证过程

检查作者的验证说明：

```
- What tests were run?
- Did the build pass?
- Was the change tested manually?
- Are there screenshots for UI changes?
- Is there a before/after comparison?
```

## 多模型审查模式

使用不同的模型，从不同视角进行审查：

```
Model A writes the code
    │
    ▼
Model B reviews for correctness and architecture
    │
    ▼
Model A addresses the feedback
    │
    ▼
Human makes the final call
```

这种方式可以发现单个模型可能遗漏的问题——不同模型有不同的盲点。

**审查代理的示例提示词：**
```
Review this code change for correctness, security, and adherence to
our project conventions. The spec says [X]. The change should [Y].
Flag any issues as Critical, Required, Optional, or Nit.
```

## 无用代码清理

在完成任何重构或实现变更后，检查是否存在孤立代码：

1. 找出目前已不可达或未使用的代码
2. 明确列出这些代码
3. **删除前先询问：**“我是否应该移除这些目前已不再使用的元素：[列表]？”

不要任由无用代码留在代码库中——这会让未来的读者和代理感到困惑。但也不要在不确定时擅自删除。如有疑问，先询问。

```
DEAD CODE IDENTIFIED:
- formatLegacyDate() in src/utils/date.ts — replaced by formatDate()
- OldTaskCard component in src/components/ — replaced by TaskCard
- LEGACY_API_URL constant in src/config.ts — no remaining references
→ Safe to remove these?
```

## 审查速度

缓慢的审查会阻塞整个团队。因审查而切换上下文的成本，低于让他人等待所带来的成本。

- **在一个工作日内响应**——这是最长时限，而不是目标
- **理想节奏：**审查请求到达后尽快响应，除非正处于高度专注的编码状态。一个常规变更应该能够在一天内完成多轮审查
- **优先保证每次响应迅速**，而不是追求快速给出最终批准。即使需要多轮审查，快速反馈也能减少挫败感
- **大型变更：**要求作者将其拆分，而不是审查一个庞大的变更集

## 处理分歧

解决审查争议时，请遵循以下优先级：

1. **技术事实和数据**优先于观点和偏好
2. **风格指南**是风格问题上的绝对权威
3. **软件设计**必须依据工程原则进行评估，而不是个人偏好
4. 如果不会损害代码库的整体健康，保持**代码库一致性**是可以接受的

**不要接受“我之后会清理”。** 经验表明，推迟的清理工作很少会真正完成。除非确实发生紧急情况，否则应要求在提交前完成清理。如果无法在本次变更中处理周边问题，则要求提交一个缺陷，并将其指派给作者本人。

## 审查中的诚实原则

审查代码时——无论代码是由你、其他代理还是人类编写的：

- **不要敷衍批准。** 没有审查依据的“LGTM”对任何人都没有帮助。
- **不要淡化实际问题。** 如果某个缺陷会影响生产环境，却说“这可能只是一个小问题”，就是不诚实。
- **尽可能量化问题。** “这个 N+1 查询会让列表中的每个项目增加约 50ms 的耗时”优于“这可能会很慢”。
- **明确反对存在明显问题的方案。** 盲目迎合是审查中的一种失败模式。如果实现存在问题，应直接指出并提出替代方案。
- **坦然接受推翻意见。** 如果作者掌握完整上下文并持有不同意见，应尊重其判断。评论代码，而不是评论人——将针对个人的批评改为聚焦代码本身。

## 依赖纪律

代码审查的一部分是依赖审查：

**添加任何依赖之前：**
1. 现有技术栈能解决这个问题吗？（通常可以。）
2. 依赖有多大？（检查对包体积的影响。）
3. 是否仍在积极维护？（检查最近一次提交和未解决的问题。）
4. 是否存在已知漏洞？（`npm audit`）
5. 使用什么许可证？（必须与项目兼容。）

**规则：** 优先使用标准库和现有工具，而不是引入新依赖。每个依赖都是一项负担。

**升级现有依赖**与其他任何代码变更一样，而风险最高的是那些以“bump deps”之类的消息批量合并的升级。请以同样严谨的态度审查它们：

1. **阅读变更日志，而不只是版本号。** 语义化版本是维护者未必遵守的承诺——一个“补丁”版本也可能包含行为变更。对于主版本升级，请阅读迁移说明并找出会破坏哪些内容。
2. **每次变更只升级一个依赖。** 单独升级并合并它们（或按关联性分成小组）。当批量升级导致构建失败时，你将无法判断是哪个包引起的；而单个包的变更会让原因一目了然，也便于干净地回滚。
3. **让测试来决定。** 升级是否通过验证，要看升级前*和*升级后测试套件是否均为绿色，而不是看“是否安装成功”。如果依赖相关行为的测试覆盖不足，那么这个缺口才是真正的问题——先添加测试。
4. **留意传递依赖图。** 大多数已安装的包都不是任何人直接选择的。审查锁文件的差异，而不只是 `package.json`；一次直接依赖升级可能会引入数十项间接变更。
5. **确保锁文件真实可靠。** 提交锁文件、审查其差异，并且绝不要手动编辑它。锁文件才是真正固定发布内容的文件。

对于 `npm audit` 发现的问题以及供应链风险（域名仿冒、维护者账号被入侵）的分类处置，请遵循 `security-and-hardening` 技能——本节涵盖升级*工作流*，而该技能涵盖安全性判定。

## 审查清单

```markdown
## Review: [PR/Change title]

### Context
- [ ] I understand what this change does and why

### Correctness
- [ ] Change matches spec/task requirements
- [ ] Edge cases handled
- [ ] Error paths handled
- [ ] Tests cover the change adequately

### Readability
- [ ] Names are clear and consistent
- [ ] Logic is straightforward
- [ ] No unnecessary complexity

### Architecture
- [ ] Follows existing patterns
- [ ] No unnecessary coupling or dependencies
- [ ] Appropriate abstraction level
- [ ] Refactors reduce complexity rather than relocate it
- [ ] No feature logic in shared modules; file stays within a healthy size

### Security
- [ ] No secrets in code
- [ ] Input validated at boundaries
- [ ] No injection vulnerabilities
- [ ] Auth checks in place
- [ ] External data sources treated as untrusted

### Performance
- [ ] No N+1 patterns
- [ ] No unbounded operations
- [ ] Pagination on list endpoints

### Verification
- [ ] Tests pass
- [ ] Build succeeds
- [ ] Manual verification done (if applicable)

### Verdict
- [ ] **Approve** — Ready to merge
- [ ] **Request changes** — Issues must be addressed
```

## 常见的自我辩解

| 自我辩解 | 事实 |
|---|---|
| “能运行就够了” | 难以阅读、不安全或架构错误的可运行代码会产生不断累积的技术债务。 |
| “这是我写的，所以我知道它是正确的” | 作者往往看不到自己的假设。每项变更都能从另一双审视的眼睛中受益。 |
| “我们之后再清理” | 所谓的“之后”永远不会到来。审查就是质量关卡——要充分利用它。要求在合并前完成清理，而不是合并后。 |
| “AI 生成的代码应该没问题” | AI 代码需要更多审查，而不是更少。即使出错，它也会表现得自信且看似合理。 |
| “测试通过了，所以没问题” | 测试是必要条件，但并不充分。它们无法发现架构问题、安全问题或可读性问题。 |
| “这次重构让代码更整洁了” | 转移复杂性并不等于降低复杂性。如果读者仍需同时理解同样数量的概念，那么结构就没有改善——应寻找能让分支消失的方案。 |
| “只是给这个文件加了一点内容” | 即使差异很小，也可能让文件超出合理规模，并将分支生硬地附加到不相关的流程中。应评估变更后的整体结构，而不是差异大小。 |
| “只是升级一下版本” | 版本升级是你未亲自编写的行为变更。请阅读变更日志；语义化版本控制并不能保证不会发生破坏性变更。 |
| “为了节省时间，我会在一个 PR 里升级所有依赖” | 如果批量升级导致构建失败，就很难确定是哪个包引起的。每次变更只升级一个依赖，才能清晰地定位原因并执行回滚。 |

## 危险信号

- PR 未经任何审查就被合并
- 审查只检查测试是否通过，而忽略其他方面
- 没有实际审查证据就给出“LGTM”
- 涉及安全的变更未经安全专项审查
- PR 规模过大，以至于“无法妥善审查”（应将其拆分）
- Bug 修复 PR 没有回归测试
- 审查意见没有严重程度标签——导致无法明确哪些是必须修改的，哪些是可选的
- 接受“我之后会修复”——之后永远不会发生
- 重构只是移动代码，却没有减少读者必须同时理解的概念数量
- 变更继续扩充一个已经很大的文件，而不是将其拆分
- 在不相关的代码路径中散布新的条件分支（说明缺少抽象）
- 自定义辅助函数重复了已有的规范实现，或者将功能逻辑放入共享模块
- 批量“升级依赖”的 PR 未审查变更日志，也未按包隔离
- 锁文件变更是手动编辑的、未提交的，或者在未审查其差异的情况下被合并

## 验证

审查完成后：

- [ ] 所有 Critical 问题均已解决
- [ ] 所有 Required（无前缀）变更均已解决，或已在给出理由的情况下明确推迟
- [ ] 测试通过
- [ ] 构建成功
- [ ] 已记录验证过程（变更了什么、如何验证）
- [ ] 依赖升级已对照其变更日志进行审查、按包隔离，并通过完整测试套件验证为正常，同时锁文件差异也已完成审查

**推定阻塞项：** 指出以下各类问题，并分别提出更简单的设计；仅当变更确实使结构恶化时，才升级为“必须修复”：重构只是转移复杂度而非降低复杂度；变更导致文件超过大小限制却未进行拆分；将功能逻辑添加到共享模块；新增与现有规范辅助函数近乎重复的实现；通过静默回退掩盖不明确的不变量。
