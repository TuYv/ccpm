# 降低熵

更多的代码会催生更多的代码。熵会不断累积。本技能倾向于尽可能小的代码库。

**核心问题：**“做完*之后*，代码库是什么样子？”

## 开始之前

**从 `references/` 加载至少一种思维模式**

1. 列出参考目录中的文件
2. 阅读 frontmatter 中的描述，挑选适用的那个
3. 加载至少一个
4. 说明你加载了哪一个及其核心原则

**在完成上述步骤之前，不要继续。**

## 目标

目标是**最终代码库中的总代码量更少**——而不是当下要写的代码更少。

- 写 50 行代码以删除 200 行 = 净赚
- 为避免写 2 个函数而保留 14 个 = 净亏
- “零改动”不是目标。代码更少才是目标。

**衡量的是最终状态，而非付出的努力。**

## 三个问题

### 1. 能解决此问题的最小代码库是什么？

不是问“最小的改动是什么”，而是最小的*结果*是什么。

- 这能不能用 2 个函数而不是 14 个来实现？
- 这能不能是 0 个函数（删掉该功能）？
- 如果做这件事，我们会删掉什么？

### 2. 拟议的改动会使总代码量更少吗？

数一数改动前后的行数。如果之后 > 之前，就否决它。

- “组织得更好”但代码更多 = 熵更多
- “更灵活”但代码更多 = 熵更多
- “分离更清晰”但代码更多 = 熵更多

### 3. 我们能删除什么？

每一次改动都是一次删除的机会。要问：

- 这让什么变得过时了？
- 哪些东西只是因为我们正在替换的旧代码才需要存在？
- 我们最多能移除掉什么？

## 危险信号

- **“保留现有的东西”**——现状偏见。关键是代码总量，而不是改动量。
- **“这增加了灵活性”**——为谁而灵活？YAGNI。
- **“更好的关注点分离”**——更多的文件/函数 = 更多代码。分离不是免费的。
- **“类型安全”**——值得为此付出多少行代码？有时用更少的代码做运行时检查更划算。
- **“更容易理解”**——14 个东西不会比 2 个东西更容易理解。

## 何时这条原则不适用

- 代码库相对于其功能已经是最小化的
- 你在使用一个约定很强的框架（不要与之对抗）
- 监管/合规要求强制规定了某些结构
