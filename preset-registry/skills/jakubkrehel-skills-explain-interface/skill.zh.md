# 界面说明

此技能回答某个内容是如何构建的。`/explain-interface how the gradient on example.com was built` 会找到产生该渐变的图层，并充分解释其机制，以便将其重新构建出来。

它解释，而不评判。没有结论，因为其他人如何构建其界面并非一项发现。依据标准进行评审使用 `interface-review` 和 `better-interface`；为你自己的界面探索替代方案则使用 `variant`。

## 根据问题确定范围

两个问题，均为一等问题，除证据规则外毫无共同之处：

| 问题 | 产出内容 | 方法 |
| --- | --- | --- |
| 这个**站点**是如何构建的？ | 前端：框架与渲染策略、样式系统、组件库、设计令牌、字体、间距与色彩系统、动效、断点，以及字体和图片的提供方式 | [read-the-system.md](read-the-system.md) |
| **这个**是如何构建的？ | 某一效果背后的图层堆叠，以及复现它的最小代码 | [find-the-effect.md](find-the-effect.md) |

给定一个具名对象时，将范围限定于它。字体比例和令牌转储并不是对“渐变是如何构建的”这个问题更长的回答，它们回答的是没人问的问题。只有在无法脱离相邻部分解释该效果时才引入它，并说明原因。

这两个问题都可以针对截图而非 URL 提出，这会从根本上改变答案。参见**从截图出发，这是一次重建**。

## 你实际可以读取的内容

你访问页面的方式决定了你可以提出哪些主张。说明你使用了哪种路径。

| | 可脚本化浏览器 | 获取到的 HTML 和 CSS |
| --- | --- | --- |
| 提供给你的内容 | 实际绘制出的内容：计算值、绘制顺序、伪元素、实时动画 | 源码：编写的声明、响应式变体、生成的工具类、所有 `:root` 令牌 |
| 无法看到的内容 | 任何你未访问的宽度或状态 | 哪条规则胜出，以及任何在运行时注入的内容 |

两者都不是降级方案。一个视口下的浏览器会遗漏原始 HTML 所提供的 `md:` 变体，而原始 CSS 无法说明九条匹配规则中哪一条胜出。当问题值得如此处理时，同时使用两者。

Chrome DevTools MCP 是最容易获取的浏览器：

```bash
claude mcp add chrome-devtools -- npx chrome-devtools-mcp@latest
```

它提供用于此处配方的 `evaluate_script`、用于切换宽度的 `resize_page` 和 `take_screenshot`、用于查看所提供资源的 `list_network_requests`，以及用于排查卡顿的 `performance_start_trace`。在以下情况中，优先于获取方式使用它：

- 效果是 `canvas` 或着色器。
- 样式在运行时通过 CSS-in-JS 或主题脚本到达。
- 多条规则匹配，而你需要确定胜出的那一条。
- 答案依赖于动效。

没有浏览器时，[no-browser.md](no-browser.md) 包含获取方式。

## 已测量、已推导、已推断

只有当你能够分辨哪些主张是事实时，一份解释才值得阅读。每项主张都带有三个层级之一，明确说明而非暗示：

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| **已测量** | 从页面读取或从像素采样。可复现。 | `filter: blur(50px)`, `--radius: 0.625rem` |
| **已推导** | 由测量结果计算得出。 | “四个色标，均匀分布至 100%”，“在 1440px 视口中宽 1496px” |
| **已推断** | 关于意图的判断。绝不作为事实陈述。 | “尺寸过大，因此没有边缘落在视口内” |

发明一个看似合理的数值，并把它呈现为测量结果，是唯一一种会让整个答案失去价值的失败。“大约 50px 的模糊，未经测量”是有用的；因为看起来合适就凭空编造的 `box-shadow` 则没有用。

## 从截图出发，这是一次重建

没有页面就没有代码可供阅读，因此答案的性质也会改变。你不是在解释它是如何构建的，而是在提出一种可以让它看起来像那样的构建方式。在答案中明确说明这一点，不要让读者误以为你进行了测量。

有两件事可以保持精确，因为它们直接来自像素本身：你采样得到的颜色，以及其中任意两种颜色之间的对比度。其他一切都是比例，因为截图比例未知，或者是基于外观的推断。

有些东西是无法获得的：设计令牌、框架、样式系统、断点、动效，以及除截图所呈现状态之外的所有状态。你甚至无法确定这个效果是否由 CSS 实现：渐变可能是一张平面图片、一个 `canvas`，或一个着色器。

因此，如果页面是在线的，请索要 URL。一条命令就能替代整个估算过程。在无法获取页面时，[from-an-image.md](from-an-image.md) 提供了相应的方法。

## 找到图层，而不是元素

当你询问是什么产生了一个渐变时，答案几乎从来不是一条声明。现代视觉效果是多个图层的堆叠，而这个堆叠**就是**解释。

一个 hero 渐变通常同时包含四个部分：

- 一个超出容器尺寸的元素，并被部分推到容器外，因此不会露出任何边缘。
- 一个**低 alpha 值的多色标渐变**，通常包含 4 个约为 20% 不透明度的色标。
- 一个较大的 **`filter: blur()`**，它负责将离散的色标变成一片晕染。
- 有时还会有一个位于上方、携带 **`backdrop-filter`** 的图层，为透过它显示的内容添加磨砂效果。

按绘制顺序报告这些图层，并写出每个图层上真正起作用的声明。拥有这组图层的读者可以重建效果。只拿到 `linear-gradient()` 的读者做不到，因为模糊和超大尺寸才是他们所看到的效果中最主要的部分。

[find-the-effect.md](find-the-effect.md) 包含搜索配方，其中包括另外三项否则会让你无法得出答案的内容：伪元素图层、动画库留下的闲置值，以及生成的色标列表。

## 以小规模重建

用能产生该效果的最小实现收尾。对于有针对性的问题，这比一篇长篇文章更好，因为它可以验证：粘贴代码，查看效果，完成。

只保留关键图层，去掉产品自身的令牌、类名和框架。然后补充一行，说明哪些内容无法直接迁移：授权字体、品牌色调，或针对你无法获得的视口宽度调校过的模糊半径。

如果效果依赖于你无法读取的内容，请如实说明，而不是继续猜测。跨源样式表、canvas 或 WebGL 着色器都可以作为诚实的止步点。

从截图出发，复现是一份提案，而不是一次还原。将其标注为实现这种外观的一种方式，并预期真实实现会有所不同。

## 完成之前

| 错误 | 修正方法 |
| --- | --- |
| 将看似合理的值表述为测量结果 | 说明其层级，或指出它未经测量 |
| 将一条声明报告为完整效果 | 按绘制顺序报告图层堆栈 |
| 从未检查伪元素 | 在每个候选元素上读取 `::before` 和 `::after` |
| 将 `filter: blur(0px)` 报告为效果 | 它是动画库的空闲状态；将其过滤掉 |
| 逐字列出十二个插值色标 | 指出生成这些色标的技术 |
| 面对关于单一事物的问题，却倾倒出整个系统 | 回答所问，并深入而非铺开 |
| 解释中没有复现代码 | 以能产生该效果的最小代码收尾 |
| 根据截图声称获得精确的 `px` 值 | 只有颜色和对比度能从像素中精确得出 |
| 将截图回答写得仿佛已阅读代码 | 称其为重建，并说明哪些内容无法得知 |
