# 使用 Git 工作树

## 概述

工作树是同时检出另一段 Git 历史记录的一种例外情况，而不是通用的安全标志。优先使用当前工作区，并复用现有的合适工作树。分支决策与工作树决策是彼此独立的。

**核心原则：** 仅在有必要性和所有权证据时创建；每个创建的工作树都必须配套一个清理路径。

**开始时宣布：** 说明需要使用工作树的具体检出冲突。

## 步骤 0：环境检测

在进行变更之前，记录仓库根目录、`HEAD`、分支/分离状态、已暂存/未暂存/未跟踪的路径、活动中的 Git 操作，以及：

```bash
git worktree list --porcelain
```

将当前宿主界面的任务/聊天绑定托管工作区语义分类为 `managed`、`non-managed` 或 `unknown`。使用受信任的宿主/会话上下文、明确的宿主契约或宿主原生生命周期结果；不要根据产品名称、目录前缀、命令级别的 `workdir`、缺失的工具或不存在的元数据来推断该分类。`non-managed` 必须有当前界面缺少任务绑定托管语义的正面证据。当宿主提供工作区字段时，记录任务工作区以及命令的默认 `cwd`，不要使用逐命令的目录覆盖。

如果存在未解决的冲突、活动中的合并/变基/拣选提交/还原/二分查找操作，或存在无法解释的分离 HEAD，则停止。只有在受信任的宿主绑定证据表明分离 HEAD 是当前托管工作树的预期状态时，分离 HEAD 才可接受；例如，Codex 管理的工作树默认以分离状态启动。保留用户状态：不得自动执行 stash、reset、clean、广泛暂存或提交。

在决定必要性或放置位置之前，阅读最小范围内相关的项目 `AGENTS.md`、`CLAUDE.md`、当前权威规范以及现有的工作树约定。仓库策略可能要求或禁止隔离，并决定任何获准的仓库内位置；不要在创建检出之后才发现该策略。

## 步骤 1：必要性决策

仅当满足以下任一条件时，最多创建一个由任务拥有的工作树：

- 在任务继续进行时，必须保持另一个分支处于检出状态；
- 无关的脏状态阻止在当前工作区中安全检出；
- 明确的用户要求或当前仓库权威规范要求这样做。

任务复杂度、规划、TDD、使用子代理，或分支名称为 `main`/`master`，都不足以构成理由。同一任务的子代理共享一个工作区；不要为每个子代理创建工作树，也不要创建嵌套工作树。如果不需要独立历史记录，也不要创建分支。

记录：原因、分支、确切路径、创建协调者以及预期的清理事件。如果所有者或清理条件未知，则在创建之前停止。

## 步骤 2：安全放置

仅当目标目录已经被忽略时，才使用现有的仓库约定（`git check-ignore`）。绝不要仅为了容纳工作树而编辑或提交 `.gitignore`。如果不存在安全的仓库内约定，则使用仓库之外、特定于任务的用户级临时目录。解析并验证确切路径后再创建；不要将宽泛的主目录、工作区或仓库根目录作为目标。

## 第 3 步：创建最小检出

优先复用承载相同目标的现有分支。仅当已批准的 Git 生命周期要求独立历史时，才创建分支。

### 受管主机绑定门禁

当主机界面声明任务/聊天绑定的受管工作区时，应使用其原生的 Worktree/Handoff 生命周期，而不是通过 shell 创建。仅当可信的主机证据表明当前任务已绑定到目标工作区时，才复用当前任务。如果原生操作创建了另一个任务，或将工作迁移到另一个任务，则只能在该已绑定的任务中继续。

在原生生命周期操作完成后，或在进入/复用已绑定的受管工作区时立即，并且在首次写入任务内容或 Git 历史之前，读取一次联合后置条件：

- 可信的任务工作区；
- 未使用命令级目录覆盖的默认命令 `cwd`；
- 目标 Git worktree 根目录；
- 目标 `HEAD` 以及分支/分离状态。

这四项必须描述同一个执行环境。`git worktree list`、看起来像受管工作区的路径，或按命令指定的 `workdir`，都只能证明该后置条件的一部分。如果原生创建/交接不可用、只能通过 UI 驱动，或无法验证，则应在 shell 创建 worktree 或写入任务内容/历史之前停止，并向用户提供主机原生的重新进入操作。不要静默回退到 `git worktree add`。
应使用适合主机的语义比较解析后的路径标识，而不是比较原始路径字符串。默认 `cwd` 可以等于 worktree 根目录，也可以位于其内部；从该默认 `cwd` 运行 Git 时，必须解析到目标 worktree 根目录。
预期中的主机管理型分离 HEAD 满足 Git 状态这一组成部分；不要仅仅为了让该状态看起来像通用检出而创建分支。

如果已经存在未绑定的手动 worktree，应保留它，并报告其准确路径、`HEAD`、分支、状态和所有权证据。脏状态、未跟踪状态或所有权未知的状态不得被自动迁移、删除、暂存、重置或覆盖。后续的提交/补丁传输应遵循正常的 Git 授权流程，并且必须在新的已绑定任务中完成验证，然后才能提出清理操作。

### 通用 Git 回退

仅当可信证据明确将当前主机/CLI 界面归类为 `non-managed` 时，才使用下面的 shell 路径。`unknown` 分类应安全失败；缺少原生工具或缺少绑定元数据，都不能作为通用回退的证据。

```bash
# Existing branch
git worktree add <exact-path> <branch>

# New independently justified branch
git worktree add -b <branch> <exact-path> <start-point>
```

读取 `git worktree list --porcelain`、新 worktree 的 `HEAD`/分支以及其状态。不要使用强制标志。在通用主机上，命令级 `workdir` 可以将目标指向此检出，但它永远不能证明受管任务绑定。

## 第 4 步：以权威信息为先进行设置和建立基线

阅读项目的安装文档、锁文件和现有设置脚本。仅运行项目明确要求的设置操作。不要仅仅因为存在清单文件，就推断需要执行 `npm install`、`cargo build`、`pip install`、`poetry install` 或下载依赖。

运行最小相关的基线验证。如果设置或测试失败，报告确切的失败信息并保留工作树；不要通过修改无关文件来掩盖问题。

## 步骤 5：交接与清理责任

报告确切路径、分支、起始 `HEAD`、基线结果、负责人和清理触发条件。创建该工作树的协调者在证明已完成清理或明确移交责任之前，仍持续负责。

在任务提交或作出集成决策后使用 `finishing-a-development-branch`。通常可以移除工作树，同时保留其尚未合并的分支；未关闭的 PR 不要求永久保留检出目录。

## 危险信号

切勿：

- 仅因为任务会修改代码就创建工作树；
- 仅为使工作树创建成为可能而修改 `.gitignore`；
- 盲目安装依赖；
- 为每个子代理创建一个工作树；
- 将 Git 读回结果、路径前缀或命令级 `workdir` 视为已建立受管理任务绑定的证据；
- 仅因为主机原生能力被延后、仅限 UI 使用或未出现在初始工具列表中，就使用 shell 创建工作树；
- 将全局 prune 或强制清理作为例行维护；
- 移除脏的、未跟踪的、被锁定的、用户拥有的或所有权未知的资源。

## 集成

仅在规划/执行工作流中、完成必要性决策之后按条件调用。与 `finishing-a-development-branch` 配合，以基于证据进行清理。
