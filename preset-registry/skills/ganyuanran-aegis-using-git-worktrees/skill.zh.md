# 使用 Git 工作树

## 概述

工作树是用于同时检出另一段 Git 历史记录的例外手段，而不是通用的安全保障。应优先使用当前工作区，并复用现有的合适工作树。分支决策与工作树决策是相互独立的。

**核心原则：**仅在有必要且有归属依据时创建；为每个创建的工作树安排清理路径。

**开始时声明：**说明具体是哪项检出冲突需要使用工作树。

## 步骤 0：环境检测

在进行任何变更之前，记录仓库根目录、`HEAD`、分支/分离状态、已暂存/未暂存/未跟踪的路径、正在进行的 Git 操作，以及：

```bash
git worktree list --porcelain
```

如果处于分离的 HEAD 状态、存在未解决的冲突，或正在进行 merge/rebase/cherry-pick/revert/bisect，请停止操作。保留用户状态：不得自动执行 stash、reset、clean、大范围暂存或 commit。

在判断必要性或放置位置之前，阅读相关范围最小的项目 `AGENTS.md`、`CLAUDE.md`、当前权威指引以及现有的工作树约定。仓库策略可能要求或禁止隔离，并规定任何获准使用的仓库内位置；不要在创建检出后才去了解该策略。

## 步骤 1：必要性决策

仅当以下条件之一成立时，最多创建一个归当前任务所有的工作树：

- 此任务进行期间，另一个分支必须保持检出状态；
- 不相关的脏状态导致无法在当前工作区中安全检出；
- 用户或当前仓库的权威指引明确要求这样做。

任务复杂度、规划、TDD、使用子代理，或分支名为 `main`/`master`，均不足以作为理由。同一任务的子代理共享一个工作区；不要为每个子代理创建工作树，也不要创建嵌套工作树。如果不需要独立历史记录，也不要创建分支。

记录：原因、分支、确切路径、负责创建的协调者以及预期的清理时机。如果所有者或清理条件未知，请在创建前停止操作。

## 步骤 2：安全放置

仅当目标目录已被忽略（`git check-ignore`）时，才使用现有的仓库约定。绝不要仅为了容纳工作树而编辑或提交 `.gitignore`。如果仓库内没有安全的约定位置，请使用仓库外、特定于任务的用户级临时目录。在创建之前解析并验证确切路径；不要将宽泛的主目录、工作区根目录或仓库根目录作为目标位置。

## 步骤 3：创建最小检出

优先复用承载相同目标的现有分支。仅当获准的 Git 生命周期需要独立历史记录时才创建分支。

```bash
# Existing branch
git worktree add <exact-path> <branch>

# New independently justified branch
git worktree add -b <branch> <exact-path> <start-point>
```

再次读取 `git worktree list --porcelain`、新工作树的 `HEAD`/分支及其状态。不要使用强制标志。

## 步骤 4：遵循权威指引进行设置并建立基线

阅读项目的安装文档、锁文件和现有设置脚本。仅运行项目明确要求的设置。不要仅根据清单文件的存在就推断需要执行 `npm install`、`cargo build`、`pip install`、`poetry install` 或下载依赖项。

运行最小范围内的相关基线验证。如果设置或测试失败，请报告
确切的失败信息并保留工作树；不要通过修改无关文件来掩盖失败。

## 步骤 5：移交与清理责任

报告确切路径、分支、起始 `HEAD`、基线结果、负责人和清理
触发条件。创建该工作树的协调者始终负有责任，直到其证明清理已完成
或明确移交责任。

在任务提交或集成决策之后使用 `finishing-a-development-branch`。
通常可以移除工作树，同时保留其尚未合并的分支；
开放的 PR 不需要永久保留检出目录。

## 危险信号

绝不要：

- 仅仅因为任务会修改代码就创建工作树；
- 仅仅为了能够创建工作树而修改 `.gitignore`；
- 盲目安装依赖；
- 为每个子代理创建一个工作树；
- 将全局剪枝或强制清理作为例行维护操作；
- 移除脏的、未跟踪的、已锁定的、归用户所有的或归属不明的资源。

## 集成

仅在完成必要性判断后，由规划/执行工作流按条件调用。
与 `finishing-a-development-branch` 配合使用，以进行基于证据的清理。
