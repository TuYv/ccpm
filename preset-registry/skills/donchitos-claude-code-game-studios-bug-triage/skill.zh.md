# Bug 分诊

此技能将待处理的开放 Bug 转化为按优先级排序并分配到冲刺的行动列表。它区分 **严重程度**（影响有多严重？）和 **优先级**（必须多快修复？），识别系统性趋势，并确保任何关键 Bug 都不会在冲刺之间遗漏。

**输出：** `production/qa/bug-triage-[date].md`

**运行时机：**
- 冲刺开始时——将开放 Bug 分配到新冲刺或待办列表
- `/team-qa` 完成并提交了新 Bug 后
- 开放 Bug 数量达到 10 个以上时

---

## 1. 解析参数

**模式：**
- `/bug-triage sprint` ——根据当前冲刺进行分诊；将可修复的 Bug 分配到冲刺待办列表；其余延后处理
- `/bug-triage full` ——完整分诊所有 Bug，不考虑冲刺范围
- `/bug-triage trend` ——仅进行趋势分析（不分配）；生成只读报告
- 无参数——如果存在当前冲刺，则运行冲刺模式，否则运行完整模式

---

## 2. 加载 Bug 待办列表

### 步骤 2a——查找 Bug 文件

按以下优先顺序使用 Glob 查找 Bug 报告：
1. `production/qa/bugs/*.md` ——独立 Bug 报告文件（首选格式）
2. `production/qa/bugs.md` ——单个汇总 Bug 日志（备用格式）
3. 任意 `production/qa/qa-plan-*.md` 中的“发现的 Bug”表格（最后手段）

如果未找到 Bug 文件：
> “在 `production/qa/bugs/` 中未找到 Bug 文件。如果 Bug 记录在其他
> 位置，请调整 Glob 模式。如果目前尚不存在 Bug，则无需进行分诊。”

停止并报告。如果不存在 Bug，请勿继续。

### 步骤 2b——加载冲刺上下文

读取 `production/sprints/` 中最近修改的文件，以了解：
- 当前冲刺编号/名称
- 范围内的故事（作为分配目标）
- 冲刺容量限制（如果有注明）

如果不存在冲刺文件，请注明“未找到冲刺计划——仅分配到待办列表。”

### 步骤 2c——加载严重程度参考标准

读取 `.claude/docs/coding-standards.md` 中的严重程度/优先级定义（如果存在）。如果不存在，则使用步骤 3 中的标准定义。

---

## 3. 对每个 Bug 进行分类

对于每个 Bug，提取或推断：

### 严重程度（Bug 的影响）

| 严重程度 | 定义 |
|----------|-----------|
| **S1 — 严重** | 游戏崩溃、数据丢失或功能完全失效。无法继续通过此处。 |
| **S2 — 高** | 主要功能损坏，但游戏仍可游玩。存在显著的错误行为。 |
| **S3 — 中** | 功能退化，但存在变通方法。存在轻微的错误行为。 |
| **S4 — 低** | 视觉故障、外观问题或拼写错误。不影响游戏玩法。 |

### 优先级（修复的紧迫程度）

| 优先级 | 定义 |
|----------|-----------|
| **P1 — 本冲刺修复** | 阻塞 QA、阻塞发布，或属于上个冲刺引入的回归问题 |
| **P2 — 尽快修复** | 应在下一个重要里程碑之前解决 |
| **P3 — 待办列表** | 最好修复，但当前不会造成阻塞影响 |
| **P4 — 不修复/延期** | 接受风险，或超出当前产品范围 |

### 分配

对于 `sprint` 模式下的每个 P1/P2 Bug：
- 确定修复归属于哪个故事或史诗
- 检查当前冲刺是否仍有剩余容量
- 如果有容量：分配到冲刺（`Sprint: [current]`）
- 如果容量已满：标记为 `Priority overflow — consider pulling from sprint`

对于 `full` 模式：将所有 P1 分配到当前冲刺，将 P2 预计安排到下一冲刺，
将 P3+ 放入待办列表。

### 偏差检查

标记暗示存在**系统性问题**的缺陷：
- 同一冲刺中有 3 个以上来自同一系统的缺陷 → “[system] 中可能存在设计或
  实现质量问题”
- 同一故事中有 2 个以上 S1/S2 缺陷 → “故事可能需要重新打开，并在
  发布前重新评审”
- 针对标记为 Complete 的故事提交了缺陷 → “已完成故事中出现回归 —
  应在冲刺跟踪中重新打开该故事”

---

## 4. 趋势分析

对所有缺陷进行分类后，生成趋势指标：

### 数量趋势
- 未解决缺陷总数：[N]
- 本冲刺新建：[N]
- 本冲刺关闭：[N]
- 净变化：[+N / -N]

### 系统热点
- 哪个系统的未解决缺陷最多？
- 哪个系统的 S1/S2 比例最高？

### 缺陷时长分析
- 有多少缺陷已存在超过 2 个冲刺？
- 是否有任何 S1/S2 缺陷尚未分配（sprint = none）？

### 回归指标
- 是否有针对先前已完成故事提交的缺陷？
- 数量：[N] 个回归缺陷（意味着故事已重新打开）

## 6. 写入并设置关卡

在对话中展示报告，然后询问：

“我可以将此分诊报告写入 `production/qa/bug-triage-[date].md` 吗？”

仅在获得批准后写入。

写入后：
- 如果有任何 S1 缺陷尚未分配：“必须先分配 S1 缺陷，才能认为冲刺处于健康状态。
  运行 `/sprint-status` 查看当前容量。”
- 如果存在回归缺陷：“发现回归问题——请考虑在冲刺跟踪中重新打开受影响的
  用户故事，并运行 `/smoke-check` 重新进行准入检查。”
- 如果不存在 P1 缺陷：“没有 P1 缺陷——构建状态良好，可以移交 QA。”结论：**已完成**——分诊报告已写入。

如果用户拒绝写入：结论：**已阻塞**——用户拒绝写入。

---

## 协作协议

- **未经用户批准，绝不关闭缺陷或将缺陷标记为 Won't Fix**——将其作为 P4 候选项列出，
  并询问：“是否可以将这些缺陷标记为 Won't Fix？”
- **绝不自动分配到容量已满的冲刺**——标记溢出项，由冲刺负责人决定要纳入哪些项
- **严重程度是客观的；优先级是团队决策**——将严重程度分类作为建议提出，而非强制要求
- **趋势数据仅供参考**——不要仅根据趋势发现阻塞工作；
  将其作为观察结果列出
