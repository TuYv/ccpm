# 测试驱动开发

TDD 就是“红 → 绿”循环。本技能是一份参考，让这个循环产出值得保留的测试：什么是好测试、测试放在哪里、反模式有哪些、循环的规则是什么。每一节都适用于每一轮循环：请在循环之前和过程中查阅它们，而不是事后才看。

在探索代码库时，先阅读 `CONTEXT.md`（如果存在），使测试命名和接口用语与项目的领域语言保持一致，并尊重你所触碰区域内的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而非实现细节。代码可以彻底重写，测试不应随之改变。好测试读起来像一份规格说明："user can checkout with valid cart" 准确告诉你存在什么能力，而且它不在乎内部结构，因此能在重构中幸存。

示例参见 [tests.md](tests.md)，mock 指南参见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝（seam）**是你进行测试的公共边界：在不伸手进入内部的情况下观察行为的接口。测试栖身于接缝处，绝不针对内部实现。

**只在事先商定的接缝处测试。** 在编写任何测试之前，先写下待测的接缝并与用户确认。任何测试都不写在未经确认的接缝上。你无法测试所有内容，因此事先就接缝达成一致，才能让测试精力落在关键路径和复杂逻辑上，而不是摊到每一条边缘情况。

可以问：“公共接口是什么？我们应该测试哪些接缝？”

当接口本身的形态尚不确定时（模块有多深、接缝属于哪里、接口应当暴露什么），调用 Skill 工具并传入 "codebase-design" 以获取相关术语。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共同出处；它是供查阅的参考，而不是一个要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路通道验证（直接查询数据库而不是使用接口）。识别信号：重构后行为并未改变，测试却失败了。
- **同义反复**：断言按代码的同样方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以同样方式手工推导出的快照、断言常量等于其自身），因此它从构造上就会通过，永远不可能与代码不一致。期望值必须来自独立的真相来源：已知正确的字面量、手工推导的完整示例、规格说明。
- **水平切分**：先写完所有测试，再写全部实现。成批的测试验证的是*想象中的*行为：你测的是事物的*形状*而非面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。请以**垂直切片**方式工作：一个测试 → 一段实现 → 重复，每个测试都是一颗**曳光弹**，对上一轮循环教给你的东西作出响应。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每轮循环一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于评审阶段（参见 `code-review` 技能），而不是红 → 绿的实现循环。
