# 回放用户体验研究

分析 sentry.io 真实外部用户的会话回放，以发现给定产品领域中的用户体验模式、痛点和具有代表性的用户旅程。此技能使用 Sentry 自己的内部试用组织。

## 输入

`$ARGUMENTS` 是要研究的产品领域（例如，"issues"、"traces"、"dashboards"、"replays"、"monitors"、"releases"、"alerts"）。

如果 `$ARGUMENTS` 为空，请询问用户要研究哪个产品领域。

## 前置条件

此技能需要连接 Sentry MCP 服务器。会使用以下工具：
- `search_events` — 搜索会话回放
- `get_replay_details` — 获取详细的回放信息
- `search_issues` — 查找错误问题
- `get_sentry_resource` — 从 URL 获取问题详情

如果这些工具不可用，请在继续之前要求用户连接 Sentry MCP 服务器。

## 第 1 步：将产品领域映射到 URL 模式

读取 `references/product-areas.md`，查找所请求领域对应的 URL 模式。

如果该产品领域未列出，请根据领域名称推断 URL 模式。大多数 Sentry 产品领域在 URL 路径中遵循 `/<area-name>/` 模式。参考文件可能未涵盖较新的产品领域——如果不确定，请向用户确认你的假设。

## 第 2 步：搜索回放

搜索外部用户（非 Sentry 员工）的回放。25 个回放是一个合适的起点——如果产品领域较为复杂、初步呈现的模式不明确，或用户希望获得更全面的了解，请进一步深入研究。

从过去 24 小时开始——如果需要达到目标数量，可将时间范围扩展至 48 小时或 7 天。如有需要，执行多次 `search_events` 调用。每次调用使用 `limit: 50`。

**如果找不到足够的回放**（即使将范围扩展至 7 天，仍少于 10 个），请告诉用户你找到了什么，并请他们协助迭代——他们可以建议使用更宽泛的 URL 模式、不同的时间范围，或纳入相关的产品领域。

**查询构造：**

使用如下自然语言查询：

```
replays from the last 24 hours where url contains "/<area-path>" excluding user emails ending in @sentry.io and @getsentry.com
```

关键筛选条件：

- **时间范围**：过去 24 小时（必要时扩展）
- **URL 模式**：匹配第 1 步中的产品领域路径
- **排除员工**：`-user.email:*@sentry.io -user.email:*@getsentry.com`
- **环境**：prod

不要传入 `projectSlug` 筛选条件——回放覆盖整个组织。

## 第 3 步：获取回放详情

对第 2 步中找到的每个回放调用 `get_replay_details`。为提高速度，请并行分批执行这些调用。

对于每个回放，记录：

- **用户**：仅记录电子邮件域名（API 会返回完整的电子邮件地址——绝不要在输出中包含这些地址）
- **旅程**：按顺序排列的已访问页面列表（来自 URL 和活动面包屑）
- **持续时间**：会话总时长
- **回放类型**：`session`（从正常浏览中随机采样）与 `buffer`（由某个事件触发——错误、手动刷新，或提交反馈、进行结账等特定用户操作）。请在分析中注明这一区别，因为 `buffer` 回放偏向于错误或操作发生的时刻，而非典型的浏览行为。
- **进入上下文**：第一个 URL 会显示用户如何进入——检查查询参数中是否存在 `referrer=slack`、`notification_uuid`、`alert_rule_id` 等来源信号（Slack 通知）、电子邮件链接模式或裸 URL（书签/直接导航）
- **参与度信号**：错误数、愤怒点击、无效点击、警告数
- **浏览器/操作系统/设备**：用于了解设备分布情况
- **活动面包屑**：页面浏览、导航模式、关键交互

## 第 4 步：调查重大错误

收集回放详情后，识别在多次回放中出现或可能影响用户体验的错误。对于每个重大错误：

1. **按出现频率进行分诊**：如果同一个问题 ID（例如 `JAVASCRIPT-33RM`）出现在 3 次以上的回放中，就值得调查。
2. **在 Sentry 中检查问题**：使用 `search_issues` 查找问题，或使用 `get_sentry_resource` 和回放详情中的问题 URL 获取问题。了解：
   - 错误是什么？（消息、堆栈跟踪上下文）
   - 它总共影响多少用户/事件？（不仅限于此回放样本）
   - 是否已分配给相关人员或正在处理中？
3. **根据行为信号推断面向用户的影响**：我们无法通过回放元数据看到渲染后的页面内容——只能在浏览器中观看回放。相反，应根据错误发生后用户的行为来推断其影响：
   - **重试相同操作** → 他们很可能看到了失败并再次尝试
   - **立即离开当前页面** → 他们遇到了阻碍或选择了放弃
   - **正常继续其操作流程** → 错误可能无感知或仅影响外观
   - **随后出现愤怒点击或无效点击** → UI 可能已无响应
   - **错误发生后在页面上停留很长时间** → 他们可能正在阅读错误消息或感到困惑
   - **行为完全没有变化** → 错误可能对用户不可见
4. **根据这些证据对每个错误进行分类**：
   - **可能造成阻塞**：发生错误后，用户重试、离开或无法继续。对用户影响的置信度高。
   - **可能导致体验下降**：发生错误后，用户继续操作，但行为异常。置信度中等。
   - **可能无感知**：触发了错误，但用户行为未受影响。对用户影响的置信度低。
   - **不明确**：没有足够的行为信号可供判断。标记为需要人工查看回放。

   始终注明置信度，并建议观看特定回放以进行确认。对于每个已分类的错误，直接链接到相应的回放 URL。

在“摩擦点与痛点”部分中包含此分类。不要将可能无感知的错误报告为痛点——为了完整起见，请将其列在单独的“后台错误（可能无感知）”子部分中。

## 第 5 步：分析模式

通过以下 UX 研究视角查看回放：

### 行为模式

1. **常见旅程**：用户采用哪些导航路径？典型流程是什么？
2. **入口点**：用户如何到达？分类为：提醒通知（Slack/电子邮件）、直接书签、从其他页面自然导航而来。第一个 URL 的查询参数可以揭示这一点。
3. **任务完成情况**：用户是否看起来完成了某个目标，还是漫无目的地浏览或中途放弃？完成的迹象：导航到详情视图后离开。放弃的迹象：会话时间短、来回导航、从进入时所在的同一页面离开。
4. **任务耗时**：用户在采取操作之前，会在关键页面上停留多长时间？

### 摩擦与功能发现

1. **摩擦信号**：愤怒点击、无效点击、错误——还包括*犹豫*（反复访问同一页面）、*频繁跳转*（在页面之间快速来回切换）以及*重试循环*（重复执行相同的操作序列）。
2. **功能发现**：用户是否发现了子功能（筛选、搜索、排序、批量操作），还是只使用主要视图？从 URL 查询参数和面包屑导航中寻找功能使用的证据。
3. **用户意图信号**：从 URL 查询参数中挖掘用户设置的搜索词、筛选值、排序顺序和日期范围。这些内容最接近用户的原话——它们揭示了用户用自己的措辞表达的查找目标。（例如，`query=is%3Aunresolved+assigned%3Ame` 表明用户正在对分配给自己的问题进行分诊。）
4. **变通方法**：是否存在任何意外的导航模式，暗示功能缺失或流程令人困惑？（例如，在任务进行过程中转到设置页面，或依次打开多个原本可以整合到一个视图中的页面）
5. **错误恢复**：当用户遇到错误时，他们是恢复并继续操作，还是放弃？

### 背景信息

1. **回放触发类型的构成**：`session`（随机抽样）与 `buffer`（事件触发）各占多大比例？Buffer 回放呈现的是发生了某些值得关注事件（错误、提交反馈、结账等）的时刻——它们对于分析操作阻碍很有价值，但不能代表典型的浏览行为。在得出结论时，应明确指出这种偏差。
2. **回访用户**：是否有任何电子邮件域名出现在多条回放中？重复访问表明用户可能已形成习惯性使用——他们的操作历程可能揭示高级用户的使用模式，或他们已经学会绕过的长期痛点。
3. **用户多样性**：回放是来自许多不同的组织/公司，还是集中在少数组织/公司？不同组织的用户在行为上是否存在差异？
4. **设备/浏览器分布**：用户主要使用什么设备和浏览器？
5. **流失点**：用户在哪里离开或导航至其他页面？

## 第 6 步：撰写报告

使用 `references/output-template.md` 中的模板。内容要具体——引用单条回放作为每种模式的证据。提供回放 URL 链接，以便读者自行观看回放。

**隐私**：切勿在报告中包含用户的完整电子邮件地址。请使用匿名标识符，例如“来自 [company domain] 的用户”或“用户 A、B、C”。
