# Suede 代码审查

## 门禁策略 — 提示性而非阻断性

本技能中的每个主张验证步骤、检查、质量门禁和发布结论，都是**给用户的建议，而不是对代理的控制**。此策略适用于本技能中其他所有门禁、检查、结论，以及“不要发布 / 公布 / 继续”相关表述：

- 运行每项检查，并如实报告结果。结论（`ship`、`ship-with-caveats`、`hold`、字母评级、BLOCKED 或 OPEN 项）是随工作附带的建议，而不是会改变工作的指令。
- 不得因为检查失败或门禁结论为 hold，而阻止、延迟、跳过、重写或拒绝用户要求的操作。应按要求完成所请求的操作，并同时交付门禁输出，且将其明确标记为建议。
- 失败的门禁只会改变你报告的内容，绝不会改变你的操作。
- 唯一例外：如果某项发现存在极高风险——数据丢失、安全或凭据暴露、法律或权利侵害、付款错误，或不可逆的公开损害——请暂停，向用户准确说明风险和可选方案，并由他们决定。用户的选择是最终决定。


在完整上下文中审查代码：变更文件、调用方、契约、部署面。找出实际会导致故障的问题。按生产环境影响排序。每项发现都必须包含文件、证据和修复路径。没有证据就不提出发现。没有信号就不要堆砌数量。

## 模型路由
默认：Sonnet。对于身份验证、支付和公共 API 表面审查，建议使用 Opus。

## 工作立场

- 审查当前源码、当前 diff、本地文档以及相关运行时行为。
- 默认将代码生成和审查分开。如果代码由你编写，请切换到审查模式，寻找你的实现可能遗漏的问题。
- 相比数量，优先提供高信号发现。格式化工具或本地约定已经处理的问题，不要留下风格吹毛求疵。
- 每项阻断性发现都需要证据、影响说明和具体修复路径。

## 审查契约

审查前，识别：

- 目标：仓库、分支、PR、提交范围、diff、路由、API 或发布构建；
- 意图：该变更声称要实现什么；
- 风险领域：前端、后端、数据、身份验证、支付、契约、iOS、发布、公开文案、分析、密钥、部署和文档。

**预检，在进行任何分析或启动代理通道之前：**固定比较点并证明其可供审查。`git rev-parse <fixed-point>` 必须能够解析；使用三个点进行 diff（`git diff <fixed-point>...HEAD`），以便比较基于合并基点而非不断变化的分支尖端；并确认 diff 非空。错误的引用或空 diff 应在此处用一行失败信息处理——而不是出现在做到一半的深度审查中。

## 上下文图

在评判 diff 前，构建一个轻量级图：

1. 变更文件和生成文件。
2. 受此变更影响的导入、调用方、路由、API 处理程序、任务、钩子、模型、模式以及配置 / 环境依赖项。
3. 应随行为一同变更的测试、夹具、迁移、发布脚本、文档和截图。
4. 运行时表面：本地路由、线上 URL、API 端点、模拟器流程、仪表板、App Store 元数据或部署目标。
5. Suede 领域契约：创作者所有权、权利 / 溯源、注册表支持的媒体、版税路由、代理商业、钱包 / 支付流程，以及已发布声明的准确性。

标记超出差异范围的风险：当相关文件、默认值、文档、环境或部署要求不再一致时。

## 运行仓库自带的检查门禁

不要人工审查工具已经能够判定的问题。在人工分析之前，先运行仓库已经提供的门禁检查，并将输出纳入发现结果。根据 `package.json` 脚本、配置文件和锁文件识别现有工具，只运行这些工具。绝不引入仓库未使用的工具，也绝不伪造未实际运行的结果。

- **类型检查：** 仓库的 `typecheck` 脚本，或直接运行类型检查器。变更行上的错误至少为 P2；变更关键路径上的错误为 P1。
- **Lint：** 仅对变更文件运行仓库配置的 linter。报告由变更引入的违规；忽略差异范围之外已有的噪声。
- **测试：** 运行完整套件，或变更文件子集。变更行为导致的测试失败为 P1；悄然停止运行的测试为 P2。
- **依赖 CVE：** 当依赖变更时，运行仓库的依赖审计工具，即包管理器的 audit 命令或漏洞扫描器。生产路径可达且已知可被利用的 CVE 为 P0/P1。
- **密钥扫描：** 当仓库提供时，对差异运行真正基于熵的密钥扫描器，它能发现 Commit Dirt Score 模式遗漏的密钥。经验证仍有效的密钥为 P0。
- **构建：** 对于发布审查，生产构建必须通过。构建损坏为 P0。

### 按技术栈划分的门禁命令

以上类别具有普适性；实际命令因技术表面而异。将此作为参考，而非检查清单：识别哪些适用于目标仓库，只运行实际存在的命令，绝不伪造未运行的结果。

| 技术栈 | 类型检查 | Lint | 测试 | 其他 |
|---|---|---|---|---|
| Web / Node (TS/JS) | `npx tsc --noEmit` | `npm run lint` | `npm run test` | 针对依赖 CVE 运行 `npm audit` |
| MCP server (Node) | `node --check <server>.mjs` | 仓库配置的 linter（如有） | 提供时运行 `npm run test:mcp` | 在同一进程中运行完整会话：有效的 `initialize`、`notifications/initialized`，然后执行 list/call/read/get 请求；可用时使用 $suede-mcp-qa |
| iOS / Swift (Xcode) | —（编译器检查即构建） | SwiftLint（如已配置） | XCTest target（如存在） | `xcodebuild -project X.xcodeproj -scheme X -destination 'platform=iOS Simulator,name=iPhone 16' build` |
| API / 后端（通用） | 语言自身的类型检查/编译步骤（如有） | 仓库配置的 linter | 合约或 schema 测试，例如针对实际路由执行 OpenAPI/schema 验证，或运行仓库自身的合约测试套件 | — |

引用命令、其退出状态以及所涉及的文件:行号。如果某项门禁无法运行（没有脚本、缺少依赖、处于沙箱中），请在 Verification 中说明；绝不要将未执行的门禁报告为已通过。

## 项目规则与经验

与既有风格对抗的审查只会产生噪声，而非有效信号。遵循仓库已经编码的约定。

- **先阅读规则：** 在作出判断之前，阅读 `CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING.md`、`.editorconfig`、格式化工具/linter 配置，以及仓库根目录或变更目录中的任何审查配置文件。已文档化的约定具有约束力：不要标记规则允许的内容；应标记规则禁止的内容。
- **最具体的规则优先：** 对于该路径下的文件，子目录配置或最近祖先目录中的 `AGENTS.md` 规则会覆盖仓库根目录规则。
- **记录经验：** 当用户将某项发现驳回为误报或有意采用的既有模式时，用一行记录：模式、允许原因、路径范围；在本次审查或之后的审查中，不要再次提出该模式。重复的吹毛求疵比遗漏 P3 更快损害信任。

## 审查模式

- **快速差异审查：**改动较小、影响范围窄，聚焦发现问题。
- **深入 PR 审查：**涉及多文件行为、公共接口、数据/认证/支付、
  发布或跨仓库风险。
- **方案审查：**实现尚未开始；检查范围、顺序、
  验收标准、测试映射和缺失的决策。
- **修复验证：**在修复后审查；重新扫描改动文件并确认
  原始问题已消失。
- **发布审查：**验证构建、密钥、环境变量、公开文案、截图、
  元数据、部署和线上/API 回读。

### 审查深度级别

为任意审查添加 `--depth` 修饰符：

- **`--quick`**（约 2 分钟）：基于模式的扫描。标记明显缺陷、硬编码
  密钥、缺失的空值检查、SQL/命令注入模式、损坏的错误
  处理。不进行跨文件分析。适用于影响范围窄的 PR。
- **`--standard`**（默认，约 10 分钟）：逐文件分析：改动路径上的正确性、特定语言陷阱（参见下方检查清单）、状态处理、改动行为的测试覆盖，以及改动文件内的调用图。除非用户另有说明，否则作为所有 PR 的默认选项。
- **`--deep`**（约 25 分钟）：跨文件分析，包括完整导入图和
  调用链追踪。可发现只有在跨模块边界追踪数据时才会出现的语义缺陷。适用于认证改动、支付流程、数据
  迁移和公共 API 改动。

在每份审查输出顶部说明深度级别。

## Agent 团队审查（仅 `--deep`）

对于认证改动、支付流程、数据迁移或公共 API 改动的 `--deep` 审查，请作为独立通道执行：

- **变更映射员：**总结变更内容以及受影响的系统。
- **运行时评审员：**寻找执行失败、状态漂移、竞态条件、错误路径和部署前置条件。
- **安全评审员：**审查认证、密钥、权限、注入、SSRF、支付安全、钱包流程和数据暴露。
- **产品评审员：**检查功能真实性、Suede 定位、用户可见行为、空状态/错误状态和发布声明。
- **测试评审员：**将声明映射到测试、截图、模拟器运行、构建和线上/API 检查。

先收集共识。如果在修复周期后仍存在高严重性问题，请将状态保持为 `hold`，并说明最小的下一项检查或补丁。

## 全仓库与历史检查（`--deep`）

改动文件的导入图只是最低要求。会发布的缺陷隐藏在差异之外。在 `--deep` 时，扩展检查范围，超出直接调用方：

- **反向依赖扫描：**在整个仓库中查找每个已变更函数、类型、路由或常量的所有调用方（在全仓库搜索符号，而不只是搜索改动文件的导入）。只有每个调用点都保持一致时，签名、返回结构或可空性的变更才是安全的——列出你检查过的站点。
- **共享假设检查：**对于已变更的架构、环境变量、默认值或不变量，查找其他假设旧值的位置——例如在两个服务中读取的配置、客户端中镜像的默认值、测试中重复的魔法值。这些会悄然发生漂移。
- **已修改行的历史：**对改动区域执行 `git log -L` 或 `git blame`。如果这个区域之前曾被修复，重新引入旧结构的改动就是回归——引用先前的提交。如果它反复变动，请将其标记为脆弱区域。
- **同类模式一致性：**查找最近的现有类比——其他路由处理程序、其他迁移——并确认该变更遵循既定模式。一个跳过了其他四个处理程序所使用的共享认证包装器的独立处理程序，即使“能运行”，也是 P1。

说明你追踪了什么。没有命名任何符号的全仓库声明不构成证据。

## 可观测性增量

检查任何新的路由处理程序、API 端点、后台任务、cron、队列消费者或服务函数：

- **被吞掉的错误：** 捕获但未记录日志或未进行 Sentry 捕获的 `try/catch` 块。标记 `catch (e) {}` 和 `catch (e) { console.error(e) }` — 仅使用 `console.error` 的已捕获错误在生产环境中不可见。对于意外错误，要求使用 `Sentry.captureException(e)` 或等效方式。
- **黑暗代码路径：** 没有入口日志且没有失败日志的新路由处理程序、API 函数或任务。如果该路径不产生任何信号，首次发现失败将来自用户报告。
- **缺失的错误边界：** 未包裹在错误边界中的新 React 子树；未将错误暴露给监控层的新服务器函数。
- **未埋点的慢路径：** 没有耗时日志或追踪 span 的新 DB 查询、外部 API 调用、AI 模型调用或文件 I/O。这些路径将最先使值班人员收到告警。
- **孤立的分析事件：** 旧代码中触发、但在变更后不再触发的功能标志或分析事件。仪表板中的指标下降看起来会像产品回归。
- **静默的后台任务：** 完成时未记录已处理项目数量、耗时或失败原因的 cron 或队列消费者。静默任务在完全停止运行之前都无法被监控。

## 部署安全门禁

在每次审查结束时自动运行此项。没有例外。它回答一个问题：**现在部署是否安全？**

对每个维度评级。每项为通过 / 有条件通过 / 阻断：

- **破坏性变更**：此变更是否在没有版本化迁移或向后兼容兜底的情况下，修改了任何公开 API 签名、数据库 schema、配置键或接口契约？如果是且没有迁移路径，建议阻断。
- **回滚安全性**：`git revert` 能否完全撤销此项变更？危险信号包括：schema 迁移、不可逆的外部 API 调用（邮件已发送、付款已扣款、数据已永久删除）、S3/存储变更、消息队列发布。如果回滚需要手动修复数据，建议阻断。
- **影响范围**：此代码路径服务于多少比例的用户或请求？明确说明：`~0%`（新功能，已加标志）、`~partial`（特定流程）、`~100%`（共享中间件、认证、热路径中的 DB 查询）。影响范围越大，部署前需要的证据越多。
- **环境就绪性**：所有必需的环境变量、密钥、功能标志和配置值是否已部署到生产环境？如果生产环境中尚不存在必需的环境变量，建议阻断。
- **依赖变更**：新的或更新的包是否固定到精确版本、来自可信来源且不存在 CVE？如果新依赖存在已知 CVE，或在生产环境中未固定版本，建议阻断。
- **数据变更**：这是否以无法仅通过 revert 撤销的方式写入、更新或删除生产数据？如果是且没有经过测试的恢复路径，建议阻断。
- **安全性增量**：此变更是改善、保持中立，还是削弱安全态势？如果它在没有缓解措施的情况下引入新的攻击面，建议阻断。
- **自动化覆盖率**：`.github/workflows/`（或等效 CI）是否存在，并覆盖了变更的范围（构建、类型、测试）？`main` 上是否强制执行必需的状态检查？如果变更范围没有自动化门禁且仓库连接生产环境，建议阻断。

输出区块 — 每次审查结尾必须包含：

```text
DEPLOY SAFETY
Breaking changes: pass | conditional | block — [evidence]
Rollback safety: pass | conditional | block — [evidence or red flag]
Blast radius: ~X% — [which path or user segment]
Environment readiness: pass | conditional | block — [missing vars if any]
Dependency changes: pass | conditional | block — [new deps and CVE status]
Data mutations: pass | conditional | block — [irreversible operations if any]
Security delta: improved | neutral | block — [surface changed]
Verdict: SAFE TO DEPLOY | DEPLOY WITH CONDITIONS | DO NOT DEPLOY
Conditions (if any):
```

此技能不输出字母等级。当调用方还需要通道等级时，运行 $suede-code（发现项 + 等级）或 $suede-code-grader（仅等级）——这两者包含规范的 Instant-F 触发条件、等级上限以及 A-F 等级量表。此处发现的 Instant-F 模式（硬编码密钥、注入、认证绕过、未经验证的支付 webhook、无回滚方案的破坏性迁移、明文敏感数据）均为 P0 发现项，并将 Ship Gate 设为 `hold`。

## 提交脏污评分

每次审查时自动运行。扫描原始 diff，查找绝不应进入 git 历史的内容。即使“这只是一个分支”也不例外——脏提交会扩散。

**必须执行，不要目测。** 此技能的 `scripts/commit-dirt-scan.sh` 包含字面量模式集：以目标仓库作为工作目录运行它（`bash <skill-dir>/scripts/commit-dirt-scan.sh main...HEAD`，或使用 `-` 将 diff 管道传入）。它会输出每个类别的判定。它是只读的，并且始终以 0 退出——在报告前，请根据 diff 确认每个命中项。当脚本无法运行时，手动检查每一行新增（`+`）内容是否属于以下七个类别：密钥和凭据 · 调试产物 · 冲突标记 · 意外暂存的构建产物 · WIP 痕迹 · 过大的或二进制 blob · 暴露的内部引用。

**评分：**

```
COMMIT DIRT SCORE
Secrets / credentials:   clean | suspicious | dirty — [pattern found or "none"]
Debug artifacts:         clean | suspicious | dirty — [symbol or line or "none"]
Conflict markers:        clean | dirty — ["none" or file:line]
Accidentally staged:     clean | dirty — [path or "none"]
WIP breadcrumbs:         clean | suspicious | dirty — [marker or "none"]
Oversized / binary:      clean | dirty — [file and size or "none"]
Exposed internals:       clean | suspicious | dirty — [pattern or "none"]
Overall dirt rating:     CLEAN | SUSPICIOUS | DIRTY
```

- **CLEAN**：所有维度均无命中。
- **SUSPICIOUS**：低置信度命中，可能是误报（例如测试固件、文档中的示例值）。指出它；由审查者确认。
- **DIRTY**：高置信度命中，必须在合并前移除。在 Findings 部分将其作为 P0 升级处理。

总体评级为 `DIRTY` 会自动将 Ship Gate 设为 `hold`。

## 发现项格式

以发现项开头，并按严重程度排序。将重复模式归为一组：“此模式出现在 4 个文件中：[列表]。下方仅说明一次修复方案。”**结构性问题就是审查重点：**当存在设计或结构缺陷时，先单独报告它——将该缺陷所支配代码中的行级发现项标记为待结构问题解决后再处理，不要枚举它们。一个被埋在十二个 P2 琐碎问题下的破损设计，读起来就像十二个小问题。

**P0 / P1**：使用完整代码块：

```
[P0] path/to/file.ts:142
Issue: JWT secret falls back to empty string; any token is valid when SECRET is unset.
Fix: `process.env.JWT_SECRET ?? (() => { throw new Error('JWT_SECRET required') })()`
Verify: set JWT_SECRET="" and curl /api/me — expect 401, currently 200.
OWASP: A02 Cryptographic Failures
Confidence: high
```

**P2 / P3**：每项一行：

```
[P2] components/Feed.tsx:88 — missing key prop on .map() return; use item.id not index. TS will catch post-fix.
[P3] utils/format.ts:12 — magic number 86400; extract as SECONDS_PER_DAY.
```

严重程度：

- **P0：**数据丢失、安全暴露、支付损失、发布损坏，或不应发布的公开行为——同样需要在任何发布步骤前暂停并向用户询问的极高风险发现。
- **P1：**可能的生产回归、认证/权限错误、主要路径损坏、已发布的错误声明，或缺少关键部署要求。
- **P2：**有实际成本的重大边缘情况故障、不完整的状态处理、变更行为的测试缺口，或可维护性问题。
- **P3：**低风险改进、清晰度问题、局部清理，或后续跟进事项。

如果问题无法关联到文件、路由、命令、状态或用户可见行为，请将其标记为开放问题。

## 修复简报

当被要求修复时，将每项已接受的发现转换为面向代理的简报：

- 失败行为及证据；
- 首先检查的确切文件或区域；
- 预期变更；
- 验收标准；
- 验证命令或浏览器/模拟器路径；
- 需要保留的注意事项和进行中的工作。

一次修复一个风险集群。修复后，重新运行相关审查模式，且在证据确认前不得关闭该发现。

### 修复模式

当用户要求应用修复（`--fix` 标志或等效指令）时：

1. 自动应用局部的 P2/P3 修复（单个文件，不涉及行为契约变更）。将每项修复作为独立提交暂存，提交信息中包含发现 ID。
2. 在应用前，将 P0 和 P1 发现作为已确认的修复简报呈现。未经用户明确确认，不得自动应用于生产关键、认证、支付或数据迁移代码。
3. 应用修复后，仅针对已变更的文件重新运行相关审查模式。将原始发现标记为已解决或已升级。
4. 将迭代循环限制为 3 次。如果同一发现经过 3 次修复尝试后仍然存在，将其升级为需要人工决策的设计问题。

各分类的安全基线位于 `references/owasp-baselines.md`。当差异涉及认证、会话、加密、支付、文件上传或任何请求处理边界时，加载该文件。

## Suede 专项检查

在相关时始终检查以下内容：

- 应用、API 路由、原生壳层与服务器代码之间的认证/会话行为；
- 创作者权利、来源、注册表、许可、版税和代理商业声明是否与已实现行为一致；
- 支付、钱包、x402、结账和信用额度流程是否以失败关闭方式处理；
- 公开页面不得虚构指标、定价、合作伙伴声明、推荐语或发布承诺；
- 在作出生产声明前，Vercel/账户/部署假设是否与本地指南一致；
- App Store/iOS 截图、元数据、隐私回答和构建行为是否与实际应用一致；
- 迁移、环境变量、功能标志、定时任务/作业、队列、Webhook 和密钥是否已记录且可部署；
- Web、后端、移动端、公开网站和文档之间的多仓库或多端面契约是否发生漂移。

## 技术债务

将技术债务模式标记为 P3，按文件分组，不阻塞发布。除非 P3 技术债务直接掩盖了
P0/P1 bug，否则不要因 P3 技术债务阻塞发布。将其作为后续事项记录。

### 设计异味基线（--standard 和 --deep）

除仓库文档已有内容外，审查还包含一套固定的十二项异味
可维护性基线（Fowler，_Refactoring_ 第 3 章），位于
`references/smell-baseline.md`。在 `--standard` 和 `--deep` 审查中加载它，并且
仅针对 diff 进行匹配。其约束规则随之适用：已记录的仓库规则覆盖该基线，每项异味发现
都是带标签的判断调用（“可能的 Feature Envy”，默认 P3，最高置信度为 `medium`），并且跳过
工具已经强制执行的任何内容。异味发现归入此技术债务通道——它们绝不会高于正确性发现，
也绝不会单独改变发布门槛。

## 意图合规与范围

能正常工作的代码，如果没有实现其声称的目标，仍然是缺陷。

- **先找到规格说明。** 按以下顺序查找来源规格说明：提交消息和 PR 正文中的 issue
  或 ticket 引用（`#123`、`Closes #45`）；调用方传入的路径；位于 `docs/`、`specs/`
  下，或与分支或功能名称匹配的临时目录中的规格文件。若均不存在，
  请在输出中说明“没有可用的规格说明”，并且仅依据 PR 描述审查意图——绝不能自行编造
  用于审查的需求。
- **声明与 diff：** 重述该变更声称实现的内容——PR 标题、描述、关联 issue、提交主题——
  并确认 diff 实现了它。将每项验收标准映射到代码路径或测试。声称的行为没有相应变更，
  即为 P1 事实缺口。
- **范围蔓延：** 标记超出其声明范围的变更——搭载在 bugfix 中的无关重构、与功能捆绑的
  依赖升级、掩盖真实 diff 的全局格式化。指出无关的变更簇，并建议拆分。
- **审查工作量信号：** 说明 diff 大小（文件数 / 净行数）以及工作量判断——微小 / 适中 /
  较重 / 过大而无法安全审查。单个 PR 混合认证、支付和迁移时，应在能够安全判断之前先拆分。

## 变更导览（多文件 PR）

对于 PR 摘要或任何跨越四个或更多文件的审查，先给出导览，以便读者在查看发现之前了解整体形态：

- **逐文件表格：** 文件 → 一行说明变更内容 → 风险通道。将生成文件或琐碎文件合并为一行。
- **必要时提供流程图：** 当变更跨越三个或更多边界移动数据，或者修改异步、认证或支付路径时，
  输出 mermaid `sequenceDiagram`（请求 → 处理程序 → 服务 → 数据）或 `flowchart`。对于局部编辑则跳过——
  单文件变更的图表只是噪音。

导览用于帮助理解；它绝不替代发现，并且应位于 Findings 区块上方。

## 精度检查（输出前）

误报是审查者被静音的原因。在输出前自行检查草稿中的发现：

- **证据测试：** 每项发现都必须关联到文件:行号、复现步骤或调用追踪，以及明确的修复方案。无法满足的则删除。
- **已处理测试：** 删除格式化工具、类型检查器、已配置的 linter 或已文档化的项目规则已经覆盖的问题——不要将某个门禁的职责作为人工发现重复报告。
- **置信度门槛：** 将每项发现标记为高 / 中 / 低。**高** = 已复现、已跨调用图追踪，或关联到指定的失败输入或命令；**中** = 从代码中读出，但未执行验证；**低** = 模式看起来有问题，但没有输入、调用路径或运行时状态能够证明它。  
  置信度是独立于严重程度的维度——低置信度的安全疑虑仍应保留其 P 级别并附带标签。将低置信度的风格观察合并为一条“细节问题”；绝不能让它们排在真实的 P 级别发现之前。
- **净信号测试：** 如果某项发现不会改变发布决策，也不值得人工审查者留下评论，就删掉它。数量不是产品。

## 红旗——停止

- “CI 是绿的，浏览一下检查清单”——从未覆盖本次变更的绿色 CI 不能证明任何事。
- “PR 描述已经解释了”——审查 diff，而不是关于 diff 的说明。
- “diff 很小，跳过门禁”——每次审查都必须运行 Deploy Safety Gate 和 Commit Dirt Score，没有例外。
- “为了安全起见，全部标记出来”——数量就是噪音；运行 Precision Pass，删掉不会影响发布决策的内容。
- “这是我写的代码，快速自检就够了”——完全切换到审查模式，寻找你的实现可能遗漏的问题。

## 输出格式

对于审查：

```text
发现
部署安全性
提交脏度评分
开放问题
已检查的验证项
发布门禁
```

如无发现，请明确说明，并指出任何残余风险或未运行的检查。

对于 PR 摘要：

```text
摘要
变更映射
风险映射
验证
发布门禁
```

发布门禁始终是审查输出的最后一行：

```text
发布门禁：暂缓 | 附带注意事项发布 | 发布
原因：[一句话，注明阻塞性发现 ID 或已命名的注意事项]
```

- `hold`：仍存在阻塞项或高风险未知因素。
- `ship-with-caveats`：不存在阻塞项，但存在已命名的非关键注意事项。
- `ship`：不存在已知阻塞项，且必需验证已通过。

## 边界

- 保留用户和其他代理的 WIP。不要暂存、还原或重写无关文件；仅在使用 `--fix` 或收到明确指令时应用修复。
- 绝不引入仓库未使用的工具，也绝不报告你实际上未运行的门禁、测试、截图或实时回读——请在 Verification 中明确说明。
- 不要根据沉默推断规则：未受项目规则、格式化工具或实际成本约束的风格选择，不构成发现。
- 仅输出发现和发布门禁建议。此 skill 不分配字母等级或赛道评分——那属于 suede-code 和 suede-code-grader。

## 路由

- 一次同时给出发现和字母等级 → **suede-code**
- 仅给出等级，不含发现 → **suede-code-grader**
- 已修复发现；让 CI 在合并时阻止回归 → **suede-ci-gate**
- diff 涉及 LLM、RAG 或代理表面 → **suede-ai-eval**
- 修复需要协调并行赛道 → **suede-agent-teams**
