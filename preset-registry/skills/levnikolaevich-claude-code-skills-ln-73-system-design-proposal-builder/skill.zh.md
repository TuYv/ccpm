# 系统设计方案构建器

**目标：** 创建一个适度且有证据支撑的目标系统设计，将需求转化为明确的边界、契约、数据流、故障行为、运维方式和权衡。只修改已批准的设计文档；不要实现、审计或批准交付内容。

**执行契约：** 将下面按顺序排列的复选框工作流视为本技能的完成定义。将每个复选框先标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用证明其条件触发器不存在的证据将其解决为 `CLEARED`，或标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。
返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，将本技能的判定、决策和批准规则应用于每个 `UNPROVEN`，并在开头添加 **清单：X/Y 已完成**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步行动**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 回退方案 |
|---|---|---|
| 需求和约束 | 已批准的需求、基线、决策以及利益相关者的直接输入 | 标记实质性缺口，并提出最少量的决策问题 |
| 当前实现和约定 | 仓库搜索、清单文件、入口点和架构工件 | 仅当用户或仓库明确表明当前为全新项目时，才将其视为 greenfield；否则将当前状态标记为 `UNKNOWN`，并在该缺口可能改变边界、兼容性或迁移方案时返回 `REVISE` 或 `BLOCKED` |
| 外部能力和限制 | 最新的官方文档和规范 | 将相关声明标记为 `UNVERIFIED`；避免做出依赖供应商的承诺 |
| 估算 | 基于有来源的工作负载假设进行可复现的算术计算 | 使用范围和敏感性分析；绝不要将估算呈现为测量结果 |
| 文档修改 | 对已批准的目标设计文档进行最小化补丁修改 | 如果范围或路径不安全，则返回 `BLOCKED` |

将模式视为候选解决方案，而非目标。仅当需求、故障模式、所有权边界或经过测量的时间范围能够抵消基础设施的生命周期成本时，才引入基础设施。

## 工件规则

- 复用清晰的目标设计文档；否则使用 `docs/architecture/target-design.md`。
- 按路径读取可用的基线、当前状态、决策、接口、图表和迁移工件；没有任何一项是强制要求。
- 分别标注事实、假设、估算、提议的决策和未解决的选择。
- 从需求和估算开始，然后是领域和契约、HLD，最后仅处理关键的 LLD。
- 对于会产生重要影响的决策，至少考虑两个可信的替代方案，包括最简单的选项。
- 优先选择可逆的方案以及模块化单体，除非有证据支持建立独立的服务边界。
- 不要悄然更改已接受的决策；记录冲突以及所需的治理行动。

## 检查清单

### 1. 界定设计

- [ ] 明确业务结果、参与者、关键旅程、范围、非目标、决策时间范围和预期读者。
- [ ] 阅读仓库说明，并检查相关架构工件和当前实现。
- [ ] 提取功能需求和可度量的质量驱动因素，同时保留其来源和状态。
- [ ] 识别架构关键的未知项，并仅询问答案会改变目标形态的问题。
- [ ] 当无法负责任地假设所需的业务边界或安全约束时，返回 `BLOCKED`。

### 2. 在选择组件前进行估算

- [ ] 在适用时，估算平均和峰值请求或事件速率、并发量、有效载荷和带宽、存储增长、保留量以及恢复数据量。
- [ ] 展示公式、范围、增长时间跨度和假设；识别可能导致选择反转的变量。
- [ ] 识别最可能首先出现的瓶颈，以及延后扩展机制的明确阈值。
- [ ] 将可用性、延迟、持久性、一致性、安全性、成本和可运维性要求，与实现偏好区分开来。
- [ ] 拒绝推测性的规模设计，并列出有意延后的复杂机制。

### 3. 定义领域、数据和契约

- [ ] 梳理业务能力、领域或模块、所有权、不变量以及允许的依赖方向。
- [ ] 定义权威数据源、架构深度上的数据模型、生命周期、保留策略、一致性和事务边界。
- [ ] 定义公共 API、事件、命令、架构、错误、幂等性、顺序、版本控制和兼容性预期。
- [ ] 根据风险程度，定义信任边界、身份、授权、敏感数据、密钥、滥用控制和审计需求。
- [ ] 除非框架和供应商细节确实构成约束，否则将其置于核心模型之外。

### 4. 构建 HLD 和关键 LLD

- [ ] 描述系统上下文、可部署单元、存储、队列、外部系统、职责以及带标签的数据流。
- [ ] 针对关键用户旅程，追踪成功、过载、依赖项故障、部分故障、重试、超时、降级、恢复和取消等情况。
- [ ] 仅深入分析在正确性、规模、安全性或可逆性方面风险最高的两到三个组件。
- [ ] 定义可观测性、SLI 测量点、健康检查、部署策略、回滚、备份和运维人员操作。
- [ ] 定义所提议拓扑的所有权、对团队的影响、成本驱动因素和运维负担。

### 5. 决策并进行验证

- [ ] 根据需求、估算、故障行为、复杂性、成本、迁移和未来触发条件，对可信的备选方案进行比较。
- [ ] 说明选定和拒绝的选项及其后果、敏感点，以及会重新开启该决策的假设。
- [ ] 识别值得拥有独立精简决策记录的重要决策，但无需为此引入另一套工作流。
- [ ] 定义架构验收证据：契约检查、负载或故障实验、安全验证、恢复证明和可观测性信号。
- [ ] 概述当前状态到目标状态的影响和兼容性需求，但不要扩展为完整的实施计划。

### 6. 编写并报告

- [ ] 编写上下文、驱动因素、估算、领域、契约、HLD、关键 LLD、故障和运维模型、安全性、备选方案、决策、验证、开放问题以及演进触发条件。
- [ ] 保留已批准范围之外的现有内容，并且仅通过文档路径或标题链接共享工件。
- [ ] 重新审阅提案，检查无依据的事实、隐藏的决策、混杂的抽象层次以及缺乏正当理由的机制。
- [ ] 确认未更改任何代码、测试、交付计划、审计结果或外部状态。
- [ ] 仅当设计已充分完成决策、足以进入实施规划时，才使用 `READY`；对于重要但可解决的缺口，使用 `REVISE`；当所需意图、证据、授权或目标位置不可用时，使用 `BLOCKED`。

## 输出契约

```markdown
# System Design Proposal

**Verdict:** READY | REVISE | BLOCKED
**Artifact:** path

## Target design
- Requirements, estimates, boundaries, contracts, HLD, and critical LLD

## Decisions and tradeoffs
| Decision | Selected option | Alternatives | Evidence | Reopen trigger |
|---|---|---|---|---|

## Validation and transition
- Required evidence, compatibility, rollout, rollback, and observability

## Open decisions and residual risks
Only items that can still change implementation planning.
```
