# 系统设计方案构建器

**目标：** 创建一份规模适当、有证据支持的目标系统设计，将需求转化为明确的边界、契约、数据流、故障行为、运维方式和权衡。仅修改已获批准的设计文档；不要实施、审计或批准交付成果。

**执行契约：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，只有当相应操作及所需证据均已完成时，才能将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，对每个未完成项目应用此技能的判定和批准规则，并在内容开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出所有未完成项目。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 需求和约束 | 已批准的需求、基线、决策以及利益相关方的直接输入 | 标记重大缺口，并提出范围最小的决策问题 |
| 当前实现和约定 | 仓库搜索、清单、入口点和架构工件 | 仅当用户或仓库明确表明是全新项目时，才按全新项目处理；否则将当前状态标记为 `UNKNOWN`，并在该缺口可能改变边界、兼容性或迁移方案时返回 `REVISE` 或 `BLOCKED` |
| 外部能力和限制 | 最新的官方文档和规范 | 将相关声明标记为 `UNVERIFIED`；避免作出依赖供应商的承诺 |
| 估算 | 基于有来源的工作负载假设进行可复现的计算 | 使用区间和敏感性分析；绝不将估算表述为测量结果 |
| 文档修改 | 对已批准的目标设计工件进行最小化补丁修改 | 如果范围或路径不安全，则返回 `BLOCKED` |

将模式视为候选解决方案，而非目标。只有当需求、故障模式、所有权边界或经测量的规划周期足以抵消基础设施的生命周期成本时，才引入该基础设施。

## 工件规则

- 复用清晰的目标设计文档；否则使用 `docs/architecture/target-design.md`。
- 按路径读取可用的基线、当前状态、决策、接口、图表和迁移工件；这些工件均不是必需的。
- 分别标注事实、假设、估算、拟议决策和未解决的选择。
- 从需求和估算开始，然后处理领域和契约、HLD，并且仅处理关键的 LLD。
- 对重大决策至少考虑两个可信的替代方案，包括最简单的方案。
- 优先选择可逆方案和模块化单体架构，除非有证据证明独立服务边界是合理的。
- 不要擅自更改已接受的决策；记录冲突以及所需的治理操作。

## 检查清单

### 1. 确定设计框架

- [ ] 明确业务成果、参与者、关键旅程、范围、非目标、决策周期和目标读者。
- [ ] 阅读仓库说明，并检查相关架构工件和当前实现。
- [ ] 提取功能需求和可衡量的质量驱动因素，同时保留其来源和状态。
- [ ] 识别对架构至关重要的未知事项，并且只提出答案会改变目标形态的问题。
- [ ] 当无法负责任地假定必需的业务边界或安全约束时，返回 `BLOCKED`。

### 2. 在选择组件之前进行估算

- [ ] 在相关情况下，估算平均及峰值请求或事件速率、并发量、载荷与带宽、存储增长、保留期限和恢复数据量。
- [ ] 展示公式、范围、增长周期和假设；识别可能推翻所选方案的变量。
- [ ] 识别最可能最先出现的瓶颈，并为延后采用的扩展机制设定明确阈值。
- [ ] 将可用性、延迟、持久性、一致性、安全性、成本和可运维性需求与实现偏好区分开来。
- [ ] 拒绝基于臆测的规模设计，并列出有意延后采用的复杂机制。

### 3. 定义领域、数据和契约

- [ ] 梳理业务能力、领域或模块、所有权、不变量以及允许的依赖方向。
- [ ] 定义记录系统、架构深度的数据模型、生命周期、保留期限、一致性和事务边界。
- [ ] 定义公共 API、事件、命令、模式、错误、幂等性、顺序性、版本控制和兼容性预期。
- [ ] 定义与风险相称的信任边界、身份、授权、敏感数据、密钥、滥用防护和审计需求。
- [ ] 除非框架和供应商细节属于真正的约束，否则应将其排除在核心模型之外。

### 4. 构建 HLD 和关键 LLD

- [ ] 描述系统上下文、可部署单元、存储、队列、外部系统、职责以及带标签的数据流。
- [ ] 针对关键流程，追踪成功、过载、依赖项故障、部分故障、重试、超时、降级、恢复和取消等场景。
- [ ] 仅深入分析在正确性、规模、安全性或可逆性方面风险最高的两到三个组件。
- [ ] 定义可观测性、SLI 测量点、健康状况、部署策略、回滚、备份和运维人员操作。
- [ ] 定义拟议拓扑的所有权、团队影响、成本驱动因素和运维负担。

### 5. 决策与验证

- [ ] 根据需求、估算、故障行为、复杂性、成本、迁移和未来触发条件比较可信的备选方案。
- [ ] 说明选中和否决的方案及其后果、敏感点，以及会促使重新审议决策的假设。
- [ ] 识别值得单独建立精简决策记录的重大决策，而无需启动另一套工作流。
- [ ] 定义架构验收证据：契约检查、负载或故障实验、安全验证、恢复证明和可观测性信号。
- [ ] 概述从当前状态到目标状态的影响和兼容性需求，但不扩展为完整的实施计划。

### 6. 编写与报告

- [ ] 编写上下文、驱动因素、估算、领域、契约、HLD、关键 LLD、故障与运维模型、安全性、备选方案、决策、验证、开放问题和演进触发条件。
- [ ] 保留已批准范围之外的现有内容，并且仅通过文档路径或标题链接共享制品。
- [ ] 重新审阅提案，检查缺乏依据的事实、隐含决策、抽象层次混杂和缺乏正当理由的机制。
- [ ] 确认没有代码、测试、交付计划、审计结果或外部状态发生变更。
- [ ] 仅当设计在决策层面足够完整、可以进行实施规划时才使用 `READY`；存在实质性但可解决的缺口时使用 `REVISE`；无法获得所需意图、证据、权限或目标位置时使用 `BLOCKED`。

## 输出约定

```markdown
# System Design Proposal

**Verdict:** READY | REVISE | BLOCKED
**Artifact:** path

## Target design
- Requirements, estimates, boundaries, contracts, HLD, and critical LLD

## Decisions and tradeoffs
| Decision | Selected option | Alternatives | Evidence | Reopen trigger |
|---|---|---|---|---|

## Validation and transition
- Required evidence, compatibility, rollout, rollback, and observability

## Open decisions and residual risks
Only items that can still change implementation planning.
```
