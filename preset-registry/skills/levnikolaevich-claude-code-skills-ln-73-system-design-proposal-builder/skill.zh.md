# 系统设计提案构建器

**目标：** 创建一份与风险相称、有证据支持的目标系统设计，将需求转化为明确的边界、契约、数据流、故障行为、运维方式和权衡。仅修改已批准的设计文档；不得实施、审计或批准交付成果。

**执行契约：** 按顺序排列的复选框即完成定义。在内部将每一项标记为 `PENDING`、有具体证据的 `PROVEN`、有证据表明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具故障均不能作为证据。完成每个章节后重新核对各项。返回结果前，处理所有 `PENDING`，并且只统计 `PROVEN` 和 `CLEARED`；对每个缺口应用该技能的结论和审批规则。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且影响重大的选择或必需的外部审批提问。根据实质性风险调整深度，不得暗中跳过检查。保留依赖关系和安全性顺序；除此之外，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 需求和约束 | 已批准的需求、基线、决策和直接的利益相关者输入 | 标记重大缺口，并提出最小范围的决策问题 |
| 当前实现和约定 | 仓库搜索、清单、入口点和架构工件 | 仅当用户或仓库明确表明是绿地项目时，才按绿地项目处理；否则将当前状态标记为 `UNKNOWN`，且当该缺口可能改变边界、兼容性或迁移方案时，返回 `REVISE` 或 `BLOCKED` |
| 外部能力和限制 | 最新的官方文档和规范 | 将相关声明标记为 `UNVERIFIED`；避免作出依赖供应商的承诺 |
| 估算 | 基于有来源的工作负载假设进行可复现的算术计算 | 使用范围和敏感性分析；绝不将估算表述为测量结果 |
| 文档变更 | 对已批准的目标设计工件进行最小化补丁修改 | 如果范围或路径不安全，则返回 `BLOCKED` |

将模式视为候选解决方案，而不是目标。仅当需求、故障模式、所有权边界或已测量的时间跨度足以抵消基础设施的全生命周期成本时，才引入基础设施。

## 工件规则

- 复用清晰的目标设计文档；否则使用 `docs/architecture/target-design.md`。
- 按路径读取可用的基线、当前状态、决策、接口、图表和迁移工件；这些工件均非强制要求。
- 分别标注事实、假设、估算、提议的决策和尚未解决的选择。
- 对影响重大的决策比较可信的替代方案，包括最简单的可行方案；当约束只允许一种方案时，记录其原因，而不是虚构另一种方案。
- 优先选择可逆决策，以及符合系统需求的最简单拓扑。对于新应用，在采用独立服务之前先考虑模块化单体；不要将这种形态强加于库、插件或已有拓扑。
- 不得暗中更改已接受的决策；应记录冲突以及所需的治理操作。

## 检查清单

### 1. 明确设计框架

- [ ] 在编辑前明确业务结果、参与者、用户旅程、范围、非目标、时间跨度、读者、语言以及已批准的规范目标位置。
- [ ] 阅读仓库说明，并检查相关架构工件和当前实现。
- [ ] 提取功能需求和可衡量的质量驱动因素，保留其来源和状态。
- [ ] 识别架构关键的未知事项，只提出答案会改变目标形态的问题。
- [ ] 当无法负责任地假设必需的业务边界或安全约束时，返回 `BLOCKED`。

### 2. 在选择组件前进行估算

- [ ] 在适用时估算平均和峰值请求或事件速率、并发量、负载和带宽、存储增长、保留量以及恢复数据量。
- [ ] 展示公式、范围、增长时间跨度和假设；识别可能导致选择反转的变量。
- [ ] 识别可能首先出现的瓶颈，并明确延后扩展机制的阈值。
- [ ] 将可用性、延迟、持久性、一致性、安全性、成本和可运维性要求与实现偏好区分开。
- [ ] 拒绝推测性扩展，并列出有意延后的复杂机制。

### 3. 定义领域、数据和契约

- [ ] 映射业务能力、领域或模块、所有权、不变量以及允许的依赖方向。
- [ ] 定义权威数据源、架构深度的数据模型、生命周期、保留策略、一致性和事务边界。
- [ ] 定义公共 API、事件、命令、架构、错误、幂等性、顺序、版本控制和兼容性预期。
- [ ] 根据风险程度定义信任边界、身份、授权、敏感数据、机密、滥用控制和审计需求。
- [ ] 除非框架和供应商细节是真实约束，否则将其置于核心模型之外。

### 4. 构建 HLD 和关键 LLD

- [ ] 描述系统上下文、可部署单元、存储、队列、外部系统、职责以及带标签的数据流。
- [ ] 针对关键用户旅程追踪成功、过载、依赖项故障、部分故障、重试、超时、降级、恢复和取消。
- [ ] 仅针对其正确性、规模、安全性或可逆性风险足以 warrant 实现级细节的组件进行深入分析。
- [ ] 定义可观测性、SLI 测量点、健康状态、部署策略、回滚、备份和运维人员操作。
- [ ] 为提议的拓扑定义所有权、团队影响、成本驱动因素和运维负担。

### 5. 决策并验证

- [ ] 根据需求、估算、故障行为、复杂性、成本、迁移和未来触发条件比较可信的替代方案。
- [ ] 说明已选择和已拒绝的选项及其后果、敏感点，以及会重新开启决策的假设。
- [ ] 识别值得拥有独立精简决策记录的重要决策，而无需启动另一套工作流。
- [ ] 为每个重要驱动因素定义适当的架构验收证据：契约检查、负载/故障实验、安全验证、恢复证明或可观测性信号。明确前置条件和通过标准；不要在设计期间执行这些验证。
- [ ] 概述从当前状态到目标状态的影响和兼容性需求，但不要扩展为完整的实施计划。

### 6. 编写和报告

- [ ] 编写背景、驱动因素、估算、领域、契约、HLD、关键 LLD、故障与运维模型、安全性、备选方案、决策、验证、开放问题和演进触发条件。
- [ ] 保留已批准范围之外的现有内容，并且仅按文档路径或标题链接共享工件。
- [ ] 重新阅读提案，检查无依据的事实、隐含决策、混合抽象以及缺乏正当性的机制。
- [ ] 仅当设计在决策上足以完整地进行实施规划时使用 `READY`；对存在重大但可解决缺口的情况使用 `REVISE`；当必需的意图、证据、权限或目标位置不可用时使用 `BLOCKED`。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖、矛盾、范围、结论以及适用的清理工作。修正报告或已授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出契约

按用户的语言并遵循以下顺序报告；保留全部五个字段，并且每项事实仅陈述一次。较小的结果可每个字段使用一行；省略空表格，且不要复制已链接的工件：

1. **结果：** 技能特定的结论和有依据的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重大假设。
3. **证据：** 下列技能特定字段；区分事实、推断和未经验证的主张。链接工件；适用时使用表格。
4. **验证：** 检查/结果、不可用证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项的原因、结果影响和确切的下一步行动；剩余风险和所需决策。

**技能特定证据：** 工件路径；需求、估算、边界、契约、HLD/关键 LLD、已选决策、备选方案、证据和重新开启触发条件。总结验证/过渡需求、兼容性、发布、回滚、可观测性，以及仅影响实施规划的未解决选择。
