# 产品需求文档 (PRD)

产品需求文档是用于传达构建内容及其原因的主要规格说明文档。它通过提供明确的需求、成功标准和范围边界，弥合问题理解与工程实现之间的差距。一份优秀的 PRD 能够让工程团队构建正确的产品，同时在实现细节上保持灵活性。

## 适用场景

- 在问题和解决方案达成一致后、工程工作开始前
- 在交接时明确功能、史诗级需求或产品计划
- 多个团队需要协调完成一项共同交付物时
- 利益相关者需要在投入资源前审批范围时
- 作为开发和 QA 期间的参考文档

## 不适用场景

- 问题仍未明确或存在争议 -> 首先使用 `define-problem-statement`；PRD 假定问题已经达成共识
- 只需要一页纸的方案简介来推动利益相关者就某种方法达成一致 -> 使用 `develop-solution-brief`；PRD 应在达成该共识后编写
- 只需要将工作拆分为一个 sprint 中的任务单 -> 使用 `deliver-user-stories`
- 正在记录技术或架构决策 -> 使用 `develop-adr`

## 说明

当被要求创建 PRD 时，请遵循以下步骤：

1. **总结问题**
   首先简要回顾要解决的问题。如果有问题陈述，请链接到该问题陈述。确保读者在深入了解要构建的*内容*之前，先理解这项工作*为何*重要。

2. **定义目标和成功指标**
   阐明成功的标准。包括具有基线和目标值的具体、可衡量指标。这些指标应直接关联到要解决的问题。

3. **概述解决方案**
   从高层次描述拟议的解决方案。重点关注面向用户的功能和关键能力。提供足够的细节，使利益相关者能够评估该方案，但不要过度规定实现方式。

4. **详细说明功能需求**
   分解系统必须完成的工作。使用用户故事或需求陈述。每项需求都应当可测试——应有人能够验证该需求是否满足。

5. **将 AI 行为与证据关联**（*仅当功能的输出来自模型时*）
   对于确定性功能，完全跳过此步骤。当模型生成输出时，其行为会因运行而异，因此“它能正常工作”这一说法需要附带证据。列出本次发布所要求的行为，并针对每项行为说明将如何证明其成立，以及达到什么阈值。拒答和拒绝回答应各自占据独立的行：模型对这两者都没有可靠的默认行为，因此功能在*不应回答*时的表现是一项需求，而不是实现细节。对于多步骤功能，应分别评估每个组件，因为端到端通过率会掩盖具体失败的步骤。说明测试用例集规模的确定方法，而不要将借用的数字当作方法。

6. **定义范围边界**
   明确说明哪些内容属于范围之内、哪些超出范围，以及哪些推迟到未来迭代。清晰的范围能够防止范围蔓延，并建立现实的预期。

7. **说明技术考量**
   记录任何技术约束、架构决策或集成要求。不要设计系统，但要提出工程团队需要了解的考量。

8. **编写 Agent 执行契约** *(仅当执行者将在没有作者上下文的情况下实现此功能时)*
   如果实现人员已参与讨论，则完全跳过此步骤。编码 Agent、外部承包商或接手此工作的团队无法推断你已经掌握的信息，因此必须明确说明：哪些来源具有权威性，以及当两个来源存在冲突时以哪个为准；哪些内容不得触碰以及原因；每个 FR-n 如何验证以及由谁验证；以及在什么情况下执行者必须停止并升级，而不是自行决定。为每个升级指定负责人；没有收件人的升级就会变成猜测。没有验证方式的需求还没有准备好交接，因为没有任何标准可以区分“已完成”和“执行者认为已完成”。

9. **识别依赖项和风险**
   列出可能影响交付的外部依赖项、假设和风险。在适用的情况下，包括缓解策略。

10. **提出时间线和里程碑**
    概述关键阶段和检查点。这有助于利益相关者了解交付计划，而无需过早承诺具体日期。

## 项目记忆契约

仅当 `.claude/pm-skills.local.md` 存在时才启用。没有该文件时，完全忽略本节，并严格按照上述说明执行。

- **读取：**读取 `active_initiative`，以及任何记录用户画像或研究发现的 `interpretation` 工件。使用这些内容，而不是询问已经生成的上下文。如果不存在任何内容，则按正常方式提问，绝不要臆造用户画像来填补空白。
- **写入：**将 PRD 作为 `decision` 工件写入，并将其已确定的范围边界和成功指标写入 `## Decisions` 部分。
- **处理方式：**写入前先提出该条目并等待确认，除非设置了 `memory_auto_append: true`；在这种情况下追加内容，并回显所写入的内容。
- **写入纪律：**写入前立即重新读取文件，绝不要使用生成提案时所依据的副本。如果文件在此期间发生变化，则将你的条目合并到当前状态中并重新提出，而不是覆盖文件；只添加你自己的条目，其他每个字段和部分都必须逐字节保持不变。运行时没有任何机制强制执行这一点，而且该文件被 gitignore 忽略，因此粗心地写入整个文件会丢失另一个会话的工作，且无法恢复。

这是演示循环的读取端：当 `discover-interview-synthesis` 已经记录了用户画像时，不要再次要求用户提供这些信息。

## 输出格式

使用 `references/TEMPLATE.md` 中的模板来组织输出。一份完整的 PRD 应填写模板中的每个部分：Overview；Goals & Success Metrics；User Stories；Scope；Solution Design；Technical Considerations；Dependencies & Risks；Timeline & Milestones；Open Questions；当存在支持材料时还包括 Appendix；当功能的输出来自模型时还包括 AI Behavior and Evaluation；以及当执行者将在没有作者上下文的情况下实现该功能时包括 Agent Execution Contract。

最后三项是有意设置为条件性的。PRD 如果省略了其功能不需要的章节，仍然是完整的；而包含空章节的 PRD 则不是。

## 质量检查清单

完成最终定稿前，请确认：

- [ ] 问题和“为什么是现在”已清晰阐述
- [ ] 成功指标具体且可衡量
- [ ] 范围边界明确（包含/不包含/未来）
- [ ] 需求可测试且无歧义
- [ ] 已提出技术方面的考虑，但未过度指定实现细节
- [ ] 依赖关系和风险均已记录，并注明负责人
- [ ] 文档可在 15 分钟内读完
- [ ] 如果输出来自模型：每项行为需求都有对应的评估和阈值，且拒答和弃答也包含在其中
- [ ] 如果评估集已确定规模：每个切片的下限都展示了得出该下限的推理过程，并指出该切片必须捕获的最小失败率。仅给出一个数字不算推导；无失败的运行结果应作为边界报告，而不是测量值
- [ ] 如果执行者将在没有作者上下文的情况下实现该文档：每个 FR-n 都有验证方式和验证者，并且每个升级条件都注明负责人
