# 产品需求文档 (PRD)

产品需求文档是用于传达要构建什么以及为什么构建的主要规范性文档。它通过提供清晰的需求、成功标准和范围边界，弥合了问题理解与工程实现之间的鸿沟。一份优秀的 PRD 能够让工程团队构建正确的产品，同时在实现细节上保持灵活性。

## 适用时机

- 在问题与解决方案达成一致之后、工程工作开始之前
- 为交接而明确功能、史诗或产品计划时
- 多个团队需要就共同交付成果进行协作时
- 利益相关者需要在投入资源前审批范围时
- 作为开发和 QA 期间的参考文档

## 不适用时机

- 问题仍未明确或存在争议 -> 首先使用 `define-problem-statement`；PRD 假设问题已经达成共识
- 只需要用一页方案来让利益相关者对某种方法达成一致 -> 使用 `develop-solution-brief`；PRD 应在达成一致之后编写
- 只需要将工作拆分为一个迭代中的工单 -> 使用 `deliver-user-stories`
- 需要记录技术或架构决策 -> 使用 `develop-adr`

## 说明

当被要求创建 PRD 时，请遵循以下步骤：

1. **总结问题**
   首先简要回顾需要解决的问题。如果有问题陈述，请链接到该问题陈述。确保读者在深入了解*要构建什么*之前，先理解这项工作*为什么重要*。

2. **定义目标和成功指标**
   阐明成功的标准。包括具有基线和目标值的具体、可衡量指标。这些指标应直接关联到要解决的问题。

3. **概述解决方案**
   从高层次描述拟议的解决方案。重点关注面向用户的功能和关键能力。提供足够的细节，让利益相关者能够评估该方案，但不要过度规定实现方式。

4. **详细说明功能需求**
   分解系统必须完成的工作。使用用户故事或需求陈述。每项需求都应当可测试——应有人能够验证它是否满足要求。

5. **将 AI 行为与证据关联** *(仅当功能的输出来自模型时)*
   对于确定性功能，完全跳过此步骤。当模型生成输出时，其行为会因运行而异，因此“它能正常工作”这一说法需要附带证据。明确列出本次发布版本所要求的行为，并针对每项行为说明将如何证明其成立，以及所需达到的阈值。拒答和弃答应各自占一行：模型对这两者都没有可靠的默认行为，因此功能在“不应回答”时的处理方式是一项需求，而不是实现细节。对于包含多个步骤的功能，应分别对每个组成部分进行评分，因为端到端通过率会掩盖具体失败的步骤。说明案例集规模的确定方法，而不是把借用的数字当作方法。

6. **定义范围边界**
   明确说明哪些内容属于范围内、哪些内容不属于范围内，以及哪些内容推迟到未来迭代。清晰的范围能够防止范围蔓延，并设定现实的预期。

7. **说明技术考量**
   记录需要注意的技术约束、架构决策或集成要求。不要设计系统，但要指出工程团队需要了解的考量。

8. **编写代理执行契约** *(仅当执行者将在没有作者上下文的情况下实现此项目时)*
   如果实施人员当时就在场，则完全跳过此步骤。编码代理、外部承包商，或在不了解背景的情况下接手项目的团队，无法推断出你已经掌握的信息，因此需要明确说明：哪些来源具有权威性，以及当两个来源发生冲突时以哪个为准；哪些内容不得改动以及原因；每个 FR-n 如何验证以及由谁验证；以及在什么情况下执行者必须停止并升级处理，而不是自行决策。为每个升级事项指定负责人；没有收件人的升级事项最终会变成猜测。没有验证方式的需求还没准备好交接，因为没有任何依据可以区分“已完成”和“执行者认为已完成”。

9. **识别依赖关系与风险**
   列出可能影响交付的外部依赖、假设和风险。在适用的情况下，加入缓解策略。

10. **提出时间线与里程碑**
    概述关键阶段和检查点。这有助于利益相关者了解交付计划，同时无需过早承诺具体日期。

## 项目记忆契约

仅当 `.claude/pm-skills.local.md` 存在时启用。没有该文件时，完全忽略本节，
并严格按照上述说明执行。

- **读取：**读取 `active_initiative`，以及记录用户画像或研究发现的任何 `interpretation` artifact。使用这些内容，而不是询问已经产出的上下文。如果不存在，则按正常流程提问，绝不要臆造用户画像来填补空白。
- **写入：**将 PRD 写入为 `decision` artifact，并将其已确定的范围边界和成功指标写入 `## Decisions` 部分。
- **操作方式：**写入前先提出该条目并等待确认，除非设置了 `memory_auto_append: true`；在这种情况下，直接追加并说明写入了哪些内容。
- **写入纪律：**写入前立即重新读取文件，绝不要使用生成提案时所依据的副本。如果文件在此期间发生变化，则将你的条目合并到当前状态中，并重新提出，而不是覆盖文件；只添加你自己的条目，其他字段和部分必须逐字节保持不变。运行时没有任何机制强制执行这一点，而且该文件被 gitignore，因此粗心地写入整个文件会丢失另一会话的工作，并且无法恢复。

这是演示循环的读取端：当 `discover-interview-synthesis` 已经记录了用户画像时，不要再要求用户重复提供这些信息。

## 输出格式

使用 `references/TEMPLATE.md` 中的模板来组织输出。完整的 PRD 应填写模板中的每个部分：概述；目标与成功指标；用户故事；范围；解决方案设计；技术考量；依赖关系与风险；时间线与里程碑；待解决问题；当存在支持材料时附录；当功能的输出来自模型时，AI 行为与评估；以及当执行者将在没有作者上下文的情况下实现该项目时，代理执行契约。

最后三项是有条件的，这是有意为之。若某个功能不需要某个章节，则省略该章节的 PRD 是完整的；而包含空章节的 PRD 则不是。

## 质量检查清单

定稿前，请确认：

- [ ] 已清晰阐述问题以及“为什么是现在”
- [ ] 成功指标具体且可衡量
- [ ] 范围边界明确（包含/不包含/未来）
- [ ] 需求可测试且表述无歧义
- [ ] 已提出技术考量，但未规定过多细节
- [ ] 已记录依赖项和风险，并标明负责人
- [ ] 文档可在 15 分钟内读完
- [ ] 如果输出来自模型：每项行为需求都有一个评估和一个阈值，且拒答和弃权也在其中
- [ ] 如果对评估集进行了规模设定：每个切片的下限都说明其承诺覆盖范围以及该切片为何值得获得这一覆盖范围，并且没有将任何切片结果报告为失败率或其上界
- [ ] 如果执行者将在没有作者上下文的情况下实现该文档：每个 FR-n 都有一个验证方式和一个验证者，并且每个升级条件都指明了负责人
