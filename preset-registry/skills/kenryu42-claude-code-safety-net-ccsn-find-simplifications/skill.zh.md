# 查找 CC Safety Net 简化点

本技能将宽泛的“查找可简化之处”请求转化为有证据支持的候选方案，以移除或合并现有的功能表面积。它是一份指导，而不是一张检查清单：沿着代码追查，持续运用判断，并优先选择少数几个证据充分的候选方案，而不是大量依据薄弱的方案。

过度工程化是此仓库文档中明确指出的主要失败模式（参见 `AGENTS.md` 中的 Scope Discipline），因此简化提案天然更容易获得支持——但同样的纪律也适用于提案本身：每个提案都必须指出当前代码所承担的具体成本，而不能只说“这看起来很复杂”。

## 从仓库上下文入手

- 阅读 `AGENTS.md`（Scope Discipline、Style Guide、Knip 规则）、`REVIEW.md`（威胁模型和审查边界）以及 `SECURITY.md`（standard/strict/paranoid 模式契约）。
- 在评判 `src/parser`、`src/analyzer` 或 `src/rules` 中的任何内容之前，先阅读 `docs/residual-risk.md`。已经裁定的绕过类型属于既定决策；用于固定这些类型的固件即使没有其他地方引用，也承担着关键作用。
- 模式契约是仓库的核心边界：standard 模式会阻止可识别的意外破坏，并明确不保证无法绕过；strict/paranoid 模式则采用故障关闭策略。仅为追逐 standard 模式中精心构造的对抗性形式而存在的复杂性，超出了文档规定的契约——`REVIEW.md` 禁止添加这种复杂性，因此任何现有实例都是优先考虑的简化候选项。反之，strict/paranoid 模式中的故障关闭机制属于契约要求，而不是冗余设计。

## 默认视为有意保留

- `src/integrations` 中针对各工具的集成（Claude Code、OpenCode、Codex、Copilot CLI、Cursor、Amp、Pi、Kimi Code、Gemini CLI、OpenClaw、Antigravity、Hermes，……）。每项集成都因真实宿主工具的需要而存在；只有当用户明确表示不再支持该工具时，才建议删除相应集成。但删除某项集成*内部*未使用的钩子或方法仍然是合理的。
- 残余风险注册表组合（`docs/residual-risk-registry.json` + `docs/residual-risk.md`），以及为其各类风险提供支撑的 strict/paranoid 故障关闭固件。
- 仅使用单一运行时依赖项的方针（只有 `zod`）。手工实现的 shell 解析器是产品本身，而不是重复造轮子的坏味道——这是一个安全钩子，并且刻意采用了最小化的供应链。不要建议用 npm 包替换解析器或防护机制；新增依赖项是需要单独提出、由维护者决定的事项，绝不能被视为“低成本”的清理工作。
- 测试中看似具有对抗性的字符串是分析器的输入数据，绝不会被执行。在未检查它们固定了哪项契约或哪类残余风险之前，不要以危险或冗余为由建议删除它们。

## 什么才算强有力的候选方案

强有力的简化方案会移除、合并或降级某些真实存在的内容，并以证据证明当前设计的成本高于其收益：

- 某个内部符号、引擎钩子或 GUI 实现表面积没有生产环境消费者。对于公开导出项、配置、策略开关以及 CLI 或 GUI 功能，必须提供契约或弃用证据；仅凭仓库内部没有使用，无法证明外部用户不依赖它们。
- 测试或注释是唯一的消费者，并且它们所固定的行为既不是模式契约保证，也不是残余风险固件。
- 两种表示方式反映的是同一个事实（例如，某个值既存储在 IR 中，又在分析器中重新派生；或者各工具存在并行代码，而这些代码本可以共享同一条路径，且不会削弱任何工具的执行保障）。请注意，`bun run check` 已经通过 jscpd 检查文本重复——应重点关注它无法发现的结构性重复。
- standard 模式中的解析器或规则逻辑，其唯一依据是某种刻意构造的绕过形式：根据 `REVIEW.md`，这应由 strict/paranoid 模式的故障关闭处理或已记录的残余风险来应对，而不是通过模拟代码来处理。
- 对由同一进程中的可信调用方已经拥有的值进行防御性复制、冻结、重新验证或规范化。这里的信任边界非常明确：来自宿主工具的钩子载荷、用户配置/策略文件以及被分析的命令字符串均不可信，理应进行验证；而在此仓库自身模块之间传递的值通常不需要如此处理。
- 没有消费者的推测性通用设计：只有一个条目的注册表、早于首个真实用户出现的 schema、值被强制固定为常量的字段、没有任何集成会设置的选项。
- 仅为保护未使用 API 而存在的不变量、回退机制或特殊情况测试。
- 简化后的行为可以略有不同，但新行为仍然合理、符合模式契约，并且更容易解释。

仅凭薄弱依据不足以构成候选项：例如，一个拼写错误、一次 `knip` 运行、没有调用点证据支撑的“这看起来很复杂”，或任何一旦移除就会导致标准模式对可识别危险产生假阴性的内容。

## 广泛调研

当用户要求覆盖面时，使用并行子代理。为每个子代理分配一个领域，并要求其提供证据，而不是猜测：

- 解析器和 IR（`src/parser`、`src/ir`）：规范化处理、节点种类、下游完全不读取的字段。
- 分析器和规则（`src/analyzer`、`src/rules`）：规则机制、严重级别传递、超出契约的模拟行为。
- 防护和策略（`src/guards`、`src/policy`）：重复反映同一事实的兜底机制、没有任何地方设置的配置选项。
- 引擎和 CLI（`src/engine`、`src/cli`）：命令、标志、安装/检测流程、输出格式。
- 集成（`src/integrations`、`hooks/`、根目录插件清单）：各工具之间的重复实现、未使用的适配器方法。
- GUI（`src/gui`）：没有交互路径的界面或状态。
- 测试、脚本、构建（`tests/`、`scripts/`）：冗余固件、检查内容已由其他门禁检查的验证脚本。

不要因为找到第一个优质候选项就停止调研，并应从最大的生产代码文件开始——重复的生命周期和防御性机制比零散的未使用符号成本更高。

## 证明或否决每个候选项

在撰写任何内容之前，先对使用方进行分类：

- 生产语料范围：`src/`、`hooks/`、构建/发布时使用的 `scripts/`、根目录插件清单（`kimi.plugin.json`、package.json 中的 `pi`/`bin`/peer-dependency 连接配置），以及被跟踪的 `skills/` 目录。忽略 `dist/`（生成内容）和未跟踪的个人目录（`report/`、`research/`、`artifacts/`、`droid-wiki/`、`TODO.md`、`REDESIGN.md`）。
- 非生产语料范围：`tests/` 和注释。README 和其他文档属于非运行时证据，但对于公共接口，应将其视为契约使用方。
- 模糊语料范围：会测试真实宿主工具连接的 e2e 和 e2e-live 测试——这些测试通常会固定集成契约；请先阅读它们，再进行分类。

首先使用 `rg`：搜索确切的符号、配置键、CLI 标志、规则 ID、工具名称字符串，以及任何线上传输/JSON 字符串（集成通过字符串形式的工具名称进行分派，因此要 grep 字符串，而不只是标识符）。然后阅读调用点。`knip` 很有帮助，但它以 `--production` 模式运行——`/** @internal */` 标签表示其设计用途仅限测试，并不意味着它是死代码；而且动态字符串分派会向它隐藏真实的使用方。

在以下情况下，否决候选项或降低其优先级：

- 存在生产使用方，且移除它属于功能决策，而不是清理。
- 该接口受到模式契约、残余风险类别或 `docs/` 中已记录决策的约束，且新证据不足以推翻已记录的理由。
- 移除后会导致标准模式对合理的意外命令产生假阴性，或削弱严格/偏执模式的失败关闭行为。
- 移除会迫使大范围改动，却没有减少公共接口或必要行为。

## 只报告，不重构

此仓库没有笔记系统，并且由单人维护。交付物是提供给用户的报告，应将最有力的证据放在最前面。对于每个候选项：

- **内容**：要移除、折叠或降级的确切符号/文件，并附上 `file:line` 引用。
- **证据**：找到的生产环境与测试/文档使用方，以及用于证实不存在其他使用方的搜索。
- **放弃的内容**：如实陈述最有力的反对理由——包括任何行为变更，以及该变更为何仍符合模式契约。
- **影响范围**：将随之发生变化的测试、文档和固件。

不要为了存放调查结果而创建新的文档、目录、依赖项或流程文件——是否引入新的仓库结构应由维护者决定。除非用户要求修复，否则不要在调查期间实施移除；如果用户确实要求修复，请针对每个候选项实施最小变更，保持 `tests/` 与 `src/` 的镜像结构，并对任何行为变更遵循红–绿规则。

## 验证

仅输出调查结果时无需执行检查。实施候选项后，在最后运行一次 `bun run check`（绝不要单独运行其中的各项检查）。如果 knip 随后报告了连带问题，请按照 `AGENTS.md` 的 Knip 章节修复根本原因——取消导出、添加 `/** @internal */` 标记，或精简桶文件；绝不要修改 `ignoreIssues`。
