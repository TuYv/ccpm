# 查找 CC 安全网简化机会

这项技能会将宽泛的“找出可以简化的地方”请求，转化为有证据支持的候选项，从而移除或合并现有的表面复杂度。这是一份指导，而不是检查清单：应遵循代码的实际情况，保持判断力，并优先选择少量证据充分的候选项，而不是大量依据薄弱的候选项。

过度工程化是此仓库已记录的主要失败模式（参见 `AGENTS.md` 中的 Scope Discipline），因此简化提案具有一定的有利条件，但同样的纪律也适用于提案本身：每一项都必须指出当前代码承担的具体成本，而不能只说“看起来很复杂”。

## 从仓库上下文开始

- 阅读 `AGENTS.md`（Scope Discipline、Style Guide、Knip rules）、`REVIEW.md`（威胁模型和审查边界）以及 `SECURITY.md`（standard/strict/paranoid 模式契约）。
- 在判断 `src/core/shell`、`src/gate/analyzer` 或 `src/core/rules` 中的任何内容之前，先阅读 `docs/residual-risk.md`。已经裁定的绕过族属于既定决策；即使没有其他代码引用，固定这些行为的 fixture 仍然是承载契约的关键部分。
- 模式契约是仓库的核心衔接点：standard 模式会阻止可识别的意外破坏，但明确不会做到无法绕过；strict/paranoid 模式则会默认拒绝。仅为应对 standard 模式中精心构造的对抗性形态而存在的复杂性，超出了文档规定的契约范围；`REVIEW.md` 禁止添加这类复杂性，因此任何现有实例都是优先考虑的简化候选项。反过来，strict/paranoid 中的默认拒绝机制属于契约内容，而不是冗余。

## 默认视为有意设计

- `src/hosts` 中按工具划分的集成（Claude Code、OpenCode、Codex、Copilot CLI、Cursor、Amp、Pi、Kimi Code、Gemini CLI、OpenClaw、Antigravity、Hermes，等等）。每个集成都存在，是因为某个真实的宿主工具需要它；只有在用户表示已弃用某个工具的情况下，才应提议删除整个集成。删除其中未使用的 hook 或方法仍然是合理的。
- 残余风险注册表文件对（`docs/residual-risk-registry.json` + `docs/residual-risk.md`），以及支持其中各个风险族的 strict/paranoid 默认拒绝 fixture。
- 零运行时依赖的立场。手写 shell 解析是产品本身，而不是手写实现方面的问题：这是一个刻意保持供应链最小化的安全 hook。不要提议改用 npm 包来替换解析器或防护逻辑；新增依赖属于需要单独提出的维护者决策，绝不是“低成本”的清理工作。
- 测试中的对抗性字符串是分析器的输入数据，不会被执行。在确认它们所固定的契约或残余风险族之前，不要提议因为它们危险或冗余而删除。

## 强候选项的标准

强候选项会移除、合并或降级某个真实存在的东西，并且有证据表明当前设计带来的成本超过了收益：

- 某个内部符号、引擎 hook 或 GUI 实现面没有生产环境消费者。对于公共导出、配置、策略开关以及 CLI 或 GUI 功能，需要有契约或弃用证据；仅凭仓库内部没有使用，无法证明外部用户不依赖它们。
- 测试或注释是唯一的消费者，并且它们固定的行为既不是模式契约保证，也不是残余风险 fixture。
- 两种表示方式镜像存储同一个事实（例如，一个值既存储在 IR 中，又在分析器中重新推导；或者各工具之间存在可以共享同一路径的并行代码，同时不会削弱任何工具的防护）。注意，`bun run check` 已经通过 jscpd 对文本重复进行检查；应关注它无法发现的结构性重复。
- standard 模式下的解析器或规则逻辑，其唯一依据是刻意构造的绕过形态：根据 `REVIEW.md`，这类逻辑应属于 strict/paranoid 的默认拒绝处理或有文档记录的残余风险，而不是模拟代码。
- 对同一进程中由受信任调用方拥有的值进行防御性复制、冻结、再次验证或规范化。此处的信任边界是明确的：来自宿主工具的 hook payload、用户配置/策略文件以及经过分析的命令字符串是不受信任的，应当进行验证；而在此仓库自身模块之间传递的值通常不需要这些处理。
- 没有消费者的推测性通用设计：只有一个条目的注册表、早于第一个真实使用者的 schema、值被强制为常量的字段、没有任何集成设置的选项。
- 仅为保护未使用 API 而存在的不变量、回退逻辑或特殊情况测试。
- 简化后的行为可能会略有不同，但新行为仍然合理，符合模式契约，并且更容易解释。

仅有单薄的候选项是不够的：一个拼写错误、单次 `knip` 运行、“这看起来很复杂”但没有调用点证据，或任何移除后会在标准模式下对可识别危险产生误报的内容，都不能作为依据。

## 广泛调查

当用户要求广度时，使用并行子代理。为每个子代理指定领域，并要求提供证据，而不是猜测：

- 解析器和 IR（`src/core/shell`、`src/core`）：规范化流程、节点类型、下游没有读取的字段。
- 分析器和规则（`src/gate/analyzer`、`src/core/rules`）：规则机制、严重性传递、超出契约范围的模拟行为。
- 防护和策略（`src/gate/guards`、`src/core/policy`）：镜像同一事实的后备机制、没有任何设置项的配置开关。
- 引擎和 CLI（`src/gate`、`src/cli`）：命令、标志、安装/检测流程、输出格式化。
- 集成（`src/hosts`、`hooks/`、根目录插件清单）：按工具重复实现的逻辑、未使用的适配器方法。
- GUI（`src/gui`）：没有交互路径的界面或状态。
- 测试、脚本、构建（`tests/`、`scripts/`）：重复的 fixture、检查另一道门已经验证内容的验证脚本。

不要让第一个合适的候选项终止调查，并从最大的生产文件开始，因为重复的生命周期和防御性机制比零散的未使用符号代价更高。

## 证明或否决每个候选项

在写入报告之前，先对消费者进行分类：

- 生产代码范围：`src/`、`hooks/`、构建/发布时使用的 `scripts/`、根目录插件清单（`kimi.plugin.json`、package.json 中的 `pi`/`bin`/peer-dependency wiring），以及受跟踪的 `skills/` 目录。忽略 `dist/`（生成文件）和未受跟踪的个人目录（`report/`、`research/`、`artifacts/`、`droid-wiki/`、`TODO.md`、`REDESIGN.md`）。
- 非生产代码范围：`tests/` 和注释。README 及其他文档属于非运行时证据，但对于公共接口仍算作契约消费者。
- 模糊代码范围：执行真实宿主工具集成的 e2e 和 e2e-live 测试，这些测试通常会固定集成契约；在分类之前先阅读它们。

优先使用 `rg`：搜索确切的符号、配置键、CLI 标志、规则 id、工具名称字符串以及所有 wire/JSON 字符串（集成通过工具名称字符串进行分发，因此要搜索字符串，而不只是标识符）。`knip` 有帮助，但它以 `--production` 模式运行——`/** @internal */` 标签表示这是有意设计为仅供测试使用，并不意味着死代码；动态字符串分发会使真实消费者无法被它发现。

在以下情况下否决或降低优先级：

- 存在生产消费者，而移除它将成为功能决策，而不是清理工作。
- 该接口受模式契约、剩余风险类别或 `docs/` 中记录的决策约束，且新证据不足以推翻既有理由。
- 移除后会导致标准模式对合理的误操作命令产生误报，或削弱严格/偏执模式的默认拒绝行为。
- 移除会迫使大量改动，却没有减少公共接口或必需行为。

## 报告，而不是重构

此仓库没有笔记系统，且由单人维护。交付物是发送给用户的报告，按证据强度排序。对于每个候选项：

- **内容**：需要移除、合并或降级处理的确切符号/文件，并附上 `file:line` 引用。
- **证据**：找到的生产代码、测试和文档消费者，以及能够证明其不存在的搜索结果。
- **我们放弃的内容**：坦诚陈述最有力的反对理由，包括任何行为变化，以及为什么该变化仍符合模式契约。
- **影响范围**：会因此发生变化的测试、文档和 fixture。

除非用户要求修复，否则不要在调查期间实施移除操作；不要创建新的文档、目录、依赖项或流程文件来存放调查结果，仓库结构的新增位置由维护者决定。当用户要求修复时，针对每个候选项实施最小改动，保持 `tests/` 与 `src/` 镜像对应，并对任何行为变化遵循 Red–Green 规则。

## 验证

仅包含调查结果的调查不需要检查。实施候选项后，在最后运行一次 `bun run check`（绝不要分别运行其中的步骤）。如果 knip 随后报告了连带问题，请根据 `AGENTS.md` 中的 Knip 部分修复根本原因：取消导出、添加 `/** @internal */` 标记，或精简 barrel；绝不要修改 `ignoreIssues`。
