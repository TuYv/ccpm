# 颜色

颜色系统是一组按角色命名，并根据其实际渲染背景进行验证的小型色阶。大多数颜色问题都是系统问题：孤立选取的值、因为看起来合适而借用的令牌、未经任何人测量的一对颜色。

永远不要报告未经测量的对比度数值，也不要估算可以计算出的颜色。颜色是少数能够得出精确答案的界面要素之一，因此请给出精确答案。

对比度要求属于 `better-accessibility`。表面、阴影和图标颜色属于 `better-ui`。

## 与项目的颜色系统保持一致

复用项目的令牌和表示法。为了修正一个值而加入第二种表示方式，会让调色板更难理解。统一的十六进制系统胜过在其中零散使用 `oklch()` 的十六进制系统。

对于新系统，`oklch()` 是最佳默认选择，因为其中的数值表现符合下方所述的色阶规则。在其他情况下，应使用颜色库，以项目自身的表示法生成相同的色阶（[color-formats.md](color-formats.md)）。

## 系统由色阶构成，而不是由颜色构成

使用一个中性色阶、一个强调色色阶，以及产品实际渲染所需的状态色阶。没有任何地方导入的 `warning` 色阶，只是在为零像素增加维护成本。只有当两种颜色必须一眼即可区分时，第二种强调色相才有存在的价值。

## 每个阶梯都有自己的用途

色阶不是供人凭眼睛挑选的渐变。每个阶梯都因某个角色的需要而存在：页面背景、组件悬停、边框、实心填充、正文文本。不要生成没有任何角色使用的阶梯。Tailwind 的 `50`–`950` 和 Radix 的 `1`–`12` 约定都映射到这些角色（[palette-structure.md](palette-structure.md)）。

## 基础色按色相命名，语义色按角色命名

基础色命名一个值（`--blue-500`），绝不直接应用于组件。语义令牌命名一个用途（`--color-text-secondary`），指向某个基础色，并且是组件唯一引用的层级。

正是这一层衔接使主题化成为可能。没有它，深色模式就意味着审查每个使用位置，以弄清哪些使用位置表示“强调色”，哪些只是需要蓝色（[token-naming.md](token-naming.md)）。

## 只在其角色中使用令牌

永远不要因为某个令牌当前的值正合适就借用它。用作分隔线的令牌被用作文本颜色后，在边框变浅时仍能正常工作，但文本也会随之变浅。如果某个角色没有令牌，就添加该令牌。

## 在整个色阶中保持色相

四个属性定义了一个结构良好的色阶：

- 各阶梯应按照*感知*亮度均匀递进，而不是按照格式所称的亮度递进。
- 色相从头到尾保持不变。
- 鲜艳度在色阶中段达到峰值，并在两端下降。
- 浅色端的阶梯应比深色端更密集。

两端都应避免达到纯黑和纯白，因为它们完全无法承载色相。请使用颜色库，而不是凭眼睛调整（[palette-generation.md](palette-generation.md)）。

## 一种颜色，一种含义

在整个界面中让一种颜色只承担一种用途，并将色相差在 `15°` 以内的颜色视为同一种颜色。如果强调色表示可交互，那么静态文本使用该色相会让用户以为某个不可点击的内容可以点击；而将交互元素渲染为中性色也同样具有误导性。颜色从来不是承载含义的唯一方式，这属于 `better-accessibility` 的职责。

## 每个视图恰好填充一个操作

当填充色用于表达主要强调时，应将其分配给一个主要操作，同级操作保持中性。将颜色放在背景上，而不是标签上。填充按钮在远处看也能读作主要操作；中性按钮上的强调色文字则读作链接。

当多个彩色背景表达的是不同状态或类别，而不是彼此竞争的同级操作时，可以使用多个彩色背景。

## 先测量实际渲染的配对，然后报告

应针对前景实际渲染所在的背景进行测量，而不是页面背景。当一组配对未通过时，报告该配对、测量值以及未达到的阈值，然后保持颜色不变。颜色是设计决策。只有在收到要求时才修改颜色，并在修改后重新测量（[contrast.md](contrast.md)）。

## 选择渐变的插值空间

插值空间决定的是视觉效果，而不是正确性设置。

- **`in oklab`** 是最佳默认选项：亮度均匀，不会出现意外的色相变化。
- **`in oklch`** 会绕着色相环变化，而不是穿过中间区域，因此能保持鲜艳，并覆盖色标之间的所有色相。当双色渐变在中间变灰时，应选用它。
- **sRGB 默认值** 会使中点变暗并降低鲜艳度。大多数界面已经采用这种效果，因为不做特别指定时得到的就是它。

参见 [color-usage.md](color-usage.md)。

## 完成之前

| 错误 | 修复 |
| --- | --- |
| 项目已有 token，却使用了原始值 | 按项目的表示法复用或添加 role token |
| 在十六进制代码库中孤立地使用一个 `oklch()` 值 | 除非迁移工作在范围内，否则保持既有表示法 |
| 在组件中直接使用了 `--blue-500` 之类的 primitive | 让 semantic token 指向它 |
| Token 根据外观命名（`--color-blue-button`）或首次用途命名（`--color-sidebar-gray`） | 根据其角色命名：`--color-accent-solid`、`--color-bg-surface` |
| `--color-primary` 表示品牌，而 `--color-text-primary` 表示正文文本 | 将 `accent` 保留给品牌；让 `primary` 表示“其所属组中最突出的项” |
| 在其角色之外使用 semantic token（例如将分隔线 token 用作文本） | 为缺失的角色添加 token；绝不要按值借用 |
| 通过改变 HSL 亮度构建色阶 | 使用恒定色相，基于感知亮度重新构建 |
| 在完整范围内均匀分布色阶 | 收紧亮色端，直到 `50` 和 `100` 能读作两个表面 |
| 在不同色相之间复用同一个饱和度数值 | 匹配各色相自身最大值的比例，而不是原始数值 |
| 状态色相与强调色相冲突 | 调整状态色相，直到 destructive 和 primary 并排显示时能够区分开 |
| 通过机械地反转浅色调色板来制作深色模式 | 以反转为起点，然后降低鲜艳度、拓宽暗色端，并重新检查每一组配对 |
| `prefers-color-scheme` 设置部分 token，而 `.dark` 类设置其他 token | 选择一种切换机制，并在整个项目中统一使用 |
| 通过改变色相来修复对比度 | 改变亮度，对比度会随之响应 |
| P3 颜色没有 sRGB 回退值 | 先声明 sRGB 值，然后在 `@media (color-gamut: p3)` 中覆盖 |

## 报告

**严重程度。** `HIGH` 表示内容无法阅读，或分配了具有误导性的语义颜色。`MEDIUM` 表示明显的主题、令牌或色域问题。`LOW` 表示局部的润色问题。

**验证。** 不使用浏览器时：检查令牌值、每个声明颜色的色域、两个主题代码块是否都存在，并根据声明的令牌对计算对比度。使用浏览器时：测量文本后方实际渲染的背景，包括不透明度以及其下方的任何图像，并在浅色和深色模式下分别测量。报告发现的失败配对，不要重新着色。将所有无法执行的检查报告为 `Not verified`。

**格式。** 按每项违反的原则对发现进行分组，并按严重程度排序；每个根本原因占一行，列出其出现的所有位置：

| 严重程度 | 位置 | 之前 | 之后 | 原因 |
| --- | --- | --- | --- | --- |

`Location` 的格式为 `path/to/file:line`。`Why` 需要说明违反的原则以及对用户造成的影响。

只要仍存在任何 `HIGH`，结尾就写上 `Block`；否则写上 `Approve`，同时将其余内容保留在表格中作为待处理项。绝不要批准未检查的覆盖范围。如果没有需要报告的内容，请写明 "No actionable color findings"，并报告验证结果。
