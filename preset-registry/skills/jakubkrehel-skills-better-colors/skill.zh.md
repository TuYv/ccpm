# 颜色

颜色系统是一组规模较小的色阶，以角色命名，并根据其实际渲染所在的背景进行验证。大多数颜色问题都是系统问题：孤立选取的值、因为看起来合适而借用的令牌、从未有人测量过的颜色组合。

绝不要报告未经测量的对比度值，也绝不要估算可以计算得出的颜色。颜色是少数具有精确答案的界面问题之一，因此请给出精确答案。

对比度要求归 `better-accessibility` 管理。表面、阴影和图标颜色归 `better-ui` 管理。

## 匹配项目的颜色系统

复用项目的令牌和表示法。为了修正一个值而添加第二种表示方式，会让调色板更难理解。统一的十六进制系统胜过夹杂着 `oklch()` 的十六进制系统。

对于新系统，`oklch()` 是最佳默认选择，因为它的数值变化方式符合下文所述的色阶规则。在其他情况下，颜色库可以用项目自身的表示法生成相同的色阶（[color-formats.md](color-formats.md)）。

## 系统由色阶组成，而非颜色

一个中性色阶、一个强调色色阶，以及仅包含产品实际渲染的状态色阶。没有任何地方导入的 `warning` 色阶，是对零个像素进行维护。只有当两种事物必须一眼就能区分时，第二种强调色相才有存在的价值。

## 每个色阶层级都有职责

色阶不是凭肉眼挑选颜色的渐变。每个层级之所以存在，是因为某个角色需要它：页面背景、组件悬停状态、边框、纯色填充、正文文本。不要生成没有任何角色使用的层级。Tailwind 的 `50`–`950` 和 Radix 的 `1`–`12` 约定都可以映射到这些角色（[palette-structure.md](palette-structure.md)）。

## 按色相命名原始令牌，按角色命名语义令牌

原始令牌用于命名一个值（`--blue-500`），绝不直接应用于组件。语义令牌用于命名一项职责（`--color-text-secondary`），指向原始令牌，并且是组件唯一引用的层级。

正是这一层分界让主题切换成为可能。没有它，实现深色模式就意味着需要审查每一处用法，以确定哪些表示“强调色”，哪些只是想要蓝色（[token-naming.md](token-naming.md)）。

## 令牌只能用于其对应角色

绝不要因为某个令牌的值目前看起来合适就借用它。将分隔线令牌用作文本颜色，在边框变浅之前似乎可行，但边框一旦变浅，文本也会随之变浅。如果某个角色没有对应令牌，就添加该令牌。

## 在整个色阶中保持色相一致

四个属性定义了结构良好的色阶：

- 各层级在*感知*明度上均匀递进，而不是按照格式中所谓的明度递进。
- 色相从头到尾保持不变。
- 鲜艳度在色阶中段达到峰值，并向两端逐渐降低。
- 浅色端的层级分布比深色端更密集。

两端都应避开纯黑和纯白，因为它们完全无法承载色相。请使用颜色库，而不要凭肉眼判断（[palette-generation.md](palette-generation.md)）。

## 一种颜色，一种含义

在整个界面中，一种颜色只用于一种用途，并将色相差在 `15°` 以内的任何颜色视为同一种颜色。如果强调色表示可交互，那么在静态文本上使用该色相会让用户误以为不可点击的内容可以点击；反之，将可交互元素渲染为中性色同样会造成严重误导。颜色绝不能成为传达含义的唯一载体，这部分归 `better-accessibility` 管理。

## 每个视图仅使用一个填充式操作

当填充色用于表示主要强调时，只为一个主要操作使用填充色，同级操作则保持中性。将颜色用于背景，而不是标签。即使隔着一段距离，填充式按钮也会被视为主要操作；中性按钮上的强调色文本则会被视为链接。

当多个彩色背景用于表示不同的状态或类别，而不是作为同级元素相互竞争时，可以同时使用。

## 测量实际渲染的前景与背景组合，然后报告结果

应针对前景实际渲染于其上的背景进行测量，而不是页面背景。当某个组合未通过时，报告该组合、测量值以及未达到的阈值，然后保持颜色不变。颜色属于设计决策。只有在收到要求时才更改颜色，并在更改后重新测量（[contrast.md](contrast.md)）。

## 选择渐变的插值空间

空间决定视觉效果，而不是正确性。

- **`in oklab`** 是最佳默认选项：亮度均匀，不会出现意外的色相变化。
- **`in oklch`** 会沿色相环移动，而不是穿过中间区域，因此能够保持鲜艳，并涵盖色标之间的所有色相。当双色渐变在中间变成灰色时，请使用它。
- **sRGB 默认值** 会使中点变暗、变柔和。大多数界面已经采用这种效果，因为不做额外指定时得到的就是它。

请参阅 [color-usage.md](color-usage.md)。

## 完成之前

| 错误 | 修复方式 |
| --- | --- |
| 项目已有令牌，却使用了原始值 | 使用项目既有的表示法复用或添加角色令牌 |
| 在使用十六进制颜色的代码库中单独加入一个 `oklch()` 值 | 除非迁移在工作范围内，否则保持既有表示法 |
| 在组件中直接使用类似 `--blue-500` 的基础令牌 | 让语义令牌指向它 |
| 根据外观（`--color-blue-button`）或首次用途（`--color-sidebar-gray`）命名令牌 | 根据角色命名：`--color-accent-solid`、`--color-bg-surface` |
| `--color-primary` 表示品牌，而 `--color-text-primary` 表示正文文本 | 保留 `accent` 表示品牌；让 `primary` 表示“所属组中最突出的项” |
| 在角色之外使用语义令牌（将分隔符令牌用于文本） | 为缺失的角色添加令牌；绝不要因为值相同而借用 |
| 通过改变 HSL 明度构建色阶 | 使用恒定色相，基于感知明度重新构建 |
| 在整个范围内均匀划分色阶 | 收紧亮色端的间距，直到 `50` 和 `100` 看起来像两个不同的表面 |
| 对不同色相复用相同的饱和度数值 | 匹配各色相自身最大饱和度的比例，而不是原始数值 |
| 状态色相与强调色相冲突 | 调整状态色相，直到破坏性操作与主要操作并排显示时能够明显区分 |
| 通过机械反转浅色调色板来制作深色模式 | 将反转作为起点，然后降低鲜艳度、扩大深色端的间距，并重新检查每个组合 |
| `prefers-color-scheme` 设置一部分令牌，而 `.dark` 类设置另一部分令牌 | 选择一种切换机制，并始终使用它 |
| 通过更改色相修复对比度 | 更改明度，即对比度所响应的通道 |
| P3 颜色没有 sRGB 回退值 | 先声明 sRGB 值，然后在 `@media (color-gamut: p3)` 内覆盖 |

## 报告

**严重性。** `HIGH` 表示内容无法阅读或被赋予具有误导性的语义颜色。`MEDIUM` 表示存在明显的主题、令牌或色域问题。`LOW` 表示孤立的细节问题。

**验证。** 无浏览器时：验证令牌值、每种已声明颜色的色域、两个主题块是否都存在，以及根据声明的令牌对计算出的对比度。有浏览器时：测量文本背后实际渲染的背景，包括透明度及其下方的任何图像，并分别在浅色和深色模式下进行测量。应报告不合格的配色对，而不是重新着色。将所有无法执行的检查报告为 `Not verified`。

**格式。** 按发现项所违反的原则进行分组，并按严重性排序；每个根本原因占一行，列出其出现的所有位置：

| 严重性 | 位置 | 修改前 | 修改后 | 原因 |
| --- | --- | --- | --- | --- |

`Location` 的格式为 `path/to/file:line`。`Why` 应说明所违反的原则及其对用户的影响。

如果仍存在任何 `HIGH`，则以 `Block` 结尾；否则以 `Approve` 结尾，并将其余问题保留在表格中作为待办工作。绝不要对未经检查的覆盖范围给出 `Approve`。如果没有任何需要报告的内容，请注明“没有可采取行动的颜色问题”，并报告验证情况。
