# 色彩

色彩系统是一小组色阶，按角色命名，并根据它们实际渲染的背景进行验证。大多数色彩问题都是系统问题：孤立挑选的数值、因为看起来合适而借用的 token、从未测量过的一对颜色。

绝不要报告未经测量的对比度数值，也绝不要估算你能够计算出的颜色。色彩是少数能够得出精确答案的界面问题之一，因此应给出精确答案。

对比度要求属于 `better-accessibility`。表面、阴影和图标颜色属于 `better-ui`。

## 匹配项目的色彩系统

复用项目的 token 和表示法。为修复一个数值而添加第二种表示方式，会让调色板更难推理。一致的十六进制系统优于其中零散混入 `oklch()` 的十六进制系统。

对于新系统，`oklch()` 是最佳默认选择，因为它的数值表现方式符合下述色阶规则。在其他情况下，使用颜色库以项目自身的表示法生成相同的色阶（[color-formats.md](color-formats.md)）。

## 系统是色阶，而不是颜色

一个中性色阶、一个强调色色阶，以及产品实际渲染的状态色阶。没有任何内容导入的 `warning` 色阶，是为零个像素进行维护。只有当两个事物必须一眼可区分时，第二种强调色相才值得存在。

## 每个层级都有职责

色阶不是凭眼睛挑选的渐变。每个层级之所以存在，是因为某个角色需要它：页面背景、组件悬停、边框、实心填充、正文文本。不要生成没有任何角色使用的层级。Tailwind 的 `50`–`950` 和 Radix 的 `1`–`12` 约定都映射到这些角色（[palette-structure.md](palette-structure.md)）。

## 按色相命名原始值，按角色命名语义

原始值命名一个数值（`--blue-500`），且绝不直接应用于组件。语义 token 命名一项职责（`--color-text-secondary`），指向一个原始值，并且是组件唯一引用的层级。

这一分层使主题化成为可能。没有它，深色模式就意味着必须审查每一处使用，以弄清哪些表示“强调色”，哪些只是需要蓝色（[token-naming.md](token-naming.md)）。

## 仅在其角色中使用 token

绝不要因为某个 token 今天的数值恰好合适而借用它。用作文本颜色的分隔线 token，在边框变浅时仍会生效，而文本也会随之变浅。如果某个角色没有 token，就添加该 token。

## 在整个色阶中保持色相

四项属性定义了一个结构良好的色阶：

- 各层级应在*感知*明度上均匀递进，而不是按照该格式所谓的明度递进。
- 色相从头到尾保持不变。
- 鲜艳度在色阶中部达到峰值，并在两端降低。
- 浅色端的层级密度高于深色端。

两端都应止于纯黑和纯白之前，因为它们根本无法承载色相。请使用颜色库，而不是凭眼睛判断（[palette-generation.md](palette-generation.md)）。

## 一种颜色，一个含义

在整个界面中，一种颜色只用于一个目的，并将色相相差 `15°` 以内的任何颜色视为同一种颜色。如果强调色表示可交互，那么静态文本上的该色相会让用户以为不可点击的内容可以点击，而以中性色呈现的交互元素同样会产生误导。颜色绝不是意义的唯一载体，这属于 `better-accessibility` 的职责。

## 每个视图恰好填充一个操作

当填充色用于编码主要强调时，只有一个主要操作使用它，其余同级操作保持中性。将颜色用于背景，而不是标签。填充按钮即使隔着房间也能被识别为主要操作；中性按钮上的强调色文本则会被理解为链接。

当多种彩色背景用于编码不同状态或类别，而非作为同级操作相互竞争时，使用它们是可以的。

## 测量实际渲染的颜色对，然后报告

应测量前景色与其实际渲染所在背景之间的对比度，而不是与页面背景之间的对比度。当一组颜色不合格时，报告该颜色对、其实测值以及未达到的阈值，然后不要改动颜色。它们是设计决策。仅在被要求时修改，并在之后重新测量（[contrast.md](contrast.md)）。

## 选择渐变的插值空间

该空间决定的是视觉效果，而不是正确性设置。

- **`in oklab`** 是最佳默认选择：亮度均匀，不会出现意外的色相变化。
- **`in oklch`** 会沿色相环移动，而不是穿过中间区域，因此能保持鲜艳，并扫过两个色标之间的每一种色相。当双色渐变在中间变灰时，优先使用它。
- **默认的 sRGB** 会使中点变暗、变灰。这正是大多数界面已有的效果，因为不特别指定时得到的就是它。

参见 [color-usage.md](color-usage.md)。

## 完成之前

| 错误 | 修正方式 |
| --- | --- |
| 项目已有令牌时仍使用原始值 | 按照项目的记法复用或添加角色令牌 |
| 在使用十六进制代码的代码库中孤立地加入 `oklch()` 值 | 除非迁移在范围内，否则保持既有记法 |
| 在组件中直接使用诸如 `--blue-500` 的原始令牌 | 让语义令牌指向它 |
| 令牌以外观（`--color-blue-button`）或首次用途（`--color-sidebar-gray`）命名 | 按其角色命名：`--color-accent-solid`、`--color-bg-surface` |
| `--color-primary` 表示品牌，而 `--color-text-primary` 表示正文文本 | 为品牌保留 `accent`；让 `primary` 表示“其所属组中最突出者” |
| 在角色之外使用语义令牌（将分隔线用作文本） | 为缺失角色添加令牌；绝不按值借用 |
| 通过改变 HSL 明度构建色阶 | 使用恒定色相，依据感知亮度重建 |
| 色阶在完整范围内均匀分布 | 收紧亮色端，直到 `50` 和 `100` 读起来像两个表面 |
| 跨色相复用相同的饱和度数值 | 匹配各色相自身最大值的比例，而不是原始数值 |
| 状态色相与强调色相冲突 | 调整它，直到破坏性操作和主要操作并排时明显不同 |
| 通过机械反转浅色调色板来制作深色模式 | 以反转作为起点，然后降低鲜艳度、扩展深色端，并重新检查每一组颜色对 |
| `prefers-color-scheme` 设置部分令牌，而 `.dark` 类设置其他令牌 | 选择一种切换机制，并始终使用它 |
| 通过改变色相修复对比度 | 改变明度，因为对比度响应的是该通道 |
| P3 颜色没有 sRGB 回退值 | 先声明 sRGB 值，然后在 `@media (color-gamut: p3)` 内覆盖 |

## 报告

**严重性。** `HIGH` 表示内容不可读，或被赋予误导性的语义颜色。`MEDIUM` 表示明显的主题、令牌或色域问题。`LOW` 表示孤立的润色问题。

**验证。** 无浏览器时：验证令牌值、每个声明颜色的色域、两个主题块是否存在，以及根据声明的令牌对计算对比度。有浏览器时：在浅色和深色模式下，测量文本背后实际渲染的背景，包括不透明度及其下方的任何图像。报告不合格的配对，而不是重新着色。将所有无法执行的检查报告为 `Not verified`。

**格式。** 按其违反的原则对发现分组，按严重性排序，每个根本原因一行，列出其出现的所有位置：

| 严重性 | 位置 | 修改前 | 修改后 | 原因 |
| --- | --- | --- | --- | --- |

`Location` 格式为 `path/to/file:line`。`Why` 应说明原则及对用户的影响。

如果仍有任何 `HIGH`，则以 `Block` 结束；否则以 `Approve` 结束，并将其余内容保留在表格中作为待处理工作。绝不 `Approve` 未检查的覆盖范围。若没有可报告的问题，请声明 "No actionable color findings" 并报告验证情况。
