# 转为工单

将计划、规范或对话拆分为一组**工单**：采用曳光弹式垂直切片，每个工单都声明**阻塞**它的其他工单。

你应该已经获得问题跟踪器和分诊标签词汇表。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的任何信息开展工作。如果用户通过参数传入了某个引用（规范路径、问题编号或 URL），请获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，请先进行探索，以了解代码的当前状态。工单标题和描述应使用项目领域术语表中的词汇，并遵循所涉及区域的 ADR。

寻找对代码进行预重构的机会，让实现变得更加容易。“先让变更变得容易，再完成这个容易的变更。”

### 3. 起草垂直切片

将工作拆分为**曳光弹式**工单。

<vertical-slice-rules>

- 每个切片都应沿着每一层（schema、API、UI、tests）切出一条狭窄但完整的路径：采用垂直切片，而不是仅涉及某一层的水平切片
- 每个已完成的切片都能够独立演示或验证
- 每个切片的规模都应适合在单个全新上下文窗口中完成
- 任何预重构都应优先完成

</vertical-slice-rules>

为每个工单注明其**阻塞边**：必须先完成哪些其他工单，该工单才能开始。没有阻塞项的工单可以立即开始。

**大范围重构是垂直切片的例外。** **大范围重构**是指某项机械式变更（重命名列、重新定义共享符号的类型），其**影响范围**会扩散至整个代码库，导致一次编辑便破坏数千个调用点，且无法让任何垂直切片在保持绿色状态的情况下落地。不要强行将其变成曳光弹式切片；应按照**扩展—收缩**的方式安排。首先扩展：在旧形式旁添加新形式，确保不会破坏任何内容。然后按照影响范围将调用点分批迁移（按包、按目录），每一批都作为独立工单并受扩展工单阻塞；由于旧形式仍然存在，因此各批次之间应保持 CI 绿色。最后收缩：在不再有任何调用方后删除旧形式，该工单受所有迁移批次阻塞。如果连各批次都无法单独保持绿色，则仍保留这一顺序，但让它们共享一个集成分支，并让它们全部阻塞最终的集成与验证工单；只承诺在该工单中恢复绿色状态。

### 4. 向用户提问确认

以编号列表的形式展示建议的拆分方案。对于每个工单，展示：

- **标题**：简短的描述性名称
- **阻塞项**：必须先完成哪些其他工单（如有）
- **交付内容**：此工单实现的端到端行为

询问用户：

- 粒度是否合适？（过粗 / 过细）
- 阻塞边是否正确：每个工单是否仅依赖那些确实会阻碍其开始的工单？
- 是否应合并某些工单，或进一步拆分？

持续迭代，直到用户批准该拆分方案。

### 5. 将工单发布到已配置的问题跟踪器

发布已批准的工单。具体**方式**取决于工单跟踪器 `/setup-matt-pocock-skills` 的配置；无论采用哪种方式，工单本身都相同，只有阻塞关系边的形式会发生变化：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单写入一个文件，按依赖顺序（阻塞项优先）从 `01` 开始编号。每个文件的“阻塞依赖”应列出它所依赖的工单编号/标题。使用下方的单工单文件模板：每个文件只放一个工单，绝不能合并到单个文件中。
- **真实的工单跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞项优先）发布工单，每个工单对应一个 issue，以便每个工单的阻塞关系边都能引用真实标识符。如果平台原生支持阻塞/子 issue 关系，请使用该功能；否则，将每个工单的“阻塞依赖”设置为阻塞它的 issue。除非另有指示，否则应用 `ready-for-agent` 分诊标签；这些工单在设计上即可由代理领取。

处理**前沿工单**：即所有阻塞项均已完成的工单。对于完全线性的依赖链，这意味着从上到下依次处理。

不得关闭或修改任何父 issue。
