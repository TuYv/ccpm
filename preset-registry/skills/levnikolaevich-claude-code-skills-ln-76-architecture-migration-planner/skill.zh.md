# 架构迁移规划器

**目标：** 从有证据支持的当前架构，安全且可逆地过渡到明确的目标架构。只更改已批准的迁移文档；不要执行迁移、编辑产品代码、构建通用任务计划、批准交付，或隐藏不可逆步骤。

**执行契约：** 将以下按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用表明其条件触发器不存在的证据将其解决为 `CLEARED`，或将其标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。
返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，对每个 `UNPROVEN` 应用此技能的判定、决策和批准规则，并添加前缀 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 当前状态和目标状态 | 仓库证据加上已批准的架构制品 | 用户明确提供的状态，并注明局限性 |
| 使用者和兼容性 | 语言智能、架构工具、配置搜索、遥测和直接检查 | 标记为 `UNVERIFIED` 的保守清单 |
| 数据规模和运行时风险 | 生产指标、已检入的报告、迁移记录和工作负载证据 | 在执行前设置验证门禁的范围值 |
| 外部迁移约束 | 供应商官方迁移和兼容性指南 | 将相关阶段标记为 `BLOCKED` 或 `UNVERIFIED` |
| 文档修改 | 对已批准迁移计划制品的最小补丁 | 当权限或路径不明确时返回 `BLOCKED` |

迁移阶段必须使系统处于受支持的状态。增量且可逆的步骤应先于切换；破坏性清理应在确认零使用后进行。

## 制品规则

- 复用清晰的架构迁移文档；否则使用 `docs/architecture/migration-plan.md`。
- 将当前状态、目标设计、基线、决策、图表、接口和遥测视为可选的共享证据。
- 保持计划的架构层级：阶段、兼容性、数据、拓扑、门禁、回滚、责任归属和移除。
- 将文件级实现任务留给下游规划。
- 分开准备、共存、迁移、切换、稳定化和移除阶段。
- 当数据或外部影响不可逆时，绝不要将回滚描述为“恢复原状”。
- 为每个破坏性步骤明确规定批准、备份、恢复和零使用者证据要求。

## 检查清单

### 1. 建立迁移契约

- [ ] 明确迁移范围、业务结果、当前状态、目标状态、非目标、截止日期或时间范围、责任人和已批准的目标位置。
- [ ] 阅读仓库说明、Git 状态、相关架构制品、迁移记录、部署配置和兼容性策略。
- [ ] 验证当前状态和目标状态是否具体到足以计算差距；不要臆造任一状态，而应返回 `BLOCKED`。
- [ ] 识别受保护的用户旅程、不变量、SLO、恢复目标、合规义务和变更窗口。
- [ ] 除已批准的迁移文档外，保持本次运行只读。

### 2. 构建差距与依赖关系图

- [ ] 盘点受影响的模块、可部署单元、数据存储、架构、API、事件、配置、基础设施和运维流程。
- [ ] 盘点内部和外部使用方、负责人、版本、流量、数据量和证据质量。
- [ ] 映射边界、归属、契约、数据、运行时拓扑、可观测性和故障行为从当前状态到目标状态的变化。
- [ ] 识别共享可变资源、时序依赖、长时间运行的工作、混合版本窗口和不可逆影响。
- [ ] 将未知使用方或未知用法记录为迁移风险；搜索无结果不代表没有使用。

### 3. 设计兼容性与数据安全

- [ ] 在适用时定义新旧契约兼容性、版本协商、适配器、双读或双写行为，以及弃用策略。
- [ ] 对架构和数据形态变更采用扩展/迁移/收缩（expand/migrate/contract）；将增量操作和破坏性操作安排在不同发布中。
- [ ] 定义回填选择、分批处理、限流、幂等性、检查点、重试、对账和正确性判定依据。
- [ ] 定义共存期间的事实来源，以及并发写入时的冲突处理方式。
- [ ] 定义数据移动对备份、恢复、RPO/RTO 的影响，以及隐私、保留期限和审计证据要求。

### 4. 构建可逆阶段

- [ ] 将准备、影子运行或共存、渐进式迁移、切换、稳定化和旧路径移除定义为可独立验证的阶段。
- [ ] 对每个阶段说明前置条件、变更后的架构状态、负责人、进入门槛、可观测的成功标准、中止条件、回滚或继续向前推进的操作，以及退出证据。
- [ ] 在有充分理由时定义功能开关、路由控制、金丝雀分组、速率限制、维护窗口和爆炸半径控制。
- [ ] 在流量或数据移动前，定义所需的指标、日志、追踪、对账报告、仪表板、告警和 SLO 门槛。
- [ ] 通过符合实际的部署顺序和回滚窗口，确保旧版本与新版本保持互操作。

### 5. 规划切换与移除

- [ ] 定义是否继续的决策权限、沟通方式、冻结条件、确切的切换控制和立即验证步骤。
- [ ] 分别定义代码、配置、流量、架构以及已迁移数据的回滚边界。
- [ ] 在进行破坏性移除前，要求确认经测量的零使用、使用方已完成迁移、保留期限已到期，并获得明确批准。
- [ ] 列出需要移除的旧代码路径、契约、开关、适配器、作业、数据、基础设施、仪表板和文档。
- [ ] 定义切换后的观察期、责任交接、事件响应和闭环证据。

### 6. 编写与报告

- [ ] 编写过渡摘要、状态差距、依赖关系、兼容性、数据计划、分阶段顺序、门槛、可观测性、回滚、移除项、负责人、假设和待决策事项。
- [ ] 通过稳定的仓库路径或标题链接共享工件，但不要求采用特定的工作流程。
- [ ] 重新审阅每个阶段，检查是否存在缺乏依据的零停机、零损失、使用方、容量或可逆性声明。
- [ ] 确认未执行任何迁移、代码、测试、部署、任务跟踪器或外部变更。
- [ ] 仅当各阶段能够安全地作为实施规划的输入执行时，才使用 `READY`；对于实质性的兼容性、数据、门槛或回滚缺口，使用 `REVISE`；当当前状态、目标状态、决策权限或安全证据不可用时，使用 `BLOCKED`。

## 输出契约

```markdown
# Architecture Migration Plan

**Verdict:** READY | REVISE | BLOCKED
**Artifact:** path

## State transition
- Current state, target state, gap, consumers, and invariants

## Phases
| Phase | Entry gate | Change | Success evidence | Abort condition | Rollback or roll-forward |
|---|---|---|---|---|---|

## Data, compatibility, and removal
- Coexistence, migration, reconciliation, cutover, and zero-use proof

## Open decisions and residual risks
Only items that can change safety, ordering, or reversibility.
```
