# 架构迁移规划器

**目标：** 规划从有证据支持的当前架构向明确目标架构的安全过渡，并明确可逆性限制和恢复操作。仅修改已批准的迁移文档；不要执行迁移、编辑产品代码、构建通用任务计划、批准交付或隐藏不可逆步骤。

**执行契约：** 有序复选框是完成标准。将每一项在内部跟踪为 `PENDING`、有具体证据支持的 `PROVEN`、有证据表明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个章节后重新核对各项。在返回前解决所有 `PENDING` 项，并且只统计 `PROVEN` 和 `CLEARED`；针对每个缺口应用该技能的判定和批准规则。

保留用户意图、范围和现有授权。继续执行已授权的工作；仅针对尚未解决且会产生重大影响的选择或所需的外部批准进行询问。根据实际风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；对于其他事项，选择适合每项义务的验证方法。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 当前状态和目标状态 | 仓库证据加上已批准的架构工件 | 使用用户明确提供的状态，并注明限制 |
| 使用者和兼容性 | 语言智能、架构工具、配置搜索、遥测和直接检查 | 采用保守的清单，并标记为 `UNVERIFIED` |
| 数据规模和运行时风险 | 生产指标、已检入的报告、迁移和工作负载证据 | 使用范围，并在执行前设置验证门 |
| 外部迁移约束 | 官方供应商迁移和兼容性指南 | 将相关阶段标记为 `BLOCKED` 或 `UNVERIFIED` |
| 文档修改 | 对已批准的迁移计划工件进行最小补丁修改 | 当权限或路径不明确时返回 `BLOCKED` |

迁移阶段必须使系统处于受支持的状态。增量且可逆的步骤应先于切换；破坏性清理应在确认没有使用者后进行。

## 工件规则

- 复用清晰的架构迁移文档；否则使用 `docs/architecture/migration-plan.md`。
- 将当前状态、目标设计、基线、决策、图表、接口和遥测视为可选的共享证据。
- 保持计划的架构层级：阶段、兼容性、数据、拓扑、门控、回滚、所有权和移除。
- 将文件级实现任务留给下游规划。
- 当数据或外部影响不可逆时，绝不要将回滚描述为“还原”。
- 对每个破坏性步骤明确规定批准、备份、恢复和零使用者证据要求。

## 检查清单

### 1. 建立过渡契约

- [ ] 明确迁移范围、业务结果、当前状态、目标状态、非目标、截止日期或时间范围、负责人和已批准的目标位置。
- [ ] 阅读仓库说明、Git 状态、相关架构工件、迁移、部署配置和兼容性策略。
- [ ] 验证当前状态和目标状态是否足够具体，能够计算差距；不得臆造任一状态，应返回 `BLOCKED`。
- [ ] 识别受保护的用户流程、不变量、SLO、恢复目标、合规职责和变更窗口。
- [ ] 除已批准的迁移文档外，保持本次执行为只读。

### 2. 构建差距与依赖关系图

- [ ] 盘点受影响的模块、可部署单元、数据存储、架构、API、事件、配置、基础设施和运维流程。
- [ ] 盘点内部和外部消费者、负责人、版本、流量、数据量和证据质量。
- [ ] 映射当前状态到目标状态在边界、所有权、契约、数据、运行时拓扑、可观测性和故障行为方面的变化。
- [ ] 识别共享可变资源、时序依赖、长时间运行的工作、混合版本窗口和不可逆影响。
- [ ] 将未知消费者或用法记录为迁移风险；搜索无结果不等于零使用。

### 3. 设计兼容性与数据安全

- [ ] 在适用的情况下，定义新旧契约兼容性、版本协商、适配器、双读或双写行为以及弃用策略。
- [ ] 当混合版本或在线迁移要求共存时，采用扩展/迁移/收缩（expand/migrate/contract）；在这种情况下，将增量发布与破坏性发布分开。对于已批准的离线原子切换，记录等效的兼容性、恢复和停机控制措施。
- [ ] 定义回填选择、分批处理、限流、幂等性、检查点、重试、对账和正确性判定依据。
- [ ] 定义共存期间的事实来源、并发写入冲突处理，以及部分双写失败的检测、重试和对账；不要假设两次写入具有原子性。
- [ ] 定义数据移动对备份、恢复、RPO/RTO、隐私、保留期限和审计证据的影响。

### 4. 构建可逆阶段

- [ ] 将准备、影子或共存、渐进式迁移、切换、稳定化和旧路径移除定义为可独立验证的阶段。
- [ ] 对每个阶段说明前置条件、变更后的架构状态、负责人、进入门槛、可观测的成功标准、中止条件、回滚或前滚操作以及退出证据。
- [ ] 在合理的情况下，定义功能开关、路由控制、金丝雀用户群、速率限制、维护窗口和影响范围控制。
- [ ] 在流量或数据移动之前，定义所需的指标、日志、追踪、对账报告、仪表盘、告警和 SLO 门槛。
- [ ] 通过符合实际部署顺序和回滚窗口的方式，保持新旧版本之间的互操作性。

### 5. 规划切换与移除

- [ ] 定义是否继续执行的决策权限、沟通机制、冻结条件、精确的切换控制和立即验证步骤。
- [ ] 分别定义代码、配置、流量、架构和已迁移数据的回滚边界，包括不可逆点，以及在回滚会丢失已接受写入时的前滚恢复方案。
- [ ] 在进行破坏性移除之前，要求在覆盖相关调度、离线消费者、已迁移消费者和适用保留期限到期情况的时间窗口内取得使用证据，并获得明确批准。短时间的零流量采样无法证明零使用。
- [ ] 列出需要移除的旧代码路径、契约、开关、适配器、任务、数据、基础设施、仪表盘和文档。
- [ ] 定义切换后的观察期、所有权交接、事件响应和闭环证据。

### 6. 编写并报告

- [ ] 编写过渡摘要、状态差距、依赖关系、兼容性、数据计划、分阶段顺序、门控条件、可观测性、回滚、移除、负责人、假设和待决事项。
- [ ] 通过稳定的仓库路径或标题链接共享工件，无需限定特定工作流。
- [ ] 重新阅读每个阶段，检查是否存在未经支持的零停机、零丢失、消费者、容量或可逆性声明。
- [ ] 仅当各阶段是可安全执行的实施规划输入时使用 `READY`；存在实质性的兼容性、数据、门控条件或回滚缺口时使用 `REVISE`；当当前状态、目标状态、权威依据或安全证据不可用时使用 `BLOCKED`。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、判定结果和适用的清理工作。更正报告或已授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每个事实只陈述一次。结果较少时，每个字段可使用一行；省略空表格，不要复制已链接的工件：

1. **结果：** Skill 专属判定结果和有证据支持的结论。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill 专属字段；区分事实、推断和未经验证的声明。链接工件；适用时使用表格。
4. **验证：** 检查及结果、不可用的证据、适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；剩余风险及所需决策。

**Skill 专属证据：** 工件路径；当前/目标差距、消费者、依赖关系和受保护的不变量。总结各阶段的进入门控条件、变更、成功证据、中止条件、回滚/前进；数据/共存/对账/切换/移除证明；以及会影响安全性、顺序或可逆性的待决事项。
