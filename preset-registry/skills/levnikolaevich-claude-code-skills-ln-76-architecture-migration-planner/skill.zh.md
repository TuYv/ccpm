# 架构迁移规划器

**目标：** 创建一个安全、可逆的过渡方案，从有证据支持的当前架构迁移到明确的目标架构。仅更改获准的迁移文档；不得执行迁移、编辑产品代码、制定通用任务计划、批准交付，也不得隐瞒不可逆步骤。

**执行约定：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。依次处理每一项，并且只有在其操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的结论和批准规则应用于每个未完成项，并在开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项。

## 工具路由

| 需求 | 首选能力 | 备选方案 |
|---|---|---|
| 当前状态和目标状态 | 仓库证据以及已批准的架构产物 | 用户明确提供的状态，并注明其局限性 |
| 使用方和兼容性 | 语言智能、模式工具、配置搜索、遥测和直接检查 | 标记为 `UNVERIFIED` 的保守清单 |
| 数据规模和运行时风险 | 生产指标、已签入的报告、迁移记录和工作负载证据 | 使用范围估算，并设置执行前验证关卡 |
| 外部迁移约束 | 官方供应商迁移和兼容性指南 | 将依赖阶段标记为 `BLOCKED` 或 `UNVERIFIED` |
| 文档修改 | 对获准的迁移计划产物进行最小化补丁修改 | 当权限或路径不明确时返回 `BLOCKED` |

迁移阶段必须使系统保持在受支持状态。增量且可逆的步骤应先于切换；破坏性清理应在确认使用量为零后进行。

## 产物规则

- 复用清晰的架构迁移文档；否则使用 `docs/architecture/migration-plan.md`。
- 将当前状态、目标设计、基线、决策、图表、接口和遥测视为可选的共享证据。
- 使计划聚焦于架构：阶段、兼容性、数据、拓扑、关卡、回滚、责任归属和移除。
- 将文件级实现任务留给下游规划。
- 将准备、共存、迁移、切换、稳定和移除分开。
- 当数据或外部影响不可逆时，绝不将回滚描述为“还原”。
- 为每个破坏性步骤明确规定批准、备份、恢复以及零使用方证据要求。

## 检查清单

### 1. 建立过渡约定

- [ ] 明确迁移范围、业务成果、当前状态、目标状态、非目标、截止日期或时间范围、责任人以及获准的目标位置。
- [ ] 阅读仓库说明、Git 状态、相关架构产物、迁移记录、部署配置和兼容性策略。
- [ ] 验证当前状态和目标状态是否足够具体，以便计算差距；不得臆造任何一种状态，而应返回 `BLOCKED`。
- [ ] 识别受保护的用户旅程、不变量、SLO、恢复目标、合规义务和变更窗口。
- [ ] 除获准的迁移文档外，本次操作对其他内容均保持只读。

### 2. 构建差距与依赖关系图

- [ ] 盘点受影响的模块、可部署单元、数据存储、模式、API、事件、配置、基础设施和运维流程。
- [ ] 盘点内部和外部使用方、负责人、版本、流量、数据量和证据质量。
- [ ] 梳理从当前状态到目标状态在边界、所有权、契约、数据、运行时拓扑、可观测性和故障行为方面的变化。
- [ ] 识别共享可变资源、时序依赖、长时间运行的工作、混合版本窗口和不可逆影响。
- [ ] 将未知的使用方或使用情况记录为迁移风险；没有搜索结果并不意味着使用量为零。

### 3. 设计兼容性与数据安全方案

- [ ] 根据需要定义新旧契约兼容性、版本协商、适配器、双读或双写行为以及弃用策略。
- [ ] 对模式和数据形态变更采用扩展/迁移/收缩方式；将增量操作与破坏性操作安排在不同版本中。
- [ ] 定义回填数据的筛选、分批、限流、幂等性、检查点、重试、对账和正确性判定依据。
- [ ] 定义共存期间的事实来源，以及并发写入的冲突处理方式。
- [ ] 定义数据移动涉及的备份、恢复、RPO/RTO 影响、隐私、保留策略和审计证据。

### 4. 构建可逆阶段

- [ ] 将准备、影子运行或共存、渐进式迁移、切换、稳定化和旧路径移除定义为可独立验证的阶段。
- [ ] 对每个阶段，说明前置条件、变更后的架构状态、负责人、准入门槛、可观测的成功标准、中止条件、回滚或前滚操作以及退出证据。
- [ ] 在合理的情况下，定义功能标志、路由控制、金丝雀群组、速率限制、维护窗口和爆炸半径控制措施。
- [ ] 定义在流量或数据迁移前所需的指标、日志、跟踪、对账报告、仪表板、告警和 SLO 门槛。
- [ ] 通过符合实际的部署顺序和回滚窗口，确保新旧版本保持互操作性。

### 5. 规划切换与移除

- [ ] 定义执行或不执行的决策权、沟通机制、冻结条件、确切的切换控制方式和即时验证措施。
- [ ] 分别定义代码、配置、流量、模式和已迁移数据的回滚边界。
- [ ] 在执行破坏性移除之前，要求有实测的零使用量、已迁移的使用方、已到期的保留期限和明确的批准。
- [ ] 列出需要移除的旧代码路径、契约、标志、适配器、作业、数据、基础设施、仪表板和文档。
- [ ] 定义切换后的观察期、所有权移交、事件响应和收尾证据。

### 6. 编写与报告

- [ ] 编写过渡摘要、状态差距、依赖关系、兼容性、数据计划、分阶段顺序、门槛、可观测性、回滚、移除、负责人、假设和待决事项。
- [ ] 通过稳定的仓库路径或标题链接共享产物，而不要求采用特定工作流。
- [ ] 重新审查每个阶段，检查是否存在缺乏依据的零停机、零丢失、使用方、容量或可逆性声明。
- [ ] 确认未执行任何迁移、代码、测试、部署、任务跟踪器或外部变更。
- [ ] 仅当各阶段可作为安全可执行的实施规划输入时使用 `READY`；如果存在重大的兼容性、数据、门槛或回滚缺口，则使用 `REVISE`；如果无法获得当前状态、目标状态、授权或安全证据，则使用 `BLOCKED`。

## 输出契约

```markdown
# Architecture Migration Plan

**Verdict:** READY | REVISE | BLOCKED
**Artifact:** path

## State transition
- Current state, target state, gap, consumers, and invariants

## Phases
| Phase | Entry gate | Change | Success evidence | Abort condition | Rollback or roll-forward |
|---|---|---|---|---|---|

## Data, compatibility, and removal
- Coexistence, migration, reconciliation, cutover, and zero-use proof

## Open decisions and residual risks
Only items that can change safety, ordering, or reversibility.
```
