## 说明

阅读 `src/index.ts`（以及它导入的所有模块）中的同步功能。对于找到的每项同步功能，逐项检查下面的清单。按严重程度分组报告检查结果。

开始之前，请阅读 `.agents/skills/sync-guide/SKILL.md`，以获取完整的同步概念参考。

### 严重问题（会导致同步中断或数据丢失）

1. **分页无法终止**：`hasMore` 最终是否会变为 `false`？注意检查：`nextState` 不推进的无限循环、缺少基本终止条件、永远无法满足的条件。

2. **游标不推进**：`nextState` 在迭代之间是否发生变化？如果游标与之前的状态相同，同步将永远循环。检查每次执行调用是否都有进展。

3. **缺少首次运行处理**：当 `state` 为 `undefined`（首次运行）时，代码是否能妥善处理？注意检查：使用 `state.cursor` 而不是 `state?.cursor`、访问可能为 undefined 的 state 的属性。

4. **批次过大**：同步是否在一次执行中返回数千项变更？建议每批约 100 项。过大的批次会导致失败。

5. **API 支持变更跟踪时却使用替换模式**：如果模式为 `replace`（或未设置——默认值为 `replace`），源 API 是否支持 `updated_at` 过滤器、事件流或类似的变更跟踪机制？如果支持，建议使用替换模式执行回填，并另外创建一个共享同一数据库的增量差异同步。不要建议将现有同步直接切换为增量模式，因为这会丧失初始加载和标记清除行为。

6. **对状态持久化的误解**：在增量模式下，游标在各周期之间永远不会重置。下一个周期会从上一个周期停止的位置准确开始。检查代码是否假设每个周期都会重新开始——这会导致记录被重复获取或永久跳过。

### 结构性问题（双模式正确性）

1. **增量同步使用单一模式游标**：同步是否对回填和差异同步使用相同的游标策略？除非 API 按 `updated_at` 排序并使用不透明游标（在这种情况下，一个游标自然可以同时服务于两种模式），否则同步应使用具有独立回填和差异阶段的可辨识状态联合类型。

2. **缺少从回填到差异同步的转换**：对于双模式同步，差异游标是如何设定初始值的？它必须来自回填开始_之前_捕获的标记（事件锚点、带重叠窗口的时间戳），而_不能_来自回填中的最后一条记录。否则，回填期间发生的变更将永久丢失。

3. **转换时没有重叠窗口**：从回填转换为差异同步时，是否设置了重叠窗口（例如 `backfillStartedAt - 5 minutes`）？如果没有重叠窗口，在回填期间、但在差异游标开始之前被修改的记录将永久遗漏。

### 警告（可能导致隐蔽的数据质量问题）

1. **没有一致性缓冲区**：对于访问最终一致性 API 的增量同步，游标应比“当前时间”滞后 10–60 秒。如果没有此缓冲区，游标可能会越过尚未被源 API 编入索引的记录——由于游标永远不会重置，这些记录将永久丢失。

2. **时间戳游标缺少打破平局的机制**：如果使用 `updated_at` 作为游标，是否可能有多条记录共享同一时间戳？如果是（批量导入、批量更新、低精度时间戳），建议使用键集模式：`(timestamp, id)`，并采用类似 `WHERE ts > X OR (ts = X AND id > Y)` 的查询。

3. **缺少删除处理**：在增量模式下，是否处理了删除？请检查：
   - 源 API 是否提供删除信号（审计日志、归档筛选器、事件）？
   - 如果有，同步是否会发出 `{ type: "delete", key }` 标记？
   - 如果删除信号位于单独的端点上，是否使用了触发器模式（在周期边界交替处理数据流）？
   - 如果不存在删除信号，是否应该改用替换模式同步？

4. **硬编码密钥**：API 密钥、令牌或凭据是否直接写在代码中，而不是使用代理凭据或 `process.env`？标记任何看起来像密钥的字符串。

5. **fetch 缺少错误处理**：没有错误处理的网络调用会导致同步在任何暂时性故障发生时崩溃。请考虑同步是否应该捕获并处理 API 错误，还是让错误继续向上传播（运行时将重试该周期）。

### 输出格式

对于发现的每个问题：

- **问题**：指出问题名称和具体代码位置
- **重要性**：如果不修复，生产环境中会发生什么
- **修复方法**：提供展示修复方法的具体代码片段

如果未发现任何问题，请明确说明。不要凭空编造问题。
