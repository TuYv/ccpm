# 性能优化器

**目标：** 仅优化经过测量的问题。保持正确性，隔离实验，并且仅在可比证据表明某项更改能够改善约定指标且不会造成不可接受的回归时保留该更改。

**执行契约：** 将以下按顺序排列的复选框工作流视为此 skill 的完成定义。将每个复选框标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用表明其条件触发因素不存在的证据将其解决为 `CLEARED`，或解决为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不能作为证明。
返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，将此 skill 的裁决、决策和批准规则应用于每个 `UNPROVEN`，并添加前缀 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 存储库状态和安全编辑边界 | Git 状态、差异、分支或 worktree 检查，以及存储库说明 | 在分析性能或编辑之前始终执行 | 如果无法安全隔离用户更改，则停止 |
| 基线和最终指标 | 现有基准测试、负载测试、可复现命令或类似生产环境的重放 | 指标和工作负载能够反映所报告的问题时 | 创建能够复现该行为的最小本地基准测试，但不要凭空设定生产规模 |
| 瓶颈证据 | 现有分析器、追踪、查询诊断、分配工具或操作系统级指标 | 定位 CPU、内存、I/O、锁、查询、网络或调度器开销时 | 使用有针对性的插桩，并制定清理计划 |
| 代码路径和影响范围 | 语言服务器或宿主原生代码智能工具 | 跟踪热点符号、调用方、实现以及受影响的契约时 | 缩小搜索范围，并直接检查定义和使用方 |
| 正确性和回归 | 存储库定义的测试、构建、lint、类型检查和冒烟测试命令 | 每次保留实验之前和之后 | 当现有证据无法检测可能存在的重大回归时，选择最小的组合操作 |
| 运行时和依赖语义 | 与已安装版本匹配的官方文档、发行说明和规范 | 假设依赖于优化器、运行时、数据库、框架或库的行为时 | 进行一手来源的网络研究；否则将该假设标记为 `UNVERIFIED` |
| 独立质询 | 在策略和范围允许时，使用一个原生子代理或顾问 | 存在相互竞争的假设、不熟悉的运行时行为或高风险更改需要独立审查时 | 单独进行对抗性假设审查 |

不要出于审美偏好进行优化，也不要针对与所报告问题不同的工作负载进行基准测试。绝不要丢弃用户更改、使用破坏性的 Git reset，或对生产环境运行不受控的负载。

## 证据规则

- 在编辑之前定义主要指标和验收阈值；不要在看到结果后更改目标。
- 前后对比时使用相同的工作负载、环境、构建模式、数据、预热过程和测量方法。
- 使用多次运行并报告分布或方差；单次更快的运行不能作为证明。
- 当所报告的问题可能发生在多个运行状态时，分别区分冷启动、温热稳定态和饱和负载行为。
- 分别分析性能贡献和端到端影响：热点函数可能得到改善，但面向用户的指标未必改善。
- 将分析器估算值、合成工作负载和生产观测视为不同的证据类别，并进行标注。
- 正确性、资源安全和运行稳定性是硬约束，而非次要指标。

## 检查清单

### 1. 定义问题并保护工作区

- [ ] 明确用户可见的问题、受影响的工作流、目标指标、工作负载、环境、约束条件和验收阈值。
- [ ] 执行工具误用门禁：确认症状确实是性能问题，而不是正确性、配置、容量、依赖或可观测性故障。
- [ ] 阅读仓库说明，检查 Git 状态、分支、未提交更改、被忽略的构件以及可用的隔离机制。
- [ ] 保护用户工作；当更改、基准测试或生成的构件可能造成干扰时，在安全的分支或 worktree 中隔离实验。
- [ ] 建立由本次运行负责的资源清单，记录每个创建的绝对路径、worktree、进程 ID、缓存、性能分析文件和临时构件；绝不要将预先存在的资源登记为清理目标。
- [ ] 确定优化绝不能违反的正确性、安全性、内存、成本、兼容性和运维约束。
- [ ] 定位现有的基准测试、性能分析结果、性能测试、生产环境跟踪数据、服务级别目标以及已知的环境变异性。

### 2. 建立可复现的基线

- [ ] 使用与所观察问题相同类型的指标：延迟分布、吞吐量、CPU、内存、分配、I/O、查询次数、锁等待或其他直接度量。
- [ ] 使工作负载具有代表性并具备足够的确定性以便比较，同时涵盖数据规模、并发度、缓存状态、预热和构建模式。
- [ ] 覆盖可能逆转结论的运行点--至少包括报告中的案例以及相关的数据规模或并发边界--不要凭空设定合成规模。
- [ ] 运行足够多次以暴露噪声，并记录原始结果、中位数或适当的百分位数、离散程度、失败情况和环境详情。
- [ ] 当漂移或噪声具有实质性影响时，交错或随机安排基线运行和候选运行，并优先采用成对比较，而不是先集中运行一组“之前”再集中运行一组“之后”。
- [ ] 在实际可行时，验证基准测试能够检测出有意变慢或明显改变的路径；对行为不敏感的基准测试无法验证优化。
- [ ] 在编辑前运行相关的正确性测试，以免将预先存在的失败归因于实验。
- [ ] 如果无法复现问题，且没有可信的生产环境证据可以定义安全的替代指标，则停止并报告 `BLOCKED`。

### 3. 性能分析并形成假设

- [ ] 在聚焦于某个函数、查询、分配、锁或网络调用之前，先对端到端路径进行性能分析。
- [ ] 建立按成本排序的映射，其中包含测得的贡献、调用频率、可用时的包含成本和独占成本，以及受影响的工作负载。
- [ ] 将最高成本追溯至实现、调用方、数据形态、并发模型、配置和外部依赖。
- [ ] 区分根本瓶颈与下游症状、测量开销、调试构建、冷启动和一次性初始化。
- [ ] 如果性能分析跨越了代码在范围内的服务或进程，则对齐跟踪数据/关联 ID，并沿着测得的下游路径继续追踪；不要将可访问的内部服务标记为“外部”后停在其延迟处。
- [ ] 估算性能分析器或插桩带来的扰动，并在不使用侵入式插桩的情况下确认最终端到端结果。
- [ ] 仅当研究官方运行时、框架、数据库和依赖项的行为能够确认或否定一个具体假设时，才进行相关研究。
- [ ] 在提出自定义缓存、池、调度器、序列化器或数据结构之前，先检查现有平台和依赖项的能力。
- [ ] 编写一组简短且有顺序的假设；对每个假设说明预期的指标变化、作用机制、受影响的文件、风险、依赖关系和验证方式。
- [ ] 驳回缺乏可测量机制、需要臆测规模或无法独立回滚的假设。
- [ ] 当多个相互竞争的解释仍然合理时，寻求独立质询；在修改代码前验证顾问的主张。

### 4. 执行原子化的保留或舍弃实验

- [ ] 将每个高风险假设映射到现有证明以及它可能导致的实质性回归；在已批准的测试范围内实施 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有充分理由的 `NO_TEST`，以生成最小且可信的安全证据，移除已被取代的测试工件，并在触发条件结束时废弃临时特征描述证明。
- [ ] 对于缓存、批处理、并行、池化或重试变更，明确保护快速路径可能破坏的失效、顺序、幂等性、取消、背压、超时和有界资源语义。
- [ ] 应用用于测试单一机制的最小一致变更；仅当多个变更的影响有意地不可分割时，才将其组合。
- [ ] 保持插桩有界、低开销且易于移除；绝不在诊断输出中留下密钥或敏感负载。
- [ ] 在编辑后立即运行有针对性的正确性检查，如果失败则舍弃该实验。
- [ ] 在可比条件下重复执行完全相同的基准测试，并保留原始结果。
- [ ] 检查差异，确认没有意外的清理、无关重构、生成文件变动、调试标志、已更改的基准测试输入或隐藏的配置变更。
- [ ] 仅当约定指标的改善超出噪声范围且所有约束均通过时，才将实验标记为 `KEEP`。
- [ ] 当未达到目标、结果出现回归或安全性变得不确定时，将其标记为 `DISCARD`，并仅回滚该实验。
- [ ] 保留某项变更后，在测试下一个假设前建立新的复合基线。

### 5. 停止、验证并报告

- [ ] 仅当新的测量结果支持另一个假设时才继续；在达到目标、收益递减、安全选项耗尽或缺少前置条件时停止。
- [ ] 在最终保留状态上运行所有相关的完整构建、代码检查、类型检查、测试、冒烟测试、基准测试和运维检查。
- [ ] 仅移除本次运行所拥有的台账条目：验证绝对路径仍位于已批准的临时根目录内，停止准确记录的进程 ID，保留脏的或预先存在的工作树，并有意保留已报告的证据工件。
- [ ] 确认基准测试定义和验收阈值在运行期间未发生漂移。
- [ ] 报告每一个保留和舍弃的假设，而不只是成功路径，以便未来工作不会重复已证伪的实验。
- [ ] 仅当至少有一项保留的变更使约定指标的改善超出噪声范围且所有约束均通过时，才使用 `IMPROVED`；当所有实验均被舍弃且基线已恢复时，使用 `NO_CHANGE`；当缺少安全前置条件、可复现的基线或安全的恢复路径时，使用 `BLOCKED`。
- [ ] 返回包含基线、最终分布、差值、正确性证据、局限性和剩余瓶颈的判定结果。
