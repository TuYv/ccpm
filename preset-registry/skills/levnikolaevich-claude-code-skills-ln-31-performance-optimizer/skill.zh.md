# 性能优化器

**目标：** 只优化经过测量确认的问题。保持正确性，隔离实验，并且仅当可比证据表明某项更改能够改善约定的指标且不会造成不可接受的回归时，才保留该更改。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，只有当其操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回之前，将此技能的裁决、决策和审批规则应用于每个未完成项目，并在回复开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备选方案 |
|---|---|---|---|
| 仓库状态和安全编辑边界 | Git 状态、差异、分支或工作树检查，以及仓库说明 | 在分析性能或编辑之前始终使用 | 如果无法安全隔离用户更改，则停止 |
| 基线和最终指标 | 现有基准测试、负载测试、可复现命令或类生产环境回放 | 指标和工作负载能够反映所报告的问题时 | 创建能够复现该行为的最小本地基准测试，但不要虚构生产规模 |
| 瓶颈证据 | 现有性能分析器、追踪、查询诊断、分配工具或操作系统级指标 | 定位 CPU、内存、I/O、锁、查询、网络或调度器开销时 | 使用有清理计划的针对性插桩 |
| 代码路径和影响范围 | 语言服务器或宿主环境原生的代码智能工具 | 追踪热点符号、调用方、实现和受影响的契约时 | 缩小范围进行搜索，并直接检查定义和使用方 |
| 正确性和回归 | 仓库定义的测试、构建、代码检查、类型检查和冒烟测试命令 | 在每次保留的实验前后 | 当现有证据无法检测可能出现的重大回归时，选择最小的组合验证操作 |
| 运行时和依赖项语义 | 与已安装版本匹配的官方文档、发行说明和规范 | 假设依赖于优化器、运行时、数据库、框架或库的行为时 | 研究第一手网络资料；否则将该假设标记为 `UNVERIFIED` |
| 独立质疑 | 在策略和范围允许时，使用一个原生子代理或顾问 | 存在相互竞争的假设、不熟悉的运行时行为，或高风险更改需要独立审查时 | 单独进行对抗性假设审查 |

不要出于审美偏好进行优化，也不要对与所报告问题不同的工作负载进行基准测试。绝不要丢弃用户更改、使用破坏性的 Git 重置，或对生产环境运行不受控的负载。

## 证据规则

- 在编辑之前定义主要指标和验收阈值；不要在看到结果后改变目标。
- 前后对比时，应使用相同的工作负载、环境、构建模式、数据、预热过程和测量方法。
- 进行多次重复运行，并报告分布或方差；单次运行更快并不能构成证据。
- 当所报告的问题可能出现在多个运行状态时，应分别评估冷启动、预热后的稳态和饱和负载行为。
- 分别分析性能热点的贡献和端到端影响：热点函数的性能可能有所改善，但用户可感知的指标并未改善。
- 将性能分析器估算、合成工作负载和生产环境观测视为不同类别的证据，并明确标注。
- 正确性、资源安全和运维稳定性是硬性约束，而不是次要指标。

## 检查清单

### 1. 定义问题并保护工作区

- [ ] 明确用户可见的问题、受影响的工作流、目标指标、工作负载、环境、约束和验收阈值。
- [ ] 执行错误工具关卡检查：确认症状属于性能问题，而不是正确性、配置、容量、依赖项或可观测性故障。
- [ ] 阅读仓库说明，并检查 Git 状态、分支、未提交的更改、被忽略的产物以及可用的隔离机制。
- [ ] 保护用户的工作；如果更改、基准测试或生成的产物可能造成干扰，请在安全的分支或 worktree 中隔离实验。
- [ ] 建立本次运行专属的资源台账，记录每个创建的绝对路径、worktree、进程 ID、缓存、性能分析数据和临时产物；绝不将预先存在的资源登记为清理目标。
- [ ] 确定任何优化都不得违反的正确性、安全性、内存、成本、兼容性和运维约束。
- [ ] 查找现有的基准测试、性能分析数据、性能测试、生产环境跟踪、服务级别目标以及已知的环境波动。

### 2. 建立可复现的基线

- [ ] 使用与观察到的问题相同的指标类型：延迟分布、吞吐量、CPU、内存、分配、I/O、查询次数、锁等待或其他直接度量。
- [ ] 确保工作负载具有代表性且足够确定，能够用于比较，其中包括数据规模、并发度、缓存状态、预热和构建模式。
- [ ] 覆盖可能导致结论反转的运行点——至少包括报告的问题场景，以及相关的数据规模或并发边界——且不要凭空构造合成规模。
- [ ] 执行足够次数的重复运行以揭示噪声，并记录原始结果、中位数或适当的百分位数、离散程度、失败情况和环境详情。
- [ ] 当漂移或噪声不可忽略时，交错执行或随机安排基线与候选方案的运行顺序，并优先采用配对比较，而不是先集中运行一组“优化前”测试，再集中运行一组“优化后”测试。
- [ ] 在可行的情况下，验证基准测试能够检测出刻意减慢或存在明显变更的路径；对行为不敏感的基准测试无法验证优化。
- [ ] 在编辑前运行相关的正确性测试，以免将预先存在的失败归因于实验。
- [ ] 如果无法复现问题，且没有可信的生产环境证据可用于定义安全的替代测试，则停止并报告 `BLOCKED`。

### 3. 进行性能分析并形成假设

- [ ] 在聚焦于某个函数、查询、分配、锁或网络调用之前，先对端到端路径进行性能分析。
- [ ] 构建按优先级排序的成本图，包含测得的贡献度、调用频率、可获得时的包含成本与独占成本，以及受影响的工作负载。
- [ ] 将成本最高的部分追溯到实现、调用方、数据形态、并发模型、配置和外部依赖项。
- [ ] 区分根本瓶颈与下游症状、测量开销、调试构建、冷启动和一次性初始化。
- [ ] 如果性能分析跨越代码在范围内的服务或进程，请对齐跟踪记录/关联 ID，并沿着测得的下游路径继续追踪；不要将可访问的内部服务标记为“外部”后便止步于其延迟。
- [ ] 估算性能分析器或插桩造成的扰动，并在不使用侵入式插桩的情况下确认最终的端到端结果。
- [ ] 仅当能够确认或否定具体假设时，才研究运行时、框架、数据库和依赖项的官方行为。
- [ ] 在提议自定义缓存、池、调度器、序列化器或数据结构之前，先检查现有的平台与依赖项能力。
- [ ] 编写一组精简且有序的假设；针对每个假设说明预期的指标变化、作用机制、受影响的文件、风险、依赖项和验证方式。
- [ ] 排除缺乏可度量机制、依赖推测性规模或无法独立回滚的假设。
- [ ] 当多个相互竞争的解释仍然合理时，引入独立质疑；在更改代码之前验证顾问提出的主张。

### 4. 执行原子化的保留或丢弃实验

- [ ] 将每个高风险假设映射到现有证明及其可能导致的实质性回归；在批准的测试范围内实施 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有充分理由的 `NO_TEST`，以生成最小且可信的安全性证据，移除已被取代的测试资产，并在临时特征化证明的触发条件结束时将其退役。
- [ ] 对于缓存、批处理、并行化、池化或重试方面的更改，明确保护更快路径可能破坏的失效、顺序、幂等性、取消、背压、超时和资源有界语义。
- [ ] 应用能够测试单一机制的最小一致性更改；仅当多个更改的影响被有意设计为不可分割时，才将它们组合在一起。
- [ ] 确保插桩有明确边界、开销低且易于移除；绝不要在诊断输出中遗留机密或敏感载荷。
- [ ] 编辑后立即运行有针对性的正确性检查；如果检查失败，则丢弃该实验。
- [ ] 在可比条件下重复完全相同的基线基准测试，并保留原始结果。
- [ ] 检查差异中是否存在意外清理、无关重构、生成内容扰动、调试标志、基准测试输入更改和隐藏的配置更改。
- [ ] 仅当约定指标的改进超出噪声范围且所有约束均通过时，才将实验标记为 `KEEP`。
- [ ] 当未达到目标、结果出现回归或安全性变得不确定时，将实验标记为 `DISCARD`，并且只还原该实验。
- [ ] 保留一项更改后，应先建立新的复合基线，再测试下一个假设。

### 5. 停止、验证并报告

- [ ] 仅当新的测量结果支持另一个假设时才继续；在达到目标、收益递减、安全选项耗尽或缺少先决条件时停止。
- [ ] 对最终保留的状态运行所有相关的构建、代码检查、类型检查、测试、冒烟测试、基准测试和运维检查。
- [ ] 仅移除本次运行所拥有的台账条目：验证绝对路径仍位于批准的临时根目录内，停止已准确记录进程 ID 的进程，保留存在未提交更改或预先存在的工作树，并保留有意纳入报告的证据制品。
- [ ] 确认基准测试定义和验收阈值在运行期间未发生偏移。
- [ ] 报告每个保留和丢弃的假设，而不仅仅是成功的路径，以免后续工作重复已被证伪的实验。
- [ ] 仅当至少一项保留的更改使约定指标的改进超出噪声范围且所有约束均通过时，才使用 `IMPROVED`；当所有实验均被丢弃且基线已恢复时，使用 `NO_CHANGE`；当安全性先决条件、可复现的基线或安全的恢复路径不可用时，使用 `BLOCKED`。
- [ ] 返回判定结果以及基线、最终分布、变化量、正确性证据、局限性和剩余瓶颈。
