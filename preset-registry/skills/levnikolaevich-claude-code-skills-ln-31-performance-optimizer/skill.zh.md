# 性能优化器

**目标：** 只优化已测量的问题。保持正确性，隔离实验，并且仅当可比证据表明某项变更能够改善约定指标且不会造成不可接受的回归时，才保留该变更。

**执行契约：** 有序复选框即为完成定义。内部将每一项标记为 `PENDING`、基于具体证据标记为 `PROVEN`、基于证明其条件不存在的证据标记为 `CLEARED`，或因存在缺口标记为 `UNPROVEN`；阅读、委派或工具失败都不构成证明。每完成一个部分后都要重新核对各项。返回前，解决所有 `PENDING` 项，并且只统计 `PROVEN` 和 `CLEARED`；对每个缺口应用该 skill 的裁决和批准规则。
保持用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且会产生重大影响的选择或所需的外部批准进行询问。根据实际风险调整深度，不得默默跳过检查。保持依赖关系和安全顺序；除此之外，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| Repository 状态和安全编辑边界 | Git status、diff、branch 或 worktree 检查，以及 repository instructions | 在 profiling 或 editing 之前始终执行 | 如果无法安全隔离用户变更，则停止 |
| 基线和最终指标 | 现有 benchmark、load test、可复现命令或类似生产环境的 replay | 指标和 workload 能反映所报告的问题时 | 创建能够复现该行为的最小本地 benchmark，不得凭空臆造生产规模 |
| 瓶颈证据 | 现有 profiler、tracing、query diagnostics、allocation 工具或 OS-level metrics | 定位 CPU、内存、I/O、锁、查询、网络或 scheduler 成本时 | 使用有清理计划的定向 instrumentation |
| 代码路径和影响范围 | Language server 或 host-native code intelligence | 跟踪 hot symbols、callers、implementations 以及受影响的 contracts 时 | 通过缩小范围的搜索，并直接检查 definitions 和 consumers |
| 正确性和回归 | repository 定义的 tests、build、lint、type 和 smoke 命令 | 每次保留实验之前和之后 | 当现有证据无法检测可能出现的重大回归时，选择最小的 portfolio action |
| Runtime 和 dependency 语义 | 与已安装版本匹配的官方文档、release notes 和 specifications | 假设依赖 optimizer、runtime、database、framework 或 library 行为时 | 进行 primary-source web research；否则将该假设标记为 `UNVERIFIED` |

不得出于审美偏好进行优化，也不得针对与所报告问题不同的 workload 运行 benchmark。绝不得丢弃用户变更、使用破坏性的 Git reset，或对生产环境运行不受控的 load。

## 证据规则

- 当所报告的问题可能出现在多个 regime 中时，分别区分 cold-start、warm steady-state 和 saturated-load 行为。
- 分别分析 profile contribution 和 end-to-end impact：某个 hot function 得到改善，并不代表用户可见指标也得到改善。
- 将 profiler estimates、synthetic workloads 和 production observations 视为不同的证据类别，并标注其类别。
- 正确性、资源安全和 operational stability 是硬性约束，而不是次要指标。

## 清单

### 1. 定义问题并保护工作区

- [ ] 在编辑前明确用户可见的问题、工作负载、环境、主要指标、总体目标、保留实验所需的最低改进幅度，以及硬性约束。
- [ ] 确认可量化的性能症状，并将其原因与错误结果或缺失的可观测性区分开来。配置、容量和依赖项可能是有效瓶颈；仅在获批范围内修复它们。
- [ ] 阅读仓库说明，并检查 Git 状态、分支、未提交的更改、被忽略的产物以及可用的隔离机制。
- [ ] 当更改、基准测试或生成的产物可能造成干扰时，在安全的分支或工作树中保留用户工作并隔离实验。
- [ ] 启动运行专属的资源台账，记录每个创建的绝对路径、工作树、进程 ID、缓存、性能分析文件和临时产物；绝不将预先存在的资源登记为清理目标。
- [ ] 确定任何优化都不得违反的正确性、安全性、内存、成本、兼容性和运维约束。
- [ ] 定位现有的基准测试、性能分析、性能测试、生产追踪、服务级别目标以及已知的环境波动因素。

### 2. 建立可复现的基线

- [ ] 使用与观察到的问题相同的指标类型：延迟分布、吞吐量、CPU、内存、分配、I/O、查询数、锁等待或其他直接度量。
- [ ] 使工作负载具有代表性并足够确定，以便进行比较，包括数据规模、并发度、缓存状态、预热和构建模式。
- [ ] 覆盖可能推翻结论的运行点——至少包括报告的场景以及相关的数据规模或并发边界——不得臆造合成规模。
- [ ] 选择足以评估实质性噪声的有界比较预算；记录原始结果、适当的中心值或百分位数、离散程度、失败情况和环境。报告无定论的测量结果，而不是重复运行直到出现收益。
- [ ] 当漂移或噪声影响显著时，交错或随机化基线和候选运行，并优先采用配对比较，而不是按“之前”后“之后”分块运行。
- [ ] 在可行时验证基准测试能够检测出有意变慢或明显改变的路径；对行为不敏感的基准测试无法验证优化。
- [ ] 在编辑前运行相关的正确性测试，以免将既有失败归因于实验。
- [ ] 如果无法复现问题，且没有可信的生产证据能够定义安全的代理指标，则停止并报告 `BLOCKED`。

### 3. 性能分析并形成假设

- [ ] 在聚焦某个函数、查询、分配、锁或网络调用之前，先对端到端路径进行性能分析。
- [ ] 建立按优先级排序的成本图，包含测得的贡献、调用频率、可用时的包含成本和独占成本，以及受影响的工作负载。
- [ ] 将最高成本追踪至实现、调用方、数据形态、并发模型、配置和外部依赖项。
- [ ] 区分根本瓶颈与下游症状、测量开销、调试构建、冷启动和一次性初始化。
- [ ] 如果性能分析跨越了代码在范围内的服务或进程，请对齐追踪/关联 ID，并跟踪测得的下游路径；不要将可访问的内部服务标记为“外部”后就止步于其延迟。
- [ ] 估计性能分析器或插桩带来的扰动，并在不使用侵入式插桩的情况下确认最终端到端结果。
- [ ] 仅当能够确认或否定具体假设时，才研究官方运行时、框架、数据库和依赖项的行为。
- [ ] 在提出自定义缓存、池、调度器、序列化器或数据结构之前，检查现有的平台和依赖项能力。
- [ ] 写出一组简短且有序的假设；针对每项说明预期指标变化、机制、受影响文件、风险、依赖项和验证方式。
- [ ] 拒绝缺乏可测量机制、需要推测性规模，或无法独立回滚的假设。

### 4. 执行原子化的保留或丢弃实验

- [ ] 将每个高风险假设映射到现有证明和可能导致的实质性回归；在已批准的测试范围内实施 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有充分理由的 `NO_TEST`，以生成最小且可信的安全证据，移除已被取代的测试材料，并在触发条件结束后退役临时特征化证明。
- [ ] 对于缓存、批处理、并行、池化或重试变更，明确保护失效、顺序、幂等性、取消、背压、超时和有限资源语义，避免这些语义被更快的执行路径破坏。
- [ ] 采用能够测试单一机制的最小一致变更；仅在变更效果有意且不可分割时才将其分组。
- [ ] 保持插桩受限、开销低且易于移除；绝不在诊断输出中留下机密或敏感负载。
- [ ] 在编辑后运行针对性的正确性检查。将失败归因于实验、基线或环境；修复范围受限的实验缺陷并重新检查，或在无法确立正确性时丢弃实验。
- [ ] 在可比条件下重复执行完全相同的基线基准测试，并保留原始结果。
- [ ] 检查差异，确认没有意外的清理、无关重构、生成文件变动、调试标志、已更改的基准测试输入或隐藏的配置变更。
- [ ] 仅当实验达到预先声明的、超出噪声范围的最低改进幅度，且所有硬性约束均通过时，才标记为 `KEEP`。
- [ ] 当未达到保留阈值、结果出现回归或安全性变得不确定时，标记为 `DISCARD`，并且仅还原该实验；观察到结果后绝不降低阈值。
- [ ] 保留某项变更后，在测试下一个假设前建立新的复合基线。

### 5. 停止、验证并报告

- [ ] 仅当新的测量结果支持另一个假设时才继续；在达到约定目标、收益递减、安全选项耗尽或缺少前置条件时停止；明确报告是否达到目标。
- [ ] 确认构建、lint、类型、测试、冒烟测试、基准测试和运维证据覆盖最终保留状态及所有必需的门禁。复用该状态已有的通过证据；仅在后续变更或未解决的失败使其失效时重新运行检查。
- [ ] 仅移除本次运行所拥有的账本条目：验证绝对路径仍位于已批准的临时根目录内，停止准确记录的进程 ID，保留有修改或预先存在的工作树，并保留已明确报告的证据工件。
- [ ] 确认基准测试定义和验收阈值在运行期间没有发生偏移。
- [ ] 将假设账本与保留的编辑及原始结果进行核对，包括已丢弃的实验。
- [ ] 仅当至少有一项保留的变更使约定指标在超出噪声范围的情况下得到改进，且所有约束均通过时，才使用 `IMPROVED`；当所有实验均被丢弃且基线已恢复时，使用 `NO_CHANGE`；当安全前置条件、可复现的基线或安全的恢复路径不可用时，使用 `BLOCKED`。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论及适用的清理工作。修正报告或已获授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。简短结果可以每个字段一行；省略空表格，不要复制已链接的产物：

1. **结果：** 特定于 Skill 的结论及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 下方特定于 Skill 的字段；区分事实、推论和未经验证的声明。链接产物；适用时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项目的原因、对结果的影响和确切的下一步操作；剩余风险和所需决策。

**特定于 Skill 的证据：** 目标工作负载、指标、验收阈值、正确性约束、环境、采样和方差方法；可比较的基线/最终分布及差异。记录每个假设、机制、`KEEP / DISCARD`、测量结果和验证。包括受影响测试组合的操作、剩余瓶颈，以及运行所属的原始样本、命令、配置、最终差异和清理证据，并在可用时提供路径/哈希。
