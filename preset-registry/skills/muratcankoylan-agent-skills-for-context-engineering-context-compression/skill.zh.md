# 上下文压缩策略

当智能体会话生成数百万 token 的对话历史时，压缩就成为必需。朴素的方法是进行激进压缩，以尽量减少每次请求的 token 数量。正确的优化目标是每项任务的 token 数量：完成一项任务所消耗的 token 总量，包括压缩丢失关键信息时重新获取信息的成本。

## 何时启用

在以下情况下启用此技能：
- 智能体会话超出上下文窗口限制
- 代码库超出上下文窗口容量（拥有 5M+ token 的系统）
- 设计对话摘要策略
- 调试智能体“忘记”自己修改过哪些文件的情况
- 构建用于评估压缩质量的框架
- 创建可持久保存的交接摘要，保留决策、文件、风险和后续行动

对于由其他技能负责的相邻工作，请勿启用此技能：
- 掩码、前缀缓存或分区等通用 token 效率策略：`context-optimization`。
- 在选择缓解措施之前，诊断长上下文失败的原因：`context-degradation`。
- 将原始输出、日志或计划写入文件而不进行摘要：`filesystem-context`。
- 设计跨会话的长期语义记忆：`memory-systems`。

## 核心概念

上下文压缩是在节省 token 与信息丢失之间进行权衡。请根据会话特征，从以下三种生产就绪的方法中进行选择：

1. **锚定式迭代摘要**：对于文件跟踪至关重要的长期运行会话，请采用此方法。维护结构化、持久化的摘要，并为会话意图、文件修改、决策和后续步骤设置明确的章节。触发压缩时，仅对新近被截断的内容片段进行摘要，并将其与现有摘要合并，而不是从头重新生成。这可以防止整体重新生成摘要时不断累积的偏移——每次重新生成都可能丢失模型认为优先级较低、但任务实际需要的细节。结构化设计能强制保留信息，因为专门设置的章节就像摘要器必须填写的检查清单，可以捕捉不易察觉的信息丢失。

2. **不透明压缩**：仅将此方法用于重新获取信息成本较低、且需要最大限度节省 token 的短会话。它会生成针对重建保真度进行优化的压缩表示，压缩率可达 99% 以上，但会完全牺牲可解释性。这种权衡很重要：如果不运行基于探针的评估，就无法验证哪些内容得到了保留，因此在调试或工件跟踪至关重要时，绝不要使用此方法。

3. **再生成式完整摘要**：当摘要可读性至关重要，且会话具有明确的阶段边界时，请使用此方法。它会在每次触发压缩时生成详细的结构化摘要。其弱点是在反复循环中会累积性地丢失细节——每次完整重新生成都是一次全新的处理过程，可能会降低早期摘要中已保留细节的优先级。

## 详细主题

### 优化每项任务的 Token 数量，而非每次请求的 Token 数量

衡量从任务开始到完成所消耗的 token 总量，而不是单个请求所消耗的 token 数量。当压缩丢失文件路径、错误消息或决策依据时，代理必须重新探索、重新读取文件并重新推导结论——浪费的 token 远多于压缩所节省的 token。某种策略即使每个请求能多节省 0.5% 的 token，但如果导致重新获取信息的成本增加 20%，那么总体成本反而更高。将重新获取信息的频率作为首要质量信号：如果代理反复要求重新读取已经处理过的文件，说明压缩过于激进。

### 首先解决制品轨迹问题

制品轨迹完整性通常是压缩评估中最薄弱的维度（claim-context-compression-factory-benchmark）。应主动解决这一问题，因为通用摘要无法可靠地保持这种完整性。

在每次压缩周期中明确保留以下类别：
- 创建了哪些文件（完整路径）
- 修改了哪些文件以及做了哪些更改（包括函数名，而不仅仅是文件名）
- 读取了哪些文件但未做更改
- 具体标识符：函数名、变量名、错误消息、错误代码

在代理脚手架中实现独立的制品索引或明确的文件状态跟踪，而不是依赖摘要器捕获这些详细信息。即使是带有专用文件章节的结构化摘要，在长会话中也难以保证完整性。

### 使用必填章节组织摘要

使用明确的章节构建结构化摘要，以防止信息在无提示的情况下丢失。每个章节都相当于一份摘要器必须填写的检查清单，使遗漏变得可见，而不是悄无声息地发生。

```markdown
## Session Intent
[What the user is trying to accomplish]

## Files Modified
- auth.controller.ts: Fixed JWT token generation
- config/redis.ts: Updated connection pooling
- tests/auth.test.ts: Added mock setup for new config

## Decisions Made
- Using Redis connection pool instead of per-request connections
- Retry logic with exponential backoff for transient failures

## Current State
- 14 tests passing, 2 failing
- Remaining: mock setup for session service tests

## Next Steps
1. Fix remaining test failures
2. Run full test suite
3. Update documentation
```

根据代理的领域调整章节。调试代理需要“根本原因”和“错误消息”；迁移代理需要“源模式”和“目标模式”。结构比具体章节更重要——任何明确的模式都优于自由形式的摘要。

### 有策略地选择压缩触发时机

何时触发压缩与如何压缩同样重要。根据会话的可预测性选择触发策略：

| 策略 | 触发点 | 权衡 |
|----------|---------------|-----------|
| 固定阈值 | 上下文利用率达到 70-80% | 简单，但可能过早压缩 |
| 滑动窗口 | 保留最近 N 轮对话和摘要 | 上下文大小可预测 |
| 基于重要性 | 优先压缩相关性较低的部分 | 复杂，但能保留关键信息 |
| 任务边界 | 在逻辑任务完成时压缩 | 摘要清晰，但触发时机不可预测 |

对于编码智能体，默认采用带结构化摘要的滑动窗口——它在可预测性与质量之间提供了最佳平衡。当会话存在清晰的阶段转换时（例如，先研究，再实现，然后测试），使用任务边界触发机制。

### 使用探针而非指标评估压缩

ROUGE 或嵌入相似度等传统指标无法衡量功能性压缩的质量。摘要可能在词汇重合度上得分很高，却遗漏了智能体继续工作所需的唯一一个文件路径。

使用基于探针的评估：压缩后，提出能够检验关键信息是否得到保留的问题。如果智能体回答正确，则说明压缩保留了正确的信息。否则，它就会进行猜测或产生幻觉。

| 探针类型 | 测试内容 | 示例问题 |
|------------|---------------|------------------|
| 回忆 | 事实保留情况 | “最初的错误消息是什么？” |
| 工件 | 文件跟踪情况 | “我们修改了哪些文件？” |
| 继续执行 | 任务规划 | “接下来我们应该做什么？” |
| 决策 | 推理链 | “关于 Redis 问题，我们做出了什么决定？” |

### 从六个维度评估压缩

从以下维度评估面向编码智能体的压缩质量。准确性和工件轨迹保留能力通常比词汇相似度更能清晰地区分不同方法（claim-context-compression-factory-benchmark），因此压缩需要采用不同于通用摘要的专门处理方式。

1. **准确性**：技术细节是否正确——包括文件路径、函数名称、错误代码？
2. **上下文感知**：响应是否反映了当前的对话状态？
3. **工件轨迹**：智能体是否知道读取或修改了哪些文件？
4. **完整性**：响应是否涵盖了问题的所有部分？
5. **连续性**：是否无需重新获取信息即可继续工作？
6. **指令遵循**：响应是否遵守了明确说明的约束？

## 实用指南

### 对大型代码库应用三阶段压缩工作流

对于超出上下文窗口容量的代码库或智能体系统，通过三个连续阶段进行压缩。每个阶段都会缩小上下文范围，使下一阶段能够在预算内运行。

1. **研究阶段**：探索架构图、文档和关键接口。将探索结果压缩为一份关于组件、依赖关系和边界的结构化分析。输出：一份取代原始探索内容的研究文档。

2. **规划阶段**：将研究文档转换为包含函数签名、类型定义和数据流的实现规范。在此阶段，一个包含 5M 个 token 的代码库可压缩为约 2,000 字的规范。

3. **实现阶段**：按照规范执行。上下文始终聚焦于规范和当前正在处理的文件，而非原始的代码库探索内容。由于规范已经足够精简，此阶段很少需要进一步压缩。

### 使用示例工件作为压缩种子

当获得手动迁移示例或参考 PR 时，应将其作为模板来理解目标模式，而不是从头开始探索代码库。示例能够揭示静态分析无法发现的约束：必须维持哪些不变量、哪些服务会因变更而出现故障，以及简洁的实现应是什么样子。

当智能体无法区分本质复杂性（业务需求）与偶然复杂性（遗留的变通方案）时，这一点尤为重要。示例工件隐式地编码了这种区别，从而节省了原本会消耗在反复试错探索上的 token。

### 逐步实现锚定式迭代摘要

1. 定义与智能体领域（调试、迁移、功能开发）相匹配的明确摘要章节
2. 首次触发压缩时，将被截断的历史记录汇总到这些章节中
3. 后续触发压缩时，仅汇总新被截断的内容——不要重新汇总现有摘要
4. 将新信息合并到现有章节中，而不是重新生成这些章节，并按照文件路径和决策标识进行去重
5. 标记每项信息来自哪个压缩周期——这有助于在摘要发生偏移时进行调试

### 根据会话特征选择合适的方法

**在以下情况下使用锚定式迭代摘要：**
- 会话持续时间较长（100 条以上消息）
- 文件跟踪很重要（编码、调试）
- 需要验证信息是否得到保留

**在以下情况下使用不透明压缩：**
- 需要最大程度地节省 token
- 会话相对较短
- 重新获取信息的成本较低（例如，无需访问文件系统）

**在以下情况下使用再生成式摘要：**
- 摘要的可解释性对于人工审查至关重要
- 会话具有明确的阶段边界
- 每次触发压缩时都可以接受完整的上下文审查

### 按方法校准压缩率

| 方法 | 压缩率 | 质量评分 | 权衡 |
|--------|-------------------|---------------|-----------|
| 锚定式迭代摘要 | 98.6% | 3.70 | 质量最佳，压缩率略低 |
| 再生成式摘要 | 98.7% | 3.44 | 质量良好，压缩率适中 |
| 不透明压缩 | 99.3% | 3.35 | 压缩率最佳，但质量有所损失 |

请将这些数据用作特定来源的基准指标，而不是通用常量（claim-context-compression-factory-benchmark）。对于任何存在重新获取信息成本的任务，这种权衡通常更有利于结构化方法。

## 示例

**示例 1：调试会话压缩**

原始上下文（89,000 个 token，178 条消息）：
- /api/auth/login 端点出现 401 错误
- 追踪了身份验证控制器、中间件和会话存储
- 发现过期的 Redis 连接
- 修复了连接池并添加了重试逻辑
- 14 项测试通过，2 项失败

压缩后的结构化摘要：

```markdown
## Session Intent
Debug 401 Unauthorized error on /api/auth/login despite valid credentials.

## Root Cause
Stale Redis connection in session store. JWT generated correctly but session could not be persisted.

## Files Modified
- auth.controller.ts: No changes (read only)
- middleware/cors.ts: No changes (examined)
- config/redis.ts: Fixed connection pooling configuration
- services/session.service.ts: Added retry logic for transient failures
- tests/auth.test.ts: Updated mock setup

## Test Status
14 passing, 2 failing (mock setup issues)

## Next Steps
1. Fix remaining test failures (mock session service)
2. Run full test suite
3. Deploy to staging
```

**示例 2：探测响应质量**

压缩后，询问“原始错误是什么？”：

良好响应（结构化摘要）：
> “原始错误是来自 /api/auth/login 端点的 401 Unauthorized 响应。用户使用有效凭据时收到了此错误。根本原因是会话存储中的 Redis 连接已失效。”

较差响应（激进压缩）：
> “我们当时正在调试一个身份验证问题。登录失败了。我们修复了一些配置问题。”

结构化响应保留了端点、错误代码和根本原因。激进压缩则丢失了所有技术细节。

## 指南

1. 优化每项任务的 token 数，而不是每次请求的 token 数
2. 使用带有明确文件跟踪部分的结构化摘要
3. 在上下文利用率达到 70-80% 时触发压缩
4. 实施增量合并，而不是完整重新生成
5. 使用基于探测的评估来测试压缩质量
6. 如果文件跟踪至关重要，请单独跟踪产物轨迹
7. 接受略低的压缩率，以更好地保留质量
8. 将重新获取信息的频率作为压缩质量信号进行监控

## 注意事项

1. **切勿压缩工具定义或模式**：压缩函数调用模式、API 规范或工具定义会彻底破坏智能体的功能。参数名称或类型一旦在摘要中丢失，智能体就无法调用相应工具。应将工具定义视为绕过压缩的不可变锚点。

2. **压缩摘要会产生事实幻觉**：当 LLM 总结对话历史时，可能会引入原文中从未出现过但听起来合理的细节。在丢弃原始内容之前，务必对照源材料验证压缩后的输出——尤其是文件路径、错误代码和数值，因为摘要器可能会对它们进行“取整”或凭空捏造。

3. **压缩会破坏产物引用**：文件路径、提交 SHA、变量名和代码片段在压缩过程中可能会被改写或丢弃。如果智能体需要的是 `config/redis.ts`，而摘要只写着“更新了配置文件”，就会导致重新探索。应在专门的部分中逐字保留标识符，而不是将其嵌入叙述性文本中。

4. **早期轮次包含不可替代的约束**：会话的最初几个轮次通常包含任务设置、用户约束和无法重新推导的架构决策。应保护早期轮次不被压缩，或将其中的约束提取到一个能在所有压缩周期中保留的持久前言中。

5. **激进压缩率会在多个周期中造成复合损失**：95% 的压缩率单独应用一次时似乎很安全，但重复应用会使损失不断累积。以 95% 的压缩率执行三个周期后，原始 token 仅剩 0.0125%。校准压缩率时，应以多个压缩周期为前提，而不是只考虑单次压缩。

6. **代码和正文需要采用不同的压缩方式**：正文具有自然语言冗余，因此容易压缩。代码则不然——从函数签名或导入路径中删除一个 token，就可能使其失去作用。应采用特定于领域的压缩策略：激进地总结正文部分，同时逐字保留代码块和结构化数据。

7. **基于探针的评估会带来虚假的信心**：即使关键信息已经丢失，探针仍可能通过，因为探针只测试其明确询问的内容。只检查文件名而不检查函数签名的探针集会遗漏签名丢失问题。应设计覆盖全部六个评估维度的探针，并在不同评估运行中轮换探针集，以避免盲区。

## 集成

此技能与集合中的其他多个技能相关联：

- context-degradation - 压缩是缓解退化的一种策略
- context-optimization - 压缩是众多优化技术之一
- evaluation - 基于探针的评估适用于压缩测试
- memory-systems - 压缩与暂存区和摘要记忆模式相关
