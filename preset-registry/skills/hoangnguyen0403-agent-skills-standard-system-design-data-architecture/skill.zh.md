# 数据架构

## **优先级：P1（高）**

访问模式决定存储选型。所有权先于 schema。最后再分片，而不是一开始就分片。

## 存储选型

1. 列出每一种读写访问模式，以及其 QPS、延迟目标和一致性需求。
2. 默认使用关系型存储。在某种特定模式证明关系型存储无法满足需求之前，都应优先选择它。
3. 只有当关系型存储无法满足某个明确的访问模式时，才将该模式迁移到专用存储：热查询使用键值存储，海量有序写入使用宽列存储，schema 多变的聚合数据使用文档存储，多跳遍历使用图存储，文本和 facet 使用搜索索引，二进制对象使用对象存储。
4. 每增加一种存储，就会带来同步延迟、双写风险，以及一个额外的运维界面。必须说明其必要性。
5. 二进制对象绝不能存放在主数据库中；应将字节存储在对象存储中，并只保留其引用。

## 所有权与一致性

- 每个实体由一个写入方负责。跨服务读取应使用 API 或事件流，绝不能共享表。
- 在选择复制方式之前，先对每条流程进行分类：资金、库存和身份需要强一致性；信息流、计数器和分析可以容忍最终一致性。
- 只读副本只能用于读取，并且副本延迟对用户是可见的。将读后写请求路由到主库，或固定会话到主库。
- 服务之间的跨实体原子性需要使用带补偿操作的 saga，而不是分布式事务。

## 扩展顺序

按以下顺序执行，并在容量余量足够时立即停止：先修复索引和查询，然后使用只读副本，
再使用缓存，然后进行纵向扩展，接着对冷数据分区或归档，最后再分片。分片应放在最后，
因为它会带来跨分片查询、重新平衡，以及对分区键的永久性承诺。

## 分区

- 选择具有高基数、出现在最热点查询中且分布均匀的分区键。
- 哈希分区可以分散负载，但会破坏范围扫描；范围分区可以保留扫描能力，但在按时间排序的键上会产生不断移动的热点分区。
- 通过对键加盐、复制记录，或从专用缓存中提供服务，来缓解 **名人键** 问题。
- 在上线前规划重新分片：将虚拟桶映射到物理分片，这样无需重写键即可移动桶。

## 反模式

- **不要过早分片**：一个 QPS 为 300 的未建立索引查询，不是分片问题。
- **服务之间不要共享数据库**：这会无声地耦合部署生命周期和 schema 生命周期。
- **没有对账机制就不要双写**：使用事件日志或 CDC，然后进行对账。
- **不要让表无界增长**：在设计阶段就定义保留策略、归档层级和删除机制。
- **没有更新路径就不要反规范化**：每份副本都需要一个所有者和一个刷新触发器。

## 验证

- [ ] 每种访问模式都恰好映射到一种存储，并说明了理由
- [ ] 为每个实体指定了唯一写入方
- [ ] 为每条流程声明了一致性类别
- [ ] 选择了分区键，并制定了热点分区缓解措施
- [ ] 定义了保留策略和归档方案
