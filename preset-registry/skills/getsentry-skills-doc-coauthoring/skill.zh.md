# 文档协作撰写工作流

此技能提供一套结构化工作流，用于引导用户协作创建文档。你应作为积极主动的引导者，带领用户完成三个阶段：上下文收集、完善与结构化，以及读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到撰写文档："write a doc"、"draft a proposal"、"create a spec"、"write up"
- 用户提到特定的文档类型："PRD"、"design doc"、"decision doc"、"RFC"
- 用户似乎正准备开始一项较为复杂的写作任务

**初始提议：**
向用户提议采用结构化工作流来协作撰写文档。说明以下三个阶段：

1. **上下文收集**：用户提供所有相关背景信息，同时 Claude 提出澄清问题
2. **完善与结构化**：通过头脑风暴和编辑，迭代构建每个章节
3. **读者测试**：使用一个全新的 Claude（没有上下文）测试文档，以便在其他人阅读之前发现盲点

说明这种方法有助于确保其他人在阅读文档时能够很好地理解它（包括他们将文档粘贴到 Claude 中时）。询问用户是否想尝试此工作流，还是更愿意采用自由形式开展工作。

如果用户拒绝，则采用自由形式开展工作。如果用户接受，则进入阶段 1。

## 阶段 1：上下文收集

**目标：** 缩小用户已知信息与 Claude 已知信息之间的差距，以便后续提供有针对性的指导。

### 初始问题

首先询问用户有关文档的元上下文：

1. 这是什么类型的文档？（例如技术规范、决策文档、提案）
2. 主要受众是谁？
3. 你希望读者阅读后产生什么变化或采取什么行动？
4. 是否需要遵循某个模板或特定格式？
5. 是否还有其他需要了解的约束或背景信息？

告知用户可以使用简短表述作答，也可以按照最适合自己的方式一次性提供所有信息。

**如果用户提供了模板或提到某种文档类型：**
- 询问他们是否有可分享的模板文档
- 如果他们提供了共享文档的链接，使用适当的集成来获取该文档
- 如果他们提供了文件，则读取该文件

**如果用户提到要编辑现有的共享文档：**
- 使用适当的集成读取文档的当前状态
- 检查是否有缺少替代文本的图片
- 如果存在缺少替代文本的图片，应说明当其他人使用 Claude 理解该文档时，Claude 将无法看到这些图片。询问他们是否希望生成替代文本。如果希望生成，请他们将每张图片粘贴到聊天中，以便生成描述性的替代文本。

### 信息倾倒

回答完初始问题后，鼓励用户倾倒他们掌握的所有上下文。请求提供以下信息：
- 项目/问题的背景
- 相关的团队讨论或共享文档
- 未采用其他解决方案的原因
- 组织背景（团队动态、过往事件、内部关系）
- 时间压力或限制
- 技术架构或依赖项
- 利益相关者的顾虑

建议他们不必担心如何组织信息——只需把所有内容都说出来。提供多种提交上下文的方式：
- 以意识流方式倾倒信息
- 指向需要阅读的团队频道或讨论串
- 提供共享文档的链接

**如果有可用的集成**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），请提及可以使用这些集成直接获取上下文。

**如果未检测到任何集成，并且用户正在使用 Claude.ai 或 Claude app：** 建议他们在 Claude 设置中启用连接器，以便直接从消息应用和文档存储中获取上下文。

告知他们，完成初步的信息倾倒后，将向他们提出澄清问题。

**在收集上下文期间：**

- 如果用户提到团队频道或共享文档：
  - 如果有可用的集成：告知他们现在将读取相关内容，然后使用适当的集成
  - 如果没有可用的集成：说明无法访问。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提到未知的实体/项目：
  - 询问是否应搜索已连接的工具来了解更多信息
  - 等待用户确认后再进行搜索

- 随着用户提供上下文，持续记录已经了解到的内容和尚不明确的内容

**提出澄清问题：**

当用户表示已完成初步的信息倾倒时（或在已经提供大量上下文后），提出澄清问题以确保理解准确：

根据上下文中的空白，生成 5-10 个带编号的问题。

告知他们可以使用简写作答（例如，“1: yes, 2: see #channel, 3: no because backwards compat”），也可以链接到更多文档、指出需要阅读的频道，或者继续倾倒信息。采用对他们而言最高效的方式即可。

**退出条件：**
当提出的问题能够体现出对上下文的理解时，即已收集到足够的上下文——此时无需再解释基础内容，就能询问边界情况和权衡取舍。

**过渡：**
询问他们现阶段是否还有更多上下文想要提供，还是该继续起草文档了。

如果用户想补充更多内容，就让他们继续。准备好后，进入阶段 2。

## 阶段 2：完善与结构设计

**目标：** 通过头脑风暴、筛选和迭代完善，逐节构建文档。

**给用户的说明：**
说明文档将逐节构建。对于每个章节：
1. 将提出澄清问题，了解应包含哪些内容
2. 将通过头脑风暴提出 5-20 个选项
3. 用户将指出要保留/删除/合并的内容
4. 将起草该章节
5. 将通过精细修改对其进行完善

从未知项最多的章节开始（通常是核心决策/提案），然后再处理其余章节。

**章节顺序：**

如果文档结构已经明确：
询问他们想从哪个章节开始。

建议从未知项最多的章节开始。对于决策文档，通常是核心提案。对于规范，通常是技术方案。总结性章节最好留到最后。

如果用户不知道需要哪些章节：
根据文档类型和模板，建议 3-5 个适合该文档类型的章节。

询问他们是否认可该结构，或者是否想对其进行调整。

**结构达成一致后：**

创建初始文档结构，并为所有章节添加占位文本。

**如果可以访问工件：**
使用 `create_file` 创建工件。这样 Claude 和用户就有了一个可以共同完善的框架。

告知用户将创建包含所有章节占位文本的初始结构。

创建包含所有章节标题和简短占位文本（如“[待撰写]”或“[在此填写内容]”）的工件。

提供框架链接，并说明现在可以开始逐一填写各章节。

**如果无法访问工件：**
在工作目录中创建一个 markdown 文件。为其指定合适的名称（例如 `decision-doc.md`、`technical-spec.md`）。

告知用户将创建包含所有章节占位文本的初始结构。

创建包含所有章节标题和占位文本的文件。

确认已创建该文件，并说明现在可以开始逐一填写各章节。

**对于每个章节：**

### 第 1 步：澄清问题

说明将开始处理 [SECTION NAME] 章节。针对应包含的内容提出 5-10 个澄清问题：

根据上下文和章节目的，生成 5-10 个具体问题。

告知用户可以简要回答，也可以只指出需要重点涵盖的内容。

### 第 2 步：头脑风暴

针对 [SECTION NAME] 章节，根据章节的复杂程度，构思 [5-20] 项可能包含的内容。重点寻找：
- 之前分享过但可能已被遗忘的背景信息
- 尚未提及的角度或考量

根据章节复杂程度，生成 5-20 个带编号的选项。最后说明，如果用户需要更多选项，可以继续进行头脑风暴。

### 第 3 步：筛选

询问哪些要点应保留、删除或合并。请用户提供简短理由，以帮助了解其优先级，从而更好地处理后续章节。

提供示例：
- “保留 1、4、7、9”
- “删除 3（与 1 重复）”
- “删除 6（受众已经知道这一点）”
- “合并 11 和 12”

**如果用户给出自由形式的反馈**（例如“看起来不错”或“我喜欢其中大部分，不过……”），而不是按编号进行选择，则提取其偏好并继续。解析他们希望保留、删除或更改的内容，并据此处理。

### 第 4 步：缺口检查

根据用户选择的内容，询问 [SECTION NAME] 章节是否还遗漏了任何重要内容。

### 第 5 步：起草

使用 `str_replace` 将该章节的占位文本替换为实际起草的内容。

说明现在将根据用户选择的内容起草 [SECTION NAME] 章节。

**如果使用工件：**
起草完成后，提供工件链接。

请用户通读内容并指出需要修改之处。说明反馈越具体，就越有助于了解其偏好并处理后续章节。

**如果使用文件（无工件）：**
起草完成后，确认该章节已完成。

告知用户已在 [filename] 中起草完成 [SECTION NAME] 章节。请用户通读内容并指出需要修改之处。说明反馈越具体，就越有助于了解其偏好并处理后续章节。

**给用户的关键说明（起草第一个章节时包含）：**
添加一条说明：不要直接编辑文档，而是请用户指出需要修改的内容。这有助于了解其风格，以便处理后续章节。例如：“删除 X 项——Y 中已经涵盖”或“让第三段更简洁”。

### 第 6 步：迭代完善

随着用户提供反馈：
- 使用 `str_replace` 进行编辑（绝不要重新输出整篇文档）
- **如果使用工件：** 每次编辑后提供工件链接
- **如果使用文件：** 只需确认编辑已完成
- 如果用户直接编辑文档并要求阅读：在心里记下他们所做的更改，并在后续章节中牢记这些更改（这体现了他们的偏好）

**继续迭代**，直到用户对该章节感到满意。

### 质量检查

连续迭代 3 次均无实质性更改后，询问是否可以删除某些内容而不丢失重要信息。

章节完成后，确认 [SECTION NAME] 已完成。询问是否准备好进入下一章节。

**对所有章节重复此流程。**

### 接近完成

当接近完成时（80% 以上的章节已完成），宣布打算重新通读整篇文档，并检查：
- 各章节之间的行文衔接和一致性
- 重复或矛盾之处
- 任何让人感觉像“水文”或泛泛填充内容的部分
- 是否每句话都言之有物

通读整篇文档并提供反馈。

**当所有章节均已起草并完善后：**
宣布所有章节均已完成起草。说明打算再完整审阅一次文档。

审查整体连贯性、行文衔接和完整性。

提供所有最终建议。

询问是否准备好进入读者测试，或者是否还想完善其他内容。

## 阶段 3：读者测试

**目标：** 使用一个全新的 Claude（无上下文干扰）测试文档，以验证它对读者是否有效。

**给用户的说明：**
解释现在将进行测试，以了解该文档对读者是否真正有效。这可以发现盲点——有些内容对作者而言很清楚，但可能会让其他人感到困惑。

### 测试方法

**如果可以访问子代理（例如在 Claude Code 中）：**

直接执行测试，无需用户参与。

### 第 1 步：预测读者问题

宣布打算预测读者在尝试发现这篇文档时可能会提出哪些问题。

生成 5–10 个读者实际可能提出的问题。

### 第 2 步：使用子代理进行测试

宣布将使用一个全新的 Claude 实例（不包含本次对话的任何上下文）测试这些问题。

对于每个问题，仅将文档内容和该问题提供给子代理。

总结阅读者 Claude 对每个问题回答正确和错误的地方。

### 第 3 步：执行额外检查

宣布将执行额外检查。

调用子代理检查歧义、错误假设和矛盾。

总结发现的所有问题。

### 第 4 步：报告并修复

如果发现问题：
报告阅读者 Claude 在哪些具体问题上遇到了困难。

列出具体问题。

说明打算修复这些缺漏。

返回有问题的章节并继续完善。

---

**如果无法访问子代理（例如在 claude.ai Web 界面中）：**

用户需要手动进行测试。

### 第 1 步：预测读者问题

询问人们在尝试发现这篇文档时可能会提出哪些问题。他们会在 Claude.ai 中输入什么？

生成 5-10 个读者实际可能会提出的问题。

### 第 2 步：设置测试

提供测试说明：
1. 打开一个全新的 Claude 对话：https://claude.ai
2. 粘贴或共享文档内容（如果使用已启用连接器的共享文档平台，请提供链接）
3. 向读者 Claude 提出生成的问题

对于每个问题，要求读者 Claude 提供：
- 答案
- 是否有任何含糊或不清楚之处
- 文档假定读者已经具备哪些知识/背景

检查读者 Claude 是否给出了正确答案，或是否误解了任何内容。

### 第 3 步：附加检查

还要询问读者 Claude：
- “本文档中有哪些内容可能会让读者感到含糊或不清楚？”
- “本文档假定读者已经具备哪些知识或背景？”
- “是否存在任何内部矛盾或不一致之处？”

### 第 4 步：根据结果迭代

询问读者 Claude 哪些内容答错了或理解起来有困难。表明打算修复这些缺口。

针对任何存在问题的章节，返回优化环节。

---

### 退出条件（两种方法均适用）

当读者 Claude 能够持续正确回答问题，并且不再发现新的缺口或歧义时，文档即可就绪。

## 最终审阅

当读者测试通过后：
宣布文档已通过读者 Claude 测试。完成前：

1. 建议用户亲自进行最后一次通读——他们是这份文档的负责人，也要对其质量负责
2. 建议再次核对所有事实、链接或技术细节
3. 请用户确认文档是否达到了他们期望的效果

询问他们是否还需要再审阅一次，或者工作是否已经完成。

**如果用户希望进行最终审阅，请执行审阅。否则：**
宣布文档已完成。提供几条最终建议：
- 考虑在附录中链接此对话，以便读者了解文档的开发过程
- 使用附录提供更深入的内容，避免主文档过于冗长
- 根据真实读者的反馈持续更新文档

## 有效指导的技巧

**语气：**
- 直接且注重流程
- 当理由会影响用户行为时，简要解释
- 不要试图“推销”这种方法——直接执行即可

**处理偏离流程的情况：**
- 如果用户想跳过某个阶段：询问他们是否想跳过此阶段并自由编写
- 如果用户显得沮丧：承认这比预期花费了更长时间。建议加快进度的方法
- 始终给予用户调整流程的自主权

**上下文管理：**
- 在整个过程中，如果提到的某项内容缺少上下文，应主动询问
- 不要让信息缺口不断累积——出现时就及时处理

**产物管理：**
- 使用 `create_file` 起草完整章节
- 所有编辑均使用 `str_replace`
- 每次更改后提供产物链接
- 切勿使用产物来记录头脑风暴列表——这类内容只需保留在对话中

**质量优先于速度：**
- 不要匆忙完成各个阶段
- 每次迭代都应带来有意义的改进
- 目标是产出一份真正对读者有效的文档
