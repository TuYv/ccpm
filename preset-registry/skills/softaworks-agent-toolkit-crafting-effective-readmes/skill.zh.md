# 编写有效的 README

## 概述

README 的作用是回答受众可能会有的问题。不同的受众需要不同的信息——OSS 项目的贡献者所需的背景信息，与未来的你打开一个配置文件夹时所需的并不相同。

**始终要问：**谁会阅读这份文档，他们需要知道什么？

## 流程

### 第 1 步：确定任务

**询问：**“你正在进行哪项 README 任务？”

| 任务 | 适用场景 |
|------|------|
| **创建** | 新项目，尚无 README |
| **新增** | 需要记录新的内容 |
| **更新** | 功能已变化，内容已过时 |
| **审查** | 检查 README 是否仍然准确 |

### 第 2 步：针对具体任务的问题

**创建初始 README：**
1. 项目属于什么类型？（参见下文“项目类型”）
2. 用一句话概括：它解决了什么问题？
3. 达到“能跑起来”的最快路径是什么？
4. 有什么值得特别指出的亮点吗？

**新增一个章节：**
1. 需要记录什么内容？
2. 它应放在现有结构中的哪个位置？
3. 谁最需要这些信息？

**更新现有内容：**
1. 哪些内容发生了变化？
2. 阅读当前 README，找出过时的章节
3. 提出具体的修改建议

**审查/刷新：**
1. 阅读当前 README
2. 对照项目的实际状态进行检查（package.json、主要文件等）
3. 标记过时的章节
4. 如有“最后审查”日期，则更新

### 第 3 步：始终要问

起草完成后，询问：**“还有什么需要突出或包含、而我可能遗漏的内容吗？”**

## 项目类型

| 类型 | 受众 | 关键章节 | 模板 |
|------|----------|--------------|----------|
| **开源** | 贡献者、全球用户 | 安装、用法、贡献、许可证 | `templates/oss.md` |
| **个人** | 未来的你、浏览作品集的人 | 功能说明、技术栈、心得收获 | `templates/personal.md` |
| **内部** | 团队成员、新员工 | 环境搭建、架构、操作手册 | `templates/internal.md` |
| **配置** | 未来的你（一头雾水） | 这里有什么、为什么存在、如何扩展、易踩的坑 | `templates/xdg-config.md` |

如有不清楚之处，**请询问用户**。不要默认所有项目都套用 OSS 的惯例。

## 必备章节（所有类型）

每份 README 至少需要包含：

1. **名称** - 不言自明的标题
2. **描述** - 用 1-2 句话说明是什么、为什么
3. **用法** - 如何使用（示例很有帮助）
