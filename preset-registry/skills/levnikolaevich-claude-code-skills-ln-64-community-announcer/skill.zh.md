# 社区公告发布者

**目标：** 创建一份有来源依据的公告，并且仅在用户批准完整草稿后发布。

**执行契约：** 将下面有序的复选框工作流视为此 skill 的完成定义。将每个复选框都标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用证明其条件触发器不存在的证据将其解决为 `CLEARED`，或标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。
返回前，解决每个 `PENDING`，只将 `PROVEN` 和 `CLEARED` 项计为已完成，对每个 `UNPROVEN` 应用此 skill 的裁决、决策和审批规则，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 仓库身份和权限 | 经过身份验证的 GitHub CLI 或连接器 | 只读发现使用公开 GitHub API |
| 讨论区分类和发布 | GitHub GraphQL API | `BLOCKED`；不要用 issue 替代 |
| 已发布变更的证据 | 远程 Git 历史、releases 和权威文件 | 干净的远程克隆 |
| 命令、路径、名称和计数 | 聚焦的仓库搜索和直接读取 | 托管平台 API 内容读取 |
| 当前外部声明 | 带日期的第一方来源 | 无法验证时省略该声明 |
| 草稿发布 | 传递给 API 的临时 Markdown 文件 | 安全转义的 API 输入并进行读回验证 |

优先使用托管平台 API，而不是抓取渲染后的页面。仅在检查呈现效果或 API 无法提供某个页面时使用浏览器。

不要在公告中暴露仓库令牌、分类节点 ID 或其他凭据。ID 可用于 mutation，但不得作为面向受众的内容。

## 清单

- [ ] 从经过身份验证的托管平台客户端解析目标仓库，并验证写入权限。
- [ ] 通过 API 发现仓库 ID、默认分支、Discussions 是否可用，以及仓库认可的合适分类。
- [ ] 当 Discussions 或合适分类不可用时，以 `BLOCKED` 停止；不要静默地发布到其他位置。
- [ ] 从用户请求、release 或限定的提交范围中确定公告主题。
- [ ] 在存在仓库沟通指南时阅读它，但不要要求存在 community strategy 文件。
- [ ] 阅读当前权威文档、安装说明、受影响的 manifests、release notes，以及相关源代码差异（如有）。
- [ ] 检查最近的提交，以及最多三个可用的类似公告，以了解发布节奏、重复声明和项目惯用风格；对于新仓库或低活跃度仓库，不要求存在以往公告。
- [ ] 使用目标远程状态作为已发布变更的来源；不要将未推送的本地差异宣布为可用。
- [ ] 区分已发布的内容、用户侧发生的变化、迁移需求和未来意图。

## 分类和风格

- [ ] 将公告分类为 release、breaking change、feature update、architecture change 或 community news。
- [ ] 选择能够解释用户结果及其重要性的最简短风格。
- [ ] 对于若干彼此独立的变更，使用简洁的 release digest。
- [ ] 当理解重新设计所需的动机时，使用从问题到解决方案的叙事。
- [ ] 当现有用户必须采取行动时，使用以迁移为先的结构。
- [ ] 在保持自然的前提下，与近期公告采用不同的开头；相比清晰度，变化并不更重要。
- [ ] 不要强行加入 emoji、口号、夸张的比喻或固定模板。
- [ ] 匹配项目的语气，同时确保即使不了解仓库内部背景，也能理解其中的声明。

## 草稿

- [ ] 撰写一个明确具体的标题，说明成果，而不只是写“更新”或“公告”。
- [ ] 开头先说明用户遇到的问题，或最重要的已交付成果。
- [ ] 使用提交记录、文档或发布说明中的证据，解释为什么进行此次更改。
- [ ] 使用成果导向的语言概括亮点，并在有帮助时写明确切的产品、包、插件、技能或组件名称。
- [ ] 当读者需要采取行动时，包含经过验证的安装或更新命令。
- [ ] 对于破坏性变更，添加 `IMPORTANT` 迁移块，其中包括清晰的变更前后步骤。
- [ ] 根据具体情况，链接到默认分支或不可变发布标签上的权威文档。
- [ ] 仅针对已确定或明确标注为暂定的工作，包含一个简短的“后续计划”部分。
- [ ] 通过用户名感谢经过核实的外部贡献者；个人独立完成时省略该部分。
- [ ] 如果社区反馈会有帮助，以一个真实且可回答的反馈问题结尾。

## 事实核查

- [ ] 根据当前权威文档，核实每条命令，以及其中使用的任何稳定包、插件或市场标识符。
- [ ] 根据远程仓库，核实每个产品、包、插件、技能、组件、文件路径、类别、版本、标签和链接的名称。
- [ ] 根据目标提交重新计算每个计数；如果计数对用户没有实际价值，则避免使用。
- [ ] 根据实际变更的源代码、文档或清单，核实功能描述，而不是依据提交标题的简写。
- [ ] 确认明确说明已移除的功能和兼容性限制。
- [ ] 不要编造采用情况、下载量、搜索量、性能、兼容性或路线图方面的声明。
- [ ] 对估算、解读和未来意图进行标注，不要将其当作已交付的事实。
- [ ] 删除泛泛的炒作、重复的结论、过多的标题、套话式过渡和对称的填充性列表。
- [ ] 优先使用具体的动词和有变化的句子长度；仅在读者需要时保留技术标识符。
- [ ] 以新用户的视角重新阅读草稿，确保其中同时说明了价值和任何必需的操作。

## 审批与发布

- [ ] 在创建外部状态之前，先向用户展示确切的标题和完整的 Markdown 正文。
- [ ] 在草稿中包含所选类别和证据范围。
- [ ] 等待明确批准；要求起草或发布公告不等于批准尚未展示的最终文案。
- [ ] 如果用户更改了任何实质性声明或指令，再次对修订后的草稿进行事实核查。
- [ ] 将获批正文写入临时文件，以保留格式并避免 shell 插值错误。
- [ ] 使用已发现的仓库 ID 和类别 ID，通过 GitHub Discussions GraphQL mutation 发布。
- [ ] 读回创建的讨论，并核实其标题、正文、类别和 URL。
- [ ] 核实后安全地删除临时草稿。
- [ ] 报告讨论 URL，以及 API 无法执行的任何手动操作，例如置顶。
- [ ] 除非明确要求，否则不要创建标签、发布版本、议题、评论或交叉发布。

## 结论

- `DRAFT READY` — 已完成事实核查的文案正在等待明确批准。
- `PUBLISHED` — 已批准的讨论已存在，并且已成功回读。
- `BLOCKED` — 所需的源证据、权限、分类或发布验证不可用。

## 输出契约

在批准之前，返回分类、证据范围、所选分类、标题、完整 Markdown 正文、事实核查摘要以及 `DRAFT READY`。

发布之后，返回已批准的标题、讨论 URL、验证证据、`PUBLISHED` 以及剩余风险。

如果已发布的讨论与已批准的草稿不一致，报告 `BLOCKED`，并在编辑或删除外部内容之前征求确认。

在响应中保留已批准的文案，以便用户将其与已发布的讨论进行比较。
