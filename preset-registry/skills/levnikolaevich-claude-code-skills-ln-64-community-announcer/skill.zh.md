# 社区公告发布者

**目标：** 创建一份有来源依据的公告，并且仅在用户批准完整草稿后发布。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，并且仅当相应操作及所需证据均已完成时，才将其标记为完成。标记为 `N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的裁定、决策和批准规则应用于每个未完成项目，并在开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 仓库身份和权限 | 已认证的 GitHub CLI 或连接器 | 用于只读发现的公开 GitHub API |
| 讨论分类和发布 | GitHub GraphQL API | `BLOCKED`；不得以议题代替 |
| 已发布变更的证据 | 远程 Git 历史记录、发行版和规范文件 | 干净的远程克隆 |
| 命令、路径、名称和数量 | 有针对性的仓库搜索和直接读取 | 托管 API 内容读取 |
| 当前外部声明 | 有日期的第一手来源 | 无法验证时省略该声明 |
| 草稿发布 | 通过临时 Markdown 文件传递给 API | 安全转义的 API 输入，并进行回读验证 |

与抓取渲染后的页面相比，优先使用托管 API。仅在检查页面呈现效果或 API 无法提供的页面时使用浏览器。

不得在公告中暴露仓库令牌、分类节点 ID 或其他凭据。ID 可用于变更操作，但不应作为面向受众的内容。

## 检查清单

- [ ] 从已认证的托管客户端解析目标仓库，并验证写入权限。
- [ ] 通过 API 查明仓库 ID、默认分支、Discussions 可用性，以及一个经仓库认可的合适分类。
- [ ] 当 Discussions 或合适的分类不可用时，以 `BLOCKED` 状态停止；不得暗中发布到其他位置。
- [ ] 根据用户请求、发行版或有明确边界的提交范围确定公告主题。
- [ ] 如果存在仓库沟通指南，则阅读该指南，但不强制要求提供社区策略文件。
- [ ] 如果存在当前的权威文档、安装说明、受影响的清单文件、发行说明和相关源代码差异，则阅读这些内容。
- [ ] 检查最近的提交以及最多三篇可用的同类公告，了解发布节奏、重复声明和项目风格；对于新仓库或公告数量较少的仓库，不强制要求存在过往公告。
- [ ] 对于已发布的变更，以目标远程状态为依据；不得将尚未推送的本地差异公告为已可用。
- [ ] 区分已发布的内容、面向用户的变化、迁移需求和未来意图。

## 分类和风格

- [ ] 将公告分类为发行版、破坏性变更、功能更新、架构变更或社区新闻。
- [ ] 选择能够说明用户所得结果及其重要性的最简短风格。
- [ ] 对多项相互独立的变更使用简洁的发行摘要。
- [ ] 当必须了解动机才能理解重新设计时，使用从问题到解决方案的叙述方式。
- [ ] 当现有用户必须采取行动时，采用迁移优先的结构。
- [ ] 在保持自然的前提下，使开场方式与近期公告有所不同；多样性不应凌驾于清晰度之上。
- [ ] 不要强行使用表情符号、口号、夸张隐喻或固定模板。
- [ ] 与项目的表达风格保持一致，同时确保读者无需了解仓库内部背景也能理解相关声明。

## 草拟

- [ ] 撰写一个明确说明成果的标题，而不是只写“更新”或“公告”。
- [ ] 开篇说明用户遇到的问题或已发布的最重要成果。
- [ ] 使用提交、文档或发布说明中的证据解释为何进行此项更改。
- [ ] 使用成果导向的语言概述亮点，并在适当情况下准确指出产品、软件包、插件、技能或组件的名称。
- [ ] 当读者必须执行操作时，提供经过验证的安装或更新命令。
- [ ] 对于破坏性更改，添加一个 `IMPORTANT` 迁移块，其中包含清晰的更改前后操作步骤。
- [ ] 根据具体情况，链接到默认分支或不可变发布标签上的权威文档。
- [ ] 仅针对已确定或明确标记为暂定的工作，添加简短的“后续计划”部分。
- [ ] 使用用户名感谢经核实的外部贡献者；如果是独立完成的工作，则省略此部分。
- [ ] 当社区意见有帮助时，以一个真诚且可回答的反馈问题结尾。

## 事实核查

- [ ] 根据当前权威文档，以及命令中使用的任何稳定软件包、插件或市场标识符，核实每条命令。
- [ ] 根据远程仓库，核实每个提及的产品、软件包、插件、技能、组件、文件路径、类别、版本、标签和链接。
- [ ] 基于目标提交重新计算每项数量；如果数量不能为用户带来价值，则避免使用。
- [ ] 根据实际更改的源代码、文档或清单确认功能描述，不要依赖提交标题中的简略表述。
- [ ] 确保明确说明已移除的功能和兼容性限制。
- [ ] 不要虚构采用情况、下载量、搜索量、性能、兼容性或路线图相关的声明。
- [ ] 将估算、解读和未来意图明确标注出来，不要将其表述为已经发布的事实。
- [ ] 删除笼统的夸张表述、重复的结论、过多的标题、套路化的过渡语和为了形式对称而添加的填充列表。
- [ ] 优先使用具体的动词，并使句子长短富有变化；仅在读者需要时保留技术标识符。
- [ ] 以新用户的视角重新阅读草稿，确保它既说明了价值，也说明了所有必要操作。

## 审批与发布

- [ ] 在创建外部状态之前，向用户展示确切的标题和完整的 Markdown 正文。
- [ ] 随草稿提供所选类别和证据范围。
- [ ] 等待明确批准；要求起草或发布公告并不等同于批准尚未查看的最终文案。
- [ ] 如果用户更改了任何实质性声明或指示，请再次对修订后的草稿进行事实核查。
- [ ] 将已批准的正文写入临时文件，以保留格式并避免 shell 插值错误。
- [ ] 使用已查明的仓库和类别 ID，通过 GitHub Discussions GraphQL mutation 发布。
- [ ] 回读已创建的讨论，并核实其标题、正文、类别和 URL。
- [ ] 验证完成后，安全删除临时草稿。
- [ ] 报告讨论的 URL，以及 API 无法执行的任何手动操作，例如置顶。
- [ ] 除非明确要求，否则不要创建标签、发布版本、议题、评论或跨平台发布。

## 结论

- `DRAFT READY` — 已完成事实核查的文案正在等待明确批准。
- `PUBLISHED` — 已批准的讨论已发布，并已成功回读验证。
- `BLOCKED` — 无法获取必需的来源证据、权限、分类或发布验证。

## 输出约定

批准前，返回分类、证据范围、所选类别、标题、完整的 Markdown 正文、事实核查摘要以及 `DRAFT READY`。

发布后，返回已批准的标题、讨论 URL、验证证据、`PUBLISHED` 以及剩余风险。

如果已发布的讨论与批准的草稿不一致，请报告 `BLOCKED`，并在编辑或删除外部内容前征求许可。

在响应中保留已批准的文案，以便用户将其与已发布的讨论进行比较。
