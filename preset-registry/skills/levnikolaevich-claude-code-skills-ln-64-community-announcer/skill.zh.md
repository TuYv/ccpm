# 社区公告员

**目标：** 创建一份有来源支撑的公告，并且仅在用户批准完整草稿后发布。

**执行约定：** 有序复选框即为完成定义。内部将每一项跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败均不构成证明。每个章节后都要核对各项。在返回前，解决所有 `PENDING`，且仅统计 `PROVEN` 和 `CLEARED`；对每一处缺口应用该技能的裁决和批准规则。
保留用户意图、范围和现有授权。继续已获授权的工作；仅针对具有实质影响的未解决选择或所需的外部批准进行询问。根据实质风险确定深度，不得在未说明的情况下跳过检查。保持依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 仓库身份和权限 | 已认证的 GitHub CLI 或连接器 | 用于只读发现的公开 GitHub API |
| 讨论分类和发布 | GitHub GraphQL API | 在存在目标限制的情况下继续撰写草稿；没有此能力时，发布为 `BLOCKED` |
| 已发布变更的证据 | 远程 Git 历史、发布版本和规范文件 | 干净的远程克隆 |
| 命令、路径、名称和计数 | 聚焦式仓库搜索和直接读取 | 托管 API 内容读取 |
| 当前外部声明 | 主要的带日期来源 | 无法验证时省略该声明 |
| 草稿发布 | 传递给 API 的临时 Markdown 文件 | 安全转义的 API 输入，并进行回读验证 |

优先使用托管 API，而非抓取渲染后的页面。仅在 API 无法公开的页面或需要检查展示效果时使用浏览器。

不得在公告中暴露仓库令牌、分类节点 ID 或其他凭据。ID 可用于变更操作，但不得作为面向受众的内容。

## 检查清单

### 确定范围和证据

- [ ] 从请求或托管客户端解析目标仓库，并确定任务仅为草稿还是包含发布。
- [ ] 阅读默认分支和源证据。在可访问时，发现 Discussions 是否可用及合适的分类；缺少发布权限不妨碍撰写经过事实核查的草稿。
- [ ] 对于仅草稿工作，报告目标限制并继续。在发布前，要求具备写入权限、仓库/分类 ID，以及合适的已启用 Discussions 分类；不得悄然发布到其他位置。
- [ ] 从用户请求、发布版本或限定的提交范围中确定公告主题。
- [ ] 在存在时阅读仓库沟通指南，但不要求存在社区策略文件。
- [ ] 在存在时阅读当前权威文档、安装说明、受影响的清单、发行说明以及相关源代码差异。
- [ ] 检查最近的提交以及最多三份可用的类似公告，以了解发布节奏、重复声明和既有风格；在新仓库或低活跃度仓库中，不要求存在过往公告。
- [ ] 将已发布声明固定到目标远程提交或发布版本，包括默认分支之后的发布线；绝不将未推送的本地差异表述为可用。
- [ ] 区分已发布内容、面向用户的变更、迁移需求和未来意图。

### 分类与风格

- [ ] 将公告归类为发布、破坏性变更、功能更新、架构变更或社区新闻。
- [ ] 选择能够说明用户结果及其重要性的最简短风格。
- [ ] 在不依赖内部仓库上下文的前提下，使表述符合项目的语气，同时保持主张易于理解。

### 草稿

- [ ] 撰写一个点明结果的具体标题，而非仅写“更新”或“公告”。
- [ ] 以用户问题或最重要的已交付结果开头。
- [ ] 使用提交记录、文档或发布说明中的证据解释进行此变更的原因。
- [ ] 用结果导向的语言概述亮点，并在适用时列出确切的产品、包、插件、技能或组件名称。
- [ ] 当读者需要采取行动时，包含经过验证的安装或更新命令。
- [ ] 突出显示破坏性变更，并提供清晰的迁移前后步骤；遵循仓库格式，而非要求特定的提示标签。
- [ ] 视情况链接至默认分支上的规范文档或不可变的发布标签。
- [ ] 仅针对已确定或明确标注为暂定的工作，加入简短的“接下来”部分。
- [ ] 以用户名感谢经验证的外部贡献者；若为独立工作，则省略该部分。
- [ ] 当社区反馈有帮助时，以一个真实且可回答的反馈问题结束。

### 事实核查

- [ ] 根据当前权威文档以及所使用的任何稳定包、插件或市场标识符，验证每条命令。
- [ ] 根据远程仓库验证每个命名的产品、包、插件、技能、组件、文件路径、类别、版本、标签和链接。
- [ ] 根据目标提交重新计算每个计数；当计数对用户没有价值时，避免使用。
- [ ] 根据实际变更的源代码、文档或清单确认功能描述，而非依赖提交标题的简写。
- [ ] 明确说明已移除的功能和兼容性限制。
- [ ] 不要虚构采用率、下载量、搜索量、性能、兼容性或路线图方面的主张。
- [ ] 将估算、解读和未来意图标记出来，而非将其表述为已交付的事实。
- [ ] 删除泛泛的宣传、重复的结论、过多的标题、陈词滥调的过渡语和对称的填充列表。
- [ ] 以新用户的视角重读草稿，确保其解释了价值以及任何必需的操作。

### 审批与发布

- [ ] 在创建外部状态之前，向用户展示确切的标题和完整的 Markdown 正文。
- [ ] 在草稿中包含证据范围和所选类别，或未解决的目标限制。
- [ ] 对于仅草稿工作，完成自检并报告 `DRAFT READY`，无需等待；以此范围理由明确仅发布相关的事项。对于发布，要求明确批准确切文案和目标；复用本会话中已给出的未变更批准。请求发布公告并不等同于批准尚未展示的最终文案。
- [ ] 如果用户更改了任何实质性主张或指示，再次对修订后的草稿进行事实核查。
- [ ] 将已批准的正文写入临时文件，以保留格式并避免 shell 插值错误。
- [ ] 仅针对已获授权的发布，验证写入权限和目标位置，然后使用已发现的仓库和类别 ID，通过 GitHub Discussions GraphQL mutation 进行发布。若请求仅止于草稿，则明确仅发布相关的标准。
- [ ] 读取讨论内容并验证标题、正文、类别和 URL。响应不确定时，在重试前检查返回的 ID 或匹配的目标内容；若身份仍不明确，则停止操作，以避免重复创建。
- [ ] 验证后安全地移除临时草稿。
- [ ] 报告讨论 URL 以及 API 无法执行的任何手动操作，例如置顶。
- [ ] 除非明确请求，否则不要创建标签、发布版本、议题、评论或交叉发布。

## 判定

- `DRAFT READY` — 已完成事实核查的文案；发布不在范围内，或正等待对确切文案的批准。
- `PUBLISHED` — 已批准的讨论已存在，且已成功回读。
- `BLOCKED` — 源证据无法支撑可信草稿，或因权限、类别或验证不可用，无法进行所请求的发布。请区分已完成的草稿与受阻的发布。

## 自检

- [ ] **返回前核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、判定以及适用的清理项。修正报告或已获授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。简短结果可每个字段占一行；省略空表格，不要复制已链接的产物：

1. **结果：** 特定 Skill 的判定及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 下列特定 Skill 字段；区分事实、推断和未经验证的声明。链接产物；适用时使用表格。
4. **验证：** 检查/结果、不可用证据，以及适用的清理项/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项目的原因、对结果的影响和确切的下一步行动；剩余风险和所需决策。

**特定 Skill 证据：** 公告分类、证据范围、目标位置/类别或限制、确切标题、批准前完整且经过事实核查的 Markdown 草稿，以及事实核查摘要。发布后，提供讨论 URL 和回读验证，同时在响应历史中保留已批准的文案。报告置顶等手动操作；与已批准文案不一致即为 `BLOCKED`，且在编辑/删除外部内容前需要获得批准。
