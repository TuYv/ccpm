# 代码库审计员

**目标：** 对生产代码执行广泛的只读健康审计。在不将检测器匹配结果或个人风格偏好作为发现项的前提下，找出具体的跨领域故障、安全、交付和维护风险。不得替代文档可信度、测试组合、整体架构或持久化专项审查。

**执行约定：** 有序复选框是完成定义。内部将每项跟踪为 `PENDING`、有具体证据的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每个部分完成后重新核对各项。返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将技能的裁决和批准规则应用于每个缺口。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对重要的未解决选择或所需的外部批准提出询问。根据实际风险调整深度，不得在不说明的情况下跳过检查。保留依赖关系和安全顺序；除此之外，为每项要求选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 代码库地图和技术栈检测 | 原生文件列表、清单、构建文件和代码库说明 | 确定范围、生成区域、入口点、支持的运行时和命令时 | 针对性目录树检查和已知入口点 |
| 符号、调用方、所有权和数据流 | 语言服务器或宿主原生代码智能工具 | 发现项取决于符号身份、引用、重写、路由连接或跨文件行为时 | 窄范围文本搜索，并直接检查每个相关匹配项 |
| 当前变更和历史背景 | Git 状态、差异、日志和 blame | 区分当前工作、回归、刻意约束和废弃的兼容路径时 | 当前实现和明确的决策记录 |
| 交付健康度 | 代码库定义的构建、lint、类型检查、测试和冒烟命令 | 确定项目能否在其文档所述环境中交付时 | 检查 CI 和脚本；标记执行不可用 |
| 依赖和安全状态 | 原生包管理器审计、清单、锁文件和官方公告 | 检查已知漏洞、不受支持的版本和依赖健康状况时 | 官方注册表和供应商来源；绝不得臆测严重程度 |
| 运行时证据 | 现有日志、指标、追踪、性能分析和诊断信息 | 静态分析无法确定频率、可达性或运行影响时 | 调用路径分析，并明确说明仅限静态分析 |
| 当前外部行为 | 官方规范、供应商文档和发行说明 | 发现项取决于当前 API、运行时或标准行为时 | 基于主要来源的网络调研；否则标记为 `UNVERIFIED` |

从摘要级发现开始，然后逐步缩小范围，之后再深入阅读。只运行代码库定义的或明确安全的诊断命令；审计期间绝不得发布、部署、迁移生产数据、轮换密钥或重写文件。

## 证据规则

- 模式匹配只是候选项，而不是问题发现。确认其可达性、上下文和后果。
- 运行时故障或确定性的命令输出优先于静态怀疑；当无法执行时，静态证据仍然有效，但必须明确说明这一限制。
- 生成代码、供应商代码、fixture、迁移历史代码以及为保持兼容性而有意保留的代码，需要结合具体上下文处理。
- 外部最佳实践只有在解决仓库中的具体缺陷或风险时才具有可执行性。
- 仅对具有不同根本原因的问题进行评分或计数；共享同一修正方案的症状应去重。

## 检查清单

### 1. 确定范围和基线

- [ ] 检测语言、框架、包管理器、入口点、部署模型、生成代码区域，以及仓库支持的验证命令。
- [ ] 在要求探针、遥测、信号处理或关闭行为之前，先将每个运行时表面归类为长期运行的服务、CLI、库、作业、无服务器函数或平台管理的组件。
- [ ] 阅读适用的说明，识别安全边界、关键业务路径、公共接口和不可逆操作。
- [ ] 检查 Git 状态，确保审计不会覆盖、错误归因或忽略用户的无关更改。
- [ ] 建立可行的构建、lint、类型检查、测试和冒烟测试基线；记录已执行的范围、环境、退出状态和证据。确认必需的工作确实运行，而不是因为没有选中的测试或被跳过的门禁而表面成功。
- [ ] 根据风险定义排除项和深度，而不是对每个文件投入同等精力进行扫描。
- [ ] 保持审计只读。仅允许使用获准的缓存和构建产物，并披露创建了这些内容。

### 2. 审计安全和交付边界

- [ ] 搜索已提交的密钥、不安全的凭据模式、敏感默认值、调试绕过机制，以及通过日志或错误造成的意外暴露。
- [ ] 对于凭据问题，绝不暴露原始值：区分真实凭据材料与占位符、fixture、示例和允许列出的指纹；仅报告类型、位置和经过编辑的证据，并且仅针对已确认的暴露建议撤销、轮换或修复历史记录，不得在审计期间执行这些操作。
- [ ] 跟踪不可信输入进入 SQL、shell、模板、HTML、文件路径、URL、反序列化、重定向和其他对注入敏感的接收点的路径。
- [ ] 检查身份验证、授权、租户或所有权隔离、权限转换、不安全的直接对象访问，以及默认拒绝行为。
- [ ] 检查信任边界处的验证、规范化、大小和速率限制、不安全的文件操作，以及破坏性操作的确认或防护措施。
- [ ] 根据实际调用路径、框架行为、配置和当前官方指导验证安全问题，然后再确定严重性。
- [ ] 检查编译器、linter、类型检查器、测试、打包和 CI 配置中被跳过的门禁、被忽略的失败、环境漂移和不可复现的交付。
- [ ] 验证成功的打包是否生成了预期的入口点、资源、元数据、目标平台和可部署产物；退出代码为零本身并不能证明构建产物可发布。
- [ ] 找出过时的 skip、隔离、允许失败、错误时继续和警告抑制路径，这些路径会让必需的信号显示为绿色。
- [ ] 检查配置完整性、必需的环境验证、不安全的回退、缺失的示例，以及本地、CI 和部署设置之间的差异。

### 3. 审计可维护性和依赖项

- [ ] 在函数、处理程序、模块、配置和集成代码中寻找有证据支持的重复；区分共享的领域概念与偶然的相似性。
- [ ] 识别过度抽象、未使用的扩展点、过多的工厂或包装器、并行机制，以及重复声明的平台能力的自定义工具。
- [ ] 在合并重复代码或移除抽象之前，检查生命周期和所有权边界、有意的解耦、依赖注入或测试接缝、框架要求、公共扩展契约，以及预期的独立演进。
- [ ] 检查复杂度热点、过长的方法、上帝模块、深层嵌套、过多参数、布尔模式 API、误导性的名称，以及混合的职责。
- [ ] 检查算法是否存在提前退出错误、重复键丢失、边界错误、无界工作量、重复扫描、迭代期间变更，以及隐藏的共享状态。
- [ ] 检查硬编码的运维值、URL、超时、限制、标识符和特定环境行为，确认这些内容是否应当成为显式配置或命名策略。
- [ ] 跨外部契约、DTO、服务、持久化和存储追踪同一个概念；只有在没有显式的序列化器、代码生成或 ORM 边界映射能够解释时，才标记同义词或大小写漂移。
- [ ] 审计依赖项漏洞、支持状态、许可证或运行时限制、重复包、未使用的包，以及可信的替换或移除机会。
- [ ] 将安全公告与已解析的版本和部署相匹配，然后利用可达性和利用条件将暴露分类为已确认、未知或不适用；不可用的调用路径不能证明受影响组件不存在风险。
- [ ] 只有在检查所需功能的对等性、迁移范围、维护状况、许可证、安全历史和领域特定行为之后，才建议使用原生能力、现有依赖项或外部替代方案。
- [ ] 查找不可达代码、未使用的导入和导出、已注释掉的实现、过时的标志、无效的兼容性垫片，以及与其后继实现并存的替换代码。
- [ ] 在报告可以安全删除之前，结合反射、注册、框架发现、配置、序列化、模板和外部入口点确认死代码结论。

### 4. 审计可诊断性、并发性和生命周期

- [ ] 检查日志是否结构化、日志级别是否正确、是否可执行、是否在请求或作业范围内具有关联性，以及是否不包含机密和过量的载荷数据。
- [ ] 验证关联上下文是否跨越出站调用、队列、重试、计划任务和分离的异步边界，而不是只存在于第一条请求日志中。
- [ ] 检查关键路径的指标、追踪、健康信号和错误上下文；仅在运维人员需要通过可观测性检测或诊断故障时才要求相关可观测性。
- [ ] 在可达的并发路径上追踪共享可变状态、锁顺序、原子性、异步任务所有权、取消、重试和竞态窗口。
- [ ] 检查 await 或 yield 点之间的读-修改-写操作，并为共享文件、子进程、终端或 OS 资源以及重复的用户触发构建资源/访问器时间线；包括当前进程之外的访问器。
- [ ] 检查异步路径中的阻塞 I/O 或同步等待、无界并发、孤儿任务、死锁、TOCTOU 风险和非线程安全资源。
- [ ] 检查启动顺序、依赖就绪状态、配置验证、快速失败行为、信号处理、优雅关闭和进行中工作排空。
- [ ] 清点启动和运行时获取的资源，然后将每项资源与安全的反向依赖顺序中的幂等清理相匹配，覆盖成功、失败、超时、取消和重复关闭信号等情况。
- [ ] 验证特定主机的探针语义：存活检查失败应当足以证明需要重启，就绪状态决定是否具备接收流量的资格，而启动检查负责保护初始化过程。避免由依赖项触发的重启级联，以及会产生实质性负载或副作用的探针。

### 5. 验证发现并报告

- [ ] 仅在外部 API、标准、漏洞和运行时行为可能改变某项发现时进行调研，并使用与相关版本匹配的官方来源。
- [ ] 在确认候选项之前，过滤掉框架约定、生成代码、范围受限的管理路径、测试、示例和有文档记录的权衡。
- [ ] 在可能的情况下，使用安全命令、测试、最小调用跟踪或完整的静态失败路径复现高严重性问题。
- [ ] 应用实质性门槛：要求在有证据支持的规模下，存在具体的失败、安全、交付、可操作性或反复出现的维护影响。拒绝审美偏好、理论纯粹性、泛化实践、假设性规模和合理替代方案；要求关注结果或约束，而不是偏好的实现方式。
- [ ] 基于与版本匹配的官方契约说明外部更正；对于尚未解决的权衡，使用一手工程来源。引用受支持的机制；对于本地缺陷，本地证据即可。
- [ ] 根据可利用性、数据或可用性影响、交付阻塞、复发性和修复紧迫性，将发现分类为 `P0`-`P3`。
- [ ] 按风险降低程度和依赖关系安排修复顺序，而不是按文件顺序或检测器类别排序。
- [ ] 当所需的安全环境、高风险行为或权威契约无法在没有可信替代方案的情况下得到验证时，使用 `BLOCKED`；对于有证据支持但尚未解决的 `P0/P1`、要求通过但失败的交付门禁，或已证实的不安全行为，使用 `FAIL`；仅对已验证的非阻塞风险使用 `CONCERNS`；只有在所需检查完成且没有实质性发现时才使用 `PASS`。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。修正报告或经授权的工件。复用有效证据；不要自动重新扫描代码库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时，每个字段可以使用一行；省略空表格，不要复制链接的工件：

1. **结果：** 技能特定的结论和有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下技能特定字段；区分事实、推断和未经验证的声明。链接工件；适用时使用表格。
4. **验证：** 检查项/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；剩余风险和所需决策。

**技能特定证据：** 安全、交付、可维护性/依赖项、可诊断性、并发性和生命周期证据。发现需要包含优先级、位置、触发条件或失败路径、置信度、实质性影响、不可接受的权衡，以及预期工作量最小的修复方案；允许采用其他等效的有效方案。按前置条件和风险降低程度安排修复顺序，而不是按检测器数量排序。
