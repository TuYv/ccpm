# 代码库审计员

**目标：** 对生产代码的健康状况执行广泛的只读审计。识别具体且涉及多处的故障、安全、交付和维护风险，但不得将检测器匹配结果或个人风格偏好直接视为发现。不得用本审计替代文档可信度审查、测试组合审查、整体架构审查或持久化专项审查。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，只有在相应操作和所需证据均完成后，才能将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回结果前，将此技能的裁定、决策和批准规则应用于每个未完成项目，并在结果开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的后续操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 仓库映射和技术栈检测 | 原生文件列表、清单文件、构建文件和仓库说明 | 确定范围、生成内容区域、入口点、受支持的运行时和命令 | 针对性检查目录树和已知入口点 |
| 符号、调用方、所有权和数据流 | 语言服务器或宿主环境原生代码智能工具 | 发现取决于符号身份、引用、重写、路由接线或跨文件行为时 | 小范围文本搜索，并直接检查每个相关匹配项 |
| 当前变更和历史背景 | Git 状态、差异、日志和追溯 | 区分当前工作、回归问题、有意施加的约束和已废弃的兼容路径 | 当前实现和明确的决策记录 |
| 交付健康状况 | 仓库定义的构建、代码检查、类型检查、测试和冒烟测试命令 | 确定项目能否在其文档所述环境中交付 | 检查 CI 和脚本；将执行标记为不可用 |
| 依赖项和安全状态 | 原生包管理器审计、清单文件、锁文件和官方安全公告 | 检查已知漏洞、不受支持的版本和依赖项健康状况 | 官方注册表和供应商来源；绝不猜测严重程度 |
| 运行时证据 | 现有日志、指标、追踪、性能剖析和诊断信息 | 静态分析无法确定发生频率、可达性或运维影响时 | 调用路径分析，并明确说明仅进行了静态分析的限制 |
| 当前外部行为 | 官方规范、供应商文档和发行说明 | 发现取决于当前 API、运行时或标准行为时 | 研究网上的第一手来源；否则标记为 `UNVERIFIED` |

先进行概要层面的探索，逐步缩小范围后再深入阅读。仅运行仓库定义的命令或明确安全的诊断命令；审计期间绝不执行发布、部署、生产数据迁移、密钥轮换或文件重写操作。

## 证据规则

- 模式匹配只是候选项，而非发现。必须确认其可达性、上下文和后果。
- 运行时故障或确定性的命令输出优先于静态推测；如果无法执行，静态证据仍然有效，但必须明确说明相应限制。
- 对生成代码、供应商代码、固件、迁移历史记录和有意保留兼容性的代码，需要结合具体上下文处理。
- 仅当外部最佳实践能够解决仓库中的具体缺陷或风险时，才具有可操作性。
- 只对根本原因不同的发现进行评分或计数；对具有相同修正方式的症状进行去重。

## 检查清单

### 1. 确定范围和基线

- [ ] 识别语言、框架、包管理器、入口点、部署模型、生成内容区域，以及仓库支持的验证命令。
- [ ] 在要求提供探针、遥测、信号处理或关闭行为之前，将每个运行时界面分类为长期运行的服务、CLI、库、作业、无服务器函数或平台托管组件。
- [ ] 阅读适用的说明，并识别安全边界、关键业务路径、公共接口和不可逆操作。
- [ ] 检查 Git 状态，确保审计不会覆盖、错误归因或忽略用户无关的更改。
- [ ] 在可行的情况下建立构建、代码检查、类型检查、测试和冒烟测试基线；记录命令、环境、退出状态和相关输出。
- [ ] 根据风险确定排除项和审计深度，而不是以相同力度扫描每个文件。
- [ ] 保持审计为只读操作。仅允许生成获准的缓存和构建产物，并在创建这些内容时予以披露。

### 2. 审计安全与交付边界

- [ ] 搜索已提交的密钥、不安全的凭据模式、敏感的默认值、调试绕过机制，以及通过日志或错误造成的意外泄露。
- [ ] 对于凭据相关发现，绝不暴露原始值：区分有效资料与占位符、固件、示例和已列入允许名单的指纹；仅报告类型、位置和经过脱敏的证据，并且只对已确认的泄露建议撤销、轮换或修复历史记录，不要在审计期间执行这些操作。
- [ ] 追踪不可信输入流向 SQL、shell、模板、HTML、文件路径、URL、反序列化、重定向及其他对注入敏感的接收点。
- [ ] 检查身份验证、授权、租户或所有权隔离、权限转换、不安全的直接对象访问，以及默认拒绝行为。
- [ ] 检查信任边界处的验证、规范化、大小和速率限制、不安全的文件操作，以及破坏性操作的确认机制或防护措施。
- [ ] 在确定严重程度之前，根据实际调用路径、框架行为、配置和当前官方指南核实安全问题。
- [ ] 检查编译器、代码检查器、类型检查器、测试、打包和 CI 配置中是否存在跳过关卡、忽略失败、环境漂移及不可复现的交付。
- [ ] 验证成功打包是否生成了预期的入口点、资源、元数据、目标平台和可部署产物；仅退出代码为零并不能证明构建结果可供交付。
- [ ] 查找过时的跳过、隔离、允许失败、出错后继续和警告抑制路径，这些路径会使必要的信号呈现为正常状态。
- [ ] 检查配置完整性、必要的环境验证、不安全的回退行为、缺失的示例，以及本地、CI 与部署设置之间的差异。

### 3. 审计可维护性与依赖项

- [ ] 查找函数、处理程序、模块、配置和集成代码中有证据支持的重复内容；区分共享的领域概念与偶然的相似之处。
- [ ] 识别过度抽象、未使用的扩展点、过多的工厂或包装器、并行机制，以及重复实现已声明平台能力的自定义工具。
- [ ] 在合并重复内容或移除抽象之前，检查生命周期和所有权边界、有意解耦、依赖注入或测试接缝、框架要求、公共扩展契约，以及预期的独立演进。
- [ ] 检查复杂度热点、过长的方法、上帝模块、过深的嵌套、过多的参数、布尔模式 API、误导性名称和混杂的职责。
- [ ] 检查算法中是否存在提前退出错误、重复键丢失、边界错误、无界工作、重复扫描、迭代期间修改数据，以及隐藏的共享状态。
- [ ] 检查应作为显式配置或具名策略的硬编码运维值、URL、超时时间、限制、标识符和环境特定行为。
- [ ] 跨外部契约、DTO、服务、持久化层和存储追踪同一概念；仅当不存在显式序列化器、代码生成或 ORM 边界映射能够解释时，才标记同义词或大小写不一致问题。
- [ ] 审计依赖项漏洞、支持状态、许可证或运行时约束、重复包、未使用的包，以及可靠的替换或移除机会。
- [ ] 根据已安装版本以及存在漏洞的 API 或功能是否可达来核实漏洞发现；区分受影响的代码与仅存在于锁文件中的包。
- [ ] 只有在检查所需的功能对等性、迁移范围、维护情况、许可证、安全历史和领域特定行为之后，才建议使用原生方案、现有依赖项或外部替代方案。
- [ ] 查找不可达代码、未使用的导入和导出、被注释掉的实现、过时的标志、无用的兼容性垫片，以及遗留在其后继实现旁边的被替代代码。
- [ ] 在报告可以安全删除之前，根据反射、注册、框架发现机制、配置、序列化、模板和外部入口点确认无用代码相关发现。

### 4. 审查可诊断性、并发与生命周期

- [ ] 检查日志是否结构化、级别设置正确、可供采取行动、能在请求或作业范围内进行关联，并且不包含机密信息和过量的有效载荷数据。
- [ ] 验证关联上下文是否能够跨越出站调用、队列、重试、计划任务和脱离主流程的异步边界传播，而不是仅存在于第一条请求日志中。
- [ ] 检查关键路径的指标、跟踪、健康信号和错误上下文；仅在运维人员需要借此检测或诊断故障的地方要求具备可观测性。
- [ ] 跟踪可达并发路径上的共享可变状态、锁顺序、原子性、异步任务所有权、取消、重试和竞态窗口。
- [ ] 检查跨越 await 或 yield 点的读取-修改-写入操作，并为共享文件、子进程、终端或操作系统资源以及重复的用户触发操作构建资源/访问者时间线；包括当前进程之外的访问者。
- [ ] 检查异步路径中的阻塞 I/O 或同步等待、无界并发、孤立任务、死锁、TOCTOU 隐患以及线程不安全的资源。
- [ ] 检查启动顺序、依赖项就绪状态、配置验证、快速失败行为、信号处理、优雅关闭以及进行中工作的排空。
- [ ] 盘点启动和运行时获取的资源，然后确保每项资源在成功、失败、超时、取消和重复关闭信号等情况下，都能按照安全的反向依赖顺序进行幂等清理。
- [ ] 明确区分探针语义：存活探针应在不检查脆弱依赖项的情况下证明进程能够恢复，而就绪探针应在所需依赖项和初始化可用之前阻止流量进入；两种探针都不应产生显著负载或副作用。

### 5. 验证发现并报告

- [ ] 仅当外部 API、标准、漏洞和运行时行为可能改变某项发现时才进行研究，并使用与相关版本匹配的官方来源。
- [ ] 在确认候选问题之前，先排除框架惯例、生成的代码、范围受限的管理路径、测试、示例和已记录的权衡取舍。
- [ ] 只要可能，就使用安全的命令、测试、最小调用跟踪或完整的静态失败路径来复现高严重性问题。
- [ ] 对每个候选问题应用实质性和可接受替代方案门槛。要求该问题在仓库现有证据所表明的规模下，具有具体的故障、安全、交付、可运维性或反复发生的维护影响。拒绝吹毛求疵、个人偏好、理论上的纯粹性、泛泛的最佳实践、假设性的规模问题，以及当前权衡合理时仅仅采用不同实现的情况；当多种设计均可行时，应要求达成结果或满足约束，而不是指定某一种偏好的风格。
- [ ] 在每项发现要求的解决方案中加入直接相关的 Markdown 实践链接：优先使用最新的官方文档或规范，仅当官方来源无法解决相关权衡时，才使用信誉良好的第一手工程资料。打开并验证来源；它必须支持所提议的机制，而不只是与缺陷类别相关。拒绝搜索结果链接、泛泛的最佳实践文章和装饰性引用。
- [ ] 根据可利用性、数据或可用性影响、交付阻塞程度、复发性和修复紧迫性，将发现分类为 `P0`-`P3`。
- [ ] 对每项发现提供位置、证据、触发条件或失败路径、影响、置信度、当前折衷方案为何不可接受，以及可信度足够的最小修复方案，同时允许采用等效解决方案。
- [ ] 按风险降低效果和依赖关系确定修复顺序，而不是按文件顺序或检测器类别排序。
- [ ] 当缺少必要的安全环境、无法在没有可信后备方案的情况下验证高风险行为或权威契约时，使用 `BLOCKED`；对于已有证据且尚未解决的 `P0/P1`、必要但失败的交付关卡或已证实的不安全行为，使用 `FAIL`；仅对已验证但不构成阻塞的风险使用 `CONCERNS`，并且仅在完成所有必要检查且没有实质性发现时使用 `PASS`。
- [ ] 返回裁定结果，并附上已执行的检查、排除的范围、已验证的发现、未经验证的候选问题以及代码库的剩余风险。

## 输出约定

```markdown
# Codebase Audit

**Verdict:** PASS | CONCERNS | FAIL | BLOCKED

## Scope and baseline
- Stack, entrypoints, and exclusions
- Commands and environments checked
- Static and runtime evidence available

## Health summary
| Area | Status | Evidence |
|---|---|---|
| Security | PASS / CONCERNS / FAIL | ... |
| Delivery | PASS / CONCERNS / FAIL | ... |
| Maintainability | PASS / CONCERNS / FAIL | ... |
| Dependencies and dead code | PASS / CONCERNS / FAIL | ... |
| Diagnosability, concurrency, lifecycle | PASS / CONCERNS / FAIL | ... |

## Findings
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete codebase defect | Location, trigger or failure path, evidence, confidence, material impact at evidenced scale, and why the current tradeoff is not acceptable | Smallest credible correction, expected effort, and a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent valid solutions |

Use `None` when no candidate survives the evidence, materiality, context, and acceptable-alternative gates.

## Remediation order and residual risks
Dependency-aware next actions, blind spots, and unverified candidates.
```
