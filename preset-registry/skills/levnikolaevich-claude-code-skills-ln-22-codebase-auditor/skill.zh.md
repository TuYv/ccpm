# 代码库审计员

**目标：** 执行广泛的、只读的生产代码健康审计。发现具体的跨领域故障、安全、交付和维护风险，但不要将检测器匹配结果或个人风格偏好当作问题。不要替代文档可信度、测试组合、整体架构或持久化专项审查。

**执行契约：** 将下方有序复选框工作流视为此技能的完成定义。将每个复选框都标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用表明其条件触发器不存在的证据将其解决为 `CLEARED`，或标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不能作为证明。
返回前，解决所有 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为完成，并将此技能的判定、决策和批准规则应用于每个 `UNPROVEN` 项，然后在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 仓库地图和技术栈检测 | 原生文件列表、清单文件、构建文件和仓库说明 | 确定范围、生成区域、入口点、支持的运行时和命令 | 针对性检查目录树和已知入口点 |
| 符号、调用方、所有权和数据流 | 语言服务器或宿主原生代码智能工具 | 问题依赖于符号身份、引用、重写、路由连接或跨文件行为时 | 缩小文本搜索范围，并直接检查每个相关匹配项 |
| 当前变更和历史背景 | Git status、diff、log 和 blame | 区分当前工作、回归、有意限制和失效的兼容路径 | 当前实现和明确的决策记录 |
| 交付健康度 | 仓库定义的构建、lint、类型检查、测试和冒烟测试命令 | 确定项目能否在其文档化环境中交付时 | 检查 CI 和脚本；标记执行不可用 |
| 依赖和安全状态 | 原生包管理器审计、清单文件、锁文件和官方公告 | 检查已知漏洞、不受支持的版本和依赖健康状况时 | 官方注册表和供应商来源；绝不要猜测严重性 |
| 运行时证据 | 现有日志、指标、追踪、性能分析和诊断信息 | 静态分析无法确定频率、可达性或运行影响时 | 调用路径分析，并明确说明仅限静态分析 |
| 当前外部行为 | 官方规范、供应商文档和发行说明 | 问题依赖于当前 API、运行时或标准行为时 | 基于主要来源进行网络研究；否则标记为 `UNVERIFIED` |

从摘要级发现开始，并在深入阅读前缩小范围。只运行仓库定义的或明显安全的诊断命令；绝不要在审计期间发布、部署、迁移生产数据、轮换机密信息或重写文件。

## 证据规则

- 模式匹配结果只是候选项，并不等于发现问题。请确认其可达性、上下文和后果。
- 运行时失败或确定性的命令输出，其证据效力高于静态怀疑；当无法执行时，只要明确说明这一限制，静态证据仍然有效。
- 生成代码、供应商代码、fixture、迁移历史代码以及为保持兼容性而特意编写的代码，都需要结合具体上下文进行处理。
- 外部最佳实践只有在能够应对仓库中的具体缺陷或风险时，才具有可操作性。
- 只对具有不同根本原因的问题进行评分或计数；共享同一修复方案的症状应去重。

## 检查清单

### 1. 确定范围和基线

- [ ] 检测语言、框架、包管理器、入口点、部署模型、生成代码区域，以及仓库支持的验证命令。
- [ ] 在要求探针、遥测、信号处理或关闭行为之前，先将每个运行时表面分类为长时间运行的服务、CLI、库、作业、无服务器函数或平台管理的组件。
- [ ] 阅读适用的指令，并识别安全边界、关键业务路径、公共接口和不可逆操作。
- [ ] 检查 Git 状态，确保审计不会覆盖、错误归因于或忽略用户无关的更改。
- [ ] 在可行的情况下建立构建、代码检查、类型检查、测试和冒烟测试基线；记录命令、环境、退出状态和相关输出。
- [ ] 根据风险确定排除项和审计深度，而不是对每个文件投入同等精力进行扫描。
- [ ] 保持审计只读。仅允许使用获准的缓存和构建产物，并在创建这些内容时予以披露。

### 2. 审计安全边界和交付边界

- [ ] 搜索已提交的密钥、不安全的凭据模式、敏感默认值、调试绕过机制，以及通过日志或错误信息造成的意外暴露。
- [ ] 对于凭据相关发现，绝不暴露原始值：区分有效凭据材料与占位符、fixture、示例及允许列出的指纹；仅报告类型、位置和经过脱敏的证据，并且只有在确认发生暴露时，才建议撤销、轮换或修复历史记录，审计期间不得执行这些操作。
- [ ] 跟踪不受信任的输入流向 SQL、shell、模板、HTML、文件路径、URL、反序列化、重定向以及其他对注入敏感的接收点。
- [ ] 检查身份验证、授权、租户或所有权隔离、权限转换、不安全的直接对象访问，以及默认拒绝行为。
- [ ] 检查信任边界处的验证、规范化、大小和速率限制、不安全的文件操作，以及破坏性操作的确认或防护措施。
- [ ] 在确定严重性之前，根据实际调用路径、框架行为、配置和当前官方指南验证安全发现。
- [ ] 检查编译器、代码检查工具、类型检查器、测试、打包和 CI 配置中是否存在跳过门禁、忽略失败、环境漂移和不可复现的交付。
- [ ] 验证成功的打包是否生成了预期的入口点、资源、元数据、目标平台和可部署产物；仅有零退出码并不能证明构建产物可以交付。
- [ ] 找出过时的 skip、quarantine、allow-failure、continue-on-error 以及警告抑制路径，这些路径会让必需的信号看起来是绿色通过。
- [ ] 检查配置完整性、必需的环境验证、不安全的回退、缺失的示例，以及本地、CI 和部署设置之间的差异。

### 3. 审查可维护性和依赖项

- [ ] 在函数、处理程序、模块、配置和集成代码之间寻找有证据支持的重复；区分共享的领域概念与偶然相似。
- [ ] 识别过度抽象、未使用的扩展点、过多的工厂或包装器、并行机制，以及重复实现已声明平台能力的自定义工具。
- [ ] 在合并重复代码或移除抽象之前，检查生命周期和所有权边界、有意的解耦、依赖注入或测试接缝、框架要求、公开扩展契约，以及预期的独立演进。
- [ ] 检查复杂度热点、过长的方法、上帝模块、过深的嵌套、过多的参数、布尔模式 API、误导性的命名，以及混杂的职责。
- [ ] 检查算法是否存在提前退出错误、重复键丢失、边界错误、无界工作量、重复扫描、迭代期间发生变更，以及隐藏的共享状态。
- [ ] 检查本应明确配置或命名策略、却被硬编码的运行值、URL、超时、限制、标识符和特定环境行为。
- [ ] 跨外部契约、DTO、服务、持久化和存储追踪同一个概念；只有在没有显式序列化器、代码生成或 ORM 边界映射可以解释时，才标记同义词或大小写漂移。
- [ ] 审查依赖项漏洞、支持状态、许可证或运行时限制、重复包、未使用的包，以及可信的替换或移除机会。
- [ ] 根据已安装版本以及易受攻击的 API 或功能是否可达，验证漏洞发现；区分受影响的代码与仅存在于锁文件中的包。
- [ ] 只有在检查所需功能的对等性、迁移范围、维护情况、许可证、安全历史和领域特定行为之后，才建议使用原生能力、现有依赖项或外部替代方案。
- [ ] 查找不可达代码、未使用的导入和导出、已注释掉的实现、过时的标志、失效的兼容性垫片，以及与后继实现并存的替代代码。
- [ ] 在报告可以安全删除之前，根据反射、注册、框架发现、配置、序列化、模板和外部入口点确认死代码发现。

### 4. 审查可诊断性、并发性和生命周期

- [ ] 检查日志是否结构化、日志级别是否正确、是否可采取行动、是否在请求或作业范围内具有关联性，以及是否不包含机密和过多的负载数据。
- [ ] 验证关联上下文是否跨越出站调用、队列、重试、计划任务和脱离式异步边界，而不是只存在于第一条请求日志中。
- [ ] 检查关键路径上的指标、跟踪、健康信号和错误上下文；仅在运维人员需要借此检测或诊断故障时，才要求具备可观测性。
- [ ] 在可达的并发路径上追踪共享可变状态、锁顺序、原子性、异步任务所有权、取消、重试和竞态窗口。
- [ ] 检查跨越 await 或 yield 点的读-修改-写操作，并为共享文件、子进程、终端或 OS 资源以及重复的用户触发建立资源/访问器时间线；包括当前进程之外的访问器。
- [ ] 检查异步路径中的阻塞 I/O 或同步等待、无界并发、孤立任务、死锁、TOCTOU 隐患以及非线程安全资源。
- [ ] 检查启动顺序、依赖就绪状态、配置验证、快速失败行为、信号处理、优雅关闭和在途工作排空。
- [ ] 清点启动和运行时获取的资源，然后在成功、失败、超时、取消以及重复收到关闭信号时，将每项资源与按安全的反向依赖顺序执行的幂等清理相匹配。
- [ ] 保持探针语义的区分：存活性证明进程可以恢复，而不检查脆弱的依赖项；就绪性则在所需依赖项和初始化可用之前拒绝流量；两种探针都不应产生实质性负载或副作用。

### 5. 验证发现并报告

- [ ] 仅在外部 API、标准、漏洞和运行时行为可能改变某项发现时进行研究，并使用与相关版本匹配的官方来源。
- [ ] 在确认候选问题之前，过滤掉框架约定、生成代码、受限的管理路径、测试、示例和已记录的权衡。
- [ ] 在可行的情况下，使用安全命令、测试、最小调用链或完整的静态失败路径复现高严重性问题。
- [ ] 对每个候选问题应用实质性和可接受替代方案门槛。要求在仓库已有证据表明的规模下，存在具体的失败、安全、交付、可运维性或重复维护影响。当当前权衡合理时，拒绝吹毛求疵、个人偏好、理论上的纯粹性、泛化的最佳实践、假设性规模，以及仅仅不同的实现方式；当多种设计都可行时，要求关注结果或约束，而不是某一种偏好的风格。
- [ ] 在每个发现的必要修复方案中放置一个直接相关的 Markdown 实践链接：优先使用当前的官方文档或规范；只有在官方来源无法解决该权衡时，才使用信誉良好的一手工程资料。打开并验证来源；该来源必须支持所提出的机制，而不仅仅是缺陷类别。拒绝搜索结果链接、泛化的最佳实践文章和装饰性引用。
- [ ] 根据可利用性、数据或可用性影响、交付阻塞、复发性和修复紧迫性，将发现分类为 `P0`-`P3`。
- [ ] 对每个发现包含位置、证据、触发条件或失败路径、影响、置信度、当前权衡为何不可接受，以及最小可信修复方案，同时允许等效解决方案。
- [ ] 根据风险降低程度和依赖关系安排修复顺序，而不是按文件顺序或检测器类别排序。
- [ ] 当无法在没有可信替代方案的情况下验证必要的安全环境、高风险行为或权威契约时，使用 `BLOCKED`；对于有证据表明尚未解决的 `P0/P1`、要求通过但失败的交付门禁，或已证明的不安全行为，使用 `FAIL`；仅对已验证但不阻塞的问题使用 `CONCERNS`，只有在必需检查完成且没有实质性发现时才使用 `PASS`。
- [ ] 返回包含已执行检查、排除范围、已验证发现、未验证候选问题以及代码库剩余风险的判定结果。

## 输出契约

```markdown
# Codebase Audit

**Verdict:** PASS | CONCERNS | FAIL | BLOCKED

## Scope and baseline
- Stack, entrypoints, and exclusions
- Commands and environments checked
- Static and runtime evidence available

## Health summary
| Area | Status | Evidence |
|---|---|---|
| Security | PASS / CONCERNS / FAIL | ... |
| Delivery | PASS / CONCERNS / FAIL | ... |
| Maintainability | PASS / CONCERNS / FAIL | ... |
| Dependencies and dead code | PASS / CONCERNS / FAIL | ... |
| Diagnosability, concurrency, lifecycle | PASS / CONCERNS / FAIL | ... |

## Findings
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete codebase defect | Location, trigger or failure path, evidence, confidence, material impact at evidenced scale, and why the current tradeoff is not acceptable | Smallest credible correction, expected effort, and a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent valid solutions |

Use `None` when no candidate survives the evidence, materiality, context, and acceptable-alternative gates.

## Remediation order and residual risks
Dependency-aware next actions, blind spots, and unverified candidates.
```
