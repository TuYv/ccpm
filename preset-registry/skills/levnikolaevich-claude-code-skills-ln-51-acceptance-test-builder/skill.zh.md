# 验收测试构建器

**目标：** 针对已声明的需求，通过用户或外部系统可观察的边界，交付最小且可信的验收测试组合。只能修改获准的测试和测试文档；实施有依据的新增、更新、合并和删除，不得修复产品代码。

**执行契约：** 有序复选框是完成定义。内部将每项跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；读取、委派或工具失败都不能作为证明。每个部分完成后重新核对各项。返回前解决所有 `PENDING` 项，并仅统计 `PROVEN` 和 `CLEARED`；根据技能的判定和批准规则处理每个缺口。

保留用户意图、范围和现有授权。继续执行已授权的工作；仅针对有重大影响的未解决选择或所需的外部批准提出询问。根据实际风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方式。

将等价的用户或仓库证据视为有效输入；其他技能、命名工件或完整生命周期都不是前置条件。尽可能保留源需求和决策标识符。将复用的证据绑定到相关源版本、未提交更改、配置和环境；发生更改时，仅使受影响的声明失效。

继续执行时，在恢复工作前重新核对任务、现有授权、当前状态和未解决的证据。对于长期工作，返回一份精简的继续记录，或更新已获授权的任务工件；只读技能不持久化该记录。区分工件是否就绪、行为是否已验证，以及是否有权执行外部操作。

在任何必需的批准之前，先准备已获授权的工作。如果某条指令阻止了进展，指出其确切来源并说明尚未解决的边界；不得仅因一般性谨慎而臆造批准门槛。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 工作区安全 | Git 状态、差异、仓库说明，以及分支或工作树检查 | 编辑前始终执行 | 当用户更改无法安全区分时停止 |
| 现有测试约定 | 文件列表、搜索、清单、运行器配置、CI，以及定向读取 | 选择项目原生的运行器、布局、fixture 和命令时 | 遵循最近的受维护测试模式 |
| 行为和接线 | 语言服务器或主机原生的代码智能 | 定位可观察入口、注册、使用方和状态边界时 | 缩小搜索范围并直接检查 |
| 测试实现 | 原生编辑工具和项目生成器 | 创建测试、fixture、辅助工具和必要的测试文档时 | 使用符合项目惯例的最少文件；绝不手动编辑生成状态 |
| 可观察执行 | 仓库定义的 shell 命令、浏览器、API 客户端、CLI 或一次性集成环境 | 证明 UI、协议、命令或持久状态结果时 | 返回 `INCOMPLETE`，并指出确切缺失的检查 |
| 外部契约 | 与版本匹配的官方文档或规范 | 预期行为依赖当前外部 API 或标准时 | 标记为 `UNVERIFIED`；不要编码未经验证的预期结果 |

切勿针对生产环境或未经批准的外部目标运行验收测试。不要部署、发布、迁移共享数据、轮换凭据，也不要仅为让测试通过而接受发生变化的输出。

## 证据规则

- 从需求、公开契约、示例、不变量或独立参考中推导预期行为；切勿从被测实现中的计算逻辑推导预期行为。
- 优先采用终端性的、用户可见的结果，而不是中间状态、模拟调用、日志行或内部方法结果。
- 仅对确定性、可审查的契约使用 golden 文件或快照。更新预期输出属于规范变更，而不是测试验证。
- 使设置、数据分配、执行、清理和重跑行为可复现；在重试或清理掩盖首次失败之前保留首次失败信息。
- 一条通过的命令只能证明它实际执行到的环境和场景。明确说明每个未覆盖的单元格和不可用的边界。
- 不要测试语言、框架、包、数据库厂商或其他通用行为；只测试依赖于仓库自有可观察契约、配置、集成或策略的内容。
- 将 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 和 `NO_TEST` 视为组合决策，并与执行结果区分开来。不要默认使用 `ADD`；当现有证据、整合、退役或接受剩余风险是更好的选择时，应采用相应决策。
- 仅当测试依据已经过时，或证据表明所有仍需覆盖的独特材料行为、故障模式、预言强度和有用的失败定位能力仍得到覆盖时，才删除或合并测试。

## 检查清单

### 1. 确定变更边界

- [ ] 明确需求、验收标准、参与者、受保护结果、可观察契约、明确的非目标、已批准的组合决策、允许的测试路径和允许的测试文档路径；将推断出的体验质量标记为假设。
- [ ] 阅读适用的仓库说明，并在编辑前检查 Git 状态、未跟踪文件、生成区域和现有用户变更。
- [ ] 检测项目原生运行器、目录布局、命名方式、fixture、设置、清理、环境配置和 CI 调用方式。
- [ ] 清点受需求或契约影响的现有测试，并在创建新测试前映射其实际预言。
- [ ] 将每项需求映射到能够证明它的边界：UI、API、CLI、消息、集成、文件或持久状态。
- [ ] 识别场景所需的凭据、服务、账户、端口、设备、浏览器、数据集和破坏性影响。
- [ ] 当不存在安全目标、可靠的预期契约或可分离的工作区时，在编辑前返回 `BLOCKED`。

### 2. 设计可复现的验收证据

- [ ] 为每项需求定义受保护结果、缺陷类别、设置、操作、终端结果、独立预言、预期证据和清理方式。
- [ ] 为每个受影响的测试和材料风险确认或推导出一个组合操作。当不存在已批准的策略时，根据影响、合理的失败可能性、独特性、可信度和维护成本论证该操作；使用现有证明、其他控制措施或接受的剩余风险记录 `NO_TEST`。
- [ ] 对重大的用户可观察业务风险，优先采用确定性的端到端证据。仅当更窄的、贴近生产形态的契约或集成边界仍能更确定或更精确地证明终端结果时，才使用它；切勿用单元实现检查替代验收证据，也不要覆盖可观察契约中不存在的内部细节。
- [ ] 仅当无效输入、授权、边界、部分失败、重试、幂等性、恢复和兼容性行为可能实质性改变受保护结果时，才将其纳入测试。
- [ ] 分配唯一或命名空间隔离的测试数据，并在时钟、随机性、区域设置、排序和并发性影响可复现性时对其进行控制。
- [ ] 当模拟会绕过验收所需的行为时，使用真实依赖或经过批准的模拟器；固定版本，并验证就绪状态和重置行为。
- [ ] 对于确定性输出，根据独立契约推导 golden 或 diff 预期，并使工件足够小以便审查。
- [ ] 对于非确定性输出，断言稳定的不变量和语义字段，而不是通过归一化消除失败或对噪声进行快照。
- [ ] 根据可观察契约和区域设置策略，使用稳定的、项目原生的语义定位器（角色、可访问名称、标签）或显式 ID/测试钩子。避免依赖样式、位置、时间和偶然的结构。当文案属于需求时，单独处理精确文案断言；当存在可靠的语义定位器时，不要仅为添加钩子而要求产品进行修改。
- [ ] 当证据是临时的、受兼容性约束的、针对特定事件的，或与不断变化的契约耦合时，定义所需的或诊断性的门禁，以及审查或退役触发条件。

### 3. 在测试范围内实施

- [ ] 在现有项目布局中创建或更新测试，使用行为导向的名称和失败消息，明确指出被违反的要求、受保护的结果以及检测到的缺陷。
- [ ] 实施获批准的 `MERGE` 和 `DELETE` 操作，不遗留已被取代的测试、fixture、快照、辅助工具、注册项或 CI 条目；通过仓库原生的路径、名称、标签或任务证据保留替换追溯性。
- [ ] 仅当维护中的 fixture 和辅助工具的默认值及副作用仍然清晰可见时才复用它们；避免为单个场景新增抽象。
- [ ] 在缺少前置条件时让 setup 快速失败，并确保 cleanup 在成功、断言失败、超时、取消或部分 setup 之后均可安全执行。
- [ ] 确保测试可重复运行且具有幂等性；不得依赖执行顺序，也不得静默复用上一次运行遗留的状态。
- [ ] 仅当贡献者无法据此配置、运行、解释或清理新增证据时，才添加范围最小的测试文档。
- [ ] 不得编辑生产代码、弱化断言、在缺乏证据时延长超时时间、跳过失败用例，或重新生成预期产物以取得通过结果。
- [ ] 检查 diff，确认不存在无关格式变更、生成文件变动、机密信息、环境特定路径以及超出获批准范围的更改。

### 4. 执行并保留证据

- [ ] 先运行受影响范围最小的场景，然后运行相关测试套件以及仓库要求的 gate（如有）；当操作仅移除证据时，运行替代证据或最接近的保留证明。
- [ ] 记录命令、工作目录、环境类别、目标、版本、退出状态、持续时间、产物以及实际执行的场景。没有选中的测试或全部跳过的输出不能证明验收通过。
- [ ] 保留首次失败所需的输出、seed、顺序、请求、响应、截图、diff 或持久状态，以便复现缺陷。
- [ ] 在修改测试之前，区分产品失败、测试缺陷、环境失败、依赖不可用和不稳定证据。
- [ ] 如果有效测试暴露出产品缺陷，保留失败的验收证据并报告最小复现步骤；绝不修复产品代码。在安全的情况下，继续进行独立的范围内测试工作。
- [ ] 当状态所有权或幂等性具有实质影响时，验证 cleanup，并至少重新运行受影响的场景。
- [ ] 除非用于诊断非确定性问题，否则避免重试；重试不得将初始失败转化为静默通过。

### 5. 完成时避免过度声明

- [ ] 将每项要求和受保护的结果映射到最终测试路径或 `NONE`、命令或替代控制、判定依据或接受的风险，以及结果 `PASS`、`FAIL`、`BLOCKED` 或 `UNPROVEN`。
- [ ] 核对计划中的操作与实际执行的测试组合，包括有依据的偏差，并报告新增、更新、合并和删除测试的净数量，不得将数量视为质量目标。
- [ ] 当所有获批准的测试组合操作均已实施，且所需证据记录了可信的 `PASS`、产品 `FAIL` 或有依据的 `NO_TEST` 控制时，使用 `COMPLETE`。未解决的测试缺陷不属于已完成的证据；该判定不代表产品正确性已获认证。
- [ ] 当仍有安全工作未完成，或环境、依赖、测试缺陷或中断阻碍可信执行时，使用 `INCOMPLETE`；说明确切的剩余操作或检查。
- [ ] 当无法安全实施相关操作、要求缺乏可靠的判定依据，或工作区无法得到保护时，使用 `BLOCKED`。

- [ ] 独立于实现保留源验收标识符和预期行为；报告已选择/已执行/已跳过的范围，绝不将相关测试执行数为零视为通过依据。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、判定结果和适用的清理工作。修正报告或经授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时，每个字段可使用一行；省略空表格，不要复制链接的产物：

1. **结果：** Skill 专属判定及有证据支持的结果。
2. **范围：** 已审查/已变更的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill 专属字段；区分事实、推断和未经验证的声明。链接产物；适用时使用表格。列出变更的测试/文档文件、合并或删除的替代证据、测试组合的净变化、确切命令和产物、保留的产品失败复现、清理工作、不可用的环境以及排除的单元格。
4. **验证：** 检查项/结果、不可用的证据以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；剩余风险及需要作出的决策。

**Skill 专属证据：** 需求/受保护的结果 → 现有证据 → 测试组合操作 → 最终测试路径或 `NONE` → 独立预言机/命令 → 门禁/结果 → 退役触发条件。列出变更的测试/文档文件、用于合并或删除的替代证据、测试组合的净变化、确切命令和产物、保留的产品失败复现、清理工作、不可用的环境以及排除的单元格。证据完整不代表产品正确性。
