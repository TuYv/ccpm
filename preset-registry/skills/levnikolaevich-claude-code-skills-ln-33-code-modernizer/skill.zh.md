# 代码现代化

**目标：** 仅当新设计能够可衡量地减少人工工作流程阻力、维护成本、风险、依赖重复或交付产物成本时，才对边界明确的能力进行现代化改造。保留现有行为，隔离迁移过程，并回退无法创造净价值的更改。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。按顺序处理每一项，只有在其操作和所需证据均已完成时，才能将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回之前，将此技能的裁决、决策和审批规则应用于每个未完成项目，并在回复开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 当前机制及其使用者 | 原生文件搜索，加上语言服务器或宿主原生代码智能 | 映射契约、调用方、配置、数据、生命周期和测试 | 对导入、符号、路由和配置进行小范围搜索并直接读取 |
| 现有平台能力 | 清单文件、锁文件、运行时 API 和当前官方文档 | 避免为已有可用功能引入新依赖或自定义代码 | 仓库示例和源代码检查；如果无法获取当前文档，则将能力标记为 `UNVERIFIED` |
| 外部替代候选项 | 官方包注册表、源代码仓库、文档、发布记录、安全公告和许可证数据 | 将维护中的软件与自定义实现进行比较 | 基于第一手来源开展网络研究；不要仅依赖流行度榜单 |
| 基线和价值 | 构建输出、包分析、代码清单、基准测试、缺陷或维护证据 | 定义现代化改造必须实现的改进 | 可复现的静态计数，并记录其范围和局限性 |
| 安全迁移 | Git 隔离、聚焦的编辑、原生包管理器和仓库生成命令 | 替换一项边界明确的能力及其使用者 | 如果无法保护用户更改或生成状态，则停止 |
| 验证 | 仓库定义的构建、代码检查、类型检查、测试、冒烟测试、打包和运行时检查 | 迁移前以及每个保留步骤之后 | 当现有证据无法证明实质性契约时，选择最小的组合操作 |
| 交付产物分析 | 现有的包分析器、大小报告、启动性能分析或依赖报告 | 包大小、加载路径或运行时成本属于目标的一部分 | 使用可复现的文件和压缩规则比较构建产物 |

不要仅仅因为存在外部包就替换运行正常的自定义代码。不要引入无人维护的依赖、接受不兼容的许可证，也不要在了解所有使用者和回滚条件之前移除旧路径。

## 证据规则

- 从具体缺陷、成本、重复、已不受支持的机制、审计发现或用户目标出发。
- 比较系统净复杂度：移除的代码和风险，减去新增的依赖、适配器、运维和迁移成本。
- 对外部候选项的主张，需要有关于维护、安全性、许可证、运行时支持和 API 适配性的当前第一手证据。
- 包大小或性能价值需要可比的测量结果；仅减少代码行数并不能证明设计更优。
- 除非请求明确授权进行契约迁移，否则应保留公开行为。

## 检查清单

### 1. 明确现代化改造目标

- [ ] 明确有边界的能力、受保护的结果、当前痛点、受影响的用户、开发者或运维人员、成功指标、约束条件以及明确的非目标；标注缺乏依据的意图推断。
- [ ] 阅读仓库说明，并检查 Git 状态、生成的文件、包管理器策略以及用户当前的更改。
- [ ] 盘点当前实现、公共契约、使用方、配置、持久化数据、运行时注册、测试以及运维流程。
- [ ] 确定必须改善的具体工作流、维护、安全性、兼容性、重复、包体积、启动或交付成本。
- [ ] 在更改代码之前建立行为基线和相关的量化基线；对于人工工作流，应采用可复现的观察指标，例如所需步骤或概念、首次获得有意义结果所需的时间、错误理解难度以及恢复工作量。
- [ ] 隔离工作，确保每个迁移步骤都可以回滚，而无须触及无关更改或用户拥有的更改。
- [ ] 建立本次运行专属的资源台账，记录创建的每个绝对路径、工作树、进程 ID、缓存、报告和临时制品；切勿将预先存在的资源登记为清理目标。
- [ ] 如果现代化改造仅涉及美化、依赖对未来规模的推测，或无法为受保护的结果定义可复现的收益，则以 `NO_CHANGE` 停止。

### 2. 评估最简单且可信的设计

- [ ] 在寻找新软件包之前，检查语言、运行时、框架、平台以及已声明依赖项的能力。
- [ ] 识别可以直接移除的过时兼容路径、并行机制、未使用的扩展点、重复集成以及过渡适配器。
- [ ] 对于外部候选方案，评估其功能适配度、API 稳定性、维护活跃度、安全历史、许可证、所有权、发布节奏、大小、运行时支持以及生态系统兼容性。
- [ ] 依据与预期版本相匹配的官方文档、仓库发布信息、安全公告和软件包元数据，验证候选方案的声明。
- [ ] 检查迁移指南、破坏性变更、配置模型、生命周期、故障行为、传递依赖以及退出策略。
- [ ] 为替代候选方案建立语义差异台账：输入规范化、Unicode/时间/日期行为、精度、顺序、错误、取消、流式处理、并发、安全限制，以及与当前契约相关的其他边缘行为。
- [ ] 在各方案均可信的情况下，比较保留现状、原地简化、使用现有平台能力、采用外部软件以及移除能力；优先选择在不掩盖事实或削弱控制的前提下，能够消除繁琐工作的最短安全路径。
- [ ] 在适用时，估算减少的工作流步骤和概念、达成结果的时间和恢复成本变化、删除的代码、增加的适配器、依赖项和包体积变化、迁移工作量、运维变化、回滚难度以及残余的锁定风险。
- [ ] 选择有证据支持且价值风险比最佳的方案，而不是最新或最流行的方案。
- [ ] 将选定的方案标记为 `SELECTED`，并将每个经过考虑但未被选中的方案标记为 `REJECTED`，同时记录决定各项选择的证据或权衡因素。
- [ ] 当许可证、公共契约、持久化数据迁移、供应商承诺或不可逆的运维权衡会改变产品意图时，请求用户指示；在一次性环境之外实施迁移始终需要明确授权。

### 3. 执行有边界的迁移

- [ ] 将当前的外部契约、重要故障以及数据或配置兼容性映射到现有证据；在获批的测试范围内实施 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有合理依据的 `NO_TEST`，移除已被取代的测试资产，并为临时的特征刻画或兼容性证据设定移除触发条件。
- [ ] 当新旧实现可以使用相同的代表性输入和对抗性输入运行时，在替换边界使用差异测试或特征刻画用例。
- [ ] 在一个明确的边界引入替代实现，而不是在整个代码库中混用新旧机制。
- [ ] 使用包管理器原生的命令和生成命令来处理依赖项及生成的状态；不要手动编辑锁文件或生成的工件。
- [ ] 更新该有边界能力所需的调用方、类型、配置、依赖注入、路由、事件、序列化、测试、构建脚本和文档。
- [ ] 仅在实际使用方确有需要时保留向后兼容性，并为每个临时适配器定义移除条件。
- [ ] 使用一次性副本准备并测试持久化数据或配置迁移，明确迁移顺序、可恢复性、混合版本行为、备份/恢复证据、回滚及故障恢复；仅当用户指定目标环境并授权执行已演练的操作时，才在其他位置应用这些迁移。
- [ ] 只有在搜索和运行时连线检查表明没有剩余使用方后，才移除旧实现。
- [ ] 在移除被报告为未使用的依赖项或模块之前，检查静态导入扫描无法发现的动态导入、反射、插件/配置注册、代码生成、构建脚本、CLI 和可选运行时路径。
- [ ] 检查差异中是否存在无关的重构、格式变更噪声、重复依赖项、调试代码和意外的公共契约变更。

### 4. 验证并保留或放弃

- [ ] 每完成一个迁移步骤后，立即运行聚焦的契约测试和回归测试。
- [ ] 运行仓库要求的构建、代码检查、类型检查、测试、冒烟测试、打包和应用启动检查。
- [ ] 在同等条件下，将约定的工作流、维护、依赖项、包体积、启动、性能或缺陷指标与基线进行比较。
- [ ] 对于包体积相关工作，应比较实际构建组成、解析后和压缩后的大小、分块、加载行为及源映射，而不应只比较包元数据。
- [ ] 分别评估入口点和路由的关键路径：总字节数可能有所下降，但初始传输、请求瀑布流、解压、解析/编译、执行或缓存失效可能变得更糟。
- [ ] 在更改导入或包元数据之前，对照实际的打包器依赖图、模块格式、导出、副作用元数据和目标浏览器/运行时，验证摇树优化和去重声明。
- [ ] 检查所保留设计的安全公告、许可证、运行时支持、包来源以及新增的传递依赖项。
- [ ] 当迁移失败的代价高昂或难以发现时，演练回滚或移除机制。
- [ ] 只有当所需行为和验证均通过，并且实现了所定义的净价值时，才将迁移标记为 `KEEP`。
- [ ] 当价值未经证实、出现回归或长期复杂性增加时，将其标记为 `DISCARD`，并彻底还原有边界的变更。
- [ ] 只有在确认其归属后，才移除未保留的适配器、检测工具、功能标志、包和生成的工件；仅清理本次运行所拥有的账本路径和确切的进程 ID，同时保留脏工作树或预先存在的工作树以及已报告的证据。

### 5. 最终确认并报告

- [ ] 确认在保留某项迁移后，没有遗留任何过时的实现、导入、注册、配置、文档或依赖。
- [ ] 对最终保留的状态运行所有相关验证，并将最终差异与最初的现代化改造范围进行比较。
- [ ] 报告已考虑的替代方案、证据、已应用和已放弃的迁移、代码与依赖变化量、测量结果、验证结果及回滚状态。
- [ ] 识别残留的自定义代码、兼容性适配器、迁移步骤、运维变更和外部依赖风险。
- [ ] 当所选的有界设计已被完全保留并通过验证时，使用 `MODERNIZED`；当一个可独立确保安全的子集被保留，且明确列出剩余工作时，使用 `PARTIAL`；当所有迁移均被放弃且基线已恢复时，使用 `NO_CHANGE`；当缺少授权、安全性证据或必要验证时，使用 `BLOCKED`。

```markdown
# Code Modernization

**Verdict:** MODERNIZED | PARTIAL | NO_CHANGE | BLOCKED

## Target and baseline
- Capability, protected outcome, affected human workflow, and current cost
- Contracts and consumers
- Behavioral, workflow, and quantitative baselines

## Alternatives
| Option | Evidence | Net value | Risk | Decision |
|---|---|---|---|---|
| ... | ... | ... | ... | SELECTED / REJECTED |

## Migration results
| Step | Change | Verification | Metric delta | Decision |
|---|---|---|---|---|
| ... | ... | ... | ... | KEEP / DISCARD |

## Final state and residual risks
Removed and retained code, dependencies, adapters, measurements, rollback, limitations, and follow-up decisions.

## Test portfolio decisions
Affected evidence, protected contract, action, oracle, gate and result, removed testware, and any review or retirement trigger; use `None` when existing proof remained sufficient and unchanged.

## Evidence artifacts
Run-owned paths and hashes for characterization evidence, exact commands, final diff, rollback, and cleanup proof.
```
