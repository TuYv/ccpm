# 代码现代化

**目标：** 仅当新设计能够以可衡量的方式降低人工工作流摩擦、维护成本、风险、依赖重复或交付产物成本时，才对范围明确的能力进行现代化改造。保持行为不变，隔离迁移，并回退无法创造净价值的变更。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框标记为 `PENDING`，然后使用具体证据将其解析为 `PROVEN`，使用表明其条件触发器不存在的证据将其解析为 `CLEARED`，或解析为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不能作为证明。
返回前，解析每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，对每个 `UNPROVEN` 项应用此技能的判定、决策和审批规则，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 回退方案 |
|---|---|---|---|
| 当前机制和使用者 | 原生文件搜索，加上语言服务器或宿主原生代码智能工具 | 梳理契约、调用方、配置、数据、生命周期和测试时 | 针对导入、符号、路由和配置进行范围明确的搜索，并直接读取 |
| 现有平台能力 | Manifest、lockfile、运行时 API 和当前官方文档 | 避免为已有功能引入新依赖或编写自定义代码时 | 仓库示例和源码检查；如果无法获取当前文档，则将该能力标记为 `UNVERIFIED` |
| 外部替代候选项 | 官方软件包注册表、源码仓库、文档、发布信息、安全公告和许可证数据 | 比较维护良好的软件与自定义实现时 | 基于主要来源的网络调研；不要仅依赖流行度列表 |
| 基线和价值 | 构建输出、包分析、代码清单、基准测试、缺陷或维护证据 | 定义现代化改造必须改善的内容时 | 使用记录了范围和局限性的、可复现的静态计数 |
| 安全迁移 | Git 隔离、针对性编辑、原生包管理器和仓库生成命令 | 替换一个范围明确的能力及其使用者时 | 如果无法保护用户变更或生成状态，则停止 |
| 验证 | 仓库定义的构建、lint、类型检查、测试、冒烟测试、打包和运行时检查 | 迁移前以及每个保留步骤之后 | 当现有证据无法证明重要契约时，选择最小化的组合操作 |
| 交付产物分析 | 现有包分析器、大小报告、启动配置文件或依赖报告 | 目标包含包大小、加载路径或运行时成本时 | 按可复现的文件和压缩规则比较构建产物 |

不要仅仅因为存在外部软件包，就替换运行正常的自定义代码。不要引入无人维护的依赖、接受不兼容的许可证，或在所有使用者和回滚条件都得到理解之前移除旧路径。

## 证据规则

- 从具体缺陷、成本、重复、无支持的机制、审计发现或用户目标出发。
- 比较系统的净复杂度：移除的代码和风险，减去新增的依赖、适配器、运维和迁移成本。
- 外部候选方案的主张必须有当前的一手证据支持，涵盖维护、安全性、许可证、运行时支持和 API 适配性。
- 捆绑包或性能价值必须有可比的测量结果；仅减少代码行数并不能证明设计更优。
- 除非请求明确授权进行契约迁移，否则应保持公共行为不变。

## 检查清单

### 1. 定义现代化目标

- [ ] 明确范围受限的能力、受保护的结果、当前痛点、受影响的用户、开发者或运维人员、成功指标、约束条件和明确的非目标；标记缺乏支持的意图推断。
- [ ] 阅读仓库说明并检查 Git 状态、生成文件、包管理器策略和当前用户更改。
- [ ] 清点当前实现、公共契约、消费者、配置、持久化数据、运行时注册、测试和运维流程。
- [ ] 确定必须改进的具体工作流、维护、安全性、兼容性、重复、捆绑包、启动或交付成本。
- [ ] 在修改代码前建立行为基线和相关的量化基线；对于人工工作流，使用可复现的观察结果，例如所需步骤或概念、获得第一个有意义结果所需的时间、错误理解程度和恢复工作量。
- [ ] 隔离工作，使每个迁移步骤都可以在不触及无关更改或用户自有更改的情况下回退。
- [ ] 从运行开始记录由本次运行负责的资源清单，其中包含每个创建的绝对路径、工作树、进程 ID、缓存、报告和临时构件；绝不要将预先存在的资源登记为清理目标。
- [ ] 如果现代化仅停留在美观层面、依赖推测性的未来规模，或无法定义对受保护结果的可复现收益，则以 `NO_CHANGE` 停止。

### 2. 评估最简单且可信的设计

- [ ] 在搜索新包之前，检查语言、运行时、框架、平台以及已声明依赖项的能力。
- [ ] 确定可以直接移除的过时兼容路径、并行机制、未使用的扩展点、重复的集成和过渡性适配器。
- [ ] 对于外部候选方案，评估功能适配性、API 稳定性、维护活动、安全历史、许可证、所有权、发布节奏、大小、运行时支持和生态系统兼容性。
- [ ] 根据与目标版本匹配的官方文档、仓库发布记录、公告和包元数据，验证候选方案的主张。
- [ ] 检查迁移指南、破坏性变更、配置模型、生命周期、故障行为、传递依赖和退出策略。
- [ ] 为替换候选方案建立语义差距清单：输入规范化、Unicode/时间/日期行为、精度、排序、错误、取消、流式处理、并发、安全限制，以及与当前契约相关的其他边界行为。
- [ ] 在每种方案都可信的情况下，比较保留现状、就地简化、使用现有平台能力、采用外部软件以及移除能力；优先选择能够消除繁琐工作、同时不掩盖事实或失去控制的最短安全路径。
- [ ] 在相关情况下，估算移除的工作流步骤和概念、结果达成时间及恢复工作的变化、移除的代码、增加的适配器、依赖和捆绑包变化、迁移工作量、运维变化、回滚难度以及残余锁定。
- [ ] 选择有证据支持的价值与风险比最佳的方案，而不是最新或最流行的方案。
- [ ] 将选定方案标记为 `SELECTED`，并将每个考虑过但未选定的方案标记为 `REJECTED`，记录决定每项选择的证据或权衡。
- [ ] 当许可证、公共契约、持久化数据迁移、供应商承诺或不可逆的运维权衡会改变产品意图时，请求用户作出决策；在一次性环境之外应用迁移始终需要明确授权。

### 3. 执行有界迁移

- [ ] 将当前外部契约、重要故障以及数据或配置兼容性映射到现有证明；在批准的测试范围内实施 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有充分理由的 `NO_TEST`，移除已被取代的测试工件，并为临时特征描述或兼容性证据设定移除触发条件。
- [ ] 当旧实现和新实现可以针对相同的代表性输入与对抗性输入运行时，在替换边界使用差分测试或特征描述测试用例。
- [ ] 在一个清晰的边界引入替换方案，而不是让新旧机制在整个代码库中交叉混用。
- [ ] 使用原生包管理器命令和生成命令处理依赖项及生成状态；不要手动编辑锁定文件或生成的工件。
- [ ] 更新有界能力所需的调用方、类型、配置、依赖注入、路由、事件、序列化、测试、构建脚本和文档。
- [ ] 仅在确实存在消费者需要时保留向后兼容性，并为每个临时适配器定义移除条件。
- [ ] 针对一次性副本准备并测试持久化数据或配置迁移，明确规定执行顺序、可恢复执行能力、混合版本行为、备份/恢复证据、回滚和故障恢复；只有在用户指定目标环境并授权执行已演练的操作时，才能在其他环境中应用这些迁移。
- [ ] 只有在搜索和运行时接线检查表明没有剩余消费者后，才能移除旧实现。
- [ ] 在移除被报告为未使用的依赖项或模块之前，检查动态导入、反射、插件/配置注册、代码生成、构建脚本、CLI 以及静态导入扫描无法覆盖的可选运行时路径。
- [ ] 检查差异，确认不存在无关重构、格式变更噪声、重复依赖项、调试代码以及意外的公共契约变更。

### 4. 验证并保留或弃用

- [ ] 每完成一个迁移步骤后，立即运行聚焦的契约测试和回归测试。
- [ ] 运行代码库要求的构建、代码检查、类型检查、测试、冒烟测试、打包和应用启动检查。
- [ ] 在等效条件下，将约定的工作流、维护、依赖、包体积、启动、性能或缺陷指标与基线进行比较。
- [ ] 对于包体积工作，应比较实际构建组成、解析后和压缩后的大小、分块、加载行为以及源映射，而不只是包元数据。
- [ ] 分别评估入口点和路由关键路径：总字节数可能减少，但初始传输、请求瀑布、解压缩、解析/编译、执行或缓存失效可能变差。
- [ ] 在更改导入或包元数据之前，针对实际打包器图、模块格式、导出、无副作用元数据以及目标浏览器/运行时，验证 tree-shaking 和去重声明。
- [ ] 针对保留的设计检查安全公告、许可证、运行时支持、包来源以及新增的传递依赖。
- [ ] 当迁移失败的代价高昂或难以检测时，执行回滚或移除机制。
- [ ] 只有在所需行为和验证均通过，且达到已定义的净价值时，才将迁移标记为 `KEEP`。
- [ ] 当价值无法证明、出现回归或长期复杂性增加时，将其标记为 `DISCARD`，并完整回滚有界变更。
- [ ] 只有在其所有权得到证明后，才能移除未保留的适配器、插桩、功能标志、包和生成的工件；仅清理由运行过程拥有的账本路径和确切的进程 ID，保留存在脏变更或预先存在的工作树以及已报告的证据。

### 5. 最终确定并报告

- [ ] 验证在保留迁移之后，没有遗留的实现、导入、注册、配置、文档或依赖。
- [ ] 对最终保留状态运行完整的相关验证，并将最终差异与原始现代化范围进行比较。
- [ ] 报告已考虑的替代方案、证据、已应用和已放弃的迁移、代码和依赖变更量、度量结果、验证结果以及回滚状态。
- [ ] 识别残留的自定义代码、兼容性适配器、迁移步骤、运维变更和外部依赖风险。
- [ ] 当选定的有界设计已完整保留并通过验证时，使用 `MODERNIZED`；当一个可独立安全保留的子集已保留，并明确说明剩余工作时，使用 `PARTIAL`；当所有迁移均被放弃且基线已恢复时，使用 `NO_CHANGE`；当无法获得授权、安全证据或所需验证时，使用 `BLOCKED`。

- Contracts and consumers
- Behavioral, workflow, and quantitative baselines

## Alternatives
| Option | Evidence | Net value | Risk | Decision |
|---|---|---|---|---|
| ... | ... | ... | ... | SELECTED / REJECTED |

## Migration results
| Step | Change | Verification | Metric delta | Decision |
|---|---|---|---|---|
| ... | ... | ... | ... | KEEP / DISCARD |

## Final state and residual risks
Removed and retained code, dependencies, adapters, measurements, rollback, limitations, and follow-up decisions.

## Test portfolio decisions
Affected evidence, protected contract, action, oracle, gate and result, removed testware, and any review or retirement trigger; use `None` when existing proof remained sufficient and unchanged.

## Evidence artifacts
Run-owned paths and hashes for characterization evidence, exact commands, final diff, rollback, and cleanup proof.
