# 代码现代化

**目标：** 仅当新设计能够切实减少人工工作流摩擦、维护成本、风险、依赖重复或交付产物成本时，才对有界能力进行现代化改造。保持行为不变，隔离迁移；对于无法产生净价值的更改，应予以回退。

**执行契约：** 有序复选框构成完成定义。将每一项内部跟踪为 `PENDING`、有具体证据证明的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个部分后重新核对各项。在返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将技能的判定和批准规则应用于每个缺口。
保持用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且具有重大影响的选择或所需的外部批准提出询问。根据实际风险调整深度，不得静默跳过检查。保持依赖关系和安全顺序；在此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 当前机制及其消费者 | 原生文件搜索，加上语言服务器或宿主原生代码智能 | 映射契约、调用方、配置、数据、生命周期和测试时 | 使用导入、符号、路由和配置的窄范围搜索，并直接读取相关内容 |
| 现有平台能力 | 清单文件、锁文件、运行时 API 和当前官方文档 | 避免为已有功能引入新依赖或编写自定义代码时 | 查找仓库示例并检查源代码；如果无法获取当前文档，则将该能力标记为 `UNVERIFIED` |
| 外部替代候选项 | 官方包注册表、源代码仓库、文档、发行版本、公告和许可证数据 | 比较维护良好的软件与自定义实现时 | 进行一手来源的网络研究；不要仅依赖热门度列表 |
| 基线和价值 | 构建产物、包分析、代码清单、基准测试、缺陷、维护或其他证据 | 明确现代化必须改进的内容时 | 使用有明确范围和局限性说明的可复现静态计数 |
| 安全迁移 | Git 隔离、聚焦编辑、原生包管理器和仓库生成命令 | 替换某项有界能力及其消费者时 | 如果无法保护用户更改或生成状态，则停止 |
| 验证 | 仓库定义的构建、 lint、类型检查、测试、冒烟测试、打包和运行时检查 | 迁移前以及每个保留步骤之后 | 如果现有证据无法证明某项重大契约，则选择最小化的验证组合 |
| 交付产物分析 | 现有的包分析器、大小报告、启动性能分析或依赖报告 | 包大小、加载路径或运行时成本属于目标时 | 使用可复现的文件和压缩规则比较构建产物 |

不要仅仅因为存在外部包，就替换正常工作的自定义代码。不要引入无人维护的依赖、接受不兼容的许可证，或在所有消费者和回滚条件都得到理解之前移除旧路径。

## 证据规则

- 比较系统净复杂度：移除的代码和风险，减去新增的依赖、适配器、运维和迁移成本。
- 外部候选方案的声明必须有当前的一手证据支持，涵盖维护、安全性、许可证、运行时支持和 API 适配性。
- 只有在具备可比测量结果时，才能证明打包或性能价值；单纯减少代码行数并不能证明设计更好。
- 除非请求明确授权进行契约迁移，否则保留公开行为。

## 检查清单

### 1. 定义现代化目标

- [ ] 明确范围受限的能力、受保护的结果、当前痛点、受影响的用户、开发者或运维人员、成功指标、约束条件和明确的非目标；标记缺乏支持的意图推断。
- [ ] 阅读仓库指令，并检查 Git 状态、生成文件、包管理器策略和当前用户更改。
- [ ] 盘点当前实现、公开契约、消费者、配置、持久化数据、运行时注册、测试和运维流程。
- [ ] 确定必须改进的具体工作流、维护、安全、兼容性、重复、打包、启动或交付成本。
- [ ] 在修改代码前建立行为基线和相关的定量基线；对于人工工作流，使用可复现的观察结果，例如所需步骤或概念、获得第一个有意义结果所需的时间、错误理解程度和恢复成本。
- [ ] 隔离工作，使每个迁移步骤都可以在不触及无关更改或用户自有更改的情况下回滚。
- [ ] 使用运行所属的资源台账，记录每个创建的绝对路径、工作树、进程 ID、缓存、报告和临时工件；绝不将预先存在的资源登记为清理目标。
- [ ] 当证据表明范围内没有值得进行的现代化时，使用 `NO_CHANGE`；当由于缺少必要证据而无法评估一个合理的请求收益时，使用 `BLOCKED`。

### 2. 评估最简单且可信的设计

- [ ] 在搜索新包之前，检查语言、运行时、框架、平台以及已声明依赖项的能力。
- [ ] 识别可以直接移除的过时兼容路径、并行机制、未使用的扩展点、重复集成和过渡性适配器。
- [ ] 对于外部候选方案，评估其功能适配性、API 稳定性、维护活动、安全历史、许可证、所有权、发布节奏、大小、运行时支持和生态系统兼容性。
- [ ] 根据与目标版本匹配的官方文档、仓库发布记录、安全公告和包元数据，验证候选方案的声明。
- [ ] 检查迁移指南、破坏性变更、配置模型、生命周期、失败行为、传递依赖和退出策略。
- [ ] 为替代候选方案建立语义差距台账：输入规范化、Unicode/时间/日期行为、精度、排序、错误、取消、流式处理、并发、安全限制，以及与当前契约相关的其他边界行为。
- [ ] 在每种方案都可信的情况下，比较保留、原地简化、使用现有平台能力、采用外部软件和移除能力；优先选择能够消除繁琐工作、又不掩盖事实或削弱控制力的最短安全路径。
- [ ] 在相关情况下，估算工作流步骤和概念的减少量、结果达成时间和恢复差异、移除的代码、增加的适配器、依赖和打包差异、迁移工作量、运维变更、回滚难度以及残余锁定。
- [ ] 选择有证据支持的价值与风险比最佳的方案，而不是最新或最受欢迎的方案。
- [ ] 将选定方案标记为 `SELECTED`，并将每个已考虑但未选定的方案标记为 `REJECTED`，记录决定每个选择的证据或权衡。
- [ ] 当许可证、公开契约、持久化数据迁移、供应商承诺或不可逆的运维权衡会改变产品意图时，请求用户作出决定；在一次性环境之外应用迁移始终需要明确授权。

### 3. 执行有界迁移

- [ ] 根据现有证据梳理当前外部契约、重要失败情况以及数据或配置兼容性；在获批准的测试范围内实施 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或有充分依据的 `NO_TEST`，移除已被取代的测试工件，并为临时的特征描述或兼容性证据设置移除触发条件。
- [ ] 针对共享的代表性输入和对抗性输入引入差分测试或特征描述测试；旧实现是比对证据，而不是已知缺陷或明确变更行为的裁决依据。根据预期契约解决差异。
- [ ] 在一个清晰的边界引入替代实现，而不是在整个代码库中混用新旧机制。
- [ ] 使用原生包管理器和生成命令处理依赖项及生成状态；不得手动编辑 lockfiles 或生成的工件。
- [ ] 更新有界能力所需的调用方、类型、配置、依赖注入、路由、事件、序列化、测试、构建脚本和文档。
- [ ] 仅在确有实际使用者需要时保留向后兼容性，并为每个临时适配器定义移除条件。
- [ ] 针对可持久化数据或配置迁移，在一次性副本上准备并测试迁移，明确规定执行顺序、可恢复执行能力、混合版本行为、备份/恢复证据、回滚和故障恢复；只有在用户指定目标环境并授权执行已演练的操作后，才能在其他环境中应用迁移。
- [ ] 在移除被报告为未使用的依赖项或模块之前，检查动态导入、反射、插件/配置注册、代码生成、构建脚本、CLIs 以及静态导入扫描无法发现的可选运行时路径。
- [ ] 只有在搜索和运行时接线检查表明不再存在任何使用者后，才移除旧实现。
- [ ] 检查差异，确认不存在无关重构、格式化变更、重复依赖项、调试代码以及意外的公共契约变更。

### 4. 验证并保留或放弃

- [ ] 在每个迁移步骤完成后，立即运行聚焦的契约测试和回归测试。
- [ ] 运行仓库要求的构建、lint、类型、测试、冒烟、打包和应用启动检查。
- [ ] 在等效条件下，将约定的工作流、维护、依赖、包体积、启动、性能或缺陷指标与基线进行比较。
- [ ] 对于包体积工作，应比较实际构建组成、解析后和压缩后的大小、分块、加载行为以及 source maps，而不能只比较包元数据。
- [ ] 分别评估入口点和路由关键路径：总字节数可能下降，但初始传输、请求瀑布、解压、解析/编译、执行或缓存失效情况可能恶化。
- [ ] 在更改导入或包元数据之前，根据实际打包器图、模块格式、导出、side-effect 元数据以及目标浏览器/运行时，验证 tree-shaking 和去重声明。
- [ ] 针对保留的设计检查安全公告、许可证、运行时支持、包来源以及新增的传递依赖项。
- [ ] 当迁移失败的代价较高或难以检测时，执行回滚或移除机制。
- [ ] 只有在必需行为和验证均通过且实现了定义的净价值时，才将迁移标记为 `KEEP`。
- [ ] 解决有界迁移缺陷，并在最终决策前重复受影响的检查；如果价值仍未得到证明、仍存在回归，或净复杂度超过约定的权衡，则标记为 `DISCARD` 并回滚有界变更。
- [ ] 只有在其归属得到证明后，才移除未保留的适配器、检测工具、功能标志、包和生成的工件；只清理由本次运行负责的账本路径和确切的进程 ID，同时保留存在未提交变更或预先存在的工作树以及已报告的证据。

### 5. 最终确定并报告

- [ ] 在保留某项迁移后，确认不存在任何过时的实现、导入、注册、配置、文档或依赖。
- [ ] 确认相关验证覆盖最终保留状态，复用仍然有效的结果，并重新运行因变更或未解决失败而失效的检查。将最终差异与原始现代化范围进行比较。
- [ ] 将选项台账和迁移台账与最终代码、依赖、测量结果及回滚状态进行核对。
- [ ] 识别残留的自定义代码、兼容性适配器、迁移步骤、运维变更以及外部依赖风险。
- [ ] 当选定的有界设计已完整保留并完成验证时，使用 `MODERNIZED`；当一个可独立安全保留的子集已保留且明确列出剩余工作时，使用 `PARTIAL`；当所有迁移均被放弃且基线已恢复时，使用 `NO_CHANGE`；当无法获得授权、安全证据或必要验证时，使用 `BLOCKED`。

## 自检

- [ ] **返回前完成核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或已获授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时，每个字段可使用一行；省略空表格，不要复制链接工件：

1. **结果：** Skill 专属结论及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线以及重要假设。
3. **证据：** 以下 Skill 专属字段；区分事实、推断和未经验证的声明。链接工件；在有用时使用表格。
4. **验证：** 检查项/结果、不可用的证据以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响以及确切的下一步操作；残留风险和所需决策。

**Skill 专属证据：** 能力、受保护的契约、消费者、当前成本以及行为/价值基线。比较已考虑的替代方案，并说明 `SELECTED / REJECTED` 的原因。逐项迁移：变更、验证、可比价值指标以及 `KEEP / DISCARD`。包括代码/依赖和工作流差异、受影响的测试操作、残留自定义代码/兼容性、未完成的过渡工作，以及由本次运行负责的测量/差异/回滚/清理证据。
