# 文档协同撰写工作流

该技能提供了一个结构化工作流，用于指导用户进行协作文档创作。它将充当积极的引导者，引导用户经过三个阶段：上下文收集、精炼与结构化，以及读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到在写文档：`write a doc`、`draft a proposal`、`create a spec`、`write up`
- 用户提到特定文档类型：`PRD`、`design doc`、`decision doc`、`RFC`
- 用户看起来正在开始一项较大规模的写作任务

**初始提议：**
向用户提供一个结构化的协作文档工作流。说明三个阶段：

1. **上下文收集**：用户提供所有相关背景，Claude 提问澄清
2. **精炼与结构化**：通过头脑风暴和编辑，逐步完善每个章节
3. **读者测试**：用一个“全新”Claude（无上下文）测试文档，在其他人阅读前发现盲点

说明这种方法有助于确保文档被他人阅读时也能顺畅理解（包括他们将其粘贴到 Claude 中时）。询问用户是否愿意尝试此工作流，还是偏好自由形式协作。

如果用户拒绝，则按自由形式处理。若用户同意，则进入第一阶段。

## 阶段 1：上下文收集

**目标：** 弥合用户知晓的信息与 Claude 知晓信息之间的差距，为后续提供更智能的引导打下基础。

### 初始问题

先向用户询问文档的元上下文：

1. 这是什么类型的文档？（例如：技术规范、决策文档、提案）
2. 主要读者是谁？
3. 读者阅读后希望产生怎样的影响？
4. 是否有要遵循的模板或特定格式？
5. 是否有其他约束或背景需要说明？

告诉他们可以用简写作答，或按对自己最方便的方式直接抛出信息。

**如果用户提供了模板或提到文档类型：**
- 询问是否有模板文档可共享
- 如果用户提供共享文档链接，使用相应集成进行抓取
- 如果用户提供文件，则读取该文件

**如果用户提到要编辑现有共享文档：**
- 使用相应集成读取当前状态
- 检查是否存在缺少 alt-text 的图片
- 若有图片未提供 alt-text，说明当其他人用 Claude 理解该文档时，Claude 将无法看到图片。询问是否希望生成 alt-text；若同意，请让其把每张图片贴到聊天中，以便生成描述性 alt-text。

### 信息倾倒

初始问题回答完后，鼓励用户倾倒所有已掌握的上下文。可索要以下信息：
- 项目/问题背景
- 相关团队讨论或共享文档
- 为什么未采用替代方案
- 组织背景（团队协作关系、既往事件、政治因素）
- 时间压力或约束
- 技术架构或依赖关系
- 干系人关注点

建议他们无需整理结构，只需尽可能完整输出。提供多种上下文提交方式：
- “意识流”式信息倾倒
- 指向可阅读的团队频道或线程
- 共享文档链接

**如果已有可用集成**（如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），可说明可以直接拉取上下文。

**如果未检测到集成，且在 Claude.ai 或 Claude app 中：** 建议在 Claude 设置中启用连接器，以便直接从消息应用和文档存储拉取上下文。

告知用户完成初始倾倒后会继续提问澄清问题。

**在上下文收集过程中：**

- 如果用户提到团队频道或共享文档：
  - 若可用集成：先说明将读取内容，然后使用对应集成
  - 若不可用集成：说明当前无法访问。建议在 Claude 设置中开启连接器，或直接粘贴相关内容

- 如果用户提到未知实体/项目：
  - 询问是否应搜索已连接工具以进一步了解
  - 在获得用户确认前先不要搜索

- 在用户持续提供上下文时，持续跟踪已掌握与仍不清晰的内容

### 提问澄清

当用户表示已完成初始倾倒（或提供了较完整上下文）后，开始提问以确认理解：

基于上下文缺口生成 5-10 个编号问题。

告知用户可用简写作答（例如：`1: yes, 2: see #channel, 3: no because backwards compat`），或链接更多文档、指向需阅读的频道，或者继续倾倒更多信息。以对方最省时的方式为准。

**退出条件：**
当问题能够检验理解程度，即能在无需再次讲基础知识的情况下讨论边界情况和权衡时，说明上下文已足够。

**过渡：**
询问此阶段是否还有更多要补充的上下文，或是否可以进入文档起草阶段。

若用户想继续补充，允许其补充。准备就绪后进入第二阶段。

## 阶段 2：精炼与结构化

**目标：** 通过头脑风暴、筛选与迭代修订，逐节构建文档。

**对用户说明：**
说明文档将按章节构建。对每一节：
1. 会提问澄清应包含哪些内容
2. 将头脑风暴 5-20 个候选点
3. 用户指明保留/移除/合并的内容
4. 起草该节
5. 通过“手术式”编辑进行精细打磨

先从未知信息最多的章节开始（通常是核心决策/提案），再依次完成其他章节。

**章节顺序：**

如果文档结构已明确：
询问用户希望从哪个章节开始。

建议从未知信息最多的章节起步。对于决策文档，通常是核心提案；对于技术规范，通常是技术方案；总结类章节通常应最后写。

如果用户不确定需要哪些章节：
根据文档类型和模板，建议 3-5 个适合该类型的章节。

询问该结构是否可行，或是否需要调整。

**结构确认后：**

为所有章节先创建初始文档结构，并放置占位文本。

**若可访问 artifact：**
使用 `create_file` 创建一个 artifact。这样 Claude 和用户都可基于同一骨架协作。

告知用户将创建一个所有章节均含占位文本的初始结构。

创建包含所有章节标题与简短占位文本（如`[To be written]`或`[Content here]`）的 artifact。

提供骨架链接，并说明现在可以开始填充每个章节。

**若无法访问 artifact：**
在工作目录中创建一个 Markdown 文件。用合适名称（如 `decision-doc.md`、`technical-spec.md`）。

告知用户将创建包含所有章节占位文本的初始结构。

创建含所有章节标题和占位文本的文件。

确认文件名已创建，并说明现在可以开始填充每一节。

**每个章节操作：**

### 步骤 1：澄清问题

宣布将开始处理[SECTION NAME]章节。提出 5-10 个关于应包含内容的澄清问题：

基于上下文和章节目的生成 5-10 个具体问题。

告知用户可用简写回答，或仅说明哪些内容最重要。

### 步骤 2：头脑风暴

针对[SECTION NAME]章节，按章节复杂度生成 5-20 个可考虑的点。查找：
- 可能被遗忘的共享上下文
- 尚未提及的角度或考虑点

基于章节复杂度生成 5-20 个编号选项。最后可提供继续头脑风暴更多选项的选项。

### 步骤 3：筛选

询问哪些要点应保留、移除或合并。请用户给出简短理由，以帮助把握后续章节的优先级。

示例：
- `Keep 1,4,7,9`
- `Remove 3 (duplicates 1)`
- `Remove 6 (audience already knows this)`
- `Combine 11 and 12`

---
  
**如果用户提供自由格式反馈**（例如“看起来不错”或“我大部分都喜欢，但……”）而不是编号选择，请提取他们的偏好并继续推进。解析他们想保留/移除/修改的内容并执行。

### 第4步：空缺检查

根据他们选择的内容，询问 `[SECTION NAME]` 小节是否有任何重要遗漏。

### 第5步：起草

使用 `str_replace` 将该小节的占位文本替换为实际起草内容。

说明即将基于他们的选择起草 `[SECTION NAME]` 小节。

**如果使用 artifact：**  
起草后，提供 artifact 链接。  

要求其通读并指出需要修改的内容。说明越具体越有助于后续小节的学习，例如：  
“删除 X 要点——该要点已在 Y 中覆盖”  
或  
“让第三段更简洁一些”。

**如果使用文件（非 artifact）：**  
起草完成后，确认完成。  

说明 `[SECTION NAME]` 小节已在 `[filename]` 中起草。要求其通读并指出需要修改的内容。说明越具体越有助于后续小节的学习，例如：  
“删除 X 要点——该要点已在 Y 中覆盖”  
或  
“让第三段更简洁一些”。

**给用户的关键指令（在起草第一小节时包含）：**  
附上提示：与其直接编辑文档，不如请他们指出需要修改的地方。这有助于学习其写作风格以便改进后续小节。例如：  
“Remove the X bullet - already covered by Y”  
或  
“Make the third paragraph more concise”。

### 第6步：迭代改进

当用户提供反馈时：  
- 使用 `str_replace` 进行修改（切勿重新打印整篇文档）
- **如果使用 artifact：**每次编辑后提供 artifact 链接  
- **如果使用文件：**仅确认编辑已完成  
- 如果用户直接修改文档并要求阅读：在心中记录他们的改动，并在后续小节中保留这些偏好（这能显示其偏好）

**持续迭代** 直至用户对该小节满意。

### 质量检查

在连续 3 次无实质性改动的迭代后，询问是否可以删减任何不影响核心信息的内容。

当小节完成后，确认 `[SECTION NAME]` 已完成，并询问是否准备进入下一小节。

**对所有小节重复执行。**

### 接近完成

当接近完成（超过 80% 的小节已完成）时，宣布将重读整篇文档并检查：  
- 跨小节的衔接与一致性  
- 冗余或矛盾  
- 是否有“废话”或泛泛空洞内容  
- 每句话是否都有价值

通读整份文档并提供反馈。

**当所有小节均已起草并完善后：**  
宣布所有小节已起草，并说明将再进行一次完整审阅。  

审阅整体连贯性、逻辑流与完整性。

提供最终建议。

询问用户是否准备进入读者测试，或是否还要继续完善。

---

## 第3阶段：读者测试

**目标：** 使用一个全新、无上下文泄露的 Claude 来验证文档是否对读者有效。

**对用户说明：**  
说明现在将进行测试，检验该文档是否真正适用于读者。这样可以发现作者觉得合理但读者可能困惑的盲点。

### 测试方法

**如果可以访问子代理（例如在 Claude Code 中）：**

直接执行测试，无需用户参与。

### 第1步：预测读者问题

说明将预测读者在尝试学习该文档时可能提出的问题。  

生成 5 到 10 个读者可能会真实提出的问题。

### 第2步：用子代理进行测试

说明这些问题将由一个全新的 Claude 实例进行测试（不使用当前对话上下文）。  

对每个问题，都调用一个子代理，输入仅包括文档内容和该问题。  

总结 Reader Claude 每个问题回答得对和做得不对的地方。

### 第3步：执行额外检查

说明将进行附加检查。  

调用子代理检查是否存在歧义、错误假设或矛盾。  

总结发现的任何问题。

### 第4步：汇报与修订

如果发现问题：  
说明 Reader Claude 在具体内容上遇到了困难。  

列出具体问题。  

说明计划修复这些空缺。  

返回问题小节继续迭代改进。

---

### 如果无法访问子代理（例如在 claude.ai 网页界面）：

用户需要手动完成测试。

### 第1步：预测读者问题

询问人们在尝试阅读该文档时可能会问什么问题，他们会在 Claude.ai 输入什么内容？  

生成 5 到 10 个读者可能会真实提出的问题。

### 第2步：搭建测试

提供测试说明：  
1. 打开一个全新的 Claude 会话：https://claude.ai  
2. 粘贴或分享该文档内容（如果使用已启用连接器的共享文档平台，请提供链接）  
3. 向 Reader Claude 提问所生成的问题  

对每个问题，要求 Reader Claude 提供：  
- 回答内容  
- 是否有任何模糊或不清楚之处  
- 该答案默认读者已具备什么知识/背景  

检查 Reader Claude 的回答是否正确，或是否有误读之处。

### 第3步：额外检查

还应向 Reader Claude 询问：  
- “这份文档中哪些内容可能对读者来说不清晰或模糊？”  
- “这份文档默认读者已经具备哪些知识或背景？”  
- “文档中是否存在内部矛盾或不一致？”

### 第4步：根据结果迭代

询问 Reader Claude 的错误点或卡壳点。说明将修复这些空缺。  

返回问题小节继续进行迭代改进。

---

### 退出条件（两种方式都适用）

当 Reader Claude 能持续正确回答问题且不再出现新盲点或歧义时，文档即完成。

## 最终审阅

当读者测试通过后：  
宣布文档已通过 Reader Claude 测试。完成前应：

1. 建议其自行再做一次通读——文档质量最终由其负责  
2. 建议再次核对所有事实、链接和技术细节  
3. 要求其验证文档是否达到了预期效果

询问是否需要再进行一次审阅，或该工作已完成。  

**如果用户想要最终审阅，就提供一次。否则：**  
宣布文档完成。给出一些最终建议：  
- 考虑在附录中链接本次对话，便于读者了解文档是如何形成的  
- 使用附录在不膨胀正文的前提下补充细节  
- 随着真实读者反馈持续更新文档

## 有效指导建议

**语气：**  
- 简明、程序化  
- 在影响用户行为时简要说明原因  
- 不要“推销”方法，只需执行

**偏离处理：**  
- 如果用户希望跳过某个阶段：询问是否要跳过并改为自由写作  
- 若用户看起来沮丧：承认流程较长，建议加快的方法  
- 始终给用户保留调整流程的主动权

**上下文管理：**  
- 若文中提及内容缺失，主动提问  
- 不要让上下文缺口累积——及时补齐

**Artifact 管理：**  
- 使用 `create_file` 起草完整小节  
- 所有编辑都使用 `str_replace`  
- 每次修改后提供 artifact 链接  
- 大纲发散或头脑风暴不要用 artifact，仅用于对话

**质量优于速度：**  
- 不要草草带过阶段  
- 每次迭代都应带来实质改进  
- 目标是写出一份真正对读者有用的文档
