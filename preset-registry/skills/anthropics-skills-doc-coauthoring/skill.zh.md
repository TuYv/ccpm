# 文档协同写作工作流

该技能提供了一套结构化流程，用于引导用户进行协作文档创建。该技能会充当主动引导者，带领用户完成三个阶段：上下文收集、精炼与结构化，以及读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到在写文档：`write a doc`、`draft a proposal`、`create a spec`、`write up`
- 用户提到具体文档类型：`PRD`、`design doc`、`decision doc`、`RFC`
- 用户似乎正在启动一项较大的写作任务

**初始建议：**
向用户提供一个结构化的协作文档工作流。说明三个阶段：

1. **上下文收集**：用户提供相关上下文，Claude 提出澄清问题
2. **精炼与结构化**：通过头脑风暴和编辑迭代构建每一部分
3. **读者测试**：使用一个新的 Claude（无上下文）测试文档，在他人阅读前发现盲点

说明该方法有助于确保文档在他人阅读时表现良好（包括他人将其粘贴到 Claude 中时）。询问用户是想尝试该工作流，还是更偏好自由写作。

若用户拒绝，则采用自由写作；若用户接受，则进入第一阶段。

## 阶段 1：上下文收集

**目标：** 缩小用户已知信息与 Claude 已知信息之间的差距，为后续的智能指导奠定基础。

### 初始问题

先向用户询问文档的元上下文：

1. 这是哪种类型的文档？（例如，技术规格、决策文档、提案）
2. 主要读者是谁？
3. 期望读者阅读后产生何种影响？
4. 是否有需要遵循的模板或特定格式？
5. 是否还有其他约束或上下文需要说明？

告知用户可用简写方式回答，也可按其最习惯的方式直接倾倒信息。

**如果用户提供了模板或提到文档类型：**
- 询问是否有可共享的模板文档
- 若用户提供共享文档链接，使用合适集成读取
- 若用户提供文件，则读取该文件

**如果用户提到在编辑现有共享文档：**
- 使用合适集成读取当前状态
- 检查是否有缺少替代文本的图片
- 若存在无替代文本的图片，说明当其他人让 Claude 理解该文档时，Claude 无法看到这些图片。询问是否要生成替代文本；若需要，请他们将每张图片粘贴到聊天中以生成描述性替代文本。

### 信息倾倒

在初始问题回答后，鼓励用户把所有上下文都倒出来。可请求的信息包括：
- 项目/问题背景
- 相关团队讨论或共享文档
- 为什么不采用替代方案
- 组织背景（团队动态、过往事件、政治因素）
- 时间压力或约束
- 技术架构或依赖关系
- 利益相关方关注点

建议他们无需担心结构化，只要全部说出来。提供多种上下文补充方式：
- 意识流式的信息倾倒
- 指向可阅读的团队渠道或讨论线索
- 提供共享文档链接

**如果可用集成（如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器）：** 可说明这些可用于直接拉取上下文。

**如果未检测到集成且在 Claude.ai 或 Claude 应用中：** 建议他们可在 Claude 设置中启用连接器，以直接从消息应用和文档存储中拉取上下文。

说明在完成初始倾倒后将继续提问澄清问题。

**在上下文收集期间：**

- 若用户提到团队渠道或共享文档：
  - 若可用集成：说明将立即读取内容，然后调用相应集成
  - 若不可用：说明无法访问，建议在 Claude 设置中启用连接器，或直接粘贴相关内容

- 若用户提到未知实体/项目：
  - 询问是否应搜索已连接工具以进一步了解
  - 等待用户确认后再搜索

- 随着用户提供上下文，记录已掌握内容与仍不清晰的内容

**提问澄清问题：**

当用户表示已完成初始倾倒（或已提供大量上下文）后，提澄清问题以确认理解：

基于上下文空缺生成 5-10 个编号问题。

说明他们可以用简写方式回答（例如“1: yes, 2: see #channel, 3: no because backwards compat”）、链接更多文档、指向可阅读的频道，或继续倾倒信息。以他们最高效的方式为准。

**退出条件：**
当问题展示出对上下文的充分理解——即能够讨论边界情况和取舍，而无需再解释基础概念时，即认为上下文已充分收集。

**过渡：**
询问此阶段是否还想补充更多上下文，或可以进入文档起草阶段。

若用户想补充，允许其补充。准备好后，进入阶段 2。

## 阶段 2：精炼与结构化

**目标：** 通过头脑风暴、筛选和迭代精炼，按章节逐步构建文档。

**对用户的说明：**
说明文档将按章节逐步构建。每一章节流程为：
1. 会提出澄清问题，确认应包含内容
2. 头脑风暴 5-20 个选项
3. 用户标注要保留/移除/合并的内容
4. 起草该章节
5. 通过精准编辑进行精修

从未知项最多的章节开始（通常是核心决策/提案），然后依次推进其他章节。

**章节顺序：**

若文档结构已明确：
询问用户希望从哪个章节开始。

建议从未知项最多的章节入手。对于决策文档通常是核心提案；对技术规格而言通常是技术方案。总结部分建议最后写。

若用户不清楚需要哪些章节：
基于文档类型和模板，建议 3-5 个适合该类型的章节。

询问该结构是否可行，或是否要调整。

**结构确认后：**

为所有章节创建初始文档结构并放入占位文本。

**若可访问 artifact：**
使用 `create_file` 创建一个 artifact。这样 Claude 和用户都能基于同一骨架进行协作。

说明会创建包含所有章节占位符的初始结构。

用完整章节标题和简短占位文本创建 artifact，例如 `"[待撰写]"` 或 `"[内容在此]"`。

提供骨架链接，并说明接下来开始逐章填充。

**若无 artifact 访问权限：**
在工作目录创建一个 Markdown 文件，按需命名（例如 `decision-doc.md`、`technical-spec.md`）。

说明将创建包含所有章节占位符的初始结构。

创建文件并包含所有章节标题与占位文本。

确认文件已创建，并说明可开始逐节填充。

**对每个章节：**

### 步骤 1：澄清问题

宣布即将开始 `[SECTION NAME]` 章节。提出 5-10 个关于该章节应包含哪些内容的澄清问题：

基于上下文和章节目的，生成 5-10 个具体问题。

说明可用简写回答，或仅指出应重点覆盖的内容。

### 步骤 2：头脑风暴

对于 `[SECTION NAME]` 章节，根据章节复杂度，头脑风暴 5-20 个可能包含的要点。查找：
- 可能被遗忘的共享上下文
- 尚未提及的角度或考虑点

基于章节复杂度生成 5-20 个编号选项。结束时提供继续头脑风暴更多选项的提议（若用户需要）。

### 步骤 3：筛选

询问应保留、移除或合并哪些点。请求简短理由，以帮助了解后续章节的优先级。

提供示例：
- `Keep 1,4,7,9`
- `Remove 3 (duplicates 1)`
- `Remove 6 (audience already knows this)`
- `Combine 11 and 12`

好的，先按流程确认：  
请先告诉我当前项目要使用哪些 **skill 或 plugin 整组**（可直接给清单；也可回复“先不用/全部不启用”）。  
收到确认后我再开始按你要求逐段翻译。
