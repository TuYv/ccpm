# 销售工程师技能

一个可用于生产环境的售前工程技能包，衔接技术专长与销售执行。可为 RFP/RFI 响应、竞争定位和概念验证规划提供自动化分析。

## 概述

**角色：** 销售工程师 / 解决方案架构师  
**领域：** 售前工程、解决方案设计、技术演示、概念验证  
**业务类型：** SaaS / 售前工程

### 此技能的作用

- **RFP/RFI 响应分析** - 评估需求覆盖度、识别差距、生成投标/不投标建议
- **竞争性技术定位** - 构建功能对比矩阵、识别差异化优势和薄弱环节
- **POC 规划** - 生成时间表、资源计划、成功标准和评估记分卡
- **演示准备** - 设计包含讲解要点和异议处理方式的演示脚本
- **技术方案创建** - 提供解决方案架构和实施规划框架
- **赢单/丢单分析** - 为交易策略提供数据驱动的竞争评估

### 关键指标

| 指标 | 描述 | 目标 |
|--------|-------------|--------|
| 赢单率 | 赢得的交易数 / 机会总数 | >30% |
| 销售周期长度 | 从需求发现到成交的平均天数 | <90 天 |
| POC 转化率 | 最终促成交易的 POC 占比 | >60% |
| 客户参与度评分 | 利益相关者对评估的参与程度 | >75% |
| RFP 覆盖度评分 | 得到充分响应的需求占比 | >80% |

## 首先澄清

在生成交付成果之前，请确认以下输入。如果有任何输入未知或含糊，请询问——不要自行假设：

- [ ] **所需的交付成果** —— RFP/RFI 覆盖度分析、竞争矩阵或 POC 计划（用于选择工具和阶段）
- [ ] **客户需求及优先级** —— 必须具备/应该具备/最好具备的事项列表（用于确定加权覆盖度以及投标/不投标决策）
- [ ] **交易中的竞争对手** —— 创建功能矩阵、差异化优势和竞争作战卡所必需的信息
- [ ] **POC 范围及成功标准** —— 规划 POC 时所需的用例以及可衡量的通过/不通过标准（防止 POC 范围无边界扩张）

停止规则：仅询问对输出影响最大的 2-3 项。如果用户说“直接起草即可”，则继续执行，并在交付成果顶部列出你的假设。

## 五阶段工作流

### 阶段 1：需求发现与研究

**目标：** 了解客户需求、技术环境和业务驱动因素。

**活动：**
1. 与利益相关者开展技术需求发现会议
2. 梳理客户当前的架构和痛点
3. 识别集成需求和约束条件
4. 记录安全与合规要求
5. 评估此次商机的竞争格局

**工具：** 使用 `rfp_response_analyzer.py` 评估初始需求匹配度。

**输出：** 技术需求发现文档、需求映射、初始覆盖度评估。

### 阶段 2：解决方案设计

**目标：** 设计满足客户需求的解决方案架构。

**活动：**
1. 将产品能力映射到客户需求
2. 设计集成架构
3. 识别定制需求和开发工作量
4. 制定竞争差异化策略
5. 创建解决方案架构图

**工具：** 使用 `competitive_matrix_builder.py` 识别差异化优势和薄弱环节。

**输出：** 解决方案架构、竞争定位、技术差异化策略。

### 阶段 3：演示准备与交付

**目标：** 针对利益相关者的优先事项，提供具有说服力的技术演示。

**活动：**
1. 构建与客户使用场景相匹配的演示环境
2. 创建演示脚本，并为每种利益相关者角色准备讲解要点
3. 准备异议处理答复
4. 演练故障场景和恢复路径
5. 收集反馈并调整方法

**模板：** 使用 `demo_script_template.md` 进行结构化的演示准备。

**输出：** 定制化演示、针对利益相关者的讲解要点、反馈记录。

### 阶段 4：POC 与评估

**目标：** 执行结构化的概念验证，以验证解决方案。

**活动：**
1. 定义 POC 范围、成功标准和时间表
2. 分配资源并搭建环境
3. 执行分阶段测试（核心功能、高级功能、边界情况）
4. 根据成功标准跟踪进展
5. 生成评估计分卡

**工具：** 使用 `poc_planner.py` 生成完整的 POC 计划。

**模板：** 使用 `poc_scorecard_template.md` 跟踪评估情况。

**输出：** POC 计划、评估计分卡、继续/终止建议。

### 阶段 5：提案与成交

**目标：** 提交支持商务成交的技术提案。

**活动：**
1. 汇总 POC 结果和成功指标
2. 创建包含实施计划的技术提案
3. 使用证据回应尚未解决的异议
4. 支持定价和产品组合讨论
5. 在决策后开展赢单/丢单分析

**模板：** 使用 `technical_proposal_template.md` 编写提案文档。

**输出：** 技术提案、实施时间表、风险缓解计划。

## Python 自动化工具

### 1. RFP 响应分析器

**脚本：** `scripts/rfp_response_analyzer.py`

**用途：** 解析 RFP/RFI 需求、评估覆盖程度、识别差距，并生成投标/不投标建议。

**覆盖类别：**
- **完全覆盖（100%）** - 当前产品完全满足需求
- **部分覆盖（50%）** - 部分满足需求，需要变通方案或配置
- **已规划（25%）** - 已列入产品路线图，但尚不可用
- **缺口（0%）** - 不支持，当前也没有相关计划

**优先级权重：**
- 必须具备：3 倍权重
- 应该具备：2 倍权重
- 最好具备：1 倍权重

**投标/不投标逻辑：**
- **投标：** 覆盖得分 >70% 且必须具备项的缺口 <=3
- **有条件投标：** 覆盖得分为 50-70%，或必须具备项的缺口为 2-3
- **不投标：** 覆盖得分 <50%，或必须具备项的缺口 >3

**用法：**
```bash
# Human-readable output
python scripts/rfp_response_analyzer.py assets/sample_rfp_data.json

# JSON output
python scripts/rfp_response_analyzer.py assets/sample_rfp_data.json --format json

# Help
python scripts/rfp_response_analyzer.py --help
```

**输入格式：** 完整架构请参阅 `assets/sample_rfp_data.json`。

### 2. 竞争矩阵构建器

**脚本：** `scripts/competitive_matrix_builder.py`

**用途：** 生成功能对比矩阵、计算竞争力得分、识别差异化优势和薄弱环节。

**功能评分：**
- **完整 (3)** - 完整支持该功能
- **部分 (2)** - 部分支持或支持有限
- **有限 (1)** - 最低限度或基础功能支持
- **无 (0)** - 不提供该功能

**用法：**
```bash
# Human-readable output
python scripts/competitive_matrix_builder.py competitive_data.json

# JSON output
python scripts/competitive_matrix_builder.py competitive_data.json --format json
```

**输出包括：**
- 带评分的功能对比矩阵
- 每个产品的加权竞争力得分
- 差异化优势（我们的产品领先的功能）
- 薄弱环节（竞争对手领先的功能）
- 基于差异化优势的制胜主题

### 3. POC 规划器

**脚本：** `scripts/poc_planner.py`

**用途：** 生成结构化 POC 计划，包括时间线、资源分配、成功标准和评估记分卡。

**默认阶段划分：**
- **第 1 周：** 设置 - 环境配置、数据迁移、系统配置
- **第 2-3 周：** 核心测试 - 主要用例、集成测试
- **第 4 周：** 高级测试 - 边界情况、性能、安全性
- **第 5 周：** 评估 - 完成记分卡、利益相关者评审、继续/终止决策

**用法：**
```bash
# Human-readable output
python scripts/poc_planner.py poc_data.json

# JSON output
python scripts/poc_planner.py poc_data.json --format json
```

**输出包括：**
- 包含分阶段时间线的 POC 计划
- 资源分配（SE、工程团队、客户）
- 带有可衡量指标的成功标准
- 评估记分卡（功能、性能、集成、易用性、支持）
- 包含缓解策略的风险登记表
- 继续/终止建议框架

## 故障排除

| 问题 | 可能原因 | 解决方案 |
|---------|-------------|------------|
| RFP 覆盖分数低于 50%，触发不投标建议 | 必备要求存在产品差距，或覆盖情况评估不正确 | 审查差距项——区分真正的差距与可通过配置、集成或路线图承诺解决的项目；在拒绝投标前重新评估 |
| 竞争矩阵显示在 3 个以上类别中存在薄弱环节 | 相对于特定竞争对手存在产品差距，或评分未反映实际竞争态势 | 与曾和该供应商竞争过的一线 SE 一起验证评分；作战卡应聚焦于己方领先领域的差异化优势，而非落后之处 |
| POC 到成交的转化率低于 60% | POC 范围过广、成功标准与买方优先事项不一致，或相关利益干系人不正确 | 将 POC 缩小至与买方明确表述的痛点相关的 3-5 个用例；开始前就成功标准达成书面协议；确保高管发起人参与评估 |
| 赢单率低于 30% | 技术上胜出但商务上失利、介入交易过晚，或需求发现不充分导致演示与需求不匹配 | 在销售周期中更早介入；使用 MEDDIC 框架提高需求发现质量；使演示叙事与买方的语言保持一致，而不是围绕产品特性展开 |
| 演示到 POC 的转化率低于 40% | 演示未解决买方的特定用例，或内容过于通用 | 根据买方明确提出的要求定制每次演示；使用买方的数据或特定于其行业的场景；在结尾加入问答环节和后续步骤提案 |
| RFP 响应时间超过 2 周 | 采用人工响应流程，缺少模板或预先构建的内容库 | 构建按要求类别索引的响应库；使用 rfp_response_analyzer.py 优先处理必备项 |
| 利益干系人参与度评分低于 75% | 关键决策者未参与技术评估 | 尽早梳理利益干系人的角色；在开展技术深度讲解的同时确保进行高管简报；向每位利益干系人发送个性化跟进信息 |

## 成功标准

- 在所有竞争性商机中，赢单率超过 30%
- 从需求探索到成交的销售周期保持在 90 天以内
- POC 到成交的转化率超过 60%
- 所跟进商机的 RFP 覆盖率评分平均高于 80%（投标决策机制运行正确）
- 竞争矩阵为每个竞争对手确定至少 3 个明确的差异化优势
- 客户参与度评分超过 75%（根据利益相关者对评估里程碑的参与情况衡量）
- 借助结构化响应库，将平均 RFP 响应时间缩短至 5 个工作日以内

## 范围与限制

**范围内：** RFP/RFI 响应分析与评分、竞争性功能矩阵构建、概念验证规划与评估、演示准备框架、技术提案结构、赢单/丢单分析方法，以及贯穿售前五阶段工作流（需求探索、解决方案设计、演示、POC、提案）的利益相关者参与度跟踪。

**范围外：** 销售策略和区域规划（客户经理职能）、定价和商业条款谈判（使用 pricing-strategy）、售后实施和客户成功（使用 customer-success-manager）、营销内容和竞争性信息传达（使用营销技能），以及基于 RFP 差距制定产品路线图决策（使用 product-team）。工具仅分析静态数据导出，不与 CRM 系统（Salesforce、HubSpot）或 RFP 平台（Loopio、Arphie）集成。

**限制：** 可配置投标/不投标阈值，但默认值以赢单率目标达到 30% 以上的 B2B SaaS 为前提。竞争矩阵评分的准确性取决于输入数据，应结合针对特定竞争对手的实战经验验证评分。POC 时间安排以标准的 5 周参与周期为前提；高度监管行业（医疗、政府）可能需要 2-3 倍的时间。AI 辅助 RFP 工具（于 2025-2026 年兴起）可将响应时间缩短 60-80%，但此处未集成这些工具。

## 集成点

- **revenue-operations** -- 需要技术验证的管线交易将进入 SE 工作流；SE 的赢单/丢单数据将用于管线分析
- **customer-success-manager** -- POC 结果和成功标准将移交给 CSM，用于跟踪成交后的采用情况
- **pricing-strategy** -- 矩阵构建器中的竞争性定价数据将为定价定位决策提供依据
- **product-team** -- RFP 中标记为“Planned”或“Gap”的差距将用于产品路线图优先级排序
- **c-level-advisor** -- 需要高管参与的战略交易将通过 C-level 顾问工作流升级处理
- **marketing** -- 来自市场营销的竞争情报将用于创建竞争作战卡和制定定位
