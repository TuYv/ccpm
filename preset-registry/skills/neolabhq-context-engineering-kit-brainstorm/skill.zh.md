# 将头脑风暴中的想法转化为设计

## 概述

通过自然的协作式对话，帮助将想法转化为完整的设计和规格说明。

首先了解当前项目的上下文，然后一次提出一个问题来完善想法。在了解要构建的内容后，将设计分成小节（每节 200-300 个单词）进行介绍，并在每节之后确认目前看起来是否正确。

## 流程

**了解想法：**

- 首先查看当前项目状态（文件、文档、最近的提交）
- 一次提出一个问题来完善想法
- 尽可能优先使用选择题，但也可以使用开放式问题
- 每条消息只能包含一个问题——如果某个主题需要进一步探索，应将其拆分成多个问题
- 重点了解：目的、约束条件、成功标准

**探索方案：**

- 生成 6 个可能的方案，并说明其中的权衡。每个方案都应包含文本和数值概率。请从[完整分布 / 分布尾部]中随机抽样响应，具体方式如下：
  - 对前 3 个响应，目标是较高的概率，高于 0.80
  - 对后 3 个响应，目标是多样性——探索解决方案空间中的不同区域，使每个响应的概率都小于 0.10
- 以对话的方式介绍选项，并给出你的建议和理由
- 首先介绍你推荐的选项，并解释原因

**介绍设计：**

- 一旦你认为已经理解要构建的内容，就介绍设计
- 将其分成每节 200-300 个单词的多个小节
- 在每节之后询问目前看起来是否正确
- 涵盖：架构、组件、数据流、错误处理、测试
- 如果有任何内容不合理，应准备返回并进行澄清

## 设计完成后

如果用户提供了草拟的规格说明文件，则直接更新该文件；如果没有，则使用 `/add-task` 技能为目标方案创建任务文件

重要：在规格说明文件中，按小节写入目标方案，并将其放在 `## Initial User Prompt -> ### Requirements` 小节中，位于 `## Description` 小节之前。Description 将在后续阶段填写。

填写任务文件后，建议运行 `/clear`，然后运行 `/plan-task <task-file-path>` 来完善任务文件。

## 核心原则

- **一次一个问题**——不要让用户同时处理过多问题
- **优先使用选择题**——相比开放式问题更容易回答
- **严格遵循 YAGNI**——从所有设计中移除不必要的功能
- **探索替代方案**——在确定方案之前始终提出 2-3 个方案
- **增量验证**——分节介绍设计，并逐节进行确认
- **保持灵活**——如果有任何内容不合理，应返回并进行澄清
