# 维护文档

## 概述

文档是一组**关于现实情况的声明**；此技能用于确保项目文档始终与现实情况保持一致。所有流程都受同一准则约束：首先进行分类，判断文档是否本就应该跟踪当前现实；仅自动修复那些*可以明确判定*的内容；将所有存在歧义的内容交由人工处理；绝不重写历史记录。**违反这些规则的字面要求，就是违背其精神。**“我只是在让文档保持最新”恰恰就是设计文档的历史记录遭到抹除的原因。

## 分派——执行任何操作之前，先阅读流程文件

| 情况 | 你必须阅读 |
| --- | --- |
| 全面审计：“文档已过时”、发布前检查、不可信的文档集 | `references/audit.md` |
| 对此前已审计的文档进行常规复查 | `references/incremental.md` |
| 刚完成代码工作；更新与之配套的文档 | `references/write-path.md` |
| 创建或扩充术语表；术语争议；例外情况 | `references/dictionary.md` |
| 编写全新文档；“这份文档应该放在哪里？” | `references/new-docs.md` |

这些是不可绕过的关卡：不要仅凭对本表的记忆启动流程。流程会补充具体步骤；下述准则约束所有流程，且不会在流程文件中重复说明。

## 停止：编辑前必须先分类（持续更新型与时间点记录型）

最严重的一类错误，是为了“匹配代码”而重写带日期的设计文档、计划或规范。三个月前编写的规范描述了某项功能*应该*如何运作，当代码后来偏离该规范时，规范本身**并没有错**——将其修改为与代码一致，会破坏历史记录。

- **持续更新型**——README、ABOUT、CLAUDE.md、教程、持续维护的 API/schema
  参考文档。约定：*反映当前现实*。出现偏差即为缺陷 → 修复。
- **时间点记录型**——设计规范、计划、头脑风暴笔记（通常带有日期，或位于
  `docs/specs|plans|…` 下）。约定：*在其日期所对应的时间点上为真*。与当前代码
  存在偏差是**预期情况**。绝不重写以匹配代码；最多添加已被取代的横幅提示或截至日期。
- **混合型 / 不明确**——存在相互冲突的信号（例如位于日期目录中的 `README`）→
  将整份文档视为只能通过访谈确认。

必须**首先**在**分组层面**（文件夹 glob 模式 + 具名例外）对文档集进行分类，并在编辑任何内容之前**与人工确认**。优先级规则：时间点记录型信号（带日期的文件名、时间点记录型目录）**优先于** `README` 这类持续更新型名称。不要在处理过程中凭直觉逐份文档判断——应将其作为一个整体决策提出。

**分类确认是唯一绝不能跳过的关卡**——即使时间紧迫、受到权威指示，或被要求“果断一点，别再把问题抛回给我”，也不能跳过。一行确认只需几秒；跳过它，才会让一次审计变成对设计记录的抹除。当分类确实存在歧义时（例如，某个看似参考文档的文件位于 `specs/` 文件夹中，而该文件夹同时也包含设计文档），**应选择安全的一侧——将其视为时间点记录型并进行确认**——因为对正文的重写会对历史记录造成不可逆的影响。在重写正文*之后*才通过脚注披露你的假设，已经太迟了。

已确认的分类会**持久保存在文档索引中**（`Class` 列——
参见产物）。编辑流程以此作为准入条件：没有索引 → 先运行审计阶段 0。
绝不要在流程中途凭直觉分类。

## 范围与排除项

默认目标：`README`、顶层 `*.md`、`docs/**`、`CLAUDE.md`。**始终
排除：**被 git 忽略的路径、`.claude/`、`.private-journal/`、工作树；
**生成的文档／由外部所有者维护的文档**（任何带有“do not edit”／“generated by”
哨兵标记的文档——编辑它们毫无意义，下次重新生成时会覆盖更改）；
非 Markdown 文件。字典（`docs/DICTIONARY.md`）不参与针对其自身的
术语扫描。

## 评判准则：哪些内容可以自动修复

**仅当以下所有条件均满足时**，才可自动修复一项声明：

1. 文档是**常青型**的；
2. 声明是**机械性的**——标识符／路径、CLI 标志、配置／环境变量的
   名称及默认值、API 路由／字段，或示例中词元级别的修复；
3. 代码中存在**唯一一个实时（非测试）对应项**，因此正确值是*可以确定的，而非猜测的*（多个匹配项／仅测试代码中存在／无匹配项 →
   访谈确认）；
4. 这是一次**局部词元替换**，且替换后周围句子仍然为真；
5. 在得出任何结论前，已通过 git 历史记录确认缺失的对应项是**已删除还是已重命名**
   （`git log -S`、`--follow`、blame）。

**字典条款。**仅在常青型正文中，当以下所有条件均满足时，才可自动修复已弃用的
同义词：该同义词恰好映射到一个字典条目（其标题即为替换词）；
匹配为完整单词；没有适用的例外；且替换后周围句子仍然为真。
此时决定依据是字典，而非代码对应项——条件 1、4 和 5 仍然适用。
代码标识符、UI 字符串：绝不自动修复——只记录发现（重命名／添加条目／添加例外）。
新的提交消息应使用字典术语；历史记录永不标记。

**无论属于哪一类别，以下情况始终需要访谈确认——绝不自动修复：**

- **数量与清单**（“14 workflows”、“~40 files”）——不存在规范统一的
  计数约定。
- **仅含行号的引用**（`file.go:120-130`）——每次编辑都可能导致其偏移。
  建议改写为 `file:symbol`；绝不要静默地重新编号。
- **缺失／否定性声明**（“there is no env-var fallback”）——无法通过
  grep 证明某事不存在。
- **交叉引用修复**——检测断开的链接没有问题；但通常无法确定其新的
  目标。
- **对嵌入式示例的结构性更改**——将示例的*结构*重写为新模式。
- **行为／语义声明**（“does X when Y”、执行顺序、设计理由）。
- **其事实依据存在于其他仓库或外部二进制文件中的声明。**

## 验证声明，而不只是符号

确认文档中提到的*事物*存在，并不等于确认*关于它的声明*。
对于形式为“X is validated / X happens when Y / X is done
by Z / X is configured as W”的声明，只有验证**实际执行该行为的代码路径**
才算完成验证——拒绝输入的验证器、关闭流的处理程序、计算该值的函数、
加载资源的代码行——而**不是**仅仅确认 X 存在。要检查动词，而不只是名词。

- “加载器会拒绝声明了 `runner` 的 emit 节点” → 在验证器中找到
  执行拒绝的代码，否则该说法就是错误的。
- “当运行进入终止状态时，流会关闭” → 找到在*每一种*
  终止状态下执行关闭的代码，否则指出遗漏了哪一种状态。
- “diff 在 `internal/document` 中计算” → 找到其中的调用，而不仅仅是
  函数的定义。
- “Tailwind 从 CDN 加载” → 检查实际的 `<script src>`，而不是仅仅确认
  使用了 Tailwind。

这是最常见的错误 `matches`：名词核对无误，验证者便放过了动词。
应说明其机制，并让引用指向实际*执行*所声称操作的代码。

## 产物：术语词典与索引

该技能为每个项目维护恰好**两个**产物，外加内联戳记。
绝不使用第三个元数据文件。

- **`docs/DICTIONARY.md`** — 文档、代码标识符、提交消息和 UI 字符串的
  规范术语；不一致项记录在其 Exceptions 部分中，且仅通过路径 glob
  确定适用范围。模板：`templates/DICTIONARY-template.md`；语法和生命周期：
  `references/dictionary.md`。持续维护、带有戳记，并且是术语的规范归属处。
- **文档索引** — 位于 `docs/README.md` 中、由哨兵标记围住的表格
  (`<!-- doc-index:begin/end -->`)；如果不存在 README，则使用独立的
  `docs/INDEX.md`。列为：Doc | What | Class | Owns。`Class` 是持久化保存的
  classify-and-confirm 输出；`Owns` 是机器可读的路径 glob（即
  `docmaint stale` 进行 diff 的对象）。模板：`templates/INDEX-template.md`。
- **`docmaint`**（`scan | stamp | stale`，用法见 `--help`）负责执行
  机械性工作。它绝不会编辑文档；代理会按照评判标准执行编辑。它位于
  **此技能的** `scripts/` 目录中，而不是目标仓库中，因此应通过绝对路径调用
  （例如 `~/.claude/skills/maintaining-documentation/scripts/docmaint`），
  并传入 `--root <target-repo>`，除非当前工作目录已经是目标仓库根目录
  （`--root` 默认为当前工作目录）。流程文件中使用不带路径的
  `docmaint <subcommand>`；此解析规则适用于所有场景。

## 戳记约定

持续维护型文档在文件末尾带有一个幂等块（由 `docmaint stamp` 维护；
哨兵标记为 `<!-- doc-audit:last-reviewed -->`）：

```
---
<!-- doc-audit:last-reviewed -->
_Last reviewed: 2026-06-09 · commit `abc1234` · verified against code (2 claims deferred to review)._
```

SHA 既是来源信息，**也是**增量游标——这是相较前身技能的一项有意变更。
增量复审只用于**分流，而不能保证可靠性**：无论 SHA 如何，存在延期声明的
文档都会保留在工作列表中；事实依据位于仓库外部的声明只能通过完整审计清除；
术语检查绝不依赖戳记（`docmaint scan` 每次运行都会执行全量扫描）。
**加盖戳记的前置条件（适用于所有流程）：** 若未对已应用的编辑进行独立验证，
则不得加盖戳记——完整审计使用两个或更多相互竞争的验证器（Phase 3）；
基于 diff 或工作列表限定范围的流程至少使用一个独立验证器。
不要为时点型文档加盖戳记。仅为已验证的内容加盖戳记——而且任何本次无法验证的
持续维护型声明，包括事实依据位于仓库外部的声明，都必须计入 `--deferred N`。
绝不要让未经验证的声明混在无延期项的戳记之下。

## 实用主义法则

- 文档为读者而存在。在创建任何文档、条目或制品之前，先明确
  读者是谁。没有读者 → 就不要写。
- 先采用现有结构，再考虑引入新结构。
- 每个项目只允许两个制品（词典、索引），外加戳记。绝不允许第三个。
- 覆盖缺口是需要记录的问题，而不是生成文档的指令。
- 词典应当能一次读完：只收录关键术语。
- 写入范围应受差异范围约束。如果维护成本不低，就不会
  有人维护。

## 危险信号 — 停止

- 在**尚未先分类**的情况下，声称“我要让整个规范/计划集合中的文档都保持最新”。
  → 先分类并确认。
- 准备对 `file:line` 引用**重新编号**。→ 通过访谈将其转换为
  `file:symbol`。
- 准备**按照新模式重写示例的结构**。→
  进行访谈，不要自动修复。
- 在被要求“果断一些 / 不要确认”的压力下，准备自行对文档分类并
  **重写其正文**。→ 分类确认是唯一绝不能跳过的
  关卡。明确提出确认；一句话的确认只需几秒钟。
- 因为 grep **没有匹配结果**就断定某项功能已“移除”或删除其文档。
  → 先检查 git 历史记录。
- “差不多了，我直接修正数量就行。”→ 数量问题交给人来处理。
- 编辑标有“generated”/“do not edit”的文件。→ 跳过该文件。
- 在**没有引用依据**的情况下将某项陈述标记为“匹配”。→ 提供引用依据，否则就不要声称
  匹配。
- 准备**在没有对自己的编辑进行第二轮对抗式检查的情况下结束工作**。
  → 在完整审计中，先运行相互竞争的验证轮次（审计阶段 3）；在
  有界流程中，适用单验证者戳记前置条件。修复它发现的问题。
- 仅仅因为**符号存在**，而没有检查代码是否确实*执行了*相关陈述所描述的行为，
  就将该陈述标记为“匹配”。→ 验证动词，而不是名词。
- 审计了每篇文档，却从未检查文档**集合**（重复、缺口、
  矛盾、索引）。→ 逐篇文档检查无法发现集合层面的缺陷；
  运行语料库审查（审计阶段 4——适用于完整审计流程）。
- 准备移除 `[permanent]` 例外，或仅凭扫描证据移除 `[temporary]`
  例外。→ 永久例外：绝不移除。临时例外：先通过 git 历史记录确认
  （grep 无匹配结果并不代表问题已解决）。
- 准备为未经任何人独立验证其编辑内容的文档加盖戳记。→
  戳记前置条件适用于所有流程，而不只是完整审计。
- 准备撰写无人被要求阅读的文档或词典条目。→ 明确
  读者是谁（实用主义法则）。
- 准备添加第三个项目级元数据文件。→ 两个制品。绝不允许
  第三个。
- 准备用自然语言描述例外范围（“涉及 X 的代码”）。→ 只能使用路径
  glob。
- 在项目尚无已确认的索引 `Class` 列时编辑文档。→ 先运行
  审计阶段 0。

## 自我辩解

| 借口 | 现实 |
|--------|---------|
| “规范说 X，但代码说 Y，所以规范是错的。” | 只有在规范是**常青文档**时才成立。时间点设计文档可以与代码不同——先分类。 |
| “这显然是参考文档，我直接修复就行。” | 凭直觉逐篇判断，正是导致设计文档的历史被重写的原因。请与人确认分类。 |
| “他们让我果断一些，不要把决定踢回去——所以我会自行分类和重写。” | 分类确认是唯一绝不能跳过的关卡；它决定了你是在修复文档，还是在抹除设计记录。一句话的确认只需几秒钟。 |
| “其中没有任何内容像带日期的设计叙述，所以它是常青文档。” | 缺少明显的设计语言并不能证明它是常青文档，尤其是在 `specs/` 这样的混合目录中。存在歧义 + 破坏性编辑 → 将其视为时间点文档并请求确认。 |
| “我在结尾披露了自己的假设。” | 在重写正文后再加脚注已经太晚了——记录已经被更改。应在编辑*之前*确认，而不是之后。 |
| “行号变了，我会更新它。” | 每次编辑都会导致行号漂移；重新定位后仍会再次失效。请转换为 `file:symbol`。 |
| “我会把示例更新为新模式。” | 对示例进行结构性重写会改变其含义 → 进行访谈，不要自动修复。 |
| “grep 什么也没找到，这项功能已经没了。” | grep 无匹配结果不能证明功能已被移除。检查 git 历史记录；它可能只是被重命名了。 |
| “37 和约 40 很接近，我直接写实际数量就行。” | 数量没有统一的权威约定——交给人来处理。 |
| “符号/路由/字段存在，所以这项陈述通过了检查。” | 存在 ≠ 陈述成立。验证真正*实施*该行为的代码路径（验证器/处理程序/调用点），而不只是确认名词所指对象存在。 |
| “每篇文档都验证无误，所以文档集没有问题。” | 单篇文档准确 ≠ 文档集健康。重复、缺失文档和跨文档矛盾只能在语料库层面显现（审计阶段 4）。 |
| “扫描结果为零，该例外已解决。” | grep 无匹配结果并不代表问题已解决——先通过 `git log -S` 确认；绝不能仅凭扫描证据移除 `[permanent]` 例外。 |
| “这只是很小的文档编辑，没有验证者也可以加盖戳记。” | 戳记的*含义*就是已经过独立验证。没有验证者，就不能加盖戳记。 |
| “文档看起来不完整，我会为每个缺口添加一篇文档。” | 缺口是问题发现。没有读者的文档不是覆盖，而是债务。 |

## 常见错误

- 在分类之前就开始编辑。
- 为每份时间点文档分别启动一个子代理——应进行批处理；这些文档并未经过声明核验。
- 首次运行时积压无上限的访谈任务——确定优先级，将剩余部分推迟到报告中处理。
- 自动提交审计结果——应保持未提交状态，供人工审查。
- 未对自己的编辑进行对抗性核验就宣布完成——你的修复内容很容易成为藏匿自信但错误声明的地方（审计阶段 3）。
- 将逐文档核验视为全部工作——重复、缺漏、跨文档矛盾以及索引缺失都是文档集层面的缺陷，逐文档检查无法发现这些问题（审计阶段 4）。
- 只核验名词，不核验动词——只确认某个符号存在，而不确认代码是否确实执行了文档所声称的行为。
- 将 `stale` 输出视为内容无误的证明——它只是用于分诊；可靠性来自完整审计。
