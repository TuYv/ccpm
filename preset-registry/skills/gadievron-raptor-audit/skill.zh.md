# /audit 技能 — 会话内代码审查

此技能是 `/audit` 的会话内执行路径，其中 Claude Code 充当 LLM。在传入 `--local` 或未配置外部模型时使用。有关编排器路径（使用外部 LLM 的 `libexec/raptor-audit run`），请参阅 `.claude/commands/audit.md`。

## [配置]

- 模型：所有代码审查均使用 Opus。仅编排衔接使用 Sonnet。
- 审查单元：目录（子系统），而非单个函数。
- 上下文切片：函数源代码 + 一跳调用方 + 一跳被调用方 + 检查清单元数据。
- 检查清单项字段：`name`、`kind`（`"function"`/`"global"`/`"macro"`/`"class"`）、`line_start`、`line_end`、`signature`、`checked_by`、`metadata`（`visibility`、`params`、`return_type`、`attributes`）。该字段是 `kind`，而不是 `type`。来源：`core/inventory/extractors.CodeItem`。
- 发现项格式：标准 `findings.json`（与 `/scan` 相同，原样传给 `/validate`）。
- 注解：每个源文件使用 markdown，结构化元数据置于 HTML 注释中。
- 前置条件：必须先运行 `/understand --map`。如果输出目录（或项目同级目录）中缺少 `context-map.json`，请在开始审查循环之前运行它——加载 `.claude/skills/code-understanding/map.md` 并按照其中的执行步骤操作。
- 作用域：`--scope <dir>` 将缺口选择限制在某个子目录内（例如 `ipc/`、`net/ipv4/`）。所有注解和覆盖率记录仍会写入项目级输出目录，因此连续执行的限定作用域运行会累积到同一条审计轨迹中。

## [领域] 审计前先研究代码库

**审计前始终先进行研究。** 你可能会从训练数据中认出 RCU、引用计数或锁顺序等概念——但训练数据可能已经过时或并不完整。API 会演变，不同内核版本之间的锁契约会发生变化，而所有权语义则取决于具体代码库。要确认先验认知是否正确，唯一的方法就是从实际源代码中提取领域模型。如果不进行研究，你会在不知不觉中套用过时的假设，并漏掉那些违反语义而非结构的缺陷。

在开始审查循环之前，先对目标运行研究，然后运行映射。请遵循各技能文件中的执行步骤——不要猜测 CLI 命令：

1. **研究**（必需）：首先尝试 `raptor-study-loop`——它使用已配置的 LLM 模型，并自动处理多轮迭代。如果失败（未配置模型），则回退到 `.claude/skills/code-understanding/study.md` 中的会话内路径。生成 `domain-model.json`。
2. **映射**（必需）：加载并遵循 `.claude/skills/code-understanding/map.md`——生成 `context-map.json`（入口点、信任边界、汇聚点）

两者都会将输出写入 `$OUTPUT_DIR`，因此审计上下文切片会自动获取这些内容。在这两个文件都存在之前，不要开始逐函数审查循环。

研究是迭代式的——首先对整个子系统进行一次广泛的路径驱动遍历，然后针对特定契约和配对操作，开展有针对性的概念驱动或多标识符遍历。技能文件记录了这两条执行路径；有关如何自动选择正确路径，请参阅 [恢复]。

三种研究入口模式：

| 模式 | 示例 | 适用场景 |
|------|---------|------|
| **路径驱动** | `/understand <target> --study ipc/` | 研究一个子系统，发现其中的重要内容 |
| **概念驱动** | `/understand <target> --study "rcu locking" --scope ipc/` | 研究一个指定概念，查找相关代码 |
| **多标识符** | `/understand <target> --study "sem_lock + sem_unlock"` | 研究特定标识符之间的关系——契约、配对操作、不变量 |

多标识符模式中的 `+` 分隔符会触发关联分析——LLM 会检查这些标识符彼此之间的关系（例如 lock/unlock 配对、get/put 引用计数对称性），而不只是分别分析每个标识符的作用。
## [EXEC] 执行规则

0. **命令不得带有环境变量前缀。** 绝不要编写 `OUTPUT_DIR=... libexec/raptor-audit ...` 或 `VAR=val command`。这会破坏权限模式。从 `raptor-run-lifecycle start` 的输出中获取 `OUTPUT_DIR`，并在之后的每条命令中通过 `--out` 标志传递它。
1. **推理之前先阅读代码。** 绝不要描述或推测尚未使用 Read 工具读取过的代码。
2. **LLM 生成假设；工具进行验证。** 绝不要直接将代码归类为存在漏洞——这种做法的准确率只有 37%。应先提出假设，生成机械化测试，运行测试，然后评估结果。
3. **禁止纯粹的自我审查。** 所有迭代都必须包含工具反馈。禁止在不运行工具的情况下“再次审查”。应改为生成新的 Semgrep 规则、CodeQL 查询或 SMT 检查。所有工具调用都必须通过 `libexec/raptor-audit sweep`（或 Python API `packages.semgrep.runner` / `packages.coccinelle.runner`）运行——绝不要通过 Bash 直接调用 `semgrep` 或 `spatch`。这可确保结果自动记录到审计跟踪中。
4. **工具证据即最终结论。** 如果工具确认了某个假设，则发现项中必须包含该工具的输出作为证据。如果工具否定了假设，则必须丢弃该假设——不得声称“但我仍然认为……”
5. **注释记录测试过的内容，而非主观意见。** 每条注释都应列出测试过的假设、运行的工具及其结果。审查者可以重新运行所生成的规则进行验证。
6. **每个函数只能有一个状态。** 对每个已审查函数，必须且只能调用一次 `libexec/raptor-audit record`。状态可以是 `clean`（无问题）、`dormant`（确有缺陷，但当前不可达或属于死代码）、`suspicious`（存在疑点，但尚未确认）、`finding`（经工具确认且可达的漏洞）或 `error`（审查受阻）。当函数中存在真实缺陷，但目前不可达（死代码、无调用者、已被注释掉）时，应使用 `dormant`，而不是 `clean`。一旦其可达性发生变化，休眠缺陷就会成为发现项。
7. **发现项需要具体证据。** 发现项必须引用：存在漏洞的代码（file:line）、被违反的假设，以及确认该问题的工具输出。不得使用“如果……这可能会很危险”之类的表述。
8. **针对模式合成检查器。** 当已确认的发现项表明存在一种可重复的模式时（例如，“未经检查的返回值被用作索引”），应生成覆盖整个代码库的 Semgrep 或 Coccinelle 规则并运行它。一个假设 → 扫描整个代码库。
9. **运行生命周期。** 使用 `raptor-run-lifecycle start` 开始，使用 `raptor-run-lifecycle complete` 结束。失败时使用：`raptor-run-lifecycle fail`。
10. **不要叙述门禁规则的遵循情况。** 只展示实质性工作——假设、工具和结果。不要写“我现在正在遵循 EXEC 规则 2……”

## [GATES] 必须通过的门禁

- **G1 [HYPOTHESIS-FIRST]**：在输出任何发现之前，每个疑点都必须表述为可验证的假设。“X 看起来很危险”不是假设。“如果输入 Y 未经检查 W 就到达汇点 Z，则适用 CWE-N”才是。
- **G2 [TOOL-GROUNDED]**：每个发现都必须至少有一项机械化验证（Semgrep 匹配、CodeQL 路径、Coccinelle 命中、SMT 可满足结果或编译测试）。没有工具依据的发现只能作为注释（`suspicious`），绝不能标记为 `finding`。
- **G3 [NO-SELF-CRITIQUE-LOOP]**：禁止在没有工具反馈的情况下进行迭代。如果要重新审查，必须发起一次新的工具调用。
- **G4 [EVIDENCE-IN-ANNOTATION]**：注释正文必须包含工具名称和结果，不能只有文字描述。
- **G5 [READ-FIRST]**：在对代码形成任何假设之前，必须先使用 Read 工具读取代码。
- **G6 [ASSUMPTION-TRUST]**：对于每个函数，都要识别它信任的内容（输入、返回值、全局状态、调用方保证），并追问每项信任被违背时会发生什么。
- **G7 [REACHABILITY]**：发现必须是可达的。`orchestrator` 阻塞点会以机械化方式强制执行此要求：
  - **双信号硬门禁**：静态调用方数量为零，并且二进制预言机为 `absent`（完整 DWARF）→ `orchestrator` 拒绝 `finding`，强制标记为 `dormant`。编译器已删除该函数——缺陷确实存在，但无法被利用。
  - **软门禁**：静态调用方数量为零，且没有二进制预言机数据 → `orchestrator` 要求通过 `--reach-via` 说明函数如何可达（回调、HTTP 路由、导出的 API、跨语言绑定、动态分派）。这可以防止 honeyslop（植入了明显缺陷的死代码）虚增发现数量。
  - 入口点（来自 context-map）和存在静态调用方的函数会自动绕过此门禁。

## [STYLE]

- JSON 中的状态值：snake_case（`clean`、`dormant`、`suspicious`、`finding`、`error`）
- 人类可读输出中的状态：Title Case（`Clean`、`Suspicious`、`Finding`、`Error`）
- 不使用红色/绿色指示符（其含义取决于观察视角）
- 注释采用 markdown prose——注释正文中不使用 JSON
- `findings.json` 中的发现使用标准 RAPTOR schema

## [STRATEGIES]

根据文件路径、参数类型和返回类型，按函数选择审查策略。同一个函数可以应用多种策略。

| 策略 | 适用场景 | 关键问题 |
|----------|------|---------------|
| **通用** | 默认适用于所有代码 | 它信任什么？假设被违背时会发生什么？有什么出人意料之处？ |
| **输入处理** | 解析器、协议处理程序、解码器 | 对输入格式/大小有何假设？长度字段是否在使用前就被信任？ |
| **并发** | 锁 API、互斥锁、原子操作 | 锁的持有窗口？并发交错执行？内存屏障？ |
| **内存** | 分配器、引用计数、池 | 所有权模型？引用计数是否对称？失败时是否清理？ |
| **认证/权限** | 权限检查、ACL、凭据 | 是否可绕过检查？错误路径是否安全？是否存在未经验证的状态转换？ |
| **密码学** | 密码学 API、密钥材料、RNG | 算法使用是否正确？是否存在时序侧信道？密钥生命周期？ |
| **别名** | splice、zero-copy、scatterlist、sk_buff | 对别名有何假设？谁拥有后备页？其他子系统能否通过别名写入？ |

策略详情和 CVE 示例位于 `.claude/skills/audit/review.md`。

## [批判]

审查一批函数后，运行基于工具的批判检查：

```bash
libexec/raptor-audit critique --out "$OUTPUT_DIR"
```

该检查会以机械方式识别：
- **扫描覆盖率低**：审查时使用的工具检查少于 2 次的函数。为这些函数生成额外的 Semgrep/SMT/CodeQL 测试。
- **Mode 2 缺口**：已有确认的发现，但没有覆盖整个代码库的规则。编写一个通用检查器，并通过 `rules save` + `rules run` 运行它。
- **存在可疑之处但尚有工具未尝试**：并非所有工具类型都已尝试的可疑函数。尝试建议的工具。

批判检查生成的是行动项，而不是文字说明。每个行动项都应产生一次新的 `sweep` 调用，绝不能只是“再次审查”。

## [上下文]

上下文切片（由 `raptor-audit context` 组装）包括：
- 带行号的函数源代码行
- 调用图中一跳范围内的调用者和被调用者
- 检查清单元数据（签名、可见性、参数、返回类型、属性）
- 来自 `context-map.json` 的可达汇点
- 预先计算的信任面问题（按参数、按被调用者）
- **策略示例**：针对每种策略的 CVE 完整示例，展示发现漏洞的推理链
- **流跟踪**：来自 `/understand --trace`、经过此函数的跨函数数据流路径
- 来自共享语料库的先前已标记尝试（如有）
- 现有注解（用于重新审查上下文）

上下文能够感知策略：接受 `(char *buf, size_t len)` 的函数会获得输入处理策略示例（CVE-2023-0179）以及通用示例。别名相关代码中的函数会获得 CVE-2026-31431（CopyFail）。

## [提醒]

- LLM 生成假设和工具；确定性分析负责确认或证伪。
- 在没有工具反馈的情况下进行 5 次自我优化迭代后，严重漏洞增加了 37.6%（IEEE-ISTAS 2025）。工具支撑是强制要求，而非可选项。
- 已确认的模式应始终生成覆盖整个代码库的扫描规则（Mode 2 / KNighter 模式）。
- 覆盖记录会跨运行累积。缺口列表每次都会缩小。
- 注解会跨运行持久保存在项目目录中。它们构成审计轨迹。
- 每批完成后，在继续下一批之前运行 `critique` 以查找缺口。

## [恢复] 扩展与上下文管理

### 自动路径选择

进行研究时，首先尝试 `raptor-study-loop`——它使用 API 密钥调用外部 LLM，并自动处理多轮迭代。如果失败（未配置 API 密钥），则回退到 `study.md` 中的会话内路径（Claude 直接读取源代码）。无需用户决定——先尝试自动化路径，并静默使用回退方案。

同样的原则也适用于审查循环：尽可能委派给代理（见下文），对于小型目标或代理不可用的情况，则回退到直接审查。

### 会话内上下文管理

在会话内运行时（使用 Claude Code 作为 LLM），大型目标会耗尽上下文。以下三种机制用于管理此问题：

### 1. 将范围限定到子系统

对于大型代码库，不要一次性审计所有内容。使用 `--scope` 将每轮审计限制在一个子系统内：

```
/audit /data/linux_kernel/linux-6.18.2/ --scope ipc/ --local
/audit /data/linux_kernel/linux-6.18.2/ --scope net/ipv4/ --local
```

多次限定范围运行所产生的覆盖率记录会累积到同一个项目级输出目录中。每次限定范围的审计都是一个可管理的单元，能够控制在上下文和子代理的限制范围内。

### 2. 跨会话恢复

启动时，在再次执行研究/映射之前，先检查是否存在已有的运行记录：

```bash
libexec/raptor-audit gaps --out "$OUTPUT_DIR"
```

如果存在缺口，并且 `domain-model.json` + `context-map.json` 已经存在，则跳过研究和映射，直接进入审查循环。先前会话中的覆盖率记录、注释和发现结果已保存在磁盘上。

### 3. 代理委派

对于包含大量文件的目标，将函数审查委派给 `audit-reviewer` 代理类型，以保持主上下文精简。每个函数审查都是独立的——上下文切片包含了代理所需的一切信息。

按文件对缺口进行分组（不要为每个函数分别创建一个代理——需要遵守子代理限制）。对于每个仍存在缺口的文件：

1. 对文件中的每个函数运行 `libexec/raptor-audit context --target "$TARGET" --file <path> --function <name> --out "$OUTPUT_DIR" --json`，以收集上下文切片
2. 每个文件启动一个 `audit-reviewer` 代理（通过 `subagent_type: "audit-reviewer"`）。提示词必须包含：
   - `OUTPUT_DIR` 和 `TARGET` 路径
   - 文件路径以及要审查的函数名称列表
   - 关键的领域模型上下文（与该文件相关的不变量和契约）
   - 步骤 1 中的上下文切片
3. 该代理已内置方法论、CLI 语法和门禁规则——无需在提示词中重复扫描/记录说明

主循环保持精简：读取缺口、按文件分组、调度代理、收集结果。对于相互独立的文件，代理可以并行运行。每批任务完成后，运行 `critique`，以便在继续之前发现薄弱的审查结果。
