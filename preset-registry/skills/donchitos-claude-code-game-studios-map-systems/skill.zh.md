## 解析参数

两种模式：

- **无参数**：`/map-systems` — 运行完整的拆解工作流（阶段 1-5），
  以创建或更新系统索引。
- **`next`**：`/map-systems next` — 从索引中选取优先级最高且尚未设计的系统，
  并将其交接给 `/design-system`（阶段 6）。

同时确定评审模式（仅确定一次，并为本次运行中的所有关卡生成任务保存该模式）：
1. 如果传入了 `--review [full|lean|solo]` → 使用该模式
2. 否则读取 `production/review-mode.txt` → 使用其中的值
3. 否则 → 默认使用 `lean`

完整的检查模式请参阅 `.claude/docs/director-gates.md`。

## 阶段 1：读取概念（必需上下文）

读取游戏概念和所有现有的设计工作。这些内容为系统拆解提供原始素材。

**必需：**
- 读取 `design/gdd/game-concept.md` — 如果缺失，**给出清晰的消息并失败退出**：
  > “在 `design/gdd/game-concept.md` 中未找到游戏概念。请先运行 `/brainstorm`
  > 创建游戏概念，然后再回来将其拆解为系统。”

**可选（如果存在则读取）：**
- 读取 `design/gdd/game-pillars.md` — 支柱会约束优先级和范围
- 读取 `design/gdd/systems-index.md` — 如果存在，则从上次停止的位置**继续**
  （更新，而不是从头重新创建）
- 对 `design/gdd/*.md` 执行 Glob — 检查哪些系统 GDD 已经存在

**如果系统索引已经存在：**
- 读取索引，并向用户展示当前状态
- 使用 `AskUserQuestion` 询问：
  “系统索引已经存在，其中包含 [N] 个系统（[M] 个已设计，[K] 个尚未开始）。
  你想做什么？”
  - 选项：“使用新系统更新索引”、“设计下一个尚未设计的系统”、
    “评审并修订优先级”

## 阶段 2：系统枚举（协作式）

提取并识别游戏所需的所有系统。这是此 Skill 的创意核心——它需要人工判断，
因为概念文档很少会明确列举每一个系统。

### 步骤 2a：提取显式系统

扫描游戏概念中直接提及的系统和机制：
- 核心机制部分（最明确）
- 核心循环部分（暗示由哪些系统驱动每一层循环）
- 技术考量部分（网络、程序化生成等）
- MVP 定义部分（必需功能 = 必需系统）

### 步骤 2b：识别隐式系统

对于每个显式系统，识别其隐含的**隐藏系统**。游戏所需的系统总是比概念文档中
提及的更多。使用以下推断模式：

- “物品栏”意味着：物品数据库、装备槽位、重量/容量规则、
  物品栏 UI、用于保存/加载的物品序列化
- “战斗”意味着：伤害计算、生命值系统、命中检测、状态效果、
  敌人 AI、战斗 UI（生命条、伤害数字）、死亡/重生
- “开放世界”意味着：流式加载/分块、LOD 系统、快速旅行、地图/小地图、
  兴趣点追踪、世界状态持久化
- “多人游戏”意味着：网络层、大厅/匹配、状态同步、
  反作弊、网络 UI（延迟、玩家列表）
- “制作”意味着：配方数据库、材料采集、制作 UI、
  成功/失败机制、配方发现/学习
- “对话”意味着：对话树系统、对话 UI、选择追踪、NPC
  状态管理、本地化钩子
- “成长”意味着：XP 系统、升级机制、技能树、解锁
  追踪、成长 UI、成长存档数据

在对话文本中解释为什么需要每个隐含系统（并提供示例）。

### 步骤 2c：用户审核

按类别组织并展示枚举结果。对于每个系统，显示：
- 名称
- 类别
- 简短描述（1 句话）
- 它是显式的（来自概念）还是隐式的（推断得出）

然后使用 `AskUserQuestion` 收集反馈：
- “此列表中是否缺少某些系统？”
- “其中是否有任何系统应该合并或拆分？”
- “列出的系统中，是否有此游戏并不需要的系统？”

反复调整，直到用户批准该枚举结果。

## 阶段 3：依赖关系映射（协作）

确定每个系统所依赖的其他系统。如果一个系统必须先有另一个系统存在才能运行，
那么该系统就“依赖”另一个系统。

### 步骤 3a：映射依赖关系

列出每个系统的依赖项。使用以下依赖关系判断方法：
- **输入/输出依赖关系**：系统 A 生成系统 B 所需的数据
- **结构性依赖关系**：系统 A 提供系统 B 接入的框架
- **UI 依赖关系**：每个玩法系统都有一个对应的 UI 系统依赖于它
  （但 UI 要在玩法系统之后设计）

### 步骤 3b：按依赖顺序排序

将系统划分为以下层级：
1. **基础层**：零依赖的系统（最先设计和构建）
2. **核心层**：仅依赖基础层系统的系统
3. **功能层**：依赖核心层系统的系统
4. **表现层**：封装玩法系统的 UI 和反馈系统
5. **打磨层**：元系统、教程、分析、无障碍功能

### 步骤 3c：检测循环依赖

检查依赖关系图中是否存在环。如果发现：
- 向用户突出显示
- 提出解决方案（接口抽象、同步设计、通过定义两个系统之间的契约
  来打破循环）

### 步骤 3d：向用户展示

以分层列表的形式展示依赖关系图。突出显示：
- 所有循环依赖
- 所有“瓶颈”系统（许多其他系统依赖它们——这些系统风险较高）
- 所有无被依赖项的系统（叶节点——风险较低，可以稍后设计）

使用 `AskUserQuestion` 询问：“这个依赖顺序看起来正确吗？是否有我遗漏的依赖关系，或应该移除的依赖关系？”

**审核模式检查**——在生成 TD-SYSTEM-BOUNDARY 之前应用：
- `solo` → 跳过。注明：“TD-SYSTEM-BOUNDARY skipped — Solo mode.” 继续进行优先级分配。
- `lean` → 跳过（不是 PHASE-GATE）。注明：“TD-SYSTEM-BOUNDARY skipped — Lean mode.” 继续进行优先级分配。
- `full` → 正常生成。

**依赖关系映射获得批准后，在继续进行优先级分配之前，通过 Task 使用门禁 TD-SYSTEM-BOUNDARY（`.claude/docs/director-gates.md`）生成 `technical-director`。**

传递：依赖关系图摘要、层级分配、瓶颈系统列表以及所有循环依赖解决方案。

展示评估结果。如果为 REJECT，则在进入优先级分配之前与用户一起修改系统边界。如果为 CONCERNS，则将问题以内联方式记录在系统索引中并继续。

## 阶段 4：优先级分配（协作）

根据每个系统在哪个里程碑中需要使用，将其分配到相应的优先级层级。

### 步骤 4a：根据概念自动分配

使用以下启发式规则进行初始分配：
- **MVP**：概念中“Required for MVP”部分提及的系统，以及它们在
  Foundation 层中的依赖项
- **Vertical Slice**：在某个领域中提供完整体验所需的系统
- **Alpha**：所有剩余的游戏玩法系统
- **Full Vision**：打磨、元系统和锦上添花的系统

### 步骤 4b：用户审查

使用表格呈现优先级分配结果。对于每个层级，说明为何将这些系统
放入该层级。

使用 `AskUserQuestion` 询问：“这些优先级分配是否符合你的设想？
哪些系统的优先级应该提高或降低？”

在对话中解释理由：“我将[系统]放入 MVP，是因为核心循环需要它——
如果没有[系统]，30 秒循环就无法运作。”

**“Why”列指南**：解释为何将每个系统放入某个优先级层级时，应结合技术必要性与玩家体验方面的理由。不要只使用“Combat needs damage math”这类纯技术论据——应在相关情况下将其与玩家体验联系起来。优秀的“Why”条目示例：
- “核心循环所必需——如果没有它，放置决策就不会产生任何后果（支柱 2：放置就是谜题）”
- “Ballista 的穿透特色在此确立——这项属性定义使它在体验上与 Archer 截然不同”
- “所有经济决策的基础——玩家必须了解升级成本，才能作出有意义的放置选择”

当系统直接影响玩家体验时，仅有纯技术必要性（“X depends on Y”）是不够的。

**审查模式检查**——在生成 PR-SCOPE 之前执行：
- `solo` → 跳过。注明：“PR-SCOPE skipped — Solo mode.” 继续编写系统索引。
- `lean` → 跳过（不是 PHASE-GATE）。注明：“PR-SCOPE skipped — Lean mode.” 继续编写系统索引。
- `full` → 正常生成。

**优先级获得批准后，在编写索引之前，通过 Task 使用关卡 PR-SCOPE（`.claude/docs/director-gates.md`）生成 `producer`。**

传递：每个里程碑层级的系统总数、每个层级的预估实现工作量（系统数量 × 平均复杂度）、团队规模、所述项目时间表。

呈现评估结果。如果为 UNREALISTIC，则在编写索引之前提出修改优先级层级分配。如果为 CONCERNS，则注明相关问题并继续。

### 步骤 4c：确定设计顺序

结合依赖项排序与优先级层级，生成最终设计顺序：
1. 首先是 MVP Foundation 系统
2. 其次是 MVP Core 系统
3. 然后是 MVP Feature 系统
4. Vertical Slice Foundation/Core 系统
5. ……依此类推

这就是团队编写 GDD 的顺序。

## 阶段 5：创建系统索引（编写）

### 步骤 5a：起草文档

使用 `.claude/docs/templates/systems-index.md` 中的模板，将阶段 2-4 的
所有数据填入系统索引：
- 填写枚举表
- 填写依赖关系图
- 填写推荐的设计顺序
- 填写高风险系统
- 填写进度跟踪器（所有系统初始均为“Not Started”，除非 GDD 已存在）

### 步骤 5b：审批

提供文档摘要：
- 按类别统计的系统总数
- MVP 系统数量
- 按设计顺序排列的前 3 个系统
- 所有高风险项目

询问：“我可以将系统索引写入 `design/gdd/systems-index.md` 吗？”

等待批准。只有在用户回答“yes”后才写入文件。

**审查模式检查** — 在生成 CD-SYSTEMS 之前应用：
- `solo` → 跳过。注明：“CD-SYSTEMS 已跳过 — 单人模式。”继续执行阶段 7 的后续步骤。
- `lean` → 跳过（不是 PHASE-GATE）。注明：“CD-SYSTEMS 已跳过 — 精简模式。”继续执行阶段 7 的后续步骤。
- `full` → 正常生成。

**写入系统索引后，通过 Task 生成 `creative-director`，并使用门禁 CD-SYSTEMS（`.claude/docs/director-gates.md`）。**

传入：系统索引路径、游戏支柱和核心幻想（来自 `design/gdd/game-concept.md`）、MVP 优先级层级系统列表。

展示评估结果。如果结果为 REJECT，则在开始编写 GDD 前与用户一起修改系统集合。如果结果为 CONCERNS，则将其记录在系统索引中对应层级章节的顶部，格式为 `> **Creative Director Note**`。

### 步骤 5c：更新会话状态

写入后，如果 `production/session-state/active.md` 不存在，则创建该文件，然后使用以下内容更新它：
- 任务：系统拆解
- 状态：系统索引已创建
- 文件：design/gdd/systems-index.md
- 下一步：设计各个系统 GDD

**结论：COMPLETE** — 系统索引已写入 `design/gdd/systems-index.md`。
如果用户拒绝：**结论：BLOCKED** — 用户未批准写入。

## 阶段 6：设计各个系统（移交给 /design-system）

在以下情况下进入此阶段：
- 用户在创建索引后对设计系统回答“yes”
- 用户调用 `/map-systems [system-name]`
- 用户调用 `/map-systems next`

### 步骤 6a：选择系统

- 如果提供了系统名称，则在系统索引中查找该系统
- 如果使用了 `next`，则选择优先级最高且尚未设计的系统（按设计顺序）
- 如果用户刚刚完成索引，则询问：
  “你想现在开始设计各个系统吗？设计顺序中的第一个系统是 [name]。还是你想先停在这里，稍后再继续？”

使用 `AskUserQuestion` 询问：“现在开始设计 [system-name]、选择其他系统，还是先停在这里？”

### 步骤 6b：移交给 /design-system

选定系统后，调用 `/design-system [system-name]` skill。

`/design-system` skill 负责完整的 GDD 编写流程：
- 从游戏概念、系统索引和依赖项 GDD 中收集上下文
- 立即创建文件框架
- 逐一完成全部 8 个必需章节（协作式、渐进式）
- 交叉引用现有文档以避免冲突
- 分派给专业 agent 以获得领域专业知识
- 每个章节一经批准，立即写入文件
- 完成后运行 `/design-review`
- 更新系统索引

**不要在此处重复 /design-system 工作流。** 此 skill 负责系统
*索引*；`/design-system` 负责各个系统的 *GDD*。

### 步骤 6c：循环或停止

在 `/design-system` 完成后，使用 `AskUserQuestion`：
- “继续下一个系统（[下一个系统名称]）？”
- “选择其他系统？”
- “本次会话到此为止？”

如果继续，返回步骤 6a。

## 阶段 7：建议后续步骤

创建系统索引后（或设计完部分系统后），使用 `AskUserQuestion` 展示后续操作：

- “系统索引已写入。接下来你想做什么？”
  - [A] 开始设计 GDD — 运行 `/design-system [first-system-in-order]`
  - [B] 运行 `/gate-check systems-design` — 自动触发 CD-SYSTEMS 和 TD-SYSTEM-BOUNDARY 门禁，对系统集合进行正式的负责人签核
  - [C] 本次会话到此为止

**门禁检查选项（[B]）值得重点强调**：运行 `/gate-check systems-design` 会同时触发 CD-SYSTEMS 和 TD-SYSTEM-BOUNDARY 门禁，从而在范围问题、系统缺失和边界问题被固化到大量文档中之前将其发现。此操作为可选项，但建议新项目执行。

完成任何单个 GDD 后：
- “在新会话中运行 `/design-review design/gdd/[system].md` 以验证质量”
- “完成所有 MVP GDD 后运行 `/gate-check systems-design`”

## 协作协议

此技能在每个阶段都遵循协作式设计原则：

1. 每一步都遵循**提问 -> 选项 -> 决策 -> 草拟 -> 审批**
2. 在每个决策点使用 **AskUserQuestion**（解释 -> 获取反馈模式）：
   - 阶段 2：“是否缺少系统？需要合并还是拆分？”
   - 阶段 3：“依赖关系顺序是否正确？”
   - 阶段 4：“优先级分配是否符合你的构想？”
   - 阶段 5：“可以写入系统索引吗？”
   - 阶段 6：“开始设计、选择其他系统，还是停止？”然后移交给 `/design-system`
3. 每次写入文件前都询问：**“可以写入 [filepath] 吗？”**
4. **增量写入**：每设计完一个系统后更新系统索引
5. **移交**：单个 GDD 的编写由 `/design-system` 负责，该技能会处理
   增量式章节写入、交叉引用、设计审查和索引更新
6. **会话状态更新**：在每个里程碑后写入 `production/session-state/active.md`
   （索引已创建、系统已设计、优先级已更改）

**绝不**在未经审查的情况下自动生成完整系统列表并将其写入。
**绝不**在未经用户确认的情况下开始设计系统。
**始终**展示系统清单、依赖关系和优先级，供用户验证。
