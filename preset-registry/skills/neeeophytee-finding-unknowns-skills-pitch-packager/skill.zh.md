# 提案包装器

审阅者一开始面对的未知因素与构建者当初面对的相同，而且还多了一个：构建者是否考虑到了专家会深入追问的故障点。一份优秀的提案文档能让审阅者一次读完就消除这两方面的疑虑。

## 步骤

1. 收集相关产物：规格说明或计划、原型或演示、实现说明以及差异内容。如果任何面向用户的行为发生了变化，请索取演示录像或截图，并将其放在最前面。
2. 按持怀疑态度的读者的阅读顺序组织文档：
   - **演示** — 首先展示实际运行时的效果。GIF 或截图胜过文字说明。
   - **问题与押注** — 最多两段：说明它解决了什么问题，以及为何选择这种方案而非其他替代方案。
   - **专家会问什么** — 列出该领域的审阅者会提出的 3-5 个尖锐问题（边界情况、规模、故障模式、迁移），并诚实回答每一个问题，包括“尚未处理，以及为什么现阶段可以接受”。
   - **与计划的偏差** — 直接摘自实现说明，因为在审阅中才发现意外情况会损害信任。
   - **此变更不包含什么** — 明确范围边界，防止审阅无限扩张。
3. 控制在一页以内。链接到规格说明、说明文档和差异内容，而不是将它们内嵌进来。
4. 让呈现形式与使用场合相匹配：可直接粘贴到 Slack 的文档、PR 描述或独立 HTML 页面——如果不明确，就询问应使用哪一种。

## 约束

- 绝不夸大其词：隐瞒已知弱点的提案，可能换来一次批准，却会永久损害可信度。
- “专家会问什么”部分是核心。如果这部分很容易写，说明问题还不够尖锐。
- 如果工作实际上尚未准备就绪，那么诚实的提案就应该是一份状态更新，而明确说明这一点也是此技能的一部分。
