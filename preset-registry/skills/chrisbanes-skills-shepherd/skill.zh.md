# Shepherd

## 核心原则

基于证据而非噪声，持续推进已获授权的 PR 或 MR：轮询，处理每一项可执行事项，将每个目标的本地修复合并为一次推送，然后解决已处理的讨论串。没有明确授权时，绝不合并。

对于一次性检查、没有开放目标，或需要人工判断的操作，不要启动持续轮询；报告当前状态并停止。

## 操作流程

1. 使用 `git remote get-url origin` 检测平台。对于包含 `github.com` 的远程仓库使用 `gh`；对于包含 `gitlab` 的远程仓库使用 `glab`。如果检测结果不明确或不可用，则停止并询问。
2. 确定目标 PR/MR。如果存在明确的已处理 ID 快照，则从该快照开始；否则使用空快照。将快照中不存在的每条外部评论、审查和讨论串都视为未处理，包括早于本次会话的反馈。每次轮询后记录得到的 ID、CI 状态以及你自己的评论。
3. 在进行重复轮询之前，尝试调度一个成本最低的只读**证据助手子代理**。向它提供目标和上次看到的快照；要求它返回每条新反馈的 ID、正文和位置，以及批准/请求状态、非手动 CI 状态、失败的作业名称和日志引用。禁止其进行本地或远程修改。如果没有此类子代理或成本控制可用，则直接轮询。让获得授权的控制器负责分类、代码修改、回复、推送、讨论串解决、重试和合并。
4. 轮询目标，使用已调度的助手（如果有）：
   - GitHub：`gh pr list`、`gh pr view <number> --json comments,reviews,reviewDecision,statusCheckRollup`、`gh pr checks <number>`，以及 `gh run view <run-id> --log-failed`。需要回复或解决内联审查讨论串的 ID 时，通过 `gh api graphql` 查询 PR 的 `reviewThreads`。
   - GitLab：`glab mr list --source-branch $(git branch --show-current) --output json`、`glab mr view <iid> --comments`、`glab ci list --mr <iid>`，以及 `glab ci trace <job-id>`。
   将评论、审查状态和 CI 与保存的快照进行比较。不要重复处理旧反馈，也不要发布轮询更新。
5. 在更改远程状态之前，先对所有新反馈进行分类。修复明确要求的更改、格式问题、lint 问题、编译失败和明显的测试修复。在相关讨论串中回答明确的问题。升级处理架构性或相互矛盾的反馈、不熟悉的失败、不明显的测试修复，以及变更范围之外的冲突。除非另有指示，否则将 GitLab 手动作业视为不阻塞。
6. 独立处理每个目标：使用该目标的头部检出，批量完成并验证所有可执行的本地修复，然后为该目标推送一次。在支持的情况下，回复每个已处理的讨论串（否则留下一条简洁的 PR/MR 评论）；只有在回复和推送都成功后，才解决讨论串。不要合并不同头部的修复，不要在每条评论后都推送，不要解决仅涉及本地的修复，也不要在没有任何更改时发表评论。
7. 推送后重新检查 CI。对于明确的失败，检查其日志，在可行时复现或验证范围狭窄的修复，然后返回第 6 步。对于疑似不稳定的作业，重试一次；在 GitLab 上使用 `glab ci retry <job-id>`；如果再次失败，则报告该情况。如果检查处于等待状态，每 2–5 分钟轮询一次；主动修复期间每 30–60 秒轮询一次；连续几轮没有变化后，退避至 10 分钟以上。
8. 仅当需求和 CI 均为绿色、没有冲突，并且用户已明确授予合并权限（或适用既有授权）时，才进行合并。根据平台使用 `gh pr merge <number> --squash --delete-branch` 或 `glab mr merge <iid> --squash`。不要从批准中推断出授权。

## 完成或升级处理

持续推进，直到用户停止监控、每个目标都已合并或关闭，或需要升级处理。报告目标、当前 CI/评审状态、已采取的操作，以及下一步需要人工决策的事项。对于平台/目标选择不明确、未解决的冲突、重大的人工判断、评审者意见相互冲突，或经过三轮修复后仍然存在的失败，立即升级处理。

## 场景检查

- **通过：** 在没有已处理快照的情况下，shepherd 在已经存在一次 `REQUESTED_CHANGES` 评审、两条行内评论以及一个失败的 lint 任务后开始工作。结构化证据响应返回这些反馈和失败信息；控制器在本地修复两条评论，运行 lint，执行一次推送，并在推送成功后回复和解决评论，然后等待 CI。
- **不通过：** 证据辅助程序发现 `APPROVED`，但 CI 仍在运行。不要合并、推送、解决无关线程，也不要发布仅包含状态的评论；持续监控，直到实际满足合并门槛。
- **反例：** 用户要求进行一次性的 PR 状态查询，或没有开放目标。报告当前状态；不要调度辅助程序，也不要启动轮询循环。
