# Shepherd

## 核心原则

通过证据而非噪音，推动已获授权的 PR 或 MR 持续推进：轮询，处理新出现的可操作事项，将每个目标的本地修复合并为一次推送，然后解决已处理的讨论串。未经明确授权，绝不合并。

不要为一次性检查、没有开放目标，或需要人工判断的操作启动持久轮询；报告当前状态并停止。

## 操作流程

1. 使用 `git remote get-url origin` 检测平台：GitHub 使用 `gh`，GitLab 使用
   `glab`。如果平台不明确或不可用，则停止并请求确认。
2. 确定目标并建立已处理 ID 快照。快照中不存在的每条外部评论、审查或讨论串都视为新内容，包括会话开始前的反馈。每次轮询后记录反馈 ID、CI 状态以及此控制器发布的评论。
3. 在开始重复轮询之前，如果有可用的低成本只读证据辅助工具，则使用一个。向其提供目标和快照；要求其返回新的反馈 ID、正文、位置、审查状态、非手动 CI 状态、失败的任务以及日志引用。它绝不执行变更。让经过授权的控制器负责分流、修复、回复、推送、解决、重试和合并。
4. 使用平台 CLI 根据[提供商命令](references/provider-commands.md)进行轮询，然后将完整的审查、评论和 CI 状态与快照进行比较。仅在需要时检查失败日志。不要重复处理旧反馈，也不要发布仅包含状态的更新。
5. 在远程变更之前先对新证据进行分流。修复明确提出的请求以及范围明确的格式、lint、编译或测试失败；在讨论串中回答明确的问题。对于架构性或相互矛盾的反馈、不熟悉的失败、不明显的修复以及超出范围的冲突，进行升级处理。除非另有指示，GitLab 手动任务不构成阻塞。
6. 在各自独立的 head 检出中处理每个目标。将其修复批量处理并验证，然后只推送一次。在变更得到处理或问题得到回答后再回复；仅在回复和所需的推送成功后解决讨论串。不要合并不同的 head，不要在每条评论后都推送，不要解决仅存在于本地的修复，也不要在没有任何变更时发表评论。
7. 推送后重新检查 CI。对于明确的失败，检查证据，执行或验证范围明确的修复，然后重复步骤 6。对于疑似偶发的 GitLab 任务，重试一次；如果第二次仍然失败，则报告该失败。每 2–5 分钟轮询待处理检查，每 30–60 秒轮询正在进行的修复；连续数轮没有变化后，改为每 10 分钟以上轮询一次。
8. 仅当所有要求和 CI 均为绿色、没有冲突，并且用户授予了明确的或持续有效的合并权限时，才进行合并。不要从批准中推断出合并权限。

## 完成或升级处理

持续执行，直到用户停止监控、每个目标都已合并或关闭，或需要升级处理为止。报告目标、当前 CI/审查状态、已采取的操作以及下一步需要人工作出的决定。对于平台或目标选择不明确、未解决的冲突、重大的人工判断、相互冲突的审查者指示，或在三轮修复后仍未解决的失败，立即升级处理。
