# Shepherd

## 核心原则

通过证据而不是噪声，推动已获授权的 PR 或 MR 持续向前：轮询，处理新的可操作事项，将每个目标的本地修复批量合并为一次推送，然后解决已处理的线程。发生代码相关的 CI 失败后，使用完整的本地验证作为修复循环，并仅将 CI 用作确认。未经明确授权，绝不合并。

对于一次性检查、没有开放目标，或需要人工判断的操作，不要启动持续轮询；报告当前状态并停止。

## 流程

1. 使用 `git remote get-url origin` 检测平台：GitHub 使用 `gh`，GitLab 使用
   `glab`。如果平台不明确或不可用，则停止并询问。
2. 确定目标并建立已处理 ID 快照。快照中不存在的每条外部评论、审查或线程都视为新的，包括会话开始前的反馈。每次轮询后记录反馈 ID、CI 状态以及此控制器的评论。
3. 在开始重复轮询之前，如果有可用的最低成本只读证据辅助工具，则使用一次。向其提供目标和快照；要求其返回新的反馈 ID、正文、位置、审查状态、非手动 CI 状态、失败的作业以及日志引用。它绝不会执行变更。让已授权的控制器负责分诊、修复、回复、推送、解决、重试和合并。
4. 使用平台 CLI 结合[提供商命令](references/provider-commands.md)进行轮询，然后将完整的审查、评论和 CI 状态与快照进行比较。仅在必要时检查失败日志。不要重新处理旧反馈，也不要发布仅包含状态的更新。
5. 在执行远程变更前，先对新证据进行分诊。修复明确的请求，以及范围较窄的格式、lint、编译或测试失败；在线程中回答明确的问题。升级架构性或相互矛盾的反馈、不熟悉的失败、不明显的修复以及超出范围的冲突。除非另有指示，GitLab 手动作业不会阻塞流程。
6. 在各自独立的 head checkout 中处理每个目标，并批量处理所有已知的可操作事项。在发生代码相关的 CI 失败之前，按适当比例进行验证。发生一次代码相关的 CI 失败后，检查其证据，运行本地可用的每一项 CI 等效检查，修复所有失败，然后重新运行完整的本地套件，再进行一次修复推送。准确报告本地无法执行的检查，不要将 CI 用作迭代式测试运行器。
   在变更得到处理或问题得到回答后回复；只有在回复和所需推送成功后，才解决其线程。
   不要合并不同的 head，不要在每条评论后都推送，不要解决仅在本地完成的修复，也不要在没有任何变更时发表评论。
7. 在经过验证的修复推送后重新检查 CI；如果再次发生代码相关的失败，则返回第 6 步。对于疑似不稳定的 GitLab 作业，在不修改代码的情况下重试一次；如果第二次仍失败，则报告该失败。每 2–5 分钟轮询待处理的检查，每 30–60 秒轮询正在进行的修复；连续三次或更多次没有变化后，每 10 分钟以上轮询一次。连续两次没有变化时，仍保持正常的 2–5 分钟轮询频率。
8. 仅当要求均已满足、CI 为绿色、没有冲突，并且用户授予了明确的或持续有效的合并权限时，才进行合并。不要从批准中推断出合并权限。

## 完成或升级处理

持续推进，直到用户停止监控、每个目标都已合并或关闭，或需要升级处理。报告目标、当前 CI/审查状态、已采取的操作，以及下一步需要人工做出的决策。对于平台/目标选择不明确、冲突未解决、涉及重大人工判断、审查者意见相互冲突，或经过三轮修复后仍未解决的故障，立即升级处理。
