# Shepherd

## 核心原则

通过证据而非噪声，推动已获授权的 PR 或 MR 持续前进：轮询，在出现新的可操作事项时采取行动，将每个目标的本地修复合并为一次推送，然后解决已处理的讨论线程。在发生与代码相关的 CI 失败后，使用完整的本地验证作为修复循环，并仅将 CI 用作确认。未经明确授权，绝不合并。

不要为一次性检查、没有开放目标或需要人工判断的操作启动持久轮询；报告当前状态后停止。

## 流程

1. 通过 `git remote get-url origin` 检测平台：GitHub 使用
   `gh`，GitLab 使用 `glab`。如果平台不明确或不可用，则停止并请求确认。
2. 确定目标并建立已处理 ID 快照。快照中不存在的每条外部评论、审查或
   讨论线程都视为新的，包括会话开始前的反馈。每次轮询后记录反馈 ID、CI 状态以及
   此控制器发布的评论。
3. 在进行重复轮询之前，如果有可用的最低成本只读证据辅助工具，则使用一次。
   向其提供目标和快照；要求其返回新的反馈 ID、正文、位置、审查状态、非手动 CI 状态、
   失败的作业以及日志引用。该工具绝不执行变更。让获得授权的控制器负责分类、
   修复、回复、推送、解决、重试和合并。
4. 使用平台 CLI 按照 [provider commands](references/provider-commands.md) 进行轮询，
   然后将完整的审查、评论和 CI 状态与快照进行比较。仅在需要时检查失败日志。
   不要重新处理旧反馈，也不要发布仅包含状态的更新。
5. 在进行远程变更之前，先对新证据进行分类。修复明确的请求以及范围明确的格式、
   lint、编译或测试失败；在对应线程中回答明确的问题。对于架构性或相互矛盾的反馈、
   不熟悉的失败、非显而易见的修复以及超出范围的冲突，进行升级处理。除非另有指示，
   GitLab 手动作业不会阻塞流程。
6. 在每个目标自己的 head checkout 中处理，并批量处理所有已知的可操作事项。
   在发生与代码相关的 CI 失败之前，按比例进行验证。发生一次之后，检查其证据，
   运行本地可用的每项 CI 等效检查，修复所有失败，并重新运行完整的本地套件，然后
   进行一次修复推送。准确报告本地不可用的检查，不要将 CI 用作迭代式测试运行器。
   在完成修复或回答后进行回复；只有在回复和所需推送成功后，才解决其讨论线程。
   不要合并不同的 head，不要在每条评论后都推送，不要解决仅限本地的修复，也不要在
   没有任何变更时发表评论。
7. 在经过验证的修复推送后重新检查 CI；如果再次发生与代码相关的失败，则返回步骤 6。
   对于疑似 GitLab 不稳定的作业，在不进行代码变更的情况下重试一次；若第二次失败则报告。
   每 2–5 分钟轮询待处理检查，每 30–60 秒轮询正在进行的修复；连续三次或更多次未发生变化后，
   每 10 分钟或更长时间轮询一次。连续两次未发生变化时，仍保持正常的 2–5 分钟轮询频率。
8. 只有在要求已满足、CI 为绿色、没有冲突，并且用户授予了明确的或长期有效的合并权限时，
   才能合并。不要从批准中推断出合并权限。

## 完成或升级处理

持续处理，直到用户停止监控、每个目标都已合并或关闭，或需要升级处理。报告目标、当前 CI/评审状态、已采取的行动，以及下一步需要人工决策的事项。对于平台/目标选择不明确、存在未解决的冲突、涉及重要人工判断、评审者意见相互冲突，或经过三轮修复后仍未解决的故障，立即升级处理。
