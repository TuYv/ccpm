# 系统设计基线构建器

**目标：** 为项目架构驱动的需求和约束创建或更新一份持久的权威来源。仅更改已批准的架构文档；不要设计解决方案、审查计划、审计实现、编辑产品代码，或编造缺失的目标。

**执行约定：** 有序复选框即为完成定义。将每个项目在内部跟踪为 `PENDING`、附有具体证据的 `PROVEN`、附有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委托或工具失败均不构成证明。每个章节后重新核对项目。返回前，解决所有 `PENDING`，且仅计入 `PROVEN` 和 `CLEARED`；对每个缺口应用本技能的结论和批准规则。保留用户意图、范围和现有授权。继续已获授权的工作；仅针对具有实质影响的未解决选择或必要的外部批准提问。根据实质性风险调整深度，但不得悄然跳过检查。保持依赖关系和安全顺序；否则，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选能力 | 备选方案 |
|---|---|---|
| 仓库规则和文档约定 | 原生文件读取加聚焦搜索 | 用户提供的约定，并明确说明限制 |
| 现有需求和架构工件 | 窄范围仓库搜索和直接读取 | 标记来源的对话证据 |
| 当前工作负载或服务证据 | 指标、仪表板、日志、清单或已检入的报告 | 标记为 `UNKNOWN`；绝不编造生产数据 |
| 当前外部限制或标准 | 官方文档或规范 | 将该声明标记为 `UNVERIFIED` |
| 文档修改 | 对已批准 Markdown 工件进行最小化补丁 | 如无安全且获授权的可写路径，则返回 `BLOCKED` |

仅当随时间变化的事实会改变约束时，才使用外部研究。不得为必须来自产品负责人、运营人员、仓库或测量工作负载的数值进行浏览。

## 工件规则

- 优先使用现有且明确无歧义的架构需求文档。
- 否则使用 `docs/architecture/system-design-baseline.md`。
- 写入前先阅读，保留无关内容，并就地更新事实，而非创建并行的权威来源。
- 将适用性单独分类为 `APPLICABLE` 或 `NOT_APPLICABLE`，并为排除项提供证据。
- 将每个适用项目划分为 `DRIVER`、`SUPPORTING` 或 `INFORMATIONAL`。
- 将证据单独分类为 `CONFIRMED`、`ASSUMED` 或 `UNKNOWN`。
- 区分已观察到的当前值、所需目标、硬性限制和未来演进触发条件。
- 通过可观察场景和响应度量表达质量属性；将未决定的目标记录为缺失决策，而非编造数值。
- 将基线视为版本化的项目知识，而非不可变的承诺。

## 检查清单

### 1. 确定范围和目标位置

- [ ] 明确项目、业务成果、目标读者、已批准的文档范围和语言。
- [ ] 阅读适用的仓库指引并检查 Git 状态，确保不触及无关改动。
- [ ] 搜索现有的需求、架构、SLO、恢复、安全、成本和所有权文档。
- [ ] 选择一个规范工件：复用明确的等效文档，或选择默认路径；说明为何不会创建重复文档。
- [ ] 若目标位置存在歧义，且选择其中之一可能会分裂项目权威来源，则返回 `BLOCKED`。

### 2. 构建证据台账

- [ ] 收集用于驱动因素分析的业务目标、参与者、用户旅程、范围、非目标和决策周期，以及其来源和置信度；不要创建第二份上下文清单。
- [ ] 记录当前工作负载、数据量、服务行为、平台限制和既有承诺的来源。
- [ ] 将仓库事实与利益相关者的选择和估算分开。
- [ ] 检测文档、代码、配置与既定需求之间的矛盾；在解决前保留两种说法。
- [ ] 仅询问其缺失会实质性改变架构的选择；将所有其他缺口标记为 `UNKNOWN`。

### 3. 定义并排序架构驱动因素

- [ ] **业务和范围：**记录参与者、关键旅程、业务周期、范围、非目标以及对外交付承诺。
- [ ] **需求和数据规模：**在相关时记录当前和目标用户数、速率、并发量、负载大小、增长、保留期限和预测周期。
- [ ] **用户可感知的服务质量：**为可用性、延迟、吞吐量、错误率、正确性或新鲜度定义 SLI 和 SLO，并指定测量窗口。
- [ ] **数据语义和恢复：**在受影响的边界处定义一致性、排序、幂等性、对账、持久性、备份、RTO、RPO 和可接受的数据丢失。
- [ ] **安全、隐私和合规：**定义信任边界、数据分类、数据驻留、访问、审计和破坏性操作约束。
- [ ] **运营和经济性：**定义职责归属、运营能力、成本范围、支持区域、交付节奏以及平台或供应商限制。
- [ ] **演进：**记录足以证明应重新审查某项假设、目标或延期能力的阈值、业务事件或证据。
- [ ] 分别处理适用性、关键性和证据状态；不要用 `UNKNOWN` 表示不重要或 `NOT_APPLICABLE`。
- [ ] 对最可能塑造架构的少数场景进行优先级排序，并将每个场景表述为来源/刺激/环境/构件/响应/度量。

### 4. 编写基线

- [ ] 创建或更新工件，包含：标识和状态；业务上下文；范围和非目标；关键场景；工作负载和数据；质量目标；恢复；一致性；安全；成本和运营；约束；假设和未知项；复审触发条件。
- [ ] 为重要参数提供其主题、适用性、关键性、证据状态、值/范围、来源、负责人、截至日期和复审触发条件。通过显式继承一次性声明共享元数据；对于缺失的负责人或值使用 `UNKNOWN`。
- [ ] 保持计算可复现，并将估算与观测到的测量结果分开标记。
- [ ] 仅通过仓库路径或文档标题链接共享架构工件；绝不要求特定工作流或工具。
- [ ] 保留理解已变更需求所需的历史上下文，而不是悄然重写先前的承诺。

### 5. 验证并报告

- [ ] 重新阅读已编写的工件，并验证没有未知项被转换为确定事实。
- [ ] 检查目标是否可度量、内部一致，并且与有证据支持的业务周期相称。
- [ ] 检查每个架构关键缺口是否都有负责人或明确的下一步证据行动。
- [ ] 仅当基线可用于决策且没有重要未知项缺少安全处理规则时使用 `READY`；当工件有用但存在影响重大的开放驱动因素时使用 `INCOMPLETE`；当范围、权限或目标位置阻止安全创建时使用 `BLOCKED`。

## 自检

- [ ] **返回前核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或已获授权的工件。复用有效证据；不要自动重新扫描存储库或重新运行已成功的命令。仅针对相关变更、失败或尚未解决的证据重复检查。披露仍然存在的缺口。

## 输出约定

使用用户的语言，按以下顺序报告；保留全部五个字段，且每项事实仅陈述一次。较短的结果可以每个字段占一行；省略空表格，不要复制已链接工件的内容：

1. **结果：** Skill 特定的结论及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 下述 Skill 特定字段；区分事实、推断和未经验证的声明。链接工件；适合时使用表格。
4. **验证：** 检查/结果、无法获得的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或逐项列出每个 `UNPROVEN` 项目的原因、对结果的影响及确切的后续操作；剩余风险和需要作出的决定。

**Skill 特定证据：** 工件路径、已确定的驱动因素和按优先级排列的质量场景、适用约束以及已变更的章节。工件负责维护驱动因素登记表：主题/参数、适用性、关键程度、证据状态、值/度量、来源/负责人、截至日期和审查触发条件。仅总结会影响决策的缺口；不要将登记表复制到回复中。
