# 系统设计基线构建器

**目标：** 为项目中驱动架构的需求和约束创建或更新一个持久的事实来源。仅更改已批准的架构文档；不要设计解决方案、评审计划、审计实现、编辑产品代码或臆造缺失的目标。

**执行契约：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序处理每一项，并且仅当其操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的结论和批准规则应用于每个未完成项，并在回复开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 仓库规则和文档约定 | 原生文件读取加聚焦搜索 | 用户提供的约定，并明确说明限制 |
| 现有需求和架构产物 | 小范围仓库搜索和直接读取 | 标明来源的对话证据 |
| 当前工作负载或服务证据 | 指标、仪表板、日志、清单或已检入的报告 | 标记为 `UNKNOWN`；绝不编造生产环境数据 |
| 当前外部限制或标准 | 官方文档或规范 | 将声明标记为 `UNVERIFIED` |
| 文档修改 | 对已批准的 Markdown 产物应用最小补丁 | 如果没有获得安全可写路径的授权，则返回 `BLOCKED` |

仅当时效性事实会改变某项约束时，才使用外部研究。不要通过浏览来查找必须由产品负责人、运维人员、仓库或实测工作负载提供的值。

## 产物规则

- 优先使用现有且无歧义的架构需求文档。
- 否则使用 `docs/architecture/system-design-baseline.md`。
- 写入前先读取，保留无关内容，并就地更新事实，而不是创建并行的事实来源。
- 将适用性单独分类为 `APPLICABLE` 或 `NOT_APPLICABLE`，并为排除项提供证据。
- 将每个适用项分级为 `DRIVER`、`SUPPORTING` 或 `INFORMATIONAL`。
- 将证据单独分类为 `CONFIRMED`、`ASSUMED` 或 `UNKNOWN`。
- 为每个架构驱动因素记录来源、负责人、确认日期和评审触发条件。
- 将观测到的当前值、要求的目标、硬性限制和未来演进触发条件分开记录。
- 使用可度量的质量属性场景；避免使用“快速”“可扩展”或“安全”等没有响应度量的词语。
- 将基线视为带版本的项目知识，而非不可变的承诺。

## 检查清单

### 1. 确定范围和目标位置

- [ ] 明确项目、业务成果、目标读者、已批准的文档范围和语言。
- [ ] 阅读适用的仓库说明并检查 Git 状态，确保不触碰无关更改。
- [ ] 搜索现有的需求、架构、SLO、恢复、安全、成本和所有权文档。
- [ ] 选择一个规范产物：复用明确等效的产物，或选择默认路径；说明为何不会创建重复文档。
- [ ] 如果目标位置存在歧义，并且自行选择可能会割裂项目事实来源，则返回 `BLOCKED`。

### 2. 构建证据台账

- [ ] 提取已确认的业务目标、参与者、关键旅程、范围、非目标和决策时间跨度。
- [ ] 记录当前工作负载、数据量、服务行为、平台限制和现有承诺的来源。
- [ ] 将代码库事实与利益相关者的选择和估算区分开来。
- [ ] 识别文档、代码、配置和声明的需求之间的矛盾；在解决矛盾之前保留各方说法。
- [ ] 仅询问那些缺失后会实质性改变架构的选择；将所有其他缺口标记为 `UNKNOWN`。

### 3. 定义架构驱动因素并确定优先级

- [ ] **业务和范围：**记录参与者、关键旅程、业务时间跨度、范围、非目标和对外承诺的成果。
- [ ] **需求和数据规模：**在相关情况下，记录当前及目标用户数、速率、并发量、有效载荷、增长、保留期限和预测时间跨度。
- [ ] **用户可感知的服务质量：**定义可用性、延迟、吞吐量、错误率、正确性或新鲜度的 SLI 和 SLO，并明确测量窗口。
- [ ] **数据语义和恢复：**定义受影响边界处的一致性、顺序性、幂等性、对账、持久性、备份、RTO、RPO 和可接受的数据丢失量。
- [ ] **安全、隐私和合规：**定义信任边界、数据分类、驻留要求、访问控制、审计和破坏性操作约束。
- [ ] **运维和经济性：**定义所有权、运维能力、成本范围、支持的区域、交付节奏以及平台或供应商约束。
- [ ] **演进：**记录足以证明应重新审视某项假设、目标或延期能力的阈值、业务事件或证据。
- [ ] 将适用性、关键性和证据状态区分开来；不要使用 `UNKNOWN` 表示不重要或 `NOT_APPLICABLE`。
- [ ] 优先考虑最有可能影响架构的少数场景，并将每个场景表述为来源/刺激/环境/制品/响应/度量。

### 4. 编写基线

- [ ] 创建或更新制品，内容包括：标识和状态；业务背景；范围和非目标；关键场景；工作负载和数据；质量目标；恢复；一致性；安全；成本和运维；约束；假设和未知项；评审触发条件。
- [ ] 为每个重要参数提供其主题、适用性、关键性、证据状态、值或范围、来源、负责人、截至日期和评审触发条件。
- [ ] 确保计算可复现，并将估算与观测测量结果分开标注。
- [ ] 仅通过代码库路径或文档标题链接共享架构制品；绝不要求采用特定的工作流或工具。
- [ ] 保留理解需求变更所需的历史背景，而不是悄然改写之前的承诺。

### 5. 验证并报告

- [ ] 重新阅读已编写的制品，验证没有将任何未知项转变为确凿事实。
- [ ] 检查目标是否可度量、内部一致，并与有证据支持的业务时间跨度相称。
- [ ] 检查每个架构关键缺口是否都有负责人或明确的下一步取证行动。
- [ ] 确认未更改任何产品代码、测试、不相关文档或外部系统。
- [ ] 仅当基线可用于决策，且不存在任何缺少安全处理规则的重要未知项时，才使用 `READY`；对于包含重大未决驱动因素但仍有用的制品，使用 `INCOMPLETE`；当范围、权限或目标位置妨碍安全创建时，使用 `BLOCKED`。

## 输出约定

```markdown
# System Design Baseline

**Verdict:** READY | INCOMPLETE | BLOCKED
**Artifact:** path

## Established drivers
- Prioritized architecture-driving scenarios
- Applicable business, demand, quality, data, security, operational, economic, and evolution constraints

## Driver register
| Theme | Parameter | Applicability | Criticality | Evidence status | Value or measure | Source and owner | Review trigger |
|---|---|---|---|---|---|---|---|

## Changes made
- Created or updated sections
- Preserved conventions and related artifacts

## Residual risks
Only constraints that can still reverse an architecture decision.
```
