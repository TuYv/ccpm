# Suede 收入运营

Suede RevOps 梳理了连接获客、销售和客户成功的生命周期规则、数据契约、评分、路由和交接流程。它产出可直接实施的运营逻辑，同时通过实时架构审查和审批，将生产环境中的 CRM 数据变更置于受控流程之后。

## 开始之前

**先检查产品营销背景：**
如果 `.agents/product-marketing.md` 存在（或 `.claude/product-marketing.md`，或者在较旧的配置中使用的旧版 `product-marketing-context.md` 文件名），请在提问前先阅读。使用其中的背景信息，只询问尚未涵盖的信息或与当前任务具体相关的信息。

收集以下背景信息（如果用户未提供，请进行询问）：

1. **GTM 模式** — 产品驱动（PLG）、销售驱动，还是混合模式？
2. **ACV 范围** — 平均合同价值是多少？
3. **销售周期长度** — 从首次接触到成交的天数是多少？
4. **当前技术栈** — CRM、营销自动化、日程安排、数据丰富工具？
5. **当前状态** — 目前如何管理线索？哪些方面运转良好，哪些方面存在问题？
6. **目标** — 提高转化率？缩短线索响应时间？修复交接漏洞？从零开始搭建？

根据用户提供的信息开展工作。如果他们已经明确了问题领域，就从那里开始。不要因缺少输入而阻塞 — 使用现有信息，并指出哪些补充内容有助于强化方案。

## 核心原则

### 唯一事实来源
每个线索和客户账户都应有一个记录系统。如果数据存在于多个地方，就会产生冲突。选定一个 CRM 作为权威来源，并将所有内容同步到其中。

### 先定义，再自动化
在构建工作流之前，先在纸面上明确阶段定义、评分标准和路由规则。将一个有问题的流程自动化，只会让错误结果更快地产生。

### 衡量每次交接
团队之间的每次交接都可能造成流失。营销到销售、SDR 到 AE、AE 到 CS — 每个环节都需要 SLA、跟踪机制，以及负责跟进的人。

### 收入团队协同
营销、销售和客户成功必须对定义达成一致。如果营销将某个对象称为 MQL，但销售不愿跟进，那么这个定义就是错误的。协同会议不是可有可无的。

## 线索生命周期框架

### 阶段定义

| 阶段 | 进入标准 | 退出标准 | 负责人 |
|-------|---------------|---------------|-------|
| **订阅者** | 订阅内容（博客、新闻通讯） | 提供公司信息或表现出参与度 | 营销 |
| **线索** | 已识别且拥有基本信息的联系人 | 符合最低匹配标准 | 营销 |
| **MQL** | 达到匹配度 + 参与度阈值 | 销售在 SLA 内接受或拒绝 | 营销 |
| **SQL** | 销售接受，并通过沟通完成资格确认 | 创建商机或重新培育 | 销售（SDR/AE） |
| **商机** | 已确认预算、决策权、需求和时间表 | 成交或输单 | 销售（AE） |
| **客户** | 交易成交 | 扩展、续约或流失 | CS / 客户账户管理 |
| **传播者** | NPS 较高、开展推荐活动、参与案例研究 | 持续参与项目 | CS / 营销 |

### MQL 定义

MQL 同时需要具备**匹配度**和**参与度**：

- **匹配度评分** — 此人是否符合你的 ICP？（公司规模、行业、职位、技术栈）
- **参与度评分** — 他们是否表现出购买意向？（定价页面、演示请求、多次访问）

仅具备其中一项并不够。一家完全符合条件但从未参与互动的公司，不是 MQL。一个下载了每本电子书的学生，也不是 MQL。

### MQL-to-SQL 交接 SLA

定义响应时间并记录下来：
- 将 MQL 提醒发送给指定销售代表
- 销售代表在 **4 小时**内联系（工作时间内）
- 销售代表在 **48 小时**内完成资格认定或拒绝
- 被拒绝的 MQL 进入回收培育流程，并注明原因代码

**如需完整的生命周期阶段模板和 SLA 示例**：请参阅 [references/lifecycle-definitions.md](references/lifecycle-definitions.md)

## 线索评分

### 评分维度

**显性评分（匹配度）** — 他们是谁：
- 公司规模、行业、收入
- 职位名称、资历、部门
- 技术栈、地理位置

**隐性评分（参与度）** — 他们做了什么：
- 页面访问（尤其是定价页、演示页、案例研究页）
- 内容下载、网络研讨会出席
- 电子邮件参与度（打开、点击）
- 产品使用情况（适用于 PLG）

**负向评分** — 不符合条件的信号：
- 竞争对手的电子邮件域名
- 学生或个人电子邮件
- 取消订阅、垃圾邮件投诉
- 职位名称不匹配（实习生、学生）

### 构建评分模型

1. 定义你的 ICP 属性并为其设置权重
2. 根据已成交数据识别高意向行为信号
3. 为每项属性和行为设置分值
4. 设置 MQL 阈值（在 100 分制中通常为 50-80 分）
5. 使用历史数据进行测试——该模型能否正确识别过去的成交案例？
6. 启动、衡量并按季度重新校准

### 常见的评分错误

- 对内容下载赋予过高权重（研究 ≠ 购买意向）
- 未纳入负向评分（会让不合格线索通过）
- 设置后置之不理（买家行为会变化；应按季度重新校准）
- 对所有页面访问赋予相同分值（定价页 ≠ 博客文章）

**如需详细的评分模板和示例模型**：请参阅 [references/scoring-models.md](references/scoring-models.md)

## 线索分配

### 分配方式

| 方式 | 工作原理 | 最适用于 |
|--------|-------------|----------|
| **轮流分配** | 在销售代表之间均匀分配 | 区域相同、交易规模相近 |
| **基于区域** | 按地理位置、垂直行业或细分市场分配 | 区域团队、行业专家 |
| **基于账户** | 将指定账户分配给指定销售代表 | ABM 业务、战略账户 |
| **基于技能** | 按交易复杂度、产品线或语言进行分配 | 产品线多样化的团队、全球团队 |

### 分配规则要点

- 优先分配给**最具体的匹配项**，然后再回退到通用规则
- 包含一个**备用负责人**——未分配的线索很快就会流失，并浪费销售管道
- 轮流分配应考虑**销售代表的承载能力和可用性**（带薪休假、配额达成情况）
- 记录每次分配决策，以便审计和优化

### 线索响应速度

响应时间是线索转化中最重要的可控因素之一。  
广为引用的供应商研究（Lead Connect、InsideSales）报告了数量级上的差异；在自行基于数据进行测量之前，应将其排序视为可靠信息，将倍数视为未经验证的信息：
- 在 **5 分钟内**联系 — 目标时限；超过这一时限后，资格评估率会急剧下降
- 超过 **30 分钟**后，转化率会显著下降
- 超过 **24 小时**后，该线索实际上已经冷却

构建优先考虑速度的路由规则。立即提醒销售代表。如果错过 SLA，则进行升级处理。

**关于路由决策树和特定平台的设置**：参见 [references/routing-rules.md](references/routing-rules.md)

## 销售管道阶段管理

### 销售管道阶段

| 阶段 | 必填字段 | 退出标准 |
|-------|----------------|---------------|
| **已确认资格** | 联系信息、公司、来源、匹配度评分 | 已安排探索性电话 |
| **探索** | 痛点、当前解决方案、时间表 | 已确认需求，已安排演示 |
| **演示/评估** | 技术要求、决策者 | 评估结果积极，已提出方案请求 |
| **方案** | 定价、条款、利益相关者关系图 | 方案已交付并完成审阅 |
| **谈判** | 修订条款、审批链、成交日期 | 条款已达成一致，合同已发送 |
| **赢单结束** | 已签署合同、付款条款 | 已完成向 CS 的交接 |
| **输单结束** | 流失原因、竞争对手（如有） | 已记录复盘 |

### 阶段规范

- **每个阶段的必填字段** — 未填写必需数据时，不要让销售代表推进交易
- **过期交易提醒** — 标记在某个阶段停留超过平均时长的交易（例如，超过平均天数的 2 倍）
- **阶段跳过检测** — 当交易跳过阶段时发出提醒（已确认资格 → 方案，跳过探索）
- **成交日期规范** — 推迟日期必须包含原因；不得无声推迟

### 销售管道指标

| 指标 | 它告诉你的信息 |
|--------|-------------------|
| 阶段转化率 | 交易在哪个阶段流失 |
| 阶段平均停留时间 | 交易在哪个阶段停滞 |
| 销售管道速度 | 每天通过漏斗的收入 |
| 覆盖率 | 销售管道价值与配额的比值（目标为 3-4 倍） |
| 按来源划分的赢单率 | 哪些渠道能带来真实收入 |

## CRM 自动化工作流

与平台无关的构建清单 — 在确定技术栈之前需要设计的工作流集合，按构建顺序排列：

1. **MQL 提醒 + 分配** — 立即向销售代表发送包含线索背景的信息
2. **SLA 升级** — 未达到响应时间要求时通知经理
3. **由评分驱动的阶段晋级** — 满足条件时推进生命周期阶段
4. **已预订会议 / 未出席** — 通知 AE；未出席时自动跟进
5. **赢单结束交接** — 创建 CS 任务并更新预测
6. **过期交易提醒** — 标记在某个阶段停留超过平均天数 2 倍的交易
7. **回收线索培育** — 将已确认不合格的线索连同原因代码返回给营销团队
8. **活动摘要 + 重新互动** — 每日高意向摘要；沉寂线索重新出现时发出提醒

**关于各平台的触发器和操作定义** — HubSpot workflows、Salesforce Flow 等效实现、Calendly/SavvyCal 和 Zapier 模式，包括轮询分配、按条件路由以及会前丰富信息：参见 [references/automation-playbooks.md](references/automation-playbooks.md)。在已知 CRM 后阅读该文档；在尚未确定 CRM 时，根据上面的清单进行构建。

## Deal Desk 流程

### 何时需要 Deal Desk

- ACV 高于 **$25K**（或适用于非标准交易的自定义阈值）
- 非标准付款条款（net-90、按季度计费）
- 采用自定义定价的多年期合同
- 超出已公布梯度的批量折扣
- 定制法律条款或 SLA

### 审批工作流层级

| 交易规模 | 所需审批 |
|-----------|-------------------|
| 标准定价 | 自动批准 |
| 10-20% 折扣 | 销售经理 |
| 20-40% 折扣 | 销售副总裁 |
| 40%+ 折扣或自定义条款 | Deal Desk 审核 |
| 多年期 / 企业级 | 财务 + 法务 |

### 非标准条款处理

记录每一项例外。跟踪最常被请求的非标准条款——如果每个人都在请求同一个例外，就应将其标准化。按季度进行审查。

## 数据卫生与丰富

### 去重策略

- **匹配规则** — 以电子邮件域名 + 公司名称 + 电话作为主要匹配键
- **合并优先级** — CRM 记录优先于营销自动化记录；对于字段，最近的活动优先
- **定期去重** — 每周运行自动去重，并对边缘情况进行人工审核

### 必填字段强制执行

- 在每个生命周期阶段强制执行必填字段
- 如果字段为空，则阻止阶段推进
- 使用渐进式用户画像——不要一开始就要求填写所有内容

丰富服务供应商列在下方的工具集成部分，其中包含在提出任何供应商之前适用的来源、时效性、合法依据和信用成本检查。

### 季度审计清单

- 审查并合并重复记录
- 验证长期未联系的联系人的电子邮件可送达性
- 归档超过 12 个月没有活动的联系人
- 审计生命周期阶段分布（寻找瓶颈）
- 抽样验证丰富数据的准确性

## RevOps 指标仪表板

### 关键指标

| 指标 | 公式 / 定义 | 基准 |
|--------|---------------------|-----------|
| Lead-to-MQL 转化率 | MQLs / 总线索数 | 5-15% |
| MQL-to-SQL 转化率 | SQLs / MQLs | 30-50% |
| SQL-to-Opportunity 转化率 | Opportunities / SQLs | 50-70% |
| Pipeline velocity | (# deals x avg deal size x win rate) / avg sales cycle | 因 ACV 而异 |
| CAC | 销售总支出 + 营销总支出 / 新客户数 | LTV:CAC > 3:1 |
| LTV:CAC 比率 | 客户生命周期价值 / CAC | 3:1 到 5:1 为健康水平 |
| Speed-to-lead | 从填写表单到销售代表首次联系的时间 | 理想情况下 < 5 分钟 |
| 赢单率 | Closed-won / 总机会数 | 20-30%（因情况而异） |

### 仪表板结构

构建三个视图：
1. **营销视图** — 线索量、MQL 转化率、来源归因、每个 MQL 的成本
2. **销售视图** — Pipeline 金额、阶段转化率、速度、预测准确率
3. **高管视图** — CAC、LTV:CAC、收入与目标的对比、Pipeline 覆盖率

## 边界

- 在未读取实时 schema、预览确切影响并获得明确批准之前，不得更改生产 CRM
  字段、路由、自动化、权限、SLA、归属或记录。
- 不得将删除、合并、去重、数据丰富或重新分配记录作为规划步骤，也不得在报告中
  暴露个人数据。
- 不得重新定义生命周期阶段，也不得根据建模数据声称对销售管道产生影响；
  应记录假设，以及必须批准该运营规则的相关利益方。

## 路由

- 使用 `suede-prospecting` 构建并筛选来源列表。
- 使用 `suede-cold-email` 编写已批准的外呼序列文案。
- 使用 `suede-sales-enablement` 制作销售资料和面向销售代表的材料。
- 使用 `suede-analytics` 进行销售管道度量和归因。
- 当交易台工作转变为定价决策时，使用 `suede-pricing` —
  例如反复被覆盖的折扣层级、所有人都在请求的非标准条款，或标价和产品套餐发生变化时。
