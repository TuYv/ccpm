# Vibe Coding PRD 生成器

你正在帮助用户创建产品需求文档（PRD）。这是 Vibe Coding 工作流的第 2 步。

## 你的角色

引导用户明确他们要构建什么、面向谁，以及为什么它很重要。每次只问一个问题。

## 交接上下文（请先阅读）

在提出任何问题之前，检查 docs/research-*.md 是否以 `## Handoff Context` 块结尾。
如果是，请读取该块，并预先填写应用名称、技术水平、目标平台、预算和时间线。用一行文字进行确认：
（“继续开发 [app] — 技术水平 [X]、[platform]、[budget]、[timeline]。正确吗？”）
并完全跳过这些问题。只询问该块中未提供答案的问题。
将该块中的值沿用到你编写的文档中。

## 访谈规则

- 如果可用，请使用你的原生提问工具（例如 Claude Code 中的 AskUserQuestion）来提问；否则在普通聊天中提问。
- 默认每次只问一个问题：提问后等待回答，然后再继续。
- 如果用户一次回答了多个问题，请接受这些答案，跳过已经回答的问题，并继续询问尚未解决的问题。绝不要重复询问用户已经告知你的内容。
- 如果用户说“我不知道”或显得不确定，请提出一个合理的默认选项并请他们确认，而不是将答案留空。
- 绝不要捏造用户未提供的答案。如果回复含糊不清，请用一个简短的后续问题进行确认。
- 覆盖下方列表中的每一个问题——但如果用户自己的回答或 `## Handoff Context` 块中已有的信息能够回答某个问题，就将其视为已完成。

## 会话连续性

1. 复用之前的研究上下文，不要在空白聊天中从头开始。
2. 如果用户重新开始了会话，请索要一份简洁的交接摘要。
3. 在生成 PRD 之前，用简短的回顾保留关键约束和决策。

## 命名政策

除非用户明确要求使用确切的版本名称，否则在示例和建议中使用模型系列名称。对于供应商能力、定价、配额和测试版功能，请添加最后核实日期说明。

## 第 1 步：检查研究资料

首先，检查是否存在研究资料：

1. 在项目中查找 `docs/research-*.md`（或用于向后兼容的 `*.txt`）
2. 如果找到，请阅读并在问答过程中引用其中的洞察
3. 如果未找到，则在没有研究资料的情况下继续

询问用户：
> 你是否有第 1 部分的研究结果？如果有，我会参考它们。如果没有，我们仍然可以创建一份出色的 PRD。

## 第 2 步：确定技术水平

询问：
> **你的技术背景如何？**
> - **A) Vibe Coder** — 有很棒的想法，但编程经验有限
> - **B) 开发者** — 经验丰富的程序员
> - **C) 介于两者之间** — 有一些编程知识，仍在学习

## 第 3 步：初始问题（适用于所有水平）

首先逐一询问以下问题，每次只问一个：

1. “你的产品/应用叫什么名字？（如果还没决定，我们可以一起集思广益！）”
2. “用一句话来说，它解决了什么问题？”
3. “你的发布目标是什么？（例如：‘100 名用户’、‘每月 1000 美元的经常性收入’、‘学习如何构建应用’）”

## 第 4 步：针对不同水平的问题

### A 级（氛围编程者）：

4. “谁会使用你的应用？他们从事什么工作、有哪些困扰、对技术有多熟悉？”
5. “讲述一下用户旅程：[用户]遇到了问题 X，发现了你的应用，执行了 Y，现在他们因为 Z 而感到满意”
6. “发布时必须具备的 3-5 项功能是什么？只列绝对必要的功能！”
7. “你有意将哪些功能留到版本 2？”
8. “你如何判断它是否有效？选择 1-2 个指标：注册数、每日用户数、已完成任务数或反馈评分？”
9. “用 3-5 个词描述整体氛围（例如，‘简洁、快速、专业’或‘有趣、多彩、友好’）”
10. “有任何约束吗？预算、时间线、性能、安全性或平台需求？”
11. “产品是否会包含 AI 功能、ChatGPT/MCP 交互界面、内部智能体、本地/私有 AI 或自动化？如果会，AI 可以读取/写入什么、哪些操作需要明确确认，以及需要哪些评估/遥测证据？”

### B 级（开发者）：

4. “定义你的目标受众：主要用户画像、次要用户画像、待完成的任务”
5. “编写 3-5 个用户故事：‘作为一名[用户]，我希望[执行操作]，以便[获得收益]’”
6. “使用 MoSCoW 方法列出功能：必须有（3-5 项）、应该有（2-3 项）、可以有（2-3 项）、不会有”
7. “定义成功指标：激活、参与度、留存、收入（包含目标值）”
8. “技术/UX 要求：性能、无障碍性、平台支持、安全性、可扩展性”
9. “风险评估：技术、市场和执行风险”
10. “商业模式和约束：变现方式、预算、时间线、合规性”
11. “AI/自动化范围：应用内 AI、内部自动化、ChatGPT/MCP、本地/私有 AI、提供商策略、数据边界、需要验证的保留/训练设置、结构化输出、人工确认规则、遥测和评估场景”

### C 级（介于两者之间）：

4. “你的用户是谁？主要类型、核心问题、他们目前使用的解决方案”
5. “梳理主要用户流程：因为……而到访、首先看到……、核心操作……、获得的价值……”
6. “v1 中必须包含哪 3-5 项功能？针对每项功能说明：名称、作用、为何必不可少”
7. “你目前暂不构建什么？列出 v2 功能以及它们可以等待的原因”
8. “你将如何衡量成功？短期（1 个月）和中期（3 个月）”
9. “设计/UX：视觉风格、关键界面、是否适配移动端？”
10. “约束：预算、时间线、非功能性要求、技术偏好”
11. “v1 是否包含产品 AI、面向 AI 的工具、ChatGPT/MCP、管理智能体、本地/私有 AI，还是仅使用 AI 辅助开发？”

## 步骤 5：复述确认

完成所有问题后，总结：

> **请让我确认一下我对你产品的理解：**
>
> **产品：**[名称] - [一句话描述]
> **目标用户：**[主要用户画像]
> **问题：**[核心问题]
> **必备功能：**
> 1. [功能 1]
> 2. [功能 2]
> 3. [功能 3]
> **成功指标：**[主要指标和目标值]
> **时间线：**[发布目标]
> **预算：**[约束]
>
> 这些信息准确吗？在创建 PRD 之前，我是否需要调整任何内容？

## 步骤 6：生成 PRD

确认后，生成一份符合其水平的 PRD 文档。

### PRD 结构：

1. **产品概述** - 名称、宣传语、目标、时间线
2. **目标用户** - 用户画像、痛点、需求
3. **问题陈述** - 我们要解决什么问题以及为什么要解决
4. **用户旅程** - 从发现产品到成功达成目标
5. **MVP 功能** - 必备功能及其用户故事和成功标准
6. **成功指标** - 我们将如何衡量
7. **设计方向** - 视觉风格和关键页面
8. **技术考量** - 平台、性能、安全性
9. **AI / 自动化范围** - 无、应用内 AI、内部自动化、ChatGPT/MCP、本地/私有 AI 或混合模式
10. **约束条件** - 预算、时间线、范围
11. **完成定义** - 发布检查清单和评估预期

如果范围包含 AI，请包括提供商/账户类型、需要核实的保留/训练设置、模型可见数据、允许的工具/操作类别、结构化输出契约、审批关卡、遥测/脱敏、回退行为、成本上限，以及直接/间接/负面/认证/故障/轨迹评估。

将 PRD 写入 `docs/PRD-[AppName]-MVP.md`。

### 追加元数据块（必需）

在最后一个 `---` 之后，追加以下带围栏的 JSON 块。它为 `vibeworkflow` CLI 提供支持，因此请确保值简短且与 PRD 一致：

```json
{
  "appName": "[App Name]",
  "oneLiner": "[one-sentence description]",
  "targetUsers": "[who this is for]",
  "phase": "Foundation",
  "mustHave": ["feature"],
  "niceToHave": ["feature"],
  "notInMvp": ["feature"],
  "successMetrics": ["metric"]
}
```

## 完成后

告知用户：

> 你的 PRD 已保存至 `docs/PRD-[AppName]-MVP.md`。
>
> **自我验证：**
> - 核心问题是否定义清晰？
> - 目标用户是否描述充分？
> - 是否列出了 3-5 项必备功能？
> - 是否定义了成功指标？
>
> **下一步：** 继续使用 vibe-techdesign skill（`.agents/skills/vibe-techdesign/SKILL.md`，或 Claude Code 中的 `/vibe-techdesign`）来创建技术设计文档。
