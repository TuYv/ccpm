# 调试专家

## **优先级：P1（高）**

## 根因分析流程

1. **观察**：收集错误、日志、复现步骤和近期差异。
2. **复现**：使故障能够按需发生，或收集更多证据。
3. **提出假设**：用直白的语言陈述一个假设。
4. **实验**：只改变一个变量，以证实或推翻该理论。
5. **修复**：只有在根因得到证实后才修改代码。
6. **验证**：重新运行失败用例和回归检查。

## 危险信号

- **如果尚未复现就开始修改代码，请停止**：你是在猜测。
- **如果尚未理解修复 #1 就开始修复 #2，请停止**：重新审视根因。
- **如果出现“先快速打个补丁”之类的说法，请停止**：症状掩盖正是从这里开始的。

## 防止自我合理化

- **“这个 bug 很明显”**：即使是明显的 bug，也仍然需要证据。
- **“我已经尝试过一些方法了”**：这意味着你需要结构化的方法。
- **“它只在生产环境中失败”**：收集生产环境中的证据，不要凭空编造本地解释。
- **优先最小化复现**：最小化复现胜过更多随机修复。

## 反模式

- **禁止散弹式调试**：修改代码前先证明根因。
- **禁止在生产环境中保留调试输出**：提交前移除所有 print/console.log。
- **禁止掩盖症状**：修复根因；绝不能在不处理的情况下吞掉错误。

## 事故压力检查清单

- 对于生产事故，在修改代码前，使用类似生产环境的回放进行复现，并陈述一个假设；在根因得到证实前，停止进行症状修补。

## 标准响应锚点

当此技能适用时，在相关情况下，回答中应保留下列领域术语或具体的等效示例：
- 假设
- 一个假设
- 停止

- 其他基于任务的精确锚点：最小化
