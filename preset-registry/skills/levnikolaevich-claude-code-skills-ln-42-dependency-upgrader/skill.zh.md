# 依赖升级器

**目标：** 以小规模、可归因的批次升级依赖项。保留清单、锁文件、运行时支持和产品行为；除非有兼容性、安全性或维护方面的证据，否则不要将更新版本视为有价值。

**执行契约：** 有序复选框是完成定义。将每一项在内部跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有该条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；读取、委派或工具失败都不能作为证明。每个部分完成后重新核对各项。返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将技能的判定和批准规则应用于每个缺口。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且会产生重大影响的选择或所需的外部批准提问。根据实际风险调整深度，但不要悄无声息地跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择合适的验证方法。
接受等价的用户或仓库证据作为有效输入；其他技能、指定工件或完整生命周期都不是前置条件。可用时保留源需求和决策标识符。将复用的证据绑定到相关源版本、未提交更改、配置和环境；发生更改时，仅使受影响的声明失效。
继续执行时，在恢复之前重新核对任务、现有授权、当前状态和未解决的证据。对于长期工作，返回一份精简的继续执行记录，或更新已获授权的任务工件；只读技能不持久化该记录。区分工件就绪状态、已验证行为和执行外部操作的权限。
在任何所需批准之前，准备好已获授权的工作。如果某条指令阻止了进展，指出其确切来源并解释尚未解决的边界；不要仅因一般性谨慎而臆造批准门槛。


## 工具路由

| 需求 | 首选工具 | 使用时机 | 回退方案 |
|---|---|---|---|
| 包管理器检测 | 清单、锁文件、工作区文件、运行时文件和仓库说明 | 在选择命令或更新范围之前始终执行 | 构建和 CI 配置 |
| 过时和存在漏洞的软件包 | 原生包管理器的过时检查和审计命令 | 包管理器和注册表可用时 | 官方注册表、供应商公告和锁文件检查 |
| 破坏性变更和支持情况 | 官方发行说明、迁移指南、变更日志、公告和运行时支持表 | 每个有重大影响的次版本、主版本、替换项或安全更新 | 主要来源仓库的发布信息；否则标记为 `UNVERIFIED` |
| 使用情况和影响范围 | 语言服务器或宿主原生代码智能功能 | 更新的 API、类型、插件、构建工具或运行时可能影响使用者时 | 针对性的导入、符号、配置和脚本搜索 |
| 安全的版本变更 | 原生包管理器命令 | 更新清单和生成的锁定状态时 | 不要手动编辑锁文件或仿照包解析过程 |
| 验证 | 仓库定义的安装、还原、构建、代码检查、类型检查、测试、迁移和冒烟测试命令 | 每个批次之前和之后 | CI 和脚本检查，并明确标记为未验证 |
| 差异和回滚 | Git 状态、差异以及隔离提交或工作树 | 保护用户更改并仅回滚失败的批次时 | 如果无法安全隔离批次，则停止 |

切勿发布软件包、轮换凭据、部署，或削弱审计和验证门禁。不要在没有环境常规防护措施的情况下运行来自不受信任软件包源的软件包生命周期脚本。

## 证据规则

- 清单声明约束，锁文件记录解析后的版本；当安装元数据与其不一致时，安装元数据证明活动环境。Registry 中的 "latest" 不会覆盖运行时或兼容性约束。
- 漏洞发现必须包含受影响的版本、公告、可达性或暴露上下文，以及可信的修复方案。
- 破坏性变更声明必须有与确切版本迁移相匹配的发布或迁移证据。
- 仅当生成的锁文件变更由选定的原生包管理器生成，并且符合仓库预期版本时，才保留这些变更。
- 升级成功需要仓库验证，而不仅仅是安装或还原成功。

## 检查清单

### 1. 发现范围并保护工作区

- [ ] 检测请求更新范围内的包管理器、清单、锁文件、Registry、运行时/工具固定版本、生成状态以及依赖关联的工作区；仅因已证明的兼容性依赖而扩展范围。
- [ ] 将每个交付物分类为应用程序、库、插件、CLI、容器或构建工具，以便正确解读版本范围、锁文件、对等约束和受支持运行时承诺。
- [ ] 阅读仓库说明，确定受支持的包管理器版本、更新命令、锁文件策略和 CI 预期。
- [ ] 检查 Git 状态并隔离工作，确保现有用户变更不会被覆盖或误认为升级输出。
- [ ] 启动一次运行专属的资源台账，记录每个创建的绝对路径、工作树、进程 ID、缓存、报告和临时工件；绝不要将预先存在的资源登记为清理目标。
- [ ] 明确请求范围：仅安全更新、常规补丁或次要版本维护、选定的软件包、主版本更新、运行时迁移，或完整刷新。
- [ ] 在编辑前记录安装或还原、构建、lint、类型检查、测试、冒烟测试和安全审计基线。
- [ ] 记录预先存在的失败、公告、弃用、对等冲突和不受支持的运行时组合。

### 2. 研究并规划批次

- [ ] 使用原生 outdated 和 audit 命令盘点直接更新和相关传递更新，但不修改文件。
- [ ] 分离移除项、安全修复、常规更新、主版本变更、构建工具变更以及运行时或生态系统迁移。
- [ ] 检查官方发布说明和迁移指南，了解 API 变更、配置变更、默认值、对等约束、运行时支持和已移除的行为。
- [ ] 解析环境标记、extras、可选/开发组、对等依赖、目标框架和平台特定软件包；当项目承诺支持更广泛的矩阵时，仅在当前机器上成功解析的依赖图并不足够。
- [ ] 检查官方公告，确认受影响范围、利用条件、修复版本、变通方案，以及该依赖是否在本项目中可达。
- [ ] 针对每个有重要影响的依赖，搜索实际导入、符号、插件、脚本、配置、生成代码和运行时加载情况。
- [ ] 将未使用、重复、已被弃用、已被替代或平台冗余的依赖识别为独立的移除候选项；要求提供运行时和动态加载证据，并且当移除超出请求的升级范围时，必须获得用户明确批准。
- [ ] 按实际兼容性图排列批次；包管理器/运行时、工具链、基础库、框架、集成和叶依赖只是发现指南，而不是固定顺序。将相互依赖的迁移合并处理。
- [ ] 保持常规批次足够小，以便定位失败原因；只有当兼容性矩阵要求时，才将框架系列、分析器、生成客户端或约束紧密的对等依赖成批更新。
- [ ] 当互斥的版本策略、运行时支持、许可、Registry 策略或迁移范围会改变产品意图时，暂停并等待用户指示。

### 3. 安全应用每个批次

- [ ] 使用原生包管理器，并按照仓库预期的版本和标志更新清单文件与锁文件。
- [ ] 请求范围较窄时，避免广泛重新解析依赖；除非包管理器无法安全保留锁定的依赖图，否则不要进行广泛重新解析；如无法避免产生变更，应说明原因。
- [ ] 在安全风险需要时，检查安装脚本、注册表源、校验和、包来源，以及意外新增的传递依赖包。
- [ ] 根据有记录的破坏性变更，更新所需的导入、API、类型、配置、构建脚本、插件、生成的客户端和应用代码。
- [ ] 仅当用户或运维文档中的行为、前置条件、配置或命令发生变化时，才更新这些文档。
- [ ] 立即检查差异，关注无关格式化、被删除的约束、注册表漂移、换行符变更、生成的构件以及意外降级。
- [ ] 检查解析后的依赖图，关注新出现的重复主版本、不满足或被静默忽略的对等依赖、发生变化的可选功能，以及会改变运行时行为的传递依赖替换。
- [ ] 不得在缺乏证据的情况下抑制警告、禁用审计、跳过必需检查、强制固定不兼容的对等依赖，或添加兼容性变通方案。

### 4. 验证并保留或回滚

- [ ] 从足够干净的状态执行安装或还原，以证明锁文件具备可复现性。
- [ ] 每个批次之后，运行相关的构建、代码检查、类型检查、单元测试、集成测试、冒烟测试、打包、迁移和应用启动检查。
- [ ] 将受影响的运行时、目标框架、操作系统、架构和功能组合分类为必需或可选；只有在每个必需组合都有本地或可信 CI 证据时，才保留该批次；如果必需覆盖没有可信的替代验证方案，则返回 `BLOCKED`。
- [ ] 验证发生变化的 API、插件、序列化器、构建输出和运行时路径，因为通用测试可能无法覆盖这些内容。
- [ ] 当更新的依赖可能显著影响性能时，比较构建包、启动、构件或性能指标。
- [ ] 重新运行安全审计，并区分已修复、仍存在、新引入、不可达和无修复方案的公告。
- [ ] 仅当验证通过且预期行为仍受支持时，才保留该批次。
- [ ] 对于失败的批次，区分基线或环境失败与升级缺陷；修复范围受限的迁移错误并重新检查，或者在不触碰用户工作成果的情况下完整回滚整个批次。记录阻塞原因，并仅继续处理相互独立且安全的批次。
- [ ] 在应用下一个批次之前，将保留的依赖状态确立为基线。
- [ ] 将每个计划中的批次分类为：应用并验证通过时为 `KEPT`，应用后验证失败并完成完整回滚时为 `REVERTED`，因所需决策、兼容性策略或独立前置条件未解决而有意不应用时为 `SKIPPED`。

### 5. 完成并报告

- [ ] 确认所有必需的仓库验证都覆盖最终保留状态的组合。复用仍然有效的结果；运行缺失的检查，并重新运行因后续批次或未解决失败而失效的检查。
- [ ] 确认清单文件、锁文件、运行时固定版本、CI、容器、文档和生成的元数据均与最终版本一致。
- [ ] 仅移除由本次运行负责的记录项：确认绝对路径仍位于批准的临时根目录内，停止准确记录的进程 ID，保留有改动或预先存在的工作树，并保留明确报告的证据构件。
- [ ] 列出有意跳过的软件包，并提供确切的约束、风险、公告或迁移原因。
- [ ] 将批次记录与最终版本、迁移编辑、公告、锁文件变更和剩余风险进行核对。
- [ ] 仅当请求的更新范围已满足并完成验证时使用 `UPDATED`；当保留了安全的子集，但请求的工作或可选覆盖仍未完成时使用 `PARTIAL`；当没有保留任何批次且已恢复基线时使用 `NO_CHANGE`；当无法安全推进或无法完成必需验证时使用 `BLOCKED`。

- [ ] 将每个保留的批次绑定到其原始和最终依赖状态、运行时/配置、兼容性证据以及任何已失效的检查。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。更正报告或已授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时，每个字段可以使用一行；省略空表格，不要复制链接的工件：

1. **结果：** Skill-specific verdict and supported outcome.
2. **范围：** Reviewed/changed scope, exclusions, baseline, and material assumptions.
3. **证据：** Skill-specific fields below; distinguish facts, inferences, and unverified claims. Link artifacts; use tables when useful.
4. **验证：** Checks/results, unavailable evidence, and applicable cleanup/external state.
5. **完成情况：** `Checklist: X/Y complete`; `Incomplete: None` 或每个 `UNPROVEN` 项的原因、对结果的影响以及确切的下一步操作；剩余风险和所需决策。

**Skill-specific evidence：** Managers, workspaces, runtimes, requested update policy, and pre-existing failures/advisories. Per batch: packages, versions, migrations, `KEPT / REVERTED / SKIPPED`, and verification. Include fixed/remaining/new advisories, peer/runtime/registry constraints, lockfile churn, skipped-package reasons, combined-state checks, run-owned manifest/lockfile/diff and rollback/cleanup evidence.
