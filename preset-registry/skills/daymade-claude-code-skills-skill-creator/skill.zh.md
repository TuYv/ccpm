# Skill 创建器

用于创建新 skill 并进行迭代改进的 skill。

从高层次来看，创建 skill 的流程如下：

- 确定你希望 skill 完成什么任务，以及大致应如何完成
- 将变更归类到能够证伪其可能失败模式的最低验证层级
- 编写 skill 草稿
- 在该层级进行验证：对于边界明确的修复执行针对性检查；对于不确定的指令变更执行采样行为重放；对于全新、高风险或范围广泛的工作执行完整的配对评估流程
- 当所选层级产生定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写 skill（如果定量基准测试暴露出明显缺陷，也要据此重写）
- 持续重复，直到你对结果满意
- 只有当当前证据无法解释变更后的行为时，才提升验证层级

使用此 skill 时，你的任务是判断用户目前处于这一流程的哪个阶段，然后介入并帮助其推进适用的阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须承担的负担。对于正确性可以直接测试的边界修复，不要创建评估文件、派发成对代理、评定输出或启动查看器。

整个过程中都必须遵守以下六项原则，因为这些失败模式会让人发布看起来令人信服、实际却错误的 skill：

1. **写作前先验证。** 每一条进入 skill 的技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的事实——无论是在本次会话中，还是在经过明确批准的挖掘会话中。如果目前无法验证，要么立即验证，要么明确标注（“未经验证——来自记忆”）。skill 会放大其中包含的一切：经验证的知识会不断积累，带有自信表述的错误也同样会不断积累。对于知识型 skill（内容主要是关于外部系统的事实，例如 API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作版本：权威性阶梯（观察到的行为 > 机器可读的契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例的冒烟运行，以及受众和 Windows 可移植性检查清单。一次源依据审计发现，多个自信的契约声明与作者已经掌握的证据相矛盾（方法论案例 9）。
2. **将“不可能/不支持”视为假设，而不是结论。** 当某项能力看似受阻时（API 错误壁垒、工具无法连接、格式无法打开），在将“平台不支持此功能”写入 skill 之前，要穷尽各种观察路径——UI 自身的网络流量、其他通道、不同的文档化标识符。观察到的行为优先于推测性的请求形式。
3. **站在该领域已有最佳实践的肩膀上——默认情况下，在编写或优化 skill 的方法论之前，将该领域已确立的最佳实践检索到上下文中。** skill 的方法论质量，取决于上下文窗口中的知识，而不是模型权重中潜在的知识：预训练知识是不完整的，会过时，而且除非实际拉取规范来源，否则通常根本不会被激活。因此，你所写内容的质量上限是 `你的训练数据 + 用户输入`——*除非*你有意识地检索该主题领域真正已有的成果。请这样做：通过 WebSearch 搜索该领域的经典理论/标准/方法，并阅读该领域中随附或已安装的 skill，然后将其中承载关键作用的原则连同出处整合进 skill。**这与下面的“既有成果研究”是不同的维度**——后者寻找可复用的工具/基础设施；这里则是让方法论本身建立在该学科积累的科学成果之上。将其作为**默认操作，而不是等待用户要求**：简要告知用户你将参考哪个领域的成果，让用户可以说“跳过”，但绝不要在距离公共领域已有 40 年成果仅需一次搜索的情况下，仍让方法论受限于你的记忆和用户的提示。例如：数据可视化 skill 必须吸收 Cleveland 与 McGill 的图形感知排序以及 Bertin 的视觉变量理论（位置/长度优于颜色，颜色优于文本——这是经过测量的事实，而非审美判断）；日期/时间 skill 必须指出成熟的库及其经典陷阱；说服/谈判 skill 必须检索已有的成熟框架，而不是凭记忆重新发明。如果经典知识只存在于你的权重中，却从未进入上下文，那么你就是在本可引用的地方进行猜测。
4. **压缩现有 skill 之前先保留它。** 更新现有 skill 是一次迁移，而不是从空白页面开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧版 bundle，或从明确的 Git ref 重建它；任意复制加上来源标签不能算作基线。盘点运行时能力、触发上下文、接口、引用资料和评估覆盖范围。渐进式披露和简洁性允许你移动或去重内容；但不允许你悄悄删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每一个无法匹配的旧单元进行分类。一个仅存在于 `evals/`、测试或未链接引用中的运行时契约，仍然属于丢失。只要仍有候选项未分类，或仍有真正的缺口未修复，就不要称更新已完成。同样的逻辑不仅适用于删除，也适用于**逆转**，并且涵盖任何先前作出的承诺——不只是带有日期和名称的承诺：**推翻已经作出的决定必须是一项提案，绝不能成为副作用。** 要明确说出来并获得接受。悄无声息的重写比悄无声息的删除更糟，因为它会一次性摧毁产物和本可发现问题的证据——也会蒙蔽所有下游审阅者（见 #5）。

5. **仅靠自审不会交付任何成果——独立、基于全新上下文的对抗性审查是固定步骤，而不是特殊情况。** 你“现在已经没问题了”的判断，运行在生成该产物的同一个模型上，因此它也共享造成缺陷的那些盲点。事实有测量依据，而非民间经验：没有外部反馈的内在自我纠正并不能可靠地改善输出，有时还会使其恶化（Huang 等，ICLR 2024）；当生成器和评估器共享错误模式时，反复迭代会**提升信心，却不会增加信息**。更多自检无法逃离这一点；只有外部视角才能做到。**完整流程——包括提示词模板、锚点选择、发现项表格和案例演示——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在首次审查前先阅读它。** 承重规则如下：
   - **独立性有两个层面，而第二个正是作者容易忽略的层面。** *审查者的上下文*不能是你的分支——分支会继承你的盲点，并交回一张“已审查”印章。但它所依据的*证据*也必须位于变更的**影响范围之外**，否则它会继承你的**结论**：它读取一个产物和一份已经与之达成一致的规范，然后报告二者一致。注意，“本次会话中未编辑”这一界线太弱——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，而三名审查者对一个他们在其未改动副本中发现过的缺陷都视而不见。应根据锚点被你触碰的难易程度进行排序：用户自己的原话 > 早于本次工作的 git 引用（`git log --oneline <ref>..HEAD -- <path>`；任何你的提交都会使其失效）> 仅追加日志（这是一种约定，而不是强制机制）。**全新项目没有锚点——请说明这一点并索要一个锚点，而不是报告一个你并未执行的通过结果。**
   - **只给它两样东西：产物，以及读者规范。** 不要给其他任何内容——不要提供设计理由、项目背景，也不要说“只需确认 X 没问题”，因为这会把独立审查者变成橡皮图章。读者规范是*规范*，而不是理由，因此它不能替任何内容盖章；省略它会浪费一半审查，因为审查者随后只能拿自己作为衡量标准。**对于 SKILL.md，读者是另一个执行它的智能体**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——请询问哪些指令是它无法执行的。在运行前陈述规范，之后绝不要用它来为发现项辩解。
   - **对于可理解性，以及针对语料库的完整性，它是真实依据；对于品味，它没有裁决权。** 直接应用前两项。把“这可能是一个 bug / 我建议使用 Y”视为假设，并先自行复现。绝不要委托 AI 垃圾内容或审美判断——同一个模型存在盲点。
   - **枚举失败的*轴*，而不是内容领域——这也决定你要运行多少名审查者。** 轴是*你提出的问题*；领域是*你阅读的材料*。三名审查者分别覆盖场景、算术和 diff，但都在问“这是否连贯”，那只是把同一名审查者计费了三次。**一名是默认配置，而且通常已经足够**；只有在增加一个额外轴时才增加一名。自审最不擅长的轴是**保真度**——“这是否仍然忠实于已经作出的承诺？”——因为正是作者移动了那项承诺，而连贯性和保真度是正交的：一个产物可以在自洽性上无可挑剔，却完全不忠实于已经决定的内容。
   - **留下一个产物，否则这只是一条警告。** 规范 #6 规定，产生意见的检查不如产生产物的检查——因此这一项也必须生成一个文件，否则它会在最关键的时候输给完成驱动力。请在你的私有、受 git 跟踪的知识库中的 `skill-reviews/<skill-name>/` 下写入 `independent-review.md`：其中必须包含**逐字记录的审查者提示词**（这样后来的读者才能看出提示词是否带有引导性）、**每项发现及其处置和理由**（这正是合法筛选与丢弃不利内容之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识库（或者你没有私有知识库），请说明并询问用户——不要猜一个位置，导致文件落入两个禁区之一。两个禁区位置：**不得放在 `<skill-name>-workspace/` 中**（这些被 git 忽略的临时目录会被清除——该文件是跨会话的审查证据，必须保留）；**不得放在任何已经公开或可能公开、分发的仓库中**——这通常意味着不能放在被审查技能自己的仓库中（审查内容必然会引用私有路径、真实姓名和项目细节）。进行实质性编辑后，应使用一个*新的*智能体重新审查——也就是规则、契约或数字发生了变化，而不是拼写错误。**从步骤 5 开始，这个文件就是审查已发生的证据；它不存在，就意味着审查没有发生。****写入文件不等于它在下个会话中仍然存在——必须在同一轮中对该私有仓库执行 `git add` + `git commit`。** 一个留在 git 工作目录中的未提交文件，不具备该规则所要求的任何“受 git 跟踪”保证：它可能丢失、被覆盖，或者根本不会被之后检查“是否已审查”的流程获取（真实案例：文件已正确写入正确路径，也包含真实发现项——但由于从未提交，仍未通过后续的自动检查；修复方式是执行一次 `git commit`，而不是迁移文件）。
   - 规范 #4 的回归门禁是机械性的，并且与此互补：它证明你没有*删除*行为。但它无法说明你写下的内容是否真的能够被遵循。

6. **设计检查时，确保它们无法自我认证为通过。** Skill 主要由各种检查组成——门禁、检查清单、“发布前”步骤——而如果执行上下文在*违反检查所编码的规则本身*的情况下仍能通过该检查，那么这种检查比没有检查更糟糕，因为它会制造虚假的信心。以下四条规则借鉴自那些早于软件行业解决过这一问题的领域：
   - **验证必须覆盖规则的每一条条款。** 如果规则写的是“A + B + C”，证据就必须分别要求证明 A、B *和* C。把一行确认信息附加到包含三个条款的规则上，最终只会被作者已经完成的那个条款满足；其他条款则完全不可见。真实案例：一个报告编写 skill 包含一道交付门禁，其规则写着“选项以并排 chips 呈现 + 推荐项突出显示 + **背景信息必须写成完整、自洽、陌生人也能理解的句子**”——但下面的证据行只要求“N 个决策项，全部以 chips 呈现”。作者运行门禁，填写了该证据，自我认证为通过，然后交付了一个标签只有单个字符、所有上下文都被删掉的页面。规则从始至终都写在文件里；只是检查根本没有衡量那一条款。
   - **在健康输入上误报的检查，比没有检查更糟糕。** 上面的失败是检查在应该失败时通过；这里则是它的镜像——检查在应该通过时失败。这种情况代价更高，因为它会教会操作者条件反射式地绕过检查（`--no-verify`、`SKIP=1`、`--force`），而一旦形成这种反射，门禁就会对*所有*输入关闭，包括它原本就是为之构建的那些输入。因此，在编写默认拒绝的检查时，**假阳性的重要性高于假阴性**：漏掉一个真实问题，只会损失这一个实例；而误杀一个健康输入，则会让整个门禁失效。
     留意这个信号：**反复踩中同一个陷阱所产生的挫败感，本身就是风险信号**——作者正是在这种状态下，最容易发布一个从未针对健康输入校准过的防御措施。真实案例：一天之内连续三次踩到同一个格式陷阱后，作者给 linter 加入了一条 regex 检查；它在项目自己的语料库上误杀了 **33 个健康输入**，并于同一小时内被回滚。启用之前先进行校准——让任何默认拒绝的检查运行在真实且已知良好的材料上，并确认假阳性为零；宁可放宽检查，让它偶尔漏掉问题，也不要让它有任何误报。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是自洽完整的”无法被撰写它的人判定为失败；而“覆盖页面的其余部分，单独阅读一张卡片，并说明它正在做什么决策”则可以。优先选择能够产生工件的检查——例如命令的输出、引用的行、截图——而不是只能产生观点的检查。
   - **同样的怀疑也适用于你运行的检查，而不仅是你编写的检查。** 上述四条规则约束的是随 skill 一起交付的检查。但你用来验证**自己**工作的 greps、finds 和一次性脚本同样是工具；错误的工具会像正确的工具一样，自信地报告干净结果。在一次 2026-07 的会话中，五条相互独立的验证命令在两个方向上都给出了谎言：没有使用 `-L` 的 `find` 报告某个已安装 skill 的文件缺失（这些文件实际位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了正在审计的对象的另一个副本；反转的 shell 条件错误地发出警报，称某项删除没有发生；跨越换行符的 regex 臆造出 55 个“丢失的引文”；而对五个文件中的两个进行搜索，却报告有两条规则缺失，实际上它们存在于第三个文件中。**这些结果一开始无一例外都被相信了，最终也无一例外都是通过重新运行形状不同的检查才被发现的。**

解决办法是实验实践中最古老的一种：**在把仪器用于你不知道答案的案例之前，先用一个答案已知的案例运行它。** 如果你要搜索一个预计不存在的字符串，先用同样的命令形式搜索一个你确定存在的字符串——如果这个搜索也返回 0，那么出问题的是命令，而不是文件。只需增加一行，就能把“我检查过了”变成“我用校准过的仪器检查过了”。

有两种具体形式值得记住，因为上文都出现过，而且两者都会*静默失败*：`find` 未加 `-L` 时不会跟随符号链接（而 skill 的安装经常是指向源代码仓库的符号链接），`--exclude-dir` 则会在整个目录树中按 basename 匹配，而不只是匹配你脑中设想的那个路径。

**这条规则还有另一半，只有当检查项要随文档发布时才会真正造成影响：要以*标准*实现为基准校准，而不是以你机器上的实现为基准。** 上面的仪器规则确保*你的*结论诚实可靠；这一半则确保*读者*的操作能够正常工作。写入 skill 的工具行为声明——某个标志、递归模式、一个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而差异会在两端都静默发生：它在你测试时有效，却在读者那里悄悄什么也不做。有两种机制会导致这种情况，而且从会话内部都无法看出来：**同一个命令名解析到不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能绕过*别名*，因此 `command tool` 或绝对路径才是唯一确定的形式），以及**同一个程序在不同实现之间行为不同**（BSD 与 GNU，或可替换实现之间）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，将其作为解决符号链接陷阱的方法写入 skill，并发布到了一个拥有 1200 颗星的公开仓库——他们使用的 `grep` 实际上是由 shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 中，同样的 `-R` 什么也匹配不到（它需要 `-RS`），因此这条规定的修复方法对大多数读者都静默失败了，恰恰发生在那个警告验证器会静默失败的章节中。

所以：**在工具行为断言进入已发布的产物之前，要用标准二进制重新运行验证**（`/usr/bin/<tool>`），而不是使用 shell 提供给你的那个版本。如果它无法通过验证，就不要写入这个标志——**优先采用与实现无关的表述**：自行解析路径（`readlink -f`），而不是押注某个递归标志；在脚本中执行子字符串测试，而不是进行面向行的匹配；描述你需要的*行为*，而不是你碰巧熟悉的选项。只在你的环境中有效的规定比没有规定更糟，因为读者没有办法发现它只是静默地什么也没做。

   - **采用成熟的清单实践已经确定的做法。** 判断一个列表属于 **READ-DO**（边读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭专业经验完成工作，然后在预先定义的**暂停点**停下来确认——适用于时间紧迫时的有经验操作者），并将其锚定在真实的暂停点上，而不是“工作流程中的某个位置”。只保留**关键项目**——既关键，*又*容易在压力下遗漏，大约五到九项；再多就会稀释遵从度（[Gawande，《清单革命》](https://www.shortform.com/blog/types-of-checklists/)）。并且优先采用 Shingo 所说的**控制**而非**警告**（[防错法](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，并且会输给完成任务的驱动力；而阻止进展或强制生成某种产物的步骤则不需要任何警觉性。在 skill 只能发出警告的地方，至少要把警告放在做出决策的位置——**写在执行上下文永远不会打开的参考资料中的规则，在实践中就不算规则。**

另一方面，也许他们已经有了该 skill 的草稿。在这种情况下，你可以直接进入这个循环中的评估/迭代部分。

当然，你始终应该保持灵活。如果用户说“我不需要运行一堆评估，只要和我一起凭感觉来就行”，那你也可以照做。

然后，在 skill 完成之后（不过再强调一次，顺序可以灵活调整），你还可以运行 skill 描述改进器。我们为此提供了一个完全独立的脚本，用于优化 skill 的触发效果。

## 首先：共存检查（官方 skill-creator 插件）

在执行任何操作之前，先快速检查一次（在常见路径下无需输出任何内容）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 什么都不做——不要安装任何东西，也不要向用户提及本节内容。继续进行当前任务。
- **存在：** 官方插件中的 skill-creator 与此版本现在会以几乎相同的描述出现在 skill 列表中，因此后续会话将在两者之间随机路由。用一两句话告知用户这一点，然后提供以下选项（未经用户同意绝不要自行执行）：
  1. **推荐** — 运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的自检 SessionStart hook 复制到用户的 Claude 配置中，并将其注册到 `settings.json`（同时创建备份），这样每个未来会话都会确定性地将 skill 相关工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 恢复；在按名称明确要求使用官方插件时，官方插件仍然完全可用。在没有官方插件的机器上，安装程序会拒绝安装任何内容，因此不会遗留无用的 hook。
  2. 备选方案 — `claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），这样会将官方条目完全移出 skill 列表，从而消除歧义。

如果 hook 已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有步骤。

同样的机制也适用于用户创建的 skill：当他们的 skill 有意与某个已安装的 skill 重叠时，使用 `scripts/generate_supersede_kit.py` 为其生成一套工具包——参见先例研究下的“共存与优先级”，以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

### 使用 AskUserQuestion（重要——请阅读）

**在每个决策点都积极使用 AskUserQuestion 工具。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最大用户体验改进——用户可能同时处理多个窗口，或者已经 20 分钟没有查看这段对话。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明 skill 名称、当前阶段，以及刚刚发生了什么（1-2 句话）。用户可能已经切换去处理其他事情。
2. **简化说明**：用通俗语言解释这个决策。不使用函数名或内部术语。说明它会做什么，而不是它叫什么。
3. **给出建议**：先给出你的建议，并用一句话说明原因。如果选项涉及工作量，同时展示两种时间尺度：`(人类：约 X 分钟 / Claude：约 Y 分钟)`。
4. **列出选项**：提供 2-4 个具体的、带字母标记的选项。每个选项都应是明确的行动，而不是抽象概念。

**规则：**
- 每个问题只涉及一个决策——绝不要把无关的选择合并在一起
- 提供退出选项（AskUserQuestion 始终隐含 “Other”）
- 接受用户的选择——可以提醒权衡，但绝不能拒绝继续执行
- 如果存在没有权衡的明显答案，则跳过提问（直接说明你将如何处理）
- **如果问题超时且没有得到回答（用户暂时不在键盘前），既不要停滞，也不要擅自推进涉及偏好或范围的决策。** 先完成无副作用的准备工作——编辑前快照、清单盘点、评估用例收集、只读审计/健康检查——并等待用户回来后再处理判断性决策（重组方向、删除内容、是否继续）。然后明确说明你完成了哪些工作，以及哪些事项仍在等待用户决定。

## 创建 skill

### 了解意图

先了解用户的意图。当前对话中可能已经包含了用户希望记录下来的工作流（例如，他们说“把这个变成一个 skill”）。如果是这样，先从对话历史中提取答案——使用过的工具、步骤顺序、用户做出的修正、观察到的输入/输出格式。用户可能需要补充缺失信息，并应在进入下一步前进行确认。

**来源清单——起草前始终执行，并明确同意边界。** 盘点当前对话，以及存在重叠内容的现有文档/skills（参见下方的先例研究）。较早的本地会话 JSONL 文件属于独立的私有来源：除非用户明确要求挖掘历史，或在你解释将读取哪些内容后明确批准该来源，否则不要打开或解析这些文件。如果获得批准，只能通过对话挖掘工作流中的脱敏提取来纳入相关的过往会话；绝不要将原始转录加载到你自己的上下文中。如果未获批准，则继续使用当前对话和现有项目来源，不要将缺少历史记录视为阻碍。

在挖掘对话（或会话转录）时，盘点**两类资产——它们应放在不同位置**。*知识*——端点、参数、陷阱、决策规则——应成为 SKILL.md 指南或 `references/` 内容。*会话中必须编写的代码*——辅助脚本、注入片段、渲染器、一次性模板——则是 `scripts/` 的候选内容：如果本次会话编写了它，下次调用时就必须重新编写，因此应将其参数化、进行清理，并打包进来。之前的一次提炼得到了经过润色的正文，却遗漏了可复用的辅助工具；总体经验是，要同时关注知识→references 和代码→scripts 两条路径。

当源材料是*过去的*会话记录（Claude Code projects directory 下的 JSONL 文件），而不是当前的实时对话时，不要将其加载到你自己的上下文中 —— 大型会话记录可能耗尽窗口，导致会话丢失。应改为委派子代理来提取信息，并明确要求它们使用脚本逐行解析、截断每个提取字段，且只返回提炼后的经验列表 —— 原始会话记录绝不能进入主上下文。

**首先，在下面四个问题之前，先确定这是哪个方向。** 请求可能属于几种*相反的*情况：构建一个全新的 skill / 编辑一个已有的 skill / 优化 skill-creator 本身 / 或者根本不是 skill，而是一次性任务。猜错方向会浪费整个会话 —— 你为“新建 skill”所做的研究，对于“优化元工具”来说完全是错误的研究。当措辞含糊时（例如，用户说“帮我做一个 skill”，但指向的是 skill-creator 自身的路径），在这里问一个 AskUserQuestion 只需 30 秒。下面的 wrapper-skill 分支是一个特殊情况，但方向检查本身是通用的。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在什么时候触发？（哪些用户表述/上下文）
3. 预期的输出格式是什么？
4. 是否应该设置测试用例来验证这个 skill 是否有效？具有客观可验证输出的 skill（文件转换、数据提取、代码生成、固定的工作流步骤）适合设置测试用例。具有主观输出的 skill（写作风格、艺术、经过品味校准的报告）通常无法使用断言 —— 但“没有断言”不等于“不验证”。它们的验证路径按成本排序如下：
   - **历史任务回放**：重新运行一个 skill 过去处理过的真实提示词，分别使用旧版和新版 skill，然后根据具体变更的规则比较输出（“新版输出是否确实遵循了这次更新引入的 tokens / 标题语法？”）。成本低，还能捕捉到“规则写进去了，但没有任何内容读取它”。
   - **以生产使用作为评估**：承认真正的测试是用户下一次实际使用 —— 然后明确建立反馈闭环：之后用户提出的每一次更正，都是需要纳入 skill 自身“迭代/活文档”部分的事件；每一次批准，都是语料库材料。一个发布时没有这种回写习惯的品味型 skill 不会进步；而包含这种机制的 skill 无需正式评估就能逐步收敛。**此外，当 skill 的输出是一个会持续运行的东西 —— 守护程序、监控器、定时任务、钩子 —— 它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户更正需要用户注意到问题并愿意反馈；而已部署的机制会自行报告问题，往往一天之内就会发生。误报是这种报告最直接的形式，因为它证明你写下的某条规则是错误的，而这是反复阅读也无法暴露的问题。应把第一次误报视为一次已安排的评估结果，而不是烦恼：在认定机制行为异常之前先检查它，因为更可能发现的是，*指令*写得过于绝对。（真实案例：某个 skill 规定了一项遇到失败就立即报错的检查，已部署的检查在一夜之间对一个完全健康的条件触发了一次，最终修复的是 skill 中那句过于绝对的表述 —— 没有人提出抱怨；是遥测数据发现了问题。）
   - 对于视觉输出，使用**渲染 + 人工审查**（skill 自身的视觉 QA 门禁），绝不要用一个假装能够衡量美观性的 grep 断言。**而且，用于验证的渲染器必须与交付物实际使用时的渲染引擎相同** —— 无论哪个预览器恰好已安装，都不能替代目标引擎。布局引擎不同于目标应用的缩略图生成器，可能会静默地*隐藏*你要查找的缺陷；在错误引擎上得到绿色验证，比完全不验证更糟糕，因为它会制造虚假的信心。真实案例（2026-07）：一个 .docx 通过 macOS Quick Look 缩略图进行了“视觉验证”，但 Quick Look 不会重现两端对齐文本的拉伸效果；用户打开文档后，Word 立刻显示信息块被严重拉开。修复方法是安装兼容 Word 的引擎（LibreOffice），转换为 PDF，逐页栅格化，然后逐页阅读。引擎必须匹配，否则验证就是走过场。**这也适用于渲染器之外的所有验证工具** —— 解析器、linter、validator：它们必须与生产环境共享实现，否则它们的绿色结果毫无意义。另一个同类案例是：有人试图捕捉一种会破坏最终文档的标记模式，却在源文件阶段使用了与生产工具链不同的 markdown 实现进行检查 —— 它把三个已知有问题的输入全部解析成完全正常的内容，因此任何基于它构建的预检查都会静默地放过所有问题。诚实的结论是，这类缺陷只有在生产工具运行之后才能检测到，检查就应该放在那里。**当没有任何可用工具与生产实现相同时，应明确说明该检查无法在该阶段完成 —— 不要构建一个只能产生虚假绿色结果的检查。**
   根据 skill 的类型，建议适当的默认选项，但由用户决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认 skill 类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这种前期分类会推动后续的整体评估策略。在这里做出正确判断，可以避免之后浪费精力。

### 扩展还是创建检查——在任何专门分支之前运行

下面三个专门工作流中的每一个都以“**do not** continue reading the sections below”结尾，而 *Prior Art Research* 恰好位于它们之后。这个顺序是版面布局，而不是执行顺序。扩展还是创建的判断适用于每个分支，跳过这一步正是导致会话交付一个与已有 skill 重复的 skill 的原因。

因此，在进入 wrapper-skill / conversation-mining / artifact-corpus 路由之前，先回答一个问题：**是否已经存在一个 skill，而这项能力本应归属于它？**

**发现根目录，不要凭记忆。** 手动维护的安装位置列表正是最容易过时的产物，而你忘记的那个根目录往往会带来问题。

**搜索文件，而不是搜索名为 `skills` 的目录。** Skill 目录以 *skill* 命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、marketplace 克隆仓库和插件缓存中根本没有名为 `skills` 的目录——搜索这个名称会在看似正常工作的情况下悄悄跳过它们。每个 skill 都有一个 `SKILL.md`；这是与目录布局无关的定位入口。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，并且仍会返回超出需求的结果；请使用针对该能力的具体术语进一步缩小范围，而不是使用通用术语（`chart` 会匹配所有内容，`stacked bar` 则不会）。

它所覆盖的根目录——也是凭记忆列出的清单通常会遗漏的目录：技能源代码仓库（一个 `claude-code-skills` checkout 以及任何 `-pro` 兄弟仓库）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件——源代码仓库中没有任何线索表明它们存在）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、每个 profile 的配置目录（`~/.claude-profiles/<name>/`），以及——完全没有任何路标的那个目录——**每个项目自己的 `.claude/skills/`**。第 2 步让这件事成为你验证过的结论，而不是你继承来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何 marketplace、全局技能列表或源代码仓库列表中；你在规划新技能时通常会打开的地方，没有任何内容会提到它们。真实案例（2026-07）：某个会话为一个领域构建了全局技能，检查了源代码仓库、全局目录和其他 agent 的目录，什么也没找到，然后完成了发布。之后的一次对话历史搜索发现了一个针对同一领域的成熟项目级技能，它已经存在了一个月，位于某个项目的 `.claude/skills/` 中——其中包含新技能所缺少的八条规则，包括一条用户亲自指定的规则。除了项目级目录之外，所有根目录都检查过了，而这次扫描却非常确信地报告“没有既有方案”。

**当重叠的技能确实是某个无关项目中的项目级技能时该怎么做**——这正是上述惨痛经历会把你带到的情形，也是下面三个要点没有涵盖的情况：你不能把一个兄弟技能添加到一个原本没有兄弟技能的套件中，而“扩展它”意味着编辑一个无关项目的工作树。实际奏效的做法是：**将其中的规则吸收到你正在构建的技能中，然后在所有者同意后废弃项目本地技能**——它是基于真实工作编写的，因此应将其视为更成熟的来源，并**向它靠拢**进行协调。废弃他人的工作技能是所有者的决定，而不是你构建过程中的副作用。

这句话遗漏了四件事，其中每一件都可能让你止步：

- **“向它靠拢”是一项可反驳的推定，而不是规则。** 有两种标准的处理方式：项目技能可能已经*过时*（规则是几个月前针对一个已经发生变化的系统编写的），也可能是*项目特定的*（规则只在该项目的约束下成立——将它们全部导入会让你的技能变得狭窄，而本文档其他部分明确告诉你不要这样做）。吸收来的规则是另一位作者的记忆，因此**必须重新验证每一条**，就像纪律 #1 要求你验证写入技能的任何内容一样。
- **“废弃”需要一种机制，而它的第一步不是你下意识会采取的那一步。** 顺序如下：

  1. **先用 `find` 查找技能的*实体目录*，再 grep 查找它的*引用*。** 一个技能通常会在同一个仓库中存在多个副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被加载，只是由同一个工作树中的不同工具加载。Grep 能回答“谁提到了它”；只有 `find` 能回答“它到底有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要把技能自己的名称放入 `--exclude-dir`**（它按 basename 匹配，因此会隐藏所有同名目录，包括那个你尚未找到的副本——参见纪律 #6 中的工具规则）。真实案例（2026-07）：一次废弃操作正是这样做的，修复了它找到的全部五处引用，却在 `.agents/skills/` 下留下了第二份完整副本——该副本由 git 跟踪，没有废弃标记，是一份缺少最新规则的过时快照——另一个工具仍会将其作为有效技能加载。
  2. **在删除任何内容之前，确认新位置确实能从旧位置所在的环境访问到**——你刚推送的 marketplace 技能，在 marketplace 更新并安装插件之前并没有安装；如果先废弃旧技能，就会出现两边都没有技能的窗口期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常会符号链接到源代码仓库，而不带 `-L` 的 `find` 会报告文件不存在（参见纪律 #6 中的工具规则）。
  3. **然后** grep 查找引用，并重新指向仍在使用的引用。区分**有效指令**（技能列表、交叉引用、告诉下一个 agent 应使用什么的交接文档）和**历史记录**（决策日志中写着“我们在日期 X 发布了这个”）——改写后者会破坏审计线索，只为解决一个它并不存在的问题。
  4. **然后**将每个实体目录替换为 `superseded by <skill>` 存根，而不是直接删除，并确保每个副本的存根在字节层面完全一致。**保留 YAML frontmatter**——没有它的 `SKILL.md` 可能会加载失败，而不是提供有意义的失败信息——但要重写 `description`，使存根声明自身已经废弃，而不是继续宣传旧的触发条件；否则它会继续赢得已经不再服务的路由。正文只需要包含：能力迁移到了哪里，以及它为何迁移的一行说明。
- **使用下面的所有权测试识别所有者**（这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍然会告诉你它属于谁）。当所有者就是与你交谈的人时，“同意”只需一次 `AskUserQuestion`。**当所有者无法联系时，只吸收规则——不要废弃技能**（这样会让两个技能都保持有效并争夺同一触发条件，其最终状态与对方拒绝废弃相同——参见下面的 Coexistence & Precedence）。
- **如果所有者拒绝废弃它**，那么现在就有两个技能在争夺同一触发条件；这属于下面的 Coexistence & Precedence 问题，而不是失败。

**按能力词汇搜索，而不是按 skill 名称搜索。** 该项目 skill 不会匹配新 skill 标题的名称搜索；它匹配的是正文中的领域术语。请在候选根目录中搜索新 skill 将要处理的*概念*。

如果存在重叠：

**判断哪个要点适用——这是谁的 skill？** 文件系统命中结果并不包含所有权信息。请读取 marketplace 的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在包含该命中项的仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中项同样可能是你自己的 marketplace 被安装回了本机。项目级 skill 没有 `marketplace.json`，但其所属项目的 `git remote` 可以回答同样的问题。

探测结果有两种情况会出错或无法回答，因此在相信结果之前请检查：**fork** 显示的是你自己的 remote，但内容属于他人——应将其视为第三方，因为他们上游的改进仍然无法传递给你。当**没有 marketplace.json 且没有 remote**时（本地专用项目、被手动复制到全局 skills 目录中的 skill），探测结果是沉默，而不是否定：**询问所有者，不要猜测**。

- **重叠的是第三方的 skill**（某个 marketplace 套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*薄增量*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本，并通过 namespaced name **引用它**。把别人的引擎复制进自己的 bundle 是代价高昂的错误：他们的升级将无法传递给你，而两份副本会在无声中逐渐偏离。
- **重叠的是你自己的 skill**：扩展它，或在其现有套件中添加一个 sibling。一个与之争夺相同触发条件的独立 skill 对任何人都没有帮助。**例外：**如果它位于*无关项目*的工作树中，则以上两种做法都不适用——请参阅上面的项目级情况。
- **某个相关 skill 已经指向了你正在填补的空缺**（例如其描述写着“对于 X，请使用 Y”）：构建完成后要闭环——更新该指向，否则你就留下了一个悬空引用。

只有在没有任何重叠时，才构建独立 skill。

**为什么这项检查应该放在最前面：**一次真实的 2026-07 会话花了一天时间让第三方 docx 引擎生成正确的中文商务文档，随后转向 wrapper-skill 分支——而该分支会直接跳过 Prior Art Research。它当时准备发布的形态，是一个重新携带该引擎能力的新 skill。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个持有正确用法和经过验证的生成器脚本的薄增量 skill → 由该增量 skill 调用的领域工作流 skill。用户不得不在交付前纠正两次，第二次纠正得更准确：*“不要再复制一个额外的——把正确用法写在他们的 skill 之上，并引用他们的 skill；这就是 skill-as-code 的含义。”*

### 验证深度路由器（在选择任何工作流之前运行）

在采取通用或专用工作流分支之前，选择能够证伪变更行为的**最低层级**。应根据失败面分类，而不是根据行数分类：一条变更的破坏性命令可能比一篇大篇幅的措辞清理更应优先处理。测试前说明所选层级及一句话理由。专用工作流可以替换不兼容的操作机制，但绝不能跳过层级选择，也不能默默降低所需的严谨程度。

| 层级 | 适用情形 | 必需证据 | 默认不添加 |
|---|---|---|---|
| **1 — 定向测试** | 以下条件全部满足：这是一个现有 skill；没有新增或实质性变更能力、触发器族、工作流分支、输出契约、依赖、权限或外部写入行为；并且编辑内容恰好属于以下一种：(a) 不改变行为的拼写/格式修改；(b) 由直接权威来源判定事实真伪的事实性文档/配置修正；或 (c) 用于恢复明确的现有契约、且修复后的行为由确定性回归检查覆盖的有界实现修复。可能改变 agent 行为的澄清不属于 Tier 1 | 三种情形都需要：运行 `quick_validate`，检查差异，并完成现有 skill 迁移门槛。之后仅使用相匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其狭窄检查；(c) 明确的现有契约及确定性回归。仅当触发纪律 #5 的规则/契约/数值阈值时，才添加一名新鲜审阅者 | agent 行为重放、成对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 抽样行为测试** | 以下条件全部满足：这是一个现有 skill；变更会影响 agent 行为；确定性检查无法完全判定其正确性；没有引入新的或实质性变更的能力、触发器族、工作流分支、输出契约、脚本行为、依赖、权限或外部写入；并且 1–2 个具有明确验收标准的指定示例可以覆盖全部变更行为 | 仅运行这 1–2 个具有代表性的带 skill 重放，以及狭窄的确定性检查和纪律 #5 要求的一次新鲜上下文审查 | 基线、成对扇出、方差分析、基准测试、查看器或评估文件。任何要求其中一项的请求都会将工作重新分类为 Tier 3 |
| **3 — 完整评估** | 满足以下任一条件：任何新 skill；任何新增或实质性变更的能力；大范围重写或方法论扩展；触发器/描述优化；新的或实质性变更的工作流分支、输出契约、脚本能力、依赖或权限；高风险自动化或外部写入；评估需要覆盖 3 个以上不同的提示类别、重复试验/方差，或需要在实质性不同的方法之间进行选择；或用户明确要求 A/B、基线、基准测试或查看器证据。仅凭主观判断，不会将原本狭窄的 Tier 2 变更升级 | 对于通用工作流，运行下面完整的成对流水线：真实案例、带 skill + 基线、断言、评分、聚合基准测试、分析师检查和查看器。专用工作流只能替换其明确标记为不兼容的机制；运行其完整验证协议及所有兼容的 Tier 3 步骤，并记录所替换的内容 | 无 —— 这是经过审慎选择的重型路径 |

当较低层级暴露出未解决的行为或相互矛盾的证据时，应升级处理。用户要求取消或降低评估级别时，覆盖的是**执行授权，而不是分类结果**：立即停止已经启动的配对评估代理、基线、评分器、聚合和查看器工作。Tier 3 变更仍然是 Tier 3；应将其所需的重型证据记录为用户放弃或尚未完成，而不是将较低层级的证据重新标记为通过。仅继续执行用户仍授权的证据收集，并且不得声称已完成 Tier 3 的完整验证。当 discipline #5 的规则/契约/数量阈值被触发时，不得取消其中唯一的新上下文审查者；任何为防止破坏性影响或外部影响所必需的安全门禁也不得取消。机械式的现有 skill 迁移审计、公共 skill 清理，以及任何特定领域的安全门禁，也独立于此路由器继续执行。

### 专用工作流：第三方 CLI 工具的 Wrapper Skills

在决定采用通用 skill 创建流程之前，检查当前会话截至此处的实际情况是否要求改用 **wrapper skill** 工作流。wrapper skill 是一种配套 skill，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或 skill 包，也就是由他人编写、而用户刚刚花费一整个会话才让其在自己机器上正常工作的代码。

适用信号（任意两项同时出现即可）：

- 用户在当前对话中一直在安装某个工具，例如下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 会话中产生了真实、具体的错误消息，并且用户和 Claude 已经针对这些错误找出了具体修复方案（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个整理成一个 skill”“把这保存成一个 wrapper skill”“这样其他人就不用再经历这一遍了”“把这次 session 做成一个 skill”之类的话。
- 用户明确提到某个第三方工具的名称，并希望其他代理或其他人能够使用它，而不必再经历自己刚刚付出的学习过程。

不适用的信号（改用上面的通用工作流）：

- 用户想要的是一个用于某项从头开始编写的内容的 skill。
- 会话过程很顺利，没有值得提炼的实际阻碍。
- 该 skill 将封装用户拥有或控制的服务（这是用户自己的代码；应直接编辑源代码，而不是进行封装）。
- 所谓的“工具”实际上是一种不涉及安装任何二进制文件或软件包的方法论或工作流。

当 wrapper skill 工作流适用时，保留上面所选的验证层级。创建 wrapper 就是在创建新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用编写部分；跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回溯式提炼**工作流，其任务是从当前对话中挖掘安装流程、已修复的 bug 以及已经做出的设计决策，并将这些挖掘结果转化为一个完整、自包含的 wrapper skill，使其他用户能够安装并从中受益，而无需重新经历这次调试会话。

包装器 skill 工作流拥有自己的架构契约、代码模板和 Tier 3 验证协议——由于其输出是用户的安装状态，而不是可以轻松断言的文件，因此它会替换不兼容的通用测试用例机制；这并不意味着降低工作标准。运行所有兼容的通用 Tier 3 步骤，并记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库根目录——这里的裸相对链接曾在该 skill 移入套件后失效，这正如下面的跨 skill 引用规则所警告的那样），它是 Tencent IMA skill 的一个包装器，根据一次严格遵循此工作流的真实会话提炼而成。

### 专用工作流：从对话历史中丰富 Skill

在提交通用 skill 创建流程之前，检查当前会话是否实际上要求**将过去的对话提炼为 skill**。当用户在多次 Claude Code / Codex 会话中调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这种方式非常有用。

符合此条件的信号（满足任意一项即可）：

- 用户说了类似“从我的聊天记录中挖掘模式”“把这次对话整理成 skill 参考”“把我们学到的内容沉淀到 skill 里”“从我的对话中丰富这个 skill”，或“把这次对话沉淀到 skill 里”这样的话。
- 当前会话明确是在从最近一次多轮调试或设计会话中提取经验。
- 用户希望根据自己已经进行过的真实对话，为现有 skill 添加 `references/` 文件。
- 目标 skill 已经存在，目标是使用从对话中挖掘的知识丰富它，而不是从头构建。

不适用的信号（改用上面的通用工作流）：

- 用户正在根据单个提示或想法创建全新的 skill。
- 用户希望为刚安装的第三方 CLI 工具创建包装器（使用上面的包装器 skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的转录导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 而不是可复用的参考文件中。
- 源材料是一批用户已经认可的成品，而不是对话——使用下面的工件语料库提炼工作流。

当对话挖掘工作流适用时，保留上面选定的验证级别。新的挖掘型 skill 属于 Tier 3；丰富现有 skill 时，只有在满足该级别的能力边界时，才能保持已选级别。**不要**继续阅读下面的通用编写章节；跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端遵循该工作流，包括其验证协议。这是一个**回顾式提炼**工作流：它会发现本地 Claude Code 项目会话、Codex 转录和命令历史记录，对其进行脱敏，将其划分为适合 agent 处理的分块，运行挖掘 agent，并在验证后将生成的候选参考文件提升到目标 skill 的 `references/` 中。

对话挖掘工作流有其自身的架构契约、代理提示词、模板和验证协议。该协议实现所选层级的专用机制；运行所有兼容的通用步骤，并记录任何替代方案。这是将真实对话历史转化为技能可复用知识库的标准方式。

### 专用工作流：从已批准成果语料库中提炼用户偏好

在采用通用流程之前，检查当前会话是否要求**从一批用户认可的已完成成果中提取用户真实偏好**——已批准的 HTML 报告页面、生成的文档、设计稿。这是不同于上述两种来源的第三种提炼来源：材料是**产品，而非对话**；输出是**可执行的品味**（明确的原则、量化的参数、词汇），而不是知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的成果，并说“这些都是我认可的样例”/“你来学到底什么是我想要的”/“extract my preferences from these approved examples”。
- 某个品味校准技能（报告生成器、文档样式工具、演示文稿构建器）拥有一个不断增长的已批准样例语料库，而用户要求让该技能从中*学习*，而不只是将其编入索引。
- 用户抱怨之前的更新“只加了示例”——只登记了样例，却没有改变技能的行为。

不适用信号：源材料是对话/修正内容，而不是经过认可的产品（使用对话挖掘）；样例并未得到用户个人批准（批准是准入门槛——先询问）。

适用时，保留上面选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新的语料库衍生技能属于第 3 层；向现有技能添加实质性的新决策能力也属于第 3 层。专用协议实现所选层级的语料库机制，并不会降低该层级；运行所有兼容的通用步骤，并记录任何替代方案。其核心纪律同样适用于向现有技能添加材料的任何时候：**编目录 ≠ 提炼**——在语料库表中登记一个样例不会改变技能的下一次运行；对于每一项新增内容，都要追问“*这是否改变了某条决策规则？*”，并且在所有写入内容都没有对该问题给出肯定回答时，不要宣布提炼会话完成（方法论 Case 15）。该工作流的主线是：对**所有**成果进行脚本提取的定量比较（每种模式至少满足 3 个成果的阈值，并对声称的常量检查例外列表）→ 带有证据锚点的分层归纳 → 写入决策规则层（区分不变量与依赖语域的变量）→ 独立的完整性审计（长期纪律 #5）→ 回归审计。

### 先例研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策、竞争优势——正是技能有价值的原因。任何公共代码仓库都无法提供这些内容。但当成熟工具已经存在时，用户不应浪费时间重新实现基础设施（API 客户端、身份验证流程、速率限制）。先例研究用于寻找基础设施层的构建模块，让技能能够专注于编码用户独有的方法论。

**两个轴，不要混为一谈。** 本节针对的是*基础设施*层（可复用的工具 / MCP / 库 / 现有技能）。*方法论*层有其自身的两个输入：用户的私有优势（只有用户自己拥有，无法检索）**以及该领域已经确立的最佳实践 / 科学知识；按照长期纪律 #3，默认将后者检索到上下文中。** 找到合适的工具并不能免除第二项要求——一个采用了 charting library，却从未吸收 Cleveland/Bertin 理论的可视化技能，能力上限仍然只是你的预训练水平。两者都要做。

**按以下顺序搜索这些渠道**（第 4-8 项使用 subagents 并行执行）：

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **对话历史** | 用户已经验证过的工作流、已确认的 API 模式、调试期间做出的修正 | 在最近的对话中 Grep 该服务/API 名称 |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已经集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP servers |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方 / 合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP servers** | 面向同一 API 的现有 MCP servers | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI packages | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 会揭示用户自己的已验证模式和现有集成。渠道 4-8 用于寻找公开的基础设施。用户的私有 SOP 始终优先——公开工具是构建模块，不是替代品。在竞争激烈的领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**倾向于合并 / 扩展，而不是重新创建，并且要扫描每一个技能根目录——不要只查看 `~/.claude`。** 当渠道 1-3 发现与请求领域重叠的现有技能时，通常正确的做法是扩展或合并到其中——**但如果它位于不相关项目的工作树中，方向就相反：应当从中提取内容，融入你正在构建的技能，而不是将新内容合并到其中**（参见上文 extend-vs-create 检查中的项目级案例）（有一个实际的“新技能”任务最终变成了“让现有 extractor 成为新 archiver 的 extract-phase”），不要交付一个会争夺相同触发条件的并行技能——两个重叠的技能会互相争夺触发，并使用户困惑。搜索时，**应发现安装根目录，而不是凭记忆列出目录——使用 `SKILL.md` 扫描及上文 extend-vs-create 部分的覆盖率自检**（搜索名为 `skills` 的目录会漏掉源代码仓库、marketplace 克隆目录和插件缓存，因为它们的技能目录是以技能名称命名的）。运行覆盖率检查，不要只相信这句话：**每个项目自己的 `.claude/skills/` 都是凭记忆列出的清单最容易漏掉的根目录，因为项目之外没有任何地方会引用它。** 用户已经安装在*任何位置*的技能，都是最有价值的先例，而项目本地技能通常最成熟：它是在真实工作中编写出来的。

**如果找到公开的 MCP 服务器或 skill，请克隆并进行验证——不要相信 README：**

1. **阅读实际源代码** —— 许多项目的 README 写得很精美，但代码库本身却空洞无物
2. **验证身份验证方式** —— 是否与 API 实际采用的身份验证方式一致？（`X-Api-Key` 请求头、`Bearer` 还是 OAuth——很多项目在这方面都弄错了）
3. **检查测试覆盖率** —— 没有测试 = 原型，而不是生产级项目
4. **检查维护情况** —— 最近一次提交日期、未解决 issue 数量、对 bug 报告的响应情况
5. **检查环境兼容性** —— 代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证** —— MIT/Apache 没问题；GPL/SSPL 可能会与专有软件的使用产生冲突
7. **检查依赖规模** —— 庞大的依赖树会增加冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用它，在其基础上构建** —— 安装 MCP，然后将 skill 构建为工作流层，用于编码用户的方法论 |
| 存在不完整的 MCP 或 SDK | **扩展它** —— 使用其基础设施能力，在 skill 中补齐缺口 |
| 公开 skill 覆盖相同领域 | **仅用于获取结构上的启发** —— 竞争领域中的公开 skill 按定义都是通用的。用户的优势在于其私有 SOP |
| **存在能够提供你正在构建的功能的某项子能力的互补 skill** | **将其打包** —— 将互补 skill 的自包含资源复制到你的包中，并将它们接入。不要依赖用户预先安装该 skill。参见下方的“互补 Skills” |
| 没有公开资源 | **从头构建** —— 在编写完整 skill 之前，先验证 API 访问模式是否可行（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建** —— 一个由你掌控、耗时 2 小时的自定义实现，胜过一个集成摩擦大且存在上游风险的“成熟”工具 |
| 用户有意取代已安装的 skill（分支版本、加固版） | **随附 supersede kit 一起发布** —— 参见下方的“共存与优先级” |

#### 共存与优先级（有意重叠）

将内容合并到现有 skill 中，是解决重叠问题的默认方式（见上文）。但当用户*有意*发布一个与已安装 skill 重叠的 skill 时——例如官方插件的分支版本、经过加固的内部版本——这两个条目会以相似的描述出现在 skill 列表中，Claude 将在它们之间随机路由。请按逐步升级的顺序解决：如果重叠是意外的，则重命名；添加描述中的决胜说明（“取代 X —— 当两者同时出现时，始终使用此 skill”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式 supersede kit 写入 skill——这是一个基于用户同意的 SessionStart 路由钩子，仅会安装在确实存在竞争者的机器上，在其他机器上拒绝安装，并且在任一方消失时自动停用。相关机制、决策表、SKILL.md 示例措辞和沙箱验证见：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此 skill 也针对官方 skill-creator 插件使用了同一套 kit（参见顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄无声息地失去了面向*已安装技能集合*的触发机会。** 一个技能所属的领域（图像生成、PDF 处理、仪表板）通常已经有多个已安装技能，新技能可能会失去对它们全部的自动路由。因此，**要尽早验证触发效果——内容写得好并不意味着构建就完成了。** 草稿完成后，通过 `claude -p` 发起几个符合实际的查询，并检查新技能是否真的能够胜出；如果没有，**指出它输给了哪个具体竞争者**（不同查询可能会输给不同技能）。接下来要明确两点：(1) **在竞争激烈的触发位置上，仅靠正文不一定能胜出**——解决阶梯是：重命名 → 通过描述进行决胜 / 使用 SUPERSEDES → 手动调用 → SessionStart 路由钩子（结构性方案；会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的纪律）；以及 (2) **修复方式取决于竞争者的作者**——竞争者是*第三方*的 → 接受手动调用或使用路由钩子；竞争者是*你自己*的 → 将它们合并 / 整合为一个，不要让自己的两个技能争夺同一个触发机会。（完整的解决阶梯位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要只是指引，不要独立扩展。）记录所选择的路径（例如添加一条“Activation”说明，写明“手动调用，竞争者为第三方”），可以避免下一次会话重新争论这个问题。（方法论案例 13）

##### 互补技能（打包，不要依赖）

当你构建的技能涉及一个已有的互补技能所属的领域时，有两种选择：

- **依赖该技能已安装**：脆弱——用户可能没有安装它，或者安装的是不同版本。每一次缺少依赖的失败，最终都可以追溯到这个选择。
- **将其打包**：把互补技能中自包含的资源（脚本、模板、参考文档）复制到你自己的包中，并进行连接配置，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包。** 这对于以下内容尤其重要：
- 状态栏 / UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证 / 清理脚本
- 通用的数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。配置文件初始化技能不依赖用户先运行 `statusline-generator`，而是将 `statusline.sh` 打包进去，并在 `claude-profiles-init` 期间将其连接到每个新配置文件中。这两个技能仍然可以独立发挥作用，但包装技能能够独立运行。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装程序”。这会把依赖转嫁给用户，并创建脆弱的安装顺序。应当改为打包。

研究完成后，通过 **AskUserQuestion** 呈现研究结果：

```
已完成对 "[skill-name]" 的研究。以下是我的发现：

[对公开存在内容的 1-2 句总结]

建议：因为[一句话说明理由]，所以选择[采用 / 扩展 / 构建]

选项：
A) 采用 [工具/MCP X] 作为基础设施，在其上构建方法论层（推荐）
B) 扩展 [不完整的工具 Y] ——使用已有可行部分，补齐 skill 中的缺口
C) 从头构建 ——没有找到足够匹配的内容
D) 在我决定之前，先向我展示详细研究结果
```

如果无法确定，优先考虑采用成熟的基础设施来处理底层支撑，并为方法论层构建自定义逻辑——价值就在于此。

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。等这些内容确定后，再编写测试提示词。

检查可用的 MCP——如果对研究有帮助（搜索文档、查找类似的 skill、了解最佳实践），并行通过子代理开展研究；否则就在当前上下文中进行。提前准备好相关背景信息，以减少用户负担。

### 编写 SKILL.md

根据用户访谈结果，填写以下组件：

- **name**：Skill 标识符
- **description**：何时触发，以及它的作用。这是主要的触发机制——同时包含 skill 的功能 AND 具体使用场景。所有“何时使用”的信息都放在这里，而不是正文中。注意：目前 Claude 有“触发不足”的倾向——在 skill 有用时不使用它。为了解决这个问题，请让 skill 描述稍微“主动”一些。例如，不要写“如何构建一个简单快速的仪表板来展示 Anthropic 内部数据”，可以写成“如何构建一个简单快速的仪表板来展示 Anthropic 内部数据。只要用户提到仪表板、数据可视化、内部指标，或者希望展示任何类型的公司数据，即使他们没有明确要求‘仪表板’，也务必使用这个 skill。”

  **控制长度：description 有严格的 1024 字符上限，验证会拒绝超出限制的内容。** 这与上面“主动触发”的建议存在直接矛盾——每添加一个触发短语来扩大覆盖范围，都会消耗预算，因此要在扩展之前测量，而不是凭感觉：使用 `len(description)`，不要凭感觉判断。真正的陷阱不在于第一版（通常距离上限还很远），而在于多年后的更新：新增触发词以覆盖后来支持的范围，可能让 description 逐渐接近上限。这时，**添加一个触发词就意味着零和——必须删除已有内容来为它腾出空间。** 要有意识地做出这种取舍，并在提交信息中说明，因为一个无声删除的触发短语实际上会缩小 skill 的触发范围，直到它不再为某个用户触发时，才会有人注意到。（实际发生过这样的情况：一次更新为新支持的故障模式添加了触发词，使 description 达到 1280 个字符，之后经过两轮压缩才降到 1003——代价是删除了三个原有触发短语。这个决定本应明确记录，而不是在与验证器反复较量时才被发现。）必须删减时，优先选择那些仍可通过同义词或相邻短语覆盖其场景的短语；保留没有其他入口的短语；还要记住，正文中的限定语（例如“在平台 X 和 Y 上”，或括号中的枚举）通常比独立的触发短语更容易删减——正文可以从内容中重新推导，触发短语则无法替代。
- **compatibility**：必需的工具、依赖项（可选，很少需要）
- **skill 的其余内容 :)**

### Skill 编写指南

#### Skill 的构成

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除了 `description` 之外，所有 frontmatter 字段都是可选的。通过在 `---` 标记之间配置以下字段来设置 skill 的行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必填 | 描述 |
|-------|----------|-------------|
| `name` | 否 | skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 推荐 | 说明 skill 的功能以及使用时机。Claude 会根据此字段决定何时应用该 skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork`，即可在派生的 subagent 上下文中运行。** 参见下方的“Inline 与 Fork：关键决策”——选择错误会导致 skill 无法正常工作。 |
| `agent` | 否 | 设置 `context: fork` 时要使用的 subagent 类型。可选值为 `Explore`、`Plan`、`general-purpose`，或 `.claude/agents/` 中的自定义 agent。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true`，以防止 Claude 自动加载此 skill。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false`，以从 `/` 菜单中隐藏。适用于不应由用户直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略该字段可让 skill 在用户权限设置的约束下获得完整的工具访问权限。设置该字段会不必要地限制 skill 的能力。 |
| `model` | 否 | 此 skill 激活时使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指示所需参数。例如：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此 skill 生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。参见 Claude Code Hooks 文档。 |

**特殊占位符：** skill 内容中的 `$ARGUMENTS` 会替换为用户在 skill 名称后提供的文本。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### Inline 与 Fork：关键决策

**这是设计 skill 时最重要的架构决策。** 选择错误会悄无声息地破坏 skill 的核心能力。

**关键限制：Subagent 不能再生成其他 subagent。** 使用 `context: fork` 运行的 skill（作为 subagent）**不能**：
- 使用 Task 工具生成并行探索 agent
- 使用 Skill 工具调用其他 skill
- 编排任何多 agent 工作流

**决策指南：**

| 你的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task tool） | **Inline**（无 `context`） | 子代理无法创建子代理 |
| 调用其他 skill（Skill tool） | **Inline**（无 `context`） | 子代理无法调用 skill |
| 运行用于外部 CLI 的 Bash 命令 | **Inline**（无 `context`） | 主上下文拥有完整的工具访问权限 |
| 执行单个聚焦任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境干净 |
| 提供参考知识（编码约定） | **Inline**（无 `context`） | 指南可以丰富主对话 |
| 被其他 skill 调用 | **Fork**（`context: fork`） | 必须作为子代理才能被启动 |

**编排器 skill 示例（必须使用 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专业 skill 示例（使用 fork 是正确的）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，无 task）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skill 应当是**正交的**：每个 skill 处理一个关注点，并通过组合协同工作。

**模式：编排器（inline）调用专业 skill（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（无 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个 skill 都应承担单一职责，不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法论，不要通过复制代码来实现

##### 流程交接（顺序 Skill 链式调用）

除了编排器/专业 skill 组合之外，skill 通常还会组成**顺序流程**，其中一个 skill 的输出会成为下一个 skill 的输入。每个 skill 在完成工作后，都应主动建议逻辑上的下一步。

**模式：SKILL.md 末尾的“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion **由用户选择加入**，绝不能在未询问的情况下自动调用下一个 skill
2. 仅在输出自然地适用于另一个 skill 时提出建议，不要强行建立关联
3. 包含一个 "No thanks" 选项，用户可能不需要完整的流水线
4. 建议中应解释为什么下一步有帮助（例如："ASR 输出通常包含识别错误"）
5. 最多提供 1-2 个建议，选项过多会导致决策疲劳

**何时添加交接：**询问“这个 skill 的输出是否通常会成为另一个 skill 的输入？”如果是，则添加一个 "Next Step" 部分。如果关联很少见或牵强，则不要添加。

**反模式：**串联没有自然数据流的 skills。`pdf-creator → youtube-downloader` 没有意义。流水线必须遵循用户的实际工作流程。

##### 优先自动检测，而不是手动标志

**绝不要为可以自动检测的能力添加手动标志。**不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: 自动检测并告知用户
Step 0: 检查可用工具
  - `which codex` → 如果找到，则告知用户并启用跨模型分析
  - `ls package.json` → 如果找到，则针对 Node.js 项目调整提示词
  - `which docker` → 如果找到，则启用基于容器的执行

# Bad: 手动标志
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力自动检测，范围由用户决定。skill 应发现自己能够做什么并据此行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | 子代理可以使用 |
|-------------|------------|----------------|----------------|
| （默认） | 是 | 是 | 否（内联运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（在明确委派时） |

#### 渐进式披露

Skills 使用三级加载系统：
1. **元数据**（名称 + 描述）- 始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文** - skill 触发时位于上下文中
3. **捆绑资源** - 按需加载（无限制，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。一份没有冗余内容的 600 行 skill，比一份省略关键知识、迫使模型猜测的 200 行 skill 更好。如果 skill 变得很长，请问：“每个部分是否都发挥了作用？”如果答案是肯定的，就保留它。如果某些部分只是填充内容，或者解释了 Claude 已经知道的事情，则应精简这些部分，而不是删除有用内容。当一个 skill 确实覆盖多个领域时，应按领域拆分到 references 中，而不是人为地把所有内容压缩进一个简短的主文件。
- 对于现有 skill，渐进式披露是一种重新定位策略，而不是删除启发式规则。旧的运行时契约必须仍然可以从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、changelog 条目或审阅者记忆都不能替代运行时内容。
- 在 SKILL.md 中清晰地引用参考文件，并说明何时读取它们
- 对于较大的参考文件（超过 300 行），应包含目录?sia

**领域组织**：当技能支持多个领域/框架时，请按变体组织：
```text
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 避免意外原则

不言而喻，技能不得包含恶意软件、漏洞利用代码，或任何可能危及系统安全的内容。如果描述技能的意图，技能的内容不应让用户感到意外。不要顺从创建误导性技能的请求，也不要创建旨在协助未经授权的访问、数据外泄或其他恶意活动的技能。诸如“扮演 XYZ”之类的角色扮演是可以的。

#### 写作模式

指令中应优先使用祈使句。

**定义输出格式** - 可以这样写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式** - 加入示例很有帮助。你可以这样设置格式（但如果示例中使用了 "Input" 和 "Output"，可能需要稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得加入技能的可用性模式** - 以下四个结构性元素反复将“能运行但令人困惑”的技能转变为用户真正能够操作的技能——它们是让高频使用的技能变得可用的具体增强措施，因此当技能具有模式、会运行命令或可以重新运行时，应考虑加入：
- **入口决策树**：如果技能有多种模式，请以一个简短的“用户说了 X → 使用模式 Y”映射开头，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧跟在命令之后展示“你应该看到的内容”，这样模型和用户都能区分真正的成功与无提示失败。
- **故障排除部分**：列出已知的失败模式及其解决方法——对于将在你无法查看的机器上运行技能的其他人来说，这是最有价值的部分。
- **第 0 步幂等性保护**：如果重新运行可能会重复已完成的工作，请先进行一个成本低廉的“是否已经完成？”检查，再执行任何耗时操作。

### 写作风格

尽量向模型解释事情为何重要，以此替代生硬、过度强制且充斥着 MUST 的要求。运用心智理论，并尽量使技能具有通用性，不要局限于特定示例。先写出草稿，然后以全新的视角重新审视并改进它。

### 日期和版本引用

**保留事实性日期——它们能告诉读者信息经过验证的时间。**关于 Suno v5.5 的技能应写成 “Suno v5.5 (March 2026)”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 August 2025，则使用旧 API”）——日期一旦过去，这种逻辑就会失效，而没有人会更新它。

规则：
- **发布日期、“最后验证”日期**：保留。这些是参考时间点，不是到期日期
- **价格、排名、法律状态**：应包含，但要标注为易变信息（“截至上次检查约为 ~$0.035/gen”），以便读者知道需要重新核实
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠的/已弃用部分中记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或反复重写任务的可执行代码（Python/Bash 等）。

- **何时包含**：当相同代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优势**：节省 token、具有确定性，并且可以在不加载到上下文的情况下执行
- **注意**：Claude 仍可能需要读取脚本，以便进行修补或针对环境进行调整
- **用户可修改的数据存放在捆绑包之外**：如果脚本会累积用户数据（修正字典、学习到的偏好、缓存），请将其存储在稳定的相对于用户主目录的目录中（例如 `~/.<skill-name>/`），并为其单独创建备份——绝不要将其放在 skill 目录内。每次更新和套件迁移都会删除并重新创建 skill 安装目录，而相对于用户主目录的存储位置可以保持不变。这正是一个不断累积词典的 skill 能够在完整套件迁移后实现用户数据零丢失的原因

##### 参考资料（`references/`）

旨在按需加载到上下文中，为 Claude 的处理过程和思考提供信息的文档与参考材料。

- **何时包含**：当 Claude 工作时需要参考相关文档
- **示例**：用于财务架构的 `references/finance.md`、用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库架构、API 文档、领域知识、公司政策、详细工作流指南
- **优势**：保持 SKILL.md 简洁，仅在 Claude 判断需要时加载
- **最佳实践**：如果文件较大（超过 10,000 个单词），请在 SKILL.md 中加入 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或参考文件中，不要两处同时存放

##### 资源（`assets/`）

不打算加载到上下文中，而是供 Claude 在生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用相关文件时
- **示例**：用于品牌资源的 `assets/logo.png`、用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件库**：对于生成制品的 skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、可逐字嵌入的片段，这些片段具有冻结的行为契约和注册表引用——参见第 4 步中的组件库检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标。**下面的所有内容描述的是 skill 发布给陌生用户时会导致的问题。对于存放在作者自己的私有仓库中的 skill，相同的“违规”通常正是其能够正常工作的原因——真实的绝对路径能让脚本直接运行，模板中的真实账户则能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 包含该 skill 的仓库是否为私有仓库），并在此情况下将可移植性/标识符问题降级为备注；当私有 skill 准备发布时，`--audience=public` 会强制执行严格检查。

**在私有 skill 中，这些问题由所有者决定，而不是由你决定。** 不要擅自将真实路径替换为占位符、重写硬编码凭据，或在未询问的情况下“清理”示例 —— 这样会为了满足一条原本针对其他发布目的而编写的规则，破坏一个正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，让所有者决定。（其设计先例是 npm 的 `"private": true`：声明发布目的后，工具会据此改变其强制执行的规则；之所以加入这一机制，是因为人们不断意外发布内容。）

**对于计划公开分发的 skills，这一点至关重要** —— 其中不得包含特定用户或特定公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，例如 `~/.claude/skills/`
- **允许**：skill bundle 内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（严格逐字实现 Forbidden 列表的 validator 会将此 skill 本身标记出来 —— 对健康输入误报，比漏报更糟）：当发布者自己的名称/品牌是解决 supersede 平局或进行归属声明所必需时，可以使用；当段落讨论这些路径本身时，可以使用类似 `~/.claude/skills/` 的安装路径（这是教学材料，而不是硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于该 skill 自己的 bundle 内” —— validator 和读者都会如此理解，因此，指向另一个 skill 文件的裸路径会验证失败，也会误导读者。指向另一个 skill 时，应在正文中注明其所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用带命名空间的名称调用 skills（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。当 skills 在不同 suite 之间迁移时，裸跨引用会静默失效 —— 某次 suite 迁移后，在两轮清理中总共留下了 21 个损坏的跨引用。

##### 版本管理

**至关重要**：SKILL.md 中不应包含版本历史或版本号：

- **禁止**：在 SKILL.md 中添加版本相关章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **理由**：Marketplace 基础设施负责版本管理；SKILL.md 应包含不随时间变化的内容

#### Reference 文件命名

文件名必须做到无需阅读内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：仅凭文件名，任何人都能理解文件内容吗？

有两个例外：连字符命名和下划线命名同样合适（分隔符从来不是重点 —— 关键在于能否自我说明）；位于具名 workflow 目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已经通过目录获得了限定信息，重命名它们会破坏各 workflow 之间的平行结构。

### 完整评估测试用例（仅限 Tier 3）

仅当路由器选择通用 Tier 3 路径，或用户明确请求完整评估流程时，才进入本节。不要仅仅因为 SKILL.md 发生了更改就使用本节。应遵循上文声明的 Tier 3 替换契约所规定的专用工作流。

编写 skill 草稿后，提出 2-3 个真实的测试提示词——也就是实际用户可能会说的话。**对于作用于实时系统的 skill（正在运行的服务、已登录的客户端、生产数据），请为每个测试提示词明确副作用预算**——例如“进行只读探测并得出结论；不要执行下载 / 驱动 UI”。在“只是测试”时修改实时环境属于真实操作，而不是测试。通过 **AskUserQuestion** 展示这些提示词：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——接下来的一步会在运行进行期间起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整模式请参阅 `references/eval_pipeline_schemas.md`（包括稍后添加的 `assertions` 字段）。

## 完整配对评估流程（仅限通用 Tier 3）

仅在选择通用 Tier 3 路径后运行本节。在 Tier 3 仍获授权期间，这是一个连续的流程——不要中途停止。用户取消或降级会覆盖本段要求；请按照路由器中的说明停止繁重流程。不要将其机械地复用于 Tier 1、Tier 2，或明确由其工作流替代的专用机制，也不要使用 `/skill-test` 或任何其他测试 skill。

将结果放入 skill 目录同级的 `<skill-name>-workspace/` 中。在该工作区内按迭代组织结果（`iteration-1/`、`iteration-2/` 等），每个测试用例在对应迭代下使用一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些目录——只在需要时逐步创建。

### 第 1 步：在同一轮中启动所有运行（包含使用技能和基线）

对于每个测试用例，在同一轮中启动两个子代理：一个使用技能，一个不使用技能。这一点很重要：不要先启动使用技能的运行，之后再回来启动基线运行。一次性启动所有运行，使它们大致同时完成。

**使用技能的运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（使用相同的提示词，但基线取决于上下文）：
- **创建新技能**：完全不使用技能。使用相同的提示词，不指定技能路径，将输出保存到 `without_skill/outputs/`。
- **改进现有技能**：使用强制性的现有技能回归门禁在首次编辑前保存的旧版本。将基线子代理指向该不可变快照，并将输出保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 恢复一个权威基线后再继续；绝不要使用已经编辑过的树作为旧基线。**要明确这种比较能够解决什么问题：它只衡量本轮的差异。** 如果你最想验证的能力已经存在于编辑前快照中——例如某个并行会话可以在你开始之前准确提交该修复——那么使用技能/旧版本的 A/B 对该能力没有解析力；在这种情况下，应选择更早的引用作为基线，以测试该能力。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据每个 eval 测试的内容为其指定描述性名称，而不要只使用 “eval-0”。同时将此名称用于目录名。如果本轮使用了新的或修改过的 eval 提示词，则为每个新的 eval 目录创建这些文件——不要假设它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：在运行进行期间起草断言

不要只是等待运行完成——你可以利用这段时间开展有价值的工作。为每个测试用例起草定量断言，并向用户说明这些断言。如果 `evals/evals.json` 中已经存在断言，则审查它们并解释其检查内容。

好的断言应当能够客观验证，并且具有描述性名称——在基准测试查看器中，它们应当清晰易懂，使浏览结果的人能够立即了解每条断言检查的内容。**应针对意图编写断言，而不是针对字面意义上的工具路径**——“语音内容保留在回答中”，而不是“调用经过批准的读取脚本”。如果运行通过其他经过批准的路径实现了该意图（例如读取一个已经内嵌了转录内容的归档文件），则应判定为通过；将其判定为字面路径失败会制造错误的负面结果，随后导致你修复错误的地方。主观技能（写作风格、设计质量）更适合进行定性评估——不要强行为需要人工判断的内容设置断言；它们真正的验证路径（历史任务重放、带回写习惯的生产环境即评估、渲染后人工审查）列在“Capture Intent”的第 4 个问题下。

起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到什么，包括定性输出和定量基准测试。

### 第 3 步：随着运行完成，捕获时序数据

每个子代理任务完成时，你会收到一条通知，其中包含 `total_tokens` 和 `duration_ms`。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会：它们会通过任务通知传来，而不会持久化到其他地方。应在每条通知到达时处理，而不是尝试批量处理。

### 第 4 步：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分** — 启动一个评分子代理（或内联评分），读取 `agents/grader.md` 并根据输出评估每项断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（不要使用 `name`/`met`/`details` 或其他变体）— 查看器依赖这些确切的字段名称。对于可以通过编程方式检查的断言，应编写并运行脚本，而不是凭肉眼检查 — 脚本更快、更可靠，并且可以在迭代之间复用。**但客观的 grep/脚本断言也有两面性**（同词异义会导致误命中，措辞差异会导致漏检），因此**基准通过率是一个信号，而不是结论**：抽查每项断言实际匹配到的内容，并留意基线运行是否揭示了技能本身存在事实错误（“等等，数据确实在 API 里”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **聚合为基准测试** — 从 skill-creator 目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、时间和 token，以及均值 +/- 标准差和差值。如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md` 以了解查看器所需的确切模式。
将每个 with_skill 版本置于其对应的 baseline 版本之前。

3. **进行分析师审查** — 阅读基准数据，并呈现聚合统计数据可能掩盖的模式。参见 `agents/analyzer.md`（“分析基准测试结果”部分）以了解需要关注的内容 — 例如，无论是否使用技能都始终通过的断言（无区分度）、高方差评估（可能不稳定），以及时间/token 权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还应传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台查看器使自身失去响应**：进程仍在运行，但没有任何程序在监听 — 使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或 curl 该 URL（请求失败）；这里“没有日志输出”不是可用的信号，因为上面的启动命令行已将其重定向到 `/dev/null`。终止该进程，然后回退到 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击“提交所有评审”时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** **告知用户**：

```
结果已准备就绪！我已在浏览器中打开评估查看器。

- “Outputs”选项卡：逐个点击每个测试用例，并在文本框中留下反馈
- “Benchmark”选项卡：查看定量比较（通过率、耗时、token 数量）

请花时间进行评审。完成后返回这里。

建议：先评审“Outputs”选项卡 — 与数字相比，你的定性反馈对下一次迭代的影响更大。

选项：
A) 我已完成评审 — 读取我的反馈并改进 skill
B) 在提供反馈之前，我对结果有疑问
C) 结果已经足够好 — 跳过迭代，打包 skill
D) 结果需要大幅返工 — 在迭代之前先讨论
```

### 用户在查看器中看到的内容

“Outputs”选项卡一次显示一个测试用例：
- **Prompt**：提供的任务
- **Output**：skill 生成的文件，在可能的情况下以内嵌方式渲染
- **Previous Output**（第 2 次迭代及之后）：显示上一次迭代输出的折叠区域
- **Formal Grades**（运行了评分时）：显示断言通过/失败情况的折叠区域
- **Feedback**：输入反馈的文本框，输入时会自动保存
- **Previous Feedback**（第 2 次迭代及之后）：文本框下方显示用户上次留下的评论

“Benchmark”选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用情况，以及每个评估的详细拆分和分析师观察结果。

通过上一个/下一个按钮或方向键进行导航。完成后，点击“提交所有评审”，所有反馈将保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "非常完美，我很喜欢", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。将改进重点放在用户提出了具体意见的测试用例上。

完成后，终止查看器服务器：

```bash

```

## 改进 skill

这是循环的核心。根据路由器选出的证据进行改进：对于 Tier 1，使用权威事实和确定性检查；对于 Tier 2，使用 1–2 个命名的行为回放；对于 Tier 3，使用经过用户审查的成对结果。不要将 Tier 3 的产物或步骤带入较低层级的迭代中。

### 如何思考改进

1. **从反馈中归纳。** 这里发生的事情，从整体上看，是我们正在尝试创建一种可以在许多不同提示中使用上百万次的 skill（也许确实是这样，甚至更多，谁知道呢）。在这里，你和用户反复针对少数几个示例进行迭代，因为这样能更快推进。用户对这些示例了如指掌，也能快速评估新的输出。但如果你和用户共同开发的 skill 只能适用于这些示例，那它就毫无用处。遇到顽固问题时，与其加入琐碎且过拟合的修改，或添加压制性很强的 MUSTs，不如尝试换用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，而且可能会得到非常好的结果。

2. **保持提示精简，但不要删除契约。** 删除那些没有发挥作用的内容，但要把从现有 skill 中删除的每一项都视为潜在回归，直到旧版与新版的审计将其归类为止。将详细但可复用的行为移入直接链接的参考资料中；不要只把它们留在评估、变更日志或你的记忆里。阅读完整的交互记录，而不只是最终输出——如果 skill 导致了无益的工作，就简化指令并重新运行旧的能力用例，不要想当然地认为字数更少就意味着行为更好。

3. **解释为什么。** 尽力解释你要求模型执行每件事背后的 **原因**。如今的 LLM 已经很 *聪明*。它们具备良好的心智理论能力，在拥有良好 harness 的情况下，能够超越机械执行指令，真正促成事情发生。即使用户的反馈简短或带有挫败情绪，也要努力真正理解任务，理解用户为什么写下他们写的内容、他们实际写下了什么，然后将这种理解传达进指令中。如果你发现自己开始用全大写写 ALWAYS 或 NEVER，或者使用非常僵化的结构，这是一个需要警惕的信号——如果可能，重新组织表达并解释原因，让模型理解你要求这件事的重要性。这种方式更人性化，也更强大、更有效。

4. **寻找重复工作——既要查看评估交互记录，也要查看 skill 所提炼自的对话。** 阅读测试运行的交互记录，注意子代理是否都各自独立地编写了相似的辅助脚本，或是否都采用了相同的多步骤方法来处理某件事。如果 3 个测试用例最终都让子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈信号，说明 skill 应该将该脚本打包进去。只需编写一次，将其放入 `scripts/`，并告诉 skill 使用它。这样可以避免每次未来调用都重新发明轮子。同样的信号也隐藏在你提炼 skill 的源对话中——即使某段会话只编写过一次的代码，也是每次未来运行都必须重新编写的代码；不要等到评估运行来证明重复性（跳过评估循环的 skill 不会获得这种证明——创建流程第 4 步中的 Scripts 检查点正是为这些情况设置的捕捉点）。

5. **逐字将修正写回 — 同一会话，两个层级都要写回。** 对于经过品味校准的 skill，用户的修正就是评估集，但前提是这些修正被写入未来运行时会读取的位置。两个属性会让写回过程逐渐收敛：(a) **逐字记录修正**，不要改写或概括 — 确切措辞携带着总结会抹平的校准信号（“绝对禁止这种东西”教会系统一条硬性边界；“用户偏好更少的跳转”则不会）。将原话连同日期一起写入它们所修正的规则中。(b) **在修正发生的同一会话中，同时写回两个层级** — 修复构件，并修复 skill 的规则/参考/组件；只修复构件的修正对每次未来运行都不可见，而推迟到“稍后”处理的修正通常永远不会落地。写回时，检查 skill 自身的文本是否*教会了*刚刚被禁止的反模式 — 修正往往会推翻现有指令，而保留旧建议就必然导致问题复发（真实案例：一个决策页契约建议使用跳转式的“goto 锚点跳到被引用的图”；用户明确禁止了这种做法，因此写回时必须修改原句，而不能只是在旁边添加一条新规则）。当被修正的内容是一个交互片段时，写回的最后一步是将其提升到组件库 — 参见第 4 步中的 Component-shelf 检查。

这项任务非常重要（我们正在努力在这里创造每年数十亿美元的经济价值！），思考时间不是瓶颈；请花时间认真斟酌。我建议先起草一版修订，然后重新审视并进一步改进。请尽最大努力设身处地理解用户想要什么以及他们需要什么。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据留下真正的选择空间时才提问。对于 Tier 2 或 Tier 3，当用户反馈暴露出有意义的设计分歧时，通过 **AskUserQuestion** 提出改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (if the total exceeds 2, reclassify to Tier 3 before running them)
```

### 迭代循环

改进 skill 后：

1. 将改进应用到 skill
2. 只重新运行所选 Tier 的证据：
   - **Tier 1：** 始终重新运行 `quick_validate`、差异检查和迁移门禁；然后只重新运行匹配的子类型证据 — (a) 精确回读/格式检查，(b) 权威事实及其范围狭窄的检查，或 (c) 明确的现有契约及确定性回归。不要创建迭代工作区。
   - **Tier 2：** 只重新运行同一组 1–2 个已命名的带 skill 示例及范围狭窄的检查。不要添加基线、基准测试、查看器或评估工作区；任何对其中之一的请求都会将工作重新分类为 Tier 3。
   - **Tier 3，在仍获授权的情况下：** 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 skill，基线始终是 `without_skill`；对于现有 skill，不可变的原始编辑前版本会在每次迭代中继续作为保留基线。紧邻的上一迭代可以作为补充，但绝不能取代原始基线。
3. 在规则、契约或数字发生实质性变化后，应用纪律 #5。对于通用 Tier 3 路径，还要使用指向上一迭代的 `--previous-workspace` 启动评估审查器；专用工作流使用其声明的审查机制。
4. 对于通用 Tier 3，等待用户审查新的查看器结果；否则，依据所选 Tier 的证据做出判断，除非仍存在真正需要用户选择的事项。
5. 阅读新的证据或反馈；如果它推翻当前版本，则再次改进，并在同一 Tier 上重复执行。

用户请求的取消或降级在任务剩余期间持续有效，且不得改变其分类。除非用户明确重新授权 Tier 3 执行，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

每次**通用 Tier 3**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（所有内容看起来都很好）
- 你没有取得有意义的进展

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某个 skill 的主要机制。创建或改进 skill 后，主动提出优化 description，以提高触发准确率。

### 第 1 步：生成触发评估查询

创建 20 条评估查询，其中混合应触发和不应触发的查询。将其保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实，且应当是 Claude Code 或 Claude.ai 用户实际会输入的内容。不要使用抽象请求，而应具体、明确并包含足够详细的信息。例如文件路径、用户工作或情境背景、列名和值、公司名称、URL 等。有些查询可以使用小写，包含缩写、拼写错误或口语化表达。长度要有所变化，并重点关注边界情况，而不是让查询过于一目了然（用户之后会有机会审核并确认这些查询）。

不好的例子：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的例子：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**的查询（8-10 条），要考虑覆盖范围。应使用相同意图的不同表达方式，其中一些正式，一些口语化。包括用户没有明确提及 skill 或文件类型、但显然需要使用它的情况。加入一些不常见的使用场景，以及该 skill 会与其他 skill 产生竞争但应当由它胜出的情况。

对于 **should-not-trigger** 查询（8-10），最有价值的是那些差一点就会触发的查询，即与该 skill 共享关键词或概念，但实际需要其他功能的查询。可以考虑相邻领域、措辞含糊且朴素的关键词匹配会触发但实际上不应触发的情况，以及查询涉及该 skill 能完成的某些内容，但所处上下文中使用其他工具更合适的情况。

需要避免的关键问题是：不要让 should-not-trigger 查询明显无关。把“编写一个 fibonacci 函数”作为 PDF skill 的负面测试太容易了，无法测试任何东西。负面案例应当真正具有挑战性。

### 第 2 步：与用户一起审查

使用以下 HTML 模板向用户展示 eval 集合供其审查：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → eval 项目的 JSON 数组（不要给它加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 的当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹，查找最新版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的 eval 查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期检查进度。”

将 eval 集合保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（即当前会话所使用的模型），这样触发测试才能匹配用户实际体验。

运行期间，定期查看输出末尾，向用户更新当前迭代次数以及得分情况。

这会自动处理完整的优化循环。它会将 eval 集合拆分为 60% 的训练集和 40% 的保留测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后根据失败情况调用 Claude 提出改进方案。每个新的描述都会在训练集和测试集上重新评估，最多迭代 5 次。完成后，它会在浏览器中打开 HTML 报告，展示每次迭代的结果，并返回包含 `best_description` 的 JSON——该结果根据测试集得分而非训练集得分选出，以避免过拟合。

**如果检测到完全没有触发，循环会在第 1 次迭代后自动中止——你无需手动捕获这种情况。** 这是 `run_loop.py` 中的代码级保护机制，而不只是建议；它可以区分“第 1 次迭代中所有 should-trigger 查询都没有触发”这一现象背后的两种原因：

- `exit_reason: "infra_error: ..."` — 某些查询执行（should-trigger *或* not-should-trigger）抛出了异常（claude CLI 不在 PATH 中、超时时间过短、网络中断），而不是干净地返回“未触发”。该检查会**首先**执行，并且有意在任何非零错误计数时触发，即使几十次运行中只有一次偶发失败也会触发——无论崩溃多么罕见，它都比“没有任何触发”更具体、更具可操作性，而修复方向是环境问题，不是重写描述。消息中的比例（例如 `3/15`）用于判断严重程度：占比较大意味着“停止，修复环境”；如果占比较小，同时有大量干净的 0-trigger 运行，则说明环境可能存在一个值得检查的轻微偶发问题，*并且*描述本身可能确实存在问题——两方面都要检查。无论哪种情况，都要检查 stderr 中是否有 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` — 只有在上面的分支排除了所有执行错误后才会检查这一项，因此这意味着每个 should-trigger *和* not-should-trigger 查询都确实运行了，*但仍然*一次都没有触发（这正是通过零分母默认值实现的“precision=100%”实际含义：不是“完美”，而是“没有可供相除的内容”）。该探针实际上没有测量到任何东西——在完全修改描述之前，先诊断竞争项冲突或低阈值领域（见下文）。

两项检查都**只针对第 1 次迭代**执行，并且**仅当 should-trigger 查询一次都没有触发时**执行——第 1 次迭代较弱但并非零触发（例如 1/9 次触发）是另一种可能恢复的情况，因此会有意留给后续迭代。`degenerate_harness` 还要求 not-should-trigger 查询也一次都没有触发：如果描述只是极性颠倒——漏掉了每个正例，却意外匹配了若干负例——则已经证明探针能够正常工作，`improve_description` 也确实有可用的梯度来采取行动，因此该保护不会中止这种情况（只有探针确实完全失效时才会中止）。同时，它还要求任一侧都没有执行错误——一个抛出异常的 not-should-trigger 查询实际上并未运行，因此不能将其“0 次触发”作为探针失效的证据；这种情况正是应当路由到 `infra_error` 的情况。无论哪种情况，流程都会立即中断，并完全跳过 `improve_description`——JSON 和 HTML 仍会照常报告 `best_description`/`best_score`（不会抑制任何内容），退出原因才是用于表明：本次运行的数值不应被解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了一个完整的 5 次迭代循环；两次完整迭代——每次都是完整的评估批次，耗时数分钟，并调用了几十个 `claude -p` 子进程——都返回了 precision=100%/recall=0%/相同分数，直到有人查看这些数字时才发现问题，而每个 should-trigger *和* not-should-trigger 查询都一次没有触发。仅凭第 1 次迭代就可以诊断出该故障；第 2 次及之后的迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会渲染一个横幅，因此浏览器视图会携带与 JSON/stderr 相同的信号，而不只是存在于那两个可见性较低的渠道中。（该保护的早期草案只检查 should-trigger 触发情况；两轮独立审查——每轮都使用一个全新的代理，第二轮检查第一轮的修复，而不是重复覆盖旧内容——构造出了极性颠倒的反例、基础设施问题与描述问题之间的歧义、负例侧错误的缺口，以及由此暴露的一个既有 `--holdout 0` 报告崩溃问题；这些问题在发布前都已修复。）

这个防护措施无法覆盖一种情况：当使用 `--runs-per-query 1` 时（默认值为 3），一个确实只有约 50% 触发率的应触发查询，可能仅凭随机因素就得到 0/1 的结果，从而因为噪声触发防护措施，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询的所有重复运行结果都为零”成为强信号的原因；如果你将其调低，这个防护措施的误报风险也会随之升高。

**在信任 `best_description` 之前，先对测试工具进行健全性检查——即使上面的两个防护措施都没有触发，它仍可能返回空洞的结果。** 这两项检查只能捕获第 1 次迭代时的*彻底失败*；测试工具也可能在全部 5 次迭代中持续维持微弱但非零的信号，却始终无法触发其中任何一项。如果每次迭代都显示 **召回率在第 1 次迭代之后持续接近 0%，且得分完全相同或近乎相同**，这就说明存在防护措施无法排除的同一个根本问题——“获胜”的描述通常只是第 1 次迭代中未发生变化的噪声。应用任何 `best_description` 之前，先自行运行一个明显应该触发的查询，并确认召回率 > 0。跨迭代保持平坦的召回率意味着测试工具是一个隐藏变量（常见情况是：该 skill 输给了已安装的竞争 skill——见下文的共存）——不要应用它的“最佳”结果；应手动编写描述，并使用真实探针进行验证。（方法论案例 12、14）召回率为 0 还有第二个根本原因，这与输给竞争 skill 不同：该 skill 的任务领域属于*低阈值*领域——模型会自行完成任务，从不查阅任何 skill——这一点会在下文 *How skill triggering works* 的末尾详细说明。在采取行动前，要区分这两种情况，因为修复方式正好相反：竞争 skill 问题通过优先级/取代关系修复，而低阈值领域则应彻底放弃触发探针，改用面向生产环境的评估。

**当你使用 `claude -p` 自行探测触发情况时，要收集运行过程中的所有 skill 调用，而不只是第一次调用——并记住，工具调用只是一个代理指标。** `UserPromptSubmit`/`SessionStart` 钩子可能会在模型做出选择之前注入一个无关的 skill，因此“第一次出现 Skill 调用就退出”的探针会错误地报告“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“该 skill 的内容是否影响了输出”（模型可能读取了该 skill，却没有可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你围绕错误的结论持续优化。

### 技能触发机制的工作原理

理解触发机制有助于设计更好的评估查询。Skills 会以名称和描述出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某个 skill。需要注意的重要一点是，Claude 只会针对自身无法轻松处理的任务查阅 skills——诸如“读取这个 PDF”这样的简单单步查询，即使描述完全匹配，也可能不会触发 skill，因为 Claude 可以使用基本工具直接处理这些任务。当描述匹配时，复杂、多步骤或专门化的查询通常能够可靠地触发 skills——但有一个系统性例外（低阈值任务领域），将在本节末尾说明。

这意味着你的评估查询应当足够实质化，使 Claude 确实能从查阅某个技能中获益。像“读取文件 X”这样的简单查询是糟糕的测试用例，因为无论描述质量如何，它们都不会触发技能。

**但有些技能无法通过这项测试，原因是任何查询改写都无法解决的：该技能的整个*职责*本身就是低门槛任务。** 上一段将问题归咎于查询（“写一个更实质化的查询”）；这里是正交的情况，即技能的*领域*阻碍了触发。如果某项技能的作用是完成 Claude 只需使用基础工具就会自行完成的事情，例如将音频转换为 16 kHz、降采样、提取单个字段、批量重命名，那么即便是完整指定的查询（“将这个 48k 立体声 wav 降采样为用于 whisper 的 16k 单声道”，连路径都给出）也不会触发它：模型会直接使用 `Bash`/`ffmpeg`，从不查阅任何技能。查询是否实质化无法解决这一点，因为“我可以直接完成它”的判断针对的是*任务*，而不是措辞。

不要在优化循环中浪费精力，先诊断这个问题：通过 `claude -p` 运行一个真实的查询，并观察模型在整个运行过程中是否*曾经*查阅该技能（按照上文的 ALL-skill-calls 规则），还是直接转向 `Bash` 并自行完成任务。如果它从未查阅，触发探针在结构上就无法识别这项技能，无论你写什么，召回率读数都会接近 0；这个 0 衡量的是模型“自己动手完成”的本能，而不是你的描述。停止针对 `claude -p` 召回率进行调优，改用真正的验证方式：生产即评估（用户下一次真实的、*交互式*使用，headless `-p` 比真实会话更偏向执行动作，会系统性低报触发情况），再加上当技能产出可检查工件时的输出对比。（曾在一个音频预处理技能上观察到：headless `run_eval` 扫描中，每个查询的召回率都是 0，包括明显的“转录这段录音”查询；手动 `claude -p` 探针显示，模型直接使用 `Bash` 查找并处理文件，整个运行中 `Skill`=0。这个 0 测量的是 headless 的动作偏向，而不是描述；真正的信号只会在交互式使用中出现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新该技能 SKILL.md 的 frontmatter。向用户展示修改前后内容，并报告分数。

## 关键：在源位置编辑技能

**绝不要先编辑已安装的技能副本。** 除非用户明确说明它们是源文件，否则应将以下所有位置视为已安装的运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装副本会导致修改：
- 在缓存刷新时丢失
- 无法同步到源代码控制
- 白白浪费精力，还需要手动重新合并

**始终验证你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，运行源位置检查并说明哪个路径是源目录：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存目录，不要假定该路径就是源目录。请先定位由仓库支持的源目录，编辑该源目录并完成验证，只有在用户需要立即在本地运行时，才同步已安装的副本。

**然后回答决定是否需要“同步已安装副本”的后续问题：运行时是否已经读取源目录？** 三种安装方式的行为不同，猜错会导致不必要的同步，或者提交一个用户下一次会话根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **通过符号链接**指向源目录树 → 编辑本身就是运行时修改。不需要同步。
- **使用 `source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本号更新只是为其他消费者做的记录工作，不是本地激活步骤。
- **任何缓存或复制的安装方式**（来自 git 的 Marketplace、使用 `cp -r` 的安装）→ 运行时使用的是独立副本，在新内容生效前确实需要运行官方更新命令。

**并且要通过内容而不是版本字符串验证激活状态。** 注册表可能记录了一个磁盘上并不存在的路径或版本号——有一次会话读取到的插件记录中写着包含*新*版本号的缓存目录，差点据此报告更新已经生效；但那个目录从未创建，真正的运行时路径一直是指向源目录的符号链接。权威检查方式是对运行时文件执行 grep，查找只有新版本包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库中的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能在你不知情的情况下提交技能 B（甚至是技能 A 较早一轮的修改）。一次真实会话在一小时内同时遇到了以下三种现象——`Write` 因文件在读取后发生变化而被拒绝，以及 HEAD 在任务中途两次移动（方法论案例 16）。失败点不在于发生冲突，而在于使用了过时的基线，或者执行了覆盖写入，导致两个会话的修改被悄无声息地混在一起。固定规则如下：

1. **只要仓库在任务开始时是干净的，就应从 git ref 而不是工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传入 `--baseline-origin git-ref:<sha>`。几分钟前创建的树快照，可能对应一个已经不存在的树，不能作为基线。**解压到一个全新且不存在的目录中。** 解压到现有目录时，`tar -x` 会静默覆盖同名文件，同时保留归档中不存在的文件，形成一个在解压时完全没有信号的混合快照，之后 `compare` 会因其与该 ref 不匹配而拒绝它。另一个命令也有同样的陷阱：`mv <dir> <existing-dir>` 会将目录嵌套进去；如果 `mv` 被别名设置为 `mv -i`，目标已存在时，重命名会打印一行提示并默认不执行，但无论是否执行，退出码都是 0（已通过实验验证）。
2. **如果写入被拒绝，或已经经过了一段时间，就必须在写入前重新读取**：检查发生了什么变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图整合到你的版本中——他们的编辑通常是有原因的——然后再写入。
3. **提交前同时检查 HEAD 以及当前所在的分支。** `git log --oneline -1` 可以发现 SHA 是否发生移动：如果它自基线建立后发生了变化，就要针对新的 ref 重新运行回归 `compare`，然后再执行 `verify`——审计工具本身也会拒绝过时的审查（“after skill changed”），提前发现可以省下一轮。但另一个会话可能做得比推进 HEAD 更糟：**它可能在你进行工作的过程中切换分支**，因为 checkout 会影响整个工作树。真实过程是——你运行 `checkout -b feat/x`，编辑了一段时间；与此同时，另一个会话运行了 `checkout main` + `pull`；之后你的提交就落在了 **main** 上，违反了仓库“绝不能直接提交到本地 main”的规则，而功能分支仍然指向旧基线。因此，提交前检查中要加入 `git branch --show-current`，不能只检查 SHA。如果这种情况已经发生，`git reflog` 是权威的重建依据（它会按顺序记录每次 `checkout: moving from X to Y`），而修复方式是——**在工作树干净的前提下**——执行 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：这两个操作都只是移动 ref，从不会修改工作树，因此不像 `reset --hard` 那样会破坏并行会话尚未提交的工作。
4. **只暂存属于自己的路径**（`git add <skill-dir> <registry-file>`），绝不能使用 `git add .`——另一个会话尚未提交的工作不能被一并带入。（这本来就是打包规则；在并发场景下更是关键。）
5. **每个会话结果只进行一次版本号递增**，而不是每轮编辑递增一次：同一会话对同一技能连续进行的多轮修改应合并为一次递增——除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），此时每个已被使用的状态都应拥有自己的版本号。

## Skill 创建流程（分步说明）

创建或更新 skill 时，请按顺序执行以下步骤。仅当某个步骤明确不适用时才跳过。

### 步骤 0：前置条件检查

在开始任何 skill 工作之前，自动检测所有依赖项，并主动安装缺失项。在工作流程中途才发现缺少工具（例如打包时缺少 gitleaks、验证时缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖项都主动安装，并向用户提供检查清单摘要。只有在所有阻塞性依赖项都满足后，才能继续执行。

主要阻塞项：Python 3、uv、PyYAML（验证/打包）以及 gitleaks（安全扫描）。只有在选定的验证级别实际运行 agent 评估时，claude CLI 才是阻塞项。使用显式的 uv 依赖声明运行 Python 工具，例如从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 依赖环境中已有的 site packages，可能找不到 PyYAML。

### 步骤 1：通过具体示例理解 Skill

仅当 skill 的使用模式已经明确理解时，才跳过此步骤。

要创建有效的 skill，必须清楚理解该 skill 的具体使用示例。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成示例。

例如，在构建 image-editor skill 时，相关问题包括：

- “image-editor skill 应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能提供一些使用此 skill 的示例吗？”
- “用户说什么话时应触发此 skill？”

为避免让用户应接不暇，避免在一条消息中提出过多问题。

### 步骤 2：规划可复用的 Skill 内容

分析每个示例时：

1. 考虑如何从头开始执行该示例
2. 确定 Claude 应拥有多大程度的自由度
3. 确定哪些脚本、参考资料和资源有助于重复执行这些工作流程

**让具体程度匹配任务风险：**
- **高自由度（文本指令）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，但允许合理变化
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 步骤 3：初始化 Skill

如果 skill 已存在，则跳过此步骤。

从头创建新 skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个模板 skill 目录，其中包含正确的 frontmatter、资源目录和示例文件。

### 步骤 4：编辑 Skill

开始编写之前，获取 Anthropic 的最佳实践文档（上方“Skill Creation Best Practice”中提供了链接）以及方法论参考资料——即使你觉得自己已经了解这些内容，也必须执行此操作：文档会更新，训练数据版本会过时，而“我基本了解”恰恰是编辑者跳过这一步并错过最新指导的状态。

编辑时，请记住，该 skill 是为另一个 Claude 实例创建的。重点关注那些对 Claude 有益且不明显的信息。

**Existing-skill migration gate — required before the first edit：**

1. 在编辑前捕获当前完整 bundle。对于非 Git 或存在未提交修改的源代码，使用该工具，以便快照包含可验证的 provenance manifest：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源代码，从选定的 ref 物化目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   包含 SKILL.md、references、scripts、assets、workflows 以及现有 evals，而不仅仅是主提示词。绝不要复制已经编辑过的目录并将其标记为“before”。
   **使用之前没有提取过任何内容的目录**——重复使用一个已经包含内容的目录，会让 `tar -x` 静默覆盖同名文件，同时保留新 archive 中不存在的旧文件，从而生成一个混合快照；提取时不会产生任何提示（`compare` 只能在之后间接通过 tree-hash mismatch 检测到这一点）。参见下方的“Concurrent sessions on the same skill repo”，其中对这一陷阱的完整版本（包括基于 `mv` 的变体）有更详细的说明。
2. 清点旧 skill 的 actor/jobs、trigger contexts、runtime contracts、commands/flags、failure and recovery cases、page/domain variants、bundled resources 以及 eval coverage。在进行结构重写前，为重要的旧版边缘行为补充 preservation cases。
3. 编辑后，生成 old-vs-new review：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，请将最后一个 flag 替换为 `--baseline-origin git-ref:<ref>`。该工具会将 ref 解析为不可变的 commit，并根据该 tree 验证每个包含的文件及其 executable bit。

   **重命名或移动 skill 目录本身**（而不仅是编辑其内容）会改变 `--after` 的路径，而两种 baseline mode 都使用该路径进行 identity 判断——默认情况下，`compare` 会拒绝这种情况（假设 `--before`/`--after` 是误配的），并报告 `pre-edit snapshot source identity does not match the edited skill`。添加 `--renamed-from <old-path>`，以明确声明此次重命名（对于 `snapshot`，该路径是 `--source` 指向的路径；对于 `git-ref:`，该路径是 skill 相对于其 repo root 的旧路径）；identity check 随后会验证该路径，而不是 `--after`。content/tree-hash check 不受影响，因此实际不匹配的配对仍会失败。**请将 `--renamed-from` 作为绝对路径传入。** 该命令接收的每个路径，在以相对路径给出时，都会相对于当前工作目录解析——不是相对于 `--after`，也不是相互相对解析——而 `--renamed-from` 通常指向一个已经不存在的目录（它已被重命名），因此不像 `--before`/`--after` 那样存在 existence check 来捕获错误的解析结果；它只会在更深处以令人困惑的方式失败。尤其是在编辑 skill-creator 自身时，这一点很容易踩坑：上面的 `cd <skill-creator-path>` 位于 skill-creator 自己的 repo 中，而该 repo 通常与正在审计的 skill 所在的 repo *不同*，因此相对的 `--renamed-from` 会静默地相对于错误的 repo 解析。

4. 审查每个候选项。对每个候选项使用且仅使用一个处置结果，并记录具体证据/原因：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移到此 skill 之外时，必须提供负责该能力的目标位置、当前边界证据以及可追溯的用户批准。明确退役也必须引用/追溯用户的批准。关于已保留/已清理/已修复的声明，必须指向当前真实文件及行号，并包含一段简短的 `contains` 引文，使验证者能够在附近找到该内容。文件级候选项必须使用当前文件指纹，并通过一项具名的语义审查说明行为为何得以保留——仅凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本——`classify` 子命令会完成机械性工作（定位目标文件中引文所在的行，填写 evidence/semantic_review，在找不到引文或原因过短时快速失败）。你仍然需要为每个候选项编写处置结果和原因；它只负责将这些内容录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置结果默认为 `preserved_or_moved`；文件级候选项只需要 destination + 40 个以上字符的 reason——指纹会自动为你计算）。**从目标文件中复制 needle（使用 Read/grep/sed），不要凭记忆输入它**——查找采用精确匹配，找不到引文时会快速失败；手动输入的 needle 实际失败的两种情况是全角与半角标点（`：` 与 `:`），以及凭记忆改写的近义字符（`也` 与 `都`）——这两种情况都会绕过自我审查，只有工具拒绝整个映射时才能发现（同一个映射正是因为这两个原因连续被拒绝了两次）。

5. 验证已完成的审查。任何后续编辑都会使审查过期，因为哈希值会发生变化，因此当候选项发生变化时，请重新生成并重新分类。通过验证后会写入 `.skill-regression-reviewed`，这是一个与内容绑定的本地状态凭据。它有助于检测后续编辑，但有意不作为独立的打包授权依据；打包过程本身会再次验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可以识别静默失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在待审核候选项，而不是工具失败；
2 表示调用或运行时失败。该工具能够证明精确迁移和接口保留，但会有意拒绝根据模糊的词语重叠来推断语义等价性。诸如“检查权限被拒绝”之类的通用短语，不能在不作提示的情况下替代精确的“已登录但没有角色”契约。还要检查标记为
`only_outside_runtime` 的候选项：如果运行时行为只存在于 eval、测试或不可达的参考内容中，那么它就不存在于正常调用路径中。

**每次编辑 SKILL.md 后立即验证，不要等到打包时（步骤 7）。** 此检查能够及早捕获真实存在的失败：在 frontmatter 中，未加引号的 YAML 标量描述可以在 Claude Code 的宽松解析器中正常解析，却会在严格解析器中出错（codex 曾报告某个已发布数月的 skill 出现 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中包含 ` #` 时甚至不会报错——它会静默截断其后的全部内容，导致触发关键词消失，而所有扫描仍然显示为通过。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**当描述包含 `: ` 或 ` #`，或跨越多个句子时，请将其写成 YAML 块标量**（使用 `description: >-`，后跟缩进的段落）；块标量原生支持这两个字符——这是自上述事件以来对每个新建或编辑的描述所推荐的约定。

**更新现有 skill 时**：扫描每个现有引用和打包资源，检查是否需要进行相应更新，然后通过上述迁移门禁。迁移契约时，SKILL.md 必须提供直接的运行时指向；eval 或变更日志不能替代它。

接下来的三项检查是**升级探针，而不是无条件扩大范围**。如果采取其中任何一项会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖、权限或外部写入，请先停止，并在修改 skill 之前重新归类为 Tier 3。Tier 1 和 Tier 2 可以检查这些问题，但不会因此获得新的交付物。

**脚本检查**：在宣布编辑完成之前，询问：*源对话（或 eval 转录）编写了哪些代码，而未来的每次调用原本都必须重新编写这些代码？* 当所选层级已经授权进行该能力工作时，将其以参数化、经过清理的形式打包到 `scripts/` 中，并修改文档以指向它。否则，将该信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的附带结果进行打包。分工如下：**脚本负责执行，文档负责理解**——如果一个 skill 的方法只存在于文字说明中，那么每次运行都会再次付出完整的编写成本。之所以将此检查放在编辑步骤中，正是因为跳过 eval 循环的路径（对话提炼、直接编辑）永远不会到达 “Improving the skill” 中 eval 转录版本的此项检查。

**组件货架检查（针对工件中嵌入片段提出的同一问题）**：Scripts 检查涵盖 *skill* 执行的代码；生成工件的 skill（报告页面、演示文稿、文档）还会积累其 *输出* 嵌入的片段——图像覆盖层组件、粘性导航、图表配置、CSS 块。如果连续的输出各自手写了相似的片段，这就是指向另一个货架的同一种重复信号。在添加 `components` 子文件夹或注册表引用之前，应用上述升级规则；Tier 1/2 可以提出建议，但不得创建组件能力。当 Tier 3 获得授权后，使一个代码片段成为货架组件的是围绕它建立的契约：(a) **原样嵌入块** —— 整段复制到工件中的 BEGIN/END 标记，零依赖，使单文件工件保持自包含；(b) **注册表条目**，说明交互契约（触发方式、按键绑定、关闭行为、边界情况）及来源——它来自哪个已交付工件、用户何时批准；(c) **准入门槛** —— 只有用户实际使用并批准的片段才能进入（将已批准语料库原则应用于交互；未经批准但好看的内容不得进入）；(d) **行为冻结，外观可调** —— 已校准的行为和按键绑定构成契约，不得在不同运行之间漂移，而颜色和尺寸可遵循工件的风格；(e) **回写循环** —— 为某个工件发明的片段，应在其获得批准的同一会话中提升到货架。其重要性不仅在于节省 token：手写重写的片段会 *漂移* —— 每次重写都会细微改变按键绑定、关闭行为、计数器——而对于每天阅读这些工件的用户，交互一致性就是产品体验。在用户为第一个此类货架奠定基础时的原话中：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。实际案例（已移除项目指纹）：某报告页面 skill 的 lightbox-gallery 组件（图像覆盖层：←/→ 切换组内项目，ESC 关闭，原位缩放，n/N 计数器）及其 interaction-components 注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击流程测试验证。参见方法论案例 17。

**流水线检查**：考虑此 skill 的输出是否会自然流向另一个 skill，以及是否有现有 skill 应链入此 skill。添加或实质性修改“Next Step”交接或流水线契约，必须在编辑前重新分类为 Tier 3；Tier 1/2 可以提出建议，但不得顺带添加它。

**引用与自我应用检查（谨慎作者仍会遗漏的缺陷）**：一组从内部看来都像已经完成工作、而且无一能通过更努力地重读而被发现的失败模式——每一种都需要一个 *机械性* 操作来替代。（该开头刻意未写数量。“三种失败模式：”是一个派生数字，只要有人追加一个项目就会过时，而统计正文是最难精确捕捉的漂移，恰恰因为它 *不包含发生变化的事物* —— 对列表本身进行重新编号的 grep 和 diff 都会直接略过它。）它们被归为一组，是因为共享同一个原因：**写下一个断言和验证它是不同的模式，单次处理无法同时容纳两者。** 当你正在撰写时，“参见规则 8” *就是* 那个断言；你并没有同时打开规则 8。

与上面的三个升级探针不同，这一个**不**按层级限定，而是按你写的内容限定。一个没有添加指针和规范性规则的 Tier 1 修复在这里无需处理，而且你不必自行判断：推论中的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 给出答案。写了指针或规则，任何层级都一样？那么以下各条均适用。

- **你写下的每个指针，都要在写指针之前打开其目标，并从中复制一行。** 不要说“我确信那条规则列出了全部三个标记”：要将其中一段粘贴出来，放进你已经为此步骤产出的任何内容中（审查备注、提交消息正文、回复），并放在第二位读者日后能将其与目标进行核对的位置。仅仅看过但没有记录的片段，正是本句开头所否定的自我评估。错误的交叉引用在重读时无法被发现，因为错误指针看起来和正确指针完全一样，而作者恰恰是唯一必然会“记得”目标内容的人。真实案例：一位作者写了“see Cardinal rule 3”，本意是指一条关于不要引用过时枚举内容的规则，但被引用文档**自身**的 rule 3 是关于样本量的，实际引用的规则位于另一个文件；遵循该文档既有自引用惯例的读者会落到无关主题上。同一次编辑还发布了一个方向颠倒的指针（材料在上方却写“see below”），以及一个指向不存在章节标题的指针。
- **一个文件中一旦有两个编号列表，裸写的 “rule N” 就具有歧义。** 检查按每个指针进行，而非按每个文件：在写下 “rule N” 前，运行 `grep -n '^N\. ' <file>`，并确认恰好有一个匹配位于你所指的章节；如果有多个，就同时写明章节名称。（**不要**把它变成“这个文件是否包含多个从 1 开始的列表”这样的文件级警报：任何长文档几乎总是如此，因此它会在健康输入上触发并被忽略，而纪律 #6 警告说这比没有检查更糟；在这个文件上运行它，亲自看看。）真实案例中，一个裸写的 “rule 1” 有三个候选列表，自上而下搜索首先命中了错误的那个。
- **写下任何规范性规则后，都要对照它相邻的行进行检查，并让检查产出工件，而非结论。** 使用与下方推论相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的 hunk。在这里自己阅读就足够了，因为你并非在对它进行模式匹配，所以不需要脚本；但必须带上该 ref：裸写的 `git diff` 只显示未暂存的工作，一旦你执行 `git add` 就不会打印任何内容，这正是本块自身推论旨在摆脱的五种静默空输出模式之一。将新规则拆分为独立条款，并为每一条款记录同一 hunk 中满足它的那一行。（下方推论中的 `scripts/reference_net.sh` 做的是另一项工作：它会列出供你解析的*正文交叉引用*。它不会把 hunk 交给你，也不会告诉你规则的某条条款是否得到满足。）**没有相邻对应行的条款就是发现的问题。** 那种诱人的简写方式，即“我的新规则通过了吗？”，对于 30 秒前刚写下它的人而言不可能失败；这正是纪律 #6 所说的，相比自我评估应优先选择可证伪观察，因此本条必须提供它所要求的同类工件。它的首个受害者通常是相邻的段落。真实案例：一条规则被新增为“始终同时报告原始计数和过滤后计数——两者的差异*就是*污染”，但同一提交中的示例只打印了过滤后的数字。同一 diff 中的第二条陈述引用了两个数字，却没有说明它们是否是在相邻新增规则刚刚规定为强制的限定条件下收集的。范围很小且有边界：不是“重读文档”，而是“我 30 秒前写下的规则，是否适用于我 30 秒前写下的行”。
- **为每条新规则提供一行，说明谁来执行它，以及他们是否实际上能够执行。** 现有工具无法满足的规则，会被自认为已遵守的人跳过，这种情况最糟糕，因为它产生了有文档记录的虚假信心。真实案例：一条新规则要求“检查两个日志存储”；项目自己的规范性一命令分诊工具硬编码了其中一个，因此标准工作流恰好会针对该规则本应捕获的故障返回干净结果。这条规则是正确的，却没有作用，也没有提到这个缺口。**使这条要求可证伪的工件**（没有它，本条就成了一个禁止自我评估的块中唯一的自我评估）：写明能够捕获违规的工具或命令，然后**针对你已知它应该捕获的案例运行一次**。如果它在已知错误输入上返回干净结果，你就已测量出该规则没有作用，应将这个缺口写入规则本身。从记忆中回答“他们是否实际上能够执行”，恰恰是纪律 #6 所否定的未经验证的断言。**当没有任何工具能够判定该规则时**，这对大多数正文和品味规则都成立，因此不要把它当作逃生出口，工件就是写明这一点的句子：*"nothing enforces this; it holds only while someone remembers it."* 这比拥有一项通过的检查处境更糟，而明确说出这一点就是目的；执行方式无声的规则会被假定已满足，而非经过验证。请注意本条自身诚实的限制：工具和已知错误案例的选择仍然是判断问题，因此它只是转移了未经验证的步骤，而非消除了它；这比替代方案成本更低，但并非免费。
- **推论——你的修复本身也是缺陷来源，因此在最后一次编辑后，重新检查你触及的区域。** 在一次针对单项变更的两轮审查中，第 1 轮产生了八项发现；第 2 轮又产生了八项，**其中七项是由第 1 轮修复引入的交叉引用错误**。重写一句话会移动其周围的锚点。这也是为什么“它已被审查”并不是读者通过指针导航的工件的终点：你一旦根据审查采取行动，审查就已经过时。重新检查是机械化的，并且它是一个**脚本**，不是需要重新输入的命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的捆绑包中）。它会列出你新增行之间的正文交叉引用，因此你可以打开每个目标并确认它确实表达了你的说法。首次使用前阅读其头部说明：其中解释了为什么它接收一个基础 ref 而非默认使用 `HEAD`，以及它特意**不会**做什么。

**在开始编辑之前获取 `<base-ref>`，不要事后再获取。** 在你开始时将它解析一次为字面量 SHA —— 此刻运行 `BASE=$(git rev-parse HEAD)` —— 并在本条以及上面的项目符号中复用同一个值。如果你运行过现有 skill 迁移门禁，那么它就是你已经完成基线记录的 ref。稍后传入 `HEAD` 才是陷阱：提交之后，`HEAD` 已经包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请恢复该值（使用 `git log`、`git reflog`，或提供给迁移门禁的基线），不要用 `HEAD` 替代；当你的 base ref 同时也是当前 HEAD 时，脚本会打印提示，但不要依赖在那里发现这个问题。

**为什么这里要使用脚本，而本段其余内容都是说明文字。** 这里所替换的一行命令经历了五轮补丁 —— 将 diff 锚定到正确的 base、查看已暂存的编辑、在提交后继续工作、跳过 diff 自带的 `+++` header、移除误导性的 `-n` —— 其中四轮都增加了另一种让它不输出任何内容并以 0 退出的方式，而这与“我检查过了，内容是干净的”无法区分。第五轮则是同一种问题的另一种表现：它移除的 `-n` 原本会输出带行号的真实匹配项，但行号是按经过管道传输的内容计数的，因此这些结果看起来很权威，实际却指向不存在的位置 —— 这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都会持续发布它本应捕获的缺陷。说明文字无法验证自己的输入，无法说明究竟发生了哪种结果，也无法接受测试；脚本三者都能做到，而且它的契约是：**每一种结果都必须被明确命名，错误输入必须明确失败**。这就是同一步骤前面提到的 Scripts 检查在本段中的应用 —— 而这五轮补丁正是忽略该检查的代价。

**读取它的判定，而不只是退出码。** 脚本只要成功运行就会以 0 退出，因此单独查看 `$?` 无法告诉你它发现了什么；答案在判定行中，并且它始终会明确说明以下情况之一：找到引用（逐一解析）、文件与 base 完全相同、文件相对于 base 发生了变化但没有新增行，或新增行中没有任何类似引用的内容。这些是不同的结果，脚本特意将它们区分开来 —— 这个检查曾将它们合并成一个无声的“没有任何内容”，正是因此才改成了脚本。它只需几秒钟，并且不依赖警觉性，而这正是纪律 #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的指针 —— “请参见下面的章节”、“正如上面的规则所述” —— 因此也要阅读新增的行。）

### 第 5 步：清理审查（任何公开 skill 都必须执行）

**在执行此门禁之前，当纪律 #5 到期时，其独立检查必须已经运行**，并且当前变更对应的 `independent-review.md`（位于你的私有、由 git 跟踪的知识仓库中 —— 不在已清空的工作区中，也不在任何已经公开或可能公开、或可能被分发的仓库中）必须存在**并且已经提交**。对于新的 skill，它始终适用；对于现有 skill，使用下一段中的阈值。一个未提交、仅位于 git 工作目录中的文件，与一个从未写入的文件没有实质区别；`ls`/`test -f` 能确认它在磁盘上，而不能确认它能够保留下来。对于**新的** skill，这是任何内容离开你掌控范围的第一步，因此也是实际执行该纪律的地方，而不只是陈述该纪律 —— 一条位于使用点上方 1000 行、没有任何检查机制的规则，每次都会输给追求完成任务的冲动。

**对于已发布技能的编辑，离开你手中的时刻是推送，而不是这一步。** 这个关卡可以用一句“仅内部使用，跳过”来回答，而纯文档变更甚至可能完全不运行打包流程，因此将评审锚定在这里意味着，某项技能编辑可能在未经过任何独立审阅的情况下抵达公共分支。真实案例（2026-07）：对这个文件本身的一项修改发布了一个发现命令，该命令无法到达旁边文字声称其覆盖的三个根目录；它被合并了，只有在*事后*委托的一次评审才发现这个问题。**因此，对于现有技能：独立审查及其记录的产物必须在 `git push` / 打开 PR 之前完成——在推送时运行的关卡（回归审计、验证、扫描）都只检查结构，无法判断说明是否错误。** 这继承了纪律 #5 的原有阈值：当*规则、契约或数字发生变化*时才需要，不适用于错别字或纯格式调整。让拼写修复也等待一轮评审，会培养出纪律 #6 警告的那种反射——“这次很小”会变成通用豁免，随后也会覆盖那些真正重要的变更。

**对于将进入公共仓库的技能，这不是可选项。** 私有内容经常泄漏到公共技能中，而扫描器遗漏的泄漏才是危险的——非英语语言中的真实姓名、真实记录中的逐字一句、被放进示例说明中的真实示例。只有当技能确实仅供内部使用时才跳过。

**按目标位置而非主题界定审查范围。** 只有会公开发布的产物——技能包本身——需要脱敏。保留在私有仓库中的配套文档（技能提炼自的事故报告、内部运行手册、项目的 CLAUDE.md）应保留其真实主机名、路径和时间戳：对这些内容脱敏会破坏其审计价值，而你最终会将其还原。有一次提炼会经历了三轮返工，正是因为脱敏审查被应用到了源材料涉及的所有内容，而不只是公共技能。

**先检查目标位置，并让它预先填入建议。** 在技能将要存放的仓库中运行
`gh repo view --json isPrivate`（或读取
`quick_validate` 已经打印的提示）。私有目标位置应使选项 C 成为默认
建议，而不是事后补充——“除非另有说明，否则假定公开”会把私有技能中正常可用的路径变成没人要求的占位符。

**是否触发脱敏取决于目标位置的 `isPrivate`，而不是任务看起来有多像发布。** 这两者可能不一致；而一旦不一致，若不明确指出，直觉感受就会占上风。将内容*迁入 marketplace skill* 会让人感觉像是在发布——市场是内容分发的地方——因此即使源和目标都是私有仓库、且没有任何内容会流向外部，脱敏反射仍会触发。真实案例（2026-07）：一次从项目级技能迁移到私有 marketplace skill 的操作，将真实配置路径、真实十六进制值和真实具名示例泛化为
占位符。`quick_validate` 在**每一次**运行中都打印了 `🔒 audience: private`；
作者每次都看到了它，却仍然进行了脱敏，因为这项*活动*读起来像是
发布。代价并不只是外观问题——真实路径能让下一位读者核查该值；“项目自己的令牌文件”则无法被打开。

所以要把它当作查询，而不是判断：**读取目标位置的 `isPrivate`，如果它是
`true`，则进行清理需要所有者提出请求。** private→private 的移动就是移动，不是发布。
**当两个探测都没有返回结果时**（尚未连接远程仓库，也没有运行 `quick_validate`），你没有
可用的查询结果——应回退为将其视为公开，并明确说明这一点，因为不对称性决定了应当如此：
一次不必要的提问只会多占用一句话，而一次不必要的信息泄露则无法挽回。而且 `isPrivate`
报告的是目标位置**今天**的状态——一个位于私有仓库中、正准备发布的 skill，应当在发布它的
push 上进行清理，而不是在这一次进行。如果你发现自己开始推理某项内容在私有目标位置中是否
“应该”被泛化，这种推理本身就是信号。

使用 **AskUserQuestion** 确认深度（对于公开目标，确认深度，而不是是否执行；对于私有目标，
确认是否需要执行）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**清理流程——通读是方法，扫描只是辅助：**

1. **亲自完整阅读整个 skill，并进行语义判断**（这是实际检查）：SKILL.md + 每个 reference + 每个
   example。对于每个具体名词 / 示例 / 代码片段，询问“这是通用占位符或公开实体，还是从真实项目 /
   人员 / 对话记录中摘取的？”替换后者——即使扫描器没有将其标记出来。这是唯一能够捕获没有关键词
   泄露的方法。完整指导以及语义问题见
   [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器作为廉价的第一轮检查**：使用 checklist 中的 grep 模式 + `security_scan.py`
   （第 6 步）。它们可以快速发现明显的密钥 / 路径 / 已知名称——但“没有匹配项”并不等于通过。
3. **替换**每个发现的问题，使用保留教学要点的通用等价内容（真实姓名 → 公众人物或
   `<placeholder>`，真实代码片段 → `<placeholder>`）。有两条从实践中得出的规则：占位符本身不能编码
   真实值——`<acme-corp-domain>` 会准确泄露它本应隐藏的名称；应改为使用角色名称
   （`<api-domain>`、`<upstream-provider>`）。此外，当你编写批量替换脚本时，应为其指定限定在
   skill 目录内的显式文件白名单——未限定范围的查找替换会毫不犹豫地改写项目自己的 CLAUDE.md，
   并迫使你执行 git restore。
4. **通过重新阅读而不是重新 grep 来验证**：重新阅读变更的部分，并确认没有损坏的引用。

### 第 6 步：安全审查

在打包或分发 skill 之前，运行安全扫描器以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）

**它不覆盖的内容** — 这也是为什么仍然需要完成第 5 步的通读检查：gitleaks 和正则规则只会匹配你列出的*已知机密格式和模式*。对于没有关键词的私密内容，它们在结构上无法识别 — 非英语语言中的真实人物/项目名称、真实对话记录中的逐字内容、从你自己的工作中直接摘取的真实示例。`security_scan` 显示绿色意味着“未发现已知格式的机密信息”，**而不是**“该 skill 已完成清理”。绝不能将其视为后者。

**首次设置：**如果尚未安装 gitleaks，请安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 清理完成（可安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前**必须**修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**在私有 skill 中，发现项是信息，而不是待办事项。**扫描器无法区分泄露的凭据和本应存在于其中的凭据 — 一个其全部价值就在于预先填充好的模板，或一个指向其运行所在的唯一机器的脚本。切勿在私有仓库中自动修复：报告发现的内容，由所有者决定如何处理。下面的选项 A（“自动修复”）适用于计划公开发布的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包 Skill

skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个现有的 Git 跟踪 skill，必须先提供并重新验证已完成的审查，才能进行打包。当前标记只是本地状态凭据，因此先提交或手写标记都无法绕过审查。下一次编辑后，审查将变为过期状态：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选输出目录，以及使用 `--include-evals` 将根目录下的 `evals/` 目录一并打包（默认排除，因为它属于开发资源）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **重新验证已完成的现有 skill 回归审查**（只要 Git HEAD 中已经包含该 skill）；单独的标记永远不能授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描一致）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 第 8 步：更新 Marketplace

打包后，更新 Marketplace 注册表，以包含新技能或已更新的技能。

**对于新技能**，在 `.claude-plugin/marketplace.json` 中添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于已更新的技能**，按照 semver 规则递增 `plugins[].version`。对技能文件的任何更改——即使只是修复一处拼写错误——都需要递增版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧技能，而你的修复则一直处于未发布状态。

**然后将其记录在变更日志中——这正是经常被跳过的一步。**版本号递增让更新变得*可安装*；变更日志条目则让它在六个月后、有人遇到相同问题并搜索相关记录时，仍然*可查找*。如果变更日志记录了其他每个技能的版本，却悄悄漏掉你的技能，那还不如完全没有变更日志：这些空白会被理解为“那里什么都没改”。

参照现有条目的格式，不要自行发明格式——在 Keep-a-Changelog 文件中，通常写成 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。

请在与版本号递增**相同的提交**中写入变更日志；“稍后”更新的变更日志，最终往往就是永远不会更新的变更日志。

真实案例（2026-08）：某个技能连续发布了两个版本，版本号递增正确、门禁检查通过、PR 也已合并——但**完全没有变更日志条目**，因为这套流程中没有任何步骤要求添加变更日志。两个版本最终都是在之后的审计中才被发现。这正是纪律 #6 在这个文件自身上的体现：如果一条规则只存在于约定中，而不是存在于步骤中，那么它每次都会输给“赶紧完成”的驱动力。

**保持注册表 diff 最小——这是所有技能共用的唯一文件。** Marketplace 清单是所有并行编辑者都会发生冲突的地方，因此其中无关的格式变更，比其他任何地方的同类变更代价都高得多：它会把原本干净的三行版本号更新变成其他编辑者正在修改时必须处理的冲突。如果你通过脚本更新文件（解析为 JSON、修改后再写回），重写过程可能会悄悄规范化原文件未必采用的格式——末尾换行、缩进宽度、键顺序、Unicode 转义。往返处理纪律：之后重新读取文件，并对该文件运行 `git diff --stat`；**唯一可以出现的行必须是你有意修改的字段。**如果出现额外行，应恢复文件原本的约定格式，而不是提交这种规范化结果（曾有一次脚本更新给一个原本从未包含末尾换行的清单添加了末尾换行——只多出一行无谓的 diff，而且还是在最可能被其他人同时编辑的文件中）。同样的原则也适用于技能涉及的任何共享注册表：锁文件、目录、索引文档。

**当 PR 经历了几次合并仍未结束时，执行 rebase——然后证明你没有吞掉任何人的工作。**正是因为清单容易发生冲突，它也最容易过时：一个修改了注册表和变更日志的开放 PR，只要其他改动合入就会发生冲突，因此应预期出现 `mergeable: CONFLICTING`，不要把它当成意外（曾有一个 PR 在主分支一个下午前进了 7 个提交后遇到这种情况）。如果仓库采用 squash merge，应执行 rebase 而不是 merge——在压缩后的历史中，合并提交没有任何收益。冲突本身几乎总是**增量式的**：两位作者分别在同一部分追加了自己的条目，因此解决冲突时应**保留双方内容**，绝不要使用 `--ours`/`--theirs`，因为这会悄悄丢弃同事添加的那一行。

人们会跳过的步骤，往往正是能发现错误解决的步骤——**解决后，确认与基线之间唯一的差异就是你自己的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要使用裸的 `--force`：如果远端自你上次获取以来发生了变化，租约会让推送失败；这正是有人向你的分支推送过，而普通强制推送会将其改动抹掉的情况。

**插件边界不属于本 skill 的职责范围。** 是否应将 skill 拆分为
独立插件、如何布局 `source`/`skills`，以及用户是否可以单独切换
skill，都属于打包/分发领域——SSOT 是 `marketplace-dev` skill，而不是本 skill。
当任务确实需要这些决策时：
确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与
`skill-reviewer` 需要其脚本时拉取 `skill-creator` 相同），然后阅读
marketplace-dev 的 cache-and-source-patterns 参考并遵循其中的规则。不要在此处重复
它的规则；复制一份会逐渐偏离。

**重命名、迁移或删除 marketplace 条目，对于所有已经安装该条目的用户来说都是破坏性变更**——
Claude Code 不会在条目消失时清理已安装的副本，导致悬空安装，并在每次
`marketplace update` 时出错。将此类变更视为 API 弃用：在变更日志中发布迁移说明，并遵循 marketplace-dev
关于具体操作的指导。

**如果你亲自提交/推送 skill 仓库：** 对于现有 skill，如果当前变更触及纪律 #5 的规则/契约/数字阈值，请确认评审产物记录了这项变更，并且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不只是确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的评审永远不能满足当前的实质性变更。第 5 步的说明解释了为什么对于已经发布的 skill，真正的强制检查点是推送，而不是打包。然后只暂存 skill 的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充满无关的变更，否则它们会被一并带入提交（曾有一次提交混入了一堆无关的 transcript 文件，后来不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库实际的可见性，不要根据路径想当然——一个公开的 skill 仓库应当走 PR + 评审流程，而不是直接推送到 main。

### 步骤 9：发布或迭代

完成 skill 后，使用 **AskUserQuestion** 确定下一步：

```
Skill "[name]" 已完成。安全扫描通过，市场已更新。

建议：基于当前状态选择 [例如：如果从未验证过触发效果，则选择 "B) 优化描述"，否则选择 "D) 暂时完成"]，因为[一行原因]。

选项：
A) 打包并导出为 .skill 文件以供分发
B) 运行描述优化 — 提高自动触发的准确性（约 5 分钟）
C) 扩展测试集并继续迭代 — 在发布前添加边界情况
D) 暂时完成 — 我会手动测试，如有需要再回来
```

测试 skill 后，用户可能会要求改进。通常这会发生在刚使用完 skill 之后，此时用户对 skill 的表现仍有清晰的上下文记忆。

**优化筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经覆盖了相关内容，则不要重复添加。

## Claude.ai 专属说明

在 Claude.ai 中，使用相同的验证深度路由器。当选择通用的 Tier 3 路径时，完整流程仍然是起草 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子代理，需要对部分机制进行调整：

**运行测试用例**：由于没有子代理，无法并行执行。对于每个测试用例，读取 skill 的 SKILL.md，然后亲自遵循其中的说明来完成测试提示。一次执行一个测试用例。这种方式不如使用独立子代理严格（你编写了 skill，同时也在运行它，因此拥有完整上下文），但它仍然是有用的合理性检查，而人工审查步骤可以弥补这一点。跳过基线运行 — 直接使用 skill 按要求完成任务即可。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或者你正在远程服务器上），则完全跳过浏览器审查环节。改为直接在对话中展示结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），将其保存到文件系统，并告知用户文件位置，以便他们下载和检查。直接询问反馈："效果如何？有什么需要修改的吗？"

**基准测试**：跳过量化基准测试 — 它依赖基线比较，而在没有子代理的情况下，这些比较没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同 — 改进 skill，重新运行测试用例，询问反馈 — 只是中间不再加入浏览器审查环节。如果有文件系统可用，仍然可以将结果整理到迭代目录中。

**描述优化**：本节需要使用 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要使用子代理。请跳过本节。

**打包**：`package_skill.py` 脚本只要有 Python 和文件系统即可在任何环境中运行。在 Claude.ai 中，你可以运行它，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新的 skill。在这种情况下：
  - **保留原始名称。** 注意 skill 的目录名称和 `name` frontmatter 字段，并保持不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前复制到可写位置。** 已安装的 skill 路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从副本进行编辑和打包。不要传递 `--new-skill`；非 Git 副本中的现有 skill 仍然是现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再复制到输出目录 — 直接写入可能会因权限问题而失败。

## Cowork 专属说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此通用 Tier 3 工作流（并行生成测试用例、运行基线、评分等）适用。不要将子代理可用性视为需要升级 Tier 1 或 Tier 2 变更的理由。（如果 Tier 3 运行遇到严重超时，可以按顺序运行测试提示词，而不是并行运行。）
- 你没有浏览器或显示器，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不要启动服务器。然后提供一个用户可以点击、在浏览器中打开的链接。
- 在完成**通用 Tier 3**运行后，在你自行修改 skill 之前，始终使用 `generate_review.py` 为用户生成评估查看器，而不是自定义 HTML。Tier 1、Tier 2 以及明确替代查看器机制的专用工作流，不会仅仅因为工作发生在 Cowork 中就产生查看器义务。
- 反馈机制有所不同：由于没有运行中的服务器，查看器中的“提交所有评审”按钮会将 `feedback.json` 文件下载到本地。随后你可以读取该文件（可能需要先请求访问权限）。
- 打包功能可用 — `package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该也能正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，但请将其留到 skill 完全制作完成并且用户确认状态良好之后再进行。
- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新的 skill。请遵循上方 Claude.ai 部分中的更新指南。

这里再重复一遍核心循环，以示强调：

- 弄清楚 skill 的用途
- 对于现有 skill，在编辑前对旧 bundle 进行快照和清点
- 选择能够在执行任何专用工作流退出操作前证伪此次变更的最低验证层级，并记录原因
- 起草或编辑 skill
- 运行该层级所需的证据收集流程，或运行所选专用工作流声明的等效机制
- 对于通用 Tier 3，与用户一起评估成对输出，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复上述步骤，直到你和用户都满意
- 运行并通过现有 skill 回归审查；仅在评估中存活不算通过
- 打包最终 skill 并将其返回给用户。
