# Skill 创建器

用于创建新 skill 并对其进行迭代改进的 skill。

从高层次来看，创建 skill 的流程如下：

- 确定你希望 skill 实现什么，以及大致应如何实现
- 将变更归类到能够证伪其可能失败模式的最低验证层级
- 编写 skill 草稿
- 使用能够证伪变更后行为的最小证据进行验证；将完整的配对评估流程视为需要单独授权的工作，而不是某个层级标签所自动带来的后果
- 当所选层级产生定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写 skill（如果定量基准测试暴露出任何明显缺陷，也要进行重写）
- 重复上述过程，直到你满意为止
- 仅当当前证据无法解决变更后的行为时，才提升验证层级

使用此 skill 时，你的任务是判断用户目前处于这一流程的哪个阶段，然后介入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一种能力，而不是每次编辑都必须承担的成本。"优化"、"改进"或"全面"等词描述的是意图，而不是失败面或评估预算。不要仅仅因为任务听起来范围很广，或因为之前进行了长时间的对话，就创建评估文件、派生配对 agent、为输出评分或启动查看器。

以下六项贯穿始终的规范必须遵守，因为这些失败模式会产出看似令人信服、实则错误的 skill：

1. **先验证，再编写。** 进入 skill 的每一项技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的结果——无论是在本次会话中，还是在获得明确批准的挖掘会话中。如果现在无法验证，要么去验证，要么明确标注（"未经验证——来自记忆"）。skill 会放大其中包含的一切：经过验证的知识会不断积累，充满自信地陈述的错误也会如此。对于知识型 skill（内容主要是关于外部系统的事实，例如 API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作层面的要求：权威层级（观察到的行为 > 机器可读的契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前的文档示例 smoke run，以及受众/Windows 可移植性检查清单。一次来源依据审计发现，多个看似自信的契约断言与作者已经掌握的证据相矛盾（方法论案例 9）。
2. **将"不可能 / 不支持"视为假设，而不是结论。** 当某项能力似乎受阻时（API 错误拦截、工具无法连接、格式无法打开），在将"平台不支持此功能"写入 skill 之前，要穷尽各种观察路径——UI 自身的网络流量、替代通道、不同的文档化标识符。观察到的行为优先于推测性的请求形式。
3. **站在该领域已有成果的肩膀上——在默认情况下、在编写或优化 skill 的方法论之前，将该领域已经确立的最佳实践检索到上下文中。** skill 的方法论质量取决于上下文窗口中的知识，而不是隐藏在模型权重中的知识：预训练知识是不完整的、会过时，而且如果没有实际拉取权威来源，往往根本不会被激活。因此，你所写内容的质量上限是 `你的训练数据 + 用户输入`——*除非*你主动检索该主题领域真正已有的成果。这样做：WebSearch 该领域的经典理论 / 标准 / 方法，并阅读该领域中随附或已安装的 skill，然后将其中承载核心作用的原则连同出处纳入 skill。**这与下面的"前人成果研究"是不同的维度**——后者用于寻找可复用的工具/基础设施；前者则是让方法论本身建立在该学科积累的科学成果之上。将其作为**默认操作，而不是等待用户提出要求**：简要告知用户你正在参考哪个领域的成果，并让用户可以说"跳过"，但绝不要在距离公开领域成果仅有一次搜索之遥时，仍让方法论受限于你的记忆加上用户的提示。示例：数据可视化 skill 必须吸收 Cleveland & McGill 的图形感知排序以及 Bertin 的视觉变量（位置/长度优于颜色，颜色优于文本——这是经过测量的结论，而非审美判断）；日期/时间 skill 必须介绍成熟的库及其经典陷阱；说服/谈判 skill 必须检索已经确立的框架，而不是凭记忆重新发明。若经典知识只存在于你的权重中、从未进入上下文，那么你就是在本可引用时进行猜测。
4. **在压缩现有 skill 之前，先保留它。** 更新现有 skill 是一次迁移，而不是从空白页面开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧 bundle，或从明确的 Git ref 重建它；任意复制并附加来源标签不能算作基线。盘点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和简洁性允许移动或去重内容；它们不允许你悄无声息地删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个无法匹配的旧单元进行分类。一个仅存在于 `evals/`、测试或未链接参考资料中的运行时契约，仍然属于丢失。只要仍有候选项未分类，或仍存在真正的缺口，就不要称此次更新已经完成。同样的逻辑也适用于**逆转**，而不仅是删除，并且涵盖任何此前作出的承诺——不仅是那些带有日期和名称的承诺：**推翻已经作出的决定必须是一项提案，绝不能成为副作用。** 要明确说出来并获得接受。悄无声息的重写比悄无声息的删除更糟，因为它会一次性摧毁产物以及本可以发现问题的证据——同时蒙蔽所有下游审阅者（见 #5）。

**在编辑前为每个预期变更分类；“压缩”指的是行为等价这一主张，而不是“更短”的同义词。** 对于每个旧有用户场景，新鲜上下文中的 agent 仍必须能够找到触发条件、决策输入、受支持的操作、停止/确认点、影响/恢复边界以及验证路径。在计划、评审和变更日志中，将这些名称作为独立的变更类型标签；在每个回归候选项的 reason/semantic review 中记录该标签，同时将审计工具的 `disposition` 字段保持为完全匹配 Step 4 的枚举值：

   | 变更类型 | 定义 | 必需处理 |
   |---|---|---|
   | **无损压缩** | 仅改变表达形式：将细节移入可直接访问的捆绑引用中、相对于随包提供的规范来源进行去重，或缩短措辞，同时保留上述每一项运行时契约 | 可以称为压缩；证明场景可达性，而不只是证明字符串仍然存在 |
   | **能力退役** | 之前可以执行的任务或操作不再可用 | 不是压缩；指明已退役的能力，取得可追溯的用户批准，并发布边界 |
   | **范围收窄 / 边界变更** | 仍受支持的输入、目标、环境或模式减少；某个执行分支变为仅分析 | 不是压缩，即使这样更安全；明确并发布边界/权衡，然后取得可追溯的批准，除非用户已经明确要求进行这一次精确的范围收窄 |
   | **工作流或安全性重新设计** | 命令、顺序、确认、副作用、恢复或成功检查发生实质性变化 | 不是压缩；明确新的契约和权衡，取得可追溯的批准，除非用户已经明确要求进行这一次精确的重新设计，然后独立于保留性验证来验证它 |
   | **错误修复 / 事实更正** | 将实现或正文恢复到某个明确的既有契约或当前权威来源 | 不是压缩；使用能够裁定该问题的最小范围权威来源或确定性回归 |
   | **有损总结** | 精确条件、命令、决策语义或执行退出点消失，且没有运行时可达的等价内容 | 是回归问题，而非优化；恢复它，或通过上方某一经批准的行重新分类 |

   只有当规范来源随 skill 一起提供，或能够可靠地获得，并且 SKILL.md 告知运行时阅读者何时加载该来源时，去重才算无损。“这个想法仍然存在于测试、变更日志、已安装的同类 skill 或作者的记忆中”不属于压缩。如果一个补丁包含多种类型，分别列出；绝不要让压缩标签掩盖退役或重新设计。

5. **任何内容都不能仅凭自我评审发布——独立的、基于新鲜上下文的对抗性检查是固定步骤，而不是特殊情况。** 你“现在已经没问题了”的判断，使用的是生成该产物的同一个模型，因此共享导致缺陷产生的全部盲点。相关结论有实证而非传闻：没有外部反馈时，内在自我纠正并不能可靠地改善输出，有时还会使输出变差（Huang 等，ICLR 2024）；当生成器和评估器共享错误模式时，反复迭代会**提高信心，却不会增加信息**。更多自检无法逃离这一点；只有外部视角可以。**完整流程——包括提示模板、锚点选择、发现项表格和示例案例——位于 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在第一次检查前先阅读它。** 以下是承重规则：
   - **独立性有两个方面，而第二个方面正是作者容易遗漏的。** *评审者的上下文*不能是你的分支——分支会继承你的盲点，并返回一个“已评审”印章。但它所依据的*证据*也必须位于变更的**影响范围之外**，否则它会继承你的**结论**：它读取一个产物和一个已经与之达成一致的规范，然后报告二者一致。注意，“本会话未编辑”这一界线太弱——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，三个评审者都对一个他们在未被触碰的副本中发现过的缺陷视而不见。按照你不太可能触碰过的程度为锚点排序：用户自己的逐字记录 > 工作开始前的 git ref（`git log --oneline <ref>..HEAD -- <path>`；你的任何提交都会使其失效）> 只追加日志（这是一种约定，而非强制机制）。**Greenfield 没有锚点——请说明这一点并要求提供锚点，不要报告一个你没有执行过的通过结果。**
   - **只向评审者提供两个承载证据的输入：不可变产物和读者规范。** 同时提供用于限定检查范围、但不承载证据的控制元数据：当前变更的影响范围、明确命名的失败轴以及终止条件。不要提供设计理由、项目背景或“只要确认 X 没问题”之类的内容——这些会把独立评审者变成橡皮图章。读者规范和控制元数据说明由谁执行什么以及在哪里停止；它们不能告诉评审者实现是正确的。**对于 SKILL.md，读者就是另一个执行它的 agent**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——应询问它哪些指令是它无法执行的。在分派前冻结全部五个字段，绝不要使用事后补充的上下文来解释掉发现项。
   - **对于可理解性以及相对于语料库的完整性，它是事实依据；对于品味，它没有权威。** 直接应用前两者。将“这可能是一个 bug / 我建议 Y”视为假设，先由你自己复现。绝不要委托 AI 垃圾内容或审美判断——这是同一模型的盲点。
   - **枚举失败的*轴*，而不是内容领域——这也决定运行多少个评审者。** 轴是*你提出的问题*；领域是*你阅读的材料*。三个评审者分别覆盖场景、算术和 diff，但都在问“这是否连贯”，那只是把一个评审者计费了三次。**一个评审者是默认配置，而且通常已经足够**；只有在增加额外轴时才增加评审者。自我评审最不擅长的轴是**保真度**——“这是否仍然忠实于已经作出的承诺？”——因为移动承诺的人正是作者，而连贯性和保真度彼此正交：一个产物可以完全自洽，却完全不忠实于已经决定的内容。
   - **在分派前冻结评审边界，并在满足该边界后停止。** 记录不可变产物/ref、读者规范、当前变更的影响范围、明确命名的失败轴以及终止条件。当发现项是由当前变更导致、扩大了影响范围、新近宣传了受影响的行为，或使旧有矛盾通过被编辑的路径变得可达时，它会阻止本次发布。一个未发生变化且未被新承诺的既有缺陷，是独立的待办假设，不会自动授权你重新设计 skill。在实质性修复后，由新的评审者重新检查失败的轴以及回归；它不会重新开启无边界的全 skill 审计。完整的决策流程和示例见：[references/independent-review-protocol.md](references/independent-review-protocol.md)。
   - **留下产物，否则这只是一条警告。** 纪律 #6 规定，产生观点的检查不如产生产物的检查——因此这一项也要生成文件，否则恰恰在最重要的时候，它会输给完成驱动。将 `independent-review.md` 写入你的私有、受 git 跟踪的知识库中的 `skill-reviews/<skill-name>/`：其中必须包含**逐字记录的评审者提示**（这样后续读者可以判断它是否具有引导性）、**每个发现项及其 disposition 和 reason**（这正是合法筛选与丢弃不利内容之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识库（或你没有私有知识库），请说明这一点并询问用户——不要猜测一个最终会落入任一禁区的位置。两个禁区：**不得位于 `<skill-name>-workspace/` 中**（会被 gitignore 的临时目录会被清除——该文件是跨会话的评审证据，必须在这些目录之外存活），**也不得位于任何已经公开或可能公开、发布的仓库中**——这通常意味着被评审 skill 自己的仓库也不行（评审内容本身会引用私有路径、真实姓名和项目细节）。在实质性编辑后，用一个*新的* agent 重新评审——实质性编辑指规则、契约或数字发生了变化，而不是错别字。从 Step 5 开始，该文件就是检查确实发生过的证据；没有它就意味着检查没有发生。**写入文件不等于下一会话中它仍然存在——在同一轮中对该私有仓库执行 `git add` + `git commit`。** 一个未提交、躺在 git 工作目录中的文件不具备这条规则所要求的任何“受 git 跟踪”保证：它可能丢失、被覆盖，或者后续检查“是否已评审”的流程根本不会获取它（真实案例：文件被正确写入正确路径，也包含真实发现项——但后续自动检查仍然失败，因为它从未被提交；修复方式只是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械性的，并且与此互补：它证明你没有*删除*行为。它完全不能说明你写出的内容实际上是否可遵循。

6. **设计你编写的检查，使其无法自行认证为绿色通过。** 技能主要由各种检查组成——门禁、检查清单、“发布前”步骤——而一个执行上下文可以在*违反其所编码的规则本身*的情况下通过的检查，比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴了那些早已解决这一问题的领域：
   - **验证必须覆盖其规则中的每一条要求。** 如果规则写的是“A + B + C”，证据就必须分别要求证明 A、B 和 C。附加在三条款规则上的一行确认语句，只会被作者已经完成的那一条满足；其他条款则完全不可见。真实案例：一个报告编写技能带有一道交付门禁，其规则写的是“选项以并排的 chips 呈现 + 推荐项突出显示 + **背景信息以完整、自洽、陌生人也能理解的句子写出**”——但其下的证据行只要求“N 个决策项，全部渲染为 chips”。作者运行了门禁，写下这条证据，自行认证为绿色通过，并交付了一个标签只有单个字符、所有上下文都被删除的页面。规则始终存在于文件中；只是检查从未度量那条要求。
   - **对健康输入产生误报的检查，比没有检查更糟。** 上述问题是检查在应该失败时通过；这里则是它的镜像——检查在应该通过时失败。后者代价更高，因为它会教会操作员条件反射式地绕过检查（`--no-verify`、`SKIP=1`、`--force`），而一旦这种条件反射形成，门禁就会对*所有*输入失效，包括那些原本正是为其构建的输入。因此，在编写 fail-closed 检查时，**误报的优先级高于漏报**：漏掉一个真实问题只会让你失去这一实例，而误杀一个健康输入则会让整个门禁失效。
     留意这个信号：**反复踩中同一个陷阱所产生的挫败感，本身就是风险信号**——作者正是在这种状态下，最容易交付一个从未使用健康输入进行校准的防护措施。真实案例：作者一天之内三次踩中同一个格式陷阱后，给 linter 加入了一个正则检查；它在项目自己的语料库中误杀了 **33 个健康输入**，并在同一小时内被回滚。启用之前先进行校准——在真实且已知正确的材料上运行任何 fail-closed 检查，并确认误报为零；宁可放宽检查，让它偶尔漏掉问题，也不要让它出现任何误报。
   - **让每个条目都成为可证伪的观察结果，而不是自我评估。** “背景信息是自洽的”无法被写下它的人判定为失败；而“覆盖页面的其余部分，单独阅读一张卡片，并说明它正在做什么决策”则可以。优先选择能产出工件的检查——例如命令输出、引用的行或屏幕截图——而不是只能产出意见的检查。
   - **同样的怀疑也适用于你*运行*的检查，而不仅仅是你编写的检查。** 上述四条规则适用于随技能一同交付的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样是工具；错误的工具会像正确的工具一样自信地报告干净结果。在一次 2026-07 会话中，五条不同的验证命令在两个方向上都给出了错误结果：没有使用 `-L` 的 `find` 报告已安装技能的文件缺失（它们位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了正在审计的对象的第二份副本；反转的 shell 条件错误地警告某项删除并未发生；跨越换行符的正则凭空捏造出 55 个“丢失的引文”；而针对五个文件中的两个进行的搜索报告有两条规则缺失，但它们实际存在于第三个文件中。**这些结果一开始无一例外都被相信了，而最终也无一例外都是通过重新运行一种形态不同的检查才被发现的。**

这种修复方法是实验实践中最古老的一种：**在把仪器用于答案未知的案例之前，先用答案已知的案例运行它。** 如果你要查找一个预期不存在的字符串？先用完全相同的命令形式查找一个你确定存在的字符串——如果这次也返回 0，那么出问题的是命令，而不是文件。只需增加一行，就能把“我检查过了”变成“我用校准过的仪器检查过了”。

     有两种具体形式值得记住，因为上文两者都出现过，而且两者都会*静默失败*：`find` 在没有 `-L` 时不会跟随符号链接（而 skill 的安装经常是指向源代码仓库的符号链接），并且 `--exclude-dir` 会在整个目录树中按基本名称匹配，而不只是匹配你心里想的那个路径。

     **这条规则还有后半部分，而只有当检查会随产物一起发布时，它才会造成影响：要以*标准*实现为基准进行校准，而不是以你机器上的实现为基准。** 上面的仪器规则保证*你的*结论诚实；这一点则保证*读者的*操作能够正常工作。写入 skill 的工具行为声明——某个标志、递归模式、某个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而两端的差异都是静默的：它在你测试时有效，却在他们那里悄悄什么也不做。有两种机制会导致这种情况，而且从会话内部都无法看出来：**同一个命令名称解析到不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能绕过*别名*，因此 `command tool` 或绝对路径才是唯一确定的形式），以及**同一个程序在不同实现之间表现不同**（BSD 与 GNU，或某个可直接替代的实现）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将其写入 skill，作为解决符号链接陷阱的方法，并将其发布到了一个拥有 1200 个 star 的公共仓库——他们的 `grep` 实际上是由 shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 中，相同的 `-R` 什么也匹配不到（它需要 `-RS`），因此这条规定的修复方法对大多数读者都静默失效了，偏偏就在警告验证器会静默失败的那一节中。

     所以：**在工具行为声明进入已发布的产物之前，使用标准二进制文件重新运行验证**（`/usr/bin/<tool>`），而不是使用 shell 提供给你的那个。如果它经不起这一验证，就不要写入这个标志——**优先采用与实现无关的表述方式**：自行解析路径（`readlink -f`），不要押注于递归标志；在脚本中进行子字符串测试，而不是进行面向行的匹配；描述你需要的*行为*，而不是描述你碰巧知道的选项。只在你的环境中有效的规定比没有规定更糟，因为读者根本无从发现它其实什么也没静默做成。

   - **采用成熟的检查清单实践已经确定的做法。** 判断一个清单属于 **READ-DO**（边阅读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭借专业经验完成工作，然后在明确的**暂停点**停下来确认——适用于时间紧迫时的有经验操作人员），并将其锚定在真实的暂停点上，而不是“工作流程中的某个地方”。只保留**关键项目**——既关键，*又*经常在压力下被遗漏，大约五到九项；再多就会稀释执行遵从度（[Gawande，《清单革命》](https://www.shortform.com/blog/types-of-checklists/)）。并且优先采用 Shingo 所说的**控制**，而不是**警告**（[防错](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，会输给“完成任务”的冲动；而阻止进度或强制生成某种产物的步骤则完全不需要警觉性。在 skill 只能发出警告的地方，至少要把警告放在做出决策的位置——**写在执行上下文从未打开的参考资料中的规则，在实践中就不是规则。**

另一方面，也许他们已经有了该 skill 的草稿。在这种情况下，你可以直接进入这个循环中的评估/迭代部分。

当然，你始终应该保持灵活：如果用户说“我不需要运行一堆评估，和我一起凭感觉来就行”，那你也可以按他们说的做。

然后，在 skill 完成之后（不过再次强调，顺序是灵活的），你还可以运行 skill description improver。我们为此准备了一个完整的独立脚本，用于优化 skill 的触发效果。

## 首先：共存检查（官方 skill-creator plugin）

在进行任何操作之前，先快速检查一次（常见情况下只需执行一次 grep，无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 中是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 不执行任何操作——不要安装任何东西，也不要向用户提及本节内容。继续进行此次交互。
- **存在：** 官方 plugin 的 skill-creator 与此版本现在会以近乎相同的描述出现在 skill 列表中，因此未来的会话将在两者之间随机路由。用一两句话告诉用户这一点，然后提供以下选项（绝不要未经用户同意就执行）：
  1. **推荐** — 运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的自检 SessionStart hook 复制到用户的 Claude 配置中，并将其注册到 `settings.json`（同时创建备份），这样未来的每个会话都会确定性地将 skill 工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；官方 plugin 在按名称请求时仍可完全正常使用。在没有官方 plugin 的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的 hook。
  2. 备选方案 — `claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），这样会将官方条目完全移出 skill 列表，从而消除歧义。

如果 hook 已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有操作。

对于用户创建的 skill，也可以使用同样的机制：当他们的 skill 有意与已安装的 skill 重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一套工具包——参见 Prior Art Research 下的“Coexistence & Precedence”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

## 与用户沟通

skill creator 可能会被各种编程术语熟悉程度不同的人使用。也许你还没听说过这种现象（毕竟它直到最近才开始出现）：如今，Claude 的强大能力正激励着水管工打开终端，也让父母和祖父母去 Google 搜索“如何安装 npm”。另一方面，大多数用户可能都具备相当不错的计算机素养。

因此，请注意上下文线索，以便了解应当如何措辞沟通！在默认情况下，给你一些参考：

- “evaluation”和“benchmark”算是临界词汇，但可以使用
- 对于“JSON”和“assertion”，在用户明确表现出了解这些概念之前，不要直接使用而不加解释

如果你不确定，简要解释术语是可以的；如果不确定用户是否能理解某个术语，也可以用简短定义加以说明。

### 使用 AskUserQuestion（关键事项——请阅读）

**在每个决策点都积极使用 AskUserQuestion。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最大单项 UX 改进——用户可能正在多个窗口之间切换，而且可能已经有 20 分钟没看这段对话了。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段，以及刚刚发生了什么（1–2 句话）。用户可能已经切换了上下文。
2. **简化说明**：用通俗易懂的语言解释这个决策。不要使用函数名或内部术语。说明它会带来什么，而不是说明它叫什么。
3. **给出建议**：先给出你的建议，并用一句话说明原因。如果选项涉及工作量，请同时展示两种时间尺度：`(人类：约 X 分钟 / Claude：约 Y 分钟)`。
4. **提供选项**：提供 2–4 个具体的、带字母编号的选项。每个选项都应是明确的行动，而不是抽象概念。

**规则：**
- 每次只做一个决策——绝不要把无关的选择合并到同一个问题中
- 提供退出选项（AskUserQuestion 中始终隐含有“其他”选项）
- 接受用户的选择——可以提醒权衡，但绝不要拒绝继续执行
- 如果没有明显权衡、答案显而易见，则跳过提问（直接说明你将如何处理）
- **如果问题超时且没有得到回答（用户暂时离开键盘），既不要停滞不前，也不要擅自推进涉及偏好或范围的决策。** 先进行不产生副作用的准备工作——预编辑快照、清单盘点、评估案例收集、只读审计/健康检查——并等用户回来后再处理判断性决策（重构方向、删除哪些内容、是否继续）。然后明确说明你已经完成了哪些工作，以及哪些事项正在等待用户决定。

## 创建技能

### 捕获意图

首先了解用户的意图。当前对话中可能已经包含了用户希望捕获的工作流（例如，他们说“把这个变成一个技能”）。如果是这样，先从实时对话中提取答案——所使用的工具、步骤顺序、用户做出的修正、观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**源清单——起草前始终执行，并明确同意边界。** 清点实时对话，以及与之有重叠的现有文档/技能（参见下方的“既有成果研究”）。较早的本地会话 JSONL 文件是独立的私有来源：除非用户明确要求挖掘历史记录，或在你解释将读取哪些内容后明确批准该来源，否则不要打开或解析它们。如果获得批准，则通过对话挖掘工作流的脱敏提取，仅纳入相关的过往会话；绝不要将原始记录加载到自己的上下文中。如果未获批准，则继续使用实时对话和现有项目来源，不要将缺失的历史记录视为阻碍。

挖掘对话（或会话记录）时，要同时盘点两类资源——它们会存放在不同的位置。*知识*——端点、参数、陷阱、决策规则——应成为 SKILL.md 指南或 `references/` 中的内容。*会话期间编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——则是 `scripts/` 的候选内容：如果本次会话编写了这些代码，那么下一次调用时就必须重新编写，因此应将其参数化、清理并打包。此前的一次提炼产出了经过润色的文字，却遗漏了可复用的辅助工具；普遍的经验是，要同时关注知识→references 和代码→scripts 这两条渠道。

当源材料是*过去的*会话记录（Claude Code projects directory 下的 JSONL 文件），而不是实时对话时，进入会话挖掘工作流。不要在主上下文中打开原始记录，也不要将原始路径/内容交给子代理。在任何代理看到内容之前，必须先完成确定性的 manifest → discover → redact → chunk 序列；只有经过删减的 chunks 才能进入最小角色/分片计划，并且必须在预算门禁下声明确切的单元数量和并发上限。

**首先，在回答下面的问题之前，先确定这是哪个方向。** 请求可能属于几种*相反*的事情：构建一个新 skill / 编辑一个现有 skill / 优化 skill-creator 本身 / 或者根本不是 skill，而是一次性任务。猜错会浪费整个会话——你为“新 skill”所做的研究，并不适用于“优化元工具”。当措辞含糊时（例如，用户说“帮我做一个 skill”，但指向的是 skill-creator 自身的路径），在这里使用一次 AskUserQuestion 只需 30 秒。下面的 wrapper-skill 分支是其中一种特殊情况；方向检查本身是通用的。

`Use skill-creator to optimize <existing-skill>` 表示采用正常的现有 skill 更新路径。它并不授权挖掘会话历史、进行大范围重写、开展 Tier 3 分类或多代理评估。先检查实际提议的差异；只有当这些差异确实引入了某个失败面时，才升级处理。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应该设置测试用例来验证这个 skill 是否有效？对于输出可以客观验证的 skill（文件转换、数据提取、代码生成、固定的工作流步骤），测试用例会很有帮助。对于输出较为主观的 skill（写作风格、艺术、经过品味校准的报告），通常无法使用断言——但“没有断言”不等于“不验证”。它们的验证路径按成本排序如下：
   - **历史任务重放**：重新运行一个该 skill 过去处理过的真实提示词，对比新旧 skill 的输出，并针对具体发生变化的规则进行比较（“新输出是否真的遵循了这次更新引入的 tokens / 标题语法？”）。成本低，还能捕捉“规则写了出来，但没有任何内容读取它”的问题。
   - **以生产环境作为评估**：承认真正的测试是用户下一次实际使用——然后明确这个闭环：之后用户的每一次纠正，都是要纳入 skill 自身“迭代/活文档”部分的事件；每一次认可，都是语料库材料。一个发布时没有这种回写习惯的品味型 skill 不会得到改进；而具备这种习惯的 skill 无需运行正式评估，就能逐渐收敛。**而且，当 skill 的输出是某种会持续运行的东西——守卫、监控器、计划任务、钩子——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户纠正需要用户注意到问题并愿意反馈；而已部署的机制会主动报告自身情况，通常在一天之内就会产生结果。误报是这种报告最明确的形式，因为它证明你写下的一条规则是错误的，而这是反复阅读也无法揭示的。应将第一次误报视为一次计划中的评估结果，而不是令人恼火的问题：在认定机制行为异常之前先检查它，因为更可能的发现是，*指令*写得过于绝对。（真实案例：某个 skill 规定了一项 fail-loud 检查，已部署的检查在夜间对一个完全健康的情况触发了一次；最终修复的是 skill 中那句过于绝对的表述——没有人提出抱怨，遥测数据本身暴露了问题。）
   - **渲染 + 人工审查**：适用于视觉输出（skill 自身的视觉 QA 门禁），绝不要用假装能够衡量审美的 grep 断言来替代。**而且，用于验证的渲染器必须与交付物实际使用的引擎相同**——无论安装了哪个方便使用的预览器，都不能替代目标应用。布局引擎不同于目标应用的缩略图工具，可能会悄悄*隐藏*你正在寻找的确切缺陷；在错误的引擎上得到绿色验证，比没有验证更糟，因为它会带来虚假的信心。真实案例（2026-07）：一个 .docx 通过 macOS Quick Look 缩略图进行了“视觉验证”，但 Quick Look 不会复现两端对齐文本的拉伸效果；用户打开文档后，Word 中的信息块立刻被撑得四分五裂。修复方法是安装兼容 Word 的引擎（LibreOffice），转换为 PDF，逐页栅格化，然后阅读每一页。引擎必须匹配，否则验证就是演戏。**这同样适用于渲染器之外的所有验证工具**——解析器、linter、验证器：它必须与生产环境共享同一实现，否则它显示为绿色就没有意义。另一个案例也是同样的模式：某作者试图通过在源文件阶段使用与生产工具链不同的 markdown 实现来检查一种会破坏最终文档的标记模式——对于已知的三个坏输入，它全部解析为完全正常，因此任何建立在该检查之上的预检都会悄悄放过所有问题。诚实的结论是：这个特定缺陷只有在生产工具运行之后才能检测到，检查也应当放在那里。**当没有可用工具与生产实现共享实现时，应说明该检查无法在那个阶段完成——不要构建一个只能产生虚假绿色结果的检查。**
   根据 skill 的类型，提出合适的默认方案，但让用户自行决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认 skill 类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类会驱动后续的整个评估策略。在这里做出正确判断，可以避免之后的无效工作。

### 扩展还是创建检查——在任何专门分支之前运行

下面的三个专门工作流都以“**do not** continue reading the sections below”结尾，而 *Prior Art Research* 恰好位于它们之后。这个顺序是排版顺序，并非执行顺序。扩展还是创建的判断适用于每个分支，跳过这一步正是导致会话最终交付一个与已安装 skill 重复的 skill 的原因。

因此，在进入 wrapper-skill / conversation-mining / artifact-corpus 分支之前，先回答一个问题：**是否已经存在一个 skill，而这项能力属于它？**

**发现根目录，不要凭记忆查找。** 手工维护的安装位置列表正是最容易过时的产物，而你忘记的那个根目录往往才是会造成问题的地方。

**搜索文件，而不是搜索名为 `skills` 的目录。** Skill 目录以 *skill* 命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、marketplace 克隆仓库和插件缓存中根本不会包含名为 `skills` 的目录——搜索这个名称会在看似正常运行的同时，悄无声息地跳过它们。每个 skill 都有一个 `SKILL.md`；这是与目录布局无关的定位方式。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，而且仍会返回比所需更多的结果；请使用与该能力相关的具体术语进一步缩小范围，而不要使用通用术语（`chart` 会匹配所有内容，`stacked bar` 则不会）。

这所覆盖的根目录——而通常凭记忆列出的清单会漏掉这些目录：技能源代码仓库（一个 `claude-code-skills` 检出目录以及任何 `-pro` 兄弟目录）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件——源代码仓库中没有任何迹象表明它们存在于此）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、每个配置文件的配置目录（`~/.claude-profiles/<name>/`），以及——完全没有任何路标的那个——**每个项目自己的 `.claude/skills/`**。第 2 步让这成为你验证过的结论，而不是你未经核实就继承下来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何 marketplace、全局技能列表或源代码仓库列表中；你在规划新技能时通常会打开的地方，没有任何内容会提到它们。真实案例（2026-07）：一个会话为某个领域构建了一个全局技能，检查了源代码仓库、全局目录和其他 agent 的目录，什么也没找到，于是交付了。后来一次对话历史搜索发现，某个项目级技能正好针对这个领域，已经存在了一个月，位于某个项目的 `.claude/skills/` 中——其中包含新技能所缺少的八条规则，包括一条用户亲自指定的规则。除了项目级目录之外，所有根目录都检查过了，而这次扫描却十足自信地报告了“没有先例”。

**当重叠的技能确实是某个无关项目中的项目级技能时该怎么做**——也就是那个故事会把你带到的情形，也是下面三条要点没有涵盖的情形：你不能向一个原本没有它的套件添加兄弟技能，而“扩展它”意味着编辑某个无关项目的工作树。有效的做法是：**将它的规则吸收到你正在构建的技能中，然后在所有者同意后废弃项目本地技能**——它是针对真实工作编写的，因此应将其视为更成熟的来源，并*向它靠拢*进行协调。废弃他人的工作技能是所有者的决定，而不是你构建过程中的副作用。

这句话遗漏了四件事，而每一件都可能让你止步不前：

- **“向它靠拢”是一项可反驳的推定，而不是规则。** 有两种标准的处理方式：项目技能可能已经*过时*（规则是几个月前针对一个已经发生变化的系统编写的），也可能是*项目特定的*（规则只在该项目的约束下成立——将它们整体导入会让你的技能变得狭窄，而本文其他地方要求你不要这样做）。采集来的规则是另一位作者的记忆，因此要像纪律 #1 要求你对写入技能的任何内容所做的那样，**重新验证每一条规则**。
- **“废弃”需要一个机制，而它的第一步不是你最先想到的那一步。** 按以下顺序进行：

  1. **先用 `find` 查找技能的*实体文件*，再 grep 查找它的*引用*。** 一个技能在同一个仓库中通常不止有一份副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被加载，只是由同一工作树中的不同工具加载。Grep 能回答“谁提到了它”；只有 `find` 能回答“它一共有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放入 `--exclude-dir`**（它会按 basename 匹配，因此会隐藏所有同名目录，包括你尚未找到的那一份——参见纪律 #6 中的 instrument 规则）。真实案例（2026-07）：一次废弃操作正是这么做的，修复了它找到的全部五处引用，却在 `.agents/skills/` 下留下了第二份完整副本——该副本受 git 跟踪，没有废弃标记，是一份缺少最新规则的过时快照——另一个工具仍会将它作为有效技能加载。
  2. **在删除任何内容之前，确认新位置确实能从旧位置所在的地方访问到它**，*然后再*删除任何内容——你刚推送的 marketplace 技能，在 marketplace 更新且插件安装之前，并不算已经安装；如果先废弃旧技能，就会留下新旧两边都没有技能的窗口期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常会符号链接到源代码仓库，而不带 `-L` 的 `find` 会报告文件不存在（参见纪律 #6 中的 instrument 规则）。
  3. **然后** grep 查找引用，并重定向仍在生效的引用。区分**有效指令**（技能列表、交叉引用、告知下一个 agent 应使用什么的交接文档）和**历史记录**（决策日志中写着“我们在某日交付了这个”）——改写后者会破坏审计线索，只为修复一个并不存在的问题。
  4. **然后**将每个实体文件替换为一个 `superseded by <skill>` 存根，而不是直接删除，并确保每一份副本的存根逐字节一致。**保留 YAML frontmatter**——没有它的 `SKILL.md` 可能会加载失败，而不是提供有用的失败信息——但要重写 `description`，让存根宣布自身已废弃，而不是继续宣传旧的触发条件；否则它会继续赢得它已经不再负责的路由。正文只需要包含：能力迁移到了哪里，以及它为何迁移的一行说明。
- **使用下面的所有权测试识别所有者**（这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍然会告诉你它属于谁）。当所有者就是你正在交谈的人时，“同意”只需要一次 `AskUserQuestion`。**当所有者无法联系时，只执行采集——不要废弃**（这样会让两个技能都保持有效并争夺同一触发条件，其最终状态与对方拒绝废弃相同——参见下面的 Coexistence & Precedence）。
- **如果所有者拒绝废弃它**，那么现在就有两个技能在争夺同一触发条件；这属于下面的 Coexistence & Precedence 问题，而不是一次失败。

**按能力词汇搜索，而不是按 skill 名称搜索。** 那个项目 skill 不会匹配新 skill 标题的名称搜索；它匹配的是正文中的领域术语。请在候选根目录中 grep 新 skill 将处理的*概念*。

如果存在重叠：

**如何判断适用哪一条——这个 skill 属于谁？** 文件系统命中结果并不携带所有权信息。读取 marketplace 的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或者在包含该 skill 的仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中结果完全可能只是你自己的 marketplace 被安装回了自己的机器。项目级 skill 没有 `marketplace.json`，但其项目的 `git remote` 可以回答同样的问题。

有两种情况是这些探测手段会判断错误或无法回答的，因此在相信结果之前请先检查：**fork** 会显示你自己的远程仓库，但其中的内容可能属于他人——应将其视为第三方，因为对方上游的改进仍然无法继续触达你。还有，当**既没有 marketplace.json，也没有 remote** 时（本地项目、被手动复制到全局 skills 目录中的 skill），这些探测结果是沉默的，而不是否定性的：**请询问所有者，不要自行猜测**。

- **重叠的是第三方的 skill**（某个 marketplace 套件、官方插件）：**不要重新实现它的能力。** 编写一个能够正确驱动它的*薄增量*——记录你遇到的陷阱、正确的调用方式以及经过验证的辅助脚本——并**使用命名空间名称引用它**。把别人的引擎克隆进自己的 bundle 是代价高昂的错误：对方的升级将无法继续触达你，而两份副本会在不知不觉中逐渐偏离。
- **重叠的是你自己的 skill**：扩展它，或在其现有套件中添加一个同级 skill。一个为相同触发条件竞争的独立 skill 对任何人都没有帮助。**例外情况：**如果它位于*不相关项目*的工作树中，则上述两种处理方式都不适用——请参见上面的项目级情况。
- **某个相关 skill 已经指向你要填补的缺口**（例如其描述写着“对于 X，请使用 Y”）：构建完成后要闭环——更新该指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才应构建独立 skill。

**为什么这项检查值得放在最前面：**一次真实的 2026-07 会话花了一天时间，让一个第三方 docx 引擎生成正确的中文商务文档，随后转而采用 wrapper-skill 分支——而该分支直接跳过了 Prior Art Research。它当时准备发布的形态，是一个重新携带该引擎能力的新 skill。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个保存正确用法和经过验证的生成器脚本的薄增量 skill → 由该增量 skill 提供调用的领域工作流 skill。用户不得不纠正两次才最终落地，第二次纠正得更准确：*“不要再复制一个额外的——在他们的实现之上写出正确用法，并引用他们的 skill；这就是 skill-as-code 的含义。”*

### 验证深度路由器（在选择任何工作流之前运行）

在进入通用或专用工作流分支之前，选择**能够证伪变更行为的最低层级**。应根据具体变更及其失败面进行分类，而不是根据行数或请求用词：一个变更的破坏性命令可能比一篇冗长的文字清理更应归入高层级，而“优化”现有 skill 的请求也可能只是一次有界修正。在选择层级之前，先列出你实际打算变更的规则、契约、脚本、权限和输出。如果尚未明确这些内容，应先进行检查，并暂时保留分类；范围存在不确定性并不是归入 Tier 3 的依据。

| Tier | 适用情形 | 所需证据 | 默认不添加 |
|---|---|---|---|
| **1 — 针对性变更** | 这是一个现有 skill；未添加或实质性改变任何能力、触发器族、工作流分支、输出契约、依赖、权限或外部写入行为；且编辑内容恰好属于以下情况之一：(a) 不改变行为的拼写/格式变更；(b) 事实性文档/配置修正，其正确性由直接权威来源决定；或 (c) 有界的实现修复，用于恢复一项明确的现有契约，**并且**修复后的行为由确定性回归检查覆盖。可能改变 agent 行为的澄清不属于 Tier 1 | 对于这三类变更：运行 `quick_validate`，检查差异，并完成现有 skill 迁移门槛。然后仅使用相匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其范围狭窄的检查；(c) 明确的现有契约及确定性回归。仅当跨越纪律 #5 的规则/契约/数值阈值时，才添加一名新的审阅者 | agent 行为重放、成对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 抽样行为** | 这是一个现有 skill；变更会影响 agent 行为，但未添加能力、触发器族、输出契约、脚本行为、依赖、权限或外部写入；并且 1–2 个带有明确验收标准的具名示例即可覆盖整个变更行为。对一个现有路由或证据选择规则的有界修正，即使会改变所选路径，仍属于此级别 | 仅运行这 1–2 个具有代表性的带 skill 重放，以及范围狭窄的确定性检查和纪律 #5 所要求的一次新上下文审查 | 默认不添加基线、成对扇出、方差分析、基准测试、查看器或评估文件。若明确要求这些内容，应通过单独的证据预算门槛，并不会因此重新分类变更 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新的 skill；任何新的或实质性改变的能力；广泛的跨分支重写或方法论扩展；触发器/描述优化；新的工作流分支，或实质性改变的输出契约、脚本能力、依赖或权限；高风险自动化或外部写入；或者变更行为本身涉及 3 个或更多不同的提示类别、重复试验或实质性不同的方法 | 先运行确定性门槛，然后仅添加针对已命名失败轴所需的证据。只有在单独的重型评估授权门槛通过后，才可使用下面的完整成对流水线；Tier 3 本身不会启动该流水线，同一门槛也可以授权在其他层级添加额外证据 | 仅根据 Tier 3 标签自动添加成对扇出、评分器、基准测试或查看器 |

#### 重型评估授权门禁——独立于层级分类

层级描述的是**风险与不确定性**；它并不授权 token 消耗或代理扇出。通过此门禁会改变获准采用的证据方案，而不会改变层级。通用的 paired baseline → grader → benchmark → viewer 流程只有在以下任一条件满足时才能运行：

- 用户明确要求 A/B、基线、基准测试、重复试验、viewer 或多代理评估；或
- 执行者能够列出至少三种不同的提示类别、多个具有竞争性的合理结果，以及成对比较将改变的决策，然后获得用户明确选择加入。

对于现有 skill 的优化，默认使用零个评估代理：先运行确定性检查；如果行为仍然存在不确定性，再至多运行一到两个 with-skill 重放。第 #5 条规范中的一个新上下文审查者是发布门禁，并不意味着可以创建审查者团队。对 token/成本敏感的指令会阻止重型流程，直到用户明确撤销该指令。

在创建多于一个研究、挖掘、评估或评分代理之前，先将**角色**与**执行单元**区分开：

- 每个额外角色或审查者都必须负责一个独立的故障轴或输出。模板是否可用绝不构成增加另一个角色的理由。
- 必要的实验组和语料库分片可以共享一个轴：with-skill 组和基线组需要隔离的上下文，而一个挖掘角色可能需要多个有界分块。启动前，说明确切的单元总数、并发上限，以及合并它们为何会污染比较结果或超出分块预算。默认串行运行；明确的 A/B/挖掘请求只授权这些必要单元，而不授权额外角色。
- 对于执行者提出而非用户明确要求的扇出规模，需获得用户对该数量的选择加入。如果交互式提问工具不可用，或用户没有回答，则采取较轻量的证据路径；沉默不代表同意。

如果某个单元既不是独立的角色/输出，也不是必要的隔离实验组/分片，则不要创建它。

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，升级处理。用户要求取消或降低评估级别时，应立即停止已经启动的成对评估代理、基线、评分器、聚合和 viewer 工作。如果风险分类仍然有助益，则予以保留，但只报告实际运行的证据以及尚未检查的轴；不要将未运行的重型套件描述为标签自动“要求”的内容。不要取消第 #5 条规范中的单个新上下文审查者（当其规则/契约/数量阈值被触发时），也不要取消任何为防止破坏性或外部影响所必需的安全门禁。机械化的现有 skill 迁移审计、公开 skill 清理，以及任何特定领域的安全门禁，也都独立于此路由器。

### 专用工作流：第三方 CLI 工具的 Wrapper Skills

在确定采用通用 skill 创建流程之前，先检查导致当前进展的会话是否实际上需要采用 **wrapper skill** 工作流。wrapper skill 是一种配套 skill，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或 skill 包——也就是他人编写的代码，而用户刚刚花费一个会话让它在自己的机器上运行起来。

适用信号（任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`、处理官方安装程序。
- 会话中出现了真实、具体的错误消息，并且用户和 Claude 已经为此找出了具体的修复方法（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个整理成一个 skill”“把这个保存为 wrapper skill”“这样其他人就不用再经历这一遍了”“把这次 session 做成一个 skill”之类的话。
- 用户明确提到了某个第三方工具的名称，并希望其他代理或其他人无需再经历自己付出的学习过程就能使用它。

不适用信号（改用上面的通用工作流）：

- 用户想要为某个准备从头编写的东西创建 skill。
- 会话进行得很顺利——没有值得提炼的实际摩擦。
- skill 将包装用户拥有或控制的服务（这是用户自己的代码；应编辑源代码，而不是进行包装）。
- 这个“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当 wrapper skill 工作流适用时，保留上面选定的验证层级。创建 wrapper 就是在创建新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用编写章节；跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一种**回顾性提炼**工作流——其任务是从当前对话中挖掘安装流程、已修复的 bug 以及已经做出的设计决策，并将这些挖掘结果转化为一个完整、自包含的 wrapper skill，使其他用户无需重新经历调试会话即可安装并从中受益。

wrapper skill 工作流有自己的架构契约、代码模板和 Tier 3 验证协议——它会替代不兼容的通用测试用例机制，因为其输出是用户的安装状态，而不是一个可以轻松断言的文件；这并不意味着降低工作等级。运行证据计划所选定的兼容通用步骤；通用的成对评估步骤仍然需要严格评估授权门槛。记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库根目录——当这个 skill 被移入一个套件时，这里的裸相对链接曾经失效过一次，正如下面的跨 skill 引用规则所警示的那样），它是一个基于真实会话、按照这一工作流提炼出的 Tencent IMA skill wrapper。

### 专用工作流：从对话历史中丰富一个 Skill

在开始通用的 skill 创建流程之前，检查当前会话是否实际上是在请求**将过去的对话提炼成一个 skill**。当用户在多个 Claude Code / Codex 会话中持续调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这种方式非常有用。

**必须明确说明来源意图。** 一段持续时间较长的实时对话、刚刚完成的调试任务，或 `use skill-creator to optimize <skill>`，都不表示同意打开本地历史记录，也不是进入此工作流的理由。对于普通更新，直接使用实时对话。只有当用户明确要求挖掘/提炼更早的本地对话，或指定特定的历史会话作为来源材料时，才进入对话挖掘流程。

适用信号（必须全部满足）：

- 用户明确将本地/过往对话历史作为输入，例如“mine my chat history”、“enrich this skill from earlier sessions”或“把以前的对话沉淀到 skill 里”。
- 源会话以及时间/范围边界已知或已确认。
- 预期输出是可复用的知识或代码资产，且无法仅从实时对话和当前 skill bundle 中表达出来。

不适用的信号（改用上面的通用工作流）：

- 用户正根据单个提示或想法创建全新的 skill。
- 用户要求优化现有 skill，但没有要求读取过往本地历史记录。
- 相关修正和证据已经存在于实时对话中。
- 用户想要为刚安装的第三方 CLI 工具创建包装器（改用上面的 wrapper-skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的会话记录导出文件。
- 挖掘出的内容是一次性的个人笔记，应放在 `memory/` 中，而不是可复用的 reference 文件中。
- 源材料是一批用户已认可的已完成产物，而不是对话——改用下面的 artifact-corpus-distillation 工作流。

当对话挖掘工作流适用时，保留上面选定的验证层级。新挖掘的 skill 为 Tier 3；只有在满足该层级能力边界的情况下，丰富现有 skill 才保持所选层级。**不要**继续阅读下面的通用编写章节；跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾式提炼**工作流：它发现获批准的本地历史记录，对其进行脱敏和分区，仅运行由语料库决定的挖掘过程，并在验证后提升经过审查的候选内容。

对话挖掘工作流有自己的架构契约、代理提示词、模板和验证协议。该协议实现了所选层级的专用机制；运行证据计划所选定的兼容通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代方案。它是将明确批准的对话历史转化为 skill 可复用知识库的规范方式。

### 专用工作流：从获批准的产物语料库中提炼用户偏好

在提交通用流程之前，检查当前会话是否要求**从一批用户已认可的完成产物中提取用户的真实偏好**——获批准的 HTML 报告页面、生成的文档、设计稿。这是第三种提炼来源，与前两种不同：材料是**产品，而不是对话**；输出是**可执行的品味**（明确的原则、量化的参数、词汇），而不是知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的成果，并说“这些都是我认可的样例” / “你来学到底什么是我想要的” / “extract my preferences from these approved examples”。
- 某个品味校准 skill（报告生成器、文档样式器、演示文稿构建器）拥有不断增长的认可样例库，而用户要求让 skill 从中*学习*，而不仅仅是将其编入索引。
- 用户抱怨之前的更新“只加了示例”——只是将样例编目，却没有改变 skill 的行为。

不适用信号：源材料是对话/修正，而不是获得认可的成品（使用 conversation-mining）；样例并未得到用户亲自认可（认可资格是准入门槛——先询问）。

适用时，保留上文选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新的语料库派生 skill 属于 Tier 3；向现有 skill 添加实质性的新决策能力也属于 Tier 3。专用协议实现了所选层级的语料库机制，不会降低其层级；根据证据计划运行兼容的通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代。其核心原则同样适用于向现有 skill 添加材料的任何时候：**编目 ≠ 提炼**——在语料库表中登记样例，并不会改变 skill 的下一次运行；对每一项新增内容都要问：“*这是否改变了决策规则？*”，如果所写入的所有内容对此问题的答案都是否定的，就不得宣布提炼会话完成（方法论 Case 15）。工作流的主线：对 ALL artifacts 进行脚本提取的定量比较（每种模式至少达到 ≥3-artifact threshold，并针对所声称的恒定项检查例外列表）→ 以证据锚点为基础的分层归纳 → 写入决策规则层（区分不变量与依赖风格的变量）→ 独立的完整性审计（standing discipline #5）→ 回归审计。

### 先例研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——正是 skill 有价值的原因。没有任何公共代码仓库能够提供这些内容。但用户不应浪费时间重复发明基础设施（API 客户端、身份验证流程、速率限制），因为已经存在成熟工具。先例研究用于寻找基础设施层可复用的构建模块，让 skill 能够专注于编码用户独有的方法论。

**两个轴，不要混为一谈。** 本节为*基础设施*层寻找来源（可复用的工具 / MCPs / 库 / 现有 skills）。*方法论*层本身有两个输入：用户的私有优势（只有用户自己拥有，无法检索）**以及该领域已确立的最佳实践 / 科学知识，这些内容应按照 standing discipline #3 默认检索到上下文中。** 找到合适的工具，并不能免除第二项要求——一个采用了图表库、却从未吸收 Cleveland/Bertin 理论的可视化 skill，仍然受限于你预训练中已有的内容。两者都要做。

**按以下顺序搜索这些渠道。** 默认进行内联研究。只有在上文的重型评估/代理预算门槛确认确实存在相互独立的未知信息后，才使用子代理；公共来源渠道不是默认的并行搜索集合。

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **实时对话或明确批准的历史记录** | 用户已验证的工作流、经过验证的 API 模式、调试过程中做出的修正 | 直接使用当前对话。只有在上文的明确来源门槛通过后，才搜索更早的本地历史记录；随后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有 skill | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区 skill | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 针对同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己的已验证模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终具有优先权——公共工具是构建模块，而不是替代品。在竞争性领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**倾向于合并/扩展，而不是新建，并且要扫描每一个 skill 根目录——不要只扫描 `~/.claude`。** 当渠道 1-3 发现了与请求领域重叠的现有 skill 时，通常正确的做法是扩展或合并到其中——**但如果它位于无关项目的工作树中，则方向相反：应当从中提取内容，应用到你正在构建的 skill 中，而不是合并到该 skill 中**（参见上文扩展与新建检查中的项目级案例）（有一次真正的“新建 skill”任务最终变成了“将现有 extractor 作为新 archiver 的 extract 阶段”），而不是交付一个会与相同触发条件竞争的平行 skill——两个重叠的 skill 会争夺触发机会并使用户困惑。搜索时，**应发现安装根目录，而不是凭记忆列出目录**——使用扩展与新建部分中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会漏掉源代码仓库、市场克隆和插件缓存，因为它们的 skill 目录是以 skill 命名的；而不是都叫 `skills`）。运行覆盖范围检查，不要仅凭这句话判断：**每个项目自己的 `.claude/skills/`** 是凭记忆列出的目录中最容易遗漏的根目录，因为项目外部没有任何内容会引用它。用户已经在*任何位置*安装的 skill，都是最有价值的先例，而项目本地的 skill 往往最为成熟：它是在真实工作中编写出来的。

**如果发现公共 MCP 服务器或 skill，请克隆并进行验证——不要盲目信任 README：**

1. **阅读实际源代码**——许多项目拥有精美完善的 README，但代码库本身却是空壳
2. **验证身份验证方式**——它是否与 API 实际采用的身份验证方式一致？（X-Api-Key 请求头、Bearer 还是 OAuth——很多项目在这方面都做错了）
3. **检查测试覆盖率**——没有测试 = 原型，而不是生产级项目
4. **检查维护情况**——最近一次提交日期、未解决 issue 数量、对 bug 报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域锁定
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有软件的使用相冲突
7. **检查依赖规模**——庞大的依赖树会带来冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用它，在其基础上构建**——安装 MCP，然后将 skill 构建为工作流层，用于编码用户的方法论 |
| 存在不完整的 MCP 或 SDK | **扩展**——将其用于基础设施，并在 skill 中补齐缺口 |
| 公共 skill 覆盖相同领域 | **仅用于获取结构上的灵感**——竞争性领域中的公共 skill 按定义都很通用。用户的优势在于其私有 SOP |
| **存在提供你正在构建的功能的某项子能力的互补 skill** | **将其打包**——把互补 skill 的自包含资源复制到你的 bundle 中，并将其接入。不要依赖用户预先安装它。请参阅下面的“互补 Skills” |
| 没有任何公共项目 | **从头构建**——在编写完整 skill 之前，先验证 API 访问模式是否可行（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——一个由你掌控、耗时 2 小时的定制实现，胜过一个集成摩擦大且存在上游风险的“成熟”工具 |
| 用户有意取代已安装的 skill（fork、强化版） | **将其与 supersede kit 一起发布**——请参阅下面的“共存与优先级” |

#### 共存与优先级（有意重叠）

将功能合并到现有 skill 中是解决重叠问题的默认方式（如上所述）。但是，当用户*有意*发布一个与已安装 skill 存在重叠的 skill——例如官方插件的 fork、经过强化的内部版本——这两个条目会以相似的描述出现在 skill 列表中，Claude 将随机在它们之间进行路由。请按以下逐步升级的顺序解决这一问题：如果重叠是意外的，就重命名；添加描述性决胜语（“取代 X——当两者同时出现时，始终使用此项”）；对于分发的 fork，使用 `scripts/generate_supersede_kit.py` 将条件性 supersede kit 写入 skill——这是一个基于用户同意的 SessionStart 路由钩子，仅在竞争对手确实存在的机器上安装，在其他机器上拒绝安装，并且当任一方消失时自动禁用。机制、决策表、SKILL.md 示例措辞以及沙箱验证请参阅：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此 skill 也针对官方 skill-creator 插件对同一 kit 进行了实际验证（请参阅顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄悄输给了*已安装技能集合*中的触发竞争。** 一个技能所处的领域（图像生成、PDF 处理、仪表盘）通常已经有多个已安装技能，而一个新技能可能会失去对所有这些技能的自动路由。因此，**要尽早验证触发效果——内容写得好并不代表构建就完成了。** 草稿完成后，通过 `claude -p` 发起几个符合实际的查询，并检查新技能是否真的胜出；如果没有，**请指出它输给的具体竞争技能**（不同查询可能会输给不同技能）。然后要明确两点：(1) **在竞争激烈的槽位中，仅靠正文不一定能胜出**——解决阶梯是：重命名 → 通过描述进行平局决胜/SUPERSEDES → 手动调用 → SessionStart 路由钩子（这是结构性方案，会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的审慎原则）；以及 (2) **修复方式取决于竞争技能的作者**——竞争技能是*第三方技能* → 接受手动调用或使用路由钩子；竞争技能是*你自己的技能* → 将它们合并/整合为一个，不要让自己的两个技能争夺同一个触发条件。（完整的解决阶梯见 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要只是指引，不要独立扩展。）记录所选择的方案（例如添加一条“激活”说明，写明“手动调用，竞争技能为第三方技能”），可以避免下一次会话再次争论这个问题。（方法论案例 13）

##### 互补技能（打包，不要依赖）

当构建的技能涉及一个已有互补技能的领域时，你有两种选择：

- **依赖该技能已安装**：这种方式很脆弱——用户可能没有安装它，或者安装的是不同版本。每一次缺少依赖的失败，最终都可以追溯到这个选择。
- **将其打包**：将互补技能的自包含资源（脚本、模板、参考文档）复制到你自己的包中，并将它们连接起来，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包。** 以下内容尤其重要：
- 状态栏/UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证/清理脚本
- 通用数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要状态栏。`statusline-generator` 技能提供 `generate_statusline.sh`。与其依赖用户先运行 `statusline-generator`，不如由配置文件设置技能将 `statusline.sh` 打包，并在 `claude-profiles-init` 期间将其连接到每个新配置文件中。这两个技能仍然可以独立发挥作用，但封装技能能够独立运行。

**反模式**：在你的 SKILL.md 中写下“先运行 `other-skill` 的安装程序”。这会把依赖转嫁给用户，并造成脆弱的安装顺序。应该改为打包。

研究完成后，通过 **AskUserQuestion** 呈现研究结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，优先采用成熟的基础设施来处理底层支撑，并在其上构建自定义的方法论层——价值就在这里。

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。等这部分确定后，再编写测试提示词。

在研究有帮助时，检查可用的 MCP（搜索文档、查找类似 skill、了解最佳实践）。默认以内联方式进行研究。仅针对尚未解决的独立问题使用子代理，绝不要因为工具可用就自动并行分发任务。提前准备好上下文，减轻用户负担。

### 编写 SKILL.md

根据用户访谈结果，填写以下组件：

- **name**：Skill 标识符
- **description**：何时触发、它的作用。这是主要的触发机制——既要包含 skill 的功能，也要包含具体的使用场景。所有“何时使用”信息都应放在这里，而不是正文中。注意：目前 Claude 有倾向于“触发不足”——在 skill 有用时也不使用它。为解决这一点，请让 skill 描述稍微“主动”一些。例如，与其写成“如何构建一个简单快速的仪表板来展示 Anthropic 的内部数据”，不如写成“如何构建一个简单快速的仪表板来展示 Anthropic 的内部数据。只要用户提到仪表板、数据可视化、内部指标，或希望展示任何类型的公司数据，即使他们没有明确要求‘仪表板’，也务必使用此 skill。”

  **注意预算：description 有严格的 1024 个字符上限，超过后验证会拒绝。** 这与上面的“主动”建议直接矛盾——你添加的每个触发短语都会消耗覆盖范围预算，因此应在扩展之前测量，而不是凭感觉扩展：使用 `len(description)`，而不是凭感觉。真正的陷阱不是第一稿（通常离上限还很远），而是多年后的更新：当新增触发条件以覆盖范围时，成熟的描述往往已经距离上限只剩几十个字符，此时**添加一个触发条件就意味着必须删除一个已有条件来腾出空间——这是零和博弈。** 请有意识地做出这种权衡，并在提交信息中说明，因为悄无声息地删掉触发短语会真正缩小 skill 的触发范围，而在它不再为某人触发之前，没有人会注意到。（实际中曾出现过这种情况：一次更新为新覆盖的故障模式添加了触发条件，使描述达到 1280 个字符，经过两轮压缩才降到 1003——代价是删除了三个原有触发短语。这本应被明确记录为一项决策，而不是在与验证器斗争时才偶然发现。）必须删减时，优先删除那些仍可通过同义词或相邻短语触达其场景的短语；保留没有其他入口的短语；并记住，正文中的限定语（例如“在平台 X 和 Y 上”、括号中的枚举）通常比一个独立的触发短语更容易删减——正文可以从主体内容中重新推导出来，而触发短语无法替代。
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **skill 的其余部分 :)**

### Skill 编写指南

#### Skill 的结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。通过在 `---` 标记之间配置以下字段来控制 skill 的行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| Field | Required | Description |
|-------|----------|-------------|
| `name` | No | skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | Recommended | skill 的功能以及使用时机。Claude 会根据此字段决定何时应用该 skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | No | **设置为 `fork` 可在 fork 出的子代理上下文中运行。** 参见下方的“Inline 与 Fork：关键决策”——选择错误会导致 skill 无法正常工作。 |
| `agent` | No | 在设置 `context: fork` 时要使用的子代理类型。可选值为 `Explore`、`Plan`、`general-purpose`，或来自 `.claude/agents/` 的自定义 agent。默认值为 `general-purpose`。 |
| `disable-model-invocation` | No | 设置为 `true` 可防止 Claude 自动加载此 skill。适用于希望通过 `/name` 手动触发的工作流。默认值为 `false`。 |
| `user-invocable` | No | 设置为 `false` 可将其从 `/` 菜单中隐藏。适用于用户不应直接调用的后台知识。默认值为 `true`。 |
| `allowed-tools` | No | 预先批准的工具列表。**建议：不要设置此字段。** 省略该字段后，skill 将获得由用户权限设置控制的完整工具访问权限。设置该字段会不必要地限制 skill 的能力。 |
| `model` | No | 此 skill 激活时要使用的模型。 |
| `argument-hint` | No | 自动补全期间显示的提示，用于指示预期的参数。例如 `[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | No | 作用域限定于此 skill 生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。参见 Claude Code Hooks 文档。 |

**特殊占位符：** skill 内容中的 `$ARGUMENTS` 会被用户在 skill 名称后提供的文本替换。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### Inline 与 Fork：关键决策

**这是设计 skill 时最重要的架构决策。** 选择错误会悄无声息地破坏 skill 的核心能力。

**关键限制：子代理无法再生成其他子代理。** 使用 `context: fork` 运行的 skill（作为子代理）**不能**：
- 使用 Task 工具生成并行探索 agent
- 使用 Skill 工具调用其他 skill
- 编排任何多 agent 工作流

**决策指南：**

| 您的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task tool） | **Inline**（无 `context`） | 子代理无法生成子代理 |
| 调用其他 skill（Skill tool） | **Inline**（无 `context`） | 子代理无法调用 skill |
| 运行 Bash 命令来调用外部 CLI | **Inline**（无 `context`） | 主上下文中具有完整的工具访问权限 |
| 执行单个聚焦任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境干净 |
| 提供参考知识（编码约定） | **Inline**（无 `context`） | 指南可以丰富主对话 |
| 被其他 skill 调用 | **Fork**（`context: fork`） | 必须作为子代理才能被生成 |

**编排器 skill 示例（必须为 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专员 skill 示例（正确使用 fork）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，无 task）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skill 应当是**正交的**：每个 skill 负责一个关注点，并通过组合实现协同。

**模式：编排器（inline）调用专员（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（不能使用 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个 skill 都应只有一个职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法，而不是重复代码

##### 流水线交接（顺序 Skill 链式调用）

除了编排器/专员组合之外，skill 还经常形成**顺序流水线**，其中一个 skill 的输出会成为下一个 skill 的输入。每个 skill 在完成工作后，都应主动建议逻辑上的下一步。

**模式：SKILL.md 末尾的“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
read-claude-code-history → continue-claude-code-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion **选择启用**——绝不能在未询问的情况下自动调用下一个 skill
2. 仅在输出自然地作为另一个 skill 的输入时提出建议——不要强行建立关联
3. 包含一个“不了，谢谢”选项——用户可能不需要完整的流水线
4. 建议应解释为什么下一步会有所帮助（例如：“ASR 输出通常包含识别错误”）
5. 最多提供 1-2 条建议——选项过多会造成决策疲劳

**何时添加交接：**询问“这个 skill 的输出是否通常会成为另一个 skill 的输入？”如果是，则添加一个“下一步”部分。如果关联很少见或牵强，则不要添加。

**反模式：**串联没有自然数据流的 skill。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**绝不要为可以自动检测的能力添加手动标志。**不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力自动检测，范围由用户决定。skill 应发现自己能够做什么并据此行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | 子代理可以使用 |
|-------------|----------------|-------------------|----------------|
| (default) | 是 | 是 | 否（内联运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（在明确委派时） |

#### 渐进式披露

Skills 使用三级加载系统：
1. **元数据**（名称 + 描述）——始终处于上下文中（约 100 个单词）
2. **SKILL.md 正文**——skill 触发时处于上下文中
3. **捆绑资源**——按需加载（不受限制，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。没有任何冗余内容的 600 行 skill，优于遗漏关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问：“每个部分是否都发挥了应有的作用？”如果是，就保留它。如果某些部分只是填充内容，或解释 Claude 已经知道的事情，则应删减这些部分——不要删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分到引用文件中，而不是人为地把所有内容硬塞进一个简短的主文件。
- 对于现有 skill，渐进式披露是一种迁移策略，而不是删除启发式规则。旧的运行时契约必须仍可从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或审阅者记忆都不能替代运行时内容。
- 在 SKILL.md 中清晰地引用参考文件，并说明何时阅读这些文件
- 对于较大的参考文件（>300 行），包含目录

**按领域组织**：当一个 skill 支持多个领域/框架时，请按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 不制造意外原则

这不言自明，但 skill 不得包含恶意软件、漏洞利用代码，或任何可能危及系统安全的内容。如果描述某个 skill 的意图，用户不应对其内容感到意外。不要顺从创建误导性 skill，或旨在协助未经授权的访问、数据外泄或其他恶意活动的请求。不过，诸如“扮演 XYZ”之类的请求是可以的。

#### 写作模式

指令中应优先使用祈使句。

**定义输出格式** - 可以这样写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式** - 包含示例很有帮助。你可以按如下方式进行格式化（但如果示例中使用了“Input”和“Output”，你可能会想稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得融入 skill 的可用性模式** - 以下四个结构要素反复将“能运行但令人困惑”的 skill 变成用户真正可以操作的 skill——它们是让一个被大量使用的 skill 变得可用的具体改进，因此当 skill 具有多种模式、会运行命令或可以重复运行时，应考虑采用它们：
- **入口决策树**：如果 skill 有多种模式，请以一个简短的“用户说了 X → 使用模式 Y”映射开头，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧跟在命令之后展示“你应该看到的内容”，这样模型（和用户）就能区分真正的成功与无声失败。
- **故障排除部分**：列出已知的失败模式及其修复方法——对于其他人将在你无法查看的机器上运行的 skill 来说，这是最有价值的单个部分。
- **第 0 步幂等性保护**：如果重新运行可能重复已完成的工作，请在开始任何耗时操作之前，先进行一个成本低廉的“是否已经完成？”检查。

### 写作风格

与其大量使用强硬、陈旧的 MUST，不如尽量向模型解释为什么这些事情很重要。设身处地理解模型，并努力让 skill 具有普适性，而不是过度局限于特定示例。先写一个草稿，然后以全新的视角重新审视并改进它。

### 日期和版本引用

**保留事实日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 skill 应写成“Suno v5.5（2026 年 3 月）”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 2025 年 8 月，则使用旧 API”）——日期一旦过去，这种逻辑就会失效，而且没有人会更新它。

规则：
- **发布日期、“最后验证”日期**：保留。这些是参考时间点，而不是有效期
- **定价、排名、法律状态**：包含，但标记为易变信息（“截至上次检查约为 ~$0.035/gen”），让读者知道需要重新核实
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠/已弃用部分记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性的任务，或反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当相同代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省 Token、具有确定性，并且无需加载到上下文中即可执行
- **注意**：Claude 仍可能需要读取脚本，以便进行修补或针对环境进行调整
- **用户可变数据存放在捆绑包之外**：如果脚本会累积用户数据（修正词典、学习到的偏好、缓存），请将其存储在稳定的相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其单独创建备份——绝不要将其存放在 skill 目录中。每次更新和套件迁移都会擦除并重新创建 skill 安装目录，而相对于主目录的存储位置会原样保留。这正是一个累积词典的 skill 在完整套件迁移后仍实现用户数据零丢失的原因

##### 参考资料（`references/`）

用于按需加载到上下文中，以便为 Claude 的流程和思考提供信息的文档与参考材料。

- **何时包含**：当 Claude 工作时需要参考文档时
- **示例**：用于金融架构的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库架构、API 文档、领域知识、公司政策、详细工作流指南
- **优点**：使 SKILL.md 保持精简，仅在 Claude 判断需要时加载
- **最佳实践**：如果文件较大（超过 10k 个单词），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应当位于 SKILL.md 或 references 文件中，而不是两者兼有

##### 资源（`assets/`）

不用于加载到上下文中，而是用于 Claude 生成的输出中的文件。

- **何时包含**：当 skill 需要在最终输出中使用的文件时
- **示例**：用于品牌资源的 `assets/logo.png`，用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件货架**：对于生成制品的 skill，`assets` 下的 `components` 子文件夹用于存放用户批准的、逐字嵌入的片段，这些片段具有冻结的行为契约和注册表引用——请参阅第 4 步中的组件货架检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标受众。**以下内容描述的是 skill 面向陌生用户发布时会出现的问题。对于存放在作者自有私有仓库中的 skill，相同的“违规”通常正是其能够正常工作的原因——真实的绝对路径能让脚本直接运行，模板中的真实账户能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 包含该 skill 的仓库是否为私有仓库），并在此情况下将可移植性/标识符相关发现降级为备注；当私有 skill 准备发布时，`--audience=public` 会强制执行严格检查。

**对于私有 skill，这些问题由所有者决定，而不是由你决定。** 不要在未询问的情况下将真实路径替换为占位符、重写硬编码凭据，或“清理”示例——这样做只是为了满足一条原本针对其他目标编写的规则，却会破坏正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，并让所有者决定。（其设计先例是 npm 的 `"private": true`：一个已声明的目标，会改变工具强制执行的规则；之所以加入这一机制，是因为人们总是不小心发布内容。）

**对于计划公开分发的 skill，这是关键要求**——其中不得包含特定于用户或公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，例如 `~/.claude/skills/`
- **允许**：skill 包内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（严格按“禁止”列表实现的验证器会将当前这个 skill 自身标记出来——对正常输入误报的危害大于漏报）：当发布者自己的名称/品牌对于解决 supersede 冲突或进行署名确实不可或缺时，可以使用；当段落讨论 `~/.claude/skills/` 等安装路径时，也可以使用（这是教学材料，而非硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于当前 skill 自己的包内”——验证器和读者都会这样理解，因此，指向其他 skill 文件的裸路径会验证失败，也会误导读者。指向其他 skill 时，应在正文中说明其所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用带命名空间的名称调用 skill（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。skill 在不同 suite 之间迁移时，裸的跨引用会静默失效——一次 suite 迁移就在两轮清理中留下了 21 个损坏的跨引用。

##### 版本管理

**关键要求**：SKILL.md 不应包含版本历史或版本号：

- **禁止**：在 SKILL.md 中添加版本章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **原因**：Marketplace 基础设施负责版本管理；SKILL.md 应包含不会随时间变化的内容

#### Reference File Naming

文件名必须无需阅读文件内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：仅从文件名本身，能否理解文件内容？

有两个例外：连字符命名与下划线命名同样合适（分隔符从来都不是重点——重点是能够自我说明）；而位于命名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已经由目录限定了范围——目录提供了具体性，重命名这些文件会破坏各个工作流之间的并行结构。

### 完整评估测试用例（仅限单独授权的配对计划）

只有在重型评估授权门槛通过后，才能进入本节。风险等级本身既不会授权也不会禁止使用此证据；明确的完整流水线请求不会重新界定底层变更。不要仅仅因为 SKILL.md 发生了更改就使用它。应遵循上文声明的替代契约所规定的专门工作流。

编写 skill 草稿后，提出 2-3 个现实的测试提示词——即真实用户实际可能说的话。**对于作用于实时系统（正在运行的服务、已登录的客户端、生产数据）的 skill，为每个测试提示词指定明确的副作用预算**——例如“仅进行只读探测并得出结论；不要执行下载 / 驱动 UI”。在“只是测试”时修改实时环境是真实操作，而不是测试。通过 **AskUserQuestion** 呈现这些测试：

```text
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——在运行进行期间，下一步再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整架构请参阅 `references/eval_pipeline_schemas.md`（包括稍后添加的 `assertions` 字段）。

## 完整配对评估流水线（仅限单独授权）

只有在重型评估授权门槛通过后，才能运行本节。风险等级仍应由变更所涉及的行为决定。以会影响决策的阶段执行流水线，并在不确定性或所请求的基准交付物得到解决后停止；不要预先启动后续的评分器、聚合或查看器工作。用户取消或降级请求会立即停止重型流水线。未经授权不得使用它；如果专门工作流明确进行了替代，也不得机械地添加通用机制；不要使用 `/skill-test` 或任何其他测试 skill。

将结果放入 `<skill-name>-workspace/`，使其与 skill 目录处于同级。在 workspace 中按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要一开始就创建全部目录——只需在进行过程中按需创建目录。

### 步骤 1：运行已批准的 with-skill / baseline 配对

对于每个已批准的测试用例，在相同的提示词和副作用预算下，运行一个 with-skill 样本及其 baseline。两条实验臂有意共享一个失败轴，但需要相互隔离的上下文；它们是必要的实验单元，而不是额外的评审角色。启动前说明实验臂总数和并发上限。默认串行运行，且绝不要超过授权的单元数量。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（使用相同的提示词，但 baseline 取决于上下文）：
- **创建新 skill**：完全不使用 skill。使用相同的提示词，不提供 skill path，并将结果保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用在首次编辑前通过强制性的现有 skill 回归门禁所捕获的旧版本。将 baseline 子代理指向该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 重建一个权威 baseline 后再继续；绝不要将已经编辑过的目录用作旧 baseline。**了解这种比较能够解决的问题：它只衡量本轮的变化。**如果你最希望验证的能力在编辑前的快照中已经存在——某个并行会话可以在你开始前恰好提交该修复——那么 with/old A/B 对此完全没有解析能力；在这种情况下，应选择更早的 ref 作为 baseline，以测试该能力。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据每个测试用例所测试的内容，为每个 eval 提供一个描述性名称——不要只使用“eval-0”。同时将此名称用于目录名。如果本次迭代使用了新的或修改过的 eval 提示词，请为每个新的 eval 目录创建这些文件——不要假设它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：在运行进行期间起草断言

不要只是等待运行结束——你可以利用这段时间开展有价值的工作。为每个测试用例起草量化断言，并向用户解释这些断言。如果 `evals/evals.json` 中已经存在断言，请检查它们并解释其检查内容。

好的断言应当能够客观验证，并且具有描述性名称——在 benchmark 查看器中应当能够清晰呈现，以便查看结果的人一眼就能理解每条断言检查的内容。**应针对意图编写断言，而不是针对字面上的工具路径**——例如“语音内容保留在答案中”，而不是“调用了获准的读取脚本”。如果运行通过另一条获准路径达成了该意图（例如读取一个已经内嵌转录内容的归档），也应判定为通过；若将其判定为字面路径失败，就会制造错误的负面结果，随后你还会在错误的位置进行“修复”。主观性较强的 skill（写作风格、设计质量）更适合进行定性评估——不要强行对需要人工判断的内容设置断言；其真正的验证路径（历史任务重放、带有写回习惯的生产环境评估、渲染后人工审查）列在“Capture Intent”的问题 4 下。

一旦断言起草完成，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试。

### 第 3 步：随着运行完成，记录计时数据

每当某个子代理任务完成时，你都会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们通过任务通知传入，不会持久化到其他位置。通知到达后应逐条处理，不要尝试批量处理。

### 第 4 步：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分** — 启动一个评分子代理（或直接评分），读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是凭肉眼判断——脚本速度更快、更可靠，并且可以在多次迭代中复用。**但客观的 grep/脚本断言也可能产生双向问题**（同词不同义导致误命中、措辞差异导致漏检），因此**基准测试通过率是一个信号，而不是结论**：抽查每条断言实际匹配到的内容，并留意基线运行是否暴露出技能本身的事实错误（“等等，数据明明就在 API 里”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **聚合为基准测试** — 从技能创建器目录运行聚合脚本：
   ```bash
   uv run --frozen python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这将为每种配置生成包含 pass_rate、time 和 tokens 的 `benchmark.json` 和 `benchmark.md`，并提供 mean +/- stddev 及 delta。若手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md` 以了解查看器所需的确切架构。将每个 with_skill 版本放在其对应的 baseline 版本之前。

3. **进行分析员检查** — 读取基准测试数据，并找出聚合统计数据可能掩盖的模式。请参阅 `agents/analyzer.md` 中的“Analyzing Benchmark Results”部分，了解需要关注的内容，例如无论是否使用技能都始终通过的断言（无区分度）、高方差评估（可能不稳定），以及时间/令牌的权衡。

4. **启动包含定性输出和定量数据的查看器**：
   ```bash
   cd <skill-creator-path>
   nohup uv run --frozen python eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台 viewer 进程自行失效**：进程仍在运行，但没有任何程序在监听 — 使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（输出为空），或 curl 该 URL（失败）；这里“没有日志输出”并不是可用的信号，因为上面的启动命令已将其重定向到 `/dev/null`。终止该进程，并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：**如果 `webbrowser.open()` 不可用，或环境没有显示器，请使用 `--static <output_path>` 来写入一个独立的 HTML 文件，而不是启动服务器。当用户点击 "Submit All Reviews" 时，反馈将以 `feedback.json` 文件的形式下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建 viewer；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** 告知用户：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在 viewer 中看到的内容

"Outputs" 标签页一次显示一个测试用例：
- **Prompt**：提供的任务
- **Output**：skill 生成的文件，在可能的情况下以内嵌形式渲染
- **Previous Output**（第 2 次迭代及之后）：显示上一次迭代输出的折叠区域
- **Formal Grades**（如果运行了评分）：显示断言通过/失败情况的折叠区域
- **Feedback**：输入框，输入内容会自动保存
- **Previous Feedback**（第 2 次迭代及之后）：显示在输入框下方的用户上一轮评论

"Benchmark" 标签页显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每个评估的详细分解和分析人员的观察结果。

可通过 prev/next 按钮或方向键进行导航。完成后，点击 "Submit All Reviews"，将所有反馈保存到 `feedback.json`。

### 步骤 5：读取反馈

当用户告知你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。请将改进重点放在用户提出了具体意见的测试用例上。

完成后，终止 viewer 服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。根据证据计划进行改进：对于 Tier 1，使用权威事实和确定性检查；对于 Tier 2，使用 1–2 个具名行为重放；或者，在单独的重型评估门控机制于任意层级授权时，使用经过用户审查的成对结果。未经授权，不要将成对评估产物导入默认的 Tier 1/2 路径。

### 如何思考改进

1. **从反馈中总结规律。** 这里发生的总体情况是，我们正试图创建可以被使用一百万次（也许确实是一百万次，甚至更多，谁知道呢）的技能，以应对许多不同的提示。现在，你和用户只是反复迭代少数几个示例，因为这样能更快推进。用户对这些示例了如指掌，因此可以快速评估新的输出。但如果你和用户共同开发的技能只能适用于这些示例，那它就是没用的。不要进行琐碎的过拟合式修改，也不要添加压制性过强的 MUST；如果存在某个顽固问题，可以尝试换用不同的比喻，或建议采用不同的工作模式。尝试的成本相对较低，说不定就能得到很好的结果。

2. **在不删除契约的前提下保持提示精简。** 删除那些没有发挥作用的内容，但要把从现有技能中删除的每一项都视为潜在回归，直到旧版本与新版本的审计对其进行分类。将详细但可复用的行为移至直接链接的参考文档中；不要只把它留在评估结果、变更日志或自己的记忆里。阅读完整的交互记录，而不只是最终输出——如果技能导致了低效工作，就简化指令并重新运行旧的能力用例，而不是想当然地认为字数越少行为就越好。

3. **解释原因。** 尽力解释你要求模型执行每件事背后的 **原因**。如今的 LLM *很聪明*。它们具备良好的心智理论能力，在得到良好测试框架的情况下，可以超越机械式指令，真正促成事情发生。即使用户的反馈简短或带有挫败感，也要努力真正理解任务，理解用户为什么写下他们所写的内容、他们实际写下的是什么，然后将这种理解传达进指令中。如果你发现自己开始使用全大写的 ALWAYS 或 NEVER，或采用过于僵化的结构，这是一个需要警惕的信号——如果可能，换一种说法并解释其中的道理，让模型理解你所要求的事情为什么重要。这是一种更人性化、更强大也更有效的方法。

4. **寻找重复性工作——既要看评估交互记录，也要看提炼技能所依据的对话。** 阅读测试运行的交互记录，注意子代理是否都独立编写了相似的辅助脚本，或采用了相同的多步骤方法来处理某件事。如果 3 个测试用例最终都让子代理编写了 `create_docx.py` 或 `build_chart.py`，这就强烈表明该技能应该捆绑这个脚本。将它编写一次，放入 `scripts/`，并告诉技能使用它。这样可以让今后的每次调用都不必重新发明轮子。在你提炼技能所依据的源对话中，也可能隐藏着同样的信号——那次会话中哪怕只编写过一次的代码，今后的每次运行都必须重新编写；不要等到评估运行来证明重复性（跳过评估循环的技能永远无法获得 այդ项证明——创建流程第 4 步中的 Scripts 检查点正是捕捉这类情况的地方）。

5. **逐字写回修正——同一会话、两个层级都要写回。** 对于经过品味校准的 skill，用户的修正就是评测集，但前提是这些修正被写入了未来运行时会读取的位置。以下两个属性能让写回过程逐步收敛：(a) **逐字记录修正内容**，不要改写——确切措辞携带着总结会抹平的校准信号（“绝对禁止这种东西”传达的是硬性边界；“用户更喜欢少一些跳转”则不是）。将这些话原样引用到它们所修正的规则中，并附上日期。(b) **在修正发生的同一会话中，同时写回两个层级**——修复产物，也修复 skill 的规则/参考/组件；只修复产物的修正对所有未来运行都不可见，而推迟到“以后”处理的修正通常永远不会落地。写回时，要检查 skill 自身的文本是否*教导了*刚刚被禁止的反模式——修正往往会证伪现有指令，而保留旧建议就必然会导致问题再次出现（真实案例：一个决策页契约建议使用跳转式的“goto 锚点跳到所引用的图”；用户明确禁止了这种做法，因此写回时必须修改原有句子，而不能只是在旁边新增一条规则）。当被修正的是交互片段时，写回的最后一步是将其提升到组件货架——参见第 4 步中的“组件货架检查”。

这项任务相当重要（我们正努力在这里创造每年数十亿美元的经济价值！），而思考时间并不是瓶颈；请花时间认真斟酌。我建议先起草一版修订稿，然后重新审视并进一步改进。请尽最大努力设身处地理解用户想要和需要什么。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据确实留下了多种选择时才提问。对于 Tier 2 或 Tier 3，当用户反馈揭示出有意义的设计分歧时，通过 **AskUserQuestion** 提出改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险层级，因为它改变了实施范围；选择 D 则不会。每个选项只授权其中明确列出的范围/证据变更。除非明确列出且单独通过了重型评测/扇出门槛，否则它不授权成对基线、评分器、基准测试、查看器或额外角色。

### 迭代循环

改进 skill 后：

1. 将改进应用到 skill
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **Tier 1 默认：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配的子类型证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归测试。除非单独授权配对计划，否则不要创建迭代工作区。
   - **Tier 2 默认：**仅重新运行相同的 1–2 个命名的 with-skill 示例和窄范围检查。除非单独授权配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任意层级单独授权的通用配对运行：**将所有获批的测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 skill，基线始终是 `without_skill`；对于现有 skill，不可变的原始编辑前版本仍是每次迭代的保留基线。紧邻的上一迭代可以作为补充，但绝不能替代原始基线。
3. 在实质性规则、契约或数字发生变化后，执行纪律 #5。对于单独授权的通用配对运行，还要使用指向上一迭代的 `--previous-workspace` 启动评估审阅器；专用工作流使用其声明的审阅器机制。
4. 对于单独授权的通用配对运行，等待用户审阅新的查看器结果；否则根据默认层级的证据作出决定，除非仍存在确实需要用户选择的问题。
5. 阅读新的证据或反馈；如果它证伪了当前版本，则再次改进，并在同一层级重复。

用户请求的取消或降级在任务的其余部分持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 `AskUserQuestion` 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（所有内容看起来都没问题）
- 你没有取得有意义的进展

如果你想对 skill 的两个版本进行更严格的比较（例如，用户询问“新版本真的更好吗？”），可以使用盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。基本思路是：将两个输出提供给一个独立的代理，但不告知它哪个对应哪个版本，然后让它判断质量。随后分析获胜者胜出的原因。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某个 skill 的主要机制。创建或改进 skill 后，应主动提出优化 description，以提高触发准确性。

### 步骤 1：生成触发评估查询

创建 20 条评估查询，其中应混合包含应该触发和不应该触发的查询。将其保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实可信，并且是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要使用抽象请求，而应使用具体、明确且包含足够细节的请求。例如，可以包含文件路径、用户工作或情境的个人背景、列名和值、公司名称、URL 等。可以加入一些背景信息。有些查询可以使用小写、包含缩写或拼写错误，或者采用较为随意的表达。查询长度应有所不同，并重点关注边界情况，而不是让它们过于明显（用户之后会有机会确认这些查询）。

不好的示例：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的示例：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应该触发**的查询（8-10 条），要考虑覆盖范围。应使用同一意图的不同表达方式——包括正式表达和随意表达。加入用户没有明确说出 skill 名称或文件类型、但显然需要使用该 skill 的情况。加入一些不常见的用例，以及该 skill 会与另一个 skill 竞争但应该由它胜出的情况。

对于**不应该触发**的查询（8-10 条），最有价值的是近似匹配案例——这些查询与该 skill 共享关键词或概念，但实际上需要处理不同的问题。应考虑相邻领域、容易触发朴素关键词匹配但实际上不应触发的模糊表述，以及查询涉及该 skill 能处理的内容、但在当前情境下应使用其他工具的情况。

最重要的是避免以下情况：不要让不应该触发的查询明显无关。用 `"Write a fibonacci function"` 作为 PDF skill 的负面测试过于简单，无法检验真正的问题。负面案例应当确实具有迷惑性。

### 步骤 2：与用户审核

使用以下 HTML 模板向用户展示评估集：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目组成的 JSON 数组（不要在其外部添加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 当前的 description
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`），并打开该文件：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——如果存在多个版本（例如 `eval_set (1).json`），请检查 Downloads 文件夹，找到最近生成的版本。

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期查看进度。”

将评估集保存到工作区，然后在后台运行：

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（即为当前会话提供支持的模型），这样触发测试才能匹配用户实际体验到的效果。

运行期间，定期查看输出末尾的内容，向用户更新当前进行到哪一轮迭代以及分数情况。

这会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，显示每轮迭代的结果，并返回包含 `best_description` 的 JSON——该值根据测试分数而不是训练分数选出，以避免过拟合。

**如果检测到完全无响应，循环会在第 1 轮迭代后自动中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中代码级别的保护机制，而不只是建议；它区分了“第 1 轮迭代中所有 should-trigger 查询都触发次数为零”的两种原因：

- `exit_reason: "infra_error: ..."` —— 某些查询执行（should-trigger 或 not-should-trigger）抛出了异常（`claude` CLI 不在 PATH 中、超时时间过短、网络中断），而不是干净地返回“未触发”。该检查优先进行，并且有意在任何非零错误计数时触发，即使几十次运行中只有一次偶发失败也会触发——无论崩溃多么罕见，它都比“没有任何触发”更具体、更容易采取行动，而修复方向是环境问题，不是重写描述。消息中的比例（例如 `3/15`）用于表示严重程度：较大比例意味着“停止，修复环境”；较小比例同时伴随大量干净的 0 触发运行，则意味着环境可能存在值得检查的小问题，且描述本身也可能确实很糟糕——两方面都要检查。无论哪种情况，都应检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` —— 只有在上一个分支排除了所有执行错误后才会检查此项，因此这意味着每个 should-trigger 和 not-should-trigger 查询都**确实运行了**，但仍然全部触发次数为零（这正是通过零分母默认值实现的“precision=100%”实际含义：不是“完美”，而是“没有可用于除法的数值”）。探针实际上什么也没有测量——在完全触碰描述之前，先去诊断竞争者冲突或低阈值领域（见下文）。

两项检查都**仅针对第 1 轮迭代**，并且**仅在 should-trigger 查询触发次数为零时进行**——第 1 轮迭代表现较弱但并非零触发（例如 1/9 次触发）是另一种可能恢复的情况，因此会有意继续迭代。`degenerate_harness` 还要求 not-should-trigger 查询的触发次数也为零：如果描述只是极性反转——漏掉了所有正例，却意外匹配了多个负例——则说明探针确实有效，`improve_description` 也有真实的梯度可以利用，因此保护机制不会中止这种情况（它只会中止真正失效的探针）。此外，它还要求任一侧都没有执行错误——抛出异常的 not-should-trigger 查询实际上并未运行，因此其“0 次触发”不能作为探针失效的证据；这种情况正是应归入 `infra_error` 的情形。无论哪种情况，程序都会立即中断，并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因才是信号，表明本次运行的数字不应被解读为“这是一个好的描述”。（真实案例，2026-08：一次没有预先检查就启动了完整的 5 轮迭代循环；两轮完整迭代——每轮都是完整的评估批次，耗费数分钟的实际时间并调用了几十个 `claude -p` 子进程——都返回了 precision=100%/recall=0%/完全相同的分数，直到有人查看这些数字才发现问题，而每个 should-trigger 和 not-should-trigger 查询都没有触发。仅凭第 1 轮迭代就可以诊断出该故障；第 2 轮及之后的迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会渲染一个横幅，因此浏览器视图会携带与 JSON/stderr 相同的信号，而不仅仅依赖这两个可见度较低的渠道。（该保护机制的早期草案只检查 should-trigger 触发情况；经过两轮独立审查——每轮都由新的代理执行，第二轮检查第一轮的修复，而不是重复检查旧问题——构造出了极性反转的反例、基础设施问题与描述问题之间的歧义、负例侧错误遗漏，以及在此过程中发现的一个既有的 `--holdout 0` 报告崩溃问题；所有问题都已在发布前修复。）

此防护措施无法覆盖一种情况：当使用 `--runs-per-query 1`（默认值为 3）时，一个本应触发、但实际触发率确实接近 50% 的查询，可能仅凭随机因素就读到 0/1，从而因为噪声而触发防护措施，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询的每次重复运行结果都为零”成为强信号的原因——如果你将其调低，这个防护措施的误报风险也会随之上升。

**在信任 `best_description` 之前，先对测试框架进行合理性检查——即使上面的两个防护措施都没有触发，它仍可能返回空洞的结果。** 这两项检查只能捕获第 1 次迭代时的*完全失败*；测试框架也可能在全部 5 次迭代中持续产生微弱但非零的信号，却始终无法触发其中任何一项。如果第 1 次迭代之后，每次迭代报告的**召回率都徘徊在接近 0%，且分数完全相同或几乎相同**，那就是防护措施无法排除的同一个根本问题——“获胜”的描述通常只是在未改变的第 1 次迭代结果周围产生的噪声。在应用任何 `best_description` 之前，先自行运行一个显然应该触发的查询，并确认召回率 > 0。跨迭代保持平坦的召回率结果意味着测试框架是一个隐藏变量（常见原因是：该技能输给了已安装的竞争技能——参见下文的“共存”）——不要应用它的“最佳”结果；应手动编写描述，并使用真实探针对其进行验证。（方法论案例 12、14）召回率为 0 还有第二个根本原因，与输给竞争技能不同：该技能的任务领域属于*低阈值*领域——模型会自行完成任务，从不查阅任何技能——详见下文*技能触发机制*末尾的说明。在采取应对措施之前，先区分这两种情况，因为修复方式正好相反：竞争技能应通过优先级/取代关系修复，而低阈值领域则应完全放弃触发探针，改用生产即评估。

**当你使用 `claude -p` 自行探测触发情况时，要收集运行期间的所有技能调用，而不只是第一次调用——并记住，工具调用只是一个代理指标。** `UserPromptSubmit`/`SessionStart` 钩子可能会在模型做出选择之前注入一个无关技能，因此“第一次出现 Skill 调用就退出”的探针会错误地报告“未触发”。此外，“它是否调用了 Skill 工具”并不等同于“该技能的内容是否影响了输出”（模型可能读取了技能，却没有可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你针对错误的结论持续优化。

### 技能触发机制

理解触发机制有助于设计更好的评估查询。技能会以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，而 Claude 会根据该描述决定是否查阅某个技能。需要注意的重要一点是，Claude 只会为自己无法轻松处理的任务查阅技能——即使描述完全匹配，像“读取这个 PDF”这样简单的单步查询也可能不会触发技能，因为 Claude 可以使用基本工具直接处理这类任务。描述匹配时，复杂、多步骤或专业化的查询能够可靠地触发技能——但存在一个系统性例外（低阈值任务领域），详见本节末尾的说明。

这意味着你的评估查询应该足够具体，使 Claude 确实能从查阅 skill 中受益。像“read file X”这样简单的查询是不好的测试用例——无论描述质量如何，它们都不会触发 skill。

**但有些 skill 未能通过这一测试，是有原因的：无论如何改写查询都无法解决——该 skill 的整体*职责*就是执行低门槛任务。** 上一段将问题归咎于查询（“写一个更具体的查询”）；而这里是正交的情况，阻碍触发的是 skill 的*领域*。如果某个 skill 的用途是完成 Claude 仅凭基础工具就会自行执行的操作——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询写得非常完整（“将这个 48k 立体声 wav 降采样为适用于 whisper 的 16k 单声道”，路径及其他信息一应俱全），它也不会触发：模型会直接使用 `Bash`/`ffmpeg`，而不会查阅任何 skill。查询的具体程度无法解决这个问题，因为“我可以自己完成这件事”的判断针对的是*任务*，而不是措辞。

在耗费一个优化循环之前先诊断这一点：通过 `claude -p` 运行一个真实的查询，并观察模型是否在整个运行过程中*曾经*查阅过该 skill（遵循上文的 ALL-skill-calls 规则），还是直接使用 `Bash` 自行完成任务。如果它从未查阅，那么触发探测从结构上就无法观测这个 skill——无论你怎么写，recall 都会接近 0，而这个 0 衡量的是模型“自己动手完成”的反射，而不是你的描述。停止针对 `claude -p` 的 recall 进行调优，改用真实方式验证：以生产环境作为评估（用户下一次真实的、*交互式*使用——无头 `-p` 比真实会话更偏向执行操作，并且系统性地低估触发情况），再加上输出比较（skill 产出可检查的制品时）。 （在一个音频预处理 skill 上观察到：无头运行的 run_eval sweep 在*每个*查询上的 read recall 都是 0——包括一个明显的“transcribe this recording”查询；而手动执行 `claude -p` 探测显示，模型直接使用 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个 0 衡量的是无头运行的操作偏差，而不是描述；真实信号只会在交互式使用中出现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新 skill 的 SKILL.md frontmatter。向用户展示修改前后的内容，并报告分数。

## 重要：在源位置编辑 Skills

**绝不要先编辑已安装的 skill 副本。** 除非用户明确说明它们就是源文件，否则应将以下所有位置视为已安装/运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装的副本会导致修改：
- 在缓存刷新时丢失
- 不会同步到源代码管理系统
- 浪费需要手动重新合并的工作量

**务必确认你编辑的是源代码仓库：**
```bash
# 错误 - 缓存位置（只读副本）
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# 错误 - 个人已安装副本，除非明确将其用作源
~/.codex/skills/my-skill/SKILL.md

# 正确 - 源代码仓库
<repo-root>/my-skill/SKILL.md
```

**在任何编辑之前**，运行源位置检查并说明哪个路径是源目录：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源目录。应先定位由仓库提供的源目录，编辑并完成验证，然后仅在用户需要立即在本地运行时，才同步已安装的副本。

**然后回答决定“同步已安装副本”是否确实需要执行的后续问题：运行时是否已经读取源目录？** 三种安装方式的行为不同，猜错会导致不必要的同步，或者提交一个用户在下一次会话中根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # 是指向仓库的符号链接？ -> 编辑已经实时生效
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> 在原位置读取仓库
```

- **符号链接**到源目录树 → 编辑内容*就是*运行时内容。不需要同步。
- **`source: directory` 的 Marketplace** 指向仓库 → 同样如此：它读取工作树，因此版本号更新只是为其他使用者记录，并不是本地激活步骤。
- **任何缓存/复制的安装方式**（来自 git 的 marketplace、通过 `cp -r` 安装）→ 运行时使用的是独立副本，因此确实需要先运行官方更新命令，新内容才会生效。

**并且要根据内容验证激活状态，而不是根据版本字符串。** 注册表可能记录了磁盘上并不存在的路径或版本——有一次会话读到的插件记录中写着包含*新*版本号的缓存目录，差点据此报告更新已经生效；但该目录从未创建过，而真正的运行时路径一直都是指向源目录的符号链接。权威检查方式是 grep 运行时文件，查找只有新版本包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = 尚未生效
```

### 同一技能仓库上的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能在你进行编辑的过程中提交技能 B（甚至是技能 A 更早一轮的修改）。有一次实际会话在一小时内同时遇到了三种症状——一次 `Write` 因文件在读取后发生变化而被拒绝，以及 HEAD 在任务期间两次移动（方法论案例 16）。失败的根源不是冲突本身，而是过时的基线，或会静默混合两个会话修改内容的覆盖式写入。固定规则如下：

1. **只要仓库在任务开始时是干净的，就应从 git ref 而不是工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传入 `--baseline-origin git-ref:<sha>`。在其他人的提交之后数分钟才获取的树快照，是一个已经不存在的树的基线。**应解压到一个全新且不存在的目录中。**解压到现有目录时，`tar -x` 会静默覆盖同名文件，并保留归档中不存在的文件，形成一个在解压时完全没有信号的混合快照，之后 `compare` 会因其与该 ref 不匹配而拒绝。同样的陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会将目录嵌套进去；如果 `mv` 被别名为 `mv -i`，目标已存在时，重命名操作会打印一行提示，并默认不执行，但无论哪种情况退出码都是 0（已通过实验验证）。
2. **在写入被拒绝后，或经过一段时间后，重新读取文件**：查看发生了哪些变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图合并进你的版本——他们的编辑通常是有原因的——然后才写入。
3. **提交前同时检查 HEAD *以及当前所在的分支***。`git log --oneline -1` 可以发现 SHA 是否发生移动：如果它自你的基线以来已经移动，就要针对新的 ref 重新运行回归 `compare`，然后再执行 `verify`——审计工具本来也会拒绝过时的审查（“after skill changed”），自行提前发现可以节省一次往返。但另一个会话可能做得比推进 HEAD 更糟：**它可能在你进行操作时切换分支**，因为 checkout 影响整个工作树。实际发生过这样的顺序——你执行 `checkout -b feat/x`，编辑了一段时间，与此同时另一个会话执行了 `checkout main` + `pull`；随后你的提交就落到了 **main** 上，违反了仓库“绝不直接提交到本地 main”的规则，而 feature 分支仍然指向旧基线。因此，提交前检查中应加入 `git branch --show-current`，不能只检查 SHA。若这种情况已经发生，`git reflog` 是权威的还原依据（它会按顺序记录每次 `checkout: moving from X to Y`），而修复方式是——**在工作树干净的前提下**——执行 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：这两者都是只移动 ref 的操作，从不会触碰工作树，因此不像 `reset --hard` 那样会破坏并行会话尚未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——另一个会话尚未提交的工作不能被一并带入。（这本来就是打包规则；在并发场景下更是如此。）
5. **每次会话结果只更新一次版本号**，而不是每轮编辑都更新：同一会话在同一技能上的连续多轮编辑应合并为一次版本更新——除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），这种情况下，每个已被使用的状态都应有自己的版本号。

## Skill 创建流程（分步）

创建或更新 skill 时，请按顺序执行以下步骤。仅当某一步明确不适用时才跳过。

### 步骤 0：前置条件检查

在开始任何 skill 工作之前，自动检测所有依赖项，并主动安装缺失的依赖。到工作流中途才发现缺少工具（例如在打包时发现缺少 gitleaks，或在验证时发现缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖就自动安装，并向用户展示检查清单摘要。只有在所有阻塞性依赖均已满足后，才能继续执行。

关键阻塞项包括：Python 3、uv、锁定的 skill-creator 运行时（验证/打包）以及 gitleaks（安全扫描）。只有在单独授权的证据计划实际运行 agent 评估时，claude CLI 才是阻塞项。从 skill-creator 根目录使用 `uv run --frozen` 运行内置的 Python 工具，例如 `uv run --frozen python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 依赖环境中已有的 site packages，可能会缺少锁定的依赖。

**uv 隔离约定：** 将此目录视为一个普通的 uv 项目。保留其中已提交的 `pyproject.toml` 和 `uv.lock`，让 uv 从共享的全局缓存中构建一个项目本地的 `.venv`，并使用 `uv run --frozen` 运行内置工具。不要为此处已锁定的依赖添加每次调用时的 `--with` 覆盖，不要跨项目设置统一的 `UV_PROJECT_ENVIRONMENT`，也不要创建项目专用的 `UV_CACHE_DIR`。不要在常规 Skill 执行过程中使用 `--no-cache`、`uv cache clean` 或 `uv cache prune`；缓存维护属于需要单独授权的磁盘操作。

### 步骤 1：通过具体示例理解 Skill

仅当 skill 的使用模式已经明确了解时，才跳过此步骤。

要创建有效的 skill，必须清楚了解该 skill 将如何通过具体示例来使用。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成式示例。

例如，在构建图像编辑器 skill 时，相关问题包括：

- “图像编辑器 skill 应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能给出一些该 skill 的使用示例吗？”
- “用户说什么话时应该触发该 skill？”

为避免让用户应接不暇，避免在一条消息中提出过多问题。

### 步骤 2：规划可复用的 Skill 内容

分析每个示例时：

1. 考虑如何从头开始执行该示例
2. 确定 Claude 应拥有的适当自由度
3. 确定哪些脚本、参考资料和资产有助于重复执行这些工作流

**使具体程度与任务风险相匹配：**
- **高自由度（文本说明）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，同时允许可接受的变化
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 第 3 步：初始化 Skill

如果该 skill 已经存在，则跳过此步骤。

从头创建新 skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个包含正确 frontmatter、资源目录和示例文件的模板 skill 目录。

### 第 4 步：编辑 Skill

开始编写前，获取 Anthropic 的最佳实践文档（上文“技能创建最佳实践”中提供了链接）以及方法论参考资料——即使你觉得自己已经了解它们，也要执行此操作：文档会更新，训练数据版本会过时，而“我基本了解”恰恰是编辑者跳过这一步并错过最新指导的状态。

编辑时请记住，这个 skill 是为另一个 Claude 实例使用而创建的。重点关注那些对 Claude 有益且不明显的信息。

**现有 skill 迁移门禁——必须在首次编辑前完成：**

1. 在编辑前捕获当前完整 bundle。对于非 Git 或处于脏状态的源代码，使用该工具，以便快照携带可验证的来源清单：

   ```bash
   cd <skill-creator-path>
   uv run --frozen python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源代码，从选定的 ref 生成目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C 要求目标目录已存在
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # 结果位于 <workspace>/skill-before/<skill-dir>/SKILL.md——比
   # snapshot 子命令的输出多一层目录，因为 `git archive` 会保留路径前缀；第 3 步中的
   # --before 应为 <workspace>/skill-before/<skill-dir>，而不是
   # <workspace>/skill-before 本身。
   ```

   包括 SKILL.md、references、scripts、assets、workflows 以及现有 evals——而不仅仅是主提示词。不要复制已经编辑过的目录并将其标记为“before”。**使用一个之前没有解压过任何内容的目录**——复用一个此前已有内容的目录，会让 `tar -x` 静默覆盖同名文件，同时保留新归档中不存在的过时文件，从而生成一个混合快照，并且在提取时完全没有任何信号（`compare` 只能在之后间接地通过目录树哈希不匹配发现这一问题）。参见下方“同一 skill 仓库中的并发会话”部分，其中有关于这一陷阱更完整的说明，包括基于 `mv` 的变体。
2. 清点旧 skill 的角色/任务、触发上下文、运行时契约、命令/标志、失败和恢复情况、页面/领域变体、捆绑资源以及 eval 覆盖范围。在进行结构重写前，为重要的旧版边缘行为添加保留用例。
3. 编辑后，生成新旧版本对比审查：

   ```bash
   cd <skill-creator-path>
   uv run --frozen python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

如果旧目录是从 Git 重建的，请将最后一个标志替换为
   `--baseline-origin git-ref:<ref>`。该工具会将该引用解析为不可变的提交，并根据该树验证每个包含的文件及可执行位。

   **重命名或移动技能目录本身**（而不仅仅是编辑其内容）会改变 `--after` 的路径，而这两种基线模式都使用该路径作为身份标识 — `compare` 默认会拒绝此操作（假定 `--before`/
   `--after` 是意外不匹配的），并显示 `pre-edit snapshot source
   identity does not match the edited skill`。添加 `--renamed-from <old-path>`
   （对于 `snapshot`，这是 `--source` 所指向的路径；对于 `git-ref:`，这是相对于其仓库根目录的技能旧路径）以显式声明重命名；随后身份检查会验证该路径，而不是 `--after`，同时内容/树哈希检查保持不变，因此实际不匹配的配对仍会失败。**请将 `--renamed-from` 作为绝对路径传入。** 此命令接受的每个路径，在以相对路径给出时，都会相对于当前工作目录解析 — 而不是相对于 `--after`，也不是相互之间相对解析 — 并且 `--renamed-from` 通常指向一个已经不存在的目录（它已被重命名），因此不像 `--before`/`--after` 那样会通过存在性检查捕获错误的解析；它只会在更深处以令人困惑的方式失败。这一点尤其会影响 skill-creator 自己的编辑：上面的 `cd
   <skill-creator-path>` 是进入 skill-creator 自己的仓库，而它通常与正在审计的技能所属的仓库是*不同的*仓库，因此相对的
   `--renamed-from` 会静默地解析到错误的仓库。

4. 审查每个候选项。每个候选项必须恰好使用一种处置方式，并记录具体证据/原因：`preserved_or_moved`、`intentional_sanitization`、
   `intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移出此技能需要提供负责接收它的目标位置、当前边界证据以及可追溯的用户批准。明确的弃用也必须引用/追踪用户的批准。关于已保留/已清理/已修复的声明必须指向当前真实存在的文件和行，并包含一段简短的 `contains` 引文，以便验证器在附近定位。文件级候选项必须使用当前文件指纹，并附带一份说明行为为何得以保留的具名语义审查 — 单凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写相同的填充脚本 —
   `classify` 子命令会完成机械性工作（定位目标文件中引文所在的行，填写 evidence/semantic_review，并在找不到引文或原因过短时快速失败）。你仍需为每个候选项编写处置方式和原因；它只负责将其录入：

   ```bash
   uv run --frozen python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

其中，`dispositions.json` 将候选索引（或 ID）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（disposition 默认为
   `preserved_or_moved`；文件级候选只需要 destination + 一个长度为 40+
   个字符的 reason——指纹会为你计算）。**从目标文件中复制 needle（使用 Read/grep/sed），绝不要凭记忆手动输入**——查找采用精确匹配，缺少引文时会立即失败；手动输入的 needle 实际上有两种失败方式：全角与半角标点（`：` 与 `:`）不同，以及凭记忆改写成近义字符（`也` 与 `都`）——这两种情况都很难通过自查发现，只有工具拒绝整个映射时才会被捕获（同一个映射曾因这两个原因连续被拒绝两次）。
5. 验证已完成的审查。任何后续编辑都会使哈希对应的审查过期，因此候选发生变化时要重新生成并重新分类。通过验证后会写入 `.skill-regression-reviewed`，这是一个与内容绑定的本地状态回执。它有助于检测后续编辑，但有意不作为独立的打包授权依据；打包过程本身会再次验证已完成的审查：

   ```bash
   uv run --frozen python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时的表现如下（真实输出，因此可以识别静默失败）：

   ```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在需要审查的候选项，而不是工具失败；
2 表示调用或运行时失败。该工具可以证明内容已被精确迁移以及接口得到保留，但会有意拒绝根据模糊的词语重叠来推断语义等价性。像“check permission denied”这样的通用短语，不能悄悄替代“已登录但没有角色”这一精确契约。还要检查标记为
`only_outside_runtime` 的候选项：如果运行时行为只存在于评估、测试或不可达的引用中，那么它就不在正常调用路径中。

**每次编辑 SKILL.md 后立即验证——不要等到打包时才验证（第 7 步）。** 该检查能够尽早捕获的失败是真实存在的：以未加引号的 YAML 标量形式编写的 frontmatter description，在 Claude Code 的宽松解析器中可以正常解析，却会在严格解析器中出错（codex 曾报告某个已发布数月的 skill 出现 `invalid YAML: mapping values are not allowed`）；而未加引号的 description 中包含 ` #` 时甚至不会报错——它会静默截断其后的全部内容，导致触发关键词消失，尽管所有扫描结果仍然显示为绿色。

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.quick_validate <path/to/skill-folder>
```

**只要描述中包含 `: ` 或 ` #`，或跨越多个句子，就应将其写成 YAML 块标量**（`description: >-` 后跟缩进段落）；块标量原生支持这两个字符，因此这是自上述事件以来对所有新建或编辑描述所推荐的约定。

**更新现有 skill 时**：扫描每个现有引用和捆绑资源，查找对应的更新，然后通过上述迁移门禁。迁移一项契约时，必须由 SKILL.md 提供直接的运行时指向；eval 或变更日志不能替代它。

接下来的三项检查是**升级探针，而不是无条件扩大范围**。如果执行其中任何一项会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖、权限或外部写入，请在修改 skill 之前停止，并重新归类为 Tier 3。Tier 1 和 Tier 2 可以检查这些问题，但不会因此获得新的交付物。

**脚本检查**：在宣布编辑完成之前，问自己：*源对话（或 eval 记录）写入了哪些代码，而这些代码在未来每次调用中都会被重新编写？* 如果所选层级已经授权进行这项能力工作，就将其封装到 `scripts/` 中（参数化、经过清理），并修改文档以指向它。否则，将这一信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的附带影响进行封装。分工如下：**脚本负责执行，文档负责理解**——如果一个 skill 的方法只存在于散文式说明中，那么每次运行都要重新支付完整的编写成本。这项检查之所以放在编辑步骤中，正是因为跳过 eval 循环的路径（对话提炼、直接编辑）不会到达 “Improving the skill” 中 eval 记录版本的这项检查。

**组件货架检查（针对嵌入工件的片段提出同一个问题）**：Scripts 检查覆盖 skill 执行的代码；生成工件的 skill（报告页面、演示文稿、文档）还会积累由其*输出*嵌入的片段——图片叠加组件、粘性导航、图表配置、CSS 块。如果连续生成的输出都各自手写相似的片段，这就是指向另一层货架的相同重复信号。在新增 `components` 子文件夹或注册表引用之前，应用上述升级规则；Tier 1/2 可以提出该方案，但不要创建组件能力。获得 Tier 3 授权后，将片段转化为货架组件的关键在于围绕它建立契约：(a) **原样嵌入块**——完整复制 BEGIN/END 标记到工件中，不依赖任何外部依赖，从而让单文件工件保持自包含；(b) **注册表条目**，说明交互契约（触发器、按键绑定、关闭行为、边缘情况）和来源——它来自哪个已交付工件、用户何时批准；(c) **准入门禁**——只有用户实际使用并批准过的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但外观漂亮的片段不得进入）；(d) **行为冻结，外观可调整**——经过校准的行为和按键绑定是契约，在不同运行之间不得漂移，而颜色和尺寸可以遵循工件的风格；(e) **回写循环**——为某个工件发明的片段，应在获得批准的同一会话中提升到货架中。其重要性不仅在于节省 token：手工重写的片段会发生*漂移*——每次重写都会 subtly 改变按键绑定、关闭行为、计数器；而对于每天阅读这些工件的用户来说，交互一致性**就是**产品体验。用用户为第一个此类货架提出的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：某报告页面 skill 的 lightbox-gallery 组件（图片叠加：←/→ 循环浏览组内图片，ESC 关闭，就地缩放，n/N 计数器）及其 interaction-components 注册表引用——该组件是在用户纠正跳转式引用的同一会话中提取的，并在交付前通过自动化点击流程测试进行了验证。参见方法论案例 17。

**流水线检查**：考虑此 skill 的输出是否会自然地传递给另一个 skill，以及是否应当由现有 skill 链接*到*此 skill。添加或实质性修改“下一步”交接或流水线契约，需要在编辑前重新归类为 Tier 3；Tier 1/2 可以提出这一建议，但不得顺手将其添加进去。

**引用与自应用检查（那些连谨慎的作者也会遗漏的缺陷）**：这是一组从内部看起来都像已经完成的工作、且没有任何一种能通过更加仔细地重读来捕获的失败模式——每一种都需要一个*机械化*操作。（开头特意没有写数量。“三种失败模式：”是一个派生出来的数字，任何人追加一个条目后它都会过时；而统计正文是最难精准捕获的漂移，因为正文*不包含发生变化的内容*——对列表进行重新编号的 grep 和 diff 都会直接略过它们。）它们在这里归为一组，是因为共享同一个原因：**写出断言和验证断言是两种不同的模式，而一次遍历无法同时进行这两件事。** 在你编写内容时，“参见规则 8”*就是*该断言；你并没有同时打开规则 8。

不同于上面的三个升级探针，这一项**不按层级限定范围**——它的范围取决于你写了什么。Tier 1 修复如果既没有添加指针，也没有添加规范性规则，就没有需要在这里做的事情；而且你不必自行判断：推论中的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 回答这个问题。在任何层级写了指针或规则？那么以下条目就适用。

- **你写出的每一个指针，都要打开其目标并从中复制一行出来——而且要在写指针之前完成。** 不要说“我确信那条规则列出了全部三个标记”：把其中一个片段粘贴到你已经为此步骤产出的内容中（审查备注、提交消息正文、你的回复，任选其一），放在之后的读者可以将它与目标进行核对的地方。你只是看过、却没有复制出来的片段，正是本句开头所拒绝的自我评估。错误的交叉引用在重读时不可见，因为错误的指针看起来与正确的指针完全一样，而作者又是唯一一个必然“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal rule 3”，想指的是一条关于不要引用过时枚举的规则——但被引用文档自身的*规则 3*讲的是样本量，实际要引用的规则位于另一个文件中；读者遵循该文档既有的自引用约定后，会落到一个无关主题上。同一次编辑还提交了一个方向颠倒的指针（对上方的材料写成“见下文”），以及一个指向不存在的章节标题的指针。
- **文件一旦包含两个编号列表，单独写“规则 N”就会产生歧义。** 检查是针对每个指针进行的，而不是针对整个文件：在写下“规则 N”之前，运行 `grep -n '^N\. ' <file>`，并确认在你所指的章节中恰好有一个匹配；如果有多个匹配，也要写明章节名称。（**不要**把它变成文件级别的警报，例如“此文件是否包含多个从 1 开始的列表”——对于任何长文档来说，这几乎总是如此，因此它会在健康输入上触发并被忽略，而纪律 #6 提醒我们，这比没有检查更糟；在这个文件上运行它，亲自看看结果。）真实案例中，一个单独写成“规则 1”的指针对应三个候选列表，而自顶向下的搜索首先命中了错误的列表。
- **写出任何规范性规则后，都要用其旁边的行来检查它——并让检查产出工件，而不是结论。** 使用与下方推论相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的 hunk。这里自己阅读就足够了——你并不是在进行模式匹配，因此不需要脚本——但必须带上该 ref：单独使用 `git diff` 只显示尚未暂存的工作，而一旦你执行 `git add`，它就会什么也不输出；这正是本段推论要规避的五种静默空结果模式之一。将新规则拆分成独立的条款，并逐条写下：在*同一个 hunk* 中，哪一行满足该条款。（下方推论中的 `scripts/reference_net.sh` 是另一项工作：它会列出供你解析的*正文交叉引用*。它不会把 hunk 交给你，也不会告诉你规则中的某个条款是否得到满足。）**某个条款旁边没有对应行，就是该条发现。** 那个诱人的简短版本——“我的新规则通过了吗？”——对于刚在 30 秒前写下它的人来说不可能失败；这正是纪律 #6 所说的应当优先采用可证伪观察而非自我评估的原因，因此本条也必须提供它所要求的同类工件。最先成为受害者的通常就是它旁边的段落。真实案例：新增一条规则，要求“始终同时报告原始计数和过滤后计数——差值*就是*污染”，但同一提交中的自身工作示例只打印了过滤后的数字。同一个 diff 中的另一条陈述引用了两个数值，却没有说明这些数值是否是在相邻的新规则刚刚规定为强制的限定条件下收集的。范围很小且有明确边界：不是“重新阅读文档”，而只是“我在 30 秒前写下的规则，在我在 30 秒前写下的行上是否通过”。
- **为每条新规则写一行，说明由谁执行它，以及他们是否确实能够执行。** 现有工具无法满足的规则，会被那些自认为已经遵守规则的人跳过——这是最糟糕的一类规则，因为它会产生有文档支持的虚假信心。真实案例：一条新规则要求“检查两个日志存储”；项目自身的规范性单命令排查工具却将其中一个硬编码为固定值，因此标准工作流会对该规则本来要捕获的故障恰好返回干净结果。规则本身是正确的，却没有实际作用，也没有提及这一缺口。**使这一点可证伪的工件**（没有它，本条就会成为禁止自我评估的这段文字中唯一一个自我评估）：写明哪个工具或命令能够捕获违规，然后**针对一个你已经知道它应该捕获的案例运行一次**。如果它在已知有问题的输入上返回干净结果，你就已经测量出该规则没有实际作用——将这一缺口直接写进规则本身。从记忆中回答“他们是否确实能够执行”正是纪律 #6 所拒绝的未经验证断言。**当没有任何工具能够判定该规则时**——大多数关于正文和品味的规则都属于此类，因此不要把它当作逃生口——工件就是那句明确指出这一点的话：*“没有任何东西强制执行这一点；只有在有人记得它时它才成立。”* 这比检查通过的状态更糟，而将其明确说出来正是重点；一个执行状态保持沉默的规则会被假定为已验证，而不是得到验证。请注意本条自身诚实的局限：工具和已知有问题案例的选择仍然属于判断，因此它只是移动了未经验证的步骤，并没有消除它——它比替代方案更便宜，但并非没有成本。
- **推论——你的修复本身也是缺陷来源，因此要在最后一次编辑之后重新检查你改动过的区域。** 在对单次变更进行的两轮审查中，第一轮产生了八个发现；第二轮又产生了八个，其中**七个是由第一轮修复引入的交叉引用错误**。重写一句话会移动其周围的锚点。这也是为什么对于读者依靠指针进行导航的工件来说，“它已经经过审查”不是终点：你一旦根据审查结果采取行动，审查就立即过时。重新检查是机械化的，而且它是一个**脚本**，不是让你重新输入命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的 bundle 中）。它会列出你添加的行之间的正文交叉引用，以便你打开每个目标，确认目标确实表达了你所声称的内容。首次使用前先阅读其头部——其中解释了它为何需要 base ref，而不是默认使用 `HEAD`，以及它有意**不**执行哪些操作。

**在开始编辑之前获取 `<base-ref>`，不要事后再获取。** 在开始时将其解析一次为字面量 SHA — 此刻执行 `BASE=$(git rev-parse HEAD)` — 并在此处以及上面的项目符号中复用同一个值。如果你运行了现有 skill 迁移门禁，它就是你已经建立基线所依据的 ref。稍后传入 `HEAD` 才是陷阱：提交后，`HEAD` 包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请恢复该值（使用 `git log`、`git reflog`，或提供给迁移门禁的基线），不要用 `HEAD` 替代；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印一条提示，但不要依赖在那里才发现这一点。

**为什么这里要使用脚本，而这一段的其余部分都是说明文字。** 它所替代的那条单行命令经历了五轮修补 — 将 diff 锚定到正确的基线、查看已暂存的编辑、在提交后仍能正常工作、跳过 diff 自带的 `+++` 标头、移除误导性的 `-n` — 其中四轮都增加了另一种让它不打印任何内容并以 0 退出的方式，而这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种问题的另一种形态：它移除的 `-n` 原本会打印带行号的实际命中，但行号是按管道传入的内容流计算的，因此看起来很权威，实际却指向错误位置 — 这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都会持续放过它本来要捕获的缺陷。说明文字无法验证自身的输入，无法说明发生了哪一种结果，也无法进行测试；脚本可以完成这三点，而它的契约是：**每一种结果都必须被明确命名，错误输入必须明确失败**。这正是本步骤前面提到的 Scripts 检查，只不过应用到了这一段 — 而这五轮修补正是忽视它所要付出的代价。

**读取它的判定结果，而不只是退出码。** 脚本只要成功运行就会以 0 退出，因此单独查看 `$?` 无法告诉你它发现了什么；答案位于判定行中，并且它始终会明确说明以下情况之一：找到引用（逐个解析）、文件与基线相同、文件已更改但没有新增行，或新增行中没有任何类似引用的内容。这些是不同的结果，脚本会有意将它们区分开来 — 这个检查曾将它们合并成一个无声的“没有任何内容”，正是这一原因促使它成为脚本。它只需几秒钟，并且不依赖警觉性，这正是规范 #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的指针 — “请参见下面的章节”、“如上面的规则所述” — 因此也要阅读新增的行。）

### 步骤 5：清理审查（任何公开 skill 都必须执行）

**在此门禁之前，当规范 #5 到期时，其独立检查必须已经运行**，并且当前更改对应的 `independent-review.md`（位于你的私有 git-tracked knowledge repo 中 — 不在已清空的工作区中，也不在任何已经公开或可能变为公开或进行分发的 repo 中）必须存在**并且已经提交**。对于新 skill，它始终适用；对于现有 skill，使用下一段中的阈值。一个未提交、仅存在于 git 工作目录中的文件，与一个从未写入的文件在实际意义上没有区别；`ls`/`test -f` 只能确认它位于磁盘上，不能确认它能够保留下来。对于**新** skill，这是你第一次将任何内容交出去的步骤，因此也是实际执行该规范的地方，而不只是陈述它的地方 — 一条位于使用点上方 1000 行、却没有任何检查机制的规则，每次都会输给追求完成的冲动。

**对于已经发布的 skill，修改离开你手中的那一刻就是 push，而不是这一步。** 这道关卡完全可以用一句“仅限内部，跳过”来回答；对于仅涉及文档的变更，打包甚至可能根本不会运行——因此把审查锚定在这里，意味着 skill 修改可能在没有任何独立审阅者查看过的情况下进入公共分支。真实案例（2026-07）：对这个文件本身的一次修改发布了一个 discovery 命令，而该命令无法访问旁边正文声称覆盖的三个根目录；它已经合并，直到之后专门委托进行的一次审查才发现了问题。**因此，对于现有 skill：独立审查及其记录产物必须在 `git push` / 创建 PR 之前完成——在 push 时运行的各道关卡（回归审计、验证、扫描）检查的都是结构，没有任何一道能告诉你说明是错误的。** 这保持了纪律 #5 的门槛不变：只有在*规则、契约或数字发生变化时*才需要执行，而拼写错误或纯格式重排则不需要。让拼写修复也必须等待一轮审查，恰恰会养成 #6 所警告的反射——“这次改动很小”变成普遍豁免，最终连真正重要的改动也会被它覆盖。

**对于要进入公共仓库的 skill，这不是可选项。** 私有内容经常泄露到公共 skill 中，而扫描器漏掉的泄露才是危险的——非英语语言中的真实姓名、真实转录中的逐字句子、插入示例中的真实内容。只有在该 skill 确实仅限内部使用时才可以跳过。

**按目标范围，而不是按主题范围来界定审查。** 只有公开发布的产物——skill bundle 本身——需要清理。留在私有仓库中的配套文档（skill 从中提炼出的事件报告、内部运行手册、项目的 CLAUDE.md）应保留真实的主机名、路径和时间戳：删改这些内容会破坏它们的审计价值，而你最终还会把修改撤销。有一次提炼会话之所以经历了三轮返工，正是因为清理流程被应用到了源材料涉及的所有内容，而不只是公共 skill。

**先检查目标位置，并让它预先填入建议。** 在 skill 将要存放的仓库中运行
`gh repo view --json isPrivate`（或者读取
`quick_validate` 已经打印出的提示）。私有目标应使选项 C 成为默认建议，而不是事后才想到的选项——“除非另有说明，否则假定为公开”正是把私有 skill 的工作路径变成无人要求的占位符的原因。

**触发清理的是目标位置的 `isPrivate`，而不是任务在主观上有多像发布。** 两者并不总是一致，而一旦不一致，除非明确指出这一点，否则最终起作用的就是主观感受。把内容*移入 marketplace skill* 会让人感觉像是在发布——marketplace 正是用于分发内容的地方——因此即使源仓库和目标仓库都是私有仓库、内容也不会流向任何地方，清理反射仍然会被触发。真实案例（2026-07）：一次从项目级 skill 迁移到私有 marketplace skill 的操作，把真实的配置路径、真实的十六进制值和一个真实的命名示例都泛化成了占位符。`quick_validate` **每次**运行都打印了 `🔒 audience: private`；作者每次都看到了，却仍然进行了清理，因为这种*活动*读起来像是在发布。代价并不只是表面上的——真实路径能让下一位读者去核对该值；而“项目自己的 token 文件”是无法打开的。

所以要把它当作查询，而不是判断：**读取目标的 `isPrivate`，如果它是
`true`，则进行脱敏需要所有者主动提出要求。** private→private 的移动是一次
移动，而不是一次发布。**当两个探针都没有返回结果时**（还没有远程仓库，
尚未运行 `quick_validate`），你就没有可用的查询结果——回退为将其视为公开并明确说明这一点，
因为不对称性就是如此：多问一个问题只会多花一句话，而不必要的信息泄露无法挽回。并且
`isPrivate` 报告的是目标**今天**的状态——一个位于私有仓库中、正准备发布的技能，
会在发布它的那次 push 中进行脱敏，而不是在这一次中进行。如果你发现自己开始思考某些内容在
私有目标中是否“应该”被泛化，这种思考本身就是信号。

使用 **AskUserQuestion** 确认深度（对于公开目标，确认深度，
而不是是否执行；对于私有目标，确认是否需要执行）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**脱敏流程——通读是方法，扫描是辅助：**

1. **亲自通读整个技能并进行语义判断**（这才是真正的检查）：SKILL.md + 每个参考资料 + 每个示例。对于每个具体名词 / 示例 / 代码片段，询问“是通用占位符或公开实体，还是从真实项目 / 人员 / 文字记录中直接取来的？”替换后者——即使扫描器没有标记它。只有这样才能捕获没有关键词的泄露。完整指南以及语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **将扫描器作为低成本的第一遍检查运行**：使用检查清单中的 grep 模式 + `security_scan.py`（步骤 6）。它们可以快速捕获明显的密钥 / 路径 / 已知名称——但“没有匹配项”不代表通过。
3. **替换**每个发现项为保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。从惨痛经验中总结出两条规则：占位符本身不能编码真实值——`<acme-corp-domain>` 恰恰泄露了它原本要隐藏的名称；应改为使用其*角色*命名（`<api-domain>`、`<upstream-provider>`）。另外，在编写批量替换脚本时，要提供一个明确的文件白名单，并将范围限定在技能目录内——未限定范围的查找替换会毫不犹豫地改写项目自己的 CLAUDE.md，并迫使你执行 git restore。
4. **通过重新阅读而不是重新 grep 来验证**：重新阅读已更改的部分，并确认没有损坏的引用。

### 步骤 6：安全审查

在打包或分发技能之前，运行安全扫描器，以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --frozen python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --frozen python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）
- 完整的发布内容集仅由 [scripts/packaging_policy.py](scripts/packaging_policy.py) 定义。打包、安全证明、内容哈希和回归审计都必须使用该共享策略；不要在说明文字中或针对特定消费者的过滤器中维护第二份排除列表。

**它不覆盖的内容**——这正是为什么仍然需要执行第 5 步的通读检查：gitleaks 和正则规则只会匹配*你列出的已知机密格式和模式*。对于没有关键词的私密内容，它们在结构上无法识别——例如非英语语言中的真实人物/项目名称、真实转录稿中的逐字内容、从你自己的工作中直接摘取的真实示例。`security_scan` 显示绿色，仅意味着“未发现已知格式的机密信息”，**并不意味着“该 skill 已完成脱敏”**。绝不要将其当作后者。

**首次设置：**如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 清洁（可以安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**对于私有 skill，发现项是信息，而不是待办事项。**扫描器无法判断泄露的凭据与*本来就应该存在*的凭据之间的区别——例如一个完整价值就在于预先填充好内容的模板，或一个指向其唯一运行机器的脚本。在私有仓库中绝不要自动修复：报告发现的内容，并让所有者自行决定。下面的选项 A（“自动修复”）适用于准备发布到公共环境的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包 Skill

skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.package_skill <path/to/skill-folder>
```

对于每个现有的 Git 跟踪 skill，必须先提供并重新验证已完成的审查，打包才会继续。当前标记仅是本地状态凭据，因此先提交或手动编写标记都无法绕过审查。下一次编辑后，审查将变为过期状态：

```bash
uv run --frozen python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及使用 `--include-evals` 发布根目录下的 `evals/` 目录（默认情况下，该目录作为开发资源被排除）：

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **在 Git HEAD 已包含该 skill 时，重新验证已完成的现有 skill 回归审查**；仅有标记永远不足以授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描一致）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，且不会创建软件包。

### 步骤 8：更新 Marketplace

打包后，更新 marketplace registry，将新的或更新后的 skill 纳入其中。

**对于新的 skill**，向 `.claude-plugin/marketplace.json` 添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于更新后的 skill**，按照 semver 在 `plugins[].version` 中递增版本号。对 skill 文件进行的任何更改——即使只是修复一行拼写错误——都需要递增版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧的 skill，而你的修复则一直处于未发布状态。

**然后将其记录到变更日志中——这一步经常被跳过。** 版本号递增使更新变得*可安装*；而条目则使它在六个月后有人遇到相同问题并进行搜索时变得*可查找*。如果变更日志记录了其他每个 skill 的版本，却默默漏掉你的版本，那比完全没有变更日志更糟：这些空缺会被理解为“那里没有发生任何变化”。

遵循现有条目的格式，而不是自行发明格式——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。在与版本号递增**同一个提交**中写入该条目；“稍后”更新的变更日志，最终往往永远不会被更新。

真实案例（2026-08）：某个 skill 连续发布了两个版本，版本号递增正确、门禁检查通过、PR 也已合并——但**完全没有变更日志条目**，因为这套流程中没有任何步骤要求添加条目。两次发布都只在之后的审计中才被发现。这正是纪律 #6 在本文档自身上的体现：存在于约定中的规则，如果没有落实为一个步骤，每次都会输给急于完成任务的倾向。

**保持 registry diff 最小——这是所有 skill 共享的唯一文件。** marketplace manifest 是所有并行编辑者都会发生冲突的地方，因此其中无关的格式更改比其他任何位置的同类更改代价都高：它会把原本干净的三行版本号递增变成冲突，让其他正在编辑的人难以继续操作。当你通过脚本更新它时（解析为 JSON、修改内容、写回文件），重写过程会悄悄规范化文件原本可能未采用的格式——末尾换行、缩进宽度、键顺序、unicode 转义。遵循往返操作规范：之后重新读取文件，并对其运行 `git diff --stat`；**其中只能出现你有意更改的字段对应的行。** 如果出现额外行，应恢复文件原有的约定，而不是提交这种规范化结果（某次脚本化的版本号递增，就曾给一个从未包含末尾换行的 manifest 添加了末尾换行——只浪费了一行 diff，而这恰恰是最可能同时被其他人编辑的文件）。同样的原则也适用于 skill 会涉及的任何共享 registry：lockfiles、catalogs、index documents。

**当 PR 经历了几次合并仍未结束时，请执行 rebase——然后证明你没有吞掉任何人的工作。** 让清单成为冲突高发点的同一属性，也会让它变得过时：一个同时修改注册表和变更日志的未合并 PR，只要其他任何内容落地就会产生冲突，因此应预期出现 `mergeable: CONFLICTING`，而不是把它当成意外（有个 PR 就是在某个下午 main 前进了 7 个提交后遇到这种情况的）。如果仓库采用 squash merge，请执行 rebase 而不是 merge——在压缩后的历史中，合并提交没有任何价值。冲突本身几乎总是**追加式的**：两位作者分别在同一节中追加了自己的条目，因此解决方式是**两者都保留**，绝不要使用 `--ours`/`--theirs`，因为那会悄无声息地丢弃同事添加的行。

人们会跳过的步骤，恰恰是能发现错误解决方案的步骤——**解决冲突后，证明与基准版本相比唯一的差异就是你自己的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
uv run --project <skill-creator-path> --frozen python -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要直接使用 `--force`：如果自你上次获取以来远程分支发生了变化，租约会让推送失败；这正是有人向你的分支推送过内容，而普通强制推送会将其覆盖的情况。

**插件边界不属于本 skill 的职责范围。** 是否应将 skill 拆分到不同插件中、如何布局 `source`/`skills`，以及用户能否单独切换 skill，都属于打包/分发领域——SSOT 是 `marketplace-dev` skill，而不是这里。当任务确实需要做出这些决策时：请确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与 `skill-reviewer` 需要其脚本时拉取 `skill-creator` 相同），然后阅读 marketplace-dev 的 cache-and-source-patterns 参考资料并遵循其中的指引。不要在这里重复其规则；复制一份只会导致内容逐渐偏离。

**重命名、迁移位置或移除 marketplace 条目，对于已经安装该条目的每位用户来说都是破坏性变更**——当条目消失时，Claude Code 不会清理已安装的副本，导致这些悬空安装在每次 `marketplace
update` 时都报错。应像处理 API 弃用一样对待此类变更：在变更日志中发布迁移说明，并遵循 marketplace-dev 对具体操作的指导。

**如果你亲自提交/推送 skill 仓库：** 对于已有 skill，如果当前变更触及 discipline #5 中关于规则/契约/数字的阈值，请确认审查产物记录了此次变更并且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不只是确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的审查不能满足当前的实质性变更。第 5 步的说明解释了为什么对于已经发布的 skill，真正的强制检查点是推送，而不是打包。然后只暂存 skill 的显式路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充满无关的变更，否则这些内容也会被一并带入提交（曾有一次提交混入了一堆无关的 transcript 文件，最后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库真实的可见性，不要根据路径想当然——一个公开的 skill 仓库应当通过 PR + 审查，而不是直接推送到 main。

### 步骤 9：发布或迭代

完成 skill 后，使用 **AskUserQuestion** 确定下一步：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试 skill 后，用户可能会要求改进。通常这会紧接着发生在使用 skill 之后，此时用户还清楚记得 skill 的表现。

**改进筛选：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了某项内容，则不要重复添加。

## Claude.ai 专属说明

在 Claude.ai 中，使用相同的验证深度路由器和严格评估授权门槛。当完整的通用配对流程获得明确授权后，工作流为：起草 -> 测试 -> 审查 -> 改进 -> 重复；但由于 Claude.ai 没有子代理，需要对部分机制进行调整。具体适配如下：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，读取 skill 的 SKILL.md，然后亲自遵循其中的说明来完成测试提示。一次执行一个测试用例。与独立子代理相比，这种方式的严谨性较低（你编写了 skill，同时也在运行它，因此拥有完整上下文），但它仍然是有用的合理性检查——而人工审查步骤可以弥补这一点。跳过基线运行——直接使用 skill 按要求完成任务即可。

**审查结果**：如果你无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或者你位于远程服务器上），则完全跳过浏览器审查环节。改为直接在对话中呈现结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），则将其保存到文件系统，并告知用户文件所在位置，以便其下载和检查。直接在线询问反馈：“效果如何？有什么需要修改的吗？”

**基准测试**：跳过定量基准测试——它依赖基线比较，而没有子代理时这种比较没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同——改进 skill，重新运行测试用例，询问反馈——只是中间不再进行浏览器审查。如果有文件系统可用，你仍然可以将结果整理到迭代目录中。

**描述优化**：此部分需要使用 `claude` CLI 工具（具体为 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过此部分。

**盲测比较**：需要使用子代理。请跳过此部分。

**打包**：`package_skill.py` 脚本可在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 上，你可以运行它，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新的 skill。在这种情况下：
  - **保留原始名称。** 注意 skill 的目录名称和 `name` frontmatter 字段——保持它们不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前复制到可写位置。** 已安装的 skill 路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从该副本进行编辑和打包。不要传递 `--new-skill`；非 Git 的现有 skill 副本仍然属于现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再将其复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 专属说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此经过明确授权的通用配对流水线可以运行基线和评分器。子代理可用并不等于获得授权，也不能据此增加额外角色；请说明必要的两组任务，限制并发，并在并行运行无法增加证据时按序运行测试用例。
- 你没有浏览器或显示器，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击、在浏览器中打开该 HTML 文件的链接。
- 在经过明确授权的**通用配对运行**之后，在你自行修改 skill 之前，使用 `generate_review.py` 为人类生成评估查看器；默认层级证据、未经授权的工作以及替代查看器机制的专用工作流，不会仅仅因为工作发生在 Cowork 中就产生查看器义务。
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。之后你可以读取该文件（可能需要先请求访问权限）。
- 打包功能可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器；但请将其留到 skill 完成、且用户同意其状态良好之后再执行。
- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新的 skill。请遵循上方 claude.ai 部分中的更新指南。

- 弄清楚 skill 的用途

- 在采用任何专用工作流退出方式之前，选择能够证伪此次变更的最低验证等级，并记录原因
- 起草或编辑 skill
- 运行该等级所要求的证据，或所选专用工作流声明的等效机制
- 对于获得明确授权的通用成对运行，与用户一起评估输出，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复上述过程，直到你和用户都满意
- 运行并通过现有 skill 回归审查；仅在 eval 中存活不算通过
- 打包最终 skill 并将其返回给用户。

如果你有 TodoList，请将选定的验证等级及其默认证据添加到其中。只有在明确获得通用成对管线授权后，才添加“创建 evals JSON 并运行 `eval-viewer/generate_review.py`，以便人类审查测试用例”。
