# Skill Creator

一个用于创建新技能并迭代改进它们的技能。

从高层来看，创建一个技能的过程如下：

- 决定你希望该技能完成什么，以及它大致应如何完成
- 将变更归类到能够证伪其可能失败模式的最低验证层级
- 编写技能草稿
- 在该层级进行验证：针对范围明确的修复执行定向检查，针对不确定的指令变更进行采样行为回放，或者针对新的 / 高风险 / 影响范围广的工作运行完整的配对评估管线
- 当所选层级产生定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写技能（如果定量基准测试中出现任何明显缺陷，也应重写）
- 重复直到你满意为止
- 仅当当前证据无法判定变更后的行为时，才提升验证层级

使用此技能时，你的工作是确定用户处于该流程的哪个阶段，然后介入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须缴纳的成本。对于可直接测试其正确性的范围明确的修复，不要创建评估文件、分派配对代理、给输出评分或启动查看器。

始终适用六项纪律，因为这些失败模式会交付看似令人信服但实际错误的技能：

1. **先验证，再编写。** 进入技能的每项技术断言（端点、参数、命令、版本、行为）都必须可追溯到你执行并观察到的内容——本次会话中，或某个已明确获批挖掘的会话中。现在无法验证？要么去验证，要么明确标注（“未经验证——来自记忆”）。一个技能会放大其中包含的所有内容：经过验证的知识会累积，自信陈述的错误也会累积。对于知识型技能（内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md) 获取操作版本：权威层级（观察到的行为 > 机器可读契约 > 已运行的生产代码 > 官方文档 > 记忆）、证据范围注释、发布前文档示例冒烟运行，以及受众 / Windows 可移植性检查清单。一项源依据审计曾发现，多项自信的契约声明与作者已获得的证据相矛盾（方法论案例 9）。
2. **将“不可能 / 不支持”视为假设，而非结论。** 当某项能力似乎被阻断时（API 错误墙、无法连接的工具、无法打开的格式），在将“平台不支持此功能”写入技能之前，穷尽观察路径——UI 自己的网络流量、替代渠道、不同的已文档化标识符。观察到的行为优先于推测性的请求形状。
3. **站在领域的肩膀上——在默认情况下，在编写或优化技能的方法论之前，将该领域既有的最佳实践检索到上下文中。** 技能的方法论质量仅取决于你上下文窗口中的知识，而不是潜藏于你权重中的知识：预训练是有损的、会过时，并且除非实际拉取了权威来源，否则通常甚至不会被激活。因此，你所编写内容的质量上限是 `your training data + the user's input`——*除非*你有意检索该主题领域真实的既有成果。去做：WebSearch 该领域的权威理论 / 标准 / 方法，并阅读该领域中任何已捆绑或已安装的技能，然后将承重原则连同归属一起融入技能。**这与下文的“既有成果研究”是不同的维度**——后者寻找可复用的*工具 / 基础设施*；前者以该学科长期积累的科学成果为*方法论质量*提供依据。将其作为**默认操作，而非等待被要求后才做的事**：简要告诉用户你正在借鉴哪个领域，并让他们可以说“跳过”，但绝不要在用户提示加你的记忆所限定的方法论质量上限下交付成果，因为只需一次搜索，就能获取该领域 40 年的公开成果。例如：数据可视化技能必须吸收 Cleveland & McGill 的图形感知排序和 Bertin 的视觉变量（位置 / 长度优于颜色，颜色优于文本——这是经过测量的，不是审美）；日期 / 时间技能必须呈现成熟的库及其经典陷阱；说服 / 谈判技能必须检索既有框架，而不是凭记忆重新发明它们。如果权威知识只存在于你的权重中，却从未进入上下文，那么你是在本可引用之处猜测。
4. **压缩现有技能之前先保留它。** 更新现有技能是一次迁移，而不是从空白页开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧包，或者从明确的 Git 引用中重建它；任意副本加上来源标签并不能构成基线。盘点运行时能力、触发上下文、接口、引用和评估覆盖范围。渐进式披露和简洁性允许移动或去重内容；它们不允许悄然删除行为。编辑后，运行 `scripts/audit_skill_regression.py` 并对每个未匹配的旧单元进行分类。仅存在于 `evals/`、测试或未链接引用中的运行时契约仍然会丢失。在任何候选项尚未分类，或任何真实缺口尚未修复时，不要称此次更新已完成。同样的逻辑也适用于*反转*，不只是删除，并且涵盖任何先前承诺——不仅是那些带有日期和名称的承诺：**推翻已作出的决定必须是一项提议，绝不能是副作用。**明确说出来并获得接受。悄然重写比悄然删除更糟，因为它一步便摧毁了制品和本可发现问题的证据——并且蒙蔽了所有下游审阅者（见 #5）。

5. **任何内容都不能仅凭自审就发布——一次独立、具备全新上下文的对抗性审查是固定步骤，不是特殊情况。** 你做出“现在已经没问题了”的判断，与产出该制品的是同一个模型，因此它共享了导致缺陷的完全相同的盲点。这是实测结果，不是民间传说：没有外部反馈时，内在自我纠正并不能可靠地提升输出，有时还会使其变差（Huang et al., ICLR 2024）；而当生成器和评估器共享错误模式时，迭代会**提高置信度，却不增加信息**。更多自检无法摆脱这一点；只有外部视角可以。**完整流程——提示词模板、锚点选择、发现记录表、实操案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；请在第一次审查前阅读。** 核心规则如下：
   - **独立性有两个层面，而第二个正是作者容易忽略的。** *审查者的上下文*不能是你的上下文的分支——分支会继承你的盲点，并返回一张“已审查”的凭证。但它所衡量的*证据*也必须位于**变更影响范围之外**，否则它会继承你的**结论**：它读到的是一个制品和一份已经相互一致的规范，并报告二者一致。注意，“本次会话中未编辑过”这一界线过于薄弱——在参考资料的受控案例中，被污染的记录是在*前一天*编辑的，三名审查者都没有发现其未修改副本中能够发现的缺陷。按你接触过它们的难易程度为锚点排序：用户自己的对话记录原话 > 早于该工作提交的 git 引用（`git log --oneline <ref>..HEAD -- <path>`；你提交的任何 commit 都会使其失去资格）> 只追加日志（这是一种约定，不是强制机制）。**全新项目没有锚点——请明确说明并要求提供一个，不要报告一次实际上未执行的通过审查。**
   - **只给它两样东西：制品和读者规范。** 不要给其他内容——不要给设计理由、项目背景，也不要说“只确认 X 没问题”，因为这会把独立审查者变成橡皮图章。读者规范是*规范*，不是理由，因此它无法为任何内容背书；省略它会浪费一半的审查，因为审查者随后只能拿自己作为衡量标准。**对于 SKILL.md，读者是另一个执行它的 agent**，它的失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——询问它哪些指令无法执行。在运行前说明规范，此后绝不使用它来解释掉发现的问题。
   - **它在可理解性和相对于语料库的完整性方面是真实依据；它对品味没有裁决权。** 直接应用这两点。将“这可能是个 bug / 我建议改成 Y”视为假设，并先自行复现。绝不委托判断 AI 垃圾内容或美学问题——同模型盲点。
   - **枚举失败*维度*，而不是内容领域——这也决定了需要运行多少名审查者。** 维度是*你提出的问题*；领域是*你阅读的材料*。三名审查者分别覆盖场景、算术和 diff，但都在问“这是否连贯？”，等于让一名审查者做了三次并付了三次费用。**一名审查者是默认配置，并且经常足够**；仅在需要增加一个维度时才增加一名。自审最差的维度是**忠实性**——“这是否仍忠实于已作出的承诺？”——因为作者正是移动承诺的人，而连贯性与忠实性彼此正交：一个制品可以完美地自洽，却完全不忠实于已经决定的内容。
   - **留下一个制品，否则这就只是一条警告。** 纪律 #6 规定，产出观点的检查不如产出制品的检查——所以这项审查也必须产出一个文件，否则它恰恰会在关键时刻输给追求完成的驱动力。在你的私有、受 git 跟踪的知识仓库中，在 `skill-reviews/<skill-name>/` 下编写 `independent-review.md`：**逐字保留审查者提示词**（这样后续读者可以判断它是否具有引导性）、**每条发现的处理结论及理由**（这是合理筛选与丢弃令人不适的发现之间的分界）、以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识仓库（或你没有这样的仓库），请明确说明并询问用户——不要猜测一个落入任一禁区的位置。两个禁区：**不得放在 `<skill-name>-workspace/` 中**（这些会被清理的 gitignored 临时目录——此文件是跨会话的审查证据，必须在其中幸存）以及**不得放在任何现在或将来可能公开或分发的仓库中**——这通常排除了被审查 skill 自己的仓库（审查内容天然会引用私有路径、真实姓名和项目细节）。在进行实质性编辑后，应使用*新的* agent 重新审查——规则、契约或数字发生变化，而非仅修正错别字。**从步骤 5 开始，此文件就是该审查已发生的证据；没有它就意味着审查未发生。** **写入文件不等于它会在下一次会话中存在——在同一轮中于该私有仓库执行 `git add` + `git commit`。** 一个未提交、放在 git 工作目录中的文件并不具备本规则所要求的任何“git 跟踪”保障：它可能丢失、被覆盖，或根本不会被后续检查“这是否经过审查？”的流程获取（真实案例：文件正确写入了正确路径，包含真实发现——但后来仍未通过自动化检查，因为它从未被提交；修复方式是一次 `git commit`，而不是迁移文件）。
   - 纪律 #4 的回归门禁是机械性的、互补的：它证明你没有*删除*行为。它并不说明你所写的内容是否实际上能够被遵循。

6. **将你编写的检查设计为无法自行认证通过。** Skill 在很大程度上由检查构成——关卡、清单、“发布前”步骤——而如果执行上下文能在*违反其所编码的规则时*仍通过某项检查，那么它比没有检查更糟，因为它会制造信心。以下四条规则借鉴自早于软件解决过这一问题的领域：
   - **验证必须覆盖规则中的每一项条款。** 如果规则写的是“A + B + C”，证据必须分别要求证明 A、*以及* B、*以及* C。一条附加在三条款规则上的确认行，会被作者已完成的任意一个条款满足；其他条款则不可见。真实案例：一个报告编写 skill 带有一道交付关卡，其规则写道：“选项以并列的 chips 形式呈现 + 突出显示推荐项 + **将背景写成完整、自足、陌生人也能理解的句子**”——但其下方的证据行只要求“共 N 个决策项，全部渲染为 chips”。作者运行关卡，写下这条证据，自行认证通过，然后发布了一个页面：其标签只有单个字符，所有上下文都被删除。规则始终都在文件中；只是检查从未衡量过那一条款。
   - **对健康输入误报的检查比没有检查更糟。** 上面的失败案例是一项本应失败却通过的检查；这里则是它的镜像——一项本应通过却失败的检查。它代价更高，因为它会教会操作者形成条件反射式的绕过行为（`--no-verify`、`SKIP=1`、`--force`）；一旦这种反射形成，关卡就会对*所有*输入失效，包括那些它原本就是为之构建的输入。因此，在编写失败即阻断的检查时，**假阳性优先于假阴性**：漏掉一个真实问题的代价只是那一次实例，而误杀一个健康输入的代价则是整个关卡。
     留意这个迹象：**反复踩到同一个陷阱所产生的挫败感本身就是风险信号**——这恰恰是作者会发布一个从未针对健康输入进行校准的防御措施的状态。真实案例：一天内三次踩到同一个格式陷阱后，作者向 linter 添加了一条正则检查；它在项目自己的语料库中误杀了 **33 个健康输入**，并在同一小时内被回滚。启用前先校准——在真实、已知正常的材料上运行任何失败即阻断的检查，并确认零假阳性；宁可放宽它，让它偶尔漏报，也不要让它发生一次误报。
   - **让每个项目都是可证伪的观察，而非自我评估。** “背景是自足的”无法被写下它的人判定为失败；“遮住页面其余部分，单独阅读一张卡片，并说明它在决定什么”则可以。优先选择会产出制品的检查——命令输出、引用的行、截图——而不是产出观点的检查。
   - **同样的怀疑也适用于你*运行*的检查，而不仅是你编写的检查。** 上述四条规则约束的是随 skill 一同发布的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本也同样是仪器；错误的仪器会和正确的仪器一样自信地报告干净结果。在一次 2026-07 会话中，五条独立的验证命令在两个方向上都说了谎：一个未带 `-L` 的 `find` 报告已安装 skill 的文件缺失（它们位于符号链接之后）；一个 `grep --exclude-dir=<name>` 隐藏了正在审计对象的第二份副本；一个反转的 shell 条件错误告警某项删除并未发生；一个跨越换行符的正则凭空制造了 55 处“丢失的引号”；而一次只搜索五个文件中两个的操作，报告有两条规则缺失，但它们实际存在于第三个文件中。**其中每一项起初都被相信，且每一项都只是在重新运行一个形态不同的检查后才被发现。**

最古老的实验实践修复方法是：**在把仪器用于你不知道答案的案例之前，先在一个你已知答案的案例上运行它。** 要 grep 一个你预期不存在的字符串？先用完全相同的命令形态 grep 一个你知道存在的字符串——如果它也返回 0，那么坏的是命令，不是文件。这只需多写一行，就能将“我检查过了”变为“我用一台校准过的仪器检查过了”。

     有两种具体的命令形态值得记住，因为它们都在上文出现过，并且都会*静默*失败：`find` 不会在没有 `-L` 的情况下跟随符号链接（而 skill 安装常常是指向源代码仓库的符号链接），并且 `--exclude-dir` 会按树中任意位置的基名匹配，而不只是在你设想的路径处匹配。

     **这条规则还有后半部分，只有当检查被交付出去时才会造成问题：应当针对*标准*实现校准，而不是你机器上的那个实现。** 上述仪器规则能保证*你的*结论诚实；这一部分则能保证*读者的*做法有效。写入 skill 的工具行为断言——一个标志、一个递归模式、一个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而两端的差异都是静默的：它在你测试时可用，却对他们悄然毫无作用。有两种机制会导致这种情况，而且在一次会话内部都不可见：**相同的命令名称解析为不同的程序**（shell 别名或函数遮蔽了二进制文件——注意 `\tool` 只能绕过*别名*，因此只有 `command tool` 或绝对路径才是确定性形式），以及**同一个程序在不同实现之间表现不同**（BSD 与 GNU，或某个可替代实现）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，将其作为解决符号链接陷阱的方法写入 skill，并发布到一个有 1200 星的公开仓库——他们的 `grep` 是通过 shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 上，相同的 `-R` 什么也匹配不到（它需要 `-RS`），因此为大多数读者规定的修复方案静默失败，且恰好位于那个警告验证器会静默失败的章节之中。

     因此：**在有关工具行为的断言进入已交付的产物之前，针对标准二进制文件重新运行它**（`/usr/bin/<tool>`），而不是针对 shell 交给你的那个版本。如果它无法通过这种验证，就不要写这个标志——**优先采用与实现无关的表述方式**：自行解析路径（`readlink -f`），而不是押注于递归标志；在脚本中进行子字符串测试，而不是使用面向行的匹配；指出你需要的*行为*，而不是你碰巧知道的选项。只在你的环境中有效的处方比没有处方更糟，因为读者没有办法发现它悄然什么也没做。

   - **采用成熟的清单实践已经确定的做法。** 判断列表是 **READ-DO**（边读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭借专业经验执行，然后在定义好的**暂停点**停下来确认——适用于时间压力下的资深操作人员），并将其锚定在真实的暂停点，而不是“工作流中的某个位置”。只保留**致命项**——既关键、又经常在压力下被遗漏的事项，大约五到九项；更多内容会稀释遵从性（[Gawande, *The Checklist Manifesto*](https://www.shortform.com/blog/types-of-checklists/)）。并且应优先采用 Shingo 的**控制**而非**警告**（[poka-yoke](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，且会输给完成驱动力；而阻止进展或强制产出工件的步骤根本不需要警觉性。当 skill 只能发出警告时，至少应将警告放在做出决策的位置——**如果一条规则被放在执行上下文从不打开的参考资料中，那么在实践中，它就不是规则。**

另一方面，他们可能已经有了该技能的草稿。在这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应始终保持灵活。如果用户说“我不需要跑一堆评估，就随意和我一起做吧”，你也可以改为那样做。

然后，在技能完成之后（但同样，顺序是灵活的），你也可以运行技能描述改进器。我们为此准备了一个单独的完整脚本，用来优化技能的触发方式。

## 首先：共存检查（官方 skill-creator 插件）

在做任何其他事情之前，先快速检查一次（只需一次 grep，常规路径无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 不做任何事——不要安装任何内容，也不要向用户提及本节。继续开展工作。
- **存在：** 官方插件的 skill-creator 与此版本现在会以几乎相同的描述同时出现在技能列表中，因此未来会话会随机路由到其中之一。用一两句话向用户说明这一点，然后提供以下选择（绝不可未经其同意就执行）：
  1. **推荐**——运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型、自检式的 SessionStart 钩子复制到其 Claude 配置中，并在 `settings.json` 中注册它（同时创建备份），从而使每个未来会话都能确定性地将技能工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 恢复；在用户按名称请求时，官方插件仍可完全正常使用。在没有官方插件的机器上，安装程序会拒绝安装任何内容，因此它绝不会遗留无用的钩子。
  2. 备选方案——`claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），它会将官方条目完全从技能列表中移除，从而消除歧义。

如果钩子已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目存在），则静默跳过以上所有内容。

同一套机制也适用于用户创建的技能：当其技能有意与已安装技能重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一个套件——请参阅 Prior Art Research 下的“Coexistence & Precedence”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

### 使用 AskUserQuestion（重要 — 请阅读）

**在每个决策点都应积极使用 AskUserQuestion 工具。** 在存在结构化选项时，不要在对话中提出开放式文本问题。这是你能够实现的最大用户体验改进，用户可能同时处理多个窗口，并且已有 20 分钟没有查看此对话。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段以及刚刚发生的事情（1-2 句话）。用户可能已切换到其他上下文。
2. **简化**：用通俗语言解释该决策。不要使用函数名称或内部术语。说明它**做什么**，而不是它叫什么。
3. **推荐**：先给出你的推荐，并用一句话说明原因。如果选项涉及工作量，请同时展示两种衡量标准：`(human: ~X min / Claude: ~Y min)`。
4. **选项**：提供 2-4 个具体的、带字母编号的选项。每个选项都应是清晰的操作，而不是抽象概念。

**规则：**
- 每个问题只处理一个决策，绝不合并不相关的选择
- 提供退出选项（AskUserQuestion 中始终隐含“其他”选项）
- 接受用户的选择，可以提示权衡，但绝不拒绝继续执行
- 如果存在没有权衡的明显答案，跳过提问（只需说明你将做什么）
- **如果问题在无人回答的情况下超时（用户离开键盘），既不要停滞，也不要直接推进涉及偏好或范围的决策。** 先完成无副作用的准备工作：编辑前快照、清单盘点、评估用例收集、只读审计/健康检查；将判断性决策（重构方向、删除内容、是否继续）留到用户回来后。然后明确说明你完成了什么，以及哪些事项正等待他们决定。

## 创建技能

### 捕捉意图

首先理解用户的意图。当前对话可能已经包含用户想要沉淀为技能的工作流（例如，他们说“把这个变成一个技能”）。如果是这样，先从对话历史中提取答案，包括：使用过的工具、步骤顺序、用户作出的修正、观察到的输入/输出格式。用户可能需要补充缺失部分，并且在进入下一步之前应进行确认。

**来源盘点 — 始终在起草之前进行，并遵守同意边界。** 盘点实时对话以及重叠的现有文档/技能（参见“既有实践研究”）。更早的本地会话 JSONL 文件属于独立的私有来源：除非用户明确要求挖掘历史记录，或在你说明将要读取的内容后明确批准使用该来源，否则不要打开或解析它们。如果获得批准，请通过对话挖掘工作流的脱敏提取，仅纳入相关的先前会话；绝不要将原始转录内容加载到你自己的上下文中。如果未获批准，则根据实时对话和现有项目来源继续推进，不要将缺少历史记录视为阻碍。

在挖掘对话（或会话转录内容）时，盘点**两类资产 — 它们应落在不同的位置**。*知识*，例如端点、参数、陷阱和决策规则，应成为 SKILL.md 指引或 `references/` 中的内容。*会话中不得不编写的代码*，例如辅助脚本、注入式片段、渲染器和一次性模板，则是 `scripts/` 的候选内容：如果本次会话编写了它，下次调用时就必须重新编写它，因此应将其参数化、净化并打包。先前的提炼保留了润色后的文字，却遗漏了可复用的辅助工具；普遍的经验是，同时关注知识→references 和代码→scripts 两条路径。

当源材料是*过去的*会话记录（Claude Code 项目目录下的 JSONL 文件），而不是实时对话时，不要将其加载到自己的上下文中——一份大型记录可能耗尽上下文窗口并丢失会话。应改为委派子代理进行提取，并明确指示它们用脚本逐行解析、截断每个提取字段，并且只返回精炼的经验教训列表——原始记录绝不能进入主上下文。

**首先，在回答下面四个问题之前，确定这是哪个方向。** 请求可能属于几种*相反*的情况：构建一个新的 skill / 编辑一个现有 skill / 优化 skill-creator 本身 / 或者根本不是 skill（一次性任务）。猜错会浪费整个会话——你为“新建 skill”所做的研究，对于“优化元工具”来说就是错误的研究。当措辞存在歧义时（例如“帮我做个 skill”，同时指向 skill-creator 自身的路径），此处花 30 秒使用一次 AskUserQuestion 是值得的。下面的包装器 skill 分支是其中一种特殊情况；方向检查则是通用要求。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在何时触发？（哪些用户表述/上下文）
3. 预期的输出格式是什么？
4. 我们是否应设置测试用例来验证该 skill 是否有效？具有可客观验证输出的 skill（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。具有主观输出的 skill（写作风格、艺术、品味校准型报告）通常无法使用断言——但“没有断言”不等于“无需验证”。其验证路径按成本从低到高排列：
   - **历史任务重放**：重新运行该 skill 过去曾服务过的一条真实提示词，对比旧版与新版 skill 的输出，并依据发生变化的具体规则进行比较（“新输出是否真的遵循了此次更新引入的令牌 / 标题语法？”）。成本低，能捕捉到“规则写了，但没有任何东西读取它”的问题。
   - **将生产使用作为评估**：承认真正的测试是用户下一次实际使用——然后明确这个闭环：之后每一次用户修正都是应回填到 skill 自身“迭代/活文档”部分的一次事件，每一次认可都是语料材料。一个没有这种回写习惯的品味型 skill 不会改进；具备这种习惯的 skill 即使从不运行正式评估，也会逐步收敛。**而当 skill 的输出是持续运行的东西——守卫、监控器、定时任务或钩子——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户修正要求用户先注意到问题，并愿意反馈；已部署的机制会主动报告自身状态，通常在一天内就会发生，而误报是这种报告最尖锐的形式，因为它证明你写下的一条规则是错误的，这是任何反复重读都无法揭示的。应将第一次误报视为计划内的评估结果，而不是麻烦：在假定机制行为异常前先检查它，因为更可能的发现是*指令*写得过于绝对。（真实案例：一个 skill 规定了一个明确失败的检查，部署后的检查在夜间对一个完全健康的条件触发了一次，而修复方式是更正 skill 中那句过于绝对的表述——没有人投诉；是遥测数据发现了问题。）
   - 对视觉输出进行**渲染 + 人工审查**（遵循 skill 自身的视觉 QA 门槛），绝不能用伪装成美学衡量的 grep 断言。**并且，你用于验证的渲染器必须与交付物实际会被使用的引擎相同**——任何恰好已安装的预览器都不能作为替代品。布局引擎不同于目标应用程序的缩略图工具会悄悄*掩盖*你正在寻找的缺陷，而在错误引擎上得到的绿色验证比没有验证更糟，因为它会带来虚假的信心。真实案例（2026-07）：一个 `.docx` 通过 macOS Quick Look 缩略图进行了“视觉验证”，但该工具无法复现两端对齐文本的拉伸；用户一在 Word 中打开文档，信息块就被拉得支离破碎。修复方法是安装与 Word 兼容的引擎（LibreOffice）、转换为 PDF、逐页栅格化，并阅读每一页。匹配引擎，否则验证就是表演。**这不仅适用于渲染器，也适用于每一种验证工具**——解析器、linter、validator：它必须与生产环境共享实现，否则它的绿色结果毫无意义。第二个案例形态相同：一位作者试图通过在源文件阶段使用与生产工具链不同的 markdown 实现，来捕捉会损坏最终文档的标记模式——它将三个已知的错误输入全部解析为完全正常，因此任何基于它的预检查都会悄悄放过所有内容。诚实的结论是，这个特定缺陷只能在生产工具运行之后检测，而检查应放在那里。**当没有可用工具与生产环境共享实现时，应说明该检查无法在那个阶段完成——不要构建一个只能产生虚假绿色结果的检查。**
   根据 skill 类型建议合适的默认方案，但由用户决定。

在从对话历史中提取答案（或提出问题 1-3）后，使用 **AskUserQuestion** 确认技能类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类决定了后续的整个评估策略。在这里判断正确，避免之后浪费精力。

### extend-vs-create 检查 — 在进入任何专用分支**之前**运行

以下三个专用工作流中的每一个都以“**不要**继续阅读以下章节”结束，而 *既有成果研究* 恰好位于它们之后。**这种顺序是版式，而不是执行顺序。** extend-vs-create 判断适用于每个分支，跳过它正是一次会话最终交付了一个与已安装技能重复的技能的原因。

因此，在路由至 wrapper-skill / conversation-mining / artifact-corpus 之前，先回答一个问题：**是否已经存在一个技能，其能力范围涵盖此项功能？**

**发现根目录，不要凭记忆回想它们。** 手动维护的安装位置列表正是容易过时的产物，而你忘记的那个根目录正是会给你带来麻烦的那个。

**搜索文件，而不是名为 `skills` 的目录。** 技能目录以*技能*命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、市场克隆和插件缓存中根本不存在名为 `skills` 的目录——搜索这个名称会在看似正常工作的同时悄悄跳过它们。每个技能都有一个 `SKILL.md`；这就是不依赖布局的定位方式。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，并且仍会返回比你需要的更多结果；请使用与该能力更具体相关的术语而不是通用术语来缩小范围（`chart` 会匹配所有内容，`stacked bar` 则不会）。

这会触及的根目录，以及通常会被记忆清单遗漏的内容：skill 源仓库（一个 `claude-code-skills` 检出目录及任何 `-pro` 同级目录）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件，源仓库中没有任何线索表明它们存在）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、按 profile 划分的配置主目录（`~/.claude-profiles/<name>/`），以及完全没有任何路标的那个：**每个项目自身的 `.claude/skills/`**。第 2 步让这成为一项经过验证的结论，而非继承而来的说法。

**每项目 skill 在结构上不可见。** 它们存在于无关项目的工作树中，因此不会出现在任何 marketplace、全局 skill 列表或源仓库清单里；你在规划一个新 skill 时通常会打开的任何东西，都不会提到它们。真实案例（2026-07）：一个会话为某个领域构建了一个全局 skill，遍历了源仓库、全局目录和其他 agent 目录，一无所获，然后发布了。之后的一次对话历史搜索找到了一个针对完全相同领域的成熟项目级 skill，已有一个月历史，位于某个项目的 `.claude/skills/` 中，其中包含新 skill 缺失的八条规则，包括一条用户亲自口述的规则。除了每项目根目录以外，所有根目录都检查过了，而扫描以十足的信心报告“没有既有先例”。

**当重叠项*确实*是无关项目中的项目级 skill 时该怎么做**：这是上面那个故事让你置身其中的情形，也是下面三条要点未涵盖的情形。你无法将其添加为某个套件的同级项，因为它根本不属于任何套件；而“扩展它”则意味着编辑无关项目的工作树。实际有效的做法是：**将它的规则提炼到你正在构建的 skill 中，然后在所有者同意的情况下弃用该项目本地 skill**。它是针对真实工作编写的，因此应将其视作更成熟的来源，并*向它*协调。弃用他人的工作 skill 是所有者的决定，而不是你构建过程的副作用。

这句话遗漏了四件事，而其中每一件都会让你停下来：

- **“向它协调”是一项可反驳的推定，不是一条规则。** 有两种标准退出情形：项目 skill 可能已经*过时*（规则是数月前针对一个已经变化的系统写下的），也可能是*项目特有的*（规则只在该项目的约束下成立，整批导入会让你的 skill 变得狭窄，而本文件其他部分明确要求你不要这样做）。提炼出的规则是另一位作者的记忆，因此请像纪律 #1 要求的那样，**重新验证每一条规则**，再将其写入 skill。
- **“弃用”需要一种机制，而它的第一步并不是你第一时间会做的事。** 按顺序：

  1. **先用 `find` 查找 skill 的*实体*，再用 grep 查找它的*引用*。** 一个 skill 在同一仓库中通常有多个副本：`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会由不同工具从同一个工作树加载。Grep 回答的是“谁提到了它”；只有 `find` 能回答“它有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要把 skill 自身的名称放入 `--exclude-dir`**（它按 basename 匹配，因此会隐藏每一个同名目录，包括你尚未发现的副本，参见纪律 #6 中的工具规则）。真实案例（2026-07）：一次弃用操作正是这样做的，修复了它找到的全部五个引用，却在 `.agents/skills/` 下留下了第二个完整副本：受 git 跟踪、没有弃用标记、缺少最新规则的过时快照，而另一个工具仍会将其作为有效内容加载。
  2. **在删除任何内容之前，验证从旧 skill 所在位置实际能够访问到新位置。** 你刚刚推送的 marketplace skill 在 marketplace 更新且 plugin 已安装之前并不算已安装；若先弃用，期间就会出现两者皆不可用的窗口：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项：plugin 缓存经常通过符号链接指向源仓库，而不带它的 `find` 会报告文件缺失（参见纪律 #6 中的工具规则）。
  3. **然后** grep 查找引用，并重新指向仍在生效的引用。区分**有效指令**（skill 列表、交叉引用、告知下一个 agent 应使用什么的交接文档）与**历史记录**（写着“日期 X 我们发布了这个”的决策日志条目）：重写后者会为了修复一个并不存在的问题而破坏审计轨迹。
  4. **然后**将每个实体替换为一个 `superseded by <skill>` 存根，而不是直接删除，并使每个副本的存根逐字节完全一致。**保留 YAML frontmatter**：没有它的 `SKILL.md` 可能无法加载，而不是以提供信息的方式失败；但应重写 `description`，让存根宣告其自身已被弃用，而不是继续宣传旧触发条件，否则它仍会在不再提供服务的路由中胜出。正文只需要：能力迁移到了哪里，以及说明其迁移原因的一行文字。
- **使用下面的所有权测试识别所有者**（它同样适用于这里：项目级 skill 没有 `marketplace.json`，但项目的 `git remote` 仍会告诉你它属于谁）。当所有者正是你正在交谈的人时，“同意”就是一次 `AskUserQuestion`。**当所有者无法联系时，只提炼，不要弃用**（这会让两个 skill 都继续生效并竞争同一触发条件，与被拒绝弃用后的最终状态相同，参见下文的 Coexistence & Precedence）。
- **如果所有者拒绝弃用它**，现在就有两个 skill 在竞争同一个触发条件；这属于下文的 Coexistence & Precedence 问题，而不是失败。

**按能力词汇搜索，而不是按技能名称。** 那个项目技能不会匹配对新技能标题的名称搜索；它匹配的是其正文中的领域术语。针对新技能将处理的*概念*，在候选根目录中执行 grep 搜索。

如果存在重叠：

**判断应适用哪个要点 — 这是谁的技能？** 文件系统命中不携带所有权信息。读取市场的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在包含它的仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中，同样可能只是你*自己的*市场又被安装回了你的机器。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 能回答同一个问题。

有两种情况这些探测方式会得出错误结果或无法回答，因此在信任结果前先检查它们：**fork** 会显示你自己的 remote，但内容属于其他人 — 将其视为第三方，因为他们上游的改进仍然无法传递给你。而当**没有 marketplace.json 且没有 remote** 时（本地专用项目、手动复制到全局技能目录中的技能），探测方式是沉默而非否定：**询问所有者，不要猜测**。

- **重叠的是第三方的技能**（市场套件、官方插件）：**不要重新实现其能力。** 编写一个能正确驱动它的*薄增量* — 你遇到的陷阱、正确的调用方式、经过验证的辅助脚本 — 并且**通过命名空间名称引用它**。将别人的引擎克隆到你的包中，是代价高昂的错误：他们的升级不再能传递给你，两份副本还会悄无声息地逐渐偏离。
- **重叠的是你自己的技能**：扩展它，或者在其现有套件中添加同级技能。一个为相同触发条件竞争的独立技能对任何人都没有帮助。**例外：**如果它位于*无关项目*的工作树中，则这两种做法都不适用 — 请参见上面的项目级情况。
- **某个相关技能已经指向你正在填补的缺口**（例如，其描述写着“对于 X，使用 Y”）：完成构建后，闭环处理 — 更新该指针，否则你会留下一个悬空引用。

只有在完全没有重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**一次真实的 2026-07 会话花了一天时间，才让第三方 docx 引擎生成正确的中文商务文档，随后却准备走向封装技能分支 — 该分支会直接跳过既有方案研究。它当时准备交付的形态，是一个重新承载该引擎能力的新技能。正确的形态应是一个**三层引用链**：第三方引擎保持不变 → 一个薄增量技能，保存正确用法以及经过验证的生成脚本 → 调用该增量技能的领域工作流技能。用户不得不两次指出问题，它才最终落地；第二次修正更为精准：*"不要额外复制一个 — 在他们的基础上写出正确用法，并引用他们的技能；这才是技能即代码的含义。"*

### 验证深度路由器（在选择任何工作流之前运行）

在采用通用或专用工作流分支之前，选择能够证伪变更后行为的**最低层级**。按失败表面而非代码行数分类：一条变更后的破坏性命令的重要性可能高于大篇幅的文案清理。测试前说明所选层级及一句话理由。专用工作流可以替换不兼容的机制，但绝不能绕过层级选择，也不能悄然降低所需的严谨性。

| 层级 | 适用场景 | 所需证据 | 默认不要添加 |
|---|---|---|---|
| **1 — 定向验证** | 这是一个现有 skill；未新增或实质性变更能力、触发器族、工作流分支、输出契约、依赖项、权限或外部写入行为；且编辑严格属于以下之一：(a) 不改变行为的纯拼写/格式修改，(b) 可由直接权威来源判定真伪的事实性文档/配置修正，或 (c) 恢复明确既有契约的有界实现修复，**并且**确定性的回归检查能够覆盖修复后的行为。可能改变 agent 行为的澄清不属于第 1 层级 | 对这三种情况都应运行 `quick_validate`、检查 diff，并完成现有 skill 迁移门禁。然后仅使用对应的证据：(a) 精确回读/格式检查；(b) 权威事实及其范围狭窄的检查；(c) 明确的既有契约及确定性回归。仅当满足纪律 #5 的规则/契约/数值阈值时，才添加其要求的一次全新审阅者审查 | Agent 行为回放、配对运行、基线、评分器、基准测试、查看器、eval 文件 |
| **2 — 抽样行为验证** | 以下条件全部满足：这是一个现有 skill；变更会影响 agent 行为；确定性检查无法完全判定；未引入新的或实质性变更的能力、触发器族、工作流分支、输出契约、脚本行为、依赖项、权限或外部写入；并且 1–2 个具有明确验收标准的命名示例能够覆盖整个变更后的行为 | 仅运行这 1–2 个有代表性的带 skill 回放，加上范围狭窄的确定性检查，以及纪律 #5 要求的一次全新上下文审查 | 基线、配对扇出、方差分析、基准测试、查看器或 eval 文件。请求其中任一项都会将工作重新归类为第 3 层级 |
| **3 — 完整评估** | 以下任一条件成立：任何新 skill；任何新的或实质性变更的能力；大范围重写或方法论扩展；触发器/描述优化；新的或实质性变更的工作流分支、输出契约、脚本能力、依赖项或权限；高风险自动化或外部写入；评估需要跨 3 个以上不同提示类别的证据、重复试验/方差，或需要在实质上不同的方法之间做出选择；或用户明确要求 A/B、基线、基准测试或查看器证据。主观判断本身不会使原本范围狭窄的第 2 层级变更升级 | 对通用工作流，运行以下完整的配对流水线：真实案例、带 skill + 基线、断言、评分、聚合基准测试、分析人员审查和查看器。专用工作流只能替换其明确标记为不兼容的机制；运行其完整验证协议以及每个兼容的第 3 层级步骤，并记录其替换的内容 | 无——这是刻意采用的重型路径 |

当较低层级暴露出未解决的行为或相互矛盾的证据时，升级处理。用户提出取消或降级评估的请求会覆盖**执行授权，而非分类**：立即停止已经启动的配对评估代理、基线、评分器、聚合和查看器工作。Tier 3 变更仍然是 Tier 3；将其所需的重型证据记录为用户豁免或未完成，而不是将较低层级证据重新标记为通过。仅继续执行用户仍授权的证据收集，不要声称已完成完整的 Tier 3 验证。当纪律 #5 的规则/契约/数量阈值被触发时，不要取消其单个新鲜上下文审阅者，也不要取消为防止破坏性或外部影响所需的任何安全门。机械化的现有技能迁移审计、公开技能净化以及任何特定领域的安全门也始终独立于此路由器。

### 专用工作流：第三方 CLI 工具的包装器技能

在投入通用技能创建流程之前，请检查引导至当前阶段的会话是否实际上需要使用**包装器技能**工作流。包装器技能是一种配套技能，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或技能包，即由他人编写、且用户刚刚在一个会话中花时间让其能在自己机器上正常工作的代码。

适用的信号（任意两个同时出现即可）：

- 用户在当前对话中一直在安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 此会话产生了真实、具体的错误消息，且用户与 Claude 已经为这些错误找到了具体修复方法（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个整理成一个技能”、“将其保存为包装器技能”、“这样其他人就不用再经历一遍了”、“把这次 session 做成一个 skill”之类的话。
- 用户明确按名称提及某个第三方工具，并希望其他代理或其他人能够使用它，而无需承担他们刚刚付出的学习成本。

不适用的信号（应改用上方的通用工作流）：

- 用户想要为他们准备从头编写的内容创建一个技能。
- 会话进行得很顺利——没有需要捕获的真实阻碍。
- 该技能将包装用户拥有或控制的服务（这是他们的代码；应编辑源代码，而不是创建包装器）。
- “工具”实际上是一种不涉及安装任何二进制文件或包的方法论或工作流。

当包装器技能工作流适用时，保留上方选定的验证层级。创建包装器即创建新技能，因此属于 Tier 3。**不要**继续阅读下方的通用编写章节；请跳转至 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端遵循该工作流，包括其验证协议。这是一个**回溯式提炼**工作流——其职责是从当前对话中挖掘安装流程、已修复的缺陷和已作出的设计决策，并将这些挖掘结果转化为一个完整、自包含的包装器技能，使另一位用户能够安装并从中受益，而无需重新经历这次调试会话。

包装器技能工作流拥有其自身的架构契约、代码模板和 Tier 3 验证协议——由于其输出是用户的安装状态，而不是可轻易断言的文件，它会替代不兼容的通用测试用例机制；这并不降低工作的标准。运行每一项兼容的通用 Tier 3 步骤，并记录哪些机制由专用协议替代。规范参考实现是 `ima-copilot` 技能（位于 daymade/claude-code-skills 仓库根目录——此处曾有一个裸相对链接在该技能移入套件时失效，这正如下面的跨技能引用规则所警示的那样），它是对腾讯 IMA 技能的包装，源自一次使用此精确工作流的真实会话提炼。

### 专用工作流：从对话历史丰富技能

在确定采用通用的技能创建流程之前，请检查该会话是否实际上要求**将过去的对话提炼为一个技能**。当用户在多个 Claude Code / Codex 会话中一直在调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这会很有用。

适用信号（任意一项即可）：

- 用户说了类似“挖掘我的聊天历史中的模式”、“将这次对话变成技能参考”、“将我们学到的内容提炼到技能中”、“用我的对话丰富此技能”或“把这次对话沉淀到 skill 里”的话。
- 该会话明确是在从最近一次多轮调试或设计会话中提取经验教训。
- 用户希望基于他们已经进行过的真实对话，向现有技能添加一个 `references/` 文件。
- 目标技能已存在，目标是用从对话中挖掘的知识来丰富它，而不是从头构建。

不适用信号（请改用上面的通用工作流）：

- 用户正从单个提示或想法创建一个全新的技能。
- 用户想要为他们刚安装的第三方 CLI 工具创建包装器（请使用上面的包装器技能工作流）。
- 没有可挖掘的本地对话历史，也没有可处理的导出记录。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件中。
- 源材料是一批用户已认可的已完成产物，而不是对话——请使用下面的产物语料提炼工作流。

当对话挖掘工作流适用时，请保留上面选定的验证层级。新建的挖掘技能为 Tier 3；只有在满足该层级的能力边界时，丰富现有技能才能保持在所选层级。**不要**继续阅读下方的通用编写章节；请跳转至 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流：它会发现本地 Claude Code 项目会话、Codex 转录记录和命令历史，对其进行脱敏，将其划分为适合代理处理的块，运行挖掘代理，并在验证后将生成的候选参考资料提升至目标技能的 `references/` 中。

对话挖掘工作流拥有自己的架构契约、智能体提示词、模板和验证协议。该协议实现所选层级的专用机制；运行每个兼容的通用步骤，并记录任何替代方案。它是将真实对话历史转化为技能可复用知识库的规范方法。

### 专用工作流：从已批准工件语料库中提炼用户偏好

在采用通用流程之前，检查该会话是否要求**从一批用户认可的已完成工件中提取用户的真实偏好**——已批准的 HTML 报告页面、生成的文档、设计。这是第三种提炼来源，与上述两种不同：材料是**产品，而非对话**，输出是**可执行的品味**（明确原则、量化参数、词汇），而非知识或安装修复。

适用信号（任意一项即可）：

- 用户列出已完成的工件，并说“这些都是我认可的样例”/“你来学到底什么是我想要的”/“extract my preferences from these approved examples”。
- 某个品味校准技能（报告生成器、文档样式工具、演示文稿构建器）拥有持续增长的已批准样本语料库，且用户要求让该技能从中*学习*，而不只是为其建立索引。
- 用户抱怨先前的更新“只加了示例”——仅编录了样本，却没有改变技能行为。

不适用信号：源材料是对话/修正，而非认可的产品（使用对话挖掘）；样本未获得用户个人批准（批准是准入门槛——先询问）。

适用时，保留上面选择的验证层级，然后跳转至 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其验证协议。一个新的语料库衍生技能属于第 3 层；为现有技能添加实质性的新决策能力也属于第 3 层。该专用协议实现所选层级的语料库机制，不会降低其要求；运行每个兼容的通用步骤，并记录任何替代方案。其核心准则同样适用于任何时候向现有技能添加材料：**编录 ≠ 提炼**——在语料库表中登记一个样本不会改变技能的下一次运行；对每次添加都要问：“*这是否改变了某项决策规则？*”，若所写内容的答案全都是否定的，就不要宣称提炼会话已完成（方法论案例 15）。该工作流的主线：针对所有工件进行脚本提取的定量比较（每种模式至少 3 个工件的阈值，对每项声称的不变量检查例外清单）→ 带有证据锚点的分层归纳 → 写入决策规则层（将不变量与依赖语域的变量分离）→ 独立完整性审计（常设准则 #5）→ 回归审计。

### 先前技术研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策、竞争优势——是让技能具备价值的关键。任何公共仓库都无法提供这些内容。但当成熟工具已经存在时，用户不应浪费时间重新发明基础设施（API 客户端、认证流程、速率限制）。先前技术研究会为基础设施层寻找构建模块，使技能能够专注于编码用户独特的方法论。

**两个轴，不要混为一谈。** 本节针对的是*基础设施*层（可复用的工具 / MCP / 库 / 现有 skill）。*方法论*层则有它自己的两个输入：用户的私有优势（仅属于用户本人，无法检索）**以及该领域已经确立的最佳实践 / 科学知识；按照既定纪律 #3，默认将其检索到上下文中。**找到合适的工具并不能免除第二项要求——一个采用了图表库、却从未吸收 Cleveland/Bertin 理论的可视化 skill，其能力上限仍然只是你的预训练知识。两者都要做。

**按以下顺序搜索这些渠道**（第 4-8 项使用子代理并行执行）：

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **对话历史** | 用户已验证的工作流、经过验证的 API 模式、调试期间做出的修正 | 在最近的对话中搜索服务/API 名称 |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有 skill | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区 skill | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作方插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 面向同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自己的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己的成熟模式和现有集成。用户的私有 SOP 始终优先——公共工具是构建模块，而不是替代品。在竞争性领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**优先选择合并/扩展，而不是新建，并扫描每一个 skill 根目录——不要只检查 `~/.claude`。** 当渠道 1-3 找到与请求领域重叠的现有 skill 时，通常正确的做法是扩展或合并到其中——**但如果它位于无关项目的工作树中，方向则相反：应当从中提取内容，应用到正在构建的 skill 中，而不是合并到那个 skill 里**（参见上文 extend-vs-create 检查中的项目级案例）（一个真实的“新建 skill”任务最终变成了“将现有 extractor 做成新 archiver 的 extract 阶段”），不要交付一个会争夺相同触发条件的平行 skill——两个重叠的 skill 会争抢触发机会并使用户困惑。搜索时，**应发现安装根目录，而不是凭记忆列出目录**——使用上文 extend-vs-create 部分中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会漏掉源码仓库、市场克隆和插件缓存，因为其中的 skill 目录是以 skill 命名的）。执行覆盖范围检查，不要只相信这句话：**每个项目自己的 `.claude/skills/`** 是凭记忆列出的清单最容易稳定漏掉的根目录，因为该项目之外没有任何地方会引用它。用户已经在*任何位置*安装的 skill 都是最有价值的先例，而项目本地的 skill 往往最成熟：它是在真实工作中编写出来的。

**如果发现公开的 MCP 服务器或技能，请克隆并验证，不要相信 README：**

1. **阅读实际源代码** — 许多项目的 README 制作精美，但代码库内容空洞
2. **验证认证方法** — 它是否与 API 实际的认证方式匹配？（`X-Api-Key` 请求头、Bearer 或 OAuth — 很多人会弄错）
3. **检查测试覆盖率** — 零测试意味着原型，而非生产级
4. **检查维护情况** — 最近一次提交日期、未关闭 issue 数量、对 bug 报告的响应情况
5. **检查环境兼容性** — 代理/网络假设、硬编码的 DNS/IP、地区限制
6. **检查许可证** — MIT/Apache 可以；GPL/SSPL 可能与专有使用冲突
7. **检查依赖规模** — 庞大的依赖树会带来冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 处理基础设施 | **采用它，并在其上构建** — 安装 MCP，然后将该技能构建为编码用户方法论的工作流层 |
| 存在部分 MCP 或 SDK | **扩展** — 将其用于基础设施，并在技能中补齐缺口 |
| 公开技能覆盖相同领域 | **仅将其用作结构灵感** — 竞争性领域中的公开技能按定义都是通用的。用户的优势在于其私有 SOP |
| **存在互补技能，可提供你正在构建内容的一项子能力** | **打包它** — 将互补技能自包含的资产复制到你的包中并接入。不要依赖用户已预先安装它。请参阅下方“互补技能” |
| 不存在任何公开内容 | **从头构建** — 在编写完整技能之前，验证 API 访问模式是否可行（认证、端点、代理） |
| 集成成本 > 构建成本 | **构建它** — 一个你拥有的、耗时 2 小时的自定义实现，胜过一个存在集成阻力和上游风险的“成熟”工具 |
| 用户有意取代已安装的技能（分支、加固版） | **随附 supersede kit 一起发布** — 请参阅下方“共存与优先级” |

#### 共存与优先级（有意重叠）

合并到现有技能是解决重叠问题的默认方法（如上所述）。但当用户*有意*发布一个与已安装技能重叠的技能时 — 例如官方插件的分支、经过加固的内部版本 — 这两个条目将以相似的描述同时出现在技能列表中，而 Claude 会随机在它们之间路由。按逐步升级的方式解决：如果重叠是意外的，则重命名；添加描述性决胜条件（“取代 X — 当两者同时出现时，始终使用此项”）；对于分发的分支，则使用 `scripts/generate_supersede_kit.py` 将条件 supersede kit 写入技能中 — 这是一个基于同意的 SessionStart 路由钩子，只会安装在实际存在竞争方的机器上，拒绝在其他地方安装，并且如果任一方消失便会自行禁用。机制、决策表、SKILL.md 示例措辞和沙箱验证：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此技能针对官方 skill-creator 插件自行采用同一个 kit（参见顶部的“首先：共存检查”）。

**更常见的情况：你的新技能在没有任何刻意分叉的情况下，悄然失去了对*已安装技能集合*的触发权。** 一个技能的领域（图像生成、PDF 处理、仪表盘）通常已经挤满了多个已安装技能，而一个新技能可能会失去对它们所有技能的自动路由。因此，**要尽早验证触发情况——内容写得好并不代表构建已经完成。** 草稿完成后，通过 `claude -p` 发送几条真实的查询，并检查新技能是否确实胜出；如果没有，**请指出它输给了哪个具体的竞争技能**（不同查询往往会输给不同技能）。然后请了解两点：(1) **在拥挤的触发位中，文案并不总能胜出**——解决阶梯是重命名 → 描述中的决胜信息/SUPERSEDES → 手动调用 → SessionStart 路由钩子（结构性方案；会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的规范）；以及 (2) **修复方案取决于竞争技能由谁编写**——竞争技能是*第三方*的 → 接受手动调用或使用路由钩子；竞争技能是*你自己的* → 将它们合并/整合为一个，不要让你的两个技能争夺同一个触发条件。（完整的解决阶梯位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是唯一事实来源；这里和上面的摘要只是指针，请不要独立扩展它们。）记录所选择的路径（例如，添加一条“Activation”说明：“手动调用，竞争技能为第三方”）可以避免下一次会话重新争论此问题。（方法论案例 13）

##### 互补技能（打包，而非依赖）

构建一个会触及已有互补技能所在领域的技能时，你有两种选择：

- **依赖其已安装**：脆弱——用户可能没有安装它，或者安装的是不同版本。每一次缺失依赖失败都可追溯到这个选择。
- **打包它**：将互补技能自包含的资产（脚本、模板、参考文档）复制到你自己的包中，并将它们接入，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就应将其打包。** 这对以下内容尤为重要：
- 状态栏 / UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证 / 清理脚本
- 通用数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要一个状态栏。`statusline-generator` 技能提供 `generate_statusline.sh`。与其依赖用户先运行 `statusline-generator`，配置文件设置技能会打包 `statusline.sh`，并在 `claude-profiles-init` 期间将其接入每个新配置文件。这两个技能仍然各自独立有用，但这个包装技能可以独立运行。

**反模式**：在 SKILL.md 中写“请先运行 `other-skill` 的安装程序”。这会将依赖转嫁给用户，并产生脆弱的安装顺序。应当改为打包。

研究完成后，通过 **AskUserQuestion** 展示发现：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑虑，应倾向于采用成熟的基础设施作为底层支撑，并为方法论层构建自定义逻辑——价值所在正是这里。

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。在把这一部分梳理清楚之前，不要编写测试提示。

检查可用的 MCP——如果它们有助于研究（搜索文档、寻找类似技能、查阅最佳实践），则在可用时通过子代理并行研究，否则以内联方式研究。提前准备好上下文，以减轻用户负担。

### 编写 SKILL.md

基于用户访谈，填写以下组成部分：

- **name**：技能标识符
- **description**：何时触发、它的作用。这是主要触发机制——既要包含技能的功能，也要包含使用它的具体场景。所有“何时使用”的信息都放在这里，不要放在正文中。注意：目前 Claude 倾向于“触发不足”——即在技能有用时却不使用它。为应对这一点，请让技能描述稍微更“主动”。例如，与其写“如何构建一个简单快速的仪表板来展示内部 Anthropic 数据。”，不如写“如何构建一个简单快速的仪表板来展示内部 Anthropic 数据。无论用户是否明确要求‘仪表板’，只要用户提及仪表板、数据可视化、内部指标，或希望展示任何类型的公司数据，都务必使用此技能。”

  **控制篇幅：description 有 1024 个字符的硬性上限，验证会拒绝任何更长的内容。** 这与上文“主动”的建议存在直接冲突——为提高覆盖率添加的每个触发短语都会消耗篇幅预算——因此，应在扩展之前而非之后测量：`len(description)`，不要凭感觉。陷阱不在初稿（它很少接近上限），而在于*数年后的更新*为了新增覆盖范围而添加触发条件：成熟的描述通常距离上限只差几十个字符，此时**增加一个触发条件就是零和博弈——你需要删除现有的一个来为它腾出空间。** 要有意识地做出这一取舍，并在提交中说明，因为一个被悄然删掉的触发短语确实会缩小技能的触发范围，而且没人会注意到，直到它不再为某人触发。（实践中的案例：一次更新为新覆盖的失败模式添加了触发条件，将描述推至 1280 个字符，经过两轮压缩才达到 1003——代价是三个已有的触发短语，这本应是一个明确的决策，而不是在与验证器较劲时才发现的结果。）必须删减时，优先删除其场景仍可通过同义词或相邻短语覆盖的表述，保留那些没有其他触达路径的表述；还要记住，正文中的限定语（“在平台 X 和 Y 上”、括号中的枚举）通常比删除独立触发短语更适合删减——正文可从内容中重新推导，触发短语则不能。
- **compatibility**：所需工具、依赖项（可选，通常不需要）
- **技能的其余部分 :)**

### Skill 编写指南

#### Skill 的构成

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。通过在 `---` 标记之间配置以下字段来设置 skill 的行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必填 | 描述 |
|-------|----------|-------------|
| `name` | 否 | skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 建议填写 | skill 的功能以及使用时机。Claude 会使用此字段来决定何时应用该 skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在 fork 的子代理上下文中运行。** 请参阅下方的“Inline 与 Fork：关键决策”——选择错误会导致 skill 无法正常运行。 |
| `agent` | 否 | 设置 `context: fork` 时要使用的子代理类型。可选值为 `Explore`、`Plan`、`general-purpose`，或 `.claude/agents/` 中的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 可阻止 Claude 自动加载此 skill。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false` 可将其从 `/` 菜单中隐藏。适用于用户不应直接调用的背景知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略该字段会让 skill 获得由用户权限设置控制的完整工具访问权限。设置该字段会不必要地限制 skill 的能力。 |
| `model` | 否 | 此 skill 激活时要使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指示预期的参数。例如 `[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 限定于此 skill 生命周期的 hooks。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** skill 内容中的 `$ARGUMENTS` 会被用户在 skill 名称后提供的文本替换。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### Inline 与 Fork：关键决策

**这是设计 skill 时最重要的架构决策。** 选择错误会悄无声息地破坏 skill 的核心能力。

**关键限制：子代理无法生成其他子代理。** 使用 `context: fork` 运行的 skill（作为子代理）不能：

- 使用 Task 工具生成并行探索代理
- 使用 Skill 工具调用其他 skill
- 编排任何多代理工作流

**决策指南：**

| 你的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **Inline**（无 `context`） | 子代理无法生成子代理 |
| 调用其他 skill（Skill 工具） | **Inline**（无 `context`） | 子代理无法调用 skill |
| 为外部 CLI 运行 Bash 命令 | **Inline**（无 `context`） | 在主上下文中拥有完整的工具访问权限 |
| 执行单个专注任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境干净 |
| 提供参考知识（编码约定） | **Inline**（无 `context`） | 指南可以丰富主对话 |
| 被其他 skill 调用 | **Fork**（`context: fork`） | 必须作为子代理才能被生成 |

**编排器 skill 示例（必须使用 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专家 skill 示例（使用 fork 正确）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，不使用 task）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skills 应该是**正交的**：每个 skill 处理一个关注点，并通过组合协同工作。

**模式：编排器（inline）调用专家（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（不能使用 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，在隔离的子代理上下文中运行
3. 每个 skill 都应只有一个职责，不要将编排与执行混合在一起
4. 通过参考资料（例如检查清单、模板）共享方法论，而不是复制代码

##### 流水线交接（顺序 Skill 链式调用）

除了编排器/专家组合之外，skills 通常还会形成**顺序流水线**，其中一个 skill 的输出会成为下一个 skill 的输入。每个 skill 完成工作后，都应主动建议合乎逻辑的下一步。

**模式：SKILL.md 末尾的“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion 由用户主动选择 — 永远不要在未询问的情况下自动调用下一个 skill
2. 仅在输出自然地适合作为另一个 skill 的输入时才提出建议 — 不要强行建立关联
3. 包含一个 "No thanks" 选项 — 用户可能不需要完整的流水线
4. 建议中应解释为什么下一步会有帮助（例如："ASR 输出通常包含识别错误"）
5. 最多保留 1-2 个建议 — 选项过多会造成决策疲劳

**何时添加交接：**询问"这个 skill 的输出是否通常会成为另一个 skill 的输入？"如果是，则添加一个 "Next Step" 部分。如果这种关联很少见或牵强，则不要添加。

**反模式：**串联不共享自然数据流的 skill。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 优先自动检测，而不是手动标志

**永远不要为可以自动检测的能力添加手动标志。**不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: 自动检测并告知
Step 0: Check available tools
  - `which codex` → 如果找到，则告知用户并启用跨模型分析
  - `ls package.json` → 如果找到，则针对 Node.js 项目调整提示
  - `which docker` → 如果找到，则启用基于容器的执行

# Bad: 手动标志
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力自动检测，范围由用户决定。skill 应发现自己能够做什么并据此行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | Subagents 可以使用 |
|-------------|----------------|-------------------|-------------------|
| (default) | 是 | 是 | 否（内联运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（显式委派时） |

#### 渐进式披露

Skills 使用三级加载系统：
1. **元数据**（名称 + 描述）- 始终处于上下文中（约 100 个单词）
2. **SKILL.md 正文** - skill 触发时处于上下文中
3. **捆绑资源** - 按需加载（不受限制，脚本可以执行而无需加载）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。一份没有填充内容的 600 行 skill，优于一份遗漏关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问："每个部分是否都发挥了应有的作用？"如果是，就保留它。如果某些部分只是凑长度，或者解释了 Claude 已经知道的内容，就删减这些部分 — 不要删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分为参考文件，而不是人为地将所有内容压缩进一个简短的主文件。
- 对于现有 skill，渐进式披露是一种重新定位策略，而不是删除启发式方法。旧的运行时契约必须仍然可以从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或评审者记忆都不能替代运行时契约。
- 在 SKILL.md 中清晰地引用参考文件，并说明何时读取它们
- 对于较大的参考文件（>300 行），包含目录

**领域组织**：当一个 skill 支持多个领域/框架时，请按变体组织：
```text
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的 reference 文件。

#### 不令人意外原则

不言而喻，skills 不得包含恶意软件、利用代码，或任何可能危及系统安全的内容。如果对 skill 的意图进行描述，其内容不应让用户感到意外。不要配合创建具有误导性的 skills，或旨在协助未经授权的访问、数据外泄或其他恶意活动的 skills。不过，诸如“扮演 XYZ”之类的角色扮演是可以的。

#### 写作模式

指令中优先使用祈使语气。

**定义输出格式** - 可以这样写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式** - 加入示例很有帮助。你可以这样排版（但如果示例中使用了 "Input" 和 "Output"，可能需要略作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得融入 skill 的可用性模式** - 以下四个结构性要素反复将“能运行但令人困惑”的 skill 转变为用户真正能够操作的 skill —— 它们是让高频使用的 skill 变得易用的具体增强措施，因此当 skill 具有多种模式、会运行命令或可以重复运行时，请考虑采用：
- **入口决策树**：如果 skill 有多种模式，请以一个简短的“用户说了 X → 使用模式 Y”映射开头，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧跟在命令之后展示“你应该看到的内容”，这样模型（以及用户）就能区分真正的成功和无提示的失败。
- **故障排除部分**：列出已知的失败模式及其修复方法 —— 对于需要在你无法查看的机器上运行的 skill，这是最有价值的部分。
- **第 0 步幂等性检查**：如果重复运行可能会重复已完成的工作，请先进行一个低成本的“是否已经完成？”检查，再执行任何开销较大的操作。

### 写作风格

尽量向模型解释事物为什么重要，以此代替大量强硬、陈旧的 MUST。运用心智理论，努力让 skill 具有通用性，而不是过度局限于特定示例。先写出草稿，然后以全新的视角重新审视并改进它。

### 日期和版本引用

**保留事实性日期 —— 它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 skill 应写成 “Suno v5.5 (March 2026)”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 August 2025，则使用旧 API”）——日期一过，这种逻辑就会失效，而且没人会更新它。

规则：
- **发布日期、“上次验证”日期**：保留。这些是参考时间点，而不是失效日期
- **定价、排名、法律状态**：包含，但要标记为易变信息（“截至上次检查约为 $0.035/gen”），让读者知道需要重新核实
- **“X 日期之前执行 Y，X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠/弃用部分记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当相同代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省 token、具有确定性，可在不加载到上下文的情况下执行
- **注意**：Claude 仍可能需要读取脚本，以便进行修补或针对环境进行调整
- **用户可修改的数据存放在捆绑包之外**：如果脚本会积累用户数据（修正词典、学习到的偏好、缓存），请将其存储在稳定的、相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其单独备份——绝不要将其放在 skill 目录中。每次更新和套件迁移都会删除并重新创建 skill 安装，而相对于主目录的存储会原样保留。这正是一个持续积累词典的 skill 能够在完整套件迁移后实现用户数据零丢失的原因

##### 参考资料（`references/`）

用于按需加载到上下文中，以便为 Claude 的处理和思考提供信息的文档与参考材料。

- **何时包含**：当 Claude 工作时需要参考相关文档时
- **示例**：用于金融 schema 的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库 schema、API 文档、领域知识、公司政策、详细的工作流指南
- **优点**：保持 SKILL.md 精简，仅在 Claude 判断需要时加载
- **最佳实践**：如果文件较大（超过 10k 个单词），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或 references 文件中，不要两者都存放

##### 资源（`assets/`）

不打算加载到上下文中，而是供 Claude 在生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用相关文件时
- **示例**：用于品牌资源的 `assets/logo.png`，用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件货架**：对于生成制品的 skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、逐字嵌入的片段，这些片段带有固定的行为契约和注册表引用——请参阅第 4 步中的组件货架检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标受众。**以下内容描述的是 skill 面向陌生用户发布时会出现的问题。对于存放在作者自己的私有仓库中的 skill，相同的“违规”通常正是它能够正常工作的原因——真实的绝对路径能让脚本直接运行，模板中的真实账户能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 包含该 skill 的仓库是否为私有仓库），并在此情况下将可移植性/标识符相关问题降级为提示；当私有 skill 准备发布时，`--audience=public` 会强制执行严格检查。

**对于私有 skill，这些问题由所有者决定，而不是由你决定。** 不要在未询问的情况下为真实路径添加占位符、重写硬编码凭据，或对示例进行“清理”——这样会为了满足一条原本针对另一个发布目标而编写的规则，破坏一个正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，让所有者自行决定。（设计先例是 npm 的 `"private": true`：声明的发布目标会改变工具所执行的规则；之所以加入这一机制，是因为人们总是不小心发布内容。）

**对于计划公开分发的 skill，这是关键要求**——其中不得包含特定于用户或公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，例如 `~/.claude/skills/`
- **允许**：skill bundle 内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（严格按禁止列表实现的验证器会将此 skill 自身标记出来——对正常输入误报，比漏报更糟）：当发布者自己的名称/品牌是解决 supersede 平局或归属要求所必需时，可以使用；当段落讨论这些路径本身时，可以使用类似 `~/.claude/skills/` 的安装路径（这是教学材料，而不是硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于此 skill 自己的 bundle 内”——验证器和读者都会如此理解，因此指向另一个 skill 文件的裸路径会验证失败，也会误导读者。引用另一个 skill 时，应在正文中注明其所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用带命名空间的名称调用 skill（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。当 skill 在不同 suite 之间迁移时，裸跨 skill 引用会静默失效——一次 suite 迁移就导致两个清理阶段中出现了 21 个失效的跨引用。

##### 版本管理

**关键要求**：SKILL.md 不应包含版本历史或版本号：

- **禁止**：在 SKILL.md 中使用版本章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **原因**：Marketplace 基础设施负责版本管理；SKILL.md 应包含不会随时间变化的内容

#### Reference 文件命名

文件名必须做到无需阅读内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：仅从文件名本身，某人能否理解文件内容？

有两个例外：使用连字符的名称与使用下划线的名称同样合适（分隔符从来都不是重点——重点是名称能够自我说明）；位于已命名 workflow 目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已通过目录限定——目录提供了具体性，重命名它们会破坏各 workflow 之间的平行结构。

### 完整评估测试用例（仅限 Tier 3）

仅当路由器选择通用 Tier 3 路径，或用户明确请求完整评估流程时，才进入本节。不要仅仅因为 SKILL.md 发生了更改就使用本节。Tier 3 专用工作流遵循上文声明的替换契约。

编写 skill 草稿后，提出 2-3 个现实的测试提示词 — 即真实用户实际上会说的话。**对于作用于实时系统的 skill（正在运行的服务、已登录的客户端、生产数据），请为每个测试提示词明确副作用预算** — 例如“进行只读探查并结束；不要执行下载或驱动 UI”。在“只是测试”时修改实时环境的评估，实际上是真实操作，而不是测试。通过 **AskUserQuestion** 呈现这些测试提示词：

```
Skill 草稿已准备好。以下是我想运行的 [N] 个测试用例：

1. "[test prompt 1]" — 测试 [what aspect]
2. "[test prompt 2]" — 测试 [what aspect]
3. "[test prompt 3]" — 测试 [what aspect]

每个测试都会运行 skill + 一个基线（不使用 skill）以进行比较。
预计总耗时：约 [X] 分钟。

建议：现在运行全部 [N] 个测试用例。

选项：
A) 运行所有测试用例（推荐）
B) 运行测试用例，但先让我修改它们
C) 在运行前添加更多测试用例
D) 跳过测试 — 这个 skill 看起来已经足够好，可以发布
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言 — 你将在下一步运行进行期间起草断言。

{

  "evals": [

    }
  ]
}
```

完整架构请参阅 `references/eval_pipeline_schemas.md`（包括稍后添加的 `assertions` 字段）。

## 完整成对评估流程（仅限通用 Tier 3）

仅在选择通用 Tier 3 路径后运行本节。只要 Tier 3 仍获授权，这就是一个连续流程 — 不要中途停止。用户取消或降级会覆盖本段要求；按照路由器中的规定停止繁重流程。不要将其机械地用于 Tier 1、Tier 2，或明确由其工作流替代的专用机制，也不要使用 `/skill-test` 或任何其他测试 skill。

将结果放入 skill 目录同级的 `<skill-name>-workspace/` 中。在工作区内按迭代组织结果（`iteration-1/`、`iteration-2/` 等），每个测试用例在其中对应一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有目录 — 只需在处理过程中逐步创建。

### 第 1 步：在同一轮中启动所有运行（包括 with-skill 和 baseline）

对于每个测试用例，在同一轮中启动两个子代理：一个使用 skill，另一个不使用。这一点很重要：不要先启动 with-skill 运行，之后再回来启动 baseline。一次性启动全部运行，以便它们大致在同一时间完成。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（使用相同的提示词，但 baseline 取决于上下文）：
- **创建新 skill**：完全不使用 skill。使用相同的提示词，不填写 skill path，将输出保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用在首次编辑之前通过强制性的 existing-skill regression gate 捕获的旧版本。将 baseline 子代理指向那个不可变快照，并将输出保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 重建一个权威 baseline，然后再继续；绝不要将已经编辑过的工作树用作旧 baseline。**请明确这种比较能够解决什么问题：它只衡量本轮的差异。** 如果你最想验证的能力在编辑前快照中已经存在——例如某个 sibling session 可以在你开始之前准确提交该修复——那么 with/old A/B 对该能力没有任何判别力；在这种情况下，应选择更早的 ref 作为 baseline。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据每个 eval 测试的内容为其指定描述性名称，不要只使用“eval-0”。同时将该名称用于目录名。如果本轮使用了新的或修改过的 eval 提示词，则为每个新的 eval 目录创建这些文件；不要假定它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：在运行进行期间起草断言

不要只是等待运行完成——你可以利用这段时间处理有价值的工作。为每个测试用例起草量化断言，并向用户解释这些断言。如果 `evals/evals.json` 中已经存在断言，则检查它们并解释其验证内容。

好的断言应当能够客观验证，并具有描述性名称——在 benchmark viewer 中，这些名称应当清晰易懂，让快速浏览结果的人能够立即了解每项断言检查的内容。**应针对意图编写断言，而不是针对某个字面意义上的工具路径**——例如“语音内容保留在答案中”，而不是“调用了规定的读取脚本”。如果某次运行通过其他符合要求的路径（例如读取一个已经内嵌 transcript 的 archive）达成了目标，也应当通过；将其判定为字面路径失败会制造错误的负面结果，之后还会导致你修复错误的位置。主观性较强的 skill（如写作风格、设计质量）更适合进行定性评估——不要强行为需要人工判断的内容设置断言；其真正的验证路径（历史任务重放、带有回写习惯的 production-as-eval、渲染后人工审查）列在“Capture Intent”的第 4 个问题下。

在起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户解释他们将在查看器中看到的内容，包括定性输出和定量基准测试。

### 第 3 步：随着运行完成，记录计时数据

每当某个子代理任务完成时，你都会收到包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会：数据通过任务通知传入，不会在其他地方持久化。每条通知到达后都要立即处理，不要尝试批量处理。

### 第 4 步：评分、汇总并启动查看器

所有运行完成后：

1. **为每次运行评分** —— 启动一个评分子代理（或直接进行评分），读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 中的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是人工目测——脚本更快、更可靠，也可以在迭代过程中重复使用。**但客观的 grep/脚本断言也可能产生相反的结果**（同词异义导致误命中、措辞差异导致漏检），因此**基准测试通过率只是一个信号，而不是最终结论**：应抽查每条断言实际匹配到的内容，并留意基线运行是否暴露出 skill 本身的事实错误（出现“等等，API 中确实有这些数据”的情况）。参见方法论 §5.3–5.6 和 §6.4。

2. **汇总为基准测试** —— 从 skill-creator 目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   该脚本会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及 mean +/- stddev 和 delta。每个 with_skill 版本应放在对应 baseline 版本之前。

   如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md`，了解查看器所需的确切 schema。

3. **进行分析师检查** —— 阅读基准测试数据，找出汇总统计数据可能隐藏的模式。参见 `agents/analyzer.md` 中的“Analyzing Benchmark Results”部分，了解需要关注的内容，例如无论是否使用 skill 都总是通过的断言（无法区分效果）、高方差的评估（可能不稳定），以及时间/令牌之间的权衡。

4. **启动查看器**，同时加载定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台查看器使自身陷入孤立状态**：进程仍在运行，但没有任何程序在监听——可以使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或 curl 该 URL（请求失败）；这里“没有日志输出”并不是可用的信号，因为上面的启动命令行已将其重定向到 `/dev/null`。终止该进程，并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击“提交全部评审”时，反馈会作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录中，以便下一轮迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** **告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

“输出”选项卡一次显示一个测试用例：
- **提示**：提供的任务
- **输出**：skill 生成的文件，可能会以内嵌方式渲染
- **上一轮输出**（第 2 次迭代及之后）：显示上一轮迭代输出的折叠区域
- **正式评分**（如果运行了评分）：显示断言通过/失败状态的折叠区域
- **反馈**：输入框，输入时会自动保存
- **上一轮反馈**（第 2 次迭代及之后）：显示在输入框下方的上一轮评论

“基准测试”选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每个评估的细分结果和分析人员的观察。

可以通过上一个/下一个按钮或方向键进行导航。完成后，点击“提交全部评审”，所有反馈将保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告知你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。将改进重点放在用户提出了具体意见的测试用例上。

完成后，终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进 skill

这是循环的核心。根据路由器选取的证据进行改进：Tier 1 使用权威事实和确定性检查，Tier 2 使用 1–2 个命名行为重放，Tier 3 使用经过用户审阅的成对结果。不要将 Tier 3 的产物或步骤带入较低层级的迭代中。

### 如何思考改进

1. **从反馈中提炼通用规律。** 这里正在发生的总体事情是：我们试图创建可以在大量不同提示中反复使用的 skill（也许真的是一百万次，甚至更多，谁知道呢）。为了更快推进，你和用户只是在反复迭代少数几个示例。用户对这些示例了如指掌，因此可以快速评估新的输出。但如果你和用户共同开发的 skill 只能用于这些示例，那它就毫无用处。遇到顽固问题时，与其添加繁琐、过拟合的修改，或加入压制性很强的限制性 MUST，不如尝试换用不同的比喻，或推荐不同的工作模式。尝试这些方法的成本相对较低，而且可能会取得很好的效果。

2. **保持提示精简，但不要删除契约。** 删除那些没有发挥作用的内容，但要将从现有 skill 中删除的每一项内容都视为潜在回归，直到新旧审计将其归类。将详细但可复用的行为移入直接链接的参考文档；不要只把它们留在评估、变更日志或你的记忆中。阅读完整对话记录，而不只是最终输出——如果 skill 导致了无益的工作，就简化指令并重新运行旧能力用例，而不要想当然地认为字数越少行为就越好。

3. **解释原因。** 尽力解释你要求模型执行每件事背后的 **原因**。如今的 LLM *很聪明*。它们具备良好的心智理论能力，在获得良好 harness 的情况下，可以超越机械执行指令，真正促成事情发生。即使用户的反馈简短或带有挫败情绪，也要努力真正理解任务，理解用户为什么写下他们所写的内容，以及他们实际上写下了什么，然后将这种理解传达进指令中。如果你发现自己开始用全大写的 ALWAYS 或 NEVER，或者使用非常僵化的结构，这是一个黄色信号——如果可能，应当换一种方式进行表述并解释理由，让模型理解你要求它做这件事为何重要。这种方式更加人性化，也更强大、更有效。

4. **寻找重复的工作——既要查看评估对话记录，也要查看 skill 所提炼自的对话内容。** 阅读测试运行的对话记录，注意子代理是否都各自编写了相似的辅助脚本，或采取了相同的多步骤方法来完成某件事。如果 3 个测试用例最终都让子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈信号，说明 skill 应该打包这个脚本。将它编写一次，放入 `scripts/`，并告知 skill 使用它。这样可以避免每次未来调用都重新发明轮子。同样的信号也可能隐藏在你提炼 skill 的源对话中——那次会话哪怕只编写过一次的代码，也意味着未来每次运行都必须重新编写；不要等到评估运行证明这种重复才采取行动（跳过评估循环的 skill 无法获得这种证明——创建流程第 4 步中的 Scripts 检查点正是为这些情况设置的捕捉点）。

5. **逐字写回修正——同一会话、两个层级。** 对于经过品味校准的技能，只有当用户的修正写入未来运行会读取的位置时，这些修正才是评测集。两个属性会让写回逐渐收敛：(a) **逐字记录修正**，不要改写概括——确切措辞包含了摘要会抹平的校准信号（“绝对禁止这种东西”教会了一个硬边界；“用户更喜欢更少的跳转”则没有）。将这些措辞连同日期写入它们所修正的规则中。(b) **在修正发生的同一会话中、在两个层级都写回**——修复产物，同时修复技能的规则/参考/组件；只修复产物的修正对所有未来运行都是不可见的，而推迟到“以后”的修正通常永远不会落地。写回时，检查技能自身的文本是否*教会了*刚刚被禁止的反模式——修正往往会证伪现有指令，而保留旧建议就必然会导致问题再次出现（真实案例：一个决策页面契约建议使用跳转式的“goto 锚点”跳到所引用的图；用户明确禁止了这种做法，因此写回必须修改旧句子，而不能只在旁边新增一条规则）。当被修正的对象是交互片段时，写回的最后一步是将其提升到组件架——参见第 4 步中的组件架检查。

这项任务非常重要（我们正在努力每年创造数十亿美元的经济价值！），思考时间不是瓶颈；请花时间认真斟酌。我建议先起草一版修订稿，然后重新审视并加以改进。请尽最大努力设身处地理解用户的想法、需求和期望。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据留下真正的选择空间时才提问。对于 Tier 2 或 Tier 3，当用户反馈暴露出有意义的设计分歧时，通过 **AskUserQuestion** 呈现改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (if the total exceeds 2, reclassify to Tier 3 before running them)
```

### 迭代循环

改进技能后：

1. 将改进应用到技能中
2. 仅重新运行所选层级的证据：
   - **Tier 1：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配的子类型证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归。不要创建迭代工作区。
   - **Tier 2：**仅重新运行同样的 1–2 个已命名的带技能示例及窄范围检查。不要添加基线、基准测试、查看器或评测工作区；任何对这些内容的请求都会将工作重新分类为 Tier 3。
   - **Tier 3，在仍获授权的情况下：**将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新技能，基线始终是 `without_skill`；对于现有技能，不可变的原始编辑前版本仍是每次迭代的保留基线。紧接着的前一次迭代可以作为补充，但绝不能替代原始基线。
3. 在实质性规则、契约或数字发生变化后，应用纪律 #5。对于通用 Tier 3 路径，还要使用指向前一次迭代的 `--previous-workspace` 启动评测审查器；专用工作流使用其声明的审查器机制。
4. 对于通用 Tier 3，等待用户审查新的查看器结果；否则，根据所选层级的证据作出决定，除非仍存在真正需要用户选择的事项。
5. 阅读新的证据或反馈；如果它证伪了当前版本，则再次改进，并在同一层级重复执行。

用户请求的取消或降级在任务剩余期间持续有效，但不会改变其分类。除非用户明确重新授权 Tier 3 执行，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次 **generic Tier 3** 迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（看起来一切都很好）
- 你没有取得有意义的进展

## Advanced: Blind comparison

如果你希望更严格地比较某个 skill 的两个版本（例如用户询问“新版本真的更好吗？”），可以使用盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详细信息。基本思路是：将两个输出交给一个独立的 agent，但不告诉它哪个对应哪个版本，由它判断质量。然后分析胜出版本获胜的原因。

这是可选的，需要使用子 agent，大多数用户不需要它。人工审查循环通常已经足够。

## Description Optimization

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某个 skill 的主要机制。创建或改进 skill 后，主动提出优化 description，以提高触发准确性。

### Step 1: Generate trigger eval queries

创建 20 个评估查询，其中混合应触发和不应触发的查询。将其保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实可信，并且是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要写抽象请求，而要写具体、明确且包含足够细节的请求。例如文件路径、用户工作相关的个人背景、列名和值、公司名称、URL 等。可以混合使用小写、缩写、拼写错误或口语化表达。长度也应有所变化，并重点关注边界情况，而不是让所有查询都过于明确（用户之后会有机会确认这些查询）。

不好的示例：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的示例：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**的查询（8-10 个），要考虑覆盖范围。你需要针对同一意图使用不同的表达方式，其中一些正式，一些口语化。包括用户没有明确提及 skill 或文件类型、但显然需要使用它的情况。加入一些不常见的使用场景，以及该 skill 会与另一个 skill 竞争但应当由它胜出的情况。

对于 **should-not-trigger** 查询（8-10），最有价值的是那些擦边案例：与该 skill 共享关键词或概念，但实际上需要其他功能的查询。可以考虑相邻领域、措辞含糊且朴素的关键词匹配会触发但实际上不应触发的查询，以及查询涉及该 skill 能处理的内容，但所处上下文更适合使用其他工具的情况。

需要避免的关键问题：不要让 should-not-trigger 查询明显无关。将“Write a fibonacci function”作为 PDF skill 的负面测试太容易了——它无法测试任何东西。负面案例应该真正具有挑战性。

### Step 2: Review with user

使用以下 HTML 模板向用户展示 eval 集供其审核：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → eval 项目的 JSON 数组（不要在它周围加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 的当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`），并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——如果存在多个文件，请检查 Downloads 文件夹中最近的版本（例如 `eval_set (1).json`）

这一步很重要——糟糕的 eval 查询会导致糟糕的描述。

### Step 3: Run the optimization loop

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期检查进度。”

将 eval 集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中提供的模型 ID（即当前会话所使用的模型），这样触发测试才能匹配用户实际体验到的效果。

运行期间，定期 tail 输出，向用户更新当前迭代次数以及分数情况。

这会自动处理完整的优化循环。它会将 eval 集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude，根据失败的情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一个 HTML 报告，显示每次迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试集分数而非训练集分数选出，以避免过拟合。

**如果检测到完全静默，循环会在第 1 次迭代后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中代码级别的保护机制，而不只是建议；它还能区分“第 1 次迭代中每个 should-trigger 查询都没有触发”这一现象背后的两种原因：

- `exit_reason: "infra_error: ..."` — 某些查询执行（should-trigger *或* not-should-trigger）抛出了异常（claude CLI 不在 PATH 中、超时时间过短、网络中断），而不是干净地返回“未触发”。该检查**最先**进行，并且有意在错误计数为任何非零值时触发，即使几十次运行中只有一次不稳定运行也是如此——崩溃无论多么罕见，都比“什么都没触发”更具体、更可操作，修复方向也在环境，而不是重写描述。消息中的比例（例如 `3/15`）用于判断严重程度：占比较大意味着“停止运行，修复环境”；占比较小且伴随大量干净的 0-trigger 运行，则意味着环境可能存在一个值得检查的轻微不稳定问题，*同时*描述也可能确实有问题——两方面都要检查。无论哪种情况，都要检查 stderr 中是否有 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` — 只有在上面的分支排除了所有执行错误后才会检查，因此这意味着每个 should-trigger *和* not-should-trigger 查询都确实运行了，*但仍然*一次也没有触发（这正是通过零分母默认值实现的“precision=100%”实际含义：不是“完美”，而是“没有可供相除的数值”）。该探针实际上没有测量到任何东西——在接触描述之前，先去诊断竞争者冲突或低阈值领域（见下文）。

两项检查都**仅针对迭代 1**，并且**仅在 should-trigger 查询一次也没有触发时**执行——迭代 1 较弱但并非零触发（例如 1/9 次触发）是另一种可能恢复的情况，因此会有意留给后续迭代。`degenerate_harness` 还要求 not-should-trigger 查询也一次没有触发：如果描述只是极性反转——漏掉了每个正例，却意外匹配了多个负例——就证明探针确实能工作，`improve_description` 也有真实的梯度可以利用，因此守卫不会中止这种情况（只有探针确实失效时才会中止）。此外，它还要求任一侧都没有执行错误——抛出异常的 not-should-trigger 查询实际上并未运行，因此其“0 次触发”不能用作探针失效的证据；这种情况正是应当路由到 `infra_error` 的情况。无论哪种情况，都会立即中断，并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因才是信号，表明这次运行的数值不应被解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了完整的 5 次迭代循环；两次完整迭代——每次都是完整的评估批次，耗时数分钟，并调用了几十个 `claude -p` 子进程——都返回了 precision=100%/recall=0%/相同的分数，直到有人查看这些数值时才发现问题，而且每个 should-trigger *和* not-should-trigger 查询都一次没有触发。仅凭迭代 1 就可以诊断出故障；迭代 2 及之后的迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会渲染一个横幅，因此浏览器视图与 JSON/stderr 一样携带相同的信号，而不只是由那两个可见性较低的渠道传达。（该守卫的早期草案只检查 should-trigger 触发情况；经过两轮独立审查——每轮都使用一个全新的代理，第二轮检查第一轮的修复，而不是重复覆盖旧问题——构造出了极性反转反例、基础设施与描述之间的歧义、负例侧错误的遗漏，以及由此发现的一个预先存在的 `--holdout 0` 报告崩溃问题；这些问题都在发布前修复。）

这个防护机制无法覆盖一个例外情况：当使用 `--runs-per-query 1` 时（默认值为 3），一个本应触发的查询如果实际触发率确实在 50% 左右，那么仅凭随机性就很可能出现 0/1 的结果，从而让防护机制因噪声而触发，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询的每次重复运行都为零”成为强信号的原因——如果你将其调低，这个防护机制产生误报的风险也会随之上升。

**在信任 `best_description` 之前，先对测试工具进行合理性检查——即使上面的两个防护机制都没有触发，它仍可能返回空洞的结果。** 两项检查只能捕获第 1 次迭代中的*完全失败*；测试工具也可能在全部 5 次迭代中始终维持微弱但非零的信号，却从未触发其中任何一项。如果每次迭代都显示 **recall 在第 1 次迭代之后仍接近 0%，且分数完全相同或几乎相同**，那仍然是防护机制无法排除的同一个根本问题——“获胜”的描述通常只是第 1 次迭代未改变的噪声。在应用任何 `best_description` 之前，先自行运行一个明显应该触发的查询，并确认 recall > 0。跨迭代保持不变的 recall 结果意味着测试工具本身是一个隐藏变量（常见情况是：该 skill 在触发上输给了已安装的竞争 skill——见下文的 Coexistence）——不要应用它的“最佳”结果；应手动编写描述，并使用真实探针进行验证。（方法论 Cases 12、14）recall-0 还有第二个根本原因，与输给竞争 skill 不同：该 skill 的任务领域属于*低阈值*领域——模型自行完成任务，从不查阅任何 skill——这一点会在下方 *How skill triggering works* 的末尾详细说明。在采取行动之前，要区分这两种情况，因为它们的修复方式正好相反：竞争 skill 应通过 precedence/supersede 解决，而低阈值领域则应彻底放弃用于生产环境评估的触发探针，改用 production-as-eval。

**当你使用 `claude -p` 自行探测触发情况时，要收集运行期间的所有 skill 调用，而不只是第一个——并记住，工具调用只是一个代理指标。** `UserPromptSubmit`/`SessionStart` hook 可能会在模型做出选择之前注入一个无关的 skill，因此“在第一次 Skill 调用时退出”的探针会错误地报告“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“该 skill 的内容是否影响了输出”（模型可能读取了 skill，却没有出现可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你围绕错误的结论持续优化。

### 技能触发机制

了解触发机制有助于设计更好的评估查询。Skills 会以名称和描述出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某个 skill。需要注意的关键点是，Claude 只会针对自身难以轻松处理的任务查阅 skills——像“读取这个 PDF”这样简单的单步查询，即使描述完全匹配，也可能不会触发 skill，因为 Claude 可以使用基本工具直接处理。复杂的多步骤任务或专业化查询，在描述匹配时通常会可靠地触发 skills——但有一个系统性例外（低阈值任务领域），会在本节末尾详细说明。

这意味着你的评估查询应当足够实质性，使 Claude 确实能从查阅某个 skill 中受益。像“读取文件 X”这样的简单查询不是好的测试用例——无论描述质量如何，它们都不会触发 skill。

**但有些 skill 无法通过重写查询来解决这个问题，因为该 skill 的整体*职责*本身就是一项低门槛任务。** 上一段把问题归咎于查询（“写一个更实质性的查询”）；这里则是另一个正交情况：阻碍触发的是 skill 的*领域*。如果某个 skill 的用途是执行 Claude 只需使用基本工具就能自行完成的操作——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询已经完整指定（“将这个 48k 立体声 wav 降采样为适用于 whisper 的 16k 单声道”，并包含完整路径），它也不会触发该 skill：模型会直接使用 `Bash`/`ffmpeg`，完全不会查阅任何 skill。查询的实质性无法解决这个问题，因为“我可以自己完成”的判断针对的是*任务*，而不是措辞。

在耗费一个优化循环之前先诊断这一点：通过 `claude -p` 运行一个真实查询，并观察模型在整个运行过程中是否曾经查阅该 skill（依据上面的 ALL-skill-calls 规则），还是直接使用 `Bash` 自己完成任务。如果它从未查阅，那么触发探测从结构上就无法观察到这个 skill——无论你怎么写，召回率都大约为 0，而这个 0 衡量的是模型“自己完成”的倾向，而不是你的描述。停止针对 `claude -p` 召回率进行调优，并用真实方式验证：使用生产环境即评估（用户下一次真实的、*交互式*使用——无头 `-p` 比真实会话更偏向执行操作，并且系统性地低估触发率），再加上输出比较（skill 产出可检查的制品时）。 （在一个音频预处理 skill 上观察到这一点：无头运行的 run_eval 扫描对*每一个*查询的读取召回率都是 0——包括一个明显的“转录这段录音”查询；手动执行 `claude -p` 探测时，模型直接使用 `Bash` 查找并处理文件，整个运行中的 `Skill`=0。这个 0 衡量的是无头模式的操作偏差，而不是描述质量；只有在交互式使用中才能看到真实信号。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新 skill 的 SKILL.md frontmatter。向用户展示修改前后的内容，并报告分数。

## 重要：在源位置编辑 Skills

**绝不要先编辑已安装的 skill 副本。** 除非用户明确说明它们就是源文件，否则应将以下所有路径视为已安装的/运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装的副本会导致修改：
- 缓存刷新时丢失
- 不会同步到源代码管理系统
- 浪费时间，并需要手动重新合并

**始终确认你编辑的是源代码仓库：**
```bash
# 错误 - 缓存位置（只读副本）
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# 错误 - 个人已安装副本，除非明确将其用作源文件
~/.codex/skills/my-skill/SKILL.md

# 正确 - 源代码仓库
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，运行源位置检查并说明哪个路径是源路径：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假设该路径就是源路径。先找到由仓库提供的源文件，编辑并验证它，只有在用户需要立即用于本地运行时，才同步已安装的副本。

**然后回答决定“是否需要同步已安装副本”的后续问题：运行时是否已经读取源文件？** 三种安装方式的行为不同，猜错会导致不必要的同步，或者提交一个用户下次会话根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **通过符号链接**指向源代码树 → 编辑本身就是运行时生效的内容。不需要同步。
- **使用 `source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本号更新只是为其他使用者准备的记录工作，并不是本地激活步骤。
- **任何缓存或复制的安装方式**（从 git 获取的 marketplace、通过 `cp -r` 安装）→ 运行时使用的是独立副本，因此在新内容生效之前确实需要运行官方更新命令。

**并且要根据内容验证是否已激活，而不是根据版本字符串。** 注册表可能记录了磁盘上并不存在的路径或版本 — 有一次会话读取到一个插件记录，其中的缓存目录标记为新版本号，差一点就报告更新已经生效；但该目录从未创建，真正的运行时路径一直是指向源代码的符号链接。权威检查方式是 grep 运行时文件，查找只有新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库中的并发会话

高阶用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能会在你不知情的情况下提交技能 B（甚至是技能 A 的更早一轮修改）。有一次真实会话在一小时内同时遇到了三种症状 — `Write` 因文件在读取后发生变化而被拒绝，并且 HEAD 在任务进行期间两次移动（方法论案例 16）。问题不在于发生冲突，而在于使用了过时的基线，或者使用会悄悄混合两个会话修改内容的覆盖式写入。固定规则如下：

1. **只要仓库在任务开始时是干净的，就应基于 git ref 而不是工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传入 `--baseline-origin git-ref:<sha>`。几分钟前创建的树快照，可能对应一个已经不再存在的树，不能作为基线。**将内容解压到一个新建且不存在的目录中。** 解压到已有目录时，`tar -x` 会静默覆盖同名文件，同时保留归档中不存在的文件 — 这样会得到一个混合快照，解压时没有任何提示，而后续 `compare` 会因其与该 ref 不匹配而拒绝。同样的陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会将目录嵌套进去；而当 `mv` 被别名为 `mv -i` 时，如果目标已存在，重命名会打印一行提示并默认不执行，但无论是否执行，退出码都是 0（已通过实验验证）。
2. **如果写入被拒绝，或距离上次读取已经过去了一段时间，则在写入前重新读取**：检查发生了什么变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图合并到你的版本中 — 他们的编辑通常是有原因的 — 然后再写入。
3. **提交前同时检查 HEAD 以及当前所在的分支。** `git log --oneline -1` 可以发现 SHA 是否发生变化：如果它自基线建立后发生了变化，则在 `verify` 之前，针对新的 ref 重新运行回归 `compare` — 审计工具本来也会拒绝过时的审查（“after skill changed”），提前发现可以省去一轮。但另一个会话可能做出比推进 HEAD 更糟糕的事情：**它可能在你不知情的情况下切换当前分支**，因为 checkout 的作用范围是整个工作树。真实过程如下 — 你运行 `checkout -b feat/x`，编辑了一段时间，与此同时另一个会话运行了 `checkout main` + `pull`；随后提交落在了 **main** 上，违反了仓库“绝不直接提交到本地 main”的规则，而功能分支仍指向旧基线。因此，提交前的检查中要加入 `git branch --show-current`，不能只检查 SHA。如果这种情况已经发生，`git reflog` 是权威的重建依据（它会按顺序记录每次 `checkout: moving from X to Y`），而修复方式 — **前提是工作树干净** — 是 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：这两者都是只移动引用、不会触碰工作树的操作，因此不会像 `reset --hard` 那样破坏并行会话未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .` — 另一个会话未提交的工作不能被一并带入。（这本来就是打包时的规则，在并发场景下更是关键。）
5. **每个会话结果只进行一次版本号更新**，而不是每轮编辑都更新：同一会话对同一技能连续进行的多轮修改应合并为一次版本号更新 — 除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），此时每个已被使用的状态都应拥有自己的版本号。

## Skill 创建流程（分步）

创建或更新 skill 时，按顺序执行以下步骤。仅当某个步骤明确不适用时才跳过。

### 步骤 0：前置条件检查

开始任何 skill 工作之前，自动检测所有依赖，并主动安装缺失的依赖。在工作流中途才发现缺少工具（例如打包时缺少 gitleaks、验证时缺少 PyYAML）会浪费时间并中断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖就自动安装，并向用户提供检查清单摘要。只有满足所有阻塞性依赖后，才能继续执行。

关键阻塞项：Python 3、uv、PyYAML（验证/打包）和 gitleaks（安全扫描）。只有在选定的验证层级实际运行 agent eval 时，claude CLI 才是阻塞项。使用显式的 uv 依赖声明运行 Python 工具，例如从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 依赖环境中已有的 site packages，可能缺少 PyYAML。

### 步骤 1：通过具体示例理解 Skill

仅当 skill 的使用模式已经明确理解时，才跳过此步骤。

要创建有效的 skill，必须清楚理解该 skill 的具体使用示例。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成示例。

例如，在构建 image-editor skill 时，相关问题包括：

- “image-editor skill 应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能给出一些该 skill 的使用示例吗？”
- “用户说什么话时应触发该 skill？”

为避免让用户应接不暇，避免在一条消息中提出过多问题。

### 步骤 2：规划可复用的 Skill 内容

分析每个示例时：

1. 考虑如何从头开始执行该示例
2. 确定应给予 Claude 多大的自由度
3. 确定哪些脚本、参考资料和资产有助于重复执行这些工作流

**让具体程度匹配任务风险：**
- **高自由度（文本说明）**：存在多种有效方案
- **中等自由度（带参数的伪代码）**：存在首选模式，但允许合理变化
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 步骤 3：初始化 Skill

如果 skill 已经存在，则跳过此步骤。

从头创建新 skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个模板 skill 目录，其中包含正确的 frontmatter、资源目录和示例文件。

### 步骤 4：编辑 Skill

开始编写之前，获取 Anthropic 的最佳实践文档（链接位于上文的“Skill 创建最佳实践”中）和方法论参考资料——即使你觉得自己已经了解这些内容，也要执行此操作：文档会更新，训练数据版本会过时，而“我基本了解”正是编辑者跳过这一步并错过最新指导的状态。

编辑时，请记住，该 skill 是为另一个 Claude 实例创建的。重点关注那些对 Claude 有益且不明显的信息。

**现有 skill 迁移门禁 — 首次编辑前必须完成：**

1. 在编辑前捕获当前完整 bundle。对于非 Git 或处于脏状态的源代码，使用该工具，以便快照包含可验证的 provenance manifest：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源代码，从选定的 ref 物化目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   包括 SKILL.md、references、scripts、assets、workflows 以及现有 evals，而不仅仅是主提示词。绝不要复制已经编辑过的目录并将其标记为“before”。**使用之前没有提取过任何内容的目录**——重用一个已经包含早期运行内容的目录，会让 `tar -x` 静默覆盖同名文件，同时保留新归档中不存在的旧文件，从而生成混合快照；提取时不会产生任何信号（`compare` 只会在之后间接地通过树哈希不匹配发现它）。参见下方的“同一 skill repo 上的并发会话”，其中更完整地说明了这个陷阱，包括基于 `mv` 的变体。
2. 清点旧 skill 的 actor/jobs、触发上下文、运行时契约、命令/标志、失败和恢复场景、页面/领域变体、捆绑资源以及 eval 覆盖范围。在进行结构性重写前，为重要的旧边缘行为添加保留用例。
3. 编辑后，生成新旧版本的审查结果：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，将最后一个标志替换为 `--baseline-origin git-ref:<ref>`。该工具会将 ref 解析为不可变的 commit，并针对该树验证每个包含的文件及其可执行位。

   **重命名或移动 skill 目录本身**（而不仅仅是编辑其内容）会改变 `--after` 的路径，而两种基线模式都会使用该路径来确定身份——默认情况下，`compare` 会拒绝这种情况（假定 `--before`/`--after` 意外不匹配），并报错 `pre-edit snapshot source identity does not match the edited skill`。添加 `--renamed-from <old-path>` 以显式声明重命名（对于 `snapshot`，这是 `--source` 指向的路径；对于 `git-ref:`，这是 skill 相对于其 repo 根目录的旧路径）；身份检查随后会验证该路径，而内容/树哈希检查保持不变，因此实际不匹配的配对仍会失败。**将 `--renamed-from` 作为绝对路径传入。** 该命令接收的每个路径在作为相对路径提供时，都会相对于当前工作目录解析——而不是相对于 `--after`，也不是相对于彼此解析——并且 `--renamed-from` 通常指向一个已经不存在的目录（它已被重命名），因此不存在检查无法像对 `--before`/`--after` 那样捕获错误解析；它只会在更深层的位置以令人困惑的方式失败。这一点尤其会影响 skill-creator 自身的编辑：上面的 `cd <skill-creator-path>` 位于 skill-creator 自己的 repo 中，而该 repo 通常与被审计的 skill 所在 repo *不同*，因此相对的 `--renamed-from` 会静默地相对于错误的 repo 解析。

4. 审查每个候选项。为每个候选项准确使用一种处置方式，并记录具体证据/原因：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移到此 skill 之外时，必须提供负责该能力的目标位置、当前边界证据以及可追溯的用户批准。明确的弃用也必须引用/追踪用户的批准。关于已保留/已清理/已修复的声明，必须指向当前真实存在的文件和行，并包含一段简短的 `contains` 引文，以便验证者在附近定位。文件级候选项需要使用当前文件指纹，并附带一份说明行为为何得以保留的具名语义审查；仅凭指纹只能证明文件身份，不能证明能力得到保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本 —— `classify` 子命令会完成机械性工作（定位目标文件中引文所在的行、填写 evidence/semantic_review，并在找不到引文或原因过短时快速失败）。你仍然需要编写每一个处置方式和原因；它只负责将它们录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（disposition 默认为 `preserved_or_moved`；文件级候选项只需要 destination + 一个长度至少为 40 个字符的 reason —— 指纹会自动为你计算）。**请从目标文件中复制 needle（使用 Read/grep/sed），不要凭记忆输入它** —— 查找采用精确匹配，找不到引文时会快速失败；手动输入的 needle 实际上会因以下两种情况失败：全角与半角标点（`：` 与 `:`）不一致，以及凭记忆改写近义字符（`也` 与 `都`）——这两种情况都会绕过自我审查，只有工具拒绝整个映射时才会被发现（有一次映射正是因为这两个原因连续被拒绝了两次）。

5. 验证已完成的审查。任何进一步的编辑都会使审查过期，因为哈希值会发生变化，因此候选项发生变化时，请重新生成并重新分类。通过验证后会写入 `.skill-regression-reviewed`，这是一个记录内容状态的本地回执。它有助于检测后续编辑，但经过刻意设计，并不具备独立的打包授权能力；打包流程会自行重新验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可以识别静默失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在需要审查的候选项，并不表示工具失败；  
2 表示调用或运行时失败。该工具可以证明内容被精确迁移且接口得到保留，但会有意拒绝根据模糊的词语重叠来推断语义等价性。诸如“check permission denied”这样的通用短语，不能悄无声息地替代“已登录但没有角色”这一精确契约。还要检查标记为 `only_outside_runtime` 的候选项：仅存在于 eval、测试或不可达引用中的运行时行为，在正常调用路径中并不存在。

**在每次编辑 SKILL.md 后立即验证，不要等到打包时（Step 7）。** 该检查能够及早捕获的失败是真实存在的：作为未加引号的 YAML 标量编写的 frontmatter description，可以在 Claude Code 的宽松解析器中正常解析，却会在严格解析器中出错（codex 曾在一个已经发布数月的 skill 上报告 `invalid YAML: mapping values are not allowed`）；而未加引号的 description 中包含的 ` #` 甚至不会报错，它会静默截断其后的全部内容，导致触发关键词消失，而每次扫描仍然显示通过。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**将 description 编写为 YAML block scalar**（`description: >-` 后跟一段缩进的文字），只要其中包含 `: ` 或 ` #`，或跨越多个句子，就应采用这种写法——block scalar 原生支持这两个字符；自上述事件以来，这是每个新建或编辑的 description 所推荐遵循的约定。

**更新现有 skill 时**：扫描所有现有引用和捆绑资源，查找相应的更新，然后通过上述迁移门禁。迁移契约时，SKILL.md 必须提供一个直接的运行时指针；eval 或变更日志不能替代它。

接下来的三项检查是**升级探查，而不是无条件扩大范围**。如果执行其中任何一项会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖、权限或外部写入，请停止并重新分类为 Tier 3，然后再修改 skill。Tier 1 和 Tier 2 可以检查这些问题，但不会因此从中获得新的交付要求。

**脚本检查**：在宣布编辑完成前，询问：*源对话（或 eval 转录）编写了什么代码，而未来的每次调用原本都必须重新编写？* 当所选 tier 已经授权进行这项能力工作时，将其参数化、完成清理后纳入 `scripts/`，并修改文档指向它。否则，将这一信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的附带结果打包进去。分工如下：**scripts 负责执行，文档负责理解**——如果一个 skill 的方法只存在于正文中，那么每次运行都会重新承担完整的编写成本。之所以将这项检查放在编辑步骤中，正是因为那些跳过 eval 循环的路径（对话提炼、直接编辑）永远不会到达“Improving the skill”中 eval 转录版本的这项检查。

**组件货架检查（针对嵌入 artifact 的片段提出同一个问题）**：Scripts 检查覆盖的是 *skill* 执行的代码；生成 artifact 的 skill（报告页面、演示文稿、文档）还会不断积累其 *输出* 所嵌入的片段——图像叠加组件、粘性导航、图表配置、CSS 块。如果连续生成的输出都各自手写相似片段，那就是同一个重复信号，只是指向了不同的货架。在添加 `components` 子文件夹或注册表引用之前，先应用上面的升级规则；Tier 1/2 可以提出方案，但不要创建组件能力。获得 Tier 3 授权后，决定一个代码片段能否成为货架组件的，是围绕它建立的契约：(a) **原样嵌入块**——带有 BEGIN/END 标记，整体复制到 artifact 中，零依赖，以便单文件 artifact 保持自包含；(b) **注册表条目**，说明交互契约（触发条件、按键绑定、关闭行为、边界情况）和来源——它来自哪个已交付的 artifact、用户何时批准了它；(c) **准入门槛**——只有用户实际使用过并批准的片段才能进入货架（将已批准语料库的纪律应用于交互；未经批准但外观漂亮的片段不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定是契约，在不同运行之间不得漂移，而颜色和尺寸可以遵循 artifact 的设计风格；(e) **回写循环**——为一个 artifact 发明的片段，应在用户批准生效的同一会话中提升到货架中。这一点的重要性不只是节省 token：手动重写的片段会发生*漂移*——每次重写都会细微改变按键绑定、关闭行为、计数器——而对于每天阅读这些 artifact 的用户来说，交互一致性本身就是产品体验。用用户为第一个此类货架提出的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。实际实例（已移除项目指纹）：一个报告页面 skill 的 lightbox-gallery 组件（图像叠加：←/→ 在组内循环切换，ESC 关闭，原位缩放，显示 n/N 计数器），以及其 interaction-components 注册表引用——它是在用户纠正跳转式引用的同一会话中提取的，并在交付前通过自动化点击流程测试进行了验证。参见方法论案例 17。

**流水线检查**：考虑此 skill 的输出是否会自然地流入另一个 skill，以及是否应当有现有 skill 串接到此 skill 中。添加或实质性修改“Next Step”交接或流水线契约，需要在编辑前重新归类为 Tier 3；Tier 1/2 可以提出方案，但不得顺手将其加入。

**引用与自应用检查（仔细的作者也会遗漏的缺陷）**：一系列失败模式都具有相同特征：从内部看起来像已经完成的工作，却没有任何一种能通过更加仔细地重读来捕获——每一种都需要改用*机械化*操作。（开头故意没有写数量。 “三种失败模式：”是一个派生数字，只要有人追加一个列表项，它就会过时；而计数文字之所以最难准确捕捉漂移，正是因为它*不包含发生变化的对象*——重新编号的 grep 和列表本身的 diff 都会径直绕过它们。）它们被归在这里，是因为共享同一个原因：**写下断言和验证断言是两种不同的模式，而单次遍历无法同时完成二者。**在你撰写内容时，“参见规则 8”*就是*这个断言；你并没有同时打开规则 8。

与上面的三个升级探针不同，这一项**不按层级限定范围**，而是按你写下的内容限定范围。一个没有添加指针、也没有添加规范性规则的 Tier 1 修复，在这里无事可做；你也不必自行判断这一点：corollary 的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 给出答案。无论在哪个层级，只要你写了指针或规则，以下条目就适用。

- **你写下的每一个指针，都要打开其目标，并从中复制一行出来——在写下指针之前。** 不要只说“我确信那条规则列出了这三个标记”：把目标中的一段内容粘贴到你已经在为这一步生成的内容中（审查记录、提交消息正文或你的回复均可），放在其他读者之后可以拿它与目标进行核对的位置。仅仅看过但没有留下片段，正是本句开头所拒绝的自我评估。错误的交叉引用在重新阅读时是看不出来的，因为错误的指针看起来和正确的指针完全一样，而作者又是唯一肯定会“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal rule 3”，意指一条关于不要引用过时枚举的规则；但被引用文档自身的 *rule 3* 讲的是样本量，而实际被引用的规则位于另一个文件中；读者按照该文档既有的自引用约定跟过去，最终会落到一个无关主题上。同一轮编辑还提交了一个方向颠倒的指针（对上方材料写成“see below”），以及一个指向不存在的章节标题的指针。
- **文件一旦有两个编号列表，单独写“rule N”就会产生歧义。** 检查是针对每个指针进行的，而不是针对每个文件：在写下“rule N”之前，运行 `grep -n '^N\. ' <file>`，并确认在你所指的章节中恰好只有一个匹配项；如果有多个匹配项，还要写出章节名称。（**不要**把这变成文件级别的警报，例如“这个文件是否包含多个从 1 开始的列表”——对任何长文档来说，这几乎总是成立，因此它会对健康输入触发，最后被人忽略，而纪律 #6 提醒我们，这比完全没有检查更糟；在这个文件上运行一次，亲自看看结果。）真实案例中，一个单独的“rule 1”对应三个候选列表，而从上到下搜索时首先命中了错误的列表。
- **写下任何规范性规则之后，都要用它旁边的行检查该规则——并让检查生成工件，而不是结论。** 使用与下方 corollary 相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的变更片段。这里自行阅读就足够了——你不是在进行模式匹配，因此不需要脚本——但必须带上那个 ref：单独运行 `git diff` 只会显示尚未暂存的工作，而一旦你执行 `git add`，它就会什么都不输出；这是本段 corollary 旨在规避的五种静默空结果模式之一。把新规则拆分成各个独立的条款，并逐条写下同一变更片段中满足该条款的那一行。（下方 corollary 中的 `scripts/reference_net.sh` 承担的是另一项工作：列出需要你解析的**正文交叉引用**。它不会把变更片段交给你，也不会告诉你规则中的某个条款是否得到了满足。）**旁边没有对应行的条款就是问题所在。** 诱人的简化版本——“我的新规则是否通过？”——对于 30 秒前写下它的人来说不可能失败；这正是纪律 #6 所说的：应当优先采用可证伪的观察，而不是自我评估，因此这一条也必须提供它所要求的工件。最先暴露问题的通常是旁边的段落。真实案例：有人新增了一条规则，要求“始终同时报告原始数量和过滤后数量——差值*就是污染量*”，但他在同一次提交中的实际演算示例只打印了过滤后的数字。同一份 diff 中的第二段陈述引用了两个数字，却没有说明这些数字是否是在相邻的新规则刚刚规定为必需的限定条件下采集的。范围很小，也有明确边界：不是“重新阅读整篇文档”，而是“我 30 秒前写下的规则，在我 30 秒前写下的那些行上是否通过”。
- **为每条新规则添加一行，说明由谁执行它，以及他们实际上是否能够执行。** 如果现有工具无法满足某条规则，那么相信自己已经遵守规则的人就会跳过它——这是最糟糕的一类规则，因为它会产生有文档依据的虚假信心。真实案例：一条新规则要求“检查两个日志存储”；但项目自己的规范性单命令分类工具将其中一个硬编码排除在外，因此标准工作流会对规则本来要捕获的故障返回干净结果。这条规则虽然正确，却不起作用，而且没有提及这一缺口。**让这一点可证伪的工件**（没有这个工件，这一条就是禁止自我评估的整段内容中唯一的自我评估）：写出能够捕获违规的工具或命令，然后**针对一个你已经知道它应该捕获的案例运行一次**。如果在一个已知有问题的输入上它返回干净结果，你就已经测量出这条规则不起作用——把这一缺口直接写进规则本身。凭记忆回答“他们实际上是否能够执行”正是纪律 #6 所拒绝的未经验证的断言。**当没有任何工具能够判断这条规则时**——大多数正文和品味规则都属于这种情况，因此不要把它当作逃避检查的出口——工件就是那句明确说明这一点的话：*“没有任何工具强制执行这条规则；它只有在有人记得它时才成立。”* 这比检查通过的状态更糟，而把它明确说出来正是要点；一条执行情况保持沉默的规则，会被默认接受，而不是得到验证。请注意这一条自身诚实的局限：工具和已知有问题案例的选择仍然是判断，因此它只是移动了未经验证的步骤，而不是消除了它——它比替代方案成本更低，但并非没有成本。
- **Corollary——你的修复本身也是缺陷来源，因此要在最后一次编辑之后重新检查你修改过的区域。** 在对同一项变更进行两轮审查时，第一轮发现了八个问题；第二轮又发现了八个，其中**七个是第一轮修复引入的交叉引用错误**。重写一句话会移动其周围的锚点。这也是为什么对于读者依靠指针导航的工件来说，“已经审查过”并不是完成标志：你一旦据此采取行动，审查结果就会过时。重新检查是机械性的，而且应当使用**脚本**，而不是要求你重新输入命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的 bundle 中）。它会列出你新增行之间的正文交叉引用，以便你打开每个目标并确认目标内容确实如你所声称。首次使用前请阅读其头部注释——其中解释了它为什么需要 base ref，而不是默认使用 `HEAD`，以及它有意**不做**哪些事情。

**在开始编辑之前获取 `<base-ref>`，不要事后再获取。** 在开始时将它解析一次为字面量 SHA，即当时执行 `BASE=$(git rev-parse HEAD)`，并将同一个值复用于本条和上面的项目符号。如果你运行过现有 skill 迁移门禁，它就是你已经完成基线设定所依据的 ref。稍后传入 `HEAD` 才是陷阱：提交之后，`HEAD` 已经包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请通过 `git log`、`git reflog`，或提供给迁移门禁的基线来恢复它，而不是用 `HEAD` 替代；当你的 base ref 同时也是当前 HEAD 时，脚本会打印提示，但不要依赖在那里才发现这一点。

**为什么这里要使用脚本，而这一段的其他部分都是说明文字。** 它所替代的单行命令经历了五轮修补——将 diff 锚定到正确的基线、查看已暂存的编辑、在提交后仍能工作、跳过 diff 自己的 `+++` 标头、移除误导性的 `-n`——其中四轮都增加了另一种让它不打印任何内容并以 0 退出的方式，而这与“我检查过了，结果是干净的”无法区分。第五轮则是同一种问题的另一种表现：它移除的 `-n` 原本会打印带行号的真实命中项，但行号是按管道传入的流计算的，因此看起来很权威，实际却指向不存在的位置——这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都会持续发布它本来要捕获的缺陷。说明文字无法验证自身的输入，无法说明发生了哪种结果，也无法接受测试；脚本可以完成这三件事，而且它的契约是：**每一种结果都必须被明确命名，错误输入必须明确失败**。这就是本步骤前面提到的 Scripts 检查在这一段中的应用——而五轮修补正是忽略它所付出的代价。

**读取它的判定结果，而不只是退出码。** 只要脚本成功运行，它就会退出 0，因此单独查看 `$?` 无法告诉你它发现了什么；答案在判定行中，而且它始终会明确说明以下情况之一：找到引用（逐一解析）、文件与基线完全相同、文件发生变化但没有新增行，或存在新增行但其中没有任何类似引用的内容。这些是不同的结果，脚本会有意将它们区分开来——这个检查曾经把它们合并成一个无声的“什么都没有”，正是因此才变成了脚本。它只需几秒钟，且不依赖警觉性，而这正是纪律 #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的指针——“见下方章节”“如上面的规则所述”——因此也要阅读新增的行。）

### 第 5 步：清理审查（任何公开 skill 都必须执行）

**在此门禁之前，当纪律 #5 到期时，其独立检查必须已经运行**，并且当前变更对应的 `independent-review.md`（位于你的私有、受 git 跟踪的知识仓库中——不在已清空的工作区中，也不在任何已经或可能变为公开或分发状态的仓库中）必须存在**并且已经提交**。对于新的 skill，它始终需要执行；对于现有 skill，使用下一段中的阈值。一个未提交、位于 git 工作目录中的文件，与一个从未写入过的文件在实际意义上没有区别；`ls`/`test -f` 只能确认它位于磁盘上，不能确认它能够保留下来。对于**新的** skill，这是第一次有任何内容离开你掌控的步骤，因此纪律应当在这里真正得到执行，而不只是停留在表述层面——一条位于使用点上方 1000 行、没有任何检查机制的规则，每次都会输给完成任务的驱动力。

**对于已发布 skill 的编辑，编辑一离开你的手，下一步就是 push，而不是这里。** 这个关卡可以用一句话回答“仅限内部，跳过”，而且对于仅涉及文档的变更，打包流程可能根本不会运行——因此把审查锚定在这里，意味着一次 skill 编辑可能在没有任何独立审阅者查看的情况下进入公共分支。真实案例（2026-07）：对这份文件本身的一次变更发布了一个 discovery command，但它无法触达旁边正文声称能够覆盖的三个根目录；该变更已合并，直到之后委托进行审查才发现问题。**因此对于现有 skill：独立审查及其记录产物必须在 `git push` / 创建 PR 之前完成——push 时运行的关卡（回归审计、验证、扫描）都会检查结构，但没有任何一个能告诉你说明是否有误。** 这沿用纪律 #5 的阈值，不作任何改变：当*规则、契约或数字发生变化时*，就必须执行；拼写错误或纯格式重排则不需要。让拼写修复也必须等待一轮审查，会教会人们形成 #6 警告的那种反射——“这个改动很小”变成普遍豁免，最终连真正重要的变更也被它覆盖。

**对于要进入公共仓库的 skill，这不是可选项。** 私有内容经常泄漏到公共 skill 中，而扫描器漏掉的泄漏才最危险——非英语语言中的真实姓名、真实对话记录中的逐字原句、被放进示例说明中的真实案例。只有当该 skill 确实仅限内部使用时，才可以跳过。

**按目标位置而不是按主题限定审查范围。** 只有会公开发布的产物——skill bundle 本身——需要清理。留在私有仓库中的配套文档（skill 提炼所依据的事件报告、内部运行手册、项目的 CLAUDE.md）应保留真实的主机名、路径和时间戳：删改这些内容会破坏它们的审计价值，而你最终还会把这些修改恢复回来。有一次提炼过程之所以经历了三轮返工，正是因为清理流程被应用到了源材料涉及的所有内容，而不只是公共 skill。

**先检查目标位置，并让它预先填充建议。** 在 skill 将要存放的仓库上运行
`gh repo view --json isPrivate`（或者读取
`quick_validate` 已经打印的提示）。私有目标位置会使选项 C 成为默认建议，而不是事后才考虑的事项——“除非另有说明，否则假设为公开”正是把私有 skill 的工作路径变成无人要求的占位符的原因。

**触发清理的是目标位置的 `isPrivate`，而不是任务在主观上有多像发布。** 两者并不总是一致，而一旦不一致，除非明确指出这一点，最终决定行动的就会是主观感受。把内容*移入 marketplace skill* 会让人感觉像是在发布——marketplace 正是用于分发内容的地方——因此即使源仓库和目标仓库都是私有仓库、内容也不会被发布到任何地方，清理反射仍会被触发。真实案例（2026-07）：一次从项目级 skill 迁移到私有 marketplace skill 的操作，把真实的配置路径、真实的十六进制值和真实的具名示例都泛化成了占位符。`quick_validate` 在**每一次**运行时都打印了 `🔒 audience: private`；作者每次都读到了，却仍然执行了清理，因为这种*活动*读起来像是在发布。代价并不只是表面上的——真实路径能让下一位读者去核对该值；而“项目自己的 token 文件”是无法打开的。

所以要把它当作一次查找，而不是一次判断：**读取目标位置的 `isPrivate`，如果它是
`true`，则执行清理需要所有者提出请求。** 私有→私有的移动是移动，不是发布。**当两个探测都没有返回结果时**（尚未连接远程仓库，也未运行
`quick_validate`），你没有可用的查找结果——应回退为将其视为公开，并明确说明这一点，因为不对称性就是如此：多问一个问题只会多花一句话，而不必要的信息泄露无法挽回。并且，`isPrivate` 报告的是目标位置**今天**的状态——一个位于私有仓库、即将发布的 skill，应当在发布它的 push 上执行清理，而不是在这一次执行。 如果你发现自己开始思考某些内容在私有目标位置中是否“应该”
被泛化，那种思考本身就是信号。

使用 **AskUserQuestion** 确认清理深度（对于公开目标位置，确认深度，
而不是是否执行；对于私有目标位置，确认是否需要执行）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**清理流程——通读是方法，扫描是辅助工具：**

1. **自行完整阅读 skill，并进行语义判断**（这才是真正的检查）：SKILL.md + 每个引用 + 每个示例。对于每个具体名词 / 示例 / 代码片段，询问“是通用占位符或公开实体，还是从真实项目 / 人员 / 讨论记录中直接取出的？”替换后者——即使没有扫描器标记出来也要替换。这是唯一能捕获没有关键词的信息泄露的方法。完整指南以及语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器，作为廉价的第一遍检查**：使用检查清单中的 grep 模式 + `security_scan.py`（第 6 步）。它们可以快速捕获明显的密钥 / 路径 / 已知名称——但“没有匹配项”并不代表检查通过。
3. **替换**每个发现的问题，使用保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。两条经过惨痛教训得出的规则：占位符本身不能编码真实值——`<acme-corp-domain>` 会原样泄露它本应隐藏的名称；应改为命名其*角色*（`<api-domain>`、`<upstream-provider>`）。另外，当你编写批量替换脚本时，要为其指定限定在 skill 目录内的明确文件白名单——未限定范围的查找替换会毫不客气地重写项目自己的 CLAUDE.md，并迫使你执行 git restore。
4. **通过重新阅读而不是重新 grep 来验证**：重新阅读已修改的部分，并确认没有破坏引用。

### 第 6 步：安全审查

在打包或分发 skill 之前，运行安全扫描器，以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密信息（API keys、密码、tokens）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）

**它不覆盖的内容** —— 这也是为什么仍然需要执行第 5 步的通读检查：gitleaks 和正则规则只会匹配*已知的机密信息格式和你列出的模式*。对于没有关键词的私密内容，它们在结构上无法识别，例如非英语语言中的真实人员/项目名称、真实对话记录中的逐字内容、从你自己工作中直接摘取的真实示例。`security_scan` 显示绿色只意味着“未发现已知格式的机密信息”，**并不意味着“该 skill 已完成脱敏”**。绝不要将其视为后者。

**首次设置：**如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 干净（可以安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前**必须修复**）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**在私有 skill 中，发现项是信息，而不是待办事项。**扫描器无法区分泄露的凭据和本来就应该存在的凭据，例如一个完整价值就在于预先填充好的模板，或一个指向其运行所在唯一机器的脚本。绝不要在私有仓库中自动修复：报告发现的内容，由所有者决定如何处理。下面的选项 A（“自动修复”）适用于计划公开发布的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包 Skill

skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个已有的 Git 跟踪 skill，在提供并重新验证完整审查结果之前，打包都会被阻止。当前标记仅是本地状态凭据，因此先提交或手动编写标记都无法绕过审查。下一次编辑会使审查失效：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及用于随包发布根目录 `evals/` 的 `--include-evals`（默认排除该目录，因为它属于开发资产）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **重新验证已完成的现有 skill 回归审查**（只要 Git HEAD 已包含该 skill）；仅有标记永远不足以授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描匹配）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 第 8 步：更新 Marketplace

打包后，更新 Marketplace 注册表，以包含新技能或已更新的技能。

**对于新技能**，在 `.claude-plugin/marketplace.json` 中添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于已更新的技能**，按照 semver 在 `plugins[].version` 中递增版本号。对技能文件的任何更改——即使只是修复一处拼写错误——都需要递增版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧技能，而你的修复则一直处于未发布状态。

**然后将其记录在变更日志中——这一步经常被跳过。** 递增版本号让更新变得*可安装*；而变更日志条目则让它在六个月后有人遇到同样的问题并进行搜索时仍然*可查找*。如果变更日志记录了其他每个技能的版本，却默默遗漏了你的技能，那还不如完全没有变更日志：这些空白会被理解为“那里没有任何变化”。

按照现有条目的格式，而不是自行发明格式——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。将它与版本递增放在**同一次提交**中；稍后再更新的变更日志，往往就永远不会被更新。

真实案例（2026-08）：某个技能连续发布了两个版本，版本号递增正确、门禁检查通过、PR 也已合并——但**完全没有变更日志条目**，因为这套流程中没有任何一步要求添加变更日志。两个版本最终都只是在之后的审计中才被发现。这正是纪律 #6 在这个文件本身上的体现：一条只存在于约定中、而没有落实为步骤的规则，每次都会输给“尽快完成”的驱动力。

**保持注册表差异最小——这是所有技能共用的唯一文件。** Marketplace 清单是所有并行编辑者都会发生冲突的地方，因此其中无关的格式变化，比其他任何地方的同类变化代价都高：它会把原本干净的三行版本递增变成其他编辑者在同时修改时必须处理的冲突。如果你通过脚本更新（解析为 JSON、修改后写回），重写过程会悄悄规范化文件原本可能没有采用的格式——末尾换行、缩进宽度、键顺序、Unicode 转义。往返处理原则：之后重新读取文件，并对其运行 `git diff --stat`；**唯一可以出现的行必须是你有意修改的字段。** 如果出现了额外行，应恢复文件原有的约定，而不是提交这种规范化结果（某次脚本化版本递增曾给一个原本从未包含末尾换行的清单添加了换行——在最可能被其他人同时编辑的文件中，平白多出一行差异，浪费了一次处理）。同样的原则也适用于技能会修改的任何共享注册表：锁文件、目录、索引文档。

**当 PR 经历了几次合并后仍未结束时，执行 rebase——然后证明你没有吞掉任何人的工作。** 清单容易产生冲突的特性，也使它最容易过时：一个修改注册表和变更日志的开放 PR，只要有其他内容合入就会发生冲突，因此应预期出现 `mergeable: CONFLICTING`，不要把它当成意外（曾有一个 PR 在某个下午主分支前进了 7 个提交后遇到这种情况）。如果仓库采用 squash merge，应执行 rebase 而不是 merge——在压缩后的历史中，合并提交没有任何收益。冲突本身几乎总是**累加式的**：两位作者分别在同一部分中追加了自己的条目，因此解决方式是**保留两者**，绝不要使用 `--ours`/`--theirs`，因为那会悄悄丢弃同事添加的那一行。

人们会跳过的步骤，往往正是能发现错误解决结果的步骤——**解决之后，确认与基线相比唯一的差异就是你的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要使用裸 `--force`：如果远程仓库自你上次获取之后发生了变化，租约会使推送失败；这正是有人向你的分支推送过更改，而普通强制推送会将其覆盖的情况。

**插件边界不属于此 skill 的职责范围。** 是否应将 skills 拆分为独立插件、如何组织 `source`/`skills`，以及用户能否单独切换 skills，都属于打包/分发领域——SSOT 是 `marketplace-dev` skill，而不是此处。当任务确实需要这些决策时：确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与 `skill-reviewer` 需要其脚本时引入 `skill-creator` 相同），然后阅读 marketplace-dev 的 cache-and-source-patterns reference 并遵循其中的要求。不要在此处重复其规则；复制一份会导致内容逐渐偏离。

**重命名、迁移或移除 marketplace 条目，对于已经安装它的每位用户来说都是破坏性变更**——当条目消失时，Claude Code 不会清理已安装的副本，导致悬空安装，并在每次 `marketplace
update` 时都报错。应像处理 API 弃用一样处理此类变更：在变更日志中附带迁移说明，并遵循 marketplace-dev 关于具体操作的指导。

**如果你亲自提交/推送 skill 仓库：**对于已有 skill，如果当前变更触及纪律 #5 的规则/契约/数值阈值，请确认审查产物记录了此次变更，并且该产物已提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不只是确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的审查不能满足当前的实质性变更。Step 5 的说明解释了为什么对于已经发布的 skill，真正的强制执行点是推送，而不是打包。然后只暂存 skill 的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充满无关变更，否则这些变更也会被带入提交（曾有一次提交卷入了一堆无关的 transcript 文件，最后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库实际的可见性，不要根据路径想当然——公共 skill 仓库应通过 PR + 审查，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成 skill 后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试 skill 后，用户可能会要求改进。通常这会紧接着使用 skill 发生，此时用户对 skill 的表现仍有清晰的上下文。

**改进筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了某项内容，就不要重复添加。

## Claude.ai 特定说明

在 Claude.ai 中，使用相同的验证深度路由器。当选择通用的 Tier 3 路径时，完整流程仍然是起草 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子代理，需要调整部分执行方式。具体调整如下：

**运行测试用例**：由于没有子代理，无法并行执行。对于每个测试用例，读取 skill 的 SKILL.md，然后自行遵循其中的说明完成测试提示。一次执行一个测试用例。这种方式不如由独立子代理执行严格（你编写了 skill，同时也在运行它，因此掌握完整上下文），但它仍然是有用的合理性检查，而人工审查步骤可以弥补这一点。跳过基线运行 — 只需使用 skill 按要求完成任务。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或者你正在远程服务器上），则完全跳过浏览器审查步骤。改为直接在对话中展示结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），将其保存到文件系统，并告知用户文件位置，以便用户下载和检查。直接询问用户反馈："How does this look? Anything you'd change?"

**基准测试**：跳过量化基准测试 — 该测试依赖基线比较，而在没有子代理的情况下，基线比较没有实际意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同 — 改进 skill，重新运行测试用例，询问用户反馈 — 只是中间不再加入浏览器审查步骤。如果文件系统中有迭代目录，也可以继续使用这些目录组织结果。

**描述优化**：本节需要使用 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要使用子代理。请跳过本节。

**打包**：`package_skill.py` 脚本只要有 Python 和文件系统，就可以在任何地方运行。在 Claude.ai 上，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新的 skill。在这种情况下：
  - **保留原始名称。** 注意 skill 的目录名称和 `name` frontmatter 字段，并保持不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前复制到可写位置。** 已安装的 skill 路径可能是只读的。先将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从副本进行编辑和打包。不要传递 `--new-skill`；非 Git 的现有 skill 副本仍然属于现有 skill。
  - **如果手动打包，先在 `/tmp/` 中暂存，**然后再复制到输出目录 — 直接写入可能会因权限问题而失败。

## Cowork 专属说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此通用的 Tier 3 工作流（并行生成测试用例、运行基线、评分等）适用。不要因为子代理可用，就将 Tier 1 或 Tier 2 更改升级处理。（如果 Tier 3 运行遇到严重超时，可以按顺序运行测试提示词，而不是并行运行。）
- 你没有浏览器或显示器，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击、在浏览器中打开该 HTML 文件的链接。
- 完成**通用 Tier 3**运行后，在自行修改 skill 之前，始终使用 `generate_review.py` 为人工生成评估查看器，而不是使用自定义 HTML。Tier 1、Tier 2 以及明确替代查看器机制的专用工作流，不会仅仅因为工作发生在 Cowork 中就产生查看器义务。
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。之后你可以读取该文件（可能需要先请求访问权限）。
- 打包功能可用 — `package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，但请将其留到 skill 完成制作且用户同意其状态良好之后再进行。
- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新的 skill。请遵循上方 claude.ai 部分中的更新指南。

- `agents/comparator.md` — 如何对两个输出进行盲测 A/B 比较
- `agents/analyzer.md` — 如何分析某个版本胜过另一个版本的原因

`references/` 目录包含其他文档：
- `references/eval_pipeline_schemas.md` — evals.json、grading.json、benchmark.json 等文件的 JSON 结构
- `references/sanitization_checklist.md` — 在公开分发前清理特定业务内容的检查清单

`scripts/` 目录包含此工作流使用的确定性门禁：
- `scripts/audit_skill_regression.py` — 比较不可变的旧 skill bundle 与编辑后的 bundle，创建明确的处置审查，并在打包现有 skill 前验证其哈希和证据。
- `scripts/reference_net.sh` — 列出你添加的行之间的正文交叉引用，用于第 4 步（编辑 Skill）中的 Reference-and-self-application 检查。其自身的标头就是契约：说明它涵盖的内容、明确交由 `lychee` 处理的内容，以及为什么它使用基础 ref 而不是 `HEAD`。

这里再重复一次核心循环，以示强调：

- 弄清楚 skill 的用途
- 对于现有 skill，在编辑前对旧 bundle 创建快照并进行清点
- 选择能够在采用任何专用工作流退出方式之前证伪此次变更的最低验证等级，并记录选择该等级的原因
- 起草或编辑 skill
- 运行该等级所需的证据验证，或运行所选专用工作流声明的等效机制
- 对于通用 Tier 3，与用户一起评估成对的输出，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复上述过程，直到你和用户都满意
- 运行并通过现有 skill 回归审查；仅 eval 通过不算完成
- 打包最终 skill 并将其返回给用户。

如果你有 TodoList，请将选定的验证等级及其所需证据添加到其中。仅对于通用 Tier 3，添加“创建 evals JSON 并运行 `eval-viewer/generate_review.py`，以便人工审查测试用例”。
