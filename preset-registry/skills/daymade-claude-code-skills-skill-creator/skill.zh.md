# Skill Creator

一个用于创建新 skill 并对其进行迭代改进的 skill。

从高层次来看，创建 skill 的过程如下：

- 确定你希望该 skill 做什么，以及它大致应如何实现
- 将变更归入能够证伪其可能故障模式的最低验证层级
- 编写该 skill 的草稿
- 使用能够证伪已变更行为的最小证据进行验证；将完整的配对评估流程视为需要单独授权的工作，而不是层级标签自动带来的结果
- 当所选层级产出定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写该 skill（如果定量基准测试暴露出任何明显缺陷，也应重写）
- 重复上述过程，直到你感到满意
- 只有当当前证据无法判定已变更行为时，才提升验证层级

使用此 skill 时，你的职责是判断用户当前处于这一流程的哪个阶段，然后切入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须缴纳的成本。诸如“优化”“改进”或“全面”这样的词描述的是意图，而不是故障面或评估预算。不要仅仅因为任务听起来范围很广，或之前的对话很长，就创建评估文件、并行派出配对 agent、对输出进行评分或启动查看器。

以下六项常设纪律贯穿始终，因为这些故障模式会产出看似令人信服、实则错误的 skill：

1. **先验证，再编写。** 写入 skill 的每一项技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察过的内容——无论是在本次会话中，还是在一个明确获批、经挖掘获得的会话中。现在无法验证？那就去验证，或者明确标注（“未经验证——源自记忆”）。skill 会放大其中包含的一切：经过验证的知识会不断积累，言之凿凿的错误同样如此。对于知识型 skill（其内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md) 以了解其操作版本：权威性层级（观察到的行为 > 机器可读契约 > 已实际运行的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前的文档示例冒烟测试，以及受众/Windows 可移植性检查清单。一次来源依据审计曾发现，多项言之凿凿的契约声明与作者当时已经掌握的证据相矛盾（方法论案例 9）。
2. **将“不可能/不支持”视为一种假设，而不是结论。** 当某项能力看似受阻时（API 错误壁垒、工具无法连接、格式无法打开），应先穷尽观察路径——UI 自身的网络流量、替代渠道、不同的已记录标识符——然后再将“平台不支持此功能”写入 skill。观察到的行为优先于推测出的请求形式。
3. **站在该领域的肩膀上——在编写或优化 skill 的方法论之前，默认将该领域公认的最佳实践检索到上下文中。** skill 方法论的质量只取决于上下文窗口中的知识，而不是潜藏在模型权重中的知识：预训练是有损的，会过时，而且如果没有真正调取权威来源，往往根本不会被激活。因此，你所编写内容的质量上限是 `your training data + the user's input`——*除非*你有意识地检索该主题领域真正的既有成果。务必这样做：通过 WebSearch 检索该领域的权威理论/标准/方法，并阅读该领域中任何随附或已安装的 skill，然后在注明出处的情况下，将起关键支撑作用的原则融入该 skill。**这与下文的“既有成果研究”属于不同维度**——后者寻找可复用的*工具/基础设施*；前者则以该学科积累的科学成果为 skill *方法论本身的质量*提供依据。将其作为**默认操作，而不是等到有人提出要求才去做**：简要告诉用户你正在借鉴哪个领域，并允许他们说“跳过”，但绝不要在该领域 40 年的公开成果只需一次搜索即可获得时，交付一个受限于你的记忆加用户提示的方法论。例如：数据可视化 skill 必须吸收 Cleveland 与 McGill 的图形感知排序以及 Bertin 的视觉变量（位置/长度优于颜色，颜色优于文本——这是测量结果，而非审美判断）；日期/时间 skill 必须揭示成熟的库及其公认的陷阱；说服/谈判 skill 必须检索成熟框架，而不是凭记忆重新发明。如果权威知识只存在于你的权重中，却从未进入上下文，那么你其实是在本可引用依据的地方进行猜测。
4. **在压缩现有 skill 之前先保留它。** 更新现有 skill 是一次迁移，而不是从空白页开始重写。在首次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧 bundle，或根据明确的 Git ref 重建它；任意副本加上来源标签并不能构成基线。清点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和简洁性允许移动内容或去除重复内容，但并不允许悄无声息地删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个无法匹配的旧单元进行分类。仅存在于 `evals/`、测试或未链接参考资料中的运行时契约仍然等同于已丢失。只要仍有任何候选项尚未分类，或任何真实缺口尚未修复，就不要宣称更新已完成。同样的逻辑也适用于*逆转*，而不仅仅是删除，并涵盖此前作出的任何承诺——不只是那些带有日期和姓名的承诺：**推翻已经作出的决定始终是一项提议，绝不能成为附带结果。** 明确说出来，并获得接受。静默重写比静默删除更糟糕，因为它会同时摧毁产物以及原本可以发现问题的证据——还会蒙蔽所有下游审阅者（参见 #5）。

**编辑前先对每项预期变更进行分类；“压缩”是一项关于行为等价性的主张，而不是“更短”的同义词。** 对于每个旧有用户场景，新启动的智能体仍必须能够找到触发条件、决策输入、支持的操作、停止/确认点、影响/恢复边界以及验证路径。在计划、审查和变更日志中，将以下名称用作独立的变更类型标签；在每个回归候选项的原因/语义审查中记录该标签，同时确保审计工具的 `disposition` 字段严格使用第 4 步中的枚举值：

   | 变更类型 | 定义 | 必需处理方式 |
   |---|---|---|
   | **无损压缩** | 仅改变表示方式：将细节迁移到可直接访问的随附参考资料中、根据打包提供的权威来源去重，或在保留上述每项运行时契约的前提下精简措辞 | 可以称为压缩；证明场景仍然可达，而不只是字符串仍然存在 |
   | **能力退役** | 之前可执行的任务或操作不再可用 | 不是压缩；明确指出退役的能力，获得可追溯的用户批准，并公布其边界 |
   | **范围收窄 / 边界变更** | 受支持的输入、目标、环境或模式减少；某个执行分支变为仅分析 | 即使这样更安全，也不是压缩；明确呈现并公布边界/权衡，然后获得可追溯的批准，除非用户已经明确要求进行这项收窄 |
   | **工作流或安全性重新设计** | 命令、顺序、确认方式、副作用、恢复方式或成功检查发生实质性变化 | 不是压缩；明确呈现新的契约和权衡，获得可追溯的批准（除非用户已经明确要求进行这项重新设计），然后独立于保留性验证对其进行验证 |
   | **缺陷修复 / 事实纠正** | 使实现或文字重新符合明确的既有契约或当前权威来源 | 不是压缩；使用能够作出判定的最小范围权威来源或确定性回归测试 |
   | **有损总结** | 精确条件、命令、决策语义或执行出口消失，且没有运行时可达的等价内容 | 这是回归，而不是优化；将其恢复，或通过上方某个已获批准的类别重新分类 |

   只有当权威来源随该技能一同提供，或该技能能够可靠访问它，**并且** SKILL.md 告知运行时读者何时加载它时，去重才算无损。“这个理念仍然存在于测试、变更日志、已安装的同级技能或作者的记忆中”不属于压缩。如果一个补丁包含多种类型，请分别列出；绝不能让压缩标签掩盖能力退役或重新设计。

5. **任何内容都不能仅凭自我审查发布——由独立且上下文全新的审查者进行对抗性检查，是固定步骤，而不是特殊情况。** 你对“现在已经没问题了”的判断来自生成该产物的同一模型，因此也会带有造成该缺陷的完全相同的盲点。这是实测结论，而不是经验之谈：在没有外部反馈的情况下，内在自我纠正并不能可靠地改进输出，有时反而会使其退化（Huang 等，ICLR 2024）；当生成者和评估者具有相同的错误模式时，反复迭代只会**增加信心，而不会增加信息**。再多的自检也无法摆脱这一点；只有外部视角可以。**完整流程——提示词模板、锚点选择、发现事项表和完整案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；首次审查前请先阅读。** 以下是关键规则：
   - **独立性有两个方面，而第二个方面正是作者容易忽略的。** *审查者的上下文*不得是你当前上下文的分叉——分叉会继承你的盲点，然后交回一个“已审查”的印章。但它据以衡量的*证据*也必须位于**变更影响范围之外**，否则它会继承你的**结论**：它读取一份已经彼此一致的产物和规范，然后报告两者一致。请注意，“本次会话中未编辑”是一条过于宽松的界线——在参考资料的受控案例中，被污染的记录是在*前一天*编辑的，三名审查者都没能发现一个他们在未经改动的对应记录中成功发现的缺陷。应按照你接触锚点的难度对其排序：用户自己的原始对话措辞 > 早于本次工作的 git 引用（`git log --oneline <ref>..HEAD -- <path>`；其中只要包含你的任何提交，该引用就失去资格）> 仅追加日志（这只是一项约定，而非强制机制）。**全新项目没有锚点——请如实说明并请求提供锚点，而不是声称某项你并未执行的检查已经通过。**
   - **只向其提供两项承载证据的输入：不可变产物和读者规范。** 还要提供用于限定本次审查范围、不作为证据的控制元数据：当前变更的影响范围、已命名的失败维度以及终止条件。不要提供设计理由、项目背景或“只需确认 X 没问题”之类的指示——这些内容会把独立审查者变成橡皮图章。读者规范和控制元数据用于说明由谁在何处执行什么操作，以及何时停止；它们不会告诉审查者实现是正确的。**对于 SKILL.md，读者是另一个负责执行它的智能体**，其失败模式是“我不知道该调用哪个工具”，而不是“我不明白这个词”——应询问它无法据以采取行动的是哪些指令。分派审查前冻结全部五个字段，绝不能使用事后补充的上下文来把发现的问题解释掉。
   - **对于可理解性，以及相对于语料库的完整性，它代表事实依据；但它无权裁决品味。** 对前两者直接采用其结论。将“这可能是一个缺陷 / 我建议采用 Y”视为假设，并先自行复现。绝不能把 AI 垃圾内容或审美判断委托给它——这属于同模型盲点。
   - **枚举失败*维度*，而不是内容领域——这也决定了要启用多少名审查者。** 维度是*你提出的问题*；领域是*你阅读的材料*。三名审查者分别覆盖场景、算术和差异，但都只问“这是否连贯？”，相当于为同一名审查者付了三次费用。**默认使用一名审查者，而且通常已经足够**；只有存在额外维度时才增加一名。自我审查最不擅长的维度是**忠实度**——“这是否仍然忠实于已作出的承诺？”——因为作者正是移动了承诺的人，而且连贯性与忠实度彼此正交：一份产物可以在内部完全自洽，同时彻底背离已经作出的决定。
   - **分派审查前冻结审查边界，并在满足该边界后停止。** 记录不可变产物/引用、读者规范、当前变更的影响范围、已命名的失败维度以及终止条件。当某项发现是由当前变更造成的、被当前变更扩大了影响、涉及的行为由当前变更新增宣传，或者某个旧有矛盾因编辑后的路径而变得可达时，该发现会阻止本次发布。既有缺陷如果没有变化，且未被重新承诺，就应作为单独的待办假设处理，而不能自动授权重新设计该技能。完成实质性修复后，由新的审查者重新检查失败维度及回归情况；不要重新开启一次范围不受限制的全技能审计。完整的判定流程和示例见：[references/independent-review-protocol.md](references/independent-review-protocol.md)。
   - **留下产物，否则这只是一则警告。** 纪律 #6 规定，只产生意见的检查不如产生实际产物的检查——因此这项检查也必须生成文件，否则它恰恰会在最关键的时候败给完成任务的冲动。请在你的私有、由 git 跟踪的知识仓库中，将 `independent-review.md` 写入 `skill-reviews/<skill-name>/`：其中应包含**审查者提示词原文**（以便后续读者判断它是否具有诱导性）、**每项都附有处置结果和理由的发现事项**（这正是合理筛选与丢弃刺耳意见之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是自己的私有知识仓库（或者根本没有这样的仓库），请如实说明并询问用户——不要猜测位置，否则可能落入两个禁区之一。两个禁止位置是：**不得放在 `<skill-name>-workspace/` 中**（这是会被清除的 gitignore 临时目录——该文件是跨会话的审查证据，必须在这些目录被清除后继续存在），以及**不得放在任何已经公开或将来可能公开或分发的仓库中**——这通常意味着不能放在被审查技能自身的仓库中（审查内容本身就会引用私有路径、真实姓名和项目细节）。在进行实质性编辑后，必须由一个*新的*智能体重新审查——实质性编辑是指规则、契约或数字发生变化，而不是修正错别字。**从第 5 步开始，该文件就是此次审查确实发生过的证据；文件缺失即意味着审查未发生。** **写入文件并不等同于确保它能在下一次会话中继续存在——必须在同一轮操作中，在该私有仓库内执行 `git add` 和 `git commit`。** 仅仅放在 git 工作目录中但尚未提交的文件，并不具备这条规则所要求的任何“由 git 跟踪”保障：它可能丢失、被覆盖，或者后续检查“是否已完成审查？”的流程根本无法发现它（真实案例：文件已正确写入正确路径，其中也包含真实发现——但后续自动检查仍然失败，因为它从未被提交；修复方式只是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械性的，并且与此互为补充：它能证明你没有*删除*行为，却无法说明你写下的内容实际上是否可供执行。

6. **在设计你编写的检查时，确保它们无法自我认证为通过。** Skill 在很大程度上由各种检查构成——门禁、检查清单、“发布前”步骤——而如果执行检查的上下文能够在*违反检查所编码的规则本身时*仍让检查通过，那么这种检查比没有检查更糟，因为它会制造信心。以下四条规则借鉴自那些在软件领域之前就已解决这一问题的领域：
   - **验证必须覆盖其规则的每一个条款。** 如果规则写的是“A + B + C”，证据就必须分别要求提供 A、*以及* B、*以及* C 的证明。在包含三个条款的规则后面附加一行确认内容，最终只会由作者已经完成的那个条款来满足；其他条款则完全不可见。真实案例：某个报告编写 Skill 包含一道交付门禁，其规则写道：“选项以并排标签块呈现 + 突出显示建议选项 + **背景以完整、自足的句子表述，让陌生人也能看懂**”——但规则下方的证据行只要求“有 N 个决策项，全部呈现为标签块”。作者执行了该门禁，写下这条证据，自我认证为通过，然后发布了一个页面；其中的标签只有单个字符，所有上下文都被删除。规则一直都在文件中；只是检查从未衡量过那个条款。
   - **会对正常输入误报的检查比没有检查更糟。** 上述故障是检查本应失败却通过；这里则恰好相反——检查本应通过却失败。后者代价更高，因为它会让操作者养成条件反射式绕过检查的习惯（`--no-verify`、`SKIP=1`、`--force`）；一旦形成这种习惯，门禁就会对*所有*输入失效，包括它原本要拦截的输入。因此，在编写默认拒绝的检查时，**假阳性的优先级高于假阴性**：漏掉一个真实问题，只会让你为该次实例付出代价；而阻止一个正常输入，则会让你失去整道门禁。
     注意这个征兆：**因反复踩中同一个陷阱而产生的挫败感，本身就是风险信号**——作者恰恰会在这种状态下匆忙发布一项从未针对正常输入进行校准的防护措施。真实案例：在一天内三次踩中同一个格式陷阱后，作者向某个 linter 添加了一项正则表达式检查；它在项目自己的语料库中拦截了 **33 个正常输入**，并在同一小时内被撤销。先校准，再启用——在真实且已知正常的材料上运行任何默认拒绝的检查，并确认假阳性为零；宁可放宽检查，让它偶尔漏报，也不要让它发生任何一次误报。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是自足的”无法被其作者判定为不合格；“遮住页面其余部分，单独阅读一张卡片，然后说明它要决定什么”则可以。应优先采用能够产出制品的检查——例如命令输出、引用的文本行或截图——而不是只能得出意见的检查。
   - **同样的怀疑也应适用于你实际*运行*的检查，而不只是你编写的检查。** 上述四条规则适用于随 Skill 一同发布的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样也是工具；错误的工具会像正确的工具一样信心十足地报告干净的结果。在 2026-07 的一次会话中，五条不同的验证命令在两个方向上都给出了错误结果：缺少 `-L` 的 `find` 报告某个已安装 Skill 的文件缺失（它们位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了被审计对象的另一个副本；一条反转的 shell 条件错误地警告说某项删除操作尚未发生；一个跨行匹配的正则表达式凭空制造出 55 个“丢失的引文”；而一项只搜索五个文件中两个文件的操作，报告有两条规则缺失，但它们其实存在于第三个文件中。**这些结果最初无一例外都被相信了，而每一个错误都只是在使用另一种形式的检查重新运行后才被发现。**

解决办法是实验实践中最古老的一条：**在你已知答案的案例上运行仪器，然后再相信它在你不知道答案的案例上的结果。** 要用 grep 搜索一个你预期不存在的字符串？先以相同的命令形式搜索一个你知道确实存在的字符串——如果这也返回 0，那么坏掉的是命令，而不是文件。这样做只多花一行，却能把“我检查过了”变成“我用校准过的仪器检查过了”。

     有两种具体形式值得牢记，因为它们都在上文出现过，而且都会*悄无声息地*失败：`find` 在没有 `-L` 时不会跟随符号链接（而 Skill 安装经常是指向源代码仓库的符号链接），并且 `--exclude-dir` 会按基本名称匹配目录树中的所有位置，而不只是在你心中所想的那条路径上匹配。

     **而且，这条规则还有后半部分，只有当检查方法被发布时才会造成问题：要针对*标准*实现进行校准，而不是针对你机器上的实现。** 上述仪器规则能保证*你的*结论可靠；这条规则则能保证*读者的*操作有效。写入 Skill 的工具行为断言——某个标志、某种递归模式、某个声称“会跟随符号链接”的选项——会在二进制程序版本完全未知的机器上执行，而且两端都无法察觉差异：你测试时它能正常工作，到读者那里却悄无声息地什么也不做。造成这种情况的机制有两种，而且从会话内部都无法看出：**同一个命令名称解析到了不同的程序**（Shell 别名或函数遮蔽了二进制程序——请注意，`\tool` 只能绕过*别名*，因此 `command tool` 或绝对路径才是唯一具有确定性的形式），以及**同一个程序在不同实现中的行为不同**（BSD 与 GNU，或某个直接替代实现）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将其作为符号链接陷阱的修复方法写入 Skill，并发布到了一个拥有 1200 个 Star 的公共仓库——他们的 `grep` 是通过 Shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 上，同样的 `-R` 什么也匹配不到（它需要 `-RS`），因此这个规定的修复方法对大多数读者都悄无声息地失效了，而它恰恰出现在警告验证器会悄无声息地失败的章节中。

     所以：**在有关工具行为的断言进入发布产物之前，要使用标准二进制程序**（`/usr/bin/<tool>`）重新运行验证，而不是使用 Shell 交给你的程序。如果无法通过这项验证，就不要写入那个标志——**应优先采用与实现无关的表述方式**：自行解析路径（`readlink -f`），而不是寄希望于某个递归标志；在脚本中执行子字符串测试，而不是使用面向行的匹配；说明你需要的*行为*，而不是你恰好知道的选项。只在你的环境中有效的操作说明比没有说明更糟，因为读者根本无法发现它其实悄无声息地什么也没做。

   - **采用成熟的检查清单实践早已确定的方法。** 确定一份清单是**边读边做（READ-DO）**（阅读的同时执行——适用于低频或不熟悉的流程），还是**先做后确认（DO-CONFIRM）**（凭借专业能力完成工作，然后在明确定义的**暂停点**停下来确认——适用于承受时间压力的熟练操作者），并将其设置在真正的暂停点，而不是“工作流中的某个位置”。清单只保留**致命关键项**——既关键，又容易在压力下被遗漏，大约五到九项；超出这一数量的内容都会降低执行率（[Gawande，*《清单宣言》*](https://www.shortform.com/blog/types-of-checklists/)）。此外，应优先采用新乡重夫所说的**控制**，而不是**警告**（[防错法](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，会败给尽快完成任务的驱动力；而阻止继续推进或强制生成产物的步骤根本不需要依赖警觉性。当 Skill 只能发出警告时，至少要把警告放在做出决策的位置——**如果执行上下文从不打开某份参考资料，那么归档在其中的规则实际上就不算规则。**

另一方面，他们也许已经有了技能草稿。在这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应该始终保持灵活。如果用户说“我不需要进行一大堆评估，跟着我的感觉来就行”，你也可以改为这样做。

然后，在技能完成之后（不过再次强调，顺序可以灵活调整），你还可以运行技能描述改进器。我们为此准备了一个完全独立的脚本，用于优化技能的触发效果。

## 首先：共存检查（官方 skill-creator 插件）

在进行任何其他操作之前，先快速检查一次（只需执行一次 grep，在常见路径下无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（最常见的情况）：**什么都不要做——不要安装任何内容，也不要向用户提及本节。继续进行当前任务。
- **存在：**官方插件的 skill-creator 与此版本现在会以近乎相同的描述同时出现在技能列表中，因此未来的会话会随机路由到其中一个。用一两句话告知用户这一情况，然后提供以下选项（未经用户同意，绝不要擅自执行）：
  1. **推荐**——运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的自检 SessionStart 钩子复制到用户的 Claude 配置中，并在 `settings.json` 中注册该钩子（同时创建备份），从而确保未来的每次会话都会将技能相关工作确定性地路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；当用户按名称指定官方插件时，它仍然完全可用。在未安装官方插件的机器上，安装程序会拒绝安装任何内容，因此绝不会遗留下无用的钩子。
  2. 替代方案——运行 `claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 撤销），将官方条目完全移出技能列表，从而消除歧义。

如果钩子已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有内容。

同样的机制也适用于用户创建的技能：当他们的技能有意与已安装的某个技能重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一个工具包——请参阅“现有方案研究”下的“共存与优先级”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

## 与用户沟通

使用技能创建器的人，对编程术语的熟悉程度可能千差万别。如果你还没听说过（你怎么可能听说过呢，这种趋势也是最近才开始的），现在出现了一种趋势：Claude 的强大能力正激励水管工打开终端，也让父母和祖父母开始搜索“如何安装 npm”。另一方面，大多数用户可能还是相当熟悉计算机的。

因此，请注意上下文线索，以判断应当如何措辞！在默认情况下，给你一些参考：

- “评估”和“基准测试”稍微有点专业，但还可以使用
- 对于“JSON”和“断言”，在不加解释地使用这些词之前，你需要从用户那里看到明确的线索，确认他们知道这些词是什么意思

如果你对某些术语有疑问，可以进行简短说明；如果不确定用户是否理解，也可以用简短的定义澄清术语。

### 使用 AskUserQuestion（关键——请务必阅读）

**在每个决策点都要积极使用 AskUserQuestion 工具。** 如果存在结构化选项，不要在对话中提出开放式文本问题。这是你能带来的最大单项用户体验改进——用户往往会同时处理多个窗口，而且可能已经有 20 分钟没看过这段对话了。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段，以及刚刚发生了什么（1-2 句话）。用户可能已经切换到其他任务。
2. **简化说明**：用通俗语言解释需要做出的决定。不要使用函数名或内部术语。说明它能做什么，而不是它叫什么。
3. **给出建议**：先给出你的建议，并用一句话解释原因。如果选项涉及工作量，请同时列出双方所需时间：`(human: ~X min / Claude: ~Y min)`。
4. **提供选项**：给出 2-4 个具体的、以字母标记的选项。每个选项都应是一项明确的操作，而不是抽象概念。

**规则：**
- 每个问题只涉及一个决定——绝不要把不相关的选择合并在一起
- 提供退出通道（AskUserQuestion 始终隐含“其他”选项）
- 接受用户的选择——可以提醒他们注意取舍，但绝不要拒绝继续执行
- 如果答案显而易见且不存在需要权衡之处，就跳过提问（直接说明你将做什么）
- **如果问题超时且没有得到回答（用户暂时离开了键盘），既不要停滞不前，也不要擅自越过有关偏好或范围的决策。** 先完成不会产生副作用的基础工作——编辑前快照、清单整理、评估用例收集、只读审计/健康检查——并将需要判断的事项（重构方向、要删除什么、是否继续）留到用户回来后再决定。然后明确说明你已经完成了哪些工作，以及还有哪些事项在等待用户决定。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话中可能已经包含了用户希望固化的工作流（例如，他们说“把这个变成一个技能”）。如果是这样，应先从当前对话中提取答案——使用过的工具、步骤顺序、用户做出的修正，以及观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**来源清单——始终在起草前完成，并遵守同意边界。** 盘点当前对话以及存在重叠内容的现有文档/技能（参见下文的“既有成果研究”）。较早的本地会话 JSONL 文件属于独立的私有来源：除非用户明确要求挖掘历史记录，或者你解释将读取哪些内容后，用户主动批准使用该来源，否则不要打开或解析这些文件。如果获得批准，只能通过对话挖掘工作流中经过脱敏的提取流程纳入相关的历史会话；绝不要将原始对话记录加载到你自己的上下文中。如果未获批准，则继续使用当前对话和现有项目来源，不要将缺少历史记录视为阻碍。

在挖掘对话（或会话记录）时，应清点**两类资产——它们会存放在不同位置**。*知识*——端点、参数、陷阱、决策规则——会成为 SKILL.md 中的指导内容或放入 `references/`。*会话中必须编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——则适合放入 `scripts/`：如果本次会话编写了这些内容，那么下次调用时还得重新编写，因此应将其参数化、清理敏感信息并打包。此前的一次提炼保留了润色后的说明文字，却遗漏了可复用的辅助工具；由此得出的一般经验是，应同时兼顾知识→references 和代码→scripts 这两条渠道。

当源材料是*过去的*会话转录记录（Claude Code 项目目录下的 JSONL 文件），而不是当前实时对话时，请进入对话挖掘工作流。不要在主上下文中打开原始转录记录，也不要将原始路径/内容交给子代理。必须先完成确定性的清单 → 发现 → 脱敏 → 分块流程，之后才能让任何代理看到内容；只有经过脱敏的分块才能进入最小角色/分片计划，并且必须在预算关卡中声明确切的单元数量和并发上限。

**首先，在回答以下问题之前，先确定这属于哪个方向。** 请求可能属于几种*相反的*情况之一：构建新技能 / 编辑现有技能 / 优化 skill-creator 本身 / 或者它根本不是技能（而是一次性任务）。方向猜错会浪费整个会话——为“新技能”开展的研究与“优化元工具”所需的研究完全不同。当措辞含糊不清时（例如，一边指向 skill-creator 自身的路径，一边说“给我做一个技能”），此时调用一次 AskUserQuestion 只需花费 30 秒。下面的包装器技能分支是其中一种特殊情况；方向检查本身是通用要求。

`Use skill-creator to optimize <existing-skill>` 表示走常规的现有技能更新路径。它**并不**授权挖掘对话历史、进行大范围重写、归类为第 3 层级，或开展多代理评估。应先检查实际提议的变更；只有当这些变更确实引入了某种故障面时，才进行升级。

1. 这个技能应该让 Claude 能够做什么？
2. 这个技能应在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应设置测试用例来验证技能是否有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。具有主观输出的技能（写作风格、艺术创作、需要品味校准的报告）往往无法使用断言——但“没有断言”并不等于“没有验证”。它们的验证路径按成本从低到高依次为：
   - **历史任务重放**：重新运行该技能过去实际处理过的一个真实提示词，分别使用旧版和新版技能，并根据本次变更涉及的具体规则比较输出（“新输出是否真的遵循了这次更新引入的 token / 标题语法？”）。这种方法成本低，并且能够发现“规则虽然写了，但没有任何内容读取它”的问题。
   - **将生产环境作为评估**：承认真正的测试是用户下一次实际使用——然后明确建立反馈循环：此后用户的每一次纠正都是需要回写的事件（纳入技能自身的“迭代/活文档”章节），每一次认可都是语料库素材。一个与品味有关的技能如果发布时没有这种回写习惯，就不会改进；如果具备这种习惯，即使从不运行正式评估，也会逐渐收敛。**而当技能的输出是会持续运行的东西——守卫、监控器、计划任务、钩子——其自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户纠正的前提是用户注意到问题并愿意费心反馈；而已部署的机制会主动报告自身情况，通常一天之内就会出现结果，误报则是这种报告最鲜明的形式，因为它证明你写下的某条规则存在错误，而这种错误无论重新阅读多少遍都无法发现。应将第一次误报视为一次按计划产生的评估结果，而不是麻烦：在认定机制行为异常之前先检查它，因为更可能的结论是*指令*写得过于绝对。（真实案例：某个技能规定了一项显式失败检查，部署后的检查在夜间因一个完全健康的状态触发了一次，修复方式是纠正技能中那句过于绝对的表述——没有人投诉，是遥测数据发现了问题。）
   - 对于视觉输出，使用**渲染 + 人工审查**（即技能自身的视觉质量检查关卡），绝不要用 grep 断言假装衡量美学效果。**而且用于验证的渲染器必须与交付物实际使用时所采用的引擎相同**——恰好安装了哪个预览器，并不意味着它可以替代目标应用程序。若缩略图工具的布局引擎与目标应用不同，它会悄无声息地*掩盖*你正在寻找的那些缺陷；在错误的引擎上得到绿色验证结果，比完全没有验证更糟，因为它会带来虚假的信心。真实案例（2026-07）：某个 .docx 文件通过 macOS Quick Look 缩略图完成了“视觉验证”，但该工具无法复现两端对齐文本的拉伸效果；用户一用 Word 打开文档，就发现其中的信息块被拉得支离破碎。修复方法是安装与 Word 兼容的引擎（LibreOffice），将文件转换为 PDF，逐页栅格化，然后阅读每一页。要么匹配引擎，要么所谓验证就只是表演。**这一原则不仅适用于渲染器，也适用于所有验证工具**——解析器、代码检查器、验证器：它必须与生产环境共享同一种实现，否则它给出的绿色结果毫无意义。第二个案例也具有相同的模式：一位作者试图在源文件阶段检查一种会破坏最终文档的标记模式，但使用的却是与生产工具链*不同*的 markdown 实现——它将三个已知有问题的输入全都解析为完全正常，因此，任何基于它构建的预检查都会悄无声息地放过所有问题。诚实的结论是，这种特定缺陷只能在生产工具运行后检测，因此检查应放在那里。**当没有任何可用工具与生产环境共享同一种实现时，应明确说明该阶段无法执行检查——不要构建一种只会产生虚假绿色结果的检查。**
   根据技能类型建议适当的默认选项，但让用户自行决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认技能类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前期分类将决定后续的整个评估策略。务必在此处正确分类，以免日后浪费精力。

### 扩展还是创建检查——在任何专用分支之前运行

以下三个专用工作流均以“**不要**继续阅读下文章节”结束，而 *Prior Art Research* 恰好位于它们之后。**这种顺序只是版面顺序，而非执行顺序。**“扩展还是创建”的判断适用于每个分支；跳过这一步，恰恰会导致会话最终交付一个与已安装技能重复的技能。

因此，在转入 wrapper-skill / conversation-mining / artifact-corpus 之前，先回答一个问题：**是否已经存在一个应当涵盖此能力的技能？**

**发现根目录，不要凭记忆回想。** 手工维护的安装位置列表恰恰是最容易过时的产物，而你遗忘的那个根目录正是最终会带来麻烦的地方。

**搜索文件，而不是名为 `skills` 的目录。** 技能目录以*技能*命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、市场克隆和插件缓存中可能根本没有名为 `skills` 的目录——搜索这个名称会悄无声息地跳过它们，表面上却像是在正常工作。每个技能都有一个 `SKILL.md`；这是与目录布局无关的搜索依据。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

步骤 3 预计需要几秒钟，并且返回的结果仍可能多于你的需求；请使用能力特有的术语而非通用术语来缩小范围（`chart` 会匹配几乎所有内容，而 `stacked bar` 则不会）。

这项工作所能触及的根目录——也是凭记忆列清单时通常会遗漏的地方：技能源码仓库（一个 `claude-code-skills` 检出目录及其任何 `-pro` 同级目录）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过市场安装的套件——源码仓库中没有任何迹象表明它们位于那里）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、各配置档案的配置主目录（`~/.claude-profiles/<name>/`），以及——这个完全没有任何路标——**每个项目自己的 `.claude/skills/`**。正是第 2 步，让这成为你亲自验证过的结论，而不是从别人那里沿袭来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何市场、任何全局技能列表或任何源码仓库清单里；在规划新技能时，你通常会打开的内容中，没有任何东西会提到它们。真实案例（2026-07）：一次会话为某个领域构建了一个全局技能，彻底检查了源码仓库、全局目录和其他智能体目录，什么都没找到，于是发布了。后来搜索对话历史时，发现了一个针对完全相同领域的成熟项目级技能，它已有一个月之久，就位于某个项目的 `.claude/skills/` 中——其中包含新技能所缺少的八条规则，包括一条用户亲自指定的规则。除了项目级根目录之外，所有根目录都检查过了，而这次排查仍以十足的信心报告“没有既有成果”。

**当重叠项*确实是*某个无关项目中的项目级技能时该怎么办**——这正是上述惨痛案例会把你带入的情形，也是下面三条没有涵盖的情形：你无法把同级技能添加到一个根本不存在的套件中，而“扩展它”就意味着编辑某个无关项目的工作树。已验证有效的做法是：**将其规则收纳进你正在构建的技能中，然后在获得所有者同意后停用项目本地技能**——它是基于真实工作编写的，因此应将其视为更成熟的来源，并以它为基准进行协调。停用他人正在使用的技能应由所有者决定，而不应成为你构建过程中的附带结果。

这句话遗漏了四件事，其中任何一件都会让你受阻：

- **“以它为基准进行协调”是一项可反驳的推定，而不是规则。** 有两种常见的例外：项目技能可能已经*过时*（规则是几个月前针对一个后来已发生变化的系统编写的），也可能具有*项目特异性*（规则仅在该项目的约束下成立——将它们全部照搬会使你的技能适用范围变窄，而本文档其他部分明确告诉你不要这样做）。收纳来的规则也是另一位作者的记忆，因此要像纪律 #1 要求你对写入技能的任何内容所做的那样，**逐条重新验证**。
- **“停用”需要一种机制，而第一步并不是你直觉上会采用的那一步。** 按以下顺序进行：

  1. 在 grep 技能的*引用*之前，先用 **`find` 查找技能的*主体***。同一个技能在同一仓库中经常不止一份——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被不同工具从同一工作树中加载。Grep 回答的是“谁提到了它”；只有 `find` 能回答“它有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要把技能自身的名称放进 `--exclude-dir`**（它按基本名称匹配，因此会隐藏所有同名目录，包括那份你尚未发现的副本——参见纪律 #6 中的工具规则）。真实案例（2026-07）：一次停用操作正是这样做的，它修复了找到的全部五处引用，却在 `.agents/skills/` 下留下了第二份完整副本——由 git 跟踪、没有停用标记，而且是缺少最新规则的陈旧快照——其他工具仍会将其作为有效技能加载。
  2. 在删除任何内容*之前*，**验证从旧技能所在的位置确实能够访问新技能的位置**——你刚刚推送的市场技能并不会自动完成安装，必须先更新市场并安装插件；如果先停用旧技能，就会出现新旧技能均不可用的空窗期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常以符号链接指向源码仓库，而不带该选项的 `find` 会报告文件缺失（参见纪律 #6 中的工具规则）。
  3. **然后** grep 查找引用，并将仍然有效的引用重新指向新位置。区分**实时指令**（技能列表、交叉引用、告诉下一位智能体该使用什么的交接文档）与**历史记录**（例如决策日志中写着“我们在 X 日发布了这个”）——改写后者会为了修复一个并不存在的问题而破坏审计轨迹。
  4. **然后**不要直接删除每个主体，而是将其替换成一个 `superseded by <skill>` 存根，并确保每份副本中的存根在字节层面完全相同。**保留 YAML frontmatter**——缺少它的 `SKILL.md` 可能会直接加载失败，而不是以提供有效信息的方式失败——但要重写 `description`，让存根声明自身已停用，而不是继续宣传旧触发条件；否则，它仍会在路由竞争中胜出，却已无法提供相应服务。正文只需要说明两件事：该能力迁移到了哪里，以及一行说明迁移原因。
- **使用下方的所有权测试来确定所有者**（它在这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍能告诉你它属于谁）。当所有者就是正在与你交谈的人时，只需一次 `AskUserQuestion` 即可获得“同意”。**当无法联系到所有者时，只收纳规则，不要停用技能**（这会让两个技能都保持有效并竞争同一触发条件，与停用请求被拒绝时的最终状态相同——参见下方的“共存与优先级”）。
- **如果所有者拒绝停用它**，现在就会有两个技能竞争同一个触发条件；这是下方所述的“共存与优先级”问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 该项目技能无法通过搜索新技能的标题名称匹配到；它是通过正文中的领域术语匹配到的。在候选根目录中 grep 新技能将处理的*概念*。

如果存在重叠：

**判断适用哪一条——这是谁的技能？** 文件系统中的命中结果并不包含归属信息。查看市场的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在其所在仓库中运行 `git remote -v`；位于 `~/.claude/plugins/marketplaces/` 下的命中项，也完全可能只是安装回你自己机器上的*自有*市场。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同一个问题。

探测操作会对以下两种情况作出错误判断或无法给出答案，因此在信任结果之前应先检查它们：**fork** 显示的是你自己的远程仓库，但内容属于其他人——应将其视为第三方技能，因为他们的上游改进仍然无法继续传递给你。而当**既没有 marketplace.json，也没有 remote** 时（仅存在于本地的项目、手动复制到全局技能目录中的技能），探测结果是无声的，而不是否定的：**询问所有者，而不是猜测**。

- **重叠的是第三方技能**（市场套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*轻量增量*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本——并**使用带命名空间的名称引用它**。把别人的引擎克隆进你的套件是代价高昂的错误：他们的升级无法继续传递给你，而两个副本会悄无声息地逐渐分化。
- **重叠的是你自己的技能**：扩展它，或在其现有套件中添加一个同级技能。创建一个争夺相同触发条件的独立技能对任何人都没有帮助。**例外：**如果它位于一个*无关项目*的工作树中，则这两种做法都不适用——请参阅上面的项目级情况。
- **某个相关技能已经指向你正在填补的空白**（例如，其描述中写着“对于 X，请使用 Y”）：构建完成后，应闭合这个引用链——更新该指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**在 2026-07 的一次真实会话中，团队花了一天时间让一个第三方 docx 引擎生成正确的中文商务文档，随后便进入了包装器技能分支——这直接跳过了既有方案研究。它当时准备交付的形态，是一个重新承载该引擎能力的全新技能。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个轻量增量技能，其中包含正确用法和经过验证的生成器脚本 → 领域工作流技能调用该增量技能。用户不得不在它落地前两次指出问题，其中第二次纠正更为尖锐：*“不要额外复制一份——在他们的实现之上编写正确用法，并引用他们的技能；这才是技能即代码的含义。”*

### 验证深度路由器（在选择任何工作流之前运行）

在进入通用或专用工作流分支之前，选择**能够证伪变更后行为的最低层级**。应根据具体变更及其故障影响面进行分类，而不是根据行数或请求中的措辞：一条发生变更的破坏性命令可能比大篇幅的文字清理具有更高的层级，而对现有技能进行“优化”的请求仍可能只是一次有明确边界的修正。在选择层级之前，列出你实际打算更改的规则、契约、脚本、权限和输出。如果尚不清楚该列表，请先检查，并将分类保留为暂定；范围存在不确定性并不能作为归入第 3 层级的依据。

| 层级 | 适用情形 | 所需证据 | 默认不要添加 |
|---|---|---|---|
| **1 — 定向** | 这是一个现有技能；没有新增或实质性更改任何能力、触发器类别、工作流分支、输出契约、依赖项、权限或外部写入行为；且编辑恰好属于以下一种：(a) 仅更正拼写/格式，不改变行为；(b) 对文档/配置进行事实性更正，且可由直接权威来源判定其正确性；或 (c) 修复有明确边界的实现问题，以恢复已有的显式契约，**并且**修复后的行为由确定性回归检查覆盖。可能改变代理行为的澄清不属于第 1 层级 | 对所有三种情况：运行 `quick_validate`、检查差异，并完成现有技能迁移门禁。然后仅使用对应的证据：(a) 精确回读/格式检查；(b) 权威事实及其针对性检查；(c) 显式的现有契约及确定性回归。仅当规范 #5 中关于规则/契约/数量的阈值被触发时，才增加其中要求的一名全新审阅者 | 代理行为重放、配对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 行为抽样** | 这是一个现有技能；变更会影响代理行为，但不会新增能力、触发器类别、输出契约、脚本行为、依赖项、权限或外部写入；并且可用 1–2 个具名示例及明确的验收标准来覆盖整个变更后的行为。对一条现有路由或证据选择规则进行有明确边界的修正，即使会改变所选路径，仍归入此层级 | 仅运行这 1–2 个具有代表性的启用技能重放，加上针对性的确定性检查，以及规范 #5 要求的一次全新上下文审阅 | 默认不添加基线、配对扇出、方差分析、基准测试、查看器或评估文件。若明确要求这些内容，则应经过独立的证据预算门禁，且不会因此重新分类该变更 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新技能；任何新增或发生实质性更改的能力；广泛的跨分支重写或方法论扩展；触发器/描述优化；新增工作流分支，或对输出契约、脚本能力、依赖项或权限进行实质性更改；高风险自动化或外部写入；或者变更后的行为本身涉及 3 个以上不同的提示词类别、重复试验或存在实质差异的方法 | 首先运行确定性门禁，然后仅添加覆盖指定故障维度所需的证据。只有在通过独立的重型评估授权门禁后，才可使用下文所述的完整配对流水线；第 3 层级本身不会启动该流水线，并且同一门禁也可以授权在其他层级添加额外证据 | 不要仅根据第 3 层级标签就自动进行配对扇出、使用评分器、运行基准测试或使用查看器 |

#### 重度评估授权门槛——与层级分类分开

层级描述的是**风险和不确定性**；它并不授权令牌消耗或智能体扇出。通过此门槛改变的是允许采用的证据计划，而不是层级。通用的成对基线 → 评分器 → 基准测试 → 查看器流水线仅可在以下任一条件下运行：

- 用户明确要求进行 A/B、基线、基准测试、重复试验、使用查看器或多智能体评估；或者
- 执行者能够列出至少三种不同的提示词类别、相互竞争且均合理的结果，以及成对比较会改变的决策，然后获得用户的明确选择加入。

对于现有技能优化，默认使用零个评估智能体：先运行确定性检查，如果行为仍存在不确定性，则最多进行一到两次启用技能的重放。规范 #5 所要求的一名全新上下文审查者是发布门槛，并非创建审查者团队的许可。有关令牌/成本敏感性的指令会阻止重度流水线，直到用户明确撤销该指令。

在生成超过一个研究、挖掘、评估或评分智能体之前，应将**角色**与**执行单元**区分开来：

- 每个额外角色或审查者都必须负责一个不同的失败维度或输出。模板可用性绝不能成为增加角色的理由。
- 必要的实验组和语料分片可以共享同一个维度：启用技能组和基线组需要隔离的上下文，而一个挖掘角色可能需要处理多个有界分块。启动前，应说明执行单元的确切总数、并发上限，以及合并它们为何会污染比较结果或超出分块预算。默认串行运行；明确的 A/B/挖掘请求只授权这些必要单元，而不授权额外角色。
- 如果扇出是由执行者提出而非用户明确要求，应就该数量获得用户的选择加入。如果交互式提问工具不可用或用户未作答，则采用较轻量的证据路径；沉默不代表同意。

如果某个单元既不对应独立的角色/输出，也不是必须隔离的实验组/分片，则不要生成该单元。

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，应升级层级。用户请求取消或降低评估级别时，应立即停止已经启动的成对评估智能体、基线、评分器、聚合和查看器工作。如果风险分类仍有参考价值，可以保留，但只能报告实际运行过的证据以及尚未检查的维度；不要把未运行的重度套件描述为该标签自动“要求”的内容。当达到规范 #5 的规则/契约/数量阈值时，不要取消其要求的单个全新上下文审查者，也不要取消任何用于防止破坏性操作或外部影响的安全门槛。机械式现有技能迁移审计、公开技能净化以及任何特定领域的安全门槛也仍独立于此路由器。

### 专项工作流：第三方 CLI 工具的包装技能

在决定采用通用技能创建流程之前，应检查此前的会话是否实际上需要改用**包装技能**工作流。包装技能是一种配套工具，用于安装、配置、诊断和修复既有的第三方 CLI 工具或技能包——这些代码由他人编写，而用户刚刚花费一轮会话在自己的机器上将其调试至可用状态。

以下信号表明此工作流适用（任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 会话中出现了真实、具体的错误消息，并且用户和 Claude 已经共同找到了具体的修复方法（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把它整理成一个 skill”“把它保存为一个封装 skill”“这样其他人就不必再经历这一遍”“把这次 session 做成一个 skill”的话。
- 用户明确提到了某个第三方工具的名称，并希望其他代理或其他人能够使用它，而无需再付出他们刚刚经历过的学习成本。

以下信号表明此工作流**不适用**（改用上面的通用工作流）：

- 用户想要为某个准备从头编写的东西创建 skill。
- 会话过程很顺利——没有值得记录的实际阻碍。
- 该 skill 将封装用户拥有或控制的服务（这是他们自己的代码；应编辑源代码，而不是进行封装）。
- 所谓的“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当封装 skill 工作流适用时，保留上面所选的验证层级。创建封装就是创建新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用编写章节；请跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流——其任务是从当前对话中挖掘安装流程、已修复的错误以及已做出的设计决策，并将挖掘结果转化为一个完整、独立的封装 skill，使其他用户能够安装并从中受益，而无需再次经历这段调试过程。

封装 skill 工作流有自己的架构约定、代码模板和 Tier 3 验证协议——由于其输出是用户的安装状态，而不是可以轻松断言的文件，因此它取代了不兼容的通用测试用例机制；这并不意味着降低工作标准。运行证据计划所选择的兼容通用步骤；通用的配对评估步骤仍然需要通过重型评估授权关卡。记录该专用协议取代了哪些机制。规范的参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库的根目录——这里的裸相对链接曾在此 skill 被移入套件时失效过一次，恰好印证了下面跨 skill 引用规则的警告），它是对腾讯 IMA skill 的封装，由一个真实会话使用这一工作流提炼而成。

### 专用工作流：利用对话历史丰富 Skill

在决定采用通用 skill 创建流程之前，请检查当前会话是否实际上是在要求将**过去的对话提炼成 skill**。当用户在多个 Claude Code / Codex 会话中持续调试、设计或探索某个主题，并希望将积累的经验转化为可复用的 `references/` 时，这会很有用。

**必须有明确的来源意图。** 一段很长的实时对话、一个刚完成的调试任务，或 `use skill-creator to optimize <skill>`，都不代表用户同意打开本地历史记录，也不能作为进入此工作流的理由。对于普通更新，应直接使用实时对话。只有当用户明确要求挖掘/提炼先前的本地对话，或指定特定的历史会话作为源材料时，才进入对话挖掘工作流。

适用信号（必须全部满足）：

- 用户明确将本地/过去的对话历史指定为输入，例如“mine my chat history”“enrich this skill from earlier sessions”或“把以前的对话沉淀到 skill 里”。
- 源会话及时间/范围边界已知或已确认。
- 预期输出是可复用的知识或代码资产，并且这些内容无法从实时对话和当前 skill 包中直接表达。

不适用信号（应改用上面的通用工作流）：

- 用户基于单个提示词或想法创建一个全新的 skill。
- 用户要求优化现有 skill，但没有要求读取先前的本地历史记录。
- 相关修正和证据已经出现在实时对话中。
- 用户希望为刚安装的第三方 CLI 工具创建封装（使用上面的 wrapper-skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的对话记录导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件中。
- 源材料是用户认可的一批成品，而不是对话——应使用下面的成品语料库提炼工作流。

当对话挖掘工作流适用时，保留上面选择的验证层级。新挖掘出的 skill 属于第 3 层；丰富现有 skill 时，只有在满足所选层级的能力边界的情况下，才能保持在所选层级。**不要**继续阅读下面的通用编写章节；直接跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端遵循该工作流，包括其验证协议。这是一个**回溯式提炼**工作流：它会发现经批准的本地历史记录，对其进行脱敏和分区，只执行语料库所支持的挖掘轮次，并在验证后提升经过审核的候选内容。

对话挖掘工作流有自己的架构约定、智能体提示词、模板和验证协议。该协议实现了所选层级的专用机制；执行证据计划所选的兼容通用步骤，将重量级通用步骤置于其授权门控之后，并记录所有替代操作。这是将明确获准使用的对话历史转化为 skill 可复用知识库的规范方法。

### 专用工作流：从经认可的成品语料库中提炼用户偏好

在采用通用流程之前，检查当前会话是否要求**从用户认可的一批成品中提取用户的真实偏好**——例如经认可的 HTML 报告页面、生成的文档和设计。这是区别于上述两类来源的第三种提炼来源：材料是**成品，而不是对话**，输出是**可执行的品味**（明确的原则、量化的参数、词汇），而不是知识或安装修复方案。

表明此流程适用的信号（任意一项即可）：

- 用户列出已完成的产物，并表示“这些都是我认可的样例” / “你来学到底什么是我想要的” / “从这些已认可的示例中提取我的偏好”。
- 某个品味校准技能（报告生成器、文档样式设计器、演示文稿构建器）拥有一个持续增长的已认可样例语料库，而用户要求让该技能真正从中*学习*，而不只是为其建立索引。
- 用户抱怨此前的更新“只加了示例”——只是将样例编入目录，而没有改变技能的行为。

表明此流程**不**适用的信号：源材料是对话/纠正内容，而不是获得认可的成品（请使用对话挖掘）；样例并未得到用户本人的认可（认可与否是准入门槛——请先询问）。

当此流程适用时，保留上方选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。基于新语料库派生的技能属于第 3 层级；向现有技能添加实质性的新决策能力也属于第 3 层级。专用协议会实现所选层级的语料库机制，且不会降低其标准；执行证据计划所选的兼容通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代操作。其核心纪律也适用于任何向现有技能添加材料的情况：**编目 ≠ 提炼**——在语料库表中登记样例不会对技能下一次运行产生任何改变；对于每一项新增内容，都要问“*这是否改变了一条决策规则？*”；如果所有写入内容的答案都是否定的，就不得宣布提炼会话已经完成（方法论案例 15）。该工作流的主干是：通过脚本提取并对所有产物进行定量比较（每种模式须达到 ≥3 个产物的阈值，并针对每个声称的常量检查例外列表）→ 通过证据锚点进行分层归纳 → 写入决策规则层（将不变量与依赖语域的变量分开）→ 独立完整性审计（常设纪律 #5）→ 回归审计。

### 既有成果研究（不可跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——正是让技能产生价值的关键。任何公共仓库都无法提供这些内容。但如果已经存在成熟工具，用户就不应该把时间浪费在重复发明基础设施（API 客户端、身份验证流程、速率限制）上。既有成果研究旨在为基础设施层寻找可复用的构建模块，让技能能够专注于编码用户独有的方法论。

**两个维度，不要将其混为一谈。** 本节为*基础设施*层寻找来源（可复用的工具 / MCP / 库 / 现有技能）。*方法论*层有两个独立的输入：用户的私有优势（仅属于用户，无法检索获得），**以及该领域已确立的最佳实践 / 科学知识；根据常设纪律 #3，默认应将这些内容检索到上下文中。** 找到合适的工具并不意味着已经完成第二项工作——一个采用了图表库却从未吸收 Cleveland/Bertin 理论的可视化技能，其能力上限仍然受限于你的预训练。两者都要做。

**按以下顺序搜索这些渠道。** 默认以内联方式开展研究。只有在上文的重度评估/智能体预算门槛确认存在真正相互独立的未知项后，才使用子智能体；公共来源渠道并不是默认的扇出式搜索组合。

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **当前对话或已明确批准的历史记录** | 用户已验证的工作流、经过验证的 API 模式、调试期间所做的修正 | 直接使用当前对话。仅在通过上文的明确来源门槛后搜索较早的本地历史记录，随后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中已配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 和 `external_plugins` 目录 |

| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或对文档 URL 使用 `WebFetch` |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于找出用户自己已验证的模式和现有集成。渠道 4-8 用于查找公共基础设施。用户的私有 SOP 始终优先——公共工具是构建模块，而非替代品。在竞争激烈的领域（金融、交易、专有业务运营），有价值的方法论绝不会公开。

**优先合并/扩展而不是新建，并且要扫描每一个技能根目录——不只是 `~/.claude`。** 当渠道 1-3 找到与所请求领域重叠的现有技能时，通常正确的做法是对其进行扩展或合并——**但如果它位于不相关项目的工作树中，则方向应反过来：从中提取内容并纳入你正在构建的技能，而不是合并进它**（参见上文“扩展还是新建”检查中的项目级案例）（一个真实的“新技能”任务最终变成了“让现有提取器成为新归档器的提取阶段”），而不是发布一个会因相同触发条件而与其竞争的并行技能——两个相互重叠的技能会争夺触发机会，并让用户感到困惑。搜索时，**应发现安装根目录，而不是凭记忆列出清单**——使用上文“扩展还是新建”部分中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会完全遗漏源代码仓库、市场克隆和插件缓存，因为其中的技能目录是以技能名称命名的）。应运行覆盖范围检查，而不是仅仅相信这句话：**每个项目自己的 `.claude/skills/`** 是凭记忆列清单时最容易遗漏的根目录，因为该项目之外没有任何地方会引用它。用户已经在*任何位置*安装的技能，都是最有力的先例，而项目本地技能通常最成熟：它是针对实际工作编写的。

**如果发现了公开的 MCP 服务器或技能，请克隆并验证它——不要轻信 README：**

1. **阅读实际源代码**——许多项目有精美的 README，代码库却徒有其表
2. **验证认证方式**——它是否与 API 的实际认证方式一致？（X-Api-Key 请求头、Bearer 或 OAuth——很多项目在这里都有错误）
3. **检查测试覆盖率**——零测试意味着它只是原型，而非生产级项目
4. **检查维护情况**——最后提交日期、未解决的议题数量、对错误报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有用途冲突
7. **检查依赖规模**——庞大的依赖树会带来冲突和更大的安全攻击面

**决策矩阵：**

| 发现 | 行动 |
|---------|--------|
| 成熟的 MCP/SDK 可处理基础设施 | **采用它，并在其上构建**——安装 MCP，然后将技能构建为工作流层，对用户的方法论进行编码 |
| 存在部分可用的 MCP 或 SDK | **扩展**——将其用于基础设施，并在技能中补齐缺失部分 |
| 公开技能涵盖相同领域 | **仅借鉴其结构**——竞争领域中的公开技能本质上都是通用的。用户的优势在于其私有 SOP |
| **存在可提供当前构建内容中某项子能力的互补技能** | **将其打包进来**——将该互补技能的自包含资产复制到你的包中并完成接线。不要依赖用户已经预先安装它。请参阅下文的“互补技能” |
| 不存在任何公开项目 | **从头构建**——在编写完整技能之前，先验证 API 访问模式是否有效（认证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——一个由你掌控、耗时 2 小时的自定义实现，胜过一个存在集成阻力和上游风险的“成熟”工具 |
| 用户有意取代已安装的技能（分叉版、加固版） | **随附取代套件发布**——请参阅下文的“共存与优先级” |

#### 共存与优先级（有意重叠）

对于重叠问题，默认的修复方式是合并到现有技能中（见上文）。但当用户*有意*发布一个与已安装技能重叠的技能时——例如官方插件的分叉版、内部加固版——技能列表中会出现两个描述相似的条目，Claude 会随机在它们之间进行路由。请按逐步升级的顺序解决：如果重叠并非有意为之，则重命名；添加用于判定优先级的描述（“取代 X——当两者同时出现时，始终使用此技能”）；对于分发的分叉版，使用 `scripts/generate_supersede_kit.py` 将条件式取代套件植入技能中——这是一种基于用户同意的 SessionStart 路由钩子，仅会安装在确实存在竞争技能的机器上，在其他机器上拒绝安装，并在任意一方消失时自行停用。有关工作机制、决策表、SKILL.md 示例措辞和沙箱验证，请参阅：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此技能也使用同一套件针对官方 skill-creator 插件进行自我实践（请参阅顶部的“第一步：共存检查”）。

**更常见的情况是：你的新技能会悄无声息地丢失对*已安装技能群体*的触发权，而这并非出于任何刻意的分叉。** 一个技能所属的领域（图像生成、PDF 处理、仪表板）通常已经挤满了多个已安装的技能，而新技能可能会在自动路由中输给所有这些技能。因此，**应尽早验证触发情况——内容做得好，并不代表构建工作已经完成。** 草稿完成后，通过 `claude -p` 发起几个真实的查询，检查新技能是否确实胜出；如果没有，**请明确指出它输给了哪个具体的竞争技能**（不同查询往往会输给不同的技能）。然后需要了解两点：(1) **在拥挤的触发位中，仅靠文字描述并不总能胜出**——解决路径依次为：重命名 → 通过描述打破平局/`SUPERSEDES` → 手动调用 → `SessionStart` 路由钩子（结构性方案；会修改全局配置，因此需要获得用户的明确同意，遵循与 `--no-verify` 相同的审慎原则）；(2) **修复方式取决于竞争技能的作者是谁**——如果竞争技能是*第三方*的 → 接受手动调用或使用路由钩子；如果竞争技能是*你自己*的 → 将它们合并/整合为一个技能，不要让自己的两个技能为同一个触发条件相互争抢。（完整的解决路径位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处和上面的摘要只是指引，不要独立扩展它们。）记录所选择的路径（例如添加一条“激活”说明，注明“手动调用，竞争技能均为第三方”），可以避免下一个会话重新争论这一问题。（方法论案例 13）

##### 互补技能（打包，不要依赖）

构建涉及某个已有互补技能所在领域的技能时，有两种选择：

- **依赖该技能已安装**：很脆弱——用户可能没有安装它，或者安装了不同的版本。每一次缺少依赖项的故障都可以追溯到这一选择。
- **将其打包**：把互补技能中可独立使用的资产（脚本、模板、参考文档）复制到你自己的包中，并完成接线配置，使你的技能可以独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，请将其打包进来。** 这对于以下内容尤其重要：
- 状态栏/UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证/清理脚本
- 通用的数据转换实用工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要一个状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。配置文件设置技能不会依赖用户先运行 `statusline-generator`，而是将 `statusline.sh` 打包进来，并在 `claude-profiles-init` 期间将其接入每个新的配置文件。两个技能仍然可以各自独立发挥作用，而作为封装器的技能也能独立运行。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装程序”。这会把依赖问题推给用户，并形成脆弱的安装顺序。应改为将其打包。

研究完成后，通过 **AskUserQuestion** 展示研究结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，优先采用成熟的基础设施来处理管道层，并为方法论层构建自定义逻辑——价值就体现在这里。

### 访谈与研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准和依赖项。在把这部分梳理清楚之前，先不要编写测试提示词。

在有助于研究时检查可用的 MCP（搜索文档、查找类似技能、查询最佳实践）。默认以内联方式开展研究。仅针对明确且尚未解决的问题使用子代理，绝不要因为工具可用就自动并行展开任务。提前准备好上下文，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈，填写以下组件：

- **name**：技能标识符
- **description**：何时触发、执行什么操作。这是主要的触发机制——既要包含技能的功能，也要包含应在何种具体场景下使用。所有“何时使用”的信息都应放在这里，而不是正文中。注意：目前 Claude 倾向于“触发不足”技能——即在技能本可发挥作用时不使用它们。为解决这一问题，请让技能描述稍微“主动”一些。例如，不要写“How to build a simple fast dashboard to display internal Anthropic data.”，而可以写成“How to build a simple fast dashboard to display internal Anthropic data. Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a 'dashboard.'”

  **控制好长度：description 有严格的 1024 字符上限，超过该长度将无法通过验证。** 这与上述“主动”建议存在直接冲突——为扩大覆盖范围而添加的每个触发短语都会占用字符预算——因此应在扩写之前而不是之后进行测量：`len(description)`，不要凭感觉。真正的陷阱并非初稿（初稿很少接近上限），而是*多年后的更新*，它会为新覆盖的范围添加触发条件：成熟的描述通常距离上限仅有几十个字符，此时**添加触发条件就是零和取舍——你必须删除一个现有触发条件来为它腾出空间。** 应有意识地作出这种取舍，并在提交中明确说明，因为悄无声息地删除触发短语，确实会缩小技能的触发范围，而且在技能不再对某人触发之前，没有人会注意到这一点。（实践中曾出现过这样的情况：一次更新为新覆盖的故障模式添加了触发条件，将描述推高到 1280 个字符，并经过两轮压缩才降至 1003——代价是删除了三个已有的触发短语，这项决策本应明确作出，而不是在与验证器较劲时才被发现。）必须删减时，优先删除其场景仍可通过同义词或相邻短语触达的短语，保留那些没有其他触达路径的短语，并记住，正文中的限定语（“on platform X and Y”、括号内的列举）通常比独立的触发短语更适合删除——正文可以从主体内容重新推导，而触发短语则不能。
- **compatibility**：所需工具、依赖项（可选，极少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。请在 `---` 标记之间使用以下字段配置技能行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 是否必需 | 描述 |
|-------|----------|-------------|
| `name` | 否 | 技能的显示名称。如果省略，则使用目录名称。仅限小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 推荐 | 此技能的作用及其适用场景。Claude 使用此字段决定何时应用该技能。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork`，以便在分叉的子代理上下文中运行。** 请参阅下文的“内联与分叉：关键决策”——选择错误会导致技能失效。 |
| `agent` | 否 | 设置 `context: fork` 时要使用的子代理类型。可选值：`Explore`、`Plan`、`general-purpose`，或来自 `.claude/agents/` 的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true`，以防止 Claude 自动加载此技能。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false`，以将其从 `/` 菜单中隐藏。适用于不应由用户直接调用的背景知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：请勿设置此字段。** 省略该字段可使技能获得由用户权限设置控制的完整工具访问权限。设置该字段会不必要地限制技能的能力。 |
| `model` | 否 | 此技能处于活动状态时使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于表明预期参数。示例：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此技能生命周期的钩子。示例：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** 技能内容中的 `$ARGUMENTS` 会被替换为用户在技能名称后提供的文本。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### 内联与分叉：关键决策

**这是设计技能时最重要的架构决策。** 选择错误会在不发出任何提示的情况下破坏技能的核心能力。

**关键约束：子代理无法生成其他子代理。** 使用 `context: fork` 运行的技能（作为子代理）无法：
- 使用 Task 工具生成并行探索代理
- 使用 Skill 工具调用其他技能
- 编排任何多代理工作流

**决策指南：**

| 你的技能需要…… | 使用方式 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **内联**（无 `context`） | 子代理无法生成子代理 |
| 调用其他技能（Skill 工具） | **内联**（无 `context`） | 子代理无法调用技能 |
| 运行外部 CLI 的 Bash 命令 | **内联**（无 `context`） | 在主上下文中拥有完整的工具访问权限 |
| 执行单个聚焦任务（研究、分析） | **分叉**（`context: fork`） | 上下文隔离，执行过程干净 |
| 提供参考知识（编码约定） | **内联**（无 `context`） | 指南可丰富主对话 |
| 可被其他技能调用 | **分叉**（`context: fork`） | 必须作为子代理才能被生成 |

**示例：编排器技能（必须内联）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**示例：专家技能（适合分叉）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**示例：参考技能（内联，无任务）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的技能设计（正交性）

技能应当彼此**正交**：每个技能只处理一个关注点，并通过组合协同工作。

**模式：编排器（内联）调用专家（分叉）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是内联的（无 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个技能都应职责单一——不要将编排与执行混在一起
4. 通过引用（例如检查清单、模板）共享方法，而不是复制代码

##### 流水线交接（顺序技能链）

除了编排器/专家组合之外，技能通常还会形成**顺序流水线**，其中一个技能的输出是下一个技能的输入。每个技能在完成工作后，都应主动建议合乎逻辑的下一步。

**模式：在 SKILL.md 末尾添加“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界中的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion **由用户主动选择**——未经询问，绝不自动调用下一个 skill
2. 仅当输出可以自然地作为另一个 skill 的输入时才提出建议——不要强行建立关联
3. 提供一个“No thanks”选项——用户可能不需要完整的流水线
4. 建议中应解释下一步**为何**有帮助（例如，“ASR 输出通常包含识别错误”）
5. 最多提供 1-2 个建议——选项过多会导致决策疲劳

**何时添加交接：**询问“此 skill 的输出通常会成为另一个 skill 的输入吗？”如果是，则添加“Next Step”部分。如果这种关联很少见或很牵强，则不要添加。

**反模式：**串联不具备自然数据流关系的 skill。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**切勿为可自动检测的能力添加手动标志。**与其要求用户传入 `--with-codex` 或 `--verbose`，不如在运行时检测能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力由系统自动检测，范围由用户决定。skill 应当自行发现它能做什么并采取相应行动，而不是要求用户记住已安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | Subagents 可以使用 |
|-------------|----------------|-------------------|-------------------|
| （默认） | 是 | 是 | 否（内联运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（显式委派时） |

#### 渐进式披露

skill 使用三级加载系统：
1. **元数据**（name + description）- 始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文** - 每当 skill 被触发时加载到上下文中
3. **捆绑资源** - 按需加载（无大小限制，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由目标行数决定。一个没有冗余内容的 600 行 skill，胜过一个遗漏关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问：“每个部分都物有所值吗？”如果是，就保留。如果某些部分只是为了凑篇幅，或解释 Claude 已经知道的内容，就删减这些内容，而不是删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分为参考文件，而不是人为地把所有内容硬塞进一个简短的主文件中。
- 对于现有 skill，渐进式披露是一种内容迁移策略，而不是删除启发式方法。旧的运行时约定必须仍可从打包产物中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或审查者的记忆都不能替代运行时约定。
- 在 SKILL.md 中清楚地引用参考文件，并说明何时应读取它们
- 对于大型参考文件（>300 行），应包含目录

**领域组织**：当一个技能支持多个领域/框架时，按变体进行组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 避免意外原则

这不言而喻，但技能不得包含恶意软件、漏洞利用代码，或任何可能危害系统安全的内容。如果技能的意图已被描述，其内容就不应让用户感到意外。不要配合创建具有误导性的技能，也不要创建旨在协助未经授权的访问、数据外泄或其他恶意活动的技能。不过，类似“扮演 XYZ”这样的内容是可以的。

#### 编写模式

在说明中优先使用祈使句。

**定义输出格式** - 可以像这样编写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式** - 加入示例很有帮助。可以像这样设置格式（但如果示例中包含 "Input" 和 "Output"，可能需要稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得内置到技能中的可用性模式** - 以下四种结构性元素一再将“能用但令人困惑”的技能转变为用户真正能够驾驭的技能——它们是让一个被频繁使用的技能变得易用的具体增强措施，因此，当技能具有多种模式、会运行命令或可以重新运行时，应优先采用这些模式：
- **入口决策树**：如果技能有多种模式，开头提供一个简短的“用户说了 X → 使用模式 Y”映射，让模型能够正确选择路径，而不是靠猜测。
- **每条命令后的预期输出块**：紧跟在命令之后展示“你应该看到什么”，这样模型（和用户）就能区分真正的成功与无提示的失败。
- **故障排除部分**：列举已知的失败模式及其修复方法——对于其他人将在你无法查看的机器上运行的技能，这是最有价值的部分。
- **步骤 0 幂等性保护**：如果重新运行可能会重复执行已完成的工作，在进行任何成本高昂的操作之前，先用一个成本较低的“这是否已经完成？”检查作为开头。

### 写作风格

尽量向模型解释为什么某些事项很重要，而不是大量使用生硬、过时的 MUST。运用心智理论，并尽量让技能具有通用性，不要过度局限于特定示例。先写一份草稿，然后以全新的视角重新审视并加以改进。

### 日期和版本引用

**保留事实性日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的技能应该写明 "Suno v5.5 (March 2026)"，因为如果没有日期，未来的读者就无法判断信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（"if before August 2025, use the old API"）——日期一过，而又无人更新时，这种逻辑就会立刻变得错误。

规则：
- **发布日期、“最后验证”日期**：保留。它们是参考时间点，而不是过期日期
- **定价、排名、法律状态**：应包含这些信息，但要标记为可能变化（“截至上次检查约为 $0.035/次生成”），以便读者知道需要重新核实
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前的方法，并可选择在折叠的/已弃用的章节中记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash/等）。

- **何时包含**：当同一段代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优势**：节省 token、结果确定，并且可以在不加载到上下文中的情况下执行
- **注意**：Claude 可能仍需读取脚本，以进行修补或针对特定环境的调整
- **用户可变数据应存放在捆绑包之外**：如果脚本会积累用户数据（纠错字典、学习到的偏好、缓存），请将其存储在稳定的、相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其单独设置备份——绝不要将其存放在 skill 目录内。每次更新和套件迁移时，skill 安装都会被清除并重新创建；相对于主目录的存储位置则会原封不动地保留下来。正是通过这种方式，一个会不断积累字典的 skill 在完整的套件迁移中实现了用户数据零丢失

##### 参考资料（`references/`）

旨在按需加载到上下文中的文档和参考材料，用于为 Claude 的处理过程和思考提供信息。

- **何时包含**：当 Claude 在工作时应参考相关文档时
- **示例**：用于财务模式的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库模式、API 文档、领域知识、公司政策、详细工作流指南
- **优势**：使 SKILL.md 保持精简，仅在 Claude 判断有需要时加载
- **最佳实践**：如果文件很大（>10k 字），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或参考资料文件中，不能同时存放在两处

##### 资产（`assets/`）

不用于加载到上下文中，而是在 Claude 生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用某些文件时
- **示例**：作为品牌资产的 `assets/logo.png`，作为 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件架**：对于生成产物的 skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、可逐字嵌入的片段，这些片段具有冻结的行为契约和注册表引用——请参阅步骤 4 中的组件架检查

##### 隐私和路径引用

**在应用以下任何内容之前，先确定目标用途。** 以下所有内容描述的都是
skill 发布给陌生人时会出现的问题。对于存放在作者自己的私有
仓库中的 skill，同样的“违规项”通常恰恰是它能够正常工作的原因——真实的绝对路径使
脚本可以运行，模板中的真实账户则免去了下次运行时重新填写
信息的麻烦。`quick_validate` 会自动检测这一点（它会询问 `gh`，确认包含该 skill 的仓库是否为私有仓库），
并在这种情况下将可移植性/标识符问题降级为提示；当私有 skill 准备发布时，`--audience=public` 会强制执行
严格检查。

**在私有 Skill 中，这些发现应由所有者决定，而不是由你决定。** 未经询问，不要用占位符替换真实路径、改写硬编码凭据，或对示例进行“脱敏”——这样做会破坏一个正常运行的工具，只为满足一条针对其根本不会发布到的目标位置而制定的规则。如果你认为某些内容应该更改，请说明你的发现，并由所有者决定。（其设计先例是 npm 的 `"private": true`：通过声明目标位置来改变工具所执行的规则；之所以添加此机制，是因为人们总是不小心发布内容。）

**对于计划公开分发的 Skill，至关重要**——其中不得包含用户特定或公司特定的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 Skill 安装路径，例如 `~/.claude/skills/`
- **允许**：Skill 包内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外情况**（严格按“禁止”列表实现的验证器会将当前这个 Skill 本身标记出来——对正常输入误报比漏报更糟）：当覆盖优先级裁决或归属说明*要求*指明发布者时，可以使用发布者自己的名称/品牌；当相关段落的主题*就是* `~/.claude/skills/` 之类的安装路径时，也可以使用这些路径（这是教学材料，而非硬编码依赖）

**跨 Skill 引用**：不带其他限定的相对路径始终表示“位于当前 Skill 自己的包内”——验证器和读者都会这样理解，因此，使用不带限定的路径指向另一个 Skill 的文件既无法通过验证，也会误导读者。指向另一个 Skill 时，应在正文中指出所有者（“marketplace-dev 的 cache-and-source-patterns 参考资料”），并使用带命名空间的名称调用 Skill（`/suite-name:skill-name`，而不是不带限定的 `/skill-name`）。当 Skill 在套件之间移动时，不带限定的跨引用会悄无声息地失效——有一次套件迁移因此产生了 21 个损坏的跨引用，经过两轮清理才全部修复。

##### 版本管理

**至关重要**：Skill 不应在 SKILL.md 中包含版本历史或版本号：

- **禁止**：SKILL.md 中的版本章节（`## Version`、`## Changelog`）
- **正确位置**：Skill 版本在 marketplace.json 的 `plugins[].version` 下进行跟踪
- **理由**：Marketplace 基础设施负责版本管理；SKILL.md 应包含不受时间影响的内容

#### 参考文件命名

文件名必须做到无需阅读内容即可理解其含义。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：人们能否仅凭文件名理解文件内容？

有两种例外情况：使用连字符的名称与使用下划线的名称同样合适（分隔符从来都不是重点——自解释性才是）；此外，命名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已由目录进行了限定——目录提供了具体性，而重命名这些文件会破坏不同工作流之间的平行结构。

Anthropic 已编写 Skill 创作最佳实践——在创建或更新任何 Skill 之前，请先获取该文档：https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices.md

### 完整评估测试用例（仅限单独授权的配对方案）

仅当重度评估授权门控通过时，才可进入本节。风险等级本身既不授权也不禁止收集此类证据；明确提出的全流程请求不会重新划分底层变更的类别。不要仅仅因为 SKILL.md 发生了变更就使用本节。专门化工作流应遵循其在上文声明的替代约定。

编写 Skill 草稿后，构思 2-3 个真实的测试提示词——即实际用户确实可能提出的那种请求。**对于会操作实时系统（正在运行的服务、已登录的客户端、生产数据）的 Skill，请为每个测试提示词明确指定副作用预算**——例如，“仅进行只读探查并得出结论；不要执行下载/操作 UI。”在“仅仅测试”时对实时环境进行变更的评估属于真实操作，而不是测试。通过 **AskUserQuestion** 向用户展示这些提示词：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——只需填写提示词。你将在下一步中于运行过程期间起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整架构请参阅 `references/eval_pipeline_schemas.md`（包括稍后要添加的 `assertions` 字段）。

## 完整配对评估流程（仅限单独授权）

仅在重度评估授权门控通过后运行本节。风险等级仍应以变更后的行为所对应的等级为准。按会影响决策的阶段执行流程，并在不确定性消除或用户请求的基准测试交付物完成后停止；不要预先启动下游评分器、聚合或查看器工作。用户取消或降低评估等级时，必须立即停止重度评估流程。未经授权时不要使用本流程，也不要机械地添加专门化工作流已明确替代的通用机制，并且不要使用 `/skill-test` 或任何其他测试 Skill。

将结果放入与技能目录同级的 `<skill-name>-workspace/` 中。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些目录——应随着工作推进按需创建。

### 步骤 1：运行已获批准的使用技能组／基线组配对实验

对于每个已获批准的测试用例，在相同的提示词和副作用预算下，运行一个使用技能的样本及其基线。这两个实验组有意共用一个失败维度，但需要彼此隔离的上下文；它们是必要的实验单元，而不是额外的审查者角色。启动前，说明实验组总数和并发上限。默认串行运行，并且绝不能超过获授权的单元数量。

**使用技能运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（提示词相同，但基线取决于具体上下文）：
- **创建新技能**：完全不使用技能。使用相同的提示词，不提供技能路径，并将结果保存到 `without_skill/outputs/`。
- **改进现有技能**：使用首次编辑前由强制性现有技能回归关卡捕获的旧版本。让基线子智能体指向该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，请停止并从 Git 重建权威基线，然后再继续；绝不能将已经编辑过的目录树用作旧基线。**要清楚这种比较能够辨别什么：它只能衡量本轮的变化量。** 如果你最想验证的能力已经存在于编辑前快照中——例如，某个同级会话可能恰好在你开始之前提交了那项修复——那么使用技能版本与旧版本之间的 A/B 测试对该能力的分辨力为零；当该能力正是测试目标时，应选择更早的引用作为基线。

为每个测试用例编写一个 `eval_metadata.json`（断言目前可以为空）。根据每个评估所测试的内容为其指定一个描述性名称——不要只使用「eval-0」。目录也使用这个名称。如果本次迭代使用了新增或修改过的评估提示词，请为每个新的评估目录创建这些文件——不要假定它们会从之前的迭代中自动沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：在运行过程中起草断言

不要只是等待运行完成——你可以高效利用这段时间。为每个测试用例起草定量断言，并向用户解释这些断言。如果 `evals/evals.json` 中已经存在断言，请审查它们并解释其检查内容。

良好的断言应当能够客观验证，并具有描述性名称——它们在基准测试查看器中应当清晰易懂，让浏览结果的人能立即明白每个断言检查的内容。**应针对意图编写断言，而不是针对字面上的工具路径**——应写成「语音内容保留在答案中」，而不是「调用获准的读取器脚本」。如果某次运行通过另一条获准路径实现了该意图（例如，读取一个已经内嵌转录文本的归档文件），它就应当通过；如果将其判定为字面路径失败，就会人为制造一个假阴性，随后还会导致你在错误的位置进行「修复」。主观性技能（写作风格、设计质量）更适合进行定性评估——不要强行为需要人工判断的内容设置断言；其真正的验证路径（历史任务重放、将生产用作评估并养成回写习惯、渲染并由人工审查）列在「Capture Intent」的问题 4 下。

断言起草完成后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试结果。

### 第 3 步：在运行完成时捕获计时数据

每个子智能体任务完成时，你会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们通过任务通知传递，不会持久化到其他位置。每条通知到达时就进行处理，不要尝试批量处理。

### 第 4 步：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分**——启动一个评分子智能体（或直接进行评分），让它读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（而不是 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过编程方式检查的断言，应编写并运行脚本，而不是凭肉眼判断——脚本速度更快、更可靠，并且可以在多轮迭代中复用。**但客观的 grep/脚本断言是一把双刃剑**（相同词语但含义不同会导致误命中，措辞不同则会导致漏检），因此**基准测试通过率只是一种信号，而不是最终结论**：抽查每条断言实际匹配到的内容，并留意基线运行是否暴露了技能本身的事实性错误（比如“等等，API 里确实有这些数据”的时刻）。参见方法论 §5.3–5.6 和 §6.4。

2. **聚合为基准测试结果**——从 skill-creator 目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及 mean +/- stddev 和 delta。如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md`，了解查看器所需的确切架构。
将每个 with_skill 版本放在对应的基线版本之前。

3. **执行一次分析审查**——阅读基准测试数据，并揭示聚合统计数据可能掩盖的模式。有关需要关注的内容，请参阅 `agents/analyzer.md`（“分析基准测试结果”部分）——例如，无论是否使用技能都始终通过的断言（不具区分能力）、高方差评估（可能不稳定），以及时间/token 之间的权衡。

4. **启动查看器**，同时展示定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器陷入失效状态**：进程仍然存活，但没有任何程序在监听——可使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或对该 URL 执行 curl（失败）；此处“没有日志输出”并不是一个可用的判断信号，因为上面的启动命令行已将其重定向到 `/dev/null`。终止该进程并改用 `--static`，而不是以相同方式重新启动。

   **Cowork / 无头环境：**如果 `webbrowser.open()` 不可用，或环境没有显示器，请使用 `--static <output_path>` 写入一个独立的 HTML 文件，而不是启动服务器。当用户点击“Submit All Reviews”时，反馈将以 `feedback.json` 文件的形式下载。下载后，将 `feedback.json` 复制到工作区目录中，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. 通过 **AskUserQuestion****告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

“Outputs”选项卡一次显示一个测试用例：
- **提示词**：给出的任务
- **输出**：Skill 生成的文件，在可能的情况下以内联方式渲染
- **上一次输出**（第 2 次及后续迭代）：折叠区域，显示上一次迭代的输出
- **正式评分**（如果运行了评分）：折叠区域，显示断言通过/失败情况
- **反馈**：一个文本框，会在用户输入时自动保存
- **上一次反馈**（第 2 次及后续迭代）：用户上一次的评论，显示在文本框下方

“Benchmark”选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及各项评测的明细和分析人员的观察结果。

可通过上一项/下一项按钮或方向键进行导航。完成后，用户点击“Submit All Reviews”，这会将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。重点针对用户提出了具体不满的测试用例进行改进。

使用完查看器服务器后，将其终止：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。根据证据计划进行改进：对于第 1 层级，使用权威事实和确定性检查；对于第 2 层级，使用 1–2 个具名行为重放；或者，当独立的重型评估门控授权时，在任何层级使用经用户审查的成对结果。未经该授权，不要将成对评估产物引入默认的第 1/2 层级路径。

### 如何思考改进

1. **从反馈中归纳出通用规律。** 这里发生的宏观情况是，我们正在尝试创建可以在许多不同提示词中使用上百万次（可能真的是，也可能更多，谁知道呢）的技能。在这里，你和用户之所以只围绕少数几个示例反复迭代，是因为这样有助于加快推进速度。用户对这些示例了如指掌，可以快速评估新的输出。但如果你和用户共同开发的技能只适用于这些示例，那它就毫无用处。与其加入繁琐、过拟合的改动，或过度限制性的 MUST，不如在遇到某个顽固问题时尝试拓展思路，使用不同的比喻，或者推荐不同的工作模式。尝试的成本相对较低，而且你或许会找到非常出色的方法。

2. **在不删除契约的前提下保持提示词精简。** 删除那些没有发挥应有作用的内容，但在新旧版本审计完成分类之前，应将对现有技能的每一处删除都视为潜在的回归。将详细但可复用的行为移至直接链接的参考资料中；不要让它只存在于评估、变更日志或你的记忆里。阅读完整记录，而不只是最终输出——如果技能导致了无效劳动，应简化指令并重新运行旧的能力用例，而不是想当然地认为字数越少，行为就越好。

3. **解释原因。** 尽力解释你要求模型做每件事背后的**原因**。如今的 LLM *很聪明*。它们具备良好的心智理论，在获得良好框架的情况下，可以超越机械执行指令，真正把事情做好。即使用户的反馈简短或带有挫败感，也要尝试真正理解任务，理解用户为什么这样写、实际写了什么，然后将这种理解传达进指令中。如果你发现自己正在使用全大写的 ALWAYS 或 NEVER，或者采用极其僵化的结构，这就是一个警示信号——如果可能，请重新表述并解释理由，让模型理解你所要求的事情为什么重要。这是一种更人性化、更强大且更有效的方法。

4. **寻找重复工作——既要查看评估记录，也要查看提炼出该技能的所有对话。** 阅读测试运行的记录，注意各个子智能体是否都独立编写了类似的辅助脚本，或采用了相同的多步骤方法来完成某件事。如果 3 个测试用例中的子智能体最终都编写了 `create_docx.py` 或 `build_chart.py`，这就是一个强烈的信号，表明该技能应该捆绑这个脚本。只编写一次，将其放入 `scripts/`，并告诉技能使用它。这样可以避免未来每次调用都重复造轮子。同样的信号也隐藏在你用于提炼技能的源对话中——即使某段代码在该会话中只编写过一次，它也是未来每次运行都必须重写的代码；不要等到评估运行来证明这种重复（跳过评估循环的技能永远无法获得这种证明——创建流程第 4 步中的脚本检查正是为这些情况设置的把关点）。

5. **逐字回写修正——在同一会话中，同时覆盖两个层级。** 对于需要校准品味的 Skill，用户的修正就是评估集，但前提是这些修正被写入未来运行能够读取的位置。两个特性可以让回写逐步收敛：(a) **逐字记录修正内容**，不要改述——原话包含会被摘要抹平的校准信号（“绝对禁止这种东西”表达的是一条硬性边界；“用户偏好更少的跳转”则不能）。将原话引用在其所修正的规则中，并附上日期。(b) **在修正发生的同一会话中，将其回写到两个层级**——既修复产物，也修复 Skill 的规则/参考资料/组件；如果修正只作用于产物，那么对未来的每次运行而言都是不可见的，而推迟到“以后”再做的修正通常永远不会落地。回写时，检查 Skill 自身的文本是否曾经*教导*了刚刚被禁止的反模式——一次修正常常会证伪某条现有指令，而保留旧建议必然导致问题再次发生（真实案例：某个决策页面的约定建议使用跳转式的“转到所引用图表的锚点”；用户明确禁止了这种做法，因此回写必须修改原有句子，而不能只在旁边添加一条新规则）。当被修正的内容是交互片段时，回写的最后一步是将其提升到组件架——参见第 4 步中的组件架检查。

这项任务非常重要（我们正努力在这里创造每年数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请花足够的时间认真斟酌。我建议先写一份修订草稿，然后重新审视并加以改进。请真正尽最大努力站在用户的角度，理解他们想要什么、需要什么。

对于第 1 级，直接应用有明确证据支持、无歧义的修正；只有当证据确实留下需要选择的空间时才提问。对于第 2 级或第 3 级，当用户反馈暴露出有实质意义的设计分岔时，通过 **AskUserQuestion** 提交改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险等级，因为它们会改变实现范围；选择 D 则不会。每个选项仅授权其中明确指定的范围/证据变更。除非明确列出，并且通过了单独的重型评估/扇出门禁，否则它并不授权配对基线、评分器、基准测试、查看器或其他角色。

### 迭代循环

改进技能后：

1. 将你的改进应用到技能中
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **第 1 层默认方案：** 始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行与之匹配的子类型证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归。除非单独授权了配对计划，否则不要创建迭代工作区。
   - **第 2 层默认方案：** 仅重新运行相同的 1–2 个具名的使用技能示例和窄范围检查。除非单独授权了配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任何层级单独授权的通用配对运行：** 将所有获批的测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新技能，基线始终是 `without_skill`；对于现有技能，不可变的原始编辑前版本在每次迭代中都继续作为保留性基线。紧邻的上一次迭代可以作为补充，但绝不能取代原始基线。
3. 在对规则、契约或数值进行实质性更改后，执行纪律 #5。对于单独授权的通用配对运行，还应启动评估审查器，并通过 `--previous-workspace` 指向上一次迭代；专门工作流使用其声明的审查器机制。
4. 对于单独授权的通用配对运行，等待用户审查新的查看器结果；否则，根据默认层级证据作出决定，除非确实仍有需要用户选择的事项。
5. 阅读新的证据或反馈；如果它们证伪了当前版本，则再次改进，并在同一层级重复此过程。

用户请求的取消或降级在任务剩余过程中持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（一切看起来都很好）
- 你无法取得有意义的进展

## 高级：盲测比较

在需要更严格地比较技能的两个版本时（例如，用户询问“新版本真的更好吗？”），可以使用盲测比较系统。详情请阅读 `agents/comparator.md` 和 `agents/analyzer.md`。其基本思路是：将两个输出交给一个独立智能体，但不告诉它两者分别来自哪个版本，让它评判质量。然后分析胜出者获胜的原因。

这是可选步骤，需要 subagents，而且大多数用户都不需要。通常，人工审核循环就足够了。

## 描述优化

SKILL.md 前置元数据中的 description 字段是决定 Claude 是否调用某项 skill 的主要机制。创建或改进 skill 后，应主动提出优化 description，以提高触发准确性。

### 第 1 步：生成触发评估查询

创建 20 条评估查询——混合包含应触发和不应触发的查询。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须真实可信，并且是 Claude Code 或 Claude.ai 用户实际会输入的内容。不要使用抽象请求，而应使用具体、明确且包含较丰富细节的请求。例如，文件路径、有关用户工作或所处情境的个人背景、列名和值、公司名称、URL。可以带有一点背景故事。有些查询可以全部使用小写字母，或包含缩写、拼写错误或口语化表达。使用不同长度的查询，并侧重于边缘情况，而不是让它们显得泾渭分明（用户将有机会审核并确认这些查询）。

差例：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好例：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**查询（8–10 条），要考虑覆盖范围。你需要用不同方式表达相同意图——有些正式，有些随意。包括用户没有明确说出 skill 或文件类型，但显然需要该 skill 的情况。加入一些不常见的用例，以及该 skill 与其他 skill 存在竞争但应当胜出的情况。

对于**不应触发**查询（8–10 条），最有价值的是那些差一点就会命中的情况——这些查询与该 skill 共享关键词或概念，但实际上需要的是其他功能。考虑相邻领域、朴素关键词匹配会触发但实际不应触发的模糊表达，以及查询虽然涉及该 skill 能够完成的某些内容，但在相应上下文中使用其他工具更合适的情况。

需要避免的关键问题：不要让不应触发的查询明显无关。对于 PDF skill 而言，将“编写一个斐波那契函数”作为负面测试太简单了——它什么也测试不出来。负面情况应当真正具有迷惑性。

### 第 2 步：与用户审核

使用 HTML 模板向用户展示评估集以供审核：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目的 JSON 数组（不要在其外部添加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 当前的 description
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中最新的版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 步骤 3：运行优化循环

告诉用户：“这将需要一些时间——我会在后台运行优化循环，并定期检查进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示词中的模型 ID（即支持当前会话的模型），以便触发测试与用户实际体验保持一致。

运行期间，定期查看输出末尾，向用户更新当前进行到哪次迭代以及分数情况。

此命令会自动处理完整的优化循环。它将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，显示每次迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试分数而非训练分数选出，以避免过拟合。

**如果循环检测到完全无响应，则会在第 1 次迭代后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中的代码级防护措施，而不只是一条建议；它会区分“第 1 次迭代中所有应触发查询的触发次数均为零”的两种原因：

- `exit_reason: "infra_error: ..."`——某些查询执行（无论应触发还是不应触发）抛出了异常（claude CLI 不在 PATH 中、超时时间过短、网络中断），而不是正常返回“未触发”。该项会被*优先*检查，并且只要错误计数非零就会特意触发，即使几十次运行中仅有一次偶发失败也不例外——崩溃无论多么罕见，都是比“什么都没有触发”更具体、更具可操作性的线索，而且修复目标是环境，而不是重写描述。消息中的比率（例如 `3/15`）可用于判断严重程度：较高的比例意味着“停止运行并修复环境”；较低的比例若同时伴随大量正常的 0 次触发运行，则意味着环境可能存在值得检查的轻微偶发问题，*同时*描述也可能确实很糟糕——两者都要检查。无论哪种情况，都应检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."`——仅在上述分支排除所有执行错误后才会检查，因此这意味着所有应触发和不应触发查询都*确实运行过*，但*仍然*一次也没有触发（这正是通过零分母默认值得到 `precision=100%` 的真正含义：不是“完美”，而是“没有可供计算的内容”）。该探针实际上没有测量到任何东西——在对描述进行任何修改之前，应先诊断竞争项冲突或低阈值领域问题（见下文）。

这两项检查都**仅针对第 1 次迭代运行**，并且**仅在没有任何应触发查询发生触发时运行**——第 1 次迭代表现较弱但并非零触发（例如 9 个查询中有 1 个触发）属于另一种可能可以恢复的情况，因此会特意让它继续迭代。`degenerate_harness` 还要求不应触发查询的触发次数也为零：如果描述只是极性反转——遗漏所有正例，却意外匹配了多个负例——那么探针已被证明可以正常工作，并且 `improve_description` 有真实的梯度可供利用，因此防护措施不会中止这种情况（它只会中止探针确实失效的情况）。此外，它还要求任意一侧的执行错误数均为零——如果某个不应触发查询抛出异常，那么它实际上从未运行，因此其“0 次触发”不能作为探针失效的证据；这正是该情况会转而进入 `infra_error` 的原因。无论哪种情况，循环都会立即停止并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因则用于表明不应将本次特定运行的数值解读为“这是一个好的描述”。（真实案例，2026-08：在未进行预检查的情况下启动了完整的 5 次迭代循环；在有人查看数值之前，已完成了两次完整迭代——每次都包含一整批评估，耗费数分钟实际时间并调用数十次 `claude -p` 子进程——而两次结果均为 precision=100%/recall=0%/分数完全相同，并且所有应触发和不应触发查询无一例外都未触发。仅凭第 1 次迭代即可诊断该故障；第 2 次及后续迭代没有增加任何信息。）触发任一退出原因时，HTML 报告也会显示横幅，因此浏览器视图会与 JSON/stderr 传递相同的信号，而不只依赖这两个可见性较低的渠道。（此防护措施的早期草案仅检查应触发查询的触发情况；经过两轮独立审查——每轮都由一个全新的智能体执行，第二轮检查第一轮的修复，而不是重新覆盖旧有内容——构造出了极性反转反例、基础设施与描述之间的歧义、负例侧错误缺口，以及审查过程中暴露出的一个预先存在的 `--holdout 0` 报告崩溃问题，所有这些问题均在发布前得到修复。）

这个保护机制无法覆盖一种情况：使用 `--runs-per-query 1`（默认值为 3）时，某个确实约有 50% 触发率的应触发查询，完全可能仅因随机性而得到 0/1 的结果，从而由于噪声而非探针失效触发保护机制。默认的 `runs_per_query=3` 使得“每个正向查询的每次重复运行结果都为零”成为一个强烈信号——如果你将其调低，此保护机制的误报风险也会随之上升。

**在信任 `best_description` 之前，先对测试框架进行健全性检查——即使上述两个保护机制都未触发，它仍可能返回空洞的输出。** 这两项检查只能捕获第 1 次迭代时的*完全*失败；测试框架也可能在全部 5 次迭代中一直维持微弱但非零的信号，勉强运行而始终不触发任何一项保护机制。如果第 1 次迭代之后的每次迭代都显示**召回率持续接近 0%，且分数完全相同或几乎相同**，那么这就是保护机制无法排除的同一个根本问题——所谓“胜出”的描述通常只是第 1 次迭代结果附近的噪声，基本没有变化。在应用任何 `best_description` 之前，请自行运行一个显然应当触发的查询，并确认召回率 > 0。如果各次迭代的召回率始终持平，则说明测试框架是一个隐藏变量（常见原因是：该 skill 在触发竞争中输给了已安装的竞品——参见下文的“共存”）——不要应用它的“最佳”结果；应改为手工编写描述，并使用真实探针进行验证。（方法论案例 12、14）召回率为 0 还有第二种根本原因，它与输给竞品不同：该 skill 的任务领域属于*低阈值*类型——模型会自行完成任务，根本不会查阅任何 skill——具体说明见下文*skill 触发机制*末尾。在采取措施前应区分这两种情况，因为解决方式正好相反：竞品问题应通过优先级/取代机制解决，而低阈值领域则应彻底放弃触发探针，改用生产即评估。

**当你使用 `claude -p` 自行探测触发情况时，应收集该次运行中的所有 skill 调用，而不只是第一次调用——并且要记住，工具调用只是一种代理指标。** `UserPromptSubmit`/`SessionStart` hook 可能会在模型做出选择*之前*注入一个无关的 skill，因此，“遇到第一次 Skill 调用便退出”的探针会错误地报告“未触发”。此外，“它是否调用了 Skill 工具”并不等同于“该 skill 的内容是否影响了输出”（模型可能在没有可见 Skill 调用的情况下读取该 skill），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你不断针对错误结论进行优化。

### skill 触发机制

理解触发机制有助于设计更好的评估查询。Skills 会以名称和描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 会根据描述决定是否查阅某个 skill。需要重点了解的是，Claude 只会针对自身无法轻松处理的任务查阅 skills——像“读取这个 PDF”这样简单的单步骤查询，即使与描述完全匹配，也可能不会触发 skill，因为 Claude 可以直接使用基础工具处理它们。当描述匹配时，复杂、多步骤或专业化的查询能够可靠地触发 skills——但存在一个系统性的例外（低阈值任务领域），本节末尾将对此进行详细说明。

这意味着你的评估查询应该足够实质，以便 Claude 确实能从查阅技能中获益。像“读取文件 X”这样的简单查询并不是好的测试用例——无论描述质量如何，它们都不会触发技能。

**但有些技能无法通过这项测试，是因为存在一种无论如何改写查询都无法解决的原因——该技能的全部*职责*就是执行一项低门槛任务。** 上一段将问题归因于查询（“写一个更实质的查询”）；而这里讨论的是与之正交的情况，即阻碍触发的是技能的*领域*。如果某项技能的用途是执行 Claude 仅凭基础工具就会自行完成的事情——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询内容完整明确（“将这个 48k 立体声 wav 降采样为适用于 whisper 的 16k 单声道”，并附带路径），也不会触发该技能：模型会直接使用 `Bash`/`ffmpeg`，根本不会查阅任何技能。增加查询的实质性无法解决这个问题，因为“我可以直接做这件事”的判断针对的是*任务*，而不是措辞。

在浪费一轮优化之前先进行诊断：通过 `claude -p` 运行一个真实查询，并观察模型在整个运行过程中是否*曾经*查阅该技能（按照上文的“所有技能调用”规则），还是直接使用 `Bash` 自行完成任务。如果它从未查阅，那么触发探针在结构上就无法检测这项技能——无论你如何编写描述，召回率读数都会约等于 0，而这个零衡量的是模型“自己动手”的本能反应，而不是你的描述。不要再针对 `claude -p` 的召回率进行调优，而应通过真正的方式进行验证：将生产使用作为评估（即用户下一次真实的*交互式*使用——无头模式的 `-p` 比真实会话更偏向直接行动，因此会系统性地低估触发情况），再加上输出对比，前提是该技能能生成可检查的产物。（在一项音频预处理技能上观察到：无头模式的 run_eval 扫描在*每个*查询上的召回率读数都是 0——其中甚至包括一个显而易见的“转录这段录音”查询——而手动执行 `claude -p` 探测后发现，模型直接使用 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个零衡量的是无头模式的行动偏差，而不是描述质量；真正的信号只会在交互式使用中显现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新技能的 SKILL.md frontmatter。向用户展示修改前后的内容并报告分数。

## 关键要求：在源位置编辑技能

**绝不要先编辑已安装的技能副本。** 除非用户明确表示它们是源位置，否则应将以下所有位置视为已安装副本或运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装副本会导致修改：
- 在缓存刷新时丢失
- 无法同步到源代码管理系统
- 浪费精力，并需要手动重新合并

**务必确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，先运行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果 available-skills 列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。先找到由仓库支持的源，对其进行编辑和验证；只有当用户需要立即在本地运行时，才同步已安装的副本。

**然后回答一个后续问题，以确定“同步已安装的副本”是否真的有工作要做：运行时是否已经直接读取源？** 三种安装方式的行为不同，猜错要么会导致无意义的同步，要么会交付一项用户下次会话根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **以符号链接形式**链接到源代码树中 → 该编辑*已经就是*运行时使用的内容。无需同步。
- **使用 `source: directory` 的 Marketplace** 指向仓库 → 情况相同：它直接读取工作树，因此版本递增只是面向其他使用者的记录工作，而不是本地激活步骤。
- **任何缓存或复制的安装**（由 git 提供源的 Marketplace、通过 `cp -r` 安装）→ 运行时使用的是单独的副本，新内容必须通过官方更新命令才能真正生效。

**此外，要根据内容而不是版本字符串来验证激活状态。** 注册表可能记录一个磁盘上并不存在的路径或版本——某次会话读取到一条插件记录，其中指定了一个名称包含*新*版本号的缓存目录，于是险些报告更新已经生效；但该目录从未创建过，真正的运行时路径一直都是指向源的符号链接。权威的检查方式是，在运行时文件中搜索仅新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库中的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是这些会话容易发生冲突的地方：当你编辑技能 A 时，另一个并行会话可能会在你操作期间提交技能 B（甚至是技能 A 先前轮次的内容）。某个真实会话在一小时内遇到了全部三种症状——一次 `Write` 因文件在读取后发生变化而被拒绝，并且 HEAD 在任务进行期间移动了两次（方法论案例 16）。问题并不在于发生冲突，而在于使用了过时的基线，或执行了覆盖式写入，悄无声息地混合了两个会话的工作。长期适用的规则如下：

1. 只要任务开始时仓库是干净的，**就从 git 引用建立基线，而不是从工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传递 `--baseline-origin git-ref:<sha>`。在他人提交前几分钟创建的树快照，是一个针对已不存在之树的基线。**将其解压到一个全新的、不存在的目录中。** 如果解压到已有目录，`tar -x` 会静默覆盖同名文件，同时保留归档中不存在的文件——从而形成一个在解压时毫无提示的混合快照，随后 `compare` 会因其与引用不匹配而拒绝该快照。同一个陷阱也存在于另一条命令中：`mv <dir> <existing-dir>` 会执行嵌套而不是替换——而在 `mv` 被设置为 `mv -i` 别名的环境中，目标已存在的重命名操作会打印一行提示，并默认*不*执行，但无论是否执行，退出码都是 0（已通过实验验证）。
2. 当写入被拒绝，或已经过去一段时间时，**在写入前重新读取**：对发生的变化进行差异检查（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图纳入你的版本——对方的编辑通常有其原因——然后再执行写入。
3. **提交前同时检查 HEAD 和当前所在的分支。** `git log --oneline -1` 可以发现 SHA 移动：如果它自你的基线建立以来发生了移动，应先针对新的引用重新运行回归 `compare`，然后再运行 `verify`——审计工具无论如何都会拒绝过时的审查（“技能发生更改之后”），因此自行提前发现可以省去一个来回。但并行会话可能做出比推进 HEAD 更糟糕的事情：**它可能在你不知情的情况下切换分支**，因为检出操作对整个工作树生效。真实发生过的顺序是——先执行 `checkout -b feat/x`，编辑一段时间，与此同时另一个会话执行了 `checkout main` + `pull`；随后提交落在了 **main** 上，违反了仓库“永远不要直接提交到本地 main”的规则，而功能分支仍然指向旧的基准。因此，在提交前检查时加入 `git branch --show-current`，而不要只检查 SHA。如果问题已经发生，`git reflog` 是重建过程的权威依据（它会按顺序记录每次 `checkout: moving from X to Y`），修复方法——**前提是工作树干净**——是先执行 `git checkout -B <feature> <your-sha>`，再执行 `git branch -f main origin/main`：两者都只是移动引用，完全不会触及工作树，因此都不会像 `reset --hard` 那样破坏并行会话尚未提交的工作。
4. **仅暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——不得将并行会话尚未提交的工作一并带入。（这本就是打包规则；在并发场景下更是至关重要。）
5. **每个会话结果只递增一次版本，而不是每轮编辑都递增**：同一会话中针对一个技能连续进行的多轮编辑应合并为一次版本递增——除非某个中间状态已经被使用（用户或另一个会话已提交并拉取），此时每个已被使用的状态都应拥有自己的版本。

## Skill 创建流程（分步说明）

创建或更新 Skill 时，请按顺序执行以下步骤。仅在明确不适用时跳过相应步骤。

### 第 0 步：检查前置条件

开始任何 Skill 工作之前，自动检测所有依赖项，并主动安装任何缺失的依赖。在工作流进行到一半时才发现缺少工具（例如，在打包时发现缺少 gitleaks，或在验证时发现缺少 PyYAML）会浪费时间并中断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，自动安装能够安装的依赖，并向用户提供一份汇总检查清单。只有在满足所有阻塞性依赖后才能继续。

关键阻塞项包括：Python 3、uv、PyYAML（验证/打包）和 gitleaks（安全扫描）。只有在单独授权的证据计划实际运行智能体评估时，claude CLI 才是阻塞项。运行 Python 工具时，应显式使用 uv 声明依赖，例如，从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 会依赖环境中的 site packages，因此可能找不到 PyYAML。

### 第 1 步：通过具体示例理解 Skill

仅当已经清楚理解该 Skill 的使用模式时，才能跳过此步骤。

要创建一个有效的 Skill，需要清楚理解该 Skill 将如何使用的具体示例。这种理解既可以来自用户直接提供的示例，也可以来自生成后经用户反馈验证的示例。

例如，在构建图像编辑器 Skill 时，相关问题包括：

- “图像编辑器 Skill 应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能否提供一些该 Skill 的使用示例？”
- “用户说什么内容时应该触发该 Skill？”

为避免让用户感到不知所措，请勿在一条消息中提出过多问题。

### 第 2 步：规划可复用的 Skill 内容

通过以下方式分析每个示例：

1. 考虑如何从头开始执行该示例
2. 确定 Claude 应具备的适当自由度
3. 确定在重复执行这些工作流时，哪些脚本、参考资料和资源会有所帮助

**使具体程度与任务风险相匹配：**
- **高自由度（文本说明）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，但允许适当变化
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 第 3 步：初始化 Skill

如果该 Skill 已存在，请跳过此步骤。

从头创建新 Skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个 Skill 模板目录，其中包含正确的 frontmatter、资源目录和示例文件。

### 第 4 步：编辑 Skill

开始编写之前，请获取 Anthropic 的最佳实践文档（链接位于上方的“Skill 创建最佳实践”中）和方法论参考资料——即使你认为自己已经了解这些内容，也要这样做：文档会持续更新，训练数据中的版本会过时，而“我基本知道”的状态恰恰最容易让编辑者跳过这一步，从而错过最新指导。

编辑时，请记住，此 Skill 是为另一个 Claude 实例创建并供其使用的。请重点关注对 Claude 有益且并非显而易见的信息。

**现有 Skill 迁移门禁——首次编辑前必须执行：**

1. 编辑前捕获完整的当前资源包。对于非 Git 来源或存在未提交更改的
   来源，请使用该工具，以便快照携带可验证的来源清单：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于由 Git 跟踪且工作区干净的来源，请从选定的引用中实体化该目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   应包含 SKILL.md、参考资料、脚本、资产、工作流以及现有的评估，而不只是
   主提示词。绝不要复制已编辑过的目录树并将其标记为“编辑前”版本。
   **请使用一个此前从未有任何内容解压到其中的目录**——复用已包含之前运行内容的目录，
   会让 `tar -x` 在不发出提示的情况下覆盖同名文件，同时保留新归档中不存在的陈旧文件，
   从而生成一个在解压时毫无异常信号的混合快照（`compare` 只能在之后通过
   目录树哈希不匹配间接发现它）。有关此陷阱的更完整说明，包括基于 `mv` 的变体，
   请参阅下文的“在同一个 Skill 仓库中进行并发会话”。
2. 清点旧 Skill 的参与者/任务、触发上下文、运行时契约、
   命令/标志、失败与恢复场景、页面/域名变体、捆绑资源
   以及评估覆盖范围。在进行结构性重写之前，为重要的旧有边缘行为添加保留用例。
3. 编辑完成后，生成一份新旧版本对比审查：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，请将最后一个标志替换为
   `--baseline-origin git-ref:<ref>`。该工具会将引用解析为不可变的
   提交，并根据该目录树验证所有包含的文件及其可执行位。

   **重命名或移动 Skill 目录本身**（而不只是编辑其
   内容）会改变 `--after` 的路径，而两种基线模式都会使用该路径确定
   身份——`compare` 默认会拒绝这种情况（假定 `--before`/
   `--after` 是意外匹配错误），并报出 `pre-edit snapshot source
   identity does not match the edited skill`。添加 `--renamed-from <old-path>`
   （即执行 `snapshot` 时 `--source` 所指向的路径，或在 `git-ref:` 模式下
   Skill 相对于其仓库根目录的旧路径），以显式声明重命名；
   随后，身份检查将验证该路径而不是 `--after`，而内容/目录树哈希检查保持不变，
   因此实际不匹配的配对仍会失败。**请将 `--renamed-from` 作为绝对路径传入。**
   此命令接收的每个路径在以相对路径给出时，都会相对于当前工作目录进行解析——
   而不是相对于 `--after`，路径之间也不会互为参照——
   且 `--renamed-from` 通常指向一个已不存在的目录（它已被重命名移走），
   因此无法像 `--before`/`--after` 那样通过存在性检查捕获错误的
   路径解析；它只会在更深层的位置以令人困惑的方式失败。这尤其容易影响
   对 skill-creator 自身的编辑：上面的 `cd
   <skill-creator-path>` 进入的是 skill-creator 自己的仓库，而该仓库通常与
   正在审计的 Skill 所在仓库*不同*，因此相对路径形式的
   `--renamed-from` 会悄无声息地基于错误的仓库进行解析。

4. 审查每个候选项。仅使用一种处置方式，并记录具体的证据/理由：`preserved_or_moved`、`intentional_sanitization`、
   `intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable`
   或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将某项运行时能力移出此 Skill 时，必须注明其归属目标、当前边界证据以及可追溯的用户批准。明确停用也必须引用/追溯用户的批准。关于已保留/已净化/已修复的声明必须指向真实的当前文件和行，并包含一段简短的 `contains` 引文，供验证器在附近定位。文件级候选项使用当前文件指纹，并附上具名的语义审查来说明为何行为得以保留——仅凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本——`classify` 子命令会完成机械性工作（在目标文件中定位引文所在行、填充证据/语义审查，并在引文缺失或理由过短时快速失败）。你仍需自行撰写每项处置方式和理由；它只负责将其录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置方式默认为
   `preserved_or_moved`；文件级候选项只需提供目标文件和不少于 40 个字符的理由——系统会替你计算指纹）。**务必从目标文件中复制 needle（Read/grep/sed），绝不要凭记忆输入**——查找采用精确匹配，缺失引文时会快速失败；手动输入的 needle 实际会因两种情况而失败：全角与半角标点不一致（`：` 与 `:`），以及根据记忆改述时使用了近义字符（`也` 与 `都`）——这两种问题都会逃过自查，只有当工具拒绝你的整个映射时才会被发现（有一个映射恰恰因为这两个原因连续两次被拒绝）。
5. 验证已完成的审查。任何后续编辑都会使哈希失效，因此候选项发生变化时，请重新生成并重新分类。验证通过后会写入 `.skill-regression-reviewed`，这是一个与内容绑定的本地状态凭据。它有助于检测后续编辑，但被刻意设计为不能单独充当打包授权；打包时会重新验证已完成的审查本身：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可识别无提示失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在需要审查的候选项，而不是工具执行失败；
返回 2 表示调用/运行时失败。该工具可以证明内容被准确迁移且接口得以保留，但会有意拒绝根据模糊的词语重叠推断语义等价性。诸如“检查权限被拒绝”这样的宽泛表述，不能悄无声息地取代“已登录但没有角色”这一精确约定。还要检查标记为 `only_outside_runtime` 的候选项：如果运行时行为仅存在于评估、测试或无法访问的参考资料中，那么正常调用路径中就不存在该行为。

**每次编辑 SKILL.md 后都要立即验证——不要等到打包时（第 7 步）。** 这能提前发现的故障确实存在：以前言描述形式编写且未加引号的 YAML 标量，在 Claude Code 宽松的解析器中可以正常解析，但在严格解析器中会出错（codex 曾在一个已经发布数月的技能上报告 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中如果包含 ` #`，甚至不会报错——它会悄无声息地截断其后的所有内容，导致触发关键词消失，而所有扫描仍然显示正常。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

当描述包含 `: ` 或 ` #`，或者由多个句子组成时，**应将描述写成 YAML 块标量**（`description: >-` 后跟一个缩进段落）——块标量原生支持这两个字符——自上述事件发生后，这已成为每个新增或编辑描述的推荐约定。

**更新现有技能时**：扫描所有现有参考资料和捆绑资源，确认是否需要进行相应更新，然后通过上述迁移门禁。迁移约定时，SKILL.md 中必须提供直接的运行时指向；评估或变更日志不能替代它。

接下来的三项检查是**升级探查，而不是无条件扩大范围**。如果执行其中任何一项会新增或实质性改变某项能力、工作流分支、输出约定、脚本行为、依赖项、权限或外部写入操作，请在修改技能之前停下来，并将其重新归类为第 3 级。第 1 级和第 2 级可以审视这些问题，但不会因此获得新的交付事项。

**脚本检查**：在认定编辑完成之前，请思考：*源对话（或评估记录）编写了哪些代码——如果不这样做，未来每次调用都会重新编写这些代码？* 当所选级别已经授权进行相应的能力工作时，将其捆绑到 `scripts/` 中（参数化并经过净化处理），并修改文档使其指向该脚本。否则，将该信号记录为第 3 级提案，不要将其作为第 1/2 级工作的附带影响而捆绑进去。职责分工是：**脚本负责执行，文档负责传达理解**——如果一个技能的方法只存在于说明文字中，那么每次运行都要重新付出完整的编写成本。这项检查之所以出现在这里，即编辑步骤中，正是因为跳过评估循环的路径（对话提炼、直接编辑）永远不会执行“改进技能”中针对评估记录的这项检查。

**组件架检查（针对嵌入制品的片段提出的同一问题）**：Scripts 检查涵盖的是由 *skill* 执行的代码；生成制品的 skill（报告页面、幻灯片、文档）也会积累嵌入其 *输出* 的片段——图像叠加组件、吸顶导航、图表配置、CSS 块。如果连续产出的输出都手写了相似的片段，这就是指向另一个架子的同类重复信号。在添加 `components` 子文件夹或注册表引用之前，先应用上面的升级规则；Tier 1/2 可以提出该建议，但不得创建组件能力。获得 Tier 3 授权后，真正让代码片段成为架上组件的是围绕它建立的契约：(a) **逐字嵌入块**——带有 BEGIN/END 标记，整体复制到制品中，零依赖，从而使单文件制品保持自包含；(b) **注册表条目**，说明交互契约（触发方式、按键绑定、关闭行为、边界情况）和来源——它来自哪个已交付制品、用户何时批准；(c) **准入门槛**——只有用户实际使用并批准过的片段才能进入（将已批准语料库纪律应用于交互；未经批准但看起来很漂亮的内容仍不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定属于契约，不得在不同运行之间发生漂移，而颜色和尺寸可以遵循制品的风格；(e) **回写循环**——为某个制品发明的片段，应在其获得批准的同一会话中晋升到组件架。其重要性不只体现在节省 token：手工重写的片段会发生 *漂移*——每次重写都会细微改变按键绑定、关闭行为、计数器——而对于每天阅读这些制品的用户来说，交互一致性就是产品体验。用用户为第一个此类组件架定下的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：某个报告页面 skill 的灯箱画廊组件（图像叠加层：←/→ 在组内循环切换，ESC 关闭，原位缩放，n/N 计数器），以及其交互组件注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击遍历测试进行了验证。参见方法论案例 17。

**流水线检查**：考虑该 skill 的输出是否会自然流入另一个 skill，以及某个现有 skill 是否应该串联 *进入* 此 skill。添加或实质性更改 "Next Step" 交接或流水线契约，必须在编辑前重新分类为 Tier 3；Tier 1/2 可以提出该建议，但不得顺手添加。

**引用与自我应用检查（即使细致的作者也难以避免的缺陷）**：这一系列故障模式从内部看都像是已经完成的工作，而且没有一种能通过更认真地重读来发现——每一种都需要采取 *机械式* 操作。（开头故意没有写数量。"Three failure modes:" 是一个派生数字，只要有人追加一个项目符号，它就会过时；而计数类正文恰恰最难发现漂移，因为它 *并不包含发生变化的内容*——针对列表本身的重新编号 grep 和 diff 都会直接漏过它。）之所以将它们归为一组，是因为它们有同一个成因：**写下断言与验证断言是两种不同的模式，单次处理无法同时容纳二者。** 当你正在撰写时，"see rule 8" *就是* 那个断言；你并不会同时打开规则 8。

与上面的三个升级探针不同，这一个**不**按层级限定范围——它的范围由你写下的内容决定。一个既未添加指针、也未添加规范性规则的 Tier 1 修复，在这里没有任何事情要做，而且你不必自行判断：推论中的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 给出答案。无论在哪个层级，只要写了指针或规则？那么以下各项就适用。

- **你每写一个指针，都要打开其目标，并在写下该指针之前，从目标中复制一行出来。** 不能只是“我确信那条规则列出了全部三个标记”：要粘贴其中一个片段——放进你在此步骤中原本就在产出的任何内容里（审查备注、提交消息正文、你的回复），放在以后第二位读者能够拿它与目标核对的位置。一个你只是看过、却没有贴出来的片段，正是本句开头所否定的那种自我评估。错误的交叉引用在重读时是不可见的，因为错误的指针看起来与正确的指针一模一样，而作者恰恰是唯一必然会“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal rule 3”，本意是指一条关于不要引用陈旧枚举的规则——但被引用文档**自身**的规则 3 讲的是样本量，而实际引用的那条规则位于另一个文件中；按照该文档既有的自引用惯例查找的读者，会落到一个无关主题上。同一轮编辑还交付了一个方向颠倒的指针（材料明明在上方，却写成“见下文”），以及一个指向不存在的章节标题的指针。
- **一旦文件中有两个编号列表，单独写“规则 N”就会产生歧义。** 检查应针对每个指针，而不是每个文件：在写“规则 N”之前，运行 `grep -n '^N\. ' <file>`，并确认你所指的章节中恰好只有一个匹配项；如果有多个，就同时写明章节名称。（**不要**把它变成“这个文件是否包含多个从 1 开始的列表”之类的文件级警报——任何长文档几乎总是如此，因此它会在正常输入上触发，继而被忽略，而纪律 #6 警告说，这比没有检查更糟；在这个文件上运行一下，亲自看看。）在真实案例中，一个单独出现的“规则 1”对应着三个候选列表，而自上而下搜索时首先命中了错误的那个。
- **写下任何规范性规则后，都要拿它与旁边的行核对——并让检查产出一份制品，而不是一个结论。** 使用 `git diff <base-ref> -- <file>` 阅读你自己的变更块，并采用与下面推论相同的 `<base-ref>`。这里由你亲自阅读就足够了——你并不是在进行模式匹配，因此不需要脚本——但它必须带上该引用：单独运行 `git diff` 只会显示未暂存的工作，而且一旦你运行 `git add`，它便什么都不输出；这正是本块自己的推论旨在规避的五种静默空结果模式之一。将新规则拆分成各个独立条款，并针对每个条款，记下满足它的、位于**同一变更块**中的那一行。（下面推论中的 `scripts/reference_net.sh` 执行的是另一项工作：它会列出需要你解析的**正文交叉引用**。它不会把变更块交给你，也不会告诉你规则中的某个条款是否得到满足。）**旁边没有对应行的条款，就是发现的问题。** 那个诱人的简短版本——“我的新规则通过了吗？”——对于 30 秒前刚写下它的人而言不可能失败；这恰恰就是纪律 #6 所说的，相比自我评估，应优先采用可证伪的观察，因此本条也必须产出它所要求的同一类制品。它的第一个受害者通常就是旁边的段落。真实案例：新增了一条规则，写道“始终同时报告原始计数和过滤后计数——两者之差*就是*污染量”，但同一个提交中的对应示例却只输出了过滤后的数字。同一差异中的另一处陈述引用了两个数字，却没有说明它们是否是在相邻的新规则刚刚规定为强制条件的限定条件下采集的。范围很小且有明确边界：不是“重读整篇文档”，而只是“我 30 秒前写下的规则，能否通过对我 30 秒前写下的那些行的检查”。
- **为每条新规则写一行，说明由谁执行，以及他们实际上是否有能力执行。** 如果现有工具无法满足一条规则，那么相信自己已经遵守规则的人就会跳过它——这是最糟糕的一类规则，因为它会制造有文档背书的虚假信心。真实案例：一条新规则写道“检查两个日志存储区”；而项目自身的规范单命令分诊工具硬编码了其中一个，因此标准工作流恰恰会针对这条规则原本要捕获的故障返回干净结果。这条规则是正确的，却不起作用，而且没有提及这一缺口。**让这一点可证伪的制品是**（如果没有它，本条就会成为这个禁止自我评估的块中唯一一处自我评估）：指出能够捕获违规行为的工具或命令，然后**针对一个你已经知道它应该能够捕获的案例运行一次**。如果它面对已知有问题的输入却返回干净结果，你就已经测量出这条规则不起作用——把这个缺口写进规则本身。凭记忆回答“他们实际上是否有能力执行”，正是纪律 #6 所拒绝的未经验证的断言。**当没有任何工具能够判定这条规则时**——大多数正文规则和品味规则都是如此，因此不要把这当作逃生通道——所需的制品就是明确指出这一点的句子：*“没有任何机制强制执行这一点；它只能在人们还记得它时成立。”* 这比检查通过更糟，而明确说出来正是本条的意义所在；执行机制保持沉默的规则，会被人假定为已验证，而不是得到实际验证。请注意本条自身诚实承认的局限：工具和已知问题案例的选择仍然需要判断，因此它只是转移了未经验证的步骤，而没有消除它——它比替代方案成本更低，但并非没有成本。
- **推论——你的修复本身就是缺陷来源，因此要在最后一次编辑之后，重新检查你触及的区域。** 在对单个变更进行两轮审查时，第 1 轮产生了八个发现；第 2 轮又产生了八个，**其中七个是第 1 轮修复所引入的交叉引用错误**。重写一句话会移动它周围的锚点。这也正是为什么，对于读者依靠其中指针进行导航的制品而言，“它已经审查过了”并不是终点：你一旦根据审查采取行动，审查结果就已过时。重新检查是机械化的，而且它是一个**脚本**，而不是需要重新键入的命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的 bundle 中）。它会列出你新增行中的正文交叉引用，以便你打开每个目标，并确认目标确实表达了你所声称的内容。首次使用前请阅读其头部说明——其中解释了为什么它接收 base ref，而不是默认使用 `HEAD`，以及它有意**不**做哪些事情。

**在开始编辑之前获取 `<base-ref>`，而不是之后。** 在开始时将它解析一次，得到字面量 SHA——`BASE=$(git rev-parse HEAD)`——并在此处和上面的项目符号中重复使用同一个值。如果你运行了现有 Skill 迁移关卡，它就是你已经用作基线的 ref。*稍后*传入 `HEAD` 正是陷阱所在：提交后，`HEAD` 包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容可检查无法区分。如果你没有预先捕获它，请恢复它（使用 `git log`、`git reflog`，或你提供给迁移关卡的基线），而不要用 `HEAD` 代替；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印一条提示，但不要指望到那时才发现问题。

**为什么这里要用脚本，而这一部分的其余内容都是文字说明。** 它所取代的单行命令经历了五轮修补——将 diff 锚定到正确的 base、识别已暂存的编辑、在提交后仍能正常工作、跳过 diff 自身的 `+++` 标头、移除误导性的 `-n`——而这五轮中有四轮都让它多了一种什么也不打印却以 0 退出的方式，这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种弊病的另一种表现：它移除的 `-n` 曾为真实匹配项打印行号，但这些行号是按管道流计数的，因此看起来很权威，却什么位置也指不到——这比沉默更糟，因为错误答案比没有答案更具支配力。无论哪种情况，这项检查都一直把它原本要捕获的缺陷放了过去。文字说明无法验证自己的输入，无法说明实际出现了哪种结果，也无法接受测试；脚本可以做到这三点，而且它的契约是：**每种结果都有明确名称，错误输入会高声失败**。这就是本步骤前面的 Scripts 检查在此部分的应用——而忽略它的代价就是那五轮修补。

**阅读它的判定结果，而不只是退出码。** 只要脚本运行过，它就会以 0 退出，因此单看 `$?` 无法告诉你它发现了什么；答案位于判定结果行中，而且该行始终会明确指出以下结果之一：发现引用（逐一处理）、文件与 base 相同、文件发生更改但没有新增行，或存在新增行但其中没有任何看起来像引用的内容。这些是不同的结果，脚本有意让它们保持不同——正是因为该检查曾有一个版本将它们合并成一个沉默的“什么都没有”，它才变成了脚本。它只需几秒钟，也不依赖警觉性，而纪律 #6 要求任何值得编写的检查都应做到这一点。（它是一张网，而不是证明。它的盲点是不含数字的指引——“参见下面的章节”“如上面的规则所述”——因此也要阅读新增的行。）

### 步骤 5：净化审查（任何公开 Skill 均为必做）

**在进入此关卡之前，当纪律 #5 适用时，其独立检查必须已经运行**，并且当前变更的 `independent-review.md`（位于你私有且由 git 跟踪的知识仓库中——不是已清空的工作区，也不是任何已经或可能变为公开或分发对象的仓库）必须存在，**并且已经提交**。对于新 Skill，它始终适用；对于现有 Skill，请使用下一段中的阈值。文件只是未提交地放在 git 工作目录中，与从未编写过该文件没有实质区别；`ls`/`test -f` 只能确认它在磁盘上，而不能确认它会被保留下来。对于**新** Skill，这是第一次有任何内容离开你的掌控，因此纪律是在这里得到实际执行，而不只是被陈述——如果一条规则位于使用位置上方 1000 行处，却没有任何检查机制，那么它每次都会输给完成任务的冲动。

**对于已发布技能的编辑，离开你掌控的时刻是推送，而不是此步骤。** 对这一关，只需用一句“仅限内部，跳过”即可作答；而对于仅修改文档的变更，打包甚至可能完全不会运行——因此，把审查安排在这里意味着，技能编辑可能在未经任何独立审阅的情况下进入公共分支。真实案例（2026-07）：对此文件本身的一次变更发布了一条发现命令，但它无法访问旁边正文声称涵盖的三个根目录；该变更已被合并，直到*事后*安排审查才发现问题。**因此，对于现有技能：必须在 `git push` / 创建 PR 之前完成独立审阅并生成留档产物——推送时运行的关卡（回归审计、验证、扫描）检查的都是结构，其中没有任何一项能够判断说明是否错误。** 此处原封不动地沿用原则 #5 的阈值：当*规则、契约或数字发生变化*时需要审查，而拼写错误或纯格式调整则不需要。让拼写修正也必须等待一轮审查，只会培养出 #6 所警告的那种条件反射——“这次改动很小”会变成普遍适用的豁免理由，继而把真正重要的变更也包括进去。

**对于将进入公共仓库的技能，这不是可选项。** 私有内容经常泄露到公共技能中，而扫描器漏掉的泄露才是危险的——非英语语言中的真实姓名、真实对话记录中逐字照搬的一行内容、放入示例图解中的真实案例。只有当技能确实仅限内部使用时才能跳过。

**按目标位置而非主题界定处理范围。** 只有将公开发布的产物——即技能包本身——需要进行脱敏。仍保留在私有仓库中的配套文档（提炼出该技能的事件报告、内部运行手册、项目的 CLAUDE.md）应保留其真实的主机名、路径和时间戳：对这些内容进行脱敏会破坏其审计价值，而你最终还得撤销这些修改。曾有一次提炼工作历经三轮返工，原因恰恰是脱敏处理被应用到了源材料涉及的所有内容，而不只是公共技能。

**先检查目标位置，并让它预先填入建议选项。** 在技能将要存放的仓库中运行
`gh repo view --json isPrivate`（或阅读
`quick_validate` 已经输出的提示）。如果目标位置是私有的，就应默认推荐选项 C，
而不是事后才想到它——“除非另有说明，否则假定为公开”
正是将私有技能中的工作路径变成无人要求的占位符的原因。

**触发脱敏的条件是目标位置的 `isPrivate`，而不是这项任务在多大程度上
让人感觉像是在发布。** 两者可能并不一致；一旦如此，除非你明确指出，否则感觉就会占据上风。
把内容移入*市场技能*会让人感觉像是在发布——毕竟市场就是分发内容的地方——
因此，即使源仓库和目标仓库都是私有仓库、没有任何内容会对外发布，也会触发脱敏的条件反射。
真实案例（2026-07）：在一次从项目级技能迁移到私有市场技能的过程中，
真实配置路径、真实十六进制值和真实具名示例都被泛化为
占位符。`quick_validate` 在**每次**运行时都输出了 `🔒 audience: private`；
作者每次都看到了，却依然进行了脱敏，因为这项*活动*看起来就像发布。
其代价并非只是表面问题——真实路径能让下一位读者前去核查相应值；
“项目自己的令牌文件”则根本无法打开。

因此，应将其视为一次查找，而不是一次判断：**读取目标位置的 `isPrivate`，如果其值为
`true`，则只有所有者提出要求时才进行净化。** 私有→私有的迁移只是迁移，而不是发布。
**当两种探测方式都没有结果时**（尚无远程仓库、尚未运行 `quick_validate`），你就没有可供
查找的信息——此时回退为将其视为公开，并且要明确说明，因为这种不对称性决定了处理方向：
一次不必要的询问只多花一句话，而一次不必要的泄露却无法挽回。并且，`isPrivate` 报告的是
目标位置**今天**的状态——某项技能即使正位于私有仓库中并准备发布，也应在真正将其公开的
那次推送中执行净化，而不是这一次。如果你发现自己正在判断某些内容在私有目标位置中是否
“应该”被泛化，这种判断本身就是一个信号。

使用 **AskUserQuestion** 确认净化深度（对于公开目标位置，确认的是深度，而不是是否执行；
对于私有目标位置，则确认是否确实需要执行）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**净化流程——通读才是核心方法，扫描只是辅助工具：**

1. **亲自阅读整项技能并进行语义判断**（这才是真正的检查）：SKILL.md + 每一份参考资料 + 每一个示例。对于每个具体名词／示例／代码片段，都要询问：“这是通用占位符或公开实体，还是取自真实项目／人物／对话记录？”替换后者——即使没有任何扫描器将其标记出来。这是捕获无关键词泄露的唯一方法。完整指南和语义判断问题参见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **将扫描器作为低成本的第一轮检查运行**：检查清单中的 grep 模式 + `security_scan.py`（第 6 步）。它们可以快速发现明显的密钥／路径／已知名称——但“没有匹配项”并不代表通过。
3. **替换**每项发现，同时使用能够保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。这里有两条从惨痛经验中总结出的规则：占位符本身绝不能包含真实值——`<acme-corp-domain>` 恰恰泄露了它本应隐藏的名称；应改为描述其*角色*（`<api-domain>`、`<upstream-provider>`）。此外，通过脚本进行批量替换时，应为其提供一个明确的文件白名单，并将范围限定在技能目录内——不限定范围的查找替换会轻易改写项目自己的 CLAUDE.md，迫使你使用 git restore 恢复文件。
4. **通过重新阅读进行验证，而不是再次使用 grep**：重新阅读修改过的部分，确认没有损坏的引用。

### 第 6 步：安全审查

在打包或分发技能之前，运行安全扫描器以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）
- 完整的软件包超集：常规发布文件，以及可选的根目录 `evals/`。不发布的 `.enrich/`、`tests/` 和 `dist/` 构件会依据打包器和内容哈希认证所使用的同一套共享策略被排除。

**不涵盖的内容** — 这就是为什么仍然需要执行步骤 5 的通读：gitleaks 和正则表达式规则只能匹配*已知的机密格式以及你列出的模式*。对于不含关键字的隐私内容，它们在结构上无能为力——例如使用非英语语言书写的真实人员/项目名称、真实对话记录中逐字照搬的一行内容，或者直接取自你自己工作的真实示例。`security_scan` 显示为绿色意味着“未发现已知格式的机密信息”，**而不是**“该 Skill 已经过脱敏处理”。绝不能将其视为后者。

**首次设置：** 如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 无问题（可以安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**在私有 Skill 中，扫描发现只是信息，而不是工作指令。** 扫描器无法
区分泄露的凭据与*本来就应该存在*的凭据——例如价值恰恰在于预先填充内容的模板，
或是指向其唯一运行机器的脚本。切勿在私有仓库中自动修复：报告发现的内容，并让所有者决定。下方的选项 A
（“自动修复”）适用于准备公开发布的 Skill。

**如果发现问题**，请通过 **AskUserQuestion** 向用户展示：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 步骤 7：打包 Skill

Skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个已由 Git 跟踪的现有 Skill，在提供并重新验证已完成的
审查之前，打包都会被阻止。当前标记只是一份本地状态回执，
因此先提交或手动编写标记都无法绕过审查。下一次编辑后，
审查就会失效：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可以选择指定输出目录，并使用 `--include-evals` 将根目录 `evals/` 一并发布（默认情况下，它作为开发资产被排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. 自动**验证**技能（YAML frontmatter、命名约定、路径引用完整性）
2. 每当 Git HEAD 已包含该技能时，**重新核验已完成的现有技能回归审查**；仅有标记绝不构成打包授权
3. **核验安全扫描**（内容哈希必须与上次扫描匹配）
4. 将技能**打包**成可分发的归档文件

如果验证失败，脚本会报告错误并退出，不创建软件包。

### 第 8 步：更新 Marketplace

打包后，更新 Marketplace 注册表，使其包含新增或更新后的技能。

**对于新技能**，在 `.claude-plugin/marketplace.json` 中添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于更新后的技能**，按照 semver 递增 `plugins[].version` 中的版本号。对技能文件的任何更改——哪怕只是修复一处单行拼写错误——都需要递增版本号：否则，`marketplace update` 将检测不到新版本，因此**已安装的副本永远不会刷新**，用户会继续运行旧技能，而你的修复则一直未能发布。

**然后将其记录在变更日志中——这一步最容易被跳过。** 版本号递增使更新变得*可安装*；变更日志条目则使其在六个月后仍然*可查找*，届时如果有人遇到相同问题并通过 grep 进行搜索，就能找到它。而如果一份变更日志记录了其他所有技能的版本，却悄无声息地漏掉了你的技能，那还不如根本没有变更日志：这些空白会被理解为“那里没有任何变化”。

请遵循现有条目的格式，而不是自行发明一种——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。
请在递增版本号的**同一个提交**中写入该条目；“稍后”再更新的变更日志，最终往往永远不会得到更新。

真实案例（2026-08）：某个技能连续发布了两个版本，版本号递增正确、门禁检查通过且 PR 已合并——但**完全没有变更日志条目**，因为此流程中没有任何步骤要求添加条目。直到后续审计时，这两个遗漏才被发现。这正是纪律 #6 在此文件自身上的体现：如果一条规则只存在于约定中，而没有落实为明确步骤，那么每次它都会输给完成任务的冲动。

**尽量缩小注册表的差异——这是所有技能共用的唯一文件。** Marketplace manifest 是所有并发编辑者都会发生冲突的唯一位置，因此，其中不相关的格式更改所造成的代价，远高于其他任何文件中的同类更改：它会把原本干净的三行版本号递增，变成与其他正在编辑该文件的人之间的冲突。使用脚本更新时（解析为 JSON、修改、再写回），重写过程会悄无声息地规范化该文件原本可能未采用的格式——末尾换行符、缩进宽度、键顺序、Unicode 转义。往返修改纪律：完成后重新读取该文件，并对其运行 `git diff --stat`；**唯一可以出现的行，必须是你原本打算更改的字段。** 如果出现额外的行，应恢复该文件原有的约定，而不是连同格式规范化一起提交（曾有一次脚本化的版本号递增，为一个从来没有末尾换行符的 manifest 添加了末尾换行符——在最有可能被其他人同时编辑的文件中，白白多出了一行差异）。同样的原则也适用于技能所涉及的任何共享注册表：lockfiles、catalogs、index documents。

**当一个 PR 经历了几次合并后仍未完成时，请执行变基——然后证明你没有吞掉任何人的工作。** 清单之所以容易发生冲突，也正是它容易过时的原因：只要其他任何内容落入主分支，一个同时修改注册表和变更日志的开放 PR 就会发生冲突，因此应当预料到 `mergeable: CONFLICTING`，而不是将其视为意外（曾有一个 PR 在 main 一下午前进了 7 个提交后遇到这种情况）。如果仓库采用压缩合并，请执行变基而不是合并——在压缩过的历史记录中，合并提交毫无益处。冲突本身几乎总是**增量式的**：两位作者各自在同一个章节中追加了自己的条目，因此解决方法是**两者都保留**，绝不要使用 `--ours`/`--theirs`，因为这会悄无声息地丢弃同事添加的行。

人们经常跳过的，恰恰是能够发现错误冲突解决的步骤——**解决冲突后，证明相较于基础分支，唯一的差异就是你的更改：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要只使用 `--force`：如果远程分支自你上次获取后发生了变化，租约会使推送失败，而这正是其他人已向你的分支推送、普通强制推送会抹掉其更改的情形。

**插件边界不属于此技能的范畴。** 是否将技能拆分到
不同的插件中、如何组织 `source`/`skills`，以及用户能否单独切换
各项技能，都属于打包/分发领域——其 SSOT 是
`marketplace-dev` 技能，而不是此处。当某项任务确实需要作出这些决策时：
确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与
`skill-reviewer` 在需要其脚本时引入 `skill-creator` 相同），然后阅读
marketplace-dev 的缓存与源模式参考资料并遵照执行。不要在
此处重述其规则；副本会逐渐偏离原文。

**重命名、移动或移除市场条目是一项破坏性变更**，会影响
每一位已经安装该条目的用户——当条目消失时，Claude Code 不会清理已安装的副本，
从而留下悬空安装，导致每次执行 `marketplace
update` 都报错。应像对待 API 弃用一样对待此类变更：在
变更日志中发布迁移说明，并按照 marketplace-dev 的指导完成具体操作。

**如果你亲自提交/推送技能仓库：** 对于现有技能，如果当前变更超过了准则 #5 的规则/契约/数值阈值，请确认评审产物记录了此次变更并且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不能仅仅确认历史上存在某个 `independent-review.md`）。拼写错误或纯格式调整不需要该产物；旧评审绝不能满足当前实质性变更的要求。第 5 步的说明解释了为什么对于已经发布的技能，真正的强制执行点是推送，而不是打包。然后只暂存该技能的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充斥着无关改动，否则这些改动会一并进入提交（曾有一次提交卷入了一大批无关的转录文件，不得不执行 `git reset` 并重新暂存）。推送之前，请使用 `gh repo view --json visibility,isPrivate` 确认仓库的实际可见性，而不要根据路径作出假设——公共技能仓库应当使用 PR 并接受评审，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成 Skill 后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试 Skill 后，用户可能会要求改进。这通常发生在刚使用完 Skill 后，因为此时对 Skill 表现的了解仍然很清晰。

**改进过滤原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了相关内容，请勿重复。

## Claude.ai 专用说明

在 Claude.ai 中，使用相同的验证深度路由机制和重度评估授权门槛。当用户明确授权执行完整的通用配对流程时，工作流为：起草 -> 测试 -> 审查 -> 改进 -> 重复；但由于 Claude.ai 没有子代理，因此某些具体机制需要调整。具体调整如下：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，先阅读 Skill 的 SKILL.md，然后按照其中的说明自行完成测试提示词所要求的任务。逐个执行测试。这不如使用独立子代理严格（因为 Skill 是你编写的，同时也是由你来运行，所以你掌握全部上下文），但仍可作为有用的合理性检查，而人工审查步骤可以弥补这一点。跳过基线运行，仅使用 Skill 按要求完成任务。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的虚拟机没有显示界面，或者你正在远程服务器上操作），请完全跳过浏览器审查器。改为直接在对话中展示结果。对于每个测试用例，展示提示词和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），请将其保存到文件系统，并告知用户文件所在位置，以便用户下载和检查。直接询问反馈：“效果如何？有什么需要修改的吗？”

**基准测试**：跳过定量基准测试，因为它依赖基线对比，而在没有子代理的情况下，这种对比没有意义。重点收集用户的定性反馈。

**迭代循环**：与之前相同——改进 Skill、重新运行测试用例并询问反馈——只是中间不再使用浏览器审查器。如果有可用的文件系统，你仍然可以将结果整理到各个迭代目录中。

**描述优化**：此部分需要 `claude` CLI 工具（具体而言是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过此部分。

**盲测比较**：需要子代理。请跳过此部分。

**打包**：只要有 Python 和文件系统，就可以在任何环境中运行 `package_skill.py` 脚本。在 Claude.ai 上，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。在这种情况下：
  - **保留原始名称。** 记下技能的目录名称和 `name` frontmatter 字段——保持二者不变。例如，如果已安装的技能是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前先复制到可写位置。** 已安装技能的路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即基于该可写副本创建审计工具的编辑前快照，然后在该副本上进行编辑，并使用 `--regression-review` 打包。不要传入 `--new-skill`；现有技能的非 Git 副本仍然属于现有技能。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再复制到输出目录——由于权限问题，直接写入可能会失败。

## Cowork 专用说明

如果你使用的是 Cowork，需要了解的要点如下：

- 你可以使用子代理，因此，经过明确授权的通用配对流水线可以运行基线测试和评分器。子代理可用并不等于获得授权，也不能成为增加额外角色的理由；请说明必要的实验分支，限制并发数量，并在并行执行无法增加有效证据时串行运行测试用例。
- 你没有浏览器或显示器，因此生成评估查看器时，请使用 `--static <output_path>` 写入一个独立的 HTML 文件，而不是启动服务器。然后提供一个链接，供用户点击并在其浏览器中打开该 HTML。
- 在经过明确授权的**通用配对运行**之后，请先使用 `generate_review.py` 而不是自定义 HTML 为用户生成评估查看器，再自行修改技能。默认层级证据、未经授权的工作，以及取代查看器机制的专用工作流，并不会仅仅因为工作发生在 Cowork 中就产生提供查看器的义务。
- 反馈的工作方式有所不同：由于没有正在运行的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。随后你可以从该文件中读取反馈（可能需要先请求访问权限）。
- 打包功能可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常运行，因为它通过子进程使用 `claude -p`，而不是浏览器；但请将其留到技能制作完全结束且用户确认其状态良好之后再进行。
- **更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。请遵循上文 claude.ai 部分中的更新指南。

- `scripts/audit_skill_regression.py` — 将不可变的旧 Skill 包

  基准引用而不是 `HEAD`。

为强调起见，这里再重复一次核心循环：

- 弄清楚该 Skill 的用途
- 对于现有 Skill，在编辑前为旧包创建快照并进行清点
- 在采用任何专门工作流出口之前，选择能够证伪此次变更的最低验证层级，并记录原因
- 起草或编辑 Skill
- 运行该层级所要求的证据流程，或所选专门工作流声明的等效机制
- 对于明确授权的通用配对运行，与用户一起评估输出，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复上述过程，直到你和用户都满意为止
- 运行并通过现有 Skill 的回归审查；仅通过评估并不算完成
- 打包最终 Skill 并将其返回给用户。

如果你有 TodoList，请将所选验证层级及其默认要求的证据添加到其中。只有在通用配对流水线获得明确授权后，才添加“创建评估 JSON 并运行 `eval-viewer/generate_review.py`，以便人工审查测试用例”。
