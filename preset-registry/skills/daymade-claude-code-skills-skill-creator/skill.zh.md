# 技能创建器

用于创建新技能并对其进行迭代改进的技能。

从高层次来看，创建技能的流程如下：

- 确定你希望技能完成什么，以及大致应如何实现
- 将变更归类到能够证伪其可能失败模式的最低验证层级
- 编写技能草稿
- 使用能够证伪变更后行为的最小证据进行验证；将完整的配对评估流程视为需要单独授权的工作，而不是某个层级标签所自动带来的后果
- 在所选层级产生结果时，帮助用户评估定性或定量结果
- 根据用户对结果的评估反馈重写技能（如果定量基准测试暴露出明显缺陷，也要据此重写）
- 持续重复，直到你满意为止
- 仅当当前证据无法解决变更后的行为时，才提升验证层级

使用此技能时，你的任务是判断用户目前处于这一流程的哪个阶段，然后介入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须承担的成本。诸如“优化”“改进”或“全面”等词描述的是意图，而不是失败面或评估预算。不要仅仅因为任务听起来范围很广，或一段较长的对话已经展开，就创建评估文件、批量启动配对代理、为输出评分或启动查看器。

以下六项长期适用的纪律贯穿始终，因为这些失败模式会产出看似令人信服、实则错误的技能：

1. **先验证，再编写。** 任何进入技能的技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的结果——无论是在本次会话中，还是在获得明确批准的挖掘会话中。如果现在无法验证，要么去验证，要么明确标注（“未经验证——来自记忆”）。技能会放大其中包含的一切：经过验证的知识会复利增长，而自信陈述的错误也会如此。对于知识型技能（内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作层面的要求：权威层级（观察到的行为 > 机器可读的契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例的冒烟测试，以及面向受众和 Windows 可移植性的检查清单。一次来源依据审计发现，多个自信的契约声明与作者已经掌握的证据相矛盾（方法论案例 9）。
2. **将“无法实现 / 不支持”视为假设，而不是结论。** 当某项能力看似受阻时（API 错误拦截、工具无法连接、某种格式无法打开），在将“平台不支持此功能”写入技能之前，应穷尽各种观察路径——UI 自身的网络流量、替代通道、不同的文档化标识符。观察到的行为高于推测性的请求形式。
3. **站在领域已有成果的肩膀上——默认情况下，在编写或优化技能的方法论之前，先将该领域已确立的最佳实践检索到上下文中。** 技能的方法论质量取决于上下文窗口中的知识，而不是你权重中潜在的知识：预训练知识会丢失、过时，而且通常只有在实际拉取权威来源后才会被激活。因此，你所编写内容的质量上限是 `your training data + the user's input`——*除非*你有意识地检索该主题领域真正已有的成果。应当这样做：通过 WebSearch 搜索该领域的权威理论 / 标准 / 方法，阅读该领域中随附或已安装的技能，然后将其中承载关键作用的原则连同出处融入技能。这与下面的“既有成果研究”是不同的维度——后者寻找可复用的工具 / 基础设施；而这里是让*方法论本身*以该学科积累的科学成果为依据。将其作为**默认操作，而不是等到用户要求后才做**：简要告知用户你正在参考哪个领域的知识，让他们可以说“跳过”，但绝不要在“你的记忆加上用户提示”这一上限下发布方法论——当该领域 40 年的公开成果只需一次搜索就能获得时，更不应如此。示例：数据可视化技能必须吸收 Cleveland & McGill 关于图形感知排序的研究，以及 Bertin 的视觉变量理论（位置 / 长度优于颜色，颜色优于文本——这是经过测量的，而非审美偏好）；日期 / 时间技能必须指出成熟的库及其典型陷阱；说服 / 谈判技能必须检索已有的成熟框架，而不是凭记忆重新发明。如果权威知识只存在于你的权重中，却从未进入上下文，那么你就是在本可引用的地方进行猜测。
4. **在压缩现有技能之前先予以保留。** 更新现有技能是一项迁移工作，而不是从空白页面开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧版本内容，或者从明确的 Git ref 中重建它；任意复制一份并附上溯源标签并不能构成基线。盘点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和简洁性允许移动或去重内容；但不允许悄然删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个未匹配的旧单元进行分类。只有存在于 `evals/`、测试或未链接的参考资料中的运行时契约，仍然算是丢失。只要仍有候选项未分类，或仍有真正的缺口未修复，就不要宣称更新完成。同样的逻辑也适用于**逆转**，而不仅仅是删除，还涵盖任何此前已经作出的承诺——不只是那些带有日期和名称的承诺：**推翻已经作出的决定是一项提案，绝不能作为副作用发生。** 要明确说出来并获得认可。悄无声息的重写比悄无声息的删除更糟糕，因为它会一次性摧毁产物以及本可发现问题的证据——同时也会蒙蔽所有下游审阅者（见 #5）。

**在编辑前为每项预期变更分类；“压缩”指的是行为等价这一主张，而不是“更短”的同义词。** 对于每个旧有用户场景，新鲜上下文中的 agent 仍必须能够找到触发条件、决策输入、支持的操作、停止/确认点、影响/恢复边界以及验证路径。在计划、评审和变更日志中，将这些名称作为单独的变更类型标签使用；在每个回归候选项的原因/语义评审中记录该标签，同时将审计工具的 `disposition` 字段保持为完全匹配 Step 4 枚举的值：

   | 变更类型 | 定义 | 必需处理 |
   |---|---|---|
   | **无损压缩** | 只改变表达形式：将细节移入可直接访问的捆绑引用中、相对于随包提供的规范来源进行去重，或缩短措辞，同时保留上述每一项运行时契约 | 可以称为压缩；必须证明场景可达性，而不仅仅是字符串仍然存在 |
   | **能力退役** | 某项此前可执行的任务或操作不再可用 | 不是压缩；明确说明已退役的能力，获得可追溯的用户批准，并发布边界 |
   | **范围收窄 / 边界变更** | 仍受支持的输入、目标、环境或模式减少；某个执行分支变为仅分析 | 即使这样做更安全，也不是压缩；明确呈现并发布边界/权衡，然后获得可追溯的批准，除非用户此前已经明确要求进行这项精确的收窄 |
   | **工作流或安全性重新设计** | 命令、顺序、确认、副作用、恢复或成功检查发生实质性变化 | 不是压缩；明确呈现新的契约和权衡，除非用户此前已经明确要求进行这项精确的重新设计，否则获得可追溯的批准，然后独立于保留性检查对其进行验证 |
   | **缺陷修复 / 事实更正** | 将实现或正文恢复到某项明确存在的契约，或恢复到当前权威来源所规定的内容 | 不是压缩；使用能够裁定该问题的狭窄权威来源或确定性回归 |
   | **有损摘要** | 精确条件、命令、决策语义或执行退出条件消失，且没有运行时可达的等价内容 | 属于回归，而非优化；恢复这些内容，或通过上方某个已批准的行重新分类 |

   只有在规范来源随 skill 一同提供，或能够可靠地获得，并且 SKILL.md 告知运行时读者何时加载该来源时，去重才算无损。“这个想法仍然存在于测试、变更日志、已安装的同级 skill 或作者的记忆中”不属于压缩。如果一个补丁包含多种类型，分别列出它们；绝不能让压缩标签掩盖退役或重新设计。

5. **任何内容都不能仅凭自我评审发布——独立、全新上下文的对抗性检查是固定步骤，而不是特殊情况。** 你“现在已经没问题了”的判断，使用的是生成该产物的同一个模型，因此也共享导致缺陷产生的那些盲点。事实已经测量过，而非民间经验：没有外部反馈的内在自我纠错并不能可靠地改善输出，有时还会使输出变差（Huang 等，ICLR 2024）；当生成器和评估器共享错误模式时，反复迭代会**提高信心，却不会增加信息**。更多的自检无法摆脱这一点；只有外部视角才能做到。**完整流程——包括提示模板、锚点选择、发现项表格和实例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在首次检查前阅读它。** 承重规则如下：
   - **独立性有两个方面，而第二个方面正是作者最容易遗漏的。** *评审者的上下文*不能是你的分支——分支会继承你的盲点，并返还一个“已评审”的印记。但它所依据的*证据*也必须位于变更的**影响范围之外**，否则它会继承你的**结论**：它读取一个产物和一份已经彼此一致的规范，然后报告二者一致。注意，“本次会话中没有编辑过”这一界线太弱——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，三名评审者都对一个他们在未改动副本中发现过的缺陷视而不见。应根据锚点被你触碰过的难易程度对其排序：用户自己的对话原文 > 工作开始前的 git ref（`git log --oneline <ref>..HEAD -- <path>`；你的任何提交都会使它失效）> 追加写入日志（这是一种约定，而非强制机制）。**全新项目没有锚点——说明这一点并索要一个锚点，不要报告一个你实际上没有执行过的通过结果。**
   - **只向评审者提供恰好两个承载证据的输入：不可变产物和读者规范。** 另外提供用于限定检查范围、但不承载证据的控制元数据：当前变更的影响范围、明确列出的失败轴以及终止条件。不要提供设计理由、项目背景或“只要确认 X 没问题”之类的内容——这些会把独立评审者变成橡皮图章。读者规范和控制元数据说明由谁执行什么以及在哪里停止；它们不能告诉评审者实现是正确的。**对于 SKILL.md，读者就是另一个执行它的 agent**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——询问它哪些指令无法执行。在派发前冻结全部五个字段，并且绝不要使用事后上下文来解释或排除发现项。
   - **它是判断可理解性以及针对语料库的完整性的事实依据；但它无权裁定品味。** 直接应用这两项。把“这可能是一个 bug / 我建议 Y”视为假设，并先自行复现。绝不要委托 AI 垃圾内容或审美判断——这属于同一个模型的盲点。
   - **列举失败*轴*，而不是内容领域——这也决定运行多少个评审者。** 轴是*你要提出的问题*；领域是*你要阅读的材料*。三个评审者分别覆盖场景、算术和 diff，但都在问“这是否连贯？”，那只是同一个评审者被计费三次。**一个评审者是默认配置，而且通常已经足够**；只有增加一个额外轴时才增加评审者。自我评审最不擅长的轴是**保真度**——“它是否仍然忠实于已经作出的承诺？”——因为正是作者移动了这项承诺，而连贯性和保真度是正交的：一个产物可以做到完全自洽，却完全不忠实于已决定的内容。
   - **在派发前冻结评审边界，并在满足该边界后停止。** 记录不可变产物/ref、读者规范、当前变更的影响范围、明确列出的失败轴以及终止条件。当某项发现是由当前变更造成、扩大了当前变更的影响范围、新近宣传了受影响的行为，或使某个旧有矛盾通过编辑后的路径变得可达时，该发现会阻止本次发布。某个既有缺陷如果没有变化，且没有被新近承诺，则属于单独的待办假设，不会自动授权重新设计 skill。在实质性修复后，由新的评审者重新检查失败轴以及回归；它不会重新开启一次无边界的全 skill 审计。完整的决策流程和示例见：[references/independent-review-protocol.md](references/independent-review-protocol.md)。
   - **留下产物，否则这只是一条警告。** 纪律 #6 规定，产生意见的检查不如产生产物的检查——因此这一步也要生成一个文件，否则它恰好会在最需要发挥作用时输给完成驱动。将 `independent-review.md` 写入你的私有、受 git 跟踪的知识库中的 `skill-reviews/<skill-name>/` 下：包括**逐字记录的评审者提示**（这样后来的读者才能判断它是否具有引导性）、**每条发现及其 disposition 和原因**（这正是合法筛选与丢弃不利内容之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识库（或者你没有这样的仓库），说明这一点并询问用户——不要猜测一个最终落入任一禁区的位置。两个禁用位置：**不得位于 `<skill-name>-workspace/` 中**（会被 gitignore 的临时目录会被清除——该文件是跨会话的评审证据，必须能够在这些目录之外留存），**也不得位于任何已经公开或可能公开、分发的仓库中**——这通常意味着不能放在被评审 skill 自己的仓库中（评审内容本身会引用私有路径、真实姓名和项目细节）。在实质性编辑后，使用一个新的 agent 重新评审——这里的实质性编辑是规则、契约或数字发生变化，而不是拼写错误。**从 Step 5 开始，该文件就是评审已发生的证据；文件缺失就意味着评审没有发生。****写入文件不等于下一次会话中它仍然存在——在同一轮中对其执行 `git add` + `git commit`，提交到那个私有仓库。** 一个停留在 git 工作目录中的未提交文件，不具备这条规则所要求的任何“受 git 跟踪”保证：它可能丢失、被覆盖，或者后来检查“是否已评审”的进程根本不会拾取它（真实案例：文件已正确写入正确路径，并包含真实发现——但后续自动检查仍然失败，因为它从未被提交；修复方式是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械性的，并且与此互补：它证明你没有*删除*行为。它无法说明你写下的内容是否真的能够被遵循。

6. **设计你编写的检查，使其无法自我认证为通过。** 技能主要由各种检查构成——门禁、检查清单、“发布前”步骤——而如果执行上下文在*违反其所编码的规则*时仍能通过某项检查，那么这项检查比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴自那些早已解决这一问题的领域：
   - **验证必须覆盖其规则中的每一条条款。** 如果规则说的是“A + B + C”，证据就必须分别要求证明 A、B 和 C。把一条确认语句附加在包含三个条款的规则上，只会让作者已经完成的那一条满足检查；其余条款则完全不可见。真实案例：一个报告编写技能有一道交付门禁，其规则写着“选项以并排芯片呈现 + 突出显示推荐项 + **背景信息必须写成完整、独立成篇、陌生人也能理解的句子**”——但其下的证据行只要求“N 个决策项，全部渲染为芯片”。作者运行门禁，写下了这条证据，自我认证为通过，然后发布了一个页面：其中的标签只有单个字符，所有上下文都被删除了。规则自始至终都在文件中；只是检查从未衡量过那条款。
   - **对健康输入误报的检查比没有检查更糟。** 上述失败属于本应失败却通过的检查；这里是它的镜像——本应通过却失败的检查。后者代价更高，因为它会教会操作人员条件反射式地绕过检查（`--no-verify`、`SKIP=1`、`--force`），而一旦形成这种反射，门禁就会对*所有*输入关闭，包括它原本就是为之构建的那些输入。因此，在编写失败即关闭（fail-closed）的检查时，**误报的优先级高于漏报**：漏掉一个真实问题，只会损失这一个实例；而误杀一个健康输入，则会让整个门禁失效。
     注意这个信号：**反复踩中同一个陷阱所产生的挫败感本身就是风险信号**——这正是作者会发布一个从未针对健康输入校准过的防护措施的状态。真实案例：作者一天内三次踩到同一个格式陷阱后，给 linter 加了一项正则检查；它误杀了项目自身语料库中的 **33 个健康输入**，并在同一小时内被回滚。启用之前先进行校准——让任何失败即关闭的检查在真实的、已知良好的材料上运行，并确认零误报；宁可放宽它，让它偶尔漏掉问题，也不要让它出现任何误报。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是独立自足的”无法由撰写它的人判定为失败；而“覆盖页面的其余部分，单独阅读一张卡片，并说明它正在决定什么”则可以。优先选择能够产出某种工件的检查——命令输出、引用的行、屏幕截图——而不是产出一种意见的检查。
   - **同样的怀疑也适用于你*运行*的检查，而不仅仅是你编写的检查。** 上述四条规则约束的是随技能一起交付的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样是工具，而错误的工具会像正确的工具一样自信地报告干净结果。在一次 2026-07 的会话中，五条不同的验证命令在两个方向上都给出了错误结果：没有使用 `-L` 的 `find` 报告已安装技能的文件缺失（它们位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了正在审计的对象的第二份副本；反转的 shell 条件错误地警告某项删除操作尚未发生；跨越换行符的正则表达式凭空制造出 55 个“丢失的引文”；而对五个文件中的两个进行搜索，却报告两条规则缺失，尽管它们存在于第三个文件中。**这些结果最初无一例外都被相信了，而最终也无一例外都是通过重新运行形态不同的检查才被发现的。**

这个修复方法是实验实践中最古老的一种：**在你信任某个仪器去检验一个答案未知的案例之前，先用一个答案已知的案例运行它。** 如果你要用 grep 查找一个预期不存在的字符串？先用完全相同的命令形式 grep 查找一个你确定存在的字符串——如果那也返回 0，那么出问题的是命令，不是文件。只需多写一行，就能把“我检查过了”变成“我用校准过的仪器检查过了”。

     有两种具体形式值得记住，因为上文都出现过，而且两者都会*静默失败*：`find` 默认不会跟随符号链接，除非加上 `-L`（而 skill 的安装经常是指向源代码仓库的符号链接）；`--exclude-dir` 会在整个目录树中按 basename 匹配，而不只是匹配你心里想到的那个路径。

     **而这条规则还有后半部分，只有当检查内容要随产物一起发布时才会真正造成影响：要针对*标准*实现进行校准，而不是针对你机器上的实现。** 上面的仪器规则确保*你的*结论可靠；这一点则确保*读者*能够正常工作。写入 skill 的工具行为断言——某个标志、递归模式、一个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而两端的差异都是静默的：它在你测试时有效，却在读者那里悄悄不起作用。有两种机制会导致这种情况，而且在会话内部都无法看出来：**同一个命令名解析到的是不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能绕过*别名*，所以 `command tool` 或绝对路径才是唯一具有确定性的形式）；以及**同一个程序在不同实现之间的行为不同**（BSD 与 GNU，或兼容替代品之间）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将其写入 skill，作为解决符号链接陷阱的方法，并将其发布到了一个拥有 1200 个 star 的公共仓库——但他们的 `grep` 实际上是 shell 函数中的 ugrep；在 macOS 自带的 `/usr/bin/grep` 上，同样的 `-R` 什么也匹配不到（它需要 `-RS`），所以对于大多数读者而言，这个规定的修复方法都静默失败了，而这恰恰发生在警告验证器会静默失败的章节中。

     因此：**在工具行为断言进入已发布的产物之前，要针对标准二进制文件重新运行它**（`/usr/bin/<tool>`），而不是针对 shell 提供给你的那个。如果它经不起这项检验，就不要写入这个标志——**优先采用与实现无关的表述方式**：自行解析路径（`readlink -f`），不要押注于递归标志；在脚本中进行子字符串测试，而不是进行面向行的匹配；描述你需要的*行为*，而不是描述你碰巧知道的选项。一个只在你自己的环境中有效的规定，比没有规定更糟，因为读者没有办法发现它只是静默地什么也没做。

   - **使用成熟的清单实践已经确定的方法。** 判断一个列表应当是 **READ-DO**（边阅读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭经验完成操作，然后在定义好的**暂停点**停下来确认——适用于时间紧迫情况下的有经验操作者），并将其锚定在一个真实的暂停点上，而不是“工作流程中的某个地方”。只保留**致命关键项**——既关键、又经常在压力下被遗漏的项目，大约五到九项；再多就会削弱执行依从性（[Gawande，《清单宣言》](https://www.shortform.com/blog/types-of-checklists/)）。并且优先采用 Shingo 所说的**控制**而不是**警告**（[防错](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，会输给“完成任务”的驱动力；而阻止进度或强制生成某个产物的步骤则完全不需要警觉性。如果某个 skill 只能发出警告，那么至少要把警告放在决策发生的位置——**写在执行上下文从未打开的参考资料中的规则，在实践中就不是规则。**

另一方面，他们可能已经有了 skill 的草稿。在这种情况下，你可以直接进入这个循环中的评估/迭代部分。

当然，你始终应该保持灵活；如果用户说“我不需要运行一堆评估，和我一起凭感觉来就行”，那你也可以按他们说的做。

然后，在 skill 完成之后（不过再次强调，顺序是灵活的），你还可以运行 skill description improver。我们为此准备了一个完整的独立脚本，用来优化 skill 的触发效果。

## 首先：共存检查（官方 skill-creator plugin）

在进行任何操作之前，先快速检查一次（在常见路径下无需输出任何内容）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 什么都不做——不要安装任何内容，也不要向用户提及本节。继续进行当前交互。
- **存在：** 官方 plugin 的 skill-creator 与本版本现在会以几乎相同的描述出现在 skill 列表中，因此未来的会话将随机在二者之间进行路由。用一到两句话告知用户这一点，然后提供以下选项（绝不要未经用户同意就执行）：
  1. **推荐**——运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型自检 SessionStart hook 复制到用户的 Claude 配置中，并将其注册到 `settings.json`（同时创建备份），这样今后的每个会话都会确定性地将 skill 工作路由到本版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；官方 plugin 在按名称请求时仍可完全正常使用。在没有官方 plugin 的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的 hook。
  2. 备选方案——执行 `claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），这会将官方条目完全移出 skill 列表，从而消除歧义。

如果 hook 已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有步骤。

同样的机制也适用于用户创建的 skill：当他们的 skill 有意与某个已安装的 skill 重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一套工具包——参见 Prior Art Research 下的“共存与优先级”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

skill creator 可能会被各种编程术语熟悉程度不同的人使用。如果你还没听说过（怎么可能呢，这种趋势才刚刚出现没多久），如今 Claude 的强大能力正促使水管工打开终端，也让父母和祖父母去 Google 搜索“如何安装 npm”。另一方面，大多数用户可能都具备相当程度的计算机使用能力。

因此，请留意上下文线索，以理解应该如何措辞沟通！在默认情况下，给你一些参考：

- “评估”和“基准测试”比较接近临界点，但可以使用
- 对于“JSON”和“断言”，在用户明确表现出他们知道这些是什么之前，不要不加解释地使用这些词语

如果你不确定，可以简要解释相关术语；如果不确定用户是否能理解某个术语，也可以通过简短定义加以澄清。

### 使用 AskUserQuestion（重要 — 请阅读）

**在每个决策点都积极使用 AskUserQuestion。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最大 UX 改进——用户可能同时处理多个窗口，而且可能已经有 20 分钟没看这段对话了。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明 skill 名称、当前阶段，以及刚刚发生了什么（1–2 句话）。用户可能刚刚切换去处理其他事情。
2. **简化说明**：用通俗易懂的语言解释这个决策。不要使用函数名或内部术语。说明它会做什么，而不是它叫什么。
3. **给出建议**：先给出你的建议，并用一句话说明原因。如果选项涉及工作量，请同时展示两种时间尺度：`（人工：约 X 分钟 / Claude：约 Y 分钟）`。
4. **提供选项**：提供 2–4 个具体的、带字母标记的选项。每个选项都应是明确的操作，而不是抽象概念。

**规则：**
- 每个问题只涉及一个决策——绝不要将无关的选择合并到同一个问题中
- 提供退出选项（AskUserQuestion 始终隐含“其他”选项）
- 接受用户的选择——可以提示权衡，但绝不要拒绝继续执行
- 如果存在没有权衡且显而易见的答案，则跳过提问（直接说明你将采取的做法）
- **如果问题超时且没有得到回答（用户不在键盘前），既不要停滞不前，也不要擅自推进涉及偏好或范围的决策。** 先完成无副作用的基础工作——编辑前快照、清单盘点、评估用例收集、只读审计/健康检查——并在用户回来后再处理需要判断的决策（重构方向、删除哪些内容、是否继续）。然后明确说明你完成了哪些工作，以及哪些事项正在等待用户决定。

## 创建 skill

### 捕获意图

首先了解用户的意图。当前对话中可能已经包含了用户想要固化的工作流（例如，他们说“把这个变成一个 skill”）。如果是这样，先从实时对话中提取答案——使用过的工具、步骤顺序、用户提出的修正、观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**源清单——起草前始终执行，并遵守同意边界。** 盘点实时对话以及与之重叠的现有文档/skills（参见下方的“既有成果研究”）。更早的本地会话 JSONL 文件属于单独的私有来源：除非用户明确要求挖掘历史，或在你解释将读取哪些内容后明确批准该来源，否则不要打开或解析这些文件。如果获得批准，应通过对话挖掘工作流中的脱敏提取，仅将相关的过往会话纳入；绝不要将原始记录加载到你自己的上下文中。如果未获批准，则继续使用实时对话和现有项目来源，不要将缺失的历史视为阻碍。

挖掘对话（或会话记录）时，要始终盘点两类资产——它们会存放在不同位置。*知识*——端点、参数、陷阱、决策规则——会成为 SKILL.md 指南或 `references/` 中的内容。*本次会话必须编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——则是 `scripts/` 的候选内容：如果本次会话编写了这些代码，下次调用时就必须重新编写，因此应将其参数化、进行清理并打包。此前的一次提炼整理出了完善的文字说明，却遗漏了可复用的辅助工具；总体经验是，要同时关注知识→references 和代码→scripts 这两条路径。

当源材料是*过去的*会话记录（Claude Code projects directory 下的 JSONL 文件），而不是当前实时对话时，进入会话挖掘工作流。不要在主上下文中打开原始记录，也不要将原始路径/内容交给子代理。在任何代理看到内容之前，必须先完成确定性的 manifest → discover → redact → chunk 流程；只有经过脱敏的分块才能进入最小化的角色/分片计划，并且必须在预算门禁下声明确切的单元数量和并发上限。

**首先，在回答下面的问题之前，先确定这是哪个方向。** 请求可能属于几种彼此相反的事情：构建新 skill / 编辑现有 skill / 优化 skill-creator 本身 / 或者根本不是 skill，而是一次性任务。猜错会浪费整个会话——为“新 skill”开展的研究，并不适用于“优化元工具”。当表述含糊时（例如，用户说“帮我做一个 skill”，但指向的是 skill-creator 自身的路径），在这里提一个 AskUserQuestion 只需 30 秒。下面的 wrapper-skill 分支是其中一个特殊情况；方向检查本身具有普适性。

`Use skill-creator to optimize <existing-skill>` 表示正常的现有 skill 更新路径。它并不授权进行会话历史挖掘、广泛重写、Tier 3 分类或多代理评估。先检查实际提议的变更；只有当这些变更确实引入了某个失败面时，才升级处理。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在什么时候触发？（哪些用户表述/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证这个 skill 是否有效？对于具有客观可验证输出的 skill（文件转换、数据提取、代码生成、固定工作流步骤），测试用例很有帮助。对于具有主观输出的 skill（写作风格、艺术、经过品味校准的报告），通常无法使用断言——但“没有断言”不等于“不验证”。它们的验证路径按成本排序如下：
   - **历史任务重放**：重新运行一个这个 skill 过去处理过的真实提示词，比较新旧 skill 的输出，并针对具体变更的规则进行检查（“新输出是否确实遵循了这次更新引入的 tokens / title grammar？”）。成本低，还能捕捉到“规则写了出来，但没有任何内容读取它”这种问题。
   - **以生产使用作为评估**：承认真正的测试是用户下一次的实际使用——然后明确这个闭环：之后用户的每一次纠正都是需要纳入其中的事件（skill 自身的“迭代/活文档”部分），每一次认可都是语料库材料。一个交付时没有这种回写习惯的品味型 skill 不会进步；而拥有这种习惯的 skill 无需正式评估就能逐渐收敛。**此外，当 skill 的输出是某个会持续运行的东西——守护程序、监控器、定时任务、钩子——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户纠正需要用户注意到问题并愿意反馈；而已部署的机制会主动报告自身情况，通常在一天内就能做到；误报则是这种报告最鲜明的形式，因为它证明你写下的某条规则是错误的，这是反复重读也无法揭示的。把第一次误报当作一次已安排的评估结果，而不是恼人的干扰：在认定机制行为异常之前先检查它，因为更可能的结论是，*指令*写得过于绝对。（真实案例：某个 skill 规定了一项必须失败即报警的检查，已部署的检查在夜间对一个完全健康的状态触发了一次，修复方式是改正 skill 中那句过于绝对的表述——没有人提出抱怨；是遥测数据发现了问题。）
   - **渲染 + 人工审查**：适用于视觉输出（使用 skill 自身的视觉 QA 门禁），绝不要用假装能够衡量美观性的 grep 断言来代替。**而且，用于验证的渲染器必须与最终交付物实际使用的引擎相同**——无论哪个预览器恰好已安装，都不能替代目标应用。布局引擎不同于目标应用的缩略图生成器，可能会静默地*隐藏*你正在寻找的确切缺陷；在错误引擎上得到绿色验证，比完全不验证更糟，因为它会制造虚假的信心。真实案例（2026-07）：一个 .docx 通过 macOS Quick Look 缩略图进行了“视觉验证”，但 Quick Look 不会复现两端对齐文本的拉伸效果；用户打开文档后，Word 才显示出信息块瞬间被撑开的情况。修复方式是安装兼容 Word 的引擎（LibreOffice），转换为 PDF，按页栅格化，然后逐页阅读。匹配引擎，否则验证就是演戏。**这一点也适用于渲染器之外的所有验证工具**——解析器、linter、验证器：它必须与生产环境共享同一实现，否则它显示为绿色就毫无意义。第二个案例也是同样的情况：作者试图捕捉一种会破坏最终文档的标记模式，却在源文件阶段使用了不同于生产工具链所用 markdown 实现的工具进行检查——它把三个已知有问题的输入全部解析为完全正常，因此任何建立在其上的预检查都会静默地放过所有内容。诚实的结论是，这种特定缺陷只能在生产工具运行之后检测到，检查也应放在那里。**当没有任何可用工具与生产实现共用时，应明确说明该检查无法在那个阶段完成——不要构建一个只能产生虚假绿色结果的检查。**
   根据 skill 的类型，建议适当的默认方案，但由用户决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认技能类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类会驱动后续的整个评估策略。在这里做出正确判断，可以避免之后的无效工作。

### 扩展与创建检查——在任何专门分支之前运行

下面的三个专门工作流都以“**do not** continue reading the sections below”结尾，而 *Prior Art Research* 恰好位于它们之后。这样的顺序是排版顺序，而不是执行顺序。扩展与创建的判断适用于每个分支；跳过这一步，正是导致会话交付出一个与已安装技能重复的技能的原因。

因此，在进入 wrapper-skill / conversation-mining / artifact-corpus 分支之前，先回答一个问题：**是否已经存在一个适用于此能力的技能？**

**发现根目录，不要凭记忆。** 手动维护的安装位置列表正是最容易过时的产物，而你忘记的那个根目录，恰恰是最容易造成问题的地方。

**搜索文件，而不是搜索名为 `skills` 的目录。** 技能目录以*技能*命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、市场克隆仓库和插件缓存中根本没有名为 `skills` 的目录——搜索这个名称会悄悄跳过它们，同时看起来却像是正常工作。每个技能都有一个 `SKILL.md`；这是与目录布局无关的定位方式。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，而且仍会返回比你需要的更多结果；请使用针对该能力的具体术语进行缩小，而不是使用通用术语（`chart` 会匹配所有内容，而 `stacked bar` 不会）。

这次检查所覆盖的根目录——也是通常凭记忆列出的清单容易遗漏的部分——包括：技能源代码仓库（一个 `claude-code-skills` checkout 以及任何 `-pro` 兄弟仓库）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件——源代码仓库中没有任何迹象表明它们存在于此处）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、每个 profile 的配置目录（`~/.claude-profiles/<name>/`），以及——完全没有任何线索可循的一处——**每个项目自身的 `.claude/skills/`**。步骤 2 才能让这成为你验证过的结论，而不是你沿袭下来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何 marketplace、全局技能列表或源代码仓库列表中；你在规划新技能时通常会打开的地方，没有任何内容会提到它们。真实案例（2026-07）：一次会话为某个领域构建了一个全局技能，检查了源代码仓库、全局目录和其他 agent 的目录，什么也没找到，然后完成了发布。后来的一次会话历史搜索发现，某个项目中正好有一个针对该领域的成熟项目级技能，已经存在了一个月，位于该项目的 `.claude/skills/` 中——其中包含新技能所缺少的八条规则，包括一条用户亲自指定的规则。除了项目级目录之外，所有根目录都检查过了，而这次扫描却信心十足地报告“没有已有方案”。

**当重叠的技能确实是某个无关项目中的项目级技能时该怎么办**——这正是上述惨痛经历会把你带入的情况，也是下面三个要点没有涵盖的情况：你无法向一个原本没有套件的套件添加兄弟技能，而“扩展它”意味着编辑无关项目的工作树。有效的做法是：**将其中的规则提取到你正在构建的技能中，然后在所有者同意后停用项目本地技能**——它是针对真实工作编写的，因此应将其视为更成熟的来源，并且向它靠拢进行协调。停用他人的工作技能是所有者的决定，而不是你构建过程的副作用。

这句话遗漏了四件事，其中每一件都可能让你止步不前：

- **“向它靠拢进行协调”是一项可反驳的推定，而不是规则。** 有两种标准的处理方式：项目技能可能已经*过时*（规则是几个月前针对某个已经发生变化的系统编写的），也可能是*项目特定的*（规则只在该项目的约束下成立——整套导入会让你的技能变得狭窄，而本文其他地方明确告诉你不要这样做）。提取出的规则是另一位作者的记忆，因此**必须逐条重新验证**，就像纪律 #1 要求你验证写入技能的任何内容一样。
- **“停用”需要一个机制，而且第一步并不是你通常会采取的那一步。** 顺序如下：

  1. **先用 `find` 查找该技能的*实体内容*，再 grep 查找它的*引用*。** 一个技能在同一个仓库中通常不止一份——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被加载，只是由同一个工作树中的不同工具加载。Grep 能回答“谁提到了它”；只有 `find` 能回答“它到底有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放入 `--exclude-dir`**（它按 basename 匹配，因此会隐藏所有同名目录，包括你尚未找到的那一份——参见纪律 #6 中关于工具的规则）。真实案例（2026-07）：一次停用操作正是这么做的，修复了它找到的全部五处引用，却在 `.agents/skills/` 下留下了第二份完整副本——该副本由 git 跟踪，没有停用标记，是一份缺少最新规则的过时快照——另一个工具仍会将其作为有效技能加载。
  2. **在删除任何内容之前，先确认新位置确实能够从旧位置所在的地方被访问到**，*然后*再删除任何内容——你刚推送的 marketplace 技能，在 marketplace 更新并安装插件之前并没有真正安装；如果先停用旧技能，就会留下新旧技能都不存在的窗口：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常通过符号链接指向源代码仓库，而不带 `-L` 的 `find` 会报告文件不存在（参见纪律 #6 中关于工具的规则）。
  3. **然后** grep 查找引用，并重新指向仍在使用的引用。区分**有效指令**（技能列表、交叉引用、告知下一个 agent 应使用什么的交接文档）和**历史记录**（决策日志中写着“我们在某日期发布了此项”）——改写后者会破坏审计线索，只为修复一个它并不存在的问题。
  4. **然后**将每个实体内容替换为 `superseded by <skill>` 存根，而不是直接删除，并确保每份副本的存根在字节级完全一致。**保留 YAML frontmatter**——没有它的 `SKILL.md` 可能会加载失败，却不会提供有意义的失败信息——但要重写 `description`，让存根声明自身已经停用，而不是继续宣传旧的触发条件；否则它会继续赢得自己已经不再服务的路由。正文只需要包含：能力迁移到了哪里，以及迁移原因的一行说明。
- **使用下面的所有权测试来识别所有者**（这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍然会告诉你它属于谁）。当所有者就是正在与你交谈的人时，“同意”只需要一次 `AskUserQuestion`。**当所有者无法联系时，只提取规则——不要停用**（这会让两个技能都保持有效，并争夺同一个触发条件，其最终状态与所有者拒绝停用相同——参见下方的共存与优先级）。
- **如果所有者拒绝停用它**，那么现在就有两个技能在争夺同一个触发条件；这属于下方的共存与优先级问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 那个项目技能不会匹配新技能标题的名称搜索；它匹配的是正文中的领域术语。请在候选根目录中 grep 新技能将处理的*概念*。

如果存在重叠：

**决定适用哪条——这个技能属于谁？** 文件系统命中结果不会携带所有权信息。请读取 marketplace 的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在所属仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中项同样可能只是你自己的 marketplace 被安装回了你的机器。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同一个问题。

有两种情况，探测结果会判断错误或无法回答，因此在相信结果之前请先检查：**fork** 会显示你自己的 remote，但内容实际上属于他人——请将其视为第三方，因为他们上游的改进仍然无法继续触达你。还有，当**既没有 marketplace.json，也没有 remote** 时（本地项目、手动复制到全局技能目录中的技能），探测结果是不置可否，而不是否定：**请询问所有者，而不是猜测**。

- **重叠的是第三方技能**（某个 marketplace 套件、官方插件）：**不要重新实现它的能力。** 编写一个能够正确驱动它的*薄增量*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本——并通过**带命名空间的名称引用它**。把别人的引擎克隆进你的 bundle 是代价高昂的错误：他们的升级将无法继续触达你，而两份副本会在不知不觉中逐渐偏离。
- **重叠的是你自己的技能**：扩展它，或在其现有套件中添加一个兄弟技能。一个为相同触发条件竞争的独立技能对任何人都没有帮助。**例外：**如果它位于*无关项目*的工作树中，则以上两种处理方式都不适用——请参见上面的项目级情况。
- **某个相关技能已经指向你正在填补的缺口**（例如其描述写着“对于 X，请使用 Y”）：构建完成后要闭环——更新该指向，否则你就留下了一个悬空引用。

只有在没有任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**一次真实的 2026-07 会话花了一天时间，让一个第三方 docx 引擎生成正确的中文商务文档，随后才转向 wrapper-skill 分支——而该分支会直接跳过 Prior Art Research。它当时准备发布的形态，是一个重新携带该引擎能力的新技能。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个包含正确用法和经过验证的生成器脚本的薄增量技能 → 领域工作流技能调用该增量技能。用户不得不纠正两次才最终落地，第二次纠正得更准确：*“不要再复制一个——在他们的能力之上写出正确用法，并引用他们的技能；这就是 skill-as-code 的含义。”*

### 验证深度路由器（选择任何工作流之前运行）

在选择通用或专用工作流分支之前，先选择能够证伪已变更行为的**最低层级**。应根据具体变更及其失败面进行分类，而不是根据行数或请求措辞：一条变更后的破坏性命令可能比一大段冗长的文字清理更应归入高层级，而请求“优化”现有 skill 也可能只是一次有界修正。在选择层级之前，列出你实际打算更改的规则、契约、脚本、权限和输出。如果这些内容尚未明确，先进行检查并暂定分类；范围不确定并不能作为归入第 3 层的依据。

| 层级 | 适用情况 | 所需证据 | 默认不要添加 |
|---|---|---|---|
| **1 — 定向** | 这是一个现有 skill；没有新增或实质性变更能力、触发器族、工作流分支、输出契约、依赖项、权限或外部写入行为；且编辑内容恰好属于以下一种：(a) 不改变行为的拼写/格式修改；(b) 事实性文档/配置更正，其真实性由直接权威来源决定；或 (c) 有界的实现修复，用于恢复明确的现有契约，**并且**修复后的行为由确定性回归检查覆盖。可能改变代理行为的澄清不属于第 1 层 | 对于以上三种情况：运行 `quick_validate`，检查差异，并完成现有 skill 迁移门禁。然后仅使用相匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其针对性检查；(c) 明确的现有契约及确定性回归。仅当触发 discipline #5 的规则/契约/数值阈值时，才添加一名新鲜审阅者 | 默认不添加代理行为回放、成对运行、基线、评分器、基准测试、查看器或评估文件 |
| **2 — 抽样行为** | 这是一个现有 skill；变更会影响代理行为，但不会新增能力、触发器族、输出契约、脚本行为、依赖项、权限或外部写入；并且 1–2 个具名示例、配合明确的验收标准，就能覆盖整个变更后的行为。对某一条现有路由或证据选择规则的有界修正，即使改变了所选路径，也仍属于此层级 | 仅运行这 1–2 个具有代表性的 with-skill 回放、针对性的确定性检查，以及 discipline #5 要求的一次新鲜上下文审查 | 默认不添加基线、成对扇出、方差分析、基准测试、查看器或评估文件。明确要求提供这些内容时，应通过单独的证据预算门禁处理，且不会因此重新划分变更层级 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新 skill；任何新增或实质性变更的能力；广泛的跨分支重写或方法论扩展；触发器/描述优化；新增的工作流分支，或实质性变更的输出契约、脚本能力、依赖项或权限；高风险自动化或外部写入；或者变更后的行为本身涵盖 3 个以上不同的提示类别、重复试验或实质不同的方法 | 先运行确定性门禁，然后仅添加针对已命名失败轴所需的证据。只有在单独的重型评估授权门禁通过后，才可使用下面完整的成对流水线；第 3 层本身不会启动该流水线，同一门禁也可以授权在其他层级添加额外证据 | 不得仅因标记为第 3 层，就自动添加成对扇出、评分器、基准测试或查看器

#### 重型评估授权门槛——独立于层级分类

层级描述的是**风险与不确定性**；它并不授权消耗令牌或进行代理扇出。通过此门槛会改变允许采用的证据方案，而不会改变层级。通用的 paired baseline → grader → benchmark → viewer 流程只有在以下任一条件满足时才可运行：

- 用户明确要求进行 A/B、基线测试、基准测试、重复试验、使用 viewer，或进行多代理评估；或
- 执行者能够指出至少三个不同的提示类别、彼此竞争且均合理的结果，以及配对比较将改变的决策，然后获得用户明确选择加入的同意。

对于现有 skill 的优化，默认使用零个评估代理：先运行确定性检查，如果行为仍存在不确定性，再最多进行一到两次 with-skill 重放。纪律 #5 中的一名全新上下文审查者是发布门槛，并不意味着可以组建审查者团队。关于令牌/成本敏感性的指令会阻止重型流程，直到用户明确撤销该指令。

在生成多于一个研究、挖掘、评估或评分代理之前，先将**角色**与**执行单元**区分开来：

- 每个额外的角色或审查者都必须负责一个不同的失败维度或输出。模板的可用性绝不构成增加另一个角色的理由。
- 必要的实验组和语料分片可以共享一个维度：with-skill 组和基线组需要彼此隔离的上下文，而一个挖掘角色可能需要处理多个有界分块。在启动之前，说明确切的单元总数、并发上限，以及为什么将它们合并会污染比较结果或超出分块预算。默认按串行方式运行；明确的 A/B/挖掘请求只授权这些必要单元，不授权额外角色。
- 对于由执行者而非用户明确要求提出的扇出，应就该数量获得用户同意。如果交互式提问工具不可用，或用户没有回答，则采取较轻量的证据路径；沉默不等于同意。

如果某个单元既不是不同的角色/输出，也不是必要的隔离实验组/分片，则不要生成它。

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，应升级处理。用户要求取消或降低评估级别时，应立即停止已经启动的配对评估代理、基线、评分器、聚合和 viewer 工作。若风险分类仍具有参考价值，则保留该分类，但只报告实际运行的证据以及尚未检查的维度；不要将未运行的重型套件描述为由该标签自动“必需”。当其规则/契约/数量阈值被触发时，不要取消纪律 #5 的单个全新上下文审查者，也不要取消任何为防止破坏性影响或外部影响所必需的安全门禁。机械化的现有 skill 迁移审计、公共 skill 清理，以及任何特定领域的安全门禁，也仍然独立于此路由器。

### 专用工作流：第三方 CLI 工具的 Wrapper Skills

在确定采用通用 skill 创建流程之前，先检查截至此处的会话过程是否实际上要求改用 **wrapper skill** 工作流。wrapper skill 是一种伴随工具，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或 skill 包——也就是由他人编写的代码，而用户刚刚花费了一整个会话才让它在自己的机器上运行起来。

适用信号（任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`、处理官方安装程序。
- 会话中产生了真实、具体的错误消息，且用户和 Claude 已经为此找出了具体的修复方案（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个封装成一个 skill”“把它保存为一个 wrapper skill”“这样其他人就不用再经历这一遍了”“把这次 session 做成一个 skill”的话。
- 用户明确提到了某个第三方工具的名称，并希望其他代理或其他人能够使用它，而不必再经历自己已经付出的学习过程。

不适用的信号（改用上面的通用工作流）：

- 用户想要为某个他们打算从头编写的内容创建 skill。
- 会话进展顺利——没有值得记录的实际摩擦。
- 该 skill 封装的是用户拥有或控制的服务（这是他们自己的代码；应编辑源代码，而不是进行封装）。
- 这个“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当 wrapper skill 工作流适用时，保留上面选定的验证级别。创建 wrapper 就是在创建新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用编写部分；跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流——其任务是从当前对话中提取安装流程、已修复的 bug 以及已经做出的设计决策，并将提取结果转化为一个完整、自包含的 wrapper skill，使其他用户无需重新经历调试会话即可安装并从中受益。

wrapper skill 工作流拥有自己的架构契约、代码模板和 Tier 3 验证协议——由于其输出是用户的安装状态，而不是一个可以轻松断言的文件，因此它会替代不兼容的通用测试用例机制；这并不意味着降低工作标准。运行证据计划所选定的兼容通用步骤；通用的成对评估步骤仍然需要进行繁重评估的授权门控。记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库根目录——这里的裸相对链接在该 skill 移入套件后曾经失效过一次，这正如下面的跨 skill 引用规则所警告的那样），它是一个从真实会话中按照这一工作流提炼出来的 Tencent IMA skill wrapper。

### 专用工作流：从对话历史中丰富 Skill

在开始通用 skill 创建流程之前，先检查当前会话是否实际上是在要求将**过去的对话提炼成一个 skill**。当用户在多次 Claude Code / Codex 会话中一直调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这种方式很有用。

**必须有明确的来源意图。** 长时间进行中的对话、最近完成的调试任务，或 `use skill-creator to optimize <skill>`，都不表示用户同意打开本地历史记录，也不是进入此工作流的理由。对于普通更新，直接使用当前对话。只有当用户明确要求挖掘/提炼更早的本地对话，或指定特定的过往会话作为来源材料时，才进入对话挖掘流程。

适用信号（必须全部满足）：

- 用户明确将本地/过往对话历史指定为输入，例如“挖掘我的聊天记录”“从之前的会话中丰富此 skill”，或“把以前的对话沉淀到 skill 里”。
- 源会话以及时间/范围边界已知或已确认。
- 目标输出是可复用的知识或代码资产，而这些内容无法仅从当前对话和现有 skill bundle 中表达出来。

不适用信号（改用上面的通用工作流）：

- 用户正根据单个提示或想法创建全新的 skill。
- 用户要求优化现有 skill，但没有要求读取过往本地历史记录。
- 相关修正和证据已经存在于当前对话中。
- 用户想要为刚安装的第三方 CLI 工具创建封装器（改用上面的 wrapper-skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的对话记录导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件中。
- 源材料是一批用户已认可的已完成产物，而不是对话——改用下面的 artifact-corpus-distillation 工作流。

当对话挖掘工作流适用时，保留上面所选的验证级别。新挖掘出的 skill 为 Tier 3；丰富现有 skill 时，只有在满足该级别能力边界的情况下，才能保持所选级别。**不要**继续阅读下面的通用编写部分；跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流：它会发现经过批准的本地历史记录，对其进行脱敏和分区，仅运行由语料库决定的挖掘步骤，并在验证后提升经过审查的候选内容。

对话挖掘工作流有自己的架构契约、代理提示词、模板和验证协议。该协议实现了所选级别的专用机制；运行证据计划所选定的兼容通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代方案。它是将经过明确批准的对话历史转化为 skill 可复用知识库的规范方式。

### 专用工作流：从获批准的产物语料库中提炼用户偏好

在采用通用流程之前，检查本次会话是否要求**从一批用户已认可的已完成产物中提取用户的真实偏好**——已批准的 HTML 报告页面、生成的文档、设计稿。这是第三种提炼来源，与前两种不同：材料是**产品，而不是对话**；输出是**可执行的品味**（明确的原则、量化的参数、词汇），而不是知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的成果，并说“这些都是我认可的样例”/“你来学到底什么是我想要的”/“extract my preferences from these approved examples”。
- 某个品味校准技能（报告生成器、文档样式设计器、演示文稿构建器）的认可样例语料库不断增长，而用户要求让技能从中*学习*，而不只是将其编入索引。
- 用户抱怨之前的更新“只加了示例”——只是把样例编目，却没有改变技能的行为。

不适用的信号：源材料是对话/修正内容，而不是得到认可的成品（使用 conversation-mining）；样例并未得到用户亲自认可（认可资格是准入门槛——先询问）。

适用时，保留上面选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新的语料库衍生技能属于第 3 级；向现有技能添加实质性的新决策能力也属于第 3 级。专用协议实现了所选层级的语料库机制，不会降低其层级；按照证据计划运行兼容的通用步骤，将繁重的通用步骤保留在其授权门槛之后，并记录任何替代。其核心纪律同样适用于向现有技能添加材料的任何时候：**编目 ≠ 提炼**——在语料库表中登记样例，不会改变技能下一次运行时的任何行为；对每一项新增内容都要问：“*这是否改变了决策规则？*”，并且在所有写入内容的答案都是否定时，不得宣布提炼会话已完成（方法论案例 15）。该工作流的主线是：针对**所有**成果，通过脚本提取的定量比较（每种模式至少达到 3 个成果的阈值，并对所声称的恒定项检查例外列表）→ 带有证据锚点的分层归纳 → 写入决策规则层（区分不变量与依赖于语域的变量）→ 独立的完整性审计（长期纪律 #5）→ 回归审计。

### 先例研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——正是技能有价值的原因。没有任何公共仓库能够提供这些内容。但用户也不应浪费时间重新发明基础设施（API 客户端、认证流程、速率限制），因为已有成熟工具可供使用。先例研究的目的是为基础设施层寻找可复用的构建模块，让技能能够专注于编码用户独有的方法论。

**两个轴，不要混为一谈。** 本节为*基础设施*层寻找来源（可复用的工具 / MCP / 库 / 现有技能）。*方法论*层本身有两个输入：用户的私有优势（只属于用户本人，无法检索）**以及领域已经确立的最佳实践 / 科学原理；根据长期纪律 #3，默认将后者检索到上下文中。**找到合适的工具，并不能免除第二项要求——一个采用了图表库却从未吸收 Cleveland/Bertin 理论的可视化技能，其能力上限仍然只是你的预训练水平。两者都要做。

**按以下顺序搜索这些渠道。** 默认在行内开展研究。只有在上方的重型评估/代理预算门槛确认确实存在相互独立的未知项之后，才使用子代理；公共来源渠道不是默认的并行搜索包。

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **实时对话或明确批准的历史记录** | 用户已验证的工作流、经过验证的 API 模式、调试期间做出的修正 | 直接使用当前对话。只有在上方的明确来源门槛允许后，才搜索较早的本地历史记录；随后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 针对同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 会发现用户自己的已验证模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终优先——公共工具是构建模块，而不是替代品。在竞争性领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**倾向于合并/扩展，而不是新建，并且要扫描每一个技能根目录——不要只扫描 `~/.claude`。** 当渠道 1-3 发现了与请求领域重叠的现有技能时，通常正确的做法是扩展或合并到该技能中——**但如果它位于无关项目的工作树中，方向则相反：应当从中提取内容，融入你正在构建的技能，而不是合并到其中**（参见上方扩展与新建检查中的项目级案例）（一次真实的“新建技能”任务最终变成了“让现有提取器充当新归档器的提取阶段”），而不是交付一个会与相同触发条件竞争的并行技能——两个相互重叠的技能会争夺触发机会并使用户困惑。搜索时，**应当发现安装根目录，而不是凭记忆列出目录**——使用扩展与新建部分中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会漏掉源代码仓库、市场克隆和插件缓存，因为它们的技能目录以技能名称命名；此外，也会漏掉项目自身的 `.claude/skills/`）。执行覆盖范围检查，不要只相信这句话：**每个项目自身的 `.claude/skills/` 都是凭记忆列出的目录清单最容易漏掉的根目录**，因为项目外部没有任何内容会引用它。用户已经安装在*任何位置*的技能，都是最有力的既有参考，而项目本地技能往往最成熟：它是在真实工作中编写出来的。

**如果发现公共 MCP 服务器或 skill，请克隆并验证——不要相信 README：**

1. **阅读实际源代码** —— 许多项目的 README 写得很完善，但代码库却空洞无物
2. **验证身份验证方式** —— 是否与 API 实际使用的身份验证方式一致？（X-Api-Key 标头、Bearer 还是 OAuth——很多项目在这方面都做错了）
3. **检查测试覆盖率** —— 没有任何测试 = 原型，而不是生产级项目
4. **检查维护情况** —— 最后提交日期、未解决 issue 的数量、对 bug 报告的响应情况
5. **检查环境兼容性** —— 代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证** —— MIT/Apache 没问题；GPL/SSPL 可能与专有软件的使用相冲突
7. **检查依赖负担** —— 庞大的依赖树会带来冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用它，在其基础上构建** —— 安装 MCP，然后将 skill 构建为工作流层，用于编码用户的方法论 |
| 存在部分 MCP 或 SDK | **扩展它** —— 将其用于基础设施，并在 skill 中补齐缺口 |
| 公共 skill 覆盖相同领域 | **仅用于获取结构上的灵感** —— 竞争性领域中的公共 skill 按定义来说都是通用的。用户的优势在于其私有 SOP |
| **存在能够提供你正在构建的功能子能力的互补 skill** | **将其打包** —— 将互补 skill 的自包含资源复制到你的包中，并完成连接。不要依赖用户预先安装该 skill。请参见下方的“互补 Skills” |
| 没有任何公共资源 | **从头构建** —— 在编写完整 skill 之前，先验证 API 访问模式是否可用（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建** —— 一个由你掌控、耗时 2 小时的定制实现，胜过一个集成摩擦大且存在上游风险的“成熟”工具 |
| 用户有意取代已安装的 skill（分支、强化版） | **携带 supersede kit 一起发布** —— 请参见下方的“共存与优先级” |

#### 共存与优先级（有意重叠）

将内容合并到现有 skill 中，是解决重叠问题的默认方式（如上所述）。但当用户*有意*发布一个与已安装 skill 存在重叠的 skill——例如官方插件的分支版本、经过强化的内部版本——这两个条目会以相似的描述出现在 skill 列表中，Claude 将随机在它们之间进行路由。请按以下逐步升级的顺序解决这一问题：如果重叠是意外的，就重命名；添加描述上的决胜说明（“取代 X——当两者同时出现时，始终使用此项”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式 supersede kit 写入 skill——这是一个基于用户同意的 SessionStart 路由钩子，仅在确实存在竞争者的机器上安装，在其他机器上拒绝安装，并且如果任一方消失则自动禁用。具体机制、决策表、SKILL.md 示例措辞和沙箱验证，请参见：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此 skill 也针对官方 skill-creator 插件对同一 kit 进行了实际验证（请参见顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何人为分叉的情况下，悄悄失去了面向*已安装技能集合*的触发机会。** 一个技能的领域（图像生成、PDF 处理、仪表板）通常已经有多个已安装技能，新技能可能会失去面向其中所有技能的自动路由。因此，**要尽早验证触发情况——内容写得好并不意味着构建就完成了。** 草稿完成后，通过 `claude -p` 发送几个符合实际的查询，并检查新技能是否真的能够胜出；如果没有，**指出它输给的具体竞争者**（不同查询可能会输给不同技能）。然后要明确两点：(1) **在竞争拥挤的触发位置中，光靠正文不一定能胜出**——解决阶梯是：重命名 → 通过描述进行平局决胜/SUPERSEDES → 手动调用 → SessionStart 路由钩子（属于结构性方案；会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的纪律）；以及 (2) **修复方式取决于竞争者的作者**——竞争者是*第三方*的 → 接受手动调用或路由钩子；竞争者是*你自己的* → 将它们合并/整合为一个，不要让两个你自己的技能争夺同一个触发条件。（完整的解决阶梯位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要只是指引，不要在其他地方独立扩展。）记录所选择的路径（例如添加一条“激活”说明，写明“手动调用，竞争者是第三方”），可以避免下一次会话重新争论这一问题。（方法论案例 13）

##### 互补技能（打包，而不是依赖）

当构建的技能涉及某个已有互补技能的领域时，你有两个选择：

- **依赖该技能已安装**：脆弱——用户可能没有安装它，或者安装的是不同版本。每一次依赖缺失导致的失败，追根溯源都源于这一选择。
- **将其打包**：将互补技能的自包含资源（脚本、模板、参考文档）复制到你自己的包中，并完成连接配置，使你的技能能够独立工作。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包。** 这一点对以下内容尤其重要：
- 状态栏 / UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证 / 清理脚本
- 通用的数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要状态栏。`statusline-generator` 技能提供 `generate_statusline.sh`。与其依赖用户先运行 `statusline-generator`，不如让配置文件设置技能打包 `statusline.sh`，并在 `claude-profiles-init` 期间将其连接到每个新配置文件中。这两个技能仍然可以独立发挥作用，但包装技能能够独立运行。

**反模式**：在你的 SKILL.md 中写下“先运行 `other-skill` 的安装程序”。这会将依赖转嫁给用户，并造成脆弱的安装顺序。请改为打包。

研究完成后，通过 **AskUserQuestion** 呈现研究结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如果无法确定，倾向于为基础设施层采用成熟的基础设施来处理底层连接和管道，并在其上构建自定义的方法论层——价值就在这里。

### 访谈与研究

主动询问有关边界情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在这部分内容敲定之前，不要开始编写测试提示词。

在研究有帮助时检查可用的 MCP（搜索文档、查找类似的 skill、了解最佳实践）。默认以内联方式进行研究。仅针对独立且尚未解决的问题使用子代理，绝不要将工具可用性自动转化为并行扩散。准备好相关上下文，以减轻用户负担。

### 编写 SKILL.md

根据用户访谈，填写以下组件：

- **name**：Skill 标识符
- **description**：何时触发，以及它的功能。这是主要的触发机制——同时包含 skill 的功能和具体的使用场景。所有“何时使用”的信息都应放在这里，而不是正文中。注意：目前 Claude 有倾向于“触发不足”——在 skill 有用时不使用它。为应对这一点，请让 skill 描述稍微“积极主动”一些。例如，与其写“如何构建一个简单快速的仪表板，用于展示 Anthropic 的内部数据”，不如写“如何构建一个简单快速的仪表板，用于展示 Anthropic 的内部数据。只要用户提到仪表板、数据可视化、内部指标，或想要展示任何类型的公司数据，即使他们没有明确要求构建‘仪表板’，也务必使用此 skill。”

  **请控制长度：description 有严格的 1024 个字符上限，验证会拒绝超出限制的内容。** 这与上述“积极主动”建议直接矛盾——你添加的每个触发短语都会消耗覆盖范围预算，因此请先测量再扩展，而不要凭感觉行事：使用 `len(description)`，而不是凭感觉判断。陷阱不在于第一版（它通常离上限还很远），而在于多年后的更新：当新增触发词以覆盖最近支持的范围时，一个成熟的描述往往已经距离上限只剩几十个字符，此时**添加一个触发词是零和博弈——你必须删除已有的一个触发词来为它腾出空间。** 请有意识地进行这种取舍，并在提交信息中说明，因为无意中删除触发短语会实际缩小 skill 的触发范围，而在它不再为某人触发之前，没有人会注意到这一点。（实践中曾出现过这样的情况：一次更新为新覆盖的故障模式添加了触发词，使 description 达到 1280 个字符，随后经过两轮压缩才降到 1003 个字符——代价是删除了三个已有的触发短语；这本应是一个需要明确说明的决策，而不是在与验证器斗争时才被发现。）必须删减时，优先删除那些仍可通过同义词或同级短语触达其场景的短语，保留那些没有其他入口的短语，并记住，正文中的限定语（例如“在平台 X 和 Y 上”、括号内的列举）通常比独立的触发短语更容易删除——正文可以重新推导出来，而触发短语无法重新推导。
- **compatibility**：所需工具、依赖项（可选，极少需要）
- **skill 的其余部分 :)**

### Skill 编写指南

#### Skill 的构成

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。通过在 `---` 标记之间配置以下字段来设置 skill 行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必需 | 描述 |
|-------|----------|-------------|
| `name` | 否 | skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 建议设置 | skill 的功能以及使用时机。Claude 使用此字段来决定何时应用该 skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在 fork 的子代理上下文中运行。** 请参阅下方的“Inline 与 Fork：关键决策”——选错会导致 skill 无法正常工作。 |
| `agent` | 否 | 在设置 `context: fork` 时要使用的子代理类型。可选项包括 `Explore`、`Plan`、`general-purpose`，或来自 `.claude/agents/` 的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 以阻止 Claude 自动加载此 skill。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false` 以从 `/` 菜单中隐藏。适用于用户不应直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略该字段可让 skill 在用户权限设置的约束下获得完整的工具访问权限。设置该字段会不必要地限制 skill 的能力。 |
| `model` | 否 | 此 skill 激活时使用的模型。 |
| `argument-hint` | 否 | 自动补全时显示的提示，用于指示预期参数。例如：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此 skill 生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** skill 内容中的 `$ARGUMENTS` 会被用户在 skill 名称后提供的文本替换。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### Inline 与 Fork：关键决策

**这是设计 skill 时最重要的架构决策。** 选错会导致 skill 的核心能力静默失效。

**关键限制：子代理不能再创建其他子代理。** 使用 `context: fork` 运行的 skill（作为子代理）**不能**：
- 使用 Task 工具创建并行探索代理
- 使用 Skill 工具调用其他 skill
- 编排任何多代理工作流

**决策指南：**

| 你的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **Inline**（无 `context`） | 子代理无法生成子代理 |
| 调用其他 skill（Skill 工具） | **Inline**（无 `context`） | 子代理无法调用 skill |
| 运行 Bash 命令来执行外部 CLI | **Inline**（无 `context`） | 主上下文中拥有完整的工具访问权限 |
| 执行单个专注任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境干净 |
| 提供参考知识（编码约定） | **Inline**（无 `context`） | 指南可丰富主对话 |
| 被其他 skill 调用 | **Fork**（`context: fork`） | 必须作为子代理才能被生成 |

**编排器 skill 示例（必须使用 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专用 skill 示例（使用 fork 是正确的）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，无 task）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skills 应当是**正交的**：每个 skill 负责一个关注点，并通过组合协同工作。

**模式：编排器（inline）调用专用 skill（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（不能使用 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个 skill 只有一个职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法论，而不是重复代码

##### 流水线交接（顺序 Skill 链式调用）

除了编排器/专用 skill 组合之外，skills 通常还会组成**顺序流水线**，其中一个 skill 的输出是下一个 skill 的输入。每个 skill 在完成工作后，都应主动建议逻辑上的下一步。

**模式：SKILL.md 末尾的“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**现实世界的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
read-claude-code-history → continue-claude-code-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion **主动选择**——绝不能在未询问的情况下自动调用下一个 skill
2. 仅在输出自然地作为另一个 skill 的输入时才提出建议——不要强行建立关联
3. 包含一个“不了，谢谢”选项——用户可能不需要完整的流水线
4. 建议中应解释下一步**为何有帮助**（例如：“ASR 输出通常包含识别错误”）
5. 最多提供 1–2 条建议——选择过多会导致决策疲劳

**何时添加交接：**询问“这个 skill 的输出是否通常会成为另一个 skill 的输入？”如果是，则添加“下一步”部分。如果这种关联很少见或牵强，则不要添加。

**反模式：**串联没有自然数据流的 skills。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**绝不要为可以自动检测的能力添加手动标志。**不要要求用户传递 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力自动检测，范围由用户决定。skill 应发现自己能做什么并据此行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | You can invoke | Claude can invoke | Subagents can use |
|-------------|----------------|-------------------|-------------------|
| (default) | Yes | Yes | No (runs inline) |
| `context: fork` | Yes | Yes | Yes |
| `disable-model-invocation: true` | Yes | No | No |
| `context: fork` + `disable-model-invocation: true` | Yes | No | Yes (when explicitly delegated) |

#### 渐进式披露

Skills 使用三级加载系统：
1. **元数据**（名称 + 描述）——始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文**——skill 触发时始终位于上下文中
3. **随附资源**——按需加载（数量不限，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。一个没有冗余内容的 600 行 skill，优于一个遗漏关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问自己：“每个部分都发挥了应有的作用吗？”如果是，就保留它。如果某些部分内容充斥冗余，或解释了 Claude 已经知道的事情，就删减这些部分——不要删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分到不同的参考文件中，而不是为了压缩主文件长度而强行塞在一起。
- 对于现有 skill，渐进式披露是一种重新定位策略，而不是删除启发式规则。旧的运行时契约必须仍可从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或评审者记忆都不能替代运行时契约。
- 在 SKILL.md 中清晰地引用参考文件，并说明何时阅读这些文件
- 对于较大的参考文件（超过 300 行），应包含目录

**领域组织**：当一个 skill 支持多个领域/框架时，应按变体组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的 reference 文件。

#### 不出意外原则

这点不言自明，但 skill 不得包含恶意软件、漏洞利用代码，或任何可能危及系统安全的内容。如果对 skill 的内容进行描述，不能让用户对其意图感到意外。不要迎合创建具有误导性的 skill，或旨在协助未经授权的访问、数据外泄或其他恶意活动的请求。不过，“扮演某个 XYZ”之类的内容是可以的。

#### 编写模式

指令应优先使用祈使句。

**定义输出格式**——可以这样写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——加入示例很有用。你可以像下面这样进行格式化（不过，如果示例中出现 "Input" 和 "Output"，你可能会想稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得构建到 skill 中的可用性模式**——以下四个结构元素反复将“能用但令人困惑”的 skill 变成用户真正能够使用的 skill——它们是让一个被广泛使用的 skill 变得易用的具体增强措施。因此，当 skill 具有多种模式、会运行命令或可以重复运行时，应考虑采用这些模式：
- **入口决策树**：如果 skill 有多种模式，开头应提供一个简短的“用户说了 X → 使用模式 Y”映射，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧接在命令之后展示“你应该看到什么”，这样模型和用户都能区分真正的成功与无提示失败。
- **故障排查部分**：列出已知的失败模式及其修复方法——对于其他将在你无法查看的机器上运行的 skill，这是最有价值的部分。
- **第 0 步幂等性保护**：如果重复运行可能会重复已完成的工作，应先执行一个成本低廉的“是否已经完成？”检查，然后再进行任何耗时操作。

### 编写风格

尝试向模型解释事情为何重要，而不是大量使用强硬、陈旧的 MUST。运用心智理论，并尽量让 skill 具有通用性，不要过度局限于特定示例。先写出草稿，然后以全新的视角重新审视并改进它。

### 日期和版本引用

**保留事实性日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 skill 应写成“Suno v5.5（2026 年 3 月）”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期只会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 2025 年 8 月，则使用旧 API”）——日期一旦过去，这种逻辑就会失效，而且没有人会更新它。

规则：
- **发布日期、“最后验证”日期**：保留。它们是参考时间点，而不是过期日期
- **定价、排名、法律状态**：包括在内，但标记为易变信息（“截至上次检查约为 ~$0.035/gen”），以便读者知道需要重新验证
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠/已弃用部分记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当相同代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省令牌、具有确定性，并且无需加载到上下文中即可执行
- **注意**：Claude 可能仍需读取脚本，以便进行修补或针对环境进行调整
- **用户可变数据存放在捆绑包之外**：如果脚本会累积用户数据（纠正词典、学习到的偏好、缓存），请将其存储在稳定的、相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其单独创建备份 — 切勿将其存放在 skill 目录内。每次更新和套件迁移都会删除并重新创建 skill 安装内容，而相对于主目录的存储会原封不动地保留下来。这正是一个会累积词典的 skill 能够在完整套件迁移后实现用户数据零丢失的原因

##### 参考资料（`references/`）

旨在根据需要加载到上下文中，以便为 Claude 的流程和思考提供信息的文档与参考材料。

- **何时包含**：当 Claude 工作时需要参考文档时
- **示例**：用于金融数据模式的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库模式、API 文档、领域知识、公司政策、详细的工作流指南
- **优点**：保持 SKILL.md 简洁，仅在 Claude 判断需要时加载
- **最佳实践**：如果文件较大（>10k words），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或 references 文件中，不要同时存放在两者中

##### 资源（`assets/`）

不旨在加载到上下文中，而是供 Claude 在其生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用的文件时
- **示例**：用于品牌资源的 `assets/logo.png`，用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件架**：对于生成 artifact 的 skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、可逐字嵌入的片段，这些片段具有冻结的行为契约和注册表引用 — 参见步骤 4 中的组件架检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标受众。**以下内容描述的是 skill 向陌生人发布时会出现的问题。对于存放在作者自己的私有
repo 中的 skill，同样的“违规”通常正是它能够正常工作的原因 — 真实的绝对路径能让脚本可运行，模板中的真实账户能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 所在的包含仓库是否为私有仓库），并在此情况下将可移植性/标识符相关发现降级为备注；在准备发布私有 skill 时，`--audience=public` 会强制执行严格检查。

**对于私有 skill，这些事项由所有者决定，而不是由你决定。** 不要擅自将真实路径替换为占位符、改写硬编码凭据，或在未询问的情况下“清理”示例——你会为了满足一条原本针对另一个发布目的而编写的规则，破坏一个正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，并让所有者决定。（设计先例是 npm 的 `"private": true`：这是一个已声明的目标，它会改变工具强制执行的规则；之所以添加它，是因为人们总是不小心发布内容。）

**面向公开分发的 skill 的关键要求**——这些 skill 不得包含特定于用户或公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，如 `~/.claude/skills/`
- **允许**：skill 包内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（如果验证器严格按字面实现禁止列表，就会将这个 skill 本身标记为有问题——对正常输入误报，比漏报更糟）：当发布者自己的名称/品牌是解决 supersede 平局或进行归属说明所必需的时，可以使用；当段落讨论这些路径本身时，可以使用类似 `~/.claude/skills/` 的安装路径（这是教学材料，而不是硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于当前 skill 自己的包内”——验证器和读者都会这样理解，因此，指向另一个 skill 文件的裸路径会验证失败，并误导读者。指向另一个 skill 时，应在正文中注明其所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用带命名空间的名称调用 skill（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。当 skill 在不同 suite 之间迁移时，裸的跨引用会静默失效——有一次 suite 迁移就导致两个清理阶段中出现了 21 个失效的跨引用。

##### 版本管理

**关键要求**：SKILL.md 不应包含版本历史或版本号：

- **禁止**：在 SKILL.md 中添加版本章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **理由**：Marketplace 基础设施负责版本管理；SKILL.md 应包含不随时间变化的内容

#### Reference File 命名

文件名必须无需阅读内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：仅从文件名本身，是否有人就能理解文件的内容？

有两个例外：连字符命名和下划线命名同样合适（分隔符从来都不是重点——关键在于能够自我说明）；位于命名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已经通过目录获得了限定信息，重命名它们会破坏各工作流之间的并行结构。

### 完整评估测试用例（仅限单独授权的配对计划）

只有在重型评估授权门禁通过后，才能进入本节。风险等级本身既不会授权也不会禁止使用这些证据；明确的全流程请求不会重新归类底层变更。不要仅仅因为 SKILL.md 发生了变更就使用本节。专用工作流遵循其上方声明的替代约定。

编写 skill 草稿后，提出 2-3 个现实的测试提示词——也就是实际用户真正可能说的话。**对于作用于实时系统（正在运行的服务、已登录的客户端、生产数据）的 skill，请为每个测试提示词明确副作用预算**——例如“进行只读探测并得出结论；不要执行下载 / 驱动 UI”。在“只是测试”时修改实时环境是真实操作，而不是测试。通过 **AskUserQuestion** 展示这些测试：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——在运行进行期间的下一步中再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整架构请参阅 `references/eval_pipeline_schemas.md`（包括稍后添加的 `assertions` 字段）。

## 完整配对评估流程（仅限单独授权）

只有在重型评估授权门禁通过后，才能运行本节。风险等级仍以变更所对应的行为为准。按具有决策意义的阶段执行流程，并在不确定性或所请求的基准交付物得到解决后停止；不要预先启动下游评分器、聚合或查看器工作。用户取消或降低级别会立即停止重型流程。未经授权不得使用本流程，也不要机械地添加专用工作流已明确替代的通用机制，并且不要使用 `/skill-test` 或任何其他测试 skill。

将结果放入 `<skill-name>-workspace/`，使其与 skill 目录处于同级。在 workspace 中按迭代组织结果（`iteration-1/`、`iteration-2/` 等），每个迭代中，每个测试用例分别使用一个目录（`eval-0/`、`eval-1/` 等）。不要一次性预先创建所有目录——只需随着进展创建目录。

### 步骤 1：运行已批准的 with-skill / baseline 配对

对于每个已批准的测试用例，在相同的提示词和副作用预算下，运行一个 with-skill 样本及其 baseline。这两个分支有意共享同一失败维度，但要求使用相互隔离的上下文；它们是必要的实验单元，而不是额外的审查者角色。启动前说明总分支数和并发上限。默认串行运行，且绝不得超过授权的单元数。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（使用相同提示词，但 baseline 取决于上下文）：
- **创建新 skill**：完全不使用 skill。使用相同提示词，不提供 skill path，将结果保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用强制性的 existing-skill regression gate 在首次编辑前捕获的旧版本。将 baseline subagent 指向该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 重建权威 baseline 后再继续；绝不要将已经编辑过的目录用作旧 baseline。**明确该比较能够解决的问题：它只能衡量本轮的变化。** 如果你最想验证的能力已经存在于编辑前快照中——某个 sibling session 可以在你开始之前准确提交该修复——那么 with/old A/B 对此完全没有判别力；应选择更早的 ref 作为 baseline，以测试该能力。

为每个测试用例编写一个 `eval_metadata.json`（暂时可以为空 assertions）。根据每个 eval 测试的内容，为其指定描述性名称——不要只使用“eval-0”。同时将此名称用于目录名。如果本轮使用了新的或修改后的 eval 提示词，请为每个新的 eval 目录创建这些文件——不要假设它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：运行进行期间起草 assertions

不要只是等待运行结束——可以利用这段时间开展有价值的工作。为每个测试用例起草定量 assertions，并向用户解释这些 assertions。如果 `evals/evals.json` 中已经存在 assertions，请检查它们并解释其检查内容。

好的 assertions 应当能够客观验证，并具有描述性名称——在 benchmark viewer 中应当清晰易懂，使查看结果的人一眼就能明白每条 assertion 检查的内容。**应针对意图编写 assertions，而不是针对字面上的工具路径**——例如“语音内容保留在答案中”，而不是“调用经过批准的 reader script”。如果某次运行通过另一条经过批准的路径实现了该意图（例如读取一个已经内嵌 transcript 的归档文件），就应判定为通过；将其判定为字面路径失败会制造错误的负面结果，之后还会导致你在错误的位置进行“修复”。主观性较强的 skill（写作风格、设计质量）更适合进行定性评估；不要强行为需要人工判断的内容设置 assertions——其实际验证路径（历史任务重放、带有回写习惯的 production-as-eval、渲染后人工审查）列在“Capture Intent”的问题 4 下。

起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。还要向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试。

### 步骤 3：随着运行完成，记录计时数据

每当某个子代理任务完成时，你都会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们会通过任务通知传入，且不会在其他地方持久化。通知到达后要立即处理，而不是尝试批量处理。

### 步骤 4：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分**——启动一个评分子代理（或直接评分），读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是凭肉眼判断——脚本速度更快、更可靠，并且可以在多次迭代中复用。**但客观的 grep/脚本断言也可能产生双向误导**（相同词语但含义不同导致的误命中、措辞差异导致的漏检），因此**基准测试通过率是一项信号，而不是最终结论**：要抽查每条断言实际匹配到的内容，并留意某次基线运行是否暴露出 skill 本身存在事实错误（即“等等，API 中确实有这些数据”时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **聚合为基准测试**——从 skill-creator 目录运行聚合脚本：
   ```bash
   uv run --frozen python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及均值 +/- 标准差和差值。如果手动生成 benchmark.json，请参见 `references/eval_pipeline_schemas.md`，了解查看器所需的确切架构。将每个 with_skill 版本放在其对应的 baseline 版本之前。

3. **进行分析员检查**——读取基准测试数据，并找出聚合统计数据可能隐藏的模式。请参见 `agents/analyzer.md` 中的“Analyzing Benchmark Results”部分，了解需要关注的内容——例如无论是否使用 skill 都始终通过的断言（无区分度）、高方差的评估（可能不稳定），以及时间/令牌的权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   cd <skill-creator-path>
   nohup uv run --frozen python eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器自行失效**：进程仍在运行，但没有任何程序在监听 — 使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或 curl 该 URL（失败）；这里“没有日志输出”不是可用的信号，因为上面的启动命令已将其重定向到 `/dev/null`。终止该进程，并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或者环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击 "Submit All Reviews" 时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** **告知用户**：

```
结果已准备就绪！我已在浏览器中打开评估查看器。

- "Outputs" 选项卡：逐个点击每个测试用例，并在文本框中留下反馈
- "Benchmark" 选项卡：查看量化比较（通过率、耗时、token 数量）

请慢慢进行查看。完成后返回这里。

建议：先查看 "Outputs" 选项卡 — 与数字相比，你的定性反馈对下一次迭代的推动作用更大。

选项：
A) 我已完成查看 — 读取我的反馈并改进 skill
B) 在提供反馈前，我对结果有一些问题
C) 结果已经足够好 — 跳过迭代，我们来打包 skill
D) 结果需要重大返工 — 在迭代前先讨论
```

### 用户在查看器中看到的内容

"Outputs" 选项卡一次显示一个测试用例：
- **Prompt**：提供的任务
- **Output**：skill 生成的文件，在可能的情况下以内嵌方式渲染
- **Previous Output**（第 2 次及后续迭代）：显示上一次迭代输出的折叠区域
- **Formal Grades**（如果运行了评分）：显示断言通过/失败情况的折叠区域
- **Feedback**：输入框，输入时会自动保存
- **Previous Feedback**（第 2 次及后续迭代）：显示在输入框下方的用户上次评论

"Benchmark" 选项卡显示统计摘要：每个配置的通过率、耗时和 token 使用量，以及各评估项的详细分解和分析人员的观察结果。

可以通过上一个/下一个按钮或方向键进行导航。完成后，点击 "Submit All Reviews"，所有反馈将保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告知你已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"

```

空反馈表示用户认为结果没问题。将改进重点放在用户提出了具体意见的测试用例上。

完成后终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进 skill

这是循环的核心。根据证据计划进行改进：对于 Tier 1，使用权威事实和确定性检查；对于 Tier 2，使用 1–2 个具名行为重放；或者在单独的重型评估门控于任意层级授权时，使用经过用户审查的成对结果。未经授权，不要将成对评估产物引入默认的 Tier 1/2 路径。

### 如何思考改进

1. **从反馈中归纳。** 这里发生的事情，从宏观上看，是我们正在尝试创建可以在许多不同提示中使用一百万次（也许确实如此，甚至更多，谁知道呢）的 skill。现在你和用户只是反复迭代少数几个示例，因为这样推进得更快。用户对这些示例了如指掌，因此可以快速评估新的输出。但如果你和用户共同开发的 skill 只能适用于这些示例，那它就是没用的。不要加入琐碎、过拟合的修改，也不要加入压制性很强的 MUST；如果某个问题顽固存在，可以尝试换用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，说不定就能得到很好的结果。

2. **保持提示精简，但不要删除契约。** 删除那些没有发挥作用的内容，但要把对现有 skill 的每次删除都视为潜在回归，直到旧版与新版的审计对其进行分类。将详细但可复用的行为移入直接链接的参考资料中；不要只把它留在评估结果、变更日志或你的记忆里。阅读完整的交互记录，而不只是最终输出——如果 skill 导致了低效的工作，就简化指令，并重新运行旧能力用例，而不要想当然地认为字数越少行为就越好。

3. **解释原因。** 尽力解释你要求模型执行每件事背后的 **原因**。如今的 LLM *很聪明*。它们具备良好的心智理论，在获得良好 harness 的情况下，能够超越机械地遵循指令，真正促成事情发生。即使用户的反馈简短或带有挫败感，也要努力真正理解任务，理解用户为什么这样写、实际写了什么，然后将这种理解传达进指令中。如果你发现自己在用全大写的 ALWAYS 或 NEVER，或使用非常僵化的结构，这是一个需要警惕的信号——如果可能，应当重新表述并解释推理过程，让模型理解你所要求之事为何重要。这是一种更人性化、更强大也更有效的方法。

4. **寻找重复的工作——既要查看评估交互记录，也要查看提炼 skill 所依据的对话。** 阅读测试运行的交互记录，注意各个子代理是否都独立编写了相似的辅助脚本，或是否都采用了相同的多步骤方法来处理某件事。如果 3 个测试用例最终都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈信号，说明 skill 应该将该脚本打包进去。只需编写一次，将其放入 `scripts/`，并告诉 skill 使用它。这样可以避免每次未来调用都重新发明轮子。在你提炼 skill 所依据的源对话中，也隐藏着同样的信号——该会话哪怕只写过一次的代码，未来每次运行都必须重新编写；不要等到评估运行证明了重复性才采取行动（那些跳过评估循环的 skill 永远不会获得这类证明——创建流程第 4 步中的 Scripts 检查点正是捕捉这类问题的地方）。

5. **逐字将修正写回——在同一会话中，同时写回两个层级。** 对于经过品味校准的技能，用户的修正就是评测集，但前提是这些修正被写入未来运行时会读取的位置。以下两个属性可以让写回过程逐渐收敛：(a) **逐字记录修正**，不要转述——确切措辞包含了摘要会抹平的校准信号（“绝对禁止这种东西”传达的是一条硬边界；“用户更喜欢少跳转”则不是）。将用户的话引用到它们所修正的规则中，并注明日期。(b) **在修正发生的同一会话中，同时写回两个层级**——修复产物以及技能的规则/参考资料/组件；只修复产物的修正对所有未来运行都不可见，而推迟到“之后”的修正通常永远不会落地。在写回时，检查技能自身的文本是否*教导了*刚刚被禁止的反模式——修正往往意味着现有指令是错误的，而保留旧建议必然会导致问题再次发生（真实案例：一个决策页面契约建议使用跳转式的“goto 锚点跳到被引用的图表”；用户明确禁止了这种做法，因此写回时必须修改旧句子，而不能只是在旁边新增一条规则）。当被修正的内容是一个交互片段时，写回的最后一步是将其提升到组件货架——参见第 4 步中的 Component-shelf check。

这项任务相当重要（我们正努力在这里创造每年数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，认真斟酌。我建议先起草一版修订稿，然后重新审视并加以改进。请尽最大努力设身处地理解用户想要什么、需要什么。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据确实留下了选择空间时才提问。对于 Tier 2 或 Tier 3，当用户反馈暴露出有意义的设计分歧时，请通过 **AskUserQuestion** 提出改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险层级，因为这会改变实施范围；选择 D 则不会。每个选项只授权其中明确列出的范围/证据变更。除非明确列出且通过单独的重型评测/扇出门槛，否则该选项并不授权配套基线、评分器、基准测试、查看器或额外角色。

### 迭代循环

改进 skill 后：

1. 将改进应用到 skill
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **Tier 1 默认设置：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配的子类型证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归测试。除非单独授权了配对计划，否则不要创建迭代工作区。
   - **Tier 2 默认设置：**仅重新运行同样的 1–2 个指定的 with-skill 示例和窄范围检查。除非单独授权了配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任意层级单独授权的通用配对运行：**将所有获批的测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 skill，基线始终是 `without_skill`；对于现有 skill，不可变的原始编辑前版本在每次迭代中都仍然是保留基线。紧邻的上一轮迭代可以作为补充，但绝不能替代原始基线。
3. 在实质性规则、契约或数值发生变化后，执行规范 #5。对于单独授权的通用配对运行，还要使用指向上一轮迭代的 `--previous-workspace` 启动评估审查器；专用工作流使用其声明的审查器机制。
4. 对于单独授权的通用配对运行，等待用户审查新的查看器结果；否则根据默认层级的证据作出判断，除非仍然存在确实需要用户选择的事项。
5. 读取新的证据或反馈；如果它证伪了当前版本，则再次改进，并在同一层级重复执行。

用户请求的取消或降级在任务剩余期间持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（所有内容看起来都很好）
- 你没有取得有意义的进展

## 高级：盲比较

当你希望更严格地比较 skill 的两个版本时（例如，用户询问“新版本真的更好吗？”），可以使用盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。其基本思路是：将两个输出交给一个独立代理，但不告知它哪个对应哪个版本，让它判断质量。然后分析获胜者胜出的原因。

这是可选步骤，需要使用子代理，而且大多数用户都不需要它。通常情况下，人工审查循环已经足够。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某项 skill 的主要机制。创建或改进 skill 后，应提供优化 description 的选项，以提高触发准确性。

### 步骤 1：生成触发评估查询

创建 20 条评估查询，其中应混合包含应该触发和不应该触发的查询。将其保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实可信，是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要使用抽象请求，而应使用具体、明确且包含足够详细信息的请求。例如，可以包含文件路径、用户工作相关的个人背景、列名和值、公司名称、URL 等。可以加入一些背景信息。有些查询可以使用小写、缩写、拼写错误或随意的口语表达。长度应有所不同，并重点关注边界情况，而不是只编写一眼就能判断的查询（用户之后会有机会确认这些查询）。

不佳：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

良好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应该触发**的查询（8-10 条），请考虑覆盖范围。你需要针对同一意图使用不同的表达方式——有些正式，有些随意。包括用户没有明确提及该 skill 或文件类型，但显然需要使用它的情况。加入一些不常见的使用场景，以及该 skill 会与另一个 skill 产生竞争、但应该由该 skill 胜出的情况。

对于**不应该触发**的查询（8-10 条），最有价值的是近似匹配案例——这些查询与该 skill 共享关键词或概念，但实际需要的是不同的功能。请考虑相邻领域、含义模糊且朴素的关键词匹配可能会触发但实际上不应触发的表达，以及查询涉及该 skill 能处理的内容、但在当前场景下更适合使用其他工具的情况。

关键是要避免：不要让不应该触发的查询显得明显无关。将 `"Write a fibonacci function"` 作为 PDF skill 的否定测试过于简单——这无法真正测试任何内容。否定案例应当确实具有迷惑性。

### 步骤 2：与用户审查

使用以下 HTML 模板向用户展示评估集：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目组成的 JSON 数组（不要在其周围加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 当前的 description
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中的最新版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期查看进度。”

将评估集保存到工作区，然后在后台运行：

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（即为当前会话提供支持的模型），这样触发测试才能匹配用户实际体验到的效果。

运行期间，定期查看输出末尾的内容，向用户更新当前进行到哪一次迭代，以及分数表现如何。

这会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后根据失败情况调用 Claude 提出改进方案。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每次迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试集分数而不是训练集分数选出，以避免过拟合。

**如果检测到完全静默，循环会在第 1 次迭代后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中的代码级保护，而不仅仅是建议；它可以区分“第 1 次迭代中每个应触发查询都完全没有触发”这一情况的两种原因：

- `exit_reason: "infra_error: ..."` —— 某些查询执行（无论是应触发查询还是不应触发查询）抛出了异常（`claude` CLI 不在 PATH 中、超时时间太短、网络中断），而不是正常返回“未触发”。该检查**优先执行**，并且会在任何非零错误数量下触发，即使几十次运行中只有一次偶发失败也会触发——崩溃无论多么罕见，都比“什么都没触发”更具体、更容易采取行动，而修复方向应是环境问题，而不是重写描述。消息中的比例（例如 `3/15`）用于表示严重程度：比例较大意味着“停止运行，修复环境”；比例较小，同时伴随大量干净的 0 触发运行，则意味着环境可能存在一个值得检查的轻微偶发问题，**并且**描述可能确实很糟——两方面都要检查。无论哪种情况，都要检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` —— 只有在上面的分支排除了所有执行错误后才会检查这一项，因此这意味着每个应触发查询和不应触发查询都确实运行了，但仍然全部触发了 0 次（这正是通过零分母默认值计算出的“precision=100%”实际意味着的情况：不是“完美”，而是“没有可供相除的数值”）。探针实际上没有测量到任何东西——在完全触碰描述之前，先去诊断竞争性冲突或低阈值领域（见下文）。

这两项检查**仅针对第 1 次迭代**运行，并且**仅在应触发查询全部未触发时**运行——第 1 次迭代较弱但并非零触发（例如 1/9 次触发）是另一种可能可以恢复的情况，因此会继续进行迭代。`degenerate_harness` 还要求不应触发查询也全部未触发：如果描述只是极性反转——漏掉了每个正例，同时意外匹配了多个负例——那么就证明探针确实有效，`improve_description` 也确实有可利用的梯度，因此保护机制不会中止这种情况（它只会中止真正失效的探针）。此外，它还要求任一侧都没有执行错误——一个抛出异常的不应触发查询实际上并未运行，因此不能用它的“0 次触发”来证明探针失效；这正是该情况会被路由到 `infra_error` 的原因。无论哪种情况，流程都会立即中断，并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因才是信号，表明这次运行的数值不应被解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了一个完整的 5 次迭代循环；连续两次完整迭代——每次都是完整的评估批次，耗费数分钟的实际时间，并调用了数十个 `claude -p` 子进程——都返回 precision=100%/recall=0%/相同的分数，直到有人查看这些数值；每个应触发查询和不应触发查询都完全没有触发。仅凭第 1 次迭代就可以诊断出失败；第 2 次及之后的迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会显示一个横幅，因此浏览器视图会携带与 JSON/stderr 相同的信号，而不只是通过这两个可见度较低的渠道传递。（该保护机制的早期草案只检查应触发查询的触发情况；两轮独立审查——每轮都使用一个新的代理，第二轮检查第一轮的修复，而不是重新覆盖旧内容——构造出了极性反转反例、基础设施问题与描述问题之间的歧义、不应触发一侧的错误遗漏，以及过程中发现的一个既有的 `--holdout 0` 报告崩溃问题；这些问题在发布前都已修复。）

这个防护机制无法覆盖一种情况：当使用 `--runs-per-query 1`（默认值为 3）时，一个本应触发的查询如果实际触发率确实在 50% 左右，那么仅凭随机因素，它就有相当概率读到 0/1，并因噪声触发防护机制，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询的每次重复运行都为零”成为强信号的原因——如果你将其覆盖为更低的值，这个防护机制产生误报的风险也会随之上升。

**在信任 `best_description` 之前，先对测试框架做合理性检查——即使上面的两个防护机制都没有触发，它仍可能返回空洞的输出。** 两项检查只能捕获第 1 次迭代时的*完全失败*；测试框架也可能在全部 5 次迭代中持续保持微弱但非零的信号，而始终不触发其中任何一项。如果在第 1 次迭代之后，每次迭代都报告 **召回率仍接近 0%，且分数完全相同或几乎相同**，那就是防护机制无法排除的同一个根本问题——“胜出”的描述通常只是第 1 次迭代结果原样不变的噪声。在应用任何 `best_description` 之前，亲自运行一个显然应该触发的查询，并确认召回率 > 0。跨迭代保持不变的召回率结果意味着测试框架是一个隐藏变量（常见情况是：该技能在触发时输给了已安装的竞争技能——见下文的 *共存*）——不要应用它的“最佳”结果；请手动编写描述，并使用真实探针对其进行验证。（方法论案例 12、14）召回率为 0 还有第二个根本原因，与输给竞争技能不同：该技能的任务领域属于*低阈值*领域——模型自己就会完成任务，从不查阅任何技能——这在下文 *技能触发机制的工作原理* 末尾有详细说明。在采取行动之前，请区分这两种情况，因为修复方式正好相反：竞争技能问题通过优先级/取代关系修复，而低阈值领域则应彻底放弃触发探针，改用面向生产环境的评估方式。

**当你使用 `claude -p` 自行探测触发情况时，请收集本次运行中的所有技能调用，而不只是第一次调用——并记住，工具调用只是一个代理指标。** `UserPromptSubmit`/`SessionStart` 钩子可能会在模型做出选择之前注入一个无关技能，因此“第一次出现 Skill 调用就退出”的探针会错误报告“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“该技能的内容是否影响了输出”（模型可能读取了技能，却没有可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你针对错误的结论持续优化。

### 技能触发机制的工作原理

理解触发机制有助于设计更好的评估查询。技能会以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某个技能。需要了解的重要一点是，Claude 只会针对自己无法轻松处理的任务查阅技能——像“读取这个 PDF”这样简单的单步查询，即使描述完全匹配，也可能不会触发技能，因为 Claude 可以使用基础工具直接处理这些任务。复杂的、多步骤的或专业化的查询，在描述匹配时能够可靠地触发技能——但有一个系统性例外（低阈值任务领域），本节末尾会对此进行说明。

这意味着你的评估查询应当足够具体、内容足够充实，让 Claude 确实能从查阅 skill 中受益。像“读取文件 X”这样简单的查询是很差的测试用例——无论描述质量多高，它们都不会触发 skill。

**但有些 skill 无法通过这个测试，原因在于任何查询改写都无法解决这一点——该 skill 的全部*职责*就是执行低门槛任务。** 上面的段落将问题归咎于查询（“写一个更具体的查询”）；而这里是正交的情况：阻碍触发的是 skill 的*领域*。如果某个 skill 的用途是完成 Claude 仅凭基本工具就会自行执行的事情——转换音频为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询写得非常完整（“将这个 48k 立体声 wav 降采样为适用于 whisper 的 16k 单声道”，包含完整路径），它也不会触发：模型会直接使用 `Bash`/`ffmpeg`，而不会查阅任何 skill。查询内容无法解决这个问题，因为“我可以直接完成这件事”的判断针对的是*任务*，而不是措辞。

在你开始反复优化之前先诊断这一点：通过 `claude -p` 运行一个真实的查询，并观察模型在整个运行过程中是否*曾经*查阅过该 skill（遵循上面的 ALL-skill-calls 规则），还是直接使用 `Bash` 自行完成任务。如果它从未查阅过，那么触发探测在结构上就无法检测到这个 skill——无论你怎么写，召回率都将接近 0，而这个 0 衡量的是模型“我可以自己完成”的反射，而不是你的描述。停止针对 `claude -p` 召回率进行调优，并通过真正的方式进行验证：以生产环境作为评估（用户下一次真实的、*交互式*使用——无头 `-p` 比真实会话更偏向执行操作，并且系统性地低估触发率），再加上输出对比，以便在 skill 生成可检查产物时进行比较。（在一个音频预处理 skill 上观察到：无头运行的 run_eval sweep 在*每个*查询上的读取召回率都是 0——包括一个明显的“转录这段录音”查询；手动执行 `claude -p` 探测后显示，模型直接使用 `Bash` 查找并处理文件，整个运行过程中的 `Skill`=0。这个 0 衡量的是无头模式的操作偏差，而不是描述；真正的信号只有在交互式使用中才会出现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新 skill 的 SKILL.md frontmatter。向用户展示修改前后内容，并报告分数。

## 关键：在源位置编辑 Skills

**绝 NEVER 先编辑已安装的 skill 副本。** 除非用户明确说明它们就是源代码，否则应将以下所有位置视为已安装/运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装副本会导致更改：
- 在缓存刷新时丢失
- 无法同步到源代码管理系统
- 造成浪费的工作，并需要手动重新合并

**始终确认你编辑的是源代码仓库：**
```bash
# 错误 - 缓存位置（只读副本）
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# 错误 - 个人已安装副本，除非明确将其用作源代码
~/.codex/skills/my-skill/SKILL.md

# 正确 - 源代码仓库
<repo-root>/my-skill/SKILL.md
```

**任何编辑之前**，运行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。应先找到由仓库支持的源，编辑并验证它，只有在用户需要立即在本地运行时，才同步已安装的副本。

**然后回答决定“同步已安装的副本”是否确实需要进行的后续问题：运行时是否已经读取源？** 三种安装方式的行为不同，猜错会导致不必要的同步，或者提交一份用户下一次会话根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **符号链接**到源代码树中 → 编辑内容*就是*运行时内容。不需要同步。
- **`source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本号递增只是为其他使用者做的记录工作，不是本地激活步骤。
- **任何缓存/复制的安装方式**（来自 git 的 marketplace、使用 `cp -r` 的安装）→ 运行时是一个独立副本，在新内容生效前确实需要运行官方更新命令。

**同时，应根据内容而不是版本字符串验证激活状态。** 注册表可能记录了磁盘上并不存在的路径或版本——某次会话读取到一个插件记录，其中写着缓存目录和*新*版本号，差点因此报告更新已生效；但那个目录从未创建过，而真正的运行时路径一直都是指向源的符号链接。权威检查方式是 grep 运行时文件，查找只有新版本包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库上的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能会在你不知情的情况下提交技能 B（甚至是技能 A 的更早一轮修改）。某个真实会话在一小时内同时遇到了三种症状——一次 `Write` 因文件在读取后发生变化而被拒绝，并且 HEAD 在任务进行期间两次移动（方法论案例 16）。失败的根源不是发生冲突，而是使用了过时的基线，或使用会悄悄混合两个会话工作的覆盖式写入。长期规则如下：

1. **只要仓库在任务开始时是干净的，就应基于 git ref 而不是工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传入 `--baseline-origin git-ref:<sha>`。在几分钟前、其他人的提交之前取得的树快照，是一个已经不存在的树的基线。**应提取到一个全新的、不存在的目录中。**提取到现有目录时，`tar -x` 会悄悄覆盖同名文件，并保留归档中没有的文件，导致一个在提取时完全没有信号的混合快照，而 `compare` 随后会因为它与该 ref 不匹配而拒绝。同样的陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会将目录嵌套进去；而当 `mv` 被别名为 `mv -i` 时，目标已存在的重命名操作会打印一行提示，并默认不执行，但无论哪种结果退出码都是 0（已通过实验验证）。
2. **在写入前重新读取**，包括写入被拒绝时或经过一段时间后：检查发生了什么变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图整合到你的版本中——他们的编辑通常是有原因的——然后再写入。
3. **提交前检查 HEAD 以及当前所在的分支。** `git log --oneline -1` 可以发现 SHA 是否发生移动：如果它自你的基线以来已经移动，就要针对新的 ref 重新运行回归 `compare`，然后再执行 `verify`——审计工具本来也会拒绝过时的审查（“after skill changed”），但自行发现可以节省一次往返。不过，另一个会话可能造成比 HEAD 前进更严重的问题：**它可能在你不知情的情况下切换分支**，因为 checkout 作用于整个工作树。真实发生过的序列是——你执行 `checkout -b feat/x`，编辑了一段时间；与此同时，另一个会话执行了 `checkout main` + `pull`；随后提交落在了 **main** 上，违反了仓库“永远不要直接提交到本地 main”的规则，而特性分支仍指向旧基线。因此，提交前检查中应加入 `git branch --show-current`，不能只检查 SHA。若这种情况已经发生，`git reflog` 是权威的还原依据（它会按顺序记录每一次 `checkout: moving from X to Y`）；而修复方式——**前提是工作树干净**——是 `git checkout -B <feature> <your-sha>`，随后执行 `git branch -f main origin/main`：两者都只是移动 ref，不会触碰工作树，因此都不会像 `reset --hard` 那样破坏并行会话尚未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——另一个会话尚未提交的工作不能被一并带入。（这本来就是打包规则；在并发场景下更是不可或缺。）
5. **每次会话结果只递增一次版本号**，而不是每轮编辑都递增：同一会话在同一个技能上的连续多轮编辑应合并为一次递增——除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），此时每个已被使用的状态都应有自己的版本号。

## 技能创建流程（分步说明）

创建或更新技能时，请按顺序执行以下步骤。仅当某个步骤明确不适用时才跳过。

### 步骤 0：前置条件检查

开始任何技能工作之前，自动检测所有依赖项，并主动安装缺失的依赖项。在工作流中途才发现缺少工具（例如在打包时发现缺少 gitleaks，或在验证时发现缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖项就自动安装，并向用户提供检查清单摘要。只有在所有阻塞性依赖项都已满足后才能继续。

关键阻塞项：Python 3、uv、已锁定的 skill-creator 运行时（验证/打包）以及 gitleaks（安全扫描）。仅当单独授权的证据计划确实运行代理评估时，claude CLI 才是阻塞项。请从 skill-creator 根目录使用 `uv run --frozen` 运行随附的 Python 工具，例如 `uv run --frozen python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 依赖环境中已有的软件包，可能会缺少已锁定的依赖项。

**uv 隔离约定：** 将此目录视为一个普通的 uv 项目。保留其中已提交的 `pyproject.toml` 和 `uv.lock`，让 uv 从共享全局缓存中生成一个项目本地的 `.venv`，并使用 `uv run --frozen` 运行随附的工具。对于此处已锁定的依赖项，不要通过每次调用时添加 `--with` 覆盖项；不要跨项目设置一个全局的 `UV_PROJECT_ENVIRONMENT`；也不要创建项目专用的 `UV_CACHE_DIR`。在常规技能执行过程中，绝不要使用 `--no-cache`、`uv cache clean` 或 `uv cache prune`；缓存维护属于需要单独授权的磁盘操作。

### 步骤 1：通过具体示例理解技能

仅当技能的使用模式已经明确理解时，才跳过此步骤。

要创建有效的技能，必须清楚了解该技能将如何通过具体示例使用。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成示例。

例如，在构建图像编辑器技能时，相关问题包括：

- “图像编辑器技能应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能否提供一些该技能使用方式的示例？”
- “用户说什么话时应该触发该技能？”

为避免让用户应接不暇，避免在一条消息中提出过多问题。

### 步骤 2：规划可复用的技能内容

分析每个示例时：

1. 考虑如何从头开始执行该示例
2. 确定应给予 Claude 多大程度的自由度
3. 确定在重复执行这些工作流时，哪些脚本、参考资料和资源会有所帮助

**让具体程度与任务风险相匹配：**
- **高自由度（文本指令）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，但允许合理变化
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 第 3 步：初始化 Skill

如果该 skill 已存在，请跳过此步骤。

从头创建新 skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个包含适当 frontmatter、资源目录和示例文件的模板 skill 目录。

### 第 4 步：编辑 Skill

开始编写之前，获取 Anthropic 的最佳实践文档（上方“Skill Creation Best Practice”中提供了链接）以及方法论参考资料——即使你觉得自己已经了解这些内容，也要执行此操作：文档会更新，训练数据版本会过时，而“我基本上了解”恰恰是编辑者跳过这一步并错过最新指导的状态。

编辑时，请记住，该 skill 是为另一个 Claude 实例使用而创建的。重点关注那些对 Claude 有益且不显而易见的信息。

**现有 skill 迁移门禁 — 首次编辑前必须完成：**

1. 在编辑前捕获完整的当前 bundle。对于非 Git 或 dirty 的源代码，请使用该工具，以便快照携带可验证的 provenance manifest：

   ```bash
   cd <skill-creator-path>
   uv run --frozen python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源代码，从选定的 ref 物化目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   包括 SKILL.md、references、scripts、assets、workflows 以及现有的 evals——不要只包含主要提示词。绝不要复制已经编辑过的目录树并将其标记为“before”。**使用一个之前没有提取过任何内容的目录**——重复使用一个已经包含早期运行内容的目录，会让 `tar -x` 静默覆盖同名文件，同时保留新归档中不存在的旧文件，从而生成一个混合快照；在提取时不会产生任何信号（`compare` 只能在之后间接通过目录树哈希不匹配发现这一点）。有关这一陷阱的更完整说明，包括基于 `mv` 的变体，请参阅下面的“Concurrent sessions on the same skill repo”。

2. 清点旧 skill 的 actor/jobs、触发上下文、运行时契约、命令/标志、失败和恢复场景、页面/域变体、捆绑资源以及 eval 覆盖范围。在进行结构重写之前，为重要的旧边缘行为添加保留用例。
3. 编辑后，生成新旧版本对比审查：

   ```bash
   cd <skill-creator-path>
   uv run --frozen python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

如果旧目录是从 Git 重建的，请将最后一个标志替换为
   `--baseline-origin git-ref:<ref>`。该工具会将该引用解析为不可变的提交，并根据该树验证每个包含的文件及可执行位。

   **重命名或移动 skill 目录本身**（而不仅仅是编辑其内容）会改变 `--after` 的路径，而这两种基线模式都会使用该路径来确定身份 — `compare` 默认会拒绝这种情况（假定 `--before`/
   `--after` 是误不匹配的），并显示 `pre-edit snapshot source
   identity does not match the edited skill`。添加 `--renamed-from <old-path>`
   （对于 `snapshot`，这是 `--source` 所指向的路径；对于 `git-ref:`，这是相对于其仓库根目录的 skill 旧路径），以显式声明此次重命名；随后，身份检查会验证该路径，而不是 `--after`，同时内容/树哈希检查保持不变，因此实际不匹配的配对仍会失败。**请将 `--renamed-from` 作为绝对路径传入。** 此命令接收的每个路径在以相对路径给出时，都会相对于当前工作目录解析 — 而不是相对于 `--after`，也不是相互之间相对 — 并且 `--renamed-from` 通常指向一个已经不存在的目录（它已被重命名移走），因此不像 `--before`/`--after` 那样会通过存在性检查来捕获错误的解析；它只会在更深处以令人困惑的方式失败。skill-creator 自身的编辑尤其容易遇到这一问题：上面的 `cd
   <skill-creator-path>` 是 skill-creator 自己的仓库，而它通常与正在审计的 skill 所在的仓库
   *不同*，因此相对的
   `--renamed-from` 会悄无声息地相对于错误的仓库进行解析。

4. 审查每个候选项。严格使用一种处置方式，并记录具体的证据/理由：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移到此 skill 之外时，必须提供负责接收的目标位置、当前的边界证据以及可追溯的用户批准。明确的弃用也必须引用/追溯用户的批准。对于保留/清理/修复的声明，必须指向当前的真实文件和行，并包含一段简短的 `contains` 引文，使验证器能够在附近找到它。文件级候选项必须使用当前文件指纹，并附带一份具名的语义审查，解释为何行为得以保留 — 指纹本身只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写相同的填充脚本 —
   `classify` 子命令会完成机械性工作（定位目标文件中引文所在的行，填写 evidence/semantic_review，并在找不到引文或理由过短时快速失败）。你仍需为每个候选项撰写处置方式和理由；它只负责将这些内容录入：

   ```bash
   uv run --frozen python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（`disposition` 默认为
   `preserved_or_moved`；文件级候选项只需提供 destination 和至少 40 个字符的 reason——指纹会自动为你计算）。**从目标文件中复制 needle（使用 Read/grep/sed），切勿凭记忆手动输入**——查找采用精确匹配，缺少引文会立即失败；手动输入的 needle 实际上有两种容易失败的情况：全角与半角标点（`：` 与 `:`），以及凭记忆改写的近义字符（`也` 与 `都`）——这两种问题都很难通过自查发现，并且只有工具拒绝整个映射时才会被捕获（曾有一次映射连续被拒绝两次，原因正是这两种情况）。

   **needle 证明的是某一行仍然存在，而不是某个概念仍然存在。**`heading` 候选项的 needle 可以匹配新文件中的任意一行，而它所标记的 *section*——标题及其正文内容——可能已经散落到其他 section 中，或被压缩到难以辨认。文本层面的保留不等于语义层面的保留。对于每个 `heading` 候选项，在 needle 通过后，还要额外验证：(a) 新文件中仍有涵盖相同主题的 section（根据含义，而不是字符串匹配，找到对应的标题或内容块）；(b) 新 section 的正文不能比旧 section 明显更短——统计旧 section 的非空行数，并与新 section 的进行比较。如果某个 section 的正文缩减超过一半，就需要一条 `semantic_review`，说明有意压缩了哪些内容，以及为什么这种压缩是无损的。跳过这项检查，就会出现重构报告“162/162 preserved”，但用户之后询问时才发现某项命名原则已经悄悄失去了专属 section（真实案例，2026-08-30：“Outcome-first gate” section 被散落到汇总表的一行中；所有 needle 都通过了；用户不得不询问“有没有丢失东西”才发现这一问题）。
5. 验证已完成的审查。哈希值会使后续任何编辑都导致审查过期，因此候选项发生变化时要重新生成并重新分类。验证通过后会写入 `.skill-regression-reviewed`，这是一个与内容绑定的本地状态凭证。它有助于检测后续编辑，但有意不作为独立的打包授权依据；打包时会自行重新验证已完成的审查：

   ```bash
   uv run --frozen python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应显示的内容（这是实际输出，因此可以据此识别静默失败）：

   ```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在待审查候选项，并不表示工具失败；
2 表示调用/运行时失败。该工具能够证明移动和接口保持完全一致，但会有意拒绝根据模糊的词语重叠来推断语义等价。诸如“检查权限被拒绝”之类的通用短语，不能悄无声息地替代“已登录但没有角色”这一精确契约。还要检查标记为
`only_outside_runtime` 的候选项：如果运行时行为只存在于 eval、测试或不可达的参考实现中，那么它就不存在于正常调用路径中。

**每次编辑 SKILL.md 后立即验证——不要等到打包时（Step 7）。** 该检查能够提前捕获的失败是真实存在的：以未加引号的 YAML 标量形式写入 frontmatter 描述，在 Claude Code 的宽松解析器中可以正常解析，却会在严格解析器中出错（codex 曾报告某个已经发布数月的 skill 出现 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中包含 ` #` 时甚至不会报错——它会静默截断其后的全部内容，导致触发关键词消失，而所有扫描结果仍然显示为绿色。

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.quick_validate <path/to/skill-folder>
```

**只要描述中包含 `: ` 或 ` #`，或跨越多个句子，就应将其写成 YAML 块标量**（`description: >-` 后跟缩进段落）——自上述事件以来，这是每个新建或编辑的描述所推荐采用的约定，因为块标量可以原生容纳这两个字符。

**更新现有 skill 时**：扫描每个现有引用和捆绑资源，查找对应的更新，然后通过上述迁移门禁。迁移契约需要 SKILL.md 中存在直接的运行时指针；eval 或变更日志不能替代它。

接下来的三项检查是**升级探针，而不是无条件扩大范围**。如果根据其中任何一项采取行动会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖、权限或外部写入，请在修改 skill 之前停止，并重新归类为 Tier 3。Tier 1 和 Tier 2 可以检查这些问题，但不会因此获得新的交付物。

**脚本检查**：在宣布编辑完成之前，询问：*源对话（或 eval 转录）编写了哪些代码，而未来的每次调用本来都会重新编写这些代码？* 当所选层级已经授权进行这项能力工作时，将其整理到 `scripts/` 中（参数化并完成清理），并修改文档以指向它。否则，将该信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的附带结果进行捆绑。分工如下：**scripts 负责执行，文档负责理解**——一个方法只存在于散文式说明中的 skill，会在每次运行时重新承担完整的编写成本。之所以将这项检查放在编辑步骤中，正是因为跳过 eval 循环的路径（对话提炼、直接编辑）不会到达 “Improving the skill” 中 eval 转录版本的这项检查。

**组件货架检查（针对嵌入工件的片段提出同一个问题）**：脚本检查涵盖 skill 执行的代码；生成工件的 skill（报告页面、演示文稿、文档）还会积累由其*输出*嵌入的片段——图片叠加控件、粘性导航、图表配置、CSS 代码块。如果连续生成的输出都各自手写相似片段，这就是同一种重复信号，只是指向了不同的货架。在新增 `components` 子文件夹或注册表引用之前，应用上述升级规则；Tier 1/2 可以提出该方案，但不要创建组件能力。当 Tier 3 获得授权后，将代码片段变成货架组件的关键在于围绕它建立契约：(a) **逐字嵌入块**——使用 BEGIN/END 标记将其完整复制到工件中，不依赖任何依赖项，使单文件工件保持自包含；(b) **注册表条目**——说明交互契约（触发条件、按键绑定、关闭行为、边界情况）和来源，即它来自哪个已交付工件、用户何时批准了它；(c) **准入门禁**——只有用户实际使用并批准过的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但看起来漂亮的片段不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定属于契约，在不同运行之间不得漂移，而颜色和尺寸可以遵循工件自身的风格；(e) **回写循环**——为某个工件发明的片段，应在其获得批准的同一会话中提升到货架中。之所以这不仅仅关系到节省 token，是因为手动重写的片段会*漂移*——每次重写都会悄然改变按键绑定、关闭行为、计数器等；而对于每天阅读这些工件的用户来说，交互一致性**就是**产品体验。在用户为第一个此类货架提出的原话中：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：某报告页面 skill 的 lightbox-gallery 组件（图片叠加层：←/→ 在组内循环切换，ESC 关闭，就地缩放，n/N 计数器），以及其对 interaction-components 注册表的引用——该组件是在用户纠正跳转式引用的同一会话中提取的，并在发布前通过自动化点击流程测试完成验证。参见方法论案例 17。

**流水线检查**：考虑一下此 skill 的输出是否会自然地供另一个 skill 使用，以及是否应当让现有 skill 链接*到*此 skill。添加或实质性修改“Next Step”交接或流水线契约，需要在编辑前重新归类为 Tier 3；Tier 1/2 可以提出该建议，但不得顺手将其添加进去。

**引用与自我应用检查（那些即使谨慎的作者也会遗漏的缺陷）**：这是一组失败模式，它们从内部看起来都像是已经完成的工作，而且没有一种能通过更加仔细地重读来捕获——每一种都需要一个*机械化*动作。（开头故意没有写数量。“三种失败模式：”是一个会过时的派生数字：任何人追加一个项目后它就会失效；而对变化最难精准捕获的，正是计数文字，因为*变化的事物本身并不包含在其中*——重新编号的 grep 和列表本身的 diff 都会直接略过它们。）之所以把它们归在这里，是因为它们有着共同的原因：**写下断言和验证断言是两种不同的模式，而单次遍历无法同时完成两者。**在你撰写内容时，“参见规则 8”*就是*该断言；你并没有同时打开规则 8。

不同于上面的三个升级探测，这一项**不按层级限定范围**——它取决于你写下了什么。Tier 1 修复如果既没有添加指针也没有添加规范性规则，就没有需要在这里处理的内容，而且你不必自行判断：corollary 中的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 回答这一点。在任意层级写下了指针或规则？那么以下项目就适用。

- **你写下的每一个指针，都要打开其目标并从中复制一行出来——而且要在写下指针之前完成。**不要说“我确信该规则列出了全部三个标记”：从中粘贴一段内容——放入你已经在为此步骤产出的任何材料中（审查记录、提交消息正文、你的回复），放在以后第二位读者可以拿它与目标进行核对的地方。只看过但没有复制出来的片段，正是本句开头所拒绝的那种自我评估。错误的交叉引用在重读时是不可见的，因为错误的指针看起来和正确的指针完全一样，而作者又是唯一一个必然“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal 规则 3”，意图指向一条关于不要引用过时枚举的规则——但被引用文档自己的*规则 3*讲的是样本量，真正被引用的规则位于另一个文件中；读者遵循该文档既有的自引用约定后，会落到一个无关的主题上。同一轮编辑还提交了一个方向颠倒的指针（对于上方的材料写成“见下文”），以及一个指向不存在的章节标题的指针。
- **一旦文件中有两个编号列表，单独写“rule N”就是有歧义的。**检查按指针进行，而不是按文件进行：在写下“rule N”之前，运行 `grep -n '^N\. ' <file>`，并确认在你所指的章节中恰好只有一个匹配；如果有多个匹配，还要写明章节名称。（**不要**把这变成文件级别的警报，例如“该文件是否包含多个从 1 开始的列表”——在任何长文档中，这几乎总是成立，因此它会在健康输入上触发并被人忽略，而纪律 #6 警告说，这比没有检查更糟；在此文件上运行它，你就会亲自看到。）真实案例中，一个单独的“rule 1”对应三个候选列表，而从上到下的搜索首先命中了错误的列表。
- **写下任何规范性规则后，都要根据它旁边的行检查该规则——并让检查产出一个工件，而不是一个结论。**使用与下面 corollary 相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的变更块。这里自行阅读就足够了——你不是在对它进行模式匹配，因此不需要脚本——但必须带上该 ref：单独的 `git diff` 只显示未暂存的工作，而一旦你 `git add`，它就会打印空内容；这是本段 corollary 为逃避的五种静默空结果模式之一。将新规则拆分成各个独立的条款，并逐条写下：**同一变更块中**满足该条款的行。（下面 corollary 中的 `scripts/reference_net.sh` 是另一项工作：它会列出供你解析的*正文交叉引用*。它不会把变更块交给你，也不会告诉你规则中的某个条款是否得到满足。）**某个条款旁边没有对应行，就是发现的问题。**那个诱人的简短版本——“我的新规则通过了吗？”——对于 30 秒前刚写下它的人来说不可能失败；这正是纪律 #6 要求优先采用可证伪观察而非自我评估的含义，因此本项目也必须提供它所要求的同一种工件。最先暴露问题的通常是它旁边的段落。真实案例：一条新规则规定“始终同时报告原始计数和过滤后计数——差值*就是*污染”，而同一提交中的配套示例却只打印了过滤后的数字。同一 diff 中的另一处陈述引用了两个数值，却没有说明它们是否是在相邻的新规则刚刚规定为强制的限定条件下收集的。范围很小且有界：不是“重读整个文档”，而只是“我 30 秒前写下的规则，在我 30 秒前写下的那些行上是否通过”。
- **为每条新规则写下一行，说明由谁执行它，以及他们是否确实能够执行。**现有工具无法满足的规则，会被那些自认为已经遵守规则的人跳过——这是最糟糕的一类，因为它会产生有文档记录的虚假信心。真实案例：一条新规则说“检查两个日志存储”；项目自己的规范性单命令排查工具却将其中一个硬编码为唯一目标，因此标准工作流会在该规则原本要捕获的故障上返回干净结果。该规则本身是真的，却不起作用，而且没有说明这一缺口。**使这一点可证伪的工件**（没有它，本项目就会成为一个禁止自我评估的段落中唯一进行自我评估的项目）：写明能够捕获违规的工具或命令，然后**针对一个你已经知道它应该捕获的案例运行一次**。如果它在已知有问题的输入上返回干净结果，你就已经测量出该规则不起作用——将这一缺口直接写入规则本身。从记忆中回答“他们是否确实能够执行”，正是纪律 #6 所拒绝的未经验证的断言。**当没有工具能够判定该规则时**——大多数正文和品味规则确实如此，因此不要把它当作逃生口——工件就是明确写出这一点的句子：*“没有任何工具强制执行这一点；它只有在人们记得它时才成立。”*这比拥有一个通过的检查更糟，而大声说出这一点正是目的；一个执行情况保持沉默的规则，会被假定为已验证，而不是实际得到验证。注意本项目自身诚实的局限：工具和已知有问题案例的选择仍然是判断，因此它只是移动了未经验证的步骤，并没有消除它——这比替代方案便宜，但并非没有成本。
- **Corollary——你的修复本身也是缺陷来源，因此要在最后一次编辑之后重新检查你触及的区域。**在一次变更的两轮审查中，第 1 轮产生了八个发现；第 2 轮又产生了八个，**其中七个是由第 1 轮修复引入的交叉引用错误**。重写一个句子会移动其周围的锚点。这也是为什么，对于读者通过指针导航的工件而言，“它已经审查过了”不是终点：你一采取行动，审查结果就会过时。重新检查是机械化的，而且它是一个**脚本**，不是让你重新输入命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的 bundle 中）。它会列出你添加的行之间的正文交叉引用，以便你打开每个目标并确认其中确实写着你所声称的内容。首次使用前先阅读其 header——其中解释了它为何需要 base ref，而不是默认使用 `HEAD`，以及它有意**不**做什么。

**在开始编辑之前获取 `<base-ref>`，不要事后再获取。** 在你开始操作的那一刻将其解析为字面量 SHA，并且只解析一次 — `BASE=$(git rev-parse HEAD)` — 然后在本条以及上面的项目符号中复用同一个值。如果你运行了现有 skill 迁移门禁，它就是你已经建立基线所依据的 ref。稍后传入 `HEAD` 才是陷阱：提交之后，`HEAD` 已经包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请恢复该值（使用 `git log`、`git reflog`，或提供给迁移门禁的基线），不要用 `HEAD` 替代；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印提示，但不要依赖在那里才发现这一点。

**为什么这里要使用脚本，而这段其余内容都是说明文字。** 它所替代的那条单行命令经历了五轮修补 — 将 diff 锚定到正确的基线、查看已暂存的编辑、在提交后仍能正常工作、跳过 diff 自身的 `+++` 标头、移除误导性的 `-n` — 而其中五轮里的四轮都增加了另一种让它不输出任何内容并以 0 退出的方式，这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种问题的另一种表现：它移除的 `-n` 原本会输出带行号的真实命中，但这些行号是按管道传入的流计算的，因此看起来很权威，却指向不存在的位置 — 这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都一直在发布它本来要捕获的缺陷。说明文字无法验证自己的输入，无法说明自己产生了哪一种结果，也无法被测试；脚本可以同时做到这三点，而它的契约是：**每一种结果都必须被明确命名，错误输入必须明确失败**。这正是同一阶段前面提到的 Scripts 检查，只不过应用到了本段 — 而这五轮修补就是忽视该要求所付出的代价。

**读取它的判定结果，而不只是退出码。** 脚本只要成功运行就会以 0 退出，因此单独查看 `$?` 无法告诉你它发现了什么；答案位于判定行中，并且它始终会明确说明以下几种结果之一：发现引用（逐一解析）、文件与基线完全相同、文件已更改但没有新增行，或存在新增行但其中没有任何类似引用的内容。这些是不同的结果，脚本特意将它们区分开来 — 这个检查曾经把它们合并成一个无声的“没有任何内容”，正是因此才变成了脚本。它只需几秒钟，而且不依赖时刻保持警惕，这正是纪律 #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的指针 — “见下方章节”、“如上面的规则所述” — 因此也要阅读新增的行。）

### 第 5 步：清理审查（任何公开 skill 都必须执行）

**在执行此门禁之前，当纪律 #5 到期时，其独立审查必须已经运行，**并且当前更改对应的 `independent-review.md`（位于你的私有、由 git 跟踪的知识仓库中 — 不在已清除的工作区中，也不在任何已经公开或可能变为公开或被分发的仓库中）必须存在**并且已经提交**。对于新 skill，它始终需要执行；对于现有 skill，使用下一段中的阈值。一个位于 git 工作目录中但尚未提交的文件，与一个从未写入过的文件没有实质区别；`ls`/`test -f` 只能确认它存在于磁盘上，不能确认它能够被保留下来。对于**新** skill，这是任何内容离开你手中的第一个步骤，因此纪律正是在这里得到实际执行，而不只是被写出来 — 一条位于使用位置上方 1000 行、却没有任何检查机制的规则，每次都会输给完成任务的冲动。

**对于已发布 skill 的修改，修改离开你手中的那一刻就是 push，而不是这一步。** 这道门槛可以用一句“仅供内部使用，跳过”来回答；对于仅涉及文档的修改，打包甚至可能完全不会运行——因此把审查锚定在这里，意味着一次 skill 修改可能在没有经过任何独立审阅的情况下进入公共分支。真实案例（2026-07）：对这份文件本身的一次修改发布了一个 discovery 命令，但它无法访问旁边正文声称涵盖的三个根目录；修改已经合并，直到*之后*委托进行的一次审查才发现了这个问题。**因此，对于现有 skill：独立审查及其留存的产物必须在 `git push` / 创建 PR 之前完成——在 push 时运行的各道门槛（回归审计、验证、扫描）检查的都是结构，而没有任何一道能告诉你说明是错误的。** 这沿用纪律 #5 的门槛，不作任何改变：当*规则、契约或数字发生变化时*就必须进行审查；拼写错误或纯格式调整则不需要。让拼写修复也必须等待一轮审查，正好会养成反射式做法 #6 所警告的那种习惯——“这次改动很小”会变成普遍例外，最终连真正重要的修改也被涵盖进去。

**对于要进入公共仓库的 skill，这不是可选项。** 私密内容一直会泄露到公共 skill 中，而扫描器漏掉的泄露才是危险的——非英语语言中的真实姓名、真实对话记录中的逐字句子、插入示例中的真实案例。只有在 skill 确实仅供内部使用时，才能跳过。

**应按目标位置而不是按主题确定审查范围。** 只有会公开发布的产物——skill bundle 本身——需要进行清理。留在私有仓库中的配套文档（skill 提炼所依据的事件报告、内部运行手册、项目的 CLAUDE.md）应保留真实的主机名、路径和时间戳：删除这些内容会破坏它们的审计价值，而你最终还会把这些修改恢复回来。有一次提炼会话之所以经历了三轮返工，正是因为清理被应用到了源材料涉及的所有内容，而不只是公共 skill。

**先检查目标位置，并让它预先填充建议。** 在 skill 将要存放的仓库上运行
`gh repo view --json isPrivate`（或者读取
`quick_validate` 已经打印的提示）。私有目标位置会使选项 C 成为默认建议，而不是事后才考虑的事项——“除非另有说明，否则假定为公开”正是把私有 skill 的工作路径变成无人要求的占位符的原因。

**触发清理的因素是目标位置的 `isPrivate`，而不是任务在主观上有多像发布。** 这两者并不总是一致，而当它们不一致时，除非明确指出这一点，否则最终起作用的就是主观感受。将内容*移入 marketplace skill* 会让人感觉像是在发布——marketplace 正是用于分发内容的地方——因此即使源仓库和目标仓库都是私有仓库、内容也不会被发布出去，清理反射仍然会被触发。真实案例（2026-07）：一次从项目级 skill 迁移到私有 marketplace skill 的操作，把真实的配置路径、真实的十六进制值和真实的具名示例都概括成了占位符。`quick_validate` 在**每次**运行时都打印了 `🔒 audience: private`；作者每次都看到了它，却仍然进行了清理，因为这种*活动*在感受上像是在发布。代价并不只是表面上的——真实路径能让下一位读者去核查该值；而“项目自己的 token 文件”却无法打开。

所以要把它当作一次查询，而不是判断：**读取目标位置的 `isPrivate`，如果它是
`true`，则是否进行清理需要由所有者提出请求。** 私有→私有的移动是一次移动，而不是一次发布。**当两个探针都没有返回结果时**（还没有远程仓库，尚未运行
`quick_validate`），你没有得到查询结果——回退到将其视为公开，并明确说明这一点，因为这种不对称性就是如此：一次不必要的问题只会多花一句话，而一次不必要的信息泄露则无法挽回。并且，`isPrivate` 报告的是目标位置**今天**的状态——一个位于私有仓库中、正准备发布的 skill，应当在发布它的那次推送中进行清理，而不是在这次推送中进行。如果你发现自己开始思考某些内容在私有目标位置中是否“应该”被泛化，这种思考本身就是信号。

使用 **AskUserQuestion** 确认清理深度（对于公开目标位置，确认清理深度，而不是是否进行清理；对于私有目标位置，确认是否完全需要清理）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**清理流程——通读是方法，扫描是辅助：**

1. **亲自通读整个 skill 并进行语义判断**（这才是真正的检查）：SKILL.md + 每个引用文件 + 每个示例。对于每个具体名词 / 示例 / 代码片段，询问“这是通用占位符或公开实体，还是从真实项目 / 人员 / 对话记录中直接取来的？”替换后者——即使没有扫描器标记出来也要替换。这是唯一能够捕获没有可匹配关键词的信息泄露的方法。完整指南以及该语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器作为廉价的第一遍检查**：使用检查清单中的 grep 模式 + `security_scan.py`（步骤 6）。它们可以快速捕获明显的密钥 / 路径 / 已知名称——但“没有匹配项”并不等于通过。
3. **替换**每个发现的问题，用保留教学要点的通用等价内容替换（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。从惨痛经验中总结出的两条规则：占位符本身不能编码真实值——`<acme-corp-domain>` 恰恰泄露了它原本要隐藏的名称；应当改用其*角色*命名（`<api-domain>`、`<upstream-provider>`）。此外，当你编写批量替换脚本时，要提供一个限定在 skill 目录范围内的显式文件白名单——未限定范围的查找替换会毫不犹豫地改写项目自己的 CLAUDE.md，并迫使你执行 git restore。
4. **通过重新阅读而不是重新 grep 来验证**：重新阅读已更改的部分，并确认没有损坏的引用。

### 步骤 6：安全审查

在打包或分发 skill 之前，运行安全扫描器以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --frozen python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --frozen python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）
- 完整的发布内容集仅由 [scripts/packaging_policy.py](scripts/packaging_policy.py) 定义。打包、安全证明、内容哈希和回归审计都必须使用该共享策略；不要在说明文字中或在特定使用者的过滤器中维护第二个排除列表。

**它不涵盖的内容** — 这也是为什么仍然需要执行第 5 步的通读检查：gitleaks 和正则规则只会匹配你列出的*已知机密格式和模式*。对于没有关键词的私密内容，它们在结构上无法识别——例如非英语语言中的真实人物/项目名称、真实文字记录中的逐字内容、从你自己的工作中直接摘取的真实示例。`security_scan` 显示绿色意味着“未发现已知格式的机密”，**而不是**“该 skill 已完成清理”。绝不要将其当作后者。

**首次设置：** 如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 清理完成（可安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**对于私有 skill，发现项是信息，而不是待办事项。** 扫描器无法判断泄露的凭据与*本应存在*的凭据之间的区别——例如，一个其全部价值就在于预先填好内容的模板，或一个指向其运行所在唯一机器的脚本。在私有仓库中绝不要自动修复：报告发现的内容，由所有者自行决定。下面的选项 A（“自动修复”）适用于准备发布到公共环境的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包 Skill

skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.package_skill <path/to/skill-folder>
```

对于每个现有的 Git 跟踪 skill，在提供并重新验证完整审查结果之前，都会阻止打包。当前标记仅是本地状态收据，因此先提交或手动编写标记都无法绕过审查。下一次编辑后，审查结果将失效：

```bash
uv run --frozen python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及使用 `--include-evals` 发布根目录下的 `evals/` 目录（默认情况下作为开发资源排除）：

```bash
cd <skill-creator-path>
uv run --frozen python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **重新验证已完成的现有 skill 回归审查**（当 Git HEAD 已包含该 skill 时）；仅有标记绝不会授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描一致）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 步骤 8：更新 Marketplace

打包后，更新 Marketplace registry，以包含新的或更新后的 skill。

**对于新 skill**，在 `.claude-plugin/marketplace.json` 中添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于已更新的 skill**，按照 semver 在 `plugins[].version` 中提升版本号。对 skill 文件的任何更改——即使只是修复一处单行拼写错误——都需要提升版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧版 skill，而你的修复则一直无法发布。

**然后将其记录在 changelog 中——这正是最容易被跳过的一步。** 版本号提升让更新变得*可安装*；而记录条目则让它在六个月后有人遇到同样问题并进行检索时变得*可查找*。如果 changelog 记录了其他每个 skill 的版本，却悄无声息地漏掉你的版本，那比完全没有 changelog 更糟：这些空缺会被理解为“那里什么也没变”。

遵循现有条目的格式，不要另创新格式——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。
将其与版本号提升放在**同一个 commit** 中；“稍后”更新的 changelog，往往就是永远不会更新的 changelog。

真实案例（2026-08）：某个 skill 连续发布了两个版本，版本号提升正确、门禁检查通过、PR 也已合并——却**完全没有 changelog 条目**，因为这套流程中没有任何步骤要求添加条目。两个版本都只在之后的审计中才被发现。这正是纪律 #6 在本文件自身上的体现：如果一条规则只存在于约定中，而不是存在于步骤中，那么它每次都会输给“尽快完成”的驱动力。

**保持 registry diff 最小——这是所有 skill 共享的唯一文件。** Marketplace manifest 是所有并行编辑者都会发生冲突的地方，因此其中无关的格式更改，比其他任何位置的同类更改代价都高：它会把原本干净的三行版本号更新变成其他正在编辑该文件的人必须解决的冲突。如果你通过脚本更新（解析为 JSON、修改、写回），重写过程可能会悄悄规范化文件原本未采用的格式——末尾换行符、缩进宽度、键顺序、unicode 转义。遵循往返处理纪律：之后重新读取文件，并对该文件运行 `git diff --stat`；**唯一可以出现的行必须是你有意更改的字段。** 如果出现额外行，应恢复文件原有的约定，而不是提交这种规范化结果（某次脚本化版本号更新就曾给一个原本没有末尾换行符的 manifest 添加了末尾换行符——只多出一行无用的 diff，而这个文件恰恰最可能在同一时刻被其他人编辑）。同样的原则也适用于 skill 接触到的任何共享 registry：lockfiles、catalogs、index documents。

**当一个 PR 经历了几次合并仍未结束时，请执行 rebase——然后证明你没有吞掉任何人的工作。** 使清单成为冲突热点的同一特性，也会让它变得过时：一个同时修改注册表和变更日志的开放 PR，只要有其他内容合入就会发生冲突，因此应预期出现 `mergeable: CONFLICTING`，而不要把它当成意外（有一个 PR 就是在某个下午 main 前进了 7 个提交后遇到这种情况的）。如果仓库采用 squash merge，应执行 rebase 而不是 merge——在经过 squash 的历史中，合并提交没有任何价值。冲突本身几乎总是**增量式的**：两位作者分别在同一节中追加了自己的条目，因此解决方式是**两者都保留**，绝不要使用 `--ours`/`--theirs`，因为这会悄无声息地丢弃同事添加的那一行。

人们会跳过的步骤，恰恰是能捕获错误解决结果的步骤——**解决冲突后，证明与基准版本相比唯一的差异就是你的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
uv run --project <skill-creator-path> --frozen python -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要直接使用 `--force`：如果远程仓库自你上次 fetch 以来发生了变化，lease 会使推送失败；而这正是有人向你的分支推送过内容、普通 force 会将其抹掉的情况。

**插件边界不属于本 skill 的职责范围。** 是否应将 skill 拆分到不同插件中、如何布局 `source`/`skills`，以及用户是否可以单独切换 skill，都属于打包/分发领域——SSOT 是 `marketplace-dev` skill，而不是这里。当任务确实需要做出这些决策时：确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与 `skill-reviewer` 需要其脚本时拉取 `skill-creator` 相同），然后阅读 marketplace-dev 的 cache-and-source-patterns reference 并遵循其中的要求。不要在此处重复其规则；复制一份只会导致内容逐渐偏离。

**重命名、迁移或移除 marketplace 条目，对于所有已经安装该条目的用户来说都是破坏性变更。** 当条目消失时，Claude Code 不会清理已安装的副本，导致悬空安装在每次 `marketplace
update` 时都报错。应将此类变更视为 API 弃用：在变更日志中发布迁移说明，并遵循 marketplace-dev 关于具体操作的指导。

**如果你亲自提交/推送 skill 仓库：** 对于已有 skill，如果当前变更触及 discipline #5 的规则/契约/数值阈值，请确认审查产物记录了这项变更并且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不只是确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的审查不能满足当前的实质性变更。Step 5 的说明解释了为什么对于已经发布的 skill，真正的强制执行点是推送，而不是打包。然后只暂存 skill 的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充满无关的变更，否则这些内容会被一并带入提交（有一次提交就带入了一堆无关的 transcript 文件，之后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库实际的可见性，不要根据路径想当然——公开的 skill 仓库应当创建 PR 并进行审查，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成 skill 后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" 已完成。安全扫描已通过，市场已更新。

建议：[根据当前状态选择——例如，如果从未验证过触发效果，则选择 "B) 优化描述"，否则选择 "D) 暂时完成"]，因为[一行原因]。

选项：
A) 打包并导出为 .skill 文件以供分发
B) 运行描述优化——提高自动触发准确率（约 5 分钟）
C) 扩展测试集并继续迭代——在发布前添加边界情况
D) 暂时完成——我会手动测试，如有需要再回来
```

测试 skill 后，用户可能会要求改进。通常这会紧接着使用 skill 之后发生，此时用户还清楚地记得 skill 的表现。

**改进筛选：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了某项内容，则不要重复添加。

## Claude.ai 专属说明

在 Claude.ai 中，使用相同的验证深度路由器和严格评估授权门控。当完整的通用配对流水线获得明确授权后，工作流为起草 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子代理，需要调整部分机制。请按以下方式适配：

**运行测试用例**：没有子代理，因此无法并行执行。对于每个测试用例，读取 skill 的 SKILL.md，然后亲自遵循其中的说明来完成测试提示。一次完成一个测试用例。这不如使用独立子代理严格（你编写了 skill，同时也在运行它，因此拥有完整上下文），但这是一次有用的合理性检查——而人工审查步骤可以弥补这一点。跳过基线运行——只使用 skill 按要求完成任务。

**审查结果**：如果无法打开浏览器（例如，Claude.ai 的 VM 没有显示器，或者你在远程服务器上），则完全跳过浏览器审查器。改为直接在对话中呈现结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），将其保存到文件系统，并告知用户文件所在位置，以便他们下载和检查。直接在线询问反馈："看起来怎么样？有什么需要修改的吗？"

**基准测试**：跳过定量基准测试——它依赖于基线比较，而在没有子代理的情况下，这些比较没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同——改进 skill，重新运行测试用例，询问反馈——只是中间不再使用浏览器审查器。如果有文件系统可用，你仍然可以将结果整理到文件系统中的迭代目录里。

**描述优化**：本节需要使用 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要使用子代理。请跳过本节。

**打包**：`package_skill.py` 脚本可在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 上，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能是在要求你更新现有 skill，而不是创建新的 skill。在这种情况下：
  - **保留原始名称。** 注意 skill 的目录名称和 `name` frontmatter 字段——保持它们不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前先复制到可写位置。** 已安装的 skill 路径可能是只读的。先将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从副本进行编辑和打包。不要传递 `--new-skill`；现有 skill 的非 Git 副本仍然属于现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再将其复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 专属说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此经过明确授权的通用配对流程可以运行基线和评分器。子代理可用并不等于获得授权，也不能据此增加额外角色；请说明必要的工作分支，限制并发，并在并行执行无法增加证据时按串行方式运行各个案例。
- 你没有浏览器或显示界面，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击、在浏览器中打开该 HTML 文件的链接。
- 在经过明确授权的**通用配对运行**之后，应在自行修改 skill 之前，使用 `generate_review.py` 为人工生成评估查看器。默认层级证据、未授权工作，以及取代查看器机制的专门工作流，不会仅仅因为工作发生在 Cowork 中就产生查看器义务。
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。之后你可以读取该文件（可能需要先请求访问权限）。
- 打包功能可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，但请将其留到 skill 完成修改且用户同意其状态良好之后再执行。
- **更新现有 skill**：用户可能是在要求你更新现有 skill，而不是创建新的 skill。请遵循上文 claude.ai 部分中的更新指南。

- 在采取任何专门工作流的退出路径之前，选择能够证伪此次更改的最低验证层级，并记录原因
- 起草或编辑 skill

- 运行并通过现有 skill 回归审查；仅通过 eval 不算完成
- 打包最终 skill 并将其返回给用户。

如果你有 TodoList，请将选定的验证层级及其默认证据添加到其中。只有在明确授权通用配对流水线之后，才添加“创建 evals JSON 并运行 `eval-viewer/generate_review.py`，以便人类审查测试用例”。
