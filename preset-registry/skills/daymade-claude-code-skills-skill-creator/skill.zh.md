# 技能创建器

一个用于创建新技能并对其进行迭代改进的技能。

从高层次来看，创建技能的流程如下：

- 确定你希望技能完成什么，以及大致应如何完成
- 将变更归入能够证伪其可能故障模式的最低验证层级
- 编写技能草稿
- 在该层级进行验证：对范围明确的修复执行针对性检查；对不确定的指令变更执行抽样行为重放；对全新、高风险或影响范围广的工作执行完整的配对评估流水线
- 当所选层级产出定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写技能（如果定量基准测试暴露出任何明显缺陷，也应据此重写）
- 重复上述过程，直到你满意为止
- 仅当当前证据无法判定变更后的行为时，才提升验证层级

使用此技能时，你的任务是判断用户当前处于该流程的哪个阶段，然后立即介入，帮助他们推进适用的阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须缴纳的成本。对于正确性可以直接测试的范围明确的修复，不要创建评估文件、并行派出配对代理、对输出进行评分或启动查看器。

以下六项常规准则贯穿始终，因为这些故障模式会导致看起来令人信服、实际上却是错误的技能被交付：

1. **先验证，再编写。** 技能中出现的每一项技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的内容——无论是在本次会话中，还是在一次经明确批准的挖掘会话中。现在无法验证？那就去验证，或者明确标注（“未经验证——来自记忆”）。技能会放大其中包含的一切：经过验证的知识会产生复利，而信心十足地陈述的错误同样如此。对于知识型技能（内容主要是有关外部系统的事实——API 端点、参数、字段、平台行为），请阅读[参考资料/知识型技能的事实依据](references/knowledge-skill-grounding.md)，了解其操作版本：权威性阶梯（观察到的行为 > 机器可读的契约 > 经过实际运行的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前的文档示例冒烟测试，以及受众/Windows 可移植性检查清单。一次来源依据审计曾发现，多项信心十足的契约断言与作者当时已经掌握的证据相矛盾（方法论案例 9）。
2. **将“不可能/不支持”视为假设，而不是结论。** 当某项能力看似受阻时（API 错误壁垒、无法连接的工具、无法打开的格式），在把“平台不支持此功能”写入技能之前，应穷尽所有观察路径——UI 自身的网络流量、替代渠道、不同的已记录标识符。观察到的行为优先于推测性的请求形式。
3. **站在领域前人的肩膀上——默认在编写或优化技能的方法论之前，将该领域已经确立的最佳实践检索到上下文中。** 技能的方法论质量取决于上下文窗口中的知识，而不是潜藏在模型权重中的知识：预训练是有损的，会随时间过时，而且除非确实将权威来源拉入上下文，否则往往根本不会被激活。因此，你所编写内容的质量上限是 `your training data + the user's input`——*除非*你主动检索该主题领域真正的既有成果。务必这样做：使用 WebSearch 搜索该领域的权威理论/标准/方法，并阅读该领域中任何随附或已安装的技能，然后在注明出处的情况下，将其中起关键支撑作用的原则融入技能。**这与下文的“既有成果研究”属于不同的维度**——后者寻找的是可复用的*工具/基础设施*；这里则以该学科积累的科学成果为*方法论本身的质量*奠定基础。将其作为**默认操作，而不是等用户提出要求才去做的事情**：简要告诉用户你正在从哪个领域汲取知识，并允许他们说“跳过”，但当该领域 40 年来的公开成果只需一次搜索便触手可及时，绝不要交付一个受限于你的记忆和用户提示的方法论。例如：数据可视化技能必须吸收 Cleveland 与 McGill 的图形感知排序以及 Bertin 的视觉变量理论（位置/长度优于颜色，颜色优于文本——这是测量所得，而不是审美判断）；日期/时间技能必须呈现成熟的库及其公认的陷阱；说服/谈判技能必须检索既有框架，而不是凭记忆重新发明它们。如果权威知识只存在于你的权重中，从未进入上下文，那么你就是在本可引用依据的地方进行猜测。
4. **在压缩现有技能之前，先保留其内容。** 更新现有技能是一场迁移，而不是从空白页开始重写。在首次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧版包，或根据明确的 Git 引用重建它；随意制作的副本加上来源标签并不能构成基线。盘点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和简洁性允许移动内容或删除重复内容，但不允许悄无声息地删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个未匹配的旧单元进行分类。仅存在于 `evals/`、测试或未链接参考资料中的运行时契约仍然属于已丢失。只要仍有任何候选项尚未分类，或任何真实缺口尚未修复，就不要宣称更新已经完成。同样的逻辑也适用于*反转*，而不仅仅是删除，并且涵盖任何先前的承诺——不只是那些带有日期和姓名的承诺：**推翻已经作出的决定必须是一项提案，绝不能成为附带结果。** 明确说出来，并获得接受。悄无声息的重写比悄无声息的删除更糟糕，因为它会一次性摧毁产物以及原本可以发现问题的证据——并让所有下游审阅者失去判断依据（参见第 5 条）。

5. **任何内容都不能仅凭自我审查就交付——由独立的、具备全新上下文的审查者进行对抗性检查，是固定步骤，而非特殊情况。** 你对“现在已经很好了”的判断来自生成该产物的同一个模型，因此它具有导致缺陷产生的完全相同的盲点。这是实测结果，而非坊间传言：在没有外部反馈的情况下，内在自我纠正并不能可靠地改善输出，有时反而会使其变差（Huang 等，ICLR 2024）；当生成者和评估者具有相同的错误模式时，反复迭代只会**增强信心，却不会增加信息**。再多的自我检查也无法摆脱这一点；只有外部视角可以。**完整流程——提示词模板、锚点选择、发现项表格、完整案例——参见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在第一次审查前阅读该文档。** 以下是起关键支撑作用的规则：
   - **独立性有两个层面，而作者往往会漏掉第二个。** *审查者的上下文*不能从你的上下文分叉而来——分叉会继承你的盲点，然后返还一个“已审查”的印章。但它据以衡量的*证据*也必须位于**变更的影响范围之外**，否则它会继承你的**结论**：它读取一份产物以及一份已经与该产物一致的规范，然后报告二者一致。请注意，“本次会话中未编辑”这条界线还不够严格——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，三名审查者因此对一个缺陷视而不见，而他们在未经改动的对应记录中都发现了该缺陷。按你接触过这些锚点的难度对其排序：用户自己的对话原文 > 早于本次工作的 git ref（`git log --oneline <ref>..HEAD -- <path>`；其中只要包含你的任何提交，该锚点即失效）> 仅追加日志（一种约定，而非强制机制）。**全新项目没有锚点——如实说明并请求用户提供锚点，而不要报告一次你并未执行的通过结果。**
   - **只向它提供两样东西：产物和读者规范。** 除此之外什么都不要提供——不要提供设计理由，不要提供项目背景，也不要说“只需确认 X 没问题”；这些内容会把独立审查者变成橡皮图章。读者规范是一份*规范*，而非理由说明，因此它无法为任何内容机械背书；省略它会浪费一半的审查价值，因为审查者随后只能以自身为衡量标准。**对于 SKILL.md，读者是另一个执行它的智能体**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——应询问它无法据以采取行动的是哪些指令。在审查运行前明确规范，并且绝不要在审查结束后用它来为发现项开脱。
   - **对于可理解性以及相对于语料库的完整性，它是事实依据；对于品味，它没有裁决权。** 对前两者直接采纳。将“这可能是一个 bug / 我建议 Y”视为假设，并先自行复现。绝不要委托它判断 AI 垃圾内容或审美问题——这些存在同模型盲点。
   - **列举失败的*轴线*，而非内容领域——这也决定了要运行多少名审查者。** 轴线是*你提出的问题*；领域是*你阅读的材料*。三名审查者分别覆盖场景、算术和 diff，但全都只问“这是否连贯？”，等于同一名审查者被计费了三次。**默认使用一名审查者，而且通常已经足够**；仅在增加一条轴线时才增加一名审查者。自我审查最不擅长的轴线是**忠实性**——“这是否仍然忠实于已经作出的承诺？”——因为作者正是改变承诺的人，而连贯性与忠实性彼此正交：一份产物可以在内部完美自洽，同时完全背离已经作出的决定。
   - **留下产物，否则这只是一条警告。** 纪律 #6 指出，只产生意见的检查不如产生实际产物的检查——因此本检查也必须生成一个文件，否则恰恰会在最重要的时刻输给急于完成任务的冲动。在你的私有、由 git 跟踪的知识仓库中，将 `independent-review.md` 写入 `skill-reviews/<skill-name>/`：包含**审查者提示词原文**（以便后续读者判断它是否具有诱导性）、**每个发现项及其处理决定和理由**（这是合理筛选与丢弃刺耳意见之间的区别），以及**哪些内容无法检查**。如果你不知道哪个仓库是你的私有知识仓库（或者没有这样的仓库），请如实说明并询问用户——不要猜测一个可能落入任一禁区的位置。两个禁止的位置：**不得放在 `<skill-name>-workspace/` 中**（这些是被 git 忽略、会被清理的临时目录——此文件是跨会话审查证据，必须在它们被清理后仍然存在），并且**不得放在任何已经公开、可能公开或可能分发的仓库中**——这通常会排除被审查 Skill 自身的仓库（审查内容本身就会引用私有路径、真实姓名和项目细节）。在进行实质性编辑后，使用一个*新的*智能体重新审查——实质性编辑是指规则、契约或数字发生变化，而非修正拼写错误。**从步骤 5 开始，此文件就是已执行审查的证据；没有该文件，就意味着没有执行审查。****写入文件并不等同于该文件能在下一次会话中继续存在——必须在同一轮中于该私有仓库内对其执行 `git add` + `git commit`。** 一个仅存在于 git 工作目录中但尚未提交的文件，不具备这条规则所要求的任何“由 git 跟踪”保障：它可能丢失、被覆盖，或者后续检查“这是否经过审查？”的流程根本无法发现它（真实案例：文件已正确写入正确路径，并包含真实的发现项——但后续自动检查仍然失败，因为它从未被提交；修复方法只需执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械式且互补的：它能证明你没有*删除*行为。但它完全无法说明你写下的内容是否真的可以被遵循。

6. **设计你所编写的检查，使其无法自证通过。** Skill 在很大程度上由检查构成——门禁、检查清单、“发布前”步骤——如果执行上下文能够在*违反检查所编码的规则本身时*仍然通过检查，那么这种检查比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴自那些早于软件领域解决此问题的行业：
   - **验证必须覆盖规则中的每一个条款。** 如果规则写的是“A + B + C”，证据就必须分别要求提供 A、*以及* B、*以及* C 的证明。给一条包含三个条款的规则附上一行确认要求，只会被作者已经完成的那个条款满足；其他条款则不可见。真实案例：一个报告编写 Skill 包含一道交付门禁，其规则写着“选项以并排筹码形式呈现 + 突出显示建议选项 + **背景信息以完整、自足的句子写成，使陌生人也能理解**”——但其下方的证据行只要求“N 个决策项，全部呈现为筹码”。作者执行了门禁，写下了这项证据，自证通过，然后发布了一个页面，其中的标签都是单个字符，所有上下文都被删除了。这条规则始终都在文件里；只是检查从未衡量过该条款。
   - **在健康输入上误触发的检查比没有检查更糟。** 上述失败是检查在本应失败时通过；这里则恰好相反——检查在本应通过时失败。后者代价更高，因为它会训练操作者形成条件反射般绕过检查的习惯（`--no-verify`、`SKIP=1`、`--force`）；一旦形成这种习惯，门禁就会对*所有*输入失效，包括它原本要拦截的那些输入。因此，在编写失败关闭型检查时，**假阳性比假阴性更需要优先避免**：漏掉一个真实问题，只会让你在那一次付出代价；而误杀一个健康输入，则会让你失去整道门禁。
     注意这个征兆：**因反复踩中同一个陷阱而产生的挫败感，本身就是风险信号**——作者正是在这种状态下，最容易发布一个从未用健康输入校准过的防御措施。真实案例：一天内三次踩中同一个格式陷阱后，作者向一个 linter 添加了正则表达式检查；它在项目自己的语料库中误杀了 **33 个健康输入**，并在同一小时内被回滚。先校准，再启用——在真实且已知良好的材料上运行任何失败关闭型检查，并确认假阳性为零；宁可放宽检查，让它偶尔漏检，也不要允许它误触发。
   - **让每个检查项都成为可证伪的观察，而不是自我评估。** “背景信息是自足的”无法被其作者判定为不合格；“遮住页面其余部分，单独阅读一张卡片，并说明它在决定什么”则可以。优先采用能产生产物的检查——命令输出、引用的一行文本、屏幕截图——而不是只能产生意见的检查。
   - **同样的质疑也适用于你所*运行*的检查，而不仅仅是你所编写的检查。** 上述四条规则约束的是随 Skill 一同发布的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样也是工具，而错误的工具会像正确的工具一样笃定地报告干净的结果。在 2026-07 的一次会话中，五条不同的验证命令在两个方向上都给出了错误结果：一个不带 `-L` 的 `find` 报告某个已安装 Skill 的文件缺失（它们位于符号链接之后）；一个 `grep --exclude-dir=<name>` 隐藏了正被审计之物的另一个副本；一个反转的 shell 条件误报删除操作尚未发生；一个跨越换行符的正则表达式凭空制造出 55 个“丢失的引号”；而只搜索五个文件中的两个文件，却报告有两条规则缺失，实际上它们存在于第三个文件中。**最初所有这些结果都被相信了，而每一个错误都只有通过重新运行一种结构不同的检查才被发现。**

修复方法是实验实践中最古老的那一套：**在用仪器检验答案未知的情况之前，先让它检验一个你已经知道答案的情况。** 要 grep 一个你预期不存在的字符串？先用相同的命令形式 grep 一个你知道存在的字符串——如果它也返回 0，那么出问题的是命令，而不是文件。这只增加一行，却能把“我检查过了”变成“我用一台校准过的仪器检查过了”。

     有两种具体情况值得牢记，因为上面都出现过，而且都会*静默*失败：`find` 在没有 `-L` 时不会跟随符号链接（而 skill 安装经常是指向源代码仓库的符号链接）；`--exclude-dir` 会匹配目录树中所有位置的基本名称，而不仅仅是你所设想路径中的名称。

     **这条规则还有后半部分，只有当检查内容要交付时才会显现其危害：要针对*标准*实现进行校准，而不是针对你机器上的实现。** 上面的仪器规则能保证*你*得出的结论可靠；这条规则则能保证*读者*的操作有效。写入 skill 的工具行为断言——某个标志、某种递归模式、某个声称会“跟随符号链接”的选项——会在使用你从未见过的二进制文件的机器上执行，而两端的差异都是静默的：你测试时它可以正常工作，到了读者那里却悄无声息地不起任何作用。造成这种情况的机制有两种，而且在会话内部都不可见：**相同的命令名称会解析到不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能避开*别名*，因此只有 `command tool` 或绝对路径才是确定性的形式）；以及**同一个程序在不同实现中的行为不同**（BSD 与 GNU，或直接替代实现之间的差异）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将它作为符号链接陷阱的修复方法写入 skill，并发布到了一个拥有 1200 个 star 的公开仓库——他们的 `grep` 实际上是通过 shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 上，相同的 `-R` 什么也匹配不到（它需要 `-RS`），因此，这个规定的修复方法对大多数读者都静默失效了，而且恰恰发生在警告验证器会静默失败的章节中。

     因此：**在有关工具行为的断言进入要交付的制品之前，请针对标准二进制文件**（`/usr/bin/<tool>`）**重新运行它**，而不是针对 shell 交给你的那个程序。如果它无法通过这项测试，就不要写下该标志——**应优先采用与具体实现无关的表述**：自行解析路径（`readlink -f`），而不是押注某个递归标志；在脚本中执行子字符串测试，而不是使用面向行的匹配；描述你需要的*行为*，而不是你恰好知道的选项。只在你的环境中有效的操作说明比没有说明更糟糕，因为读者根本无法发现它其实悄无声息地什么也没做。

   - **采用成熟的检查清单实践已经确立的方法。** 确定清单属于 **READ-DO**（边读边执行——适用于低频或不熟悉的流程）还是 **DO-CONFIRM**（先凭专业经验完成工作，然后在明确的**暂停点**停下来确认——适用于时间压力下经验丰富的操作者），并将它锚定在真正的暂停点，而不是“工作流中的某个位置”。清单只保留**致命项目**——既关键，且在压力下又经常被遗漏的项目，大约五到九项；超出这个数量只会降低遵循程度（[Gawande，*《清单革命》*](https://www.shortform.com/blog/types-of-checklists/)）。此外，应优先采用 Shingo 所说的**控制**而不是**警告**（[防错法](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，在一心求成的冲动面前往往败下阵来；而能够阻止继续推进或强制产出制品的步骤完全不需要警觉性。如果 skill 只能发出警告，至少也要把警告放在作出决策的位置——**如果执行上下文从不打开某份参考资料，那么归档在其中的规则实际上就不算规则。**

另一方面，也许用户已经有了一份技能草稿。在这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应该始终保持灵活。如果用户说“我不需要进行一大堆评估，凭感觉和我一起做就行”，那你也可以照做。

然后，在技能完成后（不过再次强调，顺序是灵活的），你还可以运行技能描述改进器——我们为此提供了一个完全独立的脚本——以优化技能的触发效果。

## 第一步：共存检查（官方 skill-creator 插件）

在做任何其他事情之前，快速执行一次检查（只需一次 grep，常见情况下无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：**什么都不要做——不要安装任何东西，也不要向用户提及本节。继续当前工作。
- **存在：**官方插件的 skill-creator 和此版本现在会以几乎相同的描述同时出现在技能列表中，因此未来的会话会随机路由到其中一个。用一两句话告诉用户这一点，然后提供以下选项（未经用户同意，绝不要擅自操作）：
  1. **推荐**——运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的、自检式 SessionStart 钩子复制到用户的 Claude 配置中，并在 `settings.json` 中注册该钩子（同时创建备份），这样未来的每个会话都会确定性地将技能相关工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；当用户明确按名称要求使用官方插件时，该插件仍可完全正常使用。在未安装官方插件的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的钩子。
  2. 另一个选择是运行 `claude plugin disable skill-creator@claude-plugins-official`（可使用 `enable` 恢复），通过将官方条目完全移出技能列表来消除歧义。

如果钩子已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有内容。

同样的机制也适用于用户创建的技能：当其技能有意与某个已安装技能重叠时，使用 `scripts/generate_supersede_kit.py` 为其生成一套工具包——参见“既有方案研究”下的“共存与优先级”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

### 使用 AskUserQuestion（关键——请阅读）

**在每个决策点都要积极使用 AskUserQuestion 工具。** 如果存在结构化选项，就不要在对话中提出开放式文本问题。这是你能做出的最大单项用户体验改进——用户往往同时处理多个窗口，并且可能已经有 20 分钟没有查看这段对话了。

**每次使用 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段以及刚刚发生了什么（1-2 句话）。用户可能已经切换到其他任务。
2. **简化说明**：用通俗语言解释需要做出的决定。不要使用函数名或内部术语。说明它能做什么，而不是它叫什么。
3. **给出建议**：先说明你的建议，并用一句话解释原因。如果选项涉及工作量，请同时显示双方所需时间：`(human: ~X min / Claude: ~Y min)`。
4. **提供选项**：给出 2-4 个具体且带字母编号的选项。每个选项都应该是一项明确的操作，而不是抽象概念。

**规则：**
- 每个问题只包含一个决策——绝不要将不相关的选择合并在一起
- 提供退出路径（AskUserQuestion 始终隐含提供“其他”选项）
- 接受用户的选择——可以提示其中的权衡，但绝不要拒绝继续执行
- 如果答案显而易见且不存在权衡，就跳过提问（只需说明你将做什么）
- **如果问题超时且没有收到回答（用户离开了键盘），既不要停滞不前，也不要擅自推进涉及偏好或范围的决策。** 先完成不产生副作用的基础工作——编辑前快照、清点、评估用例收集、只读审计/健康检查——并将需要判断的事项（重构方向、要删除的内容、继续/停止决策）留到用户回来后再处理。然后明确说明你完成了哪些工作，以及哪些事项正在等待用户决定。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话中可能已经包含了用户想要固化的工作流（例如，他们说“把这个变成一个技能”）。如果是这样，请先从对话历史中提取答案——使用过的工具、步骤顺序、用户做出的修正，以及观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**来源清点——始终在起草前进行，并遵守同意边界。** 清点当前对话以及存在重叠的现有文档/技能（请参阅下文的“现有成果研究”）。更早的本地会话 JSONL 文件属于独立的私密来源：除非用户明确要求挖掘历史记录，或者在你说明将读取哪些内容后明确批准使用该来源，否则不要打开或解析这些文件。如果获得批准，只能通过对话挖掘工作流的脱敏提取，将相关的过往会话纳入其中；绝不要将原始记录加载到你自己的上下文中。如果未获批准，则继续使用当前对话和现有项目来源，不要把缺失的历史记录视为阻碍。

在挖掘对话（或会话记录）时，要清点**两类资源——它们会归入不同位置**。*知识*——端点、参数、陷阱、决策规则——会成为 SKILL.md 中的指导内容或放入 `references/`。*会话中不得不编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——是 `scripts/` 的候选内容：如果本次会话编写了它，下次调用时就不得不重写它，因此应将其参数化、净化并打包。之前的一次提炼保留了润色后的文字，却遗漏了可复用的辅助工具；一般经验是要同时关注知识→references 和代码→scripts 这两个渠道。

当源材料是*过去的*会话转录记录（Claude Code 项目目录下的 JSONL 文件），而不是当前实时对话时，不要将它们加载到你自己的上下文中——一份大型转录记录可能会耗尽上下文窗口并导致会话丢失。应将提取工作委派给子代理，并明确指示它们使用脚本逐行解析、截断每个提取出的字段，并且只返回一份提炼后的经验教训列表——原始转录记录绝不能进入主上下文。

**首先，在回答下面四个问题之前，先确定这是哪个方向。** 请求可能属于几种彼此*相反*的情况之一：构建一个新技能 / 编辑一个现有技能 / 优化 skill-creator 本身 / 或者它根本不是技能（而是一次性任务）。方向猜错会浪费整个会话——你针对“新技能”所做的研究，并不适用于“优化元工具”。当措辞含糊不清时（例如，一边说“给我做个技能”，一边又指向 skill-creator 自身的路径），此时提出一个 AskUserQuestion 只需花费 30 秒。下面的包装器技能分支是其中一种特殊情况；方向检查则适用于一般情况。

1. 这个技能应该让 Claude 能够做什么？
2. 这个技能应该在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应该设置测试用例来验证该技能有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。输出较为主观的技能（写作风格、艺术创作、需要品味校准的报告）通常无法使用断言——但“没有断言”并不等于“无需验证”。它们的验证路径按成本从低到高依次为：
   - **历史任务重放**：重新运行该技能过去处理过的一个真实提示词，分别使用旧技能和新技能，并依据此次变更涉及的具体规则比较输出（“新输出是否确实遵循了此次更新引入的 token / 标题语法？”）。成本低，并且能够发现“规则虽然写了，但根本没有任何内容读取它”的问题。
   - **将生产环境作为评估**：承认真正的测试是用户下一次实际使用——然后将反馈循环明确化：此后用户的每一次纠正都是需要回写的事件（技能自身的“迭代/活文档”部分），每一次认可都是语料素材。一个发布后没有这种回写习惯的品味型技能不会改进；具备这种习惯的技能即使从未运行过正式评估，也会逐渐收敛。**而当技能的输出是某种会持续运行的东西——守卫、监控器、定时任务、钩子——它自身的遥测数据就是评估数据，其中信号最强的记录就是第一次误报。** 用户纠正的前提是用户注意到问题并愿意反馈；已部署的机制则会主动报告自身情况，通常一天之内就会发生，而误报是其中最尖锐的报告形式，因为它证明你写下的某条规则存在错误，这种错误无论重新阅读多少遍都无法发现。应将第一次误报视为一次定期评估结果，而不是令人烦恼的事情：在认定机制行为异常之前先检查它，因为更可能的发现是*指令*写得过于绝对。（真实案例：某个技能规定了一项响亮失败检查，部署后的检查在夜间针对一个完全健康的状态触发了一次，而修复方式是更正技能中那句过于绝对的表述——没有人投诉，是遥测数据发现了问题。）
   - 对视觉输出进行**渲染 + 人工审核**（技能自身的视觉质量保证关卡），绝不要用一个 grep 断言来假装衡量美感。**并且，用于验证的渲染器必须与交付物实际使用的引擎相同**——随手使用已安装的任意预览器并不能替代目标引擎。布局引擎与目标应用程序不同的缩略图生成器，会悄无声息地*掩盖*你正在寻找的那些缺陷；而使用错误引擎得到的绿色验证结果比完全不验证更糟，因为它会带来虚假的信心。真实案例（2026-07）：某个 .docx 文件通过 macOS Quick Look 缩略图完成了“视觉验证”，但该工具无法重现两端对齐文本的拉伸效果；用户刚在 Word 中打开文档，就看到其中的信息块被严重拉散。修复方法是安装与 Word 兼容的引擎（LibreOffice），将文件转换为 PDF，逐页栅格化，并阅读每一页。要么匹配引擎，要么验证就只是在演戏。**这一原则不只适用于渲染器，也适用于所有验证工具**——解析器、代码检查器、验证器：它必须与生产环境共享同一实现，否则它给出的绿色结果毫无意义。第二个案例具有相同的模式：一位作者试图在源文件阶段，使用一种与生产工具链所用实现*不同*的 markdown 实现，检查一种会破坏最终文档的标记模式——该实现将三个已知存在问题的输入全部解析为完全正常，因此任何基于它构建的预检查都会悄无声息地放过所有问题。坦诚的结论是，这种特定缺陷只有在生产工具运行后才能被检测到，检查也应该放在那里。**当没有任何可用工具与生产环境共享同一实现时，应明确说明该阶段无法执行检查——不要构建一个只会产生虚假绿色结果的检查。**
   根据技能类型建议合适的默认选项，但让用户自行决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认技能类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类决定了后续的整个评估策略。此处务必正确判断，以避免之后浪费精力。

### 扩展还是新建检查——在任何专门分支之前运行

下面三个专门工作流的结尾都有“**不要**继续阅读下方章节”，而 *既有成果调研* 恰好位于它们之后。**这种顺序只是排版顺序，而非执行顺序。** 扩展还是新建的判断适用于每个分支；跳过这项判断，恰恰会导致一次会话最终交付出一个与已安装技能重复的技能。

因此，在进入包装器技能／对话挖掘／制品语料库分支之前，请先回答一个问题：**是否已经存在一个应该包含此能力的技能？**

**发现根目录，不要凭记忆回想。** 手动维护的安装位置列表正是那种会逐渐过时的制品，而你遗漏的那个根目录恰恰会给你带来麻烦。

**搜索文件，而不是名为 `skills` 的目录。** 技能目录以*技能*命名（`skill-creator/`、`<suite>/<skill>/`），因此源码仓库、市场克隆目录和插件缓存中可能根本没有名为 `skills` 的目录——搜索这个名称会悄无声息地跳过它们，看起来却像是正常完成了搜索。每个技能都有一个 `SKILL.md`；这才是与目录布局无关的检索依据。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

步骤 3 预计需要几秒钟，并且仍会返回比你所需更多的结果；请使用特定于该能力的术语而非泛化术语来缩小范围（`chart` 会匹配所有内容，而 `stacked bar` 不会）。

这一步所触及的根目录——也是凭记忆列清单时通常会遗漏的地方：技能源码仓库（一个 `claude-code-skills` 检出目录及其任何 `-pro` 同级目录）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过市场安装的套件——源码仓库中没有任何迹象表明它们存在于此）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、各配置档案的配置主目录（`~/.claude-profiles/<name>/`），以及——完全没有任何路标的那个位置——**每个项目自身的 `.claude/skills/`**。第 2 步让这成为你亲自验证过的结论，而不是从别人那里承袭来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何市场、全局技能列表或源码仓库清单里；你在规划新技能时通常会查看的任何地方都不会提到它们。真实案例（2026-07）：某个会话为一个领域构建了全局技能，遍查源码仓库、全局目录和其他智能体目录，一无所获，于是发布。后来搜索对话历史时，发现了一个完全针对同一领域的成熟项目级技能，它一个月前就已存在于某个项目的 `.claude/skills/` 中——其中包含新技能所缺少的八条规则，包括一条由用户亲自指定的规则。除项目级位置外，所有根目录都已检查过，而扫描结果还无比自信地报告“没有先例”。

**当重叠对象确实是无关项目中的项目级技能时该怎么做**——这正是上述惨痛案例会让你陷入的情况，也是下面三个要点未涵盖的情况：你无法将同级技能添加到一个根本不存在的套件中，而“扩展它”意味着编辑无关项目的工作树。行之有效的做法是：**将其规则吸收到你正在构建的技能中，然后在获得所有者同意后停用项目本地技能**——它是根据真实工作编写的，因此应将其视为更成熟的来源，并以它为方向进行协调。停用他人正在使用的技能应由所有者决定，而不应成为你构建过程中的附带结果。

这句话遗漏了四件事，其中任何一件都会让你受阻：

- **“以它为方向进行协调”是一项可反驳的推定，而不是规则。** 有两种常见的例外：项目技能可能已经*过时*（规则是数月前针对一个后来发生变化的系统编写的），也可能具有*项目特定性*（规则仅在该项目的约束下成立——将它们全盘导入会让你的技能变得狭窄，而本文档其他部分明确要求你不要这么做）。吸收来的规则是另一位作者的记忆，因此应按照规范 #1 对写入技能的任何内容所提出的要求，**逐条重新验证**。
- **“停用”需要一种机制，而第一步并不是你本能想到的那一步。** 按以下顺序操作：

  1. 在 grep 技能的*引用*之前，先用 **`find` 查找技能的*主体***。同一个仓库中经常存在同一技能的多个副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会由不同工具从同一工作树中加载。Grep 回答的是“谁提到了它”；只有 `find` 才能回答“它有多少个副本”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放入 `--exclude-dir`**（它按基本名称匹配，因此会隐藏每个同名目录，包括你尚未发现的副本——参见规范 #6 中的工具规则）。真实案例（2026-07）：一次停用操作正是这么做的，它修复了找到的全部五处引用，却在 `.agents/skills/` 下留下了第二个完整副本——由 git 跟踪、没有停用标记，而且是缺少最新规则的陈旧快照——其他工具仍会将其作为有效技能加载。
  2. 在删除任何内容之前，**验证新位置确实可以从旧位置所在的环境访问**——你刚刚推送的市场技能在市场更新且插件安装之前并未完成安装，而先停用旧技能会造成一段新旧技能均不可用的空窗期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常通过符号链接指向源码仓库，而不带该选项的 `find` 会报告文件缺失（参见规范 #6 中的工具规则）。
  3. **然后**使用 grep 查找引用，并将仍然有效的引用重新指向新位置。区分**有效指令**（技能列表、交叉引用、告诉下一位智能体应使用什么的交接文档）与**历史记录**（例如决策日志中的条目：“我们在 X 日发布了这个”）——重写后者会破坏审计轨迹，却是在修复一个它本来没有的问题。
  4. **然后**不要直接删除各个主体，而应将其替换为 `superseded by <skill>` 存根，并确保所有副本的存根在字节层面完全相同。**保留 YAML frontmatter**——缺少它的 `SKILL.md` 可能会直接加载失败，而不是以提供有效信息的方式失败——但应重写 `description`，让存根声明自身已停用，而不是继续宣传旧触发条件；否则它仍会在路由过程中胜出，却无法再提供对应服务。正文只需要说明：能力迁移到了哪里，以及一行迁移原因。
- **使用下面的所有权测试确定所有者**（它同样适用于此处：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍会告诉你它属于谁）。当所有者就是正在与你交谈的人时，“同意”只需要一次 `AskUserQuestion`。**当无法联系到所有者时，只吸收规则，不要停用**（这会让两个技能都保持有效并竞争同一触发条件，与停用请求被拒绝时的最终状态相同——参见下文的“共存与优先级”）。
- **如果所有者拒绝停用它**，现在就有两个技能在竞争同一触发条件；这是下文的“共存与优先级”问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 那个项目级技能无法通过搜索新技能的标题名称匹配到；它是通过正文中的领域术语匹配到的。使用 grep 在候选根目录中搜索新技能将要处理的*概念*。

如果存在重叠：

**判断适用哪一条——这是谁的技能？** 文件系统中的命中结果并不携带所有权信息。读取市场的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在所在仓库中运行 `git remote -v`；位于 `~/.claude/plugins/marketplaces/` 下的命中项完全可能只是安装回你自己机器上的*自有*市场。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同一个问题。

探测命令会误判或无法判断以下两种情况，因此在信任结果之前要先检查它们：**分叉仓库**显示的是你自己的远程仓库，但内容属于其他人——应将其视为第三方内容，因为他们的上游改进仍然无法再传递给你。而当**既没有 marketplace.json，也没有 remote** 时（例如仅存在于本地的项目，或被手动复制到全局技能目录中的技能），探测结果是无声的，而不是否定的：**应询问所有者，而不是猜测**。

- **重叠的是第三方技能**（市场套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*轻量增量层*——记录你遇到的陷阱、正确的调用方式以及经过验证的辅助脚本——并**使用带命名空间的名称引用它**。把别人的引擎克隆进你的包中是代价高昂的错误：他们的升级将无法再传递给你，而且两个副本会在不知不觉中逐渐分化。
- **重叠的是你自己的技能**：扩展它，或者在其现有套件中添加一个同级技能。创建一个争夺相同触发条件的独立技能对任何人都没有帮助。**例外：**如果它位于某个*不相关项目*的工作树中，那么这两种做法都不适用——请参阅上面的项目级情况。
- **某个相关技能已经指向了你正在填补的空缺**（例如，其描述中写着“对于 X，请使用 Y”）：构建完成后，要闭合这个引用链——更新该指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**在 2026-07 的一次真实会话中，团队花了一天时间让一个第三方 docx 引擎生成正确的中文商务文档，随后进入了包装技能分支——而这个分支会直接跳过现有方案研究。当时准备交付的形态，是一个重新承载该引擎能力的新技能。正确的形态应当是一个**三层引用链**：保持第三方引擎不变 → 用一个轻量增量技能保存正确用法和经过验证的生成器脚本 → 由领域工作流技能调用该增量技能。在最终落地前，用户不得不两次指出问题，其中第二次纠正更加一针见血：*"不要额外复制一份——在他们的技能之上编写正确用法，并引用他们的技能；这才是技能即代码的含义。"*

### 验证深度路由器（在选择任何工作流之前运行）

在进入通用或专用工作流分支之前，选择**能够证伪变更后行为的最低层级**。应根据故障影响面而非行数进行分类：一条发生变更的破坏性命令，其层级可能高于大篇幅的文字清理。在测试前，说明所选层级并用一句话解释原因。专用工作流可以替换不兼容的机制，但绝不能绕过层级选择，也不能在未说明的情况下降低所需的严谨程度。

| 层级 | 适用情况 | 所需证据 | 默认不要添加 |
|---|---|---|---|
| **1 — 定向验证** | 这是一个现有 Skill；未新增或实质性变更任何能力、触发器类别、工作流分支、输出契约、依赖项、权限或外部写入行为；且编辑内容恰好属于以下一种：(a) 仅修正拼写/格式，不改变行为；(b) 对文档/配置中的事实进行修正，且其真实性可由直接权威来源判定；或 (c) 有界的实现修复，用于恢复明确的现有契约，**并且**修复后的行为由确定性回归检查覆盖。可能改变智能体行为的澄清不属于第 1 层级 | 对以上三种情况均需：运行 `quick_validate`、检查差异，并完成现有 Skill 迁移门禁。然后仅使用与具体情况对应的证据：(a) 精确回读/格式检查；(b) 权威事实及其窄范围检查；(c) 明确的现有契约及确定性回归。仅当规则/契约/数字达到规范 #5 的阈值时，才添加该规范要求的一名全新审查者 | 智能体行为重放、配对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 行为抽样** | 以下条件全部成立：这是一个现有 Skill；变更会影响智能体行为；确定性检查无法完全判定结果；未引入任何新增或实质性变更的能力、触发器类别、工作流分支、输出契约、脚本行为、依赖项、权限或外部写入；并且可以使用 1–2 个具名示例及明确的验收标准覆盖全部变更后行为 | 仅运行这 1–2 个具有代表性的启用 Skill 重放，再加上窄范围的确定性检查，以及规范 #5 要求的一次全新上下文审查 | 基线、配对扇出、方差分析、基准测试、查看器或评估文件。若要求其中任何一项，都应将工作重新分类为第 3 层级 |
| **3 — 完整评估** | 以下任一条件成立：任何新 Skill；任何新增或实质性变更的能力；大范围重写或方法论扩展；触发器/描述优化；新增或实质性变更的工作流分支、输出契约、脚本能力、依赖项或权限；高风险自动化或外部写入；评估需要覆盖 3 个以上不同提示类别的证据、重复试验/方差，或需要在存在实质差异的方法之间作出选择；或者用户明确要求 A/B、基线、基准测试或查看器证据。仅凭主观判断，不应将原本范围有限的第 2 层级变更升级 | 对于通用工作流，运行下方完整的配对管线：真实案例、启用 Skill + 基线、断言、评分、汇总基准测试、分析人员审查和查看器。专用工作流只能替换其明确标记为不兼容的机制；运行其完整验证协议以及所有兼容的第 3 层级步骤，并记录其替换的内容 | 无——这是有意采用的重型路径 |

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，应升级处理。用户提出取消评估或降低评估级别的请求，只会撤销**执行授权，而不会改变分类**：立即停止所有已经启动的成对评估代理、基线评估、评分器、聚合工作和查看器工作。第 3 级变更仍然是第 3 级；应将其所需的重度证据记录为用户已放弃或尚未完成，而不是通过重新标记将较低层级的证据判定为通过。只继续收集用户仍然授权的证据，并且不要声称已经完成完整的第 3 级验证。当触发纪律 #5 中的规则、契约或数值阈值时，不得取消其单个全新上下文审查者，也不得取消为防止破坏性操作或外部影响所必需的任何安全门控。机械化的现有技能迁移审计、公开技能净化以及任何特定领域的安全门控，也仍然独立于此路由器。

### 专用工作流：第三方 CLI 工具的封装技能

在采用通用技能创建流程之前，请检查此前引导至当前节点的会话实际上是否应改用**封装技能**工作流。封装技能是一种配套技能，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或技能包——也就是由他人编写，而用户刚刚花费整个会话才使其在自己机器上正常运行的代码。

适用信号（同时满足任意两项即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 会话中出现了真实、具体的错误消息，并且用户与 Claude 已经为这些错误找出了具体的修复方法（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把它总结成一个技能”“把它保存为封装技能”“这样其他人就不必再经历一遍”“把这次 session 做成一个 skill”之类的话。
- 用户明确提到某个第三方工具的名称，并希望其他代理或其他人无需重复承担他们刚刚付出的学习成本就能使用它。

不适用信号（应改用上面的通用工作流）：

- 用户想要为他们准备从头编写的内容创建技能。
- 会话过程很顺利——没有真正值得记录的阻碍。
- 该技能将封装用户拥有或控制的服务（这是他们自己的代码；应直接编辑源代码，而不是进行封装）。
- 所谓的“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当封装技能工作流适用时，请保留上面选定的验证层级。创建封装技能就是创建新技能，因此属于第 3 级。**不要**继续阅读下面的通用编写章节；请跳转至 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其中的验证协议。这是一个**回顾式提炼**工作流——其任务是从当前对话中挖掘安装流程、已经修复的错误和已经作出的设计决策，并将挖掘结果转化为一个完整、独立自足的封装技能，使其他用户能够安装并从中受益，而无需重新经历这段调试过程。

包装器技能工作流有其自身的架构契约、代码模板和 Tier 3 验证协议——它会替换不兼容的通用测试用例机制，因为其输出是用户的安装状态，而不是一个可以轻松进行断言的文件；这并不意味着降低工作标准。执行所有兼容的通用 Tier 3 步骤，并记录专用协议替换了哪些机制。规范参考实现是 `ima-copilot` 技能（位于 daymade/claude-code-skills 仓库的根目录——这里的纯相对链接曾在该技能移入套件时失效过一次，恰如下面的跨技能引用规则所警告的那样），它是基于使用这一确切工作流的真实会话提炼而成的 Tencent IMA 技能包装器。

### 专用工作流：从对话历史中丰富技能

在采用通用技能创建流程之前，先检查当前会话是否实际上是在请求**将过去的对话提炼为技能**。当用户已经在多个 Claude Code / Codex 会话中持续调试、设计或探索某个主题，并希望将积累的实用知识转化为可复用的 `references/` 时，这一工作流非常有用。

适用信号（满足任意一项即可）：

- 用户说了类似“从我的聊天历史中挖掘模式”“将这段对话转化为技能参考”“把我们学到的内容提炼到技能中”“基于我的对话丰富这个技能”或“把这次对话沉淀到 skill 里”之类的话。
- 当前会话明确旨在从近期的多轮调试或设计会话中提取经验。
- 用户希望基于自己已经进行过的真实对话，向现有技能添加一个 `references/` 文件。
- 目标技能已经存在，目标是使用从对话中挖掘出的知识来丰富它，而不是从头构建。

不适用信号（改用上面的通用工作流）：

- 用户正在根据单个提示或想法创建一个全新的技能。
- 用户希望为刚刚安装的第三方 CLI 工具创建包装器（使用上面的包装器技能工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的转录导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件中。
- 源材料是一批用户已认可的成品，而非对话——请使用下面的制品语料库提炼工作流。

当对话挖掘工作流适用时，保留上面选择的验证层级。新建的挖掘型技能属于 Tier 3；丰富现有技能时，只有在满足所选层级的能力边界的情况下，才维持所选层级。**不要**继续阅读下面的通用编写章节；直接跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流：它会发现本地 Claude Code 项目会话、Codex 转录和命令历史，对其进行脱敏，将其划分为适合智能体处理的分块，运行挖掘智能体，并在验证后将生成的候选参考内容提升到目标技能的 `references/` 中。

对话挖掘工作流拥有自己的架构契约、智能体提示词、模板和验证协议。该协议实现了所选层级的专门机制；请执行所有兼容的通用步骤，并记录任何替代操作。它是将真实对话历史转化为技能可复用知识库的规范方式。

### 专门工作流：从已认可的成果语料库中提炼用户偏好

在采用通用流程之前，请先检查当前会话是否要求**从一批用户已认可的成品中提取用户的真实偏好**——例如已认可的 HTML 报告页面、生成的文档或设计。这是区别于上述两种来源的第三种提炼来源：材料是**产品，而非对话**，输出是**可执行的品味**（明确的原则、量化参数和词汇），而不是知识或安装修复方案。

以下任一信号出现，即表示适用：

- 用户列出成品并表示“这些都是我认可的样例”/“你来学到底什么是我想要的”/“从这些已认可的示例中提取我的偏好”。
- 某个品味校准技能（报告生成器、文档样式工具、幻灯片构建器）拥有持续增长的已认可样本语料库，而用户要求让该技能从中*学习*，而不是仅仅建立索引。
- 用户抱怨之前的更新“只加了示例”——只是将样本编入目录，而没有改变技能行为。

以下信号表示**不适用**：源材料是对话/纠正内容，而不是用户认可的产品（应使用对话挖掘）；样本尚未得到用户本人认可（认可是准入门槛——请先询问）。

适用时，请保留上文所选的验证层级，然后跳转至 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。由新语料库衍生的技能属于第 3 级；为现有技能增加实质性的新决策能力也属于第 3 级。该专门协议实现所选层级的语料库机制，并且不会将其降级；请执行所有兼容的通用步骤，并记录任何替代操作。其核心准则也适用于每次向现有技能添加材料时：**编目 ≠ 提炼**——在语料库表格中登记一个样本，并不会改变技能下一次运行的行为；对于每项新增内容，都要问“*这是否改变了某条决策规则？*”，如果对写入的所有内容而言答案都是否定的，就不要宣布提炼会话已经完成（方法论案例 15）。该工作流的主干是：通过脚本提取并对所有成果进行量化比较（每个模式至少涉及 3 个成果，并针对每个声称为常量的项目检查例外列表）→ 基于证据锚点进行分层归纳 → 写入决策规则层（将不变量与依赖语域的变量分开）→ 独立完整性审计（常设准则 #5）→ 回归审计。

### 现有成果研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——正是技能价值的来源。任何公共仓库都无法提供这些内容。但如果已有成熟工具可用，用户也不应浪费时间重新发明基础设施（API 客户端、身份验证流程、速率限制）。现有成果研究旨在为基础设施层寻找构建模块，从而使技能能够专注于编码用户独有的方法论。

**这是两个维度，不要将它们混为一谈。** 本节寻找的是*基础设施*层（可复用的工具 / MCP / 库 / 现有技能）。*方法论*层有两个独立的输入：用户的私有优势（仅属于他们，无法检索）**以及该领域既有的最佳实践 / 科学知识；根据常设准则 #3，默认应检索这些内容并将其纳入上下文。** 找到合适的工具并不意味着可以不做后者——一个采用了图表库、却从未吸收 Cleveland/Bertin 理论的可视化技能，其能力上限仍然受限于你的预训练。两者都要做。

**按以下顺序搜索这些渠道**（对 4-8 使用子代理并行搜索）：

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **对话历史** | 用户已验证有效的工作流、经过验证的 API 模式、调试期间所做的修正 | 在近期对话中 Grep 服务/API 名称 |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已完成集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中已配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 和 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 面向同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或对文档 URL 使用 `WebFetch` |
| 8 | **npm / PyPI** | SDK 或 CLI 包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己已验证有效的模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终优先——公共工具只是构建模块，而不是替代品。在竞争激烈的领域（金融、交易、专有业务运营），有价值的方法论绝不会公开。

**优先合并/扩展，而不是新建，并且要扫描每一个技能根目录——不只是 `~/.claude`。** 当渠道 1-3 找到与所请求领域重叠的现有技能时，通常正确的做法是扩展它或将内容合并进去——**但如果它位于一个不相关项目的工作树中，则方向相反：应从中提取内容并纳入你正在构建的技能，而不是将内容合并到它里面**（参见上方“扩展还是新建”检查中的项目级情形）（有一个真实的“新技能”任务最终变成了“让现有提取器充当新归档器的提取阶段”），而不是发布一个争夺相同触发条件的并行技能——两个相互重叠的技能会争抢触发机会，并让用户感到困惑。搜索时，**应主动发现安装根目录，而不是凭记忆列出一份清单**——使用上方“扩展还是新建”一节中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会完全漏掉源代码仓库、市场克隆和插件缓存，因为其中的技能目录以技能本身命名）。应运行覆盖范围检查，而不是盲信这句话：**每个项目自己的 `.claude/skills/`**，都是凭记忆列清单时最容易漏掉的根目录，因为该项目之外没有任何地方会引用它。用户已经安装在*任何位置*的技能，都是最有力的既有参考，而项目本地技能往往最为成熟：它是针对实际工作编写的。

**如果发现公开的 MCP 服务器或技能，请克隆并验证——不要轻信 README：**

1. **阅读实际源代码**——许多项目的 README 精美完善，代码库却徒有其表
2. **验证身份验证方式**——它是否与 API 的实际身份验证方式一致？（X-Api-Key 请求头、Bearer 或 OAuth——很多项目会弄错）
3. **检查测试覆盖率**——零测试 = 原型，而非生产级项目
4. **检查维护情况**——最后提交日期、未解决的问题数量、对错误报告的响应
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有用途冲突
7. **检查依赖规模**——庞大的依赖树会带来冲突并扩大安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用并在其上构建**——安装 MCP，然后将技能构建为工作流层，对用户的方法论进行编码 |
| 存在部分可用的 MCP 或 SDK | **扩展**——将其用于基础设施，并在技能中补齐缺失部分 |
| 公开技能涵盖相同领域 | **仅将其作为结构上的参考**——竞争领域中的公开技能本质上必然是通用的。用户的优势在于其私有 SOP |
| **存在可提供当前构建内容某项子能力的互补技能** | **打包进来**——将互补技能的自包含资产复制到你的包中并连接起来。不要依赖用户已预先安装该技能。请参阅下文的“互补技能” |
| 不存在任何公开实现 | **从头构建**——在编写完整技能之前，先验证 API 访问模式是否有效（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——与其使用存在集成摩擦和上游风险的“成熟”工具，不如拥有一个耗时 2 小时完成的自定义实现 |
| 用户有意取代已安装的技能（分支、强化版） | **随附取代工具包发布**——请参阅下文的“共存与优先级” |

#### 共存与优先级（有意重叠）

对于重叠问题，默认的解决方式是合并到现有技能中（见上文）。但当用户*有意*发布一个与已安装技能重叠的技能时——例如官方插件的分支或经过强化的内部版本——技能列表中会出现两个描述相似的条目，Claude 将在它们之间随机路由。请按以下逐级升级的顺序解决：如果重叠是意外造成的，则重命名；添加用于打破平局的描述（“取代 X——当两者同时出现时，始终使用此技能”）；对于分发的分支，使用 `scripts/generate_supersede_kit.py` 将条件式取代工具包写入技能——这是一种基于用户同意的 SessionStart 路由钩子，只会安装在确实存在竞争技能的机器上，在其他机器上会拒绝安装，并且会在任意一方消失时自行停用。有关其机制、决策表、SKILL.md 示例措辞和沙盒验证，请参阅：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此技能也使用同一个工具包来应对官方 skill-creator 插件（请参阅顶部的“第一步：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄无声息地失去了对*已安装技能群体*的触发权。** 一个技能所属的领域（图像生成、PDF 处理、仪表板）通常已经挤满了多个已安装的技能，而新技能可能会在自动路由竞争中输给所有这些技能。因此，**要尽早验证触发情况——内容足够好并不意味着构建已经完成。** 有了草稿后，通过 `claude -p` 发起几条真实的查询，并检查新技能是否确实胜出；如果没有，**明确指出它输给了哪个具体的竞争技能**（不同的查询往往会输给不同的技能）。然后要明确两件事：(1) **单靠文案并不总能在拥挤的槽位中胜出**——解决阶梯依次为：重命名 → 通过描述决胜/`SUPERSEDES` → 手动调用 → SessionStart 路由钩子（结构性措施；会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的规范）；(2) **修复方式取决于竞争技能的作者是谁**——如果竞争技能是*第三方*编写的 → 接受手动调用或使用路由钩子；如果竞争技能是*你自己*编写的 → 将它们合并/整合为一个，不要让自己的两个技能为同一个触发条件相互竞争。（完整的解决阶梯位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md) 中——该文件是 SSOT；此处和上文的摘要只是指引，不要各自独立扩展。）记录所选择的方案（例如添加一条“激活”说明，注明“手动调用，竞争技能均为第三方”），可以避免下一个会话重新争论这个问题。（方法论案例 13）

##### 互补技能（打包，不要依赖）

当你构建的技能涉及已有互补技能的领域时，有两种选择：

- **依赖该技能已安装**：很脆弱——用户可能没有安装它，也可能安装的是其他版本。每一次缺少依赖导致的失败，都可以追溯到这个选择。
- **将其打包**：把互补技能中可自包含的资源（脚本、模板、参考文档）复制到你自己的包中，并完成接线，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包进来。** 这对于以下内容尤为重要：
- 状态栏/UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证/清理脚本
- 常用的数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要一个状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。配置文件设置技能并不依赖用户先运行 `statusline-generator`，而是将 `statusline.sh` 打包进来，并在 `claude-profiles-init` 期间将其接入每个新配置文件。这两个技能仍然可以各自独立发挥作用，但这个封装技能能够独立运行。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装程序”。这会把依赖问题推给用户，并造成脆弱的安装顺序。应当改为将其打包。

研究完成后，通过 **AskUserQuestion** 展示研究结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，优先采用成熟的基础设施来处理底层管道，并为方法论层构建自定义逻辑——真正的价值就在方法论层。

### 访谈与研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准和依赖项。在彻底明确这些内容之前，不要编写测试提示词。

检查可用的 MCP——如果它们对研究有帮助（搜索文档、查找类似 Skill、查询最佳实践），并且子智能体可用，则通过子智能体并行开展研究，否则直接进行研究。事先准备好相关背景信息，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈，填写以下组成部分：

- **name**：Skill 标识符
- **description**：何时触发、执行什么操作。这是主要的触发机制——既要包含 Skill 的功能，也要包含应在何种具体场景下使用它。所有“何时使用”的信息都应放在这里，而不是正文中。注意：目前 Claude 倾向于“少触发” Skill——也就是在 Skill 本可发挥作用时不使用它。为解决这个问题，请让 Skill 描述稍微“积极”一些。例如，不要写成“How to build a simple fast dashboard to display internal Anthropic data.”，而可以写成“How to build a simple fast dashboard to display internal Anthropic data. Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a 'dashboard.'”

  **做好字符预算：description 有严格的 1024 字符上限，超过该长度将无法通过验证。** 这与上述“积极触发”的建议存在直接冲突——为扩大覆盖范围而添加的每个触发短语都会消耗预算——因此应在扩展之前而不是之后进行测量：`len(description)`，不要凭感觉判断。陷阱不在初稿（初稿很少接近上限），而在多年后的更新：更新会为新覆盖的范围添加触发条件；一个成熟的 description 往往距离上限只有几十个字符，此时**添加一个触发条件就是零和取舍——你必须删除一个现有触发条件来为它腾出空间。** 应有意识地进行这种取舍，并在提交中明确说明，因为悄无声息地删除一个触发短语，实际上就是缩小了 Skill 的触发范围，而在它不再为某人触发之前，没有人会注意到这一点。（实践中曾出现过这样的情况：一次更新为新覆盖的故障模式添加了触发条件，使 description 增长到 1280 个字符，经过两轮压缩才缩减到 1003 个字符——代价是删除了三个原有的触发短语；这本应是一项明确作出的决定，而不应在与验证器反复较量时才被发现。）必须删减时，应优先删除那些仍可通过同义词或相近短语触达其场景的短语，保留没有其他触达路径的短语；同时要记住，正文中的限定语（“on platform X and Y”、括号内的列举）通常比独立的触发短语更适合删除——正文信息可以从主体内容中重新推导，而触发短语不行。
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **Skill 的其余部分 :)**

### Skill 编写指南

#### Skill 的结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段均为可选。请在 `---` 标记之间使用这些字段配置 Skill 的行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必需 | 说明 |
|-------|----------|-------------|
| `name` | 否 | Skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 建议填写 | Skill 的功能及其适用场景。Claude 使用此字段来决定何时应用该 Skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在分叉的子代理上下文中运行。** 请参阅下方的“内联与分叉：关键决策”——选择错误会导致 Skill 失效。 |
| `agent` | 否 | 设置了 `context: fork` 时要使用的子代理类型。可选值：`Explore`、`Plan`、`general-purpose`，或来自 `.claude/agents/` 的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 可阻止 Claude 自动加载此 Skill。适用于你希望使用 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false` 可将其从 `/` 菜单中隐藏。适用于不应由用户直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略该字段会让 Skill 获得由用户权限设置控制的完整工具访问权限。设置该字段会不必要地限制 Skill 的能力。 |
| `model` | 否 | 此 Skill 处于活动状态时使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指明预期参数。示例：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此 Skill 生命周期的钩子。示例：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** Skill 内容中的 `$ARGUMENTS` 会被替换为用户在 Skill 名称后提供的文本。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### 内联与分叉：关键决策

**这是设计 Skill 时最重要的架构决策。** 选择错误会悄无声息地破坏 Skill 的核心能力。

**关键约束：子代理无法生成其他子代理。** 使用 `context: fork` 运行的 Skill（作为子代理）无法：
- 使用 Task 工具生成并行探索代理
- 使用 Skill 工具调用其他 Skill
- 编排任何多代理工作流

**决策指南：**

| 你的 Skill 需要…… | 使用方式 | 原因 |
|------------------------|-----|-----|
| 编排并行 Agent（Task 工具） | **内联**（无 `context`） | 子 Agent 无法生成子 Agent |
| 调用其他 Skill（Skill 工具） | **内联**（无 `context`） | 子 Agent 无法调用 Skill |
| 运行 Bash 命令以使用外部 CLI | **内联**（无 `context`） | 在主上下文中拥有完整的工具访问权限 |
| 执行单个聚焦任务（研究、分析） | **分叉**（`context: fork`） | 上下文隔离，执行过程干净 |
| 提供参考知识（编码约定） | **内联**（无 `context`） | 指南可丰富主对话的上下文 |
| 可被其他 Skill 调用 | **分叉**（`context: fork`） | 必须作为子 Agent 才能被生成 |

**示例：编排器 Skill（必须内联）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**示例：专家 Skill（适合分叉）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**示例：参考 Skill（内联，无任务）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skill 应当彼此**正交**：每个 Skill 只处理一个关注点，并通过组合协同工作。

**模式：编排器（内联）调用专家（分叉）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须以内联方式运行（无 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子 Agent 上下文中运行
3. 每个 Skill 只承担一项职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法，而不是复制代码

##### 流水线交接（顺序式 Skill 链接）

除了编排器/专家组合之外，Skill 还经常形成**顺序式流水线**，其中一个 Skill 的输出是下一个 Skill 的输入。每个 Skill 完成工作后，都应主动建议符合逻辑的下一步。

**模式：在 SKILL.md 末尾添加“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实场景中的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion 由用户**主动选择**——未经询问，绝不要自动调用下一个技能
2. 仅当输出能够自然地作为另一个技能的输入时才提出建议——不要强行建立关联
3. 提供一个“不用了，谢谢”选项——用户可能不需要完整的流水线
4. 建议应说明下一步**为什么**有帮助（例如，“ASR 输出通常包含识别错误”）
5. 最多提出 1-2 个建议——选项过多会导致决策疲劳

**何时添加交接：** 询问“此技能的输出通常会成为另一个技能的输入吗？”如果是，则添加一个“下一步”部分。如果这种关联很少见或很牵强，就不要添加。

**反模式：** 将不存在自然数据流关系的技能串联起来。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流程。

##### 以自动检测取代手动标志

**切勿为能够自动检测的功能添加手动标志。** 不要要求用户传递 `--with-codex` 或 `--verbose`，而应在运行时检测相应能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：** 自动检测能力，由用户决定范围。技能应主动发现自己能做什么并采取相应行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | 子代理可以使用 |
|-------------|----------------|-------------------|-------------------|
| （默认） | 是 | 是 | 否（以内联方式运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（显式委派时） |

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（名称 + 描述）——始终位于上下文中（约 100 词）
2. **SKILL.md 正文**——每当技能触发时加载到上下文中
3. **捆绑资源**——按需加载（数量不限，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是以特定行数为目标。一个没有填充内容的 600 行技能，胜过一个遗漏关键知识并迫使模型猜测的 200 行技能。如果技能越来越长，请问：“每个部分都发挥了应有的作用吗？”如果是，就保留它。如果某些部分只是为了凑篇幅，或在解释 Claude 已经知道的内容，则应精简这些部分，而不是删减有用内容。当一个技能确实涵盖多个领域时，应按领域拆分为参考文件，而不是人为地将所有内容强行塞进一个简短的主文件中。
- 对于现有技能，渐进式披露是一种内容迁移策略，而不是删除内容的判断依据。旧的运行时契约必须仍然能够从打包产物中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或评审者的记忆都不能替代运行时契约。
- 在 SKILL.md 中清晰引用参考文件，并说明何时应读取这些文件
- 对于大型参考文件（>300 行），应包含目录

**领域组织**：当一个 Skill 支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 避免意外原则

这一点不言自明，但 Skill 不得包含恶意软件、漏洞利用代码或任何可能危害系统安全的内容。如果对 Skill 的意图进行描述，其内容不应让用户感到意外。不要同意创建误导性 Skill，也不要创建旨在协助未授权访问、数据外泄或其他恶意活动的 Skill。不过，像“角色扮演为某个 XYZ”这样的内容是可以的。

#### 编写模式

在说明中优先使用祈使句。

**定义输出格式** - 可以像这样编写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式** - 加入示例很有帮助。可以像这样设置格式（但如果示例中包含“输入”和“输出”，可能需要稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得内置到 Skill 中的可用性模式** - 以下四种结构元素屡次将“能用但令人困惑”的 Skill 转变为用户真正能够驾驭的 Skill——它们是让一个被频繁使用的 Skill 变得易用的具体改进，因此当 Skill 包含多种模式、会运行命令或可以重新运行时，应优先采用：
- **入口决策树**：如果 Skill 有多种模式，在开头提供一个简短的“用户说了 X → 使用模式 Y”映射，让模型能够正确路由，而不是靠猜测。
- **每条命令后的预期输出块**：在命令之后立即展示“你应该看到什么”，这样模型（以及用户）就能区分真正的成功与无声失败。
- **故障排查部分**：列出已知的故障模式及其修复方法——对于其他人将在你无法查看的机器上运行的 Skill，这是最有价值的部分。
- **步骤 0 幂等性防护**：如果重新运行可能会重复已完成的工作，那么在执行任何成本高昂的操作之前，先通过一个低成本的“这件事是否已经完成？”检查作为开场。

### 写作风格

尽量向模型解释事情为什么重要，而不要大量使用生硬、陈腐的“必须”。运用心智理论，尽量让 Skill 具有通用性，而不是极度局限于特定示例。先写一份草稿，然后用全新的视角审视并改进它。

### 日期和版本引用

**保留事实日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 Skill 应写明“Suno v5.5（2026 年 3 月）”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 2025 年 8 月，则使用旧 API”）——日期一过，而又无人更新，这种逻辑就会立即出错。

规则：
- **发布日期、“最后验证”日期**：保留这些日期。它们是参考时间点，而不是失效日期
- **定价、排名、法律状态**：可以包含，但需标记为易变信息（“截至上次检查约为 $0.035/次生成”），以便读者知道需要重新核实
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前采用的方法，并可选择在折叠的/已弃用的部分中记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash/等）。

- **何时包含**：当同一段代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优势**：节省 token、结果确定，并且可以在不加载到上下文的情况下执行
- **注意**：Claude 可能仍需读取脚本，以进行修补或针对特定环境做出调整
- **用户可变数据应存放在捆绑包之外**：如果脚本会积累用户数据（纠错词典、学习到的偏好、缓存），请将其存储在稳定的、相对于主目录的目录下（例如 `~/.<skill-name>/`），并设置独立备份——切勿存放在 Skill 目录内。每次更新和套件迁移时，Skill 安装内容都会被清除并重新创建；相对于主目录的数据存储则会不受影响地保留下来。这正是一个会持续积累词典的 Skill 在完整套件迁移过程中实现用户数据零丢失的方式

##### 参考资料（`references/`）

旨在按需加载到上下文中，以辅助 Claude 工作流程和思考的文档及参考资料。

- **何时包含**：当 Claude 在工作时应参考相关文档时
- **示例**：用于财务模式的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库模式、API 文档、领域知识、公司政策、详细工作流指南
- **优势**：使 SKILL.md 保持精简，仅在 Claude 判断有需要时才加载
- **最佳实践**：如果文件很大（>10k 字），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或参考资料文件中，而不是两者都存放

##### 资产（`assets/`）

不用于加载到上下文中，而是供 Claude 在生成的输出中使用的文件。

- **何时包含**：当 Skill 需要在最终输出中使用相关文件时
- **示例**：作为品牌资产的 `assets/logo.png`，作为 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件架**：对于生成制品的 Skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、可逐字嵌入的片段，这些片段具有冻结的行为契约和注册表引用——请参阅步骤 4 中的组件架检查

##### 隐私和路径引用

**在应用以下任何内容之前，先确定目标用途。** 以下所有内容描述的都是 Skill
发布给陌生人使用时会出现的问题。对于存放在作者自己的私有
仓库中的 Skill，同样的“违规项”通常恰恰是它能够正常工作的原因——真实的绝对路径可以让
脚本直接运行，模板中的真实账户可以省去下次运行时重新填写
信息的步骤。`quick_validate` 会自动检测这一点（它会询问 `gh` 以确认所在仓库是否为私有仓库），
并在这种情况下将可移植性/标识符问题降级为提示；当私有 Skill 正在准备发布时，`--audience=public` 会强制执行
严格检查。

**在私有技能中，这些发现应由所有者决定，而不是由你决定。** 未经询问，不要将真实路径替换为占位符、改写硬编码凭据，或对示例进行“净化”——你会为了遵守一条针对其根本不会发布到的目标位置而制定的规则，破坏一个原本正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，并让所有者决定。（这一设计的先例是 npm 的 `"private": true`：它声明了一个目标位置，并据此改变工具所执行的规则；之所以添加它，是因为人们总是不小心发布内容。）

**对于计划公开分发的技能，以下要求至关重要**——其中不得包含用户特定或公司特定的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的技能安装路径，例如 `~/.claude/skills/`
- **允许**：技能包内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外情况**（严格按“禁止”列表实现的验证器会将这个技能本身判定为违规——对正常输入误报比漏报更糟）：当覆盖优先级决胜规则或署名要求必须明确指出发布者时，可以使用发布者自己的名称或品牌；当相关段落讨论的就是 `~/.claude/skills/` 之类的安装路径时，也可以使用这些路径（它们是教学材料，而不是硬编码依赖项）

**跨技能引用**：不带其他限定信息的相对路径始终表示“位于此技能自身的包内”——验证器和读者都会如此理解，因此，用这种路径指向另一个技能中的文件既无法通过验证，也会误导读者。指向另一个技能时，应在正文中写明所有者（“marketplace-dev 的 cache-and-source-patterns 参考资料”），并使用带命名空间的名称调用技能（`/suite-name:skill-name`，而不是不带限定信息的 `/skill-name`）。当技能在不同套件之间移动时，不带限定信息的跨技能引用会悄无声息地失效——有一次套件迁移正因如此而产生了 21 个失效的跨技能引用，经过两轮清理才全部修复。

##### 版本管理

**至关重要**：技能不应在 SKILL.md 中包含版本历史记录或版本号：

- **禁止**：SKILL.md 中的版本章节（`## Version`、`## Changelog`）
- **正确位置**：技能版本在 marketplace.json 的 `plugins[].version` 下进行跟踪
- **原因**：市场基础设施负责管理版本；SKILL.md 应包含不受时间影响的内容

#### 参考文件命名

文件名必须做到无需阅读内容即可理解其含义。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：是否有人仅凭文件名就能理解文件的内容？

有两种例外情况：使用连字符的名称与使用下划线的名称同样合适（分隔符从来都不是重点——重点是名称应具有自解释性）；位于已命名工作流目录内的文件（`workflows/<name>/workflow.md`、`patterns.md`）则由目录提供限定信息——目录已经提供了具体含义，而且重命名这些文件会破坏不同工作流之间的并行结构。

### Skill 创建最佳实践

### 完整评估测试用例（仅限 Tier 3）

仅当路由器选择通用 Tier 3 路径，或用户明确要求使用完整评估流水线时，才进入本节。不要仅仅因为 SKILL.md 发生了更改就使用本节。专用工作流遵循上文声明的 Tier 3 替代契约。

完成 Skill 草稿后，设计 2-3 个真实的测试提示词——即真实用户实际可能会说的话。**对于会操作实时系统（正在运行的服务、已登录的客户端、生产数据）的 Skill，请为每个测试提示词明确指定副作用预算**——例如，“仅进行只读探测并得出结论；不要执行下载/驱动 UI。”在“仅仅测试”时对实时环境进行变更属于真实操作，而不是测试。通过 **AskUserQuestion** 向用户展示这些内容：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——只保存提示词。下一步，在运行进行期间起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整 schema 请参阅 `references/eval_pipeline_schemas.md`（包括稍后要添加的 `assertions` 字段）。

## 完整配对评估流水线（仅限通用 Tier 3）

仅在选择通用 Tier 3 路径后运行本节。只要 Tier 3 仍获授权，这就是一个连续流程——不要中途停止。用户取消或降级的要求优先于本段；按照路由器中的规定停止重型流水线。不要机械地将其复用于 Tier 1、Tier 2，或其工作流已明确替代的专用机制，也不要使用 `/skill-test` 或任何其他测试 Skill。

将结果放入 `<skill-name>-workspace/`，使其与 Skill 目录处于同一级。在工作区内按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代内为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些目录——只需在执行过程中逐步创建。

### 第 1 步：在同一轮中启动所有运行（带技能和基线）

对于每个测试用例，在同一轮中启动两个子智能体——一个使用技能，另一个不使用。这一点很重要：不要先启动带技能的运行，之后再回来启动基线运行。一次性启动所有运行，以便它们大致同时完成。

**带技能运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（提示词相同，但基线取决于具体情境）：
- **创建新技能**：完全不使用技能。使用相同的提示词，不提供技能路径，并将结果保存到 `without_skill/outputs/`。
- **改进现有技能**：使用首次编辑前通过强制性现有技能回归门禁捕获的旧版本。让基线子智能体使用该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，请停止并从 Git 重建权威基线，然后再继续；绝不能使用已经编辑过的工作树作为旧基线。**要清楚这种比较能够识别什么：它只能衡量本轮的变化。** 如果你最希望验证的能力已经存在于编辑前快照中——例如，某个并行会话可能恰好在你开始之前提交了相同的修复——那么带技能版本与旧版本之间的 A/B 测试对该能力没有任何分辨力；当该能力是测试目标时，请选择更早的引用作为基线。

为每个测试用例编写一个 `eval_metadata.json`（断言目前可以为空）。根据测试内容为每个评估指定一个描述性名称——不要只使用 "eval-0"。目录也使用这个名称。如果本次迭代使用了新增或修改后的评估提示词，请为每个新的评估目录创建这些文件——不要假定它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：在运行进行期间起草断言

不要只是等待运行完成——你可以高效利用这段时间。为每个测试用例起草定量断言，并向用户解释这些断言。如果 `evals/evals.json` 中已存在断言，请审查它们并说明它们检查的内容。

好的断言应当能够客观验证，并具有描述性名称——它们在基准测试查看器中应该清晰易懂，让人一眼就能看出每个断言检查的内容。**应针对意图编写断言，而不是针对字面上的工具路径**——应写成“语音内容保留在答案中”，而不是“调用指定的读取器脚本”。如果某次运行通过另一条受认可的路径实现了意图（例如，读取一个已经内嵌转录文本的归档文件），它就应当通过；如果因未使用字面路径而将其判定为失败，就会制造假阴性，随后还会让你在错误的地方进行“修复”。主观性技能（写作风格、设计质量）更适合进行定性评估——不要强行为需要人工判断的内容添加断言；其真正的验证路径（历史任务重放、将生产环境作为评估并养成回写习惯、渲染并进行人工审查）列在“捕获意图”的问题 4 下。

断言起草完成后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试结果。

### 第 3 步：在运行完成时采集计时数据

每个子代理任务完成时，你都会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是采集这些数据的唯一机会——它们通过任务通知传递，不会持久化到其他位置。每条通知到达时就进行处理，而不要尝试批量处理。

### 第 4 步：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分**——启动一个评分子代理（或直接进行评分），让其读取 `agents/grader.md` 并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过编程方式检查的断言，应编写并运行脚本，而不是凭肉眼判断——脚本更快、更可靠，并且可以在多次迭代中复用。**但客观的 grep/脚本断言也可能产生双向误差**（同词异义导致误命中、措辞差异导致漏检），因此**基准测试通过率只是一种信号，而不是最终结论**：抽查每条断言实际匹配的内容，并留意基线运行是否揭示了 skill 本身的事实错误（类似“等等，数据确实在 API 里”的情况）。参见方法论 §5.3–5.6 和 §6.4。

2. **聚合到基准测试中**——从 skill-creator 目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及 mean +/- stddev 和 delta。如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md`，了解查看器所需的确切 schema。
将每个 with_skill 版本放在其对应的 baseline 版本之前。

3. **执行一次分析检查**——阅读基准测试数据，找出聚合统计信息可能掩盖的模式。有关需要关注的内容，请参阅 `agents/analyzer.md`（“分析基准测试结果”一节）——例如，无论是否使用 skill 都始终通过的断言（缺乏区分度）、高方差评估（可能不稳定），以及时间/token 权衡。

4. **启动查看器**，同时展示定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还需传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器陷入失效状态**：进程仍然存活，但没有任何程序在监听——使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或对该 URL 执行 curl（失败）；此处“没有日志输出”并不是可用的判断信号，因为上面的启动命令行已将其重定向到 `/dev/null`。终止该进程并改用 `--static`，而不是以相同方式重新启动。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或环境没有显示设备，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击“提交所有评审”时，反馈将以 `feedback.json` 文件的形式下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过 AskUserQuestion 告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

“输出”选项卡每次显示一个测试用例：
- **提示词**：所给出的任务
- **输出**：该技能生成的文件，在可能的情况下内联渲染
- **上一次输出**（第 2 次及后续迭代）：折叠区域，显示上一次迭代的输出
- **正式评分**（如果运行了评分）：折叠区域，显示断言通过/失败情况
- **反馈**：一个文本框，会在用户输入时自动保存
- **上一次反馈**（第 2 次及后续迭代）：用户上一次的评论，显示在文本框下方

“基准测试”选项卡显示统计摘要：每种配置的通过率、耗时和令牌用量，以及各项评估的明细和分析人员的观察结果。

可通过上一项/下一项按钮或方向键进行导航。完成后，用户点击“提交所有评审”，这会将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告知你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

反馈为空表示用户认为结果没有问题。请重点改进用户提出了具体不满的测试用例。

使用完查看器服务器后，将其终止：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进 Skill

这是整个循环的核心。根据路由器所选择的证据进行改进：对于第 1 层级，使用权威事实和确定性检查；对于第 2 层级，使用 1–2 个具名行为重放；对于第 3 层级，使用经过用户审查的成对结果。不要将第 3 层级的产物或步骤引入较低层级的迭代中。

### 如何思考改进

1. **从反馈中归纳。** 这里发生的事情，从大局来看，是我们正在尝试创建能够在许多不同提示词中使用一百万次（也许真的是一百万次，甚至可能更多，谁知道呢）的 Skill。在这里，你和用户只围绕少数几个示例反复迭代，因为这样有助于加快进度。用户对这些示例了如指掌，可以快速评估新的输出。但如果你和用户共同开发的 Skill 只对这些示例有效，那它就毫无用处。与其做一些琐碎且过度拟合的改动，或加入压迫性极强的“必须”约束，不如在遇到某个顽固问题时尝试拓展思路，使用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，而且也许你会找到非常出色的方法。

2. **在不删除契约的前提下保持提示词精简。** 删除那些没有发挥应有作用的内容，但对于从现有 Skill 中删除的每一项内容，在新旧版本审计对其完成分类之前，都应将其视为潜在的回归问题。将详细但可复用的行为移入直接链接的参考资料中；不要让它只存在于评估、变更日志或你的记忆里。阅读完整记录，而不仅仅是最终输出——如果 Skill 导致了无效工作，应简化指令并重新运行旧有能力用例，而不是想当然地认为文字越少，行为就越好。

3. **解释原因。** 尽最大努力解释你要求模型做每件事背后的**原因**。如今的大语言模型很*聪明*。它们具备良好的心智理论，而且当获得良好的框架时，能够超越机械执行指令，真正把事情做成。即使用户的反馈很简短或带有挫败感，也要努力真正理解任务，理解用户为什么会写下这些内容、他们实际写了什么，然后将这种理解传达进指令中。如果你发现自己在用全大写的“始终”或“绝不”，或使用极其僵化的结构，这就是一个警示信号——如果可能，请重新组织表达并解释其中的理由，让模型理解你所要求的事情为何重要。这是一种更人性化、更强大且更有效的方法。

4. **寻找重复工作——既要查看评估记录，也要查看提炼出该 Skill 的对话。** 阅读测试运行记录，留意各个子代理是否都各自独立编写了相似的辅助脚本，或采用了相同的多步骤方法来完成某件事。如果 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这就是一个强烈信号，表明该 Skill 应该内置这个脚本。只编写一次，将其放入 `scripts/`，并让 Skill 使用它。这样可以避免未来的每次调用都重新发明轮子。同样的信号也隐藏在你用于提炼 Skill 的源对话中——只要该会话编写过一次某段代码，未来的每次运行就都必须重新编写它；不要等到评估运行来证明这种重复（跳过评估循环的 Skill 永远无法获得这种证明——创建流程第 4 步中的脚本检查正是用于捕捉这些情况的检查点）。

5. **逐字回写修正——同一会话、两个层级。** 对于经过品味校准的技能，用户的修正本身就是评估集，但前提是这些修正被写入未来运行能够读取的位置。回写具备以下两个特性时才能实现收敛：(a) **逐字记录修正内容**，不要转述——原话包含校准信号，而摘要会将其抹平（“绝对禁止这种东西”表达了明确的硬性边界；“user prefers fewer jumps”则没有）。在修正所针对的规则中引用用户原话，并注明日期。(b) **在修正发生的同一会话中，将其回写到两个层级**——既修复产物，也修复技能的规则/参考资料/组件；仅修复产物的修正对未来的每次运行都不可见，而推迟到“稍后”的修正通常永远不会真正写入。回写时，检查技能自身的文本是否曾经*教导*刚刚被禁止的反模式——一次修正常常会证伪某条现有指令，而保留原有建议必然导致问题再次发生（真实案例：某个决策页面契约建议采用跳转式的“goto anchors to the referenced figure”；用户恰恰禁止了这一做法，因此回写必须修改原有句子，而不能只在旁边添加一条新规则）。当被修正的内容是交互片段时，回写的最后一步是将其晋升到组件货架——参见步骤 4 中的组件货架检查。

这项任务非常重要（我们正试图每年创造数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请从容处理并真正深入思考。我建议先写一版修订草稿，然后重新审视并加以改进。请真正尽最大努力站在用户的角度，理解他们想要什么、需要什么。

对于第 1 层级，有明确证据支持的修正应直接应用；只有当证据确实留下需要选择的空间时才询问。对于第 2 或第 3 层级，当用户反馈揭示出有意义的设计分岔时，通过 **AskUserQuestion** 展示改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (if the total exceeds 2, reclassify to Tier 3 before running them)
```

### 迭代循环

改进技能后：

1. 将改进应用到技能
2. 仅重新运行所选层级的证据：
   - **第 1 层级：** 始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配子类型的证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归。不要创建迭代工作区。
   - **第 2 层级：** 仅重新运行相同的 1–2 个具名带技能示例和窄范围检查。不要添加基线、基准测试、查看器或评估工作区；任何对这些内容的请求都会将工作重新归类为第 3 层级。
   - **第 3 层级，在仍获授权期间：** 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新技能，基线始终是 `without_skill`；对于现有技能，不可变的原始编辑前版本在每次迭代中始终作为保留性基线。紧邻的上一次迭代可以作为补充，但绝不能取代原始基线。
3. 在对规则、契约或数字进行实质性更改后，应用纪律 #5。对于通用的第 3 层级路径，还应启动评估审阅器，并通过 `--previous-workspace` 指向上一次迭代；专用工作流使用其声明的审阅器机制。
4. 对于通用的第 3 层级，等待用户审阅新的查看器结果；其他情况下，根据所选层级的证据作出决定，除非仍存在真正需要用户选择的事项。
5. 阅读新的证据或反馈；如果它们证伪了当前版本，则再次改进，并在同一层级重复此过程。

用户请求的取消或降级在任务剩余期间持续有效，且不会改变其分类。除非用户明确重新授权执行 Tier 3，否则不要重新启动成对评估、基线、评分器、聚合或查看器工作。

在每次**通用 Tier 3**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（所有内容看起来都很好）
- 你没有取得实质性进展

## 描述优化

SKILL.md 前置元数据中的描述字段是决定 Claude 是否调用某个技能的主要机制。创建或改进技能后，主动提出优化描述，以提高触发准确率。

### 第 1 步：生成触发评估查询

创建 20 条评估查询——混合包含应触发和不应触发的查询。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须真实可信，是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要使用抽象请求，而要使用具体、明确并包含相当丰富细节的请求。例如，文件路径、有关用户工作或处境的个人背景、列名和值、公司名称、URL。可以加入一点背景信息。有些查询可以全部使用小写字母，或包含缩写、拼写错误或口语化表达。混合使用不同长度，并重点关注边界情况，而不是让它们都泾渭分明（用户之后将有机会确认这些查询）。

不佳：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

良好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**的查询（8-10 条），要考虑覆盖面。你需要为同一种意图设计不同的表达方式——有些正式，有些随意。包括用户未明确说出技能或文件类型、但显然需要该技能的情况。还应加入一些不常见的使用场景，以及该技能会与其他技能竞争但理应胜出的情况。

对于 **should-not-trigger** 查询（8-10 条），最有价值的是那些差一点就会触发的查询——它们与该技能共享关键词或概念，但实际上需要的是其他东西。考虑相邻领域、那些容易让简单关键词匹配误触发但实际不应触发的歧义表述，以及查询虽涉及该技能所做的事情、但在具体上下文中更适合使用其他工具的情况。

需要避免的关键问题：不要让 should-not-trigger 查询显得明显不相关。把“编写一个斐波那契函数”作为 PDF 技能的负向测试太简单了——它测试不出任何东西。负向案例应该真正具有迷惑性。

### 步骤 2：与用户一起审核

使用 HTML 模板向用户展示评估集以供审核：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（外面不要加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中的最新版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 步骤 3：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期检查进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示词中的模型 ID（即支持当前会话的模型），以便触发测试与用户的实际体验保持一致。

运行期间，定期查看输出末尾，向用户更新当前进行到哪个迭代以及评分情况。

该命令会自动处理完整的优化循环。它将评估集拆分为 60% 的训练集和 40% 的保留测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每次迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试分数而非训练分数选出，以避免过拟合。

**如果循环检测到完全无响应，它会在第 1 次迭代后自行中止——你无需手动捕获这种情况。** 这是 `run_loop.py` 中的代码级防护机制，而不只是一条建议；它会区分“第 1 次迭代中所有 should-trigger 查询的触发次数均为零”的两种原因：

- `exit_reason: "infra_error: ..."` — 某些查询执行（应触发*或*不应触发）抛出了异常（claude CLI 不在 PATH 中、超时时间过短、网络中断），而不是正常返回“未触发”。此项会被*优先*检查，并且只要非零错误计数就会被刻意触发，即使几十次运行中只有一次偶发失败也不例外——崩溃无论多么罕见，都是比“没有任何触发”更具体、更可操作的线索，而且修复对象是环境，而不是重写描述。消息中的比率（例如 `3/15`）反映了严重程度：较大的比例意味着“停止，修复你的环境”；较小的比例若同时伴随大量正常的 0 触发运行，则意味着环境中可能存在值得检查的小幅不稳定，*并且*描述也可能确实有问题——两者都要检查。无论哪种情况，都要查看 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` — 仅在上述分支排除所有执行错误后才会检查，因此这意味着每个应触发查询*和*不应触发查询都*确实运行了*，但仍然一次也没有触发（这正是通过零分母默认值得到“precision=100%”的实际含义：不是“完美”，而是“没有可供相除的数据”）。该探针实际上什么也没有测量到——在对描述做任何修改之前，先去诊断竞争项冲突或低阈值领域（见下文）。

这两项检查都**仅针对第 1 次迭代**运行，并且**仅在应触发查询零次触发时**运行——第 1 次迭代较弱但并非零触发（例如 9 次中触发 1 次）属于另一种可能可以恢复的情况，因此会被刻意留给后续迭代处理。`degenerate_harness` 还要求不应触发查询同样零次触发：如果描述只是极性颠倒——遗漏了每个正例，却意外匹配了多个负例——那么探针已被证明能够正常工作，且 `improve_description` 有真实的梯度可供利用，因此防护机制不会中止这种情况（它只会中止真正失效的探针）。此外，它还要求任一侧的执行错误数均为零——某个抛出异常的不应触发查询实际上从未运行，因此其“0 次触发”不能作为探针失效的证据；这正是该情况会转而进入 `infra_error` 的原因。无论是哪一种情况，程序都会立即中断并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因则用于表明，不应将本次特定运行的数值解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了完整的 5 次迭代循环；整整两次迭代——每次都包含完整的评估批次、数分钟的实际耗时和数十次 `claude -p` 子进程调用——返回的结果均为 precision=100%/recall=0%/分数完全相同，之后才有人查看这些数值，而每个应触发查询*和*不应触发查询都一次也没有触发。仅凭第 1 次迭代就能诊断出故障；第 2 次及后续迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会呈现一个横幅，因此浏览器视图会传达与 JSON/stderr 相同的信号，而不只是在这两个可见性较低的渠道中显示。（该防护机制的早期草案只检查应触发查询的触发情况；经过两轮独立审查——每一轮都由一个新代理完成，第二轮检查第一轮的修复，而不是重新覆盖已检查过的内容——构造出了极性颠倒反例、基础设施与描述之间的歧义、负例侧错误遗漏问题，以及审查过程中暴露出的一个既有 `--holdout 0` 报告崩溃问题，所有问题均在发布前得到修复。）

这个防护机制无法覆盖一种情况：使用 `--runs-per-query 1`（默认值为 3）时，对于一个确实约有 50% 触发率的应触发查询，完全可能仅仅因为随机性而得到 0/1 的结果，从而因噪声而非探针失效触发防护。默认的 `runs_per_query=3` 使“每个正向查询的每次重复运行都为零”成为一个强烈信号——如果你将它调低，这个防护机制的误报风险也会随之升高。

**在信任 `best_description` 之前，先对测试框架进行健全性检查——即使上述两个防护机制都未触发，它仍可能返回空洞无效的输出。** 这两项检查只能捕获第 1 次迭代时的*完全*失败；测试框架也可能在全部 5 次迭代中始终维持微弱但非零的信号，勉强运行下去，而始终不会触发任何一项防护。如果第 1 次迭代之后的每次迭代都报告**召回率持续接近 0%，且分数完全相同或几乎相同**，那么其根本问题与防护机制无法排除的问题相同——所谓“胜出”的描述通常只是第 1 次迭代结果周围的噪声，实质上没有变化。在应用任何 `best_description` 之前，请自行运行一个显然应该触发的查询，并确认召回率 > 0。如果各次迭代的召回率始终持平，就意味着测试框架中存在隐藏变量（常见情况是：该技能在触发竞争中输给了已安装的竞争技能——参见下文的“共存”）——请勿应用它所谓的“最佳”结果；应改为手动编写描述，并使用真实探针进行验证。（方法论案例 12、14）召回率为 0 还有第二种根本原因，与输给竞争技能不同：该技能的任务领域属于*低阈值*领域——模型会自行完成任务，从不查阅任何技能——详情见下文*技能触发的工作原理*末尾。在采取措施之前，请先区分这两种情况，因为其解决方法恰好相反：竞争技能问题应通过优先级/取代机制解决，而低阈值领域则应完全放弃触发探针，改用生产场景作为评估。

**当你使用 `claude -p` 自行探测触发情况时，应收集该次运行中的所有技能调用，而不只是第一次调用——并记住，工具调用只是代理指标。** `UserPromptSubmit`/`SessionStart` 钩子可能会在模型作出选择*之前*注入一个无关技能，因此“在第一次 Skill 调用时退出”的探针会误报“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“技能内容是否影响了输出”（模型可能读取技能，但没有可见的 Skill 调用），也不等同于“输出是否正确”。存在缺陷的探针本身就是一个隐藏变量，会让你不断依据错误结论进行优化。

### 技能触发的工作原理

理解触发机制有助于设计更好的评估查询。技能会以名称和描述的形式出现在 Claude 的 `available_skills` 列表中，而 Claude 会根据该描述决定是否查阅某项技能。需要重点了解的是，Claude 只会针对自身无法轻松处理的任务查阅技能——像“读取此 PDF”这样简单的单步骤查询，即使与描述完全匹配，也可能不会触发技能，因为 Claude 可以使用基础工具直接处理。复杂、多步骤或专业化的查询在描述匹配时能够可靠地触发技能——但存在一个系统性例外（低阈值任务领域），详见本节末尾。

这意味着你的评估查询应该足够实质化，让 Claude 确实能从查阅技能中获益。像“读取文件 X”这样的简单查询并不是好的测试用例——无论描述质量如何，它们都不会触发技能。

**但有些技能无法通过这项测试，是因为存在任何查询改写都无法解决的原因——该技能的整个*职责*就是执行低门槛任务。** 上一段将问题归咎于查询（“写一个更实质化的查询”）；这里讨论的是与之正交的情况，即阻碍触发的是技能的*领域*。如果某个技能的用途是完成 Claude 仅凭基础工具就会自行完成的事情——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询已经完整说明要求（“将这个 48k 立体声 wav 降采样为供 whisper 使用的 16k 单声道”，并附带路径），也不会触发该技能：模型会直接使用 `Bash`/`ffmpeg`，根本不会查阅任何技能。增加查询的实质性无法解决这个问题，因为“我自己就能完成”的判断针对的是*任务*，而不是措辞。

在白白耗费一轮优化之前，先诊断这种情况：通过 `claude -p` 运行一个现实的查询，并观察模型在整个运行过程中是否*曾经*查阅该技能（依据上面的 ALL-skill-calls 规则），还是直接转向 `Bash` 并自行完成任务。如果它从未查阅，该触发探针在结构上就无法检测这个技能——无论你如何编写描述，召回率读数都会约等于 0，而这个零衡量的是模型凡事亲力亲为的倾向，而不是你的描述。不要再针对 `claude -p` 的召回率进行调优，而应以真正的方式进行验证：将生产环境用作评估（用户下一次真实的*交互式*使用——无头模式的 `-p` 比真实会话更偏向直接采取行动，因此会系统性地低估触发率），并在技能会生成可检查产物的情况下进行输出对比。（在一个音频预处理技能上观察到：无头模式的 run_eval 扫描在*每个*查询上的召回率读数都为 0——包括一个显而易见的“转录此录音”查询——而手动执行的 `claude -p` 探测显示，模型直接转向 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个零衡量的是无头模式下偏向直接采取行动的倾向，而不是描述；真正的信号只会在交互式使用中显现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新技能 SKILL.md 的前置元数据。向用户展示修改前后的内容并报告分数。

## 关键要求：在源位置编辑技能

**绝不要先编辑已安装的技能副本。** 除非用户明确表示它们是源文件，否则应将以下所有位置视为已安装副本或运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装的副本会导致更改：
- 在缓存刷新时丢失
- 无法同步到源代码管理
- 浪费精力，之后还需要手动重新合并

**务必确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，先执行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果 available-skills 列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。先找到由仓库支持的源，编辑并验证它，只有当用户需要立即在本地运行时使用时，才同步已安装的副本。

**然后回答后续问题，以确定“同步已安装的副本”是否真的需要做：运行时是否已经直接读取源？** 三种安装方式的行为不同，猜错要么会浪费一次同步，要么会导致所做的编辑在用户下一个会话中根本不可见：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **以符号链接方式**链接到源代码树中 → 编辑内容*就是*运行时所用内容，无需同步。
- **具有 `source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本升级对于其他消费者而言只是记录管理，并不是本地激活步骤。
- **任何缓存或复制的安装**（源自 git 的 Marketplace、通过 `cp -r` 安装）→ 运行时使用的是独立副本，确实需要先运行官方更新命令，新内容才会生效。

**并且要通过内容验证激活情况，而不是通过版本字符串。** 注册表可能记录一个磁盘上并不存在的路径或版本——某个会话曾读取到一条插件记录，其中指定了一个名称包含*新*版本号的缓存目录，并差点将更新报告为已生效；但该目录从未创建过，而真正的运行时路径一直都是指向源的符号链接。权威检查方法是，在运行时文件中 grep 只有新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一 skill 仓库上的并发会话

高级用户会同时运行多个 Claude 会话，而 skill 仓库正是这些会话容易发生冲突的地方：当你编辑 skill A 时，另一个会话可能会在你操作期间提交 skill B（甚至是 skill A 的前一轮修改）。一个真实会话在一小时内遇到了全部三种症状——由于文件在读取后发生变化而导致 `Write` 被拒绝，以及 HEAD 在任务进行期间移动了两次（方法论案例 16）。真正的问题不是发生冲突，而是使用了过时的基线，或某次覆盖式写入悄无声息地混合了两个会话的工作。长期规则如下：

1. **只要任务开始时仓库是干净的，就应从 git ref 创建基线，而不是从工作树创建**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并将 `--baseline-origin git-ref:<sha>` 传递给审计。几分钟前创建的工作树快照，可能会因为其他人随后提交而成为一棵已不存在的工作树的基线。**请解压到一个全新且不存在的目录中。** 如果解压到已有目录，`tar -x` 会悄无声息地覆盖同名文件，同时保留归档中不存在的文件——这会生成一个在解压时没有任何警告的混合快照，随后 `compare` 会因其与 ref 不匹配而拒绝它。同一个陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会进行嵌套而非替换——而在 `mv` 被设置为 `mv -i` 别名的环境中，目标已存在的重命名操作只会打印一行提示，并默认*不*执行，但无论是否执行，退出码都是 0（已通过实验验证）。
2. **写入前重新读取**：当写入被拒绝或已经过去一段时间时，先对比发生了哪些变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图融入你的版本——对方的编辑通常有其原因——然后再写入。
3. **提交前检查 HEAD *以及当前所在的分支***。`git log --oneline -1` 可以发现 SHA 发生移动：如果它在创建基线后发生了变化，请在执行 `verify` 前，针对新的 ref 重新运行回归 `compare`——审计工具无论如何都会拒绝过时的评审（“skill 更改之后”），因此自行提前发现可以省去一个来回。但另一个会话可能做出比推进 HEAD 更糟糕的事情：**它可能在你不知情的情况下切换分支**，因为 checkout 会影响整个工作树。真实过程是——执行 `checkout -b feat/x`，编辑了一段时间，与此同时另一个会话执行了 `checkout main` + `pull`；随后提交落在了 **main** 上，违反了仓库的“绝不直接提交到本地 main”规则，而 feature 分支仍然指向旧基线。因此，请将 `git branch --show-current` 加入提交前检查，而不只是检查 SHA。如果这种情况已经发生，`git reflog` 是进行权威还原的依据（它会按顺序记录每次 `checkout: moving from X to Y`），而修复方法——**前提是工作树干净**——是先执行 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：这两项操作都只移动 ref，完全不会触碰工作树，因此不会像 `reset --hard` 那样破坏并行会话中尚未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——不能让另一个会话尚未提交的工作混入你的提交。（这本来就是打包规则；在并发情况下更是至关重要。）
5. **每个会话成果只升级一次版本**，而不是每一轮编辑都升级：同一会话中针对一个 skill 连续进行的多轮修改，应合并为一次版本升级——除非某个中间状态已经被使用（用户或另一个会话已经提交并拉取），此时每个已被使用的状态都应拥有自己的版本。

## 技能创建流程（分步说明）

创建或更新技能时，请按顺序执行以下步骤。仅当某个步骤明确不适用时才跳过。

### 第 0 步：检查先决条件

在开始任何技能相关工作之前，自动检测所有依赖项，并主动安装缺失的依赖。在工作流程进行到一半时才发现缺少工具（例如，在打包时发现缺少 gitleaks，在验证时发现缺少 PyYAML）会浪费时间并打断工作流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，自动安装能够安装的依赖项，并向用户提供一份汇总检查清单。仅当所有阻塞性依赖项均已满足时才继续。

主要阻塞项：Python 3、uv、PyYAML（验证/打包）以及 gitleaks（安全扫描）。仅当所选验证层级实际运行智能体评估时，claude CLI 才是阻塞项。运行 Python 工具时，应显式使用 uv 依赖声明，例如，从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 会依赖当前环境中的站点包，并且可能找不到 PyYAML。

### 第 1 步：通过具体示例理解技能

仅当技能的使用模式已经得到清晰理解时，才跳过此步骤。

要创建有效的技能，需要清楚理解该技能将如何使用的具体示例。这种理解可以来自用户直接提供的示例，也可以来自经用户反馈验证的生成示例。

例如，在构建图像编辑器技能时，相关问题包括：

- “图像编辑器技能应该支持哪些功能？编辑、旋转，还是其他功能？”
- “你能提供一些该技能使用方式的示例吗？”
- “用户说什么内容时应该触发该技能？”

为避免让用户不知所措，不要在一条消息中询问过多问题。

### 第 2 步：规划可复用的技能内容

通过以下方式分析每个示例：

1. 考虑如何从头开始完成该示例
2. 确定 Claude 应具有的适当自由度
3. 确定在重复执行这些工作流程时，哪些脚本、参考资料和资源会有所帮助

**使具体程度与任务风险相匹配：**
- **高自由度（文本指令）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，同时允许适度变化
- **低自由度（精确脚本）**：操作容易出错，一致性至关重要

### 第 3 步：初始化技能

如果技能已经存在，则跳过此步骤。

从头创建新技能时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个技能模板目录，其中包含正确的前置元数据、资源目录和示例文件。

### 第 4 步：编辑技能

在编写之前，获取 Anthropic 的最佳实践文档（链接见上文“技能创建最佳实践”）和方法论参考资料——即使你觉得自己已经了解这些内容，也要这样做：文档会更新，训练数据中的版本会过时，而“我基本了解”恰恰是编辑者跳过这一步并错过最新指导的状态。

编辑时，请记住，该技能是为另一个 Claude 实例创建并供其使用的。请重点关注对 Claude 有益且并非显而易见的信息。

**现有技能迁移关卡——首次编辑前必须完成：**

1. 编辑前，捕获当前完整的软件包。对于非 Git 源或存在未提交更改的源，请使用该工具，以便快照携带可验证的来源清单：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于由 Git 跟踪且工作区干净的源，请从选定的 ref 中提取该目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   应包含 SKILL.md、参考资料、脚本、资源、工作流和现有评测，而不仅仅是主提示词。绝不要复制已经编辑过的目录树并将其标记为“编辑前”。**请使用一个此前从未有任何内容解压到其中的目录**——复用一个已经包含早期运行内容的目录，会让 `tar -x` 在静默覆盖同名文件的同时，保留新归档中不存在的陈旧文件，从而生成混合快照，而解压时不会提供任何信号（`compare` 只会在之后通过目录树哈希不匹配间接发现它）。有关此陷阱的更完整说明，包括基于 `mv` 的变体，请参阅下文的“在同一技能仓库中运行并发会话”。
2. 盘点旧技能的参与者/任务、触发上下文、运行时契约、命令/标志、失败和恢复场景、页面/领域变体、捆绑资源以及评测覆盖情况。在进行结构性重写之前，为重要的旧有边界行为添加保留用例。
3. 编辑完成后，生成新旧版本对比审查：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，请将最后一个标志替换为 `--baseline-origin git-ref:<ref>`。该工具会将 ref 解析为不可变提交，并根据该目录树验证每个包含的文件及其可执行位。

   **重命名或移动技能目录本身**（而不仅仅是编辑其内容）会改变 `--after` 的路径，而两种基线模式都使用该路径进行身份验证——默认情况下，`compare` 会拒绝这种情况（假定 `--before`/`--after` 是因意外而不匹配），并报出 `pre-edit snapshot source identity does not match the edited skill`。添加 `--renamed-from <old-path>`（即 `snapshot` 的 `--source` 所指向的路径，或在 `git-ref:` 情况下技能相对于其仓库根目录的旧路径），以显式声明此次重命名；随后，身份检查会验证该路径而不是 `--after`，同时内容/目录树哈希检查保持不变，因此实际不匹配的配对仍会失败。**请向 `--renamed-from` 传入绝对路径。** 此命令接收的每个路径在以相对路径给出时，都会相对于当前工作目录解析——而不是相对于 `--after`，也不是相对于彼此——并且 `--renamed-from` 通常指向一个已不存在的目录（因为它已被重命名移走），所以不会像 `--before`/`--after` 那样通过存在性检查来捕获错误的路径解析；它只会在更深层的位置以令人困惑的方式失败。这尤其容易影响 skill-creator 自身的编辑：上面的 `cd <skill-creator-path>` 指向 skill-creator 自己的仓库，而该仓库通常与正在审计的技能所在仓库*不同*，因此相对形式的 `--renamed-from` 会在没有任何提示的情况下相对于错误的仓库进行解析。

4. 审查每个候选项。必须且只能使用一种处置方式，并记录具体的
   证据/理由：`preserved_or_moved`、`intentional_sanitization`、
   `intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable`
   或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将某项
   运行时能力移出此 Skill 时，必须提供负责接收它的目标位置、当前的
   边界证据以及可追溯的用户批准。明确弃用时也必须引用/追溯用户的
   批准。关于已保留/已净化/已修复的声明必须指向真实的当前文件及行号，
   并包含一段简短的 `contains` 引文，以便验证器可以在附近找到。
   文件级候选项使用当前文件指纹，并附上具名的语义审查，说明行为为何
   得以保留——仅凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本——
   `classify` 子命令会完成机械性工作（在目标文件中定位引文所在行、
   填充证据/语义审查，并在缺少引文或理由过短时快速失败）。每项处置
   方式和理由仍由你编写；它只负责将其填入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 ID）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置方式默认为
   `preserved_or_moved`；文件级候选项只需提供目标位置和不少于 40 个
   字符的理由——系统会替你计算指纹）。**务必从目标文件中复制 needle
   （使用 Read/grep/sed），绝不要凭记忆输入**——查找采用精确匹配，
   缺少引文时会快速失败；手动输入的 needle 实际会因两种情况而失败：
   全角与半角标点不一致（`：` 与 `:`），以及凭记忆改述造成的近义字符
   不一致（`也` 与 `都`）——这两种问题都会逃过自我审查，只有在工具
   拒绝整份映射时才会被发现（曾有一份映射正是因为这两个原因连续两次
   被拒绝）。
5. 验证已完成的审查。任何后续编辑都会导致哈希值使审查失效，因此，
   当候选项发生变化时，需要重新生成并重新分类。验证通过后会写入
   `.skill-regression-reviewed`，这是一个与内容绑定的本地状态回执。
   它有助于检测后续编辑，但刻意不作为独立的打包授权依据；打包过程
   会自行重新验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

各个关卡步骤的成功状态如下（这是实际输出，因此可以识别无提示的失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在需要审查的候选项，而不是工具执行失败；
返回 2 表示调用/运行时失败。该工具可以证明内容被原样移动以及接口得以保留，
但会刻意拒绝根据模糊的词语重叠来推断语义等价性。像“检查权限被拒绝”这样的
泛泛表述，不能悄无声息地取代“已登录但不具备角色”这一精确约定。还要检查标记为
`only_outside_runtime` 的候选项：如果运行时行为只存在于评估、测试或不可达的
参考资料中，那么正常调用路径中就不存在该行为。

**每次编辑 SKILL.md 后都要立即验证——不要等到打包时（第 7 步）。** 此检查能够提前发现的故障是真实存在的：以前言描述为例，将其写成未加引号的 YAML 标量，在 Claude Code 宽松的解析器中可以正常解析，但会在严格的解析器中出错（codex 曾针对一个已经发布数月的 skill 报告 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中如果包含 ` #`，甚至不会报错——它会悄无声息地截断其后的所有内容，导致触发关键词消失，而所有扫描仍然显示正常。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**当描述包含 `: ` 或 ` #`，或由多个句子组成时，请将其写成 YAML 块标量**（`description: >-` 后接缩进段落）——块标量原生支持这两个字符——自上述事件发生后，这是每个新增或编辑的描述所应遵循的推荐约定。

**更新现有 skill 时**：扫描每份现有参考资料和捆绑资源，检查是否需要进行相应更新，然后通过上述迁移门禁。迁移某项约定时，SKILL.md 中必须提供直接的运行时指针；评估或变更日志不能替代它。

接下来的三项检查是**升级探查，而不是无条件扩大范围**。如果据此采取行动会新增或实质性更改某项能力、工作流分支、输出约定、脚本行为、依赖项、权限或外部写入操作，请先停止，并在更改 skill 之前将其重新归类为第 3 级。第 1 级和第 2 级可以审视这些问题，但不会因此获得新的交付项。

**脚本检查**：在认定编辑完成之前，请思考：*源对话（或评估记录）编写了哪些代码，而这些代码若不处理，未来每次调用时都必须重新编写？* 如果所选级别已授权开展相应的能力工作，请将其捆绑到 `scripts/` 中（参数化并经过清理），并修改文档以指向该脚本。否则，请将该信号记录为第 3 级提案，不要将其作为第 1/2 级编辑的附带结果进行捆绑。二者的分工是：**脚本负责执行，文档负责传达理解**——如果某项 skill 的方法只存在于正文说明中，那么每次运行时都要重新付出完整的编写成本。这项检查之所以放在这里、放在编辑步骤中，正是因为跳过评估循环的路径（对话提炼、直接编辑）永远不会到达“改进 skill”中针对评估记录的这项检查。

**组件库检查（针对制品内嵌片段提出的同一问题）**：Scripts 检查涵盖的是 *skill* 执行的代码；生成制品的 skill（报告页面、演示文稿、文档）也会逐渐积累由其 *输出* 嵌入的片段——图像叠加组件、吸顶导航、图表配置、CSS 块。如果连续多次输出都手写了相似片段，这就是指向另一个库的同一种重复信号。在添加 `components` 子文件夹或注册表引用之前，先应用上述升级规则；第 1/2 级应提出该建议，但不得创建组件能力。获得第 3 级授权后，真正让代码片段成为库组件的是围绕它建立的契约：(a) **逐字嵌入块**——将 BEGIN/END 标记之间的内容完整复制到制品中，零依赖，从而让单文件制品保持自包含；(b) **注册表条目**，说明交互契约（触发方式、按键绑定、关闭行为、边界情况）和来源——它来自哪个已交付制品、用户何时批准了它；(c) **准入门槛**——只有用户实际使用并批准的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但看起来漂亮的内容不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定属于契约，不得在不同运行之间发生漂移，而颜色和尺寸可以遵循制品的风格；(e) **回写循环**——为某个制品发明的片段，应在用户批准它的同一会话中提升到组件库。其重要性不只在于节省 token：手工重写的片段会发生 *漂移*——每次重写都会细微改变按键绑定、关闭行为和计数器——而对于每天阅读这些制品的用户来说，交互一致性就是产品体验。用户在建立第一个此类组件库时的原话是：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：某个报告页面 skill 的灯箱画廊组件（图像叠加层：←/→ 循环切换同组图像、ESC 关闭、原位缩放、n/N 计数器）及其交互组件注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击遍历测试进行验证。参见方法论案例 17。

**流水线检查**：考虑该 skill 的输出是否会自然地流入另一个 skill，以及现有 skill 是否应链接 *进入* 此 skill。添加或实质性更改“Next Step”交接或流水线契约，需要在编辑前重新分类为第 3 级；第 1/2 级可以提出该建议，但不得顺手添加。

**引用与自我应用检查（即使谨慎的作者也会遗漏的缺陷）**：这一系列故障模式从内部看都像已经完成的工作，而且没有一种能通过更仔细地重读发现——每一种都需要采取 *机械化* 操作。（开头故意没有写数量。“三种故障模式：”是一个派生数字，一旦有人追加项目符号就会过时，而计数类文字恰恰最难发现漂移，因为它 *不包含发生变化的事物*——重新编号时，对列表本身执行 grep 和 diff 都会直接漏过它。）将它们归为一组，是因为它们有着共同的原因：**写下断言和验证断言是两种不同的模式，单次遍历无法同时容纳两者。** 当你正在撰写时，“参见规则 8”*就是* 断言本身；你不会同时打开规则 8。

- **你写下的每个指向性引用，都要先打开其目标并从中复制一行——然后再写这个引用。** 不要只是说“我确信那条规则列出了全部三个标记”：粘贴其中一个片段。错误的交叉引用在复读时很难被发现，因为错误的指向看起来与正确的指向完全一样，而作者恰恰是唯一必然会“记得”目标内容的人。真实案例：一位作者写下“参见基本规则 3”，本意是指一条关于不要引用陈旧枚举的规则——但被引用文档*自身*的规则 3 讲的是样本量，而实际被引用的规则位于另一个文件中；读者若遵循该文档既定的自引用惯例，就会跳转到一个毫不相干的主题。同一轮编辑还发布了一个方向颠倒的指向（材料在上方却写成“见下文”），以及一个指向根本不存在的章节标题的引用。
- **只写“规则 N”，在文件中出现两个编号列表的那一刻就会产生歧义。** 检查应针对每个指向，而不是整个文件：在写下“规则 N”之前，运行 `grep -n '^N\. ' <file>`，并确认恰好有一个命中位于你想指向的章节中；如果有多个命中，还要同时写明章节名称。（**不要**把它变成类似“这个文件是否包含多个从 1 开始的列表”这样的文件级警报——对于任何长文档，这几乎总是成立，因此它会对正常输入发出警报，最终被人忽略，而纪律 #6 警告说，这比没有检查更糟——这个文件本身会返回 19。）在真实案例中，一个未加限定的“规则 1”对应三个候选列表，而自上而下的搜索首先命中了错误的列表。
- **写下任何规范性规则后，都要根据其相邻行检查它——并让检查产出证据，而不是结论。** 对你自己的变更块运行 `git diff -U0 HEAD -- <file>`，将新规则拆分成各个独立条款，并针对每个条款写下满足该条款的、位于*同一变更块中*的那一行。（**`HEAD` 至关重要**：不带参数的 `git diff` 只显示*未暂存*的更改，因此只要你执行 `git add`——这是常规的良好习惯——它就不会输出任何内容，而检查会对一项它根本没有读取过的编辑报告干净通过。实测结果：同一个文件、同样的内容，在已暂存状态下 → 不带 `HEAD` 时为 0 字节，带上则为 120 字节。）**没有相邻行与之对应的条款，就是检查发现的问题。** 那个诱人的简化版本——“我的新规则通过了吗？”——对于 30 秒前刚写下它的人而言不可能失败；这正是纪律 #6 所说的，应优先采用可证伪的观察，而不是自我评估，因此本条也必须产出它所要求的同类证据。它的第一个受害者通常就是旁边的段落。真实案例：新增了一条规则，写着“始终同时报告原始计数和过滤后计数——两者之差*就是*污染量”，但同一提交中的配套示例却只输出了过滤后的数字。同一差异中的另一处陈述引用了两个数字，却没有说明它们是否是在相邻新规则刚刚规定为强制要求的限定条件下采集的。检查范围很小且边界明确：不是“重读整篇文档”，而只是“我 30 秒前写下的规则，能否在我 30 秒前写下的那些行上通过检查”。
- **为每条新规则留出一行，说明由谁执行，以及他们实际上是否有能力执行。** 如果现有工具无法满足某条规则，人们即使自认为已经遵守，也会跳过它——这是最糟糕的一类规则，因为它会制造有文档背书的虚假信心。真实案例：一条新规则要求“检查两个日志存储区”；该项目自身的规范化单命令分诊工具却硬编码了其中一个，因此标准工作流恰好会对这条规则旨在捕获的故障返回干净结果。这条规则是正确的，却不起作用，而且没有提及这一缺口。**使这一点可证伪的证据**（如果没有它，本条就会成为一组禁止自我评估的规则中唯一一项自我评估）：指出哪个工具或命令能够捕获违规情况，然后**针对一个你已经知道它应该能捕获的案例运行一次**。如果它对已知有问题的输入返回干净结果，你就实际测得了这条规则不起作用——把这一缺口写进规则本身。凭记忆回答“他们实际上是否有能力执行”，恰恰是纪律 #6 所否定的未经验证的断言。
- **推论——你的修复本身就是缺陷来源，因此要在最后一次编辑后重新检查你改动过的区域。** 在对单个变更进行的两轮审查中，第 1 轮发现了八个问题；第 2 轮又发现了八个，**其中七个是第 1 轮的修复所引入的交叉引用错误**。重写一个句子会移动其周围的锚点。这也解释了为什么，对于依靠指向性引用进行导航的制品而言，“已经审查过”并非终点：你一旦根据审查结果采取行动，审查就已经过时。重新检查是机械化的：`git ls-files --error-unmatch <file> && git diff -U0 HEAD -- <file> | grep -E '^\+' | grep -Ei '(see|per|above|below|§|rule|discipline|step) *#?[0-9]|\]\([^)]+\)'` 能捕获你所添加内容中大多数看起来像引用的字符串；逐一对照其目标进行核验。有三个细节，每个都经过实测，每个都决定了这究竟是检查还是安慰剂：**`HEAD`**——没有它，已暂存的编辑不可见（实测见上方相隔两条的“根据相邻行检查它”条目）。**首先执行 `ls-files --error-unmatch`**——拼错路径或使用错误的相对路径会让 `git diff` 不输出任何内容并以状态码 0 退出，这与成功完全相同；此命令会使其以状态码 1 退出，并输出 `pathspec … did not match any file(s) known to git`。**不要在第二个 `grep` 上使用 `-n`**——经过第一个过滤器后，它编号的是*管道流*，而不是文件，这些编号看起来很权威，实际却无处可指。并且应把空输出视为问题，而不是答案：即便加上了防护，它仍然可能表示“没有任何改动”，也可能表示“有改动，但没有任何内容看起来像指向性引用”，而这两者不是同一个结果。它只需几秒，并且不依赖警觉性，而纪律 #6 要求任何值得编写的检查都应如此。（它是一张网，而不是证明——它会漏掉以自然语言表达的指向，因此也要阅读新增的行。）

### 步骤 5：清理审查（任何公开技能均为必需）

**在进入此检查关口之前，如果纪律 #5 已达到触发条件，则其独立审查必须已经完成**，并且当前变更的 `independent-review.md`（位于你由私有 git 跟踪的知识仓库中——不是已清空的工作区，也不是任何已经或可能公开或分发的仓库）必须存在，**并且已提交**。对于新技能，该审查始终是必需的；对于现有技能，请使用下一段中的阈值。一个文件仅仅未经提交地留在 git 工作目录中，与一个从未写入的文件并没有实质区别；`ls`/`test -f` 只能确认它存在于磁盘上，不能确认它能够留存。对于**新**技能，这是任何内容首次离开你掌控的步骤，因此应在此处真正执行这项纪律，而不只是口头声明——一条写在实际使用位置上方 1000 行、却没有任何检查措施的规则，每次都会败给完成任务的冲动。

**对于已经发布的技能所做的编辑，它离开你掌控的时刻是推送，而不是此步骤。** 对于此检查关口，只需用一句“仅限内部，跳过”作答即可，而且仅修改文档时甚至可能完全不运行打包流程——因此，把审查锚定在这里，意味着技能编辑可能在没有经过任何独立审查的情况下进入公开分支。真实案例（2026-07）：对此文件本身的一次变更发布了一个发现命令，但该命令无法访问其旁边正文声称能够覆盖的三个根目录；该变更被合并后，直到*事后*安排的审查才发现这一问题。**因此，对于现有技能：必须在 `git push` / 创建 PR 之前完成独立审查及其记录产物——推送时运行的检查关口（回归审计、验证、扫描）全都只检查结构，其中没有任何一个能够判断说明是否错误。** 此处原封不动地沿用纪律 #5 的阈值：当*规则、契约或数字发生变化*时需要进行审查，而拼写错误修复或纯格式调整则不需要。让拼写修复也必须等待一轮审查，只会培养出纪律 #6 所警告的那种条件反射——“这次改动很小”会变成普遍适用的豁免理由，继而连真正重要的变更也被涵盖进去。

**对于将进入公开仓库的技能，这不是可选项。** 私有内容一直都在泄漏到公开技能中，而扫描器遗漏的泄漏恰恰最危险——非英语语言中的真实姓名、真实对话记录中逐字照搬的一行内容、被直接放进示例中的真实案例。只有当技能确实仅供内部使用时才能跳过。

**根据发布目标而非主题界定审查范围。** 只有会公开发布的产物——技能包本身——需要进行清理。保留在私有仓库中的配套文档（提炼出该技能的事件报告、内部运行手册、项目的 CLAUDE.md）应保留其真实的主机名、路径和时间戳：对这些内容进行脱敏会破坏其审计价值，而你最终还得撤销这些改动。某次提炼会话之所以经历了三轮返工，正是因为脱敏处理被应用到了源材料涉及的所有内容，而不只是公开技能。

**先检查目标位置，并让检查结果预先填入建议。** 对技能将要存放的仓库运行
`gh repo view --json isPrivate`（或者阅读 `quick_validate` 已经打印的说明）。
如果目标位置是私有仓库，则应默认推荐选项 C，而不是事后才考虑它——“除非另有说明，否则假定为公开”
正是导致私有技能中可正常使用的路径被替换成无人要求的占位符的原因。

**触发脱敏的条件是目标位置的 `isPrivate`，而不是任务给人的发布感有多强。**
这两者可能并不一致；当它们不一致时，除非你明确指出这一点，否则直觉会占上风。将内容移入
*市场技能*感觉就像在发布——市场本来就是分发内容的地方——因此，即使源仓库和目标仓库
都是私有仓库、内容根本不会流向任何地方，也会触发脱敏的本能反应。真实案例
（2026-07）：一次从项目级技能到私有市场技能的迁移，把真实的配置路径、真实的十六进制值
和真实的具名示例都泛化成了占位符。`quick_validate` 在**每次**运行时都打印了
`🔒 audience: private`；作者每次都看到了，却仍然进行了脱敏，因为这项*活动*看起来像是在发布。
代价不只是表面上的——真实路径能让下一位读者前去检查该值；“项目自己的令牌文件”则无法打开。

所以，要把它变成一次查值，而不是一次判断：**读取目标位置的 `isPrivate`，如果它为
`true`，则只有所有者明确要求时才能进行脱敏。** 私有→私有的迁移只是迁移，不是发布。
**如果两种探测方式都无法给出答案**（尚无远程仓库、未运行 `quick_validate`），你就无值可查——
应退回到将其视为公开内容，*并明确说明这一点*，因为风险的不对称性决定了应这样处理：
一次不必要的提问只多花一句话，一次不必要的泄露却无法收回。而且，`isPrivate` 报告的是目标位置
**当前**的状态——一个位于私有仓库中、正准备发布的技能，应在真正将其发布的那次推送中执行
脱敏，而不是这一次。如果你发现自己正在推理私有目标位置中的某些内容是否“应该”被泛化，
这种推理本身就是信号。

使用 **AskUserQuestion** 确认脱敏程度（对于公开目标位置，确认脱敏程度，而不是是否进行脱敏；
对于私有目标位置，则确认是否确实需要脱敏）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**脱敏流程——通读是主要方法，扫描只是辅助工具：**

1. **亲自通读整个技能并进行语义判断**（这才是真正的检查）：SKILL.md + 每一份参考资料 + 每一个示例。对每个具体名词 / 示例 / 片段，都要问：“这是通用占位符或公开实体，还是取自真实项目 / 人物 / 对话记录？”替换后者——即使扫描器没有标记它。这是发现无关键字泄露的唯一方法。完整指南和语义判断问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器，作为低成本的初步检查**：检查清单中的 grep 模式 + `security_scan.py`（Step 6）。它们能快速发现明显的密钥 / 路径 / 已知名称——但“无匹配项”并不代表检查通过。
3. **替换**每个发现项，用通用的等价内容保留教学要点（真实姓名 → 公众人物或 `<placeholder>`，真实片段 → `<placeholder>`）。有两条从惨痛教训中总结出的规则：占位符本身不得编码真实值——`<acme-corp-domain>` 恰恰泄露了它本应隐藏的名称；应改为描述其*角色*（`<api-domain>`、`<upstream-provider>`）。此外，在编写批量替换脚本时，要提供明确的文件白名单，并将范围限定在技能目录内——未限定范围的查找替换会毫不犹豫地改写项目自身的 CLAUDE.md，迫使你使用 git restore。
4. **通过重新阅读来验证，而不是再次运行 grep**：重新阅读修改过的部分，并确认没有损坏的引用。

### 第 6 步：安全审查

在打包或分发技能之前，运行安全扫描器以检测硬编码的机密信息和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件地址、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）

**未覆盖的内容**——这正是仍然需要执行第 5 步通读检查的原因：gitleaks 和正则表达式规则只能匹配*已知的机密信息格式和你列出的模式*。它们在结构上无法识别不包含关键词的私密内容——例如使用非英语语言书写的真实人员/项目名称、真实对话记录中的原句，或直接取自你自己工作的真实示例。`security_scan` 显示通过意味着“未发现已知格式的机密信息”，**而不意味着**“该技能已完成敏感信息清理”。绝不要将其视为后者。

**首次设置：** 如果尚未安装 gitleaks，请进行安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 无问题（可以安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**对于私有技能，扫描发现的内容是信息，而不是必须执行的工作指令。** 扫描器无法
区分泄露的凭据和*本来就应该存在于此处*的凭据——例如，价值就在于预先填充了内容的模板，或指向其唯一运行机器的脚本。
绝不要在私有仓库中自动修复：报告发现的内容，并让所有者做出选择。下面的选项 A
（“自动修复”）适用于即将公开发布的技能。

**如果发现问题**，请通过 **AskUserQuestion** 展示这些问题：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包技能

技能准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个现有且由 Git 跟踪的技能，在提供已完成的审查并重新验证之前，打包操作都会被阻止。当前标记只是本地状态凭据，
因此先提交更改或手动编写标记都无法绕过审查。下一次编辑后，审查即会失效：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及用于包含根 `evals/` 目录的 `--include-evals`（该目录作为开发资源，默认排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. 自动**验证** Skill（YAML frontmatter、命名约定、路径引用完整性）
2. 每当 Git HEAD 已包含该 Skill 时，**重新验证已完成的现有 Skill 回归审查**；仅有标记绝不代表已获准打包
3. **验证安全扫描**（内容哈希必须与上次扫描匹配）
4. 将 Skill **打包**为可分发的归档文件

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 第 8 步：更新 Marketplace

打包后，更新 Marketplace 注册表，以包含新增或更新后的 Skill。

**对于新 Skill**，向 `.claude-plugin/marketplace.json` 添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于更新后的 Skill**，按照 semver 提升 `plugins[].version` 中的版本号。对 Skill 文件的任何更改——即使只是修正一行拼写错误——都需要提升版本号：否则，`marketplace update` 不会检测到新版本，因此**已安装的副本永远不会刷新**，用户会继续运行旧版 Skill，而你的修复则一直未发布。

**然后将其记录到变更日志中——这一步最容易被跳过。** 版本号提升使更新变得*可安装*；变更日志条目则使它在六个月后仍然*可查找*，届时若有人遇到相同问题，便可通过 grep 找到它。而一份记录了其他所有 Skill 版本、却悄无声息地漏掉你的 Skill 的变更日志，比完全没有变更日志还糟：这些空缺会被理解为“这里没有任何变化”。

遵循现有条目的格式，不要自行发明一种——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。在提升版本号的**同一个提交**中写入变更日志；声称“稍后”更新的变更日志，最终永远不会得到更新。

真实案例（2026-08）：某个 Skill 连续两个版本都正确提升了版本号、通过了所有门禁检查并合并了 PR——但**完全没有变更日志条目**，因为此流程中没有任何步骤要求这样做。直到后来的一次审计才发现这两次遗漏。这正是纪律 #6 在此文件自身上的体现：如果一项规则只存在于约定中，而没有落实为具体步骤，那么每次都会败给完成任务的冲动。

**尽量减小注册表差异——这是所有 Skill 共享的唯一文件。** Marketplace 清单是所有并发编辑者都会发生冲突的地方，因此，在这里进行无关的格式更改，其代价远高于在其他任何地方进行相同更改：它会把原本干净的三行版本提升变成其他正在编辑该文件的人的合并冲突。使用脚本更新时（解析为 JSON、修改、再写回），重写过程会悄无声息地规范化文件原本可能未采用的格式——尾随换行符、缩进宽度、键顺序、Unicode 转义。往返处理纪律：之后重新读取文件，并对其运行 `git diff --stat`；**唯一允许出现的行，必须是你有意更改的字段。** 如果出现了额外的行，请恢复文件原有的约定，而不是提交这种格式规范化（某次脚本化的版本提升曾给一个从来没有尾随换行符的清单添加了尾随换行符——在最有可能同时被其他人编辑的文件中，白白多出了一行差异）。同样的原则适用于 Skill 所涉及的任何共享注册表：lockfile、catalog、index 文档。

**当一个 PR 经历了几次合并后仍未完成时，请执行 rebase——然后证明你没有吞掉任何人的工作。** 使清单成为冲突高发区的特性，也正是导致它过时的原因：只要其他任何内容落地，一个同时修改注册表和变更日志的开放 PR 就会发生冲突，因此应预期看到 `mergeable: CONFLICTING`，而不要对此感到意外（有一个 PR 就在某天下午 main 前进了 7 个提交后遇到了这种情况）。如果仓库采用 squash merge，请执行 rebase 而不是 merge——在经过 squash 的历史记录中，增加一个合并提交毫无益处。冲突本身几乎总是**增量式的**：两位作者分别在同一节中追加了自己的条目，因此解决方法是**两者都保留**，绝不要使用 `--ours`/`--theirs`，因为那会悄无声息地丢弃同事添加的行。

人们经常跳过的步骤，恰恰是能发现错误冲突解决的步骤——**解决冲突后，证明相对于基础分支的唯一差异就是你的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要只使用 `--force`：如果自你上次 fetch 后远程分支发生了变化，lease 会让推送失败，而这恰恰意味着其他人可能已向你的分支推送内容，普通的强制推送会将其抹掉。

**插件边界不属于此技能的职责范围。** 是否将技能拆分到
不同插件中、如何组织 `source`/`skills`，以及用户能否单独启用或禁用
技能，这些都属于打包/分发领域——其 SSOT 是
`marketplace-dev` 技能，而不是本文。当任务确实需要做出这些决策时：
确保 `marketplace-dev` 可用（如果缺失，则自动安装——方式与
`skill-reviewer` 在需要其脚本时引入 `skill-creator` 相同），然后阅读
marketplace-dev 的 cache-and-source-patterns 参考资料并遵循其要求。不要在
这里重述其中的规则；副本会逐渐偏离原文。

**重命名、移动或移除 marketplace 条目是一项破坏性变更**，会影响
每一位已安装该条目的用户——条目消失时，Claude Code 不会清理已安装的副本，
这会留下悬空安装，导致每次执行 `marketplace
update` 时都报错。应像对待 API 弃用一样处理此类变更：在
变更日志中提供迁移说明，并按照 marketplace-dev 的指导完成具体操作。

**如果你自行在技能仓库中提交/推送：** 对于现有技能，如果当前变更越过了第 5 条规范中关于规则/契约/数值的阈值，请确认评审产物记录了本次变更且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不是仅仅确认历史上存在某个 `independent-review.md`）。拼写错误修正或纯格式调整不需要该产物；旧的评审绝不能满足当前实质性变更的要求。第 5 步的说明解释了为什么对于已经发布的技能，真正的强制执行点是推送，而不是打包。然后仅暂存该技能的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充斥着无关变动，否则这些内容会随提交一起混入（曾有一个提交顺带卷入了一堆无关的 transcript 文件，不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库的实际可见性，不要根据路径想当然——公开技能仓库应当通过 PR + 评审来变更，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成技能后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试技能后，用户可能会要求进行改进。这通常发生在刚使用完技能之后，此时对技能表现还有清晰的上下文。

**优化筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了相关内容，请勿重复。

## Claude.ai 专用说明

在 Claude.ai 中，使用相同的验证深度路由。当选择通用的第 3 层级路径时，完整工作流仍然是草拟 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子智能体，一些具体做法需要调整。以下是需要适配的内容：

**运行测试用例**：没有子智能体意味着无法并行执行。对于每个测试用例，先阅读技能的 SKILL.md，然后自行按照其中的说明完成测试提示。逐个进行测试。这不如使用独立子智能体严谨（技能由你编写，同时也由你运行，因此你掌握全部上下文），但它仍然是一项有用的健全性检查——而人工审查步骤可以对此加以弥补。跳过基线运行——只需使用技能按要求完成任务。

**审查结果**：如果无法打开浏览器（例如，Claude.ai 的虚拟机没有显示界面，或者你位于远程服务器上），请完全跳过浏览器审查环节。改为直接在对话中展示结果。对于每个测试用例，显示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），请将其保存到文件系统，并告知用户文件位置，以便他们下载和检查。直接询问反馈："How does this look? Anything you'd change?"

**基准测试**：跳过定量基准测试——它依赖基线比较，而在没有子智能体的情况下，这种比较没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重新运行测试用例并征求反馈——只是不在中间使用浏览器审查器。如果有文件系统，你仍然可以将结果整理到各个迭代目录中。

**描述优化**：本节需要 `claude` CLI 工具（具体而言是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测对比**：需要子代理。请跳过本节。

**打包**：`package_skill.py` 脚本可在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 上，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有 Skill**：用户可能要求你更新现有 Skill，而不是创建新的 Skill。在这种情况下：
  - **保留原始名称。** 记录 Skill 的目录名称和 `name` frontmatter 字段，并保持它们不变。例如，如果已安装的 Skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前先复制到可写位置。** 已安装 Skill 的路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后在该副本中进行编辑，并使用 `--regression-review` 打包。不要传递 `--new-skill`；现有 Skill 的非 Git 副本仍然属于现有 Skill。
  - **如果手动打包，请先暂存到 `/tmp/` 中**，然后复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 专用说明

如果你使用的是 Cowork，需要了解的主要事项如下：

- 你可以使用子代理，因此通用 Tier 3 工作流（并行生成测试用例、运行基线、评分等）可以正常工作。不要因为子代理可用，就将 Tier 1 或 Tier 2 变更升级处理。（如果 Tier 3 运行遇到严重超时，可以串行而不是并行运行测试提示词。）
- 你没有浏览器或显示界面，因此生成评测查看器时，请使用 `--static <output_path>` 写入独立 HTML 文件，而不是启动服务器。然后提供一个用户可以点击并在其浏览器中打开该 HTML 的链接。
- 完成一次**通用 Tier 3** 运行后，在你自行修改 Skill 之前，始终先为人工审核生成评测查看器，并使用 `generate_review.py`，而不是自定义 HTML。Tier 1、Tier 2，以及明确替代了查看器机制的专用工作流，不会仅仅因为工作是在 Cowork 中进行，就产生生成查看器的义务。
- 反馈的工作方式有所不同：由于没有正在运行的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。之后你可以从该文件中读取反馈（可能需要先请求访问权限）。
- 打包可以正常工作——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器；但请等到你已完全完成 Skill 的制作，并且用户认可其状态良好后再进行此操作。
- **更新现有 Skill**：用户可能要求你更新现有 Skill，而不是创建新的 Skill。请遵循上方 Claude.ai 部分中的更新指南。
