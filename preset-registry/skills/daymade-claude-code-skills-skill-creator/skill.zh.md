# Skill Creator

一个用于创建新技能并对其进行迭代改进的技能。

从整体来看，创建技能的流程如下：

- 确定你希望技能完成什么，以及大致应如何完成
- 将变更归类到能够证伪其潜在失败模式的最低验证层级
- 编写技能草稿
- 使用能够证伪已变更行为的最小证据进行验证；将完整的配对评估流水线视为需要单独授权的工作，而不是层级标签自动带来的结果
- 当所选层级产生定性或定量结果时，帮助用户对其进行评估
- 根据用户对结果的评估反馈重写技能（如果定量基准测试暴露出任何明显缺陷，也应据此重写）
- 重复上述过程，直到你满意为止
- 仅当当前证据无法判定已变更行为时，才提升验证层级

使用此技能时，你的工作是判断用户当前处于该流程的哪个阶段，然后立即介入，帮助他们推进适用的阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须承担的成本。“优化”“改进”或“全面”等词描述的是意图，而不是失败面或评估预算。不要仅仅因为任务听起来范围很广，或此前已经进行了很长的对话，就创建评估文件、并行派生配对智能体、对输出进行评分或启动查看器。

以下六项长期纪律始终适用，因为这些失败模式会产出看似令人信服、实则错误的技能：

1. **先验证，再编写。** 技能中加入的每一项技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察过的内容——无论是在本次会话中，还是在经过明确批准的历史挖掘会话中。现在无法验证？要么去验证，要么明确标注（“未经验证——来自记忆”）。技能会放大其中包含的一切：经过验证的知识会复利增长，措辞自信的错误同样如此。对于知识型技能（其内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作版本：权威性阶梯（观察到的行为 > 机器可读契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例冒烟运行，以及受众/Windows 可移植性检查清单。一次来源依据审计曾发现，多项措辞笃定的契约断言与作者已经掌握的证据相矛盾（方法论案例 9）。
2. **将“不可能/不支持”视为假设，而不是结论。** 当某项能力看似受阻时（API 错误壁垒、无法连接的工具、无法打开的格式），在将“平台不支持此功能”写入技能之前，应穷尽各种观察路径——UI 自身的网络流量、替代渠道、不同的已记录标识符。观察到的行为优先于推测性的请求形式。
3. **站在领域前人的肩膀上——在编写或优化技能的方法论之前，默认将该领域公认的最佳实践检索到上下文中。** 技能方法论的质量取决于上下文窗口中的知识，而不是潜藏在模型权重中的知识：预训练是有损的，会随时间失效，而且除非真正调取规范来源，否则往往根本不会被激活。因此，你所编写内容的质量上限是 `your training data + the user's input`——*除非*你主动检索该主题领域真正的既有成果。务必这样做：通过 WebSearch 搜索该领域的规范理论/标准/方法，并阅读该领域中随附或已安装的任何技能，然后将关键原则连同出处归因一起融入技能。**这与下文的“既有成果研究”属于不同维度**——后者寻找可复用的*工具/基础设施*；前者则以该学科积累的科学成果为技能*方法论本身的质量*奠定基础。将其作为**默认操作，而不是等用户提出要求后才执行的操作**：简要告知用户你正在参考哪个领域，并允许他们说“跳过”，但当该领域 40 年的公开成果只需一次搜索即可获得时，绝不要交付一个受限于你的记忆和用户提示的方法论。例如：数据可视化技能必须吸收 Cleveland 与 McGill 的图形感知排序，以及 Bertin 的视觉变量理论（位置/长度优于颜色，颜色优于文本——这是测量结果，而非审美判断）；日期/时间技能必须呈现成熟的库及其典型陷阱；说服/谈判技能必须检索既有框架，而不是凭记忆重新发明。如果规范知识只存在于你的权重中而从未进入上下文，那么你是在本可引用依据的地方进行猜测。
4. **在压缩现有技能之前，先保留其内容。** 更新现有技能是一场迁移，而不是从空白页开始的重写。在首次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧捆绑包，或从明确的 Git 引用中重建它；任意复制一份内容再加上来源标签，并不能构成基线。盘点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和精简原则允许移动内容或删除重复内容；但并不允许悄无声息地删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个无法匹配的旧单元进行分类。仅存在于 `evals/`、测试或未链接参考资料中的运行时契约仍然属于已丢失内容。只要还有任何候选项尚未分类，或任何真实缺口尚未修复，就不要宣称更新已经完成。同样的逻辑不仅适用于*删除*，也适用于*推翻*，并涵盖此前作出的任何承诺——而不只是那些附有日期和姓名的承诺：**推翻已经作出的决定是一项提议，绝不能成为附带结果。** 明确说出来，并获得接受。静默重写比静默删除更糟糕，因为它会同时摧毁产物本身，以及原本可能一次性发现问题的证据——还会让所有下游审查者失去判断依据（参见第 5 项）。

5. **任何内容都不能仅凭自我审查就交付——由独立的新上下文进行对抗性审查，是一个固定步骤，而不是特殊情况。** 你对“现在已经没问题了”的判断，出自生成该产物的同一个模型，因此它也具有造成该缺陷的完全相同的盲点。这是实测结果，而非坊间传说：在没有外部反馈的情况下，内在自我纠正并不能可靠地改善输出，有时反而会使其恶化（Huang 等，ICLR 2024）；而当生成者和评估者具有相同的错误模式时，反复迭代只会**提高信心，却不会增加信息**。再多的自检也无法摆脱这一点；只有外部视角可以。**完整流程——提示词模板、锚点选择、发现项表格、实操案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；首次审查前请先阅读。** 以下是支撑整个流程的关键规则：
   - **独立性有两个层面，而作者往往忽略第二个。** *审查者的上下文*不能是你的上下文分叉——分叉会继承你的盲点，然后返还一个“已审查”的印章。但它用来衡量产物的*证据*也必须位于**变更的影响范围之外**，否则它就会继承你的**结论**：它读到的是已经彼此一致的产物和规范，最终报告的也只是二者一致。请注意，“本次会话中未编辑”这条界线太弱——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，结果三名审查者都没有发现一个他们在其未经改动的孪生版本中成功发现的缺陷。请按照锚点有多难被*你*改动来排序：用户自己的对话原文 > 早于本次工作的 git 引用（`git log --oneline <ref>..HEAD -- <path>`；其中只要有你的任何提交，该引用就不合格）> 仅追加日志（一种约定，而非强制保障）。**全新项目没有锚点——应明确说明这一点并请求用户提供锚点，而不是报告一项你并未执行的审查已通过。**
   - **只给它两样东西：产物和读者规范。** 不要提供其他任何内容——不要提供设计理由、项目背景，也不要说“只需确认 X 没问题”，这些都会把独立审查者变成橡皮图章。读者规范是一份*规范*，而不是理由，因此它无法为任何内容背书；省略它会浪费一半的审查价值，因为审查者随后只能以自身为衡量标准。**对于 SKILL.md，读者是另一个执行该文件的智能体**，它的失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——应询问哪些指令让它无法采取行动。在运行审查前陈述规范，之后绝不能用它来为发现项开脱。
   - **对于可理解性，以及相对于语料库的完整性，它是事实依据；但对于品味，它没有裁决权。** 对前两者直接采纳其判断。将“这可能是一个 bug / 我建议采用 Y”视为假设，并先亲自复现。绝不要把 AI 废话或审美判断委托给它——这属于同模型盲点。
   - **枚举的是失败*轴*，而不是内容领域——这也决定了要运行多少名审查者。** 轴是*你提出的问题*；领域是*你阅读的材料*。三名审查者分别覆盖场景、算术和差异，但全都只问“这是否连贯？”，等同于让一名审查者做事却按三名计费。**默认使用一名审查者，而且通常已经足够**；只有存在额外的轴时才增加一名。自我审查最不擅长的轴是**忠实度**——“这是否仍然忠实于已经作出的承诺？”——因为移动承诺的正是作者本人，而连贯性与忠实度彼此正交：一个产物可以在内部毫无瑕疵地自洽，同时完全背离已经作出的决定。
   - **必须留下产物，否则这只是一条警告。** 纪律 #6 指出，生成意见的检查不如生成产物的检查——因此本步骤也必须生成文件，否则它恰恰会在最关键的时候败给完成任务的冲动。在你的私有、由 git 跟踪的知识仓库中，将 `independent-review.md` 写入 `skill-reviews/<skill-name>/`：包括**审查者提示词原文**（以便后续读者判断它是否具有诱导性）、**每项发现及其处置结果和理由**（这是合理筛选与丢弃刺耳意见之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识仓库（或没有这样的仓库），应明确说明并询问用户——不要猜测一个位置，导致文件落入任一禁区。两个禁止位置：**不得放在 `<skill-name>-workspace/` 中**（这些是会被清理的、由 git 忽略的暂存目录——该文件是跨会话的审查证据，必须在这些目录被清理后继续存在），并且**不得放在任何已经公开或将来可能公开或分发的仓库中**——这通常意味着不能放在被审查技能自身的仓库里（审查内容必然会引用私有路径、真实姓名和项目详情）。在进行实质性编辑后，应由一个*新的*智能体重新审查——实质性编辑指修改了规则、契约或数值，而不是修正拼写错误。**从第 5 步开始，该文件就是审查已经执行的证据；缺少该文件就意味着审查并未执行。****写入文件并不等于它一定会为下次会话所保留——必须在同一轮中，在该私有仓库内执行 `git add` + `git commit`。** 位于 git 工作目录中但未提交的文件，并不具备这条规则所要求的任何“由 git 跟踪”保障：它可能丢失、被覆盖，或者后续检查“这是否已经过审查？”的任何流程根本不会发现它（真实案例：文件内容正确、路径正确，也包含真实的发现项——但后续自动检查仍然失败，因为它从未被提交；修复方法是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械性的，也是对本步骤的补充：它能证明你没有*删除*行为。但它完全无法说明你写出的内容是否真的可以被遵循。

6. **设计你编写的检查，使其无法自行证明为通过状态。** Skill 在很大程度上由检查组成——门禁、检查清单、“发布前”步骤——而如果执行上下文可以在*违反检查所编码的规则本身时*仍通过检查，那么这种检查比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴自那些先于软件领域解决了这一问题的行业：
   - **验证必须覆盖规则的每个条款。** 如果规则规定“A + B + C”，证据就必须分别要求提供 A、*以及* B、*以及* C 的证明。在一条包含三个条款的规则后面硬加一行确认要求，只会被作者已经完成的那个条款满足；其他条款则完全不可见。真实案例：一个报告编写 Skill 包含一道交付门禁，其规则写着“选项以并排选项块呈现 + 突出显示建议 + **背景信息写成完整、自足、陌生人也能理解的句子**”——但其下方的证据行只要求“N 个决策项，全部呈现为选项块”。作者执行了门禁，写下该证据，自行证明为通过状态，然后发布了一个页面，其中的标签只有单个字符，所有上下文都被删除了。这条规则始终存在于文件中；检查只是从未衡量该条款。
   - **对正常输入误报的检查比没有检查更糟。** 上述失败是检查在本应失败时却通过；这里说的是它的镜像情况——检查在本应通过时却失败。后者代价更高，因为它会让操作者养成下意识绕过检查的习惯（`--no-verify`、`SKIP=1`、`--force`）；而一旦形成这种习惯，门禁就会对*所有*输入失效，包括它原本要防范的输入。因此，在编写失败时默认关闭的检查时，**误报比漏报更应优先避免**：漏掉一个真实问题，只会让你在该实例上付出代价；而阻止一个正常输入，则会让你失去整道门禁。
     注意这个征兆：**因反复踩中同一个陷阱而产生的挫败感，本身就是风险信号**——作者正是在这种状态下，最容易发布一种从未使用正常输入校准过的防御措施。真实案例：一天之内三次踩中同一个格式陷阱后，作者向 linter 添加了一项正则表达式检查；它在项目自己的语料库中阻止了 **33 个正常输入**，并在同一小时内被回滚。启用之前先进行校准——在真实且已知正常的材料上运行任何失败时默认关闭的检查，并确认误报为零；宁可放宽检查，让它偶尔漏过问题，也不要允许它发生误报。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是自足的”这一项不可能被其撰写者判定为失败；“遮住页面其余部分，只阅读一张卡片，并说明它要决定什么”则可以。应优先选择能够产生产物的检查——命令输出、引用的文本行、截图——而不是只能产生意见的检查。
   - **同样的怀疑也适用于你所*运行*的检查，而不仅仅是你编写的检查。** 上述四条规则约束的是随 Skill 一同发布的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样也是工具，而错误的工具会像正确的工具一样自信地报告干净结果。在 2026-07 的一次会话中，五条不同的验证命令在两个方向上都给出了错误结果：一个未使用 `-L` 的 `find` 报告某个已安装 Skill 的文件缺失（它们位于符号链接之后）；一个 `grep --exclude-dir=<name>` 隐藏了正在审计的对象的另一份副本；一个逻辑取反的 shell 条件错误地警告某项删除尚未发生；一个跨越换行符的正则表达式凭空制造了 55 个“丢失的引文”；而一项只搜索五个文件中两个文件的操作报告有两条规则缺失，实际上它们存在于第三个文件中。**最初所有这些结果都被相信了，而每一个错误都只是在使用不同形式的检查重新运行后才被发现。**

解决办法是实验实践中最古老的一条：**先用仪器测试一个你已经知道答案的案例，再相信它对未知案例的测试结果。** 正在 grep 一个你预计不存在的字符串？先用相同的命令形式 grep 一个你确定存在的字符串——如果它也返回 0，那么出问题的是命令，而不是文件。这样做只多花一行，却能把“我检查过了”变成“我用校准过的仪器检查过了”。

     有两种具体情形值得牢记，因为它们都在上文出现过，而且都会*静默地*失败：如果没有 `-L`，`find` 不会跟随符号链接（而 skill 安装目录经常是指向源代码仓库的符号链接）；此外，`--exclude-dir` 会按基本名称匹配目录树中的所有位置，而不仅仅是你心中所想的那个路径。

     **这条规则还有后半部分，只有当检查内容被发布时才会造成问题：应针对*标准*实现进行校准，而不是针对你机器上的实现。** 上面的仪器规则能保证*你的*结论可靠；这一条则能保证*读者的*操作有效。写入 skill 的工具行为断言——某个标志、某种递归模式、某个声称会“跟随符号链接”的选项——会在你从未见过其二进制程序的机器上执行，而且这种差异在两端都是静默的：你测试时它能工作，到读者那里却悄无声息地什么也没做。造成这种情况的机制有两种，而且在会话内部都无法察觉：**同一个命令名称解析到了不同的程序**（shell 别名或函数遮蔽了二进制程序——请注意，`\tool` 只能绕过*别名*，因此 `command tool` 或绝对路径才是唯一确定性的形式），以及**同一个程序在不同实现中表现不同**（BSD、GNU 或直接替代品）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是把它作为符号链接陷阱的修复方法写入 skill，并发布到了一个拥有 1200 个 star 的公共仓库——他们的 `grep` 是通过 shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 中，同样的 `-R` 什么也匹配不到（它需要 `-RS`），因此这个规定的修复方法对大多数读者都静默失效了，而且恰恰发生在警告验证器会静默失败的那一节中。

     所以：**在关于工具行为的断言进入发布制品之前，请针对标准二进制程序**（`/usr/bin/<tool>`）**重新运行它**，而不是针对 shell 交给你的那个程序。如果它经不起这种测试，就不要写下那个标志——**应优先采用与实现无关的表述方式**：自行解析路径（`readlink -f`），而不是押注某个递归标志；在脚本中进行子字符串测试，而不是按行匹配；说明你需要的*行为*，而不是你碰巧知道的选项。只在你的环境中有效的操作指示比没有指示更糟，因为读者根本无法发现它悄无声息地什么也没做。

   - **采用成熟检查清单实践中已经形成的结论。** 确定清单属于 **READ-DO**（边读边执行——适用于低频或不熟悉的流程）还是 **DO-CONFIRM**（凭专业经验完成工作，然后在明确的**暂停点**停下来确认——适用于时间压力下经验丰富的操作人员），并将其设置在一个真正的暂停点，而不是“工作流中的某个位置”。清单应只保留**致命关键项**——那些既关键、又常在压力下被遗漏的事项，通常为五到九项；超出这一范围的内容都会削弱执行效果（[Gawande，*《清单革命》*](https://www.shortform.com/blog/types-of-checklists/)）。此外，应优先采用 Shingo 所说的**控制**而非**警告**（[防错法](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，会败给急于完成任务的驱动力；而阻止继续操作或强制生成制品的步骤根本不需要依赖警觉性。如果 skill 只能发出警告，至少要把警告放在做出决策的位置——**如果执行上下文从不打开某个参考资料，那么归档在其中的规则在实践中就不算规则。**

另一方面，也许他们已经有了一份技能草稿。在这种情况下，你可以直接进入循环中的评估/迭代环节。

当然，你应该始终保持灵活；如果用户说“我不需要进行一大堆评估，跟着我的感觉来就行”，你也可以照做。

然后，在技能完成后（不过再次强调，顺序可以灵活调整），你还可以运行技能描述改进器；我们为此准备了一个完全独立的脚本，用来优化技能的触发效果。

## 首先：共存检查（官方 skill-creator 插件）

在执行其他任何操作之前，快速检查一次（只需运行一次 grep，常见情况下无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 什么也不要做——不要安装任何东西，也不要向用户提及本节。继续处理当前任务。
- **存在：** 官方插件的 skill-creator 和这个版本现在会以几乎相同的描述同时出现在技能列表中，因此未来的会话会在两者之间随机路由。用一两句话告诉用户这一点，然后提供以下选项（未经用户同意，绝不要擅自操作）：
  1. **推荐**——运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型自检 SessionStart 钩子复制到用户的 Claude 配置中，并在 `settings.json` 中注册该钩子（同时创建备份），这样未来的每个会话都会确定性地将技能相关工作路由到这个版本。可以使用 `scripts/setup_supersede_hook.sh uninstall` 撤销；按名称指定官方插件时，它仍然完全可用。在未安装官方插件的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的钩子。
  2. 备选方案——`claude plugin disable skill-creator@claude-plugins-official`（可使用 `enable` 恢复），它会将官方条目完全移出技能列表，从而消除歧义。

如果钩子已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目存在），请静默跳过上述所有内容。

同样的机制也适用于用户创建的技能：当他们的技能有意与某个已安装的技能重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一套工具包——请参阅“既有方案调研”下的“共存与优先级”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

技能创建器可能会被对编码术语熟悉程度差异很大的人群使用。如果你还没听说过（你又怎么可能听说呢，这种趋势也是最近才开始的），现在有一种趋势：Claude 的强大能力正在激励水管工打开终端，也让父母和祖父母开始搜索“如何安装 npm”。另一方面，大多数用户可能仍然具备相当不错的计算机素养。

因此，请注意上下文线索，以判断应该如何措辞！在默认情况下，下面这些例子可以帮助你把握尺度：

- “评估”和“基准测试”处于临界线上，但可以使用
- 对于 “JSON” 和“断言”，在不加解释地使用之前，你需要从用户那里看到明确迹象，表明他们知道这些是什么

如果你对某个术语有疑问，可以简要解释；如果你不确定用户是否理解某个术语，也可以用简短的定义加以说明。

### 使用 AskUserQuestion（关键——请务必阅读）

**在每个决策点都要积极使用 AskUserQuestion 工具。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能实现的最重要的一项用户体验改进——用户往往同时处理多个窗口，而且可能已经有 20 分钟没有查看这段对话了。

**每次使用 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段以及刚刚发生的事情（1-2 句话）。用户可能已经切换到其他任务。
2. **简化说明**：用通俗语言解释要做的决定。不要使用函数名或内部术语。说明它能做什么，而不是它叫什么。
3. **给出建议**：先给出你的推荐选项，并用一句话说明理由。如果选项涉及投入时间，请同时展示两种时间尺度：`(human: ~X min / Claude: ~Y min)`。
4. **提供选项**：给出 2-4 个具体的、以字母标记的选项。每个选项都应是一项明确的操作，而不是抽象概念。

**规则：**
- 每个问题只包含一个决策——绝不要把不相关的选项合并到一起询问
- 提供退出路径（AskUserQuestion 中始终隐含有“其他”选项）
- 接受用户的选择——可以提醒用户权衡取舍，但绝不要拒绝继续执行
- 如果答案显而易见且不存在需要权衡之处，则跳过提问（只需说明你将怎么做）
- **如果问题超时且没有得到回答（用户暂时不在键盘旁），既不要停滞不前，也不要擅自推进涉及偏好或范围的决策。** 先完成不会产生副作用的基础工作——编辑前快照、清单盘点、评估用例收集、只读审计/健康检查——并将需要判断的事项（重构方向、要删除什么、是否继续）留到用户回来后再决定。然后明确说明你已经完成了哪些工作，以及还有哪些事项正在等待用户决定。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话中可能已经包含用户希望沉淀下来的工作流（例如，他们说“把这个做成一个技能”）。如果是这样，应先从当前对话中提取答案——使用过的工具、步骤顺序、用户做出的修正，以及观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**来源清单——始终在起草之前完成，并遵守用户授权边界。** 盘点当前对话以及与之重叠的现有文档/技能（参见下文的“既有成果研究”）。更早的本地会话 JSONL 文件属于独立的私有来源：除非用户明确要求挖掘历史记录，或者在你解释将读取哪些内容后明确批准使用该来源，否则不要打开或解析这些文件。如果获得批准，只能通过对话挖掘工作流的脱敏提取流程纳入相关的历史会话；绝不要将原始对话记录加载到你自己的上下文中。如果未获批准，则继续使用当前对话和现有项目来源，不要将无法访问历史记录视为阻碍。

挖掘对话（或会话记录）时，要清点**两类资产——它们会归入不同位置**。*知识*——端点、参数、陷阱、决策规则——会成为 SKILL.md 中的指导内容或放入 `references/`。*会话中不得不编写的代码*——辅助脚本、注入式代码片段、渲染器、一次性模板——则可能归入 `scripts/`：如果本次会话编写了这些内容，那么下次调用时就必须重写，因此应将其参数化、清理敏感信息并打包收录。此前的一次提炼保留了润色后的正文，却遗漏了可复用的辅助工具；由此得出的一般经验是，应同时兼顾知识→references 和代码→scripts 这两条渠道。

当源材料是*过去的*会话记录（Claude Code 项目目录下的 JSONL 文件），而不是当前实时对话时，请进入对话挖掘工作流。不要在主上下文中打开原始会话记录，也不要将原始路径或内容交给子代理。必须先完成其确定性的清单 → 发现 → 脱敏 → 分块流程，之后才能让任何代理看到内容；只有经过脱敏的分块才能进入最小角色/分片计划，并且必须在预算门控中声明确切的单元数量和并发上限。

**首先，在回答下列问题之前，确定这属于哪个方向。** 请求可能属于几种彼此*相反*的情况之一：创建新技能 / 编辑现有技能 / 优化 skill-creator 本身 / 或者根本不是技能（而是一次性任务）。方向猜错会浪费整个会话——为“新技能”所做的研究，与“优化元工具”所需的研究完全不同。当措辞含糊不清时（例如，一边指向 skill-creator 自身的路径，一边说“帮我做一个技能”），在这里使用一次 AskUserQuestion 只需花费 30 秒。下文的包装技能分支是其中一种特殊情况；方向检查本身适用于所有情况。

`Use skill-creator to optimize <existing-skill>` 表示采用常规的现有技能更新路径。它**不**授权挖掘对话历史、进行大范围重写、归类为 Tier 3，或开展多代理评估。应先检查实际拟议的变更；只有当这些变更确实引入了某个故障面时，才进行升级。

1. 这个技能应让 Claude 能够做什么？
2. 这个技能应在何时触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应设置测试用例来验证该技能是否有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。输出较为主观的技能（写作风格、艺术创作、按品味校准的报告）通常无法使用断言——但“没有断言”并不等于“无需验证”。它们的验证路径按成本从低到高依次为：
   - **历史任务重放**：重新运行该技能过去处理过的一个真实提示词，分别使用旧版和新版技能，并根据本次变更涉及的具体规则比较输出（“新输出是否真正遵循了此次更新引入的词元/标题语法？”）。这种方式成本低，并且能够发现“规则虽然写了，但根本没有任何部分读取它”的问题。
   - **以生产环境作为评估**：承认真正的测试是用户下一次实际使用——然后明确建立反馈闭环：此后用户的每次纠正都应视为需要回写的事件（参见技能自身的“迭代/活文档”部分），每次认可都可作为语料。一个没有这种回写习惯就发布的品味型技能不会改进；具备这种习惯的技能即使从不运行正式评估，也会逐渐收敛。**而当技能的输出是某种会持续运行的东西——守卫、监控器、定时任务、钩子——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户纠正的前提是用户注意到了问题并愿意费心反馈；已部署的机制会在无人提示的情况下自行报告，通常一天内就会有结果，而误报是这种报告最鲜明的形式，因为它证明你写下的某条规则存在错误，而且这种错误无论重读多少遍都无法发现。应将第一次误报视为预定的评估结果，而不是烦人的干扰：不要先入为主地认为机制行为异常，而应先检查误报，因为更有可能的原因是*指令*写得过于绝对。（真实案例：某个技能规定进行一种出错即高声告警的检查；部署后的检查在夜间对一个完全正常的条件触发了一次，修复方式是纠正技能中那句过于绝对的表述——没有人投诉；是遥测数据发现了问题。）
   - 对视觉输出执行**渲染 + 人工审查**（即技能自身的视觉质量保证门控），绝不能使用假装可以衡量美感的 grep 断言。**而且用于验证的渲染器必须与交付成果实际使用的引擎相同**——方便地安装在本地的任意预览器都不能作为替代品。布局引擎与目标应用程序不同的缩略图生成器，会悄无声息地*隐藏*你正在查找的具体缺陷；在错误的引擎上得到绿色验证结果，比不做验证更糟，因为它会带来虚假的信心。真实案例（2026-07）：某个 .docx 文件通过 macOS Quick Look 缩略图完成了“视觉验证”，但该工具无法复现两端对齐文本的拉伸效果；用户一用 Word 打开文档，就发现信息块被撑得七零八落。解决方法是安装兼容 Word 的引擎（LibreOffice），将文件转换为 PDF，逐页栅格化，然后阅读每一页。要么匹配引擎，要么验证就只是做做样子。**这一原则不仅适用于渲染器，也适用于所有验证工具**——解析器、代码检查器、验证器：它必须与生产环境共享同一种实现，否则它给出的绿色结果毫无意义。另一个形式相同的案例：一位作者试图在源文件阶段检查一种会破坏最终文档的标记模式，但使用的 markdown 实现与生产工具链所用实现*不同*——它将三个已知存在问题的输入都解析为完全正常，因此任何基于它构建的预检查都会悄无声息地放过所有问题。诚实的结论是，这种特定缺陷只能在生产工具运行后检测，而检查也应放在那里。**如果没有任何可用工具与生产环境共享同一种实现，就应明确说明该阶段无法执行检查——不要构建一个只会产生虚假绿色结果的检查。**
   根据技能类型建议合适的默认选项，但由用户决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认技能类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这种前置分类将决定后续的整个评估策略。此处判断正确，可以避免之后浪费精力。

### 扩展还是创建检查——在任何专用分支之前运行

下面三个专用工作流的结尾都有“**不要**继续阅读下方章节”，而*现有方案研究*恰好位于它们之后。**这种顺序只是版面布局，并非执行顺序。**“扩展还是创建”的判断适用于每个分支，而跳过这一步，恰恰会导致会话交付一个与已安装技能重复的技能。

因此，在进入包装器技能／对话挖掘／制品语料库分支之前，先回答一个问题：**是否已经存在一个应当包含此功能的技能？**

**发现根目录，不要凭记忆回想。** 手动维护的安装位置列表正是那种会过时的制品，而你忘记的那个根目录往往正是造成问题的根源。

**搜索文件，而不是搜索名为 `skills` 的目录。** 技能目录以*技能*命名（`skill-creator/`、`<suite>/<skill>/`），因此源码仓库、市场仓库克隆和插件缓存中可能根本没有名为 `skills` 的目录——搜索这个名称会悄无声息地跳过它们，看起来却像是搜索正常完成了。每个技能都有一个 `SKILL.md`；这是与布局无关的检索依据。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，并且返回的结果仍会多于你的需要；应使用与该功能密切相关的术语进一步缩小范围，而不是使用宽泛术语（`chart` 会匹配所有内容，`stacked bar` 则不会）。

这项工作所能触及、而仅凭记忆列清单时通常会遗漏的根目录包括：技能源码仓库（一个 `claude-code-skills` 检出目录及其任何 `-pro` 同级目录）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过市场安装的套件——源码仓库中没有任何迹象表明它们存在于此）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、各配置档案的配置主目录（`~/.claude-profiles/<name>/`），以及——这个完全没有任何线索——**每个项目自身的 `.claude/skills/`**。第 2 步使这成为一个经过你验证的结论，而不是一个从他处沿袭的说法。

**项目级技能在结构上是不可见的。** 它们存在于某个不相关项目的工作树中，因此不会出现在任何市场、任何全局技能列表或任何源码仓库清单里；你在规划新技能时通常会查看的内容，没有任何一处会提到它们。真实案例（2026-07）：一个会话为某个领域构建了全局技能，遍查源码仓库、全局目录以及其他智能体的目录，一无所获，于是发布了。后来搜索对话历史时，发现了一个针对完全相同领域的成熟项目级技能，它已有一个月之久，就位于某个项目的 `.claude/skills/` 中——其中包含新技能所欠缺的八条规则，包括一条用户曾亲自口述的规则。除项目级根目录外，其他所有根目录都已检查，而遍查结果仍无比确信地报告“没有既有成果”。

**当重叠对象确实是不相关项目中的项目级技能时该怎么办**——这正是上述惨痛案例会把你带入的情形，也是下方三个要点没有涵盖的情形：你无法把同级技能添加到一个根本不存在的套件中，而“扩展它”则意味着编辑一个不相关项目的工作树。行之有效的做法是：**将它的规则采纳到你正在构建的技能中，然后在获得所有者同意后停用项目本地技能**——它是基于真实工作编写的，因此应将其视为更成熟的来源，并以它为方向进行协调。停用某人正在使用的技能应由所有者决定，而不应成为你构建工作的附带结果。

这句话遗漏了四件事，其中任何一件都可能让你受阻：

- **“以它为方向进行协调”是一项可反驳的推定，而不是规则。** 有两种常见的例外：项目技能可能已经*过时*（规则是数月前针对一个后来已经变化的系统编写的），也可能具有*项目特定性*（规则只在该项目的约束条件下成立——将其全盘导入会使你的技能适用范围变窄，而本文档其他部分明确要求你不要这样做）。采纳的规则也是另一位作者的记忆，因此应按照规范 #1 对写入技能的任何内容所提出的要求，**逐条重新验证**。
- **“停用”需要一种机制，而第一步并不是你本能想到的那一步。** 请按以下顺序操作：

  1. 在 grep 搜索技能的*引用*之前，先用 **`find` 查找技能的*主体***。同一仓库中经常存在同一技能的多个副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会由不同工具从同一个工作树中加载。Grep 回答的是“谁提到了它”；只有 `find` 才能回答“它有多少个副本”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放入 `--exclude-dir`**（它按基本名称进行匹配，因此会隐藏所有同名目录，包括你尚未发现的副本——参见规范 #6 中的工具规则）。真实案例（2026-07）：一次停用操作正是这样做的，它修复了找到的全部五处引用，却在 `.agents/skills/` 下留下了第二个完整副本——由 git 跟踪、没有停用标记，并且是一个缺少最新规则的陈旧快照——其他工具仍会将其作为有效技能加载。
  2. 在删除任何内容之前，**确认从旧技能所在的位置确实能够访问新位置**——你刚推送的市场技能在市场更新并安装插件之前并未真正安装，而先停用旧技能会造成一段两者皆不可用的空窗期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 并非可选项——插件缓存经常通过符号链接指向源码仓库，而不带该选项的 `find` 会报告文件缺失（参见规范 #6 中的工具规则）。
  3. **然后**用 grep 搜索引用，并将仍然有效的引用重新指向新位置。要区分**有效指令**（技能列表、交叉引用、告诉下一个智能体应使用什么的交接文档）与**历史记录**（例如某条决策日志记录写着“在日期 X，我们发布了这个”）——改写后者会为了修复一个并不存在的问题而破坏审计轨迹。
  4. **然后**将每个主体替换为 `superseded by <skill>` 存根，而不是直接删除，并确保每个副本中的存根在字节层面完全相同。**保留 YAML frontmatter**——缺少它的 `SKILL.md` 可能直接加载失败，而无法以提供有效信息的方式失败——但要重写 `description`，使存根声明自身已被停用，而不是继续宣传旧的触发条件；否则，它仍会在路由中胜出，却已无法完成对应任务。正文只需包含：能力迁移到了何处，以及一行说明迁移原因。
- **使用下方的所有权测试确定所有者**（它也适用于此处：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍会告诉你它属于谁）。如果所有者正是与你交谈的人，那么一次 `AskUserQuestion` 就足以获得“同意”。**如果无法联系所有者，只采纳规则，不要停用技能**（这会使两个技能都保持有效并竞争同一触发条件，与所有者拒绝停用时的最终状态相同——参见下方的“共存与优先级”）。
- **如果所有者拒绝停用它**，那么现在就有两个技能在竞争同一触发条件；这属于下方的“共存与优先级”问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 如果按新技能的标题搜索，那个项目技能并不会匹配；真正让它匹配的是其正文中的领域术语。使用新技能将处理的*概念*，在候选根目录中执行 grep 搜索。

如果发现重叠：

**如何判断应适用哪一条——这是谁的技能？** 文件系统中的命中结果并不包含所有权信息。请读取该市场的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在其所在仓库中运行 `git remote -v`；位于 `~/.claude/plugins/marketplaces/` 下的命中结果，也完全可能只是你*自己的*市场被安装回了你的机器。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同一个问题。

有两种情况是这些探测方法会判断错误或无法回答的，因此在相信结果之前，请先检查它们：**fork** 显示的是你自己的远程仓库，但内容属于其他人——应将其视为第三方内容，因为你仍然无法继续获得其上游改进。还有，当**既没有 marketplace.json，也没有 remote** 时（例如仅存在于本地的项目，或手动复制到全局技能目录中的技能），探测结果是无声的，而不是否定的：**询问所有者，不要猜测**。

- **重叠的是第三方技能**（市场套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*轻量增量层*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本——并**使用带命名空间的名称引用它**。将他人的引擎克隆进你的套件，是代价高昂的错误：你将无法继续获得他们的升级，而且两个副本会悄无声息地逐渐分化。
- **重叠的是你自己的技能**：扩展它，或者在其现有套件中添加一个同级技能。创建一个争夺相同触发条件的独立技能，对任何人都没有帮助。**例外：**如果它位于某个*无关项目*的工作树中，则这两种做法都不适用——请参阅上面的项目级情况。
- **某个相关技能已经指向你正在填补的空缺**（例如，其描述中写着“对于 X，请使用 Y”）：构建完成后，要形成闭环——更新该指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**在一次真实的 2026-07 会话中，团队花了一整天让某个第三方 docx 引擎生成正确的中文商务文档，然后转而进入包装器技能分支——该分支直接跳过了现有方案调研。它当时准备交付的形态，是一个重新承载该引擎能力的全新技能。正确的形态应当是一个**三层引用链**：保持第三方引擎不变 → 用一个轻量增量技能保存正确用法和经过验证的生成器脚本 → 由领域工作流技能调用该增量技能。用户不得不纠正两次才让它走上正轨，而第二次纠正更加一针见血：*"不要额外复制一份——在他们的实现之上写明正确用法，并引用他们的技能；这才是技能即代码的含义。"*

### 验证深度路由器（在选择任何工作流之前运行）

在进入通用或专用工作流分支之前，选择**能够证伪变更后行为的最低层级**。应根据具体变更及其故障影响面进行分类，而不是根据行数或请求中的措辞：一条发生变更的破坏性命令，其层级可能高于大段文字清理；而要求“优化”现有技能的请求，仍可能只是一项有明确边界的修正。在选择层级之前，列出你实际打算变更的规则、契约、脚本、权限和输出。如果尚不清楚该列表，应先检查并保持暂定分类；对范围存在不确定性，并不构成归入第 3 层级的依据。

| 层级 | 适用情形 | 所需证据 | 默认不要添加 |
|---|---|---|---|
| **1 — 定向** | 这是现有技能；未新增或实质性变更任何能力、触发器类别、工作流分支、输出契约、依赖项、权限或外部写入行为；且编辑恰好属于以下一种：(a) 仅修改拼写/格式，不改变行为；(b) 对文档/配置中的事实进行修正，且其真实性可由直接权威来源判定；或 (c) 有明确边界的实现修复，用于恢复明确的现有契约，**并且**修复后的行为由确定性回归检查覆盖。可能改变智能体行为的澄清不属于第 1 层级 | 对于上述三种情况：运行 `quick_validate`、检查差异，并完成现有技能迁移门禁。然后只使用与之匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其针对性检查；(c) 明确的现有契约及确定性回归。仅当达到规范 #5 中的规则/契约/数量阈值时，才加入其中要求的一名新审阅者 | 智能体行为重放、成对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 抽样行为** | 这是现有技能；变更会影响智能体行为，但不会新增能力、触发器类别、输出契约、脚本行为、依赖项、权限或外部写入；且 1–2 个具名示例配合明确的验收标准即可覆盖全部变更行为。对一条现有路由或证据选择规则所做的有界修正，即使会改变所选路径，也仍属于此层级 | 仅运行这 1–2 个具有代表性的启用技能重放，加上针对性的确定性检查，以及规范 #5 要求的一次全新上下文审查 | 默认不添加基线、成对扇出、方差分析、基准测试、查看器或评估文件。对这些内容的明确请求需通过单独的证据预算门禁，且不会改变该变更的分类 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新技能；任何新增或发生实质性变更的能力；广泛的跨分支重写或方法论扩展；触发器/描述优化；新的工作流分支，或发生实质性变更的输出契约、脚本能力、依赖项或权限；高风险自动化或外部写入；或者变更后的行为本身跨越 3 个以上不同的提示类别、需要重复试验或涉及实质性不同的方法 | 先运行确定性门禁，然后仅添加覆盖具名故障维度所需的证据。只有在单独的重度评估授权门禁通过后，才可使用下述完整的成对流程；第 3 层级本身不会启动该流程，同一门禁也可授权其他层级使用额外证据 | 不得仅依据第 3 层级标签自动执行成对扇出、评分器、基准测试或查看器 |

#### 重度评估授权门槛——与层级分类分离

层级描述的是**风险与不确定性**；它并不授权令牌开销或智能体扇出。通过此门槛改变的是允许采用的证据计划，而不是层级。通用的配对基线 → 评分器 → 基准测试 → 查看器流水线仅可在以下任一情况下运行：

- 用户明确要求进行 A/B 测试、设置基线、开展基准测试、重复试验、使用查看器或进行多智能体评估；或
- 执行者能够列出至少三种不同的提示词类别、相互竞争且均合理的可能结果，以及配对比较会改变的决策，然后获得用户明确的选择加入许可。

对于现有技能优化，默认使用零个评估智能体：先运行确定性检查，然后仅在行为仍不确定时，最多进行一到两次启用技能的重放。纪律 #5 所要求的一个全新上下文审查者是发布门槛，并不表示可以创建审查者团队。令牌/成本敏感性指令会阻止重度流水线，直到用户明确撤销该指令。

在生成一个以上的研究、挖掘、评估或评分智能体之前，应将**角色**与**执行单元**分开：

- 每个新增角色或审查者都必须负责一个不同的失败维度或输出。模板可用绝不能作为增加角色的理由。
- 必要的实验分支和语料分片可以共享同一维度：启用技能的分支与基线分支需要隔离的上下文，而一个挖掘角色可能需要处理多个有界分块。启动前，应说明执行单元的确切总数、并发上限，以及合并它们为何会污染比较或超出分块预算。默认串行运行；明确的 A/B/挖掘请求仅授权这些必要单元，并不授权额外角色。
- 对于由执行者提出而非用户明确要求的扇出，应获得用户对该数量的选择加入许可。如果交互式提问工具不可用或用户没有回答，则采用较轻量的证据路径；沉默不代表同意。

如果某个单元既不承担不同的角色/输出，也不是必须隔离的实验分支/分片，就不要生成它。

当较低层级暴露出未解决的行为或相互矛盾的证据时，应升级层级。用户要求取消或降级评估时，应立即停止已经启动的配对评估智能体、基线、评分器、聚合和查看器工作。如果风险分类仍有参考价值，则予以保留，但只报告实际运行所得的证据和尚未检查的维度；不要因为标签如此，就把尚未运行的重度套件描述为自动“必需”。当达到纪律 #5 的规则/契约/数量阈值时，不要取消其要求的单个全新上下文审查者，也不要取消任何用于防止破坏性操作或外部影响的安全门槛。机械式现有技能迁移审计、公共技能净化以及任何特定领域的安全门槛也仍然独立于此路由器。

### 专用工作流：第三方 CLI 工具的包装器技能

在决定采用通用技能创建流程之前，请检查促成当前节点的会话是否实际上应改用**包装器技能**工作流。包装器技能是一种配套工具，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或技能包——即由其他人编写、而用户刚刚花费一轮会话才让其在自己的机器上正常运行的代码。

适用信号（任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或者使用官方安装程序。
- 会话中出现了真实、具体的错误消息，并且用户与 Claude 已经共同找出了具体的修复方法（编辑文件、添加标志、绕过别名）。
- 用户说了类似“wrap this up as a skill”“save this as a wrapper skill”“so other people don't have to go through this again”“把这次 session 做成一个 skill”这样的话。
- 用户明确提到某个第三方工具的名称，并希望其他代理或其他人无需再次付出他们刚刚经历的学习成本就能使用该工具。

不适用信号（改用上面的通用工作流）：

- 用户想要为某个准备从头编写的内容创建 skill。
- 会话过程很顺利——没有值得记录的实际阻碍。
- 该 skill 将封装用户拥有或控制的服务（这是他们自己的代码；应编辑源代码，而不是进行封装）。
- 所谓的“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当封装 skill 工作流适用时，保留上面选定的验证层级。创建封装就是创建一个新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用创作章节；直接跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并从头到尾遵循该工作流，包括其验证协议。这是一个**回顾式提炼**工作流——其任务是从当前对话中挖掘安装流程、已修复的 bug 以及已做出的设计决策，并将挖掘结果转化为一个完整、自包含的封装 skill，使其他用户能够安装并从中受益，而不必重历这次调试过程。

封装 skill 工作流有自己的架构约定、代码模板和 Tier 3 验证协议——由于其输出是用户的安装状态，而不是可以轻松进行断言的文件，因此它会替代不兼容的通用测试用例机制；这并不意味着降低工作标准。运行证据计划所选定的兼容通用步骤；通用的配对评估步骤仍然需要经过重型评估授权关卡。记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库的根目录——这里曾经使用的裸相对链接在该 skill 被移入套件后就失效了，这恰好印证了下面跨 skill 引用规则中的警告）；它是对 Tencent IMA skill 的封装，使用这一工作流从真实会话中提炼而成。

### 专用工作流：从对话历史中丰富 Skill

在决定采用通用 skill 创建流程之前，先检查当前会话是否实际上是在请求将**过去的对话提炼成 skill**。当用户已经在多个 Claude Code / Codex 会话中调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这种方式非常有用。

**必须有明确的来源意图。** 长时间进行中的对话、最近完成的调试任务，或 `use skill-creator to optimize <skill>`，均不代表用户同意打开本地历史记录，也不能作为进入此工作流的理由。对于常规更新，应直接使用当前对话。只有当用户明确要求挖掘/提炼更早的本地对话，或明确指定某些先前会话作为素材来源时，才进入对话挖掘工作流。

适用信号（必须全部满足）：

- 用户明确指定将本地/过往对话历史作为输入，例如“挖掘我的聊天记录”“使用早期会话丰富此 skill”或“把以前的对话沉淀到 skill 里”。
- 来源会话及时间/范围边界已知或已确认。
- 预期输出是可复用的知识或代码资产，且这些内容无法通过当前对话和现有 skill 包直接表达。

不适用信号（应改用上面的通用工作流）：

- 用户根据单个提示或想法创建全新的 skill。
- 用户要求优化现有 skill，但未要求读取先前的本地历史记录。
- 相关修正和证据已存在于当前对话中。
- 用户希望为刚安装的第三方 CLI 工具创建封装（使用上面的 wrapper-skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的对话记录导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件中。
- 来源素材是一批用户已认可的成品，而非对话——使用下面的成果语料提炼工作流。

当对话挖掘工作流适用时，保留上面所选的验证层级。新建的挖掘型 skill 属于第 3 层；只有在满足所选层级的能力边界时，对现有 skill 的丰富才可维持在所选层级。**不要**继续阅读下面的通用编写章节；请跳转至 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端遵循该工作流，包括其中的验证协议。这是一个**回顾性提炼**工作流：它会发现已获批准的本地历史记录，对其进行脱敏和分区，仅执行语料库所需的挖掘轮次，并在验证后提升已审核的候选内容。

对话挖掘工作流拥有自己的架构约定、代理提示词、模板和验证协议。该协议实现所选层级的专门机制；执行证据计划所选择且兼容的通用步骤，将高负载的通用步骤置于其授权门控之后，并记录任何替代操作。它是将明确获批的对话历史转化为 skill 可复用知识库的规范方式。

### 专用工作流：从已认可的成果语料库中提炼用户偏好

在决定采用通用流程之前，请检查当前会话是否要求**从一批用户已认可的成品中提取用户的真实偏好**——例如已认可的 HTML 报告页面、生成的文档和设计。这是区别于上述两种来源的第三类提炼来源：素材是**成果，而非对话**，输出是**可执行的品味**（明确的原则、量化的参数、词汇），而非知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的产物，并表示“这些都是我认可的样例”/“你来学到底什么是我想要的”/“从这些已认可的示例中提取我的偏好”。
- 某个品味校准技能（报告生成器、文档样式设计器、幻灯片构建器）拥有持续增长的已认可样例语料库，而用户要求让该技能真正从中*学习*，而不只是为其建立索引。
- 用户抱怨之前的更新“只加了示例”——只对样例进行了编目，却没有改变技能行为。

不适用的信号：源材料是对话/纠正，而不是得到认可的产物（应使用对话挖掘）；样例并未得到用户本人认可（认可是准入门槛——请先询问）。

适用时，保留上方选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。由新语料库衍生出的技能属于第 3 层级；向现有技能添加实质性的新决策能力也属于第 3 层级。专用协议会实现所选层级的语料库机制，而不会降低其标准；执行证据计划所选择的兼容通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代操作。其核心准则同样适用于每次向现有技能添加材料时：**编目 ≠ 蒸馏**——在语料库表格中登记样例不会对技能下一次运行产生任何改变；对于每项新增内容，都要问“*这是否改变了一条决策规则？*”；如果对写入的所有内容而言答案都是否定的，就不要宣布蒸馏会话已经完成（方法论案例 15）。该工作流的主干是：通过脚本提取，对所有产物进行定量比较（每种模式至少有 3 个产物作为阈值，并针对每个声称的常量检查例外列表）→ 依据证据锚点进行分层归纳 → 写入决策规则层（将不变量与依赖语域的变量分离）→ 独立的完整性审计（常设准则 #5）→ 回归审计。

### 既有成果研究（不可跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——正是技能价值所在。任何公共仓库都无法提供这些内容。但如果已经存在成熟工具，用户也不应浪费时间重新发明基础设施（API 客户端、认证流程、速率限制）。既有成果研究会为基础设施层寻找可复用的构建模块，使技能可以专注于编码用户独有的方法论。

**这是两个维度，不要将其混为一谈。**本节为*基础设施*层寻找来源（可复用的工具 / MCP / 库 / 现有技能）。*方法论*层有两个独立输入：用户的私有优势（仅属于他们，无法检索）**以及该领域既有的最佳实践 / 科学知识；根据常设准则 #3，默认应将后者检索到上下文中。**找到合适的工具并不意味着已经完成第二项工作——一个采用了图表库却从未吸收 Cleveland/Bertin 理论的可视化技能，仍然受限于你的预训练水平。两者都要做。

**按顺序搜索这些渠道。** 默认以内联方式开展研究。只有在上述重度评估/智能体预算门控确认存在真正相互独立的未知问题后，才使用子智能体；公共来源渠道并不是默认的扇出式搜索组合。

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **当前对话或明确获准访问的历史记录** | 用户已验证有效的工作流、经过验证的 API 模式、调试期间作出的修正 | 直接使用当前对话。仅在通过上述明确来源门控后，才搜索更早的本地历史记录；随后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档和 SOP** | 用户的私有方法论、操作手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件和 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中已配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 和 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 面向同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或对文档 URL 使用 `WebFetch` |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己已验证的模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终具有最高优先级——公共工具只是构建模块，而不是替代品。在竞争性领域（金融、交易、专有业务运营）中，有价值的方法论绝不会公开。

**优先选择合并/扩展而不是新建，并且要扫描每一个技能根目录——不能只扫描 `~/.claude`。** 当渠道 1-3 找到与所请求领域有重叠的现有技能时，通常正确的做法是扩展它或合并到其中——**但如果它位于某个不相关项目的工作树中，则方向应反过来：从中提取内容并纳入你正在构建的技能，而不是将内容合并到它里面**（参见上方扩展还是新建检查中的项目级案例）（一个真实的“新技能”任务最终变成了“让现有提取器成为新归档器的提取阶段”），而不是交付一个争夺相同触发条件的并行技能——两个相互重叠的技能会争抢触发机会，并让用户感到困惑。搜索时，**应发现安装根目录，而不是凭记忆列出一份清单**——使用上方扩展还是新建章节中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会完全遗漏源代码仓库、市场镜像和插件缓存，因为其中的技能目录是以技能名称命名的）。请运行覆盖检查，而不是轻信这句话：**每个项目自身的 `.claude/skills/`** 都是凭记忆列清单时必然容易漏掉的根目录，因为该项目之外没有任何地方会引用它。用户已在*任何位置*安装的技能，都是最有力的既有参考，而项目本地技能往往最为成熟：它是针对真实工作编写的。

**如果发现公开的 MCP 服务器或技能，请克隆并验证——不要轻信 README：**

1. **阅读实际源代码**——许多项目的 README 十分精美，代码库却徒有其表
2. **验证身份验证方式**——它是否符合 API 实际采用的身份验证方式？（X-Api-Key 请求头、Bearer 或 OAuth——许多项目在这方面存在错误）
3. **检查测试覆盖率**——零测试意味着它只是原型，而非生产级项目
4. **检查维护情况**——最近一次提交日期、未解决的问题数量、对错误报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有用途冲突
7. **检查依赖体量**——庞大的依赖树会增加冲突和安全风险面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用它，并在其上构建**——安装 MCP，然后将技能构建为工作流层，对用户的方法论进行编码 |
| 存在部分可用的 MCP 或 SDK | **扩展**——用它处理基础设施，并在技能中补齐缺失部分 |
| 公开技能覆盖相同领域 | **仅将其用于结构参考**——竞争领域中的公开技能从定义上就是通用的。用户的优势在于其私有 SOP |
| **存在能够提供你所构建内容中某项子能力的互补技能** | **将其打包**——把互补技能中自包含的资产复制到你的软件包中，并将其连接起来。不要依赖用户已预先安装该技能。参见下文的“互补技能” |
| 不存在公开实现 | **从头构建**——在编写完整技能之前，验证 API 访问模式是否有效（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——与其采用存在集成摩擦和上游风险的“成熟”工具，不如选择你自己拥有的、耗时 2 小时的自定义实现 |
| 用户有意取代已安装的技能（分支版本、强化版本） | **随附取代工具包发布**——参见下文的“共存与优先级” |

#### 共存与优先级（有意重叠）

对于重叠，默认的解决方式是合并到现有技能中（见上文）。但当用户*有意*发布与已安装技能重叠的技能时——例如官方插件的分支版本或内部强化版本——技能列表中会出现两个描述相似的条目，Claude 将在它们之间随机路由。请按递进顺序解决：如果重叠是意外造成的，则重命名；添加用于判定优先级的描述（“取代 X——当两者同时出现时，始终使用此技能”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式取代工具包写入技能——这是一个基于用户同意的 SessionStart 路由钩子，仅会安装在确实存在竞争技能的机器上，在其他机器上会拒绝安装，并且当任意一方消失时会自行禁用。有关机制、决策表、SKILL.md 示例措辞及沙盒验证，请参阅：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此技能使用同一套工具包针对官方 skill-creator 插件进行自我实践（参见顶部的“第一步：共存检查”）。

**更常见的情况是：在没有任何刻意分叉的情况下，你的新技能悄无声息地失去了对*已安装技能群体*的触发优势。** 一个技能所属的领域（图像生成、PDF 处理、仪表板）通常已经挤满了多个已安装的技能，而新技能可能会在自动路由中输给所有这些技能。因此，**应尽早验证触发情况——内容足够好并不意味着构建已经完成。** 草稿完成后，通过 `claude -p` 发起几个真实查询，检查新技能是否确实胜出；如果没有，**明确指出它输给了哪个具体竞争技能**（不同查询往往会输给不同的技能）。然后要了解两点：(1) **文案并不总能在拥挤的触发位中胜出**——解决路径依次为：重命名 → 通过描述进行决胜/使用 SUPERSEDES → 手动调用 → SessionStart 路由钩子（结构性方案；会修改全局配置，因此需要获得用户的明确同意，遵循与 `--no-verify` 相同的规范）；(2) **修复方式取决于竞争技能的作者是谁**——竞争技能由*第三方*编写 → 接受手动调用或使用路由钩子；竞争技能由*你自己*编写 → 将它们合并/整合为一个技能，不要让自己的两个技能持续争夺同一个触发条件。（完整的解决路径位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要只是指引，不要单独扩展它们。）记录所选路径（例如，在“激活”说明中写明“手动调用，竞争技能由第三方提供”），可以避免下一次会话重新争论这个问题。（方法论案例 13）

##### 互补技能（打包，而非依赖）

构建涉及某个已有互补技能领域的技能时，有两种选择：

- **依赖它已安装**：很脆弱——用户可能没有安装它，或者安装的是其他版本。每一次缺少依赖项的故障都可以追溯到这个选择。
- **将它打包进来**：把互补技能中可独立使用的资源（脚本、模板、参考文档）复制到你自己的包中，并完成接线配置，使你的技能可以独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将它打包进来。** 这对于以下内容尤其重要：
- 状态栏/UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证/清理脚本
- 通用数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要一个状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。配置文件设置技能并不依赖用户先运行 `statusline-generator`，而是将 `statusline.sh` 打包进来，并在 `claude-profiles-init` 期间将其接入每个新配置文件。这两个技能仍然可以各自独立发挥作用，但封装技能也能独立运行。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装程序”。这会把依赖问题推给用户，并产生脆弱的安装顺序。应改为将其打包进来。

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，应倾向于采用成熟的基础设施来处理底层管道，并为方法论层构建自定义逻辑——真正的价值就在这里。

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。在彻底明确这些内容之前，不要编写测试提示词。

在有助于研究时检查可用的 MCP（搜索文档、寻找类似 Skill、查找最佳实践）。默认以内联方式开展研究。仅针对某个明确且尚未解决的问题使用子代理，绝不要因为工具可用就自动进行并行扇出。事先准备好上下文，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈，填写以下组成部分：

- **name**：Skill 标识符
- **description**：何时触发、具体做什么。这是主要的触发机制——既要包含 Skill 的功能，也要包含应在何种具体情境下使用它。所有“何时使用”的信息都应放在这里，而不是正文中。注意：目前 Claude 往往会“触发不足”——即在 Skill 本可发挥作用时却不使用它。为解决这个问题，请让 Skill 描述稍微“积极”一些。例如，与其写“如何构建一个简单、快速的仪表板来展示 Anthropic 内部数据。”，不如写成“如何构建一个简单、快速的仪表板来展示 Anthropic 内部数据。只要用户提到仪表板、数据可视化、内部指标，或希望展示任何类型的公司数据，就务必使用此 Skill，即使他们没有明确要求使用‘仪表板’。”

  **做好字符预算：description 有严格的 1024 字符上限，超过此长度将无法通过验证。** 这与上述“积极”建议存在直接冲突——为扩大覆盖范围而添加的每个触发短语都会消耗预算——因此应在扩充之前而不是之后进行测量：`len(description)`，不要凭感觉。陷阱并不在初稿（初稿很少接近上限），而在于*多年后的更新*，届时会为了新覆盖的范围添加触发条件：一份成熟的 description 往往距离上限只有几十个字符，此时**添加一个触发条件是一场零和博弈——你必须删除一个现有条件来为它腾出空间。** 要有意识地进行这种取舍，并在提交中明确说明，因为悄无声息地删掉一个触发短语，实际上就是缩小了 Skill 的触发范围，而且在它不再为某位用户触发之前，没人会注意到这一点。（实践中的案例：一次更新为新覆盖的故障模式添加了触发条件，将 description 推高到 1280 个字符，经过两轮压缩才降至 1003——代价是三个预先存在的触发短语；这是一个本应明确做出的决定，而不应在与验证器周旋时才被动发现。）必须删减时，应优先删除那些仍可通过同义词或相邻短语触达其场景的短语，保留那些没有其他触达路径的短语；还要记住，正文中的限定语（“在平台 X 和 Y 上”、括号内的枚举）通常比一个独立的触发短语更适合删除——正文内容可以从主体中重新推导，而触发短语则不行。
- **compatibility**：所需工具、依赖项（可选，极少需要）
- **Skill 的其余部分 :)**

### 技能编写指南

#### 技能的结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML 前置元数据参考

除 `description` 外，所有前置元数据字段均为可选字段。使用 `---` 标记之间的这些字段配置技能行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必需 | 说明 |
|-------|----------|-------------|
| `name` | 否 | 技能的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 推荐 | 技能的功能及其适用场景。Claude 使用此字段决定何时应用该技能。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在分叉的子代理上下文中运行。** 请参阅下文的“内联与分叉：关键决策”——选择错误会导致技能失效。 |
| `agent` | 否 | 设置 `context: fork` 时要使用的子代理类型。选项包括：`Explore`、`Plan`、`general-purpose`，或来自 `.claude/agents/` 的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 可阻止 Claude 自动加载此技能。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false` 可将其从 `/` 菜单中隐藏。适用于不应由用户直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：请勿设置此字段。** 省略此字段可让技能在用户权限设置的约束下拥有完整的工具访问权限。设置此字段会不必要地限制技能的能力。 |
| `model` | 否 | 此技能处于活动状态时使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指明预期参数。示例：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此技能生命周期的钩子。示例：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** 技能内容中的 `$ARGUMENTS` 会被替换为用户在技能名称后提供的文本。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### 内联与分叉：关键决策

**这是设计技能时最重要的架构决策。** 选择错误会悄无声息地破坏技能的核心能力。

**关键约束：子代理无法生成其他子代理。** 使用 `context: fork` 运行的技能（作为子代理）无法：
- 使用 Task 工具生成并行探索代理
- 使用 Skill 工具调用其他技能
- 编排任何多代理工作流

**决策指南：**

| 你的技能需要…… | 使用方式 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **内联**（无 `context`） | 子代理无法生成子代理 |
| 调用其他技能（Skill 工具） | **内联**（无 `context`） | 子代理无法调用技能 |
| 运行 Bash 命令以使用外部 CLI | **内联**（无 `context`） | 在主上下文中拥有完整的工具访问权限 |
| 执行单个聚焦任务（研究、分析） | **分叉**（`context: fork`） | 隔离的上下文，干净的执行环境 |
| 提供参考知识（编码约定） | **内联**（无 `context`） | 指南可丰富主对话的上下文 |
| 可被其他技能调用 | **分叉**（`context: fork`） | 必须作为子代理才能被生成 |

**示例：编排器技能（必须内联）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**示例：专家技能（适合使用分叉）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**示例：参考技能（内联，无任务）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的技能设计（正交性）

技能应当保持**正交**：每个技能只处理一个关注点，并通过组合协同工作。

**模式：编排器（内联）调用专家（分叉）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须为内联模式（无 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个技能都应具有单一职责——不要将编排与执行混在一起
4. 通过参考资料（例如清单、模板）共享方法，而不是复制代码

##### 流水线交接（顺序技能链）

除了编排器/专家组合之外，技能通常还会构成**顺序流水线**，其中一个技能的输出会成为下一个技能的输入。每个技能完成工作后，都应主动建议符合逻辑的下一步。

**模式：在 SKILL.md 末尾添加“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界中的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion 让用户**主动选择**——未经询问，绝不能自动调用下一个技能
2. 仅当输出能够自然地作为另一个技能的输入时才提出建议——不要强行建立关联
3. 提供“不用了，谢谢”选项——用户可能不需要完整的流水线
4. 建议应解释下一步**为什么**有帮助（例如，“ASR 输出通常包含识别错误”）
5. 最多只提供 1-2 个建议——选项过多会导致决策疲劳

**何时添加交接：** 问自己：“这个技能的输出通常会成为另一个技能的输入吗？”如果是，则添加“下一步”部分。如果这种关联很少见或显得牵强，就不要添加。

**反模式：** 将不存在自然数据流关系的技能串联起来。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**绝不要为可以自动检测的能力添加手动标志。** 不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测相关能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：** 自动检测能力，由用户决定范围。技能应该自行发现它能做什么并据此采取行动，而不应要求用户记住已安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | 子代理可以使用 |
|-------------|----------------|-------------------|-------------------|
| （默认） | 是 | 是 | 否（内联运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（在被显式委派时） |

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（名称 + 描述）- 始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文** - 每当技能被触发时载入上下文
3. **捆绑资源** - 按需加载（数量不限，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是以行数为目标。一个没有填充内容的 600 行技能，胜过一个遗漏关键知识并迫使模型猜测的 200 行技能。如果技能变得很长，请问：“每个部分都有保留的价值吗？”如果有，就保留。如果某些部分只是填充内容，或解释 Claude 已经知道的事情，就精简这些部分——而不是删减有用的内容。当技能确实涵盖多个领域时，应按领域拆分为参考文件，而不是人为地将所有内容硬塞进一个简短的主文件中。
- 对于现有技能，渐进式披露是一种内容迁移策略，而不是内容删除的判断标准。旧有的运行时契约必须仍可通过打包产物中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或审阅者的记忆，都不能替代运行时契约。
- 在 SKILL.md 中清晰引用参考文件，并说明何时应读取这些文件
- 对于大型参考文件（>300 行），应包含目录

**按领域组织**：当一个技能支持多个领域/框架时，应按变体组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 避免意外原则

这一点不言自明，但技能不得包含恶意软件、漏洞利用代码或任何可能危害系统安全的内容。如果描述了技能的用途，其内容不应在意图上令用户感到意外。不要配合创建具有误导性的技能，也不要创建旨在协助未经授权的访问、数据外泄或其他恶意活动的技能。不过，类似“扮演某个 XYZ 角色”这样的内容是可以的。

#### 编写模式

在说明中优先使用祈使句。

**定义输出格式**——可以像这样做：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——加入示例会很有帮助。可以像这样设置格式（但如果示例中包含“Input”和“Output”，则可能需要稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得内置于技能中的可用性模式**——以下四种结构元素一再将“能用但令人困惑”的技能转变为用户真正能够驾驭的技能——它们是让一个被频繁使用的技能变得易用的具体改进，因此，当技能具有多种模式、会运行命令或可重复运行时，应优先采用这些模式：
- **入口决策树**：如果技能具有多种模式，开头应提供一个简短的“用户说 X → 使用模式 Y”映射，让模型能够正确选择路径，而不是靠猜测。
- **每条命令后的预期输出块**：在命令后立即展示“你应该看到什么”，以便模型（以及用户）能够区分真正的成功与无提示的失败。
- **故障排除部分**：列出已知的失败模式及其修复方法——对于将由其他人在你无法查看的机器上运行的技能而言，这是最有价值的部分。
- **第 0 步幂等性防护**：如果重新运行可能会重复执行已经完成的工作，应先进行一个成本较低的“这是否已经完成？”检查，再执行任何成本高昂的操作。

### 写作风格

与其大量使用生硬陈旧的 MUST，不如尝试向模型解释为什么这些事情很重要。运用心智理论，尽量让技能具有通用性，而不是过度局限于特定示例。先写出草稿，然后换一个全新的视角审视并改进它。

### 日期和版本引用

**保留事实性日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的技能应该注明“Suno v5.5（2026 年 3 月）”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应该避免的是**基于日期的条件逻辑**（“如果早于 2025 年 8 月，则使用旧 API”）——日期一过，只要没人更新，它就会立即变得错误。

规则：
- **发布日期、“上次验证”日期**：保留这些日期。它们是参考时间点，不是过期日期
- **定价、排名、法律状态**：应包含这些信息，但要将其标记为易变信息（“截至上次检查约为 $0.035/次生成”），让读者知道需要重新核实
- **“在 X 日期之前执行 Y，之后执行 Z”**：不要这样写。选择当前使用的方法，并可选择在折叠的/已弃用的章节中记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当同一段代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优势**：节省 token、结果确定，并且可以在不加载到上下文的情况下执行
- **注意**：Claude 可能仍需要读取脚本，以便进行修补或针对特定环境进行调整
- **用户可变数据应放在捆绑包之外**：如果脚本会积累用户数据（纠错词典、习得的偏好、缓存），请将其存储在稳定的、相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其单独设置备份——绝不要放在 skill 目录中。每次更新和套件迁移时，skill 安装内容都会被清除并重新创建；相对于主目录的存储则可不受影响地保留下来。正是通过这种方式，一个会持续积累词典的 skill 在完整套件迁移后实现了用户数据零丢失

##### 参考资料（`references/`）

用于按需加载到上下文中的文档和参考材料，以辅助 Claude 的工作流程和思考。

- **何时包含**：用于 Claude 在工作时应参考的文档
- **示例**：用于财务模式的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库模式、API 文档、领域知识、公司政策、详细工作流程指南
- **优势**：保持 SKILL.md 精简，仅在 Claude 判断有需要时加载
- **最佳实践**：如果文件较大（>10k 字），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应仅存在于 SKILL.md 或参考资料文件中的一处，而不是两处同时存在

##### 资产（`assets/`）

不用于加载到上下文中，而是供 Claude 在生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用某些文件时
- **示例**：作为品牌资产的 `assets/logo.png`，作为 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件架**：对于生成制品的 skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、可原样嵌入的片段，这些片段具有冻结的行为契约和注册表引用——请参阅步骤 4 中的组件架检查

##### 隐私和路径引用

**在应用以下任何内容之前，请先确定目标受众。** 以下所有内容描述的都是当 skill 发布给陌生人时会出现的问题。对于存放在作者自己的私有仓库中的 skill，同样的“违规项”通常恰恰是它能够正常工作的原因——真实的绝对路径能让脚本直接运行，模板中的真实账户能省去下次运行时重新填写的麻烦。`quick_validate` 会自动检测这一点（它会询问 `gh`，确认包含该 skill 的仓库是否为私有仓库），并在这种情况下将可移植性/标识符问题降级为提示；当正在准备发布私有 skill 时，`--audience=public` 会强制执行严格检查。

**在私有技能中，这些问题应由所有者决定，而不是你。** 未经询问，不要用占位符替换真实路径、改写硬编码凭据或对示例进行“脱敏”——这样做只会为了满足一条针对它根本不会前往的发布目标而制定的规则，破坏一个原本正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，并让所有者作出决定。（其设计先例是 npm 的 `"private": true`：通过声明发布目标来改变工具所执行的规则；之所以添加这一机制，是因为人们总是不小心发布内容。）

**对于打算公开分发的技能至关重要**——其中不得包含用户特定或公司特定的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的技能安装路径，例如 `~/.claude/skills/`
- **允许**：技能包内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外情况**（如果验证器逐字照搬上述禁止列表来实现，就会把这个技能本身标记出来——对正常输入误报比漏报更糟）：当取代关系的决胜规则或归属说明*要求*指明发布者时，可以使用发布者自己的名称/品牌；当段落的内容*就是关于* `~/.claude/skills/` 这类安装路径时，也可以使用这些路径（它们是教学材料，而非硬编码依赖项）

**跨技能引用**：不带任何限定的相对路径始终表示“位于此技能自身的包内”——验证器和读者都会按这种方式理解，因此，使用不带限定的路径指向另一个技能的文件既无法通过验证，也会误导读者。指向另一个技能时，应在正文中注明所有者（“marketplace-dev 的 cache-and-source-patterns 参考资料”），并使用带命名空间的名称调用技能（`/suite-name:skill-name`，而不是不带限定的 `/skill-name`）。当技能在套件之间迁移时，不带限定的交叉引用会悄无声息地失效——正因为如此，一次套件迁移在两轮清理后仍留下了 21 个失效的交叉引用。

##### 版本管理

**至关重要**：技能的 SKILL.md 中不应包含版本历史记录或版本号：

- **禁止**：SKILL.md 中的版本章节（`## Version`、`## Changelog`）
- **正确位置**：技能版本在 marketplace.json 的 `plugins[].version` 下跟踪
- **理由**：市场基础设施负责版本管理；SKILL.md 应当包含不受时间影响的内容

#### 参考文件命名

文件名必须做到无需阅读内容即可理解其含义。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**检验标准**：人们能否仅从文件名理解文件内容？

有两种例外情况：使用连字符的名称与使用下划线的名称同样合适（分隔符从来都不是重点——名称本身能够清楚说明内容才是重点）；命名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）由目录限定其含义——目录提供了具体性，而重命名这些文件会破坏各工作流之间的平行结构。

### 完整评估测试用例（仅限单独授权的配对方案）

仅当重度评估授权门禁通过时，才可进入本节。风险等级本身既不授权也不禁止收集此类证据；明确提出完整流水线请求不会重新划分底层变更的类别。不要仅仅因为 `SKILL.md` 发生了更改就使用它。专用工作流应遵循其在上文声明的替代契约。

编写完 Skill 草稿后，构思 2–3 个现实的测试提示词——即真实用户实际会说的内容。**对于会作用于实时系统（正在运行的服务、已登录的客户端、生产数据）的 Skill，请为每个测试提示词明确指定副作用预算**——例如，“仅进行只读探查并得出结论；不要执行下载/操控 UI。”在“只是测试”的情况下改变实时环境，属于真实操作，而非测试。通过 **AskUserQuestion** 呈现这些提示词：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存至 `evals/evals.json`。暂时不要编写断言——只写提示词。下一步中，在测试运行期间再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整模式请参阅 `references/eval_pipeline_schemas.md`（包括稍后将添加的 `assertions` 字段）。

## 完整配对评估流水线（仅限单独授权）

仅当重度评估授权门禁通过后，才可运行本节。风险等级仍应由变更后的行为决定。按影响决策的阶段执行流水线，并在不确定性消除或所请求的基准测试交付物完成后停止；不要预先启动下游评分器、聚合任务或查看器相关工作。用户取消或降低评估级别时，应立即停止重度流水线。未经授权不得使用本流程，也不要机械地添加已被专用工作流明确替代的通用机制，并且不要使用 `/skill-test` 或任何其他测试 Skill。

将结果放在与技能目录同级的 `<skill-name>-workspace/` 中。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些目录——只需在执行过程中按需创建。

### 第 1 步：运行已批准的使用技能/基线配对

对于每个已批准的测试用例，在相同的提示词和副作用预算下，分别运行一个使用技能的样本及其基线。这两个实验分支有意共用一个失败轴，但需要彼此隔离的上下文；它们是必要的实验单元，而不是额外的评审角色。启动前说明实验分支总数和并发上限。默认串行运行，且绝不能超过获准的单元数量。

**使用技能运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（提示词相同，但基线取决于具体上下文）：
- **创建新技能**：完全不使用技能。使用相同的提示词，不提供技能路径，并将结果保存到 `without_skill/outputs/`。
- **改进现有技能**：使用首次编辑前通过强制性现有技能回归门禁所捕获的旧版本。让基线子智能体使用该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，请停止并先从 Git 重建权威基线，再继续操作；绝不能将已经编辑过的目录树用作旧基线。**要清楚这种比较能够判定什么：它只能衡量本轮的变化量。** 如果你最想验证的能力已经存在于编辑前快照中——例如，某个并行会话恰好在你开始之前提交了相应修复——那么使用技能版本与旧版本之间的 A/B 测试对该能力的分辨能力为零；当该能力正是测试目标时，应选择更早的 ref 作为基线。

为每个测试用例编写一个 `eval_metadata.json`（目前断言可以为空）。根据测试内容为每个评测指定一个描述性名称，而不要只使用 "eval-0"。目录也使用这个名称。如果本次迭代使用了新增或修改后的评测提示词，请为每个新的评测目录创建这些文件——不要假设它们会从之前的迭代中自动沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：在运行过程中起草断言

不要只是等待运行完成——你可以有效利用这段时间。为每个测试用例起草量化断言，并向用户解释这些断言。如果 `evals/evals.json` 中已经存在断言，请审查它们并说明各自检查的内容。

好的断言应当能够客观验证，并具有描述性名称——它们在基准测试查看器中应清晰易懂，让浏览结果的人能够立即明白每条断言检查什么。**断言应针对意图编写，而不是针对字面上的工具路径**——应写成“语音内容保留在答案中”，而不是“调用获准的读取器脚本”。如果某次运行通过另一条获准的路径实现了目标（例如，读取一个已内嵌转录文本的归档文件），它就应该通过；如果因为未使用字面指定的路径而将其判定为失败，就会制造一个假阴性，随后还会诱使你在错误的位置进行“修复”。主观型技能（写作风格、设计质量）更适合进行定性评估——不要强行给需要人工判断的内容添加断言；其真正的验证路径（历史任务重放、将生产用作评测并养成回写习惯、渲染加人工审查）列在“Capture Intent”的问题 4 下。

起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。还要向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试。

### 步骤 3：在运行完成时采集计时数据

当每个子智能体任务完成时，你会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是采集这些数据的唯一机会——它们通过任务通知传递，不会持久化到其他地方。应在每条通知到达时进行处理，而不是尝试批量处理。

### 步骤 4：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分**——启动一个评分子智能体（或直接进行评分），让其读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于能够以编程方式检查的断言，应编写并运行脚本，而不是通过目测判断——脚本更快、更可靠，并且可以在多次迭代中复用。**但客观的 grep/脚本断言也可能产生双向误差**（相同词语但含义不同导致误命中，措辞不同导致漏检），因此**基准测试通过率只是一种信号，而不是最终结论**：抽查每条断言实际匹配的内容，并留意基线运行是否暴露了 skill 本身的事实错误（即“等等，数据确实在 API 中”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **聚合为基准测试**——从 skill-creator 目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   该脚本会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及 mean +/- stddev 和 delta。如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md`，了解查看器所需的确切 schema。
将每个 with_skill 版本放在其对应的 baseline 版本之前。

3. **执行分析审查**——读取基准测试数据，并揭示聚合统计数据可能掩盖的模式。有关需要关注的内容，请参阅 `agents/analyzer.md`（“分析基准测试结果”部分）——例如，无论是否使用 skill 都始终通过的断言（缺乏区分度）、方差较高的 eval（可能不稳定），以及时间/token 之间的权衡。

4. **启动查看器**，同时展示定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还需传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器进程陷入无响应状态**：进程仍然存活，但没有任何程序在监听——可通过 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（输出为空），或对该 URL 执行 curl（请求失败）；此处“没有日志输出”并不是可用的判断信号，因为上面的启动命令行将其重定向到了 `/dev/null`。终止该进程并改用 `--static`，而不是以相同方式重新启动。

   **Cowork / 无头环境：**如果 `webbrowser.open()` 不可用，或环境没有显示设备，请使用 `--static <output_path>` 写入一个独立的 HTML 文件，而不是启动服务器。当用户点击“Submit All Reviews”时，反馈将以 `feedback.json` 文件的形式下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. 通过 **AskUserQuestion****告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

“Outputs”选项卡每次显示一个测试用例：
- **Prompt**：给出的任务
- **Output**：该技能生成的文件，并尽可能以内嵌方式渲染
- **Previous Output**（第 2 次及后续迭代）：显示上一次迭代输出的折叠区域
- **Formal Grades**（如果执行了评分）：显示断言通过/失败情况的折叠区域
- **Feedback**：一个会在用户输入时自动保存的文本框
- **Previous Feedback**（第 2 次及后续迭代）：用户上一次的评论，显示在文本框下方

“Benchmark”选项卡显示统计摘要：每种配置的通过率、耗时和令牌使用量，以及各项评估的明细和分析人员的观察结果。

可通过上一项/下一项按钮或方向键进行导航。完成后，用户点击“Submit All Reviews”，将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告知你已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

反馈为空意味着用户认为结果没有问题。将改进重点放在用户提出了具体意见的测试用例上。

使用完查看器服务器后，将其终止：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是整个循环的核心。根据证据计划进行改进：对于第 1 层级，使用权威事实和确定性检查；对于第 2 层级，使用 1–2 个具名行为回放；或者，当独立的重型评估门控授权时，在任意层级使用经用户审查的配对结果。未经该授权，不要将配对评估产物引入默认的第 1/2 层级流程。

### 如何思考改进

1. **从反馈中归纳。** 这里发生的事情，从宏观上看，是我们正在尝试创建可以在许多不同提示词中使用无数次的技能（可能真的是一百万次，甚至更多，谁知道呢）。此时，你和用户只围绕少数几个示例反复迭代，因为这样有助于加快进度。用户对这些示例了如指掌，可以快速评估新的输出。但如果你和用户共同开发的技能只适用于这些示例，那它就毫无用处。与其加入琐碎且过度拟合的改动，或施加压迫性极强的 MUST 约束，不如在遇到某个顽固问题时，尝试拓展思路，使用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，而且或许能得到非常出色的方案。

2. **在不删减约定的前提下保持提示词精简。** 删除那些作用不大的内容，但在新旧版本审计完成分类之前，应将对现有技能的每一项删减都视为潜在的回归问题。将详细但可复用的行为移入直接链接的参考资料中；不要让它只存在于评估、变更日志或你的记忆里。阅读完整记录，而不只是最终输出——如果技能导致了无效工作，就简化指令并重新运行旧能力用例，而不要想当然地认为字数更少就意味着行为更好。

3. **解释原因。** 尽力解释你要求模型执行每一项操作背后的**原因**。如今的 LLM 很*聪明*。它们具备良好的心智理论能力，在拥有良好框架的情况下，可以超越机械执行指令，真正把事情做好。即使用户的反馈简短或带有挫败感，也要尝试真正理解任务，理解用户为什么这样写、实际写了什么，然后将这种理解传递到指令中。如果你发现自己正在用全大写形式写 ALWAYS 或 NEVER，或者使用极其僵化的结构，这就是一个警示信号——如果可能，应重新组织表述并解释其中的逻辑，让模型理解你所要求的事情为何重要。这是一种更人性化、更强大也更有效的方法。

4. **寻找重复工作——既要查看评估记录，也要查看技能所提炼自的对话。** 阅读测试运行记录，留意各个子代理是否都各自独立编写了相似的辅助脚本，或采用了相同的多步骤方法来处理某件事。如果 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这就是一个强烈信号，表明技能应该捆绑该脚本。只需编写一次，将其放入 `scripts/`，并让技能使用它。这样可以避免未来每次调用都重复造轮子。同样的信号也隐藏在你从中提炼技能的源对话里——只要那次会话编写过一次的代码，就是未来每次运行都必须重写的代码；不要等评估运行来证明这种重复（跳过评估循环的技能永远得不到这种证明——创建流程第 4 步中的脚本检查正是用来捕捉这类情况的）。

5. **逐字回写修正——同一会话、两个层级都要写。** 对于经过品味校准的 Skill，用户的修正本身就是评估集，但前提是这些修正被写到未来运行能够读取的位置。要让回写逐步收敛，需要具备两个特性：(a) **逐字记录修正内容**，不要转述——原话包含校准信号，而总结会将其抹平（“绝对禁止这种东西”划定了一条硬性边界；“用户倾向于减少跳转”则没有）。将用户原话连同日期一起引用在其所修正的规则中。(b) **在修正发生的同一会话中，将其回写到两个层级**——既修复产物，也修复 Skill 的规则、参考资料或组件；如果修正只作用于产物，那么对未来的每次运行而言都是不可见的，而推迟到“以后”再做的修正通常永远不会真正写入。回写时，应检查 Skill 自身的文本是否曾经*教导*了刚被禁止的反模式——一项修正常常会证伪某条现有指令，而保留原有建议必然导致问题再次出现（真实案例：一个决策页面的约定建议使用跳转式的“转到被引用图示的锚点”；用户恰好禁止了这种做法，因此回写必须修改原有句子，而不能只在旁边添加一条新规则）。当被修正的内容是交互片段时，回写的最后一步是将其提升到组件架——参见步骤 4 中的组件架检查。

这项任务相当重要（我们正试图在这里创造每年数十亿的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，认真反复思考。我建议先写一份修订草稿，然后以全新的视角重新审视并加以改进。请真正竭尽所能地站在用户的角度，理解他们想要什么、需要什么。

对于层级 1，直接应用有明确证据支持的修正；只有当证据确实留下选择空间时才询问。对于层级 2 或层级 3，当用户反馈揭示出有实质意义的设计分岔时，通过 **AskUserQuestion** 提出改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险层级，因为它会改变实现范围；选择 D 则不会。每个选项仅授权其中明确指出的范围或证据变更。除非选项中明确指出，并且通过单独的重型评估/扇出门控，否则它并不授权配对基线、评分器、基准测试、查看器或额外角色。

### 迭代循环

改进 Skill 后：

1. 将改进应用到 Skill
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **Tier 1 默认方案：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配子类型的证据——(a) 精确回读/格式检查，(b) 权威事实及其针对性检查，或 (c) 明确的现有契约及确定性回归。除非另行授权配对计划，否则不要创建迭代工作区。
   - **Tier 2 默认方案：**仅重新运行相同的 1–2 个指定的使用 Skill 示例和针对性检查。除非另行授权配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任何层级单独授权的通用配对运行：**将所有已批准的测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 Skill，基线始终为 `without_skill`；对于现有 Skill，编辑前不可变的原始版本在每次迭代中始终作为保留基线。紧邻的上一次迭代可以作为补充，但绝不能取代原始基线。
3. 在对规则、契约或数字进行实质性更改后，执行纪律 #5。对于单独授权的通用配对运行，还要启动评估审查器，并将 `--previous-workspace` 指向上一次迭代；专用工作流使用其声明的审查器机制。
4. 对于单独授权的通用配对运行，等待用户审查新的查看器结果；否则，除非仍有真正需要用户选择的事项，否则依据默认层级证据作出决定。
5. 阅读新的证据或反馈；如果它们证伪了当前版本，则再次改进，并在同一层级重复此过程。

用户请求的取消或降级在任务剩余期间持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 所有反馈均为空（所有内容看起来都很好）
- 无法再取得有意义的进展

## 高级：盲测比较

当你希望更严格地比较一个 Skill 的两个版本时（例如，用户询问“新版本真的更好吗？”），可以使用盲测比较系统。有关详细信息，请阅读 `agents/comparator.md` 和 `agents/analyzer.md`。其基本思路是：将两个输出交给一个独立代理，而不告诉它哪个对应哪个版本，让它评判质量。然后分析胜出者胜出的原因。

这是可选步骤，需要使用子代理，而且大多数用户都不需要。通常，人工审核循环已经足够。

## 描述优化

SKILL.md 前置元数据中的 description 字段是决定 Claude 是否调用某项技能的主要机制。创建或改进技能后，应主动提出优化描述，以提高触发准确性。

### 第 1 步：生成触发评估查询

创建 20 条评估查询——混合包含应触发和不应触发的查询。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须贴近真实情况，是 Claude Code 或 Claude.ai 用户实际会输入的内容。不要使用抽象请求，而应使用具体、明确且包含足够细节的请求。例如，文件路径、与用户工作或处境相关的个人背景、列名和值、公司名称、URL。可以加入一些背景信息。有些查询可以全小写，或包含缩写、拼写错误或口语化表达。查询长度应有所不同，并重点关注边界情况，而不是让它们显得泾渭分明（用户之后将有机会确认这些查询）。

不佳：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

良好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**查询（8-10 条），要考虑覆盖范围。应针对同一意图采用不同表述——有些正式，有些随意。包括用户未明确说出技能名称或文件类型、但显然需要该技能的情况。加入一些不常见的用例，以及该技能与另一项技能存在竞争但应优先使用该技能的情况。

对于**不应触发**查询（8-10 条），最有价值的是那些非常接近但并不匹配的情况——查询与该技能共享关键词或概念，但实际需要的是其他东西。考虑相邻领域、简单关键词匹配可能会误触发但实际不应触发的模糊表述，以及查询涉及该技能所能完成的某项工作、但在该情境下更适合使用其他工具的情况。

需要避免的关键问题：不要让不应触发的查询明显毫不相关。将“编写一个斐波那契函数”作为 PDF 技能的负面测试太简单了——它测试不出任何东西。负面案例应真正具有迷惑性。

### 第 2 步：与用户一起审核

使用 HTML 模板向用户展示评估集以供审核：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（不要在其外部加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换是否应触发、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中最新的版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期检查其进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示词中的模型 ID（即为当前会话提供支持的模型），以便触发测试与用户的实际体验一致。

运行期间，定期查看输出末尾，向用户提供更新，告知当前进行到哪次迭代以及分数情况。

这会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude，根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每次迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试分数而非训练分数选出，以避免过拟合。

**如果循环检测到完全无响应，则会在第 1 次迭代后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中的代码级防护措施，而不只是建议；它会区分“第 1 次迭代中，每个应触发查询的触发次数均为零”的两种原因：

- `exit_reason: "infra_error: ..."`——某些查询执行（应触发查询或不应触发查询）引发了异常（claude CLI 不在 PATH 中、超时时间太短、网络中断），而不是正常返回“未触发”。该项会被*优先*检查，并且只要错误数非零就会刻意触发，即使数十次运行中仅出现一次不稳定故障也是如此——无论崩溃多么罕见，它都比“什么都没有触发”更具体，也更便于采取行动，而且修复方向是环境，而不是重写描述。消息中的比率（例如 `3/15`）用于判断严重程度：占比较大意味着“停止运行并修复环境”；占比较小，同时又有大量正常的 0 触发运行，则意味着环境中可能存在值得检查的轻微不稳定问题，*并且*描述也可能确实很差——两者都要检查。无论哪种情况，都要检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."`——只有在上面的分支排除了所有执行错误后才会检查，因此这意味着每个应触发查询和不应触发查询都*确实运行了*，但*仍然*一次也没有触发（通过分母为零时的默认值获得的“precision=100%”实际含义就是如此：不是“完美”，而是“没有可供计算的对象”）。该探测实际上什么也没有测量到——在修改描述之前，先排查竞争项冲突或低阈值领域（见下文）。

这两项检查都**仅针对第 1 次迭代运行**，并且**仅在应触发查询的触发次数为零时运行**——第 1 次迭代较弱但并非零触发（例如 9 个查询中有 1 个触发）属于另一种可能可以恢复的情况，因此会刻意让其继续迭代。`degenerate_harness` 还要求不应触发查询的触发次数同样为零：如果描述只是极性反转——遗漏所有正例，同时意外匹配多个负例——那么探测已被证明能够工作，并且 `improve_description` 有真实的梯度可供利用，因此防护措施不会中止这种情况（它只会中止真正失效的探测）。此外，它还要求任一侧的执行错误均为零——引发异常的不应触发查询实际上并未运行，因此其“0 次触发”不能作为探测已失效的证据；这正是该情况会被归入 `infra_error` 的原因。无论哪种情况，循环都会立即中断并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐去任何内容），退出原因则表明不应将这次特定运行的数字解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了完整的 5 次迭代循环；在有人查看数字之前，已经完成了整整两次迭代——每次都是完整的评估批次，耗费数分钟实际时间并调用数十次 `claude -p` 子进程——两次结果都显示 precision=100%/recall=0%/分数相同，而且每个应触发查询和不应触发查询的触发次数全都为零。仅根据第 1 次迭代即可诊断出故障；第 2 次及之后的迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会显示横幅，因此浏览器视图会传递与 JSON/stderr 相同的信号，而不只是通过后两种不太显眼的渠道传递。（该防护措施的早期草案仅检查应触发查询的触发情况；经过两轮独立审查——每轮都由新的代理完成，第二轮检查第一轮的修复，而不是重新覆盖旧内容——构造出了极性反转反例、基础设施与描述之间的歧义、负例侧错误缺口，以及在此过程中暴露的一个既有 `--holdout 0` 报告崩溃问题，所有这些问题都在发布前得到了修复。）

这个保护机制无法覆盖一种情况：当使用 `--runs-per-query 1`（默认值为 3）时，对于一条确实具有约 50% 触发率的应触发查询，完全可能仅仅由于随机性而得到 0/1 的结果，从而因噪声而非失效的探针触发保护机制。默认的 `runs_per_query=3` 正是让“每条正向查询的每次重复运行均为零”成为强烈信号的原因——如果将其调低，这个保护机制产生误报的风险也会随之升高。

**在信任 `best_description` 之前，请先对测试框架进行健全性检查——即使上述两个保护机制均未触发，它仍可能返回空洞无效的输出。** 这两项检查只能捕获第 1 次迭代中的*完全*失败；测试框架也可能在全部 5 次迭代中始终只有微弱但非零的信号，勉强运行下去，却从不触发其中任何一项保护机制。如果第 1 次迭代之后，每次迭代都报告**召回率维持在接近 0%，且分数完全或近乎完全相同**，那么其底层问题与保护机制无法排除的问题相同——所谓“胜出”的描述通常只是在第 1 次迭代的结果附近产生噪声，实质上没有变化。在应用任何 `best_description` 之前，请亲自运行一条显然应该触发的查询，并确认召回率 > 0。如果召回率在多次迭代中始终持平，说明测试框架本身就是一个隐藏变量（常见情况是：该 skill 在触发竞争中输给了已安装的竞争者——参见下文的“共存”）——切勿应用它选出的“最佳”描述；应改为手工编写描述，并使用真实探针进行验证。（方法论案例 12、14）召回率为 0 还有第二种根本原因，它不同于输给竞争者：该 skill 的任务领域属于*低阈值*领域——模型会自行完成任务，从不查阅任何 skill——下文*skill 触发机制*末尾对此有详细说明。在采取措施前，请先区分这两种情况，因为其解决方法截然相反：对于竞争者问题，应通过优先级/取代关系解决；对于低阈值领域，则应完全放弃触发探针，改用生产环境即评测的方式。

**当你亲自使用 `claude -p` 探测触发情况时，请收集该次运行中的所有 skill 调用，而不仅仅是第一次调用——同时请记住，工具调用只是一种代理指标。** `UserPromptSubmit`/`SessionStart` hook 可能会在模型做出选择*之前*注入一个无关的 skill，因此，“在第一次 Skill 调用时退出”的探针会错误地报告“未触发”。此外，“它是否调用了 Skill 工具”并不等同于“该 skill 的内容是否影响了输出”（模型可能读取了该 skill，却没有产生可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你持续基于错误结论进行优化。

### skill 触发机制

理解触发机制有助于设计更好的评测查询。各个 skill 会以名称和描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某个 skill。需要重点了解的是，Claude 只会在遇到自己无法轻松处理的任务时查阅 skill——像“读取这个 PDF”这样简单的单步骤查询，即使与描述完全匹配，也可能不会触发 skill，因为 Claude 可以直接使用基础工具处理它们。当描述匹配时，复杂、多步骤或专业化的查询能够可靠地触发 skill——但存在一个系统性例外（低阈值任务领域），本节末尾将对此进行详细说明。

这意味着，你的评估查询应当足够实质，以便 Claude 确实能从查阅技能中获益。像“读取文件 X”这样的简单查询并不是好的测试用例——无论描述质量如何，它们都不会触发技能。

**但有些技能无法通过此测试，是因为存在一种无论如何改写查询都无法解决的问题——该技能的全部*职责*就是执行低门槛任务。** 上一段将问题归咎于查询（“写一个更实质的查询”）；而这里是与之正交的情况，即阻碍触发的是技能的*领域*。如果某个技能的用途是执行 Claude 仅凭基础工具就会自行完成的操作——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询包含完整细节（“将这个 48k 立体声 wav 降采样为供 whisper 使用的 16k 单声道音频”，并提供路径等所有信息），也不会触发该技能：模型会直接使用 `Bash`/`ffmpeg`，根本不会查阅任何技能。提高查询的实质性无法解决这个问题，因为“我自己就能做”的判断针对的是*任务*，而不是措辞。

在浪费一轮优化之前，先诊断是否存在此问题：通过 `claude -p` 运行一个真实查询，观察模型在整个运行过程中是否*曾经*查阅该技能（遵循上文的“所有技能调用”规则），还是直接使用 `Bash` 自行完成任务。如果它始终没有查阅该技能，那么触发探针在结构上就无法检测到这个技能——无论你如何编写描述，召回率读数都会约为 0，而这个零衡量的是模型倾向于亲自动手的本能，并非你的描述质量。停止针对 `claude -p` 的召回率进行调优，改用真实方式验证：将生产环境用作评估（即用户下一次真实的*交互式*使用——无头模式的 `-p` 比真实会话更偏向直接采取行动，因此会系统性地低估触发情况），并在技能能够生成可检查产物时进行输出对比。（在一个音频预处理技能上观察到：无头模式的 run_eval 扫描对*每个*查询测得的召回率都是 0——其中甚至包括一个显而易见的“转录这段录音”查询——而手动执行 `claude -p` 探测时，可以看到模型直接使用 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个零衡量的是无头模式下的行动偏差，而不是描述质量；真正的信号只会在交互式使用中显现。）

### 第 4 步：应用结果

从 JSON 输出中取出 `best_description`，并更新技能 SKILL.md 的 frontmatter。向用户展示修改前后的内容，并报告分数。

## 关键要求：在源位置编辑技能

**绝不要先编辑已安装的技能副本。** 除非用户明确说明它们是源文件，否则应将以下所有位置视为已安装副本或运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装副本会导致更改：
- 在缓存刷新时丢失
- 无法同步到源代码管理
- 浪费精力，之后还需要手动重新合并

**始终确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，先运行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果 available-skills 列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。先找到由仓库支持的源，对其进行编辑和验证，然后仅在用户需要立即在本地运行时使用时，才同步已安装的副本。

**然后回答一个决定“同步已安装的副本”是否真的需要执行的后续问题：运行时是否已经直接读取源？** 三种安装方式的行为不同，猜错要么会造成无意义的同步，要么会使已发布的编辑无法在用户的下一个会话中生效：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **通过符号链接**链接到源代码树中 → 编辑内容*本身就是*运行时内容。无需同步。
- **具有 `source: directory` 的 Marketplace** 指向仓库 → 情况相同：它会直接读取工作树，因此版本号递增只是为其他使用者保留的记录，而不是本地激活步骤。
- **任何经过缓存或复制的安装**（源自 git 的 Marketplace、通过 `cp -r` 安装）→ 运行时使用的是独立副本，确实需要先执行官方更新命令，新内容才会生效。

**此外，应通过内容而非版本字符串来验证激活情况。** 注册表可能记录一个磁盘上并不存在的路径或版本——某次会话读取到一条插件记录，其中指定了一个名称含有*新*版本号的缓存目录，差点就报告更新已经生效；然而该目录从未被创建，而真正的运行时路径一直是指向源的符号链接。权威的检查方式是，在运行时文件中搜索只有新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库中的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是这些会话容易发生冲突的地方：当你编辑技能 A 时，另一个同级会话可能会在你操作期间提交技能 B（甚至是技能 A 的更早一轮修改）。某次真实会话在一小时内遇到了全部三种症状——由于文件在读取后发生变化而导致 `Write` 被拒绝，以及任务进行期间 HEAD 两次移动（方法论案例 16）。问题并不在于冲突本身，而在于使用了过期的基线，或进行了覆盖式写入，从而悄无声息地混合了两个会话的工作。长期适用的规则如下：

1. 当任务开始时仓库是干净的，**应始终从 git ref 创建基线，而不是从工作树创建**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传递 `--baseline-origin git-ref:<sha>`。在其他人的提交发生前几分钟创建的工作树快照，是针对一个已不存在的工作树的基线。**请将其解压到一个全新且不存在的目录中。** 如果解压到现有目录，`tar -x` 会悄无声息地覆盖同名文件，同时保留归档中不存在的文件——由此形成一个混合快照，解压时不会发出任何信号，但 `compare` 随后会因其与该 ref 不匹配而拒绝它。另一个命令也有同样的陷阱：`mv <dir> <existing-dir>` 会进行嵌套，而不是替换——如果 `mv` 被设置为 `mv -i` 的别名，在目标已存在时，重命名操作会输出一行提示并默认*不执行*，而无论是否执行，退出码都是 0（已通过实验验证）。
2. 当写入被拒绝，或经过了一段时间后，**请在写入前重新读取**：对发生的变化进行差异检查（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图融入你的版本——对方的编辑通常有其原因——然后再执行写入。
3. **提交前检查 HEAD *以及当前所在的分支***。`git log --oneline -1` 能发现 SHA 已移动：如果它自你的基线创建后发生了移动，请先针对新的 ref 重新运行回归 `compare`，然后再执行 `verify`——无论如何，审计工具都会以基于过期评审为由拒绝它（“after skill changed”），因此自行提前发现可以省去一轮操作。但另一个同级会话可能做出比推进 HEAD 更严重的事情：**它可能在你操作期间切换分支**，因为 checkout 会影响整个工作树。真实发生过的操作顺序是：执行 `checkout -b feat/x`，编辑了一段时间，与此同时另一个会话运行了 `checkout main` + `pull`；随后提交落在了 **main** 上，违反了仓库“绝不直接提交到本地 main”的规则，而功能分支仍指向旧的基点。因此，请将 `git branch --show-current` 加入提交前检查，而不仅仅是检查 SHA。如果这种情况已经发生，`git reflog` 是权威的重建依据（它会按顺序记录每次 `checkout: moving from X to Y`），而修复方式——**前提是工作树干净**——是先执行 `git checkout -B <feature> <your-sha>`，再执行 `git branch -f main origin/main`：这两个操作都只移动 ref，完全不会触碰工作树，因此不会像 `reset --hard` 那样破坏并行会话中未提交的工作。
4. **仅暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——不能让另一个会话未提交的工作混入你的提交中。（这本就是打包规则；在并发场景下更是双重关键保障。）
5. **每个会话结果只递增一次版本号**，而不是每轮编辑都递增：同一会话中对一个技能连续进行的多轮编辑应合并为一次版本递增——除非某个中间状态已经被使用（已提交，并由用户或另一个会话拉取），在这种情况下，每个已被使用的状态都应拥有各自的版本。

## Skill 创建流程（分步说明）

创建或更新 Skill 时，请按顺序执行以下步骤。只有在明确不适用时才能跳过步骤。

### 第 0 步：检查先决条件

在开始任何 Skill 相关工作之前，自动检测所有依赖项，并主动安装任何缺失的依赖项。在工作流程进行到一半时才发现缺少工具（例如，在打包时发现缺少 gitleaks，或在验证时发现缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，自动安装可以安装的依赖项，并向用户提供一份检查清单摘要。只有在满足所有阻塞性依赖项后才能继续。

关键的阻塞性依赖项包括：Python 3、uv、PyYAML（验证/打包）和 gitleaks（安全扫描）。只有当另行授权的证据计划实际运行智能体评估时，claude CLI 才是阻塞性依赖项。运行 Python 工具时，应显式声明 uv 依赖项，例如从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 依赖环境中的站点包，因此可能无法找到 PyYAML。

### 第 1 步：通过具体示例理解 Skill

只有在已经明确理解该 Skill 的使用模式时，才能跳过此步骤。

要创建有效的 Skill，需要清楚理解该 Skill 将如何使用的具体示例。这种理解可以来自用户直接提供的示例，也可以来自生成后经用户反馈验证的示例。

例如，在构建图像编辑器 Skill 时，相关问题包括：

- “图像编辑器 Skill 应支持哪些功能？编辑、旋转，还有其他功能吗？”
- “你能提供一些此 Skill 的使用示例吗？”
- “用户会说什么来触发此 Skill？”

为避免让用户感到不知所措，请勿在一条消息中询问过多问题。

### 第 2 步：规划可复用的 Skill 内容

通过以下方式分析每个示例：

1. 考虑如何从头开始执行该示例
2. 确定应赋予 Claude 的适当自由度
3. 确定在重复执行这些工作流程时，哪些脚本、参考资料和资源会有所帮助

**根据任务风险匹配具体程度：**
- **高自由度（文本说明）**：存在多种有效方法
- **中自由度（带参数的伪代码）**：存在首选模式，同时允许适当变化
- **低自由度（精确脚本）**：操作容易出错，一致性至关重要

### 第 3 步：初始化 Skill

如果 Skill 已存在，请跳过此步骤。

从头创建新 Skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个包含正确 frontmatter、资源目录和示例文件的 Skill 模板目录。

### 第 4 步：编辑 Skill

在编写之前，请获取 Anthropic 的最佳实践文档（链接位于上方的“Skill Creation Best Practice”中）和方法论参考资料——即使你认为自己已经了解这些内容，也要这样做：文档会更新，训练数据中的版本会过时，而“我基本上知道”恰恰是编辑者会跳过这一步并错过最新指导的状态。

编辑时，请记住，该技能是为另一个 Claude 实例创建的。应重点提供对 Claude 有帮助且并非显而易见的信息。

**现有技能迁移门禁——首次编辑前必须完成：**

1. 编辑前捕获当前完整的技能包。对于未使用 Git 或工作区不干净的
   源，请使用该工具，以便快照包含可验证的来源清单：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于由 Git 跟踪且工作区干净的源，请从选定的引用中实例化该目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   应包含 SKILL.md、references、scripts、assets、workflows 和现有 evals，而不
   只是主提示词。绝不要复制已经编辑过的目录树并将其标记为“before”。
   **请使用一个此前从未解压过任何内容的目录**——复用一个已经包含之前运行
   所留内容的目录，会使 `tar -x` 静默覆盖同名文件，同时保留新归档中不存在的
   陈旧文件，从而生成一个在解压时没有任何信号提示的混合快照（`compare` 只会
   在之后以间接方式通过目录树哈希不匹配捕获该问题）。关于这一陷阱的更完整说明，
   包括基于 `mv` 的变体，请参阅下文的“同一技能仓库上的并发会话”。
2. 盘点旧技能的参与者/任务、触发上下文、运行时契约、命令/标志、失败与恢复情况、
   页面/域变体、捆绑资源以及 eval 覆盖范围。在进行结构性重写之前，为重要的旧有
   边缘行为添加保留用例。
3. 编辑后，生成一份新旧版本对比审查：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，请将最后一个标志替换为
   `--baseline-origin git-ref:<ref>`。该工具会将引用解析为不可变提交，并根据该目录树
   验证所有包含的文件和可执行位。

   **重命名或移动技能目录本身**（而不只是编辑其内容）会改变 `--after` 的路径，
   而两种基线模式都会使用该路径进行身份识别——默认情况下，`compare` 会拒绝这种
   情况（假定 `--before`/`--after` 是因误操作而不匹配），并报出
   `pre-edit snapshot source identity does not match the edited skill`。添加
   `--renamed-from <old-path>`（即执行 `snapshot` 时 `--source` 指向的路径，或者
   对于 `git-ref:`，技能相对于其仓库根目录的旧路径）以显式声明重命名；随后身份
   检查会验证该路径而不是 `--after`，同时内容/目录树哈希检查不受影响，因此真正
   不匹配的配对仍然会失败。**请为 `--renamed-from` 传入绝对路径。** 此命令接收的
   每个路径如果以相对路径给出，都会相对于当前工作目录解析——而不是相对于
   `--after`，路径之间也不会相互作为解析基准——并且 `--renamed-from` 通常指向一个
   已不存在的目录（它已被重命名移走），因此不会像 `--before`/`--after` 那样通过
   存在性检查来捕获错误的路径解析；它只会在更深层的位置以令人困惑的方式失败。
   这一问题尤其容易影响对 skill-creator 本身的编辑：上面的
   `cd <skill-creator-path>` 进入的是 skill-creator 自己的仓库，而该仓库通常与
   正在审计的技能所属仓库是*不同的*仓库，因此相对路径形式的 `--renamed-from`
   会悄无声息地相对于错误的仓库进行解析。

4. 审查每个候选项。必须且只能使用一种处置方式，并记录具体的
   证据/理由：`preserved_or_moved`、`intentional_sanitization`、
   `intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable`
   或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将某项
   运行时能力移出此 Skill 时，必须提供负责接收该能力的目标位置、当前的
   边界证据以及可追溯的用户批准。明确停用时也必须
   引用或追溯用户的批准。关于保留、净化或修复的声明必须指向
   当前真实存在的文件和行，并包含一小段 `contains` 引文，以便
   验证程序能在附近找到。文件级候选项使用当前文件的
   指纹，并附上具名的语义审查来说明行为为何得以保留——
   仅凭指纹只能证明文件身份，不能证明能力得到保留。

   不要手动编辑审查 JSON，也不要每轮都重写相同的填充脚本——
   `classify` 子命令会处理机械性工作（在目标文件中定位引文所在行、
   填充证据/语义审查，并在引文缺失或理由过短时快速失败）。
   你仍需自行撰写每项处置方式和理由；它只负责将这些内容录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置方式默认为
   `preserved_or_moved`；文件级候选项只需提供目标位置和至少 40 个
   字符的理由——指纹会自动为你计算）。**务必从目标文件中复制 needle
   （使用 Read/grep/sed），绝不要凭记忆输入**——查找采用精确匹配，
   缺失引文时会快速失败，而手动输入的 needle 实际会因两种情况失败：
   全角与半角标点不一致（`：` 与 `:`），以及根据记忆改写成近义字符
   （`也` 与 `都`）——这两种问题都无法通过自我审查发现，只会在工具拒绝
   整份映射时暴露（曾有一份映射恰好因为这两个原因连续两次被拒绝）。
5. 验证已完成的审查。任何后续编辑都会因哈希变化而使审查失效，
   因此候选项发生变化时，请重新生成并重新分类。验证通过后会写入
   `.skill-regression-reviewed`，这是一个与内容绑定的本地状态收据。
   它有助于检测后续编辑，但被刻意设计为不能单独作为打包授权；
   打包过程会自行重新验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可识别无提示失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在需要审查的候选项，并不表示工具运行失败；返回 2 表示调用/运行时失败。该工具能够证明内容的精确迁移和接口保留情况，但会刻意拒绝根据模糊的词语重合推断语义等价性。像“检查权限被拒绝”这样的通用表述，不能悄无声息地取代“已登录但不具备相应角色”这种精确约定。还要检查标记为 `only_outside_runtime` 的候选项：如果运行时行为仅存在于评估、测试或不可达的引用中，那么正常调用路径中并不存在该行为。

**每次编辑 SKILL.md 后都要立即验证——不要等到打包时（第 7 步）。** 这能及早捕获一个真实的故障：将 frontmatter 描述写成未加引号的 YAML 标量时，Claude Code 的宽松解析器可以正常解析，但严格解析器会失败（codex 在一个已发布数月的技能上报告了 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中出现 ` #` 时甚至不会报错——它会悄无声息地截断其后的全部内容，导致触发关键词消失，而所有扫描仍显示正常。

cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**当描述包含 `: ` 或 ` #`，或者跨越多个句子时，请将其写成 YAML 块标量**（`description: >-` 后跟一个缩进段落）——块标量原生支持这两种字符——这是自上述事故发生以来，所有新增或编辑描述所采用的推荐约定。

**更新现有技能时**：扫描所有现有引用和捆绑资源，进行相应更新，然后通过上述迁移门禁。迁移一项约定时，必须在 SKILL.md 中提供直接的运行时指针；评估或变更日志不能作为替代。

接下来的三项检查是**升级探测，而不是无条件扩大范围**。如果执行其中任何一项会新增或实质性改变某项能力、工作流分支、输出约定、脚本行为、依赖项、权限或外部写入，请在修改技能之前停止操作并重新归类为第 3 级。第 1 级和第 2 级可以检查这些问题，但不能因此新增交付物。

**脚本检查**：在宣布编辑完成之前，先问一问：*源对话（或评估记录）编写了哪些代码，而这些代码原本会在未来的每次调用中被重新编写？* 如果所选级别已经授权开展该能力相关工作，就将其捆绑到 `scripts/` 中（参数化并经过净化处理），并修改文档以指向该脚本。否则，将该信号记录为第 3 级提案，不要将其作为第 1/2 级工作的附带结果进行捆绑。两者的职责分工是：**脚本负责执行，文档负责传达理解**——如果一个技能的方法只存在于文字说明中，那么每次运行时都要重新付出完整的编写成本。这项检查之所以放在这里，即编辑步骤中，正是因为跳过评估循环的路径（对话提炼、直接编辑）永远不会触及“改进技能”中针对评估记录的这一检查版本。

**组件货架检查（针对制品内嵌片段提出的同一个问题）**：脚本检查覆盖的是*技能*所执行的代码；生成制品的技能（报告页面、演示文稿、文档）也会逐渐积累由其*输出*嵌入的片段——图像叠加层组件、吸顶导航、图表配置、CSS 块。如果连续生成的输出都手写了相似的片段，这就是同一种重复信号，只不过指向了不同的货架。在添加 `components` 子文件夹或注册表引用之前，应先应用上文的升级规则；Tier 1/2 可以提出该建议，但不得创建组件能力。当 Tier 3 获得授权后，真正让代码片段成为货架组件的是围绕它建立的契约：(a) **逐字嵌入块**——由 BEGIN/END 标记界定，完整复制到制品中，不含任何依赖，从而让单文件制品保持自包含；(b) **注册表条目**，说明交互契约（触发方式、按键绑定、关闭行为、边界情况）及来源——它出自哪个已交付制品，以及用户何时批准了它；(c) **准入门槛**——只有用户实际使用并批准过的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但外观精美的片段仍不得纳入）；(d) **行为冻结，外观可调**——校准后的行为和按键绑定属于契约，不得在不同运行之间漂移，而颜色和尺寸可以遵循制品的风格基调；(e) **回写闭环**——为某个制品创造的片段，应在其获批的同一会话中晋升到货架。其重要性不只体现在节省 token：手工重写的片段会发生*漂移*——每次重写都会细微地改变按键绑定、关闭行为和计数器——而对于每天阅读这些制品的用户来说，交互一致性就是产品体验。用用户在建立第一个此类货架时的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：某个报告页面技能的灯箱画廊组件（图像叠加层：←/→ 在组内循环切换，ESC 关闭，原位缩放，n/N 计数器），以及它对交互组件注册表的引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击遍历测试完成验证。参见方法论案例 17。

**流水线检查**：考虑该技能的输出是否会自然地流入另一个技能，以及现有技能是否应该通过链式调用进入该技能。在编辑之前，新增或实质性更改“下一步”交接或流水线契约，需要重新归类为 Tier 3；Tier 1/2 可以提出该建议，但不得顺手添加。

**引用与自应用检查（那些能逃过谨慎作者的缺陷）**：这是一组从内部看来都像是已完成工作的失败模式，而且没有一种能通过更仔细地重读被发现——每一种都需要采取*机械化*操作。（开头特意没有写数量。“三种失败模式：”是一个派生数字，一旦有人追加项目符号，它就会立即过时；而计数类正文恰恰是最难发现的漂移，因为它*不包含发生变化的事物*——对编号执行 grep，以及查看列表本身的 diff，都会直接漏过它。）之所以将它们归为一组，是因为它们有着共同的原因：**写下断言和验证断言是两种不同的模式，而单次检查无法同时兼顾二者。** 当你正在撰写时，“参见规则 8”*本身就是*所作出的声明；你并不会同时打开规则 8。

与上面的三个升级探针不同，这一项**不**按层级限定范围——它的范围取决于你写了什么。如果某个 Tier 1 修复既没有添加指引，也没有添加规范性规则，那么这里就没有它要做的事，而且你不必自行判断：推论中的脚本会在几秒内给出答案，报告 `NONE prose-reference-shaped`。无论在哪个层级，只要写了指引或规则？那么下面这些条目就适用。

- **你写下的每个指引，都要在写之前打开其目标，并从中复制一行。** 不要只是说“我确信那条规则列出了全部三个标记”：请粘贴其中的一个片段——放进你在这一步原本就在产出的任何内容里（审查备注、提交消息正文、你的回复），置于第二位读者之后能够对照目标进行检查的位置。一个你只是看过、却没有复制出来的片段，正是本句开头所拒绝的自我评估。错误的交叉引用在重新阅读时是不可见的，因为错误指引看起来与正确指引完全一样，而作者恰恰是唯一一个必然会“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal 规则 3”，本意是指一条关于不要引用过时枚举的规则——但被引用文档*自身*的规则 3 讨论的是样本量，而实际引用的规则位于另一个文件中；读者如果遵循该文档既定的自引用惯例，就会落到一个无关主题上。同一轮编辑还发布了一个方向颠倒的指引（材料在上方，却写成“参见下文”），以及一个指向不存在章节标题的指引。
- **只写“规则 N”，那么只要文件中出现两个编号列表，它就会产生歧义。** 检查应针对每个指引，而不是每个文件：在写下“规则 N”之前，运行 `grep -n '^N\. ' <file>`，并确认你所指的章节中恰好只有一个匹配项；如果有多个匹配项，也要写出章节名称。（**不要**把它变成“此文件是否包含多个从 1 开始的列表”之类的文件级警报——对于任何长文档，这几乎总是成立，因此它会在正常输入上触发并最终被忽略，而纪律 #6 警告说，这比完全不检查更糟；请在这个文件上运行它，亲自验证。）在真实案例中，一个只写了“规则 1”的指引有三个候选列表，而自上而下的搜索首先命中了错误的那个。
- **写下任何规范性规则后，都要对照其相邻行检查它——并让检查产出工件，而不是结论。** 使用 `git diff <base-ref> -- <file>` 阅读你自己的变更块，并采用与下方推论相同的 `<base-ref>`。这里自行阅读就足够了——你并不是在对它进行模式匹配，因此不需要脚本——但命令必须带上该引用：不带参数的 `git diff` 只显示未暂存的工作，一旦执行 `git add` 就会什么也不输出，而这正是本块自己的推论旨在规避的五种静默空输出模式之一。将新规则拆分成各个独立子句，并针对每个子句，写下*同一变更块中*满足它的那一行。（下方推论中的 `scripts/reference_net.sh` 执行的是另一项工作：它会列出*正文交叉引用*，供你逐一解析。它不会把变更块交给你，也不会告诉你规则中的某个子句是否得到了满足。）**找不到相邻行与之对应的子句，就是发现的问题。** 诱人的简化版本——“我的新规则通过了吗？”——对于 30 秒前刚写下这条规则的人而言不可能得出否定答案；这恰恰就是纪律 #6 所说的，应优先采用可证伪的观察，而不是自我评估，因此本条也必须产出它所要求的同一种工件。它的第一个受害者通常就是旁边的段落。真实案例：新增了一条规则，规定“始终同时报告原始计数和过滤后计数——二者之差*就是*污染量”，但同一提交中它自己的完整示例只输出了过滤后的数字。同一变更中的另一项陈述引用了两个数字，却没有说明它们是否是在相邻的新规则刚刚规定为强制条件的限定条件下收集的。范围很小且有边界：不是“重新阅读整篇文档”，而只是“我 30 秒前写下的规则，能否在我 30 秒前写下的那些行上通过”。
- **为每条新规则添加一行，说明由谁执行，以及他们实际上是否有能力执行。** 如果现有工具无法满足某条规则，那么相信自己已经遵守规则的人就会跳过它——这是最糟糕的一类规则，因为它会制造有文档背书的虚假信心。真实案例：一条新规则规定“检查两个日志存储”；而项目自身的规范单命令分诊工具硬编码了其中一个，因此标准工作流恰恰会对这条规则原本要捕获的故障返回干净结果。这条规则是正确的，却不起作用，而且没有提及这一缺口。**使其可证伪的工件是**（如果没有它，本条就会成为这个禁止自我评估的块中唯一一项自我评估）：指出能够捕获违规情况的工具或命令，然后**针对一个你已经知道它应当捕获的案例运行一次**。如果它在已知有问题的输入上返回干净结果，你就已经测量出这条规则不起作用——请将这一缺口写进规则本身。凭记忆回答“他们实际上是否有能力执行”，正是纪律 #6 所拒绝的未经验证的断言。**如果没有任何工具能够判定该规则**——大多数正文和风格判断规则确实如此，因此不要把这当成逃脱途径——相应的工件就是明确说明这一点的句子：*“没有任何机制强制执行这一点；它只能在人们还记得它时成立。”* 这比检查通过的处境更糟，而明确说出这一点正是目的所在；执行机制保持沉默的规则会被想当然地认为得到了遵守，而不是经过验证。请注意本条自身坦诚承认的局限：工具和已知有问题案例的选择仍然需要判断，因此它只是转移了未经验证的步骤，而没有消除它——它比替代方案成本更低，但并非毫无成本。
- **推论——你的修复本身也是缺陷来源，因此在最后一次编辑之后，要重新检查你触及的区域。** 在对单个变更进行的两轮审查中，第 1 轮发现了八个问题；第 2 轮又发现了八个问题，**其中七个是第 1 轮修复所引入的交叉引用错误**。重写一个句子会移动它周围的锚点。这也解释了为什么，对于依靠指引进行导航的工件而言，“它已经审查过了”并不是终点：你一旦根据审查结果采取行动，审查本身就过时了。重新检查是机械性的，而且它是一个**脚本**，不是需要重新输入的命令：`scripts/reference_net.sh <base-ref> <file>…`（包含在此 skill 的捆绑包中）。它会列出你所添加行中的正文交叉引用，以便你打开每个目标并确认其内容确实与你的声称一致。首次使用前请阅读其文件头——其中解释了为什么它接收基础引用，而不是默认使用 `HEAD`，以及它刻意*不*做哪些事情。

**在开始编辑之前获取 `<base-ref>`，而不是之后。** 在开始时将它一次性解析为字面量 SHA——`BASE=$(git rev-parse HEAD)`——并在这里和上一个项目符号中复用同一个值。如果你运行了现有 Skill 迁移门禁，它就是你已经用作基线的 ref。稍后传入 `HEAD` 是一个陷阱：提交之后，`HEAD` 包含了你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容可供检查无法区分。如果你没有预先捕获它，请恢复它（使用 `git log`、`git reflog`，或你提供给迁移门禁的基线），而不要用 `HEAD` 代替；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印一条说明，但不要指望到那时才发现问题。

**为什么这里要使用脚本，而此块的其余内容都是说明文字。** 它所取代的那条单行命令经历了五轮修补——将 diff 锚定到正确的基线、查看暂存的编辑、确保提交后仍能工作、跳过 diff 自己的 `+++` 标头、移除会产生误导的 `-n`——其中前四轮都让它又多了一种什么也不打印并以 0 退出的方式，而这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种病症的另一种表现：被移除的 `-n` 此前会打印真正的命中项，但行号是按管道输入流计算的，因此它们看起来很权威，却指向不了任何地方——这比沉默更糟，因为错误答案比没有答案影响更大。无论哪种情况，这项检查都会继续放过它本来用于捕获的缺陷。说明文字无法验证自己的输入，无法说明出现了哪一种结果，也无法接受测试；脚本能做到这三点，并且它的契约是：**每一种结果都有明确名称，而错误输入会响亮地失败**。这就是本步骤前面的脚本检查在此块中的应用——而忽视它的代价正是那五轮修补。

**读取它的判定结果，而不只是退出码。** 只要脚本完成了运行，就会以 0 退出，因此仅凭 `$?` 无法得知它发现了什么；答案在判定结果行中，而且它始终会明确指出以下结果之一：发现引用（逐一处理）、文件与基线相同、文件已更改但没有新增行，或存在新增行但没有任何类似引用的内容。这些是不同的结果，脚本有意让它们保持区别——这个检查曾经有一个版本把它们全部折叠成一个无声的“什么也没有”，这正是它后来变成脚本的原因。它只耗费几秒，而且不依赖警觉性，这正是准则 #6 对任何值得编写的检查提出的要求。（它是一张安全网，而不是证明。它的盲点是不含数字的指引——“参见下面的章节”“如上面的规则所述”——因此也要阅读新增的行。）

### 步骤 5：净化审查（任何公开 Skill 都必须执行）

**在进入此门禁之前，当准则 #5 适用时，其独立检查必须已经运行**，并且当前变更的 `independent-review.md`（位于你私有且由 git 跟踪的知识仓库中——不是已清空的工作区，也不是任何已经或可能公开或分发的仓库）必须存在，**并且已经提交**。对于新 Skill，它始终适用；对于现有 Skill，请使用下一段中的阈值。文件仅仅以未提交状态存在于 git 工作目录中，与从未写入该文件并没有实质区别；`ls`/`test -f` 只能确认它存在于磁盘上，不能确认它能够保留下来。对于**新的** Skill，这是第一次有任何内容离开你的掌控，因此也正是在这里，该准则才真正得到执行，而不只是被陈述——如果一条规则位于实际使用点上方 1000 行处，又没有任何机制检查它，那么它每次都会败给完成任务的冲动。

**对于已发布技能的编辑，真正脱离你掌控的时刻是推送，而不是这一步。** 对这个门禁，只需用一句话回答“仅限内部，跳过”即可，而且如果只是文档变更，打包流程甚至可能根本不会运行——因此，把审查锚定在这里，意味着技能编辑可能在未经任何独立复核的情况下进入公开分支。真实案例（2026-07）：对这个文件本身的一次修改发布了一条发现命令，但它无法访问旁边正文声称会覆盖的三个根目录；该修改被合并了，直到*事后*专门安排审查才发现问题。**因此，对于现有技能：必须在 `git push` / 创建 PR 之前完成独立复核并留下记录产物——推送时运行的门禁（回归审计、验证、扫描）都只检查结构，没有一个能判断说明本身是否错误。** 这里原样沿用准则 #5 的门槛：当*规则、契约或数字发生变化*时必须执行，而拼写错误或纯格式调整则不需要。让拼写修正也必须等待一轮审查，只会培养出准则 #6 所警告的那种思维惯性——“这次改动很小”会变成通用豁免，最终连真正重要的改动也会被它放过。

**对于将进入公开仓库的技能，这一步不是可选项。** 私密内容一直都会泄漏到公开技能中，而扫描器漏掉的泄漏才最危险——非英语语言中的真实姓名、真实对话记录中逐字照搬的一句话、插图中放入的真实示例。仅当技能确实只供内部使用时才可跳过。

**按发布目的地而非主题来界定检查范围。** 只有将公开发布的产物——技能包本身——需要进行脱敏。保留在私有仓库中的配套文档（提炼出该技能的事件报告、内部运行手册、项目的 CLAUDE.md）应保留其真实主机名、路径和时间戳：对这些内容进行脱敏会破坏其审计价值，而且你最终还得撤销这些改动。曾有一次提炼工作经历了三轮返工，原因正是脱敏流程被应用到了源材料涉及的所有内容，而不是仅应用于公开技能。

**先检查目的地，并让检查结果预先填充建议。** 在技能将要存放的仓库中运行
`gh repo view --json isPrivate`（或查看 `quick_validate` 已打印的提示）。如果目的地是私有仓库，应默认推荐选项 C，而不是事后才想到它——“除非另有说明，否则假定为公开”
正是导致私有技能中的工作路径被替换成无人要求的占位符的原因。

**触发脱敏的条件是目的地的 `isPrivate`，而不是这项任务在多大程度上
让人感觉像是在发布。** 两者并不总是一致，而一旦不一致，除非你明确指出，否则感觉就会占上风。将内容移入*市场技能*感觉上就像在发布——市场正是内容进行分发的地方——因此，即使源仓库和目标仓库都是私有仓库、任何内容都不会公开，脱敏的本能反应依然会被触发。真实案例
（2026-07）：一次从项目级技能到私有市场技能的迁移，把真实配置路径、真实十六进制值和真实具名示例都泛化成了占位符。`quick_validate` 在**每次**运行时都打印了 `🔒 audience: private`；
作者每次都看到了，却仍然进行了脱敏，因为这项*活动*本身看起来像是在发布。其代价并不只是表面上的——真实路径能让下一位读者前往检查该值；而“项目自身的令牌文件”根本无法打开。

因此，要把它当作一次查找，而不是一次判断：**读取目标位置的 `isPrivate`，如果它为
`true`，则只有所有者提出要求时才进行脱敏。** 从私有位置移至私有位置只是
移动，并非发布。**当两个探测都没有结果时**（尚无远程仓库、尚未运行 `quick_validate`），
你就没有可供查找的信息——回退为按公开处理，*并明确说明这一点*，因为
这种不对称性决定了应当如此：一个不必要的问题只多花一句话，而一次不必要的泄露
却无法挽回。此外，`isPrivate` 报告的是目标位置**当前**的状态——一个
位于私有仓库中、正准备发布的 Skill，会在真正将其公开的那次推送中执行脱敏，
而不是这一次。如果你发现自己正在推理某些内容在私有目标位置中是否“应该”
被泛化，这种推理本身就是警示信号。

使用 **AskUserQuestion** 确认脱敏深度（对于公开目标位置，确认脱敏深度，
而不是是否进行脱敏；对于私有目标位置，确认是否确实需要脱敏）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**脱敏流程——通读是主要方法，扫描只是辅助工具：**

1. **亲自阅读整个 Skill 并从语义上进行判断**（这才是真正的检查）：SKILL.md + 每一份参考资料 + 每一个示例。对于每个具体名词 / 示例 / 代码片段，都要问：“这是通用占位符或公开实体，还是取自真实项目 / 个人 / 对话记录？”替换后者——即使没有任何扫描器将其标记出来。这是唯一能够捕获无关键词泄露的方法。完整指导和语义判断问题请参阅 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器，作为低成本的第一轮检查**：检查清单中的 grep 模式 + `security_scan.py`（步骤 6）。它们能快速发现明显的密钥 / 路径 / 已知名称——但“无匹配项”并不代表通过检查。
3. **替换**每一处发现的问题，使用能够保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。有两条来自惨痛经验的规则：占位符本身不得包含真实值——`<acme-corp-domain>` 恰恰泄露了它原本应该隐藏的名称；应改为描述其*角色*（`<api-domain>`、`<upstream-provider>`）。此外，当你编写脚本进行批量替换时，要为它提供一个明确的文件白名单，并将范围限定在 Skill 目录内——不受范围约束的查找和替换会毫不犹豫地改写项目自身的 CLAUDE.md，迫使你使用 git restore 恢复。
4. **通过重新阅读来验证，而不是重新运行 grep**：重新阅读修改过的部分，并确认没有失效的引用。

### 步骤 6：安全审查

在打包或分发 Skill 之前，运行安全扫描器以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测范围：**
- 通过 gitleaks 检测硬编码密钥（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）
- 完整的软件包超集：常规发布文件，以及可选的根目录 `evals/`。非发布内容 `.enrich/`、`tests/` 和 `dist/` 会依据打包器和内容哈希认证所使用的同一套共享策略予以排除。

**未涵盖的内容**——这就是为什么仍然必须执行第 5 步的通读：gitleaks 和正则表达式规则只能匹配*已知的密钥格式和你列出的模式*。对于不含关键词的私密内容，它们在结构上无能为力——例如以非英语语言书写的真实人物或项目名称、真实对话记录中的原句、直接取自你自己工作的真实示例。`security_scan` 显示绿色意味着“未发现已知格式的密钥”，**并不**意味着“该 Skill 已完成敏感信息清理”。绝不要将其视为后者。

**首次设置：**如果尚未安装 gitleaks，请进行安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 无问题（可以安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**在私有 Skill 中，扫描发现是信息，而不是工作指令。** 扫描器无法
区分泄露的凭据与*本来就应该存在*的凭据——例如其全部价值就在于预先填好内容的模板，或指向其唯一运行机器的脚本。
绝不要在私有仓库中自动修复：报告发现的内容，并让所有者做出选择。下面的选项 A
（“自动修复”）适用于将要公开发布的 Skill。

**如果发现问题**，请通过 **AskUserQuestion** 向用户展示：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包 Skill

Skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个已由 Git 跟踪的现有 Skill，在提供并重新验证已完成的
审查之前，都会阻止打包。当前标记只是本地状态回执，
因此先提交或手动编写标记都无法绕过审查。下一次编辑后，
该审查便会失效：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可以选择指定输出目录，并使用 `--include-evals` 将根目录 `evals/` 一并发布（默认情况下，它作为开发资产被排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. 自动**验证**技能（YAML frontmatter、命名约定、路径引用完整性）
2. 每当 Git HEAD 已包含该技能时，**重新验证已完成的现有技能回归审查**；仅有标记绝不能授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描一致）
4. 将技能**打包**为可分发的归档文件

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 步骤 8：更新 Marketplace

打包后，更新 Marketplace 注册表，使其包含新增或更新后的技能。

**对于新技能**，在 `.claude-plugin/marketplace.json` 中添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于更新后的技能**，按照 semver 递增 `plugins[].version` 中的版本号。对技能文件的任何更改——即使只是修正一行中的拼写错误——都需要递增版本号：否则，`marketplace update` 看不到新版本，因此**已安装的副本永远不会刷新**，用户会继续运行旧技能，而你的修复则一直未发布。

**然后将其记录到变更日志中——这一步最容易被跳过。** 版本递增使更新变得*可安装*；而变更日志条目则使它在六个月后仍然*可查找*，届时如果有人遇到相同的问题，就可以通过 grep 找到它。而一份记录了其他所有技能版本、却唯独悄无声息地漏掉你的技能的变更日志，比完全没有变更日志更糟：这些空缺会被理解为“那里没有任何变化”。

应匹配现有条目的格式，而不是自行创造一种——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。
应在递增版本号的**同一个提交**中写入该条目；声称“稍后”更新的变更日志，最终永远不会得到更新。

真实案例（2026-08）：某个技能连续发布了两个版本，两次都正确递增了版本号、通过了所有门禁检查，并合并了 PR——但**完全没有变更日志条目**，因为本流程中没有任何步骤要求添加。直到后来的一次审计才发现这两次遗漏。这正是将纪律 #6 应用于本文件自身：如果一条规则只存在于约定中，而没有落实到具体步骤里，那么它每次都会败给完成任务的冲动。

**尽量减少注册表的 diff——这是所有技能共享的唯一文件。** Marketplace 清单是所有并发编辑者都会发生冲突的地方，因此，在这里进行无关的格式更改，其代价远高于在其他任何地方做同样的更改：它会让其他正在编辑的人原本干净的三行版本递增变成一次冲突。当你编写脚本来更新它时（解析为 JSON、修改、写回），重写过程可能会悄无声息地规范化该文件原本未采用的内容——末尾换行符、缩进宽度、键顺序、Unicode 转义。往返处理原则：之后重新读取该文件，并对其运行 `git diff --stat`；**其中唯一可以出现的行，必须是你原本打算更改的字段。** 如果出现额外的行，应恢复该文件原有的约定，而不是将规范化结果一并发布（某个自动递增版本号的脚本曾经给一个从未包含末尾换行符的清单添加了末尾换行符——在最有可能同时被其他人编辑的文件中，白白增加了一行 diff）。同样的原则也适用于技能涉及的任何共享注册表：锁文件、目录、索引文档。

**当一个 PR 经历了几次合并后仍未关闭，就进行变基——然后证明你没有吞掉任何人的工作。** 清单之所以容易成为冲突热点，也正是它容易过时的原因：只要有其他内容落入主分支，一个同时修改注册表和变更日志的开放 PR 就会发生冲突，因此应当预期看到 `mergeable: CONFLICTING`，而不是将其视为意外（有一个 PR 就是在 main 一下午前进了 7 个提交后遇到了这种情况）。如果仓库采用压缩合并，就应使用变基而不是合并——在压缩后的历史记录中加入一个合并提交毫无益处。冲突本身几乎总是**增量式的**：两位作者分别在同一章节追加了自己的条目，因此解决方法是**两者都保留**，绝不能使用 `--ours`/`--theirs`，因为这会悄无声息地丢弃同事添加的那一行。

人们经常跳过的，恰恰是能够发现错误冲突解决结果的步骤——**解决冲突后，证明相较于基线，唯一的差异就是你的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要只使用 `--force`：如果远程分支在你上次获取后发生了变化，租约机制会让推送失败，而这正是其他人向你的分支推送了内容、普通强制推送会将其抹除的情况。

**插件边界不属于本技能的职责范围。** 是否将技能拆分到
不同的插件中、如何组织 `source`/`skills`，以及用户能否单独启用或停用
技能，这些都属于打包/分发领域——其 SSOT 是
`marketplace-dev` 技能，而非此处。当任务确实需要做出这些决策时：
确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与
`skill-reviewer` 在需要相关脚本时引入 `skill-creator` 相同），然后阅读
marketplace-dev 的缓存与源模式参考文档并遵循其中的指导。不要在这里复述
它的规则；副本会逐渐产生偏差。

**重命名、移动或删除市场条目是一项破坏性变更**，会影响
每一个已经安装该条目的用户——条目消失时，Claude Code 不会清理已安装的副本，
从而留下悬空安装，导致每次执行 `marketplace
update` 时都报错。应像对待 API 弃用一样对待此类变更：在
变更日志中发布迁移说明，并遵循 marketplace-dev 对具体操作方式的指导。

**如果你亲自提交/推送技能仓库：** 对于现有技能，如果当前变更跨过了第 #5 条规范所定义的规则/契约/数值阈值，请确认评审产物记录了本次变更且已提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不能仅仅确认某个历史 `independent-review.md` 是否存在）。拼写错误修正或纯格式调整不需要该产物；旧评审永远不能满足当前实质性变更的要求。第 5 步的说明解释了为什么对于已发布的技能，真正的强制执行点是推送，而不是打包。然后仅暂存该技能的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树中通常充斥着无关变动，否则它们也会被夹带进提交中（曾有一个提交顺带纳入了一大批无关的记录文件，最终不得不执行 `git reset` 并重新暂存）。推送之前，使用 `gh repo view --json visibility,isPrivate` 确认仓库的真实可见性，而不要根据路径进行猜测——公共技能仓库应当通过 PR + 评审，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成技能后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试技能后，用户可能会要求改进。这通常发生在刚使用完技能之后，此时他们对技能的表现还有清晰的印象。

**优化筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了相关内容，请勿重复。

## Claude.ai 专用说明

在 Claude.ai 中，使用相同的验证深度路由机制和重度评估授权门槛。当用户明确授权使用完整的通用配对流水线时，工作流为：起草 -> 测试 -> 审查 -> 改进 -> 重复；但由于 Claude.ai 没有子代理，部分机制需要调整。具体调整如下：

**运行测试用例**：由于没有子代理，无法并行执行。对于每个测试用例，先阅读技能的 SKILL.md，然后按照其中的说明自行完成测试提示词所要求的任务。逐个执行测试用例。与使用独立子代理相比，这种方式的严谨性较低（因为技能由你编写，同时也由你运行，所以你掌握了全部上下文），但仍可作为有用的健全性检查——而且人工审查步骤可以对此加以弥补。跳过基线运行——只需使用该技能按要求完成任务。

**审查结果**：如果你无法打开浏览器（例如，Claude.ai 的虚拟机没有显示界面，或者你正在远程服务器上操作），请完全跳过浏览器审查环节。改为直接在对话中展示结果。对于每个测试用例，展示提示词和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），请将其保存到文件系统，并告知用户文件所在位置，以便他们下载和检查。直接询问反馈："效果如何？有什么需要修改的吗？"

**基准测试**：跳过定量基准测试——它依赖基线对比，而在没有子代理时，这种对比没有意义。重点获取用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重新运行测试用例并征求反馈——只是不再在中间加入浏览器审查环节。如果有可用的文件系统，你仍然可以将结果整理到各个迭代目录中。

**描述优化**：本节需要使用 `claude` CLI 工具（具体而言是 `claude -p`），而该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要子代理。请跳过。

**打包**：只要有 Python 和文件系统，`package_skill.py` 脚本就可以在任何环境中运行。在 Claude.ai 上，你可以运行该脚本，然后用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能是要求你更新现有 skill，而不是创建新 skill。在这种情况下：
  - **保留原始名称。** 记下 skill 的目录名称和 frontmatter 中的 `name` 字段，并保持二者不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前先复制到可写位置。** 已安装 skill 的路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即基于这个可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从该副本进行编辑和打包。不要传入 `--new-skill`；现有 skill 的非 Git 副本仍然属于现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 专用说明

如果你使用的是 Cowork，需要了解的要点如下：

- 你可以使用子代理，因此，在获得明确授权的情况下，通用配对流水线可以运行基线和评分器。子代理可用并不等同于获得授权，也不能成为增加额外角色的理由；应说明必要的实验分支、限制并发数量，并在并行执行无法增加证据时串行运行各个用例。
- 你没有浏览器或显示界面，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个链接，供用户在其浏览器中点击打开该 HTML。
- 在明确授权的**通用配对运行**之后，应先为人工评审生成评估查看器，再自行修改 skill，并使用 `generate_review.py`，而不是自定义 HTML。默认层级的证据、未经授权的工作，以及替代查看器机制的专用工作流，并不会仅仅因为工作是在 Cowork 中完成的，就产生提供查看器的义务。
- 反馈的处理方式有所不同：由于没有正在运行的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。之后你可以从该文件中读取反馈（可能需要先请求访问权限）。
- 打包功能可以正常使用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该也能正常运行，因为它通过子进程使用 `claude -p`，而不是浏览器；但请等到你已完全完成 skill 的制作，并且用户认可其状态良好后再进行。
- **更新现有 skill**：用户可能是要求你更新现有 skill，而不是创建新 skill。请遵循上文 claude.ai 部分中的更新指南。

- 在采用任何专用工作流出口之前，选择能够证伪此变更的最低验证层级，并记录原因

- 运行并通过现有技能回归审查；仅通过评估不足以算作通过
- 打包最终技能并将其返回给用户。

如果你有 TodoList，请将所选验证层级及其默认所需证据添加到其中。只有在通用配对流水线获得明确授权后，才能添加“创建评估 JSON 并运行 `eval-viewer/generate_review.py`，以便人工审查测试用例”。
