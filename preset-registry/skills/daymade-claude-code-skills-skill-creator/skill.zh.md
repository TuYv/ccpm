# Skill 创建器

用于创建新技能并对其进行迭代改进的技能。

总体而言，创建技能的流程如下：

- 决定你希望技能实现什么，以及大致应如何实现
- 将变更归类到能够证伪其潜在失败模式的最低验证层级
- 编写技能草稿
- 使用能够证伪变更后行为的最少证据进行验证；将完整的成对评估流程视为需要单独授权的工作，而不是某个层级标签所自动带来的后果
- 当所选层级产生定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写技能（如果定量基准显示出任何明显缺陷，也要进行重写）
- 重复上述过程，直到你满意为止
- 仅当当前证据无法判定变更后的行为时，才提升验证层级

使用此技能时，你的任务是判断用户在这一流程中所处的阶段，然后介入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一种能力，而不是每次编辑都必须承担的成本。诸如“优化”“改进”或“全面”等词描述的是意图，而不是失败面或评估预算。不要仅仅因为任务听起来范围很广，或因为较长的对话已经持续了一段时间，就创建评估文件、扩展成对代理、评定输出，或启动查看器。

以下六项持续适用的规范贯穿始终，因为这些失败模式会产出看起来令人信服、实则错误的技能：

1. **先验证，再编写。** 进入技能的每一条技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的结果——无论是在本次会话中，还是在获得明确批准的挖掘会话中。现在无法验证？要么去验证，要么明确标注（“未经验证——凭记忆”）。技能会放大其中包含的一切：经过验证的知识会不断积累，充满自信地陈述的错误也同样会不断积累。对于知识型技能（内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作层面的版本：权威层级（观察到的行为 > 机器可读的契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例的冒烟运行，以及面向受众/Windows 可移植性的检查清单。有一次来源依据审计发现，多个自信陈述的契约声明与作者已经掌握的证据相矛盾（方法论案例 9）。
2. **将“无法实现 / 不支持”视为假设，而不是结论。** 当某项能力似乎受阻时（API 错误壁垒、工具无法连接、格式无法打开），在将“平台不支持此功能”写入技能之前，应穷尽各种观察路径——包括 UI 自身的网络流量、替代通道、不同的文档化标识符。观察到的行为优先于推测性的请求形式。
3. **站在该领域既有最佳实践的肩膀上——默认在编写或优化技能的方法论之前，将领域已确立的最佳实践检索到上下文中。** 技能的方法论质量取决于上下文窗口中的知识，而不是你权重中潜在的知识：预训练知识是有损的，会过时，而且除非实际拉取了权威来源，否则往往根本不会被激活。因此，你所写内容的质量上限是 `你的训练数据 + 用户输入`——*除非*你有意检索该主题领域真正的既有成果。去做这件事：通过 WebSearch 搜索该领域的经典理论 / 标准 / 方法，并阅读该领域中随附或已安装的技能，然后将其中承载核心作用的原则及其出处融入技能中。**这与下面的“既有成果研究”是不同的维度**——后者用于寻找可复用的工具/基础设施；前者则是用该学科积累的科学成果为*方法论本身*提供依据。将其作为**默认行动，而不是等待用户提出要求**：简要告知用户你正在借鉴哪个领域的知识，并让他们可以说“跳过”，但绝不要在 40 年的领域公开成果只需一次搜索就能获得的情况下，仅凭你的记忆加上用户提示，交付一个质量上限受限的方法论。示例：数据可视化技能必须吸收 Cleveland & McGill 的图形感知排序以及 Bertin 的视觉变量（位置/长度优于颜色，颜色优于文本——这是经过测量的，而非审美判断）；日期/时间技能必须说明成熟的库及其经典陷阱；说服/谈判技能必须检索既有的成熟框架，而不是凭记忆重新发明。如果经典知识只存在于你的权重中，却从未进入上下文，那么你就是在本可引用的地方进行猜测。
4. **在压缩现有技能之前，先予以保留。** 更新现有技能是一项迁移工作，而不是从空白页面开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧版本内容，或从明确的 Git 引用重建；随意复制一份并附上来源标签不能作为基线。清点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和简洁性允许你移动或去重内容；但不允许你默默删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个未匹配的旧单元进行分类。仅在 `evals/`、测试或未链接的参考资料中保留下来的运行时契约，仍然算作丢失。在任何候选项尚未分类，或任何真正的缺口仍未修复之前，不要将更新称为完成。同样的逻辑也适用于**撤销**，而不仅仅是删除，并且涵盖任何先前作出的承诺——不只是那些带有日期和名称的承诺：**推翻已经作出的决策是一项提案，绝不能作为副作用发生。** 要明确说出来并获得接受。默默重写比默默删除更糟糕，因为它会一次性摧毁产物以及本可以发现问题的证据——并使所有下游审查者失去判断依据（见 #5）。

**在编辑前为每个预期差异分类；“压缩”是行为等价的主张，而不是“更短”的同义词。** 对于每个旧有用户场景，新 agent 仍必须能够找到触发条件、决策输入、支持的操作、停止/确认点、影响/恢复边界以及验证路径。在计划、评审和变更日志中，将这些名称作为独立的变更类型标签；在每个回归候选项的原因/语义评审中记录该标签，同时将审计工具的 `disposition` 字段保持为 Step 4 中规定的精确枚举值：

   | 变更类型 | 定义 | 必需处理 |
   |---|---|---|
   | **无损压缩** | 仅改变呈现方式：将细节移入可直接访问的捆绑引用中、针对随包提供的规范来源去重，或在保留上述每项运行时契约的情况下缩短措辞 | 可以称为压缩；证明场景可达性，而不只是证明字符串仍然存在 |
   | **能力退役** | 以前可执行的任务或操作不再可用 | 不属于压缩；明确说明已退役的能力，取得可追溯的用户批准，并发布该边界 |
   | **范围收窄 / 边界变更** | 仍受支持的输入、目标、环境或模式减少；某个执行分支变为仅分析 | 即使这样做更安全，也不属于压缩；说明并发布边界/权衡，然后取得可追溯的批准，除非用户此前已经明确要求这一确切的范围收窄 |
   | **工作流或安全性重新设计** | 命令、顺序、确认、副作用、恢复方式或成功检查发生实质变化 | 不属于压缩；说明新的契约和权衡，除非用户此前已经明确要求这一确切的重新设计，否则取得可追溯的批准，然后独立于保留性验证之外对其进行验证 |
   | **缺陷修复 / 事实更正** | 将实现或措辞恢复到明确的既有契约或当前权威来源 | 不属于压缩；使用能够作出判定的狭义权威来源或确定性回归测试 |
   | **有损总结** | 精确条件、命令、决策语义或执行退出点消失，且没有运行时可达的等价内容 | 属于回归，而不是优化；恢复它，或通过上方某个已批准的条目重新分类 |

   只有在规范来源随 skill 一同发布，或能够可靠地获取，并且 SKILL.md 告诉运行时读者何时加载该来源时，去重才算无损。“这个想法仍存在于测试、变更日志、已安装的同级 skill 或作者的记忆中”不属于压缩。如果一个补丁包含多种类型，分别列出；绝不要让“压缩”标签掩盖退役或重新设计。

5. **任何内容都不能仅凭自我评审发布——独立且使用全新上下文的对抗性检查是固定步骤，而不是特殊情况。** 你“现在已经没问题了”的判断来自生成该产物的同一个模型，因此共享导致缺陷的那些盲点。对此已有测量结果，而非民间经验：没有外部反馈的内在自我纠正并不能可靠地改善输出，有时还会使输出恶化（Huang 等，ICLR 2024）；当生成器和评估器共享错误模式时，反复迭代会**提升信心，却不增加信息**。更多自检无法摆脱这一点；只有外部视角可以。**完整流程——包括提示模板、锚点选择、发现项表格和示例案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在首次检查前先阅读它。** 承重规则如下：
   - **独立性有两个方面，而第二个方面正是作者容易遗漏的。** *评审者的上下文*不能是你的分支——分支会继承你的盲点，并返回一个“已评审”的印章。但它据以衡量的*证据*也必须位于变更的**影响范围之外**，否则它会继承你的**结论**：它读取一个产物和一个已经与之达成一致的规范，然后报告二者一致。注意，“本次会话中没有编辑过”是过于薄弱的界线——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，三名评审者都对一个他们在未编辑的孪生记录中发现过的缺陷视而不见。根据锚点被你触碰的难易程度对其排序：用户自己的对话原文 > 早于本次工作的 git ref（`git log --oneline <ref>..HEAD -- <path>`；你的任何提交都会使其失效）> 追加写入日志（这是一种约定，而非强制机制）。**Greenfield 没有锚点——请说明这一点并索要一个锚点，而不是报告一个你并未执行的通过结果。**
   - **只提供恰好两个承载证据的输入：不可变产物和读者规范。** 另外提供用于限定检查范围的、非证据性控制元数据：当前变更的影响范围、明确命名的失败轴以及终止条件。不要提供设计理由、项目背景或“只需确认 X 没问题”之类的内容——这些会把独立评审者变成橡皮图章。读者规范和控制元数据说明由谁执行什么以及在哪里停止；它们不能告诉评审者实现是正确的。**对于 SKILL.md，读者就是另一个执行它的 agent**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——要询问它无法据以采取行动的指令。在派发前冻结全部五个字段，绝不要使用事后上下文来解释或消除发现项。
   - **对于可理解性以及针对语料库的完整性，它是事实依据；对于品味，它没有权威性。** 直接应用前两者。将“这可能是一个 bug / 我建议 Y”视为假设，并先自行复现。绝不要委托 AI 垃圾内容或审美判断——这会复现同一个模型的盲点。
   - **枚举失败*轴*，而不是内容领域——这也决定运行多少名评审者。** 轴是*你提出的问题*；领域是*你阅读的材料*。三名评审者分别覆盖场景、算术和差异，但都在询问“这是否连贯”，那仍然只是把一名评审者计费了三次。**一名评审者是默认配置，而且通常已经足够**；只有在增加额外轴时才增加一名。自我评审最不擅长的轴是**忠实性**——“这是否仍忠实于已经作出的承诺？”——因为移动承诺的人正是作者，而连贯性和忠实性彼此正交：一个产物可以完美地自洽，同时完全不忠实于已经决定的内容。
   - **在派发前冻结评审边界，并在满足该边界后停止。** 记录不可变产物/ref、读者规范、当前变更的影响范围、明确命名的失败轴以及终止条件。当发现项由当前变更造成、扩大了影响范围、新近宣传了受影响的行为，或使一个旧有矛盾通过编辑后的路径变得可达时，它会阻止本次发布。一个未发生变化且未被新近承诺的既有缺陷，是单独的待办假设，并不自动授权重新设计 skill。完成实质性修复后，由新的评审者重新检查失败的轴以及回归；它不会重新开启无边界的整篇 skill 审计。完整的决策流程和示例见：[references/independent-review-protocol.md](references/independent-review-protocol.md)。
   - **留下产物，否则这只是一条警告。** 纪律 #6 规定，产生意见的检查不如产生产物的检查——因此这一步也要生成一个文件，否则恰恰在最需要它时，它会输给“推动完成”的倾向。在你的私有、受 git 跟踪的知识仓库中，将 `independent-review.md` 写入 `skill-reviews/<skill-name>/`：其中必须包含**逐字记录的评审者提示词**（这样后来的读者才能看出提示词是否具有诱导性）、**每项发现及其 disposition 和理由**（这正是合法筛选与丢弃不利内容之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识仓库（或者你没有这样的仓库），请说明这一点并询问用户——不要猜一个最终落入任一禁区的位置。两个禁用位置：**不得位于 `<skill-name>-workspace/` 中**（会被清理的、被 gitignore 的临时目录——该文件是跨会话的评审证据，必须在这些目录之外留存），**也不得位于任何已经公开或可能公开、分发的仓库中**——这通常意味着被评审 skill 自己的仓库也不行（评审内容必然会引用私有路径、真实姓名和项目细节）。完成实质性编辑后，使用一个*新的* agent 重新评审——实质性编辑是指规则、契约或数字发生变化，而不是拼写错误。**从 Step 5 开始，该文件就是评审已发生的证据；文件不存在就意味着评审没有发生。****写入文件不等于它在下一会话中仍然存在——在同一轮操作中，在该私有仓库执行 `git add` + `git commit`。** 一个未提交、位于 git 工作目录中的文件，不具备这条规则所要求的任何“受 git 跟踪”保证：它可能丢失、被覆盖，或者根本不会被后续检查“是否已评审”的流程发现（真实案例：文件被正确写入了正确路径，也包含真实发现项——但由于从未提交，仍未通过后续自动检查；修复只需执行一次 `git commit`，而不是迁移文件）。
   - 纪律 #4 的回归门禁是机械性的，也是互补的：它证明你没有*删除*行为。但它无法说明你写出的内容是否真的可以被遵循。

6. **设计你编写的检查，使其无法自我认证为通过。** Skill 在很大程度上由各种检查组成——门禁、检查清单、“发布前”步骤——而如果执行上下文在*违反其所编码的规则*时仍能通过某项检查，那么这项检查比没有检查更糟糕，因为它制造了虚假的信心。以下四条规则借鉴了那些早已解决这一问题的领域：
   - **验证必须覆盖规则中的每一条要求。** 如果规则写的是“A + B + C”，证据就必须分别要求证明 A、B 和 C。给一条包含三个要求的规则只配一行确认语句，执行者只需满足作者已经完成的那一条即可；其余要求完全不会被发现。真实案例：一个报告编写 skill 有一道交付门禁，其规则写的是“选项以并排芯片呈现 + 突出显示推荐项 + **背景信息必须写成完整、独立成篇、陌生人也能读懂的句子**”——但其下的证据行只要求“共有 N 个决策项，且全部以芯片呈现”。作者运行了门禁，写下了这条证据，自我认证为通过，并交付了一个标签只有单个字符、所有上下文都被删除的页面。规则始终写在文件中；只是检查从未度量过那一条要求。
   - **在健康输入上误报的检查比没有检查更糟糕。** 上面的失败属于本应失败却通过的检查；这里是它的镜像——本应通过却失败的检查。后者代价更高，因为它会教会操作者条件反射式地绕过检查（`--no-verify`、`SKIP=1`、`--force`），而一旦形成这种反射，门禁就会对*所有*输入失效，包括那些原本正是为其构建的输入。因此，在编写失败即关闭的检查时，**误报的优先级高于漏报**：漏掉一个真实问题只会让你损失这一个实例，而误杀一个健康输入则会让整个门禁失效。
     注意这个信号：**反复踩中同一个陷阱所产生的挫败感本身就是风险信号**——这正是作者会交付一个从未针对健康输入进行校准的防护措施的状态。真实案例：一天之内连续三次踩到同一个格式陷阱后，作者给 linter 加了一条正则检查；它在项目自己的语料库中误杀了 **33 个健康输入**，并在同一小时内被回滚。启用之前先进行校准——在真实且已知正确的材料上运行任何失败即关闭的检查，并确认没有误报；与其让它发生哪怕一次误报，不如适当放宽它，接受它偶尔漏掉问题。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是自洽完整的”无法被撰写它的人判定为失败；而“遮住页面的其余部分，只阅读一张卡片，并说明它正在决定什么”则可以。优先选择能产出工件的检查——例如命令输出、引用的行或屏幕截图——而不是只能产出意见的检查。
   - **同样的怀疑也适用于你*运行*的检查，而不仅仅是你编写的检查。** 上述四条规则约束的是随 skill 一起交付的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样是工具；错误的工具会像正确的工具一样自信地报告干净结果。在 2026-07 的一次会话中，五条不同的验证命令在两个方向上都给出了错误结果：不带 `-L` 的 `find` 报告已安装 skill 的文件缺失（它们实际上位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了正在审计的对象的第二份副本；一个反转的 shell 条件错误地发出警报，声称删除操作没有发生；跨越换行符的正则凭空制造了 55 个“丢失的引文”；而在五个文件中的两个文件上进行搜索，报告称有两条规则缺失，但它们实际上存在于第三个文件中。**这些结果起初全都被相信了，而最终每一个都只能通过重新运行一种形态不同的检查才被发现。**

这种修复方法是实验实践中最古老的一种：**在信任仪器、用它检查未知案例之前，先让它处理一个你已经知道答案的案例。** 如果你要搜索一个预期不存在的字符串？先用完全相同的命令形式搜索一个你确定存在的字符串——如果这次也返回 0，那么出问题的是命令，而不是文件。只需多写一行，就能把“我检查过了”转化为“我用校准过的仪器检查过了”。

     有两种具体形式值得记住，因为上文都出现过，而且两者都会*静默失败*：`find` 不带 `-L` 时不会跟随符号链接（而 skill 的安装经常是指向源代码仓库的符号链接），`--exclude-dir` 则会在整个目录树中按 basename 匹配，而不只是匹配你心里想到的那个路径。

     **而这条规则还有后半部分，只有当检查会被*发布*时才会产生影响：要以*标准*实现为基准进行校准，而不是以你机器上的实现为准。** 上面的仪器规则是为了让*你的*结论保持诚实；这一点则是为了让*读者的*操作能够正常工作。写入 skill 的工具行为声明——某个标志、递归模式、一个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而差异在两端都是静默的：它在你测试时有效，却在读者那里悄悄什么也不做。有两种机制会造成这种情况，而且在会话内部都无法察觉：**同一个命令名解析到不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能绕过*别名*，因此 `command tool` 或绝对路径才是唯一确定的形式），以及**同一个程序在不同实现之间表现不同**（BSD 与 GNU，或替代实现之间）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将其写入 skill，作为解决符号链接陷阱的方法，并将其发布到了一个拥有 1200 颗星的公开仓库——但他们的 `grep` 实际上是由 shell 函数调用的 ugrep；在 macOS 自带的 `/usr/bin/grep` 中，相同的 `-R` 什么也匹配不到（它需要 `-RS`），因此这条规定的修复方法对大多数读者都静默失败了，而且恰恰发生在警告验证器会静默失败的那一节中。

     因此：**在有关工具行为的断言进入已发布的产物之前，应当使用标准二进制文件重新运行验证**（`/usr/bin/<tool>`），而不是使用 shell 交给你的那个。如果它经不起这样的验证，就不要写入这个标志——**优先采用与实现无关的表述方式**：自己解析路径（`readlink -f`），不要押注于某个递归标志；在脚本中进行子字符串测试，而不是进行面向行的匹配；描述你需要的*行为*，而不是描述你碰巧知道的选项。只在你的环境中有效的规定比没有规定更糟，因为读者没有办法发现它其实悄悄什么也没做。

   - **采用成熟的清单实践已经确定的方法。** 判断一份列表应当属于 **READ-DO**（边阅读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭经验操作，然后在明确的**暂停点**停下来确认——适用于时间压力下的资深操作者），并将其锚定在一个真实的暂停点上，而不是“流程中的某个地方”。只保留**关键事项**——既关键、又经常在压力下被遗漏的事项，大约五到九项；再多就会稀释执行度（[Gawande，《清单宣言》](https://www.shortform.com/blog/types-of-checklists/)）。并且优先采用 Shingo 所说的**控制**，而不是**警告**（[防错](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，敌不过“完成任务”的冲动；而阻止流程继续推进或强制产出某个工件的步骤则完全不需要警觉性。在 skill 只能发出警告的情况下，至少要把警告放在作出决策的地方——**写在执行上下文从未打开的参考资料中的规则，在实践中就不算规则。**

另一方面，他们可能已经有了 skill 的草稿。在这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应该始终保持灵活；如果用户说“我不需要运行一堆评估，和我一起凭感觉来就行”，那你也可以照做。

然后，在 skill 完成之后（不过再次强调，顺序是灵活的），你还可以运行 skill 描述改进器。我们为此准备了一个完整的独立脚本，用于优化 skill 的触发效果。

## 首先：共存检查（官方 skill-creator 插件）

在执行任何操作之前，先快速检查一次（在常见路径下无需输出任何内容）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 什么都不做——不要安装任何内容，也不要向用户提及本节。继续处理当前任务。
- **存在：** 官方插件的 skill-creator 与此版本现在会以几乎相同的描述同时出现在 skill 列表中，因此未来的会话会随机在两者之间进行路由。用一到两句话告诉用户这一点，然后提供以下选项（绝不要未经用户同意就执行）：
  1. **推荐** — 运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型自检 SessionStart hook 复制到用户的 Claude 配置中，并将其注册到 `settings.json`（同时创建备份），这样今后的每个会话都会确定性地将 skill 工作路由到此版本。可以通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；官方插件在按名称请求时仍然完全可用。在未安装官方插件的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的 hook。
  2. 另一种选择 — 使用 `claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），这会将官方条目完全移出 skill 列表，从而消除歧义。

如果 hook 已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目存在），则静默跳过以上所有步骤。

对于用户创建的 skill，也可以使用相同的机制：当他们的 skill 有意与某个已安装的 skill 重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一套工具包——参见 Prior Art Research 下的“共存与优先级”，以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

## 与用户沟通

skill creator 可能会被各种编程术语熟悉程度不同的人使用。如果你还没听说过（怎么可能呢，这种趋势也才刚刚出现不久），现在有一种趋势：Claude 的强大能力正激励水管工打开终端，也让父母和祖父母开始搜索“如何安装 npm”。另一方面，大多数用户可能具备相当程度的计算机素养。

因此，请注意上下文线索，以了解应当如何措辞进行沟通！在默认情况下，可以参考以下几点：

- “evaluation”和“benchmark”处于临界范围内，但可以使用
- 对于“JSON”和“assertion”，在用户明确表现出了解这些概念之前，不要直接使用这些词而不加解释

如果你不确定，简要解释术语是可以的；如果不确定用户是否能理解某个术语，也可以用简短定义加以说明。

### 使用 AskUserQuestion（关键 — 请阅读）

**在每个决策点都积极使用 AskUserQuestion。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最大单项 UX 改进——用户可能同时切换着多个窗口，而且可能已经有 20 分钟没看这段对话了。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段，以及刚刚发生了什么（1-2 句话）。用户可能已经切换到其他任务。
2. **简化说明**：用通俗语言解释需要做出的决定。不要使用函数名或内部术语。说明它会做什么，而不是它叫什么。
3. **给出建议**：先给出你的建议，并用一句话说明原因。如果选项涉及工作量，请同时展示两个时间尺度：`(人类：约 X 分钟 / Claude：约 Y 分钟)`。
4. **提供选项**：给出 2-4 个具体的、带字母编号的选择。每个选项都应该是明确的行动，而不是抽象概念。

**规则：**
- 每个问题只涉及一个决定——绝不要把无关的选择合并到同一个问题中
- 提供退出路径（AskUserQuestion 始终隐含包含“其他”选项）
- 接受用户的选择——可以提醒权衡，但绝不要拒绝继续执行
- 如果存在没有权衡的明显答案，则跳过提问（直接说明你会怎么做）
- **如果问题超时且没有得到回答（用户暂时离开了键盘），既不要停滞不前，也不要贸然推进涉及偏好或范围的决定。** 先完成不产生副作用的准备工作——编辑前快照、清单盘点、评估用例收集、只读审计/健康检查——并等他们回来后再决定判断性事项（重构方向、删除内容、是否继续）。然后明确说明你完成了哪些工作，以及哪些事项正在等待他们决定。

## 创建技能

### 捕获意图

先了解用户的意图。当前对话中可能已经包含了用户希望提取的工作流（例如，他们说“把这个变成一个技能”）。如果是这样，先从实时对话中提取答案——使用了哪些工具、步骤顺序、用户做过哪些修正、观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**源清单——起草前始终执行，并明确同意边界。** 盘点实时对话以及与之重叠的现有文档/技能（参见下文的既有成果研究）。较早的本地会话 JSONL 文件是单独的私有来源：除非用户明确要求挖掘历史记录，或在你解释将读取哪些内容后明确批准该来源，否则不要打开或解析它们。如果获得批准，则通过对话挖掘工作流中的脱敏提取，仅将相关的过往会话纳入其中；绝不要将原始记录加载到自己的上下文中。如果未获批准，则继续使用实时对话和现有项目来源，不要将缺失的历史记录视为阻碍。

在挖掘对话（或会话记录）时，同时盘点两类资产——它们会放在不同的位置。*知识*——端点、参数、陷阱、决策规则——应成为 SKILL.md 中的指导内容或放入 `references/`。*会话需要编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——则是 `scripts/` 的候选内容：如果本次会话编写了这些代码，那么下一次调用时就必须重新编写，因此应将其参数化、进行清理，并打包进来。此前的一次提炼产出了经过润色的说明文字，却遗漏了可复用的辅助工具；总体经验是，要同时关注知识→references 和代码→scripts 这两条路径。

当源材料是*过去的*会话记录（Claude Code projects directory 下的 JSONL 文件），而不是实时对话时，进入会话挖掘工作流。不要在主上下文中打开原始记录，也不要将原始路径/内容交给子代理。在任何代理看到内容之前，必须完成确定性的 manifest → discover → redact → chunk 序列；只有经过 redact 的 chunks 才能进入最小角色/分片计划，并且必须在预算门禁下声明确切的单元数量和并发上限。

**首先，在下面的问题之前，先确定这是哪一个方向。** 请求可能属于几种*相反*的事情：构建一个新 skill / 编辑一个已有 skill / 优化 skill-creator 本身 / 或者根本不是 skill，而是一次性任务。猜错会浪费整个会话——你为“新 skill”所做的研究，并不适用于“优化元工具”。当措辞含糊时（例如指向 skill-creator 自身的路径，却说“帮我做一个 skill”），此处提出一个 AskUserQuestion 只需 30 秒。下面的 wrapper-skill 分支是其中一个特殊情况；方向检查本身则适用于所有情况。

`Use skill-creator to optimize <existing-skill>` 表示正常的已有 skill 更新路径。它并不授权进行会话历史挖掘、广泛重写、Tier 3 分类或多代理评估。先检查实际提出的差异；只有当这些差异确实引入了某种故障面时，才升级处理。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证这个 skill 是否有效？对于输出可以客观验证的 skill（文件转换、数据提取、代码生成、固定的工作流步骤），测试用例很有帮助。对于输出较为主观的 skill（写作风格、艺术、经过品味校准的报告），通常无法使用断言——但“没有断言”并不等于“没有验证”。它们的验证路径按成本从低到高排列如下：
   - **历史任务重放**：重新运行一个该 skill 之前处理过的真实提示词，分别使用旧版和新版 skill，然后根据具体发生变化的规则比较输出（“新输出是否真的遵循了这次更新引入的 token / 标题语法？”）。成本低，而且能发现“规则写进去了，但没有任何东西读取它”。
   - **以生产作为评估**：承认真正的测试是用户下一次实际使用，然后明确这个闭环：之后用户的每次纠正都是要回填的事件（skill 自身的“迭代/活文档”部分），每次认可都是语料库材料。一个发布时没有这种回写习惯的品味型 skill 不会改进；而有这种习惯的 skill 无需运行正式评估也能逐渐收敛。**当 skill 的输出是某种会持续运行的东西——守护程序、监视器、定时任务、hook——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报警。** 用户纠正需要用户注意到问题并愿意反馈；而已部署的机制会主动报告自身情况，通常在一天之内就会反馈，误报则是这种反馈最尖锐的形式，因为它证明你写下的某条规则是错误的，而这是再多的重新阅读也无法揭示的。应将第一次误报视为一次已安排的评估结果，而不是麻烦：在假定机制行为异常之前先检查它，因为更可能的发现是，*指令*写得过于绝对。（真实案例：某个 skill 规定检查必须失败即大声报警，已部署的检查在夜间对一个完全健康的状态触发了一次，最后修复的是 skill 中那句过于绝对的表述——没有人提出抱怨；是遥测数据暴露了问题。）
   - **渲染 + 人工审查**适用于视觉输出（使用 skill 自身的视觉质量检查门禁），绝不能用假装能够衡量审美的 grep 断言来代替。**而且，用于验证的渲染器必须与交付物实际使用的引擎相同**——无论安装了哪个方便的预览器，都不能替代目标应用。布局引擎与目标应用不同的缩略图工具，可能会悄悄*隐藏*你要查找的确切缺陷；在错误引擎上得到绿色验证，比没有验证更糟，因为它会制造虚假的信心。真实案例（2026-07）：一个 .docx 曾通过 macOS Quick Look 缩略图进行“视觉验证”，但 Quick Look 不会复现两端对齐文本的拉伸；用户在 Word 中打开文档后，发现信息块瞬间被撑得四分五裂。修复方法是安装与 Word 兼容的引擎（LibreOffice），转换为 PDF，逐页栅格化，然后阅读每一页。必须匹配引擎，否则这种验证就是演戏。**这不仅适用于渲染器，也适用于所有验证工具**——解析器、linter、验证器：它必须与生产环境共享同一实现，否则它显示绿色就毫无意义。第二个案例也是同样的情况：某位作者试图捕捉一种会破坏最终文档的标记模式，却在源文件阶段使用了与生产工具链不同的 markdown 实现进行检查——它把三个已知有问题的输入都解析为完全正常，因此任何建立在其上的预检查都会悄悄放过所有问题。诚实的结论是：这个特定缺陷只有在生产工具运行之后才能检测出来，检查应当放在那里。**当没有可用工具与生产实现共享同一实现时，应说明该检查无法在那个阶段完成——不要构建一个只能产生虚假绿色结果的检查。**
   
   根据 skill 类型提出适当的默认方案，但让用户做决定。

从对话历史中提取答案（或提出问题 1-3）后，使用 **AskUserQuestion** 确认 skill 类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类会推动后续的整个评估策略。在这里做出正确判断，可以避免之后的无效工作。

### 扩展与创建检查——在任何专门分支之前运行

下面的三个专门工作流都以“**不要**继续阅读下面的章节”结尾，而 *Prior Art Research* 恰好位于它们之后。这个顺序是排版顺序，而不是执行顺序。扩展与创建的判断适用于每个分支，而跳过这一步正是导致会话发布了一个与已安装 skill 重复的 skill 的原因。

因此，在进入 wrapper-skill / conversation-mining / artifact-corpus 分支之前，先回答一个问题：**是否已经存在一个 skill，当前能力应当归属于它？**

**发现根目录，不要凭记忆。** 手动维护的安装位置列表正是会过时的产物，而你忘记的那个根目录，才是最容易造成问题的地方。

**搜索文件，而不是搜索名为 `skills` 的目录。** Skill 目录以 *skill* 命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、marketplace 克隆仓库和插件缓存中根本不会包含名为 `skills` 的目录——搜索这个名称会悄无声息地跳过它们，却看起来像是正常工作。每个 skill 都有一个 `SKILL.md`；这是与目录布局无关的检索入口。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，而且仍会返回多于所需的结果；请使用与该能力相关的具体术语进一步缩小范围，而不是使用通用术语（`chart` 会匹配所有内容，`stacked bar` 则不会）。

这会触及一些通常凭记忆列出的清单会漏掉的根目录：技能源代码仓库（一个 `claude-code-skills` 检出目录以及任何 `-pro` 兄弟仓库）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件——源代码仓库中没有任何线索表明它们存在于那里）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、按配置文件划分的配置目录（`~/.claude-profiles/<name>/`），以及——完全没有任何路标的那个位置——**每个项目自己的 `.claude/skills/`**。第 2 步能让这件事成为你验证过的结论，而不是你照搬来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何 marketplace、全局技能列表或源代码仓库列表中；你在规划新技能时通常会打开的地方，没有任何内容会提到它们。真实案例（2026-07）：某个会话为一个领域构建了一个全局技能，检查了源代码仓库、全局目录和其他 agent 的目录，什么也没找到，于是完成了发布。后来的一次对话历史搜索发现，在某个项目的 `.claude/skills/` 中，正放着一个针对该领域的成熟项目级技能，而且已经存在了一个月——其中有新技能缺少的八条规则，包括一条用户亲自规定的规则。除了项目级目录之外，每个根目录都检查过了，而这次扫描却自信满满地报告“没有既有方案”。

**当重叠的技能确实是某个无关项目中的项目级技能时该怎么做**——也就是那个故事会把你带入的情况，也是下面三个要点未涵盖的情况：你无法向一个原本没有兄弟技能的套件中添加兄弟技能，而“扩展它”意味着编辑某个无关项目的工作树。有效的做法是：**将其中的规则吸收到你正在构建的技能中，然后在所有者同意后停用项目本地的技能**——它是针对真实工作编写的，因此应将其视为更成熟的来源，并且朝着它进行协调。停用他人的工作技能是所有者的决定，而不是构建过程的副作用。

这句话遗漏了四件事，而每一件都可能让你停下来：

- **“朝着它进行协调”是一项可反驳的推定，而不是规则。** 有两种常见的退出方式：项目技能可能已经*过时*（规则是几个月前针对一个已经发生变化的系统编写的），也可能是*项目特定的*（规则只在该项目的约束下成立——整套导入会让你的技能变得狭窄，而本文其他地方明确告诉你不要这样做）。吸收来的规则是另一位作者的记忆，因此要像规范 #1 要求你对写入技能的任何内容那样，**重新验证每一条规则**。
- **“停用”需要一种机制，而它的第一步并不是你通常会先做的那一步。** 顺序如下：

  1. **先用 `find` 查找技能的*实体目录*，再用 grep 查找它的*引用*。** 一个技能在同一个仓库中通常不止一份——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被加载，只是由同一个工作树中的不同工具加载。Grep 能回答“谁提到了它”；只有 `find` 能回答“它到底有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要把技能自身的名称放进 `--exclude-dir`**（它按基本名称匹配，因此会隐藏所有同名目录，包括你尚未找到的那一份——参见规范 #6 中的工具规则）。真实案例（2026-07）：一次停用操作正是这么做的，修复了它找到的全部五处引用，却在 `.agents/skills/` 下留下了第二份完整副本——该副本受 git 跟踪、没有停用标记，是一份缺少最新规则的过时快照——另一个工具仍会将它作为有效技能加载。
  2. **在删除任何内容之前，确认新的归属位置确实可以从旧位置到达**——你刚推送的 marketplace 技能并不会立即安装，必须先更新 marketplace 并安装插件；如果先停用旧技能，就会留下新旧都不存在的空窗期：
     ```bash
     claude plugin marketplace update <marketplace>   # 你的推送不等于他们的缓存
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L：安装内容通常是符号链接
     ```
     `-L` 不是可选项——插件缓存经常会链接到源代码仓库中，而不带 `-L` 的 `find` 会报告文件不存在（参见规范 #6 中的工具规则）。
  3. **然后** grep 查找引用，并重新指向仍在生效的引用。要区分**有效指令**（技能列表、交叉引用、告诉下一个 agent 应使用什么的交接文档）和**历史记录**（决策日志中的条目，说明“我们在某日期发布了这个”）——重写后者会破坏审计线索，只为修复一个它并不存在的问题。
  4. **然后**将每个实体目录替换为 `superseded by <skill>` 存根，而不是直接删除，并确保每份副本的存根都逐字节一致。**保留 YAML frontmatter**——没有它的 `SKILL.md` 可能会加载失败，而不是提供有意义的失败信息——但要重写 `description`，让存根声明自身已停用，而不是继续宣传旧的触发条件；否则它会继续赢得它已经不再负责的路由。正文只需要包含：能力转移到了哪里，以及它为何转移的一行说明。
- **使用下面的所有权测试来识别所有者**（这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍然会告诉你它属于谁）。当所有者就是你正在交谈的人时，“同意”只需要一个 `AskUserQuestion`。**当所有者无法联系时，只吸收规则——不要停用**（这样会让两个技能同时处于有效状态并争夺同一触发条件，其最终结果与对方拒绝停用相同——参见下面的“共存与优先级”）。
- **如果所有者拒绝停用它**，那么现在就有两个技能在争夺同一触发条件；这属于下面的“共存与优先级”问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 那个项目技能不会匹配新技能标题的名称搜索；它匹配的是正文中的领域术语。请在候选根目录中搜索新技能将处理的*概念*。

如果存在重叠：

**判断哪个项目符号适用——这是谁的技能？** 文件系统命中结果不会携带所有权信息。读取 marketplace 的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或者在所属仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中结果同样可能只是你自己的 marketplace 被安装回了你的机器上。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同样的问题。

探测结果有两种情况会出错或无法回答，因此在相信结果之前请先检查：**fork** 会显示你自己的远程仓库，但其中的内容可能属于其他人——应将其视为第三方，因为他们上游的改进仍然无法传递给你。而当**既没有 marketplace.json，也没有 remote**（本地项目、被手动复制到全局技能目录中的技能）时，探测结果表示的是沉默而不是否定：**请询问所有者，而不是猜测。**

- **重叠的是第三方技能**（marketplace 套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*薄增量*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本——并通过**带命名空间的名称引用它**。把别人的引擎克隆进你的软件包是代价高昂的错误：他们的升级将无法继续传递给你，而两份副本会在不知不觉中逐渐偏离。
- **重叠的是你自己的技能**：扩展它，或在其现有套件中添加一个同级技能。一个为相同触发条件竞争的独立技能对任何人都没有帮助。**例外：**如果它位于*无关项目*的工作树中，则以上两种处理方式都不适用——请参见上面的项目级情况。
- **某个相关技能已经指向了你要填补的空白**（例如其描述写着“对于 X，请使用 Y”）：构建完成后要闭环——更新那个指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**一次真实的 2026-07 会话花了一天时间让第三方 docx 引擎生成正确的中文商务文档，随后转而采用包装器技能分支——而该分支会直接跳过 Prior Art Research。它当时准备发布的形态，是一个重新携带该引擎能力的新技能。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个包含正确用法和经过验证的生成器脚本的薄增量技能 → 由领域工作流技能调用这个增量技能。用户不得不纠正两次，第二次纠正更加明确：*“不要再复制一个额外的——在他们的技能之上写出正确用法，并引用他们的技能；这就是 skill-as-code 的含义。”*

### 验证深度路由器（选择任何工作流之前运行）

在选择通用或专用工作流分支之前，选择能够证伪变更后行为的**最低层级**。应根据具体变更及其故障面进行分类，而不是根据行数或请求用词：一个变更的破坏性命令可能比一大段冗长的文字清理更应归入高层级，而请求“优化”现有 skill 也可能只是一次有界修正。在选择层级之前，先列出你实际打算变更的规则、契约、脚本、权限和输出。如果尚未明确这些内容，应先进行检查并暂定分类；范围不确定并不能作为归入 Tier 3 的依据。

| Tier | 适用情形 | 所需证据 | 默认不添加 |
|---|---|---|---|
| **1 — 定向** | 这是一个现有 skill；未新增或实质性改变任何能力、触发器系列、工作流分支、输出契约、依赖、权限或外部写入行为；且编辑内容恰好属于以下一种：(a) 不改变行为的拼写/格式修改；(b) 事实性文档/配置修正，其正确性由直接权威决定；或 (c) 有界的实现修复，用于恢复一项明确的现有契约，**并且**修复后的行为由确定性的回归检查覆盖。可能改变 agent 行为的澄清不属于 Tier 1 | 对于以上三种情况：运行 `quick_validate`，检查差异，并完成现有 skill 迁移门禁。然后仅使用相匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其范围狭窄的检查；(c) 明确的现有契约及确定性的回归检查。仅当触发纪律 #5 的规则/契约/数值阈值时，才添加一名新的审阅者 | agent 行为重放、成对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 抽样行为** | 这是一个现有 skill；变更会影响 agent 行为，但未新增能力、触发器系列、输出契约、脚本行为、依赖、权限或外部写入；并且 1–2 个带有明确验收标准的具名示例即可覆盖整个变更后的行为。对一条现有路由或证据选择规则的有界修正仍属于此级别，即使它改变了所选路径 | 仅运行这 1–2 个具有代表性的带 skill 重放，以及范围狭窄的确定性检查和纪律 #5 所要求的一次新上下文审查 | 默认不添加基线、成对扇出、方差分析、基准测试、查看器或评估文件。对这些内容的明确请求需经过单独的证据预算门禁，且不会重新划分变更层级 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新 skill；任何新增或实质性改变的能力；跨分支的广泛重写或方法论扩展；触发器/描述优化；新的工作流分支，或实质性改变的输出契约、脚本能力、依赖或权限；高风险自动化或外部写入；或变更后的行为本身覆盖 3 个以上不同的提示类别、重复试验或实质不同的方法 | 先运行确定性门禁，然后仅添加针对已命名故障轴所需的证据。只有在单独的重型评估授权门禁通过后，才可使用下方完整的成对流水线；Tier 3 本身不会启动该流水线，同一门禁也可以授权在其他层级添加额外证据 | 仅凭 Tier 3 标签自动添加成对扇出、评分器、基准测试或查看器 |

#### 重型评估授权门槛——独立于层级分类

层级描述的是**风险和不确定性**；它并不授权 token 消耗或代理扇出。通过此门槛会改变获准的证据方案，而不会改变层级。只有在以下任一条件满足时，通用的 paired baseline → grader → benchmark → viewer 流程才可以运行：

- 用户明确要求进行 A/B、基线、基准测试、重复试验、viewer 或多代理评估；或
- 执行者能够指出至少三种不同的提示词类别、彼此竞争且合理的结果，以及配对比较将如何改变决策，然后获得用户明确选择加入的同意。

对于现有 skill 的优化，默认使用零个评估代理：先运行确定性检查；如果行为仍然存在不确定性，再至多进行一到两次 with-skill 重放。规则 #5 中的一名全新上下文审查者是发布门槛，并不意味着可以创建一个审查者团队。关于 token/成本敏感性的指示会阻止重型流程，直到用户明确撤销该指示。

在生成多个 research、mining、eval 或 grading 代理之前，先将**角色**与**执行单元**区分开来：

- 每个额外的角色或审查者都必须负责一个不同的失败维度或输出。模板可用性绝不能成为增加角色的理由。
- 必要的实验组和语料分片可以共享一个维度：with-skill 组和 baseline 组需要隔离的上下文，而一个 mining 角色可能需要处理多个有界分块。在启动前，说明确切的单元总数、并发上限，以及为什么合并它们会污染比较结果或超出分块预算。默认按串行方式运行；明确的 A/B/mining 请求只授权这些必要的单元，不授权额外角色。
- 对于执行者提出而非用户明确要求的扇出，须就该数量获得用户选择加入的同意。如果交互式提问工具不可用，或用户没有回答，则采取较轻量的证据路径；沉默不构成同意。

如果某个单元既不是不同的角色/输出，也不是必要的隔离实验组/分片，则不要生成它。

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，升级处理。用户要求取消或降低评估级别时，应立即停止已经启动的配对评估代理、基线、grader、聚合和 viewer 工作。如果风险分类仍然有参考价值，则保留该分类，但只报告实际运行的证据以及尚未检查的维度；不要将未运行的重型套件描述为由该标签自动“要求”的内容。不要取消规则 #5 的单个全新上下文审查者（当其规则/契约/数量阈值被触发时），也不要取消任何为防止破坏性或外部影响而必需的安全门槛。机械式的现有 skill 迁移审计、公开 skill 清理，以及任何特定领域的安全门槛，也都独立于此路由器。

### 专用工作流：第三方 CLI 工具的 Wrapper Skills

在确定采用通用 skill 创建流程之前，先检查截至此处为止的会话是否实际上要求使用 **wrapper skill** 工作流。wrapper skill 是一种配套工具，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或 skill 包——也就是由他人编写、且用户刚刚花费一个会话让其在自己的机器上运行起来的代码。

适用信号（以下任意两项同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 会话中出现了真实、具体的错误消息，用户和 Claude 已针对这些错误制定出具体修复方案（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个整理成一个 skill”“把这个保存为一个 wrapper skill”“这样其他人就不用再经历这一遍了”“把这次 session 做成一个 skill”的话。
- 用户明确提到某个第三方工具的名称，并希望其他代理或其他人能够使用它，而不必再经历自己已经付出的学习过程。

不适用信号（改用上面的通用工作流）：

- 用户想要为某个他们准备从头开始编写的内容创建 skill。
- 会话进展顺利——没有值得提炼的实际摩擦。
- 该 skill 封装的是用户拥有或控制的服务（这是他们自己的代码；应编辑源代码，而不是进行封装）。
- 这个“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当 wrapper skill 工作流适用时，保留上面选定的验证级别。创建 wrapper 就是在创建一个新的 skill，因此属于第 3 级。**不要**继续阅读下面的通用创作部分；跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流——其任务是从当前对话中挖掘安装流程、已修复的 bug 以及做出的设计决策，并将这些挖掘结果转化为一个完整、自包含的 wrapper skill，使其他用户无需重新经历调试会话即可安装并受益。

wrapper skill 工作流有自己的架构契约、代码模板和第 3 级验证协议——由于其产物是用户的安装状态，而不是一个可以轻易断言的文件，它会替代不兼容的通用测试用例机制；这并不意味着降低工作级别。运行证据计划所选定的兼容通用步骤；通用的配对评估步骤仍然需要进行重型评估授权门控。记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库根目录——这里的裸相对链接曾经在该 skill 移入一个套件后失效过，这正如下面的跨 skill 引用规则所警告的那样），它是对 Tencent IMA skill 的封装，按照这一确切工作流从真实会话中提炼而成。

### 专用工作流：从对话历史中丰富 Skill

在提交通用 skill 创建流程之前，检查当前会话是否实际上是在请求**将过去的对话提炼为一个 skill**。当用户在多次 Claude Code / Codex 会话中一直调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这种方式非常有用。

**必须有明确的来源意图。** 长时间持续的对话、最近完成的调试任务，或 `use skill-creator to optimize <skill>`，都不构成打开本地历史记录的同意，也不是进入此工作流的理由。对于普通更新，直接使用当前对话。只有当用户明确要求挖掘/提炼更早的本地对话，或指定特定的历史会话作为来源材料时，才进入对话挖掘流程。

适用信号（必须全部满足）：

- 用户明确将本地/过去的对话历史指定为输入，例如“挖掘我的聊天记录”“从之前的会话中丰富这个 skill”，或“把以前的对话沉淀到 skill 里”。
- 已知或已确认来源会话以及时间/范围边界。
- 目标输出是可复用的知识或代码资产，且无法仅根据当前对话和现有 skill bundle 表达。

不适用的信号（改用上面的通用工作流）：

- 用户正在根据单个提示或想法创建全新的 skill。
- 用户要求优化现有 skill，但没有要求读取过去的本地历史记录。
- 相关的修正和证据已经存在于当前对话中。
- 用户希望为刚安装的第三方 CLI 工具封装一层包装器（使用上面的 wrapper-skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的对话导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件。
- 来源材料是一批用户已经认可的已完成制品，而不是对话——使用下面的制品语料提炼工作流。

当对话挖掘工作流适用时，保留上面选定的验证级别。新建的挖掘型 skill 为第 3 级；丰富现有 skill 时，只有在满足该级别能力边界的情况下，才保持所选级别。**不要**继续阅读下面的通用编写部分；跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流：它发现获批准的本地历史记录，对其进行脱敏和分区，仅运行语料库所支持的挖掘流程，并在验证后提升经过审查的候选内容。

对话挖掘工作流拥有独立的架构契约、代理提示词、模板和验证协议。该协议实现了所选级别的专用机制；根据证据计划运行所选的兼容通用步骤，将繁重的通用步骤置于授权门槛之后，并记录任何替代方案。它是将经过明确批准的对话历史转化为 skill 可复用知识库的规范方式。

### 专用工作流：从获批准的制品语料库中提炼用户偏好

在提交通用流程之前，检查当前会话是否要求**从用户认可的一批已完成制品中提取其真实偏好**——例如已批准的 HTML 报告页面、生成的文档和设计。这是第三种提炼来源，与前两种不同：材料是**产品，而不是对话**；输出是**可执行的品味**（明确的原则、量化的参数和词汇），而不是知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的成果，并说“这些都是我认可的样例” / “你来学到底什么是我想要的” / “extract my preferences from these approved examples”。
- 一个品味校准技能（报告生成器、文档样式设计器、演示文稿构建器）拥有不断增长的已批准样例库，而用户要求让技能从中*学习*，而不只是将其编入索引。
- 用户抱怨之前的更新“只加了示例”——只是整理了样例，却没有改变技能的行为。

不适用的信号：源材料是对话/修正，而不是获得认可的成品（使用 conversation-mining）；样例并未得到用户本人认可（认可资格是准入门槛——先询问）。

适用时，保留上方选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新的语料库衍生技能属于第 3 层；向现有技能添加实质性的新决策能力也属于第 3 层。专用协议实现所选层级的语料库机制，不会降低其层级；根据证据计划运行兼容的通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代方案。其核心原则同样适用于向现有技能添加材料的任何时候：**编目 ≠ 蒸馏**——在语料库表中登记一个样例，并不会改变技能下一次运行时的行为；对每一项新增内容都要问：“*这会改变一条决策规则吗？*”，并且在所有写入内容的答案都是否定时，不得宣布蒸馏会话已完成（方法论案例 15）。该工作流的主线是：对**所有**成果进行脚本提取的定量比较（每种模式至少达到 3 个成果的阈值，并为所声称的恒定项检查例外列表）→ 带有证据锚点的分层归纳 → 写入决策规则层（区分不变量与依赖语域的变量）→ 独立的完整性审计（长期纪律 #5）→ 回归审计。

### 先验成果研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——才是技能有价值的原因。没有任何公共代码仓库能够提供这些内容。但用户也不应浪费时间重新发明基础设施（API 客户端、身份验证流程、速率限制），因为已经存在成熟的工具。先验成果研究旨在为基础设施层寻找可复用的构建模块，让技能能够专注于编码用户独有的方法论。

**两个轴，不要混淆。** 本节为*基础设施*层寻找来源（可复用的工具 / MCP / 库 / 现有技能）。*方法论*层本身有两个输入：用户的私有优势（只属于用户本人，无法检索）**以及该领域既有的最佳实践 / 科学知识，你应根据长期纪律 #3 默认将其检索到上下文中。**找到合适的工具，并不能免除第二项要求——一个采用了图表库、却从未吸收 Cleveland/Bertin 理论的可视化技能，其能力上限仍然只是你预训练中已有的水平。两者都要做。

**按以下顺序搜索这些渠道。** 默认在线检索。只有在上方的重度评估/代理预算门槛确认确实存在相互独立的未知信息后，才使用子代理；公共来源渠道不是默认的并行搜索组合。

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **实时对话或明确批准的历史记录** | 用户已验证的工作流、经过验证的 API 模式、调试期间做出的修正 | 直接使用当前对话。只有在通过上方的明确来源门槛后，才搜索更早的本地历史记录；随后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有 skills | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区 skills | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 面向同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI 包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己的已验证模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终优先——公共工具是构建模块，而不是替代品。在竞争激烈的领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**倾向于合并/扩展，而不是新建，并且要扫描每一个 skill 根目录——不要只扫描 `~/.claude`。** 当渠道 1-3 发现已有 skill 与请求的领域存在重叠时，通常正确的做法是扩展或合并到其中——**但如果它位于无关项目的工作树中，方向则相反：应当从中汲取内容，加入你正在构建的 skill，而不是合并到其中**（参见上方扩展与新建检查中的项目级案例）（一次真实的“新建 skill”任务最终变成了“让现有的提取器充当新归档器的提取阶段”），而不是发布一个在相同触发条件下形成竞争的并行 skill——两个重叠的 skill 会争夺触发机会并使用户困惑。搜索时，**应发现安装根目录，而不是凭记忆列出目录**——使用扩展与新建部分中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会遗漏源代码仓库、市场克隆和插件缓存，因为其中的 skill 目录是以 skill 命名的；运行覆盖范围检查，不要只相信这句话）：**每个项目自身的 `.claude/skills/`** 都是凭记忆列出的目录清单最容易漏掉的根目录，因为该项目之外没有任何地方会引用它。用户已经安装在*任意位置*的 skill 是最有价值的先例，而项目本地的 skill 往往最成熟：它是针对真实工作编写的。

**如果发现公共 MCP 服务器或 skill，请克隆并进行验证——不要盲目信任 README：**

1. **阅读实际源代码**——许多项目的 README 写得很完善，但代码库本身却很空洞
2. **验证身份验证方式**——是否与 API 实际采用的身份验证方式一致？（X-Api-Key headers、Bearer 还是 OAuth——很多项目在这里会出错）
3. **检查测试覆盖率**——没有测试 = 原型，而不是生产级项目
4. **检查维护情况**——最后提交日期、未解决 issue 数量、对 bug 报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有软件的使用产生冲突
7. **检查依赖规模**——庞大的依赖树会带来冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用它，在其上构建**——安装 MCP，然后将 skill 构建为编码用户方法论的工作流层 |
| 存在部分 MCP 或 SDK | **扩展**——将其用于基础设施，在 skill 中补齐缺口 |
| 公共 skill 覆盖相同领域 | **仅用于获取结构方面的灵感**——竞争领域中的公共 skill 按定义都是通用的。用户的优势在于其私有 SOP |
| **存在能够提供你正在构建的功能子能力的互补 skill** | **打包它**——将互补 skill 的自包含资源复制到你的包中，并完成连接。不要依赖用户预先安装该 skill。参见下文的“互补 Skills” |
| 没有任何公共资源 | **从头构建**——在编写完整 skill 之前，先验证 API 访问模式是否可行（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——一个由你掌控、耗时 2 小时的自定义实现，胜过一个集成摩擦大且存在上游风险的“成熟”工具 |
| 用户有意取代已安装的 skill（分支版本、加固版） | **随附 supersede kit 一起发布**——参见下文的“共存与优先级” |

#### 共存与优先级（有意重叠）

将内容合并到现有 skill 中，是解决重叠问题的默认方式（如上所述）。但当用户*有意*发布一个与已安装 skill 存在重叠的 skill——例如官方插件的分支版本、经过加固的内部版本——两个条目会以相似的描述出现在 skill 列表中，Claude 将随机在它们之间进行路由。请按逐步升级的顺序解决这一问题：如果重叠是意外的，就重命名；添加描述中的决胜说明（“取代 X——当两者同时出现时，始终使用此 skill”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式 supersede kit 写入 skill——这是一个基于同意的 SessionStart 路由钩子，仅会安装在确实存在竞争者的机器上，拒绝在其他机器上安装，并且如果任一方消失则自动停用。机制、决策表、SKILL.md 示例措辞以及沙箱验证见：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。本 skill 还针对官方 skill-creator 插件对同一 kit 进行了实际使用验证（参见顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄无声息地输给了*已安装技能群体*的触发竞争。** 一个技能所处的领域（图像生成、PDF 处理、仪表板）通常已经有多个已安装技能，因此新技能可能会失去对所有这些技能的自动路由。**所以要尽早验证触发——内容写得好并不意味着构建工作就完成了。** 草稿完成后，通过 `claude -p` 运行几个符合实际的查询，并检查新技能是否真的能**胜出**；如果没有，**明确指出它输给了哪个具体竞争者**（不同查询可能会输给不同技能）。接下来需要了解两点：(1) **在竞争拥挤的槽位中，仅靠正文并不总能胜出**——解决阶梯是：重命名 → 通过描述进行平局决胜 / `SUPERSEDES` → 手动调用 → SessionStart 路由钩子（属于结构性方案；会修改全局配置，因此需要用户明确同意，对待方式与 `--no-verify` 相同）；以及 (2) **解决方案取决于竞争者的作者**——竞争者是*第三方*的 → 接受手动调用或路由钩子；竞争者是*你自己的* → 将它们合并/整合为一个，不要让你的两个技能争夺同一个触发条件。（完整的解决阶梯见 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要只是指引，不要独立扩展。）记录所选择的路径（例如添加一条“激活”说明：“手动调用，竞争者为第三方”），可以避免下一次会话重新争论这个问题。（方法论案例 13）

##### 互补技能（打包，而不是依赖）

当你构建的技能涉及一个已有的互补技能所在的领域时，有两个选择：

- **依赖它已被安装**：脆弱——用户可能没有安装它，或者安装的是不同版本。每一次依赖缺失导致的失败，根源都在于这个选择。
- **将它打包进来**：把互补技能中自包含的资源（脚本、模板、参考文档）复制到你自己的包中，并将它们连接起来，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包进来。** 以下情况尤其重要：
- 状态栏 / UI 渲染脚本（例如，`statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证 / 清理脚本
- 通用数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。与其依赖用户先运行 `statusline-generator`，不如由配置文件设置技能打包 `statusline.sh`，并在 `claude-profiles-init` 期间将其连接到每个新配置文件中。这两个技能仍然可以独立发挥作用，但包装技能能够独立运行。

**反模式**：在你的 SKILL.md 中写下“先运行 `other-skill` 的安装程序”。这会将依赖转嫁给用户，并造成脆弱的安装顺序。应改为打包。

研究完成后，通过 **AskUserQuestion** 呈现研究结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，优先考虑采用成熟的基础设施来处理底层连接工作，并在其上构建自定义逻辑来实现方法论层——价值就在这里。

### 访谈与研究

主动询问有关边界情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在这些内容理清之前，先不要编写测试提示词。

在研究有帮助时检查可用的 MCP（搜索文档、查找类似技能、了解最佳实践）。默认情况下以内联方式开展研究。仅针对独立且尚未解决的问题使用子代理，绝不要因为工具可用就自动并行分发任务。准备好相关上下文，以减少用户负担。

### 编写 SKILL.md

根据用户访谈结果，填写以下组件：

- **name**：技能标识符
- **description**：何时触发、技能执行什么操作。这是主要的触发机制——需要同时包含技能的功能，以及应在何种具体场景下使用它。所有“何时使用”相关的信息都放在这里，而不是正文中。注意：目前 Claude 有“触发不足”的倾向——在技能有用时也不使用它。为解决这一问题，请让技能描述稍微“积极”一些。例如，与其写成“如何构建一个简单快速的仪表板，用于展示 Anthropic 的内部数据”，不如写成“如何构建一个简单快速的仪表板，用于展示 Anthropic 的内部数据。只要用户提到仪表板、数据可视化、内部指标，或希望展示任何类型的公司数据，即使他们没有明确要求‘仪表板’，也务必使用此技能。”

  **控制长度：description 硬性上限为 1024 个字符，超过后验证会失败。** 这与上面的“积极”建议直接存在冲突——你添加的每个触发短语都会占用覆盖范围预算，因此应在扩展之前测量，而不是凭感觉：使用 `len(description)`，不要凭直觉判断。真正容易踩坑的并不是第一版（它通常离上限还很远），而是*多年后的更新*，因为新增触发范围后可能会使描述变长：成熟的描述通常只剩几十个字符的余量，此时**添加一个触发条件就意味着必须删除已有内容来腾出空间**。请有意识地做出这个取舍，并在提交信息中说明，因为悄无声息地删掉触发短语实际上会缩小技能的触发范围，而只有等它不再为某人触发时才会有人注意到。（实际中曾出现过这种情况：一次更新为新覆盖的故障模式添加了触发条件，使描述达到 1280 个字符，经过两轮压缩才降到 1003——代价是删掉了三个原有触发短语。这个决定本应明确记录，而不是在与验证器反复较量时才被发现。）必须删减时，优先删掉那些仍可通过同义词或相邻短语触达其场景的短语；保留没有其他入口的短语；并记住，正文中的限定语（例如“在平台 X 和 Y 上”、括号中的枚举）通常比独立的触发短语更容易删掉——正文可以从主体内容中重新推导出来，而触发短语无法重新推导。
- **compatibility**：必需的工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### Skill 编写指南

#### Skill 的构成

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。在 `---` 标记之间使用这些字段配置 skill 行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必填 | 描述 |
|-------|----------|-------------|
| `name` | 否 | Skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 建议 | Skill 的功能以及使用时机。Claude 使用此字段来决定何时应用该 skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在分叉的子代理上下文中运行。** 请参阅下方的“Inline 与 Fork：关键决策”——选错会导致 skill 无法正常运行。 |
| `agent` | 否 | 在设置 `context: fork` 时使用的子代理类型。可选值为 `Explore`、`Plan`、`general-purpose`，或来自 `.claude/agents/` 的自定义 agent。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 可阻止 Claude 自动加载此 skill。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false` 可将其从 `/` 菜单中隐藏。适用于用户不应直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略该字段可让 skill 在用户权限设置的控制下获得完整的工具访问权限。设置该字段会不必要地限制 skill 的能力。 |
| `model` | 否 | 此 skill 激活时使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指示预期的参数。例如：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此 skill 生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** Skill 内容中的 `$ARGUMENTS` 会被用户在 skill 名称后提供的文本替换。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### Inline 与 Fork：关键决策

**这是设计 skill 时最重要的架构决策。** 选错会悄无声息地破坏 skill 的核心能力。

**关键限制：子代理无法再生成其他子代理。** 以 `context: fork` 运行的 skill（作为子代理）**无法**：
- 使用 Task 工具生成并行探索 agent
- 使用 Skill 工具调用其他 skill
- 编排任何多 agent 工作流。

**决策指南：**

| 你的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **Inline**（无 `context`） | 子代理无法生成子代理 |
| 调用其他 skill（Skill 工具） | **Inline**（无 `context`） | 子代理无法调用 skill |
| 运行 Bash 命令以使用外部 CLI | **Inline**（无 `context`） | 主上下文中拥有完整的工具访问权限 |
| 执行单一的专注任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境整洁 |
| 提供参考知识（编码约定） | **Inline**（无 `context`） | 指南可以丰富主对话 |
| 被其他 skill 调用 | **Fork**（`context: fork`） | 必须作为可被生成的子代理 |

**编排器 skill 示例（必须使用 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专家 skill 示例（正确使用 fork）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，无 task）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skill 应当是**正交的**：每个 skill 负责一个关注点，并通过组合协同工作。

**模式：编排器（inline）调用专家（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（没有 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，在隔离的子代理上下文中运行
3. 每个 skill 只有一个职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法论，而不是重复代码

##### 流水线交接（顺序 Skill 链式调用）

除了编排器/专家组合之外，skill 通常还会形成**顺序流水线**，其中一个 skill 的输出会成为下一个 skill 的输入。每个 skill 在完成工作后，都应主动建议逻辑上的下一步。

**模式：在 SKILL.md 末尾添加“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**现实世界中的管道示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
read-claude-code-history → continue-claude-code-work
```

**管道交接规则：**
1. 每次交接都必须通过 AskUserQuestion **由用户选择启用** — 绝不能在未询问的情况下自动调用下一个 skill
2. 仅当输出自然地作为另一个 skill 的输入时才提出建议 — 不要强行建立关联
3. 包含一个“不了，谢谢”选项 — 用户可能不需要完整的管道
4. 建议中应解释为什么下一步有帮助（例如：“ASR 输出通常包含识别错误”）
5. 最多保留 1-2 个建议 — 选项过多会造成决策疲劳

**何时添加交接：** 询问“这个 skill 的输出是否通常会成为另一个 skill 的输入？”如果是，则添加一个“下一步”部分。如果关联很少见或牵强，则不要添加。

**反模式：** 串联没有自然数据流的 skill。`pdf-creator → youtube-downloader` 毫无意义。管道必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**绝不要为可以自动检测的能力添加手动标志。** 不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：** 自动检测能力，由用户决定范围。skill 应发现自己能够做什么并据此采取行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | You can invoke | Claude can invoke | Subagents can use |
|-------------|----------------|-------------------|-------------------|
| (default) | Yes | Yes | No (runs inline) |
| `context: fork` | Yes | Yes | Yes |
| `disable-model-invocation: true` | Yes | No | No |
| `context: fork` + `disable-model-invocation: true` | Yes | No | Yes (when explicitly delegated) |

#### 渐进式披露

Skills 使用三级加载系统：
1. **Metadata**（名称 + 描述）- 始终位于上下文中（约 100 个词）
2. **SKILL.md body** - skill 触发时位于上下文中
3. **Bundled resources** - 按需加载（不受限制，脚本可以在不加载的情况下执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。一个没有填充内容、包含 600 行的 skill，胜过一个遗漏关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问自己：“每个部分是否都物有所值？”如果答案是肯定的，就保留它。如果某些部分只是凑篇幅，或是在解释 Claude 已经知道的内容，就删减这些部分 — 而不是删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分到 reference 中，而不是为了人为缩短主文件而将所有内容硬塞在一起。
- 对于现有 skill，渐进式披露是一种重新定位策略，而不是删除启发式规则。旧的运行时契约必须仍可从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或审阅者记忆都不能替代运行时内容。
- 在 SKILL.md 中清晰地引用 reference 文件，并说明何时阅读这些文件
- 对于较大的 reference 文件（>300 行），应包含目录

**领域组织**：当一个 skill 支持多个领域/框架时，按变体进行组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的 reference 文件。

#### 不令人意外原则

这无需赘述，但 skill 不得包含恶意软件、漏洞利用代码，或任何可能危害系统安全的内容。如果对 skill 的意图进行描述，skill 的内容不应让用户感到意外。不要迎合创建误导性 skill 的请求，也不要创建旨在协助未授权访问、数据外泄或其他恶意活动的 skill。不过，类似“扮演某某角色”之类的内容是可以的。

#### 写作模式

指令中优先使用祈使语气。

**定义输出格式**——可以这样写：
```markdown
## 报告结构
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——加入示例很有用。你可以像这样进行格式化（不过，如果示例中包含 “Input” 和 “Output”，你可能会希望稍作调整）：
```markdown
## 提交消息格式
**示例 1：**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得构建到 skill 中的可用性模式**——以下四个结构元素反复将“能运行但令人困惑”的 skill 变成用户真正可以使用的 skill——它们是让高频使用的 skill 变得可用的具体增强措施，因此当一个 skill 具有多种模式、会运行命令或可以重复运行时，应考虑使用它们：
- **入口决策树**：如果 skill 有多种模式，请以一个简短的“用户说了 X → 使用模式 Y”映射开头，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧接在命令之后展示“你应该看到的内容”，这样模型和用户都能区分真正的成功与无声失败。
- **故障排除部分**：列出已知的失败模式及其修复方法——对于其他人将在你无法查看的机器上运行的 skill，这是最有价值的单个部分。
- **第 0 步幂等性检查**：如果重复运行可能会重复已完成的工作，请先进行一个简单的“是否已经完成？”检查，再执行任何耗时操作。

### 写作风格

尽量向模型解释事物为何重要，而不是大量使用强硬、陈旧的 MUST。尝试进行心理理论推演，并努力让 skill 具有普适性，而不是过度局限于具体示例。先写出草稿，然后以全新的视角重新审视并加以改进。

### 日期和版本引用

**保留事实日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 skill 应写成 “Suno v5.5 (March 2026)”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 August 2025，则使用旧 API”）——日期一旦过去，这种逻辑就会失效，而且没人会更新它。

规则：
- **发布日期、“最后验证”日期**：保留。这些是参考时间点，不是有效期
- **定价、排名、法律状态**：包含，但标记为易变信息（“截至上次检查约为 ~$0.035/gen”），以便读者知道需要重新核实
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠/已弃用部分记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或经常被重复改写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当相同代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省 token、具有确定性，可在不加载到上下文中的情况下执行
- **注意**：Claude 可能仍需读取脚本，以便进行修补或针对特定环境进行调整
- **用户可修改的数据存放在捆绑包之外**：如果脚本会积累用户数据（更正词典、习惯偏好、缓存），请将其存储在稳定的相对于 home 的目录下（例如 `~/.<skill-name>/`），并为其单独备份——绝不要存放在 skill 目录中。每次更新和套件迁移都会删除并重新创建 skill 安装内容，而相对于 home 的存储会原样保留。这正是一个不断积累词典的 skill 能够在完整套件迁移后实现用户数据零损失的原因

##### 参考资料（`references/`）

旨在根据需要加载到上下文中，以便为 Claude 的处理和思考提供信息的文档与参考材料。

- **何时包含**：当 Claude 工作时需要参考文档时
- **示例**：用于金融模式的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库模式、API 文档、领域知识、公司政策、详细的工作流指南
- **优点**：保持 SKILL.md 简洁，仅在 Claude 判断需要时加载
- **最佳实践**：如果文件较大（>10k 个单词），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或 references 文件中，不要两者同时存放

##### 资源（`assets/`）

不用于加载到上下文中，而是用于 Claude 生成的输出中的文件。

- **何时包含**：当 skill 需要在最终输出中使用的文件时
- **示例**：用于品牌资源的 `assets/logo.png`，用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件货架**：对于生成 artifact 的 skill，`assets` 下的 `components` 子文件夹用于存放用户批准的、逐字嵌入的片段，这些片段带有冻结的行为契约和注册表引用——参见第 4 步中的组件货架检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标受众。**以下内容描述的是 skill 面向陌生用户发布时会出现的问题。对于存放在作者自己的私有仓库中的 skill，同样的“违规”通常正是它能够正常工作的原因——真实的绝对路径能让脚本直接运行，模板中的真实账户能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 包含该 skill 的仓库是否为私有仓库），并将那里的可移植性/标识符问题降级为提示；当私有 skill 准备发布时，`--audience=public` 会强制执行严格检查。

**对于私有 skill，这些问题由所有者决定，而不是由你决定。** 不要擅自将真实路径替换为占位符、改写硬编码凭据，或在未询问的情况下“清理”示例——为了满足一条原本针对另一个发布目的而制定的规则，你会破坏一个正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，让所有者自行决定。（其设计先例是 npm 的 `"private": true`：一个已声明的目标，它会改变工具所执行的规则；之所以加入这一机制，是因为人们总是不小心发布内容。）

**面向公开分发的 skill 的关键要求**——这些 skill 不得包含特定用户或特定公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，例如 `~/.claude/skills/`
- **允许**：skill bundle 内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（严格逐字实现 Forbidden 列表的验证器会将此 skill 本身标记出来——对正常输入误报，比漏检更糟糕）：当发布者自己的名称/品牌是解决 supersede 决胜条件或进行署名所必需时，可以使用；当段落讨论的是这些路径本身时，可以使用类似 `~/.claude/skills/` 的安装路径（这是教学材料，而不是硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于当前 skill 自己的 bundle 内”——验证器和读者都会如此理解，因此，指向另一个 skill 文件的裸路径会验证失败，并误导读者。指向另一个 skill 时，应在正文中注明其所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用带命名空间的名称调用 skill（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。skill 在不同 suite 之间迁移时，裸的跨引用会静默失效——一次 suite 迁移就导致两个清理轮次中出现了 21 个失效的跨引用。

##### 版本控制

**关键要求**：SKILL.md 中不应包含版本历史或版本号：

- **禁止**：SKILL.md 中的版本章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **原因**：Marketplace 基础设施负责版本控制；SKILL.md 应包含不会随时间变化的内容

#### Reference File Naming

文件名必须无需阅读内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：仅从文件名本身，是否有人就能理解文件的内容？

有两个例外：带连字符的名称和带下划线的名称同样合适（分隔符从来不是重点——重点是名称能够自我说明）；而命名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已经由目录提供了限定信息，重命名它们会破坏各工作流之间的平行结构。

### Full-eval 测试用例（仅限单独授权的配对计划）

仅当重型评估授权门禁通过时，才进入本节。风险级别本身既不会授权也不会禁止使用此证据；明确的全流程请求不会重新界定底层变更。不要仅仅因为 SKILL.md 发生了变化就使用它。应遵循上文声明的替代契约所规定的专用工作流。

编写 skill 草稿后，提出 2-3 个现实的测试提示词 — 即真实用户确实可能会说的话。**对于作用于在线系统的 skill（正在运行的服务、已登录的客户端、生产数据），请为每个测试提示词明确副作用预算** — 例如：“仅进行只读探测并得出结论；不要执行下载 / 驱动 UI。”在“只是测试”的名义下修改在线环境是真实操作，而不是测试。通过 **AskUserQuestion** 呈现这些测试：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言 — 在运行进行期间的下一步中再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整架构请参阅 `references/eval_pipeline_schemas.md`（包括稍后添加的 `assertions` 字段）。

## 完整配对评估流程（仅限单独授权）

仅当重型评估授权门禁通过后，才运行本节。风险级别仍应根据变更所涉及的行为确定。以会影响决策的阶段执行流程，并在不确定性或所请求的基准交付物得到解决后停止；不要预先启动下游评分器、聚合或查看器工作。用户取消或降级请求会立即停止重型流程。未经授权不得使用本流程；如果专用工作流明确替代了通用机制，也不得机械地添加这些通用机制，并且不得使用 `/skill-test` 或任何其他测试 skill。

将结果放入 `<skill-name>-workspace/`，该目录应与 skill 目录处于同一级。在 workspace 内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要一开始就创建全部目录——只需随着进展逐步创建目录。

### 第 1 步：运行已批准的 with-skill / baseline 配对

对于每个已批准的测试用例，在相同的提示词和副作用预算下，运行一个 with-skill 样本及其 baseline。两个分支有意共享同一个失败轴，但需要彼此隔离的上下文；它们是必要的实验单元，而不是额外的审查者角色。启动前说明分支总数和并发上限。默认串行运行，且绝不要超过授权的单元数量。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（使用相同的提示词，但 baseline 取决于上下文）：
- **创建新 skill**：完全不使用 skill。使用相同的提示词，不提供 skill 路径，并将结果保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用 mandatory existing-skill regression gate 在首次编辑前捕获的旧版本。将 baseline 子代理指向该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 重建一个权威 baseline 后再继续；绝不要将已经编辑过的目录用作旧 baseline。**了解此比较能够解决的问题：它只衡量本轮的变化。** 如果你最想验证的能力已经存在于编辑前快照中——某个 sibling session 可以在你开始前恰好提交该修复——那么 with/old A/B 对此不具备任何判别能力；在该能力的测试中，应选择更早的 ref 作为 baseline。

为每个测试用例写入一个 `eval_metadata.json`（断言暂时可以为空）。根据每个测试用例所测试的内容，为其指定一个描述性名称——不要只使用“eval-0”。同时将此名称用于目录名。如果本次迭代使用了新的或修改过的 eval 提示词，则为每个新的 eval 目录创建这些文件——不要假设它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：在运行进行期间起草断言

不要只是等待运行完成——你可以利用这段时间开展有价值的工作。为每个测试用例起草定量断言，并向用户解释这些断言。如果 `evals/evals.json` 中已经存在断言，请检查它们并解释其检查内容。

好的断言应当能够客观验证，并具有描述性名称——在 benchmark viewer 中阅读时应清晰易懂，让人一眼看到结果就能明白每条断言检查的内容。**应针对意图编写断言，而不是针对字面上的工具路径**——例如“语音内容保留在答案中”，而不是“调用了获准的读取脚本”。如果某次运行通过另一条获准路径实现了该意图（例如读取一个已经内联了转录内容的 archive），则应判定为通过；将其判定为字面路径失败会制造错误的负例，随后你还会在错误的位置进行“修复”。主观性较强的 skill（如写作风格、设计质量）更适合进行定性评估——不要强行对需要人工判断的内容设置断言；它们真正的验证路径（历史任务重放、带 write-back 习惯的 production-as-eval、渲染后人工审查）列在“Capture Intent”的问题 4 中。

起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试。

### 步骤 3：随着运行完成，捕获计时数据

每当某个子代理任务完成时，你会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们会通过任务通知传递，且不会在其他地方持久化。通知到达后应立即处理每条通知，而不是尝试批量处理。

### 步骤 4：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分** — 启动评分子代理（或直接评分），让其读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 中的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是凭肉眼判断——脚本更快、更可靠，也可以在多轮迭代中复用。**但客观的 grep/脚本断言也有两面性**（相同词语不同含义造成的误命中、措辞差异造成的漏检），因此**基准测试通过率只是一个信号，而不是最终结论**：要抽查每条断言实际匹配到的内容，并留意基线运行是否暴露出 skill 本身的事实错误（出现“等等，数据明明就在 API 里”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **聚合为基准测试** — 从 skill-creator 目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及均值 +/- 标准差和差值。生成 `benchmark.json` 时如果是手动生成，请参见 `references/eval_pipeline_schemas.md` 了解查看器所需的确切架构。将每个 with_skill 版本放在对应的 baseline 版本之前。

3. **进行分析员检查** — 阅读基准测试数据，并找出聚合统计数据可能掩盖的模式。查看 `agents/analyzer.md` 中的“Analyzing Benchmark Results”部分，了解需要关注的内容——例如无论是否使用 skill 都总能通过的断言（无区分度）、高方差评估（可能不稳定），以及时间/令牌的权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 轮及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器自行脱离**：进程仍然存活，但没有任何程序在监听——使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或 curl 该 URL（失败）；这里“没有日志输出”并不是可用的信号，因为上面的启动命令已将其重定向到 `/dev/null`。终止该进程，并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或者环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击“Submit All Reviews”时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** **告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

“Outputs”选项卡一次显示一个测试用例：
- **Prompt**：提供的任务
- **Output**：技能生成的文件，可能时会以内嵌方式呈现
- **Previous Output**（第 2 次及之后的迭代）：显示上一次迭代输出的折叠区域
- **Formal Grades**（如果运行了评分）：显示断言通过/失败情况的折叠区域
- **Feedback**：输入框，输入内容时会自动保存
- **Previous Feedback**（第 2 次及之后的迭代）：显示在输入框下方的用户上次评论

“Benchmark”选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每项评估的细分结果和分析人员的观察。

可以通过上一个/下一个按钮或方向键进行导航。完成后，点击“Submit All Reviews”，所有反馈都会保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们完成后，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}

  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。将改进重点放在用户提出了具体问题的测试用例上。

完成后，终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进 skill

这是循环的核心。根据证据计划进行改进：对于 Tier 1，使用权威事实和确定性检查；对于 Tier 2，使用 1–2 个命名的行为重放；或者在单独的重型评估门控机制于任意层级授权时，使用经过用户审核的成对结果。未经该授权，不要将成对评估产物引入默认的 Tier 1/2 路径。

### 如何思考改进

1. **从反馈中归纳总结。** 这里正在发生的事情，从宏观上看，是我们试图创建能够被使用一百万次（也许真的能，也许更多，谁知道呢）的 skill，以应对许多不同的提示。在这里，你和用户只是反复迭代少数几个示例，因为这样能更快推进。用户对这些示例了如指掌，因此可以快速评估新的输出。但如果你和用户共同开发的 skill 只能适用于这些示例，那它就是无用的。不要加入琐碎、过拟合式的修改，也不要加入压制性很强的 MUST；如果某个问题一直顽固存在，不妨尝试换用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，说不定就能得到很好的结果。

2. **保持提示精简，但不要删除契约。** 删除那些没有发挥作用的内容，但要把对现有 skill 的每次删除都视为潜在回归，直到新旧版本审计将其归类为止。将详细但可复用的行为移入直接链接的参考文档；不要只把它留在评估结果、变更日志或你的记忆中。阅读完整记录，而不只是最终输出——如果 skill 导致了无效的工作，就简化指令并重新运行旧的能力用例，而不是想当然地认为字数越少行为就越好。

3. **解释原因。** 尽力解释你要求模型执行每件事背后的 **原因**。如今的 LLM 已经*很聪明*。它们具备良好的心智理论能力，在获得良好 harness 的情况下，可以超越机械地遵循指令，真正促成事情发生。即使用户的反馈简短或令人沮丧，也要努力真正理解任务，理解用户为什么写下他们所写的内容、他们实际写下的内容意味着什么，然后将这种理解传达进指令中。如果你发现自己在用全大写的 ALWAYS 或 NEVER，或使用非常僵化的结构，这是一个危险信号——如果可能，应当换一种方式来阐述并解释理由，让模型理解你要求这件事的重要性。这是一种更人性化、更强大且更有效的方法。

4. **寻找重复的工作——既要查看评估记录，也要查看 skill 所提炼自的对话。** 阅读测试运行的记录，注意各个子代理是否都独立编写了相似的辅助脚本，或采用了相同的多步骤方法来处理某件事。如果 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈信号，说明该 skill 应该捆绑这个脚本。将它编写一次，放入 `scripts/`，并告诉 skill 使用它。这样可以避免每次未来调用都重新发明轮子。同样的信号也隐藏在你从中提炼 skill 的源对话里——那次会话中哪怕只编写过一次的代码，未来每次运行都必须重新编写；不要等到评估运行证明这种重复（跳过评估循环的 skill 永远不会得到这种证明——创建流程第 4 步中的 Scripts 检查点正是捕捉这类问题的地方）。

5. **逐字回写修正——在同一会话中，同时更新两个层级。** 对于经过品味校准的 skill，用户的修正就是评估集，但前提是这些修正写入了未来运行时会读取的位置。以下两个属性会使回写逐渐收敛：(a) **逐字记录修正内容**，不要改写或概括——确切措辞包含了概括会抹平的校准信号（“绝对禁止这种东西”传达了一个硬性边界；“用户偏好更少的跳转”则没有）。将这些话原样写入它们所修正的规则中，并附上日期。(b) **在修正发生的同一会话中，同时在两个层级进行回写**——修正产物以及 skill 的规则/参考内容/组件；只修正产物的做法对所有未来运行都不可见，而拖到“以后”处理的修正通常永远不会落地。在回写时，检查 skill 自身的文本是否*教会了*刚刚被禁止的反模式——修正往往意味着现有指令是错误的，而保留旧建议就必然会导致问题重现（真实案例：一个决策页面契约建议使用跳转式的“goto 锚点跳到所引用的图”；用户明确禁止了这种做法，因此回写时必须修改旧句子，而不仅仅是在旁边新增一条规则）。当被修正的是交互片段时，回写的最后一步是将其提升到货架中——参见步骤 4 中的 Component-shelf check。

这项任务相当重要（我们正在努力让这里每年创造数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，认真斟酌。我建议先写一版修订稿，然后重新审视并加以改进。请尽最大努力设身处地理解用户想要什么以及需要什么。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据确实留下了多种选择时才提问。对于 Tier 2 或 Tier 3，当用户反馈暴露出有意义的设计分歧时，通过 **AskUserQuestion** 提出改进计划：

```text
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险层级，因为这会改变实现范围；选择 D 则不会。每个选项只授权其中明确列出的范围/证据变更。除非明确列出并且通过单独的重型评估/扇出门槛，否则它不授权成对的基线、评分器、基准测试、查看器或额外角色。

### 迭代循环

改进 skill 后：

1. 将改进应用到 skill
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **Tier 1 默认流程：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配的子类型证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归测试。除非单独授权了配对计划，否则不要创建迭代工作区。
   - **Tier 2 默认流程：**仅重新运行同一组 1–2 个指定的 with-skill 示例和窄范围检查。除非单独授权了配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任意层级单独授权的通用配对运行：**将所有获批的测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 skill，基线始终是 `without_skill`；对于现有 skill，不可变的原始编辑前版本在每次迭代中始终作为保留基线。紧邻的上一迭代可以作为补充，但绝不能替代原始基线。
3. 在实质性规则、契约或数字发生变化后，执行纪律 #5。对于单独授权的通用配对运行，还要启动 eval reviewer，并使用 `--previous-workspace` 指向上一迭代；专用工作流则使用其声明的 reviewer 机制。
4. 对于单独授权的通用配对运行，等待用户查看新的查看器结果；否则，根据默认层级的证据作出决定，除非仍存在需要用户实际选择的问题。
5. 阅读新的证据或反馈；如果它证伪了当前版本，则再次改进，并在同一层级重复执行。

用户请求的取消或降级在任务剩余期间持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 `AskUserQuestion` 作为检查点：

```
迭代 [N] 完成。结果：[pass_rate]% 的断言通过，[与上一迭代的差异]。

建议：[继续 / 接受 / 恢复]，因为[基于差异和剩余反馈给出一行原因]。

选项：
A) 继续迭代 — 我认为仍有进一步改进的空间
B) 接受此版本 — 已经足够好了，让我们进入打包阶段
C) 恢复到上一迭代 — 这一轮让结果变差了
D) 运行盲测比较 — 严格比较此版本与上一版本
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（看起来一切都很好）
- 你无法取得有意义的进展

## 高级：盲测比较

如果需要更严格地比较 skill 的两个版本（例如，用户询问“新版本真的更好吗？”），可以使用盲测比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。其基本思路是：将两个输出交给一个独立代理，但不告诉它哪个对应哪个版本，然后由它判断质量。接着分析获胜版本胜出的原因。

## 描述优化

SKILL.md 前置内容中的 description 字段是决定 Claude 是否调用某项技能的主要机制。创建或改进技能后，应主动提出优化 description，以提高触发准确性。

### 步骤 1：生成触发评估查询

创建 20 条评估查询，混合包含应触发和不应触发的查询。将其保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实，并且是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要使用抽象请求，而要使用具体、明确且包含足够细节的请求。例如，可以包含文件路径、用户工作的个人背景、列名和值、公司名称、URL 等。可以有一些全小写、包含缩写或拼写错误，或者使用口语化表达。使用不同长度的查询，并重点关注边界情况，而不是让查询一目了然（用户之后会有机会确认这些查询）。

不好的例子：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好的例子：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**的查询（8–10 条），要考虑覆盖范围。应使用同一意图的不同措辞——有些正式，有些口语化。包含用户没有明确提及技能名称或文件类型、但显然需要使用该技能的情况。加入一些不常见的使用场景，以及该技能与另一个技能存在竞争、但应由该技能胜出的情况。

对于**不应触发**的查询（8–10 条），最有价值的是近似匹配——这些查询与该技能共享关键词或概念，但实际需要的是其他功能。应考虑相邻领域、模糊措辞（朴素的关键词匹配可能会触发，但实际上不应触发），以及查询涉及该技能能够完成的某些操作、但在当前上下文中更适合使用其他工具的情况。

需要重点避免的是：不要让不应触发的查询显得明显无关。用 `"Write a fibonacci function"` 作为 PDF 技能的否定测试过于简单——它无法测试真正的边界情况。否定案例应当确实具有迷惑性。

### 步骤 2：与用户一起审查

使用 HTML 模板向用户展示评估集：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目组成的 JSON 数组（不要在其外层加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的 description
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——如果存在多个文件（例如 `eval_set (1).json`），请检查 Downloads 文件夹以找到最新版本。

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期查看进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示词中的模型 ID（即为当前会话提供支持的模型），这样触发测试才能匹配用户实际体验到的效果。

运行期间，定期查看输出内容，向用户更新当前进行到哪一轮以及分数表现。

这会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude，根据失败的情况提出改进方案。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开 HTML 报告，展示每轮的结果，并返回包含 `best_description` 的 JSON——该结果根据测试集分数而不是训练集分数选出，以避免过拟合。

**如果检测到完全静默，该循环会在第 1 轮后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中代码级别的保护措施，而不仅仅是建议；它可以区分“第 1 轮中所有 should-trigger 查询都触发次数为零”这一情况的两种原因：

- `exit_reason: "infra_error: ..."` —— 某些查询执行时抛出了异常（`claude` CLI 不在 PATH 中、超时时间过短、网络中断），而不是正常返回“未触发”。该检查**优先进行**，并且只要错误计数不为零，即使几十次运行中只有一次偶发失败，也会刻意触发——无论多么罕见的崩溃，都比“什么都没触发”更具体、更容易采取行动，而修复方向是环境问题，不是重写描述。消息中的比例（例如 `3/15`）体现了严重程度：较大的比例意味着“停止运行，修复环境”；较小的比例，同时伴随大量干净的 0-trigger 运行，则意味着环境可能存在值得检查的轻微偶发故障，且描述本身也可能确实存在问题——两方面都要检查。无论哪种情况，都要检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` —— 只有在上面的分支排除了所有执行错误后才会进行检查，因此这意味着每个 should-trigger 和 not-should-trigger 查询都**确实运行了**，但仍然全部触发零次（这正是通过零分母默认值实现的“precision=100%”实际含义：不是“完美”，而是“没有可供相除的对象”）。探针实际上没有测量到任何东西——在接触描述之前，先诊断竞争者冲突或低阈值领域（如下所述）。

这两项检查**仅针对第 1 轮**运行，并且**仅在 should-trigger 查询触发次数为零时**运行——第 1 轮表现较弱但并非零触发（例如 1/9 次触发）是另一种可能可以恢复的情况，因此会刻意留给后续迭代。`degenerate_harness` 还要求 not-should-trigger 查询的触发次数也为零：如果描述只是极性反转——漏掉了所有正例，却意外匹配了多个负例——则说明探针已被证明能够工作，`improve_description` 也有实际的梯度可以利用，因此保护机制不会中止这种情况（它只会中止真正失效的探针）。此外，它还要求任意一侧都没有执行错误——一个抛出异常的 not-should-trigger 查询实际上并未运行，因此不能将其“0 次触发”用作探针失效的证据；这正是该情况会被路由到 `infra_error` 的原因。无论哪种情况，循环都会立即中断，并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会抑制任何内容），而退出原因则是一个信号，表明不应将本次运行的数值解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了完整的 5 轮循环；两个完整迭代——每个都是完整的评估批次，耗时数分钟，并调用了几十个 `claude -p` 子进程——都返回了 precision=100%/recall=0%/相同的分数，直到有人查看这些数值时才发现问题，而每个 should-trigger 和 not-should-trigger 查询都完全没有触发。仅凭第 1 轮就可以诊断出故障；第 2 轮及之后的迭代没有提供任何额外信息。）当任一退出原因触发时，HTML 报告也会显示横幅，因此浏览器视图会携带与 JSON/stderr 相同的信号，而不只是存在于那两个可见度较低的渠道中。（该保护机制的早期草案只检查 should-trigger 的触发情况；两轮独立审查——每轮都由一个新的代理执行，第二轮检查第一轮的修复，而不是重新覆盖旧问题——构造出了极性反转的反例、基础设施与描述之间的歧义、负例侧错误的缺口，以及由此暴露的既有 `--holdout 0` 报告崩溃问题；这些问题在发布前均已修复。）

这个保护机制无法覆盖一种情况：当使用 `--runs-per-query 1` 时（默认值为 3），对于一个确实只有约 50% 触发率、且本应触发的查询，仅凭随机因素就很可能读到 0/1，从而因为噪声而触发保护机制，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询的每次重复运行结果全为零”成为强信号的原因——如果你将其调低，这个保护机制的误报风险也会随之上升。

**在信任 `best_description` 之前，先对测试框架做合理性检查——即使上面的两个保护机制都没有触发，它仍可能返回空洞的结果。** 这两项检查只能捕获第 1 次迭代时的*彻底*失败；测试框架也可能在全部 5 次迭代中持续产生微弱但非零的信号，却始终无法触发其中任何一项。如果第 1 次迭代之后，每次迭代报告的 **召回率都持续接近 0%，且分数完全相同或几乎相同**，这说明存在与保护机制无法排除的同一个根本问题——所谓“胜出”的描述通常只是第 1 次迭代结果附近未发生变化的噪声。在应用任何 `best_description` 之前，亲自运行一个明显应该触发的查询，并确认召回率 > 0。跨迭代保持不变的召回率结果意味着测试框架存在隐藏变量（常见原因是该技能输给了已安装的竞争技能——见下文的“共存”部分）——不要应用它的“最佳”结果；应手动编写描述，并使用真实探针验证。（方法论案例 12、14）召回率为 0 还有第二个根本原因，与输给竞争技能不同：该技能的任务领域属于*低阈值*领域——模型会自行完成任务，从不查阅任何技能——这一点在下文*技能触发机制的工作方式*末尾有详细说明。在采取行动之前，要区分这两种情况，因为修复方式正好相反：竞争技能问题通过优先级/取代关系修复，而低阈值领域则应彻底放弃将触发探针用于生产环境评估。

**当你使用 `claude -p` 自行探测触发情况时，要收集运行过程中的所有技能调用，而不只是第一个——并记住，工具调用只是代理指标。** `UserPromptSubmit`/`SessionStart` 钩子可能会在模型做出选择之前注入一个无关技能，因此“第一次出现 Skill 调用就退出”的探针会错误地报告“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“该技能的内容是否影响了输出”（模型可能读取了技能，却没有出现可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你围绕错误的结论持续优化。

### 技能触发机制的工作方式

理解触发机制有助于设计更好的评估查询。技能会以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，而 Claude 会根据该描述决定是否查阅某项技能。需要注意的重点是：Claude 只会针对自身难以轻松处理的任务查阅技能——即使描述完全匹配，像“读取这个 PDF”这样简单的单步查询也可能不会触发技能，因为 Claude 可以使用基础工具直接处理这类任务。只要描述匹配，复杂、多步骤或专业化的查询通常都能可靠地触发技能——但有一个系统性例外，即本节末尾所述的低阈值任务领域。

这意味着你的评估查询应当足够实质，以便 Claude 实际上能从查阅 skill 中获益。像“read file X”这样的简单查询是糟糕的测试用例——无论描述质量如何，它们都不会触发 skill。

**但有些 skill 无法通过这一测试，是有原因的，而这是任何查询改写都无法解决的——该 skill 的整个*职责*就是一项低门槛任务。** 上一段将问题归咎于查询（“写一个更实质的查询”）；这里则是正交的情况：阻碍触发的是 skill 的*领域*。如果某个 skill 的用途是完成 Claude 只需借助基础工具就会自行完成的事情——转换音频为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询写得非常完整（“将这个 48k 立体声 wav 降采样为适用于 whisper 的 16k 单声道”，包含完整路径），也不会触发它：模型会直接使用 `Bash`/`ffmpeg`，完全不会查阅任何 skill。查询的实质性无法解决这个问题，因为“我可以直接完成这件事”的判断针对的是*任务*，而不是措辞。

在浪费一个优化循环之前先诊断这一点：通过 `claude -p` 运行一个真实的查询，并观察模型在整个运行过程中是否*曾经*查阅过该 skill（依据上面的 ALL-skill-calls 规则），还是直接使用 `Bash` 自己完成任务。如果它从未查阅，那么触发探测在结构上就无法检测到这个 skill——无论你怎么写，召回率都大约为 0，而这个 0 衡量的是模型“我自己来做”的反射，而不是你的描述。停止针对 `claude -p` 召回率进行调优，改用真正的方式进行验证：以生产环境作为评估（用户下一次真实的、*交互式*使用——无头 `-p` 相比真实会话更偏向执行操作，并且系统性地低估触发情况），再加上输出比较，其中 skill 会生成可检查的产物。（在一个音频预处理 skill 上观察到的情况是：无头运行的 run_eval sweep 在*每一个*查询上的读取召回率都是 0——包括一个明显的“转录这段录音”查询；而手动执行 `claude -p` 探测时，模型直接使用 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个 0 衡量的是无头运行的操作偏差，而不是描述；真正的信号只会在交互式使用中出现。）

### 第 4 步：应用结果

从 JSON 输出中取得 `best_description`，并更新 skill 的 SKILL.md frontmatter。向用户展示修改前后内容，并报告分数。

## 关键：在源位置编辑 Skills

**绝 NEVER 先编辑已安装的 skill 副本。** 除非用户明确说明它们就是源文件，否则请将以下所有位置都视为已安装/运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装副本会导致更改：
- 在缓存刷新时丢失
- 不会同步到源代码管理
- 造成浪费的工作，并需要手动重新合并

**始终确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在任何编辑之前**，运行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。先定位由仓库支持的源，编辑并验证它，然后仅在用户需要立即在本地运行时，才同步已安装的副本。

**然后回答决定“同步已安装副本”是否确实属于工作的问题：运行时是否已经读取源？** 三种安装方式的行为不同，猜错要么会浪费一次同步，要么会发布一个用户下一次会话根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **符号链接**到源代码树 → 编辑内容*就是*运行时内容。不需要同步。
- **`source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本号递增只是为其他使用者记录，并不是本地激活步骤。
- **任何缓存/复制的安装方式**（来自 git 的 marketplace、通过 `cp -r` 安装）→ 运行时是一个独立副本，在新内容生效之前确实需要运行官方更新命令。

**同时要通过内容而不是版本字符串验证激活状态。** 注册表可能记录了一个磁盘上并不存在的路径或版本——有一次会话读取到的插件记录中包含了新版本号对应的缓存目录，差点据此报告更新已生效；但那个目录从未创建过，而真正的运行时路径一直是指向源的符号链接。权威检查方式是 grep 运行时文件，查找只有新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库上的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能会在你不知情的情况下提交技能 B（甚至是技能 A 的更早一轮修改）。有一次真实会话在一小时内同时遇到了这三种症状——一次 `Write` 因文件在读取后发生变化而被拒绝，以及 HEAD 在任务进行期间两次移动（方法论案例 16）。失败的根源不是冲突本身，而是过期的基线或会悄悄混合两个会话工作的覆盖式写入。长期规则如下：

1. **只要仓库在任务开始时是干净的，就从 git ref 而不是工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并将 `--baseline-origin git-ref:<sha>` 传给审计工具。从几分钟前的工作树创建的快照，可能对应一个已经不存在的树，不能作为基线。**解压到一个全新的、不存在的目录中。** 解压到已有目录时，`tar -x` 会静默覆盖同名文件，并保留归档中没有的文件；这是一个在解压时完全没有信号的混合快照，之后 `compare` 会因其与该 ref 不匹配而拒绝。同样的陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会将目录嵌套进去；如果 `mv` 被别名为 `mv -i`，目标已存在时的重命名会打印一行提示，并默认不执行，但无论哪种情况退出码都是 0（已通过实验验证）。
2. **在写入被拒绝后，或经过任何一段时间后，重新读取再写入**：检查发生了什么变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图整合进你的版本——他们的编辑通常是有原因的——然后再写入。
3. **提交前检查 HEAD *以及当前所在的分支***。`git log --oneline -1` 可以发现 SHA 是否发生移动：如果它自你的基线之后发生了变化，就要在 `verify` 之前，针对新的 ref 重新运行回归 `compare`——审计工具本来也会拒绝过期的审查（“after skill changed”），提前发现可以省去一轮。但另一个会话可能做得比推进 HEAD 更糟：**它可能在你不知情的情况下切换分支**，因为 checkout 的作用范围是整个工作树。真实发生过这样的顺序——先执行 `checkout -b feat/x`，编辑了一段时间，与此同时另一个会话执行了 `checkout main` + `pull`；随后提交落到了 **main** 上，违反了仓库“绝不直接提交到本地 main”的规则，而 feature 分支仍指向旧基线。因此，提交前检查中除了 SHA 之外，还要加入 `git branch --show-current`。如果这种情况已经发生，`git reflog` 是权威的重建依据（它会按顺序记录每个 `checkout: moving from X to Y`），而修复方式——**前提是工作树干净**——是 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：两者都是只移动引用、不会触碰工作树的操作，因此不像 `reset --hard` 那样会破坏并行会话尚未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要执行 `git add .`——另一个会话尚未提交的工作绝不能被一并带上。（这本来就是打包时的规则；在并发场景下更是如此。）
5. **每次会话结果只递增一次版本号**，而不是每一轮编辑都递增：同一会话在同一个技能上的连续多轮修改应合并为一次递增——除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），此时每个已被使用的状态都应拥有自己的版本号。

## 技能创建流程（分步）

创建或更新技能时，请按顺序执行以下步骤。仅在明确不适用时跳过相应步骤。

### 步骤 0：前置条件检查

在开始任何技能工作之前，自动检测所有依赖项，并主动安装缺失的依赖项。在工作流中途才发现缺少工具（例如打包时缺少 gitleaks、验证时缺少 PyYAML）会浪费时间并中断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖项就自动安装，并向用户提供检查清单摘要。只有满足所有阻塞性依赖项后，才能继续。 

关键阻塞项：Python 3、uv、PyYAML（用于验证/打包）以及 gitleaks（用于安全扫描）。仅当单独授权的证据计划实际运行代理评估时，claude CLI 才是阻塞项。使用显式的 uv 依赖声明运行 Python 工具，例如从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。裸 `python3` 依赖环境中已有的软件包，可能找不到 PyYAML。

### 步骤 1：通过具体示例理解技能

仅当技能的使用模式已经明确理解时，才跳过此步骤。

要创建有效的技能，必须清楚了解该技能的具体使用方式。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成示例。

例如，在构建图像编辑器技能时，相关问题包括：

- “图像编辑器技能应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能提供一些该技能的使用示例吗？”
- “用户说什么时应该触发该技能？”

为避免让用户不堪重负，避免在一条消息中提出过多问题。

### 步骤 2：规划可复用的技能内容

通过以下方式分析每个示例：

1. 考虑如何从头开始执行该示例
2. 确定应赋予 Claude 多大程度的自由度
3. 确定哪些脚本、参考资料和资源有助于反复执行这些工作流

**让具体程度与任务风险相匹配：**
- **高自由度（文本指令）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，但允许合理变体
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 步骤 3：初始化技能

如果技能已经存在，则跳过此步骤。

从头创建新技能时，必须始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个模板技能目录，其中包含正确的前置元数据、资源目录和示例文件。

### 步骤 4：编辑技能

开始编写之前，获取 Anthropic 的最佳实践文档（上文“技能创建最佳实践”中提供了链接）和方法论参考资料——即使你认为自己已经熟悉这些内容，也必须执行此操作：文档会更新，训练数据中的版本会过时，而“我基本上已经知道了”恰恰是编辑者跳过这一步、错过最新指导的状态。

编辑时，请记住，此 skill 是为另一个 Claude 实例创建的。重点关注那些对 Claude 有帮助且不明显的信息。

**现有 skill 迁移门禁——首次编辑前必须执行：**

1. 在编辑前，捕获当前完整 bundle。对于非 Git 或存在未提交更改的源，使用该工具，以便快照包含可验证的 provenance manifest：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源，从所选 ref 实例化目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   包含 SKILL.md、references、scripts、assets、workflows 以及现有 eval——不要只复制主提示词。永远不要复制已经编辑过的目录并将其标记为“before”。**使用一个之前没有解压过任何内容的目录**——重复使用一个已经包含内容的目录，会让 `tar -x` 静默覆盖同名文件，同时保留新归档中不存在的旧文件，从而生成一个混合快照；提取时不会产生任何信号（`compare` 只能在之后间接通过树哈希不匹配发现这一问题）。请参阅下方的“同一 skill repo 上的并发会话”以了解这个陷阱的更完整版本，包括基于 `mv` 的变体。
2. 梳理旧 skill 的 actor/jobs、触发上下文、运行时契约、命令/标志、失败与恢复场景、页面/域变体、随附资源以及 eval 覆盖范围。在进行结构重写前，为重要的旧版边界行为添加保留用例。
3. 编辑后，生成新旧版本对照审查：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，将最后一个标志替换为 `--baseline-origin git-ref:<ref>`。该工具会将 ref 解析为不可变提交，并根据该树验证每个包含的文件及可执行位。

   **重命名或移动 skill 目录本身**（而不仅仅是编辑其内容）会改变 `--after` 的路径，而两种基线模式都会使用该路径来确定身份——默认情况下，`compare` 会拒绝此操作（假定 `--before`/`--after` 是意外不匹配），并报错 `pre-edit snapshot source identity does not match the edited skill`。添加 `--renamed-from <old-path>` 以明确声明此次重命名（对于 `snapshot`，这是 `--source` 指向的路径；对于 `git-ref:`，这是 skill 相对于 repo 根目录的旧路径）；身份检查随后会改为验证该路径，而内容/树哈希检查保持不变，因此实际不匹配的配对仍会失败。**将 `--renamed-from` 作为绝对路径传入。** 此命令接收的每个路径，如果以相对路径提供，都会相对于当前工作目录解析——不会相对于 `--after` 解析，也不会相对于彼此解析——而 `--renamed-from` 通常指向一个已不存在的目录（它已被重命名），因此不像 `--before`/`--after` 那样存在目录检查来捕获错误解析；它只会在更深处以令人困惑的方式失败。这个问题尤其会影响 skill-creator 自身的编辑：上面的 `cd <skill-creator-path>` 位于 skill-creator 自己的 repo 中，而该 repo 通常与正在审计的 skill 所在的 repo *不同*，因此相对的 `--renamed-from` 会静默地相对于错误的 repo 解析。

4. 审查每个候选项。使用且仅使用一个处置结果，并记录具体的证据/理由：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移出此 skill 需要提供负责该能力的目标位置、当前边界证据以及可追溯的用户批准。明确的弃用也必须引用/追溯用户的批准。关于已保留/已清理/已修复的声明必须指向真实存在的当前文件和行，并包含一段简短的 `contains` 引文，以便验证器在附近定位。文件级候选项需要使用当前文件指纹，并附上命名的语义审查，说明行为为何得以保留——仅凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写相同的填充脚本——`classify` 子命令会完成机械性工作（定位引文在目标文件中的行，填充 evidence/semantic_review，在找不到引文或理由过短时快速失败）。你仍然需要为每个候选项编写处置结果和理由；它只负责将这些内容录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置结果默认为
   `preserved_or_moved`）；文件级候选项只需要提供 destination + 至少 40
   个字符的 reason——指纹会由工具计算。**从目标文件中复制 needle（使用 Read/grep/sed），绝不要凭记忆输入它**——查找采用精确匹配，找不到引文时会快速失败；手动输入 needle 实际上会失败的两种情况是全角与半角标点（`：` 与 `:`）以及凭记忆改写的近义字符（`也` 与 `都`）——这两种情况都会逃过自我审查，只有工具拒绝整个映射表时才会被发现（同一个映射表曾因这两个原因连续被拒绝两次）。

5. 验证已完成的审查。任何进一步的编辑都会使审查过期，因此候选项发生变化后，请重新生成并重新分类。验证通过后会写入 `.skill-regression-reviewed`，这是一个绑定内容的本地状态回执。它有助于检测后续编辑，但有意不作为独立的打包授权；打包过程本身会再次验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可以识别静默失败）：

```
   $ … compare …
   回归审计：8 个候选项，371 个精确保留项   # exit 1 = 有待审查的候选项
   $ … classify …
   已分类 8 个候选项。                                    # exit 1 = 仍有部分未分类

`compare` 返回 1 表示存在待审查的候选项，而不是工具失败；
2 表示调用或运行时失败。该工具能够证明内容已精确迁移且接口得到保留，
但会刻意拒绝根据模糊的词语重叠来推断语义等价性。诸如“检查权限被拒”
这样的通用短语，不能悄无声息地替代“已登录但没有角色”这一精确契约。
还要检查标记为 `only_outside_runtime` 的候选项：如果某项运行时行为只存在于
eval、测试或不可达的参考内容中，那么它就不在正常调用路径上。

**每次编辑 SKILL.md 后立即验证 — 不要等到打包时（第 7 步）。** 该检查能够
及早捕获的失败是真实存在的：以未加引号的 YAML 标量形式编写的 frontmatter

` #` 甚至不会报错 — 它会静默截断其后的全部内容，因此触发关键词会消失，
但所有扫描仍会显示通过。

```bash

uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**只要描述中包含 `: ` 或 ` #`，或跨越多个句子，就应将描述写成 YAML 块标量**
（`description: >-` 后跟缩进的段落）— 鉴于上述事件，这是每个新建或编辑的

**更新现有 skill 时**：扫描每个现有的引用和捆绑资源，查找对应的更新，然后
通过上述迁移门禁。迁移契约需要 SKILL.md 中存在直接的运行时指引；eval 或

接下来的三项检查是**升级探查，而不是无条件扩大范围**。如果采取其中任何
一项会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖项、
权限或外部写入，请在修改 skill 前停止，并重新分类为 Tier 3。Tier 1 和
Tier 2 可以检查这些问题，但不会因此从中获得新的交付物。

**脚本检查**：在宣布编辑完成之前，先问自己：*源对话（或 eval 转录）写入了
什么代码 — 如果没有这些代码，每次未来调用都会重新编写什么？* 当所选层级
已经授权进行这项能力工作时，将其参数化并完成清理后放入 `scripts/`，并修改
文档以指向它。否则，将该信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的
附带效果打包。分工如下：**scripts 负责执行，文档负责理解** — 如果一个 skill
的方法只存在于正文中，那么每次运行都要重新支付全部编写成本。之所以在编辑
步骤中进行这项检查，正是因为跳过 eval 循环的路径（对话提炼、直接编辑）永远
不会到达 “Improving the skill” 中 eval 转录版本的这项检查。

**组件货架检查（针对 artifact-EMBEDDED 片段提出的同一问题）**：Scripts 检查涵盖的是 *skill* 执行的代码；生成 artifact 的 skill（报告页面、演示文稿、文档）还会不断积累其*输出*所嵌入的片段——图像叠加小部件、粘性导航、图表配置、CSS 块。如果连续生成的输出都各自手写相似片段，这就是同一个重复信号，只是指向了不同的货架。在添加 `components` 子文件夹或注册表引用之前，先应用上面的升级规则；Tier 1/2 可以提出方案，但不得创建组件能力。当获得 Tier 3 授权后，真正使一个代码片段成为货架组件的是围绕它建立的契约：(a) **原样嵌入块**——将 BEGIN/END 标记整体复制到 artifact 中，不依赖任何外部依赖，以便单文件 artifact 保持自包含；(b) **注册表条目**——说明交互契约（触发条件、按键绑定、关闭行为、边界情况）以及来源信息——它来自哪个已交付的 artifact、用户何时批准了它；(c) **准入门槛**——只有用户实际使用过并批准的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但看起来漂亮的片段不得进入）；(d) **行为冻结，外观可调整**——经过校准的行为和按键绑定属于契约，在不同运行之间不得漂移，而颜色和尺寸可以遵循 artifact 自身的风格；(e) **回写循环**——为某个 artifact 发明的片段，应在获得批准的同一会话中提升到货架中。这一点的重要性不只是节省 token：手工重写的片段会*漂移*——每次重写都会悄然改变按键绑定、关闭行为、计数器等，而对于每天阅读这些 artifact 的用户来说，交互一致性**就是**产品体验。用用户为第一个此类货架提出的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：一个报告页面 skill 的 lightbox-gallery 组件（图像叠加：←/→ 在组内循环切换，ESC 关闭，就地缩放，n/N 计数器），以及其 interaction-components 注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击流程测试完成验证。参见方法论案例 17。

**流水线检查**：考虑此 skill 的输出是否会自然地流入另一个 skill，以及是否应由现有 skill 链式调用*此 skill*。添加或实质性修改“Next Step”交接或流水线契约，需要在编辑前重新归类为 Tier 3；Tier 1/2 可以提出方案，但不得顺手添加。

**引用与自应用检查（能逃过细心作者检查的缺陷）**：有一类失败模式，从内部看起来都像已完成的工作，而且无论多么仔细地重新阅读都无法发现；每一种都需要一个*机械化*动作来代替。（开头特意没有写数量。 “Three failure modes:” 是一个派生数字，只要有人追加一个项目符号就会过时；而且，计数类文字之所以最难准确捕捉漂移，正是因为它*不包含发生变化的内容*——对列表本身进行编号 grep 和 diff 都会径直错过它。）它们被归在这里，是因为共享同一个原因：**写下断言和验证断言是两种不同的模式，而单次遍历无法同时承担这两者。**在你撰写内容时，“see rule 8”*就是*那个断言；你并没有同时打开规则 8。

与上面三个升级探针不同，这一项**不按层级限定**——而是按你写下的内容限定。一个没有添加指针、也没有添加规范性规则的 Tier 1 修复，在这里无事可做；而且你不必自己判断这一点：推论中的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 给出答案。无论处于哪个层级，只要你写了指针或规则，下面这些要点就适用。

- **你写下的每一个指针，都要打开它的目标，并从中复制一行出来——在写下指针之前。** 不要只是说“我确信那条规则列出了全部三个标记”：把目标中的一段文字粘贴到你在这一步本来就要产出的内容中（审查备注、提交消息正文、你的回复，任选其一），放在某个之后第二位读者可以将其与目标进行核对的位置。你只是看过、却没有复制出来的片段，正是本句开头所拒绝的自我评估。错误的交叉引用在重新阅读时是不可见的，因为错误的指针看起来和正确的指针完全一样，而作者又是唯一必然会“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal rule 3”，意指一条关于不要引用过时枚举的规则——但被引用文档自己的 *rule 3* 讲的是样本量，而实际被引用的规则位于另一个文件中；读者遵循该文档既有的自引用约定，最终会落到一个无关主题上。同一次编辑还提交了一个方向颠倒的指针（对上方的内容写“see below”），以及一个指向不存在的章节标题的指针。
- **文件一旦包含两个编号列表，单独写“rule N”就会产生歧义。** 检查是针对每个指针进行的，而不是针对每个文件：在写下“rule N”之前，运行 `grep -n '^N\. ' <file>`，确认在你所指的章节中恰好有一个匹配；如果有多个，就同时写明章节。（**不要**把这变成文件级别的告警，例如“这个文件是否包含多个从 1 开始的列表”——在任何长文档中，这几乎总是成立，因此它会对健康输入触发，并最终被忽略，而规范 #6 警告说这比不做检查更糟；在这个文件上运行一次看看就知道了。）在真实案例中，一个单独的“rule 1”有三个候选列表，而从上到下搜索时首先命中了错误的列表。
- **添加任何规范性规则后，都要用它旁边的行检查该规则——并让检查产出一个工件，而不是一个结论。** 使用与下面推论相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的代码块。这里由你自己阅读就足够了——你不是在进行模式匹配，因此不需要脚本——但必须带上该引用：单独使用 `git diff` 只会显示尚未暂存的工作，而一旦你执行 `git add`，它就会什么也不输出；这正是本段推论要设法避开的五种静默空结果模式之一。将新规则拆分成各个独立的子句，并逐条写下：**同一个代码块中**满足该子句的行。（下面推论中的 `scripts/reference_net.sh` 是另一项工作：它会列出供你解析的**正文交叉引用**。它不会把代码块交给你，也不会告诉你规则中的某个子句是否得到了满足。）**旁边没有对应行的子句就是问题所在。** 那个诱人的简短版本——“我的新规则通过了吗？”——对于 30 秒前刚写下它的人来说不可能失败；这正是规范 #6 所说的、应优先选择可证伪观察而非自我评估的含义，因此本要点也必须提供它所要求的同一工件。最先暴露问题的通常就是它旁边的段落。真实案例：有人添加了一条规则，要求“始终同时报告原始计数和过滤后计数——差值*就是污染量*”，但同一次提交中的配套示例只打印了过滤后的数字。同一份差异中还有另一处陈述引用了两个数值，却没有说明这些数值是否是在相邻新规则刚刚规定为强制的限定条件下采集的。范围很小，也很明确：不是“重新阅读整篇文档”，而是“我 30 秒前写下的规则，在我 30 秒前写下的那些行上是否通过”。
- **为每条新规则添加一行，说明由谁执行它，以及他们是否确实能够执行。** 如果现有工具无法满足某条规则，那么相信自己已经遵守规则的人就会跳过它——这是最糟糕的一类规则，因为它会产生有文档记录的虚假信心。真实案例：一条新规则要求“检查两个日志存储”；但项目自己的规范性单命令排查工具将其中一个硬编码在内，因此标准工作流会对规则原本要捕获的故障返回干净结果。该规则本身是正确的，却不起作用，而且没有说明这一缺口。**使其可证伪的工件**（没有这个工件，本要点就是一个禁止自我评估的段落中唯一的自我评估）：指出哪个工具或命令可以捕获违规，然后**用一个你已经知道它应该捕获的案例运行一次**。如果面对一个已知有问题的输入时它返回干净结果，你就已经测量出该规则不起作用——把这个缺口直接写入规则本身。“他们是否确实能够执行”如果只是凭记忆回答，正是规范 #6 所拒绝的未经验证断言。**当没有任何工具能够判定这条规则时**——大多数正文和品味规则都属于这种情况，因此不要把它当作逃避口——工件就是那句明确说明这一点的话：*“没有任何东西会强制执行这一点；它只有在有人记得它时才成立。”* 这比检查通过更糟，而把这一点明确说出来正是关键；执行情况沉默的规则会被假定遵守，而不是得到验证。注意这个要点自身诚实的限制：工具和已知有问题案例的选择仍然属于判断，因此它只是移动了未经验证的步骤，而不是消除了它——它比替代方案更省事，但并非没有成本。
- **推论——你的修复本身也是缺陷来源，因此要在最后一次编辑之后，重新检查你改动过的区域。** 在对同一项变更进行的两轮审查中，第 1 轮发现了八个问题；第 2 轮又发现了八个，其中**七个是由第 1 轮修复引入的交叉引用错误**。重写一句话会移动它周围的锚点。这也是为什么对于读者依靠指针进行导航的工件来说，“它已经经过审查”并不是终点：你一旦据此采取行动，审查就立即过时了。重新检查是机械性的，而且它是一个**脚本**，不是让你重新输入命令：`scripts/reference_net.sh <base-ref> <file>…`（位于本 skill 的资源包中）。它会列出你添加的行之间的正文交叉引用，因此你可以打开每个目标，确认其中确实写着你所声称的内容。首次使用前先阅读它的头部注释——其中解释了它为什么需要一个 base ref，而不是默认使用 `HEAD`，以及它有意**不**做什么。

**在开始编辑之前获取 `<base-ref>`，而不是之后。** 在开始操作的那一刻将其解析为一个字面量 SHA 一次——`BASE=$(git rev-parse HEAD)`——并在本段和上面的项目符号中复用同一个值。如果你运行了现有 skill 迁移门禁，它就是你已经完成基线处理所依据的 ref。稍后传入 `HEAD` 才是陷阱：提交之后，`HEAD` 包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请恢复该值（使用 `git log`、`git reflog`，或提供给迁移门禁的基线），而不是用 `HEAD` 替代；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印提示，但不要依赖在那里才发现这一点。

**为什么这里要使用脚本，而本段其余部分都是说明文字。** 它所替代的那条单行命令经历了五轮修补——将 diff 锚定到正确的基线、查看已暂存的编辑、在提交后仍能正常工作、跳过 diff 自带的 `+++` 标头、移除误导性的 `-n`——而其中四轮都增加了另一种让它不打印任何内容并以 0 退出的方式，这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种问题的另一种表现：它移除的 `-n` 原本会打印真实命中项及其行号，但行号是按管道传入的内容计数的，因此看起来很权威，却指向不存在的位置——这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都会继续放行它本应捕获的缺陷。说明文字无法验证自己的输入，无法说明自己产生了哪一种结果，也无法接受测试；脚本三者都能做到，而且它的契约是：**每一种结果都必须被明确命名，错误输入必须明确失败**。这就是本步骤前面提到的 Scripts 检查在本段中的应用——而五轮修补正是忽略该检查所付出的代价。

**阅读它的判定结果，而不只是退出码。** 脚本只要成功运行就会以 0 退出，因此单独查看 `$?` 无法告诉你它发现了什么；答案位于判定行中，而它总会明确指出以下其中一种结果：发现引用（逐一解析）、文件与基线完全相同、文件已更改但没有新增行，或新增行中没有任何类似引用的内容。这些是不同的结果，脚本会刻意将它们区分开——这个检查曾将它们合并为一个无声的“什么都没有”，正是它后来变成脚本的原因。它只需几秒钟，且不依赖人的警觉性，这正是纪律 #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的指针——“见下文”、“如上面的规则所述”——因此也要阅读新增的行。）

### 步骤 5：清理审查（任何公开 skill 都必须执行）

**在进入此门禁之前，如果纪律 #5 已到执行时机，其独立检查必须已经完成**，并且当前变更对应的 `independent-review.md`（位于你的私有、受 git 跟踪的知识仓库中——不在已清除的工作区，也不在任何已经公开或可能会公开或分发的仓库中）必须存在**且已提交**。对于新 skill，它始终需要执行；对于现有 skill，使用下一段中的阈值。一个位于 git 工作目录中但尚未提交的文件，与一个从未写入的文件在实际意义上没有区别；`ls`/`test -f` 只能确认它在磁盘上，而不能确认它能够保留下来。对于**新** skill，这是任何内容首次离开你掌控的步骤，因此也正是在这里真正执行这项纪律，而不只是陈述它——一条位于使用点上方 1000 行、却没有任何检查机制的规则，每次都会输给追求完成的驱动力。

**对于已发布 skill 的编辑，编辑离开你手中的那一刻就是执行 push，而不是这一步。** 这个门槛可以用一句“仅限内部，跳过”来回答，而对于仅涉及文档的更改，打包甚至可能根本不会运行——因此把审查固定在这里，意味着一次 skill 编辑可能在没有任何独立审阅者查看的情况下就进入公共分支。真实案例（2026-07）：对本文件本身的一次更改发布了一个发现命令，而该命令无法触及旁边正文声称覆盖的三个根目录；它被合并了，直到*之后*委托进行的一次审查才发现这个问题。**因此，对于已有 skill：独立审阅及其记录产物必须在 `git push` / 创建 PR 之前完成——在 push 时运行的门槛（回归审计、验证、扫描）都会检查结构，但没有任何一个能告诉你这些说明是错误的。** 这沿用了纪律 #5 的原有门槛：当*规则、契约或数字发生变化时*就必须执行，而拼写错误或纯格式重排则不需要。让拼写修复也必须等待一轮审查，恰恰会养成反模式 #6 所警告的那种条件反射——“这次改动很小”变成普遍豁免，最终连真正重要的更改也被它涵盖。

**对于要进入公共仓库的 skill，这不是可选项。** 私有内容一直会泄漏到公共 skill 中，而扫描器遗漏的泄漏才是危险的——非英语语言中的真实姓名、真实对话记录中的逐字内容、被放进示例中的真实案例。只有在该 skill 确实仅限内部使用时才跳过。

**按目标范围，而不是按主题范围来限定审查。** 只有公开发布的产物——skill bundle 本身——需要进行脱敏。留在私有仓库中的配套文档（skill 提炼所依据的事件报告、内部运行手册、项目的 CLAUDE.md）应保留其真实主机名、路径和时间戳：删去这些内容会破坏它们的审计价值，而你最终还会把这些改动恢复回来。有一次提炼会话之所以经历了三轮返工，正是因为脱敏审查被应用到了源材料涉及的所有内容，而不只是公共 skill。

**先检查目标位置，并让它预先填充建议。** 在 skill 将要存放的仓库上运行
`gh repo view --json isPrivate`（或者读取
`quick_validate` 已经打印的提示）。私有目标会使选项 C 成为默认建议，而不是事后才考虑的事项——“除非另有说明，否则假设是公开的”正是把私有 skill 的工作路径变成无人要求的占位符的原因。

**触发脱敏的是目标位置的 `isPrivate`，而不是任务在主观上有多像发布。** 这两者并不总是一致，而一旦不一致，除非你明确指出这一点，否则主观感受就会胜出。将内容*移入 marketplace skill* 会让人感觉像是在发布——marketplace 正是内容得到分发的地方——所以即使源仓库和目标仓库都是私有仓库、根本没有任何内容要被发布，脱敏反射仍会触发。真实案例（2026-07）：一次从项目级 skill 迁移到私有 marketplace skill 的操作，把真实配置路径、真实十六进制值和真实具名示例都泛化成了占位符。`quick_validate` **每次**运行都会打印 `🔒 audience: private`；作者每次都看到了，却仍然进行了脱敏，因为这种*活动*在感觉上像是在发布。代价并非只是表面上的——真实路径能让下一位读者去核对该值；而“项目自己的 token 文件”是无法打开的。

所以要把它当作一次查找，而不是一次判断：**读取目标位置的 `isPrivate`；如果它是
`true`，则是否进行清理需要由所有者提出请求。** private→private 的移动是移动，不是发布。**当两个探针都没有返回结果时**（尚无远程仓库、尚未运行
`quick_validate`），你就没有可用的查找结果——回退为将其视为公开，并明确说明这一点，因为不对称性就是如此：一次不必要的问题只会多占用一句话，而一次不必要的信息泄露则无法挽回。并且，`isPrivate` 报告的是目标位置**今天**的状态——一个位于私有仓库、正准备发布的 skill，会在发布它的那次 push 中进行清理，而不是在这一次进行。如果你发现自己开始思考某些内容在私有目标位置中是否“应该”被泛化，那么这种思考本身就是信号。

使用 **AskUserQuestion** 确认深度（对于公开目标，确认深度，而不是是否执行；对于私有目标，确认是否需要执行）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**清理流程——通读是方法，扫描是辅助：**

1. **亲自通读整个 skill，并进行语义判断**（这才是真正的检查）：SKILL.md + 每个 reference + 每个示例。对于每个具体名词 / 示例 / 代码片段，都询问：“这是通用占位符或公开实体，还是从真实项目 / 人员 / 对话记录中提取的？”替换后者——即使没有扫描器将其标记出来。这是唯一能捕获没有可匹配关键词的信息泄露的方法。完整指导和语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器，作为低成本的第一轮检查**：使用检查清单中的 grep 模式 + `security_scan.py`（步骤 6）。它们可以快速捕获明显的密钥 / 路径 / 已知名称——但“没有匹配项”并不代表通过。
3. **替换**每个发现的问题，使用保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。从惨痛经验中总结出两条规则：占位符本身不能编码真实值——`<acme-corp-domain>` 恰恰泄露了它原本要隐藏的名称；应改用其*角色*命名（`<api-domain>`、`<upstream-provider>`）。另外，当你编写批量替换脚本时，要为其指定限定在 skill 目录内的明确文件白名单——未限定范围的查找和替换会毫不犹豫地重写项目自己的 CLAUDE.md，迫使你执行 git restore。
4. **通过重新阅读进行验证，而不是重新 grep**：重新阅读修改过的部分，并确认没有损坏的引用。

### 步骤 6：安全审查

在打包或分发 skill 之前，运行安全扫描器，以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）
- 完整的发布内容集合仅由 [scripts/packaging_policy.py](scripts/packaging_policy.py) 定义。打包、安全证明、内容哈希和回归审计都必须使用该共享策略；不要在说明文字中或消费者专用的过滤器里维护第二份排除列表。

**它不涵盖的内容** — 这正是为什么仍然需要执行步骤 5 的通读审查：gitleaks 和正则规则只会匹配你列出的*已知机密格式和模式*。对于没有关键词的私密内容，它们在结构上无法识别——非英语语言中的真实人物/项目名称、真实转录内容中的逐字行文、从你自己的工作中直接摘取的真实示例。`security_scan` 显示绿色只意味着“未发现已知格式的机密信息”，**并不意味着“该 skill 已完成脱敏”**。绝不要将其视为后者。

**首次设置：** 如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 清洁（可安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**对于私有 skill，发现的问题是信息，而不是待办事项。** 扫描器无法区分泄露的凭据和*本来就应该存在*的凭据——例如一个价值就在于预先填充完整内容的模板，或一个指向其运行所在唯一机器的脚本。在私有仓库中绝不要自动修复：报告发现的内容，让所有者自行决定。下面的选项 A（“自动修复”）适用于准备发布到公共环境的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 步骤 7：打包 Skill

skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个现有的 Git 跟踪 skill，必须先提供并重新验证完整的审查结果，才能进行打包。当前标记仅是本地状态回执，因此先提交或手动编写标记都无法绕过审查。下次编辑后，审查将变为过期状态：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及使用 `--include-evals` 来发布根目录下的 `evals/` 目录（默认情况下，该目录作为开发资源会被排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **重新验证已完成的现有 skill 回归审查**，只要 Git HEAD 中已经包含该 skill；单凭标记永远不足以授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描匹配）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，不会创建安装包。

### 步骤 8：更新 Marketplace

打包后，更新 Marketplace 注册表，以包含新的或更新后的 skill。

**对于新 skill**，在 `.claude-plugin/marketplace.json` 中添加一条记录：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于更新后的 skill**，按照 semver 规则递增 `plugins[].version`。对 skill 文件进行的任何更改——即使只是修复一行拼写错误——都需要递增版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧版 skill，而你的修复则一直无法发布。

**然后将其记录到变更日志中——这一步最容易被跳过。**版本递增让更新变得*可安装*；变更日志条目则让它在六个月后、有人遇到同样问题并通过 grep 搜索时，仍然*可查找*。而且，如果变更日志记录了其他每个 skill 的版本，却悄无声息地遗漏了你的版本，这比完全没有变更日志更糟：这些空缺会被理解为“那里没有任何变化”。

遵循现有条目的格式，不要自行发明格式——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。将它与版本递增放在**同一个提交**中；“稍后”再更新的变更日志，往往就意味着永远不会更新。

真实案例（2026-08）：某个 skill 连续发布了两个版本，版本号递增正确、门禁检查通过、PR 也已合并——但**完全没有变更日志条目**，因为这套流程中没有任何步骤要求添加变更日志。两次遗漏都只是在后续审计中才被发现。这正是纪律 #6 在此文件自身上的体现：如果一条规则只存在于约定中，而不是某个步骤中，它每次都会输给“赶紧完成”的驱动力。

**保持注册表 diff 最小——这是所有 skill 共享的唯一文件。**Marketplace 清单是所有并行编辑者发生冲突的地方，因此其中无关的格式变更，比其他任何位置的同类变更代价都更高：它会把原本干净的三行版本递增，变成与其他正在编辑该文件的人发生冲突。当你通过脚本更新它时（解析为 JSON、修改后写回），重写过程可能会悄悄规范化文件原本未采用的格式——末尾换行符、缩进宽度、键顺序、Unicode 转义。遵循往返处理纪律：之后重新读取文件，并对该文件运行 `git diff --stat`；**唯一可以出现的行，必须是你有意修改的字段。**如果出现了额外行，请恢复文件原有的约定，不要提交这种规范化变更（某次脚本化版本递增曾经给一个原本没有末尾换行符的清单添加了换行符——在最可能同时被其他人编辑的文件中，白白多出了一行 diff）。同样的原则也适用于 skill 会修改的任何共享注册表：lockfiles、catalogs、index documents。

**当一个 PR 经历了几次合并仍未结束时，请执行 rebase——然后证明你没有吞掉任何人的工作。** 正是因为清单容易发生冲突，它才容易过时：一个同时修改注册表和变更日志的未合并 PR，只要有其他内容合入就会产生冲突，因此应预期出现 `mergeable: CONFLICTING`，不要把它当成意外（有一个 PR 就是在某个下午主分支前进了 7 个提交后遇到这种情况的）。如果仓库采用 squash merge，应执行 rebase 而不是 merge——在压缩后的历史中，合并提交没有任何价值。冲突本身几乎总是**增量式的**：两位作者分别在同一部分追加了自己的条目，因此解决方式是**保留双方内容**，绝不要使用 `--ours`/`--theirs`，因为这会悄无声息地丢弃同事添加的行。

人们会跳过的步骤，恰恰是能发现错误解决的步骤——**解决冲突后，证明与基线之间的唯一差异就是你自己的修改：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要使用不带选项的 `--force`：如果自你上次获取以来远程分支发生了变化，lease 会让推送失败；而这正是其他人向你的分支推送过内容、普通 force 会将其抹掉的情况。

**插件边界不属于本 skill 的职责范围。** 是否应将 skill 拆分到不同插件中、如何安排 `source`/`skills`，以及用户是否可以单独切换 skill，都属于打包/分发领域——SSOT 是 `marketplace-dev` skill，而不是这里。当任务确实需要做出这些决策时：确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与 `skill-reviewer` 需要其脚本时拉取 `skill-creator` 相同），然后阅读 marketplace-dev 的 cache-and-source-patterns 参考并遵循其中的要求。不要在此重复它的规则；复制一份会逐渐偏离。

**重命名、迁移或移除 marketplace 条目，对于已经安装它的每位用户来说都是一项破坏性变更**——当条目消失时，Claude Code 不会清理已安装的副本，从而留下悬空安装，并在每次 `marketplace
update` 时出错。应像对待 API 弃用一样处理此类变更：在变更日志中附带迁移说明，并遵循 marketplace-dev 关于具体操作的指导。

**如果你亲自提交/推送 skill 仓库：** 对于一个已有的 skill，如果当前变更触及 discipline #5 的规则/契约/数值阈值，请确认审查产物记录了这项变更并且已提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不是仅仅确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的审查不能满足当前的实质性变更。第 5 步的说明解释了为什么对于已经发布的 skill，真正的强制执行点是推送，而不是打包。然后只暂存 skill 明确指定的路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充满无关的变更，否则这些内容也会被一并带入提交（有一次提交就卷入了一堆无关的 transcript 文件，最后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库实际的可见性，不要根据路径想当然——一个公开的 skill 仓库应当走 PR + 审查流程，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成 skill 后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试 skill 后，用户可能会要求改进。由于用户对 skill 的实际表现有了新鲜的了解，这种情况通常会紧接着使用 skill 发生。

**优化筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经覆盖了某项内容，则不要重复添加。

## Claude.ai 专属说明

在 Claude.ai 中，使用相同的验证深度路由器和重型评估授权门控。当完整的通用配对流水线获得明确授权后，工作流为 draft -> test -> review -> improve -> repeat，但由于 Claude.ai 没有子代理，需要调整部分机制。具体适配方式如下：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，读取 skill 的 SKILL.md，然后自行遵循其中的说明来完成测试提示。一次执行一个测试用例。这种方式不如使用独立子代理严格（你编写了 skill，同时也在运行它，因此拥有完整上下文），但仍然是有用的合理性检查，而人工审查步骤可以弥补这一点。跳过基线运行——只需使用 skill 按要求完成任务。

**审查结果**：如果你无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或者你在远程服务器上），则完全跳过浏览器审查员。改为直接在对话中呈现结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），则将其保存到文件系统，并告知用户文件位置，以便他们下载和检查。直接在对话中询问反馈："How does this look? Anything you'd change?"

**基准测试**：跳过定量基准测试——它依赖基线比较，而在没有子代理的情况下，这些比较没有意义。专注于收集用户的定性反馈。

**迭代循环**：与之前相同——改进 skill、重新运行测试用例、询问反馈，只是中间不再使用浏览器审查员。如果有文件系统可用，你仍然可以将结果整理到迭代目录中。

**描述优化**：本节需要使用 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测对比**：需要使用子代理。请跳过本节。

**打包**：`package_skill.py` 脚本可在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 上，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。在这种情况下：
  - **保留原始名称。** 注意技能的目录名称和 `name` frontmatter 字段——保持不变。例如，如果已安装的技能是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前复制到可写位置。** 已安装的技能路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从副本进行编辑和打包。不要传递 `--new-skill`；非 Git 副本的现有技能仍然是现有技能。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再将其复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 特定说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此经过明确授权的通用配对流水线可以运行基线和评分器。子代理可用并不等于获得授权，也不能据此增加额外角色；说明必要的实验组，限制并发，并在并行运行不会增加证据时按串行方式运行案例。
- 你没有浏览器或显示界面，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击、在其浏览器中打开 HTML 的链接。
- 在经过明确授权的**通用配对运行**之后，在你自行修改技能之前，使用 `generate_review.py` 为人类生成评估查看器；默认层级证据、未授权工作，以及取代查看器机制的专用工作流，不会仅仅因为工作在 Cowork 中进行就产生查看器义务。
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。随后你可以读取该文件（可能需要先请求访问权限）。
- 打包功能可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该也能正常运行，因为它通过子进程使用 `claude -p`，而不是浏览器；但请将其暂缓，直到你完全完成技能制作并且用户同意其状态良好。
- **更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。请遵循上方 claude.ai 部分中的更新指南。

这里再重复一次核心循环，以示强调：

- 弄清楚 skill 的用途
- 对于现有 skill，在编辑前对旧包进行快照和清点
- 在执行任何专用工作流退出操作之前，选择能够证伪此次变更的最低验证层级，并记录选择该层级的原因
- 起草或编辑 skill
- 运行该层级所要求的证据收集流程，或运行所选专用工作流声明的等效机制
- 对于获得明确授权的通用配对运行，与用户一起评估输出，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复执行，直到你和用户都满意
- 运行并通过现有 skill 回归审查；仅通过 eval 不算完成
- 打包最终 skill 并将其返回给用户。

如果你有 TodoList，请将所选验证层级及其默认证据添加到其中。只有在通用配对管线获得明确授权后，才添加“创建 evals JSON 并运行 `eval-viewer/generate_review.py`，以便人类审查测试用例”。
