# Skill 创建器

一个用于创建新 skill 并对其进行迭代改进的 skill。

从高层次来看，创建 skill 的过程如下：

- 确定你希望 skill 实现什么，以及大致应如何实现
- 将变更归类到能够证伪其可能失败模式的最低验证层级
- 编写 skill 草稿
- 使用能够证伪变更后行为的最小证据进行验证；将完整的成对评估流程视为需要单独授权的工作，而不是某个层级标签的自动结果
- 当所选层级产生定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写 skill（如果定量基准测试暴露出任何明显缺陷，也要据此重写）
- 重复上述过程，直到你满意为止
- 仅当当前证据无法解决变更后的行为时，才提升验证层级

使用此 skill 时，你的任务是判断用户处于这一流程的哪个阶段，然后介入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一种能力，而不是每次编辑都必须缴纳的成本。诸如“优化”“改进”或“全面”之类的词描述的是意图，而不是失败面或评估预算。不要仅仅因为任务听起来范围很广，或因为一段较长的对话已经展开，就创建评估文件、分派成对的代理、对输出进行评分，或启动查看器。

以下六项贯穿始终的规范适用于整个过程，因为这些失败模式会产出看起来令人信服、实则错误的 skill：

1. **先验证，再编写。** 任何进入 skill 的技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的结果——无论是在本次会话中，还是在获得明确批准的已挖掘会话中。现在无法验证？那就去验证，或者明确标注为“未经验证——来自记忆”。skill 会放大其中包含的一切：经过验证的知识会不断积累，充满自信地陈述的错误也会不断积累。对于知识型 skill（内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作版本：权威层级（观察到的行为 > 机器可读的契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例的冒烟运行，以及受众和 Windows 可移植性检查清单。一次源依据审计发现，多个自信陈述的契约断言与作者已经掌握的证据相矛盾（方法论案例 9）。
2. **将“无法实现 / 不支持”视为假设，而不是结论。** 当某项能力似乎受阻时（API 错误拦截、工具无法连接、格式无法打开），在将“平台不支持此功能”写入 skill 之前，先穷尽各种观察路径——UI 自身的网络流量、替代通道、不同的文档化标识符。观察到的行为优先于推测性的请求形状。
3. **站在领域已有成果的肩膀上——在编写或优化 skill 的方法论之前，默认将该领域已经确立的最佳实践检索到上下文中。** skill 的方法论有多好，取决于上下文窗口中的知识，而不是模型权重中潜藏的知识：预训练知识是不完整的，会过时，而且除非实际拉取规范来源，否则往往根本不会被激活。因此，你所编写内容的质量上限是`你的训练数据 + 用户输入`——*除非*你有意检索该主题领域真正的既有成果。这样做：使用 WebSearch 搜索该领域的经典理论 / 标准 / 方法，并阅读该领域中随附或已安装的 skill，然后将其中承载关键作用的原则及其出处融入 skill。**这与下文的“既有成果研究”是不同的维度**——后者用于寻找可复用的工具 / 基础设施；前者则是用该学科积累的科学成果来为*方法论本身*提供依据。将其作为**默认操作，而不是等到用户要求后再做**：简要告知用户你正在参考哪个领域的成果，让他们可以说“跳过”，但绝不要在 40 年的领域公开成果只需一次搜索即可获得的情况下，仅凭记忆加用户提示就交付一个方法论。示例：数据可视化 skill 必须吸收 Cleveland & McGill 的图形感知排序以及 Bertin 的视觉变量（位置 / 长度优于颜色，颜色优于文本——这是经过测量的结果，而不是审美判断）；日期 / 时间 skill 必须展示成熟的库及其典型陷阱；说服 / 谈判 skill 必须检索既有框架，而不是凭记忆重新发明。若经典知识只存在于你的权重中、从未进入上下文，那么你就是在本可引用的地方进行猜测。
4. **在压缩现有 skill 之前先予以保留。** 更新现有 skill 是一次迁移，而不是从空白页面开始重写。在首次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧版内容包，或者根据明确的 Git ref 重建它；任意复制并附加来源标签不能算作基线。盘点运行时能力、触发上下文、接口、参考资料和评估覆盖范围。渐进式披露和简洁性允许你移动或去重内容；但不允许你在未说明的情况下删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个未匹配的旧单元进行分类。只在 `evals/`、测试或未链接的参考资料中保留下来的运行时契约，仍然算作丢失。在任何候选项尚未分类或任何真正的缺口仍未修复之前，不要宣布更新完成。同样的逻辑也适用于**撤销**，而不仅仅是删除，并且适用于任何既有承诺——不只是那些带有日期和姓名的承诺：**推翻已经作出的决定必须是一项提案，而绝不能成为副作用。** 要明确说出来并获得接受。无声的重写比无声的删除更糟，因为它会一次性摧毁成果及本可发现问题的证据——也会让所有下游审阅者失去警觉（见 #5）。

**在编辑前对每个预期变更进行分类；“压缩”指的是行为等价的主张，而不是“更短”的同义词。** 对于每个旧有用户场景，新 agent 仍必须能够找到触发条件、决策输入、受支持的操作、停止/确认点、影响/恢复边界以及验证路径。在计划、评审和变更日志中，将这些名称作为独立的变更类型标签；在每个回归候选项的原因/语义评审中记录该标签，同时将审计工具的 `disposition` 字段保持为完全匹配 Step 4 枚举值：

   | 变更类型 | 定义 | 必需处理 |
   |---|---|---|
   | **无损压缩** | 仅改变表现形式：将细节移入可直接访问的捆绑引用中、相对于随包提供的规范来源进行去重，或缩短措辞，同时保留上述每一项运行时契约 | 可以称为压缩；但必须证明场景可达，而不只是字符串仍然存在 |
   | **能力退役** | 之前可执行的任务或操作不再可用 | 不属于压缩；明确说明已退役的能力，获取可追溯的用户批准，并公布边界 |
   | **范围缩小 / 边界变更** | 仍受支持的输入、目标、环境或模式减少；某个执行分支变为仅分析模式 | 即使更加安全，也不属于压缩；说明并公布边界/权衡，然后获取可追溯的批准，除非用户已经明确要求进行此次精确的范围缩小 |
   | **工作流或安全重新设计** | 命令、顺序、确认、副作用、恢复或成功检查发生实质性变化 | 不属于压缩；说明新的契约和权衡，除非用户已经明确要求进行此次精确的重新设计，否则获取可追溯的批准，然后独立于保留性验证之外对其进行验证 |
   | **缺陷修复 / 事实更正** | 将实现或正文恢复到明确存在的契约或当前权威来源所规定的状态 | 不属于压缩；使用能够决定该问题的狭义权威来源或确定性回归测试 |
   | **有损摘要** | 精确条件、命令、决策语义或执行出口消失，且没有运行时可达的等价内容 | 属于回归，而非优化；恢复它，或通过上方某个已批准的行重新分类 |

   只有当规范来源随 skill 一起发布，或能够可靠地获取，并且 SKILL.md 告诉运行时读者何时加载该来源时，去重才算无损。“这个想法仍存在于测试、变更日志、已安装的同级 skill 或作者的记忆中”不属于压缩。如果一个补丁包含多种类型，分别列出它们；绝不能让压缩标签掩盖退役或重新设计。

5. **任何内容都不能仅凭自我评审发布——独立、具有新鲜上下文的对抗性评审是固定步骤，而不是特殊情况。** 你“现在已经没问题了”的判断，是由生成该产物的同一个模型做出的，因此共享导致缺陷产生的完全相同的盲点。测量结果，而非民间经验：没有外部反馈的内在自我纠正并不能可靠地改善输出，有时还会使输出变差（Huang 等，ICLR 2024）；当生成者和评估者共享错误模式时，迭代会**在不增加信息的情况下提高信心**。更多自检无法逃离这一点；只有外部视角可以。**完整流程——包括提示模板、锚点选择、发现项表格和实操案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在第一次评审前阅读它。** 核心规则如下：
   - **独立性有两个方面，而第二个方面正是作者容易忽略的。** *评审者的上下文*不能是你的分支——分支会继承你的盲点，并返回一个“已评审”的印记。但与之对照的*证据*也必须位于变更的**影响范围之外**，否则它会继承你的**结论**：它读取一个产物和一个已经与之达成一致的规范，然后报告二者一致。注意，“本次会话未编辑”这一界线太弱——在参考资料的受控案例中，被污染的记录是在*前一天*编辑的，三名评审者都对一个他们在未触碰的副本中发现过的缺陷视而不见。按照你不太可能触碰过的程度为锚点排序：用户自己的会话原文 > 工作开始之前的 git ref（`git log --oneline <ref>..HEAD -- <path>`；你的任何提交都会使其失效）> 追加写入日志（这是一种约定，而非强制机制）。**Greenfield 没有锚点——应说明这一点并请求提供锚点，而不是报告一个你没有执行过的通过结果。**
   - **只向评审者提供恰好两个承载证据的输入：不可变产物和读者规范。** 同时提供用于限定评审范围的、非证据性控制元数据：当前变更的影响范围、明确命名的失败轴以及终止条件。不要提供设计理由、项目背景或“只需确认 X 没问题”之类的内容——这些会把独立评审者变成橡皮图章。读者规范和控制元数据说明由谁执行什么以及在哪里停止；它们不能告诉评审者实现是正确的。**对于 SKILL.md，读者就是另一个执行它的 agent**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——询问它哪些指令无法执行。在派发前冻结全部五个字段，绝不能使用事后上下文为发现项辩解。
   - **对于可理解性以及相对于语料库的完整性，它是事实依据；对于品味，它没有裁决权。** 直接应用前两项。将“这可能是个 bug / 我建议 Y”视为假设，并先自行复现。绝不要委托 AI 垃圾内容或审美判断——这属于同一个模型的盲点。
   - **枚举失败的*轴*，而不是内容领域——这也决定运行多少个评审者。** 轴是*你要提出的问题*；领域是*你要阅读的材料*。三名评审者分别覆盖场景、算术和差异，但都在问“这是否连贯？”，这只是将一次评审计费三次。**一个评审者是默认配置，而且通常已经足够**；只有在增加额外轴时才增加评审者。自我评审最不擅长的轴是**保真度**——“这是否仍忠实于已经作出的承诺？”——因为移动承诺的人正是作者本人；而连贯性与保真度彼此正交：一个产物可以完美地自洽，同时完全不忠实于已经决定的内容。
   - **在派发前冻结评审边界，并在该边界满足时停止。** 记录不可变产物/ref、读者规范、当前变更的影响范围、明确命名的失败轴以及终止条件。当发现项由当前变更造成、扩大了影响范围、首次宣传了受影响的行为，或使一条旧有矛盾通过已编辑路径变得可达时，它就会阻止本次发布。一个未被改变且未被新承诺的预先存在缺陷，是单独的待办假设，不会自动授权重新设计 skill。完成实质性修复后，由新的评审者重新检查失败的轴以及回归情况；它不会重新开启无边界的整份 skill 审计。完整的决策流程和示例见：[references/independent-review-protocol.md](references/independent-review-protocol.md)。
   - **留下产物，否则这只是一条警告。** 纪律 #6 规定，产生意见的检查要让位于产生产物的检查——因此这一步也要产出一个文件，否则它会在最需要发挥作用时败给完成驱动。将 `independent-review.md` 写入你的私有、受 git 跟踪的知识库中的 `skill-reviews/<skill-name>/`：其中必须包含**逐字记录的评审者提示词**（这样后续读者才能看出它是否具有引导性）、**每条发现项及其 disposition 和原因**（这正是合法筛选与丢弃不利内容之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识库（或者你没有私有知识库），应说明这一点并询问用户——不要猜测一个会落入任一禁区的位置。两个禁用位置：**不得位于 `<skill-name>-workspace/` 中**（会被 git 忽略的临时目录会被清理——该文件是跨会话的评审证据，必须在这些目录之外存续），以及**不得位于任何已经公开或可能公开、分发的仓库中**——这通常意味着不能位于被评审 skill 自身的仓库中（评审内容必然会引用私有路径、真实姓名和项目细节）。在完成实质性编辑后，使用一个*新的* agent 重新评审——实质性编辑指规则、契约或数字发生变化，而不是拼写错误。**从 Step 5 开始，该文件就是评审确已执行的证据；文件不存在就意味着评审没有执行。****写入文件并不等于下一次会话中它仍然存在——必须在同一轮中于该私有仓库执行 `git add` + `git commit`。** 一个停留在 git 工作目录中但未提交的文件，不具备本规则要求的任何“受 git 跟踪”保证：它可能丢失、被覆盖，或者只是从未被后续检查“是否已评审”的流程拾取到（真实案例中：文件已正确写入正确路径，也包含真实发现项——但后续自动检查仍然失败，因为它从未被提交；修复方式只是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械性的，并且与此互补：它证明你没有*删除*行为。它完全不能说明你写出的内容是否真的可以被遵循。

6. **设计你编写的检查，使其无法自行认证为通过。** Skills 很大一部分由各种检查构成——门禁、检查清单、“发布前”步骤——而如果执行上下文即使*违反了它所编码的规则*也能通过某项检查，那么这种检查比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴自那些早已解决这一问题的领域：
   - **验证必须覆盖规则中的每一条约束。** 如果规则写的是“A + B + C”，证据就必须分别要求证明 A、B 和 C。给一个包含三个约束的规则只配一行确认语句，执行者只需满足自己已经完成的那一条；其他约束则完全不可见。真实案例：一个报告编写 skill 中有一道交付门禁，其规则写的是“选项以并排的 chips 呈现 + 突出显示推荐项 + **背景信息必须写成完整、独立成篇、陌生人也能读懂的句子**”——但它下面的证据行只要求“有 N 个决策项，且全部渲染为 chips”。作者运行了门禁，写下这条证据，自行认证为通过，然后发布了一个标签只有单个字符、所有上下文都被删掉的页面。规则自始至终都在文件中；只是检查从未测量过那条约束。
   - **对健康输入误报的检查比没有检查更糟。** 上面的失败是“本应失败却通过”的检查；这里是它的镜像——“本应通过却失败”的检查。后者代价更高，因为它会教会操作者条件反射式地绕过检查（`--no-verify`、`SKIP=1`、`--force`），而一旦形成这种反射，门禁就会对*所有*输入失效，包括它原本要保护的输入。因此，在编写封闭失败式检查时，**误报的优先级高于漏报**：漏掉一个真实问题只会牺牲当前实例，而杀掉一个健康输入会让整个门禁失效。
     留意这个信号：**反复踩中同一个陷阱所产生的挫败感本身就是风险信号**——作者正是在这种状态下，最容易发布一个从未针对健康输入进行校准的防御措施。真实案例：作者一天之内三次踩到同一个格式陷阱后，给 linter 添加了一个正则检查；它误杀了项目自身语料库中的 **33 个健康输入**，并在同一小时内被回滚。在启用之前先进行校准——让任何封闭失败式检查运行于真实且已知正确的材料上，并确认零误报；与其让它出现误报，不如放宽检查，哪怕偶尔漏掉问题。
   - **让每一项都成为可证伪的观察，而不是自我评价。** “背景信息是自足的”无法被撰写它的人判定为失败；而“遮住页面的其余部分，只阅读一张卡片，并说明它正在决定什么”则可以。优先选择能够产出工件的检查——命令的输出、引用的行、截图——而不是只能产出观点的检查。
   - **同样的怀疑也适用于你所运行的检查，而不仅仅是你所编写的检查。** 上述四条规则适用于随 skill 一起交付的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样是工具，而错误的工具会像正确的工具一样自信地报告干净结果。在一次 2026-07 的会话中，五条独立的验证命令在两个方向上都给出了错误结果：没有 `-L` 的 `find` 报告已安装 skill 的文件缺失（它们实际上位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了正在审计的对象的第二份副本；一个反转的 shell 条件错误地警告某项删除操作没有发生；跨越换行符的正则凭空制造了 55 个“丢失的引文”；而对五个文件中的两个进行搜索，报告有两条规则缺失，但它们其实存在于第三个文件中。**每一条命令起初都被相信了，而每一条最终都只能通过重新运行形状不同的检查才被发现有误。**

解决办法是实验实践中最古老的一种：**在信任仪器处理未知答案的案例之前，先让它处理一个你已经知道答案的案例。** 要搜索一个你预期不存在的字符串？先用完全相同的命令形式搜索一个你确定存在的字符串——如果这次也返回 0，那么出问题的是命令，而不是文件。只需增加一行，就能把“我检查过了”变成“我用经过校准的仪器检查过了”。

     有两种具体形式值得记住，因为上文都出现过，而且都会*静默地*失败：`find` 在没有 `-L` 的情况下不会跟随符号链接（而 skill 的安装经常是指向源代码仓库的符号链接），`--exclude-dir` 则会在整个目录树中按 basename 进行匹配，而不只是匹配你心中所想的那个路径。

     **这条规则还有后半部分，只有当检查内容要随产物一起发布时才会造成问题：要以*标准*实现为基准进行校准，而不是以你机器上的实现为基准。** 上面的仪器规则保证*你的*结论真实可靠；这一点则保证*读者的*操作能够正常工作。写入 skill 的工具行为声明——某个标志、递归模式、某个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而两端的差异都是静默的：它在你测试时有效，却在他们那里悄悄什么也不做。有两种机制会导致这种情况，而且在会话内部都无法看出来：**相同的命令名解析到不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能绕过*别名*，所以 `command tool` 或绝对路径才是唯一确定的形式），以及**同一个程序在不同实现之间表现不同**（BSD 与 GNU，或替代实现之间）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将其写入 skill，作为解决符号链接陷阱的方法，并将其发布到了一个拥有 1200 颗星的公共仓库——他们使用的 `grep` 实际上是由 shell 函数提供的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 上，同样的 `-R` 什么也匹配不到（它需要 `-RS`），因此这个规定的修复方法对大多数读者都静默失效了，而就在同一节中，它还在警告验证器会静默失败。

     因此：**在工具行为断言进入已发布的产物之前，要用标准二进制重新运行它**（`/usr/bin/<tool>`），而不是使用 shell 交给你的那个。如果它经不起这样的验证，就不要写入这个标志——**优先采用不依赖具体实现的表达方式**：自行解析路径（`readlink -f`），而不是押注于某个递归标志；在脚本中进行子字符串测试，而不是进行面向行的匹配；明确写出你需要的*行为*，而不是写出你碰巧知道的选项。只在你的环境中有效的规定比没有规定更糟糕，因为读者没有办法发现它只是静默地什么也没做。

   - **采用成熟的清单实践已经确定的方法。** 判断一个列表属于 **READ-DO**（边阅读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭借专业经验操作，然后在规定的**暂停点**停下来确认——适用于时间紧迫情况下的资深操作者），并将其锚定在真正的暂停点上，而不是“流程中的某个地方”。只保留**关键事项**——既关键、又常常会在压力下遗漏，大约五到九项；再多就会削弱执行度（[Gawande，《清单革命》](https://www.shortform.com/blog/types-of-checklists/)）。并且优先采用 Shingo 所说的**控制**而不是**警告**（[防错](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，会输给完成任务的冲动；而阻止流程继续进行或强制生成某个产物的步骤则完全不需要警觉性。在 skill 只能发出警告的地方，至少要把警告放在作出决策的位置——**写在执行上下文永远不会打开的参考资料中的规则，在实践中就不是规则。**

另一方面，他们可能已经有了 skill 的草稿。遇到这种情况，你可以直接进入循环中的评估/迭代部分。

当然，你始终应该保持灵活；如果用户说“我不需要运行一堆评估，和我一起凭感觉来就行”，那你也可以照做。

然后，在 skill 完成之后（不过再说一次，顺序是灵活的），你还可以运行 skill description improver。我们为此专门准备了一个独立的脚本，用来优化 skill 的触发效果。

## 首先：共存检查（官方 skill-creator 插件）

在进行任何操作之前，快速检查一次（在常见路径下无需输出任何内容）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 什么也不做——不要安装任何东西，也不要向用户提及本节内容。继续进行当前协作。
- **存在：** 官方插件中的 skill-creator 与此版本现在会以几乎相同的描述出现在 skill 列表中，因此未来的会话将随机在两者之间进行路由。用一到两句话告诉用户这一点，然后提供以下选项（绝不要未经用户同意就执行）：
  1. **推荐** — 运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的自检 SessionStart hook 复制到用户的 Claude 配置中，并将其注册到 `settings.json`（同时创建备份），这样今后的每个会话都会确定性地将 skill 相关工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；官方插件在按名称请求时仍然可以完全正常使用。在未安装官方插件的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的 hook。
  2. 备选方案 — `claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），通过将官方条目完全移出 skill 列表来消除歧义。

如果 hook 已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上全部步骤。

同样的机制也适用于用户创建的 skill：当他们的 skill 有意与已安装的 skill 重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一套工具包——参见 Prior Art Research 下的“Coexistence & Precedence”和 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

## 与用户沟通

skill creator 可能会被各种编程术语熟悉程度不同的人使用。如果你还没听说过这种现象（怎么可能呢，这种趋势才刚刚开始），如今 Claude 的强大能力正激励着水管工打开终端，也激励着父母和祖父母去 Google 搜索“如何安装 npm”。另一方面，大多数用户可能具备相当不错的计算机素养。

因此，请注意上下文线索，以理解应当如何措辞交流！在默认情况下，可以参考以下标准：

- “evaluation”和“benchmark”属于临界情况，但可以使用
- 对于“JSON”和“assertion”，在不加解释地使用它们之前，你需要从用户那里看到明确的线索，确认他们确实了解这些概念

如果你不确定，简要解释术语是可以的；如果不确定用户是否能理解某个术语，也可以用简短定义加以说明。

### 使用 AskUserQuestion（重要 — 请阅读）

**在每个决策点都要积极使用 AskUserQuestion。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最大单项 UX 改进——用户可能需要同时处理多个窗口，而且可能已经有 20 分钟没看这段对话了。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明 skill 名称、当前阶段，以及刚刚发生了什么（1-2 句话）。用户可能已经切换去处理其他事情。
2. **简化说明**：用通俗易懂的语言解释这个决策。不使用函数名或内部术语。说明它会做什么，而不是说明它叫什么。
3. **给出建议**：先给出你的建议，并用一句话说明理由。如果选项涉及工作量，请同时展示两种时间尺度：`(human: ~X min / Claude: ~Y min)`。
4. **提供选项**：提供 2-4 个具体的、带字母标记的选项。每个选项都应是明确的行动，而不是抽象概念。

**规则：**
- 每次只做一个决策——不要把无关的选择合并到同一个问题中
- 提供退出路径（AskUserQuestion 始终隐含包含“其他”选项）
- 接受用户的选择——可以提醒权衡，但绝不能拒绝继续执行
- 如果存在没有权衡、显而易见的答案，则跳过提问（直接说明你将采取的做法）
- **如果问题超时且没有得到回答（用户暂时离开键盘），既不要停滞不前，也不要擅自推进品味或范围方面的决策。** 先完成不产生副作用的准备工作——编辑前快照、清单整理、评估用例收集、只读审计/健康检查——并在用户回来后再等待其对判断事项（重构方向、删除内容、是否继续）的决定。然后明确说明你完成了哪些工作，以及哪些事项正在等待用户决定。

## 创建 skill

### 捕获意图

先了解用户的意图。当前对话中可能已经包含了用户想要固化的工作流（例如，他们说“把这个做成一个 skill”）。如果是这样，先从实时对话中提取答案——使用了哪些工具、步骤顺序如何、用户做过哪些纠正、观察到的输入/输出格式。用户可能需要补充缺失信息，并应在进入下一步之前进行确认。

**来源清单——在起草之前始终执行，并明确征得同意的边界。** 盘点实时对话，以及与之有重叠的现有文档/skills（参见下文的既有成果研究）。更早的本地会话 JSONL 文件属于单独的私有来源：除非用户明确要求从历史记录中提取内容，或在你解释将读取哪些内容后明确批准该来源，否则不要打开或解析这些文件。如果获得批准，则通过对话挖掘工作流中的脱敏提取，仅将相关的历史会话纳入；绝不要将原始会话记录直接加载到你自己的上下文中。如果未获批准，则继续使用实时对话和现有项目来源，不要把缺失的历史记录视为阻碍。

在挖掘对话（或会话记录）时，要同时盘点两类资产——它们最终会放在不同的位置。*知识*——端点、参数、陷阱、决策规则——应成为 SKILL.md 中的指导内容，或放入 `references/`。*本次会话需要编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——则是 `scripts/` 的候选内容：如果这次会话编写了它，那么下一次调用时就必须重新编写，因此应将其参数化、完成清理并打包。一次既有的提炼过程曾捕获了经过润色的文案，却遗漏了可复用的辅助工具；其中的普遍经验是，要同时关注知识→references 和代码→scripts 这两条通道。

当源材料是*过去的*会话记录（Claude Code projects directory 下的 JSONL 文件），而不是当前正在进行的对话时，进入会话挖掘工作流。不要在主上下文中打开原始记录，也不要将原始路径/内容交给子代理。在任何代理看到内容之前，必须先完成确定性的 manifest → discover → redact → chunk 流程；只有经过脱敏的分块才可以进入最小角色/分片计划，并且必须在预算门禁下声明确切的单元数量和并发上限。

**首先，在回答下面的问题之前，先确定这是哪个方向。**请求可能属于几种相反的事情：构建一个新 skill / 编辑一个现有 skill / 优化 skill-creator 本身 / 或者根本不是 skill，而是一次性任务。猜错方向会浪费整个会话——你为“新 skill”所做的研究，并不适用于“优化元工具”。当措辞含糊时（例如，用户说“给我做一个 skill”，但指向的是 skill-creator 自身的路径），在这里提出一个 AskUserQuestion 只需 30 秒。下面的包装器 skill 分支是这种情况中的一个特例；方向检查本身是通用的。

`Use skill-creator to optimize <existing-skill>` 表示正常的现有 skill 更新路径。它不授权进行会话历史挖掘、广泛重写、Tier 3 分类或多代理评估。先检查实际拟议的变更；只有当这些变更确实引入了某个失败面时，才进行升级。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证这个 skill 是否有效？对于输出可客观验证的 skill（文件转换、数据提取、代码生成、固定工作流步骤），测试用例通常很有帮助。对于输出主观的 skill（写作风格、艺术、经过品味校准的报告），通常无法使用断言——但“没有断言”不等于“不验证”。它们的验证路径按成本从低到高依次为：
   - **历史任务重放**：重新运行一次该 skill 过去处理过的真实提示词，分别使用旧 skill 和新 skill，然后根据具体发生变化的规则比较输出（“新输出是否确实遵循了这次更新引入的 tokens / 标题语法？”）。成本低，可以捕捉到“规则写了出来，但没有任何内容读取它”这种问题。
   - **以生产过程作为评估**：承认真正的测试是用户下一次实际使用——然后明确这个闭环：之后用户的每次纠正都应作为一个事件纳入 skill 自身的“迭代/活文档”部分，每次认可都应成为语料库材料。一个发布时没有这种回写习惯的品味型 skill 不会改进；而具备这种习惯的 skill 无需正式评估就能逐步收敛。**而且，当 skill 的输出是一个会持续运行的东西——守护程序、监控器、定时任务、钩子——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。**用户纠正需要用户注意到问题并愿意反馈；而已部署的机制会主动报告自身情况，往往在一天内就能做到，误报则是这种报告最尖锐的形式，因为它证明你写下的某条规则是错误的，而且这是任何反复重读都无法揭示的。把第一次误报当作一次已安排的评估结果，而不是烦恼：在假定机制行为异常之前先检查它，因为更可能的发现是，*指令*写得过于绝对。（真实案例：某个 skill 规定必须使用失败即报错的检查；已部署的检查在夜间针对一个完全健康的条件触发过一次，最后修复的是 skill 中那句过于绝对的表述——没有人提出投诉；是遥测数据发现了问题。）
   - **渲染 + 人工审查**，用于视觉输出（使用 skill 自身的视觉 QA 门禁），绝不要用假装能够衡量美观度的 grep 断言。**而且，用来验证的渲染器必须与交付物实际使用的引擎相同**——无论安装了哪个方便的预览器，都不能替代它。布局引擎不同于目标应用的缩略图工具，会悄悄*隐藏*你正在寻找的确切缺陷；在错误引擎上得到绿色验证，比完全不验证更糟糕，因为它会制造虚假的信心。真实案例（2026-07）：一个 `.docx` 通过 macOS Quick Look 缩略图进行了“视觉验证”，但 Quick Look 无法复现两端对齐文本的拉伸；用户在 Word 中打开文档时，信息块立刻被撑得面目全非。修复方法是安装兼容 Word 的引擎（LibreOffice），转换为 PDF，逐页栅格化，然后阅读每一页。引擎必须匹配，否则验证就是演戏。**这一点也适用于渲染器之外的所有验证工具**——解析器、linter、验证器：它必须与生产环境共用同一实现，否则它显示绿色就没有意义。另一个同类案例是：某位作者试图捕捉一种会破坏最终文档的标记模式，却在源文件阶段使用了与生产工具链不同的 markdown 实现进行检查——该实现将三个已知有问题的输入全部解析为完全正常，因此任何建立在它之上的预检查都会悄悄放过所有问题。诚实的结论是，这种特定缺陷只有在生产工具运行之后才能检测到，检查就应该放在那里。**当没有任何可用工具与生产实现共用同一实现时，应明确说明该检查无法在那个阶段完成——不要构建一个只能产生虚假绿色结果的检查。**
   
   根据 skill 的类型提出适当的默认方案，但让用户自行决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认 skill 类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类会推动后续的整个评估策略。在这里做出正确判断，可以避免之后浪费精力。

### 扩展还是创建检查——在任何专门分支之前执行

下面的三个专门工作流都以“**do not** continue reading the sections below”结尾，而 *Prior Art Research* 恰好位于它们之后。这个顺序是排版顺序，而不是执行顺序。扩展还是创建的判断适用于每个分支；跳过这一步，正是导致会话交付出一个与已安装 skill 重复的 skill 的原因。

因此，在进入 wrapper-skill / conversation-mining / artifact-corpus 分支之前，先回答一个问题：**是否已经存在一个 skill，可以归入这一能力？**

**发现根目录，不要凭记忆。** 手工维护的安装位置列表正是最容易过时的产物，而你忘记的那个根目录，才是最可能造成问题的地方。

**搜索文件，而不是搜索名为 `skills` 的目录。** Skill 目录以 *skill* 命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、marketplace 克隆目录和插件缓存中根本没有名为 `skills` 的目录——搜索这个名称会悄悄跳过它们，同时看起来却像是在正常工作。每个 skill 都有一个 `SKILL.md`；这是与目录布局无关的定位方式。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，而且仍会返回比你需要的更多结果；请使用针对该能力的具体术语进行缩小，而不要使用通用术语（`chart` 会匹配所有内容，而 `stacked bar` 不会）。

这所触及的根目录——而通常凭记忆列出的清单会遗漏这些：技能源代码仓库（一个 `claude-code-skills` checkout 以及任何 `-pro` 兄弟仓库）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件——源代码仓库中的任何内容都不会暗示它们在那里）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、按配置文件划分的配置主目录（`~/.claude-profiles/<name>/`），以及——完全没有任何路标的那个——**每个项目自己的 `.claude/skills/`**。第 2 步会让这成为你验证过的结论，而不是你继承来的说法。

**按项目划分的技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何 marketplace、全局技能列表或源代码仓库列表里；你在规划新技能时通常会打开的地方，没有任何内容会提到它们。真实案例（2026-07）：某次会话为一个领域构建了全局技能，检查了源代码仓库、全局目录和其他代理的目录，什么也没找到，然后完成了交付。后来对话历史搜索发现，某个项目级技能正好覆盖该领域，已经存在了一个月，位于某个项目的 `.claude/skills/` 中——其中有八条新技能缺少的规则，包括一条用户亲自规定的规则。除了按项目划分的目录外，每个根目录都检查过了，但这次扫描仍然非常自信地报告“没有既有成果”。

**当重叠的内容确实是某个无关项目中的项目级技能时该怎么做**——这正是上述往事会把你带入的情形，也是下面三个要点没有涵盖的情形：你无法向一个根本没有该兄弟技能的套件添加兄弟技能，而“扩展它”就意味着编辑某个无关项目的工作树。行之有效的做法是：**将它的规则提取到你正在构建的技能中，然后在所有者同意后停用项目本地技能**——它是针对实际工作编写的，因此应将其视为更成熟的来源，并朝着它进行协调。停用他人的工作技能是所有者的决定，而不是构建过程的副作用。

这句话遗漏了四件事，其中每一件都可能让你停下来：

- **“朝着它进行协调”是可反驳的推定，不是规则。** 两种标准的退出方式：项目技能可能已经*过时*（几个月前针对一个已经发生变化的系统编写的规则），也可能是*项目特定的*（只在该项目约束下成立的规则——将它们整体导入会让你的技能变得狭窄，而本文其他地方会告诉你不要这样做）。提取的规则是另一位作者的记忆，因此要像纪律 #1 要求你对写入技能的任何内容所做的那样，**重新验证每一条规则**。
- **“停用”需要一个机制，而且第一步并不是你下意识会采取的那一步。** 顺序如下：

  1. **先用 `find` 查找技能的*实体文件*，再 grep 查找它的*引用*。** 同一个仓库中的一个技能通常不止有一份副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被加载，只是由同一工作树中的不同工具加载。Grep 能回答“谁提到了它”；只有 `find` 能回答“它到底有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放入 `--exclude-dir`**（它按 basename 匹配，因此会隐藏所有同名目录，包括你尚未找到的那份副本——参见纪律 #6 中的工具规则）。真实案例（2026-07）：某次停用正是这么做的，修复了它找到的全部五处引用，却在 `.agents/skills/` 下留下了第二份完整副本——该副本被 git 跟踪，没有停用标记，是一份缺少最新规则的过时快照——另一个工具仍会将它作为有效技能加载。
  2. **在删除任何内容之前，确认新位置确实可以从旧位置所在的地方访问到**，*然后*再删除任何内容——你刚推送的 marketplace 技能，在 marketplace 更新且插件安装之前，并没有安装好；如果先停用旧技能，就会留下新旧皆无的窗口：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常会符号链接到源代码仓库，而不带 `-L` 的 `find` 会报告文件不存在（参见纪律 #6 中的工具规则）。
  3. **然后** grep 查找引用，并重新指向仍在使用的引用。区分**有效指令**（技能列表、交叉引用、告知下一个代理应使用什么的交接文档）和**历史记录**（决策日志中写着“我们在 X 日期交付了这个”）——改写后者会破坏审计线索，只为修复一个并不存在的问题。
  4. **然后**将每个实体文件替换为 `superseded by <skill>` 存根，而不是直接删除，并确保每份副本的存根逐字节一致。**保留 YAML frontmatter**——没有它的 `SKILL.md` 可能会加载失败，却不会提供有用的失败信息——但要重写 `description`，让存根声明自身已经停用，而不是继续宣传旧的触发条件；否则它会继续赢得自己已经不再负责的路由。正文只需包含：能力转移到了哪里，以及为何转移的一行说明。
- **使用下面的所有权测试识别所有者**（这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍然会告诉你它属于谁）。当所有者就是你正在交谈的人时，“同意”只需要一次 `AskUserQuestion`。**当所有者无法联系时，只提取规则——不要停用**（这样会让两个技能同时处于有效状态，并争夺同一个触发条件；其最终结果与被拒绝停用相同——参见下面的“共存与优先级”）。
- **如果所有者拒绝停用它**，那么现在就有两个技能在争夺同一个触发条件；这属于下面的“共存与优先级”问题，而不是失败。

**按能力词汇搜索，而不是按 skill 名称搜索。** 该项目 skill 不会匹配新 skill 标题的名称搜索；它匹配的是其正文中的领域术语。请在候选根目录中 grep 新 skill 将要处理的*概念*。

如果存在重叠：

**如何判断适用哪条规则——这个 skill 属于谁？** 文件系统命中结果不会携带所有权信息。读取 marketplace 的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在其所属仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中项完全可能只是你自己的 marketplace 被安装回了你的机器。项目级 skill 没有 `marketplace.json`，但其项目的 `git remote` 可以回答同样的问题。

有两种情况，探测结果会判断错误或无法回答，因此在相信结果之前请先检查：**fork** 会显示你自己的 remote，但其中的内容可能属于他人——应将其视为第三方，因为他们上游的改进仍然无法传递给你。还有，当**不存在 marketplace.json 和 remote** 时（本地项目、手动复制到全局 skills 目录中的 skill），探测结果是无声的，而不是否定性的：**询问所有者，不要猜测。**

- **重叠的是第三方的 skill**（某个 marketplace 套件、官方插件）：**不要重新实现它的能力。** 编写一个能够正确驱动它的*薄增量*——记录你遇到的陷阱、正确的调用方式，以及经过验证的辅助脚本——并**使用命名空间名称引用它**。把别人的引擎克隆进自己的 bundle 是代价高昂的错误：他们的升级将无法传递给你，而两份副本会在无声中逐渐分叉。
- **重叠的是你自己的 skill**：扩展它，或在其现有套件中添加一个兄弟 skill。一个争夺相同触发条件的独立 skill 对任何人都没有帮助。**例外：**如果它位于*无关项目*的工作树中，那么以上两条规则都不适用——请参阅上面的项目级情形。
- **某个相关 skill 已经指向你正在填补的缺口**（例如其描述写着“对于 X，请使用 Y”）：构建完成后要闭环——更新该指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才构建独立 skill。

**为什么这项检查值得放在最前面：**一次真实的 2026-07 会话花了一天时间，让一个第三方 docx 引擎生成正确的中文商务文档，随后又转向 wrapper-skill 分支——而该分支直接跳过了 Prior Art Research。它正准备发布的形态，是一个重新携带该引擎能力的新 skill。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个包含正确用法和经过验证的生成器脚本的薄增量 skill → 领域工作流 skill 调用该增量。用户不得不纠正两次才最终落地，第二次纠正更加准确：*“不要再复制一个额外的——在他们的基础上写出正确用法，并引用他们的 skill；这就是 skill-as-code 的含义。”*

### 验证深度路由器（在选择任何工作流之前运行）

在选择通用或专用工作流分支之前，先选择能够证伪变更后行为的**最低层级**。应根据具体变更及其失败面进行分类，而不是根据行数或请求用词：一条变更的破坏性命令可能比一大段措辞清理更应归入高层级，而要求“优化”现有 skill 也可能只是一个有界的修正。在选择层级之前，列出你确实打算变更的规则、契约、脚本、权限和输出。如果尚未确定这份清单，就先进行检查并暂定分类；范围不确定并不能作为归入 Tier 3 的依据。

| Tier | 适用情形 | 所需证据 | 默认不添加 |
|---|---|---|---|
| **1 — 定向** | 这是一个现有 skill；未新增或实质性变更任何能力、触发器族、工作流分支、输出契约、依赖、权限或外部写入行为；且编辑内容恰好属于以下一种：(a) 不会改变行为的拼写/格式修正，(b) 其真实性由直接权威来源决定的事实性文档/配置修正，或 (c) 修复明确的现有契约的有界实现修复，**并且**修复后的行为由确定性回归检查覆盖。可能改变 agent 行为的澄清不属于 Tier 1 | 对于三种情况都要运行 `quick_validate`、检查差异，并完成现有 skill 迁移门禁。之后只使用相匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其针对性检查；(c) 明确的现有契约加确定性回归。只有在越过规范 #5 的规则/契约/数值阈值时，才添加一名新的审阅者 | agent 行为回放、成对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 抽样行为** | 这是一个现有 skill；变更会影响 agent 行为，但未新增能力、触发器族、输出契约、脚本行为、依赖、权限或外部写入；并且 1–2 个具有明确验收标准的具名示例即可覆盖整个变更行为。对一个现有路由或证据选择规则的有界修正即使改变了所选择的路径，也仍属于此层级 | 仅运行这 1–2 个具有代表性的带 skill 回放，以及针对性的确定性检查和规范 #5 要求的一次全新上下文审查 | 默认不添加基线、成对扇出、方差分析、基准测试、查看器或评估文件。若明确要求这些内容，应通过单独的证据预算门禁处理，且不会重新划分变更层级 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新 skill；任何新增或实质性变更的能力；广泛的跨分支重写或方法论扩展；触发器/描述优化；新的工作流分支，或实质性变更的输出契约、脚本能力、依赖或权限；高风险自动化或外部写入；或者变更后的行为本身覆盖 3 个以上不同的提示类别、重复试验或实质不同的方法 | 先运行确定性门禁，然后仅添加针对已命名失败轴所需的证据。只有在单独的重型评估授权门禁通过后，才可以使用下方完整的成对流水线；Tier 3 本身不会启动该流水线，同一门禁也可以授权在其他层级添加额外证据 | 不能仅根据 Tier 3 标签自动添加成对扇出、评分器、基准测试或查看器 |

#### 重型评估授权门槛——独立于层级分类

层级描述的是**风险和不确定性**；它并不授权消耗令牌或进行智能体扇出。通过此门槛会改变获准的证据方案，而不会改变层级。通用的 paired baseline → grader → benchmark → viewer 流程只有在以下任一条件满足时才可以运行：

- 用户明确要求进行 A/B、基线、基准测试、重复试验、查看器或多智能体评估；或
- 执行者能够列出至少三类不同的提示词、多个具有合理性的竞争性结果，以及配对比较将会改变的决策，然后获得用户明确选择加入的同意。

对于现有技能优化，默认使用零个评估智能体：先运行确定性检查；如果行为仍不确定，再最多进行一到两次带技能重放。规范 #5 中的一个新鲜上下文审查者是发布门槛，而不是创建审查者团队的许可。任何令牌/成本敏感指令都会阻止重型流程，直到用户明确撤销该限制。

在生成多个研究、挖掘、评估或评分智能体之前，先将**角色**与**执行单元**区分开来：

- 每个额外的角色或审查者都必须负责一个不同的失败轴或输出。模板可用性绝不是增加另一个角色的理由。
- 必要的实验分支和语料分片可以共享同一个轴：带技能分支和基线分支需要彼此隔离的上下文，而一个挖掘角色可能需要处理多个有界分块。在启动之前，说明确切的单元总数、并发上限，以及为什么合并它们会污染比较结果或超出分块预算。默认按串行方式运行；明确的 A/B/挖掘请求只授权这些必要单元，不授权额外角色。
- 对于执行者提出而非用户明确要求的扇出，须获得用户对该数量的选择加入同意。如果交互式提问工具不可用或用户没有回答，则采取较轻量的证据路径；沉默不等于同意。

如果某个单元既不是独立的角色/输出，也不是必要的隔离分支/分片，则不要生成它。

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，升级处理。用户要求取消或降低评估级别时，应立即停止已经启动的配对评估智能体、基线、评分器、聚合和查看器工作。如果风险分类仍具有参考价值，则予以保留，但只报告实际运行的证据和仍未检查的轴；不要将未运行的重型测试套件描述为由该标签自动“要求”的内容。当其规则/契约/数量阈值被触发时，不要取消规范 #5 中的单个新鲜上下文审查者，也不要取消任何为防止破坏性影响或外部影响所必需的安全门槛。机械式的现有技能迁移审计、公共技能清理，以及任何特定领域的安全门槛，也都独立于此路由器而继续执行。

### 专用工作流：第三方 CLI 工具的包装器技能

在确定采用通用技能创建流程之前，检查截至目前的会话是否实际上需要改用**包装器技能**工作流。包装器技能是一种伴随技能，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或技能包——这些代码由他人编写，而用户刚刚花费一个会话让其在自己的机器上运行起来。

适用信号（以下任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 会话中出现了真实、具体的错误消息，用户和 Claude 也针对这些错误制定了具体的修复方案（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个整理成一个 skill”“把这个保存成一个 wrapper skill”“这样其他人就不用再经历这一遍了”“把这次 session 做成一个 skill”的话。
- 用户明确提到某个第三方工具的名称，并希望其他代理或其他人能够使用它，而不必再经历自己付出的学习成本。

明确不适用的信号（改用上面的通用工作流）：

- 用户想要为某个准备从头开始编写的内容创建 skill。
- 会话进展顺利——没有值得提炼的实际摩擦。
- 该 skill 封装的是用户拥有或控制的服务（这是用户自己的代码；应直接编辑源代码，而不是进行封装）。
- 这个“工具”实际上是一种不涉及安装任何二进制文件或软件包的方法论或工作流。

当 wrapper skill 工作流适用时，保留上面选定的验证级别。创建 wrapper 就是在创建新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用编写章节；跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾式提炼**工作流——其职责是从当前对话中挖掘安装流程、已修复的 bug 以及已经做出的设计决策，并将挖掘结果转化为一个完整、自包含的 wrapper skill，使其他用户无需重新经历调试会话即可安装并从中受益。

wrapper skill 工作流有自己的架构契约、代码模板和 Tier 3 验证协议——它会替代不兼容的通用测试用例机制，因为其输出是用户的安装状态，而不是一个可以轻易断言的文件；这并不意味着降低工作级别。运行证据计划所选定的兼容通用步骤；通用的成对评估步骤仍然需要经过重型评估授权门槛。记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库根目录——当这个 skill 被移入一个套件后，这里一个裸的相对链接已经失效过一次，正如下面的跨 skill 引用规则所警告的那样），它是对 Tencent IMA skill 的封装，依据一次真实会话并使用这一完整工作流提炼而成。

### 专用工作流：从对话历史中丰富 Skill

在开始通用 skill 创建流程之前，检查当前会话是否实际上是在请求将**过去的对话提炼成一个 skill**。当用户在多次 Claude Code / Codex 会话中调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这种方式非常有用。

**必须有明确的来源意图。** 长时间进行中的对话、最近完成的调试任务，或 `use skill-creator to optimize <skill>`，都不表示用户同意打开本地历史记录，也不是进入此工作流的理由。对于普通更新，直接使用当前对话。只有当用户明确要求挖掘/提炼更早的本地对话，或指出特定的过往会话作为源材料时，才进入对话挖掘流程。

适用的信号（必须全部满足）：

- 用户明确将本地/过去的对话历史指定为输入，例如“挖掘我的聊天记录”“根据之前的会话丰富此 skill”或“把以前的对话沉淀到 skill 里”。
- 源会话以及时间/范围边界已知或已确认。
- 目标输出是可复用的知识或代码资产，而这些内容无法仅从当前对话和现有 skill 包中表达出来。

不适用的信号（改用上面的通用工作流）：

- 用户正根据单个提示或想法创建全新的 skill。
- 用户要求优化现有 skill，但没有要求读取以前的本地历史记录。
- 相关的修正和证据已经存在于当前对话中。
- 用户想要为刚安装的第三方 CLI 工具创建包装器（使用上面的包装器 skill 工作流）。
- 没有可挖掘的本地对话历史，也没有可处理的会话转录导出文件。
- 被挖掘的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件。
- 源材料是一批用户已认可的已完成成果，而不是对话——使用下面的成果语料提炼工作流。

当对话挖掘工作流适用时，保留上面选定的验证层级。新挖掘的 skill 为第 3 层；丰富现有 skill 时，只有在满足该层级能力边界的情况下，才能保持选定的层级。**不要**继续阅读下面的通用编写章节；跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端遵循该工作流，包括其验证协议。这是一个**回顾式提炼**工作流：发现获批准的本地历史记录，对其进行脱敏和分区，仅运行由语料库证明合理的挖掘过程，并在验证后提升经过审查的候选内容。

对话挖掘工作流拥有自己的架构契约、代理提示词、模板和验证协议。该协议实现了所选层级的专用机制；根据证据计划运行所选的兼容通用步骤，将繁重的通用步骤置于其授权门禁之后，并记录任何替代方案。这是将明确批准的对话历史转化为 skill 可复用知识库的规范方式。

### 专用工作流：从已批准成果语料库中提炼用户偏好

在提交通用流程之前，检查当前会话是否要求**从用户认可的一批已完成成果中提取其真实偏好**——例如已批准的 HTML 报告页面、生成的文档、设计。这是第三种提炼来源，与前面两种不同：材料是**产品，而不是对话**；输出是**可执行的审美偏好**（明确的原则、量化的参数和词汇），而不是知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的成果，并说“这些都是我认可的样例”/“你来学到底什么是我想要的”/“extract my preferences from these approved examples”。
- 一项品味校准技能（报告生成器、文档样式处理器、演示文稿构建器）的认可样例语料库不断增长，而用户要求让该技能从中*学习*，而不只是将其编入索引。
- 用户抱怨之前的更新“只加了示例”——只是将样例编目，却没有改变技能的行为。

不适用信号：源材料是对话/修正，而不是获得认可的产物（使用 conversation-mining）；样例并未得到用户本人认可（认可是一道准入门槛——先询问）。

适用时，保留上文选定的验证层级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新的语料库衍生技能属于 Tier 3；向现有技能添加实质性的新决策能力也属于 Tier 3。专门协议实现所选层级的语料库机制，不会降低其层级；根据证据计划运行兼容的通用步骤，将繁重的通用步骤继续置于其授权门槛之后，并记录任何替代操作。其核心纪律同样适用于向现有技能添加材料的任何时候：**编目 ≠ 蒸馏**——在语料库表中登记一个样例，并不会改变技能下一次运行时的行为；对于每一项新增内容，都要问自己“*这会改变一条决策规则吗？*”，并且在所写入的所有内容都没有改变决策规则时，不得宣布蒸馏会话已完成（方法论 Case 15）。工作流的主线：对 ALL 个产物进行脚本提取的定量比较（每种模式至少达到 ≥3-artifact threshold，并对所声称的恒定项检查例外列表）→ 以证据锚点为基础的分层归纳 → 写入决策规则层（区分不变量与依赖语域的变量）→ 独立的完整性审计（standing discipline #5）→ 回归审计。

### 先例研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策和竞争优势——正是技能有价值的原因。公共仓库无法提供这些内容。但当成熟工具已经存在时，用户不应浪费时间重新发明基础设施（API 客户端、身份验证流程、速率限制）。先例研究用于寻找基础设施层可复用的构件，让技能能够专注于编码用户独有的方法论。

**两个轴，不要混淆。** 本节为*基础设施*层寻找来源（可复用的工具 / MCPs / 库 / 现有技能）。*方法论*层本身有两个输入：用户的私有优势（只有用户自己拥有，无法检索）**以及领域中已经确立的最佳实践 / 科学知识，你应根据 standing discipline #3 的要求默认将其检索到上下文中。**找到合适的工具并不能免除第二项要求——一个采用图表库却从未吸收 Cleveland/Bertin 的可视化技能，仍然受限于你的预训练知识。两者都要做。

**按以下顺序搜索这些渠道。** 默认进行内联研究。只有在上面的重度评估/代理预算门槛确认确实存在相互独立的未知信息后，才使用子代理；公共来源渠道并不是默认的并行搜索集合。

| 优先级 | 渠道 | 搜索内容 | 方式 |
|----------|---------|---------------|-----|
| 1 | **实时对话或明确批准的历史记录** | 用户已验证的工作流、经过验证的 API 模式、调试过程中做出的修正 | 直接使用当前对话。只有在通过上面的明确来源门槛后，才搜索更早的本地历史记录；随后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 针对同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 能够发现用户自己的已验证模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终具有优先权——公共工具是构建模块，而不是替代品。在竞争性领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**倾向于合并/扩展，而不是新建，并扫描每一个技能根目录——不要只扫描 `~/.claude`。** 当渠道 1-3 发现已有技能与请求的领域存在重叠时，通常正确的做法是扩展或合并到其中——**但如果它位于无关项目的工作树中，则应反过来：从中提取内容，融入你正在构建的技能，而不是合并到其中**（参见上面扩展与新建检查中的项目级案例）（某个实际的“新建技能”任务最终变成了“让现有的提取器充当新归档器的提取阶段”），而不是交付一个会与相同触发条件竞争的并行技能——两个重叠的技能会争夺触发机会并使用户困惑。搜索时，**应发现安装根目录，而不是凭记忆回想一个列表**——使用扩展与新建部分中的 `SKILL.md` 扫描及其覆盖范围自检（搜索名为 `skills` 的目录会遗漏源代码仓库、市场克隆版本和插件缓存，因为它们的技能目录是按技能命名的；仅凭这一点就会完全漏掉它们）。运行覆盖范围检查，而不是相信这句话：**每个项目自己的 `.claude/skills/`** 是凭记忆列出的清单最容易漏掉的根目录，因为项目外部没有任何内容会引用它。用户已经在任何位置安装的技能，都是最有力的先例；而项目本地的技能通常最为成熟：它是针对真实工作编写的。

**如果发现公共 MCP 服务器或 skill，请克隆并进行验证——不要盲目信任 README：**

1. **阅读实际源代码**——许多项目的 README 写得很精美，但代码库却是空壳
2. **验证身份验证方式**——它是否与 API 的实际身份验证方式一致？（`X-Api-Key` 请求头 vs `Bearer` vs `OAuth`——很多项目在这里都搞错）
3. **检查测试覆盖率**——零测试 = 原型，而不是生产级项目
4. **检查维护情况**——最后提交日期、未解决 issue 数量、对 bug 报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有软件使用冲突
7. **检查依赖规模**——庞大的依赖树会带来冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 负责基础设施 | **采用它，在其基础上构建**——安装 MCP，然后将 skill 构建为工作流层，用于编码用户的方法论 |
| 存在部分 MCP 或 SDK | **扩展**——使用它负责基础设施，并在 skill 中补齐缺口 |
| 公共 skill 覆盖相同领域 | **仅用于获取结构上的灵感**——竞争领域中的公共 skill 按定义都是通用的。用户的优势在于其私有 SOP |
| **存在提供你正在构建的功能的某项子能力的互补 skill** | **将其打包**——把互补 skill 的自包含资源复制到你的 bundle 中，并将它们连接起来。不要依赖用户预先安装该 skill。请参阅下方的“互补 Skills” |
| 没有任何公共资源 | **从头构建**——在编写完整 skill 之前，先验证 API 访问模式是否可行（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——一个由你掌控、耗时 2 小时的定制实现，胜过一个集成摩擦大且存在上游风险的“成熟”工具 |
| 用户有意取代已安装的 skill（分支版本、加固版） | **携带 supersede kit 一同发布**——请参阅下方的“共存与优先级” |

#### 共存与优先级（有意重叠）

将内容合并到现有 skill 中是解决重叠问题的默认方式（如上所述）。但是，当用户*有意*发布一个与已安装 skill 存在重叠的 skill——例如官方插件的分支版本、经过加固的内部版本——这两个条目会以相似的描述出现在 skill 列表中，Claude 将随机决定在它们之间进行路由。请按以下逐步升级的顺序解决这一问题：如果重叠是意外的，则重命名；添加描述中的决胜语句（“取代 X——当两者同时出现时，始终使用此项”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式 supersede kit 写入 skill——这是一个基于同意的 SessionStart 路由钩子，仅在实际存在竞品的机器上安装，在其他机器上拒绝安装，并且在任一方消失时自动禁用。机制、决策表、SKILL.md 示例措辞以及沙箱验证请参阅：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此 skill 针对官方 skill-creator 插件使用了同一个 kit（请参阅顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄无声息地输给了*已安装技能群体*的触发竞争。** 一个技能的领域（图像生成、PDF 处理、仪表板）通常已经有多个已安装技能，新的技能可能会失去对所有这些技能的自动路由。因此，**要尽早验证触发情况——内容写得好并不意味着构建就完成了。** 草稿完成后，通过 `claude -p` 发送几个现实的查询，并检查新技能是否真的**胜出**；如果没有，**明确指出它输给了哪个具体竞争者**（不同查询可能会输给不同技能）。然后要了解两点：(1) **在竞争拥挤的触发位中，仅靠措辞并不总能胜出**——解决阶梯是：重命名 → 描述决胜/ SUPERSEDES → 手动调用 → SessionStart 路由钩子（结构性方案；会修改全局配置，因此需要用户明确同意，对待方式应与 `--no-verify` 相同）；以及 (2) **修复方式取决于竞争者的作者**——竞争者是*第三方*的 → 接受手动调用或路由钩子；竞争者是*你自己的* → 将它们合并/整合为一个，不要让自己的两个技能争夺同一个触发条件。（完整的解决阶梯位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md) ——该文件是 SSOT；此处及上文的摘要只是指引，不要独立扩展它们。）记录所选择的路径（例如添加一条“Activation”说明：“手动调用，竞争者是第三方”），可以避免下一次会话重新争论这个问题。（方法论案例 13）

##### 互补技能（打包，而不是依赖）

当构建的技能涉及一个已有互补技能的领域时，你有两个选择：

- **依赖该技能已安装**：很脆弱——用户可能没有安装它，或者安装的是不同版本。每一次依赖缺失导致的失败，归根结底都源于这个选择。
- **将其打包**：把互补技能的自包含资源（脚本、模板、参考文档）复制到你自己的包中，并将它们连接起来，使你的技能能够独立工作。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包。** 以下情况尤其重要：
- 状态栏 / UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证 / 清理脚本
- 常用的数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要状态栏。`statusline-generator` 技能提供 `generate_statusline.sh`。与其依赖用户先运行 `statusline-generator`，不如由配置文件设置技能将 `statusline.sh` 打包，并在 `claude-profiles-init` 期间将其连接到每个新配置文件中。这两个技能仍然可以独立发挥作用，但包装技能能够独立工作。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装器”。这会把依赖转嫁给用户，并造成脆弱的安装顺序。应改为打包。

研究完成后，通过 **AskUserQuestion** 呈现发现：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，优先采用成熟的基础设施来处理底层连接与支撑，并在其上构建定制逻辑来实现方法论层——价值就在这里。

### 访谈与研究

主动询问有关边界情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在这部分内容理清之前，不要开始编写测试提示词。

在研究过程中，适时检查可用的 MCP（搜索文档、查找类似技能、了解最佳实践）。默认以内联方式进行研究。仅针对单独且尚未解决的问题使用子代理，绝不要因为工具可用就自动并行展开。准备好相关上下文，以减轻用户负担。

### 编写 SKILL.md

根据用户访谈结果，填写以下组件：

- **name**：技能标识符
- **description**：何时触发、技能做什么。这是主要的触发机制——其中应同时包含技能的功能，以及具体的使用场景。所有“何时使用”信息都放在这里，而不是正文中。注意：目前 Claude 有倾向于“触发不足”——在技能有帮助时也不使用它。为避免这种情况，请让技能描述稍微“主动”一些。例如，与其写成“构建一个简单快速的仪表板，用于展示 Anthropic 内部数据”，不如写成“构建一个简单快速的仪表板，用于展示 Anthropic 内部数据。只要用户提到仪表板、数据可视化、内部指标，或希望展示任何类型的公司数据，即使他们没有明确提出要做一个‘仪表板’，也务必使用此技能。”

  **控制长度：description 有严格的 1024 字符上限，超过后验证将失败。** 这与上面的“主动”建议直接存在冲突——每增加一个触发短语来扩大覆盖范围，都会消耗预算，因此应在扩展之前而不是之后进行衡量：使用 `len(description)`，而不是凭感觉判断。真正容易踩坑的并不是第一版（通常很少接近上限），而是*多年后的更新*，因为那时为了涵盖新范围而加入触发词：成熟的描述通常距离上限只剩几十个字符，此时**增加一个触发词就意味着零和博弈——必须删除现有触发词来为它腾出空间。** 请有意识地做出这种取舍，并在提交中说明，因为悄无声息地删除触发短语实际上会缩小技能触发的场景，而在它不再为某人触发之前，没有人会注意到。（实践中曾出现过这种情况：一次更新为新覆盖的故障模式增加触发词，将描述推到了 1280 个字符，随后经过两轮压缩才降到 1003——代价是删掉了三个原有触发短语。这本应是一个明确的决策，而不是在与验证器斗争时才意外发现。）必须删减时，优先删除那些仍可通过同义词或同类短语触达的场景，保留没有其他入口的短语，并记住，正文中的限定语（例如“在平台 X 和 Y 上”、括号中的枚举）通常比独立的触发短语更容易删减——正文可以从主体内容中重新推导，而触发短语无法如此恢复。
- **compatibility**：所需工具、依赖项（可选，极少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。通过 `---` 标记之间的以下字段配置技能行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必填 | 描述 |
|-------|----------|-------------|
| `name` | 否 | 技能的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 建议填写 | 技能的功能及使用时机。Claude 使用此字段来决定何时应用该技能。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在派生的子代理上下文中运行。** 请参阅下文的“内联 vs 派生：关键决策”——选择错误会导致技能失效。 |
| `agent` | 否 | 设置 `context: fork` 时要使用的子代理类型。可选值为 `Explore`、`Plan`、`general-purpose`，或 `.claude/agents/` 中的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 可阻止 Claude 自动加载此技能。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false` 可将其从 `/` 菜单中隐藏。适用于用户不应直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略它可让技能获得完整的工具访问权限，并由用户的权限设置进行控制。设置它会不必要地限制技能的能力。 |
| `model` | 否 | 此技能处于活动状态时要使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于表明预期参数。例如：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此技能生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** 技能内容中的 `$ARGUMENTS` 会被用户在技能名称后提供的文本替换。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### 内联 vs 派生：关键决策

**这是设计技能时最重要的架构决策。** 选择错误会悄无声息地破坏技能的核心能力。

**关键限制：子代理无法再创建其他子代理。** 使用 `context: fork` 运行的技能（作为子代理）**不能**：
- 使用 Task 工具创建并行探索代理
- 使用 Skill 工具调用其他技能
- 编排任何多代理工作流

**决策指南：**

| 你的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **Inline**（无 `context`） | 子代理无法生成子代理 |
| 调用其他 skill（Skill 工具） | **Inline**（无 `context`） | 子代理无法调用 skill |
| 运行 Bash 命令执行外部 CLI | **Inline**（无 `context`） | 主上下文中拥有完整的工具访问权限 |
| 执行单个聚焦任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境干净 |
| 提供参考知识（编码约定） | **Inline**（无 `context`） | 指南可以丰富主对话 |
| 被其他 skill 调用 | **Fork**（`context: fork`） | 必须作为子代理才能被生成 |

**编排器 skill 示例（必须为 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专业 skill 示例（fork 是正确选择）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，无 task）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skill 应当是**正交的**：每个 skill 处理一个关注点，并通过组合相互协作。

**模式：编排器（inline）调用专业 skill（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（不能使用 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个 skill 只负责一项职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法论，而不是重复代码

##### 流水线交接（顺序 Skill 链式调用）

除了编排器/专业 skill 组合之外，skill 通常还会组成**顺序流水线**，其中一个 skill 的输出是下一个 skill 的输入。每个 skill 在完成工作后，都应主动建议逻辑上的下一步。

**模式：SKILL.md 末尾的“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界中的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
read-claude-code-history → continue-claude-code-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion **由用户选择启用**——绝不能未经询问就自动调用下一个 skill
2. 仅当输出能够自然地作为另一个 skill 的输入时才提出建议——不要强行建立连接
3. 包含一个“No thanks”选项——用户可能不需要完整的流水线
4. 建议中应解释**为什么**下一步会有帮助（例如：“ASR 输出通常包含识别错误”）
5. 最多保留 1-2 个建议——选项过多会导致决策疲劳

**何时添加交接：**询问“这个 skill 的输出是否通常会成为另一个 skill 的输入？”如果是，则添加一个“Next Step”部分。如果这种连接很少见或牵强，则不要添加。

**反模式：**串联没有自然数据流的 skill。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 优先自动检测，而不是手动标志

**绝不要为可以自动检测的能力添加手动标志。**不要要求用户传递 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: 自动检测并告知用户
Step 0: 检查可用工具
  - `which codex` → 如果找到，则告知用户并启用跨模型分析
  - `ls package.json` → 如果找到，则针对 Node.js 项目调整提示词
  - `which docker` → 如果找到，则启用基于容器的执行

# Bad: 手动标志
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力自动检测，范围由用户决定。skill 应发现它能够做什么并据此采取行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | You can invoke | Claude can invoke | Subagents can use |
|-------------|----------------|-------------------|-------------------|
| (default) | 可以 | 可以 | 否（内联运行） |
| `context: fork` | 可以 | 可以 | 可以 |
| `disable-model-invocation: true` | 可以 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 可以 | 否 | 可以（显式委派时） |

#### 渐进式披露

Skills 使用三级加载系统：
1. **元数据**（名称 + 描述）——始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文**——skill 触发时位于上下文中
3. **捆绑资源**——按需加载（无限制，脚本可以在不加载的情况下执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。一份没有废话的 600 行 skill，优于一份遗漏关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问自己：“每个部分是否都发挥了作用？”如果答案是肯定的，就保留它。如果某些部分只是凑篇幅，或是在解释 Claude 已经知道的内容，就删减这些部分——不要删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分到引用文件中，而不是人为地把所有内容硬塞进一个简短的主文件。
- 对于现有 skill，渐进式披露是一种重新放置策略，而不是删除启发式规则。旧的运行时契约必须仍然可以从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或审阅者记忆都不能替代运行时内容。
- 在 SKILL.md 中清晰地引用参考文件，并说明何时读取它们
- 对于较大的参考文件（>300 行），请包含目录

**领域组织**：当一个 skill 支持多个领域/框架时，按变体进行组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的 reference 文件。

#### 不令人意外原则

这无需赘述，但 skill 不得包含恶意软件、漏洞利用代码，或任何可能危及系统安全的内容。如果对 skill 的意图进行描述，其内容不应让用户感到意外。不要迎合创建误导性 skill 的请求，也不要创建旨在促进未经授权的访问、数据外泄或其他恶意活动的 skill。不过，类似“扮演某某角色”的内容是可以的。

#### 写作模式

在说明中优先使用祈使句。

**定义输出格式**——可以这样写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——加入示例很有帮助。你可以像这样进行格式化（但如果示例中使用了 “Input” 和 “Output”，可能需要稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得融入 skill 的可用性模式**——以下四个结构性元素曾多次将“能用但令人困惑”的 skill 转变为用户真正能够驾驭的 skill——它们是让一个被广泛使用的 skill 变得易用的具体改进，因此当 skill 具有多种模式、会运行命令或可以重复运行时，应考虑采用它们：
- **入口决策树**：如果 skill 有多种模式，请在开头提供一个简短的“用户说了 X → 使用模式 Y”映射，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧跟在命令之后展示“你应该看到的内容”，这样模型（以及用户）就能区分真正的成功和无提示的失败。
- **故障排除部分**：列出已知的失败模式及其修复方法——对于需要在你无法查看的机器上运行的 skill，这是最有价值的单个部分。
- **第 0 步幂等性检查**：如果重复运行可能会重复已完成的工作，请先进行一个低成本的“是否已经完成？”检查，再执行任何耗费资源的操作。

### 写作风格

尽量向模型解释为什么事情很重要，而不是大量使用生硬的 MUST。尝试进行心智理论推演，并尽量让 skill 具有普适性，而不是过度局限于具体示例。先写出草稿，然后以全新的视角重新审视并改进它。

### 日期和版本引用

**保留事实性日期——它们能告诉读者相关信息是在什么时候得到验证的。** 关于 Suno v5.5 的 skill 应写成 “Suno v5.5 (March 2026)”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 August 2025，则使用旧 API”）——日期一旦过去，这种逻辑就会失效，而没有人会更新它。

规则：
- **发布日期、“最后验证”日期**：保留它们。它们是参考时间点，而不是失效日期
- **定价、排名、法律状态**：包含这些信息，但标记为易变信息（“截至上次检查约为 ~$0.035/gen”），以便读者知道需要重新验证
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可以选择在折叠/弃用部分记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当相同代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省 Token、具有确定性，并且可以在不加载到上下文中的情况下执行
- **注意**：Claude 可能仍需读取脚本，以便进行修补或针对环境进行调整
- **用户可修改的数据存放在捆绑包之外**：如果脚本会累积用户数据（纠正词典、学习到的偏好、缓存），请将其存储在稳定的、相对于 home 的目录下（例如 `~/.<skill-name>/`），并为其单独备份 — 切勿将其存放在 skill 目录内。每次更新和套件迁移都会删除并重新创建 skill 安装，而相对于 home 的存储会原封不动地保留下来。这正是一个会累积词典的 skill 能够在完整套件迁移后实现用户数据零丢失的原因

##### 参考资料（`references/`）

用于按需加载到上下文中，以便为 Claude 的处理和思考提供信息的文档与参考材料。

- **何时包含**：当 Claude 工作时应参考相关文档时
- **示例**：用于金融 schema 的 `references/finance.md`、用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库 schema、API 文档、领域知识、公司政策、详细的工作流指南
- **优点**：使 SKILL.md 保持精简，仅在 Claude 判断有需要时加载
- **最佳实践**：如果文件较大（超过 10k words），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或 references 文件中，不要同时存放在两者中

##### 资源文件（`assets/`）

不打算加载到上下文中，而是供 Claude 在生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用的文件时
- **示例**：用于品牌资源的 `assets/logo.png`、用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件货架**：对于生成制品的 skill，`assets` 下的 `components` 子文件夹存放用户批准的、按原文嵌入的片段，这些片段具有冻结的行为契约和注册表引用 — 请参阅第 4 步中的 Component-shelf 检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标用途。**下面的所有内容描述的都是 skill 发布给陌生用户时会出现的问题。对于存放在作者自己私有 repo 中的 skill，这些“违规”通常正是它能够正常工作的原因 — 真实的绝对路径能让脚本直接运行，模板中的真实账户能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 所在的 repo 是否为私有），并将那里的可移植性/标识符问题降级为提示；当准备发布私有 skill 时，`--audience=public` 会强制执行严格检查。

**对于私有 skill，这些问题由所有者决定，而不是由你决定。** 不要在未询问的情况下替换真实路径、改写硬编码凭据，或对示例进行“清理”——你会为了满足一条原本针对另一个目的地编写的规则，而破坏一个正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，让所有者自行决定。（其设计先例是 npm 的 `"private": true`：一个已声明的目的地会改变工具强制执行的规则；之所以加入它，是因为人们一直在意外发布内容。）

**对于计划公开分发的 skill，这是关键要求**——其中不得包含特定用户或特定公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，例如 `~/.claude/skills/`
- **允许**：skill bundle 内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（严格按“禁止”列表实现的验证器会将此 skill 自身标记出来——对健康输入误报比漏报更糟糕）：当发布者自己的名称/品牌是解决取代关系中的平局或进行归属说明所必需的，可以使用；当段落讨论这些路径本身时，可以使用安装路径如 `~/.claude/skills/`（这是教学材料，而非硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于该 skill 自己的 bundle 内”——验证器和读者都会这样理解，因此指向另一个 skill 文件的裸路径会验证失败，并误导读者。指向另一个 skill 时，应在正文中注明其所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用带命名空间的名称调用 skill（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。当 skill 在不同 suite 之间迁移时，裸跨引用会静默失效——某次 suite 迁移后，在两轮清理中一共发现了 21 处损坏的跨引用。

##### 版本控制

**关键要求**：SKILL.md 不应包含版本历史或版本号：

- **禁止**：SKILL.md 中的版本章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **原因**：Marketplace 基础设施负责版本控制；SKILL.md 应包含不会随时间变化的内容

#### Reference 文件命名

文件名必须无需阅读内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：只看文件名，能否理解文件内容？

有两个例外：连字符命名与下划线命名同样合适（分隔符从来都不是重点——重点是能够自我说明）；而位于具名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已经由目录提供具体性，重命名它们会破坏各工作流之间的平行结构。

### Full-eval 测试用例（仅限单独授权的配对计划）

仅当重型评估授权门控通过后，才能进入本节。风险等级本身既不授权也不禁止使用这些证据；明确的全流程请求不会重新界定底层变更。不要仅仅因为 SKILL.md 发生了变化就使用本节。应遵循上文声明的替代契约所规定的专门工作流。

编写 skill 草稿后，提出 2-3 个现实的测试提示词——即真实用户实际会说的那种提示词。**对于作用于实时系统的 skill（正在运行的服务、已登录的客户端、生产数据），请为每个测试提示词明确副作用预算**——例如“只读探查并得出结论；不要执行下载 / 驱动 UI”。在“只是测试”的名义下修改实时环境属于真实操作，而不是测试。通过 **AskUserQuestion** 呈现这些提示词：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——在运行进行期间的下一步中再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整 schema（包括稍后添加的 `assertions` 字段）请参阅 `references/eval_pipeline_schemas.md`。

## Full paired 评估流程（仅限单独授权）

仅在重型评估授权门控通过后运行本节。风险等级仍应根据变更所导致的行为确定。分阶段执行流程，每个阶段都会产生决策；当不确定性或请求的基准交付物已经得到解决时就停止；不要预先启动后续的评分器、聚合或查看器工作。用户取消或降级后，应立即停止重型流程。未经授权不得使用本流程；如果某个专门工作流明确进行了替代，也不得机械地添加通用流程；不要使用 `/skill-test` 或任何其他测试 skill。

将结果放入 `<skill-name>-workspace/`，作为 skill 目录的同级目录。在 workspace 中按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要一开始就创建所有目录——只需随着进展逐步创建目录。

### 步骤 1：运行已批准的 with-skill / baseline 配对

对于每个已批准的测试用例，在相同的提示词和副作用预算下，运行一个 with-skill 样本及其 baseline。这两个实验分支有意共享一个失败维度，但需要隔离的上下文；它们是必要的实验单元，而不是额外的审阅者角色。在启动前说明实验分支总数和并发上限。默认串行运行，且绝不要超过授权的单元数量。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（使用相同的提示词，但 baseline 取决于上下文）：
- **创建新 skill**：完全不使用 skill。使用相同的提示词，不提供 skill path，并将结果保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用强制性的现有 skill 回归门禁在首次编辑之前捕获的旧版本。将 baseline 子代理指向该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 重建权威 baseline 后再继续；绝不要将已经编辑过的目录用作旧 baseline。**明确这项比较能够解决的问题：它只衡量本轮的变化。**如果你最想验证的能力已经存在于编辑前快照中——某个并行会话可以在你开始之前准确提交该修复——那么 with/old A/B 对该能力没有任何解析能力；在该能力下选择更早的 ref 作为 baseline。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据每个 eval 测试的内容为其指定描述性名称——不要只使用“eval-0”。同时使用该名称作为目录名。如果本次迭代使用了新的或修改过的 eval 提示词，请为每个新的 eval 目录创建这些文件——不要假定它们会从之前的迭代中沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：在运行进行期间起草断言

不要只是等待运行完成——你可以利用这段时间开展有价值的工作。为每个测试用例起草量化断言，并向用户说明这些断言。如果 `evals/evals.json` 中已经存在断言，请审查它们并说明其检查内容。

好的断言应当能够客观验证，并具有描述性名称——在基准测试查看器中应清晰易读，使浏览结果的人能够立即了解每个断言检查的内容。**根据意图编写断言，而不是根据字面上的工具路径编写断言**——“语音内容在答案中得到保留”，而不是“调用了获准的读取脚本”。如果某次运行通过其他获准路径达成了该意图（例如读取一个已经内嵌文字记录的归档文件），则应判定为通过；将其判定为字面路径失败会制造错误的负面结果，随后你还会因此在错误的位置进行“修复”。主观性较强的 skill（写作风格、设计质量）更适合进行定性评估——不要强行为需要人工判断的内容设置断言；其实际验证路径（历史任务重放、带有回写习惯的生产环境评估、渲染后人工审查）列在“Capture Intent”的问题 4 下。

起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到的内容——包括定性输出和定量基准测试。

### 步骤 3：随着运行完成，记录计时数据

每当一个子代理任务完成时，你都会收到包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们通过任务通知传来，不会在其他位置持久化保存。通知到达后应立即处理每条通知，而不是尝试批量处理。

### 步骤 4：评分、汇总并启动查看器

所有运行完成后：

1. **为每次运行评分** — 启动一个评分子代理（或直接进行评分），读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是凭肉眼判断——脚本速度更快、更可靠，也可以在多次迭代中复用。**但客观的 grep/脚本断言也有两面性**（可能因相同词语的不同含义而误命中，也可能因措辞差异而漏检），因此**基准测试通过率是一项信号，而不是最终结论**：抽查每条断言实际匹配到的内容，并留意基线运行是否揭示了技能本身存在事实错误（出现“等等，API 中确实有这些数据”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **汇总为基准测试** — 从技能创建器目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及均值 +/- 标准差和增量。如果手动生成 benchmark.json，请参见 `references/eval_pipeline_schemas.md`，了解查看器所需的确切架构。将每个 with_skill 版本放在对应的 baseline 版本之前。

3. **进行分析师检查** — 阅读基准测试数据，找出汇总统计数据可能掩盖的模式。参见 `agents/analyzer.md` 中的“Analyzing Benchmark Results”部分，了解需要关注的内容——例如无论是否使用技能都始终通过的断言（无区分度）、高方差评估（可能不稳定），以及时间/令牌之间的权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台查看器使自身陷入异常状态**：进程仍在运行，但没有任何程序在监听——使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或 curl 该 URL（失败）；这里“没有日志输出”并不是一个可用的信号，因为上面的启动命令已将日志重定向到 `/dev/null`。终止该进程，并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：** 如果 `webbrowser.open()` 不可用，或者环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击 "Submit All Reviews" 时，反馈会被下载为 `feedback.json` 文件。下载后，将 `feedback.json` 复制到工作区目录中，以便下一轮迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** **告知用户**：

```text
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

"Outputs" 选项卡一次显示一个测试用例：
- **Prompt**：所给出的任务
- **Output**：技能生成的文件，并会在可能的情况下以内嵌方式渲染
- **Previous Output**（第 2 次及之后的迭代）：显示上一次迭代输出的折叠区域
- **Formal Grades**（如果运行了评分）：显示断言通过/失败情况的折叠区域
- **Feedback**：会在用户输入时自动保存的文本框
- **Previous Feedback**（第 2 次及之后的迭代）：显示在文本框下方的用户上次评论

"Benchmark" 选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每项评估的详细结果和分析师观察。

可通过上一个/下一个按钮或方向键进行导航。完成后，点击 "Submit All Reviews"，这会将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们完成后，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。将改进重点放在用户提出了具体意见的测试用例上。

完成后，终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进 skill

这是循环的核心。根据证据计划进行改进：对于 Tier 1，使用权威事实和确定性检查；对于 Tier 2，使用 1–2 个具名行为回放；或者在单独的重型评估门槛于任意层级授权时，使用由用户审查的成对结果。未经该授权，不要将成对评估产物导入默认的 Tier 1/2 路径。

### 如何思考改进

1. **从反馈中进行泛化。** 这里发生的根本问题是：我们正在尝试创建能够在许多不同提示下被使用一百万次（也许确实是一百万次，甚至更多，谁知道呢）的 skills。现在，你和用户只是因为反复处理少数几个示例有助于加快进度，才会一遍又一遍地迭代这些示例。用户对这些示例了如指掌，因此可以快速评估新的输出。但是，如果你和用户共同开发的 skill 只能用于这些示例，那它就是无用的。不要进行琐碎且过拟合的修改，也不要添加压制性很强的 MUST；如果某个问题顽固存在，可以尝试换用不同的隐喻，或建议采用不同的工作模式。尝试的成本相对较低，而且你可能会找到非常出色的方案。

2. **保持 prompt 精简，但不要删除契约。** 删除那些没有发挥作用的内容，但要将从现有 skill 中删除的每一项内容都视为潜在回归，直到新旧审计对其进行分类。将详细但可复用的行为移入直接链接的参考文档；不要只把它们留在评估、变更日志或你的记忆中。阅读完整的交互记录，而不仅仅是最终输出——如果 skill 导致了无益的工作，就简化指令，并重新运行旧的能力用例，而不是想当然地认为字数更少就意味着行为更好。

3. **解释原因。** 尽力解释你要求模型执行每件事背后的 **原因**。如今的 LLM *很聪明*。它们具备良好的心智理论能力，在获得良好 harness 的情况下，可以超越死记硬背的指令，真正促成事情发生。即使用户的反馈简短或带有挫败情绪，也要努力真正理解任务，理解用户为什么写下他们所写的内容、他们实际写下的是什么，然后将这种理解传达进指令中。如果你发现自己在使用全大写的 ALWAYS 或 NEVER，或使用极其僵化的结构，那就是一个黄色信号——如果可能，应当重新措辞并解释其中的理由，让模型理解你所要求之事为何重要。这是一种更人性化、更强大也更有效的方法。

4. **寻找重复性工作——既要查看评估交互记录，也要查看 skill 所提炼自的对话。** 阅读测试运行的交互记录，注意子代理是否都独立编写了相似的辅助脚本，或是否都采用了相同的多步骤方法来处理某件事。如果 3 个测试用例的结果都是子代理编写了 `create_docx.py` 或 `build_chart.py`，这就是一个强烈信号，说明该 skill 应该捆绑这个脚本。将它编写一次，放入 `scripts/`，并告诉 skill 使用它。这样可以避免每次未来调用都重新发明轮子。同样的信号也隐藏在你提炼 skill 所依据的源对话中——该会话中哪怕只编写过一次的代码，未来每次运行都必须重新编写；不要等到评估运行来证明重复性（被跳过评估循环的 skills 永远无法获得这项证明——创建流程第 4 步中的 Scripts 检查点正是捕捉这类问题的地方）。

5. **逐字将修正写回——同一会话、两个层级都要写回。** 对于经过品味校准的技能，用户的修正就是评测集，但前提是这些修正写入了未来运行时会读取的位置。以下两个属性会让写回过程逐步收敛：(a) **逐字记录修正内容**，不要改写或概括——确切措辞携带着摘要会抹平的校准信号（“绝对禁止这种东西”教会的是一条硬边界；“用户偏好更少的跳转”则不是）。将这些话原样引用到它们所修正的规则中，并注明日期。(b) **在修正发生的同一会话中、在两个层级都写回**——既修复产物，也修复技能的规则/引用/组件；只修复产物的修正对所有未来运行都不可见，而推迟到“之后”处理的修正通常永远不会落地。在写回时，检查技能自身的文本是否*教会了*刚刚被禁止的反模式——修正往往会推翻现有指令，而保留旧建议就必然会导致问题再次出现（真实案例：一个决策页面契约建议使用跳转式的“goto anchors to the referenced figure”；用户明确禁止了这种做法，因此写回时必须修改旧句子，而不能只在旁边新增一条规则）。当被修正的是一个交互片段时，写回的最后一步是将其提升到组件架——请参见第 4 步中的 Component-shelf 检查。

这项任务相当重要（我们正在努力让这里每年创造数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请花时间认真斟酌。我建议先写一版修订稿，然后重新审视并加以改进。请尽最大努力站在用户的角度思考，理解他们想要什么以及需要什么。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据确实留下了多个选择时才提问。对于 Tier 2 或 Tier 3，当用户反馈暴露出有意义的设计分歧时，通过 **AskUserQuestion** 提出改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险等级，因为这会改变实现范围；选择 D 则不会。每个选项仅授权其中明确指明的范围/证据变更。除非其中明确列出，并且单独的重型评测/扇出闸门已经通过，否则它不会授权成对的基线、评分器、基准测试、查看器或额外角色。

### 迭代循环

改进 skill 后：

1. 将改进应用到 skill
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **Tier 1 默认流程：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配的子类型证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归测试。除非单独授权了配对计划，否则不要创建迭代工作区。
   - **Tier 2 默认流程：**仅重新运行同样的 1–2 个具名的 with-skill 示例及窄范围检查。除非单独授权了配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任意层级单独授权的通用配对运行：**将所有获批的测试用例（包括基线运行）重新运行到新的 `iteration-<N+1>/` 目录中。对于新 skill，基线始终是 `without_skill`；对于现有 skill，不可变的编辑前原始版本仍是每次迭代的保留基线。紧邻的上一轮迭代可以作为补充，但绝不能替代原始基线。
3. 在实质性规则、契约或数值发生变化后，执行规范 #5。对于单独授权的通用配对运行，还要使用指向上一轮迭代的 `--previous-workspace` 启动评估审查器；专用工作流则使用其声明的审查器机制。
4. 对于单独授权的通用配对运行，等待用户审查新的查看器结果；否则，根据默认层级的证据作出决定，除非仍存在需要用户实际选择的事项。
5. 读取新的证据或反馈；如果它证伪了当前版本，则再次改进，并在同一层级重复执行。

用户请求的取消或降级在任务剩余期间持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
迭代 [N] 已完成。结果：[pass_rate]% 的断言通过，[与上一轮的差值]。

建议：[继续 / 接受 / 恢复]，因为[基于差值和剩余反馈的一句话原因]。

选项：
A) 继续迭代 — 我认为还有更多改进空间
B) 接受此版本 — 已经足够好了，让我们进入打包阶段
C) 恢复到上一轮迭代 — 本轮使结果变差了
D) 运行盲测比较 — 严格比较此版本与上一版本
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（所有内容看起来都很好）
- 你已经无法取得有意义的进展

## 高级：盲测比较

当你希望对 skill 的两个版本进行更严格的比较时（例如，用户询问“新版本真的更好吗？”），可以使用盲测比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。基本思路是：将两个输出交给一个不知道哪个对应哪个的独立代理，由它判断质量。然后分析获胜者胜出的原因。

这是可选步骤，需要使用子代理，大多数用户不需要执行。通常人工审查循环已经足够。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某项技能的主要机制。创建或改进技能后，应主动提出优化 description，以提高触发准确性。

### 第 1 步：生成触发评估查询

创建 20 条评估查询，其中应混合包含应该触发和不应该触发的查询。以 JSON 格式保存：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实，且应是 Claude Code 或 Claude.ai 用户实际会输入的内容。不要使用抽象请求，而应使用具体、明确且包含足够细节的请求。例如，可以包含文件路径、用户工作或情境背景、列名和值、公司名称、URL 等信息。可以加入一些背景说明。有些查询可以使用小写、包含缩写或拼写错误，或采用口语化表达。长度应有所变化，并重点关注边界情况，而不是让查询过于容易判断（用户之后将有机会确认这些查询）。

不好：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应该触发**的查询（8-10 条），要考虑覆盖范围。应使用同一意图的不同表述——有些正式，有些口语化。包括用户没有明确提及技能名称或文件类型，但显然需要使用该技能的情况。加入一些不常见的使用场景，以及该技能会与另一项技能竞争但应由该技能胜出的情况。

对于**不应该触发**的查询（8-10 条），最有价值的是近似匹配——这些查询与该技能共享关键词或概念，但实际需要的是其他功能。应考虑相邻领域、含义模糊且朴素的关键词匹配可能会触发但实际上不应触发的表述，以及查询涉及该技能能够完成的某些操作、但在当前情境下更适合使用其他工具的情况。

需要避免的关键问题：不要让不应该触发的查询明显无关。以 `"Write a fibonacci function"` 作为 PDF 技能的负面测试过于简单——这无法测试真正的边界。负面案例应当确实具有迷惑性。

### 第 2 步：与用户审查

使用 HTML 模板向用户展示评估集：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目组成的 JSON 数组（不要在其外加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的 description
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`），并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——如果存在多个文件（例如 `eval_set (1).json`），请检查 Downloads 文件夹以找到最新版本。

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 步骤 3：运行优化循环

告诉用户：“这会需要一些时间——我会在后台运行优化循环，并定期查看进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（即为当前会话提供支持的模型），这样触发测试才能匹配用户实际体验到的效果。

运行期间，定期查看输出末尾的内容，向用户更新当前进行到哪一次迭代，以及分数表现如何。

这会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后根据失败情况调用 Claude 提出改进方案。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开 HTML 报告，展示每次迭代的结果，并返回包含 `best_description` 的 JSON——该值根据测试分数而非训练分数选出，以避免过拟合。

**如果检测到完全没有触发，循环会在第 1 次迭代后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中的代码级保护，而不只是建议；它区分了“第 1 次迭代中所有 should-trigger 查询都完全没有触发”这一现象的两种原因：

- `exit_reason: "infra_error: ..."` — 某些查询执行时抛出了异常（`claude` CLI 不在 PATH 中、超时时间过短、网络中断），而不是正常返回“未触发”。该检查**优先进行**，并且只要错误计数非零就会有意触发，即使几十次运行中只有一次不稳定失败也一样——无论多么少见，崩溃都比“什么都没有触发”更具体、更容易采取行动，而修复方向是环境问题，而不是重写描述。消息中的比例（例如 `3/15`）用于表示严重程度：占比较大意味着“停止运行，修复环境”；如果比例较小，同时存在大量干净的 0 触发运行，则意味着环境可能存在轻微的不稳定问题，值得检查，**并且**描述可能确实存在问题——两方面都要检查。无论哪种情况，都应检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` — 只有在上面的分支排除了所有执行错误后才会进行检查，因此这意味着每个 should-trigger 和 not-should-trigger 查询都**确实运行了**，但仍然全部触发了零次（这正是通过零分母默认值实现的 `precision=100%` 实际代表的含义：不是“完美”，而是“没有任何东西可供相除”）。该探针实际上没有测量到任何东西——在完全修改描述之前，先去诊断竞争者冲突或低阈值领域（见下文）。

这两项检查**仅针对第 1 次迭代**，并且**仅在 should-trigger 查询触发次数为零时进行**——第 1 次迭代表现较弱但并非零触发（例如 1/9 次触发）是另一种可能恢复的情况，因此会有意继续迭代。`degenerate_harness` 还要求 not-should-trigger 查询的触发次数也为零：如果描述只是极性反转——错过了所有正例，却意外匹配了几个负例——则说明探针确实在工作，`improve_description` 也有真实的梯度可以利用，因此保护机制不会中止这种情况（只会中止真正失效的探针）。它还要求任一侧都不存在执行错误——抛出异常的 not-should-trigger 查询实际上并未运行，因此其“0 次触发”不能作为探针失效的证据；这种情况正是应路由到 `infra_error` 的情形。无论哪种情况，系统都会立即中断，并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因才是信号，表明这次运行的数字不应被解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了一个完整的 5 次迭代循环；两次完整迭代——每次都是完整的评估批次，耗费数分钟的实际时间，并调用了几十个 `claude -p` 子进程——都返回了 precision=100%/recall=0%/完全相同的分数，直到有人查看这些数字时才发现问题，而每个 should-trigger 和 not-should-trigger 查询都完全没有触发。仅凭第 1 次迭代就能诊断出该故障；第 2 次及之后的迭代没有提供任何额外信息。）当任一退出原因触发时，HTML 报告也会渲染一个横幅，因此浏览器视图会携带与 JSON/stderr 相同的信号，而不只是通过这两个较不显眼的渠道呈现。（该保护机制的早期草案只检查 should-trigger 触发情况；两轮独立审查——每一轮都由一个新的代理执行，第二轮检查第一轮的修复，而不是重复覆盖旧内容——构造出了极性反转的反例、基础设施问题与描述问题之间的歧义、负例侧错误遗漏的问题，以及由此发现的一个既有的 `--holdout 0` 报告崩溃问题；所有问题都在发布前得到修复。）

这个防护措施无法覆盖一种情况：当使用 `--runs-per-query 1` 时（默认值为 3），一个本应触发、且实际触发率确实在 50% 左右的查询，完全可能仅仅因为偶然因素读到 0/1，从而因为噪声而触发防护措施，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询的每次重复运行都为零”成为强信号的原因——如果你将其调低，这个防护措施的误报风险也会随之升高。

**在信任 `best_description` 之前，先对测试框架进行合理性检查——即使上面的两个防护措施都没有触发，它仍可能返回空洞的输出。** 这两项检查只能捕获第 1 次迭代时的*彻底失败*；测试框架也可能在全部 5 次迭代中始终维持微弱但非零的信号，因而从未触发其中任何一项。如果在第 1 次迭代之后的每次迭代中，**召回率始终接近 0%，且分数完全相同或几乎相同**，那仍然是这些防护措施无法排除的同一个根本问题——“获胜”的描述通常只是第 1 次迭代结果未变的噪声。在应用任何 `best_description` 之前，亲自运行一个显然应该触发的查询，并确认召回率 > 0。跨迭代保持平坦的召回率结果意味着测试框架是一个隐藏变量（常见原因是：该技能在触发竞争中输给了已安装的其他技能——见下文的 Coexistence）——不要应用它的“最佳”结果；应手动编写描述，并使用真实探针验证它。（方法论案例 12、14）召回率为 0 还有第二种根本原因，与输给竞争技能不同：该技能的任务领域是*低阈值*的——模型会自行完成任务，从不查阅任何技能——具体说明见下文 *How skill triggering works* 的末尾。在采取行动之前，先区分这两种情况，因为修复方式正好相反：竞争技能问题通过优先级/取代关系修复，低阈值领域问题则应彻底放弃将触发探针用于生产评估。

**当你使用 `claude -p` 自行探测触发情况时，要收集该次运行中的所有技能调用，而不只是第一次调用——并记住，工具调用只是一个代理指标。** `UserPromptSubmit`/`SessionStart` 钩子可能会在模型做出选择之前注入一个无关技能，因此“第一次出现 Skill 调用就退出”的探针会错误地报告“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“该技能的内容是否影响了输出”（模型可能读取了技能，却没有出现可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你围绕错误的结论持续优化。

### 技能触发机制

了解触发机制有助于设计更好的评估查询。技能会以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某个技能。需要注意的要点是：Claude 只会针对自己无法轻松处理的任务查阅技能——像“读取这个 PDF”这样简单的单步查询，即使描述完全匹配，也可能不会触发技能，因为 Claude 可以使用基础工具直接处理这类任务。复杂、多步骤或专业化的查询，在描述匹配时通常会可靠地触发技能——但有一个系统性例外（低阈值任务领域），具体说明见本节末尾。

这意味着你的评估查询应当足够实质，以便 Claude 确实能从查阅 skill 中受益。像“read file X”这样的简单查询是不理想的测试用例——无论描述质量如何，它们都不会触发 skill。

**但有些 skill 无法通过这一测试，是有原因的：无论怎样改写查询都无法解决——这个 skill 的整体*职责*就是一项低门槛任务。** 上面的段落将问题归咎于查询（“写一个更实质的查询”）；而这里是正交的情况，阻碍触发的是 skill 的*领域*。如果某个 skill 的用途是执行 Claude 使用基本工具就会自行完成的事情——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询写得非常完整（“将这个 48k 立体声 wav 降采样为适用于 whisper 的 16k 单声道”，路径及其他信息一应俱全），也不会触发它：模型会直接使用 `Bash`/`ffmpeg`，而不会查阅任何 skill。查询的实质性无法解决这个问题，因为“我可以直接完成这件事”的判断针对的是*任务*，而不是措辞。

在你投入优化循环之前先诊断这一点：通过 `claude -p` 运行一个真实的查询，并观察模型在整个运行过程中是否*曾经*查阅过该 skill（依据上面的 ALL-skill-calls 规则），还是直接使用 `Bash` 自己完成任务。如果它从未查阅，那么触发探测从结构上就无法检测到这个 skill——无论你怎么写，召回率都约为 0，而这个 0 衡量的是模型“我自己来做”的条件反射，而不是你的描述。不要再针对 `claude -p` 的召回率进行调优，而应通过真正的方式进行验证：以生产环境作为评估（用户下一次真实的、*交互式*使用——无头 `-p` 比真实会话更偏向执行操作，因此系统性地低估触发率），并在 skill 生成可检查的产物时比较输出。（在一个音频预处理 skill 上观察到：无头的 run_eval 扫描在*每一个*查询上的读取召回率都是 0——包括一个明显的“转录这段录音”查询；而手动执行 `claude -p` 探测显示，模型直接使用 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个 0 衡量的是无头模式的操作偏差，而不是描述；真正的信号只会在交互式使用中出现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新 skill 的 SKILL.md frontmatter。向用户展示修改前后的内容，并报告分数。

## 重要：在源位置编辑 Skills

**绝不要先编辑已安装的 skill 副本。** 除非用户明确说明它们就是源文件，否则应将以下所有位置视为已安装/运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装的副本会导致所做更改：
- 在缓存刷新时丢失
- 不会同步到源代码管理系统
- 浪费时间，并需要手动重新合并

**始终确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在任何编辑之前**，运行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。先找到由仓库维护的源，在源上编辑并完成验证；只有当用户需要立即在本地运行时，才同步已安装的副本。

**然后回答决定“同步已安装副本”是否确实需要进行的后续问题：运行时是否已经读取源？** 三种安装方式的行为不同，猜错要么浪费一次同步，要么提交一个用户下一次会话根本看不到的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **符号链接**到源代码树中 → 该编辑就是运行时所使用的内容。不需要同步。
- **`source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本号递增只是为其他消费者做的记录工作，不是本地激活步骤。
- **任何缓存/复制的安装方式**（来自 git 的 marketplace、通过 `cp -r` 安装）→ 运行时使用的是独立副本，确实需要运行官方更新命令，新内容才会生效。

**还要根据内容而不是版本字符串验证激活状态。** 注册表可能记录了磁盘上并不存在的路径或版本号——曾有一次会话读取到一个插件记录，其中写着带有*新*版本号的缓存目录，差点就报告更新已生效；但那个目录从未创建过，而真正的运行时路径一直都是指向源的符号链接。权威检查方式是 grep 运行时文件，查找只有新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库上的并行会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能在你不知情的情况下提交技能 B（甚至是技能 A 的较早一轮修改）。有一次真实会话在一小时内遇到了全部三种症状——`Write` 因文件在读取后发生变化而被拒绝，并且 HEAD 在任务期间两次发生移动（方法论案例 16）。失败的根源不是冲突本身，而是基线过时，或覆盖式写入悄悄混合了两个会话的工作。固定规则如下：

1. **只要仓库在任务开始时是干净的，就应从 git ref 而不是工作树建立基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传入 `--baseline-origin git-ref:<sha>`。在其他人的提交之后几分钟创建的树快照，是一个已经不存在的树的基线。**要提取到一个全新的、不存在的目录中。** 提取到已有目录时，`tar -x` 会静默覆盖同名文件，同时保留归档中不存在的文件——这是一个在提取时没有任何信号的混合快照，之后 `compare` 会因其与该 ref 不匹配而拒绝它。同样的陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会将目录嵌套进去；而当 `mv` 被别名为 `mv -i` 时，目标已存在的重命名操作会打印一行提示，并默认不执行，但无论哪种结果退出码都是 0（已通过实验验证）。
2. **在写入被拒绝后，或经过了任何一段时间后，都要重新读取再写入**：检查发生了什么变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图合并到你的版本中——他们的编辑通常是有原因的——然后再写入。
3. **提交前检查 HEAD 以及当前所在的分支。** `git log --oneline -1` 可以发现 SHA 是否发生移动：如果它自基线建立后发生了变化，就要针对新的 ref 重新运行回归 `compare`，然后再运行 `verify`——审计工具无论如何都会拒绝过时的审查（“after skill changed”），提前发现可以省下一轮。但另一个会话可能做得比推进 HEAD 更糟：**它可能在你不知情的情况下切换分支**，因为 checkout 作用于整个工作树。真实情况是——你执行了 `checkout -b feat/x`，编辑了一段时间；与此同时，另一个会话执行了 `checkout main` + `pull`；之后提交落在了 **main** 上，违反了仓库“绝不直接提交到本地 main”的规则，而功能分支仍然指向旧基线。因此，提交前检查中要加入 `git branch --show-current`，不能只检查 SHA。若这种情况已经发生，`git reflog` 是权威的还原依据（它会按顺序记录每次 `checkout: moving from X to Y`）；而修复方式是——**在工作树干净的前提下**——执行 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：这两者都是只移动引用的操作，从不会触碰工作树，因此不像 `reset --hard` 那样会破坏并行会话尚未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——另一个会话尚未提交的工作不能被一并带入。（这本来就是打包时的规则；在并发场景下更是关键。）
5. **每个会话结果只递增一次版本号**，而不是每轮编辑都递增：同一会话对一个技能连续进行的多轮修改应合并为一次版本递增——除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），此时每个已被使用的状态都应拥有自己的版本号。

## Skill 创建流程（分步说明）

创建或更新 skill 时，请按顺序执行以下步骤。仅当某个步骤明确不适用时，才可以跳过。

### 步骤 0：前置条件检查

开始任何 skill 工作之前，自动检测所有依赖，并主动安装缺失项。在工作流中途才发现缺少工具（例如打包时缺少 gitleaks、验证时缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖就自动安装，并向用户提供检查清单摘要。只有满足所有阻塞性依赖后，才能继续执行。

关键阻塞项：Python 3、uv、PyYAML（验证/打包）和 gitleaks（安全扫描）。只有在单独授权的证据计划实际运行 agent 评估时，claude CLI 才是阻塞项。使用显式的 uv 依赖声明运行 Python 工具，例如从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 会依赖环境中已有的 site packages，可能找不到 PyYAML。

### 步骤 1：通过具体示例理解 Skill

仅当 skill 的使用模式已经明确理解时，才可以跳过此步骤。

要创建有效的 skill，需要清楚理解 skill 的具体使用示例。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成示例。

例如，在构建 image-editor skill 时，相关问题包括：

- “image-editor skill 应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能给出一些这个 skill 的使用示例吗？”
- “用户说什么话时应该触发这个 skill？”

为避免让用户应接不暇，不要在一条消息中提出过多问题。

### 步骤 2：规划可复用的 Skill 内容

分析每个示例时：

1. 考虑如何从头开始执行该示例
2. 确定应赋予 Claude 多大的自由度
3. 确定哪些脚本、参考资料和资源在重复执行这些工作流时会有所帮助

**让具体程度与任务风险相匹配：**
- **高自由度（文本说明）**：存在多种有效方案
- **中等自由度（带参数的伪代码）**：存在首选模式，同时允许合理变体
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 步骤 3：初始化 Skill

如果 skill 已经存在，则跳过此步骤。

从头创建新 skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个包含正确 frontmatter、资源目录和示例文件的模板 skill 目录。

### 步骤 4：编辑 Skill

开始编写之前，获取 Anthropic 的最佳实践文档（链接位于上面的“Skill Creation Best Practice”中）以及方法论参考资料——即使你觉得自己已经了解这些内容，也要执行此操作：文档会更新，训练数据版本会过时，而“我基本上已经知道了”正是编辑者会跳过这一步并错过最新指导的状态。

编辑时，请记住，该 skill 是为另一个 Claude 实例创建的。重点关注那些对 Claude 有帮助且不明显的信息。

**Existing-skill migration gate — required before the first edit:**

1. 在首次编辑之前，完整捕获当前 bundle。对于非 Git 或 dirty 的源，使用该工具，以便快照携带可验证的 provenance manifest：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源，从选定的 ref 物化目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   包括 SKILL.md、references、scripts、assets、workflows 以及现有 evals——不要只复制主提示词。绝不要复制已经编辑过的目录并将其标记为“before”。**使用一个之前没有任何内容被提取到其中的目录**——重复使用一个已经包含内容的目录时，`tar -x` 可能会静默覆盖同名文件，同时保留新归档中不存在的陈旧文件，在提取时完全不会产生任何信号，从而生成混合快照（`compare` 只能在之后间接地通过 tree-hash 不匹配发现这一点）。请参阅下方的“Concurrent sessions on the same skill repo”，其中有关于此陷阱的更完整说明，包括基于 `mv` 的变体。
2. 清点旧 skill 的 actor/jobs、trigger contexts、runtime contracts、commands/flags、failure and recovery cases、page/domain variants、bundled resources 以及 eval coverage。在进行结构重写之前，为重要的旧 edge behavior 添加 preservation cases。
3. 编辑后，生成新旧版本的审查结果：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，将最后一个 flag 替换为 `--baseline-origin git-ref:<ref>`。该工具会将 ref 解析为不可变的 commit，并根据该 tree 验证每个包含的文件及 executable bit。

   **重命名或移动 skill 目录本身**（而不仅仅是编辑其中的内容）会改变 `--after` 的路径，而这两种 baseline 模式都会使用该路径来确定 identity——默认情况下，`compare` 会拒绝此操作（假定 `--before`/`--after` 是因误配而不匹配），并报错 `pre-edit snapshot source identity does not match the edited skill`。添加 `--renamed-from <old-path>` 以明确声明重命名（即 `snapshot` 所指向的 `--source` 路径，或 `git-ref:` 中相对于 repo root 的 skill 旧路径）；identity 检查随后会验证该路径，而 content/tree-hash 检查保持不变，因此实际不匹配的配对仍会失败。**将 `--renamed-from` 作为绝对路径传入。** 该命令接收的每个路径在以相对路径给出时，都会相对于当前工作目录解析——不会相对于 `--after` 解析，也不会相互之间解析——而 `--renamed-from` 通常指向一个已经不存在的目录（它已被重命名），因此不存在检查无法像对 `--before`/`--after` 那样捕获错误解析；它只会在更深处以令人困惑的方式失败。skill-creator 自身的编辑尤其容易遇到这一问题：上面的 `cd <skill-creator-path>` 位于 skill-creator 自己的 repo 中，而该 repo 通常与正在审计的 skill 所在的 repo *不同*，因此相对的 `--renamed-from` 会静默地相对于错误的 repo 解析。

4. 审查每个候选项。使用且仅使用一个处置结果，并记录具体证据/理由：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移出此 skill 时，需要提供所属目标、当前边界证据以及可追溯的用户批准。明确弃用也必须引用/追踪用户的批准。关于已保留/已清理/已修复的声明，必须指向真实存在的当前文件和行，并包含一段简短的 `contains` 引文，以便验证器在附近定位。文件级候选项需要使用当前文件指纹，并附带一份命名的语义审查，解释为何行为得以保留——仅凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本——`classify` 子命令会完成机械性工作（定位目标文件中引文所在的行、填写 evidence/semantic_review、在找不到引文或理由过短时快速失败）。你仍需为每个候选项编写处置结果和理由；它只负责将这些内容录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射为
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置结果默认为 `preserved_or_moved`）；文件级候选项只需要 destination + 长度至少为 40 个字符的 reason——指纹会由工具为你计算。**从目标文件中复制 needle（使用 Read/grep/sed），绝不要凭记忆输入它**——查找采用精确匹配，找不到引文会快速失败；手动输入 needle 实际上会失败的两种情况是全角与半角标点（`：` 对 `:`）以及凭记忆改写的近义字符（`也` 对 `都`）——这两种情况都会绕过自我审查，只有工具拒绝整个映射表时才会被发现（同一个映射表曾因这两个原因连续被拒绝两次）。

5. 验证已完成的审查。任何进一步的编辑都会使哈希对应的审查过时，因此在候选项发生变化时，请重新生成并重新分类。通过验证后会写入 `.skill-regression-reviewed`，这是一个与内容绑定的本地状态回执。它有助于检测后续编辑，但有意不作为独立的打包授权依据；打包过程本身会重新验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可以识别静默失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在待审查的候选项，而不是工具失败；
2 表示调用或运行时失败。该工具能够证明精确迁移和接口保留，但会有意拒绝根据模糊的词语重叠来推断语义等价性。像“check permission denied”这样的通用短语，不能悄无声息地替代“已登录但没有角色”这一精确契约。还要检查标记为
`only_outside_runtime` 的候选项：如果运行时行为只存在于 eval、测试或不可达的参考实现中，那么它就不在正常调用路径中。

**每次编辑 SKILL.md 后立即验证 — 不要等到打包时（第 7 步）。** 该检查能够及早发现的故障是真实存在的：用未加引号的 YAML 标量编写 frontmatter 描述时，在 Claude Code 的宽松解析器中可以正常解析，但会在严格解析器中失败（codex 曾针对一个已经发布数月的 skill 报告 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中包含 ` #` 时甚至不会报错 — 它会静默截断其后的所有内容，导致触发关键词消失，而每次扫描仍然显示为绿色通过。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**将描述写成 YAML 块标量**（`description: >-` 后跟缩进段落）：只要描述中包含 `: ` 或 ` #`，或跨越多个句子，就应采用这种写法 — 自上述事件以来，这是每个新建或编辑的 description 的推荐约定，因为块标量原生支持这两个字符。

**更新现有 skill 时**：扫描每个现有引用和捆绑资源，查找相应更新，然后通过上述迁移门禁。迁移契约需要 SKILL.md 提供直接的运行时指针；eval 或变更日志不能替代它。

接下来的三项检查是**升级探查，而不是无条件扩大范围**。如果采取其中任何一项会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖、权限或外部写入，请先停止，并在修改 skill 前重新归类为 Tier 3。Tier 1 和 Tier 2 可以检查这些问题，但不会因此从中获得新的交付项。

**脚本检查**：在宣布编辑完成前，询问：*源对话（或 eval transcript）编写了哪些代码 — 如果不处理这些代码，每次未来调用都会重复编写？* 当所选层级已经授权开展相应的能力工作时，将其（参数化、经过清理的版本）打包到 `scripts/` 中，并修改文档以指向它。否则，将该信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的副作用进行打包。分工如下：**scripts 负责执行，文档负责理解** — 如果 skill 的方法只存在于说明文字中，那么每次运行都会重新承担完整的编写成本。之所以将这项检查放在编辑步骤中，正是因为跳过 eval 循环的路径（对话提炼、直接编辑）永远不会到达“Improving the skill”中针对 eval transcript 的这一版本检查。

**组件货架检查（针对 artifact-EMBEDDED 片段提出的同一个问题）**：Scripts 检查涵盖的是 *skill* 执行的代码；生成 artifact 的技能（报告页面、演示文稿、文档）还会不断积累由其*输出*嵌入的片段——图像叠加组件、粘性导航、图表配置、CSS 块。如果连续生成的输出都各自手写相似的片段，这就是指向另一层货架的同一种重复信号。在添加 `components` 子文件夹或注册表引用之前，先应用上述升级规则；Tier 1/2 可以提出方案，但不得创建组件能力。获得 Tier 3 授权后，使一个代码片段成为货架组件的关键在于围绕它建立的契约：(a) **原样嵌入块**——将 BEGIN/END 标记之间的整体内容复制到 artifact 中，零依赖，以便单文件 artifact 保持自包含；(b) **注册表条目**，说明交互契约（触发条件、按键绑定、关闭行为、边界情况）及其来源——它来自哪个已交付的 artifact、用户何时批准了它；(c) **准入门槛**——只有用户实际使用过并批准的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但外观漂亮的片段不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定属于契约，在不同运行之间不得漂移，而颜色和尺寸可以遵循 artifact 自身的风格；(e) **回写循环**——为某个 artifact 发明的片段，一旦获得批准，就要在同一会话中晋升到货架上。之所以重要，不只是为了节省 token：手写重做的片段会*漂移*——每次重写都会悄悄改变按键绑定、关闭行为、计数器等；而对于每天阅读这些 artifact 的用户来说，交互一致性*就是*产品体验。用用户为第一个此类货架留下的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目指纹）：某报告页面 skill 的灯箱图库组件（图像叠加：←/→ 循环切换组内图片，ESC 关闭，就地缩放，n/N 计数器）及其 `interaction-components` 注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击流程测试完成验证。参见方法论案例 17。

**流水线检查**：考虑此 skill 的输出是否会自然地馈入另一个 skill，以及是否应当由现有 skill 链接*进入*此 skill。添加或实质性修改“Next Step”交接或流水线契约，需要在编辑前重新归类为 Tier 3；Tier 1/2 可以提出方案，但不得顺手添加。

**引用与自应用检查（那些能躲过谨慎作者检查的缺陷）**：有一类失败模式，它们从内部看起来都像已经完成的工作，而且没有任何一种能通过更加仔细地重读来捕获——每一种都需要改用*机械化*操作。（开头特意没有写数量。“Three failure modes:”是一个派生数字，只要有人追加一个项目符号，它就会过时；而计算正文中的数量之所以尤其难以捕获漂移，正是因为正文*不包含发生变化的内容*——对列表本身进行重新编号的 grep 和 diff 都会径直略过它。）它们被归在这里，是因为共享同一个原因：**写下断言与验证断言是两种不同的模式，而单次遍历无法同时完成这两件事。**在你撰写内容时，“see rule 8”*就是*那个断言；你并没有同时打开 rule 8。

与上面三个升级探针不同，这一项**不按层级限定**——它取决于你写了什么。一个既没有添加指针也没有添加规范性规则的 Tier 1 修复，在这里无事可做，而且你不必自行判断：corollary 的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 给出答案。无论在哪个层级，只要你写了指针或规则，以下各条就适用。

- **你写下的每一个指针，都要打开其目标，并从中复制一行出来——而且要在写下指针之前完成。** 不要只说“我确信该规则列出了全部三个标记”：把其中一段粘贴到你已经在为此步骤产出的内容中（审查备注、提交消息正文或你的回复均可），放在第二位读者之后可以拿它与目标进行核对的地方。只看而不粘贴的片段，正是本句开头所拒绝的自我评估。错误的交叉引用在重新阅读时是不可见的，因为错误的指针看起来与正确的指针完全一样，而作者又是唯一一个必然会“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal rule 3”，意指一条关于不要引用过时枚举的规则——但被引用文档自己的 *rule 3* 讲的是样本量，而实际被引用的规则位于另一个文件中；读者按照该文档既有的自引用约定跟过去，最终会落到一个无关主题上。同一轮编辑还提交了一个方向倒置的指针（对上方内容写成“见下文”），以及一个指向不存在的章节标题的指针。
- **文件一旦包含两个编号列表，单独写“rule N”就具有歧义。** 检查应针对每个指针，而不是每个文件：在写下“rule N”之前，运行 `grep -n '^N\. ' <file>`，确认目标章节中恰好有一个匹配项；如果有多个，就同时写明章节名称。（**不要**把这变成文件级别的警报，例如“该文件是否包含多个从 1 开始的列表”——在任何长文档中，这几乎总是成立，因此它会对健康输入触发，并最终被忽略；纪律 #6 警告说，这比没有检查更糟；在这个文件上运行一次，你就会亲自看到。）在真实案例中，一个单独的“rule 1”对应三个候选列表，而从上到下搜索时首先命中了错误的那个。
- **添加任何规范性规则后，都要根据其旁边的行检查它——并让检查产出一个工件，而不是一个结论。** 使用与下面 corollary 相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的代码变更片段。这里亲自阅读就足够了——你不是在进行模式匹配，因此不需要脚本——但必须带上该 ref：单独使用 `git diff` 只会显示尚未暂存的工作，而你一旦执行 `git add`，它就会什么也不输出；这正是本段自己的 corollary 为规避的五种静默空结果模式之一。将新规则拆分为独立的条款，并逐条写下同一变更片段中满足该条款的那一行。（下面 corollary 中的 `scripts/reference_net.sh` 是另一项工作：它会列出供你解析的**正文交叉引用**。它不会把变更片段交给你，也不会告诉你规则中的某一条款是否得到满足。）**旁边没有对应行的条款就是问题所在。** 那个诱人的简短版本——“我的新规则通过了吗？”——对于 30 秒前写下它的人来说不可能失败；这正是纪律 #6 所说的应优先采用可证伪观察而非自我评估的含义，因此本条也必须提供它所要求的工件。最先暴露问题的通常就是规则旁边的段落。真实案例：某条新增规则写道“始终报告原始计数和过滤后计数——差值*就是污染量*”，但同一提交中的自身演算示例只打印了过滤后的数字。同一 diff 中的另一段陈述引用了两个数字，却没有说明这些数字是否是在相邻新增规则刚刚规定为强制的限定条件下收集的。范围很小且有明确边界：不是“重新阅读整篇文档”，而只是“我 30 秒前写下的规则，在我 30 秒前写下的那些行上是否成立”。
- **为每条新规则添加一行，说明由谁执行它，以及他们是否确实能够执行。** 现有工具无法满足的规则，会被那些认为自己已经遵守规则的人跳过——这是最糟糕的一类，因为它会产生有文档记录的虚假信心。真实案例：一条新规则要求“检查两个日志存储”；项目自己的规范性单命令分诊工具却硬编码了其中一个，因此标准工作流会针对该规则本来要捕获的故障返回干净结果。该规则本身没错，却不起作用，而且没有说明这一缺口。**让这一点可证伪的工件**（没有它，本条就是一个禁止自我评估的段落中唯一的自我评估）：写明哪个工具或命令能够捕获违规，然后**针对一个你已知它应该捕获的案例运行一次**。如果它在已知有问题的输入上返回干净结果，你就测量出了该规则不起作用——把这个缺口直接写入规则本身。“他们是否确实能够执行”如果只是凭记忆回答，正是纪律 #6 所拒绝的未经验证断言。**当没有任何工具能够判定该规则时**——大多数正文和品味规则都属于这种情况，因此不要把它当作逃生口——工件就是那句明确说明这一点的话：*“没有任何东西会强制执行这一点；只有在某人记得它的情况下，它才会成立。”* 这比检查通过处于更糟糕的位置，而把这一点明确说出来正是目的所在；执行情况保持沉默的规则会被默认遵守，而不是得到验证。请注意本条自身诚实的局限：工具和已知有问题案例的选择仍然是一项判断，因此它只是移动了未经验证的步骤，而没有消除它——这比替代方案便宜，但并非没有成本。
- **推论——你的修复本身也是缺陷来源，因此要在最后一次编辑之后，重新检查你触及的区域。** 在对单次变更进行两轮审查时，第一轮发现了八个问题；第二轮又发现了八个，其中**七个是由第一轮修复引入的交叉引用错误**。重写一句话会移动其周围的锚点。这也是为什么对于读者依靠指针导航的工件来说，“已经审查过”并不是终点：你一旦根据审查结果采取行动，审查就立刻过时了。重新检查是机械性的，而且应当使用**脚本**，而不是要求你重新输入命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的 bundle 中）。它会列出你添加的行之间的正文交叉引用，以便你打开每个目标，确认其中确实写着你所声称的内容。首次使用前请先阅读其头部注释——其中解释了它为什么要求 base ref，而不是默认使用 `HEAD`，以及它有意不执行哪些操作。

**在开始编辑之前获取 `<base-ref>`，不要事后再获取。** 在开始时将其解析一次，得到字面量 SHA——即当你开始时执行 `BASE=$(git rev-parse HEAD)`——并在此处以及上面的项目符号中复用同一个值。如果你运行了现有 skill 迁移门禁，它就是你已经建立基线所依据的 ref。稍后传入 `HEAD` 才是陷阱：提交之后，`HEAD` 包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请恢复该值（使用 `git log`、`git reflog`，或你提供给迁移门禁的基线），不要用 `HEAD` 替代；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印一条提示，但不要依赖在那里才发现这一点。

**为什么这里要使用脚本，而本段其余部分都是 prose。** 它所替代的那条单行命令经历了五轮修补——将 diff 锚定到正确的 base、查看已暂存的编辑、在提交后仍能正常工作、跳过 diff 自己的 `+++` 标头、删除误导性的 `-n`——其中四轮都增加了另一种让它不打印任何内容并以 0 退出的方式，而这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种问题的另一种表现：它删除的 `-n` 原本会打印真正的匹配项，但行号是按经过管道传输的流计算的，因此看起来很权威，实际却指向不存在的位置——这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都会持续放过它本来要捕获的缺陷。Prose 无法验证自己的输入，无法说明发生了哪种结果，也无法进行测试；脚本可以完成这三件事，而且它的契约是：**每种结果都必须被命名，错误输入必须明确失败**。这就是本步骤前面所述的 Scripts 检查，应用于本段——而这五轮修补正是忽略它所付出的代价。

**阅读它的 verdict，而不只是退出代码。** 脚本只要成功运行就会以 0 退出，因此单独查看 `$?` 无法告诉你它发现了什么；答案在 verdict 行中，而且它总会明确指出以下情况之一：发现了 references（逐一解析）、文件与 base 相同、文件已更改但没有新增行，或新增行中没有任何类似 reference 的内容。这些是不同的结果，脚本特意将它们彼此区分——这个检查曾经把它们合并成一个无声的“什么都没有”，正是它后来变成脚本的原因。它只需几秒钟，并且不依赖警觉性，这正是 discipline #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的 pointer——“见下方章节”、“如上方规则所述”——因此也要阅读新增的行。）

### 步骤 5：Sanitization Review（任何 public skill 都必须执行）

**在此门禁之前，当 discipline #5 到期时，其独立检查必须已经运行**，并且当前变更的 `independent-review.md`（位于你的私有、受 git 跟踪的知识仓库中——不在已清除的工作区中，也不在任何已经或可能变为 public 或 distributed 的仓库中）必须存在**并且已经提交**。对于新 skill，它始终适用；对于现有 skill，使用下一段中的阈值。一个尚未提交、仅存在于 git 工作目录中的文件，与一个从未写入的文件，在实际意义上没有区别；`ls`/`test -f` 只能确认它在磁盘上，而不能确认它能够留存。对于**新** skill，这是任何内容第一次离开你掌控的步骤，因此也正是在这里真正执行该 discipline，而不只是陈述它——一条位于使用点上方 1000 行、却没有任何检查机制的规则，每次都会输给完成任务的冲动。

**对于已经发布的 skill，编辑完成后真正离手的那一刻就是执行 push，而不是这一步。** 这个门槛用一句“仅限内部，跳过”就能回答；对于仅涉及文档的变更，打包甚至可能完全不会运行——因此把审查固定在这里，意味着一次 skill 编辑可能在没有任何独立人员审阅的情况下到达公共分支。真实案例（2026-07）：对这个文件本身的一次变更发布了一个发现命令，但它无法访问旁边正文声称覆盖的三个根目录；变更已经合并，直到*事后*专门安排的审查才发现了问题。**因此，对于现有 skill：独立审查及其记录产物必须在执行 `git push` / 发起 PR 之前完成——在 push 时运行的各个门禁（回归审计、验证、扫描）检查的都是结构，没有任何一个能告诉你这些指令是错误的。** 这沿用纪律 #5 的阈值，不作任何改变：当*规则、契约或数字发生变化*时就必须执行，而拼写错误或纯格式重排则不需要。让一个拼写修正也必须等待一轮审查，只会教会人们形成 #6 所警告的那种条件反射——“这次改动很小”变成普遍豁免，最终连真正重要的变更也被它涵盖。

**对于要进入公共仓库的 skill，这不是可选项。** 私密内容经常会泄漏到公共 skill 中，而扫描器漏掉的泄漏才是危险的——非英语语言中的真实姓名、真实对话记录中的逐字内容、被放进示例中的真实案例。只有在该 skill 确实仅限内部使用时才能跳过。

**按去向而不是按主题界定审查范围。** 只有公开发布的产物——skill 包本身——需要清理。留在私有仓库中的配套文档（skill 提炼所依据的事件报告、内部运行手册、项目的 CLAUDE.md）应保留真实的主机名、路径和时间戳：删去这些信息会破坏它们的审计价值，而你最终还会把这些修改撤销。曾有一次提炼会话正是因为清理过程被应用到了源材料涉及的所有内容，而不只是公共 skill，结果经历了三轮返工。

**先检查去向，并让它预先填入建议。** 在 skill 将要存放的仓库上运行
`gh repo view --json isPrivate`（或者读取
`quick_validate` 已经打印的提示）。私有去向会使选项 C 成为默认建议，而不是事后才想到的选项——“除非另有说明，否则假设为公开”正是把私有 skill 的工作路径变成没人要求的占位符的原因。

**触发清理的依据是去向的 `isPrivate`，而不是任务在主观上有多像发布。** 两者并不总是一致，而当它们不一致时，除非你明确指出这一点，否则人的直觉就会占上风。把内容*移入 marketplace skill* 会让人感觉是在发布——marketplace 正是用来分发内容的地方——所以即使源仓库和目标仓库都是私有仓库、没有任何内容会被发布，清理反射也会被触发。真实案例（2026-07）：一次从项目级 skill 迁移到私有 marketplace skill 的过程中，把真实的配置路径、真实的十六进制值和真实的具名示例都泛化成了占位符。`quick_validate` **每次**运行都打印了 `🔒 audience: private`；作者每次都看到了，却还是进行了清理，因为这种*活动*在感觉上像是在发布。代价并非只是表面上的——真实路径能让下一位读者去核对该值；而“项目自己的令牌文件”是无法打开的。

所以要把它当作一次查找，而不是一次判断：**读取目标位置的 `isPrivate`；如果它是
`true`，则脱敏需要由所有者主动提出。** 从私有位置移到私有位置是一次移动，而不是一次发布。**当两个探测都没有返回结果时**（尚未有远程仓库、尚未运行
`quick_validate`），你没有可用的查找结果——应回退为将其视为公开，并明确说明这一点，因为这种不对称性就是如此：多问一个问题只会多花一句话，而不必要的信息泄露却无法挽回。并且，`isPrivate` 报告的是目标位置**今天**的状态——一个位于私有仓库、正准备发布的 skill，应当在发布它的 push 中执行脱敏，而不是在这一次中执行。如果你发现自己开始思考某项内容在私有目标位置中是否“应该”泛化，这种思考本身就是信号。

使用 **AskUserQuestion** 确认处理深度（对于公开目标位置，确认处理深度，而不是是否执行；对于私有目标位置，确认是否需要执行）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**脱敏流程——通读是方法，扫描只是辅助：**

1. **亲自通读整个 skill，并进行语义判断**（这是真正的检查）：SKILL.md + 每个 reference + 每个示例。对于每个具体名词 / 示例 / 代码片段，询问“是通用占位符或公开实体，还是从真实项目 / 真实人物 / 真实对话记录中直接取来的？”替换后者——即使没有扫描器标记出来也要替换。这是唯一能捕获没有关键词可匹配的信息泄露的方法。完整指导和语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器，作为低成本的第一遍检查**：使用检查清单中的 grep 模式 + `security_scan.py`（步骤 6）。它们可以快速捕获明显的机密信息 / 路径 / 已知名称——但“没有匹配结果”并不等于通过。
3. **替换**每个发现的问题，将其替换为保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。从经验中学到的两条规则：占位符本身不能编码真实值——`<acme-corp-domain>` 会原样泄露它本应隐藏的名称；应改为使用其*角色*命名（`<api-domain>`、`<upstream-provider>`）。另外，当你编写批量替换脚本时，要为其指定限定在 skill 目录内的明确文件白名单——不限定范围的查找与替换会毫不留情地改写项目自己的 CLAUDE.md，并迫使你执行 git restore。
4. **通过重新阅读而不是重新 grep 来验证**：重新阅读改动过的部分，并确认没有损坏的引用。

### 步骤 6：安全审查

在打包或分发 skill 之前，运行安全扫描器，以检测硬编码的机密信息和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）
- 完整的软件包超集：普通发布文件，以及可选的根目录 `evals/`。非发布的 `.enrich/`、`tests/` 和 `dist/` 构建产物，按照打包器和内容哈希证明所使用的同一共享策略排除。

**它不涵盖的内容**——这也是为什么仍然必须执行步骤 5 的通读检查：gitleaks 和正则规则只能匹配*已知的机密格式和你列出的模式*。对于没有关键词的私密内容，它们在结构上无法识别——例如，非英语语言中的真实人物/项目名称、真实对话记录中的逐字内容、从你自己的工作中直接摘取的真实示例。`security_scan` 显示绿色，意味着“未发现已知格式的机密”，**而不是**“该 skill 已完成脱敏”。绝不要将其当作后者。

**首次设置：**如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 干净（可以安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**对于私有 skill，发现项是信息，而不是待办事项。**扫描器无法区分泄露的凭据和*本来就应该存在*的凭据——例如，一个其全部价值就在于预先填好的模板，或一个指向运行它的唯一机器的脚本。私有仓库中绝不要自动修复：报告发现的内容，让所有者做出选择。下面的选项 A（“自动修复”）适用于准备发布到公共环境的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 步骤 7：打包 Skill

Skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个现有的 Git 跟踪 skill，在提供并重新验证完整审查结果之前，都会禁止打包。当前标记仅是本地状态回执，因此先提交或手写标记都无法绕过审查。下一次编辑后，审查结果将变为过期状态：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及使用 `--include-evals` 发布根目录 `evals/` 目录（默认情况下作为开发资源排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **重新验证已完成的现有 skill 回归审查**：每当 Git HEAD 已经包含该 skill 时都执行；单独的标记永远不能授权打包
3. **验证安全扫描**（内容哈希必须与上次扫描匹配）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 步骤 8：更新 Marketplace

打包后，更新 marketplace 注册表，以包含新的或已更新的 skill。

**对于新 skill**，在 `.claude-plugin/marketplace.json` 中添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于已更新的 skill**，按照 semver 提升 `plugins[].version`。对 skill 文件的任何更改——即使只是修复一个单行拼写错误——都需要提升版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧版 skill，而你的修复则仍未发布。

**然后将其记录到变更日志中——这一步经常被跳过。**版本号提升让更新*可以安装*；而变更日志条目让它在六个月后有人遇到同样的问题并进行搜索时，仍然*可以找到*。如果变更日志记录了其他每个 skill 的版本，却悄悄漏掉你的版本，那还不如完全没有变更日志：这些空白看起来就像“那里什么都没变”。

不要自行发明格式，而应匹配现有条目的形状——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。
要在**与版本号提升相同的提交中**写入该条目；“稍后”更新的变更日志，往往就意味着永远不会更新。

真实案例（2026-08）：某个 skill 连续两个版本发布时都正确提升了版本号，通过了绿色门禁并合并了 PR——却**完全没有变更日志条目**，因为这套流程中没有任何内容要求添加变更日志。两次发布都只是在之后的审计中才被发现。这正是纪律 #6 在该文件自身上的体现：如果一条规则只存在于约定中，而不是存在于步骤中，那么它每次都会输给急于完成任务的倾向。

**让注册表差异保持最小——这是所有 skill 共用的唯一文件。** marketplace 清单是所有并行编辑者发生冲突的地方，因此，在这里进行无关的格式化更改，比在其他任何地方进行相同的更改代价都高：它会把原本干净的三行版本提升变成其他正在同时编辑的人的合并冲突。当你通过脚本更新它时（解析为 JSON、修改、写回），重写过程可能会悄悄规范化文件原本未采用的格式——末尾换行、缩进宽度、键顺序、Unicode 转义。往返处理纪律：之后重新读取该文件，并对其运行 `git diff --stat`；**唯一允许出现的行，必须是你有意修改的字段。**如果出现额外行，请恢复文件原有的约定，而不要提交这种规范化改动（某次脚本化版本提升曾给一个原本从未包含末尾换行的清单添加了末尾换行——只多出一行无用差异，却发生在最可能被其他人同时编辑的文件中）。同样的原则也适用于 skill 会修改的任何共享注册表：锁定文件、目录、索引文档。

**当一个 PR 经历了几次合并仍未结束时，请执行 rebase——然后证明你没有吞掉任何人的工作。** 正是因为清单容易发生冲突，它也最容易过时：一个同时修改注册表和变更日志的开放 PR，只要其他内容合并进来就会产生冲突，因此应预期出现 `mergeable: CONFLICTING`，而不要把它当成意外（有一个 PR 就是在某天下午 main 向前移动了 7 个提交后遇到这种情况的）。如果仓库采用 squash merge，应执行 rebase 而不是 merge——在压缩合并的历史中，合并提交没有任何意义。冲突本身几乎总是**追加式的**：两位作者分别在同一分区追加了自己的条目，因此解决方式是**两者都保留**，绝不要使用 `--ours`/`--theirs`，因为那会悄悄丢弃同事添加的行。

人们会跳过的步骤，恰恰是能够捕获错误解决结果的步骤——**解决冲突后，证明与基线相比唯一的差异就是你自己的修改：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要使用单独的 `--force`：如果远程仓库自你上次 fetch 以来发生了变化，租约机制会使推送失败；这正是有人向你的分支推送过内容、而普通 force 会将其抹掉的情况。

**插件边界不属于本 skill 的职责范围。** 是否应将 skill 拆分到不同插件中、如何组织 `source`/`skills`，以及用户是否可以单独切换 skill，都属于打包/分发领域——SSOT 是 `marketplace-dev` skill，而不是这里。当任务确实需要做出这些决策时：确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与 `skill-reviewer` 需要其脚本时拉取 `skill-creator` 相同），然后阅读 marketplace-dev 的 cache-and-source-patterns 参考资料并遵循其中的指导。不要在此处重复其规则；复制一份会导致内容逐渐偏离。

**重命名、迁移或移除 marketplace 条目，对于已经安装它的每位用户来说都是破坏性变更**——当某个条目消失时，Claude Code 不会清理已安装的副本，导致悬空安装，并在每次执行 `marketplace
update` 时出错。应将此类变更视为 API 弃用：在变更日志中附带迁移说明，并遵循 marketplace-dev 对具体操作的指导。

**如果你亲自提交/推送 skill 仓库：** 对于已有 skill，如果当前变更触及 discipline #5 的规则/契约/数值阈值，请确认审查产物记录了这项变更，并且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不只是确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的审查不能满足当前的实质性变更。第 5 步的说明解释了为什么对于已经发布的 skill，真正的强制执行点是推送，而不是打包。然后只暂存 skill 的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充斥着无关的变更，否则这些内容也会被带入提交（有一次提交就卷入了一堆无关的 transcript 文件，之后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库实际的可见性，不要根据路径想当然——一个公开的 skill 仓库应当走 PR + review 流程，而不是直接推送到 main。

### 第 9 步：交付或迭代

完成技能后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试技能后，用户可能会要求改进。通常这会紧接着发生在技能使用之后，此时用户还清楚记得技能的表现。

**优化筛选原则：**只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了某项内容，就不要重复添加。

## Claude.ai 特定说明

在 Claude.ai 中，使用相同的验证深度路由器和重型评估授权门控。当完整的通用配对流水线获得明确授权后，工作流为起草 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子代理，部分机制需要调整。

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，读取技能的 SKILL.md，然后自行遵循其中的说明来完成测试提示。一次只处理一个测试用例。这种方式不如由独立子代理执行严格（因为技能由你编写，也由你运行，所以你掌握完整上下文），但它仍然是有用的健全性检查——而人工审查步骤可以弥补这一点。跳过基线运行——直接使用技能按要求完成任务即可。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的虚拟机没有显示器，或者你正在远程服务器上），则完全跳过浏览器审查。改为直接在对话中呈现结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），将其保存到文件系统，并告知用户文件位置，以便他们下载和检查。直接在对话中询问反馈：“看起来怎么样？有什么需要修改的吗？”

**基准测试**：跳过定量基准测试——它依赖基线比较，而在没有子代理的情况下，这些比较没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重新运行测试用例、询问反馈，只是中间不再加入浏览器审查步骤。如果有文件系统可用，你仍然可以将结果整理到各次迭代的目录中。

**描述优化**：本节需要使用 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要使用子代理。请跳过本节。

**打包**：`package_skill.py` 脚本可以在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 中，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能要求你更新现有的 skill，而不是创建新的 skill。在这种情况下：
  - **保留原始名称。** 注意 skill 的目录名称和 `name` frontmatter 字段——保持原样使用。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前复制到可写位置。** 已安装的 skill 路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从副本进行编辑和打包。不要传递 `--new-skill`；非 Git 副本的现有 skill 仍然属于现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再将其复制到输出目录——直接写入可能因权限问题而失败。

## Cowork 特定说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此经过明确授权的通用配对流程可以运行基线和评分器。子代理可用并不代表已获得授权，也不足以证明需要额外角色；请说明必要的分支，限制并发，并在并行执行不会增加证据时按顺序运行案例。
- 你没有浏览器或显示界面，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击、在其浏览器中打开该 HTML 文件的链接。
- 在经过明确授权的**通用配对运行**之后，应在自行修改 skill 之前，使用 `generate_review.py` 为人工生成评估查看器；默认层级证据、未经授权的工作，以及取代查看器机制的专用工作流，不会仅仅因为工作是在 Cowork 中进行就获得查看器义务。
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 文件下载下来。随后你可以从下载的位置读取该文件（可能需要先请求访问权限）。
- 打包功能可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中也应能正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，但请将其留到 skill 完全完成且用户同意其状态良好之后再执行。
- **更新现有 skill**：用户可能要求你更新现有的 skill，而不是创建新的 skill。请遵循上方 claude.ai 部分中的更新指南。

- 弄清楚 skill 的用途
- 对于现有 skill，在编辑前对旧包进行快照和清点
- 在执行任何专用工作流退出操作之前，选择能够证伪此次更改的最低验证层级，并记录原因
- 起草或编辑 skill
- 运行该层级所需的证据，或所选专用工作流声明的等效机制
- 对于获得明确授权的通用配对运行，使用用户提供的结果进行评估，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复上述步骤，直到你和用户都满意
- 运行并通过现有 skill 回归审查；仅通过评估并不算完成
- 打包最终 skill 并将其返回给用户。

如果你有 TodoList，请将选定的验证层级及其默认证据添加到其中。只有在明确获得通用配对流水线授权后，才添加“创建 evals JSON 并运行 `eval-viewer/generate_review.py`，以便人类审查测试用例”。
