# 技能创建器

用于创建新技能并持续改进技能的技能。

从高层次来看，创建技能的流程如下：

- 确定你希望技能实现什么，以及大致应如何实现
- 将变更归类到能够证伪其潜在失败模式的最低验证层级
- 编写技能草稿
- 使用能够证伪变更后行为的最少证据进行验证；将完整的成对评估流程视为需要单独授权的工作，而不是某个层级标签的自动后果
- 当所选层级产生定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写技能（如果定量基准测试暴露出任何明显缺陷，也要据此重写）
- 重复这一过程，直到你满意为止
- 仅当当前证据无法解决变更后的行为时，才升级验证层级

使用此技能时，你的任务是判断用户目前处于这一流程的哪个阶段，然后介入并帮助他们推进适用的阶段。完整的 A/B 基准测试是一种能力，而不是每次编辑都必须承担的成本。诸如“优化”“改进”或“全面”之类的词描述的是意图，而不是失败面或评估预算。不要仅仅因为任务听起来范围很广，或因为一段较长的对话已经展开，就创建评估文件、扩展成对代理、评定输出，或启动查看器。

以下六项持续适用的准则贯穿始终，因为这些失败模式会产出看似令人信服、实则错误的技能：

1. **先验证，再编写。** 任何进入技能的技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你执行并观察到的内容——无论是在本次会话中，还是在经过明确批准的既有会话中挖掘出的内容。现在无法验证？要么立即去验证，要么明确标注（“未经验证——来自记忆”）。技能会放大其中包含的一切：经过验证的知识会复利增长，自信陈述的错误也会复利增长。对于知识型技能（内容主要是关于外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md)，了解其操作层面的要求：权威层级（观察到的行为 > 机器可读的契约 > 实际运行过的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例的冒烟测试，以及受众/Windows 可移植性检查清单。一次源头依据审计发现，多个自信陈述的契约声明与作者已有的证据相矛盾（方法论案例 9）。
2. **将“无法实现 / 不支持”视为假设，而不是结论。** 当某项能力看似受阻时（API 错误壁垒、工具无法连接、格式无法打开），在将“平台不支持此功能”写入技能之前，应穷尽各种观察路径——UI 自身的网络流量、替代通道、不同的文档化标识符。观察到的行为优先于推测性的请求形状。
3. **站在领域已有成果的肩膀上——在编写或优化技能的方法论之前，默认将该领域已确立的最佳实践检索到上下文中。** 技能的方法论质量取决于上下文窗口中的知识，而不是潜藏在权重中的知识：预训练知识是不完整的，会过时，而且往往只有在实际提取出权威来源后才会被激活。因此，你所编写内容的质量上限是 `你的训练数据 + 用户输入`——*除非*你有意检索该主题领域真正已有的成果。去做这件事：使用 WebSearch 搜索该领域的经典理论 / 标准 / 方法，并阅读该领域中随附或已安装的技能，然后将其中起关键作用的原则连同出处纳入技能。这与下面的“既有成果研究”是不同的维度——后者用于寻找可复用的工具/基础设施；前者则是让技能的方法论以该学科积累的科学成果为依据。将其作为**默认行动，而不是等用户要求后才做的事情**：简要告知用户你正在参考哪个领域的成果，让他们可以说“跳过”，但绝不要在距离你进行一次搜索就能获得 40 年公开领域成果的情况下，仅凭记忆加用户提示，交付一个方法论上限受限的技能。例如，数据可视化技能必须吸收 Cleveland & McGill 的图形感知排序和 Bertin 的视觉变量（位置/长度优于颜色，颜色优于文本——这是经过测量的结果，而非审美判断）；日期/时间技能必须呈现成熟的库及其经典陷阱；说服/谈判技能必须检索既有框架，而不是凭记忆重新发明。如果经典知识只存在于你的权重中，却从未进入上下文，那么你就是在本可引用的地方进行猜测。
4. **在压缩现有技能之前，先保留它。** 更新现有技能是一项迁移工作，而不是从空白页面开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧版内容包，或从明确的 Git 引用重建它；随意复制一份并附上来源标签不能算作基线。盘点运行时能力、触发上下文、接口、参考资料以及评估覆盖范围。渐进式披露和简洁性允许你移动或去重内容，但不允许你悄无声息地删除行为。编辑后，运行 `scripts/audit_skill_regression.py`，并对每个未匹配的旧单元进行分类。仅存在于 `evals/`、测试或未链接的参考资料中的运行时契约，仍然算是丢失。在任何候选项尚未分类，或任何真正的缺口仍未修复之前，不要称更新已完成。同样的逻辑也适用于**反转**，而不仅是删除，并涵盖任何此前做出的承诺——不只是带有日期和名称的承诺：**推翻已经做出的决定必须是一项提案，绝不能是副作用。** 要明确说出来并获得接受。无声的重写比无声的删除更糟糕，因为它一次性摧毁了成果及本可发现问题的证据——也让所有下游审查者失去判断依据（见 #5）。

5. **仅靠自我审查不会有任何成果交付——独立、全新上下文的对抗性审查是固定步骤，而不是特殊情况。** 你“现在已经没问题了”的判断，运行在生成该产物的同一个模型上，因此共享了导致缺陷产生的所有盲点。这一点有实证而非民间传说：没有外部反馈的内在自我纠正并不能可靠地改善输出，有时还会使其恶化（Huang 等，ICLR 2024）；当生成器和评估器共享错误模式时，反复迭代会**提升信心，却不会增加信息**。更多自检无法摆脱这一点；只有外部视角才能做到。**完整流程——包括提示词模板、锚点选择、发现项表格和示例案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；在第一次审查前先阅读它。** 承担核心作用的规则如下：
   - **独立性有两个层面，而第二个层面正是作者容易忽略的。** *审查者的上下文*不能是你的分支——分支会继承你的盲点，并返回一个“已审查”的印记。但它所依据的*证据*也必须位于变更的**影响范围之外**，否则它会继承你的**结论**：它读取一个与规范已经一致的产物和规范，然后报告二者一致。注意，“本次会话中未编辑过”这一界线太弱——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，三名审查者因此对一个缺陷视而不见，而他们在其未触碰的副本中发现了该缺陷。应根据锚点被你触碰过的难易程度进行排序：用户自己的对话原文 > 早于此次工作的 git ref（`git log --oneline <ref>..HEAD -- <path>`；其中任何一个属于你的提交都会使其失效）> 只追加日志（这是一种约定，而不是强制机制）。**Greenfield 没有锚点——请明确说明这一点并索要一个锚点，而不是报告一个你并未执行的通过结果。**
   - **只给它两样东西：产物和读者规范。** 不要给其他任何东西——不要提供设计理由、项目背景，也不要说“只需确认 X 没问题”，因为这会把独立审查者变成橡皮图章。读者规范是*规范*，而不是理由，因此它不会替任何东西盖章；省略它会浪费一半审查，因为审查者随后只能拿自身作为衡量标准。**对于 SKILL.md，读者是执行它的另一个代理**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——请询问哪些指令是它无法执行的。在运行前声明规范，之后绝不要用它来为发现项开脱。
   - **对于可理解性以及相对于语料库的完整性，它是真实依据；对于品味，它没有权威。** 直接应用前两项。把“这可能是个 bug / 我建议 Y”视为假设，先自行复现。绝不要委托 AI 垃圾或审美判断——这同样属于模型盲点。
   - **列举失败的*轴线*，而不是内容领域——这也决定运行多少个审查者。** 轴线是*你要提出的问题*；领域是*你要阅读的材料*。三个审查者分别覆盖场景、算术和 diff，但全都在问“这是否连贯？”，那只是把一个审查者计费了三次。**一个审查者是默认选项，而且通常已经足够**；只有增加一个额外轴线时，才再增加一个审查者。自我审查最不擅长的轴线是**忠实性**——“这是否仍然忠实于已经作出的承诺？”——因为正是作者移动了那项承诺；而连贯性与忠实性是正交的：一个产物可以完美地自洽，却完全不忠实于已经决定的内容。
   - **留下一个产物，否则这只是一条警告。** 纪律 #6 规定，产生意见的检查不如产生产物的检查——因此这一步也必须生成一个文件，否则在真正重要的时候，它会输给完成驱动。将 `independent-review.md` 写入你的私有、受 git 跟踪的知识仓库中的 `skill-reviews/<skill-name>/`：**逐字记录审查者提示词**（这样后来的读者才能看出它是否带有诱导性）、记录**带有处置结果及各自理由的发现项**（这正是合法筛选与丢弃不利内容之间的区别），以及记录**无法检查的内容**。如果你不知道哪个仓库是你的私有知识仓库（或者你没有这样的仓库），请说明这一点并询问用户——不要猜一个位置，以免文件落入两个禁区之一。两个禁区位置：**不得放在 `<skill-name>-workspace/` 中**（会被 gitignore 的临时目录会被清除——此文件是跨会话的审查证据，必须在这些目录之外存续），也**不得放在任何已经公开或可能公开、或会被分发的仓库中**——这通常意味着不能放在被审查 skill 自己的仓库中（审查内容本身必然会引用私有路径、真实姓名和项目细节）。在进行实质性编辑后，使用*新的*代理重新审查——也就是规则、契约或数字发生了变化，而不是拼写错误。**从步骤 5 开始，此文件就是审查已发生的证据；它不存在，就意味着审查没有发生。****写入文件不等于它在下一次会话中仍然存在——必须在同一轮中对该私有仓库执行 `git add` + `git commit`。** 一个未提交、位于 git 工作目录中的文件，不具备这条规则所要求的任何“受 git 跟踪”保证：它可能丢失、被覆盖，或者后续检查“是否已审查”的流程根本不会拾取它（真实案例：文件已正确写入正确路径，也包含真实发现项——但后续自动检查仍然失败，因为它从未被提交；修复方式是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械性的，并且与此互补：它证明你没有*删除*行为。但它完全不能说明你写下的内容是否真的可以被遵循。

6. **设计你编写的检查，使其无法自我认证为绿色通过。** Skill 很大程度上由各种检查组成——门禁、检查清单、“发布前”步骤——而一个执行上下文即使*违反了它所编码的规则*仍能通过的检查，比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴自那些早已解决这一问题的领域：
   - **验证必须覆盖其规则中的每一条款。** 如果规则写的是“A + B + C”，证据就必须分别要求证明 A、B 和 C。附加在三条款规则上的一行确认语句，会被作者已经完成的那一条满足；其余条款则完全不可见。真实案例：一个报告编写 skill 带有一道交付门禁，其规则写的是“选项以并排芯片呈现 + 突出显示推荐项 + **背景信息应使用陌生人也能理解的完整、自洽句子来书写**”——但其下的证据行只要求“包含 N 个决策项，且全部渲染为芯片”。作者运行门禁、写下这条证据，自我认证为绿色通过，最终发布的页面上的标签却只有单个字符，所有上下文都被删除了。规则始终存在于文件中；只是检查从未衡量过那一条款。
   - **对健康输入误报的检查，比没有检查更糟。** 上面的失败是检查在应当失败时通过；这里则是它的镜像——检查在应当通过时失败。这种情况代价更高，因为它会教会操作人员反射性地绕过检查（`--no-verify`、`SKIP=1`、`--force`），而一旦形成这种反射，门禁就会对*所有*输入失效，包括它原本要保护的那些输入。因此，在编写失败即关闭的检查时，**误报应优先于漏报**：漏掉一个真实问题只会让你损失这一实例，而误杀一个健康输入则会让整个门禁失效。  
     注意这个信号：**反复踩中同一个陷阱所产生的挫败感本身就是风险信号**——这正是作者会发布一个从未在健康输入上校准过的防护措施的状态。真实案例：一天之内连续三次踩到同一个格式陷阱后，作者向 linter 中加入了一个正则检查；它误杀了项目自身语料库中的 **33 个健康输入**，并在同一小时内被回滚。启用之前先进行校准——在真实且已知正确的材料上运行任何失败即关闭的检查，并确认零误报；宁可放宽检查，让它偶尔漏掉问题，也不要让它出现任何误报。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是自洽的”无法由撰写它的人判定为失败；而“覆盖页面的其余部分，单独阅读一张卡片，并说明它正在决定什么”则可以。优先选择能产生某种产物的检查——命令输出、引用的行、屏幕截图——而不是只能产生一种意见的检查。
   - **同样的怀疑也适用于你所*运行*的检查，而不仅是你所编写的检查。** 上述四条规则约束的是随 skill 一起交付的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样是工具，而错误的工具会像正确的工具一样自信地报告干净结果。在一次 2026-07 的会话中，五条彼此独立的验证命令在两个方向上都给出了错误结果：没有 `-L` 的 `find` 报告已安装 skill 的文件缺失（它们其实位于符号链接之后）；`grep --exclude-dir=<name>` 隐藏了正在审计的对象的第二份副本；反转的 shell 条件错误地警告某项删除并未发生；跨越换行符的正则凭空制造出 55 个“丢失的引文”；而在五个文件中的两个文件上进行搜索，却报告有两条规则缺失，而它们其实存在于第三个文件中。**这些结果一开始无一例外都被相信了，而最终也无一例外都是通过重新运行形态不同的检查才被发现的。**

这个修复办法在实验实践中古老得不能再古老：**在把仪器用于你不知道答案的案例之前，先用一个答案已知的案例运行它。** 想用 `grep` 查找一个你预期不存在的字符串？先用完全相同的命令形式，查找一个你确定存在的字符串——如果这样也返回 0，那么出问题的是命令，不是文件。只需多写一行，就能把“我检查过了”变成“我用经过校准的仪器检查过了”。

     有两种具体形式值得记住，因为上文都出现过，而且两者都会*静默地*失败：没有 `-L` 时，`find` 不会跟随符号链接（而 skill 的安装经常是指向源代码仓库的符号链接）；`--exclude-dir` 会在整个目录树中按 basename 匹配，而不只是匹配你原本想到的那个路径。

     **而这条规则还有后半部分，只有当检查内容要随产物一起发布时才会产生影响：要针对*标准*实现进行校准，而不是针对你机器上的实现。** 上面的仪器规则保证*你的*结论真实可靠；这一点保证*读者*能够正常工作。写入 skill 的工具行为声明——某个标志、递归模式、某个“跟随符号链接”的选项——会在你从未见过其二进制文件的机器上执行，而两端的差异都是静默的：它在你测试时有效，却在他们那里悄悄什么也不做。有两种机制会导致这种情况，而且从会话内部都无法看出来：**同一个命令名解析到不同的程序**（shell 别名或函数遮蔽了二进制文件——注意，`\tool` 只能绕过*别名*，因此 `command tool` 或绝对路径才是唯一确定的形式），以及**同一个程序在不同实现之间行为不同**（BSD 与 GNU，或替代实现之间）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是将其写入 skill，作为解决符号链接陷阱的办法，并发布到一个拥有 1200 颗星的公共仓库中——他们的 `grep` 实际上是由 shell 函数提供的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 中，同样的 `-R` 什么也匹配不到（它需要 `-RS`），因此对大多数读者而言，指定的修复会静默失败，而这恰恰发生在警告验证器会静默失败的章节中。

     所以：**在工具行为断言进入已发布的产物之前，要针对标准二进制文件重新运行它**（`/usr/bin/<tool>`），而不是使用 shell 交给你的那个。如果它经不起这一检验，就不要写入这个标志——**优先采用与实现无关的表述**：自行解析路径（`readlink -f`），不要押注于某个递归标志；在脚本中进行子字符串测试，而不是进行面向行的匹配；描述你需要的*行为*，而不是描述你碰巧知道的选项。只在你的环境中有效的指令比没有指令更糟糕，因为读者无法发现它其实什么也没做。

   - **采用成熟的清单实践已经确定的做法。** 判断一份清单应当属于 **READ-DO**（边读边执行——适用于低频或不熟悉的流程），还是 **DO-CONFIRM**（凭经验操作，然后在定义好的**暂停点**停下来确认——适用于时间压力下的有经验操作人员），并将其锚定在一个真实的暂停点，而不是“工作流中的某处”。只保留**关键项**——既关键、又经常在压力下被遗漏的项目，大约五到九项；超出这一范围的内容都会削弱执行力（[Gawande，《清单革命》](https://www.shortform.com/blog/types-of-checklists/)）。并且优先采用 Shingo 所说的**控制**，而不是**警告**（[poka-yoke](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，会输给完成任务的冲动；而阻止进度或强制生成产物的步骤完全不需要警觉性。在 skill 只能发出警告的情况下，至少要把警告放在作出决策的位置——**写在执行上下文从不打开的参考资料中的规则，在实践中就不算规则。**

另一方面，他们可能已经有了该 skill 的草稿。在这种情况下，你可以直接进入循环中的评估/迭代部分。

当然，你应当始终保持灵活；如果用户说“我不需要运行一堆评估，和我一起凭感觉来就行”，那你也可以照做。

然后，在 skill 完成之后（不过再次强调，顺序是灵活的），你还可以运行 skill 描述改进器。我们为此准备了一个完整的独立脚本，用来优化 skill 的触发。

## 首先：共存检查（官方 skill-creator 插件）

在进行任何操作之前，先快速检查一次（常见情况下无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：** 什么都不做——不要安装任何东西，也不要向用户提及本节内容。继续进行当前交互。
- **存在：** 官方插件中的 skill-creator 与此版本现在会以几乎相同的描述出现在 skill 列表中，因此后续会话可能会在两者之间随机路由。用一到两句话告诉用户这一点，然后提供以下选项（绝不要未经用户同意就执行）：
  1. **推荐** —— 运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的自检 SessionStart hook 复制到用户的 Claude 配置中，并将其注册到 `settings.json`（同时创建备份），这样今后的每个会话都会确定性地将 skill 相关工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；官方插件在按名称请求时仍可完全使用。在未安装官方插件的机器上，安装程序会拒绝安装任何内容，因此绝不会留下无用的 hook。
  2. 备选方案——`claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 恢复），这样会将官方条目完全移出 skill 列表，从而消除歧义。

如果 hook 已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有步骤。

对于用户创建的 skill，也可以使用同样的机制：当他们的 skill 有意与某个已安装的 skill 重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一套工具包——参见 Prior Art Research 下的“共存与优先级”（"Coexistence & Precedence"）以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

- “evaluation”和“benchmark”属于边界情况，但可以使用

### 使用 AskUserQuestion（重要——请阅读）

**在每个决策点都积极使用 AskUserQuestion。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最大用户体验改进——用户可能正在多个窗口之间切换，而且可能已经有 20 分钟没看这段对话了。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明 skill 名称、当前阶段，以及刚刚发生了什么（1-2 句话）。用户可能已经切换到其他上下文。
2. **简化说明**：用通俗易懂的语言解释这个决策。不使用函数名或内部术语。说明它会“做什么”，而不是它“叫什么”。
3. **给出建议**：先给出你的建议，并用一句话说明原因。如果选项涉及工作量，同时展示两种时间尺度：`(人类：约 X 分钟 / Claude：约 Y 分钟)`。
4. **列出选项**：提供 2-4 个具体的、带字母标记的选项。每个选项都应是明确的行动，而不是抽象概念。

**规则：**
- 每个问题只涉及一个决策——绝不要将无关的选择合并到同一个问题中
- 提供退出选项（AskUserQuestion 中始终隐含有“其他”选项）
- 接受用户的选择——可以提醒其中的权衡，但绝不能拒绝继续执行
- 如果答案显而易见且不存在权衡，则跳过提问（直接说明你将采取的做法）
- **如果问题超时且没有得到回答（用户暂时离开键盘），既不要停滞不前，也不要擅自推进涉及偏好或范围的决策。** 先完成不产生副作用的准备工作——编辑前快照、清单盘点、评估案例收集、只读审计/健康检查——并等用户回来后再处理判断性决策（重构方向、删除哪些内容、是否继续）。然后明确说明你完成了哪些工作，以及哪些事项正在等待用户决定。

## 创建 skill

### 捕获意图

首先了解用户的意图。当前对话中可能已经包含了用户想要捕获的工作流（例如，他们说“把这个变成一个 skill”）。如果是这样，先从当前对话中提取答案——使用过的工具、步骤顺序、用户做出的修正、观察到的输入/输出格式。用户可能需要补充缺失信息，并应在进入下一步之前进行确认。

**来源清单——起草之前始终执行，并明确同意边界。** 盘点当前对话，以及与之有重叠的现有文档/skills（参见下文的“既有成果调研”）。更早的本地会话 JSONL 文件属于单独的私有来源：除非用户明确要求挖掘历史记录，或在你解释将读取哪些内容后明确批准该来源，否则不要打开或解析它们。如果用户批准了，则通过对话挖掘工作流中的脱敏提取，仅纳入相关的过往会话；绝不要将原始会话记录加载到你自己的上下文中。如果用户未批准，则继续使用当前对话和现有项目来源，不要把缺少历史记录视为阻碍。

在挖掘对话（或会话记录）时，要同时盘点**两类资产——它们会落在不同的位置**。*知识*——端点、参数、陷阱、决策规则——应成为 SKILL.md 指南或 `references/` 中的内容。*会话中必须编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——是 `scripts/` 的候选内容：如果本次会话编写了它，那么下一次调用时就必须重新编写；因此，应将其参数化、完成清理，并打包进 skill。之前的一次提炼生成了经过润色的文字，却遗漏了可复用的辅助工具；其中的普遍经验是，要同时关注知识→references 和代码→scripts 这两条路径。

当源材料是*过往*会话记录（Claude Code projects directory 下的 JSONL 文件），而不是当前实时对话时，进入会话挖掘工作流。不要在主上下文中打开原始会话记录，也不要将原始路径/内容交给子代理。在任何代理看到内容之前，必须先完成确定性的 manifest → discover → redact → chunk 序列；只有经过 redact 的分块才能进入最小角色/分片方案，并且必须在预算门控下声明确切的单元数量和并发上限。

**首先，在回答下面的问题之前，先确定这是哪个方向（DIRECTION）。** 请求可能属于几种*相反*的事情：构建一个新 skill / 编辑一个现有 skill / 优化 skill-creator 本身 / 或者根本不是 skill，而是一次性任务。猜错方向会浪费整个会话——为“新 skill”所做的研究，与为“优化元工具”所做的研究完全不同。当措辞含糊时（例如，用户说“帮我做一个 skill”，但指向的是 skill-creator 自身的路径），在这里提出一个 AskUserQuestion 只需 30 秒。下面的包装器 skill 分支是其中一个特殊情况；方向检查本身则适用于一般情况。

`Use skill-creator to optimize <existing-skill>` 意味着采用正常的现有 skill 更新路径。它**不**授权挖掘会话历史、进行大范围重写、执行 Tier 3 分类或开展多代理评估。先检查实际提议的变更；只有当这些变更确实引入了某种失败面时，才升级处理。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应该设置测试用例来验证这个 skill 是否有效？对于具有客观可验证输出的 skill（文件转换、数据提取、代码生成、固定工作流步骤），测试用例很有帮助。对于具有主观输出的 skill（写作风格、艺术、经过品味校准的报告），通常无法使用断言——但“没有断言”不等于“没有验证”。它们的验证路径按成本从低到高依次为：
   - **历史任务重放**：重新运行一个 skill 过去处理过的真实提示词，对比新旧 skill 的输出，并根据具体发生变化的规则进行比较（“新输出是否真的遵循了这次更新引入的 token / 标题语法？”）。成本低，而且能发现“规则虽然写了，但没有任何内容读取它”。
   - **以生产作为评估**：承认真正的测试是用户下一次实际使用——然后明确这个闭环：之后用户的每次纠正都是要纳入反馈的事件（skill 自身的“迭代/活文档”部分），每次认可都是语料库材料。一个发布时没有这种回写习惯的品味型 skill 不会进步；而拥有这种习惯的 skill 无需运行正式评估也会逐渐收敛。**而当 skill 的输出是持续运行的东西——例如防护机制、监控器、定时任务或 hook——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。**用户纠正需要用户注意到问题并愿意反馈；而已部署的机制会主动报告自身情况，通常一天之内就会产生反馈。误报是这种反馈最尖锐的形式，因为它证明你写下的某条规则是错误的，而这是反复重读也无法揭示的。把第一次误报当作一次已安排的评估结果，而不是烦恼：在认定机制行为异常之前先检查它，因为更可能的结论是，*指令*写得过于绝对。（真实案例：某个 skill 规定了一项 fail-loud 检查，已部署的检查在一夜之间针对一个完全正常的情况触发了一次；修复方式是纠正 skill 中那句过于绝对的表述——没有人提出投诉，但遥测数据发现了问题。）
   - **渲染 + 人工审查**：适用于视觉输出（使用 skill 自身的视觉 QA 门控），绝不要用假装能够衡量美观程度的 grep 断言。**而且，用来验证的渲染器必须与交付物实际使用的渲染引擎相同**——无论什么预览器碰巧已安装，都不能替代目标应用。布局引擎不同于目标应用的缩略图生成器，会悄无声息地*隐藏*你正在寻找的确切缺陷；在错误的引擎上得到绿色验证，比完全不验证更糟，因为它会制造虚假的信心。真实案例（2026-07）：一个 `.docx` 通过 macOS Quick Look 缩略图进行了“视觉验证”，但 Quick Look 不会复现两端对齐文本的拉伸效果；用户打开文档后，Word 立即显示信息块被严重撑开。修复方式是安装兼容 Word 的引擎（LibreOffice），转换为 PDF，逐页栅格化，然后逐页阅读。引擎必须匹配，否则这种验证就是演戏。**这同样适用于渲染器之外的所有验证工具**——解析器、linter、验证器：它必须与生产环境共享同一实现，否则它显示绿色就毫无意义。另一个同类案例是：一位作者试图捕获一种会破坏最终文档的标记模式，却在源代码阶段使用了与生产工具链不同的 markdown 实现进行检查——该实现将三个已知有问题的输入全部解析为完全正常，因此任何基于它构建的预检查都会悄无声息地放过所有问题。诚实的结论是，这种特定缺陷只有在生产工具运行之后才能检测到，检查应该放在那里。**当没有任何可用工具与生产实现相同时，要说明该检查无法在那个阶段完成——不要构建一个只能产生虚假绿色结果的检查。**
   根据 skill 的类型提出合适的默认方案，但让用户自行决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认 skill 类型和测试策略：

```
正在创建 skill "[name]" — 目前我的理解如下：
- 用途：[1 句话概述]
- 触发条件：[关键短语]
- 输出：[格式]

建议：[Objective/Subjective/Hybrid] skill → [建议的测试方法]

选项：
A) 客观输出（文件、代码、数据）——设置自动化测试用例（如果输出可验证，推荐此选项）
B) 主观输出（写作、设计）——仅进行定性人工审查
C) 混合型——对结构进行自动化检查，由人工审查质量
D) 暂时跳过测试——先构建 skill，再凭感觉迭代
```

这一前置分类会驱动后续的整个评估策略。在这里做出正确判断，可以避免之后浪费精力。

### extend-vs-create 检查——在任何专门分支之前运行

下面的三个专门工作流都以“**不要**继续阅读以下部分”结尾，而 *Prior Art Research* 恰好位于它们之后。这个顺序是排版上的顺序，不是执行顺序。extend-vs-create 判断适用于每个分支，跳过它正是导致会话交付一个与已安装 skill 重复的 skill 的原因。

因此，在进入 wrapper-skill / conversation-mining / artifact-corpus 之前，先回答一个问题：**是否已经存在一个 skill，该能力本应归属于它？**

**发现根目录，不要凭记忆回想。** 手动维护的安装位置列表正是最容易过时的产物，而你忘记的那个根目录，往往就是最后造成问题的地方。

**搜索文件，而不是搜索名为 `skills` 的目录。** Skill 目录以 *skill* 命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、市场克隆仓库和插件缓存中根本不会包含名为 `skills` 的目录——搜索这个名称会悄无声息地跳过它们，却看起来像是在正常工作。每个 skill 都有一个 `SKILL.md`；这是与目录布局无关的定位依据。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，并且仍会返回比你需要的更多结果；请使用与该能力相关的具体术语进一步缩小范围，而不是使用通用术语（`chart` 会匹配所有内容，而 `stacked bar` 不会）。

这涵盖的根目录——也是凭记忆列出的清单通常会漏掉的：技能源代码仓库（一个 `claude-code-skills` checkout 以及任何 `-pro` 同级仓库）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过 marketplace 安装的套件——源代码仓库中的任何内容都不会暗示它们存在于这些位置）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、按配置文件划分的配置目录（`~/.claude-profiles/<name>/`），以及——完全没有任何线索的一处——**每个项目自己的 `.claude/skills/`**。第 2 步让这成为你亲自验证过的结论，而不是从别人那里继承来的说法。

**每项目技能在结构上是不可见的。** 它们位于某个无关项目的工作树中，因此不会出现在任何 marketplace、全局技能列表或源代码仓库列表中；你在规划新技能时通常会打开的任何地方，都不会提到它们。真实案例（2026-07）：某个会话为一个领域构建了全局技能，检查了源代码仓库、全局目录和其他 agent 的目录，什么也没找到，于是完成交付。后来的一次对话历史搜索发现，某个项目级技能正好覆盖该领域，而且已经存在了一个月，位于某个项目的 `.claude/skills/` 中——其中包含新技能所缺少的八条规则，包括一条用户亲自规定的规则。除每项目目录外，所有根目录都检查过了，但这次扫描仍然极其肯定地报告“没有既有方案”。

**当重叠的技能确实是另一个无关项目中的项目级技能时该怎么做**——这正是那个故事把你带到的情形，也是下面三个要点没有涵盖的情况：你不能向一个根本没有对应套件的套件添加同级技能，而“扩展它”则意味着编辑无关项目的工作树。有效的做法是：**将其中的规则提取到你正在构建的技能中，然后在所有者同意后废弃项目本地技能**——它是在真实工作中编写的，因此应将其视为更成熟的来源，并朝着它进行协调。废弃他人的工作技能是所有者的决定，而不是你构建过程的副作用。

这句话遗漏了四件事，其中每一件都可能阻止你继续：

- **“朝着它进行协调”是可反驳的推定，而不是规则。** 有两种标准的退出方式：项目技能可能已经*过时*（规则是几个月前针对一个已经发生变化的系统编写的），也可能是*项目特定的*（规则只在该项目的约束下成立——将它们整体导入会使你的技能变得狭窄，而本文其他地方会告诉你不要这样做）。提取出的规则是另一位作者的记忆，因此**必须像纪律 #1 要求你对写入技能的任何内容所做的那样，重新验证每一条规则**。
- **“废弃”需要一个机制，而且第一步不是你下意识会采取的那一步。** 顺序如下：

  1. **先用 `find` 查找技能的*实体副本*，再 grep 其*引用*。** 一个技能通常会在同一个仓库中有多个副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会被加载，只是由同一工作树中的不同工具分别加载。Grep 回答的是“谁提到了它”；只有 `find` 才能回答“它有多少个副本”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放入 `--exclude-dir`**（它按 basename 匹配，因此会隐藏所有同名目录，包括你尚未找到的那个副本——参见纪律 #6 中的工具规则）。真实案例（2026-07）：一次废弃操作正是这样做的，修复了它找到的全部五处引用，却在 `.agents/skills/` 下留下了第二个完整副本——该副本受 git 跟踪、没有废弃标记，是一个缺少最新规则的过时快照——另一个工具仍会将其作为活动技能加载。
  2. **在删除任何内容之前，确认新位置确实能从旧位置所处的环境访问到**——你刚推送的 marketplace 技能，在 marketplace 更新并安装插件之前并没有真正安装；如果先废弃旧技能，就会出现两边都没有技能的窗口期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 不是可选项——插件缓存经常会符号链接到源代码仓库，而不带 `-L` 的 `find` 会报告文件不存在（参见纪律 #6 中的工具规则）。
  3. **然后** grep 引用并重新指向活动引用。区分**活动指令**（技能列表、交叉引用、告诉下一位 agent 应使用什么的交接文档）与**历史记录**（决策日志中写着“X 日期我们交付了这个”）——重写后者会破坏审计轨迹，只为修复一个它并不存在的问题。
  4. **然后**将每个实体替换为 `superseded by <skill>` 存根，而不是直接删除，并使每个副本的存根逐字节一致。**保留 YAML frontmatter**——缺少它的 `SKILL.md` 可能会加载失败，却不会提供有用的失败信息——但要重写 `description`，让存根声明自身已废弃，而不是继续宣传旧的触发条件；否则它会继续赢得它已经不再服务的路由。正文只需要包含：能力转移到了哪里，以及它为何转移的一行说明。
- **使用下面的所有权测试识别所有者**（这里同样适用：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍然会告诉你它属于谁）。当所有者就是你正在交谈的人时，“同意”只需要一个 `AskUserQuestion`。**当所有者无法联系时，只提取规则——不要废弃**（这会让两个技能都保持活动状态并争夺同一触发条件，其最终结果与对方拒绝废弃相同——参见下面的共存与优先级）。
- **如果所有者拒绝废弃它**，那么现在就有两个技能在争夺同一触发条件；这是下面的共存与优先级问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 那个项目技能不会匹配新技能标题的名称搜索；它匹配的是其正文中的领域术语。在候选根目录中搜索新技能将处理的*概念*。

如果存在重叠：

**决定适用哪条规则——这个技能属于谁？** 文件系统命中项本身不带所有权信息。读取市场的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在包含该技能的仓库中运行 `git remote -v`；`~/.claude/plugins/marketplaces/` 下的命中项完全可能只是你自己的市场被安装回了自己的机器。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同样的问题。

探查结果有两种情况会出错或无法回答，因此在相信结果之前要检查它们：**fork** 会显示你自己的远程仓库，但其中的内容可能属于他人——应将其视为第三方，因为他们上游的改进仍然无法传递给你。而当**既没有 marketplace.json，也没有远程仓库**时（本地专用项目、手动复制到全局技能目录中的技能），探查结果是无声的，而不是否定性的：**应询问所有者，而不是猜测**。

- **重叠的是第三方技能**（市场套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*薄增量*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本——并使用**带命名空间的名称引用它**。把别人的引擎克隆进自己的套件是代价高昂的错误：他们的升级将无法继续传递给你，而两份副本会在无声中逐渐偏离。
- **重叠的是你自己的技能**：扩展它，或在其现有套件中添加一个兄弟技能。一个争夺相同触发条件的独立技能对任何人都没有帮助。**例外：**如果它位于*不相关项目*的工作树中，则以上两种方式都不适用——参见上面的项目级情况。
- **某个相关技能已经指向你正在填补的空白**（例如其描述写着“对于 X，请使用 Y”）：构建完成后要闭环——更新该指向，否则你就留下了一个悬空引用。

只有在没有任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**一次真实的 2026-07 会话花了一天时间让第三方 docx 引擎生成正确的中文商务文档，随后转向了包装技能分支——而该分支直接跳过了 Prior Art Research。它当时准备发布的形态，是一个重新携带该引擎能力的新技能。正确的形态应当是一个**三层引用链**：第三方引擎保持不变 → 一个包含正确用法和经过验证的生成器脚本的薄增量技能 → 领域工作流技能调用该增量。用户不得不纠正两次才最终落地，第二次纠正更为明确：*“不要再复制一个额外的——在他们的技能之上写出正确用法，并引用他们的技能；这就是 skill-as-code 的含义。”*

### 验证深度路由器（在选择任何工作流之前运行）

在采取通用或专用工作流分支之前，先选择能够证伪变更后行为的**最低层级**。应根据具体变更及其失败面进行分类，而不是根据行数或请求用词：一条变更后的破坏性命令，其优先级可能高于大段的文字清理；而要求“优化”现有 skill，也可能只是一次有界修正。在选择层级之前，列出你实际打算变更的规则、契约、脚本、权限和输出。如果尚未明确这份清单，应先进行检查，并暂时保留分类；范围不确定并不能作为 Tier 3 的依据。

| Tier | 适用情形 | 必需证据 | 默认不添加 |
|---|---|---|---|
| **1 — 定向** | 这是一个现有 skill；没有新增或实质性变更任何能力、触发器族、工作流分支、输出契约、依赖、权限或外部写入行为；且编辑内容恰好属于以下之一：(a) 不改变行为的拼写/格式修改；(b) 事实性文档/配置修正，其真实性由直接权威来源决定；或 (c) 有界的实现修复，用于恢复一项明确的现有契约，**并且**修复后的行为由确定性回归检查覆盖。可能改变代理行为的澄清不属于 Tier 1 | 对以上三种情况都要运行 `quick_validate`、检查差异，并完成现有 skill 迁移门禁。然后仅使用相匹配的证据：(a) 精确回读/格式检查；(b) 权威事实及其范围窄化的检查；(c) 明确的现有契约及确定性回归。仅当触及纪律 #5 的规则/契约/数值阈值时，才添加一名新的审阅者 | 代理行为重放、成对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 抽样行为** | 这是一个现有 skill；变更会影响代理行为，但没有新增能力、触发器族、输出契约、脚本行为、依赖、权限或外部写入；并且通过 1–2 个具名示例及明确的验收标准，就能覆盖整个变更后的行为。对一条现有路由或证据选择规则进行的有界修正，即使改变了所选路径，也仍属于此层级 | 仅运行这 1–2 个具有代表性的 skill 内重放，以及范围窄化的确定性检查和纪律 #5 所要求的一次全新上下文审查 | 默认不添加基线、成对扇出、方差分析、基准测试、查看器或评估文件。对这些内容的明确请求应经过单独的证据预算门禁，且不会重新对变更进行分级 |
| **3 — 广泛 / 高风险** | 满足以下任一条件：任何新 skill；任何新增或实质性变更的能力；广泛的跨分支重写或方法论扩展；触发器/描述优化；新的工作流分支或实质性变更的输出契约、脚本能力、依赖或权限；高风险自动化或外部写入；或者变更后的行为本身涉及 3 个以上不同的提示词类别、重复试验或实质性不同的方法 | 先运行确定性门禁，然后仅添加针对已命名失败轴所需的证据。只有在单独的重型评估授权门禁通过后，才可使用下方完整的成对流水线；Tier 3 本身不会启动该流水线，并且同一门禁也可以授权在其他层级添加额外证据 | 不得仅根据 Tier 3 标签自动添加成对扇出、评分器、基准测试或查看器 |

#### 重型评估授权门槛——独立于层级分类

层级描述的是**风险和不确定性**；它并不授权消耗 token 或进行 agent 扇出。通过此门槛会改变获准采用的证据方案，而不会改变层级。只有在以下任一条件满足时，才可以运行通用的 paired baseline → grader → benchmark → viewer 流程：

- 用户明确要求 A/B、基线、基准测试、重复试验、viewer 或多 agent 评估；或
- 执行者能够列出至少三类不同的提示词、多个具有合理性的竞争结果，以及配对比较将改变的决策，然后获得用户明确选择加入的同意。

对于现有 skill 的优化，默认使用零个评估 agent：先运行确定性检查，如果行为仍然不确定，再运行至多一到两次 with-skill 重放。规范 #5 中的一个全新上下文审查者是发布门槛，并不代表可以创建审查者团队。关于 token/成本敏感性的指令会阻止重型流程，直到用户明确撤销该限制。

在启动超过一个研究、挖掘、评估或评分 agent 之前，应将**角色**与**执行单元**区分开来：

- 每个额外角色或审查者都必须负责一个独立的失败轴或输出。模板可用性绝不是增加另一个角色的理由。
- 必要的实验组和语料库分片可以共享一个轴：with-skill 组和 baseline 组需要隔离的上下文，而一个挖掘角色可能需要多个有边界的分块。在启动前，说明确切的单元总数、并发上限，以及合并它们为何会污染比较结果或超出分块预算。默认按串行方式运行；明确的 A/B/挖掘请求只授权这些必要单元，不授权额外角色。
- 对于执行者而非用户明确要求的扇出，应获得用户对该数量的选择加入同意。如果交互式提问工具不可用，或用户没有回答，则采取较轻量的证据路径；沉默不代表同意。

如果某个单元既不是独立的角色/输出，也不是必要的隔离实验组/分片，则不要启动它。

当较低层级暴露出尚未解决的行为或相互矛盾的证据时，应升级处理。用户请求取消或降级评估时，应立即停止已经启动的配对评估 agent、基线、评分器、聚合和 viewer 工作。如果风险分类仍然具有参考价值，则予以保留，但只报告实际运行过的证据以及尚未检查的轴；不要将未运行的重型套件描述为由该标签自动“要求”的内容。不要在规范 #5 的单个全新上下文审查者达到其规则/契约/数量阈值时取消它，也不要取消任何为防止破坏性影响或外部影响所必需的安全门槛。机械式的现有 skill 迁移审计、公共 skill 清理，以及任何特定领域的安全门槛，也都独立于此路由器。

### 专用工作流：第三方 CLI 工具的 Wrapper Skills

在确定采用通用的 skill 创建流程之前，先检查截至目前为止引导至此的会话是否实际上需要改用 **wrapper skill** 工作流。wrapper skill 是一种配套 skill，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或 skill 包——这些代码由他人编写，而用户刚刚花费一个会话让其在自己的机器上运行起来。

适用信号（任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`、处理官方安装程序。
- 会话中出现了真实、具体的错误消息，并且用户和 Claude 一起为这些错误找出了具体的修复方法（编辑文件、添加标志、绕过别名）。
- 用户说出类似“把这个整理成一个 skill”“把这个保存成一个包装器 skill”“这样其他人就不用再经历这一遍了”“把这次 session 做成一个 skill”的话。
- 用户明确提到某个第三方工具的名称，并希望其他 agent 或其他人能够使用它，而不必经历自己刚刚付出的学习成本。

不适用的信号（改用上面的通用工作流）：

- 用户想要为某个准备从头开始编写的内容创建 skill。
- 会话过程很顺利——没有值得记录的实际阻碍。
- skill 要包装的是用户拥有或控制的服务（这是用户自己的代码；应直接编辑源代码，而不是进行包装）。
- 这个“工具”实际上是一种不涉及安装任何二进制文件或软件包的方法论或工作流。

当包装器 skill 工作流适用时，保留上面选定的验证级别。创建包装器就是创建新的 skill，因此属于 Tier 3。**不要**继续阅读下面的通用编写部分；跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一种**回溯式提炼**工作流——其任务是从当前对话中挖掘安装流程、已修复的 bug 以及所做的设计决策，并将这些挖掘结果转化为一个完整、自包含的包装器 skill，使其他用户可以安装并从中受益，而无需重新经历整个调试会话。

包装器 skill 工作流拥有自己的架构契约、代码模板和 Tier 3 验证协议——它会替代不兼容的通用测试用例机制，因为其产物是用户的安装状态，而不是一个可以轻易断言的文件；这并不意味着降低工作级别。运行证据计划所选定的兼容通用步骤；通用的成对评估步骤仍需要严格评估授权门槛。记录专用协议替代了哪些机制。规范参考实现是 `ima-copilot` skill（位于 daymade/claude-code-skills 仓库根目录——这个 skill 移入套件后，这里一个裸的相对链接曾经失效过，正如下面的跨 skill 引用规则所警告的那样），它是对 Tencent IMA skill 的包装器，使用这一完全相同的工作流从真实会话中提炼而成。

### 专用工作流：从对话历史中丰富 Skill

在提交到通用 skill 创建流程之前，检查当前会话是否实际上是在要求将**过去的对话提炼成一个 skill**。当用户在多次 Claude Code / Codex 会话中一直调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，这一流程非常有用。

**必须明确说明来源意图。** 长时间进行中的对话、最近完成的调试任务，或 `use skill-creator to optimize <skill>`，都不构成打开本地历史记录的同意，也不是进入此工作流的理由。对于普通更新，直接使用当前对话。只有当用户明确要求挖掘/提炼较早的本地对话，或指出特定的过往会话作为源材料时，才进入对话挖掘流程。

适用信号（必须全部满足）：

- 用户明确将本地/过往对话历史作为输入，例如“挖掘我的聊天记录”“从之前的会话中丰富此 skill”，或“把以前的对话沉淀到 skill 里”。
- 源会话以及时间/范围边界已知或已确认。
- 目标输出是可复用的知识或代码资产，且无法仅从当前对话和现有 skill 包中表达出来。

不适用信号（改用上面的通用工作流）：

- 用户正在根据单个提示或想法创建全新的 skill。
- 用户要求优化现有 skill，但没有要求读取过往本地历史记录。
- 相关修正和证据已经存在于当前对话中。
- 用户想要为刚安装的第三方 CLI 工具封装一层（改用上面的 wrapper-skill 工作流）。
- 没有可供挖掘的本地对话历史，也没有可处理的对话导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件。
- 源材料是一批用户已认可的成品，而不是对话——改用下面的 artifact-corpus-distillation 工作流。

当适用对话挖掘工作流时，保留上面所选的验证层级。新建的挖掘型 skill 属于 Tier 3；只有在满足该层级能力边界的情况下，丰富现有 skill 才保持所选层级。**不要**继续阅读下面的通用编写章节；跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端地遵循该工作流，包括其验证协议。这是一个**回顾性提炼**工作流：发现获批的本地历史记录，对其进行脱敏和分区，仅运行语料库所支持的挖掘过程，并在验证后提升经过审阅的候选内容。

对话挖掘工作流拥有自己的架构契约、代理提示词、模板和验证协议。该协议实现了所选层级的专用机制；运行由证据计划选定的兼容通用步骤，将繁重的通用步骤置于授权门槛之后，并记录任何替代方案。它是将明确获准的对话历史转化为 skill 可复用知识库的规范方式。

### Specialized Workflow: Distill User Preferences from an Approved-Artifact Corpus

在提交通用流程之前，检查当前会话是否要求**从用户已认可的一批成品中提取其真实偏好**——已批准的 HTML 报告页面、生成的文档、设计稿。这是第三种提炼来源，与前面两种不同：材料是**产品，而不是对话**，输出是**可执行的品味**（明确的原则、量化的参数、词汇），而不是知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出已完成的成果，并说“这些都是我认可的样例” / “你来学到底什么是我想要的” / “从这些已批准的样例中提取我的偏好”。
- 某个品味校准 skill（报告生成器、文档样式设计器、演示文稿构建器）拥有不断增长的已批准样例库，而用户要求让该 skill 从中*学习*，而不只是为其建立索引。
- 用户抱怨之前的更新“只加了示例”——只是将样例编目，却没有改变 skill 的行为。

不适用信号：源材料是对话/修正，而不是获得认可的产品（请使用 conversation-mining）；样例并未得到用户亲自认可（认可是一道准入门槛——请先询问）。

适用时，保留上方选定的验证等级，然后跳转到 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新的基于语料库的 skill 属于 Tier 3；为现有 skill 增加实质性的新决策能力同样属于 Tier 3。专用协议会实现所选等级的语料库机制，不会降低该等级；运行证据计划所选的兼容通用步骤，将繁重的通用步骤置于其授权门槛之后，并记录任何替代方案。其核心纪律也适用于你向现有 skill 添加材料的任何时候：**编目 ≠ 提炼**——在语料库表中登记一个样例，并不会改变 skill 的下一次运行；对每一项新增内容都要问自己“*这是否改变了某条决策规则？*”，如果对所写入的所有内容答案都是否定的，就不要宣布提炼会话已完成（方法论案例 15）。该工作流的主线是：针对**所有**成果进行脚本提取的定量比较（每种模式至少达到 3 个成果的阈值，并核查所声称恒定项的例外列表）→ 以证据锚点为基础的分层归纳 → 写入决策规则层（区分不变量与依赖语域的变量）→ 独立的完整性审计（长期纪律 #5）→ 回归审计。

### 先例研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策、竞争优势——正是 skill 有价值的原因。任何公开仓库都无法提供这些内容。但用户也不应浪费时间重复发明基础设施（API 客户端、身份验证流程、速率限制），因为已有成熟工具可供使用。先例研究的目的是为基础设施层寻找可复用的构建模块，从而让 skill 专注于编码用户独有的方法论。

**两个轴，不要混为一谈。** 本节为*基础设施*层寻找来源（可复用的工具 / MCP / 库 / 现有 skill）。*方法论*层自身有两个输入：用户的私有优势（只有用户拥有，无法检索）**以及该领域已经确立的最佳实践 / 科学知识，你应根据长期纪律 #3 默认将其检索到上下文中。**找到合适的工具，并不能免除第二项工作——一个采用了制图库，却从未吸收 Cleveland/Bertin 理论的可视化 skill，其能力上限仍然只是你的预训练水平。两者都要做。

**按以下顺序搜索这些渠道。** 默认进行内联研究。只有在上文的重型评估/代理预算门槛确认确实存在相互独立的未知项之后，才使用子代理；公共来源渠道不是默认的并行搜索组合。

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **实时对话或明确批准的历史记录** | 用户已验证的工作流、经过验证的 API 模式、调试过程中做出的更正 | 直接使用当前对话。只有在通过上文的明确来源门槛之后，才搜索更早的本地历史记录；然后使用经过脱敏的对话挖掘路径，而不是临时使用 grep |
| 2 | **本地文档与 SOP** | 用户的私有方法论、运行手册、现有技能 | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区技能 | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 针对同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或 `WebFetch` 文档 URL |
| 8 | **npm / PyPI** | SDK 或 CLI 包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己的已验证模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终优先——公共工具是构建模块，而不是替代品。在竞争性领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**倾向于合并/扩展，而不是新建，并且要扫描每一个技能根目录——不要只扫描 `~/.claude`。** 当渠道 1-3 发现了与请求领域重叠的现有技能时，通常正确的做法是扩展或合并到其中——**但如果它位于无关项目的工作树中，则方向相反：应当从中提取内容，加入你正在构建的技能，而不是合并到其中**（参见上文扩展与新建检查中的项目级案例）（某个真正的“新建技能”任务最终变成了“将现有提取器作为新归档器的提取阶段”），而不是发布一个争夺相同触发条件的并行技能——两个重叠的技能会争抢触发，并让用户感到困惑。搜索时，**应当发现安装根目录，而不是凭记忆列出目录**——使用 `SKILL.md` 扫描及扩展与新建部分中的覆盖范围自检（搜索名为 `skills` 的目录会漏掉源代码仓库、市场克隆和插件缓存，因为它们的技能目录以技能名称命名）。运行覆盖范围检查，不要只相信这句话：**每个项目自己的 `.claude/skills/`** 是凭记忆列出的目录中最容易漏掉的根目录，因为项目外没有任何内容会引用它。用户已经安装在*任意位置*的技能，是最有价值的先例；而项目本地技能往往最成熟：它是在实际工作中编写的。

**如果发现公共 MCP 服务器或 skill，请克隆并验证——不要相信 README：**

1. **阅读实际源代码**——许多项目的 README 写得很完善，但代码库却是空壳
2. **验证身份验证方式**——是否与 API 实际采用的身份验证方式一致？（X-Api-Key 请求头、Bearer 还是 OAuth——很多项目在这方面都弄错了）
3. **检查测试覆盖率**——零测试意味着这是原型，而不是生产级项目
4. **检查维护情况**——最后提交日期、未解决 issue 数量、对 bug 报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域锁定
6. **检查许可证**——MIT/Apache 没问题；GPL/SSPL 可能与专有用途冲突
7. **检查依赖规模**——庞大的依赖树会带来冲突和安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 已处理基础设施 | **采用它，在其之上构建**——安装 MCP，然后将 skill 构建为工作流层，用于编码用户的方法论 |
| 存在部分 MCP 或 SDK | **扩展**——将其用于基础设施，并在 skill 中补齐缺口 |
| 公共 skill 覆盖相同领域 | **仅用于获取结构灵感**——竞争领域中的公共 skill 按定义都是通用的。用户的优势在于其私有 SOP |
| **存在提供你所构建内容的某项子能力的互补 skill** | **打包它**——将互补 skill 的自包含资源复制到你的包中，并将其连接起来。不要依赖用户预先安装它。参见下方的“互补 Skills” |
| 没有任何公共资源 | **从头构建**——在编写完整 skill 之前，先验证 API 访问模式（身份验证、端点、代理）是否可行 |
| 集成成本 > 构建成本 | **自行构建**——一个由你掌控、耗时 2 小时的定制实现，胜过一个集成摩擦大且存在上游风险的“成熟”工具 |
| 用户有意取代已安装的 skill（分支版本、强化版） | **附带 supersede kit 发布**——参见下方的“共存与优先级” |

#### 共存与优先级（有意重叠）

将内容合并到现有 skill 中，是处理重叠的默认方案（如上所述）。但当用户*有意*发布一个与已安装 skill 重叠的 skill——例如官方插件的分支版本或经过强化的内部版本——这两个条目会以相似的描述出现在 skill 列表中，而 Claude 会随机在它们之间进行路由。请按以下逐步升级的顺序解决：如果重叠是意外的，则重命名；添加描述中的决胜说明（“取代 X——当两者同时出现时，始终使用此项”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式 supersede kit 写入 skill——这是一个基于同意的 SessionStart 路由钩子，仅会安装在实际存在竞争者的机器上，拒绝在其他机器上安装，并且如果任一方消失则自行禁用。具体机制、决策表、SKILL.md 示例措辞和沙箱验证见：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此 skill 针对官方 skill-creator 插件使用同一 kit 进行 dogfood（参见顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄无声息地失去了对*已安装技能集合*的触发权。** 一个技能的领域（图像生成、PDF 处理、仪表板）通常已经有多个已安装技能，而新技能可能会失去对所有这些技能的自动路由。因此，**要尽早验证触发情况——内容写得好并不意味着构建就完成了。** 有了草稿后，通过 `claude -p` 发起几个真实的查询，并检查新技能是否确实**胜出**；如果没有，**明确指出它输给了哪个具体竞争者**（不同查询可能会输给不同技能）。然后要了解两点：(1) **在竞争拥挤的位置上，单靠正文不一定能胜出**——解决梯度为：重命名 → 描述中的决胜信息/SUPERSEDES → 手动调用 → SessionStart 路由钩子（这是结构性方案；会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的规范）；以及 (2) **修复方式取决于竞争者的作者**——竞争者是*第三方*的 → 接受手动调用或路由钩子；竞争者是*你自己的* → 将它们合并/整合为一个，不要让自己的两个技能争夺同一个触发条件。（完整的解决梯度位于 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要只是指引，不要独立扩展。）记录所选择的路径（例如添加一条“激活”说明，写明“手动调用，竞争者为第三方”），可以避免下一次会话重新争论这个问题。（方法论案例 13）

##### 互补技能（打包，而不是依赖）

当构建的技能涉及一个已有互补技能的领域时，有两种选择：

- **依赖它已被安装**：这很脆弱——用户可能没有安装它，或者安装的是不同版本。每一次依赖缺失导致的失败，追根溯源都来自这一选择。
- **将其打包**：将互补技能的自包含资源（脚本、模板、参考文档）复制到你自己的包中，并将它们连接起来，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将其打包进来。** 这对以下内容尤其重要：
- 状态栏/UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证/清理脚本
- 常见的数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要一个状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。与其依赖用户先运行 `statusline-generator`，配置文件设置技能不如将 `statusline.sh` 打包进来，并在 `claude-profiles-init` 期间将其连接到每个新配置文件中。这两个技能仍然各自具备独立用途，但包装技能可以独立运行。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装程序”。这会将依赖推给用户，并造成脆弱的安装顺序。应改为打包。

研究完成后，通过 **AskUserQuestion** 呈现研究结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如果无法确定，优先考虑采用成熟的基础设施来处理底层支撑，并在其上构建自定义的方法论层——价值就在这里。

### 访谈与研究

主动询问有关边界情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在这部分内容理清之前，不要开始编写测试提示词。

在研究有帮助时，检查可用的 MCP（搜索文档、查找类似技能、了解最佳实践）。默认情况下直接进行内联研究。只有针对明确且尚未解决的问题时才使用子代理，绝不要因为工具可用就自动进行并行扩散。准备好相关上下文，以减轻用户负担。

### 编写 SKILL.md

根据用户访谈结果，填写以下组件：

- **name**：技能标识符
- **description**：何时触发、技能执行什么操作。这是主要的触发机制——同时包含技能的功能以及使用技能的具体场景。所有“何时使用”的信息都应放在这里，而不是正文中。注意：目前 Claude 有“触发不足”的倾向——在技能有帮助时不使用它。为应对这一点，请让技能描述写得更“主动”一些。例如，与其写“如何构建一个简单、快速的仪表板来展示 Anthropic 的内部数据”，不如写成“如何构建一个简单、快速的仪表板来展示 Anthropic 的内部数据。当用户提到仪表板、数据可视化、内部指标，或想要展示任何类型的公司数据时，即使他们没有明确提出要制作‘仪表板’，也务必使用此技能。”

  **控制长度：description 有严格的 1024 字符上限，超过长度会导致验证失败。** 这与上述“主动”建议直接冲突——你添加的每个触发短语都会消耗覆盖范围预算，因此应在扩展之前而不是之后进行测量：使用 `len(description)`，而不是凭感觉判断。陷阱不在于第一版（通常距离上限还很远），而在于多年后的更新：为新覆盖的范围添加触发词后，成熟的描述往往只剩几十个字符的余量，此时**添加一个触发词就意味着删除另一个已有触发词来支付成本**。要有意识地进行这种权衡，并在提交信息中明确说明，因为悄无声息地删除触发短语会实实在在地缩小技能的触发范围，而直到它不再为某人触发之前，没有人会注意到。（实际遇到过这样的情况：一次更新为新覆盖的故障模式添加了触发词，使描述达到 1280 个字符，之后经过两轮压缩才降到 1003 个字符——代价是删除了三个原有触发短语；这本应是一个需要明确说明的决策，而不应是在与验证器反复较量时才发现。）必须删减时，优先删除那些仍可通过同义词或相邻短语触达其场景的短语，保留没有其他入口的短语，并记住，正文中的限定语（例如“在平台 X 和 Y 上”、括号内的枚举）通常比独立的触发短语更容易删掉——正文内容可以从主体重新推导，而触发短语无法重新推导。
- **compatibility**：必需的工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### Skill 编写指南

#### Skill 的组成

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML Frontmatter 参考

除 `description` 外，所有 frontmatter 字段都是可选的。在 `---` 标记之间使用以下字段配置 skill 行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必填 | 描述 |
|-------|----------|-------------|
| `name` | 否 | skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 推荐 | skill 的功能以及使用时机。Claude 使用此字段决定何时应用该 skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork` 可在 fork 的子代理上下文中运行。** 请参阅下方的“Inline 与 Fork：关键决策”——选择错误会导致 skill 无法正常运行。 |
| `agent` | 否 | 设置 `context: fork` 时使用的子代理类型。可选值为 `Explore`、`Plan`、`general-purpose`，或 `.claude/agents/` 中的自定义 agent。默认值为 `general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true` 以阻止 Claude 自动加载此 skill。适用于希望通过 `/name` 手动触发的工作流。默认值为 `false`。 |
| `user-invocable` | 否 | 设置为 `false` 以从 `/` 菜单中隐藏。适用于用户不应直接调用的后台知识。默认值为 `true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。**省略该字段后，skill 将拥有由用户权限设置控制的完整工具访问权限。设置该字段会不必要地限制 skill 的能力。 |
| `model` | 否 | 此 skill 激活时使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指示预期参数。例如：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此 skill 生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** skill 内容中的 `$ARGUMENTS` 会被用户在 skill 名称后提供的文本替换。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### Inline 与 Fork：关键决策

**这是设计 skill 时最重要的架构决策。**选择错误会悄无声息地破坏 skill 的核心能力。

**关键限制：子代理不能再生成其他子代理。**使用 `context: fork` 运行的 skill（作为子代理）**不能**：
- 使用 Task 工具生成并行探索代理
- 使用 Skill 工具调用其他 skill
- 编排任何多代理工作流

**决策指南：**

| 你的 skill 需要…… | 使用 | 原因 |
|------------------------|-----|-----|
| 编排并行 agents（Task 工具） | **Inline**（不使用 `context`） | 子代理无法生成子代理 |
| 调用其他 skills（Skill 工具） | **Inline**（不使用 `context`） | 子代理无法调用 skills |
| 运行 Bash 命令执行外部 CLI | **Inline**（不使用 `context`） | 主上下文拥有完整的工具访问权限 |
| 执行单一且聚焦的任务（研究、分析） | **Fork**（`context: fork`） | 隔离的上下文，执行环境清晰 |
| 提供参考知识（编码约定） | **Inline**（不使用 `context`） | 指南可以丰富主对话 |
| 被其他 skills 调用 | **Fork**（`context: fork`） | 必须作为子代理才能被生成 |

**编排器 skill 示例（必须使用 inline）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**专业 skill 示例（正确使用 fork）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**参考 skill 示例（inline，不执行任务）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的 Skill 设计（正交性）

Skills 应当是**正交的**：每个 skill 处理一个关注点，并通过组合协同工作。

**模式：编排器（inline）调用专业 skill（fork）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须是 inline（不使用 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，在隔离的子代理上下文中运行
3. 每个 skill 只有一个职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法论，而不是重复代码

##### 管道交接（顺序 Skill 链式调用）

除了编排器/专业 skill 组合之外，skills 通常还会形成**顺序管道**，其中一个 skill 的输出会成为下一个 skill 的输入。每个 skill 都应在完成工作后，主动建议合乎逻辑的下一步。

**模式：SKILL.md 末尾的“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**现实世界中的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion 由用户**主动选择**——绝不要未经询问就自动调用下一个 skill
2. 仅在输出能够自然地作为另一个 skill 的输入时才提出建议——不要强行建立关联
3. 包含一个“不了，谢谢”选项——用户可能不需要完整的流水线
4. 建议中应解释**为什么**下一步会有帮助（例如：“ASR 输出通常包含识别错误”）
5. 最多提供 1-2 条建议——选项过多会导致决策疲劳

**何时添加交接：**询问“这个 skill 的输出是否通常会成为另一个 skill 的输入？”如果是，则添加“下一步”部分。如果关联罕见或牵强，则不要添加。

**反模式：**串联没有自然数据流的 skill。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**绝不要为可以自动检测的能力添加手动标志。**不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测能力：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：**能力自动检测，用户决定范围。skill 应发现自己能做什么并据此行动，而不是要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | You can invoke | Claude can invoke | Subagents can use |
|-------------|----------------|-------------------|-------------------|
| (default) | Yes | Yes | No (runs inline) |
| `context: fork` | Yes | Yes | Yes |
| `disable-model-invocation: true` | Yes | No | No |
| `context: fork` + `disable-model-invocation: true` | Yes | No | Yes (when explicitly delegated) |

#### 渐进式披露

Skills 使用三级加载系统：
1. **元数据**（名称 + 描述）- 始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文** - skill 触发时即位于上下文中
3. **捆绑资源** - 按需加载（不限量，脚本可以在无需加载的情况下执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是由行数目标决定。没有填充内容的 600 行 skill，胜过省略关键知识、迫使模型猜测的 200 行 skill。如果 skill 变得很长，请问：“每个部分是否都发挥了应有的作用？”如果答案是肯定的，就保留它。如果某些部分只是凑字数，或解释了 Claude 已经知道的内容，就删减这些部分——而不是删减有用内容。当一个 skill 确实涵盖多个领域时，应按领域拆分为多个参考文件，而不是为了让主文件保持简短而人为压缩所有内容。
- 对于现有 skill，渐进式披露是一种迁移策略，而不是删除启发式规则。旧的运行时契约必须仍然可以从打包后的 bundle 中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或评审者记忆都不能替代运行时内容。
- 在 SKILL.md 中明确引用参考文件，并说明何时阅读这些文件
- 对于较大的参考文件（>300 行），请包含目录

**领域组织**：当一个 skill 支持多个领域/框架时，请按变体组织：
```text
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的 reference 文件。

#### 避免意外原则

这点不言自明，但 skill 不得包含恶意软件、漏洞利用代码，或任何可能危及系统安全的内容。如果对 skill 的内容进行描述，用户不应对其意图感到意外。不要迎合创建误导性 skill 的请求，也不要创建旨在协助未经授权的访问、数据窃取或其他恶意活动的 skill。诸如“扮演 XYZ”之类的角色扮演则没有问题。

#### 编写模式

指令中应优先使用祈使句。

**定义输出格式**——可以这样做：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——加入示例很有帮助。可以按如下方式进行格式化（但如果示例中使用了“Input”和“Output”，你可能会希望稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得构建到 skill 中的可用性模式**——以下四个结构元素反复将“能运行但令人困惑”的 skill 变成用户真正能够操作的 skill——它们是让高频使用的 skill 变得易用的具体增强措施，因此当 skill 具有多种模式、会运行命令或可以重复运行时，应优先考虑加入这些元素：
- **入口决策树**：如果 skill 有多种模式，请以简短的“用户说了 X → 使用模式 Y”映射开头，让模型能够正确路由，而不是自行猜测。
- **每条命令后的预期输出块**：紧跟在命令后展示“你应该看到什么”，这样模型（和用户）就能区分真正的成功与无提示的失败。
- **故障排除部分**：列出已知的失败模式及其修复方法——这是最有价值的部分，因为其他人将在你无法查看的机器上运行该 skill。
- **第 0 步幂等性检查**：如果重新运行可能会重复已完成的工作，请先进行成本低廉的“是否已经完成？”检查，再执行任何耗时操作。

### 写作风格

尽量向模型解释事物为何重要，而不是大量使用强硬、陈旧的 MUST。尝试进行心智理论推演，并让 skill 保持通用性，不要过度局限于具体示例。先写出草稿，然后以全新的视角审阅并改进它。

### 日期和版本引用

**保留事实性日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 skill 应写成“Suno v5.5 (March 2026)”，因为如果没有日期，未来的读者就无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应避免的是**基于日期的条件逻辑**（“如果早于 August 2025，则使用旧 API”）——日期一旦过去，这种逻辑就会失效，而且没人会更新它。

规则：
- **发布日期、“上次验证”日期**：保留它们。它们是参考时间点，不是有效期
- **定价、排名、法律状态**：包含这些信息，但标记为易变信息（“截至上次检查约为 ~$0.035/gen”），让读者知道需要重新验证
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠/弃用部分记录旧方法

#### 随附资源

##### 脚本（`scripts/`）

用于需要确定性可靠性的任务，或会被反复重写的可执行代码（Python/Bash 等）。

- **适合包含的情况**：同一段代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优点**：节省 Token、具有确定性，可在不加载到上下文的情况下执行
- **注意**：Claude 仍可能需要读取脚本，以便进行修补或针对环境进行调整
- **用户可修改的数据应存放在捆绑包之外**：如果脚本会累积用户数据（更正词典、学习到的偏好、缓存），请将其存放在稳定的相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其单独创建备份——绝不要存放在 skill 目录中。每次更新和套件迁移都会删除并重新创建 skill 安装目录，而相对于主目录的存储位置会原样保留。这正是一个不断积累词典的 skill 能够在完整套件迁移后实现用户数据零丢失的原因

##### 参考资料（`references/`）

文档和参考材料，按需加载到上下文中，用于为 Claude 的处理过程和思考提供信息。

- **适合包含的情况**：Claude 在工作时需要参考相关文档时
- **示例**：用于财务 schema 的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库 schema、API 文档、领域知识、公司政策、详细的工作流指南
- **优点**：保持 SKILL.md 简洁，仅在 Claude 判断需要时加载
- **最佳实践**：如果文件较大（>10k words），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存放在 SKILL.md 或 references 文件中，不要同时存放在两者中

##### 资源（`assets/`）

不 intended to be loaded into context，而是在 Claude 生成的输出中使用的文件。

- **适合包含的情况**：skill 需要在最终输出中使用相关文件时
- **示例**：用于品牌资源的 `assets/logo.png`，用于 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件架**：对于生成 artifact 的 skill，`assets` 下的 `components` 子文件夹用于存放用户批准的、逐字嵌入的片段；这些片段具有冻结的行为契约和注册表引用——请参阅第 4 步中的组件架检查

##### 隐私与路径引用

**在应用以下任何内容之前，先决定目标受众。**下面的所有内容描述的是 skill 面向陌生用户发布时会出现的问题。对于存放在作者自己的私有 repo 中的 skill，相同的“违规”通常正是其能够正常工作的原因——真实的绝对路径能让脚本直接运行，模板中的真实账户能避免下一次运行时重新填写。`quick_validate` 会自动检测这一点（它会询问 `gh` 包含该 skill 的 repo 是否为私有），并将可移植性/标识符相关发现降级为备注；当私有 skill 准备发布时，`--audience=public` 会强制执行严格检查。

**在私有 skill 中，这些发现由所有者决定，而不是由你决定。** 不要在未询问的情况下，将真实路径替换为占位符、改写硬编码凭据，或对示例进行“清理”——你会为了满足一条原本针对另一个发布目的而编写的规则，破坏一个可正常工作的工具。如果你认为某些内容应该更改，请说明你发现了什么，并让所有者决定。（设计先例是 npm 的 `"private": true`：一个已声明的发布目的，会改变工具强制执行的内容；之所以加入它，是因为人们总是不小心发布内容。）

**对于计划公开分发的 skill，这一点至关重要**——这些 skill 不得包含特定于用户或公司的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 skill 安装路径，如 `~/.claude/skills/`
- **允许**：skill bundle 内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外**（严格按“禁止”列表实现的验证器会将当前这个 skill 误判为不合格——对正常输入误报，比漏过问题更糟）：当发布者自己的名称/品牌是解决 supersede 平局或进行署名所必需时，可以使用；当段落讨论这些路径本身时，可以使用类似 `~/.claude/skills/` 的安装路径（这是教学材料，而非硬编码依赖）

**跨 skill 引用**：裸相对路径始终表示“位于当前 skill 自己的 bundle 内”——验证器和读者都会这样理解，因此，指向另一个 skill 文件的裸路径会验证失败，并误导读者。指向另一个 skill 时，应在正文中注明所有者（“marketplace-dev 的 cache-and-source-patterns reference”），并使用 skill 的命名空间名称调用 skill（`/suite-name:skill-name`，而不是裸的 `/skill-name`）。skill 在不同 suite 之间迁移时，裸跨引用会悄无声息地失效——一次 suite 迁移就导致两个清理阶段中出现了 21 个失效的跨引用。

##### 版本控制

**至关重要**：SKILL.md 中不应包含版本历史或版本号：

- **禁止**：在 SKILL.md 中添加版本章节（`## Version`、`## Changelog`）
- **正确位置**：skill 版本记录在 marketplace.json 的 `plugins[].version` 中
- **原因**：Marketplace 基础设施负责版本控制；SKILL.md 应包含不随时间变化的内容

#### Reference File Naming

文件名必须做到无需阅读内容即可自我说明。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**测试**：仅从文件名本身，能否理解文件的内容？

有两个例外：连字符命名和下划线命名同样合适（分隔符从来不是重点——重点是能够自我说明）；而命名的工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）已经由目录提供了具体性，因此重命名会破坏各工作流之间的并行结构。

### 完整评估测试用例（仅限单独授权的配对计划）

仅当重型评估授权门禁通过时，才进入本节。风险等级本身既不会授权也不会禁止使用此证据；明确的全流程请求不会重新界定底层变更。不要仅仅因为 SKILL.md 发生了变化就使用本节。应遵循上文声明的替代契约所规定的专用工作流。

编写 skill 草稿后，提出 2-3 个现实的测试提示词——即真实用户确实可能说出的内容。**对于作用于实时系统（运行中的服务、已登录的客户端、生产数据）的 skill，请为每个测试提示词明确副作用预算**——例如“仅执行只读探测并得出结论；不要执行下载或操作 UI。”在“只是测试”的名义下修改实时环境是真实操作，而不是测试。通过 **AskUserQuestion** 呈现这些测试：

```text
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——在运行进行期间的下一步中再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整架构请参阅 `references/eval_pipeline_schemas.md`（其中包括稍后添加的 `assertions` 字段）。

## 完整配对评估流程（仅限单独授权）

仅当重型评估授权门禁通过后，才运行本节。风险等级仍应根据变更所涉及的行为确定。以具有决策意义的阶段执行流程，并在不确定性或所请求的基准交付物得到解决后停止；不要预先启动下游评分器、聚合或查看器工作。用户取消或降低要求后，应立即停止重型流程。未经授权不得使用本流程；如果专用工作流明确替代了通用机制，也不得机械地添加这些通用机制；不得使用 `/skill-test` 或任何其他测试 skill。

将结果放入 `<skill-name>-workspace/`，使其与 skill 目录处于同级。在 workspace 中按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建全部目录——只需随着进展逐步创建目录。

### 步骤 1：运行获批的 with-skill / baseline 配对

对于每个获批的测试用例，在相同的 prompt 和副作用预算下，运行一个 with-skill 样本及其 baseline。这两个实验臂有意共享一个失败轴，但要求使用隔离的上下文；它们是必要的实验单元，而不是额外的审查者角色。启动前说明实验臂总数和并发上限。默认串行运行，绝不能超过授权的单元数量。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（使用相同的 prompt，但 baseline 取决于上下文）：
- **创建新 skill**：完全不使用 skill。使用相同的 prompt，不提供 skill path，将结果保存到 `without_skill/outputs/`。
- **改进现有 skill**：使用强制性现有 skill 回归门禁在首次编辑前捕获的旧版本。将 baseline 子代理指向该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，则停止并从 Git 重建权威 baseline 后再继续；绝不能将已编辑的树用作旧 baseline。**明确这项比较能够解决什么问题：**它只能衡量本轮的变化。如果你最希望验证的能力已经存在于编辑前快照中——例如某个 sibling session 可以在你开始前恰好提交该修复——那么 with/old A/B 对该能力没有任何判别力；在这种情况下，应选择更早的 ref 作为 baseline。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据每个 eval 测试的内容为其指定描述性名称，而不只是使用“eval-0”。同时使用该名称作为目录名。如果本次迭代使用了新的或修改后的 eval prompt，请为每个新的 eval 目录创建这些文件——不要假设它们会从之前的迭代中自动沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：运行进行期间起草断言

不要只是等待运行完成——可以利用这段时间开展有价值的工作。为每个测试用例起草定量断言，并向用户解释这些断言。如果 `evals/evals.json` 中已经存在断言，请检查它们并解释其验证内容。

好的断言应当能够客观验证，并具有描述性名称——在基准查看器中，它们应当清晰易懂，让人只需浏览结果就能立即明白每条断言检查的内容。**应针对意图编写断言，而不是针对字面上的工具路径**——例如“语音内容保留在答案中”，而不是“调用了获准的读取脚本”。如果某次运行通过其他获准路径达成了该意图（例如读取已经内嵌文字记录的归档），也应判定为通过；将其判定为字面路径失败会制造错误的负面结果，随后还会让你在错误的地方进行“修复”。主观型 skill（写作风格、设计质量）更适合进行定性评估——不要强行为需要人工判断的内容设置断言；其真正的验证路径（历史任务重放、带回写习惯的生产环境评估、渲染 + 人工审查）列在“Capture Intent”的问题 4 下。

一旦断言起草完成，就更新 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户解释他们将在查看器中看到什么——包括定性输出和定量基准测试。

### 步骤 3：随着运行完成，捕获计时数据

每当某个子代理任务完成时，你都会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们会通过任务通知传来，不会持久化到其他位置。每当收到通知时就立即处理，而不是试图批量处理。

### 步骤 4：评分、汇总并启动查看器

所有运行完成后：

1. **为每次运行评分** — 启动一个评分子代理（或直接评分），让它读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是凭目测判断——脚本更快、更可靠，并且可以在多次迭代中复用。**但客观的 grep/脚本断言也可能产生相反的结果**（相同词语但含义不同导致误命中、措辞差异导致漏检），因此**基准测试通过率是一个信号，而不是定论**：抽查每条断言实际匹配到的内容，并注意是否存在某次基线运行暴露出技能本身的事实错误（出现“等等，API 中确实有这些数据”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **汇总为基准测试** — 从技能创建器目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   该脚本会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及均值 +/- 标准差和差值。如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md`，了解查看器所需的确切架构。将每个 with_skill 版本放在对应的 baseline 版本之前。

3. **进行分析员检查** — 阅读基准测试数据，找出汇总统计数据可能隐藏的模式。参见 `agents/analyzer.md` 中的“Analyzing Benchmark Results”部分，了解需要关注的内容——例如无论是否使用技能都始终通过的断言（无区分度）、高方差评估（可能不稳定），以及时间/令牌的权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器自行失效**：进程仍在运行，但没有任何程序在监听 — 使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 检查（结果为空），或 curl 该 URL（失败）；这里“没有日志输出”不是可用的信号，因为上面的启动命令已将其重定向到 `/dev/null`。终止该进程，并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：**如果 `webbrowser.open()` 不可用，或者环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击 "Submit All Reviews" 时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录中，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **通过** **AskUserQuestion** **告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

"Outputs" 选项卡一次显示一个测试用例：
- **Prompt**：提供的任务
- **Output**：技能生成的文件，并在可能的情况下以内嵌方式呈现
- **Previous Output**（第 2 次及后续迭代）：折叠部分，显示上一次迭代的输出
- **Formal Grades**（如果运行了评分）：折叠部分，显示断言通过/失败情况
- **Feedback**：文本框，用户输入时自动保存
- **Previous Feedback**（第 2 次及后续迭代）：文本框下方显示用户上一次的评论

"Benchmark" 选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每个评估项的细分和分析人员的观察结果。

可以通过上一个/下一个按钮或箭头键进行导航。完成后，用户点击 "Submit All Reviews"，将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果没有问题。将改进重点放在用户提出了具体问题的测试用例上。

完成后，终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。根据证据计划进行改进：对于 Tier 1，使用权威事实和确定性检查；对于 Tier 2，重放 1–2 个已命名的行为；或者，当单独的重型评估门在任何层级授权使用时，采用经过用户审阅的成对结果。未经授权，不要将成对评估产物导入默认的 Tier 1/2 路径。

### 如何思考改进

1. **从反馈中进行泛化。** 这里发生的事情，从宏观上看，是我们正在尝试创建可以在大量提示中使用一百万次（也许真的能达到，甚至更多，谁知道呢）的技能。现在，你和用户只是反复迭代少数几个示例，因为这样推进更快。用户对这些示例了如指掌，也能快速评估新的输出。但如果你和用户共同开发的技能只适用于这些示例，那它就毫无用处。不要加入琐碎的过拟合式修改，也不要加入压制性很强的限制性 MUST；如果某个问题顽固存在，不妨尝试换用不同的比喻，或推荐不同的工作模式。尝试的成本相对较低，说不定就能找到很好的方案。

2. **保持提示精简，但不要删除契约。** 删除那些没有发挥作用的内容，但要将对现有技能的每次删减都视为潜在回归，直到新旧审计对其进行归类。将详细但可复用的行为移入直接链接的参考文档；不要只把它们留在评估、变更日志或你的记忆中。阅读完整记录，而不只是最终输出——如果技能导致了无益的工作，就简化指令并重新运行旧的能力用例，不要想当然地认为字数越少行为就越好。

3. **解释为什么。** 尽力解释要求模型执行每件事背后的 **原因**。如今的 LLM 已经很 *聪明*。它们具备良好的心智理论能力，在获得良好 harness 的情况下，可以超越死记硬背的指令，真正促成事情发生。即使用户的反馈简短或带有挫败感，也要努力真正理解任务，理解用户为什么写下他们写的内容、他们实际写下了什么，然后将这种理解传达进指令中。如果你发现自己开始用全大写书写 ALWAYS 或 NEVER，或者使用极其僵化的结构，这是一个黄色警告信号——如果可能，重新表述并解释其中的理由，让模型理解你所要求的事情为什么重要。这是一种更人性化、更强大、更有效的方法。

4. **寻找重复的工作——既要在评估记录中寻找，也要在提炼技能的对话中寻找。** 阅读测试运行的记录，观察各个子代理是否都独立编写了类似的辅助脚本，或是否都采用了相同的多步骤方法来处理某件事。如果 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈信号，说明技能应该捆绑该脚本。只需编写一次，将其放入 `scripts/`，并告诉技能使用它。这样可以避免每次未来调用都重新发明轮子。在提炼技能所依据的源对话中，也存在同样的信号——那次会话哪怕只编写过一次的代码，都是每次未来运行都必须重新编写的代码；不要等到评估运行证明重复出现才行动（跳过评估循环的技能永远不会获得这一证明——创建流程第 4 步中的 Scripts 检查点就是为这些情况设置的捕捉点）。

5. **逐字写回修正——同一会话，两个层级都要写。** 对于经过品味校准的 skill，用户的修正就是评测集，但前提是这些修正落在未来运行时会读取的位置。两个属性会让写回逐渐收敛：(a) **逐字记录修正**，不要改述——确切措辞携带了校准信号，而摘要会将其抹平（“绝对禁止这种东西”传达的是一条硬性边界；“用户偏好更少的跳转”则不是）。将这些措辞连同日期写入它们所修正的规则中。(b) **在修正发生的同一会话中、在两个层级都写回**——修复产物，同时修复 skill 的规则/引用/组件；只修复产物的修正对所有未来运行都不可见，而推迟到“以后”的修正通常永远不会落地。写回时，检查 skill 自身的文本是否*教导了*刚刚被禁止的反模式——修正往往会推翻现有指令，而保留旧建议就必然会导致问题再次出现（真实案例：一个决策页契约建议使用跳转式的“goto 锚点跳到所引用的图”；用户明确禁止了这种做法，因此写回时必须修改原句，而不能只在旁边新增一条规则）。当被修正的内容是交互片段时，写回的最后一步是将其提升到组件架——参见第 4 步中的 Component-shelf check。

这项任务非常重要（我们正努力在这里每年创造数十亿美元的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，认真斟酌。我建议先写一版修订稿，然后重新审视并加以改进。请尽最大努力设身处地理解用户想要什么、需要什么。

对于 Tier 1，直接应用有明确证据支持的修正；只有当证据确实留下了选择空间时才提问。对于 Tier 2 或 Tier 3，当用户反馈暴露出有意义的设计分歧时，通过 **AskUserQuestion** 提出改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (authorizes only the named extra evidence; risk tier still follows the changed behavior)
```

选择 B 或 C 可能会改变风险等级，因为这会改变实现范围；选择 D 则不会。每个选项只授权其中明确命名的范围/证据变更。除非其中明确命名且单独的 heavy-eval/fan-out gate 已通过，否则它不授权配套基线、评分器、基准测试、查看器或额外角色。

### 迭代循环

改进 skill 后：

1. 将改进应用到 skill
2. 重新运行默认层级的证据，以及任何单独授权的证据计划：
   - **层级 1 默认流程：**始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配的子类型证据 — (a) 精确回读/格式检查，(b) 权威事实及其狭义检查，或 (c) 明确的现有契约及确定性回归测试。除非单独授权了配对计划，否则不要创建迭代工作区。
   - **层级 2 默认流程：**仅重新运行相同的 1–2 个指定的带 skill 示例及狭义检查。除非单独授权了配对计划，否则不要添加基线、基准测试、查看器或评估工作区。
   - **在任意层级单独授权的通用配对运行：**将所有获批的测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 skill，基线始终是 `without_skill`；对于现有 skill，不可变的原始编辑前版本仍是每次迭代的保留基线。紧邻的上一迭代可以作为补充，但绝不能替代原始基线。
3. 在实质性规则、契约或数值发生变化后，执行纪律 #5。对于单独授权的通用配对运行，还要启动评估审查器，并使用 `--previous-workspace` 指向上一迭代；专用工作流使用其声明的审查机制。
4. 对于单独授权的通用配对运行，等待用户审查新的查看器结果；否则，除非仍存在真实的用户选择，否则根据默认层级的证据作出决定。
5. 阅读新的证据或反馈；如果它证伪了当前版本，则再次改进，并在相同层级重复。

用户请求的取消或降级在任务剩余期间持续有效，且不会改变其分类。除非用户明确重新授权该证据计划，否则不要重新启动配对评估、基线、评分器、聚合或查看器工作。

在每次**单独授权的通用配对**迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（看起来一切都很好）
- 你没有取得有意义的进展

## 高级：盲比较

当你希望对 skill 的两个版本进行更严格的比较时（例如，用户询问“新版本真的更好吗？”），可以使用盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。其基本思路是：将两个输出交给一个独立的智能体，但不告诉它哪个对应哪个版本，然后由它判断质量。接着分析获胜者胜出的原因。

这是可选步骤，需要使用子代理，大多数用户不需要它。人工审查循环通常已经足够。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用某项 skill 的主要机制。创建或改进 skill 后，主动提出优化 description，以提高触发准确性。

### 步骤 1：生成触发评估查询

创建 20 条评估查询，其中混合应触发和不应触发的查询。将其保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实，并且是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要使用抽象请求，而应使用具体、明确且包含足够细节的请求。例如，可以包含文件路径、用户工作或情境背景、列名和值、公司名称、URL 等。可以加入一些背景信息。有些查询可以使用小写、包含缩写或拼写错误，或者采用口语表达。长度要有所不同，并重点关注边界情况，而不是让查询过于一目了然（用户之后会有机会确认这些查询）。

不佳：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

较好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**的查询（8–10 条），要考虑覆盖范围。需要使用同一意图的不同表述——有些正式，有些口语化。包括用户没有明确说出 skill 名称或文件类型、但显然需要该 skill 的情况。加入一些不常见的使用场景，以及与另一个 skill 存在竞争但应由当前 skill 处理的情况。

对于**不应触发**的查询（8–10 条），最有价值的是临界相似案例——这些查询与该 skill 共享关键词或概念，但实际需要的是不同的处理方式。考虑相邻领域、表面上模糊但朴素的关键词匹配会触发而实际上不应触发的表述，以及查询涉及该 skill 能做的事情、但在特定上下文中更适合使用其他工具的情况。

需要避免的关键点：不要让不应触发的查询明显无关。将 `"Write a fibonacci function"` 作为 PDF skill 的负面测试过于简单，无法进行有效测试。负面案例应当确实具有迷惑性。

### 步骤 2：与用户审查

使用以下 HTML 模板向用户展示评估集：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目的 JSON 数组（不要在其周围加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → skill 的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → skill 当前的 description
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`），并打开该文件：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加或删除条目，然后点击 "Export Eval Set"
5. 文件会下载到 `~/Downloads/eval_set.json`——如果存在多个文件，请检查 Downloads 文件夹中的最新版本（例如 `eval_set (1).json`）

这一步很重要——不好的评估查询会导致不好的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期查看进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（即驱动当前会话的模型），这样触发测试才能匹配用户实际体验到的效果。

运行期间，定期查看输出，为用户更新当前进行到哪一轮以及分数表现。

此过程会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开 HTML 报告，显示每轮的结果，并返回包含 `best_description` 的 JSON——该描述根据测试分数而非训练分数选出，以避免过拟合。

**如果检测到完全没有触发，循环会在第 1 轮后自行中止——你不必手动捕获这种情况。** 这是 `run_loop.py` 中基于代码实现的保护机制，而不仅仅是建议；它会区分“第 1 轮中所有应该触发的查询都完全没有触发”这一情况的两种原因：

- `exit_reason: "infra_error: ..."` —— 某些查询执行时抛出了异常（`claude` CLI 不在 PATH 中、超时时间太短、网络中断），而不是干净地返回“未触发”。该检查会**首先**执行，并且只要错误计数非零就会触发，即使几十次运行中只有一次偶发失败也一样——无论多么罕见的崩溃，都比“什么都没触发”更具体、更容易采取行动，而修复方向是环境问题，而不是重写描述。消息中的比例（例如 `3/15`）表示严重程度：比例较高意味着“停止，修复环境”；比例较低，同时伴随大量干净的 0 触发运行，则意味着环境可能存在轻微偶发故障，且描述确实可能存在问题——两方面都要检查。无论哪种情况，都要检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` —— 只有在上一个分支排除了所有执行错误后才会检查这一项，因此这意味着每个应该触发的查询和不应该触发的查询都确实运行了，但仍然一次也没有触发（这正是通过零分母默认值实现的“precision=100%”实际代表的含义：不是“完美”，而是“没有可供相除的内容”）。该探针实际上没有测量到任何东西——在完全触碰描述之前，先去诊断竞争者冲突或低阈值领域（见下文）。

这两项检查**仅针对第 1 轮**，并且**仅在没有任何应该触发的查询触发时执行**——第 1 轮较弱但并非零触发（例如 1/9 次触发）是另一种可能恢复的情况，因此会有意继续迭代。`degenerate_harness` 还要求不应该触发的查询同样一次也没有触发：如果描述只是极性反转——漏掉了所有正例，却意外匹配了多个负例——那么探针已被证明能够工作，`improve_description` 也确实有可利用的梯度，因此保护机制不会中止这种情况（只会中止真正失效的探针）。它还要求任一侧都没有执行错误——一个抛出异常的不应该触发查询实际上并未运行，因此其“0 次触发”不能作为探针失效的证据；这种情况正是应归入 `infra_error` 的情况。无论哪种情况，程序都会立即中断并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因才是信号，表示不应将本次运行的这些数值解读为“这是一个好的描述”。（真实案例，2026-08：在没有预检查的情况下启动了完整的 5 轮循环；两个完整迭代——每轮都是完整的评估批次，耗时数分钟，并调用了几十个 `claude -p` 子进程——都返回了 precision=100%/recall=0%/相同分数，直到有人查看这些数值；每个应该触发和不应该触发的查询都一次也没有触发。仅凭第 1 轮就可以诊断出故障；第 2 轮及之后的迭代没有提供任何额外信息。）当任一退出原因触发时，HTML 报告也会显示横幅，因此浏览器视图会携带与 JSON/stderr 相同的信号，而不仅仅依赖这两个可见性较低的渠道。（该保护机制的早期草案只检查应该触发的查询是否触发；经过两轮独立审查——每一轮都使用一个全新的代理，第二轮检查第一轮的修复，而不是重复覆盖旧问题——构造出了极性反转的反例、基础设施问题与描述问题之间的歧义、负例侧错误遗漏的问题，以及期间发现的一个已有的 `--holdout 0` 报告崩溃问题；这些问题都已在发布前修复。）

这项防护措施无法覆盖一种情况：当使用 `--runs-per-query 1` 时（默认值为 3），对于一个本应触发、且实际触发率确实在 50% 左右的查询，仅凭随机性也很有可能读到 0/1，从而因噪声触发防护措施，而不是因为探针失效。默认的 `runs_per_query=3` 正是让“每个正向查询在每次重复运行中都为零”成为强信号的原因——如果你将其调低，这项防护措施的误报风险也会随之增加。

**在信任 `best_description` 之前，先对测试框架进行健全性检查——即使上面的两个防护措施都没有触发，它仍可能返回空洞的输出。** 这两项检查只能捕获第 1 次迭代中的*完全失败*；测试框架也可能在全部 5 次迭代中始终维持微弱但非零的信号，却从未触发任一项检查。如果在第 1 次迭代之后的每次迭代中，**召回率都保持接近 0%，且分数完全相同或几乎相同**，这就与防护措施无法排除的根本问题相同——所谓“获胜”的描述通常只是第 1 次迭代附近未发生变化的噪声。在应用任何 `best_description` 之前，先自行运行一个明显应该触发的查询，并确认召回率 > 0。跨迭代召回率持平意味着测试框架是一个隐藏变量（常见情况是：该 skill 输给了已安装的竞争 skill——见下文的 Coexistence）——不要应用它的“最佳”结果；应手动编写描述，并用真实探针验证。（方法论案例 12、14）召回率为 0 还有第二个根本原因，与输给竞争 skill 不同：该 skill 的任务领域属于*低阈值*领域——模型自己完成任务，完全不会查阅任何 skill——这在下面 *How skill triggering works* 的末尾有详细说明。在采取行动前要区分这两种情况，因为修复方式正好相反：竞争 skill 需要通过优先级/取代关系修复，而低阈值领域则需要完全放弃触发探针，改用生产即评估的方式。

**当你使用 `claude -p` 自行探测触发情况时，要收集运行过程中的所有 skill 调用，而不只是第一个——并记住，工具调用只是一个代理指标。** `UserPromptSubmit`/`SessionStart` hook 可能会在模型作出选择之前注入一个无关的 skill，因此“在第一次 Skill 调用时退出”的探针会错误地报告“未触发”。而且，“它是否调用了 Skill 工具”并不等同于“该 skill 的内容是否影响了输出”（模型可能读取了该 skill，却没有可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你针对错误的结论持续优化。

### skill 触发机制的工作方式

理解触发机制有助于设计更好的评估查询。Skills 会以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某个 skill。需要注意的重要一点是，Claude 只会针对自己无法轻松处理的任务查阅 skills——像“读取这个 PDF”这样简单的单步查询，即使描述完全匹配，也可能不会触发某个 skill，因为 Claude 可以使用基本工具直接处理这些任务。复杂、多步骤或专业化的查询，在描述匹配时通常能够可靠地触发 skills——但有一个系统性例外（低阈值任务领域），具体说明见本节末尾。

这意味着你的评估查询应当足够实质，Claude 才会确实从查阅 skill 中受益。像“read file X”这样的简单查询是不好的测试用例——无论描述质量如何，它们都不会触发 skill。

**但有些 skill 未能通过这一测试是有原因的：没有任何查询改写能够解决这一点，因为该 skill 的整体 *工作* 就是一项低门槛任务。** 上面的段落将问题归咎于查询（“写一个更实质的查询”）；而这里是正交的情况：阻碍触发的是 skill 的*领域*。如果某个 skill 的用途是完成某件 Claude 使用基本工具就会自行完成的事情——转换音频为 16 kHz、降采样、提取单个字段、批量重命名——那么即使查询写得非常完整（“将这个 48k 立体声 wav 降采样为用于 whisper 的 16k 单声道”，包含路径和所有细节），它也不会触发：模型会直接使用 `Bash`/`ffmpeg`，而不会查阅任何 skill。查询内容的实质性无法解决这一问题，因为“我可以自己完成这件事”的判断针对的是*任务*，而不是措辞。

在浪费一个优化循环之前先诊断这一点：通过 `claude -p` 运行一个真实的查询，并观察模型在整个运行过程中是否*曾经*查阅过该 skill（遵循上面的 ALL-skill-calls 规则），还是直接使用 `Bash` 自行完成任务。如果它从未查阅，那么触发探测从结构上就无法检测到这个 skill——无论你怎么写，recall 都会接近 0，而这个 0 衡量的是模型“我可以自己做”的反射，而不是你的描述。停止针对 `claude -p` 的 recall 进行调优，改用真实方式进行验证：production-as-eval（用户下一次真实的、*交互式*使用——无头 `-p` 比真实会话更偏向执行操作，并且系统性地低估触发率），再加上输出比较，即 skill 会生成可检查的产物。（在一个音频预处理 skill 上观察到过这一点：无头的 run_eval sweep 在*每个*查询上的读取 recall 都是 0——包括一个明显的“转录这段录音”查询；而手动执行 `claude -p` 探测显示，模型直接使用 `Bash` 查找并处理文件，整个运行中的 `Skill`=0。这个 0 衡量的是无头运行的操作偏差，而不是描述；只有在交互式使用中才能看到真正的信号。）

### 第 4 步：应用结果

从 JSON 输出中取得 `best_description`，并更新 skill 的 SKILL.md frontmatter。向用户展示修改前后内容，并报告分数。

## 关键：在源位置编辑 Skills

**绝不要先编辑已安装的 skill 副本。** 除非用户明确说明它们就是源代码，否则请将以下所有位置都视为已安装/运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装副本会导致修改：
- 缓存刷新时丢失
- 不会同步到源代码管理中
- 浪费工作，并需要手动重新合并

**始终确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，运行源位置检查，并说明哪个路径是源文件：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果可用技能列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假设该路径就是源文件。先定位由仓库支持的源文件，编辑并验证它；只有当用户需要立即在本地运行时，才同步已安装的副本。

**然后回答后续问题，以判断“同步已安装的副本”是否确实属于必要工作：运行时是否已经读取源文件？** 三种安装方式的行为不同，猜错了要么浪费一次同步，要么提交的编辑在用户下一次会话中根本不会生效：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **符号链接**到源代码树中 → 编辑内容*就是*运行时内容。不需要同步。
- **`source: directory` 的 Marketplace** 指向仓库 → 同样如此：它会直接读取工作树，因此版本提升只是为其他使用者记录，不是本地激活步骤。
- **任何缓存/复制的安装方式**（来自 git 的 marketplace、通过 `cp -r` 安装）→ 运行时使用的是独立副本，在新内容生效前确实需要运行官方更新命令。

**并且要根据内容验证激活状态，而不是根据版本字符串。** 注册表可能记录了磁盘上并不存在的路径或版本号——有一次会话读取到一个记录了*新*版本号的插件缓存目录，差点就报告更新已生效；但那个目录从未创建过，真正的运行时路径一直都是指向源文件的符号链接。权威检查方式是：在运行时文件中 grep 只有新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库中的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们发生冲突的地方：当你编辑技能 A 时，另一个会话可能会在你的工作下提交技能 B（甚至是技能 A 的较早一轮修改）。有一次真实会话在一小时内遇到了全部三种症状——`Write` 因文件在读取后发生变化而被拒绝，以及 HEAD 在任务期间两次移动（方法论案例 16）。问题不在于发生冲突；问题在于基线过时，或覆盖式写入悄悄混合了两个会话的工作。长期规则如下：

1. **只要任务开始时仓库是干净的，就应从 git ref 而不是工作树获取基线**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并将 `--baseline-origin git-ref:<sha>` 传给审计工具。从几分钟前的工作树快照得到的基线，可能对应一个已经不存在的工作树。**解压到一个新建且不存在的目录中。** 解压到已有目录时，`tar -x` 会静默覆盖同名文件，并保留归档中不包含的文件——这会形成一个混合快照，在解压时完全没有任何信号，之后 `compare` 会因其与该 ref 不匹配而拒绝。同样的陷阱也存在于另一个命令中：`mv <dir> <existing-dir>` 会嵌套移动，而不是替换；当 `mv` 被别名为 `mv -i` 时，如果目标已存在，重命名操作会打印一行提示，并默认不执行，但两种情况下退出状态都为 0（已通过实验验证）。
2. **在写入前重新读取**，包括写入被拒绝时，或任何一段时间过去之后：检查发生了哪些变化（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图整合到你的版本中——他们的编辑通常是有原因的——然后再写入。
3. **提交前检查 HEAD 以及当前所在的分支。** `git log --oneline -1` 可以捕获 SHA 是否发生移动：如果它自基线建立后发生了变化，请在 `verify` 之前针对新的 ref 重新运行回归 `compare`——审计工具本来也会拒绝过时的审查（“after skill changed”），但自行提前发现可以节省一轮操作。不过，另一个会话可能做出比推进 HEAD 更糟糕的事情：**它可能会在你不知情的情况下切换分支**，因为 checkout 的作用范围是整个工作树。真实发生过这样的顺序——执行 `checkout -b feat/x`，编辑了一段时间，同时另一个会话执行了 `checkout main` + `pull`；之后提交落在了 **main** 上，违反了仓库“永远不要直接提交到本地 main”的规则，而 feature 分支仍然指向旧基线。因此，提交前检查中除了 SHA，还要加入 `git branch --show-current`。如果这种情况已经发生，`git reflog` 是权威的重建依据（它会按顺序记录每一次 `checkout: moving from X to Y`），而修复方式——**前提是工作树干净**——是 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：两者都是只移动引用、不会触碰工作树的操作，因此不像 `reset --hard` 那样会破坏并行会话中未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要使用 `git add .`——另一个会话未提交的工作不能被一并带入。（这本来就是打包规则；在并发场景下更是关键。）
5. **每次会话结果只提升一次版本，而不是每轮编辑都提升一次**：同一会话在同一个技能上的连续多轮编辑应合并为一次版本提升——除非某个中间状态已经被使用（已提交并被用户或另一个会话拉取），此时每个已使用的状态都应拥有自己的版本。

## Skill 创建流程（分步）

创建或更新 skill 时，按顺序执行以下步骤。仅当某个步骤明确不适用时，才可跳过。

### 步骤 0：前置条件检查

开始任何 skill 工作之前，自动检测所有依赖项，并主动安装缺失的依赖项。在工作流中途才发现缺少工具（例如在打包时发现缺少 gitleaks，在验证时发现缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，能够自动安装的依赖项就自动安装，并向用户提供摘要清单。只有满足所有阻塞性依赖项后，才能继续执行。

关键阻塞项：Python 3、uv、PyYAML（验证/打包）和 gitleaks（安全扫描）。仅当单独授权的证据计划实际运行 agent evals 时，claude CLI 才是阻塞项。使用显式的 uv 依赖声明运行 Python 工具，例如从 skill-creator 根目录运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 依赖环境中已有的 site packages，可能找不到 PyYAML。

### 步骤 1：通过具体示例理解 Skill

仅当已经明确理解 skill 的使用模式时，才可跳过此步骤。

要创建有效的 skill，必须清楚理解该 skill 将如何通过具体示例使用。这种理解可以来自用户直接提供的示例，也可以来自经过用户反馈验证的生成示例。

例如，在构建 image-editor skill 时，相关问题包括：

- “image-editor skill 应支持哪些功能？编辑、旋转，还是其他功能？”
- “你能给出一些该 skill 的使用示例吗？”
- “用户说什么时应该触发该 skill？”

为避免让用户应接不暇，避免在一条消息中提出过多问题。

### 步骤 2：规划可复用的 Skill 内容

分析每个示例时：

1. 考虑如何从头开始执行该示例
2. 确定 Claude 应拥有的适当自由度
3. 确定哪些脚本、参考资料和资源有助于重复执行这些工作流

**使具体程度与任务风险相匹配：**
- **高自由度（文本指令）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，但允许合理变体
- **低自由度（精确脚本）**：操作脆弱，一致性至关重要

### 步骤 3：初始化 Skill

如果 skill 已经存在，则跳过此步骤。

从头创建新 skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个包含正确 frontmatter、资源目录和示例文件的模板 skill 目录。

### 步骤 4：编辑 Skill

开始编写之前，获取 Anthropic 的最佳实践文档（在上面的“Skill 创建最佳实践”中提供了链接）和方法论参考资料——即使你认为自己已经了解这些内容，也要执行此操作：文档会更新，训练数据版本会过时，而“我基本了解”恰恰是编辑者会跳过这一步并错过最新指导的状态。

编辑时，请记住，该 skill 是为另一个 Claude 实例创建的。重点关注那些对 Claude 有益且不明显的信息。

**现有 skill 迁移门禁 — 首次编辑前必须执行：**

1. 在编辑前捕获当前完整 bundle。对于非 Git 或 dirty 的源，使用该工具，以便快照携带可验证的 provenance manifest：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于干净且由 Git 跟踪的源，从所选 ref 构造目录：

   ```bash
   mkdir -p <workspace>/skill-before   # tar -C requires the target to already exist
   git -C <repo-containing-the-skill> archive <ref> <skill-dir-relative-to-repo-root> \
     | tar -x -C <workspace>/skill-before
   # lands at <workspace>/skill-before/<skill-dir>/SKILL.md — one level deeper than
   # the snapshot subcommand's output, because `git archive` preserves the path
   # prefix; --before in step 3 is <workspace>/skill-before/<skill-dir>, not
   # <workspace>/skill-before itself.
   ```

   包含 SKILL.md、references、scripts、assets、workflows 以及现有 evals，而不只是主提示词。绝不要复制已经编辑过的目录并将其标记为“before”。**使用一个之前没有解压过任何内容的目录**——重复使用一个已包含内容的目录时，`tar -x` 会静默覆盖同名文件，却会保留新归档中不存在的旧文件，从而生成一个混合快照；提取时不会提供任何信号（`compare` 只会在之后间接地通过 tree-hash mismatch 检测到这一点）。参见下方的“同一 skill repo 上的并发会话”，其中更完整地说明了这个陷阱，包括基于 `mv` 的变体。
2. 清点旧 skill 的 actor/jobs、trigger contexts、runtime contracts、commands/flags、failure and recovery cases、page/domain variants、bundled resources 以及 eval coverage。在进行结构重写前，为重要的旧 edge behavior 添加 preservation cases。
3. 编辑后，生成 old-vs-new review：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，将最后一个 flag 替换为 `--baseline-origin git-ref:<ref>`。该工具会将 ref 解析为不可变 commit，并根据该 tree 验证每个包含的文件及 executable bit。

   **重命名或移动 skill 目录本身**（而不仅仅是编辑其内容）会改变 `--after` 的路径；两种 baseline mode 都会使用该路径进行 identity 校验——默认情况下，`compare` 会拒绝此操作（认为 `--before`/`--after` 错配），并报错 `pre-edit snapshot source identity does not match the edited skill`。添加 `--renamed-from <old-path>`（即 `snapshot` 所指向的 `--source` 路径，或 `git-ref:` 对应的 skill 相对于 repo 根目录的旧路径），以显式声明此次重命名；随后 identity 校验会改为验证该路径，而 content/tree-hash 校验保持不变，因此实际不匹配的配对仍会失败。**将 `--renamed-from` 作为绝对路径传入。** 该命令接收的每个路径，如果以相对路径给出，都会相对于当前工作目录解析——而不是相对于 `--after`，也不是相对于彼此——并且 `--renamed-from` 通常指向一个已不存在的目录（该目录已经被重命名），因此不存在检查无法像对 `--before`/`--after` 那样捕获错误解析；它只会在更深层处以令人困惑的方式失败。这一点尤其容易影响 skill-creator 自身的编辑：上面的 `cd <skill-creator-path>` 进入的是 skill-creator 自己的 repo，而通常与被审计的 skill 所在的 repo *不同*，因此相对的 `--renamed-from` 会静默地相对于错误的 repo 解析。

4. 审查每个候选项。对每个候选项使用且仅使用一种处置方式，并记录具体证据/原因：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移到此技能之外时，必须提供所属目标、当前边界证据以及可追溯的用户批准。明确退役也必须引用/追溯用户的批准。关于已保留/已清理/已修复的声明必须指向一个真实存在的当前文件和行，并包含一段简短的 `contains` 引文，以便验证者在附近定位。文件级候选项必须使用当前文件指纹，并附带一项具名的语义审查，解释行为为何得以保留——仅凭指纹只能证明文件身份，不能证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本——`classify` 子命令会执行机械性工作（在目标文件中定位引文所在行、填写 evidence/semantic_review，并在找不到引文或原因过短时快速失败）。你仍然需要为每个候选项编写处置方式和原因；它只负责将这些内容录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

   其中，`dispositions.json` 将候选项索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（处置方式默认为
   `preserved_or_moved`）；文件级候选项只需要 destination + 一个至少 40 个字符的 reason——指纹会自动为你计算。**从目标文件中复制 needle（使用 Read/grep/sed），不要凭记忆输入它**——查找采用精确匹配，找不到引文时会快速失败；手动输入的 needle 实际上有两种失败方式：全角与半角标点（`：` 与 `:`）不一致，以及凭记忆改写近义字符（`也` 与 `都`）——这两种问题都会绕过自我审查，只有工具拒绝整个映射表时才会被发现（同一个映射表曾因这两个原因连续被拒绝两次）。
5. 验证已完成的审查。任何进一步的编辑都会使哈希对应的审查过时，因此当候选项发生变化时，请重新生成并重新分类。通过验证后会写入 `.skill-regression-reviewed`，这是一个与内容绑定的本地状态凭据。它有助于检测后续编辑，但有意不作为独立的打包授权依据；打包过程本身会再次验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时应呈现的结果（真实输出，因此可以识别静默失败）：

```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在待审核的候选项，并不表示工具失败；返回 2 表示调用/运行时失败。该工具能够证明内容被准确迁移且接口得到保留，但会有意拒绝根据模糊的词语重叠来推断语义等价性。诸如“检查权限被拒绝”这样的通用短语，不能悄无声息地替代“已登录但没有角色”这一精确契约。此外，还要检查标记为 `only_outside_runtime` 的候选项：如果运行时行为只存在于 eval、测试或不可达的参考内容中，那么它就不存在于正常调用路径中。

**每次编辑 SKILL.md 后立即验证 — 不要等到打包时（第 7 步）。** 该检查能够及早捕获的失败是真实存在的：用未加引号的 YAML 标量书写前置元数据描述时，在 Claude Code 的宽松解析器中可以正常解析，但会在严格解析器中出错（codex 曾针对一个已经发布数月的 skill 报告 `invalid YAML: mapping values are not allowed`）；而未加引号的描述中包含 ` #` 时甚至不会报错 — 它会静默截断其后的所有内容，因此触发关键词会消失，但每次扫描仍会显示为通过。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**将描述写成 YAML 块标量**（`description: >-` 后跟缩进段落），只要其中包含 `: ` 或 ` #`，或跨越多个句子，就应采用这种写法 — 这是上述事件发生后针对所有新建或编辑的描述所推荐的约定。

**更新现有 skill 时**：扫描每个现有引用和捆绑资源，查找对应的更新，然后通过上述迁移门禁。迁移契约时，SKILL.md 必须提供直接的运行时指引；eval 或变更日志不能替代它。

接下来的三项检查是**升级探测项，而不是无条件扩大范围**。如果执行其中任何一项会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖、权限或外部写入，请停止并重新归类为 Tier 3，然后再修改 skill。Tier 1 和 Tier 2 可以检查这些问题，但不会因此获得新的交付物。

**脚本检查**：在宣布编辑完成之前，询问：*源对话（或 eval 转录）编写了哪些代码 — 如果不将其固化，未来每次调用都会重新编写这些代码？* 当所选层级已经授权进行这项能力工作时，将其打包到 `scripts/` 中（进行参数化和清理），并修改文档以指向它。否则，将该信号记录为 Tier 3 提案，不要将其作为 Tier 1/2 的附带结果进行打包。分工如下：**脚本负责执行，文档负责理解** — 如果一个 skill 的方法只存在于散文式说明中，那么每次运行都会重新承担完整的编写成本。之所以将此检查放在编辑步骤中，正是因为跳过 eval 循环的路径（对话提炼、直接编辑）永远不会到达“改进 skill”中 eval 转录版本的这项检查。

**组件货架检查（针对 artifact-EMBEDDED 片段提出的同一个问题）**：Scripts 检查涵盖的是 *skill* 执行的代码；生成 artifact 的 skill（报告页面、演示文稿、文档）还会积累其*输出*所嵌入的片段——图像叠加组件、粘性导航、图表配置、CSS 代码块。如果连续生成的输出都各自手写相似片段，这就是同一种重复信号，只是指向了不同的货架。在添加 `components` 子文件夹或注册表引用之前，先应用上述升级规则；Tier 1/2 可以提出建议，但不得创建组件能力。获得 Tier 3 授权后，决定一个代码片段能否成为货架组件的，是围绕它建立的契约：(a) **逐字嵌入代码块**——将 BEGIN/END 标记之间的完整内容复制到 artifact 中，零依赖，从而让单文件 artifact 保持自包含；(b) **注册表条目**，说明交互契约（触发条件、按键绑定、关闭行为、边界情况）以及来源——它来自哪个已交付的 artifact、用户何时批准了它；(c) **准入门槛**——只有用户实际使用过并批准的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但外观漂亮的内容仍不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定属于契约，在不同运行之间不得漂移，而颜色和尺寸可以遵循 artifact 的风格；(e) **回写循环**——为某个 artifact 发明的片段，应在其获得批准的同一会话中晋升到货架。之所以这件事的重要性不止于节省 token，是因为手工重写的片段会*漂移*——每次重写都会细微改变按键绑定、关闭行为、计数器等——而对于每天阅读这些 artifact 的用户来说，交互一致性**就是**产品体验。用用户为第一个此类货架留下的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实实例（已移除项目特征）：报告页面 skill 的 lightbox-gallery 组件（图像叠加：←/→ 在组内循环切换，ESC 关闭，原位缩放，n/N 计数器），以及其 interaction-components 注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击测试验证。参见方法论案例 17。

**流水线检查**：考虑此 skill 的输出是否会自然地馈入另一个 skill，以及是否应该由现有 skill 链式调用*此 skill*。添加或实质性更改“Next Step”交接或流水线契约，需要在编辑前重新归类为 Tier 3；Tier 1/2 可以提出建议，但不得顺手添加。

**引用与自我应用检查（能躲过细致作者检查的缺陷）**：有一类失败模式，从内部看起来都像完成的工作，而且无论怎样反复阅读都无法发现——每一种都需要改用*机械化*操作。（开头特意没有写数量。 “Three failure modes:” 是一个会过时的派生数字：任何人追加一个项目符号后它就会失效；而且，计数性文字之所以最难准确捕捉漂移，正是因为它*不包含发生变化的内容*——对列表本身执行的重新编号 grep 和 diff 都会径直绕过它。）之所以将它们归在这里，是因为它们有着共同的原因：**写下断言和验证断言是两种不同的模式，而单次遍历无法同时承担这两者。**在撰写过程中，“see rule 8”*就是*该断言；你并没有同时打开 rule 8。

与上面三个升级探针不同，这一项**不按层级限定范围**，而是按你写下的内容限定范围。一个没有新增指针、也没有新增规范性规则的 Tier 1 修复，不需要在这里做任何处理，而且你不必自己判断这一点：corollary 的脚本会在几秒内通过报告 `NONE prose-reference-shaped` 给出答案。只要你在任意层级写了指针或规则，下面这些要点就适用。

- **你写下的每一个指针，都要打开其目标，并从中复制一行出来——在写下指针之前。** 不要只是“我确信那条规则列出了全部三个标记”：把其中一段粘贴到你已经在为这一步产出的内容中（审查备注、提交消息正文或你的回复），放在某个第二位读者之后可以拿来与目标核对的位置。只看过但没有贴出的片段，正是本句开头所拒绝的自我评估。重新阅读时，错误的交叉引用是不可见的，因为错误的指针看起来和正确的指针一模一样，而作者又是唯一一个必然“记得”目标内容的人。真实案例：一位作者写下“参见 Cardinal rule 3”，指的是一条关于不要引用过时枚举的规则——但被引用文档**自身**的 rule 3 讲的是样本量，而实际被引用的规则位于另一个文件中；读者遵循该文档既有的自引用约定，就会落到一个无关主题上。同一轮编辑还提交了一个方向颠倒的指针（对于上方的材料却写成“见下文”），以及一个指向并不存在的章节标题的指针。
- **一旦文件中有两个编号列表，单独写一个 `rule N` 就存在歧义。** 检查是针对每个指针，而不是针对整个文件：在写下“rule N”之前，运行 `grep -n '^N\. ' <file>`，并确认在你所指的章节中恰好有一个匹配；如果有多个匹配，就同时写出章节名称。（**不要**把这变成文件级别的告警，例如“这个文件是否包含多个从 1 开始的列表”——在任何较长的文档中，这几乎总是成立，因此它会对健康输入触发，随后被人忽略，而纪律 #6 说明了这比没有检查更糟；在这个文件上运行一下，你就会亲自看到。）在真实案例中，一个单独的“rule 1”对应三个候选列表，而从上到下的搜索首先命中了错误的那个。
- **写下任何规范性规则后，都要用它旁边的行检查这条规则——并且让检查产出一个工件，而不是一个结论。** 使用与下面 corollary 相同的 `<base-ref>`，通过 `git diff <base-ref> -- <file>` 阅读你自己的代码块。这里自己阅读就足够了——你不是在进行模式匹配，因此不需要脚本——但必须带上那个 ref：单独使用 `git diff` 只显示尚未暂存的工作，而你一旦 `git add`，它就会什么也不输出；这正是本区块自身的 corollary 为逃避的五种静默空结果之一。把新规则拆分成各个独立的条款，并逐条写下：**同一个代码块中**满足该条款的行。（下面 corollary 中的 `scripts/reference_net.sh` 是另一项工作：它会列出供你解析的**正文交叉引用**。它不会把代码块交给你，也不会告诉你规则中的某个条款是否得到满足。）**旁边没有对应行的条款，就是发现的问题。** 那个诱人的简短版本——“我的新规则通过了吗？”——对 30 秒前写下它的人来说不可能失败；这正是纪律 #6 所说的：应当优先选择可证伪的观察，而不是自我评估，因此本要点也必须产出它所要求的同样工件。最先暴露问题的通常就是它旁边的段落。真实案例：有人新增了一条规则，要求“始终报告原始计数和过滤后计数——二者的差值**就是**污染”，但同一次提交中的自身工作示例只打印了过滤后的数字。同一个 diff 中的另一段陈述引用了两个数字，却没有说明这些数字是否是在邻近新规则刚刚规定的限定条件下采集的。范围很小且有明确边界：不是“重新阅读文档”，而只是“我 30 秒前写下的规则，在我 30 秒前写下的那些行上是否通过”。
- **为每条新规则增加一行，说明由谁执行它，以及执行者实际上是否有能力执行。** 如果现有工具无法满足某条规则，相信自己已经遵守规则的人就会跳过它——这是最糟糕的一类规则，因为它会产生有文档记录的虚假信心。真实案例：一条新规则要求“检查两个日志存储”；但项目自身的规范性单命令排查工具将其中一个硬编码，因此标准工作流会对这条规则本来要捕获的故障恰好返回干净结果。这条规则虽然正确，却不起作用，而且没有提到这一缺口。**让这一点可证伪的工件**（没有它，本要点就是一个禁止自我评估的区块中唯一的自我评估）：写出能够捕获违规的工具或命令，然后**针对一个你已经知道它应该捕获的案例运行一次**。如果它在已知有问题的输入上返回干净结果，你就已经测量出这条规则不起作用——把这一缺口直接写进规则本身。从记忆中回答“他们实际上是否有能力执行”正是纪律 #6 所拒绝的未经验证的断言。**当没有任何工具能够判定这条规则时**——大多数正文规则和审美规则都属于这种情况，因此不要把它当成逃避的出口——工件就是那句明确说明这一点的话：*“没有任何东西强制执行这条规则；只有在有人记得它时，它才会成立。”* 这比检查通过更糟，而明确说出来正是关键；一条执行情况保持沉默的规则会被默认遵守，而不是得到验证。注意本要点自身诚实的局限：工具的选择和已知有问题案例的选择仍然属于判断，因此它只是移动了未经验证的步骤，并没有消除它——这比替代方案便宜，但并不是免费的。
- **推论——你的修复本身也是缺陷来源，因此要在最后一次编辑之后，重新检查你触及的区域。** 在一次变更的两轮审查中，第一轮发现了八个问题；第二轮又发现了八个，**其中七个是由第一轮修复引入的交叉引用错误**。重写一句话会移动它周围的锚点。这也是为什么对于读者依靠指针导航的工件而言，“它已经审查过了”并不是终点：你一旦据此采取行动，审查结果就会立即过时。重新检查是机械性的，而且应当使用**脚本**，而不是让你重新输入命令：`scripts/reference_net.sh <base-ref> <file>…`（位于此 skill 的 bundle 中）。它会列出你新增行之间的正文交叉引用，以便你打开每个目标并确认其中确实写着你所声称的内容。首次使用前请阅读其头部——其中解释了它为什么接受 base ref，而不是默认使用 `HEAD`，以及它有意**不做**哪些事情。

**在开始编辑之前获取 `<base-ref>`，不要事后再获取。** 在开始时将其解析一次为字面量 SHA — `BASE=$(git rev-parse HEAD)` — 并将同一个值同时用于此处和上面的项目。如果你运行了现有 skill 迁移门禁，它就是你已经建立基线所依据的 ref。之后再传入 `HEAD` 才是陷阱：提交之后，`HEAD` 已经包含你自己的工作，脚本会如实报告 `IDENTICAL`，而这与没有任何内容需要检查无法区分。如果你没有预先捕获它，请恢复该值（通过 `git log`、`git reflog` 或你提供给迁移门禁的基线），不要用 `HEAD` 替代；当你的 base ref 同时也是当前 `HEAD` 时，脚本会打印提示，但不要依赖在那里发现这个问题。

**为什么这里要使用脚本，而这部分其余内容都是散文。** 它所替代的那条单行命令经历了五轮修补 — 将 diff 锚定到正确的基线、查看已暂存的编辑、在提交后仍能正常工作、跳过 diff 自带的 `+++` 标头、删除误导性的 `-n` — 而其中四轮都增加了另一种让它不输出任何内容并以 0 退出的方式，这与“我检查过了，而且没有问题”无法区分。第五轮则是同一种问题的另一种表现：它删除的 `-n` 原本会输出带行号的真实命中，但行号是按管道传入的流计算的，因此看起来很权威，却指向了错误位置 — 这比沉默更糟，因为错误答案的优先级高于没有答案。无论哪种情况，这项检查都在持续发布它本来要捕获的缺陷。散文无法验证自己的输入，无法说明发生了哪种结果，也无法被测试；脚本三者都能做到，而且它的契约是：**每种结果都必须明确命名，错误输入必须明确失败**。这就是本步骤前面提到的 Scripts 检查，应用于本段 — 而这五轮修补正是忽视它所要付出的代价。

**阅读它的判定结果，而不只是退出码。** 脚本只要成功运行就会以 0 退出，因此单独查看 `$?` 对它发现了什么毫无说明作用；答案在判定行中，并且它总会明确指出以下情况之一：找到了引用（逐一解析）、文件与基线完全相同、文件发生了变化但没有新增行，或存在新增行但其中没有任何类似引用的内容。这些是不同的结果，脚本特意将它们保持区分 — 曾经把它们合并成一个无声的“没有任何内容”的版本，正是它后来变成脚本的原因。它只需几秒钟，而且不依赖警觉性，这正是纪律 #6 对任何值得编写的检查所要求的。（它是一张网，而不是证明。它的盲点是没有数字的指针 — “请参见下面的章节”、“正如上面的规则所说” — 因此也要阅读新增的行。）

### 步骤 5：清理审查（任何公开 skill 都必须执行）

**在执行此门禁之前，如果纪律 #5 已到执行时机，其独立检查必须已经运行**，并且当前变更的 `independent-review.md`（位于你的私有、受 git 跟踪的知识仓库中 — 不在已清除的工作区中，也不在任何已经公开或可能变为公开、或会被分发的仓库中）必须存在**并且已经提交**。对于新 skill，它始终需要执行；对于现有 skill，使用下一段中的阈值。一个未提交、仅存在于 git 工作目录中的文件，与从未写入过的文件在实际意义上没有区别；`ls`/`test -f` 只能确认它位于磁盘上，不能确认它能够留存下来。对于**新** skill，这是任何内容第一次离开你掌控的步骤，因此也正是在这里真正执行这项纪律，而不只是陈述它 — 一条位于使用位置上方 1000 行、却没有任何检查机制的规则，每次都会输给追求完成的冲动。

**对于已发布 skill 的修改，它离开你手中的那一刻就是 push，而不是这一步。** 这个门槛可以用一句话回答“仅限内部，跳过”，而且对于仅修改文档的变更，打包可能根本不会运行——因此把审查锚定在这里，就意味着一次 skill 修改可能在没有任何独立审阅者检查的情况下进入公共分支。真实案例（2026-07）：对本文件本身的一次修改发布了一个 discovery command，但它无法访问旁边正文声称能够覆盖的三个根目录；该修改已经合并，直到*之后*委托的一次审查才发现了问题。**因此，对于现有 skill：独立审查及其记录下来的产物必须在 `git push` / 开 PR 之前完成——在 push 时运行的各个门槛（回归审计、验证、扫描）检查的都是结构，没有任何一个能告诉你这些指令是错的。** 这完全沿用纪律 #5 的门槛：当*规则、契约或数字发生变化时*必须执行，而拼写错误或纯格式调整则不需要。让拼写修复也必须等待一轮审查，只会教会人们形成反射式的做法——纪律 #6 警告的正是这一点：“这次改动很小”会变成普遍豁免，最终连真正重要的改动也被它涵盖。

**对于要进入公共仓库的 skill，这不是可选项。** 私有内容一直会泄露到公共 skill 中，而扫描器漏掉的泄露才是危险的——非英语语言中的真实姓名、真实对话记录中的逐字原句、被放进示例说明中的真实案例。只有当该 skill 确实仅限内部使用时，才可以跳过。

**按目标范围界定审查，而不是按主题界定。** 只有会公开发布的产物——skill bundle 本身——需要进行清理。留在私有仓库中的配套文档（skill 提炼自的事件报告、内部运行手册、项目的 CLAUDE.md）应保留其真实主机名、路径和时间戳：对这些内容进行脱敏会破坏其审计价值，而且你最终会把这些改动恢复回去。有一次提炼会话之所以经历三轮返工，正是因为脱敏审查被应用到了源材料涉及的所有内容，而不只是公共 skill。

**先检查目标位置，并让它预先填入建议。** 在 skill 将要存放的仓库上运行
`gh repo view --json isPrivate`（或者读取
`quick_validate` 已经打印出的提示）。私有目标位置应使选项 C 成为默认建议，而不是事后才想到的选项——“除非另有说明，否则假定为公开”正是把私有 skill 的工作路径变成无人要求的占位符的原因。

**触发脱敏的是目标位置的 `isPrivate`，而不是任务让人感觉有多像发布。** 这两者并不总是一致，而当它们不一致时，除非你明确指出这一点，感觉就会占上风。把内容*移入 marketplace skill*会让人感觉像是在发布——marketplace 正是用于分发内容的地方——因此即使源仓库和目标仓库都是私有仓库、内容也不会被发布出去，脱敏反射仍会被触发。真实案例（2026-07）：一次从项目级 skill 迁移到私有 marketplace skill 的操作，把真实配置路径、真实十六进制值和真实命名示例都泛化成了占位符。`quick_validate` 在**每次**运行时都打印了 `🔒 audience: private`；作者每次都读到了它，却仍然进行了脱敏，因为这种*活动*在观感上像是在发布。代价并不只是表面上的——真实路径能让下一位读者去检查该值；“项目自己的 token 文件”却无法打开。

所以要把它当作一次查询，而不是一次判断：**读取目标的 `isPrivate`，如果它是 `true`，则进行清理需要所有者主动提出。** 从私有目标到私有目标的移动是一次移动，而不是一次发布。**当两个探针都没有返回结果时**（尚未有远程仓库、尚未运行 `quick_validate`），你就没有查询结果——应回退为将其视为公开，并明确说明这一点，因为不对称性就是如此：一次不必要的询问只会多花一句话，而一次不必要的泄露则无法挽回。并且，`isPrivate` 报告的是目标**今天**的状态——一个位于私有仓库、正准备发布的 skill，会在发布它的 push 上进行清理，而不是在这次进行。如果你发现自己开始思考某些内容在私有目标中是否“应该”被泛化，这种思考本身就是信号。

使用 **AskUserQuestion** 确认清理深度（对于公开目标，确认清理深度，而不是是否进行清理；对于私有目标，则确认是否需要清理）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**清理流程——通读是方法，扫描是辅助：**

1. **亲自通读整个 skill 并进行语义判断**（这才是真正的检查）：SKILL.md + 每个 reference + 每个 example。对于每个具体名词 / 示例 / 代码片段，询问“这是通用占位符或公开实体，还是从真实项目 / 人员 / 对话记录中直接取来的？”替换后者——即使扫描器没有标记它。这是唯一能捕获没有可匹配关键词的泄露的方法。完整指南及语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **运行扫描器，作为一次低成本的初步检查**：使用清单中的 grep 模式 + `security_scan.py`（步骤 6）。它们可以快速捕获明显的密钥 / 路径 / 已知名称——但“没有匹配结果”并不代表检查通过。
3. **替换**每个发现的问题，用保留教学重点的通用等价内容替换（真实姓名 → 公众人物或 `<placeholder>`，真实代码片段 → `<placeholder>`）。从过去的经验中总结出两条规则：占位符本身不能编码真实值——`<acme-corp-domain>` 会准确泄露它原本要隐藏的名称；应改为命名其*角色*（`<api-domain>`、`<upstream-provider>`）。此外，当你编写批量替换脚本时，要为其指定限定在 skill 目录范围内的明确文件白名单——未限定范围的查找替换会毫不犹豫地改写项目自己的 CLAUDE.md，迫使你执行 git restore。
4. **通过重新阅读而不是重新 grep 来验证**：重新阅读已修改的部分，并确认没有破坏引用。

### 步骤 6：安全审查

在打包或分发 skill 之前，运行安全扫描器以检测硬编码的密钥和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测覆盖范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）

**不覆盖的内容** — 这也是为什么仍然需要执行步骤 5 的通读检查：gitleaks 和正则规则只能匹配*你列出的已知机密格式和模式*。对于没有关键词的私密内容，它们在结构上是无法识别的——非英语语言中的真实人物/项目名称、真实记录中的逐字内容、从你自己的工作中直接摘取的真实示例。`security_scan` 显示绿色表示“未发现已知格式的机密信息”，**并不表示“该 skill 已完成清理”**。绝不要将其视为后者。

**首次设置：** 如果尚未安装 gitleaks，请先安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 无问题（可安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**对于私有 skill，发现的问题是信息，而不是待办事项。** 扫描器无法区分泄露的凭据和*本来就应该存在的*凭据——例如，一个全部价值就在于预先填充好内容的模板，或一个指向其运行所在那台机器的脚本。永远不要在私有仓库中自动修复：报告发现的内容，让所有者自行决定。下面的选项 A（“自动修复”）适用于准备公开发布的 skill。

**如果发现问题**，请通过 **AskUserQuestion** 呈现：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 步骤 7：打包 Skill

skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于每个已存在且受 Git 跟踪的 skill，在提供完整审查结果并重新验证之前，都会阻止打包。当前标记仅是本地状态回执，因此先提交或手动编写标记都无法绕过审查。下次编辑后，审查将变为过期状态：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及使用 `--include-evals` 将根目录下的 `evals/` 目录一并打包（默认作为开发资源排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. **自动验证** skill（YAML frontmatter、命名约定、路径引用完整性）
2. **重新验证已完成的现有 skill 回归审查**，只要 Git HEAD 已包含该 skill；仅凭标记永远无权进行打包
3. **验证安全扫描**（内容哈希必须与上次扫描一致）
4. **将** skill **打包为可分发的归档文件**

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 步骤 8：更新 Marketplace

打包后，更新 Marketplace 注册表，以包含新技能或已更新的技能。

**对于新技能**，在 `.claude-plugin/marketplace.json` 中添加一条记录：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于已更新的技能**，按照 semver 规则递增 `plugins[].version`。对技能文件进行的任何更改——即使只是修复一个单行拼写错误——都需要递增版本号：否则，`marketplace update` 会认为没有新版本，因此**已经安装的副本永远不会刷新**，用户会继续运行旧技能，而你的修复则无法发布。

**然后将其记录到变更日志中——这正是容易被跳过的一步。**版本号递增使更新*可安装*；而记录条目，才能让它在六个月后有人遇到相同问题并通过 grep 搜索时*可查找*。如果变更日志记录了其他每个技能的版本，却悄无声息地漏掉了你的版本，那比完全没有变更日志更糟：这些空缺会被理解为“那里什么都没变”。

不要另起炉灶，按照现有条目的格式来写——在 Keep-a-Changelog 文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。

将其与版本号递增放在**同一个提交**中；“稍后”再更新的变更日志，往往就是永远不会更新的变更日志。

真实案例（2026-08）：某个技能连续发布了两个版本，版本号递增正确、检查门禁通过、PR 也已合并——但**完全没有变更日志条目**，因为这套流程中没有任何内容要求记录变更。直到后来的一次审计才发现这两个版本。这正是纪律 #6 在本文件自身上的体现：一条只存在于约定而不属于步骤的规则，每次都会输给“赶紧完成”的惯性。

**保持注册表差异最小——这是所有技能共用的唯一文件。**Marketplace 清单是所有并行编辑者都会发生冲突的地方，因此，与其他位置的同类更改相比，在这里进行无关的格式化更改代价高得多：它会把原本干净的三行版本号递增变成其他正在编辑该文件的人必须解决的冲突。使用脚本更新时（解析为 JSON、修改后再写回），重写过程可能会悄悄规范化文件原本未采用的格式——末尾换行、缩进宽度、键顺序、Unicode 转义等。遵守往返处理规范：之后重新读取文件，并对该文件运行 `git diff --stat`；**唯一可以出现的行，必须是你有意修改的字段对应的行。**如果出现了额外行，恢复文件原有的约定格式，不要发布这次规范化更改（某次脚本化版本号递增曾给一个原本从未包含末尾换行的清单添加了末尾换行——在最可能与他人同时编辑的文件中，白白多出了一行差异）。同样的原则也适用于技能会修改的任何共享注册表：锁文件、目录、索引文档。

**当 PR 经历了几次合并后仍未结束时，执行 rebase——然后证明你没有吞掉任何人的工作。**正是因为清单容易成为冲突热点，它也最容易过时：一个修改注册表和变更日志的开放 PR，只要有其他内容合入就会发生冲突，因此应预期 `mergeable: CONFLICTING`，不要把它当成意外（某个 PR 就是在主分支一个下午前进了 7 个提交后遇到这种情况的）。如果仓库采用 squash merge，应执行 rebase 而不是 merge——在压缩后的历史中，合并提交没有任何收益。冲突本身几乎总是**追加式的**：两位作者分别在同一部分追加了各自的条目，因此解决冲突时应**保留两者**，绝不要使用 `--ours`/`--theirs`，因为那会悄悄丢弃同事添加的那一行。

人们跳过的步骤，正是能发现错误解决结果的步骤——**完成解决后，证明与基准相比唯一的差异就是你的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要使用裸 `--force`：如果远程仓库自你上次获取以来发生了变化，lease 会使推送失败；而这正是有人向你的分支推送、普通强制推送会将其覆盖的情况。

**插件边界不属于此 skill 的职责范围。** 是否应将 skills 拆分到不同的插件中、如何组织 `source`/`skills`，以及用户是否可以单独切换 skills，都属于打包/分发领域——这里的 SSOT 是 `marketplace-dev` skill，而不是本 skill。当任务确实需要这些决策时：确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与 `skill-reviewer` 需要其脚本时拉取 `skill-creator` 相同），然后阅读 marketplace-dev 的 cache-and-source-patterns 参考并遵循其中的要求。不要在此重复其规则；复制一份会导致内容逐渐偏离。

**重命名、迁移或移除 marketplace 条目，对于已经安装该条目的每位用户来说都是破坏性变更**——当条目消失时，Claude Code 不会清理已安装的副本，从而留下每次执行 `marketplace
update` 都会报错的悬空安装。应将此类变更视为 API 弃用：在变更日志中附上迁移说明，并遵循 marketplace-dev 对具体操作的指导。

**如果你亲自提交/推送 skill 仓库：** 对于已有 skill，如果当前变更触及 discipline #5 的规则/契约/数值阈值，请确认审查产物记录了这项变更并且已提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不只是确认某个历史上的 `independent-review.md` 是否存在）。拼写错误或纯格式重排不需要该产物；较早的审查不能满足当前的实质性变更。Step 5 的说明解释了，为什么对于已经发布的 skill，真正的强制检查点是推送，而不是打包。然后仅暂存 skill 的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要执行 `git add .`；工作树通常充满无关的变更，否则这些内容也会被一并带入提交（曾有一次提交混入了一堆无关的 transcript 文件，之后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库的实际可见性，不要根据路径想当然——公开的 skill 仓库应当通过 PR + review，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成 skill 后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试 skill 后，用户可能会要求改进。通常这会紧接着发生在使用 skill 之后，此时用户对 skill 的表现还记忆犹新。

**优化筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经覆盖了某个问题，则不要重复添加。

## Claude.ai 特定说明

在 Claude.ai 中，使用相同的验证深度路由器和重型评估授权门控。当明确授权执行完整的通用成对流水线时，工作流为起草 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子代理，需要对部分机制进行调整。具体调整如下：

**运行测试用例**：由于没有子代理，无法并行执行。对于每个测试用例，读取 skill 的 `SKILL.md`，然后亲自遵循其中的说明来完成测试提示。一次执行一个测试用例。这种方式不如独立子代理严格（你编写了 skill，同时也在运行它，因此拥有完整上下文），但可用于进行合理性检查，而人工审查步骤可以弥补这一点。跳过基线运行——直接使用 skill 按要求完成任务即可。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或者你在远程服务器上），则完全跳过浏览器审查员。改为直接在对话中展示结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），将其保存到文件系统，并告知用户文件位置，以便他们下载和检查。直接在线询问反馈：“看起来怎么样？有什么想修改的吗？”

**基准测试**：跳过定量基准测试——它依赖基线对比，而在没有子代理的情况下，这些对比并没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同——改进 skill，重新运行测试用例，询问反馈——只是中间不再使用浏览器审查员。如果有文件系统可用，仍然可以将结果整理到迭代目录中。

**描述优化**：本节需要使用 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要使用子代理。请跳过本节。

**打包**：`package_skill.py` 脚本可在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 中，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能是要求你更新现有 skill，而不是创建新的 skill。在这种情况下：
  - **保留原始名称。** 注意 skill 的目录名称和 `name` frontmatter 字段——保持不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前复制到可写位置。** 已安装的 skill 路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即从该可写副本创建审计工具的编辑前快照，然后使用 `--regression-review` 从副本进行编辑和打包。不要传递 `--new-skill`；非 Git 副本的现有 skill 仍然是现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后再复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 专属说明

如果你在 Cowork 中，主要需要了解以下事项：

- 你拥有子代理，因此经过明确授权的通用配对流程可以运行基线和评分器。子代理可用并不等于已获得授权，也不能据此增加额外角色；请说明必要的执行分支，限制并发，并在并行运行无法提供额外证据时按序运行各个案例。
- 你没有浏览器或显示界面，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个用户可以点击、在浏览器中打开该 HTML 文件的链接。
- 在经过明确授权的**通用配对运行**之后，在你自行修改 skill 之前，使用 `generate_review.py` 为用户生成评估查看器。默认层级证据、未经授权的工作，以及替代查看器机制的专用工作流，不会仅仅因为工作在 Cowork 中进行，就产生查看器义务。
- 反馈的工作方式有所不同：由于没有运行中的服务器，查看器中的“Submit All Reviews”按钮会将 `feedback.json` 文件下载下来。然后你可以读取该文件（可能需要先请求访问权限）。
- 可以进行打包——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中也应该可以正常工作，因为它通过子进程使用 `claude -p`，而不是浏览器，不过请在完全完成 skill 且用户确认其状态良好后再进行。
- **更新现有 skill**：用户可能是要求你更新现有 skill，而不是创建新的 skill。请遵循上方 claude.ai 部分中的更新指南。

## 参考文件

`agents/` 目录包含专用子代理的说明。需要生成相关子代理时，请阅读这些说明。

- `agents/grader.md` — 如何根据输出评估断言
- `agents/comparator.md` — 如何对两个输出进行盲测 A/B 比较
- `agents/analyzer.md` — 如何分析为什么一个版本胜过另一个版本

`references/` 目录包含额外文档：
- `references/eval_pipeline_schemas.md` — `evals.json`、`grading.json`、`benchmark.json` 等的 JSON 结构
- `references/sanitization_checklist.md` — 在公开发布前清理业务特定内容的检查清单

`scripts/` 目录包含此工作流使用的确定性门禁：
- `scripts/audit_skill_regression.py` — 将不可变的旧技能包与编辑后的包进行比较，创建明确的处置审查，并在打包现有技能前验证其哈希值/证据。
- `scripts/reference_net.sh` — 列出你新增各行之间的文本交叉引用，用于步骤 4（编辑技能）中的“引用与自我应用”检查。其自身的头部即为约定：它涵盖什么、刻意留给 `lychee` 的内容，以及为何它使用基础引用而不是 `HEAD`。

为强调起见，再次在此重复核心循环：

- 弄清该技能的用途
- 对于现有技能，在编辑前快照并清点旧包
- 在采取任何专用工作流出口之前，选择能够证伪此更改的最低验证层级，并记录原因
- 起草或编辑技能
- 运行该层级所需的证据，或所选专用工作流声明的等效机制
- 对于明确授权的通用配对运行，与用户一起评估输出，创建 `benchmark.json`，并运行 `eval-viewer/generate_review.py`
- 重复，直到你和用户都满意
- 运行并通过现有技能回归审查；仅通过评估不算
- 打包最终技能并将其返回给用户。

如果你有 TodoList，请将所选验证层级及其默认证据添加进去。只有在明确授权通用配对管道后，才添加“创建 evals JSON 并运行 `eval-viewer/generate_review.py`，以便人工审查测试用例”。
