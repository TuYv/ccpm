# 技能创建器

一个用于创建新技能并对其进行迭代改进的技能。

从宏观上看，创建技能的流程如下：

- 确定你希望技能实现什么功能，以及大致应如何实现
- 将变更归入能够证伪其可能故障模式的最低验证层级
- 编写技能草稿
- 在该层级进行验证：对范围明确的修复执行针对性检查，对存在不确定性的指令变更进行抽样行为重放，或者对全新、高风险或范围广泛的工作运行完整的成对评测流程
- 当所选层级产出定性或定量结果时，帮助用户评估这些结果
- 根据用户对结果的评估反馈重写技能（如果定量基准测试中暴露出任何明显缺陷，也应进行重写）
- 重复上述过程，直至你感到满意
- 仅当现有证据无法判定变更后的行为时，才提升验证层级

使用此技能时，你的职责是判断用户目前处于该流程的哪个阶段，然后立即介入并帮助他们推进相应阶段。完整的 A/B 基准测试是一项能力，而不是每次编辑都必须缴纳的成本。对于能够直接测试其正确性的范围明确的修复，不要创建评测文件、扇出成对代理、对输出进行评分或启动查看器。

以下六项长期准则贯穿始终，因为这些故障模式会导致看似令人信服、实则错误的技能被交付：

1. **先验证，再编写。** 技能中出现的每项技术断言（端点、参数、命令、版本、行为）都必须能够追溯到你亲自执行并观察到的内容——无论是在当前会话中，还是在一个经过明确批准的历史会话中。现在无法验证？要么去验证，要么明确标注（“未经验证——来自记忆”）。技能会放大其包含的一切：经过验证的知识会复利增长，言之凿凿的错误也同样如此。对于知识型技能（内容主要是有关外部系统的事实——API 端点、参数、字段、平台行为），请阅读 [references/knowledge-skill-grounding.md](references/knowledge-skill-grounding.md) 以了解实际操作规范：权威性层级（观察到的行为 > 机器可读契约 > 经实际运行的生产代码 > 官方文档 > 记忆）、证据范围标注、发布前文档示例冒烟运行，以及受众/Windows 可移植性检查清单。一次来源依据审计曾发现多项言之凿凿的契约声明与作者当时已经掌握的证据相矛盾（方法论案例 9）。
2. **将“不可能/不支持”视为假设，而不是结论。** 当某项能力似乎受阻时（API 错误壁垒、工具无法连接、格式无法打开），应先穷尽所有观察路径——UI 自身的网络流量、替代渠道、不同的已记录标识符——然后再将“平台不支持此功能”写入技能。观察到的行为优先于推测出的请求形式。
3. **站在该领域巨人的肩膀上——在编写或优化技能的方法论之前，默认将该领域已经确立的最佳实践检索到上下文中。** 技能方法论的质量上限取决于上下文窗口中的知识，而不是潜藏在模型权重中的知识：预训练是有损的，会随时间过时，而且除非真正将权威来源调取进来，否则往往根本不会被激活。因此，你所编写内容的质量上限是 `your training data + the user's input`——*除非*你主动检索该主题领域真正的既有成果。务必这样做：使用 WebSearch 搜索该领域的权威理论、标准和方法，并阅读该领域中任何随附或已安装的技能，然后将其中起支撑作用的原则连同归属信息融入技能。**这与下文的“既有成果研究”是不同的维度**——后者寻找可复用的*工具/基础设施*；此处则是用该学科积累的科学成果为*方法论本身的质量*奠定基础。将其设为**默认操作，而不是等别人要求后才去做的事**：简要告诉用户你正在参考哪个领域，并允许他们说“跳过”，但当该领域 40 年来公开积累的成果只需一次搜索即可获得时，绝不要交付一个受限于你的记忆和用户提示的方法论。例如：数据可视化技能必须吸收 Cleveland 与 McGill 的图形感知排序和 Bertin 的视觉变量理论（位置/长度优于颜色，颜色优于文本——这是测量结论，而非审美偏好）；日期/时间技能必须呈现成熟的库及其公认的陷阱；说服/谈判技能必须检索已经确立的框架，而不是凭记忆重新发明。如果权威知识只存在于你的权重中，却从未进入上下文，那么你就是在本可引用依据的地方进行猜测。
4. **压缩现有技能之前，先保留其内容。** 更新现有技能是一项迁移工作，而不是从空白页开始重写。在第一次编辑之前，使用审计工具的 `snapshot` 命令捕获完整的旧技能包，或者从明确的 Git 引用重建它；任意副本加上来源标签并不能构成基线。盘点运行时能力、触发上下文、接口、参考资料和评测覆盖范围。渐进式披露和简洁性允许移动内容或对内容去重；它们不允许悄无声息地删除行为。编辑完成后，运行 `scripts/audit_skill_regression.py`，并对每个未匹配的旧单元进行分类。仅存在于 `evals/`、测试或未链接参考资料中的运行时契约仍然属于丢失。在任何候选项尚未分类或任何真实缺口尚未修复时，都不要宣称更新已完成。同样的逻辑不仅适用于*删除*，也适用于*反转*，并且涵盖之前作出的任何承诺——而不只是那些附有日期和姓名的承诺：**推翻已经作出的决定是一项提议，绝不能成为附带影响。** 明确说出来并获得接受。悄无声息的重写比悄无声息的删除更糟，因为它会同时摧毁产物以及原本可以发现问题的证据——并使所有下游审阅者失去判断依据（参见 #5）。

5. **任何内容都不能仅凭自我审查就交付——由独立、全新上下文进行的对抗性审查是固定步骤，而不是特殊情况。** 你对“现在已经没问题了”的判断，运行在生成该产物的同一个模型上，因此它具有造成该缺陷的完全相同的盲点。这是实测结论，而非坊间传言：没有外部反馈时，内在自我纠正并不能可靠地改善输出，有时反而会使其变差（Huang 等，ICLR 2024）；而当生成者与评估者具有相同的错误模式时，反复迭代只会**提高信心，却不会增加信息**。再多的自检也无法摆脱这一点；只有外部视角可以。**完整流程——提示词模板、锚点选择、发现项表格、完整案例——见 [references/independent-review-protocol.md](references/independent-review-protocol.md)；请在首次审查前阅读。** 其中不可或缺的规则如下：
   - **独立性有两个方面，而第二个方面正是作者容易忽视的。** *审查者的上下文*不能是你的上下文分叉——分叉会继承你的盲点，然后交还一个“已审查”的印章。但它用来衡量产物的*证据*也必须位于**变更的影响范围之外**，否则它就会继承你的**结论**：它读取的是已经彼此一致的产物与规范，然后报告二者一致。请注意，“本次会话中未编辑”这一界线过于宽松——在参考文档的受控案例中，被污染的记录是在*前一天*编辑的，三名审查者因此都未能发现一个他们在未经改动的对应版本中成功发现的缺陷。应根据锚点有多难被*你*改动来排序：用户自己的原始对话用词 > 早于本次工作的 git 引用（`git log --oneline <ref>..HEAD -- <path>`；只要其中有你的任何提交，就不再符合条件）> 仅追加日志（这是一种约定，而非强制机制）。**全新项目没有锚点——应明确说明并向用户索取锚点，而不是报告一次你实际上并未执行的通过结果。**
   - **只向它提供两样东西：产物和读者规范。** 不要提供其他任何内容——不要提供设计理由、项目背景，也不要说“只需确认 X 没问题”，因为这会把独立审查者变成橡皮图章。读者规范是一份*规范*，而非理由，因此它无法为任何内容盲目背书；省略它会浪费一半的审查价值，因为审查者随后只能以自身为衡量标准。**对于 SKILL.md，读者是执行它的另一个智能体**，其失败模式是“我不知道该调用哪个工具”，而不是“我不认识这个词”——应询问哪些指令令其无法采取行动。在审查运行前陈述规范，之后绝不能用它来解释或搪塞发现项。
   - **对于可理解性，以及相对于语料库的完整性，它是事实依据；对于品味，它没有裁决权。** 直接采纳前两类判断。将“这可能是一个缺陷／我建议采用 Y”视为假设，并先自行复现。绝不要委托它判断 AI 垃圾内容或审美问题——这属于同模型盲点。
   - **枚举失败*维度*，而非内容领域——这也决定了需要运行多少名审查者。** 维度是*你提出的问题*；领域是*你阅读的材料*。让三名审查者分别覆盖场景、算术和差异，但都只问“这是否连贯？”，等同于把一名审查者计费三次。**默认使用一名审查者，而且通常已经足够**；只有增加新的维度时才再增加一名。自我审查最不擅长的维度是**忠实度**——“这是否仍然忠实于此前已经作出的承诺？”——因为作者正是改变承诺的人，而连贯性与忠实度彼此正交：一份产物可以在内部完美自洽，却完全背离已经作出的决定。
   - **必须留下产物，否则这只是一则警告。** 纪律 #6 规定，得出意见的检查不如生成产物的检查——因此这项检查也必须生成一个文件，否则它恰恰会在最重要的时候败给完成任务的冲动。在你的私有、由 git 跟踪的知识仓库中，将 `independent-review.md` 写入 `skill-reviews/<skill-name>/`：包含**审查者提示词原文**（以便后续读者判断其是否具有诱导性）、**每项发现及其处置方式和理由**（这正是合理筛选与丢弃刺耳意见之间的区别），以及**无法检查的内容**。如果你不知道哪个仓库是你的私有知识仓库（或者没有这样的仓库），应明确说明并询问用户——不要猜测一个位置，导致文件落入任一禁区。两个禁用位置：**不得放在 `<skill-name>-workspace/` 中**（这些是被 git 忽略且会被清除的暂存目录——该文件是跨会话的审查证据，必须在这些目录被清除后仍然存在），并且**不得放在任何已经或可能变为公开或分发用途的仓库中**——这通常意味着不能放在被审查技能自身的仓库中（审查内容本身必然会引用私有路径、真实姓名和项目细节）。进行实质性编辑后，必须由一个*新的*智能体重新审查——实质性编辑是指规则、契约或数值发生变化，而非修正拼写错误。**从第 5 步开始，该文件就是审查确已执行的证据；文件不存在就意味着审查未执行。** **写入文件并不等同于确保它在下一次会话中仍然存在——必须在同一轮中于该私有仓库内执行 `git add` + `git commit`。** 一个留在 git 工作目录中但尚未提交的文件，并不具备这条规则所要求的任何“由 git 跟踪”保障：它可能丢失、被覆盖，或者之后检查“是否已经审查？”的任何流程都可能根本无法发现它（真实案例：文件已正确写入正确路径，并包含真实发现项——但后续自动检查仍然失败，因为它从未被提交；解决方法是执行一次 `git commit`，而不是移动文件）。
   - 纪律 #4 的回归门禁是机械式且互补的：它证明你没有*删除*行为。它完全无法说明你写下的内容是否真的可以被遵循。

6. **设计你编写的检查，使其无法自证通过。** Skill 在很大程度上由检查组成——关卡、检查清单、“发布前”步骤——如果执行检查的上下文能够在*违反检查所编码的规则本身时*仍然通过检查，那么这种检查比没有检查更糟，因为它会制造虚假的信心。以下四条规则借鉴自那些先于软件领域解决了这一问题的领域：
   - **验证必须覆盖规则中的每一项要求。** 如果规则写的是“A + B + C”，证据就必须分别要求提供 A、*以及* B、*以及* C 的证明。在包含三项要求的规则后面生硬地附上一行确认项，只会被作者已经完成的那一项满足；其他要求则形同无物。真实案例：一个报告编写 Skill 包含一道交付关卡，其规则写着“选项以并排筹码形式呈现 + 突出显示建议选项 + **背景信息使用完整、独立成篇的句子编写，使陌生人也能理解**”——但其下方的证据行只要求“N 个决策项，全部呈现为筹码”。作者执行了该关卡，写下了这条证据，自证通过，然后发布了一个页面，其中的标签只有单个字符，所有上下文都已被删除。规则始终都在文件里；只是检查从未衡量过那项要求。
   - **对正常输入误报的检查比没有检查更糟。** 上述失败是检查本应失败却通过；这里则恰好相反——检查本应通过却失败。后者代价更高，因为它会训练操作者形成条件反射般绕过检查的习惯（`--no-verify`、`SKIP=1`、`--force`）；而一旦形成这种习惯，关卡对于*所有*输入都会失效，包括它原本要拦截的那些输入。因此，在编写失败关闭型检查时，**假阳性的优先级高于假阴性**：漏掉一个真实问题只会让你在该实例上付出代价，而误杀一个正常输入则会让你失去整道关卡。
     注意这个征兆：**因反复踩中同一个陷阱而产生的挫败感，本身就是风险信号**——作者恰恰会在这种状态下发布一项从未使用正常输入校准过的防御措施。真实案例：在一天内三次踩中同一个格式陷阱后，作者向一个 linter 添加了正则表达式检查；它在项目自身的语料库中误杀了 **33 个正常输入**，并在同一小时内被回滚。先校准，再启用——在真实且已知正常的材料上运行任何失败关闭型检查，并确认假阳性为零；宁可放宽检查，让它偶尔漏检，也不要让它发生误报。
   - **让每一项都成为可证伪的观察，而不是自我评估。** “背景信息是独立完整的”这一项不可能被其作者判定为失败；“遮住页面其余部分，只阅读一张卡片，并说明它在决定什么”则可以。应优先采用能够产出制品的检查——命令输出、引用的行、截图——而不是只能产出意见的检查。
   - **同样的怀疑也适用于你所*运行*的检查，而不仅仅是你编写的检查。** 以上四条规则约束的是随 Skill 一同交付的检查。但你用来验证**自己**工作的 grep、find 和一次性脚本同样也是工具，而错误的工具会像正确的工具一样信心十足地报告结果无误。在 2026-07 的一次会话中，五条不同的验证命令在两个方向上都给出了错误结果：一个不带 `-L` 的 `find` 报告已安装 Skill 的文件缺失（这些文件位于符号链接之后）；一个 `grep --exclude-dir=<name>` 隐藏了正在审计的对象的另一份副本；一个逻辑取反的 shell 条件错误地发出警报，称删除操作尚未发生；一个跨越换行符的正则表达式凭空制造了 55 个“丢失的引文”；而一次只搜索五个文件中的两个文件的操作报告有两条规则缺失，但它们其实存在于第三个文件中。**最初，所有这些结果都被相信了；而且每一个错误都只有在改用不同形式的检查重新运行后才被发现。**

修复方法是实验实践中最古老的一条：**在把仪器用于答案未知的案例并信任其结果之前，先用它测试一个答案已知的案例。** 要用 grep 查找一个预期不存在的字符串？先以相同的命令形式查找一个你知道确实存在的字符串——如果这也返回 0，那么出问题的是命令，而不是文件。这样做只多花一行，却能把“我检查过了”变成“我用经过校准的仪器检查过了”。

     有两种具体情况值得牢记，因为它们都在上文出现过，而且都会*静默地*失败：`find` 在没有 `-L` 时不会跟随符号链接（而 skill 的安装位置通常是指向源代码仓库的符号链接），并且 `--exclude-dir` 会按基本名称匹配目录树中所有位置，而不只是你心中所想的那个路径。

     **这条规则还有后半部分，而它只有在检查方法被发布时才会带来麻烦：请针对*标准*实现进行校准，而不是针对你机器上的实现。** 上面的仪器规则确保*你的*结论可靠；这条规则则确保*读者的*操作有效。写入 skill 的工具行为断言——某个标志、某种递归模式、某个声称“会跟随符号链接”的选项——会在你从未见过其二进制程序的机器上执行，而且这种差异在两端都是静默的：你测试时它有效，而到了读者那里却悄无声息地什么也不做。有两种机制会导致这种情况，而且从会话内部看，两者都不可见：**相同的命令名称会解析到不同的程序**（shell 别名或函数遮蔽了二进制程序——请注意，`\tool` 只能绕过*别名*，因此只有 `command tool` 或绝对路径才是确定性的形式），以及**同一个程序在不同实现中的行为不同**（BSD、GNU 或直接替代实现）。真实案例（2026-07）：一位作者验证了 `grep -R` 会跟随符号链接，于是把它作为符号链接陷阱的修复方法写入 skill，并发布到了一个拥有 1200 个 star 的公共仓库——他们的 `grep` 实际上是通过 shell 函数调用的 ugrep；而在 macOS 自带的 `/usr/bin/grep` 中，同样的 `-R` 什么也匹配不到（它需要 `-RS`），因此这个指定的修复方法对大多数读者都静默失败了，而且偏偏发生在警告验证器会静默失败的章节里。

     因此：**在任何关于工具行为的断言进入发布制品之前，请使用标准二进制程序**（`/usr/bin/<tool>`）重新运行测试，而不是使用 shell 交给你的程序。如果断言无法通过这项测试，就不要写下那个标志——**应优先采用与具体实现无关的表述**：自行解析路径（`readlink -f`），而不是押注某个递归标志；在脚本中执行子字符串测试，而不是使用面向行的匹配；描述你需要的*行为*，而不是你碰巧知道的选项。仅在你的环境中有效的操作指示比没有指示更糟，因为读者无法发现它其实悄无声息地什么也没做。

   - **采用成熟的检查清单实践早已确定的做法。** 确定清单属于 **READ-DO**（边读边执行——适用于低频或不熟悉的流程）还是 **DO-CONFIRM**（凭专业经验工作，然后在预先定义的**暂停点**停下来确认——适用于时间压力下的熟练操作者），并将其锚定在真正的暂停点，而不是“工作流中的某个位置”。清单应只保留**致命条目**——既关键、又通常会在压力下被遗漏的项目，数量大约为五到九项；超出这个范围的内容会降低遵从度（[Gawande，*《清单宣言》*](https://www.shortform.com/blog/types-of-checklists/)）。此外，应优先采用 Shingo 的**控制**而不是**警告**（[防错法](https://en.wikipedia.org/wiki/Poka-yoke)）：文字提醒依赖警觉性，抵挡不住急于完成任务的冲动，而能够阻止流程继续或强制生成制品的步骤根本不需要警觉性。当 skill 只能发出警告时，至少要把警告放在做出决策的位置——**如果执行上下文从不打开某份参考资料，那么归档在其中的规则实际上就不算规则。**

另一方面，他们可能已经有了一份技能草稿。在这种情况下，你可以直接进入循环中的评估/迭代环节。

当然，你始终应该保持灵活。如果用户表示“我不需要进行一大堆评估，跟着我的感觉来就行”，你可以改为按他们说的做。

然后，在技能完成之后（不过再次强调，顺序是灵活的），你还可以运行技能描述改进器；我们为此提供了一个完全独立的脚本，用于优化技能的触发效果。

## 首先：共存检查（官方 skill-creator 插件）

在进行任何其他操作之前，先快速检查一次（只需执行一次 grep，在常见情况下无需输出）：`${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/installed_plugins.json` 是否包含 `"skill-creator@claude-plugins-official"`？

- **不存在（常见情况）：**无需执行任何操作——不要安装任何东西，也不要向用户提及本节。继续进行当前任务。
- **存在：**官方插件的 skill-creator 和此版本现在会以几乎相同的描述同时出现在技能列表中，因此未来的会话将在两者之间随机路由。用一两句话告知用户这一情况，然后提供以下选项（未经用户同意，绝不要擅自执行）：
  1. **推荐**——运行 `scripts/setup_supersede_hook.sh install`。它会将一个小型的、可自检的 SessionStart 钩子复制到用户的 Claude 配置中，并在 `settings.json` 中注册该钩子（同时创建备份），这样未来每个会话都会确定性地将技能相关工作路由到此版本。可通过 `scripts/setup_supersede_hook.sh uninstall` 撤销；当明确按名称调用官方插件时，它仍可正常使用。在未安装官方插件的计算机上，安装程序会拒绝安装任何内容，因此绝不会留下无用的钩子。
  2. 另一种选择——`claude plugin disable skill-creator@claude-plugins-official`（可通过 `enable` 撤销），它会将官方条目完全移出技能列表，从而消除歧义。

如果钩子已经安装（`scripts/setup_supersede_hook.sh status` 显示 SessionStart 条目已存在），则静默跳过以上所有内容。

同一套机制也适用于用户创建的技能：当他们的技能有意与已安装的某个技能重叠时，使用 `scripts/generate_supersede_kit.py` 为他们生成一个工具包——请参阅“现有方案调研”下的“共存与优先级”以及 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。

### 使用 AskUserQuestion（关键——请务必阅读）

**在每个决策点都要积极使用 AskUserQuestion 工具。** 当存在结构化选项时，不要在对话中提出开放式文本问题。这是你能带来的最重要的用户体验改进——用户往往同时处理多个窗口，而且可能已经有 20 分钟没有查看此对话。

**每个 AskUserQuestion 都必须遵循以下结构：**

1. **重新建立上下文**：说明技能名称、当前阶段以及刚刚发生了什么（1-2 句话）。用户可能已经切换去处理其他事情。
2. **简化说明**：用通俗语言解释需要做出的决定。不要使用函数名称或内部术语。说明它能做什么，而不是它叫什么。
3. **给出建议**：先给出你的推荐，并用一句话说明理由。如果选项涉及工作量，请同时展示两种尺度：`(human: ~X min / Claude: ~Y min)`。
4. **提供选项**：提供 2-4 个具体的、带字母编号的选项。每个选项都应是一项明确的操作，而不是抽象概念。

**规则：**
- 每个问题只包含一个决策——绝不要把不相关的选择合并在一起
- 提供退出路径（AskUserQuestion 中始终隐含“其他”选项）
- 接受用户的选择——可以提示其中的权衡，但绝不要拒绝继续执行
- 如果答案显而易见且不存在权衡，则跳过提问（直接说明你将采取的操作）
- **如果问题超时且没有得到回答（用户离开了键盘），既不要停滞不前，也不要擅自推进涉及偏好或范围的决策。** 先完成不会产生副作用的基础工作——编辑前快照、清单整理、评估用例收集、只读审计/健康检查——并将需要判断的事项（重构方向、删除哪些内容、是否继续）留待用户回来后决定。然后明确说明你已经完成了哪些工作，以及哪些事项正在等待用户决定。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话可能已经包含用户希望沉淀为技能的工作流（例如，他们说“把这个做成一个技能”）。如果是这样，请先从对话历史中提取答案——使用过的工具、步骤顺序、用户所做的修正，以及观察到的输入/输出格式。用户可能需要补充缺失信息，并且应在进入下一步之前进行确认。

**来源清单——始终在起草前完成，并遵守授权边界。** 盘点当前对话以及存在重叠的现有文档/技能（参见下文的“既有成果调研”）。更早的本地会话 JSONL 文件属于独立的私有来源：除非用户明确要求挖掘历史记录，或在你解释将读取哪些内容后明确批准使用该来源，否则不要打开或解析这些文件。如果获得批准，只能通过对话挖掘工作流中的脱敏提取流程纳入相关的先前会话；绝不要将原始对话记录加载到你自己的上下文中。如果未获批准，则继续基于当前对话和现有项目来源开展工作，不要把缺失的历史记录视为阻碍。

在挖掘对话（或会话记录）时，要盘点**两类资产——它们会存放在不同位置**。*知识*——端点、参数、陷阱、决策规则——会成为 SKILL.md 中的指导内容或放入 `references/`。*会话中不得不编写的代码*——辅助脚本、注入的代码片段、渲染器、一次性模板——则是 `scripts/` 的候选内容：如果本次会话编写了这些代码，那么下次调用时就不得不重新编写，因此应对其进行参数化、清理并打包。一份先前的提炼结果保留了经过润色的文字，却遗漏了可复用的辅助工具；一般经验是要同时关注知识→参考资料和代码→脚本这两条渠道。

当源材料是*过去的*会话转录记录（Claude Code 项目目录下的 JSONL 文件），而不是当前实时对话时，不要将它们加载到你自己的上下文中——大型转录记录可能会耗尽上下文窗口并导致会话丢失。应改为将提取工作委派给子代理，并明确指示其使用脚本逐行解析、截断每个提取字段，并且只返回一份提炼后的经验教训列表——原始转录记录绝不能进入主上下文。

**首先，在回答下面四个问题之前，确定这次请求的方向。** 该请求可能属于几种彼此*相反*的情况之一：构建一个新 skill / 编辑一个现有 skill / 优化 skill-creator 本身 / 或者它根本不是 skill（而是一次性任务）。方向猜错会浪费整个会话——你为“新 skill”所做的研究，并不适用于“优化这个元工具”。当措辞含糊不清时（例如，一边说“给我做一个 skill”，一边却指向 skill-creator 自身的路径），在这里调用一次 AskUserQuestion 只需花费 30 秒。下面的 wrapper-skill 分支是其中一个特殊情况；方向检查则是通用要求。

1. 这个 skill 应该让 Claude 能够做什么？
2. 这个 skill 应该在何时触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应该设置测试用例来验证这个 skill 是否有效？对于输出可客观验证的 skill（文件转换、数据提取、代码生成、固定工作流步骤），测试用例会很有帮助。对于输出具有主观性的 skill（写作风格、艺术创作、需要品味校准的报告），通常无法使用断言——但“没有断言”并不等于“没有验证”。其验证路径按成本由低到高依次为：
   - **历史任务重放**：重新运行一个该 skill 过去实际处理过的提示词，分别使用旧版和新版 skill，并根据本次变更涉及的具体规则比较输出（“新输出是否真的遵循了此次更新引入的词元 / 标题语法？”）。成本低，并且能够发现“规则虽然写进去了，但没有任何地方读取它”的问题。
   - **将生产环境作为评估**：承认真正的测试是用户下一次实际使用——然后将反馈闭环明确化：此后用户的每一次纠正都应作为一个事件回写（写入该 skill 自身的“迭代/活文档”章节），每一次认可都应成为语料材料。一个没有这种回写习惯就发布的品味型 skill 不会改进；养成这种习惯后，它即使从不运行正式评估，也会逐渐收敛。**而当该 skill 的输出是某种会持续运行的东西——守卫、监控器、定时任务、钩子——它自身的遥测数据就是评估数据，其中信号最强的记录是第一次误报。** 用户纠正的前提是用户注意到了问题并愿意反馈；而已部署的机制会主动报告自身情况，往往一天之内就会出现信号，误报则是这种报告中最尖锐的形式，因为它证明了你写下的某条规则是错误的，而无论重新阅读多少遍都无法发现这一点。把第一次误报当作一次预定的评估结果，而不是恼人的意外：在断定机制行为异常之前先检查它，因为更有可能发现的是，*指令*写得过于绝对。（真实案例：某个 skill 规定了一项失败时高声告警的检查；部署后的检查在夜间对一个完全健康的状态触发了一次，而修复方式是纠正该 skill 中过于绝对的句子——没有人投诉，是遥测数据发现了问题。）
   - 对于视觉输出，采用**渲染 + 人工审查**（即该 skill 自身的视觉质量检查关卡），绝不要用假装能够衡量美感的 grep 断言。**而且，用于验证的渲染器必须与交付物实际使用时所依赖的引擎相同**——方便安装的任何预览器都不能作为替代品。如果缩略图生成器的布局引擎与目标应用不同，它会悄无声息地*隐藏*你正在寻找的那些缺陷；在错误的引擎上得到绿色验证结果，比完全不做验证更糟，因为它会带来虚假的信心。真实案例（2026-07）：一个 .docx 文件通过 macOS Quick Look 缩略图进行了“视觉验证”，但该工具无法复现两端对齐文本的拉伸效果；用户一用 Word 打开文档，就看到其中的信息块被完全撑散。修复方式是安装与 Word 兼容的引擎（LibreOffice），将文件转换为 PDF，逐页栅格化，然后阅读每一页。引擎必须匹配，否则验证只是表演。**这一原则不仅适用于渲染器，也适用于所有验证工具**——解析器、代码检查器、验证器：它必须与生产环境共享同一种实现，否则它给出的绿色结果毫无意义。第二个案例具有相同的模式：一位作者试图在源文件阶段检查一种会破坏最终文档的标记模式，但使用的却是与生产工具链所用实现*不同*的 markdown 实现——它将全部三个已知有问题的输入都解析为完全正常，因此任何基于它构建的预检查都会悄无声息地放过所有问题。诚实的结论是，这个特定缺陷只有在生产工具运行后才能检测到，因此检查应该放在那里。**当没有任何可用工具与生产环境共享同一种实现时，应明确说明在该阶段无法执行这项检查——不要构建一个只会产生虚假绿色结果的检查。**
   根据 skill 类型建议合适的默认选项，但由用户决定。

从对话历史中提取答案（或询问问题 1-3）后，使用 **AskUserQuestion** 确认技能类型和测试策略：

```
Creating skill "[name]" — here's what I understand so far:
- Purpose: [1-sentence summary]
- Triggers on: [key phrases]
- Output: [format]

RECOMMENDATION: [Objective/Subjective/Hybrid] skill → [suggested testing approach]

Options:
A) Objective output (files, code, data) — set up automated test cases (Recommended if output is verifiable)
B) Subjective output (writing, design) — qualitative human review only
C) Hybrid — automated checks for structure, human review for quality
D) Skip testing for now — just build the skill and iterate by feel
```

这一前置分类决定了后续的整个评估策略。此处判断正确，可以避免之后浪费精力。

### 扩展还是创建检查——在任何专门分支之前运行

下面三个专门工作流都以“**不要**继续阅读下文章节”结尾，而 *Prior Art Research* 恰好位于它们之后。**这种顺序只是版面编排顺序，而不是执行顺序。** 扩展还是创建的判断适用于每个分支；跳过此判断，恰恰会导致会话最终交付一个与已安装技能重复的技能。

因此，在进入包装器技能／对话挖掘／产物语料库分支之前，先回答一个问题：**是否已经存在一个应当包含此能力的技能？**

**发现根目录，不要凭记忆回想。** 手工维护的安装位置列表正是那种会过时的产物，而被你遗漏的根目录正是最终会带来麻烦的那个。

**搜索文件，而不是名为 `skills` 的目录。** 技能目录以*技能*命名（`skill-creator/`、`<suite>/<skill>/`），因此源代码仓库、市场克隆目录和插件缓存中可能根本没有名为 `skills` 的目录——搜索该名称会悄无声息地跳过它们，同时看上去却像是正常执行了。每个技能都有一个 `SKILL.md`；这是与目录布局无关的定位依据。

```bash
# 1) discover
find ~ -type f -name SKILL.md -not -path '*/node_modules/*' -not -path '*/.git/*' > /tmp/all-skills.txt

# 2) VERIFY COVERAGE BEFORE TRUSTING IT — `2>/dev/null` and permission denials hide gaps
#    silently, which is exactly how a sweep reports "nothing found" from a root it never
#    entered. A 0 on any line you expect means the search did not go there:
for r in '/.claude/skills/' '/plugins/marketplaces/' '/plugins/cache/' '/.claude-profiles/'; do
  printf '%6s  %s\n' "$(grep -c "$r" /tmp/all-skills.txt)" "$r"
done
# ...and grep for your own skill source repos by path; they must appear too.

# 3) filter by capability VOCABULARY, not by skill name — in every language the target
#    skill might be written in (a skill whose body is Chinese will not match English terms):
xargs grep -li -e '<domain-term>' -e '<域内术语>' < /tmp/all-skills.txt
```

预计第 3 步需要几秒钟，并且仍会返回多于所需的结果；应使用该能力特有的术语而不是宽泛术语来缩小范围（`chart` 会匹配所有内容，而 `stacked bar` 不会）。

这次检索覆盖到的根目录——也是凭记忆列清单时通常会遗漏的地方——包括：技能源代码仓库（一个 `claude-code-skills` 检出目录及其任何 `-pro` 同级目录）、`~/.claude/plugins/marketplaces/` 和 `~/.claude/plugins/cache/`（通过市场安装的套件——源代码仓库中没有任何迹象表明它们在那里）、`~/.claude/skills/`、`~/.codex/skills`、`~/.agents/skills`、各配置文件专属的配置主目录（`~/.claude-profiles/<name>/`），以及——完全没有任何线索指向的那个地方——**每个项目自己的 `.claude/skills/`**。步骤 2 让这成为一项经过你验证的结论，而不是你沿袭来的说法。

**项目级技能在结构上是不可见的。** 它们位于某个不相关项目的工作树中，因此不会出现在任何市场、任何全局技能列表或任何源代码仓库清单里；你在规划新技能时通常会打开的内容，没有任何一处会提到它们。真实案例（2026-07）：某次会话为一个领域构建了全局技能，彻查了源代码仓库、全局目录和其他智能体的目录，什么都没找到，于是便发布了。后来搜索对话历史时，发现了一个恰好针对该领域的成熟项目级技能，它已有一个月历史，就位于某个项目的 `.claude/skills/` 中——其中包含新技能所欠缺的八条规则，包括一条用户亲自指定的规则。除了项目级位置之外，所有根目录都检查过了，而扫描结果仍十足确信地报告“没有先例”。

**当重叠的内容确实是某个不相关项目中的项目级技能时该怎么做**——也就是上述教训会让你面对的情况，同时也是下面三个要点未涵盖的情况：你无法将同级技能添加到一个根本不存在的套件中，而“扩展它”则意味着编辑某个不相关项目的工作树。已验证有效的做法是：**将其中的规则收纳到你正在构建的技能中，然后在获得所有者同意后停用项目本地技能**——它是基于真实工作编写的，因此应将其视为更成熟的来源，并以它为方向进行协调。停用他人正在使用的技能应由所有者决定，而不应成为你的构建过程所产生的副作用。

这句话遗漏了四件事，其中每一件都会让你受阻：

- **“以它为方向进行协调”是一项可以反驳的推定，而不是规则。** 有两种常见的例外：项目技能可能已经*过时*（规则是在数月前针对一个后来发生变化的系统编写的），也可能具有*项目特定性*（规则只在该项目的约束下成立——原封不动地导入它们会让你的技能变得狭窄，而本文档其他部分明确要求你不要这样做）。收纳来的规则是另一位作者的记忆，因此要按照准则 #1 对写入技能的任何内容所提出的要求，**重新验证每一条规则**。
- **“停用”需要一种机制，而它的第一步并不是你下意识会采用的那一步。** 按以下顺序执行：

  1. 在 grep 技能的*引用*之前，先用 **`find` 查找技能的*本体***。同一技能通常在同一仓库中存在多个副本——`.claude/skills/<name>/` 和 `.agents/skills/<name>/` 都会由不同工具从同一个工作树中加载。Grep 回答的是“谁提到了它”；只有 `find` 才能回答“它究竟有多少份”。
     ```bash
     find <project> -type d -name '<skill-name>' -not -path '*/.git/*'
     ```
     **不要将技能自身的名称放进 `--exclude-dir`**（它按基本名称进行匹配，因此会隐藏每个同名目录，包括你尚未找到的副本——参见准则 #6 中的工具规则）。真实案例（2026-07）：某次停用操作正是这样做的，它修复了找到的全部五处引用，却在 `.agents/skills/` 下遗留了第二个完整副本——该副本由 git 跟踪，没有停用标记，是一个缺少最新规则的陈旧快照——另一个工具仍会将其作为有效技能加载。
  2. 在删除任何内容之前，**验证从旧位置实际能够访问新位置**——你刚推送的市场技能在市场更新且插件安装之前并未完成安装，而先停用旧技能会产生一个两者皆不存在的空窗期：
     ```bash
     claude plugin marketplace update <marketplace>   # your push is not their cache
     claude plugin install <skill>@<marketplace>
     find -L ~/.claude/plugins/cache -path '*<skill>*' -name '*.md'   # -L: installs are often symlinks
     ```
     `-L` 并非可选项——插件缓存经常通过符号链接指向源代码仓库，而不带该选项的 `find` 会报告文件缺失（参见准则 #6 中的工具规则）。
  3. **然后**使用 grep 查找引用，并将仍然有效的引用重新指向新位置。区分**有效指令**（技能列表、交叉引用，或告诉下一个智能体应使用什么的交接文档）和**历史记录**（例如决策日志中写着“我们在日期 X 发布了此内容”的条目）——重写后者会为了修复一个它并不存在的问题而破坏审计轨迹。
  4. **然后**将每个本体替换为 `superseded by <skill>` 存根，而不是直接删除，并确保每个副本的存根在字节层面完全相同。**保留 YAML frontmatter**——缺少它的 `SKILL.md` 可能无法加载，而不是以提供有效信息的方式失败——但要重写 `description`，使存根明确宣告自身已经停用，而不是继续宣传旧触发条件；否则，它仍会赢得自己已不再服务的路由。正文只需要说明两点：能力迁移到了哪里，以及一行迁移原因。
- **使用下方的所有权测试来识别所有者**（该测试同样适用于此处：项目级技能没有 `marketplace.json`，但项目的 `git remote` 仍会告诉你它属于谁）。当所有者就是正在与你交谈的人时，只需通过一次 `AskUserQuestion` 即可获得“同意”。**当无法联系到所有者时，只收纳规则——不要停用**（这会让两个技能都保持有效并争夺触发条件，与所有者拒绝停用后的最终状态相同——参见下方的“共存与优先级”）。
- **如果所有者拒绝停用它**，那么现在会有两个技能争夺同一个触发条件；这是下方所述的“共存与优先级”问题，而不是失败。

**按能力词汇搜索，而不是按技能名称搜索。** 该项目技能无法通过搜索新技能的标题名称匹配到；它是通过正文中的领域术语匹配到的。使用 grep 在候选根目录中搜索新技能将处理的*概念*。

如果发现重叠：

**判断适用哪一条——这是谁的技能？** 文件系统中的匹配结果并不包含所有权信息。读取市场的 `.claude-plugin/marketplace.json` 中的 `owner` 字段，或在所属仓库中运行 `git remote -v`；位于 `~/.claude/plugins/marketplaces/` 下的匹配项同样可能只是安装回你自己机器上的*自有*市场。项目级技能没有 `marketplace.json`，但其项目的 `git remote` 可以回答同一个问题。

探测操作会错误判断或无法判断以下两种情况，因此在信任结果之前应先检查它们：**分叉仓库**显示的是你自己的远程仓库，但内容属于其他人——应将其视为第三方内容，因为他们的上游改进仍然无法传递给你。而当**既没有 marketplace.json，也没有远程仓库**时（仅存在于本地的项目、手动复制到全局技能目录中的技能），探测操作不会给出否定结果，而是完全没有结果：**询问所有者，不要猜测**。

- **重叠的是第三方技能**（市场套件、官方插件）：**不要重新实现其能力。** 编写一个能够正确驱动它的*轻量增量层*——记录你遇到的陷阱、正确的调用方式、经过验证的辅助脚本——并**使用带命名空间的名称引用它**。将其他人的引擎克隆到你的包中是代价高昂的错误：他们的升级将无法传递给你，而两个副本会在不知不觉中逐渐产生差异。
- **重叠的是你自己的技能**：扩展它，或在其现有套件中添加一个同级技能。创建一个针对相同触发条件展开竞争的独立技能，对任何人都没有帮助。**例外：**如果它位于一个*不相关项目*的工作树中，则上述两种做法都不适用——请参阅前面的项目级情况。
- **某个相关技能已经指向你正在填补的空缺**（例如，其描述中写着“对于 X，请使用 Y”）：构建完成后，闭合这个环路——更新该指向，否则你就留下了一个悬空引用。

只有在不存在任何重叠时，才构建独立技能。

**为什么这项检查值得放在最前面：**在 2026-07 的一次真实会话中，有人花了一整天让一个第三方 docx 引擎生成正确的中文商务文档，之后直接进入包装技能分支——这会径直跳过现有方案研究。它原本即将交付的是一个重新承载该引擎能力的全新技能。正确的形态应该是一条**三层引用链**：保持第三方引擎不变 → 创建一个轻量增量技能，其中包含正确用法和经过验证的生成器脚本 → 由领域工作流技能调用该增量技能。在最终落地之前，用户不得不两次指出问题，其中第二次纠正更加尖锐：*“不要额外复制一份——在他们的技能之上编写正确用法，并引用他们的技能；这才是技能即代码的含义。”*

### 验证深度路由器（在选择任何工作流之前运行）

在进入通用或专用工作流分支之前，选择**能够证伪变更后行为的最低层级**。应按故障影响面分类，而不是按行数分类：一条发生变更的破坏性命令，其层级可能高于大篇幅的文字清理。测试前，说明所选层级及一句话理由。专用工作流可以替换不兼容的机制，但绝不能绕过层级选择，也不能在不作说明的情况下降低所需的严谨程度。

| 层级 | 适用情形 | 必需证据 | 默认情况下不要添加 |
|---|---|---|---|
| **1 — 定向验证** | 这是一个现有技能；没有新增或实质性变更任何能力、触发器类别、工作流分支、输出契约、依赖项、权限或外部写入行为；并且编辑恰好属于以下一种：(a) 仅修正拼写/格式，不改变行为；(b) 对文档/配置中的事实进行修正，且该事实可由直接权威来源判定；或 (c) 有限范围的实现修复，用于恢复明确的现有契约，**并且**修复后的行为由确定性的回归检查覆盖。可能改变智能体行为的澄清不属于第 1 层级 | 对这三种情况，都要运行 `quick_validate`、检查差异，并完成现有技能迁移门禁。然后仅使用对应的证据：(a) 精确回读/格式检查；(b) 权威事实及其有限范围的检查；(c) 明确的现有契约及确定性回归测试。仅当纪律 #5 中的规则/契约/数量阈值被触发时，才增加其中要求的一位全新审阅者 | 智能体行为回放、配对运行、基线、评分器、基准测试、查看器、评估文件 |
| **2 — 行为抽样** | 以下条件全部成立：这是一个现有技能；变更会影响智能体行为；确定性检查无法完全判定；没有引入任何新增或实质性变更的能力、触发器类别、工作流分支、输出契约、脚本行为、依赖项、权限或外部写入；并且可以使用 1–2 个具名示例及明确的验收标准覆盖全部变更后行为 | 仅运行这 1–2 个有代表性的启用技能回放，以及有限范围的确定性检查和纪律 #5 要求的一次全新上下文审阅 | 基线、配对扇出、方差分析、基准测试、查看器或评估文件。只要请求其中任何一项，就应将该工作重新分类为第 3 层级 |
| **3 — 完整评估** | 以下任一条件成立：任何新技能；任何新增或实质性变更的能力；大范围重写或方法论扩展；触发器/描述优化；新增或实质性变更的工作流分支、输出契约、脚本能力、依赖项或权限；高风险自动化或外部写入；评估需要覆盖 3 个以上不同提示类别的证据、重复试验/方差，或需要在实质不同的方法之间进行选择；或者用户明确要求 A/B、基线、基准测试或查看器证据。仅凭主观判断，不会将原本范围有限的第 2 层级变更升级 | 对于通用工作流，运行下述完整的配对流水线：真实案例、启用技能版本 + 基线、断言、评分、汇总基准测试、分析人员审查和查看器。专用工作流只能替换其明确标记为不兼容的机制；运行其完整验证协议以及所有兼容的第 3 层级步骤，并记录其替换了哪些内容 | 无——这是有意采用的重型路径 |

当较低层级暴露出未解决的行为或相互矛盾的证据时，应升级层级。用户要求取消评估或降低评估级别时，覆盖的是**执行授权，而不是分类**：立即停止已经启动的成对评估代理、基线测试、评分器、聚合以及查看器相关工作。Tier 3 变更仍然是 Tier 3；应将其所需的重度证据记录为用户放弃或未完成，而不是把较低层级的证据重新标记为通过。仅继续收集用户仍然授权的证据，并且不要声称已完成完整的 Tier 3 验证。不得取消第 5 条纪律所要求的单个全新上下文审查者（当其规则、契约或数值阈值被触发时），也不得取消任何为防止破坏性影响或外部影响所必需的安全门控。机械式的现有技能迁移审计、公开技能净化以及任何特定领域的安全门控也保持独立于此路由器。

### 专用工作流：第三方 CLI 工具的包装器技能

在采用通用技能创建流程之前，请先检查走到当前阶段的会话是否实际上应改用**包装器技能**工作流。包装器技能是一种配套技能，用于安装、配置、诊断和修复预先存在的第三方 CLI 工具或技能包——即由他人编写、而用户刚刚在一个会话中设法使其能在自己的机器上正常工作的代码。

适用信号（任意两个同时出现即可）：

- 用户一直在当前对话中安装某个工具——下载 `.zip`、运行 `npx` / `pip install` / `brew install`，或处理官方安装程序。
- 会话中出现了真实、具体的错误消息，并且用户和 Claude 已经为这些错误找到了具体的修复方案（编辑文件、添加标志、绕过别名）。
- 用户说了类似“把这个整理成一个技能”“把这个保存为包装器技能”“这样其他人就不必再经历这一遍了”“把这次 session 做成一个 skill”的话。
- 用户明确提到某个第三方工具的名称，并希望其他代理或其他人无需承担其刚刚付出的学习成本，就能使用该工具。

不适用信号（应改用上面的通用工作流）：

- 用户想为某个准备从头编写的内容创建技能。
- 会话进行得很顺利——没有值得捕获的实际障碍。
- 该技能将包装用户拥有或控制的服务（这是用户自己的代码；应编辑源代码，而不是进行包装）。
- 所谓的“工具”实际上是一种方法论或工作流，不涉及安装任何二进制文件或软件包。

当包装器技能工作流适用时，保留上面选择的验证层级。创建包装器就是创建新技能，因此属于 Tier 3。**不要**继续阅读下面的通用创作章节；直接跳转到 [`workflows/wrapper-skill/workflow.md`](workflows/wrapper-skill/workflow.md)，并端到端遵循该工作流，包括其中的验证协议。这是一个**回顾式提炼**工作流——其任务是从当前对话中挖掘安装流程、已修复的缺陷以及已做出的设计决策，并将挖掘结果转化为一个完整、自包含的包装器技能，使其他用户能够安装并从中受益，而无需重历这段调试过程。

包装器技能工作流有其自身的架构契约、代码模板和第 3 级验证协议——它会取代不兼容的通用测试用例机制，因为它的输出是用户的安装状态，而不是一个可以轻松断言的文件；这并不意味着降低工作标准。运行所有兼容的通用第 3 级步骤，并记录专用协议取代了哪些机制。规范的参考实现是 `ima-copilot` 技能（位于 daymade/claude-code-skills 仓库的根目录——此前，当此技能被移入一个套件时，这里的裸相对链接就曾失效，恰如下面的跨技能引用规则所警告的那样），它是 Tencent IMA 技能的包装器，由使用这一确切工作流的真实会话提炼而成。

### 专用工作流：从对话历史中充实技能

在采用通用技能创建流程之前，先检查当前会话是否实际要求将**过往对话提炼为技能**。当用户已经在多个 Claude Code / Codex 会话中调试、设计或探索某个主题，并希望将积累的知识转化为可复用的 `references/` 时，此工作流非常有用。

适用信号（满足任意一项即可）：

- 用户表达了类似“从我的聊天历史中挖掘模式”“将这次对话转化为技能参考”“将我们学到的内容提炼到技能中”“根据我的对话充实这个技能”或“把这次对话沉淀到 skill 里”的诉求。
- 当前会话明确是在从近期的多轮调试或设计会话中提取经验。
- 用户希望根据已经真实发生过的对话，为现有技能添加一个 `references/` 文件。
- 目标技能已经存在，目标是用从对话中挖掘出的知识来充实它，而不是从头构建。

不适用信号（应改用上面的通用工作流）：

- 用户正在根据单个提示或想法创建一个全新的技能。
- 用户希望为刚刚安装的第三方 CLI 工具创建包装器（应使用上面的包装器技能工作流）。
- 没有可挖掘的本地对话历史，也没有可处理的会话记录导出文件。
- 挖掘出的内容是一次性的个人笔记，应存放在 `memory/` 中，而不是可复用的参考文件中。
- 源材料是一批已经完成且获得用户认可的产物，而不是对话——应使用下面的产物语料库提炼工作流。

当对话挖掘工作流适用时，请保留上面选择的验证级别。新建的挖掘型技能属于第 3 级；对现有技能进行充实时，只有在满足所选级别的能力边界时，才维持该级别。**不要**继续阅读下面的通用编写章节；请跳转到 [`workflows/conversation-mining/workflow.md`](workflows/conversation-mining/workflow.md)，并端到端遵循该工作流，包括其中的验证协议。这是一个**回顾式提炼**工作流：它会发现本地 Claude Code 项目会话、Codex 会话记录和命令历史，对其进行脱敏，将其划分为适合代理处理的分块，运行挖掘代理，并在验证后将得到的候选参考内容纳入目标技能的 `references/` 中。

对话挖掘工作流有其自身的架构契约、智能体提示词、模板和验证协议。该协议实现了所选层级的专门机制；请执行所有兼容的通用步骤，并记录任何替代操作。它是将真实对话历史转化为技能可复用知识库的规范方式。

### 专用工作流：从获批成果语料库中提炼用户偏好

在采用通用流程之前，请检查当前会话是否要求**从一批用户认可的成品中提取用户的真实偏好**——例如获批的 HTML 报告页面、生成的文档、设计作品。这是不同于上述两种来源的第三种提炼来源：其材料是**成果，而非对话**，其输出是**可执行的品味**（明确的原则、量化参数、词汇），而非知识或安装修复方案。

适用信号（满足任意一项即可）：

- 用户列出成品并表示“这些都是我认可的样例”/“你来学到底什么是我想要的”/“从这些获批样例中提取我的偏好”。
- 某个品味校准技能（报告生成器、文档样式工具、幻灯片构建器）拥有一个持续扩充的获批样例语料库，并且用户要求让该技能从中*学习*，而不只是建立索引。
- 用户抱怨之前的更新“只加了示例”——只是对样例进行了编目，却没有改变技能行为。

不适用信号：源材料是对话/纠正内容，而非用户认可的成果（请使用对话挖掘）；样例并未得到用户本人的认可（认可是准入门槛——请先询问）。

适用时，请保留上面选定的验证层级，然后跳转至 [`workflows/artifact-corpus-distillation/workflow.md`](workflows/artifact-corpus-distillation/workflow.md)，并遵循其中的验证协议。新建的语料库衍生技能属于第 3 级；为现有技能添加实质性的新决策能力也属于第 3 级。该专用协议实现了所选层级的语料库机制，并且不会降低其层级；请执行所有兼容的通用步骤，并记录任何替代操作。其核心纪律也适用于任何向现有技能添加材料的情况：**编目 ≠ 提炼**——在语料库表格中登记样例并不会改变技能下一次运行的行为；对于每项新增内容，都要问“*这是否改变了一条决策规则？*”，如果所有已写入内容的答案都是否定的，就不要宣布提炼会话已经完成（方法论案例 15）。该工作流的主干是：通过脚本提取并对所有成果进行量化比较（每种模式至少需要 3 个成果作为支撑，对每个声称的常量核查例外列表）→ 基于证据锚点进行分层归纳 → 写入决策规则层（将不变量与依赖语域的变量分开）→ 独立完整性审计（常设纪律 #5）→ 回归审计。

### 既有方案研究（不得跳过）

用户的私有方法论——其领域规则、工作流决策、竞争优势——正是技能价值所在。任何公共仓库都无法提供这些内容。但如果已经存在成熟工具，用户就不应该浪费时间重新发明基础设施（API 客户端、身份验证流程、速率限制）。既有方案研究旨在为基础设施层寻找构建模块，使技能能够专注于编码用户独有的方法论。

**这是两个维度，不要混为一谈。** 本节寻找的是*基础设施*层（可复用的工具 / MCP / 库 / 现有 Skill）。*方法论*层有两个自己的输入：用户的私有优势（仅属于用户，无法检索）**以及该领域既有的最佳实践 / 科学知识；按照常设原则 #3，你默认应将后者检索到上下文中。** 找到合适的工具并不意味着第二项工作已经完成——一个采用了图表库却从未吸收 Cleveland/Bertin 理论的可视化 Skill，其能力上限仍然受限于你的预训练。两者都要做。

**按以下顺序搜索这些渠道**（使用子代理并行搜索 4-8）：

| 优先级 | 渠道 | 搜索内容 | 方法 |
|----------|---------|---------------|-----|
| 1 | **对话历史** | 用户经过验证的工作流、已验证的 API 模式、调试期间做出的修正 | 在近期对话中 grep 服务/API 名称 |
| 2 | **本地文档与 SOP** | 用户的私有方法论、操作手册、现有 Skill | 搜索项目目录、`~/.claude/CLAUDE.md`、`~/.claude/references/` |
| 3 | **已安装的插件与 MCP** | 已集成的工具 | 检查 `~/.claude/plugins/`，解析 `installed_plugins.json`；检查 `~/.claude.json` 中已配置的 MCP 服务器 |
| 4 | **skills.sh** | 社区 Skill | `WebFetch https://skills.sh/?q=<keyword>` |
| 5 | **Anthropic 官方插件** | 官方/合作伙伴插件 | `WebFetch https://github.com/anthropics/claude-plugins-official/tree/main/plugins` 以及 `external_plugins` 目录 |
| 6 | **GitHub 上的 MCP 服务器** | 面向同一 API 的现有 MCP 服务器 | `WebSearch "<service-name> MCP server site:github.com"` |
| 7 | **官方 API 文档** | 目标服务自身的文档 | `WebSearch "<service-name> API documentation"` 或对文档 URL 使用 `WebFetch` |
| 8 | **npm / PyPI** | SDK 或 CLI 软件包 | `npm search <keyword>` 或 `curl https://pypi.org/pypi/<name>/json` |

渠道 1-3 用于发现用户自己已验证的模式和现有集成。渠道 4-8 用于寻找公共基础设施。用户的私有 SOP 始终优先——公共工具是构建模块，而不是替代品。在竞争性领域（金融、交易、专有运营）中，有价值的方法论永远不会公开。

**优先合并/扩展，而不是新建，并且要扫描每一个 Skill 根目录——不只是 `~/.claude`。** 当渠道 1-3 找到与所请求领域重叠的现有 Skill 时，通常正确的做法是扩展它或合并到其中——**但如果它位于不相关项目的工作树中，则方向相反：应从中汲取内容并纳入你正在构建的 Skill，而不是合并到它里面**（参见上文扩展还是新建检查中的项目级情形）（一个真实的“新建 Skill”任务最终变成了“让现有提取器成为新归档器的提取阶段”），而不是交付一个争夺相同触发条件的并行 Skill——两个相互重叠的 Skill 会争抢触发机会并让用户困惑。搜索时，**应发现安装根目录，而不是凭记忆罗列清单**——使用上文扩展还是新建部分中的 `SKILL.md` 全面扫描及其覆盖范围自检（搜索名为 `skills` 的目录会完全漏掉源代码仓库、市场镜像和插件缓存，因为其中的 Skill 目录是以 Skill 名称命名的）。执行覆盖范围检查，而不要只相信这句话：**每个项目自身的 `.claude/skills/`** 是凭记忆列举根目录时最容易遗漏的目录，因为该项目之外没有任何位置会引用它。用户已经安装在*任何位置*的 Skill 都是最有力的既有参考，而项目本地 Skill 往往最为成熟：它是针对真实工作编写的。

**如果发现公开的 MCP 服务器或技能，请克隆并验证——不要轻信 README：**

1. **阅读实际源代码**——许多项目的 README 十分精美，代码库却空洞无物
2. **验证身份验证方式**——它是否符合 API 的实际身份验证机制？（X-Api-Key 请求头、Bearer 或 OAuth——很多项目都弄错了）
3. **检查测试覆盖率**——零测试意味着它只是原型，而非生产级项目
4. **检查维护情况**——最后提交日期、未解决的问题数量、对错误报告的响应情况
5. **检查环境兼容性**——代理/网络假设、硬编码的 DNS/IP、区域限制
6. **检查许可证**——MIT/Apache 没有问题；GPL/SSPL 可能与专有用途冲突
7. **检查依赖规模**——庞大的依赖树会引发冲突并扩大安全攻击面

**决策矩阵：**

| 发现 | 操作 |
|---------|--------|
| 成熟的 MCP/SDK 能够处理基础设施 | **采用并在其上构建**——安装 MCP，然后将技能构建为工作流层，对用户的方法论进行编码 |
| 存在功能不完整的 MCP 或 SDK | **扩展**——将其用于基础设施，并在技能中补齐缺失部分 |
| 公开技能涵盖相同领域 | **仅将其用作结构参考**——竞争领域中的公开技能从定义上就是通用的。用户的优势在于其私有 SOP |
| **存在互补技能，可提供你正在构建的内容所需的某项子能力** | **将其打包进来**——把互补技能的自包含资源复制到你的技能包中并完成接线。不要依赖用户已预先安装该技能。请参阅下文的“互补技能” |
| 不存在任何公开实现 | **从头构建**——在编写完整技能之前，验证 API 访问模式是否有效（身份验证、端点、代理） |
| 集成成本 > 构建成本 | **自行构建**——一个由你掌控、耗时 2 小时的自定义实现，胜过存在集成阻力和上游风险的“成熟”工具 |
| 用户有意取代已安装的技能（分支版本、加固版本） | **随附取代工具包发布**——请参阅下文的“共存与优先级” |

#### 共存与优先级（有意重叠）

对于重叠问题，默认解决方案是合并到现有技能中（见上文）。但当用户*有意*发布一个与已安装技能重叠的技能时——例如官方插件的分支版本或经过加固的内部版本——技能列表中将出现两个描述相似的条目，Claude 会随机在它们之间进行路由。请按以下顺序逐步解决：如果重叠并非有意为之，则重命名；添加用于判定优先级的描述（“取代 X——当两者同时出现时，始终使用此技能”）；对于分发的分支版本，使用 `scripts/generate_supersede_kit.py` 将条件式取代工具包嵌入技能中——这是一种基于用户同意的 SessionStart 路由钩子，只会安装在确实存在竞争技能的机器上，在其他机器上会拒绝安装，并且会在任一方消失时自行禁用。有关其机制、决策表、SKILL.md 示例措辞和沙箱验证，请参阅：[references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)。此技能也使用同一工具包针对官方 skill-creator 插件进行了自用验证（请参阅顶部的“首先：共存检查”）。

**更常见的情况是：你的新技能在没有任何刻意分叉的情况下，悄然失去了对*已安装技能群体*的触发机会。** 一个技能所属的领域（图像生成、PDF 处理、仪表板）往往已经挤满了多个已安装的技能，而新技能可能会在自动路由中输给所有这些技能。因此，**请尽早验证触发情况——内容做得好并不意味着构建工作已经完成。** 初稿完成后，通过 `claude -p` 发起几条贴近实际的查询，检查新技能是否确实能够胜出；如果没有，**明确指出它输给了哪个具体的竞争技能**（不同查询往往会输给不同的技能）。然后要了解两件事：(1) **单靠正文描述并不总能在拥挤的触发槽位中胜出**——解决阶梯为：重命名 → description 决胜条件/SUPERSEDES → 手动调用 → SessionStart 路由钩子（结构性措施；会修改全局配置，因此需要用户明确同意，遵循与 `--no-verify` 相同的规范）；以及 (2) **修复方式取决于竞争技能的作者是谁**——如果竞争技能是*第三方*的 → 接受手动调用或使用路由钩子；如果竞争技能是*你自己*的 → 将它们合并/整合为一个，不要让你自己的两个技能为同一个触发条件相互争夺。（完整的解决阶梯见 [references/skill-precedence-and-coexistence.md](references/skill-precedence-and-coexistence.md)——该文件是 SSOT；此处及上文的摘要仅用于指引，请勿单独扩展。）记录所选路径（例如添加一条 "Activation" 注释，注明“手动调用，竞争技能均为第三方”），可以避免下一个会话再次对此争论不休。（方法论案例 13）

##### 互补技能（打包，而非依赖）

构建涉及某个已有互补技能领域的技能时，你有两种选择：

- **依赖它已被安装**：很脆弱——用户可能没有安装它，也可能安装了其他版本。每一次缺少依赖项的失败都可以追溯到这一选择。
- **将它打包进来**：把互补技能中自包含的资源（脚本、模板、参考文档）复制到你自己的包中，并完成接线，使你的技能能够独立运行。

**规则：如果你的技能所需的某项子能力由另一个可安装技能提供，就将它打包进来。** 这对以下内容尤其重要：
- 状态栏/UI 渲染脚本（例如 `statusline-generator` 的 `generate_statusline.sh`）
- 共享的验证/净化脚本
- 通用数据转换工具

**示例**：`claude-switch-models-setup` 管理多个 Claude Code 配置文件。每个配置文件都需要一个状态栏。`statusline-generator` 技能提供了 `generate_statusline.sh`。配置文件设置技能不会依赖用户先运行 `statusline-generator`，而是将 `statusline.sh` 打包进来，并在 `claude-profiles-init` 期间将其接入每个新配置文件。两个技能仍然可以各自独立发挥作用，但这个封装技能也能独立运行。

**反模式**：在你的 SKILL.md 中写“先运行 `other-skill` 的安装程序”。这会把依赖问题推给用户，并造成脆弱的安装顺序。应改为将其打包进来。

研究完成后，通过 **AskUserQuestion** 展示调查结果：

```
Research complete for "[skill-name]". Here's what I found:

[1-2 sentence summary of what exists publicly]

RECOMMENDATION: [ADOPT / EXTEND / BUILD] because [one-line reason]

Options:
A) Adopt [tool/MCP X] for infrastructure, build methodology layer on top (Recommended)
B) Extend [partial tool Y] — use what works, fill gaps in the skill
C) Build from scratch — nothing found matches well enough
D) Show me the detailed findings before I decide
```

如有疑问，优先采用成熟的基础设施来处理管道层，并为方法论层构建自定义逻辑——真正的价值就在这里。

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。在彻底明确这些内容之前，不要编写测试提示词。

检查可用的 MCPs——如果对研究有帮助（搜索文档、查找类似技能、查询最佳实践），并且存在可用的 subagents，则通过它们并行开展研究，否则直接进行研究。提前准备好相关背景信息，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈，填写以下组成部分：

- **name**：技能标识符
- **description**：何时触发、它的作用。这是主要的触发机制——既要包含技能的作用，也要包含应在何种具体情境下使用它。所有“何时使用”的信息都应放在这里，而不是正文中。注意：目前 Claude 有“触发不足”技能的倾向——即在技能本来有用时却不使用。为了解决这个问题，请让技能描述稍微“积极主动”一些。例如，与其写“如何构建一个简单、快速的仪表板来展示 Anthropic 内部数据。”，不如写成“如何构建一个简单、快速的仪表板来展示 Anthropic 内部数据。只要用户提到仪表板、数据可视化、内部指标，或想要展示任何类型的公司数据，即使他们没有明确要求使用‘仪表板’，也务必使用此技能。”

  **做好预算：description 存在严格的 1024 字符上限，任何超出该限制的内容都会验证失败。** 这与上面的“积极主动”建议存在直接冲突——为扩大覆盖范围而添加的每个触发短语都会消耗预算——因此应在扩展之前而不是之后进行测量：看 `len(description)`，不要凭感觉。陷阱不在初稿（初稿很少接近上限），而在于*多年后的更新*为新覆盖的范围添加触发条件：成熟的描述通常距离上限只有几十个字符，此时**添加一个触发条件就是零和操作——你必须删除一个现有触发条件来为它腾出空间。** 要有意识地做出这种权衡，并在提交中明确说明，因为悄无声息地删掉一个触发短语，实际上就是缩小了技能的触发范围，而且在它不再为某位用户触发之前，没有人会注意到。（实践中曾出现过这种情况：一次更新为新覆盖的故障模式添加了触发条件，使描述膨胀到 1280 个字符，并经过两轮压缩才降至 1003——代价是删除了三个已有的触发短语。这本应是一项明确作出的决定，而不是在与验证器周旋时才被动发现。）必须删减时，优先删除那些仍可通过同义词或同类短语覆盖其场景的短语，保留那些没有其他触发路径的短语，并记住，正文中的限定语（如“在平台 X 和 Y 上”、括号内的枚举）通常比独立的触发短语更适合删除——正文内容可以从主体重新推导出来，而触发短语则不能。
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### Skill 编写指南

#### Skill 的结构

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### YAML 前置元数据参考

除 `description` 外，所有前置元数据字段均为可选。请在 `---` 标记之间使用以下字段配置 Skill 的行为：

```yaml
---
name: my-skill
description: What this skill does and when to use it. Use when...
context: fork
agent: general-purpose
argument-hint: "[topic]"
---
```

| 字段 | 必填 | 说明 |
|-------|----------|-------------|
| `name` | 否 | Skill 的显示名称。如果省略，则使用目录名称。只能包含小写字母、数字和连字符（最多 64 个字符）。 |
| `description` | 建议填写 | Skill 的功能及其适用时机。Claude 使用此字段决定何时应用该 Skill。如果省略，则使用 Markdown 内容的第一段。 |
| `context` | 否 | **设置为 `fork`，以便在派生的子代理上下文中运行。** 请参阅下文的“内联与派生：关键决策”——选择错误会导致 Skill 无法正常工作。 |
| `agent` | 否 | 设置 `context: fork` 时要使用的子代理类型。可选值：`Explore`、`Plan`、`general-purpose`，或 `.claude/agents/` 中的自定义代理。默认值：`general-purpose`。 |
| `disable-model-invocation` | 否 | 设置为 `true`，以阻止 Claude 自动加载此 Skill。适用于希望通过 `/name` 手动触发的工作流。默认值：`false`。 |
| `user-invocable` | 否 | 设置为 `false`，以将其从 `/` 菜单中隐藏。适用于不应由用户直接调用的后台知识。默认值：`true`。 |
| `allowed-tools` | 否 | 预先批准的工具列表。**建议：不要设置此字段。** 省略此字段可让 Skill 在用户权限设置的约束下拥有完整的工具访问权限。设置此字段会不必要地限制 Skill 的能力。 |
| `model` | 否 | 此 Skill 激活时要使用的模型。 |
| `argument-hint` | 否 | 自动补全期间显示的提示，用于指明预期参数。例如：`[issue-number]` 或 `[filename] [format]`。 |
| `hooks` | 否 | 作用域限定于此 Skill 生命周期的钩子。例如：`hooks: { pre-invoke: [{ command: "echo Starting" }] }`。请参阅 Claude Code Hooks 文档。 |

**特殊占位符：** Skill 内容中的 `$ARGUMENTS` 会被替换为用户在 Skill 名称后提供的文本。例如，`/deep-research quantum computing` 会将 `$ARGUMENTS` 替换为 `quantum computing`。

##### 内联与派生：关键决策

**这是设计 Skill 时最重要的架构决策。** 选择错误会在不发出提示的情况下破坏 Skill 的核心能力。

**关键限制：子代理无法生成其他子代理。** 使用 `context: fork` 运行的 Skill（作为子代理）无法：
- 使用 Task 工具生成并行探索代理
- 使用 Skill 工具调用其他 Skill
- 编排任何多代理工作流

**决策指南：**

| 你的技能需要…… | 使用方式 | 原因 |
|------------------------|-----|-----|
| 编排并行代理（Task 工具） | **内联**（无 `context`） | 子代理无法生成子代理 |
| 调用其他技能（Skill 工具） | **内联**（无 `context`） | 子代理无法调用技能 |
| 为外部 CLI 运行 Bash 命令 | **内联**（无 `context`） | 在主上下文中拥有完整的工具访问权限 |
| 执行单一的聚焦任务（研究、分析） | **分叉**（`context: fork`） | 上下文隔离，执行过程清晰 |
| 提供参考知识（编码规范） | **内联**（无 `context`） | 指南可丰富主对话的上下文 |
| 可被其他技能调用 | **分叉**（`context: fork`） | 必须作为子代理才能被生成 |

**示例：编排器技能（必须内联）：**
```yaml
---
name: product-analysis
description: Multi-path parallel product analysis with cross-model synthesis
---

# Orchestrates parallel agents — inline is REQUIRED
1. Auto-detect available tools (which codex, etc.)
2. Launch 3-5 Task agents in parallel (Explore subagents)
3. Optionally invoke /competitors-analysis via Skill tool
4. Synthesize all results
```

**示例：专家技能（适合分叉）：**
```yaml
---
name: deep-research
description: Research a topic thoroughly using multiple sources
context: fork
agent: Explore
---

Research $ARGUMENTS thoroughly:
1. Find relevant files using Glob and Grep
2. Read and analyze the code
3. Summarize findings with specific file references
```

**示例：参考技能（内联，无任务）：**
```yaml
---
name: api-conventions
description: API design patterns for this codebase
---

When writing API endpoints:
- Use RESTful naming conventions
- Return consistent error formats
```

##### 可组合的技能设计（正交性）

技能应当保持**正交**：每个技能只处理一个关注点，并通过组合协同工作。

**模式：编排器（内联）调用专家（分叉）**
```
product-analysis (inline, orchestrator)
  ├─ Task agents for parallel exploration
  ├─ Skill('competitors-analysis', 'X') → fork subagent
  └─ Synthesizes all results

competitors-analysis (fork, specialist)
  └─ Single focused task: analyze one competitor codebase
```

**可组合性规则：**
1. **调用方**必须采用内联方式（无 `context: fork`），才能使用 Task/Skill 工具
2. **被调用方**应使用 `context: fork`，以便在隔离的子代理上下文中运行
3. 每个技能只承担单一职责——不要将编排与执行混在一起
4. 通过参考资料（例如检查清单、模板）共享方法，而不是复制代码

##### 流水线交接（顺序技能串联）

除编排器/专家组合之外，技能通常还会形成**顺序流水线**，其中一个技能的输出会成为下一个技能的输入。每个技能完成工作后，都应主动建议合乎逻辑的下一步。

**模式：在 SKILL.md 末尾添加“下一步”部分**

```markdown
## Next Step: [Action Description]

After [this skill completes], suggest the natural next skill:

\```
[Summary of what was just accomplished].

Options:
A) [Next skill] — [one-line reason] (Recommended)
B) [Alternative skill] — [when this is better]
C) No thanks — [the current output is sufficient]
\```
```

**真实世界中的流水线示例：**

```
youtube-downloader → asr-transcribe-to-text → transcript-fixer → meeting-minutes-taker → pdf-creator
deep-research → fact-checker → ppt-creator
doc-to-markdown → docs-cleaner
claude-code-history-files-finder → continue-claude-work
```

**流水线交接规则：**
1. 每次交接都必须通过 AskUserQuestion **由用户选择启用**——未经询问，绝不能自动调用下一个技能
2. 仅当输出能够自然地作为另一个技能的输入时才提出建议——不要强行建立关联
3. 提供一个“不用了，谢谢”选项——用户可能不需要完整的流水线
4. 建议应说明下一步**为何**有帮助（例如，“ASR 输出通常包含识别错误”）
5. 最多提供 1-2 个建议——选项过多会导致决策疲劳

**何时添加交接：** 询问“此技能的输出通常会成为另一个技能的输入吗？”如果答案是肯定的，则添加“下一步”部分。如果这种关联很少见或显得牵强，就不要添加。

**反模式：** 将不存在自然数据流关系的技能串联起来。`pdf-creator → youtube-downloader` 毫无意义。流水线必须遵循用户的实际工作流。

##### 自动检测优于手动标志

**绝不要为可自动检测的功能添加手动标志。** 不要要求用户传入 `--with-codex` 或 `--verbose`，而应在运行时检测功能：

```
# Good: Auto-detect and inform
Step 0: Check available tools
  - `which codex` → If found, inform user and enable cross-model analysis
  - `ls package.json` → If found, tailor prompts for Node.js project
  - `which docker` → If found, enable container-based execution

# Bad: Manual flags
argument-hint: [scope] [--with-codex] [--docker] [--verbose]
```

**原则：** 功能自动检测，范围由用户决定。技能应自行发现它能做什么并采取相应行动，而不应要求用户记住安装了哪些工具。

##### 调用控制

| Frontmatter | 你可以调用 | Claude 可以调用 | 子代理可以使用 |
|-------------|----------------|-------------------|-------------------|
| （默认） | 是 | 是 | 否（内联运行） |
| `context: fork` | 是 | 是 | 是 |
| `disable-model-invocation: true` | 是 | 否 | 否 |
| `context: fork` + `disable-model-invocation: true` | 是 | 否 | 是（显式委派时） |

#### 渐进式披露

技能采用三级加载系统：
1. **元数据**（名称 + 描述）- 始终位于上下文中（约 100 个单词）
2. **SKILL.md 正文** - 每当技能触发时载入上下文
3. **捆绑资源** - 按需使用（不限量，脚本无需加载即可执行）

**关键模式：**
- SKILL.md 的长度应由**信息密度**决定，而不是以行数为目标。一个没有填充内容的 600 行技能，胜过一个遗漏关键知识、迫使模型猜测的 200 行技能。如果技能变得很长，请询问：“每个部分是否都物有所值？”如果是，就保留它。如果某些部分只是填充内容，或解释 Claude 已经知道的事情，就删减这些部分——而不是有用的内容。当一个技能确实涵盖多个领域时，应按领域拆分为参考文件，而不是人为地将所有内容硬塞进一个简短的主文件。
- 对于现有技能，渐进式披露是一种内容迁移策略，而不是内容删除启发法。旧的运行时契约必须仍可从已打包捆绑包中的 SKILL.md 访问；触发查询、测试断言、变更日志条目或审查者的记忆都不能替代运行时契约。
- 在 SKILL.md 中清晰引用参考文件，并说明何时应读取它们
- 对于大型参考文件（超过 300 行），应包含目录

**领域组织**：当一个 Skill 支持多个领域/框架时，应按变体组织：
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 避免意外原则

这虽然不言自明，但 Skill 不得包含恶意软件、漏洞利用代码或任何可能危害系统安全的内容。如果将一个 Skill 的意图描述给用户，其内容不应让用户感到意外。不要配合创建具有误导性的 Skill，也不要创建旨在协助未经授权的访问、数据外泄或其他恶意活动的 Skill。不过，诸如“扮演 XYZ”之类的内容是可以的。

#### 编写模式

说明应优先使用祈使句。

**定义输出格式**——可以这样做：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——加入示例很有帮助。可以按如下方式设置格式（但如果示例中包含 "Input" 和 "Output"，你可能需要稍作调整）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

**值得内置到 Skill 中的可用性模式**——以下四种结构元素一再将“能用但令人困惑”的 Skill 转变为用户真正能够驾驭的 Skill——它们是让一个被频繁使用的 Skill 变得易用的具体改进，因此，当 Skill 包含多种模式、会运行命令或可以重复运行时，应优先采用这些模式：
- **入口决策树**：如果 Skill 有多种模式，在开头提供一个简短的“用户说了 X → 使用模式 Y”映射，让模型正确选择路径，而不是靠猜测。
- **每条命令后的预期输出块**：紧接在命令后展示“你应该看到什么”，以便模型（以及用户）区分真正的成功和无提示的失败。
- **故障排除部分**：列出已知的故障模式及其修复方法——对于需要由他人在你无法查看的机器上运行的 Skill，这是最有价值的部分。
- **第 0 步幂等性防护**：如果重新运行可能会重复执行已经完成的工作，应先进行一次成本很低的“这是否已经完成？”检查，再执行任何开销较大的操作。

### 写作风格

与其大量使用生硬陈腐的 MUST，不如尝试向模型解释事情为何重要。运用心智理论，尽量让 Skill 具有通用性，而不是过度局限于特定示例。先写一份草稿，然后换一个全新的视角审视并改进它。

### 日期和版本引用

**保留事实日期——它们能告诉读者信息是在何时得到验证的。** 关于 Suno v5.5 的 Skill 应注明 "Suno v5.5 (March 2026)"，因为如果没有日期，未来的读者将无法判断这些信息是否仍然有效。删除日期会让情况变得更糟，而不是更好。

应该避免的是**基于日期的条件逻辑**（"if before August 2025, use the old API"）——一旦日期过去而又无人更新，这类逻辑就会立即出错。

规则：
- **发布日期、“上次验证”日期**：保留这些日期。它们是参考时间点，而不是过期日期
- **定价、排名、法律状态**：包含这些信息，但应标记为易变信息（“截至上次检查约为 $0.035/次生成”），以便读者知道需要重新核实
- **“在 X 日期之前执行 Y，在 X 日期之后执行 Z”**：不要这样写。选择当前方法，并可选择在折叠的/已弃用的章节中记录旧方法

#### 捆绑资源

##### 脚本（`scripts/`）

用于需要确定性可靠性或会被反复重写的任务的可执行代码（Python/Bash 等）。

- **何时包含**：当同一段代码被反复重写，或需要确定性可靠性时
- **示例**：用于 PDF 旋转任务的 `scripts/rotate_pdf.py`
- **优势**：节省 token、具有确定性，并且可以在不加载到上下文中的情况下执行
- **注意**：Claude 可能仍需读取脚本，以进行补丁修改或针对特定环境进行调整
- **用户可变数据应存放在捆绑包之外**：如果脚本会积累用户数据（纠错词典、学习到的偏好、缓存），请将其存储在稳定的、相对于主目录的目录下（例如 `~/.<skill-name>/`），并为其提供独立备份——绝不要存放在 skill 目录中。每次更新和套件迁移时，skill 安装内容都会被清除并重新创建；相对于主目录的存储位置则可以不受影响地保留下来。正是通过这种方式，一个会持续积累词典的 skill 在完整套件迁移后实现了用户数据零丢失

##### 参考资料（`references/`）

供 Claude 根据需要加载到上下文中，用于指导其处理过程和思考的文档及参考材料。

- **何时包含**：当 Claude 在工作时应参考相关文档时
- **示例**：用于财务模式的 `references/finance.md`，用于公司 NDA 模板的 `references/mnda.md`
- **使用场景**：数据库模式、API 文档、领域知识、公司政策、详细的工作流程指南
- **优势**：使 SKILL.md 保持精简，仅在 Claude 判断有需要时加载
- **最佳实践**：如果文件较大（>10k 个单词），请在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应只存在于 SKILL.md 或参考资料文件中的一处，而不应同时存在于两者中

##### 资源文件（`assets/`）

不用于加载到上下文中，而是供 Claude 在其生成的输出中使用的文件。

- **何时包含**：当 skill 需要在最终输出中使用的文件时
- **示例**：用作品牌资源的 `assets/logo.png`，用作 PowerPoint 模板的 `assets/slides.pptx`
- **使用场景**：模板、图像、图标、样板代码、字体、示例文档
- **组件库**：对于生成制品的 skill，`assets/` 下的 `components` 子文件夹用于存放经用户批准、可逐字嵌入的片段，这些片段具有冻结的行为契约和注册表引用——请参阅步骤 4 中的组件库检查

##### 隐私和路径引用

**在应用以下任何内容之前，先确定目标用途。** 以下所有内容描述的都是 skill
发布给陌生人使用时会出现的问题。对于存放在作者自有私有仓库中的 skill，
同样的“违规项”通常恰恰是它能够正常工作的原因——真实的绝对路径能让脚本运行，
模板中的真实账户信息可以省去下次运行时重新填写的麻烦。`quick_validate` 会自动检测这一点
（它会询问 `gh` 当前所在的仓库是否为私有仓库），并在这种情况下将可移植性/标识符问题降级为备注；
当正在准备发布私有 skill 时，`--audience=public` 会强制执行严格检查。

**在私有 Skill 中，这些发现应由所有者决定，而不是你。** 不要擅自将真实路径替换为占位符、改写硬编码凭据，或在未经询问的情况下对示例进行“脱敏”——这样做会破坏一个正常运行的工具，只为满足一条针对它根本不会发布到的目标位置而编写的规则。如果你认为某些内容应该更改，请说明你的发现，并让所有者决定。（其设计先例是 npm 的 `"private": true`：通过声明目标位置来改变工具所执行的规则；之所以添加它，是因为人们总是不小心发布内容。）

**对于打算公开分发的 Skill，这是关键要求**——其中不得包含用户特定或公司特定的信息：

- **禁止**：指向用户目录的绝对路径（例如用户主目录）
- **禁止**：个人用户名、公司名称、产品名称
- **禁止**：硬编码的 Skill 安装路径，例如 `~/.claude/skills/`
- **允许**：Skill 包内的相对路径（`scripts/example.py`、`references/guide.md`）
- **允许**：标准占位符（`<workspace>/project`、`<user>`、`<organization>`）
- **例外情况**（严格照字面实现“禁止”列表的验证器会将这个 Skill 本身标记出来——对正常输入产生误报比漏报更糟）：当替代优先级判定规则或署名*要求*提及发布者自己的名称/品牌时，可以使用该名称/品牌；当段落本身*讨论的就是* `~/.claude/skills/` 之类的安装路径时，也可以使用这些路径（这是教学材料，而不是硬编码依赖）

**跨 Skill 引用**：不带其他限定的相对路径始终表示“位于当前 Skill 自己的包内”——验证器和读者都会如此理解，因此，使用这种路径指向另一个 Skill 的文件既无法通过验证，也会误导读者。指向另一个 Skill 时，请在正文中注明所有者（“marketplace-dev 的 cache-and-source-patterns 参考资料”），并使用带命名空间的名称调用 Skill（`/suite-name:skill-name`，而不是不带限定的 `/skill-name`）。当 Skill 在不同套件之间移动时，不带限定的交叉引用会悄无声息地失效——正因如此，一次套件迁移在两轮清理后仍留下了 21 个失效的交叉引用。

##### 版本控制

**关键要求**：Skill 的 SKILL.md 中不应包含版本历史或版本号：

- **禁止**：SKILL.md 中的版本章节（`## Version`、`## Changelog`）
- **正确位置**：Skill 版本在 marketplace.json 的 `plugins[].version` 下进行跟踪
- **理由**：市场基础设施负责管理版本；SKILL.md 应包含不受时间影响的内容

#### 参考文件命名

文件名必须做到无需阅读内容便能知晓其含义。

**模式**：`<content-type>_<specificity>.md`

**示例**：
- 不佳：`commands.md`、`cli_usage.md`、`reference.md`
- 良好：`script_parameters.md`、`api_endpoints.md`、`database_schema.md`

**检验方法**：别人能否仅通过文件名理解文件内容？

有两种例外情况：使用连字符的名称与使用下划线的名称同样合适（分隔符从来都不是重点——自解释性才是）；此外，位于已命名工作流目录中的文件（`workflows/<name>/workflow.md`、`patterns.md`）由目录提供限定信息——目录已经赋予了名称所需的具体性，而重命名这些文件会破坏各工作流之间的并行结构。

### Skill 创建最佳实践

### 完整评估测试用例（仅限 Tier 3）

仅当路由器选择通用 Tier 3 路径，或用户明确请求完整评估流水线时，才进入本节。不要仅仅因为 SKILL.md 发生了更改就使用本节。专用工作流遵循上文声明的 Tier 3 替代约定。

编写完 Skill 草稿后，构思 2 至 3 个切合实际的测试提示词——即真实用户实际可能会说的话。**对于会操作实时系统（正在运行的服务、已登录的客户端、生产数据）的 Skill，请为每个测试提示词明确指定副作用预算**——例如，“仅进行只读探查并得出结论；不要执行下载，也不要操作 UI。”在“仅仅测试”时改变实时环境的评估属于真实操作，而不是测试。通过 **AskUserQuestion** 向用户展示这些提示词：

```
Skill draft is ready. Here are [N] test cases I'd like to run:

1. "[test prompt 1]" — tests [what aspect]
2. "[test prompt 2]" — tests [what aspect]
3. "[test prompt 3]" — tests [what aspect]

Each test runs the skill + a baseline (no skill) for comparison.
Estimated time: ~[X] minutes total.

RECOMMENDATION: Run all [N] test cases now.

Options:
A) Run all test cases (Recommended)
B) Run test cases, but let me modify them first
C) Add more test cases before running
D) Skip testing — the skill looks good enough to ship
```

将测试用例保存至 `evals/evals.json`。暂时不要编写断言——只需编写提示词。下一步中，在运行进行期间再起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整模式请参阅 `references/eval_pipeline_schemas.md`（其中包括稍后要添加的 `assertions` 字段）。

## 完整配对评估流水线（仅限通用 Tier 3）

仅在选择通用 Tier 3 路径后运行本节。只要 Tier 3 仍处于授权状态，这就是一个连续的流程——不要中途停止。用户取消或降级请求的优先级高于本段要求；请按照路由器中的规定停止高负载流水线。不要机械地将其复用于 Tier 1、Tier 2，或工作流明确替代了相关机制的专用流程，也不要使用 `/skill-test` 或任何其他测试 Skill。

将结果放入与 Skill 目录同级的 `<skill-name>-workspace/` 中。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些目录——只需随着流程推进逐步创建。

### 第 1 步：在同一轮中启动所有运行（使用技能和基线）

对于每个测试用例，在同一轮中启动两个子代理——一个使用技能，另一个不使用。这一点很重要：不要先启动使用技能的运行，之后再回来启动基线运行。一次性启动所有运行，使它们大致同时完成。

**使用技能的运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（提示词相同，但基线取决于具体情境）：
- **创建新技能**：完全不使用技能。使用相同的提示词，不提供技能路径，将结果保存到 `without_skill/outputs/`。
- **改进现有技能**：使用首次编辑前由强制性现有技能回归门禁捕获的旧版本。让基线子代理使用该不可变快照，并将结果保存到 `old_skill/outputs/`。如果不存在编辑前快照，请停止并先从 Git 重建权威基线，再继续操作；绝不能将已经编辑过的工作树用作旧基线。**要清楚这种比较能够分辨什么：它只衡量本轮的变化。** 如果你最想验证的能力已经存在于编辑前快照中——例如，某个并行会话可能恰好在你开始之前提交了完全相同的修复——那么使用新版与旧版进行 A/B 对比对此能力的分辨力为零；如果这正是待测试的能力，请选择更早的引用作为基线。

为每个测试用例编写一个 `eval_metadata.json`（断言目前可以为空）。根据测试内容为每个评估指定一个描述性名称，而不要只使用“eval-0”。目录也使用这个名称。如果本次迭代使用了新增或修改过的评估提示词，请在每个新的评估目录中创建这些文件——不要假定它们会从之前的迭代中自动保留下来。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：在运行进行期间起草断言

不要只是等待运行完成——你可以高效利用这段时间。为每个测试用例起草定量断言，并向用户说明这些断言。如果 `evals/evals.json` 中已经存在断言，请审查它们并说明其检查内容。

好的断言应当能够被客观验证，并具有描述性名称——这些名称应当能在基准测试查看器中清晰呈现，使浏览结果的人一眼就能理解每个断言检查的内容。**应当针对意图编写断言，而不是针对字面上的工具路径**——应写成“语音内容保留在答案中”，而不是“调用指定的读取器脚本”。如果某次运行通过另一条获准路径实现了该意图（例如，读取已经内嵌转录文本的归档文件），它就应当通过；若将其判定为字面路径失败，就会制造一个假阴性，而你随后还会在错误的位置“修复”它。主观性技能（写作风格、设计质量）更适合进行定性评估——不要强行为需要人类判断的事项设置断言；其真正的验证路径（历史任务重放、将生产环境作为评估并养成写回习惯、渲染后进行人工审查）列在“Capture Intent”的问题 4 下。

断言起草完成后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。还要向用户说明他们将在查看器中看到什么——包括定性输出和定量基准测试结果。

### 步骤 3：随着运行完成，记录计时数据

每个子智能体任务完成时，你都会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是记录这些数据的唯一机会——它们通过任务通知传递，不会持久化到其他位置。每条通知到达时就进行处理，而不要尝试批量处理。

### 步骤 4：评分、聚合并启动查看器

所有运行完成后：

1. **为每次运行评分**——启动一个评分子智能体（或直接进行评分），让其读取 `agents/grader.md`，并根据输出评估每条断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以通过程序检查的断言，应编写并运行脚本，而不是靠肉眼判断——脚本更快、更可靠，并且可以在多次迭代中复用。**但客观的 grep/脚本断言是一把双刃剑**（同一词语含义不同导致误命中，措辞不同导致漏检），因此**基准测试通过率只是一种信号，而非最终结论**：抽查每条断言实际匹配到的内容，并留意基线运行是否揭示了技能本身的事实性错误（“等等，数据确实在 API 里”的时刻）。参见方法论 §5.3–5.6 + §6.4。

2. **聚合为基准测试结果**——运行 skill-creator 目录中的聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、time 和 tokens，以及 mean +/- stddev 和 delta。如果手动生成 benchmark.json，请参阅 `references/eval_pipeline_schemas.md`，了解查看器所需的确切模式。
将每个 with_skill 版本放在对应的基线版本之前。

3. **进行分析审查**——阅读基准测试数据，揭示聚合统计信息可能掩盖的模式。有关需要关注的内容，请参阅 `agents/analyzer.md`（“Analyzing Benchmark Results”一节）——例如，无论是否使用技能都始终通过的断言（缺乏区分能力）、高方差评估（可能不稳定），以及时间/token 之间的权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

**如果后台运行的查看器进程陷入失效状态**：进程仍然存活，但没有任何程序在监听——可使用 `lsof -a -p $VIEWER_PID -iTCP -sTCP:LISTEN` 进行检查（输出为空），或访问相应 URL（访问失败）；此处“没有日志输出”并不是可用的判断信号，因为上面的启动命令行已将输出重定向到 `/dev/null`。终止该进程并改用 `--static`，不要以相同方式重新启动。

   **Cowork / 无头环境：**如果 `webbrowser.open()` 不可用或环境没有显示设备，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。当用户点击“Submit All Reviews”时，反馈将以 `feedback.json` 文件形式下载。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. 通过 **AskUserQuestion****告知用户**：

```
Results are ready! I've opened the eval viewer in your browser.

- "Outputs" tab: click through each test case, leave feedback in the textbox
- "Benchmark" tab: quantitative comparison (pass rates, timing, tokens)

Take your time reviewing. When you're done, come back here.

RECOMMENDATION: Review the Outputs tab first — your qualitative feedback drives the next iteration more than the numbers do.

Options:
A) I've finished reviewing — read my feedback and improve the skill
B) I have questions about the results before giving feedback
C) Results look good enough — skip iteration, let's package the skill
D) Results need major rework — let's discuss before iterating
```

### 用户在查看器中看到的内容

“Outputs”选项卡一次显示一个测试用例：
- **Prompt**：给出的任务
- **Output**：该技能生成的文件，能以内联方式呈现时会直接呈现
- **Previous Output**（第 2 次及后续迭代）：折叠区域，显示上一次迭代的输出
- **Formal Grades**（如果执行了评分）：折叠区域，显示断言通过/失败情况
- **Feedback**：一个文本框，会在用户输入时自动保存
- **Previous Feedback**（第 2 次及后续迭代）：用户上一次的评论，显示在文本框下方

“Benchmark”选项卡显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每项评估的明细和分析人员的观察结果。

可通过上一个/下一个按钮或方向键进行导航。完成后，用户点击“Submit All Reviews”，将所有反馈保存到 `feedback.json`。

### 步骤 5：读取反馈

当用户告诉你他们已完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

反馈为空表示用户认为结果没有问题。改进时应重点关注用户提出了具体意见的测试用例。

使用完查看器服务器后，将其终止：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是整个循环的核心。根据路由器选定的证据进行改进：第 1 层级使用权威事实和确定性检查，第 2 层级使用 1–2 个指定的行为重放，第 3 层级则使用经过用户审阅的成对结果。不要将第 3 层级的产物或步骤引入较低层级的迭代中。

### 如何思考改进

1. **从反馈中提炼出可泛化的结论。** 这里发生的事情，从宏观上看，是我们正在尝试创建可以在许多不同提示词中使用无数次的技能（可能真有一百万次，甚至更多，谁知道呢）。在这里，你和用户只围绕少数几个示例反复迭代，因为这样可以加快推进速度。用户对这些示例了如指掌，因此能快速评估新的输出。但如果你和用户共同开发的技能只能适用于这些示例，那它就毫无用处。与其做一些琐碎且过拟合的改动，或添加极其苛刻的 MUST，不如在遇到某个顽固问题时，尝试拓展思路，使用不同的比喻，或者推荐不同的工作模式。尝试的成本相对较低，而且说不定你会找到非常出色的方案。

2. **在不删除约定的前提下保持提示词精简。** 删除那些没有发挥应有作用的内容，但在新旧版本审计完成分类之前，应将对现有技能的每一处删除都视为潜在的回归问题。将详细但可复用的行为移至直接链接的参考资料中；不要让它只存在于评估、变更日志或你的记忆里。阅读执行记录，而不只是最终输出——如果技能导致了无效工作，应简化指令并重新运行原有能力用例，而不要想当然地认为字数越少，行为就越好。

3. **解释原因。** 尽量认真解释你要求模型执行每件事背后的**原因**。如今的 LLM *非常聪明*。它们具备良好的心智理论，在获得良好的执行框架时，能够超越机械照做，真正把事情办成。即使用户的反馈简短或带有挫败情绪，也要尝试真正理解任务、用户为什么要写下这些内容、他们实际写了什么，然后将这种理解传递到指令中。如果你发现自己在用全大写的 ALWAYS 或 NEVER，或者使用极其僵化的结构，这就是一个警示信号——如果可能，应重新组织表述并解释其中的道理，让模型理解你所要求的事情为什么重要。这是一种更人性化、更强大、也更有效的方法。

4. **寻找重复性工作——既要查看评估执行记录，也要查看提炼出该技能的原始对话。** 阅读测试运行的执行记录，留意各个子智能体是否都独立编写了相似的辅助脚本，或采用了相同的多步骤方法来处理某件事。如果 3 个测试用例都导致子智能体编写了 `create_docx.py` 或 `build_chart.py`，这就是一个强烈信号，说明该技能应该捆绑这个脚本。只需编写一次，将其放入 `scripts/`，并要求技能使用它。这样可以避免以后的每次调用都重复造轮子。你从中提炼技能的源对话中也隐藏着同样的信号——那次会话中哪怕只编写过一次的代码，也是未来每次运行都必须重写的代码；不要等到评估运行证明这种重复性后才采取行动（跳过评估循环的技能永远得不到这种证明——创建流程第 4 步中的 Scripts 检查正是用于捕捉这些情况的关卡）。

5. **将修正原文回写——在同一会话中，同时覆盖两个层级。** 对于经过品味校准的 skill，用户的修正本身就是评估集，但前提是这些修正被写入未来运行能够读取的位置。两个属性可确保回写过程收敛：(a) **逐字记录修正内容**，不要改写——原话携带的校准信号会被摘要抹平（“绝对禁止这种东西”传达的是一条硬性边界；“用户更喜欢少一些跳转”则不能）。在修正所针对的规则中引用用户原话，并标注日期。(b) **在修正发生的同一会话中，将其回写到两个层级**——既修复产物，也修复 skill 的规则/参考资料/组件；如果修正只作用于产物，那么所有未来运行都无法感知它，而推迟到“以后”的修正通常永远不会真正落地。回写时，检查 skill 自身的文本是否曾经*教导*了刚刚被禁止的反模式——一次修正常常会证伪某条现有指令，而保留原有建议必然导致问题再次发生（真实案例：某个决策页面契约建议使用跳转式的“转到所引用图形的锚点”；用户明确禁止了这种做法，因此回写必须修改原有句子，而不能只在旁边新增一条规则）。当被修正的内容是交互片段时，回写的最后一步是将其提升至组件架——参见步骤 4 中的组件架检查。

这项任务非常重要（我们正试图在这里每年创造数十亿的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，真正深入斟酌。我建议先写一份修订草稿，然后以全新的视角重新审视并加以改进。请真正尽最大努力站在用户的角度思考，理解他们想要什么、需要什么。

对于第 1 层级，直接应用有明确证据支持的修正；只有当证据确实留下了需要选择的空间时才询问。对于第 2 或第 3 层级，当用户反馈揭示出有实质意义的设计分支时，通过 **AskUserQuestion** 提交改进计划：

```
I've read the feedback from [N] test cases. [X] had specific complaints, [Y] looked good.

Key issues:
- [Issue 1]: [plain-language summary]
- [Issue 2]: [plain-language summary]

RECOMMENDATION: [strategy] because [reason]

Options:
A) Iterative refinement — targeted fixes for the specific issues above (Recommended)
B) Structural redesign — the core approach needs rethinking (reclassifies Tier 1/2 work to Tier 3 before changing it)
C) Bundle a script — I noticed all test runs independently wrote similar code for [X] (reclassifies Tier 1/2 work to Tier 3 before adding the capability)
D) Expand test set first — add [N] more test cases to avoid overfitting (if the total exceeds 2, reclassify to Tier 3 before running them)
```

### 迭代循环

改进 skill 后：

1. 将你的改进应用到 skill
2. 仅重新运行所选层级的证据：
   - **第 1 层级：** 始终重新运行 `quick_validate`、差异检查和迁移门禁；然后仅重新运行匹配子类型的证据——(a) 精确回读/格式检查，(b) 权威事实及其窄范围检查，或 (c) 明确的现有契约及确定性回归测试。不要创建迭代工作区。
   - **第 2 层级：** 仅重新运行相同的 1–2 个已命名的启用 skill 的示例和窄范围检查。不要添加基线、基准测试、查看器或评估工作区；任何要求添加这些内容的请求都会将该工作重新归类为第 3 层级。
   - **第 3 层级，仍处于授权范围内时：** 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。对于新 skill，基线始终为 `without_skill`；对于现有 skill，不可变的原始编辑前版本在每次迭代中始终作为保留性基线。紧邻的上一次迭代可以作为补充，但绝不能取代原始基线。
3. 在对规则、契约或数值进行实质性更改后，应用纪律 #5。对于通用的第 3 层级路径，还要启动评估审查器，并通过 `--previous-workspace` 指向上一次迭代；专用工作流则使用其声明的审查器机制。
4. 对于通用的第 3 层级，等待用户审查新的查看器结果；其他情况下，根据所选层级的证据作出决定，除非仍存在确实需要用户选择的问题。
5. 阅读新的证据或反馈；如果它们证伪了当前版本，则再次改进，并在同一层级重复这一过程。

用户请求的取消或降级将在任务剩余期间持续生效，且不会改变其分类。除非用户明确重新授权执行 Tier 3，否则不要重新启动成对评估、基线、评分器、聚合或查看器工作。

在每次**通用 Tier 3** 迭代结束时，使用 **AskUserQuestion** 作为检查点：

```
Iteration [N] complete. Results: [pass_rate]% assertions passing, [delta vs previous].

RECOMMENDATION: [Continue / Accept / Revert] because [one-line reason from the delta and remaining feedback].

Options:
A) Continue iterating — I see more room for improvement
B) Accept this version — it's good enough, let's move to packaging
C) Revert to previous iteration — this round made things worse
D) Run blind comparison — rigorously compare this version vs the previous one
```

持续进行，直到：
- 用户表示满意
- 反馈全部为空（一切看起来都很好）
- 你没有取得有意义的进展

## 高级：盲测比较

如果你希望更严格地比较技能的两个版本（例如，用户询问“新版本真的更好吗？”），可以使用盲测比较系统。有关详细信息，请阅读 `agents/comparator.md` 和 `agents/analyzer.md`。其基本思路是：将两个输出提供给一个独立智能体，但不告诉它哪个对应哪个版本，让它判断质量。然后分析胜出版本获胜的原因。

这是可选功能，需要子智能体，而且大多数用户不需要使用。人工审核循环通常就已足够。

## 描述优化

SKILL.md frontmatter 中的描述字段是决定 Claude 是否调用某项技能的主要机制。创建或改进技能后，主动提出优化描述，以提高触发准确率。

### 第 1 步：生成触发评估查询

创建 20 条评估查询——混合包含应触发和不应触发的查询。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须真实可信，应当是 Claude Code 或 Claude.ai 用户实际会输入的内容。不要使用抽象请求，而应使用具体、明确且包含充分细节的请求。例如，可以包含文件路径、有关用户工作或所处情境的个人背景、列名和值、公司名称、URL。可以加入一些背景信息。某些查询可以全部使用小写字母，或者包含缩写、拼写错误或口语化表达。混合使用不同长度的查询，并重点关注边界情况，而不是让它们泾渭分明（用户将有机会确认这些查询）。

不佳：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

良好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应触发**查询（8-10 条），要考虑覆盖面。你需要用不同的表述来表达相同意图——有些正式，有些随意。加入用户没有明确说出技能名称或文件类型，但显然需要使用该技能的情况。还应加入一些不常见的用例，以及该技能与其他技能存在竞争但应当胜出的情况。

对于 **不应触发** 的查询（8-10 条），最有价值的是那些差一点就会触发的查询——它们与技能共享关键词或概念，但实际需要的是其他东西。可以考虑相邻领域、使用含糊措辞且简单的关键词匹配会错误触发的查询，以及涉及该技能所执行的操作、但在相应场景中更适合使用其他工具的情况。

需要避免的关键问题是：不要让不应触发的查询显得明显无关。对于 PDF 技能而言，将“编写一个斐波那契函数”作为负面测试太简单了——它测试不出任何东西。负面用例应该真正具有迷惑性。

### 第 2 步：与用户一起审查

使用 HTML 模板向用户展示评估集以供审查：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（不要在其外部添加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并将其打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换是否应触发、添加或删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中最新的版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的评估查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我将在后台运行优化循环，并定期检查进度。”

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示词中的模型 ID（即为当前会话提供支持的模型），以确保触发测试与用户实际体验相符。

运行期间，定期查看输出末尾内容，向用户更新当前所处的迭代轮次以及分数情况。

这会自动处理完整的优化循环。它会将评估集拆分为 60% 的训练集和 40% 的留出测试集，评估当前描述（每个查询运行 3 次，以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每轮迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试分数而非训练分数选出，以避免过拟合。

**如果循环检测到完全无响应，它会在第 1 轮迭代后自行中止——你无需手动处理这种情况。** 这是 `run_loop.py` 中的代码级保护措施，而不仅仅是一条建议；它能够区分“第 1 轮迭代中，每个应触发查询的触发次数均为零”的两种原因：

- `exit_reason: "infra_error: ..."` — 某些查询执行（should-trigger *或* not-should-trigger）抛出了异常（claude CLI 不在 PATH 中、超时时间过短、网络中断），而不是正常返回“未触发”。此项会被*优先*检查，并且只要非零错误计数便会刻意触发，即使数十次运行中只有一次不稳定运行也不例外——崩溃无论多么罕见，都是比“什么都没有触发”更具体、更可操作的线索，而且修复对象是环境，而不是重写描述。消息中的比率（例如 `3/15`）反映了严重程度：较大的比例意味着“停下来，修复你的环境”；如果比例较小，同时存在大量正常的 0-trigger 运行，则意味着环境可能存在值得检查的轻微不稳定问题，*并且*描述也可能确实很差——两者都要检查。无论哪种情况，都应检查 stderr 中的 `Warning: query failed` 行。
- `exit_reason: "degenerate_harness: ..."` — 仅在上述分支排除所有执行错误后才会检查，因此这意味着每个 should-trigger *和* not-should-trigger 查询都*确实运行了*，但触发次数*仍然*全部为零（这正是通过零分母默认值获得“precision=100%”的真实含义：不是“完美”，而是“没有可供相除的数值”）。该探针实际上什么也没有测量到——在对描述进行任何修改之前，先去诊断竞争项冲突或低阈值领域（见下文）。

这两项检查都**仅针对第 1 次迭代**运行，并且**仅在零个 should-trigger 查询触发时**运行——第 1 次迭代即使很弱但并非零触发（例如 9 个查询中触发 1 个），也属于另一种可能可以恢复的情况，因此会被刻意留给后续迭代。`degenerate_harness` 还要求 not-should-trigger 查询的触发次数同样为零：如果描述只是极性反转——漏掉所有正例，却意外匹配了若干负例——那么探针已被证明可以工作，且 `improve_description` 有真实的梯度可供利用，因此守卫不会中止这种情况（只会中止探针确实失效的情况）。此外，它还要求任一侧的执行错误均为零——抛出异常的 not-should-trigger 查询实际上从未运行，因此其“0 次触发”不能作为探针失效的证据；这正是该情况会转而进入 `infra_error` 的原因。无论哪种情况，它都会立即中断并完全跳过 `improve_description`——JSON 和 HTML 仍会正常报告 `best_description`/`best_score`（不会隐藏任何内容），退出原因则用于表明，不应将这次特定运行的数值解读为“这是一个好的描述”。（真实案例，2026-08：在未进行预检查的情况下启动了完整的 5 次迭代循环；两个完整迭代——每个迭代都包含完整的评估批次、数分钟的实际耗时以及数十次 `claude -p` 子进程调用——均返回 precision=100%/recall=0%/相同分数，之后才有人查看这些数值，而每个 should-trigger 和 not-should-trigger 查询都一次也没有触发。仅凭第 1 次迭代就能诊断出该故障；第 2 次及之后的迭代没有增加任何信息。）当任一退出原因触发时，HTML 报告也会显示横幅，因此浏览器视图会传达与 JSON/stderr 相同的信号，而不只是通过这两个可见性较低的渠道传达。（此守卫的早期草案只检查 should-trigger 的触发情况；经过两轮独立审查——每轮都由一个全新的代理执行，第二轮检查第一轮的修复，而不是再次覆盖旧问题——构造出了极性反转反例、基础设施与描述之间的歧义、负例侧错误缺口，以及审查过程中暴露出的一个原有 `--holdout 0` 报告崩溃问题，所有这些问题均在发布前得到修复。）

这个防护机制无法覆盖一种情况：使用 `--runs-per-query 1`（默认值为 3）时，某个本应触发、实际触发率确实在 50% 左右的查询，完全可能仅因偶然而得到 0/1 的结果，导致防护机制因噪声而触发，而非因探针失效而触发。默认的 `runs_per_query=3` 使“每个正向查询的每次重复运行结果均为零”成为一个强信号——如果你将其调低，这个防护机制的误报风险也会随之升高。

**在信任 `best_description` 之前，请先对测试框架进行健全性检查——即使上述两个防护机制都未触发，它仍可能返回空洞无效的输出。** 这两项检查只能捕获第 1 次迭代时的*完全*失败；测试框架也可能在全部 5 次迭代中始终维持微弱但非零的信号，勉强运行，却从不触发其中任何一项防护机制。如果第 1 次迭代之后的每次迭代都显示**召回率始终接近 0%，且分数完全或几乎完全相同**，这就是防护机制无法排除的同一类根本问题——所谓的“获胜”描述通常只是第 1 次迭代结果周围的噪声，内容基本没有变化。在应用任何 `best_description` 之前，请亲自运行一个显然应当触发的查询，并确认召回率 > 0。各次迭代的召回率始终持平，意味着测试框架是一个隐藏变量（常见情况是：该技能在触发竞争中输给了已安装的竞争技能——参见下文的“共存”）——不要应用它的“最佳”结果；请改为手动编写描述，并使用真实探针进行验证。（方法论案例 12、14）召回率为 0 还有第二种根本原因，与输给竞争技能不同：该技能的任务领域属于*低阈值*领域——模型会自行完成任务，根本不会查阅任何技能——具体说明见下文*技能触发机制*一节末尾。采取措施前，请先区分这两种情况，因为二者的修复方式恰好相反：竞争技能问题应通过优先级/取代机制解决，而低阈值领域则应完全放弃触发探针，改用生产任务作为评估。

**当你自行使用 `claude -p` 探测触发情况时，请收集该次运行中的所有技能调用，而不只是第一次调用——同时请记住，工具调用只是一种代理指标。** `UserPromptSubmit`/`SessionStart` hook 可能会在模型作出选择*之前*注入一个无关技能，因此“遇到第一次 Skill 调用就退出”的探针会误报“未触发”。此外，“是否调用了 Skill 工具”并不等同于“技能内容是否影响了输出”（模型可能读取该技能，但没有可见的 Skill 调用），也不等同于“输出是否正确”。有缺陷的探针本身就是一个隐藏变量，会让你一直基于错误结论进行优化。

### 技能触发机制

理解触发机制有助于设计更好的评估查询。技能会以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否查阅某项技能。需要了解的重点是，Claude 只会针对自身无法轻松处理的任务查阅技能——“读取这个 PDF”这类简单的单步骤查询，即使与描述完全匹配，也可能不会触发技能，因为 Claude 可以直接使用基础工具处理它们。当描述匹配时，复杂、多步骤或专业化的查询能够可靠地触发技能——但存在一个系统性例外（低阈值任务领域），具体说明见本节末尾。

这意味着你的评测查询应当足够充实，让 Claude 确实能从查阅技能中获益。像“读取文件 X”这样的简单查询并不是好的测试用例——无论描述质量如何，它们都不会触发技能。

**但有些技能未能通过这项测试，是因为存在一种无论如何改写查询都无法解决的原因——该技能的全部*职责*就是执行一项低门槛任务。** 上一段将问题归咎于查询（“写一个更充实的查询”）；而这里讨论的是与之正交的情况，即阻碍触发的是技能的*领域*。如果某个技能的用途是执行 Claude 仅凭基础工具就会自行完成的事情——将音频转换为 16 kHz、降采样、提取一个字段、批量重命名——那么即使查询包含完整规格（“将这个 48k 立体声 wav 降采样为供 whisper 使用的 16k 单声道”，并附上路径），也不会触发该技能：模型会直接使用 `Bash`/`ffmpeg`，完全不会查阅任何技能。提高查询的充实程度无法解决这个问题，因为“我自己就能完成”的判断针对的是*任务*，而不是措辞。

在白白耗费一轮优化之前，先诊断这一点：通过 `claude -p` 运行一次真实查询，并观察模型在整个运行过程中是否*曾经*查阅该技能（按照上面的“所有技能调用”规则），还是直接使用 `Bash` 自行完成任务。如果它从未查阅该技能，那么触发探针在结构上就无法观测这个技能——无论你怎么写，召回率读数都会接近 0，而这个零衡量的是模型“自己动手”的本能反应，并非你的描述质量。不要再针对 `claude -p` 的召回率进行调优，而应通过真正的方式进行验证：将生产环境作为评测（即用户下一次真实的*交互式*使用——无头模式的 `-p` 比真实会话更偏向直接采取行动，因此会系统性地低估触发情况），再加上输出对比，前提是该技能会生成可检查的产物。（在一个音频预处理技能上观察到了这种情况：无头模式的 run_eval 扫描在*每个*查询上的召回率读数都是 0——其中甚至包括一个显而易见的“转录这段录音”查询——而手动执行 `claude -p` 探测显示，模型直接使用 `Bash` 查找并处理文件，整个运行过程中 `Skill`=0。这个零衡量的是无头模式下的行动偏向，而不是描述质量；真正的信号只有在交互式使用中才会显现。）

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新技能 SKILL.md 的 frontmatter。向用户展示修改前后的内容并报告分数。

## 关键要求：在源位置编辑技能

**绝不要先编辑已安装的技能副本。** 除非用户明确说明它们就是源文件，否则应将以下所有位置视为已安装的副本或运行时副本：
- `~/.codex/skills/<skill-name>`
- `~/.claude/skills/<skill-name>`
- `~/.agents/skills/<skill-name>`
- `~/.claude/plugins/cache/...`
- `~/.codex/plugins/cache/...`

先编辑已安装的副本会导致更改：
- 在缓存刷新时丢失
- 未同步到源代码控制系统
- 浪费精力，之后还需要手动重新合并

**务必确认你编辑的是源代码仓库：**
```bash
# WRONG - cache location (read-only copy)
~/.claude/plugins/cache/daymade-skills/my-skill/1.0.0/my-skill/SKILL.md

# WRONG - personal installed copy unless explicitly used as source
~/.codex/skills/my-skill/SKILL.md

# RIGHT - source repository
<repo-root>/my-skill/SKILL.md
```

**在进行任何编辑之前**，先运行源位置检查，并说明哪个路径是源：

```bash
pwd
git rev-parse --show-toplevel
rg -n '"name": "<skill-or-suite-name>"' .claude-plugin/marketplace.json
find . -path '*/SKILL.md' -maxdepth 4 | rg '(^|/)<skill-name>/SKILL.md$'
```

如果 available-skills 列表指向 `~/.codex/skills`、`~/.claude/skills` 或插件缓存，不要假定该路径就是源。先定位由仓库支持的源，对其进行编辑和验证，然后仅在用户需要立即在本地运行时使用时，才同步已安装的副本。

**然后回答一个后续问题，以确定“同步已安装的副本”是否真的需要做：运行时是否已经直接读取源？** 三种安装方式的行为不同，猜错要么会造成不必要的同步，要么会导致用户下一个会话看不到你发布的编辑：

```bash
ls -la ~/.claude/skills/<name>                       # a symlink into the repo? -> edits are live already
grep -A3 '"<marketplace-name>"' ~/.claude/plugins/known_marketplaces.json   # "source": "directory" -> reads the repo in place
```

- **通过符号链接**链接到源代码树 → 编辑内容*就是*运行时内容。无需同步。
- **`source: directory` 指向仓库的 Marketplace** → 同样如此：它直接读取工作树，因此版本升级只是面向其他使用者的记录工作，并不是本地激活步骤。
- **任何缓存或复制的安装**（以 git 为源的 Marketplace、通过 `cp -r` 安装）→ 运行时使用的是单独的副本，在新内容生效之前确实需要运行官方更新命令。

**并且要根据内容验证激活状态，而不是根据版本字符串。** 注册表可能记录一个磁盘上并不存在的路径或版本——有一次会话读取到一条插件记录，其中指定了一个名称带有*新*版本号的缓存目录，并且差点报告更新已经生效；但该目录从未被创建，真正的运行时路径始终是指向源的符号链接。权威的检查方法是在运行时文件中 grep 仅新版本才包含的内容：

```bash
grep -c "<a phrase unique to the new content>" <resolved-runtime-path>/SKILL.md   # 0 = not live
```

### 同一技能仓库中的并发会话

高级用户会同时运行多个 Claude 会话，而技能仓库正是它们容易发生冲突的地方：当你编辑技能 A 时，另一个并行会话可能会在你操作期间提交技能 B（甚至是技能 A 更早一轮的版本）。一次真实会话在一小时内遇到了全部三种症状——由于文件在读取后发生变化而被拒绝的 `Write`，以及任务进行期间 HEAD 两次移动（方法论案例 16）。问题不在于发生冲突本身，而在于使用过期基线，或者通过覆盖式写入悄无声息地混合了两个会话的工作。长期遵守以下规则：

1. **只要任务开始时仓库是干净的，就应基于 git ref 建立基线，而不是基于工作树**：`git archive <HEAD-sha> <skill-dir> | tar -x -C <workspace>/skill-before`，并向审计传递 `--baseline-origin git-ref:<sha>`。在其他人的提交发生前几分钟创建的工作树快照，只是一个针对已不存在工作树的基线。**请解压到一个全新的、不存在的目录中。** 如果解压到现有目录，`tar -x` 会悄无声息地覆盖同名文件，并保留归档中不存在的文件——这会形成一个在解压时毫无异常信号的混合快照，之后 `compare` 会因其与 ref 不匹配而拒绝该快照。同样的陷阱也存在于另一条命令中：`mv <dir> <existing-dir>` 会将目录嵌套进去，而不是替换目标——如果 `mv` 被设置为 `mv -i` 的别名，当目标已存在时，重命名会打印一行提示，并默认*不*执行操作，无论哪种情况退出码都是 0（已通过实验验证）。
2. 当写入被拒绝或已经过去一段时间时，**在写入前重新读取**：对发生的变化进行比较（`git log --oneline -3`、`git show <new-commit> --stat`），将另一个会话的意图整合到你的版本中——对方的编辑通常有其原因——然后再写入。
3. **提交前检查 HEAD，*同时检查当前所在的分支***。`git log --oneline -1` 可以发现 SHA 发生移动：如果它在你建立基线后发生了移动，应先针对新的 ref 重新运行回归 `compare`，然后再运行 `verify`——无论如何，审计工具都会拒绝过期的审查（“after skill changed”），因此自行提前发现可以省去一轮操作。但并行会话可能做出比推进 HEAD 更糟糕的事情：**它可能在你不知情的情况下切换分支**，因为 checkout 的作用范围是整个工作树。一个真实过程是——先执行 `checkout -b feat/x`，编辑一段时间，而与此同时另一个会话运行了 `checkout main` + `pull`；结果提交落在了 **main** 上，违反了仓库“绝不直接提交到本地 main”的规则，而功能分支仍然指向旧基线。因此，在提交前的检查中加入 `git branch --show-current`，不要只检查 SHA。如果这种情况已经发生，`git reflog` 是权威的还原依据（它按顺序记录每一次 `checkout: moving from X to Y`）；修复方法——**前提是工作树干净**——是先执行 `git checkout -B <feature> <your-sha>`，然后执行 `git branch -f main origin/main`：两者都只是移动 ref，完全不会触碰工作树，因此不会像 `reset --hard` 那样破坏并行会话中尚未提交的工作。
4. **只暂存你自己的路径**（`git add <skill-dir> <registry-file>`），绝不要运行 `git add .`——不能让并行会话中尚未提交的工作被一并带入。（这已经是打包时的规则；在并发情况下更是至关重要。）
5. **每个会话结果只升级一次版本**，而不是每轮编辑都升级：同一会话中针对同一技能的连续多轮编辑应合并为一次版本升级——除非某个中间状态已经被使用（已提交，并被用户或另一个会话拉取），在这种情况下，每个已被使用的状态都应拥有独立版本。

## Skill 创建流程（分步说明）

创建或更新 Skill 时，请依次执行以下步骤。仅当某个步骤明确不适用时才跳过。

### 步骤 0：先决条件检查

开始任何 Skill 工作之前，自动检测所有依赖项，并主动安装缺失的依赖项。在工作流中途才发现缺少工具（例如，在打包时发现缺少 gitleaks，在验证时发现缺少 PyYAML）会浪费时间并打断流程。

运行 [references/prerequisites.md](references/prerequisites.md) 中的快速检查，自动安装可以安装的依赖项，并向用户提供一份汇总检查清单。只有在满足所有阻塞性依赖项后才能继续。

关键阻塞项：Python 3、uv、PyYAML（验证/打包）和 gitleaks（安全扫描）。只有当所选验证层级确实会运行智能体评估时，claude CLI 才是阻塞项。运行 Python 工具时，应使用显式的 uv 依赖声明，例如在 skill-creator 根目录中运行 `uv run --with PyYAML python -m scripts.quick_validate <skill-path>`。直接使用 `python3` 会依赖环境中的 site packages，因此可能找不到 PyYAML。

### 步骤 1：通过具体示例理解 Skill

仅当 Skill 的使用模式已经得到清晰理解时，才跳过此步骤。

要创建有效的 Skill，需要清楚理解该 Skill 将如何使用的具体示例。这种理解既可以来自用户直接提供的示例，也可以来自生成后经用户反馈验证的示例。

例如，在构建图像编辑器 Skill 时，相关问题包括：

- “图像编辑器 Skill 应支持哪些功能？编辑、旋转，还有其他功能吗？”
- “能否提供一些该 Skill 的使用示例？”
- “用户会说什么来触发该 Skill？”

为避免让用户感到不知所措，请勿在一条消息中提出过多问题。

### 步骤 2：规划可复用的 Skill 内容

通过以下方式分析每个示例：

1. 考虑如何从头开始执行该示例
2. 确定应赋予 Claude 的适当自由度
3. 确定在重复执行这些工作流时，哪些脚本、参考资料和资源会有所帮助

**使具体程度与任务风险相匹配：**
- **高自由度（文本说明）**：存在多种有效方法
- **中等自由度（带参数的伪代码）**：存在首选模式，同时允许适当变化
- **低自由度（精确脚本）**：操作容易出错，一致性至关重要

### 步骤 3：初始化 Skill

如果 Skill 已经存在，请跳过此步骤。

从头创建新 Skill 时，始终运行 `init_skill.py` 脚本：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

该脚本会创建一个模板 Skill 目录，其中包含正确的 frontmatter、资源目录和示例文件。

### 步骤 4：编辑 Skill

在开始编写之前，请获取 Anthropic 的最佳实践文档（链接见上文“Skill 创建最佳实践”）和方法论参考资料——即使你觉得自己已经了解这些内容，也要这样做：文档会更新，训练数据中的版本会过时，而“我基本知道”恰恰是编辑者会跳过这一步并错过最新指导的状态。

编辑时，请记住，该技能是为另一个 Claude 实例创建并使用的。请重点关注对 Claude 有益且并非显而易见的信息。

**现有技能迁移门禁——首次编辑前必须完成：**

1. 编辑前，完整捕获当前捆绑包。对于非 Git 源或存在未提交更改的源，请使用该工具，以便快照包含可验证的来源清单：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression snapshot \
     --source <path/to/skill-folder> \
     --output <workspace>/skill-before
   ```

   对于由 Git 跟踪且工作区干净的源，请从选定的引用中实体化该目录。应包含 SKILL.md、参考资料、脚本、资产、工作流和现有评估，而不仅仅是主提示词。切勿复制已经编辑过的目录树并将其标记为“before”。
2. 盘点旧技能的参与者/任务、触发上下文、运行时契约、命令/标志、失败与恢复情形、页面/域变体、捆绑资源以及评估覆盖范围。在进行结构性重写之前，为旧有的重要边缘行为添加保留用例。
3. 编辑后，生成新旧版本对比审查：

   ```bash
   cd <skill-creator-path>
   uv run --with PyYAML python -m scripts.audit_skill_regression compare \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --output <workspace>/skill-regression-review.json \
     --baseline-origin pre-edit-snapshot
   ```

   如果旧目录是从 Git 重建的，请将最后一个标志替换为 `--baseline-origin git-ref:<ref>`。该工具会将该引用解析为不可变提交，并根据该目录树验证所有已包含的文件及其可执行位。

4. 审查每个候选项。必须且只能使用一种处置方式，并记录具体证据/理由：`preserved_or_moved`、`intentional_sanitization`、`intentional_boundary`、`removed_by_explicit_user_request`、`not_reusable` 或 `true_gap_fixed`。运行时能力不能使用 `not_reusable`；将运行时能力移出此技能时，必须提供负责该能力的目标位置、当前边界证据以及可追溯的用户批准。明确弃用时，也必须引用或追溯用户的批准。保留、净化或修复声明必须指向真实的当前文件和行，并包含一段简短的 `contains` 引文，以便验证程序能够在附近定位。文件级候选项应使用当前文件指纹，并附上具名的语义审查，说明行为为何得以保留——仅凭指纹只能证明文件身份，无法证明能力得以保留。

   不要手动编辑审查 JSON，也不要每轮都重写同一个填充脚本——`classify` 子命令会完成机械性工作（在目标文件中定位引文所在行、填充 evidence/semantic_review，并在缺少引文或理由过短时快速失败）。你仍需撰写每一项处置方式和理由；它只负责将其录入：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression classify \
     --review <workspace>/skill-regression-review.json \
     --after <path/to/skill-folder> \
     --map <workspace>/dispositions.json \
     --reviewer "<who-reviewed>"
   ```

其中，`dispositions.json` 将候选项的索引（或 id）映射到
   `{"destination": "<rel-file>", "needle": "<verbatim current quote>",
   "reason": "<why this counts as preserved/sanitized/…>",
   "disposition": "preserved_or_moved"}`（disposition 默认为
   `preserved_or_moved`；文件级候选项只需提供 destination 和长度超过 40 个
   字符的 reason——指纹会自动为你计算）。**请从目标文件中复制 needle
   （使用 Read/grep/sed），绝不要凭记忆输入**——查找采用精确匹配，缺少引文时会立即失败，而手动输入的
   needle 实际失败的两种情况是全角与半角标点混淆（`：` 与 `:`），以及
   凭记忆改写时使用了近义字符（`也` 与 `都`）——这两种问题都会逃过
   自查，并且只有当工具拒绝你的整个映射时才会被发现（有一个映射正是因为这两个原因
   连续被拒绝了两次）。
5. 验证已完成的审查。任何后续编辑都会因哈希变化而使审查失效，
   因此当候选项发生变化时，请重新生成并重新分类。验证通过后会写入
   `.skill-regression-reviewed`，这是一个与内容绑定的本地状态凭证。
   它有助于检测后续编辑，但特意不作为独立的打包授权依据；
   打包流程会自行重新验证已完成的审查：

   ```bash
   uv run --with PyYAML python -m scripts.audit_skill_regression verify \
     --before <workspace>/skill-before \
     --after <path/to/skill-folder> \
     --review <workspace>/skill-regression-review.json
   ```

每个门禁步骤成功时的输出如下（真实输出，因此可据此识别无声失败）：

   ```
   $ … compare …
   Regression audit: 8 candidate(s), 371 exact preservation(s)   # exit 1 = candidates to review
   $ … classify …
   Classified 8 candidate(s).                                    # exit 1 = some still unclassified
   $ … verify …
   Skill regression review passed.
   Regression attestation created: .skill-regression-reviewed    # exit 0 = gate cleared
   ```

`compare` 返回 1 表示存在需要审查的候选项，而不是工具执行失败；
返回 2 表示调用或运行时失败。该工具可以证明内容的精确移动和接口
保留情况，但特意拒绝根据模糊的词语重合来推断语义等价性。
“check permission denied” 这样的通用短语不能在不提示的情况下
替代“已登录但不具备角色”这一精确约定。还要检查标记为
`only_outside_runtime` 的候选项：如果运行时行为只存在于 eval、测试或
不可达的参考资料中，那么正常调用路径中就不存在该行为。

**每次编辑 SKILL.md 后都要立即验证——不要等到打包时（步骤 7）。** 这确实能及早捕获实际问题：将 frontmatter 的 description 写成未加引号的 YAML 标量，在 Claude Code 的宽松解析器中可以正常解析，但在严格解析器中会失败（codex 曾对一个已经发布数月的 skill 报告 `invalid YAML: mapping values are not allowed`）；而未加引号的 description 中如果包含 ` #`，甚至不会报错——它会悄悄截断其后的所有内容，导致触发关键词消失，而所有扫描仍然显示正常。

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.quick_validate <path/to/skill-folder>
```

**将描述写成 YAML 块标量**（先写 `description: >-`，后接一个缩进段落），只要其中包含 `: `、` #` 或多个句子——块标量原生支持这两种字符——这是自上述事件以来，每个新增或编辑过的描述都应遵循的推荐惯例。

**更新现有 Skill 时**：扫描每一处现有引用和捆绑资源，并进行相应更新，然后通过上述迁移门禁。迁移契约时，SKILL.md 中必须有直接的运行时指针；评测或变更日志不能替代它。

接下来的三项检查是**升级探针，而不是无条件扩大范围**。如果根据其中任何一项采取行动会新增或实质性改变某项能力、工作流分支、输出契约、脚本行为、依赖项、权限或外部写入，请在更改 Skill 前停止并将其重新归类为第 3 级。第 1 级和第 2 级可以审视这些问题，但不会因此获得新的交付事项。

**脚本检查**：在宣布编辑完成之前，先问：*源对话（或评测记录）编写了哪些代码——若不这样做，今后每次调用都会重新编写这些代码？* 当所选级别已经授权开展该能力相关工作时，将其捆绑进 `scripts/`（参数化、净化处理），并修改文档以指向该脚本。否则，将此信号记录为第 3 级提案，不要将其作为第 1/2 级的附带影响捆绑进来。分工原则是：**脚本负责执行，文档负责传达理解**——如果某个 Skill 的方法只存在于文字说明中，那么每次运行都要重新支付完整的编写成本。这项检查之所以放在这里，即编辑步骤中，正是因为跳过评测循环的路径（对话提炼、直接编辑）永远不会触及“改进 Skill”中针对评测记录的此项检查版本。

**组件架检查（针对嵌入制品的片段提出同一个问题）**：脚本检查覆盖由 *Skill* 执行的代码；生成制品的 Skill（报告页面、演示文稿、文档）还会积累嵌入其*输出*的片段——图像叠加层组件、粘性导航栏、图表配置、CSS 块。如果连续生成的输出都手写了相似的片段，这就是同一种重复信号，只是指向了另一个架子。在添加 `components` 子文件夹或注册表引用之前，请应用上述升级规则；第 1/2 级应提出该提案，但不得创建组件能力。当第 3 级获得授权后，真正将代码片段转化为架上组件的是围绕它建立的契约：(a) **逐字嵌入块**——将 BEGIN/END 标记及其间内容完整复制到制品中，零依赖，从而让单文件制品保持自包含；(b) **注册表条目**，说明交互契约（触发方式、按键绑定、关闭行为、边界情况）和来源——它来自哪个已交付制品、用户何时批准了它；(c) **准入门禁**——只有用户实际使用并批准过的片段才能进入（将已批准语料库的纪律应用于交互；未经批准但很漂亮的片段不得进入）；(d) **行为冻结，外观可调**——经过校准的行为和按键绑定属于契约，不得在不同运行之间发生漂移，而颜色和尺寸可以遵循制品的风格基调；(e) **回写循环**——为某个制品发明的片段，应在其获得批准的同一会话中晋升到组件架。其重要性不仅在于节省 token：手工重写的片段会发生*漂移*——每次重写都会细微地改变按键绑定、关闭行为、计数器——而对于每天阅读这些制品的用户来说，交互一致性就是产品体验。用用户为第一个此类组件架定下的原话来说：交互形式要沉淀下来、可复用、有复利，代表一致的交互喜好 (2026-07)。真实案例（已移除项目指纹）：某个报告页面 Skill 的灯箱画廊组件（图像叠加层：←/→ 循环浏览分组，ESC 关闭，原位缩放，n/N 计数器）及其交互组件注册表引用——在用户纠正跳转式引用的同一会话中提取，并在交付前通过自动化点击遍历测试完成验证。参见方法论案例 17。

**流水线检查**：考虑此技能的输出是否会自然地流入另一个技能，以及是否应由某个现有技能串联*进入*此技能。新增或实质性更改“下一步”交接机制或流水线契约，要求在编辑前重新归类为第 3 级；第 1/2 级可以提出该建议，但不得顺手将其加入。

### 第 5 步：净化审查（任何公开技能都必须执行）

**在进入此关卡之前，如果纪律 #5 规定需要执行独立审查，则该审查必须已经完成**，并且当前更改的 `independent-review.md`（位于你由私有 git 跟踪的知识仓库中——而不是已清空的工作区，也不是任何当前或将来可能公开或分发的仓库）必须存在，**且已提交**。新技能始终需要执行此审查；对于现有技能，请采用下一段中的阈值。文件只是以未提交状态留在 git 工作目录中，与从未写入该文件并无实质区别；`ls`/`test -f` 只能确认它存在于磁盘上，不能确认它会被保留下来。对于**新**技能，这是内容第一次离开你掌控的步骤，因此也正是在此处真正强制执行该纪律，而不只是口头声明——一条写在使用位置上方 1000 行、却没有任何检查机制的规则，每次都会输给尽快完成任务的冲动。

**对于已发布技能的编辑，内容离开你掌控的时刻是推送，而不是此步骤。** 对此关卡可以只用一句“仅限内部，跳过”作答，而对于仅修改文档的更改，打包甚至可能根本不会运行——因此，把审查锚定在此处意味着技能编辑可能在完全未经独立审视的情况下进入公开分支。真实案例（2026-07）：对此文件本身的一次更改发布了一个发现命令，但该命令无法访问其旁边正文声称能够覆盖的三个根目录；它被合并了，直到*事后*安排的审查才发现问题。**因此，对于现有技能：必须在 `git push` / 创建 PR 之前完成独立审查并记录其产物——推送时运行的关卡（回归审计、验证、扫描）检查的都是结构，它们都无法判断说明本身是否错误。** 此处原样沿用纪律 #5 的阈值：当*规则、契约或数字发生更改*时，需要执行审查；拼写错误修正或纯格式调整则不需要。让拼写修正也必须等待一轮审查，只会培养纪律 #6 所警告的那种条件反射——“这次改动很小”会变成普遍适用的豁免理由，继而连真正重要的更改也被涵盖进去。

**对于将进入公开仓库的技能，此步骤不可省略。** 私有内容经常泄漏到公开技能中，而扫描器漏掉的泄漏才是危险的——非英语语言中的真实姓名、真实对话记录中逐字照搬的一行内容、被直接放入示例说明中的真实案例。仅当该技能确实只供内部使用时，方可跳过。

**应按发布目标而不是主题来界定审查范围。** 只有将公开发布的产物——即技能包本身——需要进行净化。保留在私有仓库中的配套文档（提炼出该技能的事件报告、内部运行手册、项目的 CLAUDE.md）应保留其真实主机名、路径和时间戳：对这些内容进行脱敏会破坏其审计价值，并最终导致你不得不撤销这些更改。某次提炼工作之所以经历了三轮返工，正是因为脱敏处理被应用到了源材料涉及的所有内容，而不只是公开技能。

**先检查目标位置，并让检查结果预先决定建议选项。** 对该 Skill 将要存放的仓库运行
`gh repo view --json isPrivate`（或者阅读 `quick_validate` 已经打印的提示）。
如果目标位置是私有的，默认建议应当是选项 C，而不是事后才想到它——“除非另有说明，否则假定为公开”
正是导致私有 Skill 中原本可用的路径被替换成无人要求的占位符的原因。

**触发净化处理的条件是目标位置的 `isPrivate`，而不是这项任务在多大程度上
让人感觉像是在发布。** 这两者可能并不一致，而当它们不一致时，除非你明确指出这一点，
否则感觉会占上风。将内容移入*市场中的 Skill* 会让人感觉像是在发布——市场就是分发内容的
地方——因此，即使源仓库和目标仓库都是私有仓库、内容根本不会流向任何地方，也会触发净化处理的
本能反应。真实案例（2026-07）：一次从项目级 Skill 到私有市场 Skill 的迁移，
将一个真实配置路径、一个真实十六进制值以及一个真实的具名示例泛化成了
占位符。`quick_validate` 在**每次**运行时都打印了 `🔒 audience: private`；
作者每次都读到了，却依然进行了净化处理，因为这项*活动*看起来像是在
发布。其代价并非只是表面上的——真实路径能让下一位读者据此
检查对应的值；而“项目自己的令牌文件”则无法被打开。

所以，应当把它变成一次查找，而不是一次判断：**读取目标位置的 `isPrivate`，如果它
是 `true`，则只有所有者明确提出要求时才进行净化处理。** 私有→私有的迁移只是
迁移，而不是发布。**当两种探测方式都无法给出答案时**（尚无远程仓库、未运行
`quick_validate`），你就没有可供查找的结果——此时回退为将其视为公开内容，*并明确说明这一点*，
因为风险的不对称性决定了应当这样做：一次不必要的提问只多花一句话，而一次不必要的泄露
却无法挽回。此外，`isPrivate` 报告的是目标位置**当前**的状态——一个位于私有仓库中、
正在准备发布的 Skill，应当在真正将其公开的那次推送中执行净化，而不是在这一次。
如果你发现自己正在推断私有目标位置中的某项内容是否“应该”被泛化，
这种推断本身就是一个警示信号。

使用 **AskUserQuestion** 确认处理深度（对于公开目标位置，确认的是处理深度，
而不是是否要处理；对于私有目标位置，则确认是否确实需要处理）：

```
This skill will be public. I'll do a sanitization pass — the core of it is
me reading the whole skill and judging each name/example/snippet, because
scanners miss real content that has no keyword to match.

Options:
A) Full — I replace everything that looks lifted from a real project/person
B) Selective — I show you each finding and you decide (Recommended)
C) This skill is genuinely internal-only — skip
```

**净化流程——通读是核心方法，扫描只是辅助工具：**

1. **亲自通读整个 Skill，并根据语义进行判断**（这才是真正的检查）：SKILL.md + 每一份参考资料 + 每一个示例。对于每个具体名词、示例和片段，都要询问：“这是通用占位符或公开实体，还是取自真实项目、人物或对话记录？”替换后者——即使扫描器没有标记它。这是捕获不含关键字的泄露内容的唯一方法。完整指南及该语义问题见 [references/sanitization_checklist.md](references/sanitization_checklist.md)。
2. **将扫描器作为低成本的第一轮检查来运行**：检查清单中的 grep 模式 + `security_scan.py`（第 6 步）。它们能快速捕获明显的密钥、路径和已知名称——但“没有匹配项”并不表示通过检查。
3. **替换**每一处发现项，使用能够保留教学要点的通用等价内容（真实姓名 → 公众人物或 `<placeholder>`，真实片段 → `<placeholder>`）。两条通过惨痛经验总结出的规则：占位符本身不得包含真实值——`<acme-corp-domain>` 恰恰泄露了它原本应该隐藏的名称；应改为描述其*角色*（`<api-domain>`、`<upstream-provider>`）。此外，使用脚本进行批量替换时，应为其提供一个明确的文件白名单，并将范围限定在 Skill 目录内——不限定范围的查找替换会毫不犹豫地改写项目自己的 CLAUDE.md，迫使你使用 git 恢复。
4. **通过重新阅读来验证，而不是重新执行 grep**：重新阅读已更改的部分，并确认没有损坏的引用。

### 第 6 步：安全审查

在打包或分发 Skill 之前，请运行安全扫描器，以检测硬编码的机密信息和个人信息：

```bash
# Required before packaging
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder>

# Verbose mode includes additional checks for paths, emails, and code patterns
uv run --with PyYAML python -m scripts.security_scan <path/to/skill-folder> --verbose
```

**检测范围：**
- 通过 gitleaks 检测硬编码的机密信息（API 密钥、密码、令牌）
- 在详细模式下检测个人信息（用户名、电子邮件地址、公司名称）
- 在详细模式下检测不安全的代码模式（命令注入风险）

**未涵盖的内容** — 这正是仍然需要执行第 5 步通读检查的原因：gitleaks 和正则表达式规则只能匹配*已知的机密信息格式以及你列出的模式*。对于不含关键词的私密内容，它们在结构上无能为力——例如，使用非英语语言书写的真实人物/项目名称、真实谈话记录中逐字引用的一行内容，或直接取自你自己工作的真实示例。`security_scan` 显示通过意味着“未发现已知格式的机密信息”，**而不意味着**“该 Skill 已完成敏感信息清理”。绝不要将其理解为后者。

**首次设置：** 如果尚未安装 gitleaks，请进行安装：

```bash
# macOS
brew install gitleaks

# Linux/Windows - see script output for installation instructions
```

**退出代码：**
- `0` - 无问题（可安全打包）
- `1` - 高严重性问题
- `2` - 严重问题（分发前必须修复）
- `3` - 未安装 gitleaks
- `4` - 扫描错误

**在私有 Skill 中，扫描结果只是一条信息，而不是一项必须执行的工作。** 扫描器无法
区分泄露的凭据与*本来就应该存在于其中*的凭据——例如，一个价值就在于预先填好内容的模板，或一个指向其唯一运行机器的脚本。
绝不要在私有仓库中自动修复：报告发现的内容，并让所有者自行选择。下面的选项 A
（“自动修复”）适用于准备公开发布的 Skill。

**如果发现问题**，请通过 **AskUserQuestion** 展示：

```
Security scan found [N] issues in "[skill-name]":
- [SEVERITY] [file]: [description]
- ...

RECOMMENDATION: Fix automatically — these look like [accidental leaks / false positives].

Options:
A) Fix all issues automatically (Recommended)
B) Review each finding — let me decide per-item (some may be intentional)
C) Override and proceed — I accept the risk for internal distribution
```

### 第 7 步：打包 Skill

Skill 准备就绪后，将其打包为可分发文件：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder>
```

对于 Git 已跟踪的每个现有 Skill，在提供并重新验证已完成的
审查之前，打包操作都会被阻止。当前的标记仅是本地状态回执，
因此先提交或手动编写标记都无法绕过审查。下一次编辑后，
审查即会过期：

```bash
uv run --with PyYAML python -m scripts.package_skill \
  <path/to/skill-folder> \
  --regression-review <workspace>/skill-regression-review.json
```

可选的输出目录，以及用于包含根 `evals/` 目录的 `--include-evals`（该目录作为开发资源默认被排除）：

```bash
cd <skill-creator-path>
uv run --with PyYAML python -m scripts.package_skill <path/to/skill-folder> ./dist --include-evals
```

打包脚本将：

1. 自动**验证**技能（YAML 前置元数据、命名约定、路径引用完整性）
2. 每当 Git HEAD 中已包含该技能时，**重新核验已完成的现有技能回归审查**；仅有标记绝不构成打包授权
3. **验证安全扫描**（内容哈希必须与上次扫描匹配）
4. 将技能**打包**为可分发的归档文件

如果验证失败，脚本会报告错误并退出，不会创建软件包。

### 第 8 步：更新市场

打包后，更新市场注册表以包含新增或更新后的技能。

**对于新技能**，向 `.claude-plugin/marketplace.json` 添加一个条目：

```json
{
  "name": "skill-name",
  "description": "Copy from SKILL.md frontmatter description",
  "source": "./skill-name",
  "strict": false,
  "version": "1.0.0",
  "category": "developer-tools",
  "keywords": ["relevant", "keywords"]
}
```

**对于更新后的技能**，按照语义化版本规范提升 `plugins[].version` 中的版本号。对技能文件的任何更改——哪怕只是修复一个单行拼写错误——都需要提升版本号：否则，`marketplace update` 不会检测到新版本，因此**已安装的副本永远不会刷新**，用户会继续运行旧技能，而你的修复仍未发布。

**然后在变更日志中记录它——这一步最容易被跳过。** 版本号提升使更新变得*可安装*；相应条目则使它在六个月后仍然*可查找*，届时如果有人遇到同样的问题，就能通过搜索找到它。而如果一份变更日志记录了其他每个技能的版本，却悄无声息地遗漏了你的技能，那还不如完全没有变更日志：这些空白看起来就像是“那里什么都没变”。

应遵循现有条目的格式，而不是自行发明一种——在 Keep a Changelog 格式的文件中，通常是 `- **skill-name** (\`suite\` vX.Y.Z): what broke, why, and what proves it fixed`。应在提升版本号的**同一个提交**中写入；“稍后”再更新的变更日志，最终往往永远不会被更新。

真实案例（2026-08）：某个技能连续发布了两个版本，版本号提升正确、门禁检查通过、PR 也已合并——但**完全没有变更日志条目**，因为本流程中没有任何步骤要求添加条目。直到后来的一次审计才发现这两次遗漏。这正是将纪律 #6 应用于本文件本身：如果一条规则只存在于约定中，而没有落实为明确步骤，那么每次它都会败给尽快完成任务的驱动力。

**尽量缩小注册表差异——这是所有技能共享的唯一文件。** 市场清单是所有并发编辑者都会发生冲突的地方，因此在那里进行一次无关的格式更改，代价远高于在其他任何地方进行同样的更改：它会把原本干净的三行版本号提升，变成另一个正在编辑该文件的人必须处理的冲突。使用脚本更新时（解析为 JSON、修改、再写回），重写过程会悄无声息地规范化一些原文件可能未采用的格式——末尾换行符、缩进宽度、键顺序、Unicode 转义。往返修改规范：之后重新读取文件，并对其运行 `git diff --stat`；**唯一允许出现的行应当是你有意更改的字段。** 如果出现额外行，应恢复文件原有的格式约定，而不是提交这种规范化更改（曾有一次脚本化版本号提升给一个从未以换行符结尾的清单添加了末尾换行符——在最有可能同时被其他人编辑的文件中，白白多出了一行差异）。同样的原则也适用于技能涉及的任何共享注册表：锁文件、目录、索引文档。

**当一个 PR 经历了几次合并后仍未落地，就执行 rebase——然后证明你没有吞掉任何人的工作。** manifest 之所以容易发生冲突，也正是它容易过时的原因：只要其他变更先行合入，任何同时修改 registry 和 changelog 的开放 PR 都会产生冲突，因此应当预期看到 `mergeable: CONFLICTING`，而不是把它当成意外（曾有一个 PR 在 main 一个下午前进了 7 个 commit 后就遇到了这种情况）。如果仓库采用 squash merge，就应当 rebase 而不是 merge——在经过 squash 的历史记录中添加 merge commit 没有任何意义。冲突本身几乎总是**增量式的**：两位作者分别在同一节追加了自己的条目，因此解决方式是**两者都保留**，绝不要使用 `--ours`/`--theirs`，因为这会悄无声息地丢弃同事添加的那一行。

人们往往会跳过的，恰恰是能够发现错误冲突解决的步骤——**解决冲突后，证明相对于基线的唯一差异就是你的改动：**

```bash
# Every version the base has vs. what your branch has; the diff must contain
# ONLY the entry you bumped. Anything else means the resolution ate someone's work.
python3 -c "
import json,subprocess
mine=json.load(open('<manifest>'))
base=json.loads(subprocess.run(['git','show','origin/main:<manifest>'],capture_output=True,text=True).stdout)
b={p['name']:p['version'] for p in base['plugins']}; m={p['name']:p['version'] for p in mine['plugins']}
print({k:(b.get(k),m.get(k)) for k in set(b)|set(m) if b.get(k)!=m.get(k)})"
```

然后使用 `--force-with-lease` 推送，绝不要只使用 `--force`：如果远程分支在你上次 fetch 后发生了变化，lease 会让推送失败，而这正是有人向你的分支推送了内容、普通强制推送会将其抹除的情形。

**插件边界不属于此 Skill 的职责范围。** 是否要将 Skill 拆分到
不同的插件中、如何组织 `source`/`skills`，以及用户能否单独启用或禁用
Skill，都属于打包/分发领域——这里的 SSOT 是
`marketplace-dev` Skill，而不是本文。当任务确实需要做出这些决策时：
确保 `marketplace-dev` 可用（如果缺失则自动安装——方式与
`skill-reviewer` 在需要相关脚本时引入 `skill-creator` 相同），然后阅读
marketplace-dev 的 cache-and-source-patterns 参考文档并遵照执行。不要在这里复述
其中的规则；副本会逐渐产生偏差。

**重命名、迁移或移除 marketplace 条目是一项破坏性变更**，会影响
所有已经安装它的用户——条目消失时，Claude Code 不会清理已安装的副本，
从而留下悬空安装，并在每次执行 `marketplace
update` 时出错。应当像对待 API 弃用一样处理此类变更：在
changelog 中提供迁移说明，并按照 marketplace-dev 的指导完成具体操作。

**如果你亲自提交/推送 Skill 仓库：** 对于现有 Skill，如果当前变更达到了准则 #5 中规则/契约/数字变更的阈值，请确认审查产物记录了本次变更并且已经提交（使用 `git status` 和 `git log -1 -- <artifact>` 检查其确切路径，而不能仅仅确认历史上存在某个 `independent-review.md`）。拼写错误修复或纯格式调整不需要该产物；旧审查永远不能满足当前实质性变更的要求。步骤 5 的注释解释了为什么对于已经发布的 Skill，真正的强制执行点是 push，而不是打包。然后只暂存该 Skill 的明确路径（`git add <skill-dir> .claude-plugin/marketplace.json`）——绝不要使用 `git add .`；工作树通常充斥着无关变动，否则它们会一并进入 commit（曾有一个 commit 意外包含了一大批无关的 transcript 文件，最后不得不执行 `git reset` 并重新暂存）。推送前，使用 `gh repo view --json visibility,isPrivate` 确认仓库的真实可见性，而不要根据路径进行猜测——公共 Skill 仓库应当走 PR + review 流程，而不是直接推送到 main。

### 第 9 步：发布或迭代

完成 Skill 后，使用 **AskUserQuestion** 确定后续步骤：

```
Skill "[name]" is complete. Security scan passed, marketplace updated.

RECOMMENDATION: [pick based on state — e.g. "B) optimize the description" if triggering was never verified, else "D) done for now"] because [one-line reason].

Options:
A) Package and export as .skill file for distribution
B) Run description optimization — improve auto-triggering accuracy (~5 min)
C) Expand test set and iterate more — add edge cases before shipping
D) Done for now — I'll test it manually and come back if needed
```

测试 Skill 后，用户可能会要求改进。这通常发生在刚刚使用 Skill 之后，此时他们对 Skill 的表现仍有清晰印象。

**优化筛选原则：** 只添加能够解决已观察到的问题的内容。如果最佳实践已经涵盖了相关内容，请勿重复。

## Claude.ai 专用说明

在 Claude.ai 中，使用相同的验证深度路由。当选择通用的 Tier 3 路径时，完整工作流仍然是草拟 -> 测试 -> 审查 -> 改进 -> 重复，但由于 Claude.ai 没有子代理，部分机制需要调整。以下是需要适配的内容：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，先阅读 Skill 的 SKILL.md，然后按照其中的说明，自行完成测试提示所要求的任务。逐个执行测试用例。这不如使用独立子代理严格（因为 Skill 是你编写的，而运行它的也是你，所以你掌握了全部上下文），但它仍是一项有用的基本检查——而人工审查步骤可以弥补这一点。跳过基线运行——只需使用 Skill 按要求完成任务。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的 VM 没有显示界面，或者你正在远程服务器上操作），请完全跳过浏览器审查器。改为直接在对话中展示结果。对于每个测试用例，展示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），请将其保存到文件系统，并告知用户文件位置，以便他们下载和检查。直接询问反馈：“效果如何？有什么想修改的吗？”

**基准测试**：跳过定量基准测试——它依赖于基线比较，而在没有子代理的情况下，这种比较没有意义。重点关注用户的定性反馈。

**迭代循环**：与之前相同——改进 Skill、重新运行测试用例、征求反馈——只是中间不再使用浏览器审查器。如果有可用的文件系统，你仍然可以将结果整理到各个迭代目录中。

**描述优化**：本节需要 `claude` CLI 工具（具体来说是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，请跳过本节。

**盲测比较**：需要子代理。请跳过本节。

**打包**：`package_skill.py` 脚本可在任何具备 Python 和文件系统的环境中运行。在 Claude.ai 上，你可以运行该脚本，用户可以下载生成的 `.skill` 文件。

- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新 skill。在这种情况下：
  - **保留原始名称。** 记下 skill 的目录名称和 `name` frontmatter 字段，并保持它们不变。例如，如果已安装的 skill 是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
  - **编辑前先复制到可写位置。** 已安装 skill 的路径可能是只读的。将其复制到 `/tmp/skill-name/`，立即基于这个可写副本创建审计工具的编辑前快照，然后在该副本中进行编辑，并使用 `--regression-review` 打包。不要传入 `--new-skill`；现有 skill 的非 Git 副本仍然属于现有 skill。
  - **如果手动打包，请先在 `/tmp/` 中暂存**，然后复制到输出目录——由于权限问题，直接写入可能会失败。

## Cowork 专用说明

如果你使用的是 Cowork，需要了解的要点如下：

- 你可以使用子代理，因此通用的 Tier 3 工作流（并行启动测试用例、运行基线测试、评分等）可以正常使用。不要因为子代理可用，就将 Tier 1 或 Tier 2 变更升级处理。（如果 Tier 3 运行出现严重超时，可以串行而不是并行运行测试提示词。）
- 你没有浏览器或显示界面，因此生成评估查看器时，请使用 `--static <output_path>` 写入独立的 HTML 文件，而不是启动服务器。然后提供一个链接，供用户点击并在其浏览器中打开该 HTML。
- 在完成一次**通用 Tier 3** 运行后，在自行修改 skill 之前，始终先为人工审核者生成评估查看器，并使用 `generate_review.py`，而不是自定义 HTML。Tier 1、Tier 2 以及明确替代了查看器机制的专用工作流，不会仅仅因为工作在 Cowork 中进行，就产生生成查看器的义务。
- 反馈的工作方式有所不同：由于没有正在运行的服务器，查看器中的 “Submit All Reviews” 按钮会将 `feedback.json` 下载为文件。然后你可以从该文件中读取反馈（可能需要先请求访问权限）。
- 打包功能可以正常使用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常运行，因为它通过子进程使用 `claude -p`，而不是浏览器；但请等到 skill 制作全部完成，并且用户认可其状态良好后再进行。
- **更新现有 skill**：用户可能要求你更新现有 skill，而不是创建新 skill。请遵循上方 Claude.ai 章节中的更新指南。
