# 拉取请求

在整个 PR 生命周期中使用此技能，而不仅仅是在打开或合并 PR 时使用。

## 运行时设置

对于 Basic Memory Python 工具，请优先使用项目环境：

```bash
source .venv/bin/activate
```

激活后，使用 `python ...` 运行 Python 脚本。对于不便激活环境的一次性命令，优先使用 `./.venv/bin/python ...` 或仓库的 `uv run ...` 模式。不要仅仅因为缺少某个命令，就退回使用系统的 `python`、`python3` 或全局包。

## 流程

1. 首先检查当前实际产物。
   - 在决定要更改什么之前，使用 `gh pr view`、`gh issue view`，查看关联的审查评论、CI 状态和当前分支状态。
   - 如果用户链接了某个特定的 PR 讨论，请先检查该讨论，再进行大范围编辑。

2. 保持分支范围清晰。
   - 基于预期的远程基础分支创建产品修复 PR。
   - 避免将工作流、技能或文档提交混入无关的产品分支。
   - 在 `basic-memory` 中，除非用户要求使用工作树，否则优先在主工作区中使用本地分支。

3. 实现并验证。
   - 编辑前完整阅读文件。
   - 进行行为层面完整且范围最小的更改。
   - 针对变更涉及的范围运行聚焦测试。
   - 在宣布分支已就绪之前，运行仓库要求的检查关卡，例如对源代码变更运行 `just fast-check`，或对代理/包变更运行 `just package-check`。

4. 编写或更新 PR 描述。
   - 没有实用描述的 PR 不能算完成。
   - 如果现有的 `pr-description` 技能可用，请使用它。
   - PR 正文应向未参与聊天过程的审查者解释此次变更。

5. 打开或更新 PR。
   - 包含关联的议题、审查评论或规范。
   - 包含准确的验证命令及其结果。
   - 仅当 PR 有意尚未准备好接受审查时，才将其标记为草稿。

6. 立即进入审查循环。
   - 在打开 PR、推送、对 PR 正文进行有实质意义的更新之后，或当用户询问 PR 是否已就绪时，使用 `pr-review-loop`。
   - 当用户期望后续跟进审查时，不要将创建 PR 视为任务的终点。

## 范围纪律

Codex 反馈是对抗性输入，并非有权重新定义拉取请求的权威。在针对审查发现更改
代码之前：

1. 重述 PR 的 `Why`、验收标准以及需要保护的行为。
2. 针对当前 head 追踪或复现具体故障。
3. 对审查发现进行分类：
   - **范围内的阻断问题**：分支引入的任何回归，或对既定行为、验收标准、安全边界、数据完整性或必需检查的直接违反。在当前 PR 中修复。
   - **支线任务 / 过度打磨**：推测性的加固、更广泛的并发模型、无关的清理、新的抽象，或对既定结果并非必需的改进。用证据反驳，并将其排除在该分支之外。
   - **快速跟进项**：确实存在且影响重大的问题，值得处理，但可与当前结果分离。保持当前 PR 聚焦，并单独跟踪该问题。

狭窄的 PR 措辞绝不能让当前分支引入的回归变成快速跟进项。应将当前分支造成的每一项
回归都视为范围内的阻塞问题，即使 `Why` 或验收标准中遗漏了受影响的行为。

不要照单全收 `P1`、`P2` 或其他严重程度标签。严重程度必须根据可复现的影响和产品契约来
确定。尤其是，当文档中规定的行为允许最终一致性时，不要仅仅为了处理每一种理论上可能的
交错情况而添加锁、租约、重试、迁移或通用框架。

对于范围外的反馈，应在评审讨论串中回复范围边界及支持证据。如果该问题本身非常关键或因
其他原因值得安排处理，并且用户已经授权创建议题，则创建一个快速跟进议题；否则，请提供
拟议的议题标题和正文并征求用户意见。链接 PR 和评审评论，说明具体影响，并为跟进项制定
独立的验收标准。不要将跟进项的实现混入当前产品分支。

## PR 描述标准

每个 PR 正文都应包含以下要点，并使用符合仓库风格的标题：

- `Why`：说明为什么现在必须进行这项变更，包括问题、评审意见、议题、事故、用户需求或规范要求。
- `What Changed`：使用便于评审者理解的语言，说明具体变更的行为或文件。
- `Implementation Details`：说明重要的设计选择、约束、权衡、数据流变更，或为何没有采用看似更简单的替代方案。
- `Testing`：列出实际运行的命令以及它们是否通过。如果有相关内容未测试，应明确说明。
- `Risks / Follow-ups`：说明仍然存在的不确定性、发布顾虑、已知的延后工作，或为何不存在这些问题。

避免 PR 正文只是重复提交消息。相较于冗长的变更日志，应优先提供简短但完整的说明。

## Codex 评审循环

将 `pr-review-loop` 作为常规 PR 工作的一部分：

- 创建可供评审的 PR 后，检查 Codex 状态和 CI。
- 如果 Codex 显示眼睛表情，请继续监控；眼睛表示待处理，而不是批准。
- 如果 Codex 留下反馈，应立即对其范围进行分类，并在可能的情况下让测试继续运行。
- 如果反馈正确且属于范围内，则进行修复、运行针对性验证、推送，并在新的提交头上重新启动
  循环。
- 如果反馈错误、仅属推测、属于过度设计或超出范围，则使用证据进行反驳，在回复后解决
  该讨论串，并继续推进循环。
- 如果另一个问题非常关键，应创建或提议一个快速跟进议题，而不是扩大当前 PR 的范围。
- 只有当必需的检查全部通过，并且 Codex 以点赞批准了最新提交头时，循环才算完成，除非用户明确要求绕过该门禁。

在循环状态得到明确说明之前，不要合并、宣称已可合并，也不要像工作已经完成一样继续处理其他事项：

```text
Codex gate: approved | waiting | blocking | overridden
Head: <sha>
Tests: passing | pending | failing
Evidence: <thumbs-up reaction, blocking comment URL, reply URL, or explicit user override>
```

## 合并纪律

合并前：

- 确认最新的 head SHA。
- 确认该 head 上所需的检查均已通过。
- 确认当前 head 上的 Codex 评论均已处理。
- 确认已获得 Codex 的点赞或用户的明确覆盖指示。
- 除非用户已经给出合并指示，否则应询问或等待用户的合并指示。

绝不能仅凭 CI 通过就执行合并。
