# 架构图构建器

**目标：** 创建一组数量最少、易于理解且有证据支撑的图表，用于传达当前或拟议的架构。仅更改已获批准的架构文档；不要虚构关系、进行可视化产品设计、用图表取代文字证据、审查适用性或编辑实现。

**执行约定：** 将以下按顺序排列的复选框工作流视为此技能的完成定义。按顺序处理每一项，只有在其操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的裁决和批准规则应用于每个未完成项，并在开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 架构证据 | 仓库文件、运行时装配、IaC、契约和已批准的工件 | 使用带有 `UNVERIFIED` 标签的用户提供模型 |
| 关系追踪 | 语言智能、依赖分析工具和聚焦搜索 | 直接检查生产者、消费者和注册项 |
| 图表格式 | 现有仓库约定和渲染器 | Markdown 中的 Mermaid，其次是纯 ASCII |
| 语法验证 | 仓库渲染器、解析器或预览 | 手动检查围栏、标识符和关系 |
| 文档修改 | 对已批准图表工件进行最小化补丁修改 | 如果路径或证据边界不安全，则返回 `BLOCKED` |

图表用于传达模型；对于当前状态，可执行行为仍具有权威性。确保当前、目标和过渡视图在视觉上清晰区分。

## 工件规则

- 复用现有图表约定，或使用 `docs/architecture/diagrams/<view>.md`。
- 优先使用带 Mermaid 的 Markdown，以提供便于文本审查的源文件；不支持 Mermaid 时使用 ASCII。
- 仅选择能够回答特定受众问题的视图。
- 对于静态结构，从系统上下文视图和容器视图开始；仅当组件层面的深度会改变决策时，才添加组件视图。
- 对关键运行时交互和故障路径使用序列视图或动态视图。
- 对存储、敏感数据、信任边界和转换使用数据流视图。
- 对运行时节点、区域、网络、扩缩容和故障转移使用部署视图。
- 为每个图表提供标题、范围、受众、图例、元素描述以及带标签的关系。
- 确保图表源文件可在版本控制中审查。
- 当一张图需要讲述多个互不相关的故事时，应拆分视图。
- 切勿将颜色作为传达含义的唯一方式。
- 使用稳定的元素标识符和简洁的显示标签，使修订能够产生便于审查的差异。
- 将详细证据置于图表旁边，而不是塞满节点和关系。
- 保留易于理解的现有表示法；仅当新表示法能更好地回答受众问题时，才引入新表示法。

## 检查清单

### 1. 建立图表约定

- [ ] 明确受众、问题、当前或目标状态、范围、已批准的目标位置以及所需的表示法。
- [ ] 阅读仓库说明、相关架构工件以及现有的图表约定。
- [ ] 选择最少但有用的一个或多个视图；拒绝不能提升关系清晰度的图表。
- [ ] 定义证据边界，并分别标注用户提供或提议的元素。
- [ ] 除已批准的架构图文档外，确保整个过程仅执行只读操作。

### 2. 构建架构模型

- [ ] 识别与问题相关的人员、软件系统、可部署容器、组件、存储、队列和外部依赖项。
- [ ] 记录每个元素的职责、类型、与决策相关时的技术、已知时的负责人，以及当前/目标状态。
- [ ] 明确关系方向、标签、协议或数据、同步性，以及相关的信任边界或网络边界。
- [ ] 在纳入当前状态的路由、处理程序、作业、插件或消费者之前，追踪其运行时发现和注册过程。
- [ ] 将不确定的元素或关系标记为 `UNKNOWN`，而不是为了让图表看起来完整而擅自补全。

### 3. 选择并绘制视图

- [ ] 当读者需要了解系统范围和外部参与者时，创建系统上下文视图。
- [ ] 当读者需要了解职责、可部署性、存储或运维拓扑时，创建容器或部署视图。
- [ ] 仅针对其内部边界会改变理解方式的复杂区域创建组件视图。
- [ ] 为关键的成功、失败、重试、超时、恢复或迁移交互创建时序或动态视图。
- [ ] 当安全、隐私、驻留位置或权威数据源问题需要时，创建数据流或信任边界视图。
- [ ] 避免在同一视图中混合抽象层级，除非这种例外是明确且必要的。

### 4. 让图表具备自描述性

- [ ] 添加标题、图表类型、范围、当前/目标标记、目标受众以及观察或提议日期。
- [ ] 为形状、颜色、线条样式、缩写和不确定性标记添加图例。
- [ ] 使用意图或数据标注每一种关系；避免使用泛化箭头和未解释的缩写词。
- [ ] 确保名称与代码、契约和共享架构文档保持一致。
- [ ] 添加简洁的证据说明或链接，使当前状态的声明具备充分的可追溯性。

### 5. 验证并报告

- [ ] 使用仓库渲染器验证语法，或执行完整的手动语法检查。
- [ ] 检查图表在正常渲染尺寸下的可读性，并拆分负载过重的视图，而不是缩小标签。
- [ ] 根据仓库证据验证每个当前状态的元素和关系。
- [ ] 确认未更改任何 UI 设计、审计结论、代码、测试或外部状态。
- [ ] 当图表有效、范围明确且有证据支持时，使用 `READY`；当重要关系仍不明确时，使用 `INCONCLUSIVE`；当范围、证据、格式或目标位置妨碍生成可信图表时，使用 `BLOCKED`。

## 输出契约

```markdown
# Architecture Diagrams

**Verdict:** READY | INCONCLUSIVE | BLOCKED
**Artifacts:** paths

## Views created or updated
| View | State | Audience question | Evidence basis |
|---|---|---|---|

## Verification
- Syntax or render check
- Current-state relationship checks

## Unknowns and residual risks
Only missing relationships or rendering limits that affect interpretation.
```
