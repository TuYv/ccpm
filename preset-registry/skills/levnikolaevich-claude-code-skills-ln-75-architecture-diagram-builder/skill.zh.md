# 架构图构建器

**目标：** 创建数量最少且易于理解、以证据为依据的图表，以传达当前或拟议的架构。仅修改已批准的架构文档；不得捏造关系、进行视觉产品设计、替代文字证据、审计适用性，或编辑实现代码。

**执行契约：** 有序复选框是完成定义。内部将每项跟踪为 `PENDING`、以具体证据证明的 `PROVEN`、以条件不存在的证据确认的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不构成证明。每完成一节后重新核对各项。返回前解决所有 `PENDING` 项，并只统计 `PROVEN` 和 `CLEARED`；针对每个缺口应用该技能的判定和批准规则。

保留用户意图、范围和现有授权。继续执行已获授权的工作；只有存在需要作出重大选择的未解决问题或需要外部批准时才提问。根据实际风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方式。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 架构证据 | 仓库文件、运行时连接、IaC、契约和已批准的产物 | 使用带有 `UNVERIFIED` 标签的用户提供模型 |
| 关系追踪 | 语言智能、依赖工具和定向搜索 | 直接检查生产者、消费者和注册项 |
| 图表格式 | 现有仓库约定和渲染器 | Markdown 中的 Mermaid，然后是纯 ASCII |
| 语法验证 | 仓库渲染器、解析器或预览 | 手动检查代码围栏、标识符和关系 |
| 文档修改 | 对已批准图表产物进行最小补丁修改 | 如果路径或证据边界不安全，则返回 `BLOCKED` |

图表表达的是一个模型；可执行行为仍然是当前状态的权威来源。确保当前状态、目标状态和过渡视图有明显区分。

## 产物规则

- 复用现有图表约定，或使用 `docs/architecture/diagrams/<view>.md`。
- 对于文本可审查的源文件，优先使用带 Mermaid 的 Markdown；如果不支持 Mermaid，则使用 ASCII。
- 对于静态结构，选择能够回答所提问题的上下文、容器或组件层级；如果现有上下文已经足够，不要创建前置概览图。
- 确保图表源文件可在版本控制中审查。
- 如果一个图表需要表达多个无关故事，则拆分视图。
- 绝不要让颜色成为传达含义的唯一方式。
- 使用稳定的元素标识符和简洁的显示标签，使修订能够产生易于审查的差异。
- 将详细证据放在图表旁边，不要让节点和关系过于拥挤。
- 保持易于理解的现有表示法；只有在新表示法能更好地回答受众问题时才引入它。

## 检查清单

### 1. 建立图表契约

- [ ] 明确受众、问题、当前状态或目标状态、范围、批准的目标位置以及所需表示法。
- [ ] 阅读仓库说明、相关架构产物和现有图表约定。
- [ ] 选择最少但有用的视图；拒绝无法增加关系清晰度的图表。
- [ ] 定义证据边界，并将用户提供的元素或拟议元素分别标记。
- [ ] 除已批准的架构图文档外，保持本次执行为只读。

### 2. 构建架构模型

- [ ] 识别相关人员、系统、应用程序/数据存储（使用 C4 时包括 C4 容器）、组件、队列和外部依赖；区分逻辑容器与 OS/容器运行时部署单元。
- [ ] 记录每个元素的职责、类型、技术（仅在对决策有影响时记录）、所有者（如已知）以及当前/目标状态。
- [ ] 在相关情况下，确定关系的方向、标签、协议或数据、同步性，以及信任边界或网络边界。
- [ ] 在纳入当前状态的路由、处理程序、作业、插件或消费者之前，追踪运行时发现与注册过程。
- [ ] 将不确定的元素或关系标记为 `UNKNOWN`，不要为了让图景看起来完整而补全内容。

### 3. 选择并绘制视图

- [ ] 当读者需要了解系统范围和外部参与者时，创建系统上下文视图。
- [ ] 针对职责、可部署性、存储或运维拓扑，创建容器视图或部署视图；当受众的问题涉及相关内容时，纳入节点、区域、网络、扩展和故障转移。
- [ ] 仅为内部边界会改变理解方式的复杂区域创建组件视图。
- [ ] 针对关键的成功、失败、重试、超时、恢复或迁移交互，创建序列视图或动态视图。
- [ ] 当安全、隐私、数据驻留或系统记录来源问题有此要求时，创建数据流视图或信任边界视图。
- [ ] 避免在同一视图中混合不同抽象层级，除非明确说明且确有必要。

### 4. 使图表能够自我说明

- [ ] 添加标题、图表类型、范围、当前/目标标记、目标受众以及观察或提议日期。
- [ ] 添加图例，说明形状、颜色、线型、缩写和不确定性标记。
- [ ] 为每条关系标注意图或数据；避免使用通用箭头和未作解释的缩写。
- [ ] 确保名称与代码、契约和共享架构文档保持一致。
- [ ] 添加足够的简要证据说明或链接，以便追溯当前状态的声明。

### 5. 验证并报告

- [ ] 使用仓库渲染器验证语法，或执行完整的手动语法检查。
- [ ] 当有预览可用时，检查渲染后的可读性，并拆分过于拥挤的视图，而不是缩小标签。没有渲染器时，将视觉可读性记录为 `UNPROVEN`；手动语法检查不能证明渲染结果正确。
- [ ] 根据实现证据验证当前状态的元素和关系，并根据已声明的提议或明确标记的假设验证目标状态的元素。
- [ ] 当图表有效、范围明确且有证据支持时使用 `READY`；当重要关系仍未知时使用 `INCONCLUSIVE`；当范围、证据、格式或目标位置导致无法生成可信图表时使用 `BLOCKED`。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或经授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

1. **Result：** 无法判定 Skill-specific 结果；当前未提供待审阅或修改的 `SKILL.md` 片段及相关任务。

2. **Scope：** 未审阅或修改任何文件；未假设目标文件、视图、基线或验收标准。

3. **Evidence：** 未提供 Artifact paths、视图当前状态/目标状态、受众问题、证据依据或关系信息。

4. **Verification：** 未执行语法检查、渲染检查或当前状态关系检查；没有可用的外部状态或渲染证据。

5. **Completion：** `Checklist: 0/1 complete`；`Incomplete: UNPROVEN`：缺少待处理的 `SKILL.md` 片段和任务上下文，因此无法得出技能专属结论。下一步：提供需要翻译或审阅的英文片段及相关 Artifact paths。残余风险：在缺少输入前，无法验证内容完整性、Markdown 结构保留情况或渲染结果。
