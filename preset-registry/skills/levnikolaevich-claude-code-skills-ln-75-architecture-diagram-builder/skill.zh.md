# 架构图构建器

**目标：** 创建用于传达当前或拟议架构的、最少数量且易于理解并有证据支持的图表。仅修改已批准的架构文档；不得捏造关系、进行视觉产品设计、替代文字证据、审计适用性或编辑实现。

**执行契约：** 将以下有序复选框工作流视为此技能的完成定义。将每个复选框标记为 `PENDING`，然后使用具体证据将其解决为 `PROVEN`，使用证明其条件触发器不存在的证据将其解决为 `CLEARED`，或解决为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不构成证明。返回前，解决每个 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，对每个 `UNPROVEN` 项应用此技能的判定、决策和审批规则，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 架构证据 | 仓库文件、运行时 wiring、IaC、契约和已批准的工件 | 使用带有 `UNVERIFIED` 标签的用户提供模型 |
| 关系追踪 | 语言智能、依赖工具和聚焦搜索 | 直接检查生产者、消费者和注册项 |
| 图表格式 | 现有仓库约定和渲染器 | Markdown 中的 Mermaid，然后是纯 ASCII |
| 语法验证 | 仓库渲染器、解析器或预览 | 手动检查代码围栏、标识符和关系 |
| 文档修改 | 对已批准图表工件进行最小补丁修改 | 如果路径或证据边界不安全，则返回 `BLOCKED` |

图表传达的是一个模型；对于当前状态，可执行行为仍是权威依据。确保当前视图、目标视图和过渡视图在视觉上明确区分。

## 工件规则

- 复用现有图表约定，或使用 `docs/architecture/diagrams/<view>.md`。
- 优先使用带 Mermaid 的 Markdown 作为可进行文本审查的源文件；当 Mermaid 不受支持时使用 ASCII。
- 仅选择能够回答明确受众问题的视图。
- 对于静态结构，从系统上下文视图和容器视图开始；仅当增加组件深度会改变决策时才添加组件级细节。
- 对于关键运行时交互和故障路径，使用序列视图或动态视图。
- 对于存储、敏感数据、信任边界和转换，使用数据流视图。
- 对于运行时节点、区域、网络、扩展和故障转移，使用部署视图。
- 每个图表都必须有标题、范围、受众、图例、元素描述和带标签的关系。
- 确保图表源文件在版本控制中可供审查。
- 当一个图表需要讲述多个无关故事时拆分视图。
- 绝不能使用颜色作为传达含义的唯一方式。
- 使用稳定的元素标识符和简洁的显示标签，使修订能够产生易于审查的差异。
- 将详细证据放在图表旁边，而不是让节点和关系过于拥挤。
- 保留易于理解的现有表示法；仅当新表示法能够更好地回答受众问题时才引入它。

## 检查清单

### 1. 确立图表契约

- [ ] 明确受众、问题、当前状态或目标状态、范围、批准的目标位置以及所需的表示法。
- [ ] 阅读仓库说明、相关架构产物以及现有图表约定。
- [ ] 选择最少但有用的视图；拒绝无法增加关系清晰度的图表。
- [ ] 定义证据边界，并将用户提供的元素或提议的元素单独标记。
- [ ] 除经批准的架构图文档外，保持运行过程只读。

### 2. 构建架构模型

- [ ] 识别与问题相关的人员、软件系统、可部署容器、组件、存储、队列和外部依赖。
- [ ] 为每个元素记录其职责、类型、在决策相关时记录技术、已知时记录所有者，以及当前/目标状态。
- [ ] 在相关情况下明确关系的方向、标签、协议或数据、同步性，以及信任边界或网络边界。
- [ ] 在纳入当前状态的路由、处理器、作业、插件或消费者之前，追踪运行时发现和注册过程。
- [ ] 将不确定的元素或关系标记为 `UNKNOWN`，而不是为了图表美观而补全整体图景。

### 3. 选择并绘制视图

- [ ] 当读者需要了解系统范围和外部参与者时，创建系统上下文视图。
- [ ] 当读者需要了解职责、可部署性、存储或运维拓扑时，创建容器视图或部署视图。
- [ ] 仅针对内部边界会改变理解的复杂区域创建组件视图。
- [ ] 针对关键的成功、失败、重试、超时、恢复或迁移交互，创建序列视图或动态视图。
- [ ] 当安全、隐私、数据驻留或权威数据源问题需要时，创建数据流视图或信任边界视图。
- [ ] 除非例外情况明确且必要，否则避免在一个视图中混合不同的抽象层级。

### 4. 使图表能够自我说明

- [ ] 添加标题、图表类型、范围、当前/目标标记、目标受众以及观察或提议日期。
- [ ] 为形状、颜色、线条样式、缩写和不确定性标记添加图例。
- [ ] 为每条关系标注意图或数据；避免使用通用箭头和未解释的缩写。
- [ ] 保持名称与代码、契约和共享架构文档一致。
- [ ] 添加足够简洁的证据注释或链接，以便追溯当前状态声明。

### 5. 验证并报告

- [ ] 使用仓库渲染器验证语法，或执行完整的手动语法检查。
- [ ] 在正常渲染尺寸下检查可读性；拆分过载的视图，而不是缩小标签。
- [ ] 根据仓库证据核实每个当前状态元素及其关系。
- [ ] 确认未更改任何 UI 设计、审计结论、代码、测试或外部状态。
- [ ] 当图表有效、范围明确且有证据支持时使用 `READY`；当重要关系仍然未知时使用 `INCONCLUSIVE`；当范围、证据、格式或目标位置导致无法绘制可信图表时使用 `BLOCKED`。

## 输出契约

```markdown
# Architecture Diagrams

**Verdict:** READY | INCONCLUSIVE | BLOCKED
**Artifacts:** paths

## Views created or updated
| View | State | Audience question | Evidence basis |
|---|---|---|---|

## Verification
- Syntax or render check
- Current-state relationship checks

## Unknowns and residual risks
Only missing relationships or rendering limits that affect interpretation.
```
