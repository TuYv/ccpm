一个模糊的想法出现了，它对于一次智能体会话来说过于庞大，并且笼罩在迷雾中：从这里通往**目的地**的道路尚不可见。寻路的重点是找到这条道路，而不是直接冲向目的地。此技能会在仓库的议题跟踪器上将道路绘制成一张**共享地图**，然后逐一处理其中的**决策票据**（需要通过解答问题来形成决策，而不是要执行的构建工作切片），直到路线清晰为止。

每项工作的目的地各不相同，而为它命名是绘制地图的第一步：它决定了每张票据的形态。目的地可能是一份需要移交并持续迭代的规范、一项必须在规划开始前确定的决策，也可能是一项就地完成的变更，例如数据结构迁移。地图与领域无关：工程工作、课程内容，或任何符合这种形态的工作都可以。

## 规划，而非执行

寻路器默认用于**规划**：每张票据解决一项决策，而当道路清晰、在有人着手执行之前已没有任何待决事项时，地图即告完成。想要直接动手完成工作的冲动，通常意味着你已经抵达地图的边缘，是时候移交了。某项工作可以在其**备注**中覆盖这一默认行为，将执行本身也纳入地图；但若无此说明，应产出决策，而非交付物。

## 以名称引用

每张地图和每张票据都是一个议题，因此都有一个**名称**：即它的标题。在所有供人阅读的内容中（叙述、地图的“截至目前的决策”），都应使用该名称来引用它，绝不能只使用裸露的 ID、编号或 slug。满墙的 `#42, #43, #44` 难以阅读；名称则能让人一目了然。ID 和 URL 并不会消失；名称会包裹其链接，但它们应位于名称的_内部_，绝不能代替名称。

## 地图

地图是此仓库议题跟踪器中的单个议题，带有 `wayfinder:map` 标签，是规范性的产物。地图的票据是其子议题。

地图是一个**索引**，而非存储库。它列出已做出的决策，并指向保存其详细信息的票据；一项决策只存在于一个地方，即对应的票据，因此地图绝不会重述它，只会概述要点并提供链接。

**地图、其子票据、阻塞关系和前沿查询在物理上存放于何处，取决于具体的跟踪器。** 你应该已经获得了议题跟踪器。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。请查阅跟踪器文档中的“寻路操作”部分，了解此仓库如何表达这些内容。如果尚未提供跟踪器，则默认使用本地 Markdown 跟踪器。

### 地图正文

这是整张地图的低分辨率视图，每次会话只加载一次。开放票据**不会**列在其中：它们是开放的子议题，通过查询找到。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每个工单都是地图的一个**子议题**；跟踪器中的议题 ID 就是它的身份标识。工单正文是一个问题，其规模应适合在一次 100K token 的智能体会话中处理：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每个工单都带有一个 `wayfinder:<type>` 标签，其值为 `research`、`prototype`、`grilling`、`task` 之一（参见[工单类型](#ticket-types)）。

会话在开展任何工作之前，必须**首先**通过将工单指派给负责推进地图的开发者来**认领**该工单，以便并发会话跳过它。该受理人本身_就是_认领标记：一个处于开放状态且未指派的工单即为未认领。

阻塞关系使用跟踪器的**原生**依赖关系：这至关重要，因为它能在跟踪器自身的 UI 中以_可视化_方式呈现前沿，让人无需打开地图就能看到哪些工单可以领取。只有缺少原生阻塞功能的跟踪器才回退到正文约定。当阻塞某个工单的所有工单均已关闭时，该工单即为**未阻塞**；**前沿**是所有处于开放、未阻塞且未认领状态的子议题，也就是已知范围的边缘。

答案不属于正文的一部分；它会在解决工单时记录（参见[沿地图推进工作](#work-through-the-map)）。解决工单期间创建的资产应从议题中链接，而不是直接粘贴进去。

## 工单类型

每个工单要么是 **HITL**（human in the loop，与能够代表自己发言的人类_共同_处理），要么是 **AFK**，由智能体独立推进。HITL 工单只能通过这种实时交流来解决；智能体绝不能代替人类一方作答（一个自行回答自己问题的追问智能体已经违背了这一原则）。

- **研究**（AFK）：阅读文档、第三方 API 或知识库等本地资源，以查明某项决策正在等待的事实。由调用 Skill 工具并传入 "research" 的子智能体解决。当需要当前工作目录之外的知识时使用。
- **原型**（HITL）：通过调用 Skill 工具并传入 "prototype"，制作一个廉价、粗略且具体、可供反馈的产物（提纲、初稿、存根或 UI/逻辑代码），以提高讨论的保真度。将原型作为资产链接。当关键问题是“它应该是什么样子”或“它应该如何运行”时使用。
- **追问**（HITL）：对话。默认情形。始终调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"。
- **任务**（HITL 或 AFK）：在作出某项_决策_之前必须完成的手动工作：没有需要决定、制作原型或研究的内容，但在完成该工作之前讨论会受阻。例如，注册某项服务以便评估其 API、配置访问权限、迁移数据以便查看其结构。这是唯一一种重在_执行_而非决策的类型；它之所以有存在的价值，是因为它能解除对决策的阻塞，而不是因为它交付了最终目的地。智能体会在力所能及的情况下独立推进（AFK）；否则，它会向人类提供一份精确的检查清单（HITL）。工作完成后即视为解决；答案会记录完成了哪些工作，以及后续工单所依赖的任何结果事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图_有意_保持不完整：不要绘制你尚且看不到的内容。在现有工单之外是**战争迷雾**：你能隐约看出即将出现的决策和调查，但因为它们取决于仍未解决的问题，所以还无法准确界定。解决一个工单会驱散其前方的迷雾，将此时已经可以明确说明的内容逐一转化为新工单，直到通往目的地的道路变得清晰，并且不再有任何工单。

地图中的 **尚未明确** 部分正是记录这种模糊认识的地方：疑似需要回答的问题、稍后需要重新审视的领域。它是通往目的地、尚未探索的前沿：这里的一切都在范围内，只是还不够清晰，无法转化为工单。根据当前认识所允许的程度，可以写得宽泛，也可以写得详尽；对于查看工作将走向何方的协作者而言，它同时也是一块路标。

**迷雾还是工单？** 判断标准是你现在能否准确地表述问题，_而不是_ 你现在能否回答问题。

- **应创建工单的情况：** 问题已经足够明确，即使它处于阻塞状态，你目前还无法采取行动。
- **应归入尚未明确的情况：** 你还无法如此准确地表述问题。不要预先把迷雾切分成工单大小的片段：它的粒度比工单更粗，而当前沿推进到某片迷雾时，它可能演变成多个工单，也可能一个都不会产生。

**尚未明确** 不包括已经决定的事项（目前为止的决策）、已经存在的活跃工单，以及超出范围的事项（下一节）。

## 超出范围

迷雾只会聚集在_通往_目的地的方向上。目的地决定了范围，因此超出目的地的工作属于 **超出范围**：它不是迷雾，也不应放入 **尚未明确**。它在地图上有自己单独的 **超出范围** 部分：即你有意识地排除在_本次_工作之外的事项。决定它归入这里的是范围，而不是明确程度。

超出范围的工作永远不会转化为工单（前沿止于目的地），因此，只有重新划定目的地时，它才会再次出现；届时它将作为一项全新的工作，而不是原工作的延续。

将某件事排除在范围之外是一项范围界定行为，而不是路线上的一步。当一个已经存在的工单后来被发现位于目的地之外（绘制地图时被错误地纳入范围，或因某项结论而显现出来）时，请**关闭它**（已关闭的工单明确不在前沿上），并在 **超出范围** 部分留下一行：概述其要点以及超出范围的原因，并链接到已关闭的工单。它不应出现在 **目前为止的决策** 中，后者记录的是实际走过的路线；范围边界并不是这条路线上的一步。

## 调用方式

有两种模式。无论采用哪种模式，除研究工单外，**每个会话绝不能解决一个以上的工单**。

### 绘制地图

用户以一个宽泛的想法发起调用。

1. **明确目的地。** 调用 Skill 工具两次，分别使用 "grilling" 和 "domain-modeling"，以明确这张地图要寻找通往何处的路径：规格、决策或变更。目的地决定范围，因此必须首先确定。
2. **绘制前沿。** 再次进行深入追问，但这次采用**广度优先**：横向展开整个问题空间，而不是深入某一条线索，从而发现尚待决定的事项以及现在即可采取的第一步。**如果这一步没有发现任何迷雾**（通往目的地的道路已经清晰，整个旅程足够短，可以在一个会话中完成），则不需要地图。停止操作，并询问用户希望如何继续。
3. **创建地图**（标签为 `wayfinder:map`）：填写目的地和备注，将目前为止的决策留空，并在 **尚未明确** 中勾勒迷雾。
4. **将目前可以明确说明的事项创建为工单**，并将其设为地图的子议题；然后在**第二遍**操作中连接阻塞边（议题必须先有 ID，才能相互引用）。连接关系会将它们分为前沿工单和被阻塞工单；所有尚无法明确说明的事项都留在迷雾中，即 **尚未明确** 部分。
5. **启动研究子智能体。** 对于刚刚创建的每个 `research` 工单，启动一个子智能体，让它使用 "research" 调用 Skill 工具以并行解决该工单；将研究结果记录在临时的 `research/<name>` 分支上，并在工单中添加上下文指针。
6. 停止：绘制地图是一个会话的工作；它本身不直接解决任何工单。

### 逐步处理地图

用户通过地图（URL 或编号）调用。工单是**可选的**：如果没有指定工单，则由你选择下一个决策，而不是由用户选择。

1. 加载**地图**：使用低分辨率视图，而不是加载每个工单的完整正文。
2. 选择工单。如果用户指定了工单，就使用该工单。否则，按顺序选择第一个前沿工单。**认领工单**：在开始任何工作之前，将其分配给自己。
3. 解决工单。**按需放大查看**：根据需要获取任何相关工单或已关闭工单的完整正文；针对 `## Notes` 区块中指定的每项技能调用 Skill 工具。如果不确定，则调用 Skill 工具两次，分别用于 "grilling" 和 "domain-modeling"。
4. 记录解决结果：将答案发布为**解决结果评论**，**关闭**议题，并在地图的 Decisions-so-far 中**追加上下文指针**。
5. 添加新浮现的工单（先创建再连接）；将答案已使其变得可明确说明的任何模糊项升级为工单，并从 **Not yet specified** 中清除每个已升级的片段，使其仅存在于新工单中。如果答案表明某个工单（当前工单或其他工单）位于目标范围之外，则应**将其排除在范围之外**，而不是在路线中解决它。如果该决策使地图的其他部分失效，则更新或删除相应工单。

用户可能会并行处理未受阻塞的工单，因此应预期其他会话也在同时编辑跟踪器。
