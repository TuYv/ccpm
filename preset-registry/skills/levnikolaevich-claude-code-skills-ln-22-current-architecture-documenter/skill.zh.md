# 当前架构文档编写器

**目标：** 生成已检出仓库中所实现架构的可信快照。记录实际存在的内容及其行为；不要评分、规定目标架构、修复代码，或将意图中的图表当作事实。

**执行约定：** 有序复选框即为完成定义。将每个项目在内部跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有其条件不存在证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败均不构成证明。每个章节后重新核对项目。返回前，解决所有 `PENDING`，且仅统计 `PROVEN` 和 `CLEARED`；对每个缺口应用该技能的裁决和批准规则。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对有重大影响的未解决选择或必需的外部批准提出询问。将深度与实质性风险相匹配，不得悄然跳过检查。保留依赖关系和安全顺序；其他情况下，选择适合每项义务的验证方法。
将等价的用户或仓库证据视为有效输入；其他技能、具名工件或完整生命周期均不是前置条件。在可用时保留源需求和决策标识符。将复用的证据绑定到相关的源版本、未提交变更、配置和环境；在变更后仅使受影响的声明失效。
继续执行时，在恢复前核对任务、现有授权、当前状态和未解决的证据。对于长时间工作，返回紧凑的续办记录，或更新已获授权的任务工件；只读技能不持久化该记录。区分工件就绪状态、已验证行为以及执行外部操作的授权。
在任何必需批准之前准备已获授权的工作。如果某项指令阻碍进展，请指出其确切来源并说明未解决的边界；不要因一般性谨慎而臆造批准关卡。

## 工具路由

| 需求 | 首选能力 | 备选方案 |
|---|---|---|
| 快照身份和工作区状态 | Git 状态、分支、远程仓库和 HEAD | 将提供的快照记录为 `UNVERIFIED` |
| 结构和配置 | 原生列举、搜索、清单和直接文件读取 | 有针对性的手动检查 |
| 符号、依赖项和使用方 | 语言智能或已解析的依赖工具 | 搜索定义、注册、导入和调用方 |
| 运行时和部署拓扑 | 入口点、IaC、容器、CI、配置和运行时证据 | 将部署关系标记为 `UNKNOWN` |
| 文档修改 | 对已批准的架构文档进行最小补丁 | 如果没有已授权的可写路径，则返回 `BLOCKED` |

优先使用本地证据，而不是远程仓库状态。路径、图表或命名约定在得到可执行连接或权威契约确认之前，仅是线索。

## 工件规则

- 复用清晰的当前状态架构文档；否则使用 `docs/architecture/current-state.md`。
- 将文档锚定到远程仓库、分支、HEAD、工作区状态和观察日期。
- 使用文件路径、符号、命令或配置键引用实质性声明。
- 将声明标记为 `OBSERVED`、`DOCUMENTED`、`INFERRED` 或 `UNKNOWN`。
- 将实际结构与意图中的目标设计及审计发现分开。
- 先粗粒度地映射声明的系统范围，然后仅深入分析能够解释其关键行为的部分；不要将有边界的请求扩展为全仓库清单。
- 优先采用面向职责的描述，而不是详尽的文件清单。
- 记录证据截止点，以便读者区分未检查范围与确实不存在的内容。
- 仅在易变的计数或清单会影响架构理解时才保留它们。

## 检查清单

### 1. 建立文档契约

- [ ] 明确仓库范围、目标读者、批准的目标位置、所需深度和语言。
- [ ] 阅读仓库说明，并记录快照标识以及工作区存在未提交更改时的限制。
- [ ] 搜索现有的当前状态、基线、目标设计、决策、图表和部署文档。
- [ ] 复用明确无歧义的当前状态文档，或选择默认路径，避免重复记录项目知识。
- [ ] 除批准的架构文档外，保持本次操作只读。

### 2. 梳理系统广度

- [ ] 根据清单文件和 CI 识别语言、框架、包根目录、生成内容，以及规范的构建或运行命令。
- [ ] 识别用户、外部系统、入口点、应用程序、服务、进程、工作线程、定时任务和部署单元。
- [ ] 梳理主要领域或模块、职责、所有权和依赖方向。
- [ ] 梳理数据存储、缓存、队列、文件、外部 API、架构以及事实来源系统。
- [ ] 记录公共接口、运行时发现、注册、配置组合和环境边界。
- [ ] 记录构建、部署、扩展和故障边界，不要仅依据目录名称推断独立性。

### 3. 跟踪关键行为

- [ ] 根据业务重要性和架构影响范围，选择具有代表性的关键流程。
- [ ] 跟踪每个流程从参与者或触发器开始，经由入口点、运行时协调、领域行为、持久化或集成，到可观察结果的完整路径。
- [ ] 在有证据的情况下，记录同步和异步跳转、事务归属、一致性、重试、超时、幂等性和错误传播。
- [ ] 描述从仓库证据中可见的部署、启动、关闭、健康检查、可观测性和恢复路径。
- [ ] 仅深入研究其复杂性或不确定性会影响架构理解的子系统；不要将普通实现细节写入架构文档。

### 4. 编写当前状态文档

- [ ] 编写快照标识、系统上下文、组件清单、职责、依赖和数据流、运行时拓扑、关键流程、部署、所有权和证据索引。
- [ ] 内嵌最少但有用的图表，或通过路径链接到现有图表文档。
- [ ] 区分已观察到的实现和已记录的意图，并明确列出偏差或矛盾，不对其分配严重程度。
- [ ] 对远程专有、仅运行时可见、组织层面或生产环境中的事实标记为 `UNKNOWN`，除非有权威证据确立这些事实；区分已声明的部署配置和已观察到的实时拓扑。
- [ ] 保留有来源且由人工维护的上下文，并标注其证据状态；记录矛盾，并将缺乏支持的历史声明标记为不受支持，而不是将其作为已观察事实继承下来。

### 5. 验证并报告

- [ ] 根据检查过的快照证据验证每条引用，并移除不受支持的声明；仅当源文件发生变化或先前的检查不足以确立该声明时，才重新打开源文件。
- [ ] 确认该映射能够解释关键行为如何被发现、执行、持久化和部署。
- [ ] 确认抽象层级没有混用，并确保术语在正文和图表中保持一致。
- [ ] 当快照有证据支持且具备实用价值时，使用 `DOCUMENTED`；当重要拓扑仍然未知时，使用 `INCONCLUSIVE`；当无法安全确定仓库身份、范围或目标位置时，使用 `BLOCKED`。

- [ ] 将当前状态账户绑定到所检查的修订版本以及相关的脏状态/配置状态；识别会使已记录边界失效的变更。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。修正报告或经授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败项或未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言，并按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时可以每个字段使用一行；省略空表格，不要复制链接的工件：

1. **结果：** Skill 专属结论及有依据支持的结果。
2. **范围：** 已审查/已变更的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill 专属字段；区分事实、推断和未经验证的声明。链接工件；适用时使用表格。
4. **验证：** 检查项/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；剩余风险及所需决策。

**Skill 专属证据：** 工件路径和快照标识（远程仓库、分支、HEAD、工作树、日期）；映射的上下文、模块、运行时/部署、数据/接口、所有权和关键流程。识别发生变更的章节/图表，以及需要运行时、组织层面或外部确认的声明或区域，并注明状态、已检查的证据和确切的后续操作。
