# 采购优化器

大多数软件支出削减并不是谈判问题，而是衡量问题：
组织往往以整数批量购买席位，宽松地分配这些席位，却从不查看是否
有人实际登录。典型的中型软件组合中，有 20-30% 的席位支出可以回收，
甚至无须与供应商交涉，而这种回收也完全不需要供应商作出任何让步。

本技能按照收益从高到低依次运用各项杠杆：先**停止为未使用的席位付费**，然后
**停止为相同的能力重复付费**，最后再**协商价格**。颠倒这个
顺序——一开始就针对臃肿的合同进行价格谈判——只会让组织
在购买的席位比实际需求多 40% 的情况下，还为争取到 10% 的折扣而沾沾自喜。

## 何时使用此技能

- 已下达**预算削减目标**，且软件支出在削减范围内
- **续约即将到来**，你需要在与供应商通话前形成一个站得住脚的立场
- **SaaS 蔓延审计**：没人能说清楚公司究竟为多少款工具付费
- **并购后整合**，两个软件组合存在大量重叠
- 制定**续约日历**，避免合同未经审查便自动续约
- 供应商提出了**涨价**，而你需要筹码来予以反制

## 此技能需要的输入

- **支出清单**：工具、类别、年度成本、续约日期、合同期限
- **席位数据**：已购买、已分配，以及最关键的——*过去 30 天内活跃*
- **合同条款**：通知期、自动续约标记、期限长度
- 每项工具的**关键程度**，以及是否存在能力相同的替代方案
- **员工人数**，用于人均基准比较
- **截至日期**，以便续约窗口的计算可复现

## 首先澄清

生成前，请确认以下输入。如果有任何一项未知或含糊，请询问——不要自行假设：

- [ ] **席位数据是已分配数据还是活跃数据**——这是影响最重大的单项输入。已分配席位会将使用量高估 30-60%，基于这些数据进行分析几乎发现不了任何问题
- [ ] **通知期和自动续约标记**——处于通知期内的合同意味着已承诺再续一个完整周期，因此其“节省金额”在本周期内无法实现，也绝不能计入目标
- [ ] **目标是本年度现金节省还是年化支出削减**——在续约时削减席位可以降低年化支出，但本财年可能无法实现任何节省，这并不能解决本年度现金问题
- [ ] **哪些工具在政治层面不可触碰**——如果 CRM 归 CRO 管且无法削减，这将改变哪些机会值得分析

停止规则：只询问对输出影响最大的 2-3 个问题。如果用户说“直接起草”，则继续执行，并在交付物顶部列出你的假设。

## 工作流

### 工作流 1——找出浪费的席位

始终从这里开始。它不需要与供应商沟通，也不需要跨团队协商。

1. 汇总清单，包含已购买 / 已分配 / **过去 30 天活跃**的席位数。如果你
   只有已分配数量，请停止并获取活跃数量——没有这些数据，分析就没有意义。
2. 运行分析器。它会根据各类别的基准比较活跃使用率（LMS
   不会每周使用，而 CRM 会），并使用 12% 的安全缓冲来估算可回收支出。
3. 将报告中的两种失效模式区分开来。**许可过量**意味着应削减席位。
   **采用失败**意味着席位分配给了从不登录的人员——在这种情况下削减席位
   只是治标，而这款工具可能根本没有继续保留的价值。

```bash
python3 business-operations/procurement-optimizer/scripts/license_utilization_analyzer.py \
  --input business-operations/procurement-optimizer/assets/sample_spend.json --format text
```

### 工作流 2——找出你正在重复付费的工具

1. 运行重叠检测器。它按类别分组，并根据**替换成本**而非价格来选择保留的工具——
   无论许可证成本是多少，迁移 400 名活跃用户的代价都很高。
2. 首先检查宽泛标签警告。如果某个类别被标记为宽泛类别，说明你的标签将 Wiki
   和聊天工具视为可相互替代的产品。在相信输出中的任何数字之前，请根据工具所完成的
   工作重新标记，然后再次运行。
3. 将回收金额视为已扣除假定的 20% 迁移成本。在迁移成本为 20% 时看起来收益有限的
   整合方案，一旦计入业务中断的影响，实际收益通常为负。

```bash
python3 business-operations/procurement-optimizer/scripts/tool_overlap_detector.py \
  --input business-operations/procurement-optimizer/assets/sample_spend.json --format text
```

### 工作流 3——结合续约日历对机会进行排序

1. 使用明确的 `--as-of` 运行排序器。它会根据续约时点在本周期内实际提供的议价能力，
   对每个机会进行折算。
2. 从上到下处理候选清单。有时间限制的项目（处于通知期内或理想的
   T-120 至 T-90 谈判窗口内）会排在续约时间尚远但 ROI 更高的项目之前，
   因为错过一个窗口意味着损失整整一个合同年度。
3. 在承诺节省金额之前，向管理层说明 `locked_this_cycle` 数值。
   它表示机会中今年确实无法实现的部分；在承诺目标之后才发现这一点，
   将导致一场棘手的沟通。

```bash
python3 business-operations/procurement-optimizer/scripts/savings_opportunity_ranker.py \
  --input business-operations/procurement-optimizer/assets/sample_spend.json \
  --as-of 2026-07-21 --top 10 --format text
```

## 决策框架

### 按类别划分的使用率基准 [建议]

过去 30 天内的活跃席位数除以已购买席位数。在这里，采用单一统一基准是最常见的
分析错误——它会将 LMS 标记为浪费极其严重，而按季度使用本就是其正常模式。

| 类别 | 健康的活跃使用率 | 原因 |
|----------|---------------------------|-----|
| 安全 / 身份认证 | 90% | 几乎全面部署；未使用的席位纯属浪费 |
| CRM、聊天、客服支持系统 | 85% | 每日使用的工具，用户群体明确 |
| 开发者工具 | 80% | 每日使用，但合同工流动会产生实际闲置 |
| 财务系统 | 80% | 用户群体规模小且定义明确 |
| 设计 | 70% | 许可证占用较多的工具，包含偶尔使用的查看者 |
| 产品分析 | 60% | 确实存在大量偶尔进行查询的长尾用户 |
| 法务 / 合同工具 | 55% | 由小型团队间歇性使用 |
| 知识库 | 50% | 以阅读为主；许多用户只阅读，不会触发席位活动 |
| 白板 | 40% | 使用呈突发性，由研讨会驱动 |
| LMS / HR 培训 | 40% | 按设计以季度或年度为使用周期 |

### 续约时机与议价能力 [已验证]

| 时间窗口 | 议价能力 | 应采取的行动 |
|--------|----------|-----------|
| T-180d 及更早 | 低 | 为时过早。供应商不会针对尚且遥远的续约提供折扣。将启动日期记入日历 |
| **T-120d 至 T-90d** | **最高** | 理想窗口。在此时启动。你有时间开展替代方案评估，而供应商的季度末业绩压力尚在前方 |
| T-90d 至 T-60d | 中等 | 仍可操作，但预计需要以更长的合同期限换取价格优惠 |
| T-60d 至通知截止日期 | 低 | 即使你打算续约，也应发出通知以保留选择空间。通知并不等于终止合同 |
| 自动续约合同已进入通知截止日期之后 | 无 | 已承诺再续一个合同期。为下一个周期做好计划 |

软件采购中最有价值的一项实践，是在每份自动续约合同的通知截止日期，**默认发出通知**。
这样可以将自动续约转变为一场谈判，而且没有任何成本——供应商不会因为客户发出通知
就放弃客户，而是会安排一次通话。不这样做的组织在谈判时没有其他选择，而供应商对此
心知肚明。

### 应使用哪个杠杆

| 情况 | 杠杆 | 典型收益 |
|-----------|-------|---------------|
| 利用率低于基准 | 续约时减少席位 | 该合同金额的 20-40% |
| 利用率健康，但价格高于市场水平 | 争取价格让步 | 5-12% |
| 两款工具功能相同，且均未得到充分使用 | 整合 | 扣除迁移成本后，被替代工具成本的 60-80% |
| 已分配席位，但无人登录 | 改善采用情况或淘汰该工具 | 0% 或 100%——不存在中间状态 |
| 以折扣换取多年期合同 | 通常应拒绝 | 参见下方的反模式 |

## 反模式

### 将已分配席位计为使用量
**错误：**基于已分配席位而非活跃席位进行利用率分析。
**产生原因：**管理控制台首页显示的是已分配数量；活跃数量通常需要通过导出或 API 调用
才能获得。
**正确做法：**在开展任何分析之前，坚持获取 30 天活跃数量。在典型的软件组合中，
已分配席位会将实际使用量高估 30-60%，而这恰恰也是你所寻找的节省空间——基于已分配
席位的分析发现不了任何问题，并会得出该软件组合效率良好的结论。

### 多年期折扣陷阱
**错误：**为一款有 40% 席位未使用的工具接受以三年期承诺换取 15% 的折扣。
**产生原因：**折扣具体、即时，而且很容易作为成果汇报。被锁定的浪费则较为分散，并会
在其他人的季度中显现。
**正确做法：**先将席位数量调整到合理规模，再以修正后的基准评估多年期报价。在席位数量
多出 40% 的基础上提供 15% 的折扣，实际上是披着折扣外衣的 26% 涨价。只有当你确信会
继续使用某款工具、其利用率已经处于健康水平，且折扣超过 20% 时，多年期合同才值得接受。

### 未发出通知就开始谈判
**错误：**在合同仍被设为自动续约的情况下启动续约谈判。
**产生原因：**发出通知让人感觉是在与供应商对抗，而且没有人希望与自己打算继续合作的
供应商发生事态升级。
**正确做法：**将每份自动续约合同在截止日期发出通知作为标准实践。这是一项程序性步骤，
而不是威胁，供应商也会如此看待。否则，你除了续约别无选择，也毫无议价能力，而供应商的
客户团队比你更清楚你的通知窗口。

### 按价格而非替换成本进行整合
**错误：** 在两个功能重叠的工具中保留更便宜的那个。
**原因：** 许可证成本是显而易见的数字，而且比较起来很容易。
**正确做法：** 保留活跃用户更多、关键性更高的工具，即使其成本更高。
迁移 400 名活跃用户所造成的生产力损失和支持负担，远高于年度许可证费用的差额——而且，取代现有主流工具的整合往往会彻底失败，
导致你既要为两个工具付费，还要承担迁移成本。

### 将锁定的节省额计入今年的目标
**错误：** 将整个产品组合的机会总额报告为节省承诺。
**原因：** 总额数字更大，而且续约窗口期的细微差别很难解释。
**正确做法：** 分别报告机会总额、本周期可实现的节省额以及锁定的节省额。采用自动续约且
已进入通知期限内的合同，意味着还需承诺一个完整合同期；相关节省确实存在，但要到明年才能实现。承诺一个包含这些节省额的数字，必然会导致目标落空，而且
从你作出承诺的那一天起，就能预见这次落空。
