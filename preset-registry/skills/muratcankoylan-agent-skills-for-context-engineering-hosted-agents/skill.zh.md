# 托管式智能体基础设施

托管式智能体在远程沙箱环境中运行，而不是在本地计算机上运行。如果设计得当，它们可以提供无限并发能力、一致的执行环境和多人协作支持。关键在于，会话速度应当只受模型提供商的首个令牌生成时间限制，所有基础设施的设置工作都应在用户开始会话之前完成。

## 何时启用

在以下情况下启用此技能：
- 构建独立于用户设备运行的后台编码智能体
- 为智能体工作负载设计沙箱化执行环境
- 实现具有共享状态的多人智能体会话
- 创建多客户端智能体界面（Slack、Web、Chrome 扩展程序）
- 将智能体基础设施扩展到本地计算机的限制之外
- 构建由智能体生成子智能体以并行工作的系统

对于由其他技能负责的相邻工作，请勿启用此技能：
- 设计自主研究循环、新颖性门控、回滚策略或合并边界：`harness-engineering`。
- 在不涉及托管基础设施问题的情况下选择监督者、智能体群或交接拓扑：`multi-agent-patterns`。
- 设计托管式智能体使用的工具，例如生成/状态工具或 PR 工具：`tool-design`。
- 管理会话内部基于文件的状态，而不是托管运行时本身：`filesystem-context`。

## 核心概念

将智能体执行迁移到远程沙箱环境中，以消除本地执行的根本限制：资源争用、环境不一致和单用户约束。远程沙箱可实现无限并发、可复现的环境和协作式工作流，因为每个会话都会获得独立的计算资源和已知可用的环境镜像。

将架构设计为三层，因为每一层都可以独立扩展。构建用于隔离执行的沙箱基础设施、用于状态管理和客户端协调的 API 层，以及用于跨平台用户交互的客户端界面。确保这些层之间清晰分离，以免沙箱变更波及客户端。

## 详细主题

### 沙箱基础设施

**核心挑战**
消除沙箱启动延迟，因为用户会认为任何超过几秒的等待都意味着系统已经出错。开发环境需要克隆代码仓库、安装依赖项并运行构建步骤——所有这些工作都应在用户提交提示词之前完成。

**镜像仓库模式**
定期预构建环境镜像（每 30 分钟一次效果很好），因为这样一来，与最新代码同步时只需快速获取增量，而不必完整克隆。每个镜像中应包含：
- 在已知提交处克隆的代码仓库
- 已安装的所有运行时依赖项
- 已完成的初始设置和构建命令
- 运行一次应用程序和测试套件后生成的缓存文件

启动会话时，从最新镜像创建一个沙箱。代码仓库最多只会落后 30 分钟，因此剩余的 git 同步可以快速完成。

**快照与恢复**
在关键节点创建文件系统快照，以便在收到后续提示时立即恢复，而无需重新运行设置：
- 初始镜像构建完成后（基础快照）
- 智能体完成更改后（会话快照）
- 沙箱退出前，以便处理潜在的后续请求

**后台智能体的 Git 配置**
在每个沙箱中显式配置 Git 身份，因为在镜像构建期间，后台智能体并不绑定到特定用户：
- 生成 GitHub 应用安装令牌，以便在克隆期间访问仓库
- 在提交和推送更改时设置 Git 配置 `user.name` 和 `user.email`
- 使用发出提示的用户身份进行提交，而不是应用身份

**预热池策略**
为高使用量仓库维护一个预热沙箱池，因为冷启动是用户受挫的主要原因：
- 在用户开始会话之前准备好沙箱
- 随着新镜像构建完成，使池中的条目过期并重新创建
- 用户一开始输入内容，就开始预热沙箱（预测性预热）

### 智能体框架选择

**服务器优先架构**
首先将智能体框架构建为服务器，并让 TUI 和桌面应用充当轻量客户端，因为这样可以避免在不同交互界面中重复实现智能体逻辑：
- 多个自定义客户端共享同一个智能体后端
- 在所有交互界面中保持一致的行为
- 插件系统无需更改客户端即可扩展功能
- 事件驱动架构可向任何已连接的客户端实时传递更新

**以代码为事实来源**
选择智能体能够读取自身源代码以理解其行为的框架。应优先考虑这一点，因为以代码作为事实来源，可以防止智能体对自身能力产生幻觉——这是 AI 开发中一种被低估的故障模式。

**插件系统要求**
要求插件系统支持运行时拦截，因为这样无需修改智能体核心逻辑，就能实现安全控制和可观测性：
- 监听工具执行事件（例如 `tool.execute.before`）
- 根据条件阻止或修改工具调用
- 在运行时注入上下文或状态

### 速度优化

**预测性预热**
用户一开始输入提示就开始预热沙箱，而不是等到提交提示时才开始，因为输入所需的时间（5-30 秒）足以完成大部分设置：
- 在用户输入的同时并行克隆最新更改
- 在用户按下回车键之前运行初始设置
- 如果启动足够快，沙箱可以在用户完成输入之前准备就绪

**并行文件读取**
即使尚未完成与最新基础分支的同步，也允许智能体立即开始读取文件，因为在大型仓库中，收到的提示很少涉及最近更改的文件：
- 智能体可以立即进行研究，而无需等待 Git 同步
- 在同步完成之前阻止文件编辑（但不阻止读取）
- 这种分离方式是安全的，因为对于研究而言，读取时数据存在 30 分钟的时效延迟通常无关紧要

**最大化构建时工作量**
尽可能将所有工作移至镜像构建步骤，因为用户无法感知构建所耗费的时间：
- 完整安装依赖项
- 设置数据库架构
- 首次运行应用和测试套件（填充缓存）

### 自生成代理

**代理生成的会话**
构建允许代理生成新会话的工具，因为前沿模型能够分解工作并协调子任务：
- 跨不同代码仓库的研究任务
- 针对大型变更并行执行子任务
- 将一个重大任务拆分为多个较小的 PR

提供三个基本操作：使用指定参数启动新会话、读取任意会话的状态（签入能力），以及在子会话并行运行时继续开展主要工作。

**自生成代理的提示词工程**
设计提示词，引导代理判断何时应生成子会话，而不是直接在当前会话中执行工作：
- 需要跨代码仓库探索的研究任务
- 将单体式变更拆分为较小的 PR
- 并行探索不同的方法

### API 层

**按会话隔离状态**
按会话隔离状态（每个会话使用一个 SQLite 效果很好），因为跨会话干扰是一种隐蔽且难以调试的故障模式：
- 每个会话使用专用数据库
- 任何会话都不能影响其他会话的性能
- 架构可处理数百个并发会话

**实时流式传输**
实时流式传输代理的所有工作，因为高频反馈对于建立用户信任至关重要：
- 来自模型提供商的 Token 流式传输
- 工具执行状态更新
- 文件变更通知

使用带休眠 API 的 WebSocket 连接，在保持连接开放的同时降低空闲期间的计算成本。

**跨客户端同步**
构建一个可在所有客户端（聊天界面、Slack 机器人、Chrome 扩展程序、Web 界面、VS Code 实例）之间同步的统一状态系统，因为用户经常切换使用界面，并期望保持连续性。所有变更都会同步到会话状态，从而实现无缝的客户端切换。

### 多人协作支持

**多人协作为何重要**
从一开始就为多人协作进行设计，因为在具备适当同步架构的情况下，增加此功能几乎无需额外成本，并且能够解锁高价值工作流：
- 教导非工程师有效使用 AI
- 多名团队成员参与的实时 QA 会话
- 可立即实施变更的实时 PR 审查
- 协作式调试会话

**实现要求**
构建数据模型时，不要将会话绑定到单一作者，因为如果作者身份被硬编码，多人协作会在不易察觉的情况下失效：
- 将作者身份信息传递给每个提示词
- 将代码变更归属于发出提示的用户
- 共享会话链接以实现即时协作

### 身份认证与授权

**基于用户身份的提交**
使用 GitHub 身份认证代表用户（而不是应用）创建 PR，因为这可以保留审计轨迹，并防止用户批准由自己的 AI 生成的变更：
- 获取用于创建 PR 的用户 Token
- PR 显示为由人类用户而非机器人创建

**从沙箱到 API 的流程**
遵循以下顺序，因为这样既可以将沙箱权限保持在最低限度，又能让 API 处理敏感操作：
1. 沙箱推送变更（更新 git 用户配置）
2. 沙箱向 API 发送包含分支名称和会话 ID 的事件
3. API 使用用户的 GitHub Token 创建 PR
4. GitHub Webhook 将 PR 事件通知给 API

### 客户端实现

**Slack 集成**
优先将 Slack 作为推动内部采用的首个分发渠道，因为当团队成员看到其他人使用它时，会形成病毒式传播循环：
- 无需语法，采用自然的聊天界面
- 构建一个分类器（使用包含仓库描述的快速模型），以确定应在哪个仓库中工作
- 为常用仓库提供提示；对于存在歧义的情况，允许使用 "unknown"

**Web 界面**
构建具备以下功能的 Web 界面，因为它是高级用户的主要操作界面：
- 在桌面端和移动端实时流式展示智能体的工作过程
- 在沙箱内运行托管的 VS Code 实例
- 通过流式桌面视图进行可视化验证
- 为 PR 提供变更前后的截图
- 统计页面：产生已合并 PR 的会话数（首要指标）、使用量随时间的变化、实时“正在发出提示的人数”

**Chrome 扩展程序**
为非工程用户构建 Chrome 扩展程序，因为提取 DOM 和 React 内部信息比使用原始截图精度更高，同时 token 成本更低：
- 带截图工具的侧边栏聊天界面
- 提取 DOM/React 内部信息，而不是原始图像
- 通过托管设备政策分发（绕过 Chrome Web Store）

## 实践指南

### 托管智能体设计检查清单

在构建系统之前，明确决定以下基础设施属性：

1. **沙箱生命周期**：会话如何启动、创建快照、恢复、超时和终止。
2. **镜像和热池策略**：镜像多久重建一次、预先计算哪些缓存，以及热沙箱何时过期。
3. **读写同步**：是否允许智能体在仓库同步完成前读取，以及哪些事件会解除写入限制。
4. **每会话状态隔离**：哪些存储属于单个会话、哪些存储是共享的，以及如何防止跨会话干扰。
5. **身份验证和提交身份**：哪些操作使用应用 token、哪些操作使用用户 token，以及如何标注提交归属。
6. **输出提取**：分支、PR、文件、日志、截图和会话摘要如何从沙箱中导出。
7. **预算和销毁**：最长运行时间、成本上限、空闲策略和强制清理行为。

### 后续消息处理

对于执行期间发送的后续消息，可选择排队或插入。优先选择排队，因为它更易于管理，并且允许用户在智能体工作时发送有关后续步骤的想法。构建一种可在需要时中途停止智能体执行的机制，因为如果没有这种机制，用户会感到受困。

### 重要指标

跟踪以下指标，因为它们反映的是真实价值，而不是虚荣指标：
- 产生已合并 PR 的会话数（首要成功指标）
- 从会话开始到模型首次响应的时间
- PR 批准率和修订次数
- 各仓库中由智能体编写的代码占比

### 采用策略

通过提高可见性而不是强制要求来推动内部采用，因为强制使用会引发抵触情绪：
- 在公开空间（Slack 频道）中开展工作，以提高可见性
- 让产品形成病毒式传播循环
- 不要强制用户放弃现有工具
- 根据人们的实际需求进行构建，而不是假想的要求

## 示例

**示例 1：后台编码会话生命周期**

```text
user prompt
-> API allocates warm sandbox from current image
-> sandbox syncs latest branch delta
-> reads allowed immediately, writes blocked until sync completes
-> agent edits and tests inside isolated workspace
-> sandbox snapshots final filesystem
-> branch is pushed
-> API creates PR using user token
-> session summary, logs, and PR URL are returned to clients
```

此流程将准备工作移出用户可见路径，同时保留可审计性以及用户对代码变更的所有权。

**示例 2：边界判断**

如果任务是“让智能体循环在锁定评判标准并要求 PR 审批的情况下持续运行数天”，请使用 `harness-engineering`。如果任务是“在具备预热池、会话快照、流式客户端和以用户身份创建的 PR 的远程沙箱中运行该循环”，请使用此技能。

## 指南

1. 定期预构建环境镜像（默认每 30 分钟一次较为合适）
2. 在用户开始输入时预热沙箱，而不是等到用户提交时
3. 在 git 同步完成前允许读取文件；仅阻止写入
4. 将智能体框架构建为服务端优先的架构，并让客户端仅作为轻量封装
5. 按会话隔离状态，防止会话之间相互干扰
6. 将提交归属到发出提示的用户，而不是应用
7. 将已合并的 PR 作为主要成功指标进行跟踪
8. 从一开始就支持多人协作；采用合适的同步架构后，这几乎无需额外成本

## 注意事项

1. **冷启动延迟**：首次启动沙箱需要 30–60 秒，用户会认为系统出了故障。使用预热池，并在用户按键输入时进行预测性预热，以消除用户感知到的等待时间。
2. **镜像陈旧**：镜像重建频率过低意味着智能体会使用过时的依赖项或代码运行。设置每 30 分钟一次的重建周期并监控镜像的存续时间；如果构建在没有提示的情况下失败，则发出警报。
3. **沙箱成本失控**：没有超时或预算上限的长时间运行智能体会产生意外成本。设置硬性超时限制（默认 4 小时）以及每个会话的成本上限。
4. **会话期间身份验证令牌过期**：当 GitHub 令牌在任务执行过程中失效时，长时间任务会失败。实现令牌刷新逻辑，并在创建 PR 等敏感操作前检查令牌有效性。
5. **沙箱中的 Git 配置**：缺少 `user.name` 或 `user.email` 会导致后台智能体提交失败。配置沙箱时始终显式设置 Git 身份信息，绝不要假定它会从镜像中继承。
6. **沙箱回收时状态丢失**：如果沙箱在提取结果前被回收或超时，智能体会丢失已完成的工作。终止前务必创建快照，并在沙箱销毁前提取产物（分支、PR、文件）。
7. **预热池过度配置**：在低流量时段维持过多预热沙箱会浪费资金。根据流量模式和时段调整池大小；使用自动扩缩容，而不是固定的池大小。
8. **缺少输出提取**：智能体在沙箱内完成了工作，但结果从未被提取并交付给用户。将明确的提取步骤（推送分支、创建 PR、返回文件内容）纳入会话清理流程。

## 集成

本技能负责托管式运行时基础设施。相邻技能分别负责控制系统、拓扑结构和工具契约：

- `harness-engineering`：围绕自主工作的治理、锁定的评估器、回滚、新颖性门控以及人工审批边界。
- `multi-agent-patterns`：托管式基础设施就绪后的自生成和监督者模式。
- `tool-design`：向智能体开放的生成、状态、销毁和 PR 工具。
- `context-optimization`：管理分布式托管会话中的上下文。
- `filesystem-context`：使用沙箱文件系统保存持久化的会话状态和工件。
