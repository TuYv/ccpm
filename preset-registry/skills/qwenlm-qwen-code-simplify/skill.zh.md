# 简化近期变更

你正在对近期的代码变更执行结构化清理流程。你的目标不仅是评论代码，还要安全地改进代码。

## 第 1 步：确定审查范围

确定要审查的文件和变更。

1. 首先检查当前 git 状态。
2. 如果存在已暂存的变更，则针对 `HEAD` 进行审查，以同时包含已暂存和未暂存的跟踪文件变更。
3. 否则审查当前未提交的差异。
4. 如果不存在 git diff，则回退到 `git ls-files --modified --others --exclude-standard`，以确保范围遵循 `.gitignore`（这样可以将构建输出、`node_modules` 和其他被忽略的路径排除在清理范围之外）。
5. 如果结果仍为空，则回退到本次对话中编辑过的文件。
6. 如果仍无法确定有意义的范围，则停止并告知用户没有近期变更可供简化。

首选命令：

- `git diff --name-only`
- `git diff --staged --name-only`
- `git diff HEAD --name-only`
- `git diff`
- `git diff HEAD`
- `git status --short`

存在已暂存的变更时使用 `git diff HEAD`。否则使用 `git diff`。

## 第 2 步：并行启动三个审查流程

使用 `agent` 工具，并在单个响应中启动所有审查流程，使它们并发运行。**每次调用都必须设置 `subagent_type: "general-purpose"` 和 `run_in_background: false`——每个流程都必须直接返回其发现。不要派生它们：绝不要设置 `subagent_type: "fork"`。派生流程会即发即弃，且不会返回其发现，因此第 3 步将没有内容可供汇总。** 每个流程都必须接收相同的审查范围和差异命令。这些流程是只读的：每个流程只能检查并报告发现，不得修改文件——所有编辑操作都将在第 4 步执行。

让每个审查提示保持简短并聚焦。不要将完整差异粘贴到提示中。告诉每个流程自行读取差异，并且只检查与其发现相关的文件。

### 流程 1：代码复用审查

寻找减少重复并复用现有代码的机会：

- 应当复用的现有工具或辅助函数
- 新代码中引入的重复逻辑
- 应委托给现有抽象的内联逻辑
- 当项目中已有对应工具时，为字符串、路径、环境变量、解析或类型检查编写的临时辅助函数

### 流程 2：代码质量审查

寻找影响可维护性的问题：

- 应当统一的复制粘贴变体
- 参数过多或 API 设计别扭
- 冗余状态或间接层
- 抽象泄漏
- 应以更清晰方式建模的字符串类型代码
- 不必要的嵌套
- 解释“做什么”而非“为什么”的不必要注释
- 与周围代码不一致的命名或结构

### 流程 3：效率审查

寻找浪费性工作和不必要的开销：

- 可以记忆化、缓存或移除的重复工作
- 可以安全并行化的串行工作
- 不必要的扫描、分配、读取或遍历
- 热路径上的阻塞工作
- 冗余的无操作更新
- 如果使用更窄的操作即可完成，却采用了范围过大的操作
- 会引入 TOCTOU 式浪费或风险的存在性检查模式

## 第 3 步：汇总发现

等待三个检查轮次全部完成，然后合并重叠的发现。

优先处理符合以下条件的修复：

- 风险低
- 范围局部
- 与现有项目模式明确一致
- 易于通过测试或有针对性的命令进行验证

如果清理工作需要推测性的架构变更，不要强行进行。

## 第 4 步：应用直接改进

直接实施安全的清理改进。

适合自动修复的示例：

- 使用现有辅助函数替换重复逻辑
- 只有在全仓库搜索确认不再有调用方后，才移除冗余代码
- 简化条件判断或控制流
- 收紧循环或重复执行的工作
- 减少不必要的状态或包装代码
- 移除价值较低的注释
- 使代码与附近的约定保持一致

跳过不确定、有风险或侵入性过强的项目。不要花时间争论已被否决的发现；直接继续处理后续项目。

## 第 5 步：验证清理结果

完成更改后：

1. 如果存在针对更改区域的测试，运行这些重点测试。
2. 运行能够识别出的、与所修改代码相关的项目质量检查。
3. 如果没有适用的测试，至少运行能够覆盖所编辑文件的定向构建、类型检查或 lint 命令。

除非项目只提供全仓库检查，否则优先进行定向验证，而不是运行全仓库命令。
