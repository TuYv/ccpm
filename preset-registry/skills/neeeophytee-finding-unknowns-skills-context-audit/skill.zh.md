# 上下文审计

提示词是为某一项任务编写的；上下文却会在每项任务中复用，因此永远不可能同样具体。这种落差正是指令腐化之处：为不再出现的最坏情况编写的规则、在三个层级重复的指导，以及两个层级悄无声息地向模型提出相反的要求。模型能够解决所有这些问题——代价是在开始实际工作之前先为此消耗思考预算。此技能旨在找出应该删除的内容。

## 步骤

1. 盘点会传递给模型的每一个层级：根目录及嵌套目录中的 `CLAUDE.md`/`AGENTS.md`、每个技能的描述与正文、钩子、工具和 MCP 服务器描述，以及用户可控制的任何执行框架提示词。报告每个层级的大小。用户忘记自己写过的那一层，通常声音最大。
2. 像模型接收它们时那样一起阅读，而不是一次只读一个文件。矛盾只存在于不同层级之间。
3. 将每条指令归入以下五类之一：
   - **冲突**——两个层级朝相反方向施力（“酌情编写文档”与“绝不添加注释”）。逐字引用双方内容。这是代价最高的发现，应最先列出。
   - **重复**——同一条指令出现在两个位置。保留最靠近使用位置的那份；工具的行为应写在该工具的描述中，而不是全局前言里。
   - **显而易见**——重复陈述文件树、编程语言或周围代码已经表明的内容。
   - **当下判断**——为防止最坏情况而写下的一刀切规则，它对某些真实请求并不适用，而且属于当前模型完全有能力自行做好的判断。
   - **陷阱**——不明显、特定于此仓库且不可或缺的内容。这才是应该保留的；大多数仓库中的大部分内容都属于另外四类。
4. 以 diff 形式提出删减方案：先解决冲突，再处理重复项，最后处理其余内容。对于值得保留但仅在某些情况下才需要的内容，建议将其移入技能或按需加载的链接文件中，而不是删除。
5. 最后给出删减前后的行数，并明确指出最没有把握的一项删除内容，以便由人工决定。

## 约束条件

- 只提出方案，不实际应用。每项删除都必须由用户批准。
- 看似过度约束的规则，有时是某次真实事故留下的伤疤。任何点名具体故障的内容都应先询问，而不是直接删减。
- 判断指令时，要看它是否会改变行为，而不是听起来是否明智。如果模型默认就会遵循某一行内容，那么它只会消耗 token，却没有提供任何价值。
- 如果执行框架自带调整上下文规模的命令，此技能应与其配合运行，而不是取代它。
- 审计时删掉一项真正的不变量，代价远高于节省下来的 token。当某一行的用途不明确时，这种不明确本身就是审计发现——应将其报告出来，而不是自行猜测。
