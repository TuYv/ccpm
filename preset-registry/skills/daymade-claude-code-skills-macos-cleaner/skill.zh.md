# macOS 清理器

诊断磁盘空间压力的实际来源，仅回收已批准的空间，并证明清理没有损坏用户数据或共存服务。

## 入口路由

选择能够回答请求的最窄路径：

| 用户信号 | 路由 |
|---|---|
| Apple Content Caching、`AssetCacheManagerUtil`、`CacheUsed`、`ActualCacheUsed`、iCloud 缓存或“Caching needs more space” | 在进行探测或提出命令之前，完整阅读 `references/apple_content_caching.md` |
| Docker、OrbStack、镜像、容器或卷 | 阅读 `references/docker_analysis.md`；检查每个对象，绝不使用 prune 系列命令 |
| Docker 构建缓存 | 使用 `docker builder du` 进行测量；本 skill 会报告它，但不会删除它，因为 Docker 提供的是按类别整体清理的控制，而不是针对单条记录意图的控制 |
| Chrome、ChromeDriver、Playwright、Codex Computer Use、Edge 或 Chromium 存在较大的 `*.code_sign_clone` 目录 | 完整阅读 `references/chromium_code_sign_clones.md`；使用随附的分析器区分活动、非活动和未知的精确子项，绝不能将 `du` 等同于实际释放的空间 |
| 已经确定某个命名缓存、目录、应用程序或服务为嫌疑对象 | 先检查该目标，并阅读 `references/cleanup_targets.md` 中对应的语义；不要从主目录或整块磁盘扫描开始 |
| 来源确实未知 | 使用下面的通用分析工作流；Mole 是可选项，不是通用的第一步 |

用户提供的范围排除项优先于所有通用扫描建议。如果用户排除了个人目录、凭据、数据库、应用程序状态或无关服务，则不要检查这些内容。

## 安全与授权契约

1. **分离观察与变更。** 先完成只读诊断。在此阶段不要删除内容、停止服务、编辑设置、安装或升级工具，也不要运行可能在此阶段改变状态的清理预览。
2. **确认精确目标。** 在远程 Mac 上，开始任何其他操作之前记录当前主机身份。绝不能根据 IP、旧 PID、目录名称或先前的报告推断机器。
3. **先制定计划再请求批准。** 在进行任何状态变更之前，列出每条命令、它会造成的变化、预期实际回收的空间、影响、可恢复性和后置条件。如果用户请求的只是计划阶段，则在此之后停止。
4. **要求明确批准。** 如果用户提供了确切的确认短语，则必须要求该短语。否则，要求用户明确批准所列出的命令和目标。对一个计划的批准不授权执行后备方案或范围更大的清理。
5. **使用精确且受支持的控制方式。** 优先使用应用程序受支持的缓存管理命令或精确的对象 ID。如果没有受支持的控制方式，只有在验证其所有者、确认应用程序已停止或该目录处于非活动状态、说明重建/重新下载的影响并获得批准之后，才能删除精确的、由应用程序拥有的缓存目录。绝不能针对宽泛的缓存根目录或活动的应用程序状态。
6. **绝不使用 Docker prune 系列命令。** 这包括 image、container、volume、system、builder 和 buildx prune。按类别整体删除无法表达用户针对单个对象的意图。
7. **避免宽泛的破坏性 shell 形式。** 不要建议或执行宽泛的 `rm -rf` 或通配符删除。对于已精确批准的普通文件，优先使用 Finder 废纸篓。随附的旧版辅助工具会永久删除内容，且只有下文记录的有限保护措施；绝不能将其视为等同于废纸篓。
8. **保留有价值的状态。** 绝不能仅仅为了增加报告中的节省空间，就以用户文档、凭据、SSH 材料、活动数据库、应用程序配置或运行中服务的状态为目标。在删除任何文件之前阅读 `references/safety_rules.md`。
9. **执行遵循用户授权。** 如果用户只要求分析，或希望亲自运行命令，则将命令交给用户。如果用户要求代理修复机器，并明确确认了范围明确的计划，则执行确切的已批准命令并进行验证。无人值守的定期删除逻辑在编写或启用之前需要单独批准。
10. **快速失败。** 如果命令出现预期之外的非零退出状态、后置条件不匹配、目标出乎预期或依赖项发生变化，则停止清理。在判定失败之前，先解读已记录的探测状态，例如输出为空且 `lsof` 退出状态为 1。报告部分完成的状态；不要自行设计后备方案。

## 阶段契约

每次清理都使用此状态机：

1. **观察 — 只读。** 记录身份信息、磁盘基线、疑似子系统的状态和配置、物理分配情况，以及关键服务的健康状态。
1b. **在不可避免时，授权有状态检查。** 如果更深入的证据需要创建临时容器、拉取镜像、挂载卷或写入快照，先完成仅元数据观察，列出确切的检查命令及其副作用，并获得单独批准。检查批准不等于清理批准。
2. **规划 — 不进行变更。** 说明发现、命令、影响、恢复方式、预期释放空间和成功标准。在确认关卡处停止。
3. **执行 — 仅限已批准范围。** 在执行操作前立即重新读取实时状态，然后分别运行每条已批准的命令，并检查其退出状态和执行后条件。
4. **验证 — 独立回读。** 再次测量磁盘空间和子系统状态，重新检查受保护的服务，并持续观察足够长时间，以检测是否立即重新占满空间。

不要将第 2 阶段和第 3 阶段压缩到同一条消息中。将计划打印在清理命令旁边并不构成确认关卡。

## 阶段 1：只读诊断

### 建立基线

至少记录：

```bash
/bin/date "+%F %T %Z %z"
/usr/sbin/scutil --get ComputerName
/usr/sbin/scutil --get LocalHostName
/usr/bin/sw_vers
/bin/df -k /System/Volumes/Data
/bin/df -h /System/Volumes/Data
```

使用 `df -k` 进行计算，使用 `df -h` 生成人类可读的报告。在实时命令确认之前，将扩展名、标签或旧报告视为线索。

在扫描未知来源之前先确定成功目标。完全照抄用户提供的可用空间或容量目标。如果用户未提供目标，则报告当前值，并要求其提供以 GiB、容量百分比或两者表示的目标；不要自行臆造目标。命名的疑似对象诊断可以在没有清理目标的情况下继续，但有序的未知来源扫描在目标明确之前不能声称已达到停止条件。

保持此第一阶段为只读。暂时不要运行 `scripts/cleanup_report.py`：它会创建本地状态目录和快照文件。应将命令输出直接保留在报告中。在远程目标上，始终在该主机上直接运行 `df` 命令；本地辅助程序不得误测控制器 Mac。

### 在广泛扫描之前跟进已命名的疑似对象

- 查询该子系统自身的状态和设置。
- 仅当权限和用户范围允许时，针对确切的数据路径使用有边界的 `du` 测量物理分配情况。
- 区分逻辑内容大小、稀疏文件的表观大小、可清除空间和实际分配的字节数。
- 对于 APFS 克隆，将 `du` 标记为按路径计数或名义大小，而不是物理大小：共享区段可能会被归因于每条路径，因此在删除并回读 `df` 之前，实际释放量仍然未知。
- 对于疑似正在增长的日志，记录两个或更多时间点的确切文件大小。单个大文件或单个最近的 mtime 并不能证明其持续增长。
- 记录用户标记为关键的任何共存服务的当前进程、监听器、启动机制以及受支持的健康探测。在每个检查点重新解析 PID。

如果仅已知的可疑项就能满足用户的可用空间目标，则不要为了“以防万一”而扫描无关的个人目录或开发目录。

### 源位置未知时的一般分析

按最小化的顺序执行一系列操作，以识别出足够的物理空间来满足目标。只有在具备受支持的确切操作、且有充分依据证明其预期可释放物理空间的候选项能够满足目标时，才停止。原始分配总量、逻辑缓存大小、共享的 Docker 层、移入废纸篓的操作，以及未经验证的“潜在节省空间”都不能满足停止条件。

不要让物理可信度排序掩盖用户可见的最大热点。当按名义大小或路径统计的候选项大于推荐操作时，应同时展示这两个数字，并解释其物理释放量为何存在不确定性。应根据有充分依据的物理释放量、安全性和所需工作量进行排序；将名义大小作为单独的列报告，而不是默默地将其视为零或完全可回收。

| 顺序 / 信号 | 只读操作 | 停止或继续 |
|---|---|---|
| 1. 始终执行 | 获取身份信息并运行 `df -k/-h`；盘点用户排除项 | 目标不匹配时停止 |
| 2. 缓存/日志压力，并且 `~/Library/Caches` 加上 `~/Library/Logs` 属于获准的读取范围 | `uv run scripts/analyze_caches.py --user-only` | 测得的候选项能够满足目标时停止 |
| 3. 存在开发者工具，且脚本的固定范围已获批准 | `uv run scripts/analyze_dev_env.py` 会读取 Docker/包管理器，以及现有的 `~/Projects`、`~/workspace`、`~/dev`、`~/src` 和 `~/code` 根目录 | 将 Docker/OrbStack 的发现结果转交给其专用参考文档；任一固定根目录超出范围时跳过此辅助工具 |
| 4. 卸载应用的残留是合理怀疑对象，且其固定根目录已获批准 | `uv run scripts/find_app_remnants.py` 会读取 `/Applications`、`~/Applications`，以及文档所述的四个 `~/Library` 应用状态根目录 | 将每个结果视为候选项，绝不能视为已废弃的证据；未批准该范围时跳过 |
| 5. 某个包含内容的路径已获得明确批准 | `uv run scripts/analyze_large_files.py --threshold 100MB --path "<approved-path>"` | 未批准任何路径时，不要用 `~`、Downloads、Documents 或数据卷根目录替代 |
| 6. 在有界检查后仍未知，且用户明确批准 Mole 的固定广泛扫描根目录 | 阅读 `references/mole_integration.md`，并通过 TTY 使用 `mo analyze` | Mole 无法接受任意路径范围；用户批准的范围比其文档所述根目录更窄时跳过 |

`<approved-path>` 是用户点名或在了解其范围后明确接受的确切路径。如果不存在这样的路径，则跳过大文件和重复内容扫描，说明该证据分支未获授权，并继续收集非内容承载型证据。只读阶段不得安装或升级 Mole，除非用户另行授权该变更。

Mole 的分析器会扫描一个固定集合，其中包括主目录、应用程序数据、系统库、应用程序和卷。在结果中进行导航，并不会使底层扫描变为限定路径范围的扫描。如果未批准这一广泛的读取范围，则不要运行 Mole；应以已收集的有界证据为基础停止，或在计划中请求缺失的扫描授权。

对于已明确批准的重复文件调查，请阅读 `references/cleanup_targets.md` 中的“Optional duplicate files”部分。该调查为只读操作，绝不使用自动删除选项。

### Docker 和 OrbStack

在报告 Docker 可释放空间之前，请阅读 `references/docker_analysis.md`。逐一列出每个镜像、容器和卷；检查引用关系以及类似数据库的内容；使用实际的稀疏文件分配大小，而不是表观大小。被报告为悬空的资源并不能证明其中的数据毫无价值。支持测量构建缓存，但构建缓存删除明确不在范围内，因为可用的 Docker 控制项属于 prune 系列操作。

## 阶段 2：报告并在关卡处停止

报告观测到的值，而不是推断出的属性。长篇布局请使用 `references/report_templates.md`，并为每个拟议操作包含以下字段：

| 字段 | 必填内容 |
|---|---|
| 当前状态 | 时间戳、目标标识、磁盘已用空间/可用空间/容量，以及子系统状态 |
| 证据 | 命令和观测值；说明该数字是逻辑大小还是物理大小 |
| 精确命令 | 将改变状态的命令，以及精确的目标或对象 ID |
| 变更 | 命令将修改或删除的内容 |
| 可恢复性 | 可逆命令、从废纸篓恢复、从备份恢复，或只能重新下载 |
| 预计释放空间 | 物理空间估算值、单位及假设 |
| 服务影响 | 用户可见的影响以及受保护服务的不变量 |
| 后置条件 | 在将操作判定为成功之前必须成立的值 |

按后果而不是按数字有多诱人来分类调查结果：

- **可重建缓存：** 删除只会丢失本地副本，但要说明重新下载或重建的成本。
- **需要用户决策：** 价值取决于用户的工作流或对所有权的了解。
- **保留：** 用户数据、凭据、数据库状态、活动中的配置，或任何用途不明确的内容。

不要仅仅因为软件可以重新生成缓存，就称其为“绝对安全”。重新生成所需的时间、带宽、身份验证以及离线可用性都是真实成本。

## 阶段 3：执行已确认的计划

在第一条改变状态的命令执行前，立即：

1. 重新确认目标标识和当前磁盘状态。
2. 重新查询对象或子系统状态；实时状态发生变化时，清理计划即会过期。
3. 重新检查受保护服务的运行状况。
4. 将已批准的命令和精确目标集与即将运行的命令进行比较。任何更宽泛或不同的目标集都需要重新获得批准。某个单独保留的项目变为非活动状态，并不会使计划失效，前提是该项目仍被明确排除，且已批准的目标集哈希仍然匹配。

如果已批准的计划包括创建本地前后报告产物，请现在捕获清理前快照：在获得批准后、第一条清理命令执行前运行：

```bash
uv run scripts/cleanup_report.py --snapshot before
```

该命令会写入 `~/.macos-cleaner`，因此请在计划中列出该路径。此步骤是可选的，且仅适用于本地目标；直接的 `df -k/-h` 读数仍是事实依据。绝不要在控制器 Mac 上运行它来代替对远程目标的测量。

一次只运行一个会改变状态的命令。读取结果后，再发送下一个命令。每条命令执行后，运行能够区分成功与部分成功的后置条件检查。

对于不是用户数据、应用状态、数据库或受保护路径的精确普通文件，在用户确认确切路径后，优先使用可恢复的 Finder 废纸篓移动操作：

```bash
/usr/bin/osascript \
  -e 'on run argv' \
  -e 'tell application "Finder" to delete (POSIX file (item 1 of argv))' \
  -e 'end run' -- "<exact-path>"
```

移到废纸篓通常不会立即释放物理空间，必须在计划中说明这一点。`scripts/safe_delete.py` 是一个旧版永久删除辅助工具，带有交互式提示以及有限的系统/凭据拒绝列表。它不会将文件移到废纸篓，不会检查每个用户数据根目录，不会检测打开的文件，也无法独立证明已回收的字节数。只有在用户明确批准了确切的非用户数据目标以及不可逆删除操作时，才使用它：

```bash
uv run scripts/safe_delete.py <exact-path> [<exact-path> ...]
```

不要将此辅助工具用于用户文档、应用管理的缓存（例如 Apple 内容缓存）、数据库、凭据或任何用途不明确的目标。

以下两个范围有限的 Finder 废纸篓分支仍然可用，且不会削弱上述排除条件：

- 对于确切的非活动应用缓存，如果没有经过验证的受支持管理控制，请遵循 `references/cleanup_targets.md` 中针对命名缓存的发现/使用中协议，解释重建成本，并获得对该确切缓存路径的明确批准。
- 对于确切获批准的用户数据根目录中的重复文件，首先显示每组重复文件的大小/哈希值以及所有路径。用户必须指定要保留的副本以及要移除的每个副本。仅将这些已确认的文件移到 Finder 废纸篓；绝不要使用永久删除辅助工具、自动重复项选择标志、`all`、通配符或目录级目标。验证源路径已移到废纸篓，并说明在单独检查并清空废纸篓之前，物理空间不会被释放。

## 第 4 阶段：验证与观察

验证必须涵盖已批准计划中的所有条款：

- 重新读取 `df -k` 和 `df -h`；根据前后读数计算回收的空间，而不是依据删除工具的声明。
- 重新查询已清理子系统的激活状态、配置和物理使用量。
- 重新解析每项受保护服务的 PID、监听器、启动机制和健康探针。磁盘状态健康并不能证明服务仍然正常运行。
- 当 APFS 记账可能存在延迟或源可能重新填充时，以有界时间间隔进行观察。记录每个时间戳和值。
- 如果未达到可用空间目标，停止所有删除操作。开始第二次只读分析，并依据测得的物理分配量对剩余来源进行排序。

仅知道命令退出代码时，绝不要报告“已修复”。成功的清理必须同时满足预期状态和受保护的不变量。

对于由辅助工具捕获了清理前快照的本地目标，使用以下命令生成比较结果：

```bash
uv run scripts/cleanup_report.py --snapshot after --compare
```

- `references/cleanup_targets.md` — 缓存、日志、应用程序、开发者、大文件和 Time Machine 目标语义。
- `references/docker_analysis.md` — 按对象进行的 Docker 和 OrbStack 分析、数据库卷保护措施以及重新填充的根因诊断。
- `references/mole_integration.md` — 交互式 Mole 分析和预览的 TTY 工作流。
- `references/report_templates.md` — 长篇通用报告和 Docker 报告模板。
- `references/safety_rules.md` — 受阻路径、确认、恢复和文件删除安全检查。
- `scripts/analyze_caches.py` — 有界缓存清单。
- `scripts/analyze_code_sign_clones.py` — 只读的当前用户代码签名克隆清单；获得批准后，可以重新验证精确的候选 SHA，并写入不覆盖现有文件的批处理清单。
- `scripts/find_app_remnants.py` — 应用程序残留候选项；读取其固定的 Applications 和 `~/Library` 根目录，因此需要先要求获得该范围的授权。
- `scripts/analyze_large_files.py` — 在已批准路径内发现大文件。
- `scripts/analyze_dev_env.py` — Docker/包管理器清单，以及固定常见项目根目录下的 `.git` 大小；需要先要求获得完整的读取范围授权。
- `scripts/safe_delete.py` — 针对精确批准的非用户数据目标进行永久删除的旧版防护工具；它不是废纸篓或恢复工具。
- `scripts/cleanup_report.py` — 默认针对 `/System/Volumes/Data` 进行本地目标清理前后报告，并支持使用显式的 `--volume` 覆盖。

## 不要在以下情况下使用此技能

- 目标是 Windows 或 Linux。
- 请求的操作需要禁用 SIP 或绕过 macOS 保护机制。
- 用户要求在没有可审计范围和确认门槛的情况下静默或自动删除。
- 任务仅用于调整应用程序行为，不涉及磁盘空间诊断或恢复目标。
