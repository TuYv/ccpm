调用此 skill 时：

1. **解析参数**，获取可选的类型/主题提示（例如 `roguelike`、
   `space survival`、`cozy farming`）。如果参数为 `open` 或未提供参数，则从头开始。
   同时确定审核模式（仅确定一次，并在本次运行中用于所有 gate 的生成）：
   1. 如果传入了 `--review [full|lean|solo]` → 使用该值
   2. 否则读取 `production/review-mode.txt` → 使用其中的值
   3. 否则 → 默认为 `lean`

   完整的检查模式请参阅 `.claude/docs/director-gates.md`。

2. **检查是否已有概念设计工作**：
   - 如果 `design/gdd/game-concept.md` 存在，则读取它（继续推进，不要重新开始）
   - 如果 `design/gdd/game-pillars.md` 存在，则读取它（基于已确定的支柱继续构建）

3. 以交互方式**逐步完成构思阶段**，在每个阶段向用户提问。
   不要在无交流的情况下生成所有内容——目标是进行**协作式探索**，
   AI 应充当创意引导者，而不是取代人类的愿景。

   在整个头脑风暴过程中的关键决策点**使用 `AskUserQuestion`**：
   - 有约束的偏好问题（类型偏好、范围、团队规模）
   - 展示选项后进行概念选择（“哪些 2-3 个概念最能引起你的共鸣？”）
   - 方向选择（“进一步发展、继续探索，还是制作原型？”）
   - 概念完善后对支柱进行排序
   先在对话正文中写出完整的创意分析，然后使用
   `AskUserQuestion` 通过简洁的标签记录决策。

   应遵循的专业工作室头脑风暴原则：
   - 暂缓评判——在探索阶段，没有坏点子
   - 鼓励不同寻常的想法——跳出框架的思考能够激发更好的概念
   - 相互延展——使用“是的，而且……”式回应，而不是“但是……”
   - 将约束作为创意燃料——限制往往能催生最好的想法
   - 为每个阶段设定时间限制——保持推进势头，不要在早期过度斟酌

### 阶段 1：创意发现

首先了解创作者，而不是游戏。以对话方式询问以下问题
（不要像核对清单一样逐项提问）：

**情感锚点**：
- 游戏中是否有某个时刻真正打动了你、令你兴奋，或让你忘记了时间？
  具体是什么营造了这种感受？
- 是否有某种你一直想在游戏中体验、却始终未能真正找到的幻想或力量体验？

**偏好画像**：
- 你投入时间最多的 3 款游戏是什么？是什么让你不断回到这些游戏中？
  *（以纯文本形式询问此问题——用户必须能够自由输入具体的游戏名称。
  不要将此问题放入带有预设选项的 AskUserQuestion 中。）*
- 你喜欢哪些游戏类型？会避开哪些类型？为什么？
- 你更喜欢挑战你的游戏、让你放松的游戏、为你讲故事的游戏，
  还是让你表达自我的游戏？*（对此使用 `AskUserQuestion`——这是一个有约束的选择。）*

**实际约束**（在头脑风暴之前明确探索空间）。
将这些问题合并到一个多标签页的 `AskUserQuestion` 中，并使用以下准确的标签页名称：
- 标签页“体验”——“你最希望玩家获得哪种体验？”（挑战与精通 / 故事与发现 / 表达与创造 / 放松与心流）
- 标签页“时间线”——“你现实可行的开发周期是多久？”（数周 / 数月 / 1-2 年 / 多年）
- 标签页“开发水平”——“你目前处于开发历程的哪个阶段？”（第一款游戏 / 曾发布过游戏 / 有专业背景）

请严格使用这些选项卡名称——不要重命名或重复使用。

将答案**综合**为一份**创意简报**——用 3-5 句话概括此人的情感目标、品味偏好和限制条件。
向其复述该简报，并确认它准确表达了他们的意图。

### 阶段 2：概念生成

以创意简报为基础，生成 **3 个不同的概念**，
每个概念采用不同的创意方向。使用以下构思技巧：

**技巧 1：动词优先设计**
从玩家的核心动词（建造、战斗、探索、解谜、生存、
创造、管理、发现）出发，并以此向外扩展。这个动词本身就是游戏。

**技巧 2：混搭法**
组合两个意想不到的元素：[类型 A] + [主题 B]。两者之间的张力
会创造出独特的吸引点。（例如，“农场模拟 + 宇宙恐怖”、
“类 Rogue + 恋爱模拟”、“城市建造 + 即时战斗”）

**技巧 3：体验优先设计（MDA 逆向推导）**
从期望玩家产生的情感出发（MDA 框架中的审美目标：
感官、幻想、叙事、挑战、社交、探索、表达、
消遣），反向推导出能够产生这种情感的动态与机制。

对于每个概念，提供：
- **暂定标题**
- **一句话推介**（1-2 句话——必须通过“10 秒测试”）
- **核心动词**（玩家最常执行的单一动作）
- **核心幻想**（情感承诺）
- **独特卖点**（通过“而且还有”测试：“像 X，而且还有 Y”）
- **主要 MDA 审美目标**（哪种情感占主导？）
- **预计规模**（小型 / 中型 / 大型）
- **可行理由**（用 1 句话说明其与市场/受众的契合度）
- **最大风险**（用 1 句话说明最难解答的未决问题）

展示全部三个概念。然后使用 `AskUserQuestion` 获取选择。

**关键要求**：这必须是一个普通列表调用——不要使用选项卡或表单字段。严格使用以下结构：

```
AskUserQuestion(
  prompt: "Which concept resonates with you? You can pick one, combine elements, or ask for fresh directions.",
  options: [
    "Concept 1 — [Title]",
    "Concept 2 — [Title]",
    "Concept 3 — [Title]",
    "Combine elements across concepts",
    "Generate fresh directions"
  ]
)
```

此处不要使用 `tabs` 字段。`tabs` 表单仅用于多字段输入——在这里使用它会导致“Invalid tool parameters”错误。这是一个普通的 `prompt` + `options` 调用。

绝不要施压要求对方做出选择——让他们从容考虑。

### 阶段 3：核心循环设计

针对选定的概念，使用结构化提问来构建核心循环。
核心循环是游戏跳动的心脏——如果它单独运行时都不好玩，
那么再多的内容或打磨也无法拯救这款游戏。

**30 秒循环**（即时体验）：

将以下问题作为 `AskUserQuestion` 调用提出——根据选定的概念生成选项，不要硬编码：

1. **核心动作的手感**——提示：“核心动作应具备怎样的主要手感？”生成 3-4 个符合该概念类型和基调的选项，并提供一个可自由输入的出口（`I'll describe it`）。

2. **关键设计维度**——确定对这一特定概念而言最重要的设计变量（例如世界反馈性、节奏、玩家自主性），并就此提问。生成与该概念相符的选项。始终提供一个可自由输入的出口。

收集回答后，进行分析：这个动作本身是否令人满足？是什么让它感觉良好？（音频反馈、视觉表现力、时机带来的满足感、战术深度？）

**5 分钟循环**（短期目标）：
- 是什么结构将每时每刻的游玩过程组织成循环？
- “再来一回合”/“再跑一局”的心理效应会在何处出现？
- 玩家在这一层面需要做出哪些选择？

**单次游玩循环**（30-120 分钟）：
- 一次完整的游玩过程是什么样的？
- 自然的停止点在哪里？
- 什么样的“钩子”会让玩家在不玩游戏时仍然想着它？

**成长循环**（数天/数周）：
- 玩家如何成长？（力量？知识？可选项？故事？）
- 长期目标是什么？游戏在何时算是“完成”？

**玩家动机分析**（基于自我决定理论）：
- **自主性**：玩家拥有多少有意义的选择？
- **胜任感**：玩家如何感受到自己的技能正在提升？
- **归属感**：玩家如何感受到联结（与角色、
  其他玩家或这个世界的联结）？

### 阶段 4：支柱与边界

真正的 AAA 工作室（《战神》《哈迪斯》《最后生还者》）会使用游戏支柱，
确保数百名团队成员做出的决策都指向同一个方向。即使对于独立开发者，
支柱也能防止范围蔓延，并让愿景保持清晰。

共同定义 **3-5 个支柱**：
- 每个支柱都有一个**名称**和一个**单句定义**
- 每个支柱都有一个**设计检验标准**：“如果我们在 X 和 Y 之间争论，
  这个支柱要求我们选择 __”
- 各个支柱之间应该让人感到彼此存在张力——如果所有支柱都指向
  同一个方向，那它们发挥的作用还不够

然后定义 **3 个以上的反支柱**（明确这款游戏不是什么）：
- 反支柱可以防止最常见的范围蔓延形式：“如果加入……会不会很酷？”
  这类功能并不能服务于核心愿景
- 表述格式为：“我们不会做[某件事]，因为它会损害[某个支柱]”

**支柱确认**：展示完整的支柱集合后，使用 `AskUserQuestion`：
- 提示：“这些支柱符合你对游戏的设想吗？”
- 选项：`[A] Lock these in` / `[B] Rename or reframe one` / `[C] Swap a pillar out` / `[D] Something else`

如果用户选择 B、C 或 D，完成修改，然后再次使用 `AskUserQuestion`：
- 提示：“支柱已更新。可以确定下来了吗？”
- 选项：`[A] Lock these in` / `[B] Revise another pillar` / `[C] Something else`

重复此过程，直到用户选择 [A] Lock these in。

**审查模式检查**——在启动 CD-PILLARS 和 AD-CONCEPT-VISUAL 之前应用：
- `solo` → 跳过二者。注明：“CD-PILLARS skipped — Solo mode. AD-CONCEPT-VISUAL skipped — Solo mode.” 继续进入阶段 5。
- `lean` → 跳过二者（它们不是 PHASE-GATE）。注明：“CD-PILLARS skipped — Lean mode. AD-CONCEPT-VISUAL skipped — Lean mode.” 继续进入阶段 5。
- `full` → 正常启动。

**在支柱和反支柱达成一致后，先通过 Task 并行启动 `creative-director` 和 `art-director`，然后再进入阶段 5。同时发出两个 Task 调用——不要等其中一个完成后才启动另一个。**

- **`creative-director`** — 门禁 **CD-PILLARS**（`.claude/docs/director-gates.md`）
  通过条件：完整的支柱体系，包括设计测试、反支柱、核心幻想和独特亮点。

- **`art-director`** — 门禁 **AD-CONCEPT-VISUAL**（`.claude/docs/director-gates.md`）
  通过条件：游戏概念的电梯演讲、包含设计测试的完整支柱体系、目标平台（如果已知），以及用户提到的任何参考游戏或视觉参照。

收集两个评审结果，然后使用包含两个选项卡的 `AskUserQuestion` 将它们一并呈现：
- 选项卡 **“支柱”**：呈现创意总监的反馈。选项沿用标准的 CD-PILLARS 处理方式——`Lock in as-is` / `Revise [specific pillar]` / `Discuss further`。
- 选项卡 **“视觉锚点”**：呈现美术总监提出的 2-3 个有名称的视觉方向选项。选项：每个已命名的方向（每个方向对应一个选项）+ `Combine elements across directions` + `Describe my own direction`。

用户选择的视觉锚点（已命名的方向或用户的自定义描述）将存储为**视觉识别锚点**——它会被写入游戏概念文档，并成为美术圣经的基础。

如果创意总监针对支柱返回 CONCERNS 或 REJECT，请先解决支柱问题，再询问用户选择视觉锚点——视觉方向应源自已经确认的支柱。

### 阶段 5：玩家类型验证

使用 Bartle 分类法和 Quantic Foundry 动机模型，验证这款游戏的实际目标受众：

- **主要玩家类型**：哪些人会热爱这款游戏？（成就型玩家、探索型玩家、
  社交型玩家、竞争型玩家、创造型玩家、叙事型玩家）
- **次要吸引力**：还有哪些人可能会喜欢它？
- **这款游戏不适合哪些人**：明确哪些人不会喜欢这款游戏，与了解哪些人会喜欢它
  同样重要
- **市场验证**：是否有面向类似玩家类型的成功游戏？我们能从它们的受众规模中学到什么？

### 阶段 6：范围与可行性

让概念立足于现实：

- **目标平台**：使用 `AskUserQuestion`——“你计划让这款游戏登陆哪些平台？”
  选项：`PC (Steam / Epic)` / `Mobile (iOS / Android)` / `Console` / `Web / Browser` / `Multiple platforms`
  记录答案——它会直接影响引擎建议，并将传递给 `/setup-engine`。
  如果相关，请注明平台方面的影响（例如，移动平台通常强烈推荐 Unity；主机平台意味着 Godot 存在局限；Web 平台意味着 Godot 可以顺利导出）。

- **引擎经验**：使用 `AskUserQuestion`——“你是否已经有自己惯用的引擎？”
  选项：`Godot` / `Unity` / `Unreal Engine 5` / `No preference — help me decide`
  - 如果他们选择了某个引擎 → 将其记录为他们的偏好，然后继续。不要质疑他们的选择。
  - 如果选择“No preference”→ 告诉他们：“本次会话结束后运行 `/setup-engine`——它会根据你的概念和目标平台，引导你完成整个决策过程。”不要在这里提出建议。
- **美术管线**：美术风格是什么？其制作成本有多高？
- **内容范围**：估算关卡/区域数量、物品数量和游戏时长
- **MVP 定义**：能够验证“核心循环是否有趣”的绝对最小构建版本是什么？
- **最大风险**：技术风险、设计风险、市场风险
- **范围层级**：完整愿景是什么？如果时间不足，最终发布的版本是什么？

**审查模式检查** — 在生成 TD-FEASIBILITY 之前应用：
- `solo` → 跳过。注明：“TD-FEASIBILITY 已跳过 — 单人模式。”直接进入范围层级定义。
- `lean` → 跳过（不是 PHASE-GATE）。注明：“TD-FEASIBILITY 已跳过 — 精简模式。”直接进入范围层级定义。
- `full` → 正常生成。

**确定最大的技术风险后，在定义范围层级之前，通过 Task 使用关卡 TD-FEASIBILITY（`.claude/docs/director-gates.md`）生成 `technical-director`。**

传入：核心循环描述、目标平台、引擎选择（或“未决定”）、已识别的技术风险列表。

向用户展示评估结果。如果为 HIGH RISK，则在最终确定之前提议重新审视范围。如果为 CONCERNS，则注明这些问题并继续。

**审查模式检查** — 在生成 PR-SCOPE 之前应用：
- `solo` → 跳过。注明：“PR-SCOPE 已跳过 — 单人模式。”继续生成文档。
- `lean` → 跳过（不是 PHASE-GATE）。注明：“PR-SCOPE 已跳过 — 精简模式。”继续生成文档。
- `full` → 正常生成。

**定义范围层级后，通过 Task 使用关卡 PR-SCOPE（`.claude/docs/director-gates.md`）生成 `producer`。**

传入：完整愿景范围、MVP 定义、时间估算、团队规模。

向用户展示评估结果。如果为 UNREALISTIC，则在编写文档之前提议调整 MVP 定义或范围层级。

4. **生成游戏概念文档**，使用以下位置的模板：
   `.claude/docs/templates/game-concept.md`。根据头脑风暴对话填写所有章节，包括 MDA 分析、玩家动机画像和心流状态设计章节。

   **在游戏概念文档中包含“视觉识别锚点”章节**，其中包含：
   - 选定的视觉方向名称
   - 一句话视觉规则
   - 2-3 条辅助视觉原则及其设计测试
   - 色彩理念摘要

   此章节是美术圣经的种子 — 它记录了“一切都必须动起来”这一决策，避免它在不同会话之间被遗忘。

5. 使用 `AskUserQuestion` 请求写入批准：
- 提示：“游戏概念已准备就绪。可以将其写入 `design/gdd/game-concept.md` 吗？”
- 选项：`[A] 是 — 写入` / `[B] 暂不 — 先修改一个章节`

如果选择 [B]：使用 `AskUserQuestion` 询问要修改哪个章节，选项为：`电梯演讲` / `核心幻想与独特卖点` / `支柱` / `核心循环` / `MVP 定义` / `范围层级` / `风险` / `其他 — 我会描述`

修改后，以 diff 或清晰的前后对比形式展示更新后的章节，然后使用 `AskUserQuestion` — “准备好写入更新后的概念文档了吗？”
选项：`[A] 是 — 写入` / `[B] 修改另一个章节`
重复此过程，直到用户选择 [A]。

如果选择“是”，则使用 `.claude/docs/templates/game-concept.md` 中的模板生成文档，根据头脑风暴对话填写所有章节，并写入文件，按需创建目录。

**范围一致性规则**：核心身份表中的“预估范围”字段必须与“范围层级”章节中的完整愿景时间线一致 — 不能只写“大型（9 个月以上）”。应写为“大型（X–Y 个月，单人）”或“大型（X–Y 个月，N 人团队）”，以确保摘要表准确无误。

6. **建议后续步骤**（按以下顺序——这是专业工作室的
   前期制作流程）。列出所有步骤——不要缩写或截断：

**路径 A——设计优先**（如果概念已经明确定义，推荐使用）：
