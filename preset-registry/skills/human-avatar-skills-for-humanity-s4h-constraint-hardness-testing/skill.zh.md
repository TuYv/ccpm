# 约束硬度测试

组织会积累各种幽灵约束——有些规则曾经确实存在，后来却僵化了；有些观念从未经过检验；还有些只是某个人的偏好，却因反复提及而听起来像是政策。这项技能会在你投入精力规避或接受这些约束之前，将真正的限制与想当然的限制区分开来。

---

## 你的流程

**第 1 步：陈述约束**
完全按照其被陈述或假定的原样写下来。不要对其加以润色——幽灵往往就藏在这种不精确之中。

**框架确认：** 在继续之前，确认具体的约束及其所阻碍的目标。用一句话说明你识别出的内容——即你所理解的确切约束，以及它所阻止的目标或行动——然后使用 `AskUserQuestion`：
- **问题：** “我的理解是：[用一句话概括约束及其所阻碍的目标]。对吗？”
- **标题：** “框架”
- **选项：**
  - **是——继续**——框架正确
  - **调整**——其中一个要素有误；用户会在你继续之前予以纠正
  - **重新界定**——实际情况与当前理解不同；在继续之前纳入修正内容

**第 2 步：追溯来源**
是谁说这个约束存在？什么时候说的？它的来源是法律或法规、已签署的合同、技术上的不可能性、领导层的决定、团队偏好，还是来源不明？来源决定了其硬度上限。

**第 3 步：后果测试**
如果违反这个约束，实际会发生什么？具体说明其后果。如果答案是“我不确定”或“有人会不高兴”，那么这个约束就不是硬约束。区分真实后果（罚款、违约、系统故障）和假定后果（阻力、尴尬、政治成本）。

**第 4 步：先例检查**
以前是否有人尝试过改变或违反这个约束？结果如何？没有先例通常意味着从未有人检验过它，而不意味着它无法改变。

**第 5 步：条件测试**
在什么情况下这个约束不适用？真正的硬约束没有例外。如果你能找到某种不受该约束限制的情形，那么这个约束就比所陈述的更软。

**第 6 步：分类**
- **硬约束**：来源真实，后果具体，无例外，且有先例证实
- **软约束**：真实存在但可协商，后果涉及政治因素或个人偏好
- **假定约束**：没有明确来源，后果未经检验
- **过时约束**：曾经是硬约束，但情况已经发生变化

## 人工确认

在继续之前，使用 `AskUserQuestion` 工具。用 1–2 句话陈述你对当前情况的理解——正在分析什么，以及核心问题是什么——然后询问：

- **问题：** “我的理解是：[用 1–2 句话说明你的理解]。你希望如何继续？”
- **标题：** “范围”
- **选项：**
  - **完整分析**——完成所有步骤，并在整个过程中展示推理
  - **仅关键发现**——只输出结论，跳过分步细节
  - **仅判断真实还是假定**——对每项约束进行分类，不提供完整分析
  - **重新界定**——当前理解有误；请予以纠正，后续分析将基于修正后的框架进行

根据用户的选择继续。如果用户重新表述了问题，请在运行任何分析之前纳入其更正。

## 输出格式

**所陈述的约束：**
> [原文措辞]

**来源：** [法律/合同/技术/决策/偏好/未知] — [具体出处]

**违反约束的后果：**
> [具体说明] — 真实 / 假定

**先例：** [测试时发生的情况，或“未经测试”]

**不适用的条件：**
> [如有]

**分类：** 硬性 / 软性 / 假定 / 过时

**建议采取的行动：**

| 分类 | 行动 |
|----------------|--------|
| 硬性 | 接受 — 围绕它进行设计 |
| 软性 | 明确协商 |
| 假定 | 对其进行测试 — 直接询问来源方 |
| 过时 | 对其提出质疑 — 建议移除 |

---

## 注意事项

最危险的类别是假定，因为它看起来像硬性约束。在接受任何无法精确追溯来源的
约束之前，应将其视为假定并进行测试 — 测试的成本几乎总是低于采用永久性变通方案的成本。

- **标题：**“下一步”
- **选项：**
  - `/s4h-constraint-workaround-mapping` — 绕开硬性约束
  - `/s4h-constraint-scope-reduction` — 缩小范围，以避开无法绕过的约束
  - `/s4h-decision-option-mapping` — 查看在既有硬性和软性约束下还剩哪些选项
  - **完成** — 收尾并综合整理目前为止的内容
