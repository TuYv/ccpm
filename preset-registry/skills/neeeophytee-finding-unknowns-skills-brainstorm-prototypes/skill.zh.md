# 头脑风暴与原型

用户有一些尚未意识到的已知条件：他们无法用语言表达某些标准，但看到时便能辨认。在原型设计阶段发现这些标准的成本很低；在实现过程中才发现则代价高昂，因为细微的规格变更可能意味着截然不同的代码。应提供一些可供他们反馈的方案。

## 步骤

1. 首先明确范围：要决定什么（布局？方案？数据模型？语气？），以及明确不包含什么。每轮只做一个决策。
2. 提供 3-5 个**截然不同，而非同一想法的细微变体**。如果两个变体可能得到相同的反馈，就替换掉其中一个。
3. 确保它们成本低廉且可随时丢弃：
   - 视觉/UX → 使用虚假数据的单个自包含 HTML 文件，不使用后端，不保存状态。
   - 方案 → 为每个方案提供一屏草图：核心构想、优化目标以及最突出的权衡。
   - 排序列表 → 从成本最低到最具雄心的方案依次排列，以便用户划定界限。
4. 为每个变体标注它所依据的假设（“这个方案假设信息密度比留白更重要”），这样用户的反馈揭示的是背后的评判标准，而不仅仅是偏好。
5. 收集反馈，然后用语言概括所了解到的内容：“你始终否定 X，这表明真正的需求是 Y。”这句话就是交付成果——它将成为规格的一部分。

## 约束

- 此处产出的任何内容都不是生产代码。应明确说明这一点，并且不要将原型接入真实应用。
- 不要过早收敛到你会选择的变体。重点在于覆盖整个可能性空间。
- 如果用户对所有变体都没有反应，这本身也是一种信号：对决策空间的界定有误。应重新界定并再次尝试，而不是生成更多同类方案。
