# 完成开发分支

## 概述

集成方式的选择与检出项的生命周期是相互独立的。先验证，只变更任务拥有的资源，然后证明哪些内容已被移除或保留。

**核心原则：** 最新证据 -> 经授权的集成 -> 感知所有权的清理 -> Git/路径回读验证。

**开始时声明：** 说明正在结束哪个分支/工作树的生命周期。

## 第 1 步：环境和所有权检测

读取任务的 `TaskStartSnapshot` 和仓库当前状态。记录：

- 根目录、`HEAD`、分支/分离状态、与上游的分歧，以及正在进行的 Git 操作；
- 已暂存/未暂存/未跟踪的路径，以及任务拥有的增量；
- `git worktree list --porcelain`；
- 分支/工作树的创建者、任务所有权、基础分支和清理触发条件。

如果存在冲突、处于分离状态、验证失败、清理目标中存在脏状态/未跟踪内容，或所有权未知，则停止。不要根据名称 `main` 或 `master` 推断基础分支；应使用任务记录、仓库权威信息或用户的明确指示。绝不要自动执行 stash、reset、clean、pull、rebase、amend、force-push，也不要绕过钩子。

如果不存在任务创建的分支/工作树，并且未要求集成，则跳过此工作流：报告本地任务提交以及 `Task clean` 和 `Repository clean`；不要凭空增加合并/PR 流程。

## 第 2 步：最新验证

运行可证明任务已完成的最小当前权威测试集。如果测试失败，则保留所有工作并返回诊断。不要将该分支描述为已就绪。

## 第 3 步：选择经授权的结果

当任务分支确实需要处置时，仅提供适用的选项：

1. 在本地合并到已记录的基础分支；
2. 推送并创建/更新 PR；
3. 保留分支以供稍后集成；
4. 丢弃确切的任务所有分支/工作树。

推送、PR、远程删除、发布和强制操作需要用户明确授权。丢弃操作需要用户重新进行准确的键入式确认，并明确指出将丢失的分支、工作树路径以及提交/增量。笼统同意是不够的。

## 第 4 步：执行时不进行隐藏变更

### 本地合并

验证目标检出项是安全的，切换到已记录的基础分支，在不隐式执行 pull 的情况下进行合并，并对合并后的结果重新运行验证。如果集成或验证失败，则保留双方历史并停止。

### 推送或 PR

仅推送经授权的任务分支，并创建/更新包含摘要和最新测试证据的 PR。创建 PR 本身并不能证明已完成合并，也不要求保留临时工作树。

### 保留分支

保留该分支。默认移除由任务创建且状态干净的临时工作树；只有在明确需要持续使用该检出项时才保留它，并报告原因。

### 丢弃

在收到准确确认后，仅移除指定的、状态干净且归任务所有的工作树，然后移除指定分支。如果任一项与确认内容不一致，则停止并再次询问。

## 第 5 步：删除分支前证明已集成

使用与合并策略相匹配的证据：

- merge/fast-forward：证明任务分支的顶端提交是已记录基础分支的祖先；
- squash/rebase：使用最新的 PR 合并元数据，以及适合相应策略的补丁等价性验证（对经过 rebase 的提交使用 `git cherry`；对 squash 使用稳定的 patch-id 或有界的变更路径/树比较），而不是仅使用祖先关系测试；
- 未合并/开放的 PR：保留分支，除非已准确确认丢弃。

绝不能仅仅因为 PR 已打开，或存在名称相似的提交，就删除分支。

## 第 6 步：按依赖顺序清理

对于干净且归任务所有的资源：

1. 切换到另一个安全且已注册的检出目录；绝不能移除当前工作目录；
2. 首先使用 `git worktree remove <exact-path>` 移除/注销工作树；
3. 再次读取 `git worktree list --porcelain` 的输出；
4. 验证该确切路径已不复存在；
5. 只有这样，才能删除已集成或已得到明确确认的分支；
6. 再次读取分支引用、`HEAD` 和仓库状态。

不要例行使用 `--force`、全局 `git worktree prune`、通配符删除，也不要清理任务所有权记录中不存在的资源。在 Windows 上，Git 可能会注销工作树，但其目录仍处于锁定状态：重新检查注册状态和确切的解析后路径；在安全的情况下，只移除经证实归任务所有且干净的残留项，否则保留它并报告锁定状态/路径。绝不能扩大删除范围。

## 最终 Git 回执

报告：

- 当前分支和提交 SHA/消息；如果不存在提交，则报告原因；
- 分别报告 `Task clean: yes|no` 和 `Repository clean: yes|no`；
- 已创建、移除或保留的分支/工作树，以及相应的证据/原因；
- 集成证据以及仍需用户执行的任何操作。

`Task clean` 表示不存在归任务所有且尚未提交的变更。`Repository clean` 表示仓库中不存在任何已暂存、未暂存或未跟踪的状态。

这是本地 Git 回执；除再次读取到的证据外，它并不是有关完成或合并情况的权威结论。

## 集成

仅在分支/工作树集成或显式生命周期处理属于任务范围时调用。与 `using-git-worktrees` 和 `verification-before-completion` 配合使用。
