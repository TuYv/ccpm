# 诊断 Bug

一套用于处理棘手 Bug 的严谨方法。只有在有明确理由时才能跳过阶段。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），以清晰理解相关模块，并检查你所涉及区域中的 ADR。

## 脱敏

此技能会要求你展示命令、输出和捕获的制品。**务必先对所有机密信息进行脱敏**——在原位置写入 `<REDACTED>`。基于环境变量构建循环，让凭据保留在环境中，而不是出现在你展示的内容里。捕获的制品会携带身份验证标头：仅引用包含有效信号的行。

如果脱敏后的输出不足以诊断 Bug，请说明情况并询问用户。

## 阶段 1——构建反馈循环

**这就是此技能的核心。** 其他一切都是机械性工作。如果你有一个针对该 Bug 的**紧密**通过/失败信号——一个会因_这个_ Bug 而变红的信号——你就能找到原因；二分查找、假设检验和插桩都只是在利用这个信号。如果没有这样的信号，无论盯着代码看多久都无济于事。

要在这里投入远超其他环节的精力。**要积极。要有创造力。绝不放弃。**

### 构建反馈循环的方法——大致按以下顺序尝试

1. 在任何能够触达该 Bug 的边界编写**失败测试**——单元测试、集成测试或端到端测试。
2. 针对正在运行的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用固定输入进行 **CLI 调用**，将 stdout 与已知正确的快照进行差异比较。
4. 编写**无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并对 DOM/控制台/网络进行断言。
5. **重放捕获的跟踪记录。** 将真实的网络请求 / 载荷 / 事件日志保存到磁盘；以隔离方式通过相应代码路径进行重放。
6. **一次性测试工具。** 启动系统的最小子集（一个服务、模拟的依赖项），通过一次函数调用来执行触发 Bug 的代码路径。
7. **属性测试 / 模糊测试循环。** 如果 Bug 是“输出有时错误”，运行 1000 个随机输入并查找失败模式。
8. **二分查找测试工具。** 如果 Bug 出现在两个已知状态（提交、数据集、版本）之间，自动执行“在状态 X 启动、检查、重复”，以便使用 `git bisect run`。
9. **差异比较循环。** 让相同输入分别通过旧版本和新版本（或两种配置），并比较输出差异。
10. **HITL bash 脚本。** 最后的手段。如果必须由人来点击，就使用 `scripts/hitl-loop.template.sh` 来引导_他们_，使循环仍然保持结构化。捕获的输出会反馈给你。

构建正确的反馈循环，Bug 就已经解决了 90%。

### 收紧循环

将循环视为一个产品。一旦拥有了_一个_循环，就要将其**收紧**：

- 能否让它更快？（缓存设置、跳过无关的初始化、缩小测试范围。）
- 能否让信号更明确？（针对具体症状进行断言，而不是只检查“没有崩溃”。）
- 能否让它更具确定性？（固定时间、设置 RNG 种子、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环只比没有循环稍好一点；一个耗时 2 秒且结果确定的循环才足够紧密——堪称调试超能力。

### 非确定性 Bug

目标不是得到一个稳定复现，而是获得**更高的复现率**。将触发过程循环 100 次、并行执行、增加压力、缩小时间窗口、注入休眠。复现率为 50% 的偶发 Bug 是可调试的；复现率为 1% 的则不是——继续提高复现率，直到它变得可调试。

### 当你确实无法构建循环时

停下来并明确说明情况。列出你尝试过的方法。使用 AskUserQuestion 工具向用户请求：(a) 访问能够复现问题的环境，(b) 一份经过脱敏的已捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 获得添加临时生产环境插桩的许可。在没有循环的情况下，**不要**继续提出假设。

### 完成标准——一个能够变红的紧密循环

当循环足够**紧密**且**能够变红**时，阶段 1 即告完成：你可以给出**一个命令**——脚本路径、测试调用或 curl——并且你**已经至少运行过一次**（展示调用及其经过脱敏的输出），同时该命令满足：

- [ ] **能够变红**——它会执行实际存在缺陷的代码路径，并断言**用户描述的确切症状**，因此能在此缺陷存在时变红，并在修复后变绿。不能只是“运行时不报错”——它必须能够_捕获这个特定缺陷_。
- [ ] **确定性**——每次运行都得到相同的判定结果（对于偶发性缺陷：按照上述要求，将其固定到较高的复现率）。
- [ ] **快速**——耗时应为数秒，而不是数分钟。
- [ ] **可由智能体运行**——你可以在无人值守的情况下运行它；只有通过 `scripts/hitl-loop.template.sh` 才允许人类参与循环。

如果你发现自己在这个命令尚不存在时就开始阅读代码以构建理论，**请停下来——直接跳到假设，正是此技能要防止的失败方式。** 没有能够变红的命令，就不能进入阶段 2。

## 关键：没有循环，就没有理论

反馈循环**就是**这项技能。在一个紧密且能够变红的命令存在之前，不要提出假设、添加插桩或进行修复——这个命令必须已经至少运行过一次，能够快速、确定性地触发此缺陷的确切症状。没有能够变红的命令，就不能进入阶段 2。

## 阶段 2——复现并最小化

运行循环。观察它变红——缺陷出现了。

确认：

- [ ] 循环产生的是**用户**所描述的失败模式，而不是恰好发生在附近的另一个失败。缺陷找错了 = 修复也会错。
- [ ] 该失败可以在多次运行中复现（或者，对于非确定性缺陷，其复现率足够高，可以据此进行调试）。
- [ ] 你已经捕获了确切症状（错误消息、错误输出、响应缓慢），以便后续阶段能够验证修复是否确实解决了该问题。

### 最小化

一旦循环变红，就将复现场景缩减为**仍然会变红的最小场景**。每次**只删除一项**输入、调用方、配置、数据或步骤，并在每次删除后重新运行循环——只保留触发失败不可或缺的内容。

这样做的原因：最小复现可以缩小阶段 3 中的假设空间（剩余需要怀疑的活动部件更少），并在阶段 5 中成为简洁的回归测试。

当**所有剩余元素都不可或缺**时，即告完成——移除其中任意一个元素，都会使循环变绿。

在完成复现**并且**最小化之前，不要继续。

## 阶段 3——提出假设

在测试任何假设之前，先生成 **3–5 个按优先级排序的假设**。只生成一个假设会让你锚定在第一个看似合理的想法上。

每个假设都必须**可以证伪**：说明它会作出什么预测。

> 格式：“如果 <X> 是原因，那么 <changing Y> 会让错误消失 / <changing Z> 会让错误变得更严重。”

如果你无法明确说出预测结果，那么这个假设就只是一种感觉——丢弃它，或者让它更精确。

**在测试前向用户展示排序后的列表。** 他们通常掌握能够立即改变排序的领域知识（“我们刚刚部署了与第 3 项相关的更改”），或者知道哪些假设已经被排除。这是一个成本很低、却能节省大量时间的检查点。不要因此停滞——如果用户暂时不在线，就按你的排序继续进行。

## 阶段 4 — 插桩

每个探针都必须对应阶段 3 中的某个具体预测。**每次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分不同假设的边界处添加**针对性日志**。
3. 绝不要“记录所有内容，然后用 grep 搜索”。

**为每条调试日志添加标签**，使用唯一前缀，例如 `[DEBUG-a4f2]`。这样在最后清理时，只需执行一次 grep。没有标签的日志保留；带标签的日志删除。

**性能分支。** 对于性能回归，日志通常不是正确的工具。应该先建立基准测量（计时工具、`performance.now()`、分析器、查询计划），然后进行二分排查。先测量，再修复。

## 阶段 5 — 修复 + 回归测试

在修复之前编写回归测试——但前提是存在一个**正确的测试接缝**。

正确的接缝是指，测试能够按照调用点实际发生的方式覆盖**真实的错误模式**。如果唯一可用的接缝过于浅层（例如，错误需要多个调用方才能触发，但测试只覆盖单个调用方；或者单元测试无法复现触发错误的调用链），那么在该处编写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是一个发现。** 将其记录下来。代码库架构正在妨碍对此错误进行可靠的回归保护。将此问题标记出来，留待下一阶段处理。

如果存在正确的接缝：

1. 将最小化复现转换成该接缝处的失败测试。
2. 确认它会失败。
3. 应用修复。
4. 确认它会通过。
5. 针对原始的（未经最小化的）场景，重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 复盘

在宣布完成之前，必须满足以下要求：

- [ ] 原始复现不再能够复现问题（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或者已记录不存在测试接缝）
- [ ] 已删除所有 `[DEBUG-...]` 插桩（对该前缀执行 `grep`）
- [ ] 已删除一次性原型（或者将其移至明确标记的调试位置）
- [ ] 在提交 / PR 消息中说明最终被证实正确的假设——让下一位调试人员能够从中学习

**然后使用 AskUserQuestion 工具询问，什么措施原本可以防止这个错误**——选项包括：没有良好的测试接缝 / 调用方相互纠缠 / 隐式耦合 / 没有值得改变的地方，并提供“其他”选项以涵盖其余情况。如果答案涉及架构更改（没有良好的测试接缝、调用方相互纠缠、隐式耦合），请将具体情况移交给 `/mattpocock:improve-codebase-architecture` skill。在修复完成**之后**再提出建议，而不是之前——现在你掌握的信息比开始时更多。

完成事后复盘后，对修复运行 `/mattpocock:code-review`——未经双轴审查的错误修复不能算完成。
