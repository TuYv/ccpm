# 公开构建——最佳实践

## 理念

公开构建不是营销，而是让人们看到你的工作过程。最好的帖子读起来就像你在向一位同为资深工程师的朋友讲述自己的思考过程。没有浮夸的营销废话，也没有“我很高兴地宣布”。只有：这是我构建的东西，这是它重要的原因，这是我从中学到的经验。

## 应该分享什么（以及不应该分享什么）

**应该分享：**
- 技术决策及其背后的理由（“之所以选择 SQLite 而不是 Postgres，是因为……”）
- 架构洞见（“这是 9 层路由管线的工作原理”）
- 失败经历以及你从中学到的东西（“花了 3 个小时调试一个竞态条件。根本原因是：……”）
- 前后指标对比（“压缩死亡螺旋：采用 Mnemos 后从 26 降至 0”）
- 发布开源项目时提供背景信息，而不只是贴链接
- 令你感到意外的反直觉发现

**绝不要分享：**
- 收入数字、用户数量、估值
- 客户名称或可识别客户身份的详细信息
- 内部 URL、API 密钥、凭据
- 任何受保密协议约束的内容
- 你可能无法兑现的路线图承诺
- 伪装成内容的“我们正在招聘”

## 各渠道的最佳实践

### LinkedIn

**受众：** 真正动手构建产品的工程师、CTO 和创始人。他们会在会议间隙浏览内容，寻找能引发思考的东西。

**格式：**
- 1-3 个段落，800-2000 个字符是最佳长度
- 开头先讲洞见，而不是背景
- 多使用换行——大段文字会扼杀互动
- 每篇帖子只传达一个明确要点
- 第一段不要放外部链接（LinkedIn 会降低引导用户离开平台的内容权重）

**语气：** 自信，并且能让人有所收获。你是一位资深工程师，正在向同行解释自己的方法。不要使用未经解释的术语。如果你采用了一种其他人可能不了解的技术，请简要说明。

**发布时间：** 周二至周四，目标时区上午 8-10 点。避免周末和周一早晨（每个人都在处理积压事务）。

**有效的内容：**
- 带有具体代码示例的技术深度解析
- 配有架构图的“我是如何构建 X 的”叙事
- 从失败中吸取的经验（这类内容的表现是成功故事的 3 倍）
- 对行业趋势立场鲜明的观点（但前提是你有数据支撑）

**表现不佳的内容：**
- 以“很高兴地宣布”开头的新闻稿
- 没有技术洞见的纯产品更新
- 缺乏实质内容的励志内容
- 超过 2500 个字符却没有强有力开头的帖子

### X (Twitter)

**受众：** 真正交付产品的开发者。他们浏览得快，做判断更快。你只有一句话的机会来赢得他们的注意。

**格式：**
- 最多 280 个字符
- 除非这个洞见确实需要 3 篇以上的帖子才能讲清楚，否则不要发帖串
- 开头先讲反直觉或令人意外的部分
- 每篇帖子只表达一个想法。如果你有两个想法，就发两篇帖子。
- 截图需要配有描述画面内容的替代文本

**语气：** 犀利、立场鲜明、零废话。想象一下，你正在给一位做产品的朋友发消息。如果听起来像营销文案，就删掉。

**发布时间：** 周二至周五，目标时区上午 9-11 点或下午 2-4 点。对于开发者受众，周末也可能有效（他们会在周末开发业余项目）。

**有效的内容：**
- 一句话技术洞见（“优秀 API 和卓越 API 之间的区别在于错误消息。”）
- 带有指标的前后对比
- “刚刚发布了 X。这是最令我意外的一件事。”
- 提出真诚的技术问题（诱导互动会适得其反）

**哪些做法效果不佳：**
- 堆砌话题标签
- 本可用一条帖子说完却拆成串文
- 没有个人经验支撑的泛泛“犀利观点”
- 发布链接却不提供上下文

## 内容日历节奏

**每天（如果你有话可说）：**
- 发布一条 X 帖子，介绍你当天正在做的事情或学到的东西

**每周：**
- 发布一条 LinkedIn 帖子：分享更深入的技术见解或项目里程碑

**每次事件发生时（由插件触发）：**
- PR 合并 → 24 小时内发布到 LinkedIn，当天发布到 X
- 功能上线 → 两个平台都发布，先发 LinkedIn，90 分钟后发 X
- 评审通过 → 仅发布到 X（架构见解简洁有力）
- 重大版本发布 → LinkedIn 深度解析 + X 公告

## 要避免的反模式

1. **“我们”陷阱** — 独立开发者使用“我们”会显得缺乏自信。除非你确实有一个团队，否则请使用“我”。
2. **互动诱饵** — 每篇帖子结尾都加上“同意吗？”或“有什么想法？”，会显得很迫切。让见解独立成章。
3. **只发帖、不构建** — 如果你已经两周没有交付任何成果，就不要发帖。你的内容应该是工作的副产品，而不是工作的替代品。
4. **LinkedIn 精英腔** — “我怀着谦卑与荣幸的心情宣布……”立即删掉。你又不是在领奖。
5. **过度润色** — 一篇读起来像是经过 5 轮编辑的帖子，会显得过于企业化。直接发布草稿。
6. **忽略回复** — 如果有人花时间与你互动，请在 24 小时内回复。评论区里的对话往往比原帖表现更好。

## 衡量哪些做法有效

跟踪以下指标（Buffer、LinkedIn 分析、X 分析）：
- **曝光量** — 有多少人看到了帖子
- **互动率** — (likes + comments + reposts) / impressions
- **个人资料访问量** — 帖子是否促使人们进一步了解你？
- **主动联系** — 提及具体帖子的私信、连接请求或电子邮件

一篇表现良好的 LinkedIn 帖子：互动率为 3-5%。表现出色的帖子：8% 以上。在 X 上，对于技术内容而言，任何高于 2% 的互动率都相当不错。

## 插件集成

公开构建插件会自动遵循这些实践：

```yaml
# What gets shared vs skipped:
on_pr_merged:
  - Share if: >3 files changed, meaningful commit message
  - Skip if: typo fix, dependency bump, config change only

on_feature_shipped:
  - Share: always, with screenshot
  - LinkedIn: deep dive on architecture decisions
  - X: punchy one-liner on impact

on_review_passed:
  - Share if: 3/3 unanimous approval
  - X only: architecture insights are punchy
  - Skip if: 1/3 or 0/3 (revisions aren't share-worthy)
```

## 默认匿名

所有帖子在发布前都会通过 `anonymize.yaml` 进行脱敏。公司名称会替换为通用描述。营收会替换为“规模化”。读者了解到的是你的工程实践，而不是你雇主的财务数据。
