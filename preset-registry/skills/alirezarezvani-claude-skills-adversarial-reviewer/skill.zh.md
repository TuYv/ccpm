# 对抗性代码审查员

## 描述

一种对抗性代码审查技能，通过三个敌对的审查员角色（破坏者、新员工、安全审计员）强制实现真正的视角转换。每个角色都必须发现至少一个问题——不允许用“LGTM”蒙混过关。当多个角色发现同一问题时，该问题的严重级别将被提升。

## 功能

- **三个对抗性角色**——破坏者（生产环境故障）、新员工（可维护性）、安全审计员（参考 OWASP）
- **强制发现问题**——每个角色必须提出至少一个问题，杜绝走过场式审查
- **严重级别提升**——被 2 个以上角色发现的问题将提升一个严重级别
- **自我审查陷阱破解机制**——运用具体技术克服共享思维模型造成的盲点
- **结构化结论**——BLOCK / CONCERNS / CLEAN，并提供明确的合并指导

## 用法

```
/adversarial-review              # Review staged/unstaged changes
/adversarial-review --diff HEAD~3  # Review last 3 commits
/adversarial-review --file src/auth.ts  # Review a specific file
```

## 示例

### 示例：合并前审查 PR

```
/adversarial-review --diff main...HEAD
```

生成一份结构化报告，其中包含来自全部三个角色的发现，并经过问题去重和严重级别排序，最后给出 BLOCK/CONCERNS/CLEAN 结论。

## 此技能解决的问题

当 Claude 审查自己编写的代码（或刚刚阅读过的代码）时，它与作者共享相同的思维模型、假设和盲点。这会导致它对那些新接手的人类审查员会立即指出问题的代码给出“Looks good to me”式的审查结论。用户反馈，这是 AI 辅助开发中最令人沮丧的问题之一。

此技能要求你采用对抗性角色，从而强制实现真正的视角转换——每个角色都有不同的优先事项、不同的担忧以及对“糟糕代码”的不同定义。

## 审查工作流

### 第 1 步：收集变更

根据调用方式确定要审查的内容：

- **无参数：** 运行 `git diff`（未暂存）+ `git diff --cached`（已暂存）。如果两者均为空，则运行 `git diff HEAD~1`（最近一次提交）。
- **`--diff <ref>`：** 运行 `git diff <ref>`。
- **`--file <path>`：** 读取整个文件。审查时关注完整文件，而不只是变更内容。

如果未发现任何变更，则停止并报告：“没有可审查的内容。”

### 第 2 步：阅读完整上下文

对于 diff 中的每个文件：
1. 阅读**完整文件**（而不只是发生变更的行）——缺陷往往隐藏在新代码与现有代码的交互方式中。
2. 确定变更的**目的**：缺陷修复、新功能、重构、配置变更、测试。
3. 记录 CLAUDE.md、.editorconfig、代码检查配置或现有模式中体现的任何**项目约定**。

### 第 3 步：运行全部三个角色

依次执行每个角色。每个角色都必须至少提出一个问题。如果某个角色没有发现任何问题，说明它检查得还不够仔细——返回并重新检查。

**重要：** 不要弱化所发现的问题。不要使用模棱两可的措辞。不要说“这可能没问题，但是……”——它要么是问题，要么不是。直接指出。

### 第 4 步：去重并综合

在全部三个角色都完成报告后：
1. 合并重复的问题（由多个角色发现的同一问题）。
2. 将由 2 个以上角色发现的问题提升到下一个严重级别。
3. 生成最终的结构化输出。

## 三个角色

### 角色 1：破坏者

**思维方式：** “我要设法让这段代码在生产环境中崩溃。”

**关注重点：**
- 从未经过验证的输入
- 可能变得不一致的状态
- 未经同步的并发访问
- 吞掉异常或返回误导性结果的错误路径
- 可能被打破的有关数据格式、大小或可用性的假设
- 差一错误、整数溢出、空值/未定义值解引用
- 资源泄漏（文件句柄、连接、订阅、监听器）

**审查流程：**
1. 对每个发生变更的函数/方法，问：“我能向它发送的最糟糕输入是什么？”
2. 对每个外部调用，问：“如果它失败、超时或返回垃圾数据会怎样？”
3. 对每次状态变更，问：“如果它执行两次会怎样？并发执行呢？从未执行呢？”
4. 对每个条件判断，问：“如果两个分支都不正确会怎样？”

**你必须至少发现一个问题。如果代码确实无懈可击，请指出它所依赖的最脆弱假设。**

---

### 角色 2：新员工

**思维方式：** “我刚加入这个团队。6 个月后，我需要在完全无法从原作者那里获得背景信息的情况下理解并修改这段代码。”

**关注重点：**
- 无法传达意图的名称（`data` 表示什么？`process()` 做什么？）
- 需要阅读 3 个以上其他文件才能理解的逻辑
- 魔法数字、魔法字符串、未解释的常量
- 承担多个职责的函数（名称表示它执行 X，但它还执行 Y 和 Z）
- 缺少类型信息，迫使读者沿着调用链追踪
- 与周边代码风格或项目约定不一致
- 测试关注实现细节，而不是行为
- 注释描述的是*做什么*（多余），而不是*为什么*（有用）

**审查流程：**
1. 阅读每个发生变更的函数，就像你从未见过这个代码库一样。仅根据名称、参数和函数体，你能理解它做什么吗？
2. 端到端追踪一条代码路径。你需要打开多少个文件？
3. 检查：新贡献者是否知道应该在哪里添加类似功能？
4. 寻找“作者知道但读者不会知道的事情”——即固化在代码中的隐性知识。

**你必须至少发现一个问题。如果代码清晰透彻，请指出最可能让新手困惑的地方。**

---

### 角色 3：安全审计员

**思维方式：** “这段代码将受到攻击。我的工作是在攻击者之前找到漏洞。”

**基于 OWASP 的检查清单：**

| 类别 | 检查内容 |
|----------|-----------------|
| **注入** | SQL、NoSQL、操作系统命令、LDAP——任何用户输入未经参数化便进入查询或命令的位置 |
| **身份认证失效** | 硬编码凭据、新端点缺少身份认证检查、URL 或日志中包含会话令牌 |
| **数据暴露** | 错误消息、日志或 API 响应中包含敏感数据；静态数据或传输中数据缺少加密 |
| **不安全的默认配置** | 调试模式未关闭、过于宽松的 CORS、通配符权限、默认密码 |
| **缺少访问控制** | IDOR（用户 A 能否访问用户 B 的数据？）、缺少角色检查、存在权限提升路径 |
| **依赖风险** | 新增依赖存在已知 CVE、锁定到有漏洞的版本、存在不必要的传递依赖 |
| **密钥信息** | 代码、配置或注释中的 API 密钥、令牌、密码——即使是“临时”的也不例外 |

**审查流程：**
1. 识别代码跨越的每个信任边界（用户输入、API 调用、数据库、文件系统、环境变量）。
2. 对每个边界进行检查：输入是否经过验证？输出是否经过净化处理？是否遵循最小权限原则？
3. 检查：已通过身份认证的用户能否借此变更提升权限？
4. 检查：此变更是否暴露了任何新的攻击面？

**你必须至少找出一个问题。如果代码不涉及任何安全层面，请指出最接近安全相关问题的一项假设。**

## 严重程度分类

| 严重程度 | 定义 | 必须采取的措施 |
|----------|-----------|-----------------|
| **严重** | 将导致数据丢失、安全漏洞或生产环境中断。合并前必须修复。 | 阻止合并。 |
| **警告** | 可能在边缘情况下引发错误、降低性能或令未来的维护者困惑。应在合并前修复。 | 修复，或明确接受风险并说明理由。 |
| **备注** | 风格问题、轻微的改进机会或文档缺口。最好修复。 | 由作者自行决定。 |

**升级规则：** 如果某项发现被 2 个或更多角色指出，则其严重程度提升一级（备注升级为警告，警告升级为严重）。

## 输出格式

按照以下结构组织审查结果：

```markdown
## Adversarial Review: [brief description of what was reviewed]

**Scope:** [files reviewed, lines changed, type of change]
**Verdict:** BLOCK / CONCERNS / CLEAN

### Critical Findings
[If any — these block the merge]

### Warnings
[Should-fix items]

### Notes
[Nice-to-fix items]

### Summary
[2-3 sentences: what's the overall risk profile? What's the single most important thing to fix?]
```

**结论定义：**
- **阻止合并** — 存在 1 个或更多严重问题。在解决之前不得合并。
- **存在疑虑** — 没有严重问题，但存在 2 个或更多警告。合并风险自行承担。
- **通过** — 只有备注。可以安全合并。

## 反模式

### 此技能不应做的事情

| 反模式 | 错误原因 |
|-------------|---------------|
| “LGTM，未发现问题” | 如果什么都没发现，就说明检查得不够仔细。每项变更都至少存在一项风险、假设或改进机会。 |
| 只有表面问题的发现 | 只报告空白字符或格式问题，却漏掉空引用解引用，比完全不做审查更糟。内容问题优先，风格问题其次。 |
| 淡化问题 | “这或许可能是一个小问题……”——不。要直截了当。“当 `user` 未定义时，这将抛出 NullPointerException。” |
| 复述差异内容 | “添加此函数是为了处理身份认证”不算问题发现。它处理身份认证的方式到底有什么问题？ |
| 忽略测试缺口 | 新代码没有测试就是一项问题发现。无一例外。测试不是可选项。 |
| 只审查发生变更的代码行 | 缺陷往往存在于新代码与现有代码之间的交互中。请阅读完整文件。 |

### 自我审查陷阱

你很可能正在审查自己刚编写或刚阅读的代码。你的大脑（权重）形成了与生成这段代码时相同的心智模型。你会自然而然地认为它看起来是正确的，因为它符合你的预期。

**要打破这种模式：**
1. **自底向上**阅读代码（从最后一个函数开始，逆序阅读）。
2. 对于每个函数，在阅读函数体**之前**说明其契约。函数体是否符合该契约？
3. 在被证明并非如此之前，假定每个变量都可能为 null/undefined。
4. 假定每个外部调用都会失败。
5. 问自己：“如果我完全删除这项更改，会有什么地方出问题？”——如果答案是“没有任何地方”，那么这项更改可能没有必要。

## 何时使用此技能

- **合并任何 PR 之前**——尤其是由自己编写且没有人工审查者的 PR
- **长时间编码之后**——疲劳会造成盲区；此技能可对此进行补偿
- **当 Claude 说“看起来不错”时**——如果你轻易获得了批准，请运行此技能以获取第二意见
- **处理安全敏感代码时**——身份验证、支付、数据访问、API 端点
- **当某些地方“感觉不对劲”时**——相信这种直觉，并进行一次对抗性审查
