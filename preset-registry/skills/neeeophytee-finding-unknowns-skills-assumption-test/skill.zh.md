# 假设测试

一个看似合理的假设可以经受住每次规划讨论，却仍可能一接触系统就失败。将具有决定性影响的不确定性转化为一个实验能够回答的问题。

## 步骤

1. 阅读请求、相关代码和现有证据。如果检查已经解决了这个问题，就引用该证据并停止；不要人为设计实验。如果仍有多个假设，选择其中失败后最可能改变方案的那个。
2. 将假设表述为可观察的预测。定义什么情况会证伪它、在测试范围内什么情况会支持它，以及什么情况会使结论无法确定。在观察结果之前先设定这些标准。
3. 设计最小化的区分性实验。使用隔离的 fixture 或测试环境，在可用时使用实际被质疑的组件，并将操作次数控制在有限范围内。说明该设置无法代表什么；mock 的行为不能作为其提供方的证据。
4. 在用户授权的范围内运行实验。保留命令、相关输入、实际输出，以及复现所需的环境详细信息。如果工具或依赖不可用，则将该实验报告为未运行或结论不确定，并说明缺失的前置条件。
5. 最后说明假设、方法、观察结果、结论（**在范围内得到支持**、**被证伪**或**结论不确定**），以及这项证据改变的规划决策。只有当下一项区分性检查可能改变该决策时，才建议进行该检查。将临时代码与生产实现分开。

## 约束

- 一次成功的试验不能证明普遍性结论。说明经过测试的条件和剩余的不确定性，尤其是并发性和性能方面的不确定性。
- 未经授权，不得使用生产写入、真实支付、破坏性操作或产生新的成本。实验不会授予额外权限。
- 区分是组件失败，还是实验未能运行。绝不要把缺少访问权限或损坏的 fixture 变成关于系统的结论。
- 除非用户要求，否则不要修复实现，也不要扩展为构建任务。交付物是能够为决策提供依据的证据。
