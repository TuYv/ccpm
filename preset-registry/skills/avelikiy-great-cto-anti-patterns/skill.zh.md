# 应拒绝的 SDLC 反模式

参考目录。在阻止某项提案时，请引用反模式的名称——这能为用户提供清晰的术语来讨论该问题。

## 架构反模式

### A-1. 上帝服务
**异味：** 一个服务同时负责身份验证、计费、搜索、文件存储和电子邮件。
**危害：** 单一部署单元、单点故障，每个团队都需要改动它，变更速度会随时间推移而下降。
**修复：** 按业务能力拆分（DDD 限界上下文）。

### A-2. 分布式单体
**异味：** 有 12 个微服务，但它们共享同一个数据库并一起部署。
**危害：** 承担了分布式系统的所有成本（延迟、最终一致性、运维开销），却没有获得任何收益（独立部署、隔离）。
**修复：** 要么真正分离（拥有各自的数据库和部署流水线），要么合并。

### A-3. 同步调用链
**异味：** 请求 → 服务 A → 服务 B → 服务 C → 服务 D。
**危害：** 故障概率叠加，p99 延迟累积。
**修复：** 使用事件进行异步处理，或将热路径放在一起。

### A-4. 过早优化
**异味：** 在获得第一个付费用户之前，就编写自定义 Redis Lua 脚本、手工调优二进制协议。
**危害：** 预先付出了复杂性成本，却永远无法收回。
**修复：** 从简单方案开始。获得负载数据后再优化。

### A-5. 简历驱动开发
**异味：** “让我们使用 Kubernetes / GraphQL / 事件溯源 / DDD”，但它们并不能解决当前的任何痛点。
**危害：** 优化的是工程师的简历，而不是用户的成果。
**修复：** 问一问：“能够奏效的最简单方案是什么？”

## 计划 / 流程反模式

### P-1. 大爆炸式重写
**异味：** “让我们用 <new framework> 重写它。”
**危害：** 80% 的重写都会失败。旧系统中沉淀了多年的缺陷修复。
**修复：** 绞杀者模式。新行为使用新代码实现，旧代码继续共存，在流量迁移后将其删除。

### P-2. 英雄文化
**异味：** “高级工程师 X 总是负责处理凌晨 3 点的事故。”
**危害：** 巴士因子为 1。X 会精疲力竭。知识无法传递。
**修复：** 操作手册、事后复盘、轮值待命、结对调试。

### P-3. 没有可逆性计划
**异味：** 计划发布的是一扇单向门（数据迁移、公共 API 变更、破坏契约的发布）。
**危害：** 如果出错，恢复需要数天甚至数周。
**修复：** 在批准前强制要求提供试运行和回滚路径。

### P-4. 计划没有时间盒
**异味：** 任务命名为“实现功能 X”，但没有结束标准。
**危害：** 范围开放，耗时会不断膨胀以填满可用时间。
**修复：** 每项任务 ≤ 4 小时，并明确规定“完成 = X”的标准。

## 代码级反模式

### C-1. 上帝类 / 上帝函数
**异味：** 一个超过 500 行的类或超过 100 行的函数，执行 5 件互不相关的事情。
**危害：** 测试会变成集成测试。差异内容的可读性会崩溃。
**修复：** 遵循单一职责。提取协作者。

### C-2. 字符串类型滥用
**异味：** 状态以字符串（“open”、“closed”、“blocked”）传递，且没有枚举。
**危害：** 拼写错误也能通过编译。新增状态会在 switch 中被遗漏。
**修复：** 枚举 / 可辨识联合 / 品牌类型。

### C-3. 捕获后继续执行
**异味：**
```js
try { doThing(); } catch (e) { console.log(e); }
```
**危害：** 隐藏缺陷。造成静默的数据损坏。
**修复：** 只捕获能够处理的异常；重新抛出其余异常；记录日志时附带上下文。

### C-4. 硬编码的密钥
**坏味道：** 源代码中包含 API 密钥、密码、数据库 URL。
**为何有害：** 会永久泄露在 git 历史记录中；轮换密钥需要强制推送（不可行）。
**修复方法：** 使用环境变量或密钥管理器。使用 pre-commit hook 搜索 `sk-`、`ghp_` 等内容。

## 事故 / 运维反模式

### O-1. 没有 SLO
**坏味道：** “生产环境今天似乎很慢”，但没有 SLO 目标。
**为何有害：** 无法判断是违反目标还是正常情况。
**修复方法：** 设定 p99 延迟、错误率和可用性 SLO。跟踪消耗速率。

### O-2. 告警泛滥
**坏味道：** 每个错误都会触发呼叫。工程师逐渐不再查看告警。
**为何有害：** 真正的事故会被淹没在噪声中。
**修复方法：** 仅在出现用户可感知的故障时触发呼叫。其他信号发送到仪表盘，而非寻呼系统。

### O-3. 事后复盘追责
**坏味道：** “工程师 X 未经测试就进行了部署。”
**为何有害：** 会让人们以后不愿开展事后复盘。追责无法修复系统。
**修复方法：** 开展无责事后复盘。关注缺失的防护机制，而非个人。

### O-4. 雪花服务器
**坏味道：** “不要重启 SRV-PROD-3，它有未纳入 IaC 的特殊配置。”
**为何有害：** 无法进行灾难恢复。
**修复方法：** 一切都应纳入 IaC。服务器应该是牲畜，而不是宠物。

## 如何使用此目录

在提案/评审中发现其中某种反模式时：

1. 引用编号（A-3、P-1 等），为用户提供统一的术语
2. 引用提案中具体的坏味道
3. 提出具体的修复方法
4. 如果用户不同意，则将其记录为 ADR，并填写备选方案部分

## 不应适用的情况

- 业余项目、学习练习——反模式针对的是规模化场景
- 带有明确 `// TODO delete in 2 weeks` 的一次性代码
- 目标是“这个 API 到底能不能用”的限时 POC
