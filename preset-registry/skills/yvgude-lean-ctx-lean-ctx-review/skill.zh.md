# lean-ctx 会话审查

上游仓库：`yvgude/lean-ctx`（https://github.com/yvgude/lean-ctx）。

读取 Claude Code 的会话转录文件，因此适用于会写入 `~/.claude/projects/*/*.jsonl` 的代理。其他运行框架需要各自的提取器；下文的分诊规则与具体框架无关。

## 1. 提取

在本技能所在目录下运行（需要 `python3`）：

```bash
python3 scripts/scan_session.py
```

默认使用 `~/.claude/projects/*/` 下最新的转录文件——即当前活跃的 Claude Code 会话。传入一个路径即可审查其他会话。`-d N` 会完整转储第 `#N` 次调用。

该脚本报告的是**事实，而非结论**：按顺序列出每一次 `ctx_*` 调用、哪些结果被运行框架标记了 `is_error`、哪些调用重复了完全相同的参数、哪些请求了 `raw`/`fresh` 输出，以及发生了多少次原生 `Read`/`Grep`/`Bash` 调用。它有意不去猜测其中哪些是问题——那个判断由你在下文做出。

转录文件可达数兆字节，所以请读表格，不要读原始 JSONL。

## 2. 分诊

**从 `is_error` 入手。** 实际上每一次真正的工具失败都带有该标记。然后阅读调用列表，寻找较弱的信号：完全相同的重试、`raw`/`fresh` 重新读取、紧随 `ctx_*` 调用之后成串出现的原生调用，或者一段只有在放弃 `ctx_*` 之后才得以完成的调用序列。

### 在为任何问题开脱之前，先做这两件事

跳过它们，正是这项审查返回虚假的“无可报告”结果的原因。二者各只需一条命令。

**为你即将开脱的防护或工具搜索一下 issue 跟踪器。** 在分诊阶段就做这件事，而不是等到第 4 步。已关闭的 issue 界定了预期行为：如果某个已发布的修复声称支持某种形式，而你刚刚亲眼看到它失败，那就是一次回归，也是这类审查最有价值的发现之一。这还能防止你把一个已有定论的设计决策重新提交一遍。

```bash
gh issue list --repo yvgude/lean-ctx --search "<guard or tool keyword>" --state all
```

**检验其陈述的理由——绝不接受消息的自我描述。** 错误消息会解释自身，而这番解释可能是错的。三项检查，各只需一条命令：

- *被认可的替代方案能否达到同样的效果？* 如果这个拦截可以通过消息本身推荐的路径绕过，那么它约束的是语法，而非能力。有时这是有意为之（在 shell 字符串无法可靠解析之处，结构化输入可以可靠解析）——请自行判断属于哪种情况，不要想当然。
- *陈述的原因与观察到的规则一致吗？* 一次只改变一个维度。一个防护把问题归咎于负载大小，实际却以路径为判断依据；或把问题归咎于管道，而针对的命令本身就是通过管道传递的——这就是在自我误诊。
- *消息是否自相矛盾？* 一条拒绝消息同时还声称被拒绝的形式是允许的，这本身就是一项发现，无论该策略最终应当如何裁定。

错误的诊断是一个真实的 bug，即使拦截本身是正确的：它会把下一个调用者引上一条行不通的路。

### 不构成发现

- **返回内容中的字眼。** 文件中包含 `http.StatusConflict`、`git rebase` 打印出 `CONFLICT (content):`、`gh` 返回 `"mergeable":"CONFLICTING"`、测试运行打印出 `not found`。工具返回的正是所请求的内容。评判工具自身的行为，永远不要评判负载的用词。
- **自我引用。** 任何引用了先前扫描、本技能或某份转录文件的结果，都会回显其中的每一个错误字眼。
- **防护性拦截——仅在其经受住上述检验之后。** 内联环境变量覆盖（`GIT_EDITOR=`）、shell 重定向（`>`/`>>`）、不在白名单内的命令、项目根目录之外的路径。“它提供了替代方案，而且替代方案有效”*不足以*为其开脱：一个理由错误的、规则与描述不符的、或自相矛盾的防护同样满足这一条件。只有当其陈述的理由站得住脚时，才能判定它没有问题。
- **格式错误的工具输入。** `__unparsedToolInput` 上的 `InputValidationError` 是调用方自身的 JSON 序列化问题——通常是字符串中含有原始制表符或换行符——在 lean-ctx 尚未运行之前就被拒绝了。
- **我自己传错的参数**、确实缺失的文件、失败的构建。

### 可确认的发现

工具在*输入正确的前提下*做了错误或无益的事：

- 输出错误、有损或被截断，而该模式承诺的并非如此
- 内容被注入到文档声明为逐字（verbatim）的输出中，或任何破坏已文档化输出格式的行为（例如破坏批量读取的分隔符）
- 崩溃、挂起，或与已文档化参数不符的 schema 错配
- 已文档化的模式行为与描述不符
- 只有在退回到原生工具后才获得成功的重试
- **错误或自相矛盾的诊断**，即使拦截本身是对的——指错原因会把下一个调用者引上一条行不通的路，其代价超过拦截本身
- **相对某个已关闭 issue 的回归**：已发布的修复声称支持该形式，而实际并不支持

## 3. 复现

**没有最小复现，就没有 issue。** 重新运行完全相同的工具和参数。如果这次通过了，尝试隔离触发条件；如果做不到，就不要提交——改为向用户报告这一观察结果，直白地说明它未能复现以及你尝试过什么。对内部机制的猜测比沉默更糟。

用 `lean-ctx --version` 获取版本号。

零个已确认的发现是有效且常见的结果。如实说明即可，不要提交任何 issue。

## 4. 提交 issue

仅针对已确认的发现提交，每个独立问题一个 issue。你在分诊阶段已经搜索过跟踪器；如果发现的问题有所偏移，在这里扩大搜索范围：

```bash
gh issue list --repo yvgude/lean-ctx --search "<keywords>" --state all
```

如果已被报告过则跳过——重新提交前先读一读关闭说明，因为一个已关闭的 issue 可能已经认可了你正要提出的观点。当某项发现与某个已关闭的修复相矛盾时，引用该 issue，并把新 issue 表述为那个修复中的缺口。否则：

```bash
gh issue create --repo yvgude/lean-ctx --title "..." --body-file <file>
```

正文包括：发生了什么、预期结果、最小复现（确切的工具 + 参数）、版本、操作系统。不要对内部机制进行猜测。每个 issue 正文的末尾都要附上 Claude Code 署名页脚。把该 issue 的 `html_url` 报告给用户。
