# 系统化调试

## 概述

随机修复既浪费时间，又会制造新的错误。快速补丁会掩盖根本问题。

**核心原则：** 在尝试任何修复之前，必须先调查根本原因。只修复症状意味着流程失效。

**违反此流程的具体规定，就是违背调试的根本精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

在完成阶段 1 之前，不得提出修复方案。

## 适用场景

系统化调试适用于任何技术问题：
- 测试失败
- 生产环境中的错误
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**在以下情况下尤其有价值：**
- 时间压力让人忍不住猜测
- “快速修复”似乎显而易见
- 已经尝试过多种修复方案
- 之前的修复失败了
- 尚未完全理解问题

**即使在以下情况下，也不应跳过此流程：**
- 问题看起来很简单（简单的错误也有根本原因）
- 时间紧迫（系统化方法比盲目折腾更快）
- 情况紧急（调查比返工更快）

## 四个阶段

必须先完成每个阶段，才能进入下一阶段。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 错误消息和警告通常包含解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径和错误代码

2. **稳定复现**
   - 确定问题是否能稳定触发
   - 明确具体步骤
   - 确认可复现性
   - 如果无法复现，应收集更多数据，而不是猜测

3. **检查近期变更**
   - Git diff 和近期提交
   - 新增依赖项、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **对于包含多个组件的系统（CI -> 构建 -> 签名，API -> 服务 -> 数据库）：**

   在提出修复方案之前，应添加诊断检测：
   ```
   对于每个组件边界：
     - 记录哪些数据进入组件
     - 记录哪些数据离开组件
     - 验证环境/配置的传递
     - 检查每一层的状态

   运行一次以收集能够表明故障发生位置的证据
   然后分析证据以确定发生故障的组件
   然后调查该特定组件
   ```

   **多层系统示例：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   这会揭示哪一层发生了故障。

5. **跟踪数据流**

   **当错误位于调用堆栈深处时：**

   有关完整的反向跟踪技术，请参阅 `./references/root-cause-tracing.md`。

**快速方法：**
   - 确定错误值的来源
   - 确定是什么使用错误值调用了此处
   - 继续向上追踪，直到找到源头
   - 从源头修复，而不是修复症状

### 阶段 2：模式分析

**在进行任何修复之前，应先识别模式：**

1. **查找正常工作的示例**
   - 在同一代码库中找到类似且正常工作的代码
   - 找出与故障代码相似的正常工作代码

2. **与参考实现比较**
   - 如果要实现某种模式，请完整阅读参考实现
   - 阅读每一行，不要略读
   - 在应用之前充分理解该模式

3. **识别差异**
   - 列出正常代码与故障代码之间的每一处差异
   - 不要认为细微差异无关紧要

4. **了解依赖项**
   - 此操作所需的其他组件
   - 所需的设置、配置和环境
   - 该模式所基于的假设

### 阶段 3：提出假设并测试

**应用科学方法：**

1. **提出单一假设**
   - 清晰表述：“X 是根本原因，因为 Y”
   - 要具体，不要含糊

2. **进行最小化测试**
   - 进行尽可能小的改动来验证假设
   - 每次只改变一个变量
   - 不要同时修复多个问题

3. **验证后再继续**
   - 如果假设得到证实：进入阶段 4
   - 如果未得到证实：提出新的假设
   - 不要在现有改动之上叠加更多修复

4. **缺乏理解时**
   - 承认自己尚未理解
   - 寻求帮助
   - 进一步研究

### 阶段 4：实施

**修复根本原因，而不是症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现方式
   - 如果可能，使用自动化测试
   - 如果没有测试框架，则使用一次性测试脚本
   - 必须先有测试，再进行修复

2. **实施单一修复**
   - 解决已确定的根本原因
   - 每次只做一项改动
   - 不要做“既然都到这里了”式的改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 是否没有破坏其他测试？
   - 问题是否真正得到解决？

4. **如果修复不起作用**
   - 停止
   - 统计已尝试的修复次数
   - 如果 < 3：返回阶段 1，根据新信息重新分析
   - 如果 >= 3：质疑架构

5. **在 3 次以上修复失败后质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都会在不同位置暴露新的共享状态、耦合或问题
   - 修复需要“大规模重构”
   - 每次修复都会在其他地方产生新的症状

   **停下来质疑根本设计：**
   - 该模式从根本上是否合理？
   - 是否只因惯性而继续采用这种方法？
   - 应该重构架构，还是继续修复症状？

   **在尝试更多修复之前，与人类协作伙伴讨论**

   这并不是假设失败，而是架构错误。

## 复杂错误与规划

**对于复杂错误，任何代码改动之前都必须先进行规划：**

### 错误何时属于复杂错误

当满足以下任一条件时，必须先执行 EnterPlanMode，再进行改动：

- **涉及多个组件** - 问题跨越多个文件、模块或子系统
- **涉及架构影响** - 修复可能影响系统设计、契约或接口
- **存在多种潜在方案** - 存在多条有效的实施路径
- **存在副作用风险** - 改动可能影响不相关的功能
- **需要重构** - 修复需要进行超出最小补丁范围的结构性改动
- **尚未完全理解** - 完成阶段 1 的调查后，根本原因仍不明确

### 规划流程

1. **完成第 1 阶段（根因调查）**
   - 在制定计划之前，必须弄清楚哪里出了问题以及为什么会出问题
   - 首先收集所有证据

2. **使用 EnterPlanMode**
   - 这向用户表明你需要在继续之前获得批准
   - 允许用户在实施前审查方案

3. **编写实施计划，涵盖：**
   - 根因摘要（来自第 1 阶段）
   - 拟议的修复策略
   - 将要修改的文件
   - 将要创建/修改的测试
   - 潜在风险及缓解措施
   - 考虑过的替代方案

4. **等待用户批准**
   - 用户可能会建议不同的方案
   - 用户可能会提供额外的上下文
   - 用户可能会按原方案批准

### 为什么复杂 Bug 需要规划

- 避免因错误的架构选择而导致代价高昂的返工
- 确保与用户的偏好和约束保持一致
- 尽早发现被忽略的依赖关系
- 在执行前明确展示拟议的变更

**对于简单 Bug：** 无需规划，直接继续执行第 2-4 阶段。

## 危险信号

以下思维模式表明违反了流程，需要返回第 1 阶段：
- “先快速修复，以后再调查”
- “先试着改一下 X，看看是否有效”
- “添加多项更改，然后运行测试”
- “跳过测试，我会手动验证”
- “可能是 X，让我修一下”
- “我并未完全理解，但这样也许能行”
- “该模式要求 X，但我会以不同方式调整它”
- 在追踪数据流之前就提出解决方案
- **“再尝试修复一次”（已经尝试 2 次以上时）**
- **每次修复都会在不同位置暴露新问题**

**如果修复失败 3 次以上：** 应质疑架构。

## 人类合作伙伴发出的信号

**留意以下纠正方向的表述：**
- “不是这样吗？”——表明存在未经验证的假设
- “它会向我们显示……吗？”——表明缺少证据收集
- “别再猜了”——表明在尚未理解问题时就提出修复方案
- “深入思考一下”——表明需要质疑根本原理，而不仅是处理症状
- “我们是不是卡住了？”（感到沮丧）——表明当前方法行不通

**遇到这些信号时：** 返回第 1 阶段。

## 常见的自我辩解

| 借口 | 事实 |
|--------|---------|
| “问题很简单，不需要走流程” | 简单问题也有根因。对于简单 Bug，该流程执行起来很快。 |
| “情况紧急，没时间走流程” | 系统化调试比反复猜测和试错更快。 |
| “先试试这个，然后再调查” | 第一次修复会定下后续模式。从一开始就用正确的方法。 |
| “确认修复有效后我再写测试” | 未经测试的修复无法长久维持。先写测试才能证明修复有效。 |
| “一次进行多项修复可以节省时间” | 这样无法区分是哪项修复起了作用，还会引发新的 Bug。 |
| “参考内容太长了，我会调整一下这个模式” | 一知半解必然会导致 Bug。完整阅读它。 |
| “我看出问题了，让我修一下” | 看到症状 != 理解根因。 |
| “再尝试修复一次”（已失败 2 次以上） | 失败 3 次以上 = 架构问题。应质疑现有模式，而不是再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误信息、复现问题、检查变更、收集证据 | 理解问题是什么以及为什么发生 |
| **2. 模式** | 查找正常工作的示例并进行比较 | 找出差异 |
| **3. 假设** | 形成理论，以最小范围进行验证 | 假设得到确认或形成新假设 |
| **4. 实施** | 创建测试、修复问题、验证结果 | 缺陷已解决，测试通过 |

## 当流程未能揭示根本原因时

如果系统性调查表明问题与环境有关、依赖于时序或源于外部因素：

1. 确认流程已完整执行
2. 记录已调查的内容
3. 实施适当的处理措施（重试、超时、错误消息）
4. 添加监控/日志，以便后续调查

**注意：** 95% 的“没有根本原因”案例实际上是调查不完整。

## 辅助技术

以下技术是系统化调试的一部分：

- **`./references/root-cause-tracing.md`** - 沿调用栈反向追踪缺陷，找出最初的触发因素
- **`./references/defense-in-depth.md`** - 找到根本原因后，在多个层级添加验证
- **`./references/condition-based-waiting.md`** - 使用条件轮询替代任意设置的超时
- **`./references/condition-based-waiting-example.ts`** - 基于条件等待的实现示例
- **`./find-polluter.sh`** - 对测试套件进行二分查找，确定哪个测试污染了共享状态

**相关技能：**
- **superpowers:behavior-driven-development** - BDD 原则，包括用于测试设计的 Gherkin 场景

## 实际影响

根据调试会话的结果：
- 系统化方法：15-30 分钟完成修复
- 随机修复方法：2-3 小时反复折腾
- 首次修复成功率：95%，相比之下为 40%
- 引入的新缺陷：几乎为零，相比之下则很常见
