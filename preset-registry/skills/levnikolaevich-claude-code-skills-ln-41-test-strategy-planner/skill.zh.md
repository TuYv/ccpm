# 测试策略规划器

**目标：** 针对所请求的范围，制定一项只读、基于风险的测试组合决策。在防止测试数量增长却无法提供独特缺陷信号的同时，最大限度地增强对重要局部行为的信心，并明确如何保留、变更、整合、淘汰或有意省略受影响的证据。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。依次完成每一项，并且仅当其操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的裁定、决策和批准规则应用于每个未完成项目，并在回复开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个未完成项目。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 需求和仓库规则 | 原生文件读取工具及 Git | 确定范围、当前工作、验收标准和支持的命令 | 用户提供的需求，并明确说明限制 |
| 现有测试范围 | 文件列表、搜索、清单、运行器配置和 CI | 梳理测试层级、夹具、环境和约定 | 仓库目录树和已知测试入口点 |
| 行为和边界 | 语言服务器或宿主环境原生代码智能工具 | 跟踪入口点、使用方、信任边界、持久化、队列和外部契约 | 小范围搜索后直接检查 |
| 现有证据 | 仓库定义的安全测试和覆盖率命令 | 确定哪些行为已被证明，以及哪些方面的信心较弱 | 检查测试和 CI；将执行标记为不可用 |
| 当前外部故障模式 | 官方文档、规范、公告和一手现场证据 | 外部契约或真实用户故障可能改变场景或优先级 | 将相关声明标记为 `UNVERIFIED`；不得虚构风险 |

整个过程须保持只读。不得创建测试、夹具、快照、任务或文档，也不得更新所审查的实现。

## 证据规则

- 对于重大的业务风险，优先选择通过用户可观察边界提供的确定性端到端证据。仅当存在独特的边界或确定性理由时，才选择契约或集成证据；仅当更广泛的证明不够精确或实用时，才针对重大的、孤立的局部规则选择单元证据。
- 覆盖率是发现问题的证据，而非证明。必须有一个能够在指定缺陷出现时失败的判定依据。
- 根据影响、合理的故障可能性、独特性、可检测性和恢复成本确定优先级；不得将这些判断转换为通用数值阈值。
- 只有当现有测试的设置和断言证明了相同的行为和故障模式时，它们才能缩小缺口。
- 框架、语言、ORM、序列化器或库的行为不属于产品测试，除非本地配置或集成改变了其契约。
- 将测试组合操作与执行状态分开。使用 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或 `NO_TEST` 表示决策，仅使用 `PASS`、`FAIL`、`BLOCKED` 或 `UNPROVEN` 表示证据状态。
- `NO_TEST` 是明确的风险决策，而非未完成的工作。应说明现有证明、替代控制措施或已接受的残余风险。
- 持久化测试登记表是可选的。除非规模或治理要求维护额外的工件，否则优先使用仓库原生的测试名称、路径、标签、CI 配置和任务输出。
- 只有当外部研究为此计划增加了具体的故障模式、边界或判定依据时，它才具有可操作性。

## 检查清单

### 1. 明确范围和证据

- [ ] 明确功能、需求、验收标准、参与者、显式非目标，以及需要保护的人员或系统结果；将请求采用的机制与其必须实现的结果分开；如果没有可供规划的具体行为，则返回 `BLOCKED`。
- [ ] 阅读适用的仓库说明并检查 Git 状态，以免将当前工作和无关变更误认为已确立的行为。
- [ ] 识别语言、框架、运行器、测试目录、固件、工厂、环境、CI 门禁、覆盖率、契约测试和手动测试界面。
- [ ] 将现有证据以及受请求行为影响的每项测试映射到各项需求；根据实际判定依据，而不是测试名称或接近程度，将证明标记为 `PROVED`、`PARTIAL`、`MISSING` 或 `UNAVAILABLE`。
- [ ] 当手动、探索性、事故和生产环境证据能够揭示自动化测试套件未覆盖的行为时，对其进行检查。
- [ ] 在提出场景之前，识别环境、数据、凭据、服务、设备、浏览器和破坏性状态约束。
- [ ] 记录可能改变测试层级、优先级或可行性的假设和未知项；仅当不同解释会实质性改变策略时，才提出一个简洁的问题。

### 2. 构建风险图谱

- [ ] 跟踪关键流程，从参与者触发操作开始，经过入口点、运行时接线和状态变更，直至持久化或用户可见的结果。
- [ ] 识别涉及资金、身份验证、授权、所有权、数据完整性、破坏性操作、迁移、公共契约或不可逆工作流，且在本地具有独特重要性的行为。
- [ ] 列举合理的缺陷类别：错误成功、拒绝有效输入、接受无效输入、边界错误、部分失败、重复交付、顺序、超时、重试、取消、竞态、回滚、恢复和兼容性漂移；说明会丧失哪些受保护的结果，或会造成哪些具体损害。
- [ ] 将产品风险与实现细节以及依赖项已保证的行为区分开来；排除那些虽可在技术上表示、但并不保护任何独特本地结果或决策的状态。
- [ ] 识别涉及隐私或受监管的测试数据，并要求使用合成的、最小化的或经过明确批准的固件。
- [ ] 仅当对版本敏感的契约、反复出现的用户故障、滥用模式或互操作性风险可能改变风险图谱时，才使用当前外部证据。
- [ ] 对风险进行定性排序，并解释并列情况或不确定性；不要在缺少频率或影响数据时虚构精确度。

### 3. 确定测试组合操作、层级和判定依据

- [ ] 为每项重大风险和受影响的测试恰好分配一个临时操作：当可信且独特的证明仍然有效时使用 `KEEP`；对于尚未证明的重大风险使用 `ADD`；当有价值的意图仍然存在，但基础、边界、设置或判定依据已发生变化时使用 `UPDATE`；对于可安全合并的证明使用 `MERGE`；对于已过时、重复、琐碎或不可信的证明使用 `DELETE`；当其他控制措施或已接受的风险足够时使用 `NO_TEST`。
- [ ] 对于 `DELETE` 或 `MERGE`，证明测试基础已经过时，或明确指出可保留所有仍然需要的重大行为、失败模式、判定依据和有效故障定位能力的替代证据；绝不要仅仅因为已有过时证明就予以保留。
- [ ] 对隔离的本地规则选择单元测试，对生产者与消费者之间的一致性选择契约测试，对自有边界选择集成测试，对无法在更低层级证明最终结果且具有生产环境形态的用户旅程选择端到端测试。
- [ ] 避免在每个层级重复测试相同行为，除非每个层级都能检测不同的缺陷类别。
- [ ] 为每个场景定义一个独立的判定依据：返回的契约、持久化状态、发出的事件、渲染行为、外部效果、不变量或确定性产物。
- [ ] 检查模拟对象和伪实现是否绕过了场景声称要证明的边界或失败语义。
- [ ] 对于 UI 或交互场景，要求使用稳定的、由仓库拥有的 ID 或专用测试钩子作为定位器；仅当可见或翻译后的文案、样式、布局、位置和附带结构属于显式契约时，才可以对其进行断言，绝不能用它们进行元素查找。
- [ ] 仅在风险图谱表明相关风险重大时，才纳入正向、无效输入、边界、授权、错误、恢复、并发和兼容性用例。
- [ ] 当默认值可能掩盖硬编码行为时，明确指定非默认配置、时间、区域设置、随机性、顺序或数据规模。
- [ ] 仅当受支持的契约或已知风险使其与决策相关时，才添加浏览器、设备、操作系统、运行时或版本组合单元。
- [ ] 优先采用确定性设置和有界数据；明确哪些场景需要真实依赖项、模拟器、一次性环境或类生产环境拓扑。
- [ ] 为每项测试组合操作定义仓库门禁或诊断角色、进入前提条件以及基于证据的完成标准；不要使用测试数量或原始覆盖率作为完成标准。

### 4. 生成按优先级排序的测试矩阵

- [ ] 对于每项决策，说明测试依据、受保护的结果、风险、现有证据或受影响的测试、测试组合操作、层级、设置、判定标准、预期证据、环境、门禁，以及已知时的结果状态。
- [ ] 对于其价值取决于契约、迁移、兼容性窗口、变通方案、事故、依赖项或临时风险的证据，定义评审或退役触发条件；不要在没有明确责任归属理由的情况下虚构日期。
- [ ] 对场景进行排序，使安全关键型和高信息量检查先于成本高昂的广度覆盖执行，同时保留前置条件和状态依赖关系。
- [ ] 确定哪些场景可以并行运行，哪些场景共享可变状态、速率限制、账户、设备或环境设置。
- [ ] 将发布门禁场景与较慢的诊断性或探索性覆盖分开，以免该计划使常规交付变得不切实际。
- [ ] 明确说明排除项，包括没有独特受保护结果或缺陷信号的场景、低价值重复测试、框架行为、不可行的环境以及已接受的残余风险。
- [ ] 当策略可执行且决策完整时使用 `READY`；当可以进行有用的部分规划但缺少重要证据时使用 `INCONCLUSIVE`；当无法确定需求或安全关键边界时使用 `BLOCKED`。
- [ ] 返回结论、风险图、决策台账、测试组合净影响、环境需求、排除项、局限性和残余风险。
- [ ] 对每个 `INCONCLUSIVE` 或 `BLOCKED` 区域，说明获取下一项证据所需的最小操作。

## 输出契约

```markdown
# Test Strategy

**Verdict:** READY | INCONCLUSIVE | BLOCKED

## Scope and existing evidence
- Requirements, actors, and outcomes
- Existing suites, commands, and environments
- Assumptions and unavailable evidence

## Risk map
| Protected outcome | Behavior | Failure or defect class | Impact | Existing proof | Priority rationale |
|---|---|---|---|---|---|
| ... | ... | ... | ... | PROVED / PARTIAL / MISSING / UNAVAILABLE | ... |

## Portfolio decisions and prioritized scenarios
| Priority | Test basis and protected risk | Existing evidence or affected test | Action | Level, scenario, and environment | Oracle, gate, and result | Review or retirement trigger |
|---:|---|---|---|---|---|---|
| ... | ... | path / command / NONE | KEEP / ADD / UPDATE / MERGE / DELETE / NO_TEST | unit / contract / integration / E2E / manual | independent evidence; required / diagnostic; PASS / FAIL / BLOCKED / UNPROVEN | change that requires reconsideration |

## Portfolio effect
Tests added, updated, merged, and deleted; explain every `NO_TEST` decision and whether the maintained portfolio grows, shrinks, or stays neutral.

## Next evidence-gathering actions
Exact repository, environment, contract, or user decision needed for each `INCONCLUSIVE` or `BLOCKED` area.

## Exclusions and residual risks
Low-value duplication, unavailable environments, accepted gaps, and evidence still required.
```
