# 测试策略规划器

**目标：** 针对请求的范围设计一份只读、基于风险的测试组合决策。在防止测试增长却无法提供独特缺陷信号的同时，最大限度地提高对重要局部行为的信心，并明确受影响的证据应如何保留、变更、合并、退役或有意省略。

**执行契约：** 有序复选框即为完成定义。将每项在内部跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有证明条件不存在的证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；读取、委派或工具失败都不能作为证明。每完成一个部分后重新核对各项。返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将该技能的裁决和批准规则应用于每个缺口。
保留用户意图、范围和现有授权。继续执行已授权的工作；仅针对影响重大的未解决选择或所需的外部批准提出询问。根据实质风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；在此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 需求和仓库规则 | 原生文件读取工具加 Git | 确定范围、当前工作、验收标准和受支持的命令 | 在用户提供明确限制的需求时，使用用户提供的需求 |
| 现有测试范围 | 文件列表、搜索、清单、运行器配置和 CI | 梳理测试层级、fixture、环境和约定 | 仓库树和已知的测试入口 |
| 行为和边界 | 语言服务器或宿主原生代码智能工具 | 跟踪入口点、消费者、信任边界、持久化、队列和外部契约 | 先进行范围狭窄的搜索，再直接检查 |
| 现有证据 | 现有测试/CI 报告、测试读取结果和安全的仓库命令 | 当前证明中的重大不确定性可能改变策略时 | 在执行受限的情况下使用静态证据；不要仅为生成计划而运行测试套件 |
| 当前外部故障模式 | 官方文档、规范、公告和一手现场证据 | 外部契约或真实用户故障可能改变场景或优先级时 | 将该声明标记为 `UNVERIFIED`；不要臆造风险 |

保持运行只读。不要创建测试、fixture、快照、任务或文档，也不要更新被审查的实现。

## 证据规则

- 选择能够证明每项重大风险的最小可靠边界。当无法在更低层级建立端到端旅程时，使用端到端证据；当单元、集成和契约证据能够发现不同故障时，分别保留这些证据。
- 覆盖率是发现证据，而非证明。必须有一个能够因指定缺陷而失败的判定依据。
- 根据影响、合理的故障可能性、独特性、可检测性和恢复成本进行排序；不要将这些判断转换为通用的数值阈值。
- 只有当现有测试的设置和断言证明了相同的行为及故障模式时，它们才会缩小缺口。
- 框架、语言、ORM、序列化器或库的行为不属于产品测试，除非本地配置或集成改变了其契约。
- 将测试组合动作与执行状态分开。使用 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或 `NO_TEST` 表示决策，仅使用 `PASS`、`FAIL`、`BLOCKED` 或 `UNPROVEN` 表示证据状态。
- `NO_TEST` 是明确的风险决策，而不是遗漏的工作。应说明现有证明、替代控制措施或已接受的残余风险。
- 持久化的测试登记表是可选的。除非规模或治理要求维护另一份工件，否则优先使用仓库原生的测试名称、路径、标签、CI 配置和任务输出。
- 外部研究只有在为本计划增加具体故障模式、边界或判定依据时才具有可操作性。

## 清单

### 1. 确立范围和证据

- [ ] 明确功能、需求、验收标准、参与者、显式非目标，以及受保护的人类或系统结果；将请求的机制与其必须促成的结果分离；如果没有可规划的具体行为，则返回 `BLOCKED`。
- [ ] 阅读适用的仓库说明并检查 Git 状态，避免将当前工作和无关变更误认为既有行为。
- [ ] 识别语言、框架、运行器、测试目录、夹具、工厂、环境、CI 门禁、覆盖率、契约测试和手动测试面。
- [ ] 将现有证据以及受请求行为影响的每个测试映射到各项需求；基于实际判定依据记录覆盖情况为完整、部分、缺失或不可用，并附带 Evidence Rules 中定义的执行状态；名称和位置接近不能作为证明。
- [ ] 在手动、探索性、事故和生产证据揭示自动化套件未覆盖的行为时，对其进行检查。
- [ ] 在提出场景之前，识别环境、数据、凭据、服务、设备、浏览器和破坏性状态约束。
- [ ] 记录可能改变测试层级、优先级或可行性的假设和未知项；只有当不同解释会实质性改变策略时，才提出一个简洁问题。

### 2. 构建风险图谱

- [ ] 从参与者触发点开始，沿入口点、运行时接线、状态变更，到持久化或用户可见结果，追踪关键流程。
- [ ] 识别涉及资金、身份认证、授权、所有权、数据完整性、破坏性操作、迁移、公共契约或不可逆工作流的独特重要本地行为。
- [ ] 枚举合理的缺陷类别：错误成功、拒绝有效输入、接受无效输入、边界错误、部分失败、重复交付、顺序、超时、重试、取消、竞态、回滚、恢复和兼容性漂移；说明会丢失哪项受保护结果，或会造成什么具体损害。
- [ ] 将产品风险与实现细节以及已由依赖项保证的行为分开；排除虽在技术上可表示但不保护任何独特本地结果或决策的状态。
- [ ] 识别隐私敏感或受监管的测试数据，并要求使用合成、最小化或明确批准的夹具。
- [ ] 仅当版本敏感契约、反复出现的用户失败、滥用模式或互操作风险可能改变风险图谱时，才使用当前外部证据。
- [ ] 对风险进行定性排序，并解释并列或不确定性；不要根据缺失的频率或影响数据制造精确性。

### 3. 决定组合操作、层级和判定依据

- [ ] 为每个实质性风险和受影响测试恰好分配一个临时操作：当可信的唯一证明仍然有效时为 `KEEP`；对于未被证明的实质性风险为 `ADD`；当有价值的意图仍然存在但基础、边界、设置或判定依据发生变化时为 `UPDATE`；对于可安全合并的证明为 `MERGE`；对于过时、重复、琐碎或不可信的证明为 `DELETE`；当另一项控制或已接受风险足够时为 `NO_TEST`。
- [ ] 对于 `DELETE` 或 `MERGE`，证明测试基础已过时，或识别能保留每个仍然需要的实质性行为、失败模式、判定依据和有用失败定位的替代证据；不要仅仅因为证明已经存在就保留过时证明。
- [ ] 为隔离的本地规则选择单元测试，为生产者-消费者协议选择契约测试，为自有边界选择集成测试，为无法在更低层级证明终端结果的生产形态旅程选择端到端测试。
- [ ] 避免在每个层级重复测试同一行为，除非每个层级能检测出不同的失败类别。
- [ ] 定义最小充分的独立判定依据，并在契约要求时组合多种观察：返回契约、持久化状态、发出的事件、渲染行为、外部效果、不变量或确定性产物。
- [ ] 检查 mock 和 fake 是否绕过了场景声称要证明的边界或失败语义。
- [ ] 根据可观察契约和区域设置策略，使用稳定的项目原生语义定位器（角色、可访问名称、标签）或显式 ID/test hook。避免使用样式、位置、时序和偶然结构。当文案是需求时，单独处理精确文案断言；当存在稳健的语义定位器时，不要仅为添加 hook 而要求产品变更。
- [ ] 仅在风险图谱表明其具有实质性时，才包括正向、无效、边界、授权、错误、恢复、并发和兼容性用例。
- [ ] 当默认值可能掩盖硬编码行为时，指定非默认配置、时间、区域设置、随机性、顺序或数据规模。
- [ ] 仅当受支持契约或已知风险使其与决策相关时，才添加浏览器、设备、操作系统、运行时或版本单元。
- [ ] 优先使用确定性设置和有界数据；识别何处需要真实依赖、模拟器、一次性环境或类生产拓扑。
- [ ] 为每个组合操作定义仓库门禁或诊断角色、入口前置条件，以及基于证据的完成标准；不要使用测试数量或原始覆盖率作为完成标准。

### 4. 生成按优先级排序的测试矩阵

- [ ] 针对每项决策，说明测试依据、受保护的结果、风险、现有证据或受影响的测试、测试组合行动、级别、设置、判定依据、预期证据、环境、门禁，以及已知的结果状态。
- [ ] 为价值依赖于合同、迁移、兼容性窗口、权宜方案、事件、依赖项或临时风险的证据定义审查或退役触发条件；除非存在明确的责任归属理由，否则不要凭空设定日期。
- [ ] 对场景排序时，应让安全关键型和高信息量检查先于昂贵的广泛测试运行，同时保留前置条件和状态依赖关系。
- [ ] 识别哪些场景可并行运行，以及哪些场景共享可变状态、速率限制、账户、设备或环境设置。
- [ ] 按失败后果和所需检测时间对门禁进行分类；仅当另一项控制措施覆盖发布关键风险时，才将缓慢的诊断检查置于常规门禁之外。
- [ ] 明确说明排除项，包括没有独特受保护结果或缺陷信号的场景、低价值重复项、框架行为、不可行环境和已接受的残余风险。
- [ ] 当策略可执行且决策完整时使用 `READY`；当可进行有用的部分规划但缺少实质性证据时使用 `INCONCLUSIVE`；当无法确定需求或安全关键边界时使用 `BLOCKED`。
- [ ] 核对风险图与决策台账：不得有任何实质性风险或受影响测试缺少行动及其支持理由。
- [ ] 针对每个 `INCONCLUSIVE` 或 `BLOCKED` 区域，说明最小的下一步证据收集行动。

## 自检

- [ ] **返回前进行核对。** 检查逐项证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或已授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实仅陈述一次。简短结果可每个字段使用一行；省略空表格，且不要复制已链接的产物：

1. **结果：** 特定于 Skill 的结论和有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和实质性假设。
3. **证据：** 以下特定于 Skill 的字段；区分事实、推断和未经验证的主张。链接产物；必要时使用表格。
4. **验证：** 检查/结果、不可获得的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项目的原因、对结果的影响和确切的下一步行动；残余风险和所需决策。

**特定于 Skill 的证据：** 受保护的结果 → 缺陷类别 → 影响 → 现有证明 → 优先级。针对每个受影响的测试或缺口：测试组合行动、级别/场景/环境、独立判定依据、必需/诊断性门禁及结果，以及审查/退役触发条件。报告测试组合的净影响和合理的 `NO_TEST`、排除的低价值重复项、环境需求，以及针对结论不确定区域的确切证据行动。
