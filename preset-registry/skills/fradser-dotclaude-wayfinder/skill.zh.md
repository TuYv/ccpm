一个尚不成熟的想法出现了——它过于庞大，无法在一次智能体会话中完成，而且还笼罩在迷雾中：从这里通往**目的地**的道路尚不可见。寻路的重点是找到这条路，而不是径直冲向目的地。本技能会在仓库的问题跟踪器上将路径绘制为一张**共享地图**，然后逐一处理其中的**决策工单**——这类问题的解决结果是一项决策，而不是要执行的构建工作切片——直到路线清晰为止。

每项工作的目的地各不相同，而为其命名是绘制地图的第一步——它会塑造每一张工单。目的地可能是一份需要移交并持续迭代的规范、一项必须在规划开始前敲定的决策，也可能是一项直接实施的变更，例如数据结构迁移。地图与领域无关——工程工作、课程内容，或任何符合这种形态的事项都可以。

## 规划，而非执行

Wayfinder 默认用于**规划**：每张工单解决一项决策；当道路已经清晰——在有人着手执行之前，已经没有任何待决事项——地图就完成了。想要直接动手做这项工作的冲动，通常意味着你已经到达地图的边缘，该进行移交了。某项工作可以在其**备注**中覆盖这一默认规则——将执行本身纳入地图——但如果没有这样的说明，就应产出决策，而不是交付成果。

## 以名称指代

每张地图和工单都是一个 issue，因此都有一个**名称**——也就是它的标题。在所有供人阅读的内容中——叙述、地图的“截至目前的决策”——都应使用该名称来指代它，绝不能只使用 id、编号或 slug。满墙的 `#42, #43, #44` 难以辨读；名称则一眼即可看懂。id 和 URL 并不会消失——名称会包裹对应的链接——但它们始终位于名称*之内*，绝不能代替名称。

## 地图

地图是此仓库问题跟踪器中的单个 issue，标有 `wayfinder:map` 标签——它是规范产物。地图的工单是该地图的子 issue。

地图是一个**索引**，而不是存储库。它列出已作出的决策，并指向保存其详细信息的工单；一项决策只存在于一个地方——它对应的工单中——因此地图绝不复述决策，只会概述其要点并提供链接。

**地图、其子工单、阻塞关系和前沿查询具体存放在哪里，取决于所使用的跟踪器。**你应该已经获得了问题跟踪器——如果没有，请运行 `/mattpocock:setup-matt-pocock-skills`。请查阅跟踪器文档中的“寻路操作”一节，了解*此*仓库如何表示这些内容。如果没有提供跟踪器，则默认使用 local-markdown 跟踪器。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。未关闭的工单**不会**列在其中——它们是未关闭的子 issue，需要通过查询找到。

```markdown
## Destination

<what reaching the end of this map looks like — the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index — one line per closed ticket: enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link) — <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每个工单都是地图的**子议题**；跟踪器的 issue id 就是它的标识。它的正文是一个问题，规模应控制在一次 100K token 的代理会话内：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每个工单都带有一个 `wayfinder:<type>` 标签——可取 `research`、`prototype`、`grilling`、`task` 之一（参见[工单类型](#ticket-types)）。

会话通过将工单分配给负责推进地图的开发者来**认领**它，而且必须在任何工作开始之前**首先**完成此操作，以便并发会话跳过该工单。该受理人本身就是认领标记：一个处于开放状态且未分配的工单即为无人认领。

阻塞关系使用跟踪器的**原生**依赖关系——这一点至关重要，因为它能在跟踪器自身的 UI 中以_可视化_方式呈现前沿，让人无需打开地图就能看到哪些工单可以领取。只有缺少原生阻塞功能的跟踪器才退回使用正文约定。当阻塞某个工单的所有工单都已关闭时，该工单即为**未阻塞**；**前沿**是所有开放、未阻塞且无人认领的子工单——即已知范围的边缘。

答案不属于正文的一部分——它会在解决工单时记录（参见[沿地图推进工作](#work-through-the-map)）。解决工单期间创建的资产应从 issue 中链接，而不是直接粘贴进去。

## 工单类型

每个工单要么是 **HITL**——人类参与其中，与能够代表自己发言的人类*共同*处理；要么是 **AFK**，由代理独立推进。HITL 工单只能通过这种实时交流来解决；代理绝不能代替人类完成交流中属于人类的部分（一个自己回答自己问题的追问代理已经违背了这一原则）。

- **研究**（AFK）：阅读文档、第三方 API 或知识库等本地资源，以查明某项决策所等待的事实。由 `/mattpocock:research` **subagent** 解决。当需要当前工作目录以外的知识时使用。
- **原型**（HITL）：制作一个廉价、粗糙、具体且可供反馈的产物，以提高讨论的保真度——可以是提纲、初稿、存根，或通过 /mattpocock:prototype skill 创建的 UI/逻辑代码。将原型作为资产链接。当关键问题是“它应该是什么样子”或“它应该如何运行”时使用。
- **追问**（HITL）：通过 /mattpocock:grilling 和 /mattpocock:domain-modeling skills 进行对话，每次提出一个问题。这是默认情况。
- **任务**（HITL 或 AFK）：在做出某个*决策*之前必须完成的手动工作——没有需要决定、制作原型或研究的内容，但讨论在工作完成前无法继续。例如注册某项服务以便评估其 API、开通访问权限、移动数据以便查看其形态。这是唯一一种执行工作而不是做出决策的类型——它之所以有存在的价值，是因为它能解除某项决策的阻塞，而不是因为它交付了最终目标。代理会在能力范围内独立推进（AFK）；否则，它会向人类提供一份精确的检查清单（HITL）。工作完成后即视为解决；答案会记录完成了什么，以及后续工单所依赖的任何结果性事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图是_有意_不完整的：不要绘制尚且看不清的内容。当前工单之外是**战争迷雾**——你能隐约看出即将出现的决策和调查，但尚且无法明确界定，因为它们取决于仍未解决的问题。解决一个工单会驱散其前方的迷雾，将现在已经能够明确描述的内容逐一转化为新的工单，直到通往目的地的道路清晰可见，并且不再有任何工单。

地图中的 **尚未明确** 部分，记录的正是这种模糊视图：推测中的问题、留待以后重新审视的领域。它是通往目的地的未探索前沿——这里的一切都在范围之内，只是还不够清晰，无法转化为工单。根据当前视图所允许的程度，描述可以宽泛，也可以详尽；它同时也为阅读地图的协作者提供路标，让他们了解这项工作正朝哪里推进。

**迷雾还是工单？** 判断标准是你现在能否精确地表述问题——而*不是*你现在能否回答它。

- **应创建工单的情况**：问题已经足够清晰——即使它仍被阻塞，你暂时还无法采取行动。
- **应归入尚未明确的情况**：你还无法如此清晰地表述它。不要预先把迷雾切分成工单大小的碎片：它比工单更粗略，而且当前沿推进到某片迷雾时，它可能演变成多个工单，也可能一个都不会产生。

**尚未明确** 不包括已经决定的事项（迄今的决策）、已经存在的有效工单，以及范围之外的事项（下一节）。

## 范围之外

迷雾只会聚集在*通往*目的地的方向上。目的地确定了范围，因此超出目的地的工作属于**范围之外**——它不是迷雾，也不应放入**尚未明确**。它在地图上有自己独立的**范围之外**部分：你有意识地排除在*本次*工作之外的事项。决定它归入这里的是范围，而不是清晰程度。

范围之外的工作永远不会转化为工单——前沿会止步于目的地——因此，只有在重新划定目的地时，它才会重新出现，而且会作为一项全新的工作，而不是原有工作的恢复。

将某件事排除在范围之外是一项范围界定行为，而不是路线上的一步。当一个已经存在的工单后来被发现位于目的地之外——可能是在绘制地图时被错误地纳入范围，也可能是在解决问题的过程中暴露出来——请**关闭它**（已关闭的工单明确不在前沿上），并在**范围之外**部分留下一行：简述事项及其超出范围的原因，并链接到已关闭的工单。它不应进入**迄今的决策**，因为该部分记录的是实际走过的路线——范围边界并不是路线上的一步。

## 关键要求：每个会话只处理一个工单，工作前先认领

每个会话绝不能解决超过一个工单（研究工单除外）。在开展任何工作**之前**先认领工单——将其分配给自己——这样并发会话就会跳过它。默认产出决策，而不是交付物：当你产生亲自完成工作的冲动时，这正是应当移交工作的信号。

## 调用方式

有两种模式。无论采用哪一种，**每个会话都绝不能解决超过一个工单**——研究工单除外。

### 绘制地图

用户以一个宽泛的想法发起调用。

1. **明确目的地。** 运行一次 `/mattpocock:grilling` 和 `/mattpocock:domain-modeling` 会话，确定这张地图要寻找通往何处的道路——某项规范、决策或变更。目的地决定范围，因此必须先确定目的地。
2. **绘制前沿。** 再次深入提问，但这次采用**广度优先**：横向探索整个空间，而不是深入任何一条线索，从而找出尚待决定的问题，以及当前即可采取的第一步。**如果此过程没有发现任何迷雾**——通往目的地的道路已经清晰，整个旅程也足够短，可以在一个会话内完成——那么你不需要地图。停止操作，并使用 AskUserQuestion 工具询问用户希望如何继续（例如，不使用地图直接继续／仍然绘制地图）。
3. **创建地图**（标签为 `wayfinder:map`）：填写目的地和备注，将迄今的决策留空，并在**尚未明确**中勾勒迷雾。
4. **为当前可以明确描述的事项创建工单**，并将其作为地图的子议题——然后在**第二轮**中连接阻塞关系（议题需要先有 id，才能相互引用）。连接关系会将它们划分到前沿或阻塞区；所有当前仍无法明确描述的事项都留在迷雾中——即**尚未明确**部分。
5. **启动研究子代理。** 对刚刚创建的每个 `research` 工单，启动一个 `/mattpocock:research` 子代理并行解决它，将研究结果记录在临时的 `research/<name>` 分支上，并在工单中留下上下文指针。
6. 停止——绘制地图就是一个会话的工作；它本身不解决任何工单。

### 按地图推进

用户使用地图（URL 或编号）调用。工单是**可选的**——如果未指定工单，则由你选择下一个决策，而不是用户。

1. 加载**地图**——使用低分辨率视图，不要加载每个工单的正文。
2. 选择工单。如果用户指定了工单，就使用该工单。否则，按顺序选择第一个前沿工单。**认领工单**：开始任何工作之前，先将其分配给自己。
3. 解决工单——**按需放大**：根据需要获取任何相关工单或已关闭工单的完整正文；调用 `## Notes` 块中指定的技能。如有疑问，使用 `/mattpocock:grilling` 和 `/mattpocock:domain-modeling`。
4. 记录解决结果：将答案发布为**解决结果评论**、**关闭**议题，并在地图的 Decisions-so-far 中**追加上下文指针**。
5. 添加新浮现的工单（先创建，再连接）；将答案使其变得可明确说明的任何模糊事项转为正式工单，并从 **Not yet specified** 中清除每个已转化的条目，使其仅存在于对应的新工单中。如果答案表明某个工单——无论是当前工单还是其他工单——超出了目标范围，应将其**判定为范围之外**，而不是在推进途中解决它。如果该决策使地图的其他部分失效，请更新或删除相应工单。

用户可能会并行处理未受阻塞的工单，因此应预期其他会话也在并发编辑跟踪器。
