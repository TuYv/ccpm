# 沟通

将沟通思维应用于任何消息、提案或交付决策。诊断所面对的沟通问题类型，并应用正确的工具。

## 适合使用哪种工具

| 你需要…… | 工具 |
|---|---|
| 了解受众真正相信和关心什么 | audience-modeling |
| 在发送前找出消息可能被误读或遗漏的地方 | clarity-audit |
| 为消息选择正确的渠道和形式 | medium-selection |
| 预判并提前回应可能的异议 | objection-mapping |

## 路由决策

**框架检查：** 继续之前，确认消息、受众和目标。用一句话说明你识别出的内容——当前实际要解决的沟通情境——然后使用 `AskUserQuestion`：
- **问题：** “我的理解是：[用一句话概述消息、接收对象，以及成功的标准]。对吗？”
- **标题：** “框架”
- **选项：**
  - **是——继续** — 框架正确
  - **调整** — 有一个要素不准确；用户会先纠正它，然后你再继续
  - **重新界定** — 实际情境与你的理解不同；先纳入修正内容，然后再继续

- **不太了解受众，或不知道他们为什么无法理解** → audience-modeling
- **已有草稿，并希望找出其中的问题** → clarity-audit
- **不确定应该使用电子邮件、会议、异步沟通、同步沟通还是文档** → medium-selection
- **即将陈述有争议的内容，需要提前准备** → objection-mapping
- **不明确** → 先使用 audience-modeling；沟通失败发生在接收者一端，而非发送者一端

## 确认方向

诊断出适合使用的工具后，使用 `AskUserQuestion` 工具确认方向。动态构造问题，并包含你的诊断结果：

- **问题：** “我的判断是：**[诊断出的工具]**——[用一句话说明它为什么适用]。你希望如何继续？”
- **标题：** “方向”
- **选项：**
  - **是，运行该工具** — 使用已提供的上下文，立即执行诊断出的技能
  - **显示所有选项** — 列出此类别中的所有技能，并为每项提供一句话说明
  - **快速版本** — 如果当前情境存在轻量级替代方案，则运行该方案
  - **重新诊断** — 重新审视情境描述，以得出不同的判断

根据用户的选择继续。

## 受众建模

*梳理受众当前相信什么、真正关心什么，以及害怕什么。*

在沟通之前建立受众模型。他们目前对该主题已经持有哪些看法？他们的真实目标是什么（通常不同于其角色所声称的目标）？他们害怕什么——对消息本身、变化或后果的担忧？要让他们改变想法或采取行动，需要满足哪些条件？沟通失败并不是因为消息不清晰，而是因为发送者没有对接收者进行建模。

**输出：** 受众信念图、真实目标、担忧，以及获得积极回应所需满足的阈值条件。

## 清晰度审查

*找出消息会在哪里丢失、被误读或被误解。*

将这条消息视为没有任何前置上下文来阅读。它在哪些地方假定读者具备其可能并不拥有的知识？哪些词语或短语可能有不同的理解？哪些地方的结构掩盖了重点？请求在哪些地方被埋没或只是隐含表达？对于每个问题：将其分类为歧义（存在多种合理解释）、假设（缺少上下文）或结构（信息架构掩盖了消息本意）。

**输出：** 带注释的清晰度问题列表，按类型分类，并为每个问题提供具体的改写方案。

---

## 媒介选择

*为消息匹配合适的渠道和格式。*

从四个维度评估消息：(1) 复杂度——理解它是否需要对话，还是内容本身已完整自洽？(2) 语气——它是否承载了情绪分量，需要在场交流？(3) 留档——它是否需要便于日后查找？(4) 紧迫性——响应的时间敏感度有多高？根据可用渠道对照评估这些维度。同样的内容如果使用了错误的媒介，其效果会大打折扣——本需要在场交流却使用了异步消息，或本需要文档却安排了会议。

**输出：** 推荐的渠道及理由、该渠道内应采用的格式，以及应避免的做法。

---

## 异议梳理

*在提出方案前梳理可能出现的异议。*

列出所有会接触到该方案的利益相关者。对于每一方：他们最可能提出的第一个异议是什么？该异议背后更深层的顾虑是什么？然后评估每项异议：它能否通过修改方案来解决、能否通过调整表达方式来解决，还是确实无法解决？事先预判的异议会让人感到已得到回应；突如其来的异议则会打乱进程。

**输出：** 异议图谱——利益相关者、表层异议、深层顾虑，以及应对方式。标记出无法解决、需要提案者提前做好准备的异议。
