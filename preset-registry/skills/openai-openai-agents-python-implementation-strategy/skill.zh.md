# 实施策略

## 工作流程

1. 确定你正在变更或审查的接口面：已发布的公共 API、未发布的分支本地 API、内部辅助工具、持久化模式、线协议、CLI/配置/环境变量接口面，或仅限文档/示例。
2. 首先从 `origin` 确定用作兼容性基线的最新发布标签，仅当远程标签不可用时才回退到本地标签：
   ```bash
   BASE_TAG="$(.agents/skills/final-release-review/scripts/find_latest_release_tag.sh origin 'v*' 2>/dev/null || git tag -l 'v*' --sort=-v:refname | head -n1)"
   echo "$BASE_TAG"
   ```
   将回退到本地标签的情况报告为可能已过时。
3. 在编码之前，记录下方的实施范围契约。
4. 确定最接近的现有实现管线，以及作为每个受影响关注点之事实来源的函数、类型或模块。优先调整所需输入以适配该管线，而不是创建并行的模式、元数据、验证、命名或执行机制。
5. 使用核心决策规则选择最小且连贯的变更。仅为必须支持的边界添加兼容性机制。
6. 在编辑每一批审查反馈之前，针对完整的分支差异运行审查关卡，而不只是检查最新修订。
7. 在交接之前，运行有效性检查。如果任何答案为否，请修改设计。

## 实施范围契约

在计划或工作笔记中记录以下四项，并在扩大或缩小实施范围之前更新它们：

1. **必需行为：** 必须正常工作的最小用户可见场景。
2. **兼容性要求：** 必须保持可用的已发布且受支持的行为或持久边界。
3. **有意不支持的情况：** 应拒绝的相近输入或结构，包括拒绝发生的时机和方式。
4. **受支持的替代方案：** 现有的包装器、覆盖项、适配器、配置或底层 API；如不存在则注明 `none`。

如果无法清晰说明有意不支持的情况，请勿从添加通用解析器开始。应先定义更窄的行为契约。如果不存在足够适用的受支持替代方案，仅在任务要求时添加；不要凭空臆测并创建一个。

在已发布版本中可复现只能证明可达性，不能证明受支持。仅当确切结构被公共文档、示例、测试或类型定义有意涵盖；为持久边界所必需；或有具体的用户依赖或维护者意图作为依据时，才将其视为兼容性要求。否则，请记录风险，并优先选择尽早拒绝，同时提供现有的受支持替代方案。

## 审查反馈关卡

在编辑每一批新反馈之前，重复执行此关卡：

```text
审查检查点：
- 根本原因和必需行为：
- 兼容性证据和不支持的情况：
- 事实来源：
- 行为空间变化：缩小 / 不变 / 扩大
- 操作：聚焦修补 / 复杂度重置 / 以不受支持为由拒绝
```

将每个发现分类为必需行为缺陷、受支持的兼容性要求、相同实现维度的另一种组合或不相关的问题。扩大行为空间需要新的契约证据。

如果第二个相关发现会给同一抽象再增加一个条件、协议跳转、兼容性情形或测试排列组合，请停止打补丁并执行复杂性重置。只有当具体证据表明该确切情形属于必需或受支持的契约时，才继续处理。

重置后的规范一旦冻结，就应将后续每个发现归类为：违反该规范、有证据支持的规范修订理由、明确不受支持的情形，或不相关的问题。不要仅仅因为新发现可以在局部修复，就恢复渐进式打补丁。

示例：如果接连出现的发现要求遍历直接包装器、偏函数、嵌套包装器、描述符和绑定方法，请不要再增加一层跳转。除非支持任意包装器图，否则应保留必需的普通可调用对象行为，并在调用前拒绝有歧义的包装器。

## 核心决策规则

- 保留已发布的公共 API、文档化行为和受支持的持久边界，或提供明确的迁移路径。
- 直接重写分支本地接口、内部辅助函数、同一分支上的测试，以及 `main` 上发布后新增的内容，除非它们已经定义了受支持的持久边界。
- 如果中间快照明确不受支持，则可以对尚未发布的持久化模式版本重新编号或进行压缩；应同步更新支持集合和测试。
- 不要将广泛的 Python 或第三方协议等同于支持所有可表示的形态。
- 优先采用最近的现有管线，并确保模式、文档、验证、身份标识和调用各自只有一个事实来源。
- 将接口视为调用者为正确使用该行为而必须了解的一切，包括顺序、错误、生命周期、配置，以及相关情况下的性能约束；不要仅根据签名判断接口大小。
- 在保留新抽象之前应用删除测试：如果移除它会将必需的复杂性分散到各调用方，则保留它；但如果复杂性本身也会随之消失，则移除它。
- 只有在已证实存在变化、所有权或可测试性需求时，才添加可替换边界。当现有管线已经提供稳定边界时，一个假想适配器或仅供测试使用的间接层并不足以成为添加边界的理由。
- 只有为了明确的需求、受支持的契约或已验证的风险，才添加抽象、状态、分类、分支、配置、依赖项或并行路径。
- 对尚未发布的代码，优先选择删除或直接替换。将分支本地实现和测试视为可丢弃内容。
- 与部分模拟协议相比，优先选择在构造或验证时给出可操作的错误，并提供现有替代方案。
- 不要在补丁中包含不相关的重构和既有故障。
- 测试必需行为、最近的受支持路径，以及每个不受支持类别中的一个代表性情形，而不是测试所有可构造的排列组合。
- 在计划和交接中明确指出对受支持的已发布行为或持久格式所做的更改。

## 复杂性重置

在以下情况下，停止扩展当前设计：

- 相关发现不断组合相同的维度，例如包装器、描述符、泛型、绑定、上下文注入、同步/异步分类或提供程序变体。
- 补丁对宿主语言或第三方协议进行了解释，或者分别推断可能发生偏移的表示形式。
- 一项范围狭窄的需求却需要递归解析、缓存模式、新状态或对无关子系统的更改。
- 测试逐一枚举实现机制，或者完整差异不断增大，而所需场景仍然很小。

触发任一信号时：

1. 停止编辑并冻结当前修订以供分析，而不是逐条处理评论。
2. 按根本原因对发现进行分组，并重新阅读原始需求、范围约定以及受支持的版本边界或持久边界。
3. 使用这些输入编写一份根据发现得出的候选重置规范。不要将累积的评审说明、分支局部机制或同一分支中的测试视为需求。
4. 针对每个受影响的入口点和最接近的现有受支持路径审核候选规范。根据需要进行修订，然后在恢复编辑前将其冻结。
5. 将完整差异与预期的合并基准或最新版本标签进行比较，并将每个抽象、分支和测试按照与冻结规范的关系标记为 `retain`、`replace` 或 `delete`。
6. 删除无法映射到规范的机制，收窄约定，并在产生副作用之前拒绝不受支持的情况。
7. 围绕必需行为、受支持的兼容性、跨入口点一致性以及具有代表性的不受支持类别重新构建测试。
8. 根据冻结规范评估后续发现。在更改规范或扩大行为范围之前，先停止并记录新的约定证据。

在计划或工作笔记中使用以下精简重置规范：

```text
Finding-derived reset spec:
- Original required outcome:
- Supported release or durable boundaries:
- Grouped findings and common root cause:
- Invariants across affected entry points:
- Allowed states and behavior:
- Rejected states, failure timing, and side-effect boundary:
- Trusted and untrusted boundaries:
- Single sources of truth:
- Persistence, resume, cleanup, or other lifecycle semantics:
- Non-goals and supported alternatives:
- Representative test categories:
- Diff reset: retain / replace / delete:
```

候选规范是一项可证伪的设计假设，而不是当前实现的记录。在将其冻结之前，审核可能会对其进行修正。一旦冻结，必须有明确证据才能修订它，并且在任何修订后都要重新执行完整差异映射。

当这些信号已经出现时，不要等待用户或评审者提出重置请求。

## 有效性检查

在宣布设计完成之前，请用具体证据回答以下所有问题：

- 能否在不提及内部辅助类型或反射机制的情况下描述所需行为？
- 实现是否复用了最接近的现有流水线，而不是维护一套并行解释逻辑？
- 每个新增抽象和分支是否都能映射到范围约定或经验证的风险？
- 删除每个新增抽象是否只会迫使多个调用方分别承担所需复杂性，并且每个新边界是否都对应已证实的变化、所有权或可测试性需求？
- 是否在产生副作用之前拒绝了相邻的不受支持情况，并指出了现有替代方案？
- 测试是否覆盖了能够复现所需行为的最高稳定调用方边界，且预期值独立于实现逻辑？
- 完整差异和测试是否在覆盖约定的同时，避免将每一种可构造的排列都纳入支持范围？
- 最新的评审修订是否缩小或维持了行为范围，而不是在没有证据的情况下将其扩大？
- 发生复杂性重置时，每个保留的抽象、分支和测试是否都能映射到冻结的重置规范，并且后续发现是否都已依据该规范进行分类？

## SDK 特定的决策规则

- 将已发布的 `RunState`、会话持久化以及其他明确持久化的序列化状态视为对跨提交、跨进程和跨机器兼容性敏感。
- 当不受支持的 OpenAI API 或提供商适配器行为已有已发布的默认路径时，除非最新发布边界足以证明这种破坏性变更合理，否则应避免将其变为默认的硬错误。优先采用可选择启用的严格模式，例如 `strict_feature_validation=True`，同时通过警告、忽略不受支持的数据或提供明确的非空占位符来保持默认路径兼容。
- 对于 OpenAI API 的功能缺口，应同时评估流式和非流式路径。自定义工具调用、多选项 Chat Completions 数据块、非文本工具输出以及类似的提供商载荷差异，不得在一条路径中严格处理，而在另一条路径中宽松处理或产生格式错误。
- 当一项变更新增公共 SDK 行为时，不要仅通过硬编码的模块全局变量将其公开。优先使用显式的公共配置对象或参数；在兼容性敏感的情况下保留现有默认行为，并明确说明可选择启用的 SDK 默认值。
- 对于 SDK 自有的公共配置，应在公共输入边界接受现有的类型化对象和等效字典，同时保留内部的类型化表示。应遵循所属模型的验证和额外字段策略，而不是重新实现任意第三方模式的语义。
- 将特定于模型的设置保留在现有的 `model_settings` 参数中。添加字典支持时，应保留已发布的构造函数参数、类型化对象行为以及提供商请求载荷。
- 将新的可选字段或构造函数参数追加到公共数据类和构造函数末尾。不要将其插入现有公共字段之前，除非同时为旧的位置参数调用形式提供兼容层和回归测试覆盖。
- 当阈值和配额值会影响运行时行为时，应将其视为 API 设计的一部分。区分源自 OpenAI 平台配额的值与 SDK 的防御性默认值；如果某个值并非基于有文档记录的平台限制，应避免将其设为无条件默认启用的行为。
- 应有意识地定义公共配置中 `None` 的语义。例如，应分别表达“功能已禁用或无 SDK 限制”“使用 SDK 默认限制”和“仅禁用这一特定限制”，而不是依赖隐式真值检查。

## 何时停止并确认

- 变更会改变最新发布标签中已交付的受支持行为，或有具体证据表明存在对该版本偶然接受的行为的实质性依赖。
- 变更会修改持久化的外部数据、协议格式或序列化状态。
- 正确的解决方案会实质性超出所请求的结果，或需要进行无关的架构工作。
- 复杂度重置触发条件被触发，且更窄范围的替代方案会改变已经发布的受支持契约，而不仅仅是分支本地代码。
- 用户明确要求向后兼容、弃用或迁移支持。

## 输出预期

当此技能对实现方式产生实质性影响时，请在推理或交接说明中简要陈述相关决策，例如：

- `Compatibility boundary: latest release tag v0.x.y; branch-local interface rewrite, no shim needed.`
- `Implementation scope contract: support X; preserve Y; reject Z before side effects; use supported alternative W, or none exists.`
- `Complexity reset: repeated edge-case combinations show the approach is too broad; redesign from the original requirement instead of adding another branch.`
- `Finding-derived reset spec: findings F1-F3 expose invariant X across entry points A-C; freeze that contract, delete unmapped machinery, and review later findings against it.`
