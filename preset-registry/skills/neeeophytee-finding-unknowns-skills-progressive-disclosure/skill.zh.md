# 渐进式披露

每一次交互都要为冗长的说明文件付出成本，即使有些交互根本不需要其中的任何内容。解决办法不是删除——这些材料确有其用——而是调整位置：将每次运行都需要的内容保留在入口文件中，并将只有部分运行才需要的内容移到指针之后，在相关时触发读取。本技能用于重构单个工件。要找出哪些工件需要重构，请先进行审查。

## 步骤

1. 阅读整个工件并识别其中的**分支**——即一次运行处理该工件时真正不同的路径。只有当用户要求验证时才会进入的验证章节属于分支；每次都适用的规则则不属于分支。
2. 将每个章节分为两类：每个分支都需要的内容，以及仅一个分支需要的内容。这一划分是整个决策的核心，而且通常没有看上去那么均衡——大多数文件都是一个简短的通用核心，外围包裹着特定于分支的细节。
3. 将通用核心保留在入口文件中，并合理安排顺序，使该文件单独阅读时仍然连贯。如果入口文件脱离其子文件后便无法理解，说明拆分位置有误。
4. 将每个分支移入同级文件，并根据文件所包含的内容命名，而不是根据其来源命名——例如 `verification.md`、`glossary.md`——让读者仅通过名称就能判断何时应打开该文件。
5. 谨慎编写指针，因为指针的措辞决定了这些材料是否会被实际读取。将触发条件和文件一起写明：“当变更涉及迁移时，请在规划前阅读 `migrations.md`。”文件底部单独放置的链接不算指针。
6. 从头到尾检查每个分支，确认其仍具备所需的全部内容。然后报告哪些内容已移动、哪些内容被保留，以及入口文件的新大小。

## 约束

- 拆分不等于删除。如果某个章节确实已经无用，应明确说明并直接将其删除，而不是把它藏进一个无人打开的文件中。
- 切勿拆分每个分支都需要的材料。如果两个文件总是要一起读取，那么它们只是一个被增加了额外步骤的文件。
- 永远不会被触发的指针会使材料不可见，这比将其保留在原处更糟。当触发条件无法明确表述时，该章节应留在原处。
- 在依赖同级文件之前，请验证目标运行框架是否确实会将这些文件与 `SKILL.md` 一起分发；不同安装程序的行为有所差异，指向未被一同传输的文件会使技能失效。
- 当入口文件已经易于阅读时便应停止。超过这一点继续拆分，只会用一种难读取代另一种难读。
