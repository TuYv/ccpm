# 查找缺陷

审查此分支上的更改，查找缺陷、安全漏洞和代码质量问题。

## 阶段 1：完整收集输入

1. 获取完整 diff：`git diff $(gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name')...HEAD`
2. 如果输出被截断，请逐个读取每个已更改的文件，直到查看完所有更改的行
3. 在继续之前，列出此分支中修改的所有文件

## 阶段 2：攻击面梳理

对于每个已更改的文件，识别并列出：

* 所有用户输入（请求参数、请求头、请求体、URL 组成部分）
* 所有数据库查询
* 所有身份验证/授权检查
* 所有会话/状态操作
* 所有外部调用
* 所有加密操作

## 阶段 3：安全检查清单（对每个文件检查每一项）

* [ ] **注入**：SQL、命令、模板、请求头注入
* [ ] **XSS**：模板中的所有输出是否都已正确转义？
* [ ] **身份验证**：所有受保护的操作是否都有身份验证检查？
* [ ] **授权/IDOR**：是否验证了访问控制，而不仅仅是身份验证？
* [ ] **CSRF**：改变状态的操作是否受到保护？
* [ ] **竞态条件**：是否有任何先读后写模式中的 TOCTOU 问题？
* [ ] **会话**：会话固定、过期、安全标志是否存在问题？
* [ ] **加密**：是否使用安全随机数和适当的算法，日志中是否没有秘密信息？
* [ ] **信息泄露**：错误消息、日志、计时攻击是否存在问题？
* [ ] **DoS**：是否存在无边界操作、缺少速率限制或资源耗尽问题？
* [ ] **业务逻辑**：是否存在边界情况、状态机违规或数值溢出？

## 阶段 4：验证

对于每个潜在问题：

* 检查已更改代码中的其他位置是否已处理该问题
* 搜索是否有覆盖该场景的现有测试
* 阅读周边上下文，验证该问题是否确实存在

## 阶段 5：结论前审计

在最终确定结论之前，你必须：

1. 列出你审查过的每个文件，并确认已完整阅读
2. 列出检查清单中的每一项，并注明是发现了问题还是确认没有问题
3. 列出所有无法完全验证的区域及其原因
4. 只有完成上述步骤后，才能给出最终发现

## 输出格式

**优先级**：安全漏洞 > 缺陷 > 代码质量

**跳过**：样式/格式问题

对于每个问题：

* **文件:行号** - 简要描述
* **严重程度**：严重/高/中/低
* **问题**：错误之处
* **证据**：为何这是真实存在的问题（尚未修复、没有现有测试等）
* **修复**：具体建议
* **参考资料**：如适用，请提供 OWASP、RFC 或其他标准

如果没有发现重大问题，请如实说明——不要捏造问题。

不要进行更改——只需报告发现。我会决定要处理哪些问题。
