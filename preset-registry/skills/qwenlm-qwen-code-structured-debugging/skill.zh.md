# 结构化调试

调试棘手问题时，人们的自然反应往往是先形成一个理论，然后立即应用修复方案。但这种做法失败的次数多于成功的次数。修复方案可能针对了错误的原因，引入了复杂性，制造虚假的信心，并掩盖真正的问题。更糟的是，几次尝试失败后，你会失去对已尝试方案的记录，开始随机猜测。

这种方法论用一个有纪律的循环取代猜测，逐步收敛到根本原因。每次迭代都会缩小搜索范围。虽然每次尝试花费的时间更多，但总体上会快得多，因为你不再把运行时间浪费在错误的理论上。

## 循环

### 1. 提出假设

在修改代码之前，先写下你认为发生了什么以及原因。明确说明执行路径中每一步的预期状态。

反例：“等待循环有问题。” 正例：“leader 会卡住，因为
`hasActiveTeammates()` 在所有 agent 都报告完成后仍返回 true，可能是因为 backend 进程退出后没有在 agent 对象上设置 terminal status。”

对于预计需要多轮排查的 bug，请在项目用于存放此类笔记的位置创建一个旁注文件。

将你的假设写在那里。这个文件会跨越对话轮次持续存在，甚至可以跨会话保留——它就是你的调查日志。

### 2. 设计检测手段

在能够确认或否定假设的确切决策点，添加有针对性的调试日志或断言。思考你需要看到哪些数据。

不要到处散落 `console.log`。找出 2-3 个假设会做出可测试预测的位置，并在那里添加检测手段。

优先记录 _值_（返回码、payload 内容、stream 类型、消息正文、env 状态），而不是记录 _是否存在_（“这个函数是否被调用了？”“是否走了这个分支？”）。代码路径跟踪告诉你运行了什么；数据跟踪告诉你这些代码处理了什么。大多数非平凡 bug 都是正确的代码处理了错误的数据。

问问自己：“如果我的假设正确，我会在 X 点看到什么？如果错误，我又会看到什么？”

### 3. 验证数据采集

运行之前，确认检测手段产生的输出确实会被捕获并且可以访问。

常见陷阱：

- 测试命令中的 `2>/dev/null` 丢弃了 stderr
- 进程在 flush 前被终止（日志丢失）
- 日志写入的目录不存在
- 输出经过了会截断内容的管道
- 查看的是_上一次_运行的日志文件，而不是当前运行的日志文件

一次没有产生任何数据的测试运行就是浪费。

### 4. 运行并观察

执行测试。读取实际输出——每一行都要读。不要想当然地假设输出内容。

当数据与假设矛盾时，相信数据。不要为其找理由。此步骤的全部意义，就是让现实推翻你的理论。

### 5. 记录发现

在旁注中更新以下内容：

- 数据显示了什么（引用具体的日志行）
- 哪些内容得到确认，哪些内容被否定
- 下一轮迭代更新后的假设

这一点对于避免在多次尝试之间丢失上下文至关重要。棘手的 bug 通常需要 3-5 轮排查。没有笔记，你会忘记已经排除的方向，并浪费运行时间重新检查这些内容。

### 6. 迭代

根据新证据更新假设。回到第 2 步。每一轮都应缩小搜索空间。

如果经过 3 轮后仍没有进展，就退一步，质疑你的假设。Bug 可能位于你尚未考虑的某一层。

## 应避免的失败模式

这些是该方法专门用于避免的具体陷阱。当你注意到自己开始偏向其中任何一种时，停下来，回到这个循环中。

### 在没有证据的情况下直接修复

这是最常见的失败模式。你有一个看似合理的理论，于是就“修复”它，然后再次运行。如果理论是错的，你就增加了复杂性，浪费了一次测试运行，还可能引入新的 Bug。在应用任何修复之前，旁注中始终应显示“假设已通过[具体数据]验证”。

### 归咎于外部系统

“模型在幻觉。”“API 不稳定。”“库有 Bug。”这些结论让人感觉满意，因为它们把问题置于你的控制范围之外。但它们通常也是错的。

在归咎于外部系统之前，先检查它实际收到了什么。一个看似产生幻觉的模型，可能只是因为你不知道其中存在过时数据，而在做出合理响应。一个看似不稳定的 API，可能只是收到了格式错误的请求。查看输入，而不仅仅是输出。

### 只检查代码路径，不检查数据

你为代码添加了检测，并证明它执行正确——调用了正确的函数，顺序正确，也没有错误。但 Bug 仍然存在。为什么？

因为代码在处理垃圾输入时，完全可以正常工作。一个能够正确读取收件箱、正确传递消息并正确格式化输出的函数，如果收件箱中包含上一次运行遗留的过时消息，仍然是有问题的。

始终检查流经代码的_内容_，而不仅仅是代码是否运行。检查 payload、消息内容、文件数据和数据库状态。

### 不去调查用户的报告，反而重新解释它

当用户报告的症状无法在你自己的运行中复现时，这个矛盾本身_就是_证据——两个环境以某种你尚未识别的方式存在差异。错误的做法是重新解释他们的报告（“他们肯定使用的是过时的 SHA”，“他们肯定弄错了自己看到的内容”，“肯定只是偶发故障”），让你的运行结果成为事实标准。一旦这样做，之后的每一条证据都会被扭曲，以维护这种重新解释，而真正的 Bug 仍会被隐藏。

正确的做法是：在形成任何假设之前，列出他们的环境与你的环境之间有哪些差异（TTY 与 pipe、终端模拟器、shell、locale、环境变量、之前的状态、构建产物）。对于含义模糊的症状（“没有输出”、“很慢”、“不对”），先问一个用于消除歧义的问题——例如：“它是卡住了，还是正常退出了？”这样可以在运行任何测试之前缩小假设空间。

### 在多次尝试之间丢失上下文

经过几轮调试后，你开始忘记已经尝试过什么，以及已经排除了什么。你会重复检查某些内容、兜圈子，或者因为忘记了调查方向而放弃一条有希望的调查路线。

这就是旁注文件存在的原因。每次运行后都要更新它。开始新一轮时，先重新阅读它。

## 持久状态：一个特殊类别

跨运行持久化数据的功能——缓存、会话记录、消息队列、临时文件和数据库行——经常会导致“不可解释”的错误。
当前运行的行为会受到之前运行遗留状态的污染。

当行为看起来不合逻辑时，始终检查：

- 是否存在会跨运行保留的持久状态？
- 在本次运行之前是否已清除？
- 系统响应的是陈旧数据，而不是当前数据吗？

这很容易被忽略，因为代码是正确的——出错的是数据。

## 何时退出循环

只有当你能指出仪器记录中的具体数据，确认根本原因后，才应用修复。在旁注中写下：

```
Root cause: [specific mechanism]
Evidence: [specific log lines / data that confirm it]
Fix: [what you're changing and why it addresses the root cause]
```

然后应用修复，移除仪器记录，并通过一次干净运行进行验证。
