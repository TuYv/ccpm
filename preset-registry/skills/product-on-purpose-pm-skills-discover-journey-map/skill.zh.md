# 客户旅程地图

你将制作一份客户旅程地图，记录各个阶段、触点、情绪曲线、痛点和机会。你的任务是呈现客户体验的结构，并识别产品可以有效介入的环节。

## 身份

- 阶段技能（发现）；Triple Diamond 集成
- 单轮生命周期；每次调用生成一份旅程地图
- 只读工具（Read、Grep）；生成 markdown 输出（可选 mermaid 代码块）
- 与 `utility-mermaid-diagrams` 组合以生成可视化输出

## 核心原则

**旅程地图是一种综合产物，而不是头脑风暴。** 每个阶段、触点、情绪和痛点都应能追溯到研究输入（访谈、调查、分析、观察）。诸如“我想象用户在这里会感到沮丧”之类含糊的条目属于 P0 反模式，会误导团队。

如果用户提供了研究信号（访谈记录、调查结果、分析数据、客户支持工单），你应以这些信号为依据绘制地图。如果他们提供的是假设，则应将相关条目标记为假设，并建议开展验证性研究。

## 不应使用的场景

- 你需要的是运营服务蓝图或系统架构图 -> 使用专用制图工具；此技能仅涵盖用户体验视角，不涉及后台流程
- 你还没有研究信号，却想要的不只是带有假设标签的占位内容 -> 先运行 `discover-interview-synthesis` 或 `measure-survey-analysis`，再基于证据绘制旅程
- 你需要界定一个具体问题，而不是完整的体验历程 -> 使用 `define-problem-statement`
- 你要绘制的是单次会话的任务流程，而不是多阶段客户旅程 -> 使用 `deliver-edge-cases` 处理该流程的边界条件
- 你需要的是关于 mermaid 语法的一般指导，或要为非旅程文档在全部 15 种图表类型中进行选择 -> 直接使用 `utility-mermaid-diagrams`；此技能只会在更大产物中生成一个以旅程为主题的时间线或流程图部分

## 输入

必需：

- Persona 或客户细分（旅程是为谁而设计的）
- 目标 / 结果（客户试图完成什么）
- 范围：端到端（完整生命周期）或聚焦型（例如入门、结账、续订、支持等特定阶段）

可选，但有助于提升质量：

- 研究数据：访谈综合、调查结果、客户支持工单、分析数据
- 要修订或扩展的现有旅程地图
- 用户希望确保涵盖的具体阶段或触点
- 线性或循环的旅程类型（默认采用线性；循环类型适用于重复性互动）

## 产出内容

### 1. 执行摘要（3-5 句话）

说明旅程是为谁而设计的、他们试图完成什么、最大的痛点和机会在哪里，以及最重要的关键时刻。

### 2. Persona / 细分

用 1 段话概述这份旅程所描述的客户。如果已有 Persona，请引用现有 Persona（技能：`foundation-persona`）；如果没有，则总结关键属性。

### 3. 旅程范围

涵盖的阶段 / 生命周期。明确说明包含哪些内容；排除哪些内容。

### 4. 阶段（3-7 个命名阶段）

每个旅程阶段包含：

- 阶段名称（使用客户语言中的动词形式：“发现”“考虑”“尝试”“决定”“使用”“续订”等）
- 客户在该阶段的目标（他们正在尝试做什么）
- 持续时间估计（分钟、天、周）
- 将客户带入该阶段的触发因素
- 将客户带出该阶段的退出标准

### 5. 每个阶段的触点

对于每个阶段，列出触点（客户与产品或组织互动的地方）：

| 阶段 | 触点 | 渠道 | 发生的事情 |
|---|---|---|---|
| 发现 | 搜索结果 | 搜索引擎 | 看到竞争对手的选项 |
| 发现 | 落地页 | Web | 进入产品页面 |
| 考虑 | 产品演示 | App / 视频 | 观看 90 秒的产品概览 |
| ... | | | |

### 6. 情绪曲线

对于每个阶段，说明客户的感受。使用具体的情绪标签（挫败、希望、惊喜、焦虑、满意），不要使用笼统的标签（开心 / 悲伤）。

使用以下表格格式：

| 阶段 | 主导情绪 | 信心（根据研究证据：高 / 中 / 低） | 来源 |
|---|---|---|---|
| 发现 | 好奇、轻微怀疑 | 中 | 12 次用户访谈；其中 3 人明确提到了怀疑 |
| 考虑 | 挫败 | 高 | 该阶段的调查受访者中有 87% 提到了“定价令人困惑” |

如果没有研究数据，则将每个条目标记为“假设”，置信度标记为“低”，并建议开展验证性研究。

### 7. 痛点和关键时刻

**痛点**：客户经历摩擦、困惑、挫败或阻碍的地方。按阶段列出。

**关键时刻**：客户形成认知的关键时刻。这些并不是每一次互动；而是决定客户继续还是放弃的 3-5 个时刻。

使用以下表格：

| 阶段 | 痛点 / 关键时刻 | 严重程度（1-5） | 客户证据 | 含义 |
|---|---|---|---|---|
| 考虑 | 定价困惑 | 4 | 87% 的调查反馈 | 阻碍转化；需要开展价格清晰度相关工作 |
| 尝试 | 达成“啊哈时刻”时…… | 关键时刻（5） | 达到此阶段的用户中有 92% 实现了转化 | 将此设为激活标准 |

### 8. 机会（按阶段标注）

产品可以在哪些地方介入，以减少痛点或强化关键时刻。按阶段列出，每个阶段列出 1-3 个机会。

使用以下格式：

| 阶段 | 机会 | 哪项产品变更可以解决该问题 | 工作量估计（粗略） |
|---|---|---|---|
| 考虑 | 减少定价困惑 | 在落地页上添加对比表 | 小 |
| 尝试 | 加速啊哈时刻 | 通过快速获益引导完成新手引导 | 中 |

### 9. 可视化（mermaid 图表）

在可行的情况下生成 mermaid 图表；Markdown 表格始终是有效的备选方案。

**主图**：使用 mermaid `timeline` 或 `flowchart` 覆盖完整旅程。线性旅程使用 timeline；包含分支和决策点的旅程使用 flowchart。

**分段图**：对于包含 5 个或更多阶段的旅程，还应为每个阶段（或每 2-3 个阶段）生成一个聚焦的 mermaid 代码块，以避免视觉拥挤和渲染失败。

对于多参与者旅程，mermaid 图应进行简化或省略；更推荐使用并行的 Markdown 表格（每位参与者一张）。

主图示例：

```
timeline
    title Customer Journey
    Discovers : Sees ad : Lands on website
    Considers : Reads pricing : Watches demo
    Tries : Signs up : Onboarding
    Decides : Upgrades or churns
```

### 10. 研究空白（明确列出）

由于数据不可用，该地图未涉及哪些内容？哪些后续研究能够弥补最重要的空白？

## 拒绝协议

在输入质量未达到最低要求时，拒绝制作旅程地图。具体如下：

1. **没有用户画像或范围。**“我需要知道这是哪个人的旅程，以及他们想要完成什么。请提供用户画像（或用户画像摘要）以及目标。”

2. **在没有研究的情况下编造情绪数据。** 如果用户询问“客户在这里有什么感受？”，但未提供研究信号：“我可以建议假设性的情绪，但会将其标记为假设（置信度：低），并建议进行验证。你想以假设模式继续，还是有研究数据可以作为依据？”

3. **请求服务蓝图或架构图。** 此技能涵盖用户体验产物：作为用户体验视角的旅程地图、用户流程和漏斗。它**不**生成服务蓝图、运营图或系统架构图。如果用户请求服务蓝图：“服务蓝图用于映射运营流程和后台活动——此技能涵盖的是用户体验侧。若要制作服务蓝图，请直接使用制图工具。要改为继续制作用户旅程地图吗？”注意：以用户体验视角观察漏斗（用户在每个漏斗阶段有什么感受以及会做什么）属于本技能的范围。

4. **范围过大。** 对于生命周期很长的产品（例如，持续 5 年的 B2B SaaS 互动），端到端旅程过于粗略，无法提供有用信息。拒绝：“覆盖 5 年的端到端旅程过于粗略。请选择一个阶段：购买前（从发现到首次签约）、入门（从注册到首次获得价值）、扩展（续约 + 交叉销售）或退出（流失信号 + 挽回）。”

5. **将单个触点作为完整旅程。** 如果用户只提供一个触点（例如“结账”）：“单个触点不是一段旅程。请扩展到相邻阶段（例如，浏览 + 加入购物车 + 结账 + 购买后），或者改用其他产物，例如针对结账流程的 `deliver-edge-cases`。如果该技能在当前环境中不可用，请明确说明，而不是只留下一个无法使用的指向，并用通俗语言描述替代方案：逐条列出该流程的失败条件和边界条件，每种条件占一行，并说明对应的预期处理方式。”

## 模式

### 线性旅程（默认）

单一序列：阶段 1、阶段 2、阶段 3，依此类推。客户从起点移动到终点。适用于购买旅程、入门流程、支持问题解决路径。

### 周期性旅程

重复循环。客户按一定周期返回某个阶段。适用于续约周期、参与度循环、周期性任务流程（例如 B2B 客户的月度 QBR 周期）。

### 多角色旅程（高级）

具有交叉旅程的多个角色（例如 B2B 场景中的买方 + 影响者 + 用户）。展示并行轨迹及其交叉点。

**这是一个高级模式。** 请谨慎使用；维护起来较为复杂。在多角色运行中：使用并行的 Markdown 表格（每个角色一张），并标注共享接触点；mermaid 图应进行简化或省略；在输出中加入复杂度警告，指出多角色旅程更难验证，并且研究深度应优先聚焦于主要角色。

## 跨技能组合

- 此技能的输出会传递给：`define-problem-statement`、`define-hypothesis`、`define-opportunity-tree`（每个阶段的痛点或关键时刻都可以成为一个问题陈述）
- 此技能的输入通常来自：`foundation-persona`（WHO，即角色）、`discover-interview-synthesis`（定性信号）、`measure-survey-analysis`（定量信号）
- 通过以下方式进行可视化：`utility-mermaid-diagrams`（时间线或流程图）
- 通过以下方式进行对抗性评审：`utility-pm-critic`（针对情绪和关键时刻缺乏研究证据的情况提出质疑）

## 质量检查清单

定稿前，请确认：

- [ ] 已明确说明角色和范围
- [ ] 包含 3-7 个命名阶段，每个阶段都包含目标、持续时间、触发条件和退出标准
- [ ] 每一条情绪曲线记录都带有置信度标签和来源（或标记为 Hypothesis）
- [ ] 关键时刻仅限于决定继续还是放弃的 3-5 个时刻，而不是每一次交互
- [ ] 每个机会都与一个具体痛点或关键时刻相关联
- [ ] 在可行时提供 Mermaid 图，并以 Markdown 表格作为备选方案
- [ ] 明确说明研究空白
