# 客户旅程地图

你将制作一份客户旅程地图，呈现各个阶段、触点、情绪曲线、痛点和机会。你的任务是揭示客户体验的结构，并找出产品可以有效介入的环节。

## 身份

- 阶段技能（发现）；Triple Diamond 集成
- 单轮生命周期；每次调用生成一份旅程地图
- 只读工具（Read、Grep）；生成 markdown 输出（可选 mermaid 代码块）
- 与 `utility-mermaid-diagrams` 组合，用于可视化输出

## 核心原则

**旅程地图是综合产物，而不是头脑风暴。** 每个阶段、触点、情绪和痛点都应能够追溯到研究输入（访谈、问卷、分析数据、观察）。凭空臆测的“我想象用户在这里会感到沮丧”类条目属于 P0 反模式，会误导团队。

如果用户提供了研究信号（访谈记录、问卷结果、分析数据、客户支持工单），你应以这些信号为依据构建地图。如果用户提供的是假设，则应将条目标记为假设，并建议开展验证性研究。

## 不应使用此技能的情况

- 你需要的是运营服务蓝图或系统架构图 -> 使用专门的制图工具；此技能仅关注用户体验视角，不涉及后台流程
- 你还没有研究信号，却希望得到不只是带有假设标记的占位内容 -> 先运行 `discover-interview-synthesis` 或 `measure-survey-analysis`，然后基于证据绘制旅程
- 你需要界定一个具体问题，而不是完整的体验弧线 -> 使用 `define-problem-statement`
- 你要绘制的是单次会话中的任务流程，而不是多阶段的客户旅程 -> 使用 `deliver-edge-cases` 处理该流程的边界条件
- 你需要的是关于 mermaid 语法的一般指导，或需要在非旅程文档中从全部 15 种图表类型中进行选择 -> 直接使用 `utility-mermaid-diagrams`；此技能仅将特定于旅程的时间线或流程图作为更大产物中的一个部分生成

## 输入

必需：

- 角色或客户细分（旅程服务的对象）
- 目标 / 结果（客户试图达成的目标）
- 范围：端到端（完整生命周期）或聚焦型（某个特定阶段，例如引导、结账、续订、支持）

可选，但有助于提升质量：

- 研究数据：访谈综合、问卷结果、客户支持工单、分析数据
- 需要修订或扩展的现有旅程地图
- 用户希望确保覆盖的具体阶段或触点
- 线性旅程或循环旅程类型（默认为线性；循环类型适用于重复性参与）

## 产出内容

### 1. 执行摘要（3-5 句话）

说明旅程服务的对象、他们试图达成的目标、最大的痛点和机会所在，以及最重要的关键时刻。

### 2. 角色 / 细分

用 1 段话概述这份旅程所描述的客户。如果已有角色画像，则引用现有画像（技能：`foundation-persona`）；如果没有，则总结其关键特征。

### 3. 旅程范围

涵盖的阶段 / 生命周期。明确说明包含哪些内容；排除哪些内容。

### 4. 阶段（3-7 个命名阶段）

每个旅程阶段包含：

- 阶段名称（使用客户语言中的动词形式：“发现”“考虑”“尝试”“决定”“使用”“续订”等）
- 客户在此阶段的目标（他们想要完成什么）
- 持续时间估计（分钟、天、周）
- 促使他们进入此阶段的触发因素
- 促使他们离开此阶段的退出标准

### 5. 每个阶段的接触点

对于每个阶段，列出接触点（客户与产品或组织互动的地方）：

| 阶段 | 接触点 | 渠道 | 发生的事情 |
|---|---|---|---|
| 发现 | 搜索结果 | 搜索引擎 | 看到竞争对手的选项 |
| 发现 | 着陆页 | Web | 进入产品页面 |
| 考虑 | 产品演示 | App / 视频 | 观看 90 秒的产品概览 |
| ... | | | |

### 6. 情绪曲线

对于每个阶段，说明客户的感受。使用具体的情绪标签（挫败、希望、惊讶、焦虑、满足），不要使用泛化的标签（开心 / 难过）。

使用以下表格格式：

| 阶段 | 主要情绪 | 信心程度（根据研究证据填写：高 / 中 / 低） | 来源 |
|---|---|---|---|
| 发现 | 好奇、轻微怀疑 | 中 | 12 次用户访谈；其中 3 人明确提到怀疑 |
| 考虑 | 挫败 | 高 | 处于此阶段的调查受访者中，有 87% 提到了“令人困惑的定价” |

如果没有研究数据，将每个条目标记为“假设”，信心程度标记为“低”，并建议开展验证性研究。

### 7. 痛点和关键时刻

**痛点**：客户经历摩擦、困惑、挫败或阻碍的地方。按阶段列出。

**关键时刻**：客户形成认知的关键时刻。这些并不是每一次互动，而是决定客户继续前进还是放弃的 3-5 个时刻。

使用以下表格：

| 阶段 | 痛点 / 关键时刻 | 严重程度（1-5） | 客户证据 | 影响 |
|---|---|---|---|---|
| 考虑 | 定价困惑 | 4 | 调查中 87% 的反馈 | 阻碍转化；需要开展价格清晰度优化 |
| 尝试 | 达成“顿悟时刻”，发生在…… | 关键时刻（5） | 在达到此阶段的用户中，有 92% 完成转化 | 将其设为激活标准 |

### 8. 机会（按阶段标注）

产品可以在哪些地方介入，以减少痛点或放大关键时刻。按阶段列出，每个阶段列出 1-3 个机会。

使用以下格式：

| 阶段 | 机会 | 解决该问题的产品变更 | 工作量估计（粗略） |
|---|---|---|---|
| 考虑 | 减少定价困惑 | 在着陆页上添加对比表 | 小 |
| 尝试 | 加速达到顿悟时刻 | 通过快速见效的引导流程进行引导 | 中 |

### 9. 可视化（mermaid 图表）

在可行的情况下生成 mermaid 图表；Markdown 表格始终是有效的备选方案。

**主图：**生成一张覆盖完整旅程的 mermaid `timeline` 或 `flowchart`。线性旅程使用 timeline；包含分支和决策点的旅程使用 flowchart。

**分段图：**对于包含 5 个或更多阶段的旅程，还应为每个阶段（或每 2-3 个阶段）生成一个聚焦的 mermaid 区块，以避免视觉拥挤和渲染失败。

对于多角色旅程，mermaid 图应简化或省略；更推荐使用并行的 Markdown 表格（每个角色一张）。

示例主图：

```
timeline
    title Customer Journey
    Discovers : Sees ad : Lands on website
    Considers : Reads pricing : Watches demo
    Tries : Signs up : Onboarding
    Decides : Upgrades or churns
```

### 10. 研究缺口（明确列出）

由于缺乏数据，这张图**没有**涵盖哪些内容？哪些后续研究能够弥补最重要的缺口？

## 拒绝协议

在输入质量未达到最低要求时，拒绝生成旅程地图。具体如下：

1. **没有角色或范围。**“我需要知道这是哪个人的旅程，以及他们想要完成什么。请提供一个角色（或角色概述）和目标。”

2. **在没有研究的情况下编造情绪数据。**如果用户询问“客户在这里有什么感受？”，但没有提供研究信号：“我可以提出假设性的情绪，但会将其标记为假设（置信度：低），并建议进行验证。你想以假设模式继续，还是有研究数据可以作为依据？”

3. **请求服务蓝图或架构图。**此技能涵盖用户体验产物：旅程地图、用户流程和漏斗，作为用户体验视角进行分析。它**不会**生成服务蓝图、运营图或系统架构图。如果用户请求服务蓝图：“服务蓝图用于描述运营流程和后台活动——此技能涵盖的是用户体验侧。要制作服务蓝图，请直接使用绘图工具。你想改为继续制作用户旅程地图吗？”注意：从用户体验视角审视漏斗（用户在每个漏斗阶段有什么感受和行为？）**属于**本技能的范围。

4. **范围过大。**对于生命周期很长的产品（例如，持续 5 年的 B2B SaaS 使用过程），端到端旅程过于粗略，无法提供有效信息。拒绝：“覆盖 5 年的端到端旅程过于粗略。请选择一个阶段：购买前（从发现到首次签约）、引导（从注册到首次获得价值）、扩展（续约 + 交叉销售），或退出（流失信号 + 挽回）。”

5. **将单个触点作为完整旅程。**如果用户只提供了一个触点（例如“结账”）：“单个触点不是一段旅程。请扩展到其周边阶段（例如，浏览 + 加入购物车 + 结账 + 购买后），或者改用其他产物，例如针对结账流程的 `deliver-edge-cases`。如果该技能在当前环境中不可用，应明确说明，而不是只留下一个空泛的指向，并用通俗语言描述替代方案：逐行列出流程的失败条件和边界条件，并为每种条件写明预期处理方式。”

## 模式

### 线性旅程（默认）

单一序列：阶段 1、阶段 2、阶段 3，依此类推。客户从起点移动到终点。适用于购买旅程、引导流程和支持问题解决路径。

### 循环旅程

反复循环。客户按一定周期返回某个阶段。适用于续约周期、参与度循环和重复性任务流程（例如 B2B 客户的月度 QBR 周期）。

### 多角色旅程（高级）

具有交叉旅程的多个角色（例如 B2B 中的买方 + 影响者 + 用户）。展示带有交叉点的并行轨迹。

**这是一个高级模式。** 请谨慎使用；维护起来较为复杂。在多角色运行中：使用并行 Markdown 表格（每个角色一张），并标注共享触点；mermaid 图应简化或省略；在输出中加入复杂性警告，指出多角色旅程更难验证，研究深度应优先聚焦于主要角色。

## 跨技能组合

- 此技能的输出将馈入：`define-problem-statement`、`define-hypothesis`、`define-opportunity-tree`（每个阶段的痛点或关键时刻都可以转化为问题陈述）
- 此技能的输入通常来自：`foundation-persona`（WHO）、`discover-interview-synthesis`（定性信号）、`measure-survey-analysis`（定量信号）
- 可视化方式：`utility-mermaid-diagrams`（时间线或流程图）
- 对抗性评审方式：`utility-pm-critic`（质疑情绪和关键时刻缺乏研究证据的情况）
