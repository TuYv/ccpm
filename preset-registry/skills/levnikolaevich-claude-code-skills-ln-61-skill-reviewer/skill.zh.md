# Skill 审查器

**目标：** 在不修改仓库或外部状态的情况下审查技能变更。

**执行契约：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。将每个复选框追踪为 `PENDING`，然后使用具体证据将其解析为 `PROVEN`，使用表明其条件触发器不存在的证据将其解析为 `CLEARED`，或解析为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不能作为证明。
返回前，解析每个 `PENDING`；仅将 `PROVEN` 和 `CLEARED` 项计为已完成；将此技能的裁决、决策和批准规则应用于每个 `UNPROVEN` 项，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 仓库范围和证据 | 原生文件搜索、聚焦读取和 Git diff | 等效的只读 shell 命令 |
| Frontmatter 和技能结构 | 仓库定义的或宿主原生的技能验证器 | 手动执行 YAML、路径、命名和仓库契约检查 |
| 插件集成 | 仓库定义的插件验证器加清单解析 | 手动解析清单并与适用目录进行比较 |
| 宿主发现 | 针对每个已配置分发面的宿主原生验证器 | 手动检查目录、清单和源路径 |
| 当前宿主规则 | 宿主官方文档 | 不可用时将该声明标记为 `UNVERIFIED` |
| 行为独立性 | 新鲜子代理或干净上下文 | 以降低置信度的披露方式执行独立的自我审查 |

仅针对当前宿主行为或不断变化的标准使用外部研究。不要使用网络来源覆盖仓库中的实际文件、已安装版本或本地验证输出。

工具缺失本身并不是技能缺陷。应用文档化的备用方案，并且仅当缺失的能力阻碍可靠裁决时使用 `BLOCKED`。

## 检查清单

- [ ] 根据明确路径、Git diff、已暂存文件和未跟踪文件确定审查目标。
- [ ] 在判断仓库特定约定之前，阅读仓库说明、技能契约以及每个已配置的宿主目录；不要要求仓库并未分发的目录。
- [ ] 将主要技能与受同一变更影响的清单、目录和文档区分开。
- [ ] 确认仓库定义的规范技能布局；将未经授权、过时或存在差异的宿主特定副本视为缺陷，同时允许仓库策略明确要求的适配器或生成副本。
- [ ] 确认 Frontmatter 和文件夹命名符合仓库契约以及每个目标宿主的要求；仅当声明的本地约定如此规定时，才要求 `name` 和 `description`，而不是将其普遍强加于所有场景。
- [ ] 检查每个描述是否说明了能力、正向触发条件以及重要的近似否定边界。
- [ ] 检查描述是否处于宿主限制以内，并避免做出超出工作流支持范围的声明。
- [ ] 确认每个技能都是独立的：不依赖必需的技能、MCP 服务器、追踪器、协调器、工作器或共享运行时。
- [ ] 应用仓库声明的完成约定；当有序检查清单是完成定义时，将重复的完成部分标记出来。
- [ ] 保留不明显的领域规则、工具路由决策、安全门槛、证据要求、裁决映射、输出契约和剩余风险。
- [ ] 标记那些有能力的当前模型已经了解的解释，除非它们能防止已演示的执行失败。
- [ ] 检查内容层级和单一来源归属：将每条规则保留在最狭窄的规范部分，并标记正文、支持文件、清单和仓库说明之间重复或相互矛盾的指导。
- [ ] 标记填充内容、生成的摘要式措辞、复制的实现或业务逻辑，以及可以替换为稳定契约、权威来源、能力描述或明确更新触发条件的易变版本、路径、数量、默认值或宿主行为。
- [ ] 验证每项必需能力都有可用的工具路径、可信的备用方案或明确的 `BLOCKED` 结果。
- [ ] 检查每个技能的变更边界是否与其声明的结果一致；只读工作流不得获得隐式写入权限。
- [ ] 对于优化或实验类技能，在其修改状态时要求基于证据做出保留、舍弃或回滚决策。
- [ ] 对于测试构建或其他受限写入者，确认其无法修复产品代码或触及未经批准的外部状态，除非其声明的契约明确授权这样做。
- [ ] 追踪工作流在工具缺失、上下文不足、Git 状态不干净、命令失败和证据冲突情况下的行为。
- [ ] 检查输出契约是否区分事实、推断、缺失证据、裁决和剩余风险。
- [ ] 检查相邻描述是否存在触发条件重叠，但不要假设技能彼此知晓。

## 仓库验证

- [ ] 发现并运行针对已更改技能目录的、仓库要求的所有技能验证器；不要假定仓库证据中不存在的验证器名称或位置。
- [ ] 如果所需验证器不可用，请根据仓库和宿主契约，手动验证 YAML 解析、命名、描述约束以及必需的文件布局。
- [ ] 运行受影响分发单元所需的所有仓库插件或包验证器。
- [ ] 当相应目录或清单存在时，运行每个宿主原生的严格验证器；记录其实际覆盖范围，除非宿主已明确会遍历这些技能，否则不要将市场验证视为技能 frontmatter 验证。
- [ ] 解析所有已配置的目录；仅当仓库策略要求跨宿主一致性时，才比较插件名称和顺序。
- [ ] 确认每个声明的目录源、清单路径和技能路径都存在。
- [ ] 在仓库要求保持一致性的所有位置，确认重复的元数据（例如插件描述）保持一致。
- [ ] 对于市场仓库，确认稳定标识符未发生非预期变化；展示品牌不能替代标识符。
- [ ] 搜索过时名称、已删除路径、草稿标记、MCP 耦合、编排术语以及生成的副本。
- [ ] 仅当仓库策略定义了行数目标时才应用这些目标，并将其视为维护约束，而不是行为质量的证据。

## 行为审查

- [ ] 根据已声明的触发条件，而不只是技能标题，推导具有代表性的正向提示词。
- [ ] 根据相邻能力和用户可能使用的含糊措辞，推导接近的负向提示词。
- [ ] 验证技能会针对正向提示词激活，并针对接近的负向提示词保持不激活。
- [ ] 至少演练一个正常场景、一个缺少证据的场景以及一个安全边界场景。
- [ ] 当技能会编写代码或其他产物时，评估一个由智能体实际生成的结果，并根据独立的任务契约进行差异比对；不要用文字审查、回答简洁度或静态检查替代对执行行为的评估。
- [ ] 独立评定任务完整性、正确性、安全性、范围控制和清理情况；只有在必需结果通过后，才将代码或 token 减少视为辅助证据。
- [ ] 对于复杂或高风险的更改，在可用时使用全新的独立上下文，并且仅提供技能和原始任务产物。
- [ ] 不要向独立评估者透露预期发现、计划中的修复或先前的结论。
- [ ] 将只有在上下文泄露的情况下才能成功的正向测试视为技能缺陷。
- [ ] 检查独立上下文是否受到全局安装的技能、钩子、插件、用户指令、环境设置、缓存或产物的污染；证明目标技能已激活，并使行为无法可靠归因的评估分支失效。
- [ ] 除非有具体且反复出现的失败证明其必要性，否则不要创建或保留评估测试框架。

## 证据规则

- [ ] 将每项发现引用到确切的文件及最小有用的行或章节。
- [ ] 区分验证器失败、人工关注点和推测性改进。
- [ ] 在判定阻断级严重性之前，复现关键失败。
- [ ] 不要将偏好报告为正确性缺陷。
- [ ] 记录已执行的命令、退出状态和重要输出，但不得暴露机密信息。
- [ ] 当无法运行必需的主机或干净上下文测试时，报告覆盖缺口。

## 判定

- `PASS` — 结构、行为和集成检查均通过，且不存在实质性问题。
- `PASS WITH CONCERNS` — 可以发布，但仍存在范围明确的非阻断性不确定性。
- `FAIL` — 已确认的缺陷可能导致错误触发、不安全行为、安装损坏或契约无效。
- `BLOCKED` — 所需证据或工具不可用，且不存在可信的替代方案。

## 输出契约

返回：

1. 范围和变更涉及的表面。
2. 验证器和行为证据。
3. 按严重性排序的发现，每项包括位置、影响、证据和最小修正。
4. 触发边界评估。
5. Marketplace 和主机一致性评估。
6. 判定。
7. 剩余风险和未运行的检查。

审查期间不要编辑文件、暂存更改、发布软件包、更新 Marketplace 或创建 GitHub 状态。

任何诊断产物都必须是临时的，位于规范插件目录之外，并在剩余风险部分中披露。
