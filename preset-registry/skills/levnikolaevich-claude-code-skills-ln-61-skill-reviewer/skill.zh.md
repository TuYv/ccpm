# Skill 审查器

**目标：** 审查 Skill 变更，但不修改仓库或外部状态。

**执行契约：** 将下方按顺序排列的复选框工作流视为此 Skill 的完成定义。按顺序处理每一项，并且只有在其操作和所需证据均已完成时，才能将其标记为完成。`N/A`、已跳过、不可用或已委派的项目均保持未完成状态。
返回前，将此 Skill 的结论、决策和批准规则应用于每个未完成项目，并在输出前添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项目。

## 工具路由

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 仓库范围和证据 | 原生文件搜索、聚焦读取和 Git 差异 | 等效的只读 shell 命令 |
| Frontmatter 和 Skill 结构 | 仓库定义或宿主原生的 Skill 验证器 | 手动检查 YAML、路径、命名和仓库契约 |
| 插件集成 | 仓库定义的插件验证器并解析清单 | 手动比较清单与适用目录 |
| 宿主发现 | 针对每个已配置分发入口的宿主原生验证器 | 手动检查目录、清单和源路径 |
| 当前宿主规则 | 官方宿主文档 | 不可用时将声明标记为 `UNVERIFIED` |
| 行为独立性 | 全新的子代理或干净上下文 | 分离的自审查流程，并披露置信度降低 |

仅针对当前宿主行为或不断变化的标准使用外部研究。不得使用 Web 来源来推翻仓库中的实际文件、已安装版本或本地验证输出。

缺少工具本身并不构成 Skill 缺陷。应用已记录的后备方案，并且仅在缺少的能力导致无法得出可靠结论时使用 `BLOCKED`。

## 检查清单

- [ ] 根据明确路径、Git 差异、暂存文件和未跟踪文件确定审查目标。
- [ ] 在判断仓库特定约定之前，阅读仓库说明、Skill 契约和每个已配置的宿主目录；不要要求仓库并未分发的目录。
- [ ] 将主要 Skill 与受同一变更影响的清单、目录和文档区分开来。
- [ ] 确认仓库定义的规范 Skill 布局；将未经授权、过时或有差异的宿主特定副本视为缺陷，同时允许仓库策略明确要求的适配器或生成副本。
- [ ] 确认 Frontmatter 和文件夹命名满足仓库契约及每个目标宿主的要求；当声明的本地约定仅要求 `name` 和 `description` 时，只要求这两个字段，而不是将其普遍强制应用。
- [ ] 检查每条描述是否说明了能力、正向触发条件和重要的近似反向边界。
- [ ] 检查描述是否保持在宿主限制以内，并避免作出超出工作流支持范围的声明。
- [ ] 确认每个 Skill 都可独立运行：不需要其他 Skill、MCP 服务器、跟踪器、协调器、工作器或共享运行时。
- [ ] 应用仓库声明的完成约定；当按顺序排列的检查清单是完成定义时，标记重复的完成章节。
- [ ] 保留不明显的领域规则、工具路由决策、安全门槛、证据要求、结论映射、输出契约和残余风险。
- [ ] 标记当前具备能力的模型已经知道的解释，除非这些解释能够防止已证实的执行失败。
- [ ] 检查内容层级和单一来源归属：将每条规则置于范围最窄的规范章节中，并标记正文、支持文件、清单和仓库说明之间重复或矛盾的指导。
- [ ] 标记填充内容、生成式摘要文本、复制的实现或业务逻辑，以及可由稳定契约、权威来源、能力描述或明确更新触发条件替代的易变版本、路径、数量、默认值或宿主行为。
- [ ] 验证每项必需能力都有可用的工具路径、可信的后备方案或明确的 `BLOCKED` 结果。
- [ ] 检查每个 Skill 的变更边界是否与其声明的结果相匹配；只读工作流不得隐含获得写入权限。
- [ ] 对于优化或实验类 Skill，如果它们会改变状态，则要求基于证据作出保留、丢弃或回滚决策。
- [ ] 对于测试构建类或其他有限写入类 Skill，确认它们不能修复产品代码或触及未经批准的外部状态，除非其声明的契约明确授权。
- [ ] 追踪工作流在工具缺失、上下文不足、Git 状态不干净、命令失败和证据冲突情况下的处理路径。
- [ ] 检查输出契约是否区分事实、推断、缺失证据、结论和残余风险。
- [ ] 检查相邻描述是否存在触发条件重叠，不要假定这些 Skill 彼此知晓。

## 仓库验证

- [ ] 发现并运行仓库对已更改技能目录要求的每个技能验证器；在没有仓库证据的情况下，不要臆测验证器的名称或位置。
- [ ] 如果所需的验证器不可用，则根据仓库和宿主契约，手动验证 YAML 解析、命名、描述约束以及必需的文件布局。
- [ ] 对受影响的分发单元运行仓库要求的每个插件或软件包验证器。
- [ ] 当对应的目录或清单存在时，运行每个宿主原生的严格验证器；记录其实际覆盖范围，并且除非宿主明确会遍历这些技能，否则不要将市场验证视为技能前置元数据验证。
- [ ] 解析所有已配置的目录；仅当仓库策略要求跨宿主一致性时，才比较插件名称和顺序。
- [ ] 确认声明的每个目录源、清单路径和技能路径均存在。
- [ ] 确认插件描述等重复元数据在仓库要求一致的所有位置保持一致。
- [ ] 对于市场仓库，确认稳定标识符未被无意更改；显示品牌不能替代标识符。
- [ ] 搜索过时名称、已删除路径、草稿标记、MCP 耦合、编排术语以及生成的副本。
- [ ] 仅当仓库策略有所规定时才应用行数目标，并将其视为维护约束，而非行为质量的证据。

## 行为审查

- [ ] 根据所述触发条件而非仅根据技能标题，推导具有代表性的正向提示词。
- [ ] 根据相邻能力和可能存在歧义的用户措辞，推导相近的负向提示词。
- [ ] 验证该技能会因正向提示词而激活，并对相近的负向提示词保持不激活。
- [ ] 至少逐步检查一个正常场景、一个证据缺失场景和一个安全边界场景。
- [ ] 当技能编写代码或其他产物时，评估由真实智能体生成的结果，并将其与独立的任务契约进行差异比较；不要以文字审查、答案简短程度或静态检查代替执行行为评估。
- [ ] 分别评定任务完整性、正确性、安全性、范围控制和清理情况；只有在所需结果通过后，才将代码量或 token 数量的减少视为辅助证据。
- [ ] 对于复杂或高风险的更改，在条件允许时使用全新的独立上下文，并且仅提供技能和原始任务产物。
- [ ] 不要向独立评估者透露预期发现、计划中的修复或先前结论。
- [ ] 将只有在上下文泄露时才能成功的前向测试视为技能缺陷。
- [ ] 检查独立上下文是否受到全局安装的技能、钩子、插件、用户指令、环境设置、缓存或产物的污染；证明目标技能已激活，并使任何无法可靠归因其行为的实验组失效。
- [ ] 除非已证实存在具体且反复出现的故障，否则不要创建或保留评估框架。

## 证据规则

- [ ] 将每项发现引用到确切的文件以及最小的有效行范围或章节。
- [ ] 区分验证器失败、人工审查关注点和推测性的改进建议。
- [ ] 在将严重级别定为阻断之前，复现关键失败。
- [ ] 不要将偏好作为正确性缺陷报告。
- [ ] 记录已执行的命令、退出状态和关键输出，同时不得暴露机密信息。
- [ ] 当无法运行所需的宿主测试或干净上下文测试时，报告覆盖缺口。

## 结论

- `PASS` — 结构、行为和集成检查均通过，且不存在实质性问题。
- `PASS WITH CONCERNS` — 可以发布，但仍存在范围明确且非阻断性的不确定性。
- `FAIL` — 已确认的缺陷可能导致错误触发、不安全行为、安装失败或契约无效。
- `BLOCKED` — 所需证据或工具不可用，且不存在可信的替代方案。

## 输出契约

返回：

1. 范围和变更面。
2. 验证器和行为证据。
3. 按严重程度排序的发现，每项均包含位置、影响、证据和最小修正方案。
4. 触发边界评估。
5. Marketplace 和宿主一致性评估。
6. 结论。
7. 残余风险和未运行的检查。

审查期间不得编辑文件、暂存更改、发布软件包、更新 Marketplace 或创建 GitHub 状态。

任何诊断产物都必须是临时的、位于规范插件目录之外，并在残余风险部分披露。
