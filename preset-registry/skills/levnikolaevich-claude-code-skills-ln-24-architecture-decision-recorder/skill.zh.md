# 架构决策记录器

**目标：** 在一份紧凑且持久的记录中保留某项具有架构重要性的选择所涉及的背景、影响因素、备选方案、决策和后果。仅更改经过批准的决策文档；不要设计整个系统、默默批准决策、删除历史、审计代码或实施该选择。

**执行契约：** 有序复选框构成完成定义。将每一项在内部跟踪为 `PENDING`、具有具体证据的 `PROVEN`、具有该条件不存在的证据的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个部分后重新核对各项。在返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将该技能的判定和批准规则应用于每个缺口。

保留用户意图、范围和现有授权。继续已获授权的工作；仅针对具有重大影响的未解决选择或所需的外部批准提出询问。根据实质风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；对于其他义务，选择适合各项义务的验证方法。

将等价的用户或仓库证据视为有效输入；其他技能、命名工件或完整生命周期都不是前置条件。尽可能保留源需求和决策标识符。将复用的证据绑定到相关源版本、未提交的更改、配置和环境；发生更改后，仅使受影响的声明失效。

继续执行时，在恢复之前重新核对任务、现有授权、当前状态和未解决的证据。对于长期工作，返回一份简洁的继续记录，或更新已有的获授权任务工件；只读技能不会持久化该记录。区分工件就绪状态、已验证行为以及执行外部操作的权限。

在任何所需批准之前，先准备好已获授权的工作。如果某条指令阻止了进展，指出其确切来源并解释未解决的边界；不要仅凭一般谨慎臆造批准门槛。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 现有决策约定 | 仓库搜索和直接读取文档 | 使用默认路径和紧凑格式 |
| 决策驱动因素 | 需求、架构工件、实现证据和利益相关者陈述 | 将不受支持的驱动因素标记为 `UNKNOWN` |
| 备选方案和外部声明 | 仓库证据加当前官方来源 | 将时效性声明标记为 `UNVERIFIED` |
| 顺序和取代关系 | 现有文件名、索引和决策链接 | 返回 `BLOCKED`，而不是复用编号 |
| 文档变更 | 对一份获批准的决策记录进行最小补丁修改，并添加必要的取代关系链接 | 如果授权或路径不明确，则返回 `BLOCKED` |

一份记录只承载一个决策。如果请求包含具有不同驱动因素或生命周期的独立决策，只有在获得明确批准后才能拆分。

## 工件规则

- 如果仓库中已有 ADR 约定，则复用该约定。
- 否则使用 `docs/architecture/decisions/NNNN-<slug>.md`，并采用下一个未使用的单调递增编号。
- 永远不要重新编号、删除或改写历史记录中的决策和理由。根据以下规则，允许在限定范围内更新状态和取代关系链接；区分不断演进的拟议草稿与已接受的历史记录。
- 新记录默认设为 `Proposed`。
- 只有在获得获授权决策者的明确确认后，才能使用 `Accepted`。
- 拟议的替代记录应链接到当前决策，但不得更改其生效状态。只有在替代记录获得明确接受后，才将旧记录标记为 `Superseded`，并建立双向链接；保留历史内容。
- 保持记录足够简短，以便作为单个决策进行审阅。
- 保留未来维护者安全地重新考虑该决策所需的理由。
- 明确标记回顾性记录；不要让实施之后创建的文档看起来像是事先获得的批准。
- 将接受前所需的证据与采用后的监控要求分开。
- 优先使用稳定的仓库引用，而不是对话、分支本地链接或临时链接。

## 清单

### 1. 建立决策契约

- [ ] 明确具体决策、范围、负责人或决策者、受影响的系统，以及该选择为何具有架构意义。
- [ ] 阅读仓库说明、Git 状态和现有的决策记录规范。
- [ ] 在分配新记录之前，搜索重复、冲突、已弃用或已被取代的决策。
- [ ] 确认请求针对的是一个决策，而不是宽泛的设计或实施计划。
- [ ] 明确批准状态；未明确接受时，默认为 `Proposed`。

### 2. 收集背景与影响因素

- [ ] 以价值中立的语言陈述当前背景和问题。
- [ ] 根据现有证据提取业务驱动因素、质量属性、约束、假设和决策期限。
- [ ] 识别受影响的边界、契约、数据、安全性、运维、成本、所有权和迁移影响。
- [ ] 将当前事实与预测和偏好区分开来。
- [ ] 记录可能改变选择的矛盾或缺失证据。

### 3. 评估备选方案

- [ ] 包括现状和最简单的可信选项，除非它们已被证明不可行。
- [ ] 包括具有实质差异的备选方案，而不是只有表面差异的变体。
- [ ] 针对相同的驱动因素比较各个选项：正确性、质量目标、复杂度、可逆性、成本、运维、团队适配度和演进能力。
- [ ] 说明每个被否决的备选方案为何在当前情境下处于劣势，但不要声称其普遍更差。
- [ ] 记录敏感性或复核触发条件，说明在什么情况下被否决的选项日后可能更合适。

### 4. 记录决策

- [ ] 撰写标题、状态、日期、决策者或负责人、背景、驱动因素、考虑过的选项、决策、后果、验证方式和复核触发条件。
- [ ] 使用主动且可测试的语言陈述决策，并明确哪些事项仍有意保持未决。
- [ ] 记录正面、负面和中性的后果，以及已接受的风险。
- [ ] 通过稳定的仓库引用链接受影响的需求、设计、图表、接口、迁移文档或问题单。
- [ ] 对提议的或已接受的取代关系应用 Artifact Rules；验证链接并保留先前的理由。

### 5. 验证并报告

- [ ] 确认记录只包含一个决策，并且无需对话历史即可理解。
- [ ] 确认重要主张都有证据，或已标注为假设/未知并附有验证行动；对于回顾性记录，绝不要编造历史理由或被否决的备选方案。
- [ ] 确认未在没有明确授权的情况下指定 `Accepted`。
- [ ] 当记录和状态有效时使用 `RECORDED`；当重要背景或所需的接受授权仍未解决时使用 `INCOMPLETE`；完整且明确标记为 `Proposed` 的记录无需接受即可使用 `RECORDED`；对于范围不明确、编号不安全、所有权冲突或没有可写入目标的情况使用 `BLOCKED`。

- [ ] 识别受此决策或其取代关系影响的需求、接口和下游决策；保留已接受/已提议的区分和历史理由。

## 自检

- [ ] **返回前核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。更正报告或经授权的工件。复用有效证据；不要自动重新扫描仓库或重新运行已成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言并按以下顺序报告；保留全部五个字段，且每项事实只陈述一次。简短结果可每个字段占一行；省略空表格，且不要复制已链接的工件：

1. **结果：** 特定 Skill 的结论及有证据支持的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下特定 Skill 字段；区分事实、推论和未经验证的主张。链接工件；适用时使用表格。
4. **验证：** 检查/结果、不可获得的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或逐项列出每个 `UNPROVEN` 条目的原因、对结果的影响和确切的下一步行动；剩余风险和所需决策。

**特定 Skill 证据：** 工件路径、决策标识/状态/负责人、所选选项、备选方案、后果、证据以及验收/验证需求。报告链接或历史记录的状态变更，同时保留其理由；指出未解决的选择和审查触发条件，不得暗示某项提案已被接受。
