## 代码专属反思标准

当输出涉及代码时，还需要进行以下评估：

### 停止：库与现有解决方案检查

**在继续编写自定义代码之前：**

1. **搜索现有库**
   - [ ] 是否已在 npm/PyPI/Maven 中搜索现有解决方案？
   - [ ] 这是否是其他人已经解决的常见问题？
   - [ ] 是否正在为工具函数重复造轮子？

   **需要检查的常见领域：**
   - 日期/时间处理 → moment.js、date-fns、dayjs
   - 表单验证 → joi、yup、zod
   - HTTP 请求 → axios、fetch、got
   - 状态管理 → Redux、MobX、Zustand
   - 工具函数 → lodash、ramda、underscore

2. **现有服务/解决方案评估**
   - [ ] 是否可以通过现有服务/SaaS 处理？
   - [ ] 是否有合适的开源解决方案？
   - [ ] 使用第三方 API 是否更易于维护？

   **示例：**
   - 身份验证 → Auth0、Supabase、Firebase Auth
   - 发送电子邮件 → SendGrid、Mailgun、AWS SES
   - 文件存储 → S3、Cloudinary、Firebase Storage
   - 搜索 → Elasticsearch、Algolia、MeiliSearch
   - 队列/作业 → Bull、RabbitMQ、AWS SQS

3. **决策框架**

   ```
   IF common utility function → Use established library
   ELSE IF complex domain-specific → Check for specialized libraries
   ELSE IF infrastructure concern → Look for managed services
   ELSE → Consider custom implementation
   ```

4. **何时定制代码确实合理**
   - 领域中特有的业务逻辑
   - 具有特殊要求的性能关键路径
   - 外部依赖会显得过度使用时（例如，为了一个函数引入 lodash）
   - 需要完全控制的安全敏感代码
   - 评估后现有解决方案无法满足要求时

1. **NIH（非我发明综合征）**

## 事实核查与声明验证

### 需要立即验证的声明

1. **性能声明**
   - “这比……快 X%” → 需要进行基准测试
   - “这具有 O(n) 复杂度” → 需要进行分析证明
   - “这会减少内存使用量” → 需要进行性能分析

   **验证方法**：如果存在实际基准测试则运行；否则提供算法分析

2. **技术事实**
   - “此 API 支持……” → 查阅官方文档
   - “此框架要求……” → 根据最新文档进行验证
   - “此库版本……” → 确认版本兼容性

   **验证方法**：与官方文档交叉核对

3. **安全断言**
   - “这可以安全防御……” → 需要进行安全分析
   - “这可以防止注入……” → 需要提供证明/测试
   - “这遵循 OWASP……” → 根据相关标准进行验证

   **验证方法**：参考安全标准并进行测试

4. **最佳实践声明**
   - “最佳实践是……” → 引用权威来源
   - “行业标准是……” → 提供参考资料
   - “大多数开发者更喜欢……” → 需要数据/调查支持

   **验证方法**：引用具体来源或标准

### 评分标准

**默认分数为 2。任何向上调整都必须说明理由。**

| 分数 | 含义 | 所需证据 | 评估态度 |
|-------|---------|--------|---------------|
| 1 | 不可接受 | 明确的失败表现、缺失要求 | 很容易判定 |
| 2 | 低于平均水平 | 存在多个问题，仅部分满足要求 | 常见结果 |
| 3 | 合格 | 满足基本要求，存在小问题 | 需要证明其满足基本要求 |
| 4 | 良好 | 满足**所有**要求，仅有极少的小问题 | 需要证明其配得上这一分数 |
| 5 | 卓越 | 超出要求，真正表现出色 | **极其罕见**——需要非凡的证据 |

#### 评分分布现实检查

- **评分 5**：应在少于 5% 的评估中给出。如果你给出更多 5 分，说明你的评判过于宽松。
- **评分 4**：仅保留给真正扎实的工作。不是“相当不错”，而是真正的好。
- **评分 3**：经过完善的工作应落在这个分数段。不是平均水平。
- **评分 2**：初次尝试中很常见。不要害怕使用这个分数。
- **评分 1**：仅保留给根本性失败。但如果确实应得，也不要回避使用它。

## 迭代完善工作流

### 验证链（CoV）

1. **生成**：创建初始解决方案
2. **验证**：检查每个组成部分/主张
3. **质疑**：可能出现什么问题？
4. **重新回答**：处理已发现的问题

### 思维树（ToT）

对于复杂问题，考虑多种方法：

1. **分支 1**：当前方法
   - 优点：[列出优点]
   - 缺点：[列出缺点]

2. **分支 2**：替代方法
   - 优点：[列出优点]
   - 缺点：[列出缺点]

3. **决策**：根据以下因素选择最佳路径：
   - 简洁性
   - 可维护性
   - 性能
   - 可扩展性

## 完善触发条件

如果满足以下任一条件，自动触发完善：

1. **复杂度阈值**
   - 圈复杂度 > 10
   - 嵌套深度 > 3 层
   - 函数长度 > 50 行

2. **代码异味**
   - 重复代码块
   - 过长的参数列表（>4 个）
   - 上帝类/函数
   - 魔法数字/字符串
   - 通用工具文件夹（`utils/`、`helpers/`、`common/`）
   - NIH 综合征迹象（自定义实现标准解决方案）

3. **缺失要素**
   - 没有错误处理
   - 没有输入验证
   - 没有为复杂逻辑编写文档
   - 没有为关键功能编写测试
   - 没有针对常见问题搜索库
   - 没有考虑现有服务

4. **依赖/影响缺口**（关键）
   - 未检查依赖关系就建议删除/移除
   - 未检查是否存在取代先前决策的后续决策，就引用先前的决策
   - 未检查相关权威文档或配置，就提出配置变更（例如 `AUTHORITATIVE.yaml`）
   - 未搜索依赖方，就修改生态系统文件
   - 未通过相关的修改前门禁或检查清单，就执行任何破坏性操作
   - 未根据事实来源验证，就生成交叉引用
   - 提交包含绝对路径或用户名的文件
   - 更改计数/统计数据，却未更新引用这些数据的文档
   - 未运行验证命令，就宣布完成

5. **架构违规**
   - 在控制器/视图中编写业务逻辑
   - 领域逻辑依赖于基础设施
   - 上下文之间的边界不清晰
   - 使用通用命名，而非领域术语
