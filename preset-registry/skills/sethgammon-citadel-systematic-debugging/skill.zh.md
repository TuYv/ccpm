# /systematic-debugging — 先找根因，再修复

## 定位

**使用时机：** 根因未知、且仓促的修复屡屡失败时——强制在改动代码之前先完成 观察 -> 假设 -> 验证。
**不使用时机：** 根因已经明确（用 /marshal 实施修复）；bug 很浅显、堆栈跟踪足以定位（用 /do）。

## 协议

### 阶段 1：观察与复现

1. 阅读错误信息、堆栈跟踪或 bug 描述
2. 复现问题：
   - 如果是类型错误：运行 typecheck 并阅读完整错误信息
   - 如果是运行时错误：找出触发条件
   - 如果是行为性 bug：记录预期行为与实际行为的差异
3. 隔离出故障所在的组件/函数：
   - 哪个文件？哪个函数？哪一行？
   - 失败发生时的输入是什么？
   - 它是稳定失败还是间歇性失败？

**输出**：一份清晰的问题陈述：
"{Component} 本应执行 {Y}，实际却执行了 {X}，由 {condition} 触发"

### 阶段 2：假设与验证

1. 提出最多 3 个解释 bug 为何存在的假设：
   - H1: {most likely cause} —— 因为 {evidence}
   - H2: {second candidate} —— 因为 {evidence}
   - H3: {third candidate} —— 因为 {evidence}

2. 为每个假设定义一个验证步骤：
   - 添加 console.log / 诊断读取 / 断点
   - 在特定的位置检查特定的值
   - 此时不要改动任何逻辑——只观察

3. 运行验证：
   - 哪个假设得到了证实？
   - 哪些被排除了？
   - 如果一个都没有得到证实：利用新信息重新提出假设

**关键**：切勿跳过此阶段。切勿“直接试着修一下”。先验证。

### 阶段 3：根因分析

一旦某个假设得到证实：

1. 解释 bug 为什么会发生，而不仅仅是在哪里发生：
   - 从症状出发，反向追踪数据流直至源头
   - 找出具体的错误假设或逻辑错误
   - 记录因果链：
     “A 调用 B 时传入 X，B 假设 X > 0，但 A 在 {condition} 时传入了 -1”

2. 检查相关的同类出现：
   - 这个模式是否还在别处使用？类似的代码中是否可能存在同样的 bug？
   - 是否存在系统性问题（例如在边界处缺少校验）？

**输出**：根因陈述：
“该 bug 的成因是 {cause}。它在 {trigger} 时发生。”

### 阶段 4：实施

1. 编写一个能复现该 bug 的失败测试用例（如果存在测试框架）
2. 应用最小修复——只修改解决根因所必需的内容
3. 验证修复：
   - 测试用例现在通过
   - typecheck 通过
   - 相关功能无回归
4. 如果根因分析发现了相关的同类出现，也一并修复

## 紧急停止规则

**如果修复失败了两次：停止。**

不要尝试第三次猜测。说明根因分析是错的。要么：
- 带着新假设回到阶段 2
- 向用户询问关于系统预期行为的更多背景信息
- 检查是否存在更高层面的架构问题

连续三次修复失败，意味着你是在瞎猜，而不是在调试。

## 本技能所防止的问题

- **霰弹枪式调试**——随机乱改，直到错误消失
- **症状式修复**——在不理解原因的情况下修补输出
- **修复级联**——一个糟糕的修复制造出三个新 bug
- **隐性回归**——修好一条路径的同时破坏另一条

## 情境门控

**披露：**“正在调试 [症状]。阶段 1-3 为只读；在阶段 4 应用修复前会先确认。”
**可逆性：** amber —— 阶段 4 会对源文件应用针对性的修复；可对被修改的文件执行 `git checkout` 撤销。阶段 1-3 为只读。
**信任门控：**
- 任意级别：调查（阶段 1-3）。
- 熟悉（5+ 次会话）：应用修复（阶段 4）。

## 质量门控

- 在形成任何假设之前，已有清晰的问题陈述
- 在编写修复之前，至少有一个假设经过验证（而非仅凭臆测）
- 修复解决的是根因，而不只是症状
- 修复后 typecheck 通过，且没有新错误
- 如果发现了相关的同类出现，它们已被修复或已记录在案

## 边缘情况

**bug 为间歇性**：尽可能精确地记录触发条件。在形成假设之前至少复现一次。如果无法复现，停在阶段 1 并请求更多背景信息。

**已有两次修复尝试失败**：启用紧急停止规则。带着新假设回到阶段 2。在未重新阅读相关代码之前，不要进行第三次猜测。

**不存在测试框架**：跳过阶段 4 中“编写失败测试”这一步。手动验证修复，并记录原始 bug 的复现方法，以备将来参考。

**错误位于依赖或生成文件中**：记录根因，但不要修改依赖。改为在使用该依赖的代码中提出变通方案。
