# 分诊

通过一个由分诊角色组成的小型状态机，在项目的问题跟踪器中推进问题。

如果此仓库将外部拉取请求视为一种请求入口（请参阅问题跟踪器配置），则分诊也涵盖这些请求：**PR 是附带代码的问题**，使用相同的角色、相同的状态和相同的状态机，但存在一些差异，已在下文以“对于 PR”标出。根据跟踪器配置，将单独出现的 `#42` 解析为问题或 PR。

分诊期间发布到问题跟踪器的每条评论或每个问题，**必须**以下列免责声明开头：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写持久有效的智能体任务简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug`：某些内容出现故障
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：正在等待报告者提供更多信息
- `ready-for-agent`：已完整说明，可交由 AFK 智能体处理
- `ready-for-human`：需要由人工实现
- `wontfix`：不会采取行动

对于 PR，相同的状态应结合其附带的代码来理解：`ready-for-agent` 表示已附上任务简报，智能体应对差异内容执行下一步操作；`ready-for-human` 表示已准备好由人工合并。

每个经过分诊的问题都应恰好带有一个类别角色和一个状态角色。如果状态角色发生冲突，请标记该情况，并在执行任何其他操作之前询问维护者。

这些是规范的角色名称。问题跟踪器中实际使用的标签字符串可能不同。你应已获得相关映射。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

状态转换：未加标签的问题通常会先进入 `needs-triage`；之后再转入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 会返回 `needs-triage`。维护者可随时覆盖状态；如果状态转换看起来不寻常，请标记并在继续之前询问。

## 调用

维护者调用 `/triage`，并用自然语言描述他们的需求。理解该请求并执行操作。示例：

- “向我展示所有需要我关注的内容”
- “让我们看看 #42”（问题或 PR）
- “将 #42 移至 ready-for-agent”
- “有哪些内容已准备好供智能体接手？”

## 显示需要关注的内容

查询问题跟踪器，并按最早优先的顺序展示以下三个分组：

1. **未加标签**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **自上次分诊备注以来报告者有新活动的 `needs-info`**：需要重新评估。

当 PR 属于分诊范围时，在这些分组中包含外部 PR，并在每行标记 `[PR]` 或 `[issue]`。发现流程仅显示*外部* PR（跟踪器配置定义了哪些人属于外部人员），因此协作者正在处理的 PR 不属于分诊工作。此筛选器仅用于发现；无论作者是谁，明确指定的 PR 始终都要进行分诊。

显示数量以及每个项目的一行摘要。让维护者进行选择。

## 对特定 issue 或 PR 进行分类处置

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还要阅读 diff）。解析此前的所有分类处置备注，避免重复询问已经解决的问题。使用项目的领域术语表探索代码库，并遵循相关区域中的 ADR。针对代码库执行两项检查：(a) **冗余性**：按领域概念（而不只是请求中的措辞）搜索所请求行为的现有实现，并报告搜索过的位置。如果找到，则属于已经实现的 `wontfix`（第 5 步）。(b) **先前拒绝记录**：阅读 `.out-of-scope/*.md`，并指出其中与此请求相似的内容。

2. **提出建议。** 告知维护者你建议的类别和状态，并说明理由，同时简要总结与该请求相关的代码库情况（包括它是否已实现）。等待进一步指示。

3. **验证主张。** 在进行任何深入追问之前，先检查相关主张是否成立。对于 bug，根据报告者提供的步骤进行复现。对于 PR，确认 diff 是否实现了其声称的功能：检出该 PR，并运行相关测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是一个强烈的 `needs-info` 信号）。经过确认的验证可以形成说服力更强的代理简报。

4. **深入追问（如有必要）。** 如果请求需要进一步完善，请调用 Skill 工具两次，分别用于 "grilling" 和 "domain-modeling"，并逐轮提出问题以使其成形，同时明确领域术语，并在决策确定后即时更新 `CONTEXT.md`/ADR。

5. **应用处理结果：**
   - `ready-for-agent`：发布代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：使用与代理简报相同的结构，但注明无法委派的原因（需要判断、外部访问、设计决策、手动测试）。
   - `needs-info`：发布分类处置备注（模板如下）。
   - 对于 `wontfix`，关闭 issue，评论内容取决于具体的*原因*：
     - **已经实现**：所请求的变更已存在于代码库中。指出其所在位置；**不要**写入 `.out-of-scope/`（该知识库用于记录*被拒绝的*请求，而不是已经构建的功能）。
     - **已拒绝（bug）**：礼貌地解释原因，然后关闭。
     - **已拒绝（增强功能）**：写入 `.out-of-scope/`，在评论中链接到该记录，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如果已有部分进展，可以选择添加评论。

## 快速状态覆盖

如果维护者说“将 #42 移至 ready-for-agent”，请信任他们并直接应用该角色。先确认你将要执行的操作（角色变更、评论、关闭），然后执行。跳过深入追问。如果未经过深入追问会话就移至 `ready-for-agent`，请询问他们是否希望编写代理简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

将深入追问期间解决的所有事项记录在 "established so far" 下，以免丢失相关工作成果。问题必须具体且可执行，而不能只是“请提供更多信息”。

## 恢复之前的会话

如果 issue 或 PR 中已有先前的分类处理备注，请先阅读这些备注，检查报告者是否已回答任何尚未解决的问题，并在继续之前说明最新情况。不要重复询问已经解决的问题。
