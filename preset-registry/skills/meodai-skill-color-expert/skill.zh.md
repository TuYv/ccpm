# 色彩专家

一个面向色彩相关工作的综合知识库。有关 140 多个详细参考文件，请参阅 `references/INDEX.md`；本技能文件包含可直接回答大多数问题所需的核心知识。

## 如何使用本技能

根据用户的明确请求以及从上下文中清晰推断出的约束来调整回答。常见模式有五种：

**具体的设计或艺术项目**——“帮我为徽标 / 海报 / 插画 / 应用选择颜色。”询问媒介（印刷、屏幕、颜料、混合媒介）、品牌或氛围、受众、无障碍需求，以及是否有任何需要与之协调的现有颜色。然后提出方案。除非用户询问，否则不要讲授 CIE 1931 或 OKLCH 的内部原理。推荐符合约束条件的具体工具和调色板，而不是泛泛的理论。

**设计系统、色阶或主题令牌**——“为我构建一个 9 级强调色色阶”“适用于浅色 + 深色模式的调色板”“Tailwind/Radix 风格的色阶”“什么样的灰色色阶适合我们的品牌？”按以下优先顺序处理：

- 使用 OKLCH 构建感知均匀的色阶（不同色相之间的明度保持一致，避免浑浊的中间色调）。
- 构建令牌图：引用令牌（调色板）→ 语义令牌（表面、表面上的内容、强调色、成功、警告、危险）→ 组件用法；参见下方的*实施指南*。
- 在浅色和深色模式下，使用 APCA 或 WCAG 验证每一组文本/背景配色。
- 仅在需要时推荐工具：Huetone（LCH/OKLCH 构建器）、Leonardo（由对比度驱动的色阶 + 自适应主题，Adobe）、Components.ai Color Scale（参数化）、dittoTones（从 Tailwind/Radix 中提取感知特征）、Color Buddy（检查）。对于专门用于数据可视化的顺序色阶/发散色阶，则使用 CuspHanger（OKLCH 中的 Wijffelaars 模型，在构建时即保证处于色域内）或 viscm（viridis 编辑器：拖动控制点时提供实时感知导数诊断 + CVD + 灰度预览）。

检验顺序色阶的标准是**平坦的感知导数**——绘制相邻样本之间的感知步长；无论在彩色还是灰度下，它都应该是一条水平线。凸起表示色阶夸大了数据中并不存在的变化；这正是 jet 的核心缺陷，而不只是因为它难看。

**生成艺术 / 创意编程**——“为我的 fxhash 作品配色”“为数千条生成的笔触设计调色板”“在 p5.js / WebGL 中实现颜料般的混色。”这不同于构建调色板生成器：代码*就是*艺术作品，而用户希望理解的是*技术*，不是复制某位知名艺术家的风格。帮助他们构建自己的系统。适合教授和组合使用的技术包括：

- **严格约束，而后变化**——在较窄的明度或色度范围内选择 3–7 种色相；多样性来自密度和交互，而不是调色板的大小。
- **加权 / 基于概率的色相选择**——为每种颜色分配权重，使某些颜色频繁出现，而另一些颜色很少出现；这会让生成结果显得经过精心编排，而不是随机产生。
- **窄带色相抖动**——在固定范围内添加较小的随机色相偏移，使笔触看起来彼此关联但又不完全相同。
- **固定色度下的明度变化**——在不失去调色板特征的情况下营造深度和氛围（使用 OKLCH）。
- **光谱 / K-M 混色**（Spectral.js、Mixbox），用于实现颜料般的重叠和次生色；在相同情况下，RGB 平均会产生浑浊、暗淡的结果。
- **IQ 余弦调色板**——使用 `a + b·cos(2π(c·t + d))`，通过 12 个浮点数生成循环 / 周期配色方案。
- **基于锚点的插值**（Poline）——在 OKLCH 中设置 2–3 个锚点，得到插值色阶。
- **带缓动的色相 / 明度 / 色度轨迹**（RampenSau）——让每个轴沿缓动函数变化，与色彩空间无关；当你希望获得确定性的色阶形状，而不是随机锚点时，这种方法非常适合。
- **能够避开浑浊区域的和谐感知生成**（pro-color-harmonies）——采用自适应 OKLCH 色彩和谐规则，提供 4 种样式 × 4 种修饰方式；自动跳过感知上浑浊的区域。
- **在历史 / 非数字色彩空间中生成**（RYBitten）——当你希望获得严格的 sRGB/OKLCH 无法实现的绘画感时，可以在 RYB 或 26 种历史色彩立方体之一中进行创作。
- **场景光照采样**（ray-color）——在一个带有最多 3 个彩色光源的房间中对球体进行光线追踪，并从其表面采样颜色；一致性来自共享的照明物理规律（就像在同一光源下拍摄的物体），而不是色彩空间几何关系。

参见 `references/techniques/` 中的 tyler-hobbs、fontana、mattdesl、iq-cosine、spectraljs、poline、rampensau、pro-color-harmonies、rybitten、ray-color（这些文档记录的是技术方法，而不是要模仿的风格）。

**一般颜色问题**——“什么是 OKLCH？”、“为什么我的渐变中间会变灰？”、“APCA 比 WCAG 更好吗？”直接根据此技能文件或 `references/INDEX.md` 回答，并引用相关参考资料。除非用户询问如何实现某项操作，否则无需介绍工具。

**构建生成器、工具或调色板算法**——“我想制作一个调色板生成器”、“如何生成无障碍色阶？”、“给我一个 OKLCH 渐变函数。”默认优先推荐现有库，而不是从头实现（Culori、Poline、RampenSau、Spectral.js——参见“推荐工具”）。使用用户的技术栈给出可运行的代码，并根据上表选择色彩空间。

当用户要求生成或比较调色板时，**先展示多种方法及其权衡，再收敛到其中一种**——基于锚点（Poline）、色相循环（RampenSau）、余弦（IQ 公式）、基于色彩和谐（pro-color-harmonies）、场景光照（ray-color）以及从系统中提取（dittoTones）的方法分别适用于不同问题。应积极提供多种选项。

绝不要推荐 coolors.co——它并不会生成调色板，而只是从包含 7,821 个预制调色板的硬编码列表中进行选择（参见“推荐工具”）。

## 色彩空间——何时使用哪一种

| 任务                            | 使用                                    | 原因                                                                       |
| ------------------------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| 感知均匀的颜色处理   | **OKLCH**                              | 在明度、色度和色相方面具有最佳均匀性。修正了 CIELAB 的蓝色问题。  |
| CSS 渐变与调色板        | **OKLCH** 或 `color-mix(in oklab)`     | 不会像 RGB/HSL 那样导致渐变中段变暗                                    |
| 感知色域的颜色选取       | **OKHSL / OKHSV**                      | Ottosson 的拾色器色彩空间——像 HSL 一样采用圆柱坐标，但以感知特性为基础 |
| 归一化饱和度（0-100%）  | **HSLuv**                              | 按色相/明度对 CIELUV 色度进行归一化。柔和色可使用 HPLuv。            |
| 印刷工作流                 | **CIELAB D50**                         | ICC 标准光源                                                   |
| 屏幕工作流                | **CIELAB D65** 或 OKLAB                | D65 = 屏幕标准                                                     |
| 跨媒介外观匹配 | **CAM16 / CIECAM02**                   | 将环境、适应、亮度和观察条件纳入考量      |
| HDR                             | **Jzazbz / ICtCp**                     | 专为扩展动态范围设计                                       |
| 颜料/涂料混合模拟 | **Kubelka-Munk**（Spectral.js、Mixbox） | 光谱反射率混合，而非 RGB 平均                            |
| 色差（精确）    | **CIEDE2000**                          | 感知距离的黄金标准                                         |
| 色差（快速）         | **OKLAB 中的欧几里得距离**                 | 对大多数应用而言已足够                                         |
| 视频/图像压缩         | **YCbCr**                              | 亮度与色度分离，可实现色度子采样                         |
| 色图均匀性             | **CAM02-UCS**（或 OKLAB）               | CIELAB 对于*距离较远*的颜色表现尚可，但对于*相近*颜色表现不佳——而均匀采样恰恰依赖于后者。MATLAB 的 parula 在 Lab 中被设计为均匀色图，但结果是在底部附近出现了一条明显的色带 |

### 理解 HSL 的局限性

HSL 并不“差”——它只是将 RGB 以一种简单、快速的几何方式重新排列到一个圆柱体中。它适合用于快速选色和基础 UI 工作。但它的三个通道与人类感知并不对应：

- **明度（L）：**完全饱和的黄色（`hsl(60,100%,50%)`）和完全饱和的蓝色（`hsl(240,100%,50%)`）具有相同的 L=50%，但感知亮度却相差巨大。L 是数学平均值，而不是感知测量值。
- **色相（H）：**间距并不均匀。在红色附近偏移 20° 会产生显著变化；而在绿色附近同样偏移 20°，变化却几乎不可见。绿色区域被压缩，红色区域被拉伸。
- **饱和度（S）：**与感知饱和度并不相关。一种颜色即使 S=100%，看起来仍可能很暗淡（例如深色的饱和蓝色）。

**适合使用 HSL 的情况：**简单的颜色选择器、快速调整 CSS，以及不重视感知准确性的场景。如果不适合使用 HSL，上表针对每项任务给出了相应的感知替代方案（色阶使用 OKLCH，渐变使用 OKLAB，选色使用 OKHSL，归一化饱和度使用 HSLuv）。

### 关键区别

- **色度** = 相对于相同明度的中性参考色的色彩丰富程度
- **饱和度** = 相对于颜色自身亮度的感知色彩丰富程度
- **明度** = 相对于在类似照明条件下白色的感知反射率
- **亮度** = 对刺激源所发出光线强度的感知
- 相同色度 ≠ 相同饱和度。它们是不同的维度。

### 实践中的色域映射

使用 OKLCH 时最常见的错误是：选择目标色域中不存在的色度。`oklch(70% 0.3 150)` 所要求的色度超出了 sRGB（甚至 P3）能够显示的范围，因此它会被静默裁剪——通常会变得更暗淡并发生色相偏移。

- **CSS 会为你执行色域映射。**浏览器会自动映射 `oklch()` / `color()`，因此编写的 CSS 很少会出现严重裁剪。JS 转换则**不会**——`oklch→hex` 只会截断通道值。
- **降低色度，而不是明度或色相。**裁剪 R/G/B 会导致色相偏移；将色度拉回色域边界则能保留颜色的特征。请使用 Culori 的 `clampChroma(color, 'oklch')`（保持 L 和 H 不变）或 `toGamut()`，而不要直接裁剪 RGB。
- **针对实际目标进行测试：**`inGamut('rgb')` 与 `inGamut('p3')`——在 P3 中有效的颜色，在 sRGB 中仍可能被裁剪。
- **或者从构造方式上避免该问题：**nutelch 使用*相对于色域边界*的方式表示色度（`relC: 0.5` = 位于该 L/H 下到色域外壳距离的一半），因此生成的颜色不会意外请求不存在的色度。

## 实现指南 — 代码与 CSS

在程序或 CSS 中使用颜色时，应在原始颜色值与 UI 角色之间添加一个语义层。

以下示例是伪代码，而不是字面意义上的 CSS 要求。它们表达的是智能体应保留的决策结构，即使目标技术栈使用不同的语法也是如此。

无论使用 CSS、JS/TS、Swift、设计令牌 JSON、模板还是伪代码，默认都应采用相同的结构：

- 用于表示具体颜色的**引用令牌/调色板值**
- 将含义映射到这些颜色的**语义令牌/角色**
- 使用语义令牌而非原始字面量的**组件用法**

原始颜色字面量通常应仅出现在调色板/引用定义、转换、诊断或刻意设计的一次性示例中。

- **使用引用令牌表示具体颜色**：`ref.red = #f00`
- **使用语义令牌表示含义/角色**：`semantic.warning = ref.red`
- **优先在组件中使用语义令牌**，这样主题便可以替换含义，而无须重写组件代码。
- **这一默认原则适用于任何语言**；应转换为目标系统中等效的别名/引用机制（CSS 自定义属性、Swift 枚举、设计令牌 JSON 等）。
- **尽可能将颜色决策编码为规则**，而不是将某个人工选择固化为字面量。

伪代码示例：

- `ref.red := closest('red', generatedPalette)`
- `semantic.warning := ref.red`
- `semantic.onSurface := mostReadableOn(surface)`

良好模式：调色板/引用令牌定义可用颜色；语义令牌则将这些颜色映射到表面、文本、强调色、成功、警告和危险等角色。

如果系统可以根据约束推导出某项决策，就应将这种推导编码为规则。例如：在生成的调色板中选择最接近的命名色相；根据 APCA/WCAG 目标选择前景色；在 OKLCH 中基于基础令牌计算悬停状态，而不是手动挑选另一个毫不相关的十六进制颜色。

**尤其是在将生成的颜色应用于 UI 时**：生成器提供的是基础元素，但将这些元素*映射*到角色的方式，才是设计逐渐腐化的根源。不要将某次人工映射固化为字面量——应输出规则。以下是一组实用的决策词汇（来自 Design Book，见下文）：

- `text := bestContrastWith(surface, palette)` — 当调色板重新生成时重新计算
- `accent := mostVivid(palette, { against: surface, minContrast: 4.5, not: [error, success] })` — 在可读性约束下选择鲜艳度，并排除为特定角色保留的令牌
- `surface := nth(ramp, 0)`, `text := nth(ramp, -1)` — 将色阶角色固定到*位置*，因此即使使用不同的色阶节点数量重新生成色阶，这些角色仍能保持不变
- `hover := colorMix(accent, ink, 0.12)` 或自适应的 `shade(surface)` — 根据输入颜色的明度切换变暗/变亮方向，因此在深色主题中绝不会失效

在 CSS 中，许多决策都可以保持为原生形式（由浏览器重新执行）：使用 `var()` 进行引用，使用 `color-mix()` 生成悬停状态，使用相对颜色语法编辑通道——请参阅下方的速查表。

对于较大的系统，相比扁平化的令牌堆积，应优先采用**令牌图**：其中包含引用、语义角色、派生函数和作用域继承。这使主题变更、无障碍保证和多平台导出更易于审计和维护。**Design Book**（`npm install design-book`）是参考实现：它是一个响应式约束系统，其中令牌存储的是*如何选择值*，依赖项会在发生变更时重新计算，而 `inspect()` 会解释某个值胜出的原因；它可渲染为 CSS 变量、JSON 和 W3 设计令牌。请参阅 `references/techniques/designbook-reactive-design-token-spec.md`。

## CSS Color 4/5 — 语法速查表

现代 CSS 原生支持感知色彩；在引入 JS 库之前，应优先使用这些功能。

- **感知色彩：** `oklch(70% 0.12 250)`、`oklab(0.7 -0.1 0.1)`，以及通过 `color(display-p3 1 0.2 0.3)` 使用广色域。
- **混色：** `color-mix(in oklab, blue 30%, white)` — 在 `oklab`/`oklch` 中插值，可避免 RGB/HSL 产生的渐变中段发灰问题。对于柱面色彩空间，应设置色相策略：`color-mix(in oklch longer hue, …)`。
- **相对颜色语法（从基础颜色派生）：** `oklch(from var(--brand) l c h / 0.5)`，也可以在不额外硬编码第二个十六进制颜色的情况下计算阴影色/悬停色：`oklch(from var(--brand) calc(l * 0.9) c h)`。
- **无需媒体查询的亮色/暗色：** `light-dark(white, black)`（需要 `color-scheme: light dark`）。
- **色域定位：** `@media (color-gamut: p3) { … }`。
- **在指定色彩空间中创建渐变：** `linear-gradient(in oklch, red, blue)`。

常青浏览器（2024 年及以后版本）已广泛支持；相对颜色语法是其中最新的部分。有关边缘情况，请参阅 `references/techniques/` 中的 CSS Color 4/5。

## 无障碍 — 关键数字

在约 281 万亿种十六进制颜色组合中（研究者为 @mrmrs\_，通过 Rust 暴力运行计算）：

| 阈值                      | 通过比例  | 概率             |
| ------------------------- | --------- | ---------------- |
| WCAG 3:1（大号文本）      | 26.49%    | 约四分之一       |
| WCAG 4.5:1（AA 正文文本） | 11.98%    | 约八分之一       |
| WCAG 7:1（AAA）           | 3.64%     | 约二十七分之一   |
| APCA 60                   | 7.33%     | 约十四分之一     |
| APCA 75（流畅阅读）       | 1.57%     | 约六十四分之一   |
| APCA 90（正文首选）       | **0.08%** | **约 1/1,250**   |

在可读性相当的情况下，APCA 的限制远比 WCAG 严格。在 APCA 90 下，281 万亿种组合中只有 2390 亿种可用。JPEG 压缩利用了相同的生物学原理：色度子采样（颜色数据减少 4 倍）无法被察觉，因为人类视觉对亮度的分辨率高于对颜色的分辨率。

**图表 — 边框技巧。** WCAG 要求相邻非文本元素之间达到 3:1。找到三种彼此之间均能保持 3:1 的图表颜色极其困难；超过三种实际上就不可能了。不要尝试这样做。为图表元素添加**边框**，并要求每种填充色与边框颜色之间达到 3:1 — 每种颜色只需满足一个约束，而不是 N² 个约束。（Ström，参见 `references/techniques/strom-least-wrong-colors-simulated-annealing.md`。）

## 色彩和谐 — 真正有效的方法

### 色相优先的和谐法则作为独立启发式方法并不可靠

互补色、三角色和四角色间隔本身并不能有效预测情绪、易读性或无障碍性。每个色相平面在感知空间中的形状都不同，因此几何色相间隔并不能保证感知上的平衡。

### 特征优先的和谐法则有效（Ellen Divers 的研究）

按特征（浅淡/柔和/深沉/鲜艳/暗色）而非色相来组织。研究发现：**与色度和明度相比，色相通常较难预测情绪反应** — 柔和的调色板在多种色相下通常都会给人平静的感觉。轻松与强烈的感受更多由色度和明度驱动，而非仅由色相决定。

### 易读性 = 明度变化

灰度模式可以快速合理地检查明度区分，但不能作为符合无障碍要求的证明。你仍需使用 WCAG/APCA 验证对比度，并考虑文字大小、字重、极性和 CVD。相同色相 + 不同明度通常更易读。无论色相如何都采用相同明度，通常会难以辨认。

### 60-30-10 法则

60% 主色、30% 辅色、10% 强调色。让一种颜色占据主导地位，避免出现“三只体型相同的大猩猩打架”的局面。

## 颜料混合——并非如你所想

- **仅靠简单的减色模型无法很好地描述颜料混合**——“综合混合”（Küppers/Briggs）是更实用的描述。其表现类似于减色混合与加色平均之间的折中。
- **CMY 混合路径向外弯曲**（保留彩度 = 鲜艳的间色）——“外向型章鱼”
- **RGB 混合路径向内弯曲**（损失彩度 = 暗淡的棕色）——“内向型章鱼”
- **混合是非线性的**：颜料比例 ≠ 色相变化比例。在某些配比下，你会“突然转弯”。
- **蓝色→黄色是一段漫长的路**，红色→黄色则很短。传统色轮严重歪曲了这些距离。
- **着色力各不相同**：蓝色颜料浓度高、着色力强，黄色颜料则较弱。
- **白色不只是让颜色变亮**——它还会改变色相并降低彩度。
- **在代码中进行光谱/K-M 混合**：使用 Spectral.js（开源）或 Mixbox（商业）。

## 色温

- **色温 ≠ 色相**——它是色相和饱和度的系统性偏移，且取决于起始色相
- **光谱偏向**：光源偏向光谱的哪一端（短 λ = 冷，长 λ = 暖）
- **冷色日光**：蓝色的大气散射会填充阴影；绘制中性高光和蓝色阴影
- **暖色白炽光**：偏向包括红外线在内的长波长（其热量可以被直接感受到）
- **绿色和紫色**无法像红橙色或蓝青色那样明确对应冷暖；感知到的色温在很大程度上取决于上下文

## 历史纠正

- **Moses Harris（1769）**是首位将 RYB 以相等的 120° 间隔排列的人——Newton、Boutet 和 Schiffermüller 都没有这样做。他自己的色轮需要第 4 种颜料。这是错误色彩理论的起源。
- **Von Bezold（1874）**否定了将“靛蓝”视为光谱色——Newton 的“蓝色”≈现代的青色，Newton 的“靛蓝”≈现代的蓝色。
- **“magenta”一词**直到 1907 年（Carl Gustav Zander）才被用于指代减法混色的原色。此前使用的是：“粉色”（Benson，1868）、“深红色”、“紫色”。
- **Amy Sawyer（1911）**为 CMY 色轮（樱草黄/玫瑰红/绿松石色）申请了专利，比它成为主流早了数十年。
- **Elizabeth Lewis（1931）**在一个色轮上将三色视觉理论与对立过程理论结合起来，比 CIE Lab 早了 30 年。

### 调色板生成（真正的算法，而非预制色板）

注意：coolors.co 并不会生成调色板——它只是从其 JS 包中硬编码的 7,821 个预制调色板里随机挑选。

- **RampenSau**——色相循环 + 缓动，与色彩空间无关
- **CuspHanger**——以 OKLCH 实现的 Wijffelaars 2009 EuroVis 调色板模型：贝塞尔路径穿过每种色相的黑色–尖点–白色色域三角形，并采用根据 Brewer 校准的感知明度采样。为数据可视化生成顺序型/发散型渐变，天然保证位于色域内，支持 sRGB + Display-P3，提供与 RampenSau 兼容的 API；`fromColor()` 对模型进行逆向求解，使渐变精确经过已有颜色（品牌色 → 数据可视化渐变）
- **Poline**——锚点 + 每个轴的位置函数（1.2K 个星标）；附带用于交互式控制的 `<poline-palette>` Web 组件
- **pro-color-harmonies**——自适应 OKLCH 色彩和谐，避开浑浊区域，4 种样式 × 4 种修饰方式
- **dittoTones**——提取 Tailwind/Radix 的“感知 DNA”，并将其应用到你的色相
- **FarbVelo**——具有从暗到亮结构的随机调色板
- **ray-color**——从光线追踪场景生成调色板（“编辑条件，而不是颜色”）：球体 + 五面房间 + 最多 3 盏彩色灯，镜面墙作为虚拟光源；从表面采样测地线/圆。确定性、线性 RGB 着色、零依赖、约 6 kB、无 DOM，可用于无头环境；提供支持拖拽灯光以及导出 PNG/代码的交互式实验场

- **category-colors**（Ström）——采用*优化器*方法，而非构造式模型：编写加权损失函数（与品牌参考色的相似度 + ΔE 间隔 + 各色觉缺陷类型下的 CVD 间隔），然后让模拟退火进行搜索。最适合各项标准相互冲突且无法通过色彩空间几何表达的情况；权重将成为明确、可审计的设计决策。`npx categorycolors run`；可插拔评估器（能量、范围、JND、相似度、WCAG 对比度、避开指定颜色、显著性），支持按通道锁定，使品牌色相保持不变而明度/饱和度可以调整；还可使用 `categorycolors report` 审计任何现有调色板，检查模拟 CVD 下的 JND 冲突。Node + Culori，MIT

### 颜色排序

将任意一组颜色排列成感知上平滑的序列，**不存在唯一正确的线性顺序** — 颜色是三维的，因此任何一维排序都是一条穿过三维空间的*路径*，与旅行商问题密切相关。简单的排序方法会以可预测的方式失败：仅按色相排序会混杂明暗颜色；仅按明度排序会将不同色相挤在一起；对打包的 RGB/HSL 值使用 `.sort()` 会产生突兀且毫无意义的跳变。不要自行实现单通道排序。

- **colorsort-js** (darosh) — 对颜色进行排序时可靠的默认选择。它将此问题视为寻找最平滑路径的问题（最近邻/TSP 风格），在感知空间中使用定量平滑度指标；okpalette.color.pizza 和 FarbVelo 均由其驱动。几乎所有“将这些颜色按合理顺序排列”的场景都可以使用它 — 调色板展示、色样面板、生成式输出、从图像中提取的调色板。参见 `references/techniques/colorsort-js.md`。
