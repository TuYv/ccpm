## 强制准备

调用 /impeccable——其中包含设计原则、反模式以及**上下文收集协议**。在继续之前遵循该协议——如果尚不存在设计上下文，则必须先运行 /impeccable teach。此外还需了解：质量标准（MVP 还是旗舰级）。

进行细致入微的最终检查，找出所有让优秀作品迈向卓越的微小细节。这正是已交付与精雕细琢之间的区别。

## 设计系统探索

在进行打磨之前，先了解你要遵循的系统：

1. **找到设计系统**：搜索设计系统文档、组件库、样式指南或 token 定义。研究核心模式：颜色 token、间距尺度、排版样式、组件 API。
2. **记录约定**：共享组件如何导入？使用什么间距尺度？哪些颜色来自 token，哪些是硬编码值？已经建立了哪些动效和交互模式？
3. **识别偏差**：目标功能在哪些地方偏离了系统？哪些硬编码值应改用 token，哪些自定义组件与共享组件重复，哪些间距不符合既定尺度。

如果存在设计系统，打磨工作应使该功能与其保持一致。如果不存在，则应根据代码库中可见的约定进行打磨。

## 打磨前评估

了解当前状态和目标：

1. **检查完整性**：
   - 功能是否完整？
   - 是否存在需要保留的已知问题（用 TODOs 标记）？
   - 质量标准是什么？（MVP 还是旗舰级功能？）
   - 何时发布？（有多少时间用于打磨？）

2. **确定打磨领域**：
   - 视觉不一致
   - 间距和对齐问题
   - 交互状态缺失
   - 文案不一致
   - 边界情况和错误状态
   - 加载与过渡的流畅度

**关键要求**：打磨是最后一步，而不是第一步。不要打磨功能尚未完成的工作。

## 系统化打磨

有条不紊地逐项处理以下方面：

### 视觉对齐与间距

- **像素级精确对齐**：所有内容均与网格对齐
- **一致的间距**：所有间隔都使用间距尺度（不要出现随意设置的 13px 间隔）
- **视觉对齐**：根据视觉重量进行调整（图标可能需要偏移才能实现视觉居中）
- **响应式一致性**：间距和对齐在所有断点下都能正常呈现
- **遵循网格**：元素与基线网格对齐

**检查**：
- 启用网格叠加层并验证对齐情况
- 使用浏览器检查器检查间距
- 在多个视口尺寸下进行测试
- 查找那些“感觉”不对的元素

### 排版优化

- **层级一致性**：相同元素在各处使用相同的字号和字重
- **行长**：正文文本每行 45-75 个字符
- **行高**：与字号和上下文相适应
- **孤行与寡行**：最后一行不能只有一个单词
- **断词**：适合所用语言和栏宽
- **字距调整**：在需要时调整字母间距（尤其是标题）
- **字体加载**：不出现 FOUT/FOIT 闪烁

### 颜色与对比度

- **对比度**：所有文本均符合 WCAG 标准
- **设计令牌使用一致**：不使用硬编码颜色，全部使用设计令牌
- **主题一致性**：适用于所有主题变体
- **颜色含义**：相同颜色在各处表达相同含义
- **无障碍焦点**：焦点指示器清晰可见，并具有足够的对比度
- **带色调的中性色**：不使用纯灰或纯黑——添加细微的色彩倾向（0.01 色度）
- **彩色背景上的灰色**：切勿在彩色背景上使用灰色文本——应使用该颜色的某种明暗色调或透明度

### 交互状态

每个交互元素都需要具备所有状态：

- **默认**：静止状态
- **悬停**：细微反馈（颜色、缩放、阴影）
- **焦点**：键盘焦点指示器（绝不能在没有替代方案的情况下移除）
- **激活**：点击/轻触反馈
- **禁用**：明确表示不可交互
- **加载**：异步操作反馈
- **错误**：验证或错误状态
- **成功**：成功完成

**缺少状态会造成困惑和体验缺失**。

### 微交互与过渡

- **平滑过渡**：所有状态变化均应采用适当的动画（150-300ms）
- **一致的缓动**：使用 ease-out-quart/quint/expo 实现自然减速。切勿使用弹跳或弹性效果——它们会显得过时。
- **无卡顿**：动画达到 60fps，仅对 transform 和 opacity 应用动画
- **恰当的动效**：动效应服务于功能，而非装饰
- **减少动态效果**：遵循 `prefers-reduced-motion`

### 内容与文案

- **术语一致**：相同事物在各处使用相同名称
- **大小写一致**：一致应用标题式大小写或句式大小写
- **语法与拼写**：无拼写错误
- **长度恰当**：既不过于冗长，也不过于简略
- **标点一致**：句子使用句号，标签不使用句号（除非所有标签都使用）

### 图标与图像

- **风格一致**：所有图标来自同一系列或采用相匹配的风格
- **尺寸恰当**：图标尺寸与使用场景保持一致
- **正确对齐**：图标与相邻文本在视觉上对齐
- **替代文本**：所有图像都有描述性的替代文本
- **加载状态**：图像不会导致布局偏移，并具有正确的宽高比
- **Retina 支持**：为高 DPI 屏幕提供 2x 资源

### 表单与输入项

- **标签一致**：所有输入项均有正确的标签
- **必填指示**：清晰且一致
- **错误消息**：有帮助且一致
- **Tab 顺序**：键盘导航顺序符合逻辑
- **自动聚焦**：适当使用（不要过度使用）
- **验证时机**：保持一致（失去焦点时与提交时）

### 边界情况与错误状态

- **加载状态**：所有异步操作都有加载反馈
- **空状态**：提供有帮助的空状态，而非仅显示空白区域
- **错误状态**：提供清晰的错误消息和恢复路径
- **成功状态**：确认操作已成功完成
- **长内容**：能够处理很长的名称、描述等
- **无内容**：能够妥善处理数据缺失
- **离线**：提供适当的离线处理（如适用）

### 响应式设计

- **所有断点**：测试移动端、平板端和桌面端
- **触控目标**：触控设备上最小为 44x44px
- **文本可读性**：移动端文本不得小于 14px
- **无水平滚动**：内容适应视口
- **合理重排**：内容以符合逻辑的方式自适应

### 性能

- **快速初始加载**：优化关键路径
- **无布局偏移**：元素不会在加载后跳动（CLS）
- **流畅交互**：无延迟或卡顿
- **优化图片**：使用适当的格式和尺寸
- **延迟加载**：屏幕外内容采用延迟加载

### 代码质量

- **移除控制台日志**：生产环境中不保留调试日志
- **移除注释代码**：清理无效代码
- **移除未使用的导入**：清理未使用的依赖项
- **统一命名**：变量和函数遵循约定
- **类型安全**：不使用 TypeScript `any`，也不忽略错误
- **无障碍性**：使用恰当的 ARIA 标签和语义化 HTML

## 打磨检查清单

逐项系统检查：

- [ ] 在所有断点下实现完美的视觉对齐
- [ ] 间距始终使用设计令牌
- [ ] 字体层级保持一致
- [ ] 实现所有交互状态
- [ ] 所有过渡都流畅（60fps）
- [ ] 文案一致且经过精心打磨
- [ ] 图标风格一致且尺寸恰当
- [ ] 所有表单均正确添加标签并进行验证
- [ ] 错误状态能够提供有效帮助
- [ ] 加载状态清晰明确
- [ ] 空状态友好亲切
- [ ] 触控目标最小为 44x44px
- [ ] 对比度符合 WCAG AA 标准
- [ ] 键盘导航正常工作
- [ ] 焦点指示器清晰可见
- [ ] 控制台中没有错误或警告
- [ ] 加载时无布局偏移
- [ ] 能在所有受支持的浏览器中正常运行
- [ ] 尊重减少动态效果的偏好设置
- [ ] 代码整洁（无 TODO、console.logs、注释代码）

**重要**：打磨的关键在于细节。放大查看。眯起眼睛审视。亲自使用。细微之处积少成多。

**绝不要**：
- 在功能完整之前进行打磨
- 如果 30 分钟内就要发布，不要花数小时打磨（合理取舍）
- 在打磨过程中引入缺陷（充分测试）
- 忽视系统性问题（如果所有地方的间距都有问题，就修复整个系统）
- 只把一处做到完美，却让其他地方保持粗糙（确保质量水平一致）
- 在设计系统中已有等效组件时创建新的一次性组件
- 对本应使用设计令牌的值进行硬编码

## 最终验证

在标记为完成之前：

- **亲自使用**：实际与该功能进行交互
- **在真实设备上测试**：不要只使用浏览器 DevTools
- **请其他人评审**：新的视角更容易发现问题
- **与设计稿对比**：确保符合预期设计
- **检查所有状态**：不要只测试理想路径

## 清理

完成打磨后，确保代码质量：

- **替换自定义实现**：如果你重新实现了设计系统已有的组件，请改用共享版本。
- **移除孤立代码**：删除因打磨而过时的未使用样式、组件或文件。
- **整合令牌**：如果引入了新值，请检查它们是否应当定义为令牌。
- **验证 DRY 原则**：查找打磨过程中引入的重复内容并进行整合。

请记住：你拥有无可挑剔的细节把控力和卓越的品味。持续打磨，直到一切显得毫不费力、意图明确且运行完美。精雕细节——它们至关重要。
