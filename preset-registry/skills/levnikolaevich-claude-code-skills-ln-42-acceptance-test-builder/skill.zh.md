# 验收测试构建器

**目标：** 针对已陈述的需求，通过用户或外部系统可观察的边界，交付规模最小且可信的验收测试组合。只能修改已批准的测试和测试文档；在不修复产品代码的前提下，实现有依据的新增、更新、合并和删除。

**执行契约：** 有序复选框是完成定义。内部跟踪每一项，状态为 `PENDING`、有具体证据证明的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每个部分完成后重新核对各项。返回前解决所有 `PENDING`，并只统计 `PROVEN` 和 `CLEARED`；根据该技能的判定和批准规则处理每个缺口。

保留用户意图、范围和现有授权。继续执行已授权的工作；仅针对具有重大影响的未解决选择或所需的外部批准进行询问。根据实质风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择适当的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 工作区安全 | Git status、diff、仓库说明，以及分支或工作树检查 | 始终在编辑前执行 | 当无法安全分离用户更改时停止 |
| 现有测试约定 | 文件列表、搜索、清单、运行器配置、CI，以及针对性读取 | 选择项目原生运行器、布局、fixture 和命令时 | 遵循最近的受维护测试模式 |
| 行为和接线 | 语言服务器或宿主原生代码智能功能 | 定位可观察入口、注册、消费者和状态边界时 | 缩小搜索范围并直接检查 |
| 测试实现 | 原生编辑工具和项目生成器 | 创建测试、fixture、辅助工具和必要范围内的测试文档时 | 使用符合项目风格的最少文件；绝不手动编辑生成状态 |
| 可观察执行 | 仓库定义的 shell 命令、浏览器、API 客户端、CLI，或一次性集成环境 | 证明 UI、协议、命令或持久状态结果时 | 返回 `INCOMPLETE`，并明确缺失的检查 |
| 外部契约 | 与版本匹配的官方文档或规范 | 预期行为依赖当前外部 API 或标准时 | 标记为 `UNVERIFIED`；不要编码猜测的判定依据 |

绝不针对生产环境或未经批准的外部目标运行验收测试。不要部署、发布、迁移共享数据、轮换凭据，也不要仅为让测试通过而接受变更后的输出。

## 证据规则

- 从需求、公开契约、示例、不变量或独立参考中推导预期行为；绝不能从被测实现的计算结果中推导。
- 优先采用终端持久结果或用户可见结果，而不是中间状态、模拟调用、日志行或内部方法结果。
- 仅对确定、可审查的契约使用 golden 文件或快照。更新预期输出属于规范变更，而不是测试验证。
- 使设置、数据分配、执行、清理和重跑行为具备可重复性；在重试或清理掩盖首次失败之前保留首次失败。
- 一条通过的命令只能证明它实际执行过的环境和场景。明确说明每个被排除的单元格以及不可用的边界。
- 不要测试语言、框架、包、数据库厂商或其他通用行为；只测试依赖于这些因素的、由仓库负责的可观察契约、配置、集成或策略。
- 将 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 和 `NO_TEST` 视为测试组合决策，与执行结果区分开。现有证据、整合、退役或已接受的残余风险可能是更好的选择时，不要默认 `ADD`。
- 仅当测试依据已过时，或证据表明所有仍需覆盖的独特实质行为、故障模式、判定依据强度和有用的失败定位能力仍然得到覆盖时，才删除或合并测试。

## 检查清单

### 1. 确立变更边界

- [ ] 明确需求、验收标准、参与者、受保护结果、可观察契约、明确的非目标、获批准的组合决策、允许的测试路径和允许的测试文档路径；将推断出的体验质量标记为假设。
- [ ] 在编辑前阅读适用的仓库说明，检查 Git 状态、未跟踪文件、生成区域以及现有用户变更。
- [ ] 检测项目原生运行器、目录布局、命名约定、fixture、设置、清理、环境配置和 CI 调用方式。
- [ ] 清点受需求或契约影响的现有测试，并在创建新测试前梳理其实际断言方式。
- [ ] 将每项需求映射到能够证明它的边界：UI、API、CLI、消息、集成、文件或持久化状态。
- [ ] 识别场景所需的凭据、服务、账户、端口、设备、浏览器、数据集以及破坏性影响。
- [ ] 当不存在安全的目标、可靠的预期契约或可分离的工作区时，在编辑前返回 `BLOCKED`。

### 2. 设计可复现的验收证据

- [ ] 为每项需求定义受保护结果、缺陷类别、设置、操作、终止结果、独立断言、预期证据和清理步骤。
- [ ] 为每个受影响的测试和每项重大风险确认或推导出一项组合操作。当不存在获批准的策略时，根据影响、合理的失败可能性、唯一性、可信度和维护成本说明该操作的依据；如果已有证明、其他控制措施或已接受的残余风险，则记录 `NO_TEST`。
- [ ] 对重大的用户可观察业务风险，优先采用确定性的端到端证据。只有当更窄的、贴近生产的契约或集成边界能够更确定或更精确地证明终止结果时，才使用该方式；绝不能用单元实现检查替代验收证据，也不能覆盖可观察契约中不存在的内部细节。
- [ ] 仅在会实质性改变受保护结果时，纳入无效、授权、边界、部分失败、重试、幂等性、恢复和兼容性行为。
- [ ] 分配唯一的或带命名空间的测试数据，并在时钟、随机性、区域设置、排序和并发性会影响可复现性时对其进行控制。
- [ ] 在 mock 会绕过验收行为时，使用真实依赖或获批准的模拟器；固定版本，并验证就绪状态和重置行为。
- [ ] 对于确定性输出，根据独立契约推导 golden 或 diff 预期，并将产物保持在足够小、便于审查的范围内。
- [ ] 对于非确定性输出，断言稳定的不变量和语义字段，而不是通过归一化消除失败或对噪声进行快照。
- [ ] 根据可观察契约和区域设置策略，使用稳定且符合项目惯例的语义定位器（角色、可访问名称、标签）或显式 ID/test hook。避免使用样式、位置、时序和偶然的结构。将精确文案断言单独处理；当存在稳健的语义定位器时，不要仅为添加 hook 而要求产品修改。
- [ ] 定义必需的或诊断性的 gate，并在证据是临时的、受兼容性约束的、特定于事件的或与不断变化的契约耦合时，定义审查或退役触发条件。

### 3. 在测试范围内实施

- [ ] 在现有项目布局中创建或更新测试，使用体现行为的名称和失败消息，明确指出被违反的要求、受保护的结果以及检测到的缺陷。
- [ ] 实施获批准的 `MERGE` 和 `DELETE` 操作，不得遗留已被取代的测试、fixture、快照、辅助工具、注册项或 CI 条目；通过仓库原生的路径、名称、标签或任务证据保留替换的可追溯性。
- [ ] 仅在默认值和副作用仍然可见时复用受维护的 fixture 和辅助工具；避免为单个场景新增抽象。
- [ ] 缺少前置条件时让设置快速失败，并确保清理在成功、断言失败、超时、取消或部分设置之后都安全执行。
- [ ] 保持测试可重复运行且幂等；不得依赖执行顺序，也不得静默复用上一次运行遗留的状态。
- [ ] 仅当贡献者无法据此配置、运行、解释或清理新的证据时，才添加范围最小的测试文档。
- [ ] 不得编辑生产代码、弱化断言、在没有证据的情况下扩大超时时间、跳过失败用例，或重新生成预期产物来获得通过结果。
- [ ] 检查差异，确认不存在无关格式变更、生成文件变动、密钥、环境特定路径以及超出批准范围的变更。

### 4. 执行并保留证据

- [ ] 先运行受影响范围最小的场景，然后运行相关测试套件以及在可用时所需的仓库门禁；当操作只会移除证据时，运行替代证据或最近的保留证明。
- [ ] 记录命令、工作目录、环境类别、目标、版本、退出状态、持续时间、产物以及实际执行的场景。未选中任何测试或全部跳过的输出不能证明验收通过。
- [ ] 保留重现缺陷所需的首次失败输出、种子、顺序、请求、响应、屏幕截图、差异或持久状态。
- [ ] 在修改测试之前，区分产品失败、测试缺陷、环境失败、依赖不可用和不稳定证据。
- [ ] 如果有效测试暴露出产品缺陷，保留失败的验收证据并报告最小复现步骤；绝不得修复生产代码。在安全的情况下继续独立的范围内测试工作。
- [ ] 当状态所有权或幂等性具有实质影响时，验证清理并至少重新运行受影响的场景。
- [ ] 避免重试，除非重试用于诊断非确定性；重试不得将初始失败转化为静默通过。

### 5. 最终确定但不过度声称

- [ ] 将每项要求和受保护结果映射到最终测试路径或 `NONE`、命令或替代控制、判定依据或接受的风险，以及结果 `PASS`、`FAIL`、`BLOCKED` 或 `UNPROVEN`。
- [ ] 核对计划中的组合操作与实际执行的组合操作，包括有理由的偏差，并报告新增、更新、合并和删除的测试净数量，不得将数量视为质量目标。
- [ ] 当所有获批准的组合操作均已实施，并且所需证据记录了可信的 `PASS` 或产品 `FAIL`，或记录了有充分理由的 `NO_TEST` 控制时，使用 `COMPLETE`。未解决的测试缺陷不属于已完成的证据；此结论不证明产品正确性。
- [ ] 当安全工作仍未完成，或环境、依赖、测试缺陷或中断导致无法可信地执行时，使用 `INCOMPLETE`；说明确切的剩余操作或检查。
- [ ] 当操作无法安全实施、要求缺少可靠的判定依据，或工作区无法受到保护时，使用 `BLOCKED`。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。更正报告或已获授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言按以下顺序报告；保留全部五个字段，并且每项事实仅陈述一次。简短结果可每个字段占一行；省略空表格，且不要复制已链接的产物：

1. **结果：** 技能特定的结论和有依据的结果。
2. **范围：** 审查/变更范围、排除项、基线和重要假设。
3. **证据：** 以下技能特定字段；区分事实、推断和未经验证的声明。链接产物；必要时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或列出每个 `UNPROVEN` 条目的原因、对结果的影响和确切的下一步操作；剩余风险和所需决策。

**技能特定证据：** 需求/受保护结果 → 现有证据 → 组合行动 → 最终测试路径或 `NONE` → 独立验证器/命令 → 门禁/结果 → 退役触发条件。列出变更的测试/文档文件、用于合并/删除的替代证据、组合的净影响、确切的命令和产物、保留的产品失败复现、清理工作、不可用环境和排除的单元。证据完成不代表产品正确性。
