# 原型

原型是**用于回答某个问题的一次性代码**。问题决定其形态。

## 选择一个分支

根据用户的提示、周边代码来确定要回答的问题；如果用户在线，也可以直接询问：

- **“这个逻辑／状态模型合理吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单文件 HTML（包含自由操作按钮以及带标签页的引导式演练），推动状态机经历那些难以在纸面上推演的场景，并且让非开发人员也能操作。
- **“这个应该是什么样子？”** → [UI.md](UI.md)。在单个路由上生成若干种截然不同的 UI 变体，并可通过 URL 查询参数和底部悬浮栏进行切换。

这两个分支会产出截然不同的成果，因此选错分支会浪费整个原型。如果问题确实含糊不清且无法联系到用户，则默认选择与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性的，并明确标注这一点。** 将原型代码放在靠近其实际使用位置的地方（紧邻它所针对的模块或页面），使上下文一目了然；但命名时要让普通读者一眼就能看出它是原型，而不是生产代码。对于一次性 UI 路由，应遵循项目已有的路由约定；不要自行创建新的顶层结构。
2. **运行起来极其简单。** UI 原型通过项目任务运行器中的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是一个用户双击即可打开的 HTML 文件。无论哪种方式，启动时都不需要思考。
3. **默认不持久化。** 状态保存在内存中。持久化是原型要_验证_的内容，而不是原型应依赖的内容。如果问题明确涉及数据库，则使用临时数据库或本地文件，并用清晰的“PROTOTYPE, wipe me”名称标注。
4. **略过打磨。** 不写测试；除保证原型_可运行_所必需的错误处理外，不做其他错误处理；不做抽象。重点是快速学到东西。
5. **暴露状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染所有相关状态，让用户能够看到发生了什么变化。
6. **完成后将其留档。** 将所有已验证的决策整合进真实代码，然后把原型本身作为**第一手资料**留档：将其提交到一个位于主分支之外的一次性分支，并在实现任务中留下指向该分支的上下文链接。还要在任务或提交中记录答案（结论及其解决的问题）。主分支只保留经过验证的决策。
