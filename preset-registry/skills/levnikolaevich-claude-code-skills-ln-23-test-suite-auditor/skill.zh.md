# 测试套件审计员

**目标：** 将测试组合审计为一个只读的生命周期与信心系统。确定它能够检测哪些重要故障，哪些证据不可信或已过时，以及哪些新增、变更、合并、退役或明确省略的措施能够构成最小且可持续的测试组合。

**执行契约：** 有序复选框即为完成定义。对每一项在内部标记为 `PENDING`、有具体证据证明的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每个部分完成后重新核对各项。返回结果前，解决所有 `PENDING`，并只统计 `PROVEN` 和 `CLEARED`；针对每个缺口应用该技能的裁决和批准规则。

保留用户意图、范围和现有授权。继续执行已获授权的工作；只有在存在具有重大影响且尚未解决的选择，或需要外部批准时才提问。根据实际风险调整深度，不得默默跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 源码和测试清单 | 原生文件列表、搜索、清单文件和测试配置 | 映射领域、测试类型、运行器、fixture 和生成区域时 | 仓库树以及已知的测试入口点 |
| 测试与代码的关系 | 语言服务器或宿主环境原生代码智能功能 | 映射单元、调用方、实现、路由和测试目标时 | 通过直接读取验证的命名和路径搜索 |
| 执行与信任度 | 通过 shell 执行仓库定义的测试命令 | 确定通过/失败状态、执行时间、顺序依赖或可复现性时 | 检查 CI 结果和配置；将执行不可用标记为不可用 |
| 覆盖率和遗漏行为 | 现有覆盖率工具和报告 | 已配置覆盖率数据且能够与源码范围进行比较时 | 静态的行为到测试映射；绝不虚构百分比 |
| 不稳定性和隔离证据 | 使用仓库支持的重复、乱序、并行或种子控制运行 | 怀疑测试依赖顺序、时间、随机性或共享状态时 | 历史记录、CI 日志和代码路径证据 |
| 断言强度 | 测试读取、失败输出和已配置的变异测试 | 确定测试是否会因有意义的行为缺陷而失败时 | 与具体断言相关联的反事实推理 |
| 框架语义 | 官方测试运行器或框架文档 | 某项发现取决于生命周期、fixture、重试、隔离或模拟行为时 | 以主要来源为依据的网络调研；否则标记为 `UNVERIFIED` |

仅运行安全的测试和诊断命令。审计期间不得重写快照、更新 golden 文件、重新生成 fixture，或接受变更后的输出。

## 证据规则

- 覆盖率表示执行过，而不是得到证明。重要行为必须有断言或可观测的判定依据。
- 当一个慢速测试唯一保护某条关键旅程时，它并不属于低价值测试；当一个快速测试只证明框架行为时，它也不属于高价值测试。
- 必须将不稳定失败与间歇性失败的产品依赖，或确实具有非确定性的需求区分开来。
- 删除建议必须证明测试依据已经过时，或其他证据能够以相同或更高的可信度覆盖所有仍然需要的行为和失败模式。
- 合并建议必须基于已证实的重复覆盖或碎片化覆盖，并且必须保留不同的业务场景和失败场景、判定依据强度以及失败定位能力；测试更大并不天然意味着更好。
- 已知回归防护，以及罕见关键边界情况的唯一证明，不会仅仅因为数值启发式较低就成为删除候选。
- 真实依赖并不天然意味着测试存在缺陷。应判断其版本、状态、所有权、重置方式、可用性和失败证据是否使结果可复现。
- 将组合操作（`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE`、`NO_TEST`）与执行状态（`PASS`、`FAIL`、`BLOCKED`、`UNPROVEN`、`QUARANTINED`）分开。`NO_TEST` 必须有现有证明、其他控制措施或明确的剩余风险接受作为依据。
- 默认不要要求新建注册表。优先使用可从仓库原生测试路径、行为名称、标签、需求、CI 配置和评审证据中推导出的可追溯性。
- 外部测试指导只有在能够解释本测试套件中的具体薄弱点时，才具有可执行性。

## 检查清单

### 1. 梳理测试组合并建立基线

- [ ] 检测测试运行器、配置、命令、目录、fixture、工厂、快照、基准文件、手动脚本、覆盖率工具和变异测试工具。
- [ ] 将源代码领域和关键入口映射到单元测试、集成测试、契约测试、端到端测试和手动测试范围。
- [ ] 在存在证据的情况下，将需求、产品风险、事故、公开契约和变更行为追溯到测试及其结果；识别当前没有测试依据的测试，以及没有可信证明的依据要素。
- [ ] 阅读仓库说明和 CI 配置，以识别必需的测试套件、环境假设、重试、分片和排除项。
- [ ] 在可行时运行具有代表性的测试套件和必需的门禁；记录环境、耗时、退出状态、发现/执行的范围、失败、跳过和重试。标记那些静默地未选择任何测试的必需测试套件。
- [ ] 在评估测试组合之前，将生成的、供应商提供的、示例、迁移历史和基础设施 fixture 与产品测试区分开。
- [ ] 保持审计为只读操作，并披露经许可的命令所创建的任何缓存或测试产物。

### 2. 审计产品价值和覆盖率

- [ ] 识别本地独有的关键逻辑：金钱、身份验证、授权、数据完整性、算法、领域规则、破坏性操作和不可逆工作流。
- [ ] 将每个关键行为追溯到至少一个测试，并确保该测试的预期结果会因对应缺陷而失败；名称/路径匹配和行覆盖率只能作为发现依据。
- [ ] 识别那些仅仅重新验证语言、框架、数据库引擎、ORM、HTTP 客户端、密码学、序列化器或库行为的测试，而没有断言仓库自有的配置、查询、模式、适配、验证、失败处理或可观察结果。
- [ ] 检查端到端测试是否跨越与风险相关的、符合生产形态的边界，并证明最终的持久化结果或用户可见结果，而不仅仅是中间状态、页面或模拟调用。
- [ ] 找出没有端到端证明的关键流程，以及其行为已经在更低层级得到更可靠覆盖的高成本端到端测试。
- [ ] 检查错误、重试、超时、授权、并发、迁移、兼容性和恢复行为，尤其是在这些失败可能发生且代价高昂的情况下。
- [ ] 使用覆盖率数据定位未执行的关键路径，然后在报告缺口之前检查其行为和断言。
- [ ] 将每个实质性缺口和范围内受影响的测试分类为 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或 `NO_TEST`，并根据影响、合理的失败可能性、独特性、可信度和维护成本说明理由；当有价值的意图仍然存在，但其依据、设置、边界、断言或预期结果必须改变时，使用 `UPDATE`。

### 3. 审计隔离性和确定性

- [ ] 检查共享数据库、文件系统、环境、进程、网络、缓存、时钟、随机数生成器和全局状态是否在测试之间发生泄漏。
- [ ] 检查成功和失败情况下的设置与清理、唯一测试数据、事务边界、清理操作以及并行安全的资源所有权。
- [ ] 仅使用具有区分性的模式诊断疑似不稳定测试：单独运行、在测试套件中运行、固定种子重复运行、随机/反向顺序运行或并行执行。保留首次失败、顺序、种子、工作进程和环境；当证据确定原因或有限的诊断预算耗尽时停止。
- [ ] 检测时间、时区、区域设置、随机性、休眠、调度器和竞态敏感性；当行为依赖这些因素时，要求使用可控时钟或种子。
- [ ] 对于真实依赖和模拟器，验证版本固定、就绪状态、命名空间/状态重置、失败清理、凭据和 CI 可用性，而不是假定使用真实依赖或模拟依赖中的任何一种更为合适。
- [ ] 检查重试和隔离规则，确保它们保留首次失败和可复现性数据，而不是将初始失败转换为静默通过。
- [ ] 要求每个被隔离的测试在通过结果之外仍然可见，并配有负责人或决策路径，以及具体的恢复、替换或退役触发条件；隔离是执行状态，而不是测试组合操作。
- [ ] 通过重复证据、日志和失败路径，区分测试不稳定与真实的间歇性产品缺陷。

### 4. 审计结构、维护性与判定依据

- [ ] 检查测试布局是否遵循源代码领域划分或清晰的按类型约定，以及贡献者是否能够找到负责维护这些测试的归属位置。
- [ ] 查找孤立测试、已禁用的测试套件、重复的测试固件、碎片化的场景覆盖、过大的文件，以及掩盖归属关系的扁平目录。
- [ ] 根据当前风险审查临时的特征描述、迁移、兼容性、事故、变通方案和回归测试。已修复的事故不会使其回归防护失效；在建议合并或删除之前，必须要求存在已过时的行为，或有可信的替代覆盖。
- [ ] 检查测试名称和编排是否体现行为意图、前置条件、操作和预期结果，而不是叙述实现细节。
- [ ] 根据可观察契约和本地化策略，使用稳定且符合项目惯例的语义定位器（角色、可访问名称、标签），或使用显式 ID/测试钩子。避免依赖样式、位置、时序和偶然的结构。当文案本身是要求时，应单独处理精确文案断言；如果已有可靠的语义定位器，不要仅为添加钩子而要求修改产品。
- [ ] 检查断言是否具体，是否包含反向证明，是否平衡覆盖状态和交互，是否提供有用的失败消息，以及是否能抵抗误报。
- [ ] 标记缺少有意义失败判定依据的测试、薄弱的真值断言、对偶然或不可审查输出的快照、宽泛的异常接受，以及绕过被测行为的模拟。对于能够独立证明所需契约的快照或隐式失败判定依据，应予以保留。
- [ ] 检查预期值是否来自独立的契约、示例、不变量或黄金文件，而不是在测试中复现实现的计算。
- [ ] 检查模拟对象、伪造对象、仿真器和生成的客户端是否存在契约漂移；如果漂移可能造成虚假的信心，则要求契约测试，或要求与真实边界进行其他可信的对比。
- [ ] 使用非默认配置值进行测试，因为使用默认值且通过的测试可能掩盖硬编码的端口、限制、超时、路径或功能行为。
- [ ] 对关键的薄弱判定依据候选项，使用已有的变异测试结果或安全且有针对性的反事实验证；不要强制要求仓库范围的变异测试。
- [ ] 审查手动测试是否具备可复现的设置、快速失败行为、明确的预期证据、幂等性、清理机制、可移植性和操作员文档。
- [ ] 检查测试固件和辅助工具的抽象是否易读且默认值真实；构建器中的隐藏行为不能使重要的测试条件变得不可见。
- [ ] 审查门禁的位置和套件成本：必需门禁应保护实质性的发布风险，而较慢的诊断性或探索性证据应保持可发现，同时不应不必要地阻塞日常交付。

### 5. 验证发现并报告

- [ ] 仅在生命周期、测试固件、隔离、重试或模拟行为可能改变某项发现时，研究运行器或框架语义；使用与版本匹配的官方来源。
- [ ] 在安全的情况下复现高严重性信任失败，并保留命令、种子、顺序和环境证据。
- [ ] 对共享同一根因的发现进行去重，例如全局测试固件导致多个测试套件不稳定。
- [ ] 应用实质性门槛：必须有具体的关键证明缺口、虚假的信心、交付风险，或在已有证据规模上反复出现的维护成本。拒绝审美偏好、理论纯粹性、泛化实践、假设性规模和合理替代方案；要求关注结果或约束，而不是偏好的实现方式。
- [ ] 基于与版本匹配的官方契约提出外部修正；对于未解决的权衡，使用一手工程来源。对于本地缺陷，本地证据即可。
- [ ] 根据未被证明的关键行为、虚假的信心、交付阻塞和维护负担，将发现分类为 `P0`-`P3`。
- [ ] 在有证据时报告具有决策价值的整体信号：按证明状态划分的实质性风险、行动分布、必需门禁的结果和耗时、跳过、重试、隔离，以及孤立或过时候选项。不要将测试总数、未排除项的通过率、原始覆盖率和级别比例单独作为质量目标。
- [ ] 当必需的关键测试套件、环境或判定依据无法访问，且不存在可信的静态或历史替代方案时，使用 `BLOCKED`；当证据表明关键行为未被证明、必需门禁失败，或不可信的关键表面仍造成虚假信心时，使用 `FAIL`；仅对非阻塞的整体状况或维护风险使用 `CONCERNS`；只有在必需证据可信且不存在关键缺口时，才使用 `PASS`。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论和适用的清理工作。修正报告或经授权的工件。复用有效证据；不要自动重新扫描代码库或重新运行已成功的命令。仅针对相关变更、失败项或尚未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言，按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。结果较小时，每个字段可使用一行；省略空表格，不要复制链接的工件：

1. **结果：** 技能特定的结论和有依据的结果。
2. **范围：** 已审查/变更的范围、排除项、基线和重要假设。
3. **证据：** 以下技能特定字段；区分事实、推断和未经验证的声明。链接工件；适用时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；说明剩余风险和所需决策。

**技能特定证据：** 测试依据/受保护的风险 → 现有测试或缺失的证明 → 组合行动 → 判定依据 → 门禁/结果 → 替代证据或退役触发条件。涵盖在有证据支持的情况下的关键行为、隔离性、可维护性、断言强度、生命周期、测试组合的净影响、必需/诊断门禁、持续时间、跳过、重试和隔离项。发现项需要包含优先级、测试位置、遗漏的缺陷类别、影响、不可接受的权衡和最小修正；保留独有覆盖，并区分测试组合行动与执行状态。
