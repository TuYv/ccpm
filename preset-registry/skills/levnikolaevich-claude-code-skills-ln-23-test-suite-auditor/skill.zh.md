# 测试套件审计员

**目标：** 将测试组合视为一个只读的生命周期与信心保障系统进行审计。确定它能够检测哪些重要故障、哪些证据不可信或已经过时，以及哪些新增、变更、合并、退役或明确省略的措施能够形成规模最小且可持续维护的测试组合。

**执行约定：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，并且只有在相应操作及其所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的判定、决策和批准规则应用于每个未完成项，并在回复开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 源代码与测试清单 | 原生文件列表、搜索、清单文件和测试配置 | 映射领域、测试类型、运行器、夹具和生成区域 | 仓库目录树及已知的测试入口点 |
| 测试与代码之间的关系 | 语言服务器或宿主环境原生的代码智能工具 | 映射单元、调用方、实现、路由和测试目标 | 通过直接读取内容验证的命名及路径搜索 |
| 执行与可信度 | 通过 shell 运行仓库定义的测试命令 | 确定通过/失败状态、耗时、顺序依赖性或可复现性 | 检查 CI 结果和配置；将执行标记为不可用 |
| 覆盖率与遗漏行为 | 现有的覆盖率工具和报告 | 已配置覆盖率数据，并且其范围可与源代码范围进行比较 | 静态映射行为与测试；绝不虚构百分比 |
| 不稳定性与隔离性证据 | 仓库支持的重复运行、打乱顺序运行、并行运行或受种子控制的运行 | 怀疑测试依赖于顺序、时间、随机性或共享状态时 | 历史记录、CI 日志和代码路径证据 |
| 断言强度 | 阅读测试、分析失败输出及已配置的变异测试 | 确定测试是否会因具有实际意义的行为缺陷而失败 | 与具体断言相关联的反事实推理 |
| 框架语义 | 官方测试运行器或框架文档 | 某项发现依赖于生命周期、夹具、重试、隔离或模拟行为时 | 基于第一手来源的 Web 调研；否则标记为 `UNVERIFIED` |

仅运行安全的测试和诊断命令。审计期间不要重写快照、更新黄金文件、重新生成夹具或接受已更改的输出。

## 证据规则

- 覆盖率表示代码被执行过，而不是证明其正确。对于重要行为，必须有断言或可观察的判定依据。
- 当一个慢速测试能够唯一保护某个关键流程时，它并非低价值测试；当一个快速测试只是在证明框架本身的行为时，它也并非高价值测试。
- 必须将不稳定的失败与间歇性失败的产品依赖项或真正具有非确定性的需求区分开来。
- 建议删除测试时，必须证明测试所依据的基础已经过时，或者其他证据能够以同等或更高的可信度覆盖所有仍然需要的行为和故障模式。
- 建议合并测试时，必须证明存在重复或碎片化的覆盖，并且合并后必须保留不同的业务场景和故障场景、判定依据的强度以及故障定位能力；规模更大的测试并不天然更好。
- 已知的回归防护测试以及能够证明罕见关键边界情况的唯一测试，不能仅仅因为某个数值化价值指标较低就成为删除候选。
- 使用真实依赖项并不天然属于测试缺陷。应判断其版本、状态、所有权、重置方式、可用性和故障证据能否使结果具备可复现性。
- 将测试组合操作（`KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE`、`NO_TEST`）与执行状态（`PASS`、`FAIL`、`BLOCKED`、`UNPROVEN`、`QUARANTINED`）分开。`NO_TEST` 需要现有证明、其他控制措施或明确接受残余风险。
- 默认情况下，不要要求建立新的登记表。优先使用可从仓库原生测试路径、行为化名称、标签、需求、CI 配置和评审证据中推导出的可追溯性。
- 只有当外部测试指南能够解释此测试套件中的具体弱点时，它才具有可操作性。

## 检查清单

### 1. 梳理测试组合和基线

- [ ] 识别测试运行器、配置、命令、目录、夹具、工厂、快照、黄金文件、手动脚本、覆盖率工具和变异测试工具。
- [ ] 将源代码领域和关键入口点映射到单元测试、集成测试、契约测试、端到端测试和手动测试的覆盖面。
- [ ] 在存在证据的情况下，将需求、产品风险、事故、公开契约和行为变更追溯到测试及其结果；识别当前没有测试依据的测试，以及没有可信证明的依据要素。
- [ ] 阅读仓库说明和 CI 配置，以识别必需的测试套件、环境假设、重试、分片和排除项。
- [ ] 先运行最小规模的代表性测试套件，然后在可行的情况下运行必需的测试门禁；记录环境、持续时间、退出状态、失败、跳过和重试情况。
- [ ] 在评估测试组合之前，将生成的、供应商提供的、示例用的、迁移历史相关的以及基础设施夹具与产品测试区分开来。
- [ ] 确保审计过程只读，并披露获准执行的命令所创建的任何缓存或测试产物。

### 2. 审计产品价值和覆盖情况

- [ ] 识别本地特有的关键逻辑：资金、身份验证、授权、数据完整性、算法、领域规则、破坏性操作和不可逆工作流。
- [ ] 将每项关键行为追溯到至少一个测试，且该测试的判定机制会在出现相应缺陷时失败；名称/路径匹配和行覆盖率仅可作为发现线索。
- [ ] 识别那些仅仅再次验证语言、框架、数据库引擎、ORM、HTTP 客户端、加密、序列化器或库的行为，却未断言仓库自身的配置、查询、模式、适配、验证、失败处理或可观察结果的测试。
- [ ] 检查端到端测试是否跨越了与风险相关且符合生产环境形态的边界，并证明最终的持久化结果或用户可见结果，而不只是中间状态、页面或模拟调用。
- [ ] 找出缺少端到端证明的关键流程，以及那些行为已在更低层级得到更可靠覆盖、但成本高昂的端到端测试。
- [ ] 在错误、重试、超时、授权、并发、迁移、兼容性和恢复故障可能发生且代价高昂的情况下，检查相应行为。
- [ ] 使用覆盖率数据定位未执行的关键路径，然后检查其行为和断言，再报告缺口。
- [ ] 将每个重大缺口和范围内受影响的测试分类为 `KEEP`、`ADD`、`UPDATE`、`MERGE`、`DELETE` 或 `NO_TEST`，并依据影响、可能发生的故障、独特性、可信度和维护成本给出理由；当有价值的意图仍然存在，但其依据、准备过程、边界、断言或判定机制必须改变时，使用 `UPDATE`。

### 3. 审计隔离性和确定性

- [ ] 检查共享数据库、文件系统、环境、进程、网络、缓存、时钟、随机数生成器和全局状态是否会在测试之间泄漏。
- [ ] 检查成功和失败情况下的准备与清理、唯一测试数据、事务边界、资源清理以及并行安全的资源所有权。
- [ ] 使用可用的最小判别矩阵诊断疑似不稳定测试：单独运行、在测试套件中运行、使用固定种子重复运行、打乱顺序/逆序运行以及并行运行；保留首次失败时的顺序、种子、工作进程和环境信息。
- [ ] 检测对时间、时区、区域设置、随机性、休眠、调度器和竞态的敏感性；当行为依赖这些因素时，要求使用可控的时钟或种子。
- [ ] 对于真实依赖项和模拟器，应验证版本固定、就绪状态、命名空间/状态重置、失败清理、凭据和 CI 可用性，而不是假定真实依赖或模拟依赖中的任何一种更可取。
- [ ] 审查重试和隔离规则，确保它们保留首次失败和可复现性数据，而不是将初次失败变成无声的通过。
- [ ] 要求每项隔离都必须在通过结果之外保持可见，并指定负责人或决策路径，以及具体的恢复、替换或退役触发条件；隔离是一种执行状态，而不是测试组合处置措施。
- [ ] 使用重复证据、日志和失败路径，区分测试不稳定与真实的间歇性产品缺陷。

### 4. 审查结构、维护性和判定依据

- [ ] 检查测试布局是否遵循源代码领域划分或清晰的类型划分约定，以及贡献者能否找到相应的归属测试。
- [ ] 查找孤立测试、已禁用的测试套件、重复的夹具、碎片化的场景覆盖、过大的文件，以及使归属关系模糊的扁平目录。
- [ ] 识别原始触发因素已经消失的临时特征测试、迁移测试、兼容性测试、事故测试、变通方案测试和回归测试；要求提供当前仍存在独特风险的证据，或给出安全的合并或删除路径。
- [ ] 检查测试名称和组织方式是否体现行为意图、前置条件、操作和预期结果，而非叙述实现过程。
- [ ] 对于 UI 和交互测试，拒绝使用与可见或已翻译文案、样式、布局、位置或附带结构耦合的定位器；要求使用由仓库所有并维护的稳定 ID 或专用测试钩子，并将显式文案断言与元素查找分开。
- [ ] 检查断言的具体性、反向验证、状态与交互之间的平衡、有效的失败消息，以及抵御假阳性的能力。
- [ ] 标记无断言测试、薄弱的真值检查、仅以快照为依据的验证、宽泛的异常接受，以及绕过被测行为的模拟。
- [ ] 检查预期值是否来自独立的契约、示例、不变量或黄金制品，而不是在测试中复现实现的计算过程。
- [ ] 检查模拟、伪实现、模拟器和生成的客户端是否存在契约漂移；当漂移可能造成虚假信心时，要求提供契约测试，或以其他可信方式与真实边界进行比较。
- [ ] 使用非默认配置值进行测试，因为使用默认值即可通过的测试可能掩盖硬编码的端口、限制、超时、路径或功能行为。
- [ ] 对关键的弱判定依据候选项，使用已有的变异测试结果或安全且有针对性的反事实测试；不要强制要求对整个仓库进行变异测试。
- [ ] 审查手动测试是否具备可复现的设置、快速失败行为、明确的预期证据、幂等性、清理机制、可移植性和操作人员文档。
- [ ] 检查夹具和辅助工具的抽象是否具备可读性并采用如实反映行为的默认值；构建器中的隐藏行为不得使重要测试条件不可见。
- [ ] 审查质量门禁的设置位置和测试套件成本：必需门禁应防范实质性的发布风险，而较慢的诊断性或探索性证据应保持可发现，同时避免不必要地阻碍常规交付。

### 5. 验证发现并报告

- [ ] 仅当运行器或框架的生命周期、夹具、隔离、重试或模拟行为可能改变某项发现时，才研究其语义；使用与版本匹配的官方资料。
- [ ] 在安全的情况下复现高严重性的信任失效，并保留命令、种子、顺序和环境证据。
- [ ] 对具有相同根本原因的发现进行去重，例如由某个全局夹具导致多个测试套件不稳定。
- [ ] 对每个候选项应用实质性和可接受替代方案门槛。要求在该测试套件经证实的规模下，存在具体且未获验证的关键行为、虚假信心、交付风险或反复出现的维护成本。拒绝吹毛求疵、测试风格偏好、理论纯粹性、覆盖率虚荣指标、泛泛的最佳实践，以及虽不同但同样可信的测试设计；当多种测试形式均可行时，应要求覆盖相应风险并提供判定依据，而不是指定某一种首选实现。
- [ ] 在每项发现的必要解决方案中加入直接相关的 Markdown 实践链接：优先使用最新的官方文档或规范，只有当官方资料无法解决权衡问题时，才使用信誉良好的第一手工程资料。打开并验证资料来源；其必须支持所提议的测试机制，而不仅仅是与缺陷类别相关。拒绝搜索结果链接、泛泛的最佳实践文章和装饰性引用。
- [ ] 根据未获验证的关键行为、虚假信心、交付阻塞和维护负担，将发现分类为 `P0`-`P3`。
- [ ] 包括受影响的行为、测试位置、证据、遗漏的缺陷类别、测试组合层面的处置措施、当前折中方案不可接受的原因，以及最小可信修复方案，同时允许采用等效解决方案。
- [ ] 在有证据时，报告有助于决策的测试组合信号：按验证状态划分的实质性风险、处置措施分布、必需门禁的结果和持续时间、跳过、重试、隔离，以及孤立或过时的候选项。拒绝将测试总数、未计入排除项的通过率、原始覆盖率和测试层级比例作为独立的质量目标。
- [ ] 当无法访问必需的关键测试套件、环境或判定依据，且不存在可信的静态或历史替代证据时，使用 `BLOCKED`；当证据表明关键行为未获验证、必需门禁失败，或不可信的关键表面仍造成虚假信心时，使用 `FAIL`；仅对不阻塞交付的测试组合风险或维护风险使用 `CONCERNS`；仅当必需证据可信且不存在关键缺口时，使用 `PASS`。
- [ ] 返回判定结果，并包括可信覆盖范围、关键缺口、不可信表面、测试组合层面的处置措施、局限性和残余测试风险。

## Output Contract

```markdown
# Test Suite Audit

**Verdict:** PASS | CONCERNS | FAIL | BLOCKED

## Portfolio map and baseline
- Runners, suites, and test types
- Commands and environments executed
- Coverage, flake, and mutation evidence available

## Confidence summary
| Area | Status | Evidence |
|---|---|---|
| Critical behavior coverage | PASS / CONCERNS / FAIL | ... |
| Isolation and determinism | PASS / CONCERNS / FAIL | ... |
| Structure and maintenance | PASS / CONCERNS / FAIL | ... |
| Assertion and oracle strength | PASS / CONCERNS / FAIL | ... |
| Lifecycle and portfolio control | PASS / CONCERNS / FAIL | traceability, gates, quarantine, retirement triggers, and net portfolio effect |

## Portfolio decisions
| Test basis or protected risk | Existing evidence or affected test | Action | Gate and result | Replacement evidence or review trigger |
|---|---|---|---|---|
| ... | path / command / NONE | KEEP / ADD / UPDATE / MERGE / DELETE / NO_TEST | required / diagnostic; PASS / FAIL / BLOCKED / UNPROVEN / QUARANTINED | ... |

## Findings and portfolio actions
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete confidence or maintenance defect | Test basis, behavior and test location, evidence, missed defect class, material risk, and why the current tradeoff is not acceptable | `KEEP` / `ADD` / `UPDATE` / `MERGE` / `DELETE` / `NO_TEST`, replacement evidence or accepted risk, the smallest sufficient correction, and a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent test designs with the same risk coverage and oracle strength |

Use `None` when no candidate survives the evidence, materiality, portfolio-value, and acceptable-alternative gates.

## Portfolio control
Net additions, updates, merges, and deletions; `NO_TEST` decisions; required versus diagnostic gates; skips, retries, quarantine, and review or retirement triggers. Use only evidenced signals that can change a decision.

## Residual risks
Unexecuted suites, unavailable environments, accepted `NO_TEST` exposure, and behavior that remains unproven.
```
