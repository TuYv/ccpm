# 多智能体架构模式

多智能体架构将工作分配给多个语言模型实例，每个实例都有自己的上下文窗口。如果设计得当，这种分配方式可以实现超越单智能体限制的能力。如果设计不当，则会引入协调开销，抵消其优势。关键在于，子智能体的存在主要是为了隔离上下文，而不是将角色分工拟人化。

## 何时启用

在以下情况下启用此技能：
- 单智能体的上下文限制制约了任务复杂度
- 任务可以自然地分解为并行子任务
- 不同子任务需要不同的工具集或系统提示词
- 构建必须同时处理多个领域的系统
- 将智能体能力扩展至单一上下文限制之外
- 设计包含多个专用组件的生产级智能体系统

对于由其他技能负责的相邻工作，请勿启用此技能：
- 在拓扑结构尚未确定前，决定任务与模型的适配性、流水线形态或项目级成本：`project-development`。
- 设计托管式沙箱、热资源池、远程会话或后台运行时基础设施：`hosted-agents`。
- 在受控运行时中通过 KV-cache 压缩共享编排器状态：`latent-briefing`。
- 设计每个智能体所公开的工具：`tool-design`。

## 核心概念

当单个智能体的上下文窗口无法容纳与任务相关的全部信息时，请采用多智能体模式。上下文隔离是其主要优势——每个智能体都在没有其他子任务所累积噪声的干净上下文中运行，从而避免信息因反复总结而逐渐失真的传话游戏问题。

根据协调需求而非组织隐喻，从以下三种主流模式中进行选择：

- **监督者/编排器**——当任务可以明确分解且人工监督至关重要时，用于集中式控制。由单个协调器将任务委派给各个专家，并综合处理结果。
- **点对点/集群**——当僵化规划会适得其反时，用于灵活探索。任何智能体都可以通过显式交接机制将控制权移交给其他任意智能体。
- **分层式**——用于具有分层抽象结构（战略、规划、执行）的大型项目。每一层都以不同的详细程度运行，并拥有各自的上下文结构。

设计每个多智能体系统时，都应围绕显式协调协议、能够抵御迎合倾向的共识机制，以及能够防止错误级联传播的故障处理机制展开。

## 详细主题

### 为什么采用多智能体架构

**上下文瓶颈**
当单个智能体的上下文因累积的历史记录、检索到的文档和工具输出而趋于饱和，以至于性能下降时，应考虑采用多智能体架构。需要识别三种性能下降信号：中间信息丢失效应（对上下文中部内容的注意力减弱）、注意力稀缺（需要争夺注意力的项目过多），以及上下文污染（无关内容挤占有用内容）。

将工作分配到多个上下文窗口，使每个智能体都能在专注于其子任务的干净上下文中运行。在协调层汇总结果，同时避免让任何单个上下文承担全部负担。

**Token 经济的现实**
应为大幅增加的 Token 成本做好预算。生产数据表明，多智能体系统消耗的 Token 可能远多于单智能体聊天系统（claim-multi-agent-token-multiplier）：

| 架构 | Token 倍数 | 使用场景 |
|--------------|------------------|----------|
| 单智能体聊天 | 基准 | 简单查询 |
| 使用工具的单智能体 | 高于基准 | 使用工具的任务 |
| 多智能体系统 | 远高于基准 | 复杂研究/协调 |

浏览智能体评估研究表明，Token 使用量、工具调用和模型选择是造成性能差异的主要因素（claim-evaluation-browsecomp-variance）。这说明应将多智能体配置与单智能体基准进行比较，而不是想当然地认为增加智能体就会有所帮助。

在设计架构的同时，应优先考虑模型选择——升级到更好的模型通常比将 Token 预算翻倍带来更大的性能提升。BrowseComp 数据表明，模型质量的提升往往优于单纯增加 Token。应将模型选择和多智能体架构视为互补策略。

**并行化论点**
将可并行的子任务分配给拥有全新上下文的专用智能体，而不是由单个智能体依次处理。对于需要搜索多个独立来源、分析不同文档或比较多种竞争方案的研究任务，并行执行会带来更大收益。现实中的总耗时将接近最长子任务的执行时间，而不是所有子任务执行时间的总和。

**专业化论点**
仅为每个智能体配置其特定子任务所需的系统提示词、工具和上下文。通用智能体必须在上下文中携带所有可能的配置，从而分散注意力。专业化智能体只携带所需内容，以针对其领域优化的精简上下文运行。通过协调器将任务路由至专业化智能体，从而在不引发组合爆炸的情况下实现专业化。

### 架构模式

**模式 1：监督者/编排器**
部署一个中央智能体来维护全局状态和执行轨迹，将用户目标分解为子任务，并将其路由至适当的工作智能体。

```
User Query -> Supervisor -> [Specialist, Specialist, Specialist] -> Aggregation -> Final Output
```

在以下情况下选择此模式：任务可以清晰分解、需要跨领域协调，或人工监督非常重要。

需要预见这些权衡：它能提供严格的工作流控制，并使人工介入更加容易，但监督者的上下文会成为瓶颈，监督者的故障会级联影响所有工作智能体，而且会出现“传话游戏”问题，即监督者错误地转述子智能体的响应。

**传话游戏问题及解决方案**
应预见到，由于传话游戏问题，监督者架构最初的性能会比优化后的版本低约 50%（LangGraph 基准测试）。监督者会转述子智能体的响应，并在每次传递过程中损失保真度。

通过实现一个 `forward_message` 工具来解决此问题，使子智能体能够将响应直接传递给用户：

```python
def forward_message(message: str, to_user: bool = True):
    """
    Forward sub-agent response directly to user without supervisor synthesis.

    Use when:
    - Sub-agent response is final and complete
    - Supervisor synthesis would lose important details
    - Response format must be preserved exactly
    """
    if to_user:
        return {"type": "direct_response", "content": message}
    return {"type": "supervisor_input", "content": message}
```

当子智能体可以直接响应用户时，优先采用群体架构而非监督者架构，因为这样可以彻底消除转译错误。

**模式 2：点对点/群体**
移除中央控制，并允许智能体根据预定义协议直接通信。任何智能体都可以通过显式的交接机制将控制权转移给其他任意智能体。

```python
def transfer_to_agent_b():
    return agent_b  # Handoff via function return

agent_a = Agent(
    name="Agent A",
    functions=[transfer_to_agent_b]
)
```

在以下情况下选择此模式：任务需要灵活探索、僵化规划会适得其反，或者需求会动态出现且无法预先分解。

需要考虑以下权衡：不存在单点故障，并且能够有效地进行广度优先扩展，但协调复杂度会随智能体数量增加而上升；如果缺少中央状态维护者，偏离目标的风险也会增大，因此稳健的收敛约束变得至关重要。

定义带有状态传递的显式交接协议。确保智能体将其上下文需求传达给接收方智能体。

**模式 3：分层式**
将智能体组织为不同的抽象层级：战略（目标定义）、规划（任务分解）和执行（原子任务）。

```
Strategy Layer (Goal Definition) -> Planning Layer (Task Decomposition) -> Execution Layer (Atomic Tasks)
```

在以下情况下选择此模式：项目具有清晰的层级结构、工作流涉及管理层级，或者任务同时需要高层规划和细节执行。

需要考虑以下权衡：关注点分离清晰，并且支持不同层级采用不同的上下文结构，但层级之间存在协调开销，战略与执行可能不一致，并且错误传播路径较为复杂。

### 将上下文隔离作为设计原则

将上下文隔离视为多智能体架构的主要目的。每个子智能体都应在一个专注于其子任务的干净上下文窗口中运行，而不携带从其他子任务累积而来的上下文。

**隔离机制**
为每个子任务选择合适的隔离机制：

- **完整上下文委派** — 与子智能体共享规划者的全部上下文。适用于子智能体需要完整理解的复杂任务。子智能体拥有自己的工具和指令，但会接收完整上下文以便做出决策。注意：这会在一定程度上违背上下文隔离的初衷。
- **指令传递** — 通过函数调用创建指令；子智能体仅接收其所需的内容。适用于简单且定义明确的子任务。这样可以保持隔离，但会限制子智能体的灵活性。
- **文件系统记忆** — 智能体读取持久化存储中的内容并向其写入数据。适用于需要共享状态的复杂任务。文件系统充当协调机制，避免因传递共享状态而导致上下文膨胀。它会带来延迟和一致性方面的挑战，但比消息传递方式更具可扩展性。

根据任务复杂度、协调需求和可接受的延迟进行选择。默认采用指令传递；当需要共享状态时，升级为文件系统记忆。除非子任务确实需要，否则应避免委托完整上下文。

### 共识与协调

**投票问题**
避免简单多数投票——这种方式会将弱模型的幻觉与强模型的推理同等对待。如果不加干预，多智能体讨论会因其固有的趋同倾向，逐渐演变为对错误前提达成共识。

**加权投票**
根据置信度或专业水平对智能体的投票进行加权。置信度更高或更具领域专业知识的智能体，应当在最终决策中拥有更大的权重。

**辩论协议**
组织智能体在多轮交互中相互批评对方的输出。对于复杂推理，对抗性批评通常比协作式共识能带来更高的准确率。应防止谄媚式趋同，即智能体为了表现得随和而彼此赞同，而不是为了得出正确结论。

**基于触发器的干预**
监控多智能体交互中的行为标志。当讨论没有取得任何进展时，激活停滞触发器。当智能体模仿彼此的答案而没有独立推理时，检测并激活谄媚触发器。

### 框架考量

不同框架以不同的理念实现这些模式。LangGraph 使用具有显式节点和边的基于图的状态机。AutoGen 使用基于对话/事件驱动的模式，并提供 GroupChat。CrewAI 使用基于角色的流程，并采用分层式团队结构。

## 实用指南

### 失败模式与缓解措施

**失败：监督者瓶颈**
监督者会累积来自所有工作智能体的上下文，从而容易出现上下文饱和和性能退化。

缓解方法是约束工作智能体的输出模式，使其仅返回提炼后的摘要。使用检查点持久化监督者状态，从而无需在上下文中携带完整历史记录。

**失败：协调开销**
智能体之间的通信会消耗令牌并增加延迟。复杂的协调可能会抵消并行化带来的收益。

缓解方法是通过清晰的交接协议尽量减少通信。尽可能批量处理结果。采用异步通信模式。衡量多智能体协调与使用更长上下文的单个智能体相比，是否确实能够节省时间。

**失败：目标偏离**
在缺乏中央协调的情况下，追求不同目标的智能体会偏离预期目标。

缓解方法是为每个智能体定义清晰的目标边界。实现收敛检查，以验证是否正在朝共同目标推进。为智能体执行设置存活时间限制，以防止无边界探索。

**失败：错误传播**
一个智能体输出中的错误会传播给使用该输出的下游智能体，并不断累积，导致结果越来越错误。

缓解方法是在将智能体输出传递给使用方之前对其进行验证。实现带有熔断器的重试逻辑。尽可能使用幂等操作。考虑添加一个验证智能体，在关键输出进入流水线之前对其进行交叉检查。

## 指南

1. 将上下文隔离设计为多智能体系统的主要优势
2. 根据协调需求而非组织隐喻选择架构模式
3. 实现包含状态传递的显式移交协议
4. 使用加权投票或辩论协议达成共识
5. 监控监督者瓶颈并实现检查点机制
6. 在智能体之间传递输出之前对其进行验证
7. 设置生存时间限制以防止无限循环
8. 显式测试失败场景

## 注意事项

1. **监督者瓶颈的扩展问题** — 监督者的上下文压力会随着工作智能体数量的增加而呈非线性增长。当工作智能体达到 5 个以上时，监督者处理摘要所消耗的 token 会超过工作智能体执行实际任务所消耗的 token。为每个监督者管理的工作智能体数量设置硬性上限（3-5 个），并增加第二层监督者，而不是让单个监督者过载。
2. **低估 token 成本** — 多智能体运行的成本约为基准成本的 15 倍。团队经常会低估预算，因为他们只估算每个智能体的成本，而没有考虑协调开销、重试和多轮共识。按 15 倍成本编制预算，任何低于这一水平的结果都可视为额外收益。
3. **迎合式共识** — 采用辩论模式的智能体往往会趋同于令人接受的答案，而非正确答案。LLM 天生存在倾向于认同的偏差。可通过分配明确的对抗性角色，并要求智能体在获准达成共识之前陈述分歧来抵消这一问题。
4. **智能体无节制扩张** — 智能体数量超过 3-5 个后，继续增加智能体会产生收益递减，并增加协调开销。每增加一个智能体，通信通道的数量都会呈二次方增长。应从满足需求的最少智能体数量开始，仅在存在明确的上下文隔离优势时才增加智能体。
5. **消息传递中的传话游戏** — 信息在智能体之间传递时，会因反复摘要而逐渐失真。每个智能体都会进行改述并丢失细节。对于需要由多个智能体准确访问的状态，应使用文件系统协调，而不是消息传递。
6. **错误传播级联** — 一个智能体的幻觉会成为另一个智能体眼中的“事实”。下游智能体无法区分上游的幻觉与真实信息。应在智能体之间添加验证检查点，并且未经验证绝不信任上游输出。
7. **过度分解** — 将任务拆分得过细，会导致协调开销超过任务本身。一个由 10 个智能体组成的 10 步流水线，在移交上消耗的 token 会多于实际工作。仅当子任务确实能从独立上下文中受益时才进行分解。
8. **缺少共享状态** — 在没有共享文件系统或状态存储的情况下运行的智能体会重复工作、产生不一致的输出，并无法追踪已经完成的工作。在构建多智能体工作流之前，应先建立共享的持久化存储。

## 集成

此技能负责智能体拓扑结构和协调协议。相邻技能分别负责项目形态、托管运行时和潜在状态传递：

- `project-development`：在确定拓扑结构细节之前，进行项目级单智能体与多智能体选择。
- `hosted-agents`：远程沙箱、会话、热池和多人协作基础设施。
- `memory-systems`：跨智能体共享持久状态。
- `tool-design`：工具专业化以及生成/状态工具契约。
- `context-optimization`：将分区作为一种令牌效率优化策略。
- `latent-briefing`：当模型一致时，在编排器和工作智能体之间进行 KV 缓存轨迹交接。
- `evaluation`：衡量在计入协调成本后，多智能体是否能改善结果。
