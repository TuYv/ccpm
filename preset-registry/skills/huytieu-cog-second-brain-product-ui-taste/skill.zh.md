# product-ui-taste：密集产品界面的反俗套 Skill

> 仪表板、数据表格、表单、向导、设置、列表/详情、管理控制台、应用外壳。不适用于落地页、作品集或营销页面（那是 `taste-skill`）。不适用于图表（那是 `dataviz`）。不适用于原生移动端。
> 每条规则都具有**上下文相关性和机械性**。它是否触发取决于你正在构建的界面，而不是自动触发。先阅读界面、规划框架预算，然后只提取适合的部分。
> **配套约定：**`taste-skill` 明确将“仪表板 / 密集型产品 UI / 数据表格 / 多步骤表单”交给“合适的工具”。这个 Skill 就是那个工具。如果需求一半是营销页面、一半是产品界面（例如包含嵌入式实时仪表板的落地页），营销主视觉/营销区块使用 `taste-skill`，产品界面使用此 Skill。永远不要在同一个组件上同时运行两者。

## 0. 产品审视（先阅读界面，再做任何其他事情）

营销 UI 依赖第一印象。产品 UI 则要经受真实数据下、用户为完成工作而进行的**第一百次**使用。俗套设计的失败模式也不同：不是“模板化的审美”，而是**一接触真实数据就夭折的原型**——表格让整个页面横向滚动、按钮把自己的标签截断、同一个灰色“无数据”框被重复用于三种不同情况、用户因误触一个字段而导致表单清空。

### 0.A 先阅读这些信号
1. **界面类型**——最重要的一项判断。类型包括：**索引/表格**（用于扫描、筛选、选择记录列表）、**详情/记录**（单个实体及其字段和相关数据）、**仪表板/概览**（KPI + 小组件 + 一到两个表格）、**表单/设置**（输入和配置）、**多步骤流程/向导**（顺序执行的任务）、**控制台/可观测性**（日志、指标、部署）、**信息流/消息**（项目流）。大多数真实界面都是其中两到三种类型的组合（索引 + 详情抽屉；仪表板 + 下钻表格）。
2. **数据形状和规模**——p95 时有多少行，一行有多宽，单元格是统一的还是参差不齐，数据是实时/流式的还是静态的，字段是否可能为空/null/非常长。
3. **密度需求**——交易员的驾驶舱和消费者设置页都属于“产品 UI”，但它们需要完全相反的密度。判断是：专家日常工作界面（紧凑、键盘优先）还是偶尔使用的消费者界面（舒适、宽容）。
4. **后果等级**——主要操作是信息性的（查看）、可逆的（重命名、移动），还是破坏性/不可逆的（删除、部署、扣款）。这会决定确认机制、默认焦点以及是否适合自动保存。
5. **用户是谁，以及他们被允许做什么**——角色、只读查看者、套餐/许可证层级。产品 UI 存在营销 UI 永远不会有的状态：无权限、只读、套餐锁定（第 6.G 节）。现在就读取这些信息，不要等到构建完正常流程后才处理。
6. **现有系统**——是否已经存在 Carbon/Fluent/Polaris/Atlaskit 应用，或者已有一套内部设计令牌？产品 UI 几乎从来不是从零开始的。在引入自己的审美之前，先匹配宿主系统。

### 0.B 生成前输出一行“Product Read”

在任何代码之前，声明：**“将其理解为：面向 \<user> 的 \<surface type>，采用 \<density> 密度、\<data volume> 数据量，后果等级为 \<level>，构建于 \<design system | house tokens | none> 之上。”**

示例：
- *“将其理解为：面向内部运营人员的索引+详情抽屉，采用紧凑密度，约 2k 行（进行虚拟化），后果可逆，构建于内部设计系统（Table + 侧面板检查器）之上。”*
- *“将其理解为：面向终端客户的设置/表单界面，采用舒适密度，数据量较低，后果混合（账单操作 = 破坏性操作），构建于内部设计系统的表单布局之上。”*

### 0.C 最重要的反默认原则：使用行，而不是卡片

让产品界面看起来像 AI 原型的最快方式，就是**把每条记录都包在一个带 Badge 的 Card 中**。用户需要扫描、筛选、排序或选择的密集数据，应当放在**行**中（列式数据使用 Table，单行数据使用 List/Item），横向铺满容器，使用分隔线，并将行高控制在 32-40px。Card 是一个**组件容器**（KPI 磁贴、图表面板、设置分组、画廊条目），绝不是列表项的包装器。[Material3 lists; Carbon] 如果你看到记录列表时的第一反应是使用 Card 网格，请停下来重新阅读这一行。

### 0.D 如果需求不明确，只问一个问题，然后继续

几乎总是值得询问的问题，是关于**数据量或后果**的问题（它们会改变架构）：“数据量较大时大约有多少行？”或“这个操作是否可逆？”其他所有信息，都根据 Product Read 推断并声明你的假设。不要进行访谈式提问。

### 0.E 反默认纪律

模型对产品 UI 的默认做法是：Card 堆砌、会溢出页面的固定宽度 `<table>`、把 `disabled` 提交按钮作为唯一的校验方式、一个通用的空状态、`z-index: 9999`，以及每次加载都显示全页 spinner。下面的内容分别为每一种做法提供了具体的正确替代方案。当你发现自己正准备采用其中一种时，这就是打开对应章节的信号。

## 1. 三个旋钮（核心配置）

在 Product Read 之后，设置三个旋钮。与为富有表现力的营销页面调节 VARIANCE / MOTION / DENSITY 的 taste-skill 不同，产品旋钮是针对**信息处理工作**进行调节的。产品 UI 中几乎刻意不使用动效；动效用于反馈，而不是装饰。

* **`DENSITY: 2`** - 1 = 舒适/消费者，2 = 标准，3 = 紧凑/驾驶舱。它决定行高、内边距比例、字号，以及是否提供密度切换器。
* **`DATA_COMPLEXITY: 2`** - 1 = 简单列表（普通 Table/List），2 = 可排序+可筛选+可选择的表格，3 = 企业级网格（冻结列、虚拟化、列管理、实时数据）。
* **`CONSEQUENCE: 2`** - 1 = 信息展示/只读，2 = 可逆变更，3 = 破坏性/不可逆/财务操作。它决定确认操作的默认行为、是否适合自动保存、错误提示的语气，以及“未保存的更改”提示的醒目程度。

**基线：`2 / 2 / 2`**（带详情视图的标准 SaaS 产品表格）。根据 Product Read 进行覆盖。

### 1.A 旋钮推断

| 信号 | DENSITY | DATA_COMPLEXITY | CONSEQUENCE |
|---|---|---|---|
| “内部管理 / 运营工具 / 专家日常使用工具” | 3 | 2-3 | 2 |
| “企业数据控制台 / 网格 / 分析” | 3 | 3 | 2 |
| “消费者设置 / 账户 / 引导流程” | 1 | 1 | 1-2 |
| “SaaS 产品仪表板（默认）” | 2 | 2 | 2 |
| “账单 / 删除 / 部署 / 权限界面” | 匹配 | 匹配 | 3 |
| “可观测性 / 日志 / 实时指标” | 3 | 3 | 1 |

### 1.B 用例预设
| 预设 | DENSITY | DATA_COMPLEXITY | CONSEQUENCE | 框架 |
|---|---|---|---|---|
| 内部管理工具 | 3 | 2 | 2 | AppShell + SideNav，选择时显示检查器 |
| SaaS 产品仪表板 | 2 | 2 | 2 | AppShell + SideNav 或 TopNav + TabList |
| 企业数据控制台 | 3 | 3 | 2 | AppShell + SideNav，全高网格 |
| 消费者设置/账户 | 1 | 1 | 1-2 | AppShell + 设置模板（导航 + 表单面板） |
| 多步骤向导 | 1 | 1 | 2-3 | 居中列、步骤条、不添加干扰性的界面装饰 |

### 1.C 这些旋钮如何驱动输出
在推理中使用这些确切名称作为全局变量。`DENSITY` 控制行高和密度切换器决策（第 10.A 节）。`DATA_COMPLEXITY` 控制表格深入分析（第 7 节）的深度。`CONSEQUENCE` 控制第 6.G、8.E、8.F、9.A 节。不要自行发明别名。

## 2. 产品原型 → 设计系统映射

产品 UI 几乎从来不是手写 CSS。先根据宿主应用选择基础系统，再考虑产品原型。**每个应用只使用一个系统。** 不要将 Carbon 与 Fluent 混用，也不要把 shadcn 放进 Polaris 的组件树中。

### 2.A 优先使用现有系统（发现，而不是猜测）
如果应用已经有设计系统，则应优先使用该系统，你的首要任务是**弄清楚它实际提供了什么**，而不是凭想当然进行假设。大多数成熟系统已经解决了本技能所关注的密集型界面问题，因此你很少需要退回到原始 CSS。猜测组件名称和 props，是智能体生成看起来正确但无法编译的代码时最常见的原因。

在编写 UI 之前，针对宿主系统的真实 API（其 CLI、文档网站或 `.d.ts` 文件）确认以下各项：

| 需求 | 要寻找的内容 | 解决方式 |
|---|---|---|
| 全页面外壳 | 一个 app-shell 原语及其导航插槽 | 查阅系统文档中的“layout”或“app shell”页面 |
| 多面板工具 / 检查器 | 一个布局组件 + 侧面板组件的组合，而不是两个浮动的 div | 查阅“layout”页面；确认面板是否可调整大小 |
| 列式数据 | 系统的 Table 及其排序/选择/分页插件 | 查阅组件参考，而不是博客示例 |
| 粘性 / 冻结列 | 专用 hook 或插件（大多数系统都会提供） | 在手写实现之前，先搜索文档中的“sticky”或“frozen” |
| 可调整大小的列 | 列宽调整 hook | 同上 |
| 分页页脚 | 表格分页 + 每页大小控制 | 查阅组件参考 |
| 搜索 + 筛选工具栏 | 区别于普通搜索的工具栏/筛选组件 | 查阅组件参考 |
| 单行记录 | List / Item 组件组合 | 查阅组件参考 |
| 空白区域 | EmptyState 组件 | 查阅组件参考 |
| 状态 / 元数据 | 区别于 Badge 的状态指示器 | 查阅令牌/状态文档 |

**始终遵循以下工作流程：** 找到系统已经提供的最接近的页面或区块模板，研究其布局骨架，然后阅读你所使用的每个组件的真实 props。**绝不要自行发明 props。** 优先使用系统自带的布局组件，而不是原始的 `<div>`，以便间距始终遵循系统的尺度。每个值都使用设计令牌（`var(--color-*)`、间距令牌），绝不要使用原始十六进制颜色值或 px。Badge 仅用于数量和枚举状态；状态应使用状态指示器。

**设计系统桥接（化解这一张力）：**第 5-10 节中的 CSS 机制（滚动归属、`position:sticky` 标题、冻结列偏移量、z-index 层级、`min-width:0`）其实正是成熟系统的 hooks 在底层已经满足的**契约**。在此类系统内部，应优先使用 hook 或插件，因为真正的粘性列 hook 会正确处理偏移量、纯色背景和阴影分隔线。只有在以下情况下，才应回到底层 CSS 契约：(a) 当有内容穿透显示时，用于验证系统是否正确实现；或 (b) 当你完全处于设计系统之外。系统 Table 中存在 hook 时，绝不要使用内联样式手写粘性列。

### 2.B 外部系统（匹配宿主系统，或按原型选择）
| 原型 / 简述 | 选择 | 原因 |
|---|---|---|
| IBM 风格的企业分析、密集网格 | `@carbon/react` + `@carbon/styles` | 最成熟的数据密度 + 2x 网格 + 空状态/加载状态模式 [carbon] |
| Microsoft / 企业 SaaS、DataGrid | `@fluentui/react-components` (v9) | 官方 Fluent 2、Overflow 原语、tokens [fluent] |
| Atlassian / Jira 风格产品 | `@atlaskit/*` + `@atlaskit/tokens` | 根据语义选择的间距 tokens [atlaskit] |
| 商户/管理后台、资源列表 | Polaris（`@shopify/polaris` 或 web components） | IndexTable、四状态理念、错误内容 [polaris] |
| GitHub 风格开发者工具 chrome | `@primer/react` / `@primer/css` | PageLayout 地标、Blankslate、Truncate [primer] |
| 自适应/规范化布局、偏消费端 | `@material/web` + Material 3 tokens | 窗口尺寸类别、列表-详情/辅助面板 [material3] |
| 代码自主管理的精简内部工具 | Radix Primitives + shadcn/ui + TanStack Table | 无头 a11y 原语，样式由你负责 [radix, tanstack] |
| 企业级 React 高密度数据场景，追求快速交付 | Ant Design 或 Mantine + Mantine React Table | 开箱即用的 Table/Form [ant, mantine] |
| 精简的键盘优先体验（Linear/Vercel 风格） | Radix/shadcn + 自定义 tokens | 密度 + 命令面板 + 克制 [linear, vercel] |

**诚实原则：**如果应用属于上述某一种，请使用官方 package 及其 Table/Form/Dialog。不要用原始 CSS 重建 Carbon 的数据表格。不要导入某个系统的 tokens 后再覆盖其中的 90%。

## 3. 以框架优先的 APP SHELL 架构

**在写下第一行内容之前，先用像素规划框架。**真实应用是自上而下构建的：选择 shell，命名其区域，为每个区域分配明确的 px 预算，决定其容器策略和响应式行为，然后再填充内容。以内容为先的布局（先写各个区块，再分别用 Card 包裹）会产生一列带有内边距的滚动内容，看起来像原型。[most systems' layout docs]

### 3.A 选择 shell
- **AppShell**（标题栏和/或侧边导航）- 默认的全页面产品框架。
- **Layout + LayoutContent + LayoutPanel** - 多窗格工具：浏览器、控制台、主从布局以及带检查器的界面。
- **普通内容列** - 单个表单、设置区块、向导。

### 3.B 区域 px 预算（牢记这些数值）
| 区域 | 预算 |
|---|---|
| 侧边导航 | 240-280px |
| 图标栏（折叠后的导航） | 64-72px |
| 详情 / 检查器面板 | 340-420px（可调整大小：320-480） |
| 筛选器 / facet 栏 | 220-260px |
| 行高 | 32px 紧凑 / 40px 标准 / 48px 舒适 [密集型系统预算为 32-40；Carbon 提供 5 个相对层级，不设固定 px] |
| 标题栏 / 顶部导航 | 48-64px（常见的应用栏惯例） |

### 3.C 地标区域（不要混淆它们）
为每个区域使用真实的地标名称，并了解它们之间的区别 [primer PageLayout]：
- **Header** - 全宽，位于顶部，用于应用外壳。
- **Content** - 主要区域，通过 flex 扩展以填充空间。
- **Pane** - 位于 Content **旁边**的次要区域，仅与内容等高。用于检查器或辅助信息。
- **Sidebar** - **全高**导航区域，与 Pane 有明确区别。绝不要构建一个实际上是内容高度 Pane 的“sidebar”，也不要构建一个实际上是全高导航的“pane”。
- **Footer** - 全宽，位于底部（状态栏、分页上下文）。

### 3.D 规范布局（识别并搭建）[material3]
- **List-detail** - 左侧为列表，右侧为选中的记录。在约 1024px 以下，详情会覆盖显示或变为单独的路由。
- **Supporting-pane** - 主要内容约占 2/3，辅助面板约占 1/3。
- **Feed** - 单一滚动流（行/气泡，流中不使用卡片）。
- **Master-detail with inspector**（工具的骨干）- 选择一行后打开一个**固定宽度的 LayoutPanel 检查器**，而不是离开当前页面进行导航。添加 `resizable`。在约 1024px 以下，将其改为覆盖显示，而不是压缩 Content。

### 3.E 营销 UI 永远不会有的应用外壳控件
- **Workspace / org switcher** - 几乎每个 SaaS 外壳都需要一个，固定在侧边导航顶部或 header-left，显示当前租户的名称/头像。点击后打开下拉菜单（不是模态框），列出工作区；当工作区达到 8 个以上时提供搜索字段、一个“最近使用的工作区”分组，以及底部的“创建/加入”操作。它用于切换上下文（数据范围），不是导航目标。将其保持为一个元素；绝不要把租户选择分散到导航列表中。为每个用户持久化最近一次激活的工作区。
- **Global command palette**（Cmd/Ctrl-K）- 对于 DATA_COMPLEXITY >= 2 的键盘优先工具，这是最快的导航方式。应将其视为一级外壳功能，而不是可有可无的增强功能。
- **Background-job / async status tray** - 当应用启动并发的长时间运行操作（导入、导出、部署）时，持久化的通知托盘（带有数量徽标的 header 图标，点击后打开作业下拉菜单）优于每个作业一个模态框。每个作业行显示确定进度条、取消操作，以及带有结果链接的最终成功/错误状态。Carbon 的规则是：对于超过几分钟的等待，让用户离开，并在完成时通知用户。绝不要让整个 UI 阻塞于一个后台作业。[carbon loading]

### 3.F 按区域制定容器策略（按原型决定使用 Cards 还是 Rows）
| Archetype | Container policy |
|---|---|
| Tracker / work tool (issues, tickets, CRM) | 仅使用 Rows。使用分组的边到边列表，完全不使用卡片。 |
| Console / observability | 仪表板小组件使用卡片网格；其他所有内容使用 Table。 |
| Messaging / feed | 使用 Rows 和气泡。流中不使用卡片。 |
| Media / gallery | 使用卡片网格（ClickableCard）+ 详情中的密集元数据行。 |
| Settings / forms | 使用 FormLayout 分区；仅使用 Card 对危险操作/计费操作进行分组。 |

禁止：为每个列表项使用一个 Card（卡片汤）；将全宽 Card 叠放作为页面结构；嵌套 Card；将 Badge 作为装饰。

## 4. 布局硬性规则（违反其中任何一条都会导致交付的作品无法正常运行）

* **滚动归属（产品 UI 布局中排名第一的问题）。** 每个滚动轴必须恰好由 **一个** 包装器负责（`overflow:auto`）。页面的 `<body>` **绝不能** 横向滚动。宽表格应在自己的容器内滚动，而不是把整个应用向侧面撑开。粘性表头应使用作用域限定在该滚动包装器内的 `position:sticky`，**绝不能** 使用相对于视口的 `position:fixed`。[carbon, ant table-scroll, tanstack] 如果两个嵌套元素同时滚动同一个轴，那就是一个 bug。
* **每个粘性元素都需要一个具有边界高度的祖先元素。** 如果没有祖先元素建立滚动边界，`position:sticky` 会静默失效。粘性表头要求表格的滚动容器具有实际的最大高度。[css mechanics]
* **承载文本的 flex 子元素必须设置 `min-width:0`。** flex/grid 子元素默认使用 `min-width:auto`，这会拒绝缩小到内容尺寸以下，因此 `text-overflow:ellipsis` 会静默失效，子元素反而会把布局撑得更宽。flex 行中的任何截断文本都需要在承载文本的子元素上设置 `min-width:0`。这是“我的省略号为什么不起作用”最常见的原因。[overflow-truncation]
* **提前声明响应式契约，并按区域分别定义。** 在填充内容之前，先写明各区域会在什么断点折叠、覆盖或隐藏。不要假设“Tailwind 会处理好一切”。导航栏应折叠为图标栏或移出画布的 MobileNav；检查器应在约 1024px 以下以覆盖层显示；宽表格应保持水平滚动，而不是重新排列列。
* **断点：使用尺寸类别，而不是设备名称。** 使用紧凑 / 中等 / 扩展（Material 3），或将 Carbon 的精确 2x 网格断点（320 / 672 / 1056 / 1312 / 1584，8px 迷你单位、16px 内边距、32px 间距）作为备用网格。[material3, carbon 2x-grid]
* **可复用组件使用容器查询。** 出现在宽 Content 区域和窄 Pane 中的卡片或面板，应根据**自身**宽度响应，而不是视口宽度。对于任何会在多个区域宽度中渲染的内容，使用 `container-type` + `@container`，而不是视口媒体查询。[joshwcomeau, responsive-layout]
* **侧边栏折叠 = 移出画布或图标栏，而不是原地缩窄。** 将 260px 的导航缩窄到 180px 只会让它变得拥挤。应折叠为 64-72px 的图标栏（带工具提示），或将其滑出画布，并保留一个持久显示的重新打开条。在调整大小或折叠时保留已显示面板的状态，避免用户丢失上下文。
* **密度是一种布局模式，而不是 CSS 缩放。** 至少应提供 DENSITY 刻度盘所要求的密度预设，并将其作为真正的切换功能（切换行高和内边距 token），而不是使用浏览器缩放技巧。[i18n-a11y-density, carbon 5 row heights]
* **绝不要在文本容器上硬编码固定宽度。** 徽章、按钮、表头、芯片、标签必须使用自动布局（flex/grid，自适应内容宽度），以便文本能够重新排列或扩展。固定宽度的文本容器在真实数据和翻译场景下都会发生裁切（第 10.B 节）。
* **用于比较的数字应使用表格式数字。** 用户会在纵向比较的任何数字列或数字列表，都应使用 `font-variant-numeric: tabular-nums`，使数字对齐。在指标列中使用比例数字是一种明显的错误信号。

## 5. 溢出与截断目录（深入探讨）

产品 UI 才是实际字符串出现的地方：90 个字符的文件路径、德语按钮标签、只有一个单词或长达四十个单词的客户姓名。截断应当是一把手术刀，而不是默认方案。

### 5.A 永不截断清单（强制要求）
**永远不要截断主要内容或标识性内容**：标题、实体名称、唯一 ID、错误和验证消息、页面标题、按钮标签。截断仅适用于**次要/补充内容**（描述、次要元数据、面包屑中间部分）。[carbon overflow, primer truncate] 如果标识字符串过长，应当换行、为其提供更多空间，或使用保留两端的中间截断（适用于路径/ID）——绝不要使用隐藏了区分两条记录所需部分的尾部省略号。

### 5.B 每个被截断的字符串都需要真正的完整文本回退方案
仅在悬停时显示的 `title` 工具提示**不是**无障碍回退方案：它无法服务于仅使用键盘的用户、触摸设备用户和语音识别用户。应当在获得焦点和悬停时都提供完整文本，或支持在行内展开，或在详情视图中提供完整文本。[carbon, primer]

### 5.C 较长的按钮标签（强制要求，产品 UI 的典型特征）
**永远不要截断按钮标签。** 按照内容调整按钮尺寸（“hug contents”），并设置 `min-width` 下限，以满足点击目标的无障碍要求。如果标签很长（或经过翻译），在考虑截断之前，先允许其最多换成 2 行，并重新评估标签文案。显示为“Save chang...”的按钮意味着工作未完成。仅图标按钮需要 `aria-label` 和工具提示。[overflow-truncation, i18n]

### 5.D 单行省略号方案
`overflow:hidden; text-overflow:ellipsis; white-space:nowrap;` **以及**文本与滚动/行容器之间每个 flex 祖先元素上的 `min-width:0`（第 4 节）。如果缺少这条 `min-width:0` 链，CSS 将不会生效。

### 5.E 多行截断方案（`-webkit-line-clamp`）
四个属性必须同时存在，否则都无法正常工作：`display:-webkit-box; -webkit-line-clamp:N; -webkit-box-orient:vertical; overflow:hidden;`。**绝不要将内边距放在被截断元素本身上**——截断计算会忽略内边距，导致文本溢出。如果需要内边距，应将截断元素包裹在带内边距的父元素中，或使用固定高度回退方案（`line-height * N`）。[css-tricks line-clampin]

### 5.F 内容边界情况：计数、大数字、缺失数据（强制要求）
真实数据可能是 0、1 或 1,000,000——这三种情况都要设计，而不只是演示中的“3”。
- **零 / 一个 / 多个（复数形式）：**每个计数字符串都必须正确处理 0、1 和 N，并符合语法——“0 items”、“1 item”、“24 items”，绝不能出现“1 items”或“24 item”。使用支持 ICU/复数形式的格式化程序，绝不要进行字符串拼接；某些语言最多有 6 种复数形式。零值通常应进入空状态（第 6.C 节），而不是让“0 items”孤零零地出现在完整布局中。
- **非常大 / 非常精确的数字：**在密集场景中，为便于快速浏览，可以使用缩写（1.2k、3.4M、1.1B），但必须在悬停/获得焦点时以及详情视图中提供精确值；**绝不要缩写用户必须精确操作的数字**（例如发票总额、账户余额）。使用符合地区设置的分组格式（1,234.56 与 1.234,56）、对比列使用 tabular-nums（第 4 节），并在切换到缩写前设定一致的阈值。
- **缺失 / null / 不适用（一般规则，不仅适用于表格单元格）：**null 字段应渲染为一致且低调的占位符（“Not set”、“-”、“Unknown”），并在视觉上区别于空字符串和零值。应针对每个字段决定 null 表示“尚未设置”（邀请用户输入）、“不适用”（简要说明原因），还是“因权限而隐藏”（第 6.G 节）——这是三种不同的占位符，绝不能使用一个空白值，让用户误以为是渲染错误。
- **较长的无分隔符标记**（URL、哈希值、文件路径、没有空格的 ID）：使用保留两端的中间截断，或使用 `overflow-wrap:anywhere`；绝不要使用隐藏了用于区分内容的尾部的省略号，也绝不能让该标记撑破其所在列的宽度。

### 5.G 列标题和界面元素溢出
- **列标题**：换行显示为 2 行，随后截断，并通过 tooltip 展示完整标题。 [carbon]
- **面包屑**：将中间部分折叠为省略号/溢出菜单，保留第一个和最后一个。 [carbon overflow]
- **工具栏 / 操作栏 / 标签页**：使用 priority-plus 溢出模式（Fluent Overflow）：声明可见优先级顺序和 `minimumVisible` 下限，将其余项目移入“更多”菜单，并按反向 DOM 顺序渲染，使第一个项目优先显示。 [fluent]
- **较长的自由内容块**：对于可展开的文字内容使用“显示更多 / 显示更少”，对于列表使用“加载更多”（第 7.D 节）。

## 6. 状态矩阵（深入探讨）

每个数据显示区域都不只有理想路径。应在 **页面、组件/区域和字段** 三种粒度上设计完整矩阵。最糟糕的做法，是为每种非理想状态都复用同一个灰色方框。

### 6.A 四种基础状态必须始终一并设计
对于任何加载数据的区域，在交付理想状态之前，先设计好 **理想 / 加载中 / 空 / 错误** 状态。 [polaris four-states, nngroup]

### 6.B 加载时间阈值（强制要求）
- **< 1 秒**：不显示任何内容。一闪即逝的骨架屏比短暂的静止状态更糟。
- **1-10 秒，整页/区域加载**：使用**与真实布局形状一致的骨架屏**（即将呈现的实际行/字段），绝不能只是只有边框的灰色方框，也绝不能对结构化内容使用 spinner。 [nngroup skeleton, carbon loading]
- **> 10 秒，或时长未知的任务**（上传、下载、转换、部署）：使用**确定性进度条**，绝不能使用不确定性 spinner 或骨架屏。对于持续数分钟的任务，应允许用户离开，并在完成后通知用户。 [carbon]
- **已显示数据的后台刷新**：保留旧内容可见，同时显示低调的内联指示器。刷新时**绝不能重新清空**缓存内容并显示 spinner/骨架屏。

### 6.C 空状态是三种不同的状态（强制要求）
绝不能在以下状态之间复用同一个空状态组件/消息：
1. **尚未使用过（首次运行）**——采用引导语气：说明这是什么，并提供创建第一条记录的主要 CTA。 [primer empty-states, pencilandpaper]
2. **筛选/搜索后无结果**——显示“没有关于 X 的结果”，并提供清除筛选条件的操作。数据是存在的；原因在于筛选条件。
3. **零结果是一种胜利**——例如“收件箱为空”“没有提醒”。采用积极的语气，不要设置带有负罪感的 CTA。
[carbon empty-states, atlaskit empty-state] 对于很小的磁贴/侧边面板，居中的纯文本空状态是“镜像布局”规则的例外。

### 6.D 错误状态绝不是空状态
加载失败**始终**是 ErrorState，绝不是 EmptyState。错误文案应具体、使用通俗语言、可执行（说明下一步该做什么），并携带供支持人员使用的错误代码/ID。所有错误都应通过一个共享的 ErrorState 组件处理，以保持语气和布局一致；绝不要交付一个简单的“发生错误”。 [polaris error-messages, nngroup]

### 6.E 字段和内联状态
字段有自己的微状态：异步校验进行中（第 8.D 节）、内联错误、成功确认、保存中/已保存（自动保存，第 8.E 节）。不要让字段级失败悄无声息地无任何反应。

### 6.F 部分加载、过期和离线状态（必须考虑）

“已加载”和“失败”之间还存在真实网络环境会产生的状态：

- **部分加载 / 部分失败：**当复合视图加载时某个小组件失败，应当**就地**让**该小组件**失败（显示其自身的内联 ErrorState + 重试），绝不要因为一个面板失败就将整个页面置空。一个损坏的磁贴导致所有磁贴都失效的仪表板就是 bug。
- **过期 / 缓存 / 刷新中：**显示最近一次成功获取的数据，并配合不显眼的“正在更新”指示器以及“上次更新于 <time>”时间戳；后台刷新时绝不要重新显示骨架屏导致页面再次置空（第 6.B 节）。刷新失败时，保留过期数据，并显示非阻塞式提示：“无法刷新，当前显示的是 <time> 的数据”。
- **离线 / 断开连接：**检测连接丢失，显示持久的非模态横幅，禁用或**排队**处理变更，并在重新连接时进行协调。绝不要让用户在一个实际上无法静默保存的表单中输入内容。
- **乐观更新契约：**如果你在服务器确认之前就渲染变更，那么你**必须**提供回滚路径——恢复之前的值，并在写入失败时显示清晰的错误。没有回滚机制的乐观更新是数据完整性方面的警示信号。

### 6.G 权限和计划状态（仅限产品 UI，必须考虑）

营销 UI 没有这些概念；产品 UI 则依赖它们：

- **无权限 / 角色限制：**应有意识地决定采用**禁用还是隐藏**。对于用户永远不可能拥有的操作，将其隐藏；对于用户在角色变更后可能拥有的操作，将其禁用（并在悬停或聚焦时说明原因）。绝不要显示一个没有任何解释的无效控件。
- **只读模式：**保持相同的布局，将输入框渲染为静态值，并提供清晰的“只读”提示，而不是显示看起来像损坏了一样的灰显输入框。
- **计划 / 许可证锁定：**锁定功能提示（“升级以解锁”）是一种独立状态，应使用其专属组件——可见、有解释并提供升级路径——而不是一个禁用按钮。[保持与宿主应用已有的先例一致。]

## 7. 数据表深度解析（最难处理的产品界面）

根据 DATA_COMPLEXITY 控制深度。简单列表需要 7.A-7.B；企业级网格则需要全部内容。**在设计系统内部，使用其 `Table` 以及系统提供的插件/钩子；下面的机制是这些钩子需要满足的契约，也是脱离设计系统时的指导。**

### 7.A 滚动归属和粘性表头（必须）

一个包装器同时负责两个轴（`overflow:auto`），并设置有界高度；页面绝不进行横向滚动（第 4 节）。通过 `position:sticky; top:0` 实现粘性表头，且**作用域限定在该包装器内**。[carbon, ant table-scroll]

### 7.B 冻结 / 固定列（必须采用的方案）

`position:sticky` + 明确的 `left:0`（或 `right:0`）偏移量 + `z-index >= 10`（高于滚动主体）+ **不透明的纯色背景，并且该背景还要覆盖悬停和选中行状态** + **内嵌式 `box-shadow` 分隔线，绝不要使用 CSS `border`**（在粘性滚动下边框会消失或重复渲染）。如果遗漏纯色背景，滚动内容就会透过冻结列显示。[ant, mantine-react-table column-pinning, tanstack]

### 7.C 虚拟化（DATA_COMPLEXITY 3）
超过约 100-200 行后进行虚拟化。必需的 DOM 结构：**两个包装器**——外层 = 视口高度的可滚动容器，内层 = 完整的虚拟内容高度（一个占位元素）。**绝不要将 `<table>` 元素本身设置为完整的虚拟高度**——这会扭曲行高，并使粘性表头折叠（因为表头无法脱离过短的父元素）。[tanstack virtual #640] 不要在虚拟渲染期间附加逐行样式对象或逐行菜单实例（性能会严重下降）；除非已进行记忆化，否则使用 `columnResizeMode:"onEnd"`。[ant, mantine]

### 7.D 分页 vs. 无限滚动 vs. 加载更多（决策树）
- 当索引超过约 50 项时进行**分页**（具体采用 Polaris 的分界值）；对于“查找特定项目 / 比较相距较远的项目 / 查看最前面的几项”这类任务，则始终使用分页。[polaris, smashingmagazine]
- **无限滚动**：仅适用于探索式、同质化、无尽的信息流——**绝不要**用于搜索结果或比较任务。如果使用无限滚动，应提供 `history.pushState()`，以便返回按钮恢复滚动位置（超过 90% 的实现都错误地处理了这一点）。在移动端，加载一个更大的扁平批次（15-30 项），绝不要在滚动过程中分块延迟加载（活动滚动期间触发的请求并不可靠）。[nngroup infinite-scrolling, baymard]
- **“加载更多”按钮**：对于有限但很长的列表，这是安全的折中方案；由用户控制获取数据。

### 7.E 选择、批量操作与选择持久性
- 行选择支持 Shift-click 范围选择和全选。在文案中区分“全选 N 项（跨页面）”与“全选本页”。[polaris]
- **选择持久性（经典的企业级正确性 bug）：** 在分页、排序和筛选变化时，保留已选行的 **IDs**；页面变化时不要静默丢弃选择。显示一个在导航过程中仍然保留的实时“已选择 N 项”计数。
- 在批量操作进行期间，禁用逐行操作，以防止发生冲突的变更。
- **工具栏操作上限为 5 个可见的主要操作**，其余操作放入溢出菜单。[polaris]

### 7.F 筛选、分面与搜索（彼此不同）
- **搜索**（自由文本）和**筛选**（结构化谓词）是不同的控件；不要将它们不加说明地合并为一个输入框。根据数据类型匹配每个筛选控件（日期范围、枚举多选、数值范围）。[data-table-mechanics；大多数系统会提供工具栏筛选组件]
- **已应用筛选条件标签**：在表格上方以可移除的标签行显示活动筛选条件，并提供“全部清除”；对于包含许多分面的情况，还应提供分面侧边栏。这是目前 Jira/Linear/Notion 的标准模式；没有标签行，用户就无法查看或撤销当前正在筛选其数据的条件。

### 7.G 单元格内容
单元格中包含不规则的真实数据。按照第 5 节的规定截断次要单元格（同时确保完整文本可通过聚焦访问），但绝不要截断标识性单元格。数值列右对齐，并使用 tabular-nums（第 4 节）。空单元格 = 统一的“未设置”占位符（禁止使用破折号；使用 "-" 或 "Not set"），绝不要留白，以免看起来像渲染 bug。

## 8. 表单、验证与多步骤流程（深入探讨）

### 8.A 标签位置
默认将标签置于顶部（最快速浏览，最利于本地化和移动端）。仅在垂直空间紧张的密集型企业表单中，将标签右对齐。仅在需要有意放慢用户操作、引导其仔细完成任务时，将标签左对齐。在本地化产品中绝不要将标签右对齐（文本扩展会破坏列布局）。[lukew web-form, nngroup web-form-design]

### 8.B 校验时机
在 **失去焦点** 和 **提交** 时进行校验，而不是在用户输入不完整值的每次击键时进行校验（不要在用户输入第一个字符时就大喊“邮箱无效”）。例外情况是密码强度这类实时的正向辅助提示。在字段旁显示行内错误，**并且**在提交时于顶部显示汇总错误摘要，绝不能只显示其中一种。[nngroup errors-forms, polaris inline-error]

### 8.C 绝不能将禁用“提交”作为唯一提示（强制要求）
对于包含 5 个或更多字段的表单，**绝不要**让禁用的“提交”按钮成为唯一反馈——用户无法判断缺少什么。允许用户提交，然后显示错误总数并将焦点移至第一个错误。只有在简单（少于 3 个字段）的表单中，才可以使用禁用的“提交”按钮。**提交失败后始终保留用户输入**——绝不要清空表单。[forms-flows, nngroup]

### 8.D 异步 / 远程字段校验
对其进行防抖处理，**并且**使用 `AbortSignal` 取消已被后续请求取代的请求——未取消的慢速响应可能会覆盖更新且正确的结果（用户名可用性竞态）。[forms-flows]

### 8.E 自动保存（按 CONSEQUENCE 控制）
- 自动保存应按**逻辑字段组**进行，绝不要在每次击键时保存整个表单。
- **绝不要自动保存**密码、可见性/权限、机密性或具有财务影响的字段——这些字段需要显式手动确认（CONSEQUENCE 3）。
- 在失去焦点时触发，并在最后一次击键约 3 秒后触发。显示“正在保存…”然后显示“已保存 <relative time>”。
- 自动保存失败时，应显示带重试选项的**持久**提示（不会自动消失），绝不能静默失败。

### 8.F 多步骤流程 / 向导
- 步骤指示器必须对应**真实**步骤；已完成的步骤应可点击返回。不要使用虚假的“阶段 1 / 阶段 2”标签——应直接命名实际步骤。[taste-skill tell parity]
- 通过减少**字段数量**而不是增加步骤来解决用户放弃向导的问题。不要在流程中途插入追加销售内容。[baymard checkout-linear]
- 保持流程线性；分支式向导需要提供清晰可见的地图。

### 8.G 破坏性 / 不可逆操作确认（CONSEQUENCE 3，强制要求）
对于删除/部署/收费操作的确认对话框，默认将键盘焦点置于安全操作（“取消”）上，而不是破坏性操作上。使用 `role="alertdialog"`、`aria-modal="true"` 以及指向警告文本的 `aria-describedby`。对于高影响的删除操作，必须要求用户输入资源名称，才能启用破坏性按钮。关闭时，将焦点返回到打开对话框的元素（或下一个逻辑元素）。[w3 alertdialog, radix dialog]

## 9. 导航、叠加层与分层（深入探讨）

### 9.A 对话框 / 模态框
打开时锁定焦点，关闭时恢复焦点，按 Escape 键关闭；仅在非破坏性操作中允许点击叠加层关闭。即使在视觉上隐藏，也**绝不能省略** `Dialog.Title` 和 `Dialog.Description`（屏幕阅读器会读出它们）。[radix dialog, w3 dialog-modal]

### 9.B Toast / 通知
默认约 5000ms，**悬停和聚焦时暂停**，滑动关闭阈值约为 50px，可手动关闭。针对屏幕阅读器的优先级，应区分前台播报（用户自己的操作已成功）和后台播报（某些内容发生了变化）。绝不要在 toast 中放置破坏性操作确认。[radix toast]

### 9.C 菜单、下拉菜单、选项卡、组合框
完整的键盘交互契约：方向键导航、Home/End、按键快速跳转、roving tabindex（第 10.D 节）。Tab 在复合组件与下一个内容之间移动；方向键在复合组件**内部**移动。需要保持键盘可访问的菜单/选项卡项应使用 `aria-disabled`，而不是原生的 `disabled`（后者会将其从 Tab 顺序中移除）。[radix, w3 grid]

### 9.D z-index / stacking-context 系统（强制要求，取代临时的 z-index）
- **为每个层级分配较大的数值间隔**，并一次性定义为 tokens，例如 base 0、sticky 100、dropdown 1000、sticky-header 1050、overlay/drawer 1100、modal 1200、popover 1300、toast 1400、tooltip 1500。绝不要孤立地手动调整单个 z-index；应参照整个层级刻度进行修改。临时使用 `9999`/`99999` 是一个警示信号。
- **在调试层叠问题前，枚举每一个 stacking-context 触发条件**：带有 z-index 的 `position:fixed/sticky`、`opacity < 1`、指定上下文属性的 `transform` / `filter` / `will-change`、`contain`、`container-type`、`isolation:isolate`、top-layer 元素。[mdn stacking-context]
- **嵌套的 stacking context 是原子化的**：深层嵌套元素上的巨大 z-index **无法**胜过浅层祖先的兄弟元素。如果菜单被裁剪在标题栏后面，修复的应是祖先上下文，而不是设置更大的数值。
- **Overlay 应按打开顺序分层**，而不是为每种类型设置静态常量：最后打开的 overlay 获胜。在可用时，使用 layering manager / 平台的 top-layer（`<dialog>`、popover API）。

## 10. 密度、I18N 与无障碍（深入探讨）

### 10.A 将密度作为一等模式
提供 >= 3 个密度预设（comfortable / standard / compact），作为真正的切换选项，用于替换行高和内边距 tokens，而不是缩小后的缩放效果。[i18n-a11y-density] Carbon 提供 5 种行高；选择适合你的 DENSITY 刻度所需的那组。

### 10.B 国际化文本扩展预算（强制要求）
设计容器时应为翻译预留空间，因为英语是最短的 UI 语言之一：
- 德语：通常 **+30-40%**，最差情况下最高约 +70%。
- 法语 / 俄语 / 西班牙语：+20-25%。
- 芬兰语：最高 +100%（长度翻倍）。
- CJK：会收缩，而不是扩展。
绝不要对文本容器硬编码固定宽度（第 4 节）。使用 flex/grid，使文本重新流动，而不是被裁剪。伪本地化（在字符串周围包裹带重音符号的填充文本）是一种快速的冒烟测试，可发现约 80% 的扩展问题。[crowdin, i18n-a11y-density]

### 10.C RTL
只镜像**具有方向性的**图标（后退/前进箭头、尖括号、进度方向）。**绝不要**镜像通用图标（时钟、播放、对勾、徽标）。即使在 RTL 文本中，数字也应保持 LTR 形态。主要操作按钮移到左侧（这是 RTL 阅读扫描的自然末端）。进度条从右向左填充。[crowdin]

### 10.D ARIA 网格键盘契约（任何包含可聚焦单元格的自定义网格/表格都必须遵守）
- **Roving tabindex**：恰好一个单元格具有 `tabindex="0"`，其他单元格均为 `-1`；网格容器本身永远不是 Tab 停靠点。
- 方向键在单元格之间移动，并且**限制在边界内**（到达行/列边缘时不循环）。
- **Home/End** 在当前行内移动；**Ctrl+Home / Ctrl+End** 跳转到网格的第一个/最后一个单元格。
- **Page Up/Down** 仅适用于可滚动网格（移动约 5 行）。
[w3 grid data-grids] 如果使用真正的设计系统 Table（Carbon、Fluent、Polaris、Ant），这些功能已经得到处理——不要重复实现。只有在手动构建网格时，才需要采用这一契约。

### 10.E 横向适用的 a11y 底线
- 触控目标 >= 44-48px（触控场景），>= 24px（密集型桌面端）。[material3 accessibility]
- 使用 `:focus-visible`，绝不要使用会在鼠标点击时闪现的裸 `:focus`；除非用其他方式替代，否则绝不要移除焦点轮廓。
- 每个仅包含图标的控件都必须具有 `aria-label`。
- 使用符合区域设置的数字/日期/货币格式；绝不要发布含义不明确的 `01/02/2025`。

## 11. 入门与渐进式披露

密集型产品会让用户在首次使用时不堪重负。逐步展示高级能力；让复杂性随着使用逐渐显现。

**渐进式披露（默认机制）：**
- 将高级控件（批量编辑、列管理、已保存视图、API/webhook 配置）放在一次交互之内（“更多”、展开器、设置弹出框），不要一次性全部显示在屏幕上。Linear 的原则是：简单易用地开始，逐渐变得更强大。[linear]
- **经验法则：一个区域内超过 7 个控件时，就应触发披露。** 将主要的 3-5 个操作以内联方式分组，其余操作放入溢出菜单；将高级设置放在带标签的展开器后面，绝不要使用没有工具提示、令人摸不着头脑的齿轮图标。
- 披露应按界面区域分别处理，而不是全局统一：不要隐藏用户两次点击前刚刚使用过的控件。

**首次运行（必须遵守）：**
- 首次运行应显示**“从未使用过”空状态**（第 6.C.1 节），而不是空白网格或加载指示器。用一句话说明这个界面是什么，并指向唯一的首个操作（“创建你的第一个项目”），而不是列出十个选项。
- 仅在示例/演示数据有明确标记且可以一键移除时才提供这些数据；绝不要留下用户无法区分真实数据的虚假“Acme Inc”行。

**引导提示、产品导览、清单（除非可关闭，否则禁止）：**
- 任何引导提示、产品导览或入门清单都**必须**在第 1 步即可跳过，并且可以永久关闭；关闭状态应按用户跨会话持久化（绝不要再次触发已关闭的导览）。无法跳过的导览，或没有关闭入口的清单，都是一种 **Tell**。
- 同时最多只能有一个处于活动状态的导览；绝不要在模态框上叠加引导提示。
- 导览应指向真实界面中的真实控件；绝不要使用虚假的高亮截图。退出时应将用户带回可用状态，而不是带到死胡同。
- 区分回访用户/有经验的用户与受邀队友，让他们跳过首次运行流程；不要让加入已有数据工作区的用户重新进行入门引导。

**从空状态到高效工作的路径：**每个空状态的 CTA 都必须在 <=3 步内引导用户完成真正能创造价值的操作。只会链接到文档的入门清单只是装饰。

## 12. 上下文感知的主动性（需要识别的规范骨架）

当产品需求符合以下某一种时，应搭建完整骨架，而不是片段：
- **索引/表格页面**：标题 + 工具栏（搜索、筛选、主要操作、密度）+ 已应用筛选条件的标签 + Table（固定表头、选择）+ 分页页脚 + 三种空状态 + 错误状态。
- **列表-详情 / 主从布局**：列表区域 + Inspector LayoutPanel，在约 1024px 以下时覆盖显示 + “未选择任何内容”空状态。
- **设置页面**：分区导航 + FormLayout 面板 + 自动保存或保存栏 + 仅在危险区域周围使用 Card。
- **多步骤向导**：真正的步骤指示器 + 线性步骤 + 每步验证 + 审核步骤 + 非破坏性退出。
- **仪表板/概览**：KPI 磁贴行（Cards）+ 小组件网格 + 一个或两个可深入查看的 Table（行）。
- **带批量操作的管理控制台**：表格 + 选择状态持久化 + 批量操作栏（最多显示 5 项，其余放入溢出菜单）+ 确认对话框。

完整的组件实现位于宿主系统中，此处不重复：通过宿主系统的模板/骨架命令或其文档（`references/canonical-sources.md`）访问它们。`references/block-skeletons.md` 中实现了三个高价值骨架，因为它们体现了最容易出错的契约；应将其视为规范形态，并根据宿主系统进行调整。

## 13. 性能与无障碍防护规范
- 表格加载/筛选响应应让人感觉即时；超过约 1 秒时显示乐观反馈/加载反馈，超过 6.B 中的阈值时升级处理。
- 企业级网格性能：渲染时不要为每一行分配样式/菜单对象；限制自动调整大小的作用域；除非进行了记忆化，否则使用 `columnResizeMode:"onEnd"`；超过约 100-200 行时进行虚拟化。
- 产品 UI 中的动效仅用于**反馈**：状态转换、焦点移动、行进入/离开。不要使用装饰性滚动动画、跑马灯或视差效果。所有内容都应尊重 `prefers-reduced-motion`。
- Core Web Vitals 仍然适用：CLS < 0.1（骨架屏必须预留真实尺寸，以避免内容跳动），交互时 INP < 200ms。

## 14. 深色模式
由令牌驱动，每个应用锁定一种主题（遵循 taste-skill 第 8/11 节的相同规范：应用内不能有区域中途切换为反转主题）。使用宿主系统的语义层令牌（`var(--color-*)`、Carbon `$layer`/`$border-subtle` 等），绝不要使用硬编码的灰色值。在两种模式下测试表格、冻结列（实心背景必须是**主题令牌**，否则在深色模式下会出现背景透出）、覆盖层和焦点环。只在 shell 根部设置一次主题，绝不要按分区设置。

## 15. 产品 UI 的 AI 痕迹（禁止模式）

这与 taste-skill 的落地页痕迹不同。以下是模型伪造产品界面的典型特征。除非需求确实要求，否则严禁使用。

- **卡片汤**：每条记录都包在 Card + Badge 中。应使用行。（第 0.C 节）
- **会导致页面横向滚动的固定宽度 `<table>`**：不要使用自身不承载滚动的包装器。（第 4 节）
- **被截断的按钮标签**（“保存更改...”）。应根据内容调整大小。（第 5.C 节）
- **被截断的身份识别内容**（名称/ID/错误信息），并仅通过悬停显示 `title`。（第 5.A-B 节）
- **在包含 5 个以上字段的表单中，将 `disabled` Submit 作为唯一验证方式**。（第 8.C 节）
- **在首次运行、筛选结果为空和加载失败时重复使用同一个通用空状态**。（第 6.C-D 节）
- **“发生错误”**，却没有原因、操作或代码。（第 6.D 节）
- **永远不会结束的骨架屏**，或只显示框架的灰色方框，且不映射真实布局。（第 6.B 节）
- **在缓存背景刷新时使用全页面加载指示器**（让用户正在阅读的数据重新变为空白）。（第 6.B 节）
- **背景透明的固定/冻结列**（滚动时底层内容会透出）。（第 7.B 节）
- **临时拼凑的 z-index**（`9999`、`99999`），而不是分层的令牌刻度。（第 9.D 节）
- **固定宽度的徽标/标签/选项卡**，在德语/芬兰语文本扩展时被裁切。（第 4、10.B 节）
- **对本应保持键盘可访问的菜单/选项卡项使用原生 `disabled`**（应使用 `aria-disabled`）。（第 9.C 节）
- **将徽标作为装饰**，以及**在每一行滥用状态圆点**（仅表示状态，且应谨慎使用）。
- **在工作工具中为了炫技而使用动效**（装饰性滚动/悬停动画）。（第 13 节）
- **虚假的步骤标签**（“阶段 1 / 阶段 2”）、虚假的精确数字，以及在已交付界面中使用“Jane Doe”/“Acme”占位数据。
- **任何可见位置的 Em-dash（`—`）**。标题、单元格、标签、空状态/错误文案、工具提示中均禁止使用，也不能将其作为“未设置”单元格的占位符。应使用连字符（`-`）。这是违反次数最多的单项痕迹；零容忍。（taste-skill 第 9.G 节，内部规则）

## 17. 重设计协议（审查现有高密度屏幕）
在调整视觉样式之前，先审查那些比美观更重要的正确性问题：
1. **Scroll ownership** 违规（页面横向滚动；嵌套的双重滚动）。
2. **主要内容被截断**；仅在悬停时提供备用内容。
3. **缺少状态区分**（三个状态共用一个空框；没有错误状态；缺少 skeleton）。
4. **冻结列内容穿透**；透明的 sticky 背景。
5. **z-index 临时拼凑**；嵌套 stacking context 导致的分层错误。
6. **没有 i18n 缓冲空间**；固定宽度的文本容器。
7. **键盘/a11y 缺口**：没有 roving tabindex、裸露的 `:focus`、没有标签的图标按钮、仅将禁用提交作为唯一提示信号。

先修复这些问题。然后再应用密度、token 和视觉层面的精修。保留宿主设计系统；不要为了“重设计”而将 Carbon 替换为 shadcn。

**逐项检查。任何一项失败，都表示该界面尚未完成。**

- [ ] **Product Read** 是否已说明（第 0.B 节的一句话）？
- [ ] 是否根据 Product Read 设置了 **Dials**（DENSITY / DATA_COMPLEXITY / CONSEQUENCE），而不是默默使用基线值？
- [ ] 是否在内容之前以 px 规划了 **Frame**；是否命名了 shell + landmark 区域（没有混淆 Header/Content/Pane/Sidebar）？
- [ ] 对于高密度数据是否使用 **Rows 而不是 cards**；Card 仅用于 widgets；没有 card soup，也没有嵌套 cards？
- [ ] **Scroll ownership**：每个轴恰好只有一个 wrapper，页面绝不横向滚动，sticky 的作用域限定在该 wrapper 内？
- [ ] 每个会截断的 flex 文本子元素是否都有 `min-width:0`？
- [ ] **没有被截断的主要内容**（名称/ID/错误/标题），也**没有被截断的按钮标签**；每次截断是否都有可通过焦点到达的完整文本备用内容？
- [ ] **Line-clamp recipe** 是否完整（全部 4 个 props，clamped 节点上没有 padding）？
- [ ] 每个数据区域是否都设计了 **四种状态**（ideal/loading/empty/error）？
- [ ] **Loading thresholds**：<1s 时不显示任何内容，skeleton 镜像布局，>10s 时显示确定性进度，缓存刷新绝不重新显示空白？
- [ ] 是否有 **三种不同的空状态**（首次运行 / 筛选后为空 / 零值即成功）；加载失败是否使用包含原因 + 操作 + code 的 ErrorState？
- [ ] 是否处理了 **部分/过期/离线状态**（一个 widget 失败时仅在原位失败；缓存刷新绝不重新显示空白；离线时排队或阻止操作并显示通知；乐观更新是否有回滚路径）？
- [ ] **内容边界情况**：计数是否进行了复数化（0/1/N，不出现“1 items”）；大数字是否进行了缩写，同时可触达精确值，并且在精度重要时绝不缩写；缺失数据是否使用与零值/空值一致且有区别的占位符？
- [ ] 在存在角色/层级时，是否考虑了 **权限/计划状态**（禁用与隐藏、只读、计划锁定）？
- [ ] **Table**：是否有负责滚动的 wrapper + 有界高度；sticky header；冻结列是否具有实心的 theme-token 背景 + inset-shadow 分隔线 + z-index；virtualization 是否使用了双 wrapper DOM？
- [ ] 是否正确选择了 **分页与无限滚动**（>50 条或用于搜索时分页；无限滚动仅用于带 pushState + 移动端扁平批次的 feed）？
- [ ] **Selection** 是否在翻页/排序/筛选后保持；批量工具栏是否限制为最多 5 项 + overflow？
- [ ] 存在筛选条件时，是否显示 **Applied-filter chips** 行；搜索与筛选是否为不同的控件？
- [ ] **Forms**：默认使用顶部标签；在 blur+submit 时进行验证；同时提供行内错误和汇总错误；提交失败时保留输入内容；字段数达到 5 个或以上时，没有将禁用提交作为唯一提示信号？
- [ ] **Async validation** 是否进行了防抖处理，并通过 AbortSignal 取消？
- [ ] **Autosave** 是否按组进行；密码/权限/财务字段是否不使用 Autosave；是否有 Saving/Saved 状态，并在失败时提供持久的重试？
- [ ] **Destructive confirm** 是否将焦点放在安全操作上，使用 `role=alertdialog`，并在关闭时返回焦点？
- [ ] **Dialogs** 是否捕获并返回焦点、支持 Escape-close、包含 Title/Description；**toasts** 是否在悬停时暂停并可关闭？
- [ ] **z-index** 是否来自分层的 token scale（没有 9999）；分层错误是否追溯到 stacking contexts，而不是使用更大的数字？
- [ ] 每个文本容器是否都有 **i18n 缓冲空间**（德语增加 +30-40%）；没有硬编码的固定宽度文本；比较的数字是否使用 tabular-nums？
- [ ] 如果 RTL 在范围内，是否仅镜像方向性图标？
- [ ] **Keyboard/a11y**：自定义 grids 上是否使用 roving tabindex，使用 `:focus-visible`，图标按钮是否有标签，键盘可到达的菜单项是否使用 `aria-disabled` 而非 `disabled`，目标尺寸是否为 44px/24px？
- [ ] 在 DENSITY 要求时，是否提供 **Density switch**（切换模式，而不是缩放）？
- [ ] **Dark mode** 是否锁定为一个主题，冻结列背景是否为 theme token，是否在两种模式下都经过测试？
- [ ] **House system**：props 是否来自真实文档中的发现（没有自行发明）；没有使用 `<div>` 进行布局；仅使用 tokens；Badge 仅用于计数；状态是否通过 status indicator 表示？
- [ ] 是否没有第 15 节中的 **Product-UI Tells**；可见内容中是否**完全没有 em dash**？
- [ ] 每个应用是否只使用**一个设计系统**（没有混用 Carbon + Fluent）？

如果有任何一项无法诚实地勾选，请在交付前修正。
