# Skill Creator

一个用于创建新技能并对其进行迭代改进的技能。智能体的上下文预算是主要约束，因此此 SKILL.md 通过链接指向聚焦于特定主题的参考文件。

核心循环：

1. 确定技能应该做什么以及应该如何实现
2. 编写草稿
3. 使用测试提示词对可访问该技能的 Claude 运行测试
4. 与用户一起评估结果（通过 `eval-viewer/generate_review.py` 进行定性审查，并结合定量评估）
5. 根据反馈和基准测试结果修订技能
6. 重复上述过程直到满意；扩充测试集，并再次进行规模化测试

识别用户当前处于此循环的哪个阶段，并从那里开始。完全从头创建新技能 → 从第 1 步开始。已有草稿 → 直接进入第 3 或第 4 步。用户希望凭感觉迭代，不进行正式评估 → 支持这种方式。技能稳定后，可以选择运行描述改进器来优化触发效果。

## 两条入口路径

该技能支持两种不同的工作流。**在执行任何其他操作之前，先确定用户正在走哪条路径**——两条路径的起始步骤不同。

- **路径 A——从头创建新技能。** 用户希望固化一个工作流、将某种模式编写成规范，或构建一种新能力。从下文的 **“创建技能”** 开始（捕获意图 → 访谈 → 编写 SKILL.md → 测试 → 评估）。
- **路径 B——改进现有技能。** 用户指向一个已经存在的技能，并希望使其达到标准、修复问题、进行优化，或根据评估反馈迭代。**不要从捕获意图开始**——意图已经编码在现有的 SKILL.md 中。从下文的 **“改进现有技能”** 开始。

如果请求含糊不清（“你能看看这个技能吗？”），则假定为**路径 B**，并在像对待新技能一样开始访谈之前进行确认。当对技能目录或文件调用 `/skill-creator` 时，也会触发路径 B。

两条路径都必须遵守以下强制规则：**编辑前同步仓库**、**版本管理**、**YAML Frontmatter 安全**以及**审查/评估时进行 Frontmatter 审计**。无论采用哪条路径，都要应用这些规则。

## 步骤完成报告

完成每个主要步骤后，按以下格式输出状态报告：

```
◆ [Step Name] ([step N of M] — [context])
··································································
  [Check 1]:          √ pass
  [Check 2]:          √ pass (note if relevant)
  [Check 3]:          × fail — [reason]
  [Check 4]:          √ pass
  [Criteria]:         √ N/M met
  ____________________________
  Result:             PASS | FAIL | PARTIAL
```

调整检查项名称，使其与该步骤实际验证的内容相符。使用 `√` 表示通过，使用 `×` 表示失败，并使用 `—` 添加简短的上下文说明。“Criteria”行汇总满足了多少项验收标准。“Result”行给出总体结论。

**意图捕获阶段检查项：** `Worth building`、`Goal defined`、`Triggers identified`、`Output format agreed`

**技能编写阶段检查项：** `SKILL.md written`、`README generated`、`Subagents designed`、`Predictability pass`（来自 _Make it predictable_ 的 7 项评分标准——每项满足时标记为 √，不满足时标记为 × 并指出缺口）、`Adversarial review`（已处理全新子智能体发现的问题）

**测试阶段检查项：** `Evals created`、`Runs completed`、`Viewer launched`

**迭代阶段检查项：** `Feedback incorporated`、`Benchmarks improved`、`Description optimized`

## 与用户沟通

用户的技术熟悉程度差异很大。应根据上下文线索调整术语的使用——使用「JSON」或「断言」等术语时，需要有依据表明用户了解它们；如有疑问，请简要定义相关术语。

## 修改仓库的技能必须遵循的规则

创建或更新任何会更改 git 仓库中文件（代码、文档、配置、提交、发布）的技能时，请在该技能的 SKILL.md 中包含以下规则：

- 在靠近顶部的位置添加一个 **「编辑前同步仓库（强制）」** 章节，要求在修改前执行 `branch="$(git rev-parse --abbrev-ref HEAD)"; git fetch origin && git pull --rebase origin "$branch"`。
- 如果工作树存在未提交的更改：先暂存更改，再同步，之后恢复暂存的更改。
- 如果缺少 `origin` 或发生冲突：停止操作，并在继续之前询问用户。

不得交付缺少此预同步防护措施的仓库修改型技能。

## Frontmatter 规则（强制）

阅读 `references/frontmatter-rules.md` 以了解完整的强制规则：

- **版本管理**——创建时设置 `metadata.version: 1.0.0`；每次编辑时递增补丁版本号、次版本号或主版本号。
- **YAML Frontmatter 安全性**——任何包含 YAML 特殊字符的字符串值都必须使用双引号括起来（完整列表见参考文档）。
- **审查/评估时的 Frontmatter 审计**——检查必填字段、名称与目录是否匹配、允许使用的顶层键、`metadata.version`、`metadata.author`、YAML 安全性，以及与 `docs/README.md` 的一致性。首先运行 `python scripts/quick_validate.py <skill-path>`；它无需 LLM 推理即可发现机械性问题。

这些规则适用于每次写入。保存前务必确认已遵守这些规则。

## 创建技能

### 明确意图

首先理解用户的意图。当前对话中可能已经包含用户希望固化的工作流（例如，他们说「把这个变成一个技能」）。如果是这样，请先从对话历史中提取答案——使用过的工具、步骤顺序、用户做出的更正，以及观察到的输入/输出格式。由用户补充缺失信息并在继续之前进行确认。

**首先设置门槛——这真的应该成为一个技能吗？** 只有当工作流具有**重复性**（将来还会再次出现）、**非显而易见性**（有能力的智能体若没有它也会做错）和**稳定性**（流程不会在下个月发生变化）时，技能才有存在的价值。如果不满足其中任何一项，请建议不要创建技能——一次性任务更适合使用普通提示词处理，而且每个不必要的技能都会干扰其他技能的触发。用户可以推翻这一建议；设置此门槛是为了避免默认答案总是「创建技能」。

1. 这个技能应该让 Claude 能够做什么？
2. 这个技能应在何时触发？（哪些用户表述/上下文）
3. 预期的输出格式是什么？
4. 是否应该设置测试用例来验证技能是否有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。输出较为主观的技能（写作风格、艺术创作）通常不适合。根据技能类型建议恰当的默认选项，但让用户做最终决定。
5. **这个技能是否应该使用子智能体？** 阅读 `references/subagent-patterns.md` 以获取完整指南。关键信号：
   - 技能是否会读取大量文件或扫描大型代码库？→ 探索型子智能体
   - 工作的各个部分能否并行运行？→ 并行工作型子智能体
   - 技能是否需要独立的质量审查？→ 使用全新子智能体的审查循环
   - 技能是否会生成需要专注推理的大型产物？→ 执行型子智能体
     如果符合其中任何一项，请采用主智能体作为编排者的架构来设计技能，让子智能体负责繁重工作，并保持主对话上下文整洁。
6. **由模型调用还是由用户调用？** 在起草之前确定_主要_调用方式——它会影响你的写作方式。**模型调用型**（默认）是智能体在情境合适时应用的一套可复用规范；应优化描述以确保可靠触发。**用户调用型**（`/skill-name`）是由用户主动运行的编排流程（管线、成本高昂或具有破坏性的操作）；正文应体现「用户已要求执行此操作，继续进行」。这里也要权衡**上下文负载和认知负载**预算。完整的权衡说明请参阅 `references/predictability-rubric.md`。

### 访谈与研究

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。在这部分内容明确之前，不要编写测试提示词。检查可用的 MCP——如果子智能体可用，则通过它们并行开展研究；否则直接在当前上下文中研究。

**在起草正文之前梳理技能的分支。** 识别技能运行时的不同模式——即需要不同指令的路径（创建与改进、不同框架、不同环境、试运行与实际应用）。预先了解这些分支后，你就可以在 SKILL.md 开头放置一个简短的选择器，并且仅在实际使用某一分支时才展示该分支特有的内容，而不必强迫每次运行都读取所有分支。本技能顶部的“两个入口路径”区块本身就是一个分支选择器示例。参见 `references/predictability-rubric.md` → _在起草之前梳理分支_。

### 编写 SKILL.md

起草之前，先浏览 `references/exemplars.md`，并模仿最接近此技能的原型——工作流型、知识型或编排型。然后，根据用户访谈填写：

- **name**：1–64 个字符，仅限小写字母、数字和连字符，不得出现连续连字符，并且必须与父目录名称完全一致。由 `scripts/quick_validate.py` 强制校验。
- **description**：说明何时触发以及执行什么操作。它是主要的触发机制。必须为单行，不得包含换行。Claude 往往会_触发不足_——应让描述稍微更“积极”一些，并加入否定触发条件。
- **effort**（可选）：`low | medium | high | xhigh | max`。默认为 `high`。
- **metadata.version**：Semver 字符串（参见 frontmatter 规则）。
- **compatibility**：所需工具或依赖项（很少使用）。

#### 编写良好的描述

阅读 `references/description-guide.md` 获取完整指南：积极触发 + 否定触发模式（使用“不要用于……”子句点名 2–3 个相邻领域）、每个分支设置一个触发条件，以及三项长度限制。最先产生影响的规则是：**目标长度 ≤250 个字符**——Claude Code 的 `/skills` 列表会从尾部开始截断超出该长度的内容，从而切掉否定触发子句。当否定子句看起来缺失时，`scripts/quick_validate.py` 会发出警告（不会导致失败）。

### 技能编写指南

阅读 `references/writing-guide.md` 获取完整指南。其中涵盖：

- **技能的组成结构**——目录布局，以及 `agents/`、`references/`、`scripts/`、`assets/`、`docs/` 的放置位置。
- **渐进式披露**——三级加载、SKILL.md 的 500 行上限，以及何时应拆分到 `references/` 中。
- **无惊讶原则**——不得包含恶意软件，不得编写具有误导性的技能。
- **编写与工作流模式**——祈使语气、严格规定输出格式、示例以及工作流模式表。
- **捆绑脚本与错误消息**——脚本在退出前必须输出描述清晰的错误，使智能体能够自行纠正。
- **步骤完成报告**——每个技能在每个主要阶段结束后都要生成一份报告。
- **写作风格**——解释_原因_，而不是大量使用 MUST。
- **生成 README.md**——仅生成 `docs/README.md`，并包含 AI 跳过通知；参见 `references/readme-template.md`。
- **测试用例**——至少 5 个提示词（≥3 个正常路径、≥1 个边界情况、≥1 个不应触发的情况），保存到 `evals/evals.json`；参见 `references/schemas.md`。
- **评估前的 LLM 验证**——强制性对抗审查背后的各个阶段；参见 `references/validation-prompts.md`。

### 使其可预测（构建即达到发布就绪状态）

在这里创建技能的目标是形成一个**可预测的流程**——智能体每次运行都遵循同一条可靠路径——并让交付的技能直接达到**发布就绪**状态，而无需之后再通过 `skill-auto-improver` 进行清理。请阅读 `references/predictability-rubric.md`，了解完整标准及其可检查的通过/失败门槛；以下是在*编写过程中*需要应用的要点：

- **严格的完成标准。** 对于分步骤的工作流，应在每个主要步骤的结尾设置一个智能体能够*检查*而非凭感觉判断的门槛——与命令、文件状态或数量挂钩。上文的步骤完成报告格式就是实现这一点的载体（`√/×` 检查项 + 一行 `Result:`）。严格的标准可以阻止智能体过早宣布成功；这正是可重复流程与仅凭希望的流程之间的区别。
- **对非通用材料进行渐进式披露。** 任何特定于分支、篇幅较长或并非每次运行都需要的内容，都应放入 `references/`，并通过一行指引链接过去（具体机制见 `references/writing-guide.md` → *渐进式披露*）——这样可以降低上下文负载，并将 SKILL.md 控制在 500 行以内。
- **引导词。** 对反复出现的概念，用一个简短且承载核心含义的术语命名一次（“原子提交”“软失败”“发布就绪”），之后重复使用该术语，而不是每次使用时都重新解释。
- **精简检查——完成前执行。** 明确执行一次检查，以删减**重复内容**（同一指令出现在两个位置——只保留一个归属位置，并从其他位置链接过去）、**陈旧沉积**（遗留指导、失效引用、过时名称）、**内容蔓延**（章节篇幅超出其价值、本应改为表格或引导词的散文式说明）以及**无效指令**（不会改变智能体行为的语句——如“请谨慎”“运用良好判断”——应替换为可检查的标准，或直接删除）。这一步最常用于区分由 skill-creator 编写、已经完备的技能，与仍需 `skill-auto-improver` 处理的技能。

完成前，**逐项检查全部 7 个评分项**（`references/predictability-rubric.md`——上述四项，再加上调用方式选择、分支映射和发布就绪），并将结果作为技能编写步骤完成报告中的 `Predictability pass` 行输出：每个已满足项标记为 `√`，任何缺口标记为 `×` 并注明具体问题。这能让评分项检查过程显式可见，而非静默完成——`×` 表示发布前需要修复的信号，而不是阻断项。

`skill-auto-improver` 仍然是用于修复*外部编写*或*遗留*技能的工具——而不是通过此流程创建技能时必需的第二阶段。

### 对抗性审查（评估前强制执行）

起草上下文无法审查自己的草稿——它会凭记忆补全每个缺口，而不是仅依据页面上的内容。完成评分项检查后，启动一个**全新的子智能体**，向其提供技能草稿以及 `references/validation-prompts.md` 的第 1–3 阶段（发现、逻辑演练、边界情况攻击）；它将返回触发条件遗漏、含糊步骤和破坏性提示。运行评估前修复实际发现的问题；其余发现则纳入测试集。如果没有可用的 Agent 工具，请在全新会话中自行执行这些阶段（见 `references/environment-modes.md`）。

## 运行和评估测试用例

阅读 `references/eval-loop.md`，了解完整的 5 步流程（启动运行、起草断言、记录耗时、评分/汇总/查看、阅读反馈）。其中涵盖了使用技能 + 基线子代理的模式、`eval_metadata.json` 和 `timing.json` 格式、`generate_review.py` 的调用方式，以及如何读取 `feedback.json`。

不要使用 `/skill-test` 或任何其他测试技能——此技能要求采用 `references/eval-loop.md` 中的流程。

## 改进现有技能

这是顶部入口路径块中的**路径 B**。它包含两个不同的子路径——根据用户的要求进行选择。

### 子路径 B1——改造现有技能以符合标准

当用户提出“更新此技能以符合标准”“修复此技能”“审查并改进”，或对一个已有一段时间未维护的已发布技能调用 `/skill-creator` 时，使用此路径。目标是实现机械层面的规范一致性，而不是重新设计行为。**不要询问用户有关用途、触发条件或输出格式的问题**——这些信息已经编码在现有的 SKILL.md 中。

流程：

1. 阅读现有的 SKILL.md 及其所在目录。记录当前的 frontmatter、正文长度、引用、脚本和版本。浏览 `docs/README.md`，了解面向用户的功能声明。
2. 运行 `python scripts/quick_validate.py <skill-path>`。它会验证允许使用的键、名称格式、描述长度、是否缺少负向触发条件，以及 YAML 是否损坏。
3. 执行 `references/frontmatter-rules.md` 中描述的**Frontmatter 审计**。涵盖检查清单中的每一项，而不只是 `quick_validate.py` 标记的问题。
4. 根据此技能中的标准检查正文：
   - SKILL.md 不超过 500 行（如果超过，则拆分至 `references/`）。
   - 包含“步骤完成报告”章节。
   - 如果该技能会修改 git 仓库，则包含“编辑前同步仓库”章节。
   - 捆绑的脚本在退出前会输出描述性错误信息。
   - 恰当地使用渐进式披露；引用层级只深入一层。
5. 决定采用修复模式还是仅审查模式。如果进行修复，则应用编辑并**递增 `metadata.version`**——仅修复 frontmatter 时递增补丁版本，新增章节时递增次版本，重构时递增主版本。如果仅进行审查，则以修改前/修改后建议的形式列出发现的问题，不要悄悄编辑。
6. 重新运行 `quick_validate.py`，确认验证通过。输出一份步骤完成报告，其中包含一项 `Frontmatter valid` 检查。
7. 可选：提供描述优化选项（见下文）。不要自动运行——它会消耗评估 token。

此子路径**不要求**运行评估。只有当正文更改足够实质，且用户希望进行验证时，才转到子路径 B2。

### 子路径 B2——根据评估反馈迭代技能

当用户已有评估结果（或希望运行评估），并希望根据评估所反映的问题修订技能时，使用此路径。第一步是执行**评估循环**，而不是进行访谈。

1. 如果存在 `evals/misfires.jsonl`，请先读取它——记录的真实故障是信号最强的评估；将其转换为测试用例（schema 位于 `references/schemas.md`）。然后，如果评估已存在，则读取最新结果和用户的 `feedback.json`；如果不存在，则按照上面的“运行和评估测试用例”执行。
2. 阅读 `references/iteration.md`，了解修订的五项原则（泛化、保持精简、解释原因、发现重复工作、考虑使用子代理）以及迭代循环（应用 → 重新运行 → 审查 → 重复）。
3. 在修订内容的同时执行**Frontmatter 审计**——即使正文经过精心打磨，存在损坏的 frontmatter 仍会导致验证失败。
4. 根据版本管理规则递增 `metadata.version`——新增能力或扩展触发条件时递增次版本，仅修改措辞时递增补丁版本。
5. 在新的 `iteration-<N+1>/` 目录中重新运行评估，让用户进行比较。

`references/iteration.md` 还记录了可选的盲测 A/B 比较系统。

## 描述优化

描述字段是决定 Claude 是否调用技能的主要机制。创建或改进技能后，应主动提出优化描述，以提高触发准确率。

阅读 `references/description-optimization.md`，了解完整的四步流程：生成触发评估查询、通过 HTML 模板与用户一起审核、使用 `run_loop.py` 运行优化循环、应用最佳描述。

### 打包并展示（仅当 `present_files` 工具可用时）

如果 `present_files` 工具可用（否则跳过），请打包技能并展示生成的 `.skill` 文件路径，以便用户安装：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

## 特定环境说明

如果你使用的是 Claude.ai（无子代理）或 Cowork（有子代理但无浏览器），部分机制会有所变化。请阅读 `references/environment-modes.md`，了解相应的调整流程。核心循环（起草 → 测试 → 审核 → 改进）在所有环境中都相同——只有执行机制有所变化。
