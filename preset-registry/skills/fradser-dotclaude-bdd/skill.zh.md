# 行为驱动开发（BDD）

BDD 不仅仅关乎工具；它是一套旨在建立共同理解并实现高质量交付的方法论。本技能规范了 **发现 → 形式化 → 自动化** 生命周期：Gherkin 场景定义行为，而自动化阶段（红-绿循环）则委托给 `/mattpocock:tdd`（由 BDD 驱动）。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），以确保测试名称和接口词汇与项目的领域语言保持一致，并遵循与你所修改区域相关的 ADR。

## 如何使用本技能

当用户要求实现功能、修复错误或进行重构时，请采用以下思维方式：

1.  **首先理解行为：** 在明确系统*应该做什么*之前，不要开始编码。
2.  **定义场景：** 创建或要求提供预期行为的具体示例（Gherkin）。
3.  **用测试驱动实现：** 使用红-绿-重构循环。

## BDD 循环

该流程从需求逐步推进到代码：

*   **发现：** 通过示例澄清需求（“三个朋友”）。
*   **形式化：** 将这些示例编写为具体场景（Given/When/Then）。
*   **自动化：** 通过 `/mattpocock:tdd` 使用红-绿-重构循环进行实现，由该技能规范测试质量、接缝、模拟和反模式。

详细指南请参阅 `./references/bdd-best-practices.md`。

## 编写场景（Gherkin）

场景是你的“可执行规格”。

*   保持声明式表达（聚焦业务）。
*   避免使用技术术语和 UI 细节。
*   每个场景只描述一种行为。
*   **将可执行场景存储在 `.feature` 文件或框架原生的可执行测试格式中**——不要将其写成代码注释。实现开始后，将需要自动化的场景转换为 `.feature` 文件或框架原生的可执行测试格式，使其同时成为活文档。

有关语法和存储结构，请参阅 `./references/gherkin-guide.md`。

## 自动化阶段

自动化阶段（红-绿循环）由 `/mattpocock:tdd` 技能（BDD 驱动）规范。当 Gherkin 场景已定义且接缝已达成一致时，调用 `/mattpocock:tdd` 来处理：

- **接缝**——测试应放置在哪个公共边界
- **测试质量**——怎样才算好的测试，以及反模式
- **模拟**——何时进行模拟，以及在哪些边界进行模拟
- **红-绿循环规则**——每次只实现一个切片，在变绿后进行重构

## 接缝——测试应放在哪里

接缝是你进行测试的公共边界。完整的接缝指南请参阅 `/mattpocock:tdd`。

**仅在预先约定的接缝处进行测试。** 在编写任何测试之前，先写下待测试的接缝，并通过 AskUserQuestion 工具与用户确认。不得在未经确认的接缝处编写测试。测试所有内容是不可能的——预先就接缝达成一致，能够确保测试工作集中在关键路径和复杂逻辑上，而不是覆盖每个边缘情况。

使用 AskUserQuestion 工具询问要测试哪些接缝，并将候选接缝作为选项提出（用户可以通过“其他”进行调整）。

## 什么是好的测试

测试通过公共接口验证行为，而不是实现细节。完整指南、示例和反模式请参阅 `/mattpocock:tdd`。

## 关键：铁律

> **“没有先失败的测试，就不能编写生产代码。”**

在编写任何实现之前，红灯步骤必须确认测试因正确的原因而失败（运行测试并阅读失败输出）。跳过这一步或为此寻找借口会导致：

1.  测试假性通过——你无法判断它们是否具备发现失败的能力。
2.  偏向实现的测试——它们反映的是已经编写的代码，而不是契约规定的行为。
3.  从第一天起就产生遗留代码——没有行为安全网来捕获未来的回归。

### 如果生产代码已经存在

删除它，然后从一个失败的测试重新推导实现——不要保留它“作为参考”，不要将它“调整”为测试先行的版本，也不要在编写测试时阅读它。上述任何一种做法都会从后门重新引入前文所述的偏向实现的测试这一失败模式：如果测试是在看着它要约束的代码时编写的，那么无论它是否检查了正确的内容，第一次运行时都会通过。删除就是删除。

### 常见的合理化借口（全部拒绝）

| 合理化借口 | 为什么站不住脚 |
|---|---|
| “我之后再写测试——无论怎样覆盖率都一样” | 针对已经正常工作的代码编写的测试，在第一次运行时总会通过。这只能证明测试不会崩溃，而不能证明它验证了正确的行为。只有先因所述原因而失败过的测试，才被证明有能力捕获回归。 |
| “我已经手动验证过它能正常工作” | 手动验证不可重复，也不会留下回归防护。它回答的是“这一次是否成功”，而不是“以后是否会继续正常工作”。 |
| “这个太简单了，不需要测试” | 简单代码和复杂代码一样容易改变行为。铁律没有复杂度门槛——它只有下文明确列出的三个例外，除此之外别无其他。 |
| “对于 BDD 驱动的 TDD，我会务实一些，而不是教条主义” | 这正是合理化借口，而不是它的替代方案。这些表格中的每一项，都是有人以“务实”为由跳过红灯步骤。 |
| “我已经在这上面花了一个小时，删掉太浪费了” | 这是沉没成本。无论删除还是保留代码，这一个小时都已经花掉了；保留未经测试的代码无法挽回这一小时，只会额外增加未经验证的回归风险。 |

唯一合理的例外已在 `./references/bdd-best-practices.md` 中明确列出（一次性原型、生成的代码、配置文件）——即使是这些情况，也应该向用户提出，而不能默认其适用并保持沉默。

### 事后编写的测试回答的是另一个问题

测试先行编写的测试表达的是“这是系统根据契约必须执行的行为”。事后编写的测试表达的是“这是我已经编写的代码碰巧执行的行为”——即使代码行为错误，测试也会通过，因为测试是为了匹配该行为而设计的，而不是依据一份独立的规格说明。如果你发现自己正在针对眼前可见的代码编写测试，请停下来，删除代码，改为针对*行为*编写测试。

## 循环规则

有关完整的红-绿循环规则、反模式和测试质量指南，请参阅 `/mattpocock:tdd`（BDD 驱动）。要点如下：

- **先红后绿。** 先编写失败的测试，然后只编写足以使其通过的代码。
- **每次只处理一个切片。** 每个循环只处理一个接缝、一个测试和一个最小实现。
- **重构不属于此循环。** 它应在审查阶段进行（参见 `/mattpocock:code-review`），而不是在红 → 绿的实现循环中进行。
