# 分诊

将项目 issue 跟踪器上的 issue 在一个由分诊角色构成的小型状态机中流转。

如果本仓库将外部拉取请求视为一种请求受理面（见 issue 跟踪器配置），分诊同样覆盖它们：**PR 就是附带代码的 issue**，使用相同的角色、相同的状态和相同的状态机，仅有少数差异在下方标注为“针对 PR”。根据跟踪器配置，将光杆的 `#42` 解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或每个 issue **必须**以以下免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写持久耐用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug`：某些东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：规格已完整，可交给无人值守的 agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会被处理

针对 PR，同样的状态需结合附带的代码来解读：`ready-for-agent` 表示已附上一份简报，应由 agent 在 diff 上执行下一步；`ready-for-human` 表示已准备好由人来合并。

每个经过分诊的 issue 都应恰好带有一个类别角色和一个状态角色。如果状态角色发生冲突，先标记出来并询问维护者，然后再做其他事情。

这些是规范的角色名称。issue 跟踪器中实际使用的标签字符串可能不同。映射关系应当已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；再从那里流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后回到 `needs-triage`。维护者可以随时覆盖；对看起来不寻常的流转要先标记并询问后再继续。

## 调用

维护者调用 `/triage` 并用自然语言描述自己的意图。理解该请求并执行。示例：

- “给我看看所有需要我关注的东西”
- “我们来看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些是 agent 可以接手的？”

## 展示需要关注的内容

查询 issue 跟踪器并呈现三个桶，按时间从旧到新排序：

1. **未打标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分诊记录后报告者有新活动**：需要重新评估。

当 PR 在受理范围内时，将这些外部 PR 也纳入这些桶，并为每一行标注 `[PR]` 或 `[issue]`。发现过程只会呈现*外部* PR（跟踪器配置定义了谁算外部），因此协作者进行中的 PR 不属于分诊工作。该筛选仅适用于发现阶段；被明确点名指出的 PR 无论作者是谁，始终会被分诊。

显示数量以及每个条目的一行摘要。让维护者来选择。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还包括 diff）。解析已有的分诊记录，避免重复询问已解决的问题。使用项目的领域词汇表探索代码库，并尊重相关区域的 ADR。对代码库执行两项检查：(a) **冗余性**：按领域概念（而不只是请求的措辞）搜索所请求行为的既有实现，并报告你在哪些地方查找过。如果找到了，这属于已实现的 `wontfix`（见第 5 步）。(b) **此前曾被拒绝**：阅读 `.out-of-scope/*.md`，找出任何与本请求相似的记录。

2. **给出建议。** 告诉维护者你推荐的类别和状态及理由，并附上与该请求相关的简要代码库摘要（包括是否已实现）。等待指示。

3. **验证主张。** 在任何追问之前，先核实该主张是否站得住脚。对于 bug，按照报告者的步骤复现它。对于 PR，确认 diff 确实做到了它所声称的事情：将其检出到本地，运行相关的测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（一个强烈的 `needs-info` 信号）。经过确认的验证会让 agent 简报有力得多。

4. **追问（如有需要）。** 如果请求需要充实完善，调用两次 Skill 工具，分别对应 “grilling” 和 “domain-modeling”，一次一轮问题地把它问成形，在此过程中打磨领域术语，并在决策落定时同步更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但需说明为何无法委派（需要主观判断、需要外部访问、设计决策、手工测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - 对于 `wontfix`，关闭 issue，评论内容取决于*原因*：
     - **已实现**：该改动已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求用的，不是给已实现的需求用的）。
     - **拒绝（bug）**：礼貌地给出解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如有部分进展，可酌情留下评论。

## 快速状态覆盖

如果维护者说“把 #42 移到 ready-for-agent”，相信他们并直接应用该角色。确认你即将执行的操作（角色变更、评论、关闭），然后行动。跳过追问。如果在没有经过追问环节的情况下移到 `ready-for-agent`，询问他们是否想撰写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把追问期间已确认的所有内容记录在 "established so far" 之下，以免这些工作丢失。问题必须具体、可执行，而不是“请提供更多信息”之类的话。

## 恢复之前的会话

如果该 issue 或 PR 上已存在先前的分诊记录，阅读它们，检查报告者是否已回答了任何悬而未决的问题，并在继续之前呈现更新后的全貌。不要重复询问已解决的问题。
