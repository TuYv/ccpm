# 智能体接口设计

示例会教授一条路径，同时悄然封死其他路径：如果展示了三种调用工具的方式，模型往往就只会使用这三种方式。设计良好的接口能够一次性呈现完整的可能性空间。参数说明什么是可能的，描述说明什么是预期的，除此之外几乎无需再写任何内容。

## 步骤

1. 在重新设计工具之前，先弄清楚它实际上是如何被误用的。阅读对话记录、日志或用户投诉。误用首先是接口问题的表现，其次才是文档问题，而解决办法通常是重命名或使用类型，而不是增加一段说明。
2. 将语义融入参数：
   - 使用枚举，而不是接受自由文本。`pending | in_progress | completed` 这样的状态无需一句文字说明，就能呈现完整的状态机。
   - 根据意图而非实现来命名，让读起来正确的调用方式就是正确的调用方式。
   - 只要类型系统允许，就让无效状态无法表示。无法表达错误的参数，也就不需要针对该错误发出警告。
3. 将行为指令放在工具自身的描述中，也就是使用工具的地方，并且只放在那里。在全局前言中重复相同的指导，是代码库中产生矛盾的根源。
4. 将添加用法示例的冲动视为一种诊断信号：它通常意味着某个参数定义得不够明确。先修正接口。只有当某种格式确实无法靠猜测得知时，才保留示例，例如定制的查询语法。
5. 确定哪些工具需要常驻，哪些工具可以按需发现。大多数轮次都需要使用的工具应放在上下文中；很少使用的工具则应支持按需查找，这样在需要之前不会产生任何成本。
6. 最后，明确指出该设计仍然允许出现的错误，并说明其代价是否低到可以接受，还是需要设置明确的防护措施。

## 防护准则

- 如果描述必须解释某个参数的含义，说明该参数需要一个更好的名称。
- 不可逆和高风险的操作是上述所有原则的例外：在这些情况下，明确的约束和确认比优雅更重要。
- 在找到所有现有调用方之前，绝不要重新设计函数签名。
- 简短不是目标，表达力才是。删掉承载了实际行为要求的描述，比描述过长更糟糕。
