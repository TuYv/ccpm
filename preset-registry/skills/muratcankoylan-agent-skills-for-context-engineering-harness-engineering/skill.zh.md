# 智能体约束框架工程

智能体约束框架工程负责设计围绕智能体的控制系统：它可以编辑什么、如何接收反馈、在哪里写入状态、如何从故障中恢复，以及谁可以批准不可逆操作。约束框架决定了一次智能体会话究竟只是提供帮助，还是能够连续运行数天而不偏离其目标的自主循环。

## 何时启用

在以下情况下启用此技能：

- 构建自主研究或实验循环
- 设计具有锁定指标以及可编辑代码或内容的智能体环境
- 创建能够生成 PR 或在后台运行的智能体
- 评估智能体能否在无需频繁人工提示的情况下安全运行
- 为智能体工作流添加新颖性、消融、剪枝、回滚或持久化日志机制
- 防止智能体操纵基准测试、弱化评分标准，或在上下文压缩过程中丢失状态

对于由其他技能负责的相邻工作，请勿启用此技能：
- 不涉及自主控制面的通用质量门禁、回归测试套件或结果指标：`evaluation`。
- 约束框架工具的工具模式、响应格式和恢复错误：`tool-design`。
- 项目级任务与模型的适配、流水线形态和成本规划：`project-development`。
- 远程沙箱、预热池和托管会话基础设施：`hosted-agents`。

## 核心概念

### 约束框架边界

将智能体与其运行环境分离。智能体提出操作；约束框架定义允许操作的界面、反馈、持久化机制和晋级规则。

使用四类界面：

| 界面 | 示例 | 规则 |
| --- | --- | --- |
| 锁定 | 评估指标、评分标准、验证脚本、合并策略 | 智能体可以读取并提出变更，但不能使用修改后的规则为自己评分 |
| 可编辑 | 技能草稿、实验文件、提示词、测试中的配置 | 智能体可以在循环期间修改 |
| 仅追加 | 结果日志、研究线程、被否决的想法 | 智能体可以追加，但不能重写 |
| 人工控制 | 合并、生产部署、凭证、破坏性操作 | 需要明确的人工批准 |

### 紧密反馈循环

当反馈快速、明确且难以操纵时，自主运行才会奏效。Karpathy 的 `autoresearch` 是最简模式：一个可编辑文件、一个锁定的评估文件、固定的实际运行时间预算、一个标量指标、git 回滚，以及一份持久化结果日志。其启示并非每个约束框架都需要单一指标，而是模糊的反馈会导致模糊的自主行为。

对于开放式的“研究到技能”工作，应使用锁定的评分标准、确定性的结构检查、来源可追溯性和人工审核阈值来取代标量指标。

### 持久化状态

长时间运行的智能体必须将状态外部化。将计划、来源队列、结果、失败记录和交接信息存储在文件中，以便后续智能体无需依赖聊天历史即可恢复工作。Prime Intellect 的自主 nanoGPT 工作展示了持久化草稿文件和 `THREAD.md` 式日志对于恢复、监控和审计的价值。

使用仅追加日志记录：

- 尝试过什么
- 哪些方面得到改善或遭遇失败
- 为什么保留、舍弃某个候选方案，或将其转交审核
- 检查了哪些上游来源
- 下一个智能体应该做什么

### 搜索纪律

智能体往往会利用最近的表层信息、不断叠加复杂性，并且不充分执行剪枝。应添加明确的搜索规则：

1. 按计划定期刷新上游来源。
2. 在投入大量预算之前，必须进行新颖性检查。
3. 保留被拒绝的尝试，以避免再次发现相同内容。
4. 当一个堆栈包含多项新增内容时，执行留一法剪枝。
5. 在质量相同的情况下，奖励简化。
6. 在晋升之前进行独立验证。

### 机制注册表

对于从研究到技能的系统，应将已接受的机制与说明性文本分开跟踪。机制记录应包含稳定的 `mechanism_id`、`owning_skill`、`status`、激活场景、行为变化、证据和失败模式。新颖性门控应先与此注册表进行比较，再使用更广泛的语料库重叠度，因为关键词重叠只能发现陈旧措辞，而机制比较则能发现真正的重复。

### 治理

自主智能体可以准备 PR，但治理规则必须明确。它们可以起草变更、运行检查并撰写 PR 摘要。除非用户已明确授予针对特定操作的权限，否则它们不应进行合并、部署或推送。

## 详细主题

### Autoresearch 风格循环

在针对稳定评估器优化产物时，使用以下模式：

```text
read locked context -> choose hypothesis -> edit allowed surface -> commit/checkpoint
-> run evaluator -> log result -> keep if better -> discard or rollback if worse
-> repeat
```

必需属性：

- 评估器位于可编辑范围之外。
- 反馈节奏足够固定，以便比较不同尝试。
- 失败的尝试会留下审计轨迹。
- 回滚成本低。
- 智能体具有处理崩溃和超时的策略。

### 从研究到技能的循环

当来源转化为技能变更时，使用以下模式：

```text
discover -> retrieve -> gate -> score -> extract mechanism
-> map to existing or new skill -> draft proposal -> validate structure
-> prepare PR -> human review
```

锁定的评估器由来源评分标准、技能变更评分标准、结构检查和审阅者批准共同组成。可编辑的产物是所提议的技能增量。

### 抵抗指标博弈

应假设执行优化的智能体会逐渐掌握评测框架的规律。需要防范：

- 编辑评估代码或评分标准，然后使用新版本进行自我批准
- 添加迎合评判者但会损害技能激活效果的冗长内容
- 引用未实际检索的来源
- 优化总分，却在某个关键维度上不合格
- 在日志中避而不谈失败结果

缓解措施：每次运行都锁定评分标准，报告各维度分数，要求提供来源检索证据，保留被拒绝的尝试，并将治理变更提交人工审阅。

### 监控智能体

对于长时间运行的任务，应使用监控智能体，但除非明确分配了其他任务，否则应将其限制为只读报告。监控输出应报告：

- 当前最佳候选方案
- 活跃的作业或草案
- 最近一次上游刷新
- 失败或停滞的循环
- 日志与所声称状态之间的不一致
- 下一步操作和阻碍因素

## 实用指南

### 运行框架设计检查清单

1. 用一句话定义目标。
2. 确定锁定、可编辑、仅追加以及由人工控制的操作范围。
3. 选择反馈机制：标量指标、评分标准、确定性测试、人工审核，或这些方式的组合。
4. 定义保留、丢弃、崩溃、超时和待审核状态。
5. 在循环开始前创建持久化线程日志。
6. 为长期运行的循环添加来源刷新、机制注册表新颖性检查和剪枝规则。
7. 定义智能体无需询问即可执行的操作，以及需要批准的操作。
8. 使用一个已知良好的工件和一个已知不良的工件验证运行框架。

### 文件布局

```text
research-run/
  THREAD.md
  sources/
    queue.md
    evaluations/
  proposals/
  logs/
    results.tsv
    rejected.md
  drafts/
```

使用 TSV 或 JSONL 记录仅追加、机器可读的日志。使用 Markdown 编写交接文档和面向审核者的摘要。

## 示例

**示例 1：锁定指标**

智能体优化 `train.py`，但 `prepare.py` 负责数据加载和评估。智能体可以编辑模型，但不能更改指标。失败的实验会被记录并回滚。

**示例 2：锁定评分标准**

智能体评估一篇新的 Anthropic 或 OpenAI 工程文章，但本次运行的来源筛选评分标准会被锁定。如果来源通过，智能体就起草一份 Skill 提案。它不能通过降低评分标准的阈值来接纳该来源。

**示例 3：自动创建 PR，但不自动合并**

智能体在通过来源、Skill 和结构检查后准备分支和 PR 正文。PR 会说明尚未解决的风险，并等待人工批准合并。

## 指南

1. 在启动循环前锁定评估器。
2. 将可编辑范围限制到足够小，以确保差异可靠。
3. 在上下文压缩可能清除状态之前写入持久化日志。
4. 报告各维度分数，而不只是总分。
5. 引用前必须检索来源。
6. 为广泛搜索添加新颖性门控，为复杂技术栈添加剪枝门控。
7. 在质量相同的情况下优先选择更简单的方案。
8. 将 PR 准备权限与合并权限分开。
9. 使用旧评估器和新评估器重新验证运行框架的变更。
10. 将自主循环停止视为运行框架故障，而不是智能体的个性问题。

## 常见陷阱

1. **可变评估器**：如果智能体可以编辑指标，它可能会针对基准进行优化，而不是针对任务进行优化。在运行期间锁定评分标准和评估代码。
2. **仅依赖聊天记忆**：如果计划只存在于对话历史中，长时间运行会在上下文压缩后失败。从一开始就写入线程日志和结果文件。
3. **没有丢弃记录**：如果没有被拒尝试的日志，智能体就会重复失败的想法。保留足够详细的失败信息，避免再次探索同样的方案。
4. **复杂性累积**：智能体会不断叠加变更，却很少移除变更。要求执行剪枝轮次，并奖励质量相同但更简单的方案。
5. **过早宣称新颖性**：智能体会将重新组合的内容标记为新颖。在宣称新颖性之前，应与仓库中现有的 Skill、来源队列和拒绝日志进行比较。
6. **监控误报**：监控智能体可能会总结过时或不一致的状态。要求它们引用支撑其断言的文件或日志。
7. **人工批准含义不明确**： “准备 PR”并不等于“合并 PR”。在运行框架中明确规定批准边界。
8. **易变来源发生漂移**：快速演进的实验室声明很快就会过时。在参考资料中加入带日期的证据，并安排重新验证。

## 集成

此技能与以下技能关联：

- evaluation - 评估量规和质量门提供锁定的反馈界面
- advanced-evaluation - 成对比较和偏差缓解可改进提案审查
- filesystem-context - 持久化日志、草稿和线程文件用于保存状态
- multi-agent-patterns - 研究、验证、监控和写作智能体需要相互隔离的上下文
- tool-design - 智能体运行框架工具必须提供清晰的契约和恢复错误
- project-development - 基于文件的流水线和任务模型适配分析可保持循环简洁
- hosted-agents - 后台执行需要沙箱、快照和审批边界
