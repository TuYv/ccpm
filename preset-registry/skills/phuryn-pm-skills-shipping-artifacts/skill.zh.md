# 交付产物：让 AI 构建的代码可供审查的文档

## 目的

AI agent 编写代码很快，但不会留下关于*意图*的持久记录——系统应该做什么、谁被允许做什么、机密信息存放在哪里、哪些规则确实经过了验证。如果没有这份记录，任何人（包括审计 agent）都无法判断代码是否适合安全地发布。这项 skill 定义了一小组能够恢复可审查性的文档。

这些文档位于仓库根目录下的 `documentation/` 中，面向两类读者：人工审查者和下一位 AI 编码 agent。它们是后续每次审计的**预期状态**部分——安全审查或性能审查的质量，取决于它能够将代码与什么样的意图进行比对。

## 文档集合的组织方式

该集合**不是**一个固定列表——它由一个小型的**核心**文档集和一组仅在相应能力存在时才添加的**条件**文档组成。

- **核心文档**——每个具备可审查性的应用都有这些表面，因此始终要生成。
- **条件文档**——仅当应用确实具备相应能力时才包含该文档。如果没有，就在 `architecture.md` 中写一行（“没有计划任务——没有 `cron.md`。”），而不是凭空创建一个空文档。可审查性来自诚实的映射，而“我们不做 X”也是映射的一部分。
- 大多数文档都由 `/document-app` 从代码逆向工程得出。唯一的例外是 `tests.md`，它由 `/derive-tests` 根据其他文档*推导*得出——它是验证映射，而不是某个子系统的描述。

要对当前状态保持极其诚实，但不要疑神疑鬼。任务是绘制准确的映射，而不是出具健康证明。每份文档都应简短，以表格和项目符号为主，并跳过泛泛的理论。

## 核心文档

每项包括：文件 · 一句话用途 · 必须记录的内容 · 审查者如何使用它。

1. **`architecture.md`** — 系统是什么，以及各部分如何协同运作。
   - 必须记录：产品概览和关键假设；技术栈；身份验证/会话/声明如何端到端流转；信任边界（例如服务角色与客户端之间）；简短的**已知风险 / 假设**列表（每一项都必须由其在代码中的出现位置作为依据，而不是通用检查清单）；包含每一份其他已生成文档的“相关文档”索引。
   - 审查者用途：根文档——其他所有文档都从这里交叉引用。

2. **`flows.md`** — 实际执行权限检查和副作用的业务流程。
   - 必须记录：每个承载关键业务的流程，包括参与者 + 前置条件 + 成功结果；跨越 UI → server → data → jobs → providers → agents 的逐步顺序；每个受保护步骤中的**授权检查**（使用哪个 claim/role/scope、针对哪个资源，以及预期的*拒绝*情况）；**信任边界跨越**（browser→server、server→provider、job→app、agent→tool、webhook→app）；每个步骤引起的状态变化和副作用（写入、排队的邮件、触发的任务、出站调用）。
   - 审查者用途：提供静态的 `permissions.md` 矩阵无法展现的运行时视图——授权*在哪里*以及*以什么顺序*执行，以及哪些地方可能被跳过。
   - **反 PRD 规则：**不涉及权限、数据完整性、外部副作用、资金、隐私或运行安全的流程不属于此处。这是一份安全/运维映射，而不是功能规格说明。

3. **`permissions.md`** — 谁被允许执行哪些操作。
   - 必须涵盖：角色/声明；作用域从何处派生（令牌还是数据库）；资源 × 操作 × 角色矩阵；哪些表启用了行级安全策略，以及哪些表依赖代码强制执行检查。
   - 审阅用途：访问控制审计用来与代码进行比对的基线。`flows.md` 展示其实际运行过程；这是静态参考。

4. **`variables.md`** — 配置与机密信息，以及它们对应的风险。
   - 必须涵盖：Name · used-by · scope (server/client) · source · rotation · risk 表格；明确确认没有任何机密信息被打包到客户端；上线前检查清单。
   - 审阅用途：机密信息/PII 泄露面，以及事件响应期间的轮换计划。

5. **`tests.md`** — 验证映射：哪些已记录的规则确实经过检查，哪些仅为提议，哪些完全没有任何检查。
   - 必须分为以下三个清晰区分的部分，以避免该映射被误读为全部通过：
     - **Existing coverage** — 当前就在代码仓库中的测试，每个测试都关联到其所固定的规则（使该映射反映现实，而不是愿望清单）。
     - **Proposed tests** — 尚未编写的推荐用例，并按**测试类型**标记（自动化单元测试/集成测试 · 受保护的线上测试 · 人工审查）。
     - **Gaps** — 完全没有任何验证的已记录规则，并按照跨越这些规则后会暴露的风险进行排序。
   - 每一行都包含：用例 → 规则 → 预期行为（包括拒绝/否定场景）→ 证据来源（文档 + 代码）→ 状态（existing / proposed / none）。同时注明哪些检查是 CI 必需的，并会阻止合并到 `main`。
   - 审阅用途：将“已记录 == 已实现”落地为可执行形式——它展示其他文档声称的每条规则，究竟是当前已有测试固定、仅有提议，还是未经验证。
   - 由 `/derive-tests` 生成（而不是 `/document-app`），因为它是根据其他文档和现有测试套件推导出来的，而不是从某个子系统中直接读取。

## 条件性文档（仅在具备相应能力时包含）

6. **`emails.md`** — 系统发送的每一封通知邮件。*仅当应用发送事务性或自动化邮件时包含。*
   - 必须涵盖：队列 → 处理器 → 提供商路径；模板及其接受的变量；重试/退避行为；发送失败时的排查位置。
   - 审阅用途：发现未经验证的模板输入和 PII 暴露边界。

7. **`cron.md`** — 所有计划任务，以及如何安全地运行这些任务。*仅当存在计划任务或后台作业时包含。*
   - 必须涵盖：清单表（任务 → 计划 → 函数 → 机密信息 → 限制 → 重试）；每个任务如何保持幂等；内部调用如何进行身份验证；在哪里查看最近一次运行记录。
   - 审阅用途：发现可伪造的触发器和无界的后台作业。

8. **`seo.md`** — 单页应用如何处理 SEO 和社交预览。*仅当存在公开/可索引路由或面向机器人的路由时包含。*
   - 必须涵盖：预览方案（静态 meta / 预渲染 / 边缘 HTML）；route → needs-SEO → public-data-only 表格；动态元数据如何进行清理；机器人与人类用户的路由方式。
   - 审阅用途：发现仅限公开数据的违规行为，以及机器人路由上的元数据注入问题。

9. **`automation.md`** — 嵌入式代理和其他自动化路径。*仅当应用嵌入了 AI 代理、LLM 工作流、工具调用、webhook 或外部自动化时才包含。*
   - 对每个自动化流程/代理，必须记录：触发条件 + 所有者 + 它是自动运行还是仅在批准后运行；它可以读取的输入以及可以调用的**确切工具/API**（工具范围本身就是一道硬性护栏）；**引导**所在的位置（提示词）与**非提示词硬性护栏**所在的位置；返回给应用的**输出契约**（架构、验证、失败处理）；**应用所有的副作用与代理所有的建议**；以及各项控制措施——批准门禁、审计/时间线日志、速率限制、重试、终止开关。
   - 审阅用途：使隐藏的自动化路径清晰可见，并划清代理*提议的内容*与应用*强制执行的内容*之间的界限——这是现代 AI 构建应用中风险最高的表面。

## 注意事项

- 每个生成的文档都会在 `architecture.md` 的 "Related Documents" 部分添加对自身的引用，以便整个文档集保持可发现性。
- 跳过任何不适用的条件文档，并用一行说明这一点，而不是编造内容。
- 不要在这些文档中加入示例和完成的模板——它们描述的是*这个*系统，而不是通用方法。
- 代理运行上下文文件（`CLAUDE.md` / `AGENTS.md`）是*不同的*产物——它是从这些文档派生出的指令，而不是系统文档。它由交接步骤中的 `/ship-check` 生成，而不是在此处生成。
- `tests.md` 由 `/derive-tests` 生成；其余文档由 `/document-app` 生成。
- 不要包含“更新日期”一行；文件的历史记录才是事实来源。
