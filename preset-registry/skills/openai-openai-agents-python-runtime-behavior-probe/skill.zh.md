# 运行时行为探测

## 概述

使用此技能调查真实的运行时行为，而不是复述代码或文档。首先规划调查，然后执行用例矩阵，记录观察到的行为，并报告调查结果以及获得这些结果所使用的方法。

## 核心规则

- 将此技能视为只能手动调用。不要依赖隐式调用。
- 调用此技能仅授权进行规划。每次运行时探测都必须在提出确切的探测方案后获得用户的明确批准。不要从技能调用或调查运行时行为的一般性请求中推断出执行批准。
- 在请求批准之前，披露所提议探测的来源身份、确切命令、传递执行的材料、已知的文件系统、环境、网络和主机服务能力、预期副作用以及控制措施。对于未知的能力，应将其标记为未知，而不是假定其不可用。
- 在执行探测之前，等待肯定答复。批准仅适用于已披露的来源、命令、执行材料和能力范围。在更改其中任何字段、添加其他探测或扩大已获批准的矩阵之前，须重新获得批准。
- 基准成功用例或冒烟用例通常是合适的切入点，但当真正的问题涉及边缘情况、行为漂移或失败行为时，不要止步于此。
- 在运行任何内容之前先进行规划。首先编写用例矩阵，然后用观察到的结果填充该矩阵。矩阵可以放在草稿笔记、临时文件或探测脚本的头部。
- 默认提议本地或只读探测。仅在实时服务明确相关时才考虑使用它，然后在请求批准之前应用下述轻量级门控。
- 根据决策需要确定探测规模。从能够证伪或验证当前假设的最小矩阵开始，仅在仍存在不确定性时才扩大范围。
- 在进行实时探测之前，应用三项轻量级门控：
  - 目标门控。仅使用明确允许用于该任务的实时目标。
  - 意图门控。仅当用户明确希望对该集成进行运行时验证，或在你提出探测方案后明确批准时，才运行实时探测。
  - 数据门控。如果探测将读取环境变量、改变远程状态、产生实质性成本，或使用非公开数据或用户数据，请指出确切的变量名或数据类别，并首先获得明确批准。
- 在执行前，将每个用例分类为只读、变更型或高成本型。对于变更型或高成本型用例，或任何将读取环境变量的实时用例，应在运行探测之前定义清理或回滚方案。
- 对一次性探测脚本使用临时文件或临时目录。
- 在最终回复起草完成之前保留临时产物。之后默认删除它们，除非用户要求保留，或后续工作需要使用它们。即使删除了产物，也应在报告中保留一份简短的运行摘要，其中包括命令形式、运行时上下文和产物状态。
- 在执行将读取环境变量的实时探测之前，告知用户你计划使用的确切变量名及其用途，然后等待明确批准。示例包括 `OPENAI_API_KEY` 以及受测系统预期使用的其他默认名称。
- 当需要进行环境变量批准门控且 `request_user_input` 工具可用时，应使用该工具，而不是通过纯文本询问是否批准。提出一个简洁的问题，并提供互斥选项，例如 `Allow once (Recommended)` 和 `Do not allow`；省略 `autoResolutionMs`，并将批准限制为单次探测、确切的已命名变量及目标。如果该工具不可用，则改用简洁的纯文本批准问题，并且在用户明确批准之前不得继续。
- 切勿输出密钥，即使它们来自此技能可能使用的标准环境变量。
- 对于此仓库中的 OpenAI API 或 OpenAI 平台探测，应尽早使用 [$openai-knowledge](../openai-knowledge/SKILL.md) 确认对契约敏感的详细信息，例如支持的参数、字段名和限制。使用运行时探测来验证或质疑文档中描述的行为，而不是完全跳过文档查阅环节。如果 docs MCP 不可用，则改用 OpenAI 官方文档，并在报告中说明使用了该备用方案。
- 对于基准测试或比较探测，在执行前明确说明对等条件。记录保持不变的内容、受测变量、确保比较公平的响应结构约束，以及任何对解释延迟或成本具有重要意义的用量或令牌计数器。
- 对于 OpenAI 托管工具探测，在将负面结果归因于运行时行为之前，应先消除设置上的歧义：
  - 当问题取决于工具调用时，使用匹配的 `tool_choice` 强制采用工具路径。
  - 将 `container_auto` 和 `container_reference` 视为独立用例，而不是可互换的设置细节。
  - 首先移除不受支持的模型或工具选项，以免它们使探测无效。

## 工作流程

1. 用可操作的术语重新表述调查目标。明确运行时层面、关键不确定性，以及需要测试的最高风险行为。
2. 进行简短的预检。先检查相关代码或文档，判断问题需要本地验证还是在线验证，并注明任何相关的仓库、基线或发布边界。
3. 在构建矩阵之前定义决策信号。对于疑似缺陷，明确具体的用户可见症状、可将其与正确行为区分开的命令或探针、预期的失败观测结果，以及一个已知正常的对照。确认该信号覆盖了真实的生产方和调用方路径，而不只是相邻的辅助函数。如果快速、确定性的本地循环能够回答问题，应优先采用。如果无法构建可信的信号，请说明缺少的访问权限或工件，不要用相近行为替代作为证据。
4. 在执行探针之前创建验证矩阵。既要覆盖基线行为，也要覆盖最相关的失败或漂移情况。矩阵可以放在草稿笔记、临时文件中，或作为探针脚本内的结构化头部。
5. 对于每个用例，预先选择执行模式：
   - 对确定性的单次运行检查使用 `single-shot`。
   - 对缓存、重试、流式处理、中断、速率限制、并发或其他对多次运行敏感的行为使用 `repeat-N`。
   - 当首次运行的冷启动效应可能扭曲结果时，使用 `warm-up + repeat-N`。
   除非任务明确需要其他设置，否则使用以下默认值：
   - 对重复敏感问题的快速筛查：`repeat-3`。
   - 用于决策的延迟测试或发布建议：`warm-up + repeat-10`。
   - 成本较高的在线用例：从 `repeat-3` 开始，仅当答案仍不明确时才增加运行次数。
   如果确实不清楚额外运行是否值得投入相应的时间或成本，请在扩大探针范围之前询问用户。
6. 当问题类似基准测试或涉及比较时，分阶段运行。先针对对照组运行高信号的试点矩阵，然后仅扩展仍符合条件的候选项或尚未解决的用例。
7. 如果问题涉及疑似回归或行为变化，请至少添加一个已知正常的对照用例，例如 `origin/main`、最新版本，或不带可疑选项的同一请求。
8. 对于比较探针，在执行之前定义对等条件。记录提示词或输入的结构、工具选择设置、模型设置的对等性、状态复用规则，以及任何用于确保比较公平的响应结构约束。如果输出长度存在实质性差异并可能使结果产生偏差，也要记录用量或 token 相关说明。
9. 如果问题询问一个选项是否与另一个选项具有相同的智能水平或质量，请判断矩阵仅支持示例模式层面的对等性，还是支持更广泛的质量结论。对于更广泛的结论，至少添加一个难度更高或更开放的用例。否则，应明确说明结果仅限于所覆盖的模式。
10. 当隐藏状态可能影响结果时，在执行之前规划状态控制。记录每个用例使用全新状态还是复用状态、如何处理缓存复用或缓存失效、使用哪些唯一 ID 隔离重复运行，以及如何验证清理结果。
11. 如果任何在线用例将读取环境变量，请列出每个用例所用变量的确切名称和用途，然后在执行之前请求用户批准。如果 `request_user_input` 可用，应优先用它完成此审批环节，并且不要自动决定；提供的选项应仅批准或拒绝这一特定探针。审批请求应简短，并包含目标位置、只读操作还是存在修改或成本风险、确切的变量名称，以及相关的清理或回滚方式。
12. 在临时位置构建任务专用的探针脚本。确保脚本精简、可观测且易于丢弃。
13. 在 `openai-agents-python` 中，明确指定运行时上下文：
   - 在可行的情况下，从仓库根目录使用 `uv run python` 运行 Python 探针。
   - 记录当前提交、工作目录、Python 可执行文件和 Python 版本。
   - 避免意外从其他检出目录或 site-packages 位置导入内容。如果必须偏离 `uv run python`，请准确说明原因，以及改用的解释器或环境。
14. 提交完整的探针方案以及上述要求的披露信息，包括每个用例或已批准矩阵的确切命令，然后请求用户明确批准并等待。
15. 仅执行已获批准的矩阵并捕获证据。记录请求结构、设置、观测结果摘要、意外或负面结果、错误详情、耗时、运行时上下文、已批准的环境变量名称、重复次数、预热处理方式、相关情况下的方差、清理行为；对于比较，还要注明保持不变的条件，以及会影响解读的任何响应结构或用量说明。
16. 使用实际结果更新矩阵，而不是填写猜测。
17. 在最终回复起草完成之前保留临时工件。之后将其删除，除非用户要求保留，或后续工作仍需要这些工件。基准测试和高重复次数的探针通常需要后续跟进，因此当结果可能需要重新审视时，保留工件是正常做法。如果已删除，请保留并报告简短的运行摘要。
18. 首先报告发现，并优先报告意外或负面发现。然后总结验证的执行方式以及覆盖的用例。
19. 如果探针隔离出了一个明确缺陷，可以附上简短的实现假设或最小复现方向。除非用户提出要求，否则不要将其扩展成更大范围的后续步骤计划。

## 验证矩阵

使用矩阵，让信息易于快速浏览。从运行时问题和观察摘要出发，而不只是从 `expected` 和 `pass` 或 `fail` 出发。

矩阵至少应包含以下列：

- `case_id`
- `scenario`
- `mode`
- `question`
- `setup`
- `observation_summary`
- `result_flag`
- `evidence`

当以下列能够实质性改善调查时，请添加它们：

- `comparison_basis`
- `variable_under_test`
- `held_constant`
- `output_constraint`
- `status`
- `confidence`
- `state_setup`
- `repeats`
- `warm_up`
- `variance`
- `usage_note`
- `risk_profile`
- `env_vars`
- `approval`
- `control`

将 `result_flag` 用作快速浏览字段，例如 `unexpected`、`negative`、`expected` 或 `blocked`。仅当存在可信的比较依据、基线或可供对照的书面契约时，才使用 `status`。

始终考虑矩阵是否应包含以下类别：

- 基线成功。
- 怀疑存在回归时的对照或基线比较。
- 边界输入或参数变化。
- 无效或不受支持的输入。
- 缺失或错误的配置。
- 超时、网络中断或速率限制等瞬态外部故障。
- 重试、幂等性或清理行为。
- 当共享状态或顺序可能产生影响时的并发或重叠操作。
- 当问题范围超出模式一致性时，使用开放式质量或智能样本。

当你需要更强的优先级排序模型或可复用的用例模板时，请打开 [validation-matrix.md](./references/validation-matrix.md)。

## 临时探测脚本

将一次性脚本写入临时文件或临时目录，例如通过 `mktemp -d` 或 Python `tempfile` 创建的目录。默认将脚本保存在仓库之外，即使它会导入仓库中的代码也是如此。

如果探测需要使用仓库代码：

- 以仓库作为工作目录运行它，或
- 显式设置 `PYTHONPATH` 或等效的导入路径。
- 在 `openai-agents-python` 中，优先从仓库根目录运行 `uv run python /tmp/probe.py`。

设计探测脚本时，应最大限度地提高可观测性：

- 打印或记录正在执行的确切场景。
- 捕获运行时上下文，例如 git SHA、工作目录、Python 可执行文件及版本、相关软件包版本、模型或部署名称、端点或基础 URL 别名，以及任何会实质性影响行为的重试或工具选项。
- 对于实时探测，只记录已获准使用的环境变量名称。绝不要打印它们的值。
- 尽可能捕获结构化输出。
- 保留原始错误类型、消息和状态码。
- 对于对重复执行敏感的用例，捕获尝试序号、预热状态，以及有助于比较各次运行的任何稳定标识符。
- 对于重复执行或基准测试式探测，在可行的情况下同时写入原始结果和精简的摘要工件。
- 尽量减少分支，使每个脚本只回答一个范围明确的问题。

删除临时脚本或目录之前，保留一份简短的运行摘要，其中包括脚本路径、所用命令、运行时上下文，以及证据是已保留还是已删除。

需要轻量级、用完即弃的 Python 探针脚手架时，请打开 [python_probe.py](./templates/python_probe.py)。

## 报告

请按以下顺序报告：

1. 发现。首先列出意外或负面的发现。如果没有实质性的新发现，请明确说明。
2. 验证方法。概述所使用的代码、覆盖的运行时表面、执行模式和用例矩阵覆盖范围。
3. 用例结果。用例数量较多时，请包含完整矩阵或其精简版本。
4. 产物状态和简要运行摘要。说明临时产物是已删除还是已保留，并提供保留的路径或留存的摘要。
5. 可选的实现说明。仅当明确定位到一个缺陷，并且简短的实现方向会有所帮助时，才包含此项。

对于对比探针，报告还应说明哪些条件保持不变、测试了哪个变量，以及结果是仅支持模式一致性，还是支持更广泛的质量结论。

请打开 [reporting-format.md](./references/reporting-format.md)，查看推荐的响应模板。
