# 分诊

通过一个由分诊角色组成的小型状态机，推进项目问题跟踪器中的问题。

如果此仓库将外部拉取请求视为请求入口（参见问题跟踪器配置），分诊也涵盖这些请求：**PR 就是附带代码的问题**——使用相同的角色、相同的状态和相同的状态机，但存在少量差异，已在下文标记为“对于 PR”。请根据跟踪器配置，将单独出现的 `#42` 解析为问题或 PR。

分诊期间发布到问题跟踪器的每条评论或每个问题，**必须**以以下免责声明开头：

```
> *This was generated by AI during triage.*
```

## 关键要求：免责声明不可省略

分诊期间发布到问题跟踪器的每条评论或每个问题都必须以 `> *This was generated by AI during triage.*` 开头。每个问题只能有一个类别角色和一个状态角色；如果状态角色存在冲突，请标记该冲突，并在执行任何其他操作之前询问维护者。

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写持久有效的智能体任务说明
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug` — 某些功能出现故障
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 需要维护者评估
- `needs-info` — 正在等待报告者提供更多信息
- `ready-for-agent` — 已完整定义，可交由 AFK 智能体处理
- `ready-for-human` — 需要由人工实现
- `wontfix` — 不会采取行动

对于 PR，同样的状态需要结合其附带的代码来理解：`ready-for-agent` 表示已附上任务说明，智能体应对差异内容采取下一步行动；`ready-for-human` 表示已准备好由人工合并。

每个已分诊的问题都应只有一个类别角色和一个状态角色。如果状态角色存在冲突，请标记该冲突，并在执行任何其他操作之前询问维护者。

这些是规范角色名称——问题跟踪器中实际使用的标签字符串可能有所不同。相关映射应已提供给你；如果没有，请运行 `/mattpocock:setup-matt-pocock-skills`。

状态转换：未添加标签的问题通常会先进入 `needs-triage`；之后再转为 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 会返回 `needs-triage`。维护者可以随时覆盖状态——请标记看起来异常的状态转换，并在继续之前询问维护者。

## 调用方式

维护者调用 `/mattpocock:triage`，并使用自然语言描述他们想要执行的操作。理解请求并采取行动。示例：

- “向我显示所有需要我关注的内容”
- “我们来看看 #42”（问题或 PR）
- “将 #42 移至 ready-for-agent”
- “有哪些内容已准备好供智能体接手？”

## 显示需要关注的内容

查询问题跟踪器，并按从旧到新的顺序显示以下三个分组：

1. **未添加标签**——从未分诊。
2. **`needs-triage`**——正在评估。
3. **自上次分诊备注以来报告者有新活动的 `needs-info`**——需要重新评估。

如果 PR 在范围内，请在这些分组中包含外部 PR，并为每一行添加 `[PR]` 或 `[issue]` 标记。发现流程仅展示*外部* PR（由跟踪器配置定义哪些人属于外部人员）——协作者正在处理的 PR 不属于分诊工作。此过滤规则仅适用于发现流程；无论作者是谁，明确指定的 PR 始终都要进行分诊。

显示数量，并为每个条目提供一行摘要。让维护者选择。

## 分类处理特定 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；如果是 PR，还要阅读 diff）。解析之前的所有分类处理记录，以免重复询问已经解决的问题。使用项目的领域术语表探索代码库，并遵循相关区域中的 ADR。针对代码库执行两项检查：(a) **重复性** —— 按领域概念（而不只是请求中的措辞）搜索是否已有请求行为的实现，并报告你检查过的位置。如果找到，则属于已实现的 `wontfix`（第 5 步）。(b) **曾被拒绝** —— 阅读 `.out-of-scope/*.md`，并指出其中与此请求相似的内容。

2. **提出建议。** 告知维护者你建议的类别和状态并说明理由，同时提供与请求相关的简要代码库摘要——包括它是否已经实现。等待指示。

3. **验证主张。** 在进行任何深入追问之前，先检查该主张是否成立。对于 bug，根据报告者提供的步骤进行复现。对于 PR，确认 diff 确实实现了其声称的内容——检出对应代码，运行相关测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是一个强烈的 `needs-info` 信号）。经过确认的验证可以让代理任务简报更有说服力。

4. **深入追问（如有必要）。** 如果请求需要进一步完善，同时运行 `/mattpocock:grilling` 和 `/mattpocock:domain-modeling` 技能——每次提出一个问题来完善请求、明确领域术语，并随着决策落定即时更新 `CONTEXT.md`/ADR。

5. **应用处理结果：**
   - `ready-for-agent` —— 发布代理任务简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` —— 使用与代理任务简报相同的结构，但注明无法委派的原因（需要判断、外部访问、设计决策、手动测试）。
   - `needs-info` —— 发布分类处理记录（模板见下文）。
   - `wontfix` —— 关闭，并根据*原因*发布相应评论：
     - **已经实现** —— 该变更已经存在于代码库中。指出其所在位置；**不要**写入 `.out-of-scope/`（该知识库用于记录*被拒绝*的请求，而不是已经构建的功能）。
     - **已拒绝（bug）** —— 礼貌地解释原因，然后关闭。
     - **已拒绝（增强功能）** —— 写入 `.out-of-scope/`，在评论中添加指向它的链接，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` —— 应用该角色。如果已有部分进展，可以选择发布评论。

## 快速状态覆盖

如果维护者说“将 #42 移至 ready-for-agent”，请信任他们并直接应用该角色。先确认你将要执行的操作（角色变更、评论、关闭），然后执行。跳过深入追问。如果在没有进行深入追问会话的情况下移至 `ready-for-agent`，请使用 AskUserQuestion 工具询问他们是否希望编写代理任务简报（是 / 否）。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

将在追问过程中解决的所有事项记录在“established so far”下，以免工作成果丢失。问题必须具体且可操作，不要使用“请提供更多信息”之类的笼统表述。

## 恢复之前的会话

如果议题或 PR 中已有先前的分类处理记录，请先阅读这些记录，检查报告者是否已回答尚未解决的问题，并在继续之前说明最新情况。不要重复询问已经解决的问题。
