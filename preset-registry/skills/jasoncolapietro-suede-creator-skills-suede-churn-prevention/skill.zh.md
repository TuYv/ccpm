# Suede 流失预防

使用这套 Suede 留存手册，通过透明的取消流程、有限的挽留优惠、主动信号和支付恢复来降低主动和非主动流失。

## 开始之前

**请先检查产品营销背景信息：**
如果 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，或者在较旧的设置中使用旧版文件名 `product-marketing-context.md`）存在，请在提问前阅读它。使用该背景信息，仅询问尚未涵盖或与此任务相关的具体信息。

收集以下背景信息（如未提供则询问）：

### 1. 当前流失情况
- 你们的月流失率是多少？（如已知，请区分主动与非主动流失）
- 有多少活跃订阅者？
- 每位客户的平均 MRR 是多少？
- 目前是否有取消流程，还是会立即取消？

### 2. 计费与平台
- 使用什么计费服务商？（Stripe、Chargebee、Paddle、Recurly、Braintree）
- 按月、按年，还是同时提供两种计费周期？
- 是否支持暂停套餐或降级？
- 是否已有留存工具？（Churnkey、ProsperStack、Raaft）

### 3. 产品与使用数据
- 是否跟踪每位用户的功能使用情况？
- 能否识别参与度下降？
- 是否有来自过往流失用户的取消原因数据？
- 你们的激活指标是什么？（留存用户做了哪些流失用户没有做的事？）

### 4. 约束条件
- 面向 B2B 还是 B2C？（会影响流程设计）
- 是否必须支持自助取消？（部分法规要求易于取消）
- 用户离开时的品牌语气是什么？（富有同理心、直接、轻松有趣）

## 此 Skill 的工作方式

流失分为两种类型，需要采用不同策略：

| 类型 | 原因 | 解决方案 |
|------|-------|----------|
| **主动流失** | 客户选择取消 | 取消流程、挽留优惠、退出调查 |
| **非主动流失** | 支付失败 | 催款邮件、智能重试、卡片更新器 |

主动流失通常占总流失的 50-70%。非主动流失占 30-50%，但通常更容易解决。

此 Skill 支持三种模式：

1. **构建取消流程** — 从零开始设计，包含调查、挽留优惠和确认
2. **优化现有流程** — 分析取消数据并提高挽留率
3. **设置催款流程** — 通过重试和邮件序列恢复失败支付

## 取消流程设计

### 取消流程结构

每个取消流程都遵循以下顺序：

```
Trigger → Survey → Dynamic Offer → Confirmation → Post-Cancel
```

**步骤 1：触发**
客户在账户设置中点击“取消订阅”。

**步骤 2：退出调查**
询问他们为什么取消。这决定了应展示哪种挽留优惠。

**步骤 3：动态挽留优惠**
根据其原因提供有针对性的优惠（折扣、暂停、降级等）。

**步骤 4：确认**
如果他们仍想取消，请明确确认，并说明将在当前计费周期结束时生效。

**步骤 5：取消后**
设定预期，提供便捷的重新激活路径，触发召回序列。

### 退出调查设计

退出调查是基础。好的原因分类包括：

| 原因 | 说明 |
|--------|-------------------|
| 价格太高 | 对价格敏感，可能会对折扣或降级作出响应 |
| 使用得不够 | 参与度低，可能会对暂停或新手引导帮助作出响应 |
| 缺少某项功能 | 产品缺口，展示路线图或替代方案 |
| 转向竞争对手 | 竞争压力，了解对方提供什么 |
| 技术问题 / Bug | 产品质量问题，升级至支持团队处理 |
| 临时 / 季节性需求 | 使用模式，提供暂停选项 |
| 业务关闭 / 发生变化 | 无法避免，学习并妥善放手 |
| 其他 | 兜底选项，包含自由文本字段 |

**调研最佳实践：**
- 1 个问题，单选，可选择填写自由文本
- 最多提供 5-8 个原因选项（避免决策疲劳）
- 将最常见的原因放在前面（每季度复审数据）
- 不要让用户感觉这是在进行道德指责
- 使用“帮助我们改进”的措辞，比“您为什么要离开？”效果更好

### 动态挽留优惠

关键洞察：**让优惠与原因相匹配。** 对于不使用产品的用户，折扣无法挽留他们。对于无力承担费用的用户，功能路线图也无法挽留他们。

**优惠与原因的映射：**

| 取消原因 | 主要优惠 | 备用优惠 |
|---------------|---------------|----------------|
| 太贵了 | 折扣（2-3 个月内优惠 20-30%） | 降级到更低级别的方案 |
| 使用得不够多 | 暂停（1-3 个月） | 免费入门指导 |
| 缺少某项功能 | 路线图预览 + 时间线 | 解决方法指南 |
| 转投竞争对手 | 竞品对比 + 折扣 | 反馈交流 |
| 技术问题 | 立即升级至支持团队处理 | 赠送额度 + 优先修复 |
| 暂时性 / 季节性需求 | 暂停订阅 | 临时降级 |
| 企业已关闭 | 跳过优惠（尊重用户处境） | — |

### 挽留优惠类型

**折扣**
- 2-3 个月内优惠 20-30% 是最佳区间
- 避免提供 50% 以上的折扣（会让客户养成为了优惠而取消的习惯）
- 限时提供优惠（“离开此页面后，该优惠将失效”）
- 不要只显示百分比，还要显示节省的具体金额

**暂停订阅**
- 最长暂停 1-3 个月（更长的暂停期很少会重新激活）
- 60-80% 的暂停用户最终会恢复活跃
- 提前通过邮件通知自动重新激活
- 保留用户的数据和设置不变

**方案降级**
- 提供更低级别的方案，而不是直接完全取消
- 显示用户可以保留什么，以及会失去什么
- 将其定位为“调整方案规模”，而不是“降级”
- 用户准备好后，可轻松恢复到更高级别

**功能解锁 / 延长使用期限**
- 解锁用户尚未尝试过的高级功能
- 延长更高级别方案的试用期
- 对于“没有获得足够价值”这一类原因最有效

**个性化联系**
- 面向高价值账户（按 MRR 排名前 10-20%）
- 转交客户成功团队安排通话
- 对于规模较小的公司，由创始人发送个性化邮件

### 取消流程 UI 模式

**UI 原则：**
- 保持“继续取消”选项可见（不要使用黑暗模式）
- 提供一个主要优惠 + 一个备用优惠，而不是罗列大量选项
- 显示具体的节省金额，而不是抽象的百分比
- 尽可能使用客户姓名和账户数据
- 适配移动设备（许多取消操作发生在移动端）

在设计流程之前，请阅读 [references/cancel-flow-patterns.md](references/cancel-flow-patterns.md)；其中包含按行业和计费提供商整理的模式、针对不同细分群体的变体、取消后的后续流程，以及调查和优惠步骤的界面样例。

## 流失预测与主动留存

最有效的挽留发生在客户点击“取消”之前。

### 风险信号

跟踪以下流失先行指标：

| 信号 | 风险等级 | 时间范围 |
|--------|-----------|-----------|
| 登录频率下降 50% 以上 | 高 | 取消前 2-4 周 |
| 停止使用关键功能 | 高 | 取消前 1-3 周 |
| 支持工单激增后停止 | 高 | 取消前 1-2 周 |
| 邮件打开率下降 | 中 | 取消前 2-6 周 |
| 访问计费页面的次数增加 | 高 | 取消前几天 |
| 移除团队席位 | 高 | 取消前 1-2 周 |
| 发起数据导出 | 极高 | 取消前几天 |
| NPS 分数降至 6 以下 | 中 | 取消前 1-3 个月 |

### 健康度评分模型

基于加权信号构建一个简单的健康度评分（0-100）：

```
Health Score = (
  Login frequency score × 0.30 +
  Feature usage score   × 0.25 +
  Support sentiment     × 0.15 +
  Billing health        × 0.15 +
  Engagement score      × 0.15
)
```

| 评分 | 状态 | 操作 |
|-------|--------|--------|
| 80-100 | 健康 | 追加销售机会 |
| 60-79 | 需要关注 | 主动联系 |
| 40-59 | 存在风险 | 干预活动 |
| 0-39 | 严重 | 一对一触达 |

### 主动干预

**在他们考虑取消订阅之前：**

| 触发条件 | 干预措施 |
|---------|-------------|
| 使用量连续 2 周下降 >50% | “我们注意到您尚未使用 [feature]。需要帮助吗？”邮件 |
| 接近套餐限制 | 升级提示（不是限制墙——付费墙负责处理此事） |
| 14 天未登录 | 包含近期产品更新的重新互动邮件 |
| NPS 贬损者（0-6） | 在 24 小时内进行个人跟进 |
| 支持工单超过 48 小时未解决 | 升级处理 + 主动状态更新 |
| 年度续订将在 30 天内到期 | 价值回顾邮件 + 续订确认 |

## 非自愿流失：付款追回

付款失败导致了全部流失中的 30-50%，但也是最有可能追回的部分。

### 催款体系

```
Pre-dunning → Smart retry → Dunning emails → Grace period → Hard cancel
```

### 预催款（防止失败）

- **卡片到期提醒**：在卡片到期前 30、15 和 7 天发送邮件
- **备用付款方式**：在注册时提示添加第二种付款方式
- **卡片更新服务**：Visa/Mastercard 自动更新计划（可减少 30-50% 的硬拒付）
- **预扣费通知**：针对年度套餐，在扣费前 3-5 天发送邮件

### 智能重试逻辑

并非所有失败都相同。应根据拒付类型制定重试策略：

| 拒付类型 | 示例 | 重试策略 |
|-------------|----------|----------------|
| 软拒付（临时） | 余额不足、支付处理器超时 | 按照下方的标准时间表重试 |
| 硬拒付（永久） | 卡片被盗、账户已关闭 | 不要重试——要求提供新卡 |
| 需要验证 | 3D Secure、SCA | 引导客户更新付款信息 |

**标准重试时间表：** 此技能由唯一的时间表管理——[references/dunning-playbook.md](references/dunning-playbook.md)
§“按提供商划分的重试时间表”中的手动重试表（第 1 / 3 / 5 / 7 / 10 天，第五次尝试是宽限期结束前的最后一次）。在配置重试前阅读该表，并且不要在任何地方重复声明不同的时间表。

### 催款邮件序列

在第 0 / 3 / 7 / 10 天发送四封邮件。每封邮件的时机、语气和完整文案均位于
[references/dunning-playbook.md](references/dunning-playbook.md) §“催款邮件序列”中——在撰写或配置该序列之前阅读它。

**催款邮件最佳实践：**
- 提供直达付款更新页面的链接（如有可能，无需登录）
- 展示他们将失去什么（其数据、其团队的访问权限）
- 不要指责（“您的付款失败了”，而不是“您未能付款”）
- 包含用于求助的支持联系方式
- 对于催款而言，纯文本邮件的效果优于经过设计的邮件

### 恢复基准

| 指标 | 较差 | 平均 | 良好 |
|--------|------|---------|------|
| 软拒付恢复率 | <40% | 50-60% | 70%+ |
| 硬拒付恢复率 | <10% | 20-30% | 40%+ |
| 整体付款恢复率 | <30% | 40-50% | 60%+ |
| 预催款预防率 | 无 | 10-15% | 20-30% |

这些区间是用于校准建议的行业范围。绝不要将其断言为该产品的结果。

有关包含特定提供商设置的完整催款操作手册，请参阅 [references/dunning-playbook.md](references/dunning-playbook.md)。

## 指标与衡量

### 关键流失指标

| 指标 | 公式 | 目标 |
|--------|---------|--------|
| 月流失率 | 流失客户 / 月初客户数 | <5% B2C，<2% B2B |
| 收入流失率（净额） | (Lost MRR - Expansion MRR) / Start MRR | 负值（净扩张） |
| 取消流程挽回率 | 挽回数 / 总取消会话数 | 25-35% |
| 优惠接受率 | 已接受优惠 / 已展示优惠 | 15-25% |
| 暂停后重新激活率 | 已重新激活 / 总暂停数 | 60-80% |
| 催款恢复率 | 已恢复 / 总支付失败数 | 50-60% |
| 取消耗时 | 从首次流失信号到取消的天数 | 跟踪趋势 |

### 群组分析

按以下维度细分流失：
- **获客渠道** — 哪些渠道带来的客户留存性更强？
- **套餐类型** — 哪些套餐的流失最多？
- **使用时长** — 大多数取消发生在什么时候？（30、60、90 天？）
- **取消原因** — 哪些原因正在增长？
- **挽回优惠类型** — 哪些优惠最适合哪些细分群体？

### 取消流程 A/B 测试

每次测试一个变量：

| 测试 | 假设 | 指标 |
|------|-----------|--------|
| 折扣百分比（20% vs 30%） | 更高的折扣能挽回更多客户 | 挽回率、LTV 影响 |
| 暂停时长（1 个月 vs 3 个月） | 更长的暂停时间会提高回归率 | 重新激活率 |
| 问卷位置（优惠前 vs 优惠后） | 先进行问卷可实现优惠个性化 | 挽回率 |
| 优惠呈现方式（模态框 vs 整页） | 整页能获得更多关注 | 挽回率 |
| 文案语气（共情式 vs 直接式） | 共情式能减少阻力 | 挽回率 |

**如何运行取消流程实验：** 将假设、样本、持续时间和停止规则交由 `suede-ab-testing`。使用经过授权的实验系统，该系统能够一致地分配用户，并读取漏斗中的每个步骤（问卷 → 优惠 → 接受/拒绝 → 确认）。在上线前，验证该系统当前的官方实现指南、分配行为和事件回读能力。

## 常见错误

- **完全没有取消流程** — 立即取消会错失收入机会。即使是简单的问卷 + 一个优惠，也能挽回 10-15%
- **未跟踪挽回优惠的 LTV** — 一位“被挽回”的客户如果 30 天后流失，实际上并没有被真正挽回
- **没有取消后的路径** — 应使重新激活变得容易，并触发召回邮件，因为部分已流失用户会希望回来

## 工具集成

此包不附带留存、计费或分析连接器。请从用户实际的技术栈中选择经过授权的系统，并在配置前验证其当前官方文档、账户计划、测试模式和回滚路径。

### 能力清单

- 取消流程路由、问卷收集，以及不受阻碍的最终取消操作
- 稳定的实验分配和步骤级事件回读
- 具有明确资格条件的暂停、降级和挽留优惠规则
- 支付重试状态、卡片更新器状态和客户通知控制
- 审计历史、测试模式、角色控制，以及回滚或禁用行为

### 实施路由

- 将消息撰写路由至 `suede-emails`。
- 将事件架构和回读路由至 `suede-analytics`。
- 将测试设计路由至 `suede-ab-testing`。
- 将账单重试、折扣、订阅变更和激活视为需要分别授权的变更操作。

### 账单变更的暂停格式

在对线上账单对象进行任何变更之前——重试规则、折扣、套餐
变更、暂停、取消、订阅状态或面向客户的账单
消息——停止并输出以下区块，然后等待。推断出的同意并非
授权，“用户要求取消流程”也不构成配置该流程的授权。

```
HALT — billing mutation requires authorization

Mutation: <the exact change, e.g. "enable 5-attempt retry rule">
Objects touched: <provider, environment, subscriptions/customers/coupons affected, count>
Reversible by: <the exact rollback, or "not reversible">

Options:
1. Proceed in test mode only
2. Proceed on live objects as specified
3. Narrow the scope to <smaller set> and proceed
4. Abandon this mutation

Waiting for your choice.
```

## 边界

- 不得阻碍取消操作、隐藏降级路径、制造紧迫感，或使用具有欺骗性的挽留阻力。
- 未经明确授权，不得变更订阅、重试规则、折扣、账单对象或客户消息。
- 未定义群组、时间窗口、分母并验证支付状态时，不得声称已挽回收入或降低流失率。
- 不得依据受保护特征或缺乏依据的推断，决定哪位具体客户应获得敏感优惠。

## 路由

- 需要留存、催缴或召回消息 -> 使用 `suede-emails`。
- 需要套餐结构或优惠经济模型 -> 使用 `suede-pricing` 或 `suede-offers`。
- 需要付费墙或试用到期 UX -> 使用 `suede-paywalls`。
- 需要流失事件或受控留存测试 -> 使用 `suede-analytics` 或 `suede-ab-testing`。
- 以订阅者身份查找、取消或争议处理自己的定期扣费 -> 使用 `subscription-recovery`。此技能仅面向商家侧。
- 从这些技能中，将取消和支付恢复策略路由回 `suede-churn-prevention`。
