# Suede A/B 测试设置

使用这份 Suede 实验手册来设计能够产生统计有效且可执行结果的测试。

## 铁律

```
在测试启动前预先确定三件事——每个变体的样本量、
最短持续时间和决策规则——并且只有在三者全部满足后才读取结果。
在此之前读取的结果都属于初步结果。
绝不能据此判定胜者。
```

- **每个变体的样本量**：使用下方的样本量表，或根据实际基线运行计算器。
- **最短持续时间**：完整的 1 周（考虑星期几的变化）；B2B 场景覆盖 2 个业务周期；电子商务场景覆盖发薪日——参见 [references/sample-size-guide.md](references/sample-size-guide.md) 中的“最短持续时间规则”部分。
- **决策规则**：明确由哪个指标、达到什么阈值来决定结论——必须在启动前写下，而不是事后补写。

只有以下两种例外：

- **预先声明的序贯设计或始终有效设计**可以根据其自身的停止规则提前查看结果（参见样本量指南中的“序贯测试”）。在查看结果后才声明采用序贯设计，不算数。
- **因护栏指标触发而出于避免伤害目的停止**属于停止，不是胜者判定。终止该变体，不报告结果。

## 初步评估

检查是否存在 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，或旧版的 `product-marketing-context.md`），如果存在则读取它——基线转化率、流量规模和可用工具决定测试是否具备足够的统计功效，而这些信息通常已经记录在那里。

## 假设框架

### 结构

```
由于 [观察结果/数据]，
我们认为 [变更]
将为 [受众]
带来 [预期结果]。
当 [指标] 达到预期时，我们就知道这一点成立。
```

### 示例

**较弱**：“更改按钮颜色可能会增加点击量。”

**较强**：“由于用户反馈难以找到 CTA（热力图和反馈均显示如此），我们认为放大按钮并使用高对比度颜色，将使新访客的 CTA 点击量提升 15% 以上。我们将衡量从页面浏览到开始注册的点击率。”

|------|-------------|----------------|

| A/B/n | 多个变体 | 更高 |

## 样本量

### 快速参考

| 基线 | 10% 提升 | 20% 提升 | 50% 提升 |
|----------|----------|----------|----------|
| 1% | 每个变体 150k | 每个变体 39k | 每个变体 6k |
| 3% | 每个变体 47k | 每个变体 12k | 每个变体 2k |
| 5% | 每个变体 27k | 每个变体 7k | 每个变体 1.2k |
| 10% | 每个变体 12k | 每个变体 3k | 每个变体 550 |

## 指标选择

### 主要指标
- 最重要的单一指标
- 与假设直接相关
- 用于判定测试结果的指标

### 次要指标
- 支持对主要指标的解读
- 解释变更为何以及如何奏效

### 护栏指标
- 不应变差的指标
- 如果出现显著负面影响，则停止测试

### 示例：定价页面测试
- **主要指标**：方案选择率
- **次要指标**：页面停留时间、方案分布
- **护栏指标**：支持工单、退款率

## 设计变体

### 可变更的内容

| 类别 | 示例 |
|----------|----------|
| 标题/文案 | 信息角度、价值主张、具体程度、语气 |
| 视觉设计 | 布局、颜色、图片、层级 |
| CTA | 按钮文案、大小、位置、数量 |
| 内容 | 包含的信息、顺序、数量、社会证明 |

### 最佳实践
- 进行单一且有意义的变更
- 变更幅度要足够大，能够产生差异
- 确保变更符合假设

## 流量分配

| 方式 | 比例 | 适用场景 |
|----------|-------|-------------|
| 标准 | 50/50 | A/B 测试的默认选择 |
| 保守 | 90/10、80/20 | 限制不良变体的风险 |
| 逐步增加 | 从较小比例开始，逐步增加 | 降低技术风险 |

**注意事项：**
- 一致性：用户回访时应看到相同的变体
- 确保不同时间段（一天中的不同时段、不同星期）获得均衡曝光

### 客户端
- 页面加载后由 JavaScript 修改页面
- 实施快速，但可能导致闪烁
- 工具：PostHog、Optimizely、VWO

### 服务端
- 在渲染前确定变体
- 不会闪烁，但需要开发工作
- 工具：PostHog、LaunchDarkly、Split

## 运行测试

### 发布前检查清单

每个复选框都标明了完成该项所需的产物。未勾选的复选框意味着测试
在未经验证的情况下运行：它产生的任何结果只能作为未经验证的结果进行报告，
而一个悄然损坏的变体会使整个运行期间的流量失效。

- [ ] **假设已记录** — 按照上述框架结构编写，并与测试记录一起保存
- [ ] **已定义主要指标** — 指标名称及预先声明的决策规则
- [ ] **已计算样本量** — 每个变体所需的 n 值及预计结束日期，依据表格或计算器得出
- [ ] **变体已正确实现** — 每个变体实际提供时的准确截图或录屏
- [ ] **已验证追踪** — 显示曝光事件和转化事件已触发且属性正确的事件回读（使用 `suede-analytics` 完成埋点和回读）
- [ ] **所有变体均已完成 QA** — 测试将覆盖的每种浏览器和设备类别均已通过检查

### 测试期间

**应该做：**
- 监控技术问题
- 检查细分群体质量
- 记录外部因素

**应避免：**
- 偷看结果并提前停止
- 修改变体
- 从新的来源增加流量

### 偷看结果的问题
在达到样本量之前查看结果并提前停止，会导致假阳性和错误决策。预先承诺样本量，并相信这一流程。

## 分析结果

### 统计显著性
- 95% 置信度 = p-value < 0.05
- 表示结果由随机因素造成的概率小于 5%
- 这不是保证，只是一个阈值。

### 分析检查清单

1. **达到样本量了吗？** 如果没有，结果仍属于初步结果
2. **具有统计显著性吗？** 检查置信区间
3. **效果量有意义吗？** 与 MDE 和项目影响进行比较
4. **次要指标是否一致？** 是否支持主要指标？
5. **是否存在护栏指标问题？** 是否有任何指标变差？
6. **不同细分群体之间是否存在差异？** 移动端与桌面端？新用户与回访用户？

### 结果解读

| 结果 | 结论 |
|--------|------------|
| 具有显著性的获胜方案 | 实施该变体 |
| 具有显著性的失败方案 | 保留对照组，了解原因 |
| 无显著差异 | 需要更多流量或更大胆的测试 |
| 信号不一致 | 深入分析，或许可以进行细分 |

## 增长实验项目

单个测试很有价值。持续的实验项目是一项会产生复利效应的资产。本节介绍如何将实验作为持续的增长引擎来运行，而不只是一次性测试。

### 实验循环

```
1. 生成假设（来自数据、研究、竞争对手、客户反馈）
2. 使用 ICE 评分进行优先级排序
3. 设计并运行测试
4. 以严谨的统计方法分析结果
5. 将获胜方案纳入行动手册
6. 从经验总结中生成新的假设
→ 重复
```

### 假设生成

从多个来源为你的实验待办列表提供假设：

| 来源 | 需要关注的内容 |
|--------|-----------------|
| 分析数据 | 流失点、低转化页面、表现不佳的细分群体 |
| 客户研究 | 痛点、困惑、未满足的预期——使用 `suede-customer-research` 生成这些内容 |
| 竞争对手分析 | 他们使用而你没有使用的功能、消息传递或 UX 模式——使用 `suede-competitor-profiling` 生成这些内容 |
| 支持工单 | 关于转化流程的重复问题或投诉 |
| 热力图/录屏 | 用户犹豫、愤怒点击或放弃的位置 |
| 过往实验 | “显著失败方案”通常会揭示值得尝试的新方向 |

### ICE 优先级排序

在三个维度上分别以 1-10 分为每个假设评分：

| 维度 | 问题 |
|-----------|----------|
| **影响力** | 如果奏效，它将对主要指标产生多大影响？ |
| **信心** | 我们有多大把握它会奏效？（基于数据，而不是直觉。） |
| **易行性** | 我们能以多快的速度、以多低的成本发布并衡量它？ |

**ICE 得分** = (影响力 + 信心 + 易行性) / 3

优先运行得分最高的实验。随着背景情况变化，每月重新评分。

### 实验速度

将实验速率作为增长的先行指标进行跟踪：

| 指标 | 目标 |
|--------|--------|
| 每月启动的实验数 | 对大多数团队而言为 4-8 个 |
| 胜率 | 对于成熟项目而言，20-30% 很常见（持续更高的胜率可能意味着假设过于保守） |
| 平均测试时长 | 2-4 周 |
| 待办列表深度 | 排队中的假设数量达到 20+ |
| 累计提升 | 所有获胜方案带来的复合收益 |

### 实验手册

当一个测试获胜时，不要只是实施它——要记录下这一模式：

```
## [Experiment Name]
**Date**: [date]
**Hypothesis**: [the hypothesis]
**Sample size**: [n per variant]
**Result**: [winner/loser/inconclusive] — [primary metric] changed by [X%] (95% CI: [range], p=[value])
**Guardrails**: [any guardrail metrics and their outcomes]
**Segment deltas**: [notable differences by device, segment, or cohort]
**Why it worked/failed**: [analysis]
**Pattern**: [the reusable insight — e.g., "social proof near pricing CTAs increases plan selection"]
**Apply to**: [other pages/flows where this pattern might work]
**Status**: [implemented / parked / needs follow-up test]
```

随着时间推移，你的手册会逐渐成为一个专属于你的产品和受众、收录已验证增长模式的知识库。

### 实验节奏

**每周（30 分钟）**：检查正在运行的实验是否存在技术问题，以及防护指标的表现。不要过早宣布获胜——但如果防护指标显著为负，应停止测试。

**每两周**：结束已完成的实验。分析结果，更新手册，从待办列表中启动下一个实验。

**每月（1 小时）**：复盘实验速度、获胜率和累计提升。补充假设待办列表。使用 ICE 重新确定优先级。

**每季度**：审查实验手册。哪些模式已经得到广泛应用？哪些获胜模式还没有扩展？漏斗的哪些环节测试不足？

## 诡辩

这项技能旨在防止的失败，是在压力下过早宣布结果。当以下说法中的任何一句出现时——无论是利益相关者说的，还是你自己说的——答案已经写在本文件中。

| 借口 | 事实 |
|--------|---------|
| “在 95% 的置信水平下已经显著了” | 95% 是一个阈值，不是保证。在预先声明的样本量达到之前检查显著性属于窥探，而窥探会提高假阳性率。分析检查清单第 1 项仍然适用：初步结果。 |
| “我们已经运行两周了” | 时长只是三个条件之一，并非唯一条件。在解读任何内容之前，先根据样本量表检查每个变体的 n。 |
| “趋势已经很明显了” | 早期趋势经常反转——这正是“窥探问题”所描述的情况。在样本量达到 30% 时出现明显趋势，恰恰是应该等待而不是停止的理由。 |
| “领导层周五需要一个答案” | 那就将其报告为初步结果，并披露已达到的样本量以及提前停止的状态（边界）。把提前停止的结果包装成胜者，会在两季度后损害你的可信度。 |
| “失败的变体显然很差，为什么还要继续提供” | 因防护指标显著为负而停止是合理的（实验节奏）。但因伤害而停止就是停止，并不等于宣布控制组获胜。 |
| “移动端细分获胜了” | 未预先声明的细分只是下一次测试的假设，而不是结果。事后选择细分，会从噪声中人为制造显著性。 |
| “数据看起来没问题，不需要重新检查构建” | 变体可能在运行过程中静默失效：脚本失败、标记翻转、事件停止触发。在解读结果之前，而不仅仅是在启动前，重新验证事件是否触发以及变体是否正确渲染。 |
| “它没有获胜，但次要指标获胜了” | 无结论本身就是一种结果。过度解读无效测试，正是实验手册最终充满无法复现的模式的原因。 |
| “我们再往这个实验里加入几个改动吧” | 同时进行多项改动无法被单独隔离，而且进一步拆分流量会使每个实验臂都低于所需样本量（参见设计变体）。 |

## 针对任务的问题

1. 你当前的转化率是多少？
2. 此页面获得了多少流量？
3. 你正在考虑什么变更，原因是什么？
4. 值得检测的最小改进幅度是多少？
5. 你有哪些测试工具？
6. 你之前测试过这一区域吗？

---

## 边界

- 在满足预先声明的样本量、持续时间和决策规则之前，不要声称某个方案胜出。
- 未经明确授权且没有回滚路径，不要更改生产流量分配、实验设置或分析数据。
- 发布结果时，必须报告不确定性、护栏指标变化、排除项以及是否提前停止。
- 不要认定统计显著性等于业务价值；应将效果与最小有用提升幅度进行比较。

## 路由

- 需要事件或转化埋点 -> 使用 `suede-analytics`。
- 需要页面级诊断或测试创意 -> 使用 `suede-site-alchemy`。
- 需要变体文案 -> 使用 `suede-copy`。
- 结果无法得出结论，且问题是该变更是否产生了任何影响 -> 使用 `suede-attribution` 进行增量性分析和地理留出设计。
- 对于这些技能，将假设设计、统计功效检查和实验结果解读转回 `suede-ab-testing`。
