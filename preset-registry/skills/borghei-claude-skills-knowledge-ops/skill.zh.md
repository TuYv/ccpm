# 知识运营

知识库不会因为内容不完整而失败。它们失败是因为变得不再可信：一旦读者被言之凿凿却错误的页面坑过两次，他们就会停止阅读，转而在聊天中提问，此后你写的每一篇文档都如同石沉大海。此技能将知识库视为一个具备负责人、内容新鲜度 SLA 和可量化健康评分的运营系统，而不是一份写作积压清单。

核心洞见是：**删除是可采取的最高价值行动**。大多数陷入困境的知识库需要的不是更多页面，而是减少 30% 的页面。

## 何时使用此技能

- Wiki **规模庞大且不受信任**——人们宁愿在聊天中提问也不愿搜索，而且事实证明他们是对的
- 在新员工群体入职、收购整合或合规审查之前，需要进行一次**文档审计**
- **搜索总是返回错误的页面**，通常是因为三个近乎重复的页面相互竞争
- 知识库的大部分内容**无人负责**，也没人能说清哪些内容是最新的
- 正在规划一次**文档债务冲刺**，需要的是一份按优先级排序的积压清单，而不是愿望清单
- 正在不同 Wiki 平台之间进行**迁移**，需要决定哪些内容值得保留

## 此技能所需的输入

- 一份**文档清单**：路径、标题、负责人、最后更新日期和出站链接
- 每份文档的**关键性层级**，或足以推断该层级的信号（流量、所属领域）
- 如有可用的**使用数据**——过去 90 天的浏览量可以区分承担关键作用的页面和归档内容
- 审计的**截止日期**，以确保结果可复现
- 你的**内容新鲜度 SLA 策略**，或接受下方的默认分层方式
- **在组织层面是否允许删除**，这会改变整个修复计划

## 首先澄清

生成内容之前，请确认以下输入。如有任何一项未知或含糊，请提问——不要自行假设：

- [ ] **哪些文档承担关键作用，哪些属于归档内容**——陈旧的入职操作手册可能会导致事故；陈旧的 2019 年复盘则无伤大雅。若对二者一视同仁，只会产生一份无人处理的积压清单
- [ ] **页面可以删除，还是只能归档**——拥有删除权限大约能让修复工作量减半，因此计划在结构上会有所不同
- [ ] **谁可以被指定为负责人**——将负责人指定为团队别名与没有负责人无异，审计仍会持续报告此问题
- [ ] **审计的截止日期**——内容是否过时取决于参照时间，没有日期的审计无法与下一次审计进行比较

停止规则：只询问对输出影响最大的 2-3 项。如果用户说“直接起草”，则继续执行，并在交付物顶部列出你的假设。

## 工作流

### 工作流 1——评估知识库健康状况

1. 将文档清单构建为 JSON，或让审计工具扫描一个包含
   YAML 前置元数据（`owner`、`updated`、`tier`）的 markdown 目录。
2. 使用明确的 `--as-of` 日期运行审计工具，以确保此次运行可复现。
3. 将健康评分视为趋势，而不是绝对值。首次运行低于 60 分很正常；
   真正重要的是每季度运行之间的变化方向。
4. 优先处理 `critical` 发现项——关键层级文档内容陈旧，正是会导致真实事故的那类故障。

```bash
python3 business-operations/knowledge-ops/scripts/kb_health_auditor.py \
  --input business-operations/knowledge-ops/assets/sample_kb.json \
  --as-of 2026-07-21 --format text
```

如果要改为扫描实际的 Markdown 目录：

```bash
python3 business-operations/knowledge-ops/scripts/kb_health_auditor.py \
  --root ./docs --as-of 2026-07-21 --format json
```

### 工作流 2 — 查找孤立页面、失效链接和重复内容

1. 对同一份清单运行孤立页面检测器。它会构建链接图，并报告没有任何内容链接到的页面、指向不存在页面的链接，以及枢纽页面。
2. 将孤立页面与流量数据进行交叉核对。**有流量的孤立页面属于可发现性缺陷**（人们通过搜索或书签访问它，但信息架构并未将其连接起来）。**没有流量的孤立页面可以考虑删除。**这两种情况需要采取相反的修复措施。
3. 优先修复失效链接——修复成本低，而且它们是知识库缺乏维护最显眼的信号。

```bash
python3 business-operations/knowledge-ops/scripts/orphan_detector.py \
  --input business-operations/knowledge-ops/assets/sample_kb.json \
  --format text
```

### 工作流 3 — 构建按优先级排序的文档债务待办列表

1. 对清单运行债务排序器。它会根据价值（流量 × 关键程度 × 严重程度）和工作量为每个问题评分，然后将其分为立即处理 / 计划处理 / 批量处理 / 放弃。
2. 选取排名前 10 的问题纳入一次债务冲刺。不要试图处理整个待办列表——待办列表是衡量工具，而不是计划。
3. 冲刺结束后，使用相同的 `--as-of` 约定重新运行审计器，以展示变化。

```bash
python3 business-operations/knowledge-ops/scripts/doc_debt_ranker.py \
  --input business-operations/knowledge-ops/assets/sample_kb.json \
  --as-of 2026-07-21 --top 10 --format text
```

## 决策框架

### 按层级划分的时效性 SLA [已验证]

统一的审查周期之所以失败，是因为它产生的审查工作量超出了任何团队的承受能力，最终导致没有任何内容得到审查。因此，应当按层级划分 SLA。

| 层级 | 示例 | 审查 SLA | 过期时间 | 过期后的操作 |
|------|----------|-----------|----------|-------------------|
| **关键** | 值班运行手册、事件处理流程、安全策略、薪资流程 | 90 天 | 120 天 | 通知负责人；过期的运行手册会带来事件风险 |
| **核心** | 新员工入职、架构概览、团队章程、发布流程 | 180 天 | 270 天 | 在下一个冲刺中为负责人创建审查工单 |
| **参考** | 操作指南、工具指南、常见问题 | 365 天 | 540 天 | 每年批量审查 |
| **归档** | 复盘文档、过往项目文档、历史决策 | 永不 | 永不 | 标记为已归档；从搜索和评分中排除 |

对于大多数知识库而言，最有价值的单项配置变更，是将 40% 的页面移入归档，并将其从搜索中排除。搜索质量是一个比率，而问题通常出在分母上。

### 孤立页面分诊 [已验证]

| 入站链接数 | 90 天流量 | 诊断 | 操作 |
|---------------|----------------|-----------|--------|
| 0 | 0 | 无用内容 | 删除。不是归档——而是删除 |
| 0 | 低（1-50） | 仅靠书签存续的页面 | 从正确的枢纽页面链接到它，或将其合并到父页面中 |
| 0 | 高（50+） | 可发现性缺陷 | 立即从枢纽页面链接到它；人们依赖着一个被信息架构隐藏的页面 |
| 1-2 | 任意 | 连接薄弱 | 如果父页面正确，则没有问题 |
| 10+ | 高 | 枢纽页面 | 保护它；指定一名明确的负责人，并应用关键层级 SLA |

### 重复内容的处理 [建议]

当两个或更多页面涵盖同一主题时，**应合并到入站链接最多的页面中**，而不是合并到写得最好的页面中。入站链接代表整个组织长期积累的导航习惯；重写胜出的页面成本很低，而重建链接权重则不然。将其他页面重定向到胜出页面，绝不要直接悄然删除——收藏页面出现 404，比页面内容陈旧更损害信任。

例外情况：如果链接最多的版本存在事实性错误，而另一个版本是正确的，则仍合并到链接最多的页面中，但彻底替换其内容。URL 胜出，内容则不然。

### 健康评分区间

| 分数 | 解读 | 应对措施 |
|-------|---------|----------|
| 80-100 | 健康；维护模式 | 每季度审计，维持 SLA |
| 60-79 | 正在退化；信任仍然存在 | 开展一次技术债冲刺，重点处理关键层级内容的陈旧问题 |
| 40-59 | 已失去信任；人们开始在聊天工具中询问 | 先开展所有权分配冲刺，再处理内容 |
| 0-39 | 已失效；重写比修复成本更低 | 按流量选出前 20 个页面，重建这些页面，归档其他所有页面 |

## 反模式

### 没有所有者的文档冲刺
**错误做法：** 开展为期一周、人人都参与编写文档的活动，然后宣布知识库已经修复。
**产生原因：** 编写工作直观可见、令人有成就感，而且易于组织。所有权工作则不具备这些特点。
**正确做法：** 在编写任何内容之前先指定所有者。无人负责的页面在写成之日便已陈旧——只是尚未被人发现而已。如果只能做一件事，就分配所有权；拥有所有者但内容陈旧的知识库能够恢复，而内容崭新却无人负责的知识库会在两个季度内退化到相同状态。

### 将团队别名设为所有者
**错误做法：** 将所有者字段设置为 `@platform-team` 或 `docs@company.com`。
**产生原因：** 这种方式不受人员离职影响，而且感觉比指定个人更稳健。
**正确做法：** 指定一个人，并将团队作为备用字段。发送到群组别名的审核通知无人阅读——这是知识库运维中最可靠的结论。必要时可以每季度轮换指定的所有者，但所有者必须是个人。

### 用归档代替删除
**错误做法：** 将每个过时页面都移至归档空间，而不是将其删除。
**产生原因：** 删除让人感觉有风险且不可逆，而且总会有人说“我们以后可能还会用到它”。
**正确做法：** 直接删除入站链接和流量均为零的页面——版本历史已经保留了这些页面。归档用于具有历史或合规价值的文档，而不是用于存放你不敢删除的内容。无限增长的归档并不比删除更安全，只是一种发生得更慢的失效模式。

### 优化搜索而不是修复内容
**错误做法：** 面对“搜索坏了”的反馈，通过调整搜索引擎或购买新搜索引擎来应对。
**产生原因：** 这是一个有供应商解决方案的采购问题，比需要组织层面解决方案的内容问题更容易处理。
**正确做法：** 搜索失败几乎总是因为三个近乎重复的页面在竞争同一个查询，而搜索引擎无法判断哪个页面是最新的。合并重复页面，并将归档内容排除在索引之外。在评估任何搜索产品之前先这样做——通常这样就能彻底解决问题。

### 在没有截止日期的情况下进行审计
**错误：** 临时运行审计，并比较不同运行批次的结果。
**原因：** 工具默认使用“今天”，却没有人记录“今天”具体是哪一天。
**正确做法：** 始终显式传入 `--as-of` 并保存输出。知识库健康状况只有作为趋势时才有意义；两次没有日期的审计无法进行比较，而没有趋势支撑的数字也不会受到 remediation 资金提供者的重视。
