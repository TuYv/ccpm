# 技术栈评估器

一个用于比较技术、框架、云提供商和完整技术栈的综合评估框架。提供基于数据的建议，包括 TCO 分析、安全评估、生态系统健康度评分和迁移路径分析。

## 功能

此技能提供八项综合评估功能：

- **技术比较**：对框架、语言和工具进行一对一比较（React 与 Vue、PostgreSQL 与 MongoDB、Node.js 与 Python）
- **技术栈评估**：针对特定用例评估完整的技术栈（实时协作、以 API 为主的 SaaS、数据密集型平台）
- **成熟度与生态系统分析**：评估社区健康度、维护状态、长期可行性和生态系统实力
- **总体拥有成本 (TCO)**：计算包括许可、托管、开发者生产力和扩展在内的综合成本
- **安全与合规**：分析漏洞、合规准备情况（GDPR、SOC2、HIPAA）和安全态势
- **迁移路径分析**：评估从遗留技术栈迁移到现代技术栈的复杂性、风险、时间表和策略
- **云提供商比较**：针对特定工作负载比较 AWS、Azure 和 GCP，并进行成本与功能分析
- **决策报告**：生成包含优缺点、置信度评分和可行建议的综合决策矩阵

## 输入要求

### 灵活的输入格式（自动检测）

此技能可自动检测并处理多种输入格式：

**文本/对话**：
```
"Compare React vs Vue for building a SaaS dashboard"
"Evaluate technology stack for real-time collaboration platform"
"Should we migrate from MongoDB to PostgreSQL?"
```

**结构化格式 (YAML)**：
```yaml
comparison:
  technologies:
    - name: "React"
    - name: "Vue"
  use_case: "SaaS dashboard"
  priorities:
    - "Developer productivity"
    - "Ecosystem maturity"
    - "Performance"
```

**结构化格式 (JSON)**：
```json
{
  "comparison": {
    "technologies": ["React", "Vue"],
    "use_case": "SaaS dashboard",
    "priorities": ["Developer productivity", "Ecosystem maturity"]
  }
}
```

**用于生态系统分析的 URL**：
- GitHub 仓库 URL（用于健康度评分）
- npm 软件包 URL（用于下载量统计）
- 技术文档 URL（用于功能提取）

### 分析范围选择

用户可以选择要运行的分析：
- **快速比较**：基础评分和比较（200-300 个 token）
- **标准分析**：评分 + TCO + 安全（500-800 个 token）
- **综合报告**：包括迁移路径在内的所有分析（1200-1500 个 token）
- **自定义**：用户选择特定部分（模块化）

   - 可扩展性特征

## 脚本

### 核心模块

- **`stack_comparator.py`**：使用加权评分算法的主比较引擎
- **`tco_calculator.py`**：总拥有成本计算（许可、托管、开发者生产力、扩展）
- **`ecosystem_analyzer.py`**：社区健康度评分、GitHub/npm 指标、可持续性评估
- **`security_assessor.py`**：漏洞分析、合规准备情况、安全评分
- **`migration_analyzer.py`**：迁移复杂度评分、风险评估、工作量估算
- **`format_detector.py`**：自动检测输入格式（文本、YAML、JSON、URL）
- **`report_generator.py`**：支持渐进式披露的上下文感知报告生成器

### 实用工具模块

- **`data_fetcher.py`**：从 GitHub、npm、CVE 数据库获取实时数据
- **`benchmark_processor.py`**：处理并标准化性能基准测试数据
- **`confidence_scorer.py`**：计算推荐结果的置信度

## 指标与计算

### 1. 评分与比较指标

**技术比较矩阵**：
- 功能完整性（0-100 分）
- 学习曲线评估（简单/中等/困难）
- 开发者体验评分
- 文档质量（0-10 分）
- 加权总分

**决策评分算法**：
- 用户自定义的标准权重
- 标准化评分（0-100）
- 置信区间
- 敏感性分析

### 2. 财务计算

**TCO 构成**：
- **初始成本**：许可、培训、迁移
- **运营成本**：托管、支持、维护（按月/按年）
- **扩展成本**：每用户成本、基础设施扩展预测
- **开发者生产力**：对产品上市时间的影响、开发速度倍数
- **隐性成本**：技术债务、供应商锁定风险

**ROI 计算**：
- 成本节省预测（3 年、5 年）
- 生产力提升（节省的开发者工时）
- 盈亏平衡分析
- 风险调整后回报

**单位指标成本**：
- 每用户成本（按月/按年）
- 每次 API 请求的成本
- 每 GB 存储/传输成本
- 每计算小时成本

### 3. 成熟度与生态系统指标

**健康度评分（0-100 分）**：
- **GitHub 指标**：星标数、复刻数、贡献者数量、提交频率
- **npm 指标**：每周下载量、版本稳定性、依赖项数量
- **发布节奏**：定期发布、语义化版本规范遵循情况
- **问题管理**：响应时间、解决率、未解决与已解决问题的数量对比

**社区指标**：
- 活跃维护者数量
- 贡献者增长率
- Stack Overflow 问题数量
- 就业市场需求（招聘信息分析）

**可行性评估**：
- 企业支持力度
- 社区可持续性
- 替代方案的可用性
- 长期风险评分

### 4. 安全与合规指标

**安全评分**：
- **CVE 数量**：已知漏洞（过去 12 个月、过去 3 年）
- **严重程度分布**：严重/高危/中危/低危漏洞数量
- **补丁频率**：平均修复时间（天）
- **安全历史记录**：历史安全状况

**合规就绪度**：
- **GDPR**：数据隐私功能、同意管理、数据可移植性
- **SOC2**：访问控制、加密、审计日志
- **HIPAA**：PHI 处理、加密标准、访问控制
- **PCI-DSS**：支付数据安全（如适用）

**合规评分（按标准）**：
- 就绪：合规度为 90-100%
- 基本就绪：70-89%（存在少量差距）
- 部分就绪：50-69%（需要开展大量工作）
- 未就绪：<50%（存在重大差距）

### 5. 迁移分析指标

**复杂度评分（1-10 分）**：
- **代码变更**：预计受影响的代码行数
- **架构影响**：破坏性变更、API 兼容性
- **数据迁移**：模式变更、数据转换复杂度
- **停机要求**：能否实现零停机与计划停机的对比

**工作量估算**：
- 开发工时（按组件划分）
- 测试工时
- 培训工时
- 总人月数

**风险评估**：
- **技术风险**：API 不兼容、性能下降
- **业务风险**：停机影响、功能对等性差距
- **团队风险**：学习曲线、技能差距
- **缓解策略**：针对具体风险的建议

**迁移阶段**：
- 阶段 1：规划和原型设计（时间线、工作量）
- 阶段 2：核心迁移（时间线、工作量）
- 阶段 3：测试和验证（时间线、工作量）
- 阶段 4：部署和监控（时间线、工作量）

### 6. 性能基准指标

**吞吐量/延迟**：
- 每秒请求数（RPS）
- 平均响应时间（ms）
- P95/P99 延迟百分位数
- 并发用户容量

**资源使用情况**：
- 内存消耗（MB/GB）
- CPU 利用率（%）
- 存储需求
- 网络带宽

**可扩展性特征**：
- 水平扩展效率
- 垂直扩展上限
- 单位性能成本
- 扩展拐点

## 最佳实践

### 确保评估准确

1. **明确用例**：说明具体需求、约束条件和优先级
2. **提供完整背景信息**：团队规模、现有技术栈、时间线、预算约束
3. **设定合理的优先级**：对于多因素决策，使用加权标准（总计 = 100%）
4. **考虑团队技能**：将学习曲线和现有专业能力纳入考量
5. **着眼长期**：评估未来 3-5 年的发展前景，而不仅仅是当前需求

### TCO 分析

1. **纳入所有成本构成**：不要遗漏培训、迁移和技术债务
2. **采用切合实际的扩展预测**：以实际增长指标为基础，而非一厢情愿的设想
3. **将开发者生产力纳入考量**：上市时间和开发速度是关键成本
4. **考虑隐性成本**：供应商锁定、退出成本、技术债务累积
5. **验证假设**：记录所有 TCO 假设以供审查

### 迁移决策

1. **从风险评估开始**：尽早识别阻碍性问题
2. **规划渐进式迁移**：尽可能避免一次性全面重写
3. **为关键路径构建原型**：在正式投入前测试复杂的迁移场景
4. **制定回滚计划**：始终准备好后备策略
5. **测量基准性能**：在迁移前确定当前指标

### 安全评估

1. **检查近期漏洞**：重点关注过去 12 个月，以评估当前安全状况
2. **审查补丁响应时间**：快速修补比零漏洞更重要
3. **验证合规声明**：供应商声明 ≠ 实际的合规就绪程度
4. **考虑供应链**：评估所有依赖项的安全性
5. **测试安全功能**：不要想当然地认为功能会按照文档所述正常工作

## 局限性

### 数据准确性

- **生态系统指标**是特定时间点的快照（GitHub 星标数、npm 下载量变化迅速）
- **TCO 计算结果**是基于所提供假设和市场费率的估算
- **基准测试数据**可能无法反映您的具体用例或配置
- **安全漏洞数量**取决于公共 CVE 数据库的完整性

### 范围边界

- **行业特定要求**：某些专业行业可能存在标准分析未涵盖的独特约束
- **新兴技术**：非常新的技术（问世不足 1 年）可能缺乏足够的数据，无法进行准确评估
- **定制/专有解决方案**：没有相关数据时，无法评估闭源或内部工具
- **政治/组织因素**：无法考虑公司政治、供应商关系或遗留承诺

### 上下文限制

- **团队技能评估**：无法直接评估您团队的具体技能和学习能力
- **现有架构**：除非提供迁移上下文，否则建议均以全新项目为前提
- **预算约束**：TCO 分析可以提供成本信息，但无法替您做出预算决策
- **时间压力**：无法考虑业务期限和产品上市时间的紧迫性

### 不应使用此技能的情况

- **简单决策**：在几乎相同的工具之间进行选择（根据团队偏好决定）
- **指定解决方案**：技术选型已由管理层或政策决定
- **上下文不足**：不了解自身的需求、优先级或约束条件
- **实时生产决策**：用于规划，而非处理紧急生产问题
- **非技术决策**：业务战略、招聘、组织问题

## 置信度等级

此技能会为所有建议提供置信度分数：

- **高置信度（80-100%）**：数据充分、胜出者明确、风险较低
- **中等置信度（50-79%）**：数据良好、存在权衡、风险适中
- **低置信度（<50%）**：数据有限、难分高下、不确定性较高
- **数据不足**：没有更多信息便无法提出建议

置信度基于：
- 数据的完整性和时效性
- 多项指标之间的一致性
- 用例需求的明确程度
- 行业成熟度和标准
