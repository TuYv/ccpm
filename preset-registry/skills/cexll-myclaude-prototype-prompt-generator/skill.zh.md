# 原型提示词生成器

## 概述

生成全面、可用于生产环境的 UI/UX 原型创建提示词。将用户需求转化为详细的技术规格，其中包括设计系统、配色方案、组件规格、布局结构和实现指南。输出的提示词采用结构化形式，便于构建 HTML/CSS/React 原型的 AI 工具或人工开发者高效使用。

## 工作流程

### 第 1 步：收集需求

首先收集用户的关键信息。通过有针对性的问题了解以下内容：

**应用类型与用途：**
- 什么类型的应用？（例如，企业工具、电子商务、社交媒体、仪表板）
- 目标用户是谁？
- 主要使用场景和工作流程是什么？

**平台与使用环境：**
- 目标平台：iOS、Android、Web、微信小程序，还是跨平台？
- 设备：手机、平板电脑、桌面设备，还是响应式布局？
- 已知的视口尺寸（例如，iPhone 使用 375px，桌面设备使用 1200px）

**设计偏好：**
- 设计风格：企业微信、iOS 原生、Material Design、Ant Design Mobile，还是自定义风格？
- 品牌色或视觉偏好？
- 是否有任何设计参考或灵感来源？

**功能需求：**
- 所需的关键页面和功能
- 导航结构（标签页、抽屉式导航、堆栈导航）
- 要展示的数据（指标、列表、表单、媒体）
- 用户交互（点击、滑动、长按等）

**内容与数据：**
- 要展示的实际内容（真实可信的文本、数字、名称）
- 空状态、错误状态、加载状态
- 任何特定的业务逻辑或规则

**技术约束：**
- 框架偏好：原生 HTML、React、Vue，还是与框架无关？
- CSS 方案：Tailwind CSS、CSS Modules、styled-components？
- 图片资源：真实图片、占位图，还是特定来源？
- CDN 依赖项或版本要求？

**采用渐进式提问**（每次 2-3 个问题），避免让用户不知所措。许多细节可以根据上下文推断，或使用合理的默认值补充。

### 第 2 步：选择设计系统

根据收集到的需求，从 `references/design-systems.md` 中选择合适的设计系统：

**企业微信风格：**
- **适用场景**：中国企业应用、工作管理工具、B2B 平台、内部业务系统
- **特点**：简洁专业，以科技蓝为主色，信息层级清晰
- **主要受众**：中国企业用户、公司办公环境

**iOS 原生风格：**
- **适用场景**：iOS 专属应用、Apple 生态系统集成、面向 iPhone/iPad 用户的应用
- **特点**：极简主义、宽松的布局、San Francisco 字体、系统颜色
- **主要受众**：Apple 用户、消费者应用、以内容为中心的应用

**Material Design 风格：**
- **适用场景**：Android 优先的应用、Google 生态系统集成、采用 Material UI 的跨平台应用
- **特点**：醒目的图形、层级高度系统、涟漪效果、Roboto 字体
- **主要受众**：Android 用户、Google 服务用户、开发者工具用户

**Ant Design Mobile 风格：**
- **适用场景**：具有复杂数据录入和表单的企业级移动应用
- **特点**：注重效率、组件一致，适合业务应用
- **核心受众**：业务用户、企业级移动应用、数据密集型界面

**如果用户尚未指定设计系统**，请根据以下因素推荐：
- 地理位置：中国用户 → WeChat Work，西方用户 → iOS/Material
- 平台：iOS → iOS Native，Android → Material Design
- 应用类型：企业 B2B → WeChat Work 或 Ant Design，消费者应用 → iOS 或 Material

从 `references/design-systems.md` 加载完整的设计系统规范，以确保颜色代码、组件尺寸和交互模式准确无误。

### 第 3 步：构建提示词结构

使用 `references/prompt-structure.md` 中的模板，构建包含以下部分的完整提示词：

**1. 角色定义**
定义与原型相关的专业能力：
```
# Role
You are a world-class UI/UX engineer and frontend developer, specializing in [specific domain] using [technologies].
```

**2. 任务描述**
清晰说明要构建的内容和设计风格：
```
# Task
Create a [type] prototype for [application description].
Design style must strictly follow [design system], with core keywords: [3-5 key attributes].
```

**3. 技术栈规范**
列出所有技术、框架和资源：
- 文件结构（单个 HTML、多页面、基于组件）
- 框架和版本（例如 Tailwind CSS CDN）
- 设备模拟（视口尺寸、设备外框）
- 素材来源（Unsplash、Pexels、真实图片）
- 图标库（FontAwesome、Material Icons）
- 自定义配置（Tailwind 配置、主题变量）

**4. 视觉设计要求**
提供详细规范：

**(a) 调色板：**
包含所有颜色及其十六进制代码：
- 背景颜色（主背景、分区、卡片）
- 主色和强调色及其用途
- 状态颜色（成功、警告、错误）
- 文本颜色（标题、正文、次要、禁用）
- UI 元素颜色（边框、分隔线）

**(b) UI 风格特征：**
为每种组件类型指定：
- 卡片：背景、圆角、阴影、边框、内边距
- 按钮：变体（主要、次要、幽灵）、尺寸、状态
- 图标：风格、尺寸、颜色、容器
- 列表项：布局、高度、分隔线样式、激活状态
- 阴影：类型和用途

**(c) 布局结构：**
描述每个主要区域：
- 顶部导航栏：高度、标题样式、图标、背景
- 内容区域：网格、卡片、列表、间距
- 快捷访问区域：图标网格、布局
- 数据展示卡片：指标、布局、样式
- 功能列表：结构、图标、交互
- 底部标签栏：高度、标签页、激活/未激活状态、徽标

**(d) 具体页面内容：**
提供实际内容，而非占位符：
- 真实的页面标题和分区标题
- 实际数据点（数字、名称、日期）
- 功能名称和说明
- 按钮标签和链接文本
- 包含真实内容的示例列表项

**5. 实现细节**
涵盖具体技术细节：
- 页面宽度与居中方式
- 布局系统（Flexbox、Grid 或两者结合）
- 导航的固定/粘性定位
- 间距尺度（外边距、内边距、间隙）
- 排版（字体系列、字号、字重）
- 交互状态（悬停、激活、聚焦、禁用）
- 图标来源与用法
- 边框与分隔线样式

**6. Tailwind 配置**
如果使用 Tailwind CSS，请提供自定义配置：
```javascript
tailwind.config = {
  theme: {
    extend: {
      colors: {
        'brand-primary': '#3478F6',
        // ... all custom colors
      }
    }
  }
}
```

**7. 内容结构与层级**
以树形结构直观展示页面结构：
```
Page Name
├─ Section 1
│  ├─ Element 1
│  └─ Element 2
├─ Section 2
│  ├─ Subsection A
│  │  ├─ Item 1
│  │  └─ Item 2
│  └─ Subsection B
└─ Section 3
```

**8. 特殊要求**
突出需要特别考虑的事项：
- 特定于设计系统的指南
- 主色的应用场景
- 交互细节（点击反馈、动画、手势）
- 无障碍要求（对比度、触控目标、ARIA）
- 性能注意事项（图像优化、延迟加载）

**9. 输出格式**
明确指定交付内容：
```
# Output Format

Please output complete [file type] code, ensuring:
1. [Requirement 1]
2. [Requirement 2]
...

The output should be production-ready and viewable at [viewport] on [device].
```

### 第 4 步：填充具体信息

将所有模板占位符替换为具体值：

**用精确规范替换模糊表述：**
- ❌ “使用蓝色” → ✅ “主色：#3478F6（科技蓝），链接：#576B95（链接蓝）”
- ❌ “让按钮采用圆角” → ✅ “圆角半径：4px（Tailwind：rounded）”
- ❌ “添加一些间距” → ✅ “卡片间距：12px，页面边距：16px”
- ❌ “显示用户信息” → ✅ “显示用户名（15px 粗体）、电子邮箱（13px 灰色）、头像（48px 圆形）”

**使用真实内容，而非占位符：**
- ❌ “Lorem ipsum dolor sit amet” → ✅ “客户总数：14，今日新增客户：1，今日营收：¥0.00”
- ❌ “[Company Name]” → ✅ “Acme Insurance Co.”
- ❌ “功能 1、功能 2、功能 3” → ✅ “客户联系、客户动态、客户分组”

**明确所有尺寸：**
- 组件高度（44px、50px、64px）
- 字号（13px、15px、16px、18px）
- 间距值（8px、12px、16px、24px）
- 图标尺寸（24px、32px、48px）
- 圆角半径（4px、8px、10px）

**定义所有状态：**
- 默认：基础颜色与样式
- 悬停：如适用（桌面端）
- 激活/按下：透明度或背景变化
- 禁用：灰显并降低透明度
- 选中：高亮颜色（通常为品牌主色）

**包含所有颜色：**
提及的每种颜色都必须带有十六进制色值。请参考 `references/design-systems.md` 中选定的设计系统，以使用准确的值。

### 第 5 步：质量保证

在提交最终提示词之前，请根据 `references/prompt-structure.md` 中的清单进行核验：

**完整性检查：**
- [ ] 明确定义角色及其相关专业能力
- [ ] 任务明确说明要构建的内容和设计风格
- [ ] 列出所有技术栈组件及其版本/CDN
- [ ] 提供完整的调色板，所有颜色均包含十六进制色值
- [ ] 明确所有 UI 组件的精确尺寸和样式
- [ ] 使用精确尺寸完整描述页面布局
- [ ] 提供真实、合理的内容（不使用“Lorem Ipsum”或“[Name]”等占位符）
- [ ] 实现细节涵盖所有技术要求
- [ ] 如果使用 Tailwind CSS，则包含 Tailwind 配置
- [ ] 以树形结构直观展示内容层级
- [ ] 记录特殊要求和交互方式
- [ ] 明确定义输出格式及所有交付内容

**清晰度检查：**
- [ ] 不存在歧义术语或模糊描述（例如，“一些内边距”“好看的颜色”）
- [ ] 所有尺寸均指定单位（px、rem、%、vh 等）
- [ ] 所有颜色均使用十六进制代码定义（例如，#3478F6，而不只是“蓝色”）
- [ ] 已描述组件状态（正常、悬停、激活、禁用、选中）
- [ ] 布局关系清晰（父子关系、间距、对齐、z-index）

**具体性检查：**
- [ ] 明确指定设计系统（WeChat Work、iOS Native、Material Design 等）
- [ ] 提供视口尺寸（例如，iPhone 的 375px × 812px）
- [ ] 定义字体排印层级（字号、字重、行高）
- [ ] 记录交互行为；如果包含动画，则注明时长
- [ ] 已考虑边缘情况（长文本溢出、空状态、加载、错误）

**真实性检查：**
- [ ] 使用真实内容示例，而非拉丁文占位文本
- [ ] 使用真实可信的数据点（符合实际的数字、姓名、日期、金额）
- [ ] 功能集实用（不过度设计，也不缺少必要细节）
- [ ] 复杂度与所述使用场景相匹配

**技术准确性检查：**
- [ ] Tailwind 类名有效（如果使用 Tailwind）
- [ ] CDN 链接及版本正确（例如，https://cdn.tailwindcss.com）
- [ ] 隐含正确的 HTML 结构（语义化元素、层级）
- [ ] 布局技术可行（能够正常工作的 Flexbox/Grid 模式）
- [ ] 考虑无障碍标记（触控目标 ≥44px、颜色对比度）

如果有任何检查未通过，请先完善提示词再继续。

### 第 6 步：展示并迭代

**向用户展示生成的提示词**，并附上简要说明：
- 选择了什么设计系统，以及选择原因
- 所做的关键设计决策
- 应用了哪些假设或默认设置
- 如何使用该提示词（复制并提供给其他 AI 工具或开发者）

**提供优化选项：**
- “你想调整任何颜色或间距吗？”
- “我们是否应该添加更多页面或功能？”
- “你想更改设计系统吗？”
- “是否有需要重点强调的特定交互或动画？”

**根据反馈进行迭代：**
如果用户请求更改：
1. 更新提示词中的相关部分
2. 保持所有部分的一致性
3. 根据质量检查清单重新验证
4. 展示更新后的提示词

**保存或导出：**
主动询问是否要将提示词保存到文件：
- 用于文档记录的 Markdown 文件
- 便于复制的文本文件
- 作为代码块提供，以便立即使用

## 最佳实践

**1. 默认采用高质量标准：**
即使用户提供的需求很少，也要生成全面的提示词。删除细节比后续补充细节更容易。应包括：
- 完整的调色板（至少 8-12 种颜色）
- 所有常见 UI 组件（按钮、卡片、列表、输入框）
- 多种组件状态（正常、激活、禁用）
- 响应式设计考量
- 无障碍基础要求（对比度、触控目标）

**2. 智能使用设计系统默认值：**
当用户需求模糊时：
- 始终如一地应用完整设计系统
- 使用设计系统中的标准组件尺寸
- 遵循既有模式（例如，WeChat Work 的 64px 列表项）
- 包含平台常见的交互模式

**3. 清晰优先于简短：**
相比简短、模糊的提示词，更长、更详细的提示词能够生成更好的原型。应包含：
- 使用准确的十六进制代码，而不是颜色名称
- 使用精确尺寸，而不是相对描述
- 使用具体的组件布局，而不是笼统描述
- 使用实际内容，而不是占位文本

**4. 优先考虑移动端：**
对于移动应用，始终要考虑：
- 安全区域（iOS 刘海、Android 手势条）
- 触控目标尺寸（最小 44px × 44px）
- 拇指可触达区域（底部导航优于顶部导航）
- 以竖屏方向为主（横屏为辅）
- 尽可能支持单手操作

**5. 平衡灵活性与明确性：**
- 明确说明核心设计元素（颜色、字体排印、关键组件）
- 在实现细节上保留灵活性（准确的动画时长、细微的间距调整）
- 清楚指定“必需项”，将“锦上添花项”标记为可选

**6. 考虑完整的用户旅程：**
应包含以下方面的规范：
- 入口点（启动画面、引导流程，如适用）
- 主要工作流（贯穿关键功能的理想路径）
- 边缘情况（空状态、错误状态、加载状态）
- 退出点（退出登录、返回导航、完成状态）

**7. 提供上下文，而不只是规范：**
解释设计决策背后的“原因”：
- “科技蓝（#3478F6）可在企业场景中传达可信赖感和专业感”
- “64px 的列表项高度便于在移动设备上使用拇指舒适地点按”
- “固定底部标签栏可快速访问主要功能”

**8. 验证技术可行性：**
在最终确定提示词之前：
- 确保 CSS/Tailwind 类能够实现所描述的设计
- 验证布局模式是否适用于指定的 grid/flexbox 方案
- 确认指定的视口能够容纳所有内容
- 检查 CDN 链接和版本是否正确且可用

**9. 使其可直接执行：**
提示词应支持立即实现：
- 包含所有必需的 CDN 链接和导入项
- 提供完整的 Tailwind 配置（不要使用“...根据需要添加更多内容”）
- 指定文件结构和组织方式
- 明确定义交付物（HTML 文件、React 组件等）

**10. 预判问题：**
在提示词中说明常见的不确定事项：
- 字体回退方案（例如，使用 "sans-serif" 系统字体栈）
- 图像尺寸和宽高比
- 图标用法（何时使用 FontAwesome、SVG 或 emoji）
- Z-index 层级关系（哪些内容位于上层）
- 溢出行为（滚动、截断、换行）

## 常见模式

### 模式 1：企业办公仪表板（企业微信风格）
**典型结构：**
- 顶部导航栏（44px，标题 + 搜索/菜单图标）
- 快捷入口网格（4 列图标网格）
- 数据摘要卡片（采用横向布局展示关键指标）
- 功能列表（图标 + 文本行，每行高度为 64px）
- 底部标签栏（5 个标签，高度为 50px）

**关键元素：**
- 主要操作和激活状态使用科技蓝（#3478F6）
- 浅灰色背景上的白色卡片，带有细微阴影
- 48px 图标，使用 rounded-lg 容器
- 使用向右箭头指示导航

### 模式 2：iOS 消费级应用（iOS 原生风格）
**典型结构：**
- 大标题导航栏（展开时高度为 96px）
- 基于卡片的内容分区
- 系统标准列表（最小行高为 44px）
- 使用 SF Symbols 图标的标签栏

**关键元素：**
- 交互元素使用系统蓝色（#007AFF）
- 充足的留白（20px 外边距，16px 内边距）
- 带左侧缩进的细微分隔线
- 导航采用半透明模糊效果

### 模式 3：Android 应用（Material Design 风格）
**典型结构：**
- 顶部应用栏（移动端为 56px，平板端为 64px）
- 使用 FAB（悬浮操作按钮）执行主要操作
- 具有层级阴影的卡片式内容
- 底部导航或导航抽屉

**关键元素：**
- 醒目的主色（#6200EE）搭配层级阴影
- 点击时的涟漪效果
- 16dp 网格系统
- Material 图标（24px）

### 模式 4：企业表单应用（Ant Design Mobile）
**典型结构：**
- 简洁的导航栏（45px）
- 包含分组输入项的表单区块
- 包含详细信息的列表视图
- 带主要按钮的固定底部操作栏

**关键元素：**
- 操作使用专业蓝色（#108EE9）
- 紧凑的信息布局
- 清晰的表单字段标签和验证
- 多步骤流程使用面包屑或步骤指示器

## 故障排查

**问题：用户需求过于模糊**
**解决方案：** 提出有针对性的问题，提供类似应用的示例，建议可供选择的设计系统，或创建默认提示词并支持后续迭代。

**问题：用户希望混合多种设计风格**
**解决方案：** 选择一个主要设计系统，以确保整体结构和一致性，然后将其他系统中的特定元素作为点缀功能融入其中。说明其中的权衡。

**问题：用户提出无法实现或相互冲突的需求**
**解决方案：** 找出冲突，解释其存在问题的原因（例如，“64px 图标无法放入 44px 导航栏中”），提出替代方案，并请求用户澄清。

**问题：一个提示词中包含过多功能**
**解决方案：** 首先聚焦主要页面/工作流，为其生成提示词，然后为其他功能分别创建提示词。确保各提示词之间的一致性。

**问题：用户缺乏技术知识**
**解决方案：** 避免使用术语，以通俗语言解释设计决策，使用视觉描述代替技术术语，并在提示词中加入有帮助的注释。

**问题：原型提示词未能产生良好结果**
**解决方案：** 根据质量检查清单进行审查，确保所有颜色都有十六进制代码，验证所有尺寸均已明确指定，添加更具体的内容示例，并检查是否存在歧义性表述。
