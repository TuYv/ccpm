# 前端视觉 QA

审计用户实际可见的界面。将构建成功、DOM 中存在元素以及未经检查的截图文件视为辅助信号，绝不能将其视为视觉证明。

默认采用**仅审计**模式。除非用户明确要求修复或更改 UI，否则不要编辑实现、添加测试、安装依赖项或更新快照。获得修复源代码的权限，并不代表获准重新构建、重启或部署任何目标。

## 范围与路由

仅在渲染产物已存在后使用此技能。选择能够覆盖请求的最小审计配置：

- **核心视觉** — 构图、排版、间距、换行、裁切、图像；
- **响应式** — 断点、重排、移动端替代方案、滚动归属；
- **状态与用户旅程** — 条件分支、过渡、恢复、路由；
- **浏览器输出** — 下载、分享、剪贴板、弹出窗口、文件对话框、打印、PDF；
- **原生外壳** — Electron 或混合式窗口框架、权限、拖拽区域、IPC UI；
- **页面契约** — 仪表盘/管理后台、落地页/演示文稿、设计系统产物、浏览器工具/游戏、地图/GIS 或评审工具；
- **参考一致性** — 与指定截图、产品或层级进行比较；
- **数据可视化** — 图表层级、令牌、语义和无障碍性。

仅当变更涉及多个界面范围，或用户请求广泛的发布审查时，才组合多个配置。不要为了审查本地换行问题，而强行执行无关的身份验证、地图、导出和原生外壳检查。

根据阶段使用相邻技能：

- 使用 ui-designer、frontend-design 或其他设计技能来推导或创建视觉方向。
- 使用此技能测试已渲染的结果。
- 使用 qa-expert 制定完整的测试策略、缺陷管理计划和发布指标。
- 仅当渲染后的视觉证据是更广泛 QA 门禁的一部分时，才同时使用此技能和 qa-expert。
- 此技能审计产物是否正确**渲染**，而不是其是否有效**传达信息**。即使某个页面通过了这里的每一项检查，其标签仍可能是含义不明的内部缩写，各部分之间的数字也可能相互矛盾。应将文案、术语和受众适配问题交由内容/写作规范类技能处理，绝不能将通过视觉检查报告为“首次阅读者能够理解”——这是另一个问题，应由读者而非渲染结果来回答。

## 必需结果

生成以下所有内容：

1. 一份范围契约，说明产物、参与者、任务、目标类型与规范目标标识、条件状态、视口、受影响的用户旅程、参考/SSOT 以及授权。
2. 验证状态：**已验证**、**部分验证**或**受阻**。
3. 与可见证据、影响、状态、视口和复现步骤相关联的发现。
4. 实际执行过的检查以及仍未验证内容的列表。
5. 当声称内容为最新或已部署时，提供单独的交付状态及其身份标识证据；当明确授权修改目标时，提供修改前/后的身份标识、针对同一目标/状态/视口的重新运行结果，以及回归防护措施。

绝不能因为某类证据最容易收集，就把用户的真实目标降格为该类证据所能证明的内容。

## 工作流程

对于非简单审计，请跟踪以下检查清单：

    - [ ] 1. 确立审计契约和授权
    - [ ] 2. 选择所需的证据级别和规范测试工具
    - [ ] 3. 证明目标、状态、数据、视口以及所声称的新鲜度
    - [ ] 4. 捕获并检查宏观、局部和响应式证据
    - [ ] 5. 执行受影响的用户旅程并检查接收方输出
    - [ ] 6. 报告发现；仅在获得授权时修复并重新运行

### 1. 确立审计契约

阅读项目说明、设计系统 SSOT、令牌、已批准的资源、启动器/测试 SOP，以及变更后的代码。然后编写一份可证伪的契约：

    制品/页面类型：
    参与者及其任务：
    目标类型 + 规范身份：
      Web = 确切的浏览器内 URL（包括查询参数/片段）+ 指定环境
      单个文件/图像 = 规范路径 + 内容哈希 + 渲染方案
      多资源制品 = 规范入口 + 依赖项/清单摘要 + 渲染器
      原生应用 = 已安装制品指纹 + 构建/版本 + 进程/窗口 + 渲染器路由
    条件状态：
    交付身份/状态，仅当声明了新鲜度/部署状态时：
    参考或设计系统 SSOT：
    相关视口/设备矩阵：
    预期投影/画布尺寸（如有）：
    受影响的交互和输出：
    审计配置：
    源代码授权：audit-only | fix-and-verify
    交互/操作权限：只读导航 | 对固件安全的状态更改 | <named actions>
    目标变更权限：无 | 隔离诊断 | 本地目标 | 部署到 <named environment>
    反目标 / 绝不能变成：
    通过条件：

在评判像素之前，先明确正确的状态。已退出登录、引导流程、空状态、权限被拒绝、已植入数据、已有数据、加载中以及功能标志分支，看起来可能像是不同的产品。错误分支的一张干净截图是无效的。当授权属于审计范围时，已登录但无角色是一条独立分支；已退出登录或拥有完整权限的证据不能替代它。

以参与者的任务作为成功目标。当用户需要判断严重程度、完成审查或从错误中恢复时，“图表存在”或“标签页可以切换”是不够的。

当通过条件指定了视觉参考——截图、另一个产品的页面或“让我们的产品看起来像他们的”——请在评判实现之前加载 [references/reference-parity-decomposition.md](references/reference-parity-decomposition.md)，**并且在 fix-and-verify 模式下，应在编写下一轮修复之前加载它**。这不会扩大该技能仅适用于实现后阶段的范围：分解是*审计*的第一个动作，应用于参考制品（它始终已经存在），而每一轮一致性修复都是在该技能的 fix-and-verify 权限内进行的实现工作。如果同一请求还需要从零创建视觉方向，这部分仍然属于设计技能——应将完成后的清单移交过去，而不是在那里重新推导。契约的第一项交付物是对参考进行测量后得到的结构清单，而一致性结论是针对该清单逐项关系得出的差异。每一轮都只修复用户最新截图所抱怨的差异，最终只能通过耗尽用户的耐心来收敛——该文件分解了一个真实的五轮案例。它还规制了两个即使完成清单后仍然存在的陷阱：你自己的几何断言对于一致性而言属于 D 级（它们编码的是你对参考的理解，即使理解错误也会一直保持通过），而用户对某种效果的否决（“绝不裁剪图像”）所否定的是迫使该效果出现的结构前提，而不是决定该效果具体形式的参数。对于与某个层级参考进行比较的报告级数据页面，该文件与 [references/data_viz_tier_and_token_audit.md](references/data_viz_tier_and_token_audit.md) 对工作进行划分：分解文件负责页面结构，层级基准负责数据呈现参数——两者都要加载。

### 2. 选择证据级别

采用声明所要求的最强证据级别：

| 级别 | 证据 | 可支持的声明 |
|---|---|---|
| A | 真实可见的 Chrome/浏览器或规范原生应用窗口，并实际完成用户操作流程 | 浏览器/操作系统界面、下载、剪贴板、弹窗拦截、文件选择器/对话框、打印预览、权限、原生外壳、与实际可见窗口有关的问题 |
| B | 相同状态下的浏览器 DevTools，或使用代表性数据运行的项目 E2E/Playwright 测试 | DOM 几何布局、路由、焦点、叠加层、交互状态、可重复的响应式行为 |
| C | 通过内置脚本全新执行的无头机械扫描 | 溢出、换行、图像、基本布局启发式检查、候选截图 |
| D | 源代码、lint、构建、单元测试或静态 DOM 推理 | 仅用于支持假设和回归验证 |

不要将较低级别的证据提升为更强的结论：

- 从未打开过的截图路径不具备任何视觉证据价值。
- 全新的无头空状态无法验证用户已有数据的状态。
- 渲染器 URL 无法验证 Electron/原生外壳。
- 调用处理程序无法验证 Chrome 打印预览、弹窗或下载界面。
- 指针光标、悬停样式或“点击以执行 X”的徽标无法证明点击
  确实会产生效果：没有可用处理程序的视觉提示只是无效点击，只有实际触发它
  （第 5 步）才能确认。
- 设备模拟只是一种近似；当特定于设备的行为非常重要时，请使用真实设备。

如果所需的 A 级界面不可用，或 GUI 正由另一个会话占用，
则只能继续收集不会佯装可替代它的证据。报告
确切缺失的证据，并将受影响的声明标记为 **部分完成** 或 **受阻**。

### 3. 证明目标、状态和视口

启动任何内容之前，先读取项目权威状态。仅当每项副作用都符合其各自的授权范围时，
才使用规范启动器：生命周期权限涵盖重新构建/重启/部署，而种子数据或事务性数据变更
则需要交互/操作权限。绝不要根据其中一种权限推断另一种权限。经过授权的
隔离诊断服务器应标记为非目标。

在浏览器内存中保留准确的 Web URL，但持久化时仅保存经过脱敏的结构化
URL，以及稳定的摘要/查询键列表。单个文件/图像使用路径、内容
哈希和渲染器；包含多个资源的 HTML/幻灯片需要权威资源
清单或依赖闭包摘要。原生 UI 需要已安装构件的
指纹/代码签名，以及构建、进程/窗口和渲染器路由。
渲染器开发 URL 仅用于诊断。将原始截图视为临时的本地
敏感证据；仅共享/提交最小化的脱敏衍生版本。

当声明涉及源代码变更、新鲜度或部署时，还应进一步
闭合从源代码到目标的链路：

1. 从目标的发布契约中获取预期标识，而不是使用本地 HEAD，
   除非该目标本就应该运行 HEAD；
2. 读取项目权威的运行时构建/镜像/发布状态；
3. 将浏览器/数据平面证据映射到该预期构件——仅有哈希文件名
   不能证明任何事情，除非预期清单中存在对应映射；
4. 证明预期的路由、参与者、数据、条件状态和视口。

如果没有身份映射，关于新鲜度/部署的声明就是**无法证明的**；当两者均未声明时，使用**不适用**。当前像素仍可独立验证。如果源修复与目标不同，其闭环状态仍为**部分完成 — 源已修复，验证目标已过时**。仅审计工作继续检查实时目标，不进行任何变更。仅拥有源修复权限并不代表可以对目标执行生命周期操作；如果另有明确授权允许修改目标，则在操作前记录身份，仅运行指定的规范生命周期，再次证明身份，并使用相同的目标/状态/视口重复验证。如果生命周期的归属尚未明确，则该变更路径处于**阻塞**状态。

优先使用禁用缓存的重新加载/全新上下文。仅当项目声明查询参数在语义上无影响时才更改查询参数，保留现有查询参数/片段，并在原始 URL 上生成最终证据。详细的页面状态探测、`file://` 边界、缓存规则、重定向和视口比较请参阅 [references/browser-driving-and-observation-traps.md](references/browser-driving-and-observation-traps.md) §2–§5。在诊断 CSS 之前记录最终 URL 和尺寸，完成后再恢复用户预期的视口。

对于脚本化全面检查，首先使用以下方式之一证明目标状态可复现：

- 项目的固件/storage-state/setup 路径；
- 通过重复使用 --require 标志指定的一个或多个必需渲染标记；
- 刷新后可恢复相同状态的直接深层链接。

否则，应将该次运行标记为**全新会话诊断**，而不是通过。

当审计必须登录 SPA、脚本化登录失败或跳回认证路由，或者目标运行在 shell 代理后的 localhost 上时，在提交任何登录/网络问题之前，请先加载 [references/auth-session-and-environment-traps.md](references/auth-session-and-environment-traps.md)——这些失败通常是驱动工具或环境伪装成了产品缺陷。

认证后，不要根据记忆中的侧边栏标签进行操作，也不要假定目标导航已经挂载。记录最终 URL、简短的可见正文摘录以及当前可用的链接/按钮；然后沿着渲染后的落地页实际提供的规范入口进行操作。如果预期的定位器不存在，在目标路由/状态得到独立证明之前，应优先诊断为导航契约或驱动工具发生漂移。

### 4. 捕获并检查渲染证据

在放大查看缺陷之前，先捕获整个可见构图，然后捕获受影响的组件、相关响应式宽度和页面下部区域。使用图像查看器打开每张截图并记录所见内容；未经检查的文件不能作为证据。

在信任捕获结果之前先对其进行校准。根据 DOM 几何信息证伪表面上的裁切问题，在支持的情况下固定设备缩放比例，等待字体/网络/动画完成，并使用接收者实际查看时所用的引擎。DOM 证据可以解释像素，但不能取代像素。

完整的捕获校准协议和最低检查集请参阅 [references/browser-driving-and-observation-traps.md](references/browser-driving-and-observation-traps.md) §12。无头捕获特有的范围和设备模拟陷阱也收录在同一参考文档的 §4–§5 中。

加载 [references/history-derived-checklist.md](references/history-derived-checklist.md)，
以获取核心视觉/响应式缺陷目录以及有标准依据的检查项。

有些缺陷不会在任何地方产生诊断信息：全局重置规则的优先级高于组件自身的样式；某个库重命名了其内部 DOM 类，导致整组规则无法匹配任何内容；声明了某个字体系列却从未提供对应字体；将几何参数写入主题配置，而源码扫描无法发现它；新的设计令牌复用了文件中已经使用过的名称；某个属性无法生效，因为规则从未设置该属性所依赖的布局模式；以及各个元素分别符合规范，但整体看起来仍然像是“没有设计系统”。源码审查、类型检查和几何断言在结构上无法发现这些问题——产物本身有效，只是什么作用都没有。当页面看起来很粗糙，但所有门禁检查都显示通过时，这种组合就是典型特征。加载
[references/silent-degradation-and-evidence.md](references/silent-degradation-and-evidence.md)
以了解各类问题的检测方法，并以机械方式探测其中两种收益最高的问题：

    node <skill-root>/scripts/silent_degradation_probe.mjs font \
      --url http://127.0.0.1:5173/ --weight 700 \
      --family "Brand Sans" --family "Fallback Sans"

    node <skill-root>/scripts/silent_degradation_probe.mjs class \
      --css path/to/bridge.css --library-css node_modules/<lib>/dist/<lib>.css

传入字体栈中的每个字体系列，以及页面实际使用的字重。准确解读全部五种判定结果；平台通用字体是正常的，只有 host-provided-only 和 broken asset 属于缺陷。参考文档解释了为何计算后的字体系列名称、`document.fonts.check()`、未加载的候选字体以及仅限 CJK 的宽度探测可能会导致错误结论。

从被审计的项目中运行捆绑的扫描工具，以便它能够解析项目现有的 Playwright 依赖：

    node <skill-root>/scripts/visual_layout_audit.mjs \
      --url 'http://127.0.0.1:5173/?state=fixture#/ready' \
      --page-type app \
      --require "Expected state marker" \
      --screenshot-sections

对于本地 HTML 产物，使用 --file <artifact.html>。运行
node <skill-root>/scripts/visual_layout_audit.mjs --help 查看所有标志。对于具有固定画布规格的内容，传入一个或多个精确视口；自定义视口会取代默认的响应式矩阵：

    node <skill-root>/scripts/visual_layout_audit.mjs \
      --file deck.html --page-type deck --viewport 1920x1080 \
      --screenshot-sections

对于证据依赖首屏以下封面或缩略图的长页面，添加 --scroll-visible-media。它会在捕获前访问已渲染的媒体行，以便启动懒加载，同时排除由 CSS 隐藏的响应式替代项。如果不使用该标志，屏幕外的懒加载媒体会被报告为延迟覆盖，而不是损坏的资源。无论采用哪种模式，都要检查屏幕截图：“not requested”、“still loading”和“request completed but undecodable”是不同的状态。

仅对项目特有的陈旧名称，或当前产品契约明确禁止的已渲染术语，重复使用 --forbid 模式。不要将通用的审美偏好编码为禁止使用的正则表达式。

脚本退出码如下：

- 0：没有剩余的机械性错误；
- 1：仍有错误，或使用 --fail-on-warning 时仍有警告；
- 2：输入无效、缺少前置条件，或运行时/设置失败。

脚本会将截图及其 JSON 报告写入唯一的临时运行目录；
显式指定的 --out 必须是新目录或空目录。这是一次 C 级扫描，并非
最终结论。绝不要提交/分享原始证据：报告会对渲染后的标签进行哈希处理，并
遮盖从目标中派生的值，而派生截图中可识别身份的
像素也需要遮盖。它的目标字符串指纹和单文件字节哈希无法
计算多资源闭包/原生身份；请提供项目契约。

不要仅仅为了运行扫描而修改被审计的项目。复用其包

### 5. 执行用户旅程并验证输出

**可见的示意元素并不能证明行为有效——触发每一个相关控件，
前提是其副作用符合明确的操作权限；确认响应，并将其余项标记为未验证。**
指针/悬停/按钮样式可能是虚假的可操作暗示：
处理程序可能不存在或已失效，而截图和看似合理的源代码仍都能通过。
只有真实的 A/B 级触发才能验证行为。优先检查后期添加的灯箱、
缩略图网格和复制操作。断言最终状态，而非事件是否已分发，并且
在判定为无响应点击之前，排除事件委托、水合时序或受信任手势门控
（browser-driving-and-observation-traps.md 陷阱 1）。正常行为周围缺少可见
提示，则是静默退化参考中的反向故障。

仅执行相关的状态转换矩阵：

    entry -> ready -> active -> processing -> success/error -> recovery -> ready

在适用时还应验证：

- 点击 -> URL/状态 -> 刷新 -> 深层链接 -> 后退/前进；
- 抽屉/模态框/弹出框的打开、焦点、背景交互、关闭以及移动端表现；
- 临时通知的生命周期，并在触发前启用观察；
- 高级模式 -> 当前模式和触发控件归属清晰可见 -> 一步返回默认模式；
- 提供商/模型/运行时状态 -> 已选配置和当前状态证据；
- 下载 -> 文件下载完成 -> 打开接收方制品；
- 分享 -> 复制/打开 URL -> 刷新后的接收方状态；
- 文件选择器/对话框 -> 可见的打开/取消/选择路径 -> 恢复后的应用状态；
- 打印/PDF -> 真实的 Chrome 预览 -> 页面非空白；
- Electron/原生应用 -> 规范的应用进程/窗口 -> 原生控件和 shell。

当审计涉及状态转换、授权、模式、提供商/模型/运行时真实性、路由、瞬态、
浮层、浏览器输出、原生外壳、落地页/演示文稿/浏览器工具/游戏产物、仪表板、
设计系统产物、GIS/地图或评审工具时，加载
[references/journey-and-page-contracts.md](references/journey-and-page-contracts.md)。

仅当涉及报告级数据页面、具名层级/参考比较、图表令牌审计或分类调色板时，
加载
[references/data_viz_tier_and_token_audit.md](references/data_viz_tier_and_token_audit.md)。

在报告非简单审计之前，以一个不了解调试器上下文的疲惫用户身份重新走一遍
主要路径。首先查找不明确的触发器或模式归属、隐藏的默认状态恢复、受阻的
恢复流程、误导性的运行时标签、原始机器语言、无法访问的控件、可避免的
手动操作，以及缺失的、原本可防止同一缺陷再次发生的防护机制。这是一次
证伪检查，而不是将局部的纯视觉审计扩展到所有配置的借口。

### 6. 报告、修复并重新运行

**每一项外观声明都必须附带能展示它的像素证据。** 看不到缺陷的读者无法
做出任何判断，也无法核实发现是否真实。裁剪到受影响的元素，只保留足以
定位它的周边上下文——整页截图无法证明 14px 的错位，而仅凭文字描述
（“这些按钮看起来很廉价”）无论多么准确都无法付诸行动。
`scripts/silent_degradation_probe.mjs shot` 正是用于裁剪单个元素及其
周边留白的。

以下四条规则决定证据在呈现给读者后是否仍然成立：比较必须**匹配缩放比例**
（将两个全宽区域并排放置会使其缩小，直至正在讨论的 3px 差异消失——应改为
以相同宽度将二者裁剪到同一组件）；尺寸必须以 **CSS px 而非 device px**
报告（DPR-2 截图的像素数是两倍，将其作为页面高度引用曾导致错误的
“长达 20 屏”结论）；修复前获取的截图应**标注其所对应的提交**，而不能当作
当前状态呈现；基于**代码计数**而非截图得出的发现应**明确标注这一点**，
以便读者了解列表中的哪些部分具有同等程度的证据支持。

将**影响**与**类别**分开。项目存在严重性分类体系时，应遵循该体系。
否则使用：

- **阻断**——虚假的成功状态、破坏性/误导性操作，或主要流程在没有安全
  变通方案的情况下无法完成；
- **严重**——核心任务、接收方输出、恢复流程、路由或关键控件不可用；
- **中等**——理解或操作受到实质性影响，但存在安全的变通方案；
- **轻微**——对任务影响很小的完善度缺陷。

使用布局、响应式、状态、路由、无障碍、浏览器输出、原生外壳、意图或审美
等类别。审美和意图不是严重性级别。

使用以下紧凑结构报告：

    Current-render status: verified | partial | blocked
    Delivery status: matched | mismatched | unprovable | not applicable
    Fix-closure status: verified | partial | blocked | not applicable
    Target: <web: redacted requested/final + target-string fingerprint/query keys/redirects | single-file/image: redacted canonical path + content hash + renderer | multi-resource: entry + authoritative manifest/dependency-closure digest + renderer | native: installed-artifact fingerprint/signature + build/version + process/window + renderer route>
    Environment: <verified name or unverified>
    Delivery identity: <expected; observed before -> after; evidence>
    Actor/job; reference/pass condition; affected journeys:
    Authorization: <source scope; interaction/action scope; target-mutation scope>
    Scope: <state, viewports, profiles>

发现：
    - 严重 · 浏览器输出 · PDF 操作 · 桌面端
      影响/状态/视口/复现步骤：
      证据工件/裁剪区域：
      证据：点击可见控件会打开 about:blank；打印预览中没有页面。
      修复：使用可确保由用户手势触发的打印路径，并重新测试接收方预览。

    参考一致性清单（仅限一致性审计）：
    - <关系 -> 已匹配 | 有意偏离（推导依据） | 尚未完成，每项一行>

    已验证：
    - <流程/状态/视口 + 具体证据>

    未验证：
    - <缺失的界面/证据及原因>

在**仅审计**模式下，继续以只读方式收集证据，但不得对源或目标进行任何
变更。在**修复并验证**模式下：

1. 修复根本原因，而不是隐藏溢出、缩小所有字体、更改选择器以规避检测器，
   或移除功能。
2. 在提交共享视觉令牌之前，先实时预览各个主观备选方案。
3. 仅在拥有单独且明确命名的变更权限时更新目标；否则应报告源已修复/目标未验证，
   不得扩大范围。
4. 重新运行同一个规范目标，并重新证明其身份、路由、状态、视口、流程和
   接收方输出。
5. 添加或更新能够捕获已确认故障类别的最小回归防护。

有三个习惯可以防止修复过程制造自身缺陷——每一种情况都曾真实发生过：

- **在缺陷仍然存在时拍摄“修复前”截图。** 重建后将无法再复现该缺陷，
  此时结案报告只能声称有所改进。修复后截图应复用完全相同的裁剪窗口，
  使前后对比仅存在一个变量的差异。
- **引入新的共享名称前先进行 Grep 搜索。** 如果令牌名称使用了文件中
  已经用过的词（`rail`、`bar`、`card`），它会根据定义顺序悄然覆盖其他定义
  或被其他定义覆盖，从而同时改变两个子系统（静默退化类别 1f）。
- **证明修复后的断言确实能够失败。** 重新引入缺陷，观察它以预期幅度
  变红，然后再移除缺陷。一个在整个缺陷存在期间始终保持绿色的断言，
  不会仅仅因为被重写就成为防护。

## 完成门槛

仅在满足以下条件时，才将**当前渲染状态**标记为已验证：

- 已证明规范目标的类型/身份、最终目标、数据和参与者状态；
- 声明新鲜度时，交付状态已确定为匹配、不匹配或无法证明，否则为不适用；
- 报告中引用的每张截图都已打开并检查；
- 已覆盖相关视口和页面下部区域；
- 已按照所需证据级别执行受影响的交互和输出；
- 不存在与本次通过结论相矛盾且尚未解决的阻断级/严重级发现；
- 已明确说明剩余限制。

仅在授权修复已针对同一规范目标/状态/视口重新检查后，才将**修复闭环状态**标记为已验证；否则使用部分完成或已阻断。

否则应报告为**部分完成**或**已阻断**。绝不要让用户执行现有代理工具
能够完成的检查。
