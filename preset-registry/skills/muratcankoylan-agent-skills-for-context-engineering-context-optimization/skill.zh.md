# 上下文优化技术

上下文优化通过策略性压缩、掩蔽、缓存和分区，扩展有限上下文窗口的有效容量。有效的优化无需使用更大的模型或更长的窗口，即可增加可用容量——但前提是以严谨的度量为基础来应用。以下技术按影响和风险排序。

## 何时启用

在以下情况下启用此技能：
- 上下文预算或 token 成本限制了任务复杂度
- 可以使用可检索的引用替代冗长的工具输出，从而实现观察结果掩蔽
- 需要提高前缀缓存或 KV 缓存的命中率
- 限定检索范围可以减少加载的无关上下文
- 上下文分区可以跨智能体扩展有效容量
- 需要为掩蔽、压缩或分区设置预算触发条件

不要对由其他技能负责的相邻工作启用此技能：
- 解释注意力或上下文窗口为何会以这种方式运行：`context-fundamentals`。
- 诊断当前存在的中间信息丢失、污染、干扰、混淆或冲突：`context-degradation`。
- 为长对话设计结构化的交接摘要：`context-compression`。
- 将大型输出、计划或日志存储为文件：`filesystem-context`。

## 核心概念

按照以下优先顺序应用四种主要策略：

1. **KV 缓存优化**——重新排列并稳定提示词结构，使推理引擎能够复用已缓存的键/值张量。当运行时支持前缀缓存时，这是成本最低的优化方式：质量风险低，并且可以立即节省成本、降低延迟。当存在稳定前缀时，应首先应用此策略。

2. **观察结果掩蔽**——当冗长的工具输出已经完成其用途后，用紧凑的引用替代它们。工具输出可能会在智能体轨迹中占据主导地位（claim-context-optimization-tool-output-dominance），因此掩蔽通常能带来最大的容量收益。如果后续需要，原始内容仍可检索。

3. **压缩**——当上下文利用率超过 70% 时，总结累积的上下文，然后使用该摘要重新初始化。这样可以在保留任务关键状态的同时提炼窗口内容。压缩是有损的——应在掩蔽已经移除低价值的大量内容后再应用。

4. **上下文分区**——当单个窗口无法容纳完整问题时，将工作拆分给具有隔离上下文的子智能体。每个子智能体都在专注于其子任务的干净上下文中运行。仅当预计上下文超过窗口限制的 60% 时才使用此策略，因为协调开销确实存在。

指导原则是：上下文质量比数量更重要。每项优化都应在减少噪声的同时保留信号。先度量再优化，然后度量优化效果。

## 详细主题

### 压缩策略

当上下文利用率超过 70% 时触发压缩：总结当前上下文，然后使用该摘要重新初始化。这样能够以高保真方式提炼窗口内容，使任务得以继续，同时将性能下降降至最低。优先压缩工具输出（它们消耗 80% 以上的 token），其次是较早的对话轮次，最后是检索到的文档。绝不要压缩系统提示词——它决定了模型行为，移除它会导致不可预测的性能下降。

根据消息类型保留不同的元素：

- **工具输出**：提取关键发现、指标、错误代码和结论。移除冗长的原始输出、堆栈跟踪（除非正在进行调试）以及样板式页眉。
- **对话轮次**：保留决策、承诺、用户偏好和上下文转变。移除无实质内容的填充语、寒暄，以及已得出并记录结论的探索性往返讨论。
- **检索到的文档**：保留与当前任务相关的主张、事实和数据点。移除仅服务于一次性推理的佐证和详细阐述。

目标是在质量下降不超过 5% 的前提下，将 token 数减少 50-70%。如果压缩幅度超过 70%，应审查摘要是否丢失了关键信息——过度压缩是最常见的失败模式。

### 观察结果遮蔽

应根据观察结果的新近程度和持续相关性有选择地进行遮蔽，而不是统一处理。应用以下规则：

- **绝不遮蔽**：对当前任务至关重要的观察结果、最近一轮中的观察结果、用于当前推理链的观察结果，以及仍在进行调试时的错误输出。
- **在 3 轮以上后遮蔽**：其要点已提取到对话流程中的冗长输出。将其替换为紧凑的引用：`[Obs:{ref_id} elided. Key: {summary}. Full content retrievable.]`
- **始终立即遮蔽**：重复输出、样板式页眉和页脚，以及先前已在对话中总结过的输出。

遮蔽应在质量影响低于 2% 的前提下，将被遮蔽的观察结果减少 60-80%。关键在于保持可检索性——将完整内容存储在外部，并在上下文中保留引用 ID，以便智能体在需要时请求原始内容。

### KV 缓存优化

通过组织提示词结构，使稳定内容位于前缀、动态内容位于末尾，从而最大化前缀缓存命中率。KV 缓存存储推理期间计算出的 Key 和 Value 张量；当连续请求共享完全相同的前缀时，会复用缓存的张量，从而同时节省成本并降低延迟。

在每个提示词中应用以下顺序：
1. 系统提示词（最稳定——在会话中从不变化）
2. 工具定义（在不同请求间保持稳定）
3. 经常复用的模板和少样本示例
4. 对话历史（持续增长，但与之前的轮次共享前缀）
5. 当前查询和动态内容（最不稳定——始终放在最后）

提示词设计应确保缓存稳定性：从系统提示词中移除时间戳、会话计数器和请求 ID。将动态元数据移至单独的用户消息或工具结果中，以免破坏前缀。即使前缀中只有一个空白字符发生变化，也会使该变化位置之后的整个缓存块失效。

对于稳定的工作负载，目标是达到 70% 以上的缓存命中率。在大规模应用中，这意味着可将缓存 token 的成本降低 50% 以上、延迟降低 40% 以上。

### 上下文分区

当单个上下文无法容纳完整问题而不触发激进压缩时，应将工作划分给多个子智能体。每个子智能体都在干净、聚焦的上下文中处理其子任务，然后将结构化结果返回给协调智能体。

当预计任务上下文超过窗口限制的 60% 时，规划任务分区。将任务拆分为相互独立的子任务，把每个子任务分配给一个子智能体，并汇总结果。在合并前验证所有分区均已完成，合并兼容的结果；如果汇总后的输出仍超出预算，则进行摘要压缩。

这种方法实现了关注点分离——详细的搜索上下文被隔离在各个子智能体中，而协调器则专注于综合整理。然而，协调本身会产生实际的词元成本：协调器提示词、结果汇总和错误处理都会消耗词元。只有在节省量超过这部分开销时才进行分区。

### 预算管理

在会话开始前，为各个上下文类别分配明确的词元预算：系统提示词、工具定义、检索到的文档、消息历史记录、工具输出，以及预留缓冲区（总量的 5-10%）。持续监控预算使用情况，并在任一类别超出其分配额度或总使用率超过 70% 时触发优化。

采用基于触发条件的优化，而不是周期性优化。监控以下信号：
- 词元使用率超过 80%——触发压缩
- 注意力退化指标（重复、遗漏指令）——触发遮蔽和压缩
- 质量评分低于基准线——在优化前审查上下文构成

## 实用指南

### 优化决策框架

根据上下文中的主要组成部分选择优化技术：

| 上下文构成 | 首选操作 | 次选操作 |
|---|---|---|
| 工具输出占主导（>50%） | 观察结果遮蔽 | 压缩剩余轮次 |
| 检索到的文档占主导 | 摘要 | 如果文档相互独立，则进行分区 |
| 消息历史记录占主导 | 选择性保留并压缩 | 针对新子任务进行分区 |
| 多个组成部分共同占比较高 | 先进行 KV 缓存优化，再进行层级遮蔽和压缩 |
| 接近限制且正在主动调试 | 仅遮蔽已解决问题的工具输出——保留错误详情 |

### 性能目标

跟踪以下指标，以验证优化效果：

- **压缩**：词元减少 50-70%，质量下降 <5%，压缩步骤本身带来的延迟开销 <10%
- **遮蔽**：被遮蔽的观察结果减少 60-80%，质量影响 <2%，延迟开销接近于零
- **缓存优化**：对于稳定工作负载，命中率达到 70% 以上，成本降低 50% 以上，延迟降低 40% 以上
- **分区**：计入协调器开销后仍实现词元净节省；通常需要 3 个以上子任务才能达到盈亏平衡点

根据测量结果迭代调整策略。如果某种优化技术无法显著改善目标指标，就将其移除——优化机制本身也会消耗词元并增加延迟。

## 示例

**示例 1：压缩触发条件**
```python
if context_tokens / context_limit > 0.8:
    context = compact_context(context)
```

**示例 2：观察结果遮蔽**
```python
if len(observation) > max_length:
    ref_id = store_observation(observation)
    return f"[Obs:{ref_id} elided. Key: {extract_key(observation)}]"
```

**示例 3：缓存友好的排序**
```python
# Stable content first
context = [system_prompt, tool_definitions]  # Cacheable
context += [reused_templates]  # Reusable
context += [unique_content]  # Unique
```

**示例 4：预算触发的优化策略**
```yaml
budgets:
  tool_outputs: 35%
  message_history: 30%
  retrieved_documents: 20%
  reserved_buffer: 15%
triggers:
  tool_outputs_over_budget: mask resolved observations
  total_context_over_70_percent: compact message history
  repeated_irrelevant_retrievals: tighten retrieval scope
```

## 指南

1. 先衡量再优化——了解当前状态
2. 先应用掩蔽，再进行压缩——先移除价值较低的大块内容，然后总结剩余内容
3. 使用一致的提示词进行设计，以确保缓存稳定性
4. 在上下文出现问题之前进行分区
5. 持续监控优化效果
6. 在节省令牌与保持质量之间取得平衡
7. 在生产规模下测试优化方案
8. 针对边缘情况实现优雅降级

## 注意事项

1. **空白字符会破坏 KV 缓存**：提示词前缀中即使只有一个空格或换行发生变化，也会使该位置之后的整个 KV 缓存块失效。将系统提示词固定为不可变字符串——不要在其中插入时间戳、版本号或会话 ID。在不同部署之间逐字节比较提示词模板的差异。

2. **系统提示词中的时间戳会严重降低缓存命中率**：在系统提示词中包含 `Current date: {today}` 或类似的动态内容，会导致每天都发生一次完整的缓存未命中（如果使用具体时间，则每次请求都会发生）。将动态元数据移至用户消息中，或放入追加在稳定前缀之后的单独工具结果中。

3. **压力下的压缩会丢失关键状态**：当执行压缩的模型本身也承受上下文压力（利用率 >85%）时，其总结质量会下降——它会遗漏任务目标、丢弃用户约束，并抹平状态中的细微差别。应在 70-80% 时触发压缩，而不是等到 90% 以上。如果必须在较晚阶段进行压缩，请使用单独的模型调用，并提供仅包含待总结材料的干净上下文。

4. **掩蔽错误输出会破坏调试循环**：过度激进的掩蔽会隐藏错误消息、堆栈跟踪和失败详情，而智能体在后续轮次中需要这些信息来诊断并修复问题。在主动调试期间（最近 3 轮中出现错误），应暂停掩蔽所有与错误相关的观察结果，直至问题解决。

5. **分区开销可能超过节省量**：每个子智能体都需要自己的系统提示词、工具定义和协调消息。对于少于 3 个独立子任务的任务，协调开销通常会超过上下文节省量。在决定采用分区之前，应估算令牌总量（协调器 + 所有子智能体）。

6. **部署变更后，缓存未命中的成本会激增**：在不同部署之间重新排列工具、改写系统提示词或更改少样本示例，会使整个前缀缓存失效，从而导致成本暂时激增至原来的 2-5 倍，直到新缓存完成预热。应逐步推出提示词变更，并在部署窗口期间监控缓存命中率。

7. **压缩会让人对过时的摘要产生错误的信心**：上下文一旦被压缩，摘要看起来就具有权威性，但其中可能反映的是过时状态。如果任务在压缩后发生了变化（新的用户要求、修正后的假设），摘要就会悄无声息地继续沿用过时信息。压缩后，在继续执行之前，应根据当前任务目标重新验证摘要。

## 集成

此技能负责令牌效率策略和预算策略。相邻技能分别负责诊断、存储和架构：

- `context-fundamentals`：解释上下文质量和注意力位置为何重要的心智模型。
- `context-degradation`：在输出质量已经下降时进行诊断。
- `context-compression`：有损摘要和交接策略。
- `filesystem-context`：基于文件卸载完整输出和日志。
- `multi-agent-patterns`：将工作划分到相互隔离的智能体上下文中。
- `latent-briefing`：在兼容的运行时中，跨协调器与工作智能体边界选择性保留 KV。
- `evaluation`：衡量优化是否改善了质量、成本或延迟。
- `memory-systems`：在恰当时机向上下文提供信息的持久化检索层。
