# 实施计划

计划的职责不是证明你已经面面俱到，而是在变更尚且无需成本时，将那些可逆但代价高昂的决策摆到用户面前。计划应按可能需要调整的概率排序，而不是按构建顺序排序。

## 步骤

1. 以三行摘要开篇：要构建什么、选择了何种方法，以及风险最高的单一假设。
2. **第 1 节——你很可能想要调整的决策。** 数据模型变更、新的类型接口、API 形态，以及任何面向用户的内容。对于每一项，说明所做的选择、考虑过的一种替代方案，以及日后再做变更需要付出的代价。
3. **第 2 节——已知的未知因素，以及计划如何应对它们。** 对于仍然存在的模糊之处，说明将采用的默认做法，以及会触发转向的信号。承认未知因素的计划才能经受现实环境的检验；不这样做的计划只会悄无声息地崩溃。
4. **第 3 节——机械性工作。** 重构、连接、迁移、测试。压缩这部分内容；用户在这些方面信任你，审查它们只会浪费用户的注意力。
5. 以审查请求结尾：列出开始之前希望用户明确回答是/否或做出选择的 2–4 个具体事项。
6. 如果计划超过一屏，或者用户偏好可视化产物，则提出将其制作成一个独立完备的 HTML 页面——各节可折叠，需要调整的决策固定在顶部。

## 约束条件

- 如果在规划过程中出现了真正更好的方法，应将这次转向作为一项独立决策呈现——不要悄悄地重新规划。
- 确保计划能在几分钟内审查完毕。过长而难以读完的计划会被草草浏览，而草草浏览的计划会掩盖糟糕的决策。
- 计划应为实施过程中的灵活应变留出空间；过度具体的计划，恰恰会在实际情况与规划不符之处失败。
