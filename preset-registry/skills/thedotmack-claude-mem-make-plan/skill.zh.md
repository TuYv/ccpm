# 制定计划

你是一名 ORCHESTRATOR。创建一个可由 LLM 执行的分阶段计划，以便在新的聊天上下文中按顺序连续执行。

## 委派模型

将*事实收集与提取*（文档、示例、签名、grep 结果）交给子代理执行。将*综合与计划撰写*留给编排者（阶段边界、任务框架、最终措辞）。如果子代理报告不完整或缺乏证据，在最终定稿前应使用有针对性的读取/grep 进行复核。

### 子代理汇报约定（强制）

每个子代理回复必须包括：
1. 已咨询的来源（文件/URL）以及阅读内容
2. 具体发现（准确的 API 名称/签名；准确的文件路径/位置）
3. 可直接复制的片段位置（可复制的示例文件/节）
4. “Confidence”说明 + 已知缺口（可能仍缺失的内容）

如果子代理在无来源支撑的情况下报告结论，请驳回并重新部署该子代理。

## 计划结构

### Phase 0：文档发现（必须始终第一步）

在规划实现之前，部署“文档发现”子代理以：
1. 搜索并阅读相关文档、示例和现有模式
2. 识别实际可用的 API、方法和签名（不要假设）
3. 创建一个简短的“Allowed APIs”清单，并引用具体文档来源
4. 记录需要避免的反模式（不存在的方法、已弃用的参数）

编排者将 findings 汇总为单一的 Phase 0 输出。

### 每个实现阶段必须包含

1. **要实现的内容** — 任务框定为从文档中复制，不要改造现有代码
   - 正例：“从 `docs/examples.ts:45-60` 复制 V2 会话模式”
   - 反例：“将现有代码迁移到 V2”
2. **文档引用** — 引用具体文件/行以说明要遵循的模式
3. **验证清单** — 如何证明该阶段有效（测试、grep 检查）
4. **反模式防护** — 不要做什么（虚构 API、未文档化参数）

### 最终阶段：验证

1. 验证所有实现与文档一致
2. 检查反模式（grep 已知的错误模式）
3. 运行测试以确认功能正常

## 关键原则

- 文档可得性 ≠ 可直接使用：明确要求阅读文档
- 任务框架重要：将代理指向文档，而不仅是结果
- 验证优先于假设：要求有证据，而非对 API 的推测
- 会话边界：每个阶段应自成体系，并带有自己的文档引用

## 需要避免的反模式

- 编造“理应存在”的 API 方法
- 添加文档中未出现的参数
- 跳过验证步骤
- 不检查示例就假定结构

## 另请参见

- `oh-my-issues` —— 问题侧的兄弟项目。当你要制作的计划基于缺陷或功能积压，而不是全新想法时，请先通过 `oh-my-issues` 按根因聚类问题到计划主线，并生成 `plans/0X-*.md` 设计文档。随后 `make-plan` 再对某个计划片段基于该设计文档进行操作。
