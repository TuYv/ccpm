# 更新文档 — 文档维护

使项目文档与当前代码状态保持同步。根据需要更新核心 `docs/ai-context/` 文件和 `CLAUDE.md`。

## 核心文档原则

**积极压缩——每一行的默认处理方式都是删除。** 只有当一行内容记录了 AI 代理无法从代码、git log 或 spec.md 推导出的信息时，它才值得保留。每次运行都应在增加内容的同时尽可能多地删减内容。

**只记录当前的“是”状态——绝不引用旧实现或描述发生了什么变化。**

- 假设读者是第一次阅读文档
- 不使用“之前”“曾经是”“过去使用”或“改进了”等表述
- 文档本身不包含迁移说明或升级路径
- 如果某项内容已被移除，就从文档中删除，不要留下“已移除 X”的说明
- 不使用构建状态限定词（“最近添加”“刚刚合入”“本版本新增”）——工作交付后这些词就会失效；这些信息由 git log 记录

**受众是 AI 代理，而不是人类。** 这些文档用于让未来的会话快速建立上下文。不要营销性内容，不要叙事，不要“我们先做了 X，然后做了 Y”，不要友善的模糊表述。优先使用表格、**粗体行内标签**和伪代码，而不是散文。将代码标识符放在反引号中。每条不明显的规则都应配上一句短原因（安全性、历史事故、供应商特性）。

## 何时跳过

**标准是架构，而不是活动。** 只有当某项变更引入了**新架构**——即未来会话无法仅凭代码重建的数据流、契约、不变量或设计决策——本次运行才值得修改文档。将其以现在时态写入 `spec.md`。这才是唯一值得新增文档内容的情况——绝不要记录工作已经完成（git 会记录），也不要留下“我们修复/添加了 X”的说明。如果“记录这项变更”归根结底只是“记下我们做过这件事”，就什么都不要写。

以下情况不要运行此 skill：
- 不改变架构或能力的 bug 修复
- 不改变行为的小型重构（重命名、提取方法）
- UI 调整或样式变更
- 在现有模式内新增单个文件
- 不具有架构影响的性能优化
- 注释或格式变更

## 不要记录的内容

Claude Code 可以读取文件并使用 grep 搜索代码。只记录**无法从代码本身推断出的内容**：

| 不要记录 | 原因 | 应改为 |
|---------|------|--------|
| 标准语言约定 | Claude 已经了解这些约定 | 只记录项目特有的偏差 |
| 响应 JSON 示例 | Claude 可以读取实际源文件 | 只记录请求契约和错误代码 |
| 按文件逐一说明 | Claude 可以使用 Glob 和 Read | 只记录不明显的文件用途 |
| 已完成的检查项 | 已完成的内容存在于 git 历史中 | 从 progress.md 中删除 |
| ASCII 艺术图 | 行数多、价值低 | 使用紧凑的表格 |

**密度测试：** 添加内容前，先问：“Claude 能否通过阅读代码得出这一点？”如果可以，就不要记录。

## 流程

### 步骤 0（可选）：限定到一个模块

默认范围是**整个项目**——每个仓库对应一个项目。如果仓库将模块/组件拆分到不同的顶层路径下（每个路径都有自己的 `docs/ai-context/`），可以将范围缩小到本次会话修改的模块：`git status --short` 会显示哪些路径包含修改过的文件；只更新该模块的文档。如果项目只有一个 `docs/ai-context/`——这是常见情况——则完全跳过此步骤。

### 第 1 步：分析发生了哪些变化

检查近期变更：

```bash
git diff --stat HEAD
git log --oneline -5
```

确定发生了哪些类别的变更：
- **新功能或新能力** → 更新 `spec.md`，必要时更新 `progress.md`
- **新文件或新目录** → 更新 `project-structure.md`
- **部署或基础设施变更** → 更新 `deployment-infrastructure.md`
- **里程碑完成或状态变更** → 更新 `progress.md`
- **新的架构决策或规则** → 更新 `CLAUDE.md`

### 第 2 步：更新相关文件

仅在变更具有实际意义时更新文件。4 个核心文件及其负责范围如下：

| 文件 | 负责内容 | 更新时机 |
|------|-------------|-------------|
| `docs/ai-context/spec.md` | 产品做什么——功能、API 契约、数据流 | 新功能、API 变更、行为变更 |
| `docs/ai-context/project-structure.md` | 文件树、技术栈、目录组织 | 新文件/目录、依赖变更、技术栈变更 |
| `docs/ai-context/progress.md` | 已完成事项、下一步工作、阻塞项 | 阶段完成、新工作开始、状态变更 |
| `docs/ai-context/deployment-infrastructure.md` | 托管、账户、密钥、CI/CD | 基础设施变更、新服务、新密钥 |
| `CLAUDE.md` | 项目规则、架构决策、编码规范 | 新规则、新决策、约束变更 |

### 第 3 步：遵循单一事实来源规则

在 ai-context + `CLAUDE.md` 文档集合中，**每条事实只陈述一次**。如果同一事实出现在多个文件中，只保留规范归属文件中的内容，并删除其余内容——不要留下任何面包屑式指针。通过信任规范归属文件来解决矛盾。

- **允许使用文件内部章节引用**——在同一个文件中，使用 `§3.7 → §3.2` 进行导航是可以的。
- **禁止使用跨文件面包屑引用。** `/update-docs` 和 `/prime` 会同时加载整个文档集合，因此从另一个文件写入 `See spec.md §X` 只是纯粹的额外负担。将事实移动到其归属文件中；不要留下指针。

示例：
- API 端点详情 → `spec.md`（而非 `CLAUDE.md`）
- 文件命名约定 → `CLAUDE.md`（而非 `project-structure.md`）
- 部署 URL → `deployment-infrastructure.md`（而非 `spec.md`）

**标题重命名风险：** 在单一事实来源文档中，章节编号指针承担着关键作用。如果 `/prime` 采用轻量加载方式（仅加载目录和开头的约束），则深层事实会通过 `CLAUDE.md → spec.md <section>` 指针访问。重命名 `## ` 标题意味着必须更新所有引用该标题的指针——否则指针会失效。

### 第 4 步：保持文档精简

只记录那些无法通过阅读代码推断出的非显性复杂性：
- 架构决策及其依据
- 非显性约束（例如“绝不能存储音频”）
- 跨越多个文件的横切关注点
- 外部服务配置

不要记录：
- 函数的作用（代码已经说明了这一点）
- 标准框架模式（框架文档已经涵盖）
- 显而易见的文件用途（例如，“utils.ts 包含工具函数”）

### 第 5 步：创建缺失文件

如果 `docs/ai-context/` 下的文件尚不存在，请根据代码库的当前状态创建它们。分析代码、技术栈和项目结构，为每个文件填充准确反映当前状态的文档。

## 特定文档规则

**progress.md：**
- 使用绝对日期，绝不使用相对日期（使用「2026 年 3 月」，而不是「上周」）
- 将事项标记为完成时，删除该事项（不要使用删除线）——修复记录已保存在 git 历史中
- 已完成阶段的摘要应保持为单个表格行（约 10 个字），不要写成段落
- 删除已完成 2 周以上的清单项
- 安全事项：修复后删除，仅保留未解决的问题

**spec.md：**
- 不要重复 CLAUDE.md 中的内容（架构原则、编码标准）
- 记录请求格式、错误码和关键行为——省略响应示例
- 通过路径引用共享实用工具文件，不要复述其内容
- 关键的／横切关注点的不变量应放在规范的**开头**章节。轻量预加载只会读取开头和目录，因此埋在文档中部的不变量在会话开始时不可见。合并已发布的功能时，应将所有新的横切关注点不变量提升至开头，以一行简洁说明加一个指向详细章节的 `→ §` 引用表示。

**CLAUDE.md：**
- 仅保留会改变 Claude 行为的规则——如果删除某一行不会使 Claude 采取不同的行动，就删除该行
- 它不是参考文档：不要包含测试结构表，也不要包含标准模式的命名约定表

## 文档生命周期——永久文档与非永久文档

- **发布即合并。** 功能发布后，将其功能文档中的当前架构以现在时合并到 `spec.md`，并停用该功能文档。绝不要将已发布的架构留在未来规划文档／功能文档中。
- **将横切关注点不变量提升至开头。** 贯穿整个项目的不变量应放在 `spec.md` 的开头，而不是埋在功能文档中。
- **永久性。** `spec.md` / `project-structure.md` / `CLAUDE.md` 是永久文档，绝不能通过具体文件链接引用非永久文档（例如 `open-issues/*`、功能文档）。只有 `progress.md`（路线图）可以这样做。例外：`project-structure.md` 可以将非永久文档列为文件树条目（文件名 + 一行用途说明），但不能深入引用其中的具体章节编号。

## 命名引用生命周期（可选约定）

如果你使用稳定 ID 标记反复出现的陷阱、易错点或未解决问题，请为每个标签制定过时检查规则，以便清除失效引用，避免其不断累积。具体方案由你决定——下面是一个使用未解决问题标签 `T-XX` 的示例；你可以采用、重命名或完全跳过它。

- **陷阱／易错点：** 对每个带标签的事项，grep 其引用的文件／符号。如果引用的所有文件／符号都已不存在，则该事项已经失效——将其删除。如果该事项对应的解决方案已经发布，请进行验证并将其删除。
- **关卡／清单：** 任何已勾选（`[x]`）的行 → 立即删除；完成记录保存在 git 中。
- **待处理跟进事项：** 如果引用的文件／符号已不存在，或者近期提交已解决该事项 → 删除。
- **库版本说明**（例如「X 需要 Y ≥ 0.31」）：如果当前锁定版本已经超过该阈值，请向用户指出，而不是静默删除——你可能无法确定上游是否确实已修复该问题。

无论使用哪种标记方案（如果有），每次调用时都要执行过期项清理。

## 膨胀检查

更新后，静默检查 `progress.md`：
- 每个已完成阶段的行：“What”列最多约 10 个词——如果更长，立即精简
- 不得与 spec.md 重复——如果 progress.md 重述架构细节，请将其删除并添加交叉引用
- 无效项目：删除已完成 2 周以上且不再具有持续相关性的清单项

**净行数审计护栏：**如果一次运行增加了 ≥10 行，却删除了 0 行，请暂停并重新考虑。几乎总有内容可以精简——只增不减的运行是一种危险信号。

然后，根据所做的更改，检查 CLAUDE.md 是否也需要更新。
