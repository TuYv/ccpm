# 发布版本

**目标：** 准备可复现的版本发布，并且只有在用户批准确切的标签和说明后才进行发布。

**执行契约：** 有序复选框构成完成定义。将每一项在内部跟踪为 `PENDING`、有具体证据的 `PROVEN`、有证据证明其条件不存在的 `CLEARED`，或存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个部分后都要重新核对各项。返回前，解决所有 `PENDING` 项，并且只统计 `PROVEN` 和 `CLEARED`；将技能的判定规则和批准规则应用于每个缺口。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且会产生重要影响的选择，或必须取得的外部批准询问用户。根据实际风险调整检查深度，但不得在未说明的情况下跳过检查。保留依赖关系和安全顺序；对于其他事项，选择适合各项义务的验证方法。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 发布边界和提交证据 | Git 历史、标签和差异 | Hosting API 提交比较 |
| 现有发布风格和状态 | 已认证的 GitHub CLI 或连接器 | 只读证据使用公共 GitHub API |
| 发布身份和版本范围 | 仓库策略、先前标签，以及存在时的规范版本文件 | 仅当发布身份仍不明确时停止 |
| 发布验证 | 仓库原生检查和干净检出 | 手动结构检查，但置信度降低 |
| 创建标签和 GitHub Release | Git 加上已认证的 GitHub release 能力 | `BLOCKED`；不要在文件中模拟发布状态 |
| 安装验证 | 针对文档所述分发源的隔离环境 | 不包含安装证明的干净源代码验证 |

通过 shell 发布时，使用临时说明文件，以免 Markdown、引号和代码块被重新解释。将凭据保存在主机凭据存储中，绝不回显凭据。

当仓库策略和之前的可比发布已经能够回答问题时，不要浏览通用的发布建议。仅针对当前 API 或 CLI 行为使用官方主机文档。

## 检查清单

### 确立范围和证据

- [ ] 确认用户明确请求了发布，并识别仓库、发布目标和预期受众。
- [ ] 在选择版本、标签格式、文件或发布顺序之前，阅读仓库发布规则。
- [ ] 验证已认证的 GitHub release 能力、仓库访问权限，以及创建发布的权限。
- [ ] 要求工作树干净，或明确排除无关更改。
- [ ] 获取标签和目标分支；确认本地 HEAD 与远程发布分支同步。
- [ ] 确定此发布线的上一个发布边界；对于首次发布，使用约定的初始历史边界，并明确标注。
- [ ] 检查从上一个发布边界到拟议发布提交之间的提交及完整提交正文。
- [ ] 阅读受影响的清单文件、权威文档、安装说明、已配置的目录，以及存在时面向用户的迁移说明。
- [ ] 将提交和源代码差异视为证据；现有发布说明只能作为次要上下文。

### 版本与范围

- [ ] 使用仓库声明的版本策略；未指定时，不要强行采用 CalVer、SemVer 或共享目录版本。
- [ ] 如果发布目标或标签存在歧义，停止并询问，不要自行杜撰约定。
- [ ] 在本地和远程检查建议的标签。对于恢复执行的已批准发布，继续前先验证其确切目标和现有发布状态；否则，将冲突视为阻塞项，绝不覆盖它。
- [ ] 仅在仓库说明确定的规范字段中准备版本变更；在提案获批前，保持变更在本地且可供审查。
- [ ] 仅更新纳入本次发布的软件包、插件或组件；不要为保持视觉一致性而提升无关清单的版本。
- [ ] 新的分发单元应保持其已批准的初始版本，除非本次发布明确要求推进其版本。
- [ ] 确保标签、发布标题和说明描述的是同一发布单元；仅要求该单元所含的已版本化清单与版本对齐。
- [ ] 在仓库要求的迁移说明位置，记录破坏性安装或行为变更。

### 发布说明

- [ ] 阅读最近的可比发布，并保留有用的既有风格，但不要复制过时的结构。
- [ ] 按用户收益而非文件列表或内部实现时间顺序对变更分组。
- [ ] 先说明本次发布为何重要，再陈述用户将获得的具体行为。
- [ ] 仅在根据当前权威文档和适用的分发元数据验证后，才包含精确的安装或更新命令。
- [ ] 为每项已确认的破坏性变更提供迁移步骤，并清楚区分旧行为与新行为。
- [ ] 直白说明已移除的行为；不要将移除伪装成简化。
- [ ] 通过经验证的账号标识致谢外部贡献者；若为单人工作，则省略贡献者部分。
- [ ] 链接到在发布提交中存在的规范文档和仓库路径。
- [ ] 排除无法复现的采用情况、性能、兼容性或数量相关声明。
- [ ] 区分测量事实、解释和未来意图。

### 验证与批准

- [ ] 运行所有仓库发布门禁，以及适用于现有产品、软件包、插件、技能或市场发布面的检查。
- [ ] 当存在多个主机目录且仓库策略要求保持一致时，确认它们仍然对齐；除非已批准迁移，否则保留每个稳定的分发标识符。
- [ ] 当安装发布面发生变化时，在批准前验证精确建议树的隔离快照，并标识其基线和补丁；提交后，验证发布提交包含该已验证的树。
- [ ] 记录命令、版本、退出代码和跳过的检查，但不得泄露密钥。
- [ ] 提供精确的版本变更、标签、标题、完整说明、验证证据和计划执行的命令。
- [ ] 在提交版本变更、打标签或发布前，等待用户对该精确提案的明确批准。
- [ ] 在版本变更、目标、标签、标题和说明与已批准内容完全一致时复用批准；在发布前如发布内容发生变更，则展示变更后的内容以重新获得批准。

### 发布

- [ ] 根据已批准的提案协调准备好的元数据和文档；应用所有尚未完成的已批准编辑，并排除无关更改。
- [ ] 确认必需的发布门禁覆盖最终批准的树；仅重新运行因最终编辑而失效的检查或尚未解决的失败检查。
- [ ] 使用授权的分支工作流提交并推送发布提交。
- [ ] 在创建标签前，确认必需的 CI 在发布提交上成功。
- [ ] 创建指向已验证提交的带注释标签或仓库标准标签，并在不使用强制推送的情况下推送。
- [ ] 从包含已批准说明的文件创建 GitHub Release，以保留 Markdown 和 shell 安全性。
- [ ] 通过托管服务 API 验证已发布的标签、目标提交、标题、正文和发布 URL。
- [ ] 当发布更改了安装界面时，从仓库记录的发布源或分发源测试文档化的安装或更新。
- [ ] 除非另行获得授权，否则不要发布 npm、PyPI、NuGet、容器或其他软件包。
- [ ] 不要将社区公告作为隐式副作用创建。

### 失败处理

- [ ] 在公开打标签前，诊断失败并在范围内修正有界的准备缺陷；仅当提案未发生变化时才重用审批。对尚未解决的前置条件停止操作并保留精确状态。
- [ ] 如果标签发布或发布创建返回不确定结果，在重试前检查远程标签和发布的身份。报告部分状态，并仅恢复缺失的已批准操作；绝不要创建重复内容或覆盖冲突内容。
- [ ] 未经明确批准，绝不要删除或移动已发布的标签。
- [ ] 绝不要覆盖现有发布，也不要使用强制操作来掩盖错误的发布提交。

## 判定

- `RELEASED` — 标签和 GitHub Release 指向已验证的提交，且远程检查通过。
- `READY` — 提案和证据已完整，但发布等待批准。
- `PARTIAL` — 外部可见的发布状态已存在，但验证或后续步骤失败。
- `BLOCKED` — 无法安全地继续发布。

## 自检

- [ ] **返回前进行协调。** 检查逐项证据、需求覆盖、矛盾、范围、判定和适用的清理工作。修正报告或已授权的制品。重用有效证据；不要自动重新扫描仓库或重新运行成功的命令。仅针对相关更改、失败或尚未解决的证据重复检查。披露剩余缺口。

## 输出约定

使用用户的语言按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。较小的结果可以每个字段占一行；省略空表格，不要复制链接的制品：

1. **结果：** Skill 特定的判定和有证据支持的结果。
2. **范围：** 已审查/更改的范围、排除项、基线和重要假设。
3. **证据：** 以下 Skill 特定的字段；区分事实、推断和未经验证的声明。链接制品；适当时使用表格。
4. **验证：** 检查/结果、不可用的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None` 或每个 `UNPROVEN` 项的原因、对结果的影响和确切的下一步操作；剩余风险和所需决策。

**技能专属证据：**发布范围、规范版本变更、标签/提交、标题、审批或发布前的完整拟议说明，或发布后的 URL、验证证据以及发布状态。对于 `PARTIAL`，列出每个对外可见的对象，以及在删除、移动或替换它之前所需的审批。
