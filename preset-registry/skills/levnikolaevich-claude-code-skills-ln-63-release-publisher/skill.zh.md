# 发布版本

**目标：** 准备一个可复现的版本发布，并且只有在用户批准确切的标签和说明后才进行发布。

**执行契约：** 将下面按顺序排列的复选框工作流视为此 skill 的完成定义。将每个复选框都标记为 `PENDING`，然后根据具体证据将其解决为 `PROVEN`，根据其条件触发器不存在的证据将其解决为 `CLEARED`，或标记为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不能作为证明。
返回前，解决每个 `PENDING`，只将 `PROVEN` 和 `CLEARED` 项计为已完成，根据此 skill 的判定、决策和批准规则处理每个 `UNPROVEN`，并在开头添加 **检查清单：X/Y 已完成**<br>**未完成：无 | 部分/项目 — 原因；对结果的影响；确切的后续操作**；列出所有 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选能力 | 备用方案 |
|---|---|---|
| 版本边界和提交证据 | Git 历史记录、标签和差异 | Hosting API 提交比较 |
| 现有版本风格和状态 | 已认证的 GitHub CLI 或连接器 | 只读证据使用公开 GitHub API |
| 版本身份和版本范围 | 仓库策略、之前的标签，以及在存在时使用规范版本文件 | 仅当版本身份仍然含糊不清时停止 |
| 版本验证 | 仓库原生检查和干净检出 | 使用手动结构检查，但置信度降低 |
| 标签和 GitHub Release 创建 | Git 加上已认证的 GitHub release 能力 | `BLOCKED`；不要在文件中模拟版本发布状态 |
| 安装验证 | 针对文档所述分发源的隔离环境 | 不包含安装证明的干净源码验证 |

通过 shell 发布时，使用临时说明文件，以免 Markdown、引号和代码块被重新解释。将凭据保存在主机凭据存储中，绝不要回显凭据。

当仓库策略和之前可比的版本已经能够回答问题时，不要浏览通用的版本发布建议。仅在需要了解当前 API 或 CLI 行为时使用官方主机文档。

## 检查清单

- [ ] 确认用户明确请求发布版本，并确定仓库、发布目标和预期受众。
- [ ] 在选择版本、标签格式、文件或发布顺序之前，阅读仓库的版本发布规则。
- [ ] 验证已认证的 GitHub release 能力、仓库访问权限，以及创建版本发布的权限。
- [ ] 要求工作区干净，或在版本准备之前明确排除无关更改。
- [ ] 获取标签和目标分支；确认本地 HEAD 与远程发布分支同步。
- [ ] 找到最新的相关标签和 GitHub Release，而不是假设最新标签属于此版本线。
- [ ] 检查从上一个版本边界到拟议版本提交之间的提交，以及完整的提交正文。
- [ ] 阅读受影响的清单文件、权威文档、安装说明、已配置的目录，以及存在时面向用户的迁移说明。
- [ ] 将提交和源码差异视为证据；仅将现有版本说明作为次要背景信息。

## 版本与范围

- [ ] 遵循仓库声明的版本策略；未指定时，不要强行采用 CalVer、SemVer 或共享目录版本。
- [ ] 如果发布目标或标签存在歧义，应停止并询问，而不是自行臆造约定。
- [ ] 确认拟议的标签在本地或远程尚不存在。
- [ ] 仅在仓库说明所确定的规范版本字段中修改版本。
- [ ] 仅更新包含在本次发布中的包、插件或组件；不要为了视觉一致性而提升无关清单的版本。
- [ ] 除非本次发布明确推进新分发单元的版本，否则保持其已批准的初始版本。
- [ ] 确保标签、发布标题和说明描述的是同一个发布单元；仅要求该单元中包含的版本化清单与版本对齐。
- [ ] 在仓库要求的迁移说明位置记录会导致安装或行为发生破坏性变化的修改。
- [ ] 当仓库策略规定发布说明和 README 已足够时，不要创建 `CHANGELOG.md`。

## 发布说明

- [ ] 阅读最近的可比发布，并在不照搬过时结构的前提下保留有用的既有风格。
- [ ] 按用户获得的结果对变更分组，而不是按文件列表或内部实现时间顺序分组。
- [ ] 先说明发布为何重要，再陈述用户实际获得的具体行为。
- [ ] 只有在根据当前权威文档和适用的分发元数据完成验证后，才加入准确的安装或更新命令。
- [ ] 对每项已确认的破坏性变更都包含迁移步骤，并清楚区分旧行为和新行为。
- [ ] 直白地说明已移除的行为；不要将移除伪装成简化。
- [ ] 使用经验证的账号名致谢外部贡献者；对于个人完成的工作，不要加入贡献者部分。
- [ ] 链接到在发布提交中确实存在的规范文档和仓库路径。
- [ ] 排除无法复现的采用情况、性能、兼容性或数量方面的声明。
- [ ] 区分已测量的事实、解读和未来意图。

## 验证与批准

- [ ] 运行仓库的每个发布门禁，以及针对现有表面的相关产品、包、插件、技能或市场检查。
- [ ] 当存在多个主机目录且仓库策略要求保持一致时，确认它们仍然对齐；除非已批准迁移，否则保留每个稳定的分发标识符。
- [ ] 当安装表面发生变化时，从确切拟议发布提交的干净检出进行验证。
- [ ] 记录命令、版本、退出代码和跳过的检查，但不要暴露机密信息。
- [ ] 提交确切的版本变更、标签、标题、完整说明、验证证据和计划执行的命令。
- [ ] 在提交版本变更、创建标签或发布之前，等待用户明确批准该确切提案。
- [ ] 将批准后提出的修改视为需要再次获得批准的新提案。

## 发布

- [ ] 仅应用已批准的元数据和文档变更。
- [ ] 在最终编辑后重新运行发布门禁。
- [ ] 使用获授权的分支工作流提交并推送发布提交。
- [ ] 在创建标签前，确认发布提交上的必要 CI 已成功。
- [ ] 创建指向已验证提交的附注标签或仓库标准标签，并以非强制方式推送。
- [ ] 从包含已批准说明的文件创建 GitHub Release，以保留 Markdown 和 shell 安全性。
- [ ] 通过托管服务 API 验证已发布的标签、目标提交、标题、正文和发布 URL。
- [ ] 当发布改变安装表面时，根据仓库记录的发布或分发来源测试文档化的安装或更新流程。
- [ ] 除非另行获得授权，否则不要发布 npm、PyPI、NuGet、容器或其他包。
- [ ] 不要将创建社区公告作为隐式副作用。

## 失败处理

- [ ] 如果在标签公开之前发生失败，请停止并保留证据；不要临时进行部分发布。
- [ ] 如果标签已公开但创建发布失败，请在采取纠正措施之前，报告确切的部分状态。
- [ ] 未经明确批准，绝不要删除或移动已发布的标签。
- [ ] 绝不要覆盖现有发布，也不要使用 force 来掩盖错误的发布提交。

## 结论

- `RELEASED` — 标签和 GitHub Release 均指向已验证的提交，且远程检查通过。
- `READY` — 提案和证据均已完整，但发布仍等待批准。
- `PARTIAL` — 已存在对外可见的发布状态，但验证或后续步骤失败。
- `BLOCKED` — 无法安全地继续发布。

## 输出约定

返回发布范围、版本变更、标签和提交、完整说明或发布 URL、验证证据、发布状态、结论以及剩余风险。

对于 `PARTIAL`，描述每个对外可见的对象，并在删除、移动或替换其中任何对象之前获得批准。
