# 发布版本

**目标：** 准备一个可复现的发布版本，并且仅在用户批准确切的标签和发布说明后才进行发布。

**执行约定：** 将下面按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，并且仅当相应操作和所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目仍视为未完成。
返回前，将此技能的判定、决策和批准规则应用于每个未完成项目，并在开头添加 **检查清单：已完成 X/Y 项**<br>**未完成：无 | 章节/项目 — 原因；对结果的影响；确切的下一步操作**；列出每个未完成项目。

## 工具选择

| 需求 | 首选能力 | 后备方案 |
|---|---|---|
| 发布边界和提交证据 | Git 历史记录、标签和差异 | 托管平台 API 提交比较 |
| 现有发布风格和状态 | 已认证的 GitHub CLI 或连接器 | 用于只读证据的公共 GitHub API |
| 发布标识和版本范围 | 仓库策略、先前标签，以及存在时的规范版本文件 | 仅当发布标识仍有歧义时停止 |
| 发布验证 | 仓库原生门禁和干净检出 | 置信度较低的手动结构检查 |
| 创建标签和 GitHub Release | Git 加上已认证的 GitHub 发布能力 | `BLOCKED`；不要通过文件模拟发布状态 |
| 安装验证 | 在隔离环境中针对文档所述的分发源进行验证 | 不含安装证明的干净源代码验证 |

通过 shell 发布时，使用临时发布说明文件，以免 Markdown、引号和代码块被重新解释。将凭据保存在主机凭据存储中，切勿将其回显。

当仓库策略和先前的同类发布已能回答问题时，不要浏览通用发布建议。仅使用官方托管平台文档来了解当前的 API 或 CLI 行为。

## 检查清单

- [ ] 确认用户已明确请求发布，并识别仓库、发布目标和预期受众。
- [ ] 在选择版本、标签格式、文件或发布顺序之前，阅读仓库发布规则。
- [ ] 验证已认证的 GitHub 发布能力、仓库访问权限以及创建发布版本的权限。
- [ ] 要求工作树干净，或在准备发布版本之前明确排除无关更改。
- [ ] 获取标签和目标分支；确认本地 HEAD 已与远程发布分支同步。
- [ ] 查找最新的相关标签和 GitHub Release，而不是假定最新标签属于此发布线。
- [ ] 检查从上一个发布边界到拟议发布提交之间的提交及完整提交正文。
- [ ] 阅读受影响的清单文件、权威文档、安装说明、已配置的目录，以及存在时面向用户的迁移说明。
- [ ] 将提交和源代码差异视为证据；仅将现有发布说明用作辅助背景信息。

## 版本和范围

- [ ] 使用仓库声明的版本控制策略；如果未指定，不要强行采用 CalVer、SemVer 或共享目录版本。
- [ ] 如果发布目标或标签存在歧义，请停止并询问，而不是自行编造约定。
- [ ] 确认拟议标签在本地或远程均不存在。
- [ ] 仅更改仓库说明中确定的规范版本字段。
- [ ] 仅更新此发布包含的软件包、插件或组件；不要为了视觉一致性而提升无关清单文件的版本。
- [ ] 除非此次发布明确推进其版本，否则将新的分发单元保持在已批准的初始版本。
- [ ] 确保标签、发布标题和发布说明描述的是同一个发布单元；仅要求该单元中包含的版本化清单文件与版本保持一致。
- [ ] 在仓库要求的迁移说明载体中记录会破坏兼容性的安装或行为变更。
- [ ] 如果仓库策略规定发布说明和 README 已足够，则不要创建 `CHANGELOG.md`。

## 发布说明

- [ ] 阅读近期最具可比性的发布说明，沿用其中有用的既有风格，但不要照搬过时的结构。
- [ ] 按用户收益对变更进行分组，而不是按文件列表或内部实现时间顺序分组。
- [ ] 首先说明此次发布为何重要，然后陈述用户将获得的具体行为。
- [ ] 只有在根据当前权威文档和适用的分发元数据进行验证后，才可包含准确的安装或更新命令。
- [ ] 为每项已确认的破坏性变更提供迁移步骤，并清楚区分旧行为与新行为。
- [ ] 明确说明已移除的行为；不要将移除粉饰成简化。
- [ ] 使用经验证的账号名称向外部贡献者致谢；如果仅由一人完成，则省略贡献者部分。
- [ ] 链接到在发布提交中确实存在的规范文档和仓库路径。
- [ ] 排除无法复现的有关采用情况、性能、兼容性或数量的声明。
- [ ] 区分实测事实、解释和未来意图。

## 验证与批准

- [ ] 运行仓库的每个发布门禁检查，以及针对现有产品、软件包、插件、技能或市场界面的相关检查。
- [ ] 如果存在多个宿主目录且仓库策略要求保持一致，请确认它们仍然对齐；除非迁移已获批准，否则保留所有稳定的分发标识符。
- [ ] 当安装界面发生变化时，从拟发布的确切提交的全新检出副本进行验证。
- [ ] 记录命令、版本、退出代码和跳过的检查，但不得泄露机密信息。
- [ ] 提供确切的版本变更、标签、标题、完整说明、验证证据和计划执行的命令。
- [ ] 在提交版本变更、创建标签或发布之前，等待用户对该确切方案给予明确批准。
- [ ] 将批准后要求的编辑视为需要再次批准的新方案。

## 发布

- [ ] 仅应用已获批准的元数据和文档变更。
- [ ] 在最终编辑后重新运行发布门禁检查。
- [ ] 使用获授权的分支工作流提交并推送发布提交。
- [ ] 在创建标签之前，确认发布提交上的必需 CI 已成功完成。
- [ ] 创建指向已验证提交的附注标签或符合仓库标准的标签，并在不强制推送的情况下推送该标签。
- [ ] 使用包含已批准说明的文件创建 GitHub Release，以保留 Markdown 格式并确保 shell 安全。
- [ ] 通过托管 API 验证已发布的标签、目标提交、标题、正文和发布 URL。
- [ ] 当此次发布变更了安装界面时，从仓库文档所述的发布源或分发源测试已记录的安装或更新流程。
- [ ] 除非另行获得授权，否则不要发布 npm、PyPI、NuGet、容器或其他软件包。
- [ ] 不要将创建社区公告作为隐含的附带操作。

## 失败处理

- [ ] 如果在标签公开之前发生失败，请停止操作并保留证据；不要临时拼凑出不完整的发布。
- [ ] 如果标签已公开但创建发布失败，请在采取纠正措施之前报告确切的不完整状态。
- [ ] 未经明确批准，绝不删除或移动已发布的标签。
- [ ] 绝不覆盖现有发布，也不得使用强制操作来掩盖有问题的发布提交。

## 结论

- `RELEASED` — 标签和 GitHub Release 指向已验证的提交，且远程检查通过。
- `READY` — 提案和证据均已完备，但发布仍在等待批准。
- `PARTIAL` — 已存在外部可见的发布状态，但验证或后续步骤失败。
- `BLOCKED` — 无法安全地继续发布。

## 输出约定

返回发布范围、版本变更、标签和提交、完整的发布说明或发布 URL、验证证据、发布状态、结论以及残余风险。

对于 `PARTIAL`，请描述每一个外部可见对象，并在删除、移动或替换其中任何对象之前获得批准。
