# tasteskill：反套路前端技能

> 适用于落地页、作品集和重新设计。不适用于仪表盘、数据表格或多步骤产品 UI。
> 以下每条规则都**取决于上下文**，没有任何规则会自动触发。先阅读需求简述，再只选用适合的规则。

---

## 0. 需求推断（做任何事之前，先读懂情境）

在接触代码或调整参数之前，**先推断用户真正想要什么**。大多数 LLM 的设计输出之所以糟糕，是因为模型没有读懂情境，就直接套用了默认审美。

### 0.A 首先阅读这些信号
1. **页面类型**——落地页（SaaS / 消费产品 / 代理机构 / 活动）、作品集（开发者 / 设计师 / 创意工作室）、重新设计（保留还是彻底改造）、编辑类页面 / 博客。
2. 用户使用的**氛围词**——“极简”“沉静”“Linear 风格”“Awwwards”“粗野主义”“高端消费品牌”“Apple 感”“活泼”“严肃 B2B”“编辑风”“代理机构感”“玻璃质感”“暗黑科技”。
3. **参考信号**——他们提供的 URL、粘贴的截图、提到的产品，以及与之竞争的品牌。
4. **受众**——B2B 采购评审团队、注重设计的消费者，还是快速浏览作品集的招聘人员。审美应由受众决定，而不是由你的品味决定。
5. **已有品牌资产**——logo、颜色、字体、摄影素材。对于重新设计项目，这些是起始素材，而不是可有可无的输入（参见第 11 节）。
6. **隐性约束**——无障碍优先的受众、公共部门、受监管行业、信任优先型商业、儿童产品。这些约束的优先级**高于**审美偏好。

### 0.B 生成前先输出一行“设计解读”
在编写任何代码之前，用一行说明：**“我将其理解为：面向\<受众>的\<页面类型>，采用\<氛围>语言，倾向于\<设计系统或审美类别>。”**

解读示例：
- *“我将其理解为：面向技术采购者的 B2B SaaS 落地页，采用 Linear 风格的极简语言，倾向于 Tailwind utilities + Geist + 克制的动效。”*
- *“我将其理解为：面向招聘经理的独立设计师作品集，采用编辑式 / 动态字体语言，倾向于 native CSS + scroll-driven animation + custom typography。”*
- *“我将其理解为：公共部门服务网站的重新设计，采用信任优先的语言，倾向于 GOV.UK Frontend 或 USWDS。”*

### 0.C 如果需求含糊，只问一个问题，不要猜测
只提出**一个**澄清问题——绝不要一次抛出多个问题——并且仅在设计解读确实可能出现分歧时提问。例如：*“它应该更接近 Linear 式的简洁，还是 Awwwards 式的实验性？”*

如果你能根据上下文有把握地推断，**不要提问**。直接声明设计解读并继续。

### 0.D 反默认套路原则
不要默认使用：AI 紫色渐变、置于深色网格背景上方的居中首屏、三个等宽功能卡片、到处滥用的通用玻璃拟态、无处不在的无限循环微动画、Inter + slate-900。这些都是 LLM 的默认套路。应根据设计解读，有意识地超越这些套路。

## 1. 三个旋钮（核心配置）

完成设计解读后，设置三个旋钮。下文中的每一项布局、动效和密度决策都由这些旋钮控制。

* **`DESIGN_VARIANCE: 8`** - 1 = 完美对称，10 = 艺术化混乱
* **`MOTION_INTENSITY: 6`** - 1 = 静态，10 = 电影感 / 物理效果
* **`VISUAL_DENSITY: 4`** - 1 = 艺术画廊 / 疏朗，10 = 驾驶舱 / 数据密集

**基准值：** `8 / 6 / 4`。除非设计解读结果要求覆盖，否则使用这些值。不要要求用户编辑此文件——覆盖应通过对话完成。

### 1.A 参数推断（设计解读 → 参数值）
| 信号 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| “极简 / 简洁 / 平静 / 编辑风 / Linear 风格” | 5-6 | 3-4 | 2-3 |
| “高端消费级 / 苹果风 / 奢华 / 品牌感” | 7-8 | 5-7 | 3-4 |
| “有趣 / 狂野 / Dribbble / Awwwards / 实验性 / 代理机构风格” | 9-10 | 8-10 | 3-4 |
| “落地页 / 作品集 / 营销网站（默认）” | 7-9 | 6-8 | 3-5 |
| “信任优先 / 公共部门 / 强监管 / 无障碍至关重要” | 3-4 | 2-3 | 4-5 |
| “重新设计——保留现有风格” | 匹配现有值 | +1 | 匹配现有值 |
| “重新设计——全面改版” | +2 | +2 | 匹配现有值 |

### 1.B 使用场景预设
| 使用场景 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 落地页（SaaS，主流风格） | 7 | 6 | 4 |
| 落地页（代理机构 / 创意型） | 9 | 8 | 3 |
| 落地页（高端消费级） | 7 | 6 | 3 |
| 作品集（设计师 / 工作室） | 8 | 7 | 3 |
| 作品集（开发者） | 6 | 5 | 4 |
| 编辑内容 / 博客 | 6 | 4 | 3 |
| 公共部门服务 | 3 | 2 | 5 |
| 重新设计——保留现有风格 | 匹配 | 匹配值+1 | 匹配 |
| 重新设计——全面改版 | +2 | +2 | 匹配 |

### 1.C 参数如何驱动输出
将这些值（或用户覆盖后的值）用作全局变量。本文档中的交叉引用均指向这些确切的变量名——切勿杜撰 `LAYOUT_VARIANCE` 或 `ANIM_LEVEL` 之类别名。

## 2. 需求简报 → 设计系统映射

获得设计解读（第 0 节）和参数值（第 1 节）后，选择合适的基础方案。对于已有官方软件包的内容，不要自行编写 CSS。不要把某种审美趋势冒充为官方系统。

### 2.A 何时采用真正的设计系统（使用官方软件包）
| 需求简报呈现为…… | 采用 | 原因 |
|---|---|---|
| Microsoft / 企业级 SaaS / 仪表板 | `@fluentui/react-components` 或 `@fluentui/web-components` | 官方 Fluent UI、Microsoft 令牌，已处理无障碍支持 |
| 类 Google UI、Material 风格产品 | `@material/web` + Material 3 令牌 | 官方方案，可通过 Material Theming 配置主题 |
| IBM 风格的 B2B / 企业分析 | `@carbon/react` + `@carbon/styles` | 官方 Carbon，成熟的数据密度模式 |
| Shopify 应用界面 | `polaris.js` Web Components / Polaris React | Shopify 管理界面的必需方案 |
| Atlassian / Jira 风格产品 | `@atlaskit/*` + `@atlaskit/tokens` | 官方 Atlassian 设计系统 |
| GitHub 风格的开发者工具 / 社区页面 | `@primer/css` 或 `@primer/react-brand` | 官方 Primer；营销场景使用 Brand 变体 |
| 英国公共部门服务 | `govuk-frontend` | 法律 / 监管层面的预期要求 |
| 美国公共部门 / 信任优先 | `uswds` | 同上 |
| 快速构建的本地企业 / 代理机构 MVP | Bootstrap 5.3 | 朴实、快速、有效 |
| 现代无障碍 React 基础方案 | `@radix-ui/themes` | 原语组件 + 精致主题 |
| 自主拥有组件的现代 SaaS | shadcn/ui（`npx shadcn@latest add ...`） | 代码归你所有，易于自定义；绝不要直接交付默认状态 |
| 基于 Tailwind 的现代 SaaS / AI 营销网站 | Tailwind v4 实用类 + `dark:` 变体 | 独立开发者和小型团队构建项目的默认选择 |

**诚实原则：**如果需求说明明显属于上述某个系统，请安装并使用其**官方**软件包。不要手动重新实现其 CSS。不要导入某个系统的令牌后，又覆盖其中 90% 的内容。

**每个项目只使用一个系统。**不要在同一个组件树中混用 Fluent React 和 Carbon。不要将 shadcn/ui 组件导入 Material 3 应用。

### 2.B 当需求说明指向的是一种美学风格，而非系统时
对于这些设计方向，**不存在唯一的官方软件包**。请使用原生 CSS + Tailwind + 一个仍在维护的组件库进行构建。在代码注释中如实说明哪些内容只是借鉴灵感，哪些属于官方材料。

| 美学风格 | 诚实的实现方式 |
|---|---|
| 玻璃拟态 / “磨砂玻璃” | 使用 `backdrop-filter`、分层边框和高光叠层。为 `prefers-reduced-transparency` 提供纯色填充的降级方案。 |
| Bento（Apple 风格的磁贴网格） | 使用包含不同单元格尺寸的 CSS Grid。没有任何单一库独占这种风格。 |
| 粗野主义 | 使用原生 CSS、等宽字体和原始边框。无需使用库。 |
| 编辑风 / 杂志风 | 使用衬线字体、非对称网格和充足的留白。无需使用库。 |
| 暗黑科技 / 黑客风 | 使用等宽字体、霓虹强调色和终端视觉元素。无需使用库。 |
| 极光 / 网格渐变 | 使用 SVG 或分层径向渐变。无需使用库。 |
| 动态排版 | 使用原生 CSS 动画、滚动驱动动画，并使用 GSAP 实现滚动劫持。无需使用库。 |
| **Apple Liquid Glass** | Apple 仅为 Apple 平台提供了相关文档。**不存在官方的 `liquid-glass.css`。**Web 实现都是使用 `backdrop-filter` + 分层边框 + 高光做出的近似效果。请明确标注为近似实现。 |

## 3. 默认架构与约定

除非设计判断选择了真实的设计系统（第 2.A 节），否则采用以下默认设置：

### 3.A 技术栈
* **框架：**React 或 Next.js。默认使用服务器组件（RSC）。
  * **RSC 安全性：**全局状态仅可在客户端组件中使用。在 Next.js 中，请将 provider 包装在一个包含 `"use client"` 的组件中。
  * **交互隔离：**任何使用 Motion、滚动监听器或指针物理效果的组件都必须是一个隔离的叶子组件，并在顶部添加 `'use client'`。服务器组件仅渲染静态布局。
* **样式：****Tailwind v4**（默认）。仅当现有项目有要求时才使用 Tailwind v3。
  * 对于 v4：不要在 `postcss.config.js` 中使用 `tailwindcss` 插件。请使用 `@tailwindcss/postcss` 或 Vite 插件。
* **动画：****Motion**（原名 Framer Motion 的库）。从 `motion/react` 导入（`import { motion } from "motion/react"`）。`framer-motion` 软件包仍可作为旧版别名使用——在新代码中优先使用 `motion/react`。
* **字体：**始终使用 `next/font`（Next.js），或通过 `@font-face` + `font-display: swap` 自托管。生产环境中绝不要通过 `<link>` 引入 Google Fonts。

### 3.B 状态
* 对于隔离的 UI，使用局部 `useState` / `useReducer`。
* 仅在需要避免深层 prop 逐级传递时使用全局状态——Zustand、Jotai 或 React context。
* **绝不要**使用 `useState` 跟踪由用户输入驱动的连续值（鼠标位置、滚动进度、指针物理效果、磁性悬停）。请使用 Motion 的 `useMotionValue` / `useTransform` / `useScroll`。`useState` 会在每次值发生变化时重新渲染 React 组件树，并会在移动端导致性能崩溃。

### 3.C 图标
* **允许使用的库（按优先级排序）：** `@phosphor-icons/react`、`hugeicons-react`、`@radix-ui/react-icons`、`@tabler/icons-react`。
* **不推荐：** `lucide-react`。仅当用户明确要求使用，或项目已依赖该库时才可接受。
* **绝不要手写 SVG 图标。** 如果缺少某个字形，请安装第二个库或使用基础图元组合实现——不要从头绘制图标路径。
* **每个项目只使用一个图标家族。** 不要在同一个组件树中混用 Phosphor 和 Lucide。
* **全局统一 `strokeWidth`**（例如 `1.5` 或 `2.0`）。

### 3.D Emoji 政策
默认不建议在代码、标记和可见文本中使用 Emoji。请改用图标库中的字形。**例外：** 仅当用户明确要求营造俏皮 / 聊天风格 / 原生社交媒体氛围时，才允许使用 Emoji——即便如此，也应有意图地克制使用。

### 3.E 响应式与布局机制
* 统一断点（`sm 640`、`md 768`、`lg 1024`、`xl 1280`、`2xl 1536`）。
* 使用 `max-w-[1400px] mx-auto` 或 `max-w-7xl` 约束页面布局。
* **视口稳定性：** 全高 Hero 区域绝不要使用 `h-screen`。始终使用 `min-h-[100dvh]`，以防止移动端出现布局跳动（iOS Safari 地址栏）。
* **使用 Grid，避免 Flex 数学计算：** 绝不要使用复杂的 flexbox 百分比计算（`w-[calc(33%-1rem)]`）。始终使用 CSS Grid（`grid grid-cols-1 md:grid-cols-3 gap-6`）。

### 3.F 依赖验证（强制）
在导入任何第三方库之前，检查 `package.json`。如果缺少该包，请先输出安装命令。**绝不要**假定某个库已经存在。

## 4. 设计工程指令（偏差纠正）

LLM 默认倾向于使用陈词滥调。应主动覆盖这些默认倾向。每条规则都有一条结合上下文的例外路径。

### 4.1 排版
* **展示文字 / 标题：** 默认为 `text-4xl md:text-6xl tracking-tighter leading-none`。
* **正文 / 段落：** 默认为 `text-base text-gray-600 leading-relaxed max-w-[65ch]`。
* **无衬线字体选择：**
  * **默认不推荐：** `Inter`。应优先选择 `Geist`、`Outfit`、`Cabinet Grotesk`、`Satoshi`，或符合品牌调性的衬线字体。
  * **例外：** 当用户明确要求中性 / 标准 / Linear 风格的观感，或者需求是面向公共部门 / 无障碍优先的网站时，可以使用 Inter。
* **应熟悉的搭配：** `Geist` + `Geist Mono`、`Satoshi` + `JetBrains Mono`、`Cabinet Grotesk` + `Inter Tight`、`GT America` + `IBM Plex Mono`。

* **衬线字体规范（默认情况下非常不推荐）：**
  * **非常不建议将衬线字体作为任何项目的默认字体。** “它感觉很有创意 / 高级 / 编辑感”并不是选用衬线字体的理由。智能体默认认为“创意需求 = 衬线字体”，这是生产评审中最常被检出的 AI 痕迹。
  * **仅当以下任一条件明确成立时，才可使用衬线字体：**
    - 品牌需求中明确指定了某款衬线字体，或者
    - 美学风格确实属于编辑 / 奢华 / 出版物 / 手稿 / 传承 / 复古类型，并且你能够阐明为什么这款特定的衬线字体适合这个特定品牌
  * 对于其他所有类型（创意机构、设计工作室、现代品牌、高端消费品牌、作品集、生活方式），**默认使用无衬线展示字体**（Geist Display、ABC Diatype、Söhne Breit、Cabinet Grotesk Display、Migra Sans、GT Walsheim、Inter Display、PP Neue Montreal）。无衬线展示字体并不“无聊”——它们成为默认选择的原因，与黑色在时尚界成为默认选择的原因相同。
  * **强调规则（相关）：** 当你想强调标题中的某个词时（例如富有动感的“and `spatial` design”式处理），请使用**同一字体的斜体或粗体**。不要仅仅为了增加视觉趣味，就在无衬线标题中随意插入一个衬线字体的词（反之亦然）。混用字体家族的强调方式很业余。使用同一字体家族中的斜体 / 粗体才是正确做法。
  * **明确禁止作为默认字体：** `Fraunces` 和 `Instrument_Serif`（LLM 最偏爱的两款展示衬线字体）。
  * **如果使用衬线字体有充分理由**（按照上述规则，这种情况很少见），请从以下字体池中轮换选择，不要在连续的项目中重复使用同一款衬线字体：PP Editorial New、GT Sectra Display、Cardinal Grotesque、Reckless Neue、Tiempos Headline、Recoleta、Cormorant Garamond、Playfair Display、EB Garamond、IvyPresto、Migra、Editorial Old、Saol Display、Söhne Breit Kursiv、Domaine Display、Canela、Schnyder、Tobias、NB Architekt、ITC Galliard。

* **斜体下伸部留白（强制）：** 当展示字体使用斜体，且单词中包含下伸字母（`y g j p q`）时，`leading-[1]` 或 `leading-none` 会裁切字母的下伸部。至少使用 `leading-[1.1]`，并在包裹元素上添加 `pb-1` 或 `mb-1` 作为预留空间。发布前检查展示型标题中的每一个斜体单词。

### 4.2 色彩校准
* 最多使用 1 种强调色。默认情况下饱和度低于 80%。
* **LILA 规则：** 默认不建议采用“AI 紫色 / 蓝色辉光”美学。不要自动为紫色按钮添加辉光，也不要使用随意的霓虹渐变。使用中性色作为基础色（Zinc / Slate / Stone），搭配高对比度的单一强调色（Emerald、Electric Blue、Deep Rose、Burnt Orange 等）。
* **例外：** 如果品牌或需求说明明确要求使用紫色 / 紫罗兰色 / 淡紫色，应大胆采用。但要有明确意图地执行：保持调色板一致、中性色协调、渐变克制。不要做成泛滥俗套的 AI 渐变。
* **每个项目使用一套调色板。** 不要在同一个项目中混用暖灰色和冷灰色。
* **色彩一致性锁定（强制）：** 一旦为页面选定强调色，就必须在整个页面中使用该颜色。采用暖灰色的网站不能到了第 7 个区块突然出现蓝色 CTA。以玫瑰色为强调色的网站不能在页脚中出现青绿色状态徽章。选定一种强调色并锁定，发布前检查每个组件。

* **高端消费品牌调色板禁令（强制，第二常见的 AI 痕迹）：**
  * 对于高端消费品牌需求（炊具、健康、手工艺品、奢侈品、传统工艺、DTC 家居用品等），LLM 默认倾向于使用**暖米色/奶油色 + 黄铜色/陶土色/牛血红/赭色 + 浓缩咖啡色/墨色深色文本**。具体而言，禁止默认使用以下十六进制色系作为背景色和强调色：
    - 背景色：`#f5f1ea`、`#f7f5f1`、`#fbf8f1`、`#efeae0`、`#ece6db`、`#faf7f1`、`#e8dfcb`（均属于“暖纸色 / 奶油色 / 粉笔色 / 骨白色”）
    - 强调色：`#b08947`、`#b6553a`、`#9a2436`、`#9c6e2a`、`#bc7c3a`、`#7d5621`（均属于“黄铜色 / 陶土色 / 牛血红 / 赭色”）
    - 文本色：`#1a1714`、`#1a1814`、`#1b1814`（均属于“浓缩咖啡色 / 暖调近黑色”）
  * 禁止将此调色板作为高端消费品牌需求的默认选择。你以往发布的每个高端消费品牌网站都在使用完全相同的调色板。品牌因此失去了辨识度。
  * **默认替代方案（轮换使用，不要重复）：**
    - **冷调奢华：** 银灰色 + 铬色 + 烟灰色（参考 Tesla、没有皮革元素的 Apple Watch Hermès）
    - **森林：** 深绿色 + 骨白色 + 琥珀色强调色（参考 Filson、Patagonia 高端系列）
    - **黑色与棕褐色：** 纯正的近黑色 + 暖棕褐色，形成鲜明对比，不使用米色
    - **钴蓝色 + 奶油色：** 高饱和度蓝色搭配单一中性色，不使用黄铜色
    - **赤陶色 + 板岩灰：** 暖锈色搭配冷灰色，不使用黄铜色
    - **橄榄绿 + 砖红色 + 纸张色：** 柔和的橄榄绿色搭配砖红色强调色
    - **纯单色 + 单一高饱和度亮色：** 米白色 + 近黑色 + 一种明亮的强调色（电光蓝、祖母绿、亮粉色等）
  * **调色板轮换规则：** 如果你上一个生成的高端消费品牌项目使用了米色+黄铜色色系，那么这一个项目必须使用其他色系。不得连续两次发布相同的暖调手工艺风格调色板。
  * **例外：** 仅当品牌需求说明明确指定这些颜色，或者品牌形象确实属于复古 / 手工艺 / 暖调工艺风格，并且你能够阐明为什么这一特定调色板适合这一特定品牌时，才可以使用米色+黄铜色+浓缩咖啡色调色板。禁止仅仅因为“这是一个炊具需求”就默认选择该调色板。

### 4.3 布局多样化
* **反居中偏向：** 当 `DESIGN_VARIANCE > 4` 时，避免使用居中的 Hero / H1 区块。强制采用“分屏”（50/50）、“内容左对齐 / 素材右对齐”、“非对称留白”或滚动固定结构。
* **例外：** 对于编辑类 / 宣言类 / 发布公告类需求，如果信息本身就是设计，则可以使用居中的 Hero。

### 4.4 材质感、阴影、卡片
* 仅当层级抬升能够表达真实的信息层级时才使用卡片。否则，请使用 `border-t`、`divide-y` 或负空间进行分组。
* 使用阴影时，应使其色调与背景色相一致。浅色背景上禁止使用纯黑色投影。
* 当 `VISUAL_DENSITY > 7` 时：禁止使用通用卡片容器。数据指标应在简洁的布局中获得充足的呼吸空间。
* **形状一致性锁定（强制）：** 为页面选择一套且仅一套圆角尺度，并始终坚持使用。选项包括：全部直角（圆角 0）、全部柔和圆角（圆角 12-16px）、全部胶囊形（交互元素使用全圆角）。仅当存在明确记录的规则时才允许混用体系（例如“按钮使用全胶囊形，卡片使用 16px，输入框使用 8px”），并且该规则必须在所有位置得到遵循。在方正布局中使用圆形按钮，或在胶囊按钮页面中使用方形卡片，都属于设计错误。

### 4.5 交互式 UI 状态
LLM 默认只实现“静态成功状态”。始终实现完整的状态周期：
* **加载状态：** 使用与最终布局形状一致的骨架加载器。避免使用通用的圆形加载指示器。
* **空状态：** 精心设计；说明如何填充内容。
* **错误状态：** 清晰明确，并采用行内形式（表单）或上下文形式（仅对瞬时错误使用 toast）。
* **触觉反馈：** 在 `:active` 状态下，使用 `-translate-y-[1px]` 或 `scale-[0.98]` 来模拟实体按压效果。
* **按钮对比度检查（强制，无障碍）：** 发布任何按钮之前，确认按钮文字相对于按钮背景清晰可读。白色按钮 + 白色文字、使用 `bg-white` 的 CTA 搭配 `text-white` 标签、透明按钮与页面背景之间没有边框 → 全部禁止。审核每个 CTA：对比度至少达到 WCAG AA 标准（正文为 4.5:1，18px+ 的大号文字为 3:1）。同一规则也适用于置于摄影背景上的幽灵按钮（使用底层背景、遮罩或描边）。
* **禁止 CTA 按钮文字换行（强制）：** 在桌面端，按钮文字必须保持在一行内。如果像“VIEW SELECTED WORK”这样的标签换成 2 行或 3 行，则该按钮已损坏。修复方式二选一：缩短标签（主要 CTA 最多 3 个单词，最好为 1-2 个），或加宽按钮（不要人为限制 CTA 的 `max-width`）。桌面端 CTA 换行会导致预检失败。
* **禁止重复的 CTA 意图（强制）：** 同一页面上存在两个意图相同的 CTA 会导致预检失败。相同意图的示例：“Get in touch”+“Contact us”+“Let's talk”+“Start a project”+“Start something”+“Reach out”均属于“联系”意图 → 选择一个标签，并在整个页面（导航、Hero、页脚）中统一使用。对于“Try free”+“Get started”+“Sign up free”（均属于“注册”意图）以及“View work”+“See selected work”+“Browse projects”（均属于“作品集”意图），同样适用此规则。每种意图只使用一个标签。
* **表单对比度检查（强制，无障碍）：** 表单输入框、占位文字、焦点环、辅助文字和错误文字相对于区块背景的对比度均须达到 WCAG AA 标准。近白色表单上的浅色占位文字、白色页面区块上的白色表单、对比度低于 4.5:1 的灰色表单标签 → 全部禁止。发布前审核每个表单。

### 4.6 数据与表单模式
* 标签位于输入框上方。辅助文本可选，但应存在于标记中。错误文本位于输入框下方。输入块统一使用 `gap-2`。
* 绝不能用占位符代替标签。

### 4.7 布局规范（硬性规则。违反其中任何一条都意味着交付的是有缺陷的作品）

* **首屏区必须完整呈现在初始视口内。** 桌面端标题最多 2 行，副文案最多 **20 个单词**且最多 3-4 行，无需滚动即可看到 CTA。如果文案太长：缩小字号或删减文案。如果你无法用 20 个单词的副文案描述清楚价值主张，说明价值主张本身不清晰，而不是规则过于严格。绝不能让首屏区溢出，迫使用户滚动后才能找到 CTA。
* **首屏区字号规范。** 字号和图片尺寸必须*一起*规划。如果首屏素材较大且标题超过 6 个单词，不要从 `text-7xl/text-8xl` 起步。对大多数首屏区而言，合理的默认范围是 `text-4xl md:text-5xl lg:text-6xl`；只有标题为 3-5 个单词时才使用 `text-6xl md:text-7xl`。首屏标题出现 4 行始终是字号错误，绝不是文案长度错误。
* **首屏区顶部内边距上限（强制）：** 桌面端首屏区顶部内边距最大为 `pt-24`（约 6rem）。超过此值会让首屏内容悬浮在视口中部，看起来像布局错误，而非有意留白。如果首屏区需要更多呼吸空间，应增大字号或素材尺寸，而不是顶部内边距。
* **首屏区堆叠规范（最多 4 个文本元素）。** 首屏区是一个聚焦时刻，不是功能列表。允许的文本元素总计最多 4 个：
  1. 眉题（小号大写标签）或品牌条，或二者皆无——只能选择零个或一个
  2. 标题（最多 2 行，见上文）
  3. 副文案（最多 20 个单词，最多 4 行）
  4. CTA（1 个主要 CTA + 最多 1 个次要 CTA）
  - **首屏区内禁止出现：** CTA 下方的小号标语（“支持 GitHub、GitLab 和自托管 Git”）、信任背书微型条（“深受……工程团队使用”）、定价预告（“个人免费，团队每位用户 10 美元”）、功能要点列表、社会认同头像行。所有这些内容都应移至首屏区正下方的独立区块。
  - 如果同一个首屏区中既有眉题，又有位于 CTA 下方的标语，请删除标语。如果既有品牌条又有标语，请删除标语。每个首屏区最多只能有一个小型文本元素。
* **“Used by”/“Trusted by”徽标墙应放在首屏区下方，绝不能放在其中。** 首屏区用于展示价值主张和主要 CTA。徽标墙应作为正下方的独立区块。不要把信任徽标硬塞进与首屏文案相同的 flex 行中。
* **桌面端导航必须呈现为单行。** 如果导航项在 `lg`（1024px）下无法容纳，应精简标签、移除次要项目或将其收进汉堡菜单。桌面端出现两行导航属于设计缺陷。
* **导航高度上限：桌面端最多 80px，默认 64-72px。** 不要使用占据视口 15% 空间的超大“代理公司风格”导航栏。
* **便当网格必须富有节奏，不能单向重复。** 不要堆叠 6 行左图右文布局。应改变构图：交替使用全宽功能行、非对称图块尺寸和纵向分隔。
* **便当单元格数量规则（强制）：** 便当网格的单元格数量必须与内容数量完全一致。3 个项目 → 3 个单元格（1+2 拆分、2+1 拆分或非对称三单元格）。5 个项目 → 5 个单元格（2+3、3+2、主单元格+4 个单元格等）。如果网格中间或末尾存在空单元格，说明规划有误。应重新设计网格结构；不要塞入空白图块。
* **禁止重复区块布局。** 一旦某个区块使用了一种布局类型（例如三列图片卡片、全宽引语、文字与图片拆分布局），该类型在页面中最多只能出现一次。“精选委托项目”的外观不能与“我们的服务”相同。一个包含 8 个区块的着陆页必须至少使用 4 种不同的布局类型。
* **之字形交替布局上限（强制）。** 先“左图 + 右文”，再“左文 + 右图”的之字形交替布局非常俗套。连续使用这种图片+文字拆分模式的区块最多 2 个。连续第 3 个图片+文字拆分区块会导致预检失败。应使用全宽区块、纵向堆叠区块、便当网格、跑马灯或其他布局类型来打破这种模式。
* **克制使用眉题（强制，这是生产测试中违反次数最多的规则）。** “眉题”是位于区块标题上方、采用大写字母和较宽字间距的小号标签（例如 `FOUR COLORWAYS`、`SELECTED WORK`、`THE HARDWARE`、`Git-native task management`）。典型 CSS 特征：`text-[11px] uppercase tracking-[0.18em]`、`font-mono text-[10.5px] uppercase tracking-[0.22em]`。每个由 AI 构建的网站都会在每个区块标题上方放置眉题，形成千篇一律的模板化节奏。硬性规则：
  - **每 3 个区块最多使用 1 个眉题。** 首屏区计为 1 个区块。因此，包含 9 个区块的页面最多只能使用 3 个眉题。
  - 如果区块 A 使用了眉题，接下来的 2 个区块就不能使用眉题。
  - **预检采用机械式检查：** 统计所有区块组件中 `uppercase tracking`（或标题上方类似的小型大写等宽标签）的实例数。如果数量 > ceil(sectionCount / 3)，则输出不合格。
  - **眉题的替代方案：** 直接将其删除。仅使用标题就足够了。如果需要对区块进行分类，区块在页面中的位置本身已经起到了分类作用；无需额外标签。
* **禁止拆分式区块标题（强制）。** 将“左侧大标题 + 右侧小号说明段落”用作区块标题的模式（左侧为 col-span-7/8，右侧为 col-span-4/5，并在右栏悬置一小段正文）**禁止作为默认方案**。区块应传达一个聚焦的信息。如果确实同时需要标题和说明段落，应将二者纵向堆叠（标题在上，正文在下，最大宽度为 65ch）。只有存在真正的构图理由时才使用拆分式标题模式（例如右栏承载视觉元素或交互元素，而非仅仅用于填充的文字）。
* **便当背景多样性（强制）。** 便当和功能网格区块不能由 6 张内部只有文字的白底白色卡片组成。任何多单元格网格中，至少 2-3 个单元格必须具有真正的视觉变化：真实图片、符合品牌调性的渐变（而非 AI 风格的紫色）、图案或带色调的背景。仅由排版构成的米白底米白色便当布局会显得像乏味的 AI 默认设计，即使页面其他部分表现良好也是如此。
* **必须为每个区块明确声明移动端折叠方式。** 对于每个多列布局，都应在同一组件中声明 `< 768px` 时的回退方案。不要假设“它自然会正常工作，Tailwind 会处理好”。

### 4.8 图像与视觉素材策略

落地页和作品集是**视觉产品**。只有文本、充斥着伪截图 div 的页面就是粗制滥造。

**视觉素材的优先顺序：**
1. **优先使用图像生成工具。** 如果环境中有任何图像生成工具（`generate_image`、MCP 图像工具、IDE 集成的生成工具、OpenAI 图像工具等），你就必须使用它为各个区块创建专属素材：首屏摄影图、产品图、纹理背景、氛围图。根据区块生成正确宽高比的图像。不要因为手写 CSS 感觉更快就跳过此步骤。
2. **其次使用真实的网络图片。** 如果没有可用的生成工具，请使用真实摄影图片来源。可接受的默认选择：
   * `https://picsum.photos/seed/{descriptive-seed}/{w}/{h}`，用于占位摄影图片（seed 应描述对应区块，例如 `marrow-cookware-kitchen`）
   * 简介中提供的实际图库或品牌 URL
   * 明确允许时，可使用开放许可来源（通过直链使用 Unsplash、Pexels）
3. **最后的选择：告知用户。** 如果两者都不可行，不要在页面中塞满手写 SVG 插图或基于 div 的“伪截图”。相反，应留下带有明确标签的占位区域（`<!-- TODO: hero product photo, 1600x1200 -->`），并在回复末尾说明：*“此页面的以下位置需要真实图片：\[位置列表\]。请生成或提供这些图片。”*

**即使是极简网站也需要真实图片。** 纯文本页面并不等于极简主义，而是未完成的作品。即使是 Linear 风格的编辑型网站，也至少需要 2-3 张真实图片（首屏图、一张产品/生活方式图片、一张辅助图片）。如果简介要求风格克制，就生成黑白极简摄影图片；不要仅仅因为风格强度较低就完全跳过图片。

**用于社会认同的真实公司徽标。** 当简介要求提供“受信赖者 / 使用者 / 客户”徽标墙时，不要默认使用纯文本字标（将 `<span>Acme Co</span>` 设置样式后横向排列）。应使用真实的 SVG 徽标：
* **来源：Simple Icons**（`https://cdn.simpleicons.org/{slug}/ffffff` 可用于任意颜色，或使用 `simple-icons` npm 包）。它涵盖了大多数知名品牌。
* **替代方案：devicon**，用于技术栈徽标（`@svgr/cli` 或 CDN）。
* **虚构品牌名称？那也要虚构一个 SVG 标志。** 生成一个符合页面风格的简单字母组合图形（圆圈内的单个字母、双字母连字、抽象字形），并以内联 `<svg>` 的形式呈现。为虚构品牌名称使用纯文本字标会显得很普通。
* **始终**确保徽标在浅色和深色模式下都能正常显示（深色背景使用白色、浅色背景使用黑色，或使用单色主题变量）。
* **仅限徽标规则（强制）：** 徽标墙 = 只有徽标，不包含其他任何内容。不要在每个徽标下方显示行业/类别标签（不要在 `Vercel` 下方加 `hosting`，不要在 `Stripe` 下方加 `payments`，也不要在 `Cloudflare` 下方加 `infra`）。徽标本身就是可信度的体现，标签并没有提供用户尚未知晓的信息。可选项：将品牌名称作为屏幕阅读器可用的替代文本，也可以添加指向品牌网站的链接。仅此而已。

**手写插图：**
* 来自图标库的 SVG 图标：可以使用（参见第 3.C 节）。
* 手写装饰性 SVG（自定义插图、徽标、标志）：**强烈不建议使用**，绝不能作为默认选择。仅在以下情况下可以接受：
  - 简介中明确要求这样做（“为我绘制一个 SVG 徽标”）
  - 它是单个简单的几何标志（正方形、圆形、使用展示字体的字标）
  - 你对输出质量有信心

**禁止使用基于 div 的伪截图。** 用 `<div>` 矩形手工搭建的产品预览、虚假任务列表、虚假仪表盘、虚假终端窗口，都是明显的破绽。如果需要展示产品：
* 如果有真实截图 URL，就使用它
* 通过图像工具生成一张
* 使用真实的组件预览（即页面内实际可用的迷你版 UI）
* 或完全跳过预览，改用编辑类摄影图片

**Hero 区需要真实的视觉内容。** 文本 + 渐变色块不算 Hero 区——那只是占位符。

### 4.9 内容密度

落地页依赖的是**第一印象**，而不是让用户通读全文。务必大刀阔斧地删减。

* **每个区块的默认内容结构：**简短标题（≤ 8 个词）+ 简短副段落（≤ 25 个词）+ 一个视觉素材或一个 CTA。任何额外内容都必须能由该区块的职责证明其必要性。
* **禁止堆砌数据的区块。** 在营销页面上放置 20 行的出版物表格、30 行的奖项列表或庞大的定价矩阵 = 布局错误。应使用：
  - 3-5 个最重要的亮点 +“查看完整列表”链接
  - 使用跑马灯 / 轮播来体现广度
  - 如果数据本身就是产品，则应完全放到另一个页面
* **长列表需要不同的 UI 组件，而不是更长的列表。** 默认使用带项目符号的 `<ul>` / `divide-y` 行是一种偷懒的选择。如果项目超过 5 个，请改用以下方式之一：
  - 按组划分的双栏布局
  - 每项包含图片 + 标签的卡片网格
  - 如果项目可以分类，则使用标签页 / 手风琴
  - 支持水平滚动吸附的胶囊项
  - 对于强调广度的列表（用户评价、Logo、能力），使用轮播
  - 对于“大量无需逐项关注的内容”，使用跑马灯
  一张包含 10 行且每行下方都有细分隔线的规格表，是最糟糕的默认方案。要么将这些行分成 2-3 组，仅使用少量分隔线；要么改成每项规格一张卡片的布局。
* **尤其是规格表（Marrow 炊具模式）。** 在每一行都使用 `border-b` 的长篇产品规格表，是 AI 处理炊具 / 五金 / 服装 / 手工艺品需求时的默认做法。禁止使用。具体替代方案：
  - **双栏卡片网格：**每项规格使用独立卡片，包含规格名称、规格值（使用大号展示数字）以及一行“为什么重要”的正文。桌面端使用双栏排列，移动端使用单栏排列。
  - **支持滚动吸附的水平胶囊项：**每项规格都是一个胶囊项，用户可以滑动浏览。
  - **分组区块：**将 10 项规格划分为 3 个逻辑组（例如“材料”“烹饪”“保修”），每组仅使用一条柔和的分隔线和一个组标题。
  - **重点项与其余项：**将 3-4 项核心规格可视化为大型展示卡片，其余规格折叠在“查看完整规格”展开项下。

* **文案自查（发布前强制执行）：**在宣布任何任务完成之前，重新阅读页面上的每一个可见字符串（标题、副标题、眉题、按钮标签、正文、说明文字、替代文本、页脚文本、错误消息）。标记符合以下任一情况的字符串：
  - **语法错误**（“对它的过去免费”“两个方案，但只有一个诚实”“把它摆到桌面上”在缺少上下文时）
  - **指代不清**（在没有前文铺垫的情况下使用“我们计划继续保持下去”）
  - **听起来像 AI 幻觉**（可爱但错误的文字游戏、逻辑不通的生硬隐喻、“优雅的虚无”式短语）
  - **读起来像 LLM 在故作深沉**（被动攻击式谦逊、虚假的工匠标签、刻意诗化的微型元叙事）
  重写所有被标记的字符串。如果不确定某个字符串是否合理，请用直白、实用的句子替换它。AI 生成的俏皮文案比平淡文案更糟糕。
* **伪精确数字会被标记。** `92%`、`4.1×`、`48k`、`5.8 mm`、`13.4 lb` 之类的数字必须符合以下任一情况：
  - 来自真实数据（需求说明、品牌指南、公开指标）——可以
  - 明确标记为模拟数据（`<!-- mock -->`、“示例”“样例数据”）——可以
  - 是 AI 为营造规格美感而编造的——禁止。不要伪造品牌从未宣称过的工程精度。
* **每个页面只使用一种文案语体。** 不要在同一个设计中混用技术型等宽文本（“47 个任务 · 0.6 次上下文切换/天”）、编辑式散文和营销短句，除非品牌调性明确要求这样做。

### 4.10 引语与推荐语

* 引语正文**最多 3 行**。绝不能是 6 行。如果原始引语更长 → 将其删减。落地页上的引语只是摘录，而不是完整评论。
* 对于非常小的字号（例如页脚风格的推荐语），行数上限可以略微放宽。核心原则是：“一眼即可看完。”
* **不要在引语文本中使用长破折号**作为设计性修饰（长停顿、动态长破折号、长破折号项目符号）。参见第 9.G 节，长破折号已被完全禁用。
* 署名：姓名 + 职位 +（可选）公司。绝不能只有姓名（“- Sarah”）。
* 引号：使用真正的排版引号（“ ”），或者完全不使用引号。不要使用 ASCII 直引号（" "）。

### 4.11 页面主题锁定（浅色/深色模式一致性）

页面只能有一种主题。各个区块不得反转主题。

* 如果页面采用深色模式，所有区块都必须采用深色模式。不要在深色区块之间夹入一个浅色模式的暖色纸张风格区块（反之亦然）。不能让用户在滚动到页面中途时感觉自己进入了另一个网站。
* 例外情况：如果需求简述明确要求使用“色块叙事”或“滚动时切换主题”的设计手法，并且这是经过深思熟虑的构图方式（一次完整的主题切换，并伴随明显的过渡，而不是随意交替），则每个页面允许使用一次。
* 默认行为：在页面层级选择浅色、深色或自动（`prefers-color-scheme`）模式并将其锁定。同一主题色系内的区块级背景色调变化是可以接受的（例如 `bg-zinc-950` 紧邻 `bg-zinc-900`）；但在一个以 `bg-zinc-950` 为主的页面中间突然切换为 `bg-amber-50`，则属于错误设计。
* 使用内置主题机制的设计系统时（Radix Themes、带有 `<Theme>` 的 shadcn/ui），只在 `layout.tsx` 或页面根节点设置一次主题。不要让各个区块自行覆盖主题。

## 5. 上下文感知式主动设计

这些是工具，而不是默认设置。仅在设计判断认为合适时使用。**它们都不会自动启用。**

* **液态玻璃/玻璃拟态：**适合高端消费产品、类似 Apple 的风格、奢侈品牌或媒体叠加层氛围。不适合仪表板、公共部门或“乏味的 B2B”产品。使用时，不要仅限于 `backdrop-blur`：添加 1px 内边框（`border-white/10`）和细微的内阴影（`shadow-[inset_0_1px_0_rgba(255,255,255,0.1)]`），以营造实体边缘的折射效果。在 `prefers-reduced-transparency` 下提供纯色填充的回退方案。
* **磁性微物理效果：**当 `MOTION_INTENSITY > 5`，并且需求简述呈现高端、有趣或创意代理公司风格时使用。必须仅通过 React 渲染周期之外的 Motion `useMotionValue` / `useTransform` 实现。绝不要使用 `useState`。参见第 3.B 节。
* **持续性微交互**（脉冲、打字机、漂浮、微光、轮播）：当 `MOTION_INTENSITY > 5`，并且该区块确实能从动效中受益时使用（例如状态指示器、实时信息流、AI 感体验）。**并非每张卡片都需要无限循环。**如果某个区块用于传递信息，就让它保持静止。应用弹簧物理参数（`type: "spring", stiffness: 100, damping: 20`），不要使用线性缓动。
* **“既然声明有动效，就要实际展示动效。”**如果 `MOTION_INTENSITY > 4`，页面就必须真正动起来：至少应包括主视觉区的入场过渡、关键区块的滚动揭示效果，以及 CTA 的悬停物理效果。一个声称 `MOTION_INTENSITY: 7` 却完全静止的页面是有问题的。反过来，如果无法在现有范围内交付正常工作的动效，就把数值调低到 3，并交付一个干净的静态页面。绝不要交付完成一半且存在故障的动效（被截断的 ScrollTriggers、跳动的入场效果、缺失的清理逻辑）。
* **动效必须有明确动机（强制要求）。**添加任何动画之前，先问：“这个动画传达了什么？”有效答案包括：层级关系（将注意力引导至正确内容）、叙事（按照符合故事脉络的顺序揭示内容）、反馈（确认用户操作）、状态转换（表明某些内容发生了变化）。无效答案是：“它看起来很酷。”仅仅因为 GSAP 可用就到处使用 GSAP，是业余做法。每个 ScrollTrigger、每个跑马灯、每个固定区块都需要有存在的理由。如果无法用一句话阐明理由，就移除该动画。
* **每个页面最多一个跑马灯（强制要求）。**横向滚动的文字跑马灯（“无休止滚动的徽标”“横向滚动的宣言”“动态文字条”）每个页面最多只能使用一次。同一页面使用两个或更多跑马灯，会显得像是偷懒填充内容。选择一个真正需要跑马灯来服务内容的区块；其他区块应采用不同布局。
* **GSAP 粘性堆叠模式（使用滚动堆叠时）。**“随滚动堆叠卡片”必须是真正的粘性堆叠，而不是依次揭示的列表。规范代码骨架见下方第 5.A 节。常见问题：触发器在滚动到一半时才触发，而不是在视口顶部固定。修复方法：使用 `start: "top top"`，而不是 `start: "top center"` 或 `"top 80%"`。
* **GSAP 横向平移模式（使用横向滚动劫持时）。**规范代码骨架见下方第 5.B 节。常见问题：动画在区块固定之前就开始，导致用户看到半张幻灯片。修复方法相同：使用 `start: "top top"`，固定外层容器，并让内层轨道随滚动同步播放。

### 5.A Sticky-Stack - 规范骨架

```tsx
"use client";
import { useRef, useEffect } from "react";
import { gsap } from "gsap";
import { ScrollTrigger } from "gsap/ScrollTrigger";
import { useReducedMotion } from "motion/react";

gsap.registerPlugin(ScrollTrigger);

export function StickyStack({ cards }: { cards: React.ReactNode[] }) {
  const ref = useRef<HTMLDivElement>(null);
  const reduce = useReducedMotion();

  useEffect(() => {
    if (reduce || !ref.current) return;
    const ctx = gsap.context(() => {
      const cardEls = gsap.utils.toArray<HTMLElement>(".stack-card");
      cardEls.forEach((card, i) => {
        if (i === cardEls.length - 1) return;
        ScrollTrigger.create({
          trigger: card,
          start: "top top",                              // pin at viewport top
          endTrigger: cardEls[cardEls.length - 1],
          end: "top top",
          pin: true,
          pinSpacing: false,
        });
        gsap.to(card, {
          scale: 0.92,
          opacity: 0.55,
          ease: "none",
          scrollTrigger: {
            trigger: cardEls[i + 1],
            start: "top bottom",
            end: "top top",
            scrub: true,
          },
        });
      });
    }, ref);
    return () => ctx.revert();
  }, [reduce]);

  return (
    <div ref={ref} className="relative">
      {cards.map((card, i) => (
        <div
          key={i}
          className="stack-card sticky top-0 min-h-[100dvh] flex items-center justify-center"
        >
          {card}
        </div>
      ))}
    </div>
  );
}
```

关键点：`start: "top top"`、`pin: true`，除最后一张卡片外，每张卡片都会被固定；缩放/透明度变换由下一张卡片的滚动触发器驱动（因此，下一张卡片进入时，前一张卡片会缩小）。

### 5.B Horizontal-Pan - 规范骨架

```tsx
"use client";
import { useRef, useEffect } from "react";
import { gsap } from "gsap";
import { ScrollTrigger } from "gsap/ScrollTrigger";
import { useReducedMotion } from "motion/react";

gsap.registerPlugin(ScrollTrigger);

export function HorizontalPan({ children }: { children: React.ReactNode }) {
  const wrap = useRef<HTMLDivElement>(null);
  const track = useRef<HTMLDivElement>(null);
  const reduce = useReducedMotion();

  useEffect(() => {
    if (reduce || !wrap.current || !track.current) return;
    const ctx = gsap.context(() => {
      const distance = track.current!.scrollWidth - window.innerWidth;
      gsap.to(track.current, {
        x: -distance,
        ease: "none",
        scrollTrigger: {
          trigger: wrap.current,
          start: "top top",                              // pin starts when section top hits viewport top
          end: () => `+=${distance}`,                    // scroll distance = track width minus viewport
          pin: true,
          scrub: 1,
          invalidateOnRefresh: true,
        },
      });
    }, wrap);
    return () => ctx.revert();
  }, [reduce]);

  return (
    <section ref={wrap} className="relative overflow-hidden">
      <div ref={track} className="flex h-[100dvh] items-center">
        {children}
      </div>
    </section>
  );
}
```

关键点：`start: "top top"`、`pin: true`、`end: "+=${distance}"`（滚动长度 = 所需的水平移动距离）、`scrub: 1`。外层容器被固定，用户垂直滚动时，内部轨道会水平滑动。

### 5.C 滚动触发的交错显现——标准骨架（更轻量的替代方案）

对于简单的“元素进入视口时出现”效果（无需固定），优先使用 Motion 的 `whileInView`，而非 GSAP——它更轻量，并且不需要 ScrollTrigger：

```tsx
"use client";
import { motion, useReducedMotion } from "motion/react";

export function RevealStagger({ items }: { items: string[] }) {
  const reduce = useReducedMotion();
  return (
    <ul className="grid gap-6">
      {items.map((item, i) => (
        <motion.li
          key={item}
          initial={reduce ? false : { opacity: 0, y: 24 }}
          whileInView={{ opacity: 1, y: 0 }}
          viewport={{ once: true, amount: 0.3 }}
          transition={{
            duration: 0.6,
            delay: i * 0.06,
            ease: [0.16, 1, 0.3, 1],
          }}
        >
          {item}
        </motion.li>
      ))}
    </ul>
  );
}
```

适用于：功能列表、用户评价网格、徽标墙，以及任何只需要“滚动进入时出现”效果的内容。将 GSAP 留给真正需要固定或滚动同步的场景。

### 5.D 禁止使用的动画模式

* 禁止使用 **`window.addEventListener("scroll", ...)`**。它会在每一帧滚动时运行，容易造成卡顿，并且无法批处理。请使用 Motion 的 `useScroll()`、GSAP 的 `ScrollTrigger`、IntersectionObserver 或 CSS `scroll-driven animations`（`animation-timeline: view()`）。
* **在 React 状态中使用 `window.scrollY` 自定义计算滚动进度。** 原因相同：每一帧都会触发重新渲染。
* **会修改 React 状态的 `requestAnimationFrame` 循环。** 请改用运动值（`useMotionValue` + `useTransform`）。
* **布局过渡：** 对于可见状态变化（列表重新排序、模态框展开、路由之间的共享元素），请使用 Motion 的 `layout` 和 `layoutId` 属性。不要“为了保险”而给静态内容添加 `layout` 属性——这会产生测量开销。
* **交错编排：** 对于顺序很重要的显现时刻，请使用 `staggerChildren`（Motion）或 CSS 级联（`animation-delay: calc(var(--index) * 100ms)`）。使用 `staggerChildren` 时，父元素（`variants`）和子元素必须位于同一个客户端组件树中。

## 6. 性能与可访问性防护准则

### 6.A 硬件加速
* 仅对 `transform` 和 `opacity` 进行动画处理。绝不要对 `top`、`left`、`width`、`height` 进行动画处理。
* 谨慎使用 `will-change: transform`——仅用于实际会执行动画的元素。

### 6.B 减少动态效果（强制要求）
* **任何 `MOTION_INTENSITY > 3` 的动态效果都必须遵循 `prefers-reduced-motion`。** 这一点不可妥协。
* 在 Motion 中：使用 `useReducedMotion()`，并降级为静态效果。
* 在 CSS 中：使用 `@media (prefers-reduced-motion: no-preference)` 限制动画，或者在 `@media (prefers-reduced-motion: reduce)` 下提供禁用动画的覆盖规则块。
* 无限循环、视差、滚动劫持和磁性物理效果在启用减少动态效果时，必须降级为静态或即时效果。

### 6.C 深色模式（任何面向用户的页面都必须支持）
* 从一开始就为**两种模式进行设计**。除非用户明确要求，否则绝不能只交付浅色模式或深色模式。
* 使用 Tailwind `dark:` 变体或 CSS 变量定义令牌。每个项目选择一种策略。
* **不要在此指定具体的深色模式颜色。** 由需求简报决定。两种模式都必须保持视觉层级、品牌识别度和 WCAG AA 对比度（正文采用 AAA）。
* 尊重 `prefers-color-scheme: dark`。除非品牌坚持使用某一种模式，否则默认跟随系统偏好。

### 6.D Core Web Vitals 目标
* **LCP** < 2.5s。首屏主图必须使用 `next/image priority` 或进行预加载。
* **INP** < 200ms。将繁重任务移出主线程。
* **CLS** < 0.1。为图片、字体和嵌入内容预留空间。
* 在宣布页面完成之前运行 Lighthouse。

### 6.E DOM 开销
* 粒子 / 噪点滤镜只能应用于固定定位且带有 `pointer-events-none` 的伪元素（例如 `fixed inset-0 z-[60] pointer-events-none`）。绝不能应用于滚动容器——持续的 GPU 重绘会严重破坏移动端 FPS。
* 注意包体积。Motion 并不小。Three.js 体积很大。任何不在首屏中的内容都应延迟加载。

### 6.F 克制使用 Z-Index
绝不能滥用任意的 `z-50` 或 `z-10`。仅将 z-index 用于系统性的层级上下文（吸顶导航栏、模态框、遮罩层、粒子效果）。在项目常量文件中记录 z-index 层级规范。

## 7. 调节参数定义（技术参考）

### DESIGN_VARIANCE（级别 1-10）
* **1-3（可预测）：** 对称 CSS Grid（12 列、相等的 fr 单位）、相等的内边距、居中对齐。
* **4-7（错位）：** 使用 `margin-top: -2rem` 制造重叠、采用不同的图片宽高比（4:3 与 16:9 并列）、在居中对齐的数据上方使用左对齐标题。
* **8-10（非对称）：** 瀑布流布局、使用分数单位的 CSS Grid（`grid-template-columns: 2fr 1fr 1fr`）、大面积留白区域（`padding-left: 20vw`）。
* **移动端覆盖规则：** 对于 4-10 级，在 `md:` 以上使用的非对称布局，必须在 `< 768px` 的视口中折叠为严格的单列布局（`w-full`、`px-4`、`py-8`）。

### MOTION_INTENSITY（级别 1-10）
* **1-3（静态）：** 不使用自动动画。仅使用 CSS `:hover` 和 `:active` 状态。无论如何，`prefers-reduced-motion` 都是默认模式。
* **4-7（流畅 CSS）：** `transition: all 0.3s cubic-bezier(0.16, 1, 0.3, 1)`。使用级联的 `animation-delay` 实现加载入场效果。重点使用 `transform` 和 `opacity`。
* **8-10（高级编排）：** 复杂的滚动触发显现、视差效果、滚动驱动动画（CSS `animation-timeline` 或 GSAP ScrollTrigger）。使用 Motion hooks。**绝不能使用 `window.addEventListener('scroll')`**——这是硬性禁令，而不是“最好不要”。允许使用的替代方案请参见第 5.D 节。

### VISUAL_DENSITY（级别 1-10）
* **1-3（艺术画廊）：** 大量留白。巨大的区块间距（`py-32` 到 `py-48`）。高端、简洁。
* **4-7（日常应用）：** 标准 Web 应用间距（`py-16` 到 `py-24`）。
* **8-10（驾驶舱）：** 紧凑的内边距。不使用卡片容器；使用 1px 线条分隔数据。强制要求：所有数字都使用 `font-mono`。

## 8. 深色模式协议

默认同时支持双模式。除非需求简述明确要求模拟印刷效果的编辑风格，否则绝不要假定仅支持浅色模式。

### 8.A 令牌策略（选择一种并坚持使用）
* **Tailwind `dark:` 变体**（工具类优先项目的默认选择）：每个颜色工具类都应搭配对应的深色变体（`bg-white dark:bg-zinc-950`、`text-gray-900 dark:text-gray-100`）。
* **CSS 变量**（适用于 shadcn/ui、Radix Themes 或支持主题化的组件库）：定义语义化令牌（`--surface`、`--surface-elevated`、`--text-primary`、`--accent`），并在 `[data-theme="dark"]` 或 `@media (prefers-color-scheme: dark)` 下切换值。

### 8.B 此处不要指定具体颜色
具体颜色由需求简述和品牌决定。本 Skill 仅强制执行以下要求：
* **对比度** - 正文文本最低满足 WCAG AA，主视觉文案以 AAA 为目标。
* **层级一致性** - 在浅色模式下有效的视觉层级，在深色模式下也必须有效。如果 CTA 在浅色模式下足够醒目，在深色模式下也必须如此。
* **品牌忠实度** - 主品牌色必须保持可识别。不要为了深色模式而降低品牌色的饱和度。
* **禁止使用纯 `#000000` 和纯 `#ffffff`** - 使用近黑色（zinc-950、接近黑色的暖灰色）和近白色。纯色值会破坏层次感。

### 8.C 默认模式
除非品牌方坚持另有要求，否则应遵循 `prefers-color-scheme`。如果任一模式会削弱关键的品牌表现力，则添加手动切换功能。

### 8.D 完成前在两种模式下测试
开发期间应分别以两种模式打开页面。不要发布只在一种模式下查看过的页面。

## 9. AI 痕迹（禁止模式）

除非需求简述明确要求，否则应避免以下特征。

### 9.A 视觉与 CSS
* 默认**禁止霓虹色 / 外发光**。使用内边框或带有轻微色调的阴影。
* **禁止纯黑色（`#000000`）。** 使用近黑色、zinc-950 或炭灰色。
* **禁止饱和度过高的强调色。** 降低饱和度，使其与中性色协调。
* **禁止在大标题中过度使用渐变文字**。
* **禁止自定义鼠标光标。** 这种做法已经过时，对无障碍和性能都不友好。

### 9.B 排版
* **避免默认使用 Inter。** 参见第 4.1 节。可以通过例外方式覆盖。
* **禁止只靠夸张尺寸吸引注意的超大 H1。** 应通过字重 + 颜色控制层级，而不是单纯依赖尺寸。
* **衬线字体限制：** 衬线字体适用于编辑、奢侈品或出版物风格，不适用于仪表盘。

### 9.C 布局与间距
* **避免数学意义上过于完美的**内边距和外边距。不要让浮动元素周围出现别扭的空隙。
* **禁止三列等宽功能卡片。** 通用的“横向排列三张完全相同的卡片”式功能区域不可使用。应改用双列之字形布局、非对称网格、滚动固定式布局或横向滚动方案。

### 9.D 内容与数据（“Jane Doe”效应）
* **禁止使用泛化姓名。** “John Doe”“Sarah Chan”“Jack Su” → 使用有创意、真实可信且符合当地语境的姓名。
* **禁止使用泛化头像。** 不要使用 SVG“鸡蛋”头像或 Lucide 用户图标 → 使用可信的照片占位图或具有明确设计风格的头像。
* **禁止使用虚假完美数字。** 避免 `99.99%`、`50%`、`1234567`。使用自然、不规则的数据（`47.2%`、`+1 (312) 847-1928`）。
* **禁止使用粗制滥造的初创公司品牌名。** “Acme”“Nexus”“SmartFlow”“Cloudly” → 创造符合语境、听起来真实且有质感的名称。
* **禁止使用空洞动词。** “提升”“无缝”“释放”“下一代”“颠覆” → 只使用具体动词。

### 9.E 外部资源与组件
* **禁止手工绘制 SVG 图标。** 使用 Phosphor / HugeIcons / Radix / Tabler。仅在明确要求时使用 Lucide。
* **默认情况下强烈不建议手工绘制装饰性 SVG**（参见第 4.8 节）。
* **禁止使用基于 div 的伪截图。** 绝不要用 `<div>` 矩形拼出虚假产品 UI 来模拟截图。请使用真实图片、生成的图片，或直接省略预览。
* **禁止使用失效的 Unsplash 链接。** 使用 `https://picsum.photos/seed/{descriptive-string}/{w}/{h}`、生成的照片占位图或实际素材。
* **shadcn/ui 自定义：** 允许，但绝不能保持默认状态。根据项目美学自定义圆角、颜色、阴影和字体排印。
* **生产就绪的整洁度：** 代码在视觉上应整洁、令人印象深刻，并经过细致打磨。

### 9.F 生产测试中的典型迹象（全面禁止）

这些模式源自真实的 LLM 生成落地页测试。它们是模型试图让页面“看起来经过设计”时默认采用的典型特征。除非需求明确要求使用，否则应将其视为严格禁用项。

**首屏主视觉与页面顶部**
* **禁止在首屏主视觉中使用版本标签。** `V0.6`、`v2.0`、`BETA`、`INVITE-ONLY PREVIEW`、`EARLY ACCESS`、`ALPHA`，禁止默认将其用作上方标签。仅当需求明确涉及产品发布或预览状态时才可使用。
* **禁止使用“品牌 · 编号 01”风格的次级上方标签。** 例如“Marrow · 编号 01 · 6 夸脱款”这类微型元信息行。直接省略。

**章节编号与微型标签**
* **禁止使用章节编号式上方标签。** `00 / INDEX`、`001 · Capabilities`、`002 · Featured commission`、`06 · how it works`、`05 · The honest table`，均禁止使用。上方标签应使用直白语言说明主题，而不是进行编号。
* **禁止在图片或便当盒式区块上使用 `01 / 4` 风格的分页标记。** 如果用户自己能数清楚，就不需要这种标签。
* **禁止使用 `Scroll · 001 Capabilities` 风格的滚动提示。** 简单的箭头或“滚动”就足够了，不要添加章节编号前缀。
* **禁止将“作品索引，2018 - 2026”风格的范围标签**用作上方标签。直接说明该章节的内容即可。

**分隔符与圆点**
* **中间点（`·`）必须限量使用。** 元信息条中每行最多使用 1 个。不要默认用它分隔所有内容（“foo · bar · baz · qux · quux”）。如果需要一套分隔方式，优先使用换行、细线或分栏。
* **禁止在每个列表、导航或徽章上添加装饰性的彩色状态点。** 默认禁止在“第四季度尚有一个名额”前、每个导航链接前或每个任务行前添加彩色圆点。仅当圆点表达真实的语义状态（例如服务器状态或可用性标记）且使用克制时才可接受。

**长破折号与字体排印装饰**
* **禁止将长破折号（`—`）用作设计元素，也禁止在其他任何位置使用。** 完整且不可协商的禁令参见下方第 9.G 节。标题、上方标签、胶囊标签、正文、引文、署名、说明文字、按钮文本和替代文本中均禁止使用长破折号字符。请使用普通连字符（`-`）。
* **禁止默认将使用 `<br>` 断行并设置斜体的标题作为一种“设计手法”。** 例如“长达三十\<br\>*年。*”这类拆分方式。标题首先应自然易读，只有在需求明确要求时才使用巧妙的形式。
* **禁止使用垂直旋转文本**（例如将“作品索引，2018 - 2026”旋转 90°）。这是代理商作品集的陈词滥调。仅当需求明确要求代理商 / Awwwards / 实验性风格，且这种方式确实服务于构图时才使用。
* **禁止将十字准线或细线网格用作装饰。** 仅仅为了让页面“看起来经过设计”而绘制的垂直线和水平线一律禁止。仅当这些线条用于组织实际内容时才可使用。

**虚假产品预览**
* **首屏主视觉中禁止使用基于 div 构建的虚假产品 UI**（用带样式的 div 构建虚假任务列表、虚假终端、虚假仪表盘）。这是排名第一的 LLM 设计破绽。请使用真实截图、生成的图像、真实组件预览，或者完全不使用。
* **虚假截图中禁止使用虚假版本页脚**（如 "v0.6.2-rc.1"、"last sync 4s ago · main"）。毫无作用，一眼就能看出是 AI 生成的。

**营销文案破绽**
* **禁止使用 "Quietly in use at" / "Quietly trusted by"** 作为社会认同标题。请使用自然的表达："Trusted by"、"Used at"、"Customers include"，或者如果徽标本身足以说明问题，就完全省略标题。
* **禁止在引言、博客或侧边栏区块中使用 "From the field" / "Field notes" / "Currently on the bench" / "On our desks" / "Loose plates" 这类诗意标签**。读起来像是刻意表演工匠气质。请使用直白的功能性标签（"Testimonials"、"Latest writing"、"Now working on"），或者省略标签。
* **正文中禁止使用 "We respect the French ones" 这类**故作谦逊的行业梗。既卖萌，又很有 AI 味。
* **禁止在页眉或页脚中使用天气／地点信息条**（如 "LIS 14:23 · 18°C"），除非需求明确与某个地点或跨时区分布的工作室有关。
* **眉题下方禁止使用微型元说明句。** 诸如 *"Each of these is a feature we ship today, not a roadmap promise. The list will stay short on purpose."* 这样的句子放在区块标题下只会显得杂乱。眉题 + 主标题 + 正文就足够了。
* **禁止使用笼统的步骤标签。** "Stage 1 / Stage 2 / Stage 3"、"Step 1 / Step 2 / Step 3"、"Phase 01 / Phase 02 / Phase 03"、"Pass One / Pass Two / Pass Three"。一律禁用。实际的步骤内容本身就是标签。如果必须体现流程推进，请直接使用“动词-名词”形式（"Install"、"Configure"、"Ship"），而不是 "Stage 1: Install"。

**胶囊标签、标注与版本戳**
* **禁止在图像上叠加胶囊标签／标注／标签。** 不要在照片上使用 `<span>` 叠加层添加 `Brand · 02`、`PLATE · BRAND`、`Field notes - journal` 等标签。要么让图像独立呈现，要么直接在图像下方（图像外部）添加说明文字。
* **禁止将照片署名说明用作装饰。** 在素材图或 picsum 图像下方放置 `Field study no. 12 · Ines Caetano`、`Plate 03 · House archive`、`Frame XII · 35mm` 之类的字符串，显得矫揉造作。仅当确实需要为真实照片的真实摄影师署名（并已获得许可）时，才允许使用照片署名。否则，请省略说明文字，或使用一行功能性说明（"The 6-quart, in Sage."）。
* **营销页面中禁止使用版本页脚。** `v1.4.2`、`Build 0048`、`last sync 4s ago · main` 之类的页脚字符串属于 CLI／开发工具界面元素，不是落地页内容。禁止出现在营销页、落地页或作品集页面中。
* **禁止将 "Reservation 412 of 800" 这类实时库存计数器**用作装饰。仅当需求明确是使用真实数据的限量候补名单时才可使用。

**装饰性文本条**
* **首屏主视觉底部禁止使用装饰性文本条。** 将 `BRAND. MOTION. SPATIAL.`、`TYPE / FORM / MOTION`、`DESIGN · BUILD · SHIP`、`ESTD. 2018 · LISBON · BRAND. MOTION. SPATIAL.` 等内容以小号等宽全大写文本条的形式横贯首屏底部，是代理商作品集的陈词滥调。默认禁用。仅当文本条包含真实的可导航链接（底部粘性导航）或真实状态信息（Cookie 横幅、文档网站上的构建信息）时才可接受。
* **区块标题中禁止使用悬浮在右上角的辅助文本。** 典型模式是：区块左侧有一个巨大的左对齐标题；同一区块标题区域的右上角悬浮着一小段说明文字，与其他任何内容都没有清晰的对齐关系。这个悬浮文本就是设计破绽。请将辅助文本直接放在标题下方，或构建整洁的双栏标题布局（左侧：标题，右侧：对齐的正文），不要使用悬浮在角落的小段落。

**列表、分隔线与评分**
* **禁止在长列表或规格表的每一行同时使用 `border-t` 和 `border-b`。** 二选一（在行与行之间使用底部边框，或在整组内容上方使用顶部边框），并尽量少用。一个 10 行规格表，如果每行下方都有细线，就是最偷懒的布局方式。替代 UI 组件请参见第 4.9 节。
* **禁止将带有填充背景轨道的评分条或进度条用作对比视觉元素。** 如果需要展示“Y 中的 X”这类对比，优先使用数字加小图标，或使用不带背景轨道的微型行内条。大块填充的 `bg-zinc-200` 轨道上再叠加部分填充，在着陆页中只会造成仪表盘式 UI 的视觉杂乱。

**地区、时间与滚动提示**
* **99% 的需求都禁止使用地区、城市名称、时间或天气信息条。** 首屏中的“里斯本，与创始人合作”、页脚中的“1200-690 里斯本，葡萄牙”、导航中的“里斯本 14:23 · 18°C”。这些都是暴露代理公司作品集套路的装饰性特征。仅在以下情况下允许使用：需求明确描述了一个全球分布式工作室，且其工作与时区相关；旅行类品牌；或现实世界中的实体场所。页脚中单独出现一次联系地址没有问题，但营造氛围的地区信息条不可以。
* **禁止使用滚动提示。** `Scroll`、`↓ scroll`、“滚动探索”、“滚动查看完整内容”、带动画的鼠标滚轮图标。如果用户尚未滚动，他们正在查看首屏。他们知道如何滚动。视口底部不需要标签。
* **默认完全禁止装饰性状态圆点。** 导航项前、列表行前、徽章前或状态标签前的彩色圆点，都是明显的套路特征。只有在传达真实语义状态时才可以接受，例如实际服务器状态的实时指示器或实时可用性标记，并且每个页面区块最多只能使用一个。

### 9.G 长破折号禁令（违反次数最多的单一套路特征）

**完全禁止使用长破折号（`—`）。** 它是 LLM 标志性的文体拐杖，也是生产测试中排名第一的视觉套路特征。不存在“有限使用”的余地，不存在“符合自然语言使用频率”的余地，也不存在“在正文中使用没问题”的余地。完全没有。

* **禁止在标题中使用。** 使用句号或逗号。
* **禁止在眉题、标签、胶囊、按钮文本、图片说明和导航项中使用。** 改用换行、分栏或细分隔线。
* **禁止在正文中使用。** 重构句子：用句号拆成两个句子，或使用逗号、括号或冒号。
* **禁止在引语署名中使用。** 使用两侧带空格的普通连字符（` - `），或换行并使用字重更小的姓名。
* **以分隔符形式使用的短破折号（`–`）同样禁止。** 日期范围（`2018-2026`）使用连字符。数字范围（`€40-80k`）使用连字符。

页面上唯一允许使用的横线字符是：
* 普通连字符 `-`（用于复合词、范围和标记中的行分隔符）
* 数学中的减号（`-5°C`）

如果输出中任何用户可见的位置包含一个 `—` 或 `–`，该输出就无法通过发布前检查，必须重写。

此规则不容协商。过去，当要求表述为“谨慎使用”时，代理一直会忽略对长破折号的限制。这里的表述是二元的：长破折号数量必须为零。

## 10. 参考词汇（智能体应了解的模式名称）

这是一套词汇，而非代码库。智能体应当了解这些模式名称，以便在沟通时使用、在设计时将其纳入考量，并在设计解读表明需要它们时加以采用。**具体实现和代码草图位于区块库（第 12 节）中，该库会通过迭代逐步填充。**

### 首屏模式
* **非对称分栏首屏** - 文本位于一侧，素材位于另一侧，并留有充足的留白空间。
* **编辑式宣言首屏** - 大号字体、不使用素材，整体近似海报。
* **视频 / 媒体蒙版首屏** - 以文字作为镂空蒙版，叠加在视频背景之上。
* **动态文字首屏** - 以动画排版作为主要视觉元素。
* **幕布揭示式首屏** - 首屏各部分随滚动像幕布一样展开。
* **滚动固定式首屏** - 首屏保持固定，内容在其后方滚动。

### 导航与菜单
* **Mac OS Dock 放大效果** - 边缘导航，图标在悬停时流畅缩放。
* **磁吸按钮** - 按钮向光标方向吸附。
* **黏液菜单** - 子项像黏稠液体一样分离。
* **灵动岛** - 用于状态 / 提醒、可变形的胶囊形组件。
* **上下文径向菜单** - 在点击位置展开的圆形菜单。
* **悬浮快捷拨盘** - 悬浮操作按钮弹性展开为弧形排列的次级操作。
* **大型菜单揭示** - 全屏下拉菜单，内容交错淡入。

### 布局与网格
* **便当网格** - 非对称的区块组合（类似 Apple 控制中心）。
* **瀑布流布局** - 错落排列的网格，没有固定行高。
* **幻彩网格** - 带有微妙动态渐变的边框 / 区块。
* **分屏滚动** - 两个半屏向相反方向滑动。
* **黏性堆叠区段** - 滚动时固定并堆叠的区段。

### 卡片与容器
* **视差倾斜卡片** - 跟踪鼠标坐标产生 3D 倾斜效果。
* **聚光边框卡片** - 光标经过时边框被照亮。
* **玻璃拟态面板** - 带有内部折射效果的磨砂玻璃。
* **全息箔片卡片** - 悬停时呈现虹彩变幻效果。
* **Tinder 滑动卡片堆** - 具有实体感的卡片堆，可通过滑动移除。
* **变形模态框** - 按钮展开为其自身对应的对话框。

### 滚动动画
* **黏性滚动堆叠** - 卡片保持固定并产生实体堆叠效果。
* **横向滚动接管** - 垂直滚动 → 横向平移。
* **机车式 / 序列式滚动** - 视频 / 3D 序列与滚动条联动。
* **缩放视差** - 中央背景图像随滚动缩放。
* **滚动进度路径** - SVG 线条随滚动逐步绘制。
* **液态滑动过渡** - 像黏稠液体一样的页面过渡效果。

### 图库与媒体
* **穹顶画廊** - 3D 全景画廊。
* **封面流轮播** - 两侧带有倾斜效果的 3D 轮播。
* **拖拽平移网格** - 可拖拽的无边界画布。
* **手风琴图像滑块** - 悬停时展开的狭窄图像条。
* **悬停图像轨迹** - 鼠标移动时留下不断弹出的图像轨迹。
* **图像故障效果** - 悬停时产生 RGB 通道偏移。

### 排版与文本
* **动态跑马灯** - 随滚动反向移动的无尽文本带。
* **文本蒙版揭示** - 将巨型文字作为通向视频的透明窗口。
* **文本乱序效果** - 加载 / 悬停时呈现《黑客帝国》风格的解码效果。
* **环形文本路径** - 文本沿旋转圆环弯曲排列。
* **渐变描边动画** - 带有流动渐变的描边文字。
* **动态排版网格** - 字母会躲避光标。

### 微交互与特效
* **粒子爆炸按钮** - CTA 在操作成功时碎裂成粒子。
* **液态下拉刷新** - 如同液滴分离般的重新加载指示器。
* **骨架屏微光** - 光线反射在占位元素上流动。
* **方向感知悬停按钮** - 填充效果从光标进入的准确方向出现。
* **点击涟漪效果** - 波纹从点击坐标处扩散。
* **SVG 线条绘制动画** - 矢量图形实时自行绘制。
* **网格渐变背景** - 如熔岩灯般自然流动的色块。
* **镜头模糊景深** - 模糊背景 UI，以聚焦前景操作。

### 动画库选择
* **Motion (`motion/react`)** - 默认用于 UI / Bento / 状态变化动画。
* **GSAP + ScrollTrigger** - 用于整页滚动叙事和滚动劫持。将其隔离在专用的叶子组件中，并通过 `useEffect` 进行清理。
* **Three.js / WebGL** - 用于画布背景和 3D 场景。遵循相同的隔离规则。
* **绝不要在同一组件树中混用 GSAP / Three.js 与 Motion。** 它们会争夺相同的帧。

## 11. 重新设计协议

此技能同时适用于**从零构建和重新设计**。错误判断模式是导致重新设计结果不佳的最大原因。

### 11.A 检测模式（第一步操作）
* **从零构建** - 不存在现有网站，或已批准进行全面改造。根据第 1 节调整基准值。
* **重新设计 - 保留** - 在不破坏品牌的前提下实现现代化。先进行审计，提取品牌令牌，再逐步演进。
* **重新设计 - 全面改造** - 在现有内容之上采用新的视觉语言。视觉方面按从零构建处理；保留内容和信息架构。

如果不明确，只询问**一次**：*"这次重新设计是要保留现有品牌，还是从视觉上完全重新开始？"*

### 11.B 修改前先审计
在提出更改建议之前，记录当前状态：
* **品牌令牌** - 主色 / 强调色、字体组合、徽标处理方式、圆角。
* **信息架构** - 页面树、主导航、关键转化路径。
* **内容区块** - 现有内容、真正发挥作用的内容、仅用于填充的内容。
* **需要保留的模式** - 标志性交互、易于识别的首屏、文案语调。
* **需要淘汰的模式** - AI 垃圾内容特征、损坏的布局、失效链接、通用图库图片、性能陷阱。
* **现有网站的调节值读数** - 推断当前的 `DESIGN_VARIANCE` / `MOTION_INTENSITY` / `VISUAL_DENSITY`。这是你的起点，而不是基准值。
* **SEO 基准** - 当前已有排名的页面、元标题、结构化数据、OG 卡片。**SEO 迁移是重新设计中的首要风险。**

### 11.C 保留规则
* **除非收到明确要求，否则不要更改信息架构。** 保持页面 slug、锚点 ID 和主导航标签稳定，以维持 SEO 效果和用户的操作习惯。
* **在应用第 4.2 节之前提取品牌颜色。** 已经采用紫色的品牌应继续使用紫色——应用 LILA 规则中的覆盖条款。
* **除非收到重写要求，否则保留文案语调。** 视觉现代化 ≠ 内容重写。
* **保留现有的无障碍优势。** 不要让焦点状态、替代文本、键盘导航和对比度出现倒退。
* **尊重现有的分析事件。** 不要重命名下游跟踪所依赖的按钮、表单字段和分区 ID。

### 11.D 现代化调整杠杆（按优先级排序）
按顺序应用——当简报要求得到满足时即停止：
1. **字体排印焕新**——单位风险所带来的视觉提升最大。
2. **间距与节奏**——增加区块内边距，修正垂直节奏。
3. **色彩重新校准**——降低饱和度，统一中性色，保留品牌强调色。
4. **动效层**——为现有组件添加符合 `MOTION_INTENSITY` 的微交互。
5. **首屏与关键区块重构**——使用第 10 节中的词汇重构漏斗顶部。
6. **完整区块替换**——仅当现有区块已无法挽救时采用。

### 11.E 决策树：针对性演进与全面重新设计
* 信息架构、内容和 SEO 状况良好 → **针对性演进**（杠杆 1-4）。以约 40% 的风险获得约 70% 的价值。
* 视觉债务属于结构性问题（信息架构混乱、没有设计系统、移动端不可用）→ **全面重新设计**，并严格保留内容。
* 品牌本身正在改变 → **从零开始设计**。

### 11.F 绝不静默更改的内容
未经用户明确批准，绝不修改：
* URL 结构 / 路由 slug。
* 主导航标签。
* 表单字段名称或顺序（会破坏分析 + 自动填充）。
* 品牌徽标或文字标识。
* 现有法律 / 同意 / Cookie 文案。

## 附录 C - Apple Liquid Glass：如实说明的 Web 近似实现

**不要**将随意拼凑的 CSS 代码片段视为 Apple 官方的 Liquid Glass。

### 哪些是官方内容
Apple 在其人机界面指南和开发者文档中介绍了用于 **Apple 平台**的 Liquid Glass。它是一种应用于 Apple 各平台 UI 的动态材质。Apple 的原生实现属于 Apple 平台 API 和系统组件，**并非公开的 Web CSS 包**。

相关官方文档：
- Apple 人机界面指南 → 材质
- Apple 开发者文档 → Liquid Glass
- Apple 开发者文档 → 采用 Liquid Glass
- SwiftUI → Material

### 哪些不是官方内容
Apple 并未为普通网站提供 `liquid-glass.css`。

Web 近似实现可以使用：
- `backdrop-filter`
- 透明背景
- 分层边框
- 高光叠加层
- 渐变
- 动效
- 高对比度回退方案

但这只是 **Web 玻璃拟态 / 毛玻璃近似实现**，并非 Apple 官方的 Liquid Glass。请在注释中明确标注这一点。

### 更稳妥的 Web 近似实现骨架

```css
.liquid-glass-web-approx {
  position: relative;
  isolation: isolate;
  overflow: hidden;
  border-radius: 999px;
  border: 1px solid rgb(255 255 255 / .32);
  background:
    linear-gradient(135deg, rgb(255 255 255 / .30), rgb(255 255 255 / .08)),
    rgb(255 255 255 / .12);
  backdrop-filter: blur(24px) saturate(180%) contrast(1.05);
  -webkit-backdrop-filter: blur(24px) saturate(180%) contrast(1.05);
  box-shadow:
    inset 0 1px 0 rgb(255 255 255 / .48),
    inset 0 -1px 0 rgb(255 255 255 / .12),
    0 18px 60px rgb(0 0 0 / .18);
}

.liquid-glass-web-approx::before {
  content: "";
  position: absolute;
  inset: 0;
  z-index: -1;
  border-radius: inherit;
  background:
    radial-gradient(circle at 20% 0%, rgb(255 255 255 / .55), transparent 34%),
    linear-gradient(90deg, rgb(255 255 255 / .18), transparent 42%, rgb(255 255 255 / .14));
  pointer-events: none;
}

.liquid-glass-web-approx::after {
  content: "";
  position: absolute;
  inset: 1px;
  border-radius: inherit;
  border: 1px solid rgb(255 255 255 / .14);
  pointer-events: none;
}

@media (prefers-color-scheme: dark) {
  .liquid-glass-web-approx {
    border-color: rgb(255 255 255 / .18);
    background:
      linear-gradient(135deg, rgb(255 255 255 / .16), rgb(255 255 255 / .04)),
      rgb(15 23 42 / .42);
    box-shadow:
      inset 0 1px 0 rgb(255 255 255 / .22),
      0 18px 60px rgb(0 0 0 / .42);
  }
}

@media (prefers-reduced-transparency: reduce) {
  .liquid-glass-web-approx {
    background: rgb(255 255 255 / .96);
    backdrop-filter: none;
    -webkit-backdrop-filter: none;
  }
}
```

**重要提示：** `prefers-reduced-transparency` 的浏览器支持情况不一致；请进行测试。即使没有模糊效果，也务必提供足够的对比度。
