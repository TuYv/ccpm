# tasteskill：反低质前端技能

> 落地页、作品集和重新设计。不适用于仪表盘、数据表格或多步骤产品 UI。
> 以下每条规则都具有**上下文相关性**。没有任何规则会自动生效。先阅读需求，再只选取适用的部分。

---

## 0. 需求推断（先读懂场景，再做其他事情）

在接触代码或调整参数之前，**先推断用户真正想要什么**。大多数 LLM 生成的设计之所以糟糕，是因为模型没有读懂场景，就直接套用了默认审美。

### 0.A 先读取这些信号
1. **页面类型** - 落地页（SaaS / 消费者 / 代理机构 / 活动）、作品集（开发者 / 设计师 / 创意工作室）、重新设计（保留还是彻底改造）、编辑 / 博客。
2. 用户使用的**氛围词** - “极简主义”、“平静”、“Linear 风格”、“Awwwards”、“粗野主义”、“高端消费品”、“Apple 风格”、“活泼”、“严肃的 B2B”、“编辑风”、“代理机构风”、“玻璃质感”、“暗黑科技”。
3. **参考信号** - 他们提供的 URL、粘贴的截图、提到的产品、正在竞争的品牌。
4. **受众** - B2B 采购评审小组、注重设计的消费者，还是快速浏览作品集的招聘人员。审美应由受众决定，而不是由你的品味决定。
5. **已有的品牌资产** - logo、颜色、字体、摄影素材。对于重新设计，这些是起始素材，而不是可有可无的输入（见第 11 节）。
6. **隐性约束** - 无障碍优先的受众、公共部门、受监管行业、以信任为先的商业场景、儿童产品。这些约束会**覆盖**审美偏好。

### 0.B 生成前输出一行“设计判断”
在任何代码之前，用一行说明：**“我的判断是：这是面向 \<受众> 的 \<页面类型>，采用 \<氛围> 语言，倾向于 \<设计系统或审美范式>。”**

判断示例：
- *“我的判断是：这是面向技术买家的 B2B SaaS 落地页，采用 Linear 风格的极简语言，倾向于 Tailwind utilities + Geist + 克制的动效。”*
- *“我的判断是：这是面向招聘经理的独立设计师作品集，采用编辑风 / 动态字体语言，倾向于原生 CSS + 滚动驱动动画 + 定制字体。”*
- *“我的判断是：这是公共部门服务网站的重新设计，采用以信任为先的语言，倾向于 GOV.UK Frontend 或 USWDS。”*

### 0.C 如果需求不明确，提出一个问题，不要猜测
只提出**一个**澄清问题，绝不要一次抛出多个问题，并且只有在设计判断确实存在分歧时才这样做。示例：*“你希望它更接近 Linear 式的整洁，还是 Awwwards 式的实验性？”*

如果你能根据上下文自信地推断出来，**不要提问**。直接声明设计判断并继续。

### 0.D 反默认原则
不要默认使用：AI 紫色渐变、深色网格背景上的居中 hero、三个相同的功能卡片、到处使用通用玻璃拟态、无休止循环的微动画、Inter + slate-900。这些都是 LLM 的默认选项。应根据设计判断，有意识地突破这些套路。

## 1. 三个旋钮（核心配置）

完成设计判断后，设置三个旋钮。下面的所有布局、动效和密度决策，都由这三个旋钮控制。

* **`DESIGN_VARIANCE: 8`** - 1 = 完美对称，10 = 艺术化混沌
* **`MOTION_INTENSITY: 6`** - 1 = 静态，10 = 电影感 / 物理效果
* **`VISUAL_DENSITY: 4`** - 1 = 艺术画廊 / 空灵，10 = 驾驶舱 / 数据密集

**基线：** `8 / 6 / 4`。除非设计判断另有覆盖，否则使用这些值。不要要求用户编辑此文件，覆盖应在对话中进行。

### 1.A 拨盘推断（设计判断 → 拨盘值）
| 信号 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| “极简 / 干净 / 平静 / 编辑风格 / Linear 风格” | 5-6 | 3-4 | 2-3 |
| “高端消费品 / Apple 风格 / 奢华 / 品牌” | 7-8 | 5-7 | 3-4 |
| “趣味 / 狂野 / Dribbble / Awwwards / 实验性 / 创意机构” | 9-10 | 8-10 | 3-4 |
| “落地页 / 作品集 / 营销网站（默认）” | 7-9 | 6-8 | 3-5 |
| “信任优先 / 公共部门 / 强监管 / 无障碍要求严格” | 3-4 | 2-3 | 4-5 |
| “重新设计 - 保留” | 匹配现有设计 | +1 | 匹配现有设计 |
| “重新设计 - 全面改造” | +2 | +2 | 匹配现有设计 |

### 1.B 使用场景预设
| 使用场景 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 落地页（SaaS、主流产品） | 7 | 6 | 4 |
| 落地页（创意机构 / 创意类） | 9 | 8 | 3 |
| 落地页（高端消费品） | 7 | 6 | 3 |
| 作品集（设计师 / 工作室） | 8 | 7 | 3 |
| 作品集（开发者） | 6 | 5 | 4 |
| 编辑内容 / 博客 | 6 | 4 | 3 |
| 公共部门服务 | 3 | 2 | 5 |
| 重新设计 - 保留 | 匹配 | 匹配+1 | 匹配 |
| 重新设计 - 全面改造 | +2 | +2 | 匹配 |

### 1.C 拨盘如何驱动输出
将这些值（或用户覆盖后的值）作为全局变量使用。本文档中的交叉引用均指向这些确切的变量名，绝不要创建如 `LAYOUT_VARIANCE` 或 `ANIM_LEVEL` 这样的别名。

## 2. 简报 → 设计系统映射

确定设计判断（第 0 节）和拨盘值（第 1 节）后，选择合适的基础。对于有官方包的内容，不要自行编写 CSS。不要把一种美学趋势伪装成官方系统。

### 2.A 何时应选择真正的设计系统（使用官方包）
| 简报呈现为…… | 应选择 | 原因 |
|---|---|---|
| Microsoft / 企业 SaaS / 仪表盘 | `@fluentui/react-components` 或 `@fluentui/web-components` | 官方 Fluent UI、Microsoft 令牌、已处理无障碍 |
| 类 Google UI、Material 风格产品 | `@material/web` + Material 3 tokens | 官方方案，可通过 Material Theming 配置主题 |
| IBM 风格 B2B / 企业分析 | `@carbon/react` + `@carbon/styles` | 官方 Carbon，成熟的数据密度模式 |
| Shopify 应用界面 | `polaris.js` web components / Polaris React | Shopify 管理后台 UI 的必需项 |
| Atlassian / Jira 风格产品 | `@atlaskit/*` + `@atlaskit/tokens` | 官方 Atlassian DS |
| GitHub 风格开发工具 / 社区页面 | `@primer/css` 或 `@primer/react-brand` | 官方 Primer；营销场景使用 Brand 变体 |
| 英国公共部门服务 | `govuk-frontend` | 法律 / 监管层面通常要求 |
| 美国公共部门 / 信任优先 | `uswds` | 同上 |
| 快速本地企业 / 创意机构 MVP | Bootstrap 5.3 | 朴素、快速、可用 |
| 现代且无障碍的 React 基础 | `@radix-ui/themes` | 原语组件 + 精致主题 |
| 组件由你掌控的现代 SaaS | shadcn/ui (`npx shadcn@latest add ...`) | 代码归你所有，易于自定义；绝不要以默认状态发布 |
| 基于 Tailwind 的现代 SaaS / AI 营销 | Tailwind v4 utilities + `dark:` variant | 独立开发者和小团队构建的默认选择 |

**诚实原则：**如果需求读起来属于上述某个系统，请安装并使用该系统的**官方**包。不要手动重新创建其 CSS。不要导入某个系统的设计令牌，却又覆盖其中 90% 的内容。

**每个项目使用一个系统。**不要在同一棵组件树中混用 Fluent React 和 Carbon。不要将 shadcn/ui 组件导入 Material 3 应用。

### 2.B 当需求描述的是一种审美风格，而非设计系统时
对于以下方向，**不存在单一的官方包**。请使用原生 CSS + Tailwind + 维护良好的组件库进行构建。在代码注释中如实说明哪些内容借鉴了灵感，哪些是官方材料。

| 审美风格 | 诚实的实现方式 |
|---|---|
| Glassmorphism / “磨砂玻璃” | `backdrop-filter`、分层边框、高光叠加层。为 `prefers-reduced-transparency` 提供纯色填充回退方案。 |
| Bento（Apple 风格的磁贴网格） | 使用带有不同单元格尺寸的 CSS Grid。没有任何单一库拥有这一方案。 |
| Brutalism | 原生 CSS、等宽字体、粗犷边框。不使用库。 |
| Editorial / 杂志风格 | 衬线字体、不对称网格、充足留白。不使用库。 |
| Dark tech / 黑客风格 | 等宽字体 + 强调色霓虹、终端元素。不使用库。 |
| Aurora / 网格渐变 | SVG 或分层径向渐变。不使用库。 |
| Kinetic typography / 动态排版 | 原生 CSS 动画、滚动驱动动画；对于接管式滚动效果使用 GSAP。不使用库。 |
| **Apple Liquid Glass** | Apple 仅针对 Apple 平台对其进行文档说明。**不存在官方的 `liquid-glass.css`。**Web 实现都是使用 `backdrop-filter` + 分层边框 + 高光效果进行的近似实现。请明确标注为近似方案。 |

## 3. 默认架构与约定

除非设计判断选择了真实的设计系统（第 2.A 节），否则默认采用以下方案：

### 3.A 技术栈
* **框架：**React 或 Next.js。默认使用 Server Components (RSC)。
  * **RSC SAFETY：**全局状态只能在 Client Components 中工作。在 Next.js 中，请将 providers 包裹在一个带有 `"use client"` 的组件中。
  * **INTERACTIVITY ISOLATION：**任何使用 Motion、滚动监听器或指针物理效果的组件都必须是一个独立的叶子组件，并在顶部添加 `'use client'`。Server Components 仅渲染静态布局。
* **样式：****Tailwind v4**（默认）。只有现有项目有要求时才使用 Tailwind v3。
  * 对于 v4：不要在 `postcss.config.js` 中使用 `tailwindcss` plugin。请使用 `@tailwindcss/postcss` 或 Vite plugin。
* **动画：****Motion**（原名为 Framer Motion 的库）。从 `motion/react` 导入（`import { motion } from "motion/react"`）。`framer-motion` 包仍可作为旧版别名使用，但新代码优先使用 `motion/react`。
* **字体：**始终使用 `next/font`（Next.js），或通过 `@font-face` + `font-display: swap` 自托管。生产环境中绝不要通过 `<link>` 引入 Google Fonts。

### 3.B 状态
* 对于隔离的 UI，使用本地 `useState` / `useReducer`。
* 只有为避免深层属性逐级传递时才使用全局状态 - Zustand、Jotai 或 React context。
* **绝不要**使用 `useState` 跟踪由用户输入驱动的连续值（鼠标位置、滚动进度、指针物理效果、磁性悬停效果）。请使用 Motion 的 `useMotionValue` / `useTransform` / `useScroll`。`useState` 会在每次变化时重新渲染 React 树，并且在移动端会崩溃。

### 3.C 图标
* **允许使用的库（优先级顺序）：** `@phosphor-icons/react`、`hugeicons-react`、`@radix-ui/react-icons`、`@tabler/icons-react`。
* **不推荐：** `lucide-react`。仅当用户明确要求使用它，或项目已经依赖它时才可接受。
* **绝对不要手工绘制 SVG 图标。** 如果缺少某个字形，请安装第二个库，或使用基础图元组合实现，不要从头绘制图标路径。
* **每个项目只使用一个图标系列。** 不要在同一个组件树中混用 Phosphor 和 Lucide。
* **全局统一 `strokeWidth`。**（例如 `1.5` 或 `2.0`。）

### 3.D Emoji 政策
默认不建议在代码、标记和可见文本中使用 Emoji。使用图标库中的字形替代符号。**例外：** 只有当用户明确要求活泼、聊天风格或原生社交媒体风格时才允许使用 Emoji，即使如此也应有目的地少量使用。

### 3.E 响应式与布局机制
* 统一断点（`sm 640`、`md 768`、`lg 1024`、`xl 1280`、`2xl 1536`）。
* 使用 `max-w-[1400px] mx-auto` 或 `max-w-7xl` 限制页面布局宽度。
* **视口稳定性：** 绝对不要在全高度 Hero 区块中使用 `h-screen`。始终使用 `min-h-[100dvh]`，以避免移动端（iOS Safari 地址栏）发生布局跳动。
* **优先使用 Grid，而不是 Flex 数学计算：** 绝对不要使用复杂的 flexbox 百分比计算（`w-[calc(33%-1rem)]`）。始终使用 CSS Grid（`grid grid-cols-1 md:grid-cols-3 gap-6`）。

### 3.F 依赖验证（强制）
在导入任何第三方库之前，检查 `package.json`。如果缺少该包，先输出安装命令。**绝不要假设某个库已经存在。**

## 4. 设计工程指令（偏差校正）

LLM 默认会采用陈词滥调。主动覆盖这些默认倾向。每条规则都有基于上下文的例外路径。

### 4.1 字体排版
* **展示文字 / 标题：** 默认使用 `text-4xl md:text-6xl tracking-tighter leading-none`。
* **正文 / 段落：** 默认使用 `text-base text-gray-600 leading-relaxed max-w-[65ch]`。
* **无衬线字体选择：**
  * **不建议作为默认选择：** `Inter`。优先选择 `Geist`、`Outfit`、`Cabinet Grotesk`、`Satoshi`，或与品牌相符的衬线字体。
  * **例外：** 当用户明确要求中性、标准或 Linear 风格，或需求是面向公共部门 / 无障碍优先的网站时，可以使用 Inter。
* **可参考的字体搭配：** `Geist` + `Geist Mono`、`Satoshi` + `JetBrains Mono`、`Cabinet Grotesk` + `Inter Tight`、`GT America` + `IBM Plex Mono`。

* **衬线字体规范（默认情况下强烈不建议）：**
  * 衬线字体**非常不建议作为任何项目的默认字体。**“它感觉有创意 / 高级 / 编辑感”并不是选择衬线字体的理由。代理默认认为“创意需求 = 衬线字体”的思维模式，是生产评审中最容易被识别的 AI 痕迹。
  * **只有明确符合以下任一条件时，衬线字体才可接受：**
    - 品牌需求明确指定了衬线字体，或
    - 美学风格确实属于编辑 / 奢华 / 出版物 / 手稿 / 传统 / 复古，并且你能够说明为什么这款特定的衬线字体适合这个特定品牌
  * 对于其他所有情况（创意机构、设计工作室、现代品牌、高端消费品牌、作品集、生活方式），**默认使用无衬线展示字体**（Geist Display、ABC Diatype、Söhne Breit、Cabinet Grotesk Display、Migra Sans、GT Walsheim、Inter Display、PP Neue Montreal）。无衬线展示字体并不“无聊”——它之所以是默认选择，就像黑色之所以是时尚界的默认颜色一样。
  * **强调规则（相关）：** 当你想在标题中强调某个词时（例如动态的“and `spatial` design”式处理），请使用**同一字体**的斜体或粗体。不要为了增加视觉趣味，在无衬线标题中突然插入一个随机的衬线词，反之亦然。混用字体家族来强调内容是业余做法。在同一字体家族中使用斜体 / 粗体强调，才是正确方式。
  * **明确禁止作为默认选择：** `Fraunces` 和 `Instrument_Serif`（这两款是 LLM 最偏爱的展示衬线字体）。
  * **如果衬线字体确有充分理由**（按照上述标准，这种情况很少见），请从以下字体池中轮换选择，不要在连续项目中重复使用同一款衬线字体：PP Editorial New、GT Sectra Display、Cardinal Grotesque、Reckless Neue、Tiempos Headline、Recoleta、Cormorant Garamond、Playfair Display、EB Garamond、IvyPresto、Migra、Editorial Old、Saol Display、Söhne Breit Kursiv、Domaine Display、Canela、Schnyder、Tobias、NB Architekt、ITC Galliard。

* **斜体下行字母留白（强制）：** 当展示性字体使用斜体且单词包含下行字母（`y g j p q`）时，`leading-[1]` 或 `leading-none` 会裁切下行部分。至少使用 `leading-[1.1]`，并在包裹元素上添加 `pb-1` 或 `mb-1` 预留空间。发布前审查展示型标题中的每个斜体单词。

### 4.2 色彩校准
* 最多使用 1 种强调色。默认饱和度 < 80%。
* **LILA 规则：** 不鼓励默认采用“AI 紫色 / 蓝色光晕”美学。不要自动为紫色按钮添加光晕，不要随意使用霓虹渐变。使用中性色基底（Zinc / Slate / Stone），搭配高对比度的单一强调色（Emerald、Electric Blue、Deep Rose、Burnt Orange 等）。
* **例外：** 如果品牌或需求明确要求紫色 / 紫罗兰色 / 淡紫色，就大胆使用。但要有明确意图地执行：保持调色板一致、中性色协调、渐变克制。不要使用泛滥的通用 AI 渐变。
* **每个项目使用一套调色板。** 不要在同一项目中于暖灰与冷灰之间摇摆。
* **色彩一致性锁定（强制）：** 一旦为页面选择了强调色，必须在**整个**页面中使用。暖灰色网站不能在第 7 节突然出现蓝色 CTA。以玫瑰色为强调色的网站不能在页脚出现青绿色状态徽章。选择一种强调色，锁定它，并在发布前审查每个组件。

* **高端消费品调色板禁令（强制，第二常见的 AI 痕迹）：**
  * 对于高端消费品需求（炊具、健康、手工艺、奢侈品、传统工艺、DTC 家居用品等），LLM 默认倾向于使用**暖米色/奶油色 + 黄铜/陶土/牛血红/赭黄 + 浓缩咖啡色/墨色深色文本**。以下十六进制色系默认禁止作为背景和强调色：
    - 背景：`#f5f1ea`、`#f7f5f1`、`#fbf8f1`、`#efeae0`、`#ece6db`、`#faf7f1`、`#e8dfcb`（均为“暖纸色 / 奶油色 / 粉笔色 / 骨白色”）
    - 强调色：`#b08947`、`#b6553a`、`#9a2436`、`#9c6e2a`、`#bc7c3a`、`#7d5621`（均为“黄铜色 / 陶土色 / 牛血红 / 赭黄”）
    - 文本：`#1a1714`、`#1a1814`、`#1b1814`（均为“浓缩咖啡色 / 暖调近黑色”）
  * 此调色板被禁止作为高端消费品需求的默认选择。你曾经交付的每个高端消费品网站都使用了这套完全相同的调色板，导致品牌失去辨识度。
  * **默认替代方案（轮换使用，不要重复）：**
    - **冷调奢华：** 银灰色 + 铬色 + 烟灰色（参考 Tesla、Apple Watch Hermes，但不要皮革感）
    - **森林：** 深绿色 + 骨白色 + 琥珀色强调（参考 Filson、Patagonia 高端系列）
    - **黑色与棕褐色：** 纯正近黑色 + 暖棕褐色，强烈对比，不使用米色
    - **钴蓝 + 奶油色：** 高饱和蓝色搭配单一中性色，不使用黄铜色
    - **陶土色 + 石板灰：** 暖锈色搭配冷灰色，不使用黄铜色
    - **橄榄绿 + 砖红 + 纸白：** 柔和橄榄绿搭配砖红色强调
    - **纯单色 + 单一高饱和点缀：** 米白色 + 近黑色 + 一种明亮强调色（电光蓝、翡翠绿、亮粉色等）
  * **调色板轮换规则：** 如果你上一个生成的高端消费品项目使用了米色+黄铜色系，这个项目**必须**使用不同的色系。不要连续两次交付相同的暖调工艺风调色板。
  * **例外：** 仅当品牌需求明确指定米色+黄铜色+浓缩咖啡色，或品牌识别确实属于复古 / 手工艺 / 暖调工艺风格，并且你能够说明为什么这套特定调色板适合这个特定品牌时，米色+黄铜色+浓缩咖啡色调色板才可接受。因为“这是一个炊具需求”而默认采用它是被禁止的。

### 4.3 布局多样化
* **反中心偏置：** 当 `DESIGN_VARIANCE > 4` 时，应避免居中的 Hero / H1 区块。强制使用“Split Screen”（50/50）、“左对齐内容 / 右对齐资产”、“非对称留白”或滚动固定结构。
* **覆盖规则：** 对于编辑类 / 宣言类 / 发布公告类 brief，如果信息本身就是设计的一部分，可以使用居中的 Hero。

### 4.4 材质感、阴影、卡片
* 仅在抬升效果能够传达真实层级关系时使用卡片。否则应使用 `border-t`、`divide-y` 或负空间进行分组。
* 使用阴影时，应将其色调调整为与背景色相协调。浅色背景上禁止使用纯黑投影。
* 对于 `VISUAL_DENSITY > 7`：禁止使用通用卡片容器。数据指标应在朴素的布局中保持呼吸感。
* **形状一致性锁定（强制）：** 为页面选择 ONE 套圆角尺度，并始终遵守。可选方案：全直角（radius 0）、全柔和（radius 12-16px）、全胶囊（交互元素使用完整圆角）。只有在存在明确记录的规则时，才允许混用系统（例如“按钮使用 full-pill，卡片使用 16px，输入框使用 8px”），并且该规则必须在所有地方一致执行。在方形布局中使用圆角按钮，或在胶囊按钮页面中使用方形卡片，都属于设计缺陷。

### 4.5 交互式 UI 状态
LLM 默认只实现“静态成功状态”。始终实现完整的状态循环：
* **加载：** 使用与最终布局形状相匹配的骨架屏加载器。避免使用通用的圆形加载指示器。
* **空状态：** 精心编排；说明如何填充内容。
* **错误状态：** 清晰呈现，表单错误应以内联方式展示，提示消息仅用于临时性错误。
* **触觉反馈：** 在 `:active` 状态下，使用 `-translate-y-[1px]` 或 `scale-[0.98]` 来模拟实体按压效果。
* **按钮对比度检查（强制，无障碍）：** 发布任何按钮前，确认按钮文字在按钮背景上清晰可读。白色按钮配白色文字、`bg-white` CTA 配 `text-white` 标签、透明按钮置于页面背景上且没有边框，均属禁止情况。审核每个 CTA：对比度至少符合 WCAG AA 标准（正文为 4.5:1，18px 及以上的大号文字为 3:1）。同样的规则也适用于位于摄影背景上的 ghost 按钮（应使用背景衬底、遮罩或描边）。
* **CTA 按钮换行禁令（强制）：** 桌面端按钮文字 MUST 保持在一行内。如果类似 “VIEW SELECTED WORK” 的标签换成 2 行或 3 行，说明按钮存在问题。修复方式是缩短标签（主要 CTA 最多 3 个词，理想情况下为 1-2 个词）或加宽按钮（不要人为限制 CTA 的 `max-width`）。桌面端 CTA 换行属于 Pre-Flight Fail。
* **禁止重复 CTA 意图（强制）：** 同一页面上不得出现两个具有相同意图的 CTA。相同意图的示例：“Get in touch” + “Contact us” + “Let's talk” + “Start a project” + “Start something” + “Reach out” 都属于“联系”意图 → 选择 ONE 个标签，并在页面上的所有位置（导航、Hero、页脚）统一使用。同样，“Try free” + “Get started” + “Sign up free” 都属于“注册”意图；“View work” + “See selected work” + “Browse projects” 都属于“作品集”意图。每种意图只能使用一个标签。
* **表单对比度检查（强制，无障碍）：** 表单输入框、占位文本、焦点环、辅助文本和错误文本，均必须针对区块背景通过 WCAG AA 对比度标准。接近白色的表单上使用浅色占位符、白色表单置于白色页面区块中、表单标签灰度低于 4.5:1 对比度，均属禁止情况。发布前审核每个表单。

### 4.6 数据与表单模式
* 标签位于输入框**上方**。辅助文本可选，但必须存在于标记中。错误文本位于输入框**下方**。输入块统一使用 `gap-2`。
* 禁止将占位符用作标签。永远不要这样做。

### 4.7 布局规范（硬性规则。违反其中任何一条都意味着交付的是有问题的作品）

* **Hero 必须适配初始视口。** 桌面端标题最多 2 行，辅助文本最多 **20 个词**，并且最多 3-4 行；CTA 必须无需滚动即可看到。如果文案太长：缩小字体比例，或删减文案。如果无法用 20 个词的辅助文本描述价值主张，说明价值主张不清晰，而不是规则过于严格。绝不能让 Hero 溢出，迫使用户滚动才能找到 CTA。
* **Hero 字体比例规范。** 必须将字体大小和图片大小*一起*规划。如果 Hero 资源很大且标题超过 6 个词，不要从 `text-7xl/text-8xl` 开始。大多数 Hero 的默认合理范围是：`text-4xl md:text-5xl lg:text-6xl`；只有在标题为 3-5 个词时，才使用 `text-6xl md:text-7xl`。4 行的 Hero 标题始终是字体大小错误，而不是文案长度错误。
* **HERO 顶部内边距上限（强制）：** 桌面端 Hero 顶部内边距最大为 `pt-24`（约 6rem）。超过该值会让 Hero 内容悬浮在视口中部，看起来像布局错误，而不是有意设计的留白。如果 Hero 需要更多呼吸感，应增大字体比例或资源尺寸，而不是增加顶部内边距。
* **HERO 内容堆叠规范（最多 4 个文本元素）。** Hero 是一个完整的瞬间，而不是功能列表。允许的文本元素总数最多为 4 个：
  1. Eyebrow（小型大写标签）或品牌条，或两者都没有 - 三选一
  2. 标题（最多 2 行，见上文）
  3. 辅助文本（最多 20 个词，最多 4 行）
  4. CTA（1 个主要 CTA + 最多 1 个次要 CTA）
  - **Hero 中禁止出现：** CTA 下方的小型标语（"Works with GitHub, GitLab, and self-hosted Git"）、信任信息微条（"Used by engineering teams at..."）、价格预告（"Free for solo, $10/user for teams"）、功能要点列表、社会证明头像行。所有这些内容都应移至 Hero 正下方的专门区块。
  - 如果同一个 Hero 中既有 Eyebrow，又有 CTA 下方的标语，则删除标语。如果既有品牌条，又有标语，则删除标语。每个 Hero 最多只能有一个小型文本元素。
* **“Used by” / “Trusted by” logo wall 应位于 Hero 下方，绝不能放在 Hero 内。** Hero 用于呈现价值主张和主要 CTA。logo wall 是其正下方的独立区块。不要将信任标志塞进与 Hero 文案相同的 flex 行中。
* **桌面端导航必须保持单行显示。** 如果在 `lg`（1024px）下无法容纳所有项目，应精简标签、删除次要项目，或改用汉堡菜单。桌面端两行导航属于损坏的设计。
* **桌面端导航高度上限为 80px，默认高度为 64-72px。** 不要使用占据视口 15% 的大型“agency”导航栏。
* **Bento 网格必须有节奏感，不能单边重复。** 不要堆叠 6 个左侧图片 / 右侧文本的行。应改变构图：交替使用全宽功能行、不对称的单元格尺寸、纵向分隔。
* **BENTO 单元格数量规则（强制）：** Bento 网格必须**恰好**拥有与内容数量相同的单元格。3 个项目 → 3 个单元格（1+2 分割、2+1 分割，或不对称三元组）。5 个项目 → 5 个单元格（2+3、3+2、Hero+4 等）。如果网格中间或末尾出现空单元格，说明规划错误。重新调整网格形状；不要粘贴空白卡片。
* **区块布局重复禁令。** 一旦某个区块使用了一种布局类型（例如 3 列图片卡片、全宽引用、文本图片分栏），该类型在页面上最多只能出现**一次**。“Selected commissions”不应看起来像“What we do”。包含 8 个区块的落地页必须至少使用 4 种不同的布局类型。
* **ZIGZAG 交替上限（强制）。** 先使用“左图 + 右文”，再使用“左文 + 右图”的交替之字形布局属于陈旧套路。连续使用这种图片+文本分栏模式的区块最多为 2 个。第 3 个连续的图片+文本分栏区块属于 Pre-Flight Fail。应使用全宽区块、纵向堆叠区块、Bento 网格、marquee 或其他布局类型打破这种模式。
* **EYEBROW 使用克制（强制，生产测试中违反次数最多的规则）：** “Eyebrow”是位于区块标题上方、采用小型大写宽字距样式的标签（例如 `FOUR COLORWAYS`、`SELECTED WORK`、`THE HARDWARE`、`Git-native task management`）。典型 CSS 特征：`text-[11px] uppercase tracking-[0.18em]`、`font-mono text-[10.5px] uppercase tracking-[0.22em]`。每个 AI 构建的网站都会在**每个**区块标题上方放置 Eyebrow，形成相同的模板化节奏。硬性规则：
  - **每 3 个区块最多使用 1 个 Eyebrow。** Hero 计为 1 个。因此，一个包含 9 个区块的页面最多只能使用 3 个 Eyebrow。
  - 如果区块 A 有 Eyebrow，则接下来的 2 个区块不能有 Eyebrow。
  - **Pre-Flight Check 是机械式的：** 统计所有区块组件中 `uppercase tracking`（或类似的、位于标题上方的小型大写等宽字体标签）的实例数量。如果数量 > ceil(sectionCount / 3)，则输出不合格。
  - **替代 Eyebrow 的做法：** 完全删除它。标题本身已经足够。如果需要对区块进行分类，区块在页面中的位置已经起到了分类作用；无需标签。
* **SPLIT-HEADER 禁令（强制）。** “左侧大标题 + 右侧小型说明段落”作为区块标题的模式（左列 `col-span-7/8`，右列 `col-span-4/5`，右列中悬浮一段小型正文）**禁止作为默认方案**。区块应传达**一个**聚焦的信息。如果确实需要同时使用标题和说明段落，应将它们垂直堆叠（标题在上，正文在下，最大宽度为 65ch）。只有在存在真实构图理由时才使用分栏标题模式，例如右列承载视觉元素或交互元素，而不仅仅是填充文本。
* **Bento 背景多样性（强制）。** Bento 和功能网格区块不能由 6 个白底白字的卡片组成。任何多单元格网格中，至少有 2-3 个单元格需要真正的视觉变化：真实图片、符合品牌的渐变（不能是 AI 紫色）、图案或有色背景。只有排版内容的奶油色背景 Bento 会显得乏味、像 AI 默认产物，即使页面其余部分做得很好。
* **必须明确每个区块在移动端的折叠方式。** 对于每个多列布局，都必须在同一组件中声明 `< 768px` 时的回退方案。不要假设“它会正常工作，Tailwind 会处理”。

### 4.8 图片与视觉资产策略

落地页和作品集是**视觉产品**。只有文本、用虚假截图 div 拼出来的页面属于低质量产物。

**视觉资产的优先级：**
1. **优先使用图像生成工具。** 如果环境中有任何图像生成工具（`generate_image`、MCP 图像工具、IDE 集成的生成工具、OpenAI 图像工具等），你**必须**使用它来创建针对各个区块的素材：主视觉摄影、产品图、纹理背景、氛围图。根据区块的需求生成正确的宽高比。不要因为手写 CSS 感觉更快就跳过这一步。
2. **其次使用真实的网络图片。** 没有图像生成工具时，使用真实的摄影素材来源。可接受的默认选项：
   * 占位摄影图使用 `https://picsum.photos/seed/{descriptive-seed}/{w}/{h}`（seed 应描述区块内容，例如 `marrow-cookware-kitchen`）
   * 需求中提供的实际图库或品牌 URL
   * 如果明确获准，可使用开放许可来源（通过直接 URL 使用 Unsplash、Pexels）
3. **最后的办法：告知用户。** 如果以上两种方式都无法使用，**不要**用手写的 SVG 插画或基于 div 的“虚假截图”填充页面。相反，应留下清晰标注的占位区域（`<!-- TODO: hero product photo, 1600x1200 -->`），并在响应末尾写上：*"This page needs real images at: \[list of placements\]. Please generate or provide them."*

**即使是极简网站也需要真实图片。** 纯文本页面不是极简主义，而是不完整的工作。即使是 Linear 风格的编辑式网站，也至少需要 2-3 张真实图片（主视觉、一张产品图或生活方式图片、一张辅助图片）。如果需求风格克制，就生成黑白极简摄影；不要因为整体风格低调就完全跳过图片。

**使用真实公司 Logo 展示社会认同。** 当需求要求设置“Trusted by / Used by / Customers”Logo 墙时，**不要**默认使用一排纯文本的品牌字标（`<span>Acme Co</span>`）。请使用真实的 SVG Logo：
* **来源：Simple Icons**（`https://cdn.simpleicons.org/{slug}/ffffff` 可用于任意颜色，或使用 `simple-icons` npm 包）。涵盖大多数知名品牌。
* **替代方案：devicon**，用于技术栈 Logo（使用 `@svgr/cli` 或 CDN）。
* **如果是自行创造的品牌名称，也要自行创造一个 SVG 标志。** 生成一个与页面风格一致的简单字母组合标志（圆形中的一个字母、两个字母的连字、抽象字形），并以内联 `<svg>` 的形式渲染。虚构品牌名称使用纯文本字标会显得很普通。
* **始终**确保 Logo 在浅色和深色模式下都能正常显示（深色背景使用白色、浅色背景使用黑色，或使用单色主题变量）。
* **仅 Logo 规则（强制）：** Logo 墙中只能有 Logo，不得包含其他内容。不要在每个 Logo 下方打印行业或类别标签（不要在 `Vercel` 下方加 `hosting`，不要在 `Stripe` 下方加 `payments`，不要在 `Cloudflare` 下方加 `infra`）。Logo 本身就是可信度的来源，标签不会增加用户已经知道的信息。可选：将品牌名称作为屏幕阅读器使用的 alt-text，可选：添加指向品牌网站的链接。仅此而已。

**手写插画：**
* 来自图标库的 SVG 图标：可以使用（参见第 3.C 节）。
* 手写的装饰性 SVG（自定义插画、Logo、标志）：**强烈不建议**，绝不应作为默认方案。仅在以下情况下可以接受：
  - 需求明确要求这样做（“为我绘制一个 SVG Logo”）
  - 这是一个单一且简单的几何标志（正方形、圆形、使用展示字体的字标）
  - 你确信最终输出质量可靠。

**基于 `div` 的伪截图已被禁止。** 用 `<div>` 矩形、伪任务列表、伪仪表盘、伪终端窗口渲染的“手工搭建产品预览”是明显破绽。若需要展示产品：
* 若存在真实截图 URL，则使用它
* 通过图像工具生成截图
* 使用真实组件预览（页面内实际可用的迷你版 UI）
* 或完全跳过预览，改用编辑摄影

**Hero 区域需要真实视觉素材。** 文字加渐变色块不是 Hero，只是占位符。

### 4.9 内容密度

落地页的价值在于**第一印象**，而不是完整阅读。果断删减。

* **每个区块的默认内容形式：** 简短标题（≤ 8 个词）+ 简短说明段落（≤ 25 个词）+ 一个视觉素材或一个 CTA。任何更多内容都必须由该区块的职责证明其合理性。
* **禁止数据倾倒型区块。** 20 行的出版物表格、30 行的获奖列表、营销页面上的巨型定价矩阵 = 错误的布局。请使用：
  - 3-5 个核心亮点 + “查看完整列表”链接
  - 用于展示广度的跑马灯 / 轮播
  - 如果数据本身就是产品，则使用完全不同的页面
* **长列表需要不同的 UI 组件，而不是更长的列表。** 默认的带项目符号的 `<ul>` / `divide-y` 行是偷懒的选择。如果项目超过 5 个，请改用以下方式之一：
  - 分组项目的双栏拆分布局
  - 每项包含图片 + 标签的卡片网格
  - 如果项目可分类，使用标签页 / 手风琴
  - 水平滚动吸附胶囊标签
  - 用于内容广泛列表的轮播（评价、标志、能力）
  - 用于“不需要逐项关注的大量内容”的跑马灯
  包含 10 行规格、每行下方都有细分隔线的规格表是最糟糕的默认方案。要么将行分为 2-3 个组，并使用稀疏的分隔线；要么改为每项规格一张卡片的布局。
* **尤其是规格表（Marrow-cookware 模式）。** 对于炊具 / 硬件 / 服装 / 手工艺品简介，带有每行 `border-b` 的长产品规格表是 AI 的默认产物。禁止使用。具体替代方案：
  - **双栏卡片网格：** 每项规格各占一张卡片，包含规格名称、数值（大号展示数字）以及一句“为何重要”的说明。桌面端双栏排列，移动端单栏。
  - **滚动吸附水平胶囊标签：** 每项规格是一个胶囊标签，用户可以横向滑动浏览。
  - **分组区块：** 将 10 项规格分为 3 个逻辑分组（例如“材料”、“烹饪”、“保修”），每个分组只使用一条柔和分隔线和一个分组标题。
  - **重点与其余内容：** 将 3-4 项核心规格展示为大型展示卡片，其余内容折叠在“查看完整规格”展开项下。

* **文案自查（发布前必须执行）：** 在宣布任何任务完成前，重新阅读页面上的每一条可见字符串（标题、副标题、眉题、按钮标签、正文、说明文字、替代文本、页脚文本、错误消息）。标记任何以下类型的字符串：
  - **语法错误**（“在它的过去中免费”、“有两个计划但其中一个是诚实的”、“把它放到桌面上”且脱离上下文）
  - **指代不清**（前文没有上下文却写“我们计划保持这种状态”）
  - **听起来像 AI 幻觉**（可爱但错误的文字游戏、不成立的牵强隐喻、“优雅的虚无”式短语）
  - **读起来像试图显得深刻的 LLM**（被动攻击式谦逊、伪工匠标签、装腔作势的微型元叙述）
  重写每一条被标记的字符串。如果不确定某个字符串是否通顺，就用朴素、功能性的句子替换。AI 生成的卖萌文案比平淡文案更糟糕。
* **伪精确数字会被标记。** 诸如 `92%`、`4.1×`、`48k`、`5.8 mm`、`13.4 lb` 的数字必须：
  - 来自真实数据（简介、品牌指南、公开指标）- 可以
  - 被明确标注为模拟数据（`<!-- mock -->`、“示例”、“样例数据”）- 可以
  - 如果只是 AI 编造的规格美学 - 禁止。不要伪造品牌未宣称的工程精度。
* **每个页面只使用一种文案语域。** 除非品牌语调明确要求，否则不要在同一构图中混用技术风格的等宽文本（“47 个任务 · 每天 0.6 次上下文切换”）、编辑式散文和营销式短句。

### 4.10 引用与用户评价

* 引用正文**最多 3 行**。绝不能是 6 行。如果原始引用更长 → 截短。落地页引用是片段，不是完整评价。
* 对于非常小的字号（例如页脚样式的用户评价），行数上限可以略微放宽。原则是：“一眼就能看完。”
* **引用文本中不得使用 em-dash 作为设计装饰**（长停顿、动态 em-dash、em-dash 项目符号）。参见第 9.G 节，em-dash 完全禁止。
* 署名：姓名 + 身份 + （可选）公司。绝不能只有姓名（“- Sarah”）。
* 引号：使用真正的排版引号（“ ”）或完全不使用引号。不能使用直引号 ASCII（" "）。

### 4.11 页面主题锁定（浅色 / 深色模式一致性）

页面只能有一个主题。各个区块不能交替反转。

* 如果页面是深色模式，**所有**区块都必须是深色模式。不能在深色区块之间夹入浅色、暖色纸张风格的区块（反之亦然）。用户不应在滚动过程中产生自己中途进入了另一个网站的感觉。
* 例外情况：如果 brief 明确要求使用“Color Block Story”或“Theme Switch on Scroll”手法，并且这是经过刻意设计的构图（每页进行一次完整的主题切换，并带有明显的过渡，而不是随机交替），则允许这样做一次。
* 默认行为：在页面级别选择浅色、深色或自动（`prefers-color-scheme`）主题，并将其锁定。同一主题家族内可以使用区块级背景色调（`bg-zinc-950` 紧邻 `bg-zinc-900`）；在一个 `bg-zinc-950` 页面中途切换到 `bg-amber-50` 则是错误的。
* 使用内置主题功能的设计系统（Radix Themes、带有 `<Theme>` 的 shadcn/ui）时，应在 `layout.tsx` 或页面根节点中设置一次主题。不要让单独的区块覆盖主题设置。

## 5. 上下文感知的主动性

这些是工具，而不是默认设置。只有当设计判断认为适合时才使用。**这些功能都不会自动触发。**

* **Liquid Glass / Glassmorphism：** 适用于高端消费品、Apple 相邻风格、奢侈品牌或媒体叠加风格。不适用于仪表板、公共部门或“无聊的 B2B”场景。使用时不要只停留在 `backdrop-blur`：添加 1px 内边框（`border-white/10`）和微妙的内阴影（`shadow-[inset_0_1px_0_rgba(255,255,255,0.1)]`），以实现真实的边缘折射效果。在 `prefers-reduced-transparency` 下提供纯色填充回退方案。
* **Magnetic Micro-physics：** 仅在 `MOTION_INTENSITY > 5` 且 brief 体现出高端、趣味或代理机构风格时使用。必须完全使用 Motion 的 `useMotionValue` / `useTransform`，并置于 React 渲染周期之外实现。绝不能使用 `useState`。参见第 3.B 节。
* **Perpetual Micro-Interactions**（Pulse、Typewriter、Float、Shimmer、Carousel）：仅在 `MOTION_INTENSITY > 5` 且区块确实能从动效中受益时使用（状态指示器、实时信息流、AI 感）。不是每张卡片都需要无限循环。如果区块用于传达信息，就让它保持静止。应用 Spring Physics（`type: "spring", stiffness: 100, damping: 20`），不要使用线性缓动。
* **“声称有动效，就必须展示动效。”** 如果 `MOTION_INTENSITY > 4`，页面必须实际产生运动：至少要有 hero 的进入过渡、关键区块的滚动显现，以及 CTA 的悬停物理效果。声称 `MOTION_INTENSITY: 7` 却提供静态页面，是错误的。反过来，如果无法在可用范围内交付正常工作的动效，就将数值调低到 3，并交付干净的静态页面。绝不要交付会出问题的半成品动效（被截断的 ScrollTriggers、跳动的进入动画、缺失的清理逻辑）。
* **动效必须有动机（强制要求）。** 添加任何动画前，都要先问：“这个动画传达了什么？”有效答案包括：层级（将注意力引向正确的对象）、叙事（按照符合故事线的顺序揭示内容）、反馈（确认用户操作）、状态转换（展示某些内容发生了变化）。无效答案是：“看起来很酷”。因为 GSAP 可用就到处使用 GSAP，是业余做法。每个 ScrollTrigger、每个 marquee、每个固定区块都必须有充分理由。如果无法用一句话说明理由，就删掉该动画。
* **MARQUEE 每页最多一个（强制要求）。** 水平滚动的文字 marquee（“无限滚动的 logos”、“横向滚动的 manifesto”、“动态文字条”）每页最多适合使用一次。同一页面出现两个或更多 marquee，会显得是在偷懒填充内容。选择一个 marquee 真正服务于内容的区块；其他区块使用不同的布局。
* **GSAP Sticky-Stack 模式（使用 scroll-stack 时）。** “滚动时的卡片堆叠”必须是真正的 sticky-stack，而不是按顺序显现的列表。参见第 5.A 节中的规范代码骨架。常见错误：触发器在滚动到一半时触发，而不是固定在视口顶部。修复方式：使用 `start: "top top"`，不要使用 `start: "top center"` 或 `"top 80%"`。
* **GSAP Horizontal-Pan 模式（使用横向滚动劫持时）。** 参见第 5.B 节中的规范骨架。常见错误：动画在区块固定之前就开始，因此用户会看到半个 slide。使用相同的修复方式：`start: "top top"`，固定 wrapper，让内部 track 进行 scrub。

### 5.A 粘性堆叠 - 规范骨架

规范 tsx 骨架：`references/motion-skeletons.md`。

关键点：`start: "top top"`、`pin: true`，除最后一张外的每张卡片均应固定，缩放/透明度变换由下一张卡片的滚动触发器驱动（因此下一张卡片到达时，前一张卡片会缩小）。

### 5.B 水平平移 - 规范骨架

规范 tsx 骨架：`references/motion-skeletons.md`。

关键点：`start: "top top"`、`pin: true`、`end: "+=${distance}"`（滚动长度 = 所需的水平移动距离）、`scrub: 1`。外层包装器会被固定，用户垂直滚动时，内部轨道会水平滑动。

### 5.C 滚动揭示错开动画 - 规范骨架（更轻量的替代方案）

对于简单的“项目进入视口时出现”效果（无需固定），优先使用 Motion 的 `whileInView`，而不是 GSAP；它更轻量，无需 ScrollTrigger：

规范 tsx 骨架：`references/motion-skeletons.md`。

适用场景：功能列表、客户评价网格、Logo 墙，以及任何只需要“滚动进入时显示”效果的内容。将 GSAP 留给真正需要固定/滚动同步的工作。

### 5.D 禁止的动画模式

* **`window.addEventListener("scroll", ...)`** 被禁止。它会在每个滚动帧运行，容易产生卡顿，且没有批处理。请使用 Motion 的 `useScroll()`、GSAP 的 `ScrollTrigger`、IntersectionObserver 或 CSS `scroll-driven animations`（`animation-timeline: view()`）。
* **在 React state 中使用 `window.scrollY` 进行自定义滚动进度计算。** 原因相同：每一帧都会重新渲染。
* **会触及 React state 的 `requestAnimationFrame` 循环。** 请改用 motion values（`useMotionValue` + `useTransform`）。
* **布局过渡：** 对可见状态变化（重新排序列表、展开模态框、路由之间的共享元素）使用 Motion 的 `layout` 和 `layoutId` props。不要为了“保险”而将静态内容包裹在 `layout` props 中，这会带来测量开销。
* **错开编排：** 对于序列顺序很重要的揭示时刻，使用 `staggerChildren`（Motion）或 CSS 级联（`animation-delay: calc(var(--index) * 100ms)`）。对于 `staggerChildren`，父级（`variants`）和子级必须共享同一个 Client Component 树。

## 6. 性能与可访问性护栏

### 6.A 硬件加速
* 仅动画化 `transform` 和 `opacity`。绝不要动画化 `top`、`left`、`width`、`height`。
* 谨慎使用 `will-change: transform`，仅应用于确实会发生动画的元素。

### 6.B 减少动态效果（强制要求）
* **任何高于 `MOTION_INTENSITY > 3` 的动态效果都必须遵循 `prefers-reduced-motion`。** 这不可协商。
* 在 Motion 中：使用 `useReducedMotion()` 包裹，并降级为静态效果。
* 在 CSS 中：通过 `@media (prefers-reduced-motion: no-preference)` 限制动画生效，或在 `@media (prefers-reduced-motion: reduce)` 下提供禁用动画的覆盖块。
* 无限循环、视差、滚动劫持和磁性物理效果在减少动态效果模式下必须降级为静态/即时效果。

### 6.C 深色模式（所有面向消费者的页面均为强制要求）
* 从一开始就为**两种模式**进行设计。未经用户明确指示，绝不要交付仅支持浅色或仅支持深色的版本。
* 对 token 使用 Tailwind `dark:` 变体或 CSS 变量。每个项目选择一种策略。
* **不要在这里规定具体的深色模式颜色。** 由设计简报决定。在两种模式下都应保持视觉层级、品牌标识和 WCAG AA 对比度（正文使用 AAA）。
* 遵循 `prefers-color-scheme: dark`。除非品牌坚持使用单一模式，否则默认采用系统偏好。

### 6.D Core Web Vitals 目标
* **LCP** < 2.5s。Hero 图片必须使用 `next/image priority` 或预加载。
* **INP** < 200ms。将繁重工作移出主线程。
* **CLS** < 0.1。为图片、字体、嵌入内容预留空间。
* 在宣布页面完成前运行 Lighthouse。

### 6.E DOM 成本
* 仅将颗粒 / 噪点滤镜应用于固定定位、`pointer-events-none` 的伪元素（例如 `fixed inset-0 z-[60] pointer-events-none`）。绝不要应用于滚动容器 - 持续的 GPU 重绘会摧毁移动端 FPS。
* 注意包体积。Motion 并不小。Three.js 很大。延迟加载所有不在首屏的内容。

### 6.F Z-Index 克制
绝不要滥用随意的 `z-50` 或 `z-10`。仅将 z-index 用于系统性的层级上下文（粘性导航栏、模态框、遮罩层、颗粒）。在项目常量文件中记录 z-index 层级规范。

## 7. DIAL 定义（技术参考）

### DESIGN_VARIANCE（等级 1-10）
* **1-3（可预测）：** 对称 CSS Grid（12 列、相等的 fr 单位）、相等的内边距、居中对齐。
* **4-7（偏移）：** `margin-top: -2rem` 重叠、不同的图片宽高比（4:3 紧邻 16:9）、左对齐标题置于居中对齐数据之上。
* **8-10（非对称）：** 瀑布流布局、采用分数单位的 CSS Grid（`grid-template-columns: 2fr 1fr 1fr`）、大面积留白区域（`padding-left: 20vw`）。
* **移动端覆盖：** 对于等级 4-10，`md:` 以上的非对称布局在视口 `< 768px` 时必须折叠为严格的单列布局（`w-full`、`px-4`、`py-8`）。

### MOTION_INTENSITY（等级 1-10）
* **1-3（静态）：** 不使用自动动画。仅使用 CSS `:hover` 和 `:active` 状态。无论如何，`prefers-reduced-motion` 都是默认模式。
* **4-7（流畅 CSS）：** `transition: all 0.3s cubic-bezier(0.16, 1, 0.3, 1)`。使用 `animation-delay` 级联实现加载入场效果。重点关注 `transform` 和 `opacity`。
* **8-10（高级编排）：** 复杂的滚动触发揭示、视差、滚动驱动动画（CSS `animation-timeline` 或 GSAP ScrollTrigger）。使用 Motion hooks。**绝不要使用 `window.addEventListener('scroll')`** - 这是硬性禁止，不是“尽量避免”。允许的替代方案请参见第 5.D 节。

### VISUAL_DENSITY（等级 1-10）
* **1-3（艺术画廊）：** 大量留白。巨大的分区间距（`py-32` 到 `py-48`）。昂贵、干净。
* **4-7（日常应用）：** 标准 Web 应用间距（`py-16` 到 `py-24`）。
* **8-10（驾驶舱）：** 紧凑的内边距。不使用卡片框；使用 1px 线条分隔数据。强制要求：所有数字使用 `font-mono`。

## 8. 深色模式协议

默认支持双模式。除非简报是模拟印刷品的编辑设计，否则绝不要假定仅支持浅色模式。

### 8.A Token 策略（选择一种并坚持使用）
* **Tailwind `dark:` variant**（实用优先项目的默认方案）：每个颜色实用类都应配对其深色变体（`bg-white dark:bg-zinc-950`、`text-gray-900 dark:text-gray-100`）。
* **CSS variables**（适用于 shadcn/ui、Radix Themes 或支持主题化的组件库）：定义语义 token（`--surface`、`--surface-elevated`、`--text-primary`、`--accent`），并在 `[data-theme="dark"]` 或 `@media (prefers-color-scheme: dark)` 下切换值。

### 8.B 不要在此处规定具体颜色
由需求说明和品牌决定。本技能仅强制要求：
* **对比度** - 正文文本最低达到 WCAG AA，主视觉文案以 AAA 为目标。
* **层级一致性** - 在浅色模式中有效的视觉层级，在深色模式中也必须有效。如果 CTA 在浅色模式中突出，它在深色模式中也应突出。
* **品牌保真度** - 主品牌色必须保持可识别性。不要为了深色模式而降低品牌色的饱和度。
* **不使用纯 `#000000`，也不使用纯 `#ffffff`** - 使用非纯黑（zinc-950、接近黑色的暖灰）和非纯白。纯色值会削弱层次感。

### 8.C 默认模式
除非品牌明确要求，否则应遵循 `prefers-color-scheme`。如果任一模式会损失关键的品牌表达，则添加手动切换开关。

### 8.D 完成前在两种模式下测试
开发期间应分别在两种模式下打开页面。不要发布仅在一种模式中查看过的页面。

## 9. AI 痕迹（禁止模式）

除非需求说明明确要求，否则避免以下特征。

### 9.A 视觉与 CSS
* 默认情况下**不要使用霓虹 / 外发光**。使用内边框或细微的染色阴影。
* **不要使用纯黑色（`#000000`）。** 使用非纯黑、zinc-950 或炭黑色。
* **不要使用过度饱和的强调色。** 降低饱和度，使其与中性色融合。
* **不要对大标题过度使用渐变文字**。
* **不要使用自定义鼠标光标。** 过时、对无障碍不友好、对性能不友好。

### 9.B 排版
* **避免默认使用 Inter。** 参见第 4.1 节。存在覆盖路径。
* **不要使用只会显得喧闹的超大 H1。** 使用字重 + 颜色控制层级，而不是单纯依赖尺寸。
* **衬线字体限制：** 衬线字体适用于编辑、奢侈品 / 高端、出版类场景。不适用于仪表盘。

### 9.C 布局与间距
* **数学上精确**的内边距和外边距。不要使用带有别扭空隙的悬浮元素。
* **不要使用三列等宽功能卡片。** 禁止使用通用的“三张完全相同的横向卡片”功能行。应使用双列交错布局、非对称网格、滚动固定或横向滚动等替代方案。

### 9.D 内容与数据（“Jane Doe”效应）
* **不要使用通用姓名。** “John Doe”、“Sarah Chan”、“Jack Su” → 使用有创意、真实可信、符合地区语境的姓名。
* **不要使用通用头像。** 不要使用 SVG“蛋形”头像或 Lucide 用户图标 → 使用可信的照片占位符或具体的样式设计。
* **不要使用虚假且完美的数字。** 避免 `99.99%`、`50%`、`1234567`。使用自然、有零散感的数据（`47.2%`、`+1 (312) 847-1928`）。
* **不要使用套路化的创业公司品牌名。** “Acme”、“Nexus”、“SmartFlow”、“Cloudly” → 创造与上下文契合、听起来真实且高端的名称。
* **不要使用填充性动词。** “Elevate”、“Seamless”、“Unleash”、“Next-Gen”、“Revolutionize” → 仅使用具体动词。

### 9.E 外部资源与组件
* **不要手写 SVG 图标。** 使用 Phosphor / HugeIcons / Radix / Tabler。仅在明确要求时使用 Lucide。
* 默认情况下，**强烈不建议手写装饰性 SVG**（参见第 4.8 节）。
* **不要使用基于 div 的伪截图。** 绝不要用 `<div>` 矩形搭建伪产品 UI 来模拟截图。应使用真实图片、生成的图片，或省略预览。
* **不要使用失效的 Unsplash 链接。** 使用 `https://picsum.photos/seed/{descriptive-string}/{w}/{h}`、生成的照片占位符或实际资源。
* **shadcn/ui 自定义：** 允许，但绝不能保持默认状态。根据项目美学自定义圆角、颜色、阴影和排版。
* **可投入生产的整洁度：** 代码在视觉上应整洁、令人印象深刻，并经过细致打磨。

### 9.F 生产测试痕迹（全面禁止）

这些模式来自真实的 LLM 生成落地页测试。当模型试图“让页面看起来像经过设计”时，默认会使用这些特征。除非 brief 明确要求其中某项，否则一律视为硬性禁用项。

**Hero 区域与页面顶部**
* **Hero 区域中不得使用版本标签。** `V0.6`、`v2.0`、`BETA`、`INVITE-ONLY PREVIEW`、`EARLY ACCESS`、`ALPHA`，这些作为默认眉题一律禁止。只有当 brief 明确围绕产品发布或预览状态展开时才可以使用。
* **不得使用“Brand · No. 01”风格的副眉题。** 例如“Marrow · No. 01 · The 6-quart”这类微型元信息行。跳过它们。

**章节编号与微型标签**
* **不得使用章节编号眉题。** `00 / INDEX`、`001 · Capabilities`、`002 · Featured commission`、`06 · how it works`、`05 · The honest table`，一律禁止。眉题应使用直白的主题名称，而不是进行编号。
* **图片或 bento 磁贴上不得使用 `01 / 4` 风格的分页标记。** 如果用户能数出来，就不需要这个标签。
* **不得使用 `Scroll · 001 Capabilities` 风格的滚动提示。** 一个简单的箭头或“Scroll”就足够了，不要加章节编号前缀。
* **不得使用“Index of Work, 2018 - 2026”风格的范围标签**作为眉题。直接说明该章节的内容。

**分隔符与圆点**
* **中点（`·`）需限制使用。** 元信息条中每行最多使用 1 个。不要将它作为所有内容的默认分隔符（“foo · bar · baz · qux · quux”）。如果需要一组分隔符，优先使用换行、细线或分栏。
* **不得在每个列表、导航项或徽章上使用装饰性的彩色状态圆点。** 例如在“ONE Q4 SLOT OPEN”前加彩色圆点，或在每个导航链接、每个任务行前加圆点，默认一律禁止。只有当圆点传达真实的语义状态（例如服务器状态、可用性标记），并且使用克制时才可以接受。

**破折号与排版装饰**
* **不得将长破折号（`—`）作为设计元素，也不得在其他任何地方使用。** 完整且不可协商的禁用规定见下方第 9.G 节。标题、眉题、胶囊标签、正文、引语、署名、说明文字、按钮文本和 alt 文本中均禁止使用长破折号字符。请使用普通连字符（`-`）。
* **不得默认使用通过 `<br>` 换行并配合斜体的标题**作为“设计手法”。例如将“for thirty\<br\>*years.*”这样的内容拆分。标题首先应自然流畅，只有在 brief 要求时才进行巧妙处理。
* **不得使用竖直旋转文本**（例如将“INDEX OF WORK, 2018 - 2026”旋转 90°）。这是代理机构作品集中的陈词滥调。只有当 brief 明确要求代理机构风格 / Awwwards / 实验性设计，并且它确实服务于构图目的时才可以使用。
* **不得使用十字准线 / 细线网格作为装饰。** 仅为让页面“看起来经过设计”而绘制的纵横线，一律禁止。只有在这些线条用于组织真实内容时才可以使用。

**虚假的产品预览**
* **Hero 区域中不得使用基于 div 构建的虚假产品 UI**（例如虚假的任务列表、虚假的终端、或完全由样式化 div 构成的虚假仪表板）。这是最典型的 LLM 设计痕迹。请使用真实截图、生成的图片、真实组件预览，或者完全不使用预览。
* **不得在虚假截图中使用虚假的版本页脚**（例如“v0.6.2-rc.1”或“last sync 4s ago · main”）。这毫无价值，只会暴露 AI 生成痕迹。

**营销文案特征**
* **禁止使用“Quietly in use at” / “Quietly trusted by”** 这类社会认同标题。请使用自然语言：“Trusted by”、“Used at”、“Customers include”，或者如果 Logo 本身已经足够表达，就完全省略标题。
* **禁止在引言、博客或侧边栏区块中使用“From the field” / “Field notes” / “Currently on the bench” / “On our desks” / “Loose plates”这类诗意标签**。这类表述读起来像是在刻意扮演工匠。请使用朴素、功能性的标签（“Testimonials”、“Latest writing”、“Now working on”），或者省略标签。
* **禁止在正文中使用“We respect the French ones”风格的**假谦逊行业梗。这种写法故作可爱，也很像 AI。
* **禁止在页眉/页脚加入天气 / 地点信息条**（“LIS 14:23 · 18°C”），除非简介明确围绕地点，或是一个跨时区分布的工作室。
* **禁止在眉题下方加入微型元说明句。**像 *“Each of these is a feature we ship today, not a roadmap promise. The list will stay short on purpose.”* 这样放在章节标题下的句子会显得杂乱。眉题 + 标题 + 正文已经足够。
* **禁止使用通用步骤标签。**“Stage 1 / Stage 2 / Stage 3”、“Step 1 / Step 2 / Step 3”、“Phase 01 / Phase 02 / Phase 03”、“Pass One / Pass Two / Pass Three”。全部禁止。实际的步骤内容就是标签。如必须展示流程，请直接使用动词-名词表达（“Install”、“Configure”、“Ship”），而不是“Stage 1: Install”。

**药丸标签、标签与版本标记**
* **禁止将药丸标签/标签/标记叠加在图片上。**不要在照片上用 `<span>` 叠加诸如 `Brand · 02`、`PLATE · BRAND`、`Field notes - journal` 的标签。要么让图片独自表达，要么在图片下方直接添加说明文字（置于图片外）。
* **禁止将图片署名说明作为装饰。**在图库/`picsum` 图片下使用 `Field study no. 12 · Ines Caetano`、`Plate 03 · House archive`、`Frame XII · 35mm` 之类的字符串显得矫饰。仅当确实需要为获得授权的真实照片署名给真实摄影师时，才允许图片署名。否则：省略说明，或使用一行功能性说明（“The 6-quart, in Sage.”）。
* **禁止在营销页面使用版本页脚。**诸如 `v1.4.2`、`Build 0048`、`last sync 4s ago · main` 的页脚字符串属于 CLI / 开发工具元素，而不是落地页内容。在营销页/落地页/作品集页面中禁止使用。
* **禁止将“Reservation 412 of 800”风格的实时库存计数器**作为装饰。仅当简介明确是带有真实数据的限量候补名单时才允许。

**装饰性文字条**
* **禁止在首屏底部使用装饰性文字条。**诸如 `BRAND. MOTION. SPATIAL.`、`TYPE / FORM / MOTION`、`DESIGN · BUILD · SHIP`、`ESTD. 2018 · LISBON · BRAND. MOTION. SPATIAL.` 的模式，即在首屏底部横跨一整行的小号等宽全大写文字条，是代理商作品集的陈词滥调。默认禁止。只有当该文字条承载真实、可导航的链接（固定底部导航），或真实状态信息（Cookie 横幅、文档站点中的构建信息）时才可接受。
* **禁止在章节标题中使用右上角悬浮的小段说明文字。**模式是：章节包含一个左对齐的大标题；同一章节标题区域的右上角，有一小段与其他任何元素都没有明确对齐关系的说明段落悬浮着。这个悬浮文本就是典型特征。要么把说明文字直接放在标题下方，要么构建整洁的双栏标题（左侧：标题，右侧：对齐的正文），但不要放置一小段角落文字。

**列表、分隔线和评分**
* **不要在长列表或规格表的每一行同时使用 `border-t` + `border-b`。** 选择一种方式（行与行之间使用底部边框，或在分组上方使用顶部边框），并谨慎使用。一个包含 10 行规格的表格，如果每行下面都有细线，是最偷懒的布局方式。请参见第 4.9 节中的替代 UI 组件。
* **不要使用带填充背景轨道的评分条或进度条**作为比较视觉元素。如果需要展示“Y 中的 X”这类比较，优先使用数字加小图标，或使用不带背景轨道的极小型行内条形图。在营销页中，大块填充的 `bg-zinc-200` 轨道上叠加部分填充，会造成仪表盘 UI 式的杂乱感。

**地区、时间和滚动提示**
* **99% 的需求都禁止使用地区、城市名称、时间或天气条。** 例如，在首屏主视觉中写“Lisbon，与创始人一起工作”，在页脚写“1200-690 Lisbon, Portugal”，或在导航中写“Lisbon 14:23 · 18°C”。这些都是机构作品集式装饰的典型特征。只有在以下情况下才允许使用：需求明确描述了需要关注时区工作的全球分布式工作室，或是以旅行​​为重点的品牌，或是真实存在的实体场所。页脚中单独提及一次联系地址没有问题，但不应使用营造氛围的地区信息条。
* **禁止使用滚动提示。** 例如 `Scroll`、`↓ scroll`、`Scroll to explore`、`Scroll to walk through it`，以及动画鼠标滚轮图标。如果用户还没有滚动，他们看到的就是首屏主视觉。他们知道滚动是什么。视口底部不需要标签。
* **默认完全禁止装饰性状态点。** 在导航项、列表行、徽章或状态标签前放置彩色圆点，是一种典型特征。只有在表达真实的语义状态时才可以接受，例如实际服务器状态的在线指示器或实时可用性标记，并且每个页面分区最多使用一个。

### 9.G 破折号禁用规则（最常见、最容易违反的特征）

**破折号（`—`）完全禁止使用。** 这是 LLM 标志性的语言习惯，也是生产测试中最明显的特征之一。不允许“有限使用”，也不允许“自然语言中偶尔使用”。完全不允许。

* **标题中禁止使用。** 使用句号或逗号。
* **眉题、标签、胶囊、按钮文本、图片说明和导航项中禁止使用。** 使用换行、分栏或细线替代。
* **正文中禁止使用。** 重构句子：使用句号拆成两个句子，或使用逗号、括号或冒号。
* **引用署名中禁止使用。** 使用带空格的普通连字符（` - `），或换行后使用较小字重的姓名。
* **用作分隔符时，同样禁止使用 en dash 形式（`–`）。** 日期范围（`2018-2026`）使用连字符。数字范围（`€40-80k`）使用连字符。

页面中唯一允许使用的短横线字符是：
* 普通连字符 `-`（用于复合词、范围、标记语言中的分隔线）
* 数学中的减号（`-5°C`）

只要输出中出现一个可见于用户的 `—` 或 `–`，就会无法通过发布前检查，必须重写。

这条规则不可协商。过去，代理在规则被表述为“谨慎使用”时经常忽略破折号限制。本规则的表述是二元的：零个破折号。

## 11. 重新设计协议

本技能同时处理**从零开始构建和重新设计**。错误判断模式是导致重新设计输出质量不佳的首要原因。

### 11.A 检测模式（第一步操作）
* **从零开始构建** - 没有现有网站，或已批准全面改版。根据第 1 节设定基线。
* **重新设计 - 保留** - 在不破坏品牌的前提下实现现代化。先进行审计，提取品牌令牌，逐步演进。
* **重新设计 - 全面改版** - 在现有内容之上采用新的视觉语言。视觉方面按从零开始构建处理；保留内容和 IA。

如有歧义，只询问**一次**：*"此次重新设计应保留现有品牌，还是我们要在视觉上从头开始？"*

### 11.B 修改前审计
在提出更改前记录当前状态：
* **品牌令牌** - 主色 / 强调色、字体栈、Logo 处理方式、圆角半径。
* **信息架构** - 页面树、主导航、关键转化路径。
* **内容区块** - 当前有哪些内容，哪些在发挥作用，哪些只是填充内容。
* **应保留的模式** - 标志性交互、可识别的 Hero 区域、文案语调。
* **应淘汰的模式** - AI 劣质内容迹象、破损布局、失效链接、通用素材图库图片、性能陷阱。
* **现有网站的拨盘读数** - 推断当前的 `DESIGN_VARIANCE` / `MOTION_INTENSITY` / `VISUAL_DENSITY`。这是你的起点，而不是基线。
* **SEO 基线** - 当前有排名的页面、meta 标题、结构化数据、OG 卡片。**SEO 迁移是重新设计的头号风险。**

### 11.C 保留规则
* 除非被要求，否则**不要更改信息架构**。保持页面 slug、锚点 ID、主导航标签稳定，以维护 SEO 和用户肌肉记忆。
* **在应用第 4.2 节之前提取品牌颜色。**已经是紫色的品牌仍应保持紫色 - 应用 LILA RULE 的覆盖规则。
* 除非被要求重写，否则**保留文案语调**。视觉现代化 ≠ 内容重写。
* **保留现有的无障碍优势。**不要削弱焦点状态、替代文本、键盘导航或对比度。
* **尊重现有的分析事件。**不要重命名下游跟踪所依赖的按钮、表单字段和区块 ID。

### 11.D 现代化手段（优先顺序）
按顺序应用 - 当需求已满足时停止：
1. **字体更新** - 单位风险带来最大的视觉提升。
2. **间距与节奏** - 增加区块内边距，修正垂直节奏。
3. **色彩重新校准** - 降低饱和度，统一中性色，保留品牌强调色。
4. **动效层** - 为现有组件添加与 `MOTION_INTENSITY` 相适应的微交互。
5. **Hero 区域与关键区块重新编排** - 使用 `references/pattern-vocabulary.md` 中的词汇重构漏斗顶部。
6. **完整区块替换** - 仅当现有区块无法挽救时使用。

### 11.E 决策树：定向演进与全面重新设计
* IA、内容和 SEO 状况良好 → **定向演进**（手段 1-4）。约以 40% 的风险获得 70% 的价值。
* 视觉债务具有结构性（IA 损坏、没有设计系统、移动端损坏） → **全面重新设计**，并严格保留内容。
* 品牌本身正在改变 → **从零开始构建**。

### 11.F 永远不会静默变更的内容
未经用户明确批准，绝不要修改：
* URL 结构 / route slugs。
* 主导航标签。
* 表单字段名称或顺序（会破坏分析数据和自动填充）。
* 品牌标志或字标。
* 现有的法律 / 同意 / Cookie 文案。

## 14. 最终起飞前检查

在输出代码之前运行此矩阵。这是最后一道过滤。
