# Break

此技能接收一个组件，并在所有实际能够到达该组件的场景下，将其渲染到一个全新的页面中。该页面就是交付物：一份供用户滚动查看的可视化报告，将每种状态并排展示，并标出发生的断裂点。针对单一路径构建的组件，在真实内容到来之前，看起来总是已经完成。

它负责观察，而不是评判。这里的发现，是指页面上确实出现了可见的破损，并使用负责修复该问题的领域技能所采用的术语来命名。根据标准审查代码属于 `interface-review` 和 `better-interface`；探索设计替代方案属于 `variant`。

`variant` 强调真实页面，而此技能则是有意进行隔离。你不评判组件在上下文中的表现，而是检查它在内容处于最坏情况时能否自我防护。

整个运行流程是构建、查看一次、报告：耗时几分钟，而不是一次完整的会话。工作内容只是使用不同的 props 渲染一个已有组件，其中没有任何事情值得进行插桩、浏览器调试或第二轮检查。

## 1. 确定一个组件的范围

每次运行只处理一个组件。“设置页面”不是一个组件；个人资料表单中的文本输入框才是。如果请求涉及多个组件，请列出候选项并询问要测试哪一个，而不是替用户自行选择。

用一句话重述组件是什么：它接受什么、渲染什么，以及将存在于什么位置。

## 2. 从组件推断场景

只对会发生变化的内容进行压力测试。当组件接受的内容在生产环境中确实可能呈现某种形态时，该场景才值得占用一个位置。因此要先阅读组件：它的 props、插槽、状态以及所渲染的数据。

[scenarios.md](scenarios.md) 保存了各个维度、每个维度上的取值，以及用于判断某个维度是否适用的提示。将它与组件逐项对照，只保留提示与组件匹配的维度。文本输入框需要测试内容长度和状态，而不需要测试项目数量。带有固定标签的静态图标按钮需要测试容器和环境，而不需要测试长文本。

在构建之前写下保留的场景，每行一个，这样测试页面渲染的是一组经过规划的集合，而不是临时想到什么就渲染什么。然后用一行说明舍弃了哪些维度以及原因，这样一旦推断错误，就能低成本发现。

## 3. 构建测试页面

创建一个一次性页面，从项目中导入真实组件，在单列中针对每个场景各渲染一次，并在每个实例上方放置一段简短的文字标签。

组件应保持原样，并处于真实环境中。应用内部的临时路由可以免费为它提供应用自身的布局、字体和全局样式。页面额外添加的内容只有标签、容器宽度和 fixture props：不能有页面自带的字体或样式，不能模拟主题或替换 token，也不能添加探针。在这些条件下观察到的组件，已经是另一个组件。

如果框架将服务器组件与客户端组件分开，页面本身应是客户端代码；在 Next 中使用 `"use client"`。Fixture props 在跨越边界进入交互式组件时可能会悄悄消失，导致每个场景都渲染为空。

宽度就是页面上的场景。将不同宽度的情况渲染在全宽场景旁边的固定宽度容器中，这样一次加载就能展示所有宽度，并且任何内容都不会被调整大小。

将场景作为 props 和 fixture 数据传入。测试线束绝不导入生产状态，绝不连接实时数据，生产代码也绝不从测试线束中导入任何内容。

## 4. 只看一次

只进行一轮。使用手边已有的浏览器加载页面，从上到下浏览每个场景，并记录所有明显出问题的地方。“文本从字段右边缘溢出”，不要写成“间距感觉很紧”。从未渲染成功的运行，只是披着伪装的代码审查；而预测中的失败，仍然不算发现。

一次加载就是预算。如果没有浏览器，或者需要启动浏览器、调整窗口，或进行任何调试，就完全跳过查看：交出 URL，让用户亲自观察。反正他们的查看比你的更有价值，因为页面是给他们阅读的。

然后，在页面上标记你确实看到的每个问题：在对应场景标签下方添加一行备注，并在一次编辑中完成。页面本身必须能够作为报告来阅读。

## 5. 报告出现的问题，然后停止

以表格形式报告发现的问题，并将出问题的场景放在前面：

| 场景 | 观察结果 | 负责方 |
| --- | --- | --- |
| 一个无法断开的 60 个字符的字符串 | 溢出卡片，既不换行也不截断 | `better-typography` |
| 零个项目 | 空白区域，没有任何消息 | `better-writing` |

负责方列应填写其规则能够诊断该问题的领域技能名称，以便从正确的位置开始修复。本技能不负责任何领域规则，也不做任何判定。

“一切都正常”是一份完整且有用的报告。说明页面上有哪些场景以及页面运行在哪里，让用户可以亲自查看每一个场景。到此为止，不要再用偏好之类的内容来填充结果。

不要修复任何未被要求修复的问题。收到修复请求后，遵循负责方技能的规则，然后重新渲染失败的场景以确认修复结果。

## 6. 保持页面运行，收到请求后再删除

页面是报告的一半，因此它的存续时间应超过发现问题的表格。保持页面运行，只有在用户表示已经用完后，才删除页面及其 fixture。

## 在完成之前

| 错误 | 修复 |
| --- | --- |
| 每个轴都针对每个组件运行 | 只保留提示与之匹配的轴，并说明舍弃了哪些轴 |
| 将预测中的失败报告为已观察到的失败 | 渲染它，否则不要写入报告 |
| 场景缺少传入给它的内容 | 测试线束坏了，不是组件坏了；让页面客户端代码显示内容，然后重新检查 |
| 在测试线束中重建一个外观相似的组件 | 从项目中导入真实组件 |
| 测试线束重新设置组件样式或主题 | 使用应用原本的布局、字体和 token；标签和宽度是页面唯一添加的内容 |
| 针对每个场景分别启动浏览器、调试或截图 | 一次加载并查看一次，或者交出 URL 并跳过查看 |
| 用品味来措辞描述发现的问题 | 报告页面上实际可见的内容，否则什么都不要报告 |
| 报告问题却没有指定负责方 | 指出其规则能够诊断该问题的领域技能 |
| 在一次干净的运行结果中填充建议 | “一切都正常”加上场景列表就是报告 |
| 逐个场景调整视口大小 | 宽度应当是页面上的固定容器；一次加载即可展示所有宽度 |
| 表格中报告了问题，却没有在页面上标记 | 在场景标签下方添加备注；页面本身要能作为报告来阅读 |
| 在报告的同一轮操作中删除页面 | 页面是报告的一半；只有在用户表示可以删除后才删除 |
