# Break

此 skill 接受一个组件，并在每个实际能够到达该组件的场景下，将其渲染到一个全新的页面上。该页面就是交付物：一份供用户滚动浏览的可视化报告，其中每种状态并排展示，并标出发生的破坏。基于单一理想路径构建的组件，在真实内容到来之前，看起来总是已经完成。

它负责观察，而不是评判。这里的发现，是页面上确实发生了可见破坏的问题，并使用负责修复该问题的领域 skill 的术语来命名。根据标准审查代码属于 `interface-review` 和 `better-interface`；探索设计替代方案属于 `variant`。

`variant` 坚持使用真实页面，而此 skill 则有意进行隔离。你不是在判断组件放入上下文后的外观，而是在检查当内容处于最坏情况时，它能否自我防护。

整个运行流程是构建、查看一次、报告：耗时几分钟，而不是一次完整会话。工作内容是使用不同的 props 渲染一个现有组件，其中没有任何事情值得进行埋点、浏览器调试或第二轮检查。

## 1. 确定一个组件

每次运行只处理一个组件。“设置页面”不是一个组件；个人资料表单中的文本输入框才是。如果请求涉及多个组件，请列出候选项并询问要测试哪一个，而不是替用户做决定。

用一句话重述组件是什么：它接受什么、渲染什么，以及它将位于哪里。

## 2. 从组件推断场景

只对会发生变化的部分进行压力测试。当组件接受的内容在生产环境中可能呈现某种形态时，该场景才值得占据一个位置。因此要先阅读组件：它的 props、插槽、状态以及它所渲染的数据。

[scenarios.md](scenarios.md) 中列出了各个维度、每个维度的取值，以及用于说明某个维度是否适用的提示。将其与组件逐项对照，只保留提示与组件匹配的维度。文本输入框需要测试内容长度和状态，而不需要测试项目数量。带有固定标签的静态图标按钮需要测试容器和环境，而不需要测试长文本。

在构建之前，先将保留的场景写下来，每行一个，这样 harness 渲染的是经过规划的一组场景，而不是临时想到什么就渲染什么。然后用一行说明舍弃了哪些维度以及原因，这样一旦推断错误，就能以较低成本发现。

## 3. 构建 harness 页面

创建一个一次性页面，从项目中导入真实组件，在单列中为每个场景各渲染一次，并在每个实例上方放置一段简短的文本标签。

组件保持原样，在其真实环境中运行。应用内部的临时路由可以免费为它提供应用自身的布局、字体和全局样式。页面额外添加的内容只有标签、容器宽度和 fixture props：不要添加页面自身的字体或样式，不要模拟主题或替换 token，不要添加探针。在这些条件下观察到的组件，已经是另一个组件。

如果框架将服务器组件与客户端组件分开，则页面本身必须是客户端代码，在 Next 中使用 `"use client"`。fixture props 跨越边界传入交互式组件时可能会静默消失，导致每个场景都渲染为空。

宽度是页面上的场景。将各种宽度案例渲染在全宽案例旁的固定宽度容器中，这样一次加载就能展示所有宽度，并且不会发生任何调整大小的情况。

将场景作为 props 和 fixture 数据传入。测试框架从不导入生产状态，从不连接实时数据，生产代码也从不从测试框架导入内容。

## 4. 看一次

只进行一轮。使用手头已经打开的浏览器加载页面，从上到下浏览每个场景，并记录肉眼可见的所有问题。写“文本溢出字段右边缘”，不要写“间距感觉太紧”。从未实际渲染过的运行，只是披着外衣的代码审查；预测出的失败也仍然不算发现。

一次加载就是预算。当没有浏览器，或者需要启动浏览器、调整窗口，或进行任何调试时，完全跳过查看：交出 URL，让用户亲自观察。反正他们的查看比你的更有价值，因为页面是他们要阅读的。

然后在页面上标记你确实看到的每个问题：在对应场景标签下方用一行简短说明，并在一次编辑中完成。页面本身必须能够作为报告独立阅读。

## 5. 报告出现的问题，然后停止

以表格形式报告发现的问题，并将出现问题的场景放在前面：

| 场景 | 观察结果 | 负责人 |
| --- | --- | --- |
| 一个无法断开的 60 字符字符串 | 溢出卡片，既不换行也不截断 | `better-typography` |
| 零个项目 | 空白区域，没有任何消息 | `better-writing` |

负责人列写明负责诊断该问题的领域技能，以便从正确的位置开始修复。本技能不拥有任何领域规则，也不下结论。

“全部通过”是一份完整且有用的报告。说明页面上有哪些场景以及页面运行在哪里，让用户可以亲自查看每一个场景。到此为止，不要再用个人偏好填充结果。

不要修复任何未被要求修复的问题。收到修复请求后，遵循负责人的规则，然后重新渲染失败的场景进行确认。

## 6. 保持页面运行，按请求删除

页面是报告的一半，因此它的生命周期应当长于发现问题的表格。保持页面运行，只有当用户说他们已经用完时，才删除页面及其 fixture。

## 完成前

| 错误 | 修复 |
| --- | --- |
| 每个轴都针对每个组件运行 | 只保留提示与之匹配的轴，并说明你舍弃了哪些轴 |
| 将预测出的失败报告为已观察到的失败 | 渲染它，否则不要写入报告 |
| 场景缺少传入给它的内容 | 测试框架坏了，而不是组件坏了；让页面客户端代码正常工作，然后重新检查 |
| 在测试框架中重建一个外观相似的组件 | 从项目中导入真实组件 |
| 测试框架重新设置组件的样式或主题 | 保持应用原有的布局、字体和设计令牌；标签和宽度是页面唯一添加的内容 |
| 针对每个场景启动浏览器、调试或截图 | 一次加载、一次查看；或者交出 URL 并跳过查看 |
| 用品味来措辞描述发现的问题 | 报告页面上可见的内容，否则什么也不要报告 |
| 报告了问题却没有指定负责人 | 指明负责诊断该问题的领域技能 |
| 在一次干净的运行结果中填充建议 | “全部通过”加上场景列表就是报告 |
| 逐个场景调整视口大小 | 宽度应当是页面上的固定容器；一次加载展示全部场景 |
| 表格中报告了问题，却没有在页面上标记 | 在场景标签下方记下该问题；页面本身应当能够作为报告独立阅读 |
| 在报告的同一轮操作中删除页面 | 页面是报告的一半；只有在用户明确表示后才删除 |
