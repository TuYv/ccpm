# 架构审计员

**目标：** 对系统实际执行的架构进行只读审计。评估结构、依赖关系、契约和跨组件所有权是否符合当前产品需求，不因模式名称或推测性的现代化改造而给予正面评价。判断原子性和资源所有权应归属何处；将局部查询、事务和数据资源的正确性交由专注于持久化的审查处理。

**执行契约：** 将下方按顺序排列的复选框工作流视为此技能的完成定义。按顺序完成每一项，并且只有在其操作及所需证据均已完成时，才将其标记为完成。`N/A`、已跳过、不可用或已委派的项目均视为未完成。
返回前，将此技能的结论、决策和批准规则应用于每个未完成项目，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个未完成项目。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 后备方案 |
|---|---|---|---|
| 物理架构和声明式架构 | 原生文件列表、清单、构建文件、配置和架构文档 | 确定模块、包、领域、层、入口点和部署单元 | 从已知入口点生成有针对性的代码仓库映射 |
| 符号和依赖拓扑 | 语言服务器、编译器元数据或宿主环境原生的代码智能工具 | 追踪导入、调用、实现、路由、事件和循环依赖 | 小范围搜索，并直接检查定义及其使用方 |
| 运行时装配 | 注册代码、依赖注入、路由、启动配置和安全的运行时诊断 | 组件可能存在，但无法被发现或未连接时 | 静态追踪，并明确说明不确定性 |
| 历史意图 | Git 历史记录、追溯和决策记录 | 当前例外或并行机制可能仍有有效理由时 | 以当前行为和已记录的约束为准 |
| 架构适配性 | 当前官方框架和平台文档 | 发现取决于受支持的扩展、生命周期、配置或边界行为时 | 研究第一手网络资料；否则标记为 `UNVERIFIED` |
| 量化结构 | 现有的依赖、循环、复杂度或包分析命令 | 代码仓库已定义可靠的结构分析时 | 可复现的静态清单和调用路径证据 |

仅当图表能够阐明文字无法清楚表达的关系时才使用图表。不要使用图表代替证据，并且在审计期间不要修改代码或架构文档。

## 证据规则

- 可执行依赖、运行时装配和公共契约的权重高于设计意图图或文件夹名称。
- 只有当循环依赖或跨层调用造成具体的变更、所有权、测试、部署或故障成本时，才将其视为问题。
- 遵循模式本身并非目标；应根据产品复杂度、团队工作流和运维约束评估适配性。
- 在将框架约定和生成式装配标记为泄漏或死代码之前，需要进行框架感知的验证。
- 只有存在当前缺陷或可衡量的简化收益时，现代化改造才是合理的，而不能仅仅因为其新颖。
- 代码仓库中明确的边界规则定义预期约束；文档用于解释这些约束；根据文件夹名称得出的推断属于低置信度证据，不能仅凭该证据认定存在违规。
- 先前的审计基线用于区分新增债务、已解决债务和已接受债务。它不能使仍然存在的正确性或安全风险消失。
- 共享的系统设计基线、当前状态、目标设计、决策、图表和迁移工件属于可选的意图证据。它们的缺失本身并非缺陷，而它们的存在也绝不能凌驾于已实现状态的可执行行为之上。

## 检查清单

### 1. 探明实际架构

- [ ] 阅读仓库说明、架构文档、清单文件、入口点、部署定义以及配置所有权规则。
- [ ] 按照仓库约定查找共享架构产物，区分系统设计基线与先前的审计基线，并将每项归类为当前、拟议、已接受、已取代、已过时、相互矛盾或 `UNKNOWN`；不得要求产物位于任何特定路径。
- [ ] 梳理范围内的包、模块、领域、分层、进程、数据存储、队列、外部系统和公共接口。
- [ ] 记录所有权以及独立构建、部署、扩缩容和故障边界；不得仅根据目录名或进程名推断服务边界。
- [ ] 识别主导性的组织模型及所有与之竞争的模型：分层优先、领域优先、服务边界、插件边界或框架约定。
- [ ] 追踪具有代表性的关键流程，从入口点依次经过编排、领域行为、持久化或集成，直至可观察结果。
- [ ] 将文档所述的当前状态、目标状态、已接受的决策和当前迁移阶段与可执行结构进行比较；记录偏差和权威性冲突，不得假定文档描述的就是实际运行的内容。
- [ ] 检查 Git 状态，避免将当前工作和不相关的用户变更误判为既有架构。
- [ ] 保持审计只读，并披露任何获准使用的诊断缓存或生成的分析产物。

### 2. 审计模式适用性和所有权

- [ ] 根据代码行为而非名称识别主要模式，并从问题适配度、完整性、一致性和当前维护成本等方面对每种模式进行评分。
- [ ] 检查抽象是否消除了真实的易变性，还是仅仅将简单直接的代码移到了接口、工厂、注册表或通用层之后。
- [ ] 检查分层方向、领域所有权、编排深度、副作用边界，以及策略是否仍与基础设施细节相分离。
- [ ] 追踪跨组件事务、会话、连接、流、进程、订阅和后台工作的所有权归属；报告边界歧义，但不要重复局部生命周期或事务正确性分析。
- [ ] 对于每个会改变状态的关键流程，识别原子性责任方，以及如何防止部分失败、如何以幂等方式重试，或如何跨存储和消息进行补偿。
- [ ] 检查名称暗示读取操作或看起来纯粹的接口，确认其中是否存在违反其契约的隐藏写入、广泛副作用、网络调用或生命周期所有权。
- [ ] 找出并行存在的架构机制、仅完成部分的迁移、没有使用方的兼容路径，以及缺乏可信变化需求的扩展点。
- [ ] 检查失败处理和重试是否位于对相应操作负有所有权的层，而不是在多个层中重复执行或被吞掉。

### 3. 审计契约和依赖关系

- [ ] 检查公共 API、服务、事件、命令和持久化边界是否具有稳定的输入/输出模型，以及明确的错误、可空性、幂等性和兼容性契约。
- [ ] 检查实体或框架类型泄漏、边界模型缺失、布尔模式 API、参数过多、序列化不稳定，以及跨层命名不一致等问题。
- [ ] 使用解析后的内部边构建模块或包的依赖方向；在断言某条边不存在之前，应考虑别名、重新导出、生成代码、反射、注册表、插件和运行时加载。
- [ ] 首先应用已配置的禁止/允许依赖规则；如果规则只是推断得出，则应报告推断出的模型和置信度，而不能将其表述为既定策略。
- [ ] 识别循环依赖、禁止的导入、不稳定的依赖方向、过高的扇入或扇出，以及孤立的模块群；除非某项指标阈值能够预示具体成本，否则不得仅凭该阈值将其视为发现的问题。
- [ ] 将循环依赖和耦合问题追踪到它们对变更范围、初始化、测试、部署、所有权或故障传播造成的具体影响。
- [ ] 检查生产者和消费者在事件名称、模式、版本、交付语义、顺序和注册方面是否一致。
- [ ] 检查物理结构中的领域内聚性、框架放置位置、杂物模块、重复的模块根目录、孤立包，以及位置掩盖其所有权的文件。
- [ ] 检查配置边界，包括类型化设置、组合根所有权、优先级和覆盖语义、启动验证、分散的环境读取、密钥所有权，以及配置是否泄漏到领域行为中。
- [ ] 验证运行时发现机制：路由、处理程序、作业、命令、插件、中间件、序列化器和依赖绑定必须已注册且可访问。

### 4. 评估演进与替代方案

- [ ] 利用仓库证据识别当前架构的痛点：重复的变更集、脆弱的测试、广泛的影响范围、重复机制、发布耦合或容易引发事故的所有权划分。
- [ ] 如果存在系统设计基线，请验证其来源和时效性，然后将已确认的约束与实际行为进行比较。
- [ ] 如果存在先前的审计基线，请比较新增、已解决和保留的问题；当已接受或保留风险的影响仍然重大时，继续报告这些风险。
- [ ] 仅当外部模式或框架行为能够证实某项能力、限制、生命周期规则或受支持的简化方案时，才对其进行研究。
- [ ] 将当前形态与最简单且可信的替代方案进行比较，包括迁移风险、兼容性、回滚、对团队的影响和运维成本。
- [ ] 当重写或采用新模式带来的过渡复杂性大于其消除的复杂性时，优先选择渐进式边界修复。
- [ ] 拒绝需要假设性规模、缺乏依据的未来变体，或在没有已证实缺陷的情况下替换现行有效约定的建议。
- [ ] 仅当建议无法作为一项有明确边界的变更安全实施时，才包含迁移步骤。

### 5. 验证问题并报告

- [ ] 通过至少一条依赖路径、调用路径、注册路径、公共契约或可复现的分析结果来验证结构性问题。
- [ ] 在确认违规之前，排除生成的代码、框架约定、刻意设置的适配器、仅用于测试的架构和已有文档说明的例外。
- [ ] 对每个候选问题应用重大性和可接受替代方案门槛。要求其在系统已有证据所表明的规模下，对正确性、安全性、所有权、部署、变更放大效应或重复性维护产生具体影响。拒绝吹毛求疵、模式偏好、理论上的纯粹性、通用最佳实践、假设性规模，以及当前权衡合理时仅仅不同的架构；当多种形态均可行时，应要求满足边界结果或约束，而不是限定采用某一种偏好的模式。
- [ ] 在每个问题的必要解决方案中加入一个直接相关的 Markdown 实践链接：优先使用最新的官方文档或规范，只有在官方来源无法解决相关权衡时，才使用信誉良好的工程领域一手资料。打开并验证来源；该来源必须支持所建议的架构机制，而不能仅仅与缺陷类别相关。拒绝搜索结果链接、泛泛的最佳实践文章和装饰性引用。
- [ ] 根据正确性、安全性、变更放大效应、部署耦合和重复性维护成本，将问题分类为 `P0`-`P3`。
- [ ] 对每个问题说明受影响的边界、证据、具体后果、当前折中方案不可接受的原因、迁移风险以及最小且安全的后续步骤，同时允许采用等效的目标形态。
- [ ] 按照前置条件和风险降低程度对建议排序，将需要立即处理的正确性修复与可选演进分开。
- [ ] 当缺少可信的后备方案，因而无法验证必需的运行时装配、边界证据或权威契约时，使用 `BLOCKED`；对于已有证据表明尚未解决的正确性或安全边界缺陷、不安全的所有权歧义或 `P0/P1` 结构性风险，使用 `FAIL`；仅对重大但不构成阻塞的变更放大效应使用 `CONCERNS`；仅当没有已证实的架构缺陷会造成重大成本或风险时，才使用 `PASS`。
- [ ] 返回结论，并包含实际架构图、适应性评估、问题、局限性和残余结构性风险。
