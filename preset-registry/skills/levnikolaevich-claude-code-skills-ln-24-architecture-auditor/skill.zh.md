# 架构审计员

**目标：** 对系统实际执行的架构进行只读审计。评估结构、依赖关系、契约以及跨组件所有权是否符合当前产品需求，不因模式名称或推测性的现代化改造而给予额外评价。判断原子性和资源所有权应归属何处；将局部查询、事务和数据资源正确性交由以持久化为重点的审查负责。

**执行契约：** 将下方有序复选框工作流视为此技能的完成定义。将每个复选框追踪为 `PENDING`，然后使用具体证据将其解析为 `PROVEN`，使用证明其条件触发器不存在的证据将其解析为 `CLEARED`，或解析为 `UNPROVEN`；阅读、提及、委派、跳过或工具失败都不能作为证明。
返回前，解析所有 `PENDING`，仅将 `PROVEN` 和 `CLEARED` 项计为已完成，将此技能的裁决、决策和批准规则应用于每个 `UNPROVEN`，并在开头添加 **Checklist: X/Y complete**<br>**Incomplete: None | section/item — reason; outcome impact; exact next action**；列出每个 `UNPROVEN` 项。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 物理架构和声明式架构 | 原生文件列表、清单文件、构建文件、配置以及架构文档 | 确定模块、包、领域、分层、入口点和部署单元时 | 基于已知入口点的定向仓库映射 |
| 符号和依赖拓扑 | 语言服务器、编译器元数据或宿主原生代码智能工具 | 跟踪导入、调用、实现、路由、事件和循环时 | 缩小搜索范围，并直接检查定义及其使用者 |
| 运行时连接 | 注册代码、依赖注入、路由、启动配置以及安全的运行时诊断 | 某个组件可能存在但无法被发现或连接时 | 使用明确的不确定性进行静态追踪 |
| 历史意图 | Git 历史、blame 和决策记录 | 当前例外或并行机制可能仍有有效理由时 | 当前行为和已记录的约束仍具有权威性 |
| 架构适配性 | 当前官方框架和平台文档 | 某项发现取决于受支持的扩展点、生命周期、配置或边界行为时 | 基于一手来源的网络研究；否则标记为 `UNVERIFIED` |
| 定量结构 | 现有的依赖、循环、复杂度或包分析命令 | 仓库已经定义了可靠的结构分析时 | 可复现的静态清单和调用路径证据 |

仅在图示能够阐明文字无法清晰表达的关系时使用图示。不要生成图示来替代证据，也不要在审计期间修改代码或架构文档。

## 证据规则

- 可执行依赖、运行时连接和公共契约的权重高于预期中的图示或文件夹名称。
- 只有当循环或跨层调用造成具体的变更、所有权、测试、部署或故障成本时，才将其视为发现。
- 模式合规本身不是目标；应根据产品复杂度、团队工作流和运营约束评估适配性。
- 框架约定和生成的连接在被标记为泄漏或死代码之前，需要进行框架感知的验证。
- 只有当前存在的缺陷或可衡量的简化才能证明现代化改造的合理性，而不是新颖性。
- 明确的仓库边界规则定义预期约束；文档对其进行解释；从文件夹名称推断属于低置信度证据，不能仅凭此推断产生违规。
- 之前的审计基线用于区分新增、已解决和已接受的债务。它不会使当前存在的正确性或安全风险消失。
- 共享的系统设计基线、当前状态、目标设计、决策、图示和迁移工件均属于可选的意图证据。它们缺失本身不是缺陷，其存在也绝不会在已实现状态方面超越可执行行为。

## 检查清单

### 1. 发现实际架构

- [ ] 阅读仓库说明、架构文档、清单文件、入口点、部署定义以及配置所有权规则。
- [ ] 按仓库约定发现共享架构产物，区分系统设计基线与先前审计基线，并将每项分类为当前、提议、已接受、已取代、过时、相互矛盾或 `UNKNOWN`；不要要求任何特定的产物路径。
- [ ] 映射范围内的包、模块、领域、层、进程、数据存储、队列、外部系统和公共接口。
- [ ] 记录所有权以及独立构建、部署、扩缩容和故障边界；不要仅凭目录名或进程名推断服务边界。
- [ ] 识别主要的组织模型及任何相互竞争的模型：按层优先、按领域优先、服务边界、插件边界或框架约定。
- [ ] 从入口点开始，经过编排、领域行为、持久化或集成，直到可观测结果，追踪具有代表性的关键流程。
- [ ] 将文档记录的当前状态、目标状态、已接受的决策和当前迁移阶段与可执行结构进行比较；记录偏差和权威冲突，不要假定文档描述的就是实际运行的内容。
- [ ] 检查 Git 状态，避免将当前工作和用户无关的变更误判为既定架构。
- [ ] 保持审计为只读，并披露任何获准使用的诊断缓存或生成的分析产物。

### 2. 审计模式适配性与所有权

- [ ] 根据代码行为而非名称识别主要模式，并从问题适配性、完整性、一致性和当前维护成本四个方面对每种模式进行评分。
- [ ] 检查抽象是否消除了真实的易变性，还是只是将直白的代码隐藏在接口、工厂、注册表或通用层之后。
- [ ] 检查层级方向、领域所有权、编排深度、副作用边界，以及策略是否仍与基础设施细节分离。
- [ ] 追踪跨组件事务、会话、连接、流、进程、订阅和后台工作的所有权位置；报告边界歧义，但不要重复局部生命周期或事务正确性分析。
- [ ] 对于每个会改变状态的关键流程，识别原子性所有者，以及如何在多个存储和消息之间防止部分失败、以幂等方式重试或进行补偿。
- [ ] 检查名称表示读取或看似纯粹的接口是否存在隐藏写入、广泛副作用、网络调用或违反其契约的生命周期所有权。
- [ ] 找出并行的架构机制、未完成的迁移、没有消费者的兼容路径，以及没有可信变化需求的扩展点。
- [ ] 检查故障处理和重试是否位于拥有该操作的层中，而不是在各层之间重复或被吞掉。

### 3. 审计契约与依赖

- [ ] 检查公共 API、服务、事件、命令和持久化边界是否具有稳定的输入/输出模型，以及明确的错误、可空性、幂等性和兼容性契约。
- [ ] 检查实体或框架类型泄漏、缺失的边界模型、布尔模式 API、过多参数、不稳定的序列化，以及各层之间不一致的命名。
- [ ] 使用已解析的内部边来构建模块或包的依赖方向；在声明某条边不存在之前，考虑别名、重新导出、生成代码、反射、注册表、插件和运行时加载。
- [ ] 优先应用已配置的禁止/允许依赖规则；如果规则仅为推断所得，应报告推断出的模型及其置信度，而不是将其表述为政策。
- [ ] 识别循环依赖、禁止导入、不稳定的依赖方向、过高的扇入或扇出，以及没有将度量阈值作为发现依据的孤立模块；只有当某项指标能够预测具体成本时，才将其视为发现。
- [ ] 将循环和耦合发现追溯到对变更范围、初始化、测试、部署、所有权或故障传播的具体影响。
- [ ] 检查生产者和消费者是否在事件名称、模式、版本、交付语义、顺序和注册方面达成一致。
- [ ] 检查物理结构中的领域内聚性、框架放置位置、杂物抽屉式模块、重复的模块根目录、孤立包，以及位置掩盖所有权的文件。
- [ ] 检查配置边界中的类型化设置、组合根所有权、优先级和覆盖语义、启动校验、分散的环境变量读取、密钥所有权，以及配置泄漏到领域行为中的情况。
- [ ] 验证运行时发现机制：路由、处理器、作业、命令、插件、中间件、序列化器和依赖绑定都必须完成注册并且可达。

### 4. 评估演进方向与替代方案

- [ ] 基于仓库证据识别当前架构痛点：重复的变更集、脆弱的测试、过大的影响范围、重复的机制、发布耦合，或容易引发事故的责任归属。
- [ ] 如果存在系统设计基线，验证其来源和时效性，然后将已确认的约束与实际行为进行比较。
- [ ] 如果存在此前的审计基线，比较新增、已解决和保留的问题；当已接受或保留的风险影响仍然重大时，继续报告这些风险。
- [ ] 仅在能够确认某项能力、限制、生命周期规则或受支持的简化方式时，才研究外部模式或框架的行为。
- [ ] 将当前形态与最简单且可信的替代方案进行比较，包括迁移风险、兼容性、回滚、团队影响和运维成本。
- [ ] 如果重写或引入新模式所产生的过渡复杂性大于其消除的复杂性，优先进行渐进式边界修复。
- [ ] 拒绝那些要求基于推测的规模、未经支持的未来变体，或在没有已证明缺陷的情况下替换现有有效惯例的建议。
- [ ] 仅当建议无法作为一个有界变更安全实施时，才纳入迁移顺序。

### 5. 验证发现并进行报告

- [ ] 至少通过一条依赖路径、调用路径、注册路径、公开契约或可复现的分析结果，验证结构性发现。
- [ ] 在确认违规之前，排除生成代码、框架惯例、有意设计的适配器、仅用于测试的架构以及有文档记录的例外情况。
- [ ] 对每个候选问题应用重要性和可接受替代方案门槛。要求在系统已有证据支持的规模上，存在具体的正确性、安全性、责任归属、部署、变更放大或持续维护影响。拒绝吹毛求疵、模式偏好、理论纯粹性、泛化的最佳实践、推测的规模，以及在当前权衡合理时仅仅不同的架构；当存在多种可行形态时，要求关注边界结果或约束，而不是某一种首选模式。
- [ ] 在每个问题的所需解决方案中加入一个直接相关的 Markdown 实践链接：优先使用当前的官方文档或规范；仅当官方来源无法解决该权衡时，才使用信誉良好的主要工程资料。打开并验证来源；该来源必须支持所提出的架构机制，而不只是问题类别。拒绝搜索结果链接、泛化的最佳实践文章和装饰性引用。
- [ ] 根据正确性、安全性、变更放大、部署耦合和持续维护成本，将问题分类为 `P0`-`P3`。
- [ ] 对每个问题包含受影响的边界、证据、具体后果、当前折衷方案为何不可接受、迁移风险以及最小安全下一步，同时允许使用等价的目标形态。
- [ ] 按前置条件和风险降低程度排列建议，将即时正确性修复与可选演进分开。
- [ ] 当无法在没有可信回退方案的情况下验证所需的运行时连接、边界证据或权威契约时，使用 `BLOCKED`；对于已有证据支持但尚未解决的正确性或安全边界缺陷、不安全的责任归属歧义，或 `P0/P1` 结构性风险，使用 `FAIL`；仅对于具有实质影响但不会阻塞的变更放大问题使用 `CONCERNS`；只有在没有已证明的架构缺陷会造成重大成本或风险时，才使用 `PASS`。
- [ ] 返回包含实际架构图、适配性评估、问题、局限性和残余结构性风险的判定结果。

## Fitness summary

| Dependency topology | PASS / CONCERNS / FAIL | ... |
| Physical structure and configuration | PASS / CONCERNS / FAIL | ... |

## Findings
| Priority | Problem | Evidence and justification | Required resolution |
|---|---|---|---|
| P0 / P1 / P2 / P3 | Concrete architectural defect | Boundary and evidence, material consequence at evidenced scale, migration context, and why the current tradeoff is not acceptable | Smallest safe outcome or boundary correction, migration and rollback constraints, and a verified `[practice reference](URL)` to official or primary engineering guidance; allow equivalent valid target shapes |

Use `None` when no candidate survives the evidence, materiality, fitness, and acceptable-alternative gates.

## Evolution order and residual risks
Prerequisite-aware recommendations, accepted exceptions, and blind spots.
