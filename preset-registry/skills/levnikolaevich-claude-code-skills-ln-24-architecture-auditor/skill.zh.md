# 架构审计员

**目标：** 对系统实际执行的架构进行只读审计。评估结构、依赖、契约以及跨组件所有权是否符合当前产品需求，不因模式名称或推测性的现代化改造而给予正面评价。判断原子性和资源所有权应归属何处；将局部查询、事务和数据资源的正确性交由专注于持久化的审查负责。

**执行契约：** 有序复选框是完成定义。内部将每一项标记为 `PENDING`、以具体证据证明的 `PROVEN`、以证明其条件不存在的证据标记为 `CLEARED`，或标记为存在缺口的 `UNPROVEN`；阅读、委派或工具失败都不能作为证明。每完成一个部分后重新核对各项。返回前解决所有 `PENDING`，并仅统计 `PROVEN` 和 `CLEARED`；将该技能的裁决和批准规则应用于每个缺口。
保留用户意图、范围和现有授权。继续执行已获授权的工作；仅针对尚未解决且具有重大影响的选择或所需的外部批准提出问题。根据实际风险调整深度，不得在未说明的情况下跳过检查。保留依赖关系和安全顺序；除此之外，为每项义务选择合适的验证方法。

## 工具路由

| 需求 | 首选工具 | 使用时机 | 备用方案 |
|---|---|---|---|
| 物理架构和声明架构 | 原生文件列表、清单文件、构建文件、配置和架构文档 | 确定模块、包、领域、层、入口点和部署单元时 | 根据已知入口点生成有针对性的仓库映射 |
| 符号和依赖拓扑 | Language server、编译器元数据或宿主原生代码智能工具 | 跟踪导入、调用、实现、路由、事件和循环时 | 缩小搜索范围，并直接检查定义及其使用者 |
| 运行时连线 | 注册代码、依赖注入、路由、启动配置和安全的运行时诊断 | 某个组件可能存在，但可能无法被发现或连接时 | 使用明确标注不确定性的静态跟踪 |
| 历史意图 | Git 历史、blame 和决策记录 | 当前例外或并行机制可能仍有有效理由时 | 当前行为和已记录的约束仍具有权威性 |
| 架构适配性 | 当前官方框架和平台文档 | 某项发现取决于受支持的扩展、生命周期、配置或边界行为时 | 基于一手来源的网络研究；否则标记为 `UNVERIFIED` |
| 定量结构 | 现有依赖、循环、复杂度或包分析命令 | 仓库已经定义了可靠的结构分析时 | 可复现的静态清单和调用路径证据 |

仅在图示能够阐明文字无法清晰表达的关系时使用图示。不得用生成图示来替代证据，也不得在审计期间修改代码或架构文档。

## 证据规则

- 可执行依赖、运行时连线和公共契约的权重高于预期中的图示或文件夹名称。
- 只有当循环或跨层调用造成具体的变更、所有权、测试、部署或故障成本时，才将其作为发现项。
- 模式合规本身不是目标；应根据产品复杂度、团队工作流和运营约束评估其适配性。
- 在将某项行为标记为泄漏或死代码之前，框架约定和生成的连线必须经过了解框架的验证。
- 只有当前存在的缺陷或可衡量的简化，才能为现代化改造提供正当理由，而不是新颖性。
- 明确的仓库边界规则定义预期约束；文档对其进行说明；从文件夹名称推断属于低置信度证据，不得单独据此认定存在违规。
- 先前的审计基线用于区分新增、已解决和已接受的技术债务。它不会让正在发生的正确性或安全风险消失。
- 共享的系统设计基线、当前状态、目标设计、决策、图示和迁移文档属于可选的意图证据。缺少这些内容本身不是缺陷；对于已实现状态，其存在也绝不优先于可执行行为。

## 检查清单

### 1. 发现实际架构

- [ ] 阅读仓库说明、架构文档、清单文件、入口点、部署定义以及配置所有权规则。
- [ ] 按仓库约定发现共享架构产物，区分系统设计基线与既有审计基线，并将每项归类为当前、拟议、已接受、已被取代、过时、相互矛盾或 `UNKNOWN`；不要要求任何特定的产物路径。
- [ ] 映射范围内的包、模块、领域、层、进程、数据存储、队列、外部系统和公共接口。
- [ ] 记录所有权以及独立构建、部署、扩展和故障边界；不要仅凭目录名或进程名推断服务边界。
- [ ] 识别主要的组织模型及任何竞争模型：以层为先、以领域为先、服务边界、插件边界或框架约定。
- [ ] 从入口点开始，经过编排、领域行为、持久化或集成，再到可观测结果，追踪具有代表性的关键流程。
- [ ] 将文档记录的当前状态、目标状态、已接受的决策和活跃迁移阶段与可执行结构进行比较；记录偏差和权威冲突，不要假设文档描述的就是实际运行的内容。
- [ ] 检查 Git 状态，避免将当前工作和用户无关的变更误判为既定架构。
- [ ] 保持审计为只读，并披露任何获准使用的诊断缓存或生成的分析产物。

### 2. 审计模式适配性与所有权

- [ ] 根据行为识别主要模式，并评估其问题适配性、完整性、一致性和有证据支持的维护成本；避免臆造数值评分。
- [ ] 检查抽象是否消除了真实的变化性，还是仅仅将直白的代码隐藏在接口、工厂、注册表或通用层之后。
- [ ] 检查层级方向、领域所有权、编排深度、副作用边界，以及策略是否仍与基础设施细节分离。
- [ ] 追踪跨组件事务、会话、连接、流、进程、订阅和后台工作的所有权所在；报告边界不明确的问题，但不要重复本地生命周期或事务正确性分析。
- [ ] 对每个会改变状态的关键流程，识别原子性所有者，以及如何在多个存储和消息之间避免部分失败、以幂等方式重试或进行补偿。
- [ ] 检查名称表明读取或看似纯粹的接口是否存在隐藏写入、广泛副作用、网络调用或违反其契约的生命周期所有权。
- [ ] 找出并行的架构机制、未完成的迁移、没有消费者的兼容路径，以及没有可信变化需求的扩展点。
- [ ] 检查故障处理和重试是否位于拥有该操作的层，而不是在各层之间重复或被吞掉。

### 3. 审计契约与依赖

- [ ] 检查公共 API、服务、事件、命令和持久化边界是否具有稳定的输入/输出模型，以及明确的错误、可空性、幂等性和兼容性契约。
- [ ] 检查共享实体或框架类型、缺失的边界模型、布尔模式、过多参数、不稳定的序列化或命名漂移是否造成耦合或契约歧义；如果共享模型是有意设计的稳定契约，不要强制要求 DTO。
- [ ] 使用已解析的内部边构建模块或包的依赖方向；在声明某条边不存在之前，考虑别名、重新导出、生成代码、反射、注册表、插件和运行时加载。
- [ ] 首先应用已配置的禁止/允许依赖规则；如果规则仅为推断得出，应报告推断出的模型及其置信度，而不要将其表述为策略。
- [ ] 识别禁止的导入、循环、不稳定的依赖方向、过高的扇入/扇出以及孤立的区域；使用结构指标定位候选项，然后应用下面的影响检查。
- [ ] 将循环和耦合发现追溯到其对变更范围、初始化、测试、部署、所有权或故障传播的具体影响。
- [ ] 检查生产者和消费者是否在事件名称、模式、版本、交付语义、顺序和注册方面保持一致。
- [ ] 检查物理结构中的领域内聚性、框架放置位置、杂物箱、重复的模块根目录、孤立包，以及位置掩盖所有权的文件。
- [ ] 检查配置边界中的类型化设置、组合根所有权、优先级和覆盖语义、启动验证、分散的环境读取、密钥所有权，以及配置是否泄漏到领域行为中。
- [ ] 验证运行时发现机制：路由、处理器、作业、命令、插件、中间件、序列化器和依赖绑定都必须完成注册并且可达。

### 4. 评估演进与替代方案

- [ ] 使用仓库证据识别当前架构痛点：重复的变更集、脆弱的测试、过大的影响范围、重复机制、发布耦合，或容易引发事故的所有权问题。
- [ ] 如果存在系统设计基线，验证其来源和时效性，然后将已确认的约束与实际行为进行比较。
- [ ] 如果存在先前的审计基线，比较新增、已解决和保留的问题；当已接受或保留的风险影响仍然重大时，继续报告这些风险。
- [ ] 仅在能够确认某项能力、限制、生命周期规则或受支持的简化方式时，研究外部模式或框架行为。
- [ ] 将当前形态与最简单且可信的替代方案进行比较，包括迁移风险、兼容性、回滚、团队影响和运维成本。
- [ ] 如果重写或引入新模式所产生的过渡复杂性多于其消除的复杂性，优先进行渐进式边界修复。
- [ ] 拒绝需要推测性规模、未经支持的未来变体，或在没有已证实缺陷的情况下替换现有有效约定的建议。
- [ ] 仅当建议无法作为一次有界变更安全实施时，才包含迁移序列。

### 5. 验证发现并报告

- [ ] 至少通过一个依赖路径、调用路径、注册路径、公共契约或可复现的分析结果，验证结构性发现。
- [ ] 在确认违规之前，过滤生成的代码、框架约定、有意设计的适配器、仅用于测试的架构以及有文档记录的例外。
- [ ] 应用实质性门槛：要求在已有证据所体现的规模上，存在具体的正确性、安全性、所有权、部署、变更放大或持续维护影响。拒绝品味偏好、理论纯粹性、通用实践、假设性规模和合理替代方案；要求关注结果或约束，而非偏好的实现方式。
- [ ] 外部修正应以版本匹配的官方契约为依据；对于尚未解决的权衡，使用一手工程来源。引用受支持的机制；对于本地缺陷，本地证据即可。
- [ ] 根据正确性、安全性、变更放大、部署耦合和持续维护成本，将发现分类为 `P0`-`P3`。
- [ ] 按前置条件和风险降低程度排列建议，将即时正确性修复与可选演进分开。
- [ ] 当无法在具备可信替代方案的情况下验证所需的运行时接线、边界证据或权威契约时，使用 `BLOCKED`；对于有证据支持但尚未解决的正确性或安全边界缺陷、不安全的所有权歧义，或 `P0/P1` 结构性风险，使用 `FAIL`；仅对重大的非阻塞变更放大问题使用 `CONCERNS`；只有在没有任何有证据支持的架构缺陷会造成重大成本或风险时，才使用 `PASS`。

## 自检

- [ ] **返回前进行核对。** 检查条目级证据、需求覆盖情况、矛盾、范围、结论以及适用的清理工作。修正报告或获授权的产物。复用有效证据；不要自动重新扫描仓库或重新运行成功的命令。仅针对相关变更、失败或未解决的证据重复检查。披露剩余缺口。

## 输出契约

使用用户的语言按以下顺序报告；保留全部五个字段，并且每项事实只陈述一次。简短结果可以每个字段占一行；省略空表格，不要复制链接的工件：

1. **结果：** 技能特定的结论及支持的结果。
2. **范围：** 已审查/更改的范围、排除项、基线和重要假设。
3. **证据：** 以下技能特定字段；区分事实、推断和未经验证的声明。链接工件；适用时使用表格。
4. **验证：** 检查/结果、无法获得的证据，以及适用的清理工作/外部状态。
5. **完成情况：** `Checklist: X/Y complete`；`Incomplete: None`，或列出每个 `UNPROVEN` 项的原因、对结果的影响和确切的后续操作；剩余风险和所需决策。

**技能特定证据：** 实际模块、边界、连接关系、依赖项、配置和关键流程；区分当前状态、目标状态、过渡状态和偏差。发现项需要包含优先级、受影响边界、证据、在当前规模下的后果、不可接受的权衡、迁移风险以及最小安全后续步骤；允许等价的目标形态。按照前置条件的顺序排列演进，并保留已接受的例外。
